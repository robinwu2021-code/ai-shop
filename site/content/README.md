## 一、官网是干什么的

**宣传站，不是说明书。**

受众是**还没入驻的商家**，他在这里停留 40 秒到 3 分钟，只想知道三件事：

1. **支不支持我这种店？**
2. **用起来方不方便？**
3. **要花多少钱？**

按这三个问题写，别的都往后放。

### 三条写法

**一、说「支持什么」，不说「怎么实现」。**
商家不关心系统怎么工作。
- ✅「生鲜、便利、烘焙、餐饮、美业、维修、宠物、药房都能开」
- ❌「同样一套系统，六种用法」—— 这是在夸我们的架构，他不关心

**二、说「你会这样用」，不铺流程。**
一句话一件事，能列成条就别写成段。
- ✅「忙不过来就下架，页面立刻停止接单」
- ❌「顾客侧的路径是浏览 → 下单 → 就近取货，不涉及跨仓调拨……」

**三、费率讲「有哪几种方式」，不讲「怎么算」。**
算法留给收费页，宣传页只要让他知道有哪几种收款、哪几种送达、大概多少钱。
- ✅「送达：到店自提 · 送货上门 · 快递 · 自提点代收 · 到店核销 · 预约上门」
- ❌「应结 = 毛收入 − 退款 − 佣金 − 履约服务费」—— 这是对账公式，不是卖点

**四、用店主的话，不用我们自己的词。**
需求文档与代码里的说法是准确的，写到官网上就成了门槛 ——
「个人主体免执照」，他要先猜「主体」是什么意思，才明白这句是在说他不用办执照。

| 我们自己人说 | 官网上写 |
|---|---|
| 个人主体免执照 / 免资质 | **没有营业执照也能开**，用个人身份就行 |
| 经营主体 | 身份（开店用什么身份）/ 商户 |
| 提交收款进件 | 交一次收款申请 |
| 自带客流 | 老客扫码进店 |
| 履约方式 | 怎么把东西交到顾客手上 |
| 经营范围 / 覆盖社区 | 能卖到哪几个小区 |

由 `lib/content.test.ts` 的「不出现内部术语」逐页拦着，报错里直接给替换写法。

> **功能清单不进宣传主线。** 它是销售支持材料，收在 `/capabilities/`，
> 从收费页底部进入。把 79 条功能铺在首页，读者一条都记不住。

## 二、目录结构 = 站点地图

```
content/
  sitemap.md              站点地图与每页的转化目标（先读这个）
  home/                   首页
  scenarios/              支持哪些店：总览 + 六类
  how-it-works/           怎么开店
  pricing/                收费与套餐
  capabilities/           功能总览（附录 · 销售支持）
  mini-program/           自有品牌小程序
  download/               顾客端下载
```

一页一个 `index.md`；六类各自一个文件。**文件路径即 URL**（`scenarios/fresh.md` → `/scenarios/fresh/`）。

## 三、文件格式

页首 YAML frontmatter + 若干 `##` 小节。每个小节可紧跟一个 ```yaml 块声明版式属性，其余是正文 markdown。

````markdown
---
title: 生鲜果蔬                    # <title> 与面包屑
slug: /scenarios/fresh/
description: …                     # <meta description>，60–120 字
audience: 社区果蔬店、菜店、水果店   # 内部用：这一页写给谁
goal: 免费开店                      # 内部用：这一页要促成的动作
---

## 卖完就下架，不做「预计三天后到货」
```yaml
type: hero
cta: [免费开店, 看看怎么算账]
```

正文段落。**加粗**、列表、表格都可以用。
````

### 小节 `type` 取值

| type | 版式 | 用在哪 |
|---|---|---|
| `hero` | 大标题 + 导语 + CTA | 每页第一节 |
| `prose` | 标题 + 正文 | 通用 |
| `timeline` | 有序步骤/时间轴 | 「一天是这样的」「开店三步」 |
| `list` | 加粗开头的要点列表 | 「你会这样用」 |
| `tags` | 词条云（`·` 分隔的一行） | 「这些店都能开」 |
| `solution` | 左右对照，用表格写 | 需要两栏并置时 |
| `cards` | 卡片网格（`###` 为卡标题） | 特色、六类入口 |
| `table` | 表格 | 价格、权益对照 |
| `faq` | 手风琴 + FAQPage 结构化数据（`###` 为问题） | 各页 FAQ |
| `cta` | 收尾行动区 | 每页最后一节 |
| `dark` | 与上一节相同版式但墨底 | 需要节奏变化时叠加：`type: prose, tone: dark` |

未识别的 `type` 按 `prose` 渲染 —— **加了新 type 而组件没跟上时，页面照常出内容**，不是白屏。

## 四、篇幅

## 五、数字不许手写：插值 token

费率、额度、试用天数**一律写成 token**，渲染时从真源取值。
手抄一份的后果是可预见的：运营在库里调了额度，官网还是旧数字，而没有任何东西会报错。

| token | 取自 | 现值 |
|---|---|---|
| `{{fee.ownedTraffic}}` | `SETTLE.commissionRate.MERCHANT_OWNED` | 0% |
| `{{fee.platformTraffic}}` | `SETTLE.commissionRate.PLATFORM` | 2% |
| `{{fee.fulfillPerItem}}` | `SETTLE.fulfillFeePerItemMinor` | ¥0.30 |
| `{{fee.settlePeriodDays}}` | `SETTLE.periodDays` | 7 |
| `{{plan.free.stores}}` `{{plan.pro.stores}}` `{{plan.chain.stores}}` | `sys_merchant_plan_def` 种子（V150） | 1 / 3 / 10 |
| `{{plan.pro.staff}}` `{{plan.chain.staff}}` | 同上 | 3 / 15 |
| `{{plan.trialDays}}` | 同上 | 14 |
| `{{site.name}}` `{{site.email}}` `{{site.merchantEntry}}` | `lib/site.config.ts` | — |

未知 token **原样保留并在构建时报错**，不静默渲染成空 —— 空白处最难被发现。

## 六、红线（写之前先看这一节）

1. **不承诺时效**：审核是人工的。可以写「表单十几分钟填完」，不许写「当天开张」。
2. **不出现到账、提现、T+N**：一期只记账、线下结算，支付链路本身还是桩。
3. **不写覆盖数字**：「已覆盖 X 个社区 / X 家门店」在有真实数字之前一个字都不放。
4. **未上线的能力必须带角标**：`对接中` / `规划中`。当前有 —— 微信/支付宝支付通道、
   微信订阅消息（对接中）；OCR 识别、线上提现、分拣单打印导出、对账与客户导出、
   iOS App（规划中）。**角标在销售转述时会消失**，所以话术材料里也要跟着标。
5. **活动只有四类**：店铺券 / 满减 / 限时特价 / 买赠。模型里没有百分比折扣、没有 N 件优惠。
6. **不写价格数字**：定价是商务决策，尚未拍板。统一写「联系报价」。
7. **禁用词，两类**：
   - **空话**：高效、赋能、一站式、打造、闭环、抓手、全方位、生态化 ——
     与竞品的同款说法无法区分，等于没说。
   - **营销腔**：别处没有、独家、超值、划算、神器、爆款、轻松搞定、一键搞定 ——
     **这一类最容易混进来，因为它读着像「写得好」。**
     商家要的是陈述句：你有什么、怎么用、多少钱。他不需要被说服，他在做判断。

   口语俏皮话同样不用（「老客回头不抽佣」「顺手做自提点」「账自己会算」）——
   写成「老客复购不收佣金」「承接社区自提点」「按周生成结算单」。
   两类都由 `lib/content.test.ts` 逐页拦着。
