## 0. 一句话

OpsKit 提供工单和审批的基础能力：业务流程定制、审批管理、接收业务提交的审批、**由审批流程里的执行节点触发业务执行**。near-pay 和 ai-shop 的全部业务审批都用 OpsKit 的流程；审批单、步骤、决定、执行结果都在 OpsKit，业务数据和业务动作本身留在业务系统。业务系统在 OpsKit 提供的 client 之上封装自己的审批网关，两边只经 HTTP 和 webhook 交互，没有构建期依赖。

## 1. 用户已定的规则（OpsKit 侧需要能表达）

| # | 规则 | OpsKit 表达 |
|---|---|---|
| U1 | 两个系统用同一套审批 | 同一账户、同一平台空间、同一套审批组件 |
| U2 | 允许本人提交、本人审批 | 模板 `rules.selfApproval=true`（作为**默认值**） |
| U3 | 审批统一进审批表 | 审批单全部在 OpsKit；业务侧只留 `approval_no` 关联 |
| U4 | 默认一人提交、一人审批 | 默认模板 1 步、`mode=ANY` |
| U5 | 按业务指定审批流 | 一个业务一条流程，在控制台「流程配置」改：审批节点 · 执行节点 · 审批人 · `when` 条件 · `selfApproval` · `crossStepExclusive` |
| U7 | OpsKit 提供工单和审批的基础能力：业务流程定制、审批管理、业务系统提交审批、**审批节点触发业务执行**；**业务系统封装审批调用，OpsKit 提供 client 封装** | §2 分工 · §5a 执行节点 · §5b client |

## 2. 分工

| 事 | OpsKit | 业务系统（near-pay / ai-shop） |
|---|---|---|
| **业务流程定制**：审批节点、执行节点、条件、版本 | ✅（控制台 + API） | 启动时登记默认流程（只在不存在时创建） |
| **审批管理**：审批单、待办、决定、审批人资格、本人审批规则、理由必填、历史 | ✅ | —— |
| 审批页面（审批中心 · 详情 · 通过 / 驳回 · 流程配置） | 只提供后端接口（契约 §3.2 P1–P16），**不做任何页面** | ✅ **ai-shop 自己做全部页面**（用户 2026-11-23 定）；near-pay 只放「去审批」跳转；b-app 调同一组接口 |
| **提交审批** | 接收 `POST /instances` | ✅ 经自己的 `ApprovalGateway` 封装提交（发件箱 → client） |
| **节点触发业务执行** | ✅ 流程走到执行节点时发事件、等结果、按成功 / 失败推进、失败可重试 | ✅ 注册执行动作（`ApprovalAction`），执行后回复结果 |
| **client 封装** | ✅ 提供：送审 · 撤回 · 接收事件（验签、去重、按 action 分发）· 回复执行结果 · 对账 | 在 client 之上包一层业务网关，业务代码不直接碰 OpsKit |
| 业务对象、业务数据、业务动作本身 | —— | ✅ |
| 对象在审批中被修改 | —— | ✅ 撤回；执行时版本不一致 → 回复失败（`STALE`） |
| 成员身份 | 联邦 + 目录 | ✅ ai-shop 提供令牌内省端点 + 目录同步 |
| 待办通知（站内消息） | 发 `task.created` 事件 | ✅ 收事件，推站内消息 |

## 5. 业务 → OpsKit 的调用

全部经 `opskit-connector`，写请求都带 `Idempotency-Key`。

| 场景 | 调用 | 关键参数 |
|---|---|---|
| 送审 | `POST /v1/workspaces/{ws}/instances` | `processCode`=模板代号 · `subject{type=bizType, ref, display{title, summary}}` · `fields`（模板 `when` 条件要用的，如 `amount`、`market`）· `scopes` · `onBehalfOf{externalRef=提交人}`；幂等键 `{bizType}:{ref}:{revision}` |
| 撤回（对象在审批中被编辑 / 提交人撤回） | `POST /approvals/{no}/withdraw` + `onBehalfOf=提交人` | 见 §7 A4 |
| 对账 | `GET /subjects/{type}/{ref}/history`（connector `Reconciler`） | 每日一次，处理 `PENDING_APPROVAL` 超过 24h 的 |
| 登记默认流程 | `client.ensureProcess`（底层 `PUT /workspaces/{ws}/approval-templates/{code}`） | 只在不存在时创建，见 §7 A2；含执行节点，见 A12 |
| 详情展示字段 | 送审时一并给 `facts` | 变更类要带改前值，见 §7 A3 |

## 5a. 执行节点：审批节点触发业务执行

**默认流程（每个业务一条，控制台可改）：**

```
草稿 ─submit─▶ 审批节点[1 步 · PERM:<权限码> · selfApproval=true]
                 ├─ 驳回 ─▶ 已驳回（终态）
                 └─ 通过 ─▶ 执行节点[action=<bizType>.apply] ─成功─▶ 已生效
                                                  └─失败/超时─▶ 生效失败 ─重试─▶ 执行节点
                                                                     └─放弃─▶ 已取消（终态）
```

> OpsKit 方案：`opskit/docs/design/24-方案重审-多宿主与执行节点.md`（A12 · A13 · A9 的结论都以它为准）。

| 项 | 约定 |
|---|---|
| 实现 | 执行节点 = OpsKit 的**外部确认门**，门上带 `action` 代号 |
| 触发 | 进入执行节点 → 事件 `instance.awaiting_confirmation{instanceNo, approvalNo, subject, action, gateEpoch, token, fields}` |
| 业务执行 | client 按 `action` 分发给业务注册的 `ApprovalAction`；业务先校验对象版本，再执行。**必须按 `ctx.idempotencyKey()`（`instanceNo:gateEpoch`）幂等**：执行成功但回复没送到时，OpsKit 会重投同一事件 |
| 回复 | 成功 → `CONFIRM`（可带回 `fields`），流程到「已生效」或下一节点；失败 → `REJECT` + 错误码 `code`（`STALE` / 业务错误码）+ 原因，流程到「生效失败」 |
| 重试 | 「生效失败」上有「重试」（重新进入执行节点、发新令牌，`gateEpoch+1`）和「放弃」（→ 已取消，终态）。能点的人：**提交人 + 前一个审批段按 PERM / ROLE / GROUP 配的审批人**；业务系统用应用凭证也可以。`process:manage` **不能**重试（OpsKit 批 1 实现如此） |
| 生效失败的列表 | 生效失败**不进待办**（那一步没有任务）。ai-shop 用 `POST /instances/query` 按状态（`failed_` 开头）查出来单独做列表 |
| 位置 | 执行节点可以放在任意两个审批节点之间（如「冻结额度 → 二审 → 出款」），一个流程可以有多个执行节点，每个对应一个 action |
| 超时 | 执行节点默认 10 分钟没有回复 → 视为失败、进入「生效失败」（防止业务丢事件后单子永远卡住；对账也会补） |
| 编译 | 连续的审批步骤合成一个审批段；没有 ACTION 的模板编译结果与现在逐字节相同，在途单不受影响 |
| 撤回 | 执行节点之后的审批段**不能撤回**（Q7 已定） |
| 补偿 | 执行节点已生效、后面的审批段被驳回时，**业务负责补偿**（Q8 已定）：`onFinished(REJECTED)` 带上已执行的 action 列表，业务按列表回滚。只有一个执行节点、且放在最后的默认流程不会遇到 |

## 5b. OpsKit client（OpsKit 提供）与业务网关（业务封装）

```java
// OpsKit 提供：新模块 opskit-approval-client（connector 之上，纯 JDK）
ApprovalClient client = ApprovalClient.builder()
        .baseUrl(...).workspace("ext:PLATFORM").credential(...).signingSecret(...)
        .action("np.credential_enable.apply", ctx -> credentials.applyApproved(ctx.subjectRef(), ctx.field("revision")))
        .onFinished(e -> links.onFinished(e))          // APPLIED / APPROVED / REJECTED / WITHDRAWN / CANCELLED，由 instance.transitioned 触发
        .build();

client.submit(Submit.of("np.credential_enable", subject, facts, fields, scopes, submitter), idemKey);
client.withdraw(approvalNo, submitter);
client.cancel(approvalNo, reason);                    // 应用级作废（A4）
client.handleWebhook(signatureHeader, rawBody);        // 验签 · 去重 · 未注册的 action / 他系统的单直接 200 · 分发 · 自动回复 CONFIRM / REJECT
client.reconcile(subjectType, subjectRef);

// 业务封装（near-pay、ai-shop 各一份）：业务代码只见到这一层
approvalGateway.submit("np.credential_enable", "CRD0042");   // 组装 subject/facts/fields + 发件箱 + client.submit
```

| client 要做的 | 说明 |
|---|---|
| `action` 注册与分发 | 业务只写 `ctx -> 执行逻辑`；正常返回即 `CONFIRM`（可带回 fields），抛 `ApprovalActionException(code, msg)` 即 `REJECT` + 错误码 |
| 他系统事件过滤 | 未注册的 action、`subject.type` 前缀不是本应用的事件，直接 200，不进台账、不记 WARN（解决 A10） |
| 去重台账 | 提供接口，由业务用 DB 唯一键实现，与业务执行同一事务 |
| 回复失败重试 | 回复本身失败时重试 3 次，仍失败则 webhook 返回 500，由 OpsKit 重投；令牌过期（409）视为正常结束 |
| 默认流程登记 | `client.ensureProcess(code, 默认定义)`：不存在才创建（A2） |
| 不依赖 Spring | 纯 JDK；Spring 适配（自动注册 `@ApprovalAction` Bean）放二期 |

## 6. OpsKit → 业务的回写

### 6.1 订阅的事件

| 事件 | 业务做什么 |
|---|---|
| `instance.awaiting_confirmation`（执行节点） | 见 §5a：client 分发给 `ApprovalAction`，执行后回复 |
| `instance.transitioned` 进入 DONE / CANCELLED 类别 | **最终结果只看这个**（client 转成 `onFinished`）：APPLIED → 徽标「已生效」；REJECTED / WITHDRAWN → 业务回到可编辑状态，记下理由；CANCELLED → 同上并提示原因 |
| `approval.completed` | **不用来判最终结果**：多段审批时每段通过都会发一次（带 `gateStatus`、`final`）。业务可不订阅 |
| `task.created` | 给候选审批人推站内消息「有 1 条待你审批」 |

### 6.2 接收方义务（照 host-integration §2）

验签（原始字节）→ **`subject.type` 不是本系统前缀（`np.*` / `shop.*`）的直接回 200、不记日志**（A10）→ 按 `approvalNo:roundNo` 去重（台账用 DB 唯一键，与业务推进同事务）→ 只推进自己的状态 → 处理中不同步回调 OpsKit。本系统的单但业务已不在等待态时，回 200 并记 WARN。上线前两边各跑一遍 `WebhookTck`。

### 6.3 回调地址

| 应用 | 地址 |
|---|---|
| `nearpay` | `{near-pay 内网}/internal/opskit/webhook` |
| `aishop` | `{ai-shop 内网}/internal/opskit/webhook` |

## 8a. 对接契约 v1 确认意见（ai-shop / near-pay → OpsKit，用户确认，2026-11-23 已发出）

> 契约：OpsKit 仓库 `docs/integration/对接契约-NEARGO.md`（v1-草案）。下面是按 ai-shop 现有代码核对后的意见。

### 透传（契约 §1）—— 同意，按现有做法落地

| 项 | 落地 |
|---|---|
| 位置 | `backend/shop-gateway` 照 `PayOpsPassThrough` 新增 `OpsKitPassThrough`：`/ops/opskit/v1/**` → OpsKit `/api/opskit/v1/**`，挂在 `AuthorizationFilter` 之后（要求有效运营会话），自己不判权限 |

### 内省端点（契约 §1）—— 同意字段，有 4 点要 OpsKit 知道（I3 的「展开 `*`」已被 §8b E5 取代）

| # | 意见 |
|---|---|
| I1 | ai-shop 新做 `POST /internal/opskit/introspect`（RFC 7662 + Basic），复用现有 `OperatorIdentityEndpoint` 的身份解析（`OperatorIdentityLoader`）。`sub` = 运营员工号，`name` = 姓名，`tenant` = `PLATFORM`，`exp` = 会话的 `expires_at`（30 天滑动），`perms` = 该员工的**全部**权限码（不按 `pay:` 过滤） |
| I2 | **`scopes` 不总是 `*`**：运营员工可以被限定到某个商户 / 社区 / 自提点（`StaffScopes`）。不限定的发 `["*"]`，限定的发 `merchant:{no}` / `community:{no}` / `pickup:{no}`。因此业务送审时 `scopes` 必须带 `merchant:{no}`，否则被限定的员工看不到 |
| I3 | **通配授权**：ai-shop 今天只有超级管理员 / 通配角色的 `*`，没有 `pay:*` 这类授权。ai-shop 的匹配规则是「去掉末尾 `*` 后做字符串前缀匹配」（不按冒号分段）。批 1（C6）之前，内省端点把 `*` 展开成全部权限码；C6 之后直接发 `*`。ai-shop 承诺以后的通配授权只写在冒号边界上（`pay:*`），与 OpsKit 的分段展开一致 |
| I4 | **缓存时长**：ai-shop 会话改角色、登出后 5 秒内生效（`revokePoll 5s`，身份缓存 30–60 秒）。OpsKit 按 `min(exp, 5 分钟)` 缓存内省结果，意味着撤权后最多 5 分钟仍能审批。建议对 ai-shop IdP 把缓存上限配成 60 秒；做不到就在契约里写明这个延迟 |
