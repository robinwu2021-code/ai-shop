## 一、测试目的

1. **链路真的通**：在真实部署（.80 的 OpsKit + 换包后的 ai-shop-v2、nearpay-prod）上，验证「业务送审 → OpsKit 审批 → 执行节点回调 → 业务生效 / 未通过回调」整条链路，以及运营员工令牌经 ai-shop 透传、内省、角色映射到 OpsKit 的身份链。
2. **每项业务行为对**：第一批 T1–T12 每一项在启用审批后，送审时机、申请内容、审批步骤、生效结果、未通过的回退都与方案一致。
3. **旧路被封住**：启用审批后，原来的「直接决定」入口不能绕过审批中心。
4. **开关可控、可回退**：不启用时行为与现网完全一样；任一项出问题，从启用列表去掉即回到原流程。
5. **不伤现网**：上线与联调过程中现网业务（门店、收银、开放 API）可用，测试数据可识别、可清理。

**不在本次范围**：第二批、第三批（代码在包里但不启用）；T3 提现（near-pay 没有提现申请入口）；ops-web 界面（静态页在 .166，未发新版前只做后端联调，界面联调另排）。

## 二、测试环境与前提

| 项 | 要求 |
|---|---|
| 部署 | 按 [README](./README.md) ①–④ 完成：两库迁移已执行（ai_shop_ume 到 V691、nearpay_prod 到 V138）、两服务已换包、OpsKit 已加回调并重启 |
| 初始开关 | `SHOP_OPSKIT_ENABLED_SUBJECTS`、`NEARPAY_OPSKIT_ENABLED_SUBJECTS` 都为空 |
| 测试账号 | 一个持超管角色的运营员工号（用户提供，**口令不进聊天**；令牌只在服务器或本机临时文件里用）。本次允许「本人提交、本人审批」 |
| 测试对象 | 每项只用**专门的测试对象**：测试商户 / 测试门店 / 测试申请单。名称统一带「联调」或 `OPSKIT-TEST` 前缀，记下单号，便于事后清理 |
| 调用方式 | 运营端接口：`https://<ops 入口>/ops/...` 或在 .80 上直连 `http://127.0.0.1:18180/ops/...`，带 `Authorization: Bearer <otk_ 令牌>`；OpsKit 页面接口经 ai-shop 透传：`/ops/opskit/v1/workspaces/ext:PLATFORM/...` |
| 查库 | 只读查询；.80 没有 mysql 客户端，用 .61 mysql9 容器内只读会话（或用户执行） |

**审批操作（所有项通用）**：

```
GET  /ops/opskit/v1/workspaces/ext:PLATFORM/approvals/{approvalNo}      → mine.taskNo、mine.canDecide、facts、steps、pipeline
POST /ops/opskit/v1/workspaces/ext:PLATFORM/approvals/{approvalNo}/decide
     {"taskNo": "<mine.taskNo>", "decision": "APPROVE" | "REJECT", "reason": "联调"}
POST /ops/opskit/v1/workspaces/ext:PLATFORM/todos/query  {"origin":"PROCESS"}   → 待办里有 approvalNo、subject
```

审批单号从业务侧关联表查：ai-shop `approval_link`、near-pay `pay_approval_link`（按 `subject_type` + `subject_ref`，取最大 `revision`）。

## 四、测试用例

### S0 冒烟（不启用业务）

| # | 用例 | 步骤 | 预期 |
|---|---|---|---|
| S0-1 | 服务健康 | 两服务启动日志、健康检查 | ai-shop `Started ShopApplication`、Flyway `validated`；near-pay `Started PayApplication`、`[schema] database at V138 matches` |
| S0-2 | 现网不受影响 | openapi 会话要求的三条 | `tpay.neargo.ai/openapi/v1/ping` 401；`/oms-api/pay-ops/v2/*` 401；`/h5/s/ume-breakfast` 200 |
| S0-3 | 流程登记 | ai-shop 日志 `[opskit] 流程 shop_… 已创建 / 已存在`；near-pay 同 `np_…` | ai-shop 9–10 个、near-pay 第一批 7 类都有；重启后为「已存在」、版本不变 |
| S0-4 | 身份链 | 用测试运营令牌 `GET …/me` | 返回该员工角色与 `approval:decide`（超管另有 `process:manage`、`approval:view:all`） |
| S0-5 | 回调可达 | OpsKit 日志 `webhooks=2`；在 OpsKit 投递记录里看两应用回调无 4xx/5xx | 回调地址 18180 / 18093 可达、验签通过 |
| S0-6 | 未启用时行为不变 | 任选一项（如门店开通）走原入口 | 与换包前一致（未送审、直接决定照常可用） |

### S1 低风险项

**T1 门店开通**（`shop.store_opening`，二级：审核 + 条件复核，审批人 `merchant:apply:audit`）

| # | 用例 | 步骤 | 预期 |
|---|---|---|---|
| T1-1 | 送审 | 选测试门店（`status=ACTIVE` 且 `operational_review` 为空）→ `POST /ops/stores/{no}/operational-review/submit` | 门店 `PENDING_OPEN/PENDING`；`approval_link` 一行 `PENDING`，有 approvalNo |
| T1-2 | 申请内容 | 看审批详情 | facts 含门店、主体、「营业状态 待开通 → 营业中」；复核步 `SKIPPED` |
| T1-3 | 本人通过 | decide APPROVE | 关联 `APPLIED`；门店 `ACTIVE/APPROVED/MANUAL`；pipeline 执行节点 DONE |
| T1-4 | 驳回与重提 | 另一测试门店送审 → REJECT | 门店回到 `PENDING_OPEN/REJECTED`；关联 `REJECTED`；再提交 = 新修订、新审批单 |
| T1-5 | 旧入口被拒 | `POST …/operational-review/decide` | 业务码 82101「这项审核已改由审批中心处理」 |

**T10 入驻审核**（`shop.merchant_entry`，二级，审批人 `merchant:apply:audit`；拟定结果随送审冻结）

| # | 用例 | 步骤 | 预期 |
|---|---|---|---|
| T10-1 | 「通过」只送审 | 代填测试申请 `POST /ops/merchants/apply-on-behalf`（名称带「联调」）→ `POST /ops/merchant/apply/{no}/audit` `{approved:true, serviceScope, communityNos}` | 申请单 `REVIEWING`；`mch_entity` 无新主体；关联 `PENDING` |
| T10-2 | 申请内容 | 审批详情 | facts 含主体、类型、行业、联系人、服务范围、社区 |
| T10-3 | 通过建主体 | decide APPROVE | 申请单 `APPROVED`、`audited_by=OPSKIT`；按冻结的服务范围 / 社区建出主体 |
| T10-4 | 驳回不走审批 | 另一测试申请 audit `{approved:false, reason}` | 当场 `REJECTED`，不送审 |
| T10-5 | 期间被改 → STALE | 送审后改动该申请单（如补材料让 version 变）再通过 | 执行节点失败 `STALE`，进「生效失败」，不建主体 |

### S2 near-pay 资料类（只用测试商户）

送审入口：通用 `POST /pay-ops/v2/approvals`（SY01）在启用后路由到 OpsKit，返回状态 `OPSKIT`；账户转移在**建转移单时**送审。执行人记 `OPSKIT`，旧审批中心不产生新单。

| 项 | 启用名 / 旧类型 | 级别 / 审批人 | 测试要点 |
|---|---|---|---|
| T11a 法币进件平台审核 | `np.onboarding_review` / `ONBOARDING_REVIEW` | 一级 · `pay:onboarding:approve` | 通过 → `review(APPROVE)`，**送渠道仍要单独点**；驳回 → REJECT；撤回 / 放弃 → REQUEST_MORE |
| T11b 商户资料修订 | `np.merchant_profile` / `MERCHANT_PROFILE_APPROVE` | 二级 · `pay:merchant:approve` | facts 为逐字段「当前 → 本修订」，账号 / 证件只显示后四位；改法人 / 代表人 / 银行 / 账户 / 结算字段时出现复核步 |
| T12a 门店关联变更 | `np.store_association` / `STORE_ASSOCIATION_CHANGE` | 三级 · `pay:store:approve` | 两步；执行时重检负债评估；未通过 → 清空待变更 |
| T12b 渠道账户转移 | `np.channel_account_transfer` / `CHANNEL_ACCOUNT_TRANSFER` | 三级 | 建转移单即送审；执行重检事实哈希，不符 → STALE；未通过 → 转移单 REJECTED / CANCELLED 持久化 |
| T12c 门店换绑 | `np.store_rebind` / `STORE_BINDING_REBIND` | 一级 · `pay:store-binding:approve` | 通过 → 换绑；未通过 → 清空待换绑 |

每项至少：送审 1 次 + 通过 1 次 + 驳回 1 次 + 「期间被改 → STALE」1 次（能造则造）。

### S3 密钥（**启用前问用户**，建议用测试密钥 / 测试凭据版本）

| 项 | 启用名 | 要点 |
|---|---|---|
| T5 凭据版本启用 | `np.credential_enable` | 三级两步；版本 VERIFIED 后提交 → 通过后 `enable(…, OpsKit 审批号, OPSKIT)`；已 ACTIVE 重投视为成功；未通过保持 VERIFIED |
| T6 平台密钥启用 | `shop.platform_key_enable` | 三级两步，审批人 `sec:key:enable`；修订 = 生效版本×16+状态序号；别的版本被启用 → STALE；两人控制（启用人 OPSKIT ≠ 录入人）自然满足 |

### S4 动钱（**每项启用前单独问用户**，金额用最小值、对象用测试单）

| 项 | 启用名 | 要点 |
|---|---|---|
| T2 退款复核 | `np.refund_review` | **先发布退款复核规则**（无 ACTIVE 规则 = 全部复核），且只与 `shop.pay.refund.review` 一起开；两步；通过 → APPROVED 并在提交后派发；驳回 → 释放预占 |
| T4 佣金规则发布 | `np.commission_rule` | 新建版本先 `enabled=0` → 两步通过后启用；**生效时间必须设在审批完成之后**，否则 `EFFECTIVE_TIME_PASSED`；审批人码 `pay:fee-plan:approve` 默认只授超管 |
| T7a 结算放行 | `shop.settle_release` | 系统 BLOCKED 的批次自动送审；运营「放行」改为送审；驳回 = 继续挂起、原因记入批次 |
| T7b 结算放款 | `shop.settle_payout` | 两步；通过后 `releaseBatch`（三道闸重检）生成放款记录并写 critical 审计 |
| T8 积分资金池 / 补充计划 / 调账 | `shop.points_pool_request`、`shop.points_adjustment` | 提交即送审（计划任务自动提交补充）；原「审核」入口 `request-review`、`adjustment-review` 返回 82101 |
| T9a 商城退款 | `shop.mall_refund` | **审批通过 → 运营再点执行**：第一次点「退款通过」→ 返回 `approvalStatus=SUBMITTED`；审批中再点 → PENDING；通过后**同样内容**再点才执行；改金额 = 新审批 |
| T9b 商城线下核款 | `shop.mall_offline_payment` | 同 T9a，拦在「确认收款」；已有该动作记录的不拦 |
| T9c 套餐线下付款 | `shop.plan_offline_payment` | 只在商城开关全开时登记；运营确认只送审，冻结确认内容与填单人；通过后以填单人身份 confirm |

### S5 通用场景（在已启用的低风险项上做）

| # | 场景 | 做法 | 预期 |
|---|---|---|---|
| G-1 | 回调重复 | 在 OpsKit 对同一事件人工重投 | 业务只生效一次（去重台账 / 执行幂等） |
| G-2 | 生效失败 → 重试 / 放弃 | 送审后让对象变化（造 STALE），在「生效失败」页签里重试、再放弃 | 重试仍 STALE；放弃后关联关闭，业务回到可重提 |
| G-3 | 对账补结论 | 暂停业务服务回调接收（或在 OpsKit 标记投递失败）后通过，再等对账任务 | 对账任务补上结论，只生效一次 |
| G-4 | 开关回退 | 从启用列表去掉 T1 重启 ai-shop | 门店开通回到原流程（submit 不送审、decide 可用）；已在途的审批单不受影响地走完或失败 |
| G-5 | 改流程不影响在途 | 在审批流程页改 T1 模板（如加一步），对已在途的单通过 | 在途单按旧版本走；新单按新版本 |
| G-6 | 重启不覆盖流程 | 改模板后重启 ai-shop | 日志「已存在」，模板保持运营改过的版本 |
| G-7 | 本人审批 | 全程用同一员工号提交与审批 | 允许（`selfApproval=true`）；旧业务里的「申请人 ≠ 审核人」不拦（执行人是 OPSKIT） |

## 五、停止条件（出现即停，按 README 第四节回退）

- 现网冒烟任一条失败（门店页非 200、开放 API 不是 401、收银报错）。
- 服务启动失败、迁移校验失败、OOM 或 .80 可用内存低于 800 MB。
- 业务数据出现非预期变化（审批未通过却生效、生效两次、改到非测试对象）。
- OpsKit 回调持续失败（同一事件重投 3 次仍 5xx）。
- 用户要求暂停。
