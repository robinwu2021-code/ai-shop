# 渠道办理与门店支付方式实施计划

> 执行时使用 superpowers:executing-plans 或 superpowers:subagent-driven-development。按任务提交、验证，再部署 UME166。

**目标**　完成多渠道申请、分渠道办理和开通落库，让 App 门店、运营端和 H5 读取持久化的门店设置与有效展示结果。

**架构**　NearPay 持有渠道办理、账户、产品、门店策略和有效展示数据。ai-shop 校验店主与门店权限并转发业务请求。Flutter App、运营端和 H5 使用同一套支付方式码和渠道映射。交易按当前资格校验并选择渠道。

**基线**　MySQL 9、Flyway、NearPay Spring Boot、ai-shop Spring Boot、Flutter 商户 App、NearPay 运营端与 H5。执行前重新获取三仓目标分支，核对 UME166 实际制品与数据库版本，保存差异及待合并提交清单。

**设计依据**　[流程评审](./channel-flow-review.md)和[数据库评审](./channel-storage-review.md)。

## §0 交付约定

- 首次申请默认勾选地区内全部可办理的正式渠道，包含人工渠道。保存过草稿便沿用选择。每条渠道独立拥有申请、处理结果及时间。
- 商户账户和产品授权复用现有表。运营和 App 商户区分渠道审核通过、等待接入、实际开通以及停用。
- 门店显式选择继承或自定义，默认继承。自定义按支付方式及正式／测试类别收窄，底层继续保留原渠道产品约束。多个渠道均支持同一方式时，由 NearPay 按既有规则选路。
- 运营端查询和新建接口独立，重复判断由脚本负责。保存、审核、派发、停用等使用明确的业务命令。
- 使用现有可信租户及执行分区。变更使用版本控制和原有权限。新增迁移使用分支上未占用的 Flyway 版本，已执行迁移保持原校验和。

## §1 接口与数据依赖

| 消费方 | 入口及传递内容 |
|---|---|
| Flutter 申请 | 现有主体工作区选项查询和 `channel-requests`。服务端返回 `code/name/selectable/mode/state/reason`，提交传所选渠道、原请求号、资料版本及已有材料引用 |
| Flutter 商户详情 | ai-shop `GET /biz/pay/v2/merchant-channels`。NearPay 返回渠道办理状态、账户接入状态、审核与开通时间、授权产品及方式映射 |
| Flutter 门店设置 | ai-shop `GET/PUT /biz/payment/store-method` 经现有内部 collection-methods 接口转发。新增显式 `mode` 和 `enabledMethods[{paymentMethodCode,test}]`，沿用 `requestNo/expectedVersion`。读接口同时返回商户允许范围、门店持久化选择、有效方式、不可开原因及 `eligibilityRevision`，新版提交回传此版本 |
| NearPay 运营端 | 沿用商户渠道总览、进件及账户产品命令。门店在已有策略入口单独维护方式选项，App 与运营端共用策略版本 |
| H5 | 沿用扫码详情及付款会话接口，通过持久化结果返回方式、公开渠道显示字段及测试标记。过渡期由同一结果生成旧的 `payMethods/testMethods/sandboxMethods` 字段 |

旧客户端只提供产品级设置时继续按旧契约解释。新旧客户端针对同一门店保存时共享版本，旧格式对新方式配置无法无损表达时返回需要更新客户端的明确错误。

#### 3.1 门店读取与提交的核心逻辑

现有 `StoreCollectionMethodService.view` 从门店绑定找产品，再由 `CollectionPolicyService.preview/decide` 叠加商户和门店策略。商户已开通但未绑定到本店的方式在这条链路上不可见。现有 `save` 用读接口结果筛选选项，`saveStore` 再检查商户产品范围。新版将这两处共用的资格规则集中到 NearPay 的门店策略服务，读取使用批量装载或已持久化结果，提交在事务中按当前数据校验。

| 步骤 | GET 门店设置 | PUT 门店设置 |
|---|---|---|
| 1. 授权和归属 | ai-shop 验证操作者及当前门店，NearPay 从可信租户、执行分区和当前门店关联取商户。运营端同样检查数据范围 | 重新校验上述信息，使用当前归属。门店换绑给另一商户时返回冲突，页面刷新后再操作 |
| 2. 商户渠道上限 | 同时读取商户策略及已核验、可收款账户下的已开通产品，按目录展开全部支付方式。返回商户允许的方式和渠道产品范围 | 按当前商户策略、账户状态、产品授权和方式映射重新核验。客户端回传的商户号、渠道列表和授权结果仅作展示或并发提示 |
| 3. 门店范围 | 叠加本店绑定、入口与环境限制，再读库中已保存的继承模式和选项。每项分别返回 `configuredEnabled`、`effectiveEnabled`、`editable`、`blockedReason`，并保留对应渠道产品 | 显式继承时使用本店当前可用全集。自定义时新增或重新开启的方式必须属于当前允许范围。已有但暂不可用的选择可原样保留或移除，保持有效关闭。实际保存后须至少有一种有效方式，沿用现有最后一种方式保护 |
| 4. 版本与结果 | 返回门店策略版本 `version` 和上游资格版本 `eligibilityRevision`。商户已授权但本店未绑定的方式以不可启用状态展示 | 校验 `expectedVersion` 及新版客户端提交的 `eligibilityRevision`。商户策略、账户、绑定或入口已经变化时返回版本冲突、刷新后重试。写入方式配置和展示更新或失效状态后回读 |

上游资格版本对应当前归属、商户策略、账户及产品、目录、绑定和入口。服务端应将该版本纳入提交事务的并发校验。对应变更与版本更新同事务提交，保存持有共享的版本校验点或等价的原子写入条件，避免核验后、写入前被另一事务改变。已有旧客户端仍按原产品契约及门店版本提交，NearPay 以当前商户资格重新校验。请求超时重试沿用原请求号，已执行的相同命令按现有幂等规则回读，禁止重复写入。

有效方式以候选渠道产品为单位求交后再按 `支付方式码 + 正式／测试类别` 分组。例：商户允许 A 渠道的信用卡，门店只绑定 B 渠道，即使方式码相同也不可开启。A、B 都有资格时，A 停用只移除 A 的候选路由。H5 快速读取与当前资格版本相符的持久化结果。资格变化后旧结果失效，支付发起继续检查实时资格和交易条件。

- [ ] 服务端覆盖商户允许但未绑定、渠道产品交集不成立、部分渠道停用、正式与测试不混用，以及已保存选择受限后恢复。
- [ ] 集成测试覆盖读到旧商户资格后提交、提交校验与商户停用并发、跨商户换绑、重复提交、旧版 App 提交、App 与运营并发保存。验收数据库状态和 H5 可见范围。

### 6. 运营和商户变更后的门店联动

- [ ] 统一收口运营侧和商户侧已授权的渠道变更。运营开通、暂停账户或产品，调整商户允许范围、门店绑定和入口时，以及商户侧申请或补件最终导致授权生效时，均从 NearPay 同一个变更入口更新展示。商户提交申请只更新办理状态，实际开通才更新可收款范围。商户现有权限继续生效。
- [ ] 按变更范围定位受影响的门店。产品或账户变更按商户和现有绑定定位。新增方式也检查当前商户下满足绑定和入口条件的继承门店，覆盖原先没有该展示项的情况。App 与运营端修改单店设置时只更新该店。
- [ ] 每次按最新商户授权、门店设置、绑定与入口规则重建有效列表。停用、关闭或解绑与旧结果失效同事务提交。批量重建按版本写入，连续变更以最新有效版本为准。

| 变更 | 继承门店 | 自定义门店 |
|---|---|---|
| 新开通支付方式 | 本店具备绑定和入口条件后自动显示 | 沿用已保存选择，新增方式进入可选列表 |
| 暂停渠道、关闭产品或撤销绑定 | 移除该渠道的候选产品。没有其他有效渠道时隐藏该方式 | 同样收窄有效列表，保留原生效意愿，设置页显示受限原因 |
| 恢复渠道或产品 | 满足本店条件后重新显示 | 先前已选择且仍符合门店设置的方式恢复；其他方式保持关闭 |
| 同一支付方式有多个渠道，其中一个停用 | 有其他有效渠道时继续显示，并更新可用渠道列表 | 已选该方式且有其他有效渠道时继续显示，原有产品授权上限仍适用 |
| 商户在 App 或运营在后台修改单店设置 | 按最新模式更新本店的 App 和 H5 | 按最新选择更新本店的 App 和 H5 |

验收使用同一商户下的继承门店和自定义门店。依次验证开通、停用、恢复、双渠道剩单渠道和单店保存，核对持久化设置、App、运营端与 H5。批量重建期间验证旧列表失效，连续变更后验证旧任务无法覆盖最新结果。

## §3 发布到 UME166

1. **发布前核对**　记录三仓提交、线上 JAR 哈希、静态目录、数据库迁移版本和关键开关。备份当前制品、配置及受影响数据，冻结回填范围。确认测试门店和渠道归属以运营接口当日回读为准。
2. **NearPay 先上线**　执行增量 schema 迁移并部署向后兼容的服务端。先开启变更更新与回填，旧展示入口继续服务。用少量真实归属门店对比新旧四端结果，逐批补齐其余记录并核对缺失及失效数量。
3. **部署 ai-shop**　部署新版接口转发，确保旧 App 仍可登录、查商户和使用已有收款功能。实际制品从兼容线上版本构建，核对并保留并行发布的变更。
4. **部署前端并切换数据源**　部署 NearPay 运营端和 H5 静态资源，安装指向 UME166 的 Flutter 验收包。灰度打开门店与 H5 持久化读取，以同一门店、同一入口复验。通过后扩大范围并按发布流程交付 App。
5. **回滚**　发现配置外放、归属冲突、方式缺失或无法支付时，停止扩大切换。先恢复该入口的兼容读路径及前端，保留已写入的方式配置。旧路径若无法表达新的方式级限制，先关闭该门店受影响的入口，待修复后恢复。必要时按备份恢复相应服务制品。加法 schema 保留，历史订单继续按已冻结路由处理。
