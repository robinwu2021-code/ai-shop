# 渠道办理、门店设置与四端展示评审

状态为设计评审与开发清单。源码基线为 ai-shop `5a3f5a0c2`、NearPay `c761ed8fa`、Flutter 商户 App `0363d56e1`。线上耗时沿用[原交接记录](./README.md)，本页的接口缺口与行为判断来自源码核对。

## 一、目标流程

商户提交资料时选择渠道，首次默认选中当前地区所有可办理的正式渠道，包含运营人工代办渠道。商户可取消部分选项，重开草稿保留原选择。提交后，每个渠道独立办理。渠道通过后记录审核依据和账户，核验凭据并开通产品后进入商户可配置范围。门店默认继承商户，店主按支付方式选择，H5 读取该店有效设置。

运营端和 App 商户详情按渠道展示办理及开通状态。App 门店与 H5 按支付方式展示。四端消费 NearPay 同一份渠道、产品和支付方式映射，保留环境和支付场景。测试配置沿用现有环境规则。

## 二、逐项评审

| 环节 | 已有实现与证据 | 缺口 |
|---|---|---|
| 申请时选择渠道 | Flutter 的 `EntityChannelSelectPage` 多选并提交 `channel-requests`，主体工作区已有渠道选择和资料采集。NearPay 的 `EntityProfileService.options` 返回是否可选与 API／人工模式 | Flutter 从已有 `channelMaterials` 初始化选中项，首次为空。Flutter 和 NearPay 都维护固定的三渠道列表。主体初次提交、补件修订及后续新增需要共用服务端可办规则。商城旧 `pay-service/apply` 是主体来源申请，表单不携带选中渠道，应明确入口职责 |
| 分渠道办理 | `pay_entity_channel_request` 已按资料版本、渠道和环境持久化。主体通过后，`EntityChannelPreparation` 分渠道准备或复用进件草稿，记录进件号及失败重试。渠道草稿和运营审核、API 派发、人工结果登记亦已存在 | 运营入口应从商户提交的渠道清单进入办理。需要展示尚未生成草稿、准备失败、待运营办理、待渠道、待补件等状态。现有准备任务按批次执行，页面须展示单渠道阻塞原因。人工渠道应复用同一条申请记录关联登记结果 |
| 结果落库 | `OnboardingApplicationService` 已保存渠道批准、决定时间和账户候选。 `ChannelAccountService.intake` 幂等承接候选，初始为待核验。账户启用和产品开通各有命令，产品授权写入 `pay_merchant_product` | 现有商户视图对所有账户行一律使用 `OPEN` 分类，部分待核验账户在运营列表被写成停用。已有同渠道账户可能遮住另一个进行中的申请。需要按申请号或可核实的关联归并，分别显示渠道通过时间、接入完成时间和当前运营状态 |
| 商户与门店继承 | `CollectionPolicyService` 已支持商户允许范围、门店 `INHERIT/OVERRIDE`、版本与审计。门店能力仍由本店有效绑定决定 | App 门店页从本店绑定倒推候选，商户已开通但尚未绑定的产品无法解释。全选会自动改为继承，容易误把固定选择变为自动接收新产品。需要明确继承或自定义，由 App 和运营端编辑同一配置 |
| 支付方式映射 | PAY 目录已有产品和支付方式关联表 `pay_product_payment_method`。运营产品目录支持为一个产品配置多个方式 | 商户渠道视图返回产品名但缺方式明细。 `StoreCollectionMethodService` 对每个产品取第一个方式，App 门店页本地映射名称并按产品保存，H5 则消费去重后的方式数组。一个产品有多个方式及同方式有多个渠道时，当前契约无法表达门店独立选择与对应路由 |
| H5 展示 | H5 读取扫码及会话接口返回的付款方式和测试标识，选路已检查账户、绑定、产品、入口及资格 | 扫码页通过 `RouteSelectionPolicy.available` 重算，同一入口的完整 `readiness` 可按每个候选产品反复执行。App 门店页反查这一缓存，造成缓存过期时体验不一致。展示应读同一份门店有效设置，发起交易时校验实时路由、金额及风险 |

## 三、状态与映射口径

每条渠道请求应可定位到主体、资料版本、渠道、环境以及对应进件。办理状态包括待平台审核、待办理、待补件、渠道处理中、审核通过或驳回，接入结果包括待核验、待绑定凭据或开产品、已开通及已停用。展示由已落库事实派生，按各渠道独立显示，各渠道分别记录通过与开通时间。现有渠道、账户和产品表继续提供业务事实。

统一映射由 NearPay 返回，基本维度为 `paymentMethodCode`、名称、`channelCode`、`productCode`、环境及适用场景。运营和 App 商户视图可含脱敏账户标识，H5 使用公开方式标识和可展示渠道信息。相同支付方式可有多个渠道产品，同一产品也可对应多个支付方式。前端使用方式码和可信环境显示及提交，PAY 负责选择符合条件的账户和产品。

门店有效展示取商户已开通且允许的方式、本店有效绑定、店内选择及 H5 入口支持范围的交集。未绑定的商户方式在设置页说明原因。继承门店在新方式具备绑定和入口资格后随商户更新，自定义门店保留自身选择。运营停用及绑定撤销需及时反映到新的 H5 读取和下单。建议显式区分继承与自定义，存量产品策略需要按实际映射验证兼容性。

## 四、开发清单与验收顺序

| 顺序 | 服务端开发 | 端上开发 | 验收 |
|---|---|---|---|
| 1. 统一渠道选择 | 扩展现有主体工作区选项查询，提供地区、渠道是否可办理、已有办理状态、API／人工类型及显示顺序。提交校验实际选中集合，复用现有渠道请求表和幂等规则 | Flutter 读取服务端选项。首次默认全选可办渠道，保留已保存草稿与取消项。运营代办使用同一选项和规则 | 两个 API／人工渠道可一起提交。取消的渠道不生成请求，重复提交只保留一份 |
| 2. 统一运营办理 | 为现有运营工作台关联渠道请求、草稿、进件和失败原因。复用准备、审核、派发、查证及人工结果命令 | 运营按渠道逐个办理，显示当前动作及错误。App 商户展示对应进度 | 一个渠道通过时另一个仍可待补件。单渠道重试不重复送件，也不阻塞同商户其他渠道 |
| 3. 落库并对齐开通视图 | 核对候选、账户、凭据和产品的接入顺序与回读。扩展商户渠道视图，归并真实状态、时间和方法映射，批量加载账户产品 | 运营和 App 商户共同显示申请进度与开通情况，按渠道可追踪 | 有 MID 但待核验时显示待开通。实际开通后可回读时间及产品。进行中的同渠道申请仍可查看 |
| 4. 门店设置与继承 | 复用现有门店策略、绑定和版本控制。支持显式继承与自定义。核对现有产品级策略能否表达方式级选择，必要时扩展方式粒度并设计兼容读取 | App 门店按方式展示，并列出当前可用渠道、不可开原因和测试标记。运营查看或维护同一份配置 | 同一产品的多个方式能分别配置，同一方式多个渠道能正确展示。继承随商户变更，自定义保留选择。两个端并发保存返回版本冲突 |
| 5. H5 与门店对齐 | 提供同源有效配置读模型。目录、绑定和策略按请求复用，入口条件按范围一次求值。实际支付继续验证实时资格 | H5 消费同一方式码和展示字段。App 门店用同源结果显示收银台可用性 | 关闭方式、停用账户或撤销绑定后，新收银页与门店页口径一致。正式和测试匹配正确，展示耗时分别测冷、热请求及 SQL 次数 |
| 6. 存量验收 | 核对存量渠道账户、原审核依据、门店绑定与策略。保留原已开通结果，按需用独立运营 API 查询或新建 | 以交接中的 Oscar 门店回归四端流程，记录每个渠道各自的状态 | 支付测试按目标渠道产品获得渠道受理和有效支付入口，支付状态仍以真实结果为准 |

步骤 1—3 先落实申请及开通事实，步骤 4—5 再更换门店和 H5 读模型。首轮以请求内共享数据和批量读取作为性能实现方向。冷请求具体 SQL 数量和耗时需在实现验收时采样，原交接中的约 7.3 秒作为对照。

待在接口设计中落实两项规则。第一项是“同一方式多个渠道”默认由 PAY 选路，门店界面是否需要独立指定某个渠道另行定稿。第二项是自定义门店迁移时如何把既有产品选择转换为方式选择，需要对一个产品含多种方式的存量配置逐项校对。

运营脚本仍使用独立的查询与新建 API，流程和重复执行判断留在脚本。业务状态转换继续使用明确命令。参见 [Oscar 同步执行交接](../oscar-channel-sync-2026-11-16/README.md)。
