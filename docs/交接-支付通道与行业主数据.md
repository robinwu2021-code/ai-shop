## 五、刚开始、没有结论的 ❓

### 5.1 多门店

**只调研了一步，就有一个关键发现**：

`usr_merchant_store` **已经存在**（`V36`，另一个会话建的），但它是
「店铺**门面资料**」（公告 / 营业时间 / 地址 / 主推商品），
且 **`UNIQUE (merchant_no)`** —— **一个商家一行，不是多门店**。

所以现状是：**一个商家 = 一个店**。门店属性散在两处：

| 在 `usr_merchant` | 在 `usr_merchant_store` |
|---|---|
| `name` / `logo` / `address` / `open_hours` / `store_code` / `service_scope` / `service_city_code` | `announcement` / `open_hours` / `address` / `featured` |

⚠️ **`address` 与 `open_hours` 两张表都有** —— 这本身是个待清理的重复。

真要做多门店，要回答的问题（**都没答**）：

| 问题 | 为什么难 |
|---|---|
| 进件是按主体还是按门店？ | 收付通的二级商户号按**经营主体**发。多门店共用一个号的话，分账分不到具体门店 |
| 订单归属哪一级？ | `ord_sub_order.merchant_no` 现在指主体。改成门店的话，结算、积分、评价全要跟着改 |
| 积分开关按主体还是门店？ | 四级串联的 L3 现在是 `usr_merchant.points_enabled` |
| 自提点与门店的关系？ | `cmt_pickup_point.owner_ref` 的 `STORE` 现在指 `merchant_no` |

**建议**：不要在当前迭代顺手做。它会穿透订单、结算、积分、履约四个域。
建议单独出一份 ADR，先定「主体 / 门店」的边界，再动模型。

### 5.2 「经营范围」的语义没确认

用户提到「经营范围」，但库里现有的 `service_scope` 是
`COMMUNITY / CITY / PLATFORM` —— 那是**服务覆盖范围**（这家店的货能被谁看到，ADR-009），
**不是营业执照上的经营范围**。

两者都可能是需求，**没确认要哪个**：

| 理解 | 现状 |
|---|---|
| 服务覆盖范围 | ✅ 已有 `service_scope` + `usr_merchant_community` |
| 营业执照经营范围（文本） | ❌ 没有。进件资质在 `usr_merchant_apply.qualifications`（JSON） |

## 七、环境备忘

```bash

cd backend && mvn -o dependency:build-classpath -pl shop-app \
  -Dmdep.outputFile=/tmp/cp.txt -DincludeScope=runtime
DB_URL='jdbc:mysql://127.0.0.1:3306/ai_shop?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=UTC&characterEncoding=UTF-8' \
DB_USER=shop DB_PASS=shop MIG_DIR=$PWD/shop-app/src/main/resources/db/migration \
java -cp "$(cat /tmp/cp.txt):<classes>" FlywayRun migrate
```

**跑迁移前先 `mysqldump` 备份。** 上次备份在 scratchpad（会话结束后可能没了）。
