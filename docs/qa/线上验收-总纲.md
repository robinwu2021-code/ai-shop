## L1 这是什么

在**已上线的腾讯云环境**上跑一轮功能验收。不是单元测试、不是 mock 联调——
测的是「真 nginx + 真 MariaDB + 真短信通道 + 桩支付」这一套组合下，
三端各自还剩多少条路是通的。

**执行顺序按用户要求：B 端 → C 端 → 平台端。**
但数据依赖是反的（见 §四），所以 B 端用例里有两处必须跳到平台端才能继续，已在用例中标出。

## L3 三条硬约束（决定哪些用例现在跑不了）

### ① 支付是桩，且桩的开关也没开

`OrderServiceImpl.pay()` 无条件返回 `{"payChannel":"STUB","prepayId":"stub_<orderNo>"}`
（[OrderServiceImpl.java:629](../../backend/shop-core/src/main/java/ai/neargo/shop/trade/service/impl/OrderServiceImpl.java:629)），
唤不起任何收银台；`WX_PAY_ENABLED` 未设（默认 false），`SHOP_PAY_STUB` 也未设。

**订单会永远停在 `WAIT_PAY`，直到有人打回调。** 唯一能推进的入口是
`POST /callback/pay/stub`，body `{"outTradeNo":"<订单号>","transactionId":"任意","sign":"stub-secret"}`
（`shop.pay.stub-secret` 未在 env 覆盖 → 就是默认值 `stub-secret`）。

**这个端点 nginx 没有反代**，公网打不到，只能在机器上执行：

```bash
ssh soukmind-tx 'curl -s -X POST localhost:8081/callback/pay/stub -H "Content-Type: application/json" -d "{\"outTradeNo\":\"ORDER_NO\",\"transactionId\":\"T1\",\"sign\":\"stub-secret\"}"'
```

返回 `SUCCESS` 即订单转 `PAID`。**所有「支付之后」的用例（履约、核销、售后、结算、评价）都靠这一步**，
在用例里统一记作「**执行付款桩**」。

### ② 验证码是真短信，没有万能码

`SHOP_SMS_STUB=false`（真走阿里云）、`SHOP_OTP_FIXED` 未设（无预设码）。
所以 **C 端和 B 端登录都要一个能收短信的真手机号**，并受限流约束：

| 闸 | 值 |
|---|---|
| 同号发码间隔 | 60 秒 |
| 单号每日上限 | 10 次 |
| 单 IP 每小时 | 20 次 |

**建议**：验收窗口内临时给 `shop-app.env` 加 `SHOP_OTP_FIXED=888888` 并重启，
测完删掉。代价与风险要先确认——它是一把能登进任意手机号的万能钥匙
（`FixedOtpGuard` 只在 `prod` profile 拦，当前 profile 是 `api,ops`，**拦不住**）。
**这条需要你拍板**，用例默认按「真手机号」写。

### ③ 演示商家登录不进 B 端

DevSeeder 建了 `mch_entity` / `mch_account` / `mch_store`，但**没建 `usr_user`**——
`U-DEMO-1` / `U-DEMO-2` 只是一个字符串，没有手机号可以登录。

所以 **B 端不能「用演示商家登录看看」，必须从入驻走一遍**：
手机号登录 → 提交入驻 → 平台端审核通过 → 才有 `/biz/**` 的作用域。
这也是为什么 B 端用例 TB-03 之后要跳到平台端 TP-10。

## L3 四、跨端主链路（用例之间的依赖）

三份用例各自独立可读，但真正能验证系统的是这一条串起来的路。**顺序不能换**：

```
[B] 手机号B 登录 → 填入驻（个人主体，免资质）
        ↓
[平台] bd 账号 → 入驻审核 → 通过           ← B 端在这里被卡住，必须切过来
        ↓
[B] 建商品 → 上架 → 铺到社区 C0001
        ↓
[C] 手机号A 登录 → 绑社区 C0001 → 看到这个商品 → 加购 → 下单（自提点 PP0001）
        ↓
[运维] 执行付款桩 → 订单 PAID              ← 支付桩，见 §① 
        ↓
[B] 工作台待办 +1 → 分拣 → 发货到自提点
        ↓
[C] 订单详情看到取货码
        ↓
[B] 核销台输码 → 核销成功 → 订单 COMPLETED
        ↓
[C] 写评价（总分 + 三维度）
        ↓
[平台] 结算单生成 · 评价出现在评价治理 · 归因显示「自带客流」
```

**任一环断了，后面的用例直接标「阻塞」不要硬试**——硬试出来的失败会掩盖真正的断点。

## L4 五、验收之外必须上报的三件事

这三条不是用例，是这轮准备工作里查出来的**线上问题**，跟功能验收无关但更急：

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | **公网可用 `admin/admin123` 登进超管** | `POST https://www.hxmall.top/ops/auth/login` 实测返回 `perms:["*"]`，`mustChangePassword:false` | 任何人可改费率、批提现、封商家。`shop-app.env` 自己的注释写着「生产环境务必关闭」，而它开着 |
| 2 | **ops 面与 C/B 面同机同域** | profile `api,ops`，nginx 无 IP 白名单 | 与 S8/`DeploymentProfileTest` 的设计原意相反（部署 README §8.2 已记，未处理） |
| 3 | **`/callback/pay/stub` 用默认共享密钥** | `shop.pay.stub-secret` 未覆盖 = `stub-secret` | 目前靠「nginx 没反代 /callback」侥幸挡住。哪天 nginx 加一条通配 location 就变成「知道订单号就能白拿货」 |

第 1 条建议在验收开始前就处理：要么关种子重建运营账号，要么至少把 `admin` 改密并给 ops 加 IP 白名单。
**但关种子会把演示数据一起带走**，那三份用例的前置就全变了——所以先定这个，再开跑。
