积分能被商家接收并向平台兑付 —— 它是**平台的负债**，不是营销数字，

### 要做

   - `usr_point_account`：`user_no` 唯一、`balance`、`total_earned`、`total_used`、`expiring_soon`、`expiring_at`

2. `ord_sub_order` 补列：`points_deduct_amount`、`points_used`、`points_earn`、`points_granted`

### 注意

`points_granted` 是**幂等标记**（防重复核销重复发分）。
[契约漂移清单](契约漂移清单.md#a-服务端内部语义泄漏进契约复议时建议删)里已记录它「不该下发到端上」，

# 第二批：结构不匹配（补列解决不了，要重新对）

## T-9　卡包：`UserCard` ↔ `mkt_user_coupon` 映射不成立

**类型**：需决策

`mkt_user_coupon` 是**优惠券领取记录**（`coupon_no` / 领取时间 / 核销时间），
而契约的 `UserCard` 是**卡包**：储值卡余额、次卡剩余次数、卡面、有效期 —— **一列都没有**。

**两个选项**：

- (a) 卡包独立建表 `mkt_user_card`（`card_no`、`goods_no`、`balance_minor`、`times_left`、`expire_at`、`currency`）
- (b) 明确一期不做卡包，从契约删除 `UserCard` 类型与 `/mp/card/mine` 接口

选 (b) 要确认 C 端「我的卡包」页面一并下线。

## T-10　结算：账单粒度 vs 明细粒度

**类型**：需决策

库里 `stl_bill` 是**一个子订单一条**（`sub_order_no` + gross/commission/net）——这是分账明细。
契约的 `SettleBill` 是**一个商家一个周期一张**（`periodStart`/`periodEnd`/`orderCount`）——这是账单。
两者不是同一个东西。

**两个选项**：

- (a) 新增周期账单表 `stl_settlement`，`stl_bill` 降为其明细（改名 `stl_split_detail` 更准）
- (b) 改契约：B 端直接读明细，周期聚合在服务端做，删掉 `SettleBill` 的周期字段

推荐 (a)：对账与开票都按周期走（平台端 P-12.2.2 开票申请就是按 `period` 的），
明细粒度撑不起这些场景。

# 第三批：命名与口径统一（非阻塞，但拖着会一直付利息）

## T-11　金额列命名统一

**类型**：需决策　**影响面**：全部迁移文件与实体

现在库里**两套写法并存**：`ord_*` 用 `xxx_amount`，`mkt_*`/`stl_*` 用 `xxx_minor`，
而契约统一 `xxxMinor`。三方各一套。

`_minor` 携带口径（最小货币单位整数），`_amount` 不携带 —— 后者会让人以为可以是小数。
建议**统一到 `_minor`**，写一个迁移改 `ord_order` / `ord_sub_order` / `ord_item` 的列名。

改了之后 `scripts/gen-model-align.mjs` 的 `COLUMN_ALIAS` 里
`goodsMinor`/`freightMinor`/`discountMinor`/`payableMinor`/`paidMinor` 五条要删掉。

## T-12　其余 21 组命名不一致

**类型**：需决策

完整表见[领域模型对齐清单 §四](领域模型对齐清单.md)（共 26 组，其中 5 组金额别名由 T-11 覆盖）。典型的几处：

| 契约 | 库 | 说明 |
|---|---|---|
| `verifyCode` | `pickup_code` | 同一个取货码两个名字 |
| `cUserNo` | `user_no` | 契约特意加 `c` 前缀区分三个账号池 |
| `expireAt` | `end_at` | 出现在 3 个实体上 |
| `desc` | `description` / `note` | 同一个语义两个库列名 |

**不改也能跑**（ORM 映射一次即可），代价是此后每个人都要记住两套名字，
且那张映射表本身会成为新的漂移点。建议至少统一 `verifyCode` 与 `expireAt` 这两个高频的。

平台端后端覆盖率只有 0.6%（178 条里实现了 1 条），**现在改成本最低**，
再往后每实现一个接口就多一处要改。

# 建议的执行顺序

```
第一批：T-2 ~ T-8 ✅ 已完成 ｜ T-1（积分）待做
                      ↓
第二批（先决策后动手）：T-9 T-10
                      ↓
第三批（一次性批量改名）：T-11 T-12
                      ↓
第四批（契约侧）：T-13 T-14 T-15
```

第一批是纯增量（建表 / 加列），互不冲突，可以多人并行。
第三批要碰已有列名，**必须等第一批全部落地后再做**，否则会与在途的迁移冲突。
