# 网关接口验证清单

状态：2026-11-19 首版；同日 C 端接入网关后更新。底表是 [网关接口清单](网关接口清单.md)（三端共 2027 个入口，由生成器从源码出），
本文按「运营端 → B 端 → C 端」的顺序，把每一端、每个业务对象**已经验证到哪、还差什么**列出来，并列出要完成的开发与对接。

## 一句话

清单已经形成，并且与两处事实对过：与运行时登记的入口逐条相同；生产网关索引里的 1579 条全部在清单里、判权类别零差异。
对齐下来最大的三个差：**餐饮与服务业整块没有部署**（共 337 个入口）、**C 端还没有指向 v2 的端**（索引与公网入口已有）、
**所有登录之后的验证都还没做**。

## 清单本身可信吗

| 核对 | 结果 |
|---|---|
| 与运行时登记的入口比（默认构建、测试配置下 Spring MVC 实际登记的 1343 条三端入口） | 清单缺 0 条；权限式不一致 0 条 |
| 与生产网关索引比（网关版本写进正式库的 1579 条：运营端 630、支付运营面 10、B 端 765、C 端 174） | 生产有而清单没有 0 条；判权类别不一致 0 条 |
| 清单里有、生产网关里没有 | 运营端 17 条、B 端 390 条，逐类原因见下面各端 |

清单比运行时多出来的部分，是带条件装配的入口（模块开关没开）和插件里的入口（默认构建不带）。

## 验证分四层

每个对象都按同样的四层来验，下面各表里的「验证到」指到了哪一层：

| 层 | 验什么 | 怎么验 |
|---|---|---|
| ① 清单 | 入口在清单里，权限要求与源码一致 | 生成器 + 与运行时比对（已做） |
| ② 入网关 | 生产的网关索引里有这一条，判权类别一致 | 与生产索引导出比对（已做） |
| ③ 未登录 | 经公网入口不带令牌访问：该 401 的 401，该 404 的 404，公开的 200 | curl，不需要账号（部分已做） |
| ④ 登录后 | 用真实账号走一遍：有权限的能用、没权限的被拒、要调下游的调得通 | 要正式账号，**全部未做** |

C 端已做的 ③（公网）：`/shop-api-v2/mp/goods` 不带令牌 200；`/mp/order/list` 不带令牌 401；不存在的地址 404；
从 `/mp/` 用 `..` 绕到 `ops`、`internal` 404。只抽了这几条，没有把 174 条逐条探过。

「已入网关」对 C 端的含义比另外两端窄：网关只定位、可以按条停用，**不判登录与权限**。
C 端整条链在网关上是放行的，要不要登录由业务代码判。清单里「要登录 / 不用登录」取自 c-app 的接口声明：
215 条里 97 条要登录、35 条不用登录、83 条端上没有声明（其中 41 条是餐饮与服务业插件的入口）。
**这 83 条是 C 端对齐时要逐条确认的**：后端有入口、端上没有声明，要么是端上漏了，要么是这个入口不该对 C 端开放。

## 这份清单没有覆盖的

三端之外的入口不在清单里：内部入口 `/internal`（166 条）、库存服务自己的 `/api`（82 条）、终端 `/terminal`、开放接口 `/open`、
收银台 `/checkout`、回调等。它们不经三端的网关链，要不要纳入网关是另一个决定。

## 怎么更新

- 接口清单：`python3 scripts/gen-gateway-api-inventory.py`，改了入口或权限注解后重跑（已挂进生成文档的闸门）。
- 生产状态一列：取自 `docs/api/gateway-prod-index-*.tsv` 里最新的一份。生产上的网关换了版本或开关之后，重新导出一份放进来再重跑。
- 本文是手写的：验证每推进一层，改对应那一行的「验证到」。
