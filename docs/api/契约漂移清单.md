## 决策 2：C 端后端端点不在契约里（35 → 33）

后端实现了一批 C 端契约没有的端点。分三类处理：

### 2a. 同一功能、两边路径不同 —— 必须二选一

| 功能 | c-app | 后端 | 说明 |
|---|---|---|---|
| 我的券 | `GET /mp/coupon` | `GET /mp/coupon/mine` | 后端更明确（区分「可领的」与「我的」） |
| 一键再来一单 | `POST /mp/order/{orderNo}/reorder` | `POST /mp/store/{merchantNo}/rebuy` | **资源锚点不同**：按订单复制 vs 按店铺常买复制，是两种语义，要先定清楚做的是哪个 |
| 退货运单回填 | `POST /mp/order/{orderNo}/return-express` | `POST /mp/after-sale/{afterSaleNo}/ship` | 同下 |
| 上升平台裁决 | `POST /mp/order/{orderNo}/dispute` | `POST /mp/after-sale/{afterSaleNo}/escalate` | 同下 |

> **售后的资源锚点是核心分歧**：c-app 把售后挂在订单下（`/mp/order/{orderNo}/after-sale`），
> 后端把售后建成独立资源（`/mp/after-sale/{afterSaleNo}`，含 list / detail / cancel / escalate / ship / reasons）。
> 后端的建模更对 —— 售后单有自己的生命周期和单号，`AfterSale` 类型在 shared 里也已经是独立实体。
> **✅ 2026-08-06 已按此对齐**：`AfterSale` 加上 `afterSaleNo` 成为独立实体，
> C 端 `fillReturnExpress` / `raiseDispute` 改挂到 `/mp/after-sale/{afterSaleNo}/ship|escalate`，
> B 端 `mHandleAfterSale(orderNo, agree, reply)` 拆成 `mApproveAfterSale` / `mRejectAfterSale`
> 两个动词、两条路径（与后端一致，也让「谁被调用了」在日志与权限里能分开看）。
>
> 顺带说清为什么这个建模更对：一个订单**可能先后发起多次售后**，
> 挂在订单下用 orderNo 寻址，第二次申请就没法表达了。
>
> 剩下的 `我的券` 与 `一键再来一单` 两条**仍待定** —— 后者两边语义都不一样
> （按订单复制 vs 按店铺常买复制），要先定做的是哪一个，不是改个路径的事。

## 决策 3：B 端与平台端没有契约文件（B 端 ✅ 已解决）

`/biz/**`（后端 19 条）和 `/ops/**`（后端 8 条）都没有 openapi 契约，守卫只能退化成
「前端 ↔ 后端」直比。**这一档最容易烂掉** —— 两边都没有第三方约束，谁改了对方都不会知道。

**✅ B 端已解决**：新增 `b-app/scripts/gen-openapi.mjs` → `docs/api/openapi-b.yaml`（46 条），
守卫已纳入。**但它的覆盖面窄于 C 端那份，这是有意的**：
C 端有独立的 wire 入参类型（`api/requests.ts`，ADR-007 §5），能连 requestBody schema 一起生成；
B 端没有 —— 入参散在 `contract.ts` 的位置参数里（`mQuote(requestNo, price)`），
从签名反推 JSON body 只能靠猜，**猜出来的契约比没有契约更坏**。
要补齐，先给 b-app 建 `src/api/requests.ts`。

**⬜ 平台端仍缺**：`/ops/**` 后端 8 条，ops-web 是 Next.js，未纳入守卫。

## 审查（2026-08-06）：宽响应体的字段必要性

> 起因：评审提出「有的返回字段过多，是否都有必要」。
> 方法：把最宽的响应类型（C/B 端 10 个类型 186 字段、平台端 13 个类型）逐字段
> 与**消费侧代码**（pages/components/stores + 组件库）做引用比对。api/mock 层不算消费 ——
> mock 造数据是为了满足类型，不代表有人在用。

**结论：186 个字段里 180 个有真实消费（97%），响应体宽是业务宽，不是冗余。**

> **决定（2026-08-06）：6 个零引用字段全部保留，本轮不动。**
> 它们不构成正确性问题，删除要连带改 mock 与三份生成文档；
> 而后端尚未实现这些端点 —— 等后端启动时**在同一处一起定**，比现在改一遍、
> 届时再对一遍便宜。下面的定性结论保留作为那次复议的输入，勿重新论证。

零引用的 6 个逐一定性如下 —— 三类，届时处置不同：

### A. 服务端内部语义泄漏进契约（复议时建议删）
