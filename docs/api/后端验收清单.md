# 后端验收清单（行为规格）

> 2026-08-06 ｜ 拒绝规则与状态机由 `npm run gen:spec` **从 mock 代码抽取**，不是人写的清单。
> 契约（OpenAPI）定**形状**，本文定**行为**——两者合起来才是完整的实现依据。

对照：[三端与后端对照](三端与后端对照.md) ｜ [C 端契约](openapi.yaml) ｜ [B 端契约](openapi-b.yaml) ｜ [项目词典](../requirements/项目词典.md)

---

## 为什么需要这份东西

OpenAPI 能表达「`expressNo` 是必填字符串」，表达不了：

- `PREPARING` 不能直接跳 `COMPLETED`
- 驳回售后**必须**填理由，同意则不必
- 核销要校验三件事，其中一件是「这单属不属于本自提点」
- 极速退只对**仅退款**成立，退货退款走这条就是把货和钱一起送出去

这些是**行为**。目前它们唯一可执行的定义在 mock 里——后端照着形状实现完，行为对不对没人知道，只能等线上出事。所以把 mock 的行为导出成验收标准：**mock 拒绝的输入，后端必须同样拒绝；mock 允许的迁移，后端必须同样允许。**

## 怎么用

1. 实现某个端点前，先在下表里找它的方法名（`mShip`、`applyAfterSale`…），看它有哪些拒绝条件
2. 写完后端后，对照状态机表检查迁移约束
3. 错误码可以另定（本表只给语义），但**拒绝与否不能变**

## 三条最容易实现错的

| 规则 | 错误实现的后果 |
|---|---|
| **驳回售后不改订单状态** | 置回已完成后，用户的「申请平台介入」入口消失，争议无处可去 |
| **极速退只对 `REFUND_ONLY`** | 退货退款也秒退 = 货没回来钱先出去 |
| **拆单后一单只属一家** | 按「订单含本店商品」筛会把别家的单也捞出来，商家看到别人的生意 |

### 订单状态机（后端必须一致，非法迁移要拒绝）

| 当前状态 | 允许迁移到 |
|---|---|
| `WAIT_PAY` | `PAID` · `CANCELLED` |
| `WAIT_OFFLINE_PAY` | `PAID` · `CANCELLED` |
| `PAID` | `FULFILLING` · `COMPLETED` · `REFUNDED` · `CANCELLED` |
| `FULFILLING` | `COMPLETED` · `REFUNDED` |
| `COMPLETED` | `REFUNDED` |
| `REFUNDED` | **终态** |
| `CANCELLED` | **终态** |

> 共 7 个状态。**不在表内的迁移必须报错**，不能静默成功 ——
> 静默成功的后果是订单卡在一个谁也没预料到的状态里，前端界面直接空白。

## 计算规则（这些没法从 throw 里抽，单独列）

| 规则 | 定义 | 依据 |
|---|---|---|
| **结算公式** | `应结 = 毛收入 − 退款 − 佣金(按客流档) − 履约服务费(按件)` | `SETTLE`，值见[规则表](../requirements/需求矩阵-三端.md#七之二交易规则常量唯一事实源) |
| **拆单** | 一次结算按 `merchantNo` 分组建子订单，共享 `payGroupNo`，一次支付付掉整组 | `createOrder` |
| **退款三件事** | 改状态 + 回收已得积分 + 退还已用积分，**必须一起做** | `settleRefund()` |
| **配送费** | 满额免配送，未满收固定费 | 规则表 |
| **称重差价** | 生鲜按标称预扣，称重后多退少补 | `strategies/pricing/weighed` |
| **活动叠加** | 同类活动取最优、不重复叠加；券与满减可叠加。**由结算侧统一算**，别在活动模块各算各的 | B-10.5 |
| **归因** | 带 `merchantNo` 进店 → `trafficSource=MERCHANT_OWNED`（佣金 0%），否则 `PLATFORM` | 平台端 P-9.1 |

## 售后状态机（与订单状态机是两条线）

```
APPLIED ──同意·仅退款────→ REFUNDING ──────────────────────────→ REFUNDED
        ──同意·退货退款──→ REFUNDING ──填运单号──→（同态，记 returnExpressNo）
                                     ──确认收货──→ REFUNDED
        ──驳回──────────→ REJECTED ──用户上升──→ ARBITRATING ──平台裁决──→ REFUNDED / 保持
        ──用户撤销 / 超时─→ CLOSED
```

约束：

- `fillReturnExpress` 只在 `REFUNDING` 且 `RETURN_REFUND` 可调；`raiseDispute` 只在 `REJECTED` 可调；
  `mConfirmReturn` 只在 `REFUNDING` 且已有 `returnExpressNo` 可调
- **同意后没有「等寄回 / 已收货」两个独立状态** —— 都是 `REFUNDING`，
  是否已寄回看 `returnExpressNo` 有没有值
- **售后全程不改订单状态**：订单保持它原本的状态，退款到账才迁到 `REFUNDED`。
  订单状态里没有 `REFUNDING` 这个值
- 所有售后动作按 `afterSaleNo` 寻址，不是 `orderNo`——一笔订单可能有多次售后

## 维护约定

- 改了 mock 的拒绝条件或状态机，跑 `npm run gen:spec` 重新生成
- **不要手改标记之间的内容**——它会被下次生成覆盖
- 后端实现与本表冲突时：先确认是 mock 错了还是后端错了，改对的那一边，再重新生成
