# 经营实体映射与开店合同（T01）

日期：2026-11-14。已核对源码；消息 v2 为待实现合同，不表示新接口已部署。

| 商家端产品名称 | 当前真实字段／来源 | 规则 |
|---|---|---|
| 经营实体（用于本轮开店选择） | `StoreCreationAccessService.Source.entityNo`、`/biz/merchant/store-creation-context` sources | 当前商家主体及其门店额度／权限，复用实体以此作为建店真源 |
| 独立运营组织（可选管理关系） | `/biz/app/operating-entities` 的 `operatingEntityId`，表 `mch_operating_entity` | 账号独立组织，与旧 entityNo 不是别名，不能把此 ID 填入建店 entityNo |
| 公司／商业登记资料 | `legalSubjectId`，独立组织可关联经验证的 `mch_entity.entity_no` | 法定登记资料及验证状态，不等于支付渠道已开通 |
| 门店 | `storeNo` | 行业、套餐授权、业务数据与门店支付资格分别核对 |
| 支付签约账户 | `MerchantChannel.payMerchantNo` 及 PAY 可信来源映射 | 不等于 entityNo 或 operatingEntityId，新店不自动继承其他店开通状态 |

用户提出的“经营实体对应平台商户”作为产品表达，由已有建店主体 entityNo 承担；不删除或改名后台独立组织模型。本轮不新增未经核对的组织主键映射，不修改表数据。

## 已有建店能力

- 首店／新实体：现有 quick-start 及幂等结果恢复。
- 已有实体新增：现有 branch 建店，来源由 store-creation-context 返回，canCreate 与额度由服务端判定。
- 当前 App 是行业→资料→（实体→渠道）→确认。目标改为资料→行业与免费方案→实体→确认；渠道选择移至建店后的收款设置，不自动勾选并启用。
- 免费初始化使用已发布目录与原初始化服务；不得凭前端“免费”标签授予套餐。选择的付费方案另走购买生效链路。
- 门店设置现有合同应逐分区复用；没有真实写入能力的部分明确只读／待接入，不使用原型内存保存冒充成功。

## 消息合同身份字段

账号流 scope 使用 environment、tenantNo，并按场景附 storeNo、entityNo、chainNo；`operatingEntityId` 仅在真实独立组织关联场景提供。原草案中含义不明的 operatingEntityNo 不进入冻结合同。PAY 商户号只用于对应后端映射，不直接成为 App 鉴权范围。

统一消息文件：`app-events-v2.openapi.json`、`app-events-v2.schema.json`、`app-events-v2-registry.json`。18 个明确规则定义事件、场景、功能、资源类型、Handler、缓存失效和可选提醒；禁止业务写操作。eventId 只用于唯一标识、幂等、日志，不按其文本推断业务动作。

v2 只冻结合同，`/biz/app/events` 尚未实现。当前可用仍是 v1 `/biz/payment/events`，当前权限、store header、游标和帧格式不改。

## 建店名称增量

quick-start 新增可选 entityName（1–100字符），省略时沿用店名。store-creation-context 返回 entityNameSupported=true；旧服务未返回时前端保持店名默认。重试不能用新实体名覆盖已有待补件实体；不同名称返回冲突。只改名称不改变渠道或认证状态。当前为本地实现，尚未部署。

## 消息恢复快照（合同，未部署）

新增 `/biz/app/messages/snapshot`，返回标准成功信封内的 `schemaVersion/messages/unread/syncCursor/serverTime`；消息字段复用现有 MessageVO，不改变旧 List 和整数未读接口。快照与游标必须在相同一致性读边界产生，禁止查完列表再取最新游标。详细分页／过滤与 MySQL 竞态测试在 T05 落地前补齐，App 当前不得调用此待实现接口。
