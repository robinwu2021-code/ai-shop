# 服务业App后端接入与剩余能力

更新：2026-11-10。需求依据为 ai-shop-bapp 同日服务业接口交接。本文记录本轮新增合同及已核验边界，不能代替营业环境部署收据。

## 一 工单工作台正式合同

`GET /biz/x/beauty/work-orders`，正式插件前缀保持不变。需要已登录商家USR/MCH、当前实体/门店及现有`biz:booking:view`或`biz:booking:manage`权限；服务功能使用权与角色权限仍独立。SELF技师只读入口不因此获得全店工单权限。门店头`X-Store-No`沿平台合同；请求参数不能覆盖当前身份、实体或门店。

| 参数 | 约束/含义 |
|---|---|
| page / size | 默认1/20；page为1—1000000，size为1—100；SQL分页，不在端上截取全部记录 |
| status | 可不传；真实工单根状态`OPEN`、`IN_SERVICE`、`SERVICE_FINISHED`、`CLOSED`、`CANCELLED`；不使用演示`COMPLETED`、`PAUSED`或`TO_PAY`冒充根状态 |
| query | 原工单号或原预约号精确匹配，最多64字符；不是顾客姓名、手机号模糊检索 |
| from / to | 可不传；ISO8601带偏移时间，按创建时刻筛选，UTC `[from,to)`，同时存在时from必须小于to |
| storeNo | 可省略；若传，必须等于当前可信门店；不能跨店查询 |

```http
GET /biz/x/beauty/work-orders?page=1&size=20&status=SERVICE_FINISHED
X-Store-No: STORE001
Authorization: Bearer <当前账号会话>
```

平台公开响应沿现有ApiResult包装；下例为解包后的data，不改变平台错误合同。插件MockMvc直接返回对象的测试不是宿主公开包装证明。

```json
{
  "records": [{
    "entityNo": "ENTITY001", "storeNo": "STORE001",
    "workOrderNo": "WO001", "appointmentNo": "AP001",
    "status": "SERVICE_FINISHED", "scopeRevision": 2, "revision": 7,
    "createdAt": "2026-11-10T01:00:00Z", "startedAt": "2026-11-10T01:30:00Z",
    "finishedAt": "2026-11-10T02:10:00Z", "closedAt": null
  }],
  "total": 51, "page": 1, "size": 20
}
```

此例是合同示意，不是本次产生的实际履约样本。排序按创建时刻倒序，同刻按内部物理序稳定排序；物理id不对外返回。空的末页仍返回真实总数和所请求页号。使用普通页码分页；列表变化时刷新第一页，不把多次请求当作一致快照。列表不捏造顾客姓名、项目标题、支付状态、可开工权限或完整账单，详情仍沿`GET /work-orders/{workOrderNo}`。App当前生产工作台尚未改调本接口；不能把后端新增等同客户端联调完成。

本地owner为`WorkOrderWorkbenchService`。独立服务内部是`POST /internal/beauty/work-orders/queries`的typed bound合同，固定endpoint/action、当前actor/entity/store、请求摘要及响应归属必须一致；它不是App可直连的接口。分页/状态等格式由公开MVC和独立协议边界分别校验一次，Service仅做业务权限/范围及原事实读取。

| `/biz/payment/refund`、`/biz/after-sale/...` | 各自实际退款/售后owner | 当前工单部分履约可退范围、取消/退款/到账三者同步成功 |

扫码恢复必须在实际支付owner补合同：持久原键/输入摘要、同键同参原单、异参冲突、当前权限与原键查询。原CheckoutService的令牌仅存哈希；禁止为省事把含token的CollectView放入通用明文幂等响应缓存。令牌恢复/换发须保持原付款单、冻结有效期及明确的换发规则，不能因网络未知再开付款单。这是SVC-B04的合同约束，实际near-pay v2及本轮增量见§六，不把工程验证当渠道已验证。

## 五 SVC-B03 实际履约合同（已验收：当前冻结支持范围）

准备入口保持原语义：`POST /work-orders/{w}/tasks/{t}/preparations`仍只准备来源、数量与完整库存保留，`canStart=false`，不建步骤、参与或实际资源占用。以下路径均加正式前缀`/biz/x/beauty`，由当前实体/门店/真实账号决定范围，不能提交actor或替换来源身份。

| 路径/动作 | 真实权限与前置 | 成立的事实 |
|---|---|---|
| POST `/work-orders/{w}/tasks/{t}/assignments` | COORDINATE、现场未开工任务、冻结来源/定义/真实资源及排班 | 新direct安排原件；不覆盖历史task执行快照，不伪造预约hold |
| POST `…/accept` | 当前SELF、完整岗位选择、scope/task/binding及岗位版本 | 本人接单原件，不代表已开始参与 |
| POST `…/start` | 全部必需岗位真实接单、原START/attempt、完整retention、Native实际APPLIED、Core ACK、当前Native资格/生命周期证明，最后SELF | 任务IN_SERVICE、唯一SERVICE步骤开始、真实人员参与；原开始人不被接手人覆盖 |
| POST `…/handover-proposals` | 当前COORDINATE、真实当前占用及版本、一个明确STAFF段、接手人员/资源 | 冻结交接后剩余窗口计划和理由；尚无实际交接或参与 |
| POST `…/workflow`，PAUSE | 当前原实际参与SELF、task/binding/scope/occupation修订 | 任务PAUSED，当前参与闭合；实际容量继续保留 |
| 同上，RESUME | 新的当前资格/排班/资源兼容证明、Core仍可执行、最后SELF | 任务IN_SERVICE，追加参与段；不重置原步骤开始或重复占数量 |
| 同上，HANDOVER | 已批准原proposal、当前接手SELF、原新资源集合原子切换、当前证明 | 旧段闭合、新段追加及handoverFromNo；原START作者/永久unit/原收费不变 |
| 同上，END | 当前实际参与SELF、原实际步骤及数量、真实Native结束原件 | SERVICE步骤完成、任务DONE；Core独立确认COUNT履约，资源可能仍CLEANING |
| 同上，CLEAN | 当前COORDINATE、明确原待人工清洁segmentNos | 只确认选定清洁义务并释放相应容量；预计分钟经过不自动释放 |
| GET `…/execution` | VIEW/COORDINATE当店；仅SELF须本人冻结岗位或真实参与/接手关系 | 返回真实当前Native修订/状态/段与停止冲突事实，不拿初始START回执冒充当前 |
| POST `…/operations/{operationNo}/recover` | 同上读取范围、完整原操作父链 | START或TASK_FLOW原号查证/恢复；不重放保存的人身份。RESUME/HANDOVER需要新增参与时返回HUMAN_REQUIRED |
| POST `…/operations/{operationNo}/cancel` | 当前COORDINATE、已持久化待确认动作 | Native同根验证：已APPLIED返回真实效果；确无效果才永久NO_EFFECT_SEALED并解除该动作阻塞。空查询不是取消成功 |

`start`的DTO为`StartServiceTaskReq`：expectedScopeRevision、expectedTaskRevision、expectedBindingRevision、ownSlots(requirementNo/ordinal/assignmentRevision)。`workflow`为`TaskWorkflowReq`，另含expectedOccupationRevision、action、reason、handoverProposalNo、cleaningSegmentNos。安排、接单、开工、提案和实际动作均沿原`Idempotency-Key`；同key同参查原件，异参冲突，未知不换key或attempt。请求版本来自实际回执，不能拿预计计划版本代替实际占用版本。

`TaskWorkflowVO`分列taskStatus/taskRevision、occupationNo/occupationRevision/occupationState、segments、fulfilled、stockDisposition与pendingReason。`fulfilled=true`仅指Core COUNT事实；`RETAINED_PENDING_DISPOSITION`不等于库存已消费。缺真实耗材issue/终态政策时不关闭整张工单；本批不新增库存消费、扣次、支付、退款或提成账。旧关闭原语明确拒绝含实际TASK_START的根，后续完整关闭必须由结算/资产切片消费各owner终态。

初始START真实无效果封印后仍保留原`T04B_RELEASE_REQUIRED`，不冒充Core数量/stock已释放，不开放重新安排或新attempt；这与已存在occupation上的workflow取消封印不同。

支持边界沿原准入：MANUAL_OFFLINE、STORE_ORDER、单任务COUNT=1及单一有效来源绑定；预约沿原CONFIRMED完整分配，现场沿真实direct计划。任意多阶段/跳过、拆并实际资源组、计划窗口过期后未获新许可的开工恢复、自动清洁释放、未定义早退退款/资产处置及其他未有真实来源授权的资金类型继续关闭。暂停/交接/人工清洁本身已有政策，不以“缺少规则”为由关闭正常受支持链。

本地和独立部署均消费同一typed服务合同。独立模式的Source/Native/Core双向HUMAN与MACHINE固定路由只承接已注册owner；MACHINE原件及当前状态查询不安装保存的actor，当前资格验证必须是当前HUMAN并留下Native VALIDATE_WORKFLOW原件。缺provider、坏回执、跨范围或用途错位均失败关闭。


## 六 SVC-B04 扫码原键恢复（2026-11-11）

实际owner为独立near-pay的DynamicCollectionService及SourceCommandExecutor，复用V30 pay_source_command永久命令，不复制支付账。宿主已补限定POST/GET `/biz/pay/v2/collections`桥接；开关沿shop.pay.biz-onboarding.enabled/base-url与原BIZ认证链，原凭据/X-Merchant-No传给支付侧，当前支付成员的payment.create及门店归属仍由owner判定。老POST `/biz/payment/collection`未具备这份合同，服务页仍不能使用它。

POST body：requestNo、storeNo、amountMinor，及可空subject/expireMinutes/bizNo。requestNo为1—64位ASCII原键，不能只发Idempotency-Key头；原键限定可信租户/来源/商户/门店/actor。bizNo如传必须为原工单号，进入规范化摘要并写原PayOrder，同键改金额/用途/期限/工单号报409 IDEMPOTENCY_CONFLICT。无bizNo历史请求保持旧摘要，不能以同键补绑工单。

GET query：storeNo、requestNo。只读原requestNo/payOrderNo/status/expireAt/bizNo，checkoutUrl=null；不新建付款、不换发令牌、不自动向渠道查询。POST同键同参重放可按现有政策为原未过期付款签发新短能力，不改变原付款期限；已付/已关/过期/取消处理中没有付款链接。expireAt是原付款期限，短令牌可能更早到期；需要链接时重放原POST，不调用会延长截止的legacy reissue。来源命令只存安全坐标及摘要，不保存明文token/URL。

外层保持near-pay `{code,message,data,requestId}`，错误及状态原样透传。超时/503是结果未知，保留原完整输入与原键，先GET查原号，不能换键重收。跨账号/门店恢复不回读其他scope原件。业务关联不代表B05已收齐或组合结算授权，缺资金/订金/资产规则仍关闭。正式OpenAPI见[原键恢复合同](./service-collection-recovery.openapi.json)。App服务页尚未接入、embedded legacy尚未开放、未部署、未真实收款；收款与来源结算仍须分别验收。


## 七 SVC-B05.1/2 正式结算查询与诊断预览（阶段交付）

正式GET `/biz/x/beauty/work-orders/{workOrderNo}/settlement`返回原bill、financial fingerprint、逐来源decision、观察complete、关闭原因；canSettle=false、methods为空。原bill保留多币种与人工声明/渠道实收区别，不将manualDeclaredMinor填到receivedMinor，不额外叠加通用receivables或预约订金。原bill读取权限、当前实体/门店/actor检查及未知处理保持不变。

逐来源状态：MANUAL_DECLARED表示准入时已全额人工声明；PREPAID表示已有预付来源；REFUND_RECOLLECTION_CLOSED表示退款产生的差额不授予再次收款；COLLECTION_CONSENT_REQUIRED表示缺少新增收款来源许可；INCOMPLETE/UNSUPPORTED表示未知或当前合同不支持。任何状态的canCollect均为false，不等于工单完成、渠道到账或资金结清。

正式POST `/biz/x/beauty/work-orders/{workOrderNo}/settlement-previews`接收expectedFingerprint、currency、walletMinor、externalMinor、method（CASH/EXTERNAL_POS/SCAN）。金额必须为JSON非负整数，不接受字符串、浮点或由客户端提供的“应收”；实际应收仍为原bill。预览重读原owner，身份namespace、绑定、资金、退款或声明变化后旧指纹返回CONFLICT；币种必须在原bill。返回诊断提案及executable=false，不持久化previewNo、不签支付许可、不调用资金或资产writer。

该切片包含embedded/standalone同一owner及固定HUMAN内部typed路由；它不是完整组合结算。未授权服务后付、独占订金分配和多资产扣款/撤销，故本轮不提供settlements执行入口；储值/权益仍待B07对应来源授权与资产合同，实际结算仍为B05剩余项。App正式接线列为B09分段任务，不能将/__demo路径换前缀直接上线。详见[阶段合同](./service-settlement-observation.openapi.json)。
