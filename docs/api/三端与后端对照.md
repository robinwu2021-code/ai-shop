## 一、总览

| 域 | 前缀 | 契约（前端生成的 OpenAPI） | 前端在调 | 后端已实现 | 覆盖率 |
|---|---|---|---|---|---|
| C 端 | `/mp/**` | 60 | 60 | 75 | **70.0%** |
| B 端 | `/biz/**` | 50（含 schema：113 个类型 + 23 个 requestBody） | 50 | 19 | **30.0%** |
| 平台端 | `/ops/**` | 151（本轮才**可读**，见 §四） | — | 8 | 未纳入守卫 |

> 「后端已实现」多于契约不是好事也不是坏事——它意味着后端先行，或存在没人调的暴露面。
> 两个方向都要看：**前端要调但后端没有 = 关掉 mock 即 404**；**后端有但前端不调 = 要么待接入，要么该删**。

## 四、平台端 —— 契约本轮才变成机器可读

平台端此前在守卫里显示「契约 0」，原因不是没有契约，而是**契约文件读不进去**：

`ops-web/scripts/gen-openapi.mjs` 把 YAML 的每个 key 都加了引号（`"paths":`），
而守卫按 `^paths:` 匹配——一条也读不到。**这与 C 端曾经踩过的是同一个坑**
（见[契约漂移清单](契约漂移清单.md)开头），C 端修了，ops 侧没跟着修。

本轮修了三处：

1. **生成器**：key 只在必要时加引号（与 C 端一致）
2. **生成器自带的回读校验**：原本只认带引号的 key——它把这个错误约定固化了，两种写法都要认
3. **路径参数泄漏**：10 条路径原样带着 `${v.asNo}` 进了契约（转换正则只匹配裸标识符，不认带点的），
   后端永远匹配不上，会被永远算成「前端独有」

修完后 `docs/api/openapi-ops.yaml` 是 **151 个端点 / 135 条路径 / 122 个类型**，`paths:` 裸键，可被任何工具解析。

**还差最后一步**：`backend/scripts/api-align.py` 目前只加载 `openapi.yaml` 与 `openapi-b.yaml`，
把 `openapi-ops.yaml` 加进去（约一行），平台端就能和另外两端一样被守卫盯着。
这一步没做是因为该脚本正被另一条线编辑，避免互相覆盖。

## 四之一、字段级对齐：路径对得上 ≠ body 对得上

契约守卫比的是**路径**——两边都能平等地抽出来。body 一边是 TS 一边是 Java，于是没人比。
后果是这一类漏洞只在联调时以 400「参数错误」的形式暴露，而那个报错既不说是哪个字段、也不说是谁的错。

已加断言（`packages/shared/tests/wire-alignment.test.ts`）：解析后端 controller 的
`record XxxReq(...)` 与前端 `requests.ts` 的 wire 类型，逐字段比对，**C/B 两端都覆盖**。

**B 端三条已修**（纯命名问题，按后端字段名对齐）：

| 端点 | 后端收 | 前端发 |
|---|---|---|
| `/biz/pickup/verify` | `verifyCode` | ~~`code`~~ |
| `/biz/after-sale/{no}/reject` | `remark` | ~~`reply`~~ |
| `/biz/group-request/{no}/quote` | `unitPriceMinor` `minQty` `note` `validDays` | ~~`priceMinor` `minCount` `desc`~~（**四个全不对**） |

**C 端三条是设计差异，改名解决不了**，已登记基线待决策：

| 端点 | 差在哪 | 谁该改 |
|---|---|---|
| `/mp/order` | 前端多发 `usePoints` / `groupNo` / `appointmentAt` | **后端补字段**——后两个是已实现的下单路径，不补就是**静默丢数据**：参团单变普通单、预约单没时段 |
| `/mp/order/{no}/after-sale` | 后端要 `refundMinor`，前端发 `reasonCode` | 待定：退款金额由服务端算还是前端传（部分退款要不要支持，M4） |
| `/mp/group-request` | 前端有 `pickupNo`/`budgetMinor`，后端有 `images`/`days` | **产品拍板**：求团单到底收哪些信息——这是需求没对齐，不是实现问题 |

基线内不报错、基线外立刻失败；对齐了却忘了从基线删也会报错。
另有一条「至少比到了几条」——正则解析最危险的失败方式是一条都没抽到却报绿。

## 四之二、形状之外：行为怎么验收

契约（OpenAPI）给的是**形状**——字段、类型、必填。后端照它实现完，「`PREPARING` 能不能直接跳
`COMPLETED`」「驳回要不要填理由」「核销要不要校验属不属于本自提点」这些**行为**仍然没有依据。

这些规则唯一可执行的定义在 mock 里：**9 个状态迁移 + 66 条拒绝规则**，
已导出成[后端验收清单](后端验收清单.md)（`npm run gen:spec` 从代码抽取，不是手写）。

用法：实现某端点前先查它的方法名有哪些拒绝条件；写完对照状态机表检查迁移约束。
错误码可以另定，**拒绝与否不能变**。清单与 mock 的同步有断言守着——mock 加一条规则、清单没更新，`npm test` 就红。

## 五、结论：接后端的顺序

按「缺口大小 × 业务价值」排：

1. **B 端 35 条**——覆盖率只有 25.5%，且缺的是商品、订单、履约这些日常主路径。B 端商家一旦接真后端，现在能用的只有四分之一
2. **C 端 18 条**——团购与评价两块整条链没有，其余是一期关闭的积分
3. **接住后端已有的 40 条**（C 端 33 + B 端 7）——尤其 `order/preview`、`coupon/best`、`config/bootstrap`：
   它们现在都由前端本地算，**规则散在两处迟早对不上**
4. **平台端纳入守卫**——一行的事，做完三端就都在同一张网里

> ⚠️ 别只看覆盖率数字：C 端 70% 里包含大量「后端有前端没接」，
> 真正决定能否关掉 mock 的是**「前端要调但后端没有」那一列必须清零**（C 18 / B 35）。
