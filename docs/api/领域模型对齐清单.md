## 一、契约有、库里没有列（阻塞）

后端实现这些接口时会发现**这个字段填不出来**，而前端页面已经按契约写完了。
每条要么补列，要么改契约删字段 —— 不能留着。

### 积分域整体未落库（4 处）

积分能被商家接收并向平台兑付 —— 它是**平台的负债**（ADR-006），要按资金标准建模。但库里没有积分账户表、没有积分流水表，订单上也没有任何积分列。C 端已实现下单抵扣与完成返分，接后端即刻失效。

| 契约字段 | 目标表 |
|---|---|
| `Goods.points` | `prd_goods` |
| `OrderItem.points` | `ord_item` |
| `OrderAmount.pointsUsed` | `ord_sub_order` |
| `OrderAmount.pointsEarn` | `ord_sub_order` |

**处置**：新建 `usr_point_account` + `usr_point_record`，并在 ord_sub_order 上补 points_* 列

## 二、契约有类型、库里无承载（阻塞）

既没有映射到表，也未登记为聚合视图 —— 要么该建表，要么该在生成器的 `VIEW_TYPES` 里
写明它由哪些表拼出来。**留白就是没人想过这件事**。

### `PointRecord`

积分流水。见「积分域整体未落库」—— 积分是平台负债，流水是对账依据，不能只存余额。

**处置**：新建 `usr_point_record`（含 balance_after 便于对账）

## 三、结构不匹配（要重新对齐，不是补列）

### `UserCard` ↔ `mkt_user_coupon`

映射不成立。`mkt_user_coupon` 是**优惠券领取记录**（coupon_no / 领取时间 / 核销时间），而契约的 `UserCard` 是**卡包**：储值卡余额、次卡剩余次数、卡面、有效期 —— 一列都没有。

**处置**：卡包需要独立的表（如 `mkt_user_card`），或明确一期不做卡包并从契约删除该类型

### `SettleBill` ↔ `stl_bill`

粒度不同。库里 `stl_bill` 是**一个子订单一条**（sub_order_no + gross/commission/net），契约的 `SettleBill` 是**一个商家一个周期一张**（periodStart/periodEnd/orderCount）。两者不是同一个东西：前者是分账明细，后者是账单。

**处置**：要么新增周期账单表（`stl_bill` 降为明细，另建 `stl_settlement`），要么改契约让 B 端直接读明细并在服务端按周期聚合

## 六、平台端：契约与库的整体缺口

平台端契约有 **64** 个实体类型，库里有对应表的只有 **12** 个。

这不是漂移，是**后端尚未开工**（API 清单里平台端后端覆盖率 0.6%）。
列在这里是为了让规模可见：平台端落地时要新建的表大致就是这个数量级，
而其中相当一部分（风控、内容、消息、财务）与现有 39 张表没有交集，是全新的域。

已有表的：`Merchant`、`OrderItem`、`Order`、`Community`、`PickupPoint`、`Coupon`、`Review`、`ReviewAppeal`、`AfterSale`、`Quote`、`Category`、`Sku`。
