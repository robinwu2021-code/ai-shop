## 三、结构不匹配（要重新对齐，不是补列）

### `UserCard` ↔ `mkt_user_coupon`

映射不成立。`mkt_user_coupon` 是**优惠券领取记录**（coupon_no / 领取时间 / 核销时间），而契约的 `UserCard` 是**卡包**：储值卡余额、次卡剩余次数、卡面、有效期 —— 一列都没有。

**处置**：卡包需要独立的表（如 `mkt_user_card`），或明确一期不做卡包并从契约删除该类型

### `SettleBill` ↔ `stl_bill`

粒度不同。库里 `stl_bill` 是**一个子订单一条**（sub_order_no + gross/commission/net），契约的 `SettleBill` 是**一个商家一个周期一张**（periodStart/periodEnd/orderCount）。两者不是同一个东西：前者是分账明细，后者是账单。

**处置**：要么新增周期账单表（`stl_bill` 降为明细，另建 `stl_settlement`），要么改契约让 B 端直接读明细并在服务端按周期聚合

## 六、平台端：契约与库的整体缺口

平台端契约有 **114** 个实体类型，库里有对应表的只有 **12** 个。

这不是漂移，是**后端尚未开工**（API 清单里平台端后端覆盖率 0.6%）。
列在这里是为了让规模可见：平台端落地时要新建的表大致就是这个数量级，
而其中相当一部分（风控、内容、消息、财务）与现有 39 张表没有交集，是全新的域。

已有表的：`OrderItem`、`Order`、`Community`、`PickupPoint`、`Coupon`、`Review`、`ReviewAppeal`、`AfterSale`、`Quote`、`Category`、`Sku`、`SpecTemplate`。
