## 2 环境与身份

生产Base URL：`https://www.hxmall.top`，请求路径直接拼接，无额外/api前缀。运营端入口：`https://www.hxmall.top/ops-web/`。生产只用于获授权业务，联调写入应先在隔离环境执行。

| 调用方 | 常见前缀 | 身份与门店范围 |
| --- | --- | --- |
| 收银/服务员/厨房/商家管理/老板端 | /biz/x/food | 复用商家登录签发的Bearer token；按接口提供X-Store-No/路径storeNo，服务端核对真实商家门店及操作权限 |
| 扫码/H5/消费者 | /mp/x/food | 按接口使用消费者登录、桌码会话或设备会话，不可把全部mp路径视作匿名 |
| 平台运营 | /ops/x/food | 平台运营登录态及原平台权限，不能复用普通商家token |
| CORE/FOOD/CIM内部服务 | /internal/food | 沿服务令牌、必要的签名范围和原内部客户端调用；公网不开放，终端不可调用 |

商家和消费者登录沿平台已有账号系统，不另造餐饮账号。主体、操作者、库存owner由服务端确定，不在业务请求中伪造。请求的storeNo只是授权目标，不是商家身份。

扫码开会话使用POST /mp/x/food/sessions，body为tableToken、可选deviceCredential，带Idempotency-Key；服务端解析真实桌码并返回sessionNo、accessToken、expiresAt、checkNo。后续需要会话的请求使用X-Food-Session。设备凭据入口使用X-Food-Device、X-Food-Device-Credential，具体见MpDiningDeviceSessionController。桌码/会话/设备凭据属于敏感信息，不写普通日志或URL。

## 3 公共约定

- JSON写入使用Content-Type: application/json；认证通常使用Authorization: Bearer <token>。
- 清单明确声明Idempotency-Key的写请求必须提供原键。网络重试使用同一键和同一业务内容，新业务操作使用新键；具体长度及约束以各接口声明为准。
- 带version的修改使用最近一次查询返回的版本。冲突后重新查询并让操作方确认，不能盲目递增version重复提交。
- 常规公开JSON成功：`{"code":0,"msg":"success","data":{}}`。按code判断业务成功，msg仅供展示。业务失败常仍为HTTP200，鉴权失败可返回401；断网、5xx、超时也要单独处理。详[统一响应规范](../响应格式规范.md)。内部接口、SSE和文件流不套用此示例。
- PageData形状为records、total、page、size；并非所有列表都分页，数组接口与afterId游标接口按实际返回类型处理。
- 金额以具体DTO约定的币种最小单位为准，不自行把所有数字乘除100；库存qty使用BigDecimal语义和基础单位，避免浮点误差。不同币种和单位不可直接汇总。
- 营业日、营业时间和日结沿门店策略；不要把营业日固定解释为服务器自然日。清单中的日期边界、枚举、必填关系须结合对应DTO和服务规则。
- 结果为UNKNOWN/待确认时先查原操作结果，再按原业务号处理，不能当作失败重新创建订单、扣库存或退款。

## 4 典型业务对接顺序

| 场景 | 调用顺序与注意点 | 清单定位 |
| --- | --- | --- |
| 菜品和餐牌 | 复用基础商品/SKU → 餐饮配方、配料、套餐配置 → 餐牌及门店/时段/渠道价格配置 → 发布 → 查询可售目录 | Bundle、Modifier、Recipe、Menu、Catalog相关Controller |
| 堂食开台点餐 | 查询桌台/策略 → 开台取得check → 创建/关联购物车 → 按原行标识改数量和选项 → 试算 → 提交订单批次 | Check、Cart、Pricing、OrderBatch |
| 扫码/H5 | 真实桌码换会话 → 读餐牌 → 创建/读取购物车 → 试算与提交 → 查询原订单 | MpDiningSession、MpCatalog、MpCart、MpOrderBatch |
| 先付后吃 | 冻结试算/提交 → 按原结账合同确认支付状态 → 厨房履约；前端不能自行制造paid状态 | Settlement、Checkout、Kitchen |
| 先吃后付 | 门店策略允许POSTPAY → 接受未付款履约 → 加菜/厨房 → 最终试算及结账 | Check、OrderBatch、Kitchen、Settlement |
| 拼桌/转台/AA | 原check版本和操作键执行；经营分单与最终付款分摊不能混为一个操作 | TableSharing、TableOperation、CheckSeat、BusinessShare |
| 厨房 | 按工位取任务 → start → ready → serve；催菜/作废/损耗/重做走各自动作及版本 | KitchenTask、Station、Kds |
| 退餐库存 | 原退餐流程审批 → 明确可再售/损耗及原因 → 查询库存处置 → 原operationNo查回/重试；不把库存返还当退款成功 | Return、FoodReturnStock |
| 打印 | 根据原订单/厨房事实生成任务 → 设备领取/处理并上报 → 查询原任务状态；已排队不代表纸面打印成功 | PrintJob、DiningDevice |
| 日结及报表 | 预览 → 处理未决项 → 签署；日报每日汇总，周月复用统计，实时数据和统计数据分别看水位/来源 | BusinessClose、FoodReport |

上表为导航与业务顺序，不提供可绕过服务端状态机的捷径。真实支付/外卖厂家/打印硬件接入状态仍按各自专项；现有Mock证据不等于真实厂家已接通。后端具备接口不代表相应前端页面已交付。

## 5 本地库存主路径示例

以下为可替换参数的命令模板，未使用真实生产凭据。先设置隔离环境BASE、商家TOKEN及STORE。源码入口BizFoodStockController。

创建物料：
```sh
curl -X POST "$BASE/biz/x/food/stores/$STORE/stock-items" \
  -H "Authorization: Bearer $TOKEN" -H "X-Store-No: $STORE" \
  -H "Idempotency-Key: opening-item-001" -H "Content-Type: application/json" \
  -d '{"itemKind":"MATERIAL","name":"测试原料","baseUnit":"KG","trackingMode":"TRACKED","weighed":1}'
```

从data.itemNo取服务端物料号后初始化：
```http
POST /biz/x/food/stores/{storeNo}/stock-balances
Authorization: Bearer <商家token>
X-Store-No: <storeNo>
Idempotency-Key: opening-balance-001
Content-Type: application/json

{"itemNo":"<itemNo>","trackingMode":"TRACKED","status":"ACTIVE","initialQty":5.25,"reasonCode":"COUNT","reasonDetail":"期初盘点"}
```

成功data类型BalanceVO：balanceNo、itemNo、baseUnit、trackingMode、status、onHand、reservedQty、availableQty、version、commandNo。调整使用原version：
```http
POST /biz/x/food/stores/{storeNo}/stock-balances/{itemNo}:adjust
Idempotency-Key: opening-adjust-001

{"delta":-1.125,"version":<查询返回的version>,"reasonCode":"COUNT","reasonDetail":"盘点调整"}
```
同样携带认证、门店、JSON头；后续GET同物料余额查询路径，预期本例onHand=4.125。初始化/调整失败先看业务code及原命令结果，不直接改数据库余额。

## 6 出品、退餐与同步异常

- 待处理出品：GET /biz/x/food/stores/{storeNo}/production-pending?afterId=0&limit=20。返回sourceId、sourceEventNo、taskNo、action、status数组，下一页使用末项sourceId。NOT_STARTED表示无耗用凭据；现有PREPARED/SUBMITTED/UNKNOWN/REVERSAL_PENDING/BLOCKED/FAILED也会列出。列表是实时事实，不是冻结快照。
- 查询耗用：GET /biz/x/food/production-events/{eventNo}；首次缺口可能尚无耗用记录，不能将404解释为出品事件不存在。
- 人工处理：POST /biz/x/food/production-events/{eventNo}:consume，沿当前门店与STOCK权限；原实现先查库存回执后决定是否执行。使用服务端返回状态，不能仅以HTTP成功判断库存已扣。
- 退餐：GET /biz/x/food/stores/{storeNo}/returns/{returnNo}/stock-dispositions，POST同前缀/{operationNo}:retry。使用原退餐号/操作号，按AFTERSALE及STOCK权限，不新建退餐。
- 可选镜像：GET /biz/x/food/stores/{storeNo}/stock-sync/deliveries；POST /biz/x/food/stores/{storeNo}/stock-sync/deliveries/{syncNo}:retry（Idempotency-Key）。配置、映射、preflight及对账的具体入出参见清单。
- 餐饮默认本地库存；镜像默认关闭。镜像异常不等于本地库存扣减失败，不反向修改进销存原生库存。

当前上线仍采用既有事务外耗用与恢复链路，food-production-recovery、order-points-recovery已获授权启用并有成功运行记录。不得把本文解释成“本地库存与厨房原子提交改造已完成”；该改造仍待实施。
