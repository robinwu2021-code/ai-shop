# 积分第三阶段生产基线整合计划

## 目标与基线

把已验收的新积分方案整合进正在运行的生产代码。工作分支从主应用提交 `a0a41a6c327f8557f5f0d3db1a0c48e6429f1a67` 建立；积分来源为 `codex/points-v3` 当前提交 `b673dd7128adf74d89da9bbc19356b5097b39e70`。生产工作树还含有已随线上 jar 发布、但未进该生产 Git 提交的收件人称谓改动，必须一并纳入。

## 约束

- 积分以最新设计实现；删除旧积分运行逻辑，不兼容旧 API/引擎，不迁移积分余额或旧积分数据。
- 积分是 `pay` 中的独立业务模块，不拆 jar。`storeNo` 是账务和业务隔离维度；商家主体只用于归属和授权查询。
- 保留生产手机会话、收藏、物流、普通现金支付和退款、商家退款待办等线上能力。
- 生产订单、现金退款及其迁移历史不是积分数据。不得重置、删除、改写其状态、历史迁移文件或 checksum。
- 积分业务与恢复开关保持关闭。不创建或启用真实商家、门店、协议、余额或资金业务。
- 测试按变更面窄跑并记录各用例时长；最终整合提交需要完整发布闸门。部署目标为已有生产环境，必须使用同一整合提交并记录回滚包。

## 执行任务

1. **复核来源和数据库。** 确认运行 jar、生产源码及额外收件人称谓改动一致；通过只读查询固定生产 Flyway 版本、checksum、退款表和待处理状态数量。核实当前观察到的 jar 含 V424 而 `ai_shop.flyway_schema_history` 最高 V327 的差异。未解释该差异前不执行生产迁移。
2. **合并代码。** 从本分支合并已验收积分分支，按语义解决冲突，确保所有生产变更保留。先处理订单创建/回调、售后和退款执行 mapper/job，再处理支付账务、结算与对账；普通现金退款沿生产协议，积分退款沿最新准备/回退/UNKNOWN/人工处理协议。移除旧积分逻辑，不以“选择 ours/theirs”消除冲突。
3. **整理迁移。** 对照实际生产历史和整合后的 migration 目录；对未部署积分迁移分配不冲突的新版本，只在修复和审核后修改积分迁移文件名。保持生产已执行迁移及 V424 收件人称谓迁移原样。积分无存量数据回填或余额迁移。
4. **接入端与契约。** 在生产 B/C 页面上增量接入新积分能力，保留生产订单、支付、售后、物流界面行为；更新 API、权限矩阵、词条和生成文档。运营管理仍按门店隔离。
5. **分层验收。** 先跑退款协议、订单回调、迁移结构和积分门店隔离的窄测试及并发测试；记录命令时长和慢用例。所有点通过后，针对整合 SHA 运行后端完整闸门、三端测试、类型检查、构建和文档守卫。不得把积分分支的既有测试结果当作整合结果。
6. **部署与观测。** 先固定发布 SHA 和原生产包，再以同一 SHA 发布主应用、现有 pay-svc 和三端 H5。检查每项健康状态、版本、Flyway 结果、门店隔离和关闭状态。若健康检查或迁移前置核对失败，保持原服务运行并停止发布；不做线上回填或修表。

## 关键验收

- `git diff` 证明生产分支自共同祖先引入的在线能力均被保留；额外收件人称谓改动进入整合树。
- 生产现金退款的原请求、回执、UNKNOWN、人工待办和重复调用语义保持不变；积分补收失败回退后的售后保持待处理，可人工重试或关闭。
- 新积分模块只在 `pay` 内运行，金额、订单和积分均以门店为边界；DETACHED 默认且服务端拒绝新接线。
- 没有旧积分余额迁移，没有对生产订单/退款记录做重置或回填。
- 全部验证通过且线上开关仍关闭后，才视为发布完成。
