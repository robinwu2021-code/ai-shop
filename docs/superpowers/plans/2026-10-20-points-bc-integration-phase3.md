# 第三阶段：B/C 端积分接入开发计划

> **For agentic workers:** 使用 superpowers:executing-plans 逐项实施，以每项交付结果更新复选框。

**Goal:** 让 B/C 端基于统一积分接口展示真实账户、交易赠送、抵扣和退款结果。

**Architecture:** 端侧调用 shop-app 的 /biz、/mp 应用接口；应用层校验用户、门店与权限，调用支付域统一积分能力。支付系统负责余额、预算、记账及处理状态，交易域保留规则快照和操作关联，不新增第二套账本。

**Tech Stack:** Java/Spring、现有支付账本与 Outbox、Vue/uni-app、共享 API 契约及现有 UI 组件。

**Spec:** docs/superpowers/specs/2026-10-20-points-unified-operations-phase2-design.md；docs/technical/points-unified-operations.md；已确认的默认全部门店参与、多积分独立运营且保留现有订单默认积分规则。

## 约束和范围

- 默认全部门店参与；本期不提供单门店参与开关，不以签约作为新增参与条件。历史合同与结算证据保留。
- 多积分分别展示名称、代码、币种和余额，不跨类型或跨币种汇总，不自动换汇。
- 首批订单沿用现有默认积分。其他生效积分可独立运营，但不因前端可见而自动成为订单赠送或抵扣类型；多类型订单策略另行规划。
- 新交易切换必须先具备持久化接线版本和操作映射；旧订单、旧预占和旧退款继续原路径，避免双发、双扣。
- 复用现有设计组件，B 端涉及布局变动先补充基于现有页面的原型。
- 定向验证变更路径，不做全量或并发测试。线上只读验收，真实订单、积分划拨及资金操作人工验收。
- 提交进入 codex/ai-shop-codex；服务端、B 端和 C 端分开构建发布，C 端基于统一分支发布。

## 已核实现状

- B 端已有 pages/points、pages/points-records、StorePointStatements，账户页仍混有条款签约、收款渠道及结算方式设置。
- C 端已有 points 页面和 /mp/points/accounts、/mp/points/entries；BuyerPointsAppService.Account 缺少名称，页面使用市场和代码做类型标签。
- B 端已有 /biz/points/store-types、store-account、store-entries 和账单接口。
- 统一 PointsOperationsPort 是内部 SPI，不是可直接供手机调用的 HTTP 接口。第二阶段未切换订单业务接线。

## Review Focus

- 切换积分或门店时晚返回的旧请求不得覆盖新页面数据。
- ACCEPTED 不能显示为已到账；待入账、预占、冻结和可用余额分别展示。
- 无账户读取不得创建账户；停用类型的历史流水、退款与释放仍可追溯。
- 网络重试、支付回调重放不能重复发放；新旧路径不能处理同一个承诺两次。
- 取消及部分退款需匹配原类型、订单快照和现金证据；页面文案不得将处理中显示为完成。
