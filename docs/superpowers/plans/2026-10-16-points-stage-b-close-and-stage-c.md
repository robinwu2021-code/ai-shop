# 积分第二阶段收尾与第三阶段开发任务清单

## 目标与边界

积分继续作为 `pay` 内的独立业务模块，账务基本维度为门店；商家只负责归属、签署和聚合。第二阶段只完成运营端能力，不接入真实商家、门店、订单或银行资金。第三阶段再接入订单生产者，并保持生产资金通道和定时任务在验收前关闭。

## 第三阶段任务清单：订单对接

### C1 订单积分事件契约

目的：定义订单、支付、退款与积分之间唯一、可重放的事件边界。

- 定义订单支付成功、取消、部分退款、全额退款、售后完成和异常关闭事件。
- 每个事件必须包含订单号、门店号、商家归属、订单行/商品范围、金额、币种、事件版本和幂等键。
- 明确事件发生时间与会计日期，禁止客户端直接提交积分数量作为权威值。
- 定义重复事件、乱序事件、补发事件和未知事件的处理状态。
- 先完成契约测试，再实现生产者和消费者。

### C2 订单与门店拆单映射

目的：保证积分账务以门店为基本维度，并与订单拆单结果一致。

- 一个订单按门店拆分为独立积分结算单元。
- 同一门店多个原路由账单保留独立路由组和 statement/revision 关系。
- 校验订单商品归属门店、库存门店和结算门店的一致性。
- 禁止跨门店合并入账、扣回、退款或对账。
- 增加跨门店串账、重复拆单和门店缺失的失败测试。

### C3 支付成功后的积分入账

目的：把已确认支付转换为可审计的积分入账事件。

- 仅消费已确认支付证据，不能依据订单创建或客户端回调入账。
- 按当前生效的类型、规则、协议和门店开关计算 U/C/D/B/R。
- 记录规则版本、类型版本、门店、订单和支付事件版本快照。
- 入账操作具备幂等性、可重放性和并发版本保护。
- 支付成功但积分入账失败时进入可重试状态，不伪造成功流水。

### C4 取消、退款与售后扣回

目的：让积分回滚与订单售后事实保持一致。

- 订单取消按已入账积分生成扣回或冻结事件，不直接修改历史流水。
- 部分退款按订单行和门店比例计算扣回，禁止按整单粗暴扣回。
- 全额退款和售后完成遵循同一状态机，重复通知不重复扣回。
- 积分不足时进入待处理/应收状态，不能产生负余额绕过规则。
- R 类型只参与同店抵销，不转换为现金提现或现金退款。

### C5 订单与积分状态一致性

目的：提供订单、支付、积分三方状态的可检查和修复能力。

- 建立订单事件、支付证据、积分流水和结算单之间的关联查询。
- 增加超时、缺事件、重复事件、版本冲突和金额不一致告警。
- 对账修复必须基于原始订单/支付证据，不能由运营端手工写入成功事实。
- 支持门店、订单、事件版本和会计日维度的只读排查。

### C6 订单联调与灰度开关

目的：在不影响现有订单流程的前提下逐步启用积分。

- 使用合成商家、门店、订单和支付网关完成集成测试。
- 增加按门店、积分类型和订单场景的开关，默认关闭。
- 订单事件消费者在未知类型、未知门店和未知规则时失败关闭并留痕。
- 不做历史订单余额迁移；上线前确认没有生产积分余额需要兼容。
- 完成订单支付、取消、部分退款、全额退款和售后场景的端到端定向测试。

### C7 第三阶段验收与上线准备

目的：确认订单接入具备上线条件。

- 完成 API、数据库、权限、幂等、对账和异常处理文档。
- 通过后端定向测试、前端回归测试、SQL/架构检查和浏览器验收。
- 生成测试耗时和慢测试报告，明确未覆盖项及风险。
- 确认真实资金通道、生产任务和真实主体数据仍由上线审批单独开启。
- 形成第三阶段 Review、修复、提交和发布检查记录。
