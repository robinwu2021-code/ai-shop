# 两套套餐线下购买闭环

Goal: 商家提交线下付款，运营核实真实银行到账后生效；不接线上支付。
Architecture: 门店商城继续使用 commerce offline；主体额度包独立订单、冻结价格及额度，复用 PlatformPaymentPort / OfflineCollectionPort / PrivateEvidencePort，不另建资金账本。
Tech: Java21 / Spring / MySQL9 / Flutter / Next.js。
Spec: 用户明确两套套餐均支持线下付款，先代码和本地闭环，真实收款配置后补。

## Global Constraints
- 保留原工作区全部未提交改动；只修改隔离工作树。
- 不部署、不修改166业务或收款配置，不虚构实际收款账户、售价或已实现行业能力。
- 商家申报不等于到账；只有可信平台核款事实可生效。金额不符不生效。
- 主体额度归主体，门店数字权益归门店。支付请求和核款重试使用原始冻结命令。
- 支持中断恢复；业务数据库事务不包含资金/媒体IO。

## Task 1: 门店商城离线可用性及核款恢复
App仅接受offlineReadiness.available=true；展示离线阻断原因。运营确认取订单冻结收款主体，不要求人工输入内部编号。增加原核款动作查询，未知结果保留原命令，不可变更后复用幂等键。同步API/测试。

## Task 2: 主体额度包线下购买
新增配置报价（不预置真实价格）及主体购买单、付款申报、核款动作和证据保留。价格/额度/期数/收款档案冻结。仅同档续费、免费或已到期开通；有效付费跨档先联系运营（不发明折算政策）。FREE保持免费无付款。运营核款后按冻结快照一次性开通，保留override和trial_used。未配置档案不可下单。对已收款但主体/套餐条件变化保留资金并进入人工处理。

## Task 3: 两端页面及本地验证
App额度包报价/购买/付款凭证/历史状态，OPS报价维护/核款/拒绝/恢复。沿用已有权限划分。局部单元及MySQL9联调覆盖正常、重复、拒绝再申报、金额不符、核款后失败恢复及错误主体。整理线上实际目录差距与发布前配置清单。
