## 0. 结论先行

| # | 问题 | 方案 | 对标 |
|---|---|---|---|
| 1 | 部分退款把整单标「已退款」，可重复申请、上限仍为全额 | **行级退款**：售后单挂到「商品行 × 件数」；订单状态不因部分退款改变，另记**退款进度**（无 / 部分 / 全部） | 淘宝按子订单（商品行）退款；拼多多按商品退 |
| 2 | 再申请上限 | **可退额 = 行实付 − 已退**；行实付在下单时按优惠分摊**落快照** | 跨店满减按实付折扣率折算（行业通行） |
| 3 | 申请无时限 | **售后期 = 完成后 N 天**（默认 7，与结算解冻同一配置）；质量问题另给延长期 | 淘宝交易成功后 15 天、三包 90 天 |
| 4 | 极速退已废但标签还在 | 下掉「极速退款」标签与 `instantRefundEligible`；换成**商家自动化策略**（未发货自动同意等），只有商家开了才对买家说「秒退」 | 千牛售后自动化：未发货仅退款自动退、退货入仓自动退、按物流节点「优先退」 |
| 5 | 关单与付款并发 | 写入门**条件更新**（`where status = 旧值`），0 行即冲突 | — |
| 6 | 商家不知道该怎么处理 | **处理建议**：每张售后单由后端算出「建议动作 + 理由 + 建议金额」，B 端一键采纳；配套**自动化策略**与**协商** | 千牛的自动化策略 / 协商；商家后台的处理建议 |

## 1. 行业做法对照（只列多个来源一致的口径）

| 维度 | 淘宝 | 拼多多 | 我们现在 | 2.0 |
|---|---|---|---|---|
| 退款粒度 | 子订单（商品行） | 商品 | 整张子单 | **行 × 件数** |
| 部分退的优惠 | 按实付折扣率折算；**部分退不退店铺券**，整单全退才退券 | 同类 | 整单全退才退券/积分 | 金额按快照折算；券维持「整单全退才退」；积分**按比例** |
| 售后期 | 交易成功后 15 天；三包 90 天 | 签收后一段时间 | 无 | 完成后 7 天（可配），质量问题 15 天 |
| 商家处理时限 | 超时自动达成；买家催促时缩短到 24/48h | 未发货约 24h、已发货约 36h 未处理即自动退款（各来源有 24/48h 两说） | 48h 统一 | **分场景**：未发货 24h、已发货仅退款 48h、退货退款 48h |
| 自动化 | 千牛 AG：未发货自动退、入仓自动退、按物流节点优先退、按原因/金额自定义 | 系统默认同意 | 无（极速退已废） | **商家自选策略** |
| 协商 | 商家可选「协商」 | 可协商部分退款 | 无 | 商家改金额 → 买家确认 |

> 资料多为第三方整理，平台规则会调；这里取的是**结构**（粒度、时限分场景、自动化策略、协商），不照搬具体天数，天数全部做成配置。

## 2. 数据模型

### 2.1 行级退款

```text
ord_after_sale (售后单，一张可含多行)
  └─ ord_after_sale_item 🆕  after_sale_no · item_id · qty · refund_minor
ord_item（订单行）
  + paid_share_minor 🆕   下单时落快照：本行分摊后的实付（含优惠/积分抵扣分摊，不含运费）
  + refunded_qty 🆕       已退件数（售后落定时累加）
  + refunded_minor 🆕     已退金额
ord_sub_order
  + refunded_minor 🆕     已退总额（含运费）
  + refund_progress 🆕    NONE / PARTIAL / FULL —— 与订单状态正交
```

- **订单状态不因部分退款改变**。全部行退完（`refunded_qty = qty` 且运费已处理）才迁到 `REFUNDED`。
- `refund_progress` 下发给三端，作为状态旁的**角标**（「部分退款 ¥12.00」），不占状态。
- 存量：迁移时按现有 `amount / goodsAmount × (payAmount − freight)` 回填 `paid_share_minor`；已有 REFUNDED 子单按售后单金额回填 `refunded_minor`。

> 已经写好的行级退款内核（`RefundCalc` / `RefundHandler`）就是这一层的算法，接线即用。

### 2.2 金额口径

| 项 | 规则 |
|---|---|
| 行可退额 | `paid_share_minor × 退件数 / qty`，末件吃尾差；上限 `paid_share_minor − refunded_minor` |
| 运费 | **未发货**：最后一笔（退完全部行）连运费一起退；**已发货**：不退运费，除非原因属商家责任（质量/错发/少发/破损）→ 运费随首笔退 |
| 券 | 整单全退才退回（维持现状，与淘宝一致） |
| 抵扣积分 | **按退款比例退回**（积分是钱，部分退不退等于吞了买家的钱） |
| 赠送积分 | 按比例扣回（不足扣到 0 不追） |
| 称重商品 | 用 `weigh_adjust_minor` 修正后的实付 |

### 2.3 写入门（并发）

所有状态写入经 `OrderTransitions`，持久化改为 `update … set status = :to where no = :no and status = :from`；影响 0 行 → `CONFLICT`，调用方按「已被别的流程处理」收口（关单撞上付款 → 不释放库存/券）。

## 3. 售后期与时效（全部可配，默认值如下）

| 场景 | 默认 | 超时结果 | 现有配置 |
|---|---|---|---|
| 申请窗口：完成/签收后 | 7 天（质量类原因 15 天） | 入口消失；后端拒 `AFTERSALE_WINDOW_CLOSED` | 新增（默认取 `shop.settle.after-sale-days`，两者必须一致：窗口长于结算期 = 钱已分走再退） |
| 商家处理：**未发货**仅退款 | 24h | 自动同意 | `replyHours` 拆成两档 |
| 商家处理：已发货仅退款 / 退货退款 | 48h | 自动同意（生鲜灰色地带除外，维持现状） | `replyHours` |
| 买家寄回 | 7 天 | 关闭申请 | `shipBackDays` |
| 商家确认收货 | 48h | 自动退款 | `confirmHours` |
| 在途待签收（WAIT_RECEIPT） | 签收后自动退；**15 天未签收 → 转平台** | 补上现缺的出口 | 新增 |
| 买家对驳回申请平台介入 | 驳回后 7 天 | 关闭 | 新增 |

## 4. 商家操作推荐（核心新能力）

### 4.1 处理建议（每张售后单一条）

后端 `AfterSaleAdvisor`（纯函数，输入售后单 + 履约进度 + 订单 + 买家售后画像，输出建议），随 `AfterSaleVO.advice` 下发：

```text
advice = { action, reasonKey, suggestedRefundMinor?, needEvidence?, deadlineAt }
action ∈ APPROVE | APPROVE_INTERCEPT | APPROVE_AFTER_RETURN | NEGOTIATE | VERIFY | REJECT_SUGGESTED
```

| 条件（按顺序取第一条命中） | 建议 | 理由文案（示意） |
|---|---|---|
| 未发货 / 备货中，非生鲜 | **同意**（APPROVE） | 货还没发，同意即可，库存自动回补 |
| 生鲜已备货 / 已出单未揽收 | **同意并拦截**（APPROVE_INTERCEPT） | 已打包，同意后请取消取件或留作现货 |
| 已揽收在途 + 仅退款 | **同意，签收后退**（走 WAIT_RECEIPT） | 货在路上，签收后系统自动退 |
| 已签收 + 质量类原因 + 有凭证 | **同意**；金额 = 申请额 | 买家已举证，拒绝大概率被平台判退 |
| 已签收 + 质量类原因 + 无凭证 | **核实**（VERIFY） | 先请买家补图 |
| 已签收 + 非质量原因 + 退货退款 | **同意退货**（APPROVE_AFTER_RETURN） | 收到退货再退款 |
| 已签收 + 仅退款 + 申请额 > 行实付 × 50% | **协商**（NEGOTIATE），建议金额 = 行实付 × 30% | 可提议部分退款，买家同意即结 |
| 生鲜已签收 + 非质量原因 | **建议拒绝**（REJECT_SUGGESTED），附驳回模板 | 生鲜签收后只受理质量问题 |
| 买家近 30 天售后率异常高 | 在上述建议上加「谨慎」标记，不改动作 | — |

- 建议只是建议：**不替商家做决定**（自动化策略除外，见 4.2）。
- 每条建议带 `deadlineAt`（超时自动同意的时刻）—— 商家最需要知道的是「不处理会怎样」。
- 驳回给**模板**（生鲜签收、超出售后期、已与买家协商一致……），驳回理由必填维持。

### 4.2 自动化策略（商家自选，默认全关）

| 策略 | 触发 | 动作 |
|---|---|---|
| 未发货自动同意 | 申请时未备货、仅退款 | 立即同意并退款 |
| 小额自动同意 | 申请额 ≤ 商家设定额（如 ¥20）且非生鲜 | 立即同意 |
| 退货揽收即退 | 退货运单首个揽收节点 | 自动退款（商家承担在途风险换体验） |
| 退货签收即退 | 退货运单签收 | 自动退款 |

- 开了「未发货自动同意」的商家，买家端才显示「未发货秒退」——**承诺与行为同源**，替代已废的极速退标签。
- 每次自动执行写售后时间线「按店铺策略自动同意」，B 端可查、可关。

### 4.3 协商

商家点「协商」→ 填金额（≤ 可退额）+ 说明 → 售后单进 `NEGOTIATING`（新状态）→ 买家接受（按协商额退款）/ 拒绝（回到 APPLIED，商家时限重新计）/ 超时 48h 未答（视为拒绝）。

## 5. 三端呈现

| 端 | 变化 |
|---|---|
| C 端 | 申请页按**商品行选件数**，实时显示可退额与运费是否退；售后期倒计时；订单状态旁「部分退款 ¥x」角标；协商卡（接受/拒绝） |
| B 端 | 售后卡顶部**建议条**（动作 + 理由 + 截止时刻 + 「按建议处理」）；行级明细；协商入口；店铺设置里「售后自动化」页 |
| 运营端 | 售后列表加退款进度、建议动作、是否自动执行；裁决支持部分金额 |

## 6. 状态机变化

```text
售后单：APPLIED ─┬→ NEGOTIATING 🆕 ─┬→ REFUNDING/REFUNDED（买家接受）
                 │                  └→ APPLIED（买家拒绝/超时）
                 ├→ …（其余不变）
子单：  部分退款 → 状态不变，refund_progress=PARTIAL
        全部退完 → REFUNDED，refund_progress=FULL
```

## 7. 分期

| 期 | 内容 | 依赖 | 风险 |
|---|---|---|---|
| **一期（资金正确）** | 写入门条件更新；行级退款 + 快照 + 已退额；可退额校验；售后期窗口；下掉极速退标签 | 迁移（4 列 + 1 表 + 回填） | 中：改退款主链路，需灰度 + 对账脚本 |
| **二期（商家效率）** | 处理建议 `AfterSaleAdvisor` + B 端建议条 + 驳回模板；时效分场景；WAIT_RECEIPT 出口 | 一期 | 低：建议只读 |
| **三期（自动化与协商）** | 自动化策略页 + 执行器；协商状态；运营端部分裁决 | 二期 | 中：自动退款需额度与审计 |

## 8. 不做

- 平台垫付式「极速退款」（淘宝按买家信用垫付）：我们没有信用分体系，也没有垫付资金池。
- 换货（EXCHANGE）：维持按退款处理，入口不开放，另立项。
