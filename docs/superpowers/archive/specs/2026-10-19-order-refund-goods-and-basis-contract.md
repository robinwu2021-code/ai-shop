# M2/M3 商品数量、批准决定与退款结算契约附录

状态：已延期。用户执行中决定只支持整单退款，本文保留为后续研究，不再作为本轮待实施契约；本附录不代表部分退款入口已经开放。承接订单退款对齐开发计划 T4/T5，M1 继续只开放整单全退。

## 1. 本轮源码复核补出的依赖

现有普通现金回退接口在现金退款前已经记结算回退；积分 prepared hold 则在资金/积分确认后记商品退款进度。直接删除 BasicRefundPolicy 限制，会把两个协议差异带入部分退款，不能只修改订单终态。

现有 RefundPlan 的金额在积分追回抵销场景是业务可退额度，未必等于实际退回现金。refunded_minor 仍被旧容量模型使用，不能直接宣布它就是实际现金进度。M2 必须拆开商品覆盖、业务额度、实际现金和权益结果。

现有一行商品只绑定一张发货单。M2 支持多个商品行分包，不在本次将同一行拆到多包；请求遇到这种交付范围必须拒绝，不能虚构数量归属。

## 2. 批准决定

新增不可变 RefundDecisionV2：decisionNo、afterSaleNo、revision、purpose、actor/actorNo、批准时间、agreementNo、order/subOrder/user/store/currency、原支付快照、行范围、应退现金、权益义务和运费/合法保留额。

purpose 固定为 CANCEL_GOODS、RETURN_GOODS、AMOUNT_ADJUSTMENT：

- CANCEL_GOODS 只覆盖尚未交付且能够停止履约的明确数量；已发出但无法证明可拦截时不能走该目的。
- RETURN_GOODS 必须有对应退货数量及商家确认收到的凭据。可售/不可售分开，收到退货不等于允许回补可售库存。
- AMOUNT_ADJUSTMENT 只改变金额，不增加取消/退回件数、不回补库存、不取消交付义务。不得复用“未备货买家自动整退”事件直接执行补偿。

批准后不再修改决定；同键异参冲突。重试只恢复原执行；UNKNOWN 期间不能重新批准一个替代退款来绕过原执行。首个版本每决定一条现金执行，各权益有独立幂等任务；多现金渠道合并执行不在首版能力中。

协商保留运费或商品损耗必须关联买家接受或平台裁决凭据，不能仅凭商家减少金额推断买家已接受。商品交易已终止后，不得把约定保留额继续作为新退款容量。

## 3. 数量模型

订单行保存 orderedQty、cancelledQty、returnedQty、deliveredQty；后者表示已经有可信交付证据的历史数量。有效交付量为 deliveredQty-returnedQty，终止量为 cancelledQty+returnedQty。

约束：0<=cancelledQty；0<=returnedQty<=deliveredQty；deliveredQty+cancelledQty<=orderedQty。退货收妥是该批货曾交付给消费者的事实，可在缺物流签收时补齐对应交付数量，但不得补造承运商轨迹。

覆盖/取消/退回数量以批准决定和执行幂等登记，现金成功回执重放不再次累计。金额调整 qty=0。RefundLine 的旧 qty 只作兼容聚合，新目的与覆盖范围必须显式存储。

发货按 orderedQty-cancelledQty 计算剩余范围；已取消的行无需再绑定包裹。包裹确认收货只确认实际归属行；核销和商家送达必须明确覆盖全部剩余交付范围。订单级锁内 current read 重算：

- 尚有未闭合数量：保持原履约状态。
- 有正常交付且全部数量闭合：COMPLETED。
- 全部交易终止且批准义务结清：REFUNDED。
- 金额补偿：不改变上述数量事实。

新增行字段对旧合同版本保留“未知”口径；新订单在下单时初始化。不能给历史缺事实订单批量填 0 后直接使用新闭合算法。

## 4. 金额和结算基数

分别保留 originalBusinessCash、approvedBusinessRefund、actualCashRefunded、originalPoints/returnedPoints、originalEconomicGoods/cumulativeCoveredEconomicGoods。实际现金只由成功资金回执或合法线下确认增加；零现金完成增加 0。

对外 refundProgress 迁移为实际现金比例时须版本化读模型；旧 refunded_minor 的业务容量用途保留到迁移完成。新字段不能与旧字段成为同一事实的双写权威。

经济价值使用下单时冻结的积分折算及商品快照，退款时不读当前积分汇率。每项结算份额为：floor(原金额×退后累计/原基数)-floor(原金额×退前累计/原基数)。全积分不使用现金 0 作分母；真实零经济价值明确为不产生该项金额调整，不视为一次全退全部商家应付。

新版 SPI 携带 schemaVersion、decisionNo、原快照号/hash、原经济商品基数、本次和退前累计覆盖价值、原现金及实际现金回退、原积分及本次权益变化、运费应退额。旧 SplitReversal 仅处理可证明的旧现金协议；无法升级的历史数据返回人工核对，不反推原额。

## 5. 普通现金也使用准备/确认协议

M2 普通现金与积分共用持久结算 hold，但确认凭据按资金类型分开：

1. 事务内冻结决定、容量和原始结算基数，建立 hold 并阻断放款。
2. 事务外按原账户和原请求提交分账回退；未知只查原请求。
3. 回退确认后才发送现金退款。
4. 普通现金以 pay 内原退款执行号对应的成功资金凭据确认 hold；积分以现有积分确认凭据确认。不能伪造积分 preparation 号让普通现金通过积分守卫。
5. 现金明确失败时，只有确认未发生/已安全中止的执行才可释放容量；已发生银行回退必须保留并进入可审计恢复/人工处理，不清除回退事实。
6. 已付供应商保留 paid_at/payment_ref 和原应付，新增追偿义务；未付按原基数调整；UNKNOWN 继续阻断冲突放款。

在普通现金准备/确认与失败处置均验收前，不开放 M2 部分现金退款。M2 和 M3 的共享结算契约必须一起冻结，避免先上线一个无法正确确认的中间版本。

## 6. 入口和兼容

新请求显式声明 contractVersion=2 和 purpose，服务端同时检查订单快照、客户端能力、门店/本人权限与通道部分退款能力。仅客户端传 version 不构成授权。

新建决定固定合同版本；旧执行不迁移，原号查询/恢复继续。关闭新增开关不停止已批准执行。历史差异先只读出单，禁止按当前 REFUNDED 状态直接猜测取消数量或改回履约中。

## 7. 实现顺序及退出条件

1. 定义不可变批准决定与数量 schema/API、原数据分类及版本门槛。
2. 为普通现金补 prepared hold 资金证明、结果未知及明确失败处置，与既有积分协议共存。
3. 增加数量账本、发货/收货/核销闭合及库存范围处理。
4. 增加全积分经济基数与逐项累计比例，保留原付款及追偿。
5. 新旧模型影子比较，可信新单小范围开放，三端按服务端 allowed 动作展示。

必验：两件退一件；少额补偿不耗件；合法保留运费；交付与取消混合闭合；两包并发最后收货；退款与放款竞争；现金成功权益失败重启；回退成功但现金明确失败；全积分三次不整除部分退；旧快照缺失；同键异参；旧客户端拒绝新能力。
