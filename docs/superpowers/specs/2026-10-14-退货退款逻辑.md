# 退货退款逻辑（售后 2.0 · 整合稿）

状态：草稿（待拍板 §12）
创建：2026-10-14
整合自：《订单与售后-三端状态关联》《售后2.0-方案》、`TDD-售后规则-审核与部分退款`（现行）、`TDD-订单售后三端断点修复`（已修）
新增需求：**商家「开始备货」后不再自动退款**（食品类损耗、物流信息与实际不一致）

---

## 0. 六条原则

1. **钱不在商家没点头时自动退出去 —— 除非商家还没付出任何成本。**
   付款后、商家开始备货前：超时自动同意（对标淘宝/拼多多未发货仅退款）。
   商家开始备货之后：仅退款一律要商家决定；超时**转平台介入**，不自动退。
2. **退货退款按「货回来才退钱」**：自动同意只推进到「等买家寄回」；货回到商家手里后商家超时不确认，才自动退。
3. **阶段以申请时刻为准**：申请那一刻的履约阶段落快照，之后商家再点备货，不改变这张申请的规则（防止「看到退款申请才去点备货」）。
4. **按商品行 × 件数退**；部分退款不改订单状态，只记退款进度。
5. **承诺与行为同源**：端上说的「秒退 / 需商家确认 / 售后期还剩 N 天」都由后端同一个判据算出来。
6. **部分退款只能由商家确认或商家发起**，永不自动执行；且先问**支付渠道能不能部分退**，不能就给替代方案，不硬退（§4A）。

## 1. 履约阶段（判规则的唯一维度）

| 阶段 | 判据 | 对买家怎么说 |
|---|---|---|
| `NOT_PREPARED` 未备货 | 已付款，商家未点「开始备货」，无运单 | 待发货 / 待备货 |
| `PREPARING` 备货中 🔁 | 商家已点「开始备货」，且在**备货时效**内 | 商家备货中（显示开始时间） |
| `LABELED` 已出单未揽收 | 有运单号、轨迹停在 CREATED，6h 宽限内 | 已出单 |
| `SHIPPED` 运输中 | 运单已揽收及以后；或出单超 6h 未揽收（从严） | 已发货 |
| `AT_PICKUP` 已到自提点 🆕 | 自提单已到货（子单 FULFILLING，自提类） | 已到自提点 |
| `RECEIVED` 已签收 | 子单 COMPLETED（买家确认 / 自动收货 / 核销） | 已完成 |

🔁 = 规则变化，🆕 = 新增阶段（现状把自提到货算作 NOT_PREPARED/PREPARING，错把「货已到店」当成可以秒退）。

## 2. 「开始备货」（新需求的落点）

| 项 | 规则 |
|---|---|
| 谁、何时可点 | 商家；子单**已付款待发货**（契约 PAID）；**全部履约方式、全部品类**（现状只对快递/自送显示） |
| 次数 | 一次，不可撤销；记 `prepared_at` 与操作人，写订单时间线 |
| 批量 | B 端订单列表「待发货」页签支持多选「开始备货」 |
| 前置 | 该子单**没有进行中的售后**（有了再点也不影响那张申请，见原则 3，干脆不让点，避免误解） |
| 效果 | 此后的**仅退款**：不再超时自动同意、不适用任何自动化策略；商家超时 → 转平台介入 |
| **备货时效**（防滥用） | 默认 48h（可配，可按品类覆盖）：点了备货 48h 内未发货 / 未到店 → **备货保护失效**，阶段回落 `NOT_PREPARED`（时间线记「备货超时未发货」），自动退款规则恢复。备货不延长发货承诺时效 |
| 买家可见 | 订单详情显示「商家已于 10-14 09:30 开始备货」；申请页提示「商家已开始备货，退款需商家确认，可能扣除已产生的损耗」 |

**为什么要时效**：没有它，商家可以付款后一律点备货，把所有退款都拖进人工 + 平台，买家体验和平台成本都会崩。备货保护换的是「我真的在做这单」，过期即失效。

## 3. 决策矩阵（阶段 × 类型 → 能否申请 / 谁决定 / 超时结果）

### 3.1 仅退款

| 阶段 | 可申请 | 商家时限 | 商家不处理 | 自动化策略 | 处理建议（B 端） |
|---|---|---|---|---|---|
| NOT_PREPARED | ✅ | 24h | **整单全额**：自动同意并退款；**部分**：转平台介入（部分退款不自动，§4A） | ✅ 仅整单全额 | 同意（库存自动回补） |
| PREPARING | ✅ | 24h | **转平台介入**（不退） | ❌ | 普通品：同意；食品/定制：**协商**（扣损耗）或拒绝（模板「已备货/定制」） |
| LABELED | ✅ | 24h | 转平台介入 | ❌ | 同意，并**取消取件单**（按钮直达） |
| SHIPPED | ✅ 生鲜仅质量类原因 | 48h | 非生鲜：自动同意 → **签收后退**（WAIT_RECEIPT）；生鲜：转平台介入 | 仅「退货揽收即退」类不适用 | 同意，签收后自动退；或建议买家拒收 |
| AT_PICKUP | ✅ 生鲜仅质量类原因 | 24h | 转平台介入 | ❌ | 协商（货已到店，食品有损耗） |
| RECEIVED（售后期内） | ✅ 生鲜仅质量类；非质量仅退款进入「核实」 | 48h | 转平台介入 | ❌ | 质量+有图：同意；无图：核实（请补图）；高额：协商 |
| RECEIVED（售后期外） | ❌ 入口消失，后端拒 | — | — | — | — |

### 3.2 退货退款

| 阶段 | 可申请 | 商家时限 | 商家不处理 | 之后 |
|---|---|---|---|---|
| 发货前（NOT_PREPARED / PREPARING / LABELED） | ❌ 不适用（货没出门，走仅退款） | — | — | — |
| SHIPPED | ✅（拒收/签收后寄回） | 48h | 自动同意 → 等寄回 | 同下 |
| AT_PICKUP / RECEIVED（售后期内） | ✅ 生鲜仅质量类 | 48h | 自动同意 → 等寄回 | 买家 7 天内填运单，否则关闭；商家收货后 48h 不确认 → **自动退款**（货已回到商家手里） |

### 3.3 服务类（到店核销 / 上门）

| 阶段 | 规则 |
|---|---|
| 未使用（未核销 / 未到预约时间） | 仅退款；未「开始备货/排期」→ 自动同意；已排期 → 商家决定，超时转平台 |
| 已使用 | 只能协商或平台介入（服务已消耗，不适用退货） |

## 4. 金额

| 项 | 规则 |
|---|---|
| 退款单位 | 商品行 × 件数（`ord_after_sale_item`） |
| 行可退额 | 下单时落快照的行实付 `paid_share_minor` × 退件数 / 购件数；上限 = 行实付 − 已退 |
| 再次申请 | 允许；上限按剩余可退额，**不再是整单实付** |
| 运费 | 发货前退完全部行 → 连运费退；已发货 → 仅商家责任原因（质量/错发/少发/破损）退运费 |
| 备货损耗 | 仅在 PREPARING / AT_PICKUP / 食品类可由商家**协商**扣减，买家接受才生效；商家不能单方面少退 |
| 券 | 整单全部退完才退回 |
| 抵扣积分 | 按退款比例退回 |
| 赠送积分 | 按比例扣回，不足扣到 0 不追 |
| 资金执行 | 回退分账 → 原路退 → 积分/券 → 退货回补库存（现有 `doRefund` 链路，改为按行金额） |

## 4A. 部分退款（商家确认 / 商家发起 + 渠道能力）

### 4A.1 什么算「部分」

退款额 **小于该子单剩余可退额**（选了部分商品行、部分件数、或改了金额）。整张子单剩余部分全额退 = 「整单退」，其余都是部分。

### 4A.2 三个来源，都必须经商家

| 来源 | 流程 | 自动？ |
|---|---|---|
| **买家申请部分**（选件数 / 金额） | APPLIED → 商家同意 / 协商 / 驳回；商家超时 → 转平台介入 | ❌ 任何阶段都不自动同意、不适用自动化策略 |
| **商家协商**（对买家的申请提出较少金额） | NEGOTIATING → 买家接受才执行 | ❌ |
| **商家主动退款** 🆕（无需买家申请） | 商家在订单上点「部分退款」→ 选原因（缺货少发 / 称重差价 / 补偿 / 价格调整 / 其他）+ 行与金额 → 直接执行，买家收到通知 | ❌（商家本人就是确认方） |

- 商家主动退款也生成售后单（`initiator = MERCHANT`），走同一条资金链路与可退额校验；**不能超过剩余可退额**。
- 称重商品的差价退款、缺货少发是最常见的商家主动退款 —— 现在只能靠买家来申请，商家没有入口。

### 4A.3 支付渠道能力

不是所有渠道都能「原路部分退」。每个渠道登记一份能力，申请/确认前先查：

| 渠道 | 原路部分退 | 说明 / 限制（以渠道文档为准，做成配置） |
|---|---|---|
| 微信支付（直连 / 收付通） | ✅ | 同一笔支付可多次部分退，有**次数上限**与**可退期限**；收付通须先按比例**回退分账** |
| 支付宝直付通 | ✅ | 可多次部分退，有可退期限；分账后须先退分账 |
| 0 元单（FREE） | — | 没有现金可退，只退积分 / 券 |
| 线下当面付（OFFLINE） | ❌ 平台不经手 | 钱在商家手里：商家**线下退款并在 B 端登记**（金额 + 方式 + 凭证），买家确认收到或 72h 自动确认 |
| 将来接入的聚合 / 银行通道 | 视通道 | 不支持部分退的，按下表兜底 |

渠道不支持部分退、或超出次数 / 期限 / 分账已结算无法回退（现在会抛 `SPLIT_EXPIRED`）时，**不硬退**，商家确认那一步直接给替代方案：

| 替代方案 | 条件 | 说明 |
|---|---|---|
| **积分补偿** | 买家同意 | 现有 `refundMode=POINTS` 链路；按 1 元 = N 积分 |
| **商家线下退款并登记** | 商家与买家协商 | 同 OFFLINE 流程，平台只记账、不动钱 |
| **整单退后买家重拍** | 仅未发货 | 渠道只支持全额退时的最后手段，需买家同意 |

> 端上：商家点「同意部分退款」前就显示「本单渠道：微信支付，支持部分退款（已退 1 次）」或「本单线下付款，需线下退款后登记」——不要等点下去才报错。

### 4A.4 系统内部要先改的

- 退款请求号现为 `AS-<子单号>`（支付流水按它幂等）→ **一张子单只能退一次钱**，第二次部分退款会被幂等吞掉、账实不符。改为**按售后单号**（一张售后单一个退款请求号）。
- 分账回退按退款金额比例回退，不再整笔回退。
- 渠道能力表：`pay_channel_refund_capability`（渠道 · 是否支持部分退 · 次数上限 · 期限天数 · 是否需先回退分账），运营端可改。

## 5. 时效总表（全部可配）

| 时效 | 默认 | 超时 |
|---|---|---|
| 售后期（完成后） | 7 天；质量类 15 天 | 入口关闭 |
| 备货时效（开始备货后未发出） | 48h | 备货保护失效，回落未备货 |
| 商家处理：未备货 / 已备货 / 已出单 / 到店 | 24h | 未备货：自动同意；其余：转平台 |
| 商家处理：运输中 / 已签收 | 48h | 见 §3 |
| 买家寄回 | 7 天 | 关闭申请 |
| 商家确认退货收货 | 48h | 自动退款 |
| 在途待签收（WAIT_RECEIPT） | 15 天未签收 | 转平台 |
| 驳回后买家申请介入 | 7 天 | 关闭 |
| 协商待买家回应 | 48h | 视为拒绝，回到待商家处理 |
| 平台介入处理承诺 | `interveneWorkDays` | 告警运营 |

> 现状的生鲜灰色地带「超时只再提醒商家」**没有出口**，买家会永远卡着 —— 统一改为「转平台介入」。

## 6. 售后单状态机

```text
APPLIED ─┬→ REFUNDING ─→ REFUNDED                （同意：仅退款立即退 / 退货等寄回后退）
         ├→ WAIT_RECEIPT ─→ REFUNDED             （在途仅退款：签收后退；15 天未签收 → ARBITRATING）
         ├→ NEGOTIATING 🆕 ─┬→ REFUNDING          （买家接受协商额）
         │                  └→ APPLIED            （买家拒绝 / 48h 未答）
         ├→ REJECTED ─→ ARBITRATING / CLOSED     （买家 7 天内可申请介入）
         ├→ ARBITRATING 🆕入口：商家超时（备货后） ─→ REFUNDING（可部分）/ CLOSED
         └→ CLOSED                               （买家撤销 / 寄回超时）
```

**子单**：部分退 → 状态不变，`refund_progress = PARTIAL`；全部行退完 → `REFUNDED`。
**主单**：不受售后影响；对外总状态由投影聚合（已接线）。

## 7. 商家操作推荐

每张售后单下发 `advice = { action, reasonKey, suggestedRefundMinor?, deadlineAt, deadlineOutcome }`：
- `deadlineOutcome` 明说「不处理会怎样」：`AUTO_APPROVE` / `TO_PLATFORM` / `AUTO_REFUND_ON_RETURN`。
- 动作按 §3 矩阵「处理建议」列；买家近 30 天售后异常高时附「谨慎」标记。
- 驳回给模板：已备货/定制、生鲜签收非质量、超出售后期、已协商一致、商品无质量问题（附检测说明）。

**自动化策略**（商家自选，默认关）只在 `NOT_PREPARED` 且**整单全额**时生效，加上货已回到商家手里的两条（部分退款永不自动）：

| 策略 | 生效阶段 |
|---|---|
| 未备货自动同意 | NOT_PREPARED |
| 小额自动同意（≤ 商家设定额，非生鲜） | NOT_PREPARED |
| 退货揽收即退 / 退货签收即退 | 退货运单节点 |

开了「未备货自动同意」的店，买家端才显示「未备货秒退」。

## 8. 物流信息不一致：处置口径

| 场景 | 现象 | 处置 |
|---|---|---|
| 已发货但没录单号 / 轨迹未同步 | 买家看到「待发货」去申请 | 商家先点了备货 → 不会被自动退；商家**补录运单**后阶段重算为 SHIPPED，按在途处理（签收后退或建议拒收） |
| 单号录错 | 轨迹对不上、显示别人的件 | 商家**改单号**：原发货单作废、新建发货单（订单服务 2.0 发货单层），时间线留痕；改号期间售后按改号后的阶段判 |
| 出单后迟迟不揽收 | 6h 宽限内算已出单；超期从严算运输中 | 建议商家取消取件单后再同意 |
| 轨迹签收但买家说没收到 | RECEIVED + 原因「未收到货」 | 建议「核实」：商家上传签收凭证 / 联系快递；超时转平台 |
| 自提到店但买家没来取 | AT_PICKUP | 不自动退；食品类建议协商（扣损耗） |

## 9. 三端呈现

| 端 | 内容 |
|---|---|
| C 端 | 订单详情：备货时间、售后期倒计时、「部分退款 ¥x」角标；申请页：选商品行与件数、实时可退额、运费是否退、「需商家确认」或「秒退」提示（同一判据）；协商卡（接受/拒绝） |

## 11. 分期

| 期 | 内容 |
|---|---|
| **一期 · 规则与资金正确** | 退款请求号改按售后单号（解锁多次部分退）；渠道能力表 + 不支持时的替代方案；部分退款只经商家；写入门条件更新；「开始备货」全开放 + 备货时效 + 备货后不自动退（超时转平台）；灰色地带出口；售后期；行级退款 + 快照 + 可退额；下掉极速退标签 |
