# 退货退款逻辑（售后 2.0 · 整合稿）

状态：历史 v2 已确认（2026-10-14；§12 保留确认记录）；本轮 R0 设计修订待评审、未实现。
历史定调：**退款永远不自动；以商家运营为主，商家与消费者协商，平台介入兜底**。
修订边界：§13 为本轮推荐定义；本轮授权修改文档不等于业务决策已确认，不表示代码已经实现。历史完成情况以 [TDD-订单状态机](../../technical/TDD-订单状态机.md) 的历史记录为准。

## 0. 原则

1. **退款永远不自动。** 每一笔售后退款都由一个人的明确动作触发：**商家同意 / 商家主动退 / 平台裁决**。
   系统超时只做两件事：**提醒**（商家），**开门**（买家获得「申请平台介入」）。不替任何人决定退钱。
2. **商家与消费者协商为主，平台兜底。** 平台不主动接管；只有买家（或商家）申请介入时才进场。
3. **备货是信息，不是开关。** 「开始备货」告诉买家「商家已在做这单」、允许商家协商扣损耗；它不改变「谁来决定」（反正都是商家）。
4. **申请资格以申请时刻为准**（阶段快照）；本轮拟定：库存、实际取消/退回数量及资金执行前置条件仍按真实履约事实重验，不能把申请快照当作尚未发货的证明。
5. **按商品行表达退款范围**；本轮拟定：退款用途、现金与真实退件分别记账，金额调整不消耗件数；订单结束条件见 §13.2。
6. **先问渠道能不能退**，不能就给替代方案，不硬退。
7. **承诺与行为同源**：端上不再出现「秒退」「自动退款」字样；说的每一句（需商家确认 / 售后期剩 N 天 / 商家还有 N 小时处理）都来自后端同一判据。

## 1. 两类退款，别混

| 类 | 是什么 | 谁决定 | 自动？ |
|---|---|---|---|
| **售后退款** | 交易成立后，买家申请或商家主动发起的退款 | 商家（平台介入时由平台裁决） | **永不** |
| **交易不成立的原路退回** | 拼团未成团、集单截单前撤单、关单后才到账的支付回调（钱进来了但订单已关） | 规则本身（交易没成立，钱不属于任何商家） | 保持自动（历史确认 §12-1） |

> 第二类不是「退款决定」，是「这笔钱本就不该收」——不退会变成平台无主资金。本文其余部分只讲第一类。

## 2. 履约阶段

| 阶段 | 判据 | 对买家怎么说 |
|---|---|---|
| `NOT_PREPARED` 未备货 | 已付款，商家未点「开始备货」，无运单 | 待发货 |
| `PREPARING` 备货中 | 商家已点「开始备货」 | 商家已于 HH:mm 开始备货 |
| `LABELED` 已出单未揽收 | 有运单号、轨迹停在 CREATED，6h 宽限内 | 已出单 |
| `SHIPPED` 运输中 | 已揽收及以后；或出单超 6h 未揽收（从严） | 已发货 |
| `AT_PICKUP` 已到自提点 🆕 | 自提类子单已到货 | 已到自提点 |
| `RECEIVED` 已签收 | 子单 COMPLETED | 已完成 |

## 3. 「开始备货」

| 项 | 规则 |
|---|---|
| 谁、何时 | 商家；子单已付款待发货；**全部履约方式、全部品类**（现状只对快递/自送显示）；B 端列表可批量 |
| 次数 | 一次，不可撤销；记 `prepared_at`，操作者写事件流水 `operator_no`（当前没有 `prepared_by` 列），写时间线 |
| 前置 | 该子单没有进行中的售后（见 §12-4） |
| 买家可见 | 订单详情「商家已于 10-14 09:30 开始备货」；申请页「商家已开始备货，退款需与商家协商，可能扣除已产生的损耗」 |
| 商家可做 | 对这单的退款申请**协商扣损耗**（买家接受才生效） |
| 备货超时未发出（默认 48h，可配） | **不自动退，不改规则**。只做：① 提醒商家发货 ② 买家端出现「催发货 / 申请平台介入」③ 运营看板记一次「备货超时」（滥用指标） |

## 4. 决策矩阵

所有格子「商家超时」的结果都一样：**提醒商家（到时 + 再过 24h 各一次）；买家获得「申请平台介入」**。所以表里只列差异项。

### 4.1 仅退款

| 阶段 | 可申请 | 商家处理时限 | 处理建议（B 端） |
|---|---|---|---|
| NOT_PREPARED | ✅ | 24h | 同意（库存回补） |
| PREPARING | ✅ | 24h | 普通品：同意；食品/定制：协商扣损耗 或 驳回（模板「已备货/定制」） |
| LABELED | ✅ | 24h | 先取消取件单，再同意（按钮直达） |
| SHIPPED | ✅ 生鲜仅质量类 | 48h | 同意并「签收后退」，或建议买家拒收 |
| AT_PICKUP | ✅ 生鲜仅质量类 | 24h | 协商（货已到店，食品有损耗） |
| RECEIVED · 售后期内 | ✅ 生鲜仅质量类 | 48h | 质量+有图：同意；无图：请补图；高额：协商 |
| RECEIVED · 售后期外 | ❌ 入口消失，后端拒 | — | — |

**「签收后退」（WAIT_RECEIPT）**：商家在货在途时同意了，钱等签收。签收那一刻**不自动打款**，而是提醒商家「已签收，确认退款」一键完成；15 天未签收 → 买家可申请介入。（历史确认 §12-2；现金请求受理不等于退款到账，见 §13.3）

### 4.2 退货退款

| 阶段 | 可申请 | 流程 |
|---|---|---|
| 发货前 | ❌（货没出门，走仅退款） | — |
| SHIPPED / AT_PICKUP / RECEIVED（售后期内） | ✅ 生鲜仅质量类 | 商家同意退货（48h）→ 买家 7 天内填退货运单（超时关闭申请）→ 商家确认收货并退款（48h，超时提醒 + 买家可申请介入） |

### 4.3 服务类（到店核销 / 上门）

| 阶段 | 规则 |
|---|---|
| 未使用 | 仅退款，商家同意 |
| 已使用 | 协商或平台介入 |

## 5. 部分退款

### 5.1 三个来源

| 来源 | 流程 |
|---|---|
| 买家申请部分（选件数 / 金额） | 商家同意 / 协商 / 驳回；本轮拟定按 §13.1 明确用途，只有金额时不推导退件 |
| 商家协商 | 商家对买家的申请提出较少金额（扣损耗、按件折算）→ 买家接受才执行；48h 未答视为拒绝，回到待商家处理 |
| **商家主动退款** 🆕 | 不需买家申请：商家在订单上选原因（缺货少发 / 称重差价 / 补偿 / 价格调整 / 其他）+ 行与金额 → 执行，买家收到通知 |

商家主动退款也生成售后单（`initiator = MERCHANT`），走同一资金链路与可退额校验。本轮拟定：归集路径平台是卖家时，商家可提议，资金批准走平台权限；不是把归集售后绕回商家单方面批准。

### 5.2 渠道能力与兜底

| 渠道 | 原路部分退 | 说明（限制做成配置） |
|---|---|---|
| 微信支付（直连 / 收付通） | ✅ | 可多次部分退，有次数上限与可退期限；收付通须先按比例回退分账 |
| 支付宝直付通 | ✅ | 可多次部分退，有可退期限；分账后须先退分账 |
| 0 元单 | — | 只退积分 / 券 |
| 线下当面付 | ❌ 平台不经手 | 商家线下退款 → B 端登记（金额 + 方式 + 凭证）→ 买家确认收到 |

渠道不支持 / 超次数 / 超期限 / 分账已结算退不回时，商家确认那一步就给替代方案（不等点下去才报错）：
**积分补偿**（买家同意）→ **商家线下退款并登记** → **整单退后重拍**（仅未发货、买家同意）。本轮拟定：这是能力确定或确定失败后的备选顺序；原路退款/回退处于 PROCESSING 或 UNKNOWN 时禁止切换另一付款路径，见 §13.3。

### 5.3 系统内部先改

- 退款请求号 `AS-<子单号>` → **按售后单号**（否则一张子单只能退一次钱，第二次被幂等吞掉、账实不符）。
- 分账按退款金额比例回退。
- 渠道能力表 `pay_channel_refund_capability`，运营端可改。

## 6. 金额

以下是本轮待评审的金额定义；§12 的历史确认记录不变。

| 项 | 推荐规则 |
|---|---|
| 范围与单位 | 行上分别记录 coveredQty / closedQty / returnedQty / cancelledQty / cashMinor；四种 RefundPurpose 见 §13.1 |
| 行现金基准 | 下单paid_share_minor是不可变上限；按件终止以剩余可退现金/剩余可终止件数切分，最后一次取剩余全额；范围覆盖不等于消费所有可售后件数，细则见§13.1 |
| 再次申请 | 行可用现金 = 原始现金份额 − 已成功实退 − 已生效约定留存 − 进行中现金预占；终止件数上限独立检查 |
| 运费 | 发货前取消全部剩余商品交易才退；已发货仅商家责任原因退，只退一次；合法保留运费单列，不使已结清交易永远 PARTIAL |
| 损耗扣减 | 买家接受协商或平台裁决后才生效，记录 agreedRetainedMinor 与依据；商家同意不能单方面改少额；价差/称重调整不套损耗协议 |
| 券 | 主单全部商品交易终止触发返券意图，真实返券结果计入权益结清，再推进终态；交付与取消混合闭合的主单不按整单退款退券 |
| 抵扣积分 / 赠送积分 | 历史目标是按比例退回/扣回；具体积分域重整仍待确认。本轮只定义订单权益意图、结果、幂等与恢复边界，0 元单不能按现金比例除以零 |

## 7. 时效（全部可配；超时都不退钱）

| 时效 | 默认 | 超时 |
|---|---|---|
| 售后期（完成后） | 7 天；质量类 15 天 | 入口关闭 |
| 商家处理申请 | 24h（发货前 / 到店）· 48h（在途 / 已签收） | 提醒商家 ×2；买家可申请介入 |
| 备货后未发出 | 48h | 提醒商家；买家可催发货 / 申请介入；运营看板计数 |
| 协商待买家回应 | 48h | 视为拒绝，回到待商家处理 |
| 买家寄回 | 7 天 | 关闭申请（不是退款） |
| 商家确认退货收货 | 48h | 提醒商家；买家可申请介入 |
| 签收后待商家确认退款（WAIT_RECEIPT） | 签收即提醒 | 24h 后再提醒；买家可申请介入 |
| 驳回后买家申请介入 | 7 天 | 关闭 |
| 平台介入处理承诺 | `interveneWorkDays` | 告警运营 |

## 8. 售后单状态机

历史迁移表和状态拆分见 [订单状态机完整方案](2026-10-14-订单状态机-完整方案.md)。本轮拟定以下资金与业务含义，跨文档状态机修订须一并评审；不声称当前代码支持这些新语义。

- 同意/接受协商/平台裁决持久化批准方案并进入执行态，买家不能撤销钱已在路上的方案。
- REFUNDING 只表示执行中；现金请求 ACCEPTED、PROCESSING、UNKNOWN 均不能推进 REFUNDED。
- 资金到账以可信回执或回查的 SUCCEEDED 为准；现金为零走 BENEFITS_SETTLED，不能等待不存在的现金回调。
- 一张售后的 REFUNDED 表示本张批准方案的现金及应退权益已结清，不能直接推导整张订单全退；订单 cashProgress 与 goodsClosed 按 §13.2 独立计算。
- 线下退款登记仍需买家确认；资金结果未知不能改成另一条退款路径。确定永久失败留存批准决定与失败证据，转人工处理。
- 归集路径申请直接由平台处理是“平台作为卖家审核”，不是买家申请介入的争议升级；原 ARBITRATING 名称的展示区分应在状态机修订中明确。

## 9. 商家操作推荐（效率靠建议，不靠自动）

每张售后单下发 `advice = { action, reasonKey, suggestedRefundMinor?, deadlineAt }`：
- `action` 按 §4 矩阵「处理建议」列；附理由。
- `deadlineAt` 只说「几点前处理，否则买家可申请平台介入」—— 这是商家真正在乎的后果。
- 买家近 30 天售后异常高时附「谨慎」标记。
- 驳回给模板：已备货/定制、生鲜签收非质量、超出售后期、已协商一致、商品无质量问题。
- **一键按建议处理**；售后列表支持**勾选多条 → 批量同意**（商家逐条看过、自己点，不是规则代办）。

> 删掉原方案的「自动化策略」与买家端「秒退」：与「退款永远不自动」冲突。

## 12. 已拍板（2026-10-14，「按照建议执行」）

1. 交易不成立的原路退回（拼团未成团 / 集单撤单 / 关单后迟到回调）**保持自动** —— 唯一的系统退款，且只限这三种原因。
2. 签收后待退（WAIT_RECEIPT）：签收后**提醒商家一键确认**，不自动打款。
3. 售后期 **7 天**（质量类 15 天），与结算解冻同一配置。
4. 有进行中售后时**禁止点备货**。
5. 抵扣积分 / 赠送积分**按比例**；已发货运费**仅商家责任原因**退。
6. 商家主动退款：原因清单按 §5.1；**不另设单笔上限**（上限即剩余可退额）；运营端出**抽查看板**（按商家统计主动退款笔数 / 金额 / 占比），不做事前审批。
7. 渠道兜底顺序：积分补偿 → 商家线下退款登记 → 整单退后重拍。
8. 线下退款登记：**买家确认收到才结**；买家有异议可申请介入。
9. 分期按 §12-9 原文：一期关掉自动退 + 退款请求号 + 写入门条件更新 + 开始备货全开放 + 行级退款与可退额 + 售后期。

## 13. 本轮设计修订（推荐，待评审、未实现）

关联：[第 5 步行级方案](2026-10-14-第5步-售后写路径与行级退款-方案.md)、[第 5 步对象模型](2026-10-14-第5步-对象模型.md)。下列定义需与状态机、TDD 及后续代码修复计划一同评审。

### 13.1 用途、数量与库存

| RefundPurpose | 含义 | 数量与库存 |
|---|---|---|
| CANCEL_ITEMS | 未交付商品交易取消 | coveredQty 表达范围；closedQty = cancelledQty；未付款取消释放占用，已付款取消回补已实扣数量一次；发货事实改变时重验 |
| RETURN_ITEMS | 已交付商品退回并终止交易 | closedQty = returnedQty；确认实收、验货及可回售事实后入库；退款到账不是证明货物可回售的证据 |
| REFUND_WITHOUT_RETURN | 已交付商品不退货、终止相应商品交易并退款 | closedQty 表达交易终止数量；returnedQty/cancelledQty = 0，不回补库存；必须明确无需寄回的批准依据 |
| MONEY_ADJUSTMENT | 称重差价、价格调整、货保留的现金补偿 | coveredQty 可用于金额归属；closedQty/returnedQty/cancelledQty = 0，不耗可退件数、不回补库存 |

coveredQty 不累加为“已退件数”；closedQty 不能重复终止同一份商品交易，returnedQty 与 cancelledQty 表示不同真实履约事实。不能仅因金额减少就减少/耗尽件数。类型（仅退款/退货退款）是用户流程，purpose 是批准后账务用途，两者均须保存。

协商退回 3 件但扣 10 元损耗：现金实退与 agreedRetainedMinor 分列，批准依据包含买家接受记录或平台裁决；三件交易可结清，10 元不能再被当作未退债务。退款后改金额须建立新提议，不能改写已经发出的不可变方案。金额调整不要求损耗协议，但需其自身原因、权限和金额依据。

本轮拟定按件终止交易的 LineAmountPolicy：remainingRefundableCashMinor = paidShareMinor − 已成功现金实退 − 已接受/裁决生效的合法留存 − 其他执行现金预占；remainingClosableQty = orderedQty − 已终止closedQty − 其他执行终止件数预占。当前执行批准前算本次 closedQty 的现金：floor(remainingRefundableCashMinor × 本次closedQty / remainingClosableQty)，本次终止全部剩余件数时取剩余现金全额。当前槽位串行；批准时余额/数量与预占同事务冻结，已生成不可变plan后发送、回执、重试不得重算金额或把本执行预占再扣一遍。

反例：3件原现金3000，先MONEY_ADJUSTMENT退1000，剩余可终止件数仍3、剩余现金2000；随后依次终止1件，现金为666 / 667 / 667，总现金含调整恰为3000。CANCEL_ITEMS / RETURN_ITEMS / REFUND_WITHOUT_RETURN消费closedQty，MONEY_ADJUSTMENT只降现金不耗件；不能继续按原paidShare × 本次qty / orderedQty算1000一件。原始快照仍用于总额上限与可追溯；初版原份额按件公式作为历史记录保留，已被本轮剩余额/剩余件数推荐公式替代，尚未实现。

### 13.2 现金进度、商品闭合与权益

cashProgress 是内部语义，旧 JSON `refundProgress` 继续表示现金比例，不新增重复 `cashProgress` JSON。goodsClosed 另行下发。cashProgress 仅表示已成功退回现金相对原始现金实付的比例：NONE / PARTIAL / FULL；0 元单现金进度为 NONE，不能用 0/0 判 FULL。
goodsClosed 表示本订单所有商品交易都已终止（取消、退回或批准无需退回），不等于商品已交付。

推荐订单结束判定：

- 全部商品交易终止、无资金结果未知或进行中预占、应退现金/权益均已结清 → REFUNDED；合法保留运费/协商损耗留存独立记载，cashProgress 可以仍为 PARTIAL。
- 部分商品正常交付、其余已取消/退回/终止，全部履约义务闭合且应退权益已结清 → COMPLETED，可保留部分退款角标。
- 仍有待履约商品 → 保持履约状态。主单全部商品交易终止触发退券意图，真实返券结果参与权益结清，不能等最终REFUNDED再发返券而造成循环；不按任意cashProgress或部分售后成功判断。

零现金交易保留售后申请、退货和权益返还流程；权益意图落库、获取真实结果并可恢复后，经 BENEFITS_SETTLED 推进。积分补偿是一种达成协议的赔付，不是原现金退款到账；补偿成功不能把仍欠现金的整单标 REFUNDED，也不能释放其现金退款预占后重复赔付。

返券评价通过子单事实提交后的可靠事件/outbox触发，由独立支付级事务锁定Payment后汇总主单商品终止与应返券事实、幂等生成/执行返券意图。子单退款事务只更新自身事实并提交事件，不能已经持有Order锁再同步获取Payment锁；支付级评价失败可恢复、真实券结果参与权益结清。该锁顺序和异步边界为本轮待评审建议，不改变历史验收记录。

### 13.3 资金执行、失败恢复与幂等

RefundExecution（拟持久化在 ord_refund_execution，未建表）保存不可变批准方案（执行号、售后号、用途、行数量、现金/运费、约定留存、权益意图、付款路径和批准证据）。状态为 PREPARED / PROCESSING / UNKNOWN / FAILED / SUCCEEDED；内部可用 DISPATCHING 租约控制发送，不对用户伪称已到账。
批准时以 CAS 原子占用可退现金/终止件数，并持久化执行与待发事件；成功回执将预占转实退。申请未批准不占资金，申请槽位仍由库保证唯一；真正取消一个未发送执行时才安全释放预占。

SettlePort.requestRefund(RefundRequest) 返回 RefundDispatchResult{ACCEPTED, SUCCEEDED, FAILED, UNKNOWN}，不能用非空流水号证明成功。可信同步成功、异步回执和回查经同一幂等成功入口；失败区分可重试、确定永久失败、结果未知。可重试用同一个不可变执行号与方案；UNKNOWN 先回查，不能改号重发另一退款或启用线下/积分替代。确定永久失败进入人工，不自动改变批准金额；人工切换路径须证明原请求不能再成功并记录买家同意。

回退分账也有独立请求结果与恢复阶段。外部资金成功不随本地事务回滚；执行决定、通道消息、回执认领与 outbox 要构成可恢复链路。预占、实退、库存与权益账分别按执行/事实幂等；本地 CAS 冲突不能抹掉已经动钱的证据。

### 13.4 结算与归集供应商追偿

SettlementRefundBasis（拟持久化在 stl_bill_refund_basis，未建表）保存不可变原始商品现金实付、商家所得、佣金、服务费、积分费用/补贴及运费归属快照。每项本次份额 = floor(原始总额 × 退后累计 / 原始商品现金实付) − floor(原始总额 × 退前累计 / 原始商品现金实付)。剩余应付、实际已付、累计已回退、待追回分别记载，不能把扣减后的应付当作原始比例基数。

分账前扣剩余应付；分账后回退实际已付份额；先部分退款再分账再退款使用同一不可变基数并按资金事实恢复。运费份额单列，不能在货款比例中重复回退。
FinancialClosure 独立计算剩余应付、已付未回退、待追回及合法留存；goodsClosed 不自动把结算单标 REVERSED，保留运费/损耗的合法商家应付仍可结算。
归集供应商已付款后，退款形成可审计追偿记录（责任方、金额、原付款与售后关联、追回/下期抵扣结果），不是单纯冲减已付款账单。买家退款不等供应商追偿；平台垫付来源、额度与授权规则仍待评审，不能以推荐原则替代资金批准。

### 13.5 申请预览与待评审决策

拟定接口分为可退事实与方案预览：

- GET /mp/order/{subOrderNo}/refundable 只返回当前可退事实、各行现金/数量/预占、运费事实、路径能力，以及 normalDeadlineAt / qualityDeadlineAt；不通过复杂 query 编码选行。
- 新增只读 POST /mp/order/{subOrderNo}/after-sale-preview，输入 {type,reasonCode,items[{itemId,qty}],refundMinor?}，计算当前方案/effectiveDeadlineAt/运费资格及其理由；不占申请槽位、不写账。用途由服务端按流程映射并校验。items省略按用途决定，只有金额不推导全退件数。
- 最终售后提交复用同一个 planner，在事务内重读事实并按版本/CAS重验金额、数量、履约与窗口。预览不是锁价/占位，过期应返回明确冲突及新可退值。

动作合同拟采用 ActionDescriptor（actionContractVersion=1）；版本缺失表示旧合同需要兼容映射，空动作集合表示确无动作，不能以旧端按钮猜测资金授权。

待评审：上述用途与订单终态投影；零现金权益结清事件；库存取消/实收/验货落点；未知退款转人工与换路证明；结算快照及归集垫付授权。积分域重整整套方案仍待确认，本轮不新增或实施积分域 18 张表；订单只要求真实权益结果、幂等和恢复能力。
