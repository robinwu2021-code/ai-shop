# 订单领域模型（草案）· 门店 / 订单 / 支付单 / 物流单 关联

> 2026-10-12。基于淘宝式三层方向（见 [订单服务设计](./2026-10-11-订单服务-详细设计.md) 末轮澄清）。
> ⚠️ 草案：①②③④ 核心问题尚未拍板，图中 `假设` 标记处待你确认。

---

## 1. 一句话模型

**一次付款（支付单）→ 一或多笔订单（每笔一个门店，ADR-031）→ 每笔订单一或多个发货单（每个带运单）**。
门店就是拆单维度（一店一单）；此外行上另记**供货门店**、发货单上记**发货门店**。

## 3. 实体清单（现状 → 目标）

| 实体 | 是什么 | 现状对应 | 目标变化 |
|---|---|---|---|
| **支付单 Payment** | 一次付款的聚合 | `ord_order`（主单） | 语义收窄为纯支付；暂与订单 1:1 |
| **订单 Order** | 买家对一个门店的一笔交易，业务核心对象 | `ord_sub_order`（子单） | 粒度**门店**（维持现状，ADR-031）；订单号对外不含支付单结构 |
| **订单行 OrderItem** | 一个 SKU 一行 | `ord_item` | 新增 `supplyStoreNo`（供货店）、`shipmentNo`（发货后归属） |
| **发货单 Shipment** | 一次发货/一个包裹 | **无**（运单挂子单 1:1） | **新增层**；订单 1..N |
| **运单 Waybill** | 承运商单号与轨迹 | `lgs_waybill` / `lgs_waybill_node`（`biz_ref`=子单） | `biz_ref` 改指**发货单** |
| **门店 Store** | 卖货/发货的实体店 | `mch_store` | 从拆单维度降为"供货/发货"属性 |
| **商家 Merchant** | 经营主体 | `entityNo`（主体） | 订单的归属主体 |
| **售后 AfterSale** | 退款/退货 | `ord_after_sale`（子单级） | 假设③：下沉到**行级**（可退部分件） |

## 4. 关联基数

| 关系 | 基数（暂时 / 将来） | 说明 |
|---|---|---|
| User → Payment | 1 : N | 一个买家多次付款 |
| **Payment → Order** | **1:N** | 一次付款按门店拆成一或多笔订单（同商家多店 = 多笔，淘宝式） |
| Merchant → Order | 1 : N | 订单只属一个商家 |
| Merchant → Store | 1 : N | 一个商家多家门店 |
| Order → OrderItem | 1 : N | 一笔订单多个商品行 |
| Store → OrderItem | 1 : N | 行记供货门店 |
| **Order → Shipment** | **1 : 0..N** | 下单时 0 个；发货后 1..N（多数 1，一起发） |
| Shipment → OrderItem | 1 : N | 一个发货单发哪些行（部分发货，假设②） |
| Store → Shipment | 1 : N | 发货单记发货门店 |
| Shipment → Waybill | 1 : 0..1 | 快递才有；自提/自送无运单 |
| Waybill → WaybillNode | 1 : N | 轨迹 |
| OrderItem → AfterSale | 1 : 0..N | 行级售后（假设③） |

## 5. 门店的双重角色（①的落点）

订单=门店（ADR-031）；门店之外，行与发货单另记两个门店角色：

| 角色 | 挂在哪 | 用途 | 多数情况 |
|---|---|---|---|
| **供货门店** `supplyStoreNo` | 订单行 | 这件货哪家店卖的 → 营销/统计/可见性归属 | 一笔订单的行通常同一门店 |
| **发货门店** `shipStoreNo` | 发货单 | 这个包裹哪家店发的 → 物流、备货台归属 | 与供货店一致 |

> 两者分开是为了容纳"A 店卖、调 B 店的货发"这类少数场景；多数相等。若你认为不需要区分，可合并为订单级一个 `storeNo`（更简单）——待①确认。

## 6. 现状 → 目标 的关系变化（迁移要点）

| # | 现状 | 目标 | 影响 |
|---|---|---|---|
| R1 | 主单 1:N 子单（**按门店**，可跨商家） | 支付单 1:N 订单（**按门店**，不变） | 拆单维度维持门店（ADR-031），`split` 不改 |
| R2 | 运单 `biz_ref` = 子单（1:1，只能发一次） | 运单 `biz_ref` = 发货单（订单 1:N 发货单） | **新增发货单层**；`ship()` 从"改子单单号"变"建发货单" |
| R3 | 售后 → 子单 | 售后 → 订单行（可部分件） | 售后粒度变细（假设③） |
| R4 | 金额/积分在子单 | 在订单 | 粒度不变（门店） |
| R5 | 跨商家主单（现状支持，测试有） | 维持：多订单一起付 | 无存量处理 |

## 7. 待你确认的假设（对应上一轮 ①②③④ + 新增）

| 假设 | 内容 | 影响图中 |
|---|---|---|
| ① | 订单=门店（ADR-031，已定）；行另记供货门店、发货单记发货门店 | Store 的两条关系 |
| ② | 下单不预拆包裹，**发货时**商家勾行+填单生成发货单，支持部分发货 | Order→Shipment、Shipment→Item |
| ③ | 售后对准**订单行**（可退部分件），非整订单 | AfterSale→OrderItem |
| ④ | 现在是否允许跨商家购物车下单（决定存量处理） | Payment→Order 基数 |
| ⑤(新) | `fulfillment` 放在**发货单**层（一订单理论可多种履约，多数一致）还是订单级 | Shipment.fulfillment |
| ⑥(新) | 订单行是否允许**同一行分批发货**（买3件先发1件） | Shipment↔Item 是否要带数量 |

> 我的默认倾向：①是 ②是 ③是 ⑤发货单级 ⑥暂不支持行内分批（一行整件归一个发货单，够覆盖"多数一起发"且简单）。
> 你逐条过一遍，或直接说"按默认"，我就把这版升成正式模型，再往下梳理**状态流转**（下单→部分发货→部分收货→完成，以及各层状态如何联动）。
