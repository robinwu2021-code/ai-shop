# 线上交易赠送积分规则改造

依据：本对话中用户批准的修改方案。执行范围为交易规则、积分运营页面及现有支付积分链路，不修改 B/C 客户端。

- 积分设置只维护类型及兑换配置；新增独立“赠送规则”列表，操作使用现有抽屉/弹框。
- 线上订单沿用市场订单默认积分类型。所有门店默认参与，不增加门店、商品例外或营销叠加。
- 商品末级品类 → 最近配置上级 → 默认规则；明确不赠送终止继承，停用覆盖恢复继承。
- 按优惠及积分抵扣后商品现金实付金额的百分比折算积分，排除运费；万分比整数 0..10000，沿用支付精度向下取整。
- 新订单在服务端匹配并冻结规则修订；历史快照继续读取，不重新解释。
- 复用支付 PENDING / AVAILABLE 及统一 Outbox：支付后待入账、完成后可用；退款与追回继续走原生命周期，禁止另建账本。
- 规则写操作权限、版本校验、请求幂等、不可变修订及操作审计。
- 现有兜底值按需复制为默认规则，固定赠送保留兼容并明确提示，不猜测转换；旧写入口退出。
- 发放可追踪，预算不足不透支、可受控重试。仅进行本次定向测试，不做全量和并发测试。

## 实施细节

- 交易域 `PointsEarningRules`：`ord_points_earn_rule` 保存当前草稿和生效修订，`ord_points_earn_rule_revision` 保存不可变历史及请求回执。首次读取/下单时按类型幂等迁入旧兜底配置，后续旧入口禁止写入；固定规则保持原值直到运营发布比例版本。
- 商品域通过 `PointsEarningCatalogPort` 提供平台品类及商品所属品类，交易侧不信任候选行携带的规则和品类。快照 schemaVersion=2，逐行记录命中范围与修订；缺少 trace 的 schemaVersion=1 仍可读。
- 服务端以市场订单默认类型为准；运营规则页面不提供默认类型切换。品类规则覆盖默认值，草稿保存不会替换 activeMode/activeValue。
- 支付沿用待入账和完成后转可用；接受的发放遇预算不足抛出可重试异常，不写永久跳过回执。退款准备在缺少发放/核销持仓时，必须验证已支付事实、支付快照及累计商品退款。
- 延迟发放按照原支付商品金额基线扣除已经确认的累计退款，后续退款继续计算差额；已承诺交易允许在类型 DRAINING 时完成记账。
- 运营端“发放与核销”的“处理记录”抽屉展示事件、失败原因、次数和处理状态；仅 MANUAL 状态开放带备注与版本校验的重新提交，复用原队列及操作审计。

接口：`GET earning-context`、`GET/POST earning-rules`、`GET earning-rule-history`、`POST earning-preview`、`GET order-earning`，统一位于 `/ops/points/`。复用原 `/ops/points/events` 与 `event-retry`。
