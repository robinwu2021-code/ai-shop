# 第二阶段：统一积分操作接口设计

状态：第二阶段本地开发及 24 项定向验证完成；未切换业务接线、推送或部署。

## 目标与范围

承接第一阶段赠送规则配置与统一试算接口，由支付系统提供发放、预占/释放、核销、退款追回、账户冻结/解冻、余额与操作状态查询。统一预算、精度、幂等、审计和记账入口；规则服务只计算，不产生积分余额。

本期实现能力与契约，不将订单、营销或结算业务切换至新接口，不改 B/C，不执行线上金融操作。不将“结算”作为任意修改积分余额的命令；门店结算沿用既有资金及应收处理服务，业务接入属于第三阶段。

## 现状及缺口

| 能力 | 现有实现 | 第二阶段补充 |
| --- | --- | --- |
| 发放 | PointsEarnPort / EarnService；订单行规则快照、预算与待入账/可用账本 | 明确受理与记账完成的区别；新操作标识含积分类型；仅支持有可信来源的交易赠送，不伪造营销订单 |
| 抵扣预占 | PointsRedeemPort / RedeemService | 新接口显式选择积分，旧接口保留市场默认路由；预占不等于核销 |
| 释放预占 | RedeemService.release | 新请求按类型与原操作标识定位；兼容旧根持仓与旧命令 |
| 核销 | 已支付事实通过事件队列完成既有持仓转换 | 统一事实接收与状态查询，不开放“传数量就扣账”接口 |
| 退款追回 | PointsRefundPort 准备、现金授权、确认、终止、补偿及恢复查询 | 复用既有证据链，统一调用入口；不得仅凭业务成功字段确认退款 |
| 账户冻结 | PointsAccountControlService / PointsInspectionService.freeze | 区分账户禁用与金额预占；保留版本、请求幂等和操作审计 |
| 余额 | PointsInspectionService / PointsReadStore | 增加公共 SPI 的稳定余额 DTO，不向业务模块泄漏 pay 的模型与 SQL |
| 受理事件 | PointsFactPort / PointsEventQueue | 复用已有队列、Outbox、重试与人工处理，不建立另一套消息系统 |

已核实的限制：RedeemQuery/HoldCommand 没有显式类型选择；发放凭证 ref 为 GRANT:subOrderNo；预占根持仓和凭证按 orderNo 定位。这些键不能直接承载同一业务的多种积分操作。

## 推荐方式与替代方案

推荐：保留旧 SPI 行为，新增版本化统一操作契约与支付域适配，复用现有 Posting、配置、事件及退款内核。新契约使用显式类型与完整业务标识，旧凭证、旧持仓继续按旧路径读取、重放及退款。

不推荐将已有几个接口简单合并为一个继承接口：无法解决默认类型路由、凭证碰撞及受理状态歧义。

不推荐另建通用积分账本：会重复预算和退款责任，造成两套余额来源。

## 接口职责

统一入口放在 shop-base 的 PointsOperationsPort，实现在 pay-domain；公共 DTO 不引用支付内部持仓、Mapper 或账本实体。规则接口仍为 PointsEarningRulePort，不能倒置为 pay-domain 依赖 shop-app 规则实现。

接口按职责划分为三组：

1. 查询：账户余额、操作结果、预占/核销状态、退款状态。
2. 命令：交易赠送受理、抵扣报价、预占、释放、账户冻结/解冻、退款准备及原证据链确认。
3. 可信事实：支付、完成、取消、售后结束事实接收，用于已有承诺的状态推进。

不把所有命令塞进带 action 字符串的万能请求。每种命令有明确 DTO 和返回结果。

余额 DTO：typeCode、currency、holderType、holderNo、exists、pendingPoints、availablePoints、heldPoints、frozen、expireAt、version。缺失账户返回 exists=false 和零余额，读取不创建账户，不把 PENDING 或 HELD 作为可用余额。过期状态按现有查询语义展示，不在读取中直接修复账本。

冻结是账户控制，预占是 AVAILABLE → HELD 的余额变化。禁止用冻结接口替代订单预占，禁止解冻时直接释放已有持仓。

## 新操作标识与兼容

业务标识由 source、businessNo、operationNo、typeCode 构成；金额相关命令另带币种、输入摘要及来源版本。source 为受支持的业务来源枚举，首版仅开放现有可信交易链路，其他来源明确拒绝。业务编号长度及编码受控，内部键使用规范化内容的摘要，避免拼接分隔符歧义。

- requestId 是请求重试标识；业务操作标识是记账去重标识，两者不能混用。
- 同一请求、同一规范化内容返回原回执；同一请求或业务操作换内容返回幂等冲突，不写第二笔账。
- 新凭证和持仓使用带版本的命名空间，与旧 GRANT:subOrderNo、HOLD:orderNo 等隔离。
- 同一个原业务承诺不得同时通过旧路径和新路径重复发放。第三阶段切换必须保存接线版本/原操作映射；新接口在缺少新承诺标识或遇到已存在旧承诺时拒绝，不自动制造新的承诺。
- 旧接口、旧 DTO 构造、已存储 JSON、退款定位及恢复任务保持兼容，不回写历史凭证和历史规则快照。

## 计算、预算与生命周期

业务先取得第一阶段的规则计算快照，然后保存业务承诺。支付发放接收可信业务事实及冻结后的逐行规则快照，不能只相信外部传入最终积分数量；支付按已有精度规则复核金额与数量。新统一接口不能让普通运营页面伪造已支付或已完成事实。

每次新承诺校验显式积分类型、币种、市场、ACTIVE 状态、积分精度、账户状态、预算及既有适用开关。已受理承诺沿用 DRAINING 履约规则；同类型状态校验不能阻止对历史承诺退款、释放或追回。跨币种拒绝，不自动换汇。

发放预算不足不透支、不返回已发放；已持久化受理事件继续由现有队列按原策略重试/进入人工处理。零赠送是明确结果，不以余额不足冒充零赠送。

交易赠送保留 PENDING → AVAILABLE；抵扣保留 AVAILABLE → HELD → 已核销，取消后释放 HELD。退款沿用累计商品退款、原始实付基线及差额追回规则；现金与积分退款继续通过准备/证据确认/补偿状态机协同，不简化为单次扣积分。

回执明确区分 ACCEPTED、PROCESSING、SUCCEEDED、SKIPPED、RETRYABLE、MANUAL、REJECTED；由现有事件及持仓状态映射，不能收到 ACCEPTED 就显示积分已到账。幂等回执属于原操作结果，不将新的 requestId 误认为新的财务执行。

## 事务与权限

所有账本、预算和持仓变更归属 payTxManager 下既有支付事务。统一 facade 不包裹跨业务数据库的大事务，也不从运营端直接调用 PostingService。

本期提供内部 SPI，不新增无鉴权 HTTP 写接口。未来跨进程适配必须复用支付内部鉴权、调用方范围及业务事实验证；端侧仍由既有应用层做属主与数据域校验。不同权限的账户控制与交易发放保持明确入口，统一契约不能等于向所有调用方授予所有能力。

## 实施顺序与定向验收

1. 固化新公共 DTO、请求标识、余额及状态查询；验证缺失账户、跨类型隔离、非法参数及只读不写账。
2. 增加显式积分报价与预占路径、类型化操作定位；验证两种类型同业务编号互不碰撞、同操作改参冲突、旧命令重放兼容。
3. 发放受理与状态查询封装；验证预算不足、重复受理、待入账转可用、退出类型旧承诺及旧新路径防双发。
4. 退款、预占释放与账户控制封装；验证原证据校验、累计退款差额、重复确认、冲突命令及补偿状态不丢失。
5. 更新契约与接入示例；仅运行本次服务/持仓/旧接口兼容测试和后端编译，不全量和并发测试。不修改 B/C，不做真实发放或退款。

验收以真实支付内核与隔离测试数据库验证为主；不能只验证 facade 对 mock 方法的转发。第一阶段规则代码保留在当前隔离工作区，与第二阶段的 diff 分开记录。
