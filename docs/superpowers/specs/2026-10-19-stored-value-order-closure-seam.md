# 储值与订单结清接缝设计

状态：独立接缝设计，待储值项目联调；不表示本分支已实现储值。本轮订单退款范围已收敛为整单退款，不能据此开放储值退款。

依据：`docs/technical/TDD-美业储值-系统详细设计.md` §1、§2.3–2.6，以及 ADR-038。活动规则和参与预算归 core，权益账户、核销与账务归 pay；具体 schema/API 随独立权益项目冻结，不在本文件另造一套。

## 能力与权威

|能力|本期处理|
|---|---|
|线下实收后发放本金/赠金|独立储值项目实现；实收事实与到账事实分开|
|同主体、同币种、合格门店/项目全额储值核销|独立项目实现；订单仅接受权威成功凭据|
|余额不足|整笔拒绝，不先扣尽后补假现金|
|支付未确认时取消并释放预占|允许，须源订单权威取消凭据；不称作退款|
|已消费线上退款、退储值余额、任意调账|本期排除；争议进入客服/财务待办，保留原核销|
|现金加储值、积分加储值、跨主体/币种|本期排除，入口和服务端均拒绝|

账户键固定租户、用户、主体和币种。批次固定原本金/赠金、适用范围及活动版本；消费按既有设计的可用比例分配并固化到 allocation，不能在订单回调时按当前余额或新活动重算。取消只能释放未提交 hold；COMMITTED 不可释放。将来退款须依据原 allocation 逐批退回，累计不超原扣减；该规则仅为后续设计约束，当前没有退款命令/API。

## 订单接入协议

1. 会员码仅识别，消费另需绑定订单号、版本、金额、币种、主体、门店的本人授权。识别结果不构成扣款许可。
2. core 在订单事务保存支付意图与可靠 Outbox。pay prepare 冻结明确原分配，重复同键同参返回原结果，异参冲突。
3. pay commit 核验源意图版本与授权，账户、批次、分录、唯一凭证与事件同一 pay 事务提交。整笔成功才产生可供订单使用的付款事实。
4. core Inbox 验证来源、订单版本及金额币种后推进 PAID。pay 已成功而订单未更新时，只重投原事件，不再扣款。支付成功和服务完成是不同事件。
5. 取消与 commit 的胜负按持久源支付意图串行决定；结果未知只查原号。没有取消成功证据不因本地超时释放预占。
6. 本期 ord_after_sale 的现金全退能力不自动适用于储值服务单。储值付款订单进入受限售后/人工流程，不能生成现金通道退款替代储值退回。

混合支付将来需分别引用现金和储值权威凭据；只完成一种时不能称作付款或退款全部完成。本期明确拒绝混合支付，故不实现该扩展分支。

## 联调前需由独立项目交付

可信源支付意图查询与取消证明、本人授权能力、pay 预占/确认/释放凭据、成功事件与 Inbox 去重键、门店权限白名单和读模型。接口使用既有独立设计的最终名称；不得跨数据源 SQL/事务读取储值余额，也不得复用积分余额。

迁移版本在集成前统一分配。当前工作区已有活动/储值设计修改及独立储值工作树；本任务不提交其文件，不同时创建另一套储值实现。
