## 0. 结论

**阅读边界（本轮修订）**：本文件正文的 D1–D5、数量闭合、新事件、退款执行记录、订单级串行协议与灰度门槛均为待评审目标设计，不是代码现状或上线验收记录。历史实现进度只查 [TDD-订单状态机](../../technical/TDD-订单状态机.md) 的分步记录；发货单写路径与新状态交互属于后续接线。10-11/10-12 文档保留历史内核记录，其主单/packages 买家模型和旧 `OrderTransitions` 方案不再作为新增实现依据。

对象口径：Payment 是一次付款；Order 是一门店一笔交易（[ADR-031](../../technical/ADR/ADR-031-子单按门店拆与运费按商品门店计算.md)）；Shipment 是包裹/交付批次。线上合并支付可覆盖多门店。D1 建议新增线下 Payment 仅覆盖一个门店；旧跨店线下单转人工对账，不因任一门店确认而自动推进其他门店。


1. **四个聚合、四台状态机**：支付单、订单、发货单、售后单。每台机器由「状态 × 事件 × 执行者 × 守卫 × 副作用」五元组定义，不再只是「A 能到 B」的图。
2. **状态机是纯函数**：输入（当前状态、事件、上下文），输出（新状态 + 要发的领域事件）；不碰库。落库、记流水、发事件统一由**状态转换门**（`StateTransitionGate`）做，持久化一律 **CAS**（`where status = 旧值`）。
3. **「退款永不自动」写进机器**：所有进入「退款执行中」的迁移只允许 `MERCHANT` / `PLATFORM` 触发；`SYSTEM` 只有一条例外（交易不成立的原路退回），由不变式测试锁死。
4. **备货、退款进度、履约阶段不是状态**：备货是事件 + 属性；退款进度由退款账本推导；履约阶段由发货单与运单推导。状态集合因此保持封闭。
5. 售后单拆出 3 个新状态（等寄回 / 已寄回 / 协商中）和 2 个线下退款态（待线下退款 / 已线下退款待确认），消掉现在 `REFUNDING` 一身兼三职的歧义。

## 1. 聚合与它们的关系

```text
支付单 Payment (ord_order) 1 ──< N 订单 Order (ord_sub_order，一店一单)
订单 Order 1 ──< N 发货单 Shipment (ord_shipment)
订单 Order 1 ──< N 售后单 AfterSale (ord_after_sale) 1 ──< N 售后行 (ord_after_sale_item)
订单 Order 1 ──< N 订单行 Item (ord_item：paid_share / refunded_qty / refunded_minor)
```

**不是状态、但要被状态机读到的事实**

| 事实 | 存在哪 | 怎么来 | 谁用 |
|---|---|---|---|
| 已开始备货 | `ord_sub_order.prepared_at`；操作者在事件流水 `operator_no`（当前没有 `prepared_by` 列） | 订单事件 `PREPARE`（不改状态） | 售后建议、买家提示 |
| 现金退款比例 `cashProgress` NONE / PARTIAL / FULL | 现金实际退款账本；旧 `refund_progress` 为历史字段，不复用为商品闭合判据 | 仅已确认成功的现金执行累加（通道回执/线下买家确认） | 三端金额进度，不独自决定订单终态 |
| 商品交易闭合 `goodsClosed` 与数量 | 行上 `closedQty/cancelledQty/returnedQty`，申请/决定上的 `coveredQty` | D2/D3 的数量规则；金额调整不占件数 | 履约待办、订单完成/退款终态 |
| 已批准执行决定与预占 | 不可变的批准决定 + 执行记录 `PREPARED` + 预占账 | 商家/买家接受/平台明确决定后先持久化；回执才记实退 | 退款重试、未知结果回查，避免预占伪装成功 |
| 履约阶段（未备货 / 备货中 / 已出单 / 运输中 / 已到自提点 / 已签收） | 推导，不落库；售后单申请时**快照** | `FulfillStage.of(订单, 发货单, 运单)` | 售后守卫与建议 |
| 售后期截止 | 推导：`completed_at + 7d`（质量类 15d） | 配置 | 售后申请守卫 |

## 2. 支付单（ord_order）

| 状态 | 含义 | 终态 |
|---|---|---|
| `WAIT_PAY` | 待线上支付 | |
| `WAIT_OFFLINE_PAY` | 待商家当面收款 | |
| `PAID` | 已支付 | ✅（之后的变化都在订单） |
| `CANCELLED` | 买家 / 平台取消 | ✅ |
| `CLOSED` | 支付超时关闭（对外投影为 CANCELLED） | ✅ |

| # | 从 | 事件 | 执行者 | 守卫 | 到 | 副作用（领域事件） |
|---|---|---|---|---|---|---|
| P1 | （无） | `PLACE` | BUYER / PLATFORM（代客） | 下单校验；线下付款仅单门店（D1） | WAIT_PAY 或 WAIT_OFFLINE_PAY（按支付方式） | `PaymentPlaced` |
| P2 | WAIT_PAY | `PAY_SUCCEEDED` | CHANNEL（支付回调） | 金额一致、验签 | PAID | `PaymentPaid` → 级联订单 O1 |
| P3 | WAIT_OFFLINE_PAY | `OFFLINE_CONFIRMED` | MERCHANT | D1：本店且 Payment 只有该门店；旧跨店单不走此事件 | PAID | `PaymentPaid` |
| P4 | WAIT_PAY / WAIT_OFFLINE_PAY | `CANCEL` | BUYER / PLATFORM | 本人 / 有代客权限；先解析并授权完整影响集，不能按读数据域截断级联 | CANCELLED | `PaymentCancelled` → 级联 O2、释放库存券积分 |
| P5 | WAIT_PAY | `PAY_TIMEOUT` | SYSTEM | 已过 `pay_deadline_at` | CLOSED | `PaymentClosed` → 级联 O2、释放 |
| P6 | CLOSED / CANCELLED | `LATE_PAY_SUCCEEDED` | CHANNEL | 回调晚到；以原通道交易号认领到账、判重（D4） | （不变） | `TradeVoidRefundRequired`（交易不成立的原路退回，§5 A3） |

> P5 与 P2 并发：两边都 CAS `where status='WAIT_PAY'`，只有一方成功；关单失败方**不释放库存/券**（修《退货退款逻辑》§11 所列 B4）。

|---|---|---|
| `WAIT_PAY` | WAIT_PAY / WAIT_OFFLINE_PAY（按支付单） | |

|---|---|---|---|---|---|---|
| O1 | WAIT_PAY | `PAY_CONFIRMED`（级联自 P2/P3） | SYSTEM | — | 服务类即出码：FULFILLING；其余：WAIT_FULFILL | `OrderPaid`（通知商家） |
| O2 | WAIT_PAY | `CANCEL`（级联自 P4/P5） | SYSTEM | — | CANCELLED | — |
| O3 | WAIT_FULFILL | `PREPARE` | MERCHANT | 本店；无进行中售后；未备过 | （不变，写 `prepared_at`） | `OrderPrepared`（通知买家） |

| O7 | WAIT_FULFILL / FULFILLING | `DELIVERED_BY_MERCHANT`（商家标记送达；自送单可能已在配送中） | MERCHANT | 本店；D3/D5 验证全部剩余交付范围闭合 | COMPLETED | `OrderCompleted` |
| O8 | WAIT_FULFILL / FULFILLING | `RECEIPT_CONFIRMED` | BUYER | 本人；订单级命令确认剩余交付范围，按 D3/D5 判所有数量闭合 | COMPLETED | `OrderCompleted` → WAIT_RECEIPT 提醒（不触发退款决定） |
| O9 | FULFILLING | `RECEIPT_AUTO_CONFIRMED` | SYSTEM | 包裹各自到期且剩余履约数量闭合；**无进行中售后**；D5 原子校验 | COMPLETED | 同上（确认收货不是退款，保留自动） |
| O10 | WAIT_FULFILL / FULFILLING / COMPLETED | `FULLY_REFUNDED`（级联自退款账本） | SYSTEM | D3：`goodsClosed` 且已批准退款/权益均结清；不能仅凭现金比例 | REFUNDED | `OrderRefunded` → 整单全退时退券 |
| O11 | WAIT_FULFILL / FULFILLING | `INTERVENE` | PLATFORM | 有干预权限；**仅非资金迁移**；备注必填 | FULFILLING / COMPLETED | `OrderIntervened`（审计） |

- **人工干预不再能改到 REFUNDED / PAID / CANCELLED**：动钱的走售后裁决、对账处置。运营端迁移表同步收窄。
- 金额调整不改变履约数量或商品交易是否终止；现金部分退只改变 `cashProgress`。取消/退货数量须重算履约闭合：取消与已交付混合闭合进 COMPLETED，全部商品交易终止且退款/权益结清进 REFUNDED（D3）。已按协议保留的运费、买家接受的损耗不属于欠退余额。

|---|---|---|
| `APPLIED` | 待商家处理 | 同 |
| `NEGOTIATING` 🆕 | 商家提出协商金额，待买家回应 | 无 |
| `WAIT_RETURN` 🆕 | 商家同意退货，待买家寄回 | 现在混在 REFUNDING（无运单号） |

**终态与账本（A13 / A21 / A22）**：批准决定先持久化；`PREPARED` 预占不记实退。成功回执或线下买家确认后，在同一事务释放/转实预占、以决定号和执行号幂等记现金与数量/权益账，再按 D3/D5 重算订单。退款成功回执与售后终态重放不得重复累计。零现金没有通道回执，凭权益结清事件 A22 收尾；SYSTEM 只是执行既有批准决定，不能产生退款决定。优惠券按其支付影响集全部应退权益结清后的规则归还；不能用“全部订单终态”（其中包含正常完成订单）代替“券对应范围全部退完”。抵扣/赠送积分按批准退款目的和比例退回/扣回。

现金成功先落实退与权益意图；权益仍待处理时，执行资金状态SUCCEEDED、售后仍REFUNDING，三端分别显示现金与权益结果。非零现金权益完成事件依据已保存的成功凭据重新评估A13，线下则依据买家确认重新评估A21，不要求第二次渠道回执，不再发送现金退款；A22只处理零现金。

## 6. 跨聚合联动

| 触发 | 后续 | 同事务？ | 原因 |
|---|---|---|---|
| P2 / P3 支付成功 | 每张订单 O1 | **同事务** | 钱到了订单必须同时可履约，否则「付了钱看不到单」 |
| P4 / P5 取消关闭 | 每张订单 O2 + 释放库存券积分 | 同事务 | 释放必须与状态原子，否则重复释放或漏释放 |
| P6 迟到回调 | 售后 A3 | 同事务 | 不能让钱无主 |
| 发货单 H2 首张揽收 | 订单 O4 | 异步（轨迹推送）+ 幂等 | 轨迹来自外部 |
| 发货单 H3 签收 | 售后 A9 的提醒 | 异步 | 只是提醒 |
| 发货单 H4 收货 / 取消数量变化 | 订单级锁内重算，按 D3 触发 O8/O9/O10 | 同事务 | D5：避免并发包裹各自看不到对方导致漏完成 |
| 售后 A13 / A21 / A22 落定 | 实退/权益账 → 数量闭合重算 → 订单终态及退券 | 同事务 | D3/D4：PREPARED 与实退分开；现金比例不等于商品闭合 |
| 订单 O8 / O9 完成 | 售后期起算；WAIT_RECEIPT 提醒商家确认 | 异步 | — |

同事务联动由 `StateTransitionGate` 与业务编排执行；跨包裹/数量的守卫按 D5 先获得所属订单的串行权，再用当前读校验，不能只将各行更新放进事务。领域事件在同一事务落 outbox、提交后投递；外部 IO 不持有订单锁。异步消费遵守幂等和物流版本隔离规则。

## 9. 对外契约

- **订单**：仍是 7 个契约值（`OrderStatusProjector`，已接线），外加 `refundProgress`（现金比例 NONE / PARTIAL / FULL）、`refundedMinor` 与本轮建议新增 `goodsClosed`；内部 cashProgress 不重复下发为同义字段。
- **售后单目标契约**：12 个状态（新增 5 个）。扩展枚举/查询/三端处理能力先部署；只有当前可见客户端能完整处理对应状态与动作后，才开放该新状态的创建入口，不能把目标契约写成当前全部已下发。三端词条与徽章需同步：

| 状态 | C 端 | B 端动作 | 运营端 |
|---|---|---|---|
| NEGOTIATING | 商家提议退 ¥x：接受 / 拒绝 | 等买家回应 | 协商中 |
| WAIT_RETURN | 请寄回并填运单 | 等寄回 | 待寄回 |
| RETURNING | 已寄回，等商家确认 | 确认收货并退款 | 已寄回 |
| WAIT_OFFLINE_REFUND | 商家将线下退款 | 登记线下退款（金额 / 方式 / 凭证） | 待线下退款 |
| OFFLINE_REFUNDED | 商家已线下退款：确认收到 / 有异议 | 等买家确认 | 线下退款待确认 |
| WAIT_RECEIPT（已签收） | 已签收，等商家确认退款 | 确认退款 | 待商家确认 |

- 本轮目标动作合同：`actionContractVersion=1` + `allowedActions: ActionDescriptor[]`；纯状态机 `allowed(...)` 的事件集合经资源/意图上下文映射成动作描述。缺合同为旧版本兼容路径，存在合同而空集合表示无动作；不能把空集合回退成旧前端状态按钮。
- 能力协商拟用独立 `X-Trade-Capabilities` 受控集合，不复用 X-Client。需要买家接受/确认的新状态，必须目标买家端也能处理，不能仅凭新 B 端版本开放；关闭创建入口不能关闭已有单出口。
- 查询拟区分资源事实 GET refundable（普通/质量双窗口）与只读 POST after-sale-preview（按 type/reasonCode/items 试算）；申请提交重验资格/数量/金额/能力，报价不构成预占或批准决定。三端按钮按动作描述画，后端仍原子重验。

## 10. 类设计

包：`ai.neargo.shop.trade.order.statemachine`（引擎）+ 各聚合子包。单类 ≤ 200 行、单方法 ≤ 50 行。

```text
statemachine/                       引擎（与业务无关，可单测）
  Actor                    enum     BUYER · MERCHANT · PLATFORM · SYSTEM · CHANNEL
  Transition<S,E,C>        record   from(Set<S>) · event · actors(Set<Actor>) · guards(List<Guard<C>>) · target(TargetResolver<S,C>) · effects(List<EffectFactory<C>>)
  Guard<C>                 iface    Optional<ErrorCode> check(C ctx)
  TargetResolver<S,C>      iface    S resolve(S from, C ctx)          —— 一事件多去向（A4 按类型与阶段分流）
  EffectFactory<C>         iface    DomainEvent create(C ctx)         —— 只产出事件，不做 IO
  StateMachine<S,E,C>      final    fire(S from, E event, Actor actor, C ctx) → Fired<S>；allowed(S, Actor, C) → Set<E>
  StateMachineBuilder      final    from(..).on(..).by(..).when(..).to(..).emit(..) 的 DSL
  Fired<S>                 record   from · to · event · actor · events(List<DomainEvent>)
  Invariants               final    供测试：枚举定义、校验 I1–I4

payment/   PaymentStatus · PaymentEvent · PaymentContext · PaymentMachine(定义 P1–P6)
order/     OrderStatus · OrderEvent · OrderContext · OrderMachine(定义 O1–O11)
shipment/  ShipmentStatus · ShipmentEvent · ShipmentContext · ShipmentMachine(定义 H1–H6)
aftersale/ AfterSaleStatus · AfterSaleEvent · AfterSaleContext · AfterSaleMachine(定义 A1–A22；A22 本轮建议)
           guards/  OwnerGuard · WindowGuard · RefundableGuard · ChannelCapabilityGuard · StageGuard · NoOpenAfterSaleGuard · ReasonGuard
           RefundLedger（行已退额累加、进度重算；复用 RefundCalc）

transition/                          状态转换门（唯一写入口）
  StateTransitionGate      final    apply(Command) → Fired：load → machine.fire → store.cas → log.append → outbox.publish（同事务）
  Command                  record   aggregate · no · event · actor(+operatorNo) · reason · payload
  StatusStore              iface    String load(Aggregate, no)；boolean cas(Aggregate, no, from, to)
  TransitionLog            iface    append(Aggregate, no, Fired, operatorNo, reason)
  CascadeRules             final    同事务联动表（§6 中「同事务」各行）：Fired → List<Command>
  impl/MybatisStatusStore · impl/StatusLogStore
```

**调用时序（以「商家同意退款」为例）**

```text
BizAfterSaleController.approve
  → AfterSaleCommandService.approve(no, merchantNo)
     → gate.apply(Command(AFTER_SALE, no, APPROVE, MERCHANT, …))
         1. store.load → APPLIED
         2. AfterSaleMachine.fire(APPLIED, APPROVE, MERCHANT, ctx)
               守卫：OwnerGuard → ChannelCapabilityGuard → …（第一个失败即抛对应 ErrorCode）
               去向：在途仅退款 → WAIT_RECEIPT
         3. store.cas(no, APPLIED, WAIT_RECEIPT) == false → CONFLICT
         4. log.append(…)
         5. CascadeRules：无同事务联动
         6. outbox.publish(AfterSaleApproved)
```

**为什么这样切**
- 机器定义是**数据**（一张迁移表），评审时对着 §2–§5 的表逐行核；测试枚举它验不变式。
- 守卫与去向各是一个小类，规则变了改一个类，不碰机器。
- 门是唯一写入口：CAS、流水、事件在这里一次做对，业务代码里不再有 `setStatus` + `updateById`。
- `allowed(...)` 让「能做什么」只有一处真源，前端按钮、后端校验、运营端迁移下拉都从它来。

## 15. 本轮建议设计 D1–D5（待评审、未实现）

### D1 · 支付边界与授权影响集

- 新建 OFFLINE Payment 仅单门店。线上 Payment 可跨店合并支付；支付/取消命令影响整个 Payment，不允许调用者以局部子单授权代替完整影响集授权。
- 命令入口先解析完整影响集、校验权限和数据归属，再开始写入；读数据域用于展示裁剪，不能裁剪支付成功/取消的级联集合。**全影响集授权是本轮待评审政策调整**：历史运营写路径可不受读数据域过滤；全局运营处置的合法豁免需明确权限、理由和审计，不能把旧豁免描述成已确认禁止。
- 存量跨店线下单不静默改金额、拆交易或代确认。禁止商家自动确认整笔，返回可操作的人工对账入口；运营记录各店实收/未收后执行经审计的处理方案。

### D2 · 退款目的与数量账

`refundPurpose` 的待评审域：`CANCEL_ITEMS`（未交付取消）、`RETURN_ITEMS`（交付后退回并终止商品交易）、`REFUND_WITHOUT_RETURN`（已交付免退货并终止对应商品交易）、`MONEY_ADJUSTMENT`（差价/补偿，不终止商品交易）。

- `coveredQty` 是本次申请/批准决定覆盖数量；`closedQty` 是累计已终止商品交易数量；`returnedQty` 是实际寄回验收数量；`cancelledQty` 是未交付免履约数量。四者各有语义，不共用现金退款件数或单一 `refunded_qty`。
- 商品终止类决定按数量预占，现金/权益按额预占；实退与商品终止事实按目的分别记账。`MONEY_ADJUSTMENT` 的 `coveredQty=0`，不消耗可再次申请的件数，不减少待交付数量。
- `CANCEL_ITEMS` 必须未交付；`RETURN_ITEMS` 需要退回验收；`REFUND_WITHOUT_RETURN` 需要明确批准免退回。每条行的快照记录决定目的、阶段、应退额、保留运费/接受损耗、数量和证据。
- 多行跨包裹且阶段不同：按行保存阶段与可执行条件，不以最早/最晚单一阶段覆盖所有行。若采用拆执行，执行记录按行分组，售后仅在全部批准执行结清时终态。**WAIT_RECEIPT 的签收是提醒，不是新增硬闸**：商家也可明确不等签收直接确认；该人工动作的覆盖行/金额需写入批准决定，不能因第一包自动签收而擅自执行全部退款。

### D3 · 商品闭合、现金进度与权益结清

- `cashProgress` 只反映累计现金实退占实际现金支付比例，`FULL` 不能作为全部商品退款终态的唯一条件；`goodsClosed` 表示所有商品交易数量终止。
- 剩余履约数量 = 购买数量 − `cancelledQty`；已完成交付数量与取消数量覆盖全部购买数量、且没有应完成的活跃包裹时，可进 `COMPLETED`（混合“部分取消退款＋剩余交付”）。
- 所有商品交易终止且全部已批准应退现金/权益结清，走 O10 到 `REFUNDED`；合法保留的运费、买家明确接受的损耗不算欠退，故现金比例可能仍 PARTIAL。商品已正常交付后的金额补偿保持 COMPLETED。
- 零现金不能等待不存在的通道退款回执；先校验既有批准决定，再以 `BENEFITS_SETTLED` 证明积分/券等应退权益结清后关闭售后。权益失败不得提前终态。
- 对外现有 JSON `refundProgress` 保持现金比例语义，内部称 `cashProgress`，不重复新增同义 cashProgress 字段；另增 `goodsClosed`。零现金订单可以 refundProgress=NONE 且权益结清后 Order=REFUNDED。
- Order REFUNDED 或货款退满不能直接把 StlBill 标 REVERSED；独立 `FinancialClosure` 政策核算实际应退/已退、已结清权益与合法商家应付。保留运费/约定损耗仍属合法应付时继续结算，不被商品终止吞掉。
- 完成时刻仅第一次进入 COMPLETED 写入，重放不能延后售后期；全部终止为 REFUNDED 的单使用退款终态时间，不伪造完成交付事实。

### D4 · 批准决定、执行预占与未知结果

1. 人的明确批准动作先持久化不可变决定：决定号/版本、执行者、目的、行数量、现金与权益、接受损耗/运费、渠道方案。执行重试不得重新决定金额。
2. 建 `PREPARED` 执行记录并原子预占剩余现金/商品数量/权益；预占只阻止并发超退，不能写成已实退或已 REFUNDED。决定、执行记录与预占的幂等键/唯一索引必须在开发方案中列清。
3. 提交后调用渠道；退款商户单号以售后单号为业务幂等根键；若一张售后有多次独立执行，使用持久化执行序号稳定扩展，重试同一执行不换号。回执匹配决定与执行版本，成功后同事务转实预占、记实退和相应数量/权益，再重算状态。分组执行的第一笔成功只记其账本，售后继续 REFUNDING；全部批准执行与权益结清后才发终态事件 A13/A21/A22。
4. 超时/响应丢失为 UNKNOWN：优先按原商户单号回查；不能把未知当失败释放预占，也不能切成线下退款形成双退。确定失败才在受控事务中释放/更新预占并进入可重试或替代方案。
5. 对账、重试、回执重放共用执行幂等协议。迟到支付以原通道交易号认领且退款，不因支付单仍 CLOSED 就无限创建新的退款执行。

### D5 · 订单串行协议、物流收敛与发布边界

- 所有包裹状态/行归属变化、取消数量变化、核销、人工完成及完成重算，先获得所属订单行的数据库锁或等价串行令牌；在同一事务用 **current read** 重查活跃包裹与数量账，再更新状态、流水、首次完成时间和 outbox。不同包裹的单行 CAS 不能代替该协议。
- 跨支付单多订单按稳定订单号顺序锁定；资金/库存等域遵守共同锁顺序，避免反向获取造成死锁。外部 IO 在提交后执行。事务故障必须回滚全组状态/流水/事实；补偿重算任务须可靠落库且可按待处理索引查询。
- PREPARE 是原地动作，但依然原子条件写：状态可备货、`prepared_at IS NULL`、无进行中售后占位一起校验；0 行冲突不写成功流水。与售后占位共用同一订单串行权，时间与执行人一次落库。
- 可信物流签收快照在 CREATED 到达时，适配层按同一运单版本补齐 PICKED_UP，再处理 SIGNED；原始时间/来源留痕。重复/晚到的较早阶段不回退状态；无法证实的跳跃进入回查队列，不能无限永久拒绝。
- 改号作废与新建、行归属转移同事务。事件携带 shipmentNo、waybillId/版本，旧作废运单迟到轨迹只归档，不改变替代单、订单完成或退款建议。
- 快递以物流事实推进；自提/自送/服务核销没有承运商事件，必须在后续接线设计中列清等价包裹交付事件、降级买家确认及多包裹完成条件。订单级按钮是命令入口，不能绕过数量闭合或伪造所有包裹收货。
- **灰度顺序**：先扩表/枚举和兼容查询 → 部署三端识别及动作处理 → 按商家/客户端能力开放新状态创建 → 影子校验数量/金额/终态 → 切读写 → 最后收旧逻辑。旧客户端不能接住新状态时不创建；已有新状态不可通过回滚入口隐藏或降级成旧 REFUNDING。
- 回滚关闭新增入口并继续处理已有决定/执行记录；UNKNOWN 执行保留回查能力。验收至少覆盖：跨店线下拒建、完整支付影响集授权、混合取消与交付完成、金额补偿不耗件、零现金权益失败、两包裹并发最后收货、备货与售后占位并发、缺揽收签收快照、改单号旧事件、旧客户端能力门槛、批准后响应未知再回查。
