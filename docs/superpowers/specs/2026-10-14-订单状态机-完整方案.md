# 订单状态机 · 完整方案（状态流转 + 状态机封装 + 状态转换类）

状态：草稿（待确认 §14）
创建：2026-10-14
依据：《退货退款逻辑》v2 已确认稿（退款永不自动、协商为主、平台兜底）、《订单服务-详细设计》、订单服务 2.0 内核（`ai.neargo.shop.trade.order`）

---

## 0. 结论

1. **四个聚合、四台状态机**：支付单、订单、发货单、售后单。每台机器由「状态 × 事件 × 执行者 × 守卫 × 副作用」五元组定义，不再只是「A 能到 B」的图。
2. **状态机是纯函数**：输入（当前状态、事件、上下文），输出（新状态 + 要发的领域事件）；不碰库。落库、记流水、发事件统一由**状态转换门**（`StateTransitionGate`）做，持久化一律 **CAS**（`where status = 旧值`）。
3. **「退款永不自动」写进机器**：所有进入「退款执行中」的迁移只允许 `MERCHANT` / `PLATFORM` 触发；`SYSTEM` 只有一条例外（交易不成立的原路退回），由不变式测试锁死。
4. **备货、退款进度、履约阶段不是状态**：备货是事件 + 属性；退款进度由退款账本推导；履约阶段由发货单与运单推导。状态集合因此保持封闭。
5. 售后单拆出 3 个新状态（等寄回 / 已寄回 / 协商中）和 2 个线下退款态（待线下退款 / 已线下退款待确认），消掉现在 `REFUNDING` 一身兼三职的歧义。

## 1. 聚合与它们的关系

```text
支付单 Payment (ord_order) 1 ──< N 订单 Order (ord_sub_order，一店一单)
订单 Order 1 ──< N 发货单 Shipment (ord_shipment)
订单 Order 1 ──< N 售后单 AfterSale (ord_after_sale) 1 ──< N 售后行 (ord_after_sale_item)
订单 Order 1 ──< N 订单行 Item (ord_item：paid_share / refunded_qty / refunded_minor)
```

**不是状态、但要被状态机读到的事实**

| 事实 | 存在哪 | 怎么来 | 谁用 |
|---|---|---|---|
| 已开始备货 | `ord_sub_order.prepared_at / prepared_by` | 订单事件 `PREPARE`（不改状态） | 售后建议、买家提示 |
| 退款进度 NONE / PARTIAL / FULL | `ord_sub_order.refund_progress` + 行上已退额 | 退款账本 `RefundLedger` 在售后单落 REFUNDED 时累加 | 订单是否转 REFUNDED、三端角标 |
| 履约阶段（未备货 / 备货中 / 已出单 / 运输中 / 已到自提点 / 已签收） | 推导，不落库；售后单申请时**快照** | `FulfillStage.of(订单, 发货单, 运单)` | 售后守卫与建议 |
| 售后期截止 | 推导：`completed_at + 7d`（质量类 15d） | 配置 | 售后申请守卫 |

## 2. 支付单（ord_order）

| 状态 | 含义 | 终态 |
|---|---|---|
| `WAIT_PAY` | 待线上支付 | |
| `WAIT_OFFLINE_PAY` | 待商家当面收款 | |
| `PAID` | 已支付 | ✅（之后的变化都在订单） |
| `CANCELLED` | 买家 / 平台取消 | ✅ |
| `CLOSED` | 支付超时关闭（对外投影为 CANCELLED） | ✅ |

| # | 从 | 事件 | 执行者 | 守卫 | 到 | 副作用（领域事件） |
|---|---|---|---|---|---|---|
| P1 | （无） | `PLACE` | BUYER / PLATFORM（代客） | 下单校验（复用现引擎） | WAIT_PAY 或 WAIT_OFFLINE_PAY（按支付方式） | `PaymentPlaced` |
| P2 | WAIT_PAY | `PAY_SUCCEEDED` | CHANNEL（支付回调） | 金额一致、验签 | PAID | `PaymentPaid` → 级联订单 O1 |
| P3 | WAIT_OFFLINE_PAY | `OFFLINE_CONFIRMED` | MERCHANT | 本店单 | PAID | `PaymentPaid` |
| P4 | WAIT_PAY / WAIT_OFFLINE_PAY | `CANCEL` | BUYER / PLATFORM | 本人 / 有代客权限 | CANCELLED | `PaymentCancelled` → 级联 O2、释放库存券积分 |
| P5 | WAIT_PAY | `PAY_TIMEOUT` | SYSTEM | 已过 `pay_deadline_at` | CLOSED | `PaymentClosed` → 级联 O2、释放 |
| P6 | CLOSED / CANCELLED | `LATE_PAY_SUCCEEDED` | CHANNEL | 回调晚到 | （不变） | `TradeVoidRefundRequired`（交易不成立的原路退回，§5 S1） |

> P5 与 P2 并发：两边都 CAS `where status='WAIT_PAY'`，只有一方成功；关单失败方**不释放库存/券**（修《退货退款逻辑》§11 所列 B4）。

## 3. 订单（ord_sub_order）

| 状态 | 对外契约值 | 终态 |
|---|---|---|
| `WAIT_PAY` | WAIT_PAY / WAIT_OFFLINE_PAY（按支付单） | |
| `WAIT_FULFILL` | PAID | |
| `FULFILLING` | FULFILLING | |
| `COMPLETED` | COMPLETED | （可被全额退款带到 REFUNDED） |
| `CANCELLED` | CANCELLED | ✅ |
| `REFUNDED` | REFUNDED | ✅ |

| # | 从 | 事件 | 执行者 | 守卫 | 到 | 副作用 |
|---|---|---|---|---|---|---|
| O1 | WAIT_PAY | `PAY_CONFIRMED`（级联自 P2/P3） | SYSTEM | — | 服务类即出码：FULFILLING；其余：WAIT_FULFILL | `OrderPaid`（通知商家） |
| O2 | WAIT_PAY | `CANCEL`（级联自 P4/P5） | SYSTEM | — | CANCELLED | — |
| O3 | WAIT_FULFILL | `PREPARE` | MERCHANT | 本店；无进行中售后；未备过 | （不变，写 `prepared_at`） | `OrderPrepared`（通知买家） |
| O4 | WAIT_FULFILL | `SHIPPED`（级联自发货单 H2） | SYSTEM | — | FULFILLING | `OrderShipped` |
| O5 | WAIT_FULFILL | `ARRIVED_AT_PICKUP` | MERCHANT / 自提点 | 本点的单 | FULFILLING | `OrderArrived`（通知取货） |
| O6 | WAIT_FULFILL / FULFILLING | `VERIFIED`（核销） | MERCHANT / 自提点 | 码正确；降级单（需买家确认）→ 只到 FULFILLING | COMPLETED（或 FULFILLING） | `OrderCompleted` |
| O7 | WAIT_FULFILL / FULFILLING | `DELIVERED_BY_MERCHANT`（商家标记送达；自送单可能已在配送中） | MERCHANT | 本店 | COMPLETED | `OrderCompleted` |
| O8 | WAIT_FULFILL / FULFILLING | `RECEIPT_CONFIRMED` | BUYER | 本人；所有行已发出 | COMPLETED | `OrderCompleted` → 售后 A16 |
| O9 | FULFILLING | `RECEIPT_AUTO_CONFIRMED` | SYSTEM | 签收满 N 天或发货满 M 天；**无进行中售后** | COMPLETED | 同上（确认收货不是退款，保留自动） |
| O10 | WAIT_FULFILL / FULFILLING / COMPLETED | `FULLY_REFUNDED`（级联自退款账本） | SYSTEM | `refund_progress = FULL` | REFUNDED | `OrderRefunded` → 整单全退时退券 |
| O11 | WAIT_FULFILL / FULFILLING | `INTERVENE` | PLATFORM | 有干预权限；**仅非资金迁移**；备注必填 | FULFILLING / COMPLETED | `OrderIntervened`（审计） |

- **人工干预不再能改到 REFUNDED / PAID / CANCELLED**：动钱的走售后裁决、对账处置。运营端迁移表同步收窄。
- 部分退款不触发任何订单迁移，只改 `refund_progress = PARTIAL`。

## 5. 售后单（ord_after_sale）

### 5.1 状态（相对现状的变化）

| 状态 | 含义 | 现状 |
|---|---|---|
| `APPLIED` | 待商家处理 | 同 |
| `NEGOTIATING` 🆕 | 商家提出协商金额，待买家回应 | 无 |
| `WAIT_RETURN` 🆕 | 商家同意退货，待买家寄回 | 现在混在 REFUNDING（无运单号） |
| `RETURNING` 🆕 | 买家已寄回，待商家确认收货 | 现在混在 REFUNDING（有运单号） |
| `WAIT_RECEIPT` | 商家同意仅退款、货在途；签收后由商家确认退款 | 同名，出口改为商家确认 |
| `REFUNDING` | **退款执行中**（钱在路上：回退分账 → 原路退），只此一义 | 现在兼「等寄回」「已寄回」 |
| `WAIT_OFFLINE_REFUND` 🆕 | 线下付款单：已同意 / 已接受协商 / 平台已裁决退，待商家线下退款并登记 | 无 |
| `OFFLINE_REFUNDED` 🆕 | 商家已线下退款并登记，待买家确认收到 | 无 |
| `REFUNDED` | 已退款 ✅ | 同 |
| `REJECTED` | 商家驳回（买家 7 天内可申请介入） | 同 |
| `ARBITRATING` | 平台介入中（只能由买家 / 商家申请进入） | 同，去掉自动转入 |
| `CLOSED` | 关闭 ✅ | 同 |

### 5.2 迁移表

| # | 从 | 事件 | 执行者 | 守卫 | 到 |
|---|---|---|---|---|---|
| A1 | （无） | `APPLY` | BUYER | 本人；订单已付款未取消；售后期内；无进行中售后；可退额 ≥ 申请额；类型 × 阶段矩阵（生鲜发货后仅质量类） | APPLIED（阶段快照） |
| A2 | （无） | `MERCHANT_INITIATE`（主动退款） | MERCHANT | 本店；原因 ∈ 清单；≤ 剩余可退额；渠道能力 | REFUNDING（或 OFFLINE_REFUNDED，线下单） |
| A3 | （无） | `TRADE_VOID`（交易不成立） | SYSTEM | 原因 ∈ {拼团未成团, 集单撤单, 关单后迟到回调} | REFUNDING |
| A4 | APPLIED | `APPROVE` | MERCHANT | 本店；渠道能力（部分退须渠道支持，否则只能走替代方案） | 仅退款 + 未发出 / 已签收 → REFUNDING；仅退款 + 在途 → WAIT_RECEIPT；退货退款 → WAIT_RETURN；**线下付款单的「退钱」一步一律改为 WAIT_OFFLINE_REFUND**（下同 A2/A6/A9/A12/A16） |
| A5 | APPLIED | `OFFER` | MERCHANT | 协商额 < 申请额且 > 0 | NEGOTIATING |
| A6 | NEGOTIATING | `ACCEPT_OFFER` | BUYER | 本人 | REFUNDING（按协商额；退货类 → WAIT_RETURN） |
| A7 | NEGOTIATING | `DECLINE_OFFER` / `OFFER_EXPIRED` | BUYER / SYSTEM | — / 48h | APPLIED |
| A8 | APPLIED | `REJECT` | MERCHANT | 理由必填（可选模板） | REJECTED |
| A9 | WAIT_RECEIPT | `CONFIRM_REFUND` | MERCHANT | 本店（签收后系统提醒，商家一键） | REFUNDING |
| A10 | WAIT_RETURN | `RETURN_SHIPPED` | BUYER | 退货运单通过清洗与格式 | RETURNING |
| A11 | WAIT_RETURN | `RETURN_EXPIRED` | SYSTEM | 7 天未填运单 | CLOSED |
| A12 | RETURNING | `RETURN_RECEIVED` | MERCHANT | 本店 | REFUNDING |
| A13 | REFUNDING | `REFUND_SUCCEEDED` | CHANNEL / SYSTEM | 通道回执 | REFUNDED |
| A14 | REFUNDING | `REFUND_FAILED` | CHANNEL | — | （不变，标记失败，重试作业接手；不是新决定） |
| A15 | APPLIED / NEGOTIATING / WAIT_RETURN / RETURNING / WAIT_RECEIPT / REJECTED / WAIT_OFFLINE_REFUND / OFFLINE_REFUNDED | `ESCALATE` | BUYER / MERCHANT | 入口条件：被驳回 7 天内；或商家超时；或协商僵持；或对线下退款有异议 | ARBITRATING |
| A16 | ARBITRATING | `ARBITRATE_REFUND` | PLATFORM | 有处理权限；金额 ≤ 可退额（可部分） | REFUNDING（退货类且货未回 → WAIT_RETURN） |
| A17 | ARBITRATING | `ARBITRATE_CLOSE` | PLATFORM | 裁决说明必填 | CLOSED |
| A18 | APPLIED / NEGOTIATING / WAIT_RETURN / REJECTED | `WITHDRAW` | BUYER | 本人；**钱已在路上（REFUNDING）不能撤** | CLOSED |
| A19 | REJECTED | `ESCALATION_WINDOW_EXPIRED` | SYSTEM | 驳回满 7 天未申请介入 | CLOSED |
| A20 | WAIT_OFFLINE_REFUND | `OFFLINE_REFUND_REGISTERED` | MERCHANT | 金额 = 应退额；方式 + 凭证必填 | OFFLINE_REFUNDED |
| A21 | OFFLINE_REFUNDED | `OFFLINE_REFUND_ACKED` | BUYER | 本人 | REFUNDED |

**落 REFUNDED 时（A13 / A21）**：`RefundLedger.apply(售后行)` → 行 `refunded_qty/minor` 累加 → 订单 `refund_progress` 重算 → FULL 则级联订单 O10 → 主单下全部订单终态则退券；积分按比例退回 / 扣回。

## 6. 跨聚合联动

| 触发 | 后续 | 同事务？ | 原因 |
|---|---|---|---|
| P2 / P3 支付成功 | 每张订单 O1 | **同事务** | 钱到了订单必须同时可履约，否则「付了钱看不到单」 |
| P4 / P5 取消关闭 | 每张订单 O2 + 释放库存券积分 | 同事务 | 释放必须与状态原子，否则重复释放或漏释放 |
| P6 迟到回调 | 售后 A3 | 同事务 | 不能让钱无主 |
| 发货单 H2 首张揽收 | 订单 O4 | 异步（轨迹推送）+ 幂等 | 轨迹来自外部 |
| 发货单 H3 签收 | 售后 A9 的提醒 | 异步 | 只是提醒 |
| 发货单 H4 全部收货 | 订单 O8 | 同事务 | — |
| 售后 A13 / A21 退款落定 | 账本 → 订单 O10 → 退券 | 同事务 | 状态与已退额必须一致 |
| 订单 O8 / O9 完成 | 售后期起算；WAIT_RECEIPT 提醒商家确认 | 异步 | — |

同事务的联动由 `StateTransitionGate` 在同一事务里连续 `fire`；异步的走现有 outbox（提交后投递、按聚合分线、幂等）。

## 7. 定时器（只做三件事：提醒、关闭、开门）

| 定时器 | 条件 | 动作 | 动钱？ |
|---|---|---|---|
| 支付超时 | WAIT_PAY 过期 | P5 关闭 | 否（释放） |
| 自动确认收货 | 签收 / 发货满 N 天、无进行中售后 | O9 | 否 |
| 商家处理超时 | APPLIED 超 24h / 48h | 提醒商家 ×2；买家端出现「申请平台介入」 | **否** |
| 协商超时 | NEGOTIATING 48h | A7 回到 APPLIED | 否 |
| 寄回超时 | WAIT_RETURN 7 天 | A11 关闭 | 否 |
| 退货待确认超时 | RETURNING 48h | 提醒商家；买家可申请介入 | **否** |
| 签收后待确认退款 | WAIT_RECEIPT 已签收 | 提醒商家（签收即 + 24h） | **否** |
| 在途 15 天未签收 | WAIT_RECEIPT | 买家可申请介入 | 否 |
| 驳回介入窗口 | REJECTED 7 天 | A19 关闭 | 否 |
| 备货后未发出 | prepared_at + 48h 仍 WAIT_FULFILL | 提醒商家；买家可催发货 / 申请介入；看板计数 | 否 |
| 退款重试 | REFUNDING 失败 | 重新执行**已决定**的退款 | 执行，不决定 |

## 8. 不变式（由测试枚举状态机定义锁死）

| # | 不变式 |
|---|---|
| I1 | 任何进入 `REFUNDING` / `WAIT_OFFLINE_REFUND` / `OFFLINE_REFUNDED` 的迁移，执行者 ∈ {MERCHANT, PLATFORM, BUYER（仅 ACCEPT_OFFER）}；`SYSTEM` 仅 A3（`TRADE_VOID`），且原因受限 |
| I2 | 定时器（SYSTEM）可触发的事件集合 = {P5, O9, A7, A11, A19}，无一进入退款 |
| I3 | 终态无出边（例外：订单 COMPLETED → REFUNDED 由账本驱动） |
| I4 | 每个状态从初始态可达；每个非终态至少有一条出边 |
| I5 | 每条迁移持久化为 CAS；0 行 = `CONFLICT`，不重试、不覆盖 |
| I6 | 每条迁移写一行流水（聚合类型、单号、事件、从、到、执行者、理由） |
| I7 | 对外契约值封闭：订单 7 值、售后 12 值，投影函数对全集测试 |

## 9. 对外契约

- **订单**：仍是 7 个契约值（`OrderStatusProjector`，已接线），外加 `refundProgress`（NONE / PARTIAL / FULL）与 `refundedMinor`。
- **售后单**：12 个状态全部下发（新增 5 个），三端词条与徽章需同步：

| 状态 | C 端 | B 端动作 | 运营端 |
|---|---|---|---|
| NEGOTIATING | 商家提议退 ¥x：接受 / 拒绝 | 等买家回应 | 协商中 |
| WAIT_RETURN | 请寄回并填运单 | 等寄回 | 待寄回 |
| RETURNING | 已寄回，等商家确认 | 确认收货并退款 | 已寄回 |
| WAIT_OFFLINE_REFUND | 商家将线下退款 | 登记线下退款（金额 / 方式 / 凭证） | 待线下退款 |
| OFFLINE_REFUNDED | 商家已线下退款：确认收到 / 有异议 | 等买家确认 | 线下退款待确认 |
| WAIT_RECEIPT（已签收） | 已签收，等商家确认退款 | 确认退款 | 待商家确认 |

- 每张售后单附 `allowedActions`（当前用户在当前状态下能触发的事件，由状态机算）——**端上按它画按钮**，不再各端各写一套条件。这是「三端按钮和后端规则不一致」这类问题的根治。

## 10. 类设计

包：`ai.neargo.shop.trade.order.statemachine`（引擎）+ 各聚合子包。单类 ≤ 200 行、单方法 ≤ 50 行。

```text
statemachine/                       引擎（与业务无关，可单测）
  Actor                    enum     BUYER · MERCHANT · PLATFORM · SYSTEM · CHANNEL
  Transition<S,E,C>        record   from(Set<S>) · event · actors(Set<Actor>) · guards(List<Guard<C>>) · target(TargetResolver<S,C>) · effects(List<EffectFactory<C>>)
  Guard<C>                 iface    Optional<ErrorCode> check(C ctx)
  TargetResolver<S,C>      iface    S resolve(S from, C ctx)          —— 一事件多去向（A4 按类型与阶段分流）
  EffectFactory<C>         iface    DomainEvent create(C ctx)         —— 只产出事件，不做 IO
  StateMachine<S,E,C>      final    fire(S from, E event, Actor actor, C ctx) → Fired<S>；allowed(S, Actor, C) → Set<E>
  StateMachineBuilder      final    from(..).on(..).by(..).when(..).to(..).emit(..) 的 DSL
  Fired<S>                 record   from · to · event · actor · events(List<DomainEvent>)
  Invariants               final    供测试：枚举定义、校验 I1–I4

payment/   PaymentStatus · PaymentEvent · PaymentContext · PaymentMachine(定义 P1–P6)
order/     OrderStatus · OrderEvent · OrderContext · OrderMachine(定义 O1–O11)
shipment/  ShipmentStatus · ShipmentEvent · ShipmentContext · ShipmentMachine(定义 H1–H6)
aftersale/ AfterSaleStatus · AfterSaleEvent · AfterSaleContext · AfterSaleMachine(定义 A1–A21)
           guards/  OwnerGuard · WindowGuard · RefundableGuard · ChannelCapabilityGuard · StageGuard · NoOpenAfterSaleGuard · ReasonGuard
           RefundLedger（行已退额累加、进度重算；复用 RefundCalc）

transition/                          状态转换门（唯一写入口）
  StateTransitionGate      final    apply(Command) → Fired：load → machine.fire → store.cas → log.append → outbox.publish（同事务）
  Command                  record   aggregate · no · event · actor(+operatorNo) · reason · payload
  StatusStore              iface    String load(Aggregate, no)；boolean cas(Aggregate, no, from, to)
  TransitionLog            iface    append(Aggregate, no, Fired, operatorNo, reason)
  CascadeRules             final    同事务联动表（§6 中「同事务」各行）：Fired → List<Command>
  impl/MybatisStatusStore · impl/StatusLogStore
```

**调用时序（以「商家同意退款」为例）**

```text
BizAfterSaleController.approve
  → AfterSaleCommandService.approve(no, merchantNo)
     → gate.apply(Command(AFTER_SALE, no, APPROVE, MERCHANT, …))
         1. store.load → APPLIED
         2. AfterSaleMachine.fire(APPLIED, APPROVE, MERCHANT, ctx)
               守卫：OwnerGuard → ChannelCapabilityGuard → …（第一个失败即抛对应 ErrorCode）
               去向：在途仅退款 → WAIT_RECEIPT
         3. store.cas(no, APPLIED, WAIT_RECEIPT) == false → CONFLICT
         4. log.append(…)
         5. CascadeRules：无同事务联动
         6. outbox.publish(AfterSaleApproved)
```

**为什么这样切**
- 机器定义是**数据**（一张迁移表），评审时对着 §2–§5 的表逐行核；测试枚举它验不变式。
- 守卫与去向各是一个小类，规则变了改一个类，不碰机器。
- 门是唯一写入口：CAS、流水、事件在这里一次做对，业务代码里不再有 `setStatus` + `updateById`。
- `allowed(...)` 让「能做什么」只有一处真源，前端按钮、后端校验、运营端迁移下拉都从它来。

## 12. 测试策略

| 层 | 内容 |
|---|---|
| 机器（纯单测） | 每台机器：迁移表**逐行**正例；全量（状态 × 事件 × 执行者）反例枚举 —— 不在表里的组合一律拒 |
| 不变式 | `Invariants` 跑 I1–I4、I7；尤其 I1/I2（退款永不自动）—— 往表里加一条 SYSTEM → REFUNDING 立即红 |
| 守卫 | 每个守卫独立单测（边界：可退额尾差、售后期最后一秒、渠道次数上限） |
| 门 | CAS 并发：两个线程同时 `PAY_SUCCEEDED` / `PAY_TIMEOUT`，只一个成功、关单方不释放；流水与事件各一条 |
| 联动 | 支付成功 → 订单全部 WAIT_FULFILL；全部行退完 → 订单 REFUNDED → 退券 |
| 场景（shop-app，H2） | 三端端点走一遍完整流：下单 → 付款 → 备货 → 发货 → 售后申请 → 协商 → 接受 → 退款 → 进度 PARTIAL/FULL |
| 消融 | 撤掉 CAS 条件 / 撤掉一个守卫 / 恢复自动同意 —— 对应用例必须红 |

## 13. 实施顺序

| 步 | 内容 | 影响现网 |
|---|---|---|
| 1 | 引擎 `statemachine/` + 四台机器定义 + 不变式测试 | 否（纯新增） |
| 2 | `StateTransitionGate` + CAS 存储 + 流水扩列（迁移） | 否（未接线） |
| 3 | **关掉自动退款**（定时器改提醒 + 开门）；售后状态拆分迁移 | **是**，一期核心 |
| 4 | 支付单 / 订单写路径改走门（关单与付款并发修复） | 是，灰度 |
| 5 | 售后写路径改走门 + 行级退款 + 账本 + 售后期 | 是，灰度 |
| 6 | 发货单写路径（改单号、多包裹）接门 | 是 |
| 7 | `allowedActions` 下发 + 三端按钮改读它；新售后状态三端词条 | 是，需小程序发版 |

步 1–2 可立即开工、零风险；步 3 是一期最先上线的一刀（直接兑现「退款永不自动」）。
