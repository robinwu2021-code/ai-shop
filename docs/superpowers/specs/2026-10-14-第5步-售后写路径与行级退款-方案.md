## 2. 历史数据契约（V404；本轮不改迁移）

```text
ord_item
  + paid_share_minor  BIGINT  NOT NULL DEFAULT 0  本行分摊后的实付（含优惠、积分抵扣分摊；不含运费）—— 下单时落快照
  + refunded_qty      INT     NOT NULL DEFAULT 0  已退件数
  + refunded_minor    BIGINT  NOT NULL DEFAULT 0  已退金额
ord_sub_order
  + completed_at      BIGINT  NULL                完成时刻（售后期起算点）
  + refunded_minor    BIGINT  NOT NULL DEFAULT 0  已退总额（含运费）
  + refund_progress   VARCHAR(8) NOT NULL DEFAULT 'NONE'   NONE / PARTIAL / FULL
ord_after_sale_item（新表）
  after_sale_no · sub_order_no · item_id · qty · refund_minor · 通用审计列
  唯一键 (after_sale_no, item_id)
```

**历史处理口径**（原拟 SQL 行快照回填已由 TDD AC20 取代）：
- `paid_share_minor`：新单下单落最大余数法快照；存量不在迁移里 SQL 回填，读取时用与新单相同的 `LineShares.of` 算法现算，快照齐全才直接读。原“尾差进最大行”的两段 SQL 计划已废止，不能作为后续迁移指令。
- `completed_at`：取状态流水里该子单最后一条 COMPLETED 的 `at`。
- 已 REFUNDED 的子单：历史迁移按当时存量整单退款标记 `refund_progress = FULL`，`refunded_minor` 按售后实退额求和；保留历史迁移事实。本轮区分数量/现金用途后，不能据旧 REFUNDED 状态推断真实退回件数或积分补偿是现金实退，歧义存量须核对。
- 其余：默认值。

> 历史只读排查结果已写入 TDD（2026-10-14 全库 3 行、唯一成功单为整单全退）；这是当时记录，不能当作本轮或上线时数据库仍相同的保证。

## 3. 用途、金额与订单闭合（本轮推荐，待评审）

详细术语见 [退货退款逻辑 §13](2026-10-14-退货退款逻辑.md) 与 [对象模型](2026-10-14-第5步-对象模型.md)。

| 项 | 推荐定义 |
|---|---|
| RefundPurpose | CANCEL_ITEMS / RETURN_ITEMS / REFUND_WITHOUT_RETURN / MONEY_ADJUSTMENT；批准后不可变，用户流程 type 与用途分离 |
| 行 | coveredQty 为范围；closedQty 为终止交易量；returnedQty 为实退；cancelledQty 为未履约取消；cashMinor 为现金，不用单一 qty 同时表达这些事实 |
| 价差/补偿 | MONEY_ADJUSTMENT 不耗 closedQty/returnedQty/cancelledQty，不回补库存；按行现金上限校验 |
| 少退协议 | 终止交易时减少应退额须买家接受或平台裁决，并保存 agreedRetainedMinor、提议版本及证据；普通同意不能单方面压低申请额；价差调整不适用损耗协议 |
| 行现金分摊 | 按件终止：剩余可退现金 × 本次closedQty / 剩余可终止件数，下取整；最后一次取剩余全额。现金余量扣实退/已生效留存/其他执行预占；不可变paid_share_minor仅作原始上限，批准plan冻结后不重算 |
| 运费 | 未发货取消全部余项才退；已发货仅商家责任原因退、只退一次；合法留存运费单列 |
| 老客户端 | 无金额无行且明确取消/退回用途 → 整单剩余范围；只给金额 → MONEY_ADJUSTMENT，不推导为全退件数；兼容映射须在提交时再次确认用途 |
| 现金进度 | cashProgress 仅现金退款比例，NONE / PARTIAL / FULL；0 元为 NONE，无现金回调 |
| 商品/订单结束 | goodsClosed = 全商品交易终止；应退现金/权益结清且无未知/进行中执行 → 订单 REFUNDED。正常交付+终止混合闭合 → COMPLETED；仍有待履约商品则保留履约状态 |
| 券 | 主单全部商品交易终止触发返券意图，实际结果计入权益结清，再推进终态；不能等REFUNDED再发返券造成循环；混合交付结束、部分现金退款不自动退 |
| 积分边界 | 历史比例目标保留，积分域重整整套仍待确认；本轮只要求权益意图、真实结果与恢复。零现金用 BENEFITS_SETTLED；积分补偿不能把欠现金的整单标 REFUNDED |
| 库存 | 未付款取消释放占用；已付款未发商品取消按精确数量回补已扣库存；退货按真实实收/验货可回售结果入库；不退货退款和金额调整不回补，不由现金受理判断 |

本轮拟定按件终止交易的 LineAmountPolicy：remainingRefundableCashMinor = paidShareMinor − 已成功现金实退 − 已接受/裁决生效的合法留存 − 其他执行现金预占；remainingClosableQty = orderedQty − 已终止closedQty − 其他执行终止件数预占。当前执行批准前算本次 closedQty 的现金：floor(remainingRefundableCashMinor × 本次closedQty / remainingClosableQty)，本次终止全部剩余件数时取剩余现金全额。当前槽位串行；批准时余额/数量与预占同事务冻结，已生成不可变plan后发送、回执、重试不得重算金额或把本执行预占再扣一遍。

反例：3件原现金3000，先MONEY_ADJUSTMENT退1000，剩余可终止件数仍3、剩余现金2000；随后依次终止1件，现金为666 / 667 / 667，总现金含调整恰为3000。CANCEL_ITEMS / RETURN_ITEMS / REFUND_WITHOUT_RETURN消费closedQty，MONEY_ADJUSTMENT只降现金不耗件；不能继续按原paidShare × 本次qty / orderedQty算1000一件。原始快照仍用于总额上限与可追溯；初版原份额按件公式作为历史记录保留，已被本轮剩余额/剩余件数推荐公式替代，尚未实现。

goodsClosed、cashProgress 与结算 FinancialClosure 独立。全退商品但保留合法运费/损耗，订单可结束而现金进度仍 PARTIAL；合法商家应付仍须结算，不能随订单 REFUNDED 自动把结算单标 REVERSED。

## 4. 结算退款与供应商追偿（本轮推荐，待评审）

历史已确认口径 A 按商品现金退款份额分配商家所得/佣金/服务费/补贴。本轮补齐不可变快照和资金事实，避免用扣减后的应付作为累计比例基数。

SettlementRefundBasis（拟新增独立表 stl_bill_refund_basis 保存快照；未建表）保存原始商品现金实付、原始商家所得/各费用/补贴、运费归属、资金路径及原账户。每项本次 cut = floor(original × refundedGoodsAfter / goodsPaidOriginal) − floor(original × refundedGoodsBefore / goodsPaidOriginal)。0 现金分母不能套公式，需显式非现金路径/人工核对，不假算全退。

| 资金事实 | 推荐处理 |
|---|---|
| 未支付供应商/尚未分账 | 按不可变 Basis 算份额，扣 remainingPayable；余款及合法运费/约定损耗继续可结算 |
| 直连通道已分账 | 同基数分配份额，按实际已付金额发回退；ACCEPTED/UNKNOWN 不计已追回，只在可信成功后更新 reversed |
| 归集供应商已付款 | 建 RecoveryClaim（原付款/售后/责任方/债权/追回或抵扣证据）；不能只减少已付款账单伪装追回 |
| 先退一部分 → 分账 → 再退 | 同一原始 Basis + 各阶段资金流水守恒，不能把历史预扣额重复回退或用当前 net 累计切分 |
| 保留运费/约定损耗 | legalRetained 单列责任和收益分配，允许合法剩余应付继续结算，不因商品交易全终止把它一并回退 |

FinancialClosure 依据剩余应付、实际已付未回退、待追回、合法留存及未完成指令判断结算财务结束；goodsClosed 或累计货款比例到某个值都不能单独触发整结算 REVERSED。结算结束状态的精确投影、留存收益分配和新快照恢复规则待评审。

买家退款不等归集供应商追偿；平台垫付来源、额度、审批和失败后处理仍待评审，不以这条推荐原则视为已获资金授权。后续实现应检查订单结算来源目前仅识别 COMPLETED 的约束：新 REFUNDED 订单仍有合法留存应付时必须显式保留可结算来源，不能丢账。此为未实现建议，不表示当前来源合同已更改。

通道能力需上线前按官方接口核验：微信收付通/支付宝分账回退的金额、次数、期限与异步结果；微信直连无二级分账。线下登记与平台原路退是不同路径，不能以平台不支持部分退否定合法线下部分退款。退款/回退 UNKNOWN 时禁止启用替代路径；确定永久失败转人工、有关闭证明和买家同意才换路。

## 5. 退款执行、预占与实退（本轮推荐，待评审）

```text
批准（商家合法批准 / 买家接受协商 / 平台裁决）
  → 本地CAS事务：不可变RefundPlan + RefundExecution(PREPARED)
     + RefundReservation(现金/终止数量预占) + outbox
  → dispatcher分阶段恢复：结算份额/回退 → requestRefund
     ACCEPTED → PROCESSING；UNKNOWN → 回查
     FAILED → 同号重试（可重试）或人工（确定永久失败）
     SUCCEEDED → 验真/认领/统一结果归并（回执、回查、同步可信成功）
  → success本地事务：预占转实退 + 真实现金/商品闭合事实 + 权益意图 + outbox
  → 权益真实结果/恢复完成 → 售后落REFUNDED → OrderClosurePolicy
现金0：批准/预占 → 权益意图/真实结果 → BENEFITS_SETTLED → 同一闭合入口
库存：取消未履约或实收/验货事实 → 单独幂等，不凭资金受理回补
```

RefundExecution（拟新增 ord_refund_execution，未建表；两表迁移号实施当天分配）保存不可变方案哈希、执行/售后号、请求号、阶段、结果证据、可选发送租约。PREPARED / PROCESSING / UNKNOWN / FAILED / SUCCEEDED 是执行状态，DISPATCHING 可只作内部租约阶段。已有历史接口返回的流水号不是现金成功证明；新 SettlePort.requestRefund(RefundRequest) 返回 RefundDispatchResult{ACCEPTED,SUCCEEDED,FAILED,UNKNOWN}。

预占与实退分开：申请时资金不预占，批准时原子预占；外部成功后同本地事务转实退并更新状态/事件。外部效果不会因本地事务回滚消失，必须保留决策、外部请求、结果和续跑阶段；退款已成功而权益失败只补做权益，不重退现金。只有确定未发送或确定不能再成功时才可取消预占，UNKNOWN不能释放后换号重退/线下赔付。

**历史实现边界：**TDD AC31 的“记账→回退→原路退”描述的是当时现金链路顺序，不能理解成成功前的本地增量就已经证明钱退到买家。本轮拟把此前字段中的条件增量拆成显式预占与成功实退；此拆分尚未实现。历史方案“状态/账本同事务”只适用于本地落定，不等于跨资金通道、积分域或库存域可原子回滚。

可信成功一旦被认领，不接受迟到失败倒退；回执/回查按执行/请求号、方向、金额、原账户校验归并。业务售后成功与资金执行成功分开，真实权益尚待恢复时不得把整单宣告结清。缺原收款/结算快照、无通道、确定失败必须保留失败证据和应退义务，不能“留日志后算成功”。

---

返券评价通过子单事实提交后的可靠事件/outbox触发，由独立支付级事务锁定Payment后汇总主单商品终止与应返券事实、幂等生成/执行返券意图。子单退款事务只更新自身事实并提交事件，不能已经持有Order锁再同步获取Payment锁；支付级评价失败可恢复、真实券结果参与权益结清。该锁顺序和异步边界为本轮待评审建议，不改变历史验收记录。

## 6. 写入门与并发（本轮推荐，待评审）

历史售后 CAS 接门及槽位唯一规则见 TDD AC34–37。本轮不是“只替换写法、行为不变”：用途、闭合判据和资金执行需要新的业务守卫/事件与数据字段，须与状态机修订一起实施。

- 申请槽位库内 CAS 保证同子单仅一张活动申请；批准事务另外校验行现金、已终止/预占件数和提议版本。
- 申请资格保留阶段快照；批准/取消库存/发货并发按当前真实履约事实重新校验，不能把未发货申请误当成永远未发货。
- 发货、取消、退回与商品闭合以同份商品的事实版本/CAS避免重复交付或重复终止。CAS冲突重读重算，不能覆盖方案。
- 发送阶段租约只允许同执行号同方案重放；结果归并/账本/库存/权益分别按执行或真实事实幂等。
- 关闭/驳回释放申请槽位不等于释放资金执行预占；UNKNOWN/PROCESSING尚有外部效果时禁止关闭执行后开第二赔付路径。
