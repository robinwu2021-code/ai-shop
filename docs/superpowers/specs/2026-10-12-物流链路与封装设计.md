# 物流链路与封装设计

> 2026-10-12。承 [核心逻辑与方法实现](../archive/specs/2026-10-12-订单服务-核心逻辑与方法实现.md) §5。
> 落地用户补充的四点：①发货信息上传微信(各平台可扩展) ②运单主动查询(默认微信·可切换) ③订阅推送及时更新 ④物流/支付/订单状态/退款的良好封装。

---

## 1. 物流更新三路（推 / 拉 / 上报）

```textflowchart TB
    SHIP[商家发货: 建发货单 Shipment + 运单号] --> UP[上报: 微信发货信息]
    SHIP --> SUB[订阅: 登记运单→订阅承运商推送]
    SHIP --> Q0[拉: 发货后首次查询]
    SUB -. 承运商/微信推送 .-> CB[/callback/logistics/{channel}/]
    CB --> UPD[WaybillProgress.apply 更新轨迹+状态]
    Q0 --> UPD
    POLL[定时轮询在途单] --> UPD
    READ[买家下拉 refresh·节流] --> UPD
    UPD --> EVT[发 WAYBILL_PROGRESSED / WAYBILL_SIGNED]
    EVT --> ORD[订单层: 签收→可确认收货/自动确认]
```

| 路 | 方向 | 角色 | 触发 | 说明 |
|---|---|---|---|---|
| **上报** | 推给微信 | 合规 | 发货时(实物)/支付或核销时(服务·自提) | 微信小程序交易合规要求，见 §2 |
| **订阅** | 承运商推给我 | **主路** | 发货后登记运单即订阅 | 及时、省配额，见 §4 |
| **查询** | 我拉承运商 | **兜底** | 发货后首查 + 定时轮询 + 读路径 refresh | 订阅不可用/未及时的补偿，见 §3 |

> 更新逻辑三路共用一处 `WaybillProgress.apply`（状态只进不退、签收只写一次、事件只发一次）——这是封装关键，任一路进来结果一致。

## 2. 发货信息上传（微信 / 各平台可扩展）· 用户补充①

**为什么必须**：微信小程序交易合规——订单支付后须在时限内上传"发货信息"，否则影响结算与体验分。

**时机**（按履约方式）：
| 履约 | 上传时机 | 微信 logistics_type |
|---|---|---|
| EXPRESS | **发货时**（带运单号） | 1 快递 |
| MERCHANT_DELIVERY | 标记送达时 | 2 同城 |
| STORE_PICKUP/NEIGHBOR_PICKUP | 到货登记时 | 4 自提 |
| STORE_VERIFY/APPOINTMENT | **支付成功时**（付款即出码） | 3 虚拟 |

**流程**：发货/支付 → 写 `trd_shipping_upload` 台账(PENDING) → 异步 Job 发微信 → 成功记 `wx_uploaded_at`（作为换 token 的前置）。
**封装（各平台可扩展）**：
```
interface ShippingInfoUploader {            // 平台无关
    boolean supports(String platform);      // WX / (将来)DOUYIN/ALIPAY
    UploadResult upload(ShippingInfoCmd);
}
WxShippingInfoUploader implements ShippingInfoUploader   // 现 WxShippingUploadService 收敛于此
```
按**订单来源平台**路由到对应 Uploader；现仅微信，接口预留"各平台"。交易域只调 `ShippingInfoPort.enqueue(...)`，不认平台细节。

## 3. 运单查询（主动拉·默认微信·可切换）· 用户补充②

**渠道链**：探测渠道按 `shop.logistics.routes.probe` 解析（store → carrier → default），**默认 `["wx"]`**（微信物流查询接口）；可按系统设置切快递100 等。
**触发三处**：
1. **发货后首查**：建发货单后主动查一次（可能承运商尚无记录 → 9300559，等推送）。
2. **定时轮询**：在途发货单周期查（兜底订阅遗漏）。
3. **读路径 refresh**：买家下拉时校正，`read-cache-minutes` 节流（反复下拉不打穿配额/不花钱）。

**封装**：
```
interface TrackingProber {                  // 查询策略
    String channel();                        // wx / kuaidi100
    boolean available();                     // 凭据齐备
    ProbeResult probe(waybill, now);
}
WxTraceProber / Kuaidi100Prober implements TrackingProber
ChannelRouter.probes(storeNo, carrier) → List<TrackingProber>   // 按配置选链，默认 wx
```
**系统设置切换**（增强）：把 `routes.probe/subscribe` 从配置文件提升为**运营可配的系统设置**（存库 + 运营端界面），默认微信；切换即时生效，无需改配置重启。——这是用户"根据系统设置切换"的落点。

## 4. 订阅推送（被动收·主路）· 用户补充③

**订阅**：发货登记运单后，按 `routes.subscribe` 链订阅承运商推送（`subscribe-enabled` 总开关）；失败重试/换家/FATAL。
**推送**：`POST /callback/logistics/{channel}` → 验签 → 解析 → `WaybillProgress.apply` → 发 `WAYBILL_PROGRESSED/WAYBILL_SIGNED` → 订单层响应（签收→可确认/自动确认收货）。
**封装**：
```
interface TrackingSubscriber { String channel(); boolean available(); SubscribeResult subscribe(waybill, callbackUrl); }
interface PushReceiver        { String channel(); boolean verify(raw); TraceResult parse(raw); }
Kuaidi100Subscriber / Kuaidi100PushReceiver   // 现有
```
**推拉关系**：订阅是主路（及时、省配额），查询是兜底；两者都汇到 `WaybillProgress.apply`，天然幂等（节点按"时刻+原文"去重、状态只进不退）。

## 5. 四大封装边界 · 用户补充④

```textflowchart TB

        OS[OrderService / Facade]
        OSM[OrderStateMachine 规则]
        OT[OrderTransitions 唯一写入门]
        OSP[OrderStatusProjector 投影+聚合]
        RO[RefundOrchestrator 退款编排]
    end
    subgraph 端口层 Port 交易域只依赖这些
        LP[LogisticsPort 读物流]
        SIP[ShippingInfoPort 上报]

        STP[StockPort] 
        STL[SettlePort]

        CPP[CouponPort]
    end
    subgraph 物流域 换渠道不影响交易域
        CR[ChannelRouter]

        PCH[PayChannel* 微信/FREE/stub]
    end

    RO --> STL & PP & PTP & CPP & STP
    LP --> CR --> SUBI & PRB & PR & BND & DSP
    SIP --> UPL
    PP --> PCH
```

### 5.1 物流封装（重点）
- **交易域只依赖 `LogisticsPort`（读）与 `ShippingInfoPort`（上报）两个端口**，看不到渠道。
- 物流域内部全部是**策略接口 + 路由**：`TrackingSubscriber`/`TrackingProber`/`PushReceiver`/`WaybillTokenBinder`/`TraceDisplayStrategy`/`ShippingInfoUploader`，`ChannelRouter` 按 store/carrier/系统设置选具体实现。
- **换渠道（微信↔快递100↔将来顺丰直连）= 加一个策略实现 + 改路由配置**，交易域零改动。这就是"良好封装"的验收标准。
- 收敛现状：删旧 `FulShipment` 访问层/旧绑定作业/`legacyTraceOf`（两套并存→一套）；`display_channel` 退役（读路径只认 token）。

### 5.2 支付封装
- 交易域只依赖 `PayPort{ init(payNo,channel)→params; refund(payNo,amount)→paymentNo }`。
- 渠道为 `PayChannel` 策略（微信支付/FREE/stub/将来支付宝）；回调统一 `markPaid`。
- 退款金额经 `PayPort.refund` 原路退到支付单流水。

### 5.3 订单状态封装
- **规则**`OrderStateMachine`（纯函数，唯一真源）· **写入**`OrderTransitions`（唯一门，ArchUnit 禁其他处 setStatus）· **投影/聚合**`OrderStatusProjector`（契约投影 + 发货单聚合，唯一处）。
- 三层状态（支付单/订单/发货单）的联动规则集中在 `OrderStatusProjector` + `OrderTransitions`，别处不散判。

### 5.4 退款封装
- `RefundOrchestrator` 编排**全流程**，别处不拼：
  1. 幂等（AfterSale `REFUNDED` 终态）
  2. CASH：`SettlePort.reverseSplit`（失败即停，不继续退钱）→ `PayPort.refund`（原路）
  3. POINTS：`PointsPort.compensate`（判空），不回冲分账
  4. 整单退完：`CouponPort.release` + 积分回退/追回
  5. 退货：`StockPort.restore` 回补
  6. 状态：行退完 → 订单 `REFUNDED`
- 依赖的四个 Port 各司其职；编排只在这一个类。

## 6. 发货流程串起三路（时序）

```textsequenceDiagram
    participant M as 商家
    participant OS as OrderService
    participant SIP as ShippingInfoPort(上报)
    participant LOG as 物流域
    participant WX as 微信/承运商
    M->>OS: ship(orderNo, {items, carrier, waybillNo})
    OS->>OS: 清洗/格式/重号校验; 建 Shipment; 行归属; Order→FULFILLING
    OS->>SIP: enqueue 发货信息(实物带运单)
    SIP-->>WX: 上传发货信息(异步Job) → wx_uploaded_at
    OS->>LOG: SHIPMENT_CREATED
    LOG->>WX: 登记运单→订阅(默认wx可切) + 首次查询
    WX-->>LOG: 推送/查询结果 → WaybillProgress.apply
    LOG->>OS: WAYBILL_SIGNED(签收)
    OS->>OS: 发货单→RECEIVED; 全部交付→Order COMPLETED
    Note over WX,LOG: 有运单后微信可换 display_token → C端插件展示
```
