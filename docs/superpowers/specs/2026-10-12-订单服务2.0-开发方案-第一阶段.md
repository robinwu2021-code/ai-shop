## 2. 逐类开发任务

### 2.1 `OrderStatusProjector`（纯函数，可立即做，不依赖未定假设）
**职责**：库状态 → 契约状态投影 + 跨子单聚合。收敛现有散在 `OrderStatusView.toContract` / `payView.headStatus` / `orderView` 的逻辑到一处，并修正 `CLOSED→CANCELLED`、聚合口径。
```java
String contract(String subStatus, String mainStatus)         // 单包裹投影, 结果 ∈ 契约7值
String aggregate(String mainStatus, List<String> subStatuses) // 跨子单聚合(Q12 最落后活跃)
```
- 依赖：仅 `OrderStateMachine`（判 rank）。无 IO。
- **测试**：封闭性——枚举 `OrdOrder`×`OrdSubOrder` 全部常量，断言结果 ∈ 7 值；`CLOSED→CANCELLED`；跨商家聚合取最落后活跃；全终态有 REFUNDED→REFUNDED 否则 CANCELLED。
- **不影响现有**：`OrderStatusView` 原样保留继续用；本类独立存在+测，不被现有调用。

### 2.2 `OrderTransitions`（写入门，建好备用）
**职责**：封装状态写入 = 状态机断言 + `setStatus` + 写 `ord_status_log` + 发事件。
```java
void applyOrder(OrdOrder o, String to, Operator op, String reason)
void applySub(OrdSubOrder s, String to, Operator op, String reason)
void applyMerchantSub(OrdSubOrder s, String to, Operator op, String reason)  // +商家闸
```
- 依赖：现有 `OrderMapper`/`SubOrderMapper`/`StatusLogMapper`/`OutboxEventBus`（构造注入，复用）。
- **测试**：合法迁移写入+留痕+事件；非法迁移抛 `ORDER_STATE_ILLEGAL`；商家闸拒 `WAIT_PAY→FULFILLING`；幂等 `from==to`。
- **不影响现有**：现有 5 处裸 `setStatus` **本阶段不动**（替换它们是 B3，会改现有行为）。本类建好、测好、等接线。

### 2.3 `UnifiedOrderVO` + `OrderListItemVO` + `OrderPackageVO`（新 DTO）
**职责**：消除现有 payView/orderView 两视角二义，统一成一个只读视图。
- `UnifiedOrderVO{orderNo, status(聚合), amount, items[], packages[], receiver, payTime, actions}`
- `OrderPackageVO{packageId, merchantName, status, fulfillment, items[], expressNo, trace, verifyCode, afterSale}`
- `OrderListItemVO{orderNo, status, amount, packageCount, cover, title, itemCount, primaryAction}`
- **不影响现有**：现有 `OrderVO` 原样保留；新 DTO 并存。

### 2.4 `OrderAssembler`（只读装配）
**职责**：读现有 `ord_order`/`ord_sub_order`/`ord_item` → 组装 `UnifiedOrderVO`/`OrderListItemVO`；状态经 `OrderStatusProjector`。
- 依赖：现有 mapper（**只读**）+ `OrderStatusProjector`。
- **测试**：主单+多子单 → 一个 UnifiedOrderVO，packages 对应子单，聚合状态正确；单商家单 packages=1。
- **不影响现有**：纯读，不写任何表。

### 2.5 `OrderQueryService`（只读查询，本阶段实现）
```java
UnifiedOrderVO detail(String orderNo, String userNo)
PageData<OrderListItemVO> list(String userNo, OrderQuery q, long page, long size)
```
- 依赖：`OrderAssembler` + 现有 mapper（只读）。
- **测试**：子单号/主单号都能查到统一视图；列表一行一订单；属主过滤（防 IDOR）。
- **不接 Controller**：本阶段不开放买家端点；可选加 `GET /mp/order/v2/{no}`**影子端点**（默认关闭/仅内网，用于和老接口对比输出），不对买家开放。

### 2.6 `OrderCommandService`（写接口，只定签名）
```java
interface OrderCommandService {
    UnifiedOrderVO create(CreateOrderCommand cmd, String idemKey);  // 后续实现
    void markPaid(String payNo, String channel, String tradeNo);
    ShipResult ship(String orderNo, ShipCommand cmd);
    void confirmReceipt(String orderNo, String packageId, String userNo);
    void cancel(String orderNo, String reason, String userNo);
}
```
- **本阶段只定接口 + DTO 签名，不实现**（或抛 `UnsupportedOperationException`，不接线）。写路径实现在后续阶段（依赖模型假设定稿 + 灰度）。

## 7. 与未定假设的关系

本阶段**刻意只做不依赖①~⑥的部分**：
- `OrderStatusProjector` 的 `contract`（CLOSED→CANCELLED）、`aggregate`（按现有子单聚合）—— 不依赖"订单=商家 vs 门店"，按现状子单实现即可。
- `OrderTransitions`、只读 Facade、统一 DTO —— 基于**现状**主/子单结构，不依赖模型重构。
- `ord_shipment`、按商家拆单、行级退款 —— **依赖假设，放后续阶段**。

所以本阶段可**立即开工**，不必等①~⑥拍板。待假设定稿，再做写路径与发货单层。
