# 两套套餐异常款退款与占用解除（续接）

用户要求继续补齐上轮明确剩余的退款/解除能力，修复相关回归；先本地、真实账户后补、保留已有改动。用户随后新增两场景（App购买运营审核、运营代购）修复验收后直接部署166。

## 决定
复用现有stl_payment和线下退款底座。两套业务通过同一退款协调能力处理异常实收，分别保留原有订单授权与占用释放规则；不另建资金账本，不改为线上转账。另建一条独立资金系统或仅记人工“已退款”备注都会失去原款可核验性，因此不用。

- 退款对象必须来自资金底座真实收款。金额/币种/原支付号/支付尝试从该笔实收冻结，默认退还该笔剩余可退金额；不是按套餐应付金额退款。
- 普通已交付匹配款继续走现有权益退款；异常流程只接受不匹配、关闭后迟到款，或主体单已收款但未开通的REVIEW_REQUIRED。不能通过异常流程退掉已交付权益对应的正常收款。
- 运营创建退款申请后，实际线下退回原付款方；再录入收款方核对标识、退款时间、流水及独立私有退款凭证。此流程不执行银行转账。银行真实退款核验与申请分离。
- 原始退款请求和每次核验动作持久化；未知结果恢复同一命令，明确拒绝终结原动作后允许纠正；重试不重记资金，不换账户/金额复用原动作键。
- 只有可信完整退款事实可显示REFUNDED。释放前资金底座再次核查全部异常实收均已退清且无待处理退款；银行对账关闭栅栏与新收款串行。部分退、待核验、错误凭证和不相关退款都不释放。
- 主体包释放不能改订阅/override或覆盖后续新单占用。商城通过原有对账关闭及履约恢复释放待购/库存占用，不撤销其他订单已购权益。已完成正常订单的额外重复款可单独退款，不作废原有效订单。
- App展示真实退款进度；运营可发起、上传/核验退款、恢复、对账释放。退款账户信息/平台凭证不得回给买家。

本轮把上轮商业发布阻塞项实现，不再以“人工改库”或未实现外部操作代替闭环。以MySQL9真实账本+HTTP权限+App/OPS契约回归验收；现有全量失败先归因，修复本次相关项。
