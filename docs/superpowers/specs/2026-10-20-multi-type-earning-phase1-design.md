# 多积分赠送规则第一阶段

依据：用户确认分三个阶段，并要求先实现第一阶段。复用既有规则功能，不改变订单接入方式、不修改 B/C、不进行实际财务操作。

- 规则以积分类型＋范围唯一。同类型最近品类优先于父级及默认，明确零终止继承，不跨类型叠加。
- 运营列表可按类型筛选；新增抽屉选择 ACTIVE 积分、品类范围、比例及备注；每个类型自动建立零默认规则，默认规则从列表详情调整。编辑已有规则不可改变类型和范围，历史修订不变。
- 默认订单类型继续迁入原规则；其他 ACTIVE 类型初始化为生效零比例默认规则，不能继承订单类型的比例。
- 查询可读取历史类型，只有 ACTIVE 可写入或用于新试算。默认规则不可停用，可发布零比例。
- 统一内部 PointsEarningRulePort 提供可用积分、已发布规则、匹配与试算，返回积分名称/代码、币种、精度、兑换比例、规则版本及结果。不提供记账，不自动循环全部类型发放。
- 试算显式指定积分、币种、商品现金实付最小货币单位及品类；拒绝币种不匹配、未知品类、负数、溢出及非 ACTIVE 类型。旧运营预览请求兼容省略类型和币种，以订单默认填充；统一内部接口要求显式指定。
- 已有订单协调器、支付记账和退款链路不更改；规则服务可被后续模块注入调用。新增类型的规则发布不使订单自动改用该类型。
- 仅定向后端测试、前端交互测试、类型检查及运营端构建；不全量或并发测试，不发布 B/C。

## 已实现接口及接入边界

内部统一接口：`shop-base` 的 `PointsEarningRulePort`，由 `shop-app` 应用层适配交易规则存储和支付积分类型查询。

- `availableTypes()`：仅返回 ACTIVE 类型及名称、市场、币种、精度和兑换比例。
- `published(typeCode)`：返回该类型当前生效规则范围、修订、模式与值；历史类型可读，不返回未发布草稿。
- `calculate(Query(typeCode,currency,categoryNo,cashMinor))`：类型与币种必填，品类空值表示默认；返回类型快照、输入金额、命中范围、修订、比例及积分数。此调用不记账、不检查或扣减预算，不能作为已发放凭证。
- 金额以最小货币单位传入；例如 CNY 100 元为 10000。先按赠送比例折算赠送货币金额，再按照该积分兑换比例和既有精度规则向下取整；不使用浮点数。
- 后续业务必须明确选定 typeCode，不得遍历所有类型自动发放；需在自己的业务事实中保存此计算结果及规则修订。跨进程接入和发放/结算命令留到后续阶段。

运营 HTTP（仍受 finance read/execute 权限及平台数据域限制）：

| 接口 | 参数与行为 |
| --- | --- |
| GET `/ops/points/earning-context` | 原 `type`（可为空）和 `categories` 保留；新增 `types` 用于筛选和 ACTIVE 选择 |
| GET `/ops/points/earning-rules` | `typeCode` 筛选；`all=true` 跨类型分页；两者均省略兼容原订单默认查询；page/size 原校验保留 |
| GET `/ops/points/earning-rule-history` | `scope` 必填，`typeCode` 可选；省略兼容原默认类型 |
| POST `/ops/points/earning-rules` | 原 Change 结构，按请求的 ACTIVE typeCode 校验；不再限制为订单默认类型 |
| POST `/ops/points/earning-preview` | `{typeCode,currency,categoryNo,cashMinor}`；旧请求省略类型或币种时兼容填充；返回额外 type 快照 |

前端：列表默认展示全部类型；新增品类规则选择 ACTIVE 类型。每个类型的默认规则自动初始化，点击默认行打开详情后调整，避免创建时猜测默认修订。编辑不可改变类型和范围，切换列表类型使用独立查询缓存；切换试算类型重新挂载表单，输入变更后旧请求结果不再展示。
