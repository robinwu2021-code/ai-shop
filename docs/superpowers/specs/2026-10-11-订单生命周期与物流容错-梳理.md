## 0. 一句话模型

**钱在主单，货在子单**（`OrdOrder.java:9-13`）。
支付、退款、取消走主单；发货、核销、售后、分账走子单。

- **拆单维度 = 门店**，不是商家（ADR-031，`OrderServiceImpl.java:2805-2810`）：
  **一组 = 一张子单 = 一家门店**；同一主体两家店的货在一单里是两张子单。
- **主单 `PAID` 是终态**（`OrderStateMachine.java:37`）：已支付后主单不再迁移，一切变化在子单。
  这一条是后面一大批展示 bug 的共同源头。

## 1. 工作流全图

### 1.1 状态集合

**主单**（5 个，`OrdOrder.java:19-34`）

```
WAIT_PAY ──────┬──→ PAID（终态）
               ├──→ CANCELLED
               └──→ CLOSED（超时未付自动关）
WAIT_OFFLINE_PAY ─┬─→ PAID
                  └─→ CANCELLED
```
主单**没有** `REFUNDED`。线下单没有 `→WAIT_PAY` 和 `→CLOSED` 边（理由见 `OrderStateMachine.java:27-34`）。

**子单**（6 个，`OrdSubOrder.java:23-28`）

```
WAIT_PAY ──┬──→ WAIT_FULFILL ──┬──→ FULFILLING ──┬──→ COMPLETED ──→ REFUNDED
           │                   ├──→ COMPLETED    └──→ REFUNDED
           │                   └──→ REFUNDED
           ├──→ FULFILLING（服务类：付款即出码，直落）
           └──→ CANCELLED
```

**对外契约状态**（7 个，`OrderStatusView.java:27-57`）：
`WAIT_PAY | WAIT_OFFLINE_PAY | PAID | FULFILLING | COMPLETED | CANCELLED | REFUNDED`
映射只做名字对齐：`WAIT_FULFILL → PAID`；主单是 `WAIT_OFFLINE_PAY` 且子单口径为待付时 → `WAIT_OFFLINE_PAY`。
**`SHIPPED`/`ARRIVED` 已于 2026-08-17 删除** —— 它们是「`FULFILLING` × 履约方式」冒充状态，代价是每加一种履约就要加一批状态。现模型：**状态集合封闭、履约集合开放**，展示由端上 `orderView(status, fulfillment)` 决定。

### 1.2 节点流

```
N1 下单 ──→ N2 支付 ──→ N3 备货 ──→ N4 发货（四路分叉）──→ N5 物流跟踪 ──→ N6 收货/完成
                │                                                              │
                └──→ N8 取消/关单                                    N7 售后 ←─┘（也可从 N3/N4 进入）
```

| 节点 | 做什么 | 主单 | 子单 | 入口 |
|---|---|---|---|---|
| **N1 下单** | 预览 → 拆单（按门店）→ 锁库存 → 落主单+子单+行 | `WAIT_PAY` 或 `WAIT_OFFLINE_PAY` | `WAIT_PAY` | `POST /mp/order` |
| **N2 支付** | 回调/线下确认/0元 → `markPaid` → 实扣库存、出核销码、发事件 | `→PAID`（终态） | 实物 `→WAIT_FULFILL`；服务类 `→FULFILLING` | 支付回调 / `POST /biz/order/{no}/confirm-offline-pay` / 对账自查 |
| **N3 备货** | **只写 `prepared_at`，不改状态** | — | 仍 `WAIT_FULFILL` | `POST /biz/order/{no}/prepare` |
| **N4 发货** | 见 1.3 四路分叉 | — | `→FULFILLING` 或 `→COMPLETED` | 见下 |
| **N5 物流** | 仅 `EXPRESS`：登记→订阅→推送→节点→状态推进→微信绑定 | — | — | 事件驱动 |
| **N6 完成** | 确认收货 / 核销 / 标记送达 / 自动确认 | — | `→COMPLETED` | 见下 |
| **N7 售后** | 申请→审核→(退货)→退款 | — | `→REFUNDED` | `POST /mp/order/{no}/after-sale` |
| **N8 取消/关单** | 仅未付款 | `→CANCELLED`/`→CLOSED` | `→CANCELLED` | `POST /mp/order/{no}/cancel` / `OrderAutoCloseJob` |

### 1.3 N4 发货的四路分叉（按履约方式）

履约取值域 6 个（`Fulfillments.java:24-50`）：

| 履约 | 「发货」是哪个动作 | 子单状态 | 走物流域 | 微信上报时机 |
|---|---|---|---|---|
| `EXPRESS` | `ship()` 录单号 | `→FULFILLING` | **是** | 发货时 |
| `MERCHANT_DELIVERY` | **没有 ship**，只有 `delivered()` | `→COMPLETED` | 否 | `delivered()` 时 |
| `STORE_PICKUP` / `NEIGHBOR_PICKUP` | `markArrived()` 到货登记 | `→FULFILLING` | 否 | 到货时（自提单的"发货"=到货那一刻） |
| `STORE_VERIFY` / `APPOINTMENT` | 无（付款即出码） | 支付时直落 `FULFILLING` | 否 | 支付时 |

### 1.4 N6 完成的四个出口

| 出口 | 适用 | 责任方 | 入口 |
|---|---|---|---|
| 买家确认收货 | 快递/自送 | 买家 | `POST /mp/order/{no}/confirm-receipt`、微信"确认收货"推送 |
| 核销 | 自提/到店 | 自提点 | `POST /biz/pickup/verify` |
| 标记送达 | 自送 | 商家 | `POST /biz/order/{no}/delivered` |
| 自动确认 | 快递（**排除自提类**） | 系统 | `OrderAutoReceiptJob`（签收后 N 天 / 发货后 M 天，先到为准） |

### 1.5 N7 售后状态机（`OrderStateMachine.java:57-68`）

```
APPLIED ──┬──→ REFUNDING ──→ REFUNDED
          ├──→ WAIT_RECEIPT（仅退款 + 已揽收：先同意，签收后才退钱）
          ├──→ REFUNDED
          ├──→ REJECTED ──→ ARBITRATING ──→ REFUNDING/REFUNDED/CLOSED
          └──→ CLOSED
```
售后是**子单粒度**；进行中**不改子单状态**，只在退款终局把子单置 `REFUNDED`（全仓唯一写入点 `AfterSaleServiceImpl.java:654-658`）。
**整单退完才退券/退积分**（判据：该主单下所有子单都 `REFUNDED` 或 `CANCELLED`）；部分退不退券不退分。

### 1.6 主单/子单关系速查

| 事项 | 粒度 | 备注 |
|---|---|---|
| 支付 / 退款 / 取消 | **主单** | 一次支付一个支付单号 |
| 发货 / 核销 / 售后 / 分账 / 时间线 | **子单** | `ord_status_log` 只有子单粒度 |
| 金额 | 主单冗余合计 + 子单各自 | 积分列**只在子单**，主层读时汇总 |
| C 端列表 | **子单**（行上 `orderNo` 是子单号） | |
| C 端详情 | **主/子单号都认** → 两种视角 | 支付视角有 `subOrders`、无 `fulfillment` |
| B 端 / 运营端 | **恒子单** | |
