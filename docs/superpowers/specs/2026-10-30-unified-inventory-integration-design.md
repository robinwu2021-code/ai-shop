# 独立进销存统一接入与分层调用设计

日期：2026-10-30。状态：设计草案，待用户批准后编写实施计划。

## 1. 已确认的目标与边界

用户要求：ai-shop 的零售、美业、餐饮通过统一入口接入独立进销存；先封装基础调用能力，再封装业务 Service；当前支持直接 HTTP API，未来可通过 Nacos 等服务发现中间件寻址。

用户已确认：**保留现有库存权威，只统一接入与调用层**。本次不迁移餐饮本地库存主账，不重算历史库存，不变更各行业的扣减时点、来源证明及回补规则。

本设计中的具体类名、分批顺序和扩展机制是实施建议；不表示用户已经批准实现。现有入口/API 合同需要兼容，不要求调用方同一时间升级。

## 2. 当前事实与代码基线

- 设计基线为远端 `origin/codex/ai-shop-codex` 的 `92342744b`，实施前重新 fetch 并核对增量，不使用当前存在大量未提交修改的工作区作为发布源码。
- `backend/svc-client` 已有 `ServiceClientSpec`、`ServiceClients`、`ServiceCalls`：HTTP 代理、调用时解析地址、令牌头、超时及传输异常分类。
- `backend/shop-base/.../svc/ServiceLocator` 与 `ConfigServiceLocator` 已有服务逻辑名到地址的抽象，但属于商城基础模块；独立库存不得反向依赖 `shop-base`。
- `backend/inventory/inventory-client` 已有预留、库存动作、控制台转发和餐饮镜像客户端；错误解码、熔断等基础逻辑仍绑定在 `InventoryReservationClient` 上。控制台部分依赖领域 VO，尚未做到客户端契约与领域实现彻底分离。
- `shop-app/invbridge`、`shop-inventory` 中仍有领域 Service/Mapper 直调。现有远程模式按业主 `write_authority` 切流，路由仍依赖本地 ACL，不能通过关闭 `inventory.enabled` 完成脱离内嵌。
- `92342744b` 已补餐饮远程库存镜像。应在其上收敛调用封装，不能重做另一套镜像协议。
- 云端当前库存版本为 `856bd3ad9`，服务 `neargo-inventory@standalone`，`127.0.0.1:8086`，独立库 `neargo_inv`。商城尚未切流；当前服务没有自动获得后续 `92342744b` 的新接口。

## 3. 方案比较与选择

| 方案 | 优点 | 成本与限制 |
|---|---|---|
| A：扩展现有基础调用层，提供统一库存 SDK 与行业适配（推荐） | 保留 API；当前直连；以后只替换寻址适配；能逐步清理内嵌依赖 | 必须补齐类型化业务合同及漏切路径 |
| B：直接整体改用特定微服务客户端/注册中心框架 | 在确定的框架内可获得集中配置能力 | 当前引入注册中心与框架依赖，扩大独立服务和部署改动；仍不能解决业务合同缺失 |

采用 A 作为拟实施方案。Nacos 的职责是服务发现和实例选择，业务接口仍通过现有 HTTP 合同调用。本期提供发现扩展点、模式配置和替身实现的合同测试；**本期不安装 Nacos、不新增未经验证的 Nacos 客户端依赖，不宣称实际 Nacos 联调通过**。

## 4. 分层与依赖方向

```text
零售订单/售后    美业耗材/执行留存    餐饮物料/生产/镜像
               ↓ 现有行业 SPI / Port
ai-shop 库存接入适配层（身份、所有者判断、行业合同映射）
               ↓ 类型化业务 Service
inventory-client（统一入口 + 按能力拆分的业务接口）
               ↓ 库存协议上下文和错误映射
svc-client（寻址、HTTP、令牌注入、超时、异常分类）
               ↓ DIRECT / DISCOVERY 寻址适配
inventory-svc（契约、鉴权、领域规则、库存数据库）
```

- `svc-client` 不认识商家、SKU、耗材、库存错误码、Nacos SDK，继续只依赖基础组件。
- `inventory-api` 持有公开 DTO、错误码、命令及回执；不依赖商城或领域实现。
- `inventory-client` 仅依赖 API 与基础调用组件，不依赖 `inventory-domain`、`shop-base` 或业务 Mapper。
- 库存接入适配层保留在现有 `shop-inventory` / `shop-app/invbridge` 边界内，避免新增一个重复业务域；不在本次同时重构其他支付/物流客户端。
- 统一入口指同一个 SDK、身份规则和能力路由，不是一个接收任意 URL/Object 的万能业务接口。

## 5. 基础调用能力

### 5.1 统一寻址

在 `svc-client` 定义不含业务的寻址 SPI（建议名 `ServiceEndpointResolver`），按逻辑服务名解析本次调用的目标地址。复用现有 `ServiceClientSpec` 的逐次寻址机制；商城的 `ServiceLocator` 通过兼容桥接接入该 SPI，不复制第二套配置解析。

统一逻辑服务名为 `INVENTORY`；实现需兼容既有小写 `inventory` 调用标识。配置的大小写和尾斜杠规则保持一致。

- `DIRECT`：使用配置的显式 URL，当前即可接入云端回环服务。
- `DISCOVERY`：使用宿主注入的发现适配器；适配器负责逻辑名、部署隔离和健康实例选择。未提供适配器或无可用实例时明确拒绝调用。
- 模式显式选择；不在发现失败时偷偷切回直连，也不回落内嵌。未来 Nacos 适配属于可选宿主集成，不把 SDK 厂商依赖带入库存领域和 API。
- 寻址不得覆盖业务路径/查询参数；只接受合法 HTTP(S) 基址。实例切换不改变凭证、所有者及幂等指令身份。

### 5.2 调用上下文与结果

- 基础层：连接/读超时、请求关联标识、认证头挂载及传输结果分类；沿用现有 HTTP 组件。
- 库存协议层：系统凭证、业主引用、可信操作人、原业务指令/幂等键、库存错误解码与熔断。将这些从预留客户端中抽出，供所有库存业务 Service 共用。
- 行业适配层：从认证上下文及冻结来源构造租户、商家、门店、来源系统和操作人；不信任前端自行填写的库存业主。服务端继续以凭证限制系统及业主范围。
- 业务拒绝、未配置、无可用实例、网络不可达、超时、未知执行结果分别可识别。超时不能当作“未执行”或“成功”。
- 不添加写操作自动重试。沿用业务层已有的 Outbox/恢复任务及同一指令号；同键异参拒绝。发生不确定结果时优先按原号查询，并按业务协议决定补偿/重投。
- 日志和指标包含逻辑服务、能力、结果、耗时及关联标识，不打印密钥或完整敏感请求。
- 保留现有成功响应与异常的外部语义；业务错误不算传输故障。熔断按目标服务/能力的合理边界管理，具体粒度留给实现者，不为每个请求新建熔断器。

## 6. 库存业务 Service 与统一入口

提供一个对宿主公开的类型化入口（建议名 `InventoryServices`），共享配置、传输和协议上下文，并按能力取得业务 Service。以下为能力分组，不要求把所有方法塞进一个类：

| 能力 | 合同范围 | 主要调用方 |
|---|---|---|
| 主数据 | 业主开通/查询、SKU/物料与单位映射、上下架/退休、门店与库位映射 | 三行业适配、商品事件 |
| 查询与库存单据 | 可用量、余额/流水、入出库/调拨/盘点、供应商和报表 | 商城后台、行业查询 |
| 预留与履约 | 原号查询、占用/释放、付款分配、履约出库、部分释放 | 零售及使用既有预留协议的行业 |
| 原单处置与退货 | 原来源证明、处置确认、退货收货、原单回补和回执查询 | 售后、退款恢复 |
| 执行留存与耗用 | 美业现有执行留存/来源证明及耗材动作的远程合同 | 美业执行流程 |
| 需求计划与生产 | 现有物料、需求计划和扣料合同的远程表达 | 使用进销存主账的现有流程 |
| 库存镜像 | 来源映射、generation 会话、投递与回执、镜像查询 | 餐饮本地库存同步 |

每个公开方法使用确定类型的 Command/Query/Receipt。公开 DTO 放在 `inventory-api`；领域 VO 经服务端映射返回。已有预留客户端、控制台和镜像入口暂作兼容委派，逐步迁移现有调用者；新业务不再调用通用动态 URI 控制台接口。

不把内部管理员令牌放入商城运行时。业主开通/凭证签发等运维接口与普通业务能力分离，宿主只持有经过授权的业务系统凭证。

### 6.1 保留各行业库存权威

- **零售**：沿用订单冻结的 `PLATFORM / DUAL / INVENTORY` 以及现有生命周期。属于独立进销存的动作最终经统一 Service 执行；本次不把平台库存订单强行迁成进销存库存订单。
- **美业**：保留现有来源、执行授权、留存与退回规则。仅对原本归进销存的耗材/数量动作补远程合同，不把权益次数、预约资源或资金账变成库存余额。
- **餐饮**：保留本地库存主账和制作扣减规则；镜像仅是来源事实同步，不直接过账进销存实存。复用 `92342744b` 的镜像合同。既有属于进销存的物料/生产接口维持原所有者，不借本次重构改变其业务归属。
- 行业独立进程可继续通过 PLATFORM 完成既有身份/来源编排，最终进销存调用统一落在 SDK；本期不强制把所有行业进程都配成持有跨商家系统凭证的直接调用者。不得绕过 PLATFORM 现有认证和授权。

### 6.2 物理调用位置与冻结业务所有者

订单冻结的库存所有者决定“哪本账负责”，当前服务路由决定“该所有者由哪个进程执行”。两者不能混为一个开关。历史订单按原号和冻结来源查回；不得因当前配置变化改用另一套账。

对需要更改物理执行位置的业主，明确登记当前写入方并保证单写；新 SDK 查询该路由也必须通过受限远程合同，不能为寻址继续依赖本地库存 Mapper。尚未迁移的业主可使用显式过渡适配；远端故障时禁止自动调用内嵌补写。

## 7. 已知缺口必须一并收口

1. 商品 `SKU_UPSERTED` 投影和库存模式变化仍存在本地直调，切流后会被拒；统一改由主数据 Service 执行，保留事件与业务幂等身份。
2. `InventoryStockPort.restoreOriginal/receiveReturn` 对 SVC 显式拒绝；补服务端原单处置/退货合同和客户端适配，不能只把错误屏蔽。
3. 冻结原单回补路径仍可能经本地 `OriginalInventoryRestoreAdapter` 写入；所有原单回补/执行留存路径使用统一所有者解析与写入守卫，覆盖 `FLIPPING`，禁止旁路写账。
4. 物料、需求计划、生产、美业留存及桥接任务中现存的 Service/Mapper 直调逐项登记，不以“48个控制台接口已迁移”代表全部业务已迁移。
5. `shop.inventory.enabled`、`inventory.enabled` 与远程客户端装配解耦。纯服务模式的商城不能实例化库存 DataSource/Flyway/Mapper/领域 Service；是否显示功能仍按商城权限/功能开关判断，不能靠内嵌启用状态驱动远程入口。
6. 校正独立服务 Maven 重复 repackage 的构件问题：当前构建存在 `*-exec.jar` 的 Start-Class 指向 JarLauncher，而普通可执行包入口正确；发布脚本必须验证唯一产物和入口，避免下次按文件名选错包。

这些是完成统一服务接入的验收内容，不是通过重构自动变成已解决的问题。

## 8. 配置兼容与部署

- 保留现有 `shop.inventory.service.base-url/app-key/app-secret` 的兼容读取；新增模式、逻辑服务名和发现适配配置。新旧寻址配置同时存在且冲突时明确报错，不能悄悄选一份。
- 直连仍使用当前授权的库存服务实例。新服务端合同先部署并验证，再升级宿主客户端；缺少必需能力时阻断相关功能及切流，不把 404 当空业务结果。
- 库存账本与迁移历史不搬库、不改写已执行迁移；如需新增接入元数据或协议存储，仅增加新迁移并说明权属。
- 上线顺序：基础调用与兼容合同 → 服务端补齐能力 → ai-shop/行业适配迁移 → 原生数据库与云端隔离验证 → 明确业主对账与可恢复切流。此处是依赖顺序，具体任务清单在设计批准后的实施计划中制定。
- 上述开发不自动授权全量翻转商城业主、迁移既有数据或关闭现网内嵌模块。用户原始目标仍保留，达到切流门禁后再实施相应部署；本次设计批准也不代表所有业主已满足切流条件。
- 回滚使用匹配服务端能力的客户端版本，并检查在途命令；切回内嵌需要对账和单写闸门，不以直接改数据库字段代替。

## 9. 验收标准

1. DIRECT 下现有 HTTP API 与新版业务 Service 调用兼容；旧调用入口有兼容测试。
2. 使用发现适配替身证明同一业务 Service 可按调用解析不同健康地址；无实例、未配置适配器及错误模式均明确失败，不发生静默 fallback。实际 Nacos 环境验收单独列为未来事项。
3. 纯服务模式的商城可在没有库存数据库配置、没有本地域 Bean 的条件下启动并完成远程业务；架构测试禁止适配层访问库存 Mapper/本地领域实现（显式过渡模块除外，不能在纯服务模式加载）。
4. 零售：SKU新增/更新、锁货、付款/履约、取消、部分释放、退货收货、原单回补、超时查回；覆盖跨商家、跨店与重复请求。
5. 美业：按现有执行授权与来源证明完成耗材准备/留存/耗用/撤回，业务量和状态同重构前，重复及并发不多扣。
6. 餐饮：本地主账数量与扣减结果不变；镜像 generation、幂等投递、回执及查询走统一客户端；不把镜像写成实存。
7. 原生 MySQL 验证迁移、唯一约束、触发器、原单恢复和写入守卫；不能只靠 H2。证明 SVC/FLIPPING 时商城旁路写入被阻断。
8. 故障测试覆盖网络超时、远端已提交但响应丢失、熔断恢复和 Outbox 重投；所有重放使用原指令身份，无重复出入库。
9. 发布产物入口/版本/摘要正确；云端健康、鉴权与数据库迁移通过。业务验收与启动成功分别记录。

## 10. 留给实现者的选择

具体类名与包名、能力接口拆分的数量、兼容委派何时删除、指标命名及测试夹具组织可按现有规范决定。不得改变本设计已经确定的所有者边界、协议幂等身份、基础层无业务依赖和直连/发现可替换约束。
