# 分布式部署 · 集群 · 高可用 · 高并发 方案

状态：已确认（2026-10-14，§8 已拍板）
创建：2026-10-14
依据：全仓集群就绪度排查（后端 + 部署脚本，逐条带代码位置；关键两条已回到代码复核）

---

## 0. 结论

**现在不能直接起第二个实例。** 资金与库存主链的基础是好的（状态 CAS、条件更新、号段发号、唯一索引兜底），
但**验证码 / 限流 / 事件投递 / 调度器 / 部署脚本**都默认单机。另有一个**与实例数无关、现网就会发生**的并发缺陷：一券两用。

---

## 1. 现状（排查结论）

### 1.1 起第二个实例前必须解决（阻断）

| # | 问题 | 位置 | 多实例后果 |
|---|---|---|---|
| A1 | 短信验证码存进程内存 | `OtpStore`（`ConcurrentHashMap`） | A 实例发码、B 实例验码必败 |
| A2 | 图形验证码、运营重置密码令牌、自动化防重放 nonce 存进程内存 | `CaptchaService`、`PasswordResetTokens`、`AutomationTicketVerifier` | 随机失效 / 可跨实例重放 |
| A3 | 限流与输错锁定在进程内 | `InMemoryRateLimiter`、`OtpSendGuard` | 防刷短信 / 防爆破阈值 × 实例数 |
| A4 | **事件投递不认领**：先读 PENDING 再投再改 SENT，无锁无 CAS；每个实例启动把全部 PENDING 补扫一遍 | `OutboxDispatcher#dispatchOne`（注释写明「这里不加锁」）、`OutboxPump` | 同一事件投两次；**短信 / 企微 / 邮件 / 推送没有去重，真的重复发** |
| A5 | nginx 全部 `proxy_pass 127.0.0.1:8081`，无 upstream；发布脚本单机 `systemctl restart` | `deploy/tencent/nginx/*.conf`、`deploy-backend.sh` | 无法分流；发布即停服 |
| A6 | 生产关键配置默认值是单机行为：`token-store` 默认 memory、`media.provider` 默认 local（签名密钥未配时每次启动随机生成） | `application.yml` | 漏配一个环境变量就退回单机 |

### 1.2 高并发风险（与实例数无关或放大）

| # | 问题 | 位置 | 后果 |
|---|---|---|---|
| B1 | **一券两用**：用券是「读 → 校验 → updateById」，乐观锁冲突写 0 行不报错 | `CouponPortImpl#markUsed` | 两笔订单同时用一张券，都享受了优惠（**现网即可发生**） |
| B2 | 多处 `updateById` 不检查返回值（库存锁定行、事件行） | `StockPortImpl`、`OutboxDispatcher` | 失去上游 CAS 保护时静默丢写 |
| B3 | 平台连接池固定 10，`spring.datasource.hikari.*` 绑不上（手工建数据源）；MySQL `max_connections=200` | `PlatformDataSourceConfig` | 高并发排队；约 4 个实例到顶 |
| B4 | 进销存单号：秒级时间戳 + 进程内序号 + 3 位随机 | `InvKeys` | 多实例同秒约 1/1000 撞号 |
| B5 | 调度器 job-worker 不能起多个：无选主、触发非 CAS、`lockAtLeastFor=0` | `JobRegistry`、`JobRunDao`、`JobHandlerEndpoint` | 双 worker 时短任务背靠背跑两遍 |
| B6 | 事件投递是单进程 5 线程 + 无界内存队列；兜底轮默认关闭 | `OutboxPump`、`shop.outbox.legacy-scan.enabled=false` | 进程崩溃后要等下次重启才补投 |

### 1.3 已经集群安全

订单 / 支付单 / 发货单 / 售后单状态 CAS（转换门）；付款回调与退款幂等；积分扣减、领券、锁库存的条件更新；
BizKey（50 bit 随机 + 唯一索引）与订单号号段；下单幂等键（库内唯一索引）；业务任务体 ShedLock（库锁、库时钟）；
库内会话 + 撤销轮询；配送范围快照按库版本号失效；运营端 SSE 按实例各推各的。

## 2. 目标拓扑

```text
                 ┌─ CLB / nginx upstream（健康检查 /actuator/health/readiness，失败摘除）
 用户 ──HTTPS──► ├─ shop-app #1 ─┐
                 ├─ shop-app #2 ─┼──► MySQL 主（3307）──复制──► MySQL 从（只读查询 / 报表 / 故障切换）
                 └─ shop-app #N ─┘        │
                        │                  └─ 数据库锁（ShedLock）/ 事件表 / 会话表
                        └──► Redis（主从 + 哨兵或云 Redis）：验证码、限流、短期幂等、热点缓存
 job-worker 主 ──► 经 upstream 触发任务（任务体 ShedLock 防并发）
 job-worker 备 ──► 选主失败则待命（库内租约选主）
 媒体：COS（全部实例共享）；日志：每实例独立文件 + 集中采集
```

- **无状态应用**：进程内不留任何「别的实例要读」的状态。
- **会话**：库内会话（现状，生产已用）；接入 Redis 后可改 Redis 会话降库压。
- **一致性仍以数据库为准**：所有资金 / 库存 / 状态变化靠库内 CAS 与唯一键，Redis 只放可丢失的短期数据（验证码、限流、缓存）。

## 3. 并发与幂等的统一规则（所有领域对象遵守）

| 规则 | 做法 |
|---|---|
| R1 状态只经 CAS 写 | 转换门（`where status = 旧值`），0 行 = 冲突，**不覆盖、不重试** |
| R2 计数只经条件增量写 | `set n = n + ? where n + ? <= 上限`（库存、积分、券、已退件数 / 已退额），0 行 = 冲突 |
| R3 每个对外动作有业务幂等键 | 下单：Idempotency-Key；付款回调：通道交易号；退款：**售后单号**；分账回退：`REV-售后单号`；补贴收回：`SUBR-售后单号`；事件：eventNo |
| R4 外部副作用按「事件号 + 渠道」去重 | 短信 / 企微 / 邮件 / 推送发送前查去重表（唯一键 `event_no, channel`） |
| R5 `updateById` 必须检查返回值 | 带 `@Version` 的实体冲突时写 0 行不报错；0 行即抛 CONFLICT（加架构测试：业务写路径不得忽略 update 返回值） |
| R6 进程内不放共享状态 | 验证码 / 令牌 / 限流 / nonce → Redis（带 TTL）；缓存只放可陈旧的只读数据，并给失效时限 |
| R7 定时任务可重复执行 | 任务体幂等 + ShedLock；调度器单活（库内租约选主） |
| R8 事件「认领后投递」 | `update sys_outbox set status='DISPATCHING', lease_until=? where id=? and status='PENDING'`，1 行才投；租约过期由兜底轮回收；消费者幂等 |
| R9 迁移先扩后收 | 滚动发布期间新旧代码并存：先加列 / 加表（兼容旧代码），下一版再删旧列 |

## 4. 第 5 步对象模型的集群约束（编码时照此实现）

| 对象 | 约束 |
|---|---|
| `RefundLedger` | 行已退件数 / 金额用 R2 条件增量：`refunded_qty = refunded_qty + ? where refunded_qty + ? <= qty`；子单已退额同理；0 行 = 并发超退 → CONFLICT 回滚 |
| `AfterSaleRefundExecutor` | 每一步都幂等（R3）：分账回退 `REV-售后单号`、退款键售后单号、积分按售后单号流水；重放（重试任务 / 重复事件）不会多退 |
| `AfterSaleLineStore` | `uk(after_sale_no, item_id)`，重复写报唯一键冲突 |
| 售后申请 | 「一张子单同时只有一张进行中售后」现靠先查后插 → 改为库内保证：申请时对子单做 CAS 占位（`ord_sub_order.open_after_sale_no` 为空才写入），并发两张申请只一张成功 |
| `PostSplitReverser` / `PreSplitAdjuster` | 结算单累计字段用 R2 条件增量；最后一笔标 REVERSED 用状态 CAS |
| `RefundableQuery` | 只读，可走从库（后续）；计算结果不缓存（金额必须实时） |

## 5. 改造清单（按优先级）

### P0 · 现网即需修（与集群无关）
1. **一券两用**：`markUsed` 改为 `update … set status='USED' where user_coupon_no=? and status='UNUSED'`，0 行即拒单。附并发测试（两线程同用一券只一笔成功）。

### P1 · 起第二个实例之前
2. 引入 Redis（云 Redis 主从）：验证码、图形验证码、重置令牌、nonce、限流全部迁入，带 TTL；保留内存实现仅供本地开发。
3. 事件投递认领（R8）+ 租约回收兜底轮常开 + 外部通道去重表（R4）。
4. nginx upstream（≥2 实例、健康检查、`max_fails`）+ 滚动发布脚本（逐台摘流 → 发布 → 就绪检查 → 挂回）+ 优雅停机（`server.shutdown=graceful`，等在途请求与事件投递结束）。
5. 关键配置改为「生产缺省即报错」：`token-store`、`media.provider`、`media.sign-secret` 未配置时启动失败，而不是退回单机默认。
6. 每实例独立日志文件名（含实例号）+ 集中采集。

### P2 · 高并发
7. 连接池参数可配（修 Hikari 绑定），按实例数与 `max_connections` 统一规划；慢查询与 N+1 治理（接口预算 <1s，一般 ~200ms）。
8. R5 落地：全仓排查忽略 `updateById` 返回值的写路径，加架构测试守住。
9. `InvKeys` 改用号段或 BizKey 同款随机。
10. 热点读缓存（商品详情、类目、门店）进 Redis，按版本号失效；订单 / 金额不缓存。
11. 下单链路压测（目标峰值见 §8-2），按结果调线程池、连接池、库存热点行（必要时库存分桶）。

### P3 · 高可用
12. MySQL 主从 + 故障切换（云数据库或 MHA / Orchestrator），每日全量 + binlog 增量备份与恢复演练。
13. job-worker 主备（库内租约选主），备节点自动接管。
14. 多可用区部署（实例与数据库分布两个可用区），CLB 跨区。
15. 监控告警：实例存活、事件积压、任务失败、CAS 冲突率、退款卡单、慢接口；告警要能找到人（现状「告警不主动找人」）。

- P0 一券两用独立修，小改动，可立即做。

## 7. 测试

| 关注点 | 测试 |
|---|---|
| CAS / 条件增量 | 每个并发入口一条「两线程同时做，恰一方成功」的真库测试（转换门已有同款） |
| 事件不重投 | 两个认领者同时认领同一事件，只一个投递；外部通道同事件只发一次 |
| 无进程内状态 | 双实例集成测试：实例 A 发验证码、实例 B 验证通过 |
| 滚动发布 | 预发环境双实例，发布过程中持续压测请求，零 5xx |
| 故障切换 | 杀一个实例 / 主库切从库，记录恢复时长 |

## 8. 已拍板（2026-10-14）

1. **不引入 Redis**：需要 Redis 的场景（验证码、图形验证码、重置令牌、nonce、限流、短期幂等、热点缓存）用**数据库 + 本地缓存**实现，统一放在端口接口后面（`KeyValueStore` / `RateLimiter` 等），将来换 Redis 只换实现。§2 拓扑里的 Redis 暂由数据库承担；§5-2 改为「迁入数据库实现」。
2. **高并发**：从实现逻辑上保证无慢查询（索引覆盖、无 N+1、无全表扫、接口预算 <1s），满足基本方案；§5-10 热点缓存走本地缓存 + 版本号失效，§5-11 压测与库存分桶暂不做。
3. **一券两用**立即修（§5-1）。
4. **架构满足集群，部署仍单点**：代码一律按 §3 九条规则写，P1 中与代码相关的（2 迁入数据库、3 事件认领、5 配置缺省报错、6 日志按实例）照做；与部署相关的（4 nginx upstream / 滚动发布）只准备好配置模板，暂不启用。P3 高可用暂缓。
