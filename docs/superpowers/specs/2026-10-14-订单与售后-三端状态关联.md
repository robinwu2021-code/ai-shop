# 订单与售后 · 三端状态关联（含退款与退款限制）

> 2026-10-14。基于代码通读（后端 trade 域 + c-app / b-app / ops-web / packages/shared），关键结论均已回到代码复核。
> 目的：一张表看清「同一笔单在三端各显示什么、能做什么、退款在哪被拦」，并列出断点与修复归属。

---

## 1. 三套状态与它们的关系

| 层 | 表 | 状态 | 谁推进 |
|---|---|---|---|
| 支付单（主单） | `ord_order` | `WAIT_PAY` `WAIT_OFFLINE_PAY` `PAID` `CANCELLED` `CLOSED` | 付款回调 / 买家取消 / 超时关单。**PAID 后不再迁移** |
| 订单（子单，一店一单） | `ord_sub_order` | `WAIT_PAY` `WAIT_FULFILL` `FULFILLING` `COMPLETED` `CANCELLED` `REFUNDED` | 付款→WAIT_FULFILL；商家发货/到货→FULFILLING；收货/核销/自动收货→COMPLETED；售后退款→REFUNDED |
| 售后单 | `ord_after_sale` | `APPLIED` `REFUNDING` `WAIT_RECEIPT` `REFUNDED` `REJECTED` `ARBITRATING` `CLOSED` | 买家申请/撤销/申诉；商家同意/驳回/确认退货；平台裁决；超时任务 |

**对外只发 7 个契约值**（`OrderStatusProjector`，2026-10-14 接线）：

| 库（主单 × 子单） | 对外 |
|---|---|
| 主单 WAIT_PAY / 子单 WAIT_PAY | `WAIT_PAY` |
| 主单 WAIT_OFFLINE_PAY / 子单 WAIT_PAY | `WAIT_OFFLINE_PAY` |
| 子单 WAIT_FULFILL | `PAID` |
| 子单 FULFILLING / COMPLETED / CANCELLED / REFUNDED | 同名 |
| 主单 CLOSED | `CANCELLED` |
| 主单号视图（多店） | 付款前跟主单；付款后取**最落后的活跃子单**；全终态有退款→REFUNDED |

**售后与订单的联动**：
- 售后**不改主单**；任一笔退款落定 → 子单 `REFUNDED`（**不分全额/部分**，见 §4 B1）。
- 售后进行中（APPLIED/REFUNDING/ARBITRATING）→ 自动收货、结算跳过该子单；**发货、核销不拦**。
- 整单（主单下全部子单 REFUNDED/CANCELLED）退完 → 退券、退抵扣积分、收回赠送积分（各有开关）；部分退不动券与积分。

## 2. 三端对照（同一状态显示什么）

| 契约状态 | 履约形态 | C 端（shared `orderView`） | B 端（`orders/index.vue` 自写） | 运营端（`status.tsx`） |
|---|---|---|---|---|
| WAIT_PAY | — | 待付款 | 待付款（无页签） | 待支付 |
| WAIT_OFFLINE_PAY | — | **露键名**（缺词条） | 待当面收款 | 待当面收款 |
| PAID | 自提/邻里 | 备货中 | **待核销**（错：未到货，核销会被拒） | 待履约 |
| PAID | 快递/自送 | 待发货 | 待发货 / 待自送 | 待履约 |
| PAID | 到店核销/上门 | 备货中 | 待发货（错） | 待履约 |
| FULFILLING | 自提/邻里 | 已到自提点 | 待核销 | 履约中 |
| FULFILLING | 快递 | 已发货 | 已发货 | 履约中 |
| FULFILLING | 自送 | 已发货 | 配送中 | 履约中 |
| FULFILLING | 到店核销 | 待使用 · 凭码到店 | 待核销 | 履约中 |
| FULFILLING | 上门 | 待服务 | 已发货（错） | 履约中 |
| COMPLETED / CANCELLED / REFUNDED | — | 已完成 / 已取消 / 已退款 | 同 | 同（已退款为 danger 色） |

售后状态三端文案：C 端 `afterSale.status.*`（**缺 WAIT_RECEIPT**）；B 端无徽章、按状态给动作（**CLOSED 无分支**）；运营端 7 个齐全。

## 3. 退款流程与限制（现状）

### 3.1 申请（买家，`POST /mp/order/{子单号}/after-sale`）

| 限制 | 现状 | 位置 |
|---|---|---|
| 属主 | 非本人 → NOT_FOUND | `AfterSaleServiceImpl` |
| 订单状态 | 子单 WAIT_PAY / CANCELLED 拒；**REFUNDED 不拒** | `:215` |
| 一单一个进行中 | 已有非终态售后 → CONFLICT；终态后可再申请 | `:220` |
| 金额 | 不传 = 子单实付全额；上限 = 实付，**不扣已退** | `:225` |
| 生鲜 | 已揽收/已签收只允许质量类原因（DAMAGED/QUALITY/EXPIRED）；备货中/已出单 = 需商家确认（不自动同意） | `AfterSaleRules.applyGate` |
| 时间窗口 | **无** | — |
| 粒度 | 整张子单；无行级/件数 | — |
| 凭证 | 不强制（`needImage` 无人调用） | — |

### 3.2 处理

| 角色 | 动作 | 规则 |
|---|---|---|
| 商家 | 同意 | 退货退款→REFUNDING 等寄回；仅退款+货在途→WAIT_RECEIPT 等签收；其余立即退。**改金额只在已签收时允许**，上限 = 实付（**不以申请额封顶**） |
| 商家 | 驳回 | 仅 APPLIED，备注必填 |
| 商家 | 确认收到退货 | 直接退款，**不校验类型与状态** |
| 买家 | 撤销 | 任意非终态（含 REFUNDING） |
| 买家 | 申请平台介入 | 仅 REJECTED / WAIT_RECEIPT |
| 平台 | 裁决 | 仅 ARBITRATING → 退（REFUNDING，**只改状态**）/ 不退（CLOSED）；只能全额 |
| 系统 | 超时 | 商家 48h 不处理→自动同意（生鲜灰色除外）；寄回 7 天无运单→关；寄回后商家 48h 不确认→退 |
| 系统 | 签收 | WAIT_RECEIPT 在买家确认收货/自动收货时退款 |

## 4. 断点清单（按严重度，含归属）

### 资金类（P0）

| # | 问题 | 归属 |
|---|---|---|
| B1 | 部分退款也把子单置 REFUNDED → 买家看到「已退款」；且 REFUNDED 子单可**再申请、上限仍为全额实付**。支付侧以 `AS-<子单号>` 幂等返回首笔流水，不多出钱，但售后单记 REFUNDED、发退款事件，**账实不符** | 后端（与行级退款内核一起做） |
| B2 | 商家核定面板预填**订单实付**而非**买家申请额**，直接点同意 = 退整单；前后端上限都是实付 | B 端前端（预填+封顶）+ 后端（approved ≤ 申请额） |
| B3 | 运营端「人工干预」可改到 REFUNDED / 从 WAIT_PAY 改到 PAID，只改状态不动钱，无警示 | 运营端前端（警示）+ 后端（写入门收口） |
| B4 | 超时关单 `closeOne` 无条件 `updateById`，与付款回调并发时可把已付单写成 CLOSED 并释放库存/券 | 后端写入门（条件更新） |

### 功能断（P0，用户可直接撞到）

| # | 问题 | 归属 |
|---|---|---|
| F1 | C 端售后原因提交的是**翻译文案**，后端按原因码判质量类 → 生鲜发货后**任何原因都被拒** | C 端前端 |
| F2 | C 端「申请平台介入」发 `{reason}`，后端读 `appeal` → 申诉理由丢失 | C 端前端 |
| F3 | B 端售后卡：有 `impact` 提示时，同意/驳回/确认收货按钮整块不渲染（同一条 v-if 链） | B 端前端 |
| F4 | C 端开票传子单号，后端按主单号查 → NOT_FOUND | C 端前端 |
| F5 | C 端缺 `WAIT_OFFLINE_PAY`（orderView/orderStatus）、`WAIT_RECEIPT`（售后状态/提示）、`order.next.PAID` 词条 → 露键名 / 无说明 | C 端前端 |
| F6 | C 端用主单号进详情（收银台「查看订单」）时售后入口照常显示，提交必 NOT_FOUND | C 端前端 |
| F7 | 运营端「代客取消」对已付款单显示按钮，后端必拒；文案「取消即原路退款」与实际不符 | 运营端前端 |
| F8 | C 端「我发起的团」按 PAID 找待签收，后端发库值 WAIT_FULFILL → 整批签收按钮永不出现 | 后端（端口下发契约值） |

### 体验/口径（P1）

- C 端：驳回/关闭后不能再申请（入口要求「无任何售后」）；收银台把非待付款一律显示「支付成功」；「我的订单」跳错页；列表码标签写死「取货码」；已退款仍显示取货码、仍可开票；物流轨迹步骤覆盖终态。
- B 端：PAID 自提显示「待核销」等文案与履约不符（应复用 shared `orderView` 的形态归类）；售后 CLOSED 无展示；已核定单显示申请额而非核定额。
- 运营端：订单 `fulfillType`、售后 `type/keyword`、异常单 `kind/keyword` 筛选后端不认；干预历史「从→到」空白。
- 后端：极速退已废但 `instantRefundEligible`/商品「极速退款」标签仍按规则计算（对外承诺秒退）；WAIT_RECEIPT 无超时出口、送达/核销不触发 `settleOnReceipt`；`confirmReturn`/`shipBack` 不校验状态；换货按退款处理；POINTS 退款在 `pointsPort` 缺失时 NPE、退货不回补库存。

## 5. 本轮前端修复（只修已确认的断点，不改交互结构）

| 端 | 项 | 改法 |
|---|---|---|
| C | F1 | 提交 `reason` = 原因码；补充说明拼进 `detail`（后端 `reason` 字段即码；文案另存见下） |
| C | F2 | `raiseDispute` 发 `{appeal}` |
| C | F4 | 开票用主单号 `payOrderNo`（类型补字段，后端已下发） |
| C | F5 | 三语补 `orderView.WAIT_OFFLINE_PAY`、`orderStatus.WAIT_OFFLINE_PAY`、`afterSale.status/statusHint.WAIT_RECEIPT`、`order.next.PAID` |
| C | F6 | 主单号视图（无 `fulfillment`、有 `subOrders`）不给售后入口 |
| C | P1 | 售后入口：最新售后为 REJECTED/CLOSED 时允许再申请（REFUNDED 暂不放开，等 B1） |
| B | F3 | `impact` 提示与动作区拆成两条独立分支 |
| B | B2 | 核定面板预填并封顶于**买家申请额**（`refundMinor`）；无申请额才回落实付 |
| B | P1 | 售后 CLOSED 展示；已核定显示 `approvedMinor` |
| 运营 | F7 | `ORDER_TRANSITIONS.PAID` 去掉 CANCELLED；改正「取消即原路退款」文案 |
| 运营 | B3 | 干预目标为 REFUNDED / PAID 时弹二次确认：「只改状态，不退款、不收款」 |

> F1 的取舍：后端 `reason` 字段同时当「原因码」判规则、又当退款描述传给通道。本轮端上改发码 + 说明拼接为 `CODE：说明`
> 会让 `isQualityReason` 仍匹配不上，所以**只发码**，补充说明暂放进图片旁的备注不提交——待后端拆 `reasonCode` / `reasonText` 两列后再带上。（见 §6-4）

## 6. 需要拍板（后端，接写入门/行级退款时一起做）

1. **部分退款后子单状态**：保持原状态 + 记已退额（推荐，与行级退款内核一致），还是新增「部分退款」状态？
2. **再申请的上限**：实付 − 已退（推荐）。
3. **申请时间窗口**：是否按 `shop.settle.after-sale-days`（默认 7 天，签收/完成后）封口？超过后分账已划出，回退大概率失败。
4. **原因拆列**：`reasonCode`（判规则）+ `reasonText`（买家说明），C 端恢复带说明。
5. **极速退**：已废，是否同时下掉 `instantRefundEligible` 与商品标签（现在对外承诺了做不到的事）？
