## 0. 对第一阶段的复核（纠偏三处）

| 项 | 第一阶段怎么写 | 复核后 |
|---|---|---|
| "两套存储" | 口头上说成两张表 | **同一张表两套 ORM 视图**（V387 把 `ful_shipment` 改名为 `lgs_waybill`）。危害不是数据分叉，是**两套写路径各看一半列**、两套 rank 表、两条绑定路径 |

## 1. 设计原则（最佳实践 → 本仓落地）

| # | 原则 | 落地含义 |
|---|---|---|
| P1 | **库里只存抽象状态，展示态全部派生** | 不加 `SHIPPED/ARRIVED/待收货` 这类库状态；展示 = `status × fulfillment × 物流信号` 在端上一处算 |
| P2 | **状态写入只有一扇门** | 所有 `setStatus` 经 `OrderTransitions.apply()`；ArchUnit 禁止其他地方调；裸写入（D1–D5）全部收口 |
| P3 | **幂等靠唯一键，不靠先查后插** | 已是仓库原则；扩展到**运单号唯一** |
| P4 | **物流是独立上下文；一张子单可有多张运单** | 改号 = 作废旧运单 + 新建；运单号在**活跃运单内**唯一；节点永远挂在它自己的运单上 |
| P5 | **外部失败三分级 + 死信可复活** | `NOT_READY / RETRYABLE / FATAL` 保留；FATAL 必须有运营处置入口（含数据修正后重放） |
| P6 | **资金安全集合从状态机派生，禁止手工维护** | "进行中售后"= 状态机非终态；结算闸、统计、时间线共用一个函数 |
| P7 | **契约封闭且可证明** | 契约值域有测试枚举所有库值断言落在 7 值内；三端类型与词条从同一清单生成/对账 |
| P8 | **展示策略单实现** | shared `orderView()` 三端共用；b-app 删自写；`orderStatus.*` 退役 |
| P9 | **输入即校验、尽早失败、提示可操作** | 单号清洗 + 按承运商格式 + 重号拒绝并告知冲突订单 |
| P10 | **可观测覆盖已知失败形态** | 在途 0 节点 / 重号 / FATAL / 空转作业四项告警 + 处置台 |

## 2. 决策（Q1–Q10 + 新增 Q11–Q12）

| # | 决策 | 结论 | 理由（最佳实践） |
|---|---|---|---|
| Q1 | 运单号唯一性范围 | **`(carrier, waybill_no)` 在活跃运单内唯一**（活跃 = 未作废且未取消） | 承运商会在数月后复用号段，全局永久唯一会误拒；"活跃内唯一"正好抓住真错误（同一号挂两张在途单）。实现：可空生成列 `active_key` + 唯一索引（MySQL 可空列允许多 NULL） |
| Q2 | 录入重号 | **拒绝**，错误码 `WAYBILL_DUPLICATE`，消息带冲突子单号 | 静默接受 = 数据污染；重号 99% 是粘错行。同一子单重提同号是幂等空操作，不算重号 |
| Q3 | 改号 | **作废旧运单、新建运单**；旧节点留在旧运单上 | 轨迹可审计；混在一张上是数据损坏。Shopify/Amazon 均为 fulfillment 下多 tracking 记录 |
| Q4 | 格式校验 | **清洗 + 按承运商正则（长度/前缀）**；不做校验位 | 校验位各家不公开、易脆；长度+前缀已拦住绝大多数手误 |
| Q5 | 签收后"待收货" | **不加库状态**；`orderView` 增加物流信号输入，派生 `已签收·待确认` | 否则重回 `SHIPPED/ARRIVED` 老坑；列表用批量 `signedAtOf` 补信号，无 N+1 |
| Q6 | 主单 `CLOSED` 对外 | **投影为 `CANCELLED`**；主层状态永远经投影，不直发库值 | 子单本就落 `CANCELLED`；契约不该为内部"超时关"多一个值。取消原因由 `cancelReason` 表达 |
| Q7 | b-app 收敛 | **是**：状态文案用 shared `orderView`，商家动作用 `NEXT_ACTION × 角色` | 三端一份；"待核销"是动作不是状态 |
| Q8 | `EXCHANGE` | **一期删除**取值域与契约 | 半成品比没有更危险（现在=静默退钱不退货） |
| Q9 | FATAL 复活 | **允许运营对终态运单做"重绑"类重放**；订阅类重放仍拒终态；新增"修正收件人号→重绑" | 绑 token 对已签收运单无副作用；订阅改订会触发承运商 501 |
| Q10 | 两套物流访问层 | **删旧层**（`FulShipment`、旧绑定作业、旧轮询、`legacyTraceOf`），`logisticsPort` 改必需注入 | 并存 = 两套 rank/两套写列/一套空转；换源已完成，没有回退理由 |
| **Q11** | `REJECTED` 是否算"进行中" | **算**（卡结算），并新增 **REJECTED 超时自动 CLOSED**（默认 7 天，可配） | 资金安全优先；不加超时会永久卡结算。买家申诉窗口 = 这 7 天 |
| **Q12** | 跨商家主单聚合状态 | **取最落后的活跃子单**；全部终态时：有 `REFUNDED` → `REFUNDED`，否则 `CANCELLED`/`COMPLETED` | 这是电商通行口径（Amazon "partially shipped" 的本质）；`subOrders` 仍逐家给进度 |

> Q1/Q11 的数字（活跃范围、7 天）与 Q12 口径属业务判断，**可改**；其余为工程最优解。

## 3. 目标模型

### 3.1 订单（状态集合不变，写入门收口）

```java
// 唯一写入门。所有状态变更只能经它。
final class OrderTransitions {
    void applySub(OrdSubOrder s, String to, Operator op, String reason);   // assertSubOrderTransit / 商家闸 + 写 status + ord_status_log + 发事件
    void applyOrder(OrdOrder o, String to, Operator op, String reason);    // assertOrderTransit + 写 status + 留痕
}
```
- ArchUnit：`setStatus(` 只允许出现在 `OrderTransitions` 与实体内部。
- `closeOne` / `autoConfirmReceipt` / `markArrived` / `complete` 全部改经写入门（修 D1–D4）。
- **`intervene` 禁止目标 `REFUNDED`**：要退款必须建"系统退款"售后单走 `doRefund`（修 D5）。
- `complete` 的"降级单只推到 FULFILLING"改为显式两条边：校验与写入同一条（修 D4）。

### 3.2 契约投影（封闭、可证明）

```
contract(sub, main):
  main ∈ {WAIT_PAY, WAIT_OFFLINE_PAY}  → 按现规则
  main == CLOSED                       → CANCELLED            (Q6)
  main == CANCELLED                    → CANCELLED
  main == PAID                         → sub 投影（WAIT_FULFILL→PAID，其余原样）

headStatus(main, subs):   // 支付视角
  main != PAID → contract(main)
  main == PAID → aggregate(subs)      (Q12)

aggregate(subs):
  active = subs ∖ {CANCELLED, REFUNDED}
  active 非空 → min by rank(WAIT_PAY<PAID<FULFILLING<COMPLETED)
  active 为空 → any REFUNDED ? REFUNDED : CANCELLED
```
**封闭性测试**：枚举 `OrdOrder` × `OrdSubOrder` 全部常量，断言投影结果 ∈ 契约 7 值；枚举契约 7 值，断言三端 `OrderStatus` 类型与 i18n 清单逐一存在（接入 pre-push）。

### 3.3 展示策略（P1/Q5/Q7）

```ts
orderView(status, fulfillment, info: { appointmentAt?, signedAt?, waybillStatus? })
// 新增派生：
FULFILLING × SHIP_TO_BUYER × signedAt   → orderView.FULFILLING_SHIP_TO_BUYER_SIGNED  "已签收·待确认"
FULFILLING × SHIP_TO_BUYER × EXCEPTION  → orderView.FULFILLING_SHIP_TO_BUYER_EXCEPTION "物流异常"
```
- 列表行：后端 `list()` 批量 `logisticsPort.signedAtOf(subNos)` 填 `signedAt`/`waybillStatus`（无 N+1）。
- 详情头：有轨迹节点仍优先 `trace.step`（更具体）；否则 `orderView`；主单跨商家才回落 `orderStatus`。
- **退役** `orderStatus.*`（只保留给跨商家支付视角与运营端一对一徽标，改名 `orderStatusRaw.*` 以示非默认）。
- b-app：删 `statusText()`、删死词条 `statusARRIVED/statusREFUNDING`；动作按钮由 `NEXT_ACTION` + 角色决定。
- `order.next.*` 键改为契约值（`PAID` 替换 `WAIT_FULFILL`）。

### 3.4 物流（P4：一子单多运单）

**表** `lgs_waybill`（在现有基础上）：
| 列 | 变更 |
|---|---|
| `status` | 新增 `VOIDED`（作废，改号/撤销产生） |
| `voided_at`, `void_reason`, `superseded_by` | 新增 |
| `active_key` | **新增生成列**：`status NOT IN ('VOIDED','CANCELLED') ? CONCAT(carrier,'#',waybill_no) : NULL` |
| `uk_biz_ref` | **删除**（一子单多运单） |
| `uk_active_waybill(active_key)` | **新增**（Q1） |
| `idx_biz(biz_type, biz_ref, id)` | 新增，"当前运单"= 该 biz 下最新未作废一张 |

**当前运单**：`find(bizType, bizRef)` = `status != VOIDED` 按 id 倒序第一条。

**改号流程**（Q3）：
```
ship(sub, carrier, no'):
  normalize(no') ; validate(carrier, no') ; dupCheck(carrier, no')   (L1)
  if (carrier,no') == 当前 → 空操作
  写子单 express_* ; 留痕 ; 发 SUB_ORDER_WAYBILL_CHANGED(old, new)
Registrar(消费):
  旧运单: status=VOIDED, voided_at, void_reason='CHANGED', superseded_by=new ; 尽力退订（失败只记）
  新运单: 插入骨架 → 唯一索引冲突 → 抛 WAYBILL_DUPLICATE（兜底）
  发 LGS_WAYBILL_REGISTERED(new)
```
**推送匹配**（L4）：按 `active_key = carrier#no` 找单（唯一，不再 `limit 1` 碰运气）；找不到 → `UNKNOWN_WAYBILL` 计数 + 告警。

### 3.5 售后（P6）

```java
// 唯一口径，从状态机派生
final class AfterSaleStates {
    static boolean isOpen(String s)  { return !OrderStateMachine.afterSaleGraph().get(s).isEmpty(); }  // 非终态
    static Set<String> OPEN = ...;   // = {APPLIED, REFUNDING, WAIT_RECEIPT, REJECTED, ARBITRATING}
}
```
- 结算闸、统计、`activeOf`、时间线白名单全部改用它（修 C1/C2 与三份集合不一致）。
- 新增 `REJECTED` 超时 → `CLOSED`（Q11），`AfterSaleTimeoutJob` 第四条分支。
- `arbitrated=1` 标记：裁决后 `autoCloseUnshipped`/`autoApprove` 跳过（修 C8）。
- POINTS 退款：I4 查询排除 `refund_mode='POINTS'`；`pointsPort` 判空（修 C3/C4）。
- `EXCHANGE` 删除（Q8）；`needImage/reasonsFor` 后端强制（修 C6）；`escalate` 统一 `reason` 并落 `dispute_reason`（修 C7/C10）。
- 删死代码：`ruleService` 未用注入、`placedAtOf`、`instant` 置假逻辑（字段保留、恒 false、标 deprecated）。

## 4. 逐节点详细方案

> 每节只写**与现状的差异**。格式：触发 → 前置 → 写 → 事件 → 幂等 → 失败 → 展示 → 用例。

### N1 下单
- **差异**：无结构变化。补 `ord_order.status` 列注释与长度（`VARCHAR(16)` 恰好卡住 `WAIT_OFFLINE_PAY`，放宽到 32）。
- **用例**：现有 `ConsumerOrderFlowTest` 覆盖；加"列长度"迁移守卫。

### N2 支付 → `markPaid`
- **差异**：子单 `WAIT_PAY→WAIT_FULFILL/FULFILLING` 改经 `OrderTransitions.applySub`。
- **幂等**：不变（主单 `PAID` 直接返回）。
- **用例**：重复回调一个 `ORDER_PAID` 事件（已有）。

### N3 备货 → `prepare`
- **差异**：无（只写 `prepared_at` 是正确设计）。
- **展示**：C 端 `PAID × SHIP_TO_BUYER` 文案"备货中/待发货"已由 `orderView` 给。

### N4 发货（EXPRESS） → `ship`
- **前置（新增）**：
  1. `WaybillNo.normalize(no)`：trim、全角→半角、去空白、去中文及"单号:"前缀、大写。
  2. `ExpressCompanies.pattern(carrier).matches(no)` → 否则 `WAYBILL_FORMAT`（消息带该承运商期望格式）。
  3. `logisticsPort.findActive(carrier, no)` 命中且 `biz_ref != 本子单` → `WAYBILL_DUPLICATE`（消息带冲突子单号）。
- **写**：子单 `express_company/express_no`（不变）；状态经写入门。
- **事件**：首发 `SUB_ORDER_SHIPPED`；改号 **新增** `SUB_ORDER_WAYBILL_CHANGED`。
- **幂等**：同号同公司 → 空操作（不变）。
- **失败**：唯一索引冲突作兜底 → 翻译成 `WAYBILL_DUPLICATE`。
- **用例**：格式错拒 / 粘贴带空格清洗后通过 / 同号挂另一单拒 / 同单重提同号空操作 / 改号后旧运单 VOIDED 新运单 CREATED 且旧节点不混入。

### N4′ 发货（自送/自提/服务类）
- **差异**：`markArrived`、`delivered` 经写入门；其余不变。
- **用例**：`markArrived` 对非 `WAIT_FULFILL` 被状态机拒而非静默跳过（行为变化：静默→显式幂等返回，不抛）。

### N5 物流跟踪
- **登记**：一子单多运单（3.4）。
- **订阅**：`subscribe-enabled` **写进 `application.yml` 显式暴露**（默认仍 false，生产 env 置 true）；默认链去掉未实现的 `yto`。
- **推送**：按 `active_key` 匹配（3.4）。
- **推进**：删旧 rank 表，只留 `WaybillStatus.rank`。
- **微信绑定**：
  - 保留三分级；`9300561` 仍 FATAL，但**新增运营动作"修正收件人号并重绑"**：`POST /ops/shipments/{no}/receiver-phone` → 重新加密快照 → `bind_state=WAITING` → 发 `LGS_WX_BIND_REQUESTED`。
  - `replay(WX_BIND)` 对终态运单**放行**（Q9）；`replay(SUBSCRIBE)` 仍拒。
  - 删旧 `wx-waybill-bind` 作业与 `applyWxDisplay`（Q10）；`display_channel` 列退役（读路径本就不看它）。
- **用例**：重号推送只落到持有 `active_key` 的那张 / 改号后旧号推送落旧运单且不推进新运单 / 终态重绑成功写 token / 修正收件人号后重绑。

### N6 完成
- **差异**：`confirmReceipt`、`autoConfirmReceipt`、`complete` 经写入门；`autoConfirmReceipt` 签收时间改读 `LogisticsPort.signedAtOf`（修 B6）。
- **展示**：签收未确认 → "已签收·待确认"（3.3）。
- **用例**：签收 N 天后自动完成（已有）；列表行带 `signedAt`。

### N7 售后
- 见 3.5。
- **用例**：`WAIT_RECEIPT` 单卡结算 / 时间线显示"签收后自动退款" / `REJECTED` 7 天自动关 / 裁决后超时任务不关单 / POINTS 退款不触发 I4 / `EXCHANGE` 申请被拒 / 后端拒无图的 `RECEIVED` 档申请。

### N8 取消/关单
- **差异**：`closeOne` 主单 `→CLOSED`、子单 `→CANCELLED` 经写入门（修 D1）；对外投影 `CANCELLED`（Q6）。
- **新增**：`WAIT_OFFLINE_PAY` 超时（商家 N 天未确认收款）→ `CANCELLED` + 原因"超时未确认收款"——状态机注释早已声明、代码从未实现（第一阶段 F 项）。
- **用例**：超时单主单号打开显示"已取消"而非键名 / ops-web 不再抛 / 线下单超时自动取消。
