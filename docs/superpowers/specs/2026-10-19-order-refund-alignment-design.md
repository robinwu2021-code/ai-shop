# 订单、退款与权益结清对齐设计

日期：2026-10-19。状态：开发计划设计基线，尚未实现或验收。

## 1. 目标与事实校正

目标：保留支付、订单、发货、售后四台业务状态机，统一退款结清事实，逐步支持商品级部分退款、零现金权益结清和全积分结算；储值独立接入。

基线分支 codex/ai-shop-codex，编写时 HEAD=6ba503eb6。执行时重新记录 HEAD 和工作区状态。

前轮 Review 的“普通现金部分退款会直接转 REFUNDED”结论撤回为可达性不足：AfterSaleServiceImpl.apply 调用 BasicRefundPolicy.full，RefundPreparationServiceImpl 再次要求 approved 等于整单原实付，且已有退款时拒绝。当前一期入口只支持一次整单全退。RefundResultServiceImpl 的 fullyRefunded=true 是全退前提下的实现，不能单独证明可触发的部分退款缺陷。开放部分退款前必须替换这一假设。

当前 RefundResourceServiceImpl 允许现金成功后库存、券独立恢复，这是现行协议；新设计将应退消费者权益纳入售后结清，库存恢复仍独立。零现金积分链已有积分确认、结算确认，新增 BENEFITS_SETTLED 是事件及守卫对齐，不是从零建设退款保护。

依据：2026-10-14-订单状态机-完整方案.md 的 D2–D5，以及本聊天中已整理的统一退款方案。D1–D5 的未实现能力不能因已有状态机类存在就标为上线。

## 2. 业务规则

- Payment 保存原到账事实，退款不撤销 PAID。
- 每次批准形成不可变决定：目的、商品覆盖数量、退货数量、现金/积分/券义务、运费、合法保留额、原快照、决定与执行版本。
- PREPARED 只预占，不记实退。UNKNOWN 保留原指令与容量，只查询原号。
- 现金成功永久保留实退凭据；权益失败仅恢复权益，不能再次退款。
- 售后 REFUNDED：当前批准决定的现金及应退消费者权益全部结清。库存恢复不是该条件。
- 订单 REFUNDED：全部商品交易终止，且对应批准义务全部结清。部分退保持履约状态；交付与取消混合闭合为 COMPLETED；已交付商品的金额补偿保持 COMPLETED。
- cashProgress 沿用对外 refundProgress 的现金语义，goodsClosed 单独表达商品闭合。
- REFUND_SUCCEEDED 用于非零现金；BENEFITS_SETTLED 用于现金应退为零；线下 ACK 使用独立确认凭据。事件守卫读取可信结清事实，不接受客户端布尔值作为证据。
- 券按原支付影响集和政策判断返还资格，不通过订单终态反推资格，避免等待成环。政策不要求返还时，义务状态为 NOT_REQUIRED，而非未完成。
- 库存归原库存权威，按实际退货/取消范围处理；重试不回补整张订单。
- 结算保留原始 READY 基数；未付调整应付，已付保留付款事实并记录追偿，已分账记录实际银行回退。
- 全积分部分退使用明确的原始商品经济价值及权益数量基数；现金分母为零不得自动视为全退。

## 3. 架构选择

选择：复用现有执行单、积分绑定与资金恢复协议，新增统一结清判定、义务存储和商品闭合模型。保留各资金权威的短事务，不合并成跨服务长事务。

不选择只根据退款金额决定订单终态：无法处理补偿、保留运费、混合交付和零现金。不选择重写全部执行链：既有原号恢复、资金证据和结算 hold 已有价值，整体替换会扩大资金风险。

结清结果包含 cashProgress、goodsClosed、allGoodsTerminated、approvedObligationsSettled 和 targetOrderStatus。普通现金、积分、零现金及线下确认均经同一判定接口；权威凭据来自各自账本。

事务内：订单串行锁、执行版本检查、幂等实退登记、商品数量、义务意图、状态 CAS 和 outbox。事务外：现金通道、pay 权威、库存权威等外部调用。跨权威完成通过持久凭据重评；已完成步骤不重复执行。

## 4. 分期与兼容

M0 校正现状和边界；M1 统一结清及恢复，保持全额入口；M2 商品数量与部分退款；M3 全积分结算；M4 三端及发布；M5 储值独立项目。

M1 先支持新建执行的版本化结清协议。旧执行保持原恢复路径；版本标记必须持久化，不能仅用开关决定老单行为。新入口关闭仍须查询和收尾已有执行。

M2/M3 具备可信快照且通道支持的订单才开放；未知旧数据进入核对。历史 REFUNDED 不批量改回。迁移采用增量列/表，执行时按实际 Flyway 最新版本分配编号。

储值遵守当前已确认的活动/权益归属与业务限制；不默认开放线上充值、线上退款或任意混合支付。其本金/赠金规则、数据库及 API 需形成独立可执行计划后实施。

## 5. 验收与非目标

必须验证：一期全退限制；现金成功权益失败恢复；重复/迟到/未知回执；商品交付与取消混合闭合；补偿不耗件；全积分连续部分退款；退款与收货/放款并发；券跨店影响集；历史缺快照。

本次文档交付不包含实现、迁移、生产发布或真实资金认证。既有测试记录不能作为未来改动的通过证据。

## 6. M1 冻结的持久协议

- ord_refund_execution 新增 closure_version(默认1)、closure_status(默认 LEGACY)、return_coupon(审批时政策快照)。新开关 shop.refund.closure.enabled 默认 false；只有存在下单冻结券影响集的新订单才能选择版本2。选择结果永久落在执行单。
- ord_refund_coupon_scope 按 order_no 唯一，保存用户券号与原 allocation 对应的子订单号集合；无券也保存空集合，区别于未知历史。由 trade 在下单事务保存营销分摊返回事实，不读取或重算营销规则。
- ord_refund_obligation 按 execution_no/kind/source_no 唯一，保存 input_hash、payload_json、state、authority_proof、error_code、next_attempt_at；状态为 PENDING/PROCESSING/UNKNOWN/SUCCEEDED/NOT_REQUIRED。成功与不需要状态不可回退。
- 普通现金版本2：实退记账与执行 SUCCEEDED 先持久化；同事务建立消费者权益义务。之后事务外恢复券，凭据确认后单独事务结束售后。库存独立，不阻止消费者结清。
- 多子单券：在支付根锁串行下检查原影响集的退款数量事实，未满足全退的当次决定记 NOT_REQUIRED；最后使影响集全退的决定承担唯一返还义务。判断不依赖订单 REFUNDED，避免循环。支付根锁后只读其他子单事实，不反向加子单锁。
- 券 release(orderNo) 是同一原订单的幂等恢复；UNKNOWN 只重复原释放操作，不创建新现金退款。旧执行继续资源恢复的原退券协议；版本2资源工人不重复退券。
- 积分沿用既有 pay 确认与 source binding 凭据，义务层只引用其结果，不重复生成积分退回或扣回。T3 再接统一事件。
