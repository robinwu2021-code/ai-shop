## 2. 方案比较与推荐

| 方案 | 优点 | 代价与限制 |
|---|---|---|
| A：在旧主体订阅表加行业、支付与端字段 | 初期改动较少 | 无法清楚表达每店购买、多批续费、套餐分摊及升级来源；容易混淆主体与门店 |
| B：行业 Plan＋商城商品＋门店订阅／权益流水 | 支持用户要求的完整链路，可追溯购买、时间和价值，适配现有模块化结构 | 需要新增商城订单和履约，建立迁移桥接 |
| C：引入完整订阅计费引擎 | 可扩展用量计费、自动扣款、多币种复杂账单 | 当前需求不包含这些能力，会扩大平台收款和运维范围 |

推荐 B。本稿按 B 给出可评审设计，尚未视为用户已经选择并批准实施。

## 3. 边界与核心对象

保留现有模块化架构。逻辑职责如下，具体 Java 包和类划分留给实施阶段：

- 身份与门店域：账号、主体、门店、经营类型、人员归属和岗位权限。
- 订阅域：Plan 发布版本、门店订阅周期、端访问权益、升级转换、抵扣余额。
- B 端商城域：商品、SKU、套餐、报价、订单、硬件履约、退款协调。
- 支付域：平台收款的支付单、渠道通知、原路退款、查单对账。商城只保存引用，不自造支付成功事实。
- 平台配置域：经营类型目录、业务端目录、Plan 和商品发布、审计。

这里的 SaaS 访问权益属于门店商业授权，与现有消费者卡券／储值／活动权益不是同一种资产。可以复用支付和审计基础设施，不能直接给消费者权益表塞入“经营端访问资格”。

基本关系：

```text
门店 → 经营类型 → 三档 Plan → 已发布版本 → 业务端权益组合
商城 SKU → Plan 版本／独立端包／硬件／组合套餐
门店订单 → 支付确认 → 交付任务 → 门店订阅周期 → 业务端访问权益
门店＋已认证业务端＋当前时间 → 商业准入 → 现有岗位权限 → 业务 API
```

### 3.1 经营类型与业务端

- 建议产品经营类型使用 RETAIL／FOOD／BEAUTY；其与 `sys_industry` 是产品分类与通道分类两条轴。餐饮可能映射 CATERING，美业可能映射 LIFE_SERVICE，但映射不得代替资质审核。
- 首期一个门店一个经营类型；跨行业门店迁移是独立流程，不能通过改请求字段迁移已购 Plan。
- 业务端 code 示例：`END_BIZ_APP`、`END_BIZ_MALL`、`END_APP_POS`、`END_FOOD_KDS`、`END_BEAUTY_STAFF`。具体首批端清单待评审；现有总架构中不少岗位端仍为规划项，未验收端不得销售。
- 同一个 AppPOS 可以承载三行业工作区：无需给每个菜单或每个行业复制一套权限码，访问时同时匹配门店经营类型与适用范围。
- 平台内部运营端不可作为商家商品出售。C 端消费者访问也不因商家账号购买而获得平台内部访问权。

### 3.2 三档展示建议

| 档位 | 各行业共同保证 | 可配置差异示例 |
|---|---|---|
| FREE | 基础经营台、商城、账号、已有业务的必要处理 | 免费基础业务端组合 |
| PRO | 包含 FREE | 增加该行业可售的 AppPOS 等业务端 |
| CHAIN | 包含 PRO | 再增加 KDS、技师端等已验收行业业务端 |

上表只是组合方法，不承诺每个行业都有同名岗位端。若某行业只有经营台和 POS 两个已验收业务端，三档可以先展示但第三档标为待开放、不可购买；不能为了凑三档出售未实现能力。具体价格与组合由运营发布。

发布规则：每行业恰有 FREE／PRO／CHAIN 三个档位；FREE 永远保留；付费高档包含低档的全部可售端；每端只配置一个访问权益 code，不新增菜单／按钮商业权益。Plan 可以有多种期限 SKU，期限不是第四个档位。

## 4. 注册、建店与访问控制

### 4.1 开店事务

1. 验证账号与建店资格、经营类型有效性、幂等键。
2. 沿用 quick-start 或既有主体下创建门店流程；店员未经主体级建店授权不能创建。
3. 在同一本地事务中建立门店、老板归属、门店经营类型、订阅账户、FREE 周期和 FREE 端权益；记录协议版本与审计。
4. 返回门店号、FREE 状态和用户所选付费 SKU 的报价入口。选择付费也必须先有门店，再创建支付订单。
5. 资料／证照、主体审核、收款进件、服务范围依然单独展示，不因付费直接变 ACTIVE。

已有快速开店存在“有占位主体时复用”的逻辑。补经营类型时必须校验幂等请求与既有门店类型一致，不能悄悄把原门店换行业。

### 4.2 两层会话与三个判据

账号会话用于登录、列门店、建店、购买和续费；业务端上下文用于具体门店的端访问。

```text
可进入某端 = 账号有效 ∧ 人员属于该门店 ∧ 门店治理状态允许
            ∧ 门店经营类型适配该端 ∧ 当前时间存在该端的有效访问权益
可执行端内操作 = 可进入该端 ∧ 现有 RBAC 允许 ∧ 业务自身状态允许
```

- 登录后、恢复会话时、切门店时，均重新查询门店业务端资格。
- 新增服务端签发的短期业务端上下文，绑定 userNo、tenantNo、storeNo、endCode、entitlementVersion、过期时间。
- `endCode` 不能仅信任客户端传的 header。服务端登记每个接入客户端允许的业务端，并把其绑定到端上下文；人员 API 同时要求人员会话，设备 API 按设备与人员合同执行。
- 每个受保护路由登记允许调用的业务端集合；共享路由可允许多个端。不能用免费的经营台上下文访问只允许 POS 的路由。这个路由绑定只表达端边界，不新增菜单级商品权益。
- 业务端上下文仅代表准入，不能跳过员工角色授权、设备认证或订单状态校验。
- 访问权益过期返回业务错误与续费入口；只有身份失效才返回既有 401。不把商业到期伪装成密码错误。
- FREE 续费入口保持可用。必要的已有订单履约／退款走显式的基础端合同，限定为已有业务，不能开放同一路径接新单。

### 4.3 持续校验与缓存

登录检查是入口检查，业务 API 也必须按当前时间验证，避免用户长时间不重新登录绕过到期。

缓存键包含 tenantNo、storeNo、endCode、权益版本；缓存值包含最近开始／结束时间，缓存不得越过下个时间边界。续费、升级、撤销、退款、迁移时事务提交后发失效事件。关键收费端写操作在数据库事务或强一致权益读中复核版本；不得仅靠可能丢失的缓存失效消息。

读场景建议最多 60 秒缓存；这是待压测参数，不是撤销操作必须容忍 60 秒的承诺。商业权益解析异常时，付费端拒绝新操作并提示稍后重试；账号与基础续费入口不依赖付费权益解析成功。不得沿用角色解析器的旧权限兜底而放行已撤销权益。

## 5. 同 code 全来源时长累计与排期

### 5.1 已确认规则与来源记账

累计键为 `(tenantNo, storeNo, entitlementCode)`，不因 SKU、Plan 或套餐来源不同而另起一套会同时消耗的时间。每份 Plan、独立端包、套餐叶子组件和有限赠送交付，都记录明确的原始授予时长及来源。相同 code 的有限来源在实际排期中不重叠消耗，全部时长得到保留。

Plan 自身仍有基础订阅周期：同 Plan 续费从 `max(交付时刻, 已购 BASE_PLAN 末尾)` 接续；不同档不能用普通购买制造并行基础 Plan，必须走升级。Plan 内各端与基础周期保持一致，方便明确升档及折价。一个 Plan 版本对同 code 只配置一次；套餐不同交付组件分别含同 code 的，按各组件交付时长相加。

FREE 永久基础端不参与有限排队，永不作为尾部时间参与 max 计算。已由 FREE 永久提供的端不能另售有限端包；付费 Plan 包含这些端只展示“基础永久包含”，不额外发有限时间，也不为它分配折价基数。

### 5.2 排期设计：固定 Plan 周期，保留端包余量

为在跨来源累计的同时保持 Plan 组合的各端同时生效，本稿选择以下排期细节；这是设计默认值，不是用户另行指定的优先级：

1. 对每个 code，先保留当前及未来有效 Plan 周期的固定区间。Plan 因升级／退款发生变化时才调整这些区间，不因单端增购推迟整份 Plan。
2. 收集该 code 下所有独立端包／套餐独立端组件的未使用时长，按来源交付序号 FIFO，填入 Plan 固定区间之外最早可用的时间段。若无当前 Plan，从交付时刻开始；有连续 Plan 时排在其后。
3. 新增或续费 Plan 时，保留端包已经使用的历史区间，只将其尚未使用的时长重新排入空闲区间；必要时将一个来源拆成多个时间片。Plan 使用期间不同时消耗端包余量。
4. 每次重排记录旧／新时间片、原因、来源、版本和操作号；排期、权益版本和缓存失效事件在同一事务提交。不会改掉原购买时长和原价格。

每个重排事务使用同一个服务端 `effectiveAt` 切点：此前的有效历史只读保留，剩余量只能填入 `max(effectiveAt, 来源首次交付时刻)` 之后的空闲段，禁止回填过去。这里“已使用”是已经流逝的有效日历时长，不按用户是否登录或实际操作的小时数计费。新订单的所有数字组件使用同一交付时刻。

因此：Plan 的 POS 到 12 月 1 日，加购 30 天后，POS 合计到 12 月 31 日。随后 Plan 再续 30 天，Plan 自身到 12 月 31 日，原加购的 30 天排在其后，合计到次年 1 月 30 日。

若某端包 30 天已用 10 天，再购买含该端的 30 天 Plan，则端包过去 10 天不变，Plan 立即占用后续 30 天，再继续使用端包剩余 20 天。该端从新 Plan 生效起还有 50 天，而不是重叠后只剩 30 天。

### 5.3 访问与价值的权威口径

- 业务端可用性读取当前有效时间片；合计到期日来自连续覆盖时间，不能只读 Plan 到期日。Plan 到期回 FREE 后，尚有独立端包余量的端仍可继续使用。
- 同一 code 的当前排期区间可以合并供展示，但底层必须保留各来源，不能只更新一行最大结束时间。永久 FREE 与有限来源单独处理。
- 每个独立端来源应满足：已使用时长＋所有未使用有效时间片时长＝原授予时长，扣除已退款／撤销的明确部分；重排不产生时长，也不吞掉时长。
- Plan 的端时间片始终等于该 Plan 周期，因此 Plan 升级按其固定有效周期剩余比例计价，组合内多个端不重复计价。独立端包不参加 Plan 升级折价，其未用时长只重排保留。
- 升级属于显式价值转换：旧 Plan 的未用部分先关闭并折价，再购买新 Plan；不能既保留旧 Plan 未来时长又抵扣其全部剩余价值。端包及其他未转换来源继续按 code 累计。

## 6. 升级折价

### 6.1 计算口径

仅允许同门店、同经营类型、同币种、同基础 Plan 家族的升档。端访问包首期只有续费，不单独设高低档；硬件与赠送价值不参与 Plan 升级折价。

首期升级单只允许一个新 Plan 周期：Plan 购买数量为 1，套餐 Plan 组件的 unit_count 也为 1。要买多年可使用一个明确天数的长期 SKU，或升级完成后另行续费。普通续费允许多周期；这个限制保证一次转换有一个明确的新周期目标。

对旧 Plan 中每个未消耗完的周期 i：

```text
原周期时长 Di = originalEndAt - originalStartAt
剩余时长 Ri = min(Di, max(0, effectiveEndAt - max(valuationAt, effectiveStartAt)))
可转换余额 Vi = floor(eligibleBasisMinor_i × Ri / Di)
旧权益可抵扣 C = Σ Vi
可用抵扣 A = C + 已有门店订阅抵扣余额
本单抵扣 U = min(新 Plan 优惠后成交价 P, A)
本单现金应付 = P - U
升级后余额 = A - U
```

时间统一按毫秒差计算，不按页面上取整的“剩余天数”计价。金额用最小货币单位整数，逐周期向下取整；不得使用浮点金额。

若退款使尚未开始的队列向前重排，估值使用最新有效起止计算剩余时间，原始购买时长只作为分母。已使用周期不重排；未开始周期重排前后时长必须相同。

`eligibleBasisMinor` 是该周期分摊的现金实付，加上合法转入的旧订阅抵扣价值；不含优惠券减免、赠送时长和硬件价值。续费的未来周期按全部未使用价值计入。升级多次时保留转入价值来源，不能把抵扣余额再次当作新的现金充值。

示例：365 天原实付 365 元，已用 165 天，剩余 200 天，折价 200 元。升级商品新周期成交价 699 元，则现金支付 499 元；新周期从升级交付生效时刻起算。示例价格仅用于说明。

旧余额 800 元、新价 699 元时，应付为 0，剩余 101 元留在门店订阅抵扣账户；不会支付负金额，也不静默丢弃旧价值。

### 6.2 报价、占用与付款后转换

1. 报价读取门店当前订阅版本、待生效周期、商品版本和余额版本，记录 `valuationAt` 与策略版本，建议有效 15 分钟。
2. 所有会改变门店数字权益的订单（Plan 新购／续费／升级、独立端包、含数字权益的套餐）创建时都锁门店订阅账户并建立唯一结算占用，直到全部数字组件交付或确认无付款关闭。所有使用订阅抵扣的订单均锁余额账户，校验报价未过期且版本一致，并预留指定历史批次；新购／续费无新转换时 C=0。纯硬件单不占用数字权益排期。
3. 占用不冻结既有权益的正常使用，但阻止另一笔数字购买、赠送、人工改期或退款先行改变该店排期。门店治理停用仍可即时执行；紧急来源撤销若必须越过占用，应使订单进入关闭／已付款补偿分支，不能继续按失效来源交付。
4. 在有效期内完成支付，使用订单锁定的折价；报价至交付之间的短暂使用不追扣差额，新 Plan 自实际交付生效起算。这是明确的价格锁定政策。
5. 服务端确认支付事实后，本地事务一次性：锁订阅账户 → 校验占用 → 将旧有效和未来 Plan 周期标记转换 → 写来源抵扣账 → 消耗抵扣 → 留存余额 → 创建新周期及端时间片 → 按 code 重排独立端包未用时长 → 写排期变更记录 → 增加权益版本 → 写 outbox。
6. 未支付取消前先关闭支付单并查明结果；“结果未知”不能先释放占用再允许下一笔升级。成功付款但本地交付失败，保留占用并由任务重试，不要求重新付款。
7. 订单超时后只有取得支付域“关闭终态且无成功付款”的确认才释放占用；处理中或未知仍持有占用。迟到通知若支付时间在截止前且占用仍有效，按原订单补交付。占用已释放后出现任何矛盾付款事实，或实际付款晚于截止，进入异常原路退款，不重新覆盖当前订阅；退款未知继续查原单。
8. 应付为 0 的订单走同一履约流程，记录 ZERO_SETTLEMENT，不伪造支付渠道流水。

一笔订单的全部数字周期、组件及受影响 code 的排期必须在同一本地事务交付，完成后才释放数字结算占用；单个周期任务成功或硬件发货都不能提前释放。硬件尚未发出不妨碍数字组件完整交付后释放。

升级折价只转换明确参与升级的 Plan 周期。独立单端包不会被顺带取消、重复抵扣或转成余额；其未来排期可以在保留全部未用时长的前提下随新 Plan 重排。

原有余额预留额为 `max(0, U-C)`，其中 U 为本单抵扣、C 为本次新转换价值；结算先消耗本次转换批次，再按报价锁定顺序消耗已预留的历史批次。未使用的转换价值和原余额继续留存，不能按另一种批次顺序消费未预留余额。

### 6.3 套餐分摊与防止价值重复使用

组合套餐在发布时定义每个交付项的定价分摊权重，创建订单时将折后成交金额分配到 Plan、端包、硬件等组件，分配合计必须等于整单成交额。按最小货币单位分配，尾差按固定组件顺序补齐。

只用分摊给 Plan 的可抵扣基数计算升级；硬件和赠送组件不计入。若旧套餐同时含独立端包，端包保留自己的来源和剩余时长，实际时间片参与同 code 统一排期，不会因 Plan 升级被重复转换。

新购买的是混合套餐时，抵扣上限是其中 Plan 组件的折后分摊价，而不是套餐整单金额。令整单成交价为 P_total、Plan 组件成交价为 P_plan，则 U=min(P_plan,A)，现金应付=P_total-U；硬件和独立端包不能消耗这类订阅抵扣余额。

一个数字组件购买多份周期时，先按固定顺序将该组件的现金、抵扣和可折价基数分配到每个周期，最小单位尾差补齐；所有周期分摊之和必须等于组件，不能给每份周期复制整组件金额。赠送周期单独建立零基数来源，不把赠送时长混进付费周期分母。

## 7. 商城订单、支付与交付

商品类型：PLAN、END_ACCESS、HARDWARE、BUNDLE。一个订单绑定一个门店；一个组合套餐可以产生多个组件和交付任务。

- 商品主数据、已发布版本和成交快照分开；订单保存经营类型、SKU／Plan 版本、端清单、期限、金额分摊及退款政策快照。
- 购买 Plan 不需要门店已完成向消费者收款的进件；这里是商家向平台付款，收款方为平台的合法签约收款账户。
- 支付服务必须显式区分平台商城订单业务类型和收款主体；复用现有支付网关前验证该合同，不可复用商家子商户号收取平台订阅款。
- 支付成功由服务端通知／查单确认，并核对收款主体、订单、金额、币种、支付状态；前端“支付完成”回传不产生权益。
- 订单支付状态：UNPAID、PAYING、PAID、CLOSED；交付状态另列 PENDING、PROCESSING、PARTIAL、COMPLETED、FAILED；退款状态再独立维护。
- 同一支付单重复通知、查询补偿和任务重放，通过事件幂等、交付任务唯一键保证只发一次。
- 硬件库存预占与订单超时释放按 SKU；发货必须绑定订单组件。数字权益和硬件分项交付，不能等硬件签收才激活明确约定即刻生效的 Plan。
- 套餐禁止嵌套循环；首期禁止在一个套餐里放多个基础 Plan，或硬件数量和数字周期之间做隐式相乘。每项必须声明数量单位。

## 8. 退款、撤销与异常

- 未交付订单可按快照政策退款；未使用的数字来源可执行来源级退款，并按 code 重排其他来源；已经使用过部分时间片的端包不能伪装成整份未使用来源自动全额退款。
- 已使用数字权益首期走人工审核与明确报价，不承诺无条件按日自动退款；硬件按独立售后政策处理。
- 已转换旧周期不能直接再次退款；已有转换后继的升级单进入人工链路核算，不允许先自动退旧现金再保留新权益／抵扣余额。
- 升级订单若无后续转换并允许退款：撤销新来源，现金仅原路退还本单现金部分；使用的订阅抵扣按来源恢复为门店抵扣余额，不能变现金。余额恢复与原周期恢复二选一，本稿选择余额，避免双重补偿。
- 已退款、撤销、冻结、已转换周期都不再贡献访问资格；撤销必须关联来源，不能只手改汇总到期日。
- 退款采用先冻结受影响的可用来源、确认渠道退款、再完成权益与余额调整的可恢复流程。失败或未知状态保留记录并查单处理，不能靠跨服务数据库事务假设一切会回滚。
- 因安全、治理、资质暂停门店时，即使端权益有效也不得绕过暂停；恢复付费权益不自动恢复人工或平台停用状态。
- 到期任务用于提醒和状态投影，API 读时判定有效期；任务漏跑也不得继续放行已到期端。

## 9. 发布、安全与运营

FREE 端清单属于系统保障：发布器校验经营台／商城等必要入口不被删掉，线上不得物理删除已被订单或权益引用的 code。

Plan 和 SKU 已发布版本不可变，修改创建新草稿并重新发布。停售只影响新订单；已锁价且未到支付截止的订单按快照继续，紧急风控停售应显式关闭未付款单并保留原因。

运营职责分别授权：目录读取、草稿编辑、发布、订单查询、退款审核、赠送／撤销、迁移。价格、权益组合、赠送、撤销、退款及抵扣调整都记录操作者、原因、前后版本和关联订单。

手工授予和正式购买走同一交付入口，来源不同；商业管理权限使用现有运营 RBAC 扩展的明确码，不沿用封禁权限来代表一切收费操作。

## 10. 存量迁移和兼容

1. 新表与旧表并行，旧主体订阅不直接改名为门店订阅。新门店先启用新模型，旧客户按迁移批次切换。
2. 门店经营类型从可信的已审核资料映射；LIFE_SERVICE 不能一概等同美业，未知类型进入待确认，期间维持旧资格，不强制降为 FREE。
3. 对存量付费主体生成“旧合同→覆盖门店→新端权益”的迁移清单；明确原合同覆盖哪些店、原额度、原有效期、宽限承诺、试用历史及人工覆盖。
4. 旧主体门店数上限／跨店统计等主体能力暂由 `mch_entity_plan` 兼容层负责；门店新 Plan 不增加主体门店额度。新商城不再新售旧主体方案；迁移客户在旧额度内建店仍走原规则。最终主体额度是否改为每店付费，另行确认后再退役兼容层。
5. 旧记录常没有收款单和现金金额。迁移出的访问权益可继续使用，但折价基数为 0／待核验；不得以新挂牌价虚构旧实付。经审核的历史付款凭证补入迁移基数并记审计。
6. 迁移保护权益和每店新 Plan 必须共享迁移来源标识，避免旧主体一笔付款在多家店各自生成全额抵扣价值；历史价值按确认方案分摊，分摊总额不超过历史可用价值。
7. 先影子比较门店列表、端可访问性、到期日与金额，再按门店切换权威读取；禁止在两个模型里同时续同一笔付费权益。
8. 已迁入新模型的门店，旧 `/biz/plan` 只提供适配读取，旧试用和人工授予写入口拒绝或转到新交付合同，不能双写随意延期。
9. 回滚只切读取策略并保留所有新付款和履约账；已有新订单的门店不能简单回退旧表而丢失付款权益。

## 11. 实施顺序与核验

这是一份设计，不是开发任务逐项实现计划；设计确认后再拆开发任务。

建议顺序：经营类型／业务端目录与 FREE → 账号与开店入口 → Plan 版本和运营发布 → 商城订单及平台支付 → 权益交付／续期 → 升级折价／余额／退款 → 存量迁移与端接入。

必须核验：租户门店隔离、端上下文伪造、到期边界、同 code 跨来源累计、Plan 续费重排端包、已用端包分片保留、排期时长守恒、跨版本周期、套餐分摊、赠送零折价、未来周期升级、余额守恒、重复回调、并发数字购买、支付未知、交付重放、退款来源恢复和旧合同保护。完整业务验收见需求文档。

待业务确认：各行业三档实际组合及价格、可售端验收状态、周期单位、是否宽限、退款政策、余额是否长期有效、存量合同按门店分摊原则。建议首期抵扣余额不过期，以免迁移损害既有价值；如需有效期须单独发布并告知。
