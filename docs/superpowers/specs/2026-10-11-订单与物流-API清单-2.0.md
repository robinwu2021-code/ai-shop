# 订单与物流 · API 清单与实现方案（方案 2.0 配套）

> 2026-10-11。配套：[方案 2.0 设计](./2026-10-11-订单与物流-方案2.0-design.md) · [现状梳理](./2026-10-11-订单生命周期与物流容错-梳理.md)。
> 从下单到最终结束，**按节点 N1–N8 组织，每节点分 C 端 / B 端 / 运营端**。
> 每个 API 给：方法+路径 · 粒度 · 权限 · 现状标记 · 实现方案（前置→写→事件→幂等→失败→展示）。
> 现状标记：✅保持 · ✏️改造 · 🆕新增 · 🗑️删除。标记依据方案 2.0 的批次 B1–B8。

## 0. 全局约定

| 项 | 约定 |
|---|---|
| **粒度** | C 端列表=子单；C 端详情=主/子单号都认（两视角）；C 端取消=解析成主单整体取消；B 端/运营端=恒子单 |
| **鉴权** | C 端 `Authorization: Bearer`（属主写在查询条件里防 IDOR）；B 端 `@perm.canBiz(...)` + 门店数据域；运营端 `@perm.can(...)` + 商家数据域 |
| **状态写入** | ✏️ 一律经 `OrderTransitions.applySub/applyOrder`（B3）；ArchUnit 禁其他处 `setStatus` |
| **契约状态** | 对外只有 7 值；主单 `CLOSED`→投影 `CANCELLED`（Q6）；跨商家聚合=最落后活跃子单（Q12） |
| **幂等** | 下单靠 `Idempotency-Key`；支付回调靠主单 `PAID` 终态；发货靠"单号+公司都没变"；售后退款靠 `status=REFUNDED` |
| **错误码** | 🆕 `WAYBILL_FORMAT` / `WAYBILL_DUPLICATE`（B4）；现有 `STOCK_SHORT_ITEMS` / `AFTERSALE_*` / `ORDER_STATE_ILLEGAL` 等不变 |
| **X-Client** | 决定展示面 surface（MP/APP/H5），影响 trace displayMode |

## 2. N1 下单

### C 端

**`POST /mp/order/preview`** ✅ · 预览（主单形状）
- 前置：加购项非空；按门店拆单（`split()`，ADR-031）；弱主体限额按商家分判、经营额度按主体汇总。
- 不写库。填 `offers`/`outOfRange`/`pickupDistanceM`/`maxQty`；`pickupDistanceM=-1` 表示无坐标（不是 0）。
- 失败：不拦超范围（预览只提示），建单才拦。

**`POST /mp/order/capability`** ✅ · 结算能力
- 返回可用支付方式等；无副作用。

**`POST /mp/order`** ✏️(B2) · 下单，返回**支付视角**
- 幂等：`Idempotency-Key` 头；同 key 重复提交返回原单。
- 前置：锁库存（`available-qty>=0` 守卫）；超范围此时才拦。
- 写：主单（`WAIT_PAY` 或 `WAIT_OFFLINE_PAY`）+ 每门店一张子单（`WAIT_PAY`）+ 行；积分列只落子单。
- 事件：`ORDER_CREATED`。
- ✏️：子单初态落库经写入门（B3）；无结构变化。配套迁移：`ord_order.status` 列 `VARCHAR(16)→32`（`WAIT_OFFLINE_PAY` 卡满 16）。

**`GET /mp/order/{orderNo}/pay-method`** ✅ · 可用支付方式
- 主/子单号都认（`resolveOrder`）；只认主单号会让列表进来的单报"数据不存在"。

### 运营端

**`POST /ops/orders/proxy`** ✅ · 代客下单
- 权限 `ORDER_MODIFY`；复用 `orderService.createFor(userNo,...)`，属主参数化（不用当前登录人，否则查出来是空→404）。
- 返回 `OrderVO`。

**`GET/POST /ops/orders/proxy-limit`** ✅ · 代客限额读写

## 3. N2 支付

### C 端

**`POST /mp/order/{orderNo}/pay`** ✅ · 发起支付
- 主/子单号都认；0 元/免支付通道（`FREE`）就地 `markPaid`。
- 返回 `payParams`（prepayId 等）。

**`GET /mp/order/{orderNo}/pay-result`** ✅ · 支付结果回查
- = `detail(orderNo, null)`，粒度随传入号。端侧不自判成功，回查为准。

### B 端

**`POST /biz/order/{subOrderNo}/confirm-offline-pay`** ✅ · 确认线下收款
- 权限 `BizPerms.RECEIVE`；守卫"不是等确认收款的单一律拒"；整段 `executeWithoutScope` 绕数据域（否则"确认收款报订单不存在")。
- → 复用 `markPaid`（`WAIT_OFFLINE_PAY→PAID`）。
- ✏️：子单迁移经写入门（B3）。

### 系统（非端，列此说明）

**支付回调** `POST /pay/callback/{channel}` · `/pay/callback/stub` ✅
- `markPaid`：主单 `WAIT_PAY→PAID`（终态，回调只推进不回退）；子单实物→`WAIT_FULFILL`、服务类→`FULFILLING`；出核销码（所有子单）；实扣库存；发 `ORDER_PAID`/`SUB_ORDER_PAID`；服务类支付即微信上报。
- 幂等：主单已 `PAID` 直接返回（重复回调一个 `ORDER_PAID`）。
- ✏(B3)：子单迁移经写入门。

## 4. N3 备货

### B 端

**`POST /biz/order/{subOrderNo}/prepare`** ✅ · 开始备货
- 权限 `BizPerms.SHIP`；**只写 `prepared_at`，不改状态**（仍 `WAIT_FULFILL`）；幂等（已备不覆盖时刻）；前置只允许 `WAIT_FULFILL`。
- 作用：`prepared_at` 是售后 `FulfillStage.PREPARING` 的唯一来源。

## 5. N4 发货

### B 端

**`POST /biz/order/{subOrderNo}/ship`** ✏️(B4) · 快递发货
- 权限 `BizPerms.SHIP`。
- **前置（新增三道，B4）**：
  1. `WaybillNo.normalize(no)`：trim / 全角→半角 / 去空白换行 / 去中文及"单号:"前缀 / 大写。
  2. `ExpressCompanies.pattern(carrier).matches(no)` 否则 `WAYBILL_FORMAT`（消息带该承运商期望格式）。
  3. `logisticsPort.findActive(carrier, no)` 命中且非本子单 → `WAYBILL_DUPLICATE`（消息带冲突子单号）。
- 写：子单 `express_company/express_no`；状态 `WAIT_FULFILL→FULFILLING` 经写入门（商家闸：不能从未付款出发）。
- 事件：首发 `SUB_ORDER_SHIPPED`；🆕 改号发 `SUB_ORDER_WAYBILL_CHANGED(old,new)`。
- 幂等：单号与公司**都**没变 → 空操作。
- 失败兜底：唯一索引冲突 → 翻译成 `WAYBILL_DUPLICATE`。
- 下游：`notifyShipping`（写 `trd_shipping_upload`）；`ShipmentRegistrar` 消费事件登记运单（改号时作废旧运单+新建，Q3）。

**`POST /biz/order/{subOrderNo}/delivered`** ✏️(B3) · 自送已送达
- 权限 `BizPerms.SHIP`。自送单无 ship 步，这里一步到 `COMPLETED`（商家闸）。
- 事件：`SUB_ORDER_COMPLETED`；补 `notifyShipping`（否则自送单微信侧收不到发货信息）。
- ✏️：状态经写入门。

**`GET/POST /biz/order/{orderNo}/express{,/quotes,/cancel}`** ✅ · 快递100 下单取件
- 下单取件 → 回调回填运单号 → 复用 `ship()`（仅子单仍 `WAIT_FULFILL` 时）。

### 运营端

**`GET /ops/shipments`** ✅ · 运单列表
- 权限 `FULFILLMENT_LOGISTICS_READ`；筛选 `status/carrier/keyword/subState/bindState/subChannel/profile`。

**`POST /ops/shipments/{shipmentNo}/waybill`** ✏️(B4) · 原地换号
- 权限 `FULFILLMENT_RULE_UPDATE`。
- ✏️：改号语义改为"作废旧运单（`status=VOIDED`,`superseded_by`）+ 新建"（Q3）；旧号节点留旧运单；清 `display_token` **且** `display_channel`（修 B7）。

**`POST /ops/shipments/{shipmentNo}/replay`** ✏️(B8) · 重放
- 权限 `FULFILLMENT_LOGISTICS_REPLAY`。action ∈ `{SUBSCRIBE, WX_BIND}`。
- ✏️(Q9)：`WX_BIND` 对**终态运单放行**（绑 token 对已签收单无副作用）；`SUBSCRIBE` 仍拒终态（改订触发承运商 501）。

**`POST /ops/shipments/{shipmentNo}/receiver-phone`** 🆕(B8) · 修正收件人号并重绑
- 权限 `FULFILLMENT_RULE_UPDATE`。
- 实现：校验手机号格式 → 用 `PhoneCipher` 重新加密写 `receiver_phone_enc/last4` → `bind_state=WAITING`、清 `bind_error` → 发 `LGS_WX_BIND_REQUESTED` → 审计 `SHIPMENT_RECEIVER_FIX`。
- 解决：9300561（我们存的号与承运商面单号不符）的唯一人工出路。

**`GET /ops/logistics/channels`** ✅ · 渠道能力总览

## 7. N6 完成

### C 端

**`POST /mp/order/{orderNo}/confirm-receipt`** ✏️(B3) · 确认收货
- 子单粒度（路径名 orderNo 但按 subOrderNo 查）。`FULFILLING→COMPLETED` 经写入门。
- 触发 `settleOnReceipt`（若有 `WAIT_RECEIPT` 售后→走退款）。
- 另一触发：微信"确认收货"推送事件。

### B 端

**`POST /biz/pickup/verify`** · **`/verify/batch`** · **`/verify/search`** ✏️(B3) · 核销
- 权限自提台。闸：`NOT_THIS_PICKUP`/`ALREADY_VERIFIED`/`NOT_PAID`/`NOT_ARRIVED`（未到货的码不许核销）。
- `complete()`：降级单（`require_buyer_confirm=1`）只推到 `FULFILLING`（核销≠完成，由买家确认收口），其余→`COMPLETED`。
- ✏️(D4)：校验的边与写入的边改为同一条（现在校验 `→COMPLETED` 却写 `FULFILLING`）；经写入门。
- 事件：`SUB_ORDER_COMPLETED`。

**`POST /biz/order/{subOrderNo}/delivered`** — 见 N4（自送送达即完成）。

### 系统

**`OrderAutoReceiptJob`** ✏️(B6) · 自动确认收货（cron `0 0 3 * * *`）
- 签收后 N 天或发货后 M 天先到者；**排除自提类**（超时未取该退款不该替签收）；有处理中售后跳过。
- 发货时间取 `ord_status_log` 进入 `FULFILLING` 那条（子单无发货时间列，`updated_at` 会被刷新）。
- ✏️：签收时间改读 `LogisticsPort.signedAtOf`（修 B6）；状态经写入门。

## 8. N7 售后

### C 端

**`POST /mp/order/{orderNo}/after-sale`** ✏️(B6) · 申请售后（子单粒度）
- 前置：子单须在 `{WAIT_FULFILL,FULFILLING,COMPLETED}`（`WAIT_PAY/CANCELLED` 拒）；`refundMinor<=payAmount`。
- `FulfillStage` + 生鲜判定 → `AfterSaleRules.applyGate`：生鲜已发货非质量原因→拒；灰色地带→需商家确认。
- ✏️(C6)：`needImage(RECEIVED)` **后端强制**（现在仅前端装饰）；`reasonsFor` 后端按 stage 收窄。
- ✏️(Q8)：拒绝 `EXCHANGE` 类型（取值域删除）。
- 落初态：非自营 `APPLIED`；自营资金聚合 `ARBITRATING`。进度快照 `fulfill_stage`。
- 事件：`AFTER_SALE_APPLIED`。

**`GET /mp/after-sale/reasons`** ✏️(B6) · 原因清单
- ✏️：按 `stage`/`fresh` 收窄（现在无条件全量）。

**`GET /mp/after-sale`** ✅ · 我的售后列表
**`GET /mp/after-sale/{afterSaleNo}`** ✏️(C2) · 售后详情
- ✏️：时间线白名单补 `WAIT_RECEIPT`（否则"签收后自动退款"那条任何端看不到）。

**`POST /mp/after-sale/{afterSaleNo}/cancel`** ✅ · 撤销 → `CLOSED`
**`POST /mp/after-sale/{afterSaleNo}/ship`** ✅ · 填回寄单号（写 `express_no`，无轨迹）
**`POST /mp/after-sale/{afterSaleNo}/escalate`** ✏️(C7/C10) · 申诉 → `ARBITRATING`

- 注：仅 `REJECTED`/`WAIT_RECEIPT` 可申诉（`APPLIED` 不在图里）。

**`POST /mp/upload/image?scene=aftersale`** ✅ · 上传凭证（≤5MB）

### B 端

**`GET /biz/after-sale?status=`** ✅ · 商家售后列表（待处理附 impact 预览）

**`RefundRetryJob`** ✏️(C3) · cron `0 */10 * * * *`
- I4 查询排除 POINTS 退款。

## 9. N8 取消 / 关单

### C 端

**`POST /mp/order/{orderNo}/cancel`** ✏️(B3) · 取消
- 传子单号也解析成主单整体取消。仅未付款（`WAIT_PAY`/`WAIT_OFFLINE_PAY`）。
- 已付款集单单走 `cancelPaidPeriodOrder`：不改主单状态，逐子单系统全额退款。
- 写：主单 `→CANCELLED`、子单 `→CANCELLED` 经写入门；释放库存/名额（条件 UPDATE 打标记后再减，防还两次）。

### 运营端

**`POST /ops/orders/{orderNo}/proxy-cancel`** ✏️(B3) · 代客取消（固定 to=CANCELLED）
**`POST /ops/orders/{orderNo}/intervene`** ✏️(D5) · 人工干预
- 权限 `ORDER_MODIFY`；迁移由后端状态机判定（不采信端上 `ORDER_TRANSITIONS`）；必写原因。

- 扫 `WAIT_PAY ∧ payDeadlineAt≤now` → 主单 `CLOSED`、子单 `CANCELLED`。
