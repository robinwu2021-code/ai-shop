## §0 结论与需求覆盖

原方案已包含早餐/午餐/晚餐等时段餐牌、茶饮加料、固定/自选套餐和耗用报表目标，但渠道差异与原料耗用只达到部分设计。需要把“餐牌适用范围、渠道专属选配、权威差异计价、实际库存消耗”补成闭环，不能继续把这些全部推迟为一个笼统CORE-01依赖。

| 补充需求 | 原有覆盖 | 缺口与风险 | 本版落点 |
|---|---|---|---|
| E01 早餐、午餐、晚餐及自定义餐牌 | fnb_menu/schedule/exception/context/store；API004～006/017/109～111/114 | 未固化多个命中餐牌的冲突规则；不能把餐段和渠道当互斥枚举 | §2.1时段及上下文 |
| E02 按外送平台同步不同餐牌 | 来源/履约及外部映射目标已定义 | context无provider/account；无发布批次、远端确认和旧版本回调守卫 | 渠道绑定及同步任务 |
| E03 不同渠道不同价格、不同配料 | FNB-B07和核心报价原则；全局菜品选配组 | 无渠道价格依据引用；绑定仅goods_no/group_no，无法表达餐牌专属选配 | 权威价格策略引用及餐牌菜项选配 |
| E04 饮料、奶茶、小料独立价格与库存 | modifier/component、option_group、bundle及对应API | 免费选择不等于零耗用；默认配料、组合、SKU尺寸与BOM缺闭环 | §2.3选配与§2.5配方 |
| E05 固定套餐、自选套餐 | bundle/group/choice及INCLUDED/ADD_SKU/DIFF_BASE | 缺父子计价与库存执行树的实际核心接线；容易双扣和重复记收入 | §2.4及核心合同任务 |
| E06 菜品消耗统计 | FNB-J05/J08/J11、制作事件和报表077 | 无配方/耗用事实表；领料、出库和实际耗用未分；库存数量精度不足 | §2.5/2.6及独立进销存合同 |

E01～E06是既有FNB需求的验收细化，不冒充新增六项独立顶层需求；原109项矩阵数量不因本评审自动变化。

## §2 优化设计和实施步骤

### 2.1 餐牌按时间、来源、渠道分别建模

餐牌仍独立于基础商品分类。早餐、午餐、晚餐、夜宵、节日等是模板或自定义名称，不把名称写死在程序枚举里；沿STANDARD/TIME/SEASON/EVENT表达规则。外送A午餐餐牌同时具备“午餐时段”和“A平台账号绑定”，无需新增一套渠道商品。

销售上下文至少包含：entityNo、storeNo、orderSource、fulfillment、可空channelBindingNo及服务端判定时点。终端、销售来源、履约方式和外部平台分别校验，不能让扫码H5客户端自报外送A拿到它的价格。外送渠道身份由获准适配器及平台门店映射解析。

| 条件 | 采用规则 |
|---|---|
| 门店、来源、履约、外部渠道 | 先精确匹配授权范围，未配置的外送渠道拒绝，不回退堂食餐牌 |
| 普通周规则与指定日期例外 | 指定日CLOSED拒绝；OPEN替代该营业起始日周规则，再与门店营业时间/接单日历求交 |
| 时间区间 | 左闭右开；早餐结束时刻不能继续提交早餐单；日切沿现有营业日切点，时区取门店策略，餐牌不得另设矛盾时区 |
| 跨午夜 | 22:00～次日02:00以开始营业日及星期解释，end_day_offset=1；按日历窗口求交，不重复建立营业时间 |
| 同一exclusiveGroup重叠 | 最高priority生效；同优先级重叠发布时拒绝；跨组可并存 |
| 多餐牌有同一SKU | 保留menuItemNo及各自规则；价格/选配不同不能仅按skuNo去重，购物车记录实际选择的餐牌条目 |
| 菜单快照过期 | 草稿可提示；报价/正式提交服务端重新核验，不能静默换餐牌或换价；已受理订单保留历史 |

### 2.2 同一SKU、多渠道价格与发布同步

同一杯奶茶在堂食、外送A、外送B可以有不同价格，继续共用商品/SKU和库存，不为价格差异复制SKU。餐牌上下文引用报价权威的pricePolicyRef；每个渠道绑定指向获准策略，策略内按SKU/配料/套餐和生效日期决定金额。策略也必须约束主体、门店及渠道，不能将任意策略号作为客户折扣入口。

堂食沿原门店有效价；配置了渠道策略的外送场景必须命中其有效策略，缺失/过期时报告价格不可用，不悄悄回退堂食价。报价返回quoteRef、币种、各行/选配/组件分摊、总额、有效期及策略版本，终端金额只作展示；提交用权威报价重验。

发布流程为：草稿校验 → 冻结本地修订 → Outbox同步任务 → 渠道转换/上传 → 记录外部请求号及确认版本。同步状态与本地PUBLISHED分别显示；局部失败、超时UNKNOWN、旧ACK不能误标全量成功。按原请求号查询恢复，不盲目重发；平台不支持原子替换时明确保留远端部分生效状态及补偿任务。

外部映射定位到渠道账号/外部门店、餐牌条目、SKU、选项及配置版本；回传订单按它购买时的映射/版本识别，不用最新餐牌重解释旧外部编号。若渠道回流不带可识别的修订或可靠映射依据，重用外部编号须保持语义兼容或按该渠道协议延后切换；无法确认时进入接入异常，不猜最新映射。第三方已成交订单的金额权威随既有接入authority模式确定，不能重新套当前本地价再扣款或二次扣库存。

### 2.3 奶茶、饮料与配料管理

| 层 | 用途 | 价格和库存 |
|---|---|---|
| 商品/SKU | 原味奶茶；中杯/大杯、瓶装/现制等真正销售规格 | 原商品权威；不同SKU可引用不同配方 |
| 免费口味 | 糖度、冰量、温度等 | 复用prd_spec_dim/value；免费不代表不影响原料，用明确配方调整规则解释 |
| 单项小料ADDON | 珍珠、椰果、布丁等，可附加或独立销售 | salesSkuNo引用价格；库存可由成品SKU或原料配方承担 |
| 配料组合COMBO | 珍珠+椰果双拼等固定组合 | 组合销售SKU计价一次；成员展开制作和耗用，不再次累加售价 |
| 选配组 | 必选/任选、默认、互斥、最少最多及“前一份已含” | 数量约束归餐饮；已含/追加金额及优惠分摊由报价核心确认 |

保留商品级默认选配；fnb_menu_item增加option_mode=INHERIT/REPLACE，新增菜项选配组关系。INHERIT使用商品默认；REPLACE只用餐牌条目显式列出的组，空列表表示该条目无选配；不得回退商品组。渠道特殊的数量/默认/互斥用独立选择组修订表达，避免无限叠加覆盖。

某小料沽清只禁用对应选项；必选组没有合法可选项时，整道菜不可售。不能静默换小料，恢复沽清也不补物理库存。最终可售由门店接单、已发布餐牌/渠道、基础商品、必需选配/组件、库存及配额共同确定。

配料组、配料及组合发布前校验主体/门店、成员规格、数量、默认值、循环和引用版本。第一版套餐不嵌套套餐，COMBO不嵌套COMBO；“可自由组合”通过多选组表达。组规则、数量及库存应在服务端校验，不能只由终端隐藏不可选项。

赠送或已含配料依然产生物料需求；免费糖冰不创建收费SKU。少糖、去冰等只有配置了配方调整才改变耗料，不能默认把“少糖”猜成50%。每份同SKU不同选配保留独立实例，不能合并成丢失选配归属的一行。

### 2.4 套餐的计价树与库存树

沿既有bundle/group/choice支持固定、自选套餐，保留INCLUDED/ADD_SKU/DIFF_BASE，由核心确定补差、优惠和退款分摊。一个39元套餐中有奶茶和小吃，销售收入合计仍是39元及合法追加价；组件有制作/耗用数量，不再各记一笔39元套餐收入。

每个可制作节点只选一种库存执行模式：SELLABLE_SKU、RECIPE_LEAVES或NONE。套餐容器不扣库存时为NONE；库存只在选定的叶子需求上汇总一次。若卖的是预制成品，则扣成品库存，不在销售时再次扣它生产时已消耗的原料。

CORE-01必须同时交付价格树、原来源到核心行分配和库存需求树；不得让原订单先扣商品库存、餐饮随后又扣同一份组件/原料。需要预占的原料在权威受理时按已冻结的需求树认领，实际制作再转消耗；不能等付完钱才发现没有奶或珍珠。

### 2.5 配方和耗用

餐饮维护SKU配方工作头、物料行及选配调整，发布为不可变修订。物料只引用进销存itemId、库存单位与换算版本，不要求原料能在前台销售，也不复制物料档案、余额或采购成本。配方包括基准产出和每份净用量：第一版净用量按制作数量线性缩放，损耗率定义为投入损失比例，毛用量=净用量/(1-lossRate)，0≤lossRate<1，由库存规定精度与舍入，不混用另一个“加成比例”口径；已选收费配料的配方增量与基础配方不得重复包含同一默认小料。

同SKU可有配方变体，recipe_code=DEFAULT是默认变体；特殊渠道需要不同基础配方时由餐牌SKU条目显式绑定同SKU变体，校验门店及SKU，不复制商品。未显式覆盖时取默认配方。配方调整先应用唯一SET或原值，再合计ADD；REMOVE与同目标的其他调整互斥，最终量不得为负。

QUOTE/受理冻结当时的配方、选配及换算依据；实际制作使用该冻结版本，后续修改配方不回写历史。不足料而需替代物料时记录获准替代/补料事实，不能静默应用新配方。实际领耗数量使用明确操作回执，不能用理论克重自动冒充实耗。

执行链：订单权威预占物料需求 → 厨房释放制作/部分制作 → 本地主事务记录耗用意图+Outbox → 独立库存按原需求/操作键过账 → 保存单据行和成本回执。跨服务不包长本地事务；UNKNOWN查原键；部分成功按行记录，不将整笔标CONFIRMED。

库存单位精度由进销存定义。优先评估现有物料最小单位是否能无损表达数量与估值；不可无损表达时扩展权威数量/成本合同，不在餐饮截断BigDecimal或盲目改成毫克后把单位成本舍为零。未齐前可以做理论耗用分析，但实际扣料/真实成本必须保持未就绪。

| 事件 | 库存与统计处理 |
|---|---|
| 未制作取消/退餐 | 释放尚未消耗的原预占，不生成已制作耗用 |
| 已制作退款 | 财务退款不返还原料；已发生消耗保留 |
| 部分制作 | 按制作事件及对应数量消费已冻结的需求，只处理该部分 |
| 重做 | 新制作事件和新耗用键；保留原耗用及重做原因 |
| 已制作报废 | 分类为已发生耗用中的报废，不把同一份已扣原料再扣一遍；新增原料报损才新增真实出库 |
| 库存更正/实际退库 | 依进销存获准反向单据记录，不因负数退款自动冲回 |
| 领料/库位调拨 | 厨房领料只代表移库或发出；若非真实消耗凭证，不标成逐杯实际耗用 |

### 2.6 消耗报表和示例

| 口径 | 来源 | 展示约束 |
|---|---|---|
| 销售数量、退菜数量、净销售数量 | 正式受理来源与售后事实 | 赠品、套餐容器、组件分列；不以厨房重做增加销量 |
| 制作、出品、上菜、重做和报废数量 | fnb_kitchen_task及不可变service_event | 部分制作/重复回调守恒，不用支付单数推制作份数 |
| 按销售理论需求 | 成交冻结配方×售出/已含选配 | 是预计需求，不能标实际耗用 |
| 按制作理论耗用 | 已释放/开始制作的有效数量×冻结配方及调整 | 包含实际重做，明确在制品；与库存比较时对齐事件范围和水位 |
| 实际耗用/退料 | 进销存真实耗用及反向回执 | 整批领料只有批次事实时，不伪造逐菜实耗；分摊结果标估算 |
| 差异与成本 | 同单位、同范围的实耗−制作理论耗用；历史过账成本 | 缺历史成本显示未知，不按零成本或当前采购价生成毛利 |

默认维度：门店、营业日、餐段、渠道、餐牌修订、商品/SKU、配料、物料；支持下钻制作事件与库存单据。跨单位不直接相加；报表077沿受控reportCode扩展，异步导出沿078/079，不另起餐饮库存报表账。

例：售出1杯大杯奶茶，冻结配方为牛奶150ml、茶汤100ml、糖20g，额外选择1份珍珠30g。售价由渠道报价确认；库存需求是对应原料及包材各一次。退款前已经制作，则销量/退菜及收入按财务事实展示，牛奶等耗用仍保留；重做一杯产生第二次制作耗用，但不增加第二笔销售。若只有整桶珍珠领料记录，只能展示该批领料及理论30g，不能声称这杯实耗恰好30g。

### 2.7 表设计增量候选

以下为9张新fnb候选表，未计入当前73张业务表/79张候选表，未生成DDL。均沿原BaseEntity、entity_no、业务号、CAS、逻辑归档和审计约定；事实表仅追加更正，不覆盖历史。价格规则、物料和库存余额仍在其权威域。

### 2.9 分阶段执行计划

每阶段按“AC失败测试 → 观察红灯 → 最小实现 → 真源/生成物/主库及双部署验证 → 一次只读审查与必要修复 → 独立提交”执行。下列均为目标，当前未勾选为已实施。

| 顺序 | 对齐原任务 | 工作及准出条件 |
|---|---|---|
| P0 设计和合同收口 | CAT-01B/C、CAT-02～06、CORE-01、INV扩展 | 统一主/旧生成源、9张候选和既有表增量；补渠道身份、价格规则、物料精度及成本契约；此轮评审是P0输入，不代表P0全部完成 |
| P1 菜品、配料、套餐及配方配置 | CAT-01B/C、04/05/06配置及Recipe | 菜品、配料/组/套餐及SKU配方可管理和发布；物料/单位引用真实目录；价格库存仍未就绪时仅配置 |
| P2 时段/渠道餐牌 | CAT-02/03 | 早餐午晚及自定义餐牌；日期/跨日边界；渠道专属选配与价格引用；基础时段餐牌可冻结发布；未获P3真实价格策略核验的渠道餐牌只能留草稿/预览，不能假发布 |
| P3 权威报价、库存基础与需求树 | CORE-01、ORD-02/03、CAT-05/06成交及库存扩展 | 先实现渠道报价、物料数量/估值精度及需求预占，再用P1发布配方构建唯一库存树；行分配、并发预占/取消及渠道餐牌最终发布联通；无实价/预占禁止接单 |
| P4 制作耗用执行 | KIT、ProductionConsumption、库存扩展 | 消费P1冻结配方与P3原预占；部分制作/重做/取消、UNKNOWN恢复、历史成本回执及过账不重复；旧零售交付出库兼容通过 |
| P5 渠道同步及回流 | 接入模块、CatalogSync | 先核定试点provider真实协议，再实现上传、部分失败、超时查询、映射版本、回流订单定权；框架可先开发，未核对协议不伪造已联通 |
| P6 消耗报表与日结联验 | RPT及DAY | 销量/制作/理论/实耗/损耗分列，套餐不重收入；按营业日和事件水位可追溯，缺成本不算假毛利；日结保存数据缺口，不冻结未知为已对账 |

P1内部逐个业务切片交付：①CAT-01B/C菜品维护/详情/真实分页；②CAT-04/05口味组、收费小料及COMBO；③CAT-06固定/自选套餐配置；④SKU配方及选配调整，先具备真实物料/单位目录，再发布冻结修订。通用ConfigRevisionService随P1首个选择组/配方发布交付，P2餐牌复用，不能等餐牌阶段才补发布基础。每个切片同时交付Controller、Service/Impl、Mapper、DTO及typed本地/远程链，不按技术层先批量生成空类。

P1→P2为配置主线；P3内部先交付库存数量/估值及原预占能力，再联通报价与正式受理；P4仅执行已冻结需求，不承担P3的前置实现。餐饮库存执行计划须在订单上冻结，制作已耗的叶子不能在交付时再次issue；旧零售仍沿原交付出库路径。P5必须在P2/P3及实际库存就绪后才能启用成交，P6每阶段先补事实指标，最后联验，不能最后才补事件。

## §6 取舍和待核定边界

推荐继续扩展现有商品/订单体系及餐饮配置，不另建独立商品、价格或库存账。相比“每个渠道复制商品/SKU”，配置引用更容易保持实存一致；相比“所有渠道共用全局配料再在前端隐藏”，餐牌条目显式REPLACE可以由服务端和第三方同步共同校验。代价是报价、库存和发布合同需要做实，不能只加餐饮配置表。

早餐/午餐/晚餐的具体默认时间可按门店配置，不在程序写死。默认在开始制作/释放制作时触发耗用，已制作退款不返料；实际库存提供方需确认在制品及分批扣料合同。首次外送provider及账号协议、允许原料单位和估值精度、实际盘点/领耗数据来源在对应阶段核定，不阻塞基础配置设计，但阻止相关能力被标可营业。

P0设计真源、旧菜品投影、9张PLANNED表、13个目标管理API及报价/库存输入输出定义已对齐。新增DDL及新增13个目标API尚未执行，合同实现状态为PENDING；CAT-01A既有只读合同继续保留。不能把设计收口解释为全部P0提供方合同或P1业务交付。
