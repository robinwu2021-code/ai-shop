## 1. 先纠正一条：我在 PRD AC-5 写错了

PRD 第 3.1 节 AC-5 写的是：

> 线下支付订单**不参与**平台优惠券与积分抵扣。

**积分那一半是错的。** 按 ADR-006 已定的成本模型重推一遍：

> 积分成本由**商家**承担 —— 用户抵扣的金额，在商家收入结算时扣除。
> 平台从不垫付、从不承担兑付。

于是：

| | 买家付给谁 | 平台要做的资金动作 |
|---|---|---|
| **线上支付 + 积分抵 30** | 付平台 70 | 结算时按 100 算商家应得，再扣 30 —— **平台要做一次账面动作** |
| **线下支付 + 积分抵 30** | 当面付商家 70 | **什么都不用做** —— 商家自己少收 30 就是抵扣本身 |

**线下支付用积分抵扣不但可行，而且比线上更简单。** 我上一版把它和优惠券一起划掉了，
是因为只看了「平台没有资金流可扣」，没有分清**这笔钱本来就不该平台出**。

### 1.1 优惠券要按出资方拆开，不能一刀切

券有平台出资与商家出资两种，而 `ord_sub_order` 上**早就分了两列**
（`discount_platform` / `discount_merchant`，注释写着「合成一列的话分账无法判断该扣谁的钱」）。
所以这个区分是现成的：

| 券类型 | 线下支付能不能用 | 理由 |
|---|---|---|
| **商家券** | ✅ 能 | 商家自己少收，与积分同理，平台不介入 |
| **平台券** | ❌ 不能 | 平台要把补贴的钱给商家，而线下**没有资金流可补**。硬发就是平台白送且无处对账 |

### 1.2 发放照常

ADR-006 定的发放时机是**订单完成时**，不是支付时（防「下单→拿分→花掉→退款」的套利）。
线下单一样有「完成」这一刻（履约完成），成本一样在商家。**所以线下单照常发积分**，无需特殊处理。

### 1.3 由此产生一条界面要求

线下支付 + 抵扣之后，商家该收的是**抵扣后的金额**。
b-app 的「确认收款」页必须**大字显示应收金额**，并标出「已抵扣 X 元」——
否则商家按商品原价收钱，买家凭什么？这是唯一一处「抵扣」会离开系统、
落到人当面执行的地方，界面说不清就会变成纠纷。

## 2. 主问题：积分按什么维度设

### 2.1 ADR-006 已经定了一半

> | 发放维度 | **按商品配置**，不同商品不同积分（生鲜 30 / 家电清洗 500 / 储值卡 0） |
> | 未配置商品 | 按成交额比例兜底（`defaultEarnRatio`，现为千分之一） |

即已定的是**两层**：商品配置 + 平台兜底比例。落库也做完了（`prd_goods.points_config`）。

### 2.2 但实测数据说这一层不成立

线上现状：

```
商品总数          199 件
配了积分的商品      0 件   ← 0%
积分账户            0 条
积分流水            0 条
```

**「按商品配置」的实际填写率是 0%。** 而这不是孤例 —— 今天一天之内在同一个项目里
撞到第四次同样的形态：

| 能力 | 设计上的配置层级 | 实际 |
|---|---|---|
| 商品规格 | 商家逐商品填 | 198 件里 197 件靠兜底，全叫「规格」 |
| 标准品库 | 运营逐条启用 | 导入 297 条，启用 0 条（因为只能一条条点） |
| 预售 | 商家逐商品设 | 接口有、界面无、0 使用 |
| **积分** | **商家逐商品配** | **199 件里 0 件** |

**结论不是「大家都很懒」，而是：要求每个商家对每件商品做一次决定的配置项，不会被填。**
今天修规格时验证了反面 —— 运营配 30 个类目是**做得到**的事（现在 30/30 全配齐），
而商家配 199 件商品不是。**同样叫「配置」，这两件事的可完成性差一个量级。**

### 2.3 方案选型

| 方案 | 做法 | 结论 |
|---|---|---|
| **A. 平台统一一个比例** | 全网一个 `earnPerMinor` | ❌ 太钝。生鲜与家电清洗的毛利差十倍，同一个比例要么让生鲜亏、要么让服务白送 |
| **B. 只按商品** | 维持现状 | ❌ **已被实测证伪**，填写率 0% |
| **C. 三层：平台兜底 → 类目 → 商品**（推荐） | 新增**类目**层作为主力，商品层降级为例外 | ✅ **采用** |

**采用 C，优先级：商品 > 类目 > 平台兜底。**

| 层 | 谁配 | 定位 | 覆盖面 |
|---|---|---|---|
| **平台兜底** | 平台（已有 `earnPerMinor`=0.01） | 最后的网，永远有值 | 100% |
| **类目**（新增） | **运营** | **主力**。配一次，全网该类目的商品立刻生效 | 目标 100%（今天 30/30 类目已配齐规格，证明可完成） |
| **商品** | 商家（已有 `points_config`） | **例外**。储值卡 0 分、引流款 0 分、高毛利款加倍 | 预期个位数百分比，且**不指望它** |

### 2.4 为什么类目这一层是对的

- **它是唯一"配一次覆盖多数"的层级。** 平台层太钝，商品层太细，类目层的粒度正好匹配
  「同一类商品毛利结构相近」这个真实规律 —— 生鲜、服务、储值卡的差别正是类目差别。
- **配置方是运营不是商家。** 商家配 199 件是 199 个决定；运营配 30 个类目是 30 个决定，
  而且做完惠及全部商家，包括明天才入驻的那些。
- **类目规格的基础设施刚做完，可以直接照搬。** `prd_category_spec` 那套
  （类目 → 配置 → 商家可覆盖）就是同构的问题，包括运营端的编辑页形态。
- **它天然解决「新商家开箱即用」**：新商家建一件生鲜商品，不做任何配置就有正确的积分，
  而不是掉到千分之一的兜底上。

### 2.5 需要防的一件事：三层叠加不能算错

优先级必须是**取一个值，不是相加**：

```
商品配了 → 用商品的（哪怕配的是 0）
否则类目配了 → 用类目的
否则 → 平台兜底比例
```

**「商品配了 0」必须与「商品没配」区分开** —— 储值卡配 0 分是一个明确的决定，
不能因为值是 0 就掉到类目层去拿一个非 0 的值。这是这类三层配置最常见的 bug，
`points_config` 是 JSON 列，要用「键存不存在」判，不能用「值是不是 0」判。

## 3. 订单侧：积分与订单状态的关系

这一节把 ADR-006 的规则与订单状态机对齐，并补上线下支付这一支。

| 时刻 | 动作 | 说明 |
|---|---|---|
| 下单 | **冻结**抵扣的积分 | 不是扣减 —— 订单可能不付款 |
| 支付成功 / **线下确认收款** | 抵扣转实扣 | 两条路都走 `markPaid`，积分处理**天然共用**（TDD-线下支付 §2.3 ②） |
| 订单取消 / 超时关单 | 解冻 | 线下单超时未确认收款走同一条 |
| **订单完成** | **发放**积分 | 不是支付时（防套利，ADR-006 §3.1） |
| 售后退款 | 回收已发 + 退回已抵 | `ord_after_sale.points_offset_minor` 已有此列 |

**线下支付不需要为积分写任何新分支** —— 这是选「复用 `markPaid`」而不是「独立订单类型」
换来的直接好处（见 TDD-线下支付 §3.1）。

## 4. 模块设计

**新增**

| 模块 | 路径 | 职责 |
|---|---|---|
| `prd_category_points` | 迁移 | 类目 → 积分规则。与 `prd_category_spec` 同构 |
| `PointsRuleResolver` | `shop-settle/…/impl/` | 三层取值：商品 → 类目 → 兜底。**唯一入口**，禁止别处重复实现优先级 |

**修改**

| 模块 | 变更 |
|---|---|
| `PointsServiceImpl` | 发放时调 `PointsRuleResolver` 取规则，不再直接读 `points_config` |
| `OrderServiceImpl#create` | 平台券 × 线下支付 的组合校验（下单时拒绝，不是事后回滚） |
| ops-web | 类目积分配置页（照搬「类目 × 规格」那一页的形态） |
| b-app | 确认收款页显示**应收金额**与「已抵扣 X 元」 |

**不动**：`PointsConfig` 的三个旋钮（`perMinor` / `maxDeductRatio` / `earnPerMinor`）、
积分账户与流水、抵扣上限与顺序、发放时机。

## 5. 测试策略

1. 三层优先级：只配平台 / 配了类目 / 配了商品，各取到正确的值。
2. **商品配 0 分**不掉到类目层（2.5 那个坑）。
3. 线下支付 + 积分抵扣：下单成功，`pay_amount` 是抵扣后的金额，确认收款后积分实扣。
4. 线下支付 + **平台券**：下单被拒。
5. 线下支付 + **商家券**：下单成功。
6. 线下单完成后**照常发积分**，金额与线上单一致。
7. 线下单超时关单：冻结的积分被解冻，余额复原。
8. 回归：`PointsDeductFlowTest` 现有 7 条红，本次**不得变多**（它们红在积分域从未启用，不是本方案引入）。

## 6. 风险

| 风险 | 应对 |
|---|---|
| **积分域从未在生产跑过**（账户 0、流水 0） | 本方案不负责启用它。**先把发放维度定对**，启用是另一个决定 —— 一旦发出去就收不回来 |
| 三层优先级在多处各实现一遍 | `PointsRuleResolver` 作为唯一入口，加守卫测试禁止别处直接读 `points_config` |
| 类目积分配了但商家不知道 | b-app 建品页显示「本类目默认 X 分」，让商家看得见自己继承了什么 |
| 线下收款金额与应收不符 | 界面大字显示应收；平台不介入对账（PRD 已定边界） |
