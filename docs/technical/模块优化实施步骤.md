# 模块优化实施步骤

> 2026-08-09 · 承接[后端模块规划-理想方案](./后端模块规划-理想方案.md)与[安全整改方案](./安全整改方案-认证与账号体系.md)。
> 结论先行：**在现状上演进**。321 个 Java 文件、58 张表、29 个测试、8 条 ArchUnit 规则、
> 17 个 SPI Port 全部保留，理想方案里没有一条是"必须重写才能做"的。

---

## 零、贯穿全程的一条纪律

**每一步只做一种改动：要么改包名，要么挪目录，绝不同时做。**

原因很实际：包名变了，`git` 看到的是"删一个文件、加一个文件"；目录挪了，看到的也是这个。
两件事混在一次提交里，**review 时无法区分"只是搬家"和"顺手改了逻辑"**，
出问题也没法二分定位。分开做，每一步的 diff 都能一眼判断是否安全。

## 一、现状盘点（逐个数过）

| 模块 | Java 文件 | 实际装了什么 |
|---|---:|---|
| `shop-common` | 34 | 横切基础设施 |
| `shop-spi` | 19 | 17 个 Port + DTO + Event |
| `shop-svc-user` | 49 | **三个域**：user · merchant · community |
| `shop-svc-product` | 33 | 商品 |
| `shop-svc-trade` | 29 | 交易 |
| `shop-svc-marketing` | 28 | 营销 |
| `shop-svc-settle` | 27 | 结算 + `gateway/`（支付通道） |
| `shop-svc-platform` | 23 | 运营 |
| `shop-svc-fulfillment` | 12 | 履约 |
| `shop-svc-message` | 9 | 消息 |
| `shop-app` | 58 | 23 个 Controller + config + 装配 |

**关键事实：包名不带模块名。**

```
shop-svc-trade/src/main/java/ai/neargo/shop/trade/...
shop-svc-product/src/main/java/ai/neargo/shop/product/...
```

包路径是 `ai.neargo.shop.<域>`。所以把这些 svc 并进一个 `shop-core`，
是**移动目录 + 删 pom**，包名不变、import 一行不改。

**唯一的例外**：商家域嵌在用户域下——`shop.user.merchant.entity.MchEntity` 等 6 个实体，
外加 `MerchantServiceImpl` / `MerchantStoreServiceImpl` / `MerchantStaffServiceImpl` /
`MerchantPaymentServiceImpl` / `StoreAdminServiceImpl`。抽出去必须改包名，**影响 29 个文件**
（其中 8 个是 `scenario/` 场景测试，正好当验收网）。

## 二、手机号作为唯一识别标识

采纳。这个选择比"unionid 优先"简单得多，且直接命中"引导小程序用户去 App"这个场景。
但它把复杂度从**技术**挪到了**产品**，有四件事必须先认下来。

### 2.1 表结构不变，只是解析优先级变了

[安全整改方案](./安全整改方案-认证与账号体系.md) §6.3 的 `usr_account` + `usr_identity`
拆分**照做不误**——手机号做唯一标识，并不意味着回到"一个账号一个手机号列"。
一个人仍然有多条凭证（小程序 openid、App openid、Apple sub），只是**认人时以 PHONE 为准**：

```
① PHONE       ── 命中即认定  ← 唯一权威标识
② 本次 openid / apple_sub ── 命中即认定（同应用回访，免去重复授权）
③ 全部未命中  ── 走注册流程，强制获取手机号
```

`WX_UNIONID` **仍然存**，但降级为辅助：不用它认人，用它在手机号缺失或换号时做修复线索。
存它的边际成本是一行数据，不存则将来想补要回填历史用户。

### 2.2 手机号必须在注册时强制拿到（这是产品决策）

技术上小程序有两种登录：`wx.login` 是**静默**的，只给 openid；
拿手机号必须走 `getPhoneNumber`，**要用户主动点一次按钮**。

选了手机号做唯一标识，就等于规定：**没有手机号 = 没有账号**。
好处是不会再有"孤儿账号"，代价是首次进入多一次授权点击，**转化率会有损失**。
这是产品要认的账，不是技术能绕开的——绕开就等于允许无手机号账号存在，
而那正是账号分裂的来源。

> 缓和做法：允许**静默浏览**（无账号可看商品、看门店），只在"加购 / 下单 / 领券"
> 这类需要身份的动作上触发一次授权。用户此时目的明确，转化损失小得多。

### 2.3 Apple 登录拿不到手机号——必须串接绑定

iOS 上架规则：提供第三方登录就**必须**提供 Apple 登录。而 Apple 只给一个匿名 `sub`
（用户还能选择隐藏邮箱），**永远拿不到手机号**。

所以 App 的流程必须是：Apple 登录成功 → 若该 `sub` 未关联任何账号 →
**强制进入手机号绑定页**，绑完才算注册完成。不能跳过，跳过就产生无手机号账号。

### 2.4 号码二次放号：唯一真正的风险

运营商会把停用手机号**重新发放**给新用户。若手机号是唯一标识，
新机主用该号登录会**直接继承前任的账号**——订单、地址、积分、卡包，全部可见。

这不是理论风险，是行业里持续发生的事故。三道缓解，建议至少做前两条：

| 措施 | 做法 |
|---|---|
| **长期不活跃提高门槛** | 账号超过 N 个月无登录，再次登录时除 OTP 外追加一项校验（原设备 openid 命中、或最近订单尾号） |
| **换绑留痕 + 通知** | 手机号变更写审计日志，并向**原号码**发一条通知短信 |
| 敏感操作二次校验 | 查看历史订单详情、使用余额/积分时再验一次 |

`WX_OPENID_*` 在这里体现价值：同一台设备的 openid 没变、手机号却变了，
是"换号"；openid 也变了，更可能是"换人"。**这就是 §2.1 里要保留 openid 凭证的理由。**

## 三、实施步骤

八步，前四步不动业务逻辑，后四步逐步搬运。每步都有独立验收，可单独发布、单独回滚。

### S1 · 补齐 ArchUnit 规则（**必须在合并之前**）

现在 svc 之间不能互相依赖，是 **Maven 强制**的——编译不过。
合并成 `shop-core` 后这道屏障消失，边界只剩 ArchUnit。
所以规则要**先在 11 模块状态下补齐并跑绿**，再动结构，中间不能有一刻是无约束的。

- 把 8 条扩到规划里的 11 条，核心是"`..shop.<域A>..` 不得依赖 `..shop.<域B>..`，跨域一律经 SPI Port"
- 此时规则应当**天然全绿**（Maven 已经保证了），若有红说明现状本就有违规，先修
- **验收**：11 条规则全绿；故意加一行跨域 import，测试必须变红（否则规则是摆设）

> 最后这条反向验证不能省。只跑绿不能证明规则有效——它可能什么都没匹配到。

### S2 · 用户身份统一（对应安全批二）

- 建 `usr_identity`，`UNIQUE(identity_type, identity_value)`
- 迁移：`usr_account` 的 phone / openid / apple_sub 各拆成一行
- `AuthServiceImpl.resolveIdentity` 改为返回**凭证集合**；`findOrCreate` 按 §2.1 优先级解析
- `shop-channel` 尚不存在，先把 `code2Session`、微信手机号解密、Apple 验签落在
  `shop-svc-user/channel/` 下，**S6 时整体搬走**（现在就建新工程会打断步骤节奏）
- 迁移验证通过后再删 `usr_account` 的四个凭证列
- **验收**：同一手机号从小程序与 App 两条路径登录，`user_no` 相同；
  Apple 登录未绑手机号时接口返回"需绑定"而非发令牌

### S3 · 商家域抽出 → `shop-merchant`（**唯一改包名的一步**）

```
shop.user.merchant.entity.*  →  shop.merchant.entity.*
shop.user.service.Merchant*  →  shop.merchant.service.*
shop.user.service.StoreAdminService →  shop.merchant.service.*
```

- 新建 `shop-merchant` 工程，依赖 `shop-base`（= common + spi）
- 用 IDE 的 **Move Class** 重构（自动更新 import），**不要手工改**——29 个文件手工改必漏
- `MerchantPortImpl` 一并移过去；`shop-svc-user` 对商家的调用改为**经 SPI Port**
- **此步不合并任何模块**，模块数 11 → 12（临时增加，正常）
- **验收**：8 个 `scenario/` 场景测试全绿——它们大量引用 `Mch*` 实体，是天然的回归网

> 为什么放在合并之前：此刻 Maven 还在强制边界，抽错了**编译期就报**。
> 合并之后再抽，错误要等 ArchUnit 跑到才发现，定位更慢。

### S4 · 社区域归位

`shop.user.community.*`（`CmtCommunity` / `CmtPickupPoint`，9 个文件引用）
从 `shop-svc-user` 提到与其他域平级：`shop.community.*`。同样用 Move Class。

- **验收**：编译通过 + 全量测试绿

### S5 · 八个 svc 合并 → `shop-core`（纯目录移动）

```
shop-svc-{user,product,trade,fulfillment,marketing,message,platform}/src/main/java/ai/neargo/shop/*
        ↓  全部移入
shop-core/src/main/java/ai/neargo/shop/
```

- `shop-svc-settle` **不并**，S6 单独处理
- 删除 7 个 pom，根 pom 的 `<modules>` 相应删减
- 合并各 pom 的依赖到 `shop-core/pom.xml`，**逐条核对**——这是本步唯一的实质风险点：
  原先靠依赖传递拿到的包，合并后可能缺声明
- 资源文件（`mapper/*.xml` 若有）同步合并，注意**同名文件覆盖**
- **验收**：全量编译 + 29 个测试 + 11 条 ArchUnit 规则全绿。
  规则绿是关键——它证明 Maven 屏障移除后边界仍然成立

### S6 · 拆出 `shop-settle` 与 `shop-channel`

- `shop-settle`：由 `shop-svc-settle` 改名而来，**但先把 `settle/gateway/` 移出**
- `shop-channel`：装 `gateway/`（PayGateway 四个实现）+ S2 暂存在 user 下的登录凭证适配
  + 推送 / 上传 / 分享
- 理由：支付通道是**外部适配**不是结算逻辑，且部署图里 ops 只需要 channel 的 media 部分，
  混在 settle 里没法按需装配
- **验收**：`MerchantPaymentFlowTest` / `M7SettleFlowTest` 绿；
  ArchUnit 补一条"领域层不得直接依赖 `..channel..` 的具体实现"

至此模块为 **6 个**：`shop-base`(common+spi 合并) · `shop-core` · `shop-merchant` ·
`shop-settle` · `shop-channel` · `shop-app`。

### S7 · 垂直切片：Controller 按域搬进业务工程

现在 23 个 Controller 全在 `shop-app/portal/{mp,biz,ops,callback,common}`。
搬成"每个域自带三端 API 面"：

```
shop-core/.../trade/api/{mp,biz,ops}/     ← MpTradeController · BizOrderController
shop-merchant/.../api/{biz,ops}/          ← BizMerchantController · 运营端进件审核
shop-settle/.../api/{biz,ops}/            ← BizSettleController
shop-app/                                 ← 只剩 config + 装配 + Application
```

- `OpsController` 一个类 15 个端点，**必须先按域拆开**再搬，否则它会绑死所有工程
- 拆 `OpsController` 时同步做[安全方案](./安全整改方案-认证与账号体系.md) §7.4 的权限码补齐——
  码本来就该定义在各自域里，两件事一起做只改一遍
- **验收**：所有 e2e 与 scenario 测试绿；`shop-app` 里 Controller 数量为 0

### S8 · 三种起法落地（对应[部署拓扑](./diagrams/deploy-topology.svg)）

同一个 jar，按 `--spring.profiles.active` 起 api / ops / worker：

- 三条 `SecurityFilterChain` 与对应 portal 按 profile **条件装配**
  （`@Profile("api")` 装 mp+biz 链，`@Profile("ops")` 只装 ops 链）
- `worker` profile 关 HTTP（`spring.main.web-application-type=none`），
  独占定时任务与 Outbox 派发；api / ops 上的定时任务**必须关掉**，否则多实例重复执行
- **验收**：以 `ops` profile 启动时，打 `/mp/**` 返回 404（**不是 401**——
  路由压根不存在，才叫真隔离）

## 四、顺序与并行

```
安全批一（密码/OTP）──── 独立，随时可发
                          │
S1 ArchUnit 补齐 ─────────┼──→ S3 商家抽出 ──→ S4 社区归位 ──→ S5 合并 ──→ S6 拆 settle/channel ──→ S7 垂直切片 ──→ S8 三起法
                          │                                                                              ↑
S2 身份统一（安全批二）────┴──────────────────────────────────────────────────────────────────────────────┘
                                                                          安全批三 B 端授权 ──────────────┘
```

- **S1 是所有结构改动的闸门**，不能跳
- **S2 与 S3–S6 可并行**：S2 动的是 `AuthServiceImpl` 与 usr_ 表，S3 起动的是 mch_ 与包结构，
  重叠只在 `shop-svc-user` 一个工程内，用分支隔离即可
- **安全批三（B 端授权接入）等 S7**：权限码定义要跟着 Controller 走，先搬再加码，不然加两遍

## 五、风险与回滚

| 步 | 主要风险 | 回滚 |
|---|---|---|
| S2 | 数据迁移不可逆 | 迁移**只加不删**（新表建好、旧列保留），验证通过后另发一版删列 |
| S3 | Move Class 漏改 | 编译期即报，无运行期风险 |
| S5 | pom 依赖传递丢失 | 纯结构变更，`git revert` 即可；**发布前必须全量编译** |
| S7 | Controller 路径变化 | 搬迁时**不改 `@RequestMapping` 路径**，前端零感知；改路径另开一次 |
| S8 | 定时任务重复执行 | 先在预发以三 profile 各起一份，观察一个完整结算周期 |

**S7 那条要特别守住**：搬类和改 URL 是两件事，一起做的话线上出问题分不清是搬错了还是路由错了。

## 六、一个必须由你验证的前提

我这台机器**没有 JDK**，全文所有结论都来自静态阅读（文件数、包路径、引用计数均逐个数过，
可复核）。S5 的 pom 依赖合并是唯一静态看不出问题的地方——依赖传递要编译才知道缺没缺。
每一步都请在本地跑一次全量 `mvn clean test` 再合入。
