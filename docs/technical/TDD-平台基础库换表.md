## 一句话

平台基础库的四个模块（登录与账号、商户与门店、门店设置与设备、员工与权限）共用一个句柄，只能一起换库。
换库那一步本身只是一条配置（`shop.modules.platform.datasource`），难的是之前：平台句柄下的每个实体、每条手写 SQL
都要和新库 `n_platform` 的表对得上，别的模块也不能再直接查这些表。本文件把这些事排成顺序，并用一条守卫把“还差什么”变成只准变短的清单。

## 验收标准

- W1：Given 平台句柄下的实体 When 与新库的建表语句比对 Then 差异都在 `known-platform-schema-gaps.txt` 里；新增差异或已对齐未划掉都红。
- W2：Given 本机测试库按 `db/n_platform/V1` 与 `V2` 建 When 执行 Then 39 张表全部建成（2026-11-26 在 MySQL 9.7.4 上验证）。
- W3（最后一步）：Given 平台模块绑到 `n_platform` When 跑登录、商户、门店、员工的测试 Then 全部通过。

## §1 现状（2026-11-26 盘点）

### 1.1 平台句柄下的表

| 类 | 数量 | 说明 |
|---|---:|---|
| 同名、实体列都对得上 | 9 张实体表 | 账号、凭证、人档、人员、任职、岗位、资质、B 端账号等 |
| 同名、实体有而新表没有的列 | 3 张 | 主体（评分、销量等 8 列，设计说是派生数据不放主体上）、角色（权限列表，设计改成角色权限码一行一条）、门店（推荐位） |
| 改名或并入 | 8 张实体表 | 四张服务范围 → 门店服务范围；履约方式 → 门店履约方式；人员账号关联 → 人员；门店角色 → 授权；小程序会话 → C 端会话 |
| 新库没有 | 1 张 | 服务范围网格（评审 R2：建议补表） |
| 只经手写 SQL 访问 | 约 12 张 | 三端会话与登录日志（同名）、登录票据与 PIN 找回（→ 一次性票据）、品牌、管理空间（→ 集团）、管理授权（→ 授权）、收银员 PIN 与其策略（→ 主体）等；守卫看不到手写 SQL，靠本文件 §2 逐张列 |

`PlatformSchemaGapTest` 当前列出 26 项差异，就是 1.1 前四行。

### 1.2 本步顺带纠正的

C 端账号包（`ai.neargo.shop.user`）之前整包绑到了平台句柄，但包里的收货地址（门店交易库）、收藏与到店记录（会员营销库）、
测试身份与测试手机号（设计里没有）不属于平台基础库。现在只有账号、凭证、人档、小程序会话四个 Mapper 用标记绑平台句柄；
收货地址、收藏两个服务的事务改回主库，并在事务守卫里登记。

## §2 顺序

| 步 | 做什么 | 守卫怎么变 |
|---|---|---|
| 0 | 工作清单与测试库结构；纠正 C 端账号包的绑定 | 清单建立，26 项 |
| 1 | **清越界**：网关约 90 处直接查平台表改走平台句柄或端口；在调用方事务里给门店、主体加锁的两个端口（25 处使用）改成读一次 + 版本比对；人员与预约资源的同事务拆开；准入端口读主体改走端口 | 新增“平台表只能经平台句柄访问”的守卫；`MerchantSubdomainBoundaryTest` 的例外清空 |
| 2 | **一次改表并绑定**（发票的做法）：平台句柄下的实体与手写 SQL 直接改成 `n_platform` 的结构——同名表缺列、四张服务范围并一张、门店角色与管理授权并成授权表、小程序会话并进 C 端会话、票据并成一次性票据、管理空间改集团、PIN 策略并进主体；绑定 `shop.modules.platform.datasource`；测试里平台句柄指向按 V1+V2 建的库 | 差异清单清空；W3 |

第 1 步在旧库上照样能跑，可以单独提交。第 2 步之后 v2 只能跑在新库上：平台的表在主库里还是旧结构，不再兼容。
这符合这次的前提——不迁数据、不部署，v2 本来就是跑在新库上的。

第 2 步动手前要先定的：门店角色与管理授权合成一张之后的判定规则（评审 R5）；服务范围网格补不补表（R2）；
账号与人档状态的换值表。第 2 步里改表的顺序按依赖排，但整体是一次提交（中间状态既不能跑旧库也不能跑新库）。

### 第 1 步的工作清单（2026-11-26 基线）

`PlatformTableAccessTest` 扫出不在平台句柄下、却直接访问平台表的源文件，存在 `backend/known-platform-table-access.txt`，只准变短。
基线 37 个；随后修正了判定：注入平台 Mapper 本身走平台句柄（数据域照常），只读不会读错库，只有和非平台事务混用才算越界，
因此 8 个只读的文件不再计入，现为 29 个。下表是基线时的分布：

| 归属 | 文件数 | 例子 | 做法 |
|---|---:|---|---|
| 网关的桥接包 | 15 | 建店授权、门店适配、收款来源投影、收款商户回填与比对、支付侧会话校验、顾客报表、打印操作人、库存健康 | 改调平台句柄下的端口；联表的改成两次查询 |
| 从商户域拆出去的子域 | 13 | 预约资源 6、准入与保证金 2、收款商户 2、套餐 2、预约 Mapper 里联门店 | 联平台表的那几句改成经端口取门店、主体 |
| commerce 模块 | 3 | 门店开通的端 `mch_store_end_grant` | 2026-11-26 用户定：留在平台基础库，「平台商城库只有商品和订单，权益在平台基础库」。见下方「权益归属」 |
| shop-core | 4 | 运营账号与 API 钥匙、媒体引用、报名审核 | 运营账号属于平台基础库，接进平台句柄 |
| 其他 | 2 | 开发造数、归档 | 造数登记为例外；归档按表名动态处理，单独看 |

**权益归属（2026-11-26 用户定）。** 门店开通的端留在平台基础库；订阅与套餐留在平台商城库。
用户：「购买和开通本来就是两阶段的事情，购买后有可能还需要审核，有可能自动开通，属于两件事」。

commerce 现在把两件事写在一起，要改成两步（这是 commerce 的功能改动，单独一项，不并进清越界的批量改动）：

| 现在 | 改成 |
|---|---|
| 订阅变化时同一事务里替换开通段（`JdbcSubscriptionRepository`） | 订阅在平台商城库提交；开通作为第二步（自动或审核通过后）经平台句柄写开通段，按订阅期号与来源操作号可重复执行 |
| 退款、冻结、折算靠判定时联订阅周期生效 | 订阅侧这些变化产生“撤销或替换开通段”的动作，由开通这一步执行 |
| 端的判定锁订阅账户、联开通段与订阅周期（`JdbcEndAccessRepository`） | 只读开通段的状态；开通段上已有端编码，不再每次读端定义 |

行为变化：退款原来在判定那一刻生效，拆开后要等撤销执行完；两步之间允许的延迟待定。

**报表统一在报表模块（2026-11-26 用户定）。** 运营端的顾客浏览（经营主体、注册、品牌、会员）原在网关，一条 SQL 联平台基础库与会员表。
已搬到报表模块 `ai.neargo.shop.report.customer`，查询暂不变；会员模块对齐时，按报表库「只读各业务库」拆成分别读两库再拼——
会员与平台的分页联查要先在一边筛、再到另一边取。越界清单里这一项的路径随之改到报表模块。

只提到表名、并非访问的三类不算：数据域登记、会话存储的表名配置、已执行的历史迁移。

## §3 选型

| 方案 | 结论 |
|---|---|
| 逐表：每一步先用迁移把主库旧表改成新结构，旧库新库同构后再绑定 | ❌ 原先的方案。要改已上线主库的结构，而这次不迁数据、不部署，v2 只需要跑在新库上，兼顾旧库是多余的（2026-11-26 用户：「只要在新库上能跑就行」） |
| 先清越界，再一次改表并绑定 | ✅ 越界清完后，平台的表只经平台句柄访问，改表与绑定只影响这一处；做法与发票一致 |
| 双库并存：新代码写新库、旧代码读旧库，靠同步对齐 | ❌ 平台基础库是每个请求都读的身份与门店主数据，双写的不一致直接变成越权或拒绝 |

## §4 风险

| 风险 | 缓解 |
|---|---|
| 守卫只看实体，看不到手写 SQL | 第 1 步新增的守卫按表名扫手写 SQL：平台表只许出现在平台句柄下的类里；第 2 步前用按 V1+V2 建的真库跑一遍全部登录与商户测试 |
| 第 2 步是一次大提交 | 第 1 步把影响面收窄到平台句柄之内；差异清单逐项清空，每清一项都能单独编译 |
| 状态取值换值影响三端 | 随第 2 步一起改，接口文档与各端同步，同发票那次 |
