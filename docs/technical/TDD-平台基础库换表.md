## 一句话

平台基础库的四个模块（登录与账号、商户与门店、门店设置与设备、员工与权限）共用一个句柄，只能一起换库。
换库那一步本身只是一条配置（`shop.modules.platform.datasource`），难的是之前：平台句柄下的每个实体、每条手写 SQL
都要和新库 `n_platform` 的表对得上，别的模块也不能再直接查这些表。本文件把这些事排成顺序，并用一条守卫把“还差什么”变成只准变短的清单。

## 验收标准

- W1：Given 平台句柄下的实体 When 与新库的建表语句比对 Then 差异都在 `known-platform-schema-gaps.txt` 里；新增差异或已对齐未划掉都红。
- W2：Given 本机测试库按 `db/n_platform/V1` 与 `V2` 建 When 执行 Then 39 张表全部建成（2026-11-26 在 MySQL 9.7.4 上验证）。
- W3（最后一步）：Given 平台模块绑到 `n_platform` When 跑登录、商户、门店、员工的测试 Then 全部通过。

## §2 顺序

| 步 | 做什么 | 守卫怎么变 |
|---|---|---|
| 0 | 工作清单与测试库结构；纠正 C 端账号包的绑定 | 清单建立，26 项 |
| 1 | **清越界**：网关约 90 处直接查平台表改走平台句柄或端口；在调用方事务里给门店、主体加锁的两个端口（25 处使用）改成读一次 + 版本比对；人员与预约资源的同事务拆开；准入端口读主体改走端口 | 新增“平台表只能经平台句柄访问”的守卫；`MerchantSubdomainBoundaryTest` 的例外清空 |
| 2 | **一次改表并绑定**（发票的做法）：平台句柄下的实体与手写 SQL 直接改成 `n_platform` 的结构——同名表缺列、四张服务范围并一张、门店角色与管理授权并成授权表、小程序会话并进 C 端会话、票据并成一次性票据、管理空间改集团、PIN 策略并进主体；绑定 `shop.modules.platform.datasource`；测试里平台句柄指向按 V1+V2 建的库 | 差异清单清空；W3 |

第 1 步在旧库上照样能跑，可以单独提交。第 2 步之后 v2 只能跑在新库上：平台的表在主库里还是旧结构，不再兼容。
这符合这次的前提——不迁数据、不部署，v2 本来就是跑在新库上的。

第 2 步动手前要先定的：门店角色与管理授权合成一张之后的判定规则（评审 R5）；服务范围网格补不补表（R2）；
账号与人档状态的换值表。第 2 步里改表的顺序按依赖排，但整体是一次提交（中间状态既不能跑旧库也不能跑新库）。

**权益归属（2026-11-26 用户定）。** 门店开通的端留在平台基础库；门店订阅与行业套餐留在平台商城库。2026-11-27 确认主体套餐由商户域维护，商城只承接主体套餐的交易。
用户：「购买和开通本来就是两阶段的事情，购买后有可能还需要审核，有可能自动开通，属于两件事」。

commerce 现在把两件事写在一起，要改成两步（这是 commerce 的功能改动，单独一项，不并进清越界的批量改动）：

| 现在 | 改成 |
|---|---|
| 订阅变化时同一事务里替换开通段（`JdbcSubscriptionRepository`） | 订阅在平台商城库提交；开通作为第二步（自动或审核通过后）经平台句柄写开通段，按订阅期号与来源操作号可重复执行 |
| 退款、冻结、折算靠判定时联订阅周期生效 | 订阅侧这些变化产生“撤销或替换开通段”的动作，由开通这一步执行 |
| 端的判定锁订阅账户、联开通段与订阅周期（`JdbcEndAccessRepository`） | 只读开通段的状态；开通段上已有端编码，不再每次读端定义 |

行为变化：退款原来在判定那一刻生效，拆开后要等撤销执行完；两步之间允许的延迟待定。

**顾客浏览留在运营端门户（2026-11-26 用户定）。** 报表统一在报表模块，但运营端的顾客浏览（经营主体、注册、品牌、会员）
是实时查询，不是按日摄入的报表；曾按名字搬进报表模块，随即搬回门户。按 Java 规范 §7.1 它属于门户层的跨域组合：
改成分别调平台基础库的端口（主体、品牌、账号、门店）和会员的端口再拼。会员列表跨两库分页，要先在会员一侧筛出编号、再到平台一侧取。

**第二批的两处（2026-11-26 用户定）。** 旧的主体套餐购买（`merchant.plan` 的购买与退款）退役、并入商城，由商城会话处理，本分支只做标注；
预约资源的四个文件在门店交易库一侧，跨库给人员、主体与门店加锁的地方默认改成「读一次 + 版本比对」，随预约模块对齐时做。
本会话接下来聚焦账户、门店、商户等基础领域（差异清单 `known-platform-schema-gaps.txt`）。

只提到表名、并非访问的三类不算：数据域登记、会话存储的表名配置、已执行的历史迁移。

**Q7 授权合并逐条方案（2026-11-28 用户定：按方案）**

旧的两套：门店角色 `mch_store_role`（账号 × 门店 × 角色，无有效期、无来源、不可转授）；管理授权 `mch_management_grant`（集团下按范围授权限码，带有效期、实时复核来源、可转授）。新库并成 `mch_grant`（`grant_kind` = ROLE / PERMISSION）。

| # | 问题 | 方案 |
|---|---|---|
| 7.1 | 没有集团的主体，集团号填什么 | 迁移时按老板账号自动建一个默认集团（同一老板名下的主体共用一个），`owner_actor_no` 取老板账号；`mch_entity.management_no` 一并回填（规则同[连锁-交接](design/连锁-交接.md) §3.1：老板账号 `MCH:` 账号号 / 关联了 C 端用户的 `USER:` 用户号对上集团所有人）；对出多个集团的列出来人工定 |
| 7.2 | 保不保留 `USER:` 主体 | 保留（与 Q9「B 端会话允许 C 端用户作为主体」一致）；`actor_no` 注释改为「B 端账号号或 C 端用户号，带前缀」 |
| 7.3 | 门店角色是否受有效期、来源复核、集团暂停约束 | 三者都受，统一一套判定：迁移来的门店角色 `valid_from` = 原创建时间、`valid_to` 空；来源 `OWNER_ACCOUNT`，复核「门店仍属该主体、主体仍在该集团」，不复核当初分配的那个人；集团 `SUSPENDED` 时其下全部授权失效（设计注释原意） |
| 7.4 | 能否转授 | 角色授权（ROLE）不可转授（`delegatable = 0`）；权限码授权（PERMISSION）沿用现有规则 |
| 7.5 | `STORE` 范围的权限码是否进入 B 端门店上下文 | 进入：选中门店时的能力 = 该店角色的功能点 ∪ 该店 PERMISSION 授权的码；端上不再分两处取 |
| 7.6 | 去重 | 同一集团、被授权人、范围、类型、角色码或权限码只允许一条生效行；现有 `uk_2` 只是普通索引且不含 `grant_kind` / `role_code`，**要改表**：改成唯一键并加入这两列（ROLE 行权限码、PERMISSION 行角色码写空串哨兵） |
| 7.7 | 撤销是否级联 | 不做物理级联：转授出去的授权靠「实时复核来源」自然失效（父授权撤销 → 子授权复核不过）；门店角色没有子授权 |
| 7.8 | 两套码是否统一到功能点目录 | 统一登记到同一功能点目录，码值不改名（已写进授权行与角色）；`mch_role_point` 与 PERMISSION 授权共用目录校验 |

**E 服务范围：channel 的定义与方案（2026-11-28 整理；用户已定：存储用空串哨兵，主体层不做覆盖，改绑只看门店自己的行）**

旧库四张表加一张网格：门店范围项 `mch_service_area`、渠道收窄 `mch_channel_area`、渠道自提点 `mch_channel_pickup`、
主体覆盖小区 `mch_entity_community`、多边形网格 `mch_service_area_cell`。新库并成一张 `mch_store_service_area`，靠 `channel` 列区分。

*一、`channel` 的定义*

`channel` 回答「这一行范围项给哪种履约方式用」。值域取门店履约方式（`mch_store_fulfillment.channel`，`Fulfillments` 里的码）。

| `channel` | 含义 | 谁读它 | 能写什么 |
|---|---|---|---|
| 空（对全部方式） | 门店的**基础覆盖面** | 所有范围口径为「全部」（`scope_mode=ALL`）的履约方式；买家端可达、运营端覆盖、B 端范围页 | 纳入、排除、不限（`UNLIMITED`）、多边形，各层级都可以 |
| 某种方式 | 这种方式的**收窄子集**：只在它的范围口径为「部分」（`scope_mode=SUBSET`）时生效，别的方式看不见 | 只有这种方式的可达判定 | 只能是「纳入」，且必须在基础覆盖面里有同层级、同对象的行（是从基础面里挑出来的一份拷贝）；不能写排除、不限 |
| `NEIGHBOR_PICKUP` 且层级 `PICKUP_POINT` | 这家店的**邻里自提点**（`ref_code` = 自提点号） | 只有下单时「能选哪些自提点」的校验与 B 端自提设置；**不参与覆盖判定** | 只能是「纳入」 |

规则：
- **排除只写在基础面，对所有方式生效**（与现在一致：排除先判、优先于任何纳入）。
- **快递永远按基础面**，不出现在 `channel` 里（新库注释已写明）。
- 范围口径为「全部」的方式**只看基础面**：门店有某方式的收窄行，不会让别的方式变得可达。
- 收窄子集选空 = 这种方式哪里都到不了（与现在一致）。改回「全部」时删掉它的收窄行。
- 基础面的某一行删了，各方式里对应的收窄拷贝一起删（现在是 `mch_channel_area` 的引用一起删）。
- 多边形的收窄拷贝也要进网格，否则「部分」口径下的多边形永远命中不了。

存储上「空」怎么写（**11-28 用户定：A，空串哨兵**）：

| 做法 | 说明 |
|---|---|
| A（推荐） | 写空串 `''`，列改 `NOT NULL DEFAULT ''`。唯一键 `(tenant_no, store_no, channel, level, ref_code)` 直接拦得住重复；与 Q7.6 授权表「空串哨兵」同一做法。新库注释「空表示对本店所有方式生效」照旧成立 |
| B | 保留 `NULL`，另加生成列 `channel_key = IFNULL(channel,'')` 放进唯一键。多一列，读写都还按 `NULL` |

唯一键另外两条：`area_no` 全库唯一（审核单靠它指回本行）；`(tenant_no, store_no, channel, level, ref_code)` 唯一（一店一方式同一对象只一行，「不限」每店一行）。
新库里这两个名为 `uk_` 的现在都是普通索引，进 V2 补。

*二、各对象的边界*

| 对象 | 规则 |
|---|---|
| 集团 | 每个老板账号一个，按 Q7.1 自动建；免费名额按集团计数 |
| 品牌 | 建品牌、改品牌免费，不卡权益 |
| 门店入连锁 | 门店须持有有效的 `END_CHAIN`（买连锁版 Plan 或连锁端包；来源不限：付费、赠送、运营授予）。旧模型门店（`commerce_model` 不是 `STORE_V1`）不受新商业模型约束，照旧放行（与功能矩阵「旧模型门店跳过商业状态」同口径） |
| 门店退连锁 | 免费、当场生效；已付权益不退，用到到期 |
| 跨集团 | 门店所属主体必须与品牌同集团，否则按改挂靠处理，不在这里 |
| 权益到期 | 门店留在品牌里，不自动退出；之后再入连锁会被拦（宽限、只读等「连锁写操作停用」放到连锁功能接权益时做，本步只卡入连锁） |

*三、入连锁流程（取代 submit → decide）*

1. `POST /biz/stores/{s}/brand-changes/check`：原有事实与影响检查照旧；新增 `admission`：
   `{required:"END_CHAIN", basis:"ENTITLEMENT"|"LEGACY"|null, entitledUntil}`。门店没有有效权益时
   `blockers` 带 `CHAIN_ENTITLEMENT_REQUIRED`，`nextAction=BUY`（前端去商城）。退出（`toBrandNo=null`）不判权益。
2. `POST /biz/stores/{s}/brand-changes`：校验令牌、四个版本号、权限码（门店 `store.brand.change` + 两侧品牌 `brand.manage`）、
   影响检查、准入，**通过即改绑定**并返回 `{changeNo, storeNo, fromBrandNo, toBrandNo, bindingNo, applied:true, admissionBasis, blockers:[]}`；
   影响检查或准入不过时不落任何行，返回 `applied:false` 与 `blockers`。`changeNo` 仍由单据号 `BRAND_CHANGE` 生成，写进绑定行的 `change_no`。
   幂等照旧（统一防重，G5）；审计照旧（`BRAND_CHANGE_APPLIED`、两侧品牌 `BRAND_STORE_CHANGED`，G6）。
3. 删除：`GET /biz/management/brand-changes/{changeNo}`、`POST /biz/management/brand-changes/{changeNo}/decisions`；
   `check` 返回里的 `canDecide` 去掉；权限码 `brand.change.decide` 不再使用（保留登记，不删码值）。
4. 已开通储值的品牌：仍走储值期间的入退两阶段（`mch_brand_financial_change`），入连锁一侧同样先判准入。

准入只写在一处：`ChainAdmissionPolicy`（商户域），读平台库的 `mch_store_end_grant`
（`entitlement_code='END_CHAIN'`、状态 SCHEDULED / ACTIVE / ENDED、`start_at<=现在<end_at` 或 `end_at` 空、未删）与 `mch_store.commerce_model`。

| `mall_free_quota_limit`（只增不改） | `GLOBAL` / `ACCOUNT` 两级上限，带 `effective_from/to`，可预排未来的调整；领取时取当时生效的那行，特批优先 |
| `mall_free_offer_claim` | 领取记录：池、集团、门店、零元订单、`slot_no`、`active_slot_key`（唯一键兜底并发）、依据的上限行 |

领取：锁集团行 → 取生效上限 N → 数池内有效领取 M → `M<N` 才给，取最小空闲名额号 → 零元订单交付。
调低上限不收回已领的；调高后「待开通」门店可手动领取。计数身份 = 集团（即老板 `USER:` 身份），将来要按实名或执照合并只换计数键。


**建议顺序**：补唯一键 → F、票据、PIN 策略、会话日志、H、两列 → B → D → E → G → I 其余。
第 2 步仍是一次提交，等 Q1–Q10 定完才能整体合入。在那之前，能单独提交、在旧库上照样能跑的只有两类：
不改表的代码收敛（例如把 JSON 判权收到一个类里），以及顺带发现的缺陷——
`MerchantRoleServiceImpl.usageOf` 统计“预置角色被几人持有”时没有按商家过滤（2026-11-26 已修，`c67bb6f59`）。

## §3 选型

| 方案 | 结论 |
|---|---|
| 逐表：每一步先用迁移把主库旧表改成新结构，旧库新库同构后再绑定 | ❌ 原先的方案。要改已上线主库的结构，而这次不迁数据、不部署，v2 只需要跑在新库上，兼顾旧库是多余的（2026-11-26 用户：「只要在新库上能跑就行」） |
| 先清越界，再一次改表并绑定 | ✅ 越界清完后，平台的表只经平台句柄访问，改表与绑定只影响这一处；做法与发票一致 |
| 双库并存：新代码写新库、旧代码读旧库，靠同步对齐 | ❌ 平台基础库是每个请求都读的身份与门店主数据，双写的不一致直接变成越权或拒绝 |

## §4 风险

| 风险 | 缓解 |
|---|---|
| 守卫只看实体，看不到手写 SQL | 第 1 步新增的守卫按表名扫手写 SQL：平台表只许出现在平台句柄下的类里；第 2 步前用按 V1+V2 建的真库跑一遍全部登录与商户测试 |
| 第 2 步是一次大提交 | 第 1 步把影响面收窄到平台句柄之内；差异清单逐项清空，每清一项都能单独编译 |
| 状态取值换值影响三端 | 随第 2 步一起改，接口文档与各端同步，同发票那次 |
