## L3 逐个模块

### M1 运单登记

**入口**：消费 `OrderEvents.SubOrderShipped`（交易域发货事务提交后经 `sys_outbox` 投递）。

**步骤**：
1. 事件里 `fulfillment ≠ EXPRESS` → 忽略（自提、自送、虚拟不是物流的事）。
2. `ShipmentSourcePort.sourceOf(subOrderNo)` 取快照；返回空（子单不存在或没单号）→ WARN 并返回（不抛：重试也不会有单号）。
3. 承运商码校验：`lgs_carrier` 里没有 → 登记为 `CREATED` 但 `sub_state=FATAL`、`sub_error="未知承运商 xxx"`，运营端可见。
4. 定 `profile`：`wx != null` → `WX`（`bind_state=WAITING`），否则 `SELF`（`bind_state=NA`）。
5. 手机号：`phone-key` 配了 → 加密存 `receiver_phone_enc`；没配 → 只存后四位，启动时已 WARN。
6. `INSERT lgs_waybill`；**唯一键 (`biz_type`,`biz_ref`) 冲突 = 已登记**，直接返回（重复事件、重放都走到这里）。
7. 同一事务里发内部事件 `SubscribeRequested(shipmentNo)`。

**幂等**：靠唯一键，不靠查重（查重与插入之间有并发窗口）。

**测试要点**：重复事件只登记一次；非快递忽略；无微信键 → SELF；未知承运商可见；消融：去掉唯一键冲突处理 → 重复事件抛错。

### M2 渠道路由

```java
List<String> chain(Capability cap, String storeNo, String carrier)
    // by-store[storeNo] ?: by-carrier[carrier] ?: default，链尾补 stub
<T> Optional<T> pick(Capability cap, String channel, String carrier)
    // 启用 ∧ covers(carrier) ∧ available()；订阅额外要求同渠道 PushReceiver 也 available
```

- `covers(carrier)` 默认实现 = `lgs_carrier_code` 里有 (carrier, channel) 这一行（缓存 5 分钟；运营改编码后最多 5 分钟生效）。
- **启动自检**：链里写了没装的渠道名 → 启动 WARN 一次（不阻止启动：配置错不该让全站起不来）。
- 运营端「渠道总览」（M10）直接读这里的判定结果，不另写一套。

**测试要点**：圆通单走 yto、其余跳过 yto；门店路由覆盖承运商路由；yto 推送不可用 → 订阅也跳过；链全不可用 → 落到 stub。

### M3 订阅

**入口**：消费内部事件 `SubscribeRequested(shipmentNo)`；运营重放（M10）也发同一事件。

**步骤**：
1. 读运单；`sub_state=DONE` 且不是重放 → 返回（幂等）。
2. `chain = router.chain(SUBSCRIBE, storeNo, carrier)`；从上次失败的位置之后开始试（重放可指定渠道，直接用它）。
3. 对每个可用渠道：`subscriber.subscribe(SubscribeCmd)` →
   - `OK` → `sub_state=DONE`、`sub_channel`、`sub_ref`；返回；
   - `RETRYABLE` → **抛异常**（outbox 退避后重投，仍从这个渠道开始）；
   - `FATAL` → 记 `sub_error`（渠道名 + 码 + 原文），继续下一个。
4. 链走完 → `sub_state=FATAL`、ERROR 日志。

`SubscribeCmd`：`carrierCode`（渠道编码，经 `lgs_carrier_code` 转）、`waybillNo`、`phone`（解密后，可空）、`callbackUrl`（`callback-base + "/" + channel`）。

**为什么可重试失败抛异常而不是自己循环**：退避、上限、FAILED 终态 `sys_outbox` 都有；自己写一遍就是第二套重试。

**测试要点**：200 / 501 都是成功；600 / 601 / 700 换下一家；500 抛出；未知码按 FATAL；重放指定渠道。

### M4 回调（重点）

```
POST /callback/logistics/{channel}
  ↓ LogisticsCallbackController（只做分派，不含任何渠道逻辑）
  ↓ PushReceiver[channel]            —— 不存在 → 回 result:false + WARN（写不出 404，见下）
      verify(request)                 —— 验签
      parse(request) → PushBatch      —— 统一结构：渠道单号/承运商编码、节点[]、渠道状态、子状态、停止跟踪标志、承运商纠正
      ack(outcome) → HTTP 响应体      —— 各家要的回执不一样，由它决定
  ↓ PushIngestService.ingest(channel, PushBatch)
```

`PushIngestService.ingest`：
1. 经 `lgs_carrier_code` 把渠道编码转回我方承运商码；按 (carrier, waybillNo) 找运单。
2. 找不到 / `sub_channel ≠ channel` / 已 `CANCELLED` → WARN，返回「已处理」（**回执仍是成功**）。
3. 承运商纠正（快递100 `autoCheck=1`）→ 记 `carrier_corrected_from`，按新编码更新 `carrier`（留痕，不静默覆盖）。
4. 停止跟踪（快递100 `abort`）→ `sub_state=ENDED`。
5. 节点批量插入，唯一键 (`shipment_no`,`at`,`text_hash`) 冲突即丢弃（快递100 每次推**全量**）。
6. `WaybillStatus.advance(cur, mapped)`（M5）；有新节点或新状态 → `last_event_at=now`。
7. 子状态「投柜或驿站」→ `at_locker=1`（供 L-C-05）。
8. 调 M6 判一次换 token。
9. **同一事务**提交；事件经 outbox 发出（M9）。

**回执必须返回 `String`**（`produces=application/json`）：统一信封 `ApiResponseWrapper` 会把 `ai.neargo.shop` 下所有返回对象包成 `{code,msg,data}`，
对 `/callback/**` 没有排除规则 —— 现有寄件回调 `Kuaidi100CallbackController` 就是靠返回 `String` 绕开的。返回对象的话，快递100 收到的是被包过的 JSON，认不出成功，会重推。

**回执规则**（所有渠道一致）：

| 情况 | 回执 | 为什么 |
|---|---|---|
| 正常入库 | 成功 | — |
| 验签失败 | **成功** + WARN（记来源 IP、报文前 500 字） | 回失败对方会重推，而验签失败的报文重推也不会变对 |
| 找不到运单 / 渠道不符 | **成功** + WARN | 同上 |
| 入库异常 | **成功** + ERROR | 快递100 只重试 3 次（每 30 分钟一次），之后彻底不推；与其赌重试，不如记下来由补偿作业去问 |
| 渠道名不存在 | `{"result":false}` + WARN | 这是我们配置错；写不出 404：全局异常处理把任何异常转成 200 + 10500，域里又不许碰 Servlet 响应对象 |

**第一条真实推送**：每个渠道上线后的第一条推送，原文整条落 INFO（`[lgs-push-first]`），之后只记摘要 —— 文档与真实报文对不上时，这条日志就是改解析的依据。

**测试要点**：用快递100 文档样例报文跑通；验签失败仍回成功且不入库；全量重复推送节点不翻倍；签收推送触发事件且只一次；`abort` 后 `sub_state=ENDED`；纠正承运商留痕。消融：去掉 `sub_channel` 判断 → 旧渠道推送混入。

### M5 状态机

```java
static Transition advance(Status cur, Status incoming)
// 阶段序：CREATED < PICKED_UP < IN_TRANSIT < DELIVERING < DELIVERED
// incoming 序号 ≤ cur → 不变
// EXCEPTION：任一非终态可进入；之后来了更高阶段即恢复
// DELIVERED / CANCELLED 是终态，什么都改不了
```

`Transition` 带出「首次进入 PICKED_UP」「首次进入 DELIVERED」「进入 EXCEPTION」三个标志，M9 据此发事件；
`picked_up_at` / `signed_at` 只在首次进入时写。

**签收时间取渠道节点的时间**（不是收到推送的时刻）；节点没给时间才用此刻 —— 微信确认收货提醒要求签收时间晚于发货时间，宁晚勿早。

**测试要点**：DELIVERED 收到 IN_TRANSIT 不变；EXCEPTION 后 DELIVERING 恢复；签收时间只写一次。消融：允许降级 → 用例红（这正是线上缺陷）。

### M6 微信绑定

```
WxBindPolicy.ready(w) = profile==WX ∧ bind_state==WAITING ∧ wx_uploaded_at!=null ∧ status≥PICKED_UP
```

**两个触发点**（先后不定，两边都判）：M4 每次入库后；消费 `WxShippingUploaded` 后。`trigger=on-ship` 时去掉「≥ PICKED_UP」一条。

`WxBindExecutor`（经 outbox 异步执行）调 `trace_waybill`：入参 `openid`、`receiver_phone`（申通 / 中通等必填）、`waybill_id`、`delivery_id`（经 `lgs_carrier_code` 转微信码）、`trans_id`、`goods_info`（≤3 件）、`order_detail_path`。

| 返回 | 处理 |
|---|---|
| 成功 | `display_token`、`bind_state=DONE` |
| `9300559` 运单不存在 | 保持 `WAITING`，**不重试**；下一条推送会再触发 |
| `9300561` 手机号错 / `9300534` openid 与小程序不匹配 | `FATAL` + 原因 |
| 取 access_token 失败 / `9300513` 超限 / 网络 | 抛异常，outbox 退避 |

### M7 查询（重点）

四个读入口，一个服务。**C / B 端入口都在交易域的 controller 里**：先按当前登录人（或门店）查到子单，查不到一律 `10404`，再调 `LogisticsPort.track` —— 物流不认识用户，属主只能在交易域判。

| 入口 | surface | 读库 | 可能的外部调用 |
|---|---|---|---|
| `GET /mp/order/{orderNo}`（详情摘要） | MP / APP / H5 | ✅ | **无** |
| `GET /mp/order/{orderNo}/trace`（物流页） | 按 `X-Client` | ✅ | 微信 `query_trace`（WX 单、有 token、≥10 分钟、未终态） |
| `GET /biz/order/{subOrderNo}`、`/trace` | BIZ | ✅ | 仅当 `probe-surfaces` 对某渠道放行 BIZ 且 `refresh=true` |
| `GET /ops/shipments…` | OPS | ✅ | 无 |

`TrackService.track(q)`：
1. 按 (`biz_type`,`biz_ref`) 读运单与节点（节点按时间倒序，最新在上）。
2. 展示方式：surface = MP ∧ profile = WX ∧ 有 token → `wx-plugin`；否则 `self-map`。
3. 读时校正（只在物流页）：满足条件就调 `query_trace`，**超时 2 秒**，失败就用库里的；结果经 M5 推进（可能触发签收）；写 `wx_status_checked_at`。
4. `refresh=true`：按探测链问一次，只问对该 surface 放行的渠道；都不放行 → `refreshable=false`。
5. 返回 `TrackView`。

**缓存**：不另设缓存层 —— 库就是缓存，`wx_status_checked_at` 就是 10 分钟闸。读端点本身无状态。

**为什么详情页不校正**：详情页打开次数是物流页的数倍，在详情页校正等于把 10 分钟闸的意义打折；
而且微信 `query_trace` 每个用户每天约 100 次上限，详情页刷几次就可能用掉。

**测试要点**：10 分钟内第二次不调微信；终态不调；微信超时仍返回；SELF 单永不调微信；B 端默认 `refreshable=false`。

### M8 作业（重点）

**只剩一个**：`logistics-compensate`，`0 15 * * * *`（错开整点的交易域作业）。

| 字段 | 值 | 理由 |
|---|---|---|
| 扫描条件 | 非终态 ∧ `sub_state ∈ {DONE, ENDED}` ∧ `last_event_at < now − 24h`（从未有事件的用 `created_at`） | 只看「该有推送却没有」的；正常推送中的一单都不碰 |
| 每轮上限 | 200 | 防止一次故障后的积压把一轮拖到超时 |
| 探测 | 探测链（默认只有微信）；WX 单有 token 才问 | SELF 单、没 token 的计入「无法探测」 |
| 每单节流 | 同一单 6 小时内只探测一次 | 一单持续沉默时不每小时都问 |
| detail | `扫描 / 探测成功 / 推进 / 无法探测 / FATAL+outbox FAILED 合计` | 后两个长期应为 0，不为 0 就是缺陷或配置问题 |
| 锁 | `@SchedulerLock(name="logistics-compensate", lockAtMostFor=PT50M)` | 本仓库每个 `@Scheduled` 必须带锁（ArchitectureTest） |
| 注册 | `JobDeclaration` 放 `logisticsbridge`；**新作业注册后默认关**，上线后在作业表打开 | 2026-10-09 `logistics-trace` 就是注册了一直没开 |

**删除的作业**（批 2 / 3）：`logistics-trace`（被订阅推送取代）、`wx-waybill-bind`（被 M6 事件触发取代）、`wx-confirm-receive`（被 `WaybillSigned` 事件取代）。
删除时同时把作业表里那三行停用 —— 代码删了、作业表还开着，调度器会每轮报 HandlerNotFound。

**保留的作业**：`order-auto-receipt`（交易域，每天，时间驱动）、`wx-shipping-upload`（交易域，发货上报补报）。

### M9 事件出口

| 事件 | 何时 | 消费方 | 消费方做什么 |
|---|---|---|---|
| `WaybillProgressed(status=PICKED_UP/DELIVERING/EXCEPTION)` | 首次进入该阶段 | `NotificationConsumer` | **只对 SELF 单**发订阅消息（WX 单微信已经推了，再推就是重复打扰） |
| `WaybillSigned` | 首次进入 DELIVERED | `WxConfirmReceiveService`（WX 单）、`NotificationConsumer`（SELF 单） | 提醒确认收货 / 发「已签收」 |

全部经 `sys_outbox`，与状态变更同一事务写入 —— 状态改了事件一定发，事务回滚事件一定不发。

### M10 运营

**controller 留在主应用 `portal/ops`**（鉴权、判权都在那边），经 `LogisticsAdminPort` 调物流内的 `LogisticsAdminService`。

| 能力 | 端点 | 说明 |
|---|---|---|
| 运单列表 | `GET /ops/shipments` | 加筛选 `subState`、`bindState`、`subChannel` |
| 换单号 | `POST /ops/shipments/{no}/waybill` | 旧运单 `CANCELLED`，按新单号新登记一张并订阅 |
| 重放 | `POST /ops/shipments/{no}/replay` | `{action: SUBSCRIBE|WX_BIND, channel?}`；发事件后立即返回 |
| 渠道总览 | `GET /ops/logistics/channels` | 读 M2 的判定结果 |
| 承运商编码 | `GET/PUT /ops/fulfillment/carriers…` | 读写 `lgs_carrier_code` |

### M11 渠道适配

每家一个包，结构相同：

```
logistics-channel/<name>/
  <Name>Subscriber      TrackingSubscriber
  <Name>PushReceiver    PushReceiver
  <Name>StatusProbe     StatusProbe（有就写）
  <Name>Codes           状态映射 + 失败码分类（两张表，单测逐行覆盖）
  <Name>Client          HTTP、签名（HTTP/1.1；超时 5 秒；不记请求体）
```

#### 快递100

| 项 | 值（官方文档 2026-10-09 核对） |
|---|---|
| 订阅 | `POST https://poll.kuaidi100.com/poll`，`application/x-www-form-urlencoded`，`schema=json&param={…}` |
| `param` | `company`（快递100 编码）· `number` · `key` · `parameters.callbackurl` · `parameters.salt` · `parameters.resultv2=4`（带子状态，要用「投柜或驿站」）· `parameters.phone`（**顺丰、顺丰快运、中通必填**） |
| 订阅返回 | `200` 成功 · `501` 重复（仍在跟踪）= 成功 · `500` 可重试 · `600` / `601` key 或余额 · `700` / `701` / `702` 公司或单号不对 · `502` 敏感词 → 后六个都按不可重试 |
| 限制 | 同一公司 + 单号**每月最多订阅 4 次**；回调默认 HTTP，**HTTPS 要联系客服开通** |
| 推送 | `POST callbackurl`，表单 `param` + `sign`；`sign = upper(md5(param + salt))` |
| `param.status` | `polling` 跟踪中 · `shutdown` 结束（通常已签收）· `abort` 中止（3 天无记录 / 60 天无变化）· `updateall` 全量重推 |
| 承运商纠正 | `autoCheck=1` 时带 `comOld` / `comNew` |
| 节点 | `lastResult.data[]`：`context` `time` `ftime` `status` `areaCode` `areaName` |
| 回执 | `{"result":true,"returnCode":"200","message":"成功"}`；**`abort` 也要回成功** |
| 对方重试 | 回执失败 → 30 分钟后重推，共 3 次，之后不再推 |
| 状态码 | `1` 揽收（`103` 已揽收）· `0` 在途 · `5` 派件（`501` 投柜或驿站）· `3` 签收（`301`~`304`，含代签）· `2` 疑难（`201`~`210`）· `4` 退签 · `6` 退回 · `14` 拒签 · `7` 转投 · `8` 清关 |
| 凭据 | `shop.express.kuaidi100.key` / `salt`（与寄件同一账号） |

#### 圆通直连

报文、签名、编码以 [TDD-圆通物流直连 §3](design/TDD-圆通物流直连.md) 为真源（签名已与平台在线调试逐字比对一致）。本模块只定三件事：

- **凭据按能力分组**：订阅、查询、推送、下单各一组客户编码 / 密钥（`shop.logistics.channels.yto.<能力>.*`）。
- **IP 白名单**：只有生产机能调，实测只在生产机做；单测走样例报文。
- **推送接收**：推送服务待调试，`YtoPushReceiver.available()` 在推送密钥配上之前恒为 false —— 于是订阅也不可用，圆通单自动走快递100（M2）。

### M13 安全与隐私

| 项 | 做法 |
|---|---|
| 回调验签 | 每家 `PushReceiver.verify`；验签失败不入库 |

## L4 边界

- **快递100 没有「取消订阅」接口**：撤回发货、换单号后旧单号的推送会继续来，靠状态与 `sub_channel` 丢弃。
- **每月 4 次订阅上限**：重放前先看 `kd100_sub_month` / `kd100_sub_count`，超了直接告诉运营（30013），不去撞上限。
- **圆通推送报文未知**：M4 对圆通的部分以调通后的真实报文为准。
- **取件码**：渠道不给结构化字段，只原样显示节点文字（功能清单 L-C-05）。
