# 商户域设计方案评审

状态：评审稿（2026-11-26），待用户定结论。只评审，未改代码与库表设计。
起因：把商户域接到平台基础库时发现，`backend/shop-merchant` 一个模块、一个 Mapper 包里的表分属五个目标库。
对照的两边：代码是 v2 分支的 `shop-merchant`；设计是数据库设计方案（分支 `docs/db-split-plan`）的表名对照与各库说明。
关联：[TDD-商户门店与员工权限对齐平台基础库](TDD-商户门店与员工权限对齐平台基础库.md)

## 一、结论

1. **库表设计的归属大体是对的，乱的是代码模块。** `shop-merchant` 是按“凡是商户名下的东西”收的，表名也都叫 `mch_`；
   新设计按业务对象分库之后，它实际上装着五块互不相干的业务：商户与门店本身、预约资源与排班、支付商户与出款、
   保证金与欠款、套餐购买。设计把后四块分到别的库是合理的，代码应当跟着拆开。
2. **有 13 张表在设计里没有去向**，其中 8 张是申请、命令、日志这三类，按已定口径不该建表，但代码依赖它们；另 5 张要逐张定。
3. **有 6 处合并改变了模型，不是改名**，其中“门店角色并进授权”在每个请求都走的路径上，风险最高。
4. **拆开之后有 4 处同事务的写会跨库**，要先定谁先谁后。
5. **同一个东西建了两遍**：收款商户在商户域有一套（`mch_payment_merchant`），在支付域又有一套（`pay_merchant`）；设计已经合成一张，代码还没有。

## 二、这个模块里的 67 张表去了哪里

| 目标库 | 表数 | 是什么业务 | 设计的归属合不合理 |
|---|---:|---|---|
| 平台基础库 | 24 | 主体、门店、品牌、B 端账号、角色与授权、人员与任职、资质、服务范围、履约方式、收银员 PIN | 合理，这才是商户域本身 |
| 门店交易库 | 12 | 预约资源、时段容量、预约占用、班表、服务资格、门店展示分类 | 合理：资源和预约是交易的一部分，和订单同库才能同事务占用 |
| 平台商城库 | 7 | 主体买套餐：套餐定义、报价、购买单、线下付款的认领与凭证 | 合理：是商户向平台买东西 |
| 支付商户库 | 4 | 收款商户号、出款账户、准入规则、支付开通申请 | 合理；但和支付域自己的表重复，见第五节 |
| 账务结算库 | 4 | 保证金、欠款及其流水 | 归属合理，合并方式有疑问，见第四节 |
| 基础能力库 | 2 | 行业字典、授权码 | 合理：并入统一字典 |
| 平台服务库 | 1 | 违规处置 | 合理：并入风险事件 |
| 设计里没有 | 13 | 见第三节 | — |

表名前缀 `mch_` 在新设计里只留给平台基础库；另外四块换成 `rsv_`、`plan_`/`mall_`、`pay_`、`led_`，
看前缀就知道不是商户域的东西。这一点设计已经做对了。

## 三、设计里没有去向的 13 张表

| 表 | 是什么 | 按已定口径 | 问题 |
|---|---|---|---|
| `mch_entity_creation_request`、`mch_store_opening_request`、`mch_store_audit` | 建主体、开店、门店审核的申请 | 由审核与工单服务承担，业务库不建 | 代码里申请内容、审核、执行都在这三张表上，还没有接审核服务 |
| `mch_brand_change`、`mch_brand_financial_change`、`mch_brand_financial_activation` | 品牌变更及其对储值、卡券的影响确认 | 同上（审核服务也负责通过后的执行编排） | 同上；品牌财务变更有多步执行与重试 |
| `mch_management_command`、`mch_resource_command` | 管理操作、资源操作的幂等台账 | 防重是应用层的事，不建表 | 现在的重放靠它；去掉之后靠什么防重要写清 |
| `mch_staff_log`、`mch_schedule_change_log` | 员工操作日志、排班变更日志 | 统一审计 | 统一审计没有代码 |
| `mch_service_area_cell` | 服务范围展开成的地理网格，用来按坐标快速命中门店 | 没有口径 | 它是派生数据，但“这个坐标哪些店能送”每次下单都查；设计只说多边形靠数据库，没说网格。**要补表，或换成空间索引** |
| `mch_appointment_slot` | 预约时段 | 没有口径 | 看起来已被资源时段容量取代，要确认是不是旧表 |
| `mch_store_qrcode_print` | 门店码的打印批次 | 没有口径 | 新设计有门店码 `mch_store_code`，没有打印批次；可能应归打印 |

## 四、改变了模型的合并

| 合并 | 现在 | 合并后 | 风险 |
|---|---|---|---|
| `mch_store_role` ＋ `mch_management_grant` → `mch_grant` | 两套授权：门店角色（谁在哪家店是什么角色）和管理授权（谁在集团、品牌范围有什么权限） | 一张授权表，范围有集团、品牌、门店、主体、收款商户五种 | **高**。B 端每个请求都按门店角色解析身份；两套的生效规则、转授、到期各不相同。合成一张是对的方向，但要先写清统一后的判定规则 |
| `mch_operating_entity`、`mch_entity_profile_projection` → `mch_entity` | 经营主体、它的运营资料、它的资料投影各一张 | 一张主体表 | 中。投影是从支付侧同步来的只读副本，并进主表后“谁能写哪些列”要定 |
| `mch_management_space` → `mch_group` | 管理空间 | 商户集团 | 低，基本是改名；注意它“不等于经营主体” |
| 四张服务范围表 → `mch_store_service_area` | 按主体的小区、按履约方式的区域与自提点、通用服务范围各一张 | 一张，带包含与排除 | 中。命中查询跨这四张表，是下单路径 |
| `mch_personnel_account` → `mch_personnel` | 人员与账号的关联单独一张 | 人员上一个账号号 | 低；前提是一个人员最多关联一个账号，要核 |
| `mch_deposit`、`mch_deposit_txn`、`mch_debt`、`mch_debt_txn` → `led_voucher` | 保证金、欠款各有余额表和流水表 | 都记成凭证 | 中。余额从哪里读没有写：是账户余额表，还是每次从凭证算 |

另有两处是把一张小表收成主表上的列，问题不大：收银员 PIN 策略并进主体；门店设置类的并进门店或门店设置表。

## 五、同一个东西建了两遍

| 概念 | 商户域 | 支付域 | 设计 |
|---|---|---|---|
| 收款商户号 | `mch_payment_merchant` | `pay_merchant`、`pay_merchant_binding` | 一张 `pay_merchant` |
| 支付开通申请 | `mch_pay_service_application` | `pay_onboarding` | 一张 `pay_onboarding` |

代码里两边各有服务在写，中间靠同步保持一致（`paysync`、收款商户的回填与比对）。
按“一个业务对象只有一个归属库”，商户域这一侧应当删掉，改为调支付商户的接口。这是代码要做的收敛，设计已经给出了答案。

## 六、拆开之后会跨库的同事务写

| 现在同一个事务里 | 拆开后 | 建议 |
|---|---|---|
| 改人员（平台基础库）＋ 改他的服务资格、资源（门店交易库） | 两个库 | 人员是主数据，先提交；服务资格按人员编号引用，失败可重做 |
| 门店审核通过（平台基础库）＋ 建收款商户（支付商户库） | 两个库 | 开店是多步流程，本来就该由审核服务编排 |
| 主体准入（平台基础库）＋ 保证金、欠款（账务结算库） | 两个库 | 资金一侧为准，主体上只留状态的只读副本 |
| 主体（平台基础库）＋ 套餐购买（平台商城库） | 两个库 | 购买以商城订单为准，开通结果回写到门店开通的端 |

另外有两个端口是在**调用方的事务里**给门店、主体加锁的（交易、促销、美业、餐饮共 25 处在用）。
门店交易库的事务锁不到平台基础库的行，这 25 处要改成“读一次 + 版本号比对”。这是换库时工作量最大的一项。

## 七、建议的代码结构

| 现在在 `shop-merchant` 里的 | 去哪 |
|---|---|
| 主体、门店、品牌、账号、角色与授权、人员与任职、资质、服务范围、履约方式、PIN | 留在商户域，绑平台基础库 |
| 资源、时段、预约占用、班表、服务资格 | 拆成预约资源模块，和订单同在门店交易库 |
| 门店展示分类 | 并进商品模块 |
| 收款商户、支付开通申请、准入、出款账户 | 并进支付域的支付商户 |
| 保证金、欠款 | 并进结算 |
| 套餐定义、购买、线下付款 | 并进平台商城 |
| 行业字典、授权码 | 并进公共能力的统一字典 |
| 违规 | 并进风控 |

拆的顺序建议按依赖从少到多：字典与违规 → 套餐购买 → 保证金与欠款 → 支付商户（顺带消掉第五节的重复）→ 预约资源（牵涉最广，放最后）。
每拆一块，那一块就从“商户域里不属于平台基础库”的名单里消失；名单清空时，商户域才是一个可以整体换库的模块。

## 九、没核实的

- 表的归属取自表名对照与各库说明；每张表的字段没有逐列对过。
- “代码怎么用”取自对 Mapper 与 SQL 字符串的扫描；动态拼的 SQL 看不到。
- `mch_appointment_slot` 是否还在用、人员与账号是否一对一，没有查数据。
