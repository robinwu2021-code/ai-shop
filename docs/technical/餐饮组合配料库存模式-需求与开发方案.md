> **2026-10-29 口径更新**：餐饮本期只使用餐饮本地库存，与独立进销存联动另立任务。本文将进销存作为餐饮库存权威的旧设计及验收证据以[餐饮本地库存需求与切换方案](./餐饮本地库存-需求与切换方案.md)替代。商品与订单基础能力继续复用；历史订单与现有代码必须安全过渡。

## 1. 现状与目标

配料是商家主体下的业务配置，门店、餐牌及渠道引用已发布版本；商品与销售 SKU 沿用基础商品能力，价格、库存、订单由各自 owner 负责。当前渠道餐牌选项定价依赖销售 SKU，`DiningChannelModifierDemand` 遇到带销售 SKU 的组合时按单个成品扣库存，不展开其成员。现有配料发布流程也要求销售 SKU；不能简单去掉销售 SKU 解决计价问题。

目标：组合既能有独立销售价格，又可明确选择扣组合成品库存或扣成员物料库存；一个订单按冻结的唯一口径执行，不重复扣减。旧配置、旧客户端和已有订单保持原语义；堂食、外带、外送、线上和线下使用一致的业务定义，渠道差异通过餐牌与绑定表达。

## 2. 业务对象与规则

| 对象 | 职责 | 已有来源 |
| --- | --- | --- |
| 销售 SKU | 配料的商品身份和基准售价；按成员消耗时仍可定价 | 基础商品 SKU 和价格 owner |
| 配料 | 单项 `ADDON` 或由成员组成的 `COMBO`，主体共享 | `fnb_modifier` |
| 组合成员 | 成员配料及每份组合所需数量，支持嵌套 | `fnb_modifier_component` 与已发布依赖 |
| 库存模式 | 定义销售 SKU 与成员之间由谁承担实际扣减 | 本方案新增配置，发布时冻结 |
| 餐牌/渠道绑定 | 配料可选范围、时段、门店、渠道与价格策略 | 现有餐牌、绑定及渠道目录 |
| 消耗计划 | 每个原始订单行和物料的数量、单位、版本、阶段和凭据 | 现有真实库存计划与订单履约事实 |

### 2.1 库存模式

| 模式 | 适用范围 | 定价 | 扣减 |
| --- | --- | --- | --- |
| `SALES_SKU` 成品 | 单项或组合，必须存在销售 SKU | 销售 SKU 及餐牌/渠道合法覆盖价 | 只扣该销售 SKU 对应的成品，不再展开成员 |
| `COMPONENTS` 成员 | 仅组合，成员树必须完整；渠道发布仍需可定价销售 SKU | 销售 SKU 及餐牌/渠道合法覆盖价 | 只扣已冻结成员树解析出的物料，不扣组合销售 SKU |
| `NONE` 无实物 | 仅为历史无销售 SKU 单项的兼容解释 | 不因此推断已配置价格 | 不产生库存叶子；不表示库存校验成功，不作为新组合的默认模式 |

历史无字段按实际旧规则解释：有销售 SKU 为 `SALES_SKU`，无销售 SKU 的组合为 `COMPONENTS`，无销售 SKU 的单项为 `NONE`。不得将旧历史订单统一改写成某个模式。新配置默认建议 `SALES_SKU`，商家需显式选 `COMPONENTS`；缺销售 SKU 的新配置仍按现有发布/渠道价限制失败关闭，避免承诺尚无价格来源的功能。

成员展开时从根组合依次乘以每条成员数量，叶子为经过库存 owner 解析的真实物料。单项成员须有合法销售 SKU 和物料映射；嵌套组合使用其冻结版本的模式：`SALES_SKU` 作为叶子，`COMPONENTS` 继续展开。相同物料出现多次可在库存计划中按既有规则汇总，但须保留来源路径与可追溯分配；不得丢失不同单位、不同定义版本或不同消耗阶段的区别。禁止循环、缺版本、超深度/超数量及不可表示的小数；沿用已有上限，单位换算只使用库存 owner 已支持并明确授权的转换，不能猜测。叶子没有库存或事实不明时，按现有库存能力拒绝或返回待处理，不能将未知当作有货。

### 2.2 示例

一杯奶茶 20 元，加选「双拼小料」3 元，双拼销售 SKU 是定价标识，成员为珍珠 1 份、椰果 2 份：

- 选 `SALES_SKU`：每杯扣奶茶对应库存及双拼成品 SKU 1 份，不另扣珍珠和椰果。
- 选 `COMPONENTS`：每杯扣奶茶对应库存、珍珠 1 份、椰果 2 份；双拼销售 SKU 不扣库存。下单 2 杯且每杯选 1 份双拼时，成员分别消耗 2 份和 4 份。
- 交易原价按已发布价格和订单选择计算：`2 × (20 + 3) = 46 元`；优惠、税和最终应付继续由既有试算/订单引擎处理。不同渠道可按现有餐牌价格来源不同，实际渠道覆盖能力以现有实现及专项验收为准。

组合成员数量不能直接与销售 SKU 的件数跨单位相加。跨币种、跨单位和税档由现有 owner 验证；金额分摊保留平台原发票及可追溯依据，子物料本身不制造额外交易金额。

## 3. 端与流程需求

| 端/场景 | 需求 | 本阶段 |
| --- | --- | --- |
| 商家运营 B 端 | 创建/编辑组合、成员数量和库存模式；查看草稿及已发布版本；受现有商品权限和主体/门店授权保护 | 后端合同与校验；页面暂缓 |
| 餐牌运营 | 选择门店、时段、渠道、配料选项和可定价 SKU；发布时校验冻结依赖、价格、库存模式可执行性 | 后端实现及验证 |
| 收银/服务员/扫码/H5 C 端 | 按当前有效餐牌展示可选组合和售价，提交选择及数量；结算复用现有试算和订单 | 保持现有端入口；不新增前端页面 |
| 外送渠道 | 对每个绑定餐牌生成目录；接收回调后保留原外部行、价格、数量及渠道身份，导入真实餐饮订单 | 以 Mock 平台验证，不接真实 Keeta |
| 厨房/打印 | 以冻结任务和工位路由制作、出餐、打印；成员耗材与售价展示不混淆 | 校验已有厨房/打印 owner；设备实测后置 |
| 售后/运营查询 | 区分未制作、已制作及已交付，用原冻结计划和原库存凭据进行受控释放/返还；查记录、状态和原因 | 业务回归；资金退款暂不执行 |

基本流程：草稿配置 → 校验及发布冻结 → 门店/渠道餐牌发布 → 目录/下单及金额计算 → 冻结订单和消耗计划 → 原库存 owner 预留/制作/交付 → 事件回传、打印和售后。先付后吃与先吃后付使用同一组合定义，付款资金事实仍由独立支付 owner 决定；不通过 Mock 虚构付款或退款成功。

## 4. 兼容与不变量

1. 已发布快照、历史订单的原始 JSON、hash 和历史迁移 checksum 不重写。模式在新版本快照显式冻结；读取旧快照仅按旧规则推导。
2. 老客户端更新时未带新字段不能把已有显式 `COMPONENTS` 静默重置为 `SALES_SKU`。新增字段需区分“未提供”和“明确修改”；建议采用请求字段存在性检查/专门命令，并明确是否支持清空。严格 JSON 解析、远程 DTO 与已有 Java 构造调用均需兼容。
3. 已存在的幂等请求指纹必须保持原格式：旧请求/旧键重试继续命中旧回执；新字段仅在新版本命令中纳入指纹，不得借助统一增加 null 字段改变旧摘要。同键不同内容按现有冲突规则处理。
4. 配置更新以乐观版本和原权限执行；草稿变更不影响已发布、已下单或正在重试的订单。发布/下单重验主体、门店、渠道、SKU、币种及授权。
5. 一次原始销售选择恰有一种库存权威。若售前允许更换模式，仅影响新版本、新单；库存已预留后不得通过修改配置或原订单切换模式。
6. 收到渠道重复、乱序或超时后成功的回调，依据原渠道身份、版本及幂等键恢复，不重复创建订单、配料消耗、打印任务或回传。资金和库存各自以 owner 原始回执为准。

## 5. 数据与快照方案

**建议最小增量**：在现有 `fnb_modifier` 增加可空 `inventory_mode VARCHAR(16)`，允许 `SALES_SKU`、`COMPONENTS` 和历史 NULL；通过新增 FOOD Flyway 迁移实现，实际版本号在落地前与当前分支迁移清单核对。字段可空以保留历史语义；不修改历史建表脚本、不批量重写已发布快照。`NONE` 为旧数据读取时解释，默认不作为新建配置可选值。加数据库约束前先验证线上脏数据、MySQL 兼容性与回退；服务端仍须校验类型、SKU 和成员一致性。

`fnb_modifier_component` 沿用当前数量和成员关系，不另建商品或库存表。记录商家主体、操作人、版本和操作日志沿用已有 `BaseEntity` 和审计机制，不把门店作为配料主体；发布快照须冻结本配料库存模式、销售 SKU 和每级成员依赖版本/哈希。订单使用现有餐饮原始快照和订单源绑定保存模式、数量、原外部行、定价证据与库存计划引用；实际物料、预留、出库与返还仍由库存系统保存。若现有快照无法逐条追溯，先通过增量字段或辅助表保存必要映射，明确唯一键 `(tenant, entity, order/source component, version)`，避免复制库存台账；最终表结构以核对现有实体和迁移后的结果为准。

按渐进发布分两步：先部署能读取新旧快照但不对外开放新模式的代码和可空迁移；待各部署形态均支持并通过验收后，再以配置开关开放写入/发布。回退时先关闭新模式创建和发布，仍需保留能够读取已有新快照的版本；不可简单删除字段或清理已有订单事实。

## 6. API 合同（拟议）

沿用当前 B 端和内部接口，不新建第二套商品或订单 API；字段名为建议，实施时以项目 DTO、统一响应和错误码为准。

| 接口 | 输入增量 | 输出增量/行为 |
| --- | --- | --- |
| `POST /biz/x/food/stores/{storeNo}/modifiers` | 现有 `name`、`kind`、`salesSkuNo`、`components[]`；可选 `inventoryMode`；`Idempotency-Key` | 现有配料编号、版本、草稿状态；非法模式/成员拒绝 |
| `PUT /biz/x/food/modifiers/{modifierNo}` | 现有完整草稿及 `version`；增加可区分缺失与显式设置的 `inventoryMode` | 现有编号与新版本；旧客户端缺字段保留现有显式模式 |
| `GET /biz/x/food/stores/{storeNo}/modifiers` | 现有分页/筛选 | 附 `inventoryMode` 和兼容解析后的有效模式；须区分“历史推导”和“显式配置”以免运营误判 |
| `POST /biz/x/food/modifiers/{modifierNo}:publish` | 现有版本、生效时间和幂等键 | 发布版本、内容哈希；新模式发布前验证完整成员树和兼容范围 |
| 现有门店餐牌/购物车/报价/下单接口 | 原商品、配料选择、数量、版本和幂等键 | 报价与订单返回原有金额与状态；必要时以受权限保护的追溯信息返回模式/计划引用，不暴露内部密钥 |
| 现有渠道目录、回调、接单及履约接口 | 原渠道订单和外部行、数量、价格、渠道版本 | 返回现有导入/接单/回传状态及可审计引用，保持原外部合同和幂等 |

服务端从认证上下文取主体、门店和操作人，不信任请求体自报主体；已有 B/C/云端内部 API 及远程适配保持各自权限与合同。内部同步 DTO 的模式字段、版本协商及旧服务读取均需覆盖；新模式不应在旧独立服务仍运行时开放。

## 7. 计算、库存与售后

销售数量 `Q`、每份组合选择数 `P`、某成员每级配置用量 `u1…un`，则成员需求 `Q × P × u1 × … × un`。数量乘法采用现有 `BigDecimal` 规则，精度及上限在每层检查；金额使用项目现有定点最小货币单位与试算顺序，不以成员成本重新计算销售价格。

按现有库存阶段冻结计划并执行：下单/接单校验并保留真实引用；制作阶段仅按需消耗对应物料；交付阶段按计划完成剩余成品动作。先付后吃与先吃后付都不能凭本模块捏造已支付状态。退餐先核对原始订单行、已制作/已交付数量和库存凭据；未使用的预留按既有流程释放，已经消耗的物料是否返库存取决于库存 owner 的原始凭据与返还政策，不把已消耗原料自动视为可再售。部分退餐按冻结来源和数量计算，幂等、防超退；售后金额继续由原订单/售后 owner 负责。

## 9. 开发步骤与验收

1. **基线和合同**：核对当前代码、SQL 版本、实际 C/B/内部接口和历史 JSON/幂等指纹；记录现有 `SALES_SKU` 行为和本地/渠道消费差异。交付兼容样例和可复现基线。
2. **配置与发布**：完成增量迁移、DTO、权限、版本、审计、快照和远程合同；新模式写入口默认关闭。验收旧请求重放、旧服务/快照兼容、非法模式和并发更新。
3. **下单与计划**：完善本地与渠道原始证据、金额分配和成员递归，接入真实库存计划与工位；验证成品模式只扣组合 SKU、成员模式只扣叶子、嵌套及同物料多来源无重复。
4. **执行与恢复**：完善制作/交付、加菜改单、部分履约和退餐，验证崩溃重试、重复事件、库存不足、并发和历史订单配置变更后不漂移。
5. **编译与集中测试**：按用户安排先完成本批编码及编译，再统一运行与变更有关的单元、MySQL 迁移、B/C/内部接口和 Mock 端到端测试；重点含先吃后付、先付后吃订单行为、堂食/外带/外送及真实 owner。资金支付、真实渠道和真机另列。
6. **审查与发布准备**：整批独立代码审查、配置及回退演练、生成文档校验；通过后按既有授权提交、推送与集成部署，并验证部署健康及关键接口。测试不通过不发布、不跳过失败。

验收至少包括：旧客户端省略模式不改既有设置；历史 JSON/hash/幂等键不变；门店/主体隔离；同组合不同渠道价格与配置边界；组合中相同物料不同路径、嵌套、数量精度和单位；成员不足、不可售、循环；两种库存模式及先后付；组合与套餐混用；部分出餐/退餐及重复重放；渠道原金额守恒、回传顺序；打印失败重试与审计；集成与独立部署兼容。

## 10. 待确认的实现细节

- **嵌套版本与跨门店物料映射**：严格以发布时记录的成员版本及库存 owner 返回的门店事实为准；如果现有模型不支持某种跨门店共享，发布时拒绝并提示，不创建影子库存。
- **成品与成员的库存成本**：模式影响库存物料来源；毛利/净利与跨期成本归属由后续独立报表方案基于真实成本凭据处理，不在本批伪造成本。

### 渠道订单行与物料映射的实施细化

实查后，渠道选项带有独立外部行标识及原始金额，而现有 `DiningChannelSourceFactsPortImpl` 会为带销售 SKU 的选项生成独立实物组件。不能简单删除该组件并把金额并入主菜：这会改变售后、部分履约和渠道回传的原始行对应关系。实施时应保留选项的独立商业组件、原外部行及金额分配，把其库存计划绑定到该选项自己的成员叶子；主菜侧不得再次展开该同一选项。需要按组编号、配料编号及原选择行唯一匹配，拒绝重复、歧义和找不到冻结成员的情况。

当前渠道选择模型没有独立单位字段，而现有实现从实物 SKU 库存单位获取选项单位。对无须库存的定价 SKU，不能虚构单位或拿主菜单位替代：应先核对餐饮商品、配料发布快照和渠道合同是否已有权威单位来源；无可靠来源时拒绝该订单或目录发布。确认来源后才设计选项组件与叶子之间的数量比例、厨房任务与分次交付映射，并通过真实 owner 测试验证。

### 商品销售单位证据（实现约束，待编码）

继续核对发现，基础商品 `PrdSku.saleUnit` 已保存销售单位，现有 `GoodsCatalogQueryPort.SkuIdentityFact` 和市场 SKU 查询合同并未携带该字段。应扩展商品 owner 的独立只读计量事实合同，而不是在餐饮配置中再创建一份独立单位权威：查询按主体、门店、SKU 和实际市场取原始 SKU 编号、版本及销售单位，校验商品归属、市场和单位；缺失或不可解释时拒绝发布/导入。将单位、SKU 版本和来源凭据冻结到新配料发布事实，并纳入新版本的内容哈希；不向历史 SKU 身份记录无条件添加非空字段，避免改变旧快照比较与指纹。

渠道选项的数量没有独立单位：新模式只能在冻结的销售单位与平台选择数量语义得到明确映射且与订单组件单位兼容时使用；不根据实时 SKU 或父菜品单位推测。成员叶子的库存单位仍由库存 owner 提供并单独验证，不因销售单位相同就默认允许任意单位换算。独立部署需要对应只读内部接口、服务身份认证、超时失败关闭和兼容旧服务的灰度顺序。实际接口命名和快照增量字段需在开发时依现有商品 SPI、版本和审计约束确定；这一证据链目前尚未实现。

商品单位的新增 SPI 已初步编码：以原有市场 SKU 证据为基础读取 `PrdSku.saleUnit`，前后核对 SKU/商品版本、市场和单位，并通过独立、需服务令牌的内部 API 提供；既有商品身份合同保持不变。单位事实有有效期，因此**发布时**必须在本地写事务前验证真实凭据仍有效、保存原 SKU 版本、单位和来源摘要，并在提交前验证证据期限；**历史下单时**按发布快照和其原始内容哈希验证，不把正常过期的实时查询凭据当作历史订单失效，也不读取当前 SKU 单位覆盖快照。新单位事实尚未写入发布快照，也不能用于开放成员模式。
