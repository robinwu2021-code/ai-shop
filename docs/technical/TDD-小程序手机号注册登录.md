## §1 现状与影响面

实际代码当前有两条不同的路径：

1. `WX_MINI` → `AuthServiceImpl.findOrCreate`：按 openid/unionid 查找，未命中便建账号并签发业务 token。
2. `/mp/user/phone/wx` → `WxPhonePort.phoneOf` → `UserService.bindPhoneTrusted`：只向当前账号附加手机号；手机号属于其他账号时返回 `CONFLICT`。

所以现状是「先按微信身份建户，再绑定手机号」，尚不满足「授权手机号后注册或登录该手机号对应的账号」。

可复用 `WxAuthPort`、`WxPhonePort`、PHONE 凭证唯一约束、会话存储与既有手机号登录建户主干；不信任客户端自行填写或回传的手机号。

影响范围包括 C 端小程序启动、登录成功出口、手机号业务闸门、登录服务、支付所用 openid、账号变化后的缓存刷新和旧账号迁移。此次不修改这些业务文件。原先 H5/App/商家端登录方式不作为本方案的设计对象。

## §2 方案

### 2.1 两种身份分开

| 层次 | 得到什么 | 是否代表按手机号完成业务注册/登录 |
|---|---|---|
| `wx.login` + 服务端凭证交换 | 经校验的 openid、可选 unionid、短期小程序登录上下文 | 否；不能把只有微信凭证的临时状态显示成手机号登录成功 |
| 手机号授权 + 服务端换取号码 | 已验证手机号、手机号对应 userNo、正式业务 token | 是；新号注册、旧号登录 |

已有正式业务会话优先恢复。没有会话时，静默获取小程序上下文，浏览不受打扰。已存在且归属明确的微信关联可用于恢复已有业务账号；未关联身份不因此创建新的正式手机号账号。

新用户的业务账号创建时点后移到手机号验证成功。旧的匿名账号、购物车等数据需要按 §2.5 制定兼容处理，不能仅通过改掉 `createAccount` 的调用来切换上线。

### 2.2 用户交互

浏览商品 → 进入业务页面 → 点击下单等业务按钮 → 原生手机号授权 → 后端注册/登录 → 继续原操作。

业务页面保持业务按钮，例如「立即支付 ¥29.90」，旁边提示「首次下单需授权手机号，用于订单联系」。不增加独立登录页，不要求用户手动输入手机号，也不在业务按钮之后再增加一个应用自绘的授权前弹层。

只有微信原生组件负责手机号授权。进入页面本身不能替用户点击 `getPhoneNumber` 按钮；如某页面必须先登录，则该页展示一个中性的「手机号快捷登录」授权入口。

原型中的系统弹层是交互示意，不是需要前端照着实现的自绘组件。实际小程序使用原生组件的文案与外观。

完整 UI 增补（2026-10-14）：

| 原型屏幕 | 用户可见状态 | 交互出口 |
|---|---|---|
| s01、s02、s07 | 首页自由浏览、下单、我的未登录 | 点击业务按钮或中性手机号快捷登录入口 |
| s03、s19 | 系统手机号授权与号码选择 | 允许后按实际授权号码注册/登录；拒绝不提交 |
| s08、s09 | 新手机号注册中、已有手机号登录中 | 业务请求完成前防重复点击，不假报登录成功 |
| s04、s10、s11 | 注册/登录成功，正式身份与原账号资料 | 自动继续下单，或回到原订单/优惠券入口 |
| s05、s12、s13、s14 | 拒绝授权、凭证失败、登录失败、通道不可用 | 保留业务页面，按错误阶段重试；授权 code 不复用 |
| s06、s15 | 已登录、会话过期后的静默恢复 | 身份明确时直接继续，恢复失败才按需授权 |
| s16、s17、s20 | 历史关系需核对、账号受限与客服 | 保留历史资产；账号受限不能绕过注册 |
| s18 | 用户协议/隐私政策阅读 | 返回原页面，不触发登录或订单提交 |

交互演示有 9 种模拟场景和首页/我的/下单 3 个入口。场景选择只存在于评审原型外部，正式小程序不会让用户选择“新账号/老账号”，该判断仍由后端按已验证手机号完成。协议只展示摘要示意，支付只展示登录后继续业务的衔接，均不执行真实操作。

### 2.3 服务端账号处理

1. 校验短期小程序登录上下文；静默登录未成功时不发起可提交的手机号登录请求。
2. 接收原生回调中的手机号授权 `code`；由服务端调用手机号通道换取真实号码。
3. 用完整、已验证 PHONE 凭证定位账号：命中就登录该账号；未命中才注册。并发与重复请求由唯一约束及幂等处理保证不重复建户。
4. 账号被禁用时按既有策略拒绝登录；不能通过重新注册绕过账号状态。
5. 在归属不冲突时关联本次小程序身份，签发正式业务 token，并返回该账号用户资料。既有注册归因只在真正新建账号时执行一次。

建议为手机号注册/登录提供独立的登录语义；旧 `/phone/wx` 的「绑定」语义不能偷偷改成会话切换，否则个人资料等调用方会出现账号突然变化。

建议契约形态（设计草案，尚未新增端点）：

```text
请求：短期小程序登录上下文 + phoneCode + 必要注册归因
响应：正式业务 token + user + isNewUser
```

`wx.login` 的登录 code 与 `getPhoneNumber` 的手机号 code 是不同凭证，不可混用，不复用已消费的 code。客户端不传自称已验证的手机号，不保存 session_key；app secret 和凭证交换留在服务端。

### 2.4 登录成功出口

先保存响应中的 token 与 user，确认业务登录成功，再刷新该账号的资料、购物车、优惠券、地址和社区归属，最后继续被拦下的操作。账号切换时旧缓存不能沿用；原账号资产也不能直接复制给目标账号。

登录成功与业务操作成功分开处理：授权成功、后端超时或账号校验失败，都不能提交订单；业务动作失败后保留已成功的登录态。下单继续一次，防止重复授权回调或连续点击造成重复订单。

取消授权时关闭系统弹层并留在当前业务页，清理本次待执行动作；下次点击重新走授权。已登录用户从同一业务按钮直接继续。

手机号通道不可用时提示当前无法完成快捷登录；验证码只能作为可选兜底方案，不能作为小程序的默认注册/登录 UI。本次主流程原型不展示验证码表单。

### 2.5 历史身份冲突

已验证手机号足以用于登录其对应账号，但这不等于可以覆盖另一个账号的微信凭证或迁移资产。

- 手机号已注册：始终以手机号所属账号作为本次业务登录目标，不能因为当前 openid 已建过临时账号而简单返回「手机号已注册」阻断登录。
- 微信关联未被占用或已属于目标账号：补充/复用关联，后续可无感恢复。
- 微信关联已指向另一个历史账号：保留两边账号、订单、卡券、积分和地址；不能直接接线当前闲置的 `adoptOrReject`。它只检查未完成订单且会删除旧壳，无法证明不存在其他资产。
- 本次已验证的小程序上下文需与正式会话关联，支付使用当前真实操作者的 openid，而非随意取手机号账号旧列里的 openid。永久微信关联的改绑另走关系核对；未确认关系时不能承诺后续都可依靠 openid 自动恢复。

落地前必须补迁移场景测试，覆盖空壳、已完成订单、卡券/积分、已绑定其他手机号、不同微信使用同一授权手机号、并发登录。不能以「没有未完成订单」作为安全合并的充分条件。本方案不开展自动资产合并。

实施范围补充（2026-10-14）：用户确认线上有效账号范围很小，其他账号可清理，本地测试数据允许直接清理。本轮不增加历史 unionid/openid 已分别归属不同账号的自动兼容逻辑；既有技术登录对此继续拒绝，并测试不签发会话、不转移永久身份。这与已获得可信技术会话后的手机号登录不同，后者仍按上述规则登录手机号原账号并保留另一账号资产。未对线上数据库执行清理。

### 2.8 基于系统 UI 组件的修改方案（2026-10-14，待评审）

**目标：** 将 20 屏原型落实为微信小程序交互，默认静默取得小程序凭证，在用户需要业务身份时通过原生手机号授权注册/登录。

**架构：** 页面使用系统 UI 组件和积木；新增 C 端业务层的原生授权按钮薄封装与页内登录提示组合。账号识别、会话切换、数据刷新集中在登录协调层，按钮不自行建户，通用 UI 库不调用账号 API。

**技术栈：** 现有 uni-app / Vue 3 / Pinia / `packages/ui` / `packages/shared`，沿用 Java 登录服务及微信凭证端口，不引入新的 UI 框架。

**规范依据：** [规范-组件](design/规范-组件.md)、[规范-字体](design/规范-字体.md)、[规范-版面](design/规范-版面.md)、[规范-页面](design/规范-页面.md)。`UI标准库清单.md` 已注明被生成版替代，不以其历史数字为依据。

#### 现状与本次调整

| 现状 | 调整 |
|---|---|
| 分类、店铺、我的调用 `requirePhoneOnEnter()`，进入即显示应用手机号弹层 | 浏览页面去掉进入即弹；我的展示页内手机号快捷登录入口 |
| 多个页面挂载 `phone-gate`，共享 `visible/pending`，下单页另有自己的 `phoneGate` | 主流程改为页面业务按钮直接承载原生授权；待续动作与发起页面关联，不靠跨页全局待办 |
| 下单 `submit()` 经 `await confirmPlaceMismatch()` 后才打开应用弹层 | 提前计算可提交状态及需要确认的业务条件，原生授权必须发生在有效的用户按钮点击中 |
| `isLogin` 只看 token，技术会话也被当作登录 | 保留技术会话用于兼容现有浏览接口；增加手机号业务登录的独立判据与阶段 |
| `/phone/wx` 只绑定，返回 `User`，冲突即拒绝 | 增加手机号注册/登录语义，返回正式 token 和原账号资料；保留资料页主动绑定语义 |
| 401 失败后 `reLaunch` 到通用登录页 | 优先恢复会话；失败留在当前业务页面显示标准登录提示，保留来源参数 |

新增业务封装，不新增同类基础 UI：

- `c-app/src/components/biz/biz-phone-login-button.vue`：封装原生 button 的授权事件和系统按钮样式。`label: string`、`disabled?: boolean`、`loading?: boolean`、`size?: "default" | "sm"`、`tone?: "primary" | "soft"`；成功触发 `ready({ userChanged: boolean })`，取消触发 `cancel`，失败触发 `error`。页面继续执行原业务动作。
- `c-app/src/components/biz/biz-login-panel.vue`：组合 `sh-empty` 与上述按钮，供订单、优惠券、收藏、参团记录等需要业务身份的页面复用。只组合现有件，不写新的卡片/遮罩/主按钮皮肤。

原生 button 的默认边框/边距重置从当前 `phone-gate` 复用并收敛至按钮封装；不再逐页复制 `.onetap`。页面显式 import 新业务组件，组件测试实际挂载，不用未解析的自定义元素冒充组件输出。微信平台差异放在 `c-app/src/ports/phone-login.ts`，页面不加条件编译分支。

#### 全局约束

- 外壳、贴底条、字号、色板、间距、安全区沿用现有规范；聊天原型中的 `cp-*` CSS 不复制到小程序。
- 需要手机号时按钮本身使用 `open-type="getPhoneNumber"`；业务登录成功时走普通业务点击分支。同一次点击不能让 `tap` 与 `getphonenumber` 各提交一次。
- 凭证准备失败或页面不可提交时，授权入口不可用，并显示重试或具体业务原因；不能异步准备结束后调用代码自动点击原生按钮。
- 手机号回调没有 code 时视为取消；不注册、不下单、不显示登录成功。失败重试取得新 code，不重放已消费的凭证。
- 正式会话更新及账号数据刷新成功后才发出 `ready`。离开原页面后不恢复旧页面已经取消的业务动作。
- 本轮仅拟定方案；不把 UI 改造视为后端注册/登录已经实现，不启用现有危险的历史账号自动接管代码。

### 2.9 登录协调层与接口配合

第一期采用兼容迁移：保留现有 `WX_MINI` 技术会话，避免直接破坏按该会话工作的浏览/购物车接口；只有经过手机号验证的业务账号才显示为已登录、才执行业务注册副作用。技术账号的存在不能成为“手机号已注册”的判断依据。

前端计划新增 `c-app/src/shared/phone-login.ts`，统一阶段：`preparing`、`ready`、`authorizing`、`submitting`、`authenticated`、`failed`。飞行中的请求与待续动作不持久化，发起页面销毁时撤销该页待续动作。

建议业务接口：

```ts
interface WxPhoneLoginReq {
  phoneCode: string;
  inviterNo?: string;
  merchantNo?: string;
  agreed?: boolean;
}
interface WxPhoneLoginResp extends LoginResp {
  isNewUser: boolean;
  wxRelation: "linked" | "pending";
}
// 使用已验证的小程序技术会话；openid 从服务端上下文取得，客户端不声明号码或 openid。
loginByWxPhone(req: WxPhoneLoginReq): Promise<WxPhoneLoginResp>;
```

拟新增 `POST /mp/user/login/phone`（技术会话鉴权），不偷偷改变 `/mp/user/phone/wx` 的绑定返回结构。后端通过 `WxPhonePort` 验证 phoneCode，按 PHONE 定位原账号或完成首次手机号注册，再返回正式会话。没有技术会话、无效 code、账号禁用均不能取得正式 token。

技术账号变为手机号账号时，邀请归因和注册奖励只在真正首次手机号注册时执行一次。不能在静默建技术账号时清掉 `pendingInviter`，也不能在每次手机号登录时重复发注册奖励。

`stores/user.ts` 计划保留技术态的兼容行为，增加 `isPhoneLogin` 业务判据及 `loginByWxPhone` 成功出口；同步保存 token/user，再通知账号相关缓存失效。后端返回 `wxRelation="pending"` 时，仅表示历史微信关联需核对，不表示本次手机号登录失败，也不删除/转移另一账号资产。

支付联动是该契约的前置验收项：目前 `SettlePortImpl` 用 `UserIdentityPort.wxOpenIdMp(userNo)` 找付款 openid。切到已有手机号账号后，这个 openid 未必属于当前操作者。实施时必须把本次可信小程序上下文用于支付，覆盖不同微信/历史身份冲突用例；不得仅返回新 token 却保留错误 payerId。该上下文的服务端传递与生命周期应和登录契约一起落实，再接下单 UI。

### 2.11 必须处理的衔接问题

1. **账号切换后的数据与价格。** 缓存不能混用。保留用户刚确认的 SKU/数量草稿，重新核对目标账号购物车、优惠券、积分、地址、社区及价格；旧账号地址 ID/券 ID 不能带到新账号提交。若金额或履约条件变化，回到现有确认页面让用户确认，不能盲目继续支付。
2. **过期响应不能踢掉新会话。** `http-client.ts` 目前未向统一 401 处理传递请求所用 token。计划增加可选请求会话上下文，兼容原有无参处理器；只对当前会话的 401 恢复登录，账号切换前的迟到响应不清掉新 token。
3. **原生手势与前置校验。** `confirmPlaceMismatch()` 是异步业务确认，现有离线订阅授权也占用原生用户手势。正常点击直接授权；需要地址确认的异常分支先用既有 `confirm()` 完成业务确认，再由用户明确点击原业务按钮。不能把手机号授权或订阅授权放到任意 await 之后自动补调；登录继续提交、订阅/支付拉起分别按平台能力验证。
4. **处理中反馈的宿主。** `app-overlay` 在 `sh-scaffold` 内部呈现共享状态；只由当前发起页显示处理反馈，多个页面栈不能同时恢复同一待办。页面退出后即使登录请求成功，也不自动跳回或下单。
5. **旧链接与真实资料绑定。** 外部订单路径、旧 `redirect`/`bind` 参数、本人改绑手机号与收货电话都有明确归属；不能把所有取手机号行为改成账号切换。
