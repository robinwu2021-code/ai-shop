## 一、前端独立于电商，但测试阶段能一起打包

### 1.1 目录

```
elec-app/                     新工程（uni-app + Vue3 + TS，与 c-app 同一套技术栈）
  src/
    pages/                    元器件自己的页面（首页、搜索、料号、询价、供应商…）
    api/                      只认 /elec/**，不认 /mp/**
    pages.json  manifest.json 自己的小程序配置
  package.json  vite.config.mts
packages/ui        共用（sh-* 组件）      ← 已有，不动
packages/shared    共用（类型、工具、http）← 已有，types/elec.ts 已落
```

**为什么是新工程而不是 c-app 的一个分包**：元器件将来要整个搬走（独立小程序、独立域名）。
做成分包的话，搬走那天要从 `pages.json`、`i18n`、`api/contract.ts`、`mocks` 四处把它拆出来 ——
而这四处届时已经和电商的内容缠在一起。<b>现在分开，搬走就是 `git mv` 一个目录。</b>

**共用的只有 `packages/`**：组件库与类型。这两样本来就是三端共用的，不算耦合。

### 1.2 测试阶段合并进电商

两种形态，同一份源码：

| 形态 | 怎么来 | 用在哪 |
|---|---|---|
| **独立小程序**（目标形态） | `npm --prefix elec-app run build:mp-weixin` | 正式发布 |
| **并进 c-app 测试**（过渡） | `npm --prefix c-app run build:with-elec` | 现在：借 c-app 已有的小程序与域名验证 |

合并的做法是**构建期软链 + 分包声明**，不是复制代码：

```
c-app/src/pkg-elec  →  ../../elec-app/src   （构建脚本建软链，产物进 .gitignore）
c-app/src/pages.json 里多一段 subPackages（由 scripts/with-elec.mjs 注入，不手改）
```

> ⚠️ **软链在小程序构建里踩过坑**（见记忆「npm i 会打断小程序构建」）：
> `@ai-shop/ui` 的软链曾让 mp 构建报 `Invalid pattern`，H5 与 pre-push 全绿。
> 所以这条路要**先验 mp 产物**再当成可用，不能只看 H5 跑起来了。
> 万一不成，退路是构建期 `cp -R`（慢几秒，但没有这个风险）。

### 1.3 接口指向

`elec-app` 只调 `/elec/**`，同域经 nginx 转到 8085。开发期 vite proxy：

```js
proxy: { "/elec": { target: "http://localhost:8085", changeOrigin: true } }
```

**登录态借 c-app 的**（过渡期）：并进 c-app 时共用同一个 token；独立发布时元器件小程序自己走
`/mp/user/login`（同一个主系统、同一个账号）—— 那时 `elec-app` 要多引一个登录页，
这是它与 c-app 唯一还共用的后端接口。

## 二、C 端询价与 B 端报价都要微信通知对方

### 2.1 通知矩阵（谁做了什么 → 谁收到）

| 事件 | 通知谁 | 微信订阅消息 | 站内信 | 企业微信群 | 现状 |
|---|---|:--:|:--:|:--:|---|
| 买家提交询价 | **收到派单的供应商** | ✅ | ✅ | ✅（运营） | 站内信与企微已实现 |
| 供应商报价 | **买家** | ✅ | ✅ | ✅（运营） | **待做** |
| 平台录入报价 | 买家 | ✅ | ✅ | — | 已实现 |
| 买家选中某条报价 | **那家供应商** | ✅ | ✅ | ✅（运营） | 站内信与企微已实现 |
| 买家接受平台报价 | — | — | — | ✅（运营） | 已实现 |
| 供应商拒绝（没货） | 买家（整行都没人接时） | ✅ | ✅ | ✅（运营） | **待做** |
| 平台关单「暂无货源」 | 买家 | ✅ | ✅ | — | 已实现 |
| 新供应商注册 | — | — | — | ✅（运营） | 已实现 |
| 库存将到期 | 供应商 | ❌ | ✅ | — | **待做**（见 2.3） |

### 2.2 订阅消息的硬约束：一次授权只够一条

这是整张表最要紧的一条，它决定了实现方式：

- 买家**提交询价时**弹一次授权 → 覆盖「有报价了」那一条
- 供应商**提交报价时**弹一次授权 → 覆盖「你的报价被选中了」那一条
- 供应商**每次打开待报价列表时**弹一次 → 覆盖下一条「有新求购」

**攒不住第二条**：平台改价、第二家报价、第三家报价，这些都发不出订阅消息。
所以 **站内信是必达的那一份**，订阅消息只是加速通道 —— 两条同时发，
端上消息中心里能看到全部，微信里看到的是最近那一条。

### 2.3 不做的：库存到期提醒推微信

到期提醒<b>只进站内信 + 工作台红点</b>，不发订阅消息。理由：供应商为了这条要授权，
而他授权的额度应该留给「有新求购」—— 那一条直接带来生意，到期提醒不是。

### 2.4 要做的改动

| 改动 | 文件 |
|---|---|
| 供应商报价后通知买家 | `ElecDispatchServiceImpl.quote()` → `ElecBuyerNotifier.quotedBySupplier(...)` |
| 整行都被拒绝时通知买家 | 同上，`decline()` 里判断该行还有没有 ACTIVE 报价 |
| 端上三处弹授权 | `elec-app`：提交询价、提交报价、打开待报价列表 |

## 三、供应商注册 → 企业微信通知

**已实现**：`WeComElecAlerts.newSupplier`，推公司名、类型、城市、联系人与电话、编号。
默认复用生产已配的 `SHOP_NOTIFY_WECOM_WEBHOOK`（收入驻意向的那个群），不用再给地址。

消息长这样：

```
**新的元器件供应商**
> 公司：深圳某某电子有限公司     ← 点一下就成为供应商时这里是「还没填」
> 类型：贸易商
> 城市：深圳
> 联系人：王工　13800005210
> 编号：ES2026…
点一下就成为供应商，入驻即可上传库存；有问题在库里把 status 改成 SUSPENDED
```

## 四、询价与报价都推企业微信，将来可配置

### 4.1 现在推什么

| 事件 | 现状 | 消息里有什么 |
|---|---|---|
| 新询价 | ✅ | 买家联系人与**完整电话**、每行料号×数量、目标价、**库里谁有货**（公司+电话+数量+批号+价，最多 3 家）、库里没货的标「要找货」 |
| 买家接受报价 | ✅ | 单号、料号概述、联系人与电话 |
| 新供应商 | ✅ | 见第三节 |
| **供应商报价** | **待做** | 单号、料号、**哪家报的**（运营看得到真名）、价与货况、目前几家报了价 |
| **供应商拒绝** | **待做** | 同上，带拒绝原因；**整行都被拒时要显眼**（那是运营要出手的信号） |

### 4.2 「将来可配置」怎么做

加一张表（或一个配置项）`elc_notify_rule`：事件码 → 开关 + 走哪条通道 + 哪个群。

```
| event            | wecom | webhook_key        | in_app | wx_subscribe |
| RFQ_CREATED      |  ✔    | (默认群)            |   —    |      —       |
| QUOTE_SUBMITTED  |  ✔    | ELEC_QUOTE_WEBHOOK |   —    |      —       |
| SUPPLIER_JOINED  |  ✔    | (默认群)            |   —    |      —       |
```

**现在不做**：一共五个事件、一个群，配置表的价值是零，而它会让「为什么这条没发出去」
多一个要查的地方。等真的出现「询价推 A 群、报价推 B 群」这种需求再建，
那时判据是具体的，不是猜的。

> **要先做的是另一件**：`notified_at` 为空的那些（没送到的）现在只有日志和库里的空值，
> 没有人会去看。加一条**运营端的「通知没送到」列表**比加配置表有用得多。

## 六、运营端集成：新增「元器件」菜单

### 6.1 菜单结构

运营端（ops-web）左栏加一个一级菜单，四个二级页：

```
元器件
  ├ 供应商        列表 · 详情（含他的库存）· 暂停/恢复
  ├ 料号与库存     料号搜索 · 某料号谁有货 · 库存行查询
  ├ 基础数据       厂牌 · 厂牌别名 · 认不出的厂牌（待补别名）
  └ 询报价        询价列表 · 详情（录入报价 / 关单）· 报价记录
```

### 6.2 每页做什么

| 页 | 列表 | 详情/动作 |
|---|---|---|
| **供应商** | 公司名、类型、城市、联系人电话、在售料号数、7 天内到期数、最近上传、状态 | 看他的库存；**暂停/恢复**（暂停后他的货不再给买家看）；改资料 |
| **料号与库存** | 料号搜索（与买家同一套：开头/中段/相近）| 某个料号 → **谁有货**（公司、电话、数量、批号、阶梯价、货况、包装、交期、货源地）—— 这是运营报价时最常看的一屏 |
| **基础数据** | 厂牌列表；别名列表（别名 → 厂牌） | 加厂牌、加别名；**「认不出的厂牌」**：上传时落到 UNKNOWN 的写法按出现次数排，点一下就补成别名（见 6.3） |
| **询报价** | 单号、买家、料号数、状态、派了几家、几家报了价、报价有效期、通知送达没有 | 详情：逐行看**供应商报了什么**（真名、价、货况）与**库里谁有货**；录入平台报价；手工指派给某几家；关单 |

### 6.3 「认不出的厂牌」——归一化的自我修复

上传时厂牌认不出会落到 `UNKNOWN`，原文留在 `elc_part.mfr_name_raw`。
运营端这一页把它们按出现次数排出来：

```
未认出的厂牌写法        出现次数   建议
ST Micro                  127     → 意法半导体（ST）   [补成别名]
TEXAS INSTRUMENT           89     → 德州仪器（TI）     [补成别名]
长电科技                    45     → 长电（CJ）         [补成别名]
```

点一下写进 `elc_mfr_alias`，**下次上传就认得出**。不需要新表 ——
数据来自 `elc_part where mfr_code='UNKNOWN' group by mfr_name_raw`。

> 这就是「种子数据 + 给归一化提供能力」的落地方式：种子给起点，运营端给增长的路。

### 6.4 权限码

| 码 | 管什么 |
|---|---|
| `elec:supplier:read` / `elec:supplier:manage` | 供应商列表 / 暂停恢复改资料 |
| `elec:part:read` | 料号与库存查询 |
| `elec:base:manage` | 厂牌与别名维护 |
| `elec:rfq:read` / `elec:rfq:quote` | 询报价查看 / 录入报价与关单（**已实现**） |

按运营端的既定流程登记五处（权限种子、菜单迁移、perm-map、端点矩阵、生成物）。
菜单在库里，只改 `nav.ts` 接真后端看不到 —— 要跑生成器落迁移。

### 6.5 运营端怎么调元器件服务

ops-web 同域走 nginx 的 `/elec/ops/**` → 8085，与它调 `/ops/**` 是同一种方式。
**不经主系统中转**：中转一层等于把元器件的接口在主系统里再定义一遍，
而那正是独立服务要避免的事。
