# 会员办理储值 · UI、接口与功能补充

状态：精简储值链路已实现、部署并完成非入账联调；2026-10-20。适用：B端、单门店账户。原型：[会员办理储值](../../prototypes/member-stored-value.html#s01)。

让商家从已有会员或新增会员开始办理储值。保留“顾客账户仅展示成功储值顾客”的现有规则，补齐会员选择和顾客身份，不将会员列表误当资金账户列表。

## 1. 定位与已核实问题

线上只读核查：虹选粮油、虹选鲜果、虹选粮油·深圳测试店，均返回会员1人、储值账户0个，接口HTTP200/code=0；不是接口异常或可据此断言的同步延迟。未用手机号创建新会员、未创建充值单、未执行入账。

| 当前事实 | 原因 | 本次处理 |
|---|---|---|
| 新增会员在储值账户搜不到 | account-directory限定sv_account关联索引has_recharge=1 | 保留账户目录；增加独立会员选择，不批量生成空资金账户 |
| 办理页输手机号不能找到会员 | 当前输入调用member-code/resolve，只接受动态会员码 | 明确区分手机号查询和扫码识别 |
| 新增后无法继续办理 | member-add保存后navigateBack，不返回选中对象 | 增加仅保存／保存并储值及回传 |
| 账户详情续充仍需重新扫码 | 跳转只带路由，不带受控顾客上下文 | accountRef在服务端解析归属，再换办理标识 |
| 未注册顾客无法储值 | Core允许LEAD，Pay当前依赖userNo | 建立稳定顾客身份及注册绑定能力，列为P0后端改造 |
| 姓名口径不一致 | 账户搜索读取平台昵称，会员读取人档与备注 | 选择与账户展示统一脱敏规则；备注不冒充实名 |

业务不要求先创建营销活动，沿用已启用的独立储值方案。不涉及连锁共用、线上购买、线上退款、跨店核销、成本分摊。

## 2. 精简入口与底部方案弹框（本轮修订）

门店只在App最外层切换，所有操作沿用当前门店；流程中没有门店选择。取消独立会员确认、储值填写、储值复核和到账结果页面。只有储值方案需要选择，不要求另填收款方式或凭据。

原型沿用prototypes/proto.css现有375pt储值屏、卡片和底部浮层，对应sh-scaffold、sh-card、sh-actionbar、sh-sheet。新增方案选项使用同一圆角、间距、主色及选中tint；弹框内保留顾客脱敏摘要，避免选错人。

| 屏／状态 | 操作 | 结果 |
|---|---|---|
| 01 储值管理·顾客账户 | 点击办理储值 | 进入03查会员；账户列表仍只展示已有成功储值顾客 |
| 02 会员列表 | 点击会员进入既有详情；点击储值 | 从会员详情打开底部方案弹框 |
| 03 查询会员 | 输入完整手机号查询，点击结果 | 直接打开方案弹框，不再经过确认会员页 |
| 04 会员详情／已有账户详情 | 点击储值 | 弹框自动带入当前顾客；已有余额同店复用 |
| 05 新增会员 | 仅保存／保存并储值 | 前者返回会员，后者保存后直接弹出方案 |
| 底部方案弹框 | 点击充50送10／充100送30／充200送50 | 显示选中态、到账金额和“确认储值·实收金额”按钮 |
| 弹框处理中 | 点击确认储值，明确确认线下已收款 | 禁止重复提交，仍在弹框显示处理中 |
| 弹框结果 | 服务端返回CREDITED／失败／待处理 | 在原弹框反馈；成功刷新顾客余额与记录，点击完成关闭 |

主路径：查询会员 → 点击会员 → 底部选方案 → 确认储值。已有会员详情：点击储值 → 选方案 → 确认。新增：保存并储值 → 选方案 → 确认。处理结果属于原弹框状态，不增加页面步骤。

“确认储值”是一次明确的线下已收款确认，按钮下方／上方简洁展示“确认表示已线下收取¥X”。没有权限的员工不提供可成功入账的确认按钮，不能绕过确认收款权限。仅选择方案不会创建充值或入账。

原有提交接口保留CASH/TRANSFER及receiptNo；新增§4.6线下确认接口支持只选方案办理，不得在前端默认为现金或伪造转账流水号。原型不调用真实接口，虚拟演示号13800000001命中，13800000009未找到可新增。

没有账户时返回account=null，界面显示未储值；不能伪造accountRef。后台仍校验租户、商家、当前门店及操作员，切换外层门店必须关闭弹框、清除顾客引用和选中方案。新增会员不立即开户，首次成功入账开户。

## 4. 接口增补清单

以下三个核心新增接口已实现，部署验收见执行台账；分角色待确认等扩展仍为后续需求。金额统一整数minor；时间UTC ISO8601；门店随请求明确传入，服务端同时校验X-Store-No一致性、租户／商家／操作员范围。customerNo只在服务端使用；前端不能提交userNo/personNo作为充值归属。

### 4.1 新增：查询可办理会员

`GET /biz/stored-value/customer-candidates?storeNo=…&phone=13800000001&page=1&size=20`

- 按现有会员搜索规则只接受完整手机号；默认不拉取全量会员，完整手机号查询在当前商家已授权会员范围执行。本期不加任意手机号前缀／全平台搜索。
- 当前门店决定办理及余额范围，会员可见性复用既有会员归属规则，不将其他商家会员暴露出来。
- shop-app聚合Core会员页与Pay批量余额；不得跨库JOIN、逐会员远程查账或把Pay目录当候选库。
- 权限：`biz:customer`与本店`pay:sv:recharge:create`；无账户查看权限时不返回余额字段，不扩大目录读取权限。
- 返回data示例（外层响应包沿用现有统一契约）：

```json
{"records":[{"memberNo":"M_DEMO","displayName":"林女士","phoneMasked":"138****0001","memberStatus":"ACTIVE","canRecharge":true,"unavailableReason":null,"account":{"accountRef":"opaque","currency":"CNY","availableMinor":13000}}],"page":1,"size":20,"total":1}
```

未开户：account=null；LEAD在身份改造完成后允许办理；改造前必须返回canRecharge=false和明确原因，不能前端假装已支持。候选列表不返回办理凭证，点击选用时才签发，避免列表加载完凭证已过期。

### 4.2 新增：确认办理顾客

`POST /biz/stored-value/customer-selections`

```json
{"storeNo":"S_DEMO","source":{"type":"MEMBER","memberNo":"M_DEMO"}}
```

或 `source={"type":"ACCOUNT","accountRef":"opaque"}`；source严格二选一，禁止混合字段。扫码仍走既有会员码接口，再用统一摘要契约，必要时在BFF内部聚合。

返回：`{customerRef, expiresAt, memberNo, displayName, phoneMasked, account, canRecharge, unavailableReason}`。

- 验证身份来源、会员／账户所属商家及门店权限，不接受任意账号号换取办理资格。
- 短时引用绑定租户＋商家＋门店＋操作员＋稳定顾客身份。采用现有120秒引用TTL；切店／换操作员／到期重新选择授权。该引用只识别顾客，不代表已收款，不授予扣款权限。
- 同一幂等充值创建命令超时后优先查原单；不得因换了customerRef生成另一充值。查明原命令未创建才可受控换凭证，须明确关联原命令的取消／恢复结果。
- MEMBER与ACCOUNT两种入口对同一顾客必须解析为同一canonical customerNo。

### 4.4 新增：待确认收款查询（分角色场景）

`GET /biz/stored-value/plan-recharges?storeNo=…&status=SUBMITTED&cursor=…&size=20`

仅向有本店收款确认权限的人员返回已授权原单及脱敏顾客、方案、实收、提交时间、revision。后台Pay按门店及状态查询，游标绑定过滤与操作员范围。逐单确认复用receive；操作前重新查询revision。列表无修改权不能绕过receive鉴权。

### 4.5 内部接口／端口补充

| 模块 | 能力 | 关键约束 |
|---|---|---|
| Core会员／人档 | memberNo→canonical customerNo、会员候选页、本人注册绑定 | 身份映射幂等；不伪造平台登录账号；不能只凭输入手机号认领余额 |
| Core身份端口 | customerRef→受控稳定顾客身份，兼容既有userNo | 签发与解析规则一致，凭证库不存明文token |
| Pay账户端口 | 批量查候选顾客本店账户，含未开户结果 | 数量上限、租户商家门店范围、无N+1；只读不开户 |
| Pay充值／查询端口 | 稳定顾客开户、充值归属、到账账户结果、待确认分页 | 保留幂等、状态机、行锁；事务持锁期间不等待Core远程调用 |

### 4.6 新增：弹框直接确认线下储值

`POST /biz/stored-value/plan-recharges/confirm-offline`

请求仅含`{storeNo, customerRef, planNo, versionNo}`，请求头携带`Idempotency-Key`。顾客与门店由上下文带入，前端只选择方案。该操作表示商家确认已在线下收款，不是平台线上支付。

- BFF先验证当前门店、顾客短时引用及创建＋确认收款权限；无权限在写入前拒绝，不能偷偷退化成普通员工自动确认。
- Pay协调既有创建、实收提交与收款确认逻辑，金额取方案冻结快照，不接受前端任意金额。无需前端串调三步，不改成点击方案即自动收款。
- 新增明确的`MERCHANT_OFFLINE`收款分类（数据库枚举、校验、契约及报表同步扩展），不冒充现金或银行转账；支付服务生成业务收款确认凭据，记录操作员、时间和充值单号。业务凭据不是银行流水，历史CASH/TRANSFER语义保留。
- 生成的业务凭据与同一幂等命令绑定，重试不能重新生成凭据／充值单。对已有幂等命令先找原单，即使customerRef到期仍可受控查询和恢复原命令，不能重复收款。
- 返回既有充值进度DTO及rechargeNo；CREDITED显示本次到账金额并通知外层刷新；账户引用与余额由账户接口查询，RECEIVED在同一弹框轮询。未知／失败仍查询原单，用户不会因网络超时被要求再次充值。
- Pay创建、实收提交、收款确认在同一个本地事务中完成，失败整体回滚；到账由既有outbox恢复任务幂等执行。不引入跨服务原子事务。Core身份在进入资金事务前解析，Pay持锁期间不远程回调Core。

新增接口总计：候选查询、顾客选用、线下确认3个核心接口；分角色待确认查询暂列扩展，不作为精简原型的额外页面。顾客选用是内部授权请求，不再对应独立确认页面。

## 5. 身份与数据改造边界

这是已有userNo账户模型的兼容改造。最终采用Core既有personNo作为稳定customerNo，独立字段表达；真实userNo可空，不创建假用户。Pay以customerNo选账，注册后通过Core已验证的人档关系绑定。V538/V539为本轮增量迁移。

必须覆盖：sv_account唯一键／账户号算法；sv_recharge、批次、账务凭证、收支投影、门店索引、冻结／核销选账、消费者账户读取、短时身份引用、内部远程DTO及原单指纹。不得只把开户处userNo换成memberNo，或把personNo塞入userNo字段。

现有账务保留，不改历史凭证归属和金额。建立现有用户到稳定顾客的唯一映射；同店同币种已有账户复用。注册绑定需手机号验证或已有认证人档关系，事务和唯一约束避免两份身份／两份余额；冲突人工处理，不能按手机号直接合并历史余额。未完成充值、冻结、核销、异步入账任务的兼容须有明确切换方案。新增会员不立即创建Pay账户。

## 8. 顾客账户统一搜索评审（2026-10-20，本节覆盖旧入口设计）

最新原型对应的App与接口已完成编码，发布验收结果见统一入口执行计划。取消独立“办理储值”搜索页和储值模块内新增会员入口；新增会员统一在会员模块。顾客账户是统一搜索及办理入口，仍沿用外层门店。

- 默认只列当前门店至少成功储值一次的会员，余额为0仍保留。按最后一次成功储值时间倒序，核销时间不参与该列表排序；同时间使用稳定账户号排序。收支记录仍按全部交易发生时间倒序。
- 统一搜索查本商家会员，首期使用完整手机号精确匹配。有储值账户展示本店余额，无账户不显示余额，但保留会员结果和首次储值操作；“没有账户”不等于“没有会员”。无匹配仅显示“未找到会员”，不提供新增入口。
- 点击会员进入详情；详情底部按钮统一为“储值”，点击后以底部弹框展示方案列表，选择并确认，不使用下拉框；仅选择方案不入账。清空搜索恢复默认储值会员列表。成功到账后更新余额和最近储值时间，新到账会员进入列表前部。
- 不展示其他商家/门店余额；会员没有本店账户也不会因查询自动开户。连续翻页排序需绑定门店、过滤和lastRechargeAt游标。

评审结论：入口合并合理。实现已将默认账户目录排序改为最近成功储值，新增lastRechargeAt并保留lastOccurredAt语义；复用会员候选与选用服务，前端删除第二搜索页面及新增入口。旧充值路由用于恢复原单或跳转统一入口；顾客详情底部“储值”使用既有方案弹框。发布结果见[执行计划](../superpowers/archive/plans/2026-10-20-unified-stored-value-ui.md)。
