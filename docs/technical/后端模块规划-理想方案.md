# 后端架构与模块规划 · 理想方案（v5：三端 × 三平台 × 多业态）

> 2026-08-09 · 从三端功能矩阵倒推，不受现有实现约束。
> 输入：三端功能清单 · [商家全流程矩阵](../requirements/商家全流程功能矩阵.md) ·
> [入驻进件建店](../requirements/入驻进件建店-需求与四层对齐.md) ·
> [多门店与分享激励](../requirements/多门店与分享激励-需求.md)（ADR-011）
>
> **版本演进**：v1 按域开工程（23）→ v2 业务线（9）→ v3 最少工程（5）→
> v4 多业态（业态=扩展点）→ **v5 补全接入维度**：
> 三个使用者（C / B / 平台）× 三种客户端（小程序 / App / H5）× 三种业态。
> v5 的核心是把这三者认定为**三个正交维度**，各自落在不同的层，互不污染。

---

## 一、三个正交维度（全文的总纲）

| 维度 | 取值 | 差异是什么 | 落在哪一层 | 绝不能漏进 |
|---|---|---|---|---|
| **使用者** audience | C 端 · B 端 · 平台端 | API 面 · 鉴权链 · 权限模型 · 数据域 | **portal 层**（三条独立过滤器链） | 领域层 |
| **客户端** client | 小程序 · App · H5 | 登录凭证 · 支付通道 · 推送通道 · 上传 · 分享扫码 | **channel 层**（portal 之下、domain 之上） | 领域层 |
| **业态** vertical | 零售 · 餐饮 · 服务 | 商品形态 · 库存语义 · 履约段状态机 | **domain 扩展点**（catalog / fulfillment 内） | 主干包 |

一句话规则：**领域层对"谁在用、用什么设备、什么业态"三问全部无知。**
它只知道用户号、商户号、订单号。三个维度各有一层吸收，谁也别渗进 domain。

> ⚠️ 现状已出现渗透：`AuthServiceImpl:92` 在**领域服务里** `switch (grantType)`
> 分发微信/OTP/Apple——那是客户端差异，不该由领域层判。v5 把它上移到 channel 层。

```
└──────────────────────────────────────────────────────────┘

```

## 三、维度一：三个使用者（audience）

### 3.1 三条独立的鉴权链与账号池

| 使用者 | 账号池 | 路径前缀 | 令牌 | 权限模型 | 数据域 |
|---|---|---|---|---|---|
| C 端消费者 | `usr_account` | `/mp/**` | 消费者令牌 | 无（本人数据） | 按 userNo |
| B 端商家 | `mch_account` | `/biz/**` | 商家令牌 | 门店角色（`mch_store_role`）· Plan 额度 | 按 entityNo + storeNo |
| 平台运营 | `sys_ops_staff` | `/ops/**` | 运营令牌 | RBAC 角色×权限码 | 全量 / 按辖区 |

**三池彻底独立，无互指列**。唯一合法跨池入口是「入驻通过时以申请里的
`contact_phone` 派生 `mch_account`」——派生后各活各的。

### 3.2 一个能力，三端三张面（这是 portal 层存在的理由）

以「门店」为例，同一个 `merchant` 域，三端各取所需：

| 使用者 | 看到的门店 | portal 做的事 |
|---|---|---|
| C 端 | 店铺主页：招牌·公告·我买过的 | 只读投影，隐藏经营字段 |
| B 端 | 装修·多门店·子账号·Plan | 写入口，按 storeNo 数据域裁剪 |
| 平台端 | 店招审核·主页模板·获客看板 | 治理动作，全量可见 + 审计留痕 |

**领域层只有一个 Store 聚合**；三种面貌是 portal 的 DTO 与权限裁剪，不是三份模型。

## 四、维度二：三种客户端（channel）——v5 新增的一层

### 4.1 差异清单：只有五类，且全部可枚举

| 能力 | 小程序 | App | H5 | 领域层应该看到的 |
|---|---|---|---|---|
| **登录凭证** | 微信 code 一键 | 手机号 OTP · Apple · 微信 | 手机号 OTP | 「已验证的手机号 / openid」 |
| **支付** | JSAPI（openid） | APP 支付（预下单串） | H5 / 收银台跳转 | 「支付单已创建，等回调」 |
| **推送** | 微信订阅消息 | APNs / FCM | 站内信 + 短信 | 「发一条消息给某人」 |
| **上传** | 小程序临时文件 | 本地文件 | 表单/直传 | 「一个文件 URL」 |
| **分享/扫码** | 小程序码 · 转发卡片 | 系统分享 · 相机 | 链接 · 二维码图 | 「一个可分享的 scene」 |

右列是**领域层唯一该知道的抽象**。左边四列的差异全部由 channel 层吸收。

### 4.2 结构：与前端 `packages/shared/ports/` 对称

前端已用 `ports/{auth,payment,push,share,scan,media}` 抽掉端差异，
后端建立对称的一层——同一个概念在前后端同名，联调时不用翻译：

```
channel/
 ├─ spi/                 ChannelType(MP|APP|H5) · 五个能力接口
 ├─ auth/                CredentialVerifier: WechatMp · PhoneOtp · Apple
 ├─ pay/                 PayGateway: WechatJsapi · WechatApp · WechatH5
 ├─ push/                PushSender: WechatSubscribe · Apns · Fcm · InApp
 ├─ media/               UploadAdapter
 └─ share/               SceneCodeAdapter
```

**关键改造**：登录从「领域层 switch grantType」改为
「channel 层按 `ChannelType` 选 `CredentialVerifier` → 验完只把
**已验证的 principal** 交给领域层建户」。领域层的 `AuthService` 从此
只有一个方法：`loginByVerifiedPrincipal(...)`，不再认识微信和 Apple。

### 4.3 判定 ChannelType

由网关按请求头 `X-Client: mp|app|h5` + 令牌里的 channel 声明双重判定，
**不由业务参数传递**（客户端可篡改）。令牌签发时钉死 channel，
支付/推送直接读令牌里的 channel 选通道。

## 五、维度三：多业态（v4 结论，此处收敛）

业态 = **品类模板**（商品侧多态）× **履约模式**（订单侧多态）：

```
统一主干:  CREATED → PAID → 〔履约段〕→ COMPLETED → (AFTER_SALE)
零售:  PREPARING → DELIVERING | ARRIVED → SIGNED
餐饮:  ACCEPTED → COOKING → READY → 堂食 | 自取 | 外送
服务:  BOOKED → CHECKED_IN → SERVED
```

- 金额 · 支付 · 关单 · 售后挂接 · **结算挂接** 全在主干段
  → **settle 永远只面对统一的「已完结订单」，业态对资金流不可见**
- 主干表禁止长业态列（现状 `PrdGoods.weighed / durationMin` 迁入业态附表）
- 库存语义策略化：件数（零售）/ 估清（餐饮）/ 时段容量（服务）

## 六、模块划分：6 个 Maven 工程

在 v3/v4 的 5 个基础上，新增 `shop-channel`（渠道层）：

```
shop-base ──────── 地基：common + spi（含扩展点与渠道 SPI）
   ├── shop-core ─────── 主业务：16 域包（含业态扩展）
   ├── shop-merchant ─── 商户线：入驻·进件·门店·子账号·信用   【业态无关·客户端无关】
   ├── shop-settle ───── 资金线：结算·分账·费率·提现·发票     【业态无关·客户端无关】
   └── shop-channel ──── 渠道层：登录凭证·支付·推送·上传·分享
shop-app ───────── 启动 + 三端门面（portal-mp / biz / ops）+ worker
```

| 工程 | 内容 | 为什么独立 |
|---|---|---|
| **shop-base** | `common`（认证机制·数据域·Outbox·幂等·i18n）+ `spi`（Port·事件·扩展点接口） | 零业务地基 |
| **shop-core** | identity · asset · community · catalog · review · trade · fulfillment · aftersale · marketing · group · growth · content · message · platform · risk · read | 主业务，互相只有普通领域协作 |
| **shop-merchant** | 入驻申请 · 主体 · 进件 · 门店 · 门店角色 · 服务范围 · 信用 | 变更最密集；「审核通过派生七表」同事务；**三个维度的新需求都不改它** |
| **shop-settle** | 结算单 · 分账 · 费率 · 提现 · 发票 · 个税 · 主体侧积分池 | 钱：审计/权限/发布节奏独立；第一个独立部署候选 |
| **shop-channel** | 三客户端 × 五能力的适配实现 | **变化源完全不同**：微信改接口、苹果改审核、安卓换推送——这些与业务无关的外部变更，不该让业务工程跟着发版 |
| **shop-app** | portal-mp / biz / ops + config + worker + 架构与场景测试 | 启动与门面 |

### 依赖规则（ArchUnit 强制，10 条）

工程级：
1. 三个业务工程（core/merchant/settle）互相不可见，只依赖 base
2. `shop-channel` 只依赖 base，**不依赖任何业务工程**
3. `shop-app` 依赖全部；反向禁止
4. `shop-base` 零业务依赖

包级：

5. 域包之间不得互相 import（含 core 内部），跨域只走 spi 的 Port/Event
6. Controller 只能住 `portal.*`，不得直接依赖 Mapper
7. 领域 Service 必须接口化；实现进 `.impl`，Port 实现进 `.port`
8. `read` 包不得被任何域包依赖（只订阅事件 + 只读 join）
9. 一个 `@Transactional` 只允许写本域的表；例外显式登记（仅 `StockPort`）
10. **主干不知道业态**：`*.core` 不得 import `*.retail|catering|service`
11. **领域不知道客户端**：任何 domain 包不得出现 `MP|APP|H5|wechat|apple|apns`
    等渠道标识——渠道判断只允许在 `shop-channel` 与 portal 层出现

> 第 11 条是 v5 新增，正是为修 `AuthServiceImpl` 那处 `switch (grantType)` 而立。

## 七、部署架构

![部署拓扑](./diagrams/deploy-topology.svg)

### 每份部署装什么

| 部署 | 网络 | portal | 渠道层 | 业务模块 | 实例 |
|---|---|---|---|---|---|
| **shop-api** | 公网 | `portal-mp` + `portal-biz` | shop-channel **全量**（登录·支付·推送·上传·分享） | core · merchant · settle · base | 多实例，无状态，可水平扩 |
| **shop-ops** | **内网 / VPN** | `portal-ops` | shop-channel **仅 media** | core · merchant · settle · base | 1–2 实例 |
| **shop-worker** | 内网 | **无**（不起 HTTP） | 仅出站（推送·支付重试） | core · merchant · settle · base | 1–2 实例 |

### 图上看不出来的三件事

**1. 为什么 C 端和 B 端在同一份部署里，而 ops 单独拉走。**
C 与 B 背后是同一批领域代码（商品、订单、履约、售后），拆开只多一份运维、
换不来隔离——它们本来就读写同一个库，B 端流量还比 C 端小 1–2 个数量级。
ops 拉走则不是性能考虑而是**安全**：运营接口能改费率、能封商家、能批提现，
不该和消费者接口挂在同一个公网端口上。分开后公网实例根本不加载 `/ops/**`，
路径扫描扫不到。

**2. worker 单独部署是三条里最容易被跳过、也最容易出事的一条。**
Outbox 派发、对账、批量导出如果跑在 api 进程里，会抢同一个线程池与数据库连接池。
一次批量任务把连接池占满，**症状是用户端下单超时**——而排查方向会完全指错，
没人会想到是导出报表干的。

**3. 三份部署的业务代码完全相同，差别只在两处**：装哪条 portal 链、起不起 HTTP。
所以这不是微服务拆分，是同一应用的三种角色部署：一个 jar、一个库、一条流水线，
`--spring.profiles.active=api|ops|worker` 决定角色。成本接近零，
而安全面收缩与资源隔离立刻兑现——这也是它排在所有拆分动作最前面的原因。

现状的 `SecurityConfig` 已把 `/mp/**`+`/biz/**` 划在一条链、`/ops/**` 单独一条，
改造只需给三个 `@Bean` 各加 `@Profile`，组件扫描按 profile 收窄。

## 八、三套用户体系与安全机制

三个账号池在 §三 已定「彻底独立、无互指列」。这一节补齐**认证与安全**：
注册怎么建户、登录验什么、令牌怎么隔离、失陷时炸多大。

### 7.2.1 三套体系的差别（它们不该长一样）

| | C 端消费者 | B 端商家 | 平台运营 |
|---|---|---|---|
| **表** | `usr_account` | `mch_account` | `sys_ops_staff` |
| **注册** | 自助，登录即建户 | **不自助**：入驻通过时派生，或 owner 邀请子账号 | **不自助**：管理员创建，无注册入口 |
| **登录凭证** | 微信 code / 手机号 OTP / Apple | 手机号 OTP（+ 微信绑定后一键） | **账号 + 密码 + 二次验证** |
| **凭证强度** | 低摩擦优先 | 中 | **最高**：能改费率、批提现、封商家 |
| **令牌 Realm** | `CONSUMER` | **`MERCHANT`**（新增） | `OPERATOR` |
| **有效期 / 续期** | 30 天滑动 | 7 天滑动 | **8 小时，不滑动**，到点重登 |
| **单点** | 多端并存 | 多端并存 | **单会话**，新登录踢旧 |
| **权限模型** | 无（本人数据） | 门店角色 + Plan 额度 | RBAC 角色 × 权限码 |
| **可达网络** | 公网 | 公网 | **仅内网 / VPN** |

**注册入口只有一个是开放的**——这是三套体系最重要的差别。
B 端与运营端**没有注册接口**：商家账号只能由「入驻通过」或「owner 邀请」派生，
运营账号只能由管理员创建。任何形式的「商家自助注册」都会绕开入驻审核。

### 7.2.2 🔴 现状三处安全缺陷（已核对代码）

| # | 问题 | 位置 | 后果 |
|---|---|---|---|
| 1 | **运营密码用 `String.hashCode()` 派生** | `OpsServiceImpl:372` `Integer.toHexString(("shop$"+raw).hashCode())` | 32 位、可碰撞、可暴力枚举、无盐。且用 `.equals` 比较（非恒定时间）。**这是权限最高的那套账号** |
| 2 | **OTP 无任何限流** | `OtpStore` 只有 `save` / `verifyAndConsume` | 同一手机号可无限发码（短信轰炸+费用），验证码可无限次猜（6 位数字，几千次必中） |
| 3 | **C 端与 B 端共用一个 Realm** | `Realm.CONSUMER` 注释写着「C 端与 B 端共用（`ctk_`）」 | 令牌在**类型层面**不可区分，隔离全靠业务层 `BizContext`。三个账号池配两个 Realm，是结构性错配 |

> 三条都不是"将来要做"，是**已经存在的洞**。第 1 条尤其严重：
> 运营账号一旦被爆破，攻击者能改费率、批提现、封商家。
>
> **整改方案（含改动清单、存量迁移、验收用例）**：
> [安全整改方案 · 认证与账号体系](./安全整改方案-认证与账号体系.md)

### 7.2.3 目标机制

**凭证存储**

| 用途 | 算法 | 说明 |
|---|---|---|
| 运营密码 | **BCrypt(cost≥10)** 或 Argon2id | 每条独立盐；比较用库函数（恒定时间） |
| OTP | 只存**哈希**，不存明文 | 现状明文存内存 + `log.info` 打码（标了 DEV-ONLY，生产必须移除） |
| 令牌 | 随机 256bit，Redis 存会话 | 已有 `TokenStore` 抽象，S2 换 Redis |

**Realm 改为三值**：`CONSUMER(ctk_)` · `MERCHANT(mtk_)` · `OPERATOR(otk_)`。
令牌前缀即域，**拿 B 端令牌打 `/mp/**` 在过滤器层就 401**，不进业务代码。
同时 `SecurityConfig` 把现在合并的 `/mp/**`+`/biz/**` 拆成两条链。

**限流（分层，缺一不可）**

| 层 | 限什么 | 建议阈值 |
|---|---|---|
| 发码 | 同手机号 / 同 IP / 同设备 | 60s 一次，10 次/天，同 IP 20 次/时 |
| 验码 | **同手机号连续失败次数** | 5 次锁 15 分钟——没有这条，6 位码等于没有 |
| 登录 | 同账号失败次数（运营端） | 5 次锁定，须管理员解锁 |
| 通用 | 同 IP 请求速率 | 网关层 |

**运营端额外三条**：二次验证（TOTP / 短信）· 单会话（新登录踢旧）· 敏感操作
（改费率、批提现、封商家）**二次确认 + 强制审计留痕**（`sys_audit_log` 已有）。

### 7.2.4 跨池的唯一通道：入驻派生

```
C 端用户提交入驻申请 ──► 平台审核通过 ──► 以申请里的 contact_phone
                                          派生 mch_account（owner）
                                          ▲
                                   唯一跨池写入口
```

派生之后两个账号**各活各的**：同一个手机号在两池各有一条记录，
互不指向、各自独立登录与改密。「同一手机号」是巧合，不是关联——
这条要写死在契约里，否则将来一定有人加一列 `user_no` 把两池焊死。

### 7.2.5 安全机制装在哪（对齐部署与工程）

| 机制 | 落点 | 理由 |
|---|---|---|
| 凭证校验（微信/OTP/Apple） | **shop-channel** `auth/` | 客户端差异，见 §四 |
| 限流与锁定 | **shop-base** `common/ratelimit` | 三个池共用一套，且限流是基础设施不是业务 |
| 账号与 RBAC | **shop-core** `identity/` | 三池的建户、改密、角色 |
| 令牌签发与校验 | **shop-base** `auth/` | 已有 `TokenStore` / 过滤器 |
| 门店角色与 Plan 额度 | **shop-merchant** | 它是商户的经营授权，不是身份 |
| 审计留痕 | **shop-core** `platform/` | 已有 `sys_audit_log` |

**部署维度**：运营端登录只在 `shop-ops` 装配（内网），
公网的 `shop-api` **根本不含运营登录接口**——这是 §七 把 ops 拉进内网的
第二层收益：即使有 1 号缺陷那样的弱密码，公网也没有入口可打。

## 九、Java 工程封装：垂直切片

### 8.1 关键决定：Controller 归业务工程，不归 portal

现状 21 个 Controller 的命名已经泄露了真相——`MpCatalogController`、
`BizSettleController`、`BizMerchantController`，**每一个都是「端 × 域」的交叉点**，
只是被按「端」摆进了 `portal/{mp,biz,ops}` 三个目录。

按端摆的代价：做一个「提现」功能要同时改 `shop-app/portal/biz`（Controller）
和 `shop-settle`（Service）两个工程；而这两处**永远一起改**。
把 Controller 放回它服务的域，一个功能的全部代码就落在一个工程里。

| | 按端切（现状） | **按域切（目标）** |
|---|---|---|
| 改一个功能 | 跨 2 个工程 | **1 个工程** |
| 一个端的 API 全貌 | 看目录 | 看 OpenAPI / API 清单（本就是生成的） |
| 拆微服务 | 要从 portal 里挑出 Controller 再搬 | **整个工程搬走，自带 API** |
| 鉴权/异常/DTO 一致性 | 靠"都在一个工程里" | 靠 `shop-base` 的 web 基座统一 |

> 顺带修掉一个上帝类：`OpsController` 一个类 15 个端点跨多域，
> 按域切后自然分解为各域的 `api/ops` 切片。

### 8.2 每个业务工程的标准内部结构

**六个工程一个模子**，新人看任何一个都认得路：

```
shop-settle/
 ├─ api/            该域的 Controller，按端分子包
 │   ├─ biz/            BizSettleController · BizWithdrawController
 │   └─ ops/            OpsSettleController · OpsWithdrawController
 ├─ service/        领域服务【接口】—— 对内
 ├─ impl/           服务实现
 ├─ port/           spi Port 的实现 —— 对其他域暴露的唯一入口
 ├─ job/            该域的定时任务与事件消费者（结算生成 · 对账）
 ├─ entity/ mapper/ dto/
 └─ (test)          该域单测，不启 Spring
```

`shop-core` 同一模子，只是外层多一级域名：`core/<域>/{api,service,impl,port,job,…}`。

三条封装约束：

1. **`api/` 只能调本工程的 `service/`**，不得调别的域——跨域走 `port/`
2. **`port/` 是本域对外的唯一入口**，其他域看不到 `service/` 与 `impl/`
3. **`job/` 与 `api/` 平级**：定时任务是该域自己的逻辑，不是"worker 的逻辑"。
   worker 部署只是**调度装配器**，扫描各域注册的 job，自己不含业务

### 8.3 六个工程与部署的对齐

| Java 工程 | 业务域 | 装进 api | 装进 ops | 装进 worker |
|---|---|---|---|---|
| `shop-base` | —（common · spi · web 基座） | ✅ | ✅ | ✅ |
| `shop-channel` | —（渠道适配） | ✅ 全量 | ✅ 仅 media | ✅ 仅出站 |
| `shop-core` | 16 域（含各域 api/job 切片） | ✅ | ✅ | ✅ 仅 job |
| `shop-merchant` | merchant | ✅ | ✅ | ✅ 仅 job |
| `shop-settle` | settle | ✅ | ✅ | ✅ 仅 job |
| `shop-app` | —（装配 · 全局 config · profile · 架构与场景测试） | ✅ | ✅ | ✅ |

**一份 jar 含全部六个工程**；profile 决定装配哪些 `api/` 切片、起不起 HTTP、
跑不跑 `job/`。所以「装进哪份部署」是运行时装配问题，不是工程划分问题——
这正是三份部署能共用一个构建产物的原因。

## 十、微服务拆分剧本

拆分单元 = **一个业务工程**。四个阶段，每阶段列清楚「改什么、不改什么」。

### S1 · 角色部署（上生产即做）

| 改什么 | 三个 `SecurityFilterChain` 加 `@Profile`；job 调度器加 `@Profile("worker")` |
|---|---|
| **不改** | 全部业务代码 |
| 产出 | api（公网）· ops（内网）· worker，同一 jar |

### S2 · settle 独立（接真实分账时）

| 改什么 | ① settle 加自己的启动类；② `SettlePort`/`FeeRatePort` 的**实现**从进程内换成 RPC client（接口不动）；③ 网关把 `/biz/settle/**` `/ops/settle/**` 路由到新服务 |
|---|---|
| **不改** | settle 内部全部代码；调用方（core/merchant）全部代码——它们一直只认 `spi` 接口 |
| 数据库 | **先共库**（共享库的微服务，过渡形态）；确认无跨域 join 后再分库 |

### S3 · merchant 独立（商家量上来）

同 S2。额外一步：`AccountProvisionPort`（入驻派生商家账号）由同事务改**异步补偿**
——这是 merchant 唯一一处跨域强一致点，必须先解决。

### S4 · 业态独立（某业态成事业线）

把 `catalog/<业态>` + `fulfillment/<业态>` 两个包拎成工程。
主干留守，业态通过扩展点注册——**扩展点接口从第一天就是将来的 RPC 边界**。

### 让"拆分不改业务代码"成立的四条规则

拆分之所以只是搬工程，全靠这四条从第一天就被 ArchUnit 强制：

| 规则 | 拆分时兑现的收益 |
|---|---|
| 跨域只走 `spi` Port/Event | 换 RPC 实现即可，调用方零改动 |
| 一个事务不跨域（例外显式登记） | 拆库时不会冒出分布式事务 |
| 域包互不 import | 搬工程时不会拖出一串依赖 |
| 交易用**下单快照**，不 join 实时表 | 拆库后订单页不需要跨服务查询 |

**反过来说**：任何一条被破坏，对应的拆分动作就从"搬工程"退化成"重构"。
这是这四条规则值得在单体阶段就严格执行的全部理由。

> `shop-core` 主干**永不拆**——它就是单体本体。真到了要拆它的规模，
> 域包边界一直干净着，按包再分即可。
> 拆分的终点是 **1 主干 + 2~3 个卫星服务**，不是十几个微服务。

## 十一、关键实体的归属（用户 · 实体 · 门店 · 商品 · 订单 · 资金）

| 关注点 | 归属 工程.域 | 关键约束 |
|---|---|---|
| **多端用户** | core.`identity`（三池 + RBAC） | 三池无互指列；跨池仅入驻一条路；凭证校验在 channel |
| 用户资产（双积分·卡包） | core.`asset` | 用户侧负债；与 settle 的主体侧积分池分账本 |
| **经营主体**（入驻·进件） | **merchant** | 进件按主体（收付通按执照发号，硬约束） |
| **门店** | **merchant** | 自提点挂门店；库存按门店；评价归门店 |
| 子账号/员工授权 | **merchant**（角色）+ core.`identity`（账号） | 账号在 identity，授权关系在 merchant |
| **商品** | core.`catalog`（主干 + 业态包） | 主干表禁长业态列；库存策略化 |
| **订单** | core.`trade`（主干）+ core.`fulfillment`（履约段） | 双写 `merchant_no`(结算键) + `store_no`(履约键)；商品/商户信息用**下单快照**，禁 join 实时表 |
| 售后 | core.`aftersale` | 独立状态机；按判责比例回退分账 |
| **资金/支付** | channel（支付通道）+ **settle**（账务） | 支付**渠道**在 channel，支付**单与账**在 settle |
| **结算** | **settle** | 只面对「已完结订单」；业态与客户端均不可见 |
| **提现** | **settle** | 主体维度；进件未激活不可提现 |
