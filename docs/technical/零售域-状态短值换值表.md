# 零售域 · 状态短值换值表

状态：初版（2026-11-27），供 [TDD §2.9](TDD-零售域对齐门店交易库.md) 使用。用户 2026-11-26 定：状态取值改成不超过 10 个字符的短值，列宽不放宽。
范围：门店交易库 `n_trade` 与行业库 `n_industry` 中所有 `varchar(10)` 的状态列，共 80 列；表的去向按[方案与表清单](零售域-第二段建议方案与表清单.md)。

## 1 怎么扫的、靠得住到什么程度

- **扫描来源**：后端主代码与三个插件。
  - Java 里对状态字段的赋值、比较、查询条件、`switch` 分支、实体常量；
  - SQL 文本里 `status`、`state`、`phase`、`stage` 的等值与 `IN` 条件；
  - 状态类枚举的常量。
- **结果**：在这 80 列能找到的取值共约 260 个，其中超过 10 个字符的 76 个。排除不在范围内的之后，**要换值的有 57 个**，另有 1 个去向待核（第 3 节）。
- **可能漏掉的**：取值经方法参数一路传进 SQL，或者由运行时拼接出来的，扫不全；例如 `AWAITING_RECEIPT` 就是作为参数传进更新语句的，靠人工补上。
  所以 §2.9 的要求不变：**每个子模块切换前，加一条「库里不存在超长旧值」的检查**，检查到的新值按第 2 节的规则补进本表。
- **为什么不查数据**：没有读线上库，表里只有代码里出现过的取值。迁移前要在要迁的库上跑一遍 `SELECT DISTINCT status`，和本表对账。

## 2 短值规则

1. **不超过 10 个字符**，全大写，用下划线分词。
2. **沿用设计已定的写法**（`字段设计的待确认事项.md` §5.1）：`TO_PAY`、`TO_CONFIRM`、`DOING`、`TO_CLEAN`、`HANDED`、`PART_RFD` 等。
3. **「等待某事」一律写成 `TO_<动作>`**：`WAIT_*`、`WAITING_*`、`*_PENDING`、`AWAITING_*` 都按这条改（例：`WAIT_RETURN` → `TO_RETURN`）。
4. **常用缩写**：`CH` 渠道平台、`OFF` 线下、`RFD` 退款、`BIZ` 门店业务、`DEC` 已决定、`RCPT` 收款回执、`REQ` 已申请。
5. **同一列里不能撞值**。跨表意思相同的，合成同一个写法（见第 4 节）。
6. **只改取值，不改含义**；本来不超长的取值不动。

## 4 合并的同义写法

| 短值 | 合并了 | 说明 |
|---|---|---|
| `RETURNING` | `RETURNING`（零售售后）、`RETURN_IN_PROGRESS`（渠道售后） | 都是「退货中」，并入同一张售后表后用一个值 |
| `TO_FUND` | `WAITING_FUNDS`、`WAITING_FUNDING` | 都是「等平台资金」 |
| `TO_DECIDE` | `WAITING_DECISION`、`WAITING_ORIGINAL_DECISION` | 在不同的列，含义相同 |
| `TO_STOCK` | `WAITING_STOCK`、`STOCK_PENDING` | 在不同的表，含义相同 |
| `DEC_COMMIT`、`DEC_CANCEL` | 服务单与权益占用两处同名值 | 写法照旧统一 |

## 5 不在本表的超长值及原因

| 取值 | 原因 |
|---|---|
| `RETURN_REFUND`、`REFUND_ONLY`、`ACTIVITY_ONLY`、`MERCHANT_OWNED`、`SERVICE_EXECUTION`、`CONSIDERATION`、`FUNDING_PLAN`、`BUSINESS_PRE_TAX` | 是类型、来源、阶段列的取值，新表这些列是 16–32 宽，放得下 |
| `DUPLICATE_PAYMENT`、`LATE_PAYMENT`、`RECEIPT_MISMATCH`、`MANUAL_REQUIRED` | 收款异常的原因类型，进 `ord_payment.exception_reason`，不是状态列 |
| `POINTS_CONFIRMED` 及积分各阶段（`CASH_PENDING`、`CASH_AUTHORIZED`、`ZERO_AUTHORIZED`、`COMPENSATING` 等） | 积分表去支付库 |
| `REQUOTE_REQUIRED` | 结账操作账本的阶段，结账操作改走公共幂等 |
| `RECOVERY_REQUIRED` | 下单意图表不再建 |
| `RELEASE_REQUIRED`、`RECEPTION_CHANGE` | 美业接待操作账本，改走公共幂等与统一审计 |
| `REVERSAL_PENDING` | 餐饮生产耗用，归库存库 |
| `ABORT_DECIDED` | 旧券闸门，迁移期代码，切换前下线 |
| `ACKNOWLEDGED`、渠道网关枚举里的 `PLATFORM_PAID` 等 | 渠道技术表或接口返回值，不入交易库 |
| `RELEASED_NO_EFFECT`、`WITHDRAWN_*` 等 | 方法返回结果，不落库 |

## 6 落地要点

- **字面量收口（2026-11-27 已做）**：58 个值在交易与行业相关源码里的 218 处 Java 字面量、65 处 SQL 字面量改成引用所属表的常量（注解 SQL 的文本块里用 `'${@全类名@常量}'`，拼接的 SQL 里拼常量）；插件与交易核心之间传的值，常量放在 spi 接口上（`IndustryOrderPort`、`IndustryFulfillmentPort`、`ManualServiceAdmissionPort`），交易实体引用它们。守卫 `RetailStatusLiteralGuardTest`：这些值只准在所属常量上写字面量。打印、积分、券与权益、商户开户、生产耗用与库存里的同名值不在范围。
- **状态值只从枚举或静态常量取（用户 2026-11-27 定）**：
  - 每个状态列有且只有一个定义处：有状态机的用枚举（落库存 `name()`），简单的用实体上的 `public static final String`。短值只写在这一处。
  - Java 代码里不再出现状态字符串字面量：赋值、比较、查询条件都引用枚举或常量。
  - 注解 SQL 里的状态值：用 `#{}` 传参，或者用编译期常量拼接（`"... status='" + OrdSubOrder.TO_FULFILL + "'"`）；不手写字面量。
  - 现状：本表 57 个超长值在后端主代码里有 12 处常量声明，却有 267 处 Java 字面量、79 处 SQL 字面量。换短值时顺带收口：先把字面量改成引用常量，再改常量的值，这样一处改值、全处生效。
  - 守卫：加一条源码检查，交易库、行业库实体的状态列不允许出现字符串字面量（同 `ModuleTxManagerConventionTest` 的做法，按行扫）。
  - 三端同理：状态值放在共享的常量文件里，页面和筛选项引用常量。

- **改动面**：58 个值（含待核 1 个）里，三端用到的只有 9 个：`WAIT_FULFILL`、`WAIT_OFFLINE_PAY`、`WAIT_RECEIPT`、`ARBITRATING`、`WAIT_RETURN`、`APPROVAL_PENDING`、`CANCEL_PENDING`、`NOT_REQUIRED`、`DISPATCHING`，共约 80 个文件，集中在订单与售后的状态展示和筛选；其余 49 个只改后端。
- **跟子模块走**：每个值跟着所在子模块在分支上改，后端常量、SQL 字面量、DTO、三端常量、筛选项、文案键一起改，三端各跑一遍 `vue-tsc`。
- **迁数据**：旧值按本表换成短值；迁移脚本对每一列先查 `DISTINCT`，遇到本表没有的超长值就停下，不能截断。
- **契约**：这是对外取值的变更。提交要写明改了哪些值；三端不能先于后端发版。
