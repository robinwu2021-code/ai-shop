## 0. 判据怎么来的

**两个方向都要扫，只扫一边会漏掉一整类问题。**

```bash
node scripts/check-ops-contract.mjs      # 运营端调了 → 后端有没有
node scripts/gen-perm-endpoint-matrix.mjs # 端点真源（scanEndpoints）
```

```bash
node scripts/check-ops-orphan.mjs        # 后端有   → 运营端调没调（本次新加）
```

三条命令都跑完才算对过。**只扫一边会漏掉一整类问题**，而漏掉的那一类更难发现：
「画了没后端」在切真后端时会立刻 404；「做了没入口」不报任何错 ——
它表现为「这个功能我们做过啊」，而运营点不到。

> 反向脚本是本次一并写的，已接进 `pre-push`，基线在
> `ops-web/known-orphan-endpoints.txt`（只准变短）。
> 写的时候归一化顺序踩了个坑：`${x}` 必须先于 `{x}` 替换，
> 否则 `/a/${no}` 会归一成 `/a/$*`，凭空多报 7 条 —— 手工扫的 18 条正好帮我逮到了它。

## 2. 后端有、运营端无出口的 18 条

### 2.1 结算与资金（13 条）—— 这一组是重点

| 端点 | 是什么 |
|---|---|
| `GET /ops/payables` | 自营应付账款列表 |
| `POST /ops/payables/{settleNo}/confirm` | 确认对账 |
| `POST /ops/payables/{settleNo}/no-invoice` | 标记无票供应商 |
| `POST /ops/payables/{settleNo}/paid` | 登记已付款（网银流水号）|
| `GET /ops/purchase-invoices` | 进项票列表 |
| `POST /ops/purchase-invoices/{invoiceNo}/verify` | 核验 |
| `POST /ops/purchase-invoices/{invoiceNo}/reject` | 驳回 |
| `GET /ops/invoice-requests` | 商家开票申请列表 |
| `POST /ops/invoice-requests/{requestNo}/issued` | 标记已开 |
| `POST /ops/invoice-requests/{requestNo}/reject` | 驳回 |
| `GET /ops/finance/invoice-title` · `POST` | 开票抬头配置 |
| `GET /ops/payments/recon-coverage` | **对账覆盖范围说明** |

**结论：缺的不是功能，是出口。**

整条「自营应付 + 进项票 + 销项开票」链路后端已实现（10 个端点），运营端一个入口都没有。
而这条链是今天**唯一真的能把钱付出去**的路 —— 第三方那条走分账，而分账网关是桩
（见 [PRD-商家资金到账与对账](../../requirements/PRD-商家资金到账与对账.md)）。

> 换句话说：**平台今天付得出去的那条路，只能靠人直接调接口。**

`recon-coverage` 那一条单独说：`ReconService.coverage()` 的类注释写着
「页面照它显示提示条，否则『今天没有差异』是句假话」——
**而那个接口今天没有任何调用方**，所以那句假话一直挂在页面上。

### 2.2 其余 5 条（非本域）

| 端点 | 影响 |
|---|---|
| `PUT /ops/admission/pay-quota/{merchantNo}` | 商家收款额度用尽时改不了 |
| `GET /ops/scene-channel` · `POST /ops/scene-channel/{scene}/{audience}/{channel}` | 触达配置，属另一条线 |
| `GET /ops/order` | 订单总览；运营端走的是别的入口，可能是重复能力 |
| `POST /ops/community-pool/resync` | 社区池重算，运维动作 |

## 3. B 端的对照缺口

同一套判据对 B 端扫一遍，结论更极端：

| 域 | 后端接口 | B 端页面 |
|---|---|---|
| 积分 | `/biz/points/account` · `/records` · `/toggle` | **0 个** |
| 收入到账 | `/biz/settle/bills` 有，但只给「商家实得」一个数 | 只有结算单列表 |
| 收款账户 | `/biz/payment/**` | 有页面，但不说明进件未完的后果 |

积分那一行最要紧：**积分开关是「商家自己开」的，而他看不到自己发分花了多少钱** ——
让人在看不到代价的情况下做决定。

按「让看不见的变得看得见」排，不按功能大小：

   ⚠️ 我在原型与前一版清单里把它列成缺口，那是**只看链路没看代码**得出的结论，已订正。

## 5. 这份清单怎么维护

**不要手工更新数字。** 手工清单第二周就会漏 —— 这也是界面清单不手工列的理由。

§0 那三条命令是真源，这份文档只是它们的注解：
数字变了就重跑一遍抄过来，**结论与优先级才是这份文档要维护的东西**。
两个基线文件（`known-mock-endpoints.txt` / `known-orphan-endpoints.txt`）
都由 `pre-push` 盯着只降不升，所以数字不会悄悄变大。
