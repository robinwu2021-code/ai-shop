# 幂等设计规范

> 状态：规范正文（2026-11-11起用于新增及修改的写链路）；存量按触及范围收敛，不代表运行时代码已全面改造。
> 适用：零售、餐饮、美业及共享业务。本文是幂等设计的唯一规范正文。
> 输入校验、异常处理和增量验证沿[Java规范§八](../../../.claude/skills/ai-shop-dev-standards/references/java.md#八简洁实现框架校验与增量验证2026-10-30-用户确认)，不重复定义。

## 一、总览：参数、数据库、服务端三层约定

同一次业务操作重复提交，只产生一次业务效果；重复请求能够返回原结果或明确的执行状态。不同的真实业务操作仍须分别执行，不能因参数相同就被误去重。

| 层面 | 统一约定 | 实际落点 |
|---|---|---|
| 参数传递 | 同次操作沿同一请求键、同一业务单号及原参数重试 | 既有请求DTO、Idempotency-Key、内部命令号 |
| 数据库设计 | 用唯一约束标识请求/业务效果；业务变动与执行记录同事务 | 原业务表、流水、命令日志及现有通用回执表 |
| 服务端规范 | 统一校验范围和摘要、原子执行、冲突恢复及原结果返回 | 既有Service、事务、执行器或业务状态机 |

普通写操作按这三层约定落地，不逐接口设计专用防重流程。查询及无持久副作用的计算不增加幂等记录；已有条件更新/状态机足以保证效果一次发生时，直接复用。需要返回首次创建结果时才补请求回执；长期资金、库存等效果仍保留业务唯一身份。

## 二、参数传递规范

### 2.1 最小参数约定

| 参数/上下文 | 规则 |
|---|---|
| 请求键 | 外部关键写操作沿现有 Idempotency-Key；内部调用复用已有稳定 commandNo/operationKey 等，不强制再造HTTP头。一次操作生成一次，重试不变，两次真实操作各用自己的键 |
| 业务单号/源单身份 | 使用真实订单、售后单、核销单或源单行标识。同一业务效果换了请求键，仍受该业务身份约束；已有单号足以唯一标识操作时，不另加同义参数 |
| 业务参数 | 原金额/币种、数量/单位、目标原件、版本等原样重试；服务端以稳定摘要核对同键同内容 |
| 可信范围及操作人 | 从现有登录和授权上下文取得，不能由body选择商家、门店或账本；操作命名空间由服务端固定 |
| expectedVersion（如原合同需要） | 用于并发控制，不代替幂等键；已完成原请求的回执恢复不因当前版本变化而重新执行业务 |

新增关键写入口缺必需键时由现有框架校验拒绝，不能落到旧执行器的“无键直接执行”。不修改原键原文，不截断或trim。多个HTTP别名执行同一命令时沿同一业务命名空间，不借改URL绕过去重。

### 2.2 同键同参数

请求摘要覆盖会改变业务效果的字段，使用明确字段顺序或稳定类型化快照，长度分帧复用 IdempotencyScope.requestHash。金额沿既有整数最小单位，十进制精确传递；数值尺度、数组顺序、空值/缺省值是否等价由所属DTO合同确定，不猜测式归一化。

摘要不混入重试时间、随机数、访问令牌或实时配置。摘要/回执格式升级沿旧版本或原快照恢复，不用新DTO重算旧摘要，也不删除旧键放行。现有无摘要旧行沿原合同查回，随链路修改明确兼容边界。

客户端只在确需跨超时/重启恢复时保存原键、原body及原范围，不为每个页面建立队列。精确数量不通过 JS Number 重算；切店/换账号不能把旧请求发入新范围，也不能把原账号的回执显示到新范围。

## 三、数据库设计规范

### 3.1 用既有表和唯一约束，不先查再插保证唯一

| 需要去重的对象 | 逻辑唯一身份 | 说明 |
|---|---|---|
| 一次请求 | 可信范围 + 稳定动作 + operationKey | 现有 sys_idempotent 以 idem_key+endpoint 唯一，范围编码复用 IdempotencyScope；业务命令表已有等价约束时直接使用 |
| 一个长期业务效果 | 真实原单/子行 + 明确效果类型等 | 由领域定义；不能只有一个随机请求键。例如退款按实际售后单/退款操作去重，不能只按订单号吞掉第二张真实售后 |
| 一条源补货行 | 来源系统 + 来源业主 + 源单号 + 行号 | 不把本应唯一的源行按目标门店、行业或接入代次拆成多个身份；需要拆分时先定义稳定子行合同 |
| 一次事件应用 | 稳定来源事件号 + 稳定消费者名 | 复用 EventIdempotency 或已有业务记录；换事件号的同一业务效果仍由业务唯一身份约束 |

实际索引沿所属表设计，不为上述每一行都新建表。请求键/业务身份的组成列不得利用可空值绕过唯一性；主体级动作使用真实主体范围，不为满足店级模板伪造门店。键的长度、大小写及排序规则与合同一致，不能靠截断拼接生成身份。

范围示意：业务命令表可用 `UNIQUE(tenant_no, entity_no, store_no, action, operation_key)`；已有 `UNIQUE(idem_key, endpoint)` 且endpoint编码了真实范围的通用执行器无需再加同义索引。两者是按场景选择的落点，不要求同一动作重复记录两套。

跨入口、跨行业或跨数据库的同一业务身份，由唯一业务所有者的原件/认领接口裁决。各库分别建立同名唯一索引不能保证全局唯一。执行者与账本沿原件冻结，策略切换不能让原操作换一个所有者重新执行。

### 3.2 变动、流水与结果同事务

本地业务效果、业务原件/状态、必要流水、请求执行记录及成功回执在原数据源同一事务提交。失败整体回滚，不先独立提交“已处理”再执行业务。数据库唯一约束裁决并发，余额、版本和状态继续使用原子条件更新；不能把影响行数为0当成执行成功。

有返回首次结果需求时，沿现有回执保存请求摘要、原操作人、稳定业务引用及结果；不需要接口响应的事件不强制保存resultJson，也不为普通状态设置新增完整命令日志。字段由已有表承担，不要求统一物理表结构。

资金、库存、积分、券等效果的业务身份保留周期覆盖其可重放周期。通用接口回执的24小时过期时间不能解除业务唯一约束；归档后仍能按原身份查证，不能因重开开关、重跑任务或清理回执而重新计账。

## 四、服务端执行规范

### 4.1 普通本地写入的标准过程

1. 通过既有接入边界取得身份、权限及真实范围，完成请求格式处理，生成稳定动作命名空间与摘要。
2. 在调用方原业务事务内，使用现有执行器或业务命令日志抢占请求身份。预先查询只用于查回，不替代数据库唯一约束。
3. 同键、同范围、同内容且已完成，返回原结果；同键不同内容拒绝。首次执行才处理本次业务状态及实际写入，原请求查回不依赖草稿、当前配置或远程服务仍可重算。
4. 业务变动、流水及回执同事务提交。提交成功但响应丢失时，原键重试只返回原回执；当前业务状态另查，不把历史回执覆盖到当前对象。

使用 IdempotencyService 时，由调用方事务覆盖其插入、Supplier内本地写入及结果更新；该类自身不创建业务事务。已有业务日志完整承担相同职责时，不再套通用请求日志。已有唯一约束和事务足够时，不再叠加Redis锁、新拦截器或专用防重服务。

唯一键冲突后只按对应幂等身份查回，其他唯一键冲突不能当作成功。失败事务结束后再按原键查询/重试，回查须能观察已提交结果，不沿旧MVCC快照误判；并发异常本身不是成功证据。必要锁与既有编辑/交易链路统一锁序。

### 4.2 仅在实际需要时补充的业务规则

| 适用场景 | 补充规则 |
|---|---|
| 累计收货/退仓 | 沿既有累计合同锁原件，`本次增量=目标累计量-已完成累计量`；相同目标为0，倒退/超界拒绝，累计量与余额、流水同事务。独立现金缴款等动作不因金额相同就合并 |
| 远程写入 | 沿既有业务意图/任务保存原远程号，必要时先落本地意图，再在本地锁事务之外调用原客户端；目标按原号幂等，本地事务不能保证远程效果一次发生 |
| 远程结果未知 | 按原号查询，或仅按目标明确支持的幂等合同重发；无幂等且无法核对的远程写入不能自动换号重做，沿既有人工核对流程 |
| 在途操作必须可停止 | 只有业务确需时复用原命令永久封存；封存与执行竞争同一身份，原执行先成功则返回真实结果，不能撤销已发生效果。客户端删除队列和TTL不构成封存 |
| 事件消费 | 消费标记与本地业务效果共用事务；不承担远程效果一次性保证，不与短期接口回执混表清理 |

“当前未见提交”不证明没有请求在途，必须沿原键；“处理中/未知”不能当失败、空结果或成功。上述是语义，不要求每个执行器都新增UNKNOWN/CANCELLED枚举、状态查询端点或恢复队列。

重试由一个明确执行者负责，不让App、客户端、Service和任务各自重试。Outbox沿Java规范§八的使用边界，不因幂等统一新建通用投递层。退款、晚到款等实际处置仍由原业务规则负责，通用幂等层不决定是否恢复订单或追回款项。

## 五、设计登记与验证

在原业务TDD按三栏登记即可；已有等价内容直接引用，不另写专用幂等方案，不给纯查询套卡片。

| 参数 | 数据库 | 服务端 |
|---|---|---|
| 原请求键/业务单号、可信范围、摘要字段 | 复用的表与唯一约束、原子提交内容、保留周期 | 复用执行器/状态机、结果查回、事务及必要锁序、实际验证证据 |

普通复用场景引用已有实现即可。需要远程恢复、跨库认领或封存时，才在原TDD补相应语义；不为每个接口重新设计一套状态机。

通用执行器、摘要算法的同键回执/异参冲突/范围/并发/回滚/兼容机制集中验证，修改这些能力才运行受影响用例，各业务复用已有有效证据。业务只验证实际接线与自身不变量：换请求号后的业务去重、两次真实操作均执行、金额/数量/累计差额、反向效果、实际库存池等。不能用共用执行器测试替代业务效果约束，也不逐域复制同一套通用测试。

MySQL 9唯一键、当前读、回滚和锁序需要真实原生证据，不能只用mock调用次数或H2替代。测试次数及证据复用沿Java规范§八；不另建通用测试框架或每批重跑所有幂等场景。

## 六、现有能力与实施边界

| 现有位置 | 已有能力 | 不能假定已有的能力 |
|---|---|---|
| [IdempotencyScope](../../../backend/shop-base/src/main/java/ai/neargo/shop/idem/IdempotencyScope.java) | 原键校验、带范围的稳定操作命名空间、长度分帧 SHA-256 | 不负责鉴权、业务字段规范化、数据库事务或永久业务去重；endpoint 当前面向 MAIN，未提供独立 tenant 参数 |
| [IdempotencyService](../../../backend/shop-store-mybatis/src/main/java/ai/neargo/shop/idem/IdempotencyService.java) | 唯一键抢占、操作人校验、带摘要重放、结果快照、findCompleted | 缺键的旧调用会直接执行；旧重载/旧行摘要可空；方法自身不创建业务事务；expireAt 声明24小时，不是长期业务身份，也不代表到时自动删除或自动允许重做；没有通用 UNKNOWN/封存状态机 |
| [EventIdempotency](../../../backend/shop-store-mybatis/src/main/java/ai/neargo/shop/idem/EventIdempotency.java) | 事件号+消费者去重；标记与本地业务共用 REQUIRED 事务 | 不保存接口响应；不承担远程写入的一次性保证；不与24小时接口回执混表 |
| [FoodStockReplenishmentPortImpl](../../../backend-plugins/shop-industry-food/food-core/src/main/java/ai/neargo/shop/food/port/FoodStockReplenishmentPortImpl.java)及既有业务命令/台账 | 原请求快照、长期原件去重、本地原子效果、原键查询及按需封存 | FOOD实现不是三行业共享执行器；零售真实收货接线仍待I04-D2，不能复制类后宣称统一完成 |
| [App补货原请求恢复](../../../b-app/src/shared/replenishment-command.ts) | 按原范围保存完整请求、原键、精确数量，查询后恢复 | 当前为补货实现，不是已供所有页面使用的通用 SDK；客户端本地记录不能替代服务端唯一约束 |

新增普通请求优先使用现有带摘要执行器；需要长期业务日志时优先复用本域日志。确需共用代码扩展，在原归属模块扩展，不在业务包复制 IdempotencyService、散写摘要算法或另建同义防重表。共用算法的持久化适配仍沿各域原技术栈和数据源。


本次仅规范正文与入口引用收敛，没有新增通用执行器、表、迁移、前端SDK或状态接口，不批量改存量键、hash、回执和TTL。共用能力确有缺口时在原模块补齐一次，沿实际影响验证，不预先建设万能幂等平台。

I04-D2按上述三栏登记并接入既有补货原件/命令语义，真实零售余额、源行跨入口认领及旧回写互斥仍是该批业务职责；D1观察不构成写授权。其他域随已授权任务触及收敛，不因本文启动全仓改造。业务TDD只保留自身差异，不维护平行通用规范。
