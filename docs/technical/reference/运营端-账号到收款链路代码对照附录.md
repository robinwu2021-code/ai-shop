## 2 哪些属于电商/经营，哪些属于支付

| 对象或动作 | 业务权威 | 对方可以做什么 |
|---|---|---|
| 平台入驻、经营主体、门店资料、行业与经营类型 | ai-shop 经营基础域 | near-pay 核验来源并保留授权快照/映射；不反向任意改经营主体 |
| 管理空间、品牌连锁、主体归属、经营组织授权 | ai-shop 组织域 | 支付侧引用明确的组织/主体授权，不另造一套可编辑经营品牌主档 |
| 商品品类、SPU/SKU、库存、经营订单及履约 | ai-shop 电商/经营域 | 支付侧处理收款和退款事实，不维护商品和库存 |
| 主体额度套餐、门店经营套餐、售卖目录与权益履约 | ai-shop 商业服务/commerce | 支付能力提供记账事实；不把套餐购买当作渠道开户 |
| 支付平台商户、支付资料版本、来源关联、支付成员 | 独立 near-pay | ai-shop 发起授权申请、展示摘要和办理入口，不代替支付成员授权 |
| 渠道进件、私有材料、渠道账户、商户凭据、开通审核 | 独立 near-pay | ai-shop 按正式桥接合同转发或显示安全摘要，不复制敏感真源 |
| 门店渠道绑定、收款政策、产品可用性和收款就绪 | 独立 near-pay | ai-shop 根据支付权威回显；不由本地申请状态推导支付能力 |
| 电商售后/套餐退款业务决策 | ai-shop 相应订单域 | 支付能力执行/核验退款，不能绕过权益与订单复核 |
| 支付交易、渠道执行、资金流水及退款执行事实 | 支付域 | ai-shop 回读支付结果并继续业务履约，保留原订单与支付单关联 |

**部署形态另行区分**：ai-shop 仓库中仍存在宿主装配的 `backend/pay` 组件，例如平台套餐线下核款使用的 `PlatformOfflineLedger`。它们属于支付能力，但并不因此等于独立 near-pay 的支付平台商户/渠道进件已经接通。目录中的“支付开立”按独立 near-pay 链路处理；套餐核款入口继续跟随套餐订单业务。

**支付对象再分两层**：支付平台商户管理来源、成员与支付资料；渠道收款商户/渠道账户管理某渠道下的 MID 等收款身份。平台 merchantNo 不等于渠道 MID，一个平台商户可以关联多个渠道账户。“支付开立”指支付服务及渠道收款开通，不表示代商户开立银行账户。

**编号不能混用**：经营主体 `entityNo`、经营门店 `storeNo` 与支付商户 `merchantNo`、支付门店编号须按来源关联解析。同名字段不代表编号可直接互换，不能仅凭名称或字符串相同自动关联。支付侧内部物理 ID 和租户约束按当前实际接口/表结构处理。

本次沿用 [ADR-043](../ADR/ADR-043-进件与收款商户归支付域.md) 中的支付归属与无默认号兜底边界，同时区分该 ADR 描述的渠道收款子模型与后续增加的独立支付平台商户模型。不能将其中“新表无 tenant_no、按 BIGINT 关联”机械套用到所有上层平台商户表；当前 `PlatmchStore` 实际使用 `tenant_no`、`merchant_no` 及来源关联。也不能反过来要求所有旧渠道表统一改成该形状；本次盘点不改库或重定义编号规则。

## 4 办理链路

1. 选择已验证的经营 owner/主体，或代填平台入驻申请；新店可按既有分阶段规则先建立资料与 FREE，不能为了画流程改掉快速建店政策。
2. 补齐门店市场、行业、经营类型和必要资质，完成对应平台审核；检查真实门店归属及主体权限。
3. 如是品牌连锁业务，再办理管理空间、品牌法人和关联门店；独立单店跳过这一步。
4. 申请支付服务并取得独立支付商户及来源关联，办理来源核验、资料修订和支付成员授权。
5. 在 near-pay 进行渠道草稿、私有材料、补件、商务审核/冻结送审和渠道结果处理；本人签约等须由真实授权人完成。
6. 核验渠道账户、凭据、产品与门店绑定，读取支付侧能力和具体不可用原因。
7. 总览分别展示经营准入、套餐权益、支付进件与门店收款状态；任一域故障显示未知/不可读，不用空数组、旧看板或另一域的成功代替。

各步骤按当前业务准入和渠道规则执行，不额外设定统一的强制审核顺序。尤其：入驻通过≠支付服务开立，支付商户存在≠渠道已开，渠道送件成功≠此门店已绑定且可收款；购买 PRO/CHAIN≠创建品牌组织或开通渠道账户。
