## 1. 产品定位与范围

本系统服务平台运营人员：配置平台、查看SaaS用户及门店/连锁数据、审核门店和支付商户、代购套餐、核款及处理订单异常。不是各SaaS用户日常经营的后台，不把上架、排班、出餐、盘点、营销等全套经营功能复制进来。

沿用户指定顺序整理，并将第三个父菜单建议更名为客户管理，作为后续梳理顺序：**平台设置 → 平台商城 → 客户管理 → 商户管理 → 订单中心**。本版替代上一轮16个一级的经营后台式方案，不再以“原151个入口都必须继续出现在主侧栏”为前提。

- 门店日常经营由SaaS经营方完成；平台以门店列表为中心，查看数据并办理授权的门店审核、套餐代购及开通跟踪。经营主体/品牌/组织关系主要只读关联，不铺开商家日常维护功能。
- 商户专指支付平台商户。平台导航可统一提供商户审核、渠道/费率维护和支付查询入口；后台仍调用权威服务，不在ai-shop复制支付商户、进件或支付事实。
- 平台商城是平台向SaaS经营方销售套餐、软件、硬件等服务商品；不是SaaS门店向消费者销售的商品库。
- 注册账号是SaaS用户账号；运营账号是平台工作人员；支付成员、连锁成员各有业务授权，不能互相替代。
- 本方案只定义目标目录和职责；当前41个三级入口不表示已有41个可用页面。实际路由/API、状态、权限和数据范围须确认后逐项核对。

## 3. 各模块内容

| 一级 | 平台运营要完成的事 | 页内内容与边界 |
|---|---|---|
| 平台设置 | 配置地区、业务规则、渠道、费率、运营权限及运行参数 | 地区配置包含默认地区及对应语言/币种/单位等；业务配置包含行业、经营类型、通用商品/资质规则。支付产品可在渠道详情呈现。渠道成本、支付商户费率、平台经营服务费率分别展示和授权，不混成一份费率事实。 |
| 平台商城 | 维护平台销售的套餐/商品，统一购买订单、代购、核款、退款及平台收入 | 主体/门店套餐保留各自模型；售价和版本在对应详情。收入仅统计平台销售及退款事实，不将门店营业额或顾客支付总额计入；按币种展示收款、退款与净收款。 |
| 客户管理 | 管理SaaS用户、平台会员及门店/连锁关联数据 | 门店列表继续承担审核/套餐代购与经营查看；平台会员一份统一列表，展示来源门店，关联品牌/连锁及其他门店在详情查询。会员与SaaS经营者身份不按名称/手机号强并。 |
| 商户管理 | 代建支付平台商户、填写/提交资料、审核及收款开通跟踪 | 商户列表内提供新建、代填、草稿、提交、补件等入口，具体API/权限待核对。使用支付域权威资料和流程，不复制商户主档或私有材料。 |
| 订单中心 | 监控SaaS经营订单和支付记录，办理授权异常/售后 | 平台商城购买订单已移出，避免两个同名订单中心。经营单与支付单仍分模型，按真实关联查询，不将两类交易总额算作平台商城收入。 |

经营概况可在首页或客户管理中展示，不新增工作台一级。所有角色登录后进入有权访问的入口，不强制无设置权限的人进入设置。

## 4. 关键平台场景

1. **查看用户统计：** 客户管理→用户会员→用户数据，查看用户数量、新增趋势及关联门店/连锁明细，包含未建店账号；具体字段和统计口径确认后对齐。
2. **基于门店办理：** 客户管理→门店连锁→门店列表，按门店查看或审核；选择套餐代购后复用商城报价、线下核款及履约，购买并履约成功后，同时自动通过对应门店审核并开通。
3. **查看连锁统计：** 客户管理→门店连锁→连锁数据，查看连锁/品牌数量、关联门店数量及分布，不维护组织和授权。
4. **协助商户开通：** 商户管理→商户资料→商户列表，授权运营可新建商户、代填资料、保存草稿、提交审核/补件；平台审核、渠道送件及后续签约/绑定仍分阶段办理。
5. **帮助购买：** 平台商城→商城订单→运营代购，选择主体额度包或门店套餐，沿原报价、付款凭证、运营核款、履约及权益回读闭环办理。
6. **订单异常：** 分清平台商城、SaaS经营或支付侧问题，再进入对应工单；退款和权益回退不通过手工改最终状态代替。

| 原功能类别 | 本版处理 |

| 平台套餐、平台商品、权益、购买订单及收入 | 全部归平台商城；套餐价格/权益定义、实际订阅、销售/收退款统计分别展示 |
| 支付渠道、费率、商户及进件 | 统一平台导航；渠道费率在设置，支付商户及进件在商户管理；保留支付服务事实权威 |
| SaaS经营商品、库存、订单 | 经营监控与订单中心查看；日常经营写操作不默认纳入平台运营职责 |
| 零售、餐饮、服务业 | 作为门店业态及监控维度，不新增三个完整经营工作区 |
| SaaS采购、盘点、调拨、营销、排班、履约等 | 由其经营系统承担，本版不展开为平台侧一级菜单；明确需要平台代办的例外另定正式流程 |
| 原会员、营销、社区、风控、经营财务、内容等入口 | 不机械整批搬入新侧栏；确认后按“平台确需保留/合并进页内/详情关联/迁至经营端/暂不纳入”逐项列出处置表 |
| 审核待办 | 分布在门店审核、商户审核、核款审核等实际业务；本版不新增复杂跨域审核中心 |
| 原旧支付及兼容入口 | 在原路由、调用方和替代能力核对前保留；不因目标目录简化直接删除、隐藏或改链 |

旧入口技术处置表尚未逐项完成，本轮不声称已经把151个点全部迁移到新目录。也不以“平台运营能看全量”为由自动扩大现有角色或数据范围。

### 门店列表工作台（最新需求）

客户管理维持经营概况、用户数据、会员列表、门店列表、连锁数据五个入口；审核/代购/经营查看仍收敛到门店列表及详情。审核、套餐代购及经营详情都在门店列表/详情内办理，不再为每个动作新建菜单。

| 位置 | 展示与办理 |
|---|---|
| 门店列表 | 店名/编号、经营主体/连锁关系、业态/市场、经营审核状态、当前套餐、权益有效期与开通状态；按真实数据和范围筛选 |
| 审核入口 | 保留人工审核入口；购买套餐并履约成功后，由系统自动通过对应门店审核并开通，保留审核记录。经营审核与支付商户审核分开 |
| 套餐权益 | 当前套餐、有效期、权益来源、购买/履约结果；可代购，复用平台商城内同一购买/核款/履约业务流程 |
| 经营概况 | 当前门店经营指标；包含订单记录及营业统计，按时间/门店范围查询，不复制经营订单事实 |

**已确认的自动审核/开通规则：套餐购买并履约成功后，同时自动通过对应门店审核并开通。** 商家自行购买和平台代购走同一条后续链路。

```text
商家购买 / 平台代购
    → 创建购买订单
    → 完成付款及现有线下核款
    → 套餐履约成功
    → 自动通过对应门店审核 + 开通门店
    → 回读套餐权益、审核与开通结果
```

创建订单、付款待核实或履约失败时，不触发自动审核/开通；不以页面跳转当作已成功。自动动作针对订单明确关联的门店，不默认将同一经营主体的全部门店批量开通。主体包和门店套餐保留原模型，主体包涉及门店开通时必须明确适用目标；原免费/基础能力按既有规则核对。

人工审核入口继续保留；门店审核、套餐履约和经营开通由真实结果衔接，分别记录。代购、核款、审核权限及原处置规则在实现时逐项对齐；本条自动经营开通不替代支付商户进件审核或渠道收款开通。

用户/连锁数据以查询为主；门店商品/库存/营销/排班等日常经营操作仍不纳入。此前帮助建店的例外需求继续保留待确认，不自动扩大为整套经营维护后台。

原46项现网核查记录保留历史事实，本轮仅确认业务规则及方案，未验收或实现门店列表联动、自动审核和自动开通，也未部署。

### 本轮新增边界：平台收入、商户代办及平台会员

- **平台收入：** 套餐、软件、硬件等平台商城销售与订单统一归平台商城。未付款/待核款订单单列，不混成已收款；退款单列，净收款按真实收退款事实计算；不同币种分别汇总。门店营业额及支付平台全部交易金额不等于平台商城收入。收入概况/明细仍需整合，未声称已有独立上线页面。
- **商户代办：** 商户列表内提供新建、代填资料、草稿、提交审核和补件；渠道进件资料的提交与平台审核分开，不替代必须由真实授权人完成的签约。代理操作记录来源和操作者；是否已有完整动作链须在实施前对照支付服务API，不能由“商户列表已部署”推断全部动作可用。
- **平台会员（用户已明确）：** 门店/连锁产生的会员统一属于平台会员，以平台会员标识呈现一份会员列表；列表必须显示来源门店，可按门店/连锁筛选。一个会员与多门店的关联和来源记录在详情保留，不因后续消费覆盖入会来源，也不按姓名/手机号擅自合并账号。无门店来源时显示真实平台/其他来源或未知，不强造归属。
- **会员列表范围：** 显示基础资料、来源门店、真实关联的品牌/连锁、入会时间及必要状态；SaaS经营者账号和消费会员身份/权限仍按原模型关联。原会员名单页可作来源，新增来源字段、统计口径和筛选待对齐，不作为本轮已验收功能。

## 6. 确认后才进入实施

先确认上述五个一级、三级职责及平台/经营边界。确认后按设置、平台商城、客户管理、商户、订单顺序逐模块：场景→页面/API→权限与数据范围→数据库菜单覆盖及迁移→受限角色验收。
