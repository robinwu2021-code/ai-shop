## 一、核心模型：角色挂在「人 × 门店」上

这是 B 端与运营端最本质的差别。

| | 运营端 | B 端 |
|---|---|---|
| 角色挂在哪 | **人**身上（`sys_ops_staff`） | **人 × 门店**上（`mch_store_role`） |
| 唯一键 | 员工号 | `(mch_account_no, store_no, role)` |
| 一句话 | 「你是什么人」 | 「你在哪家店担任什么」 |

三元组唯一键不是冗余：**同一个人可以在 A 店当店长、在 B 店当配送员**，这是真实业务形态。

这个模型也决定了后面那条技术选择——见 §四。

## 二、六个角色

| 角色 | 定位 | 边界 |
|---|---|---|
| `OWNER` | 老板 | `*`，**不走权限表** |
| `MANAGER` | 店长 | 除「钱」和「人」之外都能干 |
| `CLERK` | 店员 | 到货、核销、发货、看单、改库存 |
| `PICKER` | 拣货 | 到货、改库存 |
| `COURIER` | 配送 | 发货、看单 |
| `CS` | 客服 | 回评价、处理售后、看得到那张单 —— **不碰货、不碰钱** |

## 三、三条判定规则

**① `OWNER = "*"` 不是「拥有全部权限点」，是「不走这张表」**

新增权限点时 OWNER 自动有，其余角色需要显式加。
反过来做（把 13 项逐个列给 OWNER）的后果是：上一个新功能，老板被锁在外面，
而他是唯一能给自己授权的人 —— 死锁。

**② 多角色取并集，不取最小**

源码注释原话：「老板给一个人同时勾了店员与配送，他要的就是这个人两样都能干。」
取交集或取最小是那种「看起来更安全」的聪明做法，但它把老板的显式意图判成了错误。

**③ 空角色 = 零权限，不是「零权限 = 全放行」**

`BizPerms.can` 对空集合直接返回 `false`。
这条要单独写出来，是因为「空即无限制」是权限系统里最常见的一类漏洞
（本项目在类目授权码那里做过同样的判断：空 = 没有任何特许类目，**不是**不限制）。

## 四、判权链路

```
登录 → userNo
  ↓
查 mch_store_role：这个人在【当前门店】持有哪些角色
  ↓
BizPerms.permsOf(roles)  ——  多角色取并集
  ↓
@PreAuthorize("@perm.canBiz('biz:xxx')")
  ↓
DataScope 拦截器按 entity_no / store_no 再收一道
```

### 为什么不用 Spring Security 的 `hasAuthority`

**因为 B 端的角色带门店维度，装不进 `GrantedAuthority`。**

`authorities` 是会话级的、没有「当前是哪家店」这个维度；而同一个人在 A 店与 B 店
的权限本来就不同。用自定义的 `@perm` bean，才能在判权那一刻把 `storeNo` 纳入计算。

代价是判权逻辑离开了 Spring Security 的标准位置 —— 所以下面那几条守卫必须存在。

### 三层，不是两层

**认证 → 授权 → 数据范围**，第三层最容易被忽略：

- 授权回答「你能不能调这个接口」
- 数据范围回答「你能看到哪些行」

`DataScopeRegistration` 注册了哪些表按哪个维度收窄（`ord_sub_order` → `SELF:user_no`、
`prd_goods` → `MERCHANT:entity_no` …），由 MyBatis 拦截器改写 SQL。

> ⚠️ **跨属主的查询必须显式 `DataScopeContext.executeWithoutScope`**。
> 本项目在这上面栽过两次：核销的写路径（不豁免则 UPDATE 影响 0 行，
> 接口返回成功而订单纹丝不动）、日累计限额的读路径（不豁免则「该商家当日成交额」
> 被改写成「**该买家**在这家店的当日成交额」，限额实际成了「每买家一份」）。
> 两次的共同点：**没有任何报错**。

## 五、拒绝的表达方式

**一律 HTTP 200 + 业务码**，不是 HTTP 403（全站约定，测试里按业务码断言）。
但**码有两个，不是一个**：

| 情形 | 业务码 | 给用户的话 | 代码位置 |
|---|---|---|---|
| **不是商家** | `10403` | 「没有操作权限」—— 他该去入驻 | `canBiz` 返回 false → Spring `AccessDeniedException` |
| **是商家，但角色不够** | `70006` | 「你在这家店没有这个权限」—— 他该找店主 | `canBiz` 直接抛 `BIZ_ROLE_FORBIDDEN` |

**为什么必须分开**（`PermChecker.canBiz` 里有完整论证）：B 端还有另一类 403 来自
**作用域**（这家店没有自提点、这单不属于本店）。两者撞同一个码时，
「权限没配对」与「数据不在范围里」在日志里长得一模一样，排查只能靠猜。

给用户的话也不一样：一个消费者误点进 B 端，若看到的是「找店主开通」——
而他根本没有店主。反过来，店员看到通用提示会去找店主要权限，
而 `70006` 里有相当一部分开关**设计上就不存在**（比如店长看账）。

> 写断言时按这张表选码。只断言 `10403` 的测试会在「角色不够」这条路径上全错。

## 六、守卫：这套不靠自觉

`BizEndpointPermTest` 四条，从「有没有想过」一路盯到「有没有真的落地」：

| 守卫 | 拦什么 |
|---|---|
| `everyBizEndpointHasADecision` | 每个 `/biz` 端点**必须**登记权限决定，漏了就红 |
| `noStaleEntries` | 登记表里不能留已删除的端点 —— 否则清单几个月后就烂了 |
| `allCodesExist` | 映射到的码必须真的存在于 `BizPerms`。**写错一个字母 = 那个端点对所有人永久拒绝**，而表现只是「按钮点了没反应」 |
| **`decisionsAreActuallyEnforced`** | 表里定了权限的，代码里必须真的有 `@PreAuthorize` —— **登记表是许愿，注解才是执行** |

第一条的价值在于：判权逻辑不在 Spring Security 的标准位置（见 §四），
**漏一个 `@PreAuthorize` 不会有任何症状** —— 那个端点就是裸奔的。
守卫把「有没有想过这个端点的权限」变成了硬性要求。

**第四条是这套机制真正的兜底**，也正是 §四 那句「代价是判权逻辑离开了标准位置，
所以下面那几条守卫必须存在」所指的东西：一张全绿但没落地的权限表，比没有表更危险 ——
它会让人以为已经防住了。

`BizEndpointPermTest.REQUIRED` 因此成了全项目**唯一一份被强制对过账**的端点权限清单，
`gen-biz-role-matrix.mjs` 与 `gen-biz-feature-perm-matrix.mjs` 都以它为准，
而不是去扫 controller 注解 —— 扫注解拿不到「这个端点是**有意**公开的」这类判断，
会把 PUBLIC 那一批全当成缺权限。

> 端点数不在这里写死。当前分布见
> [B端功能点-权限码-页面](./B端功能点-权限码-页面.md) 的统计行（受控 / 登录即可 / 任一权限）——
> 写死的数字每加一个端点就过期一次，而没有任何东西会提醒你。
