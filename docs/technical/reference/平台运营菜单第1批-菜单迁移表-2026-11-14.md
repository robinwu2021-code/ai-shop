## 2. 迁移原则与目标入口

- 先搬已有入口，再补能力；没有目标接口的入口不创建可点击空页。
- href、point_code、ui_perm_code、perm_code及ACTION/MENU类型作为独立信息保留。页面合并不合并权限，菜单迁移不授予写权限。
- 前端结构来自nav.ts，数据库覆盖文案/排序不会自动把叶子换父级。后续必须同步导航、菜单数据与生成物；本批没有运行会写生成物的脚本。

## 4. 必须单独验收的差异

1. 线上三个入驻功能点均为`/merchants`，UI及后端权限分别是审核、代办、自营建档。当前源码仍保留`?tab=on-behalf`/`?tab=self-operated`导航；迁移不得只取href字典的最后一条来判所有动作授权，也不能据源码认定线上有三个独立页面。
2. 旧`merchant:*`涉及经营主体，不能改名后当成支付平台商户授权。`/merchants?tab=chain`是经营漏斗画像，不承接连锁组织列表；`/members`不承接SaaS注册账号列表。
3. `/products`是经营分类/规则，`/mall?tab=categories`才是平台商品分类；门店经营商品、库存、营销等保留原入口，未明确处置前不得因本版侧栏简化而丢失。
4. 套餐商城多数commerce权限由SQL配置，不在Perms.java默认角色列表。FINANCE岗位名不能证明已持有核款/退款权限；主体套餐与商城套餐动作按各自控制器鉴权。
5. 目标收入视图、平台会员来源字段、全注册账号及连锁查询仍有功能缺口；会员归平台不等于允许绕过原脱敏/数据域或按同名同号合并。
6. 独立支付源码/快照与ai-shop兼容路由分开核对。支付独立资料变更、流水、退款页的未开放状态保留，不能扩大live白名单当成功能交付。
