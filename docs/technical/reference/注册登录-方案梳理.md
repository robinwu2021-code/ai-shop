## 一、一句话说清这套设计

**一个人一个账号,认证方式是挂在它下面的凭证。**

```
                 ┌── openid   （微信小程序 / 开放平台）
usr_account ─────┼── unionid  （同主体下多个微信应用是同一个人）
（user_no 唯一）  ├── phone    （短信验证码 / 密码）
                 └── apple_sub（iOS 三方登录，App Store 强制）
```

主干只有一条,是因为**「同一个人从小程序和 App 进来必须是同一个账号」**——
每种登录方式各建一套用户表,这个保证立刻消失
（`AuthService` 类注释）。

## 二、三端各自能用哪几种（真实现状）

授权类型由端上传 `grantType`，后端 `AuthServiceImpl.credentialsOf()` 分发。

| 端 | 可用方式（按顺序） | 出处 |
|---|---|---|
| **C 端 · 微信小程序** | `WX_MINI`（静默）→ `PHONE_OTP` | `shared/ports/auth.ts` `#ifdef MP-WEIXIN` |
| **C 端 · App** | `PHONE_OTP` → `WX_OPEN` → `APPLE`（仅 iOS） | 同上 `#ifdef APP-PLUS` |
| **C 端 · H5** | `PHONE_OTP` | 同上 `#ifndef` 分支 |
| **B 端（商家）** | `PHONE_OTP` → `PASSWORD` | 同上，`pwd` 仅 B 端注入 |
| **平台运营端** | 用户名 + 密码（**独立体系**，不走 usr_account） | `/ops/auth/login` |

**`APPLE` 不是可选项**：App Store 规定，只要提供了第三方登录，就必须提供 Sign in with Apple。

## 三、「注册」这件事：除密码外，全是登录即注册

拿到一个稳定标识就开账号，**没有独立的注册页**——中间那一步没有信息增量。

唯一的例外是 **`PASSWORD`**：能用密码登录的前提是他**已经**设过密码，而设密码本身要先登录。
所以这条路上「查无此人」与「没设过密码」都必须明确报错，
不能悄悄建一个空账号——那会把「密码打错」变成「你的店不见了」（`AuthService.GRANT_PASSWORD` 注释）。

因此密码**不能是 primary**：新商家第一次来必须走验证码那条。
端上用 `GET /biz/auth/has-password` 决定要不要显示「密码登录」入口。

## 四、B 端：登录页不问「你是老板还是店员」

2026-08-15 拍板：**后端按身份判**，不让人先选。

理由不在于少点一下，而在于**他可能选错，而选错的表现是「进去什么都看不到」**——
那看起来像系统坏了，不像选错了。

判法：拿请求里的**原始手机号**（不是登录结果里那个打过码的 `185****8359`）去查 `mch_account`；
查得到是店员，查不到就按消费者账号找它名下的主体。

> ⚠️ 这条**推翻了** [B端功能测试用例](../design/B端功能测试用例.md) TB-B-1-2 里「做成显式切换」的写法，
> 那条用例该改了。

## 五、会话

| 项 | 现状 | 出处 |
|---|---|---|
| 有效期 | **30 天** | `TokenStoreConfig.TTL` |
| 存储 | `memory`（默认）/ `ehcache`（单实例）/ `redis`（多副本） | `shop.auth.token-store` |
| 续期 | `POST /mp/user/token/refresh`，**旧 token 立即作废**（rotation） | `MpUserController` |
| 登出 | `POST /mp/user/logout`，服务端作废 | 同上 |
| 强制下线 | 停用/改角色时 `revokeUser` 直接踢会话 | `TokenStore` |
| 401 分两种 | `10401` 未登录 · `10402` 登录已过期 | `ApiAuthEntryPoint` |

**`10401` / `10402` 必须分开**：一个让人重新登录，一个让人去找老板要权限，下一步动作完全相反。
（联调原缺陷就是把过期说成了「没权限」。）

**默认 `memory` = 重启即全员掉线**，只适合测试；线上单实例应当用 `ehcache`。
→ **待办 1**：确认生产的 `SHOP_TOKEN_STORE` 值，现在是默认值的话每次发版所有人被登出。

## 六、验证码的四道闸

| 闸 | 规则 | 能不能关 |
|---|---|---|
| 有效期 | 5 分钟 | — |
| 发送频率 | `shop.otp.rate-limit`（60 秒间隔等三条） | 可关（测试用） |
| **连续失败** | 15 分钟内 5 次 → 锁 | **永远开着** |
| 密码登录失败 | 15 分钟内 10 次 | — |

`shop.auth.otp.fixed`（预设码）**是一把能登进任何人账号的万能钥匙**：
设了之后任何人都能用它登录**任意手机号**，且不再走短信通道。
自动化 e2e 需要它，所以它存在；也正因为如此，它必须绑死在 `--server.address=127.0.0.1` 上。
→ **待办 2**：加一条启动期守卫——`otp.fixed` 非空且监听地址不是回环时**拒绝启动**。

| 1 | 生产会话存储 | 默认 `memory`，重启全员掉线 | 单实例改 `ehcache`，上多副本前不用碰 redis |
| 2 | 固定码的启动守卫 | 只靠人记得 | 加守卫，见上 |

| 6 | 运营端与消费者账号的关系 | 两套完全独立 | 保持独立。运营账号由管理员创建、邮件投递初始密码、首登强制改密 |

> **待办 5 是提审阻塞项**，不是可选项。微信对「有账号体系的小程序」要求提供注销入口。

## 八、一眼看懂的流程

```
新用户（小程序）
  wx.login → code ──POST /mp/user/login {grantType:WX_MINI}
                     └─ code2Session → openid
                        ├─ 命中 openid  → 老用户，发 token
                        └─ 没命中       → 建号（登录即注册），发 token

新商家（B 端）
  手机号 + 验证码 ──POST /biz/auth/login {grantType:PHONE_OTP}
                     ├─ 原始号命中 mch_account → 店员，进他被授权的门店
                     ├─ 名下有主体             → 老板，进经营台
                     └─ 都没有                 → 新用户，跳入驻申请页

运营
  用户名 + 密码 ──POST /ops/auth/login
                   └─ 首登 mustChangePassword → 强制改密
```
