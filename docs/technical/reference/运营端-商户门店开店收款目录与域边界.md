## 1 ai-shop经营运营端（修订方案待确认）

入口：`https://nearshop.umeshop.ai/ops-shop/`。商户专指支付平台商户，撤回原“账号与商户/商户中心”的经营聚合。账号管理、经营主体、门店管理、品牌连锁分别组织；经营诊断归工作台，信用与违规归风控。

商品、订单、服务购买、进销存及其他经营模块各守原事实源；门店详情只关联收款摘要和支付域办理入口，不另建平台商户主档。完整一级/二级/三级以[最新方案](./运营端-完整三级菜单-2026-11-13.md)为准。

## 2 near-pay支付运营端（修订方案待确认）

入口：`https://nearshop.umeshop.ai/oms/`。平台商户、渠道进件、支付交易、渠道配置、资金结算归支付域；平台商户、渠道商户/MID及收款门店分别识别。品牌连锁经营组织不转交支付端管理。

本地源码49个目录、8个源码live项保留全部映射，不因此声明所有能力已上线。本轮仅改方案，确认前不改导航、权限、API、数据库或部署。

以下保留的代码路径及历史业务名仅作为现状证据；旧merchantNo/mch等命名不自动等于修订后的支付平台商户。

## 3 从全部注册账号开始

| 对象 | 代码现状 | 目录处理 |
|---|---|---|
| 应用注册账号 | 有 `usr_account`、`usr_identity`，商户账号另有 `mch_account`；未见完整全量账号 OPS 页/API | 优先补“注册账号”列表和详情，按真实账号类型关联，不按同名或手机号自动合并 |
| 会员与人档 | `/members`、`/ops/members`、`/ops/persons/{personNo}` | 是会员关系及人档，不能代替全部注册账号 |
| 运营员工 | `/iam` 与运营 staff/role | 是后台操作人员，放系统设置，与应用注册账号分开 |
| 支付成员 | near-pay 商户工作区及 `/merchant-members` | 是支付授权关系，不能代替全平台注册账号 |

账号查询必须从真实账号出发，覆盖已注册但未入驻、无主体、未建店、仅有员工身份等情况；不能从商户或门店内连接反推。一个账号可关联多个身份、主体和门店。

建议列表字段：账号类型/编号、脱敏联系方式、注册时间/来源、状态、身份、关联商户与门店数、入驻及支付开通摘要；支持筛选未入驻、未建店、未完成开通。全量可见性按正式账号权限与数据范围实现；不因没有门店关联而漏掉新账号。注销记录按原保留策略展示，注册本身沿用现有认证流程，不新增人工审批门槛。

## 4 优化“商户商城”及对应对象

建议经营端统一名称为 **经营服务**，明确是平台向商家提供订阅、工具和硬件的入口；后台统一归入 **套餐与服务**，不再单列“商户商城”一级菜单。

| 对象 | ai-shop 目录 | 现有入口 |
|---|---|---|
| 主体额度包、门店经营套餐 | 套餐管理 | `/merchants?tab=plans`、`plan-defs` 与 `/mall` 方案目录；两套模型保持区别 |
| 平台向商家销售的服务商品、硬件、SKU | 经营服务商品 | `/mall?tab=products`、`categories` |
| 套餐/服务购买、运营代购 | 购买订单 | `/mall?tab=orders`、`assisted` 及主体包购买入口 |
| 线下核款、退款审核 | 订单内办理，审核中心汇总 | `/mall?tab=claims`、订单退款、主体包核款能力 |
| 门店经营订阅和功能权益 | 订阅与权益 | `/mall?tab=sources`、门店 subscription/entitlements；主体额度沿原主体模型 |
| 商家向消费者销售的商品/服务和订单 | 餐饮、零售、服务业 | 对应商品、经营订单与服务履约能力，不与平台服务购买单混表 |

服务业消费者的次卡/服务权益与门店购买的软件功能权益分开；积分、储值余额也不等同于门店套餐权益。平台套餐收款档案是“平台收商家服务费”，商户渠道结算账户是“商家收顾客的钱”，两者分开维护。

## 5 按实际页面归并与保留缺口

| 调整项 | 实际目录/代码依据 | 实施边界 |
|---|---|---|
| 账号、商户、门店、品牌 | `/merchants`、`/stores`、`ops-web/lib/nav.ts` | 注册账号和完整品牌/连锁 OPS 入口待补；`chain` tab 是经营诊断，`/stores` 是店招/主页治理，不能冒充已有组织或门店工作台 |
| 三业态入口 | 共用 `/products`、`/orders`、`/inventory`、履约售后等能力 | 当前 nav 没有完整三业态分组；整理和补接入口，不重写业务引擎 |
| 套餐与服务 | 原 `/mall` 八个 tab 和主体套餐页 | 改分组与名称，保留不同的套餐、价格版本、订单、退款及权益语义 |
| 运营管理、经营财务、系统设置 | 原商品、会员、营销、积分、内容、消息、社区、风控、`/finance`、`/iam`、`/system` | 不删除原功能或深链；商品品类与经营账号/入驻分开，基础行业字典与支付渠道行业也分开 |
| ai-shop 审核中心 | 现有各业务待办及审批动作 | 统一聚合页待补，写入仍调用原业务审批，不建替代所有领域的“总审核”状态机 |
| 支付商户/门店/进件 | ME01 `/merchants`、ME02 `/merchants/stores`、ME03 `/merchants/onboarding-review` | 保留来源核验、支付成员和真实数据范围；网页路径相对 `/oms` |
| 支付交易/资金结算/审核配置 | TR、FI、ME、RC、OP、SY 原页面和能力 | 按真实 live/stage/权限开放，不把原型或接口存在当作已上线闭环 |

菜单实施同步静态 `nav.ts`、服务端 `/ops/menu` 覆盖层、菜单增量迁移、i18n、生成目录和权限测试。目录重排不扩张角色权限，不改已部署历史 SQL/checksum。

## 6 审核和资金归属

| 事项 | ai-shop | 支付运营端 |
|---|---|---|
| 账号注册、入驻、主体、门店、品牌 | 账号查询与经营审核、组织和经营资料权威 | 校验来源和支付授权，不替代平台入驻 |
| 支付进件、开通 | 发起、转发、回显摘要与办理跳转 | 私有材料、补件送审、渠道账户/凭据、收款绑定 |
| 餐饮/零售/服务订单 | 业务订单、履约、售后与业务审核 | 支付订单、交易流水、退款执行及事实回读 |
| 套餐购买 | 套餐商品、购买单、核款入口、退款业务、权益履约 | 支付能力提供记账事实；宿主内嵌组件不等于独立 near-pay 开户链路 |
| 经营及资金结算 | 业务应收应付、商户经营账单 | 渠道清算、资金流水、商户结算及真实出款到账 |

两端均包含审核。工作台/审核中心汇总待办，原业务保留审核详情与操作，继续遵守录入/审核职责分离。平台入驻通过、套餐购买、渠道受理与门店收款就绪分别展示，不能互相替代。
