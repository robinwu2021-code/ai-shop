# 商品域 · 多行业对齐清单

> 状态：草稿 · **2026-08-28 修订**（与[商品域V2设计规格书](../design/商品域V2-设计规格书.md)对齐命名）· 创建 2026-08-28

> 可售时段挂 **listing** 不挂 goods）。本册的「标准名」列同步为 Collection / Availability Rule。
> **落点以规格书为准**，本册负责命名口径与术语层。
> 命名遵循：[全域命名基准](./全域命名基准.md)（五条原则 + 域前缀 `prd_` / `mch_`）
> 方案出处：[TDD-统一商品模型-三行业合并](../design/TDD-统一商品模型-三行业合并.md)

**这份清单回答一件事**：零售 / 餐饮 / 美业各自嘴里的那个东西，在系统里叫什么、落在哪、现在有没有。
**一行一个概念**，三行业在同一行上对齐 —— 不在同一行的，就是没合并的（§五）。

## 一 · 命名口径

沿用[全域命名基准](./全域命名基准.md)的五条原则，本册补两条商品域专用的：

| # | 口径 | 说明 |
|---|---|---|
| 6 | **英文名取行业标准词，不自造** | 选配项就是 `Modifier`（Square / Toast / Shopify 通用）；按重计价就是 `Catch Weight`；上菜顺序就是 `Course` —— 自造词会让对接 POS、ERP 的人多一层翻译 |
| 7 | **中文名取通用叫法，行业叫法只进术语层** | 表、列、API 一律用通用中文；「出品部门」「菜单分类」只出现在界面文案（§四） |

域前缀：商品本体与选品在 `prd_`；**工位属于门店经营资源，在 `mch_`**（原则 2：一域一前缀，跨域引用只经业务键）。

## 三 · 落点清单（按命名基准格式，待回填 §2.3）

| 中文 | 英文 | 表名 | 业务键 | 理由 |
|---|---|---|---|---|
| 门店陈列分组 | Collection | ⬜ `sell_collection` | `collection_no` | 与 `prd_topic`（平台陈列）正交：那是平台摆首页，这是商家摆自己的店。**owner_type 区分 PLATFORM/STORE，故归 `sell_` 售卖层而非 `prd_`** |
| 分组内商品 | Collection Item | ⬜ `sell_collection_item` | `(collection_no, goods_no)` | 关系表 = 两端实体 + 关系词（原则 5） |
| 可售时段 | Availability Rule | ⬜ `sell_availability_rule` | `rule_no` | 只控**可售**，不控价格、不控上下架 —— 与下架分开，否则「晚上自动下架」第二天没人上回来 |
| **门店选品**可售时段 | Listing Availability | ⬜ `sell_listing_availability` | `(listing_no, rule_no)` | ⚠️ **挂 listing 不挂 goods**：同一商品在 A 店午市卖、B 店全天卖，挂 goods 表达不了。一行都没有 = 全时段可售 |
| 选配项组 | Modifier Group | ⬜ `prd_modifier_group` | `modifier_group_no` | 行业标准词，不自造 |
| 选配项 | Modifier | ⬜ `prd_modifier` | `modifier_no` | 有加价的指向真实 SKU，金额链走既有 `ord_item` |
| 商品选配项组 | Goods Modifier Group | ⬜ `prd_goods_modifier_group` | `(goods_no, modifier_group_no)` | 组可复用（一个「辣度」给 30 道菜） |
| **出品工位** | **Station** | ⬜ `mch_station` | `station_no` | **归 `mch_` 不归 `prd_`**：它是门店的产出单元，与 `mch_resource` 同域；商品侧只存引用 |
| 门店选品 | Store Listing | `prd_store_goods` → ⬜ `prd_store_listing` | `(store_no, goods_no)` | 命名基准 §2.3 已列，本轮在其上加 `station_no` / `daily_quota` / `quota_reset` / `min_order_qty` |

## 四 · 术语层：标准名 ↔ 三行业叫法

表、列、API 一律用标准名；下表只用于**界面文案**，由门店的行业码选一套词条下发。

| 标准名 | 零售显示 | 餐饮显示 | 美业显示 |
|---|---|---|---|
| Store Display Group | 商品分组 | 菜单分类 | 项目分组 |
| Availability Window | 售卖时段 | 时段菜单 | 可约时段 |
| Modifier Group | 选购选项 | 做法 / 加料 | 加项 / 指定技师 |
| Station | 拣货分区 | 出品部门 | 服务区 |
| Prep Lead Time | 备货时长 | 出餐时长 | 服务时长 |
| Daily Quota | 每日限量 | 沽清份数 | 每日可约 |
| Minimum Order Quantity | 起订量 | 起售份数 | 最少人数 |
| Bundle | 礼盒装 | 套餐 | 疗程包 |
| Catch Weight | 称重商品 | 海鲜按斤 | — |
| Surcharge | 包装费 | 餐盒费 | 服务费 |

**词条是数据（i18n × 行业维度），不是代码分支。**
模型统一是给系统的，术语分行业是给人的 —— 混为一谈，要么模型分叉，要么商家看不懂后台。

## 五 · 不在同一行的：没合并的四条

| 需求 | 行业 | 为什么不合并 | 去向 |
|---|---|---|---|
| **上菜顺序 / 叫起** | Course / Fire | 餐饮 | 驱动**出品队列调度**；零售的发货优先级驱动**拣货波次**，下游完全不同。硬合并会得到零售永远为空且语义对不上的字段 | `prd_store_listing.course_seq`，**标注待观察**；第二个行业出现同构需求再提炼 |
| 可做该项目的人 | Staff Skill | 美业 | 是**员工能力**，不是商品属性 | `mch_staff_skill`（员工域） |
| 提前预约期 / 最晚可约 | Booking Lead / Cutoff | 美业 | 是**预约规则**，不是商品属性 | 门店配置（建议上收基座） |
| 连锁通兑范围 | Cross-store Redemption | 美业 | 是**门店覆盖 + 跨主体结算**问题 | 单独议题，成本在结算 |

**保留第一条不合并，是这份清单诚实性的检验点**：前十二项合并得很顺，第十三项硬凑就会破坏判据。

## 六 · 现状缺口与遗留

### 6.1 `duration_min` 与 `prep_lead_min` 必须二选一
`prd_goods.duration_min` 已存在（SERVICE 段，服务时长）。本轮引入的 `prep_lead_min` 是更通用的名字。
**两列并存就会出现「服务时长填 60、出餐时长填 30」而没人知道该读哪个。**
建议：**保留 `duration_min`、改用途注释扩到三行业**，不新增列 —— 改名的代价高于收益。**待确认。**

### 6.2 选配项与销售规格的边界
「大杯 / 中杯」是**销售规格**（进 SKU 矩阵）；「加珍珠」是**选配项**（独立订单行）。
判据：**会不会影响这件商品本身的成本与库存** —— 会 → 规格；不会 → 选配项。
判错的后果是 SKU 笛卡尔积爆炸，而规格库四层模型（V195）正是为避免它而做。
**这条判据要写进建品页的帮助文案**，不能只留在文档里。

### 6.3 不许复活的两个机制
- `prd_category.attr_template`：`@Deprecated`、全仓零读者、73 个类目零有值，注释明令「不要再往它上面建东西」；
- **通用属性袋**（自由 KV）：正是上一条警告的"第三套同类机制"。
本清单的每一项都有确定的表或列，**没有任何一项落进自由 KV**。

### 6.4 兼容
新增 6 张表 + 8 个加列，全部「**一行都没有 / 列为 NULL = 旧行为**」：
无分组、全时段可售、无选配、无工位、不限量、无起订、渠道价缺省 `ALL`。
**存量 73 个类目与全部存量商品行为零变化** —— 与基座阶段 0 的验收标准一致。

### 6.5 加列的两条既有教训
**加列必须同步实体字段**，否则那一列永远读出 null（跑 entity-alignment 守卫）；
并行会话同时加迁移必然撞 Flyway 号，**改号后 `clean package`**。
