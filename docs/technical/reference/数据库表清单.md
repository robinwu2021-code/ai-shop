## 一、这次重建改了什么

46 个历史迁移收敛为 `V1__baseline.sql + V2__seed_master_data.sql` 两个文件，同时落地命名基准：

| 旧名 | 新名 | 键改名 |
|---|---|---|
| `usr_user` | **`usr_account`** | `user_no` 不变 |
| `usr_merchant` | **`mch_entity`** | `merchant_no` → **`entity_no`**（全库 26 张表统一） |
| `usr_merchant_payment` | **`mch_payment_merchant`** | 新增业务键 **`pay_merchant_no`**（旧库缺失，见 §四.1） |
| `usr_store` | **`mch_store`** | `payment_no` → `pay_merchant_no` |
| `usr_merchant_staff` | **`mch_account`** | `merchant_staff_no` → **`mch_account_no`** |
| `usr_staff_store` | **`mch_store_role`** | —— |
| `usr_merchant_apply` | **`mch_entity_apply`** | `merchant_type` → `legal_form` |
| `usr_merchant_community` | **`mch_entity_community`** | —— |
| `sys_merchant_subject` | **`sys_legal_form`** | `subject_type` → `legal_form`（mch_entity.type、进件表同步） |
| `sys_staff` | **`sys_ops_staff`** | `staff_no` 列保留（现在只有一个含义） |

列级同步改名：`merchant_name` → `entity_name`（订单快照列等）。
其余 48 张表**只有引用列改名，表名不动**。

## 二、表清单（按域）

「键」列 = 业务唯一键；`(a,b)` 表示复合键。审计八列（id/tenant_no/created_*/updated_*/version/deleted）不再赘述。

## 三、review 结论：改完后的自检

- **`merchant` 残留**：全库只剩两类 —— `mch_payment_merchant` / `pay_merchant_no`（基准允许的支付语境）与 §四的三条列级欠账。表名、索引名、约束名、表注释均已清零。
- **两套账号池不相交**：`usr_account` 与 `mch_account` 无任何互指列（`mch_account.user_no` 是历史过渡列，已允许 NULL，M-Auth 移除）。
- **`staff` 只有一个含义**：`sys_ops_staff`。商家侧的人在 `mch_account` + `mch_store_role`。
- **验证**：V1+V2 已在真 MariaDB 12.2 原样跑通（58 表、种子 7/3/2/25）；`gen-test-schema`（H2）与 `gen:erd`（58 表 · 108 关系）从同一真源生成；shared 守卫 142 全绿（键归属、血缘、实体对齐、词汇表）。

## 四、known 欠账（登记在案，不抢跑）

| # | 项 | 为什么现在不改 | 何时改 |
|---|---|---|---|
| 1 | `mch_payment_merchant.pay_merchant_no` 允许 NULL | 新键，进件成功才生成；存量进件回填后可收紧 NOT NULL | 进件链路动工时 |
