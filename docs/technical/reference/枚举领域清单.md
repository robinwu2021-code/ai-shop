# 枚举领域清单：按业务模块与领域对象逐个判定

> 2026-08-10 · 前置：[全系统枚举统一预定义方案](枚举统一预定义方案.md) 给的是机制，
> 这一份给的是**清单** —— 121 个枚举逐个归到领域对象上，判定哪些必须改名、哪些必须合并。

## 0. 判据

采纳一条硬规则，并把它推到两个方向：

> **一个领域概念在系统里只能有一个词；一个词在系统里只能指一个领域概念。**

由此产生三种缺陷：

| 代号 | 形状 | 后果 |
|---|---|---|
| **X 同名不同义** | 一个词指两个概念 | 读代码的人把一个当成另一个；类型「兼容」但语义不兼容 |
| **Y 异名同义** | 一个概念两个词 | 两处各自演化，改一处必漏另一处 |
| **Z 错层** | 概念本该是运营字典，却被硬编码成代码枚举 | 运营改不了；改了端上不认 |

三者同等严重。**Y 的数量远大于 X** —— 下面 §3 会看到「通过」这一个意思在系统里有 11 个词。

## 1. X 类 · 同名不同义（8 组，必须改名）

| # | 词 | 含义 A | 含义 B | 判定 |
|---|---|---|---|---|
| X1 | `SubjectType` | shared/capability：商家主体 `MICRO/INDIVIDUAL/ENTERPRISE` | ops/risk：风控主体 `USER/MERCHANT/DEVICE` | **A 侧删除**（见下） |
| X2 | `MerchantTier` | shared：经营规模 `SMALL/MEDIUM/LARGE` | ops/merchant：主体类型 `PERSONAL/INDIVIDUAL/COMPANY` | **B 侧改名** |
| X3 | `ApplyStatus` | shared/capability：**支付进件**状态 `NONE/APPLYING/ACTIVE/REJECTED/FROZEN` | ops/merchant：**入驻审核** `PENDING/REVIEWING/APPROVED/REJECTED` | **A 侧改名** |
| X4 | `MerchantStatus` | shared：B 端合并视图（经营×审核） | ops：库经营状态 `ACTIVE/SUSPENDED/FROZEN` | **A 侧改名** |
| X5 | `CampaignType` | shared：店铺级活动 | ops：平台投放场次 | **B 侧改名** |
| X6 | `CampaignStatus` | shared：店铺活动状态（含 `PAUSED`） | ops：平台场次状态（含 `SCHEDULED`） | 随 X5 一起改 |
| X7 | `AfterSaleType` | shared：2 值 | ops：多 `EXCHANGE` | 同义，一方多一个未实现值 → 删或标 PLANNED |
| X8 | `PayChannel` | shared：`WECHAT/ALIPAY` | ops：多 `BALANCE` | 同上 |

### X1 的特殊性：规则早就写下来了，没有守卫

`packages/shared/src/types/index.ts` 里 `MerchantSubject` 的注释白纸黑字写着：

> **不叫 `SubjectType`**：那个名字在平台端已经是风控主体（DEVICE/MERCHANT/USER）。
> 两个不同的概念同名，读代码的人迟早会把一个当成另一个。

——而 `packages/shared/src/capability/index.ts` 里就有
`export type SubjectType = "MICRO" | "INDIVIDUAL" | "ENTERPRISE"`，
**同一个包内，取值与 `MerchantSubject` 逐字相同**。

> 结论：**写下规则不产生约束力。** 这一条不是「补一条文档」能解决的，
> 必须是一条会让 CI 变红的检查。

### X2 / X3 的连带发现

- ops 的 `MerchantTier` 取值 `PERSONAL/INDIVIDUAL/COMPANY` 正是库里
  `sys_legal_form.legacy_subject` 那一列注明的**旧取值**。
  也就是说 ops-web 用**错误的名字**装着**过时的取值**。
- shared/capability 的 `ApplyStatus` 是**支付进件**状态（`MerchantPayment.applyStatus`），
  与入驻审核毫无关系。它的 `ACTIVE`/`FROZEN` 也印证了这一点 —— 审核不会有这两个态。

### 建议命名

| 现名 | 建议 | 理由 |
|---|---|---|
| shared `SubjectType` | **删除**，并入 `MerchantSubject` | 同包内重复，且违反已写下的规则 |
| ops `MerchantTier` | `MerchantSubject` | 与 shared 对齐；取值同时迁到权威码 |
| shared `MerchantTier` | 保留 | 它才是真的「规模」 |
| shared/capability `ApplyStatus` | `PaymentApplyStatus` | 它是进件不是入驻 |
| shared `MerchantStatus` | `MerchantWorkability`（或 `BizStatus`） | 它回答的是「我现在能不能干活」，不是主体状态 |
| ops `CampaignType/Status` | `PlatformSlotType/Status` | 它是投放场次，不是店铺活动 |

## 2. Y 类 · 异名同义（按领域对象）

### 2.1 履约（order / fulfillment）

| 端 | 名字 | 取值 |
|---|---|---|
| 库 / 后端 | `ord_sub_order.fulfillment` | `STORE_PICKUP` `NEIGHBOR_PICKUP` `MERCHANT_DELIVERY` `EXPRESS` |
| shared | `FULFILLMENT` | 上述 4 个 + `STORE_VERIFY` `APPOINTMENT` `INSTANT`（标 PLANNED） |
| ops-web | **`FulfillType`** | 上述 4 个 + **`SERVICE`** |

**两个缺陷叠在一起**：名字不同（Y），且 ops-web 多一个后端没有的 `SERVICE`（按它筛必空）。

> ⚠️ 我上一轮建的字段级对账工具**没抓到这条** —— 因为 `FIELDS` 表里
> 履约字段只登记了 shared，漏登了 ops-web。
> **登记表本身的完整性没有守卫**，这是那个工具的第一个已知盲区。

建议：统一为 `FulfillmentType`，ops 的 `SERVICE` 判定后删除或标 PLANNED。

### 2.2 自提点（community）

| shared | ops-web | 判定 |
|---|---|---|
| `PickupPointType` = `STORE/NEIGHBOR/PLATFORM` | `PickupType` = 同值 | 纯异名，统一为 `PickupPointType` |

### 2.3 商家主体（merchant）—— 四套名字

| 位置 | 名字 | 取值 |
|---|---|---|
| shared/types | `MerchantSubject` | `MICRO/INDIVIDUAL/ENTERPRISE` ← 权威 |
| shared/types | `MerchantType` | `= MerchantSubject`（已标 @deprecated） |
| shared/capability | `SubjectType` | 同值（X1） |
| ops-web | `MerchantTier` | `PERSONAL/INDIVIDUAL/COMPANY`（旧取值，X2） |
| c-app/api | `MerchantApplyType` | `COMPANY/INDIVIDUAL` |

**一个概念，五处声明，三套取值。** 且库里 `sys_legal_form` 是**字典表**
（带 `enabled`/`sort`/`wechat_code`/`need_license`），说明它本该是 Z 类（运营可维护），
现在被硬编码了五遍。

### 2.4 商品状态（product）

| shared `GoodsStatus` | ops `SkuStatus` |
|---|---|
| `ON_SALE` `OFF_SALE` `AUDITING` `REJECTED` | `DRAFT` `PENDING` `ON_SALE` `OFF_SALE` `REJECTED` |

同一件事：`AUDITING` ↔ `PENDING` 是同义异名；ops 多一个 `DRAFT`（草稿≠待审，合理）。
另外 SPU 与 SKU 是两个领域对象，但状态挂在哪一层需要先定 —— 这是模型问题不只是命名问题。

### 2.5 申诉（review）

| shared `ReviewAppealStatus` | ops `AppealStatus` | ops `BlacklistAppealStatus` |
|---|---|---|
| `PENDING` `UPHELD` `REJECTED` | `PENDING` `UPHELD` `DISMISSED` | `NONE` `PENDING` `ACCEPTED` `REJECTED` |

**同一个业务动作（申诉裁决），三套词**：
成立用 `UPHELD` / `UPHELD` / `ACCEPTED`，不成立用 `REJECTED` / `DISMISSED` / `REJECTED`。

### 2.6 类目形态（product）

`CATEGORY_TYPE`（`NORMAL/FRESH/SERVICE/VIRTUAL/CARD`）↔ `CategoryTemplate`
（`STANDARD/FRESH/SERVICE/VIRTUAL/VOUCHER`）—— 两个面，已在上一轮建了
`TEMPLATE_TO_CATEGORY_TYPE` 映射。**保留两者**（确是不同的面），但映射要有测试。

### 2.7 归因来源（growth / order）

| ops `TrafficSource` | shared 内联 `trafficSource` | ops `AttrSource` |
|---|---|---|
| `MERCHANT_OWNED` `PLATFORM` `INVITE` `CHANNEL` | `MERCHANT_OWNED` `PLATFORM` | `STORE_CODE` `INVITER` `CHANNEL` |

**三套**，且 `STORE_CODE`↔`MERCHANT_OWNED`、`INVITER`↔`INVITE` 是同义异名。
而 shared 那份还是**内联无主**的。

### 2.8 内容审核（content / review / store）

`PostStatus`（多 `OFFLINE`）· `ReviewStatus` · `StoreAuditStatus` —— 三个枚举，
核心三态 `PENDING/PASSED/REJECTED` **完全相同**。
这是「同一个概念被复制了三份」，不是三个概念。

## 3. 状态词汇：系统里已有一套隐含公约，但没写下来

这是本次分析最有价值的发现。把全部枚举的取值按语义归类：

| 语义 | 用了几个词 | 分布 |
|---|---|---|
| 通过 / 同意 | **11** | `PASSED`×3 `UPHELD`×2 `APPROVED`×2 `RESOLVED`×2 `SPLIT` `ISSUED` `SIGNED` `DELIVERED` `SUCCESS` `CONFIRMED` `ACCEPTED` |
| 待处理 | **10** | `PENDING`×12 `DRAFT`×6 `OPEN`×4 `APPLIED`×2 `SCHEDULED`×2 `AUDITING` `PLANNED` `CREATED` `PENDING_AUDIT` `QUOTING` |
| 结束 / 终止 | **7** | `ENDED`×4 `CLOSED`×4 `CANCELLED`×3 `EXPIRED` `OFFLINE` `HIDDEN` `VOID` |
| 生效中 | **7** | `ACTIVE`×6 `RUNNING`×3 `ON_SALE`×2 … |
| 拒绝 / 驳回 | **4** | `REJECTED`×14 `FAILED`×3 `DISMISSED`×2 `IGNORED` |
| 停用 | **5** | `SUSPENDED`×3 `PAUSED`×3 `FROZEN`×2 `OFF_SALE`×2 `LIMIT` |

**但这些数字会骗人。** 逐个看下去，系统里其实**已经存在一套自洽的公约**：

| 公约（隐含，从未写下） | 证据 |
|---|---|
| 审**内容**通过用 `PASSED` | `PostStatus` `ReviewStatus` `StoreAuditStatus` 三处一致 |
| 批**申请**通过用 `APPROVED` | `ApplyStatus` `WithdrawStatus` 两处一致 |
| **申诉**成立用 `UPHELD` | `ReviewAppealStatus` `AppealStatus` 两处一致 |
| 活动**到期**用 `ENDED`，单据**关闭**用 `CLOSED`，主动**取消**用 `CANCELLED` | 各 3–4 处一致，语义确实不同 |
| 草稿 `DRAFT` ≠ 待处理 `PENDING`（前者未提交） | 6 处一致 |

**所以真正的违规只有少数几处**，它们都是「没follow那条没人知道的公约」：

| # | 违规 | 应改为 |
|---|---|---|
| V1 | `BlacklistAppealStatus.ACCEPTED` | `UPHELD`（申诉成立） |
| V2 | `AppealStatus.DISMISSED` vs `ReviewAppealStatus.REJECTED` | 二选一，建议 `REJECTED` |
| V3 | `GoodsStatus.AUDITING` vs `SkuStatus.PENDING` | `PENDING` |
| V4 | `GroupStatus.PENDING_AUDIT` | `PENDING` |
| V5 | `PostStatus.OFFLINE` vs `QuestionStatus.HIDDEN` | 二选一（同为「不再展示」） |
| V6 | `TicketStatus/ReconStatus/RiskStatus/DemandStatus` 的 `OPEN` | 与 `PENDING` 语义重合，需判定是否合并 |
| V7 | shared `CampaignStatus.RUNNING` vs `CouponStatus.ACTIVE` | 同为「生效中」，二选一 |

> 结论：问题不是「词太多」——`DELIVERED` 和 `PASSED` 本来就该是两个词。
> 问题是**公约存在但不可见**，于是新写的人只能靠猜，猜中率大约 80%。
> 把它写成一张表 + 一条守卫，剩下 20% 就不会再发生。

## 4. Z 类 · 错层（本该是运营字典，却硬编码在代码里）

| 概念 | 现状 | 库里已有 | 判定 |
|---|---|---|---|
| 商家主体类型 | 端上硬编码 5 处 | **`sys_legal_form`**（带 enabled/sort/通道码/是否要执照） | **必须改走字典** |
| 行业 | shared `Industry` 硬编码 7 值 | **`sys_industry`** + 4 个 ops 接口 | 取值域硬编码尚可（准入规则已在表里），**但要确认是否会新增行业** |
| 售后原因 | shared `AfterSaleReason` 7 值 | 后端 `/mp/after-sale/reasons` 下发 | 端上应只作兜底，不作真源 |
| 资质码 | — | **`sys_auth_code`** | 已正确走字典 ✅ |
| 类目 | — | `prd_category` + ops CRUD | 已正确走字典 ✅ |
| 支付渠道 | shared/ops `PayChannel` | **`sys_pay_channel`** | 需判定 |

`sys_legal_form` 那张表带着 `wechat_code`/`alipay_code`/`need_license`/`settle_account_type`
四列业务规则 —— 这些规则会随通道政策变，而**取值域跟规则绑在同一行**。
端上硬编码五份取值，等于把一个会变的东西刻进了五个发布物。

## 5. 汇总清单

| 类 | 条目数 | 是否需要业务确认 |
|---|---|---|
| X 同名不同义 · 必须改名 | **8 组** | X5/X6 需确认（店铺活动与平台场次是否合并） |
| Y 异名同义 · 必须统一 | **8 组**（履约 · 自提点 · 主体 · 商品状态 · 申诉 · 归因 · 内容审核 · 类目形态） | 商品状态需先定 SPU/SKU 分层 |
| 状态词汇违规 | **7 处**（V1–V7） | V6 需判定 |
| Z 错层 | **3 个必改**（主体类型 · 售后原因 · 支付渠道待判） | 行业是否会新增 |
| 内联无主 | **24 个** | 否，纯机械 |
| 工具盲区 | **1**（FIELDS 登记表自身无完整性守卫） | 否 |

### 立即可做、无需确认的（按风险从低到高）

1. 删 shared/capability 的 `SubjectType`，并入 `MerchantSubject`（同包重复，零风险）
2. 24 个内联无主具名化
3. `PickupType` → `PickupPointType`（纯改名）
4. `FulfillType` → `FulfillmentType` + 判定 `SERVICE`（**这条现在就在坏**）
5. 给 `FIELDS` 登记表加完整性守卫：端上每个 A 类枚举都必须被登记
6. V1–V5、V7 状态词汇归一
7. shared/capability `ApplyStatus` → `PaymentApplyStatus`

### 需要业务确认的四个问题

1. **店铺活动与平台投放场次要不要合并成一张表？**（决定 X5/X6 是改名还是合并）
2. **`sys_legal_form` 的取值域会不会变？** 若会（通道政策调整），主体类型必须走字典下发。
3. **商品状态挂 SPU 还是 SKU？** 现在 shared 挂 SPU、ops 挂 SKU，两边都在用。
4. **`OPEN` 与 `PENDING` 是不是同一件事？** 工单/对账/风险/需求四处用 `OPEN`，
   若语义确为「单据开着待处理」，应并入 `PENDING`。

## 6. 命名公约（建议写进 CLAUDE.md，并配守卫）

1. **一个领域概念一个词，一个词一个领域概念。** 新增枚举前先查本清单。
2. **状态词按语义取词**（下表），不自创近义词：

| 语义 | 用词 |
|---|---|
| 未提交 | `DRAFT` |
| 已提交待处理 | `PENDING` |
| 内容审核通过 | `PASSED` |
| 申请审批通过 | `APPROVED` |
| 申诉成立 | `UPHELD` |
| 拒绝 / 驳回 | `REJECTED` |
| 生效中（主体、券、卡） | `ACTIVE` |
| 进行中（活动、团） | `RUNNING` |
| 到期结束 | `ENDED` |
| 单据关闭 | `CLOSED` |
| 主动取消 | `CANCELLED` |
| 暂停（可恢复） | `PAUSED` |
| 封禁（惩罚） | `SUSPENDED` |
| 冻结（风控/资金） | `FROZEN` |

3. **同一概念在两端出现，取值必须逐字相同**，且只允许一处声明（其余生成）。
4. **带业务规则的取值域（有字典表的）不得硬编码**，走接口下发。
5. **禁止在 interface 里内联字面量联合类型**（已定，需补守卫）。
