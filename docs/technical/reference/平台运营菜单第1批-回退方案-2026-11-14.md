# 平台运营菜单第1批：分批发布与回退方案

日期：2026-11-14。状态：回退设计完成，未执行发布、迁移或回退演练。本方案供第2批及后续批次发布使用；本轮无运行时改动需要回退。

## 1. 回退范围

每批只调整该批菜单位置、文案及已验收的页面接线，独立提交和发布，保留该批前端产物与菜单配置快照。菜单导航回退不撤销已发生的付款、退款、套餐履约、门店审核、会员来源关系或支付进件。业务状态异常按原恢复流程处理，不能通过改菜单、删除业务记录或改最终状态修复。

不全量恢复数据库，不重置工作区，不强推分支，不改历史Flyway SQL/checksum，不删除迁移历史。当前所有未提交改动继续保留，本批仅增加文档与证据文件。

## 2. 发布前必须保存的基线

| 类别 | 要保存什么 | 存放与作用 |
|---|---|---|
| 代码及产物 | 当前提交、待发布提交、构建摘要、静态发布目录、路由/basePath及旧资源保留策略 | 发布记录；前后端版本成对可追溯，不能只切数据库菜单 |
| 功能分区 | sys_function中OPS记录的主键/业务键、name、href、icon、sort、enabled、end_code、租户及删除标识等实际字段 | 私有完整快照；仅恢复本批确实改过的字段 |
| 功能点 | sys_function_point完整记录，含point_code、function_code、name、group_name、href、sort、类型、UI/后端权限、就绪与门禁 | 发布前后逐点比对，不仅导出菜单名称 |
| 角色与授权 | sys_role、有效sys_role_point，保留role/point/end/entity/tenant及删除状态 | 证明本批未扩权；不把个人账号或私有范围明细提交仓库 |
| 角色成员与数据范围 | 仅在受控位置保存必要快照/摘要，包括已有自定义角色、受控测试账号范围；支付侧独立保存映射与scope | 权限变化检查，不扩大读取业务数据范围 |
| 迁移历史 | flyway_schema_history版本/checksum/success/执行顺序 | 历史冻结；新增正向修复迁移使用执行时未占用的新版本 |
| 验收结果 | 按角色的可见href、后端权限集合、按钮、403及范围外结果；不可用页/门禁状态 | 对比每批前后，不能只凭全局菜单快照或超管截图 |

已有MenuSnapshot.java和verify_menu_migration.py可作为基础，但不是本轮直接执行的通用发布器：旧快照的functions字段未覆盖href/icon等，核对器带V658专用删除/合并预期及参数。后续涉及这些列时应先补采集范围；新批次须生成自己的精确变更清单及期望值，不能照搬旧版本号或移除点清单。

本轮[审计JSON](../evidence/ops-menu-batch1-20261114/audit.json)记录源码提交、文件哈希和复用证据来源，作用是可追溯来源，不是新采集的生产发布前备份。

## 3. 每批发布步骤及停止条件

1. 在隔离工作区完成本批调整，按“场景→路由/API→权限/数据范围→必要菜单迁移”逐项实现，不带入其他未提交工作。未经接通的能力不先上线空入口。
2. 采集本批前基线，制作逐point的变更清单，只允许申明的文案/分组/归属/排序变化；新增能力的权限设计单独审查。
3. 本地验证导航、tab、服务端覆盖、同href授权点、登录首屏和菜单请求失败回落；模拟受限角色与不可用能力，验证后端直接请求拒绝及数据范围。
4. 如涉及SQL，在MySQL 9隔离库执行迁移和重复启动验证；对比角色/成员/权限/门禁。没有明确授权变更的批次，角色权限集合变化必须为零；可见页面集合除申明替代项外保持。
5. 在隔离库按本批修复设计演练回退，再验证原菜单、深链、受限角色及服务端鉴权恢复。未经演练不把方案写为“已可回退”。
6. 通过后再安排单批发布；先部署相互兼容的版本，校验后切换入口。保持原链接及静态资源可访问；跨域入口还需核对会话、basePath和支付权限，支付H5域名不随运营菜单变更。
7. 回读数据库和实际菜单，记录前后差异及回退锚点；本批验收结束后才继续下一批。

遇到越权、授权丢失、数据范围扩大、已可用页面404、支付未开放页意外出现、审核/核款按钮混权时停止继续切流。预期的未实现能力继续受原限制，不作为“补齐菜单”强行开放。

## 4. 按故障类型回退

| 故障 | 操作顺序 | 完成判据 |
|---|---|---|
| 仅前端导航/文案问题，数据库未变 | 切回上一批已验证静态产物，沿既有资源策略保留旧资源，重载菜单 | 原链接、默认页、受限角色菜单恢复；业务数据不变 |
| 菜单数据库与前端不同步 | 暂停后续切换；保持或切回兼容前端；用新的正向修复迁移恢复本批指定字段，再回读 | 静态导航及服务端菜单一致；point、权限、门禁与前基线符合预期 |
| 意外改了授权 | 先限制受影响操作；依据本批实际差异修复受影响授权，刷新现有权限缓存并按既有机制处理会话 | 当前有效权限和scope回到批准基线；不能只回退前端藏按钮 |
| 独立支付入口接线失败 | 回退本批统一导航接线，保留支付原独立入口与已有兼容入口 | 不改变near-pay事实、H5、live页面限制与支付权限 |
| 已发生履约、审核或退款后发现菜单问题 | 仅回退导航/接线；业务状态按对应正式恢复流程处理 | 业务结果可追溯，无重复履约、重复出款、虚构审核或数据删除 |

正向修复迁移按业务键定位，仅恢复本批改动列；执行前比对当前值是否仍等于本批写入值。如同列已有其他会话/运营的合法修改，停止覆盖并合并差异，不整表还原。事务能力以实际表/语句为准，不能假定跨数据库、跨服务回退为一个事务。

## 5. 分批回退锚点与待执行验收

| 批次 | 需保留的可回退边界 |
|---|---|
| 第2批设置 | 原配置入口与原权限；不顺便调整收款资料及支付H5 |
| 第3批商城 | 两套订单与权益模型、原核款/退款动作；收入页面可独立回退 |
| 第4批门店 | 原门店档案/审核入口；已经成功的开通及权益不因导航回退撤销 |
| 第5批用户会员 | 原会员来源事实与脱敏范围；不回滚或合并会员身份 |
| 第6批支付商户 | 独立支付工作区与旧兼容入口各自保留；不回退渠道事实 |
| 第7批订单 | 原查询深链及售后入口；不撤销真实退款或修改订单状态 |
| 第8批收尾 | 每个隐藏/停用入口对应已验收替代入口及恢复方式；83条待处置项未决前保留 |

待执行的上线门禁：当前运行时角色/自定义角色/数据域采集；本批迁移及回退MySQL 9演练；受限账号真实登录与直接接口验收。这些均未在第1批执行，本轮未发布或连接166修改任何配置。
