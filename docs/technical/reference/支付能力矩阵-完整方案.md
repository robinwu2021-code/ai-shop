# 支付能力矩阵 · 完整方案

> 状态：**待决策** · 2026-08-06
> 上游：[主体选型](../design/收款与结算-主体选型.md) · [税务矩阵](./税务方案-主体与渠道矩阵.md) · [收款与分账总体逻辑](../design/收款与分账-总体逻辑.md)
> 目标（用户确认）：**三种主体并存 · 微信+支付宝双通道 · 为 App 生态留出空间**
> 优先级不变：**① 安全 ② 成本低 ③ 简单**
>
> 前一版曾裁决「一期只做微信」以省成本。**本版按用户要求改为双通道并行**——
> 相应的复杂度不再回避，而是靠一个统一抽象把它收进模型里。

## 零、这份方案要解决的真正问题

同时支持三种主体、两个通道、四个场景，组合数是 3 × 2 × 4 = 24 种。
**不能靠 if-else 铺开**——那是必然写错且改不动的写法。

核心做法：**把「谁能在哪儿收钱」建成数据，而不是代码里的分支。**

## 一、三个维度

### 1.1 主体（商家是什么）

| 主体 | 门槛 | 税务 | 开票 |
|---|---|---|---|
| `MICRO` 小微 | 身份证+银行卡+门店照，5 分钟 | 模糊，平台可能担扣缴责任 | ❌ |
| `INDIVIDUAL` 个体工商户 | 营业执照 | 经营所得，三项优惠叠加 | ✅ |
| `ENTERPRISE` 企业 | 执照 + 对公户 | 企业所得税，分红再缴 20% | ✅ 专票 |

### 1.2 通道（钱从哪家走）

| 通道 | 平台产品 | 二级商户主体 | 备注 |
|---|---|---|---|
| `WECHAT` | 收付通 | 小微/个体户/企业 | 主力 |
| `ALIPAY` | 直付通 | 小微/个体户/企业 | 口径待官方确认 |

### 1.3 场景（用户在哪个端）

| 场景 | 支付产品（微信） | 支付产品（支付宝） |
|---|---|---|
| `MINIPROGRAM` 小程序 | JSAPI | 小程序支付 |
| `H5` 浏览器 | H5 支付 | 手机网站支付 |
| `APP` | APP 支付 | APP 支付 |
| `OFFLINE` 线下码 | 付款码 / Native | 当面付 |

### 1.4 交叉后的可用性（微信侧，官方口径）

| | 小程序 | H5 | App | 线下码 |
|---|---|---|---|---|
| **小微** | ✅ | ❌ | ❌ | ✅ |
| **个体户** | ✅ | ✅ | ✅ | ✅ |
| **企业** | ✅ | ✅ | ✅ | ✅ |

**小微只被授权 JSAPI / Native / 付款码**——这是主体授权规则，不可协商。

## 二、核心抽象：能力是数据，不是分支

### 2.1 一个商家 × 一个通道 = 一条进件记录

**关键判断**：`sub_mchid` 不能是 `usr_merchant` 上的一列。
商家可能同时进件微信和支付宝，两边的商户号、进件状态、授权能力**各不相同**，
甚至主体类型都可能不同（微信进小微、支付宝进个体户）。

```
usr_merchant                    商家主数据（一个）
     │
     └── usr_merchant_payment   进件记录（每通道一条）
             channel            WECHAT / ALIPAY
             subject_type       该通道下的主体类型
             sub_mchid          二级商户号
             apply_status       进件状态
             pay_methods        该通道授权的支付方式（JSON）
             settle_account_*   结算账户信息（脱敏）
             invoice_capable    能否开票
```

> 【安全】把 `pay_methods` 存成**通道回传的实际授权结果**，而不是按主体类型推断。
> 推断会在规则变化时静默失效——「我们以为个体户有 App 支付」，
> 而实际进件时选的经营场景没勾 App。**以通道回执为准。**

### 2.2 可售性判断：一个纯函数

```
canPay(merchant, channel, scene) =
      进件记录存在
  AND apply_status == ACTIVE
  AND scene 对应的支付产品 ∈ pay_methods
```

这个判断要在**三个地方**用同一份实现：

| 位置 | 为什么 |
|---|---|
| 商品列表 / 详情 | 【安全】App 里根本不该展示付不了的商品 |
| 购物车结算 | 拆单前先按可支付性分组 |
| 下单接口 | 服务端兜底，前端裁剪不可信 |

> 三处用三套逻辑是这类系统最典型的腐坏方式。**抽成一个函数，前后端共享同一份规则表。**

## 三、购物车跨通道：一个容易被漏掉的硬问题

合单支付**是单通道内的**：微信的合单支付只能合微信的二级商户。

于是出现这种购物车：

```
购物车
 ├─ A 商家（只进件了微信）
 └─ B 商家（只进件了支付宝）
```

**无法一次支付完成。** 处理方式三选一：

| 方案 | 体验 | 复杂度 | 评价 |
|---|---|---|---|
| (a) 结算页按通道分组，分次支付 | 差（付两次） | 中 | 诚实但难用 |
| (b) 只允许结算同通道商品，其余留在购物车 | 中 | 低 | **推荐** |
| (c) 要求所有商家双通道进件 | 最好 | 高（进件成本翻倍） | 长期目标 |

**推荐 (b) 起步 + (c) 为长期目标**：
结算页默认选中「当前通道可支付」的商品，其余灰置并说明原因。
同时在 B 端推动商家双通道进件——这是运营动作，不是技术问题。

> 【安全】无论选哪个，**都不能让用户勾选了却在支付时才失败**。
> 分组必须发生在结算页加载时，不是点击支付时。

## 四、结算与分账：双通道统一

### 4.1 抽象不变，实现分通道

现有 `SplitGateway` 的抽象是对的，扩成按通道分发：

```
SplitGateway（接口）
   ├── WechatSplitGateway    收付通：合单支付 / 分账 / 解冻
   └── AlipaySplitGateway    直付通：支付 / 分账 / 确认结算
```

`SettleServiceImpl` 里的幂等、状态机、重试计数**与通道无关**，不动。
`stl_bill` 加一列 `channel`，按通道路由到对应实现。

### 4.2 结算逻辑不变

沿用[总体逻辑](../design/收款与分账-总体逻辑.md) §3 的核心决定：

> **抽佣与解冻放在同一时点，且在售后期之后。**

两个通道都支持「资金冻结 + 平台控制放款」，所以这条逻辑**跨通道成立**：

| | 微信收付通 | 支付宝直付通 |
|---|---|---|
| 冻结 | 下单传分账标识 | 记录待结算资金 |
| 放款 | 分账 + 解冻剩余 | 平台发起「确认结算」 |
| 兜底窗口 | 分账 30 天 / 冻结 180 天 | **待确认** |

⚠️ 两个通道的**兜底窗口不同**，调度任务要按通道分别计算截止时间，
不能用一个统一常量——这类"看起来能统一"的地方最容易埋雷。

## 五、App 生态：三个必须提前想清楚的约束

### 5.1 iOS 的 IAP 规则会吃掉部分品类

Apple 的规则很明确：

- **实物商品、App 外消费的服务** → **必须不用 IAP**（原文 "must not use In-App Purchase"）
- **数字内容、App 内消费** → 必须走 IAP，抽成 30%（小企业计划 15%）

对照本项目的五个品类：

| 品类 | IAP 风险 | 判断 |
|---|---|---|
| `FRESH` 生鲜 | 无 | 实物 |
| `DAILY` 日用 | 无 | 实物 |
| `SERVICE` 服务 | 无 | 线下消费 |
| `CARD` 卡券（储值/次卡） | **低但需确认** | 线下核销消费，应属"App 外" |
| `VIRTUAL` 虚拟商品 | ⚠️ **高** | **取决于它到底是什么** |

**`VIRTUAL` 必须先定义清楚**：

- 话费充值、线下兑换码 → 属"App 外消费"，可用微信/支付宝
- App 内使用的数字内容/会员权益 → **必须 IAP，抽 30%**

> 这条不解决的话，App 上架会被拒，或者被迫对该品类走 IAP——
> 而 30% 抽成远高于 0.6% 的支付费率，**足以让这个品类在 App 上无利可图**。
>
> 建议：**一期 App 端直接隐藏 `VIRTUAL` 品类**，等定义清楚再放开。
> 这比上架被拒后再改便宜得多。

美国区自 2025 年法院裁定后允许 App 内放外部支付链接且无需额外授权；
**其他地区仍需 IAP 或申请区域性外链授权**。海外版要按地区分别处理。

### 5.2 App 支付要求主体不是小微

App 支付只授权给个体户/企业。这意味着：

> **App 上线时，只有已升级为个体户的商家能卖货。**

如果 App 是既定路线，「平台代办个体户」就不是运营优化，
而是**App 能不能有货可卖的前置条件**。

### 5.3 海外（H5 主打场景）

微信/支付宝在境外的可用性、结算币种、跨境资质是另一套体系，
**不在本方案范围**。设计上要求：`PaymentChannel` 是**可扩展枚举**，
将来加 `STRIPE` 之类不需要改模型。

## 六、数据模型改动

| 表 | 改动 | 理由 |
|---|---|---|
| `usr_merchant` | 保持主数据，**不放 sub_mchid** | 一商家多通道 |
| **`usr_merchant_payment`**（新建） | 商家 × 通道的进件记录 | 本方案核心 |
| `stl_bill` | 加 `channel` | 分账要按通道路由 |
| `ord_order` | 加 `channel` + `pay_scene` | 对账要能按通道/场景切分 |
| `prd_goods` | 加 `app_sellable` | App 端可售性（IAP 约束，见 §5.1） |

### `usr_merchant_payment` 关键设计

| 列 | 说明 |
|---|---|
| `merchant_no` + `channel` | **联合唯一** |
| `subject_type` | 该通道下的主体类型——**可能与其它通道不同** |
| `sub_mchid` | 二级商户号 |
| `apply_status` | `NONE` / `APPLYING` / `ACTIVE` / `REJECTED` / `FROZEN` |
| `pay_methods` | JSON，**通道回传的实际授权**，不推断 |
| `invoice_capable` | 能否开票——下单前要披露 |
| `reject_reason` | 进件驳回原因，原样给商家 |

## 七、分阶段落地

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| **P0 模型先行** | 建 `usr_merchant_payment`，`canPay()` 三处接入 | 现有微信 stub 走通新模型 |
| **P1 微信收付通** | 进件 + 合单支付 + 分账 + 解冻 + 兜底调度 | 小程序端真实收款 |
| **P2 支付宝直付通** | 同上，复用 `SplitGateway` 抽象 | 双通道并行 |
| **P3 代办个体户** | 平台内代办入口 + 主体升级流程 | App 有货可卖 |
| **P4 App 上架** | IAP 品类裁剪 + App 支付 | 通过审核 |

**P0 必须最先做**，且要在 P1 之前完成：
先按单通道写死、二期再抽象，等于把 P2 的成本翻三倍（改表 + 改代码 + 迁数据）。

## 八、验收红线

在[总体逻辑 §六](../design/收款与分账-总体逻辑.md)的 7 条之上追加：

8. `canPay()` **三处共用同一实现**，不得各写一份
9. 购物车分组发生在**结算页加载时**，不是点支付时
10. `pay_methods` 来自**通道回执**，禁止按主体类型推断
11. 兜底调度按**通道**分别计算截止时间，不用统一常量
12. App 端对 `VIRTUAL` 品类的处理**必须显式**（隐藏或走 IAP），不得默认放行
