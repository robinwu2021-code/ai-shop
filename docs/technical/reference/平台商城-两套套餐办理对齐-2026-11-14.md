# 平台商城两套套餐办理对齐

日期：2026-11-14。状态：第3批第一步源码核对；无新增授权，无真实资金操作。

## 1. 定位与入口

两套套餐归平台商城导航，但保留不同订单/权益模型。主体套餐是经营主体的门店、员工等额度包，现由`/merchants?tab=plans`主体详情办理；门店套餐由`/mall`目录及门店商城订单办理。相同FREE/PRO/CHAIN字样不证明是同一模型，原手工授予也不等于收到付款。

本次10个已有入口按套餐方案、商品目录、权益管理、商城订单、销售设置归组；经营订单仍在原经营订单模块，独立支付与旧支付兼容入口保持，不计为平台商城销售记录。

## 2. 两套办理动作与权限

以下为源码条件，不能代替166当前角色授权或数据范围。`AND`表示同时具备；`OR`表示其中之一。查询权限不包含资金动作权限，旧主体处置码名称暂不改。

| 场景 | 主体套餐 | 门店套餐/平台商品 | 现有入口/限制 |
|---|---|---|---|
| 目录/报价来源 | 主体报价读取merchant:merchant:read；报价编辑system:param:update | commerce:catalog:read；编辑/发布分别catalog:edit / catalog:publish | 分别保留报价/目录版本，不转成另一模型的售价 |
| 购买单查询 | merchant:merchant:read；按entityNo查询 | commerce:mall:order:read；按storeNo并以orderNo游标翻页 | 尚无覆盖两模型的全局列表 |
| 运营代购 | merchant:merchant:ban AND commerce:mall:assisted:purchase | commerce:mall:assisted:purchase | 主体通过主体详情，门店通过运营代购页；生成订单不表示收款 |
| 付款申报查询 | 主体订单详情附带claims，原读取权限 | 待审队列commerce:mall:offline:review；完整订单详情另要commerce:mall:order:read | 菜单可见不代表有全部详情/凭证权限；不能自动补授 |
| 拒绝申报 | merchant:merchant:ban AND commerce:mall:offline:review | commerce:mall:offline:review | 只拒绝申报，不能当退款/解除占用 |
| 确认到账 | merchant:merchant:ban AND commerce:mall:offline:confirm | commerce:mall:offline:confirm | 真实金额、流水、时间、凭证及原幂等号；ACCEPTED仅受理 |
| 普通退款审核 | 沿主体购买模型的既有恢复/退款流程逐单判断 | commerce:refund:review；按原review quote及审批摘要 | 不把商城商品退款审批套到主体额度订单 |
| 异常款退款及出款 | merchant:merchant:ban AND commerce:mall:offline:refund:confirm | commerce:mall:offline:refund:confirm | 保留原refundNo/actionNo、私有出款凭证与银行结果 |
| 对账作废/占用解除 | merchant:merchant:ban AND commerce:mall:offline:void | commerce:mall:offline:void | 先按原事实处理退款/异常款，再按业务规则解除；不能仅改状态 |
| 恢复与平台凭证 | 主体处置码AND（核款/作废/退款出款三者任一） | 各原接口独立鉴权；订单恢复沿order:read，凭证沿offline:evidence | 两者不能粗暴合成一套共享凭证权限 |
| 权益回读 | 原主体档位/额度查询 | commerce:subscription:read | 到账和履约分别回读；赠送/撤销使用独立权限 |
| 收款档案 | 购买链路引用平台收款档案快照，不新增另一份账户配置 | commerce:collection:profile:read / write | 不因目录改名更新账号或真实收款配置 |

## 3. 源码依据

- 主体：`backend/shop-merchant/.../api/ops/OpsPlanPurchaseController.java`（购买、代购、核款、拒绝、恢复、作废、凭证）；`OpsEntityPlanRefundController.java`（收款、异常款退款与出款）；`OpsMerchantPlanController.java`（原额度授予、档位定义）。前端`app/merchants/plan-purchases.tsx`和`components/offline/cash-refunds.tsx`保留组合授权。
- 门店：`backend/commerce/commerce-spring-boot-starter/.../http/CommerceOfflineOpsHttpController.java`及`CommerceOpsMallHttpController.java`；前端`app/mall/order-drawer.tsx`、`claims-tab.tsx`、`assisted-tab.tsx`及`components/offline/cash-refunds.tsx`。
- 接口适配：`ops-web/lib/api/contracts/commerce.ts`、`api/https/commerce.ts`、`api/https/merchant.ts`；实际adapter文件路径及相关源码摘要收录本批证据。未增加假成功mock或改写请求金额/操作号。

2. 为全局购买订单、核款待办、退款处理分别补查询契约及数据范围；保留分页/币种/时间/状态和模型标识。先只读对齐，再接原写动作。
3. 补运营代购主体/门店选取及报价回显；原主体拥有者授权、门店额度、请求幂等、在途资金表单锁及恢复能力全部保留。
4. 对受控角色核对必要的查询/凭证权限，缺授权走正式授权，不把“可进入核款队列”推成“可核款/退款”。
5. 两套模型分别走App申报、运营代购、拒绝/重报、核款、履约/权益、异常款退款、占用解除及未知结果恢复；不做真实转账。

### 3C：平台收退款统计

1. 定义收入概况/明细的只读查询及权限：实际收款、退款、净收款和待核实/异常款分别展示，金额按币种和来源模型汇总。
2. 事件时间按实际到账/出款事实，订单创建时间仅作订单维度；覆盖完整游标/分页，不能只合计当前页。退款使用可追溯资金事实避免同一笔普通退款/现金退款重复计入。
3. 未核实的申报、受理中操作、未匹配异常款不能混作套餐销售已收款；异常款保留独立对账视图。
4. 不从SaaS门店营业额、全量支付GMV或订单应付额推算平台收入；后端事实查询落地后再增加可用菜单，不先建空收入页。
