# 行业包功能清单 —— 餐饮包 / 美业包

> 状态：草稿 · 待确认 · 创建 2026-08-27
> 关联：[TDD-行业包-机制与装配](../design/TDD-行业包-机制与装配.md) · [核心能力清单](./核心能力清单.md)

一条贯穿全册的规矩：**下表里凡是没写「本包新建」的东西，都是调基座的。**
行业包不建商品、不建订单、不建会员、不建优惠、不算结算、不实现退款、不自己扣库存和余额。

# 一 · 餐饮包（`FOOD`）

## 1.1 包身份

| 项 | 值 |
|---|---|
| `code()` | `FOOD` |
| 提供能力 | `TABLE_ORDERING` `PAY_AFTER_SERVE` `KITCHEN_PRINT` |
| **依赖基座能力**（缺一拒绝启动） | `DINE_IN` `OFFLINE_PAY` `RESOURCE_BOOKING` `PRINT_RECEIPT` `PRINT_ROUTE_SPLIT` `BUNDLE_SKU` |
| 迁移 | `db/industry/food` → 历史表 `fnb_flyway_history` |
| 端点前缀 | `/biz/x/food/**`（商家）· `/mp/x/food/**`（买家）· `/ops/x/food/**`（运营） |
| 权限码段 | `food:*` |

## 1.2 本包新建的表

```sql
fnb_table(table_no, store_no, resource_no, area, seats, qr_token, status)   -- 桌台，resource_no 指向基座 mch_resource
fnb_check(check_no, store_no, table_no, status, people, opened_by, opened_at, closed_at, merged_into)
fnb_check_order(check_no, order_no, seq)                                    -- 一桌多单（加菜）
fnb_check_item_log(log_no, check_no, order_no, item_no, action, qty, reason, operator, created_at)  -- 划菜/催菜/退菜留痕
fnb_dept(dept_no, store_no, name)                                           -- 出品部门
fnb_goods_dept(store_no, goods_no, dept_no)                                 -- 菜品 → 出品部门，分单路由的依据
```

**为什么桌台既有 `fnb_table` 又要 `mch_resource`**：占用与释放的并发安全在基座（与库存、时段同一套带条件 UPDATE），
`fnb_table` 只放餐饮才有的属性（区域、座位数、桌码）。**不这么分，第二个行业要占资源时就得再写一遍并发控制。**

## 1.3 功能清单

| # | 功能 | 说明 | 依赖核心能力 | 用到的扩展点 |
|---|---|---|---|---|
| F-01 | 桌台管理 | 建桌、分区、座位数、启停用；生成/重置桌码 | E1 资源 | `ResourceTypeProvider(TABLE)` |
| F-02 | 扫码开台 | 扫桌码 → 校验桌态 → 建台账 → 占用资源 | E1、J5 幂等 | — |
| F-03 | 手工开台 | 店员在 b-app 开台（无桌码/电话订座） | E1 | — |
| F-04 | 点单下单 | 选菜 → 下单（履约 `DINE_IN`）→ 挂到台账 | C1、C3 | `CheckoutContributor` |
| F-05 | 加菜 | 同一台账下追加订单，**不合并已下单的单** | C1 | — |
| F-06 | 先付后吃 | 每单即时线上支付 | D2 | `OrderLifecycleListener.onPaid` |
| F-07 | 先吃后付 | 单落 `WAIT_OFFLINE_PAY`，结账时统一确认收款 | D3 | `CoreOrderApi.confirmOfflinePaid` |

## 1.4 台账状态机（本包私有，绝不进基座订单状态机）

```
OPEN ──下单/加菜──> OPEN
OPEN ──发起结账──> SETTLING ──收款完成──> CLOSED
OPEN ──并台──────> MERGED（merged_into 指向目标台账）
OPEN ──作废──────> VOIDED（仅限无已支付订单）
```

**SETTLING 是必要的一档**：结账过程中不许再加菜，否则「合计多少」这件事没有确定的时刻。

## 1.5 三条容易做错的地方

1. **不要给子单加「制作中/上菜中」状态。** 那是台账状态；进了基座状态机，零售和美业也要认它。
2. **后厨打印由台账事件触发，与支付无关。** 先吃后付时钱还没收，菜必须已经在做了。
3. **`WAIT_OFFLINE_PAY` 的超时取消会把正在吃的桌子取消掉。** 基座已按 D3 改成按门店取配置 + 未结台不取消 —— 这条是**行业包依赖基座改动**的典型，写进 `requiredCapabilities` 才拦得住。

## 1.6 本包明确不做

外卖配送与运力、供应链与门店进销存（基座 `shop-inventory` 已有）、发票、会员储值（基座 F2）、优惠券（基座 G1）、结算分账（基座 H1）。

# 二 · 美业包（`BEAUTY`）

> 命名用 `BEAUTY` 不用 `SERVICE`：家政、维修与美业同属基座 `sys_industry` 的 `LIFE_SERVICE`，
> 但工作流不同（一个派单上门、一个到店指定技师）。**行业包的粒度比 `sys_industry` 细**，
> 家政/维修将来是另一个包，不是本包加分支。

## 2.1 包身份

| 项 | 值 |
|---|---|
| `code()` | `BEAUTY` |
| 提供能力 | `SERVICE_WORK_ORDER` `STAFF_COMMISSION` |
| **依赖基座能力** | `STORE_VERIFY` `APPOINTMENT` `RESOURCE_BOOKING` `STAFF_PROFILE` `STAFF_SCHEDULE` `STORED_VALUE` `TIMES_CARD` `BUNDLE_SKU` `PRINT_RECEIPT` |
| 迁移 | `db/industry/beauty` → 历史表 `bty_flyway_history` |
| 端点前缀 | `/biz/x/beauty/**` · `/mp/x/beauty/**` · `/ops/x/beauty/**` |
| 权限码段 | `beauty:*` |

## 2.2 本包新建的表

```sql
bty_work_order(wo_no, store_no, order_no, member_no, staff_no, slot_no, status,
               started_at, finished_at, remark)
bty_wo_item(wo_no, item_no, goods_no, card_no, times_used, staff_no)   -- 一单多项，可各自归不同技师
bty_wo_staff_log(wo_no, from_staff, to_staff, reason, operator, created_at)  -- 换人留痕
bty_commission_rule(rule_no, store_no, scope, target_no, mode, value)  -- 提成规则
bty_commission_record(rec_no, wo_no, staff_no, base_amount, amount, status)
```

**为什么工单要独立于订单**：一张订单可能对应多次到店（疗程包 10 次 = 10 张工单），
而**订单是一次交易，工单是一次服务**。合并的话，「这次谁做的、做了多久、耗了几次」全部无处安放。

## 2.3 功能清单

| # | 功能 | 说明 | 依赖核心能力 | 用到的扩展点 |
|---|---|---|---|---|
| B-01 | 技师档案 | 建档、等级、擅长项目、照片；**可无登录账号** | E3 | — |
| B-02 | 排班 | 规则 → 滚动生成时段（写基座 slot 表） | E4、J4 | `JobHandler` |
| B-03 | 选项目 → 选技师 → 选时段 | C 端三步；不指定技师则按门店级时段 | B2、E1、E2 | `ResourceTypeProvider(STAFF)` |
| B-04 | 占位下单 | `tryBook` 抢名额 → 下单（`APPOINTMENT`/`STORE_VERIFY`） | E2、C1 | — |
| B-05 | 改约 / 取消 | 释放旧名额、占新名额；释放幂等由标记位保证 | E2 | — |
| B-06 | 到店开工单 | 核销码或会员识别 → 建工单 → 占资源 | E1、J5 | — |
| B-07 | 换技师 | 工单内换人，留痕；**提成归属随之变更** | — | — |
| B-08 | 完成与核销 | 工单完成 → 触发基座核销 / 耗卡 | C3、F2 | `CoreMemberApi` |
| B-09 | 耗卡（次卡/疗程） | 扣次数**回基座走流水**，本包不算余额 | F2、B4 | `CoreMemberApi` |
| B-10 | 储值支付 | 作为一种 `sys_pay_channel`，走基座 `markPaid` | D1、D2、F2 | — |
| B-11 | 开卡 / 充值 | **调基座**；本包只提供办卡入口与话术 | F2 | — |
| B-12 | 提成核算 | 按工单行计提，退款倒扣 | — | `OrderLifecycleListener.onRefunded` |
| B-13 | 服务单 / 结账单打印 | 到店打服务单，结账打小票 | I2、I4 | `PrintPayloadProvider(SERVICE_START/CHECKOUT)` |
| B-14 | 客史档案 | 到店记录、偏好、过敏史、照片 | F1（会员在基座） | — |
| B-15 | 未到场（no-show） | 超时未到标记，释放资源，是否扣次由规则定 | E2、J4 | `JobHandler` |

## 2.4 工单状态机（本包私有）

```
CREATED ──开始服务──> SERVING ──完成──> FINISHED ──核销/耗卡──> SETTLED
CREATED ──未到场──> NO_SHOW
CREATED/SERVING ──取消──> CANCELLED（资源释放）
```

## 2.5 三条容易做错的地方

1. **储值和次卡不在本包。** 三个行业都要，且储值是预收款、牵动结算与财务口径。本包只调 `CoreMemberApi`。
2. **技师不等于账号。** 硬绑 `user_no` 会逼商家给每个师傅开登录账号才排得了班。
3. **提成的退款倒扣必须挂事件。** 只在完成时计提、不管退款，第一次退单就会多发一笔而没人发现。

## 2.6 本包明确不做

会员与标签、优惠券与活动、储值与次卡的账、订单与退款、结算、上门服务的派单与路径（那是将来的家政包）。

# 三 · 两个包的共同边界

| 事项 | 归属 | 理由 |
|---|---|---|
| 排队叫号 | **基座**（候选能力 `QUEUE_CALL`） | 餐饮和美业都要。放任一包，另一包必抄一遍；**两个行业包互相依赖是插件化最常见的死法** |
| 资源占用并发控制 | 基座 E1/E2 | 同一套带条件 UPDATE，与库存、余额同理 |
| 打印设备/模板/路由/重试 | 基座 I1–I4 | 行业差异只在路由数据行与 `PrintPayloadProvider` 的内容 |
| 会员资产 | 基座 F2 | 预收款，财务口径唯一 |
| 组合商品 | 基座 B4 | 套餐 ≡ 疗程包 |
| 「先享后付」的支付链路 | 基座 D3 | 台账编排在包内，**同一个业务词两半归属不同** |

# 四 · 交付顺序（与 TDD §12 对齐）

| 阶段 | 内容 | 验收 |
|---|---|---|
| 0 · 基座 | A3/A4 能力开关、C3 `DINE_IN`、E1–E4 资源与排班、F2 会员资产、I1–I4 打印、`shop-industry-spi` | **存量商家行为零变化**；`-Pcore-only` 可构建可启动、零售场景全绿 |
| 1 · 美业包 | B-01…B-15 | 试点店跑通「约—到店—服务—耗卡—结账」；剔除本包后零售全绿 |
| 2 · 餐饮包 | F-01…F-15 | 试点店跑通两种付款顺序 + **真机出票**；剔除本包后零售与美业全绿 |
| 3 · 收口 | 提成、行业报表、b-app 按能力分叉、ops-web 行业配置页 | 三行业共用一份订单/会员/结算报表 |

**美业包排在餐饮包前面**：它依赖的基座能力（资源、排班、会员资产）恰好是餐饮包也要的一大半，
先做美业等于把基座验一遍；反过来先做餐饮，桌台那套自成体系，验不到排班与资产。
