## 一、一句话（L1）

**状态回答「这单走到哪了」，履约方式回答「怎么交付」。两者是两条轴，
状态不该按履约方式展开——否则每加一种履约就要加一批状态。**

这个平台的特点恰恰是履约方式多：服务、自提、自送、物流、到店核销。
按履约展开状态，状态数会跟着履约数线性涨，而它们本该是正交的。

---

## 二、模型（L2）

```
        抽象状态（6 个，与履约无关）
                 ×
        履约方式（7 种，可继续加）
                 ×
        附加信息（预约时间、快递单号、取货码…）
                 ↓
        展示：文案 · 图标 · 用户下一步动作 · 页签归属
```

**状态集合是封闭的，履约集合是开放的。** 加一种履约 = 文案表加一行，状态不动。

### 2.1 抽象状态（6 个）—— 就是库里那 6 个

| 状态 | 含义（与履约无关的那部分） |
|---|---|
| `WAIT_PAY` | 钱还没到 |
| `WAIT_FULFILL` | 钱到了，**交付方还没行动** |
| `FULFILLING` | **交付方已行动，等交接完成** |
| `COMPLETED` | 交接完成 |
| `CANCELLED` | 未付款就终止 |
| `REFUNDED` | 付款后退回 |

**库里本来就是这 6 个，模型是对的。** 问题出在它上面那层。

### 2.2 支付成功后落哪个状态，由履约方式决定

这是本模型唯一需要「按履约分支」的地方，而且只分两类：

| 履约 | 支付成功后 | 为什么 |
|---|---|---|
| 实物类（自提 / 自送 / 快递） | `WAIT_FULFILL` | 商家要备货、要发货，**得先动手** |
| 服务类（到店核销 / 上门预约） | `FULFILLING` | 码已出、时间已约，**买家立刻就能用**，商家没有前置动作 |
| `INSTANT` 虚拟即时 | `COMPLETED` | 付款即发放，没有等待 |

> 这一条也顺手解释了服务单的怪相：把服务单丢进 `WAIT_FULFILL`，
> 界面会说「待发货」——而根本没有东西要发。**不是文案错，是状态落错了。**

#### 附带的一条闸：`WAIT_PAY → FULFILLING` 只对系统开

服务类要「付款即进履约」，这条边就必须在状态机图里。但它一旦进图，
**商家侧的「发货」也能从未付款直接推过去** —— 货先出去了，钱还没收。
（`OrderStateMachineTest.cannotFulfillBeforePaid` 当场变红，守的正是这件真事。）

「谁发起」这件事图本身表达不了：同一对 (from, to)，系统走得通、人走不通。
所以分成两个入口，而不是把发起方编进状态名：

| 入口 | 用途 |
|---|---|
| `assertSubOrderTransit` | 支付回调等**系统**发起的迁移 |
| `assertMerchantSubOrderTransit` | 商家发起（发货、标记送达）——额外拒绝 `from = WAIT_PAY` |

## 三、展示：由（状态 × 履约 × 信息）决定（L3）

### 3.1 文案表

| 状态 | 履约 | 买家看到 | 买家下一步 | 商家看到 |
|---|---|---|---|---|
| `WAIT_FULFILL` | 自提类 | 备货中 | 等 | **待备货** |
| `WAIT_FULFILL` | 配送类 | 待发货 | 等 | **待发货** |
| `FULFILLING` | `STORE_PICKUP` / `NEIGHBOR_PICKUP` | 已到自提点 | **去取** | 待核销 |
| `FULFILLING` | `MERCHANT_DELIVERY` / `EXPRESS` | 已发货 | 等 | 已发货 |
| `FULFILLING` | `STORE_VERIFY` | 待使用 · 凭码到店 | **去用** | 待核销 |
| `FULFILLING` | `APPOINTMENT` | 待服务 · **{预约时间}** | 到点在场 | 待上门 |

**加一种履约 = 加一行。** 状态枚举、状态机、契约取值全不动。

### 3.2 附加信息决定细节，不决定状态

| 信息 | 影响什么 | 不影响什么 |
|---|---|---|
| `appointmentAt` | 预约单显示「明天 14:00 上门」 | 状态仍是 `FULFILLING` |
| `expressNo` | 显示物流查询入口 | 同上 |
| `verifyCode` | 显示取货码/核销码 | 同上 |
| `requireBuyerConfirm` | 是否要买家点「确认收货」才 `COMPLETED` | 同上 |

### 3.3 页签是**谓词**，不是状态

这是与现状最关键的差别：页签的筛选条件是「状态 + 履约集合」，**不是一个状态值**。

| 页签 | 谓词 |
|---|---|
| 待付款 | `status = WAIT_PAY` |
| 待发货 | `status = WAIT_FULFILL` |
| 待取货 | `status = FULFILLING ∧ fulfillment ∈ {STORE_PICKUP, NEIGHBOR_PICKUP}` |
| 待收货 | `status = FULFILLING ∧ fulfillment ∈ {MERCHANT_DELIVERY, EXPRESS}` |
| 待使用 | `status = FULFILLING ∧ fulfillment ∈ {STORE_VERIFY, APPOINTMENT}` |
| 已完成 | `status = COMPLETED` |

**页签怎么分、分几个，是纯前端的产品决定**，改它不需要动后端状态。
想把「待使用」和「待取货」并成「该你了」，改一个谓词即可 —— 后端一行不改。

## 四、与现状的差异，以及迁移代价（L4）

### 4.1 现状把「履约」烧进了状态

后端 `OrderStatusView` 现在的做法是 `库状态 × 履约 → 展示状态`，
产出 `ARRIVED` / `SHIPPED` 两个**看起来像状态、实际是「状态+履约」组合**的值。

它解决了真问题（三端此前各写一套词，且互不相同），方向是对的 ——
**但把组合结果命名成状态，代价是状态集合会跟着履约数涨**。
我上一版方案就是这么滑下去的：为服务类再加 `TO_USE` / `TO_SERVE`，
下次来个「同城闪送」就还要再加。

### 4.2 两条路

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 契约用抽象状态，展示层做映射**（本文主张） | `OrderStatus` 收敛回 6 个；列表接口按 `status + fulfillments[]` 两个参数筛；文案表落在 shared | b-app 现在按 `SHIPPED`/`ARRIVED` 筛页签，**要改**；c-app 刚改完的 tab 要再改一次；后端列表接口加 `fulfillments` 参数 |
| **B. 保留 `OrderStatusView`，只加服务类两个值** | 加 `TO_USE`/`TO_SERVE` | 今天最省；但状态集合继续跟着履约涨，下一种履约再谈一次 |

**我建议 A**，理由是你给的那条原则本身：状态抽象、展示分化。
但 A 的代价要说清楚 —— **它要动 b-app**，而 b-app 的订单页签刚在 8-12 那轮联调里稳定下来。

### 4.3 如果选 A，改动顺序

1. 后端列表接口加 `fulfillments` 参数（`OrderStatusView.pickupOnly` 那套逻辑的通用化）
2. shared 落一张文案表 + 一个 `orderView(status, fulfillment, info)` 函数，三端共用
3. c-app / b-app 页签改成传 `status + fulfillments`
4. `OrderStatus` 契约取值收敛回 6 个，`ARRIVED`/`SHIPPED` 从状态枚举里退役
5. 服务履约按 [TDD-服务履约](../design/TDD-服务履约-到店核销与上门预约.md) 接入 —— 此时**不需要新增任何状态**

### 4.4 实施记录（2026-08-17，选 A）

五步全做完，三端 + 后端一次迁完（**没有走兼容期** —— 三端都在自己手里，
留一段两套并存的日子只会让下一个人不知道该按哪套写）：

| 层 | 落点 |
|---|---|
| 契约 | `OrderStatus` 7 → 6；`ARRIVED`/`SHIPPED` 合并为 `FULFILLING` |
| shared | `strategies/order-view.ts`：交付形态 · `orderView()` · `tabQuery()`，三端共用 |
| 后端 | 列表接口加 `fulfillments`（与 `status` 正交）；`OrderStatusView` 降级为只做名字对齐，`of()`/`pickupOnly()` 与两个退役常量全删 |
| c-app / b-app / ops-web | 页签改谓词；状态文案由 `(状态 × 履约)` 决定 |

**卡单时限那处是真语义，单独处理**：`SHIPPED` 240 分钟 / `ARRIVED` 1440 分钟
原本挂在两个假状态上，现在按 `(状态 × 履约)` 判 —— 它本来就依赖履约。

#### 真链路实测

```
status=FULFILLING                          → STORE_PICKUP, EXPRESS, STORE_PICKUP
status=FULFILLING & fulfillments=自提类     → STORE_PICKUP, STORE_PICKUP
status=FULFILLING & fulfillments=配送类     → EXPRESS
```

界面上同一个 `PAID` 在自提单显示「备货中」，`FULFILLING` 在自提单显示「已到自提点」、
在快递单显示「已发货」——**一个状态，两种展示**，正是这次要的效果。

#### 守卫的表现值得记一笔

改完枚举跑全量，**6 条新红精准指向每一处该跟的地方**：类型对齐（后端还留着旧常量）、
枚举登记（新增的 `DELIVERY_SHAPE`/`NEXT_ACTION` 没登记）、项目词典（`FULFILLING` 没收录）、
后端验收清单（状态迁移表过期）、ops-web（第三端没跟）。
**没有一条要靠人想起来** —— 这正是那些守卫当初被写下来的理由。

> 一个小坑：`FULFILLING` 在 Java 里先写成了 `OrdSubOrder.FULFILLING` 的引用，
> 而枚举对账扫的是字面量，于是它「看不见」——而「看不见」与「两端不一致」
> 在报告里长得一模一样。改成字面量才对上。

## 维护约定

- **状态集合封闭，履约集合开放**。想加状态前先问：这是「订单走到哪了」，
  还是「怎么交付」？后者一律进履约或附加信息，不进状态
- 文案表是展示层的真源，三端共用一份 —— 各写一份的下场，
  `OrderStatusView` 的类注释里已经记过一次
