## 〇、一句话结论

**发现一处结构性冲突（F1）：c-app 的 `Order` 是单商家平铺模型，后端 `OrderVO` 是主单-子单两级模型，
两者无法互相渲染。** 这不是字段改名能解决的，需要业务拍板（见 §四 Q6）。

除此之外：18 个契约字段无页面消费方（多数属「后端多给」，两条属「前端尚未做」），
5 处字段命名不一致，2 个页面依赖的数据后端尚无来源。

## 二、字段级核对（已实现端点）

### 2.1 契约字段无页面消费方（18 项）

脚本对全量 `c-app/src/**` + `packages/shared/src/**` 搜索每个字段名的结果：

| 字段 | 判定 | 处置 |
|------|------|------|
| `Pickup.leaderNo` `leaderName` `leaderAvatar` | **前端已删团长展示**（ADR-004），后端仍在返回 | 契约保留但标 `deprecated`，E10 完成后删；**不要现在删** —— 前端类型里还有可选字段 |
| `CartItem.selected` `merchantName` | 前端购物车按商家分组用的是 `merchantNo`，勾选态存在本地 store | 保留：结算取「勾选行」需要服务端 `selected`；`merchantName` 供分组标题，前端待补 |
| `Order.payAmount/goodsAmount/freightAmount/discountAmount/paidAt/subOrders` | **F1 结构冲突的表征**，见 §三 | 阻塞，待 Q6 |
| `SubOrder.subOrderNo/merchantName/pickupCode` | 同上 | 阻塞，待 Q6 |
| `BootstrapConfig.*`（4 项） | 前端**尚未接入启动配置**（皮肤仍全本地） | 前端待做（C-TH-05 运营下发）；后端保留 |

> 结论：真正「后端多给、可以删」的一条都没有。18 项里 11 项是 F1 的连带，4 项是前端待做，3 项是过渡期兼容。
> **这正是 A4 要求双向核对的原因** —— 只看「字段没人用就删」会把 F1 掩盖成一堆小改名。

## 三、F1：订单模型结构冲突（**本轮最重要的发现**）

```
c-app 的 Order（现状）                     后端 OrderVO（S2 已实现）
├─ orderNo                                 ├─ orderNo（主单）
├─ fulfillment  ← 单一履约方式              ├─ payAmount / goodsAmount / ...
├─ items[]      ← 平铺，跨商家混在一起       └─ subOrders[]
├─ amount: OrderAmount（8 个金额字段）          ├─ merchantNo / merchantName
├─ verifyCode   ← 单个核销码                    ├─ fulfillment  ← 每个商家各自的
├─ pickupNo / expressNo                         ├─ pickupCode   ← 每个商家各自的
└─ timeline[]                                   └─ items[]
```

**冲突点**：一次跨商家下单，履约方式、核销码、物流单号、状态**天然是每个商家一份**。
前端模型只有一份，无法表达；后端模型给了 N 份，前端渲染不了。

这不是前端写错了 —— mock 阶段每单只有一个商家，平铺模型完全够用。
真实后端一旦按 ADR-002 拆单，这个模型就不成立了。

### 两条出路

| 方案 | 做法 | 代价 | 影响 |
|------|------|------|------|
| **甲：前端改造成两级** | `orders`/`order`/`pay`/`after-sale`/`review-write`/`store` 六个页面改为「订单 → 包裹」两层展示 | 前端 6 页 + 类型 + mock 全改 | 与 ADR-002/E3 完全一致；用户看到「一次付款，三个包裹」 |
| **乙：C 端订单 = 子单** | `/mp/order` 列表与详情**返回子单粒度**（每个商家一条「订单」），主单只在支付环节出现 | 后端 VO 调整 + 支付页要处理「一次支付多单」 | 前端几乎不用改；与主流电商（淘宝/拼多多）的用户心智一致 |

**我的建议：乙。** 理由：
1. 用户心智里「订单」本来就是按店分的 —— 淘宝一次结算多店也是生成多个订单号；
2. 履约、售后、评价、核销**全部是子单粒度**，C 端订单 = 子单能让这四条链路的 ID 一以贯之，不必到处传两个号；
3. 前端 6 个页面不用重做，而 ADR-002 的分账语义不受任何影响（分账本来就按子单）。

代价是支付页要能「一次支付覆盖多个订单」—— 这一处改动比改 6 个页面小得多。

> ⚠️ **在 Q6 拍板前，M3 的契约冻结（M3.1）无法完成**，因为订单响应结构未定。
> 这也是把 A4 排在 A2/A3 之前的价值：现在改是改一份 VO，等 DDL 和领域模型都按主单粒度铺完再发现，就是返工三层。
