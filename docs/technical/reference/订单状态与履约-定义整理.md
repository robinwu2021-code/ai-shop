## 一、为什么会乱（L1）

订单的「状态」不是一个轴，是**两个轴的乘积**：

```
库状态（粗，6 个）  ×  履约方式（7 种）  →  展示状态（细，7 个）
```

库里刻意做粗：`WAIT_FULFILL` / `FULFILLING` 对快递、自提、自送一视同仁，
状态机因此只有六个节点，好推理也好守。

但对买家来说「已发货」和「已到自提点」是**两件完全不同的事**——一个是等，一个是去取。
所以后端有一层 `OrderStatusView` 专门做这个乘法。

**乱的根源**：这一层存在，但不是每一端都用它。

## 二、三张表（L2）

### 2.1 库状态（`OrdSubOrder`，6 个）

| 值 | 含义 |
|---|---|
| `WAIT_PAY` | 待付款 |
| `WAIT_FULFILL` | 已付款，等商家备货/发货 |
| `FULFILLING` | 履约中 —— **快递是「在路上」，自提是「已到点」，同一个值** |
| `COMPLETED` | 已完成 |
| `CANCELLED` | 已取消 |
| `REFUNDED` | 已退款 |

### 2.2 展示状态（`OrderStatusView`，7 个）

| 值 | 由什么映射来 | 买家看到 | 商家看到 |
|---|---|---|---|
| `WAIT_PAY` | 同名 | 待付款 | — |
| `PAID` | `WAIT_FULFILL` | 已付款 | **待发货** |
| `ARRIVED` | `FULFILLING` + **自提类** | **待取货** | **待核销** |
| `SHIPPED` | `FULFILLING` + **配送类** | **待收货** | 已发货 |
| `COMPLETED` / `CANCELLED` / `REFUNDED` | 同名 | 同义 | 同义 |

### 2.3 履约方式（7 种）与自提/配送的划分

| 值 | 中文 | 归类 | `FULFILLING` 时展示为 |
|---|---|---|---|
| `STORE_PICKUP` | 自提点自提 | **自提类** | `ARRIVED` |
| `NEIGHBOR_PICKUP` | 邻居家自提 | **自提类** | `ARRIVED` |
| `MERCHANT_DELIVERY` | 商家自送 | 配送类 | `SHIPPED` |
| `EXPRESS` | 快递 | 配送类 | `SHIPPED` |
| `STORE_VERIFY` | 到店核销 | 配送类* | `SHIPPED` |
| `APPOINTMENT` | 上门预约 | 配送类* | `SHIPPED` |
| `INSTANT` | 虚拟即时发放 | — | 付款即 `COMPLETED`，不经此态 |

> \* **`STORE_VERIFY` 与 `APPOINTMENT` 落进「配送类」是分类的副作用，不是设计**：
> `OrderStatusView.PICKUP` 只列了两个自提值，其余一律走 else。
> 到店核销的用户要「去店里」，说他「待收货」是错的。**这是一处待决**，见 §五。

## 三、逐项定义与三端现状（L3）

### 3.1 状态机（订单）

```
WAIT_PAY  → PAID | CANCELLED
PAID      → ARRIVED | SHIPPED | CANCELLED      （库里是 WAIT_FULFILL → FULFILLING）
ARRIVED   → COMPLETED
SHIPPED   → COMPLETED
COMPLETED → 终态
CANCELLED / REFUNDED → 终态
```

**曾经写错过两个值，两次都表现为「页签恒空且不报错」**：

| 错值 | 谁的 | 后果 |
|---|---|---|
| `PREPARING` | mock 多出来的一步 | 端上按一个后端永不下发的值筛 → 空列表 |
| `REFUNDING` | **售后单的状态**，不是订单的 | b 端「售后中」页签与工作台待办数恒为 0 |

### 3.2 售后是**另一条轴**，不是订单状态

`AfterSaleStatus`：`APPLIED → REFUNDING → REFUNDED`（另有 `REJECTED` / `DISPUTED`）。

**一个订单可以「已完成」的同时挂着一张处理中的售后单** —— 两者并存。
做成互斥状态就必须二选一，而那表达不了。售后要从 `/mp/after-sale`、`/biz/after-sale` 单独查。

### 3.3 三端 tab 现状对照

| 端 | tab | 传 `status` 给后端？ |
|---|---|---|
| **b-app** | 全部 / 待发货`PAID` / 已发货`SHIPPED` / 待核销`ARRIVED` / 已完成 / 售后 | ✅ 传 |
| **c-app** | 全部 / 待付款 / 待发货`PAID` / 待取货`ARRIVED` / 待收货`SHIPPED` / 已完成 / 售后 | ✅ 传（**2026-08-17 接上**） |

> **改之前**：c-app 是三端里唯一没接的 —— 一个 `toPick` 页签并吃
> `PAID + ARRIVED + SHIPPED`，且 `orderList({ size: 100 })` 全量拉、前端筛。三条代价：
>
> 1. 丢掉后端算好的 ARRIVED/SHIPPED 区分 —— **买快递的人在「待取货」下看到自己的单**
> 2. **超过 50 单静默截断** —— 端上要 100，后端 `Math.min(size, 50)` 只给 50，
>    而前端筛的就是这 50 条。老用户的订单会缺，且不报错
> 3. 分页形同虚设
>
> 现已改为按页签传展示状态、由后端筛；`PAGE_SIZE` 与后端上限对齐成 50，
> 超出部分用「还有 N 笔更早的订单未显示」明说，不再悄悄消失。

后端的能力是齐的：`OrderStatusView.toStored(view)` 把展示状态翻回库状态，
`pickupOnly(view)` 再按履约方式收窄 —— `ARRIVED` 只要自提单，`SHIPPED` 只要非自提单。

### 3.4 「待评价」

`Order.reviewed?: boolean` 已存在。c-app 的 `done` tab 只按 `COMPLETED` 筛，
评过与没评的混在一起 —— 筛一下就能分开，**没有缺失的能力，只是没做**。

## 四、C 端 tab（2026-08-17 已落地）

不是产品取舍题。**后端已经算好、b-app 已经用对，c-app 接上即可**：

| tab | 传给后端的 `status` | 备注 |
|---|---|---|
| 全部 | — | |
| 待付款 | `WAIT_PAY` | |
| 待发货 | `PAID` | 已付款、等商家备货。既不用取也不用等收，单列 |
| **待取货** | `ARRIVED` | 自提类，用户要去取 |
| **待收货** | `SHIPPED` | 配送类，用户在等 |
| 已完成 | `COMPLETED` | |
| 售后 | 走 `/mp/after-sale` | **不按订单状态筛**，切到这个页签时不带 status |

**实测**（2026-08-17，真后端）：两笔订单在库里同为 `FULFILLING`，
一笔 `STORE_PICKUP`、一笔 `EXPRESS` —— 前者只出现在「待取货」（显示「已到自提点」），
后者只出现在「待收货」（显示「已发货」）。分流正确。

### 仍未决：待评价要不要独立成 tab

能力已具备（`Order.reviewed`），**这才是唯一真正的产品决定**：
加则 7 个 tab（现在已经 7 个了，加完 8 个），375px 下横滑更长；
不加则用户找不到「哪些还没评」，而评价率直接影响新店冷启动。

> 现在 7 个 tab 在 375px 下已经要横滑（实测截图可见「退款/售后」被截断）。
> 加第 8 个之前，值得先想想是不是该把「待发货」并回去 ——
> 它是三个等待态里用户最不需要动作的那个。
