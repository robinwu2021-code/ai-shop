# 标准能力基线 —— 零售是默认行业，其余行业是插件

> 状态：草稿 · 待确认 · 创建 2026-08-27
> 关联：[TDD-行业化扩展-餐饮与服务业](../TDD-行业化扩展-餐饮与服务业.md) · [ADR-019 行业工作流做成独立插件项目](../ADR/ADR-019-行业工作流做成独立插件项目.md)

本册回答一个问题：**哪些东西是「系统本来就该有的」，哪些是「某个行业才有的」。**
分错的代价是不对称的 —— 把标准能力错分给插件，每个行业各做一遍；
把行业能力错分给基座，主干里长出 `if (行业)`，且再也拿不掉。

---

## 0. 三条划分判据

一条能力属于**基座**，当且仅当三条同时成立：

1. **零售也要用**（哪怕形态简化）—— 零售是默认行业，基座 = 零售跑得起来的全集；
2. **换个行业只换数据不换代码** —— 例如打印：餐饮分单、美业服务单，差的是路由规则的行，不是分支；
3. **它被两个以上的域读** —— 一旦只有一个域读，它就该待在那个域里。

任一条不成立 → 是**插件能力**：基座只留扩展点，实现搬走。

---

## 1. 基座 · 不可关闭（CORE）

这一组没有开关。关掉任何一条，系统不成立。

| 域 | 能力 | 现状 | 位置 |
|---|---|---|---|
| 主体 | 入驻、资质、经营范围、押金、违规处置 | ✅ 已有 | `shop-merchant` |
| 门店 | 门店、默认店、状态三档、经营模式、渠道配置 | ✅ 已有 | `shop-merchant` |
| 商品 | 标品/SKU/规格模板/类目/门店价/门店库存 | ✅ 已有 | `shop-core/product` |
| 交易 | 主子单、统一状态机、购物车、下单、取消 | ✅ 已有 | `shop-core/trade` |
| 支付 | 通道主数据、线上支付、线下确认收款、`markPaid` 幂等 | ✅ 已有 | `shop-core/trade` + `shop-channel/pay` |
| 售后 | 独立状态机、退款、申诉裁决 | ✅ 已有 | `shop-core/trade` |
| 会员 | 会员、门店会员、标签、分群、触达 | ✅ 已有 | `shop-core/member` |
| 营销 | 活动、券、发放、核销、适用范围 | ✅ 已有 | `shop-core/promotion` |
| 结算 | 账单、对账、分账/自营两条链路 | ✅ 已有 | `shop-settle` |
| 权限 | 权限码、角色、B 端账号、端点矩阵 | ✅ 已有 | `shop-base/auth` + `shop-merchant` |
| 消息 | 站内、订阅消息、推送、受众解析 | ✅ 已有 | `shop-core/message` + `shop-notify` |
| 任务 | 调度、手动触发、worker | ✅ 已有 | `shop-job*` |
| 事件 | outbox 投递，跨域异步的唯一通道 | ✅ 已有 | `shop-base/event` |
| **打印** | **设备、模板、路由、任务、重打** | ❌ **缺，本期建** | **`shop-channel/print`（新）** |
| 能力开关 | 行业预设包 → 门店能力，唯一判定入口 | ❌ 缺，本期建 | `shop-base` + `shop-merchant` |

> 打印之所以进基座而不是跟着餐饮走：零售也出小票、快递也打面单，
> 而且**打印的本质是「把一条消息送到一台设备」，与订阅消息送到微信同构**。
> 让餐饮插件自带一套打印，等于让第二个行业再抄一遍设备管理、重试和补打。

## 2. 基座 · 标准可选（STD）—— 基座给实现，按门店开关

代码里只问能力，不问行业。**零售默认值这一列是硬约定**，写进 `sys_industry_capability` 的 `RETAIL` 行。

| 能力码 | 一句话 | 现状 | 零售默认 |
|---|---|---|---|
| `OFFLINE_PAY` | 到店/当面付，商家确认收款后进履约 | ✅ 已有 | 关（按资质授权开） |
| `PICKUP_SELF` | 到店自提 | ✅ 已有 | 开 |
| `PICKUP_NEIGHBOR` | 社区自提点 | ✅ 已有 | 开 |
| `DELIVERY_MERCHANT` | 商家自送 | ✅ 已有 | 开 |
| `DELIVERY_EXPRESS` | 第三方快递 | ✅ 已有 | 开 |
| `STORE_VERIFY` | 到店核销（服务品类） | ✅ 已有 | 关 |
| `APPOINTMENT` | 上门/到店预约，门店级时段容量 | ✅ 已有 | 关 |
| `RESOURCE_BOOKING` | **按资源**预约（指定技师/桌位/包间） | ⚠️ 需泛化 slot | 关 |
| `STAFF_PROFILE` | 服务人员档案（可不登录系统） | ❌ 缺 | 关 |
| `STAFF_SCHEDULE` | 排班规则 → 生成时段 | ❌ 缺 | 关 |
| `STORED_VALUE` | 储值（**预收款，不是营销让利**） | ❌ 缺 | 关 |
| `TIMES_CARD` | 次卡 / 疗程 | ❌ 缺 | 关 |
| `BUNDLE_SKU` | 组合商品（套餐 / 疗程包）—— 商品域，不是行业功能 | ❌ 缺 | 开 |
| `PRINT_RECEIPT` | 小票打印 | ❌ 缺（随打印基座建） | 关（无设备时无意义） |
| `PRINT_ROUTE_SPLIT` | 分单路由（一个事件出多张、按行匹配到不同设备） | ❌ 缺 | 关 |
| `PRINT_REPRINT` | 补打 / 重打 | ❌ 缺 | 开（有设备即应可用） |

**默认关的那一半才是生产常态。** 每条能力的开与关两个态都要有用例；只测开着的那一态等于没测。

## 3. 插件能力（PLUGIN）—— 基座只留扩展点

| 能力码 | 行业 | 为什么不进基座 |
|---|---|---|
| `TABLE_ORDERING` | 餐饮 | 桌台图、开台、并台、转台是一套自成体系的台账，零售一条都用不上 |
| `PAY_AFTER_SERVE` | 餐饮 | 「先吃后付」的**支付链路**在基座（`WAIT_OFFLINE_PAY` 已有），但**台账与结账编排**是行业的 |
| `KITCHEN_PRINT` | 餐饮 | 出品部门、催菜、退菜单 —— 打印**通道**在基座，**内容与路由条件**是行业的 |
| `SERVICE_WORK_ORDER` | 服务业 | 开单/换人/完成的工单流转 |
| `STAFF_COMMISSION` | 服务业 | 提成规则与归属判定 |
| `QUEUE_CALL` | 两者 | 排队叫号（美甲店也要，所以它是**插件间共享**的候选，不是餐饮专属） |

## 4. 判定入口只有一个

```java
// shop-base/spi/user/CapabilityPort.java
boolean enabled(String storeNo, String capability);
```

三态口径写死在这里，不许各处自己判：

| `mch_store_capability` 里的情况 | 结果 |
|---|---|
| 有行且 `enabled=1` | 开 |
| 有行且 `enabled=0` | 关 |
| **一行都没有** | 取 `sys_industry_capability` 该行业的 `default_on`；行业也没配 → **关** |

唯一例外：`APPOINTMENT` 沿用既有的「一个时段都没开 = 按旧口径放行」，
否则这批代码一上线，所有做上门服务的商家在开出时段之前全部接不了单。
**例外只此一条，写在这里，不允许再长第二条。**

---

## 5. 代码里唯一允许出现行业码的地方

开店（或运营改行业）时，把 `sys_industry_capability` 展开成 `mch_store_capability` 的行。
**此后没有任何业务代码读 `industry_code`。**
架构守卫要拦的就是这一条：除 `StoreProvisionService` 外，任何类引用行业常量即失败。
