# 核心能力清单（基座）

> 状态：草稿 · 待确认 · 创建 2026-08-27
> 关联：[TDD-行业包-机制与装配](../design/TDD-行业包-机制与装配.md) · [行业包功能清单](./行业包功能清单.md) · [ADR-019](../ADR/ADR-019-行业工作流做成独立行业包.md)
> 本册取代早先的《标准能力基线-零售为默认》，内容合并到此。

**基座 = 零售跑得起来的全集。** 零售不需要任何行业包。
每条能力都按同一模板写：现状 / 数据 / 接口 / 行业包能拿到什么 / 开关与零售默认。

**归属判据**（三条同时成立才进基座）：① 零售也要用；② 换行业只换数据不换代码；③ 被两个以上的域读。

**开关三态口径**（唯一判定处 `CoreCapabilityApi.enabled(storeNo, cap)`）：
有行按行；无行取 `sys_industry_capability` 的 `default_on`；再无 → **关**。
唯一例外是 `APPOINTMENT`（见 E2），**不许长出第二条例外**。

## A · 主体与门店

### A1 主体档案与准入 ✅
**职责**：主体、资质、法律形态、行业（通道准入）、押金、违规处置、经营范围。
**数据**：`mch_entity`（含 `industry` → `sys_industry`）、`mch_qualification`、`mch_deposit`、`mch_violation`、`mch_entity_community`。
**关键点**：`mch_entity.industry` 的语义是**支付通道准入**（能否小微进件）+ 强制积分，
**不是**「按什么流程做生意」。行业包的绑定是另一列（A3）。两者混用会让一个前端开关改掉商家的收款通道。
**行业包可见**：只读，`CoreMerchantApi.entity(entityNo)`。
**开关**：无（不可关闭）。

### A2 门店与经营模式 ✅
**职责**：门店、默认店、状态三档（ACTIVE/READONLY/SUSPENDED）、经营模式（自营/第三方）、渠道配置、营业时间。
**数据**：`mch_store`、`mch_fulfillment_channel`、`mch_channel_area`、`mch_store_category`。
**关键点**：`READONLY`（商家自助停用/降级）与 `SUSPENDED`（平台强制下线）必须是两个值 —— 处置中的店不能自己点两下解除。
**开关**：无。

### A3 行业包绑定 ❌
**职责**：这家门店按哪个行业包做生意。
**数据**：`ALTER TABLE mch_store ADD COLUMN industry_pkg VARCHAR(32) NOT NULL DEFAULT 'RETAIL'`。
**设计**：默认 `RETAIL` = 不装任何行业包也成立。改绑定时**重新展开能力行**（A4），已开的能力不自动关（商家可能已经在用）。
**关键点**：代码里唯一允许读 `industry_pkg` 的地方是开店/改店服务，此后无人再读；有闸门拦。
**开关**：无。

### A4 能力开关 ❌
**职责**：「这家店开没开某能力」的唯一判定处。
**数据**：
```sql
sys_industry_capability(industry_pkg, capability, default_on)   -- 行业预设包
mch_store_capability(store_no, capability, enabled)             -- 门店实际，唯一被代码读的表
```
**接口**：`CoreCapabilityApi.enabled(storeNo, cap)` / `enabledCaps(storeNo)`。
**取值域**：`Capabilities` 常量类（`shop-base/common/`，与 `Fulfillments`/`PayModes` 同构 —— 商品域、交易域、行业包都要用它）。
**关键点**：**默认关的那一半才是生产常态**。每条能力开/关两个态各要有用例，只测开着的那一态等于没测。
**开关**：无（它自己就是开关）。

## B · 商品

### B1 类目与规格模板 ✅
**职责**：平台类目树（带 `template`/`attrTemplate`/`qualificationRequired`）、规格维度与模板、商家规格覆盖。
**数据**：`prd_category`、`prd_spec_dim/_value`、`prd_spec_template`、`prd_merchant_spec*`、`prd_category_pay_mode`（平台×类目开关的现成范式）。
**行业包可见**：只读。**行业包不许建自己的商品类目** —— 菜品、服务项目都是商品，两套类目会让搜索、报表、审核各写两遍。
**开关**：无。

### B2 SKU 与门店价 ✅
**职责**：标品 SPU、商家 SKU、门店上架、门店定价。
**数据**：`prd_spu_std`、`prd_goods`、`prd_sku`、`prd_store_goods`、`prd_store_price`。
**关键点**：菜品 = SKU；服务项目 = SKU；套餐/疗程 = 组合 SKU（B4）。**行业包一件商品都不新建**。
**开关**：无。

### B3 门店库存与锁定 ✅
**职责**：门店库存、下单锁定、支付转实扣、超时释放。
**数据**：`prd_store_stock`、`prd_stock_lock`。
**关键点**：锁定用**带条件 UPDATE 判影响行数**，不是「先查再改」。资源占位（E2）、余额扣减（F2）沿用同一手法、同一理由。
**行业包可见**：只读余量。**扣减必须走基座**，理由同 F2。
**开关**：无。

### B4 组合商品（套餐 / 疗程包）❌
**职责**：一个 SKU 卖出去，核销 N 个子项。
**数据**：`prd_sku_bundle(bundle_sku_no, item_sku_no, qty, verify_mode)`；`verify_mode` = 一次性核销 / 逐项核销。
**关键点**：餐饮套餐与美业疗程包是**同一件事**，做在商品域，不在行业包 —— 否则做两遍且两边口径不同。
**开关**：`BUNDLE_SKU`，零售**开**。

## C · 交易

### C1 购物车与下单 ✅
**职责**：加购、结算试算、下单、取消。
**数据**：`trd_cart_item`、`ord_order`、`ord_sub_order`、`ord_item`。
**扩展点**：`CheckoutContributor.advise(ctx)` —— 行业包可在结账前**建议**（追加信息、阻断并给理由），**不能改价**。
**关键点**：不给 `ord_order` 加行业列。行业数据由行业包表持 `order_no`，方向是行业包 → 交易域。
**开关**：无。

### C2 订单状态机 ✅
**职责**：唯一一处判断「这个状态能不能变成那个状态」。主单 / 子单 / 售后三张图。
**数据**：`OrderStateMachine`（代码内常量图）、`ord_status_log`。
**关键点**：**行业台账状态（开台/出餐/结账/服务中）绝不进这张图** —— 一旦进去，零售和美业也要认它，而它们永远不会用。
**扩展点**：只有监听，没有干预（`OrderLifecycleListener`）。
**开关**：无。

### C3 履约方式取值域 ⚠️
**职责**：「这件商品支持怎么交付」的唯一取值域，同时决定支付成功后落哪个子单状态。
**数据**：`Fulfillments`（`shop-base/common`）+ `prd_goods.fulfillments`。
**现有**：`STORE_PICKUP` / `NEIGHBOR_PICKUP` / `MERCHANT_DELIVERY` / `EXPRESS` / `STORE_VERIFY` / `APPOINTMENT`。
**本期新增**：`DINE_IN`（堂食）—— 进 `SERVICE_LIKE`（付款后直接 `FULFILLING`，没有"待发货"），
**不进** `PHYSICAL`（不入新建商品默认集），**不进** `NEEDS_APPOINTMENT`。
**开关**：每种履约方式一个能力码（见附表），零售默认开四种实物履约。

### C4 售后 ✅
**职责**：申请、退款、驳回、申诉裁决，独立状态机。
**数据**：`ord_after_sale`。
**关键点**：行业包**不实现自己的退款**。「退菜」是台账动作，只有真退钱时才走基座售后。
**开关**：无。

### C5 评价 ✅
**职责**：订单评价与商家评分。
**关键点**：行业包可提供额外维度（如"技师服务"），但**存在基座的评价表里**，不另建表 —— 否则商家评分算不全。
**开关**：无。

## D · 支付

### D1 支付通道主数据 ✅
**职责**：通道是**表不是枚举**，带 `supports_subsidy/split/payout` 三个开关。
**数据**：`sys_pay_channel`。
**关键点**：新增付款方式（线下、储值）是**加一行数据**，不是加一处 `if`。这是本方案多处复用成立的根因。
**开关**：无。

### D2 线上支付与回调 ✅
**职责**：预下单、回调、幂等 `markPaid`、退款。
**关键点**：`markPaid(orderNo, payChannel, tradeNo)` 幂等且**不关心钱从哪来** —— 微信回调、线下确认、储值扣款是同一个方法的三个调用方。
不复用它就要把库存转实扣、入会、发分、结算触发全部重写一遍。
**开关**：无。

### D3 线下收款 / 先享后付 ✅（口径需补一条）
**职责**：下单落 `WAIT_OFFLINE_PAY`，商家确认收款后 `markPaid`，平台不碰这笔钱、不抽佣。
**本期唯一改动**：超时取消时长改为**按门店取配置**，且**台账未结账时不许自动取消** ——
现有规则会把正在吃的桌子取消掉。
**扩展点**：`CoreOrderApi.confirmOfflinePaid(...)` 给行业包结账时调。
**开关**：`OFFLINE_PAY`（按资质授权），零售默认**关**。

## E · 资源与预约

### E1 可占资源 ❌
**职责**：门店里「数量有限、按时间被占用」的东西 —— 桌台、技师、工位、包间**共用一张表**。
**数据**：
```sql
mch_resource(resource_no, store_no, resource_type, name, capacity, status, attrs)
-- resource_type: TABLE / STAFF / SEAT / ROOM，语义由行业包的 ResourceTypeProvider 提供
```
**接口**：`CoreResourceApi.occupy/release/list`。
**关键点**：**桌台 ≡ 技师 ≡ 工位**。看不穿这处同构就会做两套，那是本方案里最大的一处浪费。
**开关**：`RESOURCE_BOOKING`，零售默认**关**。

### E2 时段与占位 ⚠️
**职责**：可约时段、容量、并发安全的占位与释放。
**现有**：`mch_appointment_slot(store_no, start_at, end_at, capacity, booked)` + `AppointmentSlotPort` 三动作 + 场景测试。
**本期扩展**：加 `resource_no VARCHAR(32) NULL`（**NULL = 门店级时段，旧行为不变**）；
新增 `listByResource(...)` 供 C 端选人。**`tryBook` 签名与并发手法一个字不改**。
**关键点**：这是**唯一要动既有已测能力**的地方 —— 容量计数口径必须能按资源分组，纯扩展绕不开。按 P6 需确认。
**例外口径**：「一个时段都没开 = 按旧口径放行」保留（否则存量上门商家上线即接不了单）。**全系统仅此一条例外。**
**开关**：`APPOINTMENT` / `RESOURCE_BOOKING`。

### E3 服务人员档案 ❌
**职责**：被顾客**选择**的人。与登录账号、权限角色是三件事。
**数据**：
```sql
mch_staff(staff_no, entity_no, store_no, user_no NULL, name, level_code, avatar, status)
mch_staff_skill(staff_no, goods_no)
```
**关键点**：`user_no` 可空 —— **技师可能根本不登录系统**。硬绑账号会让商家为了排班给每个师傅开账号。
`mch_resource` 里 `resource_type='STAFF'` 的行通过 `attrs.staff_no` 指回来：排期只认资源，档案只管人。
**开关**：`STAFF_PROFILE`，零售默认**关**。

### E4 排班 ❌
**职责**：按规则**生成**时段，不是另一套时段。
**数据**：`mch_schedule_rule(rule_no, store_no, resource_no, rrule, capacity, valid_from, valid_to)`；生成结果**写既有 slot 表**。
**设计**：生成由定时任务滚动做（复用 `JobHandler`），提前 N 天；改规则只影响未来未占用的时段。
**关键点**：排班**不引入第二种时段模型**。引入了，「这个点能不能约」就有两个真源。
**开关**：`STAFF_SCHEDULE`，零售默认**关**。

## F · 会员

### F1 会员与门店会员 ✅
**数据**：`mbr_member`、`mbr_member_store`、`mbr_tag`、`mbr_segment`、`mbr_reach_log`。
**关键点**：**会员是平台级的，跨行业统一** —— 这是「一套商户系统」最值钱的一条，不许行业包另建会员。
**开关**：无。

### F2 会员资产：储值与次卡 ❌
**职责**：储值余额、次卡剩余次数、有效期、流水。
**数据**：
```sql
mbr_asset_account(account_no, member_no, entity_no, asset_type, balance, status)  -- STORED_VALUE / TIMES
mbr_asset_txn(txn_no, account_no, direction, amount, biz_type, order_no, ...)     -- 唯一的余额变更入口
mbr_card(card_no, member_no, card_def_no, remain_times, expire_at, status)
```
**三条写死的规矩**：
1. **余额变更只走流水表**，绝不无流水地 `UPDATE balance`；扣减用带条件 UPDATE 判影响行数；
2. **储值支付是一种 `sys_pay_channel`**（`supports_split=0, supports_payout=0`），于是 `markPaid` 不用认识储值；
3. **余额归主体**（`entity_no`），跨门店通用与否由能力开关决定。
**关键点**：储值是**预收款**不是营销让利，口径错了是财务问题。行业包只能通过 `CoreMemberApi` 扣，不许自己算。
**开关**：`STORED_VALUE` / `TIMES_CARD`，零售默认**关**。

### F3 触达 ✅
**职责**：站内信、订阅消息、推送、受众解析。
**扩展点**：行业包可发自己的消息类型，走基座通道。
**开关**：无。

## G · 营销

### G1 活动与券 ✅
**数据**：`pmt_activity*`、`pmt_coupon*`、`pmt_user_coupon`、`pmt_apply`。
**关键点**：行业包**不做自己的优惠**。「餐饮满减」「办卡送次数」都是活动配置，不是新代码。
唯一例外候选是「首单/储值赠送」，属 F2 的派生，仍在基座。
**开关**：无。

## H · 结算

### H1 账单、对账、分账 ✅
**数据**：`shop-settle` 全域。两条状态机：自营（对账→确认→付款）与第三方（分账）。
**关键点**：行业包**不参与结算**。所有钱最终都表达为基座订单 + 通道，结算只认这两样。
**开关**：无。

## I · 设备与打印（本期从零建，全部进基座）

> 打印进基座的理由：零售也出小票、快递也打面单；且它的本质是「把一条消息送到一台设备」，
> 与订阅消息送到微信同构。让餐饮包自带打印，第二个行业就要把设备管理、重试、补打再抄一遍。

### I1 打印设备 ❌
**数据**：`prn_printer(printer_no, store_no, vendor, device_sn, secret, status, last_seen_at)`。
**设计**：`vendor` 适配层放 `shop-channel/print/vendor/`（飞鹅、易联云、365…），**只装适配器不装业务判断**（与既有 channel 域同规矩）。
**开关**：无（有设备才有意义）。

### I2 打印模板 ❌
**数据**：`prn_template(template_code, store_no NULL, scene, content, updated_by)`；`store_no` 为空 = 平台默认模板。
**设计**：模板**存库不写代码**（零硬编码）。行业包在迁移里 INSERT 自己的默认模板。
**开关**：无。

### I3 打印路由 ❌
**数据**：`prn_route(route_no, store_no, scene, match_expr, printer_no, copies, enabled)`。
**设计**：**行业差异全落在这张表的数据行里** —— 餐饮按出品部门分单到热菜/凉菜/水吧，美业出服务单，零售出小票。**代码里没有行业分支**。
`match_expr` 用受限表达式（字段白名单），不许写成可执行脚本。
**开关**：`PRINT_ROUTE_SPLIT`，零售默认**关**（零售通常一台机器）。

### I4 打印任务与重打 ❌
**数据**：`prn_job(job_no, store_no, printer_no, template_code, payload, status, retry_count, last_error)`。
**设计**：**复用 outbox 语义**（at-least-once + 幂等键），打印不可丢；失败重试有上限，超限置 `FAILED` 并在 B 端可见可补打。
**扩展点**：`PrintPayloadProvider.render(ctx)` —— 行业包只回答「这一单该打什么」。
**触发**：**订阅事件，不在交易域调用打印**。
**关键点**：打印机是硬件，自动化测试只能覆盖「任务生成 + 路由命中 + 重试」，**真机出票必须人工验收**，不接受假打印机的绿测。
**开关**：`PRINT_RECEIPT`（默认关，无设备无意义）/ `PRINT_REPRINT`（有设备即开）。

## J · 平台横切

### J1 权限与角色 ✅
**数据**：`Perms`（68 码）+ `mch_role`/`mch_store_role`；归属登记在 `scripts/perm-endpoint-map.mjs`，由矩阵测试逐格钉住。
**行业包**：自带权限码，注册进行业段（`food:table:*`），**必须同步登记并重跑生成器**，否则 pre-push 红。
**开关**：无。

### J2 菜单 ✅
**关键点**：**运营端菜单在库里**，只改 `nav.ts` 接真后端看不到。行业包菜单由其迁移 INSERT，按能力开关可见。
**开关**：无。

### J3 领域事件（outbox）✅
**数据**：`sys_outbox` + `OutboxDispatchJob` + `OutboxConsumer`。
**行业包**：实现 `OrderLifecycleListener`，由基座桥接到 outbox。语义 **at-least-once，实现者自己保证幂等**。
**关键点**：这是行业包接入基座的**主通道**。同步调用只保留结账等必须同事务的少数点。
**开关**：无。

### J4 定时任务 ✅
**数据**：`shop-job*`，`JobHandler` 契约 + 手动触发。
**行业包**：直接实现 `JobHandler`（排班生成、超时未结账巡检），**不另造调度**。
**开关**：无。

### J5 幂等 ✅
**数据**：`sys_idem_record`。下单/支付/退款/核销必接。
**行业包**：开台、结账、耗卡同样必须接。
**开关**：无。
