## 1. 检查结论（按严重度）

### 1.1 结构问题

| # | 问题 | 现状 | 建议 |
|---|---|---|---|
| S1 | **同一功能挂两处** | 「退款分账」`/finance?tab=refund-back` 同时在 售后治理 与 经营财务 | 只留经营财务；售后治理删除该叶 |
| S2 | **支付事实在 shop 内重复** | 经营财务下挂 8 个「支付运营」叶（支付单/支付异常/退款复核/业务通知/收款码/应用授权/请求记录/平台密钥），与 near-pay 的 TR01/TR08/TR03/SY05/SY06/凭据 重复；订单履约下还有 3 个待建支付叶（收款核对/掉单补偿/关单规则） | 按 §6「支付订单、渠道清结算事实归 near-pay」：8 叶标「过渡兼容」，near-pay live 覆盖后下线；订单履约的「收款核对」「掉单补偿」删除（指向 near-pay），「关单规则」属订单超时规则，留在订单组并改用订单规则码 |
| S3 | **一级目录过碎** | 16 个一级；「会员管理」(3 叶)、「积分运营」(5 叶) 与「会员营销」分立；「内容管理」与「消息客服」分立；「风控」单列 3 叶 | 合并为 13 个一级（§2）：会员+积分 并入会员营销，内容+消息 合为内容客服，风控改为审核风控（为跨域审核待办留位） |
| S4 | **业务配置放在系统设置** | 系统设置下有 门店行业 / 行业准入 / 经营授权 / 范围开关（经营范围类） | 移到商品资料「基础资料」组；系统设置只留账号、权限、运行配置 |
| S5 | **同名菜单** | 「商品分类」同时出现在 商品资料 与 经营服务 | 经营服务那条改名「服务分类」 |
| S6 | **按状态/渠道拆菜单** | 消息客服 9 个叶共用 `message:template:read`，其中 短信/邮件/微信订阅/应用推送/站内模板 是同一页的渠道 Tab | 合为「通道模板」一叶，渠道用页内 Tab（§1 原则：状态/渠道用页内筛选） |
| S7 | 只有一个角色能进的菜单放在全员模块里 | 「准入押金」只有财务可见，却挂在商户中心 | 移到经营财务「保证金」组 |
| S8 | 截断式短名 | 「当面付禁」 | 改「限付类目」 |

### 1.2 授权问题

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| P1 | **经营服务 8/10 叶无内置角色可见** | `commerce:*` 码没有分给任何内置角色，只有超管能用；服务运营岗不存在 | 新建「服务运营」自定义角色并授予 commerce 码；财务补 `commerce:mall:offline:review`（线下核款本就是财务动作） |
| P2 | **积分配置用财务读码门着** | 积分 5 叶全部 `finance:settle:read`：营销运营配不了赠送规则，财务却拿着规则配置入口 | 拆码 `points:rule:read/update`（营销配）与 `points:ledger:read`（财务查办）；需 TDD |
| P3 | **系统管理不能管账号** | 运营账号/角色权限/菜单顺序 只有超管可见；TECH_OPS 只拿运行配置 | 建「系统管理」自定义角色 = TECH_OPS 码 + `iam:staff:*` + `iam:role:grant`；角色授权改动须另一人复核。**SUPER_ADMIN 仅作应急**，不能当日常系统管理 |
| P4 | **没有只读审计岗** | ANALYST 只有 `community:read`；AUDITOR 是审核岗且带写权限 | 新建「审计」自定义角色：全量 `*:read` 脱敏读 + `iam:audit:read`，无任何 update/handle/audit 码；ANALYST 并入 |
| P5 | **审核岗带配置权** | AUDITOR 持有 `review:score:update`、`content:material:update`（评分参数、榜单问答可改） | 收回两码，审核只「查审」 |
| P6 | **制审不分离** | GOODS_OPS 同时 `product:sku:audit`；CAMPAIGN_OPS 同时 `content:material:update` 与 `:audit`；BD 同时 `apply:onbehalf` 与 `apply:audit`（后者已有数据层拦自审） | 商品审核、内容审核收归 AUDITOR；保留 BD 现状（数据层已拦） |
| P7 | **会员 PII 授给商品运营** | 会员名单、人档 只有 GOODS_OPS 可见；营销运营反而看不到 | 会员名单/触达 → 营销运营；人档（PII）→ 客服、风控，商品运营收回 |
| P8 | **行业范围配置在社区运营手里** | `system:industry:*` 只给 COMMUNITY_OPS | 行业准入/范围开关 → 行业运营配、商户运营查；社区运营是否保留待确认 |
| P9 | **一个码门住多种动作** | `merchant:merchant:read` 同时门住 商家档案、信用档案、链条画像、**套餐授予**、**档位定义**；`merchant:admission:read` 同时门住 押金 与 进件看板；`store:page:audit` 门住 获客效果 | 套餐两叶改 `commerce:plan:*`；进件看板拆 `merchant:onboarding:read`（给 BD 追卡点而不暴露押金）；获客效果拆 `store:effect:read` |
| P10 | UI 码与后端码错位 | 「预售额度」UI 码 `product:stock:update` → 后端 `product:sku:audit`，于是审核员能进改库存额度的页 | 预售额度改用独立后端码，审核员只读 |

## 3. 角色定义

| 岗位 | 英文 | 现有角色码（166 存量码） | 职责边界 |
|---|---|---|---|
| 商户运营 | Merchant Ops | MERCHANT_BD（BD） | 入驻、主体门店、信用处置、门店展示获客、求团撮合 |
| 行业运营 | Industry Ops | PRODUCT_OPS（GOODS_OPS） | 类目规格、商品、库存、行业范围、品类营销 |
| 营销运营 | Marketing Ops | CAMPAIGN_OPS | 会员、积分规则、券、活动、内容素材、增长 |
| 服务运营 | Service Ops | **新建自定义角色** | 平台向商家卖的套餐/服务商品、购买订单、代购、权益 |
| 客服 | Support | SUPPORT | 订单异常、售后裁决、评价、消息工单 |
| 履约运营 | Fulfillment Ops | COMMUNITY_OPS | 社区网格、自提点、到货分拣、核销、物流 |
| 财务 | Finance | FINANCE | 结算、发票、费率、保证金、核款、退款执行 |
| 审核 | Reviewer | AUDITOR | 被分配的审核类型：入驻、商品、内容、评价、店招 |
| 风控 | Risk | RISK | 风险事件、黑名单、拦截规则、违规线索 |
| 审计 | Auditor (read-only) | **新建自定义角色**（ANALYST 并入） | 全域脱敏只读 + 操作审计 |
| 系统管理 | Admin | TECH_OPS + 自定义授权 | 账号、角色、菜单、运行配置；**不含业务与资金** |

SUPER_ADMIN 持 `*`，只作应急/初始化账号，不列入矩阵；ELEC_ADMIN 已退役（只剩看板），建议停用。
