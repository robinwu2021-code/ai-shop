## 为什么是 ai-shop 做

ShareHub 决定**不自建调度器**，直接用 ai-shop 已在跑的任务服务实例
（ADR-020 §六 / ADR-024）。任务模块本来就与业务无关（包名已是 `ai.neargo.job.*`、
`job-api` 零依赖、有测试守着「classpath 上没有 MyBatis、没有任何业务模块」），
所以服务留在 ai-shop，ShareHub 只做任务目标。

**它现在挡着 ShareHub 的排期。** ShareHub 侧已经实测确认：

- `backend/pom.xml` 的 enforcer 明令禁止依赖 `ai.neargo.shop:*`（`<fail>true</fail>`），
  放行名单写的是 `shop-job-api` / `shop-job-target` —— **这两个坐标今天都不存在**
  （ai-shop 这边模块叫 `job/job-api`，`shop-job-target` 尚未收拢）；
- 于是 ShareHub **连 `JobHandler` 都写不了**，接口类引不进来。

ShareHub 已落地的定时推送只能先挂一个手动扫描端点顶着
（`POST /api/user/push-messages/sweep-due`），并在台账里注明是临时入口。
本工单做完，那个端点连同台账条目一起删。

## 改什么（MJ1–MJ8）

| # | 项 | 今天 | 改成 | 为什么 |
|---|---|---|---|---|
| **MJ1** | `job_definition` | `uk_job_def_name(job_name)`，无系统列 | 加 `system VARCHAR(16) NOT NULL DEFAULT 'SHOP'`；唯一键改 `uk(system, job_name)` | 两个系统都会有 `outbox-dispatch` 这种通用任务名，全局唯一**必撞** |
| **MJ2** | `job_run` · `job_log` | 无系统列 | 同样加 `system`，**不靠 join 反查** | 运营端列表、日志清理、失败告警都要按系统过滤；join 反查在清理大表时代价高 |
| **MJ3** | worker 配置 | `worker.targets: {PLATFORM: url}` + **一把** `worker.token` | 按系统分组：`worker.systems.<SYS>.targets.<TARGET>.{url,token}` | 一个系统多个目标进程；**每个目标一把令牌**，泄露一把不波及其他系统 |
| **MJ4** | 声明同步 | 按 target 拉 `/internal/job/declarations` | 按 `(system, target)` 拉并落 `system`；某系统不可达时**只把该系统的任务标 `missing`** | 一个系统停机不该让另一个系统的任务定义被标成失踪 |
| **MJ5** | 运营端接口 | `OpsJobController` 直读 job 库、无系统过滤 | 按**登录人所属系统**过滤（不是按请求参数） | 否则 ShareHub 运营能看到并**触发** ai-shop 的任务 |
| **MJ6** | 配置前缀 | `shop.job.*` | **保留不动**；库名 `ai_shop_job` 也保留 | 改前缀要动两边配置与部署脚本，收益只是名字好看 |
| **MJ7** | 目标侧构件 | 小类散在 `shop-base/job` 与 `shop-app` | 收成 `shop-job-target`：注册表 · `/internal/job/**` 端点 · ShedLock 装配 · 进程内模式 | ShareHub 三个目标进程要装配同一套 |
| **MJ8** | 发布 | 不发布 | CI 发布 `shop-job-api` · `shop-job-target` · `shop-job`(jar) 到 Nexus | ShareHub 要依赖前两个 |

**迁移**：一条 `ALTER` 加列（默认 `SHOP`）+ 一条改唯一键；**存量数据不动**。

⚠️ MJ5 用「登录人所属系统」而不是请求参数：按参数过滤等于没过滤，
任何人把 `system=SHOP` 换成 `system=SHAREHUB` 就跨系统了。

⚠️ 坐标命名：放行名单写死的是 `shop-job-api` / `shop-job-target`。
若 ai-shop 决定沿用 `job-api` 这个名字，**要回来告诉 ShareHub 改 enforcer 的 includes**，
否则发布了也依赖不进去。

## ShareHub 侧会做什么（不用 ai-shop 管，列出来是为了说明接口面）

- 三个目标进程装 `shop-job-target`，暴露 `/internal/job/declarations` 与
  `/internal/job/{handler}/run`（令牌校验 + ShedLock 抢锁，抢不到返 409 → 记 SKIPPED）
- 业务只写 `JobHandler` + `JobDeclaration`，**不写 `@Scheduled`**（ShareHub 侧有卡口禁止）
- 首批任务：`outbox-dispatch` · `push-sweep-due` · `session-purge` ·
  `order-pending-sweep` · `order-overdue-scan`

## 验收

- [ ] 同名任务（如 `outbox-dispatch`）在 `SHOP` 与 `SHAREHUB` 两个系统下**各自存在**，互不覆盖
- [ ] 一个系统的目标进程停机，**另一个系统的任务定义不被标 `missing`**
- [ ] 用 ai-shop 的运营账号调 job 接口，**取不到 `system=SHAREHUB` 的任务**（换参数也不行）
- [ ] 每个目标一把令牌；拿 A 目标的令牌调 B 目标被拒
- [ ] `shop-job-api` / `shop-job-target` 在 Nexus 上可解析，ShareHub 侧 `mvn` 能拉到
- [ ] 存量 `SHOP` 任务迁移后照常跑（加列默认值 + 唯一键变更不影响既有行）
