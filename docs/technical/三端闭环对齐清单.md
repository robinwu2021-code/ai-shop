> 2026-08-10 · 与另两份对齐文档**看的不是同一件事**，三份配合使用：
>

> | [三端角色权限功能对齐清单](../requirements/三端角色权限功能对齐清单.md) | 角色与权限码在三端是否一致 |

---

## 一、为什么要单独看这一维

最近修掉的两个缺陷是同一个形状：

- **售后仲裁**：用户能把争议上升到平台（`escalate`），平台**没有任何接口能裁**。
  单子停在 `ARBITRATING`，用户和商家都在等一个不会来的结果
- **差评申诉**：商家能申诉，平台没有裁决台

两者的共同点值得记住：**数据模型里状态是全的，端点是缺的**。
所以任何按「表建了没有」「字段有没有」做的检查都发现不了它们——
`aft_after_sale.status` 里 `ARBITRATING` 一直好好地在枚举里。

**机械可查的信号**：某个状态/字段在数据模型里存在，
但**全仓库没有任何端点写它**。下面的断裂全部按这个信号找出来，逐条附证据。

## 三、断裂逐条

### 3.1 🔴 客服工单：用户能提，没有人能回

**证据**：`MsgTicket` 实体有三个字段——

```java
private String reply;
private Long repliedAt;
private String repliedBy;   // 注释：记客服身份 —— 代客操作要能追到人（M6 权限边界）
```

**全仓库没有任何端点写这三个字段**。C 端有 `POST /mp/ticket`（提单）、
`GET /mp/ticket`（看自己的），平台端 `/ops/**` 里工单相关端点**一条都没有**。

也就是说：用户提交工单 → 落库 → **石沉大海**。而且 C 端还有个「查看工单详情」
的页面在等 `reply` 字段，用户会反复点开看有没有回复。

这条的严重性高于其他几条：**客服是所有其他缺陷的兜底**。
其他地方出了问题，用户最后一招是找客服；这条断了，兜底就没了。

> 字段注释写着「代客操作要能追到人」——**设计时就想好了要有客服回复**，
> 只是那一半从来没实现。

**[功能点矩阵](./三端功能点矩阵.md)又往下挖了一层**，比我最初的判断更糟：

| 端 | 情况 |
|---|---|
| C 端 | 3 条已实现（提单/列表/详情），但**三份 OpenAPI 里都没有它们**——契约本身漏了 |
| 平台端 | 契约声明 7 条（`listTickets`、`assign`、`close`、`proxy-actions`、FAQ 三条），**实现 0** |

**注意平台端那 7 条里没有「回复工单」。** 有分派、有关闭、有代客操作留痕，
唯独没有把 `reply` 写进去的那个动作。也就是说：实体留了字段、C 端留了展示位，
而**契约层面从来没定义过「客服回复用户」这个功能点**。

这比「实现漏了」严重一档——漏实现是排期问题，漏定义是**没人发现这件事需要做**。
补的时候要先补契约，别直接写端点。

### 3.2 🔴 资金没有出口

**证据**：B 端 `/biz/settle/**` 只有三条，**全是只读**：

| 端点 | 作用 |
|---|---|
| `GET /biz/settle/bills` | 看结算单列表 |
| `GET /biz/settle/bills/{settleNo}` | 看单张 |
| `GET /biz/settle/rate-card` | 看费率卡 |

**没有发起提现的端点**；平台端也没有任何资金审批端点
（`/ops/**` 里与资金相关的只有 `after-sales/fast-refund-rule`）。
而 ops-web 声明了 **finance 15 条**，后端实现 **0**。

**这条需要先确认产品意图**，不能直接判为缺陷：

- 若走**电商收付通分账**，钱直接进商家二级商户，商家自己在微信侧提现——
  那平台确实不需要提现审批，只需要**对账与查询**
- 若平台**代收代付后再结给商家**，那必须有提现发起与审批，现在是**完全没有**

两种模式的资金链路和合规要求差别很大。**先定这个，再谈补哪些端点。**

### 3.3 🔴 运营员工与权限：只能看，不能管

**证据**：`/ops/staff` 只有 `GET` 一条。不能新增运营账号、不能停用、不能改角色。

这与[安全整改方案](./安全整改方案-认证与账号体系.md) §7.3 是同一个问题的两面：
`Perms.java` 里角色→权限码是**硬编码**的，注释自己写着「一期硬编码，M9b 接 DB」。
**因为映射在代码里，所以后台没法做管理界面**——不是忘了做，是做不了。

顺序上：先把角色→权限码入库（F1），员工管理界面才有意义。

### 3.4 🔴 营销与拼团：平台没有干预手段

C 端 16 条拼团 + 4 条优惠券，B 端 4 条活动，**平台端 0 条**。

后果具体说：商家发了一张规则写错的券（比如面额超过商品价），
或者开了一个违规团，**平台没有任何下架/中止的手段**——只能去数据库改。
运营端 marketing 声明 21 条、group 声明 8 条，后端都是 0。

> 这类「平台兜底干预」的端点容易被排在后面，因为正常流程不需要它。
> 但它恰恰是**出事时唯一的手段**，而出事是迟早的。

### 3.5 🟡 积分：只有行业级开关，没有单点调整

平台端唯一的积分相关端点是 `POST /ops/industries/{industry}/points-forced`
（按行业强制开启）。**没有**针对单个商家或单个用户的积分调整与冲正。

积分是**有资金属性**的（可抵扣）。发错了、算错了、被刷了，
现在没有任何后台手段能改——只能改库。

### 3.6 ⬜ 风控与举报：三端都不存在

C 端**没有举报入口**。`POST /mp/attribution/report` 是**归因上报**，
不是用户举报，名字容易误导。ops-web 的 risk 模块声明 7 条，后端 0。

这条与上面几条不同：**它不是断裂，是整块没做**。
列在这里是因为 §3.1 的工单目前实际承担了举报的角色——
而工单本身也是断的。

## 四、建议顺序

按「断了会怎样」排，不按工作量排。

| 序 | 做什么 | 理由 |
|---|---|---|
| 1 | **工单回复**（§3.1） | 客服是所有缺陷的兜底，且改动最小：一个 `/ops/tickets` 列表 + 一个回复端点，字段都是现成的 |
| 2 | **确认资金模式**（§3.2） | 不是写代码，是做决定。决定之前写的任何结算端点都可能白写 |
| 3 | **角色→权限码入库**（§3.3 前置） | 它挡着员工管理，也挡着[安全方案](./安全整改方案-认证与账号体系.md)的 F1/G1 |
| 4 | **平台干预：下架券/中止团**（§3.4） | 只做「停」不做「改」——出事时能止损就够，改由商家自己去改 |
| 5 | 积分冲正（§3.5） | 有资金属性，但发生频率低于上面几条 |

### 不做什么

- **不要按 ops-web 声明的 187 条去补**。那是前端按理想形态画的，
  其中相当一部分（内容、增长、风控）是整块的新功能，不是「补齐」
- **不要先做风控**（§3.6）。它依赖举报入口、依赖工单、依赖处置手段，
  前面几条没通之前做风控，等于建一个没有输入也没有输出的模块

## 五、边界

- **本文只看后端端点是否存在**，不看前端页面有没有接。
  「后端有、前端没接」的情况见[三端全栈对齐清单](./三端全栈对齐清单.md)
- **§3.2 的判断依赖产品决策**，在资金模式确认之前，那一条不该被当作缺陷计入进度
- 端点数是按 `@*Mapping` 数出来的，**一个端点的能力大小不等价**——
  `/ops/staff` 一条只读和 `/mp/order` 十条不是同一个量级。
  这张表用来找**零**，不适合用来比大小
