# 多门店：现状盘点与方案

> 2026-08-10 · 起因：全链路回归跑完后要判断「一个商家开第二家店」现在能不能走通。
> 结论先说：**骨架已经搭好了，但只有履约那一段真的通到底；商品、库存、结算、营销全在主体级。**

---

## 1. 现状：一句话

> **门店已经是「顾客感知的边界」，但还不是「经营的边界」。**

一家主体开第二家店，今天会发生的事是：
两家店卖**同一批商品**、共用**同一份库存**、共用**同一套营销活动**、
结算**混在一张账单里**——只有「这单是哪家店发的货」分得开。

---

## 2. 已经有的（骨架完整）

| 项 | 状态 |
|---|---|
| `mch_store` 表 | ✅ 有 `store_no` / `name` / `is_default` / `status` / `pay_merchant_no` / 装修字段 |
| 一主体多店 | ✅ 建表就支持；`is_default` 保证「找不到具体门店时去哪」有答案 |
| **每店独立收款号** | ✅ `pay_merchant_no` + `payment_changed_at`（切换有审计） |
| 员工按店授权 | ✅ `mch_store_role`（哪个员工能管哪几家店） |
| 订单落店 | ✅ `ord_sub_order.store_no` 双写（`entity_no` 结算 / `store_no` 履约） |
| B 端门店管理 | ✅ `/biz/store/list`、`/biz/store/create`、店铺码、分享物料 |
| 门店装修审核 | ✅ `mch_store_audit` + `/ops/stores/audits` |
| C 端门店主页 | ✅ 有独立页面与收藏（`usr_store_favorite`） |

`OrdSubOrder.storeNo` 的注释把这个设计讲得很清楚：

> 「双写门店：`entity_no` 是**结算键**（分账/积分/对账都按它），
> `store_no` 是**履约键**（发货/自提/评价/门店报表按它）。
> 单店时两者恒等 —— 这正是多门店能分阶段发布的原因。」

**这个分层是对的**，也是后面所有工作能增量做的前提。

---

## 3. 缺的（按「开第二家店那天会先撞上哪个」排序）

全库带 `store_no` 的表只有 **3 张**：`mch_store` / `mch_store_role` / `ord_sub_order`。
其余全部只有 `entity_no`。这句话本身就是缺口清单。

### 3.1 库存不分店 🔴 最先撞上

`prd_sku` 的唯一键是 `(entity_no, sku_no, market)`——**没有 store_no**。

后果：文三路店卖光了，古墩路店也显示无货；反过来，顾客在 A 店下单，
库存从「全公司总量」里扣，而货其实在 B 店。**自提场景下这是直接的履约事故**：
顾客到店取不到货。

> 这一条不解决，多门店就不能开给真实商家用。

### 3.2 商品不分店

`prd_goods` 只有 `entity_no`。两家店必然卖同一批商品、同一个价。

真实小店不是这样：文三路店卖早点、古墩路店卖生鲜；同一款米在两个小区可以差两块钱。

### 3.3 营销活动不分店

`mkt_campaign.entity_no NOT NULL`，没有 store 维度。
今天刚接通的四种活动（满减/特价/买赠/店铺券）**一律全主体生效**。
「新店开业第一周满减」这种最常见的诉求做不了。

### 3.4 结算不分店

`stl_bill` 只有 `entity_no`。两家店的钱混在一张账单里，
而 `mch_store.pay_merchant_no` **已经支持每店不同收款号**——
于是出现一个矛盾：钱可以打到两个不同的账户，账却只有一本。

> 这是目前模型里**最不自洽**的一处：收款分了，结算没分。

### 3.5 自提点与门店没有关联

`cmt_pickup_point.owner_ref` 在 `type=STORE` 时存的是 **`entity_no`**，不是 `store_no`。
所以「这个自提点属于哪家店」表达不了，多店时无法判断货该送到哪个点。

### 3.6 B 端没有「当前门店」这个上下文

`b-app` 存了 `shbr_store_no`，但工作台、商品、订单、营销都不按它过滤。
店长登录后看到的是全公司的数据 —— 而 `mch_store_role` 明明已经限定了他能管哪几家。
**授权模型做了，消费方没接**（与本轮反复出现的「有录入没有消费方」同形状）。

---

## 4. 方案

### 4.0 一条贯穿的原则

> **`entity_no` 管钱与合规，`store_no` 管货与人。**

每加一张表的 `store_no` 之前先问：这件事是「公司层面的」还是「这家店的」。
答错会让迁移反复做——比如把结算改成按店，就等于承认每家店是独立纳税主体，
那不是产品决定能改的。

### 4.1 P0 · 库存分店（不做这个，其余都不能上线）

| 动作 | 说明 |
|---|---|
| 新表 `prd_store_stock(store_no, sku_no, stock, locked_stock)` | **不动 `prd_sku.stock`** —— 它作为「总量」保留，避免一次性迁移 |
| `StockPort` 增加 store 维度 | 下单时按 `cmd.pickupNo → store_no` 扣对应店的库存 |
| 单店兼容 | 只有一家店时，`store_no = 默认店`，行为与今天完全一致 |

**验收**：两家店各 10 件，A 店卖光后 B 店仍可下单；A 店下单不扣 B 店的数。

### 4.2 P1 · 商品上架分店

不改 `prd_goods`（商品定义仍在主体级——同一款米就是同一款米），
新增 `prd_store_goods(store_no, goods_no, on_sale, price_override)`。

**为什么是「上架关系」而不是「商品复制」**：复制会让改一次标题要改 N 遍，
而且历史订单的快照本来就固化了，不需要靠复制来保历史。

### 4.3 P2 · 营销分店

`mkt_campaign` 加 `store_no`（可空 = 全主体）。
可空是刻意的：「全店满减」与「新店开业满减」都要能表达。
`CampaignPort` 的三个方法各加一个 store 参数。

### 4.4 P3 · 自提点归属改到门店

`cmt_pickup_point.owner_ref` 在 `type=STORE` 时改存 `store_no`。
**要迁移历史数据**（现存的是 entity_no），且要在同一个版本里改完读写两侧。

### 4.5 P4 · 结算分店（需要业务先答一个问题）

> **两家店是分别结算还是合并结算？**

- 分别结算 → `stl_bill` 加 `store_no`，与已有的 `pay_merchant_no` 自洽
- 合并结算 → 那 `pay_merchant_no` 按店配置就没有意义，应该收回到主体级

**现在两者并存是不自洽的**，必须选一个。我倾向分别结算——
每店独立收款号这个能力已经做了，且真实场景里加盟店的账本来就该分开。

### 4.6 P5 · B 端接上「当前门店」上下文

工作台/商品/订单/营销按 `shbr_store_no` 过滤；店长只看得到自己管的店。
`mch_store_role` 已经有数据，缺的是消费方。

---

## 5. 建议的顺序与判据

```
P0 库存分店  ←── 不做这个，多门店不能开给真实商家（会出履约事故）
   ↓
P5 B 端门店上下文  ←── 与 P0 同批：库存分了，界面得能选店
   ↓
P1 商品上架分店
   ↓
P3 自提点归属（要数据迁移，单独一批）
   ↓
P2 营销分店
   ↓
P4 结算分店  ←── 卡在业务问题上，先回答再动
```

**每一批都要保证单店行为逐字不变** —— 现在所有真实商家都是单店，
任何一次多门店改造让单店行为变了，都是拿全量用户给一个还没人用的功能试错。

---

## 6. 现在就可以做的一件小事

`ord_sub_order.store_no` 已经在写，但**没有任何按门店的报表或筛选**。
B 端订单列表加一个门店筛选是纯读的、零风险的，而且能立刻验证双写有没有真的写对——
在动库存那种高风险改造之前，先确认地基是实的。
