## 1. 设计

沿用现有路由与冻结point_code。拆出经营服务（旧主体额度套餐＋商城）与进销存；商户中心保留主体门店及入驻。商品分类与规格保留独立商品资料域。既有嵌入支付运营保留为兼容功能，不自动改链独立near-pay。

数据库覆盖菜单名称和排序，因此以新增迁移更新名称、分组与归属，历史迁移不改。权限码、角色授权、就绪度和运行时门禁保持。英文沿用ai-shop现有语言切换；near-pay增加导航层中英切换，不宣称页面正文已翻译。

矩阵以服务端真实功能点授权呈现，不用上一版建议角色表当成已生效的权限。保留内置角色和自定义角色，按当前授权展示菜单与按钮；数据范围需到员工配置核对，矩阵不代表某员工可读取全量数据。

### 7.1 建议角色与现有角色

| 建议岗位 | 现有落点 | 差距 |
|---|---|---|
| 商户运营 | MERCHANT_BD（166存量为BD） | 含入驻审核；现有提交者不得自审约束仍保留，不等价纯制单岗 |
| 行业运营 | PRODUCT_OPS（166存量为GOODS_OPS）及现有业务岗位 | 未提供按行业隔离；不可直接声称只看餐饮/零售/服务业 |
| 服务运营 | 可配置自定义角色 | commerce权限不能借本次菜单自动授予PRODUCT_OPS |
| 财务人员 | FINANCE | 核款/退款与结算每个动作仍按真实权限，不按岗位名推定 |
| 审核人员 | AUDITOR及业务专属审核权限 | AUDITOR不是覆盖全部审核的万能审核岗 |
| 审计人员 | 无等价内置只读岗 | 需按读权限建立自定义角色并验收敏感数据访问 |
| 系统管理 | TECH_OPS及明确授权的自定义角色 | SUPER_ADMIN是全权限账号，不能改名冒充仅配置管理员 |
| 支付岗位 | 宿主角色＋near-pay生效映射＋数据范围 | 支付端不另建注册账号池；映射矩阵不等于最终权限 |
