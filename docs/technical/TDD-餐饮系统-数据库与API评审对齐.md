## §0 结论与需求对账

原设计的基础复用方向保留，但不能直接依原表和端点清单进入逐模块开发。本轮修复关系约束、发布版本、桌台管理及订单/顾客入口等可确定问题；共享报价/支付/库存等真实依赖与专项缺口继续显式门控，不通过新增餐饮表伪造已可用能力。

当前为 **79张候选表、141个目标端点、13个业务模块、109项需求追踪**。相较原基线新增6张餐饮候选表、50个端点，原001–091编号保留但参数/语义有修订，不能视为未经版本处理即可兼容已发布客户端；目前均属未实施草案。

| 逐需求状态 | 数量 | 含义 |
|---|---|---|
| DEFINED · 目标已定义 | 32 | 本轮结构和目标合同有明确落点，仍需实现/测试；不代表设计性能或并发SQL已验证 |
| CORE_CONTRACT · 依赖共享/核心合同 | 59 | 明确复用权威能力或存在扩展依赖，需合同联通验证；不表示59项都要新建接口 |

## §1 评审问题与已应用修订

下表P0/P1表示设计风险优先级；“修订”是已进入设计真源，不是运行中的缺陷修复。

| 等级 | 问题 | 原设计风险 | 已应用的设计修订 |
|---|---|---|---|
| P0 | 关系表错误唯一键 | menu_store(menu_no)、menu_item_sku(menu_item_no)、dish_option_group(goods_no)、sku_station(sku_no)会把一对多错误限制成一对一 | 改为完整复合业务键；路由增加store_no及task_role，不因跨店或跨工位互相覆盖 |
| P0 | 可空字段参与业务去重 | 普通菜无component_no；整单结账allocation_ref为空，MySQL唯一键不能阻止重复 | 厨房增加非空task_part_key及task_role；结账增加规范scope_key；跨结账占应收仍由核心仲裁 |
| P0 | 配置发布无不可变事实 | 原菜单/套餐/选配/工位只有可变头和config_version，无法可靠还原定时发布、旧定义或回滚 | 增加fnb_config_revision，冻结完整聚合和依赖版本；可售只读发布内容，回滚发布新修订 |
| P0 | 桌台协作误变资金归属 | 原merge/split参数容易将并桌、台账服务合并和付款拆合混为一谈 | 新增并入桌台/同桌独立开台动作；旧merge/split只调整服务展示归属，资金拆合仅由收银核心处理 |
| P0 | 转台外部成功后无恢复凭据 | 资源已占成功但餐饮提交失败时，只有普通审计不足以恢复 | 新增fnb_table_operation，保存参数哈希、版本集合、资源操作号和恢复状态 |
| P0 | 顾客端仅有文字承诺 | 原仅catalog/session明确编号，点餐支付退餐没有正式白名单 | 追加127–140顾客端点，限制本人/获准台账和线上工具；无现金确认、审批、签核或厨房操作权限 |
| P1 | 桌区与桌台管理缺口 | area_name无法稳定管理桌区；原仅建桌和轮换码，缺列表详情、编辑、启停与吊销 | 新增fnb_table_area及area_no、code/name/sort等；补092–108管理/协作查询接口；status与资源状态分离 |
| P1 | 菜品展示和计量缺落点 | 多语言/标签/过敏提示及计量规则没有餐饮扩展字段 | 补presentation与measurement_policy受控结构，基础图文价格仍引用商品；实称/补差仍列专项缺口 |
| P1 | 套餐/选配DTO与表类型冲突 | 表使用int选择数量而接口允许decimal；默认选择/互斥约束缺位置 | 选择min/max/default统一decimal(18,6)；增加min_qty与selection_rules，定义互斥依赖DTO并拒循环 |
| P1 | 可售限额只有返回编号 | 原sales-restrictions接口无对应存储和消费预占事实 | 补fnb_sales_restriction及fnb_sales_quota_claim，按批次一次预占/消费/释放；UNKNOWN保留额度；不修改实物库存 |
| P1 | 订单缺不可变源行与上下文 | 原源行没有source_line_ref唯一映射；批次缺报价/草稿/营业日/先后付字段 | 补batch/line上下文、配置引用、成交单位及核心分配金额缓存；原始check保留，当前服务归属用membership追加 |
| P1 | 订单管理缺查询与正式取消 | 原只有按批次单查，缺按台账/状态查询和正式取消恢复入口 | 补123–126；取消调用核心守卫，已制作或资金未知不得购物车式删除 |
| P1 | 动作参数和返回过度通用 | 预约取消竟带到店桌台；厨房催菜也有qty；取消结账/finalize均返回支付动作 | 分动作收敛参数和输出；start/ready/serve正数量；hold/fire/urge无销量数量；取消和终结分别返回操作/结账状态 |
| P1 | 发布与管理接口不够用 | 菜品、菜单、选配组、套餐、工位缺管理查询；配料组合缺发布 | 补109–122及141创建配料，发布/回滚有独立快照号；现有001–091编号保留，新增只追加编号 |
| P1 | 软删后整份替换会撞唯一键 | 当前core的关系Mapper已记录类似问题；通用BaseEntity逻辑删不适合删除后立即重插 | 草稿关系采用upsert/差集更新；受控物理替换仅限未发布工作头；发布历史已冻结，禁止删除 |
| P1 | 日结正式版本与业务状态不够明确 | 同日同币种多修订的唯一键本身不保证当前正式版本唯一 | 营业日行增加按币种的current_close_refs指针，在day锁/CAS下签核；历史SIGNED内容不覆盖 |
| P1 | 现金与退餐状态输出未落库 | 现金pay缺当班证据；退餐响应厨房轨道但return表未存该状态 | 现金写入要求班次/实收凭据并由服务端算找零；意图保存受控请求快照；退餐增加kitchen_status |
| P1 | 代码清单生成命名及统计失配 | saveDishe、大写动作方法、列表/详情方法重名，旧91端点/73表硬编码 | 修订单数与lowerCamelCase，列表与详情区分；同步52个候选Controller、141个方法和79表映射 |
| P1 | 领域归属冒充逐项覆盖 | A–L领域有需求编号不代表有对应表/端点/失败恢复设计 | 增加13个业务模块和109条逐项表/API/状态/残余工作映射；18项明确DESIGN_GAP，不标已完成 |

## §2 按业务模块的落地边界

| 模块 | 本轮已对齐 | 实施前仍需确认 |
|---|---|---|
| MOD-01 桌台 | 桌区、桌台管理、桌码吊销/会话、开台人数座位、并桌/拼桌、操作查询恢复 | 预约预点、排队、订金合同；资源容量仲裁SQL；同桌顾客隐私及清台异常移交 |
| MOD-02 菜品 | 多餐牌及分类、发布快照、口味/配料/套餐规则、可售限制、查询发布历史 | 复杂计价/计量与库存展开；实称补差及导入合同；门店差异发布授权 |
| MOD-03 订单 | 车与报价绑定、源行唯一、批次上下文、加菜查询、正式取消、顾客白名单 | 核心源行/同键查单、匿名与代客身份、后付库存/履约、赠换及定时出餐专项 |
| MOD-04 厨房 | 分动作参数、非空派工去重、数量事实与资金分离 | 撤回交接、漏菜、齐套/打包和工位拥堵治理 |
| MOD-05 收银 | 预结/取消/终结分动作、顾客结账范围限制、现金班次证据 | 跨根/拆分/AA/组合工具/费用调整及AR等共享合同 |
| MOD-06 退餐 | 原分配数量退款、财务/厨房状态分轨 | 当前整单退款边界保留；部分退款/错单重开/反结账需合同 |
| MOD-07 打印 | 内容、投递、重试/补打归属和未知回执明确 | 设备绑定、模板路由维护、自检、订阅及诊断缺完整共享接口 |
| MOD-08 班次 | 班次/非销售现金/实盘/资金流水归班 | 跨班未收责任移交、钱箱活跃班次唯一仲裁 |
| MOD-09 日结 | 水位签核、当前正式版本指针、更正链 | 真资金对账、未知结转、迟到数据及多币种证据 |
| MOD-10 报表 | 复用投影/导出/重建，逐需求引用事实 | 每reportCode指标维度/分母；历史成本、应收、会员、排队等权威输入 |
| MOD-11 专项 | 自助权益、宴会、寄存、房账引用模型保留 | 报价资产、PMS及专项频控的权威协议 |
| MOD-12 集成 | 映射/异常/同步批次及双部署边界明确 | 供应商协议、租约/隔离、离线额度与重放认领专项 |
| MOD-13 配置 | 身份/门店/openHours复用，策略日历/能力分开 | 权限/审批/多时区全局营业时间合同，不建第二套身份营业底座 |

开发仍按模块清单逐个进行；本表不是重新按基础设施或终端划分开发。需要跨模块的基础能力，在当前业务切片明确依赖后最小交付。

## §5 验证方法与实际结果

本轮检查设计结构和生成一致性，不证明SQL锁、Java事务、支付通道或真实打印设备可用。

- `node --test scripts/tests/food-design-contract.test.mjs`：9项设计合同测试通过。负向用例恢复错误父键、引入可空去重键/重复路由/无效DTO/重复归属，验证结构守卫会拒绝它们。
- `node scripts/gen-food-system-design.mjs`：重建3本文档及17张分域SVG；输入结构守卫校验表/键/引用、DTO、API路由和109项模块归属。
- `node scripts/gen-food-code-inventory.mjs`：同步52个候选Controller、141个方法及79张表映射；列表和详情方法不重名，动作lowerCamelCase。
- 使用 `FOOD_ER_VIZ_MODULE` 指向本地已有@viz-js/viz模块重建，未增加生产项目依赖。生成物需重复生成后摘要一致。
- 旧菜品专项ER标注为历史草案，以综合设计源为当前修订依据；历史文件不叠加执行迁移。

## §6 实施交接

本册评审本身不创建Java业务工程、不更改核心业务代码；随后按用户要求完成本机表初始化，单独记录执行证据。所有接口“修订”仍仅表示目标设计同步。未验证核心合同的功能保持禁用；DESIGN_GAP进入对应模块时先补专项设计，再补参数/表/测试。
