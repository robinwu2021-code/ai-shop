## 一、定案汇总

| # | 问题 | 定案 |
|---|---|---|
| D1 | 166 缺预置角色模板 | 部署后先核实；如确实缺，补只写数据的迁移，按 `BizPerms` 写入 6 个预置角色，已存在则跳过 |
| D2 | 美业插件上线 166 | 餐饮在台北早餐联调通过后再上；先在 166 演练库跑美业 V1–V11，再正式切换 |
| D3 | 首批方案发布 | FREE = `END_BIZ_APP`；PRO = 行业码 + `END_MARKETING` + `END_APP_POS`；CHAIN = PRO + `END_CHAIN`。价格、期限由产品定 |
| D4 | 外卖接单策略谁能改 | 拆开：「暂停 / 恢复接单」放给店长（`biz:store`）；金额上限、货到付款等仍只给店主（`biz:store:admin`） |
| D5 | 多种付款结账 | 首期不做编排引擎：业务侧算应收，付款走付款链接、收款码、外部记账、储值扣款，后端补一个「已收 / 还差」汇总读口 |
| D6 | 美业订金 | 首期不做线上订金：服务项目可配建议订金；店员收订金用外部记账记一笔并关联预约，结账时抵扣；24 小时前取消可退、爽约不退，由店员手工处理 |
| D7 | 服务业报表 | 首期指标：预约数、到店数与到店率、爽约数、取消数、营收、按技师次数与金额、热门项目前 5；范围今天 / 近 7 天 / 本月 |
| D8 | 技师、排班权限 | 保持只给店主；店长需要时由店主在角色里勾选 |
| D9 | 首页汇总 | 首期 App 组合读，性能不够再补汇总接口 |
| D10 | 美业接入 pre-push | 干净副本内用 `cp -Rc` 克隆本机 Maven 仓库，在独立仓库里安装并运行美业测试，不改美业工程结构、不覆盖共用仓库 |
| D11 | 美业独立服务端 4 个失败 | 不阻塞；决定独立部署美业之前由美业负责人修复 |
| D13 | 外卖接单 / 拒单只有店主能做 | 建议放给 `biz:verify`；外卖插件负责人改（[TDD-外卖接单开关](./TDD-外卖接单开关.md) §4） |
| D17 | 外部记账 `orderNo` 只能填商城子单 | 加独立列 `biz_no`（V641，带 DDL） |
| D18 | 美业账单要不要自己扣订金 | 首期不改插件，抵扣走汇总读口 `relatedBizNo` |
| D19 | 服务业营收口径 | 建议用实收（读业务单收款汇总）；按技师金额等业绩分摊规则，首期不做 |
| D20 | 服务业报表谁实现 | 用户确认由本会话实现首期（BAPI-119 子集） |
| D21 | 美业 V10 在 MySQL 9.7.4 上建表失败（`COALESCE(布尔,0)` 不被当作布尔） | 生产 9.7.2 可用；美业上线或升级 MySQL 前改成布尔写法，由美业负责人定 |
| D22 | 子行业由谁维护 | 首批迁移写入（V643，3 行业 32 子行业）；运营端「行业管理」页面放第二期 |
| D23 | 子行业是否影响方案 | 不影响：方案、功能仍按经营类型（零售 / 餐饮 / 服务业） |
| D12 | 正式运营前清理 | 清空测试身份白名单并关闭 `SHOP_AUTH_TEST_IDENTITY_ENABLED`；配好 Google 地图两个密钥 |
