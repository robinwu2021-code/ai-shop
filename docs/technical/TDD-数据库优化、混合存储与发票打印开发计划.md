# 数据库优化、混合存储与发票打印开发计划

状态为待实施。按数据库、存储、发票三个阶段顺序交付。每阶段单独提交、验证和保留回滚点。数据库先完成全库盘点，再按实证优化。第一批优先处理文件和发票链路相关的热点及一致性。实施先在 MySQL 9 联调环境和生产结构副本验证，再按计划切换台湾 v2。

设计依据包括[数据库表清单](reference/数据库表清单.md)、[本地业务文件统一管理](TDD-服务端本地业务文件统一管理.md)、[本地存储与多云切换](TDD-本地存储根路径与多云切换.md)和[发票申请与交付追溯](TDD-发票申请与交付追溯.md)。

## 2. P0 数据库优化

### P0.1 盘点和基线

- [ ] 逐环境记录 MySQL 版本、库及模块所有权、Flyway 历史、备份位置及恢复实测。现有发票 V16–V19 属已发布基线，实际版本以运行环境查询结果为准。生成结构、表规模、增长量、字符集、排序规则及关键索引清单。
- [ ] 只读采样慢查询、锁等待、死锁、连接池占用和高频 SQL 摘要。按正常及高负载时段建立耗时、扫描行数、锁持有时间基线。生产结构和代表性数据在受控副本重放。耗时指标基于采样结果设置验收目标。
- [ ] 按业务域记录高影响问题和负责人。全库纳入盘点。每项 DDL 或 SQL 改动附执行计划、前后对照及回滚方式。低频或收益不明确的项保留在优化清单。

### P0.2 查询、索引和数据质量

| 权威记录 | 优先验证的访问路径及不变量 |
| --- | --- |
| `sys_media_asset`、现有报表导出记录 | 按主体、门店、用途、状态盘点，按有效期回收。核对无引用文件与文件缺失的业务记录。 |
| `prn_request`、`prn_job`、`prn_export_task` | 按发票号查请求、工作和导出，按状态及到期时间批量回收。评估精确来源查询、稳定分页和批量读取，消除逐行查库。 |
| `ivc_invoice_application*`、`ivc_invoice` | 按授权门店和来源查申请，开立引用确切版本。取号、退款与开立的并发约束，以及历史票查原账户均须通过。 |
| `ivc_invoice_delivery`、`ivc_transmission_attempt` | 按票号查交付和供应商尝试，按待处理状态认领任务，记录回执与重发。保持认领、重放和历史关联的幂等语义。 |

- [ ] 对比既有索引和实际谓词。以执行计划决定是否补组合索引、改分页或批量查关联。例如评估打印请求的主体、门店、来源与场景查找，以及导出任务的到期扫描。新增后测写入开销和锁等待。
- [ ] 核对主体、门店、对象键、允许为空的历史关联、UTC 时间及混用排序规则的关联查询。重复记录和孤儿报告给业务归属方。修正脚本分批、可重跑并记录差异。
- [ ] 确认每类文件已有的权威表。需要时补可空的存储提供方、位置标识和命名空间，配合现有对象键定位。位置标识指向持久配置的卷或桶，便于后续换挂载或换桶。历史归属凭对象清单和原链接验证，未确认项进入核对队列。统一治理视图从权威记录投影。
- [ ] 数据库为 MySQL 9。使用新 Flyway 迁移，不覆盖已执行文件。先加兼容结构，分批回填，再验证是否需要收紧约束。删除旧字段另行发布。更新测试 schema 投影并执行迁移一致性检查。

### P0.3 验收和发布

- [ ] 在 MySQL 9 验证空库、生产结构升级、迁移重跑、代表性数据和恢复。应用新旧版本在扩展后的结构上分别通过开放兼容窗口的回归。对大表变更先评估元数据锁和维护窗口。
- [ ] 运行同一负载做前后对照，验证重复请求、并发取号、跨店隔离、退款、作废和历史票查核。交付结构差异、性能报告、备份校验及恢复记录。
- [ ] 相关验证入口包括 `InvoiceServiceMysqlTest`、`SchemaDriftTest`、`StoreScopedDailyRoutesFlowTest` 和现有打印 MySQL 验证脚本。数据库验收完成后进入存储实施。需要回滚时先恢复兼容的应用版本。涉及数据恢复时按快照和变更范围演练结果执行。

## 3. P1 服务器磁盘与云存储

### P1.1 统一入口和配置

- [ ] 在统一文件入口编排上传、生成、授权读取、盘点和回收。继续使用 `MediaUploadService`、`MediaStore`、`PrintArtifactStorePort`、`LocalDiskMediaStore` 和既有 COS 适配。业务模块提供用途与归属，旧 HTTP 入口和稳定文件引用兼容。
- [ ] 磁盘统一根使用 `SHOP_STORAGE_ROOT`。本机使用 `/Users/robin/work/ume/invoice-qa/storage/`。台湾 v2 拟将宿主机 `/data0/app/ai-shop-v2/storage/` 挂载为容器 `/data/storage/`。分类子目录沿用 `uploads/`、`print-private/`、`documents/`、`exchange/`、`tmp/`。API、OPS、生成和清理进程共用对应持久卷。
- [ ] 配置沿用 `SHOP_MEDIA_PROVIDER`、`SHOP_PRINT_ARTIFACTS_PROVIDER` 及 [local/COS 配置样例](../../deploy/storage/README.md)。实现时区分**新文件写入配置**和**已登记文件的真实位置**。启动时校验用到的本地卷、云桶及签名配置。配置缺失要能定位到具体命名空间和提供方。

| 运行模式 | 新写入 | 已有对象 |
| --- | --- | --- |
| 磁盘模式 | 媒体与打印分别设为 `local`，从统一根派生目录。 | 按原位置读取和清理。旧云对象仍存在时保留对应连接配置，直至迁移或到期。 |
| 云模式 | 媒体与打印分别设为 `cos`，使用配置指定的逻辑桶和公开或私有策略。 | 历史磁盘对象按其登记位置读写，迁移后才更新位置。 |
| 混合模式 | 可按命名空间，例如商品图写 COS、发票 PDF 写磁盘。 | 磁盘与云对象同时可读，按记录定位。切换配置决定以后写入方向。 |

首批云实现采用现有腾讯 COS。Google Cloud Storage 作为独立适配任务，需求确认后验收桶权限、签名、缩略图和旧链接兼容。切换配置不会自动复制或改变旧对象的地址。写入异常由原任务重试，读取沿已登记位置执行。

### P1.2 迁移、权限和治理

- [ ] 根据对象清单做本地与云之间的预复制。保持稳定对象键，核对数量、大小、SHA-256、MIME 和公开或私有权限。目标验证通过后才更新位置记录。遇到不一致进入差异清单。切换时暂停相关写入或补齐全部增量。
- [ ] 所有临时文件按用途隔离。登记后写入、校验并发布。无登记文件及缺失对象由对账任务发现。运营端存储治理页按用途、作用域、提供方、有效期和占用查询。公开图和私有文件分别使用既有授权入口，私有下载通过授权或短期签名。
- [ ] 按原位置、用途、保留期和业务引用执行删除。长期图按引用回收，发票与打印 PDF 维持七天。台湾 v2 清理在验证旧、新目录归属后切换到一个执行入口。配套记录空间、孤儿、清理和迁移结果。
- [ ] 验收本地、真实 COS 验收桶、混合模式和切回本地。覆盖旧图 URL、私有凭证、CSV 与两类 PDF、授权到期、跨主体拒绝、云不可用重试、文件摘要和反向增量回滚。复用 `LocalStorageRootTest`、`LocalMediaHttpReadTest`、`PrivateArtifactRootTest`、`MediaKeyRoundTripTest` 与打印验收套件。

## 4. P2 发票 PDF、实体打印及邮件

- [ ] **独立生成和归档**。企业票读取冻结的证明联快照，手机条码票读取冻结的交易明细快照。沿用 `InvoicePrintSourceFactsPortImpl`、打印渲染器和 `prn_export_task`。保存发票号、申请版本、模板版本、文件类型、导出号、存储位置、哈希、纸宽及期限。即使门店暂未配置设备，仍可生成邮件用 PDF。
- [ ] **接口**。实施发票详情的制品查询和生成入口，拟使用 `GET/POST /biz/invoices/{invoiceNo}/documents`。生成返回任务、类型和状态。按发票、文件类型及冻结版本防重。已生成文件通过现有下载许可读取，调用方凭导出编号跟踪状态。路径、权限、状态码落地时纳入端点回归。
- [ ] **实体出纸**。走原打印中心的设备、场景和路由。正本打印和补印按冻结版面生成工作，补印保存来源、原因及新回执。核对设备纸宽、原工作关联、纸面标记和实际输出。PDF 就绪仅更新制品状态。
- [ ] **邮件与追溯**。扩展 `InvoiceDeliveryServiceImpl` 按票种接受对应制品。企业发送证明联链接，个人保留手机条码并发送开立通知及交易明细链接。沿用收件人验证码、授权期限、重发、防重和失效处理。区分 SMTP 受理、实际收件验收和授权下载。
- [ ] **Android**。在原生 Jetpack Compose「發票詳情」复用现有卡片、按钮、状态标签和 PDF 查看器。区分生成、下载、实体打印、补印和邮件状态。接入文件类型和历程，预览临时文件出渲染作用域后清理。
- [ ] **开发验证**。覆盖企业统编和完整抬头、个人载具交易明细、无设备独立生成、磁盘和云下载、重发幂等、作废后拒绝新交付、过期清理、跨店权限和设备未知结果。复用 `InvoiceProofLayoutTest`、`PrintDatabaseAcceptanceTest`、发票 MySQL 测试及 Android 发票模块测试。
- [ ] **台湾 v2 验收**。先提交与部署，再在 Oscar Retail QA 1121 做两笔 NT$1。企业使用「創勢科技股份有限公司」`50765634`，寄至 `robin@neargo.ai`。个人使用 `/LDTCMAB`，寄至 `socar@umeshop.ai`。核对鲸跃回执、PDF 内容及哈希、收件、验证码下载与邮件记录。实体打印需要已配对设备及正式路由，验证正本、补印、实物和回执。验收完成后作废测试票并查验结果，保存脱敏凭证。

## 6. P0 执行记录

- 台湾 v2 只读盘点为 MySQL 9.7.4，主库 813 张基础表，表的数据和索引合计约 74.8 MiB，存在五种表默认排序规则。采样时主库 V695、发票 V19，迁移均无失败。连接上限 250，当前连接 105，历史最高 184。累计统计中有 611 次 InnoDB 行锁等待和 5 条慢查询。累计指标用于后续排查，单次采样的数值用于记录基线。
- 累计耗时靠前的 SQL 包括门店上下文、未读通知、Outbox 和交易提交。现网已有未读通知和任务扫描索引，继续按峰时采样确认收益。此次索引优化聚焦发票详情的精确打印请求查询。
- 在 MySQL 9 恢复生产结构的 813 张基础表，并对生产结构中的三张受影响表回放 V696。发票请求查询用单店 20,000 行合成数据测量，旧执行计划读取 20,000 行并排序，新增索引后直接命中 1 行。该次本地测试约为 64.6 ms 和 0.03 ms，生产性能以后续观测为准。
- V696 为媒体和打印导出添加可空的存储提供方及位置标识。历史记录暂不回填，存储阶段凭对象盘点确认。MySQL 发票、门店准入、打印验收及测试 Schema 对齐共 66 项通过。

## 8. P2 本轮交付

- 台湾 v2 已发布 `invoice-documents-9ec1b3ef00`。原生 Android 使用提交 `db9a6c96`，在既有发票详情和组件上增加文件、邮件与文件类型显示。
