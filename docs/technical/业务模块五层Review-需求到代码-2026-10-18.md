## 2. 按设计向下复核：数据库 → API → 代码

### 2.1 支付与订单

- 数据库：审查对象是 pay 收款单及订单支付关联、状态版本/条件更新和渠道流水唯一键；不能仅有订单 paid 标志。完整索引、回调与关单交错的锁序仍待逐表/方法深查。
- API：回调协议的 HTTP 成功与业务 `SUCCESS` 分开。测试必须校验通道正文和最终业务状态，取消后晚到回调的语义要按该通道契约定义。
- 代码入口：整合分支 `shop-core/.../trade/api/callback/PayCallbackController.java`；测试助手 `shop-app/.../support/RefundScenarioPayments.java`。前轮已修正若干直接回调夹具，不能据此认定所有订单场景已修复。
- 验收：支付成功、重复回调、取消撞付款、错误金额/流水、代理下单拒绝原因；先按失败类小范围运行。

### 2.2 售后退款

- 数据库：退款执行保存批准方案及原支付坐标，资金预占与执行创建必须同事务。`V457__order_points_refund_binding.sql` 已以 after_sale_no 为主键，包含 source_version、command_json、preparation_json、cash_payment_no 及 version；这是源侧积分决策绑定，不代替 pay 退款账本。
- API：申请、批准、退货物流、确认收货、退款重试/关闭分开；`REFUNDING` 只表示处理，不表示到账。用户不能提交另一个门店或售后单越权复用退款准备。
- 代码：`AfterSaleServiceImpl` 315 行附近检查 WAIT_FULFILL、prepared_at、expressNo 与 NOT_PREPARED；380 行调用未备货退款事件。与现行 AC16 相符。此前“不自动退款”笼统建议应收回，改为区分买家事件和定时器事件。
- 待验证：原支付坐标被新支付干扰、UNKNOWN恢复、已分配资金二次退款、重复准备冲突；这些是资金边界，不能先改期望值消除红灯。

### 2.3 积分内核与接线

- 数据库：`V425__points_v3_ledger.sql` 已有 type/account/voucher/entry/pool-flow/evidence/reserve/grant/redeem/refund-preparation/payout/statement 表族。种类 active_market 唯一、账户(type,holder_type,holder_no)唯一、发放/核销(type,sub_order)唯一、退款准备 after_sale 唯一、付款 provider_idem 唯一，方向符合幂等设计。
- 重要边界：基础脚本中部分 store_no 可空；是否所有门店业务均被后续迁移及写入校验约束，尚需逐服务核对，**不能仅据 nullable 判定跨店漏洞**。USER/ISSUE 等账户也不能被错误要求填写门店。
- 源侧：`V453__order_points_binding.sql` 明确 store_no 非空，request_id 与 sub_order_no 各自唯一，保存 phase、payload、version 和恢复索引，符合按子单门店冻结接线事实的方向；不能以主单 points_integrated 代替子单绑定。
- API：整合分支 `BizStorePointsController` 提供 store-types/store-account/store-entries；账户及流水 holder 从 `BizContext.requireStoreNo()` 取得，FINANCE 权限控制，方向符合 AC35；仍需核实 BizContext 对员工门店集合的授权验证。
- 代码：关注 EarnService/EarnServiceImpl、PointsSourceFactHandlerImpl 的“新发放闸门/已接受事实”区分；前轮已加 grantAccepted。必须保留来源身份/门店/金额验证，不能把接受事实入口暴露成绕过暂停的通用 API。
- 纠正（第二轮）：旧使用记录确认、补贴5例、历史积分读取2例仅存在于残留XML，不在固定门禁逐例日志中；源文件也已不存在。撤回将其列为本次失败的归因。PRD AC36要求删除旧逻辑，不能为残留报告恢复双引擎。

### 2.4 结算账务

- 数据库：按账单、分账、出款、退款回退分别保存业务键与执行状态。固定账单候选及修订，未知资金占用不得释放。需继续逐条检查 OfflineSettleFlowTest 10个 CONFLICT 对应的唯一键和前置状态。
- API：确认账单与发起付款分开；确认需版本/修订，金额由服务端快照决定。UNKNOWN只允许查询同一执行，人工换路径需明确原请求不能再成功。
- 代码：pay 的 RefundExecutionServiceImpl 与 trade 的同名服务分属资金执行和业务编排，不因同名就认定重复实现；必须追踪调用链确认只有一个外部发款入口。当前未证实该链路完整无重复。

### 2.5 门店经营、评价与营销

- 数据库：核对 ord_sub_order.store_no → 评价 store_no → mch_store 派生评分的来源链，不能从商家当前默认店回填；计数/评分可重算。
- API：跨店比较每行携带本店评分；门店过滤由授权范围限制；商家主体可查询合法汇总但不能看未授权店。商品/券资方/套餐要有独立字段及校验。
- 代码入口：`shop-core/.../product/review/impl/ReviewServiceImpl.java`；先建立真实已支付且满足评价条件的订单，再判定 20004 是业务状态问题还是读模型缺陷。
- 状态：需求口径已确认，数据库与代码路径尚未完成全量核对，不能将27条相关失败全归为支付夹具。

### 2.6 履约物流、库存与自提

- 数据库：库存以 inv_owner/location、余额、ledger、reservation表达独立模型；回填既要数量相等，也要 held 相等。运单以 shipment/biz_ref及当前运单版本关联，历史签收不能完成新运单。
- API：发货登记、推送、签收、收货确认分别表达事实；代下快递测试模式不能产生真实运费债务；自提待办按承接关系授权。
- 代码入口：invbridge 的 InventoryBackfillServiceImpl/InventoryHealthServiceImpl；物流当前运单接线与 OrderMappedOpsLogisticsFlowTest 的 MANDATORY 事务报错。
- 状态：MANDATORY报错尚未证明是生产入口缺事务还是测试直接调用内部方法；需要追踪正式API入口后定性。两条自动收货 SQL 错误也需提取完整数据库异常，不只看截断消息。

### 2.7 消息与通知

- 数据库：业务事件身份、收件人类型/编号、去重键、投递尝试和渠道结果分列；消息不存在时不能以空数组越界异常掩盖事件未产生。
- API：收件箱按当前接收人隔离；消息 actionPending 是可操作性提示，实际操作仍须重新鉴权。
- 确认架构问题：`BizMessageController.java:7,29–33` 直接导入并注入 trade.AfterSaleService，messages() 再查询待处理售后，违背“跨域只用 SPI Port/Event”的规则，与 ArchitectureTest 对应。建议定义批量待办查询 Port，trade实现，message仅消费结构化结果；不要靠给ArchUnit加豁免解决。
- 待验证：通知空数据可能依赖支付前置；Outbox健康两例仍需检查 lastAttempt/首次尝试/重试状态的推导。

### 2.8 API 权限与装配

- 数据库：正式 Flyway 权限种子与 H2 种子不同，需检查迁移执行后的角色—权限—功能点关系；静态 API 标记不证明访问安全。
- API：门禁已发现 `/mp/user/login/phone` 未分类；公开登录端点也应明确登记 public。B端未分类项应逐URL核对，不统一默认登录可用。
- 代码：ArchitectureTest 的跨域依赖是明确问题；FulfillmentChangeService 的 Service接口规范另行处理，不与资金修复混为一项。ConditionalBeanWiringTest 的失败要按每种开关组合分析依赖，不能简单为所有可选Bean加默认实现。

## 4. 逐模块后续审查的完成门槛

每个模块都按同一顺序形成可追溯记录：

1. 需求：指定有效版本，列成功、拒绝、异常、权限、幂等和人工恢复规则；冲突条款先收拢。
2. 设计：给出状态转移、事务边界、资金及库存事实来源、锁序和失败恢复；不明处显式标待决策。
3. 数据库：逐表核对字段、不可变快照、唯一键、条件写、恢复索引和迁移序列；实际DDL与文档对应，不依赖H2推断生产。
4. API：逐URL对应角色/门店范围、请求响应、金额单位、错误码、版本/幂等及重试语义；清单与Controller一致。
5. 代码：沿正式入口追踪Service、Port、Mapper及事件消费者；列具体问题位置与触发条件，再按小范围场景验证。

建议次序：积分内核 → 售后/退款 → 支付与订单 → 结算 → 门店经营 → 履约库存 → 消息 → 权限装配。权限/资金关键问题发现后立即提升，不等待模块排序结束。

本轮完成文档有效性与跨层静态首轮复核、关键入口抽查及失败基线纠正。逐个失败用例的完整方法/SQL审查、生产数据库迁移验证和新测试运行尚未完成，不能将本报告用作发布通过证明。
