# 运营端营销四个列表：修完分页壳之后露出来的东西

> 2026-08-11 · 起因是修 `ops-pagination` 守卫报的 5 个端点，改完在浏览器里打开页面才看见。

## 一、先说已经修好的

这 5 个端点返回裸数组，而 ops-web 所有列表页按 `{records,total}` 渲染 ——
**接口 200、数据几十条、页面显示「暂无数据」，控制台一条错误都没有**。

`/ops/groups` `/ops/quotes` `/ops/coupons` `/ops/campaigns` `/ops/msg-templates`
全部包上 `PageData.ofAll`，守卫恢复绿。

值得记一笔的是：这条守卫是 `ac0ca6f`「十个列表端点返回裸数组」时立的，
**而它红着的这段时间里，又新增了 5 个端点重犯同一个错**。
守卫拦住了记录，没拦住行为 —— 因为没有人把它跑绿。
**长期红着的守卫等于没有守卫**，它只会训练人忽略它。

## 二、然后露出来的：页面能显示了，但显示的不是它要的东西

页面从「空」变成「有行」，于是错配第一次可见。

| 端点 | 分页壳 | 契约 | 性质 |
|---|---|---|---|
| `/ops/msg-templates` | ✅ | ✅ 字段全对 | 好的 |
| `/ops/quotes` | ✅ | ⚠️ 3 个字段名漂移 → ✅ 已建 `OpsQuoteVO` | 同一对象 |
| `/ops/groups` | ✅ | ⚠️ 4 个字段名漂移（含一个同名不同类型）→ ✅ 已建 `OpsGroupVO` | 同一对象 |
| `/ops/coupons` | ✅ | ❌ 不是同一个对象 → ✅ 已建 `OpsCouponVO` + 预算列 | 补了后端能力 |
| `/ops/campaigns` | ✅ | ❌ 不是同一个对象 → ✅ 页面已正名为「商家活动治理」 | 平台场次仍待产品决定 |

### 一个共同的根因：运营端接到了 C 端的 VO 上

`GroupBuyVO` 带 `joined` / `isOwner` / `neighborPickup`，`QuoteVO` 带 `chosen`，
`CouponVO` 带 `received` / `remain` —— **这些字段是给买家看的**
（「我参没参团」「我领没领券」）。运营端要的是治理视角：谁发的、发了多少、超没超预算。

一个 VO 同时服务两端，就得同时长出两套字段，而先写的那套会定下命名口径。
于是运营端要么将就，要么像现在这样对不上。

### coupons：字段几乎全不一致，且有 4 个后端根本没有

| ops-web 期望 | 后端返回 |
|---|---|
| `name` / `value` / `threshold` | `title` / `faceMinor` / `thresholdMinor` |
| `validFrom` / `validTo` | `startAt` / `endAt` |
| `budget` `issuedAmount` `issued` `redeemed` | **没有** |

实测页面上直接渲染出 `undefined / undefined`（已发/已核销那一列）。

**预算与发放统计是券治理的核心** —— ops-web 页面上那句提示写着
「预算是唯一挡住『发着发着超支』的地方」，而后端没有这个字段，
也就是说那道闸门现在**不存在**。这不是显示问题。

### campaigns：两个不同的领域对象被一根路径连着

ops-web 自己的类型注释已经写清楚了（`lib/types/marketing.ts`）：

> 这里的 `Campaign` 是**平台投放的营销场次**（带 `position`，秒杀场按位置分组做重叠校验），
> 由运营建，**后端还没有这个对象**

而后端 `/ops/campaigns` 返回的是**店铺级活动**（`entity_no NOT NULL`，商家自己建的
COUPON / FULL_CUT / FLASH / BUY_GIFT）。

实测表现：类型列一半中文一半原始枚举码 —— `FLASH` 恰好两套都有，
其余三个在 `PlatformSlotType` 里找不到映射，`StatusBadge` 就把码打给了用户。

**这一条我改分页壳之后变得更糟了**：之前页面是诚实的空，现在它显示 7 条店铺活动，
而页面标题与筛选器说的是平台场次。运营会以为这些是平台建的。

## 三、四条建议与执行结果

### ✅ 2. campaigns 止血（已做）

Notice 改成明说「当前列出的是商家自建的店铺活动（只读），平台投放的营销场次
后端尚未实现」。不删数据、不删页面 —— 诚实的有，好过误导的有。

### ✅ 3. coupons 补治理字段（已做）

- `V21__coupon_budget.sql`：`mkt_coupon.budget_minor`，**0 = 不限**
  （存量券一张都没配过，任何非零默认都会让它们当场超预算而停发）
- **预算闸门装在领券那条 UPDATE 里，与张数一起判**（原子）。
  分两步的话两个人同时领最后一份预算都会通过，而超预算的后果是真金白银
- 新建 `OpsCouponVO`：字段名对齐 ops-web，`issued`/`redeemed`/`issuedAmount` 真实统计
- 3 条测试钉住：超预算被拒、0=不限、治理视图不含 `received`/`remain`

⚠️ **折扣券挡不住**：`face_minor` 为 0，`(received_count+1) * 0` 恒 ≤ 预算。
折扣券的实际支出取决于用券那一单的金额，**发放时算不出来**。
与其按面额估一个假数去挡，不如明说这里挡不住 —— 折扣券的预算要走核销侧，那是另一件事。

### ✅ 1. quotes / groups 字段名对齐（已做）

新建 `OpsGroupVOs.OpsGroupVO` / `OpsQuoteVO`，与 `OpsCouponVO` 同一条原则。

**光改字段名对不齐这两个**，因为其中一处是同名不同义还不同类型：

| | C 端 VO | ops-web 期望 |
|---|---|---|
| `joined` | `boolean`「我参没参团」 | `number`「已参团人数」 |

发过去一个 `false`，前端拿它当人数用，页面上就是**一个不报错的错数字**。
实测两侧对照：C 端 `joined: false`，运营端 `joined: 0`。

`demandTitle`（需求标题快照）后端原先没有，批量补上 —— 逐条查会对同一个
`request_no` 查很多遍；取不到给空串而不是编一个，运营在这一列上认单。

### ✅ 4. campaigns 正名为「商家活动治理」（已做）

没有建后端对象，也没有把 tab 收掉 —— **第三条路：让页面说它实际在做的事**。

`/ops/campaigns` 返回的一直是商家自建的店铺活动，而平台对它有真实且完整的治理能力
（看得见、能停、写审计，矩阵 §2.3）。缺的从来不是能力，是这个页面的身份。

- 类型拆成两个：`MerchantCampaign`（真在用）与 `PlatformSlot`（后端未建，UI 留着）
- 枚举拆成两套：`merchantCampaignType`（COUPON/FULL_CUT/FLASH/BUY_GIFT）与
  `platformSlotType`。共用一套的表现是 **`FLASH` 恰好两边都有所以译得出来，
  其余三个把原始枚举码打给用户**
- 列：去掉「位置」（场次专属），加「商家」，商品数 = `goodsNos.length`
  —— 后端一直有这个字段，此前因类型对不上而恒为空
- mock 拆成两个数组。此前它造的是**平台场次**的数据（SECKILL/position/skuCount），
  一个后端并不存在的对象 —— 又一次「mock 比后端好看」，
  所以 mock 下一切正常，接上真后端才露馅

平台投放场次那块 UI 与它的产品规则（首尾相接不算重叠、跨位置可并行）
原样保留在 `platformSlots` 的 mock 与测试里，等产品决定要不要建后端对象。

> **一个写完了但接不上的页面，比没有这个页面更容易让人以为功能存在。**
> 正名解决的是「它到底在做什么」；「要不要做平台投放」仍然是产品的决定。

## 四、顺带修掉的：两个 DDL 解析器都把 `IF` 当成了列名

加 `budget_minor` 时 `SchemaDriftTest` 报「mkt_coupon 的列不一致」，
而两边看着都对。真因是两份解析器（`scripts/lib/ddl.mjs` 与 `SchemaDriftTest`）
的正则都写成 `ADD COLUMN\s+(\w+)` —— 遇到
`ADD COLUMN IF NOT EXISTS budget_minor` 会**抓到一列叫 `IF`**，真正那列不见了。

幂等迁移不是可选风格（V18 的教训：一次失败的迁移不该需要人手工进库才能重试），
所以修的是解析器，不是把 `IF NOT EXISTS` 去掉。

这与 `SchemaDriftTest` 自己注释里那句话是同一个教训：
**一个会静默读错的校验器，比没有校验器更危险** —— 它把人引向 schema-test.sql，
而真因在解析器里。

## 五、写操作不传 reason（已修 + 已立守卫）

后端有一批写操作**要求 reason 必填**（停别人的东西要说得出为什么，写进审计），
空理由返回 10400。而 ops-web 这边：

| 端点 | ops-web 实际发的 | 结果 |
|---|---|---|
| `/ops/coupons/{no}/status` | `{status}` | **必然 10400** |
| `/ops/quotes/{no}/price` | `{price}` | **必然 10400**，且字段名也不对（后端要 `unitPriceMinor`）|
| `/ops/campaigns/{no}/toggle` | 页面没接这个按钮 | 有能力没消费方 |

真后端实测确认过：`{"status":"PAUSED"}` → `10400`，加上 reason → `0`。
也就是说 **运营点「暂停券」按不动**，而演示、单测、E2E 全绿 ——
因为 mock 里没有这条校验。

### 怎么修的

- 契约与 http 层补 reason；`changeQuotePrice` 的字段名同时纠正为 `unitPriceMinor`
  （名字不对时后端收到 0，被「改价必须 > 0」挡下，表现为一个说不通的「参数有误」）
- `ConfirmOptions` 加 `requireReason`：填一句理由才解锁「确认」，理由交给 `action`。
  **做在弹窗里而不是各页自己加输入框** —— 这类操作有 4 处，
  各写一遍的结果就是「活动能填理由、券不能」，而后端对两者的要求一模一样
- 券的「暂停 / 恢复」与活动的「停用 / 启用」都走它
- **mock 补上同样的校验**：mock 宽于后端，等于把问题藏到上线那天

### 守卫：`packages/shared/tests/ops-reason-required.test.ts`

从后端 Controller 的 `record XxxReq(..., String reason, ...)` 反推出「这条路径要 reason」，
再看 ops-web 的 https 层发那条路径时有没有把它发出去。

两种写法都算发了，**不能只认第一种**：

```
client.post(path, { status, reason })   ← body 里字面写着
client.put(path, v)                     ← 整个入参透传，而 v 的类型里有 reason
```

只认第一种时它误报了 `auth-codes` 与 `proxy-cancel` 两处 —— 那两处本来就是对的。
**一条会误报的守卫比没有守卫更坏**：它逼人去改本来正确的代码，
改完还得回来把守卫调松，两次都在做无用功，而真正的漏网之鱼混在噪音里。

立完之后回退一行验证过它真的会红。

### 这是「mock 宽于后端」的第三个实例

前两个是「裸数组 vs 分页壳」和「平台场次 vs 商家活动」。
三次同一个形状 —— **mock 的职责是替后端，不是替后端说好话**。
下一次遇到时值得考虑更系统的做法（例如从 OpenAPI 生成 mock 的校验）。

## 六、这次的方法论收获

分页壳是形状，契约是内容。**形状不对时，内容错得再离谱也看不见** ——
页面一律显示「暂无数据」，而所有测试层都是绿的：
后端断言自己返回的形状，ops-web 的 mock 按自己的类型造数据，两边各自自洽。

这与 `docs/technical/B端权限端到端用例.md` 记的是同一件事：
**跨端的缺陷只在真的把两端接起来跑时才现形。**
