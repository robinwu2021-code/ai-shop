# 微信物流能力清单

> 核对日期：2026-10-15。依据微信官方[物流消息能力](https://developers.weixin.qq.com/miniprogram/dev/platform-capabilities/industry/express/business/express_open_msg.html)与[物流查询组件](https://developers.weixin.qq.com/miniprogram/dev/platform-capabilities/industry/express/business/express_search.html)，并对照本仓库代码。此清单只整理这两套 `open_msg` 物流能力；微信支付的发货信息管理 `upload_shipping_info` 属于另一套交易管理接口。

## 0. 对接原则（2026-10-15 用户确认）

**物流对接先用微信已经提供的能力；微信不适用、权限未开通、接口无结果或缺少所需数据时，才引入其他渠道补足缺口。** “优先”是业务能力和数据真源的选择顺序，不要求只调用一家：微信接口不向我方返回完整轨迹节点，也未在下述文档中给出商家服务端轨迹回调，快递 100 的订阅回调可作为这两个缺口的持续补充，与微信关注并行。已有订单的真实状态始终写回同一运单真源，不能让 B/C 端分别取不同渠道的临时结果。

| 场景 | 首选微信能力 | 其他渠道只补什么 |
|---|---|---|
| 发货时核对号码与当前状态 | 当前运单有 token 时调用 `query_trace` / `query_follow_trace`；新号码先做本地校验 | 新号码尚无微信 token，或微信只给状态、无完整轨迹时，用快递 100 按公司+单号查询；查无记录仍标“待核实” |
| 发货后的状态更新 | 微信关注真实订单运单，取得 token 后立即查、之后按限频主动查；微信消息通知实际购买者 | 快递 100 订阅回调补齐我方服务端实时轨迹和节点；微信权限缺失或状态暂不可用时也可校正状态 |
| C 端物流详情 | 小程序优先打开微信物流查询组件 | 微信组件不可用时展示我方 H5/自建轨迹；完整节点、地图数据由其他渠道补齐 |
| 发货通知 | 微信物流消息优先通知实际购买者 | 收件人与购买者不同，或需向收件人通知时使用短信；发送前按对象和节点去重 |

微信接口要求真实小程序购物订单和微信交易单号；非微信支付、无有效买家 `openid`、权限不符的订单直接进入补充渠道，并记录原因。渠道失败不能回滚已提交发货，也不能把物流已签收直接当成交易已完成。

## 1. 能力与权限

| 能力 | 申请入口及准入 | 商家服务端接口 | 买家侧效果 | 我方可获取的数据 |
|---|---|---|---|---|
| **物流消息能力** | 小程序后台“功能 → 物流服务 → 物流消息”；小程序已发布、已开通微信支付，近 90 天有线上交易 | `follow_waybill` 传入真实购物订单与运单，返回 `waybill_token`；`query_follow_trace` 按 token 主动查；另有 `update_follow_waybill_goods`、`get_delivery_list` | 微信跟踪运单，在已揽件、派件中、已签收三个节点向**实际购买者**发服务通知，点击后可回访商家小程序 | 主动查询返回状态、运单号、运力及商品信息；文档所列返回体**没有完整轨迹节点** |
| **物流查询组件** | 小程序后台“功能 → 物流服务 → 查询组件”；已开通微信支付，近 30 天有交易；小程序须引用组件 | `trace_waybill` 传运单并返回 `waybill_token`；`query_trace` 按 token 主动查；另有 `update_waybill_goods`、`get_delivery_list` | 小程序通过 `logisticsPlugin.openWaybillTracking({waybillToken})` 打开微信物流详情；物流变化时可向**已订阅微信快递服务且为实际购买者**的用户发消息 | 主动查询返回运单状态等摘要；轨迹/地图由微信组件展示，商家服务端查询接口不提供完整节点列表 |

两套能力都可**主动查询状态**，也都涉及微信面向买家的物流消息。这里的“订阅/关注”指微信跟踪运单并通知买家；以上两页没有给出“微信向商家服务端推送轨迹 webhook”的地址、事件格式或签名协议，因此订单系统不能只靠微信消息自动更新 B/C 端状态。需要用主动查询把结果写回我方物流真源，快递 100 回调可补充详细轨迹。不能把微信物流消息、查询组件消息和通用 `wx.requestSubscribeMessage` 模板订阅当成同一个能力。

## 2. 接口顺序与字段边界

1. **先有真实订单，再传运单。** `follow_waybill` 的官方[接口](https://developers.weixin.qq.com/miniprogram/dev/server/API/weixin-express/express-msg/api_follow_waybill)要求买家 `openid`、收件手机号、运单号、商品信息、微信支付交易号 `trans_id` 和小程序订单落地页路径，可传运力 `delivery_id` 提高识别准确度。微信限制为小程序真实购物订单、实际购买者；预检一个尚未提交的错误运单时，不应先调用此接口。
2. **保存各自 token。** 两套传运单接口分别返回用于查询的 `waybill_token`。不应假设 `follow_waybill` 与 `trace_waybill` 的 token 可以跨接口通用；分别记录来源、当前发货身份、成功/失败及时间。官方 [`query_follow_trace` 文档](https://developers.weixin.qq.com/miniprogram/dev/server/API/weixin-express/express-msg/api_query_follow_trace)的简介引用了 `trace_waybill`，与能力列表的命名不完全一致，实际 token 配对须在取得权限后联调确认。
3. **主动查到的是状态摘要。** `query_follow_trace` 返回的 `waybill_info.status` 枚举为 `0` 运单不存在**或**未揽收、`1` 已揽件、`2` 运输中、`3` 派件中、`4` 已签收、`5` 异常、`6` 代签收。`0` 不能作为“运单号错误”的确证；接口成功也不能证明号码属于当前收件人。更正号码后只接受当前发货身份对应 token 的查询结果。
4. **频次与权限分别管理。** 物流消息能力的文档列出每 appid 10 万次/日、每用户 50 次/日、每用户最多同时绑定 100 个有效运单；查询组件列出每 appid 10 万次/日、每用户 100 次/日。两套权限需分别申请，不能用查询组件已开通推断物流消息能力已开通。
5. **买家和收件人可能不同。** 这两套能力的通知对象是实际购买者。给收件人的发货短信及 H5 看件入口仍需独立保留；买家侧若两套微信能力同时产生同一节点通知，先做真实账号联调与通知去重策略，避免重复打扰。

## 4. 对订单同步方案的影响

发货预检时，当前运单已有有效微信 token 就优先向微信主动查状态；新运单没有 token 时先做本地重复绑定校验，再用快递 100 补充查询，查无记录只能标“待核实”。真实发货提交后，优先执行微信物流消息关注、查询组件传运单与微信发货信息上报；拿到微信 token 后立即查一次，后续按配额定期校正。快递 100 订阅与微信关注并行，因为微信文档未提供我方服务端轨迹回调及完整节点；其回调只补充微信缺少的轨迹和及时性，微信不可用时承担状态补偿。所有结果写入同一 `lgs_waybill` 状态真源，B/C 列表与详情统一读取它；任何渠道不可用时，显示最后可信状态、来源和查询时间。

实施前需在小程序后台分别确认两项权限及发布状态，再用真实购买者账号验证：`follow_waybill` 返回 token、`query_follow_trace` 能查状态、查询组件正常展示、关键节点通知的收件人及重复情况。上述验证只针对测试订单，不用生产中的旧订单试发通知。
