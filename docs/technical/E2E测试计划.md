# E2E 测试计划：真 HTTP · 真库 · 用端上契约驱动

> 2026-08-09 · 目标：**把现在靠人手 curl 验证的那一段，变成能重复跑的测试。**
> 上游：[测试用例清单](./测试用例清单.md) · [交付计划](../requirements/交付计划-商家侧.md)

---

## 零、为什么现有测试不够

| 现有 | 覆盖到什么 | 覆盖不到什么 |
|---|---|---|
| 单元（24 条） | 纯规则 | 任何跨层的事 |
| 集成（240 条，MockMvc + H2） | Controller→Service→Mapper→H2 | **真 HTTP 栈**（序列化、过滤器链顺序、错误包装）· **真库差异** |
| 守卫（shared 142 · ops 559） | 契约声明是否一致 | 声明一致 ≠ 跑起来一致 |
| 手工 curl | 真 HTTP + 真库 | **不可重复**：每次改代码要重敲一遍，且没人知道上次验了什么 |

**本轮真库暴露、而 H2 集成测试全绿的缺陷有三个**：

| # | 缺陷 | 为什么 MockMvc 抓不到 |
|---|---|---|
| 1 | `GoodsVO` 实际字段是 `status`/`merchant.name`，我按 `auditStatus`/`merchantNo` 写了 ops-web 类型 | MockMvc 里没人按端上的类型去解析响应 |
| 2 | 待审队列返回全部商品 | 老用例断言是恒真的 `onSale ∈ {true,false}` |
| 3 | `/biz/order` 被数据域按 `user_no` 过滤成空 | 集成用例只查过库，没走过这个端点 |

> 三条都是「**声明对、跑起来不对**」。E2E 就是补这一层。

## 一、两层 E2E，各自解决不同的事

| 层 | 名字 | 跑什么 | 抓什么 |
|---|---|---|---|
| **E2E-1** | 后端真链路 | JUnit 起真 Web 容器（随机端口）+ **真 MariaDB** + `RestClient` 发真请求 | 真 HTTP 栈 · **H2 与 MariaDB 的差异** · 过滤器链 · 错误包装 |
| **E2E-2** | 前后端整合 | Node 脚本，**import 端上的 `endpoints.ts` 与 `@shared/types`**，按端上声明的路径与形状打真服务端 | 「端上以为的契约」与「后端实际给的」是否真的一致 —— 上面第 1 条缺陷正是这一类 |

**为什么必须是两层**：
E2E-1 用 Java 类型，验的是后端自己自洽；E2E-2 用**端上的类型与端点表**，验的是端能不能真的跑。
只有 E2E-2 会因为「ops-web 写了 `auditStatus` 而后端给的是 `status`」而红。

## 二、E2E-1：后端真链路（真库）

### 2.1 与现有集成测试的边界

| | 现有集成测试 | E2E-1 |
|---|---|---|
| 用例数 | 多（240） | **少**（只放关键旅程） |
| DB | H2 内存 | **真 MariaDB** |
| HTTP | MockMvc（不过网络栈） | 真端口 + 真客户端 |
| 何时跑 | 每次 `mvn test` | **单独 profile**，不进默认构建 |

> **不把 E2E-1 塞进 `mvn test`**：它依赖一个跑着的 MariaDB，
> 在没有数据库的机器上会红 —— 而「构建在别人机器上红」会让人开始忽略红灯。

### 2.2 步骤清单

| 步 | 内容 | 细节 |
|---|---|---|
| 1.1 | 建 `application-e2e.yml` | 指向真 MariaDB（`ai_shop_e2e` 库）；`shop.pay.stub=true`；`shop.seed.enabled=true` |
| 1.2 | 建基类 `E2eBase` | `@SpringBootTest(webEnvironment = RANDOM_PORT)` + `@ActiveProfiles("e2e")`；提供 `RestClient`、登录辅助、**每个类跑前重置库** |
| 1.3 | **库重置策略** | 用 Flyway `clean + migrate`。不重置的话上一次的数据会让分页断言飘（本轮已踩过：新增商家把断言目标挤出第一页） |
| 1.4 | 用 `@Tag("e2e")` 标记 | `mvn test` 默认排除；`mvn verify -Pe2e` 才跑 |
| 1.5 | 写旅程用例 | 见 §四 |

### 2.3 关键设计取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 库怎么准备 | **每个测试类重置** | 每个方法重置太慢（迁移要跑一遍）；不重置则用例互相污染 |
| 断言粒度 | **断业务事实，不断字段全等** | 断全等的用例每加一个字段就要改一次，最后没人愿意维护 |
| 时间与随机 | 手机号带类名前缀 | 并行跑时不撞号 |
| 失败信息 | 断言必须带 `.as("...")` | E2E 失败时离现场最远，没有说明就只能重跑一遍看日志 |

## 三、E2E-2：前后端整合（用端上契约驱动）

### 3.1 核心思路

端上有三份**纯数据**的契约声明，可以直接在 Node 里 import：

```
c-app/src/api/endpoints.ts   61 条  { method, path, auth }
b-app/src/api/endpoints.ts   68 条
packages/shared/src/types    响应/请求类型
```

E2E-2 **不重写路径**，而是从这些表里取路径去打真服务端 —— 于是：
- 端上改了路径 → E2E-2 立刻按新路径打，后端没跟上就红
- 后端改了响应字段 → 按 shared 类型校验时红

> 这正是[三端全栈对齐清单](./三端全栈对齐清单.md)里那些「端上有、后端没有」的缺口，
> 从**静态比对**升级成**真的打一次**。

### 3.2 步骤清单

| 步 | 内容 | 细节 |
|---|---|---|
| 2.1 | 建 `scripts/e2e/client.mjs` | 极简 HTTP 客户端：`fetch` + Bearer + `X-Store-No`；**按 `endpoints.ts` 的表发请求**，不硬编码路径 |
| 2.2 | 建 `scripts/e2e/journey-*.mjs` | 每条旅程一个文件，见 §四 |
| 2.3 | 建 `scripts/e2e/run.mjs` | 顺序执行旅程；每条打印步骤与耗时；任何一步失败立刻停并打印上下文 |
| 2.4 | 响应形状校验 | 用 `docs/api/openapi-*.yaml`（已由端上生成）逐字段比对实际响应 —— **这一步才能抓到第 1 类缺陷** |
| 2.5 | 接进 npm | `npm run e2e`（需要先起后端）；`npm run e2e:full`（自己起后端再跑） |

### 3.3 为什么不用 Playwright 之类

| 方案 | 为什么不选 |
|---|---|
| Playwright 驱真实浏览器 | uni-app 两端要先编译成 H5 再跑，链路长、失败原因多在编译而不在业务；ops-web 可以后续单独加 |
| 直接跑 b-app 的 `http.ts` | 它绑死 `uni.request`，Node 里没有 |
| **取 `endpoints.ts` + 自写 fetch** ✅ | 拿到的是**端真正会打的路径与形状**，而不需要整个 uni 运行时 |

## 四、旅程清单：按真实发生的顺序

**一条旅程 = 一个人从头到尾做完一件事**，中间不重置数据 —— 因为真实世界里也不重置。

### J1 · 商家从零到能做生意（E2E-1 + E2E-2 都跑）

| 步 | 动作 | 断言（业务事实） |
|---|---|---|
| 1 | 消费者注册登录 | 拿到令牌 |
| 2 | 提交入驻申请（带行业 + 服务范围） | 申请单 PENDING |
| 3 | 运营登录 → 待办里有它 | 队列含此申请 |
| 4 | 运营受理 | 状态 REVIEWING |
| 5 | 运营通过 | 主体 ACTIVE；**默认店/owner账号/进件占位都在** |
| 6 | 商家登录 → 看工作台 | 出现「还不能收款」卡 |
| 7 | 查进件状态 | `canReceiveMoney=false`，`missing` 含 settleAccount |
| 8 | 补资料提交进件 | ACTIVE；`payMerchantNo` 有值；**响应里搜不到明文账号** |
| 9 | 再看工作台 | 「还不能收款」卡消失 |
| 10 | 上架商品 → 运营审核 | 过审后 OFF_SALE（不是自动上架） |
| 11 | 商家上架 | C 端能搜到 |
| 12 | 买家下单并支付 | 商家订单列表出现这一单 |
| 13 | 商家发货（带单号） | FULFILLING；**买家侧能看到快递单号** |
| 14 | 商家标记送达 | COMPLETED |

### J2 · 多门店隔离

| 步 | 动作 | 断言 |
|---|---|---|
| 1 | 沿用 J1 的商家 | —— |
| 2 | 新建分店 | 门店列表 2 家 |
| 3 | 带 `X-Store-No=分店` 查订单 | **0 单** |
| 4 | 带 `allStores=true` | 有单 |
| 5 | 加员工 + 只授权分店 | —— |
| 6 | 员工登录 → 查订单 | **只看得到分店的**（现在缺这条用例） |
| 7 | 员工用默认店的门店号 | 越权号被丢弃，回落他自己的授权店 |

### J3 · 驳回与重来（失败路径，最容易漏）

| 步 | 动作 | 断言 |
|---|---|---|
| 1 | 提交申请（不填服务范围） | PENDING |
| 2 | 运营不补范围直接通过 | **被拒**（不能产出隐形商家） |
| 3 | 运营驳回但不写理由 | 被拒 |
| 4 | 运营带理由驳回 | REJECTED，商家侧能看到理由 |
| 5 | 商家改资料重提 | 新申请单 PENDING |
| 6 | 运营补范围通过 | 主体 ACTIVE，C 端可见 |
| 7 | 同一人再申请第二张执照并通过 | **建出第二个主体**，第一个不变 |

### J4 · 进件驳回与重试

| 步 | 动作 | 断言 |
|---|---|---|
| 1 | 主体名带「驳回」二字（stub 网关据此拒） | 提交进件 → REJECTED + 有原因 |
| 2 | 补资料重提 | 拒因被清掉 |
| 3 | 已 ACTIVE 后再提交 | 被拒（重复开户会拿到新商户号） |

### J5 · 运营端真链路（ops-web 已接真的三块）

| 步 | 动作 | 断言 |
|---|---|---|
| 1 | 运营登录 | 拿到权限码 |
| 2 | 关掉某行业的小微白名单 | `/common/master-data` 里该行业 `microAllowed=false` |
| 3 | 商家用该行业申请小微 | 进件主体被翻译成非小微 / 或申请被拒（**待确认口径**） |
| 4 | 待审商品队列 | 只含 AUDITING |
| 5 | 审一件 | 队列总数减一 |

## 六、失败时怎么查

E2E 失败离现场最远，所以约定三条：

| 约定 | 为什么 |
|---|---|
| 每步打印**步骤名 + 关键返回值** | 失败时不用重跑就知道断在哪一步 |
| 断言一律带 `.as()` / 自定义消息 | 「expected 0 to be greater than 0」说明不了任何事 |
| 失败时打印**最后一次响应体全文** | 字段错配这类问题，看一眼响应就够了 |

## 七、S1/S2 落地记录

### 怎么跑

```bash
# 一次性：建 E2E 专用库（**不是开发库** —— E2E 会 clean 整个库）
mysql -uroot -p -e "CREATE DATABASE IF NOT EXISTS ai_shop_e2e CHARACTER SET utf8mb4;
                    GRANT ALL ON ai_shop_e2e.* TO 'shop'@'%';"

# 跑 E2E（默认构建不含它）
cd backend && mvn -f shop-app/pom.xml test -Pe2e

# 跑快测（自动排除 e2e）
cd backend && mvn -f shop-app/pom.xml test
```

### 三处踩到的坑

| 坑 | 现象 | 修法 |
|---|---|---|
| `@Tag` 过滤没生效 | `Tests run: 0`，看着像没写用例 | 空的 `<excludedGroups/>` 在 profile 合并时**不覆盖父值** → 改用属性 `${surefire.excludedGroups}` |
| 清库把种子一起清了 | 运营登录 401 | 清库发生在 Spring 启动**之后**，要重放 `ApplicationRunner` |
| 支付要走回调 | 单停在 WAIT_PAY，发货被状态机拒 | `/pay` 只是拿收银台参数，**推进状态的是通道回调** |

### S2 的验收：故意改坏一次

把 `orderView` 里的 `s.getExpressNo()` 换成 `null`（即本轮修复前的状态），E2E 立刻红：

```
J1MerchantGoLiveE2eTest.merchantGoesLive:171
[买家要靠快递单号查物流；看不到的话发货这件事对他没有意义]
```

> **这一步不能省**：一个从来没红过的测试，与一个不存在的测试没有区别 ——
> 而 E2E 因为链路长，最容易写成「怎么改都绿」。
> 失败信息里能直接读到业务后果，也说明 `.as()` 那条约定是有用的。

## 八、S3/S4 落地记录：E2E 抓到了一个真的越权

### 四条旅程现状

| 旅程 | 步数 | 耗时 |
|---|---|---|
| J1 从零到能做生意 | 14 | 11s（含起容器） |
| J2 多门店与员工视角 | 8 | 2.3s |
| J3 驳回与重来 | 7 | 2.3s |
| J4 进件驳回与重试 | 7 | 2.1s |

跑法：`cd backend && mvn -f shop-app/pom.xml test -Pe2e`（共 ~18 秒）

### 🔴 J2 第 8 步抓到的越权

**症状**：只被授权到分店的店员，点一下「全部门店」（`allStores=true`），
看到了**主体名下所有店**的单。

**根因**：`allStores=true` 当时的实现是「不按门店过滤」——

```java
String storeNo = allStores ? null : ctx.currentStoreNo();   // null = 不过滤
```

对老板没问题（他的「全部」本来就是主体全部），对店员就是越权。
它不报错、不告警，只是**安静地多看到一些东西** —— 这类缺陷只有越权用例能发现。

**修法**：`BizContext` 增加 `owner` 标记，「全部门店」按人解释：

| 谁 | 「全部门店」是什么 | 为什么 |
|---|---|---|
| 属主 | 不按门店过滤 | 要含多门店之前那些 `store_no` 为空的历史单 |
| 店员 | 他被授权的门店集合 | —— |
| 没有任何授权的人 | **空集合 = 一家都看不到** | 把空集合当成「不过滤」，正是这类越权最常见的写法 |

**回归由谁守**：E2E 慢（18 秒），所以同时补了一条快测
`M9bBizGoodsFlowTest.allStoresIsScopedToGrantedStoresForStaff` ——
**E2E 负责发现，快测负责守住**。

### 一处配置差异要记住

E2E profile 要显式给 `shop.store.max-per-entity: 3`。
生产默认是 1（与单店时代行为一致），不放开的话 J2 第 2 步就建不出分店。

## 九、S5/S6 落地记录：E2E-2 第一次跑，就抓到了它该抓的那类错

J1 的 11 步全部走通（登录 → 入驻 → 审核 → B 端登录 → 进件 → 上架 → 下单支付 → 发货 → 送达），
**接口全是 200，没有一步失败**。但形状校验报了 8 处：

```
c-app.merchantApply → 缺字段 MerchantApplyStatus.name / subject / status / createdAt / …
```

查下来是真错配，而且是**只有这一层能抓到**的那种：

| | 声明的 | 实际返回的 |
|---|---|---|
| `c-app/src/api/contract.ts:249` | `Promise<MerchantApplyStatus>` | —— |
| `c-app/src/api/mock.ts:1207` | 完整状态对象 | —— |
| 后端 `POST /mp/merchant/apply` | —— | `Map.of("applyNo", …)` |

端上 `pages/me/index.vue:118` 把返回值**直接赋给页面上的申请状态**。
所以真实后果是：用户提交入驻，接口 200，页面渲染出一张所有字段都是 `undefined` 的空白卡片，
**且不报任何错** —— 他只会以为没提交上去，然后再点一次。

三条证据里两条（端上契约、mock）是一致的，跑偏的是后端，所以改后端：
返回提交后的完整 `MerchantApplyVO`，与 B 端 `POST /biz/merchant/apply` 同一口径
（那边的注释早就写着「返回提交后的最新资料，前端直接替换本地状态」）。

> **这正是 E2E-2 的存在理由**：E2E-1 全绿、集成测试 253 条全绿、接口 200 ——
> 没有任何一层会因为「少了几个字段」变红，因为后端自己是自洽的。
> 只有拿端上声明的类型去对真实响应，才会看见这个洞。

## 十、S7 落地记录：J5 上线，又抓到一个「mock 上完全正常」的真错配

J5（运营维护类目与经营准入）跑通 11 步，跨越运营端与商家端 ——
它是唯一一条能验「门槛必须有发证的一侧」的旅程：类目的 `requiredCode` 由运营设，
商家的 `categoryCodes` 也由运营发，撞上门槛的却是商家。三方分处两个端，
任何单端的测试都测不出「门槛只会拒绝」这种故障。

### 顺手抓到的第二个真 bug：b-app 保存商品在真实后端上一次都没成功过

J5 第 8 步 500。查下来是请求体形状对不上：

| | `title` 发的是什么 |
|---|---|
| `b-app/src/api/http.ts`（改前） | 直接把 `GoodsDraft` 原样 POST → `title` 是**三语对象** |
| 后端 `SaveGoodsReq` | `String title` + `Map<String,String> titleI18n` —— **两个字段** |

后端反序列化直接抛 `HttpMessageNotReadableException`，返回 500「系统开小差了」。
而 mock 上完全正常（mock 收的就是 `GoodsDraft`），所以从来没人发现。

修法是在 `http.ts` 里拍平（页面继续用三语对象编辑，不该知道线上格式），
并把 `SaveGoodsReqBody` 从 `= GoodsDraft` 改成显式的线上类型。

### 顺带修好一个把自己伪装成契约错配的解析 bug
