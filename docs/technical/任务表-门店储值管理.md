## 1. 首期边界

- 账户固定按“租户＋商家＋门店＋顾客＋币种”唯一；同客同店的多个储值方案汇入同一账户，不同门店余额隔离。
- 独立储值方案本期按门店管理，当前店创建、查询、启停和办理；方案模板的连锁复用不进入本期。商家身份仍参与权限与资金隔离，不能只有storeNo就授权。
- 每笔充值、批次及收支记录保留办理门店与来源方案/版本，实收、赠送由后端计算并固化；金额不因后续启停变化。
- 首期完成：方案管理、会员识别、充值实收到账、顾客账户、基本收支查询与B端接入。
- 保留已有合法核销记录及核销内核，改造其门店选账以免跨店扣款；不新增核销业务页面或跨店核销流程。
- 暂缓：连锁共用、账户组/门店组绑定、模式选择与切换、跨店清分、核销成本分摊、线上购买、线上退款。

### 3.1 ST02门店隔离影响面

1. `sv_account`新增store_no及对应唯一键，保留entity_no；更新所有ensure/findOwner/lockOwner和账户号生成规则，门店不可由客户端任意指定。
2. 余额查询、充值到账、批次筛选、核销报价/冻结/确认、恢复路径和消费者门店查询都必须选到同一门店账户。仅充值入口加storeNo不算完成。
3. 门店切换不再返回商家合计；账户引用及分页游标绑定租户、商家、门店、筛选条件。
4. 核销批次除范围条件外必须属于当前门店账户；已有功能因本次结构变更受影响，需要做定向兼容验证。

### 3.2 ST03历史数据处理

现有商家维度账户可能已包含多店资金，不能把整笔余额归给“最近充值店”，也不能复制到每家店。

- 先只读盘点已入账批次、来源充值门店、历史核销分配、冻结预占和未完成充值。核实当前实例真实数据，再决定迁移批次。
- 可从批次剩余本金/赠金及来源门店完整恢复的，制定可对账的迁移清单；跨店历史消费按既有批次分配事实还原剩余资金归属，不倒推猜测。
- 存量预占和已收款未到账单据必须有明确处理策略，切换期间暂停相关写入或使用兼容路由，不得跨新旧账户重复入账。
- 来源不明或无法对账的账户不自动迁移；保留原账并形成处置清单。当前系统未正式上线也不能未经盘点重置余额。
- 切换前后对账按账户/门店/批次检查余额、冻结额和凭证，不修改已应用迁移，不删除历史资金事实。

### 3.3 ST04–07服务端增量

- Pay新增门店方案及版本表（方案含store_no，版本不可变）和统一收支读模型；沿用现有账户/批次/凭证，不再新增连锁账户组或模式配置表。
- 独立方案充值新增PLAN来源；保留ACTIVITY历史来源。来源校验、原单权限、事件恢复必须同时适配。
- 收支读模型从成功过账凭证生成，保存办理门店、金额、余额快照及来源；处理中、取消充值不作为余额变动。
- 目录按当前店真实储值资格过滤；会员姓名/手机资料经Core受控获取，禁止跨库JOIN和无界拉全会员前端过滤。

## 4. API范围（本轮已编码，历史端点保持兼容）

前缀`/biz/stored-value`；当前门店由统一切店上下文传递并由服务端校验，方案查询、创建、详情及启停也须校验该门店。

| 功能 | API |
|---|---|
| 门店方案 | GET/POST /plans；GET /plans/{planNo}；PUT /plans/{planNo}/status |
| 门店顾客目录/详情 | GET /account-directory；GET /accounts/{accountRef} |
| 门店统一收支 | GET /records；GET /records/{recordNo} |
| 独立方案充值 | POST /plan-recharges；POST /plan-recharges/{no}/submit、receive、cancel；GET /plan-recharges/{no} |

本期不新增账户模式设置、连锁组管理、绑定或清分接口。原GET /accounts单客余额端点保留路径并改为门店语义，须同步检查全部调用方，不能静默留一个返回商家余额的旁路。
