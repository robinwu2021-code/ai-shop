## 1. 目标

**会话从「进程本地磁盘」搬到「数据库 + 本地两级缓存」，并把三端的身份边界补齐到会话与审计层。**

三条硬要求，全文围绕它们展开：

| # | 要求 | 落法 |
|---|---|---|
| R1 | **令牌表、用户表清晰分离** | 三端各一套（用户 / 会话 / 登录日志），零 join 零外键 |
| R2 | **将来要能拆库** | 每端闭环；DAO 只认自己的 `JdbcClient`，换库=换 bean |
| R3 | **三端认证清晰隔离，但共用一套基础代码** | 一份实现 + 三份档位装配，无例外分支 |

## 3. 方案选型

| 方案 | 多实例 | 撤销 | 外部依赖 | 结论 |
|---|---|---|---|---|
| 现状：Ehcache 持久化 | ❌ | 仅本进程 | 无 | 已是瓶颈 |
| Redis | ✅ | 天然 | **要装 Redis** | 长期目标，今天没有 |
| **DB + 本地两级缓存** | ✅ | TTL + 撤销轮询 | 无 | ✅ **本次采用** |
| 无状态 JWT | ✅ | ❌ **撤不掉** | 无 | ❌ 见下 |

**为什么不是 JWT**：这套鉴权的权限新鲜度与停用生效都依赖「能撤销」，
而 JWT 签发后在过期前撤不掉 —— 除非再维护一张黑名单表，那就绕回来了，
且黑名单比会话表更难对账。**能撤销是硬需求，不是可选项。**

**与 Redis 的关系**：`TokenStore` 接口不变，`DbTokenStore` 是并列的第四种实现。
将来上 Redis 改一行配置，两者可共存灰度。

## 4. 分离边界（R1）

### 4.1 九张表，三个隔离域

| 端 | 用户表 | 会话表 | 登录日志表 | 令牌前缀 | 路径 |
|---|---|---|---|---|---|
| C | `usr_account` ✅已有 | `usr_session` 新 | `usr_login_log` 新 | `ctk_` | `/mp/**` |
| B | `mch_account` ✅已有 | `mch_session` 新 | `mch_login_log` 新 | **`btk_` 新** | `/biz/**` |
| 运营 | `sys_ops_staff` ✅已有 | `ops_session` 新 | `ops_login_log` 新 | `otk_` | `/ops/**` |

### 4.2 隔离靠什么保证（不是靠自觉）

| 维度 | 保证方式 | 违反时会怎样 |
|---|---|---|
| 令牌 | 前缀先行校验，**不符直接 401 且不查库** | 跨端令牌根本进不了下一层 |
| 存储 | 三套表，**零 join、零外键** | 架构测试拦（A13） |
| 加载 | 每端 `IdentityLoader` 只读本端用户表 | 架构测试拦 |
| 缓存 | **三份，绝不共用** | 共用等于把刚分开的边界在内存里又合上 |
| 路径 | 三个过滤器一一对应路径前缀 | 装配测试断言映射 |
| 库 | `JdbcClient` 作构造参数 | 换库=换 bean，代码不动 |

### 4.3 迁移按端分三条写，不合并

现在没有区别；将来把某一端搬去独立库时，「只把这一端的迁移拿过去跑」才成立。
合成一条的话，拆库那天要先做一次拆迁移。

## 5. 一套基础代码（R3）

### 5.1 模块

```
shop-auth-store/              新 · JdbcClient 手写 SQL，**零 MyBatis、零 shop-base**
  Realm.java                    CONSUMER / MERCHANT / OPERATOR
  SessionProfile.java           档位：表名、前缀、各种 TTL（见 §10）
  SessionRow / SessionDao       八列，三端同构
  LoginLogRow / LoginLogDao     登录审计
  IdentityLoader.java           **SPI**：user_no → LoginUser。实现留在各业务模块
  DbTokenStore.java             实现现有 TokenStore，按 profile 装配三次

<业务模块>/**                  三个 IdentityLoader 实现
  shop-core     → ConsumerIdentityLoader（usr_account）
                  OperatorIdentityLoader（sys_ops_staff + LivePermResolver + scopeOf）
  shop-merchant → MerchantIdentityLoader（mch_account）

shop-base/auth/
  AbstractTokenAuthFilter       抽公共基类
  Consumer/Merchant/OperatorTokenAuthFilter   三个薄子类，只差 profile
```

> `IdentityLoader` 必须是 SPI：还原身份要读业务表，而**鉴权基础代码不能依赖业务模块**
> —— 与 `LivePermResolver` / `BizIdentityResolver` 同一手法，那两个已经这么做了。
>
> `shop-auth-store` 不依赖 `shop-base` 是刻意的：`shop-base` 把 mybatis-plus 作为编译依赖，
> 而将来任何服务（含 `shop-job`）要嵌入鉴权，都不该被迫把 MyBatis 拖进 classpath。
> **这一条就是「统一鉴权」下一阶段的地基。**

### 5.2 装配：一份实现，三次

```java
new DbTokenStore(jdbc, SessionProfile.CONSUMER, consumerIdentityLoader)
new DbTokenStore(jdbc, SessionProfile.MERCHANT, merchantIdentityLoader)
new DbTokenStore(jdbc, SessionProfile.OPERATOR, operatorIdentityLoader)
```

**没有例外分支。** 三张会话表完全同构（§6），所以 `SessionDao` 连行映射都只有一份。
有例外分支的抽象迟早会被例外撑开。

## 6. 会话表：八列，到此为止

```sql
id            BIGINT PK
token_hash    CHAR(64)  UK    -- SHA-256(token) 十六进制，**不存明文**
user_no       VARCHAR(32)     -- 主体标识；revokeUser 按它批量撤销
issued_at     DATETIME
expires_at    DATETIME        -- 签发 + 30 天，与今天一致
last_seen_at  DATETIME        -- 节流写回（§8.4）
revoked_at    DATETIME NULL   -- **软撤销，不物理删**
revoke_reason VARCHAR(32)     -- LOGOUT / FORCED_OUT / DISABLED / PURGED
```

索引：`uk_token(token_hash)`、`idx_user(user_no, revoked_at)`、
`idx_expires(expires_at)`、`idx_revoked(revoked_at)`。

**会话表只回答一件事：这个令牌属于谁、还有效吗。**

### 6.1 三条决定

**① 不存 `nickname` / `roles` / `perms` / `tenant_no` / `scope`。**
它们的变动频率高于会话生命期（会话活 30 天，角色可能今天改）。
存进去就有第二个真源，而过期的那一份**不会报错，只会让人拥有他昨天的权限**。
§2 已实测：这几样全都能重新算出来。

**② 不存 `realm` 列。** 表本身就是按端分的，再存一列 realm
等于允许「运营端的行出现在 C 端表里」这种状态存在。

**③ 存 token 的 SHA-256，不存明文。** 库被拖走 ≠ 会话被拿走。
**用 SHA-256 而不是 bcrypt**：token 是 128 位随机串不是密码，没有字典攻击面；
上 KDF 等于给**每个请求**加几十毫秒，那会让方案第一天就被判定为太慢。

**④ 软撤销不物理删。** 删了就分不清「没这行」和「被踢了」，
而「我为什么突然被登出」是运营最常问的问题之一。物理清理交给定时任务，且只清过期很久的。

## 7. 身份还原

`token → user_no` 之后，`LoginUser` 由**本端用户表现读 + 现算**得到：

| 端 | 还原路径 | 库内读 |
|---|---|---|
| C | `usr_account`（昵称、状态） | 1 |
| B | `mch_account`（账号、状态）→ `BizIdentityResolver(userNo, X-Store-No)` | 1 + 现算（本来每请求就要算） |
| 运营 | `sys_ops_staff`（roles/real_name/status/tenant_no）→ `LivePermResolver(roles)` → `scopeOf(staff, perms)` | 1 + 两次纯计算 |

**每端只读本端用户表 —— 这同时是 R2 的第 3 条约束。**

### 7.1 白得的好处

| 变更 | 原来 | 现在 |
|---|---|---|
| 改角色 / 改数据域 / 改昵称 | 必须 `revokeUser`，否则等下次登录 | **下一个请求就生效** |
| 停用账号 | 踢人 | 仍踢人，且多一道：还原时读到 `status != ACTIVE` 直接 401 |

`revokeUser` 因此收窄回本来的语义：**主动登出、强制下线、停用**。
一个接口被用来实现四五件事时，总有人会漏调其中一处 ——
而漏调的表现是「改了权限没生效」，很难联想到会话。

### 7.2 还原失败必须 401

令牌有效、但用户表里查不到那个 `user_no`（数据清过、库不一致）：
**返回 401 并记 `LOGIN_FAILED / ORPHAN_SESSION`，不要放行。**

写成「查不到就给一个空 `LoginUser` 放行」的话，症状是**一个没有任何权限的幽灵身份在系统里游走**
—— 它在多数接口上会被权限挡住，于是不报错；直到碰上一个只判「登录了没」的接口。

### 7.3 B 端刻意不把门店存进任何地方

门店由每请求的 `X-Store-No` 决定，店长可切换，`BizIdentityResolver` 每次现算并校验归属。
存进会话就有第二个真源，过期的那份会让**「切了门店但权限还是上一个店的」**——
界面上看是「数据串了」，排查方向会完全跑偏。

## 8. 缓存与一致性

### 8.1 两级缓存，按**变化频率**分层

```
L1-会话   token_hash → (user_no, expires_at)     会话内永不变 → TTL 长
L1-身份   user_no    → LoginUser（已还原）        随用户表变   → TTL 短
```

两层都用 **Ehcache（堆内，绝不落盘）**，三端各一套共六个实例；
什么能放什么不能放，见 **§17**。

放一层里的话，TTL 要么迁就会话（身份变更迟迟不生效），要么迁就身份（令牌白白反复回源查库）。

### 8.2 两个旋钮分开拧 —— C 端能轻的全部原因

- `cacheTtl` 大 → 回源少（**轻**）
- `revokePoll` 小 → 踢人快（**安全**）

两者互不影响。把它们当成一个旋钮（「缓存久 = 踢人慢」）是最常见的误解，
而按那个误解设计，C 端只能在「贵」和「不安全」之间二选一。

### 8.3 撤销传播：两道保证，上界明确

| 机制 | 延迟 | 作用 |
|---|---|---|
| L1 TTL | ≤ `cacheTtl` | 兜底，永远成立 |
| **撤销轮询** | ≤ `revokePoll` | 主力：读 `WHERE revoked_at > :lastSeen`，**只剔那几条** |

**不清空整个 L1** —— 清空会在踢一个人时让所有在线用户的下一次请求一起回源，
把一次撤销放大成库上的尖峰。

`revokeUser` 变成一条 UPDATE，返回行数即接口约定的「踢掉的会话数」：
```sql
UPDATE <session_table> SET revoked_at = ?, revoke_reason = ?
 WHERE user_no = ? AND revoked_at IS NULL
```

**身份失效**：B 端 / 运营端的撤销轮询顺带扫 `WHERE updated_at > :lastSeen` 剔身份缓存；
**C 端不扫** —— `usr_account.updated_at` 会被改昵称改头像刷动，百万用户下扫出来多是无关变更；
C 端身份载荷只有「你是谁 + 状态」，短 TTL 足够，真要立刻生效的封禁走 `revokeUser`。

### 8.4 三条容易被「优化」掉的

**① 不做负缓存。** 查不到就 401，不缓存「不存在」。
否则用户刚在实例 A 登录，B 若缓存过该 token 的 miss，登录后头几秒会**间歇性 401**
—— 这种错「重试一下就好了」，最容易被归因成网络问题然后长期存在。
无效令牌的压力由前缀校验（不查库）与登录限流承担。

**② `last_seen_at` 节流写回。** 每请求 UPDATE 会把这张表变成全库写最频繁的表。
它只用于「这个会话还活着吗」，低精度足够。

**③ 时间一律用应用时钟。** `expires_at` 的写入与比较都在应用侧，不用 SQL 的 `NOW()`。
多实例 + 数据库时区不一致时，症状是「有的实例认为过期了、有的没有」，日志里看不出来。

## 9. 登录日志

三张同构，只有表名与保留期不同：

```sql
id / at / event / user_no / result / reason / client_ip / user_agent
```
`event`：`LOGIN` / `LOGOUT` / `LOGIN_FAILED` / `REVOKED`。

**① IP 与 UA 记这里，不记会话表。** 会话表将来要被多个服务读；日志表访问面窄、保留期短。

**② 日志表不是控制平面。** 要做「失败 N 次锁定」，计数单独放 ——
现有 `RateLimiter` 就是这么做的。审计可以丢、可以异步、可以采样，控制平面不行；
**合在一张表上等于让安全策略依赖一条允许丢失的写入。**

**③ 成功异步写、失败同步写。** 登录是最容易被刷的接口之一；
成功日志异步（有界队列，满了丢并**计数暴露成指标**）不影响响应，
而失败日志正是被刷时最该留下的证据，不能丢。运营端两者都同步（一天不到一百次）。

保留期：C 端 90 天 / B 端 180 天 / 运营端 **730 天**（运营操作要能追溯两年）。

## 10. 三端档位（`SessionProfile`）

```java
record SessionProfile(
    Realm realm, String tokenPrefix, String sessionTable, String loginLogTable,
    Duration sessionTtl, Duration cacheTtl, Duration identityTtl,
    Duration revokePoll, Duration lastSeenThrottle,
    boolean asyncLoginLog, int logRetentionDays)
```

| 参数 | C 端（轻） | B 端 | 运营端 | 理由 |
|---|---|---|---|---|
| `cacheTtl`（会话） | **5 分钟** | 60 秒 | 60 秒 | C 端会话量可能高三个数量级 |
| `identityTtl`（身份） | **60 秒** | 30 秒 | 30 秒 | 身份变更的可见延迟 |
| `revokePoll` | **10 秒** | 5 秒 | 5 秒 | 撤销事件 C 端稀少 |
| `lastSeenThrottle` | **24 小时** | 1 小时 | 1 小时 | 精度需求低 |
| `asyncLoginLog` | 是 | 是 | **否** | 运营端审计要求最高、量最小 |
| 过滤器链 | **最短**（无 RBAC、无 BizContext） | + 身份解析 | + 权限现算 | C 端本来就不需要那两步 |
| 日志保留 | 90 天 | 180 天 | 730 天 | |

> C 端的「轻」是四件事叠出来的：**列最少、回源最少、写回最少、链路最短**。
> 没有一件砍掉安全保证。

## 11. 拆库就绪（R2）

### 11.1 四条约束，现在遵守成本为零

1. **三组表之间零 join、零外键。** 会话表只存 `user_no` 字符串 ——
   外键会在拆库那天变成第一个要拆的东西。
2. **每个 Realm 的 DAO 只认自己的 `JdbcClient`**（构造参数注入）。换库 = 换 bean。
3. **登录与还原只查本端用户表。** 今天已成立，不要在新代码里破坏。
4. **跨界只允许现有两处**（见 11.2），不许新增第三处。

### 11.2 三端拆库难易，恰好与轻量化同序

| 端 | 拆库时还需要什么 | 难度 |
|---|---|---|
| **C 端** | 登录查 `usr_account`、会话查 `usr_session`、日志写 `usr_login_log` —— **闭环** | ✅ 可以先拆 |
| B 端 | 还要 `BizIdentityResolver` 读 `mch_entity` / `mch_store` / `mch_staff` | ⚠️ 同库或走 API |
| 运营端 | 还要 `LivePermResolver` 读 `sys_role_point`，菜单读 `sys_function*` | ⚠️ 同库或走 API |

> **C 端最轻、最独立、最容易先拆 —— 这三件事是同一件事。**
> 它的轻正来自「没有 RBAC、没有实体门店归属」，而那两样正是另两端拆不动的原因。

拆库后 `session-purge` 变成三份（每库一份）——
定时任务模块的 `job_definition.target` 已为此准备好，不用改设计。

## 16. 与「统一鉴权」下一阶段的关系


## 17. 本地缓存统一用 Ehcache

### 17.1 用它，但**堆内、绝不落盘**

Ehcache 已是现有依赖（`shop-base/pom.xml:102`），不新增东西。认证链路上所有高频读
统一走它，六个实例：**三端 × 两层**。

```
auth.consumer.session   auth.consumer.identity
auth.merchant.session   auth.merchant.identity
auth.operator.session   auth.operator.identity
```

| 配置项 | 取值 | 说明 |
|---|---|---|
| 存储层 | **仅 heap** | ⚠️ **绝不开 disk 持久化** |
| TTL | 来自 `SessionProfile`（§10） | 会话层长、身份层短 |
| 条目上限 | C 端大 / B·运营小 | 打满后**静默 LRU 淘汰** |
| 统计 | **必须开** | 见下 |

> ⚠️ **不落盘这条是拿事故换来的。** 2026-08-24 线上全员掉线，
> 原因就是 Ehcache 的持久化目录在非正常关闭后被整个删掉（§2.2）。
> 本方案的 L1 **丢了没有任何后果** —— 回源查库而已。
> 一旦有人给它加上 `disk` 层想「重启后还热着」，就把那个事故重新装了回来，
> 而且这次连数据都不是它的（权威在库），纯亏。

**命中率与淘汰计数必须暴露成指标。** 条目上限设小了的表现不是报错，
而是「查库莫名其妙变多」；没有指标的话，这件事只能靠猜。

### 17.2 什么能放、什么绝对不能放

**判据一句话：库里有权威副本吗？**

| | 对象 | 放 Ehcache？ |
|---|---|---|
| ✅ | `token_hash → user_no`（权威在会话表） | 放 |
| ✅ | `user_no → LoginUser`（权威在用户表） | 放 |
| ❌ | `LivePermResolver` 的整表快照 | **不放** —— 它自己已有缓存，再包一层会让失效更难推理 |
| ⏸ | `BizIdentityResolver` 的 `(userNo, storeNo) → BizContext` | **本期不缓存**。它是归属判定（安全边界），而现算只是一次带索引的查询；等有实测数据再说 |
| 🚫 | 短信验证码、图形验证码、重置令牌、限流计数 | **绝对不能放** —— 见下 |

最后一行是重点：**这些东西本身就是权威，没有第二份副本。**
Ehcache 有两个性质对它们都致命：**进程内**（多实例下各算各的）、
**可淘汰**（条目上限打满就静默丢，而丢一个验证码 = 用户收到了码但校验不过）。

它们的正确归宿与会话一样是**进库**，但性质不同：会话缓存是「加速」，
它们是「存储」—— 库是权威，本地只能做极短的读缓存，且**写必须直达库**。

### 17.3 由此暴露的：多实例还有四处前置

粗扫认证链路（非全量），发现四处进程内状态，**多实例后全部失真且不报错**：

| 组件 | 多实例后的症状 | 为什么难查 |
|---|---|---|
| `InMemoryRateLimiter` | 限流上限变成 **N 倍**（密码 15 分钟 10 次 → 两实例 20 次） | 没有任何报错，只是防线变松 |
| `OtpStore` | A 实例发码、B 实例校验 → **验证码无效** | **间歇性**，取决于负载均衡打到哪台 |
| `CaptchaService` | 同上 | 同上 |
| `PasswordResetTokens` | 重置链接间歇性失效 | 同上 |

> **结论：本 TDD 解锁的是多实例的「可能」，不是「可以」。**
> 真要跑两个实例，这四处必须先解决 —— 它们的解法与会话同型
> （权威进库 + 本地极短读缓存），但**不属于本次交付**，单列一个里程碑。
>
> 而且上面是粗扫。**正式上多实例之前需要一次专门的审计**：
> 凡是 `private static final Map` 承载跨请求状态的地方都要过一遍。

### 17.4 任务增补

- [ ] A15 六个 Ehcache 实例统一装配，**heap-only**；命中率/淘汰数暴露成指标
- [ ] A16 一条守卫测试：认证相关的 cache 配置里**不得出现 disk 层**
      —— 报错文案写明 2026-08-24 那次事故
- [ ] A17（**不在本次交付**）多实例前置审计：OTP / 验证码 / 重置令牌 / 限流计数进库

## 18. ⚠️ A7 的拦路问题：**未开店的用户也要访问 `/biz/**`**

动手做 A7（B 端改发 `btk_` + `/biz/**` 切链）时撞到一个方案没考虑到的约束。

### 18.1 先澄清一处**看似**矛盾的地方（其实不矛盾）

`BizAuthController` 的类注释主张「**商家账号与 C 端账号是同一套凭据**」，
理由很实在：「入驻申请人此刻还只是个普通用户，审核通过后同一个账号长出了商家身份。
分成两套就要回答『入驻通过时给他发个新账号吗、旧账号还能不能买东西』，
而这两个问题在邻里场景下都没有好答案 —— 店主本来就是小区里的买家。」

这看起来在反对分池，其实不是：**它说的是一套「账号」，我们分的是两套「令牌池」。**
`TDD-三端服务拆分` §5 早就写明了这一点：「仍可用 C 端账号**校验身份**，
但**签发 `btk_`** —— 校验源与令牌池是两件事，分开后才能各自演进。」

真正过时的只有那句「真正的隔离在运营池」—— 三端分池之后不再成立。

### 18.2 真正的拦路问题

入驻接口是 **`/biz/merchant/apply`**（GET 看进度 + POST 提交）。
调它的人**按定义还不是商家** —— 他此刻只有 C 端身份。

于是 `/biz/**` 一律要求 `Realm.MERCHANT` 会让**没开店的人连入驻页都打不开**，
而那正是「登录即注册」承诺的那一屏（工作台显示「还没有开店 / 去入驻」）。

生产数据佐证这条路是活的：`mch_account` 有 6 个老板行、3 个店员行，
**6 个老板行都有 `user_no`** —— 也就是说老板确实是「C 端账号长出来的商家身份」。

### 18.3 四条路

| | 做法 | 代价 |
|---|---|---|
| **A** | 入驻接口移到 `/mp/**`（消费者身份发起入驻） | 要改 b-app；但**语义最正**——`BizAuthController` 自己的注释就说「申请人此刻还只是个普通用户」 |
| B | `/biz/**` 分两段：入驻那几个口允许 CONSUMER，其余要求 MERCHANT | 两条链交叉，隔离规则从「按前缀」变成「按前缀 + 例外清单」，而例外清单会长 |
| C | 未开店用户也签发 `btk_`（subject 用 C 端 userNo） | **把「一列装两种 id」原样搬进新池子** —— 正是分池要消灭的东西 |
| D | B 链同时接受 MERCHANT 与 CONSUMER | 隔离打折，等于没分 |

**建议 A。** 它把「谁是商家」这条线画在了正确的位置上：入驻是消费者做的事，
经营才是商家做的事。C 会让这次改造白做，D 等于不做。

### 18.4 老板的 subject 用哪个（选了 A 之后仍要定）

老板在 `mch_account` 里**有一行**（`login_phone` 为 NULL，靠 `user_no` 认）。
所以签发 `btk_` 时 subject 可以取 `mch_account_no`，
于是 **MERCHANT 池的 `user_no` 列统一是商家账号号**，不再一列装两种 id。

好消息：`BizIdentityResolverImpl` 现在就是
`WHERE user_no = ? OR mch_account_no = ?` —— **两种 subject 它都认**，
所以这一步不需要改解析器。

## 19. 本版相对早期草稿改了什么

早期版本是叠着改出来的，正文里留着三处「初稿写错了」的痕迹。本版重整，实质改动三条：

1. **会话表从十四列砍到八列。** 早期把 `nickname` / `roles` / `perms` / `tenant_no` / `scope_json`
   留在 `ops_session`，违反了文档自己定的原则 ——「变动频率高于会话生命期的东西，不进会话」。
   核实后确认那几列全是可重算的（§2）。删掉后三张表完全同构，装配再无例外分支。
2. **`realm` 列删除。** 表已按端分，再存一列等于允许「跨端的行出现在同一张表里」。
3. **`revokeUser` 语义收窄**为登出 / 强制下线 / 停用，撤销触发点核对清单因此少了一半。
