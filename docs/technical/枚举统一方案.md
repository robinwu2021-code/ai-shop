# 六个核心枚举的三端统一方案

> 2026-08-10 · 触发原因：连续六轮浏览器端到端测试，每一轮都撞到同一类故障 ——
> **接口 200、数据在、页面空白或显示 i18n 键名**，而单元/集成/E2E/契约测试全绿。

## 0. 先说结论：为什么现有工具抓不到这六个

`scripts/check-enums.mjs` 当前报 33 条差异。**这六个概念一条都不在里面。**

原因是它的判定逻辑：

```
全集 = 后端所有大写字面量
报错 = 端上声明的值 ∉ 全集
```

这只能抓「**端上编了一个后端没有的词**」。而这六个里最伤人的一类是
「**两边都有词，但不是同一个词，或者是同一个词却不是同一个东西**」——
全集里两个词都在，比对永远通过。

再加上 `FULFILLMENT` 已经进了 `KNOWN_SHARED` 豁免名单，
连它名下**新出现**的差异也一并被静音了（下面 §3 就是这么漏掉的）。

> 这轮的直接教训：**把已知差异记进豁免名单 ≠ 它是安全的**。
> 记的时候判断的是「改动风险」，没判断「它现在有没有在造成后果」。

---

## 1. 梳理：六个概念的实际取值

真源一律是**库**（wire 上传的就是库里的值）。下表「端上」列标注 ⚠️ 的是有问题的。

### ① 订单状态

| 位置 | 取值 |
|---|---|
| 库 `ord_sub_order.status` | `WAIT_PAY` `WAIT_FULFILL` `FULFILLING` `COMPLETED` `CANCELLED` `REFUNDED` |
| 后端下发 `OrderStatusView` | `WAIT_PAY` `PAID` `SHIPPED` `ARRIVED` `COMPLETED` `CANCELLED` `REFUNDED` |
| shared（c/b） | 同上 **+ ⚠️`REFUNDING`** |
| ops-web | 同下发口径 ✅ |

存储态粗（三种履约一视同仁）、展示态细（按履约展开），
这个**分层是对的**，`OrderStatusView` 双向映射（输出 + 查询筛选）也已经建好。

遗留一处：shared 的 `OrderStatus` 里混进了 `REFUNDING`。
它是 **`OrdAfterSale` 售后单的状态**，订单本身没有这个态。
ops-web 的注释里恰好写明了这条原则——「售后是挂在订单上的另一张单，不是订单本身的状态」——
而 shared 自己违反了它。C 端按 `REFUNDING` 筛订单，得到的永远是空列表。

### ② 五品类

| 位置 | 取值 |
|---|---|
| 库 `prd_goods.type` | `NORMAL` `FRESH` `SERVICE` `VIRTUAL` `CARD` |
| 库 `sys_channel_category_rule.category_type` | 曾用 `GOODS`，V12 已统一为 `NORMAL` ✅ |
| 库 `prd_category.template` | `STANDARD` `FRESH` `SERVICE` `VIRTUAL` `VOUCHER` |
| shared `CATEGORY_TYPE` | 值已对 ✅，但**⚠️ 键仍叫 `GOODS`** |
| ops-web | 只有 `type: string`（没类型）+ `CategoryTemplate` ✅ |

值已经修完（上一轮）。但还剩两笔账：

- **名实不符**：`CATEGORY_TYPE.GOODS = "NORMAL"`。能跑，但下一个人读到
  `GOODS` 会以为 wire 上是 `GOODS`——这正是它当初写错的原因。
- **`template` 与 `type` 是两套近义词**：`STANDARD`↔`NORMAL`、`VOUCHER`↔`CARD`
  指的是同一件事的两个面（录入模板 / 商品形态），却用了不同的词。
  目前**没有任何地方定义它们的对应关系**，靠人脑记。

### ③ 履约方式 —— 🔴 有未修的同物异名

| 位置 | 取值 |
|---|---|
| 库 / 后端 | `STORE_PICKUP` `NEIGHBOR_PICKUP` `MERCHANT_DELIVERY` `EXPRESS` |
| shared `FULFILLMENT` | `STORE_PICKUP`✅ `NEIGHBOR_PICKUP`✅ **⚠️`DELIVERY`** `EXPRESS`✅ + `STORE_VERIFY` `APPOINTMENT` `INSTANT`（后端未实现） |
| ops-web | 无声明 |

**`DELIVERY` vs `MERCHANT_DELIVERY` 是与 `PICKUP`/`STORE_PICKUP` 完全同形状的
同物异名，而且还没修。** 上一轮修 PICKUP 时它就在旁边，因为 `FULFILLMENT`
整个在豁免名单里，工具没报、我也没看第二眼。

后果与 PICKUP 那次一模一样：任何一单送货上门的订单，
展示履约方式时都会打出 `fulfillment.MERCHANT_DELIVERY`。
之所以还没被看到，只是因为浏览器实测走的是自提链路。

### ④ 商家状态 —— 分层是对的，缺映射

| 位置 | 取值 |
|---|---|
| 库 `mch_entity.status`（经营） | `ACTIVE` `SUSPENDED` `FROZEN` |
| 库 `mch_entity_apply.status`（审核） | `PENDING` `REVIEWING` `APPROVED` `REJECTED` |
| ops-web | 两个分开声明，与库逐字一致 ✅ |
| shared `MerchantStatus`（B 端合并视图） | `NONE` `APPLYING` `REVIEWING` `REJECTED` `ACTIVE` `SUSPENDED` |

这是六个里**唯一设计本来就正确**的：库里坚持分两张表（驳回一份申请 ≠ 封禁一家店，
操作人、审计口径、可逆性全不同），B 端合并成一个「我现在能不能做生意」。

问题不在取值，在**这个合并没有落成代码**：
- `NONE` / `APPLYING` 是端上派生的词，后端从不下发
- 谁负责把 (apply.status, entity.status) 两元组算成这一个词？**目前没有明确的归属**
- shared 少一个 `FROZEN` —— 商家被冻结时 B 端会落进 `default` 分支

### ⑤ 营销活动 —— 🔴 最严重：三端三套，一个都对不上

| 位置 | 取值 |
|---|---|
| 库 `mkt_campaign.type` | `COUPON` `FULL_CUT` `FLASH` `BUY_GIFT` |
| ops-web `CampaignType` | `FLASH` `SECKILL` `FULL_REDUCE` `GIFT` `NEWCOMER` |
| shared `PROMOTION_TYPE` | `BUY_N_GET_M` |

逐个对：

| 概念 | 库 | ops-web | shared |
|---|---|---|---|
| 限时折扣 | `FLASH` | `FLASH` ✅ | — |
| 满减 | `FULL_CUT` | ⚠️`FULL_REDUCE` | — |
| 买赠 | `BUY_GIFT` | ⚠️`GIFT` | ⚠️`BUY_N_GET_M` |
| 优惠券 | `COUPON` | ❌ 缺 | — |
| 秒杀 / 新人 | ❌ 无 | `SECKILL` `NEWCOMER` | — |

**同一个「买赠」有三个名字。** 三端各自命名、各自只跑自己的 mock，
所以三套并存至今没有任何一层测试报过警。

### ⑥ 自提点类型 —— 值全对，但结构没沉淀

| 位置 | 取值 |
|---|---|
| 库 `cmt_pickup_point.type` | `STORE` `NEIGHBOR` `PLATFORM` |
| ops-web `PickupType` | 逐字一致 ✅ |
| shared | 逐字一致 ✅，但**内联**在 `PickupPoint.type` 的字面量里，无具名类型 |

今天没有 bug。但因为它不是一个具名导出，`check-enums` 扫不到它，
端上各处写的是裸字符串——**这是下一个「同物异名」的温床**，
和 `CATEGORY_TYPE` 出事前的状态完全一样。

## 2. 分类：三种形状，三种治法

梳理完最有价值的产出是这个——六个问题不是六件事，是**三种形状**：

| 形状 | 是什么 | 谁中招 | 能不能自动抓 |
|---|---|---|---|
| **A 同物异名** | 两边都有词，指同一个东西，词不同 | ③履约 ⑤营销 | ❌ 现有工具原理上抓不到 |
| **B 一物多态** | 一个概念在不同层**本就该有不同表示** | ①订单状态 ④商家状态 | ❌ 但可以要求映射函数存在 |
| **C 无主** | 值碰巧对了，但没有单一声明处 | ②五品类键名 ⑥自提点 | ⚠️ 可以要求「必须具名」 |

**治法各不相同，不能一刀切统一：**

- **A 必须消灭** —— 直接把端上的值改成库里的值（键名可以保留本地叫法）。
  已验证过的手法：改**值**不改键，i18n 词条与 mock 字面量一并跟上。
- **B 不能统一，要显式化** —— 强行统一反而会毁掉分层
  （订单存储态合进展示态，就没法表达「三种履约一视同仁」；
  商家状态合并，驳回申请和封禁店铺就共用取值）。
  正确做法是**让映射成为一段有名字、有测试的代码**，像 `OrderStatusView` 那样。
- **C 要收口** —— 每个枚举必须有且只有一个具名声明处，禁止裸字面量。

## 3. 定名规则（新增，写进 CLAUDE.md）

1. **库是唯一真源。** wire 上传输的值 = 列注释里写的值。有歧义时以 DDL 注释为准。
2. **端上常量：键名随意，值必须逐字等于库。** 键是代码里的叫法，值是契约。
3. **一个概念一个声明处。** 禁止在 interface 里内联 `"A" | "B"` 字面量。
4. **跨层的表示差异必须走具名映射函数**，不得靠调用方自己 `switch`。
5. **后端未实现的取值不写进端上契约。** 要么去实现，要么删掉——
   留着就是「按它筛必然是空列表」。

## 4. 执行计划

按「**现在正在造成后果**」而不是「工作量」排序。

### 阶段一 · 止血（A 类，正在坏）

| # | 事项 | 改动 |
|---|---|---|
| 1.1 | `FULFILLMENT.DELIVERY` → `"MERCHANT_DELIVERY"` | shared 常量值 + c/b 两端 i18n 词条键 + 两处 mock 字面量 |
| 1.2 | 删 `FULFILLMENT` 里后端未实现的 `STORE_VERIFY`/`APPOINTMENT`/`INSTANT` | 或保留但移出 wire 契约，标注为「二期」 |
| 1.3 | shared `OrderStatus` 删 `REFUNDING` | 售后状态归 `AfterSaleStatus`，两者并存不互斥 |
| 1.4 | 营销三套词统一到库口径 | ops-web `FULL_REDUCE`→`FULL_CUT`、`GIFT`→`BUY_GIFT`、补 `COUPON`；`SECKILL`/`NEWCOMER` 后端没有→删或排期；shared `BUY_N_GET_M`→`BUY_GIFT` |

**1.4 需要一次业务确认**：`SECKILL` 与 `FLASH` 是不是同一件事？
`NEWCOMER` 是活动类型还是券的适用条件？我倾向后者——
但这属于「改错了会影响钱」，按上次 finance 的处理方式，先只读对账、不动代码。

### 阶段二 · 收口（C 类，防复发）

| # | 事项 |
|---|---|
| 2.1 | shared 新增具名 `PICKUP_POINT_TYPE` 常量，替换所有裸字面量 |
| 2.2 | `CATEGORY_TYPE.GOODS` 键改名 `NORMAL`，与值一致 |
| 2.3 | 定义 `template ↔ type` 的对应关系并落成代码（`STANDARD↔NORMAL`、`VOUCHER↔CARD`） |

### 阶段三 · 显式化（B 类）

| # | 事项 |
|---|---|
| 3.1 | shared 补 `FROZEN`，并新增 `merchantStatusOf(apply, entity)` 映射函数 + 单测 |
| 3.2 | 明确该映射的归属：**建议放后端**，B 端首页直接读一个下发好的 `status`，理由是这个判断跟审计口径绑在一起，不该有两份实现 |

### 阶段四 · 补工具（让 A 类可被自动发现）

现有工具是**全局词汇表**比对，这就是它抓不到 A 的根因。
改成**字段级**比对：

```
对每个 wire 字段 f：
  后端取值域(f) ← DDL 列注释 / Java 常量类
  端上取值域(f) ← 该字段声明的类型
  报错 ← 两个集合不相等（而不是「端上 ⊄ 全局」）
```

差别在于：全局比对时 `DELIVERY` 和 `MERCHANT_DELIVERY` 都在全集里，通过；
字段级比对会发现 `ord_sub_order.fulfillment` 这一个字段上，
两边的集合根本不是同一个，**立刻报出来**。

这需要 DDL 列注释成为结构化真源（大部分已经是了，见 §1 各表）。
估计能覆盖本文六个中的四个（①③⑤⑥），B 类的两个仍需人判断。

---

## 5. 建议的执行顺序

1. **阶段一 1.1–1.3 立刻做** —— 三条都是「现在就在坏，只是没人点开那一页」，
   改动小、有先例手法、回归可验证。
2. **1.4 先出对账报告不动代码** —— 营销涉及金额口径。
3. **阶段四先于阶段二三** —— 有了字段级工具，二三阶段的改动才有验证手段，
   否则又是「改完看着对，等下次浏览器实测再说」。
4. 阶段二、三收尾。

每阶段结束跑全量回归（单元+集成 326 · E2E-2 三旅程 · shared 146 · ops-web 559），
并在浏览器里实测受影响的那一页——**这六个问题没有一个是被测试发现的，
全部是被浏览器发现的**，这个事实本身就是验收方式的一部分。
