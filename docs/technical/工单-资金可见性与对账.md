# 第 1 步　运营端出款入口（应付 + 进项票 + 销项开票）

**前置**：无。**后端 10 个端点全部现成**，这一步是纯前端。

## 为什么排第一

这是今天**唯一真的能把钱付出去的路**（第三方走分账，而分账网关是桩），
而运营端一个入口都没有 —— 只能靠人直接调接口。
投入产出比是整张单子里最高的：零后端改动，接通一条已经在跑的资金链路。

## 怎么改

三个页签的形态照搬 `/finance` 已有的那几个（`fee-rule-tab.tsx` 最接近）。

**应付账款页**要能完成一整条：列表 → 确认对账 → 收票 → 标记已付。
其中「标记已付」要填**网银流水号**（`payment_ref`）——
后端那道闸是「票到付款」，没有票或没标无票供应商的付不了。

⚠️ **运营端菜单不是 `nav.ts` 说了算**：标签、分组、可见性都来自
`sys_function_point` / `sys_role_point`。只改 `nav.ts` 的话本地 mock 看得见，
**接上真实后端就没有**。生成方式见 V251 的表头注释（跑 `ops-web/scripts/gen-perm-seed.mjs`，
从输出里逐字取出本次新增的行；**既有行一行不动、序号插空位**）。

# 第 4 步　`SPLIT` 语义拆分（**本单风险最高**）

**前置**：无。**但它改的是既有终态的语义**，读取点要扫干净。

## 为什么

`SPLIT` 今天**同时表示「指令已发出」与「资金已划转」**，而底下是
`StubSplitGateway` —— 账面显示已分账，一分钱没动。

## 动哪些文件

```
V253/V254__split_confirmed.sql          stl_bill.split_confirmed_at
StlBill.java                            加 SPLIT_CONFIRMED
SettleServiceImpl.executeSplit          落 SPLIT（已发出），不再是终态
SettleServiceImpl                       新增 confirmSplit(settleNo, ref) —— 只能由回执调
StubSplitGateway                        明确返回「已受理未确认」
ops-web / b-app                         状态措辞与筛选项
```

## 怎么改

**桩必须永远不进 `SPLIT_CONFIRMED`。** 那一步只能由通道回执产生 ——
与提现表 `APPROVED → PAID` 刻意不给人工入口是同一条规矩：
让人手动做平，之后对账差额永远说不清是通道慢了还是有人点早了。

**已确认的读取点**（靠 grep 找的，可能有漏）：
`executeSplit` 的幂等判断、`reverseSplit`、ops 结算列表筛选、b-app 结算页。

## 怎么验（**本步必须做**）

```bash
mvn -o -f backend/pom.xml -pl shop-app -am test \
  -Dtest='M7SettleFlowTest,OfflineSettleFlowTest,OpsSettleQueryFlowTest,PointsSubsidyFlowTest'
```

1. ★★★ 跑完 `executeSplit`，状态是 `SPLIT` 而**不是** `SPLIT_CONFIRMED`
2. `OFFLINE_SETTLED` 不受影响（它本来就不进分账）
3. 回归**不新增失败**

### 完成判据

四个类全绿 + 回归零新增；桩单永远停在 `SPLIT`。

# 第 5 步　B 端收入三屏

**前置**：第 4 步（状态拆分）。

## 动哪些文件

```
BizSettleController          加「按状态汇总」的接口（四个数）
b-app/src/pages/income/index.vue      新建（原型 S07）
b-app/src/pages/settle/index.vue      措辞：已到账 / 已发起等确认 / 待结算 / 当面收款

```

## 怎么改

**四个数是四种状态，不是四个口袋。** 今天结算页只显示一个「商家实得」，
读起来像已到手 —— 商家拿它对银行流水对不上就找客服，而客服看到的状态也只有一个。

措辞不是文案问题：`SPLIT` → 「已发起，等通道确认」，不是「已结算」。

### 完成判据

四个数加起来等于结算单总额（立用例钉住）；`OFFLINE_SETTLED` 显示「无需结算」。

# 第 6 步　四轴对账

**前置**：第 4 步（分账轴要靠 `split_confirmed_at` 判「发出很久没确认」）。

## 分两次提交

**6a 纯搬家**：抽 `ReconAxis` 接口，把现有收款轴迁进去，**不改任何行为**。
单独一次提交 —— 混在一起的话，行为变化与结构变化分不开，出问题不知道回滚哪个。

**6b 三条新轴**：分账轴 / 出款轴 / 积分池轴。

## 动哪些文件

```
shop-settle/service/recon/ReconAxis.java            scan() + coverage()
shop-settle/service/recon/{Split,Payout,PointsPool}ReconAxis.java
V25x__recon_diff_axis.sql                           stl_recon_diff.axis
ReconServiceImpl                                    收敛成「跑所有轴」
```

## 怎么改

⚠️ **线下单必须排除在通道类对账之外。** `OFFLINE_SETTLED` 的钱从没进过通道，
混进去就是永久无解差异 —— 而无解差异一多，对账页就没人看了，真差异跟着被埋掉。
**判据用状态不用 `pay_channel`**：后者是本批才开始写的，存量行为 null。

每条轴都要给 `coverage()`，照第 2 步那条上页面。

## 怎么验

| 场景 | 判据 |
|---|---|
| ★★★ 线下单不进通道对账 | `OFFLINE_SETTLED` 跑四轴，一条差异都不产生 |
| ★★ 分账轴逮得住「发出很久没确认」 | 造 `split_at` 在 N 小时前的 `SPLIT` 单 → 出一条差异 |
| ★★ 幂等 | 连跑两轮，差异不翻倍 |
| ★★ 每条轴说得清覆盖范围 | `coverage()` 非空且含「查不了什么」 |

**每条都要消融**：撤掉被测那行确认它变红，**且红在预期那条上**。
本仓库在这上面栽过三次假绿。

### 完成判据

四条轴各自可跑；线下单零差异；回归零新增。
