## T1 · 安全库存改得了 —— `INV-C4`

**为什么值**：两张表的列、判据、界面标红**全都在**，只差一个写入口 ——
`safety_stock` 默认 0 = 不预警，于是「缺货」这一档今天只在 `available <= 0` 时才亮。
也就是说**预警功能整个是哑的**，而库存页的第一栏、工作台那张卡的第二个数都指着它。
这是全清单里「已完成度最高、离可用最近」的一条。

| 层 | 动什么 |
|---|---|
| 端点 | 新增 `PUT /biz/inventory/items/{itemId}/safety-stock`，判 `biz:stock`。<br>入参 `{ qty, locationId? }` —— **`locationId` 为空写 `inv_item.safety_stock`（默认值），非空写 `inv_stock_balance.safety_stock`（本库位覆盖）**。两张表的列都已存在 |
| VO | `ItemDetailVO` **今天不下发 `safetyStock`**（`BalanceVO` 下发了）。要补，否则详情页显示不出当前值，只能写不能读 |
| 界面 | 库存明细页「安全库存」一行：显示当前值 + 点击改。`0` 显示成「不预警」而不是「0」 |
| 落点 | `BizStockController` · `InventoryVOs.ItemDetailVO` · `StockQueryServiceImpl` · `b-app/src/pages/stock-detail/index.vue` |

**判据**（缺一条不算做完）：

1. 设一件货安全库存 = 5，实存 3 → **库存页那件货出现在「缺货」里**，且总览的缺货数 +1。
2. 设回 0 → 它从「缺货」里消失。**两向都要验** —— 只验设上不验设回，撤不掉的预警比没有更烦。
3. 库位覆盖：主体设 5、某库位设 20，切到那个库位看到 20。**不覆盖时读回主体值**。
4. 改完刷新详情页**读得回来**（这一条专门防「只写不读」：加了列只改写入，界面看不出区别、闸门全绿）。

**不做**：按历史销量自动猜一个默认值。决策记录已定「全 0」——猜错的预警比没有预警更烦。

### ⛔ 2026-09-02 开工前查实：**这条不要做，前提不成立**

原判据第一条是「运营端加一个单位 → B 端进货页的单位选择器里当场能挑到」。
去看那个选择器，**它不存在**；再往下查，`inv_uom` 是一张**没有任何代码读写**的表：

| 层 | 实际 |
|---|---|
| 表 / 实体 / Mapper | ✅ 都在（`inv_uom` / `InvUom` / `UomMapper`），种了 8 条 |
| 后端读它的地方 | **一处都没有**。`InboundServiceImpl.uomOf` 取的是 `inv_item.base_uom`，取不到就写死 `"PIECE"` |
| `base_uom` 从哪来 | 平台商品的 `sale_unit`，经 ACL 投影进来 —— **与这张字典无关** |
| 端上怎么显示 | `uomLabel()` 查 i18n 里写死的 `stock.uom` 映射表；认不得的原样显示 |

所以照原方案做出来的是**一个改了不影响任何东西的维护页**：运营加一个单位，
B 端挑不到（没有选择器）、后端不认（不读这张表）、界面不显示（映射表里没有）。
**而它看上去是能用的** —— 这比没有更糟。

**要先定的是一个产品问题**：单位的真源到底是谁？

- **是 `inv_uom`** → 那 `uomOf`、`base_uom` 的投影、端上那张写死的映射表都要改成指向它，
  这是一件比「加个字典页」大得多的事，且要想清楚与平台 `sale_unit` 的关系；
- **不是它** → 那张表和 `InvUom` / `UomMapper` 应当标成留位或删掉，
  需求里的 `INV-P7`（原 O-6）随之撤销 —— 留着一张没人读的表，
  下一个人还会再提一次「单位字典没做」。

**倾向后者**：单位跟着商品走（平台 `sale_unit`）在今天是通的，而字典那条路要动的是
投影链路。在没有「商家要自定义单位」这个真实诉求之前，不值得为它改一条已经在跑的链。

## T3 · 预留积压监控 —— `INV-P5`

**为什么值**：`HELD` 超过 `expires_at` 还没回收，意味着 `ReservationExpiryJob` **出了问题**——
预留不回收 = 那批货永远占着，`available` 一路降到 0 而实存没动，商家看到「有货卖不出去」。

> ⚠️ **开工第一步不是写代码，是确认那个任务在不在跑。**
>
> **上线手册里「四个任务全挂 `@Profile("worker")`」那句今天是错的**（当场查过）：
> 三个任务实际挂的是 `@ConditionalOnProperty(name = "shop.job.enabled", havingValue = "true")`
> ＋ `@ConditionalOnInventory`。
>
> 关键在于 **`shop.job.enabled` 在 `application.yml` 里一个字都没有** ——
> `havingValue="true"` 不带 `matchIfMissing`，**取不到值就是不装这个 Bean**。
> 也就是说它由部署环境决定（`deploy/tencent/README.md` 里那个独立调度实例
> `/opt/ai-shop-job/job.env`），而**默认是关的**。
>
> 关着的那一半才是生产常态 —— 这正是「默认关闭的那一半没人测」那类缺陷的形状。
> 所以先量两个数，再决定这条工单怎么做：
>
> ```
> ① 线上 job 实例的 env 里有没有 SHOP_JOB_ENABLED=true
> ② inv_reservation 里 status='HELD' AND expires_at < NOW() 有几行
> ```
>
> ②不为零就说明回收确实没在跑。**那时这条监控做出来第一天就会满屏红 ——
> 那不是监控坏了，是它第一次说了实话**，而真正要修的是①。
>
> 顺带：`InvOutboxDispatchJob` 与它同一个开关。**双写靠它投递** ——
> 开关没开的话，`stock-authority=DUAL` 写进 outbox 的那些行没有人消费，
> 而线上 0 订单让这件事至今无从暴露。

### 2026-09-02 实测：三个任务在生产**一次都没跑过**

按上面那两步查下来，结论比预想的严重，而且**不是开关的问题**：

```
env（/opt/ai-shop/shop-app.env）  SHOP_JOB_ENABLED=true · SHOP_INVENTORY_ENABLED=true · DUAL
inv_outbox                        212 行，全部 PENDING，SENT 0 行
inv_outbox.retry_count            max = 0        ← 连投都没投过，不是投失败
事件跨度                          2026-08-27 18:11 ~ 2026-08-30 22:17
inv_reservation                   0 行（所以「预留积压」这个数今天恒等于 0）
```

**`retry_count` 全是 0 是判据**：投递失败会让它涨，涨不动说明**调度从来没触发过**。

根因是两道门，各自看都合理：

| 门 | 情况 |
|---|---|
| `@ConditionalOnProperty("shop.job.enabled")` | ✅ 开着 —— 所以 Bean 装出来了 |
| `@EnableScheduling` | ❌ 它挂 `@Profile("worker")`（`SchedulingConfig`），**生产不带 worker** |
| 独立调度器的注册表 | ❌ `job_definition` 里有 `inv-recon`，**没有** `inv-outbox` / `inv-reservation-expiry` / `inv-snapshot` |

也就是说：Bean 在、`@Scheduled` 注解在，**但没有任何东西会读那个注解**；
而独立调度器那条路要靠 `JobDeclaration` bean 注册，本域三个任务**一个都没声明**。
`InventoryReconJob` 声明了，所以它在表里 —— **同一个坑修过一次，剩下三个被落下了**。

**今天的影响分级**（不是「都很急」）：

| 任务 | 今天 | 真有生意之后 |
|---|---|---|
| `ReservationExpiryJob` | 无害（0 预留） | **最危险**：未付款订单的预留永不回收，那批货永久占着，商家看到「有货卖不出去」 |
| `InvOutboxDispatchJob` | 212 条积压。平台侧**没有 `INVENTORY` 聚合的消费者**，所以补投也没人接 —— 低危 | 切 G3 之后它是主链路 |
| `InvDailySnapshotJob` | 无害（报表回退扫流水，设计里认了） | 量上来才需要 |

**所以这条工单的内容变了**：原本是「加一个预留积压监控页」，
现在第一件事是**让这三个任务真的会被触发**。

### ✅ 已修（`0e0af7e7`，**尚未部署**）

- 三个任务的任务体抽成 `dispatchOnce` / `expireOnce` / `buildYesterday`，
  两条触发路径共用一份；`InventoryJobHandlers`（在 `shop-app/invbridge`）补上
  `JobHandler` + `JobDeclaration`。**没往 `shop-inventory` 里塞 `shop-job-api` 依赖** ——
  那个模块要能独立交付，`inv-recon` 当初就是为这个原因放在 invbridge 的。
- 新立守卫 `ScheduledJobConventionTest.everyScheduledJobIsDeclared`：
  每个 `@SchedulerLock(name=…)` 都要有同名的 `JobDeclaration`。
  **它当场逮到第四个 —— 平台自己的 `outbox-dispatch`**，同样两条路都不通。
  今天没出事只因为 `sys_outbox` 还是空的，而站内信、履约通知都走那条链；
  更要紧的是**进销存的事件正是投进那张表**，只修上游等于把积压挪个地方。
  一并补了 `PlatformOutboxJobHandler`。
- 101 个相关测试全绿。

**部署时要知道的一件事**：上线后 `inv-outbox-dispatch` 会把积压的 212 条一次投出，
落进 `sys_outbox`。平台侧今天**没有 `INVENTORY` 聚合的消费者**，所以不会有下游动作 ——
但那批行会在 `sys_outbox` 里出现，看到时别当成异常。

### 还没做：监控页

监控页仍然要做，但它的价值排在后面：**监控一个从来没启动过的任务，报出来的是同一件事**。
等任务真的在跑之后再加，那时它报的红才有意义。

| 层 | 动什么 |
|---|---|
| 端点 | `GET /ops/inventory/reservations?overdue=true` —— 只读，判 `inventory:stock:read` |
| 界面 | `/orders?tab=exception` 的一个筛选项。**不新建页面** —— 回收任务出问题是异常单的一种，不是库存问题 |
| 落点 | `OpsInventoryController` · `ops-web/app/orders/` |

**判据**：造一条 `expires_at` 已过、`status=HELD` 的预留 → 它出现在异常单里；
跑一次回收任务 → 它消失。**两向都验**。

## T4 · 扫码找货 —— `INV-W12` · **1–3 已做（`09a33223`，未部署）· 第 4 条待真机**

方案：[录入效率 · 扫码与拍照](design/进销存-录入效率-扫码与拍照.md)（**方向已定 · 待评审**）。

四件事，[原方案 §四](design/进销存-录入效率-扫码与拍照.md)：

| # | 内容 |
|---|---|
| 1 | `GET /biz/inventory/items/by-barcode?code=` —— 三段返回：命中货品 / 命中标准库 / 未知 |
| 2 | `POST /biz/goods/{skuNo}/barcode` —— 绑码，**幂等**，同一商家内条码唯一 |
| 3 | 挑货弹层加扫码入口（进货 / 报损 / 盘点**三处共用同一个组件**） |
| 4 | 盘点**连续扫码模式**：扫中即加、不退出 |

**开工前必须知道的三件**：

- **第一天命中率必然是 0**：`prd_sku.barcode` **0/396**、`prd_goods.std_no` **0/380**。
  已拍板不补录 —— 数据要被用出来。**上线指标看「绑定数的增长」，不看扫码成功率**。
- **扫码永远只覆盖预包装**：生鲜、现做熟食、服务本来就没有条码。当加速器成立，当主路不成立。
- **不做「扫码直接过账」**：扫错一件和数错一件的代价不一样，前者商家不会发现。

**判据**：

1. **绑码要验第二次**：扫未知码 → 绑 → **再扫一次必须直接命中**。只验第一次等于没验绑上。
2. 三条分支各走一次（命中货品 / 命中标准库 / 完全未知）。只测命中那条，另外两条上线才发现。
3. 连续模式验「扫错能撤」：连扫十件，撤掉第三件，其余九件还在。
4. **在真机上验**：扫码要用摄像头，mock 给不了。

### 2026-09-02 做到哪

| # | 内容 | 状态 |
|---|---|---|

| 2 | `POST /biz/sku-identity/barcode` | ✅ 幂等、本店内唯一；判 `biz:goods`（改的是商品那一列） |

**标准库那一段（「标准库里是《XX》」）也没做**：它要读 `prd_spu_std`，
而那是平台的表、进销存是独立库读不到。落点在 `shop-app` 的桥接层
（与健康度、对差同一处），这一轮不做。

**顺带修掉一处既有缺陷**：身份三列的 CSV 批量导入**不发投影事件** ——
三列写进 `prd_sku` 而进销存的 `inv_item_ref` / `base_uom` 一个字没变，

投递任务没开的话事件堆着，「第二次扫直接命中」不成立 —— 两件事是连着的。

**验到哪**：H5 上验了入口在、扫码失败时静默不炸。**三段逻辑要真机**（要摄像头）。

`SALE` 那道闸一个字没动。

但报表侧没有按 `target_no` 聚合的那一栏 —— 那是下一步，且线上 0 出库单，

# C 线 · 卡住的，一行代码都不要写

## T6 · 分档 `FREE`/`PRO`/`CHAIN` —— `INV-P6` ⛔

**卡在哪**：这是**产品决策不是工作量**。今天 32 个商家端点只判权限码，
进货、报表、导出、建仓、调拨对所有商家免费开着。加档之前要有答案的三条：

1. 已经在用这些功能的商家，加档之后是**关掉**还是**继承**？关掉等于线上功能倒退。
2. 判在哪一层：端点（漏一个就绕过去）还是 Port（要每个 Service 都认识档位）？
3. `FREE` 里「变动明细与盘点不收费」要保住 ——
   流水是平台自己的欠债（超卖追责、对账证据），藏在付费墙后面等于平台自己也没有证据。

**动手前的连带工作**：三份设计文档里每一屏都标了档位，那些标注今天是纸面上的。
决定不做分档的话，**那些标注要一起删掉** —— 留着比没有更糟，读的人会以为它生效了。

## T8 · 三条链的生产验证 —— `INV-M2/M3/M4` ⛔

**卡在哪**：**生产订单总数为 0**。销售出库、预留、退货入库三条链一次都没跑过，
