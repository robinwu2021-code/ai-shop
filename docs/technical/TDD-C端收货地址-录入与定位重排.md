# TDD · C 端收货地址：录入与定位重排

状态：**A–G 七批全部落地（2026-09-18）** · 创建 2026-09-18 · 档位 2（跨端 + 动了库表与端点）
关联：[TDD-C端位置选择-地址取代自提点](TDD-C端位置选择-地址取代自提点.md)（M1–M6 已落地，本方案接在它后面）
参照：美团外卖的地址录入（下文凡写「美团式」都指它那套「一个门 + 城市行 + 地点搜索页」的形状）

---

## L1 定位

**一句话：今天「填地址」这件事有两条并行的路、两个关于「我在哪」的答案，
而买家要在没有依据的情况下先替我们选一条。**

三件事凑在一起：

1. **两条兜底路并排**（「地图选点」「手动填写」）。它们的产出不一样 ——
   一条带坐标、一条不带 —— 而这个差别决定了商家自送半径判不判得了、骑手导航打不打得开，
   页面上**看不出任何区别**。把这个选择丢给买家，等于让他替我们决定一件他看不见的事。
2. **同一屏两个位置答案**。收货地址页顶上写「桂澜新村」（来自几天前绑的归属），
   选择地点页写「使用当前位置」（这一次的定位，还没回来）。实测截图两页并排，
   说的不是同一件事。
3. **只装得下深圳**。表单假设「省市区 + 高德能搜到的地点」，
   国内其他城市能填但没有城市这一层（靠定位漂到哪算哪），海外**填不了**：
   没有国家/地区、没有邮编、手机号写死 11 位数字。

## L2 结构

### 现状实测（2026-09-18，线上 + 小程序模拟器）

| 事实 | 判据 |
|---|---|
| `/mp/community/nearby` 要 **8.8 秒**，与返回条数无关（27 条 / 6 条同为 8.7s） | 线上 `curl -w time_total`，两个坐标各一次 |
| 根因：先把**全部 OPEN 聚落**（2783 条）读出来，再拿 `origin_code` 去 62 万行区划表批量反查官方名/城乡标识，**最后才按半径过滤** | `CommunityServiceImpl#nearby` |
| 于是选择地点页首屏是空壳：「附近」整块还没回来，「当前位置」只有一行占位文字 | 小程序截图 `mp-pick.png` |
| 收货地址页空态给的是**整块卡 + 整条实心大按钮**（存为收货地址），底部还有一条同样大的「新增地址」 | 小程序截图 `mp-list.png` |
| 「重新定位」只有选择地点页有；收货地址页、首页顶栏都没有 | `pages/address/index.vue` 无 `locate` 入口 |
| 收货地址页的地名来自**已持久化的归属**（`shcr_community`），不是本次定位 | storage 实测：`shcr_community.name = 桂澜新村` |
| 表单是**弹层**（`sh-sheet`），装 7 个字段 + 3 条提示 | `pages/address/index.vue` |
| `usr_address` 没有国家/地区、没有邮编；手机号输入写死 `type=number maxlength=11` | `V1__baseline.sql` + 后续两条 ALTER |
| 高德 POI 搜索与 `wx.chooseLocation` **只覆盖中国大陆** | 端口实现 + 高德服务条款 |

**数据层大体是对的**（坐标可空、`region` 是整串、`house_no` 独立），
问题集中在「录入这一段的形状」与「定位这件事有几个真源」。

### 目标模型

```
            ┌─ 国家/地区 ────────────────────────────┐
            │  中国大陆            │   其他国家/地区   │
            ├──────────────────────┼──────────────────┤
所在城市    │  城市选择器（可切）  │   City / State   │
地点        │  ▶ 选择地点（一个门）│   Address line   │
            │     搜索 / 当前位置  │   （纯文本）      │
            │     / 附近 / 地图选点│                  │
门牌        │  楼号-单元-室        │   Apt / Suite    │
            │                      │   邮编 Postal     │
联系人      │  姓名 + 手机(+86)    │   姓名 + 区号手机 │
            └──────────────────────┴──────────────────┘
                        │
                        ▼  有坐标才写 lat/lng；没有就留空并说一句
                   一条收货地址
```

三条不变量：

- **坐标是能力不是义务**。有坐标 → 自送半径、导航、聚落归属都成立；
  没有 → 照存照下单，但**必须在界面上说出来**（已有口径，不改）。
- **「我在哪」只有一个真源**：`location` store 的 `here`。
  首页顶栏、收货地址页、选择地点页读的是同一个对象，「重新定位」是同一个动作。
- **录入只有一个门**：地点这一行点进去就是选择地点页。
  地图选点、手动填写都是那一页**里面**的次级动作，不在表单上并排摆着。

## L3 详情

### M1 · 后端：`nearby` 先筛后富化 —— **已落地（2026-09-18）**

原来的顺序是「全读 → 富化 → 过滤」，富化的代价乘在 2783 条上。改成先筛后富化。

**没有下推成 SQL 外接矩形**（这是我初稿里写错的一条）：`withinRadius` 判的是
每个聚落**自己的** `fence_radius`，不是全局那一个值。按全局半径框矩形会把
宽围栏的聚落误删，而那种删除是静默的。2783 行本身读起来不慢，贵的是富化 ——
把过滤提前就够了。表再大一个量级时再谈下推，那时要框的是 `max(fence_radius)`。

**判据不能是返回结果**：这次改动**不改变任何输出**，改前改后返回的聚落
一模一样、顺序也一样。拿结果当判据的话，把修复整个撤掉它照样绿。
所以量的是**传进富化那一步的东西** —— 半径外那条的 `origin_code`
不许出现在 `regionNames` 收到的清单里，同时断言半径内那条**在**清单里
（只验前者的话，一个根本不调富化的实现也能过）。

`NearbyFiltersBeforeEnrichTest` · 消融验证过：把过滤挪回富化后面当场变红。

### M2 · 定位口径统一到一处 + 「重新定位」

`location` store 增加一个**本次会话的位置**（与「归属」分开）：

```ts
here: {
  coords: { lat, lng } | null,
  coarse: boolean,          // 区级模糊，不许显示距离
  name: string,             // 「桂澜新村」，取不到就空，不编
  at: number,               // 取到的时刻
} | null
```

- `ensureHere()`：没有或过期（> 5 分钟）就取一次；有就直接给。
- `relocate()`：**强制**重取，清掉缓存与依赖它的那几段（附近、归属候选）。
- 三处入口共用 `relocate()`：首页顶栏地名、收货地址页当前位置行、选择地点页。

**为什么必须收到一处**：今天首页/地址页读归属、选择页读本次定位，
两个数在同一屏上同时出现过，而它们不同时**没有任何提示**。

**判据**：收货地址页与选择地点页在同一时刻显示同一个地名；
点任一处的「重新定位」，两处同时变。

### M3 · 收货地址页重排（美团式）

```
┌────────────────────────────────┐
│ 当前位置 · 桂澜新村   重新定位  │  ← 一行，不是一块
│ 就近收货                存为地址│
├────────────────────────────────┤
│ 张三  138****0000   [家] [默认] │
│ 广东省深圳市龙华区…  3 栋 501   │
│                   设为默认 编辑 删除│
└────────────────────────────────┘
          ⋯
┌────────────────────────────────┐
│          新增收货地址           │  ← 底部唯一的实心按钮
└────────────────────────────────┘
```

- **「存为收货地址」不再是整块实心大按钮**。它不是这一页的主动作 ——
  这一页的主动作是「挑一条地址去下单」。降为当前位置行右侧的文字动作。
- 空态时当前位置行**保留**（不再换成整块卡），底部按钮仍是唯一的实心件。
- 「重新定位」放在当前位置行右上，与地名同行。

**表单从弹层改为整页**（`pages/address-edit/index`）。
弹层在小程序上高度受限，7 个字段 + 3 条提示条塞进去看不到头。

```
所在城市      深圳市                        ›

              广东省深圳市龙华区观澜街道…

标签          [家] [公司] [学校] ＋
                     ┌──────────┐
                     │   保存   │
                     └──────────┘
```

**「地图选点」与「手动填写」从表单上消失**，合进选择地点页：

```
选择地点                          [地图选点]   ← 右上次级动作
┌────────────────────────────────┐
│ 🔍 搜索小区 / 写字楼 / 学校      │
├────────────────────────────────┤
│ 当前位置  桂澜新村       重新定位│
│ 首信广场(松元厦地铁站E1口…)  使用│
├────────────────────────────────┤
│ 附近                            │
│ 茜坑老村老围197号          55m  │
│ 围仔小区                   95m  │
│ ⋯（最多 5 条）                  │
│ 更多地点请用「地图选点」         │

        搜不到？手动填写地址        ← 只在搜索无结果 / 海外时出现
```

**这就是第 1 问的答案：合，但不是合成一颗按钮。**
合成一个**入口**（这一页），把「地图选点」降成它的右上角动作、
「手动填写」降成搜不到时才出现的出路。两颗并排的兜底按钮之所以要拆掉，
是因为它们让买家去选一件他看不见后果的事（带不带坐标）。

### M5 · 所在城市可切（国内其他城市）

新增城市选择页 `pages/city-pick/index`：

- **定位城市**置顶（带「重新定位」）；
- **最近使用**（本地存最多 3 个）；
- **热门城市**九宫格；
- **A–Z 索引 + 搜索**，数据来自已有的区划表（市级，`region_code` 4 位）。

选了城市之后，选择地点页的搜索**围着那个城市搜**，不再围着当前定位
（今天 `searchPlacesNearNative` 只围坐标搜，人在深圳给北京的家填地址就搜不到）。

**判据**：人在深圳，切到北京，搜「望京」出来的是北京的望京，不是深圳的同名点。

### M6 · 海外地址

**数据层**（一条迁移）：

```sql
ALTER TABLE usr_address ADD COLUMN country_code CHAR(2) NOT NULL DEFAULT 'CN';
ALTER TABLE usr_address ADD COLUMN postal_code VARCHAR(16) NULL;
ALTER TABLE usr_address ADD COLUMN phone_cc VARCHAR(8) NOT NULL DEFAULT '86';
```

存量行天然是 `CN` / `86`，不需要回填。**加了列要补实体**（三处：实体、VO、写入），
否则那几列永远读出 null。

**表单形态**：`country_code != 'CN'` 时整段换形状 ——

- 关掉：地点搜索、附近、地图选点、省市区拆分（高德不覆盖，
  给一个点了搜不到东西的搜索框比没有更糟）；
- 打开：Address line 1 / line 2、City、State/Province、Postal code；
- 手机号：区号可选，位数校验按国家放宽（不再写死 11 位数字）；
- 坐标必然为空 → 复用已有的「没有坐标」提示口径，不额外发明一句。

**不做的**：海外的行政区划校验、地址格式本地化（日本的番地、英国的 postcode 格式）。
一期只保证**存得下、说得清、寄得出**。

### M7 · 固定地址库 —— **缓存就是它，不是另一层**

**先答一个问题：缓存与「固定地址」是不是一回事？是，一张表。**

`geo_place` 一条 = 「**某个坐标格子叫什么名字，上次核对是什么时候**」。
它同时是三样东西，而这三样本来就该是同一份数据：

| 它是 | 因为 |
|---|---|
| 回答「我在哪」的答案库 | 拿坐标来问，它给名字 |
| 防止频繁调地图的挡板 | 有答案就不出去问 |
| 逐步长大的自有资产 | 问过一次就永远记着，地图挂了也还在 |

做成「缓存」+「固定地址表」两层的话，同一个地方会有两条记录、两个时间戳，
而它们不一致时**没有任何人会发现**。

#### 本地与地图怎么结合：一条链，从不花钱的开始

```
取到坐标 → geohash(精度 8，约 38m×19m)
 │
 ├─① 聚落围栏命中？          cmt_community            用它，不再往下
 │     └ 这是业务对象（围栏 / 商品池 / 开没开通），我们自己维护，没有过期一说
 │
 ├─② 固定地址库有这个格子？   geo_place
 │     ├ verified_at 在 30 天内 →  直接用。**不调地图**
 │     └ 已经超过 30 天       →  **先用它**（不让用户等），再异步回头问一次刷新
 │
 ├─③ 这个格子从没见过        →  同步问一次地图 → 落库 → 用
 │
 ├─④ 地图不可用（没 key / 熔断 / 额度用完）
 │     ├ 有旧的 → 用旧的，标陈旧
 │     └ 没有   → 往下
 │
 └─⑤ 只给区县。**不编地名**
```

两处与直觉不同，都是有意的：

- **超期不阻塞**。用户在等首页，不是在等「这个地名是不是最新的」。
  超期那一行照样先返回，刷新放到后台。
  （我先前那版写的是「超期就同步去问地图」—— 那会让**正好撞上过期的那个人**
  多等三秒，而他什么也没做错。）
- **①永不过期**。聚落是我们自己维护的业务数据，不是从地图上抄来的；
  拿「30 天该核对了」去套它是把两种东西混成一种。

#### 怎么保证不频繁调用：四道，层层收窄

| 道 | 做什么 | 效果 |
|---|---|---|
| 端上 `ensureHere` | 5 分钟内不重复取坐标 | 一个人反复进出首页只算一次 |
| geohash 格子 | 同一栋楼里所有人共用一行 | 一栋写字楼一天几千次 → 一次 |
| `verified_at` 30 天 | 命中就不出去问 | 老地方基本不再花额度 |
| 熔断 + 每日上限 | 连续失败停 60 秒；额度用完停到当天结束 | 坏掉时不是每个请求等 3 秒超时 |

**唯一会同步调用地图的情形是③**：一个我们从没见过的格子。
随着库长大，③ 越来越少 —— 这正是「逐步完善」在数字上的样子。

#### 怎么定期更新：一被动一主动

**被动保鲜（自动）**：命中一条超期的行就异步刷一次。
热点自动保持新鲜，冷门的永远不刷 —— **这是对的**，没人去的地方不值得花额度。

**主动沉淀（运营点一次）**：`hit_count` 过阈值且 `kind=POI` 的行，
升级成 `cmt_community(kind=BUILDING, source=MAP, status=CLOSED)`，
走龙华那 2783 个小区已经跑通的同一条导入路（`importEstates`）。

升级之后它进①，**彻底不再依赖地图** —— 你说的兜底就是这么长出来的：
用得最多的那些地方，我们自己先认识了。

#### 取名要取到建筑，不是小区

今天 `GeoServiceImpl#reverse` 只看 `aois[0]`，于是站在龙华区地域馆里，
拿回来的是那一片的小区名。改成按**具体程度**排：

```
pois[0]（距离 < 50m，建筑/公共设施类）  「龙华区地域馆」
  └→ aois[0]（小区/楼盘）              「桂澜新村」
       └→ streetNumber（街道+门牌）     「观澜大道 155 号」
            └→ formatted_address
```

每一档把**是哪一档**一起返回（`kind`），端上据此决定还要不要再问一层。

#### 表

```sql
CREATE TABLE geo_place (
  geo_key      VARCHAR(16) NOT NULL COMMENT 'geohash 精度 8（约 38m×19m）—— 建筑级够用，同一栋楼反复进入命中同一行',
  lat_e6 INT NOT NULL, lng_e6 INT NOT NULL COMMENT '这个格子里首次落库的那个点',
  name         VARCHAR(128) NOT NULL COMMENT '最具体的那个名字',
  kind         VARCHAR(16)  NOT NULL COMMENT 'POI/AOI/STREET/REGION —— 说清这是哪一档',
  address      VARCHAR(255) NULL,
  region_code  VARCHAR(12)  NULL,
  township     VARCHAR(64)  NULL,
  verified_at  DATETIME     NOT NULL COMMENT '上次核对的时刻；超过 30 天就回头核一次（先用旧的，后台刷）',
  hit_count    INT NOT NULL DEFAULT 0,
  last_hit_at  DATETIME NULL,
  promoted_no  VARCHAR(64)  NULL COMMENT '已升级成聚落的话，指过去；指了就说明这一行不再是唯一答案',
  UNIQUE KEY uk_geo (geo_key),
  KEY idx_promote (kind, hit_count)
);
```

**这是我们自己的地名库，不是「高德结果的缓存」。** 它按坐标匹配，
与谁帮我们认出这个名字无关 —— 今天是高德，明天换谁、或者由运营直接录入，
表的形状与用法都不变。所以**不留第三方的原始返回**：留原文会把这张表
变成「某一家的结果副本」，既多一层授权问题，也会让人以为换厂商时它作废。
它不作废，它是我们的。

**格子大小要量，不能拍**。精度 8 是起点；命中率太低就退到 7（约 153m，
掉到小区级）。上线后看 `hit_count` 分布再定 —— **判据是命中率，不是格子大小**。

### M8 · 搜索也要有本地兜底

地图不可用时，选择地点页的搜索框**不消失**，改搜本地库
（`cmt_community` + `geo_place`）。今天是整段不渲染，等于告诉用户「这儿什么都没有」。

合并时**本地优先、同名去重**：本地那条带着 `communityNo`，选中它才能直接绑聚落；
地图那条只有名字与坐标。

### M9 · 首页顶栏 = **当前定位**（2026-09-18 定）

顶栏回答的是「**我在看哪一带的货**」，不是「送到哪」。

**定这一条的理由**：物流是快递，深圳全市覆盖 —— 快递能送到任何地方，
所以「站在哪儿」与「货最后去哪儿」本来就是两件独立的事。
浏览按位置走、收货按地址走，各管各的，没有冲突。

（我先前建议过「有收货地址时用地址」，理由是怕出现「看得到、买得到、送不到」。
在**纯快递**下这条站不住：看得到的都寄得到。记在这里是为了让下面那道闸有出处。）

**留一道闸**：自提与社区配送这两种履约方式**仍然与聚落绑死**，
那时「在这儿看得到」不等于「能送到你那条地址」。所以：

- 顶栏、商品可见性 → 跟当前定位（本条）；
- **下单时履约方式不是快递** → 校验「地址所属聚落」与「这批货所属聚落」是否一致，
  不一致就当场说明白，不静默放过去。

**判据**：走到另一个区，顶栏当场跟着换；同一批货用快递下单不拦，
改成自提且地址不在那个聚落时拦下并说清楚。

### M10 · 当前位置行：重新定位 + 一键存为地址

（M2/M3 已经画了形状，这里只钉行为）

- **重新定位**：强制重取坐标 → 重走 M7 的五级 → 顶栏、地址页、选择页同时变。
- **存为收货地址**：带着已经解析好的 `name / address / region_code / 坐标`

  M7 之后省市区的拆分在后端只有一处，端上不必再借那一页的逻辑。

### M11 · 地址交互收敛成一套 —— **今天同一个动作有两份实现**

先把实测的四处不一致摆出来（2026-09-18 逐页读源码）：

| 不一致 | 现状 | 出处 |
|---|---|---|
| **「存为收货地址」有两份实现、两条路** | 收货地址页 → 先跳选择地点页（`?useHere=1`）再交回来；下单页 → 直接跳新建并带坐标预填（`?new=1&latE6=…`） | `address/index.vue` vs `order-confirm/index.vue` |
| **「我在哪」有四个取法** | 首页拼 `community` + `nearestDistanceM` + `coarseRegion`；我的页读 `location.label`；收货地址页读 `community.community?.name`；选择地点页读本次 resolve | 四个文件各一份 |
| **地址卡有两种形态** | 下单页是「一张卡，点一下换」；收货地址页是「列表行 + 每条五个动作」。没有共用件 | 两处各写各的 |
| **新建地址有两个入口形态** | 收货地址页里是弹层；下单页靠 `?new=1` 去把那个弹层打开 | 同上 |

**这不是「风格不统一」，是同一个动作在不同地方做不同的事。**
「存为收货地址」那两条路产出就不一样：一条绕选点页（会多问一次地点），
一条直接预填（不问）。用户在两个地方点同一个字，得到两种流程。

收敛成三件共用件 + 一个真源：

```
components/biz/
  biz-place-bar.vue     当前位置行：地名 + 重新定位 + 存为地址
                        用在 → 首页顶栏 / 收货地址页 / 下单页 / 选择地点页
  biz-address-card.vue  一条地址长什么样（姓名 电话 标签 默认 地址 缺坐标提示）
                        用在 → 收货地址页（带动作行）/ 下单页（只读）/ 选择页
  biz-address-form.vue  新建/编辑的那张表（M4 的整页壳子里放它）

stores/location.ts
  here                  「我在哪」的唯一真源（M2）
  relocate()            唯一的重新定位
  saveHereAsAddress()   唯一的「存为收货地址」，只有一条路由
```

三条规矩：

- **同一个字 = 同一件事**。「存为地址」在哪儿点都走 `saveHereAsAddress()`，
  统一成**带坐标直接进新建页预填**（下单页那条）——
  它少问一次，而地点已经解析好了，再过一遍选点页是多余的一步。
- **地名只有一个来源**。四个页面都读 `location.here.place.name`，
  没有第二种拼法。今天那四种拼法迟早给出四个答案，而它们不同时界面上没有提示。
- **地址卡的差别只在「带不带动作」**，不在长相。`biz-address-card` 收一个
  `actions` 开关，不是两个组件。

**判据**：`grep` 全端，`saveHereAsAddress` 只有一处定义；
地名的取法只有 `location.here.place.name` 一处；
`biz-address-card` 在三处被引用而没有第二份同形状的卡片标记。

### `place` 的形状（端上唯一要读的东西）

```ts
type Place = {
  name: string;               // 「龙华区地域馆」；解析不出来就空串，**不编**
  address: string;            // 「深圳市龙华区观澜大道 155 号」
  kind: "POI" | "AOI" | "COMMUNITY" | "STREET" | "REGION";
  source: "COMMUNITY" | "PLACE_DB" | "MAP" | "PLACE_DB_STALE";
  stale: boolean;             // true → 端上标「位置可能不是最新的」
};
```

**`kind` 与 `source` 是两件事，必须都给**：`kind` 说这个名字有多具体
（端上据此决定要不要再问一层），`source` 说它是从哪儿来的
（决定要不要标陈旧、要不要计入额度统计）。合成一个字段的话，
「从缓存里拿到的建筑名」与「现问的街道名」分不开。

### 解析主链：`PlaceResolver#resolve`

```java
public ResolvedPlace resolve(int latE6, int lngE6) {
    // ① 本地聚落库：围栏命中。免费、即时，且是我们自己说了算的那一档
    var hit = communityMapper.innermostFence(latE6, lngE6);
    if (hit != null) return ResolvedPlace.local(hit);

    String key = Geohash.encode(latE6, lngE6, GEO_KEY_PRECISION);   // 默认 8

    // ② 缓存未过期
    var cached = cacheMapper.selectFresh(key, PROVIDER);
    if (cached != null) { cacheMapper.touch(cached.getId()); return ResolvedPlace.cache(cached); }

    // ③ 高德。**熔断在这一句之前**：连续失败或额度耗尽时直接跳到 ④
    if (mapUsable()) {
        var r = geoService.reverse(latE6, lngE6);          // 取名顺序见 M7
        if (r.isPresent()) {
            cacheMapper.upsert(toRow(key, latE6, lngE6, r.get()));  // 写回 ②
            return ResolvedPlace.map(r.get());
        }
        breaker.recordFailure();
    }

    // ④ 过期缓存：已经花过钱买来的东西，地图挂了正是它的用处
    var stale = cacheMapper.selectAny(key, PROVIDER);
    if (stale != null) return ResolvedPlace.staleCache(stale);

    // ⑤ 只给区县。**不编地名**
    return ResolvedPlace.region(districtOf(latE6, lngE6));
}
```

四个要点：

- **① 在最前面**，因为它既免费又最权威（已开通聚落是我们自己维护的）。
  M8 把高频建筑沉淀进来之后，越来越多的点在这一步就结束了 —— 这就是「兜底」在长出来。
- **③ 的失败不吞**。`breaker.recordFailure()` 之后连续 N 次失败熔断 60 秒，
  避免每个请求都去等 3 秒超时。额度耗尽（`DAILY_QUERY_OVER_LIMIT`）直接熔断到当天结束。
- **写回缓存与返回值用同一个对象**，不要「先返回再异步写」——
  异步写失败是静默的，而下一次请求看起来完全正常，只是又花了一次额度。
- **⑤ 永远有结果**，不抛异常。定位这条链上任何一步都不该让首页白屏。

### `mapUsable()` 的判据（降级不是猜）

```java
boolean mapUsable() {
    return geoService.available()          // 配了 key
        && !breaker.isOpen()               // 没在熔断窗口里
        && !quotaExhaustedToday;           // 今天没撞到额度上限
}
```

端上**看不到这个开关**，只看到 `source`。运营端在 `/ops/geo/places` 里看得到
熔断次数与额度状态 —— 这是唯一能提前发现「地图快不行了」的地方。

### `GET /mp/place/search`：搜索也要有本地兜底

```
kw + (lat,lng | city)
  ├─ 本地聚落库 LIKE 匹配（免费）           ─┐
  └─ 地图可用？高德 place/around|text        ─┴→ 按「本地优先、同名去重、距离升序」合并
```

- **地图不可用时这个端点照样有结果**（只是少），端上的搜索框**不消失**。
  今天是整段不渲染，等于告诉用户「这儿什么都没有」。
- 合并时本地优先：本地库里的那条带着 `communityNo`，选中它才能直接绑聚落；
  高德那条只有名字与坐标。**同名时保留本地那条**。

### 端上的调用时序（首页）

```
onShow
 ├─ location.ensureHere()            // 没有或超 5 分钟就取坐标
 │    └─ getLocation/getFuzzyLocation → resolve(lat,lng) → here{coords,place}
 ├─ 顶栏显示 here.place.name（stale 时带一个小标记）
 └─ 货 = 按「收货地址所属聚落」要（M9 建议）
      └─ 与 here 不在同一聚落 → 顶栏下给一行可切换的提示
```

**`ensureHere` 的过期判据是时间，不是「拉过没有」**。
App 的进程比一次性加载活得久，「拉过没有」那种写法在 App 上等于整段会话都用第一次的结果。
