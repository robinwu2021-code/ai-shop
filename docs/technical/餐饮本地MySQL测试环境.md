## 初次迁入与后续升级

初次结构来自本轮专用、空业务数据开始执行原始 Flyway 链的本地测试夹具；迁入截至 CORE V574 的结构和迁移产生的参考数据、成功迁移历史。临时 MariaDB 的 V575 失败记录及其两个空表不导入，V575 起由真正的 MySQL 原始 Flyway 执行。仅在导出的 DDL 上将 `utf8mb4_uca1400_ai_ci` 转为 MySQL 支持的 `utf8mb4_unicode_520_ci`，保留二进制列排序规则，数据段不转换。MariaDB 的 CHECK 名称只要求表内唯一，MySQL 要求库内唯一，因此导出的 CHECK 名称加确定性散列前缀，约束表达式保持不变。库存另外执行原始迁移到 V17 后迁入 36 张表；触发器导出的会话 SQL_MODE 去掉 MySQL 已移除的 `NO_AUTO_CREATE_USER`，定义者使用本机导入账号，不沿用容器账号。触发器业务语句保持不变。逐表核对行数，原迁移文件、版本号及 checksum 不改写，不使用 Flyway repair 伪造成功记录。

后续 CORE、FOOD、CIM、库存与报表仍由各自原始 Flyway 初始化器校验及升级。带触发器的 CORE 迁移由管理员迁移阶段执行（本次仅临时注入 `SPRING_FLYWAY_USER/PASSWORD`），应用运行时仍使用库级测试账号；不授予该账号 SUPER，也不修改 `log_bin_trust_function_creators`。报表由原报表迁移器在独立库初始化，不在业务库建统计表。日任务及 Outbox 自动投递默认关闭；支付使用既有 standalone 边界，不执行真实支付。

不会覆盖同名已有数据库，不清除已有本地业务库，也不改动云端配置。此次只迁本地测试环境，不代表推送或上线。
