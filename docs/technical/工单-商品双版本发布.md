## 步骤 1 · 新表与草稿读写

迁移（号现查）：DDL 见设计 §4.6.7 —— `goods_no` 主键（**一件商品至多一份草稿**），
`payload` 存整份 `SaveCommand` JSON（编辑缓冲、非契约，形状随编辑器走），
`base_updated_at` 记草稿基于哪一版线上快照。排序规则 `utf8mb4_unicode_520_ci`，
不写 `IF NOT EXISTS`（可移植性闸门）。

`MerchantGoodsService` 加 `draftOf(merchantNo, goodsNo)`；
`detail()` 给 B 端时带 `hasDraft` 布尔（列表页标识的数据源）。

## 步骤 2 · `save()` 改写 —— 行为变更，红测试先行

**新行为**：商品在售（`on_sale=1`）时，保存**只写草稿行**，
`prd_goods`/`prd_sku` 一个字节不动；商品未上架时行为不变（直接写主行，
草稿态商品不需要第二份草稿）。

- **保存的内容与线上相同 → 删草稿行**（标识的判据是「草稿行存在」，
  相同内容的草稿留着会造成假标识）
- V247 的 `setOnSale(false)` + `pendingOnSale` 那段**在售分支里删掉** ——
  未上架分支保留提审逻辑
- 红测试：`savingOnSaleGoodsKeepsItSelling` —— 改标题保存 → C 端看到的还是旧标题、
  商品仍在架、`hasDraft=true`。**现在会红**（现状是自动下架）

⚠️ 存量兼容：改动瞬间可能有商品正处在「V247 下架送审中」（`pendingOnSale=1`）。
过审恢复的那段逻辑保留 —— 它只服务存量在途商品，跑空之后自然死掉，
在方法注释里写明「V247 遗留，在途商品清零后可删」。

## 步骤 3 · 发布 = 原子换版

`publish(merchantNo, goodsNo)`（审核关：提交即换版；审核开：过审回调里换版）：

1. `base_updated_at` 与线上 `updated_at` 对不上 → 拒，
   「线上已变化，请查看差异后再发布」（新错误码）—— 不静默覆盖
2. 反序列化 payload → 走一期的 `bakeForPublish`（重解析 + 重烘焙；
   停用档在这里被拦，逐条点名）
3. **同一事务**：覆写 `prd_goods` + `saveSkus` + 删草稿行 + `syncPool`
4. 买家视角要么整份旧版要么整份新版 ——「先下架再上架」收敛成零窗口换版，
   没有列表消失/购物车失效的真空期

红测试：换版事务中途抛异常（模拟 saveSkus 失败）→ 线上仍是完整旧版、草稿行还在。

## 步骤 4 · `publish-preview` 差异接口

`GET /biz/goods/{goodsNo}/publish-preview`：服务端把草稿**先烘焙成发布形态**
（不落库的 dry-run），与线上快照做字段级 diff，返回
`[{field, fieldLabel, before, after}]`（标题/价格/每个规格组/每档/参数/图各一行）。

**diff 必须在服务端算**：烘焙规则只有服务端有 —— 端上比对原始 payload
会漏掉「文案将随规格库刷新」这类变化，而那正是商家最需要在发布前看见的。

契约四件套照规矩走（contract/endpoints/mock/http，`type-alignment` 守着）。

## 步骤 5 · b-app 三处 UI

- 商品列表：`hasDraft` → 「有未发布修改」徽标
- 编辑页：读草稿（有）否则读线上；顶部横幅「当前编辑的是草稿，线上仍在售旧版」
- 发布确认页：调 preview 展示「本次发布将改变……」清单 → 确认 → publish。
  冲突（步骤 3 第 1 条）时引导先看差异
