# 餐饮渠道组合配料库存兼容开发计划

> **2026-10-29 口径更新**：餐饮本期只使用餐饮本地库存，与独立进销存联动另立任务。本文将进销存作为餐饮库存权威的旧设计及验收证据以[餐饮本地库存需求与切换方案](./餐饮本地库存-需求与切换方案.md)替代。商品与订单基础能力继续复用；历史订单与现有代码必须安全过渡。

## 目标与边界

组合配料的销售 SKU 提供渠道售价；库存来源独立明确选择。既有订单和配置继续按原规则，禁止在迁移时改变历史消耗口径。使用真实库存、厨房、订单和打印 owner，外部平台使用 Mock；支付和真实设备不在本轮。

## 约定

- `SALES_SKU`：按现有销售 SKU 作为独立成品扣减；旧行及旧快照缺字段均按原规则解释。
- `NONE`：仅作为旧无销售 SKU 的单项配料的历史解释，不隐含库存成功；不得作为新组合的物料来源。
- `COMPONENTS`：只允许组合配料，销售 SKU 仍用于价格与渠道映射，不作为库存物料；按已发布成员树和数量递归展开，保留物料 ID、单位、定义哈希及发布版本。主菜与成员分别计算，不能双扣。
- 配置更改生成新发布版本；下单冻结来源与清单，已下单/已发布历史快照不被改变。无法解析配置、依赖、单位和库存事实时拒绝，不能回退为虚拟库存。
- 多门店、多个渠道价格仍沿当前餐牌和价格 owner，消费与售后回退按冻结的实际分支和履约回执；禁止重写核心订单或库存所有权。

## 实施任务

1. **配置及快照**：新增向后兼容的配料库存模式字段、数据库增量迁移、B 端请求和响应；校验默认行为、非法组合、历史快照解析与发布哈希。独立部署和集成部署必须使用同一迁移。
2. **原始渠道证据**：从冻结发布版本判断库存模式；销售 SKU 保留渠道计价证据，按成员展开时不生成销售 SKU 的实物消耗分支，原平台行及金额分摊仍可追溯，不减少原始财务金额。
3. **库存和厨房**：从冻结成员树生成原始库存计划，校验用量和工位，支持套餐嵌套、按成员消耗、分次交付和恢复；销售 SKU 模式保持现有行为。库存不足、不可用 SKU、循环/深度、单位冲突全部失败关闭。
4. **验收与发布**：先编译后集中验证配置、快照兼容、两种模式、渠道 Mock 全链路、重复回调、退餐与库存证据；更新数据库和 API 文档，独立审查。真实支付、厂商打印及线上部署依赖其各自准入条件。

## 当前状态

已确认现有 `MenuCatalogPricePolicy` 只能以销售 SKU 定价，而 `DiningChannelModifierDemand` 将有销售 SKU 的组合视为独立实物，不展开成员。已实现独立模式解析策略及 2 项单元测试，尚未接入配置、快照、订单或库存链路；不得将该场景标为通过。

兼容实现必须保留旧命令的幂等请求指纹、历史发布 JSON 和已有快照哈希。旧数据缺少模式时只在读取时按原行为解析，不批量回填历史快照；新模式在端到端实现和验收完成前不得向业务开放。
