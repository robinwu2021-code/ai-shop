> · 方案：[TDD-位置与经营范围](./design/TDD-位置与经营范围.md)

**怎么用这份计划**：每个工单是一次提交的量，自带判据。
**判据缺一条不算做完** —— 这一块的缺陷共同点是**不报错**，
所以「接口能通」不是判据，「撤掉实现会变红」才是。

# 一批 · 先把分母修对

## T1 · 匹配读每个聚落自己的围栏 —— `LOC-C10` · ✅ **已完成 2026-09-04（`744252af`）**

**为什么值**：`cmt_community.fence_radius` **23 个聚落全设了 1000 米**、运营端有设置入口、
ops 列表也显示它 —— 但 `withinRadius()` 用的是全局 `shop.community.nearby-radius-m`（5000）。
**写了不读**。于是「智能匹配」实际是「中心点五公里内按距离排」，
而楼栋（二批）在这个精度上根本不成立。**这一单不加表不加字段，只是把库里已有的数用起来。**

| 层 | 动什么 |
|---|---|
| 后端 | `CommunityServiceImpl.withinRadius`：判据换成 `c.getFenceRadius()`；**为空或 ≤0 时回落到全局值**（存量安全网） |
| 报表 | 临时脚本：新旧两套口径各算一遍，输出「候选数变化最大的前 20 个坐标」。**先看报表再切**（§7 灰度） |
| 落点 | `backend/shop-core/…/community/service/impl/CommunityServiceImpl.java` |

**判据**：

1. 把某聚落围栏改成 200，站在 500 米外**不再**匹配到它；改回 1000 又能匹配到。**两向都要验**
2. `fence_radius` 为 null 的聚落**行为不变**（回落全局值）—— 防的是「某天有人加了一个没设围栏的聚落，它从此谁也匹配不到」
3. 消融：判据改回全局值 → 第 1 条变红

**不做**：多边形围栏。圆够用，且 23 个聚落的圆心与半径都齐了。

### 落地记录

**对比报表（切换前跑的，线上真实数据）**：8 个探针候选集收窄
（「弓村社区居委会」3→1、「嘉逸花园」3→1…），**没有一个被收成 0**（最小 1、最大 5），
两条有坐标的真实收货地址在新旧口径下结果完全相同。

**写的时候差点写错一处**：最初的注释说「围栏为空的聚落回落到全局值」——
而这一列是 `NOT NULL DEFAULT 1000`、唯一写入口 `setFence` 又拒绝 ≤0，
**那个状态在库里根本不存在**。更糟的是我把 0 当成「回落全局」，
而 ops 接口注释写着「0 等于这个社区谁也覆盖不到」——**语义正好相反**。
最终写成：那个回落是纯防御，留着是因为万一取到 0，
含义必须是「没设过」而不是「半径为零」。第二条判据改成守 `setFence` 拒绝 0 这个前提。

> ⚠️ **共享工作区里支付域有别人未提交的在建代码**（`SettleServiceImpl`、
> `PaymentLedgerService*`），会让 Spring 上下文起不来（`FundInvariantService` 找不到 bean），
> **本地全量跑必红，不是你弄的**。这一单是在干净的 HEAD worktree 里只搬入本次改动验的 ——
> 后面几单大概率也要这么跑。

## T2 · `GET /mp/location/resolve` —— `LOC-C11` · ✅ **已完成 2026-09-04（`c5f32951`）**

**为什么值**：「最内层聚落」的判据（**层级优先于距离**）是业务规则。
今天端上自己取 `nearby` 的第一条，等于把规则放进了端 ——
而 c-app / b-app / 将来的 H5 会各写一份，它们迟早不一样。

| 层 | 动什么 |
|---|---|
| 端点 | `GET /mp/location/resolve?latE6=&lngE6=` → `{ innermostNo, chainNos[], coarse }` |
| 后端 | 一批时 `chainNos` 只有一层（`parent_no` 二批才有），**结构先定下来**，二批只填内容 |
| 端上 | `c-app/src/stores/location.ts` 改调它；顶栏显示 `innermost` 的名字 |
| 登记 | 鉴权分类（游客可看）· 三端 endpoints · 契约 · mock · 三个生成器 |

**判据**：

1. 同一个坐标，`resolve` 返回的 `innermostNo` 与端上原来取 `nearby[0]` **一致**（一批不改行为，只搬位置）
2. `coarse=true`（模糊定位）时**不返回 innermost** —— 见 T4
3. `MpEndpointAuthTest` 绿（新端点已分类）

**不做**：在这一单里就实现归属链上溯。`parent_no` 还不存在。

### 落地记录

**顺手修了 `nearby` 排序的一处真缺陷**：判据原是 `distance == 0 ? MAX : distance`，
用「距离为 0」当「算不出距离」的替身。而距离恰好为 0 还有另一种含义 ——
**我正站在它上面**。于是站在一个小区的中心点，它被排到最后，700 米外的邻居小区排第一。

**T1 漏跑全量的代价**：`ConsumerBrowseFlowTest.guestCanPickCommunity` 在 T1 之后就红了，
而我当时只跑了窄选择。它的探针离 C0001 有 1470 米 —— 全局 5000 米时那条也在列表里，
「第二条距离更大」才有东西可比；换成各自围栏后 1470 米本就不该算附近，列表只剩一条，
`get(1)` 是 null。探针挪到 (30.284, 120.104)（到两社区 147/588 米，都在围栏内）后恢复。

> **教训写在这儿给后面几单**：这一批改的是**匹配口径**，影响面遍布所有拿坐标查东西的用例。
> **每一单都要在干净 worktree 里跑一次全量**（约 7 分钟），窄选择会漏。
> 基线：**1818 条 / 1 红**（HEAD 自带的微信回调未分类）。

## T3 · 坐标健康度 `GET /ops/coverage/health` —— `LOC-O10` · ✅ **已完成 2026-09-04（`bc9bcada` + `40cda18a`）**

**为什么值**：**这是整个模块的分母**。9 家门店只有 2 家标过点，
而自送半径那条闸明写着「没坐标就放行」→ **7 家商家设的半径形同虚设**，
多远的单都进得来，等他要送货才发现送不到。而今天运营端**看不见这件事**。

| 层 | 动什么 |
|---|---|
| 端点 | `GET /ops/coverage/health` → 门店总数/有坐标数、地址总数/有坐标数、聚落总数/有围栏数，各自可下钻到明细 |
| 界面 | 运营端「社区与网点」下新增一页；**每一格都能点进去看是哪几家** |
| 登记 | ops 端点五处登记（跨域登记表在 `packages/shared`）+ 菜单在库里（要跑生成器落迁移） |

**判据**：

1. 数字与直接查库一致（`select count(*) from mch_store where lat_e6 is not null`）
2. 点「7 家没标点」能列出**是哪 7 家**，且能跳到该商家
3. 页面上说清后果：「没标点 = 自送半径不生效，多远的单都会进来」

**不做**：自动补录坐标。补录是运营动作，要人看着地图确认。

### 落地记录

**守卫纠正了我两处，两处我原来的判断都错了：**

1. 我给三个查询都写了 `executeWithoutScope`，理由是「平台级分母」。站不住 ——
   这一页是给不受限的管理员看的，他本来就没有域限制；绕域换来的只是
   **让配了域的运营看到他无权处置、也点不进去的别家门店**。
2. 明细里原本带商家名，而取名字要调 `findAll`，那个方法为 C 端刻意绕开了数据域。
   改成只给 `merchantNo`，名字前端自取。

**`usr_address` 登记进 `OPS_READS_UNREGISTERED_OK`**：归属列是 `user_no`，
而 ops 的三个维度是商家/片区/自提点 —— 没有一个能回答「这条地址归谁管」。

**mock 自查抓到一处测试拦不住的**：缺口为 0 时那一格只剩一个孤零零的 `23/23`，
与「后果那行还没写完」长得一样，而这一页的读者正是来找缺口的。补了三句 allGood。

> **基线要现取。** 我一度以为 shared 守卫多出来的两条里有 G1，
> 查下去发现**我存的基线是几小时前的、已经过期**（期间别的会话提交了东西）。
> 用当前 HEAD 重取后，G1（`/ops/product/stats`）与「细化登记表 12 条无归属」都在基线上。

**菜单落库**：`sort` 取 60 而不是生成器算的 40 —— 线上 40 已被「临时点监控」占着。

## T4 · 切换地址补提示 + 模糊定位分流 —— `LOC-C14/C16` · ✅ **已完成 2026-09-04（`8879273b`）**

**为什么值**：两件都是「已经在做对的事，但没说」。
切到没坐标的地址时归属**不清空**（这条已实现，是对的），但**一句话都不说** ——
用户看到「换了地址，商品没变」，无从判断是 bug 还是设计。
模糊定位误差 5 公里而围栏是 1000 米量级，**拿它匹配聚落是噪音**，今天不分流。

| 层 | 动什么 |
|---|---|
| 端上 | 切换后若新地址无坐标：提示「这个地址没有定位点，商品仍按 XX 显示」 |
| 端上 | `getLocationDetailed` 已带 `fuzzy` 标记 —— 据它分流：模糊时**不匹配聚落**，改为按区给候选列表，且**不显示任何距离** |
| 落点 | `c-app/src/stores/location.ts` · `pages/address/index.vue` · `pages/community/index.vue` |

**判据**：

1. 切到一条没坐标的地址 → 归属**不变** + **有提示**
2. 模糊定位时不显示距离、不匹配聚落（选社区页已有 `coarse` 的先例，照它做）
3. 消融：去掉分流 → 模糊坐标又能匹配出聚落 → 红

## T5 · 顶栏 chip + 定位变了主动问 —— `LOC-C17/C18` · ✅ **已完成 2026-09-04（`fd6ccaa0`）**

**为什么值**：这一单是**手动多选被否决之后的替代方案**（决策记录 D3）。
多选的真实驱动力是「切换太麻烦」，所以把切换做便宜，而不是绕过它。

| 层 | 动什么 |
|---|---|
| 端上 | 顶栏常驻家 / 公司两个 chip（取自 `tag`），一点即换 |
| 端上 | 定位与生效位置差得远时问一句「你好像在公司附近，切过去吗」——**一次询问，绝不自动切** |

**判据**：

1. 点 chip 切换，**顶栏、副标题、商品池三处同时变**（这是已经踩过的坑）
2. 询问只出现一次，**他不点就维持原样**；不弹强制弹窗
3. 消融：把询问改成自动切 → 守卫红（断言代码里不出现「无确认直接 switchTo」）

**不做**：按时段自动切。自动切会让人在完全没察觉的情况下看到另一个地方的货，比麻烦糟得多。

# 二批 · 楼栋与精确覆盖（**必须整批上线**）

> ⚠️ T6–T7 与**池重建**是一次上线，不能分开：
> 迁移上了而 `reachableCommunities` 没改 = 排除不生效；
> 改了而池没重建 = B 端显示「已排除」、C 端照样看得到，**且不报错**。

## T6 · 迁移：`parent_no` + `mode` + `kind=BUILDING` —— `LOC-DB`

| 层 | 动什么 |
|---|---|
| 迁移 | `cmt_community.parent_no`（可空 + 索引）· `mch_service_area.mode`（默认 `INCLUDE`） |
| 实体 | `CmtCommunity.parentNo` · `MchServiceArea.mode` |
| 枚举 | `kind=BUILDING` 进枚举登记表 + 三端词条（`i18n-backend-enum-keys` 会查） |
| 校验 | 楼栋建档：`parent_no` 与 `region_code` **两个都必填**；`parent_no` 指向的聚落自身 `parent_no` 必须为空（**只做两层**） |
| 契约 | `Community` 加 `kind`/`parentNo`；`ServiceArea` 加 `mode`。**每个字段都要 JSDoc**（`spec-completeness` 会查） |

**判据**：

1. `SchemaDriftTest` 绿（实体与测试库结构对得上）
2. 存量行**行为逐字不变**：`mode` 默认 INCLUDE，重建池前后行数一致
3. 楼栋建档缺 `region_code` 时**保存被拒**并说明理由
4. 三层归属（楼挂楼）**保存被拒**

**不做**：给存量聚落回填 `parent_no`。今天线上 23 个全是顶层，没有楼栋。

## T7 · `reachableCommunities` 四处改动 + 池重建 —— `LOC-CORE`

**为什么值**：这是**可见性的唯一出口**（方法注释原话）。楼栋展开与 EXCLUDE 全在这一处，
调用方一行不动 —— 这正是当初收敛到这里的回报。

| # | 改动 | 为什么 |
|---|---|---|
| ① | 取 areas 后**拆成 includes / excludes 两组** | |
| ② | 空判据从 `areas.isEmpty()` 换成 `includes.isEmpty()` | **最容易写反的一处**：只写了 `EXCLUDE 3 幢` 的自送商家，语义是「不限范围但不送 3 幢」；沿用 `areas` 会让他跳过 fallback、展开出空集 → **谁也看不到，结果相反且不报错** |
| ③ | 展开 INCLUDE 时，`COMMUNITY`+小区/园区 → **自己 + 全部子楼栋** | |
| ④ | **最后**减去 excludes 的展开集合，**对所有 include 分支一视同仁**（含 EXPRESS 与 fallback 的「全部开放社区」） | 否则「快递商家排除不掉任何地方」 |

展开 EXCLUDE **复用同一个展开函数** —— 两套的下场是有一天它们不一样了，而没有任何测试会发现。

**待审**：`status != ACTIVE` 的 INCLUDE 不生效（沿用现状）；**EXCLUDE 不看 status**。

| 层 | 动什么 |
|---|---|
| 后端 | `MerchantPortImpl.reachableCommunities`（`backend/shop-merchant/…/port/`） |
| 后端 | **写入端也要动**（做的时候才发现）：`AreaCommand` 加 `mode`、`ServiceAreaVO` 回显 `mode`、父子归一**只在同一个 mode 内**做 |
| 上线 | **全量重建 `prd_community_pool`**（已有端点 `POST /ops/community-pool/resync`，不传 entityNo 即全量）+ 回读行数差核对 |

### 做完之后补记的三件事

**① 写入端不补，这一列就只读不写。** 保存范围走的是「全量删重插」，
`AreaCommand` 没有 `mode` 的话，商家改一下营业时间、把范围原样传回来，
