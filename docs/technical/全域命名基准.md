## 一、命名原则（先定这五条，名字才不会再漂）

| # | 原则 | 反例（本轮真实踩过的） |
|---|---|---|
| 1 | **`merchant` 一词只用于支付语境（收款商户号）**；经营实体一律叫 `entity` | `usr_merchant` 的 "merchant" 二义，直接导致过一次误设计（把商户读成执照） |
| 2 | **一域一前缀**，跨域引用只经业务键 | `usr_` 里混着消费者和商家两套东西 |
| 3 | 名字要能**独立回答"这张表是什么"**，不依赖上下文 | `usr_staff_store` —— 不看注释猜不出是"角色"表 |
| 4 | 同名不同义的键**禁止存在** | `staff_no` 曾同时指平台运营与店员 |
| 5 | 关系表 = `两端实体 + 关系词`；注册表 = `sys_ + 名词` | `prd_community_pool` —— "pool" 说不清是什么关系 |

**域前缀（修订后）**：

| 前缀 | 域 | 变化 |
|---|---|---|
| `usr_` | **消费者域**（只放消费者的东西） | 商家侧全部迁出 |
| `mch_` | **商家经营域**（新） | 主体/门店/账号/收款号/Plan 归这里 |
| `prd_` `ord_` `mkt_` `pts_` `stl_` `cmt_` `msg_` | 不变 | —— |
| `sys_` | 平台注册表与运营 | —— |

## 二、对象命名总表

### 2.1 身份域

| 中文 | 英文 | 表名（现 → 新） | 业务键（现 → 新） | 理由 |
|---|---|---|---|---|
| 消费者账号 | Consumer Account | `usr_user` → `usr_account` | `user_no`（不变） | "user_user" 叠词；键约定俗成保留 |
| 消费者身份绑定 | Consumer Identity | ⬜ `usr_account_identity` | `(provider, external_id)` | —— |
| **商家账号** | Merchant-side Account | `usr_merchant_staff` → **`mch_account`** | `merchant_staff_no` → `mch_account_no` | 它已是 B 端账号池本身，不是"员工附属表"；"staff" 还与平台运营撞名 |
| 商家账号身份绑定 | Merchant-side Identity | ⬜ `mch_account_identity` | 同上结构 | —— |
| 员工门店角色 | Store Role | `usr_staff_store` → **`mch_store_role`** | `(mch_account_no, store_no)` | "staff_store" 看不出是角色表 |
| 平台运营账号 | Ops Staff | `sys_staff` → `sys_ops_staff` | `staff_no` → `ops_no` | 让 "staff" 从此只有一个含义 |

### 2.2 商家经营域

| 中文 | 英文 | 表名（现 → 新） | 业务键（现 → 新） | 理由 |
|---|---|---|---|---|
| **主体**（一张执照的经营实体） | Business Entity | `usr_merchant` → **`mch_entity`** | `merchant_no` → **`entity_no`** | 原则 1：merchant 让给支付语境 |
| **收款商户号** | Payment Merchant | `usr_merchant_payment` → **`mch_payment_merchant`** | `payment_no` → `pay_merchant_no` | 全库唯一合法的 "merchant" 用法 |
| 门店 | Store | `usr_store` → `mch_store` | `store_no`（不变） | 迁域即可，名字本身没问题 |
| 主体类型（小微/个体户/企业） | **Legal Form** | `sys_merchant_subject` → **`sys_legal_form`** | `subject_type` → `legal_form` | "小微/个体户/企业"就是法律形态；"subject" 还与风控主体撞过名 |
| 入驻申请 | Entity Onboarding | `usr_merchant_apply` → `mch_entity_apply` | `apply_no`（不变） | —— |
| Plan 档位定义 | Plan Tier | ⬜ `sys_plan_tier` | `plan_code` | "def" 是实现词，"tier" 是业务词 |
| Plan 订阅实例 | Plan Subscription | ⬜ `mch_plan` | `(entity_no)` 1:1 | —— |
| 门店覆盖社区 | Store Service Community | `usr_merchant_community` → `mch_store_community` | `(store_no, community_no)` | 它早已下沉到门店，名字还留着 merchant |

## 四、一眼校验：新名字能不能自解释

盖住中文列，只看表名自测：

```
mch_entity            → 商家域的经营实体          ✅
mch_payment_merchant  → 商家域的收款商户号        ✅（merchant 只在这出现）
mch_store             → 商家域的门店              ✅
mch_account           → 商家域的账号              ✅
mch_store_role        → 商家域·账号在门店的角色    ✅
prd_store_listing     → 商品域·门店在售清单       ✅
sys_legal_form        → 平台注册表·法律形态       ✅
sys_ops_staff         → 平台运营人员              ✅
```

旧名对照自测（为什么要改）：

```
usr_merchant        → 消费者域的商家？        ✗ 域错 + merchant 二义
usr_merchant_staff  → 商家的员工？            ✗ 它其实是 B 端账号池本身
usr_staff_store     → 员工的门店？            ✗ 它是角色表
sys_merchant_subject→ 商家科目？              ✗ subject 三义（法律形态/风控主体/学科）
prd_community_pool  → 社区的池子？            ✗ 说不清是什么关系
```

## 五、落地策略（命名归命名，迁移归迁移）

| 步 | 内容 |
|---|---|
| 1 | **新表一律用新名**（M3 起：`prd_store_listing`、`sys_plan_tier`、`mch_plan`、`cmt_region`…） |
| 2 | 存量改名是**独立的一期**（涉及 40+ 表引用、三端契约、全部测试），不与任何功能期混 |
| 3 | 改名期用 `RENAME TABLE` + 键列改名，三个迁移重放器已支持 `RENAME TO`（M1 时补的） |
| 4 | [项目词典](../requirements/项目词典.md) 在**改名落地时**同步 —— 词典有守卫（标识符必须真实存在于代码），不能提前写 |

> ⚠️ 第 2 步的量级要说实话：`merchant_no → entity_no` 贯穿订单、结算、积分、归因，
> 是全库最高频的键。收益是词汇永久对齐，成本是一次全库替换 + 全量回归。
> **值得做，但要单独排期，且在多门店（M6）发布之前** —— 之后再改，历史包袱翻倍。
