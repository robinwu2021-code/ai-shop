# B 端权限方案：老板 · 店长 · 店员 · 理货员 · 配送员

> 2026-08-11 · 起因：三端对齐盘点发现 `StaffRole`（MANAGER/CLERK）**全库没有一处用于判权** ——
> 只在校验取值合法时出现过。店长与店员权限完全一样，而
> [矩阵 §2.2](../requirements/需求矩阵-三端.md) 写着店员「无财务、无结算账户可见性」。
> **这条约束现在不存在**：一个店员能打开结算页看到全部账单。

---

## 一、先说三个前提，它们决定了方案的形状

### 1.1 角色跟着**门店**走，不跟着人走

`mch_store_role` 的唯一键是 `(mch_account_no, store_no)` —— **一个员工每家店一行**。
所以同一个人完全可能在文三路店是店长、在古墩路店是店员。

> 因此「当前角色」= `mch_store_role[当前门店]`，而不是账号上的一个字段。
> 这与已有的 `currentStoreNo`（`X-Store-No`）是同一套上下文，顺着它做就行。

老板不在这张表里 —— 列注释已经写明「OWNER 不在这里，他不需要逐店授权」。
所以解析顺序是：`is_owner=1 → OWNER`，否则查当前门店的那一行。

### 1.2 权限的分界线，画在**出错的后果**上

不按「功能重要性」这种模糊的东西分。四类后果：

| 后果 | 例子 | 谁能做 |
|---|---|---|
| **动钱** | 结算账户、进件、提现、账单、积分开关 | 只有老板 |
| **改结构** | 建店、停用店、设默认店、员工授权 | 只有老板 |
| **改经营** | 商品与价格、营销活动、评价回复、售后处理 | 老板 + 店长 |
| **日常履约** | 核销、到货登记、发货、分拣、改库存 | 按「面对谁」再分三档，见 §2.2 |

### 1.3 有一条现成的缝正好在分界线上

**改库存与保存商品本来就是两个接口**：

```
POST /biz/goods/{goodsNo}/stock    只改库存      → 店员可以
POST /biz/goods/save               改价格与全部  → 店员不行
```

这不是巧合 —— B 端功能清单里写着「改库存是最高频的日常动作，一批菜卖完了要马上改，
走完整表单等于每次重填一遍」，所以当初就拆开了。**权限边界正好落在这条已有的缝上**，
不需要为了权限去拆接口。

判据是清楚的：**改库存不出钱，改价才出钱。**

## 二、B 端到底有几个角色

### 2.1 先看真实分工，再定角色

上一版只搬了代码里现有的三个（老板/店长/店员），**中间有断层**。
按 B 端 67 个端点对应的「活」重新数一遍，一家有雇员的小店里实际有五种人：

| 岗位 | 他一天在干什么 | 不该让他碰什么 |
|---|---|---|
| **老板** | 看账、进件、开店、加人 | — |
| **店长** | 上架改价、建活动、处理售后、回评价 | 钱的去向、开店停店、加人 |
| **店员** | 站收银台：核销取货、卖完了改库存 | 改价、活动、售后、顾客资产 |
| **理货员** | 一车货到了：点数、分堆、报短少 | **顾客信息**、金额、核销 |
| **配送员** | 拿着要送的单出门，送到点一下 | 全店订单、商品、任何金额 |

后两个是上一版漏掉的。而它们不是我编的场景 ——
[矩阵 §2.2](../requirements/需求矩阵-三端.md) 里「配送员（P1）」本来就有，
理货这条则是被 `/biz/pickup/picking` 这个接口本身证明的（见下）。

### 2.2 履约不是一件事，是三件

上一版把核销/到货分拣/发货压成一个 `biz:fulfill`。**这是错的** ——
它们面对的对象完全不同，而接口早就分开了：

| 活 | 接口 | 返回里有什么 | 面对谁 |
|---|---|---|---|
| **分拣** | `GET /biz/pickup/picking` | `goodsNo/title/spec/totalQty/buyerCount` —— **无金额、无买家** | 货 |
| **核销** | `POST /biz/pickup/verify` | 取货码、买家昵称、手机尾号 | 顾客 |
| **发货/自送** | `POST /biz/order/{}/ship` `delivered` | 地址 | 收件人 |

分拣单**天然就是理货员能看的粒度**（当初为了「按商品汇总点数」设计的，
顺带就把顾客信息排除了）。所以拆成三个码不是硬切，是顺着已有的形状。

### 2.3 角色清单（五个）

| 角色码 | 中文 | 载体 | 何时用 |
|---|---|---|---|
| `OWNER` | 老板 | `mch_account.is_owner=1` | 主体负责人，不逐店授权 |
| `MANAGER` | 店长 | `mch_store_role` | 一家店的负责人 |
| `CLERK` | 店员 | `mch_store_role` | 收银台 |
| `PICKER` | 理货员 | `mch_store_role` | **新增**：只到货分拣 |
| `COURIER` | 配送员 | `mch_store_role` | **新增**：只自送 |

矩阵里的「服务人员/技师（P1）」不加 —— 服务品类还没上线，
加一个没有任何功能对应的角色，就是又一个「有录入没有消费方」。

**自提点承接方不是角色**，是数据范围（`pickupNos`）—— 它已经做好了。
把它做成角色会与门店授权打架：同一个人可能既是店员又承接自提点。

### 2.4 加了两个角色，小店老板会不会不会配

会。所以 UI 上**默认只显示三个**（老板/店长/店员），
理货员与配送员收在「更多角色」里。夫妻店永远看不到它们。

> 这条不是可选的收尾工作。三个角色的选择题谁都会做，
> 五个并排摆出来就变成一道需要读说明的题 —— 而店主不会读。

## 三、权限码与角色映射

### 3.1 十三个权限码

| 权限码 | 覆盖 | 为什么单独一个 |
|---|---|---|
| `biz:verify` | 核销、批量核销、按码搜索 | **交付确认**，等于签收 |
| `biz:receive` | 到货登记、分拣单、短少上报 | 只对货，不对人 |
| `biz:ship` | 发货、标记自送送达 | 要看地址 |
| `biz:order:view` | 订单列表与详情、工作台待办 | 含金额 |
| `biz:stock` | 改库存（含门店库存） | 高频日常，**不出钱** |
| `biz:goods` | 建/改商品、上下架、规格模板 | **含价格** |
| `biz:campaign` | 营销活动、开团、报价 | 让利与报价都是钱的承诺 |
| `biz:review` | 评价回复、差评申诉 | 回复是**公开**的 |
| `biz:aftersale` | 售后同意/驳回/收货 | 同意仅退款 = 直接出钱 |
| `biz:customer` | 顾客列表（含累计消费额）、经营数据 | 客户资产 |
| `biz:store` | 装修、配送规则、店铺码、分享物料 | 门店经营面 |
| `biz:store:admin` | 建店、改名、停用、设默认店、挂收款号 | **改主体结构** |
| `biz:finance` | 结算账单、费率卡、进件、积分开关 | 钱 |

### 3.2 角色 → 权限码

| 权限码 | 老板 | 店长 | 店员 | 理货员 | 配送员 |
|---|:-:|:-:|:-:|:-:|:-:|
| `biz:receive` 到货分拣 | ✅ | ✅ | ✅ | ✅ | — |
| `biz:verify` 核销 | ✅ | ✅ | ✅ | — | — |
| `biz:ship` 发货自送 | ✅ | ✅ | ✅ | — | ✅ |
| `biz:stock` 改库存 | ✅ | ✅ | ✅ | ✅ | — |
| `biz:order:view` 看订单 | ✅ | ✅ | ✅ | — | 🟡 |
| `biz:goods` 商品与价格 | ✅ | ✅ | — | — | — |
| `biz:campaign` 营销 | ✅ | ✅ | — | — | — |
| `biz:review` 评价 | ✅ | ✅ | — | — | — |
| `biz:aftersale` 售后 | ✅ | ✅ | — | — | — |
| `biz:customer` 顾客资产 | ✅ | ✅ | — | — | — |
| `biz:store` 门店经营面 | ✅ | ✅ | — | — | — |
| `biz:store:admin` 门店结构 | ✅ | — | — | — | — |
| `biz:finance` 钱 | ✅ | — | — | — | — |

**🟡 配送员的订单视图是受限的** —— 这是全方案唯一需要新增后端能力的地方，
其余都只是加判断。他需要「待自送的单 + 地址」，但不该看到金额与全店订单。
手法与自提点承接方看别家商家的货相同（`PickupOrderVO` 那套裁剪已经有了），
照抄即可，**不要用条件序列化把字段藏起来** —— 那种藏法迟早被某个 DTO 复用漏出去。

**理货员为什么没有 `biz:order:view`**：分拣单接口本身就够他用，
而且它天然不含金额与买家。给了订单权限反而是多给。

## 四、实施

### S1 · `BizContext` 带上当前角色

```java
// 解析顺序：老板优先，其余按**当前门店**取
String staffRole = isOwner ? "OWNER"
        : roleOfStore(mchAccountNo, currentStoreNo);   // MANAGER / CLERK / null
```

`null`（在当前门店没有授权）**当作零权限**，不是当作店员 ——
认不出角色时给权限，是这类解析最坏的失败方式（运营端那个映射刚踩过）。

### S2 · 一个 `BizPerms` 类，与 `Perms` 同构

放在 `shop-base` 的 `auth` 包，与运营端的 `Perms` 并列。
**不合成一个类**：两端的角色词表没有交集，合在一起只会让人每次都要先想「这是哪端的码」。

### S3 · 在 Controller 层加判断

与运营端同一条原则：**授权只在 Controller 层**，Service 不判功能权限 ——
散进 Service 的话，同一个业务方法被两个入口调用时就会漏掉一处。

运营端用的是 `@PreAuthorize("@perm.can('…')")`；B 端可以复用同一套
`@perm` bean，加一个 `canBiz(code)` 方法。

### S4 · 拒绝时给一句人话

不要通用的「没有操作权限」。店员点到结算页应该看到
**「结算与收款只有店主能看，找店主开通」** —— 否则他会去问店主要权限，
而店主在界面上根本找不到「给店员开结算权限」这个开关（**设计上就没有**）。

新增错误码 `BIZ_ROLE_FORBIDDEN`，i18n 三语。

### S5 · b-app 隐藏入口

后端拒绝是安全边界，前端隐藏是体验。两者都要有 ——
只做后端，店员会看到一堆点了报错的入口；只做前端，那不是安全。

`merchant` store 里存 `staffRole`，页面按它裁剪。
**切换门店时要重新解析** —— 同一个人在两家店可能是不同角色。

### S6 · 守卫

| 守什么 | 为什么 |
|---|---|
| 五个角色各自能访问的端点集合（快照测试） | 将来加端点时，忘了加权限判断会让快照变化，逼人回答「这个该给谁」 |
| 店员访问 `biz:finance` 类端点必须被拒 | 这是本次要修的那个越权口子，直接钉住 |
| `null` 角色落到最小权限 | 防止「认不出就放行」 |
| b-app 隐藏的入口 ⊇ 后端拒绝的端点 | 防止「前端显示、后端 403」 |

## 五、工作量与风险

| 步骤 | 量 | 风险 |
|---|---|---|
| S1 BizContext 带角色 | 小 | 低（新增字段） |
| S2 BizPerms | 小 | 无 |
| S3 Controller 判断（约 40 处） | **中** | 中：漏一处是越权，多一处是挡住正常使用 |
| S4 错误码与文案 | 小 | 无 |
| S5 b-app 隐藏入口 | 中 | 低 |
| S6 守卫 | 小 | 无 |

**风险集中在 S3。** 缓解办法是先写 S6 的快照测试（五个角色 × 全部端点），
**让它先红**，再逐个加判断把它变绿 —— 这样「哪些端点还没定权限」是可见的，
而不是靠人去逐个数 67 个端点。

## 六、不做什么

| 不做 | 为什么 |
|---|---|
| 让商家自定义角色权限（勾选矩阵） | 五个预设覆盖了真实分工的绝大部分；开放自定义后，店主要面对一张 13 列的表，而他真正想问的是「这个人能不能帮我发货」。**预设是答案，勾选矩阵是把问题还给他** |
| 加「服务人员/技师」（矩阵 P1） | 服务品类还没上线，加一个没有功能对应的角色就是又一个「有录入没有消费方」 |
| 把自提点承接方做成角色 | 它是数据范围（pickupNos），已经做好了。做成角色会与门店授权打架 —— 同一个人可能既是店员又承接自提点 |
| 把 B 端权限码接 DB | 与运营端同样的判断：硬编码的问题是「改要发版」，不是「对不上」。小店的角色不会天天变 |
| 给店员开「部分财务」（比如只看今日营业额） | 今日营业额已经在 `biz:customer`（经营数据）里；再切一刀会让「财务」这个边界变模糊，而它是本方案最该清晰的一条线 |
| 动数据范围（storeNos） | 那一块已经做好且正交：**角色管「能做什么」，门店管「能碰谁的数据」**，两个都要过。只判角色 → A 店店长能改 B 店的货；只判门店 → 店员能在自己店里改价 |

---

## 七、一句话

> 现在三个角色**权限完全一样**，区别只在能碰哪几家店的数据。
> 本方案补两件事：一是**能做哪些动作**（13 个权限码），
> 二是**把履约拆成三种活**（分拣 / 核销 / 发货），因为它们面对的对象不同 ——
> 对货、对顾客、对收件人。拆开之后，理货员与配送员才装得下。
>
> 分界线画在「出错会不会动钱、会不会改结构、会不会碰到顾客信息」上，
> 而不是画在功能重要性上。
