# 储值独立入口 · 服务端接口评审

日期：2026-10-20。结论：**未通过前端完整接入条件**。现有代码支持活动充值及单客余额，未实现本轮原型所需的独立方案、顾客列表与统一收支流水。本结论是需求与实现的差异，不表示历史活动充值本身存在缺陷。

范围：`prototypes/marketing-module-v2.html` 的 s11、s13、s14、s22–s27；shop-app 商家 BFF、Core 充值协调、Pay 储值模型与查询服务、B端已接入的营销接口。静态代码与契约评审；没有执行服务器写入、部署、充值或全量测试。以下新增接口仅为建议契约，尚未实现，须纳入 TDD 与接口登记后开发。

## 2. 建议补齐的契约

统一前缀 `/biz/stored-value`。方案、账户及账务仍归 Pay；shop-app BFF 提供商家上下文、权限与门店检查，并经既有 PayClient/端口调用。Core 提供会员/商家/门店资料，历史活动来源继续兼容。

| 方法与建议路径 | 主要载荷/筛选 | 必需响应/行为 |
|---|---|---|
| GET /plans | status、cursor、size；商家上下文；按适用性判断当前门店 | planNo、versionNo、revision、name、currency、paidAmountMinor、bonusAmountMinor、totalAmountMinor、status、nextCursor |
| POST /plans | name、currency、paidAmountMinor、bonusAmountMinor；Idempotency-Key | 服务端生成方案和不可变版本；创建即启用；全部门店；校验金额、溢出及名称 |
| GET /plans/{planNo} | 当前商家 | 完整定义、状态、版本与 revision |
| PUT /plans/{planNo}/status | ACTIVE/INACTIVE、expectedRevision；Idempotency-Key | 并发冲突显式返回；停用不变更已有账户/入账 |
| GET /account-directory | keyword、cursor、size；当前门店上下文 | 有成功储值记录的顾客，含余额0；accountRef、maskedName、maskedPhone、currency、availableMinor、lastOccurredAt；稳定倒序分页 |
| GET /accounts/{accountRef} | 当前门店上下文 | 顾客展示资料与合计余额；引用非授权凭证；禁止越商家读取 |
| GET /records | type=ALL/RECHARGE/REDEMPTION、from、to、accountRef?、cursor、size；统一门店上下文 | recordNo、type、customer、store、title、signedAmountMinor、balanceAfterMinor、currency、occurredAt、businessNo、nextCursor |
| GET /records/{recordNo} | 商家和当前门店上下文 | 对应原始单据、账户余额快照、方案编号/版本/名称及金额快照；不得泄漏收款私密凭证 |
| POST /plan-recharges | customerRef、planNo、versionNo、storeNo；Idempotency-Key | 独立方案来源充值意图及进度；不需要活动编号/参与预占，不接受店员输入赠金 |
| POST /plan-recharges/{rechargeNo}/submit、/receive、/cancel；GET /plan-recharges/{rechargeNo} | 复用实收、修订、凭证与幂等机制 | 由可识别来源的协调器处理独立充值；只有 CREDITED 才显示到账成功 |

路径选用独立方案充值入口以保持历史活动充值契约；具体是否合并为类型化来源载荷，应在 TDD 中定案，不能只放宽旧DTO的非空校验。当前 owned/requireOriginalStore/recover 均依赖活动意图，必须一并适配独立来源。

约束：

1. 金额使用最小货币单位，服务端生成赠送与到账合计；方案版本不可变。并发停用与办理必须定义事务边界，已经生成的合法办理单使用冻结快照，不能事后重算。
2. 方案查询是商家定义；当前门店控制办理权限和记录范围。商家共用账户余额不会因门店切换变成门店余额。目录展示权限与门店过滤须明确定义，不能直接暴露全商家顾客。
3. 顾客列表不能依赖短期扫码引用维持长期导航；新增商家范围只读 accountRef，写入仍需合法识别的顾客引用，不降低现有身份校验。
4. 收支以成功入账事实为准；处理中/取消充值不伪装成余额变动。以 happenedAt 加唯一编号/账户序号稳定排序，过滤项、商家和门店绑定分页游标。
5. 混合收支从统一查询模型输出，变动后余额使用凭证快照，不拿当前余额倒推。底层可能有其他账务类型，须定义与UI“储值/核销”的映射，不把其他调账或冲正错误归类。
6. 时间弹框显示商家时区日期；接口建议 `[from,to)`，结束日期换算为次日零点。切换类型保留时间，确认后生效、取消不改变已应用条件。
7. 独立来源的 Outbox 重放、查询及故障恢复不得继续强制解析活动意图。保持商家隔离、幂等、原修订校验，避免重复到账。

## 3. 对原型办理流程的补充

主路径仍是“识别顾客 → 选择方案 → 确认实收 → 等待到账 → 查看账单”。页面主按钮可保持一个，但后台包含创建、实收提交、收款确认、异步入账。凭证获取/提交及权限分工需在真实表单体现；网络异常重试使用原幂等键；处理中显示进度并查询原单，不自动重复发起新充值。取消原单不等于已到账退款，本期不新增线上退款。
