# 商家入驻全流程：Review 与开发计划

> 2026-08-07 · 依据四方实测（三端契约 × 后端代码 × 45 张表 × 生成的 API 清单）。
>
> **执行顺序（用户定）**：先 Review 对齐 → 确认无误 → 再开发（API → 库 → 领域对象 → Controller → Service → Mapper）
> → 单元测试 → 复核 B/平台/C 三端功能 → 最后启动对接。
>
> **本文档现在只到「Review 结论 + 计划」。R 阶段的每一处待确认都要你点头，才进 D 阶段。**

---

## 零、为什么入驻值得单独拉一条线

入驻是**唯一一条贯穿三端的链路**：C 端提交申请 → 平台端审核 → B 端开始经营。
它也是所有商家侧功能的前置 —— 没有入驻，B 端 35 条接口没有一条有数据可跑。

同时它是**目前四方口径分歧最严重的一处**（下面 R-1 会看到），
所以「先对齐再开发」在这条线上收益最大。

# 第一阶段：Review（当前阶段）

## R-1　请求体四方不一致 🔴 必须先定

| 来源 | 字段 |
|---|---|
| C 端 `MerchantApplyReq` | `name` `type` `contact` `phone` `category` `desc` |
| B 端 `MerchantApplyReq` | **契约里有类型名，但没有任何字段**（空 interface） |
| 后端 `ApplyReq` | `name` `type` `contactPhone` `qualifications` |
| 库 `usr_merchant_apply` | `name` `merchant_type` `contact_phone` `qualifications` |

四方**没有两方是一致的**：

- C 端把联系人拆成 `contact`（姓名）+ `phone`，后端只有 `contactPhone` —— **联系人姓名会丢**
- C 端有 `category`（主营类目）与 `desc`（店铺简介），后端与库**都没有** —— 提交即丢失
- 后端与库有 `qualifications`（资质图），C 端**没有输入** —— 而 EDI 资质一期虽不强制，营业执照通常要
- B 端契约的 `MerchantApplyReq` 是空的，等于 B 端提交入驻**没有任何入参定义**

**待你确认：一期入驻表单到底收哪些字段。** 我的建议：

| 字段 | 建议 | 理由 |
|---|---|---|
| `name` | 必填 | 四方都有 |
| `type` | 必填 | 个体户 / 企业，决定分账主体类型 |
| `contactName` | 必填，**后端与库补列** | 审核要打电话找人，只有号码没有姓名不合适 |
| `contactPhone` | 必填 | 统一叫 `contactPhone`（后端与库的写法） |
| `category` | 必填，**后端与库补列** | 主营类目决定授权范围（`/ops/merchants/{no}/auth-codes` 已在等它） |
| `desc` | 选填，**后端与库补列** | 店铺简介，C 端门店页要展示 |
| `qualifications` | **选填** | 一期 EDI 不强制（用户早期决策），但营业执照该能传。选填而不是去掉 |

## R-2　状态机两套，且对不上 🔴 必须先定

| 来源 | 状态取值 |
|---|---|
| 库 `usr_merchant_apply.status` | 待核实（见 D 阶段第一步） |
| 平台端契约 `/ops/merchants/{no}/status` | `DRAFT → SUBMITTED → REVIEWING → APPROVED/REJECTED` |
| 后端 `OpsService.auditApply(applyNo, approved, reason)` | **只有二值**：approved true/false |

平台端契约描述的是**五态推进**（含 `REVIEWING` 这个"已受理正在看"的中间态），
而后端实现是**一步到位的二值审批**。两者不是同一个流程。

**待你确认：审核要不要 `REVIEWING` 中间态。** 我的建议：**要**。
理由不是流程完整性，是**商家侧的体感**：提交后一直显示"待审核"，商家不知道有没有人在看；
有了"已受理"，客服接手时点一下，商家那边就有反馈。一期人少，这一步几乎零成本。

## R-3　审核通过后的动作链条不完整

后端 `auditApply` 通过时调 `merchantAdminPort.activate(ownerUserNo, name, type)` 建商家。
但入驻真正落地还需要三件事，目前**一件都没有**：

| 缺什么 | 后果 | 依据 |
|---|---|---|
| 未写 `usr_merchant_community` | 新商家 `serviceScope=COMMUNITY` 但一个社区都没覆盖 → **C 端对谁都不可见** | ADR-009。B 端有前端拦截，但入驻这条路绕过了它 |
| 未写 `usr_merchant_payment` | 没有分账主体 → 第一笔订单就分不了账 | ADR-002 |
| 未设 `service_scope` | 库列有 `DEFAULT 'COMMUNITY'`，配合上一条 = 静默不可见 | 同上 |

**这是本次最值得修的缺口**：商家审核通过、登录 B 端、上架商品，然后**一个订单都不来**，
且他和运营都查不出为什么。R-1 里建议补 `category` 也与此相关 —— 授权类目是入驻的一部分。

**待你确认：入驻通过时是否要求运营指定覆盖社区。** 我的建议：**要，且作为审核动作的一部分**
（审核页上勾选社区，与"通过"同一个提交）。分开做的结果就是永远有人忘。

## R-4　三端的接口重复与缺口

| 端 | 现状 | 问题 |
|---|---|---|
| C 端 | `POST /mp/merchant/apply` ✅ 已实现 | 入口在「我的」页弹层。**没有查询自己申请状态的接口** —— 提交后就查不到了 |
| B 端 | `POST /biz/merchant/apply` + `GET /biz/merchant/apply`（草稿/上次申请）⬜ 都未实现 | 与 C 端那条**功能重复**：同一件事两个端各一条接口 |
| 平台端 | 10 条商家管理接口，**实现 0 条** | 审核队列在后端有（`applyQueue`/`auditApply`），但**没有暴露成 `/ops` 路由** |

**待你确认：入驻从哪个端提交。** 我的建议：**C 端提交，B 端只查状态**。
理由：申请人此刻**还不是商家**，他手里只有 C 端 App；让他先下载 B 端再申请是本末倒置。
B 端的 `GET /biz/merchant/apply` 保留（登录后看审核进度、被驳回后重新提交），
`POST /biz/merchant/apply` **从契约删除** —— 重复的提交入口迟早两边逻辑走偏。

C 端需**新增** `GET /mp/merchant/apply`（查我的申请状态）—— 现在提交完就断了。

## R-5　平台端审核入口没有路由

后端 `OpsService` 有 `applyQueue()` 与 `auditApply()`，`OpsController` 里也有
`GET /ops/merchant/apply-queue`。但**平台端契约里没有这条路径** ——
契约用的是 `/ops/merchants/{merchantNo}/status`（按商家推进），
后端用的是 `/ops/merchant/apply-queue` + 按 `applyNo` 审批。

**单复数、资源锚点（申请单 vs 商家）两处都不一致。**

**我的建议（技术判断，不需产品拍板）**：以**申请单**为锚点。
审核审的是"这份申请"，而商家在通过之前根本还不存在 —— 按 `merchantNo` 推进状态在
`APPROVED` 之前无从寻址。契约侧改为 `/ops/merchant/apply` + `/ops/merchant/apply/{applyNo}/audit`。

# 第三阶段补完：B 端这一段（2026-08-07）

前两段（C 端提交、平台审核）此前已通，**B 端一条没实现** —— 商家审核通过后登录 B 端拿到的是 404，
既看不到自己什么状态，也拿不到驳回原因。于是「驳回 → 补料 → 重提」这条路根本走不通，闭环断在这里。

## 补的接口

| 路由 | 作用 |
|---|---|
| `GET /biz/merchant/profile` | 商家资料。**对「还不是商家的人」也必须可用** —— 照搬 `requireMerchantNo()` 一律 403 的话，被驳回的人永远看不到原因 |
| `GET /biz/merchant/apply` | 上次申请，驳回后回填。没申请过返回 null 而不是 404 |
| `POST /biz/merchant/apply` | 提交/重提。与 C 端同一个 `createApply`，唯一键在库上，两个入口都拦得住 |
| `POST /ops/merchant/apply/{applyNo}/accept` | **受理**（PENDING → REVIEWING）。此前 `REVIEWING` 常量和状态机都写了，但没有任何接口能进入它 |

## 修的三个静默故障

| # | 问题 | 为什么之前没被发现 |
|---|---|---|
| 1 | **驳回后永远无法重提**：`setActiveOwner(null)` 是空操作 —— MyBatis-Plus 默认 `NOT_NULL` 更新策略会把 null 字段从 UPDATE 的 SET 里剔掉，被驳回的申请一直占着「一人一份」的名额 | 只在**驳回之后重提**时现形。直接通过的链路把 activeOwner 留在那儿也没人再查，所以先前 187 条测试全绿 |
| 2 | **状态机是注释不是代码**：`TRANSITIONS` 声明了却无人引用，审核只判「是不是进行中」 | 二值审批恰好没走到非法迁移 |
| 3 | **`asPickupPoint` 填了就丢**：B 端表单一直收，`SubmitApplyCommand` 和库里都没有这一列 | 勾了这项的人既没被拒绝也没被满足，中间没有任何一处报错 |

> ⚠️ 第 3 条只补到「记录意愿 + 审核页可见」。**通过审核不会自动建自提点** ——
> 自提点服务费是逐点线下谈的（ADR-005），没有默认值能覆盖，一期由运营手工建点。

## 顺带对齐

- `MerchantApplyVO` 改名 `type`→`subject`、`description`→`desc`、`qualifications`→`licenses`，与三端共享类型一致
- `MerchantApplyStatus` 扩为**整份申请**（内容 + 进度）；B 端 `mApplyDraft` 从 `MerchantApplyReq` 改指向它
- mock 里「内容」与「状态」两份存合并成一份 —— 后端 `usr_merchant_apply` 只有一行，拆开会让同一次提交在 B/C 两端显示成两件事
- B 端申请页不再用脱敏登录号预填 `contactPhone`（`138****8000` 过不了 11 位校验，看着却像已填好）

B 端 `/biz/**` 覆盖率 30.0% → **36.0%**；后端 190 条测试全绿。

# 第四阶段前置：B 端补齐（进行中）

## 已完成：登录 → 开店（2026-08-07）

入驻通过之后商家紧接着要做的三件事，此前后端都没有：

| 路由 | 说明 |
|---|---|
| `POST /biz/auth/login` | 一次返回 token + 商家档案。分两次请求会先闪一屏错的（拿到 profile 前决定不了进哪一屏） |
| `GET /biz/communities` | 社区列表。**不带定位** —— 商家选的是「我送得到哪些小区」，与他此刻站在哪儿无关 |
| `GET /biz/store` · `POST /biz/store` | 店铺资料。新增 `usr_merchant_store` 表（V30） |

**账号池澄清**：共享类型 `MerchantLoginResp` 的注释说「商家池与 C 端用户池是两套账号，token 不通用」——
那描述的是**没有实现的设计**。库里 `usr_merchant.owner_user_no` 指向的就是 C 端 userNo，
`BizContextFilter` 也是靠它解析 merchantNo。一套凭据是对的：入驻申请人此刻还只是普通用户，
通过后**同一个账号**长出商家身份；分两套就要回答「通过时发新账号吗、旧账号还能不能买东西」，
而店主本来就是小区里的买家。真正需要隔离的是运营池，那个已经隔离了。

### 又一个静默故障

`syncCommunities` 用「先全删再全插」，而 `usr_merchant_community` 是**逻辑删除**，
唯一键 `uk_merchant_community(merchant_no, community_no)` **不含 deleted** ——
删掉的行还占着索引位，再插同一个社区直接撞键。

触发场景是最普通的操作：**改公告但不动经营范围**。先前只有入驻审核会调它、一家店只调一次，所以一直没现形。
改为按差集增删，并把这一处实现给入驻审核和店铺设置**共用** —— ADR-009 的「空覆盖 = 对谁都不可见」
必须两条路径同一份代码，否则商家可以入驻时配好、转头在店铺设置里清空。

B 端 `/biz/**` 覆盖率 36.0% → **48.0%**（22 → 26 条）；后端 194 条测试全绿。

## 入驻链路已在真实后端跑通（2026-08-07）

真库（MariaDB `ai_shop`）+ 33 个迁移 + 种子数据，用 curl 走完商家视角全程，**15 步全过**：

| 步 | 验证点 | 结果 |
|---|---|---|

### 补的过程中发现的四个缺口

| # | 缺口 | 形状 |
|---|---|---|
| 1 | **商品审核有队列没动作**：`/ops/goods/audit-queue` 早就有，但没有任何接口能把 AUDITING 推向 APPROVED，而上架要求过审 → 商家录的商品**一件都上不了架** | 两个接口各自看都"正常工作" |
| 2 | **上架不进社区池**：C 端按社区查商品读的是 `prd_community_pool`，不是 `on_sale`。只改状态位的话，商家点了上架、B 端显示"在售"，**买家在任何地方都搜不到** | 与入驻那个「通过了却对谁都不可见」**同一个形状** |
| 3 | **B 端封面上传了不提交**：`GoodsDraft` 没有 `cover` 字段，店主选了图、页面上也显示，保存后 C 端拿到的是空封面 | 不报错，只是列表里一块留白 |
| 4 | **商品文案三语无处可存**：`prd_goods.title` 只有一列，英文/阿语提交完就丢 | 切到英文看到的还是中文 |

第 2 条是本轮最值得记的：**它和入驻那个缺口是同一个错误的第二次发生** ——
一个状态位改了，而真正决定可见性的那张关联表没跟着动。所以测试断言的不是接口返回，
而是「买家真的搜得到 / 下架后真的搜不到」。

### 几个刻意的取舍

- **改商品后回到待审核并强制下架**：不这样做，「上架白菜 → 过审 → 改成别的东西继续卖」是一条通路。代价是改错别字也要重审 —— 一期人工审核，这个代价由平台承担。
- **补货不触发重审**：每天都在做的事，走完整保存等于每次补货都重新过审。
- **拍照识别恒返回「没认出来」**（confidence=0）：一期没有视觉模型。契约本来就写着「低于阈值不预填」，返回 0 是这个设计里合法的一档，前端会正确降级；删掉接口反而会让那个页面 404。接上模型时只改一个方法。
- **图片落本地磁盘**（`shop.upload.dir`，默认 `./data/uploads`）：多实例部署会失效，**生产必须换对象存储**。之所以现在这样做，是没有 OSS 凭据时这条链路完全跑不通。换 OSS 时改 `BizUploadController` 一个类。
