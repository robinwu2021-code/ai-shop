## ⚠️ 实现过程中新发现的三处（都不在对齐清单的预期内）

### 🔴 A. `/mp/points/**` 三个端点是越权的

它们从**客户端请求头 `X-User-No`** 取用户号，而不是从鉴权 token。
而 `/mp/**` 在安全层是 `permitAll`（游客要能逛商品），两者叠在一起：

> **任何人不用登录，把别人的 userNo 填进请求头，就能读到他的积分余额与消费流水**
> （流水带子单号、商家、金额）。

同时它**从来没工作过** —— c-app 根本不发这个头，真实前端调过去是 400
（本次测试第一次调用它，撞出来的就是这个）。
**一个越权漏洞和一条断掉的链路，恰好长在同一行代码上。**

已改为从 `SecurityUtils.requireUser()` 取，与同一个模块里
`BizPointsController` 那条「商家号从 BizContext 取，不收 `X-Merchant-No` 头」
的既有规矩一致 —— 规矩本来就写在旁边，只是 C 端这三个没照做。

### 🟠 B. `OrderVO.Amount.of` 把积分三个字段写死成 0

VO 里有 `pointsDeductMinor` / `pointsUsed` / `pointsEarn`，
而唯一的工厂方法固定传 `0L, 0, 0` —— 于是**库里有值、VO 有字段、端上永远是 0**，
两侧代码单独看都对。又一个「有列没人填」。

已加带积分的重载；老工厂保留（预览等路径确实没有积分），但注释写明什么时候必须用新的。

### 🟠 C. 主单不汇总子单的积分

修好 B 之后子单显示对了，主单仍是 0 —— 而**收银台读的是主单**。
不汇总的话支付页显示未抵扣的价格，用户以为多扣了钱。已在 `payView` 汇总。

> B 和 C 都是**测试写出来才发现的**：先写断言「试算说 2988，实扣就得是 2988」，
> 然后一路追着 0 往上找。只写实现不写断言的话，这两处会一直是 0 而没人知道。

`营销域-方案Review.md` 的 F3 写着「积分设计 7 张表，库里只有 3 张，缺的四张全在商家侧与清分」。
**这条不准确**，逐条查证后的实际情况是：

- `pts_redeem_alloc`、批次相关字段是**设计里主动删掉的**（预付费模型下不需要按发放方拆分），
  不是漏建 —— 设计文档写得很清楚，我当时只对了表名没读正文
- `pts_user_ledger` **已经具备 USE 全流程需要的列**
  （`acceptor_merchant_no` / `amount_minor` / `rate_snapshot` / `status` / `period`），
  设计已经并进 `V1__baseline`
- 真正缺的是 `stl_points_bill`（清分账单）与商家侧配额

**但查证过程中发现一件更严重的**，见下。

## 1. 真正的现状：积分域一个写入者都没有

```
PointsServiceImpl 调用过的 mapper 方法（全部）：
    accountMapper.selectList / selectOne
    ledgerMapper.selectList
    poolMapper.selectList
    billMapper.selectList
```

**全是 select。** 全仓库搜不到任何一处往 `pts_user_ledger` 插入的代码。

也就是说，不只是「抵扣没接进下单」：

| 环节 | 状态 |
|---|---|
| 发放（`EARN`，支付后送分） | ❌ 没有任何代码写它 |
| 抵扣（`USE`，下单时扣分） | ❌ 没有 |
| 退回（`REFUND` / `REVOKE`） | ❌ 没有 |
| 到期清零（`EXPIRE`） | ❌ 没有 |
| 查询账户 / 流水 / 试算 | ✅ 有，且能正常返回 |

**所以积分余额恒为 0**：账户表永远空，`/mp/points/account` 返回 0，
`/mp/points/deductible` 基于 0 余额算出「可抵 0 元」。

这解释了为什么 F1 那个缺陷此前没人发现 —— **它显示的确实是 0，而 0 是对的**。
用户看不到假承诺，是因为整条链路空转。等哪天补上发放，
抵扣不接的问题会立刻变成「有分花不掉」。

> **对排期的影响**：F1 不是「接一个方法」，是**把积分域从只读脚手架变成能记账的域**。
> 发放不做，抵扣做了也没有分可抵。两者必须同批。

## 4. 对齐清单 · 第三层：对象（实体 / VO / DTO）

| 对象 | 现状 | 缺口 |

| `PointAccountVO` · `PointRecordVO` · `PointsDeductibleVO` | ✅ | 无 |
| `OrderVO.pointsDeductMinor` | ✅ 已暴露 | 无（终于会有非 0 值）|
| **下单入参 DTO** | ⚠️ 无 `usePoints` | ➕ 加字段 |
| **`PointsPort`（SPI）** | ❌ 不存在 | ➕ **必须新增** |

### 4.1 为什么必须有 `PointsPort`

积分在 `shop-settle`，下单在 `shop-core/trade`。
`shop-core` **不能直接依赖 `shop-settle`** —— 现有的
`CouponPort` / `CampaignPort` / `SettlePort` 就是这个约束的产物。

`PointsPort` 要放在 `shop-base/spi/points/`，实现放 `shop-settle/port/`，
形状对齐现有的 `CouponPort.Allocation`：

```
PointsPort
  Deduction deduct(userNo, usePoints, merchantAmounts, payableAfterCouponMinor)
  void      reverse(subOrderNo, kind)
  record Deduction(long points, long amountMinor, Map<merchantNo, amountMinor> byMerchant)
```

**多商家分摊必须在这一层出结果**，与 `CouponPort.Allocation` 同一形状 ——
一单跨商家时，抵扣要落到各自的子单上，否则结算无从拆分。

## 5. 对齐清单 · 第四层：Controller / Service / Mapper

| 层 | 类 | 现状 | 本批要做 |
|---|---|---|---|
| Controller | `MpPointsController` | ✅ 3 条只读 | 不动 |
| Controller | `MpOrderController`（下单） | ✅ | 透传 `usePoints` |
| Service | `PointsService` | ⚠️ **只有读** | ➕ `deductOnPlace` ➕ `grantOnPay` ➕ `reverse` |
| Service | `OrderServiceImpl` | ✅ | ➕ 算价链路接 `PointsPort`，**券后、运费外** |
| Port | `PointsPort` + `PointsPortImpl` | ❌ | ➕ 新增 |
| Mapper | `PointsAccountMapper` | ✅ `BaseMapper` | ➕ **带乐观锁的扣减 SQL**（见下）|
| Mapper | `PointsLedgerMapper` | ✅ `BaseMapper` | 插入用 `BaseMapper.insert` 即可 |

### 5.1 Mapper 唯一需要手写 SQL 的地方

扣减余额必须**一条 UPDATE 带条件**，不能「查出来再写回去」：

```sql
UPDATE pts_user_account
   SET balance = balance - #{points},
       total_use = total_use + #{points},
       last_active_at = #{now}, expire_at = #{newExpire},
       version = version + 1
 WHERE user_no = #{userNo} AND market = #{market}
   AND deleted = 0 AND balance >= #{points}
```

`balance >= points` 那个条件就是并发闸 —— 与 `CouponMappers.tryReceive`
挡超发是同一手法。影响行数为 0 即余额不足，直接拒绝下单。

**不要用 `BaseMapper.updateById` + 先查后写**：两个请求同时下单会双花。

## 6. 本批做什么 / 不做什么

### 做

1. `PointsPort` SPI + 实现
2. `PointsService.deductOnPlace`（下单扣分，落 `USE` / `PENDING`）
3. `PointsService.grantOnPay`（支付后发分，落 `EARN`）—— **不做的话没有分可抵**
4. `PointsService.reverse`（取消 / 退款回退）
5. 下单算价接入：**券先抵、积分后抵、运费不参与**
6. 下单入参 `usePoints` 三端贯通
7. 测试

### 不做（明确登记，不是遗漏）

| 不做 | 为什么 |
|---|---|
| `confirmUseOnActivate` 兑付成立与出池 | 属结算域，且依赖售后期结束的触发点。本批只落 `PENDING` |
| `stl_points_bill` 清分账单 | 同上 |
| `/ops/points/**` 4 条 | 平台端积分管理，登记进 `KNOWN_GAPS` |
| 商家积分配额 | 一期自营模式下无消费方 |
| `expireDaily` 到期清零 | 独立定时任务，与抵扣正交 |

> **`PENDING` 一直挂着不 `CONFIRMED` 会不会出问题**：不会。
> 池子没付钱、账没做实，只是用户的分已经扣了。
> 但要在 `PointsService` 的注释里写明这是**本批的已知边界**，
> 否则下一个人会以为兑付链路已经通了。

## 7. 开发前还要确认的

### 7.1 已经有答案的（查证结果，不用你回答）

`packages/shared/src/utils/constants` 里 **`POINTS` 常量已经定好了**：

| 项 | 值 | 出处 |
|---|---|---|
| 抵扣汇率 | `perMinor: 1` —— 1 积分抵 1 分钱（100 分 = 1 元） | shared 常量 |
| 抵扣上限比例 | `maxDeductRatio: 0.3` | shared 常量，与 `ord_sub_order` 注释的 30% 一致 |
| 到期规则 | 滚动到期（任何变动推后到期日） | shared 常量 + 库表列 |
| C 端是否有 UI | ✅ 有，`FEATURES.points = false` 关着 | `order-confirm/index.vue` |

⚠️ **但这三个值只存在于前端**。后端要用它们，有两条路：

| 方案 | 结论 |
|---|---|
| **A（推荐）落 `sys_setting`，后端读配置，前端也改读接口** | ✅ 汇率与上限是运营要调的东西，写死在前端常量里等于「改汇率要发版」 |
| B 后端加一份同值常量 | ❌ **两份常量必然分叉** —— 今晚刚在 `discountFor` 上修过一次万分比 vs 百分数，代价是「优惠为负，等于加价」 |

若选 A，本批要加：`GET /mp/points/config`（或并进现有 `deductible` 返回），
以及一条守卫断言前后端取值一致（在两边都收敛到接口之前，守卫是唯一的保险）。

## 8. 影响范围与风险

- **会修改已测试通过的下单算价**（`OrderServiceImpl` 的 `Discounts`）。
  按 P6 需要你确认。现有订单测试必须全部重跑。
- 积分扣减是**资金语义**：并发双花、退款不回退、试算与实扣口径不一致，
  三种都会直接变成用户投诉。测试要覆盖这三条。
- 本批只落 `PENDING`，**账面上会积累一批未兑付的使用记录**。
  这在没有第三方商家时不影响任何人拿钱，但要写进文档，不能默默留着。
