## 1. 差距比「补三个端点」大

前端 IAM 页那三个控件是死的，登记在 `KNOWN_GAPS` 里。但逐层对下来，
**缺的不只是端点** —— `enabled` 和 `role` 后端有落点，`scope` 从表到 VO 一路不存在：

| 前端要的 | 后端表 | 后端 VO | 后端端点 |
|---|---|---|---|
| 启停 `enabled` | ✅ `status`（ACTIVE/…） | ✅ `status` | ❌ |
| 改角色 `role` | ✅ `roles` | ✅ `roles` | ❌ |
| **数据域 `merchantNo/communityNo/pickupNo`** | ❌ **三列都没有** | ❌ | ❌ |

`sys_ops_staff` 只有 `staff_no / username / password / real_name / roles / status`
加通用列 —— **数据域一列都没有**。

而矩阵 §2.3 写得很明确：

> 权限模型：**RBAC + 数据域**（`tenant_no=MAIN` / `merchant_no` / `community_no` / `pickup_no`）。
> 所有角色的数据可见性由归属键裁剪，**不靠前端隐藏**。

也就是说：**「数据域」这半个权限模型，后端从来没有过**。
BD 应该只看到自己负责的商家、社区运营只看自己的社区 —— 现在他们看到全量。
今晚补的七个角色配置解决的是「能做什么」，这一条是「能碰谁的数据」，
是[授权二维正交](../archive/运营端权限对齐方案.md)的另一维。

> ⚠️ 这不是本任务发现的新缺陷，`ops-web/lib/auth.ts` 里的 `scopeOf()` 一直带着
> 数据域往后端发，注释还写着「**越权拦截以后端为准**」——
> 而后端根本没有这个概念，那句注释描述的是一个不存在的保护。

## 2. 对齐清单

### 2.1 数据库

| 表 | 现状 | 需要 |
|---|---|---|
| `sys_ops_staff` | 无数据域列 | ➕ `merchant_no` / `community_no` / `pickup_no`，均可空 |

**一张迁移，三列，都可空**。可空是语义的一部分：**空 = 不限定（全量）**，
不是「还没配」—— 超管、商品运营本来就该是全量。

迁移号按并行协议取 **V60**（对方在 V36–V59 区间）。

### 2.2 API

| 端点 | 入参 | 权限 |
|---|---|---|
| `POST /ops/staffs/{no}/enabled` | `{enabled: boolean}` | `staff:manage` |
| `POST /ops/staffs/{no}/role` | `{role: string}` | `staff:manage` |
| `POST /ops/staffs/{no}/scope` | `{merchantNo?, communityNo?, pickupNo?}` | `staff:manage` |

三条都返回更新后的 `StaffVO`（前端拿它就地刷新那一行，不用重拉列表）。
路径与入参**照抄 ops-web 现有调用**，不另起一套。

### 2.3 对象

| 对象 | 改动 |
|---|---|
| `SysOpsStaff` 实体 | ➕ 三个字段 |
| `StaffVO` | ➕ `merchantNo` / `communityNo` / `pickupNo` / `lastLoginAt` |

⚠️ `StaffVO` 是 `LoginResultVO` 与 `/ops/auth/me` 的返回体，**加字段会同时改登录响应** ——
这是好事（前端本来就要知道自己的数据域），但 ops-web 的登录映射要同步读。

### 2.4 Controller / Service / Mapper

| 层 | 改动 |
|---|---|
| `OpsPlatformController` | ➕ 三个端点 + `@PreAuthorize(staff:manage)` + 审计留痕 |
| `OpsService` | ➕ `setStaffEnabled` / `setStaffRole` / `setStaffScope` |
| Mapper | `BaseMapper.updateById` 够用 —— 员工配置没有并发争抢 |

## 3. 三条必须有的校验

1. **改角色时校验角色码存在于 `Perms.ROLE_PERMS`**
   —— 否则会造出一个 perms 为空的账号：能登录、导航全空、看不出原因。
   今晚刚给 ops-web 修过同一个形状的问题（`can()` 遇到未登记的码静默判 false）。

2. **不能停用/降级自己**
   —— 超管把自己停了就没人能改回来了。这类「把自己锁在门外」的操作，
   拦住的成本远低于事后恢复。

3. **给全量角色配数据域 → 拒绝**
   —— ops-web 的契约注释已经写明「会让人以为它被限制了，实际没有」。
   后端要真的拒，而不是存下来假装生效。

三条都要带审计留痕（`auditLogPort.record`）：**改权限是最需要追溯的一类操作**。

## 4. 做什么 / 不做什么

### 做
1. V60 迁移三列
2. 实体 + VO 加字段
3. 三个端点 + 三条校验 + 审计
4. 从 `KNOWN_GAPS` 删掉这三条（棘轮：接通的要移出）
5. ops-web 登录映射读新字段
6. 测试

### 不做（明确登记）

| 不做 | 为什么 |
|---|---|
| **让数据域真正生效**（各域查询按它裁剪） | 那是几十处查询的改造，且每一处漏改都是越权。**单独一批**，不能混在补端点里 |
| `/ops/roles/**` 角色权限配置 | 后端权限硬编码在 `Perms.java`，改要发版（M9b 才接 DB）。UI 已标 `UNIMPLEMENTED` |
| 新建员工 / 改密码 | ops-web 没有这两个入口，补了没有消费方 |

> ⚠️ **这一批只是把数据域存下来，不等于它生效了。**
> 存了不用比不存更危险 —— 运营会以为「我给 BD 限定了商家」，而他照样看到全量。
> 所以要么同批做裁剪，要么**在 UI 上标明「配置已保存，裁剪尚未生效」**。
> **这是要你定的第一件事。**
