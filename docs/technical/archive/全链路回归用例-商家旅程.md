# 全链路回归用例 · 一个商家的完整旅程

> 2026-08-10 · 浏览器实测，连真后端与真实库（`ai_shop`），不使用 mock。
> 场景取自一家真实小店的开店到经营，而不是按接口逐个点。

---

## 0. 为什么按「一个商家的旅程」而不是按模块

这一轮所有被发现的缺陷都有同一个形状：**单看任何一端都是完整的，
断在两端之间**。

| 缺陷 | 单端看 | 链路上看 |
|---|---|---|
| 满减建了不生效 | 活动能建、状态正常 | 下单一分不减 |
| 店铺券建了领不到 | 活动存下来了 | 领券中心没有它 |
| 类目授权 | 授权写成功了 | 上架仍被拒 |
| 订单状态 | 接口 200 | 「待取货」页签永远空 |

按模块测永远测不到接缝。所以用例按**一个人做完一整件事**来编排。

## 3. 贯穿始终的三条检查

每打开一个页面都查，不单列为用例：

1. **无 i18n 键名泄漏** —— 页面上不出现 `xxx.YYY` 形态的字符串。
   这个形状本轮出现过四次，且四层测试全绿。
2. **无「接口 200 但页面空」** —— 列表有数据时必须渲染出来。
3. **金额一致** —— 页面显示的应付 = 提交后的实付。

**D5 的金额链**（今天接的四段营销一次跑通）：

```
6 × ¥9.90 = ¥59.40   （限时特价，原价 ¥12.80）
      -¥8.00          （满减，59.40 ≥ 50）
      -¥5.00          （店铺券，51.40 ≥ 30）
   = ¥46.40 应付
   + 赠品 ×3 独立行，价格 0，不参与计价（买 2 送 1）
```

## 发现的缺陷（5 个，均未修，按严重度排）

| # | 现象 | 形状 |
|---|---|---|
| 1 | b-app 新建商品页把品类显示成 `NORMAL/FRESH/SERVICE/VIRTUAL/CARD` | **原始枚举码给用户看**；b-app 完全没有品类词条 |
| 2 | ops-web 入驻审核列表把行业/主体显示成 `RETAIL`/`INDIVIDUAL` | 同上；且 ops-web **完全没接** `/common/master-data`，而后端一直在下发中文名 |
| 3 | 未过审商品点「上架」，报「**订单状态不允许该操作**」 | 交易域的错误码 `ORDER_STATE_ILLEGAL` 用在商品规则上。规则本身是对的，错在错误码 |
| 4 | 多规格商品建限时特价被拒，提示是「请求参数有误」 | 商家看不出原因，只会反复改参数 |
| 5 | **BD 角色无法完成入驻审核** | 审核前必须选覆盖社区，而 `/ops/communities` 由 `INDUSTRY_MANAGE` 守着，那个权限**明确注明不给 BD**。换 admin 才能走完 |

第 5 个最严重：**一个角色被要求做一件他没权限做的事**，招商日常流程直接卡死。
根因是读写权限没分开 —— `INDUSTRY_MANAGE` 同时管「维护主数据」和「读列表」。

第 1、2 个是同一形状：**该翻译的没翻译**。与本轮反复出现的「i18n 键原样打给用户」
是一枚硬币的两面 —— 那个是有词条没对上，这个是压根没词条。

第 3、4 个也是同一形状：**错误码/错误信息与实际业务无关**。
讽刺的是第 3 个那段代码紧挨着的下一个方法，注释里正好写着
「报一个专用错误码……通用的『请求参数有误』会让商家反复改商品信息，
而问题根本不在商品上」—— 道理想明白了，用在了类目那处，漏了紧挨着的上一处。

## 两次「以为是 bug，其实是我错了」

· C 端搜不到新商品 → 我用了测试代码里的假社区号 `CM001`，真实是 `C0001`
· 订单列表空 → 我注入 token 前页面已经请求过，是缓存不是缺陷

记下来是因为：**排查时先怀疑自己的输入，比先怀疑代码更省时间。**
