# 全系统枚举：统一预定义方案

> 2026-08-10 · 上一份《枚举统一方案》只处理了反复出事的六个。
> 这一份是全量盘点 + 机制设计：**让「端上自己编一套词」这件事在结构上不可能发生**。

## 1. 清点结果（实测，非估算）

| 位置 | 数量 |
|---|---|
| shared | 46（联合类型 25 · 常量对象 4 · **内联无主 17**） |
| ops-web | 68（联合类型 65 · **内联无主 3**） |
| c-app / b-app 的 api 层 | 7（**内联无主 4**） |
| **端上合计** | **121，其中 24 个没有具名声明** |
| 后端 Java 常量组（≥2 个 `static final String`） | 52 组 / 245 个值 |
| 后端真正的 Java `enum` 类型 | **2 个**（`Realm`、`ErrorCode`） |
| 库列注释里写了取值域的列 | 51 列 |
| 运营可维护的字典表 `sys_*` | 10 张，配 9 个下发接口 |

### 1.1 两端同名的只有 10 个，其中 8 个取值不一致

| 名字 | shared | ops-web | 判定 |
|---|---|---|---|
| `OrderStatus` | 一致 | 一致 | 纯重复声明 |
| `AfterSaleStatus` | 一致 | 一致 | 纯重复声明 |
| `SubjectType` | `MICRO`/`INDIVIDUAL`/`ENTERPRISE` | `USER`/`MERCHANT`/`DEVICE` | **重名不同物** |
| `MerchantTier` | `SMALL`/`MEDIUM`/`LARGE`（规模） | `PERSONAL`/`INDIVIDUAL`/`COMPANY`（主体类型） | **重名不同物** |
| `ApplyStatus` | `NONE`/`APPLYING`/`ACTIVE`/`REJECTED`/`FROZEN` | `PENDING`/`REVIEWING`/`APPROVED`/`REJECTED` | **重名不同物** |
| `MerchantStatus` | 合并视图 | 库口径 | 有意分层（已文档化） |
| `CampaignType` | 店铺活动 | 平台场次 | 有意分层（已文档化） |
| `CampaignStatus` | 有 `PAUSED` | 有 `SCHEDULED` | 待合并 |
| `AfterSaleType` | 2 个 | 多 `EXCHANGE` | 一期不做换货 |
| `PayChannel` | 2 个 | 多 `BALANCE` | 后端未实现 |

**`MerchantTier` / `SubjectType` 是三方错位**：ops-web 的 `tier` 里装的正是
shared 的 `SubjectType` 那件事，而 ops-web 的 `SubjectType` 是风控主体，
与商家主体毫无关系。同一个词在两端指两样东西，同一件事在两端用两个词 —— 同时发生。

### 1.2 按「后端认不认识」分三类

| 类别 | 数量 | 含义 |
|---|---|---|
| 全部值后端都有 | 33 | 大概率是 wire 契约 |
| 部分命中 | 29 | 有真差异，或后端部分未实现 |
| 一个都不命中 | 9 | 纯端上概念 **或** 整块还没接后端 |

> 最后 9 个里，`Market`/`MaterialKind` 是真·端上概念，
> 而 `RiskType`/`ReconDiffType`/`Carrier` 是**整块业务还没接后端**。
> 现在这两种混在一个桶里，工具没法区别对待 —— 这本身就是要解决的问题之一。

## 2. 诊断：为什么会长成这样

不是有人偷懒。是**三个结构性原因**：

1. **没有「先去哪里查」的地方。** 要用一个状态时，最快的路径是在自己这一端
   新写一个联合类型。查后端要翻 Java 实体类、查库要翻 V1 建表语句 ——
   两者都不在写页面的人手边。
2. **端上跑 mock。** mock 说什么就是什么，永远不会被真实响应打脸。
   ops-web 独有 55 个枚举，绝大多数从没见过真后端。
3. **文案与取值分离。** i18n 词条按端上的叫法建，取值按后端的下发。
   两者只在渲染那一刻才相遇 —— 而不匹配时不报错，回退成键名。

三条合起来：**写错的成本为零，发现的成本极高。**
这轮六个 bug 全部是浏览器点开页面才发现的，没有一个是被四层测试发现的。

---

## 3. 核心判断：不是一套机制，是三类枚举

> 想用一套「统一枚举中心」装下 121 个，会在第一天就失败 ——
> 因为它们的**真源根本不在同一个地方**，变更节奏也不同。

| 类 | 是什么 | 真源 | 变更节奏 | 谁能改 |
|---|---|---|---|---|
| **A 契约枚举** | 后端会下发/接受的值：订单状态、履约、五品类、支付渠道 | **后端代码**（Java 常量 / DDL） | 随版本发布 | 研发 |
| **B 字典枚举** | 类目、售后原因、行业、资质码、平台配置 | **库表 `sys_*` / 业务表** | 随时，运营自助 | 运营 |
| **C 端上枚举** | 皮肤、语言、展示分区、物料形态、页面步骤 | **端上代码** | 随端发布 | 前端 |

三类的治法完全不同：

- **A 必须单向生成** —— 后端是真源，端上不得手写。手写就会漂。
- **B 必须运行期下发** —— 编译进代码就等于运营改不了，
  改了还要发版；而「发版才能加一个售后原因」必然导致有人直接写死在端上。
- **C 不参与对账** —— 但必须**显式声明**它是 C 类，否则它和「还没接后端的 A 类」
  长得一模一样（现在就是这样，见 §1.2）。

**当前的错配**（这是要修的核心）：

| 现象 | 数量 | 问题 |
|---|---|---|
| A 类被端上手写了一遍 | ~33 + 部分命中的 | 双真源，必然漂移 |
| B 类被硬编码进端上 | 待逐个核（如售后原因曾硬编码） | 运营改了端上不认 |
| C 类没有标记 | 9 个混在一起 | 工具无法区别对待 |
| 无具名声明 | **24 个内联** | 扫不到、拦不住、复用不了 |

## 4. 方案

### 4.1 A 类：一份注册表 + 单向生成

新建 `packages/shared/src/contract/enum-registry.ts`，**它不是真源，是「真源在哪」的索引**：

```ts
export const ENUM_REGISTRY = {
  OrderStatus: {
    field: "ord_sub_order.status → OrderStatusView",   // 对应哪个 wire 字段
    source: { javaConst: "…/trade/service/OrderStatusView.java" },
    owner: "trade",                                     // 归属域
    status: "LIVE",                                     // LIVE | PLANNED | DEPRECATED
    consumers: ["c-app", "b-app", "ops-web"],
    labels: true,                                       // 需要 i18n 文案
  },
  …
};
```

为什么**不**让注册表自己当真源：会变成第二个真源。
已定的规则是「库/后端是 wire 值的唯一真源」（《枚举统一方案》§3 规则 1），
注册表只声明对应关系 —— 那部分信息确实只存在于人脑，必须写下来。

从注册表生成四样东西（复用项目已有的 12 个 `gen:*` 脚本的做法）：

| 产物 | 给谁 | 替代现在的什么 |
|---|---|---|
| `packages/shared/src/contract/enums.generated.ts` | c-app / b-app | 手写的联合类型 |
| `ops-web/lib/types/contract-enums.generated.ts` | ops-web | 手写的 65 个联合类型里属于 A 类的那些 |
| i18n 词条**骨架**（缺哪个值报哪个） | 三端 | 「词条按端上的叫法建」这个错误来源 |
| `check-enum-fields.mjs` 的 `FIELDS` 表 | 守卫 | 现在手写的那张表 |

生成物**入库并提交**（不是 build 期产物）：
diff 可见，评审时能看到「这次发布多了一个订单状态」。

`status: "PLANNED"` 的处理是关键：后端未实现的取值**照常生成类型**，
但生成的是一个单独的 `PLANNED_*` 白名单（`FULFILLMENT`/`PLANNED_FULFILLMENTS`
已经验证过这个手法）。对账工具据此区别对待 —— 同物异名必须报，
后端未实现是待办不是缺陷。

### 4.2 B 类：字典下发，端上零硬编码

机制**已经存在**（10 张 `sys_*` 表 + 9 个接口），缺的是三件事：

1. **统一下发端点** `GET /dict/{code}`，一次拿一类，带 ETag。
   现在是每类各一个路径（`/mp/after-sale/reasons`、`/mp/category/tree`、
   `/ops/industries`…），端上每接一个都要新写一遍请求与缓存。
2. **端上统一取用** `useDict("AFTER_SALE_REASON")`，内置缓存与兜底。
3. **一条守卫**：B 类的取值**不允许**出现在端上代码的字面量里。
   这条能自动查 —— 注册表里标了 `kind: "DICT"` 的，扫端上源码，命中即报。

> 为什么第 3 条必须有：售后原因这轮就是「端上硬编码一份、后端一份」，
> 而运营改的是后端那份。没有守卫，下一个字典还会这样。

**文案归属**：字典的文案跟着字典下发（后端已在做，下发的是**码**，
端上按当前语言翻译）—— 但翻译表也得跟着数据走，否则运营加一条新原因，
端上没有词条，又回退成键名。建议下发时带上多语文案，端上词条只作兜底。

### 4.3 C 类：显式声明，退出对账

在注册表里登记为 `kind: "CLIENT"` 并写明理由（沿用 `check-enums.mjs`
里 `CLIENT_ONLY` 的做法，那张表已经在用，每条都要求写为什么）。

**同时要区分出「还没接后端」** —— 那不是 C 类，是 `status: "PLANNED"` 的 A 类。
§1.2 里 9 个全不命中的枚举，必须逐个判定归哪边。这一步只能人做。

### 4.4 24 个内联无主：一律具名

规则已定（《枚举统一方案》§3 规则 3：禁止在 interface 里内联字面量），
缺的是执行与守卫。加一条 lint 级检查：`interface` 内的字面量联合类型
若全部是大写标识符，即报错，要求提取成具名类型。

## 5. 「提供给业务使用」的三个出口

| 出口 | 形态 | 解决什么 |
|---|---|---|
| **给业务代码** | 生成的类型/常量 + 统一的 `labelOf(enum, value)` | 取文案不再各写各的，缺词条在编译期就报 |
| **给运营** | ops-web 上一个只读的**枚举总览页**，从注册表生成 | 现在「这个状态什么意思」的知识只在代码注释里，运营查不到 |
| **给文档** | `项目词典.md` 由注册表生成，不再手写 | 这轮它已经漂了两次（`GOODS`、`AGREED` 系列），手写必漂 |

第二个出口值得单说：运营在裁决售后、处理工单时要判断状态含义，
现在只能问研发。把注册表里的语义注释渲染成一页，是零成本的副产品。

## 6. 分批推进（121 个不可能一次做完）

| 批次 | 范围 | 判据 |
|---|---|---|
| **P0** | 注册表骨架 + 生成器 + 已对齐的 8 个字段接进去 | 生成物与现有手写类型**逐字节一致**，才算生成器可信 |
| **P1** | 24 个内联无主具名化 + lint 守卫 | 纯机械，无行为变化 |
| **P2** | §1.2 那 9 个逐个判定 A/C，标进注册表 | 需要人判断，无法自动 |
| **P3** | 三方错位的 `MerchantTier`/`SubjectType`/`ApplyStatus` 改名 | **有行为风险**，要浏览器实测 |
| **P4** | B 类字典：统一 `/dict/{code}` + `useDict` + 硬编码守卫 | 后端改动最大的一批 |
| **P5** | ops-web 55 个独有枚举逐个归类 | 量最大，但多数是 PLANNED，机械 |

**每批的验收都要包含浏览器实测。** 这一轮的六个 bug 与那个 join 键错误，
没有一个是被四层测试发现的 —— 这个事实是验收方式的一部分，不是偶然。

---

## 7. 明确不做的

- **不做「枚举中心」服务。** A 类随代码发布，走生成而不是走网络；
  为编译期的东西加一次运行时依赖，是拿可用性换整洁。
- **不强行统一 B 类到代码里。** 运营能自助维护是它的价值，编译进去等于废掉。
- **不合并有意分层的那些**（`MerchantStatus`、`CampaignType`）——
  强行统一会毁掉分层，这条上一份方案已经论证过，且已有测试守着。

## 8. 需要确认的

1. **ops-web 那 55 个独有枚举，有多少对应的后端功能会真的做？**
   若大部分不做，P5 就不是「归类」而是「删」。
2. **B 类字典要不要带多语文案下发？** 不带的话运营新增一条，端上就是键名；
   带的话运营要维护翻译，需要一个录入界面。
3. **生成物提交进仓库，还是 build 期产出？** 我倾向提交（diff 可见），
   但会增加「忘了重新生成」的可能 —— 需要一条 CI 检查兜底。
