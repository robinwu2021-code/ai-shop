## 先更正一条：我上一轮判错了

[契约漂移清单](../api/契约漂移清单.md) 把「我的券」列为「同功能异路径」（`/mp/coupon` vs `/mp/coupon/mine`），
**这是错的**。实际是两个不同的东西：

```java
@GetMapping("/mp/coupon")       // 领券中心。游客也能看 —— 看到有券才有注册动机
@GetMapping("/mp/coupon/mine")  // 我领过的券
```

而 c-app 的券页是**一页两 tab**（领券中心 / 我的券），却只调了 `couponList()` 一个接口，
在端上用 `c.received` 布尔字段自己切分：

```ts
const available = computed(() => coupons.value.filter((c) => !c.received && ...));
const mine      = computed(() => coupons.value.filter((c) => c.received));
```

**这不是路径分歧，是前端少调一个接口**，且现在的做法有实际问题：领券中心要对游客开放，
而「我的券」必须登录 —— 一个接口承担两种鉴权要求，游客态要么拿不到券中心，要么泄露他人券。

**方案（无需拍板，属修正）**：c-app 增调 `/mp/coupon/mine`，`couponList` 保持为领券中心。
两 tab 各取各的数据源，鉴权边界随之干净。→ 记为 **T-C6**，并入 P0 批次。

### 方案

| | 做法 | 代价 | 后果 |
|---|---|---|---|

### ~~推荐：A（建表）~~ → **已定：二期，一期不上**

<details><summary>原推荐（建表）的分析</summary>

**A（建表）**

理由不是「功能全一点好」，而是**次卡是社区服务商家的主要收款形式**。理发店卖 10 次卡、

余额直接 UPDATE 的设计，对不平账时无从追溯。

> 这一条会让 D-1 的工作量从「一张表」变成「两张表」。仍然推荐 —— 涉及用户预付的钱，
> 没有流水的余额是不可接受的。

</details>

**落地（已做）**：加 `FEATURES.cards = false`，「我的」页卡包入口按开关隐藏（与积分同做法）。

> 决策本身也印证了上面的分析：储值余额与积分是同一类问题（都是平台负债），
> 一起做比分开做省事 —— 二期范围把它们放在一起是对的。

## D-2　结算：账单粒度 vs 明细粒度（原 T-10）

### 事实

- 库 `stl_bill`：**一个子订单一条**（`sub_order_no` + gross / commission / net）→ 这是**分账明细**
- 契约 `SettleBill`：**一个商家一个周期一张**（`periodStart` / `periodEnd` / `orderCount`）→ 这是**账单**

两者不是同一个东西，名字却撞了。

### 推荐：**A（新增周期账单表，`stl_bill` 降为明细并改名 `stl_split_detail`）**

与工单里的推荐一致，补充两条理由：

1. **开票按周期走。** 平台端 P-12.2.2 开票申请就是按 `period` 的，明细粒度撑不起
2. **分账与结算是两件事。** 分账是「这一单的钱怎么分」（微信侧实时发生，见 ADR-002），
   结算是「这个周期该打给商家多少」（平台侧周期汇总）。一张表承担两种粒度，
   将来对账出现差异时分不清是哪一层的问题

改名有代价（碰已有列/表名），但**现在改比以后改便宜** —— 结算侧后端只实现了 3 条接口。

## D-3　售后请求体：`refundMinor` 与 `reasonCode`（原 T-13 第 2 条）

### 事实

后端已支持部分退款，且**默认全额**：

```java
long refund = cmd.refundMinor() == null || cmd.refundMinor() <= 0 ? paid : cmd.refundMinor();
```

前端发的是 `reason`（拼好的文案）+ `reasonCode`（结构化枚举），**不发金额**。
后端 `/mp/after-sale/reasons` 返回 `List<String>` —— 纯文案，没有 code。

### 推荐：**退款金额由服务端算，`refundMinor` 从 C 端请求体移除；`reasonCode` 后端补上**

两个方向各有明确理由：

**`refundMinor` 不该由买家传。** 客户端传金额是**改价面** —— 前端传 999999 而服务端照收，
就是资损。后端现在的 `null → paid` 兜底已经是对的，把入口彻底关掉更干净：
C 端申请一律全额，**部分退款是商家/平台侧的动作**（B 端同意时可以改额、平台裁决时可以定额），
不是买家申请时能自己填的东西。

**`reasonCode` 后端要收。** 结构化原因是风控与统计的依据（「哪个商家的破损率高」
靠自由文本统计不出来）。同时 `/mp/after-sale/reasons` 应返回 `{code, label}` 而不是纯 `String` ——
现在返回纯文案，前端拿到也没法回传 code，这个接口等于半残。

落地：后端 `ApplyCommand` 去掉 `refundMinor`、加 `reasonCode`；
`AfterSaleService.reasons()` 返回 code+label；`OrdAfterSale` 加 `reason_code` 列（新迁移）。

## D-4　求团单收哪些字段（原 T-13 第 3 条）

### 事实

| | 字段 |
|---|---|
| 前端 `CreateRequestReq` | `pickupNo`、`title`、`desc`、`expectQty`、`budgetMinor?` |
| 后端 `CreateRequestReq` | `title`、`description`、`images`、`expectCount?`、`days?` |
| c-app 表单**实际收集** | title、desc、budget（`images` 与 `days` 没有输入控件） |

三者都不一样。**且库里 T-3 已经把 `pickup_no` / `budget_minor` 加进去了。**

### 推荐：**取并集，但 `days` 给默认值不做输入**

| 字段 | 去留 | 理由 |
|---|---|---|
| `pickupNo` | **必填** | 成团单位是自提点（ADR-005）。缺了它，求团单不知道该推给哪个小区的商家 —— 这是最不能省的一个 |
| `title` / `desc` | 必填 | 两边都有 |
| `expectQty` / `expectCount` | 保留，**统一名字为 `expectQty`** | 契约口径 |
| `budgetMinor` | 选填 | 「填了商家报价更有的放矢」，且库已有列 |
| `images` | **加到前端** | 求团的是床垫、校服这类**说不清的东西**，图比文字有用。后端已支持，前端补输入即可 |
| `days` | **保留但不做输入**，服务端默认 7 天 | 让发起人填「几天内有效」是给他出难题 —— 他不知道该填几天。默认 7 天，到期自动关闭 |

这条**需要产品确认 `images` 与 `days` 的处置**，其余可直接落。

## D-5　`verifyCode` / `redeemCode` 收敛（原 T-16）

### 事实

库 `verify_code` **一列承载三态**（自提码 / 核销码 / 兑换码），V6 注释写明是刻意设计。
契约却有两个字段指向同一个值。

不是三个数据）。这一层 c-app 已经有 i18n 键，改起来是文案映射，不是逻辑。

## D-6　自提点：承接方式与计费口径（原 T-17）✅ 已定

### 事实

`cmt_pickup_point` 同时有 `service_fee_rate`（费率）与 `service_fee_per_item_minor`（按件）。
**这是刻意保留的** —— R15 口径未定。

### 决策（2026-08-06）

自提点分两种承接方式：

- **商家自行解决** —— 用自己的门店，平台不收履约服务费
- **平台提供** —— **费率线下逐点协商，通过运营平台录入**

### 我原来的推荐被这条信息推翻了

我之前推荐「统一按件、删掉 `service_fee_rate`」，依据是分拣工作量与件数成正比而与金额无关。
那个依据没错，但**前提错了** —— 我当时假定费率是平台统一定的。

既然是**逐点线下谈**，就必然出现有的点谈成按件、有的谈成按成交额抽成。
硬统一成一种，运营在谈判桌上就没有筹码了。**两列都要留。**

但两列并存**没有判别列**是明确的 bug：结算侧只能猜用哪一个，猜错就是给自提点少付或多付钱。

### 落地（已做）

| | 改动 |
|---|---|
| 契约 | `PickupPoint.type` 从 `STORE\|NEIGHBOR` 扩到 **`STORE\|NEIGHBOR\|PLATFORM`**；`ownerType` 同步加 `PLATFORM`；新增 **`feeMode: NONE\|PER_ITEM\|RATE`**；`serviceFeeRate` 补进契约（原先只有按件那一个） |
| 库 | `V18__pickup_fee_mode.sql`：加 `fee_mode` 列，`type` 与 `owner_ref` 的注释扩到三档 |
| 规则 | `STORE` 与 `NEIGHBOR` 恒为 `feeMode=NONE`、两个费用字段恒为 0。**`NEIGHBOR` 零报酬是硬规则**（ADR-005）—— 有报酬那个邻居就是团长，ADR-004 消掉的合规问题全部回来 |

**待补**：运营平台需要「自提点费率录入」界面（平台端 `fulfillment` 模块，15 条待实现里的一条）。
在它做出来之前，平台自提点的费率只能靠直接改库 —— 这是本决策留下的唯一缺口。

## D-7　金额列命名统一（原 T-11）

### 事实

三方各一套：`ord_*` 用 `xxx_amount`，`mkt_*`/`stl_*` 用 `xxx_minor`，契约统一 `xxxMinor`。

### 推荐：**统一到 `_minor`，但排在所有实现任务之后**

**但现在别做。** 它要碰 `ord_order` / `ord_sub_order` / `ord_item` 的列名，
而这三张表正是接下来 C 端 18 条 + B 端 35 条要密集改的地方。
先改名会让所有在途工作都撞上；等实现落地后一次改完，`COLUMN_ALIAS` 里那 5 条别名同时删掉。

## 二期范围（2026-08-06 定）

**积分 · 卡包 · 工单 · 在线客服。**

四者的共同点不是"不重要"，而是**都涉及一套一期还没有的底座**：
积分与卡包是平台负债（要资金级建模与对账），工单与客服是人工处理流程（要有人在线）。
一期先把「买卖能成、钱能结」跑通，这四块二期一起上。

代码处置统一为：**模型与页面保留，入口用 `FEATURES` 开关关掉**（`points` / `cards` 已就位）。
删了二期要重做，留着的成本只是一个 if —— 但**入口必须真的关掉**，
半开的功能（页面能进、数据是空的）比没有这个功能更糟。
