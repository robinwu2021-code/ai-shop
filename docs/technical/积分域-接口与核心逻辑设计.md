## 一、先修一处契约与设计的错配

### 1.1 问题

契约里商家侧积分账户是这个形状：

```ts
merchantPointAccount(): Promise<PointAccount>
// PointAccount = { balance, totalEarned, totalUsed, expiringSoon, expiringAt }
```

但 V17 的设计是**商家有两本账**（R4.1 / R4.2）：

| 账 | 表 | 单位 | 什么时候变 |
|---|---|---|---|
| **额度台账** | `pts_merchant_quota` | 分（积分个数） | 发放即占用，过期释放 |
| **资金台账** | `pts_merchant_ledger.amount_delta_minor` | 钱 | **只在兑付时**发生 |

`PointAccount` 是**用户侧**的形状（一个余额 + 累计收支），
拿它表达商家账户会把两本账压成一本——而这正是 R4.1 要防的
「同一笔分占两次额度 / 同一笔收入拿两遍好处」。

> 这处错配是**契约早于 V17 设计**留下的：契约写在积分建模之前。
> 不修的话，B 端做出来的页面会是错的，且错得看不出来。

### 1.2 修法

新增 `MerchantPointAccount` 类型，`merchantPointAccount()` 改返回它。

```ts
/** 商家积分账户 —— **两本账**，不要压成一个余额（R4.1/R4.2） */
export interface MerchantPointAccount {
  // ── 额度台账（单位：积分个数）
  /** 授信额度 = min(固定上限, 近 3 期平均货款 × 系数)（R4.3） */
  creditLimit: number;
  /** 已占用：发放即占用，过期释放 */
  quotaUsed: number;
  /** 可发放 = creditLimit − quotaUsed */
  quotaAvailable: number;
  /** 超授信已自动停发（R4.4）。**停发同时停收**，见 R2.1 */
  suspended: boolean;
  suspendedAt?: number;

  // ── 资金台账（单位：分）
  /** 本期收到的积分对应金额（用户在本店抵扣） */
  periodIncomeMinor: number;
  /** 本期应付的积分对应金额（本店发的分被用在别家） */
  periodExpenseMinor: number;
  /** 本期净额，正=平台付给商家，负=从下期货款扣（R5.2） */
  periodNetMinor: number;
  /** 当前账期标识，如 2026-08 */
  period: string;

  // ── 开关（含主体前置）
  /** 本店积分是否生效 —— L1 AND L2 AND 主体 AND L3 */
  enabled: boolean;
  /** 不生效的原因，直接展示给商家 */
  disabledReason?: string;
  /** 平台按行业强制开，商家不可自行关闭（R3.3） */
  forced: boolean;
}
```

> 【R5.4】商家侧**以钱为主、分为辅**：资金台账的字段放在显眼处，
> 额度是"还能发多少"的约束条件，不是商家关心的主指标。

## 二、核心算法

上游文档给了规则（R1–R8），这里给**可实现的算法**。

### 2.1 发放：`grantOnComplete(subOrder)`

触发时点：子订单 `COMPLETED`（R1.1——**不是支付时**）。

```
grantOnComplete(subOrder):
  1. 幂等闸：subOrder.points_granted == 1 → 直接返回（R1.7）
  2. 开关闸：canPoints(merchant) 为否 → 不发，标记 granted=1 并记原因
  3. 计算基数（R1.2）：
       base = Σ(订单行金额)                   ← 不含运费
              − 平台券补贴部分                 ← 商家没收到的钱不该由他出分
              − 赠品行                        ← is_gift = 1 的行不发
  4. 计算积分数：
       每行 points_config 有值 → 按行配置
       否则                    → base × 兜底比例
  5. 额度闸（R4.4）：
       quota_available < points → **停发**，置 suspended=1，同时停收（R2.1）
  6. 落账（同一事务）：
       pts_user_ledger   +EARN 行（这一行**就是批次**，见上游 2.2）
       pts_user_account  balance += points
       pts_merchant_quota used += points
       pts_merchant_ledger  quota_delta=+points, amount_delta_minor=0
       ord_sub_order.points_granted = 1
```

**第 6 步里 `amount_delta_minor = 0` 是关键**：发放只占额度、不产生资金（R4.2）。
把它记成成本就是把"或有负债"计成了当期费用——那笔分可能永远不会被花。

### 2.2 抵扣：`deductOnPlace(order, usePoints)`

触发时点：**下单时**（R1.3——不是支付后，防同一笔分同时下多单）。

```
deductOnPlace(order, usePoints):
  1. 开关闸：canPoints(merchant) 为否 → usePoints 强制为 0
  2. 上限（R1.4）：
       maxDeductMinor = (券后金额 − 运费) × 30%
       maxPoints      = maxDeductMinor / 兑换比例
       actual         = min(usePoints, maxPoints, userBalance)
  3. 顺序：**券先抵、积分后抵**（R1.4）
       —— 顺序反了会让券的门槛达不到
  4. 按批次拆分（R1.5，上游 2.3）：
       按 pts_user_ledger 的 EARN 行**先到期先用**排序，
       逐批扣减，每批生成一条 pts_redeem_alloc：
         { alloc_no, user_no, sub_order_no, earn_ledger_no,
           issuer_merchant_no,   ← 这批分是谁发的
           acceptor_merchant_no, ← 在谁家用的
           points, amount_minor, status=PENDING }
  5. 落账（同一事务）：
       pts_user_ledger   +USE 行
       pts_user_account  balance -= actual
       ord_sub_order.points_deduct / points_deduct_minor  ← 快照，结算与售后直接读
```

**第 4 步的批次拆分是跨商家兑付的基础**：用户一次用 3000 分，
可能 2000 是 A 发的、1000 是 B 发的——不拆就算不出谁欠谁。

`pts_redeem_alloc.status = PENDING` 表示**预占**：
此时兑付关系还没成立，因为订单还可能取消或退款（R1.5）。

### 2.3 兑付成立：`settleAllocOnComplete(subOrder)`

触发时点：子订单 `COMPLETED`（R1.5——与发放同一时点，但**是两件事**）。

```
settleAllocOnComplete(subOrder):
  for alloc in 该子单的 pts_redeem_alloc(status=PENDING):
     if alloc.issuer_merchant_no == alloc.acceptor_merchant_no:
        # R5.3 自发自用：置 self_used=1，仍走 CONFIRMED，
        # 但账期单聚合时按 self_used 排除 —— 状态与「是不是自用」是两个正交的事
        alloc.self_used = 1
        alloc.status = CONFIRMED
        continue
     alloc.status = CONFIRMED
     pts_merchant_ledger(acceptor): amount_delta_minor = +alloc.amount_minor  # 收
     pts_merchant_ledger(issuer)  : amount_delta_minor = −alloc.amount_minor  # 付
     # 注意：**quota_delta 都为 0** —— 兑付不再动额度（R4.1）
```

> **自发自用直接冲抵**省掉一次清算，顺手堵掉"自己刷自己套现"——
> 因为它根本不产生跨商家的资金往来。

### 2.4 取消与退款：`reverse(subOrder, kind)`

R1.6：取消返还抵扣分；退款**两笔都走**。

| 场景 | 已发放的分 | 已抵扣的分 |
|---|---|---|
| 取消（未完成） | 未发放，无需处理 | **返还**，`alloc` 置 `REVERSED` |
| 退款（已完成） | **收回**（`pts_user_ledger` −REFUND） | **返还** |

```
reverse(subOrder, kind):
  # 抵扣返还
  for alloc in 该子单的 alloc(status in PENDING/CONFIRMED):
     alloc.status = REVERSED
     if 原为 CONFIRMED:            # 兑付已成立，要反向记两笔
        pts_merchant_ledger(acceptor): amount_delta_minor = −alloc.amount_minor
        pts_merchant_ledger(issuer)  : amount_delta_minor = +alloc.amount_minor
  pts_user_ledger  +REFUND 行（返还抵扣分）
  pts_user_account balance += 返还数

  # 发放收回（仅退款）
  if kind == REFUND and subOrder.points_granted:
     pts_user_ledger  −行（收回已发）
     pts_merchant_quota used -= 已发数     # 额度释放
```

**退款必须两笔都走**——只收回不返还，或只返还不收回，用户都会在积分上净赚（R1.6）。

### 2.5 过期：`expireDaily()`

```
每日任务：
  for 批次 in pts_user_ledger(type=EARN, expire_at <= now, 未用尽):
     剩余分 → pts_user_ledger +EXPIRE 行（负数）
     pts_user_account  balance -= 剩余
     pts_merchant_quota(issuer) used -= 剩余    ← **额度释放**（R4.1）
```

> 过期时**释放发放方的额度**，这是额度台账与用户余额的联动点。
> 漏了这一步，商家的额度会只增不减，最终停发。

### 2.6 对账：`reconcileDaily()`

上游 R7 要求明细可查、可监控。校验两条恒等式：

```
① 用户侧：pts_user_account.balance == Σ pts_user_ledger.points
② 商家侧：pts_merchant_quota.used == Σ pts_merchant_ledger.quota_delta
```

不一致时**以流水为准**，重算账户并告警——账户表是派生的（上游 2.1 已定此规矩）。

第三条跨账勾稽（与资金账）：

```
③ Σ ord_sub_order.points_deduct_minor == Σ pts_redeem_alloc.amount_minor(status=CONFIRMED)
```

对不上说明有一侧漏记，是[总方案 §7.3](./多端多通道-平台能力总方案.md) 要求的勾稽点。

## 三、接口设计

### 3.1 C 端 `/mp/**`

| 方法 | 路径 | 说明 | 状态 |
|---|---|---|---|
| GET | `/mp/points/account` | 我的积分账户 | ✅ 已有 |
| GET | `/mp/points/records` | 积分流水（分页） | ✅ 已有，**改为分页** |
| GET | `/mp/points/deductible` | **结算页试算**：本单最多可抵多少 | ★ 新增 |

`/mp/points/deductible` 入参 `{ items[], couponNo?, merchantNo }`，出参：

| 字段 | 说明 |
|---|---|
| `maxPoints` | 本单最多可用积分数 |
| `maxDeductMinor` | 对应金额 |
| `balance` | 用户当前余额 |
| `enabled` | 本店积分是否可用 |
| `disabledReason` | 不可用原因——**小微商家在这里返回"升级后可开启"** |

> 【为什么要单独一个试算接口】上限是 `(券后金额 − 运费) × 30%`，
> 依赖券的选择。端上自己算必然与服务端算法分叉，
> 而**分叉的表现是"页面说能抵 5 元、下单只抵了 3 元"**——用户会认为在骗他。

### 3.2 B 端 `/biz/**`

| 方法 | 路径 | 说明 | 状态 |
|---|---|---|---|
| GET | `/biz/points/account` | 商家积分账户（**两本账**） | ⚠️ 已有但**出参要改**（§1.2） |
| GET | `/biz/points/records` | 积分流水（额度 + 资金双口径） | ✅ 已有，出参补 `quotaDelta`/`amountDeltaMinor` |
| GET | `/biz/points/bills` | 积分账期单列表 | ★ 新增 |
| GET | `/biz/points/bills/{billNo}` | 账期单详情（下钻到 alloc 明细） | ★ 新增 |
| POST | `/biz/points/toggle` | 开/关本店积分 | ★ 新增 |

`POST /biz/points/toggle` 的规则（**服务端强制**，不靠前端禁用按钮）：

| 情况 | 行为 |
|---|---|
| 主体是 `MICRO` | **拒绝**，返回"升级为个体工商户后可开启" |
| `forced = 1` | **拒绝关闭**，返回强制开的说明与申诉入口（R3.3） |
| L1/L2 未开 | 拒绝，返回"平台/本社区暂未开放" |
| 关闭 | 允许，**仅影响将来**；存量已发积分仍有效、债务仍需承担（R2.2） |

## 四、幂等与并发

| 场景 | 手段 | 说明 |
|---|---|---|
| 重复发放 | `ord_sub_order.points_granted` | V17 已有 |
| 重复抵扣 | 下单幂等 `idempotencyKey` | 抵扣随下单发生 |
| 重复兑付 | `pts_redeem_alloc.status` 状态机 | `PENDING → CONFIRMED/OFFSET/CANCELLED` |
| 余额并发扣减 | **条件写在 WHERE 里** | 见下 |
| 额度并发占用 | 同上 | |

```sql
-- 用户余额扣减：先查后扣在并发下必然扣穿
UPDATE pts_user_account
   SET balance = balance - #{points}, total_use = total_use + #{points}, version = version + 1
 WHERE user_no = #{userNo} AND deleted = 0 AND balance >= #{points}

-- 商家额度占用：同时挡住超授信（R4.4）
UPDATE pts_merchant_quota
   SET used = used + #{points}, version = version + 1
 WHERE merchant_no = #{merchantNo} AND deleted = 0 AND suspended = 0
   AND used + #{points} <= credit_limit
```

返回 0 行 = 余额不足 / 超授信 / 已停发，**按业务分支处理，不重试**。

## 五、状态机

### `pts_redeem_alloc.status`

```
PENDING ──▶ CONFIRMED ──▶ REVERSED（退款/取消，反向记账）
   │
   └──▶ REVERSED   订单在兑付成立前就取消

自发自用不是一个状态，而是 `self_used=1` 标记：
它照常 CONFIRMED，但账期单聚合时按该标记排除（R5.3）。
状态（走到哪一步）与是不是自用（谁对谁）是两件正交的事，压成一个枚举会丢信息。
```

### `stl_points_bill.status`

```
DRAFT ──▶ CONFIRMED ──▶ SETTLED
```

`DRAFT` 是账期内边跑边攒的草稿，期末封账转 `CONFIRMED`，打款后 `SETTLED`。

净额为正 → 平台付给商家；为负 → 并入下期货款扣除（R5.2）。

## 七、验收

| 断言 | 防住什么 |
|---|---|
| 同一子单重复调 `grantOnComplete` 只发一次 | 重复核销重复发分（R1.7） |
| 赠品行不发分、运费不计入基数 | 买赠 + 积分叠出套利（R1.2） |
| 抵扣上限恒 ≤ 券后金额 30%，运费不参与 | 整单抵扣商家一分收不到（R1.4） |
| **券先抵、积分后抵** | 顺序反了券的门槛达不到 |
| 退款后用户积分**不净赚**（两笔都走） | R1.6 |
| 超授信时**同时停发停收** | 只停一半 = 搭便车（R2.1/R4.4） |
| 自发自用 `OFFSET`，不进账期单 | 自己刷自己（R5.3） |
| 过期时**释放发放方额度** | 额度只增不减最终停发 |
| `MICRO` 主体调 `/biz/points/toggle` 被拒 | 小微不参与积分（总方案 §8.1） |
| `forced=1` 时关闭被拒 | R3.3 |
| 三条对账恒等式成立 | §2.6 |
