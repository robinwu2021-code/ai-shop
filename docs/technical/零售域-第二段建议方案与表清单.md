# 零售域第二段（换表）· 方案与表清单

状态：**已定**（2026-11-27 用户确认，已回写 [TDD §8](TDD-零售域对齐门店交易库.md#8-待确认)、[ADR-067](ADR/ADR-067-门店交易库按耦合簇换表与行业插件公用部分并回.md) 与[对照表](零售域-旧表新表对照.md) §1.1）。下一步交设计方案拥有者改生成器。
设计稿位置：`ai-shop-slim` 的 `docs/technical/design/schema/ddl/05-n_trade.sql`（74 张）、`06-n_industry.sql`（14 张），本篇不改它。

## 0 推导依据

按业务逻辑推导，不按现有行数和现有列来定。前五条是用户已经定下的口径：

1. **库里只存业务数据**。事件由公共能力承担，防重由功能能力承担，业务库不建这类技术表。
2. **按业务概念收敛**。同一个业务概念被重复建模的，合成一张表。
3. **库归属**：积分归支付库，库存归库存库（门店只留简单库存）；审核由独立服务承担。
4. **交易不用事件**（Q2）。提交后直接调用下游；关键下游靠扫订单状态补做。
5. **状态取值改短**（Q3），≤10 个字符。
6. **防重单独说明**：防重要做到和业务写入同生同灭，同一个事务里只有业务库自己的唯一约束能兜得住，见 A2。

## A 建议方案

### A1 设计缺陷（D1–D7）的统一修法

| # | 建议 |
|---|---|
| D1 | 所有 `uk_*` 一律改成 `UNIQUE`，补上「并入后无处安放」的那批唯一约束（附录一，逐表列出） |
| D2 | 见 A2 |
| D3 | 逐表补齐（B2）。渠道恢复循环的抢占和到期列（fence、lease、next_attempt_at）**不加**：恢复循环交给任务库的公共能力 |

| D5 | **外部来源号、人员列放宽到 64**，包括渠道单号、外部回执号、支付流水号、`client_order_no`、`created_by`、`updated_by`。内部生成的编号保持 32，但迁数据前要扫一遍现有最长值，超长的列（如 `prd_spec_value_usage.value_no`，约 68）改成 64 |

| D9 | 行业库文档的「17 张」改成实际数量（按本稿是 24 张，见 B3）；提成规则移到行业库后，注释里「提成的结算走账务结算库」改成「提成在行业库计提，不进账务结算库」 |

### A2 防重列：分两类

- **业务身份列：保留，并加唯一约束。** 这类键本身就是业务事实，例如订单号、外部单号 `(channel_store_key, external_order_key)`、门店 POS 离线单号 `client_order_no`、报价单上的 `operation_no`、资源时段 `(resource_no, start_at)`。
- **纯请求键：不进业务表。** 例如请求键、命令号、`*_hash` 这类内容摘要、`source_request_key`，改由公共幂等能力承担。
  - 前提是能做到「先占幂等键，再写业务，按业务号查回结果」。
  - 业务写入本身已经靠第一类唯一约束兜底了。
- 附录一最后一列逐条列出了「缺的防重列」，由设计方案拥有者按上面两类逐条归类。我的倾向是：凡是能从业务列推出唯一性的，都归第二类。

### A6 美业执行整段留在行业库（用户 2026-11-27 定方向）

**划法**：美业的「服务怎么做」留在行业库，「卖了什么、收了多少、约了谁」在交易库。这和餐饮的厨房出品单、厨显留在行业库是对称的。

| 行业库（美业执行） | 交易库（买卖本身） |
|---|---|
| `bty_work_order`：服务工单，执行头（范围版本、冻结），并入工单上下文、到店认领、到店核验；带 `visit_no`、`appointment_no` 引用 | 服务定义 → `prd_goods`、`prd_goods_revision`、`prd_fulfillment_requirement` |
| `bty_service_task`：服务任务，带 `sub_order_no`、`order_item_id` 引用 | 预约 `ord_appointment*`；指定技师记在 `ord_appointment_item.requested_personnel_no` |
| `bty_service_step`：服务步骤 | 资源与占用 `rsv_*`（含预约资源意向与决策） |
| `bty_trade_binding`：任务 ↔ 订单行，并入来源观察与分配围栏 | 订单、收款、售后、退款 |
| `bty_service_submission`：服务提交，围栏改唯一约束 | 履约记账 `ord_fulfillment_unit`、`ord_execution`（交易这边的「已交付几份」） |
| `ind_assignment`：服务参与与交接（见 C1，和餐饮共用） | 到店单 `ord_visit`（结账容器） |

**依据**
- 「一条语句判断加写入」的四条 SQL（完成步骤、记录任务完成、关闭冻结范围、按任务查步骤）都只碰步骤、任务、工单、绑定、参与这五张表，全部留在行业库，不用拆。
- 美业和交易之间已经走接口：`ServiceExecutionPort`、`CheckoutPort`、`ManualServiceAdmissionPort`、`ResourceBookingPort`。`beauty-channel` 里还有这些接口的远程实现（`RemoteServiceExecutionPort` 等），说明美业本来就设计成可以和交易分开部署。

**核过的跨库点**（2026-11-27 读代码）

| 场景 | 现状 | 拆开后的做法 |
|---|---|---|
| 到店开工单（`WorkOrderCoordinator`） | 一个事务里锁住交易库的预约当前行、按预约数工单、插入工单和任务 | 工单表的唯一约束 `(entity_no, appointment_no)` 保证一个预约只开一张工单；提交后调交易把预约标成已到店，失败靠扫状态补做。预约取消和到店撞车时，由交易拒绝取消已到店的预约；行业这边扫到预约已取消，就关闭工单 |
| 工单结账（`WorkOrderBillServiceImpl`） | 交易事务里调结账接口，同时写服务提交和绑定 | 先调结账（结账已按 `OperationRef("BEAUTY", operationNo)` 防重），再在行业库写提交和绑定；中途退出时按操作号补做 |
| 服务执行（`ServiceTaskExecutionServiceImpl`） | 已经通过 `ServiceExecutionPort` 调交易 | 不变 |

**代价**
- 第一段里，工单、工单上下文、服务任务、服务参与这 4 个美业 Mapper 打了交易库标记，预约的持久化对象 `AppointmentPersistence` 用一个交易事务同时管预约和工单。换表前要把它拆成「预约（交易）」和「工单（行业）」两个持久化对象，这 4 个 Mapper 改到行业句柄。
- 交易这边的履约单元、执行只记到「订单行交付了几份」，看不到美业的任务和步骤；要看明细时，通过美业接口查。

## C 交易库与行业库复查（2026-11-27）

判据有三条：
1. **只有一个行业用、而且不和订单在同一个事务里写**的，移到行业库；
2. **同一个业务概念建了两张表**的，合并；
3. **不属于门店交易**的（用户资料），移到它的归属库。账务结算库只解决支付收款，业务结算（如提成）留在业务库（用户 2026-11-27）。

### C1 采纳的（已计入 B 节）

| 表 | 结论 | 依据 | 把握 |
|---|---|---|---|
| `ord_queue_ticket` | 移到行业库 | 只有餐饮用（来源 `fnb_queue_ticket`）；排队到入座只留 `check_no` 引用。**更正（2026-11-27）**：叫号入座在同一个事务里开到店单（`QueueServiceImpl` → `CheckService.openQueuedCheck`），移过去要拆成「先开单、再改排队号」两步，见 TDD 提交十二 | 中 |
| `ord_custody`、`ord_custody_movement` | 移到行业库 | 只有餐饮存酒用（来源 `fnb_bottle_*`）；`BottleCustodyServiceImpl` 只写自己两张表，其余全走查询接口 | 高 |
| `ord_assignment` | 移到行业库，改名 `ind_assignment` | 来源是美业服务参与与派工、餐饮服务交接与责任，都是「谁在做」的执行信息；美业参与随 A6 本来就留行业库；预约时指定的技师已经记在 `ord_appointment_item.requested_personnel_no` | 中：餐饮交接的统计 SQL（`FoodBusinessOperationsMapper`）现在联查订单批次和到店单行，要拆成两次读 |
| `prd_spec_value_usage` | 并入 `prd_spec_usage` | 两张都是「哪个范围用哪些规格」，一张到维度、一张到取值；值为空就表示整个维度 | 高 |
| `ord_commission_rule` | 移到行业库，改名 `ind_commission_rule` | 提成是业务结算，不进账务结算库（账务结算库只管支付收款）。算一笔提成要规则、基数、归属三样，最「行业」的是归属（技师、换人重算、服务交接），已在行业库 `ind_assignment`；规则和归属同库，按版本计提在一处算完，订单行金额经接口读。代码里还没有员工提成（现有 `commission` 都是平台佣金），设计稿里它是新建表，移动不影响现有代码。零售导购提成以后要做时，从交易库读订单上的导购归属（用户 2026-11-27 定） | 高 |
| `ord_address` | 移到平台基础库 | 收货地址是用户资料，不是门店交易；第一段已经随 C 端账号接在平台句柄上 | 高 |
| `rfq_quote_revision`（原拟新增） | 不建 | 当前报价和改价次数已在 `rfq_quote`；历史进统一审计 | 中 |

### C2 考虑过、但不建议动的

| 表 | 为什么不动 |
