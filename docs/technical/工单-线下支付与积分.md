# 第 2 步　支付方式四层判定

**前置**：第 1 步　**可与第 3 步并行**

### 动哪些文件

```
backend/shop-base/src/main/java/ai/neargo/shop/spi/merchant/QualificationPort.java   新建
backend/shop-merchant/src/main/java/ai/neargo/shop/merchant/port/QualificationPortImpl.java 新建

backend/shop-app/src/test/java/ai/neargo/shop/scenario/PayModeResolveFlowTest.java   新建
```

### 怎么改

```java
/** 这件商品在这家店支持哪些支付方式。**四层取交集**，任何一层说不行就是不行。 */
Set<String> availablePayModes(String goodsNo, String storeNo);
```

四层顺序（短路）：**类目 → 主体资质 → 门店 → 商品**。

**资质那一层按 `expire_at` 现算**，不读 `status`：

```java
// 生产只跑 api,ops 两个 profile，没有 worker —— 把 status 置成 EXPIRED 的那个定时任务
// 在生产根本不跑。所以判据是「此刻有一张未过期的证」，不是「有人记得改状态」。
boolean hasValidQualification(String entityNo, String qualType);
```

**为什么资质走 Port**：判定在 product 域、表在 merchant 域。直接依赖会造域间耦合 ——
这个仓库已经撞出过 `merchant → StoreShelfPort → MerchantGoodsService → GoodsService → merchant`
的构造环，整个上下文起不来。

### 怎么验

必测四条（缺一不可，每条都要能单独变红）：

1. 四层全放行 → 返回 `[ONLINE, OFFLINE]`
2. **主体的证过期** → 只剩 `[ONLINE]`（用 `expire_at` 造过期，**不要**改 `status`——
   要测的正是「不依赖 status」）
3. 门店关了 `offline_pay_enabled` → 只剩 `[ONLINE]`
4. 类目禁了 OFFLINE → 只剩 `[ONLINE]`，**即便其余三层都放行**

### 完成判据

四条全绿，且**逐条撤掉对应那一层的判定都会让对应用例变红**（不是"改宽了才绿"）。

# 第 3 步　积分规则取值

**前置**：第 1 步　**可与第 2 步并行**

### 动哪些文件

```
backend/shop-app/src/test/java/ai/neargo/shop/scenario/PointsRuleFlowTest.java        新建
packages/shared/tests/points-rule-single-entry.test.ts                                新建（守卫）
```

### 怎么改

取值优先级 —— **取一个值，不是相加**：

```
商品例外（运营配的 points_config）配了 → 用它，哪怕值是 0
否则类目配了                          → 用类目的
否则                                  → 平台兜底 PointsConfig.earnPerMinor
```

⚠️ **「配了 0」与「没配」是两件事。** 储值卡配 0 分是明确决定，
不能因为值是 0 就掉到下一层拿一个非 0 的值。`points_config` 是 JSON ——
**用「键存不存在」判，不能用「值是否为 0」判**。这是这类三层配置最常见的 bug。

守卫测试：禁止 `PointsRuleResolver` 之外的任何地方直接读 `points_config`。

### 怎么验

1. 只有平台兜底 → 取兜底
2. 配了类目 → 取类目的
3. 配了商品例外 → 取商品的
4. **商品例外配 0** → 得到 0，**不掉到类目层**
5. 守卫：在别处新写一行读 `points_config`，守卫要变红

### 完成判据

五条全绿；第 4 条是本步的核心，**它红了说明优先级实现错了**。

# 第 4 步　订单：新状态 + 下单校验 + 确认收款

**前置**：第 2 步　**风险最高的一步**

### 动哪些文件

```
backend/shop-core/.../trade/service/OrderStateMachine.java              加 1 状态 2 出边
backend/shop-core/.../trade/service/impl/OrderServiceImpl.java          改 create
backend/shop-core/.../trade/api/biz/BizOrderController.java             加 1 端点
backend/shop-app/src/test/java/.../scenario/OfflinePayFlowTest.java     新建
b-app/src/api/endpoints.ts                                              登记端点
```

### 怎么改

**状态机**：主单加 `WAIT_OFFLINE_PAY`，出边 `→ PAID` 与 `→ CANCELLED`。**子单不加新状态** ——
确认收款前子单保持 `WAIT_PAY`，与线上单一致。

**`create` 加四处，一律前置且只读，不改已有分支的顺序**：

1. 支付方式是否可用（调第 2 步的 `availablePayModes`）
2. 组合合法性：只有到店自提 / 商家自送 / 到店核销 / 上门预约允许线下；
   **排除快递**（货已寄出）与**自提点自提**（自提点不是卖家，代收货款就是资金归集）
3. 线下 + 平台券 → 拒（`PLATFORM_COUPON_OFFLINE_FORBIDDEN`）。**积分与商家券照常可用**
4. 写 `payScene`（从 `X-Client` 头来）

**确认收款端点**：

```java
@PreAuthorize("@perm.canBiz('" + BizPerms.RECEIVE + "')")
@PostMapping("/biz/order/{subOrderNo}/confirm-offline-pay")
```

> 权限选 `RECEIVE` 不选 `ORDER_VIEW`：后者是**只读**权限，配送员也持有（`COURIER` 角色）。
> 给只读角色一个能推进订单状态的动作是越权。

内部**复用 `markPaid(orderNo, "OFFLINE", 操作人+时间)`** —— 库存转实扣、入会、发分、
结算触发、积分实扣全部零改动。**不要另写一套**。

### 怎么验

必测（每条都要能单独变红）：

1. 线下下单后状态是 `WAIT_OFFLINE_PAY`，**库存已锁**
2. 确认收款后 `PAID`，库存转实扣
3. **买家 token 调该端点 → 403**
4. `EXPRESS + OFFLINE` 下单被拒；`NEIGHBOR_PICKUP + OFFLINE` 下单被拒
5. 线下 + 平台券 → 拒；线下 + **商家券** → 成功；线下 + **积分抵扣** → 成功
6. `payScene` 落库不为空

**回归（本步必须做）**：

```bash
mvn -o -f backend/pom.xml -pl shop-app -am test \
  -Dtest='M3TradeFlowTest,ConsumerOrderFlowTest,BizOrderFulfillFlowTest,StoreGoodsFlowTest'
```

`create` 是全站最要害的方法，这几个是 1205 条里最贴着它的。

### 完成判据

六条全绿 + 回归**不新增失败**（那几个类本来就有红的，数目不能变多）。

# 第 6 步　端开关：发放与核销分开

**前置**：第 3 步（发放规则）+ 第 4 步（`payScene` 已落库）

### 动哪些文件

```
backend/shop-base/.../auth/ClientMeta.java                    解析 X-Client
backend/shop-settle/.../PointsService.java                    加 canEarn / canRedeem
backend/shop-core/.../product/api/ops/OpsPointsSwitchController.java  新建
ops-web/app/.../points-client-switch                          新建页
```

### 怎么改

```java
/** 能不能核销。读**当前请求**的端。不可用要带能直接渲染给用户看的原因。 */
PointsAvailability canRedeem(String userNo, String merchantNo, String payMode, String clientType);

/** 能不能发放。读**订单快照 ord_order.pay_scene**，不是当前请求。 */
PointsAvailability canEarn(String orderNo);
```

⚠️ **这一步最容易写错的就是 `canEarn` 读了当前端。**
发放时机是订单完成时，而那一刻用户可能换了端、**更常见的是根本没有用户在场**
（超时自动确认收货是系统动作）。读当前端会让同一笔订单发不发积分取决于
谁在哪个端点的确认，甚至取决于是不是定时任务跑的 —— 不可复现、无法对账。

⚠️ **回收与解冻不经过任何端判定。** 退款收不回已发积分 = 账上凭空多出积分，
**那是资金事故不是策略**。

⚠️ 端标识来自客户端、**天然可伪造** —— 只能用于平台策略，
绝不能用于权限或资金判定。**这句要写进代码注释**。

### 怎么验

1. 关掉「小程序可发放」→ 小程序下的单完成时不发分；
   **并且用定时任务触发完成**（没有当前端）→ 结论不变 ← **本步核心**
2. 下单时允许、完成前把该端关掉 → 仍按下单时的规则发（不追溯）
3. 关掉「小程序可核销」→ 小程序结算页拿不到抵扣额度，App 上同一用户可以
4. **在被禁用的端上退款 → 已发积分照常收回**
5. **在被禁用的端上取消订单 → 已冻结积分照常解冻**

> 4、5 是**资金正确性**不是策略，必须独立测试，不能靠「反正没人会那么配」。

# 第 7 步　预约排期

**前置**：第 1 步　**与 2~6 都不冲突，随时可插**

### 怎么改

占用走**带条件的 UPDATE**：

```sql
UPDATE prd_appointment_slot SET booked = booked + 1
 WHERE id = ? AND booked < capacity AND deleted = 0
```

影响 0 行即已约满 → `APPOINTMENT_SLOT_FULL`。
**不能"先查再改"** —— 并发下必然超约。与到店核销扣次数、库存锁定同一个做法。

### 怎么验

1. 两个买家**并发**抢同一时段最后一个名额 → 只有一个成功
2. 选未开放/已停约的时段 → 拒
3. 取消订单 → 名额释放
