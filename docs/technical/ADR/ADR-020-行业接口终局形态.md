# ADR-020 行业接口终局形态

> 状态：**提案 · 待决策** · 创建 2026-08-27
> 数据：[三行业接口与流程对比矩阵](../design/三行业接口与流程对比矩阵.md)（P3）· 生成物 [`行业化端点盘点`](../reference/行业化端点盘点.md)
> 判定规则：[方案梳理清单](../design/方案梳理清单-行业化接口盘点与终局选型.md) §6，**P0 定稿、P3 之后未改**
> 相关：[ADR-019 行业工作流做成独立行业包](./ADR-019-行业工作流做成独立行业包.md)

## 1. 决策

**采用方案 A：基座为主，行业补充。**

具体形态三条：

1. **写按主语走门。** 基座对象的写永远走基座接口 —— 唯一写入口 = 唯一校验 = 唯一状态机；
2. **读允许行业聚合。** 行业包可提供聚合读端点，消除前端多次请求自己拼；
3. **行业自有的对象走行业入口** `/{mp,biz,ops}/x/<code>/**`，由行业包编排后调 `Core*Api`。

**否决方案 B（行业统一入口）与方案 C（按模块拆）**，理由见 §2。

## 2. 依据：判定条件是预先承诺的，数据直接触发

| 判定输入 | 实测 | 清单 §6 的条件 | 命中 |
|---|---|---|---|
| `X`（结构差异）占比 | **2.0%**（5 / 252） | `< 15%` → 方案 A | ✅ |
| `X` 集中度 | **1 个主语**（`order`） | `≤ 3 个主语` | ✅ |
| `S`（完全相同）占比 | **91.7% / 91.3%** | — | — |

**五段流程互相印证**：售后与结算**完全相同**，履约只是取值域加一档（`DINE_IN`），
支付共用同一个 `markPaid`，只有"下单"是真差异 —— 而它恰好就是那 5 条 `X`。

**方案 B 被数据直接否掉**：91.7% 的接口三行业完全相同。
让每个行业包代理 252 个完全相同的接口，是纯粹的成本 ——
基座每加一个端点，每个行业包跟一次；权限码 99 × 行业数。

**方案 C 在这份数据下与 A 收敛**：C 的做法是"把差异模块行业化"，
而差异只集中在 `order` 一个主语、且以读为主（`V` 85% 在 `goods` + `order`）。
把一个主语行业化 = A 的第 2、3 条。**C 在这里不是另一个方案，是 A 的描述方式。**
所以选 A 并写明形态，而不是引入第三个名字。

## 3. 两条否决项（与占比无关，恒成立）

1. **`external=Y` 恒走基座。** 支付/物流回调地址只能有一个，外部系统不认识行业。
   本轮 299 条里为 0（回调在 `/callback/**`），但规则继续有效。
2. **`cross=Y` 恒走基座。** `POST /mp/order` 同时是 `X` 和 `cross=Y` ——
   社区电商的购物车跨商家，一次下单可能同时含餐饮店和零售店的商品。
   **落法是"多一个行业入口"，不是"废掉基座那条"**：
   ```
   POST /mp/order          基座保留，服务跨商家混合下单
   POST /mp/x/food/place   餐饮场景，行业包编排后调 CoreOrderApi
   ```
   做反了，跨商家购物车当天失效 —— 而那是这个平台的核心形态。

## 4. 一个必须带走的数字：行业包本身有多大

判定用的是 `X` 占比（2.0%）。但**分母只含零售已有的接口，不含行业新增的**。
按"行业自有面"算：

```
餐饮：新增 25 + X 5 + V 13 + P 3 = 46 / 277 = 16.6%
美业：新增 26 + X 5 + V 14 + P 3 = 48 / 278 = 17.3%
```

**这个数不改变本 ADR 的决策**（判定维度是预先承诺的，事后换口径正是要防的事），
但它决定另一件事：**行业包不是薄壳**，各自约 25 个自有端点 + 10 张表。
排期与人力要按这个量估，不要按"2% 的差异"估。

## 5. 后果

**得到**
- 252 个接口三行业共用一份实现、一份权限码、一份测试；
- 行业包只写自己的 25 个端点，基座每加端点不需要行业包跟；
- 跨商家、跨行业的混合场景（购物车、会员、券、结算）天然成立。

**付出**
- 前端要认两个门（同一页面里读走行业聚合、写走基座）。这是本方案唯一的持续成本；
- 行业聚合读端点是**新的耦合点**：它读基座的形状。基座改字段要连带改它 —— 由 SPI 契约与 ArchUnit 拦。

**不解决**
- `/ops` 的行业化（338 个端点没盘，见 §7）；
- Service 层内部的行业分叉（没被度量过，见 §7）。

## 6. 复议条件（写死，避免"再讨论一次"）

出现下列任一情况，重跑 `npm run gen:industry-inventory` 并重新评估：

1. 任一行业的 `X` 占比 **≥ 15%**，或 `X` 摊到 **> 3 个主语**；
2. 引入第 4 个行业包，且它的 `S` 占比 **< 80%**；
3. 行业包由**第三方**开发（不能把基座全量接口给出去，方案 B 的权重立刻上升）；
4. 出现**私有化单行业交付**（届时按 ADR-019 的 L2 运行时加载评估）。

## 7. 本 ADR 未覆盖（原样声明，不含糊）

1. **`/ops` 的 338 个端点没有被盘过。**
2. **"有前端调用方"是静态前缀匹配**，272 是上界 —— `S` 的实际占比可能被高估。
3. **只盘了接口，没盘 Service 层**：同一个接口内部为行业分叉的可能性不在度量范围内。
   这恰是方案 A 最需要防的失效模式，**必须靠 ArchUnit 与 code review 兜**，统计给不了保证。
4. **社区团购（20 条）被排除出分母**；若它将来行业包化，结论要重算。
