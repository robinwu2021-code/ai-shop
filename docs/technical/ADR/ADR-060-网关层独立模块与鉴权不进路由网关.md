# ADR 060 网关层独立模块与鉴权不进路由网关

状态：已接受（用户 2026-11-18 确认定稿）；尚未实现。
关联：[TDD-网关层与统一权限-五层架构对齐](../TDD-网关层与统一权限-五层架构对齐.md)；配套 [ADR-061](ADR-061-三端认证与权限各自一套及权限库独立.md)。

## 背景

C 端、B 端、运营端的 HTTP 入口今天都在 `shop-app` 里：三端的认证链挤在一个 428 行的配置类里，按端启停靠 505 处 `@Profile`，出口包与桥接包互相引用，出口无法单独成模块。权限码集中写在基础能力层的两个常量类里，行业的码也在其中。

用户要求把三端出口定为标准的网关层，集成 Spring Security，代理支付、库存等微服务，并评估是否引入 Spring Cloud Gateway；还要求角色不能访问的链接在网关层就被拦下，而不是到微服务层才拦。

## 决定

1. **网关层是一个独立的 Maven 模块 `backend/shop-gateway`，按包划分。** 它不依赖 `shop-app`；`shop-app` 只剩启动与装配。三端的出口包与桥接包搬进来，包名不变。三端的隔离由每端的开关和架构测试保证。
2. **请求流程固定为五步：定位、认证、上下文、判定、调用。** 端、判定、调用、链接来源各一组基类，差别只写在子类里。
3. **认证与鉴权在网关层用 Spring Security 做一次。** 鉴权与权限数据同进程。微服务不认终端令牌，不建角色表。
4. **不引入 Spring Cloud Gateway。** 路由仍归 nginx；路由匹配与转发由网关模块自己实现，约 400 到 500 行。`ServiceInvoker` 留作以后替换的位置。
5. **链接与权限第一期记录在数据库里。** 本进程入口启动时扫描入库；微服务链接由种子或运营端界面录入，其权限在库里调整。库读成本地快照，逐请求只查快照。本进程入口的权限码仍由代码决定，库里只记录并可停用。
6. **微服务链接是白名单。** 没录入的地址一律 404，不转发。
7. **三处接缝留接口、不预写第二个实现：** 安全框架适配、判定来源、调用方式。

## 被否的方案

| 方案 | 为什么不选 |
|---|---|
| Spring Cloud Gateway（WebFlux）作独立网关进程 | 鉴权依赖同进程的门店上下文、数据范围和即时生效的权限解析；另起一个进程等于再抄一遍权限系统。认证、路由、限流在这里都已有归属 |
| Spring Cloud Gateway Server WebMVC 嵌入网关模块 | 全仓没有 Spring Cloud 的依赖管理，要先改跨项目的父 pom，并在 Spring Boot 4.0.7 上验证兼容（未验证）；签名、统一包体、判权仍要自己写成它的过滤器。眼下只需要匹配、改写、转发三件事 |
| 七个 Maven 模块（公共、权限、三端、约定、守卫）加一个桥接模块 | 模块太碎；三端今天就是同一个包按配置分进程部署，编译期隔离没有对应的需求 |
| 第一个请求到来时向微服务拉权限清单并缓存 | 第一个请求要等远程调用；微服务恰好不可用时无从判断；运营配角色时清单可能还没被触发 |
| 库里可以在线改本进程入口的权限码 | 权限码同时写在入口方法的注解上并会再判一次，两处会给出不同结论；要做得先改 1300 多处注解 |

## 取舍和影响

- 做不到只打包某一端：三端的类在同一个模块里，靠开关不装配。
- 桥接包按五层属于基础业务层，现在与出口放在同一个模块，分层靠架构测试守住；以后可整包移出。
- 提前判权之后，方法上的 `@PreAuthorize` 仍保留再判一次。两次读同一个内存集合；一致性由测试保证。
- 微服务进程里运行的约定与守卫进不了网关模块（它依赖业务各层与 Spring Security），放进现有的 `svc-client`。
- 新增两张接口资源表，166 环境需要 root 先建表。

对既有决策的影响：

- [TDD-三端服务拆分](../design/TDD-三端服务拆分-架构与依赖规划.md) §6.2「鉴权永远下沉」继续成立：本决策里的网关层就是那份文档里的端接入层；被否的仍是把鉴权放进独立的路由网关。§6.2「二期上 Spring Gateway」改为按本文的三个条件再评估。
- ADR-045「支付内部入口只识别、不拒绝」**暂不修订**：签名校验先以开关形式加入，默认只比对并记录，行为与 ADR-045 一致。打开拒绝时另行确认并修订 ADR-045。
- 166 环境上 nginx 把运营端 `/oms-api/pay-ops/v2/` 直连 near-pay 的做法**现在不动**（用户 2026-11-18 定），作为已知例外保留；新方案稳定后再议。

## 重新评估的条件

出现任一情况时重新评估 Spring Cloud Gateway，届时首选嵌入式的 Server WebMVC：

1. 公网上有两个以上需要各自伸缩的端服务，且需要 nginx 表达不了的动态路由或灰度。
2. 微服务要原样暴露给终端的接口数量大到自己维护转发成为负担。
3. 需要跨服务统一的限流与熔断，nginx 与 resilience4j 分别配置已经管不住。
