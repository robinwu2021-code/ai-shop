## 1. 一句话

资金有两条路径 —— **归集到平台**（平台是销售主体，代销）与**直连商户号**（商家是销售主体，分账）；
**能走哪条不由平台选，由商户类型决定**，判据是「这家商户开不开得出票」。

## 2. 问题

「先收钱再结算」这件事被问过三轮，每一轮的答案都对，但**互相之间没有连起来**：

- [结算模式-双模方案](../design/结算模式-双模方案.md) §一：平台归集必须是「延迟分账」，打进对公账户再转是**二清**
- 同文 §一之二：自营采购**不是**二清 —— 平台是交易主体，钱是自己的收入
- [商户类型定义](../design/商户类型定义.md) §6.3：无实体商户走自营 = 平台全额收入 + 成本不可扣，**禁止**

三条都成立，合起来才是完整答案：**「先收钱再结算」是否合规，取决于收的是谁的钱；
而「谁的钱」取决于平台是不是销售主体；平台能不能当销售主体，取决于供应商开不开得出票。**

## 3. 决策

### 3.1 两条路径的定义

| | **A. 归集（代销 / 自营）** | **B. 直连（第三方分账）** |
|---|---|---|
| 销售主体 | **平台**（以自己名义销售） | 商家 |
| 用户付给谁 | 平台商户号 | 商家的二级商户号（收付通） |
| 钱的性质 | **平台的营业收入** | 商家的钱，平台只分走佣金 |
| 给商家的钱 | **货款**（B2B 应付账款） | 分账，钱从未进平台 |
| 发票 | 平台开给消费者；商家开给平台 | 商家开给消费者 |
| 二清 | **不构成** —— 收的是自己的钱 | 不构成 —— 钱不经平台 |
| 依赖 | 无（今天就能跑） | EDI + 收付通开通 |

> **A 不等于「打进对公账户再转账」**。那是 [双模方案 §一](../design/结算模式-双模方案.md) 明确否掉的 B 方案（真二清）。
> A 里平台是交易主体，付给供应商的是采购/代销货款，走对公转账 + 合同 + 发票 —— 任何零售企业每天在做的事。

### 3.2 谁能走哪条：**由商户类型决定**

按[商户类型定义](../design/商户类型定义.md) §6.4 的三分：

| 商户类型 | A 归集（代销） | B 直连（分账） | 决定性理由 |
|---|---|---|---|
| **企业商户** | ✅ **首选** | ✅ 需 EDI | 能开专票，平台按适用税率抵扣 |
| **个体工商户** | ✅ 可行 | ✅ 需 EDI | 普票/代开专票，抵扣低一档但**有凭证** |
| **自然人商户** | ❌ **禁止** | ✅ **唯一可行路径** | 开不出票 → 平台成本不可税前扣除 |
| ↳ 自产农产品 | ✅ **例外** | ✅ | 平台可自开**农产品收购发票**（[§六之二](../design/商户类型定义.md)） |

**自然人那一行是本 ADR 最要紧的约束**，理由不是税负偏高，是[§6.2](../design/商户类型定义.md) 算过的账：
一件 100 元的货、平台赚 5 元佣金，自营且供应商无票时，平台按 **100 元确认收入**，
付出去的 **95 元不能作为成本扣除** —— **账面凭空多出 95 元利润**。走一单亏一单。

### 3.3 代销还是采购买断：代销

两者都能让平台成为销售主体，选代销的理由是**风险归属**：

| | 采购买断 | **代销（本 ADR 采用）** |
|---|---|---|
| 货权 | 平台先买入 | 仍属商家，售出才结算 |
| 库存风险 | **平台承担** | 商家承担 |
| 应付金额 | 采购价 × 数量，与售价无关 | **售价 − 佣金**，随实际售出浮动 |
| 退货 | 走采购退货 | 直接冲减本期结算额 |

邻里小商家不会接受平台买断，平台也不该压库存。代销在法律上是**行纪**
（以自己的名义为他人利益从事贸易），行纪人与第三人直接建立权利义务 ——
这正是「钱是平台的」的法理基础。

### 3.4 代销成立的四个必要条件：**做不到就退回 B**

| # | 条件 | 违反的后果 |
|---|---|---|
| 1 | 合同相对方是平台（用户协议、订单、条款） | 合同写商家 → 钱是商家的 → 二清 |
| 2 | 平台开票给消费者（全额），商家开票给平台 | 票流与资金流不一致，税务先出问题 |
| 3 | **平台对消费者承担商品与售后责任**，再向商家追偿 | 责任在商家 → 实质是平台模式 |
| 4 | 四流一致：合同、发票、资金、货物指向同一套关系 | 穿透认定按实质定性，名义无效 |

第 3 条是产品上最疼的：**退款、赔付、质量投诉都由平台先扛**。这不是措辞，是真实的资金与人力成本。

### 3.5 展示商家信息：可以，但**表述即法律关系**

代销模式下商家信息照常展示（这是[ADR-004](./ADR-004-增长模型从孵化团长转向商家自带客流.md) 「商家自带客流」的前提），
但措辞决定资金模式的合法性：

| 可以说 | 不能说 |
|---|---|
| 供货商：XX 果蔬 | **本商品由 XX 果蔬销售** |
| 产地 / 门店：XX 店 | **售后请联系 XX 商家** |
| 由 XX 店配送 / 自提点：XX 店 | 「入驻商户」「第三方卖家」这类身份表述 |
| 商家评分、门店主页（作为供货商与服务点介绍） | **「平台仅提供信息展示，交易由商家与您达成」** |

最后一行要特别注意：**那句免责声明恰恰是承认自己是平台模式** ——
写了它就不能再用 A 的资金路径。很多平台是在用户协议里栽的，不是在业务上。

> 因此销售主体的表述必须有**单一来源**（一处配置 + 三端引用），并加守卫。
> 散在各页各写一遍，迟早有人写成「由 XX 商家销售」，而那一句话就改变了整套资金模式的合法性。

### 3.6 端形态的叠加：iOS 是唯一有额外约束的

| 端 | 支付产品 | 对本 ADR 的影响 |
|---|---|---|
| 微信小程序 | 微信支付（JSAPI / 合单） | 无额外约束，A/B 都可 |
| 支付宝小程序 | 支付宝 | 同上 |
| Android App | 微信 App 支付 / 支付宝 | 同上 |
| **iOS App** | 实物与线下服务同上；**数字内容必须走 IAP** | **IAP 的钱进苹果、抽 30%、不支持分账** → 那部分**只能走 A**，且供应商必须能开票 |
| H5（海外） | 另一套通道 | 不在本轮 |

iOS 这一行是[多端多通道方案](../design/多端多通道-平台能力总方案.md)与本 ADR 的交点，此前两份文档都没连起来：
**iOS 上的虚拟商品天然排除 B**，因为苹果不分账。若那类商品的供应商是自然人商户，
两条路径都不通 —— 只能不在 iOS 上卖（`sys_channel_category_rule` 已经能表达这条）。

### 3.7 「提现」的语义按路径分，且**两条都不是「从平台余额提现」**

| 路径 | 「提现」实际是什么 | 依赖 | 现在能做吗 |
|---|---|---|---|
| A 归集 | **供应商申请提前付款** —— 接在既有应付账款链上（`/ops/payables`：对账 → 确认 → 付款） | 无 | ✅ **能** |
| B 直连 | **申请提前分账**（不等冻结期满），[双模方案](../design/结算模式-双模方案.md) 建议叫 `early-release` | 收付通 | ❌ 等通道 |

端上现有的 `Withdrawal` 契约（含 `availableBalance` 可提余额）**两条路径都对不上** ——
平台账上没有「商家余额」这种东西。字段要按 A 重新定义为「本期应付 / 已付 / 待付」。

## 4. 为什么不是别的做法

| 被否掉的 | 否掉的理由 |
|---|---|
| 只做 B（ADR-002 原方案） | 一期没有 EDI，开不了第三方类目；且自然人商户在 B 上还要等通道确认 |
| 只做 A | 拿到 EDI 后，企业商户会要求钱直连自己账户 —— 那是他们的正当诉求，也免去平台承担售后 |
| 平台代收后转账给商家（真 B 方案） | **二清**。被识别就直接停商户号，收款能力当场归零 |
| 按商家自选路径 | 路径决定谁是销售主体、谁开票、谁担责 —— 不是偏好问题。**由类型定** |

## 5. 数据模型影响

1. `mch_entity` 增 `funds_mode`（`AGGREGATED` / `DIRECT`），**由商户类型推导出默认值并校验**，不允许自然人商户设成 `AGGREGATED`（农产品例外）
2. `stl_bill` 快照 `funds_mode` —— 与已有的 `business_mode` 是**两个正交的轴**：前者说钱先进谁的账户，后者说谁是销售主体。压进一个字段会重演 [ADR-013](./ADR-013-经营范围改为多级地理覆盖.md) 那次「两件事一个字段」
3. 代销结算额 = 售价 − 佣金，随退货冲减 —— 与买断的「采购价 × 数量」是不同算式，`stl_bill` 要能表达是哪一种
4. 销售主体表述的单一来源（配置 + 三端引用 + 守卫），见 §3.5

## 6. 落地顺序

| 序 | 内容 | 依赖 |
|---|---|---|
| 1 | `funds_mode` 字段 + 按类型的校验（自然人不得 `AGGREGATED`） | 无 |
| 2 | 销售主体表述单一来源 + 守卫 | 无 |
| 3 | 代销结算额算式（售价 − 佣金、退货冲减） | 1 |
| 4 | 供应商提前付款申请与审批（接 `/ops/payables`） | 3 |
| 5 | B 路径：收付通分账、提前分账、渠道账单对账 | EDI + 收付通 |

**1–4 现在就能做，且不依赖通道**。这与[双模方案 §六](../design/结算模式-双模方案.md)「1–3 现在就能做」是同一判断，本 ADR 只是把它按商户类型重新排了序。

## 7. 会被这条决策推翻的既有判断

- [商户类型定义](../design/商户类型定义.md) §6.3 的警告「**若平台改为代收后再结给商家**，上面一整套结论作废」——
  本 ADR 明确：**A 是代销不是代收**，平台是销售主体而非资金通道，所以那套结论**继续成立**；
  但 §6.3 的约束要加一句：自然人商户在 A 上被禁止，正是因为这条
- ADR-002 只写分账单模，需按本 ADR 补一节说明两条路径并存
