# ADR-050 美业现金线下核心闭环与支付接入分期

日期：2026-10-25。状态：用户确认阶段方向；Task63设计审查及Task64 M1代码关口通过；完整M2～M7现金核心仍在实施，尚未部署。

## 背景

用户要求先完成美业核心逻辑，使用现金及线下方式，暂不接支付链条。Task62-S0共用操作人业务人员事实已验收；Task61原设计将Core/Pay保护作为开工前置，现需调整近期交付顺序。现有OfflineReceiptPort是正式Pay实收链路；旧商家confirmOfflinePay拒绝SERVICE_EXECUTION且触发markPaid副作用，均不能不经分析地用作“无支付链条”的开工开关。

## 决策

当前先做商品/共用订单→人工线下业务准入→真实资源占用→任务作业/参与→完工关闭/订单履约→具体任务日历。线上支付、Pay份额保护/自动退款、储值/次数权益及复杂收银后置；原全范围目标保留。默认沿用先收后服务，前台人工确认现金/线下已收，不新增未获授权的赊账/后付规则。

人工确认表达真实受权经办人对现金/线下已收的声明和业务准入，保留方式、时刻、原操作与版本/撤销审计；不是stl_payment或银行/通道核验。Core可基于该权威声明推进合法人工收款状态，必要时标明MANUAL来源，不能仅由服务完工推导已付；精确状态复用由Task63审计决定，不强制新造未付状态机。商品/价格/订单/来源和数量权威归共用所有者，人员/容量归共用人员资源；美业不复制金融/订单账。

人工模式须由服务器绑定到适当来源，不能把在线/已付/资产来源改标签以跳过既有退款约束。真实买家与临客归属、未付关单、取消/售后/履约与开工数量竞争必须在无Pay模式下获得真实合同；不能伪造顾客会话、guestNo充userNo或把UNKNOWN改成READY。Task63须审计这些现有模型限制，提出精确可实施切片后才编码。

人员权限、技能任职、资源真实占用、幂等/原号未知恢复、审计日志/outbox及历史完成量不可省略。旧SERVICE_EXECUTION通用完工拦截继续保留；专用服务履约与人工准入分别定义。已存在的正式线下/线上收款代码及历史证据不删除或改写。

## 实际审计后的工程选择（Task63设计已审查）

Core现有OFFLINE待收状态不受普通未付自动超时选择器影响，但现有managed markPaid必须核Pay回执且会触发结算/会员等副作用。选择专用Core人工确认转换，真实受权经办人对原额确认后可复用PAID业务状态，绑定不可变MANUAL来源；保留原markPaid门禁，审计所有PAID自动选择器/事件消费者与资金/退款入口，当前模式不触发Pay链条。购买确认与支付路由分开，仅新人工模式免除Pay网关/资金/商户渠道配置前置，不全局跳过原购买/支付规则。

现有order/subOrder/createIntent的user_no及checkout buyer_no必填，临客不能直接当作用户号。当前选择共用Core显式USER/GUEST对手方及条件非空约束的受控增量；先支持真实已识别顾客，下一有界片补真实临客及其购买证据，均属于本阶段核心范围。精确字段/所有读写影响和迁移在Task63独立设计关口冻结；不是本ADR已创建或应用迁移。

## 取舍与验证

缩短近期交付链，优先验证美业业务闭环；代价是人工声明不具备银行核验/正式支付对账或自动资金逆向能力。界面、报表和接口必须区分人工登记、业务执行与正式资金事实，后续接入不得重复累计或覆盖原历史。

设计/代码/必要隔离MySQL9.7.2与HTTP测试/审查/编译先完成；正式部署仍按用户原要求统一后置。方案/表/接口存在不等于可营业或已部署。实施细节及AC→测试见主TDD§0.3/§2.41/§2.42及已审查Task63设计；Task63设计阶段未创建迁移或修改业务源码，Task64已按精确清单启动编码，新迁移首次原生执行前另核实际文件。

### Task64 bound-confirm transport authorization ruling
Actual CheckoutAccessPolicy.requireCurrentCashier requires a real HOST merchant token/session; existing machine delegation alone intentionally fails it. Preserve that legacy guard. New manual CONFIRM supports two explicit ingress authorities: HOST requires current real cashier session; remote requires a verified exact MANUAL_SERVICE_ADMISSION/CONFIRM/MERCHANT binding and the complete original request digest, followed by the same live scoped canonical account checks for CASH_RECEIVE and MANUAL_CONFIRM. It cannot carry a consumer/HOST token, impersonate C, grant roles, reuse another endpoint/action/scope/payload or become a durable authorization.

Exact additional files: CREATE backend/shop-base-auth/src/main/java/ai/neargo/shop/auth/BoundActionContext.java; MODIFY backend/shop-base-auth/src/main/java/ai/neargo/shop/auth/BoundDelegatedCalls.java and src/test/java/ai/neargo/shop/auth/BoundDelegatedCallsTest.java in the same module. Only the existing token-first/route-validated helper installs context through package-private entry; store binding+original digest, not raw payload/token; match a reconstructed complete confirm envelope. A private digest function from the verified binding helper may be retained within this call. Always restore prior context in finally, including nested failure. Mismatched verified context denies and cannot fall back to HOST. Manual owner rechecks current canonical permissions/account/scope immediately before its transaction; verified transport is not current permission.

Within existing ManualServiceAdmissionProtocolTest, real owner/controller confirmation must succeed with this verified binding and no HOST token, deny revoked permission/changed payload, and retain original key/revision/amount/scope rules. GREEN finite additions because the shared helper changed: BoundDelegatedCallsTest (including absent/wrong-token/purpose/payload/nested-cleanup assertions), plus ONLY CheckoutCashPermissionFlowTest#ownerWildcardResolvesActualAccountButDelegationIsNotCurrentCashAuthorization to verify old cash denial unchanged. This is not a full BM04 replay; ablation/restored remain one settlement-filter testcase. Actual packaged topology/deployment remains the final gate.
