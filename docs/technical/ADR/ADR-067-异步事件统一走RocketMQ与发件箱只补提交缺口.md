## 背景

所有异步工作今天都走一张发件箱表 `sys_outbox`，进程内投递器逐个调消费者。盘点 155 处发布（TDD §1.4）后看到：

- 约四分之一的发布没有消费者，已删；只发通知的 10 处已改成提交后发（`AfterCommitNotifications`）；同库的 2 处已改成直接调用。
- 默认的旧投递模式下，**一条事件的所有消费者在同一事务里、失败一起重投**。按消费者独立记进度的统一模式（ADR-039）已实现但默认没开。
- 通知消费者只对站内信去重，短信、企微群、邮件、推送、微信订阅每投一次发一次。别的消费者一失败，**商户可能收到同一单最多 10 条来单短信**。
- 拆库（ADR-066）之后，跨库的消费者越来越多；一个进程内的投递器无法横向扩，也不能让别的进程订阅。

用户 2026-11-27 决定：**异步统一走 MQ**，并要求区分“哪些只要 MQ、哪些还要发件箱”。

## 决策

1. **选 Apache RocketMQ 5.x，用官方原生 Java 客户端 `rocketmq-client-java`（gRPC，连 Proxy）。**
   不用 `rocketmq-spring-boot-starter`，也不用 Spring Cloud Stream：本仓库已定不引入 Spring Cloud（ADR-060、ADR-062），
   而且那个 starter 没有跟上本仓库的 Spring Boot 与 Jackson 大版本。生产者与消费者的装配自己写，几十行。

2. **一个事件只发一条 MQ 消息，按事件类型、以最严格的那个消费者定走法**（逐处清单见异步与通知清单 §〇）：

   | 走法 | 条件 | 怎么发 | 处数 |
   |---|---|---|---|
   | MQ 直发 | 消费者都只是通知；或有按业务表扫描的兜底作业 | 业务事务**提交后**发 MQ，不落发件箱 | 45 |
   | 发件箱 → MQ | 有一个消费者丢了会造成钱、货、权益、出餐上的实际损失，又没有兜底 | 业务事务里写待投递记录，中转程序发 MQ，发成功才标记已发 | 57（+ 迁移期 4） |
   | 源头改发 MQ | 现在只是把别处的事件再转发一次 | 撤掉中转，由源头按上两行之一发出 | 8 |

   混合事件不拆：消费者各自订阅、各自一个消费组，彼此的失败与重试互不影响。

3. **发件箱只剩一个用处：补“业务提交”与“发出消息”之间的缺口。** 待投递记录放在**产生它的业务库**，
   与业务表同一事务写入（TDD §3 Q1）。现在的 `OutboxDispatcher` 从“进程内调消费者”改成“发到 MQ”；
   重试、退避、租约、死信沿用现有字段。

4. **消费者代码不改。** 消费端由一个适配器从 MQ 收消息、还原成 `SysOutbox` 信封、调现有的 `OutboxConsumer.consume`。
   **消费组 = 现有的 `handlerId`**；顺序键非空的事件用 RocketMQ 5 的顺序消息（消息组 = 聚合号）；
   主题按域分（通知、交易、库存、物流、权益、商城渠道源、餐饮），标签 = 事件类型。

5. **发布入口只有一个：`OutboxEventBus.publish`。** 由它按“这个事件类型有没有必达消费者”决定落不落发件箱。
   已改的 10 处 `notifyAfterCommit` 改回 `publish`。

6. **传输可切换，默认不变**：`shop.events.transport=local|rocketmq`，默认 `local`。
   `local` 下，MQ 直发类由进程内线程池提交后投递（现在的 `AfterCommitNotifications`），发件箱类由现在的投递器投递；
   没部署 RocketMQ 的环境行为与今天一致。

7. **所有消费者按事件号幂等**（MQ 也是至少一次）。通知的外部通道要按“事件号 + 通道 + 收件人”去重，
   去重记录用统一防重能力，不在业务库建技术表。

## 被否掉的方案

| 方案 | 为什么不选 |
|---|---|
| 全部 MQ 直发，彻底不要发件箱 | 提交后、发出前进程崩溃或 broker 不可用，这条就丢了。对通知可以接受，对扣库存、发权益、出餐不行 |
| 用 RocketMQ 事务消息代替发件箱 | 每类事件都要写一个“按业务状态回查”的接口，57 处各写一份；发件箱给了统一的回查依据，而且 `local` 模式不需要 MQ 也能跑 |
| Kafka | 运维与资源对这个规模偏重；顺序与延时要自己拼；团队与已有的 Nacos 都在阿里系生态 |
| RabbitMQ | 没有原生的按键顺序消费；大量堆积时性能下降明显 |
| Redis Streams | 生产上 Redis 目前也不是必选组件，同样要新部署；持久化与消费组语义弱于专用 MQ |
| 只开 ADR-039 的统一模式，不上 MQ | 能解决“消费者互相连累”，但仍是单进程投递、不能横向扩，也解决不了通知的重复外发 |
| `rocketmq-spring-boot-starter` / Spring Cloud Stream | 见决策 1 |

## 后果

- **多一个要运维的中间件**（NameServer、Broker、Proxy）。.80 与 UME 166 目前都没有，部署与备份由谁负责另定；
  部署之前一切照 `local` 跑。
- `local` 模式下，MQ 直发类仍是“进程内、失败只记日志”，可靠性要到切成 `rocketmq` 才提升。这是有意的过渡。
- 兜底作业成为 MQ 直发类的安全网，必须按业务表扫，而不是按发件箱扫；清单里 A8–A13 要逐个核实，核实不过的改走发件箱。
- 外部通道去重是这次顺带要补的缺陷修复；不补的话，MQ 重投照样会重复发短信。
- 撤回代价低：传输切回 `local` 即可；发件箱表与投递器始终保留。
- 守卫要加：发布入口只有 `publish`；每个事件类型的走法与清单一致（以现状为基线的守卫测试）。

## 实施顺序

1. 发布入口收成 `publish` + 按必达消费者决定落不落发件箱（`local` 传输，与 MQ 无关）。
2. 通知外部通道按事件号去重。
3. 传输抽象 + RocketMQ 实现（默认 `local`），本机装单机版跑集成测试；先切 MQ 直发类。
4. 发件箱中转改发 MQ，消费者改订阅，按域逐个切。
5. 撤中转（清单 §〇 C 类）。
