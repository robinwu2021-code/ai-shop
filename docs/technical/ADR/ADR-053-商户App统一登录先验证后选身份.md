# ADR-053 商户 App 统一登录：先验证、再列身份、凭票据进入

## 背景

一个人可能既是自己店的店主、又是别家店的员工。商户 App 已按 mock 做完「登录后列出身份让他选」的界面（E09 / E09b / E09c），正式包里被拦着，因为后端没有接口（TDD L1）。

现状（出处均在 TDD §1 / L2 的现状表，可在代码里找到）：

- `POST /biz/auth/login` 是一步登录：店主优先；名下无主体且是手机验证码时，改签员工会话（`BizAuthController#login` 调 `MerchantStaffService#issueStaffSession(phone)`，后者只取 `is_primary` 优先的**一条**员工行）。`POST /biz/auth/staff-login` 已标 `@Deprecated`，仍在。
- 2026-08-15 拍板「**后端按身份判，不让人先选**」，理由是「他可能选错，而选错的表现是进去什么都看不到」（[注册登录-方案梳理](../reference/注册登录-方案梳理.md) §四）。
- 验证码一次性：`OtpStore.verifyAndConsume` 验完即删。所以「验证」与「进入」一旦拆成两步，中间必须有东西记住「这个人已证明过哪个手机号 / 邮箱」。
- 员工行 `mch_account` 只有 `login_phone` 与可空的 `user_no`，**没有登录邮箱列**；ADR-051 决策 3 规定邮箱登录不参与员工匹配。
- `MerchantStaffServiceImpl#add` 只收 `\d{11}` 的手机号：台湾员工今天连加都加不进来；台湾没有可用短信通道（`shop.sms.mock-prefixes` 覆盖的号段只存码不发）。
- `TokenStore` 只有 `revoke(token)` 与 `revokeUser(userNo)`，没有「踢掉除当前外的全部」；USR 会话里只装 `userNo` 与昵称（`LoginUser`），不装手机号。
- `GET /biz/merchant/profile`（`BizMerchantController.MerchantProfileVO`）不带任何身份信息，App 冷启动不知道自己当前是哪个身份。

## 决策

1. **登录拆成两步：先验证并列身份，再凭一次性票据进入。**
   - `POST /biz/auth/identities`（匿名）：只验证码 / 密码，**不建账号、不写凭证、不签会话**；返回 `ticket` 与 `identities[]`。
   - `POST /biz/auth/identities/enter`（凭票据）：重新校验所选身份仍有效后签会话，响应与 `/biz/auth/login` 同形。身份已失效时回 10404、**票据不作废**，并带重算后的列表供改选。
   - 已登录换身份：`GET /biz/auth/identities/mine` 签一张换身份票据，`enter` 成功后吊销来源会话。
   - 票据存新表 `usr_login_ticket`：只存 SHA-256 哈希、5 分钟（`shop.auth.login-ticket.ttl`）、成功进入才以条件更新核销，只能进签发时列出的身份（外加 `NEW_OWNER`）。
   - **推翻 2026-08-15 拍板的哪一部分**：推翻的是「任何情况下都不让人选」——一个人确有多个身份时，由他本人在列表里选。**保留**的是那条拍板的理由与核心：登录页不出现「老板 / 店员」角色开关；列出的只是服务器按已验证凭证**查出来**的真实身份，零个、一个身份时都不选（App 直接进入），所以不存在「选了一个自己没有的身份、进去什么都看不到」。
   - **为什么推翻**：原拍板时的模型是「一个手机号要么是店主、要么是员工」，`/biz/auth/login` 店主优先、员工只取一条；对「既是店主又是别家员工」「是多家店员工」的人，后端替他选的结果就是另外的身份永远进不去。只有本人知道此刻要进哪家店。
2. **店主只列一个 `OWNER` 身份，不按主体拆（D2）。** USR 会话本来覆盖名下全部主体（`BizIdentityResolverImpl` 按门店反查主体），按主体拆成多条是假选择。多主体时 `merchantName` 为 null、另给 `entityCount`；`storeCount` 为名下全部门店数。员工身份每个员工行一条，`identityNo = STAFF-{mchAccountNo}`，号码稳定，供 App 记忆「上次进入的身份」。
3. **修订 ADR-051 决策 3：员工身份按「这个人已验证的手机号」匹配，与登录入口无关。** 手机验证码登录用本次号码；邮箱验证码或密码登录，用该账号在 `usr_identity` 里已绑定的手机号去匹配 `mch_account.login_phone`；账号没绑手机就列不出员工身份。理由：同一个人用邮箱或手机登录，看到的身份应当一样；绑定的手机号在绑定时已验证过，拿它认员工与手机验证码登录同等强度。ADR-051 的决策 1、2、4 不变（邮箱仍是独立凭证、仍不自动合并）。
4. **台湾员工登录走「员工行加登录邮箱」（D4）。** 决策 3 只救得了「绑过手机的邮箱账号」，台湾账号绑不了手机，所以对台湾员工无效。做法：`mch_account` 加登录邮箱，店主按邮箱加员工，员工用邮箱验证码登录即可列出 STAFF 身份。它**另开一份 1 档 TDD**，与统一登录**同一个版本上线**（不单独先上统一登录而让台湾员工无路可走）。届时员工匹配从「已验证的手机号」扩为「已验证的手机号或登录邮箱」，是对 ADR-051 决策 3 的再一次修订，由那份 TDD 记录。接入台湾短信通道作为长期方向另行跟进。
5. **旧入口的下线节奏（D11）。** `/biz/auth/login` 保留为兼容入口，语义（店主优先、不让选）不变，**至少保留到 uni-app B 端停用**；它与 `/biz/merchant/profile` 响应里的 `merchant` 只多一个字段 `currentIdentity`。`/biz/auth/staff-login` 在商户 App 正式包切到统一登录后，看访问日志**一个版本周期无调用**再删。
6. **换手机 / 绑邮箱后，发起变更的当前会话保留（选型 E4）。** 令牌不换、响应不带新令牌；同一人在 MERCHANT 池的其它会话经新增的 `TokenStore#revokeUserExcept(userNo, keepToken)` 作废，CONSUMER 池全部作废。注销不适用这一条（见 ADR-054）。
7. **冷启动的当前身份由 `GET /biz/merchant/profile` 给（选型 F1）。** `MerchantProfileVO` 末尾加 `currentIdentity`，形状与 `identities[]` 元素相同，由 `LoginIdentityService#current` 算，与 `/identities/mine` 的 `currentIdentityNo` 同一方法；`/biz/auth/login`、`enter` 的响应经 `profileOf` 自动带上。只读，不写票据。

## 后果

- 正面：「店主兼别家员工」「多家店员工」都能进到每一个自己的身份；零身份时不预先建账号（员工本来不需要 C 端账号，见 `MerchantStaffService` 类注释），只在用户选「我要开店」（`NEW_OWNER`）时才建；冷启动不再丢身份；换手机时在途请求不会因令牌作废回 401。
- 负面：多一张票据表、一次往返；`TokenStore` 加一个方法，五个实现各一份；`/biz/auth/login` 与统一登录两套入口并存一段时间，两边的登录限制（10450 / 10451 / 10429 / 10454 – 10457 / 60001）与测试身份白名单须保持一致（TDD AC9、AC10）。
- 风险与缓解（TDD §4）：票据被截获 → 只存哈希、一次性、5 分钟，强度与截获验证码相同；10404 不核销票据 → 只能进票据里的身份、每次重校；当前会话保留 → 走到换手机须同时拿到当前凭证与新号两个验证码，且其它会话全部作废、变更留痕。
- 依赖：决策 4 的 TDD 未写完之前，统一登录不上线。
- 不可逆点：App 正式包切到两步登录、`staff-login` 删除之后，再回到「后端替人选」就要求 App 回滚登录流程；所以单独记录。

## 被否决的选项

- **沿用 `/biz/auth/login` 签店主会话、响应附 `identities`，换身份再走 `/mine` + `enter`（A2）**：只是员工的人会先被签一个空的个人会话，并被「登录即注册」建一个 C 端账号，而员工本来不需要它。
- **登录页先选「老板 / 店员」（A3）**：正是 2026-08-15 否掉的做法，选错就进去什么都看不到。
- **多主体店主每个主体列一个 OWNER（D2-B）**：点哪条进去会话都一样，是假选择。
- **票据放内存缓存（B2）**：`OtpStore` 是单实例内存，会话已外置，票据退回内存就成了新的单点。**无状态签名票据（B3）**：做不到一次性，要吊销只能等过期。
- **邮箱登录继续不列员工身份（维持 ADR-051 决策 3 原文）**：同一个人换个入口就看不到自己的员工身份。
- **台湾员工：接入台湾短信通道（D4-B）**作为一期解法：时间不由研发决定；**员工用手机号 + 店主设的初始密码（D4-C）**：密码要挂在 `mch_account` 上另造一套凭证，初始密码由店主转交有泄露面；**一期不解决（D4-D）**：台湾员工端整体不可用。
- **统一登录上线即删 `login` / `staff-login`（D11-B）**：旧版 App 与 uni-app B 端立刻登不进。
- **凭证变更后全部作废、响应带新令牌（E1）**：换令牌前已发出的请求回 401，App 把它当登录结束踢回登录页；**宽限旧令牌（E2）**：五个 `TokenStore` 实现各做一份带时限的撤销，`DbTokenStore` 跨实例靠撤销轮询，宽限与轮询周期叠加难测；**App 串行化请求（E3）**：推播回调、后台刷新等也要挡住，漏一处就复现。
- **冷启动调 `/identities/mine`（F2）**：每次冷启动写一张票据、多一次往返；**`/biz/auth/account` 带当前身份（F3）**：同样多一次往返。
