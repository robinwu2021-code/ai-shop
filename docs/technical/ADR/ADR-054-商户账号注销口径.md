关联：[TDD-商户App统一登录与账号](../TDD-商户App统一登录与账号.md) §2 端点 7、8，§3 选型 D，§4，已拍板 D7 / D8 / D10 / D14 · [ADR-053](./ADR-053-商户App统一登录先验证后选身份.md) · [ADR-051](./ADR-051-B端账号允许邮箱作为独立登录身份.md)

## 背景

商户 App 已做好「注销账号」界面（P14），后端没有 B 端注销接口（TDD L2 现状表）。现状（出处均在 TDD §1，可在代码里找到）：

- C 端已有注销：`POST /mp/user/deregister` → `UserServiceImpl#deregister`。它**只查买家在途单**（`OpenOrderPort#hasOpenOrders(userNo)`，有则 70028），通过后物理删 `usr_identity`、`PersonService#deregister`、匿名化 `usr_account`、状态置 `DEREGISTERED`、CONSUMER 与 MERCHANT 两池 `revokeUser`。
- B 端店主的 `usr_account` 就是 C 端账号（`BizAuthController#login` 走同一个 `AuthService#login`）。所以**今天店主从小程序注销不会被拦**：`usr_identity` 被删，`mch_account` 店主行原样留着，门店成了无人能登录的店。
- 按商户 / 门店判「在途单、待拨款、未到期付费方案」的只读口子后端**没有**，`hasOpenOrders` 只按买家判。
- 门店停用 = `READONLY`（`StoreAdminServiceImpl#setStatus`），但**默认店不能停用**（10400）；门店转让后端完全没有。草案原定的「名下有未停业门店就拦」因此会让**任何有店的店主都永远注销不了**（TDD §1「顺带发现」、D14）。
- 一个人可能同时是别家主体的在职员工（`mch_account` 按 `user_no` 或 `login_phone` 匹配的行）；员工行若留着，同号的新账号仍能经手机号进入（D8）。
- `需求矩阵-三端.md` 1.3 写过「注销与冷静期」，C 端落地时没有做冷静期（D10）。

## 决策

1. **注销是匿名化，不是删除；不可逆。** 沿用 C 端口径：从 `UserServiceImpl#deregister` 拆出与入口无关的核心（删 `usr_identity`、人档解绑、匿名化、`DEREGISTERED`、两池踢人），B 端与 C 端入口共用。注销后同一手机号 / 邮箱再来，是**全新账号**，不恢复旧账号的任何关系（与 ADR-051 决策 2「不自动合并」一致）。注销连发起请求的当前会话一并作废（与 ADR-053 决策 6 换手机保留当前会话不同：人已不存在）。
2. **主体、门店、交易记录保留；名下门店全部置只读（D14）。** 注销时，在同一事务里把本人名下**全部**门店（含默认店）置为 `READONLY`；主体、订单、结算原样保留（App 文案 `delWarn`：「門店、主體與交易紀錄依法保留」）。门店「随人冻结」而不是随人删除。默认店不能停用是门店管理接口 `POST /biz/store/{storeNo}/status` 的规则，该规则不变；注销事务自己做这一步。
3. **前置检查的判据只看三项，不再看「有没有门店」（D14）。** 门店层面拦注销的只有：
   - `OPEN_ORDERS`：名下门店有进行中的订单或售后；
   - `PENDING_PAYOUT`：收款账户有待拨款项；
   - `PAID_PLAN_ACTIVE`：门店方案有未到期的付费期间。

   另保留 C 端既有的 `BUYER_OPEN_ORDERS`（本人作为买家的在途单，即今天的 70028 那一条）。草案的 `ACTIVE_STORES` 不再作为拦截项。三个门店域的只读查询各在订单、资金、方案域补一个，经 `spi` 端口给 `MerchantDeregisterPrecheck` 用。提交注销时先验码（目标由服务器按账号算出的 `verifyBy` 决定，不信请求），再在同一事务里**重跑**前置检查，防「检查完到提交之间又来一单」；不满足回 `DEREGISTER_BLOCKED`（建议 70100）；业务异常不带 `data`（`GlobalExceptionHandler#onBiz`），App 被拦后重新调 precheck 取 `blockers[]`。`verifyBy` 为 null（当前凭证都收不到码）时不能自助注销，引导联系客服。
4. **小程序注销入口也走同一份商户前置检查（D7）。** `/mp/user/deregister` 对名下有主体的人调用同一个 `MerchantDeregisterPrecheck`，不满足时回同一个 `DEREGISTER_BLOCKED`。目的是堵住上面「店主从小程序注销、门店无人能登录」的现存漏洞；小程序要认这个新错误码。
5. **本人在别家的员工身份一并停用，不拦注销（D8）。** 注销时本人的全部 `mch_account` 行（`user_no` 为本人的行，以及按本人手机号 `login_phone` 匹配的别家员工行）置 `DISABLED`，并在各家主体的员工变更记录里写一条。precheck 用 `staffMemberships` 提示「註銷後將退出 n 家店的員工身分」。App 的 `delStaffNote`（「員工帳號由店主停用，不走這裡」）与原型 P14 由 App 改。
6. **一期不设冷静期（D10）。** 与 C 端一致；前置检查已保证没有在途的钱和货。法务明确要求时再加，届时 B、C 两端一起补。
7. **逐笔留痕。** 注销写 `usr_account_change_log(DEREGISTER)`，号码只存脱敏值（TDD AC22）。

## 后果

- 正面：有店的店主能在 App 内自助注销，不依赖今天不存在的转让或运营端关店工具；改动集中在注销事务里；小程序入口的现存漏洞被堵上；员工身份不会留给「下一个用这个号的人」。
- 负面：
  - 默认店只读后买家侧找不到这家店；同一主体日后要复用，须运营恢复门店状态。
  - 订单、资金、方案三个域各要补一个只读查询；漏一个域就会出现「有待拨款的店主注销后无人收款」。缓解：提交时事务内重跑，三个端口各有一条「有数据就拦」的测试（TDD §4、§5 AC17 / AC19）。
  - 小程序要新认 70100；App 要改 `delStores`（改为「註銷後名下門店將停止營業」，去掉「或轉讓給其他店主」）、`delStaffNote` 与 P14。
- 待实施时补明：TDD 端点 8 写明了 B 端入口通过后的「成员行停用」步骤；小程序入口通过检查后须执行同一套店主处理（门店置只读、成员行停用），否则决策 4 只堵了一半。实施时在 TDD 里写清，本文的口径是两个入口处理相同。
- 不可逆点：注销后凭证物理删除、账号匿名化，无法恢复；门店只读而非删除，是这一条里唯一可由运营回退的部分。

## 被否决的选项

- **有店就不能在 App 内注销，交客服处理（D14-A）**：要运营端关店 / 转让工具，今天没有，需另开；用户在 App 里「處理 ›」无处可去。若日后产品不接受「门店随人冻结」，退回此项并同时立项运营端关店工具。
- **先给店主加「关店」接口再注销（D14-C）**：要新定「主体停业」状态及其对收款、下单兜底、门店码的影响，范围过大。
- **门店转让（D14-D）**：后端完全没有，牵涉主体与收款账户过户，一期不现实。
- **按「有未停业门店」拦截（草案原定）**：默认店不能停用，有店的店主永远注销不了。
- **小程序入口不拦店主（D7-B）**：保留门店无人能登录的漏洞。
- **员工身份不拦也不停用（D8-B）**：人已注销，按 `login_phone` 匹配的员工行仍能被同号的新账号进入。**有员工身份就拦注销（D8-C）**：要先让各家店主停用他，用户自己做不到。
- **设冷静期（D10-B）**：要一张待注销表和一个定时任务，C 端也要跟着补；一期没有法务要求。
- **物理删除账号及其数据**：交易记录依法须保留；沿用 C 端已落地的匿名化口径（TDD §3 选型 D），不另立一套。
