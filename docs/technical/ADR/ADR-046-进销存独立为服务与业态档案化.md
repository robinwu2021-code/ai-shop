# ADR 046 进销存独立为服务 `inventory`，业态差异档案化，商城也经服务调用

## 1 背景

1. 共享充电宝平台 ShareHub 要管设备仓储（入库、发货给商家、退货回仓、盘点），自己只有调拨与差异两块；ai-shop 的进销存在单据、流水、盘点、冻结上已成熟，领域模型立项时就以「可独立交付」为约束。ShareHub 侧提交了把 `shop-inventory` 提成独立服务的方案（`handoff/sharehub-进销存/`）。
2. 将来还有充电桩及其它业态要接入；它们的单据用途、收货方、放行凭证都与电商不同。
3. 今天的「可独立部署」只是 `shop-app` 换 `openapi` profile 多起一份：仍要商城主库、Redis、商城登录，只有 3 个只读 / 同步接口。外部系统接不进来。
4. `shop-inventory` 依赖 `shop-base`、`shop-base-auth`、`shop-store-mybatis`：28 个外部类、123 处 import；`shop-app` 有 37 个文件反向引用它。
5. 支付服务已有「一份代码、内嵌 / 独立两种形态」的先例，但它只做到进程独立 —— 父 POM 仍是 `shop-parent`，仍依赖 `shop-base` 等。

## 2 决定

1. **进销存成为独立服务 `inventory`**，不再是 ai-shop 的一个业务模块：
   - 目录 `backend/inventory/`，父 POM `ai.neargo:neargo-build-parent`，坐标 `ai.neargo.inventory:inventory-{api,domain,guard,svc,client}`，包 `ai.neargo.inventory`，配置前缀 `inventory.*`，进程 `neargo-inventory.service`。名称里不带 shop。
   - **允许以 Maven 包依赖不含业务的基础包**：`neargo-common-core`、`neargo-common-data`、`neargo-common-web`（仅 svc）、`job-api`、`svc-client`。**禁止**依赖 `shop-base`、`shop-base-auth`、`shop-store-mybatis` 及任何 ai-shop 业务模块，禁止 import `ai.neargo.shop.*`。由 ArchUnit + enforcer + 单独构建三道闸门守住。
   - 代码暂留 ai-shop 仓库，按「整目录可搬走」写；迁出时机见 TDD §7.2 Q5。
2. **同一个构件，部署形态由配置决定**（2026-10-29 用户定）：**测试环境共用一套**，装下全部业态以充分验证逻辑的通用性；**生产按两套部署** —— 电商套（只放行 `SHOP`，库 = 现商城进销存库 `ai_shop_inv` 原地升级）与设备套（放行 `SHAREHUB` 与充电桩，新库）。每套内按系统码 + 业主隔离；每个系统一把服务凭证，凭证只在所属实例签发，服务以凭证中的系统与业主**覆盖**请求参数，并拒绝不在本套放行范围内的系统。两套之间的差异只允许出现在环境文件里。
3. **商城也经服务调用**（`inventory-client`）。下单走预留协议：预留同步强一致；`confirm` 移出订单事务，改为订单事务写 Outbox、事务外幂等投递；`expires_at` 自动回收兜底。内嵌形态只作切流过渡与回滚，按业主灰度（`write_authority`），全部切完后删除。
4. **业态差异走配置**：业主级、带版本的业态档案定义能力包、外部目标类型与层级、出入库用途及其收货方规则、放行凭证类型。内核不出现业态名。只有新状态机才加能力包，加能力包要写 ADR。
5. **启用序列号**：`trackingMode = SERIAL` 的物料逐件管理（SN 档案 + 在库周期）；ShareHub 柜与宝都按 SN，并以「组装关系 + 扫柜码展开 + 成套随动」降低扫码量。数量物料行为不变。
6. **库存只管仓内**：签收（领取）后不再跟踪；质检、出库后的位置、人员与角色、运营界面都归调用方。人不直连库存服务。
7. 定时任务注册到共用任务服务（`ai-shop-job`），不自建调度。

## 3 理由

| 决定 | 为什么 |
|---|---|
| 独立服务而非 profile | profile 方案要求外部系统「先装一个 ai-shop」；领域模型的 A1（零跨库引用）、A2（自有身份）就是防这个 |
| 基础包允许、业务包禁止 | 基础包不带业务语义也不带运行时；`shop-base` 带 22 个业务域的契约，`shop-store-mybatis` / `shop-base-auth` 传递带入 Redis 与 Spring Security —— 后者正是今天单独起不来的根源 |
| 测试一套、生产两套 | 测试共用一套，内核里藏着的业态假设与隔离漏洞会在同一个库里暴露；生产分开，电商的下单锁库存（高频、在关键路径上）不被设备的批量作业（上千 SN 的过账、全仓盘点）拖慢，一套出事不波及另一套。`system` 维度保证分合只是部署问题（同 ADR-025 的思路） |
| 商城也走服务 | 领域模型 §二 已证明预留协议下跨进程仍是同步强一致；两种长期形态意味着一套没人测。生产订单数为 0，切流风险最低的时候就是现在 |
| 档案而非代码分支 | 充电宝、充电桩、电商、餐饮的差异经逐项比对都落在「用途 / 目标 / 放行 / 能力开关」四类规则里 |

## 4 被否决

| 方案 | 理由 |
|---|---|
| 沿用 `openapi` profile 多起 `shop-app` | 无写接口、无 SN、无出库池；仍要商城主库、Redis 与整套装配 |
| 作为 Java 库嵌入各宿主 | 带入全部商城假设；账本分散在各宿主库里；版本被宿主绑死 |
| 各宿主各自建库存 | 重写单据、流水、盘点、冻结，口径长期分叉；ShareHub 做过完整设计后放弃 |
| 生产所有业态共用一套 | 设备批量作业与商城锁库存争用同一个库的连接、锁与 IO，爆炸半径覆盖全部业务 |
| 每个系统一套实例 | 套数随系统增长；按负荷特征分两套已够，第三类业态按特征归入其一 |
| 测试环境也按生产分两套 | 失去「同库多业态」对通用性与隔离的压力测试；改为上线前临时按生产形态演练一次 |
| 商城长期内嵌 | 两套装配长期并存，一套无人测；与「脱离 ai-shop」方向相反 |
| 零依赖（基础件全部自写） | 用户裁决：基础代码可经 Maven 包依赖；自写约 10 个类且与框架重复 |
| `shop-` 前缀或 `ai.neargo.shop.inventory` 包名 | 服务不属于商城；名字会把下一个接入方引向「这是商城的东西」 |

## 5 后果

- [TDD-进销存模块化与独立部署](../design/TDD-进销存模块化与独立部署.md) §2.2 ~ 2.3 对**部署形态**的结论作废；其「定义归商品域、数量归进销存域」的边界不变。
- `shop-inventory` 保留为 **ai-shop 侧的适配模块**（商城 BFF、Port 实现、报表适配），不再含领域代码。
- 订单侧 `confirm` 的事务语义改变（事务外投递），是 ai-shop 唯一的语义改动，需在 M8 单独验收。
- 进销存不可用时商城不能下单（今天进程内挂了也一样），熔断即拒单。
- 迁移表与 `inv_flyway_history` 名称不变；新迁移接 V15 之后。
- [进销存-数据库表结构](../design/进销存-数据库表结构.md) 的表清单与张数在实施对应迁移时同步更新（有守卫测试）。
