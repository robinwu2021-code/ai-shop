# ADR-063 发票独立成模块，税制与开票通道走 SPI

> 状态：已决策（2026-11-21）；依据 [PRD-发票开立与打印](../../requirements/PRD-发票开立与打印.md)，
> 设计见 [TDD-发票模块](../TDD-发票模块.md)。

## 一、决策

1. **发票是独立业务域 `invoice`**，代码放 `backend/invoice`（`invoice-domain` + `invoice-channel`），
   表族前缀 `inv_`，与 `logistics` 同一形态：依赖 `shop-base` 与 `shop-store-mybatis`，**不依赖 `shop-core` 与任何行业插件**。
2. **行业只通过一个 Port 开票**：`ai.neargo.shop.spi.invoice.InvoicePort`（在 `shop-base`）。
   零售、餐饮、美业把「来源单 + 冻结明细 + 买受人选择」交进来，发票模块不读行业表、不重新算税。
3. **税制是 SPI**：`InvoiceRegime`（编号规则、买受人校验、证明联内容、上传报文）。首期只有 `TW_EGUI`（台湾电子发票）。
   主流程（幂等、取号事务、状态机、上传任务、打印）与税制无关。
4. **开票通道是 SPI**：`InvoiceGateway`（加值中心 / Turnkey）。首期只有本地桩通道 `STUB`；正式通道签约后加实现类。
5. **证明联走共享打印中心**：发票模块产出业务打印事实（场景 `INVOICE_PROOF`），打印中心负责模板、设备、重试与补印留痕；
   打印中心补齐 `barcode` / `qrcode` 两种版面块（zxing 生成位图）。

## 二、理由与替代方案

| 方案 | 结论 |
|---|---|
| A. 放进 `shop-core/trade`，挨着 `ord_invoice_request` | ❌ 那是「线上事后申请、平台人工开」，与门店当场开立是两个流程；放进 core 后餐饮独立部署（food-server）无法复用 |
| B. 每个行业插件各做一套 | ❌ 字轨号段是**主体级**唯一资源，三处各取号必然重号 |
| C. 独立模块 + Port + 税制 SPI | ✅ 号段唯一持有者只有一个；行业只依赖 `shop-base` 里的接口；以后拆服务只换 Port 实现 |

不选「按国家写死分支」：台湾、阿联酋、大陆的编号与上传完全不同，写在主流程里会让每加一个地区都改核心事务。

## 三、约束

- 字轨号段是**唯一不可回收**的资源：取号与发票落库在**同一事务**；作废不归还号码。
- 同一来源单同时只能有一张有效发票（数据库唯一约束兜底），作废后可重开。
- 发票明细与金额是**开立当下的冻结事实**，之后不随商品改名、改价变化。
- 加解密用的 AES 密钥不进业务表，走 `secret` 模块的密钥引用。
- 本模块不承担线上订单事后申请开票（V94），两者并存，不合并。
