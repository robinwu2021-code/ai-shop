# ADR-002 结算走微信支付分账，支持打款到个人

状态：**已决策（2026-08-05，用户确认）· 落地细节待与支付服务商核对**
关联：[ADR-001 商家端形态](./ADR-001-商家端形态与拆分时机.md) · [C端功能清单](../../requirements/C端功能清单.md)

---

## 1. 决策

1. **结算走微信支付分账**（不做平台先收后付的自建结算）
2. **支持分账到个人账户**（个人微信零钱），让个体户不必先注册公司就能开张
3. **EDI 资质暂不处理**，一期以平台自营主体收款、分账给入驻方的形态先跑起来
4. 产品目标不变：**入驻容易、做生意容易**

---

## 2. 为什么分账是对的选择

**分账不是「先收后付」的变体，它就是为了解决二清而存在的官方通道。**

自建结算（钱进平台账户 → 平台自己转给商家）属于「二次清算」，无支付牌照不可做。
微信支付分账则是：资金进平台商户号后处于**冻结待分**状态，由微信按平台的分账指令
直接划给接收方 —— 平台从头到尾没有资金支配权，因此不构成二清。

这条路径同时满足了「结算合规」和「打款到个人」两个需求，方向没有问题。

---

## 3. 落地要点与约束

| 项 | 说明 |
|----|------|
| 接收方类型 | 支持**个人**（`PERSONAL_OPENID`）与**商户号**（`MERCHANT_ID`）两种 |
| 接收方报备 | 分账前必须先调接口**添加分账接收方**，未报备无法分账 |
| 分账比例上限 | 单笔订单可分账金额有上限，**具体比例需与支付服务商/微信支付确认**（不同签约模式不同，不要按经验值写死） |
| 分账时限 | 订单完成后需在规定期限内完成分账，超期资金解冻回平台商户号 —— **结算调度必须有超时兜底** |
| 退款与分账顺序 | 已分账的订单退款需先「回退分账」再退款，**退款链路必须把分账回退算进去** |
| 个人接收方限额 | 分账给个人通常有单笔/累计限额，**同样需与服务商确认后再定商家结算周期** |

> ⚠️ 上面三处标注「需确认」的数值我没有写具体值 —— 这类参数各签约模式不同且会变，
> 按经验值写进代码是给自己埋雷。**接入前必须从支付服务商处拿到书面口径。**

---

## 4. 「入驻容易」的正解：把资质产品化，而不是绕开它

用户诉求是「入驻容易、做生意容易」。但有两条不能绕：

**（1）个税代扣代缴**
平台向个人支付经营所得/劳务报酬，**平台是法定扣缴义务人**。
小规模时容易被忽略，一旦规模化就是硬合规问题（追缴 + 滞纳金）。

**（2）个人接收方的限额天花板**
个体户做大之后，个人分账的限额会先于业务触顶。

**建议的三段式路径 —— 门槛前低后高，商家无感升级：**

| 阶段 | 商家形态 | 收款方式 | 平台侧动作 |
|------|---------|---------|-----------|
| 冷启动 | 个人（无照） | 分账到**个人微信零钱** | 报备接收方；平台代扣个税 |
| 成长期 | 个体工商户 | 分账到**个体户商户号** | **平台内提供「一键代办个体工商户」**（市面有成熟服务商，最快 T+3 出照） |
| 成熟期 | 企业 | 分账到企业商户号 | 常规商户入驻 |

**关键在中间那一步**：把「注册个体工商户」做成平台里的一个按钮，而不是丢给商家自己跑工商。
这才是「入驻容易」的真正实现方式 —— **不是没有资质，而是资质由平台代办掉**。
同时它一次性解决了限额与税务两个问题。

## 5. 对代码的影响

数据模型已经按多商家建好（`merchantNo` 贯穿商品 / 订单行 / 评价），分账所需的
「一笔订单拆到哪几个商家、各分多少」已经具备推导条件。还需补：

- [ ] `Merchant.settleAccount`：接收方类型（个人 openid / 商户号）+ 报备状态（**后端持有，C 端不暴露账户信息**）
- [ ] 订单**按商家拆单**：一个购物车跨商家时拆成多笔子订单，分账以子订单为单位
- [ ] 结算单模型：应分金额、已分金额、分账状态、超时兜底、退款回退
- [ ] C 端信息披露：订单详情标明「本单由 XX 商家提供并收款」（分账场景的披露要求）

## 6. 待确认

1. 分账比例上限、时限、个人接收方限额的**书面口径**（找支付服务商要）
2. 个税代扣的执行方案：自己算并申报，还是接第三方灵活用工/财税服务商
3. 「一键代办个体工商户」接哪家服务商，代办费谁承担（平台补贴会显著降低入驻门槛）
4. 平台佣金从分账里扣，还是另行收取
