# ADR-036 pay内积分业务模块与平台出资预存

状态：待确认，v3 · 起草/更新：2026-10-14

上游：[独立PRD](../../requirements/PRD-积分模块.md) · 展开：[资金方案](../design/积分资金方案-平台预存池.md)、[TDD与开发计划](../TDD-积分域重整.md)。本稿取代ADR-006成本模型、旧商家发分费模型以及本ADR v2的C+R备付口径；尚未表示已实施或已批准业务参数。

## 背景

旧代码计提商家费用金不等于收到备款，线下抵扣和积分退款存在无资金支持路径。v2提出平台预存与四类积分户，但review指出：R支撑的可用积分无法核销；接收户被回流后无法退款；协议解约影响在途；定期确认到付款的退款状态缺失；内存提交回调不能可靠恢复；迁移遗漏发放头寸。

用户要求积分独立为pay内业务模块，并形成完整需求、业务/技术方案和开发计划；已确认积分尚未上线，直接使用最新逻辑并移除旧方案。

## 决策提案

1. 积分集成现有pay-domain，独立为ai.neargo.shop.pay.points业务包及pts表族；复用payTxManager/paySqlSessionFactory，不新增JAR、数据源或部署服务。订单/售后经shop-base/spi/points，结算经pay.points.app.PointsSettlementHook；资金接口与适配留在pay内，必要积分/结算结果同事务提交。
2. 平台先备款再发分：U对应发放、C对应用户及门店、D应付、B退款备付。R单独应收，不参与资金覆盖恒等式；新核销hold提前预留B最大退款额度。
3. RECEIVE分退款预留与可回流。仅权威退款责任解除后可回流；TOPUP先用自由积分，绝不使用仍须保留的分。
4. 商家签受理协议，全额兑付；hold固定在途协议/比例/路径/方式；默认随单，归集可定期，直连定期无能力不开放。
5. 支付后返待生效，结算终局转正剩余部分；线下不返/不抵，积分形式售后退款下线。购物返分按件/商品现金实付，折现金额不超过商品现金实付。
6. 退款准备与确认分阶段、结果不可变重放；现金结果未知不撤销。待追回时B垫付返分，追回回补B。现金扣减不超本次可退额；补收未回平台不得记U，不支持部分由平台承担。
7. 核验备款支持的TOPUP与现金补收可新增发行；补B不发行，历史退款预留不作为现金不足收回的分来源。此条修订v2“仅TOPUP发行”，保持所有新增发行均有钱。
8. 付款意图先提交、外部执行后结果确认；超时只查不以失败重发；定期账单按修订确认，抵销成功才冲R/补B，账期唯一逻辑单可重算。
9. 凭证原子过账、条件非负、稳定锁序、唯一业务键及payload冲突拒绝；订单/售后与pay各自事务Outbox，跨域积分Inbox/账与出站同pay事务；pay内结算Hook同步协作，不人为制造异步事务边界。账务审计只追加。
10. 账户滚动到期，准备时保持备付、收入划拨明确成功后完成清零/出账；暂停按受影响不可用区间并集顺延。首次上线前完成全链路与真实资金验收；新系统产生承诺后暂停新增仍继续收尾。

11. 积分未上线，采用最新业务内核直接改造现有接线，删除旧服务、SPI、任务、积分费、配置与旧接口；不实现旧数据搬迁、新旧路由、兼容版本或迁移开账。数据库结构通过新增Flyway脚本更新，已应用脚本保持不变。

## 取舍

| 方案 | 收益 | 成本 / 结论 |
|---|---|---|
| pay内独立业务包及共享pay事务 | 独立职责、统一写账，结算/积分可原子更新 | 包级依赖守卫与付款短事务，采用；不新增构建或部署边界 |
| B备付+R分开 | 退款可兑付且实际资金覆盖 | 多一笔风险预算，采用；U临时垫付/追回后可用不满足已有承诺 |
| 接收户预留 | 不妨碍历史退款 | 回流变慢，采用；未明确窗口不能释放 |
| 事件与分阶段恢复 | 不依赖跨域共享事务 | 更多准备/意图/结果记录，采用 |

## 不可逆与后果

对外受理承诺、兑换比例、平台出资、发行与积分归属改变后不能直接切回旧余额。订单/售后事务与pay事务独立，不能用源回滚清除已提交pay占用；需要持久化阶段与补偿。pay内结算与积分账务可共享短事务，但外部付款不能随数据库回滚。B额度、退款预留的资金占用需要运营接受。

模型和任务见TDD；生产预算、协议文本、比例/账期及通道能力在PRD列待确认。状态保留待确认，本次只形成文档计划。
