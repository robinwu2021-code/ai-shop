# ADR-004 增长模型：从「孵化团长」转向「商家自带客流 + 邻里自发团购」

状态：**待确认** · 创建 2026-08-05
关联需求：[C端功能清单](../../requirements/C端功能清单.md) · [需求矩阵-三端](../../requirements/需求矩阵-三端.md) · [待完成功能清单](../../requirements/待完成功能清单.md)
关联决策：[ADR-001 商家端形态](./ADR-001-商家端形态与拆分时机.md) · [ADR-002 分账结算](./ADR-002-结算走微信支付分账.md) · [ADR-003 报价不审核](./ADR-003-报价不审核而用锁价公示信用防加价.md)

---

## 1. 背景

现有需求文档里**并存着两套互相打架的增长引擎**：

| | 引擎 A：社区团购 | 引擎 B：邻里购物平台 |
|---|---|---|
| 出处 | C端清单 §一、§14、§15、§17、§18 | C端清单 §五之三、§五之四 |
| 核心资产 | **团长**（孵化 → 裂变 → 逐单抽佣） | **商家密度**（入驻 → 报价 → 撮合） |
| 归属键 | `leader_no` | `merchant_no` |
| 用户来源 | 团长拉群 | 商家自带客户 + 邻里自发 |
| 谁赚钱 | 团长抽佣 | 商家卖货，平台收服务费 |

两套模型的角色表、归属键、结算链路都不同，同时实现会得到一个自相矛盾的产品。必须选一套。

同时业务侧明确了平台定位：**服务小商家，让创业容易**；流量起来后再引入大商家。

---

## 2. 决策

**选定引擎 B，删除引擎 A。** 具体三条：

### 决策 1 —— 删除「团长」角色

团长不是一个角色，原有职责一分为二：

| 原团长职责 | 新归属 | 报酬形式 | 法律性质 |
|---|---|---|---|
| 发起团、拉邻居 | **C 端普通用户**（无身份、无门槛、无申请） | **无额外报酬**，与参团者同价 | 消费者促销 |
| 自提点、收货、分拣、核销 | **B 端入驻小商家** | **履约服务费**（按件），走分账 | 经营所得 |

`leader_no` 归属键整条删除。

### 决策 2 —— 团购发起人不得有任何额外收益

发起人拿到的价格、权益、券，与参团邻居**完全一致**。

### 决策 3 —— 门店主页可分享，作为一期主获客路径

每个入驻商家有一个**可独立分享、可扫码直达**的店铺主页，商家用它把自己的存量客户导入平台。
**排期上优先于团购与裂变。**

---

## 3. 决策理由

### 3.1 为什么删团长

**（1）团长是引擎 A 的产物，它的职责在引擎 B 里已被覆盖。**
`C-GB-05`（C 端发起团实例）和 `C-RQ-06`（求团发起人选定报价）已经把「组织邻居一起买」这件事做完了。§14/§15 的 16 个功能点是社区团购模式带进来的冗余。

**（2）「自发省钱」与「专职抽佣」是两种不相容的动机。**
业务定位是「利我利他、为了省钱」。省钱的动机闭环在价格里：我想便宜买，我拉五个邻居，够人数大家都便宜，我也便宜。**成团价本身就是奖励，平台不需要额外出钱。**

**（3）报酬形式决定法律性质。**

| | 发券/立减（决策后） | 按单打现金（原方案） |
|---|---|---|
| 性质 | 消费者促销 | 劳务报酬 / 经营所得 |
| 个税代扣 | 不涉及 | **平台是法定扣缴义务人** |
| 分销层级红线 | 不涉及 | 三级涉传销（R1） |
| 提现风控 | 不涉及 | 必须做 |

一次性消掉 R1（分销合规）、R5（佣金税务）、R8（一社区多团长）与矩阵 M5（佣金与分账扣减顺序）四个风险项。

**（4）个人团长不稳定，小商家稳定。**
便利店/粮油店/驿站本来就有营业时间、存放空间、可升个体户商户号，跑路成本高。个人团长搬一次家就断一个自提点。

### 3.2 为什么发起人不能有额外收益

**一旦发起有额外收益，就会长出职业发起人**，随之是刷团、僵尸团、归因扯皮，绕一圈回到抽佣模型。

「发起人与参团者同价」不是省钱，是**防守设计**。

> 附带结论：C端清单已定的「单档成团、不做阶梯价」在省钱模型下更站得住。
> 阶梯价的作用是给发起人持续拉人的动力（拉到 20 人我更赚），那是抽佣模型的产物。

### 3.3 为什么门店分享是主获客路径

**这是成本最低、质量最高的获客。** 一个粮油副食店有 200 个稳定老客，店主把店铺码印在包装袋、发进自己的客户群，这 200 人带着**既有复购习惯**进来。

| | 门店分享 | 团购裂变 |
|---|---|---|
| 启动条件 | **一个店主就能启动** | 需社区内先有足够人数 |
| 用户质量 | 熟客，有复购习惯 | 陌生人，一次性 |
| 获客成本 | ≈ 0 | 需补贴 |
| 产生真实订单速度 | 立刻 | 需等成团 |

而且它正好解决当前的验证困境：交易链路做完了没有真实订单可验证（见[待完成功能清单](../../requirements/待完成功能清单.md) §五）。

**关键产品要点：粮油副食不是「逛」出来的。**
这类品类的复购路径必须压到三步内：**打开 → 常买 → 下单**。
店铺主页第一屏对登录用户应当是「我买过的」，不是店招 Banner。这与生鲜团购的「逛今日团」是两套信息架构，不复用页面。

## 4. 角色模型变更

### 变更前

```
游客 → 用户 → 有归属用户 → 团长候选 → 正式团长 → 带教上级
                                    ↘ 商家
```

### 变更后

```
游客 → 用户 → 有归属用户 ─┬─ (可发起团：只是一个动作，不是身份)
                          └─ 商家（个人 / 个体户 / 企业）
                                  ↳ 店员（P1）
                                  ↳ 服务人员 / 配送员（P1）
```

| 端 | 变更前角色数 | 变更后 | 变化 |
|---|:---:|:---:|---|
| C 端 | 7 | 6 | 删「推广员」；「求团发起人」降级为团实例上的 `ownerId` 字段 |
| B 端 | 7 | 4 | 删团长候选、正式团长、带教上级 |
| 平台端 | 11 | 10 | 「社区/团长运营」并入「商家运营」 |

## 5. 数据模型影响

### 5.1 归属键

| 归属键 | 变更 |
|---|---|
| `leader_no` | **删除** |
| `community_no` | 保留（我在哪个社区） |
| `pickup_no` | 保留，但**多数情况下等于 `merchant_no`**（见 5.2） |
| `merchant_no` | **新增归属语义**：我常在哪家买 |

`community_no` 与 `merchant_no` **正交** —— 用户可以在 A 社区却常买 B 店。

### 5.2 小店 = 商家 + 自提点，合一 ⚠️ **已被 [ADR-005](./ADR-005-履约方式与自提点模型.md) 修正**

~~粮油店本身就是取货点，不需要额外配自提点实体。`Merchant` 上直接带 `isPickupPoint`，省掉一层实体映射。~~

**修正**：这个简化**只对「到店自提」成立**。业务补充明确后还有**邻里自提**（送到团发起人家里），
承接方是**用户而非商家**，`Merchant.isPickupPoint` 表达不了。

改为独立 `PickupPoint` 实体，区分 `type: STORE | NEIGHBOR`、`scope: PERMANENT | GROUP_INSTANCE`。
详见 [ADR-005](./ADR-005-履约方式与自提点模型.md)。

> ⚠️ **邻里自提必须零报酬** —— 一旦有报酬，承接的邻居就是团长，本 ADR 消掉的四个合规问题会原样回来。
> 因此它只能限定在「自己发起的团」范围内，不能开放为「任何人可申请做自提点」。

### 5.3 双入口，价格口径必须统一

| 入口 | 商品池 | 典型场景 |
|---|---|---|
| 逛平台 | 按 `community_no` 的社区商品池 | 生鲜今日团 |
| 进店 | 按 `merchant_no` 的店铺商品池 | 粮油复购 |

⚠️ **同一 SKU 在两条路径下的价格必须同源**，否则会出现「店里 8 块、平台 7 块」的投诉。
建议：价格只挂在 `merchant_no + sku` 上，社区池是它的一个筛选视图，不单独定价。

### 5.4 新增字段 `Order.trafficSource`

用于区分客流来源，直接决定费率（见 §6）：

| 值 | 含义 | 费率 |
|---|---|---|
| `MERCHANT_OWNED` | 商家自带（店铺码/店铺分享进入） | **低费率或零佣金** |
| `PLATFORM` | 平台分配（首页/搜索/推荐/团购） | 正常费率 |

## 6. 跳单问题与费率策略

我们在主动鼓励商家把自己的客户导进平台。**那商家第二单为什么不直接微信转账？**

靠合同和技术封锁没用，只能靠平台提供他自己做不到的东西：

1. **收款与对账** —— 分账到零钱，比微信转账清楚
2. **送货上门的配送履约**
3. **一键代办个体工商户**（[ADR-002](./ADR-002-结算走微信支付分账.md) §4）
4. 将来的供应链进货

**因此：对自带客流的小商家，一期费率应极低甚至零佣金。**

他带进来的客户是平台的净增量，从这单抽 5% 是捡芝麻 —— 那个客户后来在**别家**买的东西才是西瓜。

技术落点就是 §5.4 的 `trafficSource`：**「商家自带客流」与「平台分配客流」分别计费。**

---

## 7. 「将来引入大商家」的预留

一期只有小商家（手机上传商品、单品维护、分账到个人零钱）。大商家需要的批量导入、ERP/API 对接、账期结算、专属类目，一期**不做，但留位**：

- `Merchant.tier`：`PERSONAL` / `INDIVIDUAL_BIZ` / `ENTERPRISE`
- 商品维护区分「手工录入」与「批量渠道」两个入口，后者一期留空
- 与 `tenant_no=MAIN` 是同一种预留手法：**分层做成配置，不做成两套代码**

## 8. 被否决的方案

| 方案 | 否决原因 |
|---|---|
| 保留团长，只是不抽佣改发券 | 团长的申请/审核/培训/考核/等级/退出六套流程照样要做，成本没省，还留着一个没有动机的角色 |
| 团长与商家并存，各管一摊 | 两套归属键、两套结算链路、两个入驻流程；自提点归谁产生权责真空 |
| 发起人给小额奖励（如免运费） | 有收益就有职业发起人，刷团与归因问题原样回来；且要为此建归因与防刷，成本远超收益 |
| 商家团做阶梯价 | 阶梯是给发起人持续拉人的激励，属抽佣模型产物；且已参团者差价退回逻辑复杂 |
| 门店主页复用现有商家详情页 | 商家详情页是「了解这家店」的信息页；门店主页是「快速复购」的交易页，第一屏内容完全不同 |
| 靠协议禁止商家私下交易 | 无法执行；正解是提供商家自己做不到的能力，见 §6 |

## 10. 排期影响

一期批次顺序调整（**门店主页提前，团购与裂变后置**）：

| 批次 | 变更前 | 变更后 |
|:---:|---|---|
| M1-1 | 交易闭环 | 交易闭环（不变） |
| M1-2 | 履约闭环（团长核销台） | **商家入驻 + 门店主页**（让第一批店进来卖起来） |
| M1-3 | 供给闭环（团长+商家入驻） | **履约闭环**（自提点履约台：核销 + 分拣） |
| M1-4 | 营销与评价 | 营销与评价（不变） |
| M1-5 | 增长与消息（裂变 + 群发助手） | **团购（商家团为主）+ 消息** |
| M1-6 | 资金 | 资金（不变） |

理由：门店主页一个店主就能启动并立刻产生真实订单，正好为 M1-3 的核销与 M1-4 的评价提供真实数据。团购需要社区内先有人，放后面。

> ⚠️ 冷启动补充：**一期的团绝大多数应当由商家和运营铺出来（商家团 B 发起），不是等用户自发。**
> 自发是模式成熟后的形态，不是启动方式。这与 C端清单 §五之四「初期必须靠运营把第一批需求人肉接住」是同一判断。
