# ADR 062 服务注册与发现用 Nacos 原生客户端

状态：已接受（用户 2026-11-19 决定「基于 nacos，pay、aishop 都接入进来，先用 aishop 接入」）；ai-shop 一侧已实现，默认关闭。
关联：[TDD-网关层与统一权限-五层架构对齐](../TDD-网关层与统一权限-五层架构对齐.md) §2.24；[ADR-060](ADR-060-网关层独立模块与鉴权不进路由网关.md)。

## 背景

服务地址今天全部写在配置里（`shop.services.targets.<服务>`），由 `ServiceLocator` 这一个接口读出来。
那份接口的注释写明了它为换服务发现方式留的位置：调用方只知道服务名，换实现时调用点一行不改。
生产上各进程都在 166 一台机器的回环地址上，所以配置一直够用。

现在 192.168.3.80 上装了 Nacos 3.3.0，用户要求支付与 ai-shop 都接入，先接 ai-shop。

## 决定

1. **用 Nacos 的原生 Java 客户端（`nacos-client`），不引入 Spring Cloud / Spring Cloud Alibaba。**
2. **服务发现是给 `ServiceLocator` 加一个实现**（`NacosServiceLocator`），调用点不改。
3. **逐个服务接入，按名单走。** 只有在 `shop.nacos.discovery.services` 里登记了「本仓库服务名 → Nacos 服务名」的服务才向 Nacos 要地址；没登记的照旧读配置。
4. **Nacos 给不出健康实例，或 Nacos 本身不可用时，回落到配置里的地址。** 所以 `shop.services.targets.*` 不删，它是兜底。
5. **本实例在应用就绪后登记为临时实例，停机时摘除。** 登记失败不影响启动，后台每 30 秒重试。
6. **总开关 `shop.nacos.enabled` 默认关。** 关着时不创建客户端、不建连接，行为与今天相同。
7. **这一步只做注册与发现，不做配置中心。** 配置仍然是环境变量与配置文件。

## 被否的方案

| 方案 | 为什么不选 |
|---|---|
| Spring Cloud Alibaba Nacos Discovery | 本仓库没有 Spring Cloud（ADR-060 已定不引入），父工程是跨项目共用的，加 Spring Cloud 的依赖管理要先动别的项目；而我们要的只是「按服务名给一个地址」和「启动时登记一次」，各几十行 |
| 一次把所有服务都改成从 Nacos 取 | 支付、库存、餐饮今天都还没有登记进 Nacos，全切过去等于全部调不通。按名单逐个接，才能「先 ai-shop、再支付」 |
| Nacos 取不到就报错，不回落 | 注册中心是新加的一环；它出问题时让原本能调通的服务调不通，是用一个新故障点换来的 |
| 同时把配置搬进 Nacos 配置中心 | 密钥在环境文件里有成套的发布与备份做法；搬配置是另一件事，要单独评估 |

## 后果

- 多了一个运行时依赖（约 15 MB 的客户端包）和一个要运维的组件。Nacos 现在是单机、内置存储、没有备份；它挂了不影响调用（有回落），但登记信息会丢。
- 登记的地址要求对端可达。生产上 ai-shop 的实例只绑 `127.0.0.1`，登记进去的地址别的机器连不上 —— 目前登记的作用是「看得见有哪些实例、是什么版本」，而不是「别人能按它来调」。要让别的机器按登记地址调用，得先把监听地址放开，那是另一个决定。
- Nacos 开着鉴权，接入方需要一个 Nacos 账号；账号口令与其它密钥一样放环境文件。
- 支付（near-pay）接入要在它自己的仓库里做同样的事：登记自己，并在 ai-shop 的名单里加一行 `PAY: <它登记的服务名>`。
