# ADR-008 共享组件库与四端部署

日期：2026-08-06 ｜ 状态：已实施

## 背景

C 端与 B 端是同一套技术栈（uni-app + Vue3 + TS）、同一套设计语言。抽取前两端各有一份：

| 文件 | 两端差异 |
|------|---------|
| `sh-icon.vue` / `sh-rating.vue` | **逐字节相同** |
| `stores/theme.ts` / `app.ts` / `market.ts` | **逐字节相同** |
| `sh-scaffold.vue` | 只差一行（C 端多渲染飞入动效层） |
| `sh-tabbar.vue` | 差购物车角标、落点登记与弹跳 |
| `sh-theme-sheet.vue` | 差切语言/切市场后要重拉什么 |

这些是换肤、三语 RTL、多市场的地基。两份复制品必然漂移，而且漂移的表现是**只在一端出现的样式或语言 bug**——最不容易被发现的那类。

同时要解决三件事：PC 浏览器上能正常看（现在铺满 1920px）、四端（小程序 / H5 / Android / iOS）都能出包、H5 的部署形态。

## 决策

### 1. `packages/ui`：共享组件 + 三个同构 store

差异**不用条件编译、不用 `if (isCApp)`**，走应用级注入 `configureShell()`（`packages/ui/src/shell.ts`）：tabs 从哪来、角标怎么算、切语言后重拉什么、菜单挂载后要不要量落点。

判断标准很简单：**新写一个 D 端，只要能提供这份配置就能直接用这套外壳，不必改组件库一个字**。做不到这点的抽取是假抽取。

### 2. 常驻覆盖层用约定组件 `<app-overlay>`，不用动态组件

原方案是把组件对象放进 shell 配置、由 `<component :is>` 渲染。**小程序端直接编译失败**：`<component is=""/> is not supported`。
改为约定：`sh-scaffold` 无条件渲染 `<app-overlay>`，两端各自提供 `src/components/app-overlay.vue`（C 端是飞入小球，B 端是空的）。编译期就能定死的约定，四端都成立。

> 这条是「H5 跑通不等于四端跑通」的第一个例子。

### 3. 组件库要软链进**每个 app 自己的** `node_modules`

小程序编译按「相对 app 根目录」写出每个组件的产物路径。包在根 `node_modules`（npm workspaces 的默认位置）时算出来是 `../node-modules/@ai-shop/ui/...`，rollup 拒绝越出根目录的 chunk 路径，构建直接失败。

因此：`scripts/link-ui.mjs`（挂 `postinstall`）把包软链到 `c-app/node_modules/@ai-shop/ui` 与 `b-app/...`，并在两端 vite 配置里开 `resolve.preserveSymlinks: true`（否则会解析回 monorepo 真实路径，等于没链）。

> 第二个例子：H5 与 dev server 全程正常，只有 `build:mp-weixin` 会炸。

### 3b. 组件库必须排除在依赖预打包之外

`optimizeDeps: { exclude: ["@ai-shop/ui"] }`。

vite 把 `@ai-shop/ui` 当普通 npm 依赖预打包时，会把它 import 的 `@shared/*` **一并内联进产物**，
于是 `money.ts` / `datetime.ts` 里的模块级 holder 出现两份：market store 调
`setCurrentCurrency("USD")` 改的是副本，页面读到的仍是 CNY。

表现是「切了地区，价格还是 ¥」。类型检查、单测、三端构建**全部通过**，
只有在界面上切一次市场才看得见 —— 抽取组件库最隐蔽的一个后果。

### 3c. 底层一律共享，两端只留「自己的那部分」

小程序不合并成一个包，**不代表代码要分两套维护**。抽完组件后又下沉了四样：

| 下沉的东西 | 去处 | 原状 |
|---|---|---|
| 全局样式基座（设计语言 + 皮肤变量 + 通用积木 + 宽屏适配） | `packages/ui/src/styles/base.css` | 两端 App.vue 各 ~400 行，**逐字节相同**，还由 gen-skins 同时往两处写 |
| UnoCSS 配置（主题色映射 + 圆角五档） | `packages/ui/src/uno.config.ts` | 两端各 45 行，完全相同（根目录只留一行转发，因为 unocss 要求配置在项目根） |
| i18n 引擎（createI18n + 切语言 + 同步 shared 当前语言） | `packages/ui/src/i18n.ts` | 两端各一份；**词条仍各自维护**，只有装配方式共享 |
| HTTP 传输层（uni.request 封装、鉴权头、错误归一） | `packages/shared/src/net/http-client.ts` | 两端各 68 行，只差一个入参类型（取更宽的那个） |

顺带删掉了 `i18n-bridge.ts`：i18n 实例进了组件库之后，`stores/app` 可以直接改语言，
那座桥是「库不认识 app 的 i18n 实例」时的将就办法，前提没了就不该留着。

**没有下沉的**：`main.ts`（15 行，uni 要求在 `src/main.ts`，且它 import 的正是各端自己的 App 与词条）、
`env.d.ts`（环境声明必须在各自 tsconfig 作用域内）。都属于「抽了反而多一层间接」。

现在两端 `src/` 下剩的全是**真正属于自己的东西**：页面、业务组件、契约与 mock、词条、导航。

### 3d. 抽取的判据：两端都在用、且语义相同

B 端照 C 端做 UI 优化时又清出两批共用件，判据只有一条 —— **两端都在用、且语义相同**：

| 抽到哪 | 什么 | 依据 |
|---|---|---|
| `packages/ui` | `sh-empty` | 27 个页面各写一份（B 13 / C 14），结构全同，padding 在 60/80/100rpx 之间随手取值 |
| `packages/ui` | `sh-tabs` | 12 个筛选条，且**存在两套实现**（chip 横排 vs 方块 `tabs__item`）—— 抽的同时统一 |
| b-app 全局样式 | `.field*` 表单件 | 11 个页面各一份，**已经漂移**：4 个页面 88rpx/30rpx、3 个页面 84rpx/28rpx。只有 B 端用（C 端几乎没有表单），不进平台层 |

**没抽**（写下来是为了下次不再重新讨论）：C 端商品卡 ↔ B 端商品行（语义不同：买不买 vs 管不管）、
工作台 ↔ C 端首页、`actionbar`（只有 C 端有）。为「将来可能共用」提前抽，
是把耦合写进平台层。

配套断言在 `ui-package.test.ts`：页面不许再自定义 `.empty` 与 `.tabs__item`。
这个仓库已经因为「复制一份更快」漂移过好几次，抽完不加约束，下一个页面照旧复制。

### 4. 宽度自适应：手机按机型缩放，桌面收成居中窄栏

一个参数分两段，靠 `pages.json` 的 `globalStyle`（**不是 manifest 的 h5 段** —— 写那里
uni 运行时根本读不到，桌面端 rem 仍跟着窗口宽度放大，界面整体被拉大而不自知）：

| 宽度 | 行为 |
|---|---|
| ≤ 600px | `rpxCalcMaxDeviceWidth: 600` —— **按设备自身宽度缩放**：320 的 SE、390 的 13、412 的安卓、430 的 Pro Max 各自铺满，字号与留白按比例自适应 |
| > 600px | `rpxCalcBaseDeviceWidth: 375` —— 固定按 375 渲染，并收成 375 的居中版心 |

三处必须对齐：`--sh-app-max` = 375、媒体查询断点 = 601、`rpxCalcBaseDeviceWidth` = 375。
`packages/shared/tests/ui-package.test.ts` 有断言守着——对不齐会出现一整段宽度里
「按 A 缩放却铺 B 宽」，字号与留白全都错位，肉眼只觉得「有点怪」，极难定位。

版心取 **375**：这套界面的原始画布宽度（750rpx 设计稿 = 375pt），也是 uni 自己的默认 rpx 基准。
中途取过 480、又取过 390 —— 数值一大，同样的 rpx 内边距在版心里占比就更高，
列表看着就散（用户的原话是「间距变大、结构松散」）。回到 375，桌面端与手机**逐像素同构**。

**框与滚动的分工**（两次踩坑换来的）：

```
.sh-frame     固定、与视口等高、带 transform，自己不滚
.sh-scaffold  在框内部滚
```

- transform 放在框上：让框成为页面里那十几处 `position: fixed` 悬浮条的**包含块**，
  它们自动跟着窄栏收窄，不必逐页改 left/right（漏改一处就横跨整屏）
- 滚动**不能**放在框上：那样框既是包含块又是滚动盒，而相对滚动盒定位的元素会
  跟着内容一起滚 —— 底部菜单会随下滑飘到页面中间
- 框上必须写 `min-height: 0`：`.sh-root` 自带的 `min-height: 100vh` 会压过 `top/bottom`，
  框比视口高出一个标题栏，**底部菜单被顶到屏幕外**，看起来就是「菜单没了」
- `bottom` 用 `0` 而不是 `--window-bottom`：后者是 uni 给原生 tabBar 留的 50px，
  而原生 tabBar 已被全局隐藏，跟着留会在底部空出一条

代价只有一个：桌面端滚动条属于内层而非 window，`uni.pageScrollTo` 打不着 ——
统一走 `@ai-shop/ui/scroll` 的 `scrollToTop()`。

窄屏完全不进这个分支：原生页面滚动，行为与之前一模一样。

### 5. 两端各自独立部署，**不合站**（2026-08-06 修正）

```
dist/web/c/    C 端 → 独立域名（如 shop.example.com）
dist/web/b/    B 端 → 独立域名（如 seller.example.com）
```

`npm run build:web` 一条命令产出两个站点。

**原方案是合成一个站点**（C 端根路径、B 端 `/m/` 子路径），理由是海外 H5 同源可以共用
皮肤/语言/市场的本地存储、证书与 CDN 只配一次。**这个理由恰恰是它的致命伤**：

- localStorage 按 origin 隔离，同源就意味着两端共用**同一份**登录态、皮肤、语言，
  连 mock 的整个「数据库」（`sh_mock_db`）都是同一个 key —— 商家端读到消费者的订单
- 两端路由路径完全同名（都有 `#/pages/home/index`），在一个 SPA 会话里从 `/m/` 跳回 `/`
  不会真的重载，页面与外壳对不上（底部菜单消失、组件错位就是这么来的）

省下的那点部署配置，换来的是两端互相污染。**统一管理指的是同一个仓库、同一套底层组件，
不是同一个运行时。**

第二道保险：存储 key 带端前缀（`shc_` / `shb_`，由各自 `.env` 的 `VITE_APP_NS` 决定，
见 `packages/shared/src/utils/constants`）。就算日后有人把两端放回同一域名，存储也各归各。
`packages/shared/tests/ui-package.test.ts` 里有断言守着：两端命名空间不许相同，
业务代码也不许写死 `sh_*` 绕过它。

**小程序照旧两个 appid**：两个主体、两套审核类目，硬塞一个包过不了审，
商家端体积还会拖累消费者端启动。

Android / iOS：Capacitor 各包各的 `dist/build/h5`。

## 后果

- 组件与 store 的单一事实源在 `packages/ui`；改一处两端同时生效
- 新增一条硬约束：**改动了外壳/组件库，必须真跑 `build:mp-weixin`**。本次两个致命问题（动态组件、chunk 路径）在 H5 上都毫无征兆
- `packages/ui` 里可以出现 `#ifdef`（如 `scroll.ts` 的 H5 分支），**页面与业务组件里依旧不许**——这是端能力抽象层的既有边界，不是新开口子
- 桌面端 `uni.pageScrollTo` 失效这件事是全局的：以后再写「滚回顶部」一律走 `scrollToTop()`
- **共享的边界划在「构建期」**：组件、样式、i18n 引擎、传输层可以共用一份源码；
  运行时（域名、存储、路由、包）必须各归各。这次踩的坑全在越过这条线之后

## 未决

- 竖屏平板（601–900px）按桌面处理，两侧留白偏多。要不要给一个中间档等真实反馈再说
- 海外 H5 的默认语言与市场目前仍按本地存储 + 默认值，**尚未按域名/IP 推断**（`market.ts` 留了口子）
