# ADR-010 主数据模型：行业 / 商家主体 / 支付渠道

> 2026-08-07 · 状态：**已采纳并实施** —— 取值统一已执行到第 4 步（V43），第 5 步刻意暂缓（见 §4）
> 相关：[交接-支付通道与行业主数据](../../交接-支付通道与行业主数据.md) M1/M2 · ADR-002（分账）· ADR-006（积分）

## 1. 背景：同一件事有四套取值

「这家商户是什么主体」在库与代码里有四套并存的取值：

| 出处 | 取值 | 用途 |
|---|---|---|
| shared `MerchantType` | `PLATFORM` / `COMPANY` / `INDIVIDUAL` | 展示 |
| shared `MerchantSubject` | `PERSONAL` / `INDIVIDUAL_BIZ` / `COMPANY` | 入驻表单 |
| `usr_merchant_payment.subject_type` | `MICRO` / `INDIVIDUAL` / `ENTERPRISE` | 通道进件 |
| `settleAccountType` | `PERSONAL_OPENID` / `MERCHANT_ID` | 结算账户 |

四套之间的映射**只存在于阅读者的脑子里**。这不是整洁度问题：

- 入驻选 `PERSONAL`，进件要转成 `MICRO`，而「PERSONAL 是不是就是小微」这个判断
  在代码里出现过**三次，各写各的**
- 判错一次的后果不是显示错误，是**商家进件被通道拒**——而那时入驻早已通过、
  商品已经上架，他既收不了款，也不知道为什么

行业（`sys_industry`）与渠道（`sys_pay_channel`）已经先后建了注册表，
主体类型是三件套里唯一还散在代码里的一件。

## 2. 决策

### 2.1 统一模式：表管能力，类型管取值

三样主数据用**同一种结构**：

| 表 | 管什么 | 取值域在哪 |
|---|---|---|
| `sys_pay_channel` | 能不能分账 / 补差 / 打款、支持哪些支付方式、限额 | shared `PayChannel` |
| `sys_industry` | 能不能以小微进件、是否强制开积分 | shared `Industry` |
| `sys_merchant_subject`（本次新增，V41） | 通道码映射、要不要执照、结算账户形态、是否受行业白名单限制 | shared `MerchantSubject` |

**为什么规则进表、取值域进类型**：规则来自通道，会随对方调整而变
（微信调整白名单、支付宝放开小微）。写死在代码里，对方改一次我们要发三个端的版本。
而取值域本身是稳定的——多一个行业码是产品决策，不是通道的日常调整。

### 2.2 主体的权威口径取通道侧

`MICRO` / `INDIVIDUAL` / `ENTERPRISE`，不是 `PERSONAL` / `INDIVIDUAL_BIZ` / `COMPANY`。

理由：主体类型的**唯一硬约束来自通道**——能不能进件、要什么资质、钱打到哪儿。
展示名反而是可以随便改的（「小微商户」改成「个人店」不影响任何逻辑）。
让权威口径贴着约束走，映射就只需要**一个方向**。

### 2.3 三端共用一个只读出口

`GET /common/master-data` 一次给出**启用中的**行业 + 主体 + 渠道。

**为什么合成一个响应**：它们在同一屏上被同时用到——
「选行业 → 据此过滤可选主体 → 主体决定要不要传营业执照」。
分三条接口就会出现「行业回来了、主体还没回来」的中间态，
而那个中间态里表单不知道该不该禁用某个选项。

**为什么挂 `/common` 而不是 `/mp` 或 `/biz`**：三端都要用。
挂在某一端下面，另外两端就得跨端调用一个不属于自己的前缀。

**为什么游客可读**：入驻表单在用户登录之前就要显示行业与主体选项。
里面没有敏感内容——只有取值域与展示名；密钥与平台资金账户（`pool_account_ref`）
不在响应里，有测试断言这一点。

### 2.4 「行业决定可选主体」在提交时生效

微信小微的准入白名单按行业给，线上业态不支持。这条规则落在**提交申请那一刻**，
不是进件那一刻。

放到进件时才拦的后果：入驻早已通过、商家已经在上架商品，
此时告诉他「你这行不能用这个主体」——要么改主体重走一遍资质，
要么这家店根本收不了款，而两条都不是他的错。

端上还要更早一步：`master-data` 里每个行业带 `microAllowed`，
选完行业就把「小微」这个选项禁掉。**让人填完再拒是最差的一种告知方式。**

配套：错误码 `70001 INDUSTRY_SUBJECT_NOT_ALLOWED` 单独一个，而不是复用
`BAD_REQUEST`——端上要据此把「换个主体」这条出路直接说出来。

## 3. 取舍与不做的事

| 选择 | 放弃的 | 为什么 |
|---|---|---|
| 主体建表 | 用 Java 枚举 + 常量 | 枚举改一次要发版；而这些值随通道规则变 |
| 权威码取通道口径 | 保留入驻口径 | 约束来自通道，让权威贴着约束 |
| 保留 `legacy_subject` 列 | 建表时就改名存量数据 | 改名穿透实体/契约/三端/测试，拆成五步各自发布（§4）。前四步已完成 |
| 主数据只读 | 让端上可写 | 它是通道规则的落点，商家与端上都不该改 |
| `industry_gated` 进表 | 代码里写 `if (subject == PERSONAL)` | 这个判断此前出现三次、各写各的 |
| 兜底 `needLicense = true` | 兜底 false | 少要一次执照 = 放进一个不该通过的商家；多要一次只是麻烦 |
| 兜底 `industryGated = false` | 兜底 true | 未知不该凭空加一条限制 |

**支付宝的小微准入尚未确认**：`sys_industry.alipay_micro_allowed` 与
`sys_merchant_subject.alipay_code`(MICRO) 全部保守留空/置 0。
守卫会拦住「想当然照抄微信」。确认前，小微只走微信。

## 4. 存量取值的统一（五步，已走完前四步）

V41 建表时**不改动任何现有列的取值**——改名要穿透实体、契约、三端与测试，
必须拆成能各自发布的小步。`legacy_subject` 列承担翻译，
`canonicalSubject()` 是唯一入口。

真正改名要按这个顺序，且**每一步都能单独发布**：

| 步 | 内容 | 状态 |
|---|---|---|
| 1 | 后端一律经 `canonicalSubject()` 读写主体 | ✅ |
| 2 | 新写入改为权威码，读取仍兼容两套 | ✅ 三个写入点全部改（建商家 / 建分账主体 / 入驻申请） |
| 3 | 一次性刷存量数据 | ✅ V43 |
| 4 | shared 类型合并，三端取值与文案同步 | ✅ |
| 5 | 删 `legacy_subject` 列 | ⏸ **刻意暂缓** |

**不要跳过第 1 步直接刷数据**：那样刷完之后，代码里那三处各写各的判断会各错各的。

### 第 5 步为什么暂缓

`legacy_subject` 是**旧取值的唯一翻译源**。删掉它，任何还在传老码的调用方
（未更新的端上缓存、第三方对接、历史脚本）就从"被翻译"变成"存进一个认不出来的值"。
它只有一列，留着的成本是零；而删早了的代价是脏数据，且不报错。

删的条件：确认没有任何来源还在传旧码（可加一条埋点，`canonicalSubject`
走到 legacy 分支时记一次；连续一个发布周期为零再删）。

### 第 4 步的一个发现

原本打算把类型命名为 `SubjectType`，**被类型对齐守卫拦住**——
那个名字在平台端已经是**风控主体**（`DEVICE`/`MERCHANT`/`USER`）。
两个不同概念同名，读代码的人迟早会把一个当成另一个。最终定名 `MerchantSubject`。

同时确认了一件事：旧的 `MerchantType` 里的 **`PLATFORM`（平台自营）不是主体类型** ——
平台自营的主体也是个企业，「自营」是归属标记。它混在主体枚举里，
让 `usr_merchant.type` 这一列同时承担了两件事。一期没有真实自营商家，暂不为它单开字段。

## 5. 影响

- `usr_merchant.industry` / `usr_merchant_apply.industry`（V40）现在真的能被写入了——
  此前申请单上存了行业，`activate` 却不传，商家主体的行业永远是空的，
  而 `points_forced` 的注释写着「按行业强制开」，那句话一直无法执行
- 同一批修复：店铺简介（`description`）此前也只存在申请单上，
  通过审核后就消失，而 C 端门店页读的正是 `usr_merchant.description`
- 运营侧 `/ops/industries` 系列上线，权限 `industry:manage` **不给 BD**——
  它改的是「哪些行业能开小微」，那是通道规则的落点，不是招商能自行判断的事
