# ADR-029 · 订单对收件人可见：授权来自「同步」，而不是手机号匹配

**日期**：2026-10-08 　**状态**：待确认 　**相关**：[PRD-订单同步给收件人](../../requirements/PRD-订单同步给收件人.md) · [TDD-订单同步给收件人](../TDD-订单同步给收件人.md)

## 背景

下单人和收货人常常不是同一个人。订单上早就存着收件人的姓名与手机号（`ord_sub_order` 的
`receiver_*` 快照，`V69`），但那只是联系方式——收件人本人在平台上看不到任何东西。

要让他看到，就必须回答一个此前这个仓库没有回答过的问题：
**凭什么认定「这张订单该给这个人看」。** 这是可见性决策，放出去容易、收回来难，
所以单独立 ADR。

两条都是不可逆的：**一旦有人看到过本不该看到的信息，撤回记录不能让他忘记。**

## 决定

### 一、可见性的来源是「同步」这个显式动作，不是手机号匹配

- 没有同步记录的订单，收件人**永远看不到**。默认不可见。
- 手机号 hash 只用来**认领**（注册/登录时把已有的同步记录对上人），不作为授权依据。
- 同步可以发生在收件人注册之前；他注册那一刻，此前积累的同步记录**一次性全部生效**。
- 自动同步是「代替下单人点那一下」的便利，不是另一条授权来源：它有平台总闸（**默认关**）、
  只对已注册的人生效、下单人可逐单取消、且**金额一律不可见**。

**为什么不是「号码对上就看」**：那等于把授权判断交给一个**下单人可以打错、运营商可以回收**的字段。
显式同步让「谁能看」始终是下单人的决定。

### 二、同步记录不设有效期，接受号码回收的残余风险

同步记录长期有效，收件人注册后可回溯全部历史单。

**风险是真实的**：手机号被运营商回收重新放号后，新机主注册即可看到旧单的收件人姓名、
收货地址、商品名称。

**仍然这么定的理由**：

1. 加了有效期就和「注册后能看到寄给我的东西」这个核心价值直接冲突——
   收件人注册往往就发生在收到短信之后、订单完结之前后不定，一刀切的 TTL 会把正常场景也砍掉。
2. 暴露面有上界：只有**下单人主动同步过**（或平台总闸开启且对方已注册）的那些单，
   不是全量订单。默认不可见把面积压得很小。
3. 有对冲手段：下单人可随时**撤回**；金额默认不可见，泄露的不含交易金额。

**这条是明确接受风险，不是没想到。** 如果将来出现真实投诉，补救方向是给同步记录加
「订单完结 N 天后自动失效」，而不是推翻整个模型。

### 三、给未注册收件人发短信，是「线索一律不发」政策的显式例外

仓库里有一条**写死且有测试守着**的政策
（`MemberReachService`、`AudienceResolver` 的 `SKIP_LEAD` / `SKIP_NO_ACCOUNT`，
`MemberTagFlowTest` 守着，C 端文案也写好了「记为线索，不会发送任何消息」）：

> 商家录进来的未注册手机号，本人从没同意过接收任何东西——一律不发。

本功能要给未注册收件人发短信，正面撞上它。**开例外，理由是两者性质不同**：

| | 线索 | 收件人 |
|---|---|---|
| 号码来自 | 商家录入，用于**营销触达** | 下单人填写，**用于把货寄给他** |
| 本人关系 | 与平台无任何交易关系 | 有一件实物正在寄给他 |
| 消息性质 | 营销 | **交易性通知** |

仓库自己也区分了这两类——频率闸只对 `MARKETING` 场景生效，交易/待办类豁免。
现实中快递公司给未注册收件人发派件短信也是行业惯例。

**例外的边界要钉死**（越界就不再是这条例外能覆盖的）：

- 只在**下单人主动同步**时发，不做任何批量/营销推送
- 同一子单对同一号码**只发一次**（唯一键保证幂等）
- 文案只说「有人给你寄了东西，登录可查看」，**不含商品详情、不含金额、不带短链**
- 带退订指引

## 不可逆的部分

- `ord_share` 一旦有数据，「同步 = 授权」这个语义就固定了。改成「号码对上就看」会让
  存量的「未同步」订单突然对收件人可见——**那是一次无法回滚的信息释放**。
- 新报备的阿里云短信模板一旦上线发出，就不能假装没发过。
- 「线索不发」的例外一旦开了，后续每个「给未注册的人发点什么」的需求都会引用它。
  **所以例外的边界写在上面，不是口头约定。**

## 放弃的方案

| 方案 | 放弃原因 |
|---|---|
| **号码对上就看，不需要同步** | 授权依据落在一个会打错、会被回收的字段上；且默认即可见，暴露面是全量订单 |
| **子单加 `receiver_phone_hash` 列** | 要给几十万条历史子单回填 hash——而那批单本来就不该可见。独立表天然「没记录=不可见」，不用回填 |
| **复用 `usr_person` 人档做关联** | 语义正、认领机制现成，但要给每个收货手机号建人档（人档是商家侧会员语义，会被撑成地址簿）；且我们不需要它的认领步骤，最大优势用不上 |
| **发带 token 的免登录链接** | 链接会被转发，等于绕开注册这道闸；且和「注册后才能看」的定位冲突 |
| **同步记录设 TTL** | 与核心价值冲突，见「决定二」 |
