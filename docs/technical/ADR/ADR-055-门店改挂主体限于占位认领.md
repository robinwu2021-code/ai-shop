# ADR-055 门店改挂主体限于占位认领

状态：已接受（2026-11-08，用户按 [TDD-商户App商户资料提交](../TDD-商户App商户资料提交.md)「待用户拍板」第 5、8、11、12 条的「建议」确认）
日期：2026-11-08

一句话：一期**只做「挂在占位主体下的门店，认领本账号已有的 `ACTIVE` 主体」**，不做一般意义的门店换主体；
认领要求门店干净（无交易、只有 FREE 订阅、占位主体从未向 near-pay 申请支付服务），
认领后撤销该店员工授权、逻辑删除空出来的占位主体、写 critical 审计并触发门店同步。

## 背景

**场景。** 快速开店会给门店建一个 `PENDING_LICENSE` 占位主体。商户 App 的 C02「选择商户资料」只在本店还没有已审核资料时出现
（ai-shop-bapp `apps/merchant_app/lib/features/merchant/store_payment_page.dart` 21–23 行 `unlinked`：本店主体 `review == none` 且没有能收款的渠道）。
已有一张执照、开第二家店的老板，要的是「把这家新店挂到我已认证的那个主体下」；不给这条路，就得用同一张执照再交一遍资料、再审一次（TDD §3「N1 改挂的范围」方案 C）。

**后端现状：没有任何换主体入口。**
- 门店唯一的跨字段改动是换收款号 `POST /biz/store/{storeNo}/payment`，只能在**本主体** `ACTIVE` 的号里挑
  （`backend/shop-merchant/src/main/java/ai/neargo/shop/merchant/service/impl/StoreAdminServiceImpl.java` 297 行 `setPayment`；TDD §1 第 11 行）。
- `入驻进件建店-需求与四层对齐.md` 277 行「换主体 ⬜」。

**现有文档互相矛盾。**

| 文档 | 口径 |
|---|---|
| [账号主体门店-关系定稿](../design/账号主体门店-关系定稿.md) §3.2、§3.4 | 门店 → 主体是「关联，可切换」，并列了六条换主体硬约束 |
| [门店注册到进件-流程节点与代码对齐](../../requirements/门店注册到进件-流程节点与代码对齐.md) 158 行 | 「门店换主体 ⬜ 产品明确暂不做」 |
| [多门店与分享激励-需求](../../requirements/多门店与分享激励-需求.md) §四 | 「跨主体的门店转移」不做 —— 「历史订单结算方变了，是财务事故不是功能」 |

**near-pay 不会跟着换。** 门店投影同步时，门店**还没有**关联且来源主体已映射平台商户 → 同事务建关联；
**已经**关联而来源主体变了 → **不换关联，只记 `ENTITY_CHANGED`**
（near-pay `backend/pay/pay-domain/src/main/java/ai/neargo/shop/pay/platmch/store/StoreProjectionService.java` 32 行类注释、202–216 行 `reconcileAssociation`）。
换关联只有一条路：运营登记待审变更，经 `STORE_ASSOCIATION_CHANGE` 双人审批后执行
（同目录 `StoreAssociationService.java` 27–30 行类注释）。
所以在 ai-shop 侧给一家已在 near-pay 关联过的门店改主体，结果是 ai-shop 说「B」、near-pay 仍按「A」收款 —— 钱和账分家。

**错误包不带数据。** 业务异常统一回 `ApiResult<Void>`，只有 `code` 与文案
（`backend/shop-base-auth/src/main/java/ai/neargo/shop/common/GlobalExceptionHandler.java` 48–60 行；TDD §1 第 27 行），App 无法从 10409 里知道是哪条前置没满足、会失效几名员工。

## 决策

### 1. 范围：只认领，不换

| 项 | 规则 | 防住什么 |
|---|---|---|
| 源 | 门店当前主体是 `PENDING_LICENSE` 占位主体，当前用户是它的在职店主 | 已认证主体之间互换（10409）—— 那会改纳税主体，正是「暂不做」的那件事 |
| 目标 | `ACTIVE`，且当前用户是它的在职店主（`MerchantEntityServiceImpl#requireOwned`，不是就 10403、不回落） | 把店挂到别人的主体下（资产转让，不是配置） |
| 目标状态 | **只允许 `ACTIVE`**，审核中、被驳回都不可选（拍板 5） | 门店挂在一张最后被驳回的执照下；以及「审核通过时把申请升级到哪个主体」这个没人能答的问题 |

端点：`POST /biz/store/{storeNo}/entity {entityNo}`，权限码 `biz:store:admin`，登记在 `ShopStoreMemberRoutes`（门店级动作，与 `POST /biz/store/{storeNo}/payment` 同类；TDD §2 N1）。

### 2. 前置条件（全部满足才改，任一不满足 10409）

| 条件 | 防住什么 |
|---|---|
| 门店没有任何订单、售后、线下收款、储值账户 | 交易的结算方被改到新主体（多门店需求 §四 说的「财务事故」）。守卫端口按白名单列数据源，拿不准的一律算「有交易」（TDD §4） |
| 门店订阅只有 FREE（无付费期、无商城订单） | 付费订阅账户按门店唯一且带 `entity_no`（`V3__commerce_subscription_credit.sql` 2–18 行 `mch_subscription_account`），付费期跟着换主体就是把已付的钱挪到另一个主体名下 |
| 占位主体在 near-pay 的申请状态是 `NONE`（从未申请支付服务） | 门店在 near-pay 已有关联：改了 ai-shop 也换不动 near-pay（见背景），只会多一条 `ENTITY_CHANGED` |
| 占位主体没有进行中的入驻申请 | 审核通过时把申请升级到一个已经没有门店的主体上 |
| near-pay 状态读不到 → 不放行（改挂 10505，预检 `PAY_SERVICE_UNKNOWN`） | 「拿不准」被当成「没申请过」 |

### 3. 执行（同一事务）

1. `mch_store.entity_no` 改为目标；`is_default=false`；`pay_merchant_no=null`（回到目标主体默认号）。
2. FREE 订阅账户的 `entity_no` 跟着改，**经 commerce 端口**，不在 shop-merchant 直写 commerce 表。
3. 删除该门店**非店主**的 `mch_store_role`，响应带 `revokedStaff`。
4. 占位主体下已无门店 → **逻辑删除**（`deleted=1`），成员行停用（拍板 11）。不新增主体状态值。
5. `OpsService#audit(…, critical=true, …)` 记谁、何时、A→B。
6. 事务提交后 `payMirror.changed` 触发门店同步：因为前置条件保证门店在 near-pay **从未关联**，同步走「无当前关联 → 按新主体映射建关联」那一支，而不是 `ENTITY_CHANGED`。

逻辑删除够用的依据：商城的门店读取已按 `m.deleted=0` 过滤主体
（`backend/shop-app/src/main/java/ai/neargo/shop/commercebridge/ShopCommerceStoreAdapter.java` 155 行）。

### 4. 先预检、再确认、后执行（拍板 12）

- 只读预检 `GET /biz/store/{storeNo}/entity/relink-check?entityNo=` 回 `{allowed, blockers[], revokedStaff}`，
  `blockers` 机器码与每条拒绝一一对应（`TARGET_NOT_OWNED`、`TARGET_NOT_ACTIVE`、`SOURCE_NOT_PLACEHOLDER`、`HAS_TRADES`、`PAID_PLAN`、`PAY_SERVICE_APPLIED`、`APPLY_PENDING`、`PAY_SERVICE_UNKNOWN`）。
- App 打开确认页前先调预检，写明「本店 n 名員工的授權會失效，需在新商戶下重新授權」；**后端改挂只执行、不询问**。
- `relink` 开头调用同一个 `check` —— 判据只有一份，预检说能改而改挂拒绝的情况只来自两次调用之间状态变了（App 再调一次预检即可）。
- 已经挂在目标主体 → 200，结果同上一次（幂等）。
- 响应带 `stores`（与 `GET /biz/stores/mine` 同形）。App **必须**按新 `entityNo` 重新选店：光 `reloadStores()` 不刷新已选门店，后续主体级请求仍带旧 `X-Entity-No`，会被 `FoundationTarget` 拒绝（TDD §2 N1、§4）。

### 5. 现有文档矛盾按此口径收敛

| 文档 | 与本 ADR 的关系 |
|---|---|
| 门店注册到进件 158 行「产品明确暂不做」、多门店需求 §四「不做跨主体转移」 | **仍成立**：一般意义的门店换主体一期不做。本 ADR 只开了一个例外 —— 门店从未认证、从未交易、从未进 near-pay 时的认领，它不改任何既有的结算方 |
| 关系定稿 §3.2「门店可切换主体」 | 模型方向不撤销（`mch_store.entity_no` 是关联而非归属），但**一期唯一的实现是认领**；通用切换另立 ADR |

关系定稿 §3.4 六条硬约束在认领里的落点：

| §3.4 约束 | 认领中的对应 |
|---|---|
| 新旧主体同属一个账号 | 源、目标都要求本人在职店主 |
| 新主体 `ACTIVE` 且进件就绪 | 要求 `ACTIVE`；**不要求**目标已开通收款，响应 `payReady` 告知。认领前占位主体从未申请支付服务，门店本来就不能在 near-pay 收款，认领不会让它从「能收」变「不能收」 |
| 有未完成订单不能换 | 更严：任何订单都不行 |
| 有未结算账单不能换 | 更严：任何交易都不行 |
| 员工授权全部失效 | 撤销非店主授权，且先经预检确认 |
| 变更留痕 | critical 审计 A→B |
| （附）积分与券的处置要先告知 | 门店无交易时不应有本店发出的券与积分；守卫端口实现时把券、积分列入白名单逐表核，拿不准算「有交易」 |

## 被否决的选项

- **通用换主体（关系定稿 §3.4 + 平台审核）**：要处理纳税主体变化、历史订单、券与积分，以及 near-pay 关联 —— 后者只能由运营双人审批换（`StoreAssociationService`），ai-shop 侧单方面改只会制造 `ENTITY_CHANGED`。一期做不完，且与「产品明确暂不做」冲突（TDD §3 方案 A、拍板 8 ②）。
- **不做改挂，C02 只留「以本店新建资料」**：零后端，但已有执照的老板开第二家店要再交一遍同一张执照、再审一次。保留为后备（TDD §3 方案 C、拍板 8 ③）。
- **允许选审核中 / 被驳回的主体**：要回答「目标被驳回后门店怎么办」「审核通过时申请升级到哪个主体」（拍板 5 ②）。
- **给占位主体新增一个「已被认领」状态值**：要改 B 端状态映射 `bizStatus` 与 App 枚举，而逻辑删除已被现有读取过滤（拍板 11 ②）。
- **不确认，直接撤销员工授权**：员工突然进不了店，店主不知道原因（拍板 12 ②）。
- **把拒绝原因塞进错误包 `data.reason`，或每种原因一个新错误码**：前者要改 `GlobalExceptionHandler` 对所有 `BizException` 的全局形状；后者每加一种原因就要新增 i18n 词条与三端映射（TDD §3「N1 失败原因怎么给 App」B、C）。

## 后果

- **正面**：覆盖 App C02 的真实场景；不加表、不加错误码、不加权限码（TDD §2 契约变更总表）；near-pay 侧零改动，靠已有的门店同步建首次关联。
- **负面**：门店一旦有交易、付过费或占位主体申请过支付服务，就再也不能认领，只能用本店新建资料。
- **原型与文案要改**：C02 与 v5 文案把非 `ACTIVE` 主体置灰并写「審核通過後可選」（拍板 5，需产品签字）；确认页加将失效人数。
- **风险与缓解**：漏掉某种「门店有交易」的数据源（如储值、团购）→ 交易结算方被改到新主体；守卫端口按白名单列数据源，实现时逐表核（TDD §4）。
- **不可逆点**：改挂会撤销员工授权并逻辑删除占位主体；虽然数据还在，但没有反向操作，员工要在新主体下重新授权。这也是为什么前置条件要求门店「干净」，而不是事后补救。
- **以后要做通用换主体**：另立 ADR，至少要回答 near-pay 关联由谁发起变更（目前只有运营双人审批）、历史订单与券积分如何处置。
