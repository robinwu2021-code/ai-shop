# ADR-023 · 服务发现：先做访问层，不装中间件

**日期**：2026-09-01 　**状态**：已采纳 　**相关**：[ADR-021 支付域独立](ADR-021-支付域独立为服务与独立库.md)

## 背景

支付域即将有独立进程（`pay-svc`，形态 B），`shop-job` 已经独立跑了一段时间。
进程从一个变成三个，「谁去哪里找谁」第一次成为一个需要回答的问题。

服务器现状（2026-09-01 实测）：

| 项 | 值 |
|---|---|
| 内存 | 7.5 GiB，已用 2.1 GiB（`shop-app` 899 MB + `shop-job` 310 MB） |
| DNS | `systemd-resolved` 已在跑，`/etc/resolv.conf` 指向它的 stub |
| 中间件 | 无 Consul / Nacos / dnsmasq |
| 部署形态 | **单机**，三个进程都在 `127.0.0.1` |

## 决定

**现在只做访问层，不装任何服务发现中间件。**

- 调用方通过一个 `ServiceLocator` 抽象拿地址，不关心地址从哪来；
- 今天的实现读配置（延续 `shop-job` 已有的 `targets` 写法）；
- 将来资源宽裕引入 Consul 时，换的是这个抽象的实现，**调用点一行不改**。

## 一件必须先说清楚的事：DNS 今天不解决问题

原本的想法是「用服务器本地 DNS 做简单服务发现」。查下来它今天的收益接近于零，
理由是 DNS 的一个根本限制：

> **DNS 只解析 host → IP，不带端口。**

Consul 用 SRV 记录带端口，而 `systemd-resolved` 不提供自定义 SRV 记录
（它主要做转发与缓存）。所以端口无论如何都要落在配置里 ——
**而端口既然已经在配置里，host 一起配的成本是零**。

单机部署下，配 `http://pay.svc.internal:8083` 与配 `http://127.0.0.1:8083`
的差别只是名字。前者多了一处要维护的映射（`/etc/hosts`），
而它今天不换、不漂移、不需要负载均衡。

**它的收益在多机那天**：换机器只改一处 DNS，所有服务的配置不动。
那一天到来之前，把它做进抽象里就够了 —— 见下面「DNS 怎么接进来」。

## 访问层的形状

```
调用方（业务代码）
    │  只知道服务名：ServiceName.PAY
    ▼
ServiceLocator                    ← 唯一的抽象
    │  baseUrlOf("PAY") → http://127.0.0.1:8083
    ├── ConfigServiceLocator      ← 今天：读配置（shop.services.targets）
    ├── DnsServiceLocator         ← 多机时：host 走 DNS，端口仍来自配置
    └── ConsulServiceLocator      ← 资源宽裕时：host + port 都来自 Consul
    ▼
InternalClient                    ← 调用的那一半：超时、重试、共享密钥、错误映射
```

**两件事分开**：「地址从哪来」（Locator）与「怎么调」（Client）。
合在一起的话，换服务发现方式会连带改掉重试与超时逻辑 ——
而那两件事没有任何关系。

### 为什么不是「每次都过 nginx」

nginx 反代是可行的，也是很多团队的做法。不选它的理由：

- **多一跳**：内部调用本来是 `127.0.0.1` 之间的事，绕到 nginx 再回来，
  多一次连接、多一份配置；
- **配置在服务之外**：加一个服务要改 nginx 并 reload，
  而 reload 是全站的动作 —— 改内部路由不该有影响外部流量的可能；
- **`/internal` 本来就不该经过 nginx**：`shop-job` 那条已经定下的规矩是
  「nginx 不反代 `/internal/**`，worker 走 `127.0.0.1:8081`」
  （见 `JobHandlerEndpoint` 的四条硬要求）。让 pay 走 nginx 会与它不一致，
  而两套内部寻址方式里迟早有一套没人维护。

nginx 继续只做**外部入口**：域名、TLS、静态资源、三端路径。

## DNS 怎么接进来（多机那天）

零中间件的做法，`systemd-resolved` 已经够：

```bash
# /etc/hosts —— 单机时甚至不需要改，多机时每台机器一份
10.0.0.11  pay.svc.internal
10.0.0.12  job.svc.internal
```

配置里把 host 换成域名，端口不动：

```yaml
shop:
  services:
    targets:
      PAY:      http://pay.svc.internal:8083
      PLATFORM: http://platform.svc.internal:8081
```

**这一步不需要改代码** —— `ConfigServiceLocator` 读到的是一个 URL，
它是 IP 还是域名不影响任何东西。所以「引入 DNS」实际上是一次运维动作，
不是一次发版。这也是为什么它不值得现在做：**做了和没做，代码一模一样。**

## 换 Consul 时改什么

| 改 | 不改 |
|---|---|
| 新增 `ConsulServiceLocator` | 调用点（它们只知道服务名） |
| 一个配置开关选实现 | `InternalClient` 的超时、重试、密钥 |
| 各服务启动时注册自己 | 服务名常量 |

**代价要认**：Consul 自己要吃内存（agent 每台约 50–100 MB），
还要考虑它挂了怎么办 —— 一个服务发现中间件挂掉的后果，
比它解决的问题更严重。所以引入它的判据不是「更专业」，
而是**「机器多到手工维护 `/etc/hosts` 会出错」**。今天是三个进程一台机器，
离那个判据还很远。

## 反过来说，什么时候必须做

这个 ADR 的结论会过期。三个信号，任何一个出现就该重新评估：

1. **服务超过一台机器** → 先上 DNS（改运维，不改代码）；
2. **同一个服务需要多实例** → DNS 轮询不够（无健康检查，挂掉的实例照样被解析到），
   这时才轮到 Consul；
3. **需要按环境隔离**（预发/生产同网） → 配置能做，但容易配错，
   服务发现能给出更硬的边界。

在这三个之前，多加一层中间件只是多一个会挂的东西。
