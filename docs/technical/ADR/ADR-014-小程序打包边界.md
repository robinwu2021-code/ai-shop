# ADR-014 小程序打包边界：C 端提交小程序，B 端走 H5，两者不合包

> 2026-08-11 提案 · **已决策**
> 修订：[ADR-001](./ADR-001-商家端形态与拆分时机.md)（一期形态已被现状超越，见 §5）
> 相关：[ADR-008](./ADR-008-共享组件库与四端部署.md)（两端不合站）· [ADR-012](./ADR-012-小程序类目与经营模式选择.md)（类目与经营模式）

---

## 1. 一句话

一期只提交**一个**小程序 —— C 端；B 端以 H5 交付，不进小程序包。将来商家真的需要小程序入口时，单独申请 AppID，而不是塞进 C 端的分包。

## 2. 问题

两端是同一个仓库、同一套技术栈（uni-app），都能 `build:mp-weixin` 出小程序产物。那么提审时是打一个包还是两个包？

这个问题必须在提审前定，因为它决定：申请几个 AppID、选几套类目、微信支付绑哪个、以及**登录方式要不要改**。

## 3. 决策：不合包

| 维度 | 合成一个小程序的代价 |
|---|---|
| **包体** | 主包 2MB / 总包 20MB 是硬限制。B 端的表格、批量操作、图表会直接吃掉 C 端的预算，而 C 端首屏时间是转化率的一部分 |
| **发版节奏** | 一个 AppID 一套审核队列。B 端改一个字段也要跟着 C 端过审 1–3 天 —— 而商家的问题往往是「今天就得改」。这正是 [ADR-001 §3](./ADR-001-商家端形态与拆分时机.md) 当初列的第一条拆分理由 |
| **类目与审核** | C 端是电商交易类目（[ADR-012](./ADR-012-小程序类目与经营模式选择.md)）。经营管理功能出现在同一个包里，容易被问「功能与类目不符」，而解释成本落在 C 端的上线时间上 |
| **受众不对等** | 商家几十家、消费者是全部。让每个消费者下载商家端的代码，收益为零 |
| **支付绑定** | 微信支付商户号绑 AppID，**只有 C 端收款需要**。B 端是收款方后台，不涉及这层绑定 |

合并唯一的实际好处是省一个 AppID（企业主体认证 300 元/年/个）与一次注册流程。相对上面这些不值。

## 4. B 端为什么 H5 就够

**商家不是搜出来的，是 BD 一家家谈来的。** 小程序最大的价值是入口——搜索、附近、分享卡片、扫码——这些对 C 端是获客命脉（[ADR-004](./ADR-004-增长模型从孵化团长转向商家自带客流.md)），对 B 端一条都用不上：BD 谈完直接给链接或二维码即可。

现状已经是这个形态：`npm run build:web` 产出 `dist/web/c/` 与 `dist/web/b/` 两个站点，各自独立域名（[ADR-008 §5](./ADR-008-共享组件库与四端部署.md)）。**同一个仓库、同一套底层组件，两个运行时** —— 与那条「不合站」是同一个判断，只是从部署延伸到打包。

将来若商家确实需要小程序入口（例如要用微信的消息订阅推送订单提醒），做法是**单独申请 AppID，`b-app` 直接出包**，而不是把页面搬进 C 端分包：分包能解决包体，解决不了发版节奏与类目耦合，而那两条才是主要代价。

## 5. 与 ADR-001 的关系：现状已经超越了它的一期方案

ADR-001 写的一期形态是「不做独立商家端，轻操作进 C 端小程序的商家专区」，理由是当时只有平台自己一个商家。

**这条已经不成立**：仓库里 `b-app` 是完整独立的商家端（门店、商品、订单、结算、员工授权、经营范围），实际走到了 ADR-001 的二期形态。原因是平台定位在开发过程中变了——第三方入驻从「二期再说」变成了一期就要（[ADR-011](./ADR-011-经营主体与门店边界.md) 的主体/门店两级模型正是为此而建）。

所以：
- ADR-001 的**拆分理由（§3 四条）继续有效**，本 ADR 直接引用其中两条；
- ADR-001 的**一期形态描述已作废**，以本 ADR 为准。不改 ADR-001 的正文（历史决策要保留原样），在其头部标注被本 ADR 修订。

## 6. 由此产生的待办

1. **C 端登录方式要在提审前定**。小程序里获取手机号要走微信的手机号快速验证组件（按次计费），现在的短信验证码在小程序内的体验与合规都不占优。这件事影响 C 端登录页的改造范围。
2. **B 端 H5 的进入方式要定**：短链 + 二维码，还是企业微信内打开。影响登录态保持时长与分享文案。
3. 提审材料按 [ADR-012](./ADR-012-小程序类目与经营模式选择.md) 的自营口径准备，与本 ADR 无冲突 —— 一个包、一套类目，反而是那份材料成立的前提。
