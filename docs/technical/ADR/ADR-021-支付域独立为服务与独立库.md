## 1. 一句话

**支付域独立成服务与独立库，但分四阶段走**：先收拢目录、再切库、最后切产物。
每一阶段都是可以停下来的完整状态，**而不是一次大重构的三个中间态**。

---

## 2. 问题

支付这条链路今天散在三个模块里：通道适配在 `shop-channel`，结算分账对账在 `shop-settle`，
进件档案在 `shop-merchant`。它要独立，理由不是「模块太大」——而是三件与别处不同的事：

| | 支付域 | 其余域 |
|---|---|---|
| **出错的代价** | 真金白银，且不可逆 | 数据错了可以改 |
| **变更节奏** | 跟通道走（对方改接口我们必须跟） | 跟产品走 |
| **审计要求** | 每一分钱可追溯到指令与回执，**账不能改** | 一般 |

第三条是关键：**「账不能改」这个约束，和同库里别的域「随时可以改」的常态是冲突的。**
今天任何一个会话的一次 `UPDATE` 都能改到 `stl_bill`，而没有任何机制拦住它。
不是因为有人会恶意改，是因为**同一个库里没有「这张表不许动」这种边界**。

### 2.1 三个对拆分有利的实测事实

在提出拆分之前先量了一遍（2026-08-30，全仓 grep）：

| 事实 | 数 | 意味着 |
|---|---|---|
| `shop-settle` 出方向的跨域调用 | **9 个 Port 方法** | 出边界已经是 Port，不是直连表 |
| 反向依赖 settle 的类 | **4 个** | 入边界也窄 |
| `shop-inventory` 已在跑独立数据源 | 1 套 | **样板现成**，不用从零验证可行性 |

第三条尤其重要：`InventoryDataSourceConfig` + `db/inventory/V1..V4` + 独立事务管理器
已经在生产里跑着，它踩过的两个坑（`@Primary` 抢走数据源、Flyway bean 关掉平台全部迁移）
也都记录在案。**支付库照抄这个形状，不是一次新的探险。**

### 2.2 一个对拆分不利的事实

`pts_user_account` 被 C 端高频读（商品页、购物车、个人中心），
而积分抵扣的扣减与建订单今天在**同一个数据库事务**里。见 §5.1 —— 这是最大的一处代价。

## 3. 决策

### 3.1 分四阶段，每阶段是一个可停下的完整状态

| 阶段 | 形态 | 闸门（不过不进下一阶段） |
|---|---|---|
| **0** 今天 | 散在三模块 · 同库 · 同 jar | — |
| **1** 收拢 | `backend/pay/` 四模块 · 同库 · 同 jar | ArchUnit：`pay/**` **不依赖 `shop-app-base`（MyBatis 那一层）**（见 §3.5 的 2026-08-31 修订）、不依赖任何业务域 |
| **2** 切库 | 独立库 · 同 jar（双数据源） | 主库迁移里不再出现 `stl_*` / `sys_pay_*` 建表 |
| **3** 切产物 | `pay-svc` 独立 jar · 独立进程 · AOT | **断网演练** + **AOT 产物断言**（见 §3.5 的 ⚠️） |

**每一阶段单独有价值**：
阶段 1 拿到的是依赖收敛（今天就能防住「随手 import 一个 core 里的类」）；
阶段 2 拿到的是「账不能被别的域改」这条边界；
阶段 3 才是独立伸缩与独立发布。

**阶段 3 是目标，不是备选**（2026-08-30 定）。理由与 job 模块同一条：
**驱动力是「发布不打断」，不是资源** —— 发业务不该重启支付，反之亦然。
job 模块已经证明这条路走得通，形状可以照搬。

不过**阶段 2 仍然是一个可以停下的完整状态**：如果 §4.5 三处差异中的任何一处
在阶段 2 暴露出比预期大的代价，停在那里也已经拿到了「账不能被别的域改」这条边界。

### 3.2 边界：15 张表

| 组 | 表 | 为什么在里面 |
|---|---|---|
| 结算 | `stl_bill` `stl_fee_rule` `stl_split_log` `stl_payment` `stl_recon_diff` `stl_withdraw` `stl_settle_invoice` `stl_purchase_invoice` `stl_points_pool` | 资金主体 |
| 通道 | `sys_pay_channel` `sys_pay_channel_rate` | 费率是账的输入 |
| 进件 | `mch_payment_merchant` | 它是「钱打给谁」的真源，与商家主档是两件事 |
| 积分 | `pts_user_account` `pts_user_ledger` | 积分池恒等式与资金恒等式要在同一个库里才验得动 |

**`risk_*` 四张留主库**：风控不只管资金（还有内容、账号、刷单），
整域搬过去会让非资金风控也跨库。资金风控作为**规则的一个子集**接进来，
见 [ADR-022](./ADR-022-资金风控的拦截点与误伤代价.md)。

### 3.3 跨库引用：只存业务键 + 快照列，不跨库 JOIN

支付库里的单据引用主库的商家、订单、门店时：

- 存 **业务键**（`entity_no` / `order_no` / `store_no`），不存自增 id；
- 加上生成那一刻的 **快照列**（商家名、主体形态、收款号、经营模式）;
- 展示时**逐字段标明**是用快照还是回查，写在数据库设计文档里。

> **为什么不实时回查**：历史账不能跟着主库的修改变。
> 商家改了名，去年那张结算单上该显示的仍是当时那个名字——
> 这不是缓存优化，是审计要求。
>
> **快照会陈旧，这是已知代价**。缓解不是「定期刷新」（那等于放弃了上面那条），
> 而是**在界面上说清楚**：「主体名（成交时）」。

### 3.4 目录

```
阶段 1–2
backend/pay/
├── pay-api          对外契约 + Port 接口定义（别的域只依赖这个）
├── pay-domain       结算·分账·对账·提现·进件·费率·积分
│   └── src/main/resources/db/pay/V1..Vn      ← 阶段 2 起，独立迁移目录
├── pay-channel      通道适配（微信 / 支付宝 / 后续）
└── pay-risk         资金风控

阶段 3
backend/pay-svc/     独立 jar：pay-* 四模块 + 自己的 web 层 + 自己的 Flyway
```

### 3.5 持久层：Spring Data JDBC + AOT，**不用 MyBatis-Plus**

与 job 模块同一条理由，而且是硬约束：

> **Spring Data AOT 是 Spring Data 的特性** —— 构建期把 repository 实现生成出来
> （`spring.aot.repositories.enabled`）。MyBatis 不在这条路上。
> **一旦用 MyBatis-Plus，这个模块就永远进不了 AOT / native。**

由此推出的直接事实：`shop-base` 把 `mybatis-plus-spring-boot4-starter` 作为**编译依赖**引入，
只要依赖它，MyBatis 就进了 classpath，AOT 收益当场打折 —— 而且没有任何报错。

> **2026-08-31 修订：这里原来的结论是「所以 `pay-*` 不依赖 `shop-base`」，那句下重了。**
>
> `shop-base` 共 159 个 Java 文件，**其中 113 个（71%）连 `org.springframework` 都没有**
> —— `ErrorCode` / `BizException` / `ApiResult` / `spi` 下全部 70 个 Port 都在这一档；
> 真正绑 MyBatis 的只有 22 个（14%）。为了躲那 14%，把 71% 也一起躲掉了。
>
> 而躲掉的代价比它看上去大：**错误码不是内部实现，是三端契约的一部分**。
> `ops-web` 与 b-app 都按 `ErrorCode` 分段判「这是权限问题还是业务问题」，
> 支付域自带一套，前端就要写第二套解析 —— 两套码迟早在同一个数字上表示不同的意思。
> `shop-job` 还没撞上这条，只是因为它**没有 web 层**。支付域有，一定会撞。
>
> 改成：**`shop-base` 去掉持久层**（拆出 `shop-store-mybatis` / `shop-store-data-aot`
> 两个平行实现），`pay-*` 与 `shop-job` **都依赖 `shop-base` 内核**，
> 只是各装各的持久层。方案见
> [TDD-基础包分层与支付双形态](../design/TDD-基础包分层与支付双形态.md)。
>
> 于是 `pay-api` 单开一个模块的理由回到原来那个：**它是对外契约**，别的域只依赖它 ——
> 而不是「因为 `ErrorCode` 用不了」。

> ⚠️ **2026-08-31 实施 C1 时发现的一个前提问题，本节的结论要跟着改。**
>
> 拆完之后量了依赖树（`mvn dependency:tree`，不是源码 grep）：
>
> ```
> shop-base          mybatis=0    ← 内核确实干净了
> shop-base-auth     mybatis=11   ← 拆不掉
> ```
>
> `shop-base-auth` 依赖 `neargo-common-data`（数据域引擎），
> **而那个引擎本身就是一个 MyBatis 拦截器**。用它的是 auth 的核心几个类
> （`LoginUser` / `AbstractTokenAuthFilter` / `LiveIdentityResolver` /
> `ScopeDim` / `RequestMetaContext`），不是边角。
>
> 推论：**`pay-svc` 需要三条鉴权链，也就必然带 MyBatis**。
> 本节说「一旦用 MyBatis-Plus，这个模块就永远进不了 AOT / native」——
> 按目前的形状，`pay-svc` 的 AOT 收益是打折的。三条路都要评审：
>
> **2026-08-31 当天已定，走的是比 a/b/c 更彻底的一条：支付域不做 controller。**
>
> 三端 controller、鉴权、判权、数据域解析<b>全部留在主应用</b>；
> `pay-svc` 唯一的 HTTP 表面是 `/internal/**`（共享密钥、绑内网、不认用户身份），
> 主应用传给它的是**已经收窄过的查询条件**，不是「当前用户是谁」。
>
> 于是 `pay-svc` 不依赖 `shop-base-auth` → 不依赖 `neargo-common-data`
> → **不带 MyBatis → 本节的 AOT 前提重新成立**。
>
> 顺带消掉三件：会话外置不再是拆分前置（pay 不读会话）；
> 判权不需要跨库或远程回查；nginx 不必按路径分流（只有一个进程有 controller）。
>
> 代价：支付相关的读多一跳；数据域从「SQL 拦截器自动加 where」变成「显式传参」——
> 而后者的**失败方向更安全**（拦截器漏装是静默全量，显式传参漏传是空集或编译不过）。
>
> 详见 [TDD-支付域 · 双形态部署与装配 §L1](../design/TDD-支付域-双形态部署与装配.md)。

> ⚠️ **一处必须说清的事实**：job 模块的**文档**写的是 Spring Data JDBC，
> 而它的**实现**用的是 `JdbcClient`（`JobDefinitionDao` 等三个 Dao），
> 没有 repository 接口，因此 `spring.aot.repositories.enabled` 在那边**实际没有生效**。
> 支付域按用户 2026-08-30 的要求走**真正的 Spring Data JDBC repository**，
> 并把「构建产物里存在 AOT 生成的 repository 实现类」做成验收项 ——
> 否则会重演 job 那份文档里自己列出的坑：「以为开了 AOT，其实没开：
> 启动照常、功能照常，只是什么都没生成，直到上 native 才发现」。

**混用是允许且必要的**：15 张表里，CRUD 走 repository，
对账与批次聚合那几条走 `JdbcClient` —— 后者本来就不该硬塞进 repository 方法名里。

### 3.6 数据源装配：照 `shop-inventory` 的形状，但绑定方式不同

```
PayDataSourceConfig       独立 HikariDataSource + 独立 DataSourceTransactionManager
                          ⚠️ 不标 @Primary —— 标了会把平台主数据源抢走，
                             而症状是 DataScope 行级越权防线静默丢失
@EnableJdbcRepositories   ⚠️ **显式指定本模块的 JdbcOperations / DataAccessStrategy**，
                             不吃 @Primary。不指定的话 pay_* 查询会静默打到平台库，
                             只在跑到那一行时才炸
PayFlyway                 只扫 db/pay/**
                          ⚠️ 声明 Flyway bean 会关掉 Spring Boot 的自动装配，
                             平台主库的全部迁移随之失效 —— 不报错，只是没跑
spring.aot.repositories.enabled=true   ⚠️ 显式写出来，不靠默认值
shop.pay.enabled          默认 false（业务侧）/ true（pay-svc 自己）—— 与 job 同一条
```

四条 ⚠️ 全部来自 `shop-inventory` 与 `shop-job` **已经踩过并记录**的坑，不是推测。

## 4. 为什么不是别的做法

### 4.1 为什么不一次拆到位

一次拆到位要同时改：模块归属、数据源、跨域调用、事务边界、部署、监控。
**出问题时无法二分**——回滚只能整体回滚，而资金链路的问题往往要几天后对账才发现。
分阶段的全部价值就在这里：每一阶段只动一件事，出问题知道回滚哪一个。

### 4.2 为什么不只拆库不拆模块（跳过阶段 1）

阶段 1 的闸门（`pay/**` 不依赖任何业务域、也不依赖 `shop-app-base`）是阶段 2 能不能成的前提。
今天 `shop-settle` 里如果还有一处直接 import 了 `shop-core` 的类，
切库那天它会变成一个跨库查询，而**编译期不会报错**，运行期也只在那条路径被走到时才炸。
先把依赖收敛掉，切库就只是换数据源。

### 4.3 为什么不用「共享库、只拆服务」

那是最坏的一种：两个服务同时写一个库，事务边界消失而部署边界建立起来了 ——
拿到了拆分的全部代价，一条好处都没有。ADR-016 §5.2「第一刀切在数据」说的就是这件事。

### 4.4 为什么积分进来而风控不进来

积分池与资金池的**恒等式互相引用**（池子余额 == 流通中积分 × 汇率 + 已扣未兑付），
分在两个库里就没法用一条 SQL 验，只能靠应用层两次查询——而它要验的正是
「两边对不上」，用两次查询去验两边一致是循环论证。

风控没有这种耦合：它读的是事件，写的是名单与判定，跨库读一次事件是可接受的。

### 4.5 三处**不能照抄 job 模块**

job 是本仓库第一个真独立出去的模块，形状可以照搬，但有三处差异必须自己算：

| # | job | 支付域 | 照抄会怎样 |
|---|---|---|---|
| 1 | **零存量数据**，从 V1 重来，「失败也只影响这一个模块」 | **有真实账目**，迁移一旦出错是钱的问题 | job 那句「试点成本几乎为零」对支付**不成立**。切库要停机搬迁 + 对账恒等式验收，不能「失败就回滚」了事 |
| 2 | 3 张表**纯 CRUD**，查询四五条 | 15 张表，含对账、批次、恒等式**聚合查询** | 「Spring Data JDBC 够用」这个结论要自己验，不能继承。CRUD 走 repository、聚合走 `JdbcClient` 的混用是**必然**，不是妥协 |
| 3 | 调用量约 **4640 次/天**，同步 HTTP 毫无压力 | **每笔订单至少 2–3 次**（生成结算单、查能力、积分扣减） | 那句「同步在这个量级毫无压力」**必须重算**。按日单量估算并写进阶段 3 的设计，算出来不行就得引异步 |

第 3 条尤其要小心：job 的结论建立在「一天几千次」上，而支付是**跟单量线性增长**的。
把它当结论继承下来，等于把一个会随生意变大而恶化的问题写进设计。

## 5. 拆分会打破的三件事

### 5.1 积分抵扣与建订单不再同事务 ★ 最大的一处

今天「扣积分」和「建订单」在一个数据库事务里，一个失败全都回滚。
阶段 3 之后这个保证消失，而它保的是真钱：

- 扣了分没建单 → 用户白丢积分
- 建了单没扣分 → 平台白送钱

**两个方向都不能接受**，所以必须换成两阶段：

```
下单前  预扣（HOLD）      积分置为占用，有超时
下单成  确认（COMMIT）    占用转为已扣
下单败  释放（RELEASE）   占用还回；超时未确认也自动释放
```

加 Outbox 补偿：`COMMIT` 消息丢失时，超时释放会把分还给用户，
而订单侧再走一次确认——**宁可多释放一次，不可少还一次**。

这是**阶段 3 的准入条件**，不是「以后优化」。阶段 1、2 不受影响（还在同库，事务照旧）。

### 5.2 行级数据域从线程上下文变成显式传递

`DataScopeContext` 是线程本地的，跨服务不存在。
支付域的查询要么显式带作用域参数，要么由调用方在 `pay-api` 上传进来。
（这条与 TDD-三端服务拆分 §7.2 是同一件事，此处不重复。）

### 5.3 业务系统**一个字都不写支付库**

这是 job 模块最重要的一条设计，支付域照搬：**每张表只有一个写者**。

今天 `markPaid` 在同一个事务里写 `stl_bill`。阶段 3 之后业务系统
**连支付库的连接串都不该有** —— 它只能调 `pay-api`。

> job 那边由此推翻了两条已定设计（`202` 异步改同步、三张表迁库改名）。
> 支付域会不会也被往回改，要在阶段 2 结束时重新看一遍 §4.5 第 3 条的实测量。

### 5.4 跨域事务变成 Outbox + 幂等

`markPaid` 里「改订单状态 + 生成结算单」今天同事务。
拆开后订单侧发事件、支付侧消费并幂等落单。
**幂等键必须是子单号**（已有唯一索引），不能靠事件 id ——
事件会重投，而重投两次生成两张结算单就是给商家多打一次钱。

## 6. 怎么判断这个决策错了

写下来是为了将来能证伪，而不是事后各说各话：

| 信号 | 说明这个决策错在哪 |
|---|---|
| 阶段 1 的 ArchUnit 闸门要频繁加例外 | 边界画错了，`pay/` 里装了不属于它的东西 |
| 阶段 2 之后跨库快照频繁需要「刷新」 | §3.3 的快照策略与真实用法不符，该改成回查 |
| 阶段 3 之后下单 P99 明显变差 | 积分预扣那一跳的代价超过预期，应退回阶段 2 |
| 支付域的发布频率与主站没有拉开 | 独立产物没有换来独立节奏，阶段 3 的收益不成立 |

**前两条在阶段 1/2 就能观察到，而那时回退成本还很低**——这正是分阶段的意义。

## 7. 待确认（阶段 3 的前置，不确认不能进）
