## 1. 一句话

**支付域独立成服务与独立库，但分四阶段走**：先收拢目录、再切库、最后切产物。
每一阶段都是可以停下来的完整状态，**而不是一次大重构的三个中间态**。

---

## 2. 问题

支付这条链路今天散在三个模块里：通道适配在 `shop-channel`，结算分账对账在 `shop-settle`，
进件档案在 `shop-merchant`。它要独立，理由不是「模块太大」——而是三件与别处不同的事：

| | 支付域 | 其余域 |
|---|---|---|
| **出错的代价** | 真金白银，且不可逆 | 数据错了可以改 |
| **变更节奏** | 跟通道走（对方改接口我们必须跟） | 跟产品走 |
| **审计要求** | 每一分钱可追溯到指令与回执，**账不能改** | 一般 |

第三条是关键：**「账不能改」这个约束，和同库里别的域「随时可以改」的常态是冲突的。**
今天任何一个会话的一次 `UPDATE` 都能改到 `stl_bill`，而没有任何机制拦住它。
不是因为有人会恶意改，是因为**同一个库里没有「这张表不许动」这种边界**。

### 2.1 三个对拆分有利的实测事实

在提出拆分之前先量了一遍（2026-08-30，全仓 grep）：

| 事实 | 数 | 意味着 |
|---|---|---|
| `shop-settle` 出方向的跨域调用 | **9 个 Port 方法** | 出边界已经是 Port，不是直连表 |
| 反向依赖 settle 的类 | **4 个** | 入边界也窄 |
| `shop-inventory` 已在跑独立数据源 | 1 套 | **样板现成**，不用从零验证可行性 |

第三条尤其重要：`InventoryDataSourceConfig` + `db/inventory/V1..V4` + 独立事务管理器
已经在生产里跑着，它踩过的两个坑（`@Primary` 抢走数据源、Flyway bean 关掉平台全部迁移）
也都记录在案。**支付库照抄这个形状，不是一次新的探险。**

### 2.2 一个对拆分不利的事实

`pts_user_account` 被 C 端高频读（商品页、购物车、个人中心），
而积分抵扣的扣减与建订单今天在**同一个数据库事务**里。见 §5.1 —— 这是最大的一处代价。

## 3. 决策

### 3.1 分四阶段，每阶段是一个可停下的完整状态

| 阶段 | 形态 | 闸门（不过不进下一阶段） |
|---|---|---|
| **0** 今天 | 散在三模块 · 同库 · 同 jar | — |
| **1** 收拢 | `backend/pay/` 四模块 · 同库 · 同 jar | ArchUnit：`pay/**` 只依赖 `shop-base` |
| **2** 切库 | 独立库 · 同 jar（双数据源） | 主库迁移里不再出现 `stl_*` / `sys_pay_*` 建表 |
| **3** 切产物 | `pay-svc` 独立 jar · 独立部署 | **断网演练**：停掉 pay-svc，下单要明确报错而不是挂起 |

**每一阶段单独有价值**：
阶段 1 拿到的是依赖收敛（今天就能防住「随手 import 一个 core 里的类」）；
阶段 2 拿到的是「账不能被别的域改」这条边界；
阶段 3 才是独立伸缩与独立发布。

**反过来说，停在阶段 2 是完全合理的终点**——绝大多数「支付要独立」的诉求，
在阶段 2 就已经满足了。阶段 3 的收益（独立伸缩、独立发布）要拿 §5 的代价去换，
值不值得到时候再判，**不在今天承诺**。

### 3.2 边界：15 张表

| 组 | 表 | 为什么在里面 |
|---|---|---|
| 结算 | `stl_bill` `stl_fee_rule` `stl_split_log` `stl_payment` `stl_recon_diff` `stl_withdraw` `stl_settle_invoice` `stl_purchase_invoice` `stl_points_pool` | 资金主体 |
| 通道 | `sys_pay_channel` `sys_pay_channel_rate` | 费率是账的输入 |
| 进件 | `mch_payment_merchant` | 它是「钱打给谁」的真源，与商家主档是两件事 |
| 积分 | `pts_user_account` `pts_user_ledger` | 积分池恒等式与资金恒等式要在同一个库里才验得动 |

**`risk_*` 四张留主库**：风控不只管资金（还有内容、账号、刷单），
整域搬过去会让非资金风控也跨库。资金风控作为**规则的一个子集**接进来，
见 [ADR-022](./ADR-022-资金风控的拦截点与误伤代价.md)。

### 3.3 跨库引用：只存业务键 + 快照列，不跨库 JOIN

支付库里的单据引用主库的商家、订单、门店时：

- 存 **业务键**（`entity_no` / `order_no` / `store_no`），不存自增 id；
- 加上生成那一刻的 **快照列**（商家名、主体形态、收款号、经营模式）;
- 展示时**逐字段标明**是用快照还是回查，写在数据库设计文档里。

> **为什么不实时回查**：历史账不能跟着主库的修改变。
> 商家改了名，去年那张结算单上该显示的仍是当时那个名字——
> 这不是缓存优化，是审计要求。
>
> **快照会陈旧，这是已知代价**。缓解不是「定期刷新」（那等于放弃了上面那条），
> 而是**在界面上说清楚**：「主体名（成交时）」。

### 3.4 目录

```
阶段 1–2
backend/pay/
├── pay-api          对外契约 + Port 接口定义（别的域只依赖这个）
├── pay-domain       结算·分账·对账·提现·进件·费率·积分
│   └── src/main/resources/db/pay/V1..Vn      ← 阶段 2 起，独立迁移目录
├── pay-channel      通道适配（微信 / 支付宝 / 后续）
└── pay-risk         资金风控

阶段 3
backend/pay-svc/     独立 jar：pay-* 四模块 + 自己的 web 层 + 自己的 Flyway
```

### 3.5 阶段 2 的数据源装配：照 `shop-inventory`

```
PayDataSourceConfig     独立 HikariDataSource + 独立 DataSourceTransactionManager
                        ⚠️ 不标 @Primary —— 标了会把平台主数据源抢走
PayFlyway               只扫 db/pay/**
                        ⚠️ 声明 Flyway bean 会关掉 Spring Boot 的自动装配，
                           平台主库的全部迁移随之失效。必须两个都显式声明
shop.pay.enabled        默认 false —— 与 inventory 同一条：默认关闭的那一半
                        才是别人的生产常态，装配要能在关着的时候正常起来
```

两条 ⚠️ 都是 `shop-inventory` 已经踩过并记录的，不是推测。

## 4. 为什么不是别的做法

### 4.1 为什么不一次拆到位

一次拆到位要同时改：模块归属、数据源、跨域调用、事务边界、部署、监控。
**出问题时无法二分**——回滚只能整体回滚，而资金链路的问题往往要几天后对账才发现。
分阶段的全部价值就在这里：每一阶段只动一件事，出问题知道回滚哪一个。

### 4.2 为什么不只拆库不拆模块（跳过阶段 1）

阶段 1 的闸门（`pay/**` 只依赖 `shop-base`）是阶段 2 能不能成的前提。
今天 `shop-settle` 里如果还有一处直接 import 了 `shop-core` 的类，
切库那天它会变成一个跨库查询，而**编译期不会报错**，运行期也只在那条路径被走到时才炸。
先把依赖收敛掉，切库就只是换数据源。

### 4.3 为什么不用「共享库、只拆服务」

那是最坏的一种：两个服务同时写一个库，事务边界消失而部署边界建立起来了 ——
拿到了拆分的全部代价，一条好处都没有。ADR-016 §5.2「第一刀切在数据」说的就是这件事。

### 4.4 为什么积分进来而风控不进来

积分池与资金池的**恒等式互相引用**（池子余额 == 流通中积分 × 汇率 + 已扣未兑付），
分在两个库里就没法用一条 SQL 验，只能靠应用层两次查询——而它要验的正是
「两边对不上」，用两次查询去验两边一致是循环论证。

风控没有这种耦合：它读的是事件，写的是名单与判定，跨库读一次事件是可接受的。

## 5. 拆分会打破的三件事

### 5.1 积分抵扣与建订单不再同事务 ★ 最大的一处

今天「扣积分」和「建订单」在一个数据库事务里，一个失败全都回滚。
阶段 3 之后这个保证消失，而它保的是真钱：

- 扣了分没建单 → 用户白丢积分
- 建了单没扣分 → 平台白送钱

**两个方向都不能接受**，所以必须换成两阶段：

```
下单前  预扣（HOLD）      积分置为占用，有超时
下单成  确认（COMMIT）    占用转为已扣
下单败  释放（RELEASE）   占用还回；超时未确认也自动释放
```

加 Outbox 补偿：`COMMIT` 消息丢失时，超时释放会把分还给用户，
而订单侧再走一次确认——**宁可多释放一次，不可少还一次**。

这是**阶段 3 的准入条件**，不是「以后优化」。阶段 1、2 不受影响（还在同库，事务照旧）。

### 5.2 行级数据域从线程上下文变成显式传递

`DataScopeContext` 是线程本地的，跨服务不存在。
支付域的查询要么显式带作用域参数，要么由调用方在 `pay-api` 上传进来。
（这条与 TDD-三端服务拆分 §7.2 是同一件事，此处不重复。）

### 5.3 跨域事务变成 Outbox + 幂等

`markPaid` 里「改订单状态 + 生成结算单」今天同事务。
拆开后订单侧发事件、支付侧消费并幂等落单。
**幂等键必须是子单号**（已有唯一索引），不能靠事件 id ——
事件会重投，而重投两次生成两张结算单就是给商家多打一次钱。

## 6. 怎么判断这个决策错了

写下来是为了将来能证伪，而不是事后各说各话：

| 信号 | 说明这个决策错在哪 |
|---|---|
| 阶段 1 的 ArchUnit 闸门要频繁加例外 | 边界画错了，`pay/` 里装了不属于它的东西 |
| 阶段 2 之后跨库快照频繁需要「刷新」 | §3.3 的快照策略与真实用法不符，该改成回查 |
| 阶段 3 之后下单 P99 明显变差 | 积分预扣那一跳的代价超过预期，应退回阶段 2 |
| 支付域的发布频率与主站没有拉开 | 独立产物没有换来独立节奏，阶段 3 的收益不成立 |

**前两条在阶段 1/2 就能观察到，而那时回退成本还很低**——这正是分阶段的意义。

## 7. 待确认（阶段 3 的前置，不确认不能进）

1. **积分预扣的超时定多久？**太短会误释放正在支付的单，太长会占住用户的分。
2. **pay-svc 不可用时下单怎么办？**降级放行（不抵扣直接下单）还是拒绝下单？
   这是产品决定 —— 放行意味着用户看到的抵扣金额与实际付款不一致。
3. **审计与合规**：账在独立库之后，谁有写权限、怎么留痕、备份与保留期限。
4. **阶段 3 到底做不做**：§3.1 已说明停在阶段 2 是合理终点。**今天不承诺**。
