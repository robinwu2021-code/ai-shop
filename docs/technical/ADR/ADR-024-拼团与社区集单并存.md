# ADR-024 · 拼团与社区集单并存，集单是日常、拼团是拉新

**日期**：2026-09-18 　**状态**：待确认 　**相关**：[PRD-营销-活动统一模型](../../requirements/PRD-营销-活动统一模型.md) · [TDD-营销-活动统一模型与集单](../TDD-营销-活动统一模型与集单.md)

## 背景

「团购」在这个仓库里一直是拼团的机制：`mkt_group_buy` 有起团人数、发起人、成员表，成团与否看人数。
但它的 `pickup_no` 列注释写的是另一件事 ——「团购拼的是一车送到一个点的成本」。
这是**社区集单**的经济逻辑：便宜来自按量进货、一车送到自提点，而不是来自凑够几个人。

平台形态是社区小店 + 自提点 + 生鲜为主，店主自己进货。对他最痛的是进多少货、会不会烂在手里，
拼团回答不了这个问题。

## 决定

1. **两者都做，定位不同**：集单是日常经营（以销定采），拼团是拉新工具（买家转发带人）。
2. **同一个活动模型**：都是「集体达成」类，区别只在成团条件 ——
   拼团 `GROUP`（不同买家数 ≥ N），集单 `CUTOFF`（到截单时刻）。优惠都是 `PRICE`。
3. **实例分两张表**：团留在 `mkt_group_buy`；集单新建 `pmt_period`（一期）。
   不把集单塞进团表：团按人计数，凡按 `min_count` 判断的地方都会把集单误当成团，而且不报错。
4. **提货日存在订单上**（`ord_sub_order.arrive_date`），履约不反查营销域。
5. 界面上**集单排在团前**：每天一期、每天要看。

## 不可逆的部分

- `pmt_period` 表与 `ord_sub_order` 两列一旦上线有数据，就不能再合并进团表。
- 订单的提货日口径从「下单日」变为「集单单取期的提货日」：履约看板、分拣单跟着变。
  非集单单保持 NULL，口径不变。

## 放弃的方案

- **只做拼团**：不解决以销定采；且现有团到期没有任何处理（凑不齐的团永远挂着、钱不退）。
- **只做集单**：丢掉唯一有传播性的玩法。
- **集单复用 SKU 预售字段**（`prd_sku.cutoff_at`）：一次性、挂在单个 SKU 上，没有「每天一期」。
