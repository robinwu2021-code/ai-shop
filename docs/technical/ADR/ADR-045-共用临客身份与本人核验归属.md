# ADR-045 共用临客身份与本人核验归属

日期：2026-10-22。状态：已确认，按主TDD§2.22 Task54起逐项实施验收。

## 背景

REC-01需要临客登记/认领及签到。现有会员码及CustomerIdentityPort只有真实会员短期引用；BTG匿名号不是买家，手机号资料不证明真实账号。零售、餐饮、美业均可能接待临客，行业不应复制身份表。

## 决策

临客注册和唯一认领归member原所有者，中立合同放shop-base/spi/member；美业只保存guestNo或规范customerRef。owner核验当前账号完整命名空间、当店权限及门店归属，机器令牌不赋权。认领必须临客随机凭证加原会员系统解析的真实身份引用，成功后不可改绑。登记不建用户/会员/订单；识别/签到/付款/履约分离。本人proof复用现有MEMBER_CODE并核当前CONSUMER-USR，登录令牌不充会员码。

凭证哈希仅作校验；为重启及响应丢失后原键重放，将原凭证和contact加密存于member行，AES-GCM独立32字节部署密钥、随机IV及归属/用途关联数据，无默认密钥。缺配置只关闭此能力。原始contact/凭证不写日志/outbox/幂等JSON。

## 取舍

不采用行业客户表、按手机号伪造买家、认领等同付款授权。纯哈希不能重放丢失的原凭证，进程缓存不能支撑重启/多节点，因此采用owner加密持久化；代价是新增公共表和显式密钥，轮换需后续运维方案，不能静默更换导致旧凭证不可读。

匿名BTG兼容在接待开工前详定，不凭格式伪造公共记录。跨域请求锁外执行；平台追加V537及后续经核对新版本，旧版本冻结。

实施深化：新cr1必须记录当前actor realm/kind，新guest认领拒绝旧无namespace引用，追加V538而不改已执行V537。含低熵contact的原请求指纹使用用途隔离HMAC，避免无密钥摘要离线猜测。已提交认领按精确原请求和当前权限恢复持久结果，不因原cr1自然过期重新要求授权；新认领仍严格有效证明。
