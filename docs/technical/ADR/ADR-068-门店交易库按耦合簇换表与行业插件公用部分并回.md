# ADR-068 门店交易库按耦合簇换表，行业插件里的公用部分并回交易模块

状态：**已采纳**（2026-11-26 提出；2026-11-27 用户确认，第 2 条按行业改写；2026-11-27 修订：餐饮出品整组归行业库，见文末「修订一」）
关联：[TDD-零售域对齐门店交易库](../TDD-零售域对齐门店交易库.md) · [ADR-066 业务模块按配置选数据源](./ADR-066-业务模块按配置选数据源.md) ·
[TDD-多行业统一业务架构-零售餐饮美业](../TDD-多行业统一业务架构-零售餐饮美业.md)

## 背景

数据库设计把零售、餐饮、美业共用的商品域与订单域放进门店交易库 `n_trade`（74 张表），行业特有的过程放进行业库 `n_industry`（14 张表）。
现有代码里，对应的 246 张旧表分散在 `shop-core` 的四个包、四个插件、`shop-merchant` 与 `shop-gateway`；
其中餐饮插件引用的交易表有 68 张，美业 21 张，插件里与 `shop-core` 同一件事有 8 处双份实现。
`n_trade` 内部的下单、履约、渠道、预约在同一个事务里互相写、在同一条 SQL 里互相联，和平台基础库一样不能逐表换库。

## 决策

1. **一个库一个归属模块。** `n_trade` 只由交易模块读写，句柄 `trade`；`n_industry` 只由行业插件读写，句柄 `industry`。
2. **行业插件里落在 `n_trade` 的买卖代码并回交易模块**，双份实现收成一份；依赖方向保持「插件 → spi ← 交易模块」。
   **美业的服务执行整段留在行业库**（工单、服务任务、步骤、任务与订单行绑定、服务提交、服务参与）：四处「一条语句判断加写入」只碰这几张表，美业与交易之间已经走接口（并有远程实现）；交易只记到订单行交付了几份。和餐饮出品单、厨显留行业库对称。
   同一判据下，只有一个行业用、又不和订单同事务写的表也放行业库：餐饮排队、寄存，以及人员指派与交接（`ind_assignment`）、提成规则（`ind_commission_rule`）。表数见[建议稿](../零售域-第二段建议方案与表清单.md)：`n_trade` 67、`n_industry` 28。
3. **先接句柄、后换表。** 接句柄逐子模块做，不改表，可随时推送；换表按耦合簇：
   只被读取的子模块（商品主档、社区团购与询价、顾客寄存）可以各自换；交易核心（目录可售、收银下单、订单售后、履约执行、渠道、预约资源）作为一个簇整体换。
4. **防重复靠唯一约束兜底。** 「防重由应用层做、不建表」解释为不建防重表；业务表上的防重列与唯一约束保留。

## 理由与被否掉的方案

| 方案 | 结论 |
|---|---|
| 行业插件保留公用表的代码，只把数据源绑到 `n_trade` | ❌ 一个库三处代码写，双份实现继续分叉，归属落空 |
| 美业服务执行也并进交易库的共享表（履约单元、执行、到店单） | ❌ 共享表要为美业补 13–27 列，交易库背上美业的执行模型；而执行内部的原子判断不跨交易表，留在行业库更干净（2026-11-27） |
| 逐表换库 | ❌ 下单同一事务写目录锁量、订单、预约时段；切一张表就多一处跨库事务 |
| 过渡期同实例跨库联表与同事务 | ❌ ADR-066 已否；拆库永远拆不干净 |
| 按耦合簇换表 | ✅ 簇内保持同库同事务，簇间只有读取，读取走接口 |

交易核心簇的推进方式：**在专用分支上全部改完，再一次绑定 `n_trade` 合回**（用户 2026-11-26 定；被否掉的「主库就地演进再整库搬」见 TDD §3）。

## 后果

- 交易核心簇的换表是一次集中的切换；之前要用「同库不同池」把所有跨库同事务的点找全并改掉。
- 下单里的券核销、活动限量要改成「预占—确认」两阶段。
- 美业换表前要把预约与工单拆成两个事务；到店开工单、工单结账变成「先一库、再调另一库」，靠唯一约束与扫状态补做兜底。
- 并回后 `ArchitectureTest` 的域间依赖、顶层包登记、Port 规则会立即作用到原插件代码。
- 撤回代价：接句柄可撤（解除绑定即回主库）；换表之后回退是一次数据迁移。

## 修订一（2026-11-27，用户确认）：餐饮出品整组归行业库，交易库只保留订单

**决定。** 餐饮的制作任务 `fnb_kitchen_task` 不再并入门店交易库的 `ord_execution`，与出品单、服务事件（并入厨显事件）、道次、定时出品一起留在行业库 `n_industry`。
交易库只保留订单本身：下单批次、订单行，以及订单行交付了几份；出品过程（谁在做、做到哪一步、出了多少、上了多少）全在行业库。

**为什么。** 原判断（[建议稿](../零售域-第二段建议方案与表清单.md) C2）是「厨房任务和订单批次、关账、退菜、渠道出餐信号有同事务读写，留在交易库」。
逐个服务核对后（[TDD-餐饮域迁移新库](../TDD-餐饮域迁移新库.md) §2.3）：

- 写制作任务的只有出品服务和出品耗料服务，它们写的都是出品这一组；对订单批次、订单行、账单都只读。
- 关账、渠道出餐信号、报表、退菜回库对制作任务都只读。
- 厨房的每一次动作（开始、出餐、上菜、损耗）都要在同一事务里改制作任务、记事件、改出品单。若制作任务在交易库，**这条最频繁的路径每次都跨库**；整组放行业库，它就是一个库内的本地事务。

按本 ADR 第 2 条的判据（只有一个行业用、又不和订单同事务写的表放行业库），出品整组符合；这也与美业「服务执行整段留行业库，交易只记订单行交付了几份」对称。

**剩下的跨库点**（都用「本地事务 + 业务键 + 提交后补写」，不用分布式事务）：

| 场景 | 做法 |
|---|---|
| 接单后建出品单与制作任务 | 交易提交后建，以批次号为业务键可重复；漏建由任务按「已接单、无出品单」补 |
| 退菜要取消制作 | 先在行业库按退菜行做取消（可重复），再在交易库记退菜的厨房处理状态；处理状态未完成的由任务补做 |
| 交易侧要看制作进度（关账、渠道出餐、报表、退菜回库） | 经出品的查询接口只读，按版本或摘要比对，不跨库加锁 |

**影响。** 门店交易库设计中 `ord_execution` 并入自 `fnb_kitchen_task` 的列（执行者、执行环节、下达单号、制作／出品／上菜／撤销数量）随之不再需要；
行业库增加制作任务表。设计清单与字段文档按「清单结论先记后改」等用户指令统一更新，本修订先记结论。
