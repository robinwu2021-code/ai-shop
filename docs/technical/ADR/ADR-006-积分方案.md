## 1. 已定的事

**积分成本由商家承担 —— 用户抵扣的金额，在商家收入结算时扣除。**

一笔 100 元的订单，用户用 3000 积分抵了 30 元：

```
用户实付            70 元（现金）
平台收到            70 元
商家结算时          按 100 元计算应得，再扣掉 30 元积分抵扣
```

即**积分等同于商家给出的折扣**，只是这个折扣是「以前赚的、现在花」。

### 这修正了一个之前的判断

上一轮我说「积分能被商家接收 → 是平台的负债」。**在这个成本模型下不成立**：
平台从不垫付、从不承担兑付，只是在结算时少付商家。**兑付责任在商家，平台只做记账与清算。**

这个差别很大 —— 前者要在平台账上计提递延收益，后者不用。

## 2. 未定的事：跨商家清算（这是上线前必须先答的问题）

**A 商家送出的积分，用户拿到 B 商家花掉了，谁承担？**

结算时扣的是 B 的钱，但积分是 A 送出去的。不解决这个，B 商家会拒绝接受积分。

三种解法：

| 方案 | 机制 | 优点 | 代价 |
|------|------|------|------|
| **A. 全平台通用 + 平台清算** | 积分任意商家可用；平台按月从「发放方」结算里扣、补给「接收方」 | 用户价值最高，通用积分才有吸引力 | **必须建清算系统**：发放明细、使用明细、跨商家轧差、争议处理 |
| **B. 商家专属积分** | 谁发的只能在谁那用 | 实现最简单，无清算 | 退化成会员卡，用户感知很弱；小商家的积分几乎没用 |
| **C. 平台统一发放** | 积分由平台发、平台承担成本 | 商家零成本，推广阻力最小 | **回到平台负债**，且是纯营销预算，与「结算时扣商家」矛盾 |

> **2026-08-09 补充**：多门店上线让「商家专属」这个词第一次需要精确定义。
> 定义见[跨店权益方案](../跨店权益-积分与优惠券-方案.md)：
> **商家专属 = 主体专属，主体下的多门店天然通用**（三家分店结算到同一账户，
> 店 1 送、店 3 兑是同一个口袋左手倒右手，不需要清算）。
> 跨主体仍不通用，本条的 A 方案不受影响、也未被提前消耗。
>
> **与已定的成本模型一致的只有 A 和 B。** C 与「商家结算时扣除」互斥。
>
> 我的建议是 **先 B 后 A**：一期二期用商家专属把链路跑顺（无清算复杂度），
> 等商家密度上来、确实出现「想跨店用」的诉求，再升级到 A 并同时建清算。
> 直接上 A 的风险是：清算系统没做扎实，跨商家的钱算错一次，商家信任就没了。

## 3. 完整规则（已实现，开关关闭）

### 3.1 获取

| 项 | 规则 |
|----|------|
| 发放维度 | **按商品配置**，不同商品不同积分（生鲜 30 / 家电清洗 500 / 储值卡 0） |
| 未配置商品 | 按成交额比例兜底（`defaultEarnRatio`，现为千分之一） |
| **赠品不发积分** | 否则「买赠 + 积分」可叠出套利 |
| **发放时机** | **订单完成时**，不是支付时 |

> 支付即发放的话，用户可以「下单 → 拿积分 → 立刻花掉 → 退款」，
> 积分已经花出去了追不回来。完成时发放从根上堵掉这条。

### 3.2 使用

| 项 | 规则 |
|----|------|
| 汇率 | `POINTS.perMinor`，现为 100 积分 = 1 元 |
| **抵扣上限** | 券后金额的 30%（`maxDeductRatio`） |
| **运费不参与抵扣** | 运费要付给运力，用积分抵等于平台自掏腰包 |
| 抵扣顺序 | **券先抵、积分后抵**，且积分上限按「券后金额」算 |
| 扣减时机 | **下单即扣**（不是支付后） |

> 抵扣顺序反过来的话，用户会先用积分把金额压低，导致券的门槛达不到 —— 对用户不利，也更难解释。
>
> 抵扣上限的意义在这个成本模型下更直接：**整单抵扣 = 商家一分钱收不到**，商家不会接受。
>
> 下单即扣是防「同时下多单花同一笔积分」。

### 3.3 退款与取消

| 场景 | 处理 |
|------|------|
| 订单取消 | 返还抵扣掉的积分 |
| 订单退款 | **两笔都走**：收回已发放的积分 + 返还抵扣掉的积分 |
| 幂等 | `Order.pointsGranted` 标记，防止重复核销重复发分 |

### 3.4 账务

- **余额由流水推导，不单独存字段** —— 两处存迟早对不上，而积分能折成钱，对不上就是资损
- 每条流水带 `balanceAfter`，便于对账 —— 只存变动量的话，一条错后面全错
- 流水类型：`EARN` / `USE` / `REFUND` / `EXPIRE`（C 端）、`RECEIVE` / `SETTLE`（B 端）
- **可用积分数在服务端校验**，端上传什么都不能信

### 3.5 有效期

自获得之日起 `validDays`（现为 365 天）。
未使用的积分是商家账上的或有负债，不能无限期挂着。

## 4. 一期为什么不上

1. **跨商家清算未定**（§2）—— 这是积分的地基，地基没定就上线，后面改会动到已发生的交易
2. 一期的核心是把「买卖」跑通，积分是锦上添花，不是闭环的一环
3. 商家侧还没有结算系统（ADR-002 的分账也才刚定方向），「结算时扣除」暂时无处可扣

## 6. 上线前必须定的

| # | 事项 | 说明 |
|---|------|------|
| P1 | **跨商家清算方案**（§2 选 A 还是 B） | 地基，先答 |
| P2 | 汇率与抵扣上限 | 现为 100:1、30%，均为占位值，要按品类毛利定 |
| P3 | 有效期与过期提醒节奏 | 现为 365 天 |
| P4 | 商家能否自定义发放比例 | 能的话要防「自己发自己收」套现 |
| P5 | **风控** | 刷单赚积分、商家自发自收套现 —— 机制上防不住，需要风控识别 |
| P6 | 与分账的关系 | 「结算时扣除」落到微信支付分账上是**减少分账金额**，需与 ADR-002 的分账口径对齐 |

> P6 容易被忽略但很关键：分账是在支付时按比例分的，而积分抵扣是在**结算时**扣的，
> 两者时点不同。要么分账时就按「已扣积分」的净额分，要么走后续的分账回退 —— 必须选一个。
