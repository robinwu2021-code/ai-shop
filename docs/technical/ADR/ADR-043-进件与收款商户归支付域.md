# ADR 043 进件与收款商户归支付域

> 状态：已接受 · 2026-10-25（按[开发计划 · 支付服务](../开发计划-支付服务.md) P1 推荐项执行）
> 关联：[完整设计方案](../TDD-支付服务-完整设计方案.md) D2 · [数据库表结构说明 v4](../TDD-支付服务-数据库表结构说明.md) · [I0 地基](../TDD-支付服务-I0地基.md)
> 修订：ADR-021 §3.3（收款商户解析）—— 由「按商户编号 + 主体级默认号兜底」改为「只按门店 id」
> 编号：原 ADR-041，2026-10-26 与「统一打印投递所有权」撞号，顺延为 043（[完成度复核](../支付服务-完成度复核与剩余开发计划.md) D-1）

## 1 背景

收款商户（渠道里的商户号）与进件资料今天在 `shop-merchant`：`mch_payment_merchant`、`mch_store.pay_merchant_no`、
`mch_entity.funds_mode`，解析口有 9 个方法、17 个调用方、两处原生 SQL；
主体级默认号作为兜底，导致「门店没绑也能收款、钱进了另一家店的号」（Review R01–R03）。

要支持台湾（蓝新、LINE Pay，资金直达商户）与阿联酋（PayBy 直收或平台代收，按进件结果二选一），
收款商户必须与**渠道、市场、接入方式**一起建模，而这些概念全部在支付域里。

## 2 决定

1. **进件资料、收款商户、门店绑定归支付域**（`pay_onboarding*`、`pay_merchant*`），`shop-merchant` 只保留主体与门店本身。
2. **一个主体对多个收款商户**；每个收款商户 = 某渠道里的一个商户，挂渠道与市场。
3. **收款路由只有一个解析口** `PayMerchantQueryPort`，**只按门店 id** 解析，**没有兜底**：门店没有 ACTIVE 绑定就不能收款。
4. **关联一律用 BIGINT 自增 id**（Java `Long`），与核心系统按**门店 id** 关联；新表不带 `tenant_no`。
5. 支付单在建单时**冻结路由快照**（商户、渠道、接入方式、资金路径），之后改绑不影响在途单。

## 3 未采用方案

| 方案 | 不采用原因 |
|---|---|
| 留在 `shop-merchant`，支付域经 Port 读 | 渠道、市场、接入方式都在支付域；每加一个渠道字段都要跨域改 Port，独立部署时多一条反向依赖 |
| 保留主体级默认号兜底 | R01–R03 的根因；兜底让「没绑」不报错，钱静默进错号 |
| 按商户编号（字符串）关联 | 编号可改、跨库无约束；id 自增与核心系统门店 id 一致 |

## 4 代价

- 迁移分四步（双写 → 回填 → 比对 → 读切），比对差异为 0 才读切（开发计划 I4）；收尾删旧表旧列不可逆，先备份。
- 新开门店多一步「选收款商户」；主体级默认号展开成门店绑定时有冲突报告，需人工确认。
- 两套约定（旧表 `tenant_no` / 新表无）在 I3–I4 并存，靠 `PayBaseEntity` 让新实体写不出 `tenantNo`。
