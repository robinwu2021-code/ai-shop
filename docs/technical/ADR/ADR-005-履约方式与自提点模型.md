# ADR-005 履约方式与自提点模型（含邻里自提）

状态：**待确认** · 创建 2026-08-05
关联：[ADR-004 增长模型](./ADR-004-增长模型从孵化团长转向商家自带客流.md) · [ADR-002 分账结算](./ADR-002-结算走微信支付分账.md) · [C端功能清单](../../requirements/C端功能清单.md) · [需求矩阵-三端](../../requirements/需求矩阵-三端.md)

---

## 1. 背景

[ADR-004](./ADR-004-增长模型从孵化团长转向商家自带客流.md) §5.2 为了简化模型，写了一句「**小店 = 商家 + 自提点，合一**」，并据此设计了 `Merchant.isPickupPoint`。

业务补充明确后，这个简化不成立：

> 自提是从**商家自己的门店**或者**邻居家里**提，或者通过**商家自送**或者**外接第三方物流**。

**邻居家也能当自提点，而邻居不是商家。** `Merchant.isPickupPoint` 表达不了这件事。

---

## 2. 决策

### 决策 1 —— 四类履约方式

| 履约方式 | 承接方 | 现有 strategy | 状态 |
|---|---|---|---|
| **到店自提** | 商家自己的门店 | `pickup.ts` | ✅ 有，语义收敛为「到店」 |
| **邻里自提** | **邻居家（团发起人自己家）** | — | ❌ **需新增** |
| **商家自送** | 商家本人 | `delivery.ts` | 🚧 需确认语义为「商家自送」 |
| **第三方物流** | 快递 / 即时配送运力 | `express.ts` `instant.ts` | ✅ 有 |
| 到店核销（服务） | 商家门店 | `store-verify.ts` | ✅ |
| 预约（服务） | 商家 / 服务人 | `appointment.ts` | ✅ |

### 决策 2 —— 自提点独立建模，分常驻与临时两种

**废弃 `Merchant.isPickupPoint`**，改为独立实体：

```ts
PickupPoint {
  pickupNo: string
  type: 'STORE' | 'NEIGHBOR'          // 门店 | 邻居家
  ownerType: 'MERCHANT' | 'USER'
  ownerNo: string
  scope: 'PERMANENT' | 'GROUP_INSTANCE'  // 常驻 | 团粒度
  groupNo?: string                    // type=NEIGHBOR 时必填
  addressVisibility: 'PUBLIC' | 'GROUP_MEMBERS_ONLY'
  serviceFeeRule?: FeeRule            // 仅 type=STORE 有
}
```

### 决策 3 —— 邻里自提**必须零报酬**

承接邻里自提的用户不得获得任何形式的报酬（现金、佣金、券、积分）。

---

## 3. 两种自提点的差异（这是拆分的理由）

| | **常驻自提点** | **临时自提点** |
|---|---|---|
| 主体 | 入驻商家门店 | 邻居家（团发起人） |
| 存续 | 长期，平台建档 | **团粒度，一团一销** |
| 谁能建 | 平台审核后开通 | 发起人开团时勾选「送到我家」 |
| 报酬 | 履约服务费（B9） | **必须为零** |
| 地址可见性 | 公开，进搜索与商品页 | **仅本团参团者，且仅取货时段前后** |
| 核销 | 履约台（`leader-verify`） | **发起人手机上轻核销** |
| 责任 | 商家 | 发起人签收批次，个别缺损照常走售后 |
| 计入商家评分 | 是 | **否**（不是经营行为） |

**报酬必须为零这条不能松。** 一旦邻里自提有报酬，承接的邻居就是团长 —— ADR-004 消掉的四个合规问题（分销层级、个税代扣、提现风控、职业化刷单）会原样回来。

这也是它**只能限定在「自己发起的团」范围内**的原因：它不是一门生意，是顺手。
不能开放为「任何人可申请做自提点」，那就是团长招募换了个名字。

---

## 4. 邻里自提的五条硬约束

1. **只能是发起人自己家**，不能指定别人家 —— 否则是替他人分配义务
2. 地址**不进入商品页与搜索**，只在该团的订单详情里对参团者展示；脱敏程度见 B13
3. 必须有**约定取货时段**，逾期规则比门店更严 —— 人家里不能一直堆着（B15）
4. 发起人需要一个**批次签收**动作；之后个别订单缺损照常走售后，但有留痕
5. 发起人要能在自己手机上**核销**，**权限严格限定在他发起的那个团**

> 第 5 条是新增工作量：现在核销能力只在 `leader-verify` 里、绑商家身份。
> 需要拆出一个轻量的「我发起的团 → 核销」入口，作用域为单个 `groupNo`。

## 5. 商家自送 vs 第三方物流

| | **商家自送** | **第三方物流** |
|---|---|---|
| 配送范围 | 商家自己画（LBS 半径） | 快递看地址；即时配送看运力覆盖 |
| 运费 | 商家自定（起送价 / 免运门槛） | 运费模板或运力报价 |
| 状态流转 | **商家自己点**：待配送 → 配送中 → 已送达 | 运单轨迹回调 |
| 履约异常责任 | 商家 | 承运方，平台协调 |
| 是否需骑手系统 | **不需要**，就是老板本人 | 对接第三方 |

⚠️ **商家自送不要做成骑手系统。**
小店老板骑电动车送两条街，他要的是「点一下已送达」，不是位置回传和轨迹回放。
这一条做重了，店主不会用 —— 而店主不用，送货上门这条线就是废的。

## 6. 被否决的方案

| 方案 | 否决原因 |
|---|---|
| 保留 `Merchant.isPickupPoint` 布尔字段 | 表达不了邻居家自提；`ownerType=USER` 无处安放 |
| 邻里自提点做成常驻（任何人可申请） | **就是团长招募换个名字**，ADR-004 消掉的合规问题全部回来 |
| 给邻里自提点发券/积分作为补偿 | 券和积分也是报酬，同样会催生职业化；且要为此建归因与防刷 |
| 邻里自提地址成团前就公开 | 隐私风险；且未成团的团不应暴露发起人住址 |
| 商家自送接骑手/轨迹系统 | 小店老板不会用；一期做重等于这条线不可用 |
| 即时配送自建运力 | 一期无规模，成本与合规都不划算，全外接 |
