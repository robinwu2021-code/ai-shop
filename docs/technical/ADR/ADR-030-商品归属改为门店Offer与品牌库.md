# ADR-030 商品归属改为门店 Offer，库提到品牌/连锁级

> 2026-10-08 决策 · 取代 [ADR-011 经营主体与门店边界](ADR-011-经营主体与门店边界.md) 中
> 「商品挂主体、门店做投影」那一层**实现**；ADR-011 的**钱/主体边界原样保留**。
> 相关：ADR-009（经营范围三档）· ADR-013（经营范围多级地理）· `方案-商品可见性改查询时关联.md` ·
> `商品域V2-设计规格书.md`（纸面，本 ADR 取其 listing 方向）

## 1. 背景：三层归属各说一套

ADR-011 定的边界是「钱在主体、货与人在门店」，并明确裁过两条：
**库存按门店独立**（§6.2 #2）、**评价归门店**（§6.2 #3）。
但落地时商品本身留在了主体级，门店维度靠「查询时现算的投影」补出来：

| 东西 | 实际归属 | 怎么来的 |
|---|---|---|
| 标准品库 `prd_spu_std`（311 条） | **平台级**，运营维护 | 商家取用时**把字段拷进自己的商品**，之后库改了不回流 |
| 商品 `prd_goods`（21 条）+ `prd_sku` | **主体级**（`entity_no`，无 `store_no`） | ADR-011 的双键模型 |
| 「这家店卖不卖」`prd_store_goods`（62 条） | 门店级 | 投影：无行→跟随主体 `on_sale`；有行→没有行的店视为未上架 |
| 门店价 `prd_store_price`（**1 条**） | 门店级覆盖 | 无行**回退主体价** |
| 门店库存 `prd_store_stock`（**2 条**） | 门店级覆盖 | 无行**视为 0** |

于是「一件商品在这家店卖什么价、有多少货、上没上架」要**查四张表、按三种不同的缺省方向**拼出来。
其中两种缺省方向还是**相反的**（价回退、存归零），这组不对称本身就是已记录的陷阱。

## 2. 问题

1. **连锁没有「库」**。`prd_spu_std` 是全平台单库、运营维护、复制式。
   连锁总部想维护一份自家商品库给旗下门店选品 —— 没有这个东西，
   连 V2 纸面设计里也没有（V2 的 goods 仍 `entity_no NOT NULL`）。
2. **加盟跨不过主体**。库若挂主体，同品牌不同法人（加盟店）各自一份，改一次要改 N 份。
3. **门店差异化是「投影」而不是「拥有」**。门店不能有一件「主体池里没有」的商品 ——
   它必须先在主体池里存在，再由店级行决定卖不卖。这与「商品挂门店」的直觉相反，
   也是 `prd_store_price`/`prd_store_stock` 近乎空置（1 条 / 2 条）的原因：
   这套覆盖式差异化**太绕，没人用**。

## 3. 决策

### 3.1 三层，各层只管一件事

```
品牌/连锁 brand                     ← 新聚合，在 entity 之上，可跨法人
    └── 品牌商品库 prd_brand_spu     ← 模子：类目/标题/图/规格(带 optionCode)。无价、无存、不上架
             │ 引用式（不拷贝）
门店 store ──┴──▶ 门店商品 Offer  prd_goods(goods_no, store_no)
                      ├─ 来源：自建 | 引用品牌库
                      └─ prd_sku(goods_no) ← 价、存、上架 就在这一层，没有第二层覆盖
```

**可售单元 = 门店 Offer。** 「这家店卖什么、什么价、多少货」一张表答完。

### 3.2 两条建品路径，都落成门店 Offer

| 路径 | `brand_spu_no` | 语义 |
|---|---|---|
| 门店自建 | `NULL` | 这家店自己的货，不进任何库 |
| 从品牌库选品 | 库条目号 | **引用**：类目/规格以库为准，价/存/上架是门店自己的 |

引用式与现在的「复制式」关键差别：**库改了，引用它的门店 Offer 跟着变**（标题/图/规格），
价和库存永远不跟 —— 那是门店的。这正是连锁总部要的：改一次，旗下全改。

### 3.3 `goods_no` 不换，只改归属语义

`goods_no` 在后端 **259 个文件**里出现，订单链路也引用它。
所以：**不新造标识符、不改名**，只给 `prd_goods` 加 `store_no NOT NULL`，
把它从「主体商品」重新解释为「门店 Offer」。

### 3.4 `entity_no` 留在 Offer 上，作结算键

ADR-011 的硬约束不变：**通道按营业执照发号，进件/分账/结算认主体**。
Offer 的 `entity_no` 由 `store_no` 推导、冗余存一份，使结算、分账、积分链路
**一行都不用改**（与 ADR-011 §3.2「双写」同一个手法）。

### 3.5 库在 B 端 app 维护，不新建账号体系

**维护端 = B 端 app**（不是运营端代维）。难点是 `mch_account.entity_no` 绑**单一主体**，
而品牌要跨法人。解法是**不动账号模型**：

- `mch_brand.hq_entity_no` 指定该品牌的**总部主体**；
- 总部主体的 `OWNER`/`MANAGER` 持新权限码 `biz:brand:spu` → 在 B 端看到「品牌商品库」并可写；
- 同品牌下其他主体（加盟）只读库、只能选品。

弃掉的是「给品牌单独发一套账号」：那要在 `mch_account` 之上再加一级身份，
而现实里总部本身就是一个在平台上经营的主体（如虹选科技），它已经有账号。

### 3.6 三张表被吸收

| 原表 | 处置 | 理由 |
|---|---|---|
| `prd_store_goods`（62） | **删**，`on_sale` 落到 Offer 自身 | Offer 已经是门店级，「哪家店卖不卖」就是「有没有这条 Offer」 |
| `prd_store_price`（1） | **删**，价就是 `prd_sku.price` | 门店级 Offer 的 sku 天然是门店价，不需要覆盖层 |
| `prd_store_stock`（2） | **删**，存就是 `prd_sku.stock` | 同上。连带消掉「价回退 / 存归零」两个相反缺省 |

可见性也随之简化：不再是「主体商品 × servingStores × 货架行」三方现算，
而是 **Offer 自己知道在哪家店 → 那家店送不送得到买家社区**（`ReachRule` 不变）。

## 4. 明确不做的

| 不做 | 为什么 |
|---|---|
| 门店级独立进件/分账/费率 | ADR-011 的硬约束，通道按主体发号。未变 |
| 把 `entity_no` 从 Offer 上摘掉 | 它是结算键。摘掉等于动四个域，收益为零 |
| 换掉 `goods_no` | 259 个文件 + 订单历史引用它 |
| 品牌库存价/库存 | 库是模子。价存永远是门店的，否则连锁又回到共享池 |
| 跨品牌共享库条目 | 库按品牌隔离；要共享就是平台标准品库（`prd_spu_std` 保留，另一层） |
| 给品牌单独发账号体系 | 总部本身就是平台上的经营主体，已有账号。改用 `hq_entity_no` + 权限码（§3.5） |
| 运营端代维品牌库 | 维护端定在 B 端 app。运营端只保留平台级强制下架 |
| 废弃 `prd_spu_std` | 它是**平台级**公共模子（311 条，含 barcode/optionCode），与品牌库不同层，保留 |

## 5. 代价与取舍

| 代价 | 量 | 说明 |
|---|---|---|
| 一件主体商品可能裂成多条门店 Offer | 现存 21 件 / 62 条货架行 | 存量极小。原 `goods_no` **留给主体默认店那条 Offer**，其余店新发号，历史订单引用不断 |
| 可见性/下单/B 端/运营端读写要改 | `StoreGoods` 12 文件、product 域 21 文件、商品端点 20 个 | 这是本次改造的主体工作量 |
| 多门店主体新建商品要选店 | 产品交互变化 | 单店主体默认落默认店，交互不变 |

**为什么现在做划算**：存量 21+62+311 行，迁移便宜；而三张近乎空置的覆盖表
（1 条、2 条）说明现有差异化机制已经被用户用脚否决了。
晚做的成本是线性涨的（商品越多越贵），早做的成本就是现在这一次。
