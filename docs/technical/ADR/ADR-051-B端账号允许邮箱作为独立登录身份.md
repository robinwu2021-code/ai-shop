# ADR-051 B端账号允许邮箱作为独立登录身份

状态：已接受（2026-11-05，随 [TDD-B端邮箱验证码注册登录](../TDD-B端邮箱验证码注册登录.md) 一并确认）
日期：2026-11-05

## 背景

`IdentityType` 的类注释写明：**手机号是唯一权威标识，注册时强制获取**。
这条选择对国内 C 端成立 —— 手机号跨微信生态、跨 App、跨 H5，且用户真实控制。

台湾一期打破了它的前提：没有可用的国际短信通道，PRD（`PRD-台湾一期…-V3` §3.1）规定
「以邮箱验证码注册／登录及已支持的密码登录为实际入口」。也就是说，**会有一批 B 端账号从注册起就没有手机号**。

数据层已经允许：`usr_account.phone`、`mch_account.login_phone` 均可空，`usr_identity` 以 `(identity_type, identity_value)` 唯一。
需要决定的是模型口径。

## 决策

1. **`EMAIL` 成为与 `PHONE` 并列的认人凭证**，进入 `IdentityType.RESOLVE_ORDER`，排在 `PHONE` 之后。
   邮箱值统一归一化为 `trim + 全小写`，不做供应商专属的别名合并（如 Gmail 的点号与 `+tag`）。
2. **不自动合并**：同一人先用手机号、后用邮箱各注册一次，就是两个账号。系统不凭「看起来是同一个人」去合并。
3. **邮箱登录不参与员工匹配**：员工仍只按手机号认（`staff-login` 与 `PHONE_OTP` 分支），邮箱账号只能是店主身份。
4. 「手机号唯一权威标识」的注释改为：**手机号与邮箱都是权威标识；同一账号可以先后拥有两者，但只能由已登录的本人主动绑定，系统不推断。**

## 后果

- 正面：台湾商户有了真实可用的注册入口；不加表、不加迁移。
- 负面：可能出现「同一人两个账号、门店分散」。缓解是后续在「我的 → 账号」提供已登录状态下的绑定（单开 TDD），而不是在登录时自动合并。
- 不可逆点：一旦有邮箱账号建了店、下了单，再回到「手机号唯一」就要求这些账号补手机号或迁移，代价很高。所以这里单独记录。

## 被否决的选项

- **邮箱只作为手机号账号的附加联系方式**：台湾一期根本拿不到手机号验证，等于没有入口。
- **按邮箱或手机号自动合并**：合并一旦错了会把两个商户的门店与资金混在一起，且无法安全拆分。
