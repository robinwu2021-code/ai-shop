# ADR-016 后端暂不拆构建产物 —— 边界在数据，不在 jar

状态：**已决策** · 创建 2026-08-13
关联方案：[TDD-backend](../design/TDD-backend.md) §4 · [ADR-001](./ADR-001-商家端形态与拆分时机.md) §3（拆分理由的写法沿用）

---

## 1. 背景

问题：后端能不能**至少拆成两个服务**——一个 C 端 + B 端，一个平台端，将来再拆成三个？

这个问题值得单独立案，因为它在讨论时会与一件**已经做到的事**混淆：

> **运行时它已经是两个服务了。**
> `api`（8080 · 公网 · C+B）与 `ops`（8081 · 内网 · 平台面）今天就是两个独立进程，
> 加上 `worker`（无 HTTP · 定时任务）一共三个。同一个 jar，只差 `--spring.profiles.active`。
> 隔离靠的是**路由不存在**（Controller 各带 `@Profile`），不是安全链——
> 以 ops 起时 `/mp/**` 返回 404 而不是 401。

所以「ops 挂了 C 端照跑」「平台面不上公网」「两侧各自伸缩」——**这些已经是现状**。
真正待决的是要不要拆成**两个构建产物**（两份 jar、两条流水线、两个可独立发布的单元）。

---

## 2. 决策

**暂不拆构建产物。** 保持模块化单体 + 三 profile 部署。

拆分的准备工作继续按 [TDD-backend](../design/TDD-backend.md) §4 的既定路线走
（沿用 powerbank ADR-017 的双形态：**拆分是「改依赖列表」，不是重构代码**）。

---

## 3. 依据：共享面有多大（实测，不是估计）

把每个 Controller 构造器注入的 Service 收集起来，按 `@Profile` 分两侧：

| | 数量 |
|---|---|
| 只有 C/B 侧用 | 20 |
| 只有平台侧用 | 16 |
| **两侧共用** | **15** |

共用的 15 个**不是边角料，正是核心域**：

```
MerchantOrderService  AfterSaleService  SettleService  MerchantGoodsService
GroupService  ReviewService  CouponService  CampaignService  CategoryService
MessageService  MerchantStaffService  AdmissionService  CommunityAdminService
RegionService  OpsService
```

拆 jar 之后这 15 个只有三条路，每条都要付账：

| 处置 | 代价 |
|---|---|
| 复制两份 | **当天就分叉**。同一条业务规则两处实现，改一处忘一处，而分叉不报错 |
| 抽成共享库 | 还是一起发版 —— **独立发布这个唯一收益直接归零** |
| 变成 RPC | 拿到网络成本、版本兼容、分布式事务，而库还是同一个 |

### 3.1 决定性的一条：一个 schema

`ai_shop` 一个库，两侧读写同一批表（`MerchantOrderService` 同时服务
`BizOrderController` 与 `OpsOrderController`，落到同一张 `ord_order`）。

**拆了进程但共库 = 分布式单体**：付微服务的全部成本，拿不到它的任何好处。

> **边界在数据，不在 jar。** 先拆 jar 再想数据，等于把最难的一步留到最后，
> 而那时已经有两条流水线在依赖「现在这样也能跑」。

---

## 4. 什么时候这个决策翻盘

一条明确的线，写下来免得每季度重新讨论一次：

**驱动力是组织，而不是技术时。**

两个团队要各自排期、各自发版、互不阻塞 —— 那时拆构建产物的价值是**团队自治**，
值得为 §3 那笔账买单。技术上今天不缺这一刀：想要的隔离已经在三 profile 里拿到了。

次要的翻盘条件：某一侧出现独立扩缩容诉求，而 profile 级别的伸缩满足不了
（今天 `api` 已经可以水平扩，`ops` 1–2 实例，这个诉求尚未出现）。

---

## 5. 现在该做的两件（都比拆 jar 便宜）

### 5.1 把「能不能拆」变成客观依据

[TDD-backend](../design/TDD-backend.md) §4 规划了 `module-graph.py`（原文：
**判断「能不能拆」的唯一客观依据**）与 `split-readiness.py`（拆分就绪度体检），
**两个都还没建**。

本 ADR 的 §3 数字是临时写脚本量出来的 —— 这正说明问题：
这个依据不存在，所以每次讨论都只能凭感觉。它应该常驻。

### 5.2 第一刀切在数据

那 15 个共用服务里，平台侧有相当一部分是**只读**（看板、报表、审核队列）。
这类先走只读副本，**不拆服务就能把读负载与故障域分开** —— 是真正朝边界走的一步，
而不是把耦合从进程内搬到网络上。

---

## 6. 已经在留的缝（不需要新做）

| 缝 | 现状 |
|---|---|
| 跨域调用走 `shop-spi` 的 Port | 单体内是本地调用，微服务形态换 RPC 实现，**调用方一行不改** |
| `shop-merchant` / `shop-settle` 独立成工程 | 理由原文就是「变更节奏与外部依赖都与核心域不同，**最可能先拆微服务**」 |
| 模块数 = 未来可能的部署单元数 | 域多不等于工程多；工程边界按可裂解画，不按代码整洁画 |
| Controller 不直连数据 | 三层齐全落库，不留 powerbank 那边「Controller 直连内存」的口子——那是最难拆的一块 |

---

## 7. 一句话

**问的是「能不能拆成两个服务」，答案是：运行时早就是了；
而拆成两个构建产物，今天换不回它的代价——真要拆，第一刀切在数据库，不是切在 jar。**
