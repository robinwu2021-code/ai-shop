# ADR-018 App 生产形态与推送通道

状态：已接受（2026-08-14 用户拍板）
关联：[TDD-通知与消息推送](../design/TDD-通知与消息推送.md) §4.2 决策 1/2

## 决策

1. **App 生产形态走 uni-app 原生打包**（HBuilderX 云打包/离线 SDK），不把 `android-shell/`
   演进为生产壳。b-app / c-app 本就是 uni-app 工程，原生打包的产物即真 App；
   `android-shell` 保持其自述定位 —— 开发预览用的 WebView 壳，没有原生能力。
2. **推送通道走 uni-push 2.0，先用免费档**。uni-push 2.0 的底座是个推：
   端上 `uni.getPushClientId()` 拿到的 clientId 就是个推 cid，后端直连
   **个推 RestAPI V2** 发送（appId/appKey/masterSecret 在 uni-push 控制台可见）。
   厂商通道（小米/华为/OPPO/vivo/荣耀）与 APNs 在同一控制台配置，后端零改动。

## 理由

- 原生打包路线的原生代码量≈0：clientId 获取、厂商通道注册、推送点击深链都由
  uni-push 封装；自建壳路线这三件事都要手写 JS 桥，且支付/扫码等其它原生能力同样要补。
- 免费档的取舍（写进验收口径）：**在线消息（个推长连接）不限量**；
  **厂商离线通道有日配额**，且各厂商的高优先级（息屏响铃）要按厂商逐家申请资质。
  一期规模（单城市几百商家）下免费档够用；量上来后升级付费档或换商 ——
  后端只依赖 `PushPort`，换商=换一个 gateway 实现。
- 行政前置不变：DCloud 账号 + 各厂商开发者账号/通道资质 + Apple 开发者账号，
  周期以周计，与开发并行推进。

## 后果

- 后端 `PushPort` + `GetuiPushGateway`（个推 REST V2）+ 桩即日可落地，
  真实凭据到位前全链路以桩闭环（同短信/订阅消息的既有模式）。
- iOS 依赖 uni-app 打包出 iOS 产物 + APNs 凭据，排期挂在行政项后。
- 「息屏必达响铃」这句承诺在免费档下只对配额内的离线消息成立，对商家话术如实。
