# ADR 042 统一销售渠道接入与行业来源隔离

> 状态：已按用户选择的跨行业方向分批实施；五模块、C0基础/授权及C1目录同步内核已编码验证，完整目标与真实平台仍分批推进。日期：2026-10-26。关联：[PRD](../../requirements/PRD-统一销售渠道接入.md)、[TDD](../TDD-统一销售渠道接入.md)。

## L1 决策

选择shop-commerce-integration五模块聚合，包ai.neargo.shop.commerce、cim_表族。餐饮与零售通过唯一行业来源Port提供目录、订单接入与履约；外部平台通过能力接口与AbstractCommerceGateway接入。现阶段同业务库、独立表前缀及迁移；未来独立库/进程时保留业务身份和合同。

## L2 方案比较

| 方案 | 代价 | 决策 |
|---|---|---|
| 餐饮、零售各建渠道系统 | 平台协议、授权、重放和对账重复；同外部门店全量覆盖冲突 | 不选 |
| 只扩展food-channel | 与既有访问CORE/支付/库存的内部适配混淆；电商/券核销难以独立 | 不选 |
| 独立通用模块加行业来源适配 | 需明确唯一SPI、目录发布范围及订单责任方 | 采用，符合用户明确方向 |

## L3 关键约束

1. 平台账号授权和店铺连接分离，一个授权账号可覆盖多店。Token轮换不改变远端订单去重身份。
2. 一份远端全量替换范围只有一个目录发布所有者；本地多餐牌/零售选品在捕获时合成完整快照，动态继承不进入平台执行。
3. 同步原请求、事件、外部动作和行业导入分别持久化，使用原Outbox唤醒。任何部署形态都不得依赖跨网络共享事务。
4. 平台、即时配送/快递/券核销分别声明能力；最终操作不允许平台子类跳过权限/能力检查、结果分类和调用留痕。
5. 原核心商品/订单/库存/支付/物流/权益是业务权威；渠道只保存快照、映射和接入回执。外部价格须由原定价来源合同核验后进入核心，不能造渠道计算内核。
6. 跨域Port在commerce-api的ai.neargo.shop.spi.commerce保持唯一；core不依赖web/channel或行业实现。独立server与宿主公开web保持现有平台部署分工。

## L4 后果与可逆性

收益是新增渠道复用同步与恢复，新增行业复用平台连接。代价是每个行业必须提供可信来源合同；没有付款/履约/权益合同的能力不能假装完成。混合行业目录/订单、连接跨主体转让、未获准平台协议首版关闭。

原fnb绑定和外部映射不直接改名为cim表：先盘点实际使用、制定增量迁移、保留旧订单引用，再切单写者。旧迁移冻结。生产独立拆分必须先排空/移交未决动作，切换稳定网关路由并证明单写者，不能两形态同时接单。
