# ADR-067 门店交易库按耦合簇换表，行业插件里的公用部分并回交易模块

状态：**提案，待用户确认**（2026-11-26）
关联：[TDD-零售域对齐门店交易库](../TDD-零售域对齐门店交易库.md) · [ADR-066 业务模块按配置选数据源](./ADR-066-业务模块按配置选数据源.md) ·
[TDD-多行业统一业务架构-零售餐饮美业](../TDD-多行业统一业务架构-零售餐饮美业.md)

## 背景

数据库设计把零售、餐饮、美业共用的商品域与订单域放进门店交易库 `n_trade`（74 张表），行业特有的过程放进行业库 `n_industry`（14 张表）。
现有代码里，对应的 246 张旧表分散在 `shop-core` 的四个包、四个插件、`shop-merchant` 与 `shop-gateway`；
其中餐饮插件引用的交易表有 68 张，美业 21 张，插件里与 `shop-core` 同一件事有 8 处双份实现。
`n_trade` 内部的下单、履约、渠道、预约在同一个事务里互相写、在同一条 SQL 里互相联，和平台基础库一样不能逐表换库。

## 决策

1. **一个库一个归属模块。** `n_trade` 只由交易模块读写，句柄 `trade`；`n_industry` 只由行业插件读写，句柄 `industry`。
2. **行业插件里落在 `n_trade` 的代码并回交易模块**，双份实现收成一份；插件只留行业库 14 张表的代码。依赖方向保持「插件 → spi ← 交易模块」。
3. **先接句柄、后换表。** 接句柄逐子模块做，不改表，可随时推送；换表按耦合簇：
   只被读取的子模块（商品主档、社区团购与询价、顾客寄存）可以各自换；交易核心（目录可售、收银下单、订单售后、履约执行、渠道、预约资源）作为一个簇整体换。
4. **防重复靠唯一约束兜底。** 「防重由应用层做、不建表」解释为不建防重表；业务表上的防重列与唯一约束保留。

## 理由与被否掉的方案

| 方案 | 结论 |
|---|---|
| 行业插件保留公用表的代码，只把数据源绑到 `n_trade` | ❌ 一个库三处代码写，双份实现继续分叉，归属落空 |
| 逐表换库 | ❌ 下单同一事务写目录锁量、订单、预约时段；切一张表就多一处跨库事务 |
| 过渡期同实例跨库联表与同事务 | ❌ ADR-066 已否；拆库永远拆不干净 |
| 按耦合簇换表 | ✅ 簇内保持同库同事务，簇间只有读取，读取走接口 |

交易核心簇的推进方式：**在专用分支上全部改完，再一次绑定 `n_trade` 合回**（用户 2026-11-26 定；被否掉的「主库就地演进再整库搬」见 TDD §3）。

## 后果

- 交易核心簇的换表是一次集中的切换；之前要用「同库不同池」把所有跨库同事务的点找全并改掉。
- 下单里的券核销、活动限量要改成「预占—确认」两阶段。
- 并回后 `ArchitectureTest` 的域间依赖、顶层包登记、Port 规则会立即作用到原插件代码。
- 撤回代价：接句柄可撤（解除绑定即回主库）；换表之后回退是一次数据迁移。
