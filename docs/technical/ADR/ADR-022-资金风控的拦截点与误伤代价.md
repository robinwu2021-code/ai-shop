# ADR-022 资金风控的拦截点与误伤代价：拦在钱要动的那一刻，不拦在下单

> 2026-08-30 提案 · **已决策**（§3）· 阈值与止损线未定，见 §6
>
> 相关：[ADR-021](./ADR-021-支付域独立为服务与独立库.md)（域边界：`risk_*` 留主库）·
> [账期与对账放款-方案](../design/账期与对账放款-方案.md)（三道门与四个退款时区）·
> [TDD-运营端风控域](../design/TDD-运营端风控域.md)（既有风控域：内容 / 账号 / 刷单）

---

## 1. 一句话

**资金风控只拦三处：放款前、退款前、进件时。**
不在下单那一刻拦——那里已经有准入闸（保证金 / 限额 / 履约矩阵），
再叠一层的收益远小于误伤真实交易的代价。

---

## 2. 问题

资金风控天然有两个方向的错，而**它们的代价完全不对称**：

| | 后果 | 可逆吗 |
|---|---|---|
| **漏放**（该拦没拦） | 钱出去了追不回来（Z4） | ❌ 基本不可逆 |
| **误伤**（不该拦拦了） | 真实商家的真实货款被冻住 | ✅ 可逆，但**信任不可逆** |

直觉会说「漏放更严重，所以宁可多拦」。**这个直觉在这里是错的**，理由有两条：

1. **误伤的代价不是「晚几天到账」，是商家不再信任这个平台。**
   一次无解释的冻结，比十次准时到账更能决定他还做不做。
2. **漏放已经有第二道防线**（保证金 → 欠款抵扣 → 停止放款），而误伤没有。
   被误伤的商家不会等我们排查完。

所以本文的取向是**明确的**：宁可漏放一笔进入追偿流程，不可无依据地冻住一笔正常货款。

---

## 3. 决策

### 3.1 三个拦截点，各拦各的

| 拦截点 | 时机 | 拦什么 | 拦住之后 |
|---|---|---|---|
| **P1 进件时** | 提交进件资料 | 主体黑名单、证照造假信号、同一证照多主体 | 拒绝进件，给出原因 |
| **P2 放款前** | 批次 `RECONCILED → RELEASED` | 异常交易占比、退款率突增、集中大额、欠款未清 | **整批挂起**，转人工，商家可见「审核中」与预计时长 |
| **P3 退款前** | 发起退款 | 退款滥用（同人同店高频）、金额异常 | 转人工裁决，**不自动拒绝** |

**不设 P0（下单时拦）。** 下单那一刻已经有四道准入闸
（保证金足额、单笔限额、日累计限额、履约方式矩阵）。
再加一层资金风控，拦的是同一批信号，而每一次误判都直接变成用户下不了单。

### 3.2 拦截的判据必须是**可解释的**

规则命中之后，**必须能对商家说出人话**：「本批次因近 7 天退款率 32%（阈值 20%）转人工复核」。

说不出人话的规则不许上线。理由不是体验，是**申诉链路走不通**：
商家不知道自己触发了什么，就只能反复问客服，而客服也看不到判据——
最后变成「系统说的」，那是信任崩塌最快的一条路。

> 这条排除掉一类做法：**不可解释的综合评分**。
> 打分模型可以用来**排序**（先看谁），不可以用来**判定**（拦不拦）。

### 3.3 处置一律是「挂起 + 人工」，不是「自动拒绝」

| 动作 | 允许自动 | 理由 |
|---|---|---|
| 挂起放款、转人工 | ✅ | 可逆，且钱还在冻结态没跑掉 |
| 拒绝进件 | ✅ | 可重新提交，代价低 |
| 扣划保证金 | ❌ **必须人工** | 动商家的钱，且法务边界未定（§6） |
| 拒绝退款 | ❌ **必须人工** | 拒的是买家，直接变成投诉与监管风险 |
| 封禁主体 | ❌ **必须人工** | 已在既有风控域，本文不改 |

### 3.4 挂起要有**时限**，超时自动放行并告警

**没有时限的挂起等于永久冻结**，而它会以「还在排查」的形式一直存在。

```
挂起 → 人工处置窗口（建议 2 个工作日）
         ├── 处置了 → 放行 / 继续挂起（必须写原因）
         └── 超时未处置 → 自动放行 + 告警
```

自动放行看起来危险，但对比的是另一面：**一个没人看的队列会把所有单都变成永久挂起**。
超时放行让「没人处置」这件事**立刻变成一个可见的问题**，而不是慢慢积压成常态。
（这与冻结窗口 `Tmax` 是同一个道理：到期必然发生的事，要么主动处理，要么它自己发生。）

### 3.5 风控数据留主库，规则在支付域求值

`risk_*` 四张表不进支付库（[ADR-021 §3.2](./ADR-021-支付域独立为服务与独立库.md)）。
支付域**通过 Port 读判定结果**，不读规则表：

```
pay-risk（支付域内）           risk 域（主库）
  ├─ 算资金侧指标              ├─ 名单
  │   退款率 / 集中度 / 欠款   ├─ 规则
  └─ 问一次「这个主体有没有 ───┘  └─ 事件
     资金相关的名单命中」
```

**指标在支付域算，名单在风控域查。** 分工的依据是数据在哪：
退款率要读结算单与退款流水（支付库），名单要读 `risk_blacklist`（主库）。
反过来做的话，两边都要跨库。

## 4. 资金风控看的五类信号

| 信号 | 判据 | 数据源 | 拦在 |
|---|---|---|---|
| **退款率突增** | 近 N 天退款额 / 成交额 超阈值 | 支付库 | P2 |
| **集中大额** | 单批放款额 > 保证金 × 倍数 | 支付库 | P2 |
| **欠款未清** | `mch_debt` 余额 > 0 | 支付库 | P2 |
| **异常交易形态** | 同人同店高频、整数额、深夜集中 | 支付库 + 订单 | P2 / P3 |
| **主体名单命中** | 黑名单 / 关联主体 | 主库 `risk_*` | P1 / P2 |

> **前四类都能在支付库内算完**，这是把积分与结算放在同一个库的又一个收益：
> 「这个商家的钱有没有异常」不需要跨库。

---

## 5. 怎么判断这个决策错了

| 信号 | 说明错在哪 |
|---|---|
| 挂起队列长期非空且超时放行频繁 | 阈值太松（噪声太多）或没人负责，两者都要立刻查 |
| 商家申诉里高频出现「不知道为什么被拦」 | §3.2 的可解释性没做到 |
| Z4（提走后退款）仍频繁发生 | P2 拦得太晚或指标选错，风控没起到作用 |
| 因风控导致的到账延迟成为商家流失主因 | 取向判断错了，应放宽 P2 |

## 6. 待确认（不确认不能上线）

1. **各项阈值**：退款率、集中度倍数、挂起时限。**建议先跑影子模式**——
   只记录会拦谁、不真拦，跑两周看命中的都是什么人，再定阈值。
2. **保证金扣划的合规边界**：未经商家同意从保证金扣款，协议怎么写、要不要事前通知。
3. **欠款止损线**：欠多少停止合作、走什么流程、谁批。
4. **影子模式的判据**：跑完之后凭什么说「可以真拦了」——
   要在开跑之前定好，否则两周后只会得到一堆数字和一次拍脑袋。
