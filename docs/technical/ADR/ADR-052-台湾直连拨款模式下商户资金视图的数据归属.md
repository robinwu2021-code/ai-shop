## 一句话

台湾模式下渠道（蓝新、LINE Pay）直接把钱拨给商户，平台不经手资金。商户 App「我的 › 资金」只做**看**：
**数字一律来自支付服务 near-pay，ai-shop 只认人、判权、定门店、转发；平台不出现「余额」与「提现」；
渠道没回报的数一律标「预计」，对账一律标覆盖范围。**

## 背景

商户 App 交接文档第 8 模块要 7 屏资金页（原型 F01–F07），后端一个 `/biz/funds/*` 端点都没有（TDD §L2 结构表）。
做之前要先回答「这些数字归谁」，因为现状里有好几处看起来能用、其实是另一件事的东西：

1. **资金数字本来就在支付服务**。收款、退款、渠道手续费、预计入账日、结算账户掩码在 pay 域的
   `pay_order` / `pay_refund` / `stl_payment` / `pay_merchant`（`MerchantPaymentQueryServiceImpl.java:160-196`、`:446-468`）；
   费率在 `sys_pay_channel_rate`（`PayChannelRateService#effective`）；对账差异在 `stl_recon_diff`，
   已区分 `SELF_CHECK` / `CHANNEL_BILL` 两个产出方（`StlReconDiff.java` 类注释与常量）。
   166 与生产走独立服务 near-pay（`shop.pay.deployment=standalone` 时装配 `RemoteBizPaymentAppService`，
   经 `PayBizInternalApi` 的 `/internal/pay/v1/biz/stores/{storeNo}/**` 调过去）；
   本仓库 `backend/pay` 是内嵌形态（`BizPaymentAppServiceImpl` 上 `matchIfMissing = true`）与测试用，和 near-pay 是同包名的两份代码（TDD §1.1）。
2. **渠道拨款与渠道账单两边都没有**。near-pay 的设计里 `pay_channel_bill`、`pay_channel_bill_line`、`pay_reconciliation_run`
   是「拟新增，待实现」，批次「S1台湾首期：渠道账单与对账」（near-pay `docs/database/design-v2/00-数据库表清单.md`）；
   「渠道拨款」表在 near-pay 设计里没有（TDD §2.1）。本仓库 `StatementCapability` 没有实现类，near-pay 只有 mockpay 实现（TDD §1.1）。
3. **几个名字像「资金」的已有接口都不是台湾资金**（TDD §1.2）：`/biz/settle/*`、`stl_payout` 是大陆平台抽佣结算与平台放款；
   `/biz/payout-account` 是 ADR-011 自营供应商出款卡；`/biz/merchant/payment` 读 ai-shop `mch_payment_merchant`（大陆微信 / 支付宝进件档），
   台湾店没有行；`/biz/deposit*`、`/biz/merchant/debt` 是大陆入驻模型；`stl_withdraw` 已按 PRD §7 退役。
4. **两处口径分叉**（TDD §1.5）：手续费估算用配置 `shop.pay.fee.estimate-rate-bps`（默认 0，`MerchantPaymentQueryServiceImpl.java:89,470-472`），
   而费率表没人用来估算；账期码在支付服务是 `T1 / T2 / WEEKLY`（`MerchantPaymentQueryServiceImpl.java:459-468`），
   在 ai-shop 进件档注释是 `T+1 / T+N / WEEKLY / SEMI_MONTHLY / MONTHLY`（`MchPaymentMerchant.java:150-162`）。

这些选择一旦让 App 和运营形成习惯就很难收回 —— 尤其是「余额」一旦出现，就会被要求「提现」（TDD §3 末）。所以单独记录。

## 决策

### 定死的三件事（TDD §3 末）

1. **资金视图的真源是支付服务，ai-shop 不存资金数字**（D1）。
   ai-shop 的 `BizFundsController` 只做 `biz:finance` 判权、取当前门店、`scope=ENTITY` 时定门店集合并扇出；
   每一个数字都由支付服务的 `MerchantFundsQueryService` 算出，ai-shop 不建资金表、不缓存、不二次计算（相加除外，见第 7 条）。
   - 防住什么：ai-shop 自建一份就会和 near-pay 各算各的，两边对账结果分叉；而渠道凭据在 near-pay，ai-shop 本来也拉不到渠道账单。
2. **平台不提供余额与提现**（D4）。资金页没有「余额」字段、没有提现入口，`stl_withdraw` 不复活，
   `/biz/deposit*`、`/biz/merchant/debt`、`/biz/settle/*` 不被资金页复用。
   这是**这个模式下本就不该有**，不是「暂不做」：钱从渠道直达商户，平台账上没有商户的钱，「向平台提现」就是二清（PRD §2、ADR-011 §1 第 4 条）。
   若产品说的是「渠道侧提领」，那是商户在渠道后台的操作，App 只给说明或外链。
   - 防住什么：出现「余额」这个数，就默认了平台替商户保管了钱；下一步一定是「那让我提出来」。
3. **没有渠道回报时只显示「预计」，并强制带覆盖范围标识**（D3、D9、D10）。
   - 总览带 `payoutSource`（`ESTIMATED` / `CHANNEL_REPORTED`）与 `reconcileCoverage`；拨款行带 `source`；对账带 `coverage`（`SELF_CHECK_ONLY` / `CHANNEL_BILL`）。
   - 没有已校验的渠道账单时 `channelCount` 回 `null`，不回 0、不回「等于平台笔数」（PRD §3.3 AC-6）。
   - 渠道回报的实拨只放 `paidOutMinor` / `reportedMinor`；按账期推算的数放 `estimated…` 或 `source=ESTIMATED` 的行，**两类数不进同一个字段**。
   - 防住什么：一期「已拨」没有数据来源，不标的话 0 会被读成「渠道一分没拨」；没有渠道账单时显示「没有差异」是假话。

### 由此展开的执行口径（D2、D3、D5–D11）

4. **查询代码两边都写**（D2）：near-pay（166 / 生产）与本仓库 `backend/pay`（内嵌与测试）各实现一份同形的 `MerchantFundsQueryService`
   及 `/internal/pay/v1/biz/stores/{storeNo}/funds/*`；收款汇总与期间校验 `checkRange` 与已有 `MerchantPaymentQueryServiceImpl` 共用，不复制 SQL、不另写跨度上限（TDD §2.4）。
   若之后决定本仓库 `backend/pay` 冻结只留测试，改为「只写 near-pay、内嵌实现回 10505」，需修订本条。
5. **分两期上**（D3）：一期 A 上 overview / daily / reconcile / rates / accounts 全部，payouts 只出 `ESTIMATED` 行，reconcile 只有 `SELF_CHECK_ONLY`；
   一期 B 等蓝新、LINE Pay 回传拨款 / 对账文件后出 `CHANNEL_REPORTED` 行、`PAID / MISMATCH` 与渠道侧差异。
   **渠道账单与渠道拨款表由 near-pay 建**，ai-shop 不建。
6. **手续费估算用费率表，配置只兜底**（D5）：估算先查 `sys_pay_channel_rate`（`PayChannelRateService#effective`），查不到再用 `shop.pay.fee.estimate-rate-bps`；
   总览的估算与费率页显示的是**同一个费率**。
   - 防住什么：F07 显示费率表、F01 用默认 0 的配置估算，两页对不上，且总览手续费显示 0、待拨偏高。
7. **「整个商户」= 当前主体**（D7）：`scope=ENTITY` 只汇总当前 `X-Entity-No` 名下、调用者可见的门店，由 ai-shop 逐店调支付服务后按日相加；不跨主体相加。
   扇出放在 ai-shop 而不下沉支付服务：支付服务只认门店（`PayBizInternalApi` 全部按 `{storeNo}`），「哪些门店属于这个主体、这个人看得见哪些」是 ai-shop 的知识（TDD §2.5）。
   - 防住什么：账户与账期按「主体 × 渠道」，跨主体相加的数字没有对账意义，币种也可能不同。
8. **账期码以支付服务为准扩展**（D6）：统一为 `T1…Tn / WEEKLY / SEMI_MONTHLY / MONTHLY`；ai-shop 进件档与渠道默认账期向它映射。
   全集等蓝新、LINE Pay 的实际拨款周期确认后定；定之前 App 两套都翻。
   - 防住什么：选 `T+N` 那套的话，它不带天数，预计拨款日算不出来。
9. **一期总览的已拨 / 待拨按预计拨款日拆**（D10）：`paidOutMinor` 只放渠道回报值（一期为 0）；
   预计日已过的部分另给 `estimatedPaidOutMinor`（顶层与 `channels[]`），App 显示「预计已拨（未经渠道确认）」；`pendingMinor` 只算预计日 ≥ 今天的。
   拆分用的预计日与拨款行是同一个函数，两屏数字能对上；一期 B 有真数后该字段变 0 或退场。
   - 防住什么：初稿口径下 T+1 的店月底看到「待拨」几乎是整月收入，会以为渠道一分没拨。
10. **预计拨款行按（渠道 × 收款商户 × 预计拨款日）一行**（D11）：一行 = 渠道的一笔拨款，一期 B 与渠道实拨一一对应；原型 F03 改画，必要时 App 端按周折叠显示。
    预计行编号 `E-…` 是确定性编号，但不保证跨期存活；一期 B 的渠道回报行用 `estimateNo` 指回被取代的预计行（TDD §2.3 ③）。
11. **权限只看码 `biz:finance`，不看角色**（D8）：与 F06 同码、不新增权限码；`scope=ENTITY` 另要求店主（TDD §2.0 R17、§2.1）。

## 被否决的选项

| 选项 | 否决理由 |
|---|---|
| ai-shop 自建 `fnd_channel_payout` 等表，自己拉渠道账单（D1-B） | 违反 ADR-021（支付域独立为服务与独立库，账不能被别的域改）与 ADR-043（收款商户归支付域）；渠道凭据在 near-pay，ai-shop 拉不到账单；两边对账结果会分叉 |
| App 自己拼：调 summary 与每天一次 statement（D1-C） | 一个月 31 次请求；`/biz/payment/statement` 只给单日、明细上限 1000 条且无手续费（TDD §1.2）；手续费、拨款、对账仍然没有，口径散在端上 |
| 复用 `/biz/settle/*`、`stl_payout`、`/biz/payout-account` 当「拨款」 | 那是大陆平台抽佣结算、平台放款与自营供应商出款卡；台湾模式平台不放款（TDD §1.2） |
| 只写 near-pay、本仓库内嵌回 10505（D2-B） | 本仓库流程测试只能测到 10505，要改成打 near-pay 的契约测试；只在本仓库 `backend/pay` 冻结时才取 |
| 先写本仓库、near-pay 照搬（D2-C） | near-pay 晚一拍，166 上有一段时间是空接口 |
| 等渠道回传后整体上（D3-B） | 上线时间取决于蓝新、LINE Pay 是否提供拨款 / 对账文件，目前未知 |
| 一期不上 F03–F05 / 不出预计行（D3-C、D9-B） | 三屏空着，App 已做好的页面闲置；用「预计」+ 覆盖范围标识已能避免冒充实拨。若法务或产品担心预计被当承诺，退回 D9-B |
| 做提现（D4-B） | 平台没有商户余额，「向平台提现」即二清，合规上不成立（PRD §2、ADR-011） |
| 维持配置估算手续费（D5-B） | 配置默认 0，手续费显示 0、待拨偏高；费率页与总览对不上 |
| 以 ai-shop `T+1 / T+N…` 为账期码准（D6-B） | 支付服务 `settle_cycle` 与 `expectedDate` 函数都要改；`T+N` 不带天数，算不出预计拨款日 |
| 「整个商户」= 账号下全部主体（D7-B） | 跨主体相加没有对账意义，币种也可能不同 |
| 新权限码 `mch:pay:funds` 默认给店长（D8-B） | 多一个迁移、三语权限名与角色模板改动；交接文档只要求「店主、有资金权限者」 |
| 一期已拨恒 0、待拨 = 全部净额（D10-A） | 店主会以为渠道一分没拨 |
| 一期不显示已拨 / 待拨两格（D10-C） | 最不误导，但店主看不到「还有多少没到」，原型要改 |
| 后端按周 / 账期把多个预计日合成一行（D11-B） | 一行对应多笔实际拨款，一期 B 对账要拆；`expectedDate` 变成区间，语义变 |

## 后果

### 正面

- 资金页的每个数字只有一个算的地方（支付服务），与 `/biz/payment/orders*` 同一套查询、同一条期间上限，资金页跳收款明细时两边一致（TDD §2.2）。
- ai-shop 不加资金表、不加迁移、不加权限码（TDD §2.1：推荐方案 ai-shop 侧库表「无」）。
- 一期不等渠道也能上，且不冒充实拨、不冒充「已对平」。

### 负面

- near-pay 要排期，两仓库同构代码各写一次；本仓库的往返测试只证明本仓库那份，near-pay 侧要有同名测试（TDD §4、§5）。
- 一期「已拨」「渠道笔数」没有真数；「预计已拨」在渠道真实延迟时会显示已拨而钱没到，文案要写「以渠道入账为准」。
- 估算改读费率表后，已有收款汇总与详情里 `feeEstimated=true` 的数字会变，要通知 App；上线前运营要在 `sys_pay_channel_rate` 配台湾费率。
- `scope=ENTITY` 由 ai-shop 逐店扇出，门店多时慢；一期限主体内门店 ≤ 50，超出回专用错误码（TDD §2.1、§4）。

### 对 near-pay 的要求

1. 实现 `/internal/pay/v1/biz/stores/{storeNo}/funds/{overview|daily|payouts|reconcile|rates|accounts}`，形状以 TDD-商户App资金 §2.3、§2.5 为准，并带同名测试。
2. 一期 B：落地已设计的 `pay_channel_bill`、`pay_channel_bill_line`、`pay_reconciliation_run`；新增一张「渠道拨款」表（设计里没有，建议名 `pay_channel_payout`，由 near-pay TDD 定）；
   `stl_recon_diff` 加 `store_id` 或在差异生成时冗余（今天没有门店列，要经 `payment_no` 回 `pay_order.store_id`，TDD §1.1）。
3. 账期码按第 8 条扩展；渠道默认账期（`PayChannelMasterService#settleCycle`，注释举例 `T+1`）改为同一套。
4. 手续费估算按第 6 条改为费率表优先。
5. 商户资金视图只读上述数据；near-pay 设计里的 `pay_fund_account`、`pay_fund_reservation`（运营资金视图、资金冻结及提现预占，「按专项阶段」，见同一份表清单）**不进商户资金视图**，不能借它给商户出「余额」或「提现」。

### 与已有 ADR 的关系

- **ADR-021（支付域独立为服务与独立库）**：本 ADR 是它在商户资金视图上的直接应用，不修订它。
  `stl_recon_diff`、`sys_pay_channel_rate` 在它划定的支付域边界内（§3.2）；「业务系统一个字都不写支付库」（§5.3）在这里延伸为「ai-shop 也不存一份资金数字」。
  判权留在主应用、支付服务只收已收窄的查询条件（§3.5 2026-08-31 修订）——资金接口的 `biz:finance` 判权与 `scope=ENTITY` 扇出放在 ai-shop 即源于此。
- **ADR-043（进件与收款商户归支付域）**：F06 收款账户读支付服务 `pay_merchant` 经 `pay_merchant_binding` 到门店，正是它 §2 第 1、3 条的落点；
  不再读 ai-shop `mch_payment_merchant`（台湾店没有行）。预计拨款行按收款商户分组，依赖它「门店 × 渠道同时最多一条 ACTIVE 绑定」与「建单冻结路由快照」。本 ADR 不修订它。
- **ADR-011（商家资金走自营供应商模式）**：其「不做商家向平台提现」在台湾直连模式下同样成立；它的出款卡 `/biz/payout-account` 属于自营供应商轨，不进台湾资金视图。

### 不可逆点

一期 A 上线后，App 会按 `payoutSource` / `coverage` / `estimatedPaidOutMinor` 渲染。若日后改为 ai-shop 自存资金数字，或给商户出「余额」，
就要同时改 App 契约与运营口径，且会与已经形成的「平台不经手资金」认知冲突。所以第 1–3 条改动须另开 ADR 取代本篇。
