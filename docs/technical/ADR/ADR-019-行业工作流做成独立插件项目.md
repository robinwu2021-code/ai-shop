# ADR-019 行业工作流做成独立插件项目

> 状态：**提案 · 待决策** · 创建 2026-08-27
> 相关：[TDD-行业化扩展-餐饮与服务业](../TDD-行业化扩展-餐饮与服务业.md) · [标准能力基线](../reference/标准能力基线-零售为默认.md) · [ADR-016](./ADR-016-后端暂不拆构建产物-边界在数据不在jar.md)（三 profile 一份 jar 的现状） · `shop-job-api`（零依赖契约模块的先例）

## 1. 一句话

零售是基座默认形态；餐饮、美业等行业工作流做成**独立 Maven 项目**，
只面向 `shop-plugin-api` 编程，通过 Spring 自动装配挂载，**可以整个不装而系统仍完整**。

## 2. 决策

| 项 | 决定 |
|---|---|
| 插件形态 | **独立 Maven 项目**（独立 `groupId` / 版本 / 构建），不进 `shop-parent` 的 `<modules>` |
| 代码位置 | **同一 git 仓库，`backend-plugins/` 目录，独立 reactor**（理由见 §4.1） |
| 契约 | 新增 `shop-plugin-api` —— **零依赖**（连 Spring 都不引），照 `shop-job-api` 的写法 |
| 装配 | Spring Boot AutoConfiguration + `@ConditionalOnProperty`，插件在 classpath 上才生效 |
| 打包 | 默认全装（`-Pall`）；`-Pfood` / `-Pservice` / `-Pcore-only` 可打出不含某插件的 jar |
| 运行时 | **一期不做 ClassLoader 级热插拔**，理由见 §5 |
| 数据 | 插件表独立前缀 + **独立 Flyway 历史表**，与 `shop-inventory` 同一手法 |
| 依赖方向 | 插件 → `shop-plugin-api` ←（实现）— 基座。**插件不许直接引 `shop-core` 的实体** |

## 3. 先把一件事说清楚：这是多商户平台，不是单商户软件

「不同行业加载不同子项目」在**私有化交付**里是天经地义的；
但本系统是一个平台，**同一个线上部署同时服务零售、餐饮、美业三种商家**。
所以：

- **运行时默认三个插件全装**，谁生效由门店能力开关决定 —— 否则一个部署只能接一种行业的商家；
- **构建期必须能剔除任何一个插件** —— 这是插件化是否真的成立的**唯一可证伪的判据**。

于是本 ADR 采取的立场是：**按可剔除来设计，按全装来部署。**
并且用一条构建闸门把它钉住（§6）：`-Pcore-only` 打出的 jar 必须能起、能跑通零售全量场景测试。
**做不到，就说明插件边界是假的** —— 而这一点，在没有闸门时永远不会被发现。

## 4. 为什么是独立项目

### 4.1 为什么同仓、不同 reactor

| 选项 | 结论 |
|---|---|
| 进 `shop-parent` 的 `<modules>` | ❌ 那不叫插件，叫模块。一条 `mvn -am` 就把插件编进主干构建，边界当天失效 |
| **同仓 `backend-plugins/`，独立 reactor**（推荐） | ✅ 独立构建、独立版本、依赖只能通过 `~/.m2` 里安装好的 `shop-plugin-api` 拿到 —— **边界由构建强制**，而不是靠自觉 |
| 独立 git 仓库 | ❌ **现在做不到**：父 POM `neargo-parent` 只存在于本机 `~/.m2`，没有内网 Maven 仓库。跨仓依赖 SNAPSHOT 会立刻卡死在「插件仓库拉不到 `shop-plugin-api`」上 |

> 目录整体搬走就是独立仓库 —— **等有了内网仓库再搬，那是一次 `git mv`，不是重构。**
> 现在就拆两个仓库，收益为零，成本是每天两次手工 `mvn install`。

### 4.2 为什么必须有 `shop-plugin-api`

没有它，「插件」只是一个包名。
`shop-job-api` 已经证明过这条路：**零依赖的契约模块**让 worker 与业务系统各自发版而互不认识。
这里同理 —— 插件不认识 `OrdOrder`，只认识契约上的 `OrderView`。

插件不许引 `shop-core` 实体，是因为实体会连同 MyBatis、事务、库结构一起漏过去：
一旦插件里出现 `ord_order` 的列名，「改主干不动插件」就再也不成立。

### 4.3 扩展点清单（`shop-plugin-api`，零依赖）

```java
public interface IndustryPlugin {
    String code();                     // FOOD / SERVICE
    Set<String> capabilities();        // 本插件提供哪些能力码
    String schemaLocation();           // 自己的 Flyway 目录，如 db/plugin/food
}

public interface OrderLifecycleListener {          // 挂事件，不侵入交易域
    void onPaid(OrderView order);
    void onCancelled(OrderView order);
    void onRefunded(OrderView order);
}

public interface PrintPayloadProvider {            // 打印通道在基座，内容在插件
    String scene();
    List<PrintDoc> render(PrintContext ctx);
}

public interface ResourceTypeProvider {            // 桌台 / 技师 / 工位 的语义
    String resourceType();
    void onOccupied(String resourceNo, String bizNo);
    void onReleased(String resourceNo, String bizNo);
}

public interface CheckoutContributor {             // 结账前追加/校验，不改价
    CheckoutAdvice advise(CheckoutContext ctx);
}
```

**故意没有的扩展点**：改价、改库存、改订单状态。
这三样一旦开放给插件，「主干只有一条」这句话就作废了 ——
定价与状态必须留在基座，插件只能**建议**（`CheckoutAdvice`），由基座决定采不采纳。

### 4.4 数据

```
fnb_*  餐饮插件表     db/plugin/food     → 历史表 fnb_flyway_history
svc_*  服务业插件表   db/plugin/service  → 历史表 svc_flyway_history
```
与主库同 schema、**独立迁移历史**（`shop-inventory` 已经这么干）。
顺带解决一个天天发生的问题：**插件迁移不再与主干抢 Flyway 版本号**。

插件表可以存 `order_no`（外键方向是**插件 → 交易**）；
交易域的表里**不许出现任何插件字段**。

## 5. 为什么一期不做运行时热插拔（PF4J / 独立 ClassLoader）

想要的是「放个 jar 进 `plugins/` 就多一个行业」。代价清单：

| 要付的账 | 说明 |
|---|---|
| Flyway | 插件带表。热加载意味着**运行时执行 DDL**，失败时进程已经起着，回滚无处安放 |
| MyBatis / 事务 | mapper 扫描、`@Transactional` 代理跨 ClassLoader 要专门处理，出问题的现象是「事务静默不生效」 |
| 类型泄漏 | 契约对象在两个 ClassLoader 里是两个类，`ClassCastException` 出现在与原因毫不相干的地方 |
| 部署方式 | 现在是「版本化 jar + 切软链 + 重启」。插件目录引入第二条发布路径，而**覆盖在跑的 jar 会挂住 JVM** 这个坑已经踩过 |
| AOT / native | 已在规划 GraalVM，热插拔与 AOT 直接冲突 |

**收益呢？** 少一次重启。而重启现在是分钟级、且发版本来就要重启。

结论：**先把契约做对，加载方式留在后面换。**
只要插件只依赖 `shop-plugin-api`、只通过自动装配挂载，
将来从「编译期装」换到「运行时装」**不需要改插件一行代码** —— 这正是本 ADR 的全部价值。

三档演进路线（插件代码在三档之间完全不变）：

| 档 | 加载方式 | 什么时候上 |
|---|---|---|
| **L0（一期）** | 插件在 classpath，`@ConditionalOnProperty` + 门店能力开关决定生效 | 现在 |
| L1 | Maven profile 决定打进哪份 jar；`-Pcore-only` 剔除全部插件 | **与 L0 同期**，作为闸门（§6），不作为部署形态 |
| L2 | `plugins/` 目录 + 独立 ClassLoader | 有私有化交付需求、或插件由第三方开发时 |

## 6. 闸门 —— 没有它，这个 ADR 等于没写

1. **可剔除闸**：CI/pre-push 跑一次 `-Pcore-only` 构建，**必须能起、零售场景测试必须全绿**。
2. **依赖方向闸**：ArchUnit —— 插件包不许 import `shop-core.**.entity`、`shop-merchant.**.entity`；基座不许 import 任何插件包。
3. **行业码闸**：除 `StoreProvisionService` 外，任何类引用 `industry_code` 常量即失败。
4. **能力两态闸**：每条能力的开/关都要有用例；撤掉判定后对应用例必须变红。

## 7. 后果

**得到**：主干不长行业分支；新行业 = 新项目，主干零改动；插件可单独交付给私有化客户；插件迁移不抢版本号。

**付出**：多一层契约（插件想要新数据得先加扩展点）；跨插件复用（如叫号）要下沉到基座或建共享插件，
这件事**必须由架构决定，不许两个插件互相依赖** —— 那是插件化最常见的死法。

**不解决**：前端。B 端工作台（收银台 / 桌台图 / 排班表）是三套界面，
后端不分叉不代表前端不分叉，前端按能力条件渲染，界面清单要一起重跑。
