# ADR-011 经营主体与门店的边界（多门店）

> 2026-08-07 提案 · **2026-08-09 决策反转：做多门店（P1–P3），且作为付费能力** · P0 已落地 V42
> 相关：[交接-支付通道与行业主数据](../../交接-支付通道与行业主数据.md) §5.1 · ADR-002（分账）· ADR-005（履约）· ADR-006（积分）· ADR-009（经营范围）

## 1. 现状：一个商家 = 一个店，且门店属性散在两处

| 在 `usr_merchant`（主体） | 在 `usr_merchant_store`（门面） |
|---|---|
| `name` `logo` `address` `open_hours` `store_code` `service_scope` `service_city_code` `industry` `description` | `announcement` `open_hours` `address` `featured` |

两处都有 `address` 与 `open_hours`——**这本身是个待清理的重复**，
而它恰好暴露了问题的本质：这两个字段**天然属于门店**，被放进主体只是因为一期只有一个店。

`usr_merchant_store` 上有 `UNIQUE (merchant_no)`，所以它现在不是"多门店"，
是"主体的门面资料"。

## 2. 为什么不能顺手做

多门店会穿透四个域，每一个都有一个"归属哪一级"的问题，而且**答案不一致**：

| 问题 | 现状 | 冲突点 |
|---|---|---|
| 进件按主体还是门店？ | `usr_merchant_payment.merchant_no` | 收付通的二级商户号按**经营主体**发。多门店共用一个号，分账就分不到具体门店 |
| 订单归属哪一级？ | `ord_sub_order.merchant_no` 指主体 | 改成门店，结算、积分、评价全要跟着改 |
| 积分开关按哪一级？ | `usr_merchant.points_enabled`（四级串联的 L3） | 同一主体下两个门店能不能一个开一个不开 |
| 自提点与门店什么关系？ | `cmt_pickup_point.owner_ref` 的 `STORE` 指 `merchant_no` | 门店本身就是一种自提点，两个概念会重叠 |

## 3. 提案：主体与门店是两级，钱在主体、货与人在门店

### 3.1 边界

| 归**主体**（`usr_merchant`） | 归**门店**（`usr_store`，新） |
|---|---|
| 进件与分账账户（ADR-002） | 地址、营业时间、公告、门店码 |
| 行业、主体类型、资质 | 经营范围与覆盖社区（ADR-009） |
| 信用与毁约次数 | 库存与自提承接 |
| 积分开关与费率 | 评分（顾客评的是这家店，不是集团） |

**判据**：一件事如果**通道或税务认的是它**，归主体；如果**顾客感知的是它**，归门店。

- 分账收款方是主体——通道按营业执照发号，这是硬约束，不是我们能选的
- 顾客说「楼下那家」指的是门店——评分、公告、营业时间都跟着门店走

### 3.2 订单归属：**双写**，主体是结算键，门店是履约键

`ord_sub_order` 同时带 `merchant_no` 与 `store_no`：

- `merchant_no` 保持不变 → **结算、分账、积分链路一行都不用改**
- `store_no` 新增 → 履约、评价、门店报表用它

这是本提案里唯一"看起来冗余"的设计，但它换来的是：
多门店可以**分阶段上线**，而不是四个域一起改完才能发布。
一期只有一个店时 `store_no` 恒等于主体的默认门店，链路完全等价。

### 3.3 `usr_merchant_store` 的处置

它现在是「主体的门面」，正是未来的**默认门店**。迁移路径：

1. 建 `usr_store`，把 `usr_merchant_store` 的行**原样搬过去**，每个主体一行默认门店
2. `usr_merchant.address` / `open_hours` 标记废弃，读取改走门店（那两列本来就是重复）
3. 去掉 `UNIQUE (merchant_no)`，允许一主体多门店

第 1 步之后系统行为完全不变——这是它可以先做的原因。

## 4. 明确不做的

| 不做 | 为什么 |
|---|---|
| 门店级独立进件 | 通道按主体发号，做不到；真需要就是两个主体 |
| 门店级独立积分开关 | 积分是主体的成本结构（ADR-006 的费率补偿按主体谈），门店级会让「同一家店两个门不同价」 |
| 门店级独立费率 | 同上 |
| 跨主体的门店转移 | 转移意味着历史订单的结算方变了，那是财务事故不是功能 |

## 5. 分阶段

| 阶段 | 内容 | 可独立发布 |
|---|---|---|
| P0 | 清理 `address`/`open_hours` 的两处重复，统一读 `usr_merchant_store` | ✅ 行为不变 |
| P1 | `usr_merchant_store` → `usr_store`，每主体一行默认门店 | ✅ 行为不变 |
| P2 | `ord_sub_order.store_no` 双写，履约/评价改读它 | ✅ 单店下等价 |

**P0 已执行**（V42，收益是消掉一处真实的数据重复）。
**P1–P3 按 §6.2 执行**，见 [多门店与分享激励-需求](../../requirements/多门店与分享激励-需求.md)。

## 6. 决策

### 6.1 2026-08-07：不做（已失效）

当时的结论是「一个老板开两家店，就开两个主体」，理由是两个主体天然隔离，
**代价只是店主要切换账号**。

### 6.2 2026-08-09：反转，做多门店，且第一个免费、之后收费

**反转的不是判断，是前提。** 8-07 那个结论建立在「多门店是纯成本」上：
它只带来复杂度，不带来收入，所以让店主用 workaround 是划算的。

产品侧明确它是**付费能力**之后，这个前提不成立了：

| 8-07 的算式 | 8-09 的算式 |
|---|---|
| 收益 = 省掉切换账号的麻烦 | 收益 = 一条订阅收入 + 一个明确的付费理由 |
| 成本 = 四个域各长一层 | 成本不变 |
| → 不划算 | → 划算 |

而且「让店主开两个主体」在收费模式下不再是等价替代，是**主动放弃收入**：
他开两个主体也能经营，只是我们收不到钱。收费能力必须是他**买不到替代品**的东西。

**§3 的模型原样采用** —— 那份提案本来就是按"要做"写的，只是当时被否掉了。

**P0 已执行（V42）**：`address` 与 `open_hours` 的两处重复已消除，
门面表 `usr_merchant_store` 是唯一权威。这一步与多门店做不做无关——
它消除的是一处现在就存在、且**已经在靠双写代码维持一致**的数据重复。

同时确定（若将来做 P2/P3，按此执行）：

| # | 问题 | 结论 |
|---|---|---|
| 2 | 库存按门店独立还是主体共享 | **独立**。共享意味着 A 店卖掉的货 B 店也少了，而邻里店之间不会互相调货 |
| 3 | 评价归门店还是主体 | **门店**。顾客评的是「楼下那家」，三家店评分混成一个，好店会被差店拖下去 |
