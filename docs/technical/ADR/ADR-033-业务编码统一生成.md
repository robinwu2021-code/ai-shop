# ADR-033 业务编码统一生成：日期 + 随机，收进 BizKey 一处

状态：已决策（2026-10-09）
关联：[TDD-业务编码统一生成](../TDD-业务编码统一生成.md)
背景来源：用户 2026-10-09「优化订单编号逻辑，梳理其他业务编码，整合到一个工具统一处理」

## 决策

所有业务码走一个生成器（`BizKey.next(prefix)`），格式统一为：

```
<前缀> + yyMMdd(6) + Crockford base32 随机段(10)
例：SO261009A7K3M9QF2X   （前缀 SO + 261009 + 10 位随机）
```

- **日期段 yyMMdd**：运营可直接读出哪天的单（订单哪天发生本不敏感）。
- **随机段 10 位**：50 bit，从 `SecureRandom` 取。替掉原来的「每 JVM 递增 seq」——
  那是单量泄露源，也是多实例碰撞源。
- **Crockford base32**（去掉 I/L/O/U，避免与 1/0 混淆）：人工抄写/电话报号不易错。

## 为什么这样，不那样

### 替掉原来的 `yyyyMMddHHmmss(14)+seq(4,每JVM mod 10000)+rand(3)`

四个毛病同时存在：
1. **多实例碰撞**：seq 是**每 JVM 一个 AtomicInteger**，而生产有 `app` + `worker`
   两个 @Profile 实例。同一秒两实例可生成同一 seq，只靠 3 位随机（1/1000）兜底。
2. **可枚举**：秒级时间戳 + 递增 seq 明摆着，竞品能估单量、能爬邻号。
3. **长**：前缀 + 21 = 23 字符。
4. 到秒的时间戳其实没用——排序有 `created_at`，没人靠单号排序。

新格式：无共享状态 → 天然多实例安全；随机段 → 枚举不出；前缀+16 → 短 4-5 位；
日期段 → 运营可读。**「带日期」与「不可枚举」不冲突**：保留日期、只把泄露量的那段换成随机。

### 为什么不用雪花 / ULID

- **雪花**：要 worker-id 协调（ZooKeeper/配置），运维多一层；且是毫秒内递增 = 可枚举；
  数字串无可读日期段。这套部署很简单，不想为它引协调组件。
- **ULID**：26 字符（比现在还长），时间有序 = 单调可枚举。与「更短」「不可枚举」都拧着。

### 碰撞兜底：随机 + DB 唯一索引 + 重试

10 位 = 50 bit，同日同前缀生日界 ≈ 3300 万条才有较明显概率。现实量级远不到。
而**订单/子单/支付/结算等高量类型都有唯一索引**（`uk_order_no` 等），
万一撞上，insert 抛唯一冲突 → 调用方重试取新号。随机足够稀 + DB 是最终保证，
生成本身仍是纯内存、无 DB 往返。

### 前缀必须唯一（这次一并修）

原 BizKey 有 **5 对前缀撞车**：`ST`(STAFF/STORE) `CM`(CAMPAIGN/CHANNEL_MESSAGE)
`PP`(PICKUP_POINT/POINTS_POOL) `SL`(CONTENT_SLOT/STAFF_LOG) `MT`(MEMBER_TAG/MATERIAL)。
而前缀**真的被反解**（`MpStoreController` 的 `startsWith("ST")`）。靠**改前缀**（STAFF `ST`→`STF` 等）消除根因 ——
前缀一旦全唯一，`startsWith` 的歧义就不存在了，parser 本身不用动（它的入参只会是商家号/门店号，两者前缀互斥）。
新增一道测试期守卫 `BizKeyTest#任意两个前缀常量不相等`：**任意两个前缀常量不许相等**。

## 明确不做

- **不加分隔符**（`SO-261009-...`）：保「更短」与格式干净；前缀歧义靠**改前缀保唯一**解决，不靠分隔符、也不靠改格式。
- **不改存量数据**：旧码（旧格式/旧前缀）照旧有效、照旧可查。新码用新格式。两者共存，直到自然淘汰。
- **不做全局定长前缀**：那要改所有前缀，代价远超收益。
- **不动 `startsWith` 反解的 parser**：前缀全唯一后它们在各自输入域里判定正确；强行改成「精确前缀表」是额外耦合，收益为零。
