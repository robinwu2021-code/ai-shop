# ADR-011 商家资金走自营供应商模式，分账作为将来的第二条轨

状态：**已决策（2026-09-29，用户确认）**
关联：[ADR-002 结算走微信支付分账](./ADR-002-结算走微信支付分账.md) ·
[PRD-商家资金到账与对账](../../requirements/PRD-商家资金到账与对账.md) §5 待确认第 2 条 ·
[TDD-供应商结算与双轨资金](../TDD-供应商结算与双轨资金.md)

---

## 1. 决策

1. **商家按平台供应商的模式执行**：平台是销售主体，商家是供货方，
   平台付给商家的钱是**采购货款**，不是资金清算。
2. **出款走银行卡转账**，周期 **7 天或 30 天一次**（对应已有的
   `SettleCycles.WEEKLY` / `MONTHLY`）。
3. **双轨并存**：自营（本 ADR）与第三方分账（ADR-002）**同时支持**，
   按门店的 `business_mode` 分流。分账接通前，第三方轨道保持桩实现。
4. **不做商家向平台提现**：ADR-002 §2 的二清判断不变，见 §3。

---

## 2. 为什么这是合规的，而"提现"不是

两者的资金路径看起来相似 —— 钱从平台账户到商家银行卡 —— 但**法律关系完全不同**：

| | 商家提现（不可做） | 供应商付款（本决策） |
|---|---|---|
| 平台的角色 | 资金保管者 / 中介 | **买方** |
| 这笔钱是什么 | 商家的钱，平台代管后归还 | **平台欠供应商的货款** |
| 法律依据 | 无 —— 需要支付牌照 | 采购合同 |
| 凭证 | 无 | **进项发票**（供应商开给平台） |
| 商品的责任人 | 商家 | **平台**（平台是销售主体） |

关键在最后一行：**这不是一个记账口径的选择，而是真的要承担销售主体的责任。**
平台对商品质量、售后、消费者权益负责，因此才有资格说"这批货是我采购的"。
拿了这个身份却不担这个责任，形式上的合规是撑不住的。

ADR-002 §2 排除的是"平台把商家的钱代管后还给他"。本决策下平台付的是自己的钱
（购货款），不存在代管，**因此不构成二次清算**。

> ⚠️ 这个结论成立的前提是**业务上真的按自营跑**：平台签采购合同、收进项票、
> 对商品负责、在 C 端以销售主体身份披露。只改结算口径而业务照旧撮合，
> 那还是二清，只是换了个名字。**这一条不是技术能保证的**，要靠商务与法务把住。

---

## 3. 与 ADR-002 的关系：不是推翻，是补上被卡住的那一半

ADR-002 选分账是对的，今天依然对。它卡住的原因写在
PRD §3.1：**分账参数的书面口径没拿到（B7）**，这是商务前置，不是技术问题。

本 ADR 不改变分账的地位，只是回答 PRD §5 待确认第 2 条
"在分账接通之前，第三方商家的货款怎么办"—— 三个选项里选**第二个**：
走自营代销形态，用应付账款那条已经通的路。

**两条轨道的分工：**

| | 自营轨（本 ADR） | 第三方轨（ADR-002） |
|---|---|---|
| `business_mode` | `SELF_OPERATED` | `THIRD_PARTY` |
| 谁是销售主体 | 平台 | 商家 |
| 钱怎么给 | 平台银行转账（周期性） | 微信分账，直接进商家商户号 |
| 凭证 | 进项发票（供应商 → 平台） | 无需进项票 |
| 状态机 | `PENDING_RECON → CONFIRMED → PAID` | `PENDING → SPLITTABLE → SPLIT → SPLIT_CONFIRMED` |
| 现状 | 骨架已建（V23），缺收款账户与付款单 | 网关是桩，等 B7 |

`business_mode` **挂在门店上**（V23 的决定），所以同一主体下旗舰店自营、
加盟店第三方是可表达的 —— 双轨不是过渡期的临时状态，是长期形态。

---

## 4. 这个决策带来的三件必须做的事

1. **收款账户要落库。** 今天进件的结算账号是"只在本次调用中存在，不落库"
   （`PayApplymentGateway.SubmitCommand` 的注释），库里只有掩码。
   而银行转账必须有完整账号 —— 这是本决策**唯一真正的新建**，且是敏感数据，
   见 TDD §2.3 的加密与权限设计。
2. **进项票是硬约束，不是流程装饰。** V23 已经写明：
   "付得出去和能入账是两件事 —— 对私转账银行不拦，但没有发票这笔支出在税上不存在，
   平台按全额确认收入却零成本。" 无票供应商的处理要有明确口径。
3. **C 端披露要跟上。** 自营模式下商品的销售主体是平台，
   订单页不能再显示"本单由 XX 商家提供并收款"（那是分账场景的披露要求，ADR-002 §5）。
   两条轨道的披露文案不同，**由 `business_mode` 决定**。

## 4.5 门店与商户的统一模式（2026-09-29 补充）

**定位：按京东自营旗舰店的形态跑。** 平台统一收款、统一结算；
商家负责店铺运营，法律关系上是供应商；平台也可以代运营。
将来平台拿到资质，再支持多商户。

### 这个定位落到代码上，就是两个字段的一组取值

| 字段 | 取值 | 含义 | 现状 |
|---|---|---|---|
| `mch_store.business_mode` | `SELF_OPERATED` | 平台是销售主体 | ✅ V23 的**默认值**就是它 |
| `mch_entity.funds_mode` | `AGGREGATED` | 钱进平台商户号 | ✅ `SelfOperatedServiceImpl` 建店时就这么设 |

**两个字段都已经存在，而且默认组合正是这个模式。** 不需要新建模型。

### 由此得到一个此前没被说破的结论：这个模式不需要微信支付进件

进件（`mch_payment_merchant` / `ApplymentPollJob`）的目的是**拿二级商户号**，
好让分账时钱能划给商家。而聚合模式下钱进的是平台商户号，商家不收款——
`payMerchantNo` 在全链路上只有一个消费者：`SettleServiceImpl` 里执行分账那一行。

所以一期**整条进件链路可以不走**：不要法人身份证、不要经营场景报备、
不要把结算账户提交给通道、不要轮询进件状态。

⚠️ **但进件代码不删。** 它是第三方轨道的入口，而那条轨道是
「将来平台有资质就支持多商户」的落点。删了等于把将来的路一起拆了。
默认不走 ≠ 不存在，见 §5。

### 那还需要商家提供什么

**两样，一样都不能少：**

1. **营业执照** —— 两个用途：合规留档，以及**三流一致的户名来源**。
   付款时收款账户的户名必须等于执照主体名（V358 的硬校验），
   没有执照就无法判断户名对不对。
2. **收款银行账号** —— 线下结算转账的依据（V358 已落地）。

其余的（类目、服务范围、行业、资质图）是**经营配置不是准入材料**，
可以开店之后按需要的时机再要，见 [TDD-入驻分阶段与进件简化](../TDD-入驻分阶段与进件简化.md)。

## 5. 明确不做

- **不做平台代付到商家银行卡的"提现"形态**（§2）。
- **不做微信「商家转账」当结算通道**：它只能到微信零钱、到不了银行卡，
  且用于货款结算时平台仍在支配资金，没有解决问题只是换了通道。
- **不拆表**：两条轨道共用 `stl_bill`，V23 已经论证过（拆开会让对账要 union 两张表）。
- **不自动划转**：系统只生成付款单并登记凭证，**实际转账由财务在网银执行**。
  让业务系统去动公司对公账户是财务内控问题，不是技术能力问题（V23 原话）。

## 6. 待确认

1. **无票供应商怎么办？** 小微供应商开不出票是常态。三个方向：
   代开（平台或园区代开）/ 只做有票供应商 / 接受无票并承担税负。**商务与财务决定。**
2. **自营的商品责任怎么落地？** 采购合同模板、质量责任划分、售后主体。
3. **周期定 7 天还是 30 天？** 建议按供应商分档配置而不是全局一个值 ——
   `SettleCycles` 已经支持按主体配。

---

## 7. 补充决议（2026-10-09）

§6 第 3 条「周期定 7 天还是 30 天」保持按主体配（`SettleCycles`）。另定：

- **放款单位 = 账期批次 × 收款号**，一笔转账一条 `stl_payout` 记录；凭证号回填在它上面，不在结算单上。
- **放款仍由运营触发**（§5「不自动划转」不变），银行 API 只预留通道字段。
- `stl_withdraw` 退役（§5 第 1 条的收尾）。

落地见 [TDD-账期推进与放款记录](../TDD-账期推进与放款记录.md)。
