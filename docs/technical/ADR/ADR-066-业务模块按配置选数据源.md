# ADR-066 业务模块按配置选数据源，库之间不共事务

状态：**提案，待用户确认**（2026-11-26）
关联：[TDD-多数据源与发票打印对齐新库](../TDD-多数据源与发票打印对齐新库.md) ·

[ADR-061 三端认证与权限各自一套及权限库独立](./ADR-061-三端认证与权限各自一套及权限库独立.md) ·
数据库设计方案（14 个库、376 张表，分支 `docs/db-split-plan`）

## 背景

库表设计把正式库整理成 14 个按业务域划分的库。代码仍是“一个主库 + 几个手写的例外”：
库存、任务、报表各有一份手写的独立数据源配置；支付、密钥是“同一个库、单独的连接池和事务管理器”；
网关三端是“配了用自己的库，不配回主库”。每加一个库就要再抄一份配置类，写法各不相同。
用户要求：一个进程同时提供三端，各模块在这个进程里连各自的库，由配置决定。

## 决策

1. **数据源有名字，模块绑定到名字。** `shop.datasources.<名字>.*` 定义一个数据源（地址、账号、连接池）；
   `shop.modules.<模块>.datasource=<名字>` 把模块绑上去。不写绑定就是主库 `spring.datasource`。
2. **每个模块有三个固定名字的句柄**：`<模块>DataSource`、`<模块>SqlSessionFactory`、`<模块>TxManager`。
   没绑定时它们是主库那三个 bean 的别名；绑定后指向具名数据源的 bean。业务代码只认句柄，不认库。
3. **绑到同一个名字的模块共用连接池和事务管理器**，可以在同一个事务里；绑到不同名字的模块之间没有共同事务。
   不引入分布式事务（XA、Seata）。
4. **模块内的事务一律点名自己的句柄**（`@Transactional(transactionManager = "invoiceTxManager")`），
   Mapper 由模块自己的扫描绑到自己的工厂，并从全局扫描里排除。两头都有守卫测试。
5. **跨库协作只有三种写法**：调对方的接口（各自提交）；本库提交之后再发事件；靠业务唯一键让重复执行无害。
   每一处原来同事务、切库后不同事务的地方，都要在 TDD 里写明先后顺序与失败后怎么恢复。
6. 已有的库存、任务、报表、支付、密钥的数据源配置**这次不动**，以后各模块对齐新库时再迁到这套写法。

## 理由与被否掉的方案

| 方案 | 结论 |
|---|---|
| A. 每个库再抄一份 `XxxDataSourceConfig`（现在 pay、secret 的写法） | ❌ 14 个库要写十几份，每份都可能漏拦截器、逻辑删除、填充器；“不配就用主库”要各写一遍 |
| B. 动态路由数据源（一个 `AbstractRoutingDataSource`，按线程变量切库） | ❌ 一个事务只能在一个库上，切换靠线程变量，漏设一次就静默写错库；本仓库已有“第二个数据源读写全空”的事故记录 |
| C. 每个模块一个数据源（不设名字这一层） | ❌ 发票、打印、通知都在平台服务库，各开一个池既浪费连接，又让同库的模块失去同事务 |
| D. 具名数据源 + 模块绑定 + 固定句柄 | ✅ 不配时行为与现在逐字节一样；同库模块自动同事务；加库只加配置 |

## 约束

- 任何 `@Bean` 不得返回 `Flyway`（已有守卫）；模块数据源的建表方式另定，见 TDD §2.6。
- 绑定了非主库的模块，不得在自己的事务里写主库的表（含 `sys_outbox`），也不得指望主库的行锁。
- 数据域拦截器、分页、乐观锁、逻辑删除、公共字段填充在每个数据源的工厂上都要装，行为与主库工厂一致。

## 后果

- 模块之间原来靠“同一个事务”得到的一致性，切库后要改成“各自提交 + 可重入”。这是这件事真正的成本，不在配置上。
- 撤回代价：框架本身可撤（解除绑定即回到主库）；但模块一旦真的写进新库，回主库就是一次数据迁移。
- 守卫增加：模块事务点名规则、Mapper 包归属规则、解除绑定后的装配测试。
