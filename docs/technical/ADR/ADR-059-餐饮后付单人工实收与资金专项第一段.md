# ADR-059 餐饮后付单人工实收与资金专项第一段

状态：已接受（2026-11-12，随 [TDD-餐饮柜台后付结账](../TDD-餐饮柜台后付结账.md) 一起确认）
日期：2026-11-12

## 背景

员工后付的堂食账单今天付不清：每轮下单在核心建一张 `POSTPAY / WAIT_PAY` 订单，核心没有任何受权入口把它变成已付；平台外部记账只按结算号记款，不改订单；餐饮也从不关单。

`TDD-餐饮订单结账-完整开发计划.md` §2.3 曾把「支付及资金专项」整体摘除延期（`:527`、`:578`）。

## 决定

1. **恢复资金专项的第一段**：柜台后付整桌结账（现金与外部刷卡机，经外部记账），收齐后关单、释放桌台。资金专项的其余部分（扫码、储值、找零以外的混合支付、现金交班、退款资金执行）仍按原计划延期。
2. **收齐后核心后付单推到 PAID，来源标人工实收**（来源记在核心实收表 `ord_postpay_receipt.provenance='POSTPAY_RECEIPT'`，订单行沿用线下确认的 `offline_confirmed_by/at`；不改 `ord_order` 表结构），沿用 ADR-050 美业人工实收的做法：
   - 由核心自己核验外部记账（门店、结算号、未作废、币种、未被重复使用、合计不少于应收、多收只能是现金找零）；
   - 一张结算单覆盖的所有后付单在核心**一个事务**里推到 PAID；
   - **不发通用「订单已支付」事件**：钱没有经过平台，不进平台结算与分账；只发专用的 `POSTPAY_RECEIPT_RECORDED`。
   - **按表读状态的出账路径同样排除**：资金巡检与出账以 `ord_postpay_receipt_root` 为准跳过这些单（只靠不发事件挡不住每小时的「已付缺结算单」补账）。
3. **整桌一次结账**（需求矩阵 FNB-F03，原列 P3）提前到本段。

## 后果

- 后付账单从此能闭环；日结不再因为已结清的后付批次报应收异常。
- 核心订单出现第二种「人工实收」来源，凡读 PAID 状态的地方都要能接受它。实施时已核对：出账与资金巡检已排除；报表纠偏不重算、售后退款不可用两处列为后续（TDD §6 偏差 6）。
- 已推到 PAID 的单不能由餐饮撤回；退款走后续的资金退款段。
- 新增一张核心实收表；平台迁移编号与推送分支需在合并时核对。

## 不选的方案

- **保持 WAIT_PAY，只在餐饮侧标结清**：日结会一直报应收异常，报表与核心订单状态不一致。
- **放开行业收款的先付限制，让后付单走线上支付**：现金与外部刷卡没有线上支付单，仍需要人工确认这条路。
- **复用美业人工实收表**：那张表绑着库存处置阶段与柜台单来源，语义不同。
