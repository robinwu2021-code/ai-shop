# ADR 061 三端认证与权限各自一套及权限库独立

状态：已接受（用户 2026-11-18 确认定稿）；尚未实现。
关联：[TDD-网关层与统一权限-五层架构对齐](../TDD-网关层与统一权限-五层架构对齐.md) §2.5、§2.15；配套 [ADR-060](ADR-060-网关层独立模块与鉴权不进路由网关.md)。

## 背景

三端的令牌前缀与会话表已经分开，但其余并没有：

- 会话存储用 Redis、Ehcache、内存三种形态时是单池，三端共用一个实例和同一个键前缀 `shop:session:`；全进程只有一个 Redis 连接配置。
- 账号、角色、菜单表与业务表同库，业务模块直接读它们：引用三张账号表的源文件有 78 个，这些表上有 9 行 join。
- C 端的 `usr_account` 把登录标识和业务资料放在同一张表里。

用户要求认证和权限每端一套、互不影响，令牌及其依赖的 Redis 等都要分开，用户、角色、资源/菜单要有独立的数据库。

## 决定

1. **每端一套：配置、令牌存储、Redis、权限库、本地缓存、健康检查。** 配置块为 `shop.gateway.mp` / `.biz` / `.ops`。网关模块按端自己建 Redis 连接与数据源，不使用全局的那一份。
2. **严格模式** `shop.gateway.isolation: strict` 下，三端的 Redis（地址加库号）或数据源指向同一处时启动失败。本机开发可用 `relaxed` 共用。
3. **一端的 Redis 或权限库不可用，只影响该端。**
4. **权限库一套模型、一套代码、三个库。** 现有表名不改。这些表只有网关模块的权限包能读写；三端的表之间、它们与业务表之间不做 join、不建外键，只存编号。业务层要用户信息走用户目录接口。
5. **搬库顺序：运营端 → B 端 → C 端。** 运营端最干净；B 端账号挂在经营主体上，要先改写 4 个文件里的 join；C 端要先把 `usr_account` 拆成登录标识（进权限库）与业务资料（留业务库）。
6. **C 端不建角色和资源表**，等有 C 端角色需求再加。B 端新增资源表。
7. **跨库的写入不靠同一个事务：** 先在权限库建账号（按编号幂等），再写业务库；失败后重试同一个编号。
8. **网关调微服务的进程凭据与签名密钥不按端分，按服务分。** 它证明的是调用方是 ai-shop，与哪一端无关。

## 被否的方案

| 方案 | 为什么不选 |
|---|---|
| 三端用户合成一张表 | 三端身份隔离是既有的硬要求（[TDD-统一鉴权与会话外置](../TDD-统一鉴权与会话外置.md) R1） |
| 网关层整体一个库、三端分表 | 用户明确要求每端一套、互不影响；一个库时一端的故障或连接耗尽会波及另外两端 |
| C 端把整张 `usr_account` 搬进权限库 | 表里有昵称、社区、地址等业务资料，由业务流程读写；搬过去等于让权限库持有业务数据 |
| 用分布式事务保证「建账号 + 建业务数据」原子 | 仓库的既有约定是不做分布式事务；账号按编号幂等、可重试已经够用 |

## 取舍和影响

- **不可逆：** 每一端搬库都是一次数据搬迁，各自要有回退方案。旧表保留一个发布周期后再删。
- 入驻建店、邀请店员、账号注销（ADR-054）这几个流程原来在一个事务里完成，搬库后要改成两步；实现前逐个清点。
- 业务代码改走目录接口后，列表页要用批量查询，不能逐行查。
- 本机开发默认 `relaxed`，三端落回同一个库和同一个 Redis，不增加起环境的成本。
- 166 环境的应用库账号没有建库建表权限，三次搬库的 DDL 要在交接里标出，由 root 先执行。
- 每端一份的缓存让「改权限后多久生效」变成按端回答：本实例立即，其他实例最长为该端快照的有效期（默认 60 秒）。

对既有决策的影响：

- 本决策实现并扩展了 [TDD-统一鉴权与会话外置](../TDD-统一鉴权与会话外置.md) §11「拆库就绪」。那份文档判断 C 端最容易先拆，前提是整张 `usr_account` 一起搬；本决策把 C 端拆成两张表，因此排到最后。
- ADR-040「人员主档与账号权限分开」不变：搬进权限库的是账号与权限，人员主档留在业务库。
