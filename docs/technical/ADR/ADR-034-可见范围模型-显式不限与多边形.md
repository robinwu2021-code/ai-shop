# ADR-034 可见范围模型：显式「不限」、多边形按网格入索引、去掉「开放小区」锚点

状态：已决策（2026-10-10，用户确认结论；实施计划见 TDD §2.14）
关联：[TDD-可见范围分级匹配与多边形](../TDD-可见范围分级匹配与多边形.md) · [ADR-013 服务区域](ADR-013-服务区域.md) · [ADR-031 商品归属门店](ADR-031-商品归属门店.md) · [ADR-033 业务编码统一生成](ADR-033-业务编码统一生成.md)
背景来源：用户 2026-10-10「有的门店城市可见、有的省市可见、有的某一地图范围可见，按消费者当前定位筛」；起因是虹选粮油框了嘉逸花园却全平台可见。

## 背景

门店「送不送得到」只有一个判定 `ReachRule.covers`，目录、推荐、详情送达、下单落店全走它。现有模型三处结构性问题：

1. **「不限区域」是隐式的**：INCLUDE 为空 + 开了快递/自送 = 全平台可见。INCLUDE 为空的成因有四种（框写到别家店 / 没物化 / 框成 EXCLUDE / 门店级与主体级错位），没有一种会报错。虹选粮油的故障就是这一类。
2. **匹配以「开放小区」为锚**：区级匹配和不限分支都要求 `c.open()`，区县查询先找区里的开放小区。消费者所在区没有运营开的小区就看不到任何商家。
3. **没有几何**：范围只能是小区号或行政区划前缀，表达不了「我只送地图上这一片」。每次请求还要把全平台门店的范围整表拉进内存逐店判，零缓存。

## 决策

1. **「不限」改为显式范围项** `level=UNLIMITED`，商家必须主动选；删掉隐式分支；**没框任何范围的店对谁都不可见**。存量「无 ACTIVE INCLUDE + 实际有快递/自送全部路」的门店由 Java 迁移（复刻旧 `routes()` 兜底语义）自动补一条 UNLIMITED，行为零变化、从此看得见改得掉。
2. **行政分级与聚落用「祖先码 ∈ 范围码」的集合成员判定**：消费者区划码按 2/4/6/9/12 位截出祖先集，范围项 `ref_code IN (祖先集)`；小区/楼栋 `ref_code IN (communityNo, parentNo)`。五级一条规则，走现有索引 `idx_service_area_ref(level, ref_code)`。
3. **多边形用 S2 网格离散后也走同一种成员判定**：保存时 `S2RegionCoverer` 把多边形算成覆盖 cell 集（区分内部/边界），写进派生表 `mch_service_area_cell`；查询时消费者坐标 → 各级父 cell token → `cell_id IN (...)`。**边界 cell 才用 JTS `covers()` 精判**（含边界）。几何库选纯 Java 的 JTS + S2（无 JNI）。
4. **匹配不再读 `open`**：消费者画像 = {祖先码, 聚落号, 父聚落号, cell tokens, 坐标}；纯定位也能匹配省市区与多边形。`open` 列与运营用法不删。
5. **排除判定 fail-closed**：门店带行政级排除而消费者无区划码、或带多边形排除而消费者无坐标 → 该店不可见（不能证明「不在排除里」就不放行）。
6. 范围仍是**门店级**（V381），商品继承；**所有粒度自助生效**（2026-08-24 起已无送审，省级同理）。
7. **性能结构**：门店元数据（履约路、子集、是否不限、排除维度）做进程内快照（Caffeine，写路径 `AfterCommit` 失效 + TTL 兜底）；范围/网格命中走 2 条索引点查；`allServing()` 整表加载删除。

## 否决的方案与理由

| 方案 | 为什么不 |
|---|---|
| **MySQL 空间类型 + `ST_Contains`** | 测试基础设施（H2 无 JTS）不是决策依据——可对本地/线上 MySQL 跑；真正的代价是：仓库迁移首次出现 H2/MySQL **方言分叉**（`GEOMETRY NOT NULL SRID 4326` H2 不认），且空间 SQL 在 H2 上可能连解析都过不去而炸掉整条 pre-push 闸门。S2 网格把几何变成普通 `IN`，两边 DDL 与查询完全一致，不需要这些。 |
| **Elasticsearch（geo_shape / percolator）** | 几何能力过硬但规模不匹配（几百~几千家店）；生产单机 cgroup 限额、MySQL 曾被 OOM，再加一个 JVM 堆几 GB 的 ES 不合适；MySQL→ES 同步是最终一致，可见性是强一致判定；规则会分成 ES DSL + Java 两份。**商品全文搜索迁 ES 时**（代码里已预留）再把范围一并索引。 |
| **一条聚合 SQL（反连接 + GROUP_CONCAT + MAX(布尔)）** | 性能收益与两条平铺点查相同，却多付一条手写聚合 SQL 的方言差（`GROUP_CONCAT`/布尔聚合 H2≠MySQL）与可读性代价，且把集合运算写进 SQL、规则拆两处。 |
| **预计算「门店×覆盖小区」展开表** | 即被删掉的 `prd_community_pool` 变体：两万多小区 × 上千店行数爆炸且漂移；多边形对任意坐标无法展开。 |
| **Redis GEOSEARCH / Redis Query Engine GEOSHAPE / Tile38** | 核心 GEOSEARCH 不支持多边形；GEOSHAPE 要换 Redis Stack 模块并再引一份副本；Tile38 是独立地理中间件，为「哪些店覆盖这个地址」过重。 |
| **Geohash** | 矩形网格纬度越高越扭、边界碎，围栏贴合差；S2/H3 才是多边形覆盖的正解。H3 Java 绑定走 JNI 要带原生库，S2 纯 Java 更省事。 |
| **单品级范围覆盖 / 半径圆 / 多边形审核** | 需求已明确门店级、任意多边形、自助生效。 |

## 为什么「没框范围 = 不可见」而不是「= 全平台」

隐式全平台让配置错位静默放大（空集合变成最大集合）。改成不可见后，错位的后果是「商家自己看不到订单」——会被发现、会来问、范围页还会醒目提示；而全平台可见的后果是消费者买了送不到，谁都不会主动发现。宁可少卖不可错卖，与「自提清空范围要在写入口拦」是同一条原则。

## 后果

- **正向**：范围语义一处、显式、可解释；消费者无开放小区也能看到范围覆盖的商家；商家能画任意配送边界；行政 + 聚落 + 多边形 + 排除 = **一种索引、一种查询形状**，MySQL/H2/内存三处完全一致；每请求从整表重载变成几次索引点查；虹选粮油这一类故障从根上消失。
- **代价**：两个纯 Java 依赖（`org.locationtech.jts:jts-core`、`com.google.geometry:s2-geometry`，`mvn -o` 要先把它们灌进本机与服务器的 `~/.m2`）；一张派生表与一次存量迁移（有判据：迁移前后全平台可见门店集合必须相等）；一批依赖隐式不限的旧测试要改成显式；B 端多一个画图页（原生 `<map>` 要独立页承载）。
- **不可逆点**：删隐式分支后不能回退到「空集合=全平台」，但 UNLIMITED 行可随时增删；迁移全是加列/加表/加行，旧 jar 读到未知 level 的行按「不命中」处理，**回滚只需换回旧 jar**。
