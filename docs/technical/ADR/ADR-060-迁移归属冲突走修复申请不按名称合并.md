# ADR-060 迁移归属冲突走修复申请，不按名称合并

状态：已接受（2026-11-16，用户「按建议确认并开发」）
日期：2026-11-16
关联：[TDD-商户迁移同步与渠道关联](../TDD-商户迁移同步与渠道关联.md) N3、N5 · 交接 [oscar-channel-sync-2026-11-16](../../handoff/oscar-channel-sync-2026-11-16/README.md) §3.2 · [功能矩阵](../../requirements/运营端-账户商户门店渠道-功能矩阵.md) §六 D4

## 背景

把账号、经营主体、门店和渠道商户迁入 nearshop 时，会遇到「已有记录，但挂在别的主体上」。首户即是：支付商户 `PM13A13B737D7C4A57`（創勢科技股份有限公司）的来源仍关联旧主体 `M261106BF7GK8052W`，而 Oscar 的经营主体是 `M261113Y3QW5XKEFW`；其下蓝新账户 `PMD3A0C5A8C8FB4F92` 已核验可收款。

可选做法有三：按名称自动合并到新主体；在普通保存接口里改关联；或建一个独立的修复申请，经审批后执行。

前两种都会在没有审批、没有快照的情况下改变资金相关的归属，且不可逆——改错后无法判断「当初挂在谁名下」，也可能顺带把 MID 和其他门店一起带走。

## 决策

1. **迁移脚本只认判重键，不按名称合并。** 查到多条或归属不一致，一律报冲突并停该项。
2. **一个经营主体至多一个支付商户。** `merchant-creations` 建前按主体查（代建回执与来源关联，排除已关闭商户），已有即 `STATE_CONFLICT`，说明里带出已有 `merchantNo`（TDD Q3 已确认）。
3. **历史归属只能经修复申请改。** near-pay 新增资源 `source-association-repair-requests`：申请须显式列出商户、原主体、目标主体、受影响门店和期望版本；审批人不得是申请人（2026-11-17 用户改为：`near-pay.approval.single-operator` 打开时与其他审批类型一致，允许同一人提交并审批，审计照记；开关关闭时仍拒绝）；执行时逐项比对前快照，任一不符整单拒绝；单事务执行，前后快照入库。
4. **修复范围不含渠道账户与 MID。** 渠道账户随支付商户归属走，不单独转移；其他门店不随之迁移（与 D4「门店归属迁移先不做」一致）；不给任何账号授予额外权限。
5. **修复是 `external_entity_id` 不可变规则的唯一例外。** 执行时原行原号把来源关联改到目标主体（`source_revision` 归 0），不插新行、不删行；前后快照、审批号与审计永久保留。修复后旧主体不应再作为来源同步，否则会被当作新主体另建商户。
6. **普通保存接口不承担改归属。** 现有资料维护、代建、来源核验接口保持原义。

## 后果

- 迁移脚本可重跑：冲突项停住，其余项继续，修复审批后重跑即可接上。
- 多一个资源和一张表，多一道审批；首户执行需要等审批人。
- 历史可查：修复前后快照永久保留，审计可回答「何时、谁、凭什么改了归属」。
