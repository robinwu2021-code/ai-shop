# ADR-015 三端会话外置与令牌分池

状态：**已接受**（部分实施） · 创建 2026-08-27

## 1. 背景

会话此前存在**进程本地磁盘**（Ehcache 持久化，`SHOP_TOKEN_STORE=ehcache`）。
三个后果：

1. **多副本部署被锁死** —— 同一个人被负载均衡打到另一台就是未登录，而这个症状是间歇性的
2. **`revokeUser` 只覆盖本进程** —— 按下「停用」的人以为立刻生效了，另一台上那个人照常操作
3. **持久化目录关不干净就被整个删掉**（2026-08-24 线上重现过一次，表现是全员掉线）

同时，B 端与 C 端**共用 `ctk_` 令牌池**，而 `LoginUser.userNo` 这一个字段里
C 端塞 `usr_account.user_no`、B 端塞 `mch_account.mch_account_no` ——
生产上号段恰好不撞，但那是约定不是结构保证。

---

## 2. 决策

### 2.1 会话进数据库 + 本地两级缓存

**不是 Redis**：服务器上没有 Redis，而这套方案不需要新中间件。
接口（`TokenStore`）不变，将来上 Redis 改一行配置。

**不是 JWT**：这套鉴权的权限新鲜度与停用生效都依赖「能撤销」，
而 JWT 签发后在过期前撤不掉 —— 除非再维护一张黑名单表，那比会话表更难对账。
**能撤销是硬需求，不是可选项。**

### 2.2 会话表只有八列

`token_hash / user_no / issued_at / expires_at / last_seen_at / revoked_at / revoke_reason / id`

**不存 `nickname` / `roles` / `perms` / `tenant_no` / `scope`** ——
它们的变动频率高于会话生命期（会话活 30 天，角色可能今天改）。
存进去就有第二个真源，而过期的那一份**不会报错，只会让人拥有他昨天的权限**。
身份改为每请求从用户表现读现算（带一层短 TTL 缓存）。

副作用是好的：**改角色、改数据域、改昵称下一个请求就生效，不必踢人**。
`revokeUser` 因此收窄回它本来的语义：登出 / 强制下线 / 停用。

### 2.3 三端各一个令牌池、各一套表

`ctk_`/`usr_session` · `btk_`/`mch_session` · `otk_`/`ops_session`，
外加三张登录日志表。**一套代码三次装配**，表名与各种时限是参数（`SessionProfile`）。

### 2.4 C 端轻量化靠两个旋钮分开拧

- `cacheTtl` 大 → 回源少（**轻**）
- `revokePoll` 小 → 踢人快（**安全**）

两者互不影响。把它们当成一个旋钮（「缓存久 = 踢人慢」）是最常见的误解，
而按那个误解设计，C 端只能在「贵」和「不安全」之间二选一。

### 2.5 本地缓存统一 Ehcache，**堆内、绝不落盘**

缓存的东西权威都在库里，丢了只是回源查一次。
给它加 disk 层想「重启后还热着」，等于把 2026-08-24 那次事故装回来 ——
而且这次连数据都不是它的，纯亏。

**判据一句话：库里有权威副本吗？** 有 → 可以缓存；
没有、它自己就是权威（验证码、重置令牌、限流计数）→ **绝对不能放**。

## 3. 代价与已知未决

| | |
|---|---|
| 每请求多一次身份还原 | 用两级缓存吸收；C 端稳态命中率接近 1 |
| shop-app 多一个只读数据源 | 换来「worker/运营页面在 worker 挂掉时仍能看历史」 |
| 切换当天**全员重新登录** | 分三批（运营端 → B 端 → C 端），挑低峰 |
| **多实例仍未解锁** | 见下 |

### 3.1 会话外置解锁的是多实例的「可能」，不是「可以」

认证链路上还有四处**进程内状态**，多实例后全部失真且不报错：
`InMemoryRateLimiter`（限流上限变 N 倍）、`OtpStore`（A 发码 B 校验 → 验证码无效）、
`CaptchaService`、`PasswordResetTokens`。症状都是**间歇性的**，取决于负载均衡打到哪台。

真要跑两个实例，这四处必须先解决；而且上面只是粗扫，正式上多实例前需要一次专门审计。

### 3.2 B 端换池卡在一个产品判断

入驻接口是 `/biz/merchant/apply`，而调它的人**按定义还不是商家**。
`/biz/**` 一律要求 `MERCHANT` 会让没开店的人连入驻页都打不开 ——
那正是「登录即注册」承诺的那一屏。四条路与建议见 TDD §18，**待拍板**。

在那之前：`MerchantTokenAuthFilter` 已写好但**未接线**（无人引用），
B 端会话仍在 C 端池里，由一个明确标注的过渡期回落加载器兜住。

## 4. 实施状态

已完成：契约与持久层、六张表、三端装配、身份加载器、过滤器基类、
登录审计五类事件全（LOGIN / LOGOUT / REVOKED / ORPHAN_SESSION 自动落，
LOGIN_FAILED 由四个登录入口显式记 —— 失败走不到签发那一步）、会话与日志清理、
B 端停用踢会话（**此前缺失**）、拆库就绪的架构守卫。

未完成：B 端换池（§3.2）、生产切换。

**默认关闭**：`shop.auth.token-store` 不配成 `db` 就一行代码都不执行，
生产仍是 `ehcache`。
