# ADR-015 多会话并行开发协议：迁移号分段 + 提交边界

> 2026-08-13 · **已决策**
> ℹ️ **本号曾被两篇占用**：另一篇已改号为 [ADR-017 资金归集与结算方式](./ADR-017-资金归集与结算方式.md)。
> 谈资金路径的「ADR-015 §3.x」旧引用指的是那一篇。**撞号的不止迁移号，ADR 号同样会撞** —— 见 §3.5。
> 触发：同一天内两次共享 dev 库被同一类故障卡死（V74、V77），且都是在本 ADR 定稿前发生

---

## 1. 一句话

**迁移幂等是硬性要求，不是加分项**；迁移号「分段认领」只是把冲突概率降低的礼貌，
不是防线本身——防线是「就算撞了，重跑也能成功」。提交边界的规则是：
**共享、易冲突的文件改动收敛提交频率，各自独立的模块正常提交**。

## 2. 背景

这个仓库经常有多个 Claude 会话同时在同一个工作区、同一个共享 MySQL 实例（`ai_shop`）上
并行开发（同一台 dev 机，`shop-base`/`shop-core` 等模块共用 `.m2` 缓存，8081/8082 两个
后端 profile 常驻）。这不是假设的风险——是本项目从第一天起的实际工作方式。

**同一天内发生的两次真实故障**：

| # | 迁移 | 现象 | 根因 |
|---|---|---|---|
| 1 | V74 `perm_backend_only_points` | 另一会话的迁移重跑，`sys_function_point` 撞 `uk_point`，`flyway_schema_history` 卡在 `success=0`，**所有后端实例（不分会话）从此起不来** | 22 条 `INSERT` 里只有一部分写了 `WHERE NOT EXISTS`，另一部分是裸 `VALUES` |
| 2 | V77 `iam_menu_order_point` | 同一天晚些时候，同样的故障模式再现：目标行已存在，裸 `INSERT` 重跑时 1062 | 同一个疏漏——"这次赶时间，先用裸 VALUES，反正只跑一次" |

两次都不是"迁移号冲突"（两条迁移号都没人抢），而是**同一个技术疏漏犯了两次**。
这说明问题不在"协调"，而在"没有把幂等钉成规矩"。

## 3. 决策

### 3.1 迁移必须幂等——这是唯一真正的防线

**每一条写迁移，不论看起来多大概率"只会跑一次"，都必须能安全重跑。**

标准写法（本仓库已有的两种，二选一）：

```sql
-- 写法 A：INSERT ... SELECT ... WHERE NOT EXISTS（本仓库主流写法，H2 测试夹具认得）
INSERT INTO sys_function_point (point_code, ...)
SELECT 'XXX', ... FROM DUAL
 WHERE NOT EXISTS (SELECT 1 FROM sys_function_point x WHERE x.point_code = 'XXX');

-- 写法 B：INSERT ... ON DUPLICATE KEY UPDATE（列不多、更新语义单纯时更短）
INSERT INTO t (k, v) VALUES ('XXX', 1) ON DUPLICATE KEY UPDATE v = v;
```

**为什么"这条只会跑一次"这个判断靠不住**：迁移中途失败、本地库来回切分支反复跑同一条、
两个并发会话都触发了同一次应用启动、CI 与本地各跑一次——都会让"只跑一次"的前提失效。
V74 与 V77 的作者当时都真心相信这一条不会重跑。**不必判断会不会重跑，直接按会重跑写。**

一张表的多条迁移里，**不允许"一半幂等一半不幂等"**——V74 就是这么破的：第 41 行往后全
写了 `WHERE NOT EXISTS`，唯独第 15–16 行图省事留了裸 `VALUES`，故障精确命中那两行。
Review 迁移文件时，同一个文件里的写法必须一致，不一致本身就是要改的信号。

### 3.2 迁移号：分段认领，降低概率但不是唯一防线

并行开发时，迁移号本身可能撞号（两个会话都读到"当前最大是 V73"，都想建 V74）。
**做法**：动手写迁移前，先查一次 `flyway_schema_history` 或 `db/migration/` 目录里
实际最大的号，取 `max+1`；如果预计这批要写好几条，**认领一段区间**并在自己的对齐清单/
TDD 文档里写明（本仓库已有先例：`员工写接口-对齐清单.md` 认领 V60、
`内容与素材域-对齐清单.md` 认领 V61、`BC端权限方案` 认领 V62）。

这条規則**降低撞号概率**，但**扛不住**"两个会话同时查到同一个 max"这种真并发场景——
Flyway 本身在应用层没有跨会话的号段锁。真出现两个会话都写了同一个号，处理方式见 §3.3。

### 3.3 撞了怎么办：谁先发现谁按 §3.1 修，不等对方

不追求"永不发生冲突"，追求"冲突发生后损失可控、修复成本低"：

1. 迁移号撞了（两个文件都叫 `V74__xxx.sql`）：后应用的一方在自己机器上会直接报错
   （Flyway 校验和不匹配或文件已存在），**改名让号**（改成 `max+1`），不需要与对方协商，
   因为改自己的文件不影响已经跑过的一方。
2. 迁移**内容**因为非幂等在重跑时炸了（V74/V77 这两次的真实故障）：
   - 先用 `SELECT ... FROM flyway_schema_history WHERE success=0` 确认卡在哪个版本；
   - 查目标表，确认数据是否已经在库里（通常是"已经在了，卡在重跑"，不是"半途写了一半"）；
   - **谁先发现谁按 §3.1 的写法把迁移文件改成幂等，再清掉那条 `success=0` 记录**
     （`flyway_repair` 或 `DELETE FROM flyway_schema_history WHERE version=? AND success=0`）；
   - 这是共享状态，动手前在会话里知会一声（不是"求批准"，是留痕：谁在什么时候动了
     共享库的迁移历史，后面排障能查到）。
   - 不要因为"这看起来是另一个会话的问题"就等待——**它现在正在阻塞所有人**，
     等待的成本比修复的成本高得多。V74 与 V77 都是这么处理的，两次都在几分钟内修完。

### 3.4 提交边界：共享易冲突文件收敛频率，独立模块正常提交

真正容易产生 Git 冲突的不是"两个会话都在改代码"本身，而是**多个会话同时改同一批
"全局注册表"式的文件**——本仓库典型的是：

- `Perms.java`（权限码常量 + `ROLE_PERMS` 映射，`权限码细化-对齐清单.md` 曾评估过
  147 处 controller 注解行改动的冲突面）
- `enum-registry.ts`（每新增一个具名枚举都要登记一条）
- `docs/technical/README.md`（每新增一篇文档都要加一行索引）
- `db/migration/` 目录本身（见 §3.2）

**规则**：

- 改动只落在自己负责的模块内（新建的 controller、新建的 service、新建的页面）——
  **正常提交节奏，不用等**。
- 改动会碰到上面列的"全局注册表"文件——**改完立刻提交这一小块**，不要攒着和其他
  不相关的改动一起提交。小而快的提交让"两边都改了 `enum-registry.ts`"这种情况在
  `git pull`/下次读取时尽早暴露为一个几行的 diff，而不是攒成一个大改动后才发现冲突。
- 遇到冲突：这些文件的每一行通常都是独立的登记项（一行一个枚举/一行一个权限码/
  一行一个文档索引），**冲突几乎总是"各加各的一行"，直接合并两边都要的行**，
  不存在需要協商语义的情况。

### 3.5 撞号的不止迁移号：**任何"下一个可用编号"都会撞**

本 ADR 定稿当天，两个会话各自取了 015 —— 一篇讲并行协议（本文），一篇讲资金归集。
两边都做了同一件正确的事：`ls ADR/`，看到最大是 014，取 015。

**这不是谁疏忽，是"下一个可用编号"这个动作本身在并发下不成立** ——
§3.2 给迁移号做的分段认领，同样适用于 ADR 号、功能点码、种子数据主键，
凡是"看一眼当前最大值再加一"的地方都一样。

而 ADR 号比迁移号更糟：**迁移撞号会当场报错**（Flyway 校验和不匹配），
**ADR 撞号不报任何错** —— 两个文件名不同，git 不冲突，索引也照收。
直到有人写下"见 ADR-015 §3.2"，而读的人打开了另一篇。

处置沿用 §3.3：**谁后写谁让号，不等对方**。让号方在抬头注明改号缘由与旧号，
被让方也加一行反向指引 —— 因为**存量的外部引用改不干净**，
它们散在代码注释、测试 Javadoc、别的仓库里，只能靠两头的指引兜住。

（2026-08-13 实施：资金归集那篇 → [ADR-017](./ADR-017-资金归集与结算方式.md)，
本文保留 015。判据是写作时间 14:24 晚于 12:27。）

## 4. 不做什么

- **不引入分布式锁或迁移号申请服务**：过度工程。这个仓库的并发度是"同一台机器上
  几个 Claude 会话"，不是真正的多机分布式部署，用文档约定 + 幂等写法就够。
- **不要求所有会话共用一个迁移号发号器**：做不到（会话之间没有实时通信），
  也没必要——§3.3 已经把撞号的修复成本压到几分钟。
- **不因为"避免冲突"而让不相关的功能开发相互等待**：`Perms.java` 这类文件的冲突
  修复成本很低（见 §3.4），用"排队等对方提交完"换"零冲突"不划算。
