# ADR 045 支付接入守卫独立成模块，网关集成在支付服务

> 状态：已接受 · 2026-10-27（用户决定，见[接入守卫模块 pay-guard](../TDD-支付服务-接入守卫模块pay-guard.md) 版本表 v2–v4.1）
> 关联：[支付服务-代码调整优化方案](../支付服务-代码调整优化方案.md) · [开发计划-支付接入守卫与独立部署](../开发计划-支付接入守卫与独立部署.md) · [pay-guard 代码与数据库](../TDD-支付服务-接入守卫模块pay-guard-代码与数据库.md)
> 修订：[ADR-044](./ADR-044-支付接入层模块pay-portal.md) §2-2（鉴权类的位置）、§2-3（运营 / 商家两个面退役）、§2-4（独立形态的装配）、§2-5（`pay-svc` 只暴露 `/internal/**`）；
> [I5 TDD](../TDD-支付服务-I5接入层.md) F58（运营接口迁移方向）、S10（`pay-gateway` 独立进程）、F63（内部接口每调用方凭据）

## 1 背景

ADR-044 建了 `pay-portal`，把支付面向外部的 controller 与鉴权放在一起。实施到 I5 后发现三件事：

1. **鉴权散在三个模块**：过滤器框架在 `pay-portal` `api.auth`，开放 API 验签在 `pay-domain` `openapp`，内部调用过滤器在 `pay-svc`；`PayCaller` 在 5 处被直接构造，没有守卫。
2. **内部调用完全不留痕**：`pay_api_request_log` 有 `INTERNAL_PORT` 值域，但没有代码写它；`pay-svc` 的内部过滤器只打 warn 日志。
3. **支付服务直接面对运营 / 商家会话**：`/pay-ops/v1`、`/biz/pay` 直连 `pay-portal`，独立部署时支付要能内省平台令牌；而 `shop-app` 的 `portal.ops.pay`（24 个 controller）已经是「业务服务认人判权 → 远程调支付」的形状，两种接法并存。

同时，部署现状是：支付整体内嵌在 `shop-app`（`shop.pay.deployment` 默认 `embedded`），`pay-svc` 进程在线上空跑。

## 2 决定

1. **新建 Maven 模块 `backend/pay/pay-guard`**，归支付服务所有，不是新进程。支付的全部接入处理（认调用方、验签、时间窗与 nonce、字段解密、响应签名、来源识别、请求记录）收进这里；外部 API 与 POS 凭证的发放、轮换、吊销也在这里。
   - **包根 `ai.neargo.shop.pay.api.guard`**：守卫的过滤器必然依赖 Servlet，而 `ArchitectureTest` 只豁免 `ai.neargo.shop.pay.api` 这一棵子树（ADR-044 §2-2）。放在这棵子树下，**不放宽任何架构规则**；今天的鉴权类本就在 `pay.api.auth`。
   - 依赖方向：`pay-portal`、`pay-svc` → `pay-guard` → `pay-domain`；`pay-guard` 另依赖 `secret-api`、`shop-base-auth`。业务域不依赖它。
   - **`PayCaller` 只能在 `pay-guard` 里构造**（另加内嵌形态的进程内入口），由 ArchUnit 测试守住。
2. **每个入口一个过滤器，走同一条管线**（`GuardFilter` + 每入口一个 `EntryGuard`），入口由 `PayEntry` 唯一定义（取代 `PortalFace`）：

   | 入口 | 前缀 | 过滤器 | 认什么 |
   |---|---|---|---|
   | 外部系统 | `/open/pay/v1` | `OpenApiGuard` | AppId + 签名 + 时间窗 + nonce + scope |
   | POS 刷卡机 | `/terminal/pay/v1` | `TerminalGuard` | 终端号 + 设备密钥签名 |
   | 支付渠道 | `/pay/callback` | `CallbackGuard` | 先落原文，再按渠道与收款商户验签 |
   | 收银台 H5 | `/checkout/v1` | `CheckoutGuard` | 一次性收银令牌 |
   | 业务系统 | `/internal/pay/v1` | `InternalGuard` | 只识别来源（见 4） |

3. **网关集成在支付服务里**：`pay-svc` 装 `pay-guard` + `pay-portal`，承接上表五个入口；`shop-app` 与其他业务一律经 `/internal/pay/v1` 调支付。将来可把网关独立成 `pay-gateway` 进程（同一个 jar、换装配），由它调 `pay-svc`。
4. **内部调用暂不做权限校验，只留痕**：调用方不验凭据、不判路径授权；来源（服务、实例、自报 IP、追踪号、上游接口、终端用户 IP、操作人）**封装在调用参数里**（`shop-base` `spi.pay.CallSource`，由 `CallSources.current()` 生成、客户端拦截器写进请求头），两个方向都记录（支付侧 `InternalGuard`、业务侧 `InternalCallFilter`）。原凭据校验保留为开关 `shop.pay.guard.internal.verify-credential`，默认关。
5. **业务系统的终端只调业务服务**：小程序、商家端 b-app、运营端 ops-web 只打 `shop-app`；商家与运营的支付功能由 `shop-app` 认人（平台账号体系）、判权（`Perms`）、算数据范围后，经 `/internal/pay/v1/ops|biz/**` 调支付。`pay-portal` 的 `api.ops`、`api.biz` 迁到 `shop-app`，`/pay-ops/v1`、`/biz/pay` 两个面退役。支付运营管理前端是 ops-web 的「支付运营」模块，不单独做前端。

## 3 未采用方案

| 方案 | 不采用原因 |
|---|---|
| 守卫留在 `pay-portal` | `pay-svc` 为了一个内部过滤器要依赖全部对外 controller |
| 守卫放 `pay-domain` | 支付领域依赖 Servlet 与会话，违反 ADR-021 §L1 |
| 包根 `ai.neargo.shop.pay.guard` | 要给 `ArchitectureTest` 再开一个豁免；ADR-044 刻意「只豁免一棵子树」 |
| 网关先独立成 `pay-gateway` 进程（I5 S10 原方案） | 多一个进程、多一跳；独立的价值要等接入方规模上来再兑现 |
| 内部调用每调用方凭据 + 路径授权（I5 F63 原方案） | 用户定：本阶段只留痕；网络隔离是边界，开关保留随时可开 |
| 支付服务内省平台令牌，运营 / 商家直连支付 | 支付要理解平台会话与员工授权；`shop-app` 已有现成的「认人判权 → 远程调支付」接法 |
| 支付运营单独做前端 | 第二套登录与角色；运营人员要在两个后台间切换 |

## 4 代价

- **内部入口的唯一防线是网络隔离**：nginx 所有 server `deny /internal/`、内部端口只对内网；支付信任 `shop-app` 传来的员工号与数据范围。生产切换前评审是否打开 `verify-credential`。
- 一次大搬家（约 24 个类迁入 `pay-guard`，10 个 controller 迁出 `pay-portal`）；按「只改包名」的单独提交降低风险。
- `PaymentPort` 等跨域契约加 `CallSource` 字段（保留旧构造器与 `default` 方法，现有调用方零改动）。
- `pay_api_request_log` 写入量上升（每笔下单至少 2 行内部记录；补偿任务查单抽样）。

## 5 落地

按[开发计划-支付接入守卫与独立部署](../开发计划-支付接入守卫与独立部署.md) M1–M8 执行；本 ADR 的不可逆部分是第 1、3、5 条（模块边界与部署拓扑）。第 4 条（内部调用不校验）是阶段性决定，随时可由开关收紧。
