# ADR-065 门店零售单与订单行开票资料

状态：已采纳（2026-11-24，用户：「按 B 开始 P1」）
关联：[PRD-统一订单与开票资料](../../requirements/PRD-统一订单与开票资料.md) · [TDD-统一订单与开票资料](../TDD-统一订单与开票资料.md) §3

## 背景
手持收银机的销售（含直接输入金额）没有核心订单，开不了票；需求要求开票资料只来自订单，缺的在结账或开票时补齐并冻结。现有建单路径（C 端结账、美业柜台、行业单 + 统一试算、渠道单）都不支持「店员给散客录入任意金额行」。

## 决策
1. 新增**门店零售单**写入路径（`StoreOrderService`），直接落 `ord_order / ord_sub_order / ord_item`，不经统一试算引擎。
2. 订单库表约束新增一种当事人组合：`customer_kind='WALK_IN'`、`admission_kind='STORE_SALE'`、`caller='POS'`，无 user / guest，主体、门店、操作号必填。原有组合不变。
3. **`ord_item` 的 `tax_class` / `invoice_name` 成为发票明细的权威来源**：SKU 行建单时从商品资料冻结；自订行可空（待补），补一次即冻结，开票后锁死；发票来源优先读这两列，没有时才回落到行业报价行与「无绑定按应税」。SKU 行的商品没设课税别（或不在课税范围）时，建单取门店开票设定的默认课税别（用户 2026-11-24「用门店默认税别」），门店也没设才留待补。
4. 混合税别的整单优惠按各税别金额比例（最大余数法）分摊到税别。

## 后果
- 多一条建单路径；POS 的改价与整单优惠由该服务计算，不走促销引擎。
- 改正式库热表约束与加列需要临时授 ALTER（迁移只新增，不改已有数据）。
- 撤回代价高：订单行税别列一旦被发票使用即成为历史记录的一部分，不能删列；`WALK_IN` 订单存在后约束分支不能再收窄。
