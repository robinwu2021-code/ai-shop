# P5 品牌储值与双账户实现记录

状态：2026-10-24，Java（含 food-embedded）及 B/C 类型编译通过，集中验收进行中。已有本地检查点提交，尚未推送或部署，资金能力未开放。

## 调用链

1. Merchant 从当前门店解析主体、品牌和有效绑定版本；Core 按运营范围验证会员，使用平台 canonical customer 标识，手机号不合并资金。
2. 品牌负责人从品牌入口配置发行与活动，指定结算主体。活动复用 Core 版本、审批和发布协调；门店内部创建的活动仍属于本店。
3. 办理储值先选会员，再在底部弹框选本店或品牌方案。品牌接受签名档位，不接受客户端金额或资金归属。
4. Pay 对新承诺按政策、发行方、发行/准入、额度顺序加锁，冻结实收、赠送、发行版本、收款和结算主体、实际储值门店。编号段在资金事务外预留，确认收款及入账在一个 Pay 事务提交。
5. 重试先查原操作人与原指纹，再解析短期引用。已收款原单使用冻结承诺恢复，不重新收款；原单、凭证和额度提交均防重。
6. 核销明确选一个账户；金额由 Core 商品价格决定。报价、顾客确认、预占和扣减固定同一账户，不拼接余额。商家可不传私有授权引用，Core 仍须查到该原服务单及报价的有效顾客确认。
7. 品牌按原充值组成比例固化分摊，受剩余组成约束，末笔消耗余数。扣减直接使用已冻结分配，同事务记录不可变清分事实。
8. C 端统一查看有储值记录的账户及实际发生门店。品牌账户只出现一次，按最近储值或核销排序；通知按 usage/接收人/场景防重，以持久业务单号重新定位有权查看的账户。

## 页面与接口

B 端沿用统一 scaffold/card/kv/tabs/sheet/actionbar。顾客统一搜索，详情分开显示本店与品牌账户；方案采用底部弹框。核销选择服务、顾客确认和商家完成操作均使用原服务单恢复。C 端保留全部/储值/核销三个 tab 和时间弹框，无本金赠金拆分、线上购买或退款。

新增接口与字段由 API 契约及生成的 OpenAPI 提供。关键字段是 scopeType、opaque issuerRef/accountRef/optionRef，原客户引用及 Idempotency-Key；身份、金额和资金归属不由客户端指定。

新储值和核销缓存按操作人、门店、会员、资金范围隔离。旧的未绑定操作人缓存不自动展示或接管，历史原单保留，可凭原操作或业务号核对。

## 限制

- P5 仅支持同主体品牌资金执行；跨主体接受能力等待 P6 结算闭环，会员共享独立运行。
- 财务启用后，旧直接加入/退出/换品牌/停用路径被 Core 栅栏阻止。P6 须完成金融准入同步 saga，不能删除保护绕过。
- 档位储值活动明确拒绝独立 audience、活动预算、总次数及每人次数限制的非默认值；顶层 Pay 发行限额始终生效。旧 Core 活动和已收款承诺保留。
- 真实微信模板未配置；不声称真实发送。ADB 无设备；不声称真机验收。
- 历史实收 100 元赠 30 元原单按用户决定不补账、不取消、不重投、不改状态。P3 实际切写和 P4/P5 开通仍受阻，可发布关闭开关的兼容版本。
