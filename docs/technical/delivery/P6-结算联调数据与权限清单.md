## 2. 最小账号与权限矩阵

正常进入管理空间需要有效账号和 SPACE / management.enter；以下权限分别授予指定 ENTITY、BRAND 或 STORE。品牌运营权、空间所有权不能替代主体财务授权。所有角色名称均为联调别名，不是真实账号标识。

| 角色别名 | 资源 | 最小业务权限 | 验收用途 |
|---|---|---|---|
| VIEW-A | 付款主体 A | sv.settlement.read | 账单列表、详情、明细、付款记录 |
| AUDIT-A | 主体 A | sv.settlement.read + sv.settlement.audit | 增加操作事件页；查看权限本身不包含审计权限 |
| VIEW-B | 收款主体 B | sv.settlement.read | 对侧账单可见性及主体隔离 |
| GENERATE-A | 主体 A | sv.settlement.read + sv.settlement.generate | 仅后续获准的生成测试；只领取本人有权一方的清分组 |
| RECON-A / RECON-B | 各自账单一方主体 | sv.settlement.read + sv.settlement.reconcile | 各自对账；同主体账单不产生付款 |
| DISPUTE-A | 账单任一方主体 | sv.settlement.read + sv.settlement.dispute | 提出争议 |
| RESOLVE-A | 账单任一方主体 | sv.settlement.read + sv.settlement.dispute.resolve | 处理争议，校验当前争议号和版本 |
| ADJUST-A | 账单任一方主体 | sv.settlement.read + sv.settlement.adjust | 只追加调整事实，已结清纠错进入后续账期 |
| PAY-A | 付款主体 A | sv.settlement.read + sv.settlement.payment.register | 登记线下付款事实，不代表到账 |
| VOID-A | 付款主体 A | sv.settlement.read + sv.settlement.payment.void | 撤销尚未确认收款的登记 |
| RECEIVE-B | 收款主体 B | sv.settlement.read + sv.settlement.receipt.confirm | 独立确认到账 |
| DENIED-X | 无账单双方主体授权 | 仅管理空间/品牌访问 | 不显示不应有入口；直接请求仍被服务端拒绝 |

PAY-A 与 RECEIVE-B 必须是不同 actor 且不同 principal；同一平台用户关联两个商家账号不能作为两个独立确认人。无需为了页面查看增加 sv.issuer.collection.confirm；它属于集中收款授权。

已有发行设置单独使用 BRAND/STORE / sv.issuer.read。汇总单独使用 sv.brand.report、sv.store.report 或 sv.activity.report，不用财务权限替代报表权限。

“配置储值结算权限”目前调用 prepare，为符合所有者条件的操作者准备整组 11 个财务权限，包含登记、确认、调整和集中收款。它不是只读开通按钮。本阶段不调用该操作；如后续获准准备只读角色，应通过现有资源授权能力只授予 read，以及确有需要的 audit，不授予转授权。

## 3. 测试数据依赖与准备方式

| 数据别名 | 必须具备的事实 | 当前状态 / 准备边界 |
|---|---|---|
| ORG | 一个管理空间、主体 A/B、门店 S-A/S-B、品牌 BR | 现有测试品牌停用；不自动启用或换绑门店 |
| ISSUER-BR | 品牌发行方、有效配置版本、结算主体 A、币种及经营时区 | 当前品牌不存在；需另行准备获准测试资源 |
| ISSUER-LOCAL | 独立单店发行方 | 用于与品牌筛选、归属隔离对照，不能混用余额 |
| CLEARING | 可追溯的原清分事实及账期过账水位，关联原来源和实际核销店 | 正向账单的前提，不能伪造现有业务账务来满足页面 |
| BILL | 正常业务生成的账单、独占来源明细、双方主体及冻结版本 | 当前品牌不存在账单 |
| EVENT | 对账、争议、调整等追加事件，与账单版本一致 | 通过受控业务链产生，不能覆盖历史事件 |
| PAYMENT | 登记、确认或撤销记录，与账单累计金额勾稽 | 仅后续获准的隔离操作阶段准备 |
| PAGE | 超过一页的账单、明细、付款或事件 | 用于游标和过滤隔离，按正常夹具生成并保持唯一来源 |
| NEGATIVE | 他主体、他发行方、撤销角色、同 principal 双账号 | 在独立联调夹具准备，不改变当前真实账号授权 |

优先使用已有、已获准的测试资源。当前空间缺少正向资源时，推荐以独立联调实例复用已验证的 Spring/MySQL 夹具，按域服务生成合成事实后让专用前端连接该实例。实例、数据库、账号和前端目标须先落实；当前尚未新建或切换。

独立实例的配置和能力就绪检查依然保留。当前实例的 P3 基础、历史原单、金融开关继续保持原状；不是为了演示页面而开通当前实例跨主体业务。付款凭据加密配置属于登记/确认联调的前提，只在目标实例安全配置，不在本清单填写密钥。

### 合成账单覆盖集

下列金额仅为计划中的隔离夹具示例，单位分，未写入任何环境。账单及其明细、事件、付款必须一致，不能仅修改状态字段。

| 别名 | 类型 / 状态 | 应付 | 已登记 | 已确认 | 关键显示 |
|---|---|---:|---:|---:|---|
| B-DRAFT | CROSS_ENTITY / DRAFT | 10000 | 0 | 0 | 双方对账状态 |
| B-RECON | CROSS_ENTITY / RECONCILED | 10000 | 0 | 0 | 待登记付款 |
| B-WAIT | CROSS_ENTITY / WAIT_RECEIPT | 10000 | 10000 | 0 | 登记不等于到账 |
| B-PART | CROSS_ENTITY / PART_PAID | 10000 | 4000 | 4000 | 已确认部分款、剩余应付 |
| B-DONE | CROSS_ENTITY / SETTLED | 10000 | 10000 | 10000 | 完成状态、原付款与事件 |
| B-DISPUTE | CROSS_ENTITY / DISPUTED | 10000 | 0 | 0 | 当前争议和处理原因 |
| B-INTERNAL | INTERNAL_RECON / INTERNAL_RECONCILED | 0 | 0 | 0 | 内部对账，无付款操作 |

再准备相邻账期、另一币种、另一发行方和另一主体的对照记录，分别验证隔离，不跨币种求和。记录生成顺序与账期分别验证；列表实际按 created_at、bill_no 倒序，账期过滤是区间交集。日界和账期以发行方经营时区换算，不能用手机时区替代。

## 4. 只读接口及前提

| 接口 | 用途 / 前提 |
|---|---|
| GET /biz/management/stored-value/financial-capability | 查看真实能力，只读取状态，不调整开关 |
| GET /biz/management/stored-value/financial-resources | 由主体财务授权与发行方归属筛选资源；没有资源时没有正向列表数据 |
| GET /biz/management/stored-value/settlement-bills | 至少一侧 sv.settlement.read；支持 scopeType、issuerNo、status、currency、periodFrom/periodTo、cursor、size |
| GET /biz/management/stored-value/settlement-bills/{billNo} | 必须是可访问发行方和账单一方的查看权限 |
| GET /biz/management/stored-value/settlement-bills/{billNo}/actions | 返回当前主体动作；不是客户端自行推导的权限 |
| GET /biz/management/stored-value/settlement-bills/{billNo}/items | read；来源和实际门店归因、追加分页 |
| GET /biz/management/stored-value/settlement-bills/{billNo}/payments | read；登记、确认、撤销状态与金额 |
| GET /biz/management/stored-value/settlement-bills/{billNo}/events | audit；不应因只有 read 而自动调用 |
| GET /biz/management/stored-value/settlement-bills/{billNo}/payment-resolutions | 原登记结果查询；只有需要验证原请求恢复时使用 |

每项均使用正常鉴权并带 managementNo。公开接口不能传入可信权限集合或用内部服务令牌代替用户授权。

## 5. 验收顺序与通过标准

| 阶段 | 内容 | 通过标准 / 当前状态 |
|---|---|---|
| R0 资源核对 | 状态、最小权限、发行方、账单存在性 | 本轮已完成只读核对；缺项明确，不写入补齐 |
| R1 只读入口 | 有权且有资源、无权、有权但无资源 | 当前仅“无资源入口未显示”已现场记录；其他条件待夹具 |
| R2 列表与筛选 | 已实现的发行方底部选择、全部/待对账/已对账/争议/已结清 Tab、分页 | 不漏不重、切筛选不混旧游标，迟到响应不能覆盖新结果 |
| R3 详情与权限 | 明细、付款、事件、金额、版本、只读按钮 | VIEW 无写按钮；无 audit 不展示事件 Tab、不发送事件请求 |
| R4 操作联调 | 生成、双方对账、争议、处理、调整、登记、独立确认、撤销、原请求恢复 | 仅获准隔离数据与独立实例执行；服务端拒绝越权、同 principal 自确认和过期版本 |
| R5 定向修复发布 | 对发现的问题统一编码/编译，再测修复及影响处 | 不重跑已通过且未受影响的 P5/P6 业务回归 |

接口额外支持的币种和账期筛选，不等于移动页面已提供对应筛选控件；当前页面按其实际已有控件验收，API 参数另按接口核验。PART_PAID、WAIT_RECEIPT、INTERNAL_RECONCILED 可在“全部”显示，不宣称有对应独立 Tab。
