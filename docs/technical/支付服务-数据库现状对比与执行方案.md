## 3 差异

### 3.1 约定差异与并存规则

| 项 | 现有表 | v4 新表 | **并存规则** |
|---|---|---|---|
| 主键 | `id BIGINT` 自增（有，但不用于关联） | `id BIGINT` 自增（Java `Long`） | 一致，无需处理 |
| 关联方式 | 业务号：`order_no`、`after_sale_no`、`pay_merchant_no`、`payment_no` | `<表>_id BIGINT` | **新 → 老**：新表存老表的 `id`（如 `stl_payment_id`）。**老 → 新**：老表加 `*_id` 列（如 `stl_payment.pay_order_id`）。**老 ↔ 老**：照旧按业务号，本期不改 |
| 租户 | 全部带 `tenant_no`，唯一键以它开头 | 无 | 老表照旧；新实体继承 **`PayBaseEntity`**（不含 `tenantNo`，否则 `AuditMetaObjectHandler` 会往不存在的列填值）；新老 join 时老表一侧带 `tenant_no = 'MAIN'` |
| 关联核心系统 | `entity_no` / `store_no` 字符串 | `store_id` → `mch_store.id` | 新表只存 `store_id`；老表（`stl_bill.store_no`）保留；需要时经 `pay_order_id → store_id` 取 |
| 业务时间 | `stl_payment.succeeded_at` 等 BIGINT 毫秒；`created_at` 为 `DATETIME` | `DATETIME(3)` UTC | 老表不改；Java 侧统一用 `Instant`，跨表比较在代码里换算，不在 SQL 里混比 |
| 实体与 Mapper 位置 | `MchPaymentMerchant` 在 `shop-merchant`，走主数据源 | 全部在 `ai.neargo.shop.pay.mapper.*`，走 pay 数据源（今天同库） | 迁入后 `shop-merchant` 不再有支付商户的实体与 Mapper |
| 唯一性辅助 | 无 | `active_key` / `inflight_key` / `open_key` 可空列 + 唯一索引 | 只在新表使用 |
| 排序规则 | 基线 `utf8mb4_uca1400_ai_ci` | 不写，跟随库默认 | 同库默认即基线规则，新老 join 不冲突 |

### 3.2 被替代或改造的对象：现状 → v4

#### `mch_payment_merchant`（30 列 · 主代码 14 处、测试 18 处引用）

| 现状 | v4 | 差异要点 |
|---|---|---|
| 一行 = 进件申请 + 收款商户号 | `pay_onboarding` + `pay_onboarding_version` + `pay_onboarding_material` → 成功产出 `pay_merchant` | 进件可多版本；外部单号每版唯一（修 R04）；驳回原因随版本保留（修 R23） |

| 无 market / currency / access_mode / funds_path | 全部成为 `pay_merchant` 的列 | `funds_path` 从 `mch_entity.funds_mode` 下沉 |

## 4 执行方案

### 4.1 原则

1. **先加、后切、再删**：新表和新列先上、空跑；切换靠开关；删除放在最后，且至少隔一个版本周期、先备份。
2. **结构变更走 Flyway，数据迁移走任务**：DDL 与确定性种子写迁移；需要按业务号解析 id、要出冲突报告的回填写成可重跑的 Java 任务（批量、幂等、带演练模式）。**已应用的迁移不改一个字符**（java.md §二）。
3. **每条迁移过闸门**：`node scripts/check-sql-portability.mjs`、`entity-alignment` 守卫、`ArchitectureTest`、`PayHasNoControllerTest`、`known-*` 棘轮不变长；H2 与 MariaDB 都要过（CHECK 在 H2 不生效，服务层另测）。
4. **每一步都有数字验收**：迁移前后行数、冲突数、新旧解析差异数，写进本文 §5 的校验 SQL。
5. **一个阶段一个会话**：`MerchantPortImpl`、`PaymentLedgerServiceImpl`、`SettlePortImpl` 三个高冲突文件同一时刻只让一个会话改。

### 4.5 S3–S6 · 写入、回填、比对、读切

**写路径接入（S3，开关默认关）**

| 开关 | 打开后 |
|---|---|
| `shop.pay.log.recording=true` | `RecordingChannelClient` 写 `pay_channel_call_log`；回调写 `pay_callback_log`；`stl_channel_message` 停写 |
| `shop.pay.order.enabled=true` | 内部下单先建 `pay_order`，`stl_payment.pay_order_id` 实时写入；成功经 `PaymentOutcomeService` 统一入账 |
| `shop.pay.ledger.enabled=true` | 成功 / 退款同事务写复式流水 |
| `shop.pay.refund.review=true` | 退款经 `pay_refund` 与复核规则 |

**商户双写与回填（S4）**

| 序 | 回填 | 规则要点 | 产出 |
|---|---|---|---|
| B1 | 平台级 `pay_merchant`（`owner_type=PLATFORM`） | 由 yml 里的 CN 服务商号 / 直连号生成；`channel_merchant_id` 取配置值 | 平台商户 id 映射表 |
| B2 | `mch_payment_merchant` → `pay_onboarding`（+ v1）与 `pay_merchant` | `pay_merchant_no` 原值；`store_no` 空串 → 该主体 `mch_store.is_default = 1` 的门店 id（与 V16 / V240 / V381 把主体级数据落到门店的口径一致），取不到进冲突报告；`funds_path` ← `mch_entity.funds_mode`；状态映射见表结构说明 §8.1 | 冲突报告 1 |
| B3 | `pay_merchant_binding` | `mch_store.pay_merchant_no` 与行上 `store_no` 两个来源合并；**主体级 ACTIVE 号展开到该主体下每个缺绑定的门店**；两来源不一致进冲突报告，不自动取舍 | 冲突报告 2 |
| B4 | `pay_merchant_product` | `pay_methods` 逐项映射到 `pay_channel_product.id`；额度落主产品 | 冲突报告 3（映射不到的方式） |
| B5 | 双写开 | `shop.pay.merchant.dual-write=true`：进件、启用、绑定写旧表的同时写新表 | — |
| B6 | `pay_order` / `pay_refund` | 每个 `order_no` 一张 `pay_order`（`pay_app_id` = MALL，`out_order_no = order_no`，`store_id` 由子单门店解析）；回填 `stl_payment.pay_order_id`；REFUND 行 → `pay_refund` | 未解析清单 |
| B7 | 流水期初 | 已成功交易按 `succeeded_at` 补记期初凭证（`ADJUST`） | 期初余额核对表 |

**比对（S5）**：对每个「门店 × 渠道」，比较旧解析（`paymentRouteOf` / `resolvePayment` / `payMerchantNoOf`）与新 `PayMerchantQueryPort#routeOf`。**差异为 0，或每一条都已人工确认，才进入 S6。** 比对结果留档。

**读切（S6）**：`shop.pay.merchant.read-from=pay`；17 个调用方改走 `PayMerchantQueryPort`；进件入口迁到 `pay-portal`，旧路径转发一个版本周期。出问题时开关切回 `legacy`，双写保证两边数据一致。

### 4.6 密钥搁置期间的过渡规则

| 位置 | 过渡做法 | 密钥模块就绪后 |
|---|---|---|
| `pay_merchant.sec_key_id` | NULL；CN 平台级商户的凭据**继续从 yml 读** | 录入 `sec_key`，回填 id，删 yml |
| `pay_merchant` 的 CHECK「MERCHANT_OWN 必须有密钥」 | 过渡期**服务层放宽**：`owner_type=PLATFORM` 且凭据在配置中时允许为空；新渠道（蓝新 / LINE Pay / PayBy 的商户自有密钥）**不上线** | 恢复严格校验 |
| `pay_onboarding_material` 敏感字段 | 过渡期不落敏感值：`value_masked` 存掩码，`sec_secret_blob_id` 为空，明文只透传给渠道（与今天一致） | 改为加密落库 |
| `pay_raw_payload` | 过渡期**只开脱敏副本**（`pay_channel_call_log.request_masked` 等），原文表不写 | 接入加密后开始写原文 |

也就是说：**本期能落地的是 CN 现有渠道的新数据模型**；TW / AE 新渠道要等密钥模块。

## 5 校验 SQL（只读）

```sql
-- Q1 · S1 前：out_trade_no 存量重复（必须为 0 才能加唯一键）
SELECT out_trade_no, COUNT(*) c FROM stl_payment
WHERE out_trade_no IS NOT NULL GROUP BY out_trade_no HAVING c > 1;

-- Q2 · B2 前：主体级收款号找不到默认门店（is_default = 1）的主体
SELECT mp.entity_no, mp.pay_channel, mp.pay_merchant_no
FROM mch_payment_merchant mp
WHERE mp.store_no = '' AND mp.deleted = 0
  AND NOT EXISTS (SELECT 1 FROM mch_store s
                  WHERE s.entity_no = mp.entity_no AND s.is_default = 1 AND s.deleted = 0);

-- Q3 · B3 前：同一门店同一渠道，两个来源给出不同的号
SELECT s.store_no, mp.pay_channel, s.pay_merchant_no AS from_store, mp.pay_merchant_no AS from_row
FROM mch_store s
JOIN mch_payment_merchant mp ON mp.entity_no = s.entity_no AND mp.store_no = s.store_no AND mp.deleted = 0
JOIN mch_payment_merchant cur ON cur.pay_merchant_no = s.pay_merchant_no AND cur.pay_channel = mp.pay_channel
WHERE s.pay_merchant_no IS NOT NULL AND s.pay_merchant_no <> mp.pay_merchant_no;

-- Q4 · B2 后：行数核对（ACTIVE 且有号的旧行 = 新 pay_merchant 中 owner_type=STORE 的行）
SELECT (SELECT COUNT(*) FROM mch_payment_merchant WHERE pay_merchant_no IS NOT NULL AND deleted = 0) AS legacy,
       (SELECT COUNT(*) FROM pay_merchant WHERE owner_type = 'STORE' AND deleted = 0) AS migrated;

-- Q5 · B6 后：未关联支付单的通道交易（应为 0，或全部在未解析清单里）
SELECT COUNT(*) FROM stl_payment WHERE direction = 'PAY' AND pay_order_id IS NULL AND deleted = 0;

-- Q6 · 每日：孤立的门店 id（门店被删或 id 错误）
SELECT 'pay_merchant_binding' t, b.store_id FROM pay_merchant_binding b
LEFT JOIN mch_store s ON s.id = b.store_id WHERE s.id IS NULL
UNION ALL
SELECT 'pay_order', o.store_id FROM pay_order o
LEFT JOIN mch_store s ON s.id = o.store_id WHERE s.id IS NULL;

-- Q7 · B7 后：流水借贷平衡
SELECT pay_ledger_voucher_id,
       SUM(CASE direction WHEN 'DR' THEN amount_minor ELSE 0 END) - SUM(CASE direction WHEN 'CR' THEN amount_minor ELSE 0 END) AS diff
FROM pay_ledger_entry GROUP BY pay_ledger_voucher_id HAVING diff <> 0;
```

## 6 风险与回退

| 风险 | 后果 | 缓解 / 回退 |
|---|---|---|
| `out_trade_no` 存量有重复 | 唯一键迁移失败，Flyway 记 failed，所有版本 jar 起不来 | Q1 先查；迁移前备份；失败先清 failed 记录再处理 |
| 主体级默认号展开后，门店绑定不符合今天的实际收款 | 钱打错户 | Q2 / Q3 冲突报告人工确认；S5 全量比对为 0 才读切 |
| 新开门店不再自动继承收款商户 | 新店收不了款 | 开店流程同版本加「选择收款商户」（表结构说明 Q-v3-1）；上线前演练 |
| 两套约定并存期间，有人在新表查询里带 `tenant_no` 或在老表间改用 id | 查询报错或语义混乱 | §3.1 并存规则写进 java.md；`PayBaseEntity` 让新实体写不出 `tenantNo` |
| 核心系统门店 id 被重建 / 复用 | 历史单据挂错门店 | ADR-021 §3.3 修订写入「id 永不变更、不复用」；Q6 每日扫描 |
| 回填与双写并发 | 新表数据缺失或重复 | 回填任务幂等（按旧行业务号 upsert）；双写先开、回填后跑、比对兜底 |
| 多会话同时加迁移 | 版本号撞车 | 每次加迁移前 `ls | sort -V | tail`；改号后 `clean package` |
| 密钥搁置导致 TW / AE 不能上线 | 新渠道延后 | §4.6 写明边界；本期只交付 CN 的新模型 |
