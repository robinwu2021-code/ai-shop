# TDD · 运营端支付管理（P-4.2）

覆盖矩阵 P-4.2.1 支付流水核对 / P-4.2.2 掉单补偿 / P-4.2.3 关单策略配置。
三者同页（`/orders` 的 pay / repair / close 三个 tab），因为它们是**同一条因果链**：

```
关单时限太短  →  用户还在收银台，订单已被关掉  →  渠道收了钱、平台没订单（CHANNEL_ONLY 差异）  →  掉单补偿
```

把关单策略放到别的菜单里，运营就永远只在"补单"这一端救火，不会去改造成原因的那个数字。

## 一、领域模型

`lib/types/payment.ts`

- `ReconDiffType` 分三类而不是笼统叫"异常"，因为**处置方式完全不同**：
  - `CHANNEL_ONLY` 渠道有、平台无 → 补单或退款
  - `PLATFORM_ONLY` 平台有、渠道无 → 冲正
  - `AMOUNT_DIFF` 金额不符 → 人工查是折扣算错还是重复扣款
- 金额一律最小货币单位（分），与全站一致。
- `CloseRule` 三个字段：关单时限、提醒提前量、关单后迟到回调是否自动退款。

## 二、规则落在 mock 层

页面**写不出**违规操作 —— 规则在 `lib/api/mocks/payment.ts`，不在表单校验里。

| 规则 | 不这么做会怎样 |
| --- | --- |
| 处置结论必填（忽略也要写理由） | 没有结论的"已处理"等于没处理，下个月同样的差异还得从头查 |
| `CHANNEL_ONLY` 必须选补单/退款 | 只写结论 = 钱还挂在渠道那边 |
| 非 `CHANNEL_ONLY` 传补单/退款直接报错 | 静默忽略会让调用方以为退成功了 |
| 已处置的不能再处置 | 重复处置 = 二次补单或二次退款，真金白银 |
| 补单金额恒等于渠道实收，**契约里没有 amount 入参** | 能改的金额一定会有人改错 |
| 关单时限 5–1440 分钟 | 太短持续制造掉单；太长长期占住库存 |
| 提醒提前量 < 关单时限 | 否则提醒发出时订单已经关了 |

`lib/mock/db/payment.test.ts` 11 条用例逐条锁住，其中"真落库"一条会重新读一次配置 —— 伪实现会在那里露馅。

## 三、页面

`app/orders/page.tsx` 由单页改为 4 tab（`usePageTab`）：订单检索 / 支付流水核对 / 掉单补偿 / 关单策略配置。

- **核对**：全量差异表，按类型与状态筛选，差额列带正负号（渠道多收为正、平台多记为负）。
- **补偿**：同一张表预置 `type=CHANNEL_ONLY & status=OPEN`，是"待办队列"而非又一个筛选面板；页面文案直接把人引向关单策略。
- **关单**：`ConfigCard`，每个字段的说明写的是**后果**而不是取值范围。

三个叶子在 `lib/nav.ts` 去掉 `soon`，`nav.test.ts` 的守卫会验证页面真的认这三个 `?tab=`。
