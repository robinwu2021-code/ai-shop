## 1. 为什么是这个

它是矩阵 §七「按商家拆单 + 分账」这条链路的收口，而且**已交付的域正在等它**：

- 售后裁决打了 `refundSplitPending` 标记（P-6.1.5 退款回退分账，E4），没有资金域就一直挂着
- 商家档案有 `settleAccountReady`（分账接收方报备），没有资金域就没人消费它
- 自提点有 `serviceFeeRate`（履约服务费，R15），订单有 `trafficSource`（分档计费，R16）

本批把这四个已存在的字段**接起来**。这是它比"再开一个新域"更值得先做的理由。

## 2. 方案

### 2.1 页面 `/finance`

| tab | 覆盖 |
|---|---|
| 结算单 | P-12.1.1 报备状态 · 12.1.2 结算单生成 · 12.1.3 分账指令与重试 · 12.1.4 超时兜底 |
| 分账明细 | 按子订单的分账流水（含 trafficSource 分档、履约服务费） |
| 退款回退 | **P-12.1.5 / E4**：消费售后打的 `refundSplitPending` 标记 |
| 费率配置 | P-12.1.7 按 trafficSource 分档（R16）· 12.1.8 自提点服务费（R15）· 超时兜底天数 |

提现与税（P-12.2）矩阵标 **P1 二期**，本批不做，导航保持待建。

### 2.2 数据模型

- `Settlement` 结算单：商家 × 周期，`grossAmount / platformFee / serviceFee / netAmount`，
  状态 `PENDING → SPLITTING → SPLIT`，失败进 `FAILED`（可重试），超时进 `FROZEN_BACK`（解冻回平台）
- `SplitRecord` 分账明细：一条 = 一个子订单，带 `trafficSource` 与实际适用费率
- `FeeRule` 费率配置：`byTrafficSource`（万分比）+ `pickupServiceFeeRate` + `freezeDays`

### 2.3 关键规则（mock 层强制）

1. **未报备分账接收方的商家不能执行分账**（读商家档案 `settleAccountReady`，ADR-002）
2. **对账恒等式**：`gross = platformFee + serviceFee + net`，生成与保存时都校验 ——
   这三个数分别来自三处（费率、自提点、余数），不校验就会出现"分完了还差几分钱"
3. **重试有上限**（3 次），超过转 `FAILED` 等人工介入 —— 无限重试会把一个坏账刷成一堆日志
4. **超时兜底**：冻结超过 `freezeDays` 天仍未成功 → `FROZEN_BACK`（解冻回平台，12.1.4）
5. **退款回退执行后必须清除售后单的 `refundSplitPending`**，否则队列永远消不掉
6. 费率分档：`MERCHANT_OWNED`（商家自带客流）**建议 0**（R16 未定），存结构可配

### 2.4 权限

复用 `finance:settle:read/execute`、`finance:rate:update`、`finance:withdraw:approve`、`finance:invoice:read`。
⚠️ `finance:settle:execute` 是**动钱**的码，只有超管与财务持有（`/dev/perms` 可核）。

## 4. 风险

1. **R15 / R16 口径未定**（矩阵 M8 / M9）：本批把费率做成**可配置**，默认值只是起点，不是结论。
2. **真实分账走微信支付**（ADR-002）：mock 只模拟"指令下发 → 成功/失败/重试"的状态流转，
   不模拟支付服务商的具体报文；接后端时 `SplitRecord` 需要加 PSP 单号字段。
3. 平台佣金的**出资口径**（分账内扣 vs 另收，矩阵 12.1.6 待定）：本批按"分账内扣"实现，
   若定为另收，改的是恒等式而不是模型。
