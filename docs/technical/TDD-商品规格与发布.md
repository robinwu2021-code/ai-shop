# TDD · 商品规格与发布：三种形状、一个编译点

状态：草稿（待确认）
关联需求：[PRD-商品规格与发布](../requirements/PRD-商品规格与发布.md)
创建日期：2026-08-30

> 证据底座在[商品规格参数-模型与查询性能](design/商品规格参数-模型与查询性能.md)
>（生产 EXPLAIN、20 万行实测、逐行代码核对都在那份）。本 TDD 是**决定**：
> 从那些证据里选定的方案、接口与约束，不重复论证过程。

## 1. 需求摘要

编辑时刻自由（四层规格库随便改、草稿不动线上），发布时刻严谨
（重解析+重烘焙、失效引用逐条拦、原子换版）；C 端读路径窄而快
（详情 2 表零 JOIN、列表走索引）；审核可开关；三处身份永不失配。

## 2. 当前架构分析

- **主干正确，不推倒**：写侧规范化规格库（四层稀疏裁剪），读侧 JSON 快照
  （`prd_goods.spec_groups/params` + `prd_sku.option_values/option_value_nos`），
  C 端详情零 JOIN
- **已有且比要求更严**：V247 保存即自动下架送审 + `pendingOnSale` 过审恢复；
  V171 草稿态；上架三道闸（过审/类目授权/门店货架）
- **六个缺口**（证据见底座文档 §0/§4.5）：列表零索引可用、列表 N+1、
  合并只改写三处身份之一、三处 archive 无在用检查、用量按组名正则数、
  烘焙点在保存而非发布

## 3. 方案设计

### 3.1 总模型：同一份事实，三种形状

| 形状 | 服务 | 权威性 | 一致性 |
|---|---|---|---|
| 规范化规格库（现有四层） | 写侧维护 | **唯一真源** | 事务强一致 |
| JSON 快照 | C 端整块渲染 | 快照，**故意不跟随** | 无需一致（业务语义） |
| 倒排/读模型（按触发条件建） | 按规格查、列表 | 派生 | 最终一致 + 对账守卫 |

判断新需求落哪，只问：它是「谁说了算」「给人看」还是「按它查」。

### 3.2 生命周期与编译点（方案对比已定案）

| 方案 | 结论 |
|---|---|
| A. 烘焙在保存（现状） | ❌ 草稿放两周，上架时带着过期文案/停用档，无人发现 |
| B. 烘焙在发布 + 单版本（V247 自动下架） | ❌ 审核期间线上是空的 |
| **C. 烘焙在发布 + 双版本草稿** | ✅ **采用**。线上照卖旧版，发布=事务换版 |

编译点 `bakeForPublish`（手动上架与过审共用同一段）：
①逐档对**当前**规格库 `resolveValueNos` 重解析，失败集中报（不解析到第一个就抛）；
②文案按当前四层合并重烘焙，身份列同步刷；③（倒排表建成后）同事务重建倒排行。
幂等：快照没变不写库。下架、驳回**不**烘焙。

### 3.3 双版本草稿

新表 `prd_goods_draft(goods_no PK, entity_no, payload TEXT, base_updated_at, …)`。
在售商品的保存只写草稿；内容与线上相同即删行（标识判据=草稿行存在）；
发布前 `base_updated_at` 对不上线上 `updated_at` → 拒并引导看差异。
草稿 JSON 是**编辑缓冲不是契约** —— 正确性由编译点保证，不由存储形状保证
（这就是「不加规范化引用表」的理由，论证见底座 §4.6.3）。

### 3.4 联动规则（R1–R6，防静默错位）

核心一句：**文案可以随便改（快照保护买家一致性），标识不能随便退役（它是聚合锚点）。**

- R2 改身份（合并/提升）= 枚举全部引用点一次改完：`prd_sku.option_value_nos`、
  `spec_groups[].optionCodes`、`params[].valueNo` **三处，漏一处即缺口**
- R3 退役先问谁在用：三处 archive 在用即拒；判据先 `deleted=0`，
  编译点落地后收窄为 `on_sale=1`（草稿不锁规格库，失效引用发布时拦）
- R5 快照永不跟随文案（现状，写明防被「修」掉）
- R6 位置对齐守卫：`optionValues` 与规格组按位置对齐，解析不出要告警不留 null

### 3.5 审核开关

`goods.audit` 功能开关（登记处现成，本项是第一个消费者）。
商品域经新 SPI `spi/platform/FeatureFlagPort.isEnabled(key)` 读（域间不许直依赖）。
关 = 提交即置 `APPROVED` 走编译点，落「免审自动通过」审计行。

### 3.6 查询性能

- `prd_goods` 两条复合索引（`(deleted,on_sale,audit_status,category_no,sales)` 与
  去掉 `category_no` 的一条 —— 跳中间列优化器整条放弃，生产实测过）
- 列表 N+1 修掉（`flashPrices` 批量化，照同文件 `promoted()` 的形状）
- 类目树/平台值池：Spring Cache 抽象 + ehcache 实现（不引新依赖；
  换 Redis 只换 `CacheManager` bean），30s TTL，运营写路径整区失效
- 比价/按规格筛（触发时）：倒排表 `prd_sku_spec_value`，
  主键 `(value_no, sku_no)` + 覆盖索引 `(value_no, price)` ——
  实测比 MySQL 多值索引快且改价只是一条 UPDATE
- 搜索到 5 万商品切 ES，`GoodsService` 接口不变

### 3.7 横切约束

所有新 DDL/SQL 必须 MariaDB 与 MySQL 8 双兼容
（[可移植性规矩](design/数据库可移植性-MariaDB到MySQL.md)，闸门
`check-sql-portability.mjs` 已挂 pre-push）：排序规则一律 `utf8mb4_unicode_520_ci`、
无 `IF NOT EXISTS`、无任何一边独有语法。

## 4. 核心接口

| 接口 | 说明 |
|---|---|
| `bakeForPublish(goods)` | 编译点。重解析+重烘焙，失败集中抛（错误含档位清单） |
| `FeatureFlagPort.isEnabled(key)` | SPI，商品域读平台开关 |
| `GET /biz/goods/{no}/publish-preview` | 服务端 dry-run 烘焙后做字段级 diff（端上比 payload 会漏「文案将随规格库刷新」） |
| `publish(merchantNo, goodsNo)` | 冲突检查 → 编译 → 事务换版（覆写主表+SKU+删草稿+syncPool） |
| `SPEC_IN_USE(80016)` | 在用检查错误码，信息含数量与下一步 |

## 5. 测试策略

- 每步**红测试先行**（先证明现状确实红在预期位置）
- 每处守卫**做消融**（塞坏数据必须变红并点名；否则是永远绿的代码）
- 审核开关**两态都测**（默认关的那一半才是生产常态）
- 性能判据用 **EXPLAIN 执行计划形状**，不用 380 行库上的计时数字
- 关键场景：PRD §6 的 8 条验收逐条对应场景测试

## 6. 风险与注意事项

| 风险 | 对策 |
|---|---|
| V247 在途商品（正下架送审中） | `pendingOnSale` 恢复逻辑保留至跑空，注释标明可删时机 |
| 合并/停用在生产首次使用即打中一批商品 | 一期步骤 1/2 排在所有性能项之前 |
| 生成列/JSON 索引这类「快而错」的歪路 | 底座 §4.4 已实测记录，闸门拦 `CAST AS ARRAY` |
| 单机缓存 vs 将来多实例 | `CacheManager` javadoc 写明前提，多实例换 Redis 实现 |
| 存量 71 件 spec_groups 不合规 | `JSON_SCHEMA_VALID` CHECK 约束等收敛后再加（版本下限 12.3.2，MDEV-38033） |
