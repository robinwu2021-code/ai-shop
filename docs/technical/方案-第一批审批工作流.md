## 0. 通用接法（每个审批都一样）

```
业务「提交」（业务事务内）
  → ApprovalPort.submit(类型, 对象号, 修订号, 提交人)     写 approval_link + 发件箱
  → OpsKit 审批步骤（审批人按权限码；可以本人审批）
  → 执行节点 → 业务 apply(对象号, 修订号)                幂等；先比修订号，不同 → STALE
       成功 → 已生效
       业务校验失败 → 生效失败（可重试 / 放弃）
  → 驳回 / 撤回 / 放弃 → 业务 onClosed(...)              回到可编辑或原状态
```

每个审批都要定下面几件事，下表逐项写清：

| 项 | 说明 |
|---|---|
| **提交时机** | 业务里哪一步送审，送审前要做哪些校验 |
| **审批步骤** | 默认流程。审批人一律按权限码，可以本人审批；运营可以在「审批流程」页调整 |
| **修订号** | 对象被改动时一定会变的号，用来判断 STALE |
| **申请内容** | 审批人看到的字段，含「改前 → 改后」 |
| **生效** | 执行节点调用的业务动作，以及它要重新校验的条件 |
| **未通过** | 驳回 / 撤回 / 放弃后业务回到哪个状态 |
| **要改的旧入口** | 原来的审批端点、页面按钮怎么处理 |

## 3. 逐项工作流

### T1 · 门店营业开通（ai-shop）—— 已接，待联调

| 项 | 内容 |
|---|---|
| 提交 | 运营在门店详情点「提交开通」→ `StoreOperationalReviewServiceImpl.submit`，首次进入 PENDING_OPEN / PENDING 时送审 |
| 步骤 | 审核：`merchant:apply:audit` |
| 修订号 | `mch_store.version` |
| 申请内容 | 门店、商户主体、营业状态「待开通 → 营业中」 |

| 未通过 | `decide(storeNo, false, 原因)` → PENDING_OPEN / REJECTED，可重新提交 |

### T2 · 退款复核（near-pay）

| 项 | 内容 |
|---|---|
| 提交 | `RefundServiceImpl.open()` 命中 `RefundReviewPolicy`（无 ACTIVE 规则 = 全部复核，**上线前先发布规则**）→ 状态 PENDING_REVIEW、预占退款额 → 送审。不再写旧 `pay_approval` |
| 步骤 | 审核：`pay:refund:review` → 复核：`pay:refund:review`（替代旧一审 / 二审） |
| 修订号 | 新增 `pay_refund.review_revision`（今天的 `version` 是部分更新、不可靠） |
| 申请内容 | 退款金额、订单号、已付 / 已退 / 已预占金额、命中原因（单笔额、日累计、比例、超天数）、来源（B 端 / POS / 售后）、门店、原因 |

| 旧入口 | `/pay-ops/v1/refunds/{no}/review`、内部 `InternalPayOpsEndpoint` 复核、ai-shop 支付中心退款页「复核」按钮 → 改为「去审批」；旧 `ApprovalServiceImpl` 与三人互斥的数据库 CHECK 随 S4 删除 |

### T3 · 提现审批（near-pay）

| 项 | 内容 |
|---|---|
| 提交 | 商户申请提现 `WithdrawServiceImpl.apply()` → PENDING → 送审。**今天无调用方**（Q5） |
| 步骤 | 审核：`pay:withdrawal:review` → 复核（`overThreshold`：金额 ≥ 5,000 元，沿用代码里的 `REVIEW_THRESHOLD`） |
