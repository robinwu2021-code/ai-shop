# TDD · C 端选地址，不选自提点

状态：**方案待确认** · 创建 2026-09-17 · 档位 2（跨端 + 不可逆的产品决策）
关联需求：[PRD-位置与经营范围](../requirements/PRD-位置与经营范围.md)（§A20 与本方案冲突，见 L4）

---

## L1 定位

**一句话：买家选的是「我在哪」，不是「我去哪儿取货」。自提点是履约的实现细节，下单时按规则匹配。**

今天反过来了：买家必须先挑一个自提点，挑完才算「绑定」，绑定之后才看得到货。
这条链路把一个**履约期**的决定提到了**逛之前**，代价是三件事：

1. 没有自提点的聚落，买家**绑不上、也就看不到货**——静默，无任何提示；
2. 「地址 → 聚落」那条已经接好的线，最后一步被迫替用户挑了个自提点（`pickups[0]`），
   而自提点决定履约服务费归谁——**佣金归属今天由数组顺序决定**；
3. 没选位置的人看到的是**全平台的货**（社区池过滤被跳过），看得到、买不到。

## L2 结构

### 现状实测（2026-09-17）

| 事实 | 出处 |
|---|---|
| 绑定必须成对：`bindCommunity(communityNo, pickupNo)`，且校验点属于该社区 | `UserServiceImpl#bindCommunity` |
| C 端「绑没绑」的判据是**有没有自提点** | `community.ts` `bound: (s) => !!s.pickup` |
| 地址推导聚落后，端上取 `c.pickups[0]` 凑成对；**没有点就整个不绑** | `location.ts#syncCommunityFromActive` 的 `if (c && p)` |
| 可见性认 `communityNo`（社区池），**与自提点无关** | `GoodsServiceImpl` 按 `prd_community_pool.community_no` 过滤 |
| 履约服务费认**订单上的** `pickupNo`，为空即无此费 | `SettleServiceImpl:150` |
| `communityNo` 为空时**不加任何社区池过滤** | `GoodsServiceImpl:95` |
| 下单时 `pickupNo` 由端上传入，后端只校验「存在」与「这家店服不服务」 | `OrderServiceImpl#requirePickupPointWhenPickup` / `#requirePickupServed` |

**数据层本来就是对的**：可见性挂聚落、佣金挂订单上的点。错位全在
「C 端交互 + 那个必须成对的绑定接口」这一层，改动不触及结算与分账口径。

### 目标模型

```
收货地址（用户选，地图上有就能选）
      │  坐标
      ▼
  resolve → 最内层聚落        ← 可见性的唯一输入（社区池）
      │
      ▼
  下单 · 履约方式=自提
      │
      ▼
  自提点自动匹配（后端）      ← 佣金归属，落在订单上
      │
      ▼
  买家可改（「换一个取货点」，不是必经步骤）
```

三条不变量：

- **可见性只认聚落**，不认自提点；聚落没有自提点不影响看货，只影响「能不能选自提」。
- **自提点只在履约期存在**，且只落在订单上（已快照，历史单不受影响）。
- **规则只有一份**，在后端。端上不再有任何「挑哪个点」的判断（见 T9 的教训：
  预览与判定各写一套，两个数字都对，只是算的不是同一件事）。

## L3 详情

### M1 · 绑定解耦（后端）

`bindCommunity(communityNo, pickupNo)` 的 `pickupNo` 改为**可空**：

- 传了：沿用今天的校验（点必须属于该社区）——B 端/运营端的既有调用不受影响；
- 没传：只写 `community_no`，`pickup_no` 置空。

`usr_account.pickup_no` **保留不删**：历史订单已快照，删列没有收益；
但它从此不再表示「我的自提点」，实体上标 `@Deprecated` 并写明新语义为空。

> ⚠️ 迁移：存量有 `pickup_no` 的用户**不清洗**。清了会让「我的」页面上那条
> 「我的取货点」凭空消失，而那不是这一单要传达的变化。让它自然为空即可。

### M2 · 端上「绑定」的判据换成聚落

- `community.ts`：`bound: (s) => !!s.community`
- `location.ts#syncCommunityFromActive`：`if (c && p)` → `if (c)`，`bind(c, p?)`
- 首页顶栏文案从「选择取货点」换成「选择位置」

### M3 · 删掉「选择社区自提点」页

`pages/community/index.vue` 的三个入口（`home`、`me`、`order-confirm` 的兜底跳转）
全部改指地址页。页面本身删除，`pages.json` 与界面清单同步。

> 保留一页「附近的取货点」作为**只读**信息（从「我的」进）——
> 它回答「我这一带有哪些点」，但不再是一次选择。**这一条待定，见 L4 Q2。**

### M4 · 自提点匹配（后端，新接口）

```
POST /mp/order/preview  （已有）→ 返回体加 matchedPickup
GET  /mp/pickup/candidates?addressId=&merchantNos=  （新）→ 换点时列候选
```

匹配规则（**整单一个点**，理由见 L4 Q1）：

```
候选 = ⋂(每个商家的 allowedPickupNos，空集视为不限)
      ∩ status = ACTIVE
      ∩ 点所属聚落 ∈ 买家地址所在聚落的归属链（自己 + 父级）
排序 = 距买家地址最近（Geo.meters，与围栏判定同一份）
     → 平手按 pickupNo 稳定排序
```

- 候选为空 → **点名是哪一家**没有可用的点（与「送不到要点名」同一条规矩），
  并给两条出路：换履约方式 / 把那件商品移出本单。
- 匹配到的点在确认页**显示出来**并可改；改的是这一单，不写回用户档案。

### M5 · 位置未知时看什么

今天是「全平台的货」，这是过滤被跳过的副作用，不是决定。本方案改为：

- 有定位 → 用当前位置 resolve（T 系列已实现）；
- 拿不到定位、也没有地址 → **仍然显示商品**（空屏赶人），但：
  - 顶栏明确写「未选择位置 · 以下商品不一定送得到」；
  - 商品卡不显示配送时效（那个数在未知位置下是假的）；
  - 下单时必须先选地址（`needAddress` 闸已存在）。

> 这一条是**产品取舍**，不是技术必然。另一条路是空态直接要位置，转化更差但更诚实。
> 见 L4 Q3。

## L4 边界

### 与 PRD 冲突的条目（要改）

| 条目 | 现在写的 | 改成 |
|---|---|---|
| A20 | 自提下单：自提点来自归属链并集，**选定的那个**决定订单 communityNo 与佣金归属 | 自提点**由后端匹配**；订单 communityNo 来自**买家地址**所在聚落；佣金仍挂订单上的点 |
| §6.1 的选点流程 | 定位 → 选社区 → 选自提点 → 绑定 | 定位/选地址 → 解析聚落 → 绑定；自提点下单时匹配 |

### 待拍板

| # | 问题 | 选项 |
|---|---|---|
| Q1 | 多商家拆单，自提点是**整单一个**还是**按子单各配一个** | A 整单一个（交集为空就点名那家）· B 按子单（数据层已支持，但买家要跑两个点） |
| Q2 | 「附近的取货点」这一页留不留 | 留作只读信息 · 一并删掉 |
| Q3 | 位置未知时首屏 | 照显商品 + 明确标注（M5）· 空态直接要位置 |

### 不做

- **不动结算口径**：履约服务费仍认订单上的 `pickupNo`，一行不改。
- **不清洗** `usr_account.pickup_no` 的存量值。
- **不碰** B 端的取货点配置与运营端的自提点管理。

### 验收判据（每条对一个测试）

1. 聚落**没有任何自提点**时，买家仍能绑定该聚落并看到货 —— 今天这条是红的；
2. 地址推导绑定时**不写** `pickup_no`；
3. 自提下单不传 `pickupNo`，后端匹配出一个 ACTIVE、且这家店服务的点；
4. 候选为空时报错**点名商家**，不是笼统的「没有可用取货点」；
5. 匹配结果可改，改动只落这一单、不写回用户档案；
6. 位置未知时首屏不再无声地展示全平台商品（按 Q3 的结论断言）；
7. **消融**：把匹配规则改回「取候选第一个」，判据 3 或 4 必须变红。
