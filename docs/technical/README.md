# 技术文档索引

> 2026-08-11 重整。**每一篇技术文档都必须出现在本页**（守卫：`packages/shared/tests/doc-standard.test.ts`）。
> 不在索引里的文档等于不存在 —— 重整前有 28 篇没有任何入口，其中 17 篇是仍然有效的运营端设计。

## 先看这个：怎么找到「当前有效的那一份」

本目录曾经是 108 篇平铺，没有索引、53 篇没有状态行、同一主题最多 9 份平行文档。
代价是具体的：**本次重整前，有人（我）照着一份过期文档断言「类目上架校验没接」，
而代码里 `requireCategoryAuthorized` 早就在跑。** 文档没骗人，是没人说得清哪份算数。

所以现在按**生命周期**分四层，而不是按主题：

| 目录 | 是什么 | 能不能拿它判断现状 |
|---|---|---|
| [`ADR/`](./ADR/) | **决策**：为什么选 A 不选 B | 能。决策不会过期，被推翻时由新 ADR 修订旧 ADR，正文不改写 |
| [`reference/`](#一reference--长期查阅与真源投影) | **现状投影**：ER 图、表清单、枚举清单、矩阵 | 能，且优先。多数由脚本从真源生成 |
| [`design/`](#二design--各域方案活文档) | **方案**：某个域要做成什么样、怎么做 | **看状态行**。「待决策 / 待评审」的不代表现状 |
| [`archive/`](#三archive--一次性产物) | **一次性产物**：对齐清单、实测清单、核查报告 | **不能**。完成即过期，只用于追溯当时的判断 |

三条规矩：

1. **新增技术文档必须写状态行**（`> 状态：...`），并加进本索引。规范见 [文档规范](../文档规范.md) §四。
2. **一次性产物直接放 `archive/`**，不要放 `design/` —— 混在一起是上一轮失控的起点。
3. **同一主题多份时，以状态行最新且最具体的那份为准**；确定某份已被取代，在它抬头加一行指向接替者，不要删（删掉之后，读旧代码的人会找不到当时的依据）。

## 关于「同主题多份」：读过之后的更正

重整时我按文件名聚类，判断「积分 7 篇、商家主数据 13 篇需要合并」。**读过内容之后这个判断不成立**，
如实更正：

- **积分**：7 篇里 3 篇抬头就写着「已归档」「已并入」（写于信用/负债模型时期，2026-08-06 改预付费后作废），
  它们只是**放错了位置**，已移入 `archive/`。剩下 4 篇各有分工，不该合并：
  [完整方案](./design/积分域-完整方案.md)（为什么这么设计）·
  [接口与核心逻辑](./design/积分域-接口与核心逻辑设计.md)（行为，待评审）·
  [资金补差](./design/积分抵扣的资金补差-方案.md)（待决策，P0）·
  [跨店权益](./design/跨店权益-积分与优惠券-方案.md)（待确认）
- **商家主数据与门店**：13 篇里 2 篇「已并入」（同样移入 `archive/`），其余是**不同主题**
  （主数据 / 多门店 / 账号与多执照 / 经营模式双轨 / 安全整改 / 类目树），不是同一件事的 13 个版本

**教训记在这里**：按文件名判断重复会高估，按抬头判断才作数 —— 而抬头能作数的前提是每篇都有状态行。
这正是「新增文档必须写状态行」那条守卫要守住的东西。

真正剩下的是 **56 篇没有状态行**（基线只降不升）。补一篇要确认它到底落地没有，
属于逐篇评审，不是脚本能编的。
