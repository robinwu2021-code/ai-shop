# 进销存独立服务 · 设备套上线与回滚手册

状态：**可执行**（2026-10-29；执行方案 M6）

> 对应执行方案 M6（T6.1 ~ T6.4）、ADR-046、TDD §2.18。
> 设备套 = 实例 `DEVICE`、库 `neargo_inv_device`、端口 8087，放行 `SHAREHUB,CHARGING`。
> 电商套（`SHOP`）M8 才上线，本手册不涉及；设备套任何操作都**不碰** `ai_shop_inv`。

## 一、上线前检查

| # | 检查 | 怎么做 | 不过就 |
|---|---|---|---|
| 1 | 端口空闲 | `ss -ltn \| grep -E ':8087\b'` 无输出 | 换端口并同步改 env 与 ShareHub 配置 |
| 2 | 生产形态演练已做 | 测试机临时起 `SHOP` + `DEVICE` 两套、两个库，跑 G1、G2、AC-28 | 不上线 |
| 3 | 迁移批次预演过 | 测试环境 `imports?apply=false` → 评审报告 → `apply=true` → 再 `apply=true` 报告为空 | 不上线 |
| 4 | 回滚路径可用 | ShareHub 旧仓储模块代码仍在、开关可切回 | 不上线 |

## 二、上线步骤

1. **建库与账号**

   ```sql
   CREATE DATABASE neargo_inv_device DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
   CREATE USER 'neargo_inv_device'@'127.0.0.1' IDENTIFIED BY '<另存密码管理器>';
   GRANT ALL ON neargo_inv_device.* TO 'neargo_inv_device'@'127.0.0.1';
   ```

   **同一步**把 `neargo_inv_device` 加进 `deploy/tencent/backup-to-cos.sh` 的 `DBS`（漏备一个库的事故
   2026-09-16 与 2026-09-30 各发生过一次）。当晚确认 COS 上出现 `neargo_inv_device-<日期>.sql.gz`。

2. **放程序与配置**：`/data/app/neargo/inventory-device/` 下放 `inventory-svc.jar` 与 `inventory.env`
   （样例 `backend/inventory/deploy/inventory.env.example` 设备套那组，权限 600，真实值不进仓库）。
   单元文件 `deploy/tencent/systemd/neargo-inventory@.service` 装到 `/etc/systemd/system/`。

   ```bash
   systemctl daemon-reload && systemctl enable --now neargo-inventory@device
   curl -s 127.0.0.1:8087/actuator/health    # UP
   curl -s 127.0.0.1:8087/actuator/info      # instance.code = DEVICE
   ```

   首启在空库上跑全部 Flyway 迁移；日志 `/data/log/neargo/inventory-device/inventory.log`。

3. **开通业主**（平台运维接口，`X-Inventory-Admin-Token` + `X-Inventory-Actor`）：
   `POST /api/inventory/admin/v1/owners`（`systemCode=SHAREHUB`）→ `PUT …/profile` 装 ShareHub 档案 →
   `POST …/credentials` 签凭证（密钥只显示一次，直接进 ShareHub 的 env）。任务服务登记目标 `INVENTORY_DEVICE`（`127.0.0.1:8087`，密钥与 env 里的 `INVENTORY_JOB_TOKEN` 相同），确认它拉到 `inventory-device-reservation-expiry` 与 `inventory-device-daily-snapshot` 两个任务。

4. **ShareHub 指向设备套**：`127.0.0.1:8087`；启动自检比对 `/actuator/info` 的实例代号，不是 `DEVICE` 就拒绝启动。

5. **迁移**：`POST /api/inventory/admin/v1/owners/{ownerId}/imports?apply=false`，批次格式见
   `MigrationImportService.Batch`。报告里：
   - `warehousesToCreate` / `itemsToCreate` / `itemsToUpdate` / `targetsToUpsert`：将新建或更新的主数据；
   - `stock`：将按期初入库（`OPENING`，依据 `MIGRATION`）补进来的在仓；
   - `conflicts`：`<序列号>:in_stock_elsewhere`（设备已在别的仓）、`<仓>/<物料>:book_exceeds_batch`
     （账面多于批次）。**有冲突时执行会整批拒绝（409）**，先人工处理。

   报告评审通过后 `apply=true`；再跑一次 `apply=true`，报告必须为空 —— 这是迁移完成的判据。

6. **切单一写权**：ShareHub 旧仓储模块停写，仓储页改读写库存服务。

7. **观察 3 天**（见第三节指标）。

## 三、监控（T6.2）

`/actuator/metrics`，所有指标带 `instance` 标签；两套告警分开命名（`inventory-DEVICE-*` / `inventory-SHOP-*`）。

| 指标 | 含义 | 建议告警 |
|---|---|---|
| `inventory.events.pending` | 已提交、宿主还没来拉的事件 | > 500 持续 10 分钟：宿主拉取停了 |
| `inventory.events.unacked` | 拉走了、没确认的事件 | > 2000 持续 30 分钟：宿主确认坏了，快到保留期会 410 |
| `inventory.counts.open.oldest.minutes` | 最久的未关盘点（冻结库位）已开多久 | > 1440：盘点卡住，冻结的库位一直不能出入 |
| `inventory.holds.return_pending.oldest.minutes` | 最久的退货待确认 | > 4320：退货没人确认 |
| `inventory.errors{code,status}` | 按错误码计数的失败 | `status=409` 突增：冲突率；`status=5xx`：立即看 |

## 四、故障演练（T6.3）

自动化部分在 `inventory-svc` 的 `ResilienceDrillTest`（每次构建都跑）；人工部分上线前在测试机做一遍。

| 场景 | 预期 | 证据 |
|---|---|---|
| 回包丢失（同一命令号重发） | 返回第一次的结果，不重复过账 | 自动化 |
| 同一命令号换了内容 | 409 `inventory.idempotency_conflict` | 自动化 |
| 事件重放（游标回退重拉） | 拿到同一批事件、同一序号 | 自动化 |
| 应用重启 | 已提交的单据、事件、游标都在；未提交的不留半截 | 人工：`systemctl restart neargo-inventory@device` 前后比对 |
| 库停 | `/actuator/health` 变 DOWN、命令 5xx；库起来后自动恢复，不需要重启应用 | 人工：停 `mysql97` 30 秒 |

## 五、回滚

| 时机 | 做法 | 数据 |
|---|---|---|
| 第 6 步之前 | ShareHub 指回旧仓储即可；`systemctl disable --now neargo-inventory@device` | 设备套库可整库丢弃重来（空库起步，迁移可重复） |
| 第 6 步之后、观察期内 | ShareHub 切回旧仓储模块（第 6 步前的状态保留到观察期结束）；**这期间在库存服务上发生的出入库要在旧模块补录**，按 `GET /api/inventory/v1/events` 的事件逐条核 | 设备套库保留，作补录依据 |
| 观察期之后 | 不再回滚，按故障修复处理 | — |

设备套停机**不影响电商**：商城在 M8 之前仍内嵌直连 `ai_shop_inv`，与设备套没有任何调用。
