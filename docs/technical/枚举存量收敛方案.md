# 枚举存量收敛方案（P4 / P5）

> 2026-08-10 · 前置：[命名规范与实施方案](命名规范与实施方案.md) 的 P0–P3 已完成，
> 约束已就位（登记表 115 条 + 5 条守卫）。这一份处理剩下的存量。

---

## 1. 先说一个问题：登记表现在有一部分在说谎

| | 条数 |
|---|---|
| 登记表总数 | 115 |
| 标了待办（RENAME / MERGE / TO_DICT / PLANNED） | 19 |
| 标了 `OK` | 96 |
| **96 条 `OK` 里带 `note` 的** | **4** |

`OK` 现在同时表示两件事：

- **「看过了，没问题」** —— 大约 28 条（P0 手工标注 + P1.2 新建时逐条写的）
- **「种子脚本默认填的，没人看过」** —— 大约 68 条

这两件事在数据里**分不开**。而一份把「没人看过」显示成「没问题」的登记表，
比没有登记表更危险 —— 它会让下一个人以为已经盘过了。

> 这正是词典曾经犯的病：**默认值伪装成结论**。
> 上一轮把词典从描述性改成规定性，这一轮要把登记表从「乐观默认」改成「诚实默认」。

**这也解释了为什么 P1.2 能挖出四个问题**：那 24 处内联的枚举从没被任何人看过，
而它们里面藏着两对异名同义、一处重复声明、一个自我引用的 interface。
剩下这 68 条未复核的，大概率是同一种情况。

## 2. P5-0 · 让进度可统计（先做，无风险）

### 2.1 引入 `UNREVIEWED`

```ts
export type Verdict =
  | "OK"          // **人看过，确认合规**
  | "UNREVIEWED"  // 种子默认值，还没人看过 ← 新增
  | "RENAME" | "MERGE" | "DELETE" | "TO_DICT" | "PLANNED";
```

把所有没有 `note`、且不在 P0/P1.2 手工标注名单里的条目改成 `UNREVIEWED`。
**判据要保守：拿不准的一律算未复核。** 宁可多复核一条，不可漏判一条。

### 2.2 加一条棘轮守卫

`UNREVIEWED` 的数量**只许降不许升**（写死当前基线，随复核推进逐次调低）。

为什么用棘轮而不是「必须为 0」：68 条不可能一次做完，而设成 0 会让人
把它改成 `OK` 了事 —— 那就退回今天的状态。棘轮让进度单向前进且可度量。

### 2.3 产出

一份 `UNREVIEWED` 清单，按领域分组，可以分批、可以分人。

## 3. P5 · 逐条复核（68 条）

### 3.1 复核一条要回答五个问题

| # | 问题 | 判定 |
|---|---|---|
| 1 | 这个概念在别处有没有第二个名字？ | 有 → `MERGE` |
| 2 | 这个名字在别处有没有指别的东西？ | 有 → `RENAME` |
| 3 | 取值域后端认不认？（wire 契约的话） | 不认 → `PLANNED` 或修 |
| 4 | 库里有没有一张带业务规则列的表装它？ | 有 → `TO_DICT` |
| 5 | 状态词是否取自 L1 表？领域特有词是否申报了？ | 否 → 改词或申报 |

前两问必须**跨端查**（这一轮所有 X/Y 类缺陷都只有把三端放一起才看得见）。
第 4 问的判据已定：库里那张表除了码还有别的列（`enabled`/`sort`/通道码/费率）就是字典。

### 3.2 按领域分批（数据来自登记表）

| 批 | 领域 | 条数 | 备注 |
|---|---|---|---|
| A | `core`（shared/types 主文件） | 12 | 最杂，但也最可能藏跨端重复 |
| B | `payment` + `settle` + `finance` | 13 | **涉及金额，只出报告不改代码** |
| C | `merchant` + `store` | 12 | 与 P4 的主体类型问题连着 |
| D | `content` + `review` + `risk` | 13 | ops-web 独有为主，多数是 PLANNED |
| E | `marketing` + `growth` + `group` | 10 | 与 P4 的活动/场次问题连着 |
| F | `fulfillment` + `community` + `order` + `aftersale` | 15 | 交易主链路，改动要浏览器实测 |
| G | `ui` + `infra` + `auth` + `dashboard` + `message` + `product` | 21 | 多数是 C 类（端上概念），最快 |

**建议顺序：G → D → A → F → C → E → B。**
先做纯机械的建立节奏，把涉及钱的放最后且只出报告。

### 3.3 每批的验收

1. 该领域 `UNREVIEWED` 归零
2. 四层回归绿
3. **若有改名，浏览器实测受影响页面** ——
   这一轮 i18n 键名泄漏出现过四次，其中一次是改状态词时自己制造的

## 4. 三条独立的线

### 4.1 结算单状态对账（只读，不动代码）

| 位置 | 取值 |
|---|---|
| 后端 `StlBill` | `PENDING` `SPLITTING` `SPLIT` `FAILED` `FROZEN_BACK` |
| ops-web `SettleStatus` | 同上 ✅ |
| **shared `SettleBillStatus`** | `PENDING` `PARTIAL` `DONE` `EXPIRED` ⚠️ |

**一个词都对不上**，而它内联了几个月，对所有工具不可见。

按 finance 的既有惯例：先出对账报告，回答三个问题 ——
① B 端结算页现在按 `PARTIAL`/`DONE` 筛，真实环境下是不是恒空？
② 后端的 `SPLITTING`/`SPLIT` 与端上的 `PARTIAL`/`DONE` 是不是同一组语义？
③ `EXPIRED`（结算单过期）后端有没有对应概念？

**不动任何与金额相关的代码。**

### 4.2 P4 · 四个需要业务确认的问题

| # | 问题 | 卡住了什么 |
|---|---|---|
| 1 | 店铺级活动与平台投放场次要不要合并成一张表？ | `CampaignType`/`CampaignStatus` 是改名还是合并（4 条待办） |
| 2 | `sys_legal_form` 的取值域会不会随通道政策变？ | 主体类型是改名收敛还是改走字典下发（2 条） |
| 3 | 商品状态挂 SPU 还是 SKU？ | `GoodsStatus` / `SkuStatus` 的分层（2 条） |
| 4 | `MerchantStatus` 改名要回归入驻全流程 | 影响 B 端首页判断（1 条） |

问题 1 与 2 若长期得不到答复，建议**按不合并 / 会变**处理 ——
两者都是「多做一点、错了容易改回来」的方向。

### 4.3 「营销活动建了不生效」

不是枚举问题，是一整条链路缺了后半段（后端交易链路完全不读 `mkt_campaign`），
而商家侧界面已经上线。见 [营销枚举对账报告](营销枚举对账报告.md) §2。
**优先级应高于本文全部内容** —— 它现在就在影响真实商家。

## 5. 明确不做的

- **不为了让 `UNREVIEWED` 归零而批量标 `OK`。** 那等于把今天的问题再犯一遍。
- **不在复核阶段顺手改名。** 复核只判定，改名单独走 —— 混在一起会让一次提交
  同时包含「判断」和「改动」，出问题时分不清是判断错了还是改错了。
- **不动金额相关代码**，直到对账报告有结论。

## 6. 建议的下一步

按依赖关系，**P5-0（诚实默认 + 棘轮守卫）应该最先做** ——
它无风险、当天可完成，且做完之后所有后续工作才有可度量的进度。

之后两条线可以并行：批次 G→D→A（机械复核）与 4.1（结算对账报告）。
P4 的四个问题在等答复期间不阻塞其余工作。
