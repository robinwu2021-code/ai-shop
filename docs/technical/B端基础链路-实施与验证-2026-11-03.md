## 已实施

- 手机号 OTP 登录即注册，首次档案与冷启动统一使用可信 USR／MCH 身份；CTK／BTK 分池，注销撤销当前商家会话。
- 首店按发布的经营类型创建，同事务初始化首次 FREE；重试不重复发放、不替换历史绑定版本。分店沿用 operationNo 幂等。
- 申请、协议、证照、收款进件沿用现有业务服务。所选主体和门店、成员与岗位必须一致；新模型和纯旧模型、commerce 开关两态均覆盖。外部通道调用前校验目标。
- 新增 GET `/biz/business-types`、`/biz/business-types/{typeCode}/plans`、`/biz/stores/{storeNo}/context`、`/subscription`、`/entitlements`。单端 `/end-access` 保持旧合同。
- 商家仅看到当前公开三档及安全价格投影；未发布且未持有的端不展示。已持有来源即使退役仍保留过期／冻结事实，员工不读取实付及折算基数。全部 purchaseAvailable=false。
- 本轮没有新增或改写 DDL，commerce V1–V5 和宿主 V554 保持原样。宿主使用公开 API／starter，独立 commerce 构建不依赖宿主。

API 交付以 [B 端基础链路对接文档](../api/B端基础链路-对接文档.md) 和 [请求响应 JSON](../api/examples/b-foundation.json) 为准。旧规划清单不表示其中全部路径已实现。新读接口时间为 epoch 毫秒，旧单端接口仍为 ISO 时间；旧主体额度 Plan 不是门店商业 Plan。

## 实施裁定及代价

1. 显式 B 端申请选店始终有约束力，不受建店开关影响；未选店旧请求只认当前有效属主且无歧义的纯旧候选。原因是避免选 A 实际修改 B。代价是多候选或选错主体的客户端须选择正确待补证店并重试。
2. 三档均有当前发布版本且 FREE 可初始化时，付费档停售保留卡片，不隐藏整个经营类型；停售价格不展示。原因是停售付费档不应阻断 FREE 开店。代价是 B 端须渲染不可购买卡片，未来下单仍要重新核价。
3. 纯 LEGACY 无头财务请求可以用明确的 path／query／body 分店作为候选，但同时通过原默认店方法级岗位和目标店当次财务权限；所有显式目标须一致，无目标列表只给主体默认行和当前授权默认店。原因是保留合法旧分店结算而不借 A 权限处理 B。代价是旧客户端不再获得全主体列表；仅在目标店有权时须显式传该店 X-Store-No。STORE_V1 仍须严格选店头。

B 端协议继续采用“本人最近申请与当前主体精确匹配”的既有口径。GET apply 是账号最新申请，不是各主体的申请历史；已有较早 A 申请而最新属于 B 时，不在 A 提示或接受 B 的协议。没有主体时仅可确认本人 entity_no=NULL 的初始申请，失去成员权限不能借空选择签署原主体。C／ops 单参数协议合同保持原样。

## 运行及交接边界

- 默认不启用新模型；真实目录须先发布完整三档、启用经营类型，部署使用同一主库事务管理器、DB 商家会话及服务端签名密钥。已有 STORE_V1 不能通过关闭模块绕回旧模型。
- 上线前仍需验证真实短信送达、支付商户开户回查、对象存储和 OCR。测试实际运行宿主服务，但外部支付使用可观测替身或开发 STUB；不把 STUB 的 ACTIVE 当生产收款资格。APPLE 旧分支签名缺口不在本轮安全验收内，B 端不能把它当已验收入口。
- 有界连接池在账户锁及独立 fresh 事务下的并发进展仍是上线前容量门槛；本轮串行和定向并发测试不代表生产负载验收。Flyway 版本、Mockito attach、编译及 mapper 告警保留维护。
- B 端接入时同步 `b-app/src/api/requests.ts:85`、`packages/shared/src/types/merchant.ts:681` 的旧账号描述，再生成 OpenAPI，防止覆盖本次修正。后端文档与示例已纠正共享个人身份、独立会话池和员工身份的区别。
- 交接目标为现有 B 端会话“整理 B 端文案与组件规范”（01a172c2-5a86-7721-a2f0-6080100f7f03）。后端分支、工作树和原始未跟踪设计输入保留，不推送、合并或部署；B 端页面接入结果由该会话继续验证。
