## 步骤 1 · 三处 archive 补在用检查（R3）

**为什么第一个做**：现在可以停用一个正被在售商品使用的规格值/维度。停用后商家
再保存一次商品，`resolveValueNos` 查不到（`valuesOf` 只取 ACTIVE），
`option_value_nos` 对应位变 null —— **跨店聚合从此漏掉这件商品，界面上看不出**。

### 1a 红测试先行

`backend/shop-app/src/test/java/ai/neargo/shop/scenario/CategoryTreeFlowTest.java` 加两条：

- `archiveValueInUseIsRejected`：建品用了某档 → ops 调
  `POST /ops/spec-values/{valueNo}/archive` → **期望 4xx**，错误码 80016；
  把那件商品逻辑删掉 → 再 archive → 成功。
  **现在会红**（archive 直接成功）——先跑一次确认红，再动实现。
- `archiveMerchantDimInUseIsRejected`：商家自建维度 + 建品用上 →
  `POST /biz/my-spec-dims/{dimNo}/archive` → 期望 4xx；删商品后成功。

### 1b 实现

`ErrorCode.java` 加（错误信息要说清**下一步做什么**，不是「操作失败」）：

```java
SPEC_IN_USE(80016, "err.spec.in_use"),
```

i18n 词条（后端 messages 里，`BackendI18nParityTest` 会守三语齐全）：
中文口径「仍有 N 件在售商品使用该规格，先调整商品或下架后再停用」。

`SpecLibraryServiceImpl` 加一个私有方法，三处 archive 在 `archived=true` 时调
（**unarchive 不查** —— 恢复永远该被允许）：

```java
/**
 * 这个值/维度还有没有在售商品在用。**只挡停用，不挡恢复。**
 *
 * 判据是 prd_sku.option_value_nos 的 JSON 边界匹配：值编号在数组里带引号
 * （["SV_X","SV_Y"]），LIKE '%"SV_X"%' 因引号封边不会误命中前缀相近的编号
 * （SV_COUNT_C1 vs C12 那个坑，见设计 §3.7）。维度级则匹配
 * spec_groups 的 "templateNo":"<dimNo>"。
 * 都只算 deleted=0 的行 —— 已删商品的快照不该拦住停用。
 */
```

- `archiveValue`：`prd_sku` 里 `option_value_nos LIKE '%"<valueNo>"%' AND deleted=0`
  计数 > 0 → 抛 `SPEC_IN_USE`。`prd_goods.params` 同法再查一遍
  （生产 params 现全 NULL，但这是防将来，不是防现在）。
- `archiveDim` / `archiveMerchantDim`：`prd_goods` 里
  `spec_groups LIKE '%"templateNo":"<dimNo>"%' AND deleted=0`。
  merchant 版**不要**加 `entity_no` 过滤 —— 自建维度理论上只有自己用，
  但判据宁可宽（万一有脏数据，宽的挡得住）。

⚠️ 两条 LIKE 都是全表扫。**可以接受，写明理由**：archive 是运营/商家的低频动作
（一天个位数），380~38 万行都无所谓；等倒排表建好（二期）换成索引查询，
这两处 LIKE 就是届时要删的记号 —— 在方法注释里写上「倒排表落地后改走它」。

⚠️ **判据先按 `deleted=0`（宽），步骤 6 落地后收窄为 `on_sale=1`**（设计 §4.6.4）：
收窄的前提是「草稿带着停用档上架时会被拦」，那道拦截在步骤 6 里。
先收窄后拦截的话，中间窗口期草稿能带着停用档直接上架。

### 1c 验证

- 两条新测试绿；全量零新增红
- **消融**：把 `archiveValue` 里的检查注掉 → `archiveValueInUseIsRejected` 必须红
  且红在「期望 4xx 实得 200」上；恢复后绿。写进提交信息。

## 步骤 3 · `prd_goods` 两条复合索引

**为什么两条**（设计 §6.1 有生产实测）：跳过中间列时优化器**整条索引都不用**，
不是「用一半再 filesort」。

新迁移（号现查，形如 `V27x__goods_list_indexes.sql`）：

```sql
-- C 端列表的两条热路径。deleted 在最前：@TableLogic 让每条查询都带 deleted=0。
-- 两条不能合一：不带 category_no 的查询在复合索引里跳列，sales 就用不上了
--（生产上拿 idx_stl_pool_channel 实测过：跳中间列 → 优化器整条放弃，见设计 §6.1）。
CREATE INDEX idx_goods_cat_sales ON prd_goods (deleted, on_sale, audit_status, category_no, sales);
CREATE INDEX idx_goods_sales     ON prd_goods (deleted, on_sale, audit_status, sales);
```

⚠️ **不写 `IF NOT EXISTS`**（可移植性闸门会拦）；**不写排序规则**（继承表的）。

### 验证

```bash
# 本地 MariaDB（ai_shop 库）跑迁移后：
EXPLAIN SELECT * FROM prd_goods WHERE deleted=0 AND on_sale=1
  AND audit_status='APPROVED' AND category_no='CAT110' ORDER BY sales DESC LIMIT 20;
-- 判据：key=idx_goods_cat_sales，Extra 无 filesort。type/rows 数字不作数（本地行数少）
EXPLAIN SELECT * FROM prd_goods WHERE deleted=0 AND on_sale=1
  AND audit_status='APPROVED' ORDER BY sales DESC LIMIT 20;
-- 判据：key=idx_goods_sales，无 filesort —— 这条就是「为什么要第二条索引」的证明
```

H2 测试库对索引无感，测试全绿不算验证 —— **必须看 MariaDB 的 EXPLAIN**。

## 步骤 5 · 类目树 / 平台值池缓存 —— Spring Cache 抽象 + ehcache 实现

**方案（2026-08-30 拍板）**：接 **Spring Cache 抽象**（`@EnableCaching` +
`@Cacheable` / `@CacheEvict`），实现用 **ehcache**，将来要换 Redis/Caffeine 时
只换 `CacheManager` 那一个 bean，业务代码上的注解一行不动 —— 这正是引抽象的意义。

**不引任何新依赖**（步骤 0 核对过）：

- `@EnableCaching` 与 `CacheManager` 接口在 `spring-context` 7.0.8 里，
  starter-cache 只是自动装配的便利，不需要
- ehcache 3.12.0 已在 `shop-base` 依赖树（`AuthCache` 在用）。
  ⚠️ **pom 注释里有一颗埋好的雷，沿用时别踩**：classifier 必须是 `jakarta` ——
  默认包用 javax.cache，Spring Boot 4 下报的是看不出根因的
  `NoClassDefFoundError: javax/cache/...`。现有依赖已经是 jakarta 的，别另引一份

### 5a 装配

`shop-app` 的 config 包新建 `CacheConfig`：

```java
@Configuration
@EnableCaching
public class CacheConfig {
    /**
     * Spring Cache 的 ehcache 适配。**不走 JCache 桥**（那要多引 cache-api），
     * 直接用 ehcache 3 的编程式 API —— 与 AuthCache（shop-auth-store）同一条路。
     *
     * 将来换实现（Redis/Caffeine）只换这个 bean；@Cacheable 注解不动。
     *
     * 单机缓存的前提：生产是单实例部署（scp jar + systemd）。
     * 多实例那天这里换 RedisCacheManager，失效才能跨实例 —— 到时这条注释就是入口。
     */
    @Bean
    public CacheManager cacheManager() { ... }   // 实现 Spring 的 Cache/CacheManager
                                                  // 包一层 ehcache heap 缓存，~60 行
}
```

缓存区两个，TTL 都给 **30 秒**（类目树与平台值池的变更频率是「运营偶尔动一次」，
30 秒陈旧完全可接受；TTL 兜底意味着就算失效链路漏了，最坏也只错 30 秒）：

| cache 名 | 缓存点 | 失效点（`@CacheEvict(allEntries=true)`） |
| --- | --- | --- |
| `categoryTree` | `CategoryServiceImpl.tree()` | 运营改类目（save/move/archive） |
| `specLibrary` | `SpecLibraryServiceImpl` 平台维度+值池的读取 | `saveValue` / `archiveDim` / `archiveValue` / `mergeValues` / `saveCategorySpecs` |

**宁可失效过度**（`allEntries=true` 整区清掉）也不做按 key 细粒度失效 ——
细粒度失效的每个漏网之鱼都是一个「运营改了半天不生效」的工单，
而这两个缓存区整个重建的成本是几条 SQL。

⚠️ **商家覆盖（`prd_merchant_spec_override`）不缓存**：按商家分散、命中率低，
且商家自己改自己读，陈旧 30 秒会直接被本人看见。缓存只进「平台层」——
所有人共享、极少变，才是缓存该待的地方。

### 5b 验证

- 连续两次调类目树，MyBatis 日志第二次 **0 条 SQL**
- **消融**：把 `@Cacheable` 注掉 → 第二次必须重新出 SQL —— 否则测的是别的东西
- 失效链路：运营改一次类目绑定 → 立刻读 → 新数据
- `DeploymentProfileTest` / `ControllerProfileTest` 全绿（`@EnableCaching`
  会给 Service 生成代理，装配相关的守卫要确认没被波及）

## 步骤 6 · 上架编译点：过审/上架时重解析 + 重烘焙（设计 §4.6）

**为什么**：`save()` 已经会把在售商品自动下架送审（V247），但烘焙只发生在保存
那一刻 —— 草稿放两周再上架，其间平台改文案、停档位，**上架时没有任何一处会发现**。
把「重解析 + 重烘焙」挂在编译点上，上架产物才必然与当时的规格库一致。

### 6a 红测试先行

`CategoryTreeFlowTest`（或新建 `GoodsPublishFlowTest`）两条：

- `publishRefreshesSnapshotFromSpecLibrary`：建品存草稿 → 运营改该维度的平台文案
  → 商家 `toggle(true)` 上架 → 断言 `spec_groups` 里的文案是**新**的。
  **现在会红**（toggle 只翻状态位）。
- `publishRejectsArchivedValueWithDetail`：建品存草稿 → 运营停用其中一档
  （步骤 1 收窄后草稿不挡停用）→ 上架 → **期望 4xx**，错误信息**点名那一档**；
  商家改掉该档 → 上架成功。

### 6b 实现

抽一个 `bakeForPublish(PrdGoods g)`，两个入口都调（**同一段代码，不是两份**）：

- `toggle(merchantNo, goodsNo, true)` —— 三道闸之后、写库之前
- 过审恢复上架那段（`:2015` 附近，`pendingOnSale` 兑现之前）

做三件事：① `spec_groups` 逐组逐档 `resolveValueNos` 对当前规格库重解析，
解析不出收集起来一次性抛（新错误码，信息含档位文案清单 —— 别解析到第一个就抛，
商家要一次看到全部问题）；② 文案按当前合并结果重写，身份列同步刷新；
③ SKU 的 `option_values` / `option_value_nos` 同事务重写。

⚠️ 三个别做错：**已在售商品再次 `toggle(true)` 是幂等的**（快照没变就不重写，
免得每次上架都动 `updated_at`）；**下架（`toggle(false)`）不烘焙**（快照保留给
历史订单）；**审核驳回不烘焙**（商品回编辑态，烘了白烘）。

### 6c 收窄步骤 1 的在用检查

本步落地后，把步骤 1 的三处判据从 `deleted=0` 收窄为 `on_sale=1`，
并更新步骤 1 测试（草稿引用不再挡 archive，改成断言「草稿不挡、上架被拦」）。
这半步与 6b **同一次提交** —— 分开的话中间状态是「两头都拦」或「两头都不拦」。

### 6d 验证

- 两条新测试绿；全量零新增红
- **消融**：把 `bakeForPublish` 里的重解析注掉 → `publishRejectsArchivedValueWithDetail`
  必须红在「期望 4xx 实得 200」；把重烘焙注掉 → `publishRefreshes...` 红在文案断言
- 幂等：同一商品连续 `toggle(true)` 两次，第二次 `updated_at` 不变
