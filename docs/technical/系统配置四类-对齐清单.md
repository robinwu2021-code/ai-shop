## 1. 为什么这四个一起做、且排在最前

零依赖、纯键值读写，**不建表**（全部落已有的 `sys_setting`）。
做完 `feature-flags` 就位 —— 后面几个域可以带开关灰度上线，
而不是「合并即全量生效」。

同一个页面上的 `auth-codes` / `industries` / `service-scopes` **后端已有**，
不动它们。

## 2. 对齐清单

### 2.1 数据库：不建表

四类各占 `sys_setting` 一行：

| key | 值形状 |
|---|---|
| `platform.appearance` | 对象 |
| `platform.feature-flags` | 数组 |
| `platform.rule-texts` | 对象（**带版本**，见 §3） |
| `platform.markets` | 数组 |

`sys_setting` 已有 `updated_at` / `updated_by`，前端要的
`updatedAt` / `updatedBy` 直接来自这两列 —— **不用把它们塞进 JSON**
（塞进去就有两份，且必然对不上）。

### 2.2 API（照抄 ops-web 现有调用）

| 方法 | 路径 | 权限 |
|---|---|---|
| GET | `/ops/appearance` | `industry:manage` |
| POST | `/ops/appearance` | `industry:manage` |
| GET | `/ops/feature-flags` | `industry:manage` |
| POST | `/ops/feature-flags/{key}` | `industry:manage` |
| GET | `/ops/rule-texts` | `industry:manage` |
| POST | `/ops/rule-texts` | `industry:manage` |
| GET | `/ops/markets` | `industry:manage` |
| POST | `/ops/markets/{code}/rate` | `industry:manage` |

⚠️ **权限码用 `industry:manage` 是将就**：现有 14 个码里没有「平台配置」这一类，
而这四类改的是全平台的行为（皮肤、开关、协议文案、汇率），
比「维护行业主数据」重得多。

> 两个选择：(a) 先用 `industry:manage`，(b) 新加 `platform:config`。
> **建议 (b)** —— 汇率和灰度开关不该和行业启停共用一把钥匙。
> 这是要你定的第一件事。

### 2.3 对象

后端新增四个 VO，**字段名逐个对齐 ops-web 的类型**
（`AppearanceConfig` / `FeatureFlag` / `RuleTexts` / `MarketConfig`）。
今晚已经踩过两次命名错配（`title` vs `name`、裸数组 vs 分页包），
症状都是「接口 200、页面空白」。

### 2.4 Controller / Service / Mapper

| 层 | 改动 |
|---|---|
| Controller | 新建 `OpsPlatformConfigController`，8 个端点 |
| Service | 新建 `PlatformConfigService` + impl，读写走 `SettingService` |
| Mapper | **不用动** —— `sys_setting` 已有 |

## 3. `rule-texts` 必须留版本

其余三类覆盖式保存即可，**规则文案不行**：

用户同意的是**某一版**协议。覆盖之后「他当时同意的是什么」永远查不回来，
而这正是纠纷时唯一有用的东西。

做法：`platform.rule-texts` 存**当前版**，另开一个键
`platform.rule-texts.history` 存历史数组（每次保存前把旧值追加进去，
带 `version` / `updatedAt` / `updatedBy`）。

> 不新建表：一期文案改动是低频操作，几十条 JSON 数组够用。
> 真正到了要按用户查「他同意的哪一版」时，需要的是**订单/用户侧存版本号**，
> 那是另一件事，本批不做（登记）。

## 4. mock 里已经定死的规则 = 需求

后端要逐条实现，**不能比 mock 宽**（今晚一半缺陷都源于这个）：

| 规则 | 出处 |
|---|---|
| 默认皮肤必须是 `SKIN_KEYS` 之一 | `mocks/system.ts:95` |
| 节日皮肤取值合法、且**结束晚于开始** | `:96,98` |
| 基准货币 `CNY` 汇率恒为 1，**不可改** | `:111` |
| 汇率必须 > 0 | `:113` |
| 三条规则文案**都不能为空** | `:124` |
| 灰度比例 0–100 | `:134` |

皮肤取值来自 `packages/shared` 的 `SKINS` —— 后端要能拿到这个清单。
**不在后端另抄一份**（两份同值常量必然分叉，今晚已经修过两次）：
做法是后端只校验「非空 + 在前端下发的允许集合内」，
或把皮肤清单也放进 `sys_setting`。**这是要你定的第二件事。**

## 5. 做什么 / 不做什么

### 做
1. `PlatformConfigService` + 8 个端点 + 权限 + 审计留痕
2. 四类的默认值（没配过时返回它 —— 参数表少一行不该让页面打不开）
3. `rule-texts` 的历史版本
4. 六条校验
5. 从 `UNBUILT_DOMAINS` 移出这四个，剩余缺口登记进 `KNOWN_GAPS`
6. `perm-map.ts` 里 `system:*` 从 `UNIMPLEMENTED` 换成真码
7. 测试

### 不做（登记）

| 不做 | 为什么 |
|---|---|
| `feature-flags` 真的影响后端行为 | 本批只做**配置的读写**。让某个开关真的控制某段逻辑，是那段逻辑自己的事 |
| 按用户查「他同意的哪一版协议」 | 要在订单/用户侧存版本号，另一件事 |
| 多市场真的生效（按 market 切库存/价格） | 市场维度的落地是独立一批 |
| C 端读这些配置的端点 | ops-web 先能配；C 端消费是下一步 |

> ⚠️ 与数据域那批同一个风险：**配了不生效**。
> `feature-flags` 尤其明显 —— 运营把开关关了，而代码里没人读它。
> 所以要么在 UI 上标明哪些开关**已被代码消费**，要么本批就把消费方接上。
> **这是要你定的第三件事。**
