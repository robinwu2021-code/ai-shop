# 类目树补齐方案

> 2026-08-10 · 决策：**补齐**（另一个选项是删掉 `prd_category`，已否决，理由见 §一）
> 上游：[三端全栈对齐清单](./三端全栈对齐清单.md) · [交付计划-商家侧](../requirements/交付计划-商家侧.md)

---

## 零、先说清楚：系统里有**两套**分类，它们不是重复

这是这件事一直悬着的根本原因 —— 看上去像同一个东西做了两遍，其实是两个正交维度。

| | `prd_goods.type` | `prd_category`（本方案补齐的） |
|---|---|---|
| 是什么 | 五值枚举 `NORMAL/FRESH/SERVICE/VIRTUAL/CARD` | 三级类目树，运营可维护 |
| 挂在哪 | 商品 | 商品 |
| 谁定义 | **平台硬编码**，商家和运营都改不了 | 运营在后台增删改 |
| 决定什么 | **履约与合规**：生鲜要不要冷链、服务不发货、虚拟即时核销、iOS 上能不能卖（`sys_channel_category_rule`）、规格模板 | **导购与准入**：商家上架时归到哪、C 端怎么逛、经营该类目要什么资质 |
| 变更代价 | 加一个值 = 改履约代码 | 加一个类目 = 后台点几下 |

**为什么不能合并成一个**：把 iOS 可售规则挂到一棵运营可编辑的树上，等于让运营点几下就能改变
App Store 合规判定；反过来，把「叶菜 / 根茎菜」做成硬编码枚举，则每加一个品类都要发版。

> 第三个维度是 `mch_entity.industry`（行业），它挂**商家**不挂商品 ——
> 表注释里已经写着「行业挂商家，类目挂商品」。三者互不替代。

### 为什么否决「删掉」

`prd_category` 表建了、`CategoryService.tree()` 实现了、`GET /mp/category/tree` 通了、
ops-web 的四个端点和整套 mock 类型（含 `requiredCode` 校验模型）都写好了 ——
**唯独没有数据，也没有后端 CRUD**。删掉要拆四处已成型的代码，
而它要解决的问题（商家上架归类、类目资质准入）并不会因此消失，只会变成硬编码。

## 一、当前缺口

| 层 | 状态 |
|---|---|
| 表 `prd_category`（三级树 + `attr_template` + `qualification_required`） | ✅ 齐 |
| `CategoryService.tree()`（一次查全量内存建树） | ✅ |
| `GET /mp/category/tree` | ✅ |
| **类目数据** | ❌ **空表** → tree 返回 `[]` |
| **`/ops/categories` × 4**（ops-web 早已声明并有页面） | ❌ 后端全缺 |
| **`template` 五品类模板字段** | ❌ 表里的 `attr_template` 是 JSON 属性模板，不是这个 |
| **`required_code` 校验依据** | ❌ 表里没有 |
| **`mch_entity.category_codes`**（商家已获授权的经营类目） | ❌ 表里没有 |
| **上架资质校验** | ❌ |
| **b-app 商品编辑选类目** | ❌ 端上连契约都没声明 |

> ⚠️ **c-app 的「分类」页不是类目树**：它按 `CATEGORY_TYPE`（生鲜/日用/服务）分三个 tab，
> 调的是 `goodsList({type})`。这是刻意的一期设计（页内注释写了理由），
> **本方案不动它** —— 类目树先服务于「商家上架归类 + 资质准入」，
> C 端导购是否改用类目树留到二期按数据决定。

## 二、资质校验链：三段，缺一段就等于没校验

```
prd_category.required_code  ──┐
      「经营这个类目需要 FRESH_VEG」 │
                              ├──► 上架时比对 ──► 不持有则拒绝，
mch_entity.category_codes   ──┘                   报错里给人读的资质名称
      「这家店获批了 [FOOD]」
```

**为什么 `required_code` 要与 `qualification_required` 分开两个字段**（沿用 ops-web 已定的口径）：
后者是给人看的文案（「食品经营许可证」），拿文案做判据会退化成
「类目号以 CAT1 开头就认为要生鲜资质」这类前缀魔法 —— 看起来在校验，实际上几乎总是通过。

**校验点选在「上架」而不是「保存商品」**：商家把草稿归到一个自己没资质的类目下不该被拦
（他可能正准备去申请），真正不能发生的是**这件商品对消费者可见**。

## 三、改动清单

### 3.1 V3 迁移（V1/V2 已在真库跑过，不改历史脚本）

| 表 | 列 | 说明 |
|---|---|---|
| `prd_category` | `template VARCHAR(16) NOT NULL DEFAULT 'STANDARD'` | 五品类录入模板，决定商家录入时看到哪些字段 |
| `prd_category` | `required_code VARCHAR(32) DEFAULT NULL` | 校验依据。**空 = 无门槛** |
| `prd_category` | `name_en VARCHAR(64) DEFAULT NULL` | 三语里 en 这一路；ar 二期再加，不预留空列 |
| `mch_entity` | `category_codes JSON DEFAULT NULL` | 已获授权的经营类目编码数组 |

种子：对齐 ops-web mock 那 10 个节点（食品生鲜 / 日用百货 / 生活服务 / 卡券），
**保持同样的 `categoryNo`**（CAT100…CAT400）—— 前后端 mock 与真库对得上，
联调时不用在两套编号之间换算。

### 3.2 后端

| 端点 | 行为 |
|---|---|
| `GET /ops/categories` | 平铺列表（带 `skuCount`），支持 `keyword`/`template`/`showArchived` |
| `POST /ops/categories` | 新建或更新。**三级封顶**；`level` 由 `parentNo` 推出，不信端上传的 |
| `POST /ops/categories/{no}/archive` | **有在架商品或有未归档子类目则拒绝** |
| `POST /ops/categories/{no}/unarchive` | 恢复；父类目已归档则拒绝 |

上架校验挂在 `MerchantGoodsServiceImpl.toggle(..., onSale=true)`。

### 3.3 b-app

商品编辑页加三级类目选择器，落到 `goods.categoryNo`；契约四件套（endpoints / contract / http / mock）同步。

## 五、落地记录（2026-08-10）

全部完成，三层测试全绿：单元+集成 **268**（新增 15）· E2E-1 **4** · E2E-2 J1 **11 步** · shared 守卫 **142** · ops-web **559**。

### 实际做出来的东西

| | 落点 |
|---|---|
| 迁移 | `V4__category_tree.sql`（字段 + 10 个类目）· `V5__auth_code.sql`（授权码表 + 6 条）· `V6__retire_legacy_categories.sql`（清旧编号） |
| 后端 | `/ops/categories` × 4 · `/ops/merchants/auth-codes` × 2 · `/biz/category/tree` · 上架资质校验 |
| 端上 | b-app 三级类目选择器（契约四件套 + 页面 + 三语文案）· `Goods.categoryNo` 全链路打通 |
| 覆盖率 | ops-web 5.3% → **8.0%** · b-app 76.1% → **76.8%** |

### 三件当时没预料到、但必须一起做的事

**① 授权码表（V5）不是可选项。** V4 给类目挂上 `required_code` 之后，
`mch_entity.category_codes` **没有任何写入路径** —— 有门槛没有发证机关，
挂了门槛的类目会永远拒绝所有人，而商家只看到「你还没有资质授权」，去哪申请没人知道。
**一个只会拒绝的校验比没有校验更糟：它看起来在工作。**
ops-web 早就把授权页和规则写完了，缺的一直是后端那两个端点。

**② 四套类目编号。** 动手前系统里有三套（DevSeeder 的 `CAT-ROOT-1/CAT001`、
ops-web mock 的 `CAT100`、shared 里一个没人用且字段是错的 `Category` 类型），
差点因为 V4 变成第四套。全部统一到 `CAT1xx`，并加了 `V6` 把开发库里的旧节点清掉 ——
不清的话 `/mp/category/tree` 会返回两棵树，商家在选择器里看到「日用百货」出现两次。

**③ `category_codes` 不能用 JSON 列。** H2（集成测试用）的 JSON 类型会把绑定进去的
字符串**再包一层引号**，读回来是 `"[\"FRESH_VEG\"]"` 而不是数组，反序列化失败。
失败被兜底成「没有任何授权」，于是**授权写成功、接口返回 0、审计日志也记了，
商家却依然上不了架** —— 全链路都说成功的故障。改用本库既有惯例（VARCHAR 存 JSON 数组）。

> 同一趟还修了两个「静默失败」：运营改授权时数据域会让 `updateById` 匹配 0 行却不报错
> （已 `executeWithoutScope` + 断言影响行数）；DevSeeder 的总闸只看社区表，
> 兜不住「灌到一半失败」，于是每个 seed 各自再判一次存在性。

### 仍然没做的（明确留着）

| | 为什么 |
|---|---|
| C 端改用类目树导购 | 分类页现在按 `CATEGORY_TYPE` 分三个 tab，是一期的刻意设计（页内有理由）。改不改要看数据，不在本轮 |
| 授权时校验资质证件已上传 | B-11.1.2 资质上传还没落地，`mch_entity` 上根本没有证件字段。现在的口径是**运营看着证件放行**，代码里写明了没假装校验过 |
| `attr_template` 真正驱动录入表单 | 字段在、`template` 也下发了，但 b-app 还没按模板切换字段 |
