```

```

档案与处置**刻意分成两个 tab**：合成一页的话，翻档案的人会顺手点处置，
而这两件事本该由不同的人在不同的时点做。同理，类目授权与认证标也分开 ——
混成一页会让人以为拿了标就等于扩了类目。

## 二、类目授权：按码，不按类目节点

`AuthCode` 与类目树是多对一（叶菜、根茎菜都归 `FRESH_VEG`）。
按码授权的理由很实际：**类目树会重构，而"能不能卖菜"这件事不会**。

| 规则 | 不这么做会怎样 |
| --- | --- |
| 只有 `APPROVED` 商家能配授权 | 没过审就授权等于提前放行 |
| 需要资质的码必须已有对应资质 | 无证卖生鲜 |
| **不能把授权撤空** | 商家静默失去上架能力；要停就走封禁或归档，那是明示的动作 |
| **该码下还有在售商品的不能撤** | 撤了架上还挂着那类商品，谁也说不清它算不算违规 |
| 改授权必须写原因 | 它决定商家能上架什么 |

界面上两处与规则呼应：缺资质的选项直接禁用（勾上再保存报错等于让人白点一次）；
在售商品拦截只能在保存时报（前端不知道库存），但错误文案直接给出"先下架再撤销"的下一步。

## 三、认证标：毁约次数是硬条件

认证标是平台给用户看的背书。挂在一个正在毁约的商家身上，赔的是平台的信用 ——
所以 `breachCount >= MAX_MERCHANT_BREACH`(3) 不能授标，且列表里这个数字标红。
**撤销不受限制**：要撤的恰恰是这种商家。

## 四、违规处置：只有毁约计入 breachCount

`ViolationType` 分四类而不是笼统记"违规"，因为处置尺度不同、统计口径也不同。
其中**只有 `BREACH` 计入 `breachCount`** —— 别的也计的话，
ADR-003 里"毁约达阈值即限制报价"那条阈值就失去意义了。

`SUSPEND` 走的是同一张 `MERCHANT_TRANSITIONS`：已封禁的再封一次会抛错，
而不是静默重复记一条。界面上这个选项对已封禁商家是 disabled 的。
