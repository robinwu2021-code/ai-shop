## 一、需求梳理

按流转方案的四条支柱展开，每条需求标注**它防住了什么** —— 防不住任何东西的需求不该进一期。

### 1.1 R1 三时点（产生 / 扣减 / 兑付）

| # | 需求 | 防住什么 |
|---|------|---------|
| R1.1 | 积分在子订单 `COMPLETED` 时产生，按商品配置计算，无配置按成交额兜底比例 | 支付即发 → 「下单拿分→花掉→退款」白拿 |
| R1.2 | 计算基数为**商家实收部分**，不含运费、不含平台券补贴；**赠品行不发** | 商家没收到的钱不该由他出积分；买赠 + 积分可叠出套利 |
| R1.3 | 积分在**下单时**扣减（非支付后） | 同一笔分同时下多单 |
| R1.4 | 抵扣上限 = 券后金额的 30%；**券先抵、积分后抵**；运费不参与 | 整单抵扣商家一分收不到；顺序反了会让券的门槛达不到 |
| R1.5 | 跨商家**兑付**在子订单 `COMPLETED` 时才成立，此前只是预占 | 订单还会取消/退款，那时商家之间的账就不该发生过 |
| R1.6 | 取消返还抵扣分；退款**两笔都走**（收回已发 + 返还已抵） | 退款后积分净赚 |
| R1.7 | 发放幂等：同一子单只发一次 | 重复核销重复发分 |

### 1.2 R2 发收对称

| # | 需求 | 防住什么 |
|---|------|---------|
| R2.1 | `canIssue == canAccept`，**同一个开关**，不提供拆分配置 | 搭便车：只收不发 → 理性商家全这么选 → 积分归零 |
| R2.2 | 关闭开关**只影响将来**：存量已发积分仍有效，存量债务仍需承担 | 「先猛发分引流，再关开关赖账」 |
| R2.3 | 不支持的店在 C 端**不显示抵扣入口**，而非显示后报错 | 用户到结算页才发现不能用 |

### 1.3 R3 三级灰度与强制开

| # | 需求 |
|---|------|
| R3.1 | L1 全局 `FEATURES.points`（`sys_config`）· L2 社区 `cmt_community.points_enabled` · L3 商家 `usr_merchant.points_enabled` |
| R3.2 | 三级**与**关系：任一级关闭即不可用 |
| R3.3 | `usr_merchant.points_forced` 强制开（按行业/类目），商家不可自行关闭 |
| R3.4 | 强制开的三个前置：提前 ≥30 天通知、费率补偿、申诉通道 —— **强制开不是单方面加成本** |

### 1.4 R4 商家两本账（**本次设计的重点**）

| # | 需求 | 防住什么 |
|---|------|---------|
| R4.1 | **额度台账**（单位：分）：发放即占用，过期释放；兑付**不再扣**、收单**不增加** | 同一笔分占两次额度 / 同一笔收入拿两遍好处 |
| R4.2 | **资金台账**（单位：分/钱）：只在兑付时发生，`REDEEM_IN` 收、`REDEEM_OUT` 付 | 把「或有负债」计成当期成本 —— 那笔钱可能永远不会被花 |
| R4.3 | 授信额度 = `min(固定上限, 近 3 期平均货款 × 系数)`；**可发放 = 授信 − 已占用** | 商家不预存现金也能启动积分 |
| R4.4 | 超授信 → **自动停发**，并按 R2.1 同时停收 | 债务无限扩张 |
| R4.5 | 商家不需要充值买积分 | 付费门槛会让积分永远启动不了 |

### 1.5 R5 独立账期结算

| # | 需求 | 防住什么 |
|---|------|---------|
| R5.1 | 货款按订单即时结算，积分按**账期**结算，两条线并行 | 兑付时点晚于结算单生成，塞不进 `stl_bill` |
| R5.2 | 每商家每期一张 `stl_points_bill`，净额并入下期货款 | — |
| R5.3 | **自发自用不进账期单**，直接冲抵 | 省一次清算，顺手堵掉自己刷自己 |
| R5.4 | 商家侧展示以**钱**为主、分为辅 | 积分个数是平台的内部单位 |

### 1.6 R6 平台清算账户

| # | 需求 | 防住什么 |
|---|------|---------|
| R6.1 | `stl_points_pool` 记录清算收付，单位为钱 | 发放方货款不够扣 / 跑路 / 平台自发积分 —— 三处无科目可落 |
| R6.2 | 恒等式 `Σ商家账期净额 + 池子净额 = 0`，每期校验 | 池子余额 ≠ 0 即坏账敞口 |
| R6.3 | 坏账由池子核销，**不传导给收单商家与用户** | 让 B 承担 A 跑路的损失 → 发收对称建立的参与意愿瓦解 |
| R6.4 | 平台自发积分（拉新/补偿/活动）成本从池子出，须有预算口径 | 唯一的真实成本出口，不设上限会失控 |

### 1.7 R7 明细与监控

| # | 需求 |
|---|------|
| R7.1 | B 端流水：**额度列与金额列分开**，每笔可追到订单；「收到积分」写明发放方 |
| R7.2 | B 端状态条：`可发放额度 x/y` + `本期净额 ±z` |
| R7.3 | 平台端：商家账户总表、**授信风险榜**（按占用率 = 跑路风险排序）、与商家同一份流水 |
| R7.4 | 平台监控：沉淀量、兑付率、**净流出榜**、每日三方对账 |

### 1.8 R8 合规三禁（**代码层面拦死**）

| # | 需求 |
|---|------|
| R8.1 | **无充值接口** —— 积分只能由交易产生 |
| R8.2 | **无提现接口** —— 只能在交易中抵扣 |
| R8.3 | **无转赠接口** —— 不可在用户间转让 |

> 三条要体现为**代码里根本没有对应端点**，而不是配置项关掉。
> 配置项会被人打开，缺失的接口不会。破任一条，积分即从「商家折扣的记账工具」
> 变成「平台发行的支付凭证」（[流转方案 §4quater.5](./积分流转方案.md)）。

## 二、数据库设计

### 2.0 表清单

| 表 | 作用 | 归属键（数据域） |
|----|------|-----------------|
| `pts_user_account` | 用户账户：**锁行 + 派生余额** | `user_no`(SELF) |
| `pts_user_ledger` | 用户流水（真源），EARN 行即**批次** | `user_no`(SELF) |
| `pts_redeem_alloc` | **使用分摊 / 兑付明细** —— 跨商家清算的事实表 | `issuer_merchant_no` / `acceptor_merchant_no` |
| `pts_merchant_quota` | 商家额度台账（授信、占用） | `merchant_no` |
| `pts_merchant_ledger` | 商家流水（额度列 + 金额列双口径） | `merchant_no` |
| `stl_points_bill` | 商家积分账期单 | `merchant_no` |
| `stl_points_pool` | 平台清算账户流水 | —（仅 /ops） |

外加三处 `ALTER`：`prd_goods.points_config` · `usr_merchant.points_enabled/points_forced` · `cmt_community.points_enabled`。

---

### 2.1 `pts_user_account` —— 账户表是**派生**的，真源是流水

ADR-006 §3.4 定的是「余额由流水推导，不单独存字段」。这条**不推翻**，但要说清落地：

> 每次下单都对全量流水求和不可行（活跃用户几百上千条）。
> 所以建账户表，但它的定位是 **① 并发锁行 ② 派生缓存**，
> **不是真源** —— 对账任务每日用流水重算校验，不一致以流水为准并告警。

```
balance          可用余额（派生）
frozen           无。下单即真扣，不做冻结 —— 冻结态会引入「冻结未释放」的脏数据，
                 而退款返还本来就要走 REFUND 流水，没有冻结也能表达
```

并发控制：所有扣减走 `UPDATE ... SET balance = balance - ? WHERE user_no = ? AND balance >= ?`，
**用影响行数判断是否足额**，不用「先查后扣」—— 后者在并发下必然超扣。

### 2.2 `pts_user_ledger` —— EARN 行就是批次

四种类型：`EARN` / `USE` / `REFUND` / `EXPIRE`。

**只有 `EARN` 行带 `expire_at` 与 `remaining`**，它同时是流水行和**批次行**：

| 列 | EARN | USE / REFUND / EXPIRE |
|----|------|----------------------|
| `points` | +N | ±N |
| `remaining` | 该批次剩余可用（消耗时递减） | NULL |
| `expire_at` | 到期时间 | NULL |

消耗按 **FIFO（先到期先消耗）**，不是先进先出 —— 两者在有效期相同时一致，
但一旦出现不同有效期的活动分，**先到期先用对用户更有利**，客诉最少。

> ⚠️ **退款返还必须还回原批次**（`pts_redeem_alloc` 记了消耗了哪些批次）。
> 若返还时新开一个 365 天的批次，用户就能靠「下单 → 退款」**无限续期积分**。
> 这条由 `PointsRefundBatchTest` 守卫。

### 2.3 `pts_redeem_alloc` —— 一次使用要拆到多个发放商家

这是整个积分域最关键的一张表。用户用 3000 分，可能 2000 是 A 发的、1000 是 B 发的 ——
**跨商家清算必须按批次拆行**，否则算不出谁欠谁。

```
一条 USE 流水 ──┬─→ alloc(批次1, issuer=A, 2000分, ¥20)
                └─→ alloc(批次2, issuer=B, 1000分, ¥10)
                    两条都 acceptor = 本单商家 C
```

**状态机解决时点问题**（R1.5）：

```
下单扣分     → PENDING     预占，不进账期单
子单 COMPLETED → CONFIRMED  兑付成立，**此刻才计入账期**
取消 / 退款   → REVERSED    兑付未发生过
```

| 列 | 说明 |
|----|------|
| `issuer_merchant_no` | 发放方。**平台自发积分填 `PLATFORM`** —— 成本走池子（R6.4） |
| `acceptor_merchant_no` | 收单方 |
| `rate_snapshot` | 汇率快照（分/元）。之后调汇率不影响已发生的账 |
| `period` | 账期（`YYYYMM`），`CONFIRMED` 时按当时账期落定 |
| `self_used` | `issuer == acceptor` → 1，**不进账期单**（R5.3） |

索引 `(period, status, issuer_merchant_no)` 与 `(period, status, acceptor_merchant_no)` ——
出账期单时两个方向各扫一次，这是唯一的高频批量查询。

### 2.4 `pts_merchant_quota` —— 额度台账

```
credit_limit    授信额度（分）
used            已发放未兑付未过期（分）
available       = credit_limit - used   ← 不存列，查询时算，避免两处存迟早不一致
```

| 事件 | `used` |
|------|--------|
| 发放 ISSUE | `+N` |
| 兑付 REDEEM_OUT | **不动**（发放时已占用） |
| 过期 EXPIRE_BACK | `−N`（释放） |
| 退款收回已发积分 | `−N` |

发放前置校验：`UPDATE ... SET used = used + ? WHERE merchant_no = ? AND used + ? <= credit_limit`，
同样**用影响行数判断**，0 行 = 超授信 → 停发（R4.4）。

### 2.5 `pts_merchant_ledger` —— 双口径，两列并存

| 列 | 含义 |
|----|------|
| `quota_delta` | 额度变动（分），仅 `ISSUE` / `EXPIRE_BACK` / `REVOKE` 非零 |
| `amount_delta_minor` | 金额变动（分），仅 `REDEEM_IN` / `REDEEM_OUT` / `SETTLE` 非零 |

**两列不能合并成一列**：合并后商家一定会问「为什么发了 300 分只扣 3 块又没扣」（R7.1）。
类型枚举：`ISSUE` · `REDEEM_IN` · `REDEEM_OUT` · `EXPIRE_BACK` · `REVOKE` · `SETTLE`。

### 2.6 `stl_points_bill` —— 商家积分账期单

```
income_minor  = Σ REDEEM_IN   （CONFIRMED 且 period = 本期 且 self_used = 0）
expense_minor = Σ REDEEM_OUT
net_minor     = income - expense
              ├─ > 0 → 并入下期分账付给商家
              └─ < 0 → 从下期货款扣
```

`UNIQUE (merchant_no, period)` —— 一期一张，重复生成 = 重复收付。
状态：`DRAFT` → `CONFIRMED` → `SETTLED`（并入货款后）。

### 2.7 `stl_points_pool` —— 平台清算账户

| `direction` | `pool_type` | 场景 |
|---|---|---|
| IN | `MERCHANT_PAY` | 净流出商家的账期扣款 |
| IN | `RECOVERY` | 坏账追偿回款 |
| IN | `PENALTY` | 超授信违约处置（P13） |
| OUT | `MERCHANT_RECEIVE` | 净流入商家的账期付款 |
| OUT | `PLATFORM_ISSUE` | **平台自发积分被兑付的成本**（issuer=PLATFORM） |
| OUT | `BAD_DEBT` | 坏账核销 |

每期校验 `Σ stl_points_bill.net_minor + 本期池子净额 = 0`（R6.2），不等即告警。

> 池子表**不做数据域拦截**（只有 /ops 能访问，靠 RBAC + 端点前缀），
> 但要注册进敏感表清单：它是全平台资金视图。

## 三、与已有表的关系

| 已有表 | 关系 |
|--------|------|
| `stl_bill` | **不动**。积分不进 `gross`（v2 修正的时点错误），走独立账期单 |
| `ord_sub_order` | 已有 `points_deduct_minor`？若无需 ALTER 记录本单积分抵扣额 —— 结算与售后都要读 |

| `sys_outbox` | 兑付确认、账期出单、坏账核销均走 outbox，避免与主流程同事务 |
