## 一、总览

积分域是**唯一横跨两个表名前缀的域**：`pts_*` 三张记积分，`stl_points_*` 两张记平台的钱。
加上 `ord_sub_order`（资金账与积分账的勾稽点）才是完整的一张图。

![积分域表关系](./diagrams/topic-points.svg)

| 表 | 前缀 | 职责 | 增长量级 |
|---|---|---|---|
| `pts_user_account` | `pts` | 用户余额（**派生**，可重算） | 每用户每市场一行 |
| `pts_user_ledger` | `pts` | **真源**：EARN 行即发放，USE 行即一次兑付 | 每笔发放/使用一行，最大的表 |
| `pts_merchant_ledger` | `pts` | 商家资金流水（**一本账**） | 一次发放一行 + 一次收单一行 |
| `stl_points_bill` | `stl` | 账期结算单 | 每商家每期每市场一行 |
| `stl_points_pool` | `stl` | 平台积分资金池流水 | 与商家流水同量级 |

> 图上 `pts_user_account`、`stl_points_bill`、`stl_points_pool` **没有连线** ——
> 这是真的：它们不靠单一外键关联，而是靠 `(user_no, market)` 与 `(merchant_no, period, market)`
> 这类**复合口径**归集。按名字连线会连错，所以生成器不连。见 §四。

## 二、分组

### 用户侧：`pts_user_ledger` + `pts_user_account`

流水是真源，余额是派生。`balance` 只放**能花的**分，未过售后期的记在 `pending_balance`，
两个数分开展示（「可用 400 / 待生效 100，3 天后到账」），
否则用户看到「我有 500 分」却只能用 400，无法解释。

### 兑付：`pts_user_ledger` 的 USE 行

一次使用一行，带 `acceptor_merchant_no`（池子付给谁）、`amount_minor`、`status`。

**不记发放方**。积分发出后与商家脱钩 —— 收单方从池子拿钱，池子不问这分是谁发的。
原有一张 `pts_redeem_alloc` 按发放商家拆行，那是信用模型的遗留，已于 `V28` 删除。

### 资金侧：`pts_merchant_ledger` + `stl_points_pool` + `stl_points_bill`

商家一本账，平台一个池子，按期出一张单。
**账期单不直接连用户流水**，走 `USE 行 → merchant_ledger → bill` ——
中间那一跳不能省，商家的进账（`REDEEM_IN`）就记在 `merchant_ledger` 上，跳过它没地方记。

## 三、逐表详情

6 张表（`pts_merchant_quota` 已随预付费模型删除）。省略每张表都有的审计列（`id` / `tenant_no` / `created_*` / `updated_*` / `version` / `deleted`）。

---

### 3.1 `pts_user_account` —— 用户积分账户

**一句话**：用户余额的缓存，**不是真源**。

| 列 | 类型 | 空 | 说明 |
|---|---|:---:|---|
| `user_no` | VARCHAR(64) | 否 | 一人一户，唯一键 |
| `balance` | BIGINT | 否 | 可用余额（派生，以流水为准） |
| `total_earn` | BIGINT | 否 | 累计获得，只增不减 |
| `total_use` | BIGINT | 否 | 累计使用 |
| `pending_balance` | BIGINT | 否 | **待生效积分**：已发放但未过售后期。**不计入 `balance`** |
| `market` | VARCHAR(8) | 否 | **市场隔离键**。跨市场是两个独立余额，唯一键为 `(user_no, market)` |

**`balance` 只放能花的分**。待生效的分单独计 `pending_balance` ——
合在一起的话，用户看到「我有 500 分」却只能用 400，这个数字就没有意义了。
端上展示成两行：「可用 400 / 待生效 100（3 天后到账）」。

**为什么派生值还要建表**：只有两个理由——**并发锁行**、**避免每次下单对全量流水求和**。
除此之外它没有权威性。对账任务每日用流水重算校验，不一致时以流水为准并告警。

**并发扣减必须把条件写在 WHERE 里**：

```sql
UPDATE pts_user_account
   SET balance = balance - #{points}, version = version + 1
 WHERE user_no = #{userNo} AND deleted = 0 AND balance >= #{points}
```

先查后扣在并发下必然扣穿——两个请求都查到「还有 500 分」。

### 3.2 `pts_user_ledger` —— 用户积分流水

**一句话**：全域的真源。EARN / USE / REFUND / EXPIRE / REVOKE 五种行都在这里。

| 列 | 类型 | 空 | 说明 |
|---|---|:---:|---|
| `ledger_no` | VARCHAR(64) | 否 | 流水号，唯一键 |
| `user_no` | VARCHAR(64) | 否 | 持有人 |
| `biz_type` | VARCHAR(16) | 否 | `EARN` 获得 / `USE` 使用 / `REFUND` 退回 / `EXPIRE` 到期清零（整账户一次）/ `REVOKE` 退款扣回 |
| `points` | BIGINT | 否 | **带符号**：EARN、REFUND 为正；USE、EXPIRE 为负 |
| `balance_after` | BIGINT | 否 | 变动后余额快照，用于定位「从哪条开始错的」 |
| `issuer_merchant_no` | VARCHAR(64) | 是 | **仅 EARN**：发放方。**只用于追溯统计**，不参与资金流动 |
| `acceptor_merchant_no` | VARCHAR(64) | 是 | **仅 USE**：收单方，池子付钱给它。**不记发放方** —— 发分时已付费 |
| `amount_minor` | BIGINT | 是 | **仅 USE**：本次抵扣金额（分）。与 `ord_sub_order.points_deduct_minor` 勾稽 |
| `rate_snapshot` | INT | 是 | 汇率快照（多少分 = 1 元）。调汇率不改变已发生的账 |
| `status` | VARCHAR(16) | 是 | **仅 USE**：`PENDING` 预占 / `CONFIRMED` 兑付成立 / `REVERSED` 撤销 |
| `period` | VARCHAR(8) | 是 | **仅 USE**：账期 `YYYYMM`，`CONFIRMED` 时落定 |
| `confirmed_at` | BIGINT | 是 | **仅 USE** |
| `currency` | VARCHAR(8) | 是 | `amount_minor` 的币种 |
| `sub_order_no` | VARCHAR(64) | 是 | 来源子订单 |
| `available_at` | BIGINT | 是 | **仅 EARN**：可用时间（售后期结束）。此前分**可见不可用** |
| `market` | VARCHAR(8) | 否 | 市场隔离键 |
| `remark` | VARCHAR(255) | 是 | 展示用文案 |

**索引**

| 索引 | 为什么 |
|---|---|
| `(user_no, id)` | 「我的积分明细」按时间倒序翻页 |
| `(sub_order_no, biz_type)` | 退款时找这单发过/扣过多少 |
| `(period, status, acceptor_merchant_no)` | 出账期单：按期扫已确认的兑付，聚到收单商家（V28，原在已删的 alloc 表上） |

**这张表里没有「批次」**。`remaining` 与行级 `expire_at` 在 `V30` 删除 ——
到期改挂在账户上（活跃即续期），它们唯一的读者（过期任务）不再需要它们。
留着不删的话，下一个人会以为抵扣时还要维护，而维护一个没人读的字段出错了也没有症状。

**一张表两种行**。EARN 行有 `available_at`/`issuer_merchant_no`，
USE 行有 `acceptor_merchant_no`/`amount_minor`/`status`/`period`，互不相干。
拆成两张表会有大量共同字段（`ledger_no`/`user_no`/`points`/`balance_after`/`sub_order_no`），
而且「余额 == Σ points」这条恒等式要跨两张表算 —— 那才是真正的复杂度。

**`available_at` 让套利窗口归零**。发放时点是**支付成功**（用户立刻看得到分），
但可用时点推到售后期结束。配合「等待期后不可退款」，**分能用时订单已经不能退了**。

没有这一列的话，刷子的标准打法是：下大单 → 拿分 → 立刻在别家花掉 → 退掉大单，
那笔钱平台垫。转正任务必须带 `available_at <= now`，漏了等于这一列不存在。

> **发放幂等不放在这张表**。本想用 `(sub_order_no, biz_type)` 做唯一键，
> 但部分退款会产生多条 REFUND 行，那个唯一键会误伤。
> 幂等改由 `ord_sub_order.points_granted` 标记保证。

### 3.3 `pts_merchant_ledger` —— 商家资金流水

**一句话**：商家的**唯一一本账**——发分付出去多少、收单收回来多少。

| 列 | 类型 | 空 | 说明 |
|---|---|:---:|---|
| `ledger_no` | VARCHAR(64) | 否 | 流水号，唯一键 |
| `merchant_no` | VARCHAR(64) | 否 | 商家 |
| `biz_type` | VARCHAR(16) | 否 | 见下表 |
| `amount_delta_minor` | BIGINT | 否 | 金额变动（分），带符号 |
| `counterparty_no` | VARCHAR(64) | 是 | 对手方商家 |
| `sub_order_no` | VARCHAR(64) | 是 | 来源子订单 |
| `use_ledger_no` | VARCHAR(64) | 是 | `REDEEM_IN`：对应用户的哪次使用。**一次使用一条**，金额是该次总额 |
| `period` | VARCHAR(8) | 是 | 账期 |
| `market` | VARCHAR(8) | 否 | 市场隔离键 |
| `currency` | VARCHAR(8) | 否 | 金额币种 |
| `remark` | VARCHAR(255) | 是 | 说明 |

**`biz_type` 取值**

| 值 | `amount_delta_minor` | 场景 |
|---|:---:|---|
| `ISSUE_FEE` | **−** | 发分，扣走费用金 |
| `REDEEM_IN` | **+** | 用户在我这用分，池子付我 |
| `REVOKE_REFUND` | **+** | 退款收回已发分，退还费用金 |

| `SETTLE` | **±** | 账期结算 |

**`REDEEM_OUT` 已删除**。旧的信用模型里，用户花掉 A 发的分时 A 要付钱；
预付费下 A 在发分那一刻就付过了，此刻不再产生任何资金流动。
这是模型切换带来的最直接的简化。

**额度那一本账也没了**。`quota_delta` / `quota_used_after` 两列随 `pts_merchant_quota`
一起删除——授信与停发闸是为「商家自主决定发多少分」设计的，
而现在发放比例由平台统一定、且发放即扣钱，商家货款不够就扣不出费用金，
那套机制随之空转。

**`counterparty_no` 仍然要留**——「收到积分」必须写明是谁发的。
没有它，商家只知道自己多了一笔收入，不知道该找谁对账。

**索引**

| 索引 | 为什么 |
|---|---|
| `(merchant_no, id)` | 商家看自己的流水 |
| `(merchant_no, period, biz_type)` | 生成账期单时按类型聚合 |
| `(use_ledger_no)` | 从一次使用反查商家进账 |

### 3.4 `stl_points_bill` —— 账期结算单

**一句话**：每商家每期一张，把当期的收与付轧成一个净额。

| 列 | 类型 | 空 | 说明 |
|---|---|:---:|---|
| `bill_no` | VARCHAR(64) | 否 | 账单号，唯一键 |
| `merchant_no` | VARCHAR(64) | 否 | 与 `period` **联合唯一** |
| `period` | VARCHAR(8) | 否 | 账期 YYYYMM |
| `income_minor` | BIGINT | 否 | Σ `REDEEM_IN`：别人的分在我这儿被花掉，池子付我 |
| `expense_minor` | BIGINT | 否 | Σ `ISSUE_FEE`：我发分付出的费用金（**发放时即扣**，不再是「我的分在别人那被花掉」） |
| `net_minor` | BIGINT | 否 | 净额：**>0 平台付给商家；<0 从货款扣** |
| `alloc_count` | INT | 否 | 本期兑付笔数，用于核对（一次使用一笔） |
| `status` | VARCHAR(16) | 否 | `DRAFT` 攒中 / `CONFIRMED` 封账 / `SETTLED` 已结 |
| `settled_at` | BIGINT | 是 | 结清时间 |
| `market` | VARCHAR(8) | 否 | 市场隔离键，唯一键为 `(merchant_no, period, market)` |
| `currency` | VARCHAR(8) | 否 | 金额币种 |

**`(merchant_no, period, market)` 唯一是硬约束**：重复生成账单 = 重复付款。
靠库约束挡，不指望应用层记得判。

**为什么积分要独立账期，不并进 `stl_bill`**：货款按订单即时结算，
而积分兑付的时点**晚于**结算单生成——塞不进去。两条线并行，净额并入下期货款。

**恒等式**：`net_minor = income_minor − expense_minor`。

### 3.5 `stl_points_pool` —— 积分资金池

**一句话**：**积分资金池**——每一分流通中的积分，池子里都有对应的钱。

| 列 | 类型 | 空 | 说明 |
|---|---|:---:|---|
| `flow_no` | VARCHAR(64) | 否 | 流水号，唯一键 |
| `direction` | VARCHAR(8) | 否 | `IN` 进 / `OUT` 出 |
| `pool_type` | VARCHAR(24) | 否 | 见下表 |
| `amount_minor` | BIGINT | 否 | 金额（分） |
| `balance_after` | BIGINT | 否 | 池子余额快照 |
| `merchant_no` | VARCHAR(64) | 是 | 相关商家 |
| `period` | VARCHAR(8) | 是 | 账期 |
| `ref_no` | VARCHAR(64) | 是 | 关联账期单 / 兑付明细 |
| `market` | VARCHAR(8) | 否 | 市场隔离键 |
| `currency` | VARCHAR(8) | 否 | 金额币种 |
| `remark` | VARCHAR(255) | 是 | 说明 |

**`pool_type` 六种**

| 值 | 方向 | 含义 |
|---|:---:|---|
| `MERCHANT_PAY` | OUT | 付给商家（净额为正的账期单） |
| `EXPIRE_INCOME` | OUT | **过期核销**：用户没花掉的分，那笔费用金转为平台收入 |
| `MERCHANT_RECEIVE` | IN | 从商家收（净额为负） |
| `PLATFORM_ISSUE` | OUT | 平台自发积分的成本（`issuer = PLATFORM`） |
| `RECOVERY` | IN | 追回 |
| `PENALTY` | IN | 罚没 |
| `BAD_DEBT` | OUT | 坏账核销 |

**池子是预付费模型的核心保证**。商家发分时把钱付进来、用户花分时池子付出去，
所以有一条可校验的恒等式：

```
池子余额 == Σ(流通中未兑付的积分 × 汇率)
```

这就是「积分都有对应资金」的落地方式——不是靠平台计提准备金，
而是**发分的商家自己先把钱付了**。

平台自发的积分（拉新、补偿）没有商家兜底，走 `PLATFORM_ISSUE` 由平台自己出；
商家的钱收不回来时走 `BAD_DEBT` 核销。这两类钱不建池子就会挂在账上找不到归属。

## 四、注意事项

### 容易看错的两处

**EARN 行与 USE 行在同一张表里，字段集不同**：`available_at`/`issuer_merchant_no`
只有 EARN 行有值，`acceptor_merchant_no`/`amount_minor`/`status`/`period` 只有 USE 行有值。
按 `biz_type` 分流之前不要读这些列。

**到期不在这张表上**。账户级滚动到期（`V30`）：`pts_user_account.expire_at`
随任何积分变动往后推，到期时整个账户一次清零。流水行上没有到期日，也没有批次剩余。

**没有连线不等于没有关系**。`stl_points_bill` 与 `pts_merchant_ledger` 靠
`(merchant_no, period, market)` 归集，`pts_user_account` 与 `pts_user_ledger` 靠
`(user_no, market)`。生成器只连**单列外键**，复合口径它不猜 —— 猜错的线比没有线更糟。

### 跨表约束速查

落地时这几条要写成断言：

| # | 约束 | 违反的后果 |
|---|---|---|
| 1 | `pts_user_account.balance` == Σ `pts_user_ledger.points` | 余额被改过，且查不出从哪条开始 |
| 2 | **池子余额 == Σ(流通中积分 × 汇率)** | 有分没钱，或有钱没分 —— 预付费模型的核心保证 |
| 3 | `stl_points_bill.net_minor` == `income − expense` | 账单金额错，直接付错钱 |
| 4 | Σ `ord_sub_order.points_deduct_minor` == Σ `pts_user_ledger.amount_minor(USE, CONFIRMED)` | **资金账与积分账对不上**，有一侧漏记 |
| 5 | USE 行 `status=CONFIRMED` 时 `period` 必须有值 | 这笔兑付进不了任何账期单，钱悬空 |
| 6 | `ord_sub_order.merchant_recv_minor` == 实付 − 通道费 − 佣金 − 服务费 − 积分费用金 | 商家看到的实收是错的 |
| 7 | EARN 行的 `available_at` 必须有值，转正任务带 `available_at <= now` | 分在售后期内就能花 —— 套利窗口打开 |
| 8 | 每笔 EARN / USE 都刷新 `pts_user_account.expire_at` | 滚动到期退化成固定期限，而这个退化**没有任何症状** |

第 4 条是[两本账唯一的勾稽点](./积分域-完整方案.md)，已有守卫测试锁住通路
（`packages/shared/tests/schema-lineage.test.ts`）。
