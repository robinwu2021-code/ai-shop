# 营销域 · 产品与设计方案 Review

> 日期：2026-08-11 · 范围：券 · 活动 · 平台场次 · 积分 · 跨店权益 · 会员卡
> 方法：把**文档写的**、**库里建的**、**代码调的**三份逐条对齐，只报三者对不上的地方

---

## 0. 一句话结论

营销域的**设计密度远高于实现密度**：光积分就有 8 份文档、约 2700 行、
设计了 7 张表 —— 库里建了 3 张，下单链路一张都没用上。

不是文档写得不好。问题在于**没有任何机制让文档在实现掉队时发出声音**，
于是「设计完了」和「能用了」在文档上长得一模一样。
今晚给 16 份 TDD 换上数出来的后端覆盖率，就是在补这一层。

## 2. 发现（按严重度）

### ✅ F1 · 积分抵扣：有列、有额度接口，**下单永远算不到它** —— 已修（2026-08-11）

- `ord_sub_order.points_deduct_minor` 有列，注释写着「上限 = 券后金额 30%」
- `OrderVO.pointsDeductMinor` 对外暴露
- `/mp/points/deductible` 能算出「这单最多能抵多少」
- **`OrderServiceImpl` 里一次都没有出现 `points`** —— 下单不调 `PointsService`，
  也不写那一列

也就是说：C 端能查到「你有 500 积分，这单可抵 5 元」，
下单之后**照原价付款，那一列恒为 0**。

这是本项目反复出现的那个形状的**最完整版本**：
表有了、接口有了、文档 2700 行，**唯独没有消费方**。
与「`mkt_campaign` 此前没有任何消费方」（已修）是同一件事，
只是这次还多了一个会给用户看数字的接口 —— 用户会先看到承诺，再发现没兑现。

**这一条比七个未开工的域都急**：那七个是「没有」，这一条是「说有但没有」。

> **已修**：见 [积分抵扣接入下单-对齐清单](./积分抵扣接入下单-对齐清单.md)。
> 实现时又撞出三处，其中一处是**越权漏洞**（`/mp/points/**` 从请求头取用户号）。
> 注意积分的四级开关默认全关，所以线上仍不会抵扣 —— 那是灰度设计，不是没通。

### 🔴 F2 · 需求写的活动类型，模型不支持

`B端功能清单` B-10.2：**「满减 / 折扣 / N 件优惠等」**
`MktCampaign` 实际：`COUPON` / `FULL_CUT` / `FLASH` / `BUY_GIFT`

- **「折扣」**：商家侧没有百分比折扣活动（`FLASH` 是直接改价，不是打折）
- **「N 件优惠」**：完全没有对应类型
- 反过来，模型里的 `BUY_GIFT`（买赠）在 B-10.2 里也没写

需求与模型**两个方向都对不上**。而 `type` 是「创建后不可改」的字段，
补类型意味着加枚举值 + 算价分支 + 三端展示，不是小改。

**要产品定**：B-10.2 那句「等」里到底承诺了什么。
如果只做四类，就把需求文档改成那四类 —— **需求文档写着有、而做不出来，
最后是商家在 B 端找不到那个选项**。

### 🟠 F3 · 积分设计的 7 张表，库里只有 3 张

| 表 | 用途 | 库里 |
|---|---|---|
| `pts_user_account` · `pts_user_ledger` | 用户积分账户与流水 | ✅ V1 |
| `stl_points_pool` | 积分池 | ✅ V1 |
| `pts_merchant_ledger` | 商家侧积分流水 | ❌ |
| `pts_merchant_quota` | 商家积分配额 | ❌ |
| `pts_redeem_alloc` | 兑换分摊 | ❌ |
| `stl_points_bill` | 积分清分账单 | ❌ |

缺的四张全部集中在**商家侧与清分**——也就是「积分到底是谁的钱」那一半。
`积分抵扣的资金补差-方案.md` 整份 395 行讲的就是这件事，一行没实现。

结论：**积分现在是一个单机记账本**。用户攒得到分，
但攒的分不对应任何人的负债，也不参与任何结算。
这在一期自营模式下暂时不出事，接入第三方商家的那一刻会立刻出事。

### 🟠 F4 · 最优券只有 C 端一个消费方

`CouponService.best()` 只被 `MpCouponController` 调。
结算页「自动选最优券」是 C 端自己调一次接口拿到券号，再带着下单 ——
**服务端下单时不会自己去选最优券**。

这本身是合理的（用户可能手动改选），但要注意：
`best()` 与下单算价是两条独立代码路径。今晚在 `discountFor` 上刚统一过一次口径
（此前 `best()` 只看 `faceMinor`，导致**最优券永远不推荐折扣券**）。
**两条路径算同一件事，就还会再分叉一次。**

**建议**：加一条测试，对同一组商品与券，断言
`best()` 选出的券在下单算价里得到的优惠额与 `best()` 自己报的数字一致。
这是唯一能挡住这类分叉的东西。

### 🟡 F5 · 叠加规则「由结算侧统一计算」，但结算侧没有这段逻辑

B-10.5 明确写着：「**由结算侧统一计算**：同类活动取最优、不重复叠加；
券与满减可叠加。改规则要连着结算一起改，别在这里各算各的」。

实际：叠加发生在 `OrderServiceImpl` 的下单算价（`Discounts` 那个 record），
而不是 `shop-settle`。搜「取最优 / 叠加」在结算模块**零命中**。

这句需求描述的是一个**没有发生的架构**。要么改需求文档的措辞
（叠加算在下单，结算只负责分账），要么真的把它搬过去。
**倾向前者** —— 算价必须在下单时同步完成（用户要立刻看到价格），
搬到结算侧反而不成立。需求那句话大概率是早期设想的残留。

### 🟡 F6 · 会员卡有 TDD，需求标着「二期」

`P-7.4 会员卡与权益` 在平台端功能清单里是「🔜 二期」，
但 `TDD-ops-会员卡与权益.md` 已经写完了。

不是错，但要留意：**二期的方案先写完，一期的实现缺口反而没人写**
（那七个域的后端到今天才有方案）。这反映的是精力分配，不是文档问题。

## 4. 建议的处理顺序

| 优先级 | 事项 | 类型 |
|---|---|---|
| P0 | **F1 积分抵扣**：要么接进下单，要么把 `/deductible` 与 VO 字段藏起来 | 决定 + 实现 |
| P0 | **F2 活动类型**：需求与模型对齐，改哪一边 | 产品决定 |
| P1 | **F4 加一条 `best()` ↔ 下单算价的一致性测试** | 工程，小 |
| P1 | **F5 改需求措辞**（叠加算在下单侧） | 文档，小 |
| P1 | 积分五份文档合一 | 文档整理 |
| P2 | **F3 积分商家侧四张表**：接第三方商家之前必须做 | 排期 |
| P2 | `TDD-营销预算前置` / `TDD-ops-平台场次` 确认 | 待你拍板 |

**F1 里那个「要么藏起来」不是敷衍**：在能兑现之前，
让用户看到「可抵 5 元」然后照原价付款，比不显示这个数字坏得多。
这与今晚把 24 个 UI 码标成 `UNIMPLEMENTED` 是同一条原则 ——
**诚实的空白，好过撒谎的完整**。
