## 一、先纠正我自己的一个判断

上一版方案把自营写成「没有 EDI 时的临时阶段」，EDI 下来就整体切到平台模式。
**这个判断是错的**，你举的例子正好是反证：

| 平台 | 自营 | 第三方 | 并存了多久 |
|---|---|---|---|
| 京东 | 京东自营（自有主体销售、开京东发票） | POP 商家 | 一直并存 |
| 阿里 | 天猫超市 / 猫享自营 | 淘宝 / 天猫商家 | 一直并存 |

**双轨是成熟形态，不是过渡形态。** 两者并存的三个理由，与你说的完全一致：

1. **平台能力分期** —— 早期没资质只能自营；有了资质也不必把自营砍掉
2. **门店形态不同** —— 有些品类平台自己做更可控（生鲜、标品），有些交给商家更有效率（长尾、非标）
3. **税务** —— 这一条最实在，见 §四

所以设计目标不是「从 A 迁到 B」，而是**长期支持两条轨道同时跑**，
且能按门店逐个切换。这与「阶段零」的临时心态在架构上是两回事：
临时方案允许写死，长期并存必须建模。

## 二、两个正交维度（这是整套方案的骨架）

上一版把「自营 / 平台代收 / 直连分账」并列成三个值，**那是错的**——
它们不在一个维度上。正确的结构是两个轴：

| 轴 | 取值 | 决定什么 | 谁定 |
|---|---|---|---|
| **经营模式** | `SELF_OPERATED` 自营<br>`THIRD_PARTY` 第三方 | 交易主体、开票方、售后责任、税务口径 | 法务/财务，按品类与资质 |
| **资金模式**<br>（仅第三方有） | `PLATFORM_HOLD` 平台代收<br>`DIRECT_SPLIT` 直连分账 | 分账时机、商家现金流、风险归属 | 运营，按商家信用 |

**自营模式下没有资金模式这个维度**——钱本来就是平台的，不存在「什么时候给商家」。
把三者并列会逼出一堆无意义的组合（「自营 + 直连分账」是什么意思？）。

两个轴都挂在**门店**上，因为你要的粒度是门店：同一个主体下，
旗舰店做自营、加盟店做第三方，是常见形态。

# 第一部分 · 产品方案

## 三、两条轨道的完整对照

| | 自营 | 第三方 |
|---|---|---|
| 用户买谁的货 | **平台的** | 商家的 |
| 合同关系 | 平台 ↔ 供应商（采购） | 平台 ↔ 商家（入驻服务） |
| 收款账户 | 平台商户号 | 平台商户号（代收）或 二级商户号（直连） |
| 给供货方付钱 | **采购付款**，财务对公转账 | **分账**，收付通下发 |
| 平台收入确认 | **商品全额** | **服务费/佣金** |
| 给用户开票 | **平台开**，全额 | **商家开** |
| 售后责任主体 | **平台** | 商家（平台兜底） |
| 需要 EDI | ❌ 不需要 | ✅ 需要 |
| 需要收付通进件 | ❌ 不需要 | ✅ 需要 |
| 库存与定价 | 平台掌握 | 商家掌握 |
| 资金风险 | 平台承担（先采后销或账期） | 低 |

### 3.1 怎么选：给运营一个可判定的规则

不要让运营凭感觉选。建议按**品类 + 商家能力**两个信号：

| 信号 | 倾向自营 | 倾向第三方 |
|---|---|---|
| 品类 | 标品、生鲜、高频刚需 | 长尾、非标、定制 |
| 供货方资质 | 无照个体、小微 | 有照、能开票 |
| 履约控制 | 平台自建仓配 | 商家自发货 |
| 毛利结构 | 进销差价可控 | 靠佣金 |

**「供货方能不能开票」往往是决定性的那一条**——见 §四。

## 3.2 谁能改、怎么改

- **经营模式**：只有超管能改，且**要走审批留痕**。它变更的是法律关系，不是配置项
- **资金模式**：运营可改，系统给建议（信用、退款率、经营时长），**不自动切**
- **两者都只对新订单生效**，在途订单按下单时的快照走完

---

## 四、税务：这是双轨真正的经济动因

同样 100 元的 GMV，两条轨道在平台账上完全不同：

| | 自营 | 第三方 |
|---|---|---|
| 平台确认收入 | **100 元**（商品销售收入） | **约 5 元**（佣金/服务费） |
| 销项税 | 按**商品适用税率**（如 13%） | 按**现代服务业税率**（如 6%） |
| 进项抵扣 | **有**——供应商开采购发票可抵 | 无（本就没有采购） |
| 平台报表 GMV≈营收 | 是 | 否（营收只有佣金） |

三个直接后果：

1. **供货方能不能开票，直接决定自营划不划算**。拿不到进项发票，平台按 100 元全额缴销项税却无可抵扣——**自营会亏在税上**。所以无照个体、小微供货方**反而更适合第三方模式**（他们自己按小规模纳税人处理）
2. **自营做大了平台营收好看，但税负与资金占用同步放大**（要垫资采购）
3. **同一家店切换模式会让财务报表口径突变**，所以 §3.2 规定切换只影响新单——否则当月收入会因为一次配置改动而跳变

> ⚠️ 具体税率与政策会变，且各地执行口径不同。上表只表达**结构差异**，
> **实际税务处理必须由财务/税务顾问确认**，不能按本文执行。

## 五、积分在两条轨道下（差别比想象大）

现有[积分补差方案](./积分抵扣的资金补差-方案.md)是**为第三方模式设计的**：
用户用积分抵扣，商家仍要收到全额，所以平台在分账前调补差接口把差额打进二级商户。

**自营模式下这一整套都不需要。**

| | 自营 | 第三方 |
|---|---|---|
| 积分抵扣的钱谁出 | 平台（就是自己少收） | 平台补差 或 商家出资 |
| 资金动作 | **无** | 补差接口，分账前打入二级商户 |
| `stl_points_pool` 流水 | **只记 `PLATFORM_ISSUE`**（成本） | `MERCHANT_PAY` / `MERCHANT_RECEIVE` 等全套 |
| 会计口径 | 冲减收入 或 计销售费用 | 平台营销费用 |
| 开票金额 | **按实收开**（折后价） | 商家按**全额**开（他确实收了全额） |
| 商家是否感知 | 无商家 | **不感知**——补差让他收到的就是全额 |

**「自营下不需要补差」不是省了一步，是省了一整条资金链路**：
没有二级商户，就没有「把钱推给商家」这件事，也就没有补差失败、补差回退、
补差与分账的时序这些问题。

### 5.1 一个必须统一的规则

无论哪条轨道，**积分抵扣都不改变订单的商品金额**，只改变实收金额。
理由是退款：按折后价记订单，退款时要反算积分该退多少，
而积分可能已经部分过期——**算不回去**。

现有实现已经是这个口径（订单记全额、积分单独记抵扣），双轨不改它。

### 5.2 小微为什么不能开积分

现有 `pointsDenyReason` 的四级串联里有一条：**主体是小微则不可开**。
放在双轨下看更清楚：小微商户开不了发票，积分抵扣产生的补差在他那里
**无法取得合规凭证**。这条规则在自营模式下自然消失——供货方是小微没关系，
因为积分成本记在平台自己账上，不经过他。

> 这也反过来说明 §4 的结论：**小微供货方更适合第三方 + 不开积分，或者干脆走自营**。

## 五之二、定价与抽成（决策已定：商家改价 + 平台抽成）

### 5.3 采纳：商家可改价

**这推翻了本文原判断 7**（「自营的定价权在平台，供应商不能改售价」）。
决策已定，照做。但风险不会因为决定了就消失，要用别的手段接住：

自营下平台是卖方，**商家标错价，赔的是平台**（用户按错价下单，平台得认）。
所以放开改价的同时必须有：

| 措施 | 说明 |
|---|---|
| **价格下限** | 低于采购成本价不允许提交。这是最有效的一条——错价几乎都是少打一位数 |
| **改价幅度告警** | 单次降幅超阈值（如 30%）先告警再生效，不直接拦（拦了会误伤真促销） |
| **改价留痕** | 谁、什么时候、从多少改到多少。出事时要能立刻定位 |
| **单日改价次数上限** | 反复横跳通常意味着操作失误或试探 |

> 只做「留痕」不做「下限」是不够的：留痕是事后追责，而错价是**当场**产生订单的。

### 5.4 抽成：同一个数字，两条轨道两种含义

平台抽成率 `r` 在两条轨道下是同一个配置，但记账口径不同：

| | 自营 | 第三方 |
|---|---|---|
| 商家定价 | 售价 `P` | 售价 `P` |
| 平台拿走 | `P × r` = **进销差价** | `P × r` = **佣金（服务收入）** |
| 给供货方 | 采购价 = `P × (1 − r)` | 分账 = `P × (1 − r)` |
| 平台收入确认 | 商品收入 `P`，成本 `P×(1−r)` | 服务收入 `P × r` |

**净额一样，报表完全不同**——这正是 §四 说的税务动因。
好处是：`r` 只配一次，两条轨道共用，切换模式不用重配费率。

### 5.5 ⚠️ 「前期不抽成」在自营下会亏税，必须先算这笔账

这是本节最要紧的一条。设商品税率 `t`（如 13%）：

| 供货方能否开专票 | 抽成 `r = 0` 时平台的净税负 |
|---|---|
| **能开同税率专票** | 进项 = 销项，**净税 0**，平台不赚不亏 ✅ |
| **不能开票**（小微、个体、自然人） | 进项 = 0，平台按全额缴销项：约 `P × t/(1+t)` ≈ **11.5% × P** ❌ |
| 只能开小规模普票（3%） | 多数情形不可抵扣，接近上一行 ❌ |

**也就是说：供货方开不了票时，抽 0% 的自营是「卖得越多亏得越多」**，
每单亏掉约 11.5% 的税——而且这笔亏损不出现在任何业务报表里，
它只在报税时才浮出来。

由此得到一条可执行的规则：

> **自营模式下，抽成率的下限不是 0，而是「因供货方不能开票而无法抵扣的税负」。**
> 供货方能开专票 → `r` 可以是 0；开不了票 → `r` 至少要覆盖 `t/(1+t)`，
> 想有毛利还得更高。

这也解释了为什么大平台的自营几乎都要求供货方能开票——不是流程洁癖，是算过账。

**所以「前期不抽成」这个决定，要和「供货方能不能开票」绑在一起看**：

| 供货方 | 建议 |
|---|---|
| 能开专票 | 自营 + `r=0` 可行，用免佣拉商家 |
| 不能开票 | **要么第三方模式**（他自己按小规模纳税，平台只收服务费）**，要么自营但 `r` 覆盖税负** |

> 具体税率、能否抵扣、小规模政策各地执行不同，**这笔账必须由财务复核**。
> 本节给的是结构与量级，不是可直接套用的数字。

## 五之三、第三方不是一种形态，是四种

「第三方」在平台上体现为**卖家主体类型**，而不同主体的门槛、资金路径、
开票能力差得很远。项目里已经建了三种（`sys_legal_form`），咸鱼那种是**没建的第四种**：

| # | 卖家形态 | 营业执照 | 收款方式 | 能开票 | 项目现状 |
|---|---|---|---|---|---|
| 1 | **企业** | 需要，含对公账户 | 二级商户号（对公） | ✅ 专票 | ✅ 已建模 |
| 2 | **个体工商户** | 需要 | 二级商户号 | ✅ 普票/专票 | ✅ 已建模 |
| 3 | **小微商户** | **免** | 二级商户号，**钱打到个人卡** | ❌ | ✅ 已建模 |
| 4 | **自然人闲置（咸鱼式）** | 免 | **微信生态里没有通路** | ❌ | ❌ 未建模 |

前三种都是「经营者」——持续卖货、有收款商户号、能进件分账，
双轨方案的第三方轨道原样覆盖它们。**第四种不是。**

### 5.6 咸鱼式 C2C 在微信小程序里的三道坎

**坎一：自然人收不了款。** 微信支付的收款方必须是商户。小微商户虽然免执照，
但它是「个人经营者」不是「卖闲置的自然人」——要实名 + 人脸 + 受行业白名单限制
（`sys_legal_form` 的注释已写明：**线上业态不收**）。让邻居为了卖一个旧童车
去开小微商户号，这个门槛比交易本身重得多。

**坎二：担保交易没有对等产品。** 闲鱼能做「确认收货再打款」，靠的是支付宝的
担保交易——资金进的是**持牌机构的担保账户**，不是闲鱼自己的账户。
微信侧没有面向小程序开放的等价产品。

于是平台只剩「先收进平台户、确认收货后转给卖家」这条路，
而那正是 §一 的红线：**代收自然人之间的交易资金，是二清**，且比商户代收更敏感
（对手方是自然人，无合同无发票）。

**坎三：税与票。** 自然人卖闲置在税上通常不构成经营行为，但**平台有涉税信息报送义务**，
且买家永远拿不到发票。这对「邻居之间卖个旧东西」无所谓，
一旦有人把它当生意做（同一个人月销几十单），平台就站在了「明知是经营却按闲置处理」的位置上。

> 具体的报送义务与判定标准近年在变，**必须由法务确认**，本文不给结论。

### 5.7 那社区二手怎么做：把「撮合」和「资金」分开

坎一二三都卡在**资金**上。而社区场景恰好有一个别处没有的条件：**邻居是见得到面的**。

所以建议：**做信息撮合，不碰资金。**

| 平台做 | 平台不做 |
|---|---|
| 发布闲置、图片、描述、价格 | ❌ 代收货款 |
| 邻里沟通（站内信/加微信） | ❌ 担保交易 |
| 自提点当面交易的时间地点 | ❌ 平台退款 |
| 信用与举报（复用 `mch_violation` 的思路） | ❌ 开票 |

成交与付款走**线下当面**或买卖双方自行微信转账。平台的角色是「小区公告栏」，
不是「交易平台」——这个定位同时解决了三道坎，而且**不需要 EDI**
（不撮合资金就不构成电商平台的经营范围要求，但**这一条要法务确认**）。

代价要说清楚：**没有平台担保，纠纷得邻居自己解决**。社区场景下这是可接受的
——当面验货、抬头不见低头见，本来就是最强的约束。跨小区、跨城就不成立了。

### 5.8 技术上怎么落：**不要塞进主交易链路**

C2C 闲置与主交易在几乎每个环节都不同：无库存、无履约、无结算、无售后、无发票。
硬塞进 `ord_order` / `stl_bill` 的代价是每张表都要多一堆「C2C 时无意义」的分支。

建议**独立一张 `cmt_second_hand`（社区闲置）**，与订单体系解耦：

| 它有 | 它没有 |
|---|---|
| 发布者（`user_no`，不是 `entity_no`） | 订单号、支付、结算 |
| 标题/图/描述/期望价 | 库存、SKU、履约 |
| 状态：在售 / 已下架 / 已成交（**自行标记**） | 状态机推进、售后 |
| 举报与下架 | 分账、开票 |

**「已成交」由发布者自己点**，平台不知道也不该知道钱有没有付——
这正是「不碰资金」在数据上的体现。

> 若将来要做担保交易，那是**另立一个模块**（要接持牌担保产品），
> 不是给这张表加字段。现在留好边界，将来加得进去。

## 五之四、三种经营者主体的资金处理（重点：小微）

### 5.9 先澄清：资金链路三者完全相同

容易以为小微要走一条特殊的资金路径。**不是的。**
在收付通里，三种主体都是**二级商户**，分账链路一模一样：

```
用户付款 ─► 平台商户号 ─(分账)─► 二级商户号 ─► 结算账户
                                    ▲
                        企业 / 个体户 / 小微 在这里没有区别
```

差别全部在**进件那一刻之前**与**能力边界**上，不在钱怎么走：

| | 企业 | 个体工商户 | **小微** |
|---|---|---|---|
| 进件材料 | 执照 + 对公户 + 法人 | 执照 + 法人 | **身份证 + 人脸，免执照** |
| 结算账户 | 对公 | 对公或法人个人卡 | **个人银行卡** |
| 授权的支付方式 | JSAPI / APP / H5 / Native | 同 | **仅 JSAPI / Native / 付款码** |
| 行业限制 | 无 | 无 | **白名单，线上业态不收** |
| 开发票 | 专票 | 普票/专票 | **开不了** |
| 交易累计限额 | 无特殊 | 无特殊 | **有** |
| 作为分账接收方 | ✅ | ✅ | ✅ |

**最后一行是关键**：小微一样能收分账。所以双轨方案的第三方轨道
（`PLATFORM_HOLD` / `DIRECT_SPLIT`）对三者原样适用，**不需要为小微开分支**。

### 5.10 小微的五个坑（按会不会当场炸排序）

**坑一：没有 H5 与 App 支付 —— 会当场下不了单。**

`MchPaymentMerchant` 的注释已写明「只被授权 JSAPI/Native/付款码」。
后果不是「体验差一点」，是**小微商家的货在 H5 端与 App 端直接付不了款**。

更隐蔽的是**混合购物车**：一单里既有小微的商品又有企业的商品，
合单支付会因为其中一个二级商户不支持该支付方式而**整单失败**，
而报错指向的是通道，不是「哪件商品不行」。

> 处理：结算前按「本次支付方式 × 各商家授权能力」校验，
> 不支持的商品要**在进收银台之前**分出来，而不是等通道拒绝。
> `pay_methods` 列已在存能力，注释还特意写了「只能由通道回执写入，禁止按主体类型推断」
> —— 推断会在规则变化时静默失效。

**坑二：累计限额 —— 会在某天突然收不了钱。**

小微有交易累计上限。额度用尽的表现是交易被拒，而**商家侧只看到「支付失败」**，
他不会知道是自己的额度到顶了。

> 处理：本地累计已成交金额 + 阈值预警（如 70% / 90%），预警时**直接给升级入口**
> —— 升个体工商户是解法，而不是让他停业等下个周期。
> 具体额度以微信当期规则为准，**不要写死在代码里**，放 `sys_setting`。

**坑三：开不了票 —— 用户会在下单之后才发现。**

第三方模式下平台不能替商家开票（那是自营的做法，见 §四）。

> 处理：商品详情页与结算页**明确标注「该商品不支持开票」**。
> 不标的后果是用户下单、收货、然后来客服要票 —— 那时已经无解，
> 只能退款，而货已经吃掉了。
> `mch_payment_merchant.invoice_capable` 就是给这件事用的，**现在没有任何界面读它**。

**坑四：结算到个人卡 —— 税务责任不清。**

小微的钱打到个人银行卡，性质上是个人的经营所得。商家多半没有申报意识，
而平台按现行规定有涉税信息报送义务。

> 这条不是技术问题，**必须由财务/法务给口径**：平台是否代扣代缴、报送什么、
> 达到什么规模要求商家升级主体。本文不给结论。

**坑五：行业白名单 —— 进件时才发现选不了。**

线上业态不收小微。社区电商的零售/生鲜/餐饮通常在白名单内，
但要按 `sys_industry.micro_allowed` 逐个行业校验（项目已建模）。

> 处理：入驻表单在选完行业后**立刻**过滤可选主体类型，
> 而不是让商家填完全部资料才在提交时被拒。

### 5.11 小微是「入门档」，产品上要设计升级路径

小微存在的意义是**降低入驻门槛**，不是长期形态。三个配套：

| 措施 | 说明 | 现状 |
|---|---|---|
| 平台承担手续费 | `feeBearer=PLATFORM`，小微阶段平台贴，升级后转商家 | ✅ 已建模，注释写明这是「产品杠杆不是技术约束」 |
| 额度预警 + 升级引导 | 见坑二 | ❌ 未建 |
| 升级不中断经营 | 升个体户要重新进件拿新 `sub_mchid`，**旧单的分账仍走旧号** | ⚠️ 靠 V14 的快照原则 |

**第三条最容易出事**：升级那天若把未分账的历史单一起切到新商户号，
分账会失败（旧单的支付发生在旧号下）。`stl_bill.pay_merchant_no` 是快照列，
天然挡住了这个问题——**前提是升级时不去改历史行**。

### 5.12 要补的模型（不多）

| 改动 | 用途 |
|---|---|
| `mch_payment_merchant.quota_used_minor` + `quota_period` | 小微额度本地累计（坑二） |
| `sys_setting` 的 `pay.micro-quota` | 额度阈值与预警线，不写死在代码里 |
| 结算前的支付能力校验 | 坑一，读 `pay_methods`，**不新增字段** |
| 商品页读 `invoice_capable` | 坑三，**不新增字段** |

**五个坑里三个靠已有字段就能解，只有额度要加两列。**

### 5.13 「不开票」能不能规避税务问题：不能，但可以让义务各归各位

这是最容易建立在错误前提上的一处，先把误区拆掉。

#### 误区：不开票 = 没有纳税义务

**不是。** 纳税义务由「有没有发生应税销售」触发，**不由「开没开票」触发**。
增值税申报表上专门有「未开具发票」栏次，就是给这种情况用的。

所以「平台不支持开票」这个动作：

| 它规避了什么 | 它规避不了什么 |
|---|---|
| 平台自己的开票义务 | 商家的纳税义务 |
| —— 而这个义务**平台本来就没有** | 平台的**涉税信息报送**义务 |

#### 第三方模式下，平台不给消费者开票**本来就是对的**

这不是规避，是**归位**：第三方模式的销售方是商家，不是平台。
平台去给消费者开销售发票，反而是错的——那等于平台自认是销售方，
把自己变成了自营（见 §四，两者的收入确认与税率完全不同）。

平台该开的票只有一张：**给商家开服务费/佣金发票**。

> 所以问题不该问成「平台如何规避」，而该问成
> **「消费者拿不到票，谁来兜、会不会出事」**。下面三条才是真正要处理的。

#### 真正要处理的三件事

**一、消费者侧：不能只写「不支持开票」就完事**

经营者原则上不得拒绝消费者索要发票。小微虽免执照但仍是经营者，
小规模纳税人**可以去税务机关代开**。所以正确的表述不是「本商品不能开票」，
而是分两层：

| 层 | 做法 |
|---|---|
| 下单前 | 明确标注「**平台不代开发票**」，并说明可向商家索取 |
| 下单后 | 提供**电子交易凭证**（不是发票，但能证明交易），报销场景至少有个东西 |

只写「不支持开票」而不给任何替代，投诉时平台站不住——它看起来像
「平台知道开不了票还卖」。

**二、平台侧：涉税信息报送躲不掉，而且不开票时更受关注**

近年监管要求互联网平台报送经营者身份与收入信息。**这个义务不因不开票而消失**
——恰恰相反，没有发票流的场景，平台报送的数据就是税务机关掌握交易的主要来源。

> 具体报送范围、频率、起报门槛在持续调整，**必须由财务/税务顾问按当期规定确认**。
> 本文只说结论：**别把「不开票」当成「平台没事」**。

**三、商家侧：起征点是真正的分界线**

实践中小微不开票之所以「问题不大」，**不是因为不开票，而是因为销售额在起征点以下**
——小规模纳税人月销售额低于免征额时增值税免征。

这给出一条可执行的规则，而且它与 §5.10 坑二的额度监控**是同一个机制**：

```
监控商家累计销售额
   ├─ 接近起征点 ──► 提示商家纳税义务 + 引导升级个体工商户
   └─ 持续超过   ──► 要求升级主体，否则限制继续经营
```

**平台最危险的位置，是明知商家已持续超过起征点、仍按「小微不开票」放着不管。**
那时「不知情」讲不通——交易数据全在平台手里。

#### 产品上落到三条

| # | 做法 | 复用什么 |
|---|---|---|
| 1 | 商品页/结算页标注「平台不代开发票，可向商家索取」 | `invoice_capable`（已有字段，无界面读） |
| 2 | 订单完成后出**电子交易凭证** | 订单数据，不新增表 |
| 3 | 销售额监控 + 起征点预警 + 升级引导 | **与小微额度监控同一套**（§5.12 的两列） |

第 3 条是关键：**它同时解决了额度（微信的限制）与起征点（税务的限制）两件事**，
两者都指向同一个动作——**引导升级个体工商户**。

> ⚠️ 起征点数额、免征政策、报送要求都会变，且各地执行口径不同。
> **本节给的是机制，不是可直接套用的数字与结论，必须由财务/税务顾问确认。**


### 5.14 钱「先进平台」之后，怎么说明结算给了小微

这是小微场景里最实际的一个问题：**小微开不了票，平台付给他的钱拿什么做凭证？**

答案取决于一个区分，而这个区分决定了「要不要发票」：

#### 「进平台」进的是哪个账户

| | 微信**平台商户号** | 平台的**银行对公账户** |
|---|---|---|
| 钱的位置 | 微信（持牌机构）的账户体系内 | 平台自己的银行账户 |
| 平台是否「收到」这笔钱 | **否**，只是待分账状态 | **是** |
| 会计上 | 商家那部分**不进平台的收入/成本** | 全额进平台，付出去要有凭证 |
| 需要小微开票吗 | **不需要** | **需要，而小微开不了 → 无解** |
| 合规 | ✅ | ❌ 二清 |

**`PLATFORM_HOLD` 模式下钱进的是前者。** 所以：

> **平台不需要向小微索取发票，因为这笔钱从未构成平台的成本。**
> 平台账上只体现佣金收入，商家那部分是「过路资金」，
> 在平台的利润表里根本不出现。

反过来看后者，就能明白二清除了违规之外为什么还致命：钱真进了平台对公账户，
付给小微时拿不到发票 → **这笔支出无法税前列支** → 平台要按**全额**缴税。
一边违规，一边多缴税，没有任何一面是划算的。

#### 那「说明」靠什么：三层证据，项目已经建了两层

| 层 | 证据 | 谁出 | 现状 |
|---|---|---|---|
| 1 | **微信资金账单 / 分账明细** | 微信（第三方，最有力） | 通道侧现成 |
| 2 | **结算单 + 分账流水** | 平台系统 | ✅ `stl_bill` + `stl_split_log` 已建 |
| 3 | **进件资料** | 平台留存 | ✅ `mch_payment_merchant` 已建 |

关键在第 1 层：**分账明细是微信出的，不是平台自说自话**。
`stl_split_log.provider_no`（支付服务商回执号）就是把平台记录与微信回执勾连起来的那个键
——注释里写的「失败也写日志：『发过但失败了』和『压根没发』是完全不同的排查方向」，
在这里的价值是**每一笔都能回查到通道侧的对应记录**。

所以证据链不是「平台声称打了钱」，而是：

```
平台结算单（算出该给多少）
   └─► 分账指令（request_no 幂等）
          └─► 微信回执（provider_no）
                 └─► 微信资金账单（第三方账单，可作为凭证）
```

#### 缺的是第四件事：把这条链呈现给商家

三层证据都在库里，但**商家看不到**。目前 `/biz/settle/bills` 只有列表和详情，
没有可下载的对账单。

小微商家尤其需要它：他没有发票、没有对公流水，
**平台出的对账单是他唯一能说明「这笔钱是怎么来的」的东西**——
无论是自己记账、还是将来升级个体户后向税务说明历史收入。

要补的是一份**商家对账单**，按周期出，至少含：

| 字段 | 为什么必须有 |
|---|---|
| 订单明细（单号、金额、时间） | 能逐笔对上 |
| 平台佣金与费率 | 差额要能解释，否则商家会怀疑被少给了 |
| 实结金额 | 与到账金额一致 |
| **分账回执号**（`provider_no`） | 与微信账单勾对的锚点 |
| 分账时间与状态 | 「还没到账」与「已到账」要分得清 |
| 收款账户（掩码） | 确认打给了谁 |

> 这不是报表需求，是**凭证需求**。做成「页面能看」还不够，
> 要能**导出留存**——商家和平台都要留档。

#### 一条不能碰的红线

平台商户号里属于商家的那部分资金，**绝不能提现到平台自己的对公账户**。
一旦提现，前面那张表的左列就变成了右列：性质从「待分账」变成「已归集」，
合规定性随之改变。

> 系统层面挡不住这件事（提现是在微信商户平台上手工操作的），
> 所以它是一条**财务操作纪律**，要写进结算的操作手册，不是写进代码。

## 六、数据模型

### 6.1 门店上的两个字段

| 字段 | 取值 | 说明 |
|---|---|---|
| `mch_store.business_mode` | `SELF_OPERATED` / `THIRD_PARTY` | 默认 `SELF_OPERATED`（当前无 EDI） |
| `mch_store.settle_mode` | `PLATFORM_HOLD` / `DIRECT_SPLIT` | **仅 `THIRD_PARTY` 有意义**；自营时忽略 |
| `mch_store.freeze_days` | 整数，空=平台默认 | 仅 `PLATFORM_HOLD` 有意义 |

### 6.1.1 费率从配置迁到库

现状 `merchantOwnedRate` / `platformRate` 是 `@Value` 注入的**应用配置**，
按 `traffic_source` 分两档（自带客流 0%、平台客流 X%）。
「在运营平台设置」意味着它要能在后台改、且**改动要留痕**。

| 落点 | 内容 |
|---|---|
| `sys_setting` 的 `settle.fee-rule` | 全局默认费率（两档），JSON。与售后极速退阈值同一套机制，**不建新表** |
| `mch_store.commission_rate` | 门店级覆盖，空 = 用全局。有些店要单独谈费率 |
| `stl_bill.commission_rate` | **已存在的快照列**，不动。费率改了不影响历史账 |

**不建费率表的理由**：费率是「一组参数」不是「一批记录」，
`sys_setting` 已经承担了同类角色。要历史版本的话，`sys_setting` 的 `updated_by`
加上审计日志已经够追溯——真需要版本表时再拆，那时是加表不是改表。

**为什么不合成一个枚举**：合成之后「自营 + 直连分账」这种非法组合在类型上是可表达的，
只能靠运行时校验挡；分成两个字段，非法组合在语义上就不存在。

### 6.2 结算单：一张表承载两条轨道

`stl_bill` **不拆表**。两条轨道的字段需求高度重叠，拆开会让对账要 union 两张表。

| 字段 | 自营语义 | 第三方语义 |
|---|---|---|
| `entity_no` | 供应商 | 商家主体 |
| `gross_minor` | 采购金额 | 结算基数 |
| `commission_minor` | 平台毛利 | 平台佣金 |
| `net_minor` | **应付供应商** | 应分给商家 |
| `status` | `PENDING_RECON` → `CONFIRMED` → `PAID` | `PENDING` → `SPLITTABLE` → `SPLIT` |

**新增三个快照字段**（快照的理由同 V14：改配置不能改历史账）：

| 字段 | 说明 |
|---|---|
| `business_mode` | 下单时的经营模式快照。**决定这张单走哪条状态机** |
| `settle_mode` | 资金模式快照（第三方才有值） |
| `splittable_at` | 可分账时间（`PLATFORM_HOLD` = 支付 + 冻结期；`DIRECT_SPLIT` = 支付时间） |

**再加两个自营专用**：`payment_ref`（付款凭证号）、`paid_at`（付款时间）。
自营的「打款」是财务在网银做的，系统只**登记**，不执行——理由见上一版方案，
让业务系统去动公司对公账户是财务内控问题，不是技术问题。

### 6.3 积分：不改表，只改「谁出资」的判定

`stl_points_pool` 的 `pool_type` 已经区分了出资方。双轨下只需在写流水时按
`business_mode` 选类型：

- 自营 → 只写 `PLATFORM_ISSUE`
- 第三方 → 按现有规则写 `MERCHANT_PAY` / `PLATFORM_ISSUE`

**零表结构改动。** 现有积分方案设计得够宽，这是它的功劳，不是巧合。

## 七、状态机：两条，不是一条

```
自营（business_mode = SELF_OPERATED）
  PENDING_RECON ──(对账确认)──► CONFIRMED ──(财务登记已付)──► PAID
        └──(订单退款)──► CANCELLED

第三方（business_mode = THIRD_PARTY）
  PENDING ──(splittable_at 到期)──► SPLITTABLE ──(下发成功)──► SPLIT
     │                                  └──(失败)──► FAILED ──(重试)──► SPLITTABLE
     └──(订单退款且未分账)──► CANCELLED
```

**刻意不合并成一条**。上一版我把它们合并了，那是错的：
「对账确认」与「分账下发」不是同一个动作的两种实现——
前者是人工核对后点确认，后者是系统调接口。合并会让状态名对不上任何一边的心智。

`worker` 只扫第三方那条；自营那条由运营在后台推进。

| 位置 | 自营 | 第三方 |
|---|---|---|
| 商品详情页「销售方」 | 平台 | 商家 |
| 发票抬头开具方 | 平台 | 商家 |
| 售后「联系谁」 | 平台客服 | 商家，平台兜底 |
| B 端能改什么 | 供应商只管供货，**不能改售价** | 商家掌握定价 |

**「自营店的价格谁定」是这里最容易做错的一条**：自营意味着平台是卖方，
定价权在平台。若仍让供应商改售价，等于平台对自己卖的货没有定价权，
出了低价错误还得平台承担。

## 十、落地顺序

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **A（现在）** | 两个字段 + `stl_bill` 三个快照字段与自营状态机 + 自营三条端点 | 无 |
| **B（现在）** | 三端按自营口径改销售方/开票/售后责任/定价权 | A |
| **C** | 门店模式配置界面与审批留痕 | A |
| **D（EDI 后）** | 第三方轨道：进件、分账、双资金模式 | EDI + 收付通 |
| **E（EDI 后）** | 积分补差接真接口 | D |

**A、B 现在就能做完，且做完之后系统就是「双轨就绪」的**——
D 到来时是往已有骨架里填第三方分支，不是重构。

## 十一、待 review（我做的判断，逐条确认）

| # | 判断 | 若错了会怎样 |
|---|---|---|
| 1 | 双轨长期并存，不是过渡 | 若确定将来全平台化，A 阶段的自营状态机是浪费 |
| 2 | 经营模式与资金模式是**两个正交轴**，不是一个三值枚举 | 合成一个会让非法组合可表达 |
| 3 | 粒度在**门店**，不在主体 | 若只需主体级，字段挂 `mch_entity` 更简单 |
| 4 | `stl_bill` 一张表两套语义，不拆表 | 若财务要求两套单据完全隔离，得拆 |
| 5 | 两条状态机分开，不合并 | 合并会让状态名对不上任何一边 |
| 6 | 自营下积分只记平台成本，不走补差 | 若自营也要给供应商补差，链路要保留 |
| 7 | ~~自营的定价权在平台~~ → **已决策：商家可改价** | 已采纳。风险用价格下限 + 改价告警 + 留痕接住（§5.3） |
| 8 | 抽成率两条轨道共用一个配置，只是记账口径不同 | 若财务要求两套独立费率，需拆成两个字段 |
| 9 | **抽成率下限由「供货方能否开票」决定**，不是 0 | 若忽略，自营 + 0 抽成 + 不能开票 = 每单亏约 11.5% 税 |
| 10 | 费率落 `sys_setting` + 门店级覆盖，不建费率表 | 若要费率历史版本与生效时间，需要独立表 |
| 11 | **「平台不开票」不能规避税务问题**，只是让义务各归各位 | 若按「不开票=没事」设计，平台会停在明知商家超起征点却不管的位置上 |
| 12 | 起征点监控与小微额度监控**是同一套机制**，都指向「引导升级个体户」 | 若分开做，会出现两套预警各说各话 |
| 13 | `PLATFORM_HOLD` 下平台**不需要小微开票**，因为那笔钱不进平台的收入成本 | 若财务认为需要凭证入账，说明钱其实进了对公户，那就是二清 |
| 14 | 商家对账单是**凭证**不是报表，必须可导出留存 | 只做页面展示的话，小微将来无法向税务说明历史收入 |

**§四 的税务结论必须由财务确认**——它是双轨的经济动因，我只给了结构，
具体税率与处理方式不能按本文执行。
