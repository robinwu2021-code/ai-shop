## 一、盘点结果

| 端 | 支付 | 积分 | 合计缺口 |
|---|---|---|---:|
| C 端 | 现有 4，缺 **13** | 现有 3，缺 **5** | 18 |
| B 端 | 现有 7，缺 **11** | 现有 3，缺 **5** | 16 |
| 运营端 | 现有 20，缺 **8** | 现有 **0**，缺 **8** | 16 |

> **第四个维度是后台**（§五）。前三个维度列的是「看得到什么」，
> 而钱是靠**写侧与定时任务**动的 —— 那一块目前**基本是空的**，
> 详见 §五。它不在三端里，但它才是这套设计能不能跑起来的关键。

两处失衡值得先说：

- **支付**：运营端最全（结算/分账/提现/发票/税务/对账差异都有），
  C/B 两端薄得多 —— 而它们才是钱真正流经的地方
- **积分**：C/B 两端接口齐、页面也用上了（可用/待生效分开展示、到期提醒都在），
  **运营端一个端点都没有** —— 平台既看不到池子，也调不了任何参数

### 最大的一个缺口

```ts
payOrder(orderNo: string): Promise<Order>;
```

**这个签名是不成立的。** 真实的支付要：

1. 端上带着**支付方式**（微信/支付宝）和**端**（小程序/APP/H5）来发起
2. 服务端返回**通道的支付参数**（微信的 `prepay_id` + 签名串 / 支付宝的 `orderStr`），
   端上拿它去唤起收银台
3. 用户在收银台完成后，端上**主动查一次结果**（不能只等回调 ——
   回调可能晚到或丢失，而用户已经在结果页等着）

现在的签名把这三步压成了「调一下就返回订单」，**接真通道时必然重写**。

## 二、C 端（支付 13 + 积分 5）

### 支付主链路（5 项，**P0**）

| # | 功能 | 为什么缺不得 |
|---|---|---|
| C-P1 | **`payOrder` 改签名**：入参带 `payChannel` + `payScene`，出参返回通道支付参数 | 现在的签名唤不起收银台 |
| C-P2 | **支付结果查询** `payResult(orderNo)` | 回调可能晚到或丢失，端上必须能主动查。**只等回调 = 用户卡在「支付中」** |
| C-P3 | **重新支付** `repay(orderNo)`：未超时的待付单换个方式再付 | 用户第一次选错通道/余额不足，现在只能取消重下，购物车得重来 |
| C-P4 | **支付方式可用性**：按端与商家进件状态过滤 | 商家没开通支付宝却给用户显示支付宝，点了才失败 |
| C-P5 | **待支付倒计时**：`payDeadlineAt` 已在库里，端上没用 | 用户不知道还剩多久，超时关单后一脸问号 |

> C-P4 的判据已经有了：`usr_merchant_payment.pay_methods` + `sys_pay_channel.enabled`
> + `SCENE_PAY_METHOD`。**数据齐了，只是没有接口把它暴露给端上。**

| C-R3 | **一次申请勾选多件** | 通道要求退款间隔 60 秒，按行拆会让用户等 5 分钟（三端落点 C1） |

### 积分（缺 5 项）

按用户真正会问的问题来列：

| # | 用户的问题 | 功能 | 状态 |
|---|---|---|---|
| C-J1 | 我有多少分？花到哪去了？ | 账户 + 流水 | ✅ 已做 |
| C-J2 | 这单能抵多少？ | 结算页试算 | ✅ 已做 |
| C-J3 | 待生效的什么时候能用？ | `pendingBalance` + `pendingActivateAt` | ✅ 已做 |
| C-J4 | **我的分什么时候过期？** | 账户到期日 | ✅ 字段与展示都有 |
| C-J5 | **怎么才能不过期？** | 规则说明：**任何积分变动都续期**（消费或使用都算） | ❌ 缺。滚动到期的到期日**因人而异**，用户不可能自己算出来，只给一个日期等于没解释 |
| C-J6 | **到期前提醒我** | 推送。`expire_notified_at` 幂等位已在库里 | ❌ 缺任务与推送。**到期是一次性全部清零**，不提醒这个模型对用户是敌意的 |
| C-J7 | **哪些店能用积分？** | 店铺列表/详情标注 | ❌ 缺。现在到结算页才发现不能用 |
| C-J8 | **退款时积分怎么算？** | 扣回规则说明 + 退款单明示扣减额 | ❌ 缺。与 C-R4 同一条 |
| C-J9 | 我在这家店消费能得多少分？ | 商品/结算页预告 | ❌ 缺。`earnChip` 文案有，数据没接 |

> **C-J5 与 C-J6 是一对**，缺一不可。滚动到期的规则是「不活跃 365 天才清零」——
> 对用户其实**更宽松**，但如果他不知道规则、也没收到提醒，
> 体验就是「我的分突然全没了」，比固定到期日更糟。

> 而发收对称原则下他一关，就既不发也不收，积分网络会萎缩。

| O-C4 | **未对账清单**带截止日倒计时，超 3 个月标红 | 三端落点 O1。**超期就永远查不清** |

### 积分（缺 8 项）—— **运营端目前一个端点都没有**

| # | 平台要做什么 | 状态 |
|---|---|---|
| O-J1 | **总览**：流通中的积分 vs 池子余额，**恒等式 2 的两边摆在一起** | Service 层已实现（`PointsService.overview`），**无 controller / 无页面** |
| O-J2 | **池子流水**，按 `(market, pay_channel)` 分账本 | ❌。不按通道看的话账面永远是平的，而两个真实账户一个溢一个空 |
| O-J3 | **跨通道轧差建议**：两侧净额与调拨额 | ❌ |
| O-J4 | **商家维度**：各商家发分成本与被消耗量 | ❌ |
| O-J5 | **调整发放比例**（全局 / 按商家） | ❌。`POINTS.defaultEarnRatio` 现在是代码常量，改要发版 |
| O-J6 | **社区开关**（L2） | ❌。`cmt_community.points_enabled` **有列无接口** |
| O-J7 | **按行业强制开**（`points_forced`） | ❌。`sys_industry.points_forced` 已建（`V40`），**controller 未做** |
| O-J8 | **全局参数**：兑换比例、抵扣上限、无活动期 | ❌。全在代码常量里 |
| O-J9 | **恒等式告警**：五条恒等式的日常校验结果 | ❌。**这是整套设计唯一的自检手段**，没有它，账错了没人知道 |

> **O-J9 是运营端积分部分最要紧的一条。**
> [积分域方案](./积分域-完整方案.md)列了五条恒等式（余额 == Σ流水、
> 池子余额 == 流通积分×汇率、两本账勾稽…），但**它们目前没有任何地方在跑**。
> 恒等式不跑等于没写。

> **O-J5 / O-J8 是同一类问题**：兑换比例、发放比例、抵扣上限、无活动期
> 全是**代码常量**（`POINTS.*`）。它们是**业务参数**，调整不该发版 ——
> 与 `sys_pay_channel` / `sys_industry` 一样，应该入库由运营维护。

## 五、后台：任务与写侧链路

**这一块目前基本是空的。** 现状：

| 基础设施 | 状态 |
|---|---|
| 定时任务框架（`@Scheduled` / ShedLock / xxl-job） | ❌ **一个都没有** |
| 任务/作业类 | ❌ 零个 |
| 事件表 `sys_outbox` | ✅ 表在，无消费者 |
| 支付回调 | 🚧 只有 `/callback/pay/stub`（假回调） |

前三个维度列的全是**读侧**（查询、展示、配置）。而这套设计里，
钱的每一次移动都发生在**写侧或定时任务**里 —— 那部分一行都还没有。

### 资金链路的写侧（10 项）

| # | 动作 | 触发 | 关键约束 |
|---|---|---|---|
| S-W1 | **支付回调处理** | 通道推送 | 验签 + **幂等** + 金额比对。回调会重复推、会晚到，**处理不幂等就是重复发货** |
| S-W2 | **补差调用** | 支付成功后立即 | 时序硬约束：**支付成功后、分账前**。失败要重试 |
| S-W3 | **补差失败阻断分账** | 分账前校验 | 没补上就分账 → 基数是全额而账户只有实付 → 通道拒；**「部分成功」更糟** |
| S-W4 | **计提**（生成 `stl_bill`） | 支付成功 | 费率落快照。账面与资金是两个时点（`accrued_at` vs `split_at`） |
| S-W5 | **解冻 + 分账** | 售后期结束 | 与积分转可用**同一时点**。支付宝要先确认结算再等 30 秒 |
| S-W6 | **分账失败重试 / 转人工** | 失败时 | `Result.retry` 与 `Result.fatal` 已区分，**没有消费它的重试器** |
| S-W7 | **退款链路**：分账回退 → 补差回退 → 退款 | 售后通过 | 顺序不能乱。**部分回退**，不全额回退再重分 |
| S-W8 | **超时关单** | `pay_deadline_at` 到点 | 释放库存 |
| S-W9 | **对账任务**：下载账单 → 逐笔匹配 → 差异入库 | 每日 T+1 | 账单**次日 9 点**才生成，建议 10 点后取 |
| S-W10 | **掉单巡检**：`SUCCESS` 但长期未对账 | 每日 | **只能靠对账发现**，没有别的手段 |

> **S-W3 和 S-W6 都是「已经设计好但没人执行」**：
> `PayGateway` 的注释里写清了阻断规则、`Result` 区分了可重试与要人工 ——
> 但**没有任何代码在调用它们**。抽象层建好了，驱动它的那一层是空的。

### 积分的写侧（7 项）

对应 [接口与核心逻辑设计](./积分域-接口与核心逻辑设计.md) §二的七个算法，
**目前 `PointsService` 只有读侧**（接口注释里写明了为什么不暴露写侧入口）。

| # | 算法 | 触发 | 关键约束 |
|---|---|---|---|
| P-W1 | `grantOnPay` **发放** | 支付成功 | 记 `pending_balance` 不进 `balance`；扣商家服务费；**续期账户到期日** |
| P-W2 | `deductOnPlace` **抵扣** | 下单时（不是支付后） | 防同一笔分同时下多单。券先抵、积分后抵 |
| P-W3 | `confirmUseOnActivate` **兑付成立** | 售后期结束 | 与解冻分账同一时点。此前池子未付款 |
| P-W4 | `activateDaily` **待生效转正** | 每日 | 走 `idx_pts_activate`，按时间扫不按用户扫 |
| P-W5 | `reverse` **退款扣回** | 售后通过 | 三情形。账户不够扣的从退款里扣（`points_offset_minor`） |
| P-W6 | `expireDaily` **到期清零 + 提醒** | 每日 | **先提醒后清零**。`expire_notified_at` 幂等位已在库 |
| P-W7 | `reconcileDaily` **恒等式校验** | 每日 | **五条恒等式目前没有任何地方在跑** |

### 幂等与并发（3 项）

| # | 要什么 | 现状 |
|---|---|---|
| S-I1 | 支付回调幂等 | `sys_idempotent` 表在，回调没用它 |
| S-I2 | 积分账户**行锁**（并发抵扣） | `pts_user_account` 注释写着「锁行」，**没有实现** |
| S-I3 | 通道调用限流排队（退款 60 秒 / 分账 3 秒 / 30 QPS） | 限额已入 `sys_pay_channel`，**没有消费它的排队器** |

> **S-I2 值得单说**：同一用户并发下两单，都读到 500 分余额、都扣 300 ——
> 余额变成 -100 或者少扣一次。这类 bug **不会报错**，只会在对账时发现账不平。

## 六、优先级

### P0 —— 不做整块跑不起来（32 项）

**后台**（§五全部 20 项）—— **这一层不做，前三端做得再全也是空壳**：
钱不会动、账不会平、掉单没人知道。基础设施（定时任务框架）是第一块砖。

```
基础设施：定时任务框架 + 分布式锁
S-W1  支付回调处理（验签 + 幂等 + 金额比对）
S-W2  补差调用          S-W3  补差失败阻断分账
S-W4  计提              S-W5  解冻 + 分账
S-W6  分账失败重试器     S-W7  退款链路（三步顺序）
S-W8  超时关单          S-W9  对账任务
S-W10 掉单巡检
```

## 七、结构性的发现

### 零、前三端是「看得到什么」，后台才是「钱怎么动」

前面盘出的 40 多项前台功能，**没有一项会让钱移动一分**。
补差、分账、退款、发分、扣回、到期清零 —— 全在后台，而后台
**连定时任务框架都还没有**。

这不是「还没做完」，是**盘点维度一开始就漏了一整层**。
补上之后 P0 从 12 项变成 32 项，其中 20 项在后台。

### 一、`payOrder` 的签名从一开始就不对

不是「少了几个字段」，是**把三步压成了一步**。改它会连带动：
`ord_order.pay_channel` / `pay_scene`（已有列）、`stl_payment` 的收款流水、
以及端上的收银台唤起逻辑。**建议第一个做**，它是其余支付功能的地基。

### 二、售后单**没有自己的类型**

> 我起初写成「后端有、契约没有」—— **查证后是错的**，B 端的售后端点齐全
> （列表 / 同意 / 驳回 / 确认收货）。真正的问题在**形状**上。

`mAfterSaleList(): Promise<Order[]>` —— 返回的是订单，不是售后单。
shared 里有 `AfterSaleType` / `AfterSaleStatus` 两个枚举，
**却没有 `AfterSale` 实体类型**。

于是 `ord_after_sale` 的 20 列里，`refundMinor` / `liability`（定责）/
`pointsOffsetMinor`（积分扣减）/ `splitReversed`（是否已回退分账）/
`disputeReason`（申诉理由）**端上一个都拿不到** —— 而这几列恰好是
退款金额对不上时唯一能解释清楚的东西。

C 端的 C-R1（售后单详情）撞的是同一个洞：**没有类型，详情页无从做起**。

### 三、商家提现只有运营侧

运营端有 `listWithdrawals` / `decideWithdrawal`（审批），
但**商家没有发起提现的入口**。现在的资金流是「钱到了二级商户账户，商家自己去微信/支付宝提」，
如果是这个设计，B-S3 就不该做 —— **需要确认**。
