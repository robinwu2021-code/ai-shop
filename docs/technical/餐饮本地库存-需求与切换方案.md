# 餐饮本地库存：需求与切换方案

> 2026-10-29 用户明确：本期餐饮库存只使用餐饮系统本地库存，与独立进销存的联动另立任务。本文件作为当前餐饮库存方案的优先口径；旧设计及旧测试中的进销存 owner 结论保留为历史，不代表本期目标能力已经完成。
>
> 本地指餐饮后端管理的商家/门店库存，随餐饮集成部署或独立部署；不自动包含平板离线扣库。支付、真实外送平台及前端页面继续按既定范围后置。

## 1. 目标与现状

1. 商家门店可维护菜品、饮品、小料和配方所需的库存物料与余额；餐牌可售、下单、制作、出餐、退餐、停售恢复及餐饮消耗记录均只依赖餐饮本地库存。
2. 商品/SKU、价格、订单继续使用项目基础能力；库存余额属于餐饮本地 owner，不向独立进销存发起建档、锁定、出入库、查询、回退或同步。进销存联动另立后续任务，默认不启用。
3. 当前实现尚未满足新要求：`RecipeServiceImpl`、`DiningChannelModifierDemand`、`FoodChannelSourceFactsPortImpl`、`ProductionConsumptionServiceImpl` 使用 `MaterialCatalogQueryPort`/`InventoryProductionPort`；核心订单的 `IndustryOrderServiceImpl`、`IndustryChannelStockPreparation`、`IndustryFulfillmentServiceImpl` 使用 `InventoryReservationPort`/`InventoryDemandPlanPort`。独立 FOOD 的 `food-channel` 还提供到原库存服务的远程适配。普通 Mock 渠道和先吃后付的既有通过记录验证的是旧库存 owner，不等于本地库存方案已完成。
4. 基础商品 `PrdSku.stock/lockedStock` 为整数且承担零售库存语义，不直接复用为餐饮唯一账本：餐饮还需门店粒度、小料、组合、配方小数用量及制作阶段消耗。可复用 SKU 身份与价格，但不偷偷双写商品库存。

## 2. 业务范围

- 库存对象分为销售 SKU 对应成品、配料/原料；原料可不对应可销售 SKU。每个餐饮本地物料属于商家主体，使用门店独立余额和统一基础计量单位；允许多个门店分别启用，不假设同一销售 SKU 的库存全国共享。
- 配料组合沿用 `SALES_SKU`/`COMPONENTS` 模式：前者扣餐饮本地成品 SKU，后者按发布快照展开并扣本地成员物料，定价 SKU 只负责商品/价格身份；不得双扣。数量用 `BigDecimal`，单位必须有真实来源，不能按商品售价或父菜品单位猜测。
- 门店可配置跟踪库存或不跟踪、启用状态、初始入库、人工调整和原因；有权操作的商家人员可查余额与流水。未知、未初始化、不可售和不跟踪应明确区分。是否允许超卖、是否跨库存门店共享属于显式策略；本期默认不允许超卖，不默认跨门店共享。
- 新单包括餐饮堂食、外带、外送、扫码/收银/服务员及 Mock 渠道订单，均通过同一餐饮本地库存事实；先付后吃和先吃后付的库存预留、确认、制作及交付不创造支付事实。
- 退餐需按冻结订单行与原始库存操作判断：未使用预留释放；已制作或已交付是否返库依商家可售/损耗规则及真实处理凭据决定，不能自动把消耗的原料当作可售库存。部分退餐、重复请求及并发须防超退和重复入库。
- 本期只实现餐饮所需的库存、调整、流水、预留和实际消耗，不扩展采购、供应商、调拨、批次、成本核算或复杂进销存功能；毛利/净利在真实成本来源明确前不伪造。

## 3. 数据设计候选

沿既有餐饮 `fnb_` 前缀，使用餐饮业务主数据库与既有 `tenant_no`、`entity_no`、`store_no`、审计字段及版本约定。以下为候选，迁移版本/精度/索引需按现有项目规范和真实 MySQL 验证后确定。

| 表 | 内容与关键约束 |
| --- | --- |
| `fnb_stock_item` | 商家本地物料编号、类型、可选商品/SKU 引用、基础单位、追踪策略、状态、版本。SKU 身份仍由商品 owner 验证；无 SKU 的原料有餐饮本地身份，不伪装商品。 |
| `fnb_stock_balance` | 主体+门店+物料唯一余额：现存、预留、版本；可售量按明确口径计算，数据库条件更新/行锁防负数和并发超卖。 |
| `fnb_stock_reservation` | 原订单/业务来源、门店、请求幂等键、状态、计划 hash、生命周期版本和有效期；唯一约束防重复创建。 |
| `fnb_stock_reservation_item` | 原销售组件与物料叶子、计划数量、单位、已消耗/已释放量和阶段；允许分次，累计量不能越界，保留原始快照及来源版本。 |
| `fnb_stock_movement` | 追加式变动流水：操作、实际入出量、变更前后、来源、原因、操作人、发生时间和唯一幂等引用；不得覆盖或删除历史凭据。 |
| `fnb_stock_command` | 建档/调整/锁定/出库/释放/返还命令的请求指纹、状态、结果与幂等引用；同键同参重放原结果，同键异参冲突。 |

计量精度、约束、逻辑删除及幂等键长度按现有 SKU、餐饮和订单基础合同综合确定；加表前先检查现有迁移/索引/表名，增量迁移不得改历史 checksum。初始库存和手工调整必须在余额与流水同一事务提交，支持乐观/悲观并发控制。物料基础单位一旦有余额、流水或冻结订单引用，不允许直接修改单位；换单位需后续明确转换与迁移方案。

## 4. 服务接口与订单协作

餐饮模块内新增独立的本地库存领域、service、mapper、实体、DTO、B 端 controller 及必要内部合同，按餐饮既有包风格；独立部署由餐饮服务拥有该账本，集成部署使用同一实现。门店人员身份和权限来自现有账号、主体、门店体系，不在请求中信任主体号。

拟提供商家接口：物料创建/更新/查询、门店库存初始化与调整、可售库存查询、流水与预留查询；运营查看需使用现有权限与门店范围。订单内部合同提供原计划预留、确认、按原行分次消耗/交付、取消释放、查询与受控返还，所有写操作要求业务键和幂等键，返回原始库存操作/流水凭据，不伪造支付成功。

当前共享订单 SPI 以 `ObjectProvider` 检查**唯一** `InventoryDemandPlanPort` 和 `InventoryReservationPort` 实例；集成宿主同时存在零售进销存实现时，直接注册第二个实例会导致全行业失败。必须先设计并实现明确的库存权威选择：餐饮新单固定路由餐饮本地 owner，零售/美业继续原 owner；订单创建时冻结权威标识，后续交付、取消、退餐及恢复始终回到原权威。选择必须按可信原订单来源/持久化事实，不能让前端或第三方回调指定；旧合同和非餐饮行为保持兼容。是新增专用餐饮 SPI，还是对共享接口做受控 owner 路由，以现有部署合同及定向测试选择；不能只依赖 `@Primary`、bean 顺序或全局切换。

订单与本地库存若在同一数据库，可使用明确 owner 的本地事务或既有持久化命令/回执流程；独立 FOOD 与 CORE 跨服务时保持本地短事务、幂等、未知结果查询与恢复，不依赖跨库分布式事务。不得在本地事务中远程调用商品、订单、进销存或渠道。

## 5. 切换与历史数据

- 新单仅在本地库存可用、物料和余额已明确配置后启用；不得从商品 `stock`、旧库存或报表推算并写入初始余额。真实初始数量由商家盘点/授权导入或明确来源确认，来源记录可审计。
- 旧订单和旧库存回执保持不可变。识别旧库存权威及未完成订单；切换前要求完成、停止新动作或经明确的一次性对账和迁移，不能把旧预留当成本地余额、也不能对同一订单在两个 owner 重复扣减。若执行历史恢复必须使用原始权威，作为单独受控历史清理，不将其当成本期新单进销存联动；无凭据则保持待处理。
- 不删除现有进销存实现或更改零售/美业默认装配。通过功能开关、只读/灰度与回滚方案控制入口；默认关闭未完整验证的餐饮本地库存能力。V32 配料模式迁移已在专用本地 MySQL 应用，不修改历史迁移。
- 先核对当前未提交代码、已执行迁移及测试数据，保留失败记录；不清理共享测试库、不覆盖用户变更。报表在业务稳定后对接餐饮本地库存事实，历史成本缺失标未知。

## 6. 开发与验收顺序

1. 梳理现有餐饮/订单/库存接口调用图与所有库存写入，冻结新旧权威边界；把组合配料方案调整为本地物料与单位，不再继续开发餐饮直连进销存。
2. 细化本地物料、门店余额、预留、流水和命令表；新增迁移、实体、mapper、配置、商家 API 与本地库存服务。先完成编码和编译，不修改基础商品/零售库存事实。
3. 实现按行业和冻结权威路由；餐饮本地和渠道订单、配方、厨房、退餐接入本地库存，兼容集成及独立部署，支付仍保持独立。
4. 按用户安排集中测试：本地 MySQL 迁移、门店/主体隔离、并发超卖、原键重试、缺货、分次制作/交付、取消和部分退餐、组合/套餐及历史配置变更；Mock 外送只替代外部渠道。通过断言证明餐饮新单**没有调用**进销存，也没有改动进销存数据；同时验证零售现有库存未被切换。
5. 完成迁移和旧订单切换演练、独立代码审查及部署前验证后，按已有授权提交、推送和部署。真实进销存联动单独建任务，另行设计映射、同步、冲突和对账，不在本期实现。

### 共享订单路由的进一步代码核对

当前 `IndustryOrderServiceImpl` 在准备阶段先建立意图/来源绑定，再调用 `demands().reserve(...)` 或 `inventory().reserve(...)`；渠道准备的 `IndustryChannelStockPreparation.inventory()` 及交付的 `IndustryFulfillmentServiceImpl.exactProvider()` 同样只接受全局唯一 provider。`InventoryDemandPlanPort.Plan/Scope` 本身不含可信行业或库存权威，不能仅凭库存计划号推断来源。

本期拟在原订单来源绑定及渠道准入事实中新增可持久化的库存权威（例如 `FOOD_LOCAL` 与历史 `LEGACY_INVENTORY`，具体字段和迁移号开发前核对），在第一次库存操作之前由可信行业 owner 选定并冻结；同步到意图/恢复所需事实。每次预留、查回、取消、制作、交付、售后及重试，都由对应原始来源事实选择餐饮本地合同或原库存合同。历史缺字段按原先库存权威解释，绝不按当前开关改写；外部平台、客户端和员工请求不能提交该权威。新增餐饮本地 SPI/实现应与原全局库存 bean 分开注册，不能让零售和美业的 `ObjectProvider` 看到第二个同类型实现。跨服务调用须具备原服务令牌、主体/门店/订单与计划 hash 校验、短期凭据和超时后的原键查询恢复。

此路由尚未编码，相关历史订单的权威字段/回填和可安全恢复范围必须在迁移前用原始数据库事实验证；已有订单在本地库存未就绪时保持原状态，不能转成成功或自动清空。
