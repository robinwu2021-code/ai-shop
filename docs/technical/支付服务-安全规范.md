## §1 原则

1. **一个入口只认一种凭证**。七个前缀各挂一个鉴权器，解析成同一个 `PayCaller`；带错类型的凭证一律 401，不尝试「也许是另一种」。
2. **两道闸**：nginx 是**边缘网关**（TLS、按域名与前缀分流、粗限流、IP 白名单、安全头、请求体上限）；`pay-portal` 是**应用网关**（认人、验签、细限流、幂等、能力矩阵、留痕）。**任何一道都不假设另一道存在** —— 应用层照样校验 IP 白名单，nginx 照样拒绝 `/internal/`。
3. **失败即关闭**（fail closed）：配置缺失、密钥为空、时间不同步、查不到调用方 —— 一律拒绝，而不是放行或回落默认值。
4. **最小权限、最小字段**：调用方只拿到矩阵允许的动作；响应只给调用方需要的字段；顾客端只看得到自己面前这一单。
5. **钱和密钥的动作必须两个人、必须留痕**：发起与复核分属两方（商户发起退款、平台复核；出款两人；密钥录入人 ≠ 启用人）；审计只增不改。
6. **密钥不进仓库、不进日志、不回显**：只显示指纹；明文只在生成那一刻给一次。
7. **卡数据红线**：任何位置不出现明文卡号 / 磁道 / PIN（PCI DSS 范围控制，§2.8）。

### 1.1 拓扑与信任区

```
公网 ─┬─ www.{域名}        ──▶ nginx ──▶ shop-app(api)    /mp /biz（含 /biz/pay）/common …
      ├─ api.{域名}        ──▶ nginx ──▶ pay-portal       /open/pay/v1 · /pay/callback
      ├─ pay.{域名}        ──▶ nginx ──▶ checkout-h5 静态 + pay-portal /checkout/v1
      └─ terminal.{域名}   ──▶ nginx ──▶ pay-portal       /terminal/pay/v1（I7）
办公网 / VPN ── ops.{域名} ──▶ nginx ──▶ shop-app(ops)    /ops · /pay-ops/v1
内网（不对公网）            shop-app ⇄ pay-svc            /internal/pay/**（127.0.0.1 或私网）
出站                        pay-channel ──▶ 渠道网关（固定出口 IP）· BizNotifier ──▶ 接入方 webhook
```

| 区 | 谁在里面 | 进来要过 |
|---|---|---|
| Z0 公网不受信 | 顾客、第三方、渠道、终端 | nginx 边缘 + 对应鉴权器 |
| Z1 办公网 | 运营 | VPN / 办公网 IP + 运营会话 + `pay:*` |
| Z2 应用内网 | shop-app、pay-svc、job | 每调用方服务凭据 |
| Z3 数据 | MySQL、Redis、密钥 | 只对 Z2 开放；凭据部署注入 |

### 1.2 「网关」选型

**现在不引入 Spring Cloud Gateway / Kong / APISIX**，网关 = nginx（边缘）+ `pay-portal` 过滤器链（应用）。理由：
- 支付今天是内嵌形态（`pay-portal` 装在 `shop-app` 里），多一跳独立网关不增加隔离，只增加故障点与延迟；
- 签名校验、能力矩阵、幂等都依赖支付的业务数据（`pay_app`、`pay_app_grant`、`pay_api_nonce`），放在通用网关里反而要跨库读；
- ADR-044 已定：独立形态时 **`pay-portal` 自己就是 `pay-gateway` 进程**（S10），它只经 `/internal/pay/v1` 调 `pay-svc`。

**什么时候要独立的 API 网关产品**：接入方 > 20 家且需要自助开发者门户、或需要多机房流量调度时再评估（另起 ADR）。

## §2 各端鉴权规范（A1–A8）

每个入口按同一张表写：**凭证 · 校验顺序 · 失败 · 范围 · 限流 · 撤销**。失败响应对外**只给统一错误码**，具体原因只进日志与 `pay_api_request_log`，防止被当作探测器。

### 2.1 A1 内部系统 · 内嵌

| 项 | 规范 |
|---|---|
| 凭证 | 无（进程内调用 `PaymentPort` 等） |
| 校验 | 仍过能力矩阵：`PayCaller(type=INTERNAL, callerId=MALL\|FOOD…)`；**退款必须带 `onBehalfOf` = 商家操作员**（内部系统不能以系统身份退款） |
| 范围 | `merchantScope` 由调用方传入的门店算出并强制校验（防代码 bug，不防恶意） |

### 2.2 A2 内部系统 · HTTP（`/internal/pay/**`）

| 项 | 规范 |
|---|---|
| 凭证 | `X-Internal-Caller`（= `pay_app.app_no`：`MALL` / `FOOD` / …）+ `X-Internal-Credential`；**每个调用方一把**，服务端只存 SHA-256 哈希（`shop.pay.internal-callers.{caller}.credential-sha256`） |
| 校验 | 调用方存在 → 常量时间比较（`MessageDigest.isEqual`）→ **按路径前缀授权**（`MALL` 只能调收单 / 退款，`FOOD` 同；储值、权益各自的调用方另列）→ 进矩阵 |
| 失败 | 401（认不出）/ 403（路径不授权），原因只进日志 |
| 网络 | **永不对公网**：每个 nginx server 都 `location ^~ /internal/ { deny all; }`（只有本机 / 私网例外）；跨主机时加 mTLS 或私网 + 安全组 |
| 迁移 | 旧版 201 条共用 `X-Internal-Token`（G8）：收单 / 退款 8 条随 I5 S10 换 `v1`；储值、权益 187 条由各自迭代迁，**迁完前不得把 `/internal` 暴露到 127.0.0.1 以外** |
| 轮换 | 新旧两把并存（registry 允许同一调用方两个哈希）→ 调用方切新 → 删旧 |

### 2.3 A3 第三方 · 开放 API（`/open/pay/v1`）

**签名 v1（发布即冻结，改动只能出 v2）**：

```
X-App-Id: {appNo}
X-Timestamp: {毫秒时间戳}            ±300 秒
X-Nonce: {16–64 位随机串}            300 秒内同一 app 不可重复
X-Signature: base64(HMAC_SHA256(secret, stringToSign))  或  base64(SHA256withRSA(privateKey, stringToSign))
Idempotency-Key: {建单 / 退款建议必带}

stringToSign = METHOD + "\n"
             + PATH（不含域名与查询串，原样大小写）+ "\n"
             + CANONICAL_QUERY（参数名按字典序，名与值各自 RFC 3986 编码，用 & 连接；无则空串）+ "\n"
             + X-App-Id + "\n" + X-Timestamp + "\n" + X-Nonce + "\n"
             + hex(SHA256(原始请求体字节))（无体为空串的哈希）
```

| 项 | 规范 |
|---|---|
| 校验顺序 | AppId 存在且 `ACTIVE` → **IP 白名单**（`pay_app.ip_whitelist`，用 §4.5 的可信客户端 IP）→ 时间窗 → nonce 抢占（Redis `SET NX EX 300`，无 Redis 落 `pay_api_nonce` 唯一键）→ 逐把有效密钥验签（轮换重叠期两把）→ scope → `pay_app_grant`（门店 × 动作）。**全部在读业务表之前完成** |
| 请求体 | 先缓存原始字节再算哈希（`CachedBodyRequestWrapper`）；JSON 解析用同一份字节；上限 1MB（§4.7） |
| 失败 | 401 `AUTH_FAILED`（签名、时间窗、nonce、AppId 一律同一个码）/ 403 `FORBIDDEN`（scope、授权、IP）；写 `pay_api_request_log(result=REJECTED_AUTH)` |
| 密钥 | HMAC：服务端生成 32 字节随机密钥，**发放时明文只显示一次**，此后只显示指纹（SHA-256 前 8 字节 hex）；RSA：接入方自持私钥，我方只存公钥（≥ 2048 位，推荐 3072 或 EC P-256） |
| 沙箱 | `pay_app.sandbox=1` 的 app 只能打沙箱域名（`sandbox-api.{域名}`），密钥与生产完全分开；生产域名收到沙箱 AppId 一律 401 |
| 限流 | 应用层按 `pay_app.rate_limit_qps`（默认 20）；nginx 再按 IP 兜底（§4.6）；超限 429 + `Retry-After` |
| 退款加固 | 单独 scope `pay:refund` + 门店授权含 `REFUND` + `pay_app.daily_refund_limit_minor`（0 = 不允许）+ 复核规则 |
| 时钟 | 服务端 NTP 同步；时间窗失败在日志里记偏差秒数，便于接入方排查 |
| 撤销 | 运营端吊销密钥或停用 app → 立即生效（不缓存超过 60 秒） |

**webhook 出站**（我们 → 接入方）：同一套头与 `stringToSign`（`METHOD=POST`，`PATH` 为接入方 URL 的 path），用该接入方的 HMAC 密钥签；RSA 接入方另发一把**平台 webhook 签名公钥**（我方私钥在密钥模块）。
`webhook_url` 登记时校验：**只允许 https；解析后的 IP 不得落在私网 / 回环 / 链路本地 / 云元数据地址**（防 SSRF），投递时再解析一次再校验（防 DNS 重绑定）。

### 2.4 A4 渠道回调（`/pay/callback/**`）

| 项 | 规范 |
|---|---|
| 顺序 | 原文加密落 `pay_raw_payload` + 摘要落 `pay_callback_log` → **验签** → 收款商户匹配 → **主动查单** → 金额币种比对 → 按渠道交易号幂等入账（I2 `CallbackTemplate` 已是这个顺序） |
| 微信 | 验 `Wechatpay-Signature`（SHA256withRSA，`timestamp\nnonce\nbody\n`）；**补：时间窗 ±5 分钟（G4）**；**补：按 `Wechatpay-Serial` 选平台证书 / 公钥，支持新旧并存**（证书轮换）；APIv3 密钥解密资源体 |
| 支付宝 | RSA2 验签；**修 G5 配置项名**；`notify_id` 去重 |
| 不做 | **不做来源 IP 白名单**（渠道不承诺固定 IP，白名单会在渠道换机房时静默丢回调）；安全只靠验签 + 查单 |
| 响应 | 只按渠道要求的格式回成功 / 失败，不回任何内部信息 |
| 限流 | nginx 按前缀宽松限流（§4.6），宁可多收不可误拒 |
| 链 | 给 `/pay/callback/**` 一条显式的 Spring Security 链（`permitAll` + 无会话），而不是今天的「不匹配任何链」（G11） |

### 2.5 A5 顾客 · 收银台（`/checkout/v1` + `checkout-h5`）

| 项 | 规范 |
|---|---|
| 凭证 | 动态码：收银令牌 = 32 字节 CSPRNG，base64url；**库里只存 SHA-256**；绑定一张支付单；15 分钟（不超过支付单过期）；状态 `OPEN → PAYING → DONE / EXPIRED`，关单 / 退款 / 风控可**立即作废**（所以不用 JWT）。静态码：码号随机 ≥ 16 字节，可一键停用 |
| 能做的 | 只有：看本单（商户名、门店名、金额、币种、可用方式）、选方式、看结果。**金额、商户、收款商户全部来自服务端**；静态码只有金额由顾客输入，受单笔上限、单码日累计、单 IP / 设备频率约束 |
| 结果 | 结果页只给「成功 / 处理中 / 失败」，**不入账**；`return_url` 只跳 `pay_app.return_url_whitelist` 里的域名 |
| 字段 | 响应字段白名单；不出现手机号、姓名、地址、其它订单；错误不区分「令牌不存在」与「已过期」以外的原因 |
| 浏览器 | 同源，不开 CORS；CSP 严格（§4.4）；`X-Frame-Options: DENY` / `frame-ancestors 'none'`（防把收银台套进别人页面诱导支付）；`Referrer-Policy: no-referrer`（令牌在 URL 里，不能经 Referer 泄露） |
| 日志 | 令牌出现在路径里：nginx 与应用访问日志**只记令牌哈希前 8 位**（§4.8） |
| 防换贴码 | 页头与金额确认页显示「收款方：商户名 · 门店名」 |
| 限流 | 按 IP + 令牌 / 码（§4.6）；静态码另有业务限额 |
| 登录 | 可选 C 端登录（统一鉴权的 C 端令牌池），**支付不依赖登录** |

### 2.6 A6 商家（b-app，`/biz/pay`）

| 项 | 规范 |
|---|---|
| 凭证 | 沿用商家会话（不透明令牌 `btk_…`，`MerchantTokenAuthFilter`）+ `BizContextFilter` 门店范围 |
| 权限 | 每个端点 `@PreAuthorize("@perm.canBiz(…)")`，权限码 `mch:pay:*`；`BizEndpointPermTest` 守住「每个 `/biz` 端点都有决定」 |
| 范围 | `merchantScope` 恒为本商户、`storeScope` 来自会话，**请求体里的商户 / 门店号一律忽略** |
| 敏感动作二次确认 | 退款、授权第三方、生成静态码：要求近 5 分钟内重新验证（密码或短信 OTP，step-up）；授权第三方时展示 app 名称、动作、日限额 |
| 会话 | 支付相关动作所在的商家会话：空闲超时建议 ≤ 2 小时（现为固定 30 天，见 §2.9） |

### 2.7 A7 运营（ops-web，`/pay-ops/v1`）

| 项 | 规范 |
|---|---|
| 网络 | **只对办公网 / VPN**（G1）：独立 `ops.{域名}` server，nginx `allow` 办公网段 + VPN 段，其余 `deny`；`/pay-ops/` 与 `/ops/` 同样处理 |
| 凭证 | 运营会话（`OperatorTokenAuthFilter`，实时角色）+ `pay:*` 权限码（`Perms`）；`OpsEndpointPermTest` 守住覆盖 |
| 登录 | **补失败锁定（G9）**：同账号 15 分钟 5 次失败锁 15 分钟；同 IP 限流；**运营账号强制第二因子：发到登录邮箱的 6 位码**（5 分钟、最多试 5 次、一次有效；2026-10-26 定，§10 Q2）。计数为单实例内存，多实例部署时换共享存储 |
| 会话 | 空闲 30 分钟、绝对 8 小时；改密 / 停用即 `revokeUser` |
| 两人复核 | `pay_approval`：退款复核（两人，且不能是规则最近修改人）、复核规则生效、出款、收款商户启用、商户凭据启用、接入方密钥发放后启用 —— **同一人不能复核自己的申请** |
| 敏感读 | 进件资料原文、渠道调用 / 回调原文：单独权限码（`pay:onboarding:sensitive`、`pay:log:raw`），每次查看写审计（谁、何时、看了哪条、理由） |
| 导出 | 流水 / 对账导出写审计并加水印（导出人、时间） |

### 2.8 A8 刷卡终端（`/terminal/pay/v1`，I7）

| 项 | 规范 |
|---|---|
| 激活 | 运营登记终端（绑定收款商户 + 门店）→ 一次性激活码（10 分钟、单次）→ 终端提交激活码 + 设备指纹 → 服务端下发**设备密钥**（32 字节，只此一次；服务端存于密钥模块，过渡期信封加密落库） |
| 请求 | `X-Terminal-Sn` · `X-Timestamp` · `X-Nonce` · `X-Signature`（HMAC，`stringToSign` 规则同 §2.3）；收银员登录后加 `X-Operator` |
| 撤销 / 退款 | 店长授权码（店长在商家端设置，服务端存 bcrypt 哈希，**不存终端**）+ 单终端日退款限额 + 复核规则 |
| 挂失 | 设备密钥立即 `REVOKED`；在途未付单关单（关前查单） |
| 卡数据 | 读卡只用渠道认证套件；**我方 App 与服务端任何位置不得出现明文卡号 / 磁道 / PIN**，只透传加密卡数据 |
| 网络 | `terminal.{域名}` 单独 server，限流按终端号；建议证书固定（certificate pinning）于终端 App |

### 2.9 平台现有会话（对 A6 / A7 的约束）

现状：不透明令牌 + 可选存储（memory / ehcache / redis / db），固定 30 天 TTL，`revoke` / `revokeUser` 可立即吊销。规范要求：
- 生产 `shop.auth.token-store` 必须是 `redis` 或 `db`（多实例、重启不丢、可吊销），**禁止 `memory`**（启动检查）；
- 运营端按 §2.7 缩短会话；商家端支付敏感动作走 step-up（§2.6）。

## §3 密钥规范

### 3.1 密钥清单

| 类 | 谁的 | 用途 | 目标存储 | 过渡期（密钥模块前） |
|---|---|---|---|---|
| 渠道商户凭据（微信 API v3 密钥、商户私钥、平台证书 / 公钥；支付宝应用私钥、支付宝公钥） | 平台 / 商户 | 调渠道、验回调 | `sec_key`（信封加密，版本化） | systemd `EnvironmentFile`（`WX_*`、`ALIPAY_*`）；文件型私钥放 `/etc/ai-shop/keys/`，`0400` 属运行用户 |
| TW / AE 渠道凭据（蓝新 HashKey/IV、LINE Pay ChannelSecret、PayBy 私钥） | 商户 | 同上 | `sec_key`，商户 / 运营录入，只回指纹 | **不过渡**：I8 在密钥模块之后 |
| 接入方密钥（HMAC secret / 对方 RSA 公钥） | 接入方 | 验开放 API 签名、签 webhook | `sec_key` | `ConfigAppKeyResolver` ⏸ 读部署配置（试点 1–2 家） |
| 平台 webhook 签名私钥（给 RSA 接入方验） | 平台 | 签 webhook | `sec_key` | EnvironmentFile |
| 终端设备密钥 | 终端 | 验终端请求签名 | `sec_key` | I7 落地时信封加密落库 |
| 内部调用方凭据 | 平台 | `/internal/pay/v1` | 部署注入，服务端只存哈希 | 同左 |
| 列加密密钥（`PhoneCrypto`、`PayoutAccountCipher`、`NotifyCredCipher`、物流 `PhoneCipher`、储值证据 / 快照） | 平台 | 加密手机号、出款账户等 | 主密钥在 KMS / 部署注入，数据密钥带 key-id | EnvironmentFile；每把带 key-id |
| 数据库、Redis 口令；`shop.services.internal-token`；`shop.job.internal-token` | 平台 | 连接、旧内部令牌 | 部署注入 | 同左 |
| 自动化登录票据公钥（ADR-027） | 平台 | 测试环境登录 | 部署注入 | 同左；生产关闭 |

### 3.2 存储与使用规则

1. **不进仓库**：任何密钥、口令、证书私钥不得出现在 git（含测试种子里的真实值）；`.env` 类文件只放非敏感配置。
2. **不得有默认值**：yml 里密钥类占位符一律 `${ENV}` **不带默认**；缺失时启动失败（修 G6 的 `${SHOP_DB_PASS:shop}`）。
3. **不进日志、不回显**：日志经 `PayloadMasker` / `Masks` 脱敏；运营端与商家端只显示**指纹**；异常信息不得包含密钥或签名原文。
4. **最小可读**：EnvironmentFile 与私钥文件 `0400` / `0600`，属主为运行用户；部署目录不对其它账号可读；备份加密。
5. **信封加密（目标）**：每条密钥一把数据密钥（AES-256-GCM，随机 96 位 IV）加密内容，数据密钥再由主密钥加密；主密钥来自云 KMS 或部署注入，**不落库**；解密只发生在调用渠道 / 验签那一刻，内存里不长期缓存明文（缓存 ≤ 5 分钟）。
6. **冻结版本**：支付单冻结 `收款商户 id + 密钥版本`（I3 AC7）；退款、查单用冻结版本，不随轮换漂移。

### 3.3 生成

| 密钥 | 规格 |
|---|---|
| HMAC（接入方、终端设备） | 32 字节 `SecureRandom`；base64 发放 |
| RSA | ≥ 2048 位（新发推荐 3072），或 EC P-256 |
| 收银令牌、静态码号、激活码 | 令牌 32 字节、码号 ≥ 16 字节 CSPRNG；激活码 8 位数字 + 10 分钟 + 单次 |
| 列加密数据密钥 | AES-256 |

### 3.4 轮换

| 密钥 | 周期 | 方式 |
|---|---|---|
| 接入方 HMAC / RSA | 12 个月或泄露即刻 | 发新 → **两把并存 ≤ 7 天** → 接入方切换 → 吊销旧 |
| 微信 API v3 密钥、商户证书 | 证书到期前 30 天 | 新证书上线 → 验签按 `Wechatpay-Serial` 新旧并存 → 下线旧 |
| 渠道平台证书（验回调） | 随渠道公告 | 按 serial 并存 |
| 终端设备密钥 | 挂失 / 换机即刻；常规 24 个月 | 重新激活 |
| 内部调用方凭据、旧内部令牌、job 令牌 | 6 个月或人员变动 | 双哈希并存 → 切换 → 删旧 |
| 列加密主密钥 | 12 个月 | 新 key-id 写新数据；后台任务重加密旧数据；旧 key 只读保留到重加密完成 |

**泄露应急**（写进运维手册）：① 吊销 / 停用（运营端或配置）→ ② 轮换 → ③ 查 `pay_api_request_log` / `pay_channel_call_log` / 审计找出可疑调用 → ④ 通知受影响商户与接入方 → ⑤ 复盘。

## §4 nginx 规范

### 4.1 域名与 server 拆分

| server | 承载 | 对谁开放 | 说明 |
|---|---|---|---|
| `www.{域名}` | `/mp` `/biz`（含 `/biz/pay`）`/common` `/uploads` `/media` `/s` | 公网 | 现有；**去掉 `ops`**（G1） |
| `api.{域名}` | `/open/pay/v1` · `/pay/callback/` | 公网 | 新增；回调地址可沿用 www 域名直到渠道后台改登记 |
| `sandbox-api.{域名}` | `/open/pay/v1`（沙箱） | 公网 | 新增；只路由到沙箱 app |
| `pay.{域名}` | `checkout-h5` 静态文件 + `/checkout/v1` | 公网 | 新增；Apple Pay 域名验证文件、渠道回跳地址都登记在它上面 |
| `terminal.{域名}` | `/terminal/pay/v1` | 公网（终端） | I7 |
| `ops.{域名}` | `/ops-web/` · `/ops` · `/pay-ops/v1` | **办公网 / VPN** | 新增；`allow` 办公网段与 VPN 段，`deny all` |
| — | `/internal/` | **任何 server 都 deny**（本机 / 私网例外） | 现有规则保留并复制到所有新 server |

### 4.2 每个 server 都必须有的 location 规则

```nginx
location ^~ /internal/ { allow 127.0.0.1; allow ::1; deny all; }   # 跨主机时改为私网段
location ^~ /actuator/ { allow 127.0.0.1; deny all; }              # 健康检查走本机
location ~ /\.(?!well-known) { deny all; }                          # 点文件（保留 /.well-known 给 Apple Pay / ACME）
```

### 4.3 TLS

- `ssl_protocols TLSv1.2 TLSv1.3;`，**显式写 `ssl_ciphers`**（ECDHE + AES-GCM / CHACHA20，禁用 CBC 与 RSA 密钥交换），`ssl_prefer_server_ciphers on`；
- `ssl_stapling on; ssl_stapling_verify on;`；证书自动续期并告警到期；
- HSTS：`max-age=31536000; includeSubDomains`（确认所有子域都已 https 后再加 `includeSubDomains`，之后再考虑 preload）；
- 80 端口只做 301（物流回调的明文例外维持现状，不扩散到支付）。

### 4.4 安全响应头

| 头 | www / api | pay（收银台） | ops |
|---|---|---|---|
| `server_tokens off` | ✅ | ✅ | ✅ |
| `X-Content-Type-Options: nosniff` | ✅ | ✅ | ✅ |
| `X-Frame-Options` | `DENY`（API 无页面） | `DENY` | `SAMEORIGIN` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | **`no-referrer`** | `same-origin` |
| `Content-Security-Policy` | API 响应：`default-src 'none'` | `default-src 'self'; script-src 'self'; connect-src 'self'; img-src 'self' data:; frame-ancestors 'none'; form-action 'self' {渠道收银台域名}` | 按 ops-web 实际资源收紧 |
| `Permissions-Policy` | — | `payment=(self)`，其余关闭 | — |
| `Cache-Control` | API：`no-store` | 令牌页：`no-store` | 默认 |

### 4.5 真实客户端 IP（修 G2）

- **边缘 nginx 覆写，不追加**：`proxy_set_header X-Forwarded-For $remote_addr;`、`proxy_set_header X-Real-IP $remote_addr;`。前面若再加 CDN / 负载均衡，用 `set_real_ip_from {LB 网段}; real_ip_header X-Forwarded-For; real_ip_recursive on;` 先还原再覆写。
- 应用只信任来自本机 / LB 网段的转发头：`server.forward-headers-strategy=NATIVE` + 内部代理白名单；`ClientMeta#clientIp` 改为读 `X-Real-IP`（只有 nginx 会写），不取 XFF 最左值。
- 所有按 IP 的判断（限流、`pay_app.ip_whitelist`、审计 IP、OTP 频控）统一走这一个方法。

### 4.6 限流（边缘粗限流，应用层细限流在 §5）

```nginx
limit_req_zone $binary_remote_addr zone=checkout:10m rate=10r/s;
limit_req_zone $binary_remote_addr zone=open_ip:10m  rate=50r/s;
limit_req_zone $binary_remote_addr zone=callback:10m rate=100r/s;
limit_req_zone $binary_remote_addr zone=login:10m    rate=5r/m;
limit_conn_zone $binary_remote_addr zone=perip:10m;
```

| 前缀 | 规则 |
|---|---|
| `/checkout/v1/` | `zone=checkout burst=20 nodelay`；`limit_conn perip 20` |
| `/open/pay/v1/` | `zone=open_ip burst=100`（按 app 的精确限流在应用层） |
| `/pay/callback/` | `zone=callback burst=200`（宽松，宁可多收） |
| 登录类（`/biz/auth/login`、`/biz/auth/staff-login`、`/biz/auth/otp/send`、`/mp/user/login`、`/ops/auth/login`） | `zone=login burst=5`（应用层的按账号 / 手机号频控照旧） |
| 超限 | `limit_req_status 429;` |

### 4.7 请求体与超时

| 前缀 | `client_max_body_size` | 说明 |
|---|---|---|
| `/open/pay/v1/` · `/pay/callback/` · `/terminal/pay/v1/` | `1m` | 支付报文都很小 |
| `/checkout/v1/` | `64k` | |
| 上传类（`/uploads`、进件资料） | 按业务（现 32m 只留给它们） | |

`proxy_read_timeout` 支付类 30s（渠道调用在应用内有自己的超时与熔断）；`proxy_hide_header X-Powered-By`。

### 4.8 访问日志

- 统一日志格式带 `$request_id`（并 `proxy_set_header X-Request-Id $request_id`，与应用 `requestId` 贯通）；
- **不记查询串里的敏感值**；收银台路径里的令牌用 `map` 掩码（只留前 8 位）；不记请求体；
- 日志保留与轮转见《运维-目录与日志方案》；支付相关保留 ≥ 180 天。

### 4.9 出站

- 渠道调用走固定出口 IP（渠道侧要求白名单时登记）；主机防火墙出站只放行渠道域名与接入方 webhook（443）；
- webhook 投递防 SSRF（§2.3）。

## §5 应用层网关（`pay-portal`）规范

### 5.1 过滤器链顺序（每个入口一条 `SecurityFilterChain`，按 `PortalFace` 前缀匹配）

```
RequestIdFilter（读或生成 X-Request-Id）
 → ClientIpResolver（§4.5，唯一来源）
 → BodySizeGuard + CachedBodyRequestWrapper（开放 API / 终端需要原始字节验签）
 → {入口}Authenticator：OPEN=签名（A3）· TERMINAL=设备签名（A8）· CHECKOUT=收银令牌（A5）· BIZ=商家会话（A6）· OPS=运营会话（A7）
 → RateLimiter（按 PayCaller：app / 终端 / 令牌 / 账号）
 → IdempotencyKeyInterceptor（写接口）
 → PayRequestRecorder（pay_api_request_log，体脱敏；鉴权失败也写一行）
 → controller（只拿 PayCaller，不认路径）→ CallerPolicy.check（能力矩阵）
```

- `/pay/callback/**` 与 `/internal/**` 也各给一条**显式**链（无会话、不过用户鉴权、由各自的校验器认人），不再「不匹配任何链」（G11）。
- `PortalRouteRules` 守卫：controller 的类级映射必须落在本包对应的前缀下；新增前缀只能经 `PortalFace`。

### 5.2 错误与响应

- 开放 API / 收银台：`{code, message, data, requestId}`；三语文案；**鉴权类错误统一码**（不区分签名错、时间窗、nonce、AppId 不存在）；未知异常 500 只回 `requestId`。
- 不回栈、不回 SQL、不回内部 id、不回渠道原始错误（原始错误进 `pay_channel_call_log`）。

### 5.3 CORS

| 入口 | 规则 |
|---|---|
| `/open` · `/terminal` · `/internal` · `/pay/callback` | **不开 CORS**（服务端对服务端） |
| `/checkout/v1` | 只允许 `pay.{域名}` |
| `/biz` · `/mp` | 现有白名单；**localhost 开发源只在 `dev` / `test` profile 生效**（G10） |
| `/ops` · `/pay-ops` | 只允许 `ops.{域名}` |

### 5.4 幂等与重放

- 写接口：`Idempotency-Key`（或业务外部单号）+ 请求摘要（SHA-256）；同键同摘要返回首次结果，同键异摘要 409；保留 ≥ 24 小时（与 webhook 重试窗口一致）。
- 签名类入口：nonce 300 秒；**nonce 抢占成功之后才进业务**，失败的请求不消耗业务幂等键。

## §6 数据保护

| 数据 | 规则 |
|---|---|
| 卡号 / 磁道 / PIN | **永不出现**（§2.8） |
| 结算账号、证件号 | 进件资料：敏感字段只存密文 id + 掩码（`ck_pay_onboarding_material_1`）；过渡期只存掩码（I4 偏差 15）；展示掩码，原文单独授权 + 审计 |
| 手机号、邮箱 | 列加密（`PhoneCrypto`）；日志与运营端掩码（`Masks`） |
| 渠道报文、回调原文 | 加密全量入库（`pay_raw_payload`），脱敏副本用于展示（`PayloadMasker`）；原文查看需 `pay:log:raw` |
| 请求留痕 | `pay_api_request_log` 只存摘要与脱敏体；保留 180 天 |
| 导出 | 权限 + 审计 + 水印 |

## §7 审计与监控

**审计**（`sys_audit_log` / 支付审计）：资金动作（退款发起与复核、出款、关单）、密钥动作（发放、启用、吊销、查看原文）、权限与规则变更 —— 记操作人、可信 IP（§4.5）、前后值、原因，只增不改。

**告警**：

| 信号 | 阈值（起点） |
|---|---|
| 开放 API 鉴权失败（同 app / 同 IP） | 5 分钟 > 50 |
| nonce 重放命中 | 任一（可能是攻击或接入方 bug） |
| 渠道回调验签失败 | 连续 3 次（现有）；时间窗失败单独计数 |
| webhook `GIVEN_UP` | 任一 |
| 运营登录失败 / 锁定 | 同账号锁定即告警 |
| 收银台 429 | 5 分钟 > 1000 |
| `/internal` 401 | 任一（内网里出现认不出的调用方） |
