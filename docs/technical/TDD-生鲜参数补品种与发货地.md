## §1 现状与影响面

### 为什么是 TEXT 不是 ENUM

与 `SD_ORIGIN_DETAIL`（V375）**逐字同一条理由**，那份迁移的注释已经写过：

> 入 `prd_spec_value` 只会堆满永不复用的唯一串，聚合不起来（与配料同一个坑）。

- **品种**：柿子有阳丰/富有/次郎，苹果有红富士/嘎啦，葡萄有阳光玫瑰/巨峰 ——
  要穷举就得按**三级类目**各配一套值集，而 CAT120 是二级。本版走 TEXT，
  将来真需要筛选再提升为 ENUM（TEXT → ENUM 是加值集 + 回填，不是破坏性变更）。
- **发货地**：省级，但「从哪个仓发」各店不同，同样不poolable。

### 可直接复用

`V375__origin_detail_dim.sql` 就是同形状的先例：TEXT 维度 + `universal=0` + 绑生鲜几个二级类目。
本迁移照它的骨架写，`sort` 接在它后面。

### 会被改到的

- `prd_spec_dim` / `prd_category_spec` 各加 2 + 8 行（`INSERT IGNORE`，可重复执行）。
- B 端建品页：**不用改代码**。TEXT 维度的渲染分支已经在（`b-app/src/pages/goods-edit/params.ts:273`），
  新维度下发后自动出现一行「填写内容」。
- C 端详情页：**不用改代码**。参数区按 `params[]` 平铺，新维度自动出现。

### 明确不受影响

端点、权限码、i18n、配置项、`prd_goods` 表结构、既有商品的 `params`（空 = 不显示那一行）。

### 待核实（我没能当场验到）

**「包装」在生产上到底可不可填。** 依据只有迁移文件：`SD_PACK` 已绑 CAT120。
但 2026-10-07 16:27 真机上 B 端「新建商品」的参数区只列出 7 项
（产地/保质期/口感风味/单果重量/净含量/毛重/原产地），**包装、等级、数量、重量、储存条件都不在**。
两种可能，我没法区分：

1. 生产库的 `prd_category_spec` 与迁移不一致（类目树本地≠线上是有前科的）；
2. 被刚上线的「关掉用不上的参数」（`bb2fb6891`）在那份草稿里关掉了 —— 截图上每一行右侧都有「不用这项」。

**动手前要先确认是哪一种**：若是 1，本 TDD 要多补一条 `SD_PACK` 的绑定；若是 2，什么都不用做。
确认方式：拿店主账号在 B 端新建一件水果，看参数区的全集。

## §2 方案

### 契约变更

- **端点**：无。
- **库表 / 字段**：无新表、无新列。
- **迁移号**：`V379`（当前最大 `V378`；写之前已查工作区无他人未提交迁移。
  **并行会话同时加迁移会撞号，且本地不报、上生产起不来** —— 落地当天要再查一次）。
- **权限码 / i18n / 配置项**：无。

### 模块设计

| 动作 | 路径 | 说明 |
|---|---|---|
| 新增 | `shop-app/.../db/migration/V379__fresh_variety_ship_from_dim.sql` | 2 个 TEXT 维度 + 8 条类目绑定 |
| 新增 | `shop-app/.../scenario/FreshVarietyShipFromDimTest.java` | 判据见 §5 |

**只有一个迁移文件。** 不加列、不改实体 —— 值走 `prd_goods.params[]` 的快照，
与 `SD_ORIGIN_DETAIL` 同路径，所以不触发「加列是三处」那条（迁移+实体+schema-test.sql）。

### 迁移骨架

```sql
INSERT IGNORE INTO prd_spec_dim
  (dim_no, code, name, value_type, unit, usage_type, universal, scope, sort, status,
   tenant_no, created_at, created_by, updated_at, updated_by)
VALUES
  ('SD_VARIETY',   'VARIETY',   '品种',  'TEXT', NULL, 'PROP', 0, 'PLATFORM', 206, 'ACTIVE', 'MAIN', NOW(), 'SYSTEM', NOW(), 'SYSTEM'),
  ('SD_SHIP_FROM', 'SHIP_FROM', '发货地','TEXT', NULL, 'PROP', 0, 'PLATFORM', 207, 'ACTIVE', 'MAIN', NOW(), 'SYSTEM', NOW(), 'SYSTEM');
-- sort 206/207：紧跟 SD_ORIGIN_DETAIL(205)，产地 → 品种 → 发货地 在参数区连着出现
-- 绑 CAT110 蔬菜 / CAT120 水果 / CAT121 / CAT122，与 V375 同一组类目
```

### 明确不做（写在这里，免得下次当待办捡起来）

- **包装**：已存在且已绑，不重复添加。见 §1「待核实」。
- **把「原产地」从 TEXT 换成省/市/县地区选择器**：本版不做。
  - 诱因是真的：线上 `SD_ORIGIN_DETAIL` **出现 0 次**（2026-10-07 实测 15 件在售商品），
    **没有存量数据要迁移**，现在换成结构化是最便宜的时刻，而且地区树我们已经有。
  - 不做的理由：`value_type` 只有 ENUM/TEXT 两种渲染分支，地区选择器要新开一种
    （B 端一个新控件 + 值形状从一个字符串变成「地区码 + 快照名」），
    那是比本 TDD 大一档的改动，不该搭在「加两个维度」里一起上。
  - **「到县市」在本版靠录入保证**：TEXT 填得下「山西运城临猗」。
    注意 B 端的 placeholder **不能举例子**（一打字就消失，例子最该在的那刻看不见）——
    要引导就得用常驻的行内提示，那同样是另一件事。
- **把发货地绑到所有实物类目**：本版只绑生鲜四个。发货地对快递商品普遍有意义，
  但先在一个类目族里验，别一次铺满 48 个类目。
