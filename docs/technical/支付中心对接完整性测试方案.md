# 支付中心对接完整性测试方案

> 2026-11-21 · 适用：运营端「支付中心」（`/ops-shop-v2/payment-center`）经 shop-gateway 透传 near-pay `/pay-ops/v2`。
> 对照表由 `python3 scripts/pay-center-wiring.py <near-pay 仓库>` 生成（near-pay main `da3ced2a4`、ai-shop main `82bec1849`）。对接有变化就重跑并更新本文。

## 1. 测试目的

确认 near-pay 支付运营的每一项功能，在 shop 运营端都有**对应的菜单、对应的界面，并且前后端对接完整**。范围按业务域：门店 → 商户（档案、进件、审核）→ 渠道 → 订单 → 资金对账 → 平台设置（费率等）。

## 2. 判定口径

| 状态 | 含义 | 测试要求 |
|---|---|---|
| ✅ 已接 | 前端有接口封装，且有页面调用 | 在页面上实际操作一次，确认请求发到对应接口、返回 200、界面结果正确 |
| ⚠️ 只封装 | 前端有封装，但没有页面调用 | 记为缺口：补界面或删封装 |
| ❌ 未接 | 运营端完全没有对接 | 记为缺口：按优先级补，或者明确「不在运营端提供」 |

## 3. 总体结果

## 4. 执行方法

1. **前置**：核对线上版本（shop 包、运营前端 `current`、near-pay 包）与 main 一致；刚重启的话等 3–5 分钟。
2. **工具**：自己已登录的 Chrome；打开开发者工具「网络」面板，或者在控制台用 `performance.getEntriesByType('resource')` 过滤 `/pay-ops/v2/`。
3. **每个功能点**：从菜单进入 → 找到对应按钮或区块 → 操作 → 核对请求路径、方法与表中一致，返回 200（或预期的业务错误码），界面结果正确。
4. **写操作只用测试数据**：测试商户 `PM0E0F6CC8F7454D75`、测试门店 `ST2611210W463ZZ12A`（Oscar Retail QA 1121）、测试渠道 `NEWEBPAY_TEST`/`LINEPAY_TEST`。
5. **权限**：每个业务域再用一个受限角色走一遍，确认没授权的菜单、按钮不出现，直接调接口 near-pay 返回 403。
6. **记录**：每一行打勾（通过 / 不通过 / 缺口），不通过的附截图、接口、`requestId`。
