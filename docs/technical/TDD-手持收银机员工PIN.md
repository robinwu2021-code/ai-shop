# 手持收银机员工 PIN 与锁屏

更新日期 2026-11-24。范围为原生 Android 手持收银机、商户 API 和门店支付恢复。

## 0. 状态与范围

| 环节 | 当前状态 |
| --- | --- |
| 本人设置、凭原 PIN 变更、后端验证 | 本地已实现。上轮 Android 165 项、后端 13 项定向测试通过，模拟器验证首次设置、错误原 PIN 提示及修改。 |
| 手动锁定、空闲锁定、正式 PIN 解锁 | Android 已接 S01、本人 PIN 验证、手动入口和空闲控制器。由账号管理员按商家主体启用，默认关闭。 |
| 忘记 PIN、员工切换、支付期间保护 | 已实现恢复挑战、重设及 Android 页面。员工切换沿用商家账号及逐店授权。进行中的支付暂停锁屏和切换，等待真实门店与支付设备验收。 |
| 正式发布 | V698 至 V700、PIN 密钥配置、API 和原生 Android 新入口待部署及验收。 |

收银 PIN 是门店收银画面的解锁凭证。首次进店和员工切换仍使用个人商家身份。锁屏与解锁不改变门店、角色或班次归属。

## 1. 原生 Android

| 场景 | 界面与行为 |
| --- | --- |
| 设置 PIN | 员工用本人账号登录并选店，在「設定 → 門店與員工 → 員工 PIN」输入两次相同的 4 位数字。当前页面复用现有设置与密码输入组件。 |
| 修改 PIN | 同一入口输入原 PIN，再输入两次新 PIN。失败时清空输入并显示剩余次数或锁定截止时间。 |
| 锁定收银机 | 本人在当前门店已配置 PIN 且管理员已启用时，在「今日」显示「鎖定收銀機」。支付处理中暂停锁定。空闲默认 5 分钟，沿用现有时长设置。 |
| PIN 解锁 | S01 显示门店名、员工名、PIN 输入、「忘記 PIN？」与「切換員工」。输入完整后调用本人验证接口。解锁成功回到原页面，保留同一身份的购物车、班次及未完成操作。离线或验证超时保持锁屏，提供重试。 |
| 忘记 PIN | 进入身份验证步骤，选择账号密码或账号已有的验证码渠道，验证通过后输入两次新 PIN。重设成功后解除当前锁屏，继续原页面。取消、验证失败或凭证过期回到锁屏。 |
| 切换员工 | 新员工使用自己的商家身份重新认证，重新校验门店角色并载入其 PIN 状态。旧员工页面、顾客资料和未授权操作在换人后不可见。进行中的交易先进入原单查询，班次依现有交班规则处理。 |

沿用 `StaffPosPinScreen`、`StaffPosPinApi`、`AutoLockController` 与 `AutoLockOverlay`。在导航层统一控制锁屏覆盖范围。锁屏时阻止原页面交互、扫码和无障碍读取，隐藏后台任务预览、应用内提示与打印预览。正常解锁时复用原导航栈，返回键不可跳过锁屏。

## 2. 后端接口

### 已实现

三个入口要求已登录的商家会话、明确且有效的 `X-Store-No`，以及当前门店的订单查看权限。租户、主体、门店、身份类型和员工号由服务端从会话和授权范围解析。

| 请求 | 参数与结果 |
| --- | --- |
| `GET /biz/auth/pos-pin` | 返回 `available`、`configured`、`enabled` 和 `canManagePolicy`。 |
| `PUT /biz/auth/pos-pin/policy` | 账号管理员传入 `enabled`。按当前已授权门店解析商家主体，统一设置该主体下所有门店。权限为 `STORE_ADMIN`，操作写入审计。 |
| `PUT /biz/auth/pos-pin` | 接收 `newPin`、可选 `currentPin`。首次设置省略原 PIN，已配置必须验证原 PIN。 |
| `POST /biz/auth/pos-pin/verify` | 接收 `pin`，验证当前员工在所选门店的 PIN。 |

设置与验证返回 `outcome`。成功结果为 `SAVED` 或 `MATCH`。可能返回 `WRONG`、`LOCKED`、`NOT_SET`、`CURRENT_REQUIRED`、`WEAK`、`UNAVAILABLE` 或 `DISABLED`。输错返回 `remaining`，锁定返回 `lockedUntilMs`（Unix 毫秒）。API 仅返回状态和结果。

原生 Android 在「設定 → 員工 PIN」显示管理员开关。默认关闭，关闭时停止设置、验证和恢复 PIN，已保存的 PIN 保留。已锁定的设备在前台定期查询，收到明确的关闭状态后清除锁屏；离线时保留锁定并在连线后同步。

### 忘记 PIN

| 请求 | 参数与结果 |
| --- | --- |
| `GET /biz/auth/pos-pin/recovery/methods` | 查询本人可用的验证方式。 |
| `POST /biz/auth/pos-pin/recovery/challenges` | 接收验证方式 `PASSWORD`、`PHONE_OTP` 或 `EMAIL_OTP`。服务端解析本人已绑定且可用的渠道；如需验证码，发到绑定号码或邮箱并返回遮蔽目标。响应含 `challengeId`、`expiresAtMs`，验证码方式另返回重发等待时间。 |
| `POST /biz/auth/pos-pin/recovery/challenges/{challengeId}/verify` | 接收密码或验证码 `credential`。验证成功返回短效、一次性的 `resetToken` 与到期时间。 |
| `PUT /biz/auth/pos-pin/recovery` | 接收 `resetToken`、`newPin`，二次校验身份及门店授权后重设。成功返回 `SAVED`。 |

验证密码时复用现有账号身份校验，并匹配当前会话的身份。验证码沿用现有发送、限流和校验服务，登记独立的 PIN 恢复用途。店主按本人账号识别，员工按当前员工身份和已绑定凭据识别；服务器不接受客户端指定替他人重设。缺少绑定渠道时，界面只显示该账号实际可用的验证方式。

恢复授权绑定当前会话及租户、主体、门店、身份类型、员工号。挑战有效期 5 分钟、最多验证 5 次。验证通过后的重设凭证最多有效 2 分钟，且受挑战截止时间约束。凭证过期、用过、跨会话、门店不符或员工已撤权时拒绝。会话过期时转入现有登录流程，重新确认本人及原门店后重新发起恢复。恢复接口既不签发商家会话，也不给员工增加权限。

## 3. 数据与并发

| 数据 | 设计 |
| --- | --- |
| `mch_pos_staff_pin` | V698 已定义。联合主键为 `tenant_no, entity_no, store_no, subject_kind, actor_no`。保存 `pin_hash`、`failed_count`、`locked_until_ms`。 |
| `mch_pos_staff_pin_policy` | V700 按 `tenant_no, entity_no` 保存开关。无记录时视为关闭。 |
| PIN 策略 | 4 位数字，拒绝 `1234`、`4321` 和四位相同的数字。PIN 与身份范围做 HMAC，再用 BCrypt 存储。初次设置受唯一键保护，验证、更新和失败计数由凭证行锁串行化。连续三次失败锁定五分钟。 |
| PIN 恢复记录 | V699 新增 `mch_pos_pin_recovery`。保存范围键、会话指纹、挑战 ID、验证方式、到期时间、失败次数、重设凭证摘要及消费时间。挑战及重设凭证按用途独立。凭证入库只存摘要。 |
| 原子重设 | 事务内锁定恢复记录，校验已验证且未消费，写入新 PIN 哈希，清空失败计数及锁定截止时间，并将当前员工在该店的其余恢复凭证标记为消费。并发提交只有一次成功。 |
| 审计 | 记录设置、修改、恢复的员工、门店、时间和结果。PIN、账号密码、验证码及原始重设凭证不写日志。 |

部署配置沿用 `shop.pos-pin.pepper`。使用至少 32 字节随机值的 Base64 编码，各实例使用同一密钥。配置缺失时保持不可用。PIN 哈希密钥通过服务配置保管，密钥变更与已存凭证迁移一并安排。

台湾三竹短信使用 `POS_PIN_RECOVERY` 繁中模板，支持通过 `shop.sms.mitake.otp-scenes.POS_PIN_RECOVERY` 覆盖。使用阿里云短信时，需要在 `shop.sms.ali.otp-scenes.POS_PIN_RECOVERY` 配置对应的已审核模板。

## 4. 支付与锁屏的衔接

| 状态 | 处理 |
| --- | --- |
| 购物车尚未发起支付 | 可以锁定。本人解锁后继续原购物车。 |
| 现金确认、扫码等待、刷卡授权、支付结果待确认 | 暂停空闲锁定，手动锁入口提示先完成当前操作。交易处理中禁止换人和切店。 |
| 设备系统锁屏、退到后台或网络中断 | 返回前台先恢复原支付单或原刷卡交易的查询。复用扫码查单和 N5 原交易恢复，保持原幂等标识。SSE 可触发查询，结算状态以查单结果为准。 |
| 原单已成功 | 显示原单成功结果，按原收银流程续走。 |
| 原单仍待确认 | 显示「交易確認中」，保留原单号并继续查询，暂不开放重新收款。 |
| 原单已确认失败、取消或失效 | 显示状态后允许重新发起收款。 |

同一进程中的购物车与页面状态随导航栈保留。正式启用时，Android 以商家身份与门店键保存锁定标记，重启时先检查该标记。旧安装中缺少商家身份编号的会话须重新登入后启用锁屏。应用被系统终止后，交易恢复以已有的持久化订单或 N5 交易索引为准。购物车跨进程恢复需有对应持久化数据验证。

## 5. 开发顺序与验收

1. **后端先实现恢复。** 对接账号验证与专用验证码用途，完成单次重设、并发提交、授权范围检查和限流。验证正确凭证可重设、旧 PIN 失效、锁定清除，过期或跨员工、跨店、跨会话的凭证均被拒绝。
2. **Android 接入正式锁屏。** 用本人 PIN 状态启用 S01，接手动与空闲锁定，再接忘记 PIN 页面。实测已设和未设 PIN、自动锁时长、错误次数、取消、返回键、离线重试、锁屏期间的敏感信息保护。
3. **联调切换员工和支付恢复。** 用同店两名员工验证各自 PIN 及权限，确认换人后旧操作状态不外泄。分别测试收款码、付款链接、刷卡中断后回前台查原单，确认待支付不重复扣款、付款成功只生成一份交易结果。
4. **正式发布验收。** 先部署数据库和 API、检查配置，再发布 Android 并在授权门店确认本人可设置 PIN 与自助恢复。以上场景通过后开启正式自动锁屏。

主要代码位置为 Android `feature/auth/lock`、`app/nav/AutoLock.kt`、`app/nav/PosNavHost.kt`，后端 `BizPosStaffPinController`、`PosStaffPinService` 及 V698。对应已有回归入口为 `StaffPosPinApiTest`、`PosStaffPinMysqlTest`、`BizEndpointPermTest`。

台湾 v2 部署包已包含 `V697__beauty_counter_twd_cash.sql`，与提交 `d7e5968ae` 的文件 SHA-256 一致。为兼容线上 Flyway 历史，在服务端主分支同步该迁移原文，并新增 PIN 的 V698 至 V700。

### 本地验收记录

- 原生 Android 启用锁屏的验证包通过 226 项定向单元测试。覆盖支付暂停锁定、扫码等待原单结束、员工 PIN 和 N5 原交易查询。
- 模拟器检查手动锁定及返回键、强制停止后恢复锁定、本人密码验证后重设、旧 PIN 拒绝、新 PIN 解锁和切換員工后回到账号登录页。模拟 API 使用独立应用 ID 和本机合成账户。
- 后端以隔离 MySQL 9 校验恢复凭证期限、会话/员工/门店范围、单次消费、旧 PIN 失效及验证码专用用途。网关权限映射另有回归。
- Spring 网关联调使用真实登录会话和门店授权。店主可用账号密码重设 PIN，店员可用本地短信桩重设本人 PIN。同店其他员工、其他门店及另一登录会话无法复用重设凭证。凭证只能使用一次，重设后旧 PIN 拒绝、新 PIN 可用。
- Spring 网关与隔离 MySQL 验证管理员启停、店员写入被拒、同主体门店共享设置、其他主体隔离。测试结束时将测试主体的开关关闭。
- 原生 Android 模拟器从「設定 → 員工 PIN」开启开关，验证手动锁屏后从服务端关闭。终端收到关闭状态后自动解除锁屏，手动锁屏入口随即隐藏。测试结束复查开关为关闭。
- 三竹短信本地 HTTP 回归通过，验证 PIN 重设场景使用对应繁中模板。需要显式提供私有配置的回归项按默认测试条件跳过。
- N5 模拟终端在 Android 模拟器完成 20 次 HTTPS 签名请求，覆盖支付授权、结果不明时查询原交易、撤销及退款。
- 真实门店员工换人、实际验证码发出及真实支付渠道的中断恢复仍需上线前验收。PIN 的启停由服务端主体设置控制。
