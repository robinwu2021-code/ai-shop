# B 端门店功能矩阵 · 开发计划

日期：2026-11-09 · 依据：[TDD-B端门店功能矩阵与方案准入](./TDD-B端门店功能矩阵与方案准入.md)（PR robinwu2021-code/ai-shop#3）、商户 App 交接文档（`docs/交接-商户App功能矩阵与API.md`）、`origin/codex/ai-shop-codex` fc070b2d4 与在途分支的代码现状。

读者：后端、Flutter（ai-shop-bapp）、运营、产品。各阶段写清「谁做、依赖什么、怎么验收」；单项工作开工时按 `ai-shop-dev-standards` 判档并在各自的 TDD §2 写实施步骤，本文不替代 TDD。

## 一、结论

1. **矩阵里大部分功能的后端已经有了**，缺口主要不在「写接口」，而在三件事：**新模型门店的路由登记**、**App 的 mock 契约与后端真实接口对不上**、**运营还没发布行业权益码**。
2. 餐饮（`/biz/x/food/*`，239 个接口）与美业（`/biz/x/beauty/*`，31 个控制器）插件都已实现，但新模型门店访问会被 70006 拒（路由没登记），App 用的仍是自拟的 `/biz/food/*`、`/biz/beauty/*` mock 契约。**建议 App 改调插件接口，后端不再另做一套 `/biz/food`、`/biz/beauty`。**
3. 166 已部署的路由登记（`codex/biz-host-routes-70006`）和 P0 契约（外部记账、问题回报、快递公司）都在集成分支 `codex/bapp-handoff-tdd` 上，**还没合进 `codex/ai-shop-codex`**；它与 PR #3 有 4 处冲突。合流是一切的前置。
4. 首批行业建议先做**餐饮**：166 联调门店「台北早餐」是餐饮店，后端插件也最完整。
