## 3 接口目录

> 前缀与鉴权见完整设计方案 §9；**按调用方的完整清单（含已上线的旧接口）见[支付服务 · 接口清单](./支付服务-接口清单.md)，鉴权、密钥、nginx 与网关规范见[支付服务 · 安全规范](./支付服务-安全规范.md)**。权限码登记在 `Perms` 与角色种子（I5 · D02）。所有写接口接受 `Idempotency-Key`。

### 3.1 内部调用（I3）

| 方式 | 方法 / 路径 | 说明 |
|---|---|---|
| 内嵌 | `PaymentPort#createPayment` · `#startPayment` · `#queryPayment` · `#closePayment` · `#requestRefund` | 商城、餐饮调支付的唯一入口；退款必须带商家操作员 |
| 内嵌 | `PayMerchantQueryPort#routeOf` · `#collectableRoutes` · `#routeByPayMerchantId` · `#capabilityOf` | 收款路由唯一解析口（I4 读切后生效） |
| 独立 | `POST /internal/pay/v1/payments` · `POST .../{no}/start` · `GET .../{no}` · `POST .../{no}/close` | 同上，经 `InternalCallerFilter` 按调用方授权 |
| 独立 | `POST /internal/pay/v1/refunds` · `GET .../{no}` | — |
| 独立 | `GET /internal/pay/v1/merchant-routes` | — |
| 事件 | `PaymentSucceededEvent` · `PaymentClosedEvent` · `RefundSucceededEvent` · `RefundFailedEvent` | 经 Outbox；商城 `markPaid`、餐饮结账由消费者处理 |

### 3.2 统一回调（I2）

| 方法 / 路径 | 说明 |
|---|---|
| `POST\|GET /pay/callback/{channel}/{notifyType}/{ref}` | `notifyType` = `pay` / `refund` / `onboarding` / `payout` / `return`；`ref` = 收款商户号或进件单号 |
| `POST /pay/callback/{channel}` · `POST /pay/callback/{channel}/refund` | 旧地址兼容别名，CN 渠道后台改完登记地址、30 天无流量后删 |

### 3.3 开放 API（I5）

| 方法 / 路径 | scope | 说明 |

**仓库迁移不能直接在 MySQL 上从零跑** —— 早期迁移按 MariaDB 写：
42 个文件里 113 处 `utf8mb4_uca1400_ai_ci` 排序规则（MySQL 没有），以及 31 处 `ADD COLUMN IF NOT EXISTS` / `CREATE|DROP INDEX IF [NOT] EXISTS`（MySQL 不支持）。
生产是从 MariaDB **导结构再归一排序规则**迁过去的，从没在 MySQL 上从 V1 跑过。本机的做法（仓库文件一个字不改）：

1. `ai-shop-mysql-conv`：把迁移复制到 `~/.local/var/mysql/flyway-conv`，排序规则归一为 `utf8mb4_0900_ai_ci`（与 `mysql97/migrate/lib.sh` 同规则），去掉上述 `IF [NOT] EXISTS`；
2. `ai-shop-mysql-rebuild`：DROP 并重建 `ai_shop`，按版本顺序交替执行「改写后的 SQL」与类路径里的 3 条 Java 迁移（V31 行政区划、V181 村级、V397 服务范围回填）；
3. 每段 SQL 跑完，用 `ai-shop-flyway-checksum.py`（Flyway 11 的逐行 CRC32）把 64 条被改写迁移的校验和改回原文件的值；
4. 最后用仓库原样迁移、默认配置启动应用 —— Flyway 校验通过即完成。

之后新加的迁移（V284 起禁 uca1400，`check-sql-portability` 管着）直接由应用启动执行，不用再重建；
**要清库重来就重跑 `ai-shop-mysql-rebuild <backend 目录>`**（需先 `package` 出 `shop-app` jar，约 1 分钟）。

> 根治（不在本计划）：给早期迁移补一个 MySQL 可执行的基线（Flyway baseline 脚本），让任何人在空 MySQL 上直接从零起库。
> 这会动迁移历史，属开发规范 2 档，另开 TDD。

### 10.3 新依赖对支付代码的影响

框架 `2.0.0-SNAPSHOT` 的三个公共包里，ai-shop 实际只用 `DataScope*`（约 400 处 import）与 `Permissions` / `PermissionCarrier`；
实体基类、审计填充、会话都是仓库**自有**实现。逐项对支付的结论：

| 框架类 | 现状 | 对支付的影响 | 任务 |
|---|---|---|---|
| `common.data.BaseEntity`（`regionId`、`Instant` 时间） | ai-shop 不用 | **`PayBaseEntity` 不继承它**，从仓库自有 `ai.neargo.shop.common.BaseEntity` 去掉 `tenantNo` 派生（与 §0 一致） | I0 |
| `common.data.DataAutoConfiguration`（MP 拦截器 + 审计填充，均 `@ConditionalOnMissingBean`；租户行默认关 `neargo.mp.tenant-enabled=false`） | `shop-app` 在 `application.yml` 里排除；**`pay-svc` 没排除**（它经 `pay-domain → shop-store-mybatis → shop-base-auth` 拿到 `neargo-common-data`） | 独立形态里谁的 `MetaObjectHandler` 生效取决于 bean 注册顺序；框架那份填 `regionId` / `Instant`，与支付实体字段不符 | **L1-1**：`pay-svc` 的排除列表补 `DataAutoConfiguration`，加启动测试断言审计填充 bean 是仓库自有那份 |
| `common.security.*` 自动配置 | `pay-svc` 已排除三条；`shop-app` 排除两条（保留 RBAC） | 无变化 | — |
| `common.security.rbac.Permissions` | 运营端 `@perm` 用 | `pay:*` 权限码沿用同一机制 | I5 |
| `common.data.scope.DataScope*` | 全仓按门店做数据域 | 支付运营端、商家端查询按门店 id 收敛时**复用**，新表在 `DataScopeTableRegistry` 登记 | I5（F10 独立形态数据域条件在 I1） |
| `common.core.BusinessDayPolicy` / `BusinessDayResolver`（时区 + 日切；自带 `uaeDefault()` = `Asia/Dubai`） | ai-shop 未用 | 结算、对账、终端日结按**市场**算营业日，直接用它，不另写 | I6 · I7 |
| `common.core.IdGenerator.next(prefix)`（带节点段，`neargo.node-id` / `NEARGO_NODE_ID`） | ai-shop 未用 | 支付单号沿用仓库现有单号生成器；若改用它，多实例必须配节点号 | I0 定（单号类型登记时） |
