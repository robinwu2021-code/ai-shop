## 二、第 2 问：三个词，两层东西

「商户」这个词在两个语境下指不同的东西，这是本轮反复出岔子的地方：

| 说法 | 指什么 | 表 | 一个主体有几个 |
|---|---|---|---|
| **主体 / 商户 / 经营实体** | **一张营业执照** —— 工商与税务认的那个 | `usr_merchant` | —— 它本身就是一个 |
| **收款商户号 / 商户号 / 子商户** | 进件产物 `sub_mchid`，**每个支付通道一条** | `usr_merchant_payment` | 微信一条、支付宝一条…… |

**所以：主体 = 商户，而「商户号」不是商户。**

```
usr_merchant（主体＝商户＝一张营业执照）
   ├── usr_merchant_payment(WECHAT)  → sub_mchid 微信收款号
   └── usr_merchant_payment(ALIPAY)  → sub_mchid 支付宝收款号
```

后续文档统一用词：**主体**（不再说「商户」，避免与「商户号」混）、**收款商户号**。

## 三、第 3 问：门店可切换主体 —— 我之前定错了

### 3.1 我之前说的，和为什么不对

我在[产品架构与实体关系 §2.2](./产品架构与实体关系.md) 里写：

> 主体 → 门店：**归属**，不该改，它们都是这个经营者的东西

**这句话是错的**，因为它假设「一个账号只有一个主体」。一旦承认账号可以持有多张执照，
「把文三路店从个体户执照转到公司执照名下」就是一个**必然会发生**的操作：

| 什么时候会发生 | |
|---|---|
| 个体户升级为公司 | 最常见 —— 生意做大了要开票、要对公账户 |
| 一张执照被吊销/注销 | 门店要转到另一张执照下继续经营 |
| 业务重组 | 餐饮和零售拆成两张执照分别报税 |

如果门店归属主体不可改，这三种情况都只能**关店重开**：
评价清零、老客的「我常逛的店」断链、历史订单查不到门店、库存与选品重录一遍。
而它本质上只是换了一张执照。

### 3.2 定稿：门店 → 主体是关联，可切换

```
usr_user（账号，注册一次）
   ├──关联──→ usr_merchant A（个体户执照）
   └──关联──→ usr_merchant B（公司执照）
                    ▲
                    │ 可切换
              usr_store（文三路店）
```

三条关系全部是**关联**（可改），只有一条是归属：

| 关系 | 类型 |
|---|---|
| 账号 → 主体 | 关联（多对多，`usr_merchant_staff`） |
| **门店 → 主体** | **关联，可切换** |
| 门店 → 收款商户号 | 关联，可换 |
| 主体 → 收款商户号 | **归属** —— 进件是这张执照的资质，换不了 |

### 3.3 这条改动的连锁反应：订单那两个键**不再是冗余**

上一轮我说：

> `merchant_no` 可由 `store_no` 推出，是冗余快照

**门店可切换主体之后，这句话不成立了。** 门店今天挂在主体 B 下，
但它三个月前的订单是主体 A 收的款、A 开的票、A 报的税。
用今天的归属去推历史订单的结算方，会把**已完成的资金流算到另一张执照头上** ——
那是税务问题，不是数据问题。

所以 `ord_sub_order.merchant_no` **是必需的历史快照，不是冗余**。
这个设计因为你这个问题反而更站得住了。

同样地：

| 数据 | 换主体后怎么办 |
|---|---|
| 历史订单 | `merchant_no` **一律不动** —— 那是当时的事实 |
| 历史分账/账单/发票 | 不动，跟着旧主体 |
| 积分账户 | **跟旧主体** —— 它是旧主体的负债（ADR-006） |
| 优惠券 | 跟旧主体；门店换主体后，旧主体的券在这家店**用不了** |
| 评价与评分 | **跟门店** —— 顾客评的是这家店 |
| 库存、选品、公告、门店码 | 跟门店 |
| 员工授权 | **失效** —— 他是旧主体的员工，不是新主体的 |
| 顾客关系（我常逛的店） | 跟门店，不断 |

### 3.4 换主体的硬约束

| 约束 | 为什么 |
|---|---|
| 新旧主体**必须同属一个账号** | 否则是把店送人，那是资产转让不是配置项 |
| 新主体必须 `ACTIVE` 且**进件就绪** | 换到一个收不了款的主体上，下一单就失败 |
| 有**未完成订单**时不能换 | 那些单的分账要走旧主体；换了之后钱找不到收款方 |
| 有**未结算账单**时不能换 | 同上，钱还在路上 |
| 换完**员工授权全部失效**，要重新授权 | 他是旧主体的员工。静默保留等于让前雇员继续操作新主体的店 |
| 变更**留痕**（谁、何时、A→B） | 这是会改变纳税主体的操作 |

**积分与券的处置要在换之前告诉商家**：
「本店在旧主体下发出的 X 张券、Y 分积分将无法在本店使用」——
不说清楚，第一个拿着券来的顾客就是一次纠纷。

## 四、第 1 问：多主体的唯一阻塞

模型已成立（`usr_merchant_staff` 多对多），但有一处代码把它挡死：

🔴 **`MerchantPortImpl.activate` 的幂等判据是「这个人是不是已有商家」**，
于是申请第二张执照通过时，系统当成重复点击去**改第一个主体**而不是新建。
第二张执照的名称/行业/主体类型覆盖掉第一个，两家变一家，**且没有任何报错**。

修法：幂等判据改为**申请单**（`usr_merchant_apply.merchant_no` 非空即已激活过）。

## 五、定稿后的模型一句话

> **账号持有多张执照（主体）；门店挂在其中一张下面，可以换；
> 钱与税跟主体走且历史不动，货与人跟门店走。**
