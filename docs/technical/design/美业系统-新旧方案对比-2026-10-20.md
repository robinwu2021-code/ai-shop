# 美业系统新旧方案对比

> 状态：评审草稿 · 创建：2026-10-20 · 在新版独立方案形成后进行对照，不修改旧稿。
> 新版入口：[共用商品订单与服务工作流](../TDD-美业系统-共用商品订单与服务工作流.md)。

## 一、对比结论

旧美业包的基本划分应保留：项目复用商品，预约与工单分开，卡账不放美业，加项不改原成交，服务与资金分别留事实。新版主要更新**当前底座接法、原子资源合同、支付与核销来源、分期依赖及异常恢复**。

推荐以新版作为本轮架构评审入口，按本表逐项吸收旧方案；旧稿和历史讨论保留，尚不宣告新版已经批准或旧代码已经完成迁移。储值首期已明确收敛的产品范围继续有效。

### 对比对象与适用范围

| 来源 | 原用途 | 对比时的判断方式 |
|---|---|---|

| [行业化扩展总案](../TDD-行业化扩展-餐饮与服务业.md) | 三行业共用能力与插件分层 | 保留行业包方向，逐项复核“核心不改”的假设 |
| [美业储值详细设计](../TDD-美业储值-系统详细设计.md)及[需求](../../requirements/PRD-美业储值.md) | 储值首期收敛与历史讨论 | 最新范围优先；其中早期“未找到会员码实现”等现状描述已需按源码更新 |
| [储值流转与通知](../TDD-美业储值流转与通知.md) | 早期全目标及简化原型过程 | 不复活被后续排除的混合支付、线上退款、专用码和内部拆分展示 |
| [门店独立储值设计](../TDD-独立储值方案与B端接入.md)与[营销对象关系§0](../../requirements/营销模块重整与对象关系方案.md) | 2026-10-20最新目标 | 门店账户、独立方案优先；设计状态待实施，不将其等同现行代码或已上线 |

新版先从本次共用商品订单约束、餐饮扩展边界与当前代码形成设计，再用以下表格核对旧方案。对比涵盖完整美业包和近期储值方案，两者范围不同，不将“储值方案没有排班”视为缺陷。

## 二、应继续保留的设计

| 旧方案设计 | 新版处理 | 原因 |
|---|---|---|
| 项目＝基础商品/SKU，不建另一套商品 | 保留 | 避免门店价、活动、退款分裂 |
| 预约可无订单，直客可无预约 | 保留，并明确临客认领 | 电话预约不需要先开户或生成虚假交易 |
| 预约单和服务工单分开 | 保留 | 爽约与实际服务是不同事实 |
| 改约先占后放 | 保留目标，改为资源域原子替换 | 还需支持新旧区间重叠、自身占用与并发 |
| 资源从预约转给工单，不重复计数 | 保留同一持有凭证 | 防止签到后一个技师被扣两次容量 |
| 加项用新来源，不修改已付金额 | 保留，并补资源与本人确认 | 避免加项绕过预约或资金授权 |
| 卡余额和余次不在美业保存 | 保留，写入改走当前Pay权益合同 | 不重建卡账，明确实际所有方 |
| 换人留痕、退款倒扣提成 | 保留原则，参与分配和冲回规则版本化 | 人员交接与已发工资不能靠改一列解决 |
| 打印失败不损坏交易，补打可追踪 | 保留，并沿餐饮共享打印分层 | 服务票和消费凭条不能推动资金与服务状态 |

## 三、必须修订的模型与合同

| 主题 | 旧方案表述或假设 | 新版结论 | 影响 |
|---|---|---|---|
| 商品服务属性 | 旧包§2.6/§4.1主张缓冲等上收商品SERVICE段；同节引文仍写美业入口 | `durationMin`已存在；缓冲/资源需求其余是新增规则，字段与入口尚需冻结 | 不据旧稿直接调用不存在的字段或维护接口 |
| 到店与上门预约 | 旧包场景矩阵已正确区分，但总案流程用 `APPOINTMENT/STORE_VERIFY` 并列 | 明确到店＝`STORE_VERIFY`＋预约关系，上门＝`APPOINTMENT`＋地址 | 防止将到店预约误要求地址或改坏原上门语义 |
| 技师、技能与资源 | 旧包§2.5等将 `mch_staff_skill` 等写为可直接使用 | 当前资源时段接口与实体只有门店名额；人员、技能、连续区间按缺口建共享能力 | 必须补实际数据和调用证据，不能从文档推断已实现 |
| 多资源抢位 | 旧包§4.2写循环 `tryBook` 自行回退；抬头08-28已改上收共享hold | 采纳抬头修订方向，原子集合操作归资源域；不沿用正文循环方案 | 一次失败整体无残留，避免跨请求尽力补偿漏占 |
| 资源持有表 | 旧包正文仍列 `bty_appointment_slot/bty_schedule_log`，抬头已作废 | 不恢复这些已作废表；美业只关联共享hold及调班结果 | 不是再次推翻旧案，而是将旧修订落到一致正文 |
| 基础订单编号 | 旧 `order_no` 用于预约、工单与行扩展 | 区分支付根、门店交易、成交行，以及服务核销来源 | 防止同名字段绑错粒度或跨门店汇总 |
| 普通交易与资产消费 | 旧包§4.6/§8.4统一用零实收普通订单＋抵扣列＋`markPaid` | 复用实际已有Core核销来源 `ord_ent_service_order` 与Pay使用合同；现金仍走普通交易 | 同一任务互斥选择来源，不凭美业补一张零元单来造支付事实 |
| 资产归属 | 旧 `CoreMemberApi/mbr_card/mbr_asset_txn` | 会员负责识别，Pay负责资产，Core负责消费来源和授权，桥接负责可靠编排 | 历史API名不作为当前可调用接口 |
| 收款流水 | 旧包§4.7/§8仍列 `bty_payment`，抬头已上收拟定 `ord_payment` | 保留“无美业独立收款账”；实际接现有支付/核销合同，不假称拟定 `ord_payment(ref_type=WORK_ORDER)` 已落地 | 按当前实际资金来源核对，而非替换成另一张尚未验证的表 |
| 多单混合结账 | 旧包§4.7/§10允许多工单、多笔、混合，再逐单标付 | 首期逐笔收款；一次付款覆盖多来源需共用收银分配合同 | 避免收一次钱却为多个订单各记一遍收款 |
| 事务 | 旧包§8.4称建单、扣次、标付、提成1–6同事务 | Core、Pay、资源各自本地事务，持久意图＋原号恢复 | 适配当前独立Pay边界，避免无效跨库事务假设 |
| 核销时点 | 旧流程“到店核销→服务→完成”，同时使用完成语义 | 分开签到、扣资产和基础履约；实际完工后才请求履约完成 | 防止签到即完成交易，提前启动结算与售后时钟 |
| 工单结清 | 旧工单 `FINISHED→SETTLED` 及美业结账编排 | 完工与经济结果分开；所有来源已满足各自结果后才能关闭 | 核销确认中、未结清、退款处理中都能真实呈现 |
| 提成 | 旧§4.6/§9写原价基数，§16又列原价/实收/卡价待定 | 不默认原价；规则版本明确基数、参与人与冲回 | 将旧稿内部待决变成显式政策，不把原价当已确认事实 |
| 退卡核销口径 | 旧§5.1给原价/卡价比较并带价值判断 | 不自动重算已消费价；后续按合同与历史分摊单独设计 | 不将讨论例子当产品规则，也不扩大本期退款范围 |
| 启用依赖 | 旧§11要求资源、储值、次卡、抵扣列缺一拒启 | 按现金单次、资源预约、储值、卡销售等能力分开验收/启用 | 单次现金服务不被全套卡体系阻塞；有强约束商品仍拒绝绕过 |
| 剔除与关停 | 旧要求剔除插件后基础全绿 | 保留基础回归，并增加历史单查询/恢复/收尾 | 已有顾客承诺不能因关闭新业务入口中断 |

## 四、近期储值方案的继承与范围优先级

| 主题 | 历史讨论 | 最新要求及新版处理 |
|---|---|---|
| 账户边界 | 按商家主体＋顾客＋币种聚合 | 10-20目标按门店独立；多个方案同店共用一个账户，不跨店核销；迁移尚待实施 |
| 方案与活动 | 活动先发布才能充赠 | 10-20先做独立方案，活动不作办理前置；旧活动来源受控兼容 |
| 消费方式 | 储值不足现金补款、储值/积分组合 | 保持当前首期全额合格储值；不足整笔拒绝，未知结果不得换路再收款 |
| 顾客识别 | 早期独立储值核销二维码 | 统一会员码；扫码识别与本人金额授权分开 |
| C端展示 | 本金、赠金、批次、分配及复杂账户页 | 简明项目、金额、门店、时间、状态、单号；内部拆分仍留账 |
| 入口与目录 | 全部商家统一核销流水优先 | 保留最新“储值门店→本店核销记录”，有成功充值、余额为零仍保留；门店主页进入本店记录 |
| 退款 | 服务退款、退余额、商家审核页 | 首期不提供线上退款和任意余额调整；后续纠错单独设计，不能删除原凭证 |
| 卡销售 | 美业可直接售疗程、扣次、退卡 | 共用权益能力逐项核实；储值可用不等于付费疗程销售已开通 |
| 上线状态 | 文档、原型和代码容易混写 | 独立标注目标、源码存在、定向测试、实际实例能力，避免原型冒充交付 |

最新营销文档§0内仍有“商家全部门店”的单元格与门店独立修订不一致；本方案按同节最上方最新修订及门店独立储值TDD处理为**当前门店管理与使用**。实施前需由该储值任务收口其文档和契约，本次不改共享中的旧文档。

## 五、相对旧方案新增的完整性要求

- 提交记录覆盖原号重试、未知结果、同键异参；先收到资金结果再建立行业关联也能恢复。
- 同一服务任务不同时绑定现金与资产两份有效消费来源；数量分配及稳定源行可核对。
- 到店签到不会触发订单完结；现有自动完成任务不能越过服务完成守卫。
- 资源替换处理重叠区间、同一持有者、换人、临时请假与超时冲突。
- 服务后付、定金、团体、合并收银、第三方及断网分别列基座依赖；不因扩展表能存状态就宣称可营业。
- 与餐饮共用打印和部署合同；前台、技师、老板、平台及设备权限分别定义，资金确认与服务操作分权。
- 充值、服务现金、储值/次数消耗、产出与提成分口径，不将所有事件累加进普通现金订单报表。

## 六、建议的后续动作

先评审新版的来源边界、资源合同和首期范围，再冻结PRD验收、详细表/API/权限与必要的架构决策。保留旧稿及其原型供追溯，确认后的替代章节再添加明确接替链接。

随后按新版P0–P2交付单店先付、预约资源、服务工单及既有资产消费接线；不将旧稿所有表、十二类SPI或全套卡销售作为统一前置建设。产品代码、正式DDL、数据迁移、真实资金联调与部署均不属于本轮交付。
