## 0. 一句话

品牌不是从零画一个 logo，而是**把产品里已经存在的事实说出来**——
这套系统天生支持 8 套皮肤，每个商家有自己的颜色。这就是「虹」。

---

## 1. 现状盘点（决定方案形状的四个事实）

### 1.1 品牌资产是零，且已经在挡路

| 资产 | 现状 | 后果 |
|---|---|---|
| App 图标 | **不存在**（`android-shell/app/src/*/res/mipmap*` 目录都没有） | 任何应用商店都上不了架 |
| 启动图 | 不存在 | 冷启动白屏 |
| Logo | 不存在 | 官网、分享卡片、发票、合同全都缺 |
| 隐私政策 / 用户协议页 | 不存在 | 应用商店强制项，缺一项直接驳回 |

这不是"锦上添花"的美化工作。**没有图标就没有上架，没有上架就没有下载，官网的"下载 App"按钮就没有落点。**
所以品牌工程的第一优先级不是 logo 的美感，是**解除上架阻塞**。

### 1.2 已有名称是三套，且都不是"虹选"

| 位置 | 现名 |
|---|---|
| C 端 App（`capacitor.config.ts`、`manifest.json`、`pages.json`、`index.html`、`build.gradle`） | 社区好物 |
| B 端 App | 邻里商家 |
| 包名 / 后端命名空间 | `ai.neargo.shop.*` |
| 公司域 | `neargo.ai` |

改名影响面已定位到 **8 处硬编码 + 3 个语言文件**（`zh-CN.ts` 里还有一句分享文案 `shareTitle` 带旧名）。

> **包名 `ai.neargo.shop.c` 不改。** 改包名 = 老用户视为全新 App，必须重装、本地数据全丢、应用商店评分清零。
> 包名是技术标识，用户永远看不见；显示名（`app_name` / `appName`）才是品牌。两者本来就该解耦。

### 1.3 设计系统已经成熟，品牌色必须落进去而不是另起一套

`packages/shared/src/design/tokens.ts` 里已有：**8 套皮肤 × 明暗两档 × 4 种面感**，全部 token 化，
并且由 `design-tokens.test.ts` 用 **WCAG 对比度断言**守着——色值不达标会直接测试失败。

这意味着：品牌主色**不能凭审美拍板**，它必须能过对比度测试，否则要么改色，要么改测试（改测试就是把无障碍问题藏起来，不做）。

当前默认皮肤 `fresh = #00B578` 是**微信绿**，代码里明确标了 `brandLocked`：
> "与微信生态的观感一致性比白字达标更重要"。

### 1.4 三语言，含阿拉伯语（RTL）

`c-app` 与 `b-app` 都有 `zh-CN / en / ar`，且 TDD 里写明地基"已在 MENA 项目验证"。
所以品牌标识**必须有英文名**，且 logo 图形**不能依赖左右方向**（RTL 下会镜像翻转的图形不能用）。

## 2. 核心决策：品牌色与 App 默认皮肤的冲突

这是整个方案里唯一需要你拍板的地方，先讲清楚。

**冲突**：App 内默认色是微信绿且 `brandLocked`；如果官网 / logo 用一个新的品牌色，用户会看到两张脸。

三条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 品牌色 = 微信绿 | 把 `fresh` 当品牌色 | 零改动。但「虹」和绿色毫无关系，品牌叙事从名字上就断了；且官网会被误认成微信官方产品 |
| B. **品牌色独立于 App 皮肤** | 官网 / logo / 对外物料用品牌色；App 内保持商家可换肤、默认仍是绿 | 需要接受"平台的脸"和"商家的脸"不同 |
| C. 换默认皮肤为品牌色 | 改 `DEFAULT_SKIN` | 动到已验证的默认观感，且丢掉微信生态一致性这个已经想清楚的决策 |

### 推荐 B，而且这不是妥协，是品牌的核心叙事

平台是**多商家**的。商家换肤不是一个装饰功能，是产品的既有能力（8 套皮肤已经在代码里跑着）。
「虹」正好是这件事的名字：

> **虹不是一个颜色，是七种颜色排在一起还很和谐。**
> 平台不给商家统一的脸——每个商家有自己的色，站在一起才是一道虹。

这个叙事的价值在于：它**不是编出来的**，它描述的是系统真实具备的能力。
品牌只是把工程事实翻译成了一句人话，所以它经得起追问，也不会在产品迭代中失效。

## 3. 品牌色方案

### 3.1 为什么不能真用渐变当主色

彩虹渐变做 logo 可以，做 **UI 主色不行**：渐变无法计算对比度、无法当按钮底色、单色印刷（发票 / 合同 / 传真 / 刻章）直接死掉、微信小程序头像会被压成一坨脏色。

所以拆两层：**logo 用渐变承载"虹"，UI 用单色承载"可用"。**

### 3.2 取虹的哪一段：虹橙

| 理由 | 说明 |
|---|---|
| 转化色 | 橙红是电商下单色（淘宝橙、京东红、拼多多红、美团黄），暖色催单、催食欲，这是被验证过的 |
| 与微信绿区分 | 官网一眼看上去不是微信生态产品，是独立品牌 |
| 是"虹"的代表色 | 橙是光谱里最亮最暖的一段，说"虹"时人脑先想到的就是它 |
| **零新增成本** | 现有 `promo` 皮肤的 light 值就是 `#D24600`——团队早就算过它的对比度 |

### 3.3 色值定义

```
虹橙（品牌色 · Logo / 海报 / 大色块）   #FF5A1F
虹橙（UI 主色 · 按钮 / 白字底）         #D24600   ← 复用现有 promo.light，已过 AA
虹橙（深色模式 UI 主色）                 #FF6010   ← 复用现有 promo.dark
虹紫（渐变终点 · 仅 Logo）              #7A4CE0   ← 复用现有 violet.light
墨                                       #14161A
```

**关键**：亮版 `#FF5A1F` 白字对比度约 3.1，**不达 AA 4.5**，所以它只能用在没有压字的大色块和 logo 上；
凡是要压白字的地方一律用 `#D24600`。这两个值的分工必须写进规范，否则一定会有人拿亮版做按钮然后测试红。

**这套方案不需要新增任何 token**，`promo` 和 `violet` 都已存在且已通过对比度断言。

## 4. Logo 方案

### 4.1 设计约束（先定约束再画）

1. **单色版必须成立**——微信小程序头像、发票、水印、刻章都是单色
2. **RTL 安全**——阿拉伯语环境下不能出现"方向错了"的观感，图形必须近似左右对称或方向无关
3. **16×16 可辨**——浏览器 favicon 和 Android 通知栏小图标的真实尺寸
4. **中英双字标**——`虹选好物` / 英文名（见 §4.3）

### 4.2 图形方向：虹弧 = 勾选 = 提手

一个弧形同时是三样东西，这是真双关不是硬凑：

- **虹** —— 弧本身
- **选** —— 弧的下半段收笔，自然形成一个 ✓（品牌名里的"选"）
- **购物** —— 弧的上半段是购物袋的提手

三层含义共用一根线，所以图形极简（一笔），16px 下也不糊。
渐变从虹橙走到虹紫落在这根弧上；单色版整根弧取墨色或虹橙实色。

三个具体方向已出可视化稿，见 §9。

### 4.3 英文名

`hxmall.top` 里的 `hx` = **H**ong **X**uan。但 "HX Mall" 作为对外英文名偏弱（缩写无意义、Mall 太泛）。

候选（需拍板）：

| 候选 | 说明 |
|---|---|
| **Hoxo** | hx 的元音化，两音节好念，全球可注册性较好，与"虹选"发音有联系 |
| **Rainbo** | 直译"虹"，语义直白，但商标风险高、辨识度低 |
| **HX Mall** | 与域名完全一致，零解释成本，但没有品牌感 |

> 英文名主要用在 MENA 场景和应用商店副标题，国内主战场仍是中文名。可以先定 **HX Mall** 保证一致，等出海时再启用独立英文名。

## 5. Slogan 与广告语

要区分两个东西，它们的寿命不一样：

- **Slogan（品牌定位语）**：跟 logo 一起出现，几年不换
- **广告语（传播语）**：投放物料用，一季一换

### 5.1 Slogan 候选

产品的真实差异点是 **LBS 服务半径**（代码里"社区过滤是邻里购物的第一约束，不是排序偏好"，经营范围有三档地理覆盖模型）。Slogan 应该落在这里，而不是落在虚的"品质"上。

| 候选 | 字数 | 评价 |
|---|---|---|
| **好物在身边** | 5 | **推荐**。直说 LBS 内核，与"好物"呼应，念着顺，五个字可以刻进 logo 锁定组合 |
| 一条街的好货 | 6 | 更具体，但"街"限制了想象（不适用于县域、MENA） |
| 挑好的，就在附近 | 8 | 把"选"也带上了，但偏长，logo 旁放不下 |
| 邻里之间，好物有虹 | 9 | 文艺，品牌感强，但不说人话，不适合下沉市场 |

### 5.2 一句话广告语候选

| 场景 | 候选 |
|---|---|
| 主推（拉新） | **楼下的好东西，都在虹选。** |
| 强调即时 | 今天下单，楼下自提。 |
| 强调商家 | 你家楼下那家店，也有自己的颜色。 |
| 强调选品 | 不是什么都卖，只卖挑过的。 |

## 6. 官网方案（hxmall.top）

### 6.1 技术选型：复用 ops-web 的栈，但独立部署

`ops-web` 已经是 **Next.js + Tailwind + shadcn/radix**，官网所需的一切它都有。

**新建 `site/` 独立 workspace，不塞进 ops-web**。理由：
- ops-web 是**内部运营后台**，需要登录鉴权、连后端 API；官网是**纯静态公开页**，不该和后台共用构建产物和部署单元
- 官网要做 SEO / OG 卡片 / 静态导出（`next export`），后台不需要，混在一起两边都别扭
- 安全边界：官网被扫、被爬、被挂，不应该和运营后台同源

```
site/                    ← 新增 workspace
  app/
    page.tsx             首页
    download/page.tsx    下载页（承接应用商店回跳）
    privacy/page.tsx     隐私政策  ← 上架强制
    terms/page.tsx       用户协议  ← 上架强制
    merchant/page.tsx    商家入驻
  public/
    brand/               品牌资产源文件（svg / png / 海报）
```

### 6.2 首页结构（一屏一件事）

1. **首屏** — logo + slogan + 下载按钮（iOS / Android / 微信小程序码三个入口）+ 手机实拍图
2. **虹的叙事** — 「每个商家有自己的颜色」，把 8 套皮肤做成可交互切换的演示（这是产品真能力，演示即证明）
3. **三步流程** — 挑 → 下单 → 楼下自提
4. **商家入驻** — 转化到 B 端
5. **页脚** — 备案号、隐私政策、用户协议、联系方式

### 6.3 下载按钮的真实约束

「下载 App」这个按钮背后有一串**没做完就点不了**的前置条件：

| 前置项 | 状态 | 说明 |
|---|---|---|
| App 图标 / 启动图 | ❌ 缺 | 见 §1.1 |
| 隐私政策 / 用户协议页 | ❌ 缺 | 上架强制，且要能公网访问 |
| 软件著作权登记 | ❓ 待确认 | 国内安卓商店（华为 / 小米 / OPPO / vivo）强制，办理约 30 天 |
| **ICP 备案** | ❓ 待确认 | `hxmall.top` 若用国内服务器/CDN，无备案直接封端口 |
| Apple Developer 账号 | ❓ 待确认 | 邓白氏编码 + 企业资质，首次办理可能数周 |
| App 备案（工信部） | ❓ 待确认 | 2024 起国内分发强制，需在 ICP 备案之后 |

> **`.top` 域名的两个现实风险**，建议现在就评估：
> 1. 部分企业安全网关和杀软对 `.top` 有默认低信任评分，可能影响分享链路的打开率
> 2. 微信分享 / JS-SDK 的域名校验、iOS Universal Links 都要求 **HTTPS + 已备案**
>
> 如果主战场在国内且预算允许，建议**同时持有一个 `.com`** 做主域，`hxmall.top` 做短链和跳转。这个决定越早越省事——品牌物料一旦印出去，域名就改不动了。

## 10. 明确不做的事

- **不改包名** `ai.neargo.shop.*` —— 理由见 §1.2
- **不改 `fresh` 皮肤的微信绿** —— 那个决策已经想清楚并写在代码注释里，品牌工程没有推翻它的理由
- **不新增设计 token** —— 品牌色复用已有的 `promo` / `violet`，避免对比度测试体系出现第二套真相
- **不把官网塞进 ops-web** —— 理由见 §6.1
