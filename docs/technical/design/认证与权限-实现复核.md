## 1. 生产库里有 11 个弱口令运营账号

`DevSeeder` 的代码侧是对的：`@ConditionalOnProperty(shop.seed.enabled)`、**默认关**、幂等、
口令走 `PasswordHasher.encode`（bcrypt）。类注释还写着 powerbank 那边「12 个假代理商」的教训。

问题只在于**生产把这个开关打开了**：

```
$ ssh <生产> grep '^SHOP_SEED_ENABLED' /opt/ai-shop/shop-app.env
SHOP_SEED_ENABLED=true
```

于是 `seedStaffs` 灌了 11 个平台账号，口令规则是「用户名 + 123」，其中
`admin` 的角色是 `SUPER_ADMIN`（`perms: ["*"]` —— 通配，全平台 99 个权限码全有）。
`docs/qa/线上验收-总纲.md` 在 **2026-08-18** 就把这条列进了「待修的安全问题」，
并记录 `POST /ops/auth/login` 实测通过。**11 天后仍然如此。**

> 我**没有去登录验证**。判据是：种子代码 + 生产环境变量 + 那份验收文档当时的实测记录。
> 这三条已经足够，而登录一次不会让结论更真、只会多一次真实的越权登录。

**关掉开关不够**：Seeder 是幂等的（「有数据即跳过」），账号已经在库里了。
两件事都要做，而且都需要有运营账号的人或 DBA：① `SHOP_SEED_ENABLED=false`；
② 把这 11 个账号删掉或改口令。**我没有那个权限，也不该去要。**

### 1.1 已做的：在运营端把它们标出来

处置要人来做，那就得先让人**认得出是哪几个**。员工列表（`/iam`）的登录名列上，
这 11 个账号带一枚红色「演示账号」角标，悬停说明写着口令规则与处置建议。
真后端上实测：15 个员工里 11 个带标。

名单**不是手抄的**：`ops-web/lib/seeded-accounts.test.ts` 直接读
`DevSeeder.java` 的 `seedStaff(...)` 调用逐条比对，漂了就红，并带一条
「一个都没扫到就不算通过」的对照量。手抄的名单一定会过期，而
**过期的名单比没有更糟** —— 它会让新加的那个种子账号看起来像正常账号。

## 2. `legacyHash` 不是哈希

```java
static String legacyHash(String raw) {
    return Integer.toHexString(("shop$" + raw).hashCode());   // 32 位
}
```

`matches()` 对任何**不以 `$2` 开头**的存量口令走这一条。32 位空间意味着
碰撞可以在本机秒级找到 —— 一个还停在这种口令上的账号，实际等于没有口令。

升级只发生在**登录成功那一刻**（`OpsServiceImpl:174`、`AuthServiceImpl:271`），
而**没有任何迁移回填过存量**。所以「自 bcrypt 上线后没登录过的账号」仍然是这种。

现在的写路径全是 bcrypt（`encode` 的 6 处调用都是），种子账号也是 bcrypt。
**所以这条今天可能一行都不命中 —— 但没有任何东西能证明这句话。** 两条路：
先用一条 `SELECT count(*) ... WHERE password NOT LIKE '$2%'` 确认为 0 再删掉回落分支；
或者留着回落但加一条闸门，让计数不为 0 时红。

## 3. 数据域：注释里那道闸不存在

`DataScopeRegistration` 的类注释写着两条性质（都对，且都是拿事故换来的）：

> ① **未注册的表 = 不过滤**。漏注册不报错、不告警，只会静默放行越权数据。
> 所以「注册」是建表的一部分，不是可选项。

紧接着写：「由 `DataScopeCoverageTest` 校验『带归属列的表都已注册』」。

**这个类不存在。** 全仓搜不到，换名也搜不到。实际的数字是：

| | 数 |
|---|--:|
| `schema-test.sql` 里的表 | 159 |
| `registry.register(...)` 登记的表 | **23** |
| 带归属列（`user_no`/`entity_no`/`merchant_no`/`community_no`/`pickup_no`/`store_no`/`mch_account_no`）却没登记的表 | **82** |

真正存在的守卫是 `packages/shared/tests/ops-data-scope.test.ts`，质量很高
（三条闸 G1/G2/G3、豁免表有反陈旧检查、还带一条「解析没失效」的对照量）。
但它的**边界要说清**，它自己也写明了：

- **G1 只看 `/ops` 的 GET**。写端点不在范围内，`/biz` 与 `/mp` 的绕过点也不在。
- **G3 只校验已登记的表**（登记了却缺锚点 → fail-closed → 整页空白）。
  「有归属列却根本没登记」这一类，**没有任何东西在看**。

所以现状是：第三道防线覆盖 23 张表，其余 136 张完全依赖 Service 层显式 where。
那是一个**合理的设计**，但它与注释宣称的纪律不一致 —— 而不一致的那一半正是
「以为防住了」。

> ⚠️ **不要把 82 张表一股脑登记上去。** 登记一张表会让所有主体维度 fail-closed，
> 漏一个锚点那类主体就整页空白（注释里 `mch_store` 那段把代价讲得很清楚）。
> 该做的是把注释改对，再立一道**棘轮**：今天 82 张，只准变少。

## 4. 公共依赖包：一个读请求头当身份的过滤器

三个包（`neargo-common-core` / `-data` / `-security`）**只有二进制、没有 source jar、
版本是 `1.0.0-SNAPSHOT`、只存在于开发机的 `~/.m2`**。本节结论全部来自 `javap`。

`neargo-common-security` 里是一整套**与本项目平行的认证栈**：
`OpaqueTokenAuthFilter`、`SessionStore`、`Realm`、`PermChecker`、`TenantContextFilter`。
它的 `AutoConfiguration.imports` 注册三个自动配置。其中：

```
SecurityAutoConfiguration
  └─ @Bean @ConditionalOnMissingBean → TenantContextFilter
```

`TenantContextFilter`（反编译）做的事是：

```
getHeader("X-Region-Id") / ("X-User-Id") / ("X-Merchant-Id") / ("X-Store-Scope")
    → TenantContext.set(...)
```

**直接把客户端请求头当身份**，没有任何认证。而 `neargo-common-data` 里的
`NeargoTenantLineHandler.getTenantId()` 读的正是 `TenantContext.getMerchantId()`，
作为 SQL 上 `merchant_id` 的租户条件。这套包的设计前提显然是
**「上游网关已鉴权并注入可信头」** —— 而 ai-shop 不是这个形态：
nginx 只反代，既不注入也不剥离这些头（`deploy/tencent/nginx/*.conf` 里
只有 `Host` / `X-Real-IP` / `X-Forwarded-*`）。

**今天这是哑弹，不是活口子**，三重原因，都验过：

1. `application.yml` 显式排除了 `SecurityAutoConfiguration` / `SessionStoreAutoConfiguration`
   / `DataAutoConfiguration`（注释说明了理由，是有意的）；
2. 即使装上，`NeargoTenantLineHandler` 还要 `neargo.mp.tenant-enabled`（默认 `false`），
   且 ai-shop 自己定义了 `MybatisPlusInterceptor` bean，`@ConditionalOnMissingBean` 会让公共包那个不生效；
3. **ai-shop 里没有任何一行读 `TenantContext`**（扫过，零命中）。

**问题在于这三条都没有断言。** 尤其第 1 条：`spring.autoconfigure.exclude` 是一个
YAML 列表，**列表是覆盖不是合并** —— 任何人为别的目的重写这一段、或加一个
profile 专属的同名键，`TenantContextFilter` 就静默回来。回来之后也**不会有任何症状**，
直到有人用了 `TenantContext.getUserId()`（那个方法名看起来完全合理）。

**这条已经补上**：`CommonPackageIsolationTest`，断的是 `TenantContextFilter` /
`SessionStore` / `NeargoTenantLineHandler` 三个类**不在 Spring 上下文里** ——
而不是「yml 里有那三行」。后者钉的是当前写法，换个等价写法（比如
`@SpringBootApplication(exclude=…)`）就会误报，而真正要保证的事没变。

它带一条**对照量**：先断言这三个类至少有一个在 classpath 上。没有这条，
依赖一旦换坐标，循环里三次 `ClassNotFound` 全 `continue`，测试空绿 ——
而空绿与「真的没装进来」在结果上一模一样。

**两向都证伪过**（用一次性测试覆盖属性，没有改共享的 `application.yml`）：

| 覆盖成 | 结果 |
|---|---|
| 三个排除全清掉 | **上下文起不来** —— 公共包那套与本项目的双池会话链硬冲突，会当场炸 |
| **只放回 `SecurityAutoConfiguration`** | **应用照常启动，`TenantContextFilter` bean 数 = 1** |

第二行正是要防的那一态：**没有任何症状**。而新守卫在这一态下确实变红（验过）。

> 顺带：`RbacAutoConfiguration` **没有**被排除（有意的 —— 判权引擎用的是它）。
> 但 `@perm` 这个 bean 是本项目的 `ai.neargo.shop.auth.PermChecker`（`@Component("perm")`），
> 公共包那个叫 `permChecker`，两者不冲突也没人用。`application.yml` 那句
> 「只启用 neargo 的 RBAC(@perm)」措辞上会让人以为 `@perm` 来自公共包，实际不是。

## 5. `/internal` 的两条不变量各缺一个守卫

`/internal/**` **不匹配任何一条 SecurityFilterChain**（四条链的 `securityMatcher` 里没有它），
所以它完全走在 Spring Security 之外，靠 `JobHandlerEndpoint` 自己验共享密钥。
那一段写得是对的：

```java
if (given == null || token == null || token.isBlank()) return false;   // fail-closed
return MessageDigest.isEqual(given.getBytes(UTF_8), token.getBytes(UTF_8));  // 常量时间
```

依赖两条不变量，两条都没有守卫：

1. **内部端点全部落在 `ai.neargo.shop.portal.internal` 包里** —— `ApiResponseWrapper`
   按**包**排除信封（`supports()` 拿不到请求，只拿得到方法）。在别的包写一个
   `/internal/**` 端点，它会被套上 `{code,msg,data}`，调度器读到的是**字段全 null**
   且不报错。这个形状 2026-08-27 真撞过一次。
2. **nginx 不反代 `/internal/**`** —— 这条在 nginx 配置里成立（`location` 只有
   `/(mp|biz|ops|actuator)`），但没有任何测试或部署检查会在它被改动时说话。

## 6. 角色×端点矩阵报错了两格，方向是最危险的那一边

`docs/technical/reference/运营端-角色×端点矩阵.md` 由 `gen-perm-endpoint-matrix.mjs` 生成，
它的**全部意义就是回答「谁能访问什么」**，而且它的产物是
`ops-perm-matrix.test.ts` 的基线 fixture —— 错的答案会被钉住。

它把 `@PreAuthorize` 配给端点的规则是**按字符距离就近**。注释里承认过这条的风险，
理由是「隔壁方法的那个总是隔着一整个方法体」—— **方法体短的时候不成立**：

| 端点 | 实际 | 矩阵里写的 | 距离 |
|---|---|---|--:|
| `GET /ops/captcha` | **没有注解**（有意的，登记在 PUBLIC 里） | 要 `message:template:read` | 783 字符 |
| `POST /ops/staffs/me/password` | **没有注解**（改自己的密码） | 要 `iam:staff:update` | 293 字符 |

两条都是**把敞开的端点报成有码**。报错方向朝着「看起来更安全」，是最不该出的那一种 ——
读表的人会以为这两条被权限挡着。

**已修**（本次）：按行窗口配对，两个方向各自遇到「另一个 Mapping」或「方法签名收尾行」
就停。判据是修完之后无码端点必须与 `OpsEndpointPermTest.ANY_OPERATOR` **逐条相等**，
现在是 **330 挂了判权 + 12 无码 = 342**，此前那份写的是 332。
顺带补了正则漏掉的 `@PatchMapping`（今天 `/ops` 下是 0 个，所以这条是潜伏的）。

同时把两份重复的清单钉在一起：生成器的 `PUBLIC` 与 Java 那份 `ANY_OPERATOR`
对不上就退出 1（此前 `/ops/stream` 只在 Java 那份里，生成器打了一路警告然后退出 0）。

## 7. 两道最要紧的守卫不在闸门里，其中一道红了四天

`packages/shared/tests/` 下有两道 ★★★ 的越权守卫，**都不在 `.githooks/pre-push`
的 vitest 清单里**：

| 守卫 | 管什么 | 本次实测 |
|---|---|---|
| `ops-perm-matrix.test.ts` | 角色×端点矩阵与代码一致；无注解端点必须登记 | **红**（`/ops/stream` 未登记 + 两条新端点没归属规则）→ **已修，已挂进闸门** |
| `ops-data-scope.test.ts` | G1/G2/G3 三条数据域结构守卫 | **红**，自 **2026-08-25** 起（`mbr_*` 登记进来那天）→ **未修，暂不挂** |
| `nav-function-point.test.ts` | 菜单叶子 ↔ 库里的功能点一一对应 | **红**，且**九条里有八条是假报** —— 它的迁移解析只认单行 `INSERT INTO`，漏掉 `INSERT IGNORE`、多行列清单、多元组 `VALUES`。已修解析器，现在绿 |
| `ops-web` 自己那套 vitest | 文案、圆角、i18n、权限镜像… | **红**（十余条，均为旧账）。整套都不在闸门里 |

> `nav-function-point` 那条尤其值得看一眼：**一道假报的守卫比没有守卫更贵**。
> 它当时指着四个**已经登记好**的进销存菜单喊缺，照着它去补会插出重复行。
> 修的时候它自带的「一个功能点都没解析到」对照量当场抓到了我第一版的错
> （`NOW()` 自带的括号把元组切碎了）—— 那条对照量正是这类守卫该有的样子。

`ops-data-scope` 红的两条：

- **G1**（9 条）：`/ops/coupons`、`/ops/members`、`/ops/persons/{}`、
  `/ops/inventory/health`、`/ops/inventory/recon` 等查询走了 `executeWithoutScope`，
  而它们包住的表**已经注册进数据域** —— 即「给客服配了只看城西片区，他照样看到全平台」。
- **G3**（多条）：`mbr_member` / `mbr_segment` / `mbr_member_tag` 等在
  `COMMUNITY`、`PICKUP` 两个维度上没有锚点列 —— 那两类运营打开会**整页空白**。

**这两条我没有修**：一条要决定「会员表在社区/自提点维度上按什么归属」，
另一条要逐个判断那些查询该不该接数据域。**都是域内决定，不是复核能替的。**

而**不挂闸门的理由不是「不重要」，恰恰相反** —— 挂一道红着的闸门等于把所有人挡在门外，
两天之内它就会被 `SKIP=1` 绕过，然后变成永久的噪声掩体。顺序只能是先修绿、再挂上。

> 这件事本身就是这次复核最值得记的一条：**一道 ★★★ 守卫红了四天没人知道，
> 因为没有任何东西会去跑它。** 写了守卫不等于有闸门。

## 8. 复核中确认是稳的

免得下次有人重走一遍：

| 面 | 结论 | 判据 |
|---|---|---|
| 四条链的边界 | 稳 | `/ops` 控制器 **60/60** 都带 `@Profile`，只跑 `api` 时是 404 而不是裸奔 |
| 令牌落库 | 稳 | 存的是 `SHA-256(token)` 的十六进制，明文不落库；读时校验 `expiresAt` 并逐出缓存 |
| 口令写路径 | 稳 | 6 处写全部 bcrypt（问题只在 §2 的读回落） |
| 跨端令牌 | 稳 | `AbstractTokenAuthFilter` realm 不符时**什么都不做**，最终 401；`CrossRealmRejectionTest` 六格都钉住 |
| CORS | 稳 | 显式来源清单、不用 `*`；放开的是请求头不是响应头，理由写在注释里 |
| 共享密钥 | 稳 | fail-closed + 常量时间比较 |
| 数据域引擎 | 稳（在它覆盖的 23 张表上） | fail-closed（拼 `1=0` 不是放行），`ops-data-scope.test.ts` 三条闸带对照量 |

## 9. 建议顺序

1. **§1 关种子 + 清账号** —— 唯一一条「今天就能被利用」的。需要运营/DBA，我做不了。
   顺带一个现成判据：生产日志里应该有 `DevSeeder` 那行
   `[DEV-ONLY] seeding demo data (shop.seed.enabled=true) —— 生产环境不应看到这条日志`。
   **应用自己一直在喊**，只是没人在看。
2. ~~§4 加一条断言~~ —— **本次已补**（`CommonPackageIsolationTest`）。
3. **§3 改注释 + 立棘轮**（82 张只准变少）。**不要批量登记** —— 登记一张表会让
   所有主体维度 fail-closed，漏一个锚点那类主体就整页空白。
4. **把 `nav-function-point` 与 `ops-perm-matrix` 一起挂进 pre-push**
   （后者本次已挂，前者刚修绿）。
5. **§2 先数一次**（`WHERE password NOT LIKE '$2%'`），为 0 就删掉回落分支。
6. **§7 的 `ops-data-scope` 那两条**（G1 九条绕过、G3 会员表锚点）—— 修绿之后
   立刻把它挂进 pre-push 的 vitest 清单，与 `ops-perm-matrix` 并排。
7. **§5.2 nginx 不反代 `/internal`** 还缺判据（§5.1 的包归属本次已补）。
