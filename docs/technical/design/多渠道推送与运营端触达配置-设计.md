# 多渠道推送与运营端触达配置 · 设计方案

状态：**待确认（2026-08-17）** —— 按「先方案后编码」，确认后再实现
关联：[触达能力矩阵](./触达能力矩阵.md)（通道现状权威）· [TDD-通知与消息推送](./TDD-通知与消息推送.md)（编排链路）· [ADR-018](../ADR/ADR-018-App生产形态与推送通道.md)（产品形态）· [需求矩阵 §5.4](../../requirements/需求矩阵-三端.md)

## 0. 要解决的两件事

owner 提出两个方向，本文各给一套方案：

1. **C/B 都是 App 时，微信通知不能丢，且「谁走哪些通道」要运营端可配。**
   现在的通道路由是**代码里硬编码**的规则表（`NotificationConsumer`），改一条要发版；
   而且「装了 App 就不发微信」这种决定不该藏在代码里 —— 它是运营策略。
2. **推送要多渠道并存**：个推（现有）+ 将来 Google FCM + Apple APNs 直连。
   现在 `PushPort` 只有一个实现（个推），`msg_push_token` 连「这台设备属于哪个推送供应商」
   这个维度都没有。

两件事是连贯的：**需求 1 决定「发不发 push」，需求 2 决定「push 走哪个供应商」。**

## 1. 现状与扩展点（已核对代码，2026-08-17）

| 点 | 现状 | 差距 |
| --- | --- | --- |
| 通道 SPI | `SmsPort` / `MailPort` / `WxSubscribePort` / `PushPort` / `MessageService` 各就位 | ✅ 领域只依赖 SPI，加通道不碰领域 |
| 事件→通道路由 | **硬编码**在 `NotificationConsumer`（§4.5 规则表就是它） | ❌ 运营改不了 |
| 微信订阅 | `WxSubscribePort` + `WxSubscribeGateway`，openid 来自 `usr_identity` | ✅ 通道在，但何时用它由代码定 |
| App 推送 | `PushPort.push(clientId,…)` **单方法单实现**（`GetuiPushGateway`） | ❌ 无供应商路由 |
| 设备表 | `msg_push_token(receiver_type, receiver_no, platform, client_id)` | ❌ **无 `provider` 维度**，`client_id` 注释写死「个推 cid」 |
| 运营端触达配置 | `msg-templates`（模板启停）+ `notify-quota`（频控）+ 测试发送 | ❌ **无「场景×通道」开关** |

**结论**：两个需求各需一处新增，但都**不动 SPI 契约**（领域依然只说「发什么」，不感知通道/供应商）。

## 2. 需求 1 · 场景 × 通道，运营端可配

### 2.1 核心概念：一个用户可能同时被多条通道触达

一个买家可以**同时**有：App（`client_id`）+ 微信（`openid`）+ 手机号。「到货了」这件事，
运营可能希望**三条都发**（App 息屏响一下、微信服务通知留一条、站内信永远在）。

> **「App 也继承微信」的准确含义**：装了 App **不等于**砍掉微信通道。
> 用户在 App 里下单，出门在路上收到 App 推送；但他也可能长时间在微信里，
> 微信服务通知是另一次触达机会。**是否叠加发，由运营按场景决定，不由「用户装没装 App」决定。**

### 2.2 新增配置表 `msg_scene_channel`

把 §4.5 那张硬编码规则表搬进库：

```
msg_scene_channel
  scene_code   VARCHAR   -- 场景码：ORDER_ARRIVED / SUB_ORDER_PAID / AFTER_SALE_APPLIED …（= 事件码）
  audience     VARCHAR   -- 受众：C_USER / B_STAFF / OPS_STAFF（一个事件可有多受众，各一行）
  channel      VARCHAR   -- 通道：INAPP / WXSUB / PUSH / SMS / BROWSER
  enabled      TINYINT   -- 运营开关
  push_level   VARCHAR   -- 该场景的 push 级别 NORMAL/RING（仅 channel=PUSH 有意义）
  -- 唯一键 (scene_code, audience, channel)
```

- **`INAPP` 行永远 enabled 且不可关**（站内信是事实记录，见 TDD 原则）—— 界面上置灰。
- 运营端 `POST /ops/scene-channel/{scene}/{audience}/{channel}` 切开关，
  `GET /ops/scene-channel` 拉整张矩阵（一个「场景×受众×通道」的勾选面板）。
- **种子**：把现有 §4.5 规则表灌成初始数据，行为与现在**逐格一致**（不改默认行为，只是搬到可配层）。

### 2.3 编排改造

`NotificationConsumer` 从「switch 硬编码」改成「查 `msg_scene_channel` 决定发哪些通道」：

```
收到事件 evt(scene, 受众解析出的收件人)
  → 查 msg_scene_channel WHERE scene=evt.scene AND enabled=1
  → 对每个 enabled 的 channel：
       INAPP  → 永远发（站内信必达）
       WXSUB  → 有未消耗授权额度才发，否则静默降级（现有逻辑）
       PUSH   → 交给 §3 的 PushRouter（可能命中 0~N 台设备/多供应商）
       SMS    → 仅强通知，走频控
  → 任一外发通道失败：留痕 sys_notify_log，不阻塞（现有原则不变）
```

**频控（`NotifyQuota`）位置不变**：仍只作用于 `MARKETING`，交易/待办类不受限。

### 2.4 这一步的边界

- **不做**「每个用户自定义通道偏好」——那是需求矩阵 §5.4 里单列的「用户免打扰/偏好」，本方案只做**运营侧全局配置**。用户级偏好是后续叠加层（`msg_scene_channel` 之上再 AND 一个用户开关）。
- 站内信不可关这条**硬编码在编排里**，不信任配置表 —— 配置表被误删/误关也不能让事实记录消失。

## 3. 需求 2 · 多 Push 渠道路由（个推 → +FCM +APNs）

### 3.1 为什么个推之外还要 FCM / APNs

个推（uni-push 2.0 底座）**已经聚合**了国内厂商通道（小米/华为/OPPO/vivo/荣耀）+ 透传 APNs。
但两个场景个推覆盖不到或不理想：

- **海外 Android**：Google Play 生态靠 **FCM**，国内推送商在墙外覆盖弱/不可达。
- **iOS 直连 APNs**：个推透传 APNs 够用，但若要脱离聚合商依赖、或做富媒体/精细化，需 **APNs 直连**。

所以 `PushPort` 要能按**设备所属供应商**路由到不同 gateway。

### 3.2 设备表加 `provider` 维度

```
ALTER TABLE msg_push_token ADD COLUMN provider VARCHAR(16) NOT NULL DEFAULT 'GETUI'
  COMMENT '推送供应商 GETUI / FCM / APNS';
```

- 端上注册时上报 `provider`：uni-push 打包 → `GETUI`；将来海外包集成 FCM SDK → `FCM`；
  iOS 直连 → `APNS`。默认 `GETUI` 兼容存量。
- 唯一键从 `(receiver_type, receiver_no, platform)` 扩成
  **`(receiver_type, receiver_no, platform, provider)`** —— 同一台 iOS 可能同时有个推 cid 与 APNs token，
  是两条设备令牌，两条都可发（或按路由策略择一）。

### 3.3 引入 `PushRouter`，SPI 不变

**`PushPort` 契约一个字不改**（领域仍只调 `push(clientId,…)` 的语义层）。改的是 `PushSender`：
它现在按 (receiverType, receiverNo) 查 token 列表 → 逐台发；改成**按 token.provider 分发到对应 gateway**：

```
PushSender
  → 查该收件人所有 msg_push_token（可能多台、多供应商）
  → 每台 token 按 provider 选 gateway：
       GETUI → GetuiPushGateway（现有）
       FCM   → FcmPushGateway（新，shop-channel）
       APNS  → ApnsPushGateway（新，shop-channel）
  → 逐台发，单台失败不拖累其它台（现有原则不变）
```

- 每个 gateway 是一个 `PushGateway` 实现（内部接口，不是对领域的 SPI），
  按 `provider` 注册进一个 `Map<String, PushGateway>`。加供应商 = 加一个 gateway + 一行注册，不碰领域、不碰 `PushSender` 主逻辑。
- 各 gateway 各自的密钥走环境变量（`GETUI_*` 已有；FCM 用 **OAuth2 v1**(service account，非 legacy server key)，
  APNs 用 **ES256 provider token**(`.p8`)，具体变量见 §5），默认桩 —— 与现有所有通道同一套「默认桩，生产配密钥启用」。

### 3.4 路由策略（可配，但先给默认）

初期默认策略（写死，够用）：**一台设备一个 provider，注册时定死，发送时照 provider 走。**
不做「个推失败降级到 FCM」这种跨供应商 fallback —— 那需要同一台设备有多供应商 token，
一期不制造这种复杂度。将来若需要，路由策略也进 §2 的运营配置层。

## 4. 决策与取舍

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 通道路由存哪 | **配置表 `msg_scene_channel`**，不是代码 | 运营策略要能不发版就改；种子灌成现状，默认行为不变 |
| 站内信可不可关 | **不可关，硬编码在编排** | 事实记录不能被一个配置开关抹掉 |
| `PushPort` 要不要改 | **不改** | 领域不该感知「个推还是 FCM」；路由是通道层的事 |
| 多供应商怎么落 | 设备表加 `provider` + `PushRouter` 按 provider 分发 | 加供应商 = 加 gateway + 注册，隔离干净 |
| 跨供应商 fallback | **一期不做** | 需要一台设备多 provider token，复杂度不匹配当前阶段 |
| 用户级偏好 | **一期不做**（本方案只做运营全局配置） | 是 §2 之上的叠加层，单列 |

## 5. 迁移影响与分期

**不改默认行为**：`msg_scene_channel` 种子 = 现有 §4.5 规则表逐格照搬；`provider` 默认 `GETUI`。
上线后系统行为与现在**一模一样**，只是把「硬编码」变成「可配 + 可扩」。

| 阶段 | 内容 | 依赖 | 状态 |
| --- | --- | --- | --- |
| P1 · 配置化 | `msg_scene_channel` 表 + 种子 + 编排读表 + 运营端勾选面板 | 无外部依赖，纯代码 | ✅ 已实现 |
| P2 · 多渠道骨架 | `msg_push_token.provider` + `PushRouter` + gateway 接线 | 无外部依赖，纯代码 | ✅ 已实现 |
| P3 · 渠道 HTTP 实现 | `FcmPushGateway`(OAuth2 RS256→messages:send) / `ApnsPushGateway`(ES256 JWT→HTTP/2)，纯 JDK 无 SDK，默认关（`shop.push.{fcm,apns}.stub`）；`PushCrypto` 签名单测覆盖 | 无外部依赖，纯代码 | ✅ 已实现 |
| P3′ · 真实上线 | 填密钥 + 端上按包上报 provider + 联调 | 行政：Firebase 项目、Apple APNs `.p8`/证书；海外包构建 | ⬜ 待资质 |

P3 通道所需环境变量（开启时 `stub=false` 且必填，否则 fail-fast）：
- **FCM**：`FCM_PROJECT_ID` / `FCM_CLIENT_EMAIL` / `FCM_PRIVATE_KEY`(service account PKCS#8 PEM) / `FCM_TOKEN_URI`(默认 Google)
- **APNs**：`APNS_TEAM_ID` / `APNS_KEY_ID` / `APNS_PRIVATE_KEY`(`.p8` PKCS#8 PEM) / `APNS_TOPIC`(= app bundleId) / `APNS_HOST`(默认 `api.push.apple.com`，沙箱另填)

**守卫**：`msg_scene_channel` 种子必须与代码里的场景枚举一一对应（防止改了事件码、配置表对不上，静默不发）——
一条与 `biz-role-seed` 同形的种子一致性守卫。
