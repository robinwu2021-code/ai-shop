## 1. 这是什么（L1）

**用户从头到尾看到「一单」，提交后拿到两笔子订单。**

第一轮 H5 测试实测：加购两家店的商品 → 购物车把它们并在一张「自提点自提」的卡里、
店名一个字不显示 → 确认订单页同样只列一份清单 → 提交后 `ord_sub_order` 出来两行。

功能清单 C-CT-02 早就写了防线（「购物车按店分组展示，**因为结算时会拆单**」），
只是没建起来。

## 2. 根因不是「设计成按履约分组」（L2）

一开始我以为这是产品取舍。查下来不是——**后端一直在发商家信息，端上把它丢了**。

| 层 | 有没有商家字段 |
|---|---|
| 后端 `CartItemVO` | ✅ `merchantNo` / `merchantName` |
| 实测响应 | ✅ `merchantNo="M0001"`, `merchantName="老张粮油店"` |
| **shared `CartItem`** | ❌ **两个字段都没声明** |
| `cart/index.vue` | 只按 `fulfillment` 分组（数据都没有，也分不了） |

所以它和 B 端联调那批缺陷是**同一形状的镜像**：那边是「契约有、后端不发」，
这边是「后端发了、契约不接」。两者 `check:api` 都抓不到——路径对得上，字段对不上。

> 顺带解释了为什么这个缺口能活这么久：页面看起来「就是这么设计的」，
> 而没有任何守卫会因为端上少声明一个字段而变红。

## 3. 为什么不能简单改成按商家分组（L4 前置）

履约分组**是结构性的**，不是随手选的：

`cart/index.vue:26-34` 的结算入口按 `fulfillment` 走，一个履约方式进一次确认页。
原因是不同履约方式的收货信息根本不同——自提要选自提点、快递要填地址、
上门要选预约时段。**同一家店的自提商品与快递商品塞不进同一个确认页。**

所以方案是**二级分组**：外层保留履约（结算单位不变），内层按商家分段。

## 4. 方案（L3）

### 4.1 改动清单

| 层 | 文件 | 改什么 |
|---|---|---|
| 契约 | `packages/shared/src/types/index.ts` | `CartItem` 补 `merchantNo` / `merchantName` 两个字段 |
| 视图模型 | `c-app/src/stores/cart.ts` | `groups` 内部再按 `merchantNo` 聚一层 |
| 页面 | `c-app/src/pages/cart/index.vue` | 履约卡内按商家分段，段头显示店名 |
| 页面 | `c-app/src/pages/order-confirm/index.vue` | 同样按商家分段——**这里才是拆单真正发生的地方** |
| i18n | `c-app/src/i18n/locale/*.ts` | 拆单提示文案（三语） |
| mock | `c-app/src/api/mock.ts` | 购物车行补两个字段，否则 mock 下这一层分组是空的 |

### 4.2 数据结构

```ts
// 外层不变：结算单位
interface CartGroup {
  fulfillment: FulfillmentType;
  items: CartItem[];
  /** 新增：按商家再分一层。items 保持原样，段是它的视图投影 */
  merchants: { merchantNo: string; merchantName: string; items: CartItem[] }[];
}
```

**`items` 保留不动**，`merchants` 是它的投影。结算入口 `go(fulfillment, items)` 一行不改——
拆单本来就在后端按商家做，端上只是把它显示出来。

### 4.3 确认订单页要多一句话

按商家分段之外，当段数 > 1 时显示一行提示：

> 这些商品来自 2 家店，将生成 2 笔订单，**一次付清**。

这句话直接对上 C-OD-06「拆单披露」的意图，只是把披露时机从订单详情提前到提交前。
提交后才知道会拆，那个披露就只剩解释作用了。

## 6. 边界（L4）

- **不动结算单位**：`go(fulfillment, items)` 保持按履约走。改它要先回答
  「一家店跨两种履约方式怎么结算」，那是另一个问题
- **不动后端**：字段本来就在发
- **跨商家优惠摊分仍未定**（C-CT-05 的已知未决）：券与积分目前只作用首笔子订单。
  本方案让「有几家店」变得可见，**会让这个未决更容易被用户注意到**——
  但不因此就地决定摊分口径，那是 M4 的事

## 8. 落地时多做的两件事

### 8.1 反方向的契约守卫

`biz-contract-fields.test.ts` 原先只查「契约要的、后端没有」。这个缺口能活这么久，
正是因为**没有任何东西查反方向**。补了一条「后端发了、契约没接」的棘轮。

度量踩过一次坑：第一版按「端点条目」计数，修好 `subOrders` 之后条目一条没少
（那几条还欠着别的字段），**「修了一个真问题」和「什么都没干」在数字上一模一样**。
改成按「类型.字段」去重计数才看得出进展。基线：b-app 16、c-app 31。

### 8.2 顺手修掉同族第三例：收银台

`Order` 没声明后端一直在发的 `subOrders`，于是**收银台是整条链路里唯一哑掉的一屏**：
购物车说会拆 2 单、确认页说会拆 2 单、订单详情各自标着商家，付款那一步只有一个总额。
现在显示「本次付款覆盖 N 笔订单」+ 逐店金额。

> 更正一处我自己的误判：一度以为「C-OD-06 拆单披露没实现」。**订单详情那条早就在**
> （`order/index.vue:277`），缺的只是支付视角。从守卫输出直接推断而不看页面，
> 就会得出这种结论。
