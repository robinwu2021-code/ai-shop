## 1. 这是什么

交互清单逐项复核查出的七处问题，分三批修。**根因分析在清单 §10.2**，

七条的共同点：**都不报错**。四条是判据写错（用了废弃的状态值、抄错了状态机、

## 2. 分批与理由

| 批 | 条目 | 为什么放一起 |

## 3. 批次一 · 设计

### 3.1 G16 · 让废弃的状态值编译不过

判据里的 `ARRIVED` / `SHIPPED` 早已并成 `FULFILLING`。**类型系统当时抓不到**，
因为数组字面量被推断成 `string[]`，而 `Array<string>.includes()` 收任何字符串。

所以修法不是「把两个值换掉」，是**让这一类错误以后编译不过**：

```ts
const AFTER_SALE_STATES: readonly OrderStatus[] = ["PAID", "FULFILLING", "COMPLETED"];
```

标成 `OrderStatus[]` 之后，再写一个不存在的状态值当场报错。
`canInvoice` 排除的 `"CLOSED"` 同样不是 `OrderStatus` 的成员，一并处理。

> ⚠️ **这一条是判据修复，不是放宽**：`FULFILLING` 本来就该能申请售后
>（货不对、货损了正是这个阶段发现的），此前是被两个废弃值挡在外面。

### 3.2 G14 · 取消订单：两个方向都对齐状态机

后端 `OrderStateMachine`：`WAIT_PAY → {PAID, CANCELLED, CLOSED}`、
`WAIT_OFFLINE_PAY → {PAID, CANCELLED}`、**`PAID → {}`**。

| 端上现在 | 应当 |
|---|---|
| `WAIT_PAY \|\| PAID` | `WAIT_PAY \|\| WAIT_OFFLINE_PAY` |

已付款要退钱走**售后**，不是取消 —— 而售后入口正是 G16 修好的那个。
两条必须同一批做：只修 G14 的话，已付款订单会既没有取消也没有售后，
比现在更糟。

收银台的 `cancel()` 补 `try/catch + toast`：它现在失败时既不跳也不说，
而同一个动作在订单详情页是接住并 toast 的。

> **端上仍然抄了一份状态机**，这是已知的次优解。彻底的做法是 `OrderVO`
> 带上 `cancellable`，端上只读它 —— 那是契约变更，归在批次二一起做更省事。
> 这一批先让行为对上。

### 3.3 G12 · 数量按库存封顶

`stepQty` 只封 `limitPerUser`。上限改成两者取小：

```ts
const maxQty = computed(() => Math.min(
  goods.value?.limitPerUser || Infinity,
  sku.value?.stock ?? Infinity,     // 缺省不设限，与购物车同一条口径
));
```

**不改后端**：提交时锁库存那一道必须留着，它才是真源；
端上这一层只是让人早点知道。切换规格时数量要跟着回落到新 SKU 的上限内 ——
不回落的话「选了 A 规格买 50 件，切到只剩 3 件的 B 规格」数量还停在 50。

### 3.4 G13 · 把「为什么不能买」说出来

`buyable` 有四条否决条件，按钮文案只区分两条（售罄 / 加入购物车），
截单另有一枚红 chip，**没选预约时段那一条页面上一个字都没有**。

做法与结算页的 `submitBlockedReason` 一致：**一个计算属性，与 `buyable`
共用同一份判据**，贴在操作条上方。

```ts
const buyBlockedReason = computed(() => {
  if (!sku.value) return t("goods.whyNoSku");
  if (soldOut.value) return "";                 // 按钮文案已经说了
  if (cutoffPassed.value) return "";            // 顶部那枚红 chip 已经说了
  if (!appointmentReady.value) return t("goods.whyNoSlot");
  return "";
});
```

> **已经有地方说了的就不再说一遍** —— 同一件事说两遍会让人以为是两个问题。
> 这与结算页那条「一次只说一条」是同一条原则。

### 3.5 G11 · 灰按钮必须配一句话

`removeMarked()` 开头的 `if (!n) return;` 换成 toast，与同一页的
「去结算」对称（那个已经有 `cart.pickSomething`）。新增词条 `cart.pickToRemove`。

## 4. 测试策略

全部进 `c-app/tests/`，**每条都要能做消融**（撤掉修复必须变红）：

| 用例 | 断言 |
|---|---|
| `FULFILLING` 的订单要有售后入口 | G16 的回归位 |
| 已付款订单**不给**取消入口 | G14 |
| 当面付待收款订单**要给**取消入口 | G14 |
| 收银台取消失败 → 有 toast、不跳转 | G14 |
| 库存 3 时数量加不到 4 | G12 |
| 切规格后数量回落到新上限 | G12 |
| 没选时段 → 页面出现那句话 | G13 |
| 一件没勾点删除 → 有 toast | G11 |

订单详情页此前没有组件测试，这一批**顺带把它挂起来** ——
它是这条链上分支最多的一页（六个操作按钮各有出现条件）。

## 5. 风险

- **G16 放开售后入口之后，后端会不会拒**？售后单的状态机与订单状态机是两张表，
  `FULFILLING` 的子单允许 `→ REFUNDED`，所以放开是对的。落地前在 mock 上走一遍。
- **端上抄状态机**：G14 修完仍然是抄的。批次二加 `cancellable` 之后要回来删掉这份抄写，
  否则下次后端改状态机，端上又会悄悄对不上。已记在 §3.2。

## 7. 批次二实际做了什么（与 §2 的设想有出入，记下来）

### 7.1 「四个字段」其实是**四件不同的事**

| 字段 | 设想 | 实际 |
|---|---|---|
| `reviewed` | 后端补 | ✅ 后端补。新增 `ReviewQueryPort`（trade → product），键是**子单号**不是主单号 —— 评价是对商家的 |
| `afterSale` | 后端补 | ✅ 后端补。`AfterSaleService` 加 `ofSubOrder`，取**最新一张**（一张子单可以先被驳回再申请一次） |
| `redeemCode` | 端上改口径 | ✅ 端上改。后端明说三种码共用 `verifyCode`，端上按品类与履约方式决定标签，判据抽进 `order-view.ts` 供两页共用 |
| `payGroupNo` | 后端补 | ❌ **补不了 —— 后端库里、VO 里都没有这个概念**，它是 mock 造出来的。真实模型里「这次支付覆盖几笔」由主单下的子单张数表达，所以发的是 `payGroupSize`（个数）而不是编号 |

最后那条是这一批最值得记的一点：**照着端上的类型去后端「补字段」，前提是那个字段在后端有意义**。
`payGroupNo` 没有，硬补就是把 mock 的臆想固化进契约。

### 7.2 三个字段**只在详情视角查**

`orderView(s, order)` 被列表与详情共用，在那里查就是每条订单三次额外查询（N+1）。
所以 `OrderVO` 加了一个 `withDetail(...)`，只有 `detailOf` 调它。

### 7.3 可选字段棘轮：量出来 b-app 9 / c-app 12

原来的守卫只判**必填**字段（可选的少一个不会让端上崩，按设计跳过）——
而 G15 这四条全是可选的。补了一条只许降不许升的棘轮，基线是实测值。
消融验过：随便加一个后端没有的可选字段，c-app 从 12 变 13，闸门变红。

顺带把「后端在发、契约没接」那条的 c-app 基线从 25 抬到 28。
**抬的不是欠账**：`OrderVO` 多了三个字段，而 `OrderPreview` 是它的有意子集，
于是一口气多欠三条 —— 那是这条棘轮已知的钝处（要分开得给子集类型加标记）。

### 7.4 一次险些被放过的绿

改完 `OrderVO` 之后 `mvn test-compile` 报 **BUILD SUCCESS**，而两处测试构造点
还是旧的参数个数 —— 是增量编译没有重编未变的测试源码。
删掉 `target/test-classes` 再编才报出那两处。
**「编过了」要看它到底编了什么**，尤其是改了被广泛引用的类型之后。
