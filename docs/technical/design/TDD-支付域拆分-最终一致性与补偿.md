> 图：[三层保证与 7 处调用的分类](../diagrams/pay-eventual-consistency.svg)

## L1 · 立场：跨域事务不是拆分带来的问题，是拆分暴露的缺陷

`SettlePort#generateForOrder` 上写着：

> 刻意做成**同步、同事务**而不是走事件异步：异步投递一旦失败，
> 就会出现「订单已支付但没有结算单」—— 这种不一致只能靠对账发现。

这句话在写下的那天是对的判断，但它的前提值得推敲：**同事务并没有真的消除那个不一致**。

- 数据库 commit 成功、应用没收到响应 → 业务以为失败，实际成功；
- 进程在 commit 之后、发事件之前崩溃；
- 支付回调重发时前一次仍在事务里。

单体只是把窗口从「秒级」缩到「毫秒级」，**没有消除它**。而窗口没有消除，
就意味着「订单已支付但没有结算单」今天也会发生 —— 只是频率低到没人查过，
**而且今天没有任何东西会发现它**（没有对账兜底，没有重试任务）。

所以拆分要做的不是「引入一个新风险」，而是**把一个一直存在、无人监测的风险
变成一个有机制处理的常规路径**。这也是互联网业务的通行做法：
减少分布式事务，改用最终一致性 + 幂等 + 补偿 + 对账兜底。

> 有一处**今天就已经是最终一致性的形状**：退款链路的 `REFUNDING` 状态
> 「失败就停在这里等重试」。但：
> ```bash
> grep -rln "REFUNDING" shop-*/src/main/java | grep -i "job\|retry"   # 空
> ```
> **没有任何任务在重试它。** 卡住的单子会一直卡着，直到有人发现。
> 这不是拆分才会有的问题，是今天就欠着的账。

## L2 · 一、三层保证（缺一层都不够）

| 层 | 机制 | 保证 | 现状 |
|---|---|---|---|
| **L1 可靠投递** | Outbox —— 事件与业务数据同事务落库 | at-least-once | ✅ `OutboxEventBus` + `OutboxDispatcher` 已有 |
| **L2 幂等消费** | 按业务键唯一索引去重 | at-most-once 生效 | ⚠️ 机制有（`IdempotencyService` 是**接口级**的），域内事件级要新建 |
| **L3 不变式兜底** | 定时扫「本该成立而没成立」的事实并修复 | **兜住前两层都漏掉的** | ❌ 没有 |

**L1 + L2 = 恰好一次生效**，这是常规路径。

**L3 不是可选项**，理由是 L1+L2 有两个盖不住的洞：

1. **Outbox 那一行本身没写成功** —— 比如业务事务回滚了但 pay 侧已经被别的路径写过；
2. **消费者的逻辑有 bug** —— 消息到了，处理错了。

L3 不看消息、不看重试次数，**只看事实**：「这个子单是 PAID，它有没有结算单？」
这是唯一一层不依赖上面两层正确性的检查。

> 记忆里那条「验证量要能证伪」在这里的样子：L3 的每条不变式都要有一个
> **对照量**（扫了多少行），否则「差异 0 条」和「一行都没扫到」长得一模一样。

## L2 · 二、7 处跨域调用，逐个改法

先按**方向**分类 —— 这决定了用哪种机制，不能一律套 Outbox：

| 方向 | 含义 | 机制 |
|---|---|---|
| **前置** | 业务成立**之前**先动了 pay 的账 | 预扣 + 确认 / 超时释放（TCC 形状） |
| **后置** | 业务已成，pay 侧必须最终发生 | **Outbox + 幂等** |
| **补偿** | 它本身就是补偿动作 | Outbox（补偿也要保证到达） |
| **有序** | 两步有严格先后，前一步失败必须停 | 状态机 + 任务重试 |

### 七处

| # | 位置 | 方向 | 拆后失败会怎样 | 改法 |
|---:|---|---|---|---|
| 1 | `OrderServiceImpl:586` `pointsPort.deduct` | **前置** | **分扣了、单没建** —— 用户白扣，且他不会来报（以为没下成） | 预扣冻结 + 落单后确认 + 超时释放 job |
| 2 | `OrderServiceImpl:944` `pointsPort.grant` | 后置 | 付了款没发分 | Outbox + 按 `subOrderNo` 幂等 |
| 3 | `OrderServiceImpl:963` `settlePort.generateForOrder` | 后置 | **付了款没结算单** —— 钱躺在平台账上 | Outbox + 幂等 + **不变式 I1 兜底** |
| 4 | `OrderServiceImpl:1058` `pointsPort.reverse`（取消） | 补偿 | 单取消了分没退 | Outbox + 按 `subOrderNo` 幂等 |
| 5 | `OrderServiceImpl:1105` `pointsPort.reverse`（超时关单） | 补偿 | 同上 | 同上 |
| 6 | `AfterSaleServiceImpl:319` `settlePort.reverseSplit` | **有序·第一步** | 分账没回退就退款 → 商家已提现的部分只能人工追 | **保持同步调用**，失败停在 `REFUNDING`；把重试从「没人重试」改成 job 驱动 |
| 7 | `AfterSaleServiceImpl:327` `settlePort.refund` | 有序·第二步 | 分账回退了但没退款 → 用户等着钱 | 同上，`REFUNDING` 续跑 |

### 三处要展开说

**① 下单扣积分 —— 唯一一处不能用 Outbox 的**

Outbox 的语义是「业务已成，后续必达」。而扣积分发生在订单**还没落库之前**
（要先知道扣了多少才能算实付）。事务一拆，顺序就成了：

```
扣分 → 建单            扣成功、建失败 → 用户的分白扣了
建单 → 扣分            建成功、扣失败 → 用户白拿了优惠
```

两个方向都错。做法是**预扣**，也就是 TCC 的 try/confirm/cancel，
但**只在这一个点上用**（别处不引入 TCC，成本不值得）：

```
① try     pointsPort.freeze(userNo, amount, orderNo)   →  冻结，不扣减可用余额之外的东西
② 建单
③ confirm Outbox 事件 OrderCreated → pay 侧把冻结转为已扣
④ cancel  超时 job：冻结超过 N 分钟且订单不存在 → 自动释放
```

第 ④ 步是关键：**它让「建单失败」不需要任何人处理**。
不写第 ④ 步的话，这就不是 TCC，是一个会漏的两阶段。

> `pts_user_account` 已经有 `pending_balance`（V25，未过售后期的分放在这里），
> 冻结可以复用同一套「可用 vs 不可用」的概念，不需要新表。

**② 生成结算单 —— 要改的是那句注释，不是否定它**

改成 Outbox 之后，「订单已支付但没有结算单」的窗口从「毫秒」变成「投递延迟」，
通常是秒级。这个窗口**是可接受的**，因为：

- 结算单不影响用户任何可见行为（他已经付完款了）；
- 商家看到的「待结算」本来就有账期（T+1 起）；
- **I1 兜底每小时扫一次**，窗口超过一小时会告警。

而它换来的是：`markPaid` 的事务从「订单 + 配额 + 积分 + 结算单 + 事件」缩到
「只写订单表」。**支付回调的 P99 会变好**，这是拆分顺带的收益，不是代价。

**③ 退款两步 —— 今天已经对了，只差重试**

`doRefund` 的顺序注释写得很清楚：「① 回退分账，失败就停在 REFUNDING，**绝不往下走**」。
这已经是正确的最终一致性形状 —— 拆进程后这个顺序**一个字都不用改**。

要补的只有一件事：**一个重试 job**。今天卡在 `REFUNDING` 的单子没有任何东西会碰它。

## L2 · 三、不变式清单（L3 的判据）

每条都是一句「本该成立」的话，扫出来的差异就是要修的账。

| 编号 | 不变式 | 违反时怎么办 | 频率 |
|---|---|---|---|
| **I1** | 每个 `PAID` 子单**必有** `stl_bill` | 自动补生成（幂等，安全） | 每小时 |
| **I2** | 每个 `stl_bill` **必有**对应的已支付子单 | **只告警不自动删** —— 删账是不可逆动作 | 每小时 |
| **I3** | `sub.points_granted = true` ⟺ 存在该子单的发分流水 | 两边不一致时以**流水**为准，回修标记 | 每天 |
| **I4** | 状态为 `REFUNDED` 的售后**必有** `split_reversed = true` | 告警 + 转人工（钱已经退了，只能追） | 每小时 |
| **I5** | 卡在 `REFUNDING` 超过 30 分钟的售后 | 触发重试；超过 24h 转人工 | 每 10 分钟 |
| **I6** | 冻结中的积分，其订单必须存在 | 超时自动释放 | 每 5 分钟 |
| **I7** | 积分池恒等式（发放 = 出账） | 已有 | 已有 |

**每条都要报「扫了多少行」**，不只报「差异几条」——
差异 0 条与一行都没扫到在结果上一模一样，而后者才是最该红的那种。

## L3 · 四、任务清单

分四批。**前两批与拆分无关，是今天就该有的**——所以即使拆分中途停下，
它们也不白做。

### 批 A · 补今天就欠的账（可立即开始，不依赖任何拆分动作）

| # | 任务 | 验收 |
|---:|---|---|
| A1 | `REFUNDING` 重试 job（I5） | 造一个 `reverseSplit` 失败的单，断言 job 跑过后它推进了 |
| A2 | I1 / I2 / I4 三条不变式的扫描 job + 告警 | **注入一条违反**，断言扫得出来；并断言扫描行数 > 0 |
| A3 | 域内事件级幂等表 `pay_event_consumed(event_no, handler)` | 同一事件投两次，断言只生效一次 |

> A1 + A2 做完，今天的系统就已经比现在健壮 —— **与拆不拆无关**。

### 批 B · 解开事务耦合（拆分的核心，仍不动进程）

| # | 任务 | 依赖 | 验收 |
|---:|---|---|---|
| B1 | pay 建独立 `DataSource` + `TransactionManager`（URL 仍指主库） | — | **负面对照**：`@Transactional` 里写业务表 + pay 表后抛异常，断言业务表回滚而 pay 表没有 |
| B2 | 第 2 / 3 处改 Outbox（`grant` / `generateForOrder`） | A3, B1 | 混沌：投递器停摆，断言 I1 兜底把结算单补出来 |
| B3 | 第 4 / 5 处改 Outbox（两处 `reverse`） | A3, B1 | 同上 |
| B4 | 第 1 处改预扣 + 确认 + 超时释放（I6） | B1 | 建单强制失败，断言冻结在 N 分钟后自动释放 |
| B5 | 第 6 / 7 处：确认状态机顺序不变，接上 A1 的重试 | A1 | 拆进程后行为不变 |

**B1 是这一批的地基**：它一装上，剩下四个任务就从「记得改」变成「不改就编译不过 / 测试红」。

### 批 C · 收拢与产物（结构性改动，风险低）

| # | 任务 | 说明 |
|---:|---|---|
| C1 | `shop-base` 去 MyBatis，拆 `-web` / `-auth` / `shop-store-*` | 见[基础包分层](./TDD-基础包分层与支付双形态.md) |
| C2 | `shop-settle` → `backend/pay/pay-{api,domain,store,channel,risk,web,job}` | **纯搬家**：域边界已经干净（见下） |
| C3 | `PayPort` + `LocalPayAdapter` + `RemotePayClient` + `shop.pay.mode` | 装配测试两种形态 |
| C4 | `pay-svc` 产物 + AOT 断言 + jar 内无 `mybatis-*.jar` | 本地起起来，不接流量 |

> **C2 比预想的便宜。** 量过了：
> ```bash
> grep -rh "^import ai.neargo.shop.settle" shop-{core,merchant,channel,notify,app}/src/main/java | wc -l
> # 0
> ```
> 零个业务模块 import 它；`shop-settle` 自己也只依赖 `common` / `spi` / `auth`，
> 不碰任何业务域。别处出现的十几个 `stl_` **全在注释里**，没有一处真查表。
> Port 模式确实起作用了 —— 这一步是改包名和 pom，不是解耦。

### 批 D · 切换（每步可回滚）

| # | 任务 | 回滚方式 |
|---:|---|---|
| D1 | 会话外置：`token-store` → `db`，按 operator → merchant → consumer **分三批，各观察一天** | 改回配置 |
| D2 | nginx 切一条只读路径到 :8083，比对两个进程返回是否逐字节一致 | 改一行 nginx |
| D3 | 逐步切其余只读路径 | 同上 |
| D4 | 切写路径（放款、进件、回调） | 同上 + 幂等保证重放安全 |
| D5 | 主应用去掉 pay-* 依赖，只留 `pay-api` | 发版回滚 |
| D6 | **切库**：URL 指向 `ai_shop_pay` | **第一个不可轻易回退的步骤，单独评审** |

## L3 · 五、验收：混沌注入，而不是「跑一遍没报错」

每个改造点配一条**注入测试**，形状统一：

```java
@Test
void 投递器停摆时_不变式兜底能把结算单补出来() {
    outboxDispatcher.pause();                 // 注入：L1 失效
    orderService.markPaid(orderNo, ...);
    assertThat(billsOf(orderNo)).isEmpty();   // 前置断言：确实没生成（否则这个测试测了个寂寞）
    invariantJob.run();                       // L3 兜底
    assertThat(billsOf(orderNo)).hasSize(1);
}
```

**中间那句前置断言不能省**：没有它，如果 `pause()` 没生效，
测试照样绿 —— 而它证明的是「L1 正常工作」，不是「L3 能兜底」。
（这是记忆里那条「判据本身测的不是要测的那件事」的形状，一晚撞过好几次。）

同理，**每条不变式的扫描测试都要断言扫描行数 > 0**。

## L4 · 六、工作量与风险

**批 A/B 是大头**，也是全部风险所在 —— 因为它动的是钱的路径。
批 C 是纯搬家（域边界已经干净）；批 D 每步可回滚，直到 D6。

| 批 | 性质 | 风险 | 停在这里有没有价值 |
|---|---|---|---|
| A | 补欠账 | 低 | **有** —— 今天的系统直接变健壮 |
| B | 解事务耦合 | **高**（动钱） | **有** —— 单体也该这么写 |
| C | 结构搬家 | 低 | 有（依赖收敛） |
| D1–D5 | 切流量 | 中 | 有（形态 B 验证过了） |
| D6 | 切库 | **不可回退** | 终点 |

**三条要盯住的风险：**

1. **批 B 的窗口期**：改到一半时，一部分路径已经异步、一部分还同步。
   缓解：**每处单独上线、单独观察**，不要一批改完一起发。
2. **不变式自动修复的边界**：I1 可以自动补（生成结算单是幂等的），
   I2 **绝不能自动删**（删账不可逆）。凡是「自动修复」的，都要能证明它幂等且可逆。
3. **积分预扣的超时时长**：太短会误释放正在建的单，太长会占着用户的分。
   建议 15 分钟起步，并在告警里看实际建单耗时的 P99。

## L4 · 七、待确认

1. **批 A 是否现在就开始** —— 它不依赖任何拆分决定，且做完系统直接变好。
2. **批 B 的顺序**：建议 B1 → B2（结算单，风险最高但兜底最完整）→ B4（积分预扣）→ B3 → B5。
   先做最难的那个，因为它决定其余四个的形状。
3. **I2 的告警去哪** —— 「有结算单但没有已支付子单」是最像事故的一条，
   要不要直接进运营端待办？
4. **投递延迟的可接受上限** —— 本文按「秒级正常、超过 1 小时告警」写。
