# TDD-手机号授权与自动登录

状态：**待确认**（2026-08-22）
关联：[注册登录-方案梳理](../reference/注册登录-方案梳理.md) ｜ [TDD-小程序登录打通](./TDD-小程序登录打通.md)

## 1. 要做成什么

```
首次进入小程序
  └─ wx.login 静默 → 建号 → 发 token        ← 用户此刻已经是登录态，但没有手机号
       └─ 到了「必须有手机号」的那一步
            ├─ 微信一键授权可用 → 弹授权 → 一次点击拿到手机号
            └─ 不可用           → 手机号 + 验证码
                 └─ 绑定到同一个账号
                      └─ 下次进入：静默登录命中 openid → 自动登录，不再问
```

**「自动登录」这一半已经在跑**：`WX_MINI` 静默登录 + 30 天会话，命中 openid 直接发 token。
本方案要补的是**手机号这一环**。

## 2. 现状盘点（查过代码，不是设想）

| 环节 | 现状 |
|---|---|
| 静默登录建号 | ✅ `AuthServiceImpl` `GRANT_WX_MINI` |
| 多凭证挂同一账号 | ✅ `usr_identity`，且**冲突不自动合并**（抛 `CONFLICT`，见 `registerNewCredentials`） |
| 绑手机号（验证码） | ⚠️ **后端有 `POST /mp/user/phone/bind`，端上一次都没调过** |
| 微信一键获取手机号 | ❌ 完全没有 |
| 「什么时候该问手机号」 | ❌ 没有任何触发点 |

第三行是这个项目反复出现的那个形状：**后端做了、端上没接**，
而它不报错——只是那个功能对用户不存在。

## 3. 两处必须先说清的

### 3.1 微信一键授权不是免费的，也不是现在就能用的

`button open-type="getPhoneNumber"` 要三个前提：

| 前提 | 现状 |
|---|---|
| 小程序**已认证** | ❌ 未认证（300 元/年） |
| 非个人主体 | 待确认主体类型 |
| **按次计费** | 有免费额度，超出后每次调用收费 |

所以**不能把它作为唯一入口**。设计成：**能力可用就一键，不可用就回落验证码**，
两条路同一个出口（都落到 `usr_identity` 的 PHONE 凭证）。
认证下来之后改一个开关即可，端上不用重发版。

> 与登录 / 订阅消息 / 小程序码三条通道同一套做法：各自一个 `stub` 开关，
> 因为它们的接入前置各不相同（这个坑 2026-08-17 踩过一次）。

### 3.2 手机号已经属于另一个账号时怎么办

这不是边角情况：**用户先在 H5 用手机号注册过，再从小程序进来**，就撞上了。

现有代码的答案是 **抛 `CONFLICT`，不自动合并**——理由写在 `registerNewCredentials` 注释里：
合并要迁移订单、积分、卡包、优惠券、地址，横跨五个域，合错了难回滚。

**本方案沿用这个决定**，但要把它翻译成用户看得懂的话：

| 场景 | 提示 |
|---|---|
| 手机号未被占用 | 绑定成功 |
| 手机号已属于**当前这个人**（重复点） | 视为成功，不报错 |
| 手机号属于**另一个账号** | 「这个手机号已经注册过。用它登录可以继续，但**当前微信里的浏览记录与购物车不会带过去**」+ 提供「改用它登录」按钮 |

第三行的措辞是关键：**不要说「手机号已被占用」**——用户会以为是别人抢了他的号，
而实际上多半是他自己以前注册过。

## 4. 设计

### 4.1 后端

```
POST /mp/user/phone/bind      手机号 + 验证码（已有，端上要接上）
POST /mp/user/phone/wx        微信 code → 手机号 → 绑定      ← 新增
GET  /mp/user/phone/capable   一键授权当前可不可用            ← 新增
```

- `WxPhonePort`（`spi/user`）+ `WxPhoneGateway`（真）/`StubWxPhoneGateway`（桩），
  开关 `shop.wx.phone.stub`，默认跟随 `shop.wx.stub`。
- 真实现调 `phonenumber.getPhoneNumber`，用与小程序码同一份 `stable_token`。
- **桩返回 null 而不是假号码**：假号码会被当成真手机号写进账号，
  而那比"没拿到"贵得多（与小程序码那条同一个理由）。

### 4.2 端上

一个可复用的「要手机号」弹层 `sh-phone-gate`：

- 能力可用 → `<button open-type="getPhoneNumber">` 一键
- 不可用   → 手机号 + 验证码
- **两种形态同一个出口**：拿到手机号后调对应接口，成功即关闭并继续原来的动作

### 4.3 什么时候弹

**只在真正需要的那一刻弹，不在启动时弹。**

| 时机 | 弹不弹 | 为什么 |
|---|---|---|
| 首次进入小程序 | ❌ | 还没产生任何关系就要手机号，是最典型的劝退 |
| 浏览、加购物车 | ❌ | 不需要 |
| **提交订单** | ✅ | 履约要联系买家：自提要发到货通知、配送要打电话 |
| 领券 / 参团 | ✅ | 这些是「记在谁名下」的动作 |
| 「我的」页主动绑定 | ✅（入口，不是弹层） | 让想提前绑的人能绑 |

## 5. 测试策略

- 后端：`WxPhoneBindFlowTest`
  - 验证码绑定 → `usr_identity` 多一行 PHONE，`profile` 能读到
  - 重复绑同一个号 → 幂等成功，不报错
  - 绑一个属于别人的号 → `CONFLICT`，且**原账号不被改动**
  - 桩通道 → `capable=false`，`/phone/wx` 明确拒绝而不是返回假号
- 端上：`phone-gate` 组件测试（c-app 已有 vitest）
  - 能力可用 → 渲染一键按钮；不可用 → 渲染验证码表单
  - 绑定成功 → 关闭并回调原动作
  - 冲突 → 显示「已注册过」文案与「改用它登录」，**不显示「已被占用」**

## 6. 不做什么

- **不做账号合并**。沿用现有决定，只做检测 + 说清楚。
- **不在启动时要手机号**。
- **不把一键授权作为唯一入口**——认证没下来之前它根本不可用。
