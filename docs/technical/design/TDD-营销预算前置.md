# TDD-营销预算前置（把预算从运行时的闸改成建券时的规划）

> 状态：**待确认** · 创建 2026-08-11
> 关联需求：[平台端功能清单](../requirements/平台端功能清单.md) `P-7.1` 券模板 / 发放记录
> 关联代码：`MktCoupon` · `CouponMappers.tryReceive` · `MktCoupon.discountFor`

---

## 1. 先回答那个问题：为什么会「找预算」

原本挂在待决清单上的问法是：**「折扣券超预算时，券不可用，还是照常用但超支？」**

这个问法本身就是错的 —— 它默认了「运行到一半才发现要超支」是一种正常状态。
而正常状态应该是：**这张券最多花多少钱，在建券按下保存的那一刻就是确定的**。

拆开看两类券：

| 券型 | 单张最大优惠 | 建券时敞口可算？ |
|---|---|---|
| `FULL_CUT` 满减 | `faceMinor`（固定） | ✅ `totalCount × faceMinor` |
| `DISCOUNT` 折扣 | `min(订单额 × (1 − rate), maxDiscountMinor)` | ⚠️ **仅当 `maxDiscountMinor > 0`** |

满减券从来就是可算的。折扣券之所以算不出来，只有一个原因：
**现在允许 `maxDiscountMinor = 0`（不封顶）**。一张八五折不封顶的券，
遇到一笔一万块的订单就减掉一千五 —— 敞口是无限的，
于是只能在核销那一刻去追「还剩多少预算」。

> **是「不封顶」这个取值制造了运行时问题，不是折扣券本身。**
> 堵在源头之后，运行时那条路根本不需要存在。

这也解释了为什么 `budgetMinor` 现在的位置很别扭：它被塞在
`tryReceive` 的 SQL 里（领券时按 `(received_count + 1) × face_minor` 估），
而折扣券的 `face_minor` 是 0 —— **对折扣券，那个条件恒真，等于没有预算**。
今天的预算闸只对满减券生效，而满减券恰恰是唯一不需要它的那一类。

## 2. 方案

### 2.1 选型

| 方案 | 做法 | 结论 |
|---|---|---|
| **A（推荐）建券时保证敞口可算** | `DISCOUNT` 券**强制填封顶**；`budgetMinor` 改为建券时校验 `budget ≥ 最大敞口` | ✅ 采用 |
| B 核销侧扣预算 | 每次核销累加已花金额，超了拒绝使用 | ❌ 用户已领到手的券在结算页突然不能用，是最坏的一种失败；且要在下单算价链路加一次强一致写 |
| C 核销侧扣预算但不拒绝 | 只记录、超支照付 | ❌ 「预算」不拦任何东西时，它就不是预算，是一个事后报表字段 |

**为什么不是 B**：券的价值在于「用户拿到了就该能用」。为了平台的预算表
去作废一张已发出的权益，会引发比多花几百块严重得多的纠纷 ——
这与 `MktCoupon.PAUSED` 的既有决策一致（暂停只挡新领取，不动已领到手的）。

### 2.2 数据与规则

不加新表、不加新列。改的是**约束**：

```
最大敞口 maxExposure =
    FULL_CUT  → totalCount × faceMinor
    DISCOUNT  → totalCount × maxDiscountMinor
```

建券 / 改券时强制：

1. `type = DISCOUNT` 时 **`maxDiscountMinor > 0` 必填**
   —— 取消「0 = 不封顶」这个取值
2. `totalCount > 0` 必填 —— 不限量券的敞口同样不可算
3. `budgetMinor` 若填了，必须 `≥ maxExposure`；否则直接报错，
   **不接受一个从第一天起就不可能满足的预算**

`budgetMinor` 因此从「运行时的闸」变成**建券时的一次断言**。
运行时不再读它。

### 2.3 那 `budgetMinor` 还留着干什么

留，但换语义：**它是这张券的资金申报额，用于审批与对账**，不是拦截器。

- 建券时校验 `budget ≥ maxExposure`（上面第 3 条）
- 超过阈值的券需要更高权限才能建（见 §2.4）
- 结算侧按它做平台营销费用的预提

把「拦截」和「申报」分成两件事，是因为它们的失败方式完全不同：
拦截失败 = 用户用不了券（对外），申报失败 = 账对不上（对内）。

### 2.4 高额券的审批闸（可选，建议同批做）

`maxExposure` 超过阈值时，建券需要 `marketing:govern` 之外的更高权限。
阈值走平台参数 `marketing.coupon-approval-threshold-minor`，
**不硬编码**（P4）。

理由：客服岗也持有发补偿券的能力（矩阵 §2.3）。
一个岗位能建的券的最大敞口，应该与这个岗位的职责相称。

### 2.5 存量数据

上线前需要一次性检查：库里是否存在
`type = DISCOUNT AND (max_discount_minor IS NULL OR max_discount_minor = 0)`
或 `total_count = 0` 的券。

**目前库里一张折扣券都没有**（这也是 `discountFor` 那次万分比/百分数
口径统一敢直接改的原因），所以这次同样是「趁没有数据的时候把口径定死」。
迁移脚本只需在有数据时报警，不需要写数据修复。

## 3. 影响范围

| 位置 | 改动 |
|---|---|
| `MktCoupon` | `maxDiscountMinor` 的 javadoc：删掉「0 = 不封顶」 |
| 建券 / 改券 Service | 新增三条校验；新增错误码 |
| `CouponMappers.tryReceive` | **删掉** `budget_minor` 那个条件 —— 它现在只对满减券生效，而满减券已被建券时的约束覆盖 |
| ops-web 券模板表单 | 折扣券的封顶字段改为必填；预算填写时前端先算一遍敞口给提示 |
| `packages/shared` | 券型 × 必填字段的对照进枚举登记表 |

**这会修改已测试通过的功能**（`tryReceive` 的预算条件，
以及 `M6bCouponFlowTest` 里那条预算用例）。按 P6，需要你确认后再动。

## 4. 测试策略

| 场景 | 期望 |
|---|---|
| 建折扣券不填封顶 | 拒绝，错误码指明「折扣券必须设封顶」 |
| 建券 `totalCount = 0` | 拒绝 |
| `budget < totalCount × face` | 拒绝，报文里给出算出来的敞口 |
| `budget = maxExposure` 边界 | 通过 |
| 领券到发行量上限 | 仍然拒绝（`totalCount` 那条闸不动） |
| 折扣券核销 | **不再有预算检查**，能用到发行量用完为止 |
| 存量扫描 | 有不合规券时报警，无则静默 |

现有 `M6bCouponFlowTest` 里那条「预算用尽后领券被拒」要改写成
「建券时预算不足被拒」—— 它测的东西从运行时挪到了建券时。

## 5. 风险

- **唯一的行为变化**：折扣券不再有「不封顶」这个选项。
  如果产品上真的需要不封顶的折扣券（例如新人首单五折不限额），
  那这份方案不成立 —— 需要先明确这个场景是否存在。**这是唯一要你确认的点。**
- `tryReceive` 删条件属于放宽，不会让原本能领的领不到。
