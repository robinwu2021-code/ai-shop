# 组织抽象 · 技术方案、缺口处理与「品牌 → 连锁」改名策略

> 状态：方案稿 v2（2026-10-30），待评审。
> v2 按业务模型（分层、六种关系、不变量 I1–I10）对照后做了 5 处修订，标为「v2」：
> 1. G3 去掉 ACTIVITY；
> 2. G4 纳入平台券；
> 3. G4 的成本承担落到定价资金来源；
> 4. G4 的清分和结算单与工具无关；
> 5. G1 统一两套授权。
> 业务抽象见 [组织关系-ai-shop与独立进销存-业务抽象.md](组织关系-ai-shop与独立进销存-业务抽象.md)，G1–G5 编号沿用该文 §3。
> 本文定的是方向和顺序。每个缺口动手前按 `ai-shop-dev-standards` 另写 TDD（计划写在 TDD §2）。

## 0. 结论先行

1. **技术层不叫「品牌」，也不叫「连锁」**。用五个通用概念：
   - **组**（Group）
   - **范围**（Scope）
   - **发行方**（Issuer）
   - **结算指定**（Settlement designation）
   - **清分事实**（Clearing fact）

   「连锁」只是组的一种 `kind`。以后加区域、加盟片区、商圈，也都是组，不需要新模型。
2. **API、库表和权限码现在不改名**：
   - 库表和发行版本里冻结的 `BRAND` 是金融事实，不能重写；
   - 40 个端点、12 个权限码，加上已经授出的授权行，都属于契约。

   做法是**在边界放一个编解码器**：领域代码只认 `GROUP`，存储和接口上的 `BRAND` 当成一个不透明的历史编码。这样**领域层与命名解耦，改名不再影响契约**。
3. **Java 领域层改**：
   - 136 处字符串 `"BRAND"` 收敛到 `ScopeRef` / `ScopeType`；
   - `merchant.brand` 包内的模型改叫 Group，跟业务方案一起逐步做，不单独做一次大改名。
4. **缺口顺序**：
   1. **G3** 结算指定：小，是 G4 的前提；
   2. **G4** 组券：价值最大；
   3. **G2** 按渠道收款路由：待产品确认；
   4. **G1** 账户与任职拆分：中期。

   G5 文案已经改完，提交 `9b1633430`。

## 1. 通用技术抽象

### 1.1 五个概念

| 概念 | 回答什么 | 关键字段 | 现有雏形 |
|---|---|---|---|
| **组 Group** | 哪些门店在运营上算一伙 | `group_no`, `kind`, `space_no`, `scope_revision`；成员 = 门店，带生效窗 | `mch_brand` + `mch_brand_store_binding`（只有一种 kind） |
| **范围 Scope** | 一项能力在哪生效 | `ScopeRef(type, no)`，type ∈ STORE / ENTITY / GROUP / PLATFORM | `MemberOperatingScopePort.Scope(scopeType, scopeNo, revision)`；`sv_issuer.scope_type`；`mbr_scope_member.scope_type` |
| **发行方 Issuer** | 预付性权益的负债归谁 | `issuer_no`, `scope`, 版本（结算主体、收款配置、清分规则） | `sv_issuer` / `sv_issuer_version`（只服务储值） |
| **结算指定 SettlementDesignation** | 某个运营对象统一结算落到哪个主体 | 主体对象 `subject_ref` → `entity_no`，带版本和主体确认 | 分散在 `sv_issuer_version.settlement_entity_no`、`pmt_brand_activity_owner.entity_no` |
| **清分事实 ClearingFact** | 在 A 主体的店兑付了 B 主体承担的权益，谁欠谁 | 发行方 / 版本、工具类型、核销门店、经营主体、承担主体、金额分量 | 储值的跨主体应付（储值 TDD §4.5） |

它们与资金线的关系：
- 组、范围属于**运营线**；
- 发行方、结算指定、清分是两条线之间**唯一的桥**。

**运营线只通过「结算指定」和「清分事实」碰钱**，其他任何地方都不允许从组直接推出主体。

### 1.2 范围解析：唯一入口

```java
// shop-base spi，取代散落的 "BRAND".equals(scopeType)
public record ScopeRef(ScopeType type, String no) { }
public enum ScopeType { STORE, ENTITY, GROUP, PLATFORM }

public interface ScopeResolver {
    /** 此刻（或给定时刻）在范围内的门店；带范围修订号，供调用方冻结 */
    Resolved stores(String tenant, ScopeRef scope, Instant at);
    /** 这家店此刻落在哪些范围里：自己、所属主体、所属的各类组 */
    List<ScopeRef> scopesOf(String tenant, String storeNo, Instant at);
    /** 在调用方事务里锁住门店的范围事实（变更单并发用） */
    Resolved lock(String tenant, ScopeRef scope);
    record Resolved(ScopeRef scope, long revision, List<String> storeNos) { }
}
```

- **GROUP 动态解析**：按成员关系和生效窗计算，**不存门店名单**。发行版本里已有的 `BRAND_DYNAMIC + scope_snapshot` 正是这个语义，保持不变。
- **能力代码只问三件事**：
  - 店在不在范围内；
  - 范围的发行方是谁；
  - 发行方当前的结算主体是谁。

  不再写 `if (BRAND) … else …`。

### 1.3 组：一张表，一个 kind

| 字段 | 说明 |
|---|---|
| `kind` | `CHAIN`（现有），将来可以加 `REGION`、`FRANCHISE_AREA`、`MALL` |
| 排他规则 | **按 kind 排他**：一家店在同一 kind 下至多一个有效组（连锁），不同 kind 可以并存，比如一家店既属于某连锁又属于某商圈 |
| 能力开关 | 按 kind 配置哪些能力可以挂在组上：CHAIN 可以发行、共享会员、统一核销；REGION 只能做报表和管理授权 |

**现在不建新表**：
- 只有 CHAIN 一种 kind，`mch_brand` 就是 kind=CHAIN 的组表。领域层用 `GroupRepository` 包住它，`kind` 恒为 CHAIN。
- **出现第二种 kind 时**再做一次契约变更：`mch_brand` 改名为 `org_group` 并加 `kind`，绑定表同理，`BRAND` 编码继续指向 kind=CHAIN 的组。

### 1.4 与独立进销存对齐

进销存方案里的 `inv_scope` / `inv_scope_member` 就是这里的组和范围，同一个概念：
- ai-shop 的组成员（门店）同步过去，成为库位成员；
- `scope_type` 用同一套取值（GROUP / PLATFORM / REGION …）；
- 同步按 `scope_revision` 幂等。

## 2. 改名策略：哪些层改、哪些层不改

### 2.1 现状体量

| 层 | 含 brand 的量 | 性质 |
|---|---|---|
| 库表 | `mch_brand*` 5 张、`pmt_brand_activity_owner`；`scope_type='BRAND'` 出现在 `sv_issuer`、`mbr_scope_member`、`pmt_sv_release_link`、授权的 `resource_type`；发行版本 `redemption_scope_mode=BRAND_DYNAMIC`、`scope_snapshot` | **含金融事实和冻结快照** |
| 端点 | 40 条路径含 `brand`（`/biz/management/brands/**`、`/brand-changes`、`/financial-brand-changes`） | B 端契约，b-app 唯一消费方 |
| 权限码 | `brand.*`、`store.brand.change`、`sv.brand.*` 共 12 个 | 已写入授权行和角色 |
| Java | main 119 个文件（pay-domain 34、shop-merchant 27、shop-app 30、core 13、base 13），test 53 个；`"BRAND"` 字面量 136 处 | 内部实现 |
| 前端 | b-app / c-app 共 47 个文件，基本是字段名 `brandNo` 和路由名 | 跟着端点走 |

### 2.2 决定

| 层 | 改不改 | 怎么做 | 理由 |
|---|---|---|---|
| 文案 | ✅ 已改 | 连锁 | 业务语言 |
| **领域模型（Java）** | ✅ 改成通用 | 新增 `ScopeRef` / `ScopeType` / `ScopeResolver` / `GroupRepository`；`"BRAND"` 字面量收敛到一个 `ScopeCodes` 编解码器；`merchant.brand` 的服务逐步改为 Group 语义（**做 G3、G4 时顺手**，不单独做一次全量改名） | 解耦命名和契约，以后不再因为命名动契约 |
| 存储编码 | ❌ 不改 | `'BRAND'` 作为 GROUP(kind=CHAIN) 的**历史编码**，读写都经过 `ScopeCodes` | 发行版本、余额批次、结算单都冻结了它；重写金融事实不可接受 |
| 库表名 | ❌ 现在不改 | 出现第二种组 kind 时，`mch_brand*` → `org_group*` 合并做 | 现在改名只换名字，没有能力收益 |
| 端点路径 / JSON 字段 | ❌ 不改 | 已有端点保持 `/brands`、`brandNo`；**新增的通用能力用通用形状**（见 §3），以 `scope: {type, no}` 表达范围，`type` 在接口上同样走 `ScopeCodes` | 唯一消费方是自家 b-app，改名收益只是好看，却要四层同改加回归 |
| 权限码 | ❌ 不改 | 在术语表登记 `brand.*` = 组 / 连锁管理；新能力的权限码按能力命名（如 `coupon.group.issue`），不带 brand | 授权行和委托链都存了码，改码要做授权迁移 |
| 术语表 | ✅ 登记 | `brand`（代码 / 存储 / 接口）= 连锁 = GROUP(kind=CHAIN)；`SD_BRAND` = 商品品牌，两者无关 | 让新同事不再困惑 |

**一句话：名字只在两处改，一处是给人看的文案，一处是写逻辑的领域层；所有落盘或已对外的编码都冻结。**

### 2.3 `ScopeCodes`：唯一的翻译点

```java
/** 存储 / 接口编码 ↔ 领域范围类型。'BRAND' 是 GROUP(kind=CHAIN) 的历史编码，不得在别处出现 */
final class ScopeCodes {
    static ScopeType decode(String code) { return "BRAND".equals(code) ? ScopeType.GROUP : ScopeType.valueOf(code); }
    static String encode(ScopeType t)   { return t == ScopeType.GROUP ? "BRAND" : t.name(); }
}
```

再配一道 ArchUnit 规则：`"BRAND"` 字面量只允许出现在 `ScopeCodes`、Flyway 脚本和测试夹具里。136 处随 G3、G4 逐模块收敛，规则先以**存量基线**形式上线，**只拦新增**。

## 3. 缺口方案

### G3 · 结算指定（先做，小）

**问题**：「连锁统一结算到哪个主体」没有单一真相源。储值发行版本和连锁活动各自记一个 `entity_no`，可以不一致，也没有校验。

**方案**：

```
org_settlement_designation
  designation_no, tenant_no,
  subject_type  GROUP | ISSUER                 -- 谁的统一结算（v2：活动不是指定对象，见 I6）
  subject_no,
  entity_no                                    -- 结算主体
  version_index, status DRAFT/ACTIVE/SUPERSEDED,
  acceptance JSON                              -- 主体方确认依据（复用 entity_acceptance 的格式）
  effective_at
  UNIQUE (tenant_no, subject_type, subject_no, version_index)
```

- **组级默认**：`subject_type=GROUP`，一个连锁一条有效版本。指定或更换都要主体方确认，即被指定主体的 ENTITY 级授权人确认。
- **下游冻结**：发行方新版本**默认取组级当前版本并复制冻结**到 `sv_issuer_version.settlement_entity_no`。
- **活动只继承（v2）**：连锁活动不再选择结算主体。`pmt_brand_activity_owner.entity_no` 改为在创建时从发行方当前版本推出，只读。活动的归属从「连锁 + 主体」改为「发行方 + 工具」（`issuer_no`），`pmt_sv_release_link.entity_no` 同理。
- **显式例外**：只允许**发行方**指定与组默认不同的主体，必须带 `override_reason` 并经确认。运营端列出「与组默认不一致」的发行方。
- **更换组默认**：不追溯已冻结的版本，只影响新版本和新活动。变更单提示「N 个发行方和活动仍指向旧主体」，可以一键出新版本。
- **迁移**：按现有连锁发行方的当前版本回填组级默认。已有活动的 `entity_no` 与发行方版本不一致的，列出来人工处理，不自动改；新活动一律继承。
- **停用守卫**：一个主体还是任何有效结算指定的对象时，不能停用，对应业务方案 §1.4。

契约变化：1 张新表；端点 `GET/POST /biz/management/brands/{b}/settlement-designations`（挂在现有资源下，形状通用）；权限 `settlement.designate`、`settlement.accept`。

### G4 · 组券（价值最大）

**问题**：券只能在一个主体内（`pmt_coupon.entity_no`）发和用。加盟连锁跨主体，发不了一张通用的券，也没有负债方和清分。

**方案：券接入发行方模型，范围用 `ScopeRef`。**

| 改动 | 内容 |
|---|---|
| 券的归属 | `pmt_coupon` 新增 `scope_type/scope_no`（GROUP / ENTITY / STORE / PLATFORM）和 `issuer_no`（可空：主体券和门店券沿用老逻辑，视为「发行方 = 主体自身」）。`entity_no` 保留，含义收窄为「主体券的主体」 |
| 发行方泛化 | `sv_issuer` 增加 `instruments`（`STORED_VALUE`, `COUPON`），一个组仍然只有一个发行方。若不想动储值表，就新建 `fin_issuer` 并把 `sv_issuer` 迁移进来，二选一，TDD 里定（倾向前者） |
| 成本承担 | 券版本冻结 `cost_bearing`：`ISSUER`（发行方全担）、`REDEEMING_ENTITY`（核销主体自担，相当于统一发、各自担）、`SPLIT(ratio)` |
| 适用校验 | 下单和核销时 `ScopeResolver.stores(scope, now)` 判断当前门店是否在范围内。`pmt_coupon_scope` 中的 STORE / CATEGORY / GOODS 规则继续作为**范围内的进一步限定** |
| 核销事实 | 记录核销门店、经营主体、发行方版本和承担方式 |
| 清分 | 承担主体 ≠ 核销主体时，生成 `ClearingFact(instrument=COUPON)`，**复用储值的跨主体应付和账单**；同主体只做内部对账 |
| 门店退出组 | 已领未用的组券：门店退出后不能再在该店核销，在组内其他门店照常可用。变更单影响检查新增「在途组券预占」 |
| 补贴与支付 | 券优惠在订单上仍是商家优惠，资金不走发行方，只产生清分应付，不改支付分账 |
| 平台券（v2） | 平台券（现在 `entity_no` 为空）= **平台范围的发行方**，结算主体为平台运营主体。平台承担部分走渠道补差（`sys_pay_channel.supports_subsidy`），不进商家间清分。这样券只有一套归属规则 |
| 资金来源（v2） | 成本承担在报价时落到 `ord_pricing_funding_source`：按承担方拆成多条（发行方承担 / 核销主体承担 / 平台补差），各带承担主体。清分从这里取数，券模块不另算 |
| 结算单（v2） | 清分事实加 `instrument`；`sv_clearing_entry` / `sv_settlement_bill*` 泛化为与工具无关的「发行方清分」和「发行方账单」，按发行方 / 期间 / 付款方 / 收款方 / 币种汇总，明细带工具维度。TDD 里定是改名迁移还是新表加视图 |

契约变化：`pmt_coupon` 加列、`sv_issuer` 加列（或新表）、清分事实加 `instrument` 维度；新端点放在 `/biz/management/brands/{b}/coupons`；权限 `coupon.group.manage/issue/report`。依赖 G3（承担主体默认取结算指定）。

### G2 · 门店按渠道收款路由（待产品确认）

**问题**：`mch_store.pay_merchant_no` 只有一列，而商户号按渠道区分。一家店多个渠道时，其余渠道只能退回主体默认。

**方案（确认需要后再做）**：

```
mch_store_payment_route (tenant_no, store_no, pay_channel, pay_merchant_no, changed_at)
  UNIQUE (tenant_no, store_no, pay_channel)
```

- 解析顺序：门店 × 渠道路由 → 主体在该渠道的商户号（`uk_mp_entity_channel`）。
- 统一入口 `PaymentRouteResolver.resolve(store, channel)`，现有读 `mch_store.pay_merchant_no` 的地方改调它。旧列回填为路由表中对应渠道的一行，之后只读、不再写。
- 约束不变：只能选本主体的商户号；`R12` 中发行方「门店本地收款」也走这个解析器。

需要确认的问题：同一主体是否真的存在「门店 A 用微信号 1、门店 B 用微信号 2」？若不存在（一个主体一个渠道一个号，`uk_mp_entity_channel` 已保证），G2 只是理论缺口，**可以不做**。

### G1 · 账户与任职拆分（中期）

**问题**：没有「账户」实体。`mch_account` 是主体下的员工行；跨主体靠 `login_phone` / `user_no` 拼起来；连锁授权又用 `actor_no` 另起一套。

**方案**：

```
iam_account      (account_no, login_phone, user_no, status)        -- 一个人一个
mch_account      + account_no                                       -- 含义改为「任职」：账户 × 主体
mch_management_grant.actor_no  = account_no                          -- 统一身份
```

- **统一两套授权（v2）**：主体内的 `is_owner` + `mch_store_role`，与空间内的 `mch_management_grant`，合并为同一个「账户 × 资源 × 能力」模型。资源包括 ENTITY / STORE / PAYMENT_MERCHANT / SPACE / GROUP / ISSUER。店主 = ENTITY 级的全部能力，与连锁授权走同一个判权入口。
- 登录令牌的主体从「某主体的员工」改为「账户」。进入 B 端时，先选**工作上下文**：主体任职，或有授权的连锁空间。
- 迁移：按 `login_phone` 聚合现有 `mch_account` 生成 `iam_account` 并回填 `account_no`；冲突的（同号不同人）进人工队列。
- 风险最大的是登录和令牌，对现有会话不兼容，需要灰度。放在 G3 和 G4 之后单独立项。
