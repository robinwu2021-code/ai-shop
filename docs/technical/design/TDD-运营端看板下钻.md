## 一、一句话

大盘三个数（KPI / 趋势 / 漏斗）回答「平台整体怎么样」，**运营的下一句必然是
「哪几家在拉高、哪几家在拖后腿」**——没有这一层，那个问题只能靠翻订单列表人工数。
本次补的就是大盘之下的第一层下钻：商家经营排行。

## 二、为什么是这个方案

### 2.1 排行的数据来源：复用还是新建

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 在 `TradeStatsPort` 上加一个按商家聚合的方法**（采用） | 与大盘、与 B 端商家自己看的 `stats` 是**同一份订单数据**的不同切法，口径天然一致 | 全量扫子订单表，量大时要加索引/物化 | ✅ |
| B. 新建排行榜表，定时任务算好 | 查询快 | 「榜上说 12 单、点进去只有 9 单」——B-6.0 已经吃过一次「另存计数器」的亏，平台端功能清单里那句「都从同一份订单数据算」就是这么来的 | ❌ |
| C. 前端拉订单列表自己聚合 | 后端零改动 | 分页数据聚不出全量；且把口径散到端上，三端各算各的 | ❌ |

**防住什么**：方案 B 的失败方式是**看板与详情对不上**，而两边都不报错——
运营会以为是自己看错了，直到某次对账才发现。

### 2.2 售后率为什么必须与 GMV 并列

只按 GMV 排，「卖得多但赔得也多」的商家永远混在中间不显眼，
**而他恰恰是平台最该处置的那一家**。所以排行行里带 `afterSaleRate`，
前端对 ≥10% 的标红（低于它的都在个位数，超过的只有异常商家）。

**防住什么**：一张只有 GMV 的排行榜会把运营的注意力全导向头部，
而头部商家通常是最不需要干预的。

### 2.3 排行的商家集合必须含「已退款」的单（实测推翻了第一版）

第一版只扫成交态（`WAIT_FULFILL/FULFILLING/COMPLETED`）取商家集合。
测试当场证伪：一笔 **¥30 的单低于极速退阈值（¥50）**，申请售后即自动退款、
子单转 `REFUNDED` 离开成交态，**于是那家商家从排行里整个消失**——
而「单子全退光」恰恰是这张表最该显示的一家。

现在的口径：

| 量 | 取哪些单 | 为什么 |
|---|---|---|
| `gmv` | 只算成交态（实收） | 与 `paidTotals`/KPI 同口径——看板上下两层不能有两个 GMV 定义 |
| `orderCount` | 只算成交态 | 同上 |
| `refundedCount` | 已退款 | **单列**：它让全退的商家仍留在榜上 |
| `afterSaleRate` 的分母 | 成交 + 已退 = 总成交单数 | 只用成交态的话，全退商家分母为 0、率显示 0% |

**防住什么**：一张会把「全额退款商家」自动隐藏的风控表，比没有这张表更危险。

### 2.4 售后数不按成交窗口截断

一单可能这个月成交、下个月才售后。若把售后也按 `from` 过滤，
「卖得多赔得也多」的商家在短窗口下会显得很干净——**恰好抹掉了这一列的意义**。
所以 GMV/单量按窗口算，售后数取全量。

> 这一条与 §2.3 是同一个失败模式的两种形态：**都会让「该被看见的商家」消失**。

> 代价：售后率的分子分母不同窗口，严格说不是一个比率。
> 取舍见 §五 T1。

## 三、结构

```
OpsDashboardController.merchantRanking(days, limit)   ← GET /ops/dashboard/merchants
        ↓
DashboardService.merchantRanking(days, limit)          ← 夹取 days 1–90 / limit 1–100，拼商家名
        ↓ (spi)                    ↓ (spi)
TradeStatsPort.merchantTotals(from)   MerchantQueryPort.findAll(nos)
        ↓                              ↓
   ord_sub_order + ord_after_sale    mch_entity（只取名字）
```

| 层 | 职责 | 为什么在这一层 |
|---|---|---|
| Controller | 默认值（14 天 / 前 10） | 只有它知道「看板首屏要展示多少」 |
| Service | 夹取范围、拼商家名、算客单价与售后率 | 跨 Port 的组装点 |
| `TradeStatsPort` | 按商家聚合 GMV/单量/售后数 | platform 不能直连 trade 的 mapper（ArchUnit 第 1 条） |

## 四、详细设计

### 4.1 接口

`GET /ops/dashboard/merchants?days=&limit=` → `MerchantRankRowVO[]`

| 字段 | 说明 |
|---|---|
| `merchantNo` / `merchantName` | **名字必须下发**：只给编号的话运营还要再查一次「这家是谁」 |
| `gmv` / `orderCount` | 窗口内已支付子订单聚合 |
| `avgOrderValue` | 无单时 0，**不是除零**（与 `kpi()` 同一口径） |
| `afterSaleCount` / `afterSaleRate` | 售后单数（全量）；率 = 售后数 ÷ 窗口内单量，无单时 0 |

权限沿用 `dashboard:overview:read`——排行是同一份订单聚合的另一种切法，
能看大盘的人本来就该能看它。**不新造码**（`perm-endpoint-map.mjs` 里
`GET /ops/dashboard/` 那条兜底规则已覆盖，无需加规则）。

### 4.2 排序与截断

按 GMV 降序，**只含有成交的商家**：零单商家排在末尾没有信息量，
全带上还会稀释「平台有多少家在做生意」这个数。

### 4.3 N+1 的两处规避

- 售后数：一次 `in (merchantNos)` 查回来按商家分组，不在循环里逐个查
- 商家名：`MerchantQueryPort.findAll(Set)` 批量取

**防住什么**：这个接口是看板首屏的一部分，两处 N+1 会让首屏可感知地变慢。

## 五、取舍记录

| # | 取舍 | 说明 |
|---|---|---|
| **T1** | 售后率的分子（全量）与分母（窗口内）不同窗口 | 严格说不是一个比率。但按窗口截售后会抹掉这一列存在的意义（§2.3），而运营用它是为了「挑出该处置的商家」而不是做精算。**在字段注释里写明**，不在 UI 上装作它是精确比率 |

## 附：成交口径合一（2026-08-14）

本轮做排行时留下的观察 ——「商家后台的 GMV 比平台排行大」—— 查清了：
**两处各写了一套成交口径，而没有任何地方声明过它们是两套。**

| 位置 | 原来的写法 | 含 CANCELLED？ |
|---|---|---|
| 商家看板 / 跨店对比 / 顾客画像（4 处） | `status != WAIT_PAY` | **是** |
| 平台看板 / 商家排行 | 显式集合 | 否 |

差额恰好是那些**被取消的单**。两边各自都说得通、都不报错，
而商家拿这个数去对账时，第一反应是平台少算了他的钱。

**关键事实**：状态机里 `WAIT_FULFILL` **到不了** `CANCELLED`（付过款的单只能走退款）——
也就是说被误算进商家 GMV 的那些取消单，**从头到尾一分钱都没进来过**。

**修法**：口径唯一定义处放在状态的主人 `OrdSubOrder` 上，五处全部引用它：

- `OrdSubOrder.PAID` = 成交态（不含退款）
- `OrdSubOrder.TRANSACTED` = 成交态 + 已退款 —— **GMV 是毛成交额**，
  退款单要留在里面（否则单子全退光的商家会从排行整个消失，那正是最该被看见的一家）

顺带把 `reach()` 的「付过款的人」也换成 `TRANSACTED`：退过款的人**也算转化过**，
用不含退款的集合会让转化率随退款慢慢变低，而那与获客做得好不好毫无关系。

**守卫**：`OpsDashboardRankingFlowTest#merchantDashboardAndPlatformRankingAgree` ——
下两单付款、再下一单不付款并取消，然后断言**商家后台与平台排行逐分钱相等**。
把商家侧改回 `!= WAIT_PAY`，它立刻红。
