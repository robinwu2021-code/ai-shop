# TDD-微信发货信息录入

状态：**草稿（待确认）** · 2026-09-03 · 关联 [小程序账号与切换](./小程序账号与切换.md)
前置：微信支付未开通，**本方案不触发**；支付上线那天它同时变成硬要求。

---

## 1. 一句话

用户在小程序里用微信支付付了钱之后，**必须把「发货」这件事回传给微信**，
否则这笔钱结不出来。接口是 `POST /wxa/sec/order/upload_shipping_info`。

---

## 2. 为什么现在写而不是那天再写

它**不能上线后补**：

- 官方说明是「特定类型的小程序需在平台完成发货信息录入及确认收货流程后
  **方可进行资金结算**」—— 没上报的订单，钱卡在微信那边
- 超过 **48 小时未发货**会触发提醒，属于经营指标
- 我们类目里**四个是「商家自营」**（生鲜、3C、B2b、个护家清），
  正是这套规则针对的形态

支付上线当天才发现要接，意味着**第一批真实订单的钱结不出来**，
而那时候补接口、补历史订单、补重试，全都在有真实用户等着的压力下做。

---

## 3. 最容易写错的一段：我们的六种履约方式怎么对上微信的四种

微信只有四类，而我们有六种履约方式 —— **不是一一对应**，映射写错的后果是
`10060005 invalid logistics_type` 或者更糟：报上去了但语义是错的。

| 我们的 `FULFILLMENT` | `logistics_type` | 「发货」发生在哪一刻 | 要不要运单号 |
|---|---|---|---|
| `EXPRESS` 快递 | **1** 快递 | 商家点「发货」 | ✅ `tracking_no` + `express_company` 都必填 |
| `MERCHANT_DELIVERY` 送货上门 | **2** 同城配送 | 商家点「发货」 | ❌ |
| `STORE_PICKUP` 到店自提 | **4** 用户自提 | **货到自提点**（不是核销时） | ❌ |
| `NEIGHBOR_PICKUP` 邻里自提 | **4** 用户自提 | 货到团长家 | ❌ |
| `STORE_VERIFY` 到店核销 | **3** 虚拟商品 | **支付成功即可**（付款即出码，本就没有发货这一步） | ❌ |
| `APPOINTMENT` 预约/上门（家政） | **3** 虚拟商品 | **支付成功即可**（服务没有物流） | ❌ |

两条**反直觉**的，单独说：

- **自提不是「等他来取」才算发货。** `logistics_type=4` 的语义是「商家已备货、
  用户可来取」，对应我们的「货到自提点」。等到核销才报，48 小时的表会先响。
- **服务类要在支付成功时就报。** `STORE_VERIFY` / `APPOINTMENT` 在我们这儿
  根本没有「发货」动作（见 `FULFILLMENT` 的注释：付款即出码，直接落 FULFILLING）。
  没有动作 ≠ 不用上报 —— 不报一样结不出钱。**这是最容易整块漏掉的一类。**

## 4. 接口

```
POST https://api.weixin.qq.com/wxa/sec/order/upload_shipping_info?access_token=…
```

| 字段 | 我们怎么填 |
|---|---|
| `order_key.order_number_type` | `1`（商户单号）—— 我们有 `out_trade_no`，用它比用微信单号少一次查询 |
| `order_key.mchid` / `out_trade_no` | 商户号 + 我们的支付单号 |
| `logistics_type` | 见 §3 的映射表 |
| `delivery_mode` | `1` 统一发货。拆单发货（`2`）**只有快递才允许**（`10060006`），我们暂不支持 |
| `shipping_list[].item_desc` | 商品描述，≤120 字。**不能空**（`10060008`） |
| `shipping_list[].tracking_no` / `express_company` | 只有 `logistics_type=1` 才填，且**都必填**（`268485226/227`） |
| `upload_time` | RFC 3339，例 `2022-12-15T13:29:35.120+08:00` |
| `payer.openid` | ⚠️ 见下 |

### ⚠️ openid 必须是**支付时那个 AppID 下的** openid

`openid` 按 AppID 隔离。我们刚换过一次小程序号（见
[小程序账号与切换](./小程序账号与切换.md)），将来还可能再换。
拿「当前登录用户的 openid」去报一笔旧号下的订单，微信认不出这个人。

所以：**支付单上要落当时用的 openid**，上报时从支付单读，不从会话读。

**已做（V310）**：`stl_payment` 加了 `payer_openid` + `wx_appid` 两列，成对存 ——
只有 openid 没有 appid，将来换号之后就分不清它属于谁。
现在加成本为零（还没有真实支付单）；等有了订单再补，那批订单永远补不回来，
而补不回来的后果就是那些钱结不出账。

⚠️ **列加了不等于写了**：接支付时必须在建支付单那一步把这两个值填进去。
「加了列只改写入的一半」是本仓库反复出现的形状 —— 界面看不出区别、闸门全绿，
那一列永远读出 null。

### 其余两个接口

- `GET /wxa/sec/order/is_trade_managed` —— 先查这个号开没开通，
  没开通时**别把上报失败当成缺陷**去查
- `GET /wxa/sec/order/get_order` —— 查单笔的发货状态，对账与补偿用

## 5. 设计

### 5.1 走 SPI，和微信其它通道一致

```
shop-base/spi/trade/WxShippingPort            接口
shop-channel/…/WxShippingGateway              真通道（shop.wx.shipping.stub=false）
shop-channel/…/StubWxShippingGateway          桩：只记日志，恒成功
```

与 `WxAuthPort` / `WxPhonePort` 同一手法。**开关独立**（`shop.wx.shipping.stub`）——
和登录、订阅消息各自的前置不同，合成一个开关会让「先把发货接通」被别的
fail-fast 拦在启动阶段（`WxAuthGateway` 的类注释记着这一条）。

`access_token` 复用现有的 `stable_token` 获取逻辑，不再各拿各的。

### 5.2 上报时机：挂在状态机上，不是挂在按钮上

订单状态机已经知道每种履约方式「什么时候算发出去了」，
上报应当由**状态迁移**触发，而不是在各个 controller 里各写一次调用：

| 迁移 | 触发上报 |
|---|---|
| 支付成功 → `FULFILLING`（`STORE_VERIFY` / `APPOINTMENT`） | ✅ 立即 |
| `WAIT_FULFILL` → 货到自提点（`STORE_PICKUP` / `NEIGHBOR_PICKUP`） | ✅ |
| 商家发货（`EXPRESS` / `MERCHANT_DELIVERY`） | ✅ |

挂在按钮上的写法会漏掉「服务类没有按钮」这一整类 —— 而那正是 §3 说的最易漏的一类。

### 5.3 失败不能只靠一次调用

上报是**跨网络的副作用**，超时、限流、access_token 过期都会发生一次失败，
而失败的代价是这笔钱结不出来 —— 用户端毫无感知，商家几天后才发现。

- 落一张上报台账（订单号 / 状态 / 重试次数 / 最后错误），**先落库再调用**
- 定时扫「已支付但未上报成功」的订单补报
- `10060002 订单已发货` 当**成功**处理，不是失败：重试撞到它是正常的，
  按失败重试会永远重试下去

### 5.4 幂等

同一订单重复上报会得到 `10060002`。台账 + 把这个码视为成功，两者合起来才幂等 ——
只有台账没有码的处理，重启后照样会重复调。

## 6. 测试策略

| 用例 | 防住什么 |
|---|---|
| 六种履约方式各自映射到正确的 `logistics_type` | §3 那张表写错，报上去语义是错的 |
| `STORE_VERIFY` / `APPOINTMENT` 支付成功即上报 | **整类漏报**（没有发货按钮，最容易忘） |
| `EXPRESS` 缺运单号时不发请求、报可读的错 | 让 `268485226` 变成本地可见的校验失败 |
| `10060002` 视为成功 | 无限重试 |
| openid 取自订单而非会话 | 换过 AppID 后报的是另一个人 |
| 桩模式下不发真请求 | 本地/测试环境误报生产订单 |

## 7. 待确认

   「生活服务」与四个「商家自营」。保守做法是全都报（多报无害，漏报卡钱）。
2. **商户号还没有**，`mchid` 现在填不出来 —— 支付接入时一并定。
3. **谁来写这两列**：建支付单的那条路径要一并改，见 §4 的 ⚠️。
4. 官方文档随时会改。**动手前照 §4 的三个接口再核一遍**，
   本文写于 2026-09-03。
