# 进销存 · 上线与 G3 切换手册

> 状态：**待执行** · 2026-08-26
> 这份是**操作序**：改哪个配置、按什么顺序、看什么、不对了怎么退。
> 设计见[开发计划](./进销存-开发计划.md)，G3 的含义见那里的闸门一节。
>
> **贯穿全篇的一条**：进销存默认整个关着（`shop.inventory.enabled=false`），
> 关着时**一个 Bean 都不装**。所以每一步都是「打开一点点、看一段、再打开一点点」，
> 而不是「发一版然后祈祷」。

## 零、先确认线上是什么（三条命令，缺一不可）

```bash
ssh <server> 'systemctl cat ai-shop | grep -iE "profiles|Environment"'
ssh <server> 'mysql -e "SHOW DATABASES" | grep -i inv'
ssh <server> 'ls -l /opt/ai-shop/shop-app.jar'
```

### ⚠️ 第一条命令是这份手册的前提

进销存的**四个任务全部挂 `@Profile("worker")`**：预留回收 · 事件投递 · 存量搬运 · 日快照。
而部署文档（`deploy/tencent/README.md`）里只画了**一个进程**（8081，服务 `/mp /biz /ops`），
没有 worker。

**线上确实没有 worker profile —— 已实测（2026-08-26）：**

```
Environment=SPRING_PROFILES_ACTIVE=api,ops
只有一个单元 ai-shop.service；/opt/ai-shop/shop-app.env 里没有 profile 覆盖
```

旁证：`sys_job_run` 0 行、`shedlock` 0 行、`sys_outbox` 空表。
也就是说**所有 `@Profile("worker")` 的任务从上线到今天一次都没跑过**。

后果：

| 后果 | 严重程度 |
|---|---|
| 搬运任务不跑 —— 打开开关之后**什么都不会发生**，而日志里也不会有错 | 挡住第 2 步 |
| **预留过期不回收** —— 切换真相源之后，未支付的单占着的货**永远不释放** | **G3 的硬前置**，不解决不许切 |
| 日快照不跑、事件不投递 | 报表空、事件堆积 |

> **平台自己有 12 个任务在等这个进程**（对账自查、资质到期、自动关单…，
> 数字见「定时任务」技术方案 §一；短于 1 分钟的队列 poller 留在业务进程内，
> 不算在内）。它们同样一次都没跑过 —— **这件事比进销存重要**，
> 尤其「未支付订单永不关闭」那条。
>
> 眼下的实际影响比听上去小：平台至今 0 订单、6 个商家都是演示数据。
> 这不减轻要做的分量，反而说明**现在是零数据窗口，正是启用的最好时机**。

### 顺带一条：B 端九屏在搬运跑起来之前是空的

商家看到的库存物料，**只有搬运作业会创建**（`InventoryAclService.upsertItem`
全仓只有一个调用点，就在 `InventoryBackfillServiceImpl`）。所以九屏能不能用，
取决于这条链全通：

```
worker profile 上线 → 建进销存库 → shop.inventory.enabled=true
                   → backfill.enabled=true → dry-run=false
```

四件缺一件，商家点进「库存」看到的都是一片空 —— **而且不报错**。
上线时如果先放了 B 端入口、后开搬运，第一批商家会以为这个功能坏了。

**处置**：要么给 `ai-shop.service` 的 profile 加上 `worker`，要么另起一个
`ai-shop-worker` 单元（同一个 jar，`--spring.profiles.active=worker`）。
后者更好：跑批与在线请求分开，一个拉一年流水的对接方拖不垮下单。

## 一、第 0 步：建库（**需要 DBA 权限，我做不了**）

进销存是**另一个库**。`shop` 账号没有 `CREATE DATABASE` 权限（本机试过，线上大概率相同）。

```sql
CREATE DATABASE ai_shop_inv DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_uca1400_ai_ci;
GRANT ALL PRIVILEGES ON ai_shop_inv.* TO 'shop'@'localhost';
FLUSH PRIVILEGES;
```

**不要**把 `inv_*` 建进 `ai_shop`。建进去之后一切都还能跑，而「两个库分开了」这件事
就再也不会发生 —— 这个坑本地已经踩过一次，见[代码结构 §4.5.1](./进销存-代码结构与现状对齐.md)。

---

## 二、第 1 步：只开数据源，不开任何写

`/etc/systemd/system/ai-shop.service` 加四行（Spring 的宽松绑定，全大写下划线）：

```ini
Environment=SHOP_INVENTORY_ENABLED=true
Environment=SHOP_INVENTORY_DATASOURCE_URL=jdbc:mysql://127.0.0.1:3306/ai_shop_inv?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=UTC&characterEncoding=UTF-8
Environment=SHOP_INVENTORY_DATASOURCE_USERNAME=shop
Environment=SHOP_INVENTORY_DATASOURCE_PASSWORD=<同平台库>
```

`systemctl daemon-reload && systemctl restart ai-shop`

**验收**（三条都要过）：

```bash
curl -s localhost:8081/actuator/health | grep -o '"status":"[A-Z]*"'   # UP
ssh <server> 'mysql ai_shop_inv -e "SHOW TABLES" | wc -l'              # 19（含 flyway 历史表则 20）
ssh <server> 'mysql ai_shop_inv -e "SELECT COUNT(*) FROM inv_uom"'     # 8
journalctl -u ai-shop -n 200 | grep -i "inv-pool\|flyway"              # 没有 ERROR
```

**这一步之后平台的行为一个字节都没变**：库存仍然走 `prd_sku`，进销存那边是 19 张空表。

**退**：删掉那四行、重启。

## 三、第 2 步：搬运 dry-run（只算不写）

```ini
Environment=SHOP_INVENTORY_BACKFILL_ENABLED=true
Environment=SHOP_INVENTORY_BACKFILL_DRY_RUN=true
Environment=SHOP_INVENTORY_BACKFILL_BATCH=500
```

**`DRY_RUN` 默认就是 `true`** —— 这里显式写出来，是为了让下一步「翻成 false」是一次
看得见的改动，而不是「忘了设」。

看日志（**这是这一步唯一的产出**）：

```bash
journalctl -u ai-shop-worker -f | grep inv-backfill
# scanned=500 moved=0 skipped=0 pending=500 diffs=0 (下一轮 after=1274) (dry-run)
```

**读法**：
- `scanned` 是这一批看了多少个 SKU；量大就调大 `BATCH` 或多等几轮
- `moved=0 skipped=0` 在 dry-run 下是正常的 —— 它只算不写
- **`pending` 才是「还有多少没搬」**。`diffs` 在没搬过时恒为 0（没搬过的当然对不上，
  把它算成差异会让报告永远不干净），所以**只看 diffs 会以为一切正常**
- `(下一轮 after=…)` 是游标。看到 `(到末尾)` 才表示这一圈扫完了；
  在那之前 `pending` 只是**这一批**的数，不是全量的数

**退**：`SHOP_INVENTORY_BACKFILL_ENABLED=false`、重启。

## 四、第 3 步：真搬

**唯一一次不可回退的数据动作。挑低峰。**

```ini
Environment=SHOP_INVENTORY_BACKFILL_DRY_RUN=false
```

看日志直到 **`pending=0` 且看到 `(到末尾)`**：

```
scanned=500 moved=483 skipped=0  pending=17 diffs=0 (下一轮 after=1274)
scanned=500 moved=17  skipped=483 pending=0 diffs=0 (下一轮 after=2088)
...
scanned=126 moved=0   skipped=126 pending=0 diffs=0 (到末尾)          ← 这一圈扫完了
```

> ⚠️ **不要拿「moved=0 且 skipped 很大」当搬完了。**
> 这本手册此前就是这么写的，而那正好是 2026-08-26 修掉的那个 bug 的症状：
> 扫描原本没有游标，每一轮都从第一行扫同样一批，第二轮起自然全是「已搬过」——
> 报告长得和搬完了一模一样，而第 501 个 SKU 永远搬不到。
> **判据是 `pending=0` 加上 `(到末尾)`**，两个都要。

**幂等靠 `INIT` 单**（`source_type=INIT` + `source_ref=<skuNo>|<storeNo>`），
不是靠「余额是不是 0」。所以**重跑安全**：游标丢了（比如重启）就从头再扫一遍，
已搬的会被跳过 —— 慢，但不会漏。

**为什么没有回滚按钮**：回退要在「已经搬了一半」的状态下把两边都还原，
而那时哪一边是对的本身就说不清。**双写对差期比回滚按钮可靠得多** —— 那正是下一步。

真出事的退法：`SHOP_INVENTORY_ENABLED=false` 重启（平台侧本来就没被动过），
然后 `DROP DATABASE ai_shop_inv` 重来。

## 五、第 4 步：对差观察期 —— **这就是 G3**

平台仍在扣 `prd_sku`，进销存在旁边记第二本账。每天读一次对差：

```bash
# 路子一：运营端（要运营账号，我跑不了）
GET /ops/inventory/recon?limit=2000     # 权限 product:sku:read

# 路子二：直接查库（谁都能跑）
ssh <server> 'mysql -N ai_shop_inv -e "
  SELECT COUNT(*) FROM inv_stock_balance b
  JOIN ai_shop.prd_sku s ON 1=0"'       # ⚠️ 跨库 join 是禁止的，别这么查
```

> 上面第二条是**反面示例**：两个库之间不许 join。要比就用 `/ops/inventory/recon`，
> 它在应用层各读各的再比 —— 这也是为什么那个端点存在。

**判据只有一个**：响应里的 `clean` 为 `true`。

而 `clean` 现在是**两件事同时成立**：`diffs` 为空 **且 `pending` 为 0**。

> 为什么要带上 `pending`：`clean` 原本只看 `diffs`，而对差在「没搬过」的条目上
> **故意不记差异**（没搬过的当然对不上）——于是没搬过的 SKU 在报告里一个字都不出现，
> `clean` 照样是 true。照它切过去，那些货在进销存侧余额是 0，**切换当天全都卖不了**。
> 闸门守着一个它没在看的东西。已于 2026-08-26 修正。

| 观察时长 | 建议 |
|---|---|
| **连续 7 天 clean** | 覆盖一个完整的周周期（周末的单量与工作日不同） |
| 中间出现一次 diff | **计时重置**，先查那一条是怎么来的 —— 差异本身比天数重要 |

**diff 怎么读**：`{entityNo, storeNo, skuNo, platformQty, inventoryQty}`。
两边不一样只有三种可能，按可能性排：

1. **某条写库存的路径没经过 `StockPort`** —— 平台侧还有 4 处 Service 直接
   `setStock`（见[代码结构 §4.1](./进销存-代码结构与现状对齐.md)），它们不会同步到进销存
2. 搬运那一刻正好有单在扣 —— 重跑一次对差，如果自己好了就是这个
3. 真有 bug

第 1 条是**预期内的**：D2 之前平台是真相源，商家在建品页改库存不会走 Port。
所以 **G3 的前置动作是把那 4 处也接上**，或者接受「切换前最后再搬一次」。

## 六、第 5 步：切真相源

前置**三条全满足**才动：

- [ ] worker profile 在跑（第零步）
- [ ] 对差连续 7 天 `clean=true`
- [ ] 预留回收任务有日志（`inv-reservation-expiry`）—— 否则切完货会被占死

```ini
Environment=SHOP_INVENTORY_STOCK_AUTHORITY=INVENTORY
```

重启。这一刻起：下单走 `inv_stock_balance` 的条件更新，支付产生 `SALE` 出库单，
退货走 `restore`。

**切完立刻验三件**（在真机上下一单走完）：

```bash
journalctl -u ai-shop -f | grep -iE "INV_INSUFFICIENT|reservation"
ssh <server> 'mysql -N ai_shop_inv -e "SELECT COUNT(*) FROM inv_reservation WHERE status=\"HELD\""'
ssh <server> 'mysql -N ai_shop_inv -e "SELECT doc_no,qty_delta,balance_after FROM inv_ledger ORDER BY id DESC LIMIT 5"'
```

- 下单后 `HELD` +1，取消/超时后回落
- 支付后流水多一行 `SALE`，`balance_after` 与界面一致
- 退货退款后多一行 `RETURN`（仅退款不该有）

### 退

**删掉 `SHOP_INVENTORY_STOCK_AUTHORITY` 那一行、重启。** 三十秒。

平台的 `prd_sku.stock` 在切换期间是只读缓存但**没有被删**，所以退回去之后
它仍然是那个数。代价是：切换期间进销存这边发生的变动没有同步回平台 ——
退回去之后要**再跑一轮搬运对差**才知道差了多少。

> 这是「切换是配置改动不是发版」的全部意义：
> **发现不对，改回去只要重启，不用等一次构建与发布。**

## 八、一句话的顺序

**确认 worker → 建库 → 开数据源 → dry-run → 真搬 → 对差 7 天 → 切 → 真机验一单。**
任何一步不对，退回上一步只要改配置加重启。
