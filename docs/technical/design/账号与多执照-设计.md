## 一、账号不是主体 —— 它们是两层

**问：实体（主体）对应的是注册账号么？**

**不是。这是本轮设计里最容易混的一处，也是多执照能不能成立的关键。**

| 层 | 是什么 | 一个人有几个 | 表 |
|---|---|---|---|
| **账号** | 登录凭据的持有者 | **一个**（多种登录方式指向同一个） | `usr_user` |
| **主体** | **一张营业执照**对应的经营实体 | **可以多个** | `usr_merchant` |
| **收款商户号** | 进件产生的 `sub_mchid` | 每主体 × 每通道一条 | `usr_merchant_payment` |

```
usr_user（老王的账号，注册一次）
   │
   ├── is_owner ──→ usr_merchant A（个体户执照）──┬─ 微信收款号
   │                                            └─ 支付宝收款号
   └── is_owner ──→ usr_merchant B（公司执照）  ──┬─ 微信收款号
                                                └─ 支付宝收款号
```

**「注册一次支持多张营业执照」在模型上已经成立**：
`usr_merchant_staff(user_no, merchant_no, is_owner)` 是多对多，
老王对 A、B 各有一条 `is_owner=1` 的成员行。

**「多个收款账号」也已经成立**：`usr_merchant_payment` 每通道一条，
主体 A 可以同时有微信和支付宝两个收款号；门店再用 `payment_no` 挑一个（V46）。

## 二、但有三处代码会挡住它

模型支持不等于链路通。逐条查下来有三个阻塞点：

### 2.1 🔴 审核通过时「已是商家就复用」

`MerchantPortImpl.activate` 里这段：

```java
// 已是商家就不重复创建 —— 审核通过被重复点击是常态，不是异常
UsrMerchant existing = merchantMapper.selectOne(
        ...eq(UsrMerchant::getOwnerUserNo, ownerUserNo).last("limit 1"));
if (existing != null) { /* 复用它 */ }
```

它的本意是**幂等**（防止运营重复点「通过」）。但判据用的是「这个人是不是已经有商家」——
于是老王申请第二张执照、审核通过时，**系统会把它当成重复点击，
去改第一个主体而不是新建第二个**。

结果：第二张执照的名称/行业/主体类型覆盖掉第一个，而老王只看到「审核通过了」，
两家店变成一家。**这个故障没有任何报错。**

**修法**：幂等的判据应该是**申请单**而不是人 ——
`usr_merchant_apply.merchant_no` 已经在通过时回填，非空即表示这份申请已经激活过。
按申请单幂等，同一个人申请几张执照都互不干扰。

### 2.2 🟡 一人一份进行中的申请

`uk_apply_active_owner` 唯一键：一个人同时只能有一份进行中的申请。

**这条要保留** —— 它防的是表单重复提交。而它不阻塞多执照：
第一份通过后 `active_owner` 置 NULL，名额就释放了。

只有一个体验问题：老王想同时申请两张执照会被拒，而错误只说「你已有一份进行中的申请」。
**文案要说清是"同时"而不是"只能有一个"**，否则他会以为平台不支持多执照。

### 2.3 🔴 身份解析只取一个主体

`BizIdentityResolverImpl` 现在按 `is_primary` 排序后取 `limit 1`，
`BizContext` 里也只有一个 `merchantNo`。

**这是刻意的**（M1 要零行为变化），但多执照要用就必须放开：
`BizContext` 扩成 `merchantNos` + `currentMerchantNo`，请求带 `X-Merchant-No`。

## 三、多端登录：账号打通怎么做

**问：怎么兼容支付宝、微信等小程序场景？**

### 3.1 现状：三方身份是列，不是表

`usr_user` 上有 `openid` / `unionid` / `apple_sub` 三列。这个结构有两个问题：

| 问题 | 后果 |
|---|---|
| **加一个平台就要加一列** | 支付宝进不来 —— 没有它的列 |
| 一个平台只能绑一个身份 | 同一个人的微信小程序 openid 与 App 的 openid **不是同一个**（不同 AppID） |

### 3.2 改法：身份绑定独立成表

```
usr_user（账号本体：昵称、头像、手机号）
   │
   └── usr_user_identity(user_no, provider, external_id, union_id?)
         WECHAT_MP     openid（小程序）
         WECHAT_APP    openid（App）      ← 同一个人，不同 AppID
         WECHAT_UNION  unionid           ← 微信生态内打通靠它
         ALIPAY_MP     支付宝 user_id
         APPLE         apple_sub
         PHONE         手机号
```

`UNIQUE (provider, external_id)` —— 一个三方身份只能绑一个账号。

### 3.3 三个平台怎么落到同一个账号

| 场景 | 怎么找到账号 |
|---|---|
| 微信小程序 ↔ 微信 App | 靠 **unionid**（同一开放平台下天然打通） |
| 微信 ↔ 支付宝 | **只能靠手机号** —— 两个生态之间没有任何共同标识 |
| 老用户新增登录方式 | 已登录状态下绑定，直接写一条 identity |

**手机号是跨生态的唯一锚点**，所以：

| 规则 | 为什么 |
|---|---|
| 首次通过三方登录且**手机号已存在** → 绑到该账号 | 否则老王在支付宝小程序里会变成一个新用户，看不到自己的店 |
| 手机号**未验证**时不做自动合并 | 三方返回的手机号不一定可信；合并错了两个人的账号无法拆回 |
| 合并前要**明确告知**「将与已有账号合并」 | 静默合并会让人以为数据丢了 |

> ⚠️ **账号合并是不可逆的**。宁可让他多一个账号（之后手动绑定），
> 也不要自动合并两个可能不是同一个人的账号。

### 3.4 商家端的三条登录路径

多执照 + 多端之后，B 端登录有三条路，都要落到同一套作用域：

| 路径 | principal | 用于 |
|---|---|---|
| C 端账号（老板） | `user_no` | 小程序：他从 C 端发起入驻，本来就是消费者 |
| 员工独立登录 | `merchant_staff_no` | App：店员没有也不需要 C 端账号（V46 已做） |
| 三方直登 | 经 identity 表换到 `user_no` | 支付宝/微信小程序免登 |

## 四、单库下的冗余（第 2 问）

**问：避免双写，单数据库可以冗余信息。**

**同意，而且我把它叫「双写」是个不准确的说法。** 澄清一下这里到底存了什么：

`ord_sub_order` 上的两列：

| 列 | 是什么 | 能不能推出来 |
|---|---|---|
| `merchant_no` | 下单当时的**结算方** | 能 —— 由 `store_no` 经 `usr_store` 推 |
| `store_no` | 履约门店 | —— |

所以它确实是**冗余**，不是两份可能打架的数据。留着它有两个理由：

**① 快照语义**。订单是历史事实。哪怕将来门店的归属或收款方式变了，
这一单当时的结算方也必须原样保留 —— 分账已经按它执行完了，
回头重算等于把已完成的资金流凭空改掉。

**② 避开热路径上的 join**。结算、对账、积分都按 `merchant_no` 聚合，
是最高频的几条查询。为了省一列而在每次聚合时多 join 一张门店表，不划算。

**不会打架的原因**：门店**归属**主体且不可改挂（可改的是收款商户号 `payment_no`，
不是 `merchant_no`）。所以这两列在任何时刻都自洽 —— 冗余而非分歧。

> 单库确实让这件事简单：不需要跨库一致性、不需要补偿。
> 我之前用「双写」这个词，容易让人以为有两个数据源要保持同步 —— 没有，只有一份。
> 后续文档统一改称**「冗余快照」**。
