## L1 · 定位

`pay-risk` 是一层**判定器**：输入是指标与名单，输出是「放行 / 挂起 + 一句人话」。

它**不存自己的名单**（名单在主库 `risk_*`），也**不做处置**（处置是批次状态机的事）。
只回答一个问题：**这一批钱现在放出去，有没有已知的理由不该放。**

---

## L2 · 一、模块结构

```
pay-risk/
├── metric/          指标计算：读支付库，算退款率 / 集中度 / 欠款
├── rule/            规则：每条规则 = 判据 + 阈值 + 一句人话
├── decision/        判定：汇总规则命中 → 放行 / 挂起 + 原因
└── shadow/          影子模式：只记录不拦截，与真拦截共用 rule/
```

**`shadow/` 与 `rule/` 共用同一套判据代码**，这是刻意的：
两套代码的话，切真拦那天的行为与影子期观察到的**不是同一个东西**，
而影子模式的全部价值就在于「观察到的就是将来会发生的」。

---

## L2 · 二、指标：五个，都在支付库内算得完

| 指标 | 判据 | 数据源 | 窗口 |
|---|---|---|---|
| `refundRate` | 退款额 / 成交额 | `stl_bill` + 退款流水 | 近 N 天 |
| `concentration` | 本批放款额 / 保证金 | `stl_settle_batch` + 主库保证金 | 单批 |
| `debtBalance` | 欠款余额 | `mch_debt` | 即时 |
| `abnormalPattern` | 同人同店高频 / 整数额集中 / 深夜集中 | `stl_payment` + 订单 | 近 N 天 |
| `listHit` | 黑名单或关联主体命中 | **主库 `risk_*`** | 即时 |

> **前四个都在支付库内**，这是把结算与积分放在同一个库的又一个收益：
> 「这个商家的钱有没有异常」不需要跨库。
> 只有第五个要问主库，而它是一次简单的名单查询，不是 JOIN。

### 指标计算的两条纪律

**① 分母为零时不出结论。**
近 N 天成交额为 0 的商家，退款率不是「0%」也不是「100%」，是**无意义**。
出结论的话，一个刚开店的商家会因为一笔退款被判成 100% 退款率而挂起。

**② 指标要能被复算。**
挂起原因里给出的数字，运营点进去要能看到它是怎么算的（分子、分母、窗口）。
算不出来的数字在申诉时一文不值 —— 商家问「凭什么说我 32%」，答不上就只能放行。

## L2 · 三、规则：每条自带一句人话

```java
interface FundRule {
    String code();                       // 稳定标识，进日志与统计
    Verdict evaluate(RiskContext ctx);   // PASS / HOLD
    // 命中时的原话，**直接展示给商家**，必须含具体数字与阈值
    String explain(RiskContext ctx);
}
```

| 规则 | 拦在 | 人话样例 |
|---|---|---|
| `REFUND_RATE_HIGH` | P2 | 「近 7 天退款率 32%（阈值 20%），本批转人工复核」 |
| `BATCH_TOO_LARGE` | P2 | 「本批 12,400 元超过保证金的 3 倍（保证金 3,000 元）」 |
| `DEBT_OUTSTANDING` | P2 | 「有 128 元待抵扣欠款，将从本批扣除后放款」 |
| `PATTERN_ABNORMAL` | P2 | 「近 7 天有 18 笔来自同一买家的整数额订单」 |
| `ENTITY_LISTED` | P1 / P2 | 「主体在风控名单中，请联系客服」 |
| `AMOUNT_OVER_ORIGINAL` | P3 | 「退款额超过原单金额」← **硬拦，这是错误不是风险** |
| `REFUND_ABUSE` | P3 | 「该买家近 30 天在本店退款 9 次」 |

**说不出人话的规则不许上线。** 不是体验问题，是**申诉链路走不通**：
商家不知道触发了什么，只能反复问客服，而客服也看不到判据 ——
最后变成「系统说的」，那是信任崩塌最快的一条路。

> 这条排除掉一类做法：**不可解释的综合评分**。
> 打分模型可以用来**排序**（先看谁），不可以用来**判定**（拦不拦）。

## L2 · 四、判定：三种结果，没有第四种

| 结果 | 含义 | 后续 |
|---|---|---|
| `PASS` | 无命中 | 批次继续 → `RELEASED` |
| `HOLD` | 有命中 | 批次 `BLOCKED` + 原因 + `block_expire_at` |
| `HARD_FAIL` | 数据错误（非风险） | 直接拒绝并告警，**不进人工队列** |

**`HARD_FAIL` 只用于「这不可能是对的」那一类**（退款额超原单、金额为负）。
把它和风险混在一起的话，人工队列里会混进一批根本不需要判断的东西，
而真正需要人判断的那些会被淹没。

## L2 · 五、影子模式：上线的必经一步

```
第 1–2 周   只记录：命中了谁、哪条规则、如果真拦会拦住多少钱
第 3 周     复盘：命中的都是什么人？其中几个是真问题？
第 4 周     定阈值 → 小范围真拦（先只对新商家 / 小额批次）
```

### 开跑之前就要定死「凭什么说可以真拦了」

否则两周后只会得到一堆数字和一次拍脑袋。

| 判据 | 目标 | 不达标说明 |
|---|---|---|
| 命中批次占比 | < 5% | 阈值太松，噪声淹没信号 |
| 命中中确认为真问题的比例 | > 30% | 规则选错了信号 |
| **每条规则至少有一次「只有它命中」** | 有 | 否则它是冗余的 |

第三条是防「一堆规则其实在说同一件事」——
那种规则集看着覆盖很全，实际上只有一个维度，**调其中任何一条都不会改变结果**。

### 影子期的数据要留下来

`pay_risk_shadow_log`（影子期专用，跑完可删）：
批次号、命中规则、指标快照、如果真拦会拦多少钱。
**不留的话复盘无从做起**，而复盘正是影子模式的目的。

## L2 · 六、与批次状态机的接线

```
BatchRecon ──▶ RECONCILED
                   │
             pay-risk.decide(batch)
                   │
        ┌──────────┼──────────┐
      PASS       HOLD      HARD_FAIL
        │          │            │
   BatchRelease  BLOCKED     拒绝 + 告警
                   │
              ⑧ BlockExpiry ──超时──▶ 放行 + 告警（decided_by = SYSTEM_TIMEOUT）
```

**风控判定发生在对账之后、放行之前。** 顺序不能反：
对账没过的批次连「该放多少」都还不确定，风控算集中度会算错。

## L3 · 七、可观测：四个必须能看的数

| 数 | 说明什么 | 不正常时 |
|---|---|---|
| 命中率（命中批次 / 总批次） | 阈值松紧 | 持续 > 5% → 阈值太松 |
| 超时自动放行数 | **有没有人在处置** | 持续 > 0 → 时限比处置能力短 |
| 平均挂起时长 | 处置效率 | 逼近时限 → 人手不足 |
| 每条规则的独立贡献 | 规则冗不冗余 | 长期为 0 → 该删 |

**第二个最要紧。** 超时自动放行不是异常，是设计的一部分（见 ADR-022 §3.4），
但它**持续大于零意味着这道门形同虚设** —— 那时要调的是时限或人手，不是把自动放行关掉。
关掉它只会让挂起变成永久冻结，而那是更坏的结果。

## L4 · 八、待确认

1. **全部阈值** —— 先跑影子模式，见 §五
2. 保证金扣划的合规边界（法务）
3. 欠款止损线：欠多少停止合作、谁批
4. 挂起时限：2 个工作日是建议值，要与运营的实际处置能力对齐
5. 影子期的数据保留多久、跑完删不删
