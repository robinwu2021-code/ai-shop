**主干是通的，缺口集中在「分类」这一层的上半段和「商品生命周期」的两端。**

| 层 | 结论 |

## 一、分类：四层，系统只做了两层

这是最容易混、也是缺口最大的一层。**四个东西各回答一个不同的问题**：

| # | 节点 | 回答什么 | 谁维护 | 挂在 | 系统现状 |
|:--:|---|---|---|---|---|
| 1 | **品类 / 形态** `CategoryType` | 这货**怎么交付**（生鲜要截单 / 服务不发货 / 虚拟即时发放） | 平台硬编码，5 值 | 商品 | ✅ 已有，且已改为**由类目派生**（P1-1） |
| 2 | **后台类目** `prd_category` | 这货**是什么**、要什么资质 | 运营（三级树） | 商品，**必填** | ✅ 已有 |
| 3 | **主题分类 / 专题** | 这货**属于哪场活动**（年货节 / 早餐必备 / 新店尝鲜） | 运营 | 商品，多对多 | ❌ **完全没有** |
| 4 | **店内分类** | 商家**自己怎么摆货架**（本店主推 / 蔬菜区 / 熟食区） | 商家 | 商品，多对多 | ⚠️ **只有一个扁平列表** |

> 另有一个 **前台导购分类**（C 端逛的那棵树，与后台类目多对多）。
> 现在 C 端「分类」页是按 `CATEGORY_TYPE` 分三个 tab —— 那是**前台分类缺位时的替代品**，
> 一期刻意如此（见 [类目树补齐方案](./类目树补齐方案.md) §五）。

### 1.1 为什么 ③④ 不能用后台类目顶替

后台类目是**唯一归属**（一件货只挂一个叶子），而主题与店内分类都是**多对多**：
一袋大米可以同时在「年货节」「本店主推」「粮油区」里，但它只能属于一个「粮油调味」类目。

强行用类目顶替，代价是二选一 —— 要么类目变成多值（准入判据当场失效，
`required_code` 不知道该按哪个判），要么活动只能圈类目而不能圈商品（运营选不了「就这 20 件」）。

### 1.2 ③ 主题分类：一张表都没有

全仓扫过：没有专题表、没有专题接口、端上没有任何专题概念。

**代价不是「少个功能」，是运营完全没有抓手**：想做一次「早餐必备」，
现在只能靠营销活动（`mkt_campaign`）圈商品 —— 而那个是**带折扣的**，
运营想做的往往只是「把这 20 件摆到一起」，不想降价。

### 1.3 ④ 店内分类：只有 `mch_store.featured` 一个扁平列表

```sql
mch_store.featured  TEXT  -- JSON 数组：主推商品 goods_no，有序
```

有写入路径（`POST /biz/store` 的门店资料里），能排序，但**只有一组**。
商家能表达「这几件主推」，表达不了「蔬菜区 / 熟食区 / 冷饮区」。

一家卖 200 件货的店，店铺页现在只能按上架时间倒序平铺 —— 这是 B 端商品管理里
**商家最先会问的那个功能**（「我怎么把货分类摆出来」），而它现在的答案是「摆不了」。

## 二、商品（SPU）

| 节点 | 现状 |
|---|---|
| 商品主体 `prd_goods` | ✅ 挂主体（`entity_no`），门店只是投影 |
| 标准品 `prd_spu_std` → 商家品 | ✅ 本轮新增：搜标准品 → 填充 → 服务端强制收敛类目与 `optionCode` |
| 标题 / 副标题（三语） | ✅ 整份下发、整份覆盖 |
| 封面 / 轮播图 | ✅ 本轮补齐了轮播图的**写入路径**（此前有列、有契约、没有入口） |
| 品类差异字段（生鲜 / 服务 / 限购 / 拼团） | ✅ 本轮补齐写入，按形态切换字段区 |
| 履约方式 | ✅ 本轮补齐编辑入口 |
| **商品详情（富文本 / 图文详情）** | ❌ **没有**。只有轮播图，没有「详情描述」那一段 |
| **草稿态** | ❌ **没有**。见 2.1 |

### 2.1 没有草稿态 —— 这条比看起来严重

`prd_goods.audit_status` 只有三个值：`AUDITING` / `APPROVED` / `REJECTED`。
**保存即提审**：商家填了一半点保存，就进了运营的待审队列。

三个连带后果：

1. 运营的待审队列里混着一堆半成品，而**他分不出哪些是真的要审**；
2. 商家不敢中途保存 —— 一次建品必须一口气填完，而多规格商品要填 8 行价与库存；
3. 已上架商品改一个错别字，会回到 `AUDITING` 并**强制下架**（这条是刻意的，防「改成别的东西再卖」），
   但因为没有草稿，他连「改完一起提交」都做不到。

**这三条互相咬合**：正因为没有草稿，第 3 条的代价才被放到最大。

## 三、规格

| 节点 | 落点 | 现状 |
|---|---|---|
| 规格模板（平台） | `prd_spec_template` `scope=PLATFORM` | ✅ 每个选项必须带 `code` |
| 规格模板（商家自存） | 同表 `scope=MERCHANT` | ✅ **不强制 code**（刻意：卖手工酱菜的没有匹配模板） |
| 规格组 `SpecGroup` | `prd_goods.spec_groups` 内嵌 JSON | ✅ 不单独成表 |
| 规格选项 + `optionCode` | 同上 | ✅ 写入闭环；**消费未做**（B-4.5 说的「一期只写入不消费」） |
| 规格矩阵（组 × 选项 → SKU） | 端上笛卡尔积 | ✅ 改规格保留已填价与库存、复用原 `skuNo` |

**`optionCode` 的消费缺口现在有解了**：标准品库落地之后，同一件货在不同店里终于指向同一个
`std_no` + 同一批 `code` —— 聚合、比价、跨店统计的前提第一次成立。
但**消费侧一行代码都还没写**（没有按 code 聚合的查询、没有比价视图）。

## 四、SKU

| 节点 | 落点 | 现状 |
|---|---|---|
| SKU 行 | `prd_sku`，`(entity_no, sku_no, market)` 唯一 | ✅ 一市场一行 |
| 售价 | `price` | ✅ **SPU 上无价**，展示价 = `min(sku.price)` |
| 按市场分别定价 | `market` 列 | ✅ 本轮补齐下发与保留（此前编辑一次会删掉其余市场的行） |
| 划线价 `originPrice` | ✅ 本轮补齐写入 | 必须高于售价，否则是个「涨价了」的折扣标 |
| 标称重量 `nominalGram` | ✅ 本轮补齐写入 | 生鲜按标称预扣、称重后多退少补 |
| **SKU 级图片** | ❌ 没有 | 选中「红色」不换图，多规格商品的体验缺一块 |
| SKU 独立状态 | ❌ **不存在**，也不该有 | 审核判的是整件商品（见 [TDD-ops-商品与类目](./ops/TDD-ops-商品与类目.md) §2.2 的更正） |

## 五、库存

四层，全通：

```
prd_sku.stock                主体总量        ← 商家改（/biz/goods/{no}/stock）
    ↓ 有店级行时读写都切到下面这层
prd_store_stock              门店库存        ← 商家改（/biz/goods/{no}/store-stock）
    ↓ 现货不足时回落
prd_sku.presale_quota        预售额度        ← **只有平台能设**（/ops/skus/{no}/presale）
    ↓ 下单时
prd_stock_lock               库存锁          ← 交易域经 StockPort，条件更新原子扣减
```

**语义上最需要记住的一条**：门店库存是「覆盖表」——
某个 SKU 一旦有了任意一行店级库存，**没有行的店视为 0，不回退主体总量**。
回退会让没配过的店变成无限供应；少卖可恢复，超卖不可。

**缺口**：预售只有平台能设（P1-4）。生鲜商家的日常是「今晚定明天的截单」，
每次都要找运营，这条链在真实经营里跑不动。

## 六、上架与可见性

三级，全通，且**三者必须同步**：

| 级 | 落点 | 含义 |
|---|---|---|
| 主体 | `prd_goods.on_sale` | 这件货整体还卖不卖（总闸） |
| 门店 | `prd_store_goods.on_sale` | 这家店今天卖不卖（覆盖语义，同库存） |
| 社区 | `prd_community_pool` | **买家能不能搜到** |

> 这个域最贵的一条经验：`on_sale` 是商家的心智，`prd_community_pool` 才是买家的事实。
> 不同步的故障不报错、不留日志、两端各自看都正常。

## 七、缺口汇总（按「商家会不会问」排序）

| # | 缺口 | 商家的原话大概是 | 量级 |
|:--:|---|---|---|
| 1 | **店内分类** | 「我怎么把货分类摆出来」 | 中：一张表 + B 端管理页 + 店铺页分组渲染 |
| 2 | **草稿态** | 「我填一半能不能先存着」 | 小：加一个状态值 + 列表页签 + 提审动作 |
| 3 | **商品详情图文** | 「我想写一段介绍」 | 小：一个富文本/图文段字段 |
| 4 | **批量操作** | 「我要给这 20 件一起调价 / 一起下架」 | 中 |
| 5 | **商家侧预售** | 「今晚我想改明天的截单」 | 小（P1-4，字段都在） |
| 6 | **主题分类** | 运营问，不是商家问 | 中：表 + 运营页 + C 端入口 |
| 7 | **SKU 级图片** | 「选红色能不能换张图」 | 小 |
| 8 | **`optionCode` 的消费** | 没人问，但它是标准品库的目的 | 大：聚合与比价视图 |

### 建议的下一步顺序

**先 2 + 3**（草稿态 + 图文详情）：两条都小，且都卡在「建品这件事本身」上 ——
一个让商家敢中途停，一个让他说得清自己的货。做完建品链路才算完整。

**再 1**（店内分类）：它是商家问得最多的那个，但要动店铺页的渲染，
且与 ③ 主题分类共享同一套「商品分组」结构 —— 设计时一起想，实现时先做店内。

**4 / 5 / 7 随时可插**，各自独立。

**8 单独立项**：它不是商品管理的一部分，是标准品库的下游价值兑现。
