# TDD · 团购从商品挪进活动

> 状态：**草稿 · 待确认** · 2026-09-18
> 起因：店主「团购不要在商品编辑页面做，新增一个活动功能，在活动中管理团购」
> 相关：[TDD-商品规格与发布](./TDD-商品规格与发布.md)、`promotion` 包的 `package-info`

---

## 一、一句话

**团购的「价格与人数」现在长在商品上，应该长在活动上。**

它不只是把两个输入框搬个家：搬完之后同一件货才可能**在不同时间参加不同的团**，
而今天它一辈子只有一个团购价。

---

## 二、现状（2026-09-18 查得，不是回忆）

| 东西 | 在哪 | 线上实况 |
|---|---|---|
| 团购价 / 起团人数 | `prd_goods.group_price_minor`、`group_min_count` | **0 件商品配过** |
| 团这个实体 | `mkt_group_buy` / `mkt_group_member` | — |
| 商家开团 | `GroupService.createMerchantGroup(merchantNo, goodsNo)` | 价格与人数**从商品上读** |
| 活动（新模型） | `pmt_activity`，触发 × 优惠 × 排期 × 限量 | **0 条** |
| 活动（老模型） | `mkt_campaign`，退场中 | **0 条** |
| 活动入口 | 工作台 → **营销** → **活动**（不是一级入口） | 已可达 |

**三张表都是 0 行。** 这一条决定了整份方案的形状：**没有存量要迁**，
既不用写数据迁移，也不用两套并存 —— 这是做这件事最便宜的时刻，过了就不是了。

## 三、团购能不能直接做成一种 `pmt_activity`

**一半能，一半不能，差别要说清楚。**

`pmt_activity` 管的是**算价规则**（触发 × 优惠）。团购比它多一样东西：
**「团」是一个有生命周期的实体** —— 团号、发起人、自提点、成团与否、成员名单，
都在 `mkt_group_buy` 里。活动模型里没有、也不该有这些。

所以分工是：

- **活动持有规则**：哪些商品、几人成团、成团价、什么时候到什么时候
- **`mkt_group_buy` 持有实体**：这一团是谁开的、到哪个自提点、凑够没有

开团时**从活动读规则**，不再从商品读。这就是这次改动的全部实质。

模型上要补的只有一处：新触发 `TRIGGER_GROUP`（成团人数）。
优惠复用已有的 `BENEFIT_PRICE`（改单价）—— 成团价本来就是「把单价改成 X」。

> `PmtActivity` 的类注释写着「拆开之后新玩法是新组合，不是新枚举」。
> 团购正是这句话的一个用例：`GROUP × PRICE`，而不是 `type = GROUP_BUY`。

## 四、方案

### 4.1 商品编辑页：拿掉两个字段

`groupBuy` / `groupBuyOpen` 那一段整块删掉（`goods-edit` 第 318–336 行一带），
连同保存时那条「两个值要么都填要么都不填」的校验。

### 4.2 活动编辑页：加一种玩法

现在四种预设（`ACQUIRE` / `WAKEUP` / `CLEAR` / `BASKET`）都是
`benefit + audience` 的组合。加第五种 `GROUP`：

| 字段 | 取值 |
|---|---|
| `triggerType` | **`GROUP`**（新） |
| `triggerQty` | 起团人数，复用已有列 |
| `benefitType` | `PRICE` |
| `benefitAmountMinor` | 成团价 |
| 商品范围 | 复用 `PRICE` 那一支已有的选商品 |

### 4.3 开团：规则来源换一处

```
createMerchantGroup(merchantNo, goodsNo)
  → createMerchantGroup(merchantNo, activityNo, goodsNo)
```

从活动读价与人数；活动不在 `RUNNING` 就开不出团。
**商家团（`groups`）那一页因此要先选活动再选货** —— 这是界面上唯一看得见的变化。

### 4.4 C 端「拼团价」改成问活动

商品详情今天读 `GoodsVO.groupPrice`。改成问「这件货此刻有没有在跑的团购活动」。
**这是本方案里唯一碰买家侧的改动**，也是最该单独验的一处。

### 4.5 `prd_goods` 那两列：先停写，不删

线上 0 行，删掉是安全的 —— **但仍然不删**。
理由不是怕丢数据，是**回滚**：停写只要改代码，删列之后想回去就得再来一次迁移，
而这条链跨三端，回滚的窗口应该留长一点。跑满一个发布周期再删，单开一条。

## 六、待确认（要你拍板）

1. **活动要不要升成一级入口。** 你说「新增一个活动功能」，而活动其实已经有了，
   只是埋在 工作台 → 营销 → 活动 第三层。团购挪进去之后它是常用功能，
   我建议**提到工作台一级**，但这会占掉工作台一个位置。
2. **一件货同时在两个团购活动里怎么办。** 今天不可能（价在商品上，只有一个）；
   挪进活动之后就可能了。两条路：建活动时就拦（`/biz/activity-conflicts` 已经有这个接口），
   或者允许并取较低价。**我倾向拦**——两个价同时在跑，客服解释不清。
3. **不成团怎么办这条规矩不变吧？** `groups` 页的注释写着「**不成团不作废**，
   按原价照常发货 —— 生鲜场景下不成团退款 = 用户白等一天没菜」。
   这条挪进活动之后仍然成立，我不打算动，但它值得你确认一次。

## 七、闸门

- 场景用例：建一个 `GROUP × PRICE` 活动 → 按它开团 → 成团价生效；
  **把活动停掉 → 开不出团**（消融：去掉「活动必须 RUNNING」那一判，用例必须变红）
- 反向：商品上那两列**再也不被写入** —— 建品/改品之后查库，两列恒为 null
- C 端：商品详情的拼团价来自活动，**活动结束后那一栏消失**
- 不成团：仍按原价发货，与改之前逐字一致
