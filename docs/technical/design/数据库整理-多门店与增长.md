> 状态：**M1/M2 已落地（V44/V45）**，M3–M7 待做（M4/M5/M7 等模型决策落定）· 2026-08-09

## 一、总览：改动规模

| 类别 | 张数 | 说明 |
|---|---|---|
| **新建** | 9 | 门店、子账号、Plan、区域、增长五块 |
| **改表** | 7 | 加列为主；两处语义变更 |
| **数据迁移** | 5 处 | 都要"先补数据再改结构" |
| **不动** | 22 | 交易、结算、售后、积分、消息 —— **这是双写设计换来的** |

**最重要的一行**：`ord_sub_order` 只加一列 `store_no`，
结算/分账/积分/对账**一行不改**。这是整个改造能分阶段发布的原因。

## 二、对照表：现状 → 目标

### 2.1 账号与身份

| 现状 | 目标 | 动作 |
|---|---|---|
| `usr_merchant.owner_user_no` 是**唯一身份来源** | 降级为「创建者」记录 | 保留列，改注释；身份改走新表 |
| （无） | `usr_merchant_staff` 主体成员 | **新建** |
| （无） | `usr_staff_store` 每店角色 | **新建** |

```sql
-- 我是这个主体的成员
CREATE TABLE usr_merchant_staff (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  -- 落地时改名 merchant_staff_no：**staff_no 被平台员工 sys_staff 占着**，
  -- 而两者是完全不同的人（运营 vs 店员）。同名不同义的键会让下一个按名字 join 的人连错
  merchant_staff_no VARCHAR(64) NOT NULL,
  merchant_no   VARCHAR(64) NOT NULL,
  user_no       VARCHAR(64) NOT NULL COMMENT '绑 C 端账号 —— 店员多半已是 C 端用户，不新发一套密码',
  is_owner      TINYINT     NOT NULL DEFAULT 0 COMMENT '老板：全主体全门店，不需要逐店授权行',
  is_primary    TINYINT     NOT NULL DEFAULT 0 COMMENT '该用户的默认主体（App 多商家切换用）',
  status        VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',
  ...
  -- 约束名带 ms_ 前缀：**H2 的约束名是全库唯一的**（MySQL 只在表内唯一），
  -- 所以与 sys_staff 的 uk_staff_no 冲突只有测试库会报，生产不会 —— 本地跑通 CI 才炸
  UNIQUE KEY uk_ms_merchant_staff_no (merchant_staff_no),
  -- 一个人在一个主体里只有一条成员记录；角色在 usr_staff_store
  UNIQUE KEY uk_ms_merchant_user (merchant_no, user_no),
  KEY idx_ms_user (user_no, status)
);

-- 我在这家店是什么角色。**每店一行** —— 同一个人可以 A 店店长、B 店店员
CREATE TABLE usr_staff_store (
  id        BIGINT AUTO_INCREMENT PRIMARY KEY,
  merchant_staff_no VARCHAR(64) NOT NULL,
  store_no  VARCHAR(64) NOT NULL,
  role      VARCHAR(16) NOT NULL COMMENT 'MANAGER / CLERK。OWNER 不在这里 —— 他不需要逐店授权',
  ...
  UNIQUE KEY uk_staff_store (merchant_staff_no, store_no)
);
```

**迁移**：为每个 `usr_merchant` 建一条 `is_owner=1` 的成员行，
`user_no` 取 `owner_user_no`。之后 `BizIdentityResolver` 改查新表。

> ⚠️ **`limit 1` 那一行是多商家的唯一硬阻塞**：它不报错，只是安静地把第二家店藏起来。

### 2.2 门店

| 现状 | 目标 | 动作 |
|---|---|---|
| `usr_merchant_store`（UNIQUE merchant_no，一主体一行） | `usr_store` 一主体 N 行 | **改名 + 扩列 + 去唯一键** |
| `usr_merchant.service_scope` / `service_city_code` | 下沉到门店 | **移列** |
| `usr_merchant_community.merchant_no` | 改挂 `store_no` | **换外键** |
| （无） | `service_geo` 地图区域 | **加列** |
| `usr_merchant.store_code` | 下沉到门店 | **移列** |

```sql
ALTER TABLE usr_merchant_store RENAME TO usr_store;
ALTER TABLE usr_store
  ADD COLUMN store_no    VARCHAR(64) NOT NULL COMMENT '门店业务键',
  ADD COLUMN name        VARCHAR(128) NULL COMMENT '门店名，可与主体名不同（张记粮油·文三路店）',
  ADD COLUMN is_default  TINYINT NOT NULL DEFAULT 0 COMMENT '默认店，一主体恰好一个，删不掉',
  ADD COLUMN status      VARCHAR(16) NOT NULL DEFAULT 'ACTIVE' COMMENT 'ACTIVE/SUSPENDED/READONLY(Plan降级)',
  ADD COLUMN store_code  VARCHAR(64) NULL,
  ADD COLUMN service_scope VARCHAR(16) NOT NULL DEFAULT 'COMMUNITY'
      COMMENT 'COMMUNITY/GEO/CITY/PLATFORM（ADR-009 待修订为四形态）',
  ADD COLUMN service_city_code VARCHAR(16) NULL,
  ADD COLUMN service_geo  TEXT NULL
      COMMENT 'JSON：{type:CIRCLE,lat,lng,radius} 或 {type:POLYGON,points[]}。与列举小区可并存';
-- 去掉一主体一行的限制
ALTER TABLE usr_store DROP INDEX uk_store_merchant;
ALTER TABLE usr_store ADD UNIQUE KEY uk_store_no (store_no);
-- 一主体恰好一个默认店：用生成列 + 唯一键兜底不了（默认店是 1 不是 NULL），
-- 由应用层保证，并配一条守卫测试
ALTER TABLE usr_store ADD KEY idx_merchant_default (merchant_no, is_default);
```

**迁移顺序（不能颠倒）**：

1. 补 `store_no`（为每行生成）、`is_default=1`、`name` 取主体名
2. 把 `usr_merchant.service_scope` / `service_city_code` / `store_code` **拷到门店**
3. `usr_merchant_community` 加 `store_no`，按"该主体的默认门店"回填
4. 代码读取全部切到门店
5. **最后**才 DROP 主体上那几列

> 第 5 步与第 1–4 步**必须分两个发布**：同一个迁移里删列，
> 回滚时数据已经没了。V42 消 `address` 重复时踩的就是这条顺序。

### 2.3 商品与门店

| 现状 | 目标 | 动作 |
|---|---|---|
| `prd_goods.merchant_no` | 不变（目录挂主体） | — |
| `prd_goods.on_sale` | 语义变为"主体级默认" | 保留 |
| `prd_sku.stock` | 语义变为"主体级总量"或废弃 | **见下** |
| `prd_community_pool` | **被 `prd_store_goods` 取代** | 迁移后废弃 |
| （无） | `prd_store_goods` 选品 | **新建** |
| （无） | `prd_store_stock` 库存 | **新建** |

```sql
-- 选品：这家店卖不卖这款（SPU 级）
CREATE TABLE prd_store_goods (
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  store_no    VARCHAR(64) NOT NULL,
  goods_no    VARCHAR(64) NOT NULL,
  merchant_no VARCHAR(64) NOT NULL COMMENT '冗余，避免查选品时回表取主体',
  on_sale     TINYINT NOT NULL DEFAULT 0,
  sort_weight INT     NOT NULL DEFAULT 0,
  ...
  -- **没有行 = 这家店不卖这款**，与"有行但下架""在架但库存0"是三种不同的状态
  UNIQUE KEY uk_store_goods (store_no, goods_no),
  KEY idx_store_onsale (store_no, on_sale)
);

-- 库存：这家店这个规格有几件（SKU 级）
CREATE TABLE prd_store_stock (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  store_no     VARCHAR(64) NOT NULL,
  sku_no       VARCHAR(64) NOT NULL,
  goods_no     VARCHAR(64) NOT NULL,
  stock        INT NOT NULL DEFAULT 0,
  locked_stock INT NOT NULL DEFAULT 0,
  ...
  UNIQUE KEY uk_store_sku (store_no, sku_no)
);
```

**`prd_community_pool` 怎么退场**：它现在承担"哪些商品在哪个社区可见"，
而新模型里这件事由 **门店选品 × 门店服务区域** 推出来。

| 步 | 动作 |
|---|---|
| 1 | 建 `prd_store_goods`，从 `prd_community_pool` + `prd_goods.on_sale` 回填 |
| 2 | C 端可见性查询改为 `prd_store_goods ⋈ usr_store 服务区域` |
| 3 | 双跑一段：两条路径结果比对，**不一致就告警** |
| 4 | 确认一致后废弃 `prd_community_pool` |

> 第 3 步不能省。可见性是**静默失效**的那类逻辑——算错了不报错，
> 只是商品消失，而商家会以为是没人买。

**`prd_sku.stock` 的处置**：一期单店时它就是那家店的库存。
迁移后由 `prd_store_stock` 承担，`prd_sku.stock` **保留但停止写入**，
一个发布周期后再删——留一个回滚余地。

### 2.5 区域与开城

| 现状 | 目标 | 动作 |
|---|---|---|
| `cmt_community.status` OPEN/CLOSED | 不变，但改为**入驻自动开** | 逻辑变更，无 DDL |
| `cmt_community.city_code` | 上挂到 `cmt_region` | **加外键列** |
| （无） | `cmt_region` 城市/片区开放状态 | **新建** |

```sql
CREATE TABLE cmt_region (
  region_no   VARCHAR(64) NOT NULL,
  parent_no   VARCHAR(64) NULL COMMENT '城市 → 片区，两级够用',
  name        VARCHAR(64) NOT NULL,
  level       VARCHAR(16) NOT NULL COMMENT 'CITY / DISTRICT',
  status      VARCHAR(16) NOT NULL DEFAULT 'CLOSED' COMMENT '开城由入驻驱动，默认关',
  opened_at   BIGINT NULL,
  ...
  UNIQUE KEY uk_region_no (region_no)
);
ALTER TABLE cmt_community ADD COLUMN region_no VARCHAR(64) NULL;
```

**开城触发**：某社区首个商家入驻通过 → 置该社区 `OPEN`，
其所属 region 若为 CLOSED 一并置 OPEN。

**关城的硬约束**：区域内**有未完成订单时不能关**——
与门店只读同一条理由，受损的是买家。

### 2.6 增长：分享 · 曝光 · 留存

五张全新表，互不复用现有表（理由见 §三）：

```sql
mkt_share_link    share_code / merchant_no / store_no / goods_no? / shared_by / channel / expire_at
mkt_share_click   share_code / user_no? / device_fp / valid / invalid_reason / score / created_at
mkt_exposure_pool store_no / goods_no / score / last_click_at / expire_at / status
usr_store_follow  user_no / store_no / source(SHARE|ORDER|FAVORITE) / last_seen_at / muted
mkt_store_feed    store_no / type(NEW_GOODS|PROMOTION|GROUP_BUY|ANNOUNCEMENT) / ref_no / created_at
```

**`mkt_share_click` 要记无效点击**（`valid=0` + `invalid_reason`）：
商家问「我分享了怎么没效果」时，后台要能答"其中 12 次是老客、3 次是你自己点的"。
只记有效的，这个问题就只能靠猜。

### 2.7 权益

| 现状 | 目标 | 动作 |
|---|---|---|
| `mkt_coupon.merchant_no` | 不变 —— **它本来就是主体级，多门店自动通用** | — |
| （无） | `mkt_coupon.store_scope` 可选收窄 | **加列** |
| `pts_*` 挂 `merchant_no` | 不变 | — |
| `mkt_attribution.source` | 加 `MERCHANT_EARNED` | **扩取值** |
| 积分流水 / 券领用核销 | 加 `store_no` 归因 | **加列** |

```sql
ALTER TABLE mkt_coupon ADD COLUMN store_scope TEXT NULL
  COMMENT 'JSON 数组；空 = 主体下全部门店通用（默认）。用于新店开业活动';
```

**券的门店收窄默认必须是"通用"**：绝大多数券没有门店区分，
做成必填等于让每个商家每次发券都多一次决策。

**积分流水的 `store_no` 要一期就记**：补记历史是不可能的，
当时不记，将来做跨店对比就永远缺一段。

## 三、不复用现有表的三处，及理由

| 想复用的 | 为什么不 |
|---|---|
| `mkt_attribution` 记分享点击 | 语义不同：归因答"这用户属于谁"（30 天窗口、一人一条有效），曝光答"这店最近带来多少人"。**合并会让归因窗口被点击反复刷新** |
| `usr_store_favorite` 当作 follow | 收藏是**主动**行为，follow 是**逛过即建立**。混用会让"我没收藏怎么出现在我的列表里"变成一个投诉 |
| `prd_community_pool` 改造成选品表 | 它的键是 `(community_no, goods_no)`，而选品的键是 `(store_no, goods_no)`。改键等于重建，不如新建 + 双跑比对 |

## 五、风险与守卫

| 风险 | 守卫 |
|---|---|
| 可见性静默失效（商品消失，不报错） | M3 双跑比对 + 告警；上线后保留一个发布周期 |
| 越权（切店后权限没变窄） | 7 条作用域测试（[方案 §4.3](./增值服务-多门店与子账号-方案.md)） |
| 一主体多个默认店 | 应用层保证 + 守卫测试（唯一键做不到"恰好一个 1"） |
| 降级把未完成订单冻住 | 只读态**允许核销**的测试 |
| 迁移顺序颠倒导致丢数据 | 「先补数据再改结构」；DROP 单独发布 |
| 迁移版本号撞号 | 已有 `SchemaDriftTest.migrationVersionsAreUnique` |
| **表改名后三个迁移重放器各自失明** | M1 时踩到：`gen-test-schema.py`、`SchemaDriftTest`、`scripts/lib/ddl.mjs` **都不认 `RENAME TO`**，症状各不相同（schema 建不起来 / 报「表尚未建立」/ 报「实体多出一堆字段」），三份已全部补上 |
| **一条 ALTER 加多列被静默截断** | 生成器现在直接报错；仓库惯例是一条 ALTER 一列 |
| **H2 约束名全库唯一** | 与 MySQL 不同，撞名只有测试库会报 —— 新表的约束名要带表前缀 |
| **生成器不重放 `MODIFY COLUMN`** | V46 把 `user_no` 改成可空，测试库仍是 NOT NULL —— 真库能插、测试插不进。已补（这是它第五处漏掉的迁移动作） |
