# 餐饮系统与项目底座兼容对齐

> 状态：待评审 · 2026-10-19 · 基于现有Java实体、认证及控制器核验；本轮仅修订设计，未修改核心代码。
> 适用：[领域对象](./餐饮系统-领域对象与设计总览.md)、[数据库](./餐饮系统-数据库设计.md)、[API](./餐饮系统-API设计.md)。

## 一、结论

餐饮独立项目必须复用项目业务身份与基础协议。独立部署仅改变调用位置，不新增餐饮账号、主体、商户、门店、营业时间或一套认证体系。此前73表及91端点为业务候选设计，本轮修正与底座不一致处，不能按旧草案直接实施。

## 二、账号、主体、商户、门店的含义

| 概念 | 当前落点 | 餐饮使用规则 |
|---|---|---|
| 消费者账号 | usr_account及CONSUMER realm | 顾客身份，不以服务员账号或老板账号伪装买家 |
| 商家账号 | mch_account及MERCHANT realm | 复用现有登录和老板/员工身份解析，不建fnb_user |
| 经营主体 | mch_entity.entity_no | 商品归属、经营授权和交易主体，不是tenant_no |
| 门店 | mch_store.store_no及entity_no | 桌台、工位、餐牌适用、营业流程的范围；不建fnb_store |
| 收款商户 | mch_payment_merchant及门店收款配置服务 | 支付通道进件和收款归属；不等同entity_no或账号 |
| 员工门店权限 | 现有身份解析、门店授权及BizContext | 身份权限通过现有服务取得；厨房工位为附加资源范围 |
| 平台运营账号 | OPERATOR realm | 排障诊断不自动获得商家收退款权限 |

历史文档中的usr_merchant/usr_store等命名不作为新DDL依据；以当前mch实体及迁移为准。BizContext.merchantNo和部分MerchantQueryPort参数为遗留命名，代表当前经营侧主体上下文；适配层显式映射，不再新建merchant_no身份层。

C、B、平台分别沿用ctk_、btk_、otk_凭据池；令牌前缀和realm常量引用现有定义，不在餐饮包复制。设备短会话另经受控设备鉴权合同，不允许设备令牌冒充员工或消费账号。

门店当前归属与历史订单主体快照分别处理。变更门店主体/收款配置时，餐饮不能按今天的归属重算旧单税务、应收、退款或日结；有活动台账/未知资金时先按既有变更流程检查迁移影响，新旧主体不能合并结账。

## 三、营业时间与餐饮营业日

| 信息 | 权威来源 | 本轮修订 |
|---|---|---|
| 门店营业时间文案 | mch_store.openHours；MerchantStoreService.profile/save | 直接复用；餐饮不另存可编辑openHours |
| 营业中展示 | shop-base OpenHours | 复用已有单时段/跨午夜解析；无法识别返回null，不伪装为已营业或全天营业 |
| 门店状态 | MchStore ACTIVE/READONLY/SUSPENDED | 以现有能力守卫为准，餐饮不能解除平台暂停；存量履约仍按原权限处理 |
| 餐段、临时接单例外 | fnb_service_calendar及菜单schedule/exception | 原fnb_business_calendar更名并限于餐饮接单，不接管全局营业日历 |
| 营业日核算切点 | fnb_store_policy.cutover_minute/timezone | 用于日结归期，不是开关门时间；时区不是宣称mch_store已有时区列 |
| 多时段/节假日全局营业时间 | 当前openHours文本不足以完整表达 | 如需统一硬校验，给商户域增加通用结构化营业服务，所有入口共用；不由餐饮私有表成为第二真源 |

最终可接单集合为门店基础状态与合法营业约束、餐牌时段、餐饮接单策略、商品上架可售的交集。OpenHours目前按系统默认时区解析，跨时区餐饮不能直接传餐饮时区假定已受支持；应给共享解析补明确时区合同及回归，未就绪时限制能力。

## 四、实体、权限及API风格

- 实体沿用BaseEntity：id自增且不对外、tenantNo一期MAIN、审计、version、deleted；业务号走BizKey。entity_no单独保存业务主体范围，不冒充租户隔离。事实和签核表虽保留公共字段，业务上禁止随意归档或覆盖。
- createdBy/updatedBy沿公共填充；服务员、老板和平台真实操作身份从认证取得。需要跨realm审计时保存身份类别或公共审计引用，不把客户端operatorNo当可信操作人。
- B端沿BizContextFilter、BizContext、BizPerms和现有@perm.canBiz风格。商家业务方法传入明确主体和门店；不能只检查登录，不检查对象归属。权限新码登记既有权限种子、端点映射及前端共享契约，不另建角色库。
- X-Store-No是既有经营上下文；其越权值可能回落默认门店。餐饮显式path/body目标须再校验一致性并拒绝不匹配，禁止默默写入回落店。跨主体列表不能用门店当前归属推导历史成交主体。
- 沿ApiResult(code,msg,data)、PageData(records,total,page,size)、AppException/ErrorCode和响应包装；不引入独立data/requestId外壳或强制全项目金额字符串化。普通分页沿现有page/size，确需游标的设备同步作为专用增量合同。
- API DTO用业务号camelCase，表字段snake_case，常量沿共享取值域；不暴露BaseEntity.id。商品属性值、订单行物理ID只在内部适配及关系表关联，外部使用餐饮源行号。
- 归档沿archive/unarchive语义，购物车草稿移除改为POST :archive；正式订单取消/退餐不借归档改变资金事实。时间持久化沿现有配置核验，不新增另一套全局时区策略。

| 依据代码 | 核验内容 |

后续实施验收：多主体切店、员工跨店拒绝、无权门店header回落与显式path不匹配、平台与顾客令牌越界、跨夜营业/无法解析/系统时区差异、门店暂停与存量交付、门店变更主体后旧单退款日结不漂移、统一响应分页及公共实体填充、餐饮移除后零售不回归。以上为待实施验收要求，不代表本轮已运行这些业务测试。


## 六、与core零售代码组织统一

经直接核验shop-core/product的GoodsServiceImpl、ProductMappers和api/dto/entity/service目录，餐饮采用同样的ServiceImpl直调本域Mapper方式。前版强制Repository与独立domain/application/infrastructure/web模块不再采用；模块收敛为food-api、food-core、food-channel、food-server。独立业务概念不强制建立纯DDD聚合及重复转换对象。复杂状态沿core现有policy/statemachine/assembler方式按需拆分。最终类清单以[代码结构清单](./餐饮系统-代码结构与对象清单.md)为准。


## 七、统一规范来源及命名修订

包规划及类名以[平台Java规范](../../../.claude/skills/ai-shop-dev-standards/references/java.md) §七为唯一规则入口。餐饮清单改为资源级Controller、能力级Service；跨域接口统一spi命名，实现在.port，协议client与实现区分。Entity完整驼峰保留Fnb前缀，Mapper集合统一FoodMappers，报表沿原JdbcClient/DAO栈。机器清单给出完整包名与类名；不把接口编号或统一Food/Core前缀作为业务命名。旧清单的宽泛业务组Controller和私有Port命名均不再采用。
