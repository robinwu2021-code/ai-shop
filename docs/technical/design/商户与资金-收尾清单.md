### 2.4 C2 核对结果（2026-08-13，已修正 · V93）

对着微信支付合作伙伴文档中心核完，**两条都错，且比预判更严重** ——
不是「值选得不合适」，是**描述的机制不存在**。

| 位置 | 原值 | 实际 |
|---|---|---|
| `INDIVIDUAL.wechat_code` | `'SMALL'` | **取值域里根本没有这个值**。特约商户进件的 `subject_type` 只有 `INDIVIDUAL / ENTERPRISE / GOVERNMENT / INSTITUTIONS / OTHERS` 五个 → 改为 `'INDIVIDUAL'` |
| `settle_account_type` | `'PERSONAL_OPENID'` | **微信不结算到 openid**。小微的结算账户是 `bank_account_type=BANK_ACCOUNT_TYPE_PERSONAL` + 卡号/开户行/户名，即**个人银行卡** → 改为 `'PERSONAL_BANK_CARD'` |

**还查出了第三件、原先根本没意识到的事**：

> 特约商户进件文档原话：**本接口不支持进件个体小微商户**。
> 小微走的是**另一个接口**（小微商户进件），`subject_type` 只能是 `SUBJECT_TYPE_MICRO`。

也就是说 `sys_legal_form` 把三档主体当成「同一个接口的三个参数值」，
而实际是**两个接口**。写网关的人照着个体户那条路径调，小微那一档会整档失败。
「走哪个接口」暂记在 `remark`（C1 联调时提升为字段 —— 此刻加一个没人读的列，
就是又一次「闸门写好了但数据源没接」）。

**用户可见的后果**：B 端入驻页对小微显示「微信零钱（个人）」，
商家据此以为不用提供银行卡 —— 而进件时那三个字段是必填的。
三语文案已改为「本人银行卡」。

**加了守卫** `packages/shared/tests/channel-subject-code.test.ts` ——
`wechat_code` / `settle_account_type` 只能取通道文档里真实存在的值。
（已验证：撤掉 V93 的重放 → 变红报 `INDIVIDUAL → 'SMALL'`。）

### 3.3 三条反复出现的教训

**① 校验不能早于能满足它的 UI。**
入驻执照校验第一版硬拦，当场打断 24 个测试 fixture ——
b-app 还没开始传那个字段，**拦的不是坏商家，是所有人**。

**② 拦截不能早于存量分类。**
「自然人 × 归集 → 建单即拒」照做会让 99 家存量当场停业。
改成只在写入点拦，存量另行处置。

**③ 新增一个维度时，既有 fixture 会默默落在默认值上。**
本轮三次同型：`PointsSubsidy` 没设 `payChannel`、`M5AfterSale` 没设 `funds_mode`、
`ModeRisk` 的 fixture 没设经营模式。
**症状都是「本该变红却全绿」** —— 只看到绿就往下走，新校验就是装饰品。

### 3.4 之二 · 全仓改名的三个坑（2026-08-13 一次踩全）

把 `PERSONAL_OPENID` 改成 `PERSONAL_BANK_CARD` 时，一条 `grep -rl | xargs sed` 连踩三处：

**① sed 改到了做这次改名的那条迁移自己。**
`UPDATE ... SET x='新' WHERE x='旧'` 变成了 `WHERE x='新'` —— **A=A 的空转，不报错**。
改名脚本必须排除本次迁移。

**② sed 改到了已应用的迁移（V2）。**
Flyway 校验和当场失配，**共享库下次启动直接起不来**，而且是两个会话一起。
差一点提交出去。已复原并核对校验和（`1192589979` 一致）。

> 规矩：**已应用的迁移一个字都不能改**，修正一律新开一条。
> V2 至今写着 `'SMALL'`，这不是漏改，是对的。

**③ sed 改到了测试 fixture 的 INSERT 行。**
后果最隐蔽：fixture 直接从「正确值」开始，V93 的重放成了空转，
**守卫因此永远绿 —— 包括我故意撤掉修正的那次**。
fixture 的 INSERT 必须与 V2 逐字一致，让它复现「先错、后被修正」的真实过程。

三条的共同形状：**sed 不认得「哪些文件是历史、哪些是当下」**。
而三条里有两条的表现都是「测试更绿了」。

### 3.4 「存量默认最严」是生产事故

### 3.6 定时任务的分布式锁（2026-08-13 已落地）

四个 `@Scheduled` 全部挂上 `@SchedulerLock`，锁表 `shedlock` 由 V91 建。

**为什么不等扩容时再补**：`@Profile("worker")` 只挡住「api 实例也在跑」，
挡不住 worker 自己起两份 —— 而**扩容是运维在容量吃紧时做的动作，不会回来问代码准备好没有**。

| 任务 | 锁名 | lockAtMostFor | 取这个值的理由 |
|---|---|---|---|
| `PointsActivateJob#activate` | `points-activate` | 30M | 日结，锁久无害 |
| `PointsActivateJob#expire` | `points-expire` | 30M | **必须与 activate 分开命名** —— 两者只错开 15 分钟，共用一把锁会让 expire 被静默跳过一整天 |
| `ReconScanJob#scan` | `recon-scan` | **9M** | 10 分钟一次，重叠窗口最大；**小于间隔**，真卡死时下一轮能接手 |
| `QualificationExpiryJob#scan` | `qualification-expiry` | 30M | 重复执行幂等，但会**重复触达商家** —— 通知发两遍，商家以为出了两次问题 |

锁存在库里而不是 Redis（本仓已有 Redis）：**锁和被锁的数据在同一个事务边界内** ——
库挂了两者一起不可用，不会出现「锁还在、库没了」这种半可用状态下的重复执行。
`usingDbTime()` 让过期判断走数据库时钟，否则两台机器差几秒就可能同时认为锁已过期。

**加了守卫**：`ArchitectureTest#everyScheduledMethodMustBeLocked` ——
新增 `@Scheduled` 不带锁直接构建失败。这条不能靠人记得，
**加任务的人正在想的是业务，不是部署形态**。（已验证：注释掉一个锁 → 变红。）

## 五、积分恒等式自检（2026-08-13 补）

[积分域-完整方案](./积分域-完整方案.md) §恒等式写着「对账任务**每日校验**。
恒等式是这套设计**唯一的自检手段**，违反即告警」——**而那个任务一直不存在**。
两边的数只在 ops 看板上并排显示，没有任何人比较它们。

**为什么现在才做得成**：在入账（发分收费）与出账（兑付、到期）两侧接上之前，
等式两边恒等于 0 —— 校验了也看不出任何问题。
那正是这套账最危险的一段时间：**看着挺平，因为根本没有数**。

### 等式里必须带 PENDING 项，否则天天误报

```
池子余额 == 流通中积分 × 汇率 + Σ(PENDING 的 USE 金额)
```

下单扣分之后、兑付成立之前，那笔钱**已经不在用户账上、也还没付给收单方** ——
它正躺在池子里等着。漏掉这一项，等式会在**每个未结算订单**上都差一截，
而**告警一旦天天响，就等于没有告警**。

（写测试时第一版 fixture 漏了「发分入账」这一步 —— 测试当场红了，而它红得对：
**没发过分就抵扣**这个状态在真实链路里不存在。）

### 排在转正与到期之后

`00:05` 转正 → `00:20` 到期清零 → **`00:40` 自检**。
那两个任务都会同时改动等式两边，查在中间会读到正在变化的快照，
报出来的失衡是假的 —— **而假告警比没有告警更糟**，
它会让真的那次被当成又一次误报。

### 按市场分别查，不合成总数

账面上一个总数是平的，而两个市场可能一个溢一个空 —— 合起来正好抵消，
那是最难发现的一种失衡。同理见 `overview` 里按通道分账本。

### 平的时候也要留记录

`JobSupport` 的运行记录里要看得出「今天查过了」——
返回 null 的话，「查了都平」与「任务没跑」在记录上长得一模一样，
而这正是本轮反复踩到的那个形状。
