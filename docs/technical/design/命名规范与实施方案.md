# 命名规范与实施方案

> 2026-08-10 · 前置：[枚举领域清单](枚举领域清单.md) 列出了 121 个枚举的具体缺陷。
> 这一份先 review 现有的规范体系为什么没拦住它们，再给出**规定性**的规范，最后给方案。

---

# 第一部分 · Review：现有规范为什么没起作用

现有体系有三件东西：`docs/requirements/项目词典.md`（81 条目 / 12 节）、
它的守卫 `packages/shared/tests/glossary.test.ts`、以及散落在代码注释里的约定。

## R1 · 守卫只覆盖 6.6%

`glossary.test.ts` 的 `MUST_COVER` 是**手工列的 8 个**：

```
OrderStatus · AfterSaleStatus · AfterSaleType · MerchantSubject
MerchantTier · FULFILLMENT · CATEGORY_TYPE · SERVICE_SCOPE
```

端上共 121 个枚举 —— **覆盖率 8/121 = 6.6%**。

且这 8 个的构成暴露了它的生成方式：**全部是已经出过事、事后补进来的**。
这是幸存者偏差 —— 守卫守住的永远是上一次的事故，从不覆盖下一次。

ops-web 的 68 个枚举一个都不在名单里；它们只在「词典里的值是不是编造的」
那一检里被用作**白名单**，也就是说：ops-web 的词汇被当成「事实」接受，
从不被当成「需要符合规范」的对象。

## R2 · 词典是描述性的，不是规定性的 —— 它登记问题，然后问题继续存在

词典「易混淆词」一节里有这么一行：

> `MerchantTier`（规模） vs `MerchantSubject`（主体）…… **平台端把两者写混了**（矩阵 §七之四）

**这个缺陷被写进词典了，然后继续存在。** 我在这一轮的清点里把它当成新发现重新找了一遍。

同样的事发生了第二次：`packages/shared/src/types/index.ts` 里 `MerchantSubject`
的注释白纸黑字写着「**不叫 `SubjectType`**：那个名字在平台端已经是风控主体」——
而 `packages/shared/src/capability/index.ts` 里就有一个 `SubjectType`，
取值与 `MerchantSubject` 逐字相同，**同一个包内**。

> **知识写下来不产生约束力。** 一份记录「现在是错的」的文档，
> 和一份记录「应该是什么」的规范，是两种东西。现在的词典是前者。

第三个证据：词典里那句「`AfterSaleStatus` 三端同名同义，**2026-08 已统一**」——
写下时只对 ops-web 成立，shared 那套（`PENDING`/`AGREED`/`RETURNING`…）
与后端只有一个词重合。**描述性语句会腐烂**，而没有任何机制让它腐烂时报警。

## R3 · 状态词公约事实存在，但零文档

把全部枚举的取值按语义归类，「通过」有 11 个词、「待处理」有 10 个。
但逐个查下去，系统里**已经有一套自洽的公约**：

| 事实上的公约 | 一致性 |
|---|---|
| 审**内容**通过用 `PASSED` | 3/3 |
| 批**申请**通过用 `APPROVED` | 2/2 |
| **申诉**成立用 `UPHELD` | 2/2 |
| 到期 `ENDED` / 关闭 `CLOSED` / 取消 `CANCELLED` | 各 3–4 处一致 |
| 草稿 `DRAFT` ≠ 待处理 `PENDING` | 6/6 |

真正的违规只有 7 处。**这不是混乱，是一套没写下来的规范被执行到了 80%。**
剩下 20% 不是态度问题 —— 新写的人无从知道公约存在，只能猜。

## R4 · 没有根级的命名规范文档

仓库根目录没有 `CLAUDE.md`（只有 `ops-web/` 下有一份自己的）。
词典的「维护约定」共 4 条，其中与命名相关的只有 1 条
（「新概念先定英文名再写代码」）。取值该怎么取词、同一概念跨端如何对齐、
新枚举该登记到哪里 —— 都没有规定。

# 第二部分 · 规范（规定性）

## §A 词典的角色重定义

**词典从「记录现状」改为「规定应然」。** 三条直接后果：

1. 词典里**不再出现缺陷描述**。「平台端把两者写混了」这类句子移出词典，
   进 [枚举领域清单](枚举领域清单.md)。词典只说「应该叫什么」。
2. 词典与代码不一致时，**改代码，不改词典** —— 除非经评审修改规范本身。
   （现状相反：这一轮我三次改词典去追代码。）
3. 词典成为**新增枚举的必经之路**：不在词典里的枚举，守卫直接报错。

## §B 三层结构

| 层 | 内容 | 载体 | 守卫 |
|---|---|---|---|
| **L1 通用状态词表** | 跨领域复用的状态词（下表 13 个） | 词典 §状态词 | 取值用了表外的近义词即报错 |
| **L2 领域概念登记** | 每个概念的权威名 + 权威取值来源 + 消费方 | `enum-registry.ts` | 端上枚举未登记即报错（覆盖率 100%） |
| **L3 易混淆词** | 容易被当成同一件事的两个概念 | 词典 §11（保留，这是现有词典最有价值的部分） | 引用的标识符必须真实存在 |

L1 管**取值**，L2 管**概念与名字**，L3 管**人的误解**。三者不重叠。

## §C L1 · 通用状态词表

任何枚举的取值必须从下表取词。领域特有的状态（`IN_TRANSIT`、`QUOTING`、
`SPLITTING`）不在表内，**允许但必须在 L2 登记时申报**。

| 语义 | 用词 | 说明 |
|---|---|---|
| 未提交 | `DRAFT` | 作者还在编辑，没人在等它 |
| 已提交待处理 | `PENDING` | 已进入他人的待办 |
| 处理中 | `PROCESSING` | 有人接手了但没完 |
| 内容审核通过 | `PASSED` | 审的是**内容**（评价、帖子、装修） |
| 申请审批通过 | `APPROVED` | 批的是**申请**（入驻、提现） |
| 申诉成立 | `UPHELD` | 复核推翻了原结论 |
| 拒绝 / 驳回 / 申诉不成立 | `REJECTED` | 统一用它，不用 `DISMISSED`/`DENIED` |
| 生效中（主体、券、卡、点位） | `ACTIVE` | 静态的「可用」 |
| 进行中（活动、团、批次） | `RUNNING` | 有起止时间的「在跑」 |
| 到期结束 | `ENDED` | 时间到了，非人为 |
| 单据关闭 | `CLOSED` | 人为终结，无对错判定 |
| 主动取消 | `CANCELLED` | 发起方撤回 |
| 暂停（可恢复） | `PAUSED` | |
| 封禁（惩罚性） | `SUSPENDED` | |
| 冻结（风控 / 资金） | `FROZEN` | |
| 失败（系统性） | `FAILED` | 与 `REJECTED` 区别：没有人做决定 |

> **为什么 `PASSED` 与 `APPROVED` 都保留**：审内容与批申请是两类不同的动作 ——
> 前者判断合规、可批量、可撤销；后者授予资格、有主体、有资金后果。
> 强行合并会丢掉这个区别。这正是「不同概念不许共用一个词」的正向应用。

## §D 命名规则

1. **一个领域概念只能有一个词；一个词只能指一个领域概念。**
   跨端、跨模块、跨语言（TS/Java/SQL）都算同一个系统。
2. **概念名不含所在层的信息。** 不允许靠「它在 ops-web 所以是平台的那个」区分 ——
   读代码的人没有义务先知道自己在哪一层。同名不同义一律改名，
   由更窄的一方加限定词（`PlatformSlotType` 而不是 `CampaignType`）。
3. **取值域的真源在后端**（Java 常量 / DDL / 字典表）。端上不得自行定义 wire 取值。
4. **带业务规则的取值域走字典下发**，不硬编码。判据：库里有没有一张表，
   其中除了码还有别的列（`enabled`、`sort`、通道码、费率）—— 有就是字典。
5. **禁止在 interface 里内联字面量联合**。每个枚举一个具名声明。
6. **后端未实现的取值不与已实现的混在一处**，单列 `PLANNED_*` 白名单。
7. **废弃的名字用 `@deprecated` 保留一个版本**，不直接删 —— 但必须有删除期限。
8. **新增枚举必须先在 L2 登记再写代码。** 登记时回答四个问题：
   概念是什么 / 权威取值在哪 / 谁消费 / 需不需要文案。

## §E 守卫（三条，对应三层）

| # | 检查 | 现状 |
|---|---|---|
| G1 | 端上每个枚举都在 L2 登记（覆盖率 100%） | ❌ 现在 6.6% |
| G2 | 取值用词在 L1 表内，或在 L2 申报为领域特有 | ❌ 不存在 |
| G3 | 同名枚举跨端取值逐字相同；不同概念不得同名 | ⚠️ 部分（`type-alignment.test.ts` 有基线，但靠豁免名单） |

> **G1 是关键的那一条。** 它把「新增一个枚举」从零成本变成「必须登记」，
> 这是唯一能阻止 121 变成 150 的机制。其余两条是在此基础上的检查。

# 第三部分 · 实施方案

## 排序原则

**先建立约束，再清理存量。** 反过来做的话，清理完成的当天就开始重新积累 ——
这一轮已经验证过：`MerchantSubject` 的注释就是「清理后留下的说明」，
它没能阻止同一个包内再出一个 `SubjectType`。

## P0 · 让规范可执行（不改任何业务代码）

| # | 事项 | 验收 |
|---|---|---|
| P0.1 | 建 `enum-registry.ts`，把现有 121 个**原样**登记进去 | 登记内容与代码逐字节一致 |
| P0.2 | 落 G1：端上枚举未登记即报错 | 新增一个未登记枚举，`npm test` 变红 |
| P0.3 | 词典 §状态词 写入 L1 表；落 G2 | 把某个 `PASSED` 改成 `ACCEPTED`，测试变红 |
| P0.4 | 词典移除缺陷描述，迁进[领域清单](枚举领域清单.md) | 词典里不再有「写混了」这类句子 |

**P0.1 只登记不改名。** 登记表此刻是一份「现状快照 + 每条的判定」，
判定字段取值：`OK` / `RENAME` / `MERGE` / `TO_DICT` / `PLANNED`。
这样 121 个缺陷从「散在文档里」变成「代码里的 121 条待办」，可以被统计、被 CI 盯着收敛。

## P1 · 零风险清理（纯机械，无行为变化）

| # | 事项 | 风险 |
|---|---|---|
| P1.1 | 删 `shared/capability` 的 `SubjectType`，并入 `MerchantSubject` | 无（同包重复） |
| P1.2 | 24 个内联无主具名化 | 无 |
| P1.3 | `PickupType` → `PickupPointType` | 无（纯改名） |
| P1.4 | 给对账工具的 `FIELDS` 表加完整性守卫 | 无 —— 这是它的第一个已知盲区 |

## P2 · 现在就在坏的（要浏览器实测）

| # | 事项 | 症状 |
|---|---|---|
| P2.1 | `FulfillType` 的 `SERVICE`：后端没有这个履约值 | ops-web 按它筛必然是空 |
| P2.2 | `FulfillType` → `FulfillmentType`，与 shared 统一 | 异名同义 |

## P3 · 状态词归一（7 处，逐条改）

`BlacklistAppealStatus.ACCEPTED` → `UPHELD` ·
`AppealStatus.DISMISSED` → `REJECTED` ·
`GoodsStatus.AUDITING` → `PENDING` ·
`GroupStatus.PENDING_AUDIT` → `PENDING` ·
`PostStatus.OFFLINE` / `QuestionStatus.HIDDEN` 二选一 ·
`CampaignStatus.RUNNING` vs `CouponStatus.ACTIVE` 二选一 ·
`OPEN`（4 处）判定是否并入 `PENDING`

> 这些多数是 ops-web 独有、后端未实现的枚举 —— **改名成本最低的时刻就是现在**，
> 等后端实现了就要连数据一起迁。

## P4 · 需要业务确认后再动

| # | 事项 | 待确认 |
|---|---|---|
| P4.1 | `CampaignType` 拆名 | 店铺活动与平台场次要不要合并成一张表 |
| P4.2 | 主体类型五处收敛 + 走字典 | `sys_legal_form` 的取值域会不会随通道政策变 |
| P4.3 | `GoodsStatus` / `SkuStatus` | 商品状态挂 SPU 还是 SKU（模型问题，不只是命名） |
| P4.4 | `MerchantStatus` / `ApplyStatus` 改名 | 影响 B 端首页判断，需回归入驻全流程 |

## P5 · 存量收敛

ops-web 55 个独有枚举逐个判定 `OK/RENAME/PLANNED/DELETE`。
量最大但多数机械，且 P0.2 的守卫会让它们变成一份可统计的待办清单，
可以按模块分批做，不必一次完成。

## 验收方式

每一批都跑：单元+集成 · E2E-2 · shared · ops-web 四层，**外加浏览器实测受影响页面**。

> 这一轮的六个 bug 加那个 join 键错误，**没有一个是被四层测试发现的**。
> 这不是测试写得不好 —— 是这类缺陷（取值对不上、名字指错东西）的症状
> 恰好是「接口 200、页面空白」，而所有测试都在断言自己那一侧的形状。

## 需要确认的

1. **P0.1 的登记表要不要包含 ops-web 的 68 个？** 包含则覆盖率真实但表很大；
   不包含则 G1 守不住最大的那一块。我倾向包含。
2. **P3 的状态词改名，要不要等后端实现再做？** 我倾向现在做 —— 现在只改端上代码，
   等后端实现了就要连数据迁移一起。
3. **词典改成规定性之后，谁有权改它？** 建议：改词典等同于改规范，需要评审；
   而改代码去符合词典不需要。这个不对称是规范能生效的前提。
