状态：草稿（待确认）

## 0. 先说结论

对标淘宝/京东后，本页缺的**不是区块，是内容**。现行版面（重排 v2）已经有
主图 → 价格 → 标题卖点 → 领券 → 规格 → 评价 → 参数 → 图文 → 商家 → 底栏，
位置和顺序都对得上友商。可线上一查：

| 事实 | 数 |
|---|---|
| `prd_goods` 在售商品 | 3 件（柠檬 / 阳光玫瑰青提 / 香梨） |
| `detail`（图文正文）非空 | **0** |
| `detail_images`（详情长图）非空 | **0** |
| 主图张数 | 每件 **1** 张 |
| `subtitle`（卖点）非空 | 2 |
| `prd_spu_std` 标准库 | 311 条，**无 detail、无参数字段** |
| 这三件的类目 CAT120 上平台配的 PROP 参数维度 | **1 个**（产地） |
| `rvw_review` / `cnt_question` / `cnt_post` / `cnt_material` | 0 / 0 / 0 / 0 |

所以：**参数区最多只能出一行，图文区整块被 `v-if` 隐掉，评价区只有一句空文案。**
把版面再堆厚一层，线上看到的仍是同一屏。

本方案因此分两半：**供给侧**（让现有区块有东西，批 1）与**深度侧**（版面加厚，批 2–4），
顺序不能反。

## 1. 淘宝/京东的详情页拆开是什么

| 友商区块 | 内容从哪来 | 本项目 |
|---|---|---|
| 主图 5–9 张 + 主图视频 | 商家上传，类目有张数下限 | 上限 7 张（`PHOTO_LIMIT`），**实际 1 张**；视频无通道 |
| 标题 + 卖点短句 | 商家 | 有（`title` / `subtitle`） |
| 价格 / 划线价 / 券后价 | 系统 | 有，且券与活动已合流 |
| **服务承诺条**（7 天无理由 / 正品 / 极速退） | **平台规则 + 商家资质**，非自由文本 | **没有** |
| **结构化参数表**（前几条 + 「全部参数」抽屉） | 平台类目模板 + 商家填值 | 容器有（`params`），模板几乎空 |
| **评价区**：评分分布、标签筛选、有图优先、追评 | 顾客 | 只有「全量倒序列表」 |
| **问答**「大家还问」 | 顾客提问 + 商家答 | 模型齐（`cnt_question` 带 answer），**无 `/mp` 端点** |
| 图文详情长图 | 商家（多为设计稿） | 通道齐（`detail` 2000 字纯文本 + 10 张长图），**全空** |
| 推荐位（同店热销 / 看了又看） | 系统 | 没有 |

**明确不做**（写在这里，免得下次又当待办捡起来）：
主图视频（无转码与流量预算，`nic-tx` 的账刚出过事）、富文本编辑器（B 端店主用 App，
长图通道已覆盖设计稿场景）、直播与买家秀。

## 2. 供给侧：内容从哪来（批 1，方案的重点）

三条路，按「一次投入覆盖多少商品」排序。**A 已拍板本轮不做**，所以本轮的供给侧
只有 B（商家侧生成）与 C（平台类目模板）—— 覆盖面从「一次管 311 条」退到
「一次管一个类目 + 每件商品点一次」，这是这个决定的代价，写在这里免得以后忘了为什么慢。

### A. 标准库带详情 —— **暂不处理**（2026-09-27 拍板）

`prd_spu_std` 311 条只有 title/subtitle/cover/images/spec_groups/keywords/barcode，
取用标准品也就带不出详情。补它覆盖面最大，但**本轮不动**：不加列、不改 ops-web 的
标准品表单、取用逻辑照旧。

记在这儿是因为它会回来：一旦商品数从 3 件涨到几百件，靠每个店主自己写详情不成立。
到那时再翻这一节。

### B. 商家侧一键生成（**本轮主力**）

`api.mDescribeGoods({imageUrl,title,subtitle,categoryNo})` 已经在用（`genDetail()`）。
加两件：

- 「一键生成参数」：同一个入口按类目 PROP 维度产出候选值，商家点选确认，**不直接落库**。
- 建品页保存时，详情为空给一条**软提示**（不硬拦，`required` 列注释写着本版不校验）；
  B 端商品列表加「缺详情」筛选，让店主看得见欠哪几件。

### C. 平台类目参数模板补齐（**本轮主力**，决定参数区能出几行）

48 个类目配了维度，但生鲜这支只有 1 个 PROP。补的是**顾客买菜真的会看的那几条**：
净重/规格、产地、储存条件、保质期、等级、包装。走已有的
`prd_category_spec` + `prd_category_spec_value`（`usage_type='PROP'`），不新建表。

### D. 顾客侧（评价/问答）

要有单量才有内容。前置是微信支付恢复（95017 申诉中）。届时：订单完成后邀评
（复用已有推送通道），问答等首批评价落地后再开。**这一条不作为批 1 的交付项。**

## 3. 服务承诺条：只留两项，核心是退款时效

拍板：**坏果包赔不做**（2026-09-27）。它要定赔付比例、要判责、要留证据链，是一套业务规则，
不是详情页上一行字；现在写上去等于给一条我们兑不了的承诺。

于是服务条从三项变两项：**「极速退款」+「门店自提免运」**。而「极速退款」这四个字
一旦写在详情页上就是对外承诺，所以它背后的时效必须真的成立 —— 下面是这件事的方案。

### 3.1 现状（先说清楚我们今天承诺不了什么）

1. **`APPLIED` 没有任何超时机制。** 商家不点，售后单永久挂着。全仓只有两个相关定时任务：
   `OrderAutoCloseJob`（关未付款单）与 `RefundRetryJob`（重试卡在 `REFUNDING` 的单），
   **没有一个扫 `APPLIED`**。
2. 极速退**已经有**：`REFUND_ONLY` 且金额 ≤ 阈值时 `apply()` 直接 `doRefund`，
   退货退款不自动（要等收货，这是对的）。
3. **阈值有两份真源且不一致**：后端
   `@Value("${shop.after-sale.instant-threshold-minor:10000}")` = ¥100，线上 yml 没有覆盖；
   前端 `TRADE_RULES.instantRefundMaxMinor = 5000` = ¥50。今天方向偏保守（少承诺），
   但**运营哪天把后端调到 ¥30，前端仍按 ¥50 提示 —— 那一刻页面上就是假承诺**。
4. `AfterSaleVO.updatedAt` 的注释里已经写着「超时自动同意之类的时效规则也以它为基准」——
   基准留好了，规则一直没写。
5. 自营单（`funds_mode=AGGREGATED`）申请后**直接进 `ARBITRATING`**，没有商家这一环。
   时效表必须分两列，否则自营单会被算成「商家超时」。
6. 运营可编辑的退款规则文案 `platform.rule-texts.refund` 早就存在，**C 端一处都没读**；
   线上 `sys_setting` 里 `platform.rule%` 与关单策略**一行都没有**，即全走代码默认值。

### 3.2 时限表（按淘宝/京东的通行口径，数字是配置默认值）

下面的天/小时数是两家公开规则里的通行档位，写进代码时作为**默认值**，运营可调。

| # | 环节 | 时限 | 超时后 | 自营单 |
|---|---|---|---|---|
| T1 | 买家申请 → 商家响应 | **48h** | **系统自动同意**并退款 | 不适用（直接走 T4） |
| T2 | 仅退款且金额 ≤ 阈值 | **即时** | —（本来就没有等待） | 同样即时 |
| T3a | 商家同意 → 买家寄回 | **7 天** | 关闭本次申请 | 同 |
| T3b | 商家签收 → 确认并退款 | **48h** | 系统自动退款 | 同 |
| T4 | 驳回后买家申请平台介入 | **5 个工作日** | **只告警，不自动裁决** | 这是自营单的主路径 |
| — | 退款到账 | 微信 **1–3 个工作日** | 渠道事实，非我们的处理时效 | 同 |

两条口径上的讲究：

- **T4 不自动**。钱的判定不能由定时任务做 —— 超期只产出告警与看板上的超期条数。
  把裁决自动化，等于让平台在没看材料的情况下替一方认赔。
- **到账时效单独一行、单独措辞**。混进「我们的处理时效」里，用户会把微信的 1–3 天
  算到我们头上；淘宝京东也都是分开写的。

### 3.3 实现

**时钟**：新 `AfterSaleTimeoutJob`（放 `trade/job`，与 `OrderAutoCloseJob` 同处），
cron 默认 10 分钟一轮，每轮三件事：

- `APPLIED` 且 `updatedAt` 早于 T1 → **复用已有的 `approve()` 路径**（不另写一套退款逻辑），
  操作人记 `BY_SYSTEM`，时间线写「商家 48 小时未处理，系统自动同意」。
- 已同意待寄回超 T3a → 走 `CLOSED`。
- 已寄回待确认超 T3b → 走 `confirmReturn()` 路径。

三条硬要求：**只碰非自营**（`ARBITRATING` 一律跳过）；更新用状态做 where 条件保证幂等
（同库可能跑着第二个实例）；一律不碰 `REFUNDING` —— 那是 `RefundRetryJob` 的地盘。

**配置**：不塞进 `CloseRuleVO`（那是「关单策略」，页面语义不同）。在平台配置里新开一段
`platform.after-sale-sla`，复用已有的 `readMap` + `intOf` 容器，运营端出一屏「售后时效」。
**极速退阈值从 `@Value` 挪进这一段**，后端与前端都读它（随 `/mp/config` 下发），
消掉 3.1 第 3 条的双真源。

**催办（与 job 同批，不能拖）**：自动同意等于平台替商家把钱退了，而资金上退的是
商家分账（E4 先回退分账）。所以必须在 B 端出「还有 X 小时将自动同意」的催办 ——
`AfterSaleApplied` 事件已经有了，缺的是这条倒计时提醒。没有它，第一个被自动退款的商家
一定会来投诉，而他的投诉是有道理的。

### 3.4 详情页怎么展示

服务条只放**可核验的短语**，细则在抽屉里：

- 「极速退款」**仅当该 SKU 价格 ≤ 阈值时才出现** —— 高于阈值还挂这四个字就是假承诺。
- 「门店自提免运」。
- 点开抽屉 → 3.2 那张时限表。文案主源是已存在却从未用过的
  `platform.rule-texts.refund`，为空时用内置默认表。

## 4. 深度侧

### 批 2 · 详情结构化（改版面）

1. **服务承诺条**（新）：插在配送/领券之后、规格之前。数据来自平台配置 + 门店资质，
   不是商家自由文本。**两项**：极速退款（受阈值约束）、门店自提免运；点开是时限表。
   口径与实现见第 3 节 —— 坏果包赔已拍板不做。
2. **参数区升级**：前 4 条直出 + 「全部参数」抽屉。除商家填的 `params`，把系统已知的
   事实也编进去：净重（`weighed`）、发货/自提（`saleScope`）、限购（`limitPerUser`）、
   到货说明（`arrivalDesc` —— 目前**只在商品卡渲染，详情页一行都没有**）。
3. **图文详情**：仍是纯文本，但约定「空行分段、行尾冒号视为小标题」，由前端排版；
   长图 `mode="widthFix"` 补占位高度避免跳动；`detail_images` 的 URL 进
   `MediaRefSource`（总方案 L216 的欠账，否则被当孤儿图回收）。
4. **死分支清账**：`slots` / `card` / `virtual` / `points` 后端从来不下发，
   页面里四段 `v-if` 是死代码；`cutoff_at` 无写入方（优化清单 L226）。
   建议**删分支 + 在清单里记一行**，而不是留着看起来「功能很多」。

### 批 3 · 口碑（后端先动）

5. `GET /mp/review` 加 `summary`（总分、三维度均分、评分分布、有图条数）与分页
   （现在 `ReviewServiceImpl.list` 返回全量倒序，没有 limit —— 有单量后这是个隐患）；
   筛选：全部 / 有图 / 好评 / 差评。
6. 详情页评价区：头部一行评分与分布，标签筛选，展示三维度分与商家回复时间
   （`repliedAt` 已有，页面没读）。追评不做（模型里没有，不为它加列）。
7. 问答：新开 `/mp/question`（列表）与 `/mp/question`（提问）两个端点 —— 注意这是
   **跨域组合**（内容域 + 商品域），按架构规则放 `shop-app/portal`；
   详情页出「大家还问」3 条 + 「我要问」。运营端回答界面已存在。

### 批 4 · 推荐与锚点

8. 图文之后加「同店热销」+「同类目看了又看」，取本店在售与同类目在售即可，不做算法。
9. sticky 锚点补「服务」「推荐」两栏（现在是 商品·评价·详情）。

## 5. 影响面与登记

- 新增端点 2 个（`/mp/question` 两个方法）→ 走 `biz-endpoint-registration-checklist`
  那套七处登记（判权表 + 两份白名单 + 十份产物）。
- 契约字段新增：`Goods.services[]`、`Review.summary`、`Question`；TS 声明 + JSDoc +
  wire-alignment 都要跟上。
- 迁移 2 张：类目 PROP 种子、（批 3）review 索引。标准库那张不做（见 2.A）。
  售后时效走 `sys_setting` 的一行 JSON，不需要迁移。
- 时效那批还要动：新 job 一个、平台配置新增一段 + 运营端一屏、`/mp/config` 加字段、
  B 端催办一处。极速退阈值挪位置时前端常量要**删掉**而不是留着 ——
  留着就还是两份真源。
  迁移号并行会话常撞，落号前查一次 HEAD。
- 原型：现行 `c-goods-group`（21 屏，在建）要补服务承诺条、参数抽屉、评价头部、
  推荐位四屏，登记进 `prototypes/registry.json` 的 `screens[]` 再跑
  `gen-proto-index.py` 与 `gen-ui-catalog.py`。

## 6. 验收（能证伪的那种）

不用「页面更丰富了」这种判据。

1. 线上三件在售商品，**每件详情正文非空、详情长图 ≥1、参数 ≥4 条** —— 直接查库计数。
2. 参数抽屉里出现的行数 = `params` 条数 + 系统事实条数，两边数字对上。
3. 服务承诺条：关掉平台开关后整条消失（消融）。
4. `arrivalDesc` 撤掉渲染 → 对应 c-app 用例变红。
5. 评价分布：造 5 条不同星级，分布各段计数与造的一致；分页第 2 页不重复第 1 页。
6. 死分支删除后 `vue-tsc` 与 c-app 全量测试仍绿，且 `grep -c "goods.slots"` 为 0。
7. 时效：造一张 `APPLIED` 单，`updated_at` 拨到 **49h** 前跑一轮 job → `REFUNDED` +
   时间线有「系统自动同意」+ 钱真的退了；**拨 47h → 一动不动**。两个方向都要测 ——
   只测前者证明的是「会退」，证明不了「不早退」。
8. 自营单（`AGGREGATED`）拨 49h → **不动**（它在 `ARBITRATING`）。
9. 极速退阈值改一个数，前端服务条的出现边界跟着变（同一份真源的消融）。
10. 把 job 的状态过滤条件撤掉 → 必须有用例变红（它绝不能去动 `REFUNDING` 的单）。

## 7. 排期建议

批 1（供给侧）先做，它不改版面却决定线上看到什么 —— 去掉标准库后它只剩
「类目补 PROP 维度」+「建品页一键生成参数与软提示」两件，比原计划轻；批 2 紧随（版面有内容才值得加厚）；
批 3 等支付恢复、有真实订单再动，否则测得出来的只有空态；批 4 最后。

**第 3 节（退款时效）与批 2 同期**，因为服务条是批 2 的版面项，而那四个字的承诺
必须在它出现在页面上之前就真的成立。其中「B 端催办」与 job 同批，不许拆开。
注意这批做完**只能靠测试证明** —— 线上没单量，观察不到任何东西。
