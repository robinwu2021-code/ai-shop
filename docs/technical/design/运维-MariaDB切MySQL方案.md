## L1 定位

把现网**三个业务库**从 MariaDB 12.3.2 迁到 MySQL 9.7 LTS，应用改连新库，MariaDB 退役。

**为什么可以做**（2026-09-14 连库实测）：三个库是**纯表**——0 视图、0 存储过程、0 触发器、0 事件；
迁移脚本里没有 `RETURNING`、`SEQUENCE`、生成列、`FULLTEXT`、空间类型这些 MariaDB 专有物；
应用连库串**已经是 `jdbc:mysql://`**（MySQL Connector/J），这一半天生兼容。

**为什么值得做**：不是为了省资源（实测两者内存同一量级，见[资源对比](#附资源实测)），
而是**云托管生态以 MySQL 为主**——将来上腾讯云 CDB / TDSQL-C（自动备份、只读副本、按时间点恢复）
基本都是 MySQL 协议；且 MariaDB 12.3 是短期版（支持期约一年），9.7 是 LTS（约 8 年）。

**为什么现在只出方案不动手**：这是不可逆的换存储（MySQL 数据字典升级单向），必须先把
**排序规则冲突**在副本上验干净。真正的驱动（要不要上托管 RDS）还没定——见 [L4](#l4-边界)。

### 范围

| 迁 | 不迁 |
|---|---|
| `ai_shop`（176 表 · 319MB） | `aiboss`（42 表 · 3MB）——**另一个项目 soukmind 的库**，不归我们 |
| `ai_shop_inv`（21 表 · 2MB） | `mysql` / `sys` / `performance_schema` 等系统库 |
| `ai_shop_job`（4 表 · 2MB） | |

三个库要**一起切**：应用有三个数据源，各自独立的 Flyway（见[部署约定](./后端部署-流程与约定.md)），
留一个在 MariaDB 就等于两套库并存、跨库对不上。

## L2 结构

### 迁移方式：逻辑导出 → 映射排序规则 → 导入

**不走物理拷贝**（MariaDB 与 MySQL 的 InnoDB 文件格式、数据字典不通用，直接拷进去起不来）。
走 `mysqldump` 逻辑导出 → 在导出的 SQL 里把排序规则替换掉 → 灌进 MySQL 9.7。
319MB 的库，导出+导入是**分钟级**，所以**离线切换**（停应用→最后一次导→灌→改连接→起）就够，
不必上 binlog 级复制那套重活。

### 排序规则映射（这是整件事的核心）

现网分布（2026-09-14 实测）：

| 层级 | `uca1400_ai_ci` | `unicode_520_ci` | `unicode_ci` | `utf8mb4_bin` |
|---|---|---|---|---|
| 表级（3 库共 201 张） | 198 | 2 | 1 | 0 |
| 列级（显式列，共 1864） | 1832 | 18 | 5 | 9 |

映射规则：

| 现网（MariaDB） | 换成（MySQL 9.7） | 为什么 |
|---|---|---|
| `utf8mb4_uca1400_ai_ci` | `utf8mb4_0900_ai_ci` | uca1400 是 MariaDB 专有的 UCA 14.0，MySQL 没有；0900 是 MySQL 的现代默认，最接近 |
| `utf8mb4_unicode_520_ci` | `utf8mb4_0900_ai_ci` | **统一成一个**，别留两三种——混排序规则 JOIN 会报 1267（V150 就栽在这上面） |
| `utf8mb4_unicode_ci` | `utf8mb4_0900_ai_ci` | 同上 |
| `utf8mb4_bin` | `utf8mb4_bin`（不变） | 两边都有，且它用于精确匹配键（如 token、hash），**故意二进制比较**，不能动 |

**全库归一到 `utf8mb4_0900_ai_ci`（bin 列除外）**：留着多种排序规则，将来任何跨这两列的 JOIN
都可能在生产上炸 1267，而 H2 测试看不见（见 [[sql-dialect-h2-vs-mariadb]]）。归一是一次把这个雷排掉。

### 不一致清单（2026-09-14 实测点名）——转换要逐个照顾到

不是所有表都是 uca1400。**三种表级排序规则并存**，归一化必须把异类也带上：

| 对象 | 现状 | 转成 | 备注 |
|---|---|---|---|
| 除下面之外的 198 张表 | `utf8mb4_uca1400_ai_ci` | `utf8mb4_0900_ai_ci` | 主流 |
| `ai_shop.prd_goods_draft`（整表 7 列） | `utf8mb4_unicode_520_ci` | `utf8mb4_0900_ai_ci` | 异类①：商品草稿表 |
| `ai_shop_inv.inv_supplier`（整表 12 列） | `utf8mb4_unicode_520_ci` | `utf8mb4_0900_ai_ci` | 异类②：供应商表 |
| **整个 `ai_shop_job` 库**（含 `job_flyway_history`） | `utf8mb4_unicode_ci` | `utf8mb4_0900_ai_ci` | 异类③：调度库当年建库默认就不同 |
| 9 个 JSON 列（`sys_pay_channel.pay_methods`、`rvw_review.images`…全是 longtext） | `utf8mb4_bin` | `utf8mb4_bin`（**不变**） | 存 JSON、非唯一键，故意二进制 |

**这不只是"迁过去要处理"，是现网就埋着的雷**：`prd_goods_draft`/`inv_supplier` 的 520 列一旦和
uca1400 表在字符串键上 JOIN，**MariaDB 现在就会报 1267**（只是这两张表恰好没跨库 JOIN 才没炸）。
归一到 0900 顺手把它拆了——**换库是清掉这个历史不一致的最好时机**。

**字符集层：无需转换。** 三库 1864 个字符串列**全部 utf8mb4**，没有 latin1/utf8mb3。
所以整件事只动排序规则、不动字符集——比一般的库迁移少一大块风险。

### 风险点：230 个唯一索引

`ai_shop` + `ai_shop_inv` 里有 **230 个唯一索引含字符串列**。排序规则一换，判等规则跟着变：
MariaDB 认为是两条不同的记录，MySQL 的 0900 可能认为相等 → 灌数据时撞唯一键、导入中断。
差异集中在边缘字符（新 emoji、部分 CJK 扩展区、全半角、组合字符）。
**这必须在切之前用真数据验，不能靠猜**——见 L3 的 M1。

### M1 · 排序规则冲突预检 —— ✅ **已用真数据验通（2026-09-14）**

> **结果:0 冲突。** 做法比下面的逐索引查询更彻底:把三个库真数据 dump 出来、排序规则映射成 0900、
> 灌进 MySQL 9.7 待机实例,**让 MySQL 自己用 0900 判**——撞唯一键会直接报 ER_DUP_ENTRY。
>
> - 灌库全程 **0 个 ERROR 1062(撞键)**、0 个其它错误、dump 0 警告。
> - **逐表精确行数对账**(不用估算的 `table_rows`,用 `COUNT(*)`):检查 **201 张表 / 675,786 行**,
>   只有 `ai_shop_job.job_log` 差 1 行——查实是那行(`id=3995`,`started_at=18:50`)在一致性快照(18:47:51)
>   **之后**才写进去的运行日志,不是冲突。其余 200 张表逐字一致。
> - 字符集:三库列级 **1864 个字符串列全是 utf8mb4**,无 latin1/utf8mb3 需要转;9 个 `utf8mb4_bin`
>   列都是存 JSON 的 longtext(非唯一键),保留 bin。
>
> **结论:排序规则(uca1400/520/unicode_ci → 0900)在现网真数据上无唯一键冲突、无数据丢失。**
> 换库最大的那个不确定性到此消除。测试库已删、dump 已清,现网 MariaDB 全程未被触碰。
>
> ⚠️ 这验的是「**当前存量**在 0900 下不撞」。切换之前若又攒了新数据,M4 的最后一次 dump→load
> 仍会在真库上再判一次(撞键即报错),所以这不是一劳永逸的免检,而是把风险从「未知」降到「已量过一次、极低」。

下面是这道闸门的通用做法(留作将来复跑或补查用)。在 **MySQL 副本上**跑(MariaDB 没有 0900 排序规则,
`COLLATE utf8mb4_0900_ai_ci` 在它上面直接报 Unknown collation——这也是必须真灌进 MySQL 才能验的原因):

在 **MariaDB 上**（不动 MySQL），对那 230 个唯一索引，逐个用目标排序规则查会不会撞：

```sql
-- 对每个 (表, 唯一索引, 字符串列) 生成并跑：
SELECT <唯一键列>, COUNT(*) c
  FROM <表>
 GROUP BY <列> COLLATE utf8mb4_0900_ai_ci
HAVING c > 1;
```

- **返回空** = 这个唯一键在新排序规则下不撞，安全。
- **返回非空** = 现网有两条记录，MariaDB 当不同、MySQL 会当相同。这类必须**逐条人工定夺**
  （合并？改数据？给该列单独保留 `utf8mb4_bin`？），处理完再切。
- 这一步的产物是一张「230 个索引 × 通过/需处理」的清单，附在本文，切换前必须全绿。
  （脚本我可以生成——从 `information_schema.statistics` 拼出这 230 条查询，只读、不改库。）

### M1 补 · 灌库测不到的那一半：尾随空格（PAD 属性）—— ✅ **已定：选 B**（2026-09-16）

> **定了 B（`utf8mb4_unicode_520_ci`）。** 理由是 A 要靠「380 个唯一键列的写入路径全都 trim」
> 这条纪律撑着，而那件事**没有做**；B 把「判等行为不变」变成结构保证，零前置工作。
> 这次切换的原则是**只换引擎、不换语义** —— `sql_mode` 也按同一条原则对齐了（见 M4 实施记录）。
> 切换后实测：MySQL 520 与 MariaDB uca1400 对 `'a' = 'a '` 都返回 1；
> 1855 个字符列全部落成 520（源库 1832 + 18 + 5 正好对上），9 个 bin 列保留。
> A 以后仍可做，但要当作一个独立项目：先补写入端 trim 与守卫，再 ALTER 排序规则。

### M2 · 转换与索引构建的**执行方案**（在 3307 上跑，不影响现网）

> **已落成可跑的脚本**：[`deploy/tencent/mysql97/migrate/`](../../../deploy/tencent/mysql97/migrate/)
> （`convert.sh` 正式迁移、`extract-seed.sh` 分级种子、`build-fresh.sh` 建新环境、`tiers.conf` 种子分级）。
> 下面的步骤就是 `convert.sh` 做的事。2026-09-14 在待机实例上整套跑通:三库结构+数据+索引迁移、逐表对账一致;
> 分级种子建出的"生产档"只有系统配置(菜单 13/授权 423)、零演示数据,"测试档"才含 SK9901——**测试数据不再混进生产**。

M1 那次用的是"整体 sed 一遍 dump"——**验证够用，正式迁移要换更稳的做法：schema 与 data 分离**。
整体 sed 的风险是替换字符串可能撞上**数据里恰好含 `utf8mb4_uca1400_ai_ci` 字面量**的行（虽然极少）；
拆开之后，排序规则替换只发生在 DDL 段，数据段一个字节都不碰。

**步骤①　导出并转换表结构（只在 DDL 上改排序规则）**
```bash
for db in ai_shop ai_shop_inv ai_shop_job; do
  # 只要结构，不要数据；关掉 MariaDB 专有的 gtid 选项（它不认）
  mariadb-dump --single-transaction --no-data --no-tablespaces "$db" \
  | sed -E 's/utf8mb4_uca1400_ai_ci/utf8mb4_0900_ai_ci/g;
            s/utf8mb4_unicode_520_ci/utf8mb4_0900_ai_ci/g;
            s/utf8mb4_unicode_ci\b/utf8mb4_0900_ai_ci/g' > schema.$db.sql
  # ⚠ utf8mb4_bin 不在替换列表 —— 9 个 JSON 列保持二进制
done
```
把三种排序规则（uca1400 / unicode_520 / unicode_ci）**一律归一到 0900**，异类①②③（见上表）随之被拉平。

**步骤②　建空表 → 索引结构同时落地**
```bash
mysql --defaults-file=/etc/mysql97/my.cnf "${db}" < schema.$db.sql
```
`CREATE TABLE` 里带着**全部索引定义**（主键、唯一键、普通索引），建空表这一步索引结构就位。
0900 是库/表默认，之后任何新列不写 COLLATE 也落 0900，不再有"取决于服务器版本"的问题。

**步骤③　灌数据 → InnoDB 构建二级索引**
```bash
mariadb-dump --single-transaction --no-create-info --no-tablespaces "$db" \
  | mysql --defaults-file=/etc/mysql97/my.cnf "${db}"
```
数据逐行灌进已经建好结构的表，InnoDB **一边插一边构建二级索引与唯一索引**——这就是"同时构建索引"。
**唯一索引在 0900 下会不会撞：M1 已用真数据验通（0 冲突）**；这里若报 ER_DUP_ENTRY，就是切换前又攒了新的冲突数据，停下来按 M1 的办法定夺。

> **索引构建的两个注意**：
> - InnoDB 没有 MyISAM 的 `DISABLE KEYS` 批量建索引优化；它靠 `innodb_sort_buffer_size` 在灌数据时排序建索引。319MB 规模默认参数分钟级完成，不用调。
> - **外键**：三库**实测 0 个跨表外键**（2026-09-14，应用层维护关系），灌数据不受引用顺序约束，`FOREIGN_KEY_CHECKS` 不涉及。正式迁移前仍 grep 一遍 `FOREIGN KEY` 复核。

**步骤④　验收（都要能证伪）**
- 灌库**零报错**；**逐表 `COUNT(*)` 对账**（不用估算的 `table_rows`），每张表行数与现网一致——M1 已跑通此法。
- `SHOW INDEX FROM <表>` 抽查：索引条目数、唯一性、列顺序与现网一致（结构没在转换里掉）。
- 抽查中文/emoji 记录的 `ORDER BY`、`LIKE`、唯一性行为符合预期。
- **269 个迁移在一个空 MySQL 上从头跑一遍**：验"将来全新环境能否在 MySQL 上从零建起"、逼出 DDL 方言差异。
  注意迁移文件里那 132 处 uca1400 会**卡住全新构建**——这条路要么等迁移文件改造（但会破坏现网 checksum，见 M3），要么就认定"全新环境不重跑历史迁移、直接用 dump 的结构 + baseline"。

| 改什么 | 怎么改 |
|---|---|
| 连接的 env 加载 | 部署侧用 systemd `EnvironmentFile`（能正确处理值里的 `&`）。**别用 `set -a; . env`** 在 bash 里加载——URL 里的 `&` 会被当后台符截断（排查时踩过） |
| 三个数据源的 `jdbc:mysql://` | host/port 指向 MySQL；串已是 mysql 协议，基本不改 |
| 连接参数 | 确认 `allowPublicKeyRetrieval=true`（caching_sha2 + 无 TLS 本地连接需要） |
| Flyway 基线（三个库各一套，表名各不同） | 切库走 dump→load、结构+数据一次到位，**不重跑历史迁移**。dump 把各库的 Flyway 历史表连内容一起搬过去了（`ai_shop.flyway_schema_history` 到 V327、`ai_shop_inv.inv_flyway_history` 到 V6、`ai_shop_job.job_flyway_history` 到 V2），所以切完 Flyway 一看历史齐全、只跑新版本，**多半不用手动 baseline**；启动时若因校验报错，再 `baseline` 到上述版本。三个库的 `flyway.table` 名不一样，配置别搞混 |
| 新迁移不许再写 uca1400 | 归一到 0900 之后，新迁移写 `COLLATE utf8mb4_uca1400_ai_ci` 会在 MySQL 上直接失败。**加一条 pre-push 守卫**：迁移文件里出现 uca1400/unicode_520/unicode_ci 就拦，只允许 0900 或不写（靠库默认） |
| 建表默认排序规则 | 那几张没写显式 COLLATE 的表：切库后库默认是 0900，它们自动落 0900，反而对了；隐患消失 |

### M4 · 切换（离线，一次窗口）

> **执行手册见 [`migrate/CUTOVER.md`](../../../deploy/tencent/mysql97/migrate/CUTOVER.md)** ——
> 把下面这段落成了 T-1…T5 一条按序、每步能证伪、随时可回滚的清单。

顺序：停三个服务 → **各库跑一遍 M2 的①②③④**（导出结构映射建表 → 灌数据建索引 → 对账）→
每库 `flyway baseline` → 改 env 里三个数据源指向 3307 → 起服务 →
冒烟（按生产 profile，见 [[deploy-smoke-with-prod-profile]]，注意单实例，见 [[second-app-instance-false-401]]）。
预计停机：三个库 319+2+2 MB，导+灌+建索引分钟级，加对账与冒烟 **约 10~15 分钟**。

**回滚**：MariaDB 全程不动、继续在 3306 跑着。切完发现问题，把 env 三个数据源指回 3306、重启即回退——
只要**切换后没有新数据写进 MySQL**（或写了能补回）。所以要定「观察期多久、这期间要不要双写或只读」。

| 步 | 结果 |

| T-1 预演 | `SUFFIX=_pre TARGET_COLL=utf8mb4_unicode_520_ci`：201 张表 0 报错 —— **这同时就是 520 的 M1 冲突预检**（撞键会 1062） |

### 独立核过的（不只看脚本自己的对账）

- **逐表行数**：201 张表，MariaDB 与 MySQL 逐张比，**不一致 0 张**；断言了扫描面（>190 张才算数）
- **Flyway 历史**：265 / 6 / 2 条，最新 V327 / V6 / V2，失败 0，两边逐项一致
  （⚠️ `MAX(version)` 直接比会得到 "99" —— 那是字符串比较，要 `CAST(... AS UNSIGNED)`）
- **排序规则**：1855 个字符列全是 520，9 个 bin 列保留，非字符列数两边一致
- **判等语义**：MySQL 520 与 MariaDB uca1400 对 `'a' = 'a '` 都返回 1
- **写路径**：切换后 7 个定时任务全部 SUCCESS（含两个 outbox 投递器），`Com_update` 828 / `Com_insert` 12

### 三个手册里没有、实测撞上的

1. **`Requires=mariadb.service`** —— 三个单元都写着它（不是 mysql97）。后果不是「起不来」，
   而是**「停掉 MariaDB」根本不成立**：起一次 `ai-shop` 就把 MariaDB 拉回来了；
   反过来停 MariaDB 会把三个应用一起带停（当天因此掉线约 3 分钟）。已改成 `mysql97.service`，
   并做了消融：停掉 MariaDB 后重启 `ai-shop`，3306 仍无人监听。
2. **`sql_mode` 多三项** —— MySQL 默认带 `ONLY_FULL_GROUP_BY` / `NO_ZERO_IN_DATE` / `NO_ZERO_DATE`。
   按「只换引擎、不换语义」对齐成 MariaDB 的那三项。
3. **两个运维脚本当场就坏**，且都只在日志里报：`logwatch.sh` 的 outbox 查询用裸 `mysql`（MariaDB 客户端）；

   都已改并当场跑通（备份 8.2M 落本机 + COS 200）。

## 附：ADR 草案「为什么是 MySQL 9.7 LTS」

- **不用创新版（26.x）**：只支持到下一个创新版（约一季度），数据字典升级单向，等于每季度被迫升。
- **不用 apt 装**：本机 `mysql-common` 由 MariaDB 提供，apt 装 `mysql-server` 会冲突甚至卸掉 MariaDB。已用官方通用二进制包装在 `/opt/mysql`，与 dpkg 零交集（已落地）。
- **选 MySQL 而非继续 MariaDB**：云托管生态、LTS 支持周期。资源占用不是理由（实测同量级）。
