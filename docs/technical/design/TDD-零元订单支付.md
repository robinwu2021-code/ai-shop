# TDD-零元订单支付

状态：**已实现** · 2026-09-20 · 关联 [TDD-微信发货信息录入](./TDD-微信发货信息录入.md)
档位：1（动了 `PayResult` 契约、新增 `FREE` 支付通道）

---

## 1. 一句话

**应付金额为 0 的订单现在下得出来、却永远付不掉。** 它一路走到支付网关，
被「金额必须大于 0」拒掉，流水关闭，订单卡在待支付 —— 而用户什么也做不了。

---

## 2. 怎么发现的（不是推演，是线上实测）

2026-09-20 17:40，真实下单：

```
订单 SO202609201740370006341
  商品 30 分（3 个柠檬 × ¥0.10）
  优惠 30 分     ← 活动「abc」：无门槛立减 ¥10（trigger_type=NONE / benefit_type=CUT / 1000）
  应付  0 分
```

支付流水两笔都是 `CLOSED`，`err_msg` = **「金额必须大于 0」**
（`WechatDirectPayGateway:155` 的前置校验）。同一时刻另一笔 ¥30.20 的单
拿到了 `prepay_id`，说明链路本身是通的 —— 挂的只有 0 元这一种。

线上此刻有 **1 笔**这样的僵尸单。

### 这不是「配错活动」

无门槛立减撞上低价商品是<b>迟早的事</b>：满减、优惠券、积分抵扣，
任何一种都能把应付打到 0。把活动改掉只是让这一笔消失，
下一笔换个入口还会出现，而症状完全一样（下单成功 → 付不了 → 卡死）。

全仓库 grep 过：**没有任何 0 元单的处理路径**。这是模型缺口，不是配置问题。

---

## 3. 为什么选「支持 0 元支付」而不是「不许减到 0」

两条路都能让这一笔不再出现：

| | 做法 | 代价 |
|---|---|---|
| A | 优惠不得把应付减到 0（保底留 1 分） | 改动小，但「0 元购」这个玩法永远做不了；且 1 分的兜底本身是一句假话 |
| B | **应付为 0 时走「免支付」通道，直接结清** | 范围大一些，但把缺口真正补上 |

选 **B**（2026-09-20 用户拍板）。理由：A 只是把问题推后，
而促销的方向就是让用户少付甚至不付 —— 迟早要支持。

## 4. 设计

### 4.1 新增 `FREE` 通道，而不是在交易域里绕开支付域

**0 元也要有一笔收款流水。** 绕开支付域直接把订单置为已支付的话，
库里会出现<b>「订单说付了、而支付域没有这笔钱」</b> —— 对账轴只扫
`stl_payment`，它看不见这笔单，而这正是 `SettlePort.settlePayment`
的类注释点名最严重的那一种不一致。

```
pay-channel/FreePayGateway     payChannel() = "FREE"，prepay 恒成功、参数为空
shop-core/resolvePayChannel    应付为 0 → 路由到 FREE（在查市场可用通道之前）
paybridge/SettlePortImpl       FREE 通道下单成功后**立即结清**（open → settle）
shop-core/payOrder             看到 FREE 就地调 markPaid，不等回调
```

**为什么 FREE 要在 `initPayment` 里就结清**：其它通道靠异步回调推成功，
而 0 元没有任何外部系统会回调我们。不在这里结清，那笔流水会永远停在
`PENDING`，被对账轴每轮回查一次、每轮查不到。

### 4.2 端上要知道「不用唤起收银台」

`PayResult` 加 `settled`：

```java
record PayResult(String orderNo, String payChannel,
                 Map<String, String> payParams, boolean settled)
```

端上 `settled == true` 就跳过 `requestPayment`，直接去查订单详情。
**不让端上按 `payChannel == "FREE"` 判**：那是把通道名当成了协议，
将来多一个免支付的来源（全额积分抵扣、全额券）就要改端上。

### 4.3 幂等

~~用户连点两下会多一行 0 元流水~~ —— **写方案时想错了，实测轮不到那一层**：

`pay()` 开头就挡住非 `WAIT_PAY` 的单（`OrderServiceImpl:1150`，这道闸在免支付
接进来之前就有）。第一次已经把订单推成 PAID，第二次直接 `ORDER_STATE_ILLEGAL`，
**既不多流水、也不多迁移**。

`markPaid` 自身的幂等仍然留着（回调重放要用），只是 0 元这条路走不到它。
由 `payingTwiceIsRejectedBySateGuard` 钉住真实语义 —— 断言我原先的设想的话，
会把一道有效的闸记成「可有可无」，下一个人删掉它时不会有任何东西变红。

### 4.4 退款与分账

0 元单的退款是 0 元退款。~~本次不做~~ —— **做了**：`PayGateway` 的
`refund` / `split` / `splitReverse` / `subsidy` / `subsidyReturn` 都是抽象方法，
编译器不让绕过去。这条通道上它们走同一条规矩：**只接受 0，非 0 一律不可重试地失败**。

回 ok 的话，账上会出现「已退 / 已分 N 元」而钱一分没动 —— 这条通道压根没有钱可动，
而这种差异要到对账日才冒出来。见 §6.2。

## 5. 测试策略

| 用例 | 防住什么 |
|---|---|
| 应付 0 的单：payOrder 后订单直接是 PAID | 整个特性没接上 |
| 应付 0 的单：落了一笔 SUCCESS 的 FREE 流水 | 绕开支付域 → 对账看不见这笔单 |
| `settled=true` 且 `payParams` 为空 | 端上仍去唤起收银台 |
| 应付 > 0 的单不受影响，仍走原通道 | **把所有单都变成免费的** —— 这条最重要 |
| 重复 payOrder：被状态闸拒，不多流水不多迁移 | 连点两下把订单推乱（实际语义见 §4.3） |

**消融**：把 `resolvePayChannel` 里那一行 0 元判断去掉，第一条必须变红。

## 6. 偏差说明

1. **§4.3 的幂等分析是错的**，已就地更正：实际被 `pay()` 的状态闸挡住，
   走不到 `markPaid` 的幂等。测试按实测语义写。
2. **`FreePayGateway` 比设想的多实现了五个方法**：`PayGateway` 的
   `query` / `refund` / `split` / `splitReverse` / `subsidy` / `subsidyReturn`
   都是抽象方法，编译器逼着表态。
   - `query`：0 元单恒为「已支付 0 元」。回 `notFound` 的话对账轴会把
     「通道那边没有这笔」当异常报出来，而它在任何外部通道那边本来就不存在；
   - 其余五个：**只接受 0，非 0 一律 `fatal`**。回 ok 的话账上会出现
     「已退 / 已分 N 元」而钱一分没动，且没有任何东西会发现。
     这把 §7 原先「本次不做退款」那一条变成了「做了，且只做正确的那一半」。
3. **通道名常量落在 `shop-base/PayChannels`**，不是网关里的字面量：
   `shop-core` 不依赖 `pay-channel`，交易域要按通道路由就够不着 ——
   两处各写一份字面量的话，差一个字母的表现是「通道未接入」而不是编译错误。
