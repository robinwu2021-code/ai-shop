## 0. 结论

**骨架是对的**：
- 所有数量变化只走一条写路径，单据过账 → `StockPostingService` → 流水 + 余额；没有任何地方绕过它直接改余额。
- 「账本 / 库位 / 出库对象 / 交接方式」这套抽象能同时装下电商、餐饮和充电宝。

问题集中在**两处「双轨」**：

1. **单据有两套实现**：
   - 商城后台用的 `InboundService / OutboundService / StockCountService`，用途是硬编码常量，不看档案，不发事件，不写审计；
   - 宿主接口用的 `Host*Service`，看档案，发事件，写审计。

   商家切到独立服务后，后台写入走的仍然是第一套。**档案对电商账本基本不起作用**。
2. **事件有两条通道**：
   - 过账写 `inv_outbox`，只有商城进程里有消费者；
   - 宿主接口写 `inv_event_pending/log`，宿主按游标拉取。

另外有一个 **P1 缺陷**：
- 档案允许用途码最长 32 个字符，但单据表的用途列只有 16 个字符宽（流水那一列已经扩到 32）。超长的用途码在建单时会报 500。

## 1. 统一的业务逻辑

### 1.1 对象

| 对象 | 定义 | 表 |
|---|---|---|
| 账本 | 独立持有、独立核算、可以一起预留的一份库存；宿主选粒度（门店 / 连锁 / 主体 / 平台运营方） | `inv_owner` |
| 库位 | 账本内货所在的位置：仓、门店、在途、虚拟 | `inv_location` |
| 物料 | 账本内的货；按宿主编号对应宿主商品 | `inv_item` + `inv_item_ref` |
| 余额 | 物料 × 库位：**在手**、**预留**、**冻结**；可用 = 在手 − 预留 − 冻结 | `inv_stock_balance` |
| 出库对象 | 货离开账本后的去向；可以关联另一本账 | `inv_target_ref` |
| 档案 | 一本账开哪些能力、有哪些用途、出库后怎么交接 | `inv_business_profile` |

### 1.2 一条写路径，三类单据

```
               ┌── 入库单（来源用途：采购 / 退货 / 盘盈 / 配对收货 / 纠正 …）──┐
宿主 / 后台 ──▶ ├── 出库单（去向用途 + 出库对象 + 交接方式）                    ├──▶ 过账 ──▶ 流水 + 余额 + 事件
               └── 账内移动（调拨：出 → 在途 → 入；盘点：盘盈 / 盘亏）          ┘
```

**在手只能由过账改变。** 预留和冻结只占用可用量，不动在手。

### 1.3 两类占用

| 占用 | 谁发起 | 生命周期 | 结束方式 |
|---|---|---|---|
| **预留** | 订单（宿主单号） | 预留 → 接单未付款 / 付款分配 → 按履约单出库；可以部分完成；到期自动回收 | 转成销售出库（实扣），或者释放 |
| **冻结** | 人工 / 盘点 / 退货待确认 | 生效 → 解除 | 解除 |

### 1.4 出库后的交接（统一电商与充电宝）

| 交接方式 | 货出去以后 | 「在外」状态 | 用在哪 |
|---|---|---|---|
| `NONE` | 离开即结束 | 无 | 销售（来自预留）、报废、退供应商 |
| `POOL` | 等对方签收 | 出库池：待签收 → 已签收 / 撤回 / 退回 | 充电宝投放给商家 / 站点 / 人 |
| `RECEIPT` | 对方账本待收 | 配对记录：已发未收 → 已收（带差异） | 兄弟门店调货、加盟供货 |

再加一条：**同一本账内的移动不是出库**，走调拨，经在途库位。

### 1.5 横切

| 关注点 | 统一要求 |
|---|---|
| 幂等 | 每个写操作带幂等键：同键同参返回原结果，同键不同参返回 409 |
| 审计 | 每次单据和主数据变更都有「谁、何时、前后」 |
| 事件 | 每次过账都产生一条宿主可以拉取的事件，按账本有序，至少送达一次 |
| 外部数据 | 宿主按需同步物料、出库对象，带单调递增的版本号 |
| 业态差异 | **只在档案里**：用途、对象类型、交接方式、能力包 |

下面用这套逻辑逐层对照。

## 2. 数据库设计

| # | 级别 | 现状 | 与统一逻辑的关系 | 建议 |
|---|---|---|---|---|
| D1 | **P1** | `inv_outbound_order.purpose`、`inv_inbound_order.source_type` 是 `VARCHAR(16)`（V1、V8）；档案用途码的正则允许 32 个字符（`ProfileCodec.CODE`）；`inv_ledger.reason_code` 在 V15 已经扩到 32 | 「业态差异只在档案里」的前提被列宽卡住：档案装得进去，建单写不进去，`DataIntegrityViolationException` 没被异常处理器接住，返回 500。M9 已经因为这个把 `STORE_TRANSFER_OUT` 改短成 `STORE_OUT` | V27 把两列扩到 `VARCHAR(32)`，和流水对齐；补一条测试：档案里 32 个字符的用途能建单并过账 |
| D2 | P2 | 事件两套表：`inv_outbox`（过账写，消费者 `PlatformInventoryEventSink` 只在 shop-app 里）；`inv_event_pending/log/subscription`（宿主接口写，宿主拉取） | 违背「每次过账都有一条可拉取的事件」：后台路径的单据、预留转销售出库，宿主事件源里**都没有**；独立服务进程里 `inv_outbox` 没有消费者，只能靠电商套和商城共用一个库 | 过账统一写宿主事件源（`EventPublisher`），`inv_outbox` 只保留给内嵌期的商城读取；内嵌下线（T8.6）后删掉 |
| D3 | P2 | 「在外」有三种落法：调拨经**在途库位余额**；出库池是 `inv_dispatch_*`；配对单据是 `inv_paired_transfer`（明细是 JSON 列 `line_items`） | 「已发未收」是同一个业务问题，却要查三处，而且配对单据的明细不能按物料查 | 先加统一的只读视图（见 A3）。配对明细如果要按物料统计在途，再拆成行表，现在不急 |
| D4 | P3 | `inv_owner.external_type` 的数据库缺省值是 `'ENTITY'` | 「服务不解释宿主类型」，缺省值却是商城的含义；代码里已经有 `OwnerType.defaultFor(system)` | 下次动这张表时去掉库级缺省，只由代码写入 |
| D5 | P3 | `inv_location.kind` 有一个值叫 `STORE` | 宿主概念渗进了服务。不影响行为（服务对 STORE 和 WAREHOUSE 的处理差别只在「默认库位」） | 维持现状，在注释里写明 STORE = 「对外售卖的库存点」 |
| D6 | P3 | `inv_target_ref` 唯一键按账本 `(owner, system, type, ref)` | 连锁里 N 本账都要发给同一家门店时，要同步 N 份 | 符合「出库对象是账本自己的去向」，保留；同步量由宿主按需控制 |
| ✓ | — | 余额只靠条件更新，没有「先查后改」；流水只追加，实体上没有 update；业务键全部唯一；没有外键、没有软删列 | 和「一条写路径」一致 | 保持 |

## 3. API 设计

| # | 级别 | 现状 | 与统一逻辑的关系 | 建议 |
|---|---|---|---|---|
| A1 ✅ M12 | P2 | **标识混用**：<br>- 预留按宿主编号：`itemRef` = SKU，`locationRef` = 门店号；<br>- 账本按宿主编号：`X-Inventory-Owner-Ref`；<br>- 出库对象按宿主编号；<br>- 入库、出库、盘点、余额、冻结却要**内部号**：`itemId`、`locationId`；<br>- 物料同步时返回 `itemId` | 宿主要自己维护一张「SKU → itemId」映射。ShareHub 现在就这么做，配对单据收货时也只能用 B 侧的内部物料号 | 单据和查询接口**同时接受** `itemRef` / `locationRef`（二选一），服务端解析；响应里两种都返回。原有字段不变 |
| A2 ✅ M11 | P2 | 宿主接口**没有账内调拨**：调拨只在商城后台转发接口里 | 统一逻辑里「账内移动」是三类单据之一。ShareHub 想把坏件从良品仓移到不良品仓没有接口可用（M7 遗留） | 补 `POST /transfers`、`/{no}/ship`、`/{no}/receive`、`/{no}/cancel`，复用 `TransferService` |
| A3 | P2 | 「在外」查询分两处：`GET /in-transit` 只有出库池；配对单据要查 `GET /paired-transfers?status=SHIPPED`；账内调拨的在途没有接口 | 宿主问「我有哪些货在外面」要调三个接口 | `GET /in-transit` 合并三种来源，每条带 `kind = POOL / PAIRED / TRANSFER`。只读，不加表 |
| A4 | P2 | **两套契约做同一件事**：<br>- 商城后台转发：`/v1/console/**`，48 个端点，结构照搬商城 `Biz*Controller`；<br>- 宿主接口：`/v1/**` | 后台的单据走的是另一套实现（见 K1），档案、事件、审计都不生效 | 过渡期可以接受。收敛目标：后台转发的写操作在服务端内部改调宿主接口那一套，对外结构不变 |
| A5 | P3 | 入库请求字段叫 `purpose`，库里叫 `source_type`；出库两处都叫 `purpose` | 同一个概念两个名字 | 对外统一叫 `purpose`，列名不改，在实体注释里说明 |
| ✓ | — | 预留接口按档案能力包 `RESERVATION` 拦截（`ReservationController`） | 「能力只在档案里开」 | — |
| ✓ | — | 交接动作的入口一致：出库过账自动产生后续（出库池 / 待收单），对方的确认各有专门接口（`claims` / `receive`）；幂等键、错误码结构、系统级接口的鉴权都是统一的 | — | 保持 |

## 4. 代码实现

| # | 级别 | 现状 | 与统一逻辑的关系 | 建议 |
|---|---|---|---|---|
| K1 | **P2（最大的债）** | 单据有两套实现：`InboundServiceImpl` 269 行 / `OutboundServiceImpl` 289 行 / `StockCountServiceImpl` 363 行，对比 `Host*ServiceImpl` 477 / 441 / 419 行。后台那套：用途是常量（`InvEnums.OutboundPurpose.SALE` 等 14 处），**不读档案、不写审计、不发宿主事件**，不支持 SN、放行凭证、出库对象。两套都调 `StockPostingService`，所以数量是对的 | 「业态差异只在档案里」和「每次过账都有审计和事件」在电商账本上都不成立；同一条规则（比如报废必须填原因）两处各写一遍 | 以 `Host*` 为唯一实现，商城的档案把现有常量用途都登记进去；后台那套改成薄适配层，只负责把商城的请求翻译成宿主接口的草稿。跟 T8.6（删内嵌）一起做 |
| K2 | P2 | `PairedTransferServiceImpl.receive` 直接用 `InboundLineMapper` 改待收单的行和总数，然后再调 `HostInboundService.post` | 入库单草稿的不变量（总数、行号、SN）应该只归 `HostInboundService` 管；现在有两个地方在写入库单的行 | `HostInboundService` 加 `replaceLines(caller, no, lines)`（只限草稿），配对收货改调它 |
| K3 | P3 | `HostOutboundServiceImpl.post` 末尾用 `if (POOL) … if (RECEIPT) …` 分支处理交接 | 交接方式是档案里的枚举，再加一种就要改出库过账代码 | 抽一个 `Handover` 接口（`NONE / POOL / RECEIPT` 三个实现），按 `purpose.handover()` 选用；建单时的结构检查也放进去 |
| K4 | P3 | `BalanceQueryServiceImpl.acrossOwners` 靠捕获 `InventoryException` 识别「同号多本」 | 用异常表达一个正常分支 | `ServicePlatformService` 增加一个返回全部匹配的查询，由调用方决定怎么处理 |
| K5 | P3 | `InventoryAclServiceImpl`（商城内嵌的入口）放在通用领域模块里，写死了 `ENTITY` 类型和「商家号 = 主体号」 | 宿主的映射规则不该在服务里 | 随 T8.6 和 C8（`StockOrgResolver`）移到 ai-shop 侧 |
| ✓ | — | `StockPostingService` 是唯一改余额的地方（流水 Mapper 在其他类里只做读）；预留确认生成销售出库单，而不是直接扣减；配对单据、出库池都和出库过账在同一个事务里 | 和统一逻辑一致 | 保持 |
