## 一、这是什么，为什么现在做

系统里**只有商家品**：`prd_goods.entity_no` 必填，没有平台维护的标准商品。
三家店各自录「农夫山泉 550ml」，得到三个毫无关系的商品 —— 标题不同、规格文案不同、
图各拍各的。代价有两个，一个显性一个隐性：

| | 代价 |
|---|---|
| 显性 | 商家每建一件货都要从零填标题、图、规格 —— 建品是入驻之后**最劝退的一步** |
| 隐性 | **跨店不可比**。`optionCode`（B-4.5）做了「一期只写入不消费」，而它要消费的前提正是「同一件货在不同店里指向同一个东西」—— 没有标准品，那个前提永远不成立 |

第二条是这次做它的真正理由。平台模板给了「500g」这个 code，但**哪三家店卖的是同一瓶水**，
系统里没有任何东西回答得了。

## 二、结构（L2）

```
       ┌──────────────────────────────────────────┐
       │ prd_spu_std   平台标准品（运营维护）      │
       │  标题 / 图 / 规格组(带 optionCode) / 类目 │
       │  ✗ 无价 ✗ 无库存 ✗ 无履约 ✗ 无上下架     │
       └───────────────┬──────────────────────────┘
                       │ 商家在建品页搜到它 → 取用
                       │ ① 端上把字段填进表单（可改）
                       ↓ ② 后端记 std_no，并**强制**类目与 optionCode 以标准品为准
       ┌──────────────────────────────────────────┐
       │ prd_goods     商家品（原样不变）          │
       │  std_no ← 溯源引用（可空：自建品照旧）     │
       │  价 / 库存 / 履约 / 上下架 / 审核 全部自持 │
       └──────────────────────────────────────────┘
```

图上看不出来的三件事：

1. **一期没有「回流」** —— 标准品改了不会推给已经引用它的商家品。
   所以行为上这一期是「**复制 + 溯源**」，不是完整的引用式。
   诚实地说：B 案与 C 案在不做回流时，差别只剩 `std_no` 这一条线 ——
   而那条线正是聚合、比价、统计要用的东西，也是 C 案永远拿不到的。回流留二期。
2. **标准品不参与审核，也不豁免审核**。它只保证描述规范，不保证这家店卖的真是那个东西。
   「引用即免审」是二期的事，且要先有引用后的抽检数据。
3. **价永远不在标准品上**。这与 SPU 无价是同一条不变量的延伸 ——
   标准品一旦带价，它就成了平台指导价，那是完全另一件事（且有法律含义）。

## 三、详情（L3）

### 3.1 表

```sql
prd_spu_std
  std_no        VARCHAR(64)  唯一
  category_no   VARCHAR(64)  NOT NULL   -- 必填：形态由它派生，与商家品同一条规则
  title         VARCHAR(255) NOT NULL
  title_i18n    TEXT                    -- {"en":…,"ar":…}
  subtitle      VARCHAR(255)
  cover         VARCHAR(512)
  images        TEXT                    -- JSON 数组
  spec_groups   TEXT                    -- JSON，与 prd_goods.spec_groups 同构，**必须带 optionCode**
  keywords      VARCHAR(512)            -- 别名/品牌/俗称，空格分隔。搜索用
  status        VARCHAR(16)  ACTIVE / ARCHIVED
  ref_count     INT                     -- 被引用次数，运营侧排序与去重判据用
```

**不建 `prd_spu_std_sku`**：规格组已经内嵌在 `spec_groups` 里，与 `prd_goods` 同构。
标准品没有价也没有库存，单独一张 SKU 表只剩规格文案 —— 那正是 `spec_groups` 已经有的。

`prd_goods` 加一列：

```sql
ALTER TABLE prd_goods ADD COLUMN std_no VARCHAR(64) DEFAULT NULL;   -- 溯源；NULL = 自建品
```

⚠️ 加列必须同时补 `PrdGoods` 实体字段，否则那一列永远读出 null（`entity-alignment` 守卫会红）。

### 3.2 继承与覆盖：哪些能改，哪些不能

| 字段 | 取用时 | 商家能改吗 | 为什么 |
|---|---|---|---|
| 标题 / 副标题 / 三语 | 填进表单 | ✅ 能 | 「李婶家的农夫山泉」是合理的差异化 |
| 封面 / 轮播图 | 填进表单 | ✅ 能 | 他自己拍的图比标准图更像他的店 |
| **类目** | 填进表单 | ❌ **服务端以标准品为准** | 类目决定形态（生鲜要截单、服务不发货）。改了类目就不是这个标准品了 |
| **规格组的 `optionCode`** | 填进表单 | ❌ **服务端以标准品为准** | **这是整件事的目的**。code 能被商家改掉的话，跨店可比又没了，标准品退化成一个填表助手 |
| 规格组的 name / options 文案 | 填进表单 | ✅ 能 | 展示文案，不参与聚合 |
| 价 / 库存 / 履约 / 上下架 | 不填 | ✅ 全自持 | 这些本来就只能是商家的 |

**强制那两条落在服务端，不是端上**：端上只是「填充」，而填充过的表单商家能随便改。
后端在 `save()` 里看到 `stdNo` 时，用标准品的 `category_no` 与 `optionCode` **覆盖**请求值 ——
端上算错或老客户端不认这个字段，都写不进一条破坏可比性的数据。

商家可以**追加**自己的规格组（比如「是否加冰」），追加的那些没有 code，照常展示、不参与聚合。

### 3.3 API

| 端点 | 权限 | 说明 |
|---|---|---|
| `GET /biz/spu-std?keyword=&categoryNo=` | `biz:goods` | 商家建品时搜。按 `title` + `keywords` 模糊匹配，只返回 ACTIVE |
| `GET /ops/spu-std` | `product:std:read` | 运营列表，支持 `keyword` / `categoryNo` / `showArchived`，带 `refCount` |
| `POST /ops/spu-std` | `product:std:update` | 新建或更新。**每个规格选项必须带 code**（与平台规格模板同一条校验） |
| `POST /ops/spu-std/{no}/archive` \| `/unarchive` | `product:std:update` | 归档不影响已引用的商品 —— 那是溯源不是外键 |

**没有新的建品接口**：商家取用后仍走 `POST /biz/goods/save`，只多带一个 `stdNo`。
少一条链路，也让「引用建品」与「自建品」在审核、上架、库存上逐字相同。

权限码沿用 `product:` 前缀，新增 `product:std:read` / `product:std:update`
（`ops-web/lib/permissions.ts` 与 `ops-role-endpoint-matrix.json` 同步登记）。

### 3.4 端上

**b-app 建品页**：类目选择器上方加一行「从标准品开始」——
搜名称 → 命中列表 → 选中后填充标题/图/规格组/类目，并在页面上标出
「来自标准品 · 农夫山泉 550ml」与一个「脱离标准品」的入口（清掉 `stdNo` 变成自建品）。

**ops-web**：`/products` 加第四个 tab「标准品库」，复用类目 tab 的表格 + 抽屉形状。

### 3.5 迁移

`V166__spu_std.sql`：建表 + `prd_goods.std_no` + 一批种子标准品（覆盖 CAT200 日用百货
与 CAT100 食品生鲜的常见品，10~20 条，让功能一上线就有东西可搜）。

> ⚠️ 迁移号要在动手前再确认一次：并行会话同时加 Flyway 会撞号，
> 症状是 `SchemaParityTest` 报别人的表缺失。

## 四、边界（L4）

### 一期明确不做

| 不做 | 为什么 |
|---|---|
| **变更回流** | 一次运营误操作会同时改掉几十家店的商品，要配审计与回滚。先看商家用不用 |
| **提升 / 合并 / 去重** | 标准库自我生长的机制。没有引用数据之前，无从判断哪些该合并 |
| **条码** | 已定：名称/类目搜索。生鲜、散装、手工品本来就没有条码，而那是这个平台的主力 |
| **引用即免审** | 标准品只保证描述规范，不保证这家店卖的是那个东西 |
| **标准品带价** | 平台指导价是另一件事，且有法律含义 |

### 风险

1. **运营录入成本**。标准库的价值与覆盖率成正比，而覆盖率全靠运营手录。
   种子给 10~20 条只够验证链路 —— 真要用起来，得先回答「谁来录、录多少才够」。
   这是这个功能唯一可能失败的地方，且失败方式是「上线了没人用」。
2. **搜不到就白做**。名称匹配对「农夫山泉」有效，对「张姐家的酱菜」无效。
   建品页必须让「搜不到 → 直接自建」这条路一样顺 —— 不能因为多了标准品，
   自建品反而变成一个要先失败一次才能走到的分支。
3. **`ref_count` 的维护时机**。挂在保存路径上会让建品多一次写；一期用定时统计即可，
   它只服务运营排序，不参与任何判断。

### 待决

| # | 事项 | 何时要答 |
|---|---|---|
| Q1 | 标准品的**运营录入责任人**是谁，一期铺多少条 | 开工前 |
| Q2 | 商家「脱离标准品」后 `std_no` 置空还是保留（保留能看出「他曾经用过」） | 编码时，倾向置空 —— 保留会让统计口径变成两种 |
| Q3 | 二期回流的粒度：按字段还是整份 | 二期 |

**验收（每条都要能自己红）**

1. 引用标准品建品 → `prd_goods.std_no` 有值，且 `spec_groups` 的 `optionCode` 与标准品逐条相同
2. 构造一个把 `optionCode` 改掉的请求 → 服务端以标准品为准写入（**这条是整件事的核心**）
3. 构造一个把 `categoryNo` 改成别的类目的请求 → 服务端以标准品为准，派生出的 `type` 也跟着回到标准品那一档
4. 归档标准品 → 已引用的商品照常在售、照常可编辑
5. 搜不到标准品时，自建品链路一步不多
