# 平台优化方案 · 商家分层与能力矩阵

> 状态：**待决策**。把支付通道约束、积分模型、无资质商家三条分析线**收拢成一条主线**。
> 上游：[无资质商家-邻居集市方案](./无资质商家-邻居集市方案.md) · `sys_legal_form` · `capability/index.ts`
>
> 本文按 [文档规范](../../文档规范.md) §四「方案类骨架」组织。

---

## 一、一句话

平台对不同商家承担的**责任不同**，因此给他们的**能力也不同** ——
而这套「档位 → 责任 → 能力」的对应关系目前**散在六处**，没有一个地方说得全。

把它收成一张矩阵，是这轮优化的主干；其余都是它的推论。

---

## 二、为什么是这个方案

### 2.1 三条分析线撞到了同一个东西

这段时间分开做的三件事，结论都落在「商家档位决定能力」上：

| 分析 | 结论 |
|---|---|
| 支付通道对齐 | 小微**限行业**；结算到个人**不支持分账回退** |
| 积分模型 | 小微**不参与积分**（税务定性模糊 + 结算到个人） |
| 无资质商家 | 未认证**不能收线上支付**（平台收钱即担责） |

三条各自都对，但**没有一个地方把它们放在一起**。
于是同一个问题（「这家店能做什么」）要翻三份文档、读三段代码。

### 2.2 判据现在散在六处

| 在哪 | 判什么 | 形态 |
|---|---|---|
| `canSell` | 端 × 品类可售 | 函数 + `sys_channel_category_rule` |
| `canPay` | 商家在该端能否收款 | 函数 + `mch_payment_merchant` |
| `canPoints` | 积分是否生效（四级串联） | 函数，**主体判断硬编码在里面** |
| `sys_legal_form` | 需不需要执照、通道映射 | 表 |
| `sys_industry` | 小微行业白名单、强制积分 | 表 |
| 无资质方案（待落地） | 能否收线上支付 | 尚不存在 |

**问题不是「散」本身**，是它们的**取向不一致**：

- `canSell` 查不到规则 → **判否**（写得对）
- `canPoints` 里小微的判断是 `if (subjectType === "MICRO")` **硬编码**
- 而小微限行业、结算账户类型限制回退，在这三个函数里**一个都没有**

硬编码的那一行最危险：加一个新档位（比如无资质）时，
**它不会报错，只是静默不匹配** —— 新档位的商家会走到「本店未开启积分」，
而正确的提示应该是「未认证商家不支持积分」。

### 2.3 被否掉：继续加函数

最省事的做法：再加一个 `canTakePayment`，再加一个 `canReserve`……

**否掉的理由**：每加一个能力就要在 N 个档位上重新想一遍，
而想漏的那一格**没有任何症状**。现在已经有三个函数 × 四个档位 = 12 格，
其中至少 3 格从没被明确回答过（见 §三的空格）。

函数适合表达**判断顺序**（`canPoints` 里主体排在商家开关之前是有语义的），
不适合表达**组合覆盖**。两者要分开。

### 2.4 更正：分层依据是国家法规，不是通道分类

前三节都在通道能力上打转 —— 微信认什么、支付宝认什么。**那是下游。**

上游是国家对经营主体的规定：
**不符合国家法规经营的实体，平台不应提供交易能力，只能展示。**

#### 法律怎么定

| 依据 | 内容 |
|---|---|
| 《电子商务法》第 10 条 | 电子商务经营者应当依法办理**市场主体登记**，但列了**免登记情形** |
| 同上，免登记四类 | ① 个人销售**自产农副产品** ② 个人销售**家庭手工业产品** ③ 个人利用自身技能从事依法无须许可的**便民劳务** ④ **零星小额**交易 |
| 《网络交易监督管理办法》第 8 条 | 把「零星小额」量化：个人**年交易额累计不超过 10 万元** |
| 《电子商务法》第 11 条 | 免登记的，**首次纳税义务发生后仍应办理税务登记** |
| 《市场主体登记管理条例》 | 界定市场主体：公司、个人独资企业、合伙企业、**农民专业合作社**、个体工商户等 |

#### 这推翻了「无资质 = 只能展示」

**免登记情形下的经营者是合法经营者，不是无资质。**
按「不合规才只展示」的原则，他们**法律上可以交易**。

真正该只展示的是另一群人：

| 群体 | 法律状态 | 能交易吗 |
|---|---|---|
| 已登记（个体户 / 企业 / 农民合作社…） | 合规 | ✅ |
| **免登记情形**（自产农副产品、家庭手工业、便民劳务、零星小额） | **合规** | ✅ |
| **应登记而未登记** | 不合规 | ❌ 只展示 |
| **需许可而未取得**（食品、药品…） | 不合规 | ❌ **该品类**不能交易 |

**我原先把第 2 行和第 3 行合成了一档 `NONE`。那是错的** ——
一个卖自家柿饼的农户，与一个开网店卖工业品却不办执照的人，
法律地位完全不同：前者受法律明文豁免，后者是违法经营。

把他们放进同一档，等于**用「不能交易」惩罚一群法律准许交易的人**，
同时也**给违法经营者留了一个体面的名字**。

#### 三个轴，不是一个

| 轴 | 谁定 | 管什么 | 现在落在哪 |
|---|---|---|---|
| **① 市场主体登记** | 电商法 + 登记条例 | 能不能经营 | **没有** ← 缺口 |
| **② 行政许可** | 食安法、药品法… | 这个**品类**能不能卖 | `canSell` + `sys_industry` |
| **③ 通道进件** | 微信 / 支付宝 | **怎么**收钱 | `sys_legal_form` |

`sys_legal_form` 现在**同时在管 ① 和 ③**，这是本节要拆开的东西。

> **② 是品类级，不是主体级。** 一个有执照的餐馆没拿到食品经营许可，
> 不是整店不能卖，是**熟食不能卖**。挂到主体上会误伤他的包装食品。
> 这条已经由 `canSell`（端 × 品类）承接，方向是对的，不要往主体上搬。

#### 法律准许 ≠ 技术可行

免登记的农户法律上可以收款，但**通道未必收他** ——
小微进件要门店照片，他没有。这是两个独立的门：

```
① 法律准许交易   ← 电商法第 10 条免登记
② 通道能收他的钱 ← 小微门槛 / 个人卖家 2500（见 §8.3）
两扇门都过，才能真正线上交易
```

**不要把 ② 的限制说成 ①**。对一个合法农户说「你无资质」是错的，
准确的说法是「通道暂时开不了收款，可先用线下付款」。

## 三、结构：一张矩阵 + 一层顺序

### 3.1 前置判据：经营合规性（决定能不能交易）

按 §2.4，**这一轴排在能力矩阵之前** —— 它不是矩阵里的一行，是矩阵的开关：

| 经营资格 | 法律依据 | 交易能力 |
|---|---|---|
| `REGISTERED` 已登记 | 登记条例，有营业执照 | 全部 |
| `EXEMPT` **免登记** | 电商法 §10 四类情形 | **可交易**，但受 10 万元/年 与税务登记约束 |
| `UNREGISTERED` 应登记未登记 | 违反电商法 §10 | **仅展示** |

```
经营资格 != REGISTERED/EXEMPT  →  只展示，下面的矩阵整张不用看
```

`EXEMPT` 必须记录**属于哪一类豁免**（自产农副产品 / 家庭手工业 / 便民劳务 / 零星小额）——
这不是备注，它决定后续判定：
前三类与金额无关，第四类**一旦年累计超 10 万元就自动失格**，
而失格之后继续交易，平台是明知的。

### 3.2 能力矩阵（数据）

**按门槛从低到高排**，不按业务模块 —— 排完之后矩阵是一道**阶梯**，
而阶梯的每一级落在哪，本身就是信息：那一级就是平台责任的一次跃迁。

> 下表**只对经营资格为 `REGISTERED` / `EXEMPT` 的主体适用**。
> `UNREGISTERED` 不进这张表 —— 它在上一节就被挡住了。

| # | 能力 | 免登记 `EXEMPT` | 小微 `MICRO` | 个体户 `INDIVIDUAL` | 企业 `ENTERPRISE` |
|---|---|:---:|:---:|:---:|:---:|
| | **Ⅰ 展示类** —— 钱不经过平台 | | | | |
| 1 | 建商品 / 分享 | ✅ | ✅ | ✅ | ✅ |
| 2 | 线上预定（线下付款） | ✅ | ✅ | ✅ | ✅ |
| | **Ⅱ 枢纽** —— 责任分水岭 | | | | |
| 3 | **收线上支付** | ⚠️ 法律准许，**看通道收不收** | ✅ | ✅ | ✅ |
| | **Ⅲ 收款派生** —— 必须先过第 3 行 | | | | |
| 4 | 出现在正常货架 | ⚠️ 同上 | ✅ | ✅ | ✅ |
| 5 | 分账回退（售后期后退款） | ⚠️ 同上 | ⚠️ 结算到个人则否 | ✅ | ✅ |
| 6 | 参与积分 | ❌ | ❌ | ✅ | ✅ |
| | **Ⅳ 税务类** | | | | |
| 7 | 开票 | ❌ | ❌ | ⚠️ 看进件回执 | ✅ |

**第 3 行的 ⚠️ 是本次更正的核心**：原先这里是 ❌，理由是「平台收钱要担责」。
现在改成⚠️ —— **法律准许他交易，挡住他的是通道进件门槛，不是法规**。
两者要分开说，理由见 §2.4 末节。

第 6 行仍是 ❌：积分兑付要平台向商家付钱，没有收款商户号就付不出去 ——
这是纯技术约束，与合规无关。

> 原先矩阵里有一行「行业限制：小微=白名单」。排序时它排不进去 ——
> **它不是能力，是修饰**：其余七行答「能不能」，它答「在什么范围内能」。
> 混在一起会让人以为「行业」也是一个可以开关的能力位。
> 它属于 `sys_industry`，不进这张表。

**三个此前没被明确回答的格子**（本方案顺带定掉）：

1. 免登记商家能不能参与积分 → **否**。积分兑付要平台向商家付钱，
   没有收款商户号就付不出去 —— 纯技术约束
2. 免登记商家能不能被预定 → **能**，这正是它的价值
3. 小微能不能开票 → **否**。小微没有执照，开不了增值税发票

### 3.3 四类能力的区别

七行能力**不是同一种东西**。混着看会得出错误的推论 ——
比如「既然能建商品，加个支付按钮不就行了」。

| 类 | 判据来自 | 平台角色 | 加一个新档位时 |
|---|---|---|---|
| **Ⅰ 展示** | 无（人人可有） | 信息发布方 | 默认给 |
| **Ⅱ 枢纽** | 法律责任 + 通道进件 | **交易参与方** | 默认不给，要法务点头 |
| **Ⅲ 收款派生** | 通道能力 + 结算账户 | 交易参与方 | 先看第 3 行，否则不用想 |
| **Ⅳ 税务** | 有没有执照 | 代开方 | 独立判断 |

#### Ⅱ 是分水岭，不是一个普通开关

第 3 行与前两行的差别**不是程度，是性质**：

| | 用户下单 | 钱去哪 | 出事谁赔 |
|---|---|---|---|
| 线上预定（第 2 行） | 有 | 线下，双方自理 | 商家 |
| 线上支付（第 3 行） | 有 | **过通道，平台指令分账** | **平台先行赔付** |

两行在用户界面上只差一个按钮，在责任上差一整个量级。
**这是矩阵里唯一一条要法务确认才能改的行。**

#### Ⅲ 严格依赖 Ⅱ，不是并列

第 4/5/6 行看起来是三个独立能力，实际都挂在第 3 行下面：

```
③ 收线上支付
   ├─ ④ 正常货架   上了货架就要能下单，否则用户点进去买不了 —— 不报错，只掉转化
   ├─ ⑤ 分账回退   回退的是分给商家的那笔钱，没分账就没得退
   └─ ⑥ 参与积分   抵扣的差额要平台补进**二级商户账户** —— 没有账户，钱付不出去
```

**所以第 3 行判否时，4/5/6 不用再算**。写成并列的四个函数就会各算各的，
而它们的上下文里都要重新取一遍进件状态。

#### ④ 与 ③ 绑定，但机制和时效都不同

这两行在矩阵里取值一样，容易被合并。**不能合**：

| | 靠什么判 | 多久变一次 |
|---|---|---|
| ③ 收支付 | `mch_payment_merchant.apply_status` | **几天** —— 进件中→通过 |
| ④ 上货架 | `prd_goods.shelf` 派生列 | 档位变才变，要办执照 |

合并的后果：进件状态一变，几万条商品的 `shelf` 要跟着刷。
分开之后，进件中的商家是「有资质但暂时收不了款」——
商品留在集市，进件通过再刷一次，**只刷一次**。

#### ⑤ 是唯一的二维格

其余六行都是「档位 → 能力」一维。第 5 行不是 ——
它真正的判据是**结算账户类型**（`settle_account_type`），
而账户类型与档位只是**相关**，不是决定：小微通常结算到个人，但不必然。

矩阵里写「⚠️ 结算到个人则否」是个折中标注。它放哪见 §七第 3 条。

### 3.4 判断顺序（代码）

矩阵管**能不能**，函数管**先看哪个、提示语说什么**。
顺序是有语义的，不能塞进表里：

```
canPoints 的顺序（现有，正确）
  全局开关 → 通道能否补差 → 社区开关 → 主体档位 → 商家开关
             ↑ 做不到              ↑ 不可开        ↑ 没开
```

三种「否」的提示语完全不同：

| 类型 | 例子 | 用户该做什么 |
|---|---|---|
| **做不到** | 当前支付方式不支持积分抵扣 | 换个端 |
| **不可开** | 未认证商家不支持积分 | 去认证 |
| **没开** | 本店未开启积分 | 找商家 |

混为一谈的代价：小微商家看到「本店未开启积分」，
会去后台找那个**他根本打不开**的开关。

## 四、详细设计

### 4.1 矩阵入库，不写在代码里

```sql
-- ① 经营合规性：轴 ①，法定的，与通道无关（§3.1）
ALTER TABLE mch_entity
  ADD COLUMN biz_qualification VARCHAR(16) NOT NULL DEFAULT 'UNREGISTERED'
    COMMENT 'REGISTERED 已登记 / EXEMPT 免登记 / UNREGISTERED 应登记未登记。
             **默认 UNREGISTERED** —— 没核过的一律不给交易能力',
  ADD COLUMN exempt_type VARCHAR(24) NULL
    COMMENT 'EXEMPT 时必填：AGRI 自产农副产品 / HANDCRAFT 家庭手工业 /
             SERVICE 便民劳务 / PETTY 零星小额。PETTY 受 10 万元/年 约束，其余三类不受';

-- ② 通道能力：轴 ③，跟着通道走
sys_legal_form                      -- 已存在，加能力位
  + can_points       能否参与积分     ← 把 canPoints 里的硬编码搬出来
  + can_invoice      能否开票
  + on_main_shelf    是否出现在正常货架
```

> **`can_trade` 不放在 `sys_legal_form`。** 能不能交易由**轴 ①**（法定合规性）决定，
> 而 `sys_legal_form` 是**轴 ③**（通道进件）的表。放错表的后果是：
> 法务口径一变要去改通道注册表，而改的人以为自己在改通道配置。
>
> 这正是 §2.4「三个轴」要拆开的实操落点。

**为什么入库**：这些结论来自**外部约束**（通道规则、税务定性、法律责任），
而外部约束会变 —— 微信调整小微白名单、税务口径变化、法务给出新意见。
写在代码里每次变都要发版，而变更本身与代码无关。

**为什么仍要类型**：取值域（有哪些档位）不会凭空冒出来。
`MerchantSubject` 联合类型 + 守卫断言 seed 与类型一致 ——
与 `sys_pay_channel` / `sys_industry` 完全同构：**表管能力，类型管取值**。

> ⚠️ 所有能力位**默认 0**。新增档位时默认什么都不能做，要放开必须显式改。
> 反过来（默认放开）的话，新档位会静默获得它不该有的能力，
> 而症状是「一个不能收款的店收了钱」。

### 4.2 `canPoints` 的硬编码搬出来

```ts
// 现在
if (ctx.subjectType === "MICRO") return deny("本店暂不支持积分（升级为个体工商户后可开启）");

// 改成
if (!ctx.legalFormCanPoints) return deny(ctx.legalFormDenyReason);
```

`legalFormDenyReason` 来自 `sys_legal_form.remark` —— 提示语随档位走，
不用为每个新档位改一次函数。

**这一步是本方案里唯一必须改代码的地方**，其余都是加数据。

### 4.3 一个能力函数就够

```ts
/** 这家店能做什么 —— 档位能力 × 实时状态 */
export function merchantCapability(ctx: {
  legalForm: LegalFormCaps;        // 来自 sys_legal_form 的四个能力位
  payments: MerchantPayment[];     // 进件状态
  industry: IndustryCaps;          // 行业限制
}): {
  canTakePayment: Verdict;
  canPoints: Verdict;
  canInvoice: Verdict;
  onMainShelf: boolean;
}
```

现有的 `canSell`（端 × 品类）**保持独立** —— 它判的是商品，不是商家，
两者正交。合并会让一个函数同时需要商品和商家两套上下文。

### 4.4 后台任务：上次盘点的结论已经过时

我在[支付与积分功能补充清单](../archive/支付功能-三端补充清单.md)里写过
「后台连定时任务框架都没有，20 项全是空的」。

**这个结论现在不成立了** —— 已经有：

```
config/SchedulingConfig.java
settle/job/ReconScanJob.java              对账扫描
merchant/job/QualificationExpiryJob.java  资质过期
```

接手时**先核对现状再照着那份清单做**，否则会重复建设。
本方案不重复盘点后台，只指出：矩阵入库后，
`QualificationExpiryJob` 应该顺带处理「资质过期 → 档位降级 → 商品下架到集市」
这条链路 —— 那正是本方案与既有任务的接缝。

## 五、取舍记录

| 冲突 | 让了谁 | 代价 |
|---|---|---|
| 加函数（改动小）↔ 收成矩阵 | **矩阵** | 一次性改 `canPoints` 与建表。换来加新档位不用改代码 |
| 能力写代码（类型安全）↔ 入库（可配） | **入库** | 失去编译期检查，靠守卫补。但外部约束变了不该发版 |
| 一个大函数 ↔ 保留 `canSell` 独立 | **保留独立** | 两个入口。但商品与商家是两套上下文，合并会互相污染 |
| 默认放开（少配置）↔ 默认关闭 | **默认关闭** | 新增档位要逐项开。反过来会静默放出不该有的能力 |

## 六、路线

```
① mch_entity 加 biz_qualification + exempt_type        ← 法定轴，最该先做
② sys_legal_form 加三个能力位 + seed                    ← 通道轴，数据
③ canPoints 硬编码搬出来 + 守卫（seed ↔ 类型一致）      ← 唯一的代码改动
④ 集市：shelf 列 + mkt_reservation + 入口               ← 见上游文档
⑤ 零星小额 10 万元/年 累计监控 → 触发强制登记引导        ← 法定义务，不是产品选择
⑥ QualificationExpiryJob 接上「资格失效 → 商品降架」    ← 与既有任务的接缝
```

**① 最该先做**：现在库里没有任何字段表达「这家店合不合规」——
在补上之前，任何「谁能交易」的判断都建立在通道分类上，而那是错的轴。

⑤ **不是可选项**。零星小额豁免是有量化上限的，超了仍不登记就是违法经营，
而平台此时是**明知的** —— 有累计数据却不作为，比不知道更糟。

## 八、附录：四个档位到底是什么

### 8.1 逐档释义

| 档 | 法律地位 | 登记 | 执照 | 固定场所 | 钱打到哪 | 出事追谁 |
|---|---|---|---|---|---|---|
| `EXEMPT` 免登记 | 自然人，**电商法 §10 明文豁免** | **依法免除** | 无 | **无** | 看通道 | 个人（实名后） |
| `UNREGISTERED` 未登记 | 自然人，**应登记而未登记** | **缺失** | 无 | — | **不收款** | 无从追偿 |
| `MICRO` 小微商户 | 自然人（**通道概念，非法律形态**） | 视情形 | 无 | **必须有** | 个人 openid | 个人，无限责任 |
| `INDIVIDUAL` 个体工商户 | 法律形态，工商登记在册 | 有 | 有 | 有 | 对私或对公 | 经营者个人，**无限责任** |
| `ENTERPRISE` 企业 | **法人** | 有 | 有 | 有 | 对公 | 公司资产，**有限责任** |

> **前两行以前是一档 `NONE`，现在拆开** —— 见 §2.4。
> 「依法免除」与「缺失」在法律上是相反的两件事：前者受豁免，后者是违法。
>
> **「固定场所」这一列区分的是 `EXEMPT` 与 `MICRO`。**
> 两者**都没有营业执照** —— 拿执照当分界线会把它们看成一回事。
> 真正拦住集市摊主的是**门店照片**：小微进件要交，而卖自家柿饼的邻居交不出。
> 详见[无资质商家方案 §2.5](./无资质商家-邻居集市方案.md)。
>
> ⚠️ **`MICRO` 的登记状态写「视情形」不是含糊。** 小微是通道档位，
> 一个小微商户在法律上可能是 `EXEMPT`（自产农副产品）也可能是 `UNREGISTERED`
> （该登记没登记却拿到了小微收款）—— **通道给他开了户，不代表他合规**。
> 这是轴 ① 与轴 ③ 必须分开的最直接理由。

有三件事这张表之外要说清楚：

**① 这一列叫 `legal_form` 其实名不副实。**
四档里只有 `INDIVIDUAL` 和 `ENTERPRISE` 是真正的法律形态。
`MICRO` 是**支付通道发明的概念** —— 免执照的自然人收款额度档，法律上他就是个自然人；
`NONE` 更是我们自己的产品概念。这一列混装了「法律形态」与「通道档位」两种东西。

不建议改名（成本高、注册表的实际职责本就是承载通道能力），
但**要知道它混了** —— 否则将来有人按「法律形态」的直觉去加档（比如加「合伙企业」），
会加出一个通道根本不区分的档。

**② 个体户与企业的分界不是规模，是责任形式。**
个体工商户的经营者承担**无限责任** —— 欠债要用个人财产偿还；
企业是有限责任，以注册资本为限。这直接决定平台的追偿可能性：
对个体户能追到人，对企业只能追到公司资产。

**③ 从 `NONE` 到 `ENTERPRISE` 是一条「可追偿性」递增的线。**
这才是四档真正的排序依据 —— 不是规模，不是资质多少：

```
NONE        无从追偿（所以平台不碰钱）
MICRO       能追到个人 —— 因为进件时留了身份证与银行卡
INDIVIDUAL  能追到个人 + 有登记实体
ENTERPRISE  有法人实体，但责任以注册资本为限
```

小微与未认证的追偿差别**就来自那次进件**：交了身份证和结算卡，
人就找得到。这也解释了为什么未认证仍要**实名** ——
实名是「弱化版的进件」，把追偿性从「无」拉到「有名有手机号」。

### 8.2 还有哪些形态

#### A 已被覆盖，不需要新档

| 形态 | 归到 | 为什么 |
|---|---|---|
| 个人独资企业 | `ENTERPRISE` | 通道不单列，能力一致 |
| 合伙企业（普通/有限） | `ENTERPRISE` | 同上 |
| 一人有限公司 | `ENTERPRISE` | 同上 |
| 分公司 / 分支机构 | 用主体的档 | 走 `mch_store` 多门店，不是新主体 |

**结论：法律上的形态有十几种，通道只认几类。**
加档的判据不是「法律上是不是一种形态」，而是「**能力是否与现有档不同**」。

#### B 通道支持、我们没开

| 形态 | 微信 | 支付宝 | 邻里场景会遇到吗 |
|---|---|---|---|
| **个人卖家** | `2500` | 待查 | **会** ← 见 8.3 |
| 事业单位 | `INSTITUTIONS` / `3` | `03` | 社区卫生站、服务中心 |
| 社会组织 | `OTHERS` / `1709` | `04` | 业委会、志愿团体 |
| 政府机关 | `GOVERNMENT` / `1708` | `05` | 街道办 |
| 农民专业合作社 | 归企业 | 归企业 | 生鲜直供可能有 |

后四类**建议暂不开**：邻里场景里数量极少，而每开一档都要把七行能力重想一遍。
真遇到了按 `ENTERPRISE` 手工进件更省。

### 8.3 一个可能推翻上游方案前提的发现

微信电商收付通的二级商户进件有 `organization_type=2500 个人卖家`：
**无执照、无对公账户、无固定经营场所**，仅限电商平台通过服务商开通。

这正是集市摊主的画像 —— 卖自家柿饼的邻居，没有店面。

如果这条路走得通，[无资质商家方案](./无资质商家-邻居集市方案.md)的**核心前提要重估**：
不是「平台收钱就担责所以不能收」，而是「让他进件成个人卖家，钱走通道，平台不碰钱」——
那样既能线上支付，平台又不是资金参与方。

> ⚠️ **这是待核实的线索，不是结论。** 要核实三件事：
> 1. `2500` 是否需要服务商资质特批
> 2. 个人卖家的交易限额（通常有单笔与年累计上限）
> 3. 支付宝有无对应档 —— 注意 seed 里 `MICRO.alipay_code` 就因为「尚未确认」留空
>
> 之所以标注这么重：本项目已经因为**未查证的前提**（曾误判「平台无法反向分账」）
> 设计并废弃过一整套方案。**在核实之前不要据此改设计。**

### 8.4 一个要核对的疑点：`wechat_code` 可能对错了

现有 seed：

```
MICRO       → wechat_code = 'MICRO'
INDIVIDUAL  → wechat_code = 'SMALL'
ENTERPRISE  → wechat_code = 'ENTERPRISE'
```

而微信特约商户进件的 `subject_type` 枚举里，
**`SUBJECT_TYPE_SMALL` 是「小微商户」**，个体户是 `SUBJECT_TYPE_INDIVIDUAL`。
看起来像是把小微的码给了个体户，而 `'MICRO'` 在该枚举里不存在。

需要拿实际接口文档核对。**这类错误只在真实进件时暴露**，
报错通常是「主体类型与资料不符」，不会指出映射错了 —— 排查的人会先怀疑资料。
