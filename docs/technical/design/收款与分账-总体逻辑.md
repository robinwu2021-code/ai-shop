>
> 本文是收口：把前面的调研结论压成一套可实现的逻辑。

## 零、一句话

**平台不碰钱：用户付的钱直接进商家的二级商户账户并冻结，
售后期过后平台一次性完成「抽佣 + 解冻」，商家自行提现。**

---

## 一、三条优先级各自意味着什么

先把口号变成可判断的标准，否则「安全」会变成谁都能拿来支持自己方案的词。

### ① 安全（不可妥协）

| 维度 | 具体标准 |
|---|---|
| **合规安全** | 平台不得对用户货款有支配权（二清）；平台不成为个税扣缴义务人 |
| **资金安全** | 退款**永不垫资**；分账不重复、不遗漏；超时有兜底 |
| **对账安全** | 每一分钱可追溯到指令与回执；账面恒等式恒成立 |

### ② 成本低

| 维度 | 具体标准 |
|---|---|
| 通道成本 | 费率争取优惠档；**不产生额外费用**（分账本身免费） |
| 资金成本 | **不垫资**（垫资 = 占用平台现金流） |
| 开发成本 | 复用已有抽象，不为边缘场景写第二套 |

### ③ 简单

| 维度 | 具体标准 |
|---|---|
| 状态少 | 结算状态机尽量少分支 |
| **不写回退逻辑** | 能靠时点安排避免的补偿逻辑，就不要写 |
| 商家可理解 | 商家能自己说清「我的钱现在在哪、什么时候能取」 |

## 二、收款逻辑

### 2.1 结构

```
平台 = 服务商（微信收付通 / 支付宝直付通）
商家 = 二级商户（小微 / 个体户 / 企业）
```

**平台自己的商户号只用来收佣金，不经手货款。**

> 【安全】这是不二清的根本：平台从头到尾没有对货款的支配权。
> 也是税上的根本：钱不经平台，平台就不是付款方，不承担扣缴义务。

### 2.2 支付时

| 步骤 | 做什么 | 依据 |
|---|---|---|
| 1 | 购物车按商家拆成子订单，共享一个支付组 | 已有模型（`ord_order` / `ord_sub_order`） |
| 2 | 调**合单支付**，一次支付、资金按商家拆分 | 收付通支持 1–50 个二级商户 |
| 3 | **下单时必须传分账标识** | 【安全】不传则资金不冻结，**事后无法补**，钱会直接可提现 |
| 4 | 资金进入各二级商户账户，**冻结态** | — |

> ⚠️ 第 3 步是整条链路最容易致命的一处：分账标识**只能在下单时传**。
> 漏传的订单，钱会按商家的结算周期直接落袋，售后时追不回。
> **这一条要写进代码注释和验收清单，不能只靠记性。**

### 2.3 渠道与主体的耦合

| 商家主体 | 小程序 | H5 | App |
|---|---|---|---|
| 小微 | ✅ | ❌ | ❌ |
| 个体户 / 企业 | ✅ | ✅ | ✅ |

下单前按 `usr_merchant.subject_type` 裁剪可用支付方式。

> 【安全】不裁剪的后果不是报错，是**用户在 App 里加购、结算时才发现付不了**。
> 可售性判断要和 `service_scope` 同级，前置到列表页。

## 三、分账与结算逻辑

### 3.1 核心决定：抽佣与解冻**放在同一个时点**，且这个时点在售后期之后

这是本文最重要的一条设计，它同时满足三条优先级：

| | 为什么 |
|---|---|
| 【安全】 | 售后期内钱还冻着 → 退款直接从商家冻结资金退，**平台永不垫资** |
| 【成本】 | 不垫资 = 不占用平台现金流 |
| 【简单】 | **永远不需要写「佣金回退」逻辑** —— 退款只可能发生在抽佣之前 |

反过来看：如果在确认收货时就抽佣、售后期内再退款，就必须实现
「退款 → 回退分账 → 佣金退回 → 重新对账」这一整套补偿链路。
**把时点往后挪一步，这套逻辑就整个不用写了。**

> 这是「简单」这一条能拿到的最大一笔收益，而且不牺牲安全——顺序上还更安全。

### 3.2 触发条件

子订单同时满足以下条件，才进入可结算：

| 条件 | 说明 |
|---|---|
| 履约完成 | 自提已核销 / 快递已确认收货 / 服务已完成 |
| **售后期已过** | 从履约完成起算 N 天（N 待产品定，建议 ≥7） |
| 无进行中售后 | 有未闭环的售后单则**阻塞**，不进入结算 |

> 【安全】第三条是硬闸：售后没闭环就解冻，等于把争议中的钱先给了一方。

### 3.3 结算动作（一次事务内完成）

```
子订单进入可结算
      │
      ├─ 1. 生成结算单 stl_bill（幂等：一子单一张，唯一键已有）
      │
      ├─ 2. 调分账接口：平台佣金 → 平台商户号
      │      基数 = 扣完支付手续费后的可分金额
      │
      └─ 3. 解冻剩余资金 → 商家可用余额
             （分账接口传 unfreeze_unsplit，或分账后单独调解冻）
```

**佣金基数必须是扣完支付手续费后的金额**，不是订单原价。
按原价算每笔差几分钱，累积起来对不上账。

### 3.4 状态机（沿用现有 `stl_bill.status`）

```
PENDING ──▶ SPLITTING ──▶ SPLIT（终态）
   │            │
   │            └──▶ FAILED ──▶ SPLITTING（重试）
   │                    │
   └──────────────────▶ FROZEN_BACK（终态：超时兜底）
```

| 状态 | 含义 | 【安全】要求 |
|---|---|---|
| `PENDING` | 已生成，待下发 | — |
| `SPLITTING` | 指令已发，等回执 | **不可再次下发**（靠 `request_no` 唯一键） |
| `SPLIT` | 成功 | 终态 |
| `FAILED` | 失败 | 记 `last_error`，重试有上限，超限转人工 |
| `FROZEN_BACK` | 超时未分账，资金已自动解冻 | **必须有兜底任务盯着**，否则钱悄悄回到商家而佣金没收 |

> ⚠️ `FROZEN_BACK` 不是异常分支，是**必然会发生**的分支：
> 微信分账冻结期最长 30 天、收付通默认 180 天，超期资金自动解冻。
> 如果售后期 + 处理延迟逼近这个窗口，佣金就收不到了。
> **调度必须在窗口到期前主动结算，不能等业务条件慢慢满足。**

### 3.5 退款

| 时点 | 处理 | 平台是否垫资 |
|---|---|---|
| 结算前（售后期内） | 直接从商家冻结资金退 | **否** |
| 结算后 | 需分账回退（180 天内可回退） | 否，但链路变长 |

> 【安全】设计目标是让**绝大多数退款落在「结算前」**。
> 售后期设得比退款高发期长，是最省事的做法——比事后回退可靠得多。

## 四、优先级冲突时怎么让步

这一节记录几处「三条优先级打架」的地方与裁决，避免以后有人按单一维度改回去。

### 4.1 小微零门槛 vs 税务与渠道　→ 让「简单」

| 方案 | 简单 | 安全 |
|---|---|---|
| 全用小微 | ✅ 5 分钟进件 | ❌ 税务定性模糊、平台可能担扣缴责任、渠道锁死小程序 |
| 个体户为主 | ❌ 要办照 | ✅ 税清晰、平台无扣缴义务、全渠道 |

**裁决：个体户为主，小微仅作过渡态**，并由平台提供代办降低门槛。
「简单」用**代办**去补，而不是用**降低合规标准**去换。

### 4.2 立即结算 vs 售后期后结算　→ 让「简单」中的「快」

商家当然希望钱早点到。但早结算 = 退款要垫资 + 要写回退逻辑。

**裁决：售后期后结算。** 对商家的补偿方式是**把周期讲清楚**
（B 端要能看到「本单 X 月 X 日可结」），而不是提前放款。

### 4.3 双通道（微信 + 支付宝）vs 一期只做微信　→ 让「成本」

两个通道 = 两套进件、两套对账、两套回调。

**裁决：一期只做微信收付通**，支付宝直付通在模型上预留
（`sub_mchid` 要能存多通道），实现放二期。
理由是【成本】优先于【简单】之外的覆盖面——但**模型必须先留位**，
否则二期要改表。

## 五、落到代码

| 组件 | 现状 | 需要变成 |
|---|---|---|
| `SplitGateway` | 分账抽象（stub 实现） | 实现改为收付通：**合单支付 + 分账 + 解冻**三个动作 |
| `stl_bill` | 一子单一张，状态机已有 | 语义微调：`gross_minor` = **扣完支付手续费**后的可分金额 |
| `stl_split_log` | 指令与回执分开存，append-only | 不变——这个设计本来就对 |
| `ord_sub_order` | 有状态与履约字段 | 补「可结算时间」= 履约完成 + 售后期 |
| `usr_merchant` | **无任何收款/主体字段** | 补 `subject_type` / `sub_mchid` / 进件状态 / `authorized_pay_methods` / `invoice_capable` |
| 下单 | 不传分账标识 | **必须传**——漏传无法补救 |
| 调度 | 无 | 两个任务：①到点结算 ②冻结窗口到期前兜底 |

`SplitGateway` 当初抽成接口就是为了「接真通道时只换实现」——
方案从「平台收款+分账」改成「收付通」之后，这个抽象依然成立，
改的是实现与语义，不是调用方。

## 六、验收要点（给后端）

按【安全】优先，这几条是不能过的红线：

1. 下单**必带分账标识**，缺失即拒绝下单（不是记日志）
2. 结算单**一子单一张**，靠唯一键保证，不靠应用层判断
3. 分账指令带**平台侧幂等号**，重复下发不产生第二笔
4. 售后未闭环的子单**不得进入结算**
5. 冻结窗口到期前**必须已发起结算**，兜底任务不可缺
6. 佣金基数 = **扣费后**金额，不是订单原价
7. `FROZEN_BACK` 必须告警——它意味着这笔佣金已经收不到了
