## 0. 现在是什么状态

`shop.report.enabled` **默认 false**，所以：

- 报表库的数据源、迁移、DAO **一个 bean 都不装**；
- 日结作业 `ReportDailyRollupJob` 不装（它同时挂着 `shop.job.enabled`）；
- `/biz/report/daily` 这个端点**不存在**（整个 Controller 随开关装配）。

也就是说：**不加配置的话，这套东西对生产完全没有影响**，也完全没有作用。

---

## 1. 为什么不是「打开开关重启」那么简单

第二个数据源一出现，Spring Boot 的三处自动配置就整体退让
（`DataSource` / `SqlSessionFactory` / `Flyway` 都挂着 `@ConditionalOnMissingBean`）。
2026-08-27 进销存上线时踩过：19 张表连同迁移历史一起建进了**平台库**，
自己的连接池从不启动，**日志里一行 ERROR 都没有**。

代码侧已经按那次教训写了四道（见 `ReportDataSourceConfig` 的类注释与
`ReportWiringSmokeTest` 的三条断言），但**启用当天仍要按第 2 步逐条看**：
那四道防的是「接错了」，防不了「库没建、账号没授权」。

## 2. 步骤

### 第 0 步 · 建库与账号（**需要有 DB 凭据的人执行**）

```sql
CREATE DATABASE ai_shop_report DEFAULT CHARSET utf8mb4;
CREATE USER 'ai_shop_report'@'127.0.0.1' IDENTIFIED BY '<强口令>';
-- **只授这一个库**：业务连不到报表库要靠授权强制，不靠自觉
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, DROP
  ON ai_shop_report.* TO 'ai_shop_report'@'127.0.0.1';
FLUSH PRIVILEGES;
```

> 表由 Flyway 自己建（`db/report` 的 V1，历史表 `rpt_flyway_history`），不用手工建。
>
> ⚠️ 生产主库是 **MySQL 9.7**，V1 里没有写 `COLLATE` 就是为了这个
> （`uca1400` 是 MariaDB 的）。**但 V1 至今只在 H2 上跑过** ——
> 按本仓库的规矩，迁移要在**真库副本**上先跑一遍（V336 为此在线上挂过 5 分钟）。

### 第 1 步 · 配置

`shop-app.env` 追加四行：

```sh
SHOP_REPORT_ENABLED=true
SHOP_REPORT_DATASOURCE_URL=jdbc:mysql://127.0.0.1:3306/ai_shop_report?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai
SHOP_REPORT_DATASOURCE_USERNAME=ai_shop_report
SHOP_REPORT_DATASOURCE_PASSWORD=<上一步的口令>
```

> **为什么这四个名字直接能用**：报表读配置走的是 `@ConfigurationProperties`，
> 它认 Spring 的宽松绑定（`SHOP_REPORT_DATASOURCE_URL` → `shop.report.datasource.url`）。
> 本仓库记过一条「`@Value` 不认 kebab-case，配了等于没配」——
> **那是 `@Value` 的坑，与这里不是一个机制**，别因为那条而去加一层 yml 映射。

日结还要 `SHOP_JOB_ENABLED=true`（它同时挂着两个开关）。
只开 report 不开 job 的话，端点能用但**没有数据** —— 因为没人往里写。

可调项（都有默认值，一般不用配）：

| 配置 | 默认 | 作用 |
|---|---|---|
| `shop.report.rollback-days` | `3` | 日结每次重算几天。**补历史就是把它调大跑一次** |
| `shop.job.report-daily-rollup.cron` | `0 30 1 * * *` | 日结的时间 |
| `shop.report.flyway-enabled` | `true` | 关掉它就不建表，只在排查时用 |

### 第 2 步 · 重启并**只看四件事**

```bash
# 1) 起来了吗
systemctl status ai-shop

# 2) 平台库的迁移**还在跑**吗 —— 这条最要紧
#    报表的迁移凭证刻意不是 Flyway 类型，就是为了不让平台的迁移整体退让。
#    期望：版本号是本次发版该有的那个，不是停在启用报表那天
mysql -N -B ai_shop -e "select max(version) from flyway_schema_history;"

# 3) 表建在**报表库**了吗（不是平台库）
mysql -N -B ai_shop_report -e "show tables;"     # 期望：rpt_daily_store / rpt_job_watermark / rpt_flyway_history
mysql -N -B ai_shop      -e "show tables like 'rpt_%';"   # 期望：**空**

# 4) 日结跑了吗
mysql -N -B ai_shop_report -e "select job_key, last_stat_date, rows_written from rpt_job_watermark;"
```

**第 3 条的两句要一起看。** 只看第一句的话，「表建在报表库」与
「表同时建在两个库」分不出来 —— 而后者正是接错数据源的样子。

## 3. 启用之后

- **首屏会是空的**：日结 01:30 才跑，且只算 T-1 及以前。启用当天白天打开
  「近几日」，除今天外每一行都是「统计中」（`complete=false`）——
  **那是对的，不是故障**。
- 要立刻有数：把 `shop.report.rollback-days` 调到覆盖想看的天数，手工触发一次日结。
- **今天那一格永远是现算的**，不依赖日结（见 TDD §2.4）。

---

## 4. 回退

把 `SHOP_REPORT_ENABLED` 改回 `false` 重启即可：
所有 bean 连同端点一起消失，平台库**一个字节都没被动过**
（报表库是只写不读业务的派生库，业务链路不依赖它）。
库可以留着，下次打开时日结会把窗口内的天重算一遍。
