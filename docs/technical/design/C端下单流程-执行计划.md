## B1 · 优惠面板

**为什么第一**：用户这次最直接的抱怨就是「看不到券、不知道为什么减」。而后端能力已经齐了，端上只是没调。

### 落点

| 层 | 改动 |
|---|---|
| 契约 | 新增 `couponBest(items)` → `POST /mp/coupon/best`（后端已有，端上没登记）。登记四处：`endpoints` / `contract` / `http` / `mocks`，外加 `gen-openapi.mjs` 的 `RESPONSE_TYPES` |
| 后端 | `BestResult.Unusable` 加 `code` 与 `gapMinor`（见下）；`reason` 保留不动 |
| 类型 | `CouponBestResult { bestUserCouponNo, discountMinor, usable: UserCoupon[], unusable: Array<{ userCouponNo, reason }> }`（对齐后端 `BestResult`） |
| 页面 | `pages/order-confirm`：券那一行点开换成**面板**（sh-sheet），三段：自动参与的活动 / 可用券 / 不可用券 |
| 数据 | 活动那一段来自预览返回的 `discountLines` 里 `kind === "ACTIVITY"` 的条目（0.1.54 已下发）；券两段来自 `couponBest` |
| 文案 | 三语加：面板标题、「自动参与，无需选择」、不可用原因的兜底句 |

### 不可用原因：后端要先改成「码 + 数」

**实测（2026-09-21）**：后端 `CouponServiceImpl#reasonOfUnusable` 返回的是**中文硬编码句子**，
而且门槛那句是 `"未达使用门槛，还差 " + (门槛 - 已选) + " 分"` —— 以**分**为单位。
照搬到界面上就是「还差 2000 分」，而买家心里的单位是「¥20.00」；
英文与阿语用户还会看到中文。

所以 B1 **含一处后端改动**（向后兼容）：

```java
record Unusable(String userCouponNo, String reason,   // 保留：老端上还在读
                String code,                          // 新：BELOW_THRESHOLD / EXPIRED / NOT_STARTED / OUT_OF_SCOPE
                Long gapMinor)                        // 新：门槛差额（分），其余场景为 null
```

- `reason` 原样保留 —— 老版本小程序还在用户手机上跑着，删了它那边就空白。
- 端上按 `code` 出文案，金额用 `money(gapMinor)` 自己格式化：

| code | 端上文案 |
|---|---|
| `BELOW_THRESHOLD` | 还差 ¥20.00 到门槛 |
| `EXPIRED` | 已过期（09-18） |
| `NOT_STARTED` | 09-25 才能用 |
| `OUT_OF_SCOPE` | 本单没有这家店的商品 |

**拿不到 code 时回落显示 `reason` 原句**（老后端 / 新场景），一个都没有时**券照样列出来**，只是不说原因。

### 测试

`c-app/tests/coupon-panel.test.ts`：
1. 面板三段各自渲染；活动段取自 `discountLines`；
2. 不可用券**必须出现**（消融：过滤掉 unusable → 红）；
3. 原因码映射；未知码回落后端原句；**「还差」用元不用分**（钉住这条，它正是现在的缺陷）；
4. 选中某张券后重算（调 `orderPreview` 带 couponNo）。

后端 `CouponFlowTest`（或既有券用例）：`best` 返回的 `unusable` 带 `code` 与 `gapMinor`，
且 `gapMinor` 等于门槛减已选金额。消融：不下发 code → 端上那条映射测试红。

### 风险

- `/mp/coupon/best` 在「后端做了没入口」清单上 —— 接上之后那条欠账 -1，**闸门基线要同步减**。
- 线上没有券数据，真机上看不出效果；验证靠 mock + 单测（与 0.1.54 那次同样的处境）。

## B2 · 下单页可改数量

### 落点

| 层 | 改动 |
|---|---|
| 页面 | 商品行加步进器；`items` 从只读变可编辑（它现在来自购物车快照或直购参数） |
| 规则 | 上限 = `min(可售库存, 每人限购剩余)`；到顶压暗并说明是哪一条 |
| 重算 | 改数量 → 300ms 防抖 → `orderPreview` → 金额与 `discountLines` 整体替换 |
| 购物车 | **下单页改数量不写回购物车**（它是这一单的意图，不是购物车状态）；提交成功后按实际下单的行清购物车 |
| 直购 | 直购（「立即购买」）路径的数量本来就来自规格面板，这里同样可改 |
| 后端 | 预览要带回**每行可买上限**（库存与限购取小），否则端上只能猜 |

### 契约

`OrderPreview.items[]` 加 `maxQty`（可买上限）与 `limitReason`（`STOCK` / `PER_USER`）。
预览本来就逐行算过库存，这里只是把结论说出来。

### 测试

- 后端：预览返回 `maxQty`；库存 3 时 `maxQty=3`，限购 2 时 `maxQty=2`（取小）。消融：不下发 → 红。
- 端上 `qty-edit.test.ts`：加号到上限禁用；改数量触发一次重算（防抖内多次改只发一次）；
  数量改到 0 移出该行；最后一行移出后提交按钮不可点。

### 风险

- **券可能因金额变化失效**：重算后若原选中的券不在 `usable` 里，要当场取消选择并提示，
  而不是提交时才报错。
- 防抖 + 竞态：沿用现有 `amountSeq` 那套（过期响应直接丢弃）。

## B3 · 一键支付

### 现状

```
下单页 submit → createOrder → redirectTo(收银台) → 用户再点一次 → payOrder → requestPayment
```

### 改成

```
下单页「立即支付」→ createOrder → payOrder → requestPayment
      ├─ 成功 → redirectTo(支付结果 / 订单详情)
      └─ 失败 / 取消 → redirectTo(收银台页，带原因与倒计时)
```

- 收银台页**保留**，只在「支付中断」与「订单列表点去支付」两种入口下出现（原型 k11）。
- 当面付：没有 `requestPayment` 这一步，建单后直接进订单详情；按钮文案随支付方式变
  （「立即支付」/「提交订单」）。
- **端上不自判支付成功**（收银台页里那条注释写着，必须保留）：`requestPayment` 返回只代表
  用户完成了交互，成功与否以后端订单状态为准。

### 测试

`c-app/tests/one-tap-pay.test.ts`：
1. 提交成功后**直接**调 `payOrder` + `requestPayment`，中间不 `redirectTo` 收银台（消融：恢复旧链路 → 红）；
2. `requestPayment` 失败 → 落收银台页且带 `orderNo`；
3. 当面付不调 `requestPayment`。

### 风险

- 这是支付链路，改错了是「钱的路」。**灰度**：先只对微信支付生效，当面付维持旧路径。
- 真机验不了（支付仍 banned）——申诉通过前只能在 mock 与单测上验，上线后首单要盯日志。

## B4 · 支付方式与失败原因

- 支付方式提到下单页一行（现在在页面里但位置靠后），可选集由 `orderCapability` 给。
- **当面付 × 平台券互斥**：切换时当场提示「会取消这张券」，而不是提交时报错。
- 建单失败的报错从一句笼统的话，改成**指名哪一条变了**：库存 / 券 / 活动 / 配送范围。
  后端已有分类错误码，端上按码映射文案；未知码回落后端原句。

测试：`checkout-errors.test.ts` —— 四类错误各映射到各自的一句话；未知码回落。

## B6 · 交易口径：退款退券退积分、关单回滚配额

用户 2026-09-21 拍板：按建议执行。**这批只动后端，端上不改**（端上只是把结果显示出来，那在 B5）。

### B6-1 关单回滚活动配额

现状：`closeOne` 释放了库存、券、积分、预约时段，**没有回滚活动配额** ——
限量 100 份的活动会被没付款的单吃掉量，而运营看到的「已用 4 份」里有几份从来没成交。

改法：

- `CampaignPort` 加 `default void release(String orderNo) {}`；
- 新模型实现：按 `pmt_apply` 里这一单的行，`quota_used -= qty`、`budget_used_minor -= amount`，
  并把那几行作废（逻辑删）。**幂等**：行已作废就什么都不做。
- 老模型（`mkt_campaign`）没有这张账，空实现。
- `closeOne` 里与 `stockPort.release` 并排调一次。

测试：`OrderCloseFlowTest`（或既有关单用例）——建单后关单，活动 `quota_used` 回到 0；
关两次仍是 0。消融：不调 release → 红。

### B6-2 退款退券与退积分（整单退则退）

口径：**整单退才退券与积分，部分退不退**。判据是「这笔主单下所有子单都进了 `REFUNDED`」。

- 券：直接复用 `couponPort.release(orderNo)` —— 它把 `USED` 的券改回 `UNUSED`，
  付款后同样适用（实测读过实现）。
- 积分**有一处硬约束**：`pointsPort.reverse` 只认 `PENDING` 的 USE 流水，
  而付款成功时那条流水已经转成 `CONFIRMED`（`PointsServiceImpl` 里三态：PENDING / CONFIRMED / REVERSED）。
  所以退款这条路要在 pay-domain 里**新开一个方法**（如 `refundUse(subOrderNo, reason)`）：
  冲正已确认的抵扣、并收回这一单已发放的购物积分（发放时落的是 `pending_balance`，
  售后期内要能收回 —— 这一条发放侧本来就预留了）。
  **不要把它塞进 `reverse`**：那个方法的语义是「没付成的单退回预占」，两件事混在一个方法里，
  以后没人分得清哪一种情况该调哪个。
- 已发放的购物积分：整单退时一并收回。

测试：`RefundFlowTest` —— 付款 → 整单退款 → 券回到 `UNUSED`、抵扣的分回到账户、
发放的分被收回；部分退款时三样都不动。消融：任一项不做 → 各自一条红。

### 风险

- **动的是账**。券、积分、活动配额三者都影响结算口径（券的平台补贴已经结给商家了）。
  上线前要与结算域对一次账：退券之后那笔补贴怎么冲。
- 这批**不做灰度**做不了 —— 一旦退款发生就会走到。所以先在测试库上把三条链路各跑一遍，
  再按「先上后端、观察一天」的节奏走。
