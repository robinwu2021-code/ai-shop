## 1. 设计结论

业务域选择受支持的scene和可信sourceRef；打印中心校验来源事实，按场景、模板变体和作用域解析模板。业务调用方不能自由指定另一场景的模板。设备适配器只做排版与投递，不判断这是预结单还是付款凭证。

设计者沿用服务端场景选择方案：相较前端任选模板，服务端可强制限制票据语义；相较将所有差异塞进一张通用模板，独立场景能防止未付款票据误带“已结清”。同场景的58/80mm为不同变体，不增加业务场景。

## 3. 业务触发边界

- ORDER_PAID仅用于被选定为线上订单收据的交易；POS结账使用CASHIER_RECEIPT，餐饮结账使用CHECKOUT。事实所有者根据业务流程输出receiptIntentKey和唯一收据场景；不能对同一支付同时默认触发三类收据。PICKING、KITCHEN等作业票可独立并行触发。多次部分支付需各自事实号，最终结账合并收据另有结账事实，不凭一次支付事件伪造结清。
- KITCHEN/KITCHEN_ADD以明确下达/加菜事实为准。先付流程也要映射到下达事实，不能分别消费支付和下达后各打印一次。加菜单只含本次新增；退菜单只含对应原票的取消数量；催菜单不能增加制作数量。
- KITCHEN_VOID/URGE必须关联对应原票及原档口，不能拿当前路由盲目指向另一个厨房。原票未生成时先定位需求和业务事实；确认从未执行的原票只取消，不伪造原票号。原票UNKNOWN时冲销票注明“原票结果待核实”，由业务工作流决定是否需要通知档口。
- PRE_BILL允许人工打印当前账单版本，必须固定“未结账、非支付凭证”；CHECKOUT需要已确认结清事实。SERVICE_COMPLETE不是已支付凭证。退款申请/处理中不能打印REFUND_RECEIPT，充值待支付不能打印RECHARGE_RECEIPT。
- CARD_BALANCE、RECHARGE_RECEIPT的余次/余额取该笔账完成后的不可变账务快照。补打不查询当前余额；禁止沿用旧草案“耗卡完成时现查当前余额”的规则。当前余额查询是另一个界面功能。
- HANDOVER/DAY_END仅打印已封存报告版本，不在渲染阶段临时聚合实时交易；跨日、跨币种按报告服务正式合同拆分。配送交接单不是承运商面单或收件签收证明。
- APPT_CONFIRM不代表付款；SERVICE_START只包含岗位执行必需且已授权的安全提醒，不输出完整病史、证件或未经授权的护理档案。顾客电话默认脱敏；完整配送地址只能向实际配送岗位授权，预览默认脱敏，不能因模板覆盖而扩大字段权限。
- 自动场景的人工入口只允许重现已经存在的可信事实；已有原任务优先走补打/加印。EXISTING_FACT沿用自动路径的triggerType/triggerInstance/bizRevision，按原trigger_key查找，不能因人工操作号不同而再建初打需求。仅PRE_BILL可调用CURRENT_VERSION；PRINTER_TEST走P10固定样式。预约确认、退款成功和权益耗次等不能靠用户自报scene制造事实。

## 4. 模板解析与调用合同

解析顺序：校验场景和来源 → 获取固定版本快照 → 按档口/任务拆document → 路由到目标打印机 → 确定纸宽变体 → 选择模板 → 渲染与冻结 → 创建任务。模板选择在投递前完成，代理不会自行选择另一模板。

每个路由target使用以下二选一配置：

```json
{"targetKey":"main","printerNo":"P001","copies":1,"required":true,"templateSelection":{"mode":"SCENE_DEFAULT","variantCode":"STANDARD_80"}}
```

```json
{"targetKey":"main","printerNo":"P001","copies":1,"required":true,"templateSelection":{"mode":"PINNED_VERSION","variantCode":"STANDARD_80","templateVersionNo":"TV001"}}
```

SCENE_DEFAULT：同scene＋variantCode按“门店已发布覆盖→主体已发布默认→平台已发布默认→内置同场景极简”解析。未配置/禁用的覆盖可跳过；存在但渲染失败的候选降级且告警。mode/variantCode不接受任意表达式，STANDARD_58/80必须与目标纸宽匹配。发布路由时验证可用性；生成时再次校验并按批次一致读取候选头指针、固定版本。

PINNED_VERSION：版本必须PUBLISHED、同scene、同variantCode、同payloadSchemaVersion且授权可读。固定版本失败时BLOCKED并告警，不暗中换模板；运营需显式改路由或切回SCENE_DEFAULT后恢复尚未生成的需求。模板发布页显示固定引用，不承诺新发布自动作用于固定路由。

同一头唯一键为(tenant,entity,scopeKey,scene,variantCode)；平台/主体/门店最多各有一个已发布的当前版本。定义文件definitionKey是种子定义键，不是运行时templateNo/versionNo；部署时按语义键幂等建立草稿并走发布流程，不能把JSON导入当作自动启用门店。

内置极简仍保留该场景所有强制字段及醒目标题，不能用后厨极简替代退款或支付凭证。所需业务事实缺失/超长到无法安全展示、没有同宽同场景模板、设备不能保留强制标识时BLOCKED；“兜底”不等于丢掉金额、原票号、安全提示或未付款声明。极简模板也要按场景版本测试。

补打/加印使用原job的document_snapshot、template_version_no、template_resolution_snapshot及renderer_version，服务端仅更新受控系统插槽（补打/加印标识、新票号、副本序号和本次生成时间），原业务时间、原票号和业务内容保留；不能把原jobNo照抄为新任务身份。原模板已升级或停用不影响重现原快照；若旧版渲染器已不可用则阻断，不自动用最新版重渲染。

### 4.1 按场景调用示例

人工查看当前餐饮账单，只能选预结场景；服务端选PRE_BILL.STANDARD_58/80，不接受调用方指定结账模板：

```http
POST /biz/print/requests
Idempotency-Key: 2a400843-d6f5-4ad9-bb45-552770f7ff01
```

```json
{"storeNo":"S001","scene":"PRE_BILL","sourceRef":{"type":"FOOD_BILL","no":"FB001","factNo":"BILL-V7","revision":"7"},"expectedSourceRevision":"7","printMode":"CURRENT_VERSION"}
```

重现已支付线上订单事实，选择ORDER_PAID；如果该事实已经有初打需求则返回原需求，不再出一套票：

```json
{"storeNo":"S001","scene":"ORDER_PAID","sourceRef":{"type":"SUB_ORDER","no":"SO001","factNo":"PAY-FACT001","revision":"3"},"expectedSourceRevision":"3","printMode":"EXISTING_FACT"}
```

自动后厨打印由餐饮下达事实适配成内部PrintIntent，scene=KITCHEN、source.type=KITCHEN_RELEASE；加菜事实选KITCHEN_ADD、退菜事实选KITCHEN_VOID。内部合同按同一场景目录验证，不把前端传入scene当作可信下达事件。以上编号均为示例，真实来源不存在或版本/状态不符时拒绝。

同一餐饮订单可有KITCHEN、PRE_BILL、CHECKOUT三种需求，对应制作单、未结账预结单、已结清收据；三者独立追踪，不互相替代。打印中心向代理下发的是已冻结的document和templateResolution，不要求代理再次判断业务场景。

## 5. 通用数据与受控布局

通用必填：scene,payloadSchemaVersion,store.name/timezone,source.type/no/factNo/revision/occurredAt,system.ticketNo/jobKind/copyIndex/generatedAt/warnings。system字段仅由服务端赋值，模板编辑器不能覆盖。目录的commonRequiredFields/requiredFields表示输入必填，mandatoryPrintPaths表示票面必显；store.timezone与source.type用于校验/格式化而不强制占独立票面行。source.factNo必须显示以便排查；currency由每个Money格式化输出覆盖，system.jobKind/copyIndex由不可删systemMarks覆盖（正常票也显示“正本/测试”与副本序号，不能只在补打时出现），其他必显路径必须有对应绑定区块。字段白名单按场景单独提供，未授权字段即使存在源快照也不传给模板。

Money={minor:"8800",currency:"CNY",scale:2}；金额为最小单位整数字符串，不使用浮点；所有金额币种/精度须与来源合同一致。数量为Decimal字符串，按来源单位精度显示。时间按门店时区格式化，票面生成时间与业务发生时间分别保留，不把补打时间当原交易时间。

每个场景目录列出requiredFields、lineMode、lineFields和lineRequiredFields；仅可打印允许的行字段。SALE包含金额；KITCHEN不含价格、余额、顾客电话；SERVICE只含项目执行字段。支付类payments为净入账分项，不是顾客交付现金，现金交付/找零单独显示。支付分项和paidAmount对账、tenderedAmount-changeAmount=现金净收、退款行金额合计等由来源所有者校验，渲染器不重算账。

布局DSL白名单：systemMarks、text、keyValue、lineItems、payments。绑定只读路径，不执行脚本或SQL；遍历上限、金额/时间formatter、换行和截断由渲染器校验。systemMarks和场景mandatoryNotice不可被门店编辑删除/遮挡；源文本控制字符转义后才能输出。keyValue可使用受限omitIfEmpty隐藏可选空字段，不能隐藏强制字段/声明。渲染器根据完整布局校验每个mandatoryPrintPaths均由绑定区块或明确规定的系统、格式化规则覆盖，不能用“字段存在但模板未展示”通过发布。

58mm明细采用多行堆叠，80mm采用名称/数量/金额列；字宽、字体、二维码、走纸和切纸由经验证设备档案决定，不硬编码“58mm等于固定字符数”。长订单分页必须每联带标题、票号、分页号和副本标识，不能截掉后半订单。金额汇总可只在末联，但取消/催菜/安全提醒每联必要处重复。

system.warnings为服务端产生的受控警示码列表，systemMarks必须将每个码映射为不可删除的中文警示，未知警示码阻断渲染。KITCHEN_VOID/URGE额外具有system.originalTicketState={jobNo,revision,status,observedAt}，由打印中心查原任务并冻结到payload/document/resolution快照，fields.originalTicketNo必须与其jobNo一致；systemMarks展示原票号、状态和观测时间。status=UNKNOWN时强制注入ORIGINAL_TICKET_RESULT_UNKNOWN并打印【原票结果待核实，请核对原制作情况】。警示不依赖可编辑模板条件，补打仍保留生成当时警示。

系统标识：INITIAL正常；REPRINT顶部【补打】＋原票号＋原因；EXTRA顶部【加印】＋原票号＋份序；人工CURRENT_VERSION顶部【人工打印当前版本】。制作/开工票的补打加印另带【重复凭证，勿重复执行】；退菜/催菜本身保持语义，不再变成制作命令。操作者不能通过模板清除标识。

## 7. 数据库/API同步调整

- 场景变体不增加业务表；模拟/PDF扩展后打印模块为22表，另有订单事实表归trade所有。prn_template增加variant_code并扩展作用域唯一键；prn_template_version增加paper_width_mm、payload_schema_version；prn_job增加template_resolution_snapshot。字段字典和DDL同步更新。
- C01返回场景目录及可用变体；C06建模板必须scene＋variantCode；C07/C08/C10校验纸宽、来源schema和强制字段；C18解析预演、C19读取字段目录、C20读取脱敏样例；详见API设计。
- J03根据场景允许的manualMode使用CURRENT_VERSION或EXISTING_FACT；业务端不提交templateVersionNo。已有自动事实已生成票据时返回原需求并提示补打入口，不能借EXISTING_FACT新建一批。PINNED_VERSION仅由有配置权限的路由管理选择。
- job.template_resolution_snapshot保存mode、scene、variantCode、sourceSchemaVersion、选中templateNo/versionNo或builtinKey、rendererVersion、所有尝试候选及降级原因；不保存不受权内容。冻结该记录和文档，与批次生成同事务。

## 8. 兼容旧稿与验收

旧场景ORDER_PAID/CASHIER_RECEIPT/PICKING/KITCHEN/KITCHEN_VOID/URGE/PRE_BILL/CHECKOUT/APPT_CONFIRM/SERVICE_START/CARD_BALANCE/HANDOVER保持代码。新增场景按目录注册，不把KITCHEN_ADD和REPRINT混为同义；新增业务菜品与重复打印是不同事实。旧路由target.templateVersionNo须迁为同scene的PINNED_VERSION并补variantCode；未明确模板的路由迁为SCENE_DEFAULT，校验后发布，不静默猜测其他场景。

已有单场景模板头升级时从已发布版本的纸宽校验后分配variantCode。旧58/80混用但无明确纸宽的配置进入待处理，不能盲目填80。此处仍为设计稿调整，不改已上线Flyway迁移。

验收：20场景×2纸宽；场景与来源类型不符拒绝；预结票不能显示已收款；模板跨场景引用拒绝；门店覆盖优先且仅影响对应变体；默认链降级有原因且必填完整；PINNED失败不暗换；模板发布后旧任务补打仍原样；加菜只新增、退菜只撤销、催菜不重做；余次补打保持本笔历史余次；安全字段和地址按岗位裁剪；长订单不截行；重复支付/下达事实不重复出票。

样例数据只用于设计和预览，不可作为订单、退款、耗次等业务事实。数据库兼容执行、渲染输出和真机效果属于后续实施验证。

## 9. ORDER_PAID首票基线及输出适配

本场景的58/80mm模板已同步首票字段：订单号、下单/支付时间、履约、商品数量、商品合计、优惠、配送费、实付和支付分项；可选取货码/备注/店址电话/支付流水。示例为牛奶2瓶36元＋大米1袋64元－优惠12元＋配送0元＝实付88元。优惠数据取正数，计算减去；混合单位不显示成“3件”。

无外部支付流水的免支付订单由可信NO_CASH事实提供“免支付”0金额项，隐藏支付流水，不能客户端自行构造。独立税费、服务费或权益抵扣需要正式来源金额组成及模板扩展，缺失时BLOCKED而不是错打。完整可审阅小票见总方案第4节。

PrintLayout将冻结文档排为≤270mm分联，PDF与设备消费同一布局。模拟每页系统水印不可删，PDF导出副本不表示设备已出纸；补打沿用原业务/模板/布局快照，仅更新受控系统插槽。
