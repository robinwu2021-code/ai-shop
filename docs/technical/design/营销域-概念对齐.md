# 营销域 · 概念对齐

> 状态：**草稿 · 待确认** · 2026-09-18
> 起因：店主「先整理概念，然后整理架构，再 UI 交互」
> 这一份**只定义概念**。页面与端点在「架构」那一份，界面在「UI」那一份。
> 相关：`promotion` 包的 `package-info`

---

## 一、为什么先对概念

这一片今天有**两套模型、四个入口、六个页面**，而同一个词在不同地方指不同的东西：

- 「活动」在工作台上指 `pmt_activity`，在营销页里指 `mkt_campaign`；
- 「团购」既指一条**规则**（几人成团、成团价），也指**一个团**（谁开的、凑齐没有）；
- 「券」既指**模板**（满 30 减 5 这个设计），也指**用户手上那一张**（有有效期、能核销）。

**名字重合的两个东西，讨论时会轮流指代**，方案就是这么写歪的。先把词钉死。

## 二、六个概念

### 2.1 营销

**商家为了多卖货而做的全部安排。** 它是一个<b>容器</b>，不是一个功能 ——
下面装着活动与券两类，没有自己的数据。

### 2.2 活动（`pmt_activity`）

**一条在下单时自动生效的规则。** 商家配一次，之后谁下单命中谁就享受，
<b>用户不需要做任何动作</b>。

一个活动由五件事定义，缺一不可：

| 组成 | 是什么 | 取值 |
|---|---|---|
| **触发** | 什么情况下算命中 | 无条件 / 订单满额 / 买够件数 / 命中商品 / **拼够人数** |
| **优惠** | 命中之后给什么 | 减金额 / 改单价 / 送商品 / 发券 |
| **排期** | 什么时候生效 | 短期（有起有止）/ 长期 / 周期（每周几、某时段） |
| **受众** | 给谁 | 所有人 / 非会员 / 沉睡 / 熟客 |
| **限量** | 最多给多少 | 份数 / 预算，二者至少有一个（长期活动强制） |

> **「玩法」是触发 × 优惠的组合，不是第六种属性。**
> 满减 = 满额 × 减金额；特价 = 命中商品 × 改单价；
> 团购 = 拼够人数 × 改单价；买赠 = 买够件数 × 送商品。
> 加新玩法是加新组合 —— 这条是 `PmtActivity` 类注释里写死的。

### 2.3 券（模板，`pmt_coupon`）

**一张券的设计**：面额或折扣、门槛、有效期规则、发多少张。
它<b>不作用在任何订单上</b> —— 券要先发到人手上才有意义。

### 2.4 用户券（`pmt_user_coupon`）

**发到某个人手上的那一张。** 有效期落在这一行上（领的那一刻算好），
有自己的状态（未用 / 已用 / 过期）。

> **模板改了不影响已发出的那些。** 这条是硬的：现算有效期的话，
> 商家改一次模板天数会把已发出的券一起改掉，而用户手上昨天还能用的券今天就过期了。

### 2.5 团购活动 vs 团

**这两个最容易混，必须分开。**

| | 团购活动（`pmt_activity`，`GROUP × PRICE`） | 团（`mkt_group_buy`） |
|---|---|---|
| 是什么 | **规则**：这些货、几人成团、成团价、什么时候 | **实例**：这一团，谁开的、到哪个自提点、凑齐没有 |
| 谁建 | 商家，在活动里 | 商家或用户，按规则开出来 |
| 生命周期 | 起止 / 暂停 / 结束 | 开团 → 凑人 → 成团或到期 |
| 数量关系 | 一条规则 | 可以开出**很多团** |

> 「活动结束了」与「这一团散了」**不是同一件事**。混在一起的话，
> 商家停掉活动会以为已经开出去的团也没了（它们不会）。

### 2.6 优惠发生记录（`pmt_apply`）

**每一次真的减了钱，落一行。** 线上线下同一张表 —— 两张表相加迟早对不上。
它是对账的唯一依据，只增不改，撤销是往 `reverted_at` 上写。

## 三、活动与券的分界

**一句话：活动作用在「单」上，券作用在「人」上。**

| | 活动 | 券 |
|---|---|---|
| 用户要不要做动作 | **不要**，满足条件自动生效 | **要**：领 → 挑 → 用 |
| 挂在谁身上 | 这一单 | 这个人 |
| 商家能不能指定给某人 | 不能（只能圈人群） | 能 |
| 一单能用几个 | 同类取最优，一单一个 | 一单一张 |
| 先后 | **先算活动** | 券作用在活动之后的金额上 |

> 先后那一条有理由：满减是用户没得选的，券是他挑的；
> 「这张券帮我省了多少」应当是在已有优惠基础上的增量，
> 否则同一张券在不同订单里显示的减免额会对不上他自己的心算。

**活动可以发券**（`优惠 = 发券`）—— 那是活动的一种优惠形式，
不是券的一种活动。方向别搞反。

## 四、两套模型的关系（历史债）

| | 老 `mkt_*` | 新 `pmt_*` |
|---|---|---|
| 活动 | `mkt_campaign`（一个 type 表达四类） | `pmt_activity`（触发 × 优惠） |
| 券 | `mkt_coupon` / `mkt_user_coupon` | `pmt_coupon` / `pmt_user_coupon` |
| 团 | `mkt_group_buy` | —（团这个实体**不迁**，它不是活动） |
| 线上行数 | **0 / 0** | 1 / 0 |

**老模型是同一批概念的旧实现，不是另一批概念。** 它没有「排期」与「受众」，
四个 type 是写死的枚举 —— 加一种玩法要改一次算价。

> `mkt_group_buy` **留着**：团是实例，与模型新旧无关。
> 它只是把「规则从哪读」从商品换成了活动（2026-09-18 已改）。

## 五、词表（写方案与界面时一律用这一列）

| 用这个词 | 不要用 | 指什么 |
|---|---|---|
| **营销** | 营销活动 | 容器 |
| **活动** | 促销、优惠活动、campaign | `pmt_activity` 那条规则 |
| **玩法** | 活动类型、目标 | 触发 × 优惠的组合 |
| **券** | 优惠券模板 | `pmt_coupon` |
| **用户券** | 我的券、已领券 | `pmt_user_coupon` |
| **团购活动** | 团购 | 规则 |
| **团** | 团购、拼团 | `mkt_group_buy` 那一个实例 |

> 界面上仍可以写「优惠券」「拼团」这类日常说法 —— **词表管的是方案与代码**，
> 不是文案。文案的尺子是「这一行的人怎么说话」。
