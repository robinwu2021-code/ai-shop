# 增值服务：商家成长阶梯与 Plan 体系 · 方案

> 状态：**设计待确认** · 上游 [增值服务与分享激励-需求](../../requirements/多门店与分享激励-需求.md) · 决策 [ADR-011](../ADR/ADR-011-经营主体与门店边界.md) · 优先级 P0
> 相关：**ADR-004（零佣金 → 本方案是它的收入答案）** · ADR-001（商家端形态）· ADR-002（分账按主体）· ADR-006（积分按主体）· ADR-009（经营范围）

---

## 一、一句话

平台<b>孵化期不收钱</b>（ADR-004：自带客流零佣金），
等商家做大到需要"多店、多人、要数据"时，用<b>订阅制的经营工具</b>收钱 ——
把变现从「抽每一单」换成「卖长本事之后才需要的东西」。

---

## 二、为什么是这个方案

### 2.1 它补上了 ADR-004 留下的口子

ADR-004 决定「对自带客流的小商家零佣金」，理由是
「他带进来的客户是平台的净增量，从这单抽 5% 是捡芝麻」。

**但那份 ADR 没有回答：不抽佣，平台靠什么活。**

本方案就是那个答案，而且它与零佣金是<b>同一套逻辑的两段</b>：

| 阶段 | 商家状态 | 平台做什么 | 平台收什么 |
|---|---|---|---|
| **孵化期** | 一家店、一个人、几十个客户 | 免费给全套开店能力，帮他把生意跑起来 | **不收** —— 收了他就走了 |
| **成长期** | 生意稳定，开始请人、想开第二家 | 给他<b>自己搭不出来</b>的经营工具 | 订阅费 |
| **成熟期** | 多店、多人、要看数据做决策 | 数据与效率 | 订阅费（更高档） |

**关键在于收费时点**：小商家最脆弱的时候不收他钱，
等他<b>因为做大而产生新问题</b>时才卖解决方案。
这时候他付费的理由不是"平台要收钱"，是"我确实需要"。

这也解释了为什么增值包里放的是**多门店 + 子账号 + 跨店数据**而不是别的：
这三样恰好是"一家店一个人"跨到"多店多人"时**必然撞上的三堵墙**。

### 2.2 卖点在哪，决定了模型长什么样

商家买这个包，买的不是"允许开第二家店"——那个他注册两个主体就有了。
买的是**两个主体永远给不了的东西**：

| 能力 | 两个主体能做到吗 |
|---|---|
| 一次登录看三家店的订单 | ❌ 要退出再登 |
| 今天哪家卖得好、哪家要补货 | ❌ 数据在两个账号里，**不可能横着比** |
| 店长只管自己那家，老板看全部 | ❌ 账号密码给出去就是全给 |

所以模型的重心不在"能建几个门店"，在**跨店聚合**与**分级授权**。
这也是验收标准：只做出"能建门店"而没有总览与对比，这个包就不值钱。

### 2.3 一条硬约束：不能把已经免费的东西收回去

商家现在能用的一切（单店经营、商品、订单、履约、结算、单店数据）
**永远留在免费档**。增值包只卖<b>新增能力</b>。

把免费功能挪进付费档是最快毁掉信任的做法：
一个靠"免费孵化"建立起来的关系，一旦让商家感到"你把我养大了再涨价"，
他会在第一时间找替代方案，而他带进来的客户会跟着走。

**判据**：增值包里的每一项，都必须是<b>单店单人商家用不上</b>的。
用得上的说明它属于基础能力，放错了地方。

### 2.4 被否掉的做法

| 方案 | 为什么否掉 |
|---|---|
| **A. 让商家开多个主体，B 端做「账号切换器」** | 切换器解决不了跨店对比 —— 数据在不同主体下，聚合它等于跨主体读数，而结算与风控都假设主体是隔离的 |
| **B. 门店做成一级实体，订单直接挂 `store_no`** | 结算、分账、积分、对账全部要改。四个域一起改完才能发布，中间没有可交付状态 |
| **C. 订单双写 `merchant_no` + `store_no`** ← 选定 | 结算链路一行不改；单店时 `store_no` 恒等于默认门店，行为完全等价，因此**可以分阶段发布** |
| **D. 子账号复用平台端 RBAC（`sys_staff`）** | 那是运营的角色体系（超管/BD/客服），与商家的（店长/店员）不是一回事；混用会让「给商家加个权限」变成动平台权限表 |
| **E. 子账号只做角色，不做门店范围** | 连锁店长会看到别家店的客户与销售数据。**授权必须是二维的** |
| **F. 按 GMV 抽成替代订阅** | 那就是抽佣的另一种说法，与 ADR-004 直接冲突：商家做得越好交得越多，他会开始想办法把大单挪到线下 |
| **G. 按门店数逐个计费（每店 ¥X/月）** | 商家每开一家店都要重新决策一次"值不值"，而开店那一刻他最不确定。档位制让他一次决定，之后开店是"用额度"不是"再花钱" |

## 三、结构

```
              主体 usr_merchant  ──── 进件/分账/积分/费率/信用（ADR-002/006）
                     │                 ↑ 这一层完全不动
      ┌──────────────┼──────────────┐
      ▼              ▼              ▼
   usr_store     usr_store      usr_store        ← 门店：顾客感知的那个
   （默认店）      （第2家）        （第3家）
      │              │              │
      └── 商品/库存/订单履约/评价/自提点/公告/经营范围
                     ▲
                     │ 授权
              usr_merchant_staff  ── 角色 × 门店范围（二维）
                     ▲
              usr_merchant_plan   ── 增值包：门店额度 / 子账号额度 / 有效期
```

| 表 | 职责 | 新建 |
|---|---|---|
| `usr_store` | 门店实体。由 `usr_merchant_store`（V36）升级而来 | 改名+扩展 |
| `usr_merchant_staff` | 子账号：谁、什么角色、管哪几家店 | ✅ 新 |
| `usr_merchant_plan` | 增值包：额度与有效期 | ✅ 新 |
| `ord_sub_order.store_no` | 履约键（结算仍用 `merchant_no`） | 加列 |

**一句话读法**：钱和信用挂主体，货和人挂门店，权限是"角色 × 门店"两维。

## 四、详细设计

### 4.1 门店 `usr_store`

由现有 `usr_merchant_store` 升级：去掉 `UNIQUE (merchant_no)`，补门店自己的属性。

| 列 | 说明 |
|---|---|
| `store_no` | 门店业务键 |
| `merchant_no` | 所属主体 |
| `name` | 门店名。**与主体名可以不同**（「张记粮油·文三路店」） |
| `is_default` | 默认门店。**一主体恰好一个**，删不掉 —— 它是单店商家的全部 |
| `status` | ACTIVE / SUSPENDED / **READONLY**（欠费降级，见 4.4） |
| `address` `open_hours` `announcement` `featured` | 门面（V42 已确立在此，不在主体上） |
| `service_scope` `service_city_code` | 经营范围**下沉到门店**（ADR-009）—— 两家店可以覆盖不同社区 |
| `store_code` | 门店码，扫码进的是**这家店** |

**经营范围下沉是这次唯一动到 ADR-009 的地方**：原本挂主体。
两家店在不同小区却共用一个覆盖范围，等于其中一家的货出现在它送不到的小区。

覆盖社区表 `usr_merchant_community` 同步改为挂 `store_no`。

### 4.2 子账号 `usr_merchant_staff`

**授权是「每店一个角色」，不是「一个角色 + 一串门店」。**
同一个人完全可能在 A 店当店长、在 B 店只是帮忙的店员 ——
这在夫妻店 + 分店的场景里是常态（老板娘管主店，分店只做核销）。

所以拆成两张表：

`usr_merchant_staff` —— 我是这个主体的成员

| 列 | 说明 |
|---|---|
| `staff_no` | 子账号业务键 |
| `merchant_no` | 所属主体 |
| `user_no` | 绑定的 C 端用户（**复用同一套账号**，见下） |
| `is_owner` | 老板：**全主体全门店**，不需要逐店授权 |
| `status` | ACTIVE / DISABLED |

`usr_staff_store` —— 我在这家店是什么角色

| 列 | 说明 |
|---|---|
| `staff_no` `store_no` | 联合唯一 |
| `role` | MANAGER / CLERK |

| 场景 | 数据 |
|---|---|
| 老板 | `is_owner=1`，**无** `usr_staff_store` 行 |
| 三家店都当店长 | 三行，role 都是 MANAGER |
| A 店店长、B 店店员 | 两行，role 不同 ✅ **这是拆表的理由** |
| 只管一家店 | 一行 |

**为什么不用「一个 role + store_scope 数组」**：那等于假设一个人在所有授权门店里
是同一个角色。假设一旦不成立，只能给他建两个子账号 ——
而两个子账号意味着他要切换登录，等于把多门店要解决的问题又还回去了。

**为什么绑 C 端用户而不是新建一套账号密码**：店员本来就是小区里的人，
多半已经是 C 端用户。新发一套账号意味着他要记两个密码，
而「忘了密码」在只有三个店员的小店里没人能帮他重置。

**角色能做什么**（`is_owner` 覆盖全部；MANAGER/CLERK 逐店生效）：

| | OWNER | MANAGER（店长） | CLERK（店员） |
|---|---|---|---|
| 订单查看/发货/核销 | ✅ | ✅ | ✅ |
| 商品上下架/改库存 | ✅ | ✅ | ❌ |
| 商品建/改/定价 | ✅ | ✅ | ❌ |
| 客户与经营数据 | ✅ | 仅本店 | ❌ |
| 结算与账单 | ✅ | ❌ | ❌ |
| 子账号管理 | ✅ | ❌ | ❌ |
| 增值包购买 | ✅ | ❌ | ❌ |

**结算只给 OWNER**：钱的事只有一个人能看，出问题时能定位到人（与平台端
「没有『运营』这种大角色」同一条理由）。

### 4.2.1 账号 ↔ 商家：一个账号管多个商家

**目标形态**：一个注册账号可以参与**多个经营主体**，每个主体下有多个门店。

**好消息是模型已经支持了** —— `usr_merchant_staff` 是 `(user_no, merchant_no, role)`，
一个 user_no 有多行就是多商家。真正要改的只有两处：

| 现状 | 问题 | 改法 |
|---|---|---|
| `usr_merchant.owner_user_no` | 一个主体一个 owner，且是**唯一的身份来源** | 降级为"创建者"记录；身份一律走 `usr_merchant_staff(role=OWNER)` |
| `BizIdentityResolver` 用 `limit 1` 取商家 | **一个人只能是一家店的老板** —— 这是多商家的唯一硬阻塞 | 改为返回我参与的**全部**主体 |

`limit 1` 那行是整个多商家能力的瓶颈：它不报错，只是安静地把第二家店藏起来。

#### 载体差异：后端一律多商家，端上按载体收窄

| 载体 | 能力 | 为什么 |
|---|---|---|
| **小程序** | 单商家 + 多门店 | 小程序的账号体系绑在微信生态里，切换主体的心智与入口都不合适；且它面向的是孵化期商家，本来就只有一家 |
| **App** | 多商家 + 多门店 | 有能力的商家才装 App；顶部两级切换（商家 → 门店）在 App 上是常见形态 |

**后端不做两套模型。** 小程序侧的"单商家"是**端上取默认主体**的结果，
不是接口只返回一个 —— 接口一律返回全部，端上决定展示几个。

理由：一旦后端按载体分叉，「同一个人在小程序看到 1 家、在 App 看到 3 家」
就会变成两条独立演化的代码路径，而它们对同一份数据的理解迟早会不一致。

**默认主体的选法**：`usr_merchant_staff.is_primary`，用户可在 App 里改。
没设过就取最早加入的那个 —— 那多半是他自己的第一家店。

#### 请求上下文：两级都要带

```
X-Merchant-No  我现在在哪个商家   （不传 → 默认主体）
X-Store-No     我现在在哪家门店   （不传 → 该商家的默认门店）
```

两级都不传时行为与今天完全一致 —— **这是老接口不用改的前提**。

#### 门店与主体的两种建立顺序

需求提到"门店下派生，或独立建门店再关联商家"。两种流程都支持，
但**模型上门店必须属于某个主体**：

| 流程 | 说明 |
|---|---|
| 主体 → 门店（派生） | 常规路径。已有商家，加一家分店 |
| 门店 → 主体（先建后挂） | 先填门店信息（地址/营业时间/覆盖社区），提交时**必须选一个已有主体或当场创建** |

**没有主体的门店不能存在**：主体是结算方与开票方（ADR-002），
一家没有主体的门店收了钱之后，这笔钱没有合法的归属。
所以"独立建门店"是**表单顺序**的自由，不是模型上的悬空状态。

### 4.3 作用域：`BizContext` 从一维变两维

这是**越权防线的第一道**（TDD-backend §5.1），改动最需要小心的地方。

```
现在   BizContext(merchantNo, pickupNos, groupNos)
之后   BizContext(merchantNos,          storeNos, currentMerchantNo, currentStoreNo,
                 ↑ 我参与的全部主体      ↑ 我能管的门店   ↑ 我现在在哪个商家/哪家店
                 perms, pickupNos, groupNos)
```

**三级作用域**：账号（能进哪些主体）→ 主体（能管哪些门店）→ 门店（当前在看哪家）。
每一级都是一次越权检查点。

**`perms` 随 `currentStoreNo` 变**，不是登录时算一次：
同一个人在 A 店是店长（能改价）、在 B 店是店员（不能），
切到 B 店之后权限必须跟着变窄。把 perms 缓存在会话里，就会出现
「切到 B 店还能改价」——而这类越权最难发现，因为操作本身完全正常。

| 规则 | 为什么 |
|---|---|
| `currentMerchantNo` 不在 `merchantNos` 内 → **404** | 别的主体存不存在都不该被探知 |
| `storeNos` 为空 = 该主体**全部门店**（老板） | 不用在建店时回头去补每个老板的授权列表 |
| 每个 `/biz/**` 请求带 `X-Store-No`，落在 `currentStoreNo` | 门店切换是**每个请求**的上下文，不是登录时的状态 —— 否则两个标签页会互相打架 |
| `currentStoreNo` 不在 `storeNos` 内 → **403** | 越权的唯一入口就是这里 |
| 不传 `X-Store-No` → 落到默认门店；总览类接口除外 | 老接口无改动即可继续工作 |

**必须有的测试**（缺一条这层防线就是空的）：

1. 店员 A 只授权门店 1，带 `X-Store-No=门店2` → 403
2. 店员 A 查订单列表，**不带**门店头 → 只能看到门店 1 的单，不是全部
3. 店长看不到结算，`GET /biz/settle/**` → 403
4. 主体 X 的店员带主体 Y 的 `storeNo` → **404 而不是 403**（403 等于确认那个门店存在）
5. 一个账号是 A 主体的老板、B 主体的店员：在 B 下**看不到结算**，在 A 下能看到 —— 权限跟主体走，不跟人走
7. **同一主体内**：A 店店长 / B 店店员，切到 B 店后改价被拒 —— 权限跟**当前门店**走
6. 不传 `X-Merchant-No` 时落到默认主体，且**返回体里带上当前主体号** —— 否则端上不知道自己在看谁的数据

### 4.4 Plan 体系

#### 4.4.1 档位

三档，**不是按门店数逐个计费**（否决方案 G：每开一家店都要重新决策一次"值不值"，
而开店那一刻他最不确定；档位制让他一次决定，之后开店是"用额度"不是"再花钱"）。

| | FREE（孵化） | PRO（成长） | CHAIN（连锁） |
|---|---|---|---|
| 门店额度 | 1 | 3 | 10 |
| 子账号额度 | 0 | 3 | 15 |
| 跨店总览与对比 | — | ✅ | ✅ |
| 数据留存 | 90 天 | 1 年 | 3 年 |
| 导出（对账/客户） | — | ✅ | ✅ |
| 专属客服通道 | — | — | ✅ |
| **单店经营全套** | ✅ | ✅ | ✅ |
| **零佣金/低费率** | ✅ | ✅ | ✅ |

最后两行是**承诺**，不是待遇差异：ADR-004 的零佣金对所有档位一视同仁。
把费率做成档位差异，就等于回到了抽佣，只是换了个名字（否决方案 F）。

**档位的取值域进表不进代码**（与 `sys_pay_channel` / `sys_industry` 同构，ADR-010）：
`sys_merchant_plan_def` 存每档的额度与能力位，运营可调，不发版。

#### 4.4.2 商家的实例 `usr_merchant_plan`

| 列 | 说明 |
|---|---|
| `merchant_no` | 一主体一行 |
| `plan_code` | FREE / PRO / CHAIN |
| `store_quota` `staff_quota` | **快照**，不是每次查档位定义 —— 见下 |
| `status` | ACTIVE / GRACE / EXPIRED |
| `start_at` `expire_at` | FREE 无到期 |
| `granted_by` | SELF_PAID / PLATFORM / TRIAL |
| `trial_used` | 试用过没有。**一主体一次** |

**额度存快照而不是实时查档位定义**：运营下调 PRO 的门店额度时，
已经开了 3 家店的存量商家不该突然有一家变只读。
快照让"改档位定义"只影响之后新订阅的人 —— 这是老用户保护，不是冗余。

#### 4.4.3 生命周期

```
        ┌──────── 试用 14 天（一主体一次）
        ▼
FREE ──────→ PRO/CHAIN ──到期──→ GRACE(7天) ──→ EXPIRED(降级)
 ▲              │  ▲                  │              │
 │              │  └──── 补缴 ────────┴──────────────┘
 └──── 主动降级（到期时生效，不立即）
```

| 迁移 | 何时生效 | 为什么 |
|---|---|---|
| 升档 | **立即** | 他现在就要开第四家店 |
| 降档 / 退订 | **到期时** | 已付的周期不退，但也不能立刻收走他买过的东西 |
| 到期 | 进 GRACE 7 天，**能力全部保留** | 微信支付失败、老板出差、忘了续 —— 这些都不该当天就影响生意 |
| GRACE 结束 | 降级到 FREE（4.4.5） | |
| 补缴 | 立即恢复，**配置原样** | 不需要重新建店、重新授权 |

**GRACE 是这套机制里最该有的一格**：没有它，一次扣款失败就是一次营业事故，
而扣款失败的原因九成与商家的经营无关。

#### 4.4.4 额度校验

写入口一律先问额度，**读不受限**：

| 动作 | 校验 |
|---|---|
| 建门店 | `已有 ACTIVE 门店数 < store_quota` |
| 加子账号 | `已有 ACTIVE 子账号数 < staff_quota` |
| 跨店总览/对比 | `plan 有该能力位` |

**超额时的错误必须说清楚三件事**：现在几家、上限几家、怎么解决。
只回一个「额度不足」，商家的下一步是打客服电话。

#### 4.4.5 降级：降的是能力，不是生意

**到期 ≠ 关店。** 关店伤的是消费者（下了单提不了货），
而欠费是商家与平台之间的事：

| 降级后 | 处理 |
|---|---|
| 超出额度的门店 | 置 `READONLY`：C 端**不接新单**，但历史订单可查、**未完成的单照常核销** |
| 哪几家变只读 | **保默认店，其余按建店时间倒序** —— 规则写死，不让商家选，也不让系统猜 |
| 子账号 | 全部停用；主账号照常 |
| 跨店总览与对比 | 隐藏 |
| 门店与授权配置 | **保留**，补缴后原样恢复 |
| 数据 | 不删。降级只改"能看多久"，不改"存不存" |

**未完成的单照常核销**是这条设计里最重要的一句：欠费当天还有几十个待取货订单，
把它们一起冻住，受损的是买家和取货点，而他们与这笔欠费无关。

**降级前的提醒**：到期前 7 天、前 1 天各一次；降级当天再一次，
**并写明哪几家店变成了只读**。只说"您的套餐已到期"，商家要自己去猜发生了什么。

#### 4.4.6 平台侧

| 能力 | 说明 |
|---|---|
| 给单个商家授予/延长 Plan | `granted_by=PLATFORM`。谈下来的连锁客户不走自助付费 |
| 调整档位定义 | 改 `sys_merchant_plan_def`，**只影响之后新订阅的**（4.4.2） |
| 单独调某商家额度 | 覆盖快照值，用于特例 |
| 到期与降级看板 | 谁快到期了、谁已降级、降级后掉了多少单 —— 这是判断定价合不合理的依据 |

### 4.5 跨店总览与对比（**这个包卖的东西**）

| 接口 | 说明 |
|---|---|
| `GET /biz/stores` | 我能管的门店列表（含状态与今日概览） |
| `GET /biz/stores/overview` | 总览：今日订单数/销售额/待办**按店并列** |
| `GET /biz/stores/compare?metric=&range=` | 跨店对比：销售额/订单数/复购率/评分/缺货数 |

**对比接口只给 OWNER 与全域 MANAGER**：只管一家店的店长看不到别家，
否则「门店范围」这层授权在数据接口上就漏了。

指标口径与 B-11.11（单店经营数据）**必须同源**——两处各算一遍，
商家会看到"总览里 3200、进店里 3180"，然后不再相信任何一个数字。

### 4.6 升档时机：不是等他来找我们

孵化→成长的判断，平台比商家更早知道。**这是这套模式能不能跑起来的关键**：
指望商家自己发现"我该升级了"，转化率会很低，因为他不知道有这个东西。

| 信号 | 说明 | 平台动作 |
|---|---|---|
| 单店月订单数连续 2 个月超阈值 | 一个人忙不过来了 | 推送「要不要加个店员」 |
| 同一手机号在别的主体下也有店 | **他已经在用两个主体 workaround 了** | 推送「可以合并管理」 |
| 商品数 / 客户数进入前 20% | 经营在变复杂 | 推送数据能力 |
| 主动点了「新建门店」但被额度挡住 | 意图最明确的一次 | 当场给试用，不要只弹一个「额度不足」 |

第二条最值得做：**用两个主体的商家是最该被找到的人** ——
他已经证明了需求，只是不知道有更好的办法。
识别方式：同一 `owner_user_no` 或同一联系手机号下有多个 ACTIVE 主体。

> ⚠️ 这条要**在合规范围内**：只用商家自己在平台上留的信息做匹配，
> 不做跨平台画像；推送要能一键关闭。

### 4.7 自提点归属

`cmt_pickup_point.owner_ref` 在 `owner_type=STORE` 时，含义从 `merchant_no` 改为 `store_no`。
承接取货的是具体那家店，不是集团。

⚠️ 这是**存量数据迁移**：现有值是 `merchant_no`，要按"该主体的默认门店"改写。

## 五、分阶段（每阶段可独立发布）

| 阶段 | 内容 | 发布后行为变化 |
|---|---|---|
| **S1** | `usr_merchant_store` → `usr_store`，每主体一行默认门店；`store_no` 生成 | 无（纯改名 + 补键） |
| **S2** | `ord_sub_order.store_no` 双写；履约/评价改读它 | 无（单店下恒等） |
| **S3** | `usr_merchant_staff` + `BizContext` 两维作用域 | 子账号可用（额度 0，先不放开） |
| **S4** | `sys_merchant_plan_def` + `usr_merchant_plan` + 额度校验 + GRACE/降级 | 增值包可售（额度先给 FREE，等于无变化） |
| **S5** | 放开建店 + 跨店总览与对比 + 经营范围/自提点下沉 | 多门店可用 |
| **S6** | 升档信号识别 + 定向推送 + 平台侧到期看板 | 转化开始跑 |

**S1/S2 现在就能做**，它们不改变任何行为，却把最难的模型改动提前消化掉。
S5 之前商家看不到任何变化 —— 这是刻意的：模型改动与产品发布解耦。

## 六、取舍记录

| 冲突 | 让了谁 | 为什么 |
|---|---|---|
| 订单挂主体 vs 挂门店 | **双写** | 结算链路不改，才可能分阶段发；单店时两者恒等 |
| 子账号用新账号体系 vs 复用 C 端账号 | **复用** | 店员多半已是 C 端用户；新发一套等于让他记两个密码，而小店没人能帮他重置 |
| 门店切换放登录态 vs 每请求带 | **每请求带** | 放登录态时两个标签页会互相打架，且刷新后不知道自己在哪家店 |
| 欠费关店 vs 降级只读 | **降级** | 关店伤的是消费者，而欠费是商家与平台之间的事 |
| 降级时让商家选关哪家 vs 规则写死 | **写死**（保默认店） | 让他选就要等他选，而账期是到点就到；系统猜更糟 |
| 经营范围挂主体 vs 挂门店 | **门店** | 两家店在不同小区共用范围，等于其中一家的货出现在它送不到的地方 |
| 结算给 MANAGER vs 只给 OWNER | **只给 OWNER** | 钱的事只有一个人能看，出问题能定位到人 |
