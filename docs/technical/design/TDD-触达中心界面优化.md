## 2. 模拟发送：改弹框 + 能填内容

### 2.1 收进 Drawer

本仓已有约定（`components/ui/popover.tsx` 顶部的对照表）：
**「顺手看一眼/改一下」用 Popover，「进去做一件事」用 Drawer**。
模拟发送要填收件人、内容、验证码，是典型的「进去做一件事」→ **Drawer**。

- 通道页顶部一个「模拟发送」按钮（`message:template:update` 才显示），点开右侧抽屉；
- 五种通道各一套字段（下表），**共用一个 `TestSendDrawer`**，差异由通道决定；
- 发完关闭抽屉并刷新「最近发送」——运营发完第一件事就是看结果。

### 2.2 各通道的输入项

| 通道 | 收件人 | 内容 | 图形验证码 |
|------|--------|------|:---:|
| 短信 | 手机号 | **模板 + 参数**（见 §2.3，不能自由填） | ✅ |
| 邮件 | 邮箱 | **主题 + 正文**（自由填，带默认值） | ✅ |
| 微信订阅消息 | userNo | 场景（到货/退款），参数由场景定 | ✅ |
| App 推送 | userNo | **标题 + 正文** + 提醒级别 | ✅ |
| 站内信 | 收件箱类型 + 编号 | **标题 + 正文 + 落点链接** | ❌ 发不出平台 |

### 2.3 统一形态：**模板可见 + 自定义部分可填 + 实时预览**

用户口径（2026-08-14）：**即使有模板，也要能填自定义内容，并且界面上要看得见模板**。
五条通道统一成同一个形态：

```
┌ 模板 ───────────────────────────────┐
│ 验证码模板 · 阿里云 SMS_474945291      │  ← 选（多模板时）
│ 【数智邻购】您的验证码是 {code}，5 分钟内有效 │  ← 只读展示，变量高亮
├ 自定义部分 ──────────────────────────┤
│ code: [ 328104 ]                      │  ← 可填
├ 预览 ───────────────────────────────┤
│ 【数智邻购】您的验证码是 328104，5 分钟内有效 │  ← 代入后的最终文案
└──────────────────────────────────────┘
```

**模板从哪来**：`msg_template` 表（`template_no` / `name` / `channel` / `content` /
`provider_template_id`）—— 这张表**字段完全对得上，但一行数据都没有**（建表后从没被写过）。
本轮补种子（§2.5），并让抽屉按通道读它。

**各通道的「可填」边界**（这是通道决定的，不是我们决定的）：

| 通道 | 模板 | 可填部分 | 为什么 |
|------|------|---------|--------|
| 短信 | 阿里云报备模板，**正文不可改** | 模板参数（`code`） | 阿里云接口收的是 `TemplateCode`+`TemplateParam`，不收自由文本；发未报备的内容会被直接拒 |
| 邮件 | 默认模板，**可整段改** | 主题 + 正文（全自由） | SMTP 无此约束 |
| 微信订阅消息 | mp 报备模板，字段固定 | **提示语 `thing2`**（≤20 字）+ 件数/金额 | 微信模板的 `thing` 字段本就允许自定义文本，现在是**写死的**（见 §2.4），本轮放开 |
| App 推送 | 默认模板，可整段改 | 标题 + 正文 + 提醒级别 | 聚合商无此约束 |
| 站内信 | 默认模板，可整段改 | 标题 + 正文 + 落点链接 | 自家的表 |

**短信那一行要在界面上说清楚**：「正文由阿里云报备模板决定，只能填参数」——
不写的话运营会以为是我们的功能没做，而实际改不了。

### 2.4 顺带修一处写死

`WxSubscribeGateway` 现在把提示语写死了：

```java
data.put("thing2", "包裹已到自提点，请凭取货码取货");
```

而 `thing2` 是微信模板里**允许自定义文本**的字段。写死意味着运营连改一句话都要发版。
本轮把它变成参数（默认值仍是这句），模拟发送与真实发送共用同一条路。

### 2.5 模板种子（V141）

| templateNo | 通道 | 名称 | content（含变量占位） | provider_template_id |
|---|---|---|---|---|
| `TPL_SMS_OTP` | SMS | 验证码 | `【数智邻购】您的验证码是 {code}，5 分钟内有效，请勿泄露。` | `SMS_474945291` |
| `TPL_MAIL_TEST` | MAIL | 通道联通测试 | 主题 + 正文两段，可整段改 | — |
| `TPL_WX_ARRIVED` | WXSUB | 到货通知 | `{number1} 件包裹已到自提点 · {thing2}` | 运营配置（§4.2） |
| `TPL_WX_REFUNDED` | WXSUB | 退款通知 | `退款 {amount1} · {thing2}` | 运营配置 |
| `TPL_PUSH_TEST` | PUSH | 通用推送 | `{title} / {body}` | — |
| `TPL_INAPP_TEST` | INAPP | 站内信 | `{title} / {body}` | — |

模板本身可在「站内信模板与推送任务」tab 里停用（既有能力），停用后模拟发送里也选不到。

### 2.6 安全闸不变

三道闸原样保留：权限码 + 图形验证码 + 按操作人限流（10 次/小时）。
站内信仍**不过图形验证码**（它发不出平台）。内容可填之后新增一条：
邮件正文长度上限 2000 字符，防止有人把这里当群发工具。

## 3. 记录长期保留；「清理」清的是 mock 假数据

用户口径（2026-08-14）：**发送记录长期保留，不做清理任务**；
「清理掉历史记录」指的是**清掉 mock 里那几条编的样本**。

### 3.1 不做保留期清理 —— 与既有设计一致

`SysNotifyLog` 的类注释本就写着：

> **不继承 BaseEntity**：发送记录是**只追加**的事实流水 —— 它没有「修改」这个动作，
> 也不该能被删（**能删的审计等于没有审计**）。

所以这一条不是「少做了一个功能」，而是**保持这张表的性质**：不给删除按钮、不做定时清理。
表会长，但它是运维流水，量级远小于订单；真到了需要归档的体量，那是一次带评审的容量决策，
不是顺手加个按钮。

### 3.2 清掉 mock 样本（`lib/api/mocks/message.ts` 的 NL0001–NL0006）

编的历史数据会让人以为「已经在发了」。清掉之后 mock 下是空表 + 那句
「接上真实通道之前这里会是空的」的说明 —— 这才是本地开发的真实状态。

⚠️ **代价要认**：那六条样本覆盖四通道 × 成功/失败，是「新通道被显示成短信」
（上一轮修的 ★1）这类缺陷在 mock 下唯一能暴露的途径。清掉后这条防线由
**组件测试**接手：`notify-log-tab` 的通道列映射与失败归因各补一个用例，
断言 WXSUB/PUSH 不会被渲染成「短信」。**先补测试，再清数据**，顺序不能反。

## 4. 发送记录页的其余优化

- **分页**（D1）+ 每页条数选择，用本仓 `usePaging` + `<Pagination>`；
- **时间范围**筛选（默认近 7 天）—— 排查永远是「今天/昨天出的事」；
- **收件人**模糊查（对掩码后的值查，如 `138****8888` 输 `8888` 能中）；
- **刷新**按钮；
- 两条 Notice 合一（U4）；
- 列宽：失败原因那列现在把「归因 + 原文」竖排，长原文会把行撑得很高 ——
  原文超 80 字截断 + `title` 悬浮看全文。

**不做**：导出 CSV。它会把掩码后的收件人、失败原文整表带出运营的电脑，
而这张表存在的前提就是「明文不落地」。要对账去通道后台，那边有明文也有权限。

### 实施中发现并顺手修的

1. **`MsgTemplate` 端上类型漏了 `providerTemplateId`** —— 后端 `TemplateVO` 一直有，
   端上类型没有，于是页面拿不到它。而它正是运营核对「我们发的是哪个报备模板」的唯一凭据。
2. **映射逻辑从 tsx 抽进 lib** —— 本仓 vitest 是 `environment: node`、只测 lib
   （见 `vitest.config`），内联在组件里的映射**没有任何测试能覆盖**。
   而「WXSUB 被显示成短信」正是这类缺陷。现在 `notify-label.ts` / `notify-template.ts`
   各带测试，清掉 mock 样本之后由它们接手防线。
