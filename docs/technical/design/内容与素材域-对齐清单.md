## 1. 这个域的特点：规则已经写死在契约注释里

`ops-web/lib/api/contracts/content.ts` 不是一份普通的接口声明 ——
它把**业务判断连同理由**都写下来了。这些不是「前端的实现细节」，
是这个域的需求：

| 规则 | 契约原文的理由 |
|---|---|
| 命中风险词的内容**不进批量通过** | 「批量 + 风险内容 = 事故」 |
| 批量里含命中项**直接抛错**，不是跳过 | 「静默跳过会让人以为全过了」 |
| `PASSED → OFFLINE` 是单独一条路，不能退回待审 | 「内容已经露出过、可能已被引用，退回待审等于假装没发生过」 |
| 驳回与下架**都必须写原因** | 「原样回作者，不写等于让人猜」 |
| 已回答的问题不能再答，要改先隐藏 | 「让改动这件事本身留下痕迹」 |
| `MANUAL` 榜单的商品必须**在售** | 「下架商品进了榜，用户点进去是空页」 |
| 非 `MANUAL` 传了 `manualSkus` 直接抛错 | 「传了就是调用方理解错了」 |
| 素材指定社区/商家时列表不能为空 | 「投给谁和素材本身是一件事」 |

**后端逐条实现，一条都不能比它宽。** 今晚一半缺陷源于两边各写一套。

## 2. 对齐清单

### 2.1 数据库：四张新表

按并行协议取 **V61**（对方在 V36–V59；V60 已被员工数据域占用）。

```
cnt_post          种草内容
  post_no · author_type(USER|MERCHANT) · author_name · title · content
  community_no · community_name · sku_no(可空)
  risk_hits          JSON 数组，命中的风险词
  status             PENDING|PASSED|REJECTED|OFFLINE
  audit_remark · audited_by · audited_at
  like_count

cnt_question      商品问答
  question_no · sku_no · user_no · content
  status             PENDING|ANSWERED|HIDDEN
  answer · answered_by · answered_at
  hide_reason

cnt_ranking       榜单
  rank_no · name · kind(MANUAL|SALES|...) · size
  manual_skus        JSON 数组，仅 MANUAL 有值
  enabled

cnt_material      运营素材
  material_no · title · kind · content
  scope(ALL|COMMUNITY|MERCHANT) · scope_refs JSON · langs JSON
  published · downloads
```

**风险词命中结果落库而不是每次现算**：审核页要按「是否命中」筛选，
现算的话筛选就得全表扫；更要紧的是——**命中结果要与审核决定同时留痕**，
词库改了之后，「当时是不是命中了」还查得到。

> 风险词库本身放 `sys_setting`（`content.risk-words`），
> 与四类平台配置同一套机制，**不建第五张表**。

### 2.3 权限

新增 `content:govern`。**不复用 `review:govern`**（那个是评价裁决，给客服）：
内容审核在矩阵里归**审核员**，而客服不该能改榜单。

- `AUDITOR` ← 内容审核是它的本职（矩阵 §2.3：「商品、评价、内容、凭证、图片审核」）
- `CAMPAIGN_OPS` ← 榜单与素材是活动运营的工具

> ⚠️ 这会让 AUDITOR 从「三个码」变成「四个码」，`content:material:audit`
> 等 UI 码可以从 `UNIMPLEMENTED` 移出。

| 层 | 新增 |
|---|---|

| Service | `ContentService` + impl；`RiskWordService`（命中检测，读 `sys_setting`） |

## 3. 三条要特别小心的

### 3.1 批量通过要**逐条留痕**

批量是操作方式，不是审计粒度。出事时要能回答「这一条是谁放过去的」——
只记一条「批量通过 37 条」没有用。

实现：批量在一个事务里逐条走与单条相同的裁决路径，各写一条审计。

### 3.2 状态机在服务端强制，不是前端

`POST_TRANSITIONS` 现在只存在于前端。后端要有自己的一份并强制 ——
前端那份是**为了不显示无效按钮**，后端那份是**为了防止真的发生**。
两份都要有，这不是重复（与 `OrderStateMachine` 同一口径）。

### 3.3 榜单的 `MANUAL` 校验要查商品在售

这条要跨域读商品（`cnt_ranking` 在 content，商品在 product）——
走 SPI（`GoodsQueryPort`）还是直接依赖？**走 SPI**，与
`CouponPort` / `PointsPort` 同一个约束，否则 content 域再也拆不开。

需要确认 `GoodsQueryPort` 是否已有「按 skuNo 批量查在售状态」的方法，
没有就补一个。

## 4. 做什么 / 不做什么

### 做
1. V61 四张表 + 实体 + 枚举登记
2. `ContentService` + 12 端点 + `content:govern` 权限 + 审计
3. 风险词库落 `sys_setting` + 命中检测
4. 八条业务规则逐条实现
5. 服务端状态机
6. 从 `UNBUILT_DOMAINS` 移出 `contents` / `materials`，缺口登记 `KNOWN_GAPS`
7. `perm-map.ts` 里 `content:*` 换真码
8. 测试

### 不做（登记）

| 不做 | 为什么 |
|---|---|
| **C 端发种草内容 / 提问的入口** | 本批只做**平台侧的审核与治理**。没有 C 端入口，库里就没有待审内容 —— 见下 |
| 素材真的下发到 B 端 | b-app 的素材下载是另一条链路 |
| 榜单真的影响 C 端首页排序 | 需要 C 端读榜单的端点，下一步 |
| 风险词库的维护界面 | 先落 `sys_setting`，运营改词库暂时走参数页 |

> ⚠️ **这一批做完，审核台会是空的** —— 因为 C 端还不能发内容。
> 这与 F1 积分那次是同一个形状：能力有了，没有生产者。
> 两个选择：(a) 本批只做平台侧，明确写在 UI 上「等 C 端发布链路」；
> (b) 连 C 端发布入口一起做（工作量约翻倍，且要动 c-app）。
> **这是要你定的第一件事。**
