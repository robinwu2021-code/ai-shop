# 门店交易库 · 列默认值补回方案与清单

> 状态：已确认（2026-11-27 用户：按建议；市场、币种默认改 TW、TWD；默认值要与代码一致）。设计改动在分支 feat/product-n-trade；.61 上未执行任何语句。
> 关联：[TDD-商品领域迁到门店交易库](../TDD-商品领域迁到门店交易库.md) 第 2 步。

## 1 问题

新库的设计建表语句由字段草案生成，**没有带列默认值**。旧库里很多列有默认值，代码插入时就不写这些列，靠库来填：
`tenant_no` 默认 `'MAIN'`、`status` 默认 `'ACTIVE'`、商品的 `audit_status`、`on_sale`、`pay_modes`，SKU 的 `market` 默认 `'CN'` 等。
换成新表后这些列变成空值，后续按 `tenant_no = 'MAIN'` 查不到、按状态筛不出，表现为「数据不存在」。
商品测试换到新表后新增的 227 条失败，主因就是这个。

## 2 方案

### 2.1 设计建表语句（交易库、行业库）

在 `scripts/gen-retail-ddl.py` 加一条规则，重新生成 `05-n_trade.sql`、`06-n_industry.sql`：

- 新表某列没有默认值、旧库同名列有字面量默认值时，补回默认值；旧库该列 `NOT NULL` 的一并补上。
- 旧库定义取自按旧迁移重放出来的 `schema-test.sql`；新旧表对应：同名表，加上拆库清单 `db-split-manifest.csv` 里「清理后表名」等于新表名的旧表，以及生成器里移到行业库的 5 张。
- 只补默认值与非空，**不改类型、不改长度、不增删列**；时间函数类默认值不在此列（由公共字段规则管）。
- 默认值若是已换成短值的状态，同样换成短值（目前没有命中）。
- 市场、币种不照搬旧库：旧库默认 `'CN'`、`'CNY'` 是大陆时期的值，按当前主场景改为 `'TW'`、`'TWD'`（`DEFAULT_OVERRIDES`）。

结果：交易库 106 列（24 张表），其中商品表 49 列、交易其他表 57 列；行业库 0 列（行业表在旧库里是餐饮、美业插件各自的表，不在 `schema-test.sql` 里，需另行比对）。

### 2.2 其余各库

01–04、07–14 各库的设计建表语句不由零售维护，已请维护设计的会话按同一口径在源头补。会员营销库的评价、收藏表（`rvw_review.like_count` 为 `NOT NULL` 却没有默认值）影响商品的评价功能。

### 2.3 .61 上已建的 `n_trade`

现状：按拆库分支的基础建表语句建的，74 张表，与零售定稿（67 张）的表集合不同；也缺定稿里的其他规则（金额、计数不为空默认 0 等）。库里有 323 行，看起来是正式库的同步副本（商品 4 行、SKU 5 行与正式库一致，另有订单、预约等，写入时间 11-21～11-26）。

| 做法 | 内容 | 影响 |
|---|---|---|
| A 现在不动（建议） | 线上 `n_trade` 暂不改；只改设计与测试。交易迁移完成、切换前，按最终定稿重建 `n_trade` 并重新同步数据 | 不碰正式环境；切换前本来就要按定稿对齐表集合，一次做完 |
| B 现在逐列补 | 224 条 `ALTER TABLE ... MODIFY COLUMN`（48 张表），其中 205 列要先 `UPDATE ... WHERE 列 IS NULL` 补值再改非空；备份后由 root 执行 | 只补默认值，表集合仍与定稿不一致，切换前还得再对齐一次 |

B 的语句已生成待查（未执行）。

## 3 默认值与代码一致的复核

| 项 | 结果 |
|---|---|
| 字符串默认值是不是代码里定义过的取值 | 55 个中 54 个在代码里有同名常量或枚举；`prd_goods.pay_modes` 的 `'["ONLINE"]'` 是 JSON 数组，元素即 `PayModes.ONLINE`，代码遇空也按 ONLINE 处理，一致 |
| 数字、布尔默认值与实体初始值 | 48 个对应的实体字段都没有初始值，代码完全依赖库默认值，沿用旧库数值即与现有行为一致 |
| 默认值是否超过列宽 | 无超长 |
| 状态默认值是否为已换掉的长值 | 无 |
| 市场、币种 | 代码原先把「本市场」写死为 `"CN"`（商品包 10 个文件 13 处），与 `'TW'` 默认值矛盾。已改为读部署配置 `shop.merchant.default-market`（正式环境 `TW`；没配时与 `StoreMarkets` 一样回落 `CN`）。插入 SKU 时代码都显式写市场，库默认值只是兜底，与生产配置一致即可。订单币种由代码显式写入，正式库 31 笔全是 `TWD` |

**数据搬迁要跟着改**：正式库 5 个 SKU 里 4 个是 `CN`（来源是写死的 `HOME_MARKET = "CN"`），搬到新库时改为 `TW`，否则切换后会被「本市场」过滤掉。已记入搬迁规则（TDD §2.5）。

**不在本次范围**：交易、网关、餐饮插件里还有写死的 `"CN"` / `"CNY"`（多为旧券、人工服务准入等大陆时期的契约校验），随各自模块迁移处理。

## 6 「空」有含义的列保持可空（2026-11-27 用户确认）

零售定稿的 D6 规则（金额、计数不为空、默认 0）误伤了 4 列：它们在旧库与拆库基础设计里都可空，注释也写明空值有含义。生成器加例外 `NULL_MEANS`：注释里写「空表示」「未配时」「可不填」的列不套用 D6。

| 表 | 列 | 原（v2 设计） | 改为 | 原因 |
|---|---|---|---|---|
| `prd_goods` | `group_price_minor` | `bigint NOT NULL DEFAULT 0` | `bigint DEFAULT NULL` | 空表示未开放拼团；0 会被读成团购价 0 元 |
| `prd_goods` | `group_min_count` | `int NOT NULL DEFAULT 0` | `int DEFAULT NULL` | 未配时按 2 人起；0 与之冲突 |
| `prd_store_sku` | `sellable_qty` | `int NOT NULL DEFAULT 0` | `int DEFAULT NULL` | 空表示按可售量规则换算；0 是一件都不能卖 |
| `rfq_request` | `budget_minor` | `bigint NOT NULL DEFAULT 0` | `bigint DEFAULT NULL` | 可不填；0 会被读成预算 0 元 |

`prd_goods.limit_per_user` 注释为「空或 0 不限」，0 与空含义相同，不改。
