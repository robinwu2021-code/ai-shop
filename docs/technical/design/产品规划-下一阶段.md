## 五个类型

| 类型 | 一句话 | 现在挡住了什么 |
|---|---|---|
| **A · 收款闭环** | 让钱真的走通 | 官网不许写到账，商家拿不到钱 |
| **B · 商业化落地** | 让平台能收到钱 | 官网 7 处写「联系报价」 |
| **C · 分发与触达** | 让人装得上、收得到通知 | iOS 缺位，安装包无处可下 |
| **D · 经营数据与导出** | 让商家把数据拿走 | 付费档三项权益还是空的 |
| **E · 增长机制** | 让商家愿意分享 | 分享激励与费率模型互相打架 |

排序依据：**A 不通，B 收不到钱；B 不定，C/D 卖不出去。** E 最后，因为它有一个未解的设计冲突。

## A · 收款闭环

**现状**：一期只记账、线下结算，支付链路本身是桩。

| 项 | 状态 | 说明 |
|---|---|---|
| 微信 / 支付宝支付通道 | `对接中` | 小程序 JSAPI + App SDK |
| 退款回退分账 | 未标注 | 已分账订单退款要先回退分账，否则账对不平 |
| 线上提现 | `规划中` | 依赖上面两项 |

**为什么排第一**：这是唯一一件「不做就等于没有产品」的事。商家现在能接单、能核销、
能看到结算单，**但钱不经过平台**。官网因此有一条硬约束——不许出现「到账」「提现」「T+N」，
`content.test.ts` 逐行拦着。

**完成的判据**：一笔真实订单从支付到分账到退款回退，在生产环境跑通一次。

**做完解锁**：官网可以讲结算时效；`/capabilities/` 去掉两个角标；商家端「线上提现」可上线。

---

## B · 商业化落地

**现状**：档位功能已落地，价格没定。

| 项 | 状态 | 说明 |
|---|---|---|
| 三档定价 | **未拍板** | 官网全站写「联系报价」，7 处 |
| 档位名两套叫法 | 待收口 | 官网「专业版」/ 库里「成长版」，需一条 `sys_merchant_plan_def.name` 的 UPDATE 迁移 |
| 自有品牌小程序开通链路 | `对接中` | 年费与**到期口径**都未定 |

**为什么现在做**：功能是现成的——`b-app` 的 `plan` `stores` `cross-store` `staff` 都在，
到期降级规则也写进了官网。**只差一个数字。**

> **到期口径必须有答案才能卖自有品牌小程序。** 门店订阅的降级规则（7 天宽限 → 超额只读 →
> 补缴恢复）已经定了，但小程序年费到期怎么办没有定 —— 小程序是商家自己的招牌，
> 到期直接停掉和门店只读不是一回事。

**完成的判据**：官网 `/pricing/` 出现真实数字，不再有「联系报价」。

## C · 分发与触达

**现状**：商家装不上 iOS，安卓包没有下载地址。

| 项 | 状态 | 说明 |
|---|---|---|
| iOS App | `规划中` | 仓库里只有 `android-shell`，没有 iOS 壳工程与证书链路 |
| 自有品牌 App | `规划中` | 2026-08-20 确认「未来会支持」，已进未上线表 |
| COS `download` 桶 | **未建** | 桶名与配置已设计好（`deploy/tencent/cos-buckets.md`），没建 |
| 微信订阅消息 | `对接中` | 有新单、有到货，商家现在只能靠 App 推送 |

**为什么排第三**：C 依赖 B——安装包要不要在官网上放，取决于是否已经开始正式招商。
但 **COS 桶是例外，可以立刻做**：官网 `site.config.download.merchantAndroid` 已经就绪，
填上直链即可，空着时下载页渲染成「即将上线」而不是死链。

**完成的判据**：`/download/` 四个入口没有一个是「即将上线」。

## D · 经营数据与导出

**现状**：付费档承诺的三项权益还没有。

| 项 | 状态 |
|---|---|
| 对账与客户导出 | `规划中` |
| 数据留存分档 | `规划中` |
| 专属客服通道 | `规划中` |
| 分拣单打印与导出 | `规划中` |
| 营业执照与商品图 OCR 识别 | `规划中` |

**这一类有个隐患**：前三项写在官网 `/pricing/` 的档位差异里，虽然带了「规划中」角标，
但**角标在销售转述时最容易掉**。商家照着档位表签了约却导不出账，是最难解释的一类投诉。

**建议**：B 定价拍板时，一并决定这三项算不算在首批付费权益里。
**算，就得先做；不算，就从档位表里拿掉**——不要靠一个角标兜着。

## E · 增长机制

**现状**：设计完成，有一个未解的冲突。

| 项 | 状态 |
|---|---|
| F-5 分享激励：分享 → 有效曝光 → 进首页曝光池 N 天 | ⬜ |
| F-6 分享防刷：老客不计、排除自己人、同人同店窗口内一次、新号冷却、单店日上限 | ⬜ |

**冲突**（`待完成功能清单.md` §F 已记录，待拍板）：

分享挣来的首页位若按 `PLATFORM` 计费，**商家越分享费率越高，激励是反的**。
解法是新增第三种客流来源 `MERCHANT_EARNED`，费率按自带客流走 —— 但这会动到
`SETTLE.commissionRate` 的枚举、结算快照、以及官网上「两档费率」的说法。

**为什么排最后**：它不是缺功能，是缺一个决策。**决策没做之前写代码，两种可能都要返工。**

**做完解锁**：官网可以讲「分享能带来平台曝光」——现在一个字都不能写，
因为「不承诺获客效果」是红线。

```
A 收款闭环 ──→ B 商业化落地 ──┬─→ C 分发与触达
                              └─→ D 数据与导出（随 B 一起定范围）
                                    E 增长机制（先拍板，再排期）
```

**可以立刻并行的两件小事**，不依赖任何决策：

1. 建 COS `download` 桶，填上安卓直链（属 C，但无依赖）
2. 一条迁移把 `sys_merchant_plan_def.name` 收口成官网的叫法（属 B，但无依赖）

## 不做的事

| 项 | 为什么 |
|---|---|
| 积分 | 成本模型已定，**跨商家清算未定**（ADR-006）。开关关着，打开即可上线，但不该现在打开 |
| 付费会员、砍价助力集卡、内容社群 | P1 规模化的东西。**社区小店还没跑起来，这些是给有流量的平台用的** |

| 官网客户案例与数据背书 | **一个真实案例都没有。** 编造是最快毁掉信任的方式 |
