## 一、为什么要有这份方案

一个账号可能持有几张营业执照（粮油店是个体户、干货铺子是公司）。数据模型早就支持这件事
（`mch_account` 是账号↔主体的多对多关联表），但请求/会话层严格单主体
（`BizIdentityResolverImpl.resolve()` 只取 `memberships.get(0)`），也没有任何切换机制——
这是 M6 留白，不是新问题。这份方案把它做完，同时顺手处理两件相关的事：入驻这一步的一个
静默 bug（已确认修复，见 §四），以及「每主体只能开 1 家店」这个卡人的硬限制（放开）。

## 二、定稿的产品逻辑

### 2.1 商家天天打交道的是门店，不是证照

第一版方案把「证照」设计成跟「门店」平级的切换器（先选证照、再选店）——**推翻了**。
商家的心智是「我要去哪家店干活」，从来不是「我现在代表哪张执照」。

**证照全程退到幕后，只在两个时刻露面**：

1. 新建门店时，选一张已有证照，或者当场新增一张——**只有一张证照的账号，这一步直接隐藏**，
   不能让大多数人为了开第二家店去理解「证照」是什么。
2. 单独的「证照与账户」管理页——查资料、改资料（营业执照、收款账户、资质证件），
   跟「我现在在管哪家店」完全无关，不切换。

**日常切换只有一个入口：门店选择**——候选列表从「一张证照下的门店」扩大成
「账号名下所有门店」，选中哪家店就同时定了用哪张证照。不做独立的
「切换正在管理哪个证照」会话态/请求头。

### 2.2 对外不叫「实体」「主体」，一律叫「证照」

老板认的是「我这张执照」，不是抽象的「经营主体」。列表里每一行显示的是店铺名称本身
（如「张记粮油」），不是编号或类型标签。技术文档里继续用「主体/`MchEntity`」，
但**面向商家的界面文案、按钮、提示语里不出现这两个字**。

### 2.3 新建门店不需要先建证照

入驻申请审核通过时，建证照和建默认门店是**同一个事务**
（`MerchantPortImpl.activate()` → `ensureDefaultStore(...)`），不需要商家单独操作。
「新增一张证照」本质上就是走一遍入驻申请，通过后自动带出一家同名默认门店。

### 2.4 没有证照也能先把店开起来

**开店不再以「拿到营业执照」为前置**。老板注册完可以直接建店、录商品、配经营范围、加员工、
印店铺码——把所有准备工作做完，**只是买家看不到、也下不了单**。补齐证照并审核通过后，
这家店立刻就是完整的，不用回头再把商品一件件上架。

| 能做 | 不能做 |
|---|---|
| 建店、改店铺资料（公告/营业时间/地址） | **对买家可见** |
| 录商品、上架（进自己的在架列表） | **被下单、收款** |
| 配经营范围、加员工、印店铺码 | 参与平台推荐/搜索 |

**为什么上架也放开**：上架是准备动作，可见性才是交易前置。卡在上架的话，
补完证照那一刻他要回去把几十件商品重新点一遍——而那时他最想要的是「立刻开张」。

**这带出一条今天就存在的缺口**：C 端可见性的唯一出口 `MerchantPortImpl.reachableCommunities()`
**不检查商家状态**，只算履约能力 × 地理覆盖。也就是说今天进件没完成的商家，
货一样对买家可见、一样能走到下单——首页 blocker 那句「商品能上架，但顾客付不了钱」
描述的正是这个状态。放开无证照开店之后这条缺口会被放大，所以**可见性闸门是这次的必做项**，
不是附带优化。

### 2.5 门店创建后暂不支持换证照

「把文三路店从个体户执照转到公司执照名下」是真实场景（个体户升级公司、执照吊销等），
[账号·主体·门店-关系定稿](./账号主体门店-关系定稿.md) §3 已经定过六条硬约束。
**这份方案不做这件事**——用户 2026-08-25 明确「暂不支持，将来再考虑」。两者不是同一个功能，
界面上不能长得像同一回事，商家会点错。

## 三、四个界面（原型见内部 Artifact「门店与证照」v2）

| # | 界面 | 要点 |
|---|---|---|
| 01 | **门店选择** | 唯一的日常切换入口。按证照分组列出账号名下所有门店，多证照时店名下方带归属小字；选中门店即完成「用哪张证照」+「哪家店」两件事。审核中/未通过的证照没有门店，不出现在这里 |
| 02 | **新建门店 · 选/建证照** | 「新建门店」表单最上面加一步：选已有证照或新增一张。**单证照账号这一步隐藏**，默认用唯一那张 |
| 03 | **证照与账户** | 从「我的」进的独立入口。列出所有证照及状态（营业中/审核中/未通过），不切换、不影响当前在管的门店 |
| 04 | **证照详情** | 能改：营业执照信息、收款账户、资质证件。名下门店列出来但**只读、点不进去**——要操作某家店必须回 01 屏切换，避免出现两条「进店」的路互相打架 |

## 四、硬约束

| # | 约束 | 为什么 |
|---|---|---|
| R1 | 界面上不出现「实体」「主体」，一律叫「证照」 | 见 §2.2 |
| R2 | 任何登录账号都能发起新的入驻申请，不限于已有证照持有人 | 可能是白手起家开第一家店，也可能给已有生意再开一条线；新证照通过审核后发起人自动是持有人 |
| R3 | 门店选择（01 屏）跨证照、不跨账号；只列自己账号名下的门店 | 受邀在某证照下当店员，那家店照样出现在他的门店选择里（他有权操作），但「证照与账户」页只显示他是持有人（owner）的那几张 |
| R4 | **建门店、管证照都是 `biz:store:admin`（`BizPerms.STORE_ADMIN`）** | 这个权限码本来就**不让自定义角色勾选**（`BizPerms.java` 里显式排除），天然只有 owner 有——不需要新权限码，直接复用即可满足「只有老板能建店/管证照」 |
| R5 | 入驻幂等按申请单 | ✅ 已实现且已测试，见 §五 |
| R6 | 一个账号最多 5 张证照 | 防止被当成批量注册工具用；达到上限「新增一张证照」变灰并说明原因，不是点了才报错 |
| R7 | 门店配额起点从 1 抬到 3，机制不变 | 沿用现有 FREE/PRO 套餐（`mch_entity_plan`），只改 FREE 档默认值；超过继续走现有「去看套餐」流程 |
| R8 | 证照详情页（04 屏）的门店列表只读 | 留一条能进的路，商家迟早会在「改证照资料」和「管这家店」之间分不清走的是哪条 |
| R9 | **无证照的店对买家完全不可见**，不是「可见但下不了单」 | 让买家看到一家点进去下不了单的店，比看不到更糟——他会以为平台坏了，而商家也不知道自己在浪费曝光。闸门加在 `reachableCommunities()` 这个唯一出口上，加一处即可 |
| R10 | 无证照状态在商家侧必须**一直可见且可操作** | 首页常驻一条 blocker「还不能开张营业 · 补上营业执照，顾客才能看到你的店」，点进去就是补证照的入口。不能让他建完店以为开张了，过几天才发现一单没有 |

## 五、入驻幂等 bug——复核发现已修复

原计划要做的「`activate` 幂等判据改按申请单」这一项，2026-08-25 复核代码时发现**已经修好了**：

- `MerchantPortImpl.activate()` 的幂等判据读的是 `apply.getEntityNo()`（这份申请自己的字段，
  非空即重放同一份申请），不是按人查「这个人是不是已有商家」。
- `M9aOpsFlowTest`「第二张执照不会覆盖第一个主体」有专门回归用例，`mvn test` 跑绿。

这一项不需要再做，技术方案里不必再列。

## 六、待确认的两个默认值

| # | 事项 | 草案 |

（证照数量上限）时可以随时调。
