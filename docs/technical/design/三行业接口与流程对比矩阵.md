## 2. 一处必须写在结论之前的度量盲区

**这份统计的分母只有"零售已有的接口"。而行业差异的大头，是"零售没有的接口"。**

按两份 TDD 的端点清单（KDS 的多动作按一个端点计）：

| | 复用基座接口 | 行业新增接口 | 新增占行业总面 |
|---|---:|---:|---:|
| 餐饮包 | 252 | **25** | 25 / 277 = **9.0%** |
| 美业包 | 252 | **26** | 26 / 278 = **9.4%** |

把两者合起来看「一个行业到底有多少接口是它自己的」：

```
餐饮：新增 25 + X 5 + V 13 + P 3 = 46 / 277 = 16.6%
美业：新增 26 + X 5 + V 14 + P 3 = 48 / 278 = 17.3%
```

**两个口径给出的画面不同**：
按预先承诺的判定维度（`X` 占比）是 2.0%；按"行业自有面"是 16.6%。

**判定仍按预承诺的 `X` 口径**（清单 §6，P0 定稿、P3 之后不许改）——
事后换口径正是这套方法要防的事。
但"行业自有面 16.6%"这个数**必须原样带进 P4**，因为它决定的是**另一件事**：
不是"要不要行业化入口"，而是"行业包本身有多大"。

## 3. 流程五段对比

| 段 | 零售 | 餐饮 | 美业 | 差异性质 |
|---|---|---|---|---|
| **下单** | 加购 → 试算 → 下单 | 台账购物车 → 多轮下达（每轮一单） | 预约单 → 到店才下单 | **`X`** —— 入口与时机都不同，且都在基座能表达的范围内（订单模型没变） |
| **支付** | 线上支付 → 回调 → `markPaid` | 先付 / 后付（结账时统一确认） | 先付 / 到店付 / **资产付** | `S` + 一条基座扩展（`assetDeductMinor`）。**`markPaid` 三个行业同一个方法** |
| **履约** | 自提/邻里/自送/快递 四选一 | 堂食（无交付动作）+ 外卖走基座 | 到店核销 / 上门预约 | `P` —— 加一档 `DINE_IN`，取值域扩充，不是流程分叉 |
| **售后** | 申请 → 退款/驳回 → 申诉 | 同左 | 同左 | **`S`（完全相同，一行不加）** |
| **结算** | 账单 → 对账 → 自营/分账 | 同左 | 同左 | **`S`（完全相同，一行不加）** |

**五段里三段完全相同，一段是取值域扩充，只有"下单"是真差异。**
而"下单"的差异，恰好就是 §1.1 那 5 条 `X`。**两个口径互相印证。**

## 4. 三个判定输入（交给 P4）

| 输入 | 值 | 清单 §6 对应的条件 |
|---|---|---|
| `X` 占比 | **2.0%** | `< 15%` |
| `X` 集中度 | **1 个主语**（`order`） | `≤ 3 个主语` |
| `V` 显著性 | 5.2%，集中在 `goods` + `order` | —（`V` 只在 15–40% 区间参与判定） |

两条否决项：
- `external=Y`：本轮 `/biz` `/mp` 里为 **0**（支付回调在 `/callback/**`，不在盘点范围）。
  **它仍然成立** —— 只是恰好不在这 299 条里。
- `cross=Y`：混合购物车下单（`POST /mp/order`）**是** `cross=Y`，
  而它同时是一条 `X`。**这是全表最值得看的一行**，见 §5。

## 5. `POST /mp/order` —— 既是 `X` 又是否决项

它同时满足：
- **`X`**：餐饮和美业的下单入口都在行业包（台账编排 / 预约转单）；
- **`cross=Y`**：社区电商的购物车会跨商家，一次下单可能同时含餐饮店和零售店的商品。

否决项优先级更高（清单 §6：**否决项不参与占比，恒走基座**）。
所以正确的落法是：

```
POST /mp/order              ← 基座保留，跨商家混合下单走它
POST /mp/x/food/place       ← 餐饮场景下的下单，行业包编排后调 CoreOrderApi
POST /mp/x/beauty/...       ← 同理
```

**不是"把基座下单接口废掉"，而是"多一个行业入口，基座那条继续服务混合场景"。**
这一条如果做反了，跨商家购物车当天失效 —— 而它是这个平台的核心形态。

## 6. 局限（P4 必须原样声明）

1. **`/ops` 的 338 个端点没盘。** 运营端若要行业化，本册不覆盖。
2. **"有前端调用方"是静态前缀匹配**，272 是上界；真实复用面只会更小，
   即 `S` 的实际占比可能被高估。
3. **只盘接口，没盘 Service 层。** 同一个接口内部为行业分叉的可能性没被度量过 ——
   而那正是方案 A/C 要防的东西。
4. **关系码由登记表给出**（`scripts/industry-endpoint-map.mjs`），判据是两份 TDD。
   TDD 改了而登记表没改，统计会静默分岔 —— 登记表头部已写明这条约束。
5. **社区团购（20 条）被排除**。若它将来也行业包化，分母要重算。
