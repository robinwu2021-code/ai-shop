## 〇、独立库推翻了什么（先说被改掉的）

"独立到什么程度"不是一个配置项，它会**往回改调用契约**。三条已定的设计因此失效：

| 原设计（技术方案） | 独立库之后为什么不成立 | 改成 |
|---|---|---|
| E4：业务侧 `JobSupport` 写 `sys_job_run` / `sys_job_log` | 那两张表要搬进 job 库。业务侧写它 = **业务系统反向依赖 job 库**，独立就白独立了 | **业务系统一个字都不写 job 库**，连连接串都没有 |
| E4：`POST` 返 `202` 异步，结果由业务侧落表 | 结果不再由业务侧落表，`202` 就**没有承接方**了——只能加回调，凭空多一条链路和一个"回调丢了导致 run 永远卡在 RUNNING"的失败态 | **改同步**：业务侧把 `JobResult` 放在 HTTP 响应里，worker 收到就写自己的库 |
| 5.2：三张表放平台库、`sys_` 前缀 | job 库有自己的迁移历史，从 V1 重来 | 迁到 job 库，改名 `job_definition` / `job_run` / `job_log` |

### 0.1 为什么同步比 202 好（**在独立库这个前提下**）

- **每张表只有一个写者**，这是独立库最大的价值，不能为了 202 破掉
- 202 的两条出路都更差：加回调 = 多一条链路 + 多一个失败态；让业务侧写 job 库 = 破坏独立
- **调用量根本不大**（见 0.2）：算下来一天约 330 次，worker 一个任务一个线程绰绰有余
- 超时按任务配 `timeout_sec`（默认 60）。**超时不等于失败**：worker 断开连接记 `TIMEOUT`，
  业务侧带着 ShedLock 继续跑完，不会重入
- 真出现 >5 分钟的长任务再引回调，位置留在 `JobResult` 的 async 分支

### 0.2 高频的三个**不纳入本模块**

> ⚠️ 本节初稿写着"清单里唯一的秒级任务是 `OutboxDispatchJob`"，**那是错的**：
> 盘点时进销存只有 1 个任务，一天之内变成了 3 个。以下是按当前清单（15 个）重算的。

判据一句话：**周期短于 1 分钟的队列 poller 留在业务进程内，worker 只接管分钟级及以上的业务扫描。**

| 任务 | 周期 | 为什么不交给 worker |
|---|---|---|
| `OutboxDispatchJob` | 5 秒 | 发件箱投递的内循环，形状是 MQ poller，不是"定时任务" |
| `InvOutboxDispatchJob` | 5 秒 | 同上，进销存那一侧的 |
| `MediaPurgeJob` | 30 秒（fixedDelay） | 同上；而且 `fixedDelay` 语义（上一轮结束后再等）**cron 表达不了**，硬搬过来会改掉它的行为 |

两个 5 秒任务如果走 HTTP，各自一天 17280 次，把一条内网链路变成本系统最繁忙的调用路径 ——
而把一个内循环交给远程调度器，是把可靠性变差了。

**于是纳入 worker 的是 14 个**（17 减 3），HTTP 调用量：

| 频率 | 个数 | 次/天 |
|---|---|---|
| 1 分钟（`order-auto-close` / `notify-push-task` / `inv-reservation-expiry`） | 3 | 4320 |
| 10 分钟（`recon-scan` / `inv-backfill`） | 2 | 288 |
| 每小时（`media-reconcile`） | 1 | 24 |
| 每天 | 6 | 6 |
| | | **合计约 4640 次/天 ≈ 每 19 秒一次** |

同步调用在这个量级上毫无压力（worker 一个任务一个线程，且任何时刻最多几个在飞）。
比初稿算的 330 次大一个量级，**结论不变**。

> 这条同时回答了"worker 挂了会不会影响业务"：两个发件箱投递都不依赖 worker，
> 业务系统最要紧的那条内循环**不在 worker 的故障半径里**。

> `notify-push-task` 是个边界情况：它也是 poller，但周期 1 分钟。
> 按上面的判据归给 worker —— 判据用周期而不用"像不像 poller"，
> 是因为前者客观、后者每次都要重新争论一遍。

## 一、数据库设计

### 1.1 独立到什么程度

| 层次 | 选择 | 理由 |
|---|---|---|
| Schema | ✅ 独立（`ai_shop_job`） | 独立的迁移历史、独立的清理与备份策略 |
| MariaDB 实例 | ❌ 暂不独立，与平台同实例 | 资源实测（技术方案 §三）支持同机，但真隔离要独立实例；**现在不值得**，且要诚实：同实例意味着"库挂了"两边一起挂 |
| 连接账号 | ✅ 独立账号，**只授权 `ai_shop_job.*`** | 这是"业务系统连不到 job 库"的**强制手段**，不是靠自觉 |

### 1.2 表

四张，迁移号从 **V1** 重来，历史表 `job_flyway_history`。

| 表 | 写者（唯一） | 读者 | 说明 |
|---|---|---|---|
| `job_definition` | **运营端** | worker | 定义与配置。worker 只读，永不写 |
| `job_run` | **worker** | 运营端 | 当前状态，每任务一行 |
| `job_log` | **worker** | 运营端 | 执行日志，每次一行 |
| `job_flyway_history` | Flyway | — | 自己的历史 |

> **不变式：每张表只有一个写者。**
> 这比"独占一个库"更精确，也更容易在 review 时检查。
> 业务系统三张表**一张都不碰**——它没有 job 库的连接串。

### 1.3 `job_definition`

在技术方案 A 的基础上补六列（`handler_name` / `target` / `params` / `source` / `missing` / `timeout_sec`）：

```
job_name        VARCHAR(64)  UK   一次调度实例的标识，运营可新建
display_name    VARCHAR(64)       给运营看的中文名
description     VARCHAR(255)      这个任务干什么，页面直接显示
handler_name    VARCHAR(64)       指向业务侧 JobHandler.name()，**只能靠发版新增**
target          VARCHAR(16)       调哪个业务系统：PLATFORM / INVENTORY
params          TEXT              传给 JobInvocation.params 的 JSON
cron            VARCHAR(64)       6 段。**入库即归运营，代码永不覆盖**
enabled         TINYINT           同上
timeout_sec     INT   DEFAULT 60  HTTP 读超时。超时记 TIMEOUT，不等于失败
lock_at_most_sec INT  DEFAULT 1800 传给业务侧 ShedLock
manual_trigger  TINYINT           页面显不显示「立即执行」
log_every_run   TINYINT           0 = 只在状态变化或失败时落 job_log
source          VARCHAR(8)        CODE（代码声明）/ MANUAL（运营新建）。MANUAL 的代码完全不碰
missing         TINYINT           代码里已不存在但表里还留着。**静默消失比留着危险**
owner_module    VARCHAR(32)       排查时知道找谁
created_at / updated_at / updated_by / version / deleted
```

### 1.4 `job_run`（当前状态）与 `job_log`（每次一行）

```
job_run:  job_name UK / last_run_at / last_status / duration_ms / detail / error
          / consecutive_failures / run_count / next_run_at / running / current_run_id
job_log:  run_id UK / job_name / trigger_type(CRON|MANUAL|RETRY) / biz_date
          / started_at / finished_at / duration_ms / status / detail / error
          / worker_instance / http_status
```

状态取值统一六个：

| 状态 | 含义 | 谁判定 |
|---|---|---|
| `SUCCESS` | 业务侧跑完，返回成功 | 业务侧 |
| `FAILED` | 业务侧跑完，返回失败 | 业务侧 |
| `SKIPPED` | ShedLock 没抢到，正在跑 | 业务侧（HTTP 409） |
| `UNREACHABLE` | 重试完仍调不通 | worker |
| `TIMEOUT` | 超过 `timeout_sec` 未返回。**结果未知，不是失败** | worker |
| `RUNNING` | 已发起，未回 | worker |

> `job_log` 的保留策略必须和表一起定，否则它会长成这个库里最大的表。
> 统一保留 30 天，由 `job-log-purge` 清理（它自己也在清单里）。

### 1.5 `shedlock` **不搬**，且不在 job 库建调度锁

- **执行锁留在平台库**（业务侧现有的 `shedlock`）。锁保护的是**业务副作用**，
  它必须和被保护的数据在同一个库、同一个事务边界里。搬到 job 库等于锁和数据分家
- **单 worker 不需要调度锁**。将来上第二个 worker 再在 job 库加 `job_lock`，位置留好即可
- 进销存有自己的库，它的任务要不要自己的 `shedlock` 表，由 shop-inventory 定，本模块不管

### 1.6 平台库那两张表怎么收场

`sys_job_def` / `sys_job_log` 是 `V260` 建的，**线上从未创建**（生产 Flyway 停在 V255，
已实测确认），只存在于本地与 CI。处置：

| 表 | 何时 | 怎么做 |
|---|---|---|
| `sys_job_def` / `sys_job_log` | J0 | 新迁移 `DROP TABLE IF EXISTS`。**不改 `V260`**——它已提交，改了 checksum 会让本地已跑过的人起不来 |
| `sys_job_run` | J4 之后 | 等 14 个任务都改完、worker 观察期结束再 drop。它今天还有 `JobSupport` 在写 |

⚠️ 取迁移号前**先看一眼当前最大号**（现在是 V261，是别人的）。本仓库并行会话撞过号，
本地不报、上生产起不来。

### 1.7 持久层用 Spring Data JDBC，**不用 MyBatis-Plus**

本文初稿写的是"照抄 `InventoryDataSourceConfig`"，那份用的是
`MybatisSqlSessionFactoryBean` + `@MapperScan`。**那是错的**，理由不是风格偏好：

**Spring Data AOT 是 Spring Data 的特性**——构建期把 repository 实现生成出来
（`spring.aot.repositories.enabled`）。MyBatis 不在这条路上，它的 native 故事是
给每个 mapper 与 entity 补反射提示，另一套且更弱。
**这个模块一旦用 MyBatis-Plus，就永远进不了 AOT / native。**

而 MyBatis-Plus 在这里能提供的东西一个都用不上：

| MyBatis-Plus 的价值 | 本模块的实际情况 |
|---|---|
| 复杂动态 SQL、多表 join | 3 张表纯 CRUD；**按设计不能与业务表 join**（1.2 独立库的直接后果） |
| DataScope / 租户 / 乐观锁拦截器 | 一个都不装（进销存那份注释已说明为什么不装） |
| `Wrappers` 条件构造 | 查询四五条，`findByEnabledTrue` 这种级别 |

**选 JDBC 不选 JPA**：无 session、无懒加载、无脏检查，映射直白、AOT 友好；
3 张表上 JPA 是纯负担。

**版本已核（不是推测）**：Boot 4.0.7 → `spring-data-bom 2025.1.6` →
**Spring Data JDBC 4.0.6**，jar 里确实带 `org.springframework.data.jdbc.repository.aot`，
且 `spring.aot.repositories.enabled` 是真实开关。4.0.6 已在本地 `.m2`——
本仓库 mvn 必须 `-o` 离线跑，这点满足。

> **它同时是整个后端切 Spring Data AOT 的试点。**
> 全新、独立库、零存量数据、可整体回退——试点成本几乎为零，失败也只影响这一个模块。
> 这个理由比"为了本模块好用"更重要：**先在这里把 AOT 这条路走通，再谈迁移别的域。**

### 1.8 由此推出的一条硬约束：`shop-job` **不依赖 `shop-base`**

`shop-base` 把 `mybatis-plus-spring-boot4-starter` 作为**编译依赖**引入（pom 第 50 行）。
worker 只要依赖它，MyBatis 就进了 classpath，AOT / native 的收益当场打折。

所以 worker 的依赖只有三样：`shop-job-api` + `spring-boot-starter-data-jdbc` + 驱动。
**这和 1.7 之后 `shop-job-api` 要单开是同一条理由**：这个模块的价值就在于它足够干净。

代价：`BizException` / `ErrorCode` 这些用不了，worker 自己定义几个异常。
对一个只有调度器的模块，这是划算的。

## 二、代码结构

```
shop-job-api/            新 · 零依赖契约包（无 Spring、无平台语义）
  JobHandler.java          业务侧实现：name() + run(JobInvocation) -> JobResult
  JobInvocation.java       record(runId, type, bizDate, params)
  JobResult.java           record(status, detail)
  JobDeclaration.java      record(handlerName, displayName, defaultCron, ...) 代码侧的声明
  TriggerType / JobStatus  枚举

<各业务模块>/**/job/*.java  14 个触发器 → implements JobHandler。**位置不动**
                          （另 3 个高频 poller 保留 @Scheduled，见 §0.2）
shop-app/**/internal/
  JobEndpoint.java         新 · POST /internal/job/{name}/run，鉴权 + 查 registry + ShedLock
  JobHandlerRegistry.java  新 · Map<String, JobHandler>，Spring 收集所有 JobHandler bean

shop-job-store/          新 · 持久层（**Spring Data JDBC，不是 MyBatis-Plus**，见 1.7）
  config/JobDataSourceConfig.java   独立数据源 + 独立 Flyway 历史（job_flyway_history）
  JobDefinition / JobRun / JobLog   record 式聚合，@Table/@Id
  JobDefinitionRepository 等        CrudRepository，构建期由 AOT 生成实现
  依赖：spring-boot-starter-data-jdbc + shop-job-api。**不依赖 shop-base**

shop-job/                新 · worker 的可部署单元（角色同 shop-app）
  JobApplication.java      Spring Boot 主类
  JobRegistry.java         ThreadPoolTaskScheduler + Map<String, ScheduledFuture>
  JobConfigWatcher.java    30 秒轮询 job_definition，把运营的改动应用到注册表
  invoke/JobInvoker.java   接口
  invoke/LocalJobInvoker   J2 · 查进程内 registry 直接调（行为等价，零新失败面）
  invoke/HttpJobInvoker    J5 · 走 HTTP

shop-app/**/portal/ops/
  OpsJobController.java    新 · 运营端。**写 job_definition，读 job_run/job_log**
  （shop-app 依赖 shop-job-store，因此同时存在 MyBatis-Plus 与 Spring Data JDBC——
    两个数据源互不干扰，这正是「逐步切换」该有的形状，不是妥协）
```

### 2.1 为什么契约要单独一个 `shop-job-api`，不放 `shop-base`

因为 **shop-inventory 要实现 `JobHandler`（日快照），而它刻意不依赖平台语义**——
`InventoryDataSourceConfig` 的注释里写得很清楚："独立交付时那个上下文不存在"。
把契约塞进 `shop-base`，等于让进销存为了一个接口把整个平台地基拖进去。

`shop-job-api` 里只有 5 个文件、零依赖、不引 Spring。谁都能引，引了也不欠什么。

### 2.2 运营端为什么不通过 worker 拿数据

页面直读 job 库，**不与 worker 通信**。这条从技术方案 B3 原样保留，理由不变且更强了：

> **worker 挂了的时候，页面必须还能显示"最后一次跑是 2 小时前"——那正是最需要看的时刻。**
> 如果页面要向 worker 要数据，worker 一挂页面就是空白，等于把最关键的那次故障变成了盲区。

代价：运营改配置最长 30 秒后生效（worker 轮询周期）。运维上与"立刻"没有区别。

## 三、调用契约（修订版：同步）

```
POST http://<业务系统>:8081/internal/job/{jobName}/run
Header: X-Job-Token: <共享密钥>
Body:   {"runId":"...","triggerType":"CRON","bizDate":"2026-08-25","params":{}}

200 {"status":"SUCCESS","detail":"关闭 12 单，释放库存 34 件"}
200 {"status":"FAILED","detail":"...","error":"..."}
409 {"status":"SKIPPED"}          ShedLock 没抢到
404                               没有这个 handler（代码里删了、表里还留着 → 置 missing=1）
401                               token 不对
```

### 3.1 鉴权与暴露面（四条硬要求）

1. **`/internal/**` 绑内网**，nginx 不反代。生产上业务与 worker 同机，走 `127.0.0.1:8081`
2. **共享密钥 `X-Job-Token`**，放 `shop-app.env` 与 worker 的 env，**不进仓库**
3. **不给任何用户态身份**。这个端点不建 `BizContext`、不认 token 里的用户；
   handler 里凡是需要"谁操作的"，写死系统账号
4. **不记 body、不记 params 到日志**——params 将来可能带业务标识

### 3.2 重试与失败

- 调不通：退避 **5s / 15s / 45s**，共 3 次，跨过典型重启窗口（本仓库 jar 启动约 40 秒）
- 仍失败：`job_log` 记 `UNREACHABLE`，`job_run.consecutive_failures++`
- **worker 不排队补跑**。漏跑补跑是补偿层（技术方案 §5.5）的事，J7 再做
- `SKIPPED` **不计入 `consecutive_failures`**——它是正常的并发保护，不是故障

## 四、部署形态

```
同一台机器
├── ai-shop.service        SPRING_PROFILES_ACTIVE=api,ops     :8081   ← 今天就有
├── ai-shop-job.service    SPRING_PROFILES_ACTIVE=worker      :8082   ← 新增
└── MariaDB
    ├── ai_shop        平台库（含 shedlock）
    ├── ai_shop_inv    进销存库
    └── ai_shop_job    **新** job 库，独立账号只授权这一个 schema
```

- **发布互不影响**：发业务只重启 `ai-shop.service`，worker 不动；反之亦然
- **worker 的内存**：技术方案实测平台实例堆峰值 117MB，worker 只装调度器 + 一个数据源，
  `-Xmx256m` 足够。资源不是理由（§三已实测）
- **同机的诚实说明**：这解决"发布不打断"，不解决"机器挂了"。后者要多机，
  那时 `job_definition` 需要加调度锁——位置已留

## 五、交付计划

八批。**每批都能独立停下、独立回退**，且停在任何一批都是有用的。

| 批 | 内容 | 验收（可测） | 回退 | 依赖 |
|---|---|---|---|---|
| **J0** | `shop-job-api` 契约包；`shop-job-store`（**Spring Data JDBC + AOT**）；job 库 `V1` 四张表（**默认关**）；平台库新迁移 drop 掉 `sys_job_def`/`sys_job_log`；H2 侧 `schema-job-test.sql` | 全量测试绿；`shop.job.enabled=false` 时**不需要 job 库也能起来**；**构建产物里能看到 AOT 生成的 repository 实现**（否则等于没开）；`shop-job-store` 的 classpath 不含 mybatis | 删模块，drop 迁移无数据 | — |

## 六、已知会绊人的坑（都踩过）

| 坑 | 症状 | 怎么避 |
|---|---|---|
| 第二数据源让 Spring 自动配置整体退让 | **DataScope 行级越权防线静默丢失**，无任何症状 | 平台四个 bean 已显式 `@Primary`（`PlatformDataSourceConfig`），job 数据源**必须非 primary**；动之前读那个类的注释 |
| repository 没绑到 job 数据源 | `job_*` 查询**静默打到平台库**，只在跑到那一行时才炸 | `@EnableJdbcRepositories` 显式指定本模块的 `JdbcOperations` / `DataAccessStrategy`，不吃 `@Primary`。这是进销存「Mapper 归属两头夹」那条教训在 Spring Data 侧的同一个形状 |
| 以为开了 AOT，其实没开 | 启动照常、功能照常，**只是什么都没生成**——直到上 native 才发现 | J0 验收里加一条：断言构建产物里有 AOT 生成的 repository 实现类；`spring.aot.repositories.enabled` 显式写出来，不靠默认值 |
| 误引 `shop-base` | MyBatis 被拖进 worker classpath，AOT/native 收益打折，且没有任何报错 | 见 1.8。CI 里加一条依赖断言：`shop-job` 的 classpath 不含 `mybatis` |
| 运营端菜单在库里 | 只改 `nav.ts`，接真后端就看不到 | 跑生成器落迁移（J3 的验收项之一） |
| H2 schema 生成器有盲点 | `CREATE TABLE` 里的块注释会**静默吞掉后面的列** | 长注释写在 `CREATE TABLE` 之上；`SchemaDriftTest` 会抓 |
| 并行会话撞迁移号 | 本地不报，上生产起不来 | 取号前看当前最大号（现 V261） |
| 启动 upsert 冲掉运营改的 cron | 无报错无日志，某天起任务又按老点跑 | F5 规则 + J2 那条守卫测试 |

## G0. 动手前要知道的两颗地雷

### 地雷一：`ScheduledJobConventionTest` 会在 J2 变红，而且红得像别的问题

它扫**源码**里的 `@Scheduled(cron=...)`，断言样本 `≥ 4` 再逐条检查四条约定
（cron 可配 / 有 `@SchedulerLock` / 有 `@Profile("worker")` / 扫得到）。

J2 摘掉 14 个 `@Scheduled` 之后只剩 3 个高频 poller，**3 < 4，守卫直接红**。
它的报错会长得像「任务丢了」，而真实情况是**守卫自己没跟着迁移**。

> 这条守卫的类注释里已经写明「什么都没扫到是这类守卫最常见的死法」——
> 作者当时想到的是「扫不到」，没想到「被搬走了」。J2 必须把它改成扫
> `JobDeclaration`，否则要么恒红（等于没有闸门），要么有人把阈值从 4 改成 3
> 让它绿回来 —— 而那一改，12 个任务就永远不在任何守卫的覆盖里了。

### 地雷二：运营端有**两个方向**的契约守卫，只过一个等于没过

| 脚本 | 方向 | 漏了的症状 |
|---|---|---|
| `scripts/check-ops-contract.mjs` | 前端调了 → 后端有没有 | 画了没后端。**mock 默认开着**，页面永远绿，接真后端那天集体 404 |
| `scripts/check-ops-orphan.mjs` | 后端有了 → 前端调没调 | 做了没入口。**不报任何错**，表现为「这功能我们做过啊」而运营点不到 |

两个都要跑。另外菜单**在库里**（`sys_function` / `sys_function_point`），
只改 `nav.ts` 在 mock 下看得见、接真后端就没有 —— 要跑 `ops-web/scripts/gen-perm-seed.mjs` 落迁移。
