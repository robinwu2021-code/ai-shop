# 无资质商家与邻居集市 · 方案

> 状态：**待决策**，未落地。本文只有设计。
> 上游：`sys_legal_form` 法律形态注册表 · `mch_entity` 经营主体 · `mkt_attribution` 归因
>
> 本文按 [文档规范](../../文档规范.md) §四「方案类骨架」组织。

---

## 一、一句话

**平台一旦收钱就要担责，所以这类商家的钱不经过平台** ——
线上预定、线下付款，平台只做信息展示与撮合前的连接。

而他们的价值不在成交额，在**裂变流量**：一个卖自家柿饼的邻居，
能把整栋楼的人拉进来。集市是获客入口，不是孤岛。

---

## 二、为什么是这个方案

### 2.1 责任的分界线在「钱有没有过平台」

这是整个方案的地基，其余设计都是它的推论。

| 平台做什么 | 法律角色 | 责任 |
|---|---|---|
| 收钱（哪怕只是代收、担保交易） | **交易参与方** | 商品出问题、商家跑路，用户会找平台，平台要先行赔付 |
| 只展示信息，交易双方线下自行完成 | 信息发布平台 | 显著轻，但**不是零** |

无资质商家没有营业执照、没有进件、没有可追偿的经营实体。
平台一旦替他收钱，就等于**用平台信用为一个没有任何资质的人背书** ——
出事之后平台没有任何东西可以追偿，只能自己赔。

> **所以「不支持线上支付」不是技术限制，是责任设计。**
> 写清这一点是为了防止将来有人觉得「加个支付很简单」——
> 那不是加一个功能，是把平台变成交易参与方。

### 2.2 但「不是零责任」—— 无资质 ≠ 无身份

即便只做信息展示，平台仍有**核验登记**义务。完全不核验同样担责。

所以这一档要求：

| 要 | 不要 |
|---|---|
| 真实姓名 + 手机号（实名） | 营业执照 |
| 所在社区 | 银行账户 |
| 经营品类（用于风险分级） | 进件 |

用户看到的标签是「**已实名 · 未认证经营资质**」，
而不是什么都不说 —— 后者才是真正的风险。

### 2.3 价值在裂变，不在成交

这类商家单个的成交额可以忽略，他们的价值是**把人带进来**：

```
邻居在群里分享「我家柿饼」
      ↓
新用户点进集市 → 落地在这个商家页
      ↓  ← 归因在这里发生（mkt_attribution 已有 inviter_no / entity_no）
新用户成为平台用户
      ↓  ← **这一步是设计重点**
被引导到可交易的正常商品
```

**最后一步决定这个方案有没有价值**。流量进来了却只能看不能买，
用户逛一圈就走了 —— 集市就成了一个自娱自乐的板块。
所以集市页必须有通往正常货架的路径（见 §4.4）。

### 2.4 被否掉：`legal_form` 留空（NULL）

最省事的写法：`mch_entity.legal_form` 允许为 NULL。

**否掉的理由是 SQL 语义**：`NULL` 不参与比较。
一句 `WHERE legal_form IN ('MICRO','INDIVIDUAL','ENTERPRISE')` 会**静默排除**
所有无资质商家 —— 而写这句话的人不会意识到自己漏了一整类商家。
这类漏判不报错，症状是「后台商家总数对不上」，排查的人会先怀疑数据。

### 2.5 未认证 ≠ 小微 —— 分界线不是执照

这两档最容易被当成一回事，因为**它们都没有营业执照**。
`sys_legal_form.need_license` 上小微写着 0，注释是「小微不需要，这正是它存在的意义」。

所以「没执照」**不能**用来区分。真正的分界有三条：

| | 未认证 `NONE` | 小微 `MICRO` |
|---|---|---|
| 营业执照 | 无 | **无**（一样） |
| 进件 | 不进 | 身份证 + 结算银行卡 + **门店照片** |
| **固定经营场所** | 无 | **必须有** ← 硬门槛 |
| 行业 | 不限（不交易） | **白名单**（`industry_gated=1`，线上业态不收） |
| 收款 | 否 | 是，钱到个人 |

**第三行是关键**：卖自家柿饼的邻居没有门店 ——
他不是「懒得进件的小微」，是**进不了小微的人**。

> ⚠️ **这里更正一处此前的论证。** 本文早先把未认证的理由写成
> 「无资质 = 还没有资质这个东西，要办执照才变」——**那是错的**：
> 小微本来就不需要执照，办执照不是通往收款的必经之路。
>
> 正确的理由是**进不了小微件**（无固定经营场所 / 行业不在白名单），
> 而这确实是主体属性，不是几天内会变的流程状态。
> 结论（要一个显式档位，不靠「有没有进件记录」倒推）不变，理由换了。

### 2.6 被否掉：靠「有没有进件记录」隐式判断

`mch_payment_merchant` 不存在 = 不能交易，看似够用。但它**分不清两件事**：

| | 含义 | 会变吗 |
|---|---|---|
| 进件中 / 被驳回 | 能进件，流程没走完 | 会，几天内 |
| **进不了件** | 无固定经营场所 / 行业不在白名单 | 要开店面或换行业 |

前者是**状态**，后者是**主体属性**。混在一起的话，集市成员天天变 ——
进件中的正常商家会被卷进来，过两天又出去。

## 三、结构

### 三个能力档位

| 档位 | `legal_form` | 建商品 | 分享 | 线上预定 | 线上支付 | 出现在 |
|---|---|:---:|:---:|:---:|:---:|---|
| **未认证** | `NONE` | ✅ | ✅ | ✅ | ❌ | 仅集市 |
| 有资质、进件中 | MICRO/… | ✅ | ✅ | ✅ | ❌（暂时） | 仅集市 |
| 已进件 | MICRO/… | ✅ | ✅ | ✅ | ✅ | 正常货架 |

中间那一档现在没有归宿（进件中的商家也不该出现在正常货架 —— 用户点进去下不了单），
与无资质共用同一套展示逻辑，顺带一起解决。

### 判据

新增能力函数，与 `canSell`（按端 × 品类）**正交**：

```ts
/** 这家店能不能收线上支付 —— 与「这件商品能不能在这个端卖」是两件事 */
export function canTakePayment(ctx: {
  legalFormCanTrade: boolean;   // sys_legal_form.can_trade
  payActive: boolean;           // mch_payment_merchant.apply_status === "ACTIVE"
}): Verdict
```

两条都满足才可收款。**查不到一律判否** —— 与 `canSell` 同一个取向：
新增档位时「查不到 = 放行」会静默放出一个不能收款的店，
而症状是用户付了钱进不了商家账户。

## 四、详细设计

### 4.1 数据模型

```sql
-- ① 注册表加一档与一个能力位
ALTER TABLE sys_legal_form ADD COLUMN can_trade TINYINT NOT NULL DEFAULT 0
  COMMENT '该法律形态能否收线上支付。**默认 0** —— 新增档位默认不可收款，
           要放开必须显式改。反过来会静默放出一个收了钱却进不了账的店';

INSERT INTO sys_legal_form (legal_form, name, need_license, can_trade, wechat_code, alipay_code, ...)
VALUES ('NONE', '未认证', 0, 0, NULL, NULL, ...);

UPDATE sys_legal_form SET can_trade = 1 WHERE legal_form IN ('MICRO','INDIVIDUAL','ENTERPRISE');

-- ② 商品挂货架
ALTER TABLE prd_goods ADD COLUMN shelf VARCHAR(16) NOT NULL DEFAULT 'MAIN'
  COMMENT 'MAIN 正常货架 / BAZAAR 邻居集市。由商家的 can_trade 派生并落列 ——
           首页一次查几十个商品，每次 join 三张表算能不能收款会拖垮它';
```

`wechat_code` / `alipay_code` 为空**天然阻断进件**，
不需要写「如果是 NONE 就不让进件」这种 if。

> `shelf` 是**派生值落列**，代价是可能不同步。
> 需要一条对账兜底：`shelf` 与商家实际 `can_trade` 不一致的商品数应恒为 0。

### 4.2 线上预定 + 线下付款

这是这一档**唯一的交易形态**。它不是「咨询意向」，是一次完整的交易前半段 ——
只是钱在线下付。

```
mkt_reservation
  reservation_no   业务键
  entity_no        哪家店
  goods_no         预定的商品（可空 —— 也允许整店咨询）
  user_no
  contact_phone    用户留的联系方式
  qty              数量
  pickup_at        期望自取/交付时间
  note             留言
  status           NEW 待确认 / CONFIRMED 商家已确认 / DONE 线下已成交 / CANCELLED / EXPIRED
  expire_at        过期时间。**必须有** —— 没有的话商家的待办会越积越长
  inviter_no       谁分享带来的（裂变归因，见 §4.4）
```

#### 价格怎么处理 —— 一个我改过的判断

我起初写「预定单不能填金额」。**那是过严的**：用户需要知道大概多少钱，
不给价格的商品页没人会点。

准确的边界是：

| 可以 | 不可以 |
|---|---|
| 商品页展示价格（**信息**） | 预定单产生「应付金额」 |
| 预定单**引用**商品当时的价格作参考 | 任何支付链路、优惠券、积分抵扣 |
| 商家线下收多少是他和用户的事 | 平台代收、担保、退款 |

预定单上必须写明：**「价格以商家实际收取为准，平台不参与交易、不提供担保」**。

#### 为什么不塞进 `ord_order`

那条链路每一段都假设有钱 —— 支付、计提、分账、补差、积分、对账、五条恒等式。
塞一张 0 元单进去，**所有金额字段都是 0，而 0 和「无意义」是两回事**：

- GMV 报表把它算成一笔成交（虚增）
- 对账任务为它找不到支付流水而告警
- 恒等式要为它开特例

一个只有联系方式和意向的东西，不该进交易域。

#### 履约与评价

商家确认 → 用户到店/收货 → **商家标记 DONE**。平台不碰钱，只记状态。

`DONE` 之后允许评价 —— 但要与正常订单的评价**分开计权**（见 §六待确认 4）：
没有支付凭证的评价，刷起来的成本比正常评价低得多。

### 4.3 责任的产品化落点

责任边界不能只写在文档里，要落在用户看得见的地方：

| 位置 | 要显示什么 |
|---|---|
| 集市入口 | 「集市商家未认证经营资质，交易与付款在线下完成，平台不担保」 |
| 商家页 | 「已实名 · 未认证经营资质」标签 |
| 商品页 | 无「立即购买」，只有「预定」；价格旁注「线下付款」 |
| 预定成功页 | 再次明示平台不参与交易 |
| 预定单详情 | 商家联系方式 + 免责说明 |

**四处重复不是冗余**：用户从任何一个入口进来都要看到，
而事后纠纷时「有没有明确告知」是关键事实。

### 4.4 裂变承接 —— 这个方案的价值所在

归因链路**已经有了**（`mkt_attribution` 带 `inviter_no` / `entity_no` / `channel`），
不用新建。要做的是**承接**：

```
分享落地页（集市商家）
  ├─ 这家店的商品（不可买，可预定）
  ├─ 「附近可配送的店」        ← 关键：把人导向可交易的货
  └─ 「同社区的其他集市摊主」   ← 集市内的横向流动
```

**「附近可配送的店」这一条决定成败**。没有它，新用户看完柿饼就走了 ——
流量进来变不了现，这个方案就只剩成本。

建议在集市商家页的**第一屏之内**给这个入口，不要放在页面底部。

> 归因不受影响：用户是从这个集市商家分享进来的，
> `mkt_attribution.entity_no` 记的是他 —— 即使最终在别家下单，
> 这份引流的功劳仍然算得清。这正是 `mkt_attribution` 与订单归属分开的价值。

### 4.5 风险：这一档会变成规避监管的口子

会。三条约束：

| 约束 | 为什么 |
|---|---|
| 预定单**不产生应付金额**、无任何支付入口 | 有了就是变相撮合成交，平台重新变回交易参与方 |
| 集市商家**必须实名**（真名 + 手机） | 平台的核验登记义务；出事要找得到人 |
| 单商家预定量超阈值 → **强制引导进件** | 否则会有人长期靠集市做生意，绕开资质与结算 |

第三条最要紧：**这一档的定位是过渡，不是终点**。
没有转正压力，它会变成永久的灰色地带 —— 而那时平台承担的是
「明知有人长期无证经营却持续为其导流」的责任，比一开始就不做还糟。

### 4.6 转正：未认证 → 个体户

沉淀下来的东西要能带走 —— 这是这一档存在的全部意义：

| 带走 | 怎么处理 |
|---|---|
| 商品 | **原样保留**，只把 `shelf` 从 `BAZAAR` 刷成 `MAIN` |
| 店铺资料、公告、主推 | 原样 |
| 粉丝 / 收藏 | 原样（`usr_store_favorite` 不受影响） |
| **归因关系** | 原样 —— 他之前带来的用户仍算他的 |
| **预定单** | **不转订单**，见下 |

**预定单不转订单**：预定是意向，订单是合约。转过去的话金额从哪来
（预定时没有支付）、算不算当月成交额（虚增 GMV）、要不要发积分
（没有实付金额可算）—— 每个问题都要开特例。让它自然终结，
转正后引导用户重新下单。

## 五、取舍记录

| 冲突 | 让了谁 | 代价 |
|---|---|---|
| 支持线上支付（转化高）↔ 平台不担责 | **不担责** | 转化低得多。但收钱就要先行赔付，而这类商家没有任何可追偿的实体 |
| 不展示价格（更安全）↔ 用户要知道多少钱 | **展示价格** | 需要显著的免责说明。不展示的话没人会点 |
| 模型简洁 ↔ 不用 NULL | **不用 NULL** | 注册表多一行。换来 `IN (...)` 不会静默漏人 |
| 查询实时准确 ↔ 首页性能 | **落 `shelf` 派生列** | 可能不同步，需一条对账兜底 |
| 让商家自由用集市 ↔ 强制转正压力 | **强制转正** | 体验有摩擦。但不加压力，过渡态会变成永久态 |

## 六、待确认

| # | 事项 | 影响 |
|---|---|---|
| 1 | 「邻居集市」是 C 端**独立入口**还是首页分区 | 决定 `shelf` 的粒度与信息架构 |
| 2 | 集市商家实名到什么程度：真名+手机，还是要身份证 | 核验义务的强度与入驻摩擦 |
| 3 | 预定量阈值定多少、超了硬拦还是提示 | §4.5 第三条 |
| 4 | 集市评价是否计入 `mch_entity.rating` | 没有支付凭证的评价，刷的成本低得多 |
| 5 | 站内搜索是否包含集市商品 | 与「默认排除」的口径一致性 |
| 6 | 集市商家的商品数上限 | 防止有人把它当免费商品库 |
| 7 | 转正后未完结的预定单怎么收尾 | §4.6 |

**第 1 条决定其余** —— 独立入口的话 `shelf` 一列就够；
若要「首页也能刷到但标注不可交易」，`shelf` 要变成更细的可见性规则，
且要重新评估「点进去不能买」的转化损失。
