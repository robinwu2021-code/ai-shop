# 方案：新数据库划分与迁移

状态：草稿，待用户确认后转 ADR 并分批立 TDD。创建 / 更新：2026-11-25。
依据：[库表-按业务域整理与冗余分析](库表-按业务域整理与冗余分析.md)；用户给定的业务域划分与“清理后迁到全新的干净库”的要求。
配套：[清理后的表清单-按业务模块](清理后的表清单-按业务模块.md)、[支付域-清理后的表清单](支付域-清理后的表清单.md)、逐表明细 [db-split-manifest.csv](schema/db-split-manifest.csv)。本文数字都由逐表明细统计。

## 1 目标

1. 按业务域把现在挤在一个 shop 库里的表分开，每个库只放一个业务域。
2. 分库的同时去冗余、做业务抽象：同一业务对象只留一套，旧一代模型、迁移过渡表、遗留副本不带进新库。
3. 新库是**全新建的干净库**：用新基线建表，只迁有效数据；旧库原样保留作回退，不在旧库上逐张删表。

- shop 库 850 张拆完后不再有“shop 库”：它的表分到会员营销、平台商城、平台基础、门店交易四个新库，支付遗留副本不带，密钥等归基础能力库。
- 餐饮、美业的商品和订单用门店交易库的公用域；它们特有的营业过程（桌台、厨房、堂食服务、人员安排、服务步骤）单独放行业库。两库之间不共事务：下单后厨房出品、到店后占桌这类联动走事件，短暂不一致要能自愈。并台拆台因为要改订单行，留在门店交易库。

## 3 划分原则

| 原则 | 说明 |
|---|---|
| 合并要有业务理由，不为压缩而压缩 | 同一对象的多套、旧一代、同构的重复才合并；一对多的明细（有独立的行、会单独查询或更新）保留为表，不压成主表里的 JSON |
| 一个业务对象只有一个归属库 | 其他库要用它，只存业务编号和必要的快照，不建第二份 |
| 库之间不联表、不共事务 | 跨库协作走服务接口或事件 |
| 库里只存业务数据 | 事件收发是公共能力，放基础能力库一套；防重是功能能力，由应用层做，加业务表唯一键兜底，不建表；发号、任务调度也是公共的（用户 2026-11-25 确认） |
| 一个库一条迁移线 | 每个库一个迁移目录、一张迁移历史表；现有的分模块历史表不带进新库 |
| 拆库不等于拆进程 | 仍可一个进程连多个库（现在已经连着主库、支付、库存、密钥四个数据源）；正式库连接数上限 250，每个连接池要设小 |
| 行业只留行业特有的 | 餐饮、美业只保留桌台、出品、预约编排、工单这类特有对象；订单、结账、班结、离线、套餐选配由零售统一提供 |
| 同构的账和结算各用一个内核 | 支付库里现金、积分共用账务内核与结算内核 |

## 5 主要的抽象与收敛项

| 项 | 所在库 | 做法 |
|---|---|---|
| 账务内核 | 支付库 | 现金、积分各记一套账，统一成账户、凭证、分录三张；保证金、欠款是账户的一种 |

| 日志归审计 | 基础能力库 | 各模块的变更日志、状态事件并入统一审计 |

## 6 事件与防重不进业务库之后要注意的

用户确认：数据库只存业务数据，事件属于公共能力，防重属于功能能力。这样各业务库更干净，代价是：
- **事件和业务数据不在同一个事务里。** 业务写成功而事件没发出去的情况会出现，需要靠公共事件能力的重试，加上各业务的对账与补偿来兜住。厨房出品、扣库存、发积分这几条链路要各有补偿办法。
- **防重靠应用层加业务唯一键。** 订单号、支付流水号、外部单号这类字段上要有唯一约束，重复请求靠它挡住；纯应用层的防抖挡不住并发与重试。
- **公共事件、公共发号成了所有库都依赖的东西**，它们的可用性要高于任何一个业务库。
