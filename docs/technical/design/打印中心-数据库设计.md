## 1. 设计范围与决策

用户要求：基于订单支持打印机管理、打印任务管理、云端与本地打印、不打印/漏打的容错、补打/加印监控及完成通知。

本次沿用已提出的统一打印中心＋云端/本地适配器。全云方案对现有本地设备支持受限；全本地代理方案增加全部门店部署负担；混合方案让两类设备共用需求、票据和结果模型。首家厂商及本地系统尚未选定，不影响通用结构；具体适配能力和真机验收须在接入时确定。

设计者建议的默认值：一台设备同时仅一个未决任务；副本拆任务；未知结果禁止自动补打；代理仅执行云端已接收任务；暂不包含离线新建订单和离线自主生成打印需求。快递取号不属于打印中心。

### 1.1 与项目现状对齐

- 复用 `sys_outbox` / `sys_outbox_delivery`，不建第二份订单事件或通知投递队列。
- 复用 Job 调度和 `shop-notify` 通知。打印领域拥有业务编排，独立`print-channel`只拥有打印/PDF/存储协议适配，`print-domain`拥有业务编排。
- `tenant_no`来自认证租户，`entity_no`是经营主体。BizContext的merchantNo需经既有商家合同解析到entityNo；不得假定两个字段名字不同但值必定相同。storeNo必须属于该主体且在账号授权内。
- 关联 `ord_order`、`ord_sub_order` 和行业工作流的稳定业务号，不复制订单、支付、库存账。
- DDL兼容MariaDB/MySQL 8，跟随同库统一字符集和排序规则，不引入专属COLLATE、JSON函数索引或数据库ENUM。所有时间为UTC `DATETIME(3)`，API使用带偏移的RFC3339。
- 主键 `id BIGINT` 仅供内部排序，API只使用字符串业务号。领域引用采用逻辑外键，每次写入验证完整的租户、主体、门店归属；本稿不添加跨域物理外键。

22张打印中心设计表，另有订单所有者1张ord_print_fact，不要求一次全部上线。DDL和字段字典逐列定义字段、空值、唯一键及索引。

## 3. 配置模型

### 3.1 物理设备与连接

一台物理设备只有一行主档、一种当前活动连接（CLOUD或LOCAL）。厂商序列号可规范化为physical_key；无可信序列号时通过登记标签和现场确认赋予稳定身份，不能根据IP、USB端口或打印队列名直接认定是另一台设备。跨租户重复设备登记还需按供应商账号绑定规则校验，租户内唯一键并不能阻止跨租户错误绑定。

LOCAL必须有同门店有效agent_no；CLOUD必须有适配器要求的设备及账号身份。更换连接递增connection_revision；在途未决任务存在时拒绝普通换绑，走先核实/取消的处置流程。每次attempt冻结非敏感connection_snapshot，后续查询必须用原通道身份。原通道凭据通过prn_credential_version保留不可变加密版本，attempt.credential_ref固定引用。轮换后旧版本为QUERY_ONLY，仅允许查证/取消既有任务，不能新提交；未决任务结束前禁止删除。供应商主动撤销旧密钥导致查询失效时进入UNKNOWN并告警，不能宣称一定可查。

云端credentials只在prn_credential_version存密文和key version，不返回API、不写日志；代理访问凭据存哈希。连接参数不允许任意URL、任意文件路径或任意指令，按适配器schema及允许的本地网段、端口、队列校验。

能力声明示例：

```json
{"schemaVersion":1,"submitIdempotency":false,"lookupByDispatchKey":false,"queryJob":true,"cancelJob":false,"completionEvidence":"PROVIDER_CONFIRMED","paperWidthsMm":[58,80]}
```

能力由服务端适配器和实测认证约束，不接受前端或代理自报能力后自动提高信任级别。设备健康状态为ONLINE/OFFLINE/PAPER_OUT/ERROR/UNKNOWN；只有本次可信观测才能更新，心跳只证明代理可达。

### 3.2 模板、路由与策略版本

模板、路由均采用头表＋版本表。草稿可编辑，发布后只允许新增版本和CAS切换头指针。平台模板使用平台系统主体；服务端按同scene＋variant_code的“门店→经营主体→平台→内置极简”显式读取，跨主体只允许读取公开平台模板。

scope_key使用非空字符串，避免NULL唯一键产生多个平台默认模板。variant_code标识STANDARD_58/STANDARD_80；模板发布版本paper_width_mm必须与变体一致，payload_schema_version与场景载荷合同一致。发布验证字段白名单、最大长度、循环上限、纸宽和金额格式，拒绝eval、脚本、未经允许的ESC/POS控制字节。内置极简模板也有renderer_version，不伪造template_version_no。

路由规则格式：

```json
{"schemaVersion":1,"rules":[{"ruleKey":"hot","priority":100,"match":{"all":[{"field":"stationNo","op":"EQ","value":"HOT"}]},"targets":[{"targetKey":"main","printerNo":"P001","templateSelection":{"mode":"SCENE_DEFAULT","variantCode":"STANDARD_80"},"copies":1,"required":true}]}]}
```

每个document按priority降序、ruleKey升序首中一条规则；一条规则可以有多个目标。没有普通规则命中才走fallback。规则priority负责匹配顺序，不等于任务投递priority。目标templateSelection仅允许SCENE_DEFAULT或PINNED_VERSION；固定模式必须同场景、同变体且可读，失败时阻断，不暗换模板。默认模式逐层降级只允许同场景同变体。匹配只影响对应文档，分单过程记录源业务行及数量，验证分单覆盖完整且无非预期重复。

每个门店场景启用前建立effective_from为门店建档时间、enabled=false的基线策略版本。首个版本之前视为关闭：扫描只计入不需打印统计，不创建需求；消费到已登记场景的事实可建SKIPPED请求并引用基线策略。未注册场景留隔离告警，不伪造策略版本。

场景策略默认不追溯生效。写入prn_policy_version并更新头表在同一事务，effective_from按数据库时间递增；有效区间为本版本起点到下一版本起点。对账按source_occurred_at选当时有效策略，不拿今天开启的规则给历史订单批量补票。头表字段是当前版本投影，不能单独修改。需求冻结策略和来源版本；模板/路由在生成时冻结，生成后不随当前配置变化。prn_job.template_resolution_snapshot保存mode、scene、variantCode、sourceSchemaVersion、选中的版本或builtinKey、候选尝试及失败原因；补打沿用原快照。场景目录为受版本管理的注册定义，见schema/print-scene-catalog.json，不新增门店任意编辑场景表。

## 4. 需求、快照与幂等

### 4.1 触发身份

`trigger_key = SHA256(canonical(tenant,entity,store,bizType,bizNo,bizRevision,scene,triggerType,triggerInstance))`。

triggerInstance是支付/下达/结账等稳定业务事实号，同一事实由Outbox重放和漏任务扫描发现时必须相同；不能用随机事件号、扫描时间或当前订单更新时间替代。source_event_no仅用于追溯；source_ref保存可解析的factNo、triggerInstance和snapshotRef，即使source_snapshot缺失也能用原事实恢复，不能从trigger_key哈希反推。人工EXISTING_FACT必须沿用该源事实自动触发的triggerType、triggerInstance和bizRevision，命中相同trigger_key，不用operationNo另建需求；仅PRE_BILL的CURRENT_VERSION使用operationNo作为triggerInstance，source_ref仍保存可信订单版本和人工触发身份；测试来源使用type=PRINTER_TEST、no=printerNo、factNo=operationNo、revision=connectionRevision、snapshotRef=固定测试样式版本。测试打印同样经request/batch/job链，bizType=PRINTER_TEST、jobKind=TEST，不混入业务订单汇总。

当前OrderPaid事件字段不足以直接渲染整张票。接入时需补充不可变打印事实或通过订单所有者提供“按业务事实号/业务版本取快照”的合同，包含门店、子单、稳定行引用、数量、金额、币种和必要履约字段。不得延迟消费时查询当前订单并冒充事件时快照；拿不到历史快照则BLOCKED并告警。

模板降级只处理表现层失败；缺失商品/数量/金额等业务事实不能靠默认空值伪造成功。快照含必要顾客信息时按权限裁剪，审计和异常只存脱敏摘要。

### 4.2 原子生成

1. 消费Outbox或业务事实扫描，按trigger_key插入/读取request；完成可靠留存后方可确认事件消费。
2. 取来源快照、匹配路由、渲染；无路由/快照缺失写BLOCKED与incident，任务可以为零但需求不能消失。
3. 初打generation_key固定为INITIAL；锁request并验证未取消，在单个事务中插入整批job、batch和审计，request→GENERATED。唯一键冲突读取原批次，不补插第二套。
4. 补打/加印generation_key=operationNo；同一写命令重发只得到原批次。
5. 原任务内容、document_key、route_rule_key、target_key、copy_index永久固定。副本从1编号；批量输入重复jobNo先拒绝，不能算成两份。

自动补偿只补建缺失的初打需求或安全恢复原任务。若历史任务已存在，配置变化不成为新增一套票的理由。取消事件必须留存业务事实，并在生成与投递前校验源版本/取消状态；迟到的下达事件不能覆盖较新的撤销事实。

## 5. 任务状态与完成证据

| 从 | 可到 | 条件 |
|---|---|---|
| PENDING | DISPATCHING / CANCELLED / FAILED / STALE | 领取 / 未投递取消 / 不可恢复错误 / 超过有效期 |
| DISPATCHING | ACCEPTED / PRINTING / COMPLETED / RETRY_WAIT / UNKNOWN / FAILED / CANCELLED | 已受理 / 可信进展 / 完成证据 / 明确未受理可重试 / 提交结果不明 / 明确永久失败 / 可信外部取消证据 |
| ACCEPTED | PRINTING / COMPLETED / CANCELLED / UNKNOWN / FAILED | 可信状态 / 完成 / 外部确认取消 / 失联待核实 / 明确失败 |
| PRINTING | COMPLETED / UNKNOWN / FAILED | 可信完成 / 结果不明 / 明确失败 |
| RETRY_WAIT | DISPATCHING / CANCELLED / STALE / FAILED | 到期且仍有效 / 未执行取消 / 过期 / 超限 |
| UNKNOWN | ACCEPTED / PRINTING / COMPLETED / FAILED / CANCELLED / RETRY_WAIT | 查明原提交结果；转RETRY_WAIT须有明确未受理且不会晚执行的证据 |
| STALE | PENDING / CANCELLED | 人工核查业务仍有效后恢复 / 放弃过期任务 |
| FAILED / CANCELLED / COMPLETED | 无普通迁移 | 失败后补打生成新任务，不重置原任务 |

attempt=FAILED须记录queueTerminated、partialOutput和evidenceRef：只有可信queueTerminated=true才可释放闸门；partialOutput=true不得安全重试，须带风险标识补打。取消时若已完整打印，优先采用可信完成证据，取消操作返回失败；仅明确未完成且队列已终止才置CANCELLED。

明确“未打印”未必等于“不会再打印”：外部队列仍挂起的任务保留ACCEPTED或UNKNOWN，不自动重发。部分出纸或截断应为FAILED/UNKNOWN，补打仍标明可能重复；不能认定整张从未输出。

COMPLETED必须有DEVICE_CONFIRMED、PROVIDER_CONFIRMED或MANUAL_CONFIRMED证据之一，并保存receipt。已提交、系统队列清空、断开socket均不足以认定出纸。IPP还需检查reason等字段，不能只看completed字面值；见[IPP标准](https://www.rfc-editor.org/rfc/rfc8011.html)。厂商返回未完成不能直接视为拒绝受理；例如[飞鹅接口](https://www.feieyun.com/open/apidoc-cn.html)区分打印提交返回的订单ID与按订单ID查询结果，实际适配以最新接口及真机结果为准。

人工确认记录actor、reason、evidenceRef及时间。不能提供物理完成证据的设备，UI显示“已提交，待确认”，由人工确认结束。

### 5.1 原始结果与补打解决分离

原票FAILED/UNKNOWN后补打成功，原票状态不改成COMPLETED。通过resolution_status=REPLACED和replacement_job_no表达该需求已由另一张票覆盖；EXTRA不解决原票缺失。

同一root_job_no创建新补打时锁原票行；存在未决补打则拒绝再次创建，除非已有明确终局且经权限校验重新补打。UNKNOWN的人工风险补打记录风险确认并建立replacement关系，原设备闸门仍不自动释放。

批次status统计自身原始任务结果；resolved_status按每个必需票“自身完成或被已完成补打覆盖”计算。补打完成不会伪造原批次全部原票打印成功。可选任务失败不阻止必需票完成，但必须保留异常提示。resolved_count只统计原票未完成、且补打已完成覆盖的任务，不能与confirmed_count重复计数。

## 6. 串行、租约、重试与本地恢复

### 6.1 云端与本地共用投递协议

- 锁runtime和job，分配单调printer_sequence，选择priority DESC、sequence ASC的可投递任务。优先级只在尚未提交的任务间生效，不能中断已出纸任务。
- runtime存在未决任务则不发下一张；故障闸门按同一物理设备共享。所有状态写事务统一按门店stream行→printer_no排序的runtime行→root_job_no排序的任务行→其他子行顺序加锁，禁止另一条路径先锁job再锁stream。stream行只用于短事务，不跨外部网络调用。
- 在网络调用之前提交attempt=PREPARED、job=DISPATCHING、runtime闸门与lease/fence。实际发包前记录SUBMITTING。
- lease只允许当前持有者操作；每次领取递增fence_epoch。本地session_epoch也必须匹配。
- lease失效不能证明未提交：PREPARED若缺少可证明未发包的本地日志，也按UNKNOWN处理；SUBMITTING失联必先核实。
- 云端超时按dispatch_key或provider_job_id查询；适配器不支持幂等/查询时转UNKNOWN。租约和数据库唯一键不能保证物理世界exactly-once。
- 只有明确NOT_ACCEPTED且不可能晚执行才可创建下一attempt。建议退避1/5/30/120/600秒并加抖动；retry_count统计初次提交后的自动再提交次数，max=5即最多6次提交。单纯查询不增加retry_count。
- 任务接收后未决直到可信完成、终止取消、明确失败且队列已结束；UNKNOWN不释放物理机闸门。若失败仍可能继续执行，仍保持闸门并建incident。

### 6.2 本地持久化合同

代理维护本地SQLite等可靠存储，不与云端同库，至少保存：

| 本地表 | 必需字段/唯一键 |
|---|---|
| local_dispatch | dispatchKey主键、jobNo、attemptNo、printerNo、fenceEpoch、sessionEpoch、connectionRevision、documentHash、transportHash、不可变待打印文档、状态、systemJobId、receivedAt/submittingAt/finishedAt |
| local_event | eventNo主键、dispatchKey、单调sequence、status、evidence、occurredAt、ackedAt；dispatchKey＋sequence唯一 |

代理先持久化任务再ACK接收；提交设备前持久化SUBMITTING；设备结果写local_event后持续补传直到云端确认。重启时先加载历史未决dispatch并查本地系统队列/设备结果，禁止直接重打SUBMITTING。无法查证则报UNKNOWN。

离线仅继续已持久化且仍在有效lease、安全授权范围内的任务；未提交且lease已过期的任务停止。失联期间云端不把未决任务自动交给另一代理。旧会话回传证据仍可入receipt，但不能续租或执行新任务；服务端验证历史attempt身份后裁决，不简单丢掉可能证明已出纸的迟到证据。

换代理/换备用机前必须确认原队列已取消且旧代理停止执行。取消能力不足则人工隔离设备并确认风险，不能依靠fenceEpoch宣称旧硬件被拦住。

## 7. 回执、操作与事务边界

- 回调先鉴别供应商账号/代理、验签及防重放，再映射tenant/entity；不能信任回调体自带tenantNo。未验签请求只进受限安全日志，不进入业务收件箱。
- 验证成功但尚未匹配任务的回调存UNMATCHED，定时与外部号关联；来源账号及hash限制唯一性。UNMATCHED的entity必须由可信账号绑定解析，无法解析则进入隔离入口，不猜主体。
- receipt存原始状态及脱敏证据，同ID不同payloadHash报CONFLICT；同ID同载荷幂等返回。
- 锁attempt/job/runtime，校验事件时间、序列、证据强度和执行身份，更新结果、批次投影、审计和Outbox事件在同一事务。迟到证据只作用于所属attempt及原job/原batch，按原任务状态和证据规则裁决；原票UNKNOWN可被可信完成证据收敛，并检查补打后的重复风险；已结束原票出现矛盾证据则建立CONFLICT，不影响新活动任务。释放runtime必须CAS匹配active_attempt_no和fence_epoch，不能清除已经属于下一任务的闸门。无可靠时序且结果矛盾则保留CONFLICT并人工核实；终态不被低可信旧回执覆盖。
- 同一事务写operation与领域副作用。异步命令先持久化operation=PENDING及恢复载荷，恢复Job保证操作不悬空；命令受理成功不代表打印成功。UNKNOWN保留原操作号查询，不能换幂等键重发。
- 涉及外部设备绑定、取消、探测等跨网络动作，先保存本地操作，事务外调用，再落证据；禁止持有数据库事务等待厂商响应。
- 批量补打最多50个原任务，同门店，按request_no分组创建多个批次，operation.result_ref返回batchNos；所有组在同一事务原子创建，任一状态/权限不合法整体拒绝，响应列出冲突，不静默跳过。打印执行结果仍逐票独立。

### 7.1 提交有序的页面变更流

每个会产生页面变化的写事务先锁prn_store_stream对应门店行，递增last_sequence，为该事务内action_log逐条分配store_sequence，锁保持至提交。M05按store_sequence读取，不能用AUTO_INCREMENT id直接作为可推进水位：低id事务可能晚于高id提交而永久漏读。多门店事务按tenant/entity/store排序取stream锁；清理记录后同步retained_from_sequence。回执收件箱只落原始证据时可不写页面流，状态处理事务必须写。

## 8. 漏打对账与告警通知

1. **业务→需求**：按订单/行业所有者提供的可靠打印事实增量接口，使用稳定事实号和当时策略重建应打印集合。不能只扫描Outbox，因为源事件可能根本未发布。
2. **需求→票据**：查PENDING/BLOCKED及GENERATED数量不符，恢复初打生成事务或建立异常，不创建第二套。
3. **票据→结果**：检查DISPATCHING租约、ACCEPTED/PRINTING结果超时、UNKNOWN、重试到期及过期票，按能力查询并创建待办。
4. cursor按(业务事实时间,事实号)稳定推进，包含5分钟重叠；只有本页全部需求已可靠写入才推进。事实源须提供更新日志/稳定修订序号以覆盖迟到与回填；每日全量核对近7日未闭合事实，历史回填额外触发指定范围扫描，不能靠有限重叠窗口保证无限迟到不漏。
5. prn_incident记录OPEN→ACKNOWLEDGED→RESOLVED。ACK只代表有人处理，不能把任务改成功；同一故障恢复后再发生递增故障代次并生成新incident_key。
6. 状态变化通过Outbox发布PrintTaskCompleted、PrintBatchResolved、PrintIncidentOpened/Resolved。通知去重键包含目标号、事件类型、状态revision和接收者；最终投递、重试、渠道日志归现有通知系统。
7. 批次通知区分“原票全部完成”和“补打后需求已完成”；批次解决后收到原票迟到完成，保留可能重复incident，不能再发一条无说明的普通成功通知。

## 9. 安全、保留与实现验收

- 所有逻辑引用验证tenant/entity/store一致；平台默认模板是唯一显式跨主体读取例外，公开内容不含门店数据。对他店对象统一返回不存在/无权访问，不暴露设备信息。
- 配对码单次、10分钟有效、限速；凭据撤销和轮换有审计，agent不持有商家登录Token。
- 一般任务/快照默认保留180天，原始脱敏receipt默认30天；未决任务、补打链、未消费事件及幂等台账不得提前清理。业务触发键和operation幂等摘要默认至少365天，历史对账仅在该保留边界内自动补建；更久的手工历史扫描先核对归档去重账，不能当作新事实自动打印。隐私字段支持受控加密、到期脱敏，长期审计只保留标识和摘要。
- DDL未使用物理外键，必须实现同主体引用、copies 1..10、索引字段非空、连接字段互斥、模板版本归属、策略生效递增、完成证据约束的服务端校验；数据库CHECK可在实施时补充，但不得仅靠前端校验。
- 验收覆盖：重复事件与重发幂等、路由零命中、部分副本失败、发包后进程崩溃、已受理但无回执、先回调后保存外部号、乱序/冲突回执、本地断网及代理切换、取消事件先到、补打后原票晚出、通知失败重试、跨店越权。
- 真机覆盖58/80mm中文、切纸、缺纸/卡纸、重启、断网、队列取消与结果查询。DDL兼容性最终须在隔离的MariaDB与MySQL 8中执行建表验证；文档静态检查不能替代该验证。

## 10. 独立模块、模拟与PDF增量

物理数据仍位于当前平台库，由print-domain持有22张prn_*表，不增加独立数据源。源订单事务冻结ord_print_fact并发送ORDER_PRINT_FACT_READY，消费者仅经PrintSourceFactsPort访问，不直接读订单Mapper。完整模块与接口封装见总方案。

request.output_options冻结伴随PDF策略；scene_policy.output_options是当前投影、policy_version.policy_snapshot保存历史值。job.layout_profile_snapshot和layout_snapshot固定实际纸宽、边距、字体版本、页面和系统插槽，PDF/补打不按当前模板重新排版。

prn_simulation_run：PENDING→RUNNING→PASSED/FAILED；fixture版本、输入、文档及系统模拟警示固定，RUNNING失联可从同一输入确定性重演。CAS/租约阻止多worker重复结算；独立event_journal不是生产receipt，模拟不计入订单完成统计。

prn_export_task：PENDING→GENERATING→READY/FAILED，文件过期→EXPIRED。generation_epoch和claim租约阻止旧worker提交READY；已冻结输入、导出时间、PDF标识和字体版本保证同export重试字节一致，私有原子写后核对hash/大小。失败自动重试最多3次（5/30/120秒），查询不增次数；PDF文件7天、元数据180天、授权链接60秒，required_data_scopes冻结字段权限并在每次下载时重验，签名URL不入库。

导出key按tenant/entity/store/source/profile/冻结文档集合摘要计算，手工和伴随流程命中相同有效导出；过期后若源仍可读允许新导出代次，export_key包含generation，不能违反唯一键或用旧Idempotency-Key伪装新请求。重用READY记录也需当前鉴权。清理先EXPIRED后幂等删对象，恢复Job补偿对象/元数据不一致。

模拟、PDF、实体打印状态独立，simulation不允许写生产resultEvidence，export READY不更新job.status。PrintArtifactStorePort由print-channel实现，复用受控私有存储基础设施，不复用仅允许商品图片的MediaAssetQueryPort。

订单事实ord_print_fact额外固定printability、block_code和diagnostics。业务不支持金额组成时仍与Ready事件同事务留存，由打印消费者落BLOCKED；不能以该业务诊断抛异常回滚支付。源事实不自动改写；来源控制与取消守卫见完整方案第3节。
