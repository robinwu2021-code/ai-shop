# 一 · 需求梳理（电子元器件分销/贸易）

## A · 料号主数据（Part Master）

| # | 需求 |
|---|---|
| A-01 | **MPN + 制造商**联合唯一确定一个器件（`GRM188R71H104KA93D` × Murata）；同一 MPN 不同厂 = 不同器件 |
| A-02 | 内部料号（自编码，仓库与财务用） |
| A-03 | **客户料号交叉引用（CPN）**：同一器件，A 客户叫 `R-0402-10K`、B 客户叫 `RES100`；报价与出货单要按客户的叫法打印 |
| A-04 | 参数化属性：封装（0402/0603/SOT-23）· 容值/阻值 · 精度 · 温度范围 · 耐压 · 材质（X7R/X5R） |
| A-05 | **生命周期状态**：Active / NRND（不推荐新设计）/ EOL（停产）/ Obsolete；状态变更来自厂商 PCN/PDN 通知 |
| A-06 | **替代料关系**：Pin-to-pin 完全替代 / Functional 功能等效 / 升级料号；带方向（A 可替 B 不代表 B 可替 A） |
| A-07 | 合规属性：RoHS · REACH · **MSL 湿敏等级**（决定开封后可存放时长）· HTS 海关编码 · ECCN 出口管制 · 原产地 |
| A-08 | 数据手册（PDF）链接、封装图、实物图 |
| A-09 | **包装形态**：Reel（整盘）/ Cut Tape（剪带）/ Tube（管装）/ Tray（托盘）/ Bulk（散装） |
| A-10 | **SPQ 标准包装量** · **MOQ 最小起订** · **订购倍数**（只能按 5000 的倍数买） |
| A-11 | 料号合并/别名：录入时同一器件被建了两次，要能合并且不丢历史 |

## B · 库存管理

| # | 需求 |
|---|---|
| B-01 | **批次/Lot** + **日期码（Date Code）**：`2438` = 2024 年第 38 周产；同一料号不同批次要分开算 |
| B-02 | **卷盘唯一号（Reel ID）**：一盘一码，扫码出入库；剪带后拆成"整盘 + 余料" |
| B-03 | 有效期：按 MSL 与日期码推算；临期预警 |
| B-04 | 多仓 + 库位（货架/箱位） |
| B-05 | 库存状态四分：可用 / 已预留 / 在途（PO 未到）/ 已分配（订单占用未出库） |
| B-06 | **寄售库存**：客户寄存在我这、或我寄存在客户处，**所有权不属于我但要管** |
| B-07 | 账龄与呆滞分析（>180 天） |
| B-08 | 出入库、盘点、调拨、报废 |
| B-09 | 成本：批次成本（同料号不同批次进价不同）；毛利按批次算 |
| B-10 | 静电/防潮存储条件记录（干燥柜、烘烤记录） |

## C · 线上询报价（RFQ → Quote）

| # | 需求 |
|---|---|
| C-01 | **BOM 上传**：客户传 Excel/CSV，几十到几百行；列名千奇百怪（Part No/型号/物料编码…） |
| C-02 | **逐行料号匹配**：精确 MPN / 去符号模糊匹配 / 客户料号命中 CPN / 匹配不上转人工 |
| C-03 | 询价单（RFQ）：客户提交，逐行含**需求数量、目标价、需求交期**；一次询价可含多行 |
| C-04 | **报价（Quote）**：逐行报**阶梯价**（1–99 / 100–999 / 1000+）、交期（Lead Time）、可用库存量 |
| C-05 | **报价有效期**（7/15/30 天）—— 元器件价格波动大，过期必须失效 |
| C-06 | 多轮议价：客户还价 → 重新报价，保留版本历史 |
| C-07 | **报价转订单**：整单转 or 勾选部分行转；转单时**价格锁定为报价价**，不重算 |
| C-08 | 替代料推荐：原型号 EOL 或无货时，报价单里附替代料及其价格 |
| C-09 | 客户分级价/协议价（长期客户签年度协议价） |
| C-10 | 询价来源：网站表单、销售代客录入、邮件转入 |
| C-11 | 报价单导出 PDF（带公司抬头、条款、客户料号） |

## D · 订单与交付

| # | 需求 |
|---|---|
| D-01 | 按报价下单，价格与交期锁定 |
| D-02 | **分批交货**：一行订 10000 只，先发 3000 再发 7000；订单行有"已发/未发" |
| D-03 | 交期承诺与延期通知（客户最关心的就是交期） |

| D-06 | 退换货：质量问题退料，按批次追溯 |

# 二 · 对比分析

判定：✅ 直接覆盖 · 🔧 配置/数据 · 🧩 需扩展（小） · 🔶 需扩展（大） · ❌ 全新 · ↗ 不在本域

## 2.1 料号主数据 → V2 商品域 + V1 物料

| 需求 | 判定 | 依据与落法 |
|---|---|---|
| A-01 MPN+制造商唯一 | ✅ | **`prd_spu_std` 平台标准品就是为跨店可比而设**；MPN×Manufacturer 作为标准品的自然键。既有规则「引用标准品时类目与 optionCode 以标准品为准」正好防止商家改乱 |
| A-02 内部料号 | ✅ | `prd_sku.merchant_sku_code`（既有：ERP/收银秤通用键） |
| A-03 **客户料号 CPN** | 🧩 | **`inv_item_ref(owner, ref_system, ref, item_id)` 是现成骨架**（只追加表）；`ref_system=CPN:<客户号>`。但它在库存域，商品侧要一个投影或直接查 —— 见 §3.1 |
| A-04 参数化属性 | ✅ | 描述属性走 Schema JSON（D4）；封装/容值/精度都是 `filterable` 属性 |
| A-05 生命周期状态 | 🧩 | `prd_goods` 加一列 `lifecycle`（ACTIVE/NRND/EOL/OBSOLETE）**或**作为 Trait；PCN 通知是外部数据源，一期人工维护 |
| A-06 **替代料关系** | ❌ | 全新：有向关系表 + 类型。商品域现有 `prd_sku_bundle` 是组合不是替代，不能复用 |
| A-07 合规属性 | ✅ | 同 A-04，走描述属性；**但 ECCN/HTS 参与出口管制判断时不能放属性袋**（D4 铁律：系统逻辑不读属性袋）→ 需要时提升为列 |
| A-08 数据手册/图 | ✅ | `detail_images` + 属性里的 URL |
| A-09 **包装形态** | ✅ | **Option 轴**：Reel/Cut Tape/Tray 影响成本与库存身份 → 判据成立，是 Option 不是 Modifier |
| A-10 **SPQ / 订购倍数** | 🧩 | `moq` 已有；加 `spq` 与 `order_multiple` 两列到 `prd_store_listing`；下单校验加一条 |
| A-11 料号合并 | 🔶 | 涉及历史流水改指向，V1/V2 都无；**记账不预建** |

## 2.2 库存 → V1 进销存

**V1 已实现（可直接用）**：物料 `inv_item` · 库位 `inv_location` · 余额 `inv_stock_balance(owner,item,location)` ·
流水 `inv_ledger` · 出入库单 · 盘点 · 调拨 · 预留 `inv_reservation` · **多业主 `inv_owner`** · UOM · 每日快照。

| 需求 | 判定 | 依据与落法 |
|---|---|---|
| B-01 **批次/日期码** | 🔶 | **V1 早就留了位**：`inv_item.trackBatch` 注释写着「一期恒 0，**开启后余额要从一个数变成一组批次**」。这是本方案最大的一处基座改造：余额表加批次维度、流水带批次、出库要选批次（FIFO/指定） |
| B-02 卷盘唯一号 | 🔶 | 序列号级追溯 = 批次之下再加一层；建议**一期只到批次**，Reel ID 记账 |
| B-03 有效期/MSL | 🧩 | `shelfLifeDays` 也是留位；批次上线后按 date_code 推算 |
| B-04 多仓库位 | ✅ | `inv_location` 现成 |
| B-05 四分状态 | 🧩 | 现有 `onHand/reserved`；**在途**需要采购单（E 组，范围外）；**已分配**≈reserved 可复用 |
| B-06 **寄售库存** | ✅ | **`inv_owner` 就是为此设的**：所有权不属于自己的库存挂另一个 owner |
| B-07 账龄呆滞 | 🧩 | 批次上线后按入库日算，是报表不是新模型 |
| B-08 出入库/盘点/调拨 | ✅ | 全部现成 |
| B-09 **批次成本** | 🔶 | `costMethod` 现为 LATEST/MANUAL，**FIFO 是留位**；批次上线后才谈得上 |
| B-10 存储条件记录 | ↗ | 仓储作业记录，属仓库管理系统范畴，本期不做 |

| 需求 | 判定 | 依据与落法 |

| C-01 BOM 上传 | ❌ | 全新：文件解析 + 列映射（客户列名千奇百怪 → 需要映射记忆） |

| C-11 报价 PDF | 🧩 | 打印域现成（scene=QUOTE，vendor 换成 PDF 渲染器）—— **打印是通道不是餐饮功能，这里得到验证** |

## 2.4 订单交付 → V2 订单域

| 需求 | 判定 | 依据与落法 |
|---|---|---|
| D-01 按报价下单锁价 | ✅ | 同 C-07 |
| D-02 **分批交货** | 🔶 | **V2 订单的真缺口**：现有子单是「一次履约」模型，行上没有"已发/未发"。需要**发货单（Shipment）**对多行分次 —— `ful_shipment` 已存在（履约域），但与订单行的**部分数量**关系要建 |

# 三 · 结论：复用，不另起

**可以基于现有的商品/订单逻辑实现，不需要另起一套。** 判据不是"看起来能塞进去"，
而是**逐条检验核心不变量在新业务里是否仍然成立** —— 有一条被推翻，就该另起。

| 核心不变量 | 在电子元器件里 | 成立？ |
|---|---|---|
| 主单 = 支付边界 | 一次付款一张单（B2B 一单一商家，比 C 端还简单） | 是 |
| 子单 = 商家 × 履约边界 | 同上 | 是 |
| 行 = 下单时快照 | **B2B 更需要**：报价锁价，行价必须是那一刻的快照 | 是 |
| `markPaid` 幂等且不关心钱从哪来 | 账期收款、预付、承兑都是它的调用方 | 是 |
| 主单五态够用 | **账期赊销正好是 `WAIT_OFFLINE_PAY`**：先履约、后收钱、商家确认收款 —— 与「先吃后付」同一语义，只是从几小时变成 30 天 | 是 |
| 金额只有一个真源（订单） | 报价单不存最终金额，转单时落进订单 | 是 |
| 组合模型 L6：不得要求基础流加状态/加边 | RFQ 是前置单据（同美业预约单），零新状态零新同步点 | 是 |

**七条无一被推翻。** 所以另起一套没有依据 —— 那只会得到两套订单、两份报表、两处退款逻辑。

## 3.1 为什么「议价」没有动摇根基（最容易误判的一条）

> **2026-08-30 修订**：本节原把「订单成立后能否协商改价」列为唯一翻盘条件，判「能改 = 要另起一套」。
> 业务确认**可以改价，且餐饮/零售同样需要**。经[订单改价通盘设计](./TDD-订单改价-通盘设计.md)重做后，
> **该判断作废**：改价推翻的只是「改价 = 覆盖原值」这个隐含假设 —— 改成**追加调整记录**后，
> 快照/退款/结算/发票四条链路无一被动摇。**复用结论不变**。
> 另：我自己的设计里本就有例外 —— `weigh_adjust_minor`（正补款负退款）就是订单成立后金额变了。

直觉上「B2B 要议价、要改价」像是与「行是不可变快照」冲突。实际不冲突：

```
议价发生在【报价阶段】—— 报价单是前置单据，可以改到天荒地老、可以有版本链
     ↓ 接受报价
转单那一刻价格锁定 → 订单行落快照 → 此后不可变
```

**订单之前可谈，订单之后不可改** —— 与现有模型完全一致。
反过来说：**如果需求是「订单成立后还能协商改价」，那才真的要另起** ——
它会推翻快照、退款、结算、发票四条链路。这一条必须在需求确认时问死（见 §六 待确认⑥）。

## 3.2 需要什么（三层，按是否动核心分）

| 层 | 内容 | 动核心？ |
|---|---|---|
| **A 基座小改（3 列）** | `sell_price_entry.min_qty`（阶梯价）· `prd_store_listing.spq/order_multiple` · `prd_goods.lifecycle` | 否。加列，**且三行业共享收益**（零售满量优惠也在等阶梯价） |
| **B 新建但不碰核心** | RFQ/Quote 单据与议价（行业包）· 替代料表（行业包）· 批次库存（V1 早已留位）· 应收账款 AR（新域，**只读订单不改订单**）· 分批交货（履约域 shipment ↔ 订单行部分数量） | 否 |
| **C 另起一套订单/商品** | —— | **不需要** |

**AR 为什么不动核心**：它读订单金额、生成应收、到期催收、收款时调 `markPaid` ——
订单表一列都不用加。信用额度检查是下单前的一次校验（`CheckoutContributor` 的位置），不是订单属性。

## 3.3 成本对比

| | 复用（本方案） | 另起一套 |
|---|---|---|
| 商品/订单核心 | 加 3 列 | 重写两个域 |
| 报表 | 一份（跨行业订单/收款/结算已就绪） | 两份，且永远对不齐 |
| 退款/售后 | 复用既有状态机与仲裁 | 重写 |
| 收款 | 复用 `ord_payment` 混合收款 | 重写 |
| 打印 | 复用（QUOTE 只是一个新 scene） | 重写 |
| 真正的新东西 | RFQ + 批次 + AR + 分批交货 | **同样要写，一样都不少** |

**另起一套并不能省掉任何一件真正的新工作 —— 它只是额外再付一遍旧工作的钱。**

## 3.4 一个前提：结论依赖 §六 待确认①

若目标是**平台撮合（多商家）**而非单一贸易商，结论**不变**（跨商家购物车正是三层结构存在的理由），
但 RFQ 要支持「一次询价分发多个供应商报价」，行业包复杂度上升一档 —— 核心仍不动。

# 四 · 结构性判断

## 3.1 料号 vs 商品 vs 物料 —— 三层各归其位

三个概念看着像，**其实分别属于三个域**，混一起是这个方案最容易犯的错：

| 层 | 是什么 | 落点 | 键 |
|---|---|---|---|
| **器件（Part）** | 客观世界的那颗元件，全球唯一 | **`prd_spu_std` 平台标准品** | MPN × Manufacturer |
| **商品（Product/Variant）** | 我卖什么、怎么卖（包装形态、起订量、价） | V2 商品域 | goods_no / sku_no |
| **物料（Item）** | 我仓库里的实物（批次、库位、成本） | V1 `inv_item` | item_id（**刻意不复用 sku_no**，既有注释写明） |

三层的连接：`inv_item_ref` 已经是"外部引用只追加"的映射表 —— **CPN、MPN、内部料号统统是它的 `ref_system`**。
这张表是本方案里最幸运的一处：**为多套编码而设的骨架已经在了。**

## 3.2 RFQ 在组合模型里的位置

```
电子元器件订单 = 基础订单流 + B2B 询报价工作流
```
- **RFQ/Quote 是前置单据，不是 Engagement**（判据：不聚合订单、不结清）—— 与美业预约单同构，
  组合模型 §3.4 的判据在第四个行业上**复用成功，未新增判据**；
- 开单时机（W2）= **延迟**：报价接受才开单（与美业到店才开单同理，避免"询价即订单"污染报表）；
- 付款时点（W3）= **第四种：发货后账期** —— 这是三个行业没有的，见 §3.3；
- 同步点仍是 A1–A5，**无新增**（L6 复验通过）。

## 3.3 三处真缺口（本方案的成本重心）

| 缺口 | 影响面 | 为什么是真缺口 |
|---|---|---|
| **① 批次库存** | V1 进销存 | 余额从一个数变成一组批次；流水、出库选批、成本、盘点全部随之变。**V1 早已留位**（`trackBatch`），但留位不等于实现 |
| **② 阶梯价（数量档）** | V2 商品域 | `sell_price_entry` 加 `min_qty`；解析规则扩一维。**改动小、影响大** —— 零售的"满 3 件 9 折"也会用到 |
| **③ 账期赊销（AR）** | V2 订单/结算 | 不是新支付状态，是**应收账款域**：信用额度、账期、对账、核销。三个 B2C 行业完全没有这条 |

分批交货（D-02）是第四条，但它更像履约域的既有 `ful_shipment` 与订单行建立"部分数量"关系，成本中等。

## 3.4 与三个已有行业的差异，比它们彼此之间更大

| 维度 | 零售/餐饮/美业 | 电子元器件 |
|---|---|---|
| 客户 | C 端个人 | **B 端企业**（有采购流程、账期、协议价） |
| 成交路径 | 看到即买 | **询价→报价→议价→下单**（可能持续数周） |
| 价格 | 定价即成交价 | **一单一价**（阶梯 + 协议 + 议价） |
| 库存 | 数量 | **批次 × 包装 × 所有权** |
| 履约 | 一次交付 | **分批交付** |
| 收款 | 即时/资产 | **账期赊销** |

**结论**：它不是"第四个行业包"那么轻。三个 B2C 行业各自压基座的不同侧面（履约/多轮开单/占位），
而它**同时压商品（阶梯价）、库存（批次）、订单（分批）、结算（AR）四处** ——
这决定了它是一个**独立业务线**级别的投入，不是配几行数据加个包。

# 五 · 方案

## 5.1 分层落法

| 层 | 做什么 | 归属 |
|---|---|---|
| **基座扩展**（三行业共享收益） | ① `sell_price_entry` 加 `min_qty` 阶梯价 ② `prd_store_listing` 加 `spq`/`order_multiple` ③ `prd_goods` 加 `lifecycle` | V2 商品域，**小改** |
| **V1 进销存启用留位** | 批次维度（`trackBatch` 落地）+ 批次成本 + 效期 | `shop-inventory`，**大改** |
| **新域：应收账款（AR）** | 信用额度、账期、对账、核销 | 新模块或 settle 扩展，**独立议题** |
| **行业包 `shop-industry-electronics`** | 料号交叉引用视图 · 替代料 · BOM 解析与匹配 · RFQ/Quote 单据与议价 · 报价转单编排 · 报价 PDF | 新行业包 |
| **履约扩展** | 订单行部分数量 ↔ 发货单 | 履约域，中等 |

## 5.2 行业包的六件事声明（组合模型模板）

| 声明 | 电子元器件包的答案 |
|---|---|
| W1 对象与状态机 | RFQ（DRAFT→SUBMITTED→QUOTED→ACCEPTED/EXPIRED/CANCELLED）· Quote（版本链）· BOM 匹配任务 |
| W2 **开单时机** | **延迟**：报价被接受才 place（询价不是交易意向） |
| W3 付款时点 | 先付（小客户）/ **账期赊销**（协议客户）—— 后者依赖 AR 域 |
| W4 同步点 | A1 转单 · A2 收款/核销 · A3 分批发货 · A4 退料 · A5 事件（onPaid→释放信用额度） |
| W5 超时逆向 | 报价到期自动失效（Job）；询价长期无响应归档 |
| W6 依赖与打印 | 阶梯价 · 批次库存 · SPQ/倍数 · AR；打印场景 QUOTE / PACKING_LIST / STATEMENT |

## 5.3 分期建议

| 阶段 | 内容 | 价值 |
|---|---|---|
| **E0 基座小改** | 阶梯价 + SPQ/倍数 + lifecycle | **三行业共享**（零售满量优惠也要），风险低 |
| **E1 料号与库存** | 标准品建 MPN 库 · CPN 交叉引用视图 · **批次库存落地** | 没有批次，元器件库存就是假的 |
| **E2 询报价** | BOM 上传解析 · 匹配 · RFQ/Quote · 转单锁价 | **最能立刻产生业务价值的一段** |
| **E3 B2B 交付** | 分批交货 · 账期 AR · 对账单 | 依赖新域，独立评估 |

**建议先做 E0+E2 的最小闭环**：料号用标准品 + 手工维护，库存先不动批次（按现有数量管），
把"BOM 上传→匹配→报价→转单"这条最有价值的链路跑通；批次（E1）与 AR（E3）按客户实际要求排。

# 六 · 风险与待确认

**风险**
1. **批次一旦开启不可回退**：余额语义从"一个数"变成"一组批次"，历史数据要补批次或标记为"无批次"。V1 注释已经警告过同类问题（UOM 改了历史数字含义全变且不报错）；
2. **BOM 匹配的准确率是产品成败点**，不是技术问题：匹配错一行，客户按错料号采购，损失由谁承担 —— **必须有人工确认闸**，不许全自动直报；
3. **账期赊销涉及信用风险**，不是加个字段：额度、逾期、坏账、法务追偿 —— 建议独立立项；
4. 这是 B2B 业务线，**ops 端与销售端的界面几乎全新**（客户管理、销售跟单），本分析未覆盖。

**待确认**
① 目标客户是"元器件贸易商"还是"平台撮合"？（前者=一个商家的系统，后者=多商家平台，模型差别大）
② 一期要不要批次？（不要就能快很多，但库存数会失真）
③ 账期赊销是必须的还是可延后？
④ 是否需要采购/在途（E 组）—— 没有它，"可用库存"只是账面数
⑤ 这算 `sys_industry` 的新行业码，还是归 OTHER？（涉及支付通道准入）
⑥ ~~订单成立后还能不能协商改价？~~ **已答（2026-08-30）：可以改，且四行业共同需求。**
   经通盘设计后不构成翻盘条件，见 [TDD-订单改价-通盘设计](./TDD-订单改价-通盘设计.md)。
