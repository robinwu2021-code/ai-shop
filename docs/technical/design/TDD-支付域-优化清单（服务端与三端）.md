## L1 · 这份是什么

**代码 ⇄ 设计对齐的结论，加一份按端分的优化清单。**

前几轮对齐都在后端。这一份把**前端纳进来**：
ops-web 与 b-app 实际调了哪些支付接口，与后端有的对照。

结论先说：<b>后端能力比前端入口多</b>。
服务端该有的基本都有了（缺的是「写进去」和「核验」），
而 **b-app 有 7 个后端能力没有入口** —— 商家看不到自己的钱。

<b>核对时的默认动作应该是「先问这件事今天靠什么承担」，

## L2 · 四、b-app 优化清单

b-app 有 8 个支付相关页面（收款设置、结算单、证照与账户、售后处理、积分…），
**缺的 7 个入口集中在一件事上：商家看不到自己的钱。**

| # | 缺的入口 | 对应后端端点 | 商家因此不能做什么 |
|---|---|---|---|
| **A1** | **结算单详情** | `GET /biz/settle/bills/{settleNo}` | 只能看到列表和总额，<b>点不进去看单笔怎么算的</b>（成交额 − 佣金 − 通道费 ± 补贴） |
| **A2** | **对账单** | `GET /biz/settle/statement` | 看不到按期汇总的账 |
| **A3** | **开票申请** | `GET/POST /biz/settle/invoices` | <b>无法为结算款申请发票</b> |
| **A4** | 开票抬头 | `GET /biz/settle/invoice-title` | 同上，A3 的前置 |
| **A5** | **保证金余额与流水** | `GET /biz/deposit` · `/txns` | <b>不知道自己押了多少、冻结了多少、还差多少</b>。而准入档位的限额是按保证金算的 |
| **A6** | 按门店开通收款 | `POST /biz/merchant/payment/store/{storeNo}` | 多门店商家无法给某家店单独开通 |
| **A7** | **换一种方式重付**（C 端，一并列） | 复用 `POST /mp/order/{orderNo}/pay` | 后端已支持换商户单号，<b>而端上没有入口 —— 那条能力今天没有任何用户能触达</b> |

### 优先级

**A1 + A5 优先。**理由是同一条：
<b>商家最关心的两个数字（这单我拿多少、我押的钱还剩多少）今天都看不全。</b>
A1 只是详情页，A5 是两个只读接口 —— 两者都不需要后端改动。

**A3 次之**：开票是刚需，但它牵涉抬头维护（A4），是一组。

**A6 最后**：多门店商家占比小，且有运营端兜底。

## L3 · 五、三条口径与一条改写

### 5. S17 改写：先兑现契约，映射表等真码（2026-09-02）

原计划是「驳回原因的码 → 中文说明 + 怎么改」。
而**今天没有任何通道在产出码**：真通道一个都没接（S3 卡在凭证），
桩返回的本来就是中文。现在写映射表等于凭空发明码值 ——
微信给的是「字段名 + 中文描述」，支付宝给的是 `sub_code`，两者形状都不一样，
猜出来的表接上真通道时一条都对不上。**那张表要等真通道给出真实的码。**

改做的是把一句已经写在契约里、却没有任何东西兑现的话变成不变式：
`ApplymentResult` 的注释写着「驳回必须带原因」，而实现是一行直传 ——
通道给空，这一列就是 null，b 端那句原因是 `v-if` 渲染的，
于是商家看到「已驳回」下面**什么都没有**，只能把同一份资料再提一遍。
而重复进件会产生新的收款商户号，历史订单的分账仍指向旧号。

兜底文案**不编原因**：如实说通道没给，并明确劝阻重复提交。
编一个「资料不齐」之类的猜测更糟 —— 他会照着改一个本来没错的地方。

**顺带修了一个真缺陷**：改完重提通过之后，上一次的驳回原因不会被清掉 ——
`setRejectReason(null)` 跟着 `updateById`，而 MyBatis-Plus 默认跳过 null 字段，
那句 set 一行 SQL 都不生成。页面上「可以收款」下面挂着一句
「结算账户名对不上」。这个坑仓库里踩过一次、注释里写着，这里又踩了一次 ——
**是消融把它逼出来的**（用例第一版的夹具本来就没有旧原因，清不清都一样绿）。

### 4. S16 改写：那一屏已经有了，问题是说明会过期（2026-09-02）

原计划是「对账覆盖范围结构化」，O6 写的是「今天只有一句话」。
查了一遍：**那一屏已经有了** —— 在 `/orders` 不在 `/finance`（我先找错了地方，
这是这一轮第六次「以为没有其实有」）。它把三件事分得很开：
零差异 / 这条轴没跑成 / 这条轴查不到那一类，覆盖说明永远显示、不折叠。

真正的问题是**那句话会过期**。覆盖说明是写死的字符串，
分账那条里有一句「分账网关目前是桩实现，所以每一笔已发出的单都不会有回执」——
接了真通道之后它就是假话，<b>而没有任何东西会提醒</b>：
文案不会因为换了实现而报错，页面照常显示，读的人照常相信
「这批未确认只是因为还没接通道」。于是一批**真的没划走的钱**
会被当成已知现象放过去 —— 而这条轴存在的全部意义就是发现那件事。

改法：给 `SplitGateway` 加一位 `deliversConfirmation()`，
桩覆盖成 false，真实现用接口默认值 true（真实现不该为此写一行）。
那句话由它算出来，换了实现说明自己消失。
另加一条闸门：**每条轴都必须说清覆盖范围**，空说明在页面上等于
「这条轴什么都看得见」。

「按差异类型逐一声明可见性」那种结构化<b>先不做</b>：
今天四条轴的说明都是准确的散文，而结构化的收益要等
第二个消费者（比如按类型筛选的看板）出现才兑现。

### 3. S13 改写：先接上写入，不建表（2026-09-02）

原计划是「支付方式升格为表」。动手前量了一遍，**这条链两头都断着**：

| 位置 | 实况 |
|---|---|
| `sys_pay_channel.pay_methods` | **有值，但没有任何决策读它** —— 只映射进一个前端不读的 VO |
| `mch_payment_merchant.pay_methods` | **有读取方，却从没被写过** —— 全项目 `setPayMethods` 只出现在三个测试文件里 |
| `packages/shared` 的 `canPay` | **有逻辑，零调用点** |

而中间那段逻辑写得很仔细：结算页与收银台都按它求交集（一笔支付覆盖整单，
有一家不支持就用不了），空集当「未配置」跳过、未配置返回 null 而不是空数组。
<b>只是它的输入永远是空的</b> —— 那条判据从来没有真正生效过，
而它不生效的表现是「一切正常」：交集永远不收窄，所有方式都可用。

**所以先建表是加第四个没有内容的结构。** 改做的是接上写入：
进件通过时把通道那份清单落到商家进件记录（商家能用的方式是通道支持的子集，
通道回执没有明确缩窄时两者相等）。这样：

- `sys_pay_channel.pay_methods` 有了第一个决策消费者；
- 那条交集判据的输入真的有内容 —— 一单跨微信店与支付宝店时，
  两边方式集合不同，交集<b>会真的收窄</b>；
- 将来通道回执带了范围，改的是那一行的来源，不是下游任何一处。

**表什么时候该建**：出现第二个消费者时 —— 具体说是端上要按方式渲染
（名称、图标、排序），或者要按市场分别启停某种方式。今天 C-1 返回的
`methodCode` 与 `payChannel` <b>传的是同一个值</b>（用户选的是「微信支付」
不是「JSAPI」），所以那两件事都还没发生。

## L3 · 六、两条要先定产品口径的

### 1. 提现走不走产品

事实：C 端与 B 端都没有提现端点；`WithdrawService` 没有申请方法；
提现单在生产代码里从没被创建过。**运营端的提现审批页永远是空的。**

三种口径，选一个：

| 口径 | 要做什么 |
|---|---|
| **一期就是线下结算** | 把提现表与那两个端点<b>明确标注为未启用</b>，运营页面挂提示条。今天它看起来能用 |
| 走产品，但只有运营代申请 | 加一个运营端的「代商家发起提现」入口 |
| 走产品，商家自助 | B 端加申请页 + 后端加申请方法 + 额度/频次校验 |

**不选的代价**：运营看着一个永远空的审批页，
而商家在问「我的钱怎么提出来」。

### 2. 不可用支付方式的原因给不给买家看

C 端支付方式列表里，不可用的那些要不要带原因？
「该店铺尚未开通支付宝收款」是给**买家**看的 ——
对买家说「这家店没开通」合适吗，还是说得更中性（「暂不支持」）。

这是产品口径，不是技术问题。

## L4 · 六、建议的推进顺序

立刻（不依赖任何东西）

  S2  加双写闸门

  S11 → S12 → S13 → S14
