对标口径：美团外卖的地址链路，按公开可见的产品行为整理，用来**对齐概念与主路**，不逐像素照抄。

## 0. 主张 —— 要害不在界面，在一条数据约束

抄界面是容易的：顶栏一行地址、列表卡片、右上角编辑图标。但让美团整条链路成立的是这一条：

> **地址主体是「选」出来的，不是「打」出来的。**

在美团里你敲不出一个收货地址 —— 只能从 POI 联想里挑一个、或在地图上指一个，
然后**单独补门牌号**。于是每条地址天生带坐标，门牌号天生独立。

我们现在是反过来的：主路是三个输入框手打，坐标是点过「地图选点」才有的副产品
（`c-app/src/pages/address/index.vue:66`）。后果不是「不够美团」，是下面四条链路
在**多数地址上求值为空，而界面上完全正常**：

| 链路 | 落点 | 这条地址没坐标时 |
|---|---|---|
| 商家自送半径 | `OrderServiceImpl.requireWithinDeliveryRadius`（backend/…/trade/service/impl/OrderServiceImpl.java:1755） | **直接放行**。商家以为自己限定了 3 公里，实际多远的单都进来，等他要送货才发现送不到 |
| 按坐标算可见性（多位置第二步） | [TDD-按坐标算可见性](./TDD-按坐标算可见性.md) | 这条位置推不出任何商家 |
| 生效位置 → 归属社区 | `stores/location.ts` `syncCommunityFromActive` | 静默不动 —— 用户「换了地址，商品没变」 |
| 导航到收货点 | `openLocation` | 没有入口 |

所以本方案的第一优先级是**把「选」提为主路、「打」降为兜底**，而不是重排卡片。

## 1. 美团把「地址」拆成三件事，我们挤在了一页里

美团那边这是三个界面、回答三个不同的问题：

| # | 界面 | 回答什么 | 写回什么 |
|---|---|---|---|
| **A** | 我的 › 我的收货地址 | 我有哪些地址 | 长期资料（增删改、默认） |
| **B** | 下单页 › 点收货地址 | **这一单**送到哪儿 | **只改这一单**，不动默认 |
| **C** | 首页顶栏 › 点地址 | **现在**按哪儿看货 | 浏览上下文（生效位置） |

我们三件事都有对应物 —— 而且 C 这件事[已经想清楚并上线了](./TDD-多位置单生效.md#4-设计)：
「生效位置」与「默认地址」是两个字段、两个按钮，这一点比多数同类产品都干净。

问题在于**三件事共用同一个页面、同一套操作行**：

| | 我们的落点 | 状况 |
|---|---|---|
| A | `pages/address/index` | 卡片上四个操作并排：设为当前位置 / 设为默认 / 编辑 / 删除 |
| B | 同一页 + `?picking=1`（`order-confirm:392`） | **选一条会改掉默认地址**，而且选完回去结算页不刷新 —— 见 §5 |
| C | 同一页（`home/index.vue:110` 按状态分流过来） | 与 A 的编辑/删除混在一起 |

结论：**不必新建三个页面**，但 B 与 C 必须各走各的模式，且 **B 不许写回长期资料**。

## 4. 交互方案

四个界面。A / A2 / A3 是地址簿这条线，B、C 是复用它的两个模式。

### 4.1 界面 A：地址簿（`pages/address/index`，默认模式）

```
┌ 收货地址 ─────────────────────────┐
│  张三  138****8000        [家]  默认  │
│  广东省深圳市龙华区  和平路 1 号 3 栋 501 │
│                              ✎ 编辑  │
├──────────────────────────────────┤
│  李四  139****9000        [公司]      │
│  …                            ✎ 编辑  │
└──────────────────────────────────┘
             [ + 新增收货地址 ]
```

相对现在的三处改动：

1. **卡片上只留「编辑」一个入口。** 现在四个操作（当前位置 / 默认 / 编辑 / 删除）并排在
   一行 `card__ops` 里，一张卡片上四个可点的小字 —— 密度过高，而且「设为当前位置」与
   「设为默认」这对概念差异，靠两个并排的小字是说不清的。**删除移入编辑页底部**（危险动作
   不该和高频动作同级），**设为默认移入编辑页的开关**（那里本来就有 `asDefault`）。
2. **「设为当前位置」只在 C 模式（从顶栏进来）出现。** 在「我的 › 收货地址」这个语境下，
   用户想的是管资料，不是换浏览上下文。
3. **排序**：默认置顶 → 有坐标的在前 → 最近使用（`updated_at`）。
   现在是 `is_default desc, id desc`（越新越靠前），一个用了半年的家会被上周填的一个临时地址压下去。

空列表：保持现在的 `sh-empty`，文案 + 一个显眼的「新增收货地址」。

### 4.2 界面 A2：选地址（**新增页，本方案的重点**）

点「新增收货地址」**先到这一页**，而不是直接进表单。这就是「选出来而不是打出来」的落点。

```
┌ 选择收货地址 ─────────────────────┐
│  🔍 小区 / 写字楼 / 街道             │
├──────────────────────────────────┤
│  📍 当前定位                        │
│     和平路 1 号            [重新定位] │
├──────────────────────────────────┤
│  附近                              │
│  阳光花园              和平路 1 号 · 120m │
│  科技大厦              和平路 9 号 · 450m │
│  …                                 │
├──────────────────────────────────┤
│  在地图上选点  ›                     │
│  找不到？手动填写地址  ›              │
└──────────────────────────────────┘
```

- **搜索**：复用 `searchPlacesNative` / `searchPlacesNearNative`（`packages/shared/src/ports/geo-search.ts`）。
  这条路走**包里的原生高德 SDK**，不需要 Web Key，也不经后端 —— b-app 的区划选择器已经跑了一段时间。
- **附近**：有坐标时按距离排；`canSearchPlaces()` 为 false 的端（H5、小程序）**整段不显示**，
  直接落到「手动填写」那条 —— 不给一个点了没反应的入口。
- **当前定位**：受[定位能力约束](./TDD-定位能力受限下的位置模型.md)。
  拿到的是**区级模糊坐标时不显示距离**（5 公里误差写成「733m」是假精确，用户会照着它挑最近的）；
  拿不到定位就不显示这一段，不报错、不弹窗。
- **地图上选点**：现有的 `chooseLocation`，原样保留。
- **手动填写**：**必须留着**。存量地址、区划表里没有的写法、以及所有 POI 搜不到的地方都靠它。
  走这条路的地址没有坐标 —— 保存时给一句明说的提示（见 §4.3）。

选中任意一条 → 带 `{ name, address, lat, lng, province/city/district }` 进编辑页。

### 4.3 界面 A3：编辑（保持 `sh-sheet` 弹层，字段重排）

| 字段 | 规则 | 变化 |
|---|---|---|
| 收货地址 | **只读**一行，展示 A2 选中的地址主体 + 坐标标记；点它回到 A2 重选 | 🆕 从「三个输入框」变成「一行 + 重选」 |
| 门牌号 | 必填，`maxlength=40`，占位「楼号-门牌号，如 3 栋 501」 | 🆕 独立字段 `houseNo` |
| 收货人 | 必填，`maxlength=64` | 不变 |
| 手机号 | 必填，`isPhone`（不是只查 11 位长度） | 不变 |
| 标签 | 预设 chip：家 / 公司 / 学校 / 自定义；自定义 `maxlength=8` | 🔧 现在是自由输入 16 字，而顶栏 `location.label` 直接显示它 —— 16 个字会把顶栏撑爆 |
| 设为默认 | 开关 | 不变 |
| 删除 | 底部，红色文字，二次确认（沿用现有 `confirm`） | 🆕 从列表移进来 |

- **没有坐标时**（走手填那条路）在保存按钮上方挂一句：
  「这个地址没有定位点，商家可能判断不了能否送达 —— 建议在地图上选一次」+ 一个「去选点」。
  **不拦保存**：拦了等于让一部分人存不了地址 —— 这与现在 `regionUnsplit`
  （`address/index.vue:124` 上方那段注释）的取舍是同一种口径：提示，不阻断。
- 保存后回到来处：从 A 来回 A，从 B 来则**直接选中这条新地址**并回结算页。

### 4.4 界面 B：结算页选地址（`?picking=1`）

**这一模式与 A 共用页面，但行为完全不同：**

| | A（管理） | B（选一单） |
|---|---|---|
| 点卡片 | 无动作 | **选中并返回** |
| 写回 | 增删改、默认 | **什么都不写回服务端** |
| 送不到的地址 | 正常显示 | **置灰 + 「超出配送范围」**，不可点 |
| 底部 | 新增收货地址 | 新增收货地址（存完直接用上） |

- **选中怎么传回**：`uni.navigateBack` + 事件通道（`getOpenerEventChannel` / `uni.$emit`），
  结算页收到 `addressId` 后自己 `loadAddresses()` 重取。
  **不要**再走「改默认地址让结算页读默认」那条路 —— 那正是 §5-D1。
- **置灰怎么算**：结算页已经知道这一单有哪几家商家，
  取每家的自送圆心与半径（后端 `deliveryOrigin`，与 `requireWithinDeliveryRadius` **同一套数据、同一个算法**）。
  两边都有坐标才判；地址无坐标、门店没标点、半径 ≤ 0 一律**放行**，与后端逐条对齐 ——
  端上比后端严会把本来下得成的单挡在门外。

### 4.5 界面 C：顶栏切换位置（`home:110` 进来）

维持[已上线的形态](./TDD-多位置单生效.md) §6，只加两处：

- 面板里每条**只有「切到这里」一个动作**，当前那条标出来。不出现编辑/删除/设默认。
- 底部一条「管理收货地址 ›」通向 A。
- 没有任何位置时，仍然是[「不弹窗、不跳转」](./TDD-定位能力受限下的位置模型.md)：顶栏显示「选择位置」，首页照常有东西看。

## 5. 实测抓到的三处（先修这个，再谈对标）

### D1 · 在结算页选一次地址，把用户的默认地址改掉了 —— **已修（2026-09-03）**

`c-app/src/pages/address/index.vue:186`：

```ts
async function pick(a: Address) {
  if (!picking.value) return;
  await api.setDefaultAddress(a.addressId);   // ← 长期偏好被这一单改写
  uni.navigateBack();
}
```

给父母寄一次东西，从此每一单都预填父母家。**这一单的选择不该改长期偏好** —— 与
「生效位置 ≠ 默认地址」是同一个道理，只是这次错在另一对概念上。

### D2 · 选完回到结算页，显示的还是原来那条 —— **已修（2026-09-03）**

`pages/order-confirm/index.vue` 只有 `onLoad`（:453）和 `onMounted`（:465），**没有 `onShow`**；
而 `loadAddresses()`（:366）里是 `if (!addressId.value)` —— 回来时 `addressId` 早有值，不会重取。

于是这条路的真实结果是：**用户选了 B，页面还显示 A，而他的默认已经被改成 B**。
两个缺陷叠在一起，比各自单独存在更难被发现 —— 因为下一次进结算页会显示 B，看起来「生效了，只是慢了一步」。

### D3 · 手填地址一路存到下单，商家的自送半径对它完全失效

后端那条闸写得很清楚（`OrderServiceImpl.java:1761`）：两边都有坐标才判，
没坐标**放行**。这是对的 —— 拿缺失的数据去拦会误伤。
但它意味着：只要主路是手填，商家在「送货方式」里填的半径就形同虚设，
而他**不会收到任何信号**，直到准备送货那一刻。

§4.2 把「选」提为主路，正是冲着这一条去的。

> 三处的共同点：**每一处单独看都是对的**。`pick` 复用 `setDefaultAddress` 省了一个接口；
> `onMounted` 加载是标准写法；后端放行无坐标地址是深思熟虑的。
> 错误只在把它们**接起来**的时候才出现 —— 与[多位置第一步实测抓到的那两处](./TDD-多位置单生效.md)同一个性质。

## 6. 字段与契约变更

只加一列，其余复用。

```sql
-- V319__address_house_no.sql（已落地。迁移号是提交前现查的，见「迁移号撞车」）
alter table usr_address add column house_no varchar(40) null comment '门牌号（楼号-单元-室）';
```

**加列必须同时改的七处**（漏一处那列就永远读出 null，而且零报错）。
本文原先写的是五处，落地时发现少了两处 —— 补上的两处恰恰都是「不报错」的那种：

- [x] 迁移 `V319__address_house_no.sql`
- [x] `UsrAddress` 加 `houseNo` 字段（`entity-alignment` / `SchemaDriftTest` 会查）
- [x] `AddressVO` 的 record 参数 + `build()`
- [x] `AddressService.SaveCommand` + `MpUserController.SaveAddressReq` + 透传 + `AddressServiceImpl` 写入
- [x] `packages/shared/src/types` 的 `Address`
- [x] **`c-app/src/api/requests.ts` 的 `SaveAddressReq`** ← 原先漏了。
      字段照样发得出去（`http.ts` 是展开传参），闸门全绿，但契约类型里没有它，
      于是生成的 API 文档明写着「这个接口不收 houseNo」
- [x] **`UserQueryPortImpl.receiverOf` 的下单快照** ← 原先漏了。
      只改写入不改读出，不报错、不崩、地址簿页面一切正常 ——
      只有骑手拿到的地址少了最后 50 米
- [x] 跑生成器：`gen-openapi.mjs` / `gen-api-detail.mjs` / `gen-test-schema.py`
      （文档与测试库 schema 都是产物，不手写）

`region` / `province` / `city` / `district` / `detail` **语义不变**：
`detail` 继续是「地址主体」（POI 名或街道门牌那一串），`houseNo` 是最后 50 米。
存量数据不迁移 —— `houseNo` 为空的老地址照旧显示 `detail` 一串，不会更差。

接口本身**一个都不加**：A2 那一页用的是端能力（原生高德）与已有的 `nearbyCommunities`。

## 7. 明确不做的

- **联系人性别（先生/女士）**。它在美团是给骑手电话称呼用的；我们的自提/自送场景里骑手直接见人，
  多一个必选项只是多一次点击。
- **左滑删除、批量管理**。列表上限 20，够不着「批量」这个量级；左滑在 uni 三端行为不一致。
- **定位纠偏提示**。它要静默精确定位才成立，而我们[从设计上就不押在那上面](./TDD-定位能力受限下的位置模型.md)。
- **粘贴文本智能识别**：二期。端上正则能做（姓名/手机/地址三段），但排在 1–8 之后。

### 标签存的是**文案**不是码 —— 这是个取舍，不是遗漏

按这仓对枚举的规矩，该存 `HOME/WORK/SCHOOL` 再按词条渲染。没这么做的理由很具体：
顶栏那个短名走 `location` store 的 `label` getter，而
`packages/shared/src/utils/locale.ts` **明确禁止 shared/store 反向依赖各端的 i18n**
（它自己的注释写着为什么）。存码就得把翻译推进 store，或者让 getter 返回一个
「这段要翻、那段别翻」的复合值 —— 而 `tag` 是个**纯装饰字段，全仓没有一处逻辑匹配它**
（只有三处在显示：地址簿的 chip、切换位置的 toast、顶栏短名）。

代价说清楚：**切了界面语言之后，已存的标签仍是当时那个语言的字。**
自定义标签本来就是这样（那是用户自己写的字），预设那三个会略显别扭。
存量的「家」仍然会把第一个 chip 点亮 —— 旧数据不需要迁移。

chip 与输入框**不做成两种模式**：输入框始终是唯一真源，chip 只是快捷方式，
于是没有「我现在处在哪种模式」这个问题，也没有两者对不上的中间态。

> **顺带发现：`check-i18n-orphan` 看不见动态键。** 把整段 chip 删掉之后它照样报 6 条，
> `tagHome/tagWork/tagSchool` 一个都不算落单。所以那道闸报「0 条新增」
> **在这里不构成证据** —— 确认这三个词条真能渲染出来，靠的是在 H5 上看见那三个 chip、
> 以及存量的「家」把第一个点亮。

### §6 那张清单少写了两处 —— 而且都是「不报错」的那种

原文写的是五处，实际是**七处**。补上的两处见 §6，共同点是**它们缺失时什么都不会响**：
一处让生成的 API 文档说反话，一处让骑手少拿到门牌。加列这件事的风险从来不在建表那一步。

### 三个「只改一半」的地方

**一、门牌号端上必填，后端刻意不必填。** 后端要着 `@NotBlank` 的话，
还没更新的老版本 App（它压根不发这个字段）连「改个手机号」都保存不了 ——
一个纯粹由这次改动造成的故障，而用户那边只看到「保存失败」。

**二、下单快照要把门牌拼进去**（`UserQueryPortImpl.receiverOf`）。
加了一列只改写入、忘了读出，是这类改动最容易漏的一半：
不报错、不崩、地址簿页面一切正常 —— 只有骑手拿到的地址少了最后 50 米。

**三、地址主体只在能选点的端上只读。** 它是跟坐标一起来的，在表单里随手改几个字
坐标不会跟着动，于是「文字写着 A、坐标指着 B」。但 H5 一条选点路都没有，
一律只读的话他连存量地址都改不了 —— 与 §4.2 那个 `canPick` 是同一个判断，共用一处。

### 置灰的口径必须与后端一字不差

`MerchantCapability` 补了 `deliveryLatE6 / deliveryLngE6 / deliveryRadiusM`
（§9-4 问的就是这个，已定）。判定走 `packages/shared/src/utils/geo.ts` 的
`withinDeliveryRange`，**与后端 `requireWithinDeliveryRadius` 逐条对齐，包括三条放行**：
地址没坐标 / 门店没标点 / 半径 ≤ 0。

端上比后端**严**的后果比不判更糟：本来下得成的单被挡在门外，
而用户永远查不出为什么 —— 所以这三条放行是守卫里的 ★★★。
距离算法也要一样（经度间距乘 `cos(midLat)`）：不乘的话北纬 60 度会多算一倍，
那正好是「送得到」与「送不到」的分界。

### 顺手修了一个卡着两条闸门的生成器

`backend/scripts/gen-test-schema.py` 撞上 `SELECT 1;` 就 `SystemExit` ——
而 V318 是一条**纯注记迁移**（它存在只是为了给 V315 留一句「已应用的迁移是冻结的」），
Flyway 要求文件里有条能跑的语句，于是 body 就是 `SELECT 1;`。

后果是两条：`check-generated-docs` 恒红，以及**测试库 schema 加不了新列**
（我的后端测试一开始四条全红，报的是 `10500`）。

判据刻意收得很紧：**不带 `FROM`、且选的是字面量**才跳过。
一律按前缀 `select` 放过的话，`INSERT … SELECT` 那类真回填也会被静默丢掉 ——
那正是这个脚本开头写着「不认识的语句必须炸」要防的事。

修好之后 `check-generated-docs` 第一次真正跑起来，报出四个过期产物。
三个是我的（`openapi-b.yaml` 因为 `MerchantCapability` 是三端共享的、
`C端功能点` 因为新页面用了 `nearbyCommunities`、`ui-lib.json` 的计数）。
**`数据库表清单.md` 里 `ord_sub_order` 49→51 那一行不是我的** ——
是 V317（佣金归属快照）加的两列，V318 紧接着把生成器搞哑了，所以一直没人发现。
产物只能整份重生成，所以那一行跟着一起提交了。
