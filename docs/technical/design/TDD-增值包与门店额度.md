## 一、一句话

门店额度现在读的是一个**全局配置** `shop.store.max-per-entity`（默认 1）——
「这个商家能开几家店」对所有商家是同一个数，运营调一次影响所有人。
本文把它换成**按主体的订阅档位**，并落地 P-11.2 的运营端能力。

**一期只做「有没有增值包」这个开关 + 降级规则**，不做自动续费与账单（需求 §2.3 原话）。

### 1.1 对上游方案的三处更正

| # | 上游写的 | 更正为 | 为什么 |
|---|---|---|---|
| **1** | 表名 `usr_merchant_plan` | **`mch_entity_plan`** | 那份方案写于 2026-08-09，**早于 V44 的表改名**。`usr_*` 现在只留给消费者域（`usr_account`/`usr_address`/`usr_identity`/`usr_store_favorite`），商家域一律 `mch_*`；关联表形如 `mch_entity_apply` / `mch_entity_community`。照原名建表会造出这个域里唯一一张 `usr_` 开头的商家表 |
| 2 | 「其余按建店时间**倒序**」（哪几家变只读） | 表述改为**保留集**：默认店 + 建店最早的若干家，补满免费额度；其余转只读 | 原话描述的是「变只读的顺序」，读的人容易反过来理解成「保留最新的」。改成正面描述保留集，并写死默认店必在其中 |
| 3 | 档位定义表 `sys_merchant_plan_def` | 沿用不改 | `sys_*` 是平台配置的既有前缀（`sys_industry`/`sys_pay_channel`/`sys_function_point`），这一条是对的 |

## 二、为什么是这个方案

### 2.1 收费模型（需求 §五 Q1，已拍板 A）

| 方案 | 结论 |
|---|---|
| **A 增值包订阅**（采用） | 卖的是**持续提供的服务**（统一管理 + 跨店数据 + 子账号）。一次性买断一个持续成本的服务是平台亏 |
| B 一次性开通费 | ❌ 需求 §2.3 已记录这次改判：当初以为卖的是「开店权限」，明确之后不成立 |
| C 按门店数阶梯 | ❌ 与 A 等价，但让商家每开一店都要重新决策，而开店那一刻他最不确定 |

**欠费按降级处理，不是关店** —— 关店伤的是消费者（下了单提不了货），
而欠费是商家与平台之间的事。这条直接决定了 §4.3 的状态机与 §4.5 的降级规则。

### 2.2 额度存快照，不实时查档位定义（最容易做错的一条）

运营下调 PRO 的门店额度时，**已经订阅的人不该被追溯**。
所以 `mch_entity_plan` 上存 `store_quota`/`staff_quota` 的**快照**，
`sys_merchant_plan_def` 只在**新订阅 / 续费 / 升档**时被读一次。

**防住什么**：不存快照的话，运营把 PRO 从 3 店调成 2 店，
所有现存 PRO 商家的第 3 家店当场变成只读 —— 而他们什么都没做。

### 2.3 单商家额度覆盖为什么必须有（P-11.2.4）

谈下来的连锁客户不走自助付费。没有覆盖字段，销售只能去改档位定义，
而那会影响所有同档商家 —— 正是 §2.2 要防的事。

## 三、结构

```
sys_merchant_plan_def   档位定义（FREE/PRO/CHAIN 的额度与能力位）· 运营可调 · 改了只影响新订阅
        ↓ 新订阅 / 续费 / 升档时读一次，写成快照
mch_entity_plan         主体的当前订阅：档位 + **额度快照** + 状态 + 到期 + granted_by + trial_used
        ↓ 读
StoreAdminService.create()      建店时校验额度（原先读全局配置）
BizStaffService.invite()        加子账号时校验额度
跨店总览 / 对比                  校验能力位
        ↑ 定时任务推进
ACTIVE → GRACE(7天) → EXPIRED（降级）
```

## 四、详细设计

### 4.1 具体档位内容

| | **FREE 孵化** | **PRO 成长** | **CHAIN 连锁** |
|---|---|---|---|
| 门店额度 | **1** | **3** | **10** |
| 子账号额度 | **0** | **3** | **15** |
| 跨店总览（按店并列今日订单/销售额/待办） | — | ✅ | ✅ |
| 跨店对比（销售额/订单数/复购率/评分/缺货） | — | ✅ | ✅ |
| 单店经营全套（商品·订单·履约·结算·数据） | ✅ | ✅ | ✅ |
| 零佣金（自带客流） | ✅ | ✅ | ✅ |
| 试用 | — | 14 天，一主体一次 | 14 天，一主体一次 |

**这张表里真正卖钱的只有两行**：跨店总览与跨店对比。
其余都是「他本来就有的」——需求 §2.1 说得很直白：**卖的不是「允许你开第二家店」**
（那个他开两个主体就能有，只是麻烦），**是「一个手机管完，并且能横着比」**。
两个主体的数据在两个账号里，跨店对比**做不到**——不是麻烦，是不可能。

#### 4.1.1 永远留在免费档的（硬约束）

需求「一条硬约束」原话：**现在免费的一切永远留在免费档，零佣金对所有档位一视同仁。**

| 免费档就有 | 为什么不能挪进付费 |
|---|---|
| 单店的商品/订单/履约/售后/评价/营销/结算/数据 | 把它挪走 = 向已经在用的人收过路费。这是最快毁掉「免费孵化」这层关系的做法 |
| 零佣金（自带客流） | **费率不做成档位差异** —— 那等于回到抽佣，只是换了个名字（上游方案否决的方案 F） |
| 店铺码、分享素材、门店主页 | 它们是获客路径（ADR-004），收费等于向平台自己的增长收费 |

#### 4.1.2 三档为什么是 1 / 3 / 10

| 档 | 对应的真实状态 | 额度依据 |
|---|---|---|
| FREE | 一店一人几十个老客 | **1** —— 与单店时代逐字相同，存量商家零感知 |
| PRO | 要请人、想开第二家 | **3** —— 「第二家」是决策点，给 3 留出「再开一家」的余量而不必立刻升档 |
| CHAIN | 多店多人、要数据做决策 | **10** —— 超过 10 家的连锁不走自助付费（走 P-11.2.4 单商家额度覆盖） |

**子账号 FREE 给 0 而不是 1**：一个人的店不需要子账号，老板自己就是那个账号。
给 1 会让「子账号」这个能力在免费档形同虚设（他会疑惑为什么只能加一个），
不如不给 —— 需要第二个人的时候，正是他该升档的时候。

### 4.2 数据库设计

#### 4.2.1 新增两张表

```sql
-- 档位定义：平台配置，运营可调不发版（与 sys_industry / sys_pay_channel 同构，ADR-010）
CREATE TABLE sys_merchant_plan_def (
    id                BIGINT       NOT NULL AUTO_INCREMENT,
    plan_code         VARCHAR(16)  NOT NULL COMMENT 'FREE / PRO / CHAIN',
    name              VARCHAR(64)  NOT NULL,
    store_quota       INT          NOT NULL DEFAULT 1 COMMENT '门店额度',
    staff_quota       INT          NOT NULL DEFAULT 0 COMMENT '子账号额度',
    -- 能力位。一期只有这一个 —— 它就是这个包卖的东西本身（B-11.12.5/6）
    cross_store_stats TINYINT      NOT NULL DEFAULT 0 COMMENT '1=有跨店总览与对比',
    trial_days        INT          NOT NULL DEFAULT 0 COMMENT '试用天数，0=不可试用',
    -- 停售某一档：只影响**新订阅**，已订阅的人照常用到到期
    enabled           TINYINT      NOT NULL DEFAULT 1,
    sort              INT          NOT NULL DEFAULT 0,
    tenant_no         VARCHAR(32)  NOT NULL DEFAULT 'MAIN',
    created_at        DATETIME     NOT NULL,
    created_by        VARCHAR(64)           DEFAULT NULL,
    updated_at        DATETIME     NOT NULL,
    updated_by        VARCHAR(64)           DEFAULT NULL,
    version           BIGINT       NOT NULL DEFAULT 0,
    deleted           TINYINT      NOT NULL DEFAULT 0,
    PRIMARY KEY (id),
    UNIQUE KEY uk_plan_code (plan_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='增值包档位定义';

-- 主体的订阅实例：一主体一行
CREATE TABLE mch_entity_plan (
    id             BIGINT       NOT NULL AUTO_INCREMENT,
    entity_no      VARCHAR(64)  NOT NULL,
    plan_code      VARCHAR(16)  NOT NULL DEFAULT 'FREE',
    /*
     * 额度**快照**，不是每次查档位定义。
     * 运营下调 PRO 的门店额度时，已经开了 3 家店的存量商家不该突然有一家变只读 ——
     * 快照让「改档位定义」只影响之后新订阅的人。这是老用户保护，不是冗余。
     */
    store_quota    INT          NOT NULL DEFAULT 1,
    staff_quota    INT          NOT NULL DEFAULT 0,
    cross_store_stats TINYINT   NOT NULL DEFAULT 0,
    -- 单商家额度覆盖（P-11.2.4）：谈下来的连锁客户不走自助付费。
    -- NULL = 用快照。**不写进 store_quota** —— 混在一起就分不清「这个数是档位给的还是单独谈的」
    store_quota_override INT             DEFAULT NULL,
    staff_quota_override INT             DEFAULT NULL,
    status         VARCHAR(16)  NOT NULL DEFAULT 'ACTIVE' COMMENT 'ACTIVE / GRACE / EXPIRED',
    start_at       BIGINT                DEFAULT NULL,
    expire_at      BIGINT                DEFAULT NULL COMMENT 'FREE 无到期',
    -- 催收要靠它区分「自助付费的该催」与「平台赠送的别催」；一期没有付款单，推断不出来
    granted_by     VARCHAR(16)  NOT NULL DEFAULT 'SELF_PAID' COMMENT 'SELF_PAID / PLATFORM / TRIAL',
    trial_used     TINYINT      NOT NULL DEFAULT 0 COMMENT '一主体一次',
    -- 降级执行到哪一步。重跑到期任务时靠它幂等，不重复把门店压成只读
    downgraded_at  BIGINT                DEFAULT NULL,
    tenant_no      VARCHAR(32)  NOT NULL DEFAULT 'MAIN',
    created_at     DATETIME     NOT NULL,
    created_by     VARCHAR(64)           DEFAULT NULL,
    updated_at     DATETIME     NOT NULL,
    updated_by     VARCHAR(64)           DEFAULT NULL,
    version        BIGINT       NOT NULL DEFAULT 0,
    deleted        TINYINT      NOT NULL DEFAULT 0,
    PRIMARY KEY (id),
    UNIQUE KEY uk_entity_plan (entity_no),
    KEY idx_plan_expire (status, expire_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='主体的增值包订阅';
```

#### 4.2.3 对既有表的触点

| 表 | 变更 | 说明 |
|---|---|---|
| `mch_store` | **加一列 `plan_suspended`** | 状态仍复用 `READONLY`（不新增状态值，T2），但**必须能区分「降级压下的」与「商家自己停用的」**——否则补缴恢复时不知道该回哪几家。详见 §4.6.2。列名与既有先例 `prd_store_goods.platform_suspended` 同构 |
| `mch_account` | **不加列** | 子账号停用同理，复用既有停用态 |
| 配置 `shop.store.max-per-entity` | **保留但降级为兜底** | `mch_entity_plan` 无行时才用它。一次性删掉会让「表还没回填的主体」建不了店 |

### 4.3 运营端交互（ops-web）

**落点：`/merchants` 加一个 `plans` tab**，不另起一级菜单。
理由与门店档案同一条：Plan 是**商家治理**的一部分（谁能开几家店），
运营的动线是「找到这家商家 → 看他的订阅 → 授予/延长」，
另起菜单会让他在两个页面之间来回跳。

| tab 内的区块 | 对应 | 交互 |
|---|---|---|
| **到期与降级看板**（默认视图） | P-11.2.5 | 三个筛选：`7 天内到期` / `GRACE 中` / `已降级`。列：商家名、档位、状态、到期日、门店数/额度、**降级后掉了多少单**（判断定价合不合理的依据） |
| **授予/延长** | P-11.2.2 | 行内按钮 → 抽屉：选档位 + 选时长（1/3/12 月）+ **必填原因**。`granted_by=PLATFORM`，critical 留痕 |
| **单商家额度覆盖** | P-11.2.4 | 同一抽屉的第二段：门店/子账号额度覆盖，留空 = 用档位快照。**要显示「档位给的是 3，你要覆盖成几」**，不能只有一个空输入框 |
| **升档信号** | P-11.2.6 | 独立列表：同手机号/同联系人开了两个主体的商家。**这是销售最该打的电话** |
| **档位定义** | P-11.2.3 | 超管才可写。保存时**必须弹二次确认**并写明「只影响之后新订阅的人，已订阅的 N 家不受影响」—— 不说这句，改的人会以为自己刚刚动了全部存量 |

**运营端不做的**：不代商家付款、不做账单、不做退款。一期没有这些链路。

### 4.4 B 端交互（b-app）

#### 4.4.1 入口：「我的」加一个 cell

`me` 页现有 cell 是 店铺/员工/结算/数据/消息/外观/帮助。
加一条 **「我的套餐」**，副标题直接显示当前档位与额度：`成长版 · 门店 2/3`。

**副标题必须带数字**：只写「成长版」的话，商家要点进去才知道还能开几家 ——
而他打开这一页的原因九成就是这个问题。

#### 4.4.2 套餐页（新 `plan` 页）

| 区块 | 内容 |
|---|---|
| 当前档位 | 档位名 + 状态徽标（试用中 / 生效中 / **宽限期** / 已降级）+ 到期日 |
| 用量 | `门店 2/3`、`子账号 1/3`，**用完时标红并给出路** |
| 档位对比 | 三档并列（§4.1 那张表）。**当前档高亮**，可升档的给按钮 |
| 升档/试用 | 一期**不接支付**：按钮走「联系平台」（客服会话/电话），并说明「开通由平台协助完成」 |

**为什么一期不接支付还要做这一页**：商家看不到自己有什么、还差什么，
就不会产生升档意图。需求 §3.2.1 对分享激励说过同一句话——
「看不到效果的激励等于没有激励」，套餐同理。

#### 4.4.3 建店被额度挡住时（最关键的一处交互）

现在 `stores` 页只有一句静态提示「当前套餐有门店数量上限，超出会被拒绝」。
改成**当场可行动**：

```
建店失败 →  你的成长版可开 3 家，已开 3 家
            ├─ [查看套餐]     → plan 页
            └─ [停用一家旧店] → 回列表
```

需求 §「主动点了新建门店但被额度挡住」写着：**这是意图最明确的一次，
当场给试用，不要只弹一个「额度不足」**。所以 FREE 且未试用过的商家，
这里直接给「免费试用 14 天」按钮。

后端错误码复用 `STORE_QUOTA_EXCEEDED`（70020），文案参数带三个数：
**现在几家、上限几家、怎么解决**。只回「额度不足」，商家的下一步是打客服电话。

#### 4.4.4 降级之后商家看到什么（这一段决定投诉量）

降级不是弹窗一次就完了，**状态要长期可见**：

| 位置 | 显示 |
|---|---|
| `me` 页那个 cell | 副标题变成 `已降级 · 门店 1/1`，**带警示色** |
| `plan` 页顶部 | 一条横幅：哪天降的、**哪几家店变成了只读**、怎么恢复 |
| `stores` 列表 | 只读的店打标签「套餐已到期 · 只读」，**与商家自己停用的标签区分开** —— 两者都是不接新单，但原因和解法完全不同 |
| 只读店的操作区 | 上架/改价按钮消失；**核销与订单入口保留** —— 未完成的单照常核销（§4.7） |

> **「未完成的单照常核销」在界面上也要成立**：只读店的核销台不能一起灰掉。
> 欠费当天还有几十个待取货订单，把它们冻住受损的是买家和取货点，
> 而他们与这笔欠费无关。

### 4.5 状态机与生效时机

```
        ┌──── 试用 14 天（一主体一次，trial_used 锁死）
FREE ───┴──→ PRO/CHAIN ──到期──→ GRACE(7天，能力全保留) ──→ EXPIRED(降级)
                 ↑                                              │
                 └────────────── 补缴，配置原样恢复 ←────────────┘
```

| 迁移 | 何时生效 | 为什么 |
|---|---|---|
| **升档** | **立即** | 他现在就要开第四家店 |
| **降档 / 退订** | **到期时**，不立即 | 已付的周期不退，但也不能立刻收走他买过的东西 |
| 到期 | 进 GRACE 7 天，**能力全部保留** | 扣款失败、老板出差、忘了续 —— 九成与经营无关，不该当天影响生意 |
| GRACE 结束 | 降级到 FREE（§4.7） | |
| 补缴 | **立即恢复，配置原样** | 不需要重新建店、重新授权 |

**GRACE 是这套机制里最该有的一格**：没有它，一次扣款失败就是一次营业事故。

### 4.6 额度校验：写入口一律先问，读不受限

| 动作 | 校验 |
|---|---|
| 建门店 | `已有 ACTIVE 门店数 < 有效额度` |
| 加子账号 | `已有 ACTIVE 子账号数 < 有效额度` |
| 跨店总览 / 对比 | 档位有该能力位（`canCrossStoreStats`）。**没有就明确拒绝**：`PLAN_CAPABILITY_REQUIRED`(70023)，文案带当前档位 —— 返回空数据等于把「你还没买这个」说成「它坏了」 |

有效额度 = `quota_override` 优先，否则 `store_quota` 快照。

**超额的错误必须说清三件事：现在几家、上限几家、怎么解决。**
只回一个「额度不足」，商家的下一步是打客服电话。
复用既有 `STORE_QUOTA_EXCEEDED`（70020），把三个数填进文案参数。

#### 4.6.1 并发建店必须锁住计划行

「数一下现在几家 → 小于额度就建」这个写法在两个请求同时进来时会**双双通过** ——
FREE 额度 1 的商家能开出两家店，而两次请求各自看都是合法的。

做法：建店/加子账号的事务**开头先锁 `mch_entity_plan` 那一行**
（`SELECT ... FOR UPDATE`，或用 `BaseEntity.@Version` 乐观锁重试一次）。
竞争只发生在同一主体内部，代价可以忽略。

**防住什么**：额度是这个包卖的东西本身。它能被并发绕开，等于付费档和免费档没区别 ——
而且不报错，只有对账时才看得出某个 FREE 商家有两家店。

#### 4.6.2 什么算占用额度：`plan_suspended` 这一列为什么必须有

额度只数 **ACTIVE** 的门店 —— 商家自己停掉一家再开一家是合理的。
但这带来一个恢复期的歧义，**不解决就会在补缴那天出错**：

```
PRO(3 家) → 欠费降级 → 保 1 家，压 2 家为 READONLY
                       商家又自己停掉了保留的那家（比如装修）
           → 补缴恢复 → 该让哪几家回来？
```

只看 `status=READONLY` 是分不出来的：三家店的状态一模一样，
而**其中一家是商家自己的决定，两家是平台压的**。
全部恢复 = 平台替商家做了一次开店决定；全部不恢复 = 他买的东西没还给他。

所以 `mch_store` 加一列 `plan_suspended TINYINT`：

| 场景 | `status` | `plan_suspended` | 恢复时 |
|---|---|---|---|
| 商家自己停用 | READONLY | 0 | **不动** |
| 降级压下 | READONLY | **1** | 恢复为 ACTIVE 并清零 |
| 平台强制下线 | SUSPENDED | 0 | 与本机制无关（走违规处置解除） |

**这与 `prd_store_goods.platform_suspended` 是同一个形状**（V98 加的）：
凡是「系统压下去、以后要按原样还回来」的地方，都必须留一个标记说明是谁压的 ——
否则恢复那一步只能靠猜。

#### 4.6.3 P1 实施记录（2026-08-14）：三处被实测推翻

| # | 原设计 | 实测结果 | 改成 |
|---|---|---|---|
| 1 | 「建店前数一下、再调额度闸」 | **锁形同虚设**：两个并发请求各自拿着**加锁前的旧计数**通过，双双建店成功 | 额度闸的入参从「数了多少」改成**「怎么数」**（`IntSupplier`）——「先锁、再数」的顺序由闸自己保证，调用方写不错 |
| 2 | 迁移回填就够了 | **新入驻的商家没有订阅行**：回填只覆盖迁移那一刻的存量，之后入驻的一路落到配置兜底（测试环境那个兜底是 3，于是新商家能开三家店，而他明明是 FREE） | 主体激活时建 FREE 行（`ensureFreePlan`），**与 `ensureDefaultStore` 是同一类动作** |
| 3 | 额度数「全部门店」（沿用旧代码） | —— | 改成**只数 ACTIVE**。对存量是零行为变化：默认店不能停用，而单店商家的唯一一家就是默认店，所以他的 ACTIVE 数恒等于总数 |

**第 2 条值得单独记**：`ensureDefaultStore` 早就存在，而我加订阅行时只想到了迁移回填 ——
「主体一激活就该有的东西」是一类，不是一个。下次再加这类行（结算配置、通知偏好…），
先去 `activate()` 那里看一眼已经有哪些兄弟。

#### 4.6.4 子账号额度闸：**P1 刻意不接**

服务层的 `requireStaffQuota` 已实现并可用，但**没有接进 `/biz/staff` 的写路径**。

理由：FREE 的子账号额度是 0，而现在没有任何闸 —— 存量商家今天能加员工。
此刻装闸有两个问题：① 违反 P1「零行为变化」的验收标准；
② **商家会撞上一个没有去处的错误** —— 套餐页要到 P4 才有，他看到「子账号额度不足」
却没有任何地方能看到自己是什么档、怎么升。

接它的时机是 P4（与套餐页同批），届时还要决定存量商家怎么处理
（建议按现有员工数 grandfather，不剥夺任何人已有的东西）。

### 4.7 降级：降的是能力，不是生意

**到期 ≠ 关店。**

| 对象 | 降级后 |
|---|---|
| 超出额度的门店 | 置 `READONLY`：C 端**不接新单**，但历史订单可查、**未完成的单照常核销** |
| **保留哪几家** | **默认店 + 建店最早的若干家**，补满免费额度；其余转只读。规则写死 —— 不让商家选，也不让系统猜 |
| 子账号 | 全部停用；主账号照常登录 |
| 跨店总览与对比 | 隐藏 |
| 门店与授权配置 | **保留**，补缴后原样恢复 |
| 数据 | 不删。降级只改「能看多久」，不改「存不存」 |

> **「未完成的单照常核销」是这条设计里最重要的一句**：欠费当天还有几十个待取货订单，
> 把它们一起冻住，受损的是买家和取货点 —— 而他们与这笔欠费无关。

**降级前的提醒**：到期前 7 天、前 1 天各一次；降级当天再一次，
**并写明哪几家店变成了只读**。只说「您的套餐已到期」，商家要自己去猜发生了什么。

> ⚠️ 提醒依赖商家侧触达。当前 ops→商家**没有推送链路**（见
> [TDD-运营端门店与商品治理](./TDD-运营端门店与商品治理.md) D4），
> 一期按**拉取式**做：状态与「哪几家变只读」落在数据行上，B 端打开即见。
> 主动推送等消息域的商家维度改造，见 §六 Q3。

#### 4.7.1 升档 / 续费 / 补缴：快照怎么刷新

四种迁移对**额度快照**的处理不同，写死在这里免得实现时各猜一套：

| 动作 | `plan_code` | 额度快照 | `expire_at` | `trial_used` |
|---|---|---|---|---|
| **升档**（FREE→PRO、PRO→CHAIN） | 换新档 | **重读 `plan_def` 写入新快照** | 从当下起算新周期 | 不变 |
| **续费**（同档延长） | 不变 | **重读并刷新** —— 续费等于一次新订阅 | 在原到期日上顺延 | 不变 |
| **补缴**（GRACE/EXPIRED → ACTIVE） | 不变 | **不动**，用原快照 | 顺延 | 不变 |
| **降档 / 退订** | 到期时才换 | 到期时才重读 | 到期日不动 | 不变 |

**补缴不刷新快照**是关键的一条：他买的是当初那个额度，
中途运营下调了档位定义不该殃及他（§2.2 的同一条理由）。
而**续费要刷新** —— 那是一次新的购买行为，按当下的档位定义成交。

> `trial_used` 一旦置 1 **永不回退**，包括退订后重新订阅。
> 否则「订阅→退订→再试用」就是一个可以无限循环的免费通道。
