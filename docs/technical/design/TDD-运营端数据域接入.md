## 一、一句话

`sys_ops_staff` 上的数据域（`merchant_no` / `community_no` / `pickup_no`）
**存了但没人读**：它能算出真实的 `DataScopeSpec` 并签进 `LoginUser`，
而现存每一条 ops 查询都 `executeWithoutScope` 主动绕开了它。
结果是——**给客服配了「只看城西片区」，他照样能看到全平台的单**。

## 二、为什么现在才做，以及为什么不能只做一半

### 2.1 顺序不能反

[三端对齐清单](../../requirements/三端角色权限功能对齐清单.md) §九结论 4 说的是权限对齐与功能补齐的顺序，
数据域这一层同理：**在各域能力落地之前接数据域，等于给一批还不存在的查询定过滤规则**。
所以本文排在履约/风控/增长/财务四域补齐之后。

### 2.2 为什么不能「只给新端点接」

这是本轮最需要写下来的一条。若只给新做的门店/商品端点接数据域，会得到：

> 客服打开订单检索——全平台的单；点进门店档案——只有自己片区的店。

**同一个人在同一个后台里看到两套可见性**，而没有任何提示告诉他为什么。
他会把其中一个当成故障报上来，而两个都是"按设计工作"。

所以要么整体接，要么整体不接。这也是 [TDD-运营端门店与商品治理](./TDD-运营端门店与商品治理.md) §5 T1
当时决定「本批沿用现状」的理由。

### 2.3 两条路的选型

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. 注册进 `DataScopeRegistration`，去掉 ops 查询的 `executeWithoutScope`** | SQL 层自动追加条件，业务代码零 where | 一处生效、漏不掉；与 C/B 端同一套机制 | **fail-closed**：已注册的表若在当前会话维度上找不到锚点列，handler 生成 `1=0`。运营会话没有 SELF 维度，一旦注册了却没登记 OPS 相关维度，**该表对运营全瞎** | ⚠️ 见 §2.4 |
| B. Service 层按 `SecurityUtils` 拿 scope 显式过滤 | 改动可控、可逐个端点灰度 | 58 个文件里散落 `executeWithoutScope`，逐处加判断**必然漏**；漏了不报错，就是越权 | ❌ |
| **C. A + 一条守卫**（采用） | 注册表 + 「ops 查询要么接了数据域、要么显式登记豁免」的结构性测试 | 把「漏一处」从静默变成测试红 | 要先写守卫再改代码（照抄 B 端①的手法） | ✅ |

### 2.4 A 的 fail-closed 陷阱必须正面处理

类注释里那条教训写得很清楚：「订单表登记了 MERCHANT 却漏了 SELF，
C 端『我的订单』立刻空列表」。运营端接入会重演同一形状——
**运营会话的维度是 MERCHANT/COMMUNITY/PICKUP，而 `mch_store`、`mch_entity`、
`prd_store_stock`、`prd_store_goods` 目前一张都没注册**。

所以本方案的核心不是"注册几张表"，而是**为运营会话补齐每张被注册表的维度锚点**，
并让守卫替人检查这件事。

## 三、结构

```
sys_ops_staff(merchant_no/community_no/pickup_no)   ← 已有（V60），运营配置
        ↓ StaffIdentityResolver.scopeOf()            ← 已有，每请求现算
   DataScopeSpec 签进 LoginUser                       ← 已有
        ↓
   ❌ 断在这里：每条 ops 查询都 executeWithoutScope
        ↓ 本次要接上
   DataScopeHandler 在 SQL 层追加条件（按注册表）
```

| 要动的地方 | 内容 |
|---|---|
| `DataScopeRegistration` | 补注册运营端会读的表，并**为每张表登记 MERCHANT/COMMUNITY/PICKUP 三个维度的锚点列**（缺哪个补哪个，缺列的先加冗余列） |
| 各 ops Service | 去掉查询路径上的 `executeWithoutScope`（**写路径保留**，见 §5 T2） |
| 新守卫 | ops 查询未接数据域时测试红（§4.2） |

## 四、详细设计

### 4.1 分批次，每批可独立发布

| 批 | 表 | 为什么这个顺序 |
|---|---|---|
| ① | `ord_sub_order`（已注册，只需去掉 ops 侧的 withoutScope） | 客服的第一入口，收益最大；且它三个维度锚点都已登记 |
| ② | `mch_entity` / `mch_store` | 需**新增注册**；`mch_store` 无 community 锚点，要么补冗余列，要么只登记 MERCHANT 维度并接受 COMMUNITY 域运营看不到门店（拍板项 Q1） |
| ③ | `prd_goods`（已注册 MERCHANT）/ `prd_store_goods` / `prd_store_stock` | 商品池按商家域裁剪 |
| ④ | 其余（结算、履约、内容…） | 按域收尾 |

**每批之后做一次角色走查**（§4.3），不是全做完再走查。

### 4.2 守卫（先写让它红，再逐个变绿）

照抄 B 端①验证有效的手法（[三端对齐清单](../../requirements/三端角色权限功能对齐清单.md) §10.1）：

| 守卫 | 判什么 |
|---|---|
| G1 | 每个 ops 查询端点，要么其 Service 路径不含 `executeWithoutScope`，要么在**豁免登记表**里有一条带理由的记录 |
| G2 | 豁免登记表里不能有死条目（端点已删/已接入却还登记着） |
| G3 | 每张已注册的表，运营会话可能用到的三个维度**锚点列都存在**（防 §2.4 的 fail-closed） |

> G3 是最关键的一条：G1/G2 全绿时，一张注册了但缺锚点的表仍然会让运营**整页空白**，
> 而那看起来像「这个片区没有数据」，不像故障。

### 4.3 六角色走查（不能省）

结构性守卫看不见「渲染成空白」这类问题——B 端①b 的教训就是这么来的：
后端每一条判断都对、守卫全绿，而三个角色打不开为他们设计的页面，**且不报错**。

走查矩阵：4 个已实现角色 × 配了数据域 / 没配数据域 两种，逐页记录看到什么。

### 6.1 实施记录：Q1 的前提不成立（2026-08-14）

批① 落地后开始做批②，在写迁移之前先去找「门店的社区从哪来」，结论是**没有来源**：

| 想过的来源 | 为什么不行 |
|---|---|
| `mch_store` 上现成的列 | 只有 `entity_no` / `store_no` / `address`（自由文本），没有社区 |
| 建店时填 | 建店链路（`MerchantStoreServiceImpl`）根本不问社区，界面上也没有这个字段 |
| 从 `cmt_pickup_point` 反推 | **这条是通的但多值**：`owner_ref` 在 `type='STORE'` 时存的就是 `store_no`，而自提点带 `community_no`。可是一家店可以在多个社区各挂一个自提点 —— 种子数据里 `ST-M0001` 就同时挂着 PP0001(C0001) 与 PP0002(C0002) |
| 从商家的覆盖社区 `mch_apply.community_nos` 推 | 同样多值，且是**主体级**不是门店级 |

而 `DataScopeHandler` 的锚点**只能是本表上的单列**（`col IN (refs)`），表达不了多值关系。

所以按 Q1 加一列 `mch_store.community_no` 会得到：

- 挂了多个自提点的店，只能取其中一个社区 → **另一个社区的运营看不到这家店**
- 一个自提点都不挂的店（纯配送店，种子里的 `ST-M0002` 就是）→ 列为 NULL → **所有社区运营都看不到**

这正是 Q1 想避免的那个形状（空白看起来像「这个片区没有门店」），只是从「一张表全空」变成「列表里少了几家」——
**后者更难发现**：整页空白至少还有人会报上来，少几行不会。

**但真正的结论不在这三个选项里** —— 上面整段推理默认了「社区运营需要看门店档案」，
而那一条**没有人核过**：`COMMUNITY_OPS` 的 15 个权限码里一个 `merchant:*` 都没有，
`GET /ops/stores` 要的 `merchant:merchant:read` 它没有，**这个页面它打不开**。

所以正确做法是第四个选项：**`mch_store` / `mch_entity` 只登记 MERCHANT 锚点**
（`entity_no` 现成），COMMUNITY/PICKUP 两个维度登记为**豁免并写明理由**
（「没有任何持社区/自提点域的角色能读这张表」）。批② 按此完成，不加列。

> 这一条留作教训：**加一列冗余数据之前，先确认那个角色进不进得来**。
> 我（拍板的那一侧）跳过了这一步，代价是一个多值失真的列 + 一次回填。

以下三个选项**不采用**，留作记录 —— 若将来给社区运营开了门店档案，要回到这里重选：

1. **门店建档时必填社区**（一店一社区），把多值问题在业务上消掉 —— 需要 UI + 迁移期的存量回填口径
2. **加一张 `mch_store_community` 关联表**，并让 `DataScopeHandler` 支持「经关联表的锚点」——
   动的是 `neargo-common-data`，影响所有接入方
3. **接受 `mch_store` 不接数据域**，并在门店档案页显式写明「门店档案不按数据域裁剪」——
   与 §2.2「同一个人两套可见性」冲突，但至少是**说出来的**

第 3 条是当前的事实状态（批② 未做），差别只在于要不要把它写到界面上。

批③（商品）与批④（结算/履约）未开工，它们的现状登记在
`packages/shared/tests/ops-data-scope.test.ts` 的 `SCOPE_BYPASS_OK` 里，逐条带批次号。

### 6.2 批② 实施记录（2026-08-14）：fail-closed 陷阱当场兑现了两次

按 §6.1 修正后的方案落地：`mch_entity` / `mch_store` **只登记 MERCHANT 锚点**，
COMMUNITY/PICKUP 登记为带理由的豁免。主查询接数据域，装饰性取名不接。

**注册那一刻，54 个用例同时红** —— 全是 B 端与 C 端的，不是运营端的：

| 踩点 | 症状 | 为什么 |
|---|---|---|
| `BizIdentityResolverImpl` | 商家登录后作用域恒空，**整个 `/biz/**` 403** | 它是**身份解析本身**，跑在作用域建立之前；B 端会话带 SELF，而这两张表只有 MERCHANT 锚点 → `1=0` |
| `MerchantPortImpl` 的 7 个跨域查询 | 下单时商家名快照取不到 → 分拣汇总里商家名是空串 | 调用方各带各的维度（买家是 SELF），Port 是跨域服务，不该被调用方的维度裁剪 |

两处的修法都是**显式 `executeWithoutScope` 并写明理由**，不是回退注册。

> **这条教训比修复本身重要**：`DataScopeRegistration` 类注释第 2 条早就写着
> 「订单表登记了 MERCHANT 却漏了 SELF，C 端『我的订单』立刻空列表」——
> 我读过它、在 §2.4 里引用过它、然后**在同一个地方栽了两次**。
> 注册一张表的爆炸半径不是「读这张表的 ops 查询」，是**所有读这张表的代码**，
> 包括三个端与所有跨域 Port。下一批（③ 商品）动 `prd_goods` 时，
> C 端商品浏览与 B 端商品管理会是同样的形状 —— **先去数调用方，再改注册表**。

**读写必须分成两个方法**（T2 的落地）：`require`/`requireStore` 保持不接数据域（写路径用），
新增 `requireInScope`/`requireStoreInScope` 供读路径。**不用布尔参数区分** ——
参数化的话，下一个人在写路径上传错一次就把处置变成了静默失败。
