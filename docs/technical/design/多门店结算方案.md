# 多门店结算：按结算账户归组

> 2026-08-10 · 起因：多门店方案里 P4 卡在一个业务问题上——两家店分别结算还是合并结算。
> 业务已答：**资金按店统计；打款按结算账户；两种都要支持。**

---

## 1. 先把一个事实摆正

### 1.1 微信支付侧的硬约束

**一个商户号只能绑一个结算账户。** 结算账户是商户号的属性，可以走「修改结算账户」
变更，但同一时刻只有一个。所以「一个号挂两个账户」不成立。

要两个账户各收各的钱，只有一条正路：**服务商模式下同一主体进件多个特约商户号**
（`sub_mchid`），每个号各绑各的银行账户。连锁门店本来就是这么做的。

另一条路是**分账**（profitsharing）：一个号收款后按比例分给接收方。
但那是分钱不是分账户——接收方仍须是商户号，且有分账比例上限与回退期限制。
对「两家店各收各的」这个诉求，多商户号是正路，分账是绕路。

> 以上按微信支付一贯的模型写。**落地前要拿当时的官方文档核一遍**，
> 特别是同一主体可进件的特约商户号数量限制——这条会直接决定一个主体最多开几家
> 独立结算的店。

### 1.2 代码侧的现状（比之前记的更糟）

`docs/technical/多门店能力现状与方案.md` §3.4 写的是「收款分了，结算没分」。
**这句话给多了。收款也没分。**

`pay_merchant_no` 全库的消费方只有两个：

| 位置 | 干什么 |
|---|---|
| `StoreAdminServiceImpl.setPayment()` | 写进去 |
| `StoreVO.payMerchantNo` | 显示出来 |

支付与结算侧**零消费方**。最直接的证据是分账接口自己：

```java
Result split(String subOrderNo, long amountMinor, String requestNo);
```

**没有收款账户参数。** 通道不知道钱打给谁——今天能跑通只是因为所有商家都是单店、
只有一个号，收款方是通道实现里的隐含默认。

这与本轮反复撞到的是同一形状：**有能力没有消费方**
（营销活动建了没人读、`mch_store_role` 授权了没人用、`shbr_store_no` 存了没人读）。

### 1.3 `stl_bill` 不是周期账单

它是**按子订单一行**的分账流水（`sub_order_no` 唯一）。
这改变了问题的形状：「分开结算 vs 合并结算」不是要不要拆表，
而是**按什么把流水归组打款**。

---

## 2. 设计：三个维度各归各

这三件事今天全挤在 `entity_no` 上，必须拆开：

| 维度 | 键 | 回答的问题 | 谁决定 |
|---|---|---|---|
| **统计** | `store_no` | 这笔钱是**哪家店**挣的 | 系统（订单落在哪家店） |
| **结算** | `pay_merchant_no` | 这笔钱打给**哪个账户** | 商家（给门店配收款号） |
| **合规** | `entity_no` | 谁**开票、纳税、担责**，费率按谁算 | 营业执照 |

拆开之后，两种结算模式**自然涌现，不需要开关**：

```
两家店配同一个收款号  →  归成同一组  →  合并结算（一次打款）
两家店配不同收款号    →  归成两组    →  分开结算（各打各的）
```

### 2.1 为什么不存一个 `settleMode` 枚举

因为它会立刻和 `pay_merchant_no` 打架：商家给两家店配了不同的收款号，
却把开关设成「合并」——听谁的？

任何一种解释都是坏的：听开关的，那钱只能打进一个账户，另一个号收的钱出不去；
听配置的，那开关是个骗人的摆设。

**结算模式不是一个要存的字段，它是收款号配置的结果。**
配置本身已经把话说全了，再加一个开关只会制造矛盾。

### 2.2 统计与结算是两件事，不要互相绑架

「资金按店统计」和「打款按账户」不冲突，因为它们是不同的问题：

- 老板永远能看到「河坊街店这个月做了多少」——按 `store_no` 聚合，与打给谁无关
- 钱打给谁，按 `pay_merchant_no` 归组

单店时两个维度恒等，所以今天看不出区别——这也正是能分阶段做的原因。

## 3. 实施

### S1 · `stl_bill` 补两个字段，都是快照

```sql
ALTER TABLE stl_bill ADD COLUMN store_no VARCHAR(64) DEFAULT NULL;
ALTER TABLE stl_bill ADD COLUMN pay_merchant_no VARCHAR(64) DEFAULT NULL;
```

**为什么快照而不是每次 join 回去算**：与 `commission_rate` 落库同一个理由——
商家随时可以改门店的收款号（`payment_changed_at` 已经在记这个变更）。
若打款时才去查「这家店现在用哪个号」，**改号会把还没打的历史流水一起挪到新账户**。
钱已经进了旧账户，账却说打给新账户，对不上。

**为什么可空**：存量流水都是主体级的，不能强制填。读侧按「空 = 主体默认号」解释，
与 `mch_store.pay_merchant_no` 已有的口径一致。

### S2 · `SettleSource` 补 `storeNo`

来源是 `ord_sub_order.store_no`——**已实测 100% 填充**（44 单 / 0 空），
不需要先补数据。

### S3 · 收款号解析收成一个方法

```
门店的 pay_merchant_no  ??  主体的默认收款号
```

**必须只有一处实现。** 两处各写一遍的后果是可预测的：一处按新规则、一处按老规则，
症状是「钱打错账户」——而这类错误不会报错，只会在对账时被发现，还得人工追回。

### S4 · `SplitGateway` 加收款账户参数

```java
Result split(String subOrderNo, String payMerchantNo, long amountMinor, String requestNo);
```

**这是整件事真正的接口改动。** 在此之前，分账通道从来不知道钱打给谁。
Stub 实现记进日志即可，但参数必须现在就加上——否则 S4 接真通道那天，
「打给谁」会变成一个临时补的参数，而那时已经有真钱在跑了。

### S5 · 读侧分两条，别混

| 场景 | 按什么聚合 |
|---|---|
| 商家账单 / 打款单 | `pay_merchant_no` + 周期 |
| 门店经营报表 | `store_no` |
| 平台对账 / 发票 | `entity_no` |

### S6 · 守卫

1. 一张 `stl_bill` 解析出的收款号，**必须属于本主体**且状态可用
   （越权打款：把钱打进别人的账户，是这个模型里最坏的失败）
2. 同一子订单只能有一张 bill（已有，别丢）
3. 端上与后端对「空 = 用主体默认号」的解释一致——两边解释不同，
   症状是页面显示「未配置」而钱照打

---

## 4. 一个必须一起想清楚的：退款走哪个账户

**退款必须从当初收款的那个账户出。** 靠的就是 S1 落在 bill 上的
`pay_merchant_no` 快照——不是「现在这家店用哪个号」。

不这么做的后果：商家上个月改了门店收款号，这个月发生一笔上个月订单的退款，
钱从新账户扣——新账户里可能根本没有那么多余额，退款失败；
就算成功了，两个账户的账也各错一笔，且方向相反。

`reverse()` 同样要加账户参数，与 `split()` 一起改。

---

## 5. 顺序与风险

```
S1 加字段（可空，不动读侧）      ← 零风险，先落
S2 SettleSource 补 storeNo       ← 零风险
S3 收款号解析收成一处            ← 有行为变化，但单店时恒等
S4 SplitGateway 加参数           ← 接口改动，Stub 阶段做最便宜
S5 读侧分维度                    ← B 端与运营端一起改
S6 守卫                          ← 与 S3/S4 同批，别留到最后
```

**S4 现在做最便宜。** 现在是 Stub，改接口只是改签名；
等接了真通道再改，就是在有真钱流动的链路上动刀。

**每一批都要保证单店行为逐字不变**——所有真实商家都是单店，
任何一次多门店改造让单店行为变了，都是拿全量用户给一个还没人用的功能试错。
