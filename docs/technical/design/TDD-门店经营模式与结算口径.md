# TDD · 门店经营模式与结算口径

> 状态：**方案待确认** · 2026-09-20
> 起因：[TDD-门店经营类目](TDD-门店经营类目.md) §10 —— 修「自营免资质」时发现
> `mch_store.business_mode` 这一列**从来没有人写过第三方**，而结算口径读的正是它。
> 相关：ADR-011（经营范围在门店）、V23（建表与默认值）、V28（费率规则）、V329（`mch_entity.self_operated`）

---

## 1 事实

| 事实 | 证据 |
|---|---|
| `business_mode` 建表默认 `SELF_OPERATED` | `V23__self_operated_settle.sql` L16 |
| 入驻这条路不写它 | 全仓只有两处写：`SelfOperatedServiceImpl`（写 `SELF_OPERATED`）、`OpsStoreModeController` 的 `PUT /ops/stores/{storeNo}/business-mode`（运营手动改）。进件、开店、建分店都不写 |
| 结算按它分口径 | `SettleGenerationOrchestrator` L61 取 `merchants.businessModeOf(merchantNo, storeNo)` 落进 `stl_bill.business_mode` 快照；费率规则 `stl_fee_rule` 的唯一键含 `business_mode`（V28）—— 自营走毛利率、第三方走佣金率 |
| 解析不出时也回落自营 | `MerchantPortImpl.businessModeOf` L809，注释写明是**刻意的保守方向**（误判自营只多要一张进项票；误判第三方会去给一个不存在的账户下发分账）|

**于是：一家正常入驻的第三方商家，门店在库里是「自营」。**账单快照跟着是自营，
费率按自营口径算。没有任何地方会报错。

## 2 已经有的那一半

`GET /ops/merchants/mode-risk`（运营端）已经在报这个默认值造成的问题，但**只报一种**：
**无照主体 + 自营门店** —— 那是税前扣除的问题（`MerchantGovernServiceImpl.modeRiskStores`），
且刻意「只看不拦」，因为农产品供应商正走这条合规路径。

**没覆盖的是有照的第三方商家**：他们有执照、该走佣金率与分账，而库里是自营。
这一档不在风险清单里，也没有任何闸门。

## 3 要定的是什么

**不是「把默认值改掉」**。默认值改成第三方会让自营店与农户那条路当场断掉
（第三方模式要求门店有可用收款号，`setBusinessMode` 里就是硬前提）。
要定的是：**谁、在什么时候，把一家店标成第三方。**

三个候选：

| 方案 | 做法 | 代价 |
|---|---|---|
| A 入驻时定 | 进件审核通过那一步写 `business_mode`：主体自营→自营，其余→第三方 | 要求进件时收款号已就绪；否则第三方那条硬前提过不了。存量仍要人工处理 |
| B 收款号就绪时定 | 商家进件拿到收款号（`payMerchantNo` ACTIVE）那一刻，自动把该店切成第三方 | 时点自然、前提自带。但「自动改钱怎么走」要有留痕与告警 |
| C 只做清单，人来切 | 把风险清单扩成两档（无照+自营、有照+自营+有收款号），运营逐个切 | 最小改动，不碰任何自动行为；依赖运营执行 |

**建议 C + B 的前半**：先把清单补全（看得见），再在收款号就绪时**提示**而不是自动切。
理由是这一列决定钱怎么走 —— 自动切错的代价（钱进错账户、账单口径错）远大于人工确认的成本；
而 A 的时点太早，进件通过时收款号常常还没下来。

## 4 影响面（要先量出来再决定）

上线前先用清单量三个数，**不改数据**：
1. 有照主体 + 自营门店 + 有可用收款号 —— 本该是第三方的那一批，有多少家
2. 其中已经产生过账单的，按自营口径算出的费率与按佣金率的差额
3. 已结算的那部分能不能追溯（`stl_bill.business_mode` 是快照，改当前不动历史）

**存量账单不回改**：快照的意义就是「当时按什么算的」。差额怎么处理是财务的决定，不是本文能定的。

## 5 不做什么

- 不改 `business_mode` 的建表默认值
- 不回改历史账单，也不自动补差
- 不把「经营模式」与「主体是不是平台自营」合并 —— V329 已经把这三根轴分清楚了
  （`funds_mode` 钱先进谁的账户 / `business_mode` 谁是销售主体 / `self_operated` 是不是平台自己）

## 6 验证（方案定了之后）

- 清单扩档：造一家「有照 + 自营门店 + 有收款号」的商家，必须出现在清单里；
  无照那档照旧出现（回归）。**消融**：把新判据去掉，前一条必须变红
- 若采纳 B 的提示：收款号转 ACTIVE 时产生一条待办 / 告警，且不改库里的 `business_mode`
