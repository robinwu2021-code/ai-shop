#### M03-B 确定需要补齐的独立库存服务协议（拟新增，不是现有路由）

按新的独立服务`/api/inventory/v1`和既有client认证/owner绑定方式实现，不能让inventory-domain或inventory-api反向依赖shop-base/FOOD。商家Controller保持原有路径及权限；原内部合同作为商城兼容适配入口，不与独立服务绑定商城内部令牌实现。

| 拟新增独立服务API | 输入 | 输出 |
| --- | --- | --- |
| POST /api/inventory/v1/stock-projections/validate-mappings | 经认证来源、原scope、mappings[]（itemNo/baseUnit/可选目标引用） | MappingResult[] |
| POST /api/inventory/v1/stock-projections/activate | 原scope,generation,operationKey；owner/actor按已有可信身份绑定 | ACTIVE回执、generation、receiptNo |
| POST /api/inventory/v1/stock-projections/deactivate | 同上 | OFF回执及停用屏障 |
| POST /api/inventory/v1/stock-projections/apply | 原scope,generation,eventNo,payloadHash,snapshot | APPLIED/UNCHANGED/STALE或原冲突错误，appliedVersion/receiptNo |
| POST /api/inventory/v1/stock-projections/receipt | 原scope,eventNo,payloadHash | 明确found/receipt包装；超时不表示查无 |
| POST /api/inventory/v1/stock-projections/query | 原scope,itemNos | 快照列表，沿原数量/版本/状态合同 |
| GET /api/inventory/v1/stock-projections | 经授权来源/门店、page,size | 来源镜像分页 |
| GET /api/inventory/v1/stock-projections/{sourceItemNo} | 原物料号及来源门店范围 | 单项镜像及同步状态 |

这些是独立服务端新增合同，不是新增第二套商家操作API。原eventNo、generation、payloadHash、历史snapshot字段顺序及hash算法必须保持兼容；独立身份到原scope的映射由可信客户端/owner授权建立，不信任请求体的主体/门店声明。新入口第一期仅承接现有FOOD_LOCAL，不顺带承诺任意来源通用过账。

### M05 共享订单：补齐最终金额与分摊只读事实

**已知差距**：IndustryReportFactsPortAdapter当前提供订单创建/成交/完成数量及原应收、有效应收、调整、成交金额；不能据这些总额推导所有最终优惠、税、退款和行级分摊。

**先复用**：共享订单/改单/统一定价的最终冻结快照、IndustryOrderAllocationPolicy和原分配凭据；不重算已完成订单，不让报表调用当前促销配置重放历史价格。特别注意ord_checkout_line等既有表包含行业约束，不能仅因名字通用就将餐饮写进BEAUTY限定的表。

**接口调整**：优先扩展原CORE ORDER SourceSnapshot中的MetricFact，不新增重复经营REST。候选只读Service方法`readFinalFinancialFacts(scope,orderRefs,asOf)`（拟新增名称，编码前对齐现有Service落点）：输入可信范围、订单/行/调整引用及截至时间；输出order/subOrder/lineRef、finalSnapshotRef、allocationVersion、currency、gross/discount/netExTax/tax、退款原引用与金额、sourceVersion、coverage/unknownReason。它不接收前端上传的“最终价格”。

**数据库**：先逐项核对原冻结快照是否持久保存上述事实。仅当缺少不可变行级分配时启用候选DB-C1，不默认修改所有订单行或事后回填0。

**代码**：扩展shop-core的IndustryReportFactsPortAdapter.readSnapshot、原IndustryOrderAllocationPolicy使用处及行业订单/改单相关Mapper；必要时扩展原确认/改单事务保存最终事实。shop-base继续复用ReportContracts.SourceSnapshot/MetricFact；若确需新增金融事实DTO则放共享订单合同而非food-api。ReportSourceCollectionServiceImpl仅收集事实，不承担分摊计算。

**验收**：一笔订单最终行分摊之和=原确认总额；折扣/优惠券/税内含与外加、抹零、改单、部分退餐可追溯到原分配；跨币种不相加；缺历史原始凭据的订单输出PARTIAL/UNKNOWN。退款申请不计作实际退款成功。
