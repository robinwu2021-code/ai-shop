- 仅MySQL 9；本地3308，云端按已有配置；不再支持或验收MariaDB。旧迁移文件及checksum冻结，新增迁移执行时选各库下一实际可用版本，不在本计划预占版本号。

## L2. 各模块具体实施

### M01 营业链路与历史订单：先验收，不重复开发

**任务**：堂食/外带/外送、线上/线下、先吃后付/先付后吃；开台、换台、并台、拼桌、AA；加菜改单、厨房叫起/制作/分次出餐、退餐、打印任务、交班日结与异常结转。真实资金、纸面打印和终端前端仍不计为已验收。

**API与数据库**：复用现有餐饮入口及fnb_/原共享订单表；当前不计划增加“统一营业操作API”或新订单表。已核验的代表路由：

| 现有API | 验收输入/输出重点 |
| --- | --- |
| POST /biz/x/food/stores/{storeNo}/checks | 开台请求、Idempotency-Key → CheckResultVO |
| POST /biz/x/food/checks/{checkNo}:transfer、:combine-tables | 原接口定义的版本与目标桌台 → OperationResultVO；重复查回原操作 |
| GET /biz/x/food/table-operations/{operationNo} | 原操作号 → OperationResultVO，不重新发起变更 |
| POST /biz/x/food/tasks/{taskNo}:start、:ready、:serve | 原任务动作DTO → EventVO；分次制作/交付与实际库存凭据一致 |
| POST /biz/x/food/print-jobs/{jobNo}:retry、:reprint | 原任务/权限/原因合同 → 原任务或重打审计，不冒充纸面成功 |
| POST /biz/x/food/closes:preview、:sign、:adjust | 原营业日及版本/责任确认 → 预览/签署/调整结果；日结不冒充资金对账 |

拼桌/AA、购物车、结算、退餐的完整路由沿已有Controller逐项登记验收用例，不根据路径习惯猜新路由。输入输出继续复用原DTO，不另造平行合同。

**对应代码（既有，按发现的问题定点调整）**：CheckService/CheckServiceImpl；BizCheckController、BizTableSharingController、BizCheckSeatController、BizTableOperationController；BizCartController、DiningCheckoutServiceImpl；KitchenTaskService及实现、BizKitchenTaskController；ProductionConsumptionService及实现；BusinessReturnServiceImpl、BizFoodReturnStockController；BizPrintJobController；BusinessCloseServiceImpl、BizBusinessCloseController；共享IndustryOrderServiceImpl、IndustryOrderAmendmentServiceImpl及原Mapper。不得为了验收给这些类补空方法。

**验收产物**：场景→请求/操作号→订单/库存/厨房/打印任务/日结凭据→实际结果清单。部署后的只读health不能代替业务验收。生产不创建虚构订单做写入测试；先在隔离门店环境完成流程，再用获授权的实际门店业务验收。

### M02 餐饮本地库存：准备数据并受控启用

**已有API前缀** `F=/biz/x/food/stores/{storeNo}`；写接口沿原Idempotency-Key和权限。主体、操作人来自认证，客户端不能指定库存owner。

| 现有API | 核心输入 | 核心输出 |
| --- | --- | --- |
| POST F/stock-items | itemKind,skuNo?,name,baseUnit,trackingMode,weighed | ItemVO：itemNo,kind,sku,unit,mode,status,version |
| PUT F/stock-items/{itemNo} | name,status,trackingMode,version,weighed | ItemVO |
| GET F/stock-items；GET F/stock-items/{itemNo} | 分页及原过滤参数/物料号 | 物料分页/详情 |
| POST F/stock-balances | itemNo,trackingMode,status,initialQty,reasonCode,reasonDetail | BalanceVO：onHand,reservedQty,availableQty,version,commandNo |
| PUT F/stock-balances/{itemNo}/policy | trackingMode,status,version,reasonCode,reasonDetail | BalanceVO |
| POST F/stock-balances/{itemNo}:adjust | delta,version,reasonCode,reasonDetail | BalanceVO和原命令凭据 |
| GET F/stock-balances；GET F/stock-balances/{itemNo}；GET F/stock-movements | 原分页/物料过滤 | 余额/流水及来源操作 |

**数据库**：复用fnb_stock_item、fnb_stock_balance、fnb_stock_reservation、fnb_stock_reservation_item、fnb_stock_command、fnb_stock_movement，以及已增加的定义快照、追踪模式和返还关联。无需为启用增加表；真实期初录入走现有接口，不直接SQL改余额，也不复制进销存余额。

**代码**：BizFoodStockController；FoodStockItemService、FoodStockBalanceService（均由现有FoodStockManagementServiceImpl实现）；FoodLocalStockPort/FoodStockReservationServiceImpl；FoodStockContracts；FoodMappers中StockItem/StockBalance/StockReservation/StockMovement/StockCommand相关Mapper；既有可信owner冻结与恢复入口。仅新增可复用的验收数据准备脚本/场景用例，不另建库存导入引擎。

**实施**：确认门店及真实数据 → 检查物料/配方/套餐模式与单位 → API初始化 → 验证预留/消耗/取消/返还和历史owner → 明确本地报表source-zone → 再开启本地库存功能。参数按现有配置体系维护，不把应用级装配开关伪装成已支持的门店热切换API。

### M03 单向进销存镜像：复用当前接口和9张同步表

具体逻辑以[04同步方案](./04-可选进销存库存同步方案.md)为准。

**API**：现有GET/PUT F/stock-sync/config；POST F/stock-sync:preflight；GET F/stock-sync/mappings、PUT F/stock-sync/mappings/{itemNo}；GET F/stock-sync/deliveries；POST F/stock-sync/deliveries/{syncNo}:retry；POST F/stock-sync:reconcile；GET F/stock-sync/reconciliations/{reconciliationNo}。映射PUT实际路径为带itemNo项，集合只有GET，不新增集合PUT。

关键合同：ConfigCommand(enabled,version,reason)→ConfigVO(status,generation,version,backlog,lastErrorCode)；MappingCommand(三个可选目标引用,sourceUnit,targetUnit,version)→MappingVO；DeliveryVO包含syncNo,generation,sourceVersion,status,attempts,errorCode,ackRef；对账输出ReconciliationVO包括进度、差异、水位及consistencyMode=PAGE_OBSERVED。

进销存既有GET /biz/inventory/food-stock-projections及/{sourceItemNo}；内部POST /internal/inventory/food-stock-projection/{validate-mappings|activate|deactivate|apply|receipt|query}，沿既有内部认证及范围绑定。

**数据库**：FOOD的fnb_stock_sync_config/mapping/item_state/delivery/reconciliation/difference共6表；INVENTORY的inv_food_stock_projection/sync_receipt/sync_session共3表。复用fnb_stock_command、fnb_action_log和Outbox，不新增同步审计/收件箱/worker任务表，不更新inv_stock_balance。

**代码**：FoodStockSyncServiceImpl.configure/map/retry/preflight；FoodStockSyncPublisher.capture/control/retry；FoodStockSyncDispatcher.handle及分页基线；FoodStockReconciliationServiceImpl；BizFoodStockSyncController；CoreFoodStockProjectionPortImpl；InternalFoodStockProjectionController、FoodStockProjectionServiceImpl、FoodStockProjectionMapper、BizFoodStockProjectionController及查询Service。

**实施**：owner和门店库位真实存在 → 同单位映射 → 接收端/Outbox预检 → 开启并观察backlog与回执 → 对账 → 验证OFF后改映射、重开新generation和旧消息拒绝。ACTIVE不承诺全部送达，失败恢复按原事件查回，不另发数量增减。

**不纳本批的候选需求**：自动单位转换、启用中热改映射、进销存采购/盘点/调拨回写、原生过账或完整流水复制。这些不是当前实现缺陷。

### M05 共享订单：补齐最终金额与分摊只读事实

**已知差距**：IndustryReportFactsPortAdapter当前提供订单创建/成交/完成数量及原应收、有效应收、调整、成交金额；不能据这些总额推导所有最终优惠、税、退款和行级分摊。

**先复用**：共享订单/改单/统一定价的最终冻结快照、IndustryOrderAllocationPolicy和原分配凭据；不重算已完成订单，不让报表调用当前促销配置重放历史价格。特别注意ord_checkout_line等既有表包含行业约束，不能仅因名字通用就将餐饮写进BEAUTY限定的表。

**接口调整**：优先扩展原CORE ORDER SourceSnapshot中的MetricFact，不新增重复经营REST。候选只读Service方法`readFinalFinancialFacts(scope,orderRefs,asOf)`（拟新增名称，编码前对齐现有Service落点）：输入可信范围、订单/行/调整引用及截至时间；输出order/subOrder/lineRef、finalSnapshotRef、allocationVersion、currency、gross/discount/netExTax/tax、退款原引用与金额、sourceVersion、coverage/unknownReason。它不接收前端上传的“最终价格”。

**数据库**：先逐项核对原冻结快照是否持久保存上述事实。仅当缺少不可变行级分配时启用候选DB-C1，不默认修改所有订单行或事后回填0。

**代码**：扩展shop-core的IndustryReportFactsPortAdapter.readSnapshot、原IndustryOrderAllocationPolicy使用处及行业订单/改单相关Mapper；必要时扩展原确认/改单事务保存最终事实。shop-base继续复用ReportContracts.SourceSnapshot/MetricFact；若确需新增金融事实DTO则放共享订单合同而非food-api。ReportSourceCollectionServiceImpl仅收集事实，不承担分摊计算。

**验收**：一笔订单最终行分摊之和=原确认总额；折扣/优惠券/税内含与外加、抹零、改单、部分退餐可追溯到原分配；跨币种不相加；缺历史原始凭据的订单输出PARTIAL/UNKNOWN。退款申请不计作实际退款成功。

### M06 PAY只读统计：不恢复本批真实资金开发

**已有合同**：POST /internal/pay/report-facts/snapshot，输入ReportContracts.SourceQuery，输出SourceSnapshot。不新增餐饮直连支付库查询，不调用收款/退款/储值执行接口来测试报表。

**待调整内容**：核对实际支付/退款/手续费事实与可信订单、主体、门店归属；支付渠道、退款渠道、币种、来源事件时间/业务归属时间、冲正/撤销及sourceVersion。保留遗留记录缺少归属时的UNKNOWN，不能只凭金额或买家ID匹配门店。

**代码**：独立PAY PaymentReportFactsService、PaymentReportFactsPortAdapter、InternalPaymentReportController；宿主RemotePaymentReportFactsPort；ReportSourceCollectionServiceImpl。对应Mapper/表沿PAY原owner维护；若缺少可追溯行关联，由支付专项确定增量，不在FOOD/REPORT复制支付账本。

**费用互斥**：支付手续费、外送佣金等每笔只保留一个权威费用来源；EXPENSE与PAY都出现时按原始费用引用去重/互斥归属，不在汇总末端凭相同金额去重。

### M07 历史成本与库存边界

**数量已有来源**：FoodStockReportFactsPortAdapter从本地movement、balance、command及显式sourceZone提供数量事实；InventoryReportFactsPortAdapter的原生库存数量不是餐饮本地COGS来源。

**API调整**：沿已有POST /internal/food/operating-report/local-stock-facts（SourceQuery→SourceSnapshot），补真实历史边界证据及未来可信成本事实，不改成查询“当前余额”的替代接口。来源输出区分实物消耗、损耗、返还、销售成本；数量与金额不能互相冒充。

**数据库**：优先从初始化/调整/消费/释放/返还流水及政策命令重建历史边界，不预建第二套库存余额表。无法证明某日边界时UNKNOWN。只有在可信成本owner已确定后，补所需不可变成本引用/分配事实；目前不直接增加average_cost列、不从今日采购价倒推历史COGS。

**代码**：FoodStockReportFactsPortAdapter.readSnapshot及既有FoodMappers.StockMovementMapper/StockCommandMapper/StockBalanceMapper；必要时补只读历史查询。共享成本取得合同/适配由成本事实owner确定，餐饮本地无采购成本来源时不借进销存镜像伪造成本。InventoryReportFactsPortAdapter仅维护其原生owner的数据。

**必须先确定的业务输入**：成本来自真实出库成本、已确认成本单还是其他既有财务事实；基础单位和币种；生效时间及缺失策略；损耗、退餐不返库/可售返还分别如何归属。未确定前，COGS/毛利/净利保留不完整，不硬编码移动平均/FIFO等估价方法。

**若确认没有来源且本批需要手工维护费用**，才批准以下候选（未实现、未分配迁移号）：
