# 餐饮本地库存同步到进销存：当前实现与启用流程

> 2026-10-30 按已部署代码446cf7799整理。同步后端已实现，FOOD V35和INVENTORY V18已迁移；生产本地库存及门店同步尚未启用。本文替代早期“未编码/拟新增”描述。数据库仅支持MySQL 9，不再要求MariaDB兼容或验收。本文不新增API或修改库存业务规则。

> 开发结构更新：远端38f7f0378已将原生库存域迁入backend/inventory。餐饮镜像接收/查询Java逻辑仍在商城shop-inventory，独立inventory-svc尚未提供相应镜像入口；具体补开发清单见[08 M03-B](./08-剩余功能分模块实施方案.md)。下文同步语义和生产446cf7799集成形态保持有效，不表示独立接收已完成。

## 1. 先看结论

| 问题 | 当前结论 |
| --- | --- |
| 谁管理餐饮库存 | 餐饮本地库存是唯一事实来源；订单预留、制作消耗、取消释放和退餐返还均按订单冻结的来源处理。 |
| 是否必须接进销存 | 不必须。同步按主体+门店+目标INVENTORY配置，默认OFF；本地库存功能开关与门店同步开关是两个不同层级。 |
| 同步到哪里 | 进销存独立库的FOOD_LOCAL来源镜像。既不更新原生inv_stock_balance，也不生成原生入出库、采购、盘点或调拨单据。 |
| 同步什么 | 物料编号、基础单位、跟踪模式、有效状态、实存、预留、来源版本/更新时间，以及可选的目标owner/location/item引用。当前快照不含采购成本、估值、财务费用或菜品名称目录。 |
| 如何同步 | 本地业务事务保存库存变更、来源版本、同步记录及Outbox事件；事务外异步发送绝对快照，进销存在自身事务内更新镜像并保存回执。 |
| 是否双向 | 当前单向。进销存采购/盘点/调拨不回写餐饮余额；镜像数量也不反向决定餐饮可售量。 |
| 对营业的影响 | 远端不可用或投递失败不回滚已提交的本地业务。源事务内库存与Outbox仍需一起提交，不能把本地持久化失败也称为营业成功。 |

数量示例：本地实存100、预留10，镜像收到100/10；随后制作消耗2、释放对应预留，下一消息发送98/8，而不是“扣2”。重复发送98/8不会再扣一次。可售数量由既有本地规则计算，不能把实存和预留相加。

## 2. 一次完整同步如何运行

### 2.1 首次开启

1. 准备真实本地物料、门店库存、基础单位及初始盘点；没有初始化的库存不补造为0。
2. 如需关联原生进销存身份，配置owner/location/item三个引用；也可只保留餐饮来源身份。当前只支持相同基础单位，不提供自动换算；映射不会自动创建进销存物料。
3. 接收端必须已有有效的进销存owner及该门店库位；即使只做来源镜像也要满足这项授权/范围前提。调用preflight检查接收端、主体/门店授权及映射。预检只读，不开启同步。
4. 提交enabled=true、当前version及Idempotency-Key：配置从OFF转为BOOTSTRAPPING，generation加1，冻结现有余额记录的扫描上界，持久化ACTIVATE事件。
5. Dispatcher在本地事务外激活接收会话；以余额ID分页，每页最多100条，捕获带版本的基线快照并保存游标。开启后的本地变更继续在源事务内捕获，不等整批扫描结束。
6. 基线扫描完成后配置转ACTIVE。**ACTIVE表示基线已捕获并可持续同步，不表示所有消息都已接收**；是否追平要结合backlog、投递回执及对账结果判断。

### 2.2 营业中的变更

初始化、人工调整、预留、消耗、释放、实际返还及相关物料/余额状态变更，经FoodStockSyncPublisher.capture捕获。启用状态下同一门店物料维护专用sourceVersion，不能用普通实体version替代。

业务事务中的顺序：本地物料/余额修改 → 推进同步来源版本 → 保存快照与投递记录 → 写FOOD_STOCK_SYNC_REQUESTED Outbox。事务提交后Dispatcher才调用接收端，远端请求不占据餐饮写事务。

接收端按主体、门店、来源FOOD_LOCAL和generation校验会话，并在同一事务中保存镜像与回执：

| 情形 | 结果 |
| --- | --- |
| 新事件、新版本 | APPLIED，保存新绝对快照 |
| 同版本同内容 | UNCHANGED，不重复修改数量 |
| 旧版本后到 | STALE，保留更高版本 |
| 同事件编号不同hash、同版本不同内容 | 冲突，不覆盖原事实 |
| 已关闭或旧generation | 拒绝应用，不能复活旧同步会话 |
| UNTRACKED | onHand/reservedQty为空，不当成0或无限库存 |

### 2.3 失败、超时与对账

- Dispatcher先按原syncNo及payloadHash查询回执；查无回执才调用activate/apply/deactivate。超时不能证明未提交，后续使用原事件继续查回或幂等重放。
- 实现中的投递状态为PENDING、BLOCKED_MAPPING、RETRYABLE、COMPLETED、CANCELLED。未知远端结果由原事件查回处理，当前没有单独的UNKNOWN投递枚举。
- 失败通过现有Outbox重试，投递记录保留attempts、错误码、下次尝试时间和ackRef；人工retry仍复用原快照和事件，不重新生成扣减。
- BLOCKED_MAPPING需先按映射流程处理，不能靠人工retry跳过映射约束。
- 对账consistencyMode为PAGE_OBSERVED，是分页异步观测，不是两库同一瞬间的全局冻结快照；营业中的新变更需结合版本和水位解释。对账按门店/物料比较来源与镜像的版本、单位、状态和数量，持久化进度与差异；使用现有Outbox执行分页任务，不新增每店独立定时任务。对账报告不等于已自动修正所有差异。

### 2.4 关闭、重新开启和修改映射

关闭：ACTIVE或BOOTSTRAPPING → DISABLING → 接收端确认DEACTIVATE屏障 → OFF。关闭中不再捕获普通变更；过时待发送任务取消。在屏障确认前在途事件仍可能完成，不能提前承诺远端已停用。

OFF保留镜像和最后版本，不删除或把数量清零。再次开启使用新generation并重新抓基线，关闭期间不补造历史流水。

**当前映射只允许在OFF修改**：先关闭并等到OFF → 修改映射（携带version）→ 重新preflight → 开启新generation。当前没有“边同步边改映射、自动切换会话”的API流程。

## 3. 开关、状态和数量的解释

- 应用级`shop.food.local-stock.enabled`：决定是否装配本地库存及其同步管理能力；生产当前未启用。
- 门店级`fnb_stock_sync_config`：控制该主体门店是否向INVENTORY同步，未配置视为OFF。
- Outbox基础配置：启用前核对FOOD_STOCK_SYNC_REQUESTED路由及实际消费者运行状态；仅把门店开关打开不保证消息能及时投递。
- 配置主流程：OFF → BOOTSTRAPPING → ACTIVE → DISABLING → OFF。投递错误看delivery，不把RETRYABLE误当成配置已关闭。
- 同步开关不改变已冻结订单的库存归属。历史订单沿原来源恢复，新单切换需按门店启用方案执行。

## 5. 已有API与参数

餐饮前缀`/biz/x/food/stores/{storeNo}`，权限BizPerms.STOCK，主体/操作人来自登录和门店范围，写接口使用Idempotency-Key。下表输入是当前合同，不包含旧草案中的转换公式或日期筛选。

| 方法/相对路径 | 输入 | 输出 |
| --- | --- | --- |
| GET /stock-sync/config | storeNo | status,generation,version,backlog,lastErrorCode |
| PUT /stock-sync/config | enabled,version,reason | 同ConfigVO；关闭可返回DISABLING |
| POST /stock-sync:preflight | 无请求体 | allowed,issues[] |
| GET /stock-sync/mappings | page,size | 映射分页 |
| PUT /stock-sync/mappings/{itemNo} | targetOwnerRef,targetLocationRef,targetItemRef（一起配置或都为空）,sourceUnit,targetUnit,version | itemNo、目标引用、单位、mappingRevision,status,version |
| GET /stock-sync/deliveries | page,size,status?,itemNo? | syncNo,itemNo,generation,sourceVersion,status,attempts,errorCode,ackRef分页 |
| POST /stock-sync/deliveries/{syncNo}:retry | 无请求体 | 原投递DeliveryVO |
| POST /stock-sync:reconcile | itemNos（可空列表） | ReconciliationVO |
| GET /stock-sync/reconciliations/{reconciliationNo} | page,size | 对账进度及差异分页 |

进销存查询：GET `/biz/inventory/food-stock-projections` 和GET `/biz/inventory/food-stock-projections/{sourceItemNo}`，按门店及既有库存权限控制。它们是独立镜像查询，不替换原生余额接口。

内部`InventoryFoodStockProjectionInternalApi`提供validate-mappings、activate、deactivate、apply、receipt、query；只由可信内部服务调用，范围、幂等与hash合同不向外卖平台开放。

## 6. 代码入口与部署边界

| 对象 | 职责 |
| --- | --- |
| FoodStockSyncServiceImpl | 门店配置、预检、OFF时修改映射、查询和人工重试 |
| FoodStockSyncPublisher | 参与源业务事务，捕获来源版本、完整快照及Outbox |
| FoodStockSyncDispatcher | 事务外调用接收端、基线分页、原回执查回、关闭屏障和恢复 |
| FoodStockReconciliationServiceImpl | 对账创建、分页执行及差异记录 |
| BizFoodStockSyncController | 餐饮商家端API及门店权限 |
| CoreFoodStockProjectionPortImpl | 调用既有InventoryFoodStockProjectionInternalApi，支持装配后的本地/远程内部合同 |
| FoodStockProjectionServiceImpl | 进销存会话、镜像、版本与幂等回执的本地事务 |
| BizFoodStockProjectionController | 进销存商家镜像查询 |

FOOD和INVENTORY各自只提交本库事务，不用跨库事务。集成部署不把两边写操作合并成一个事务；独立部署仍复用相同内部合同及签名授权。真实独立进程网络故障联调属于REM-07待验收，当前专项通过不替代该证据。

## 7. 启用清单与验收

1. 在MySQL 9的隔离环境准备真实形态数据，确认本地库存、配方、小料/套餐需求编译正确。
2. 核对主体/门店授权、接收端、Outbox路由和worker，完成同单位映射及preflight。
3. 开启后检查基线游标、backlog及回执，执行首轮对账；ACTIVE但有积压时继续显示未追平。
4. 验证并发新增/调整、重复/乱序、接收成功但响应丢失、双方重启，最终快照一致且无重复累计。
5. 验证关闭中断网、确认OFF后的旧消息拒绝、重新开启新generation及OFF修改映射流程。
6. 验证进销存原生余额/单据不变、餐饮在接收端不可用时仍可提交本地业务、UNTRACKED/未初始化不被伪造为零。
7. 门店真实盘点和验收通过后再显式开启生产；当前文档整理不改生产开关。

后置需求：自动单位换算、进销存原生采购/调拨/盘点回写、镜像参与原生过账/成本、完整历史流水复制，均未包含在当前同步能力中。
