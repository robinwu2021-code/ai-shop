### 部署当天踩到的三个坑

**一、业务系统起不来，反复重启六分钟。**
`jobHandlerRegistry` 的 bean 定义在 `@Profile("worker")` 的 `InProcessJobConfig` 里，
而生产跑 `api,ops`。「持有任务体」和「负责排期」是两件事，被一个 profile 合并了。
现在任务体跟 `shop.job.enabled` 走，排期仍跟 `worker` 走；`JobTargetProfileTest`
用生产的 profile 组合把上下文起一遍，守住这条。

**二、端点 200，调度器却读出一堆 null。**
全局 `ResponseBodyAdvice` 把返回值裹成 `{code,msg,data}`，调度器按自己的契约
把根当数组遍历。**不在任何一层报错** —— HTTP 200、JSON 合法、调用方也没崩，
只是任务声明变成一条条空记录。`/internal/**` 现在整个不套信封。

**三、首次登记差点全开。**
`JOB_WORKER_START_DISABLED` 我写了却没往生产配。10 个任务以「开」登记，
15 秒后关掉 —— 当时最早的 cron 点是 23:26:00，`run_count` 全是 0，一轮都没真跑。
**这一行现在在 `job.env` 里。** 换机器、重建 env 时别漏。

### 与业务系统的关系

`ai-shop-job.service` 刻意**不写** `After=ai-shop.service`。业务系统重启时调度器
拿到连接拒绝，记一次 `UNREACHABLE` 后重试；调度器挂了业务系统毫无感觉。
这正是把它拆出来的理由 —— 从前 17 个任务的存活等同于那个 85MB 单体的存活。

发布顺序也因此不重要：先发哪个都行，最多多一轮 `UNREACHABLE`。

## 1. 为什么不是「打开开关重启」那么简单

三件事必须同时成立，缺一个的表现各不相同、而且都不报错：

| 缺什么 | 表现 |
|---|---|
| 没有 `ai_shop_job` 库 | 启动直接失败（这个反而是好的：看得见） |
| 有库、没 `worker` profile | **运营页面是空的** —— 任务声明由 worker 启动时 upsert，没有 worker 就没有行 |
| 有 worker、没 `startDisabled` | **14 个任务一次性全跑起来** —— 14 处同时的行为变化，真出事时分不清是哪一个 |

第三条是这次专门加的开关（`shop.job.worker.start-disabled`）：
首次入库一律置为「停」，任务全部登记进表、页面上看得见、有说明有 cron，但一个都不跑。
**它只影响首次 INSERT** —— 运营打开之后，下次发版不会把它关回去（有测试守着这一条）。

## 2. 步骤

### 第 0 步 · 建库与账号（**需要有 DB 凭据的人执行**）

```sql
CREATE DATABASE ai_shop_job DEFAULT CHARSET utf8mb4;
CREATE USER 'ai_shop_job'@'127.0.0.1' IDENTIFIED BY '<强口令>';
-- **只授这一个库**：业务连不到 job 库要靠授权强制，不靠自觉
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, DROP
  ON ai_shop_job.* TO 'ai_shop_job'@'127.0.0.1';
FLUSH PRIVILEGES;
```

> 表由 Flyway 自己建（`db/job` 的 V1/V2，历史表 `job_flyway_history`），不用手工建。

### 第 1 步 · 配置

`/opt/ai-shop/shop-app.env` 追加：

```sh
SHOP_JOB_ENABLED=true
JOB_DB_URL=jdbc:mysql://127.0.0.1:3306/ai_shop_job?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai
JOB_DB_USER=ai_shop_job
JOB_DB_PASSWORD=<上一步的口令>
SHOP_JOB_START_DISABLED=true
```

systemd 单元里把 profile 改成 `api,ops,worker`。

> ⚠️ **worker 与业务同进程**是这一步有意的选择：先在业务实例内跑通、观察，
> 再拆独立进程（G4）。中间任何一步出问题都只回退一层。

### 第 2 步 · 重启并**只看三件事**

```bash
# 1) 起来了吗（worker profile 曾经起不来 —— SecurityConfig 少一个 @ConditionalOnWebApplication，
#    2026-08-27 修的。若回退到那之前的版本，这里会报 "No qualifying bean of type HttpSecurity"）
systemctl status ai-shop

# 2) 表建了吗
mariadb -N -B ai_shop_job -e "show tables;"        # 期望：job_definition / job_run / job_log / job_flyway_history

# 3) 任务登记了吗、且**全是停的**
mariadb -N -B ai_shop_job -e "select job_name, enabled from job_definition order by job_name;"
```

**第三条的期望是 14 行、`enabled` 全为 0。** 若有 1，说明 `SHOP_JOB_START_DISABLED` 没生效 ——
**立刻在页面上全部关掉**再继续。

### 第 3 步 · 运营页面自检

以 `TECH_OPS` 或超管登录运营端 → 左侧「定时任务」：

- 14 行都在，中文名读得懂（**不是 `plan-expiry` 这种锁名**）
- 每行「最后一次」显示**从未执行**
- 开关都是「已停」

看不到菜单 = `V269` 没跑到；看到菜单但列表空 = worker 没起来（回第 2 步第 3 条）。

### 第 4 步 · **一次只开一个**，按这个顺序

| 序 | 任务 | 先开它的理由 | 开了之后看什么 |
|---|---|---|---|
| 1 | `media-scan` 媒体资源扫描 | **只读**。跑错了最多是白跑一遍 | 日志有一条 SUCCESS |
| 2 | `session-purge` 会话与登录日志清理 | 只删过期很久的数据，且现在几乎没有 | 删了 0 行是正常的 |
| 3 | `media-reconcile` 图片记账对账 | 会改 `sys_media_asset`，但只动 PENDING 的残留 | 补齐/清掉的行数 |
| 4 | `recon-scan` 对账自查 | 只读扫描 + 补记，不动钱 | **补回不为零要查回调链路** |
| 5 | `points-identity` 积分恒等式自检 | 纯自检，不改账 | **失衡为负 = 真实资金缺口**，先别开下一个 |
| 6 | `notify-push-task` 定时推送下发 | **开始给用户发东西了** | 发出去的条数与运营配的对不对得上 |
| 7 | `order-auto-close` 订单超时关单 | **第一个改用户看得见的东西**（他的订单会没） | 关单数；平台目前 0 订单，应当是 0 |
| 8 | `points-activate` / `points-expire` | 改余额 | 转正/清零的条数 |
| 9 | `qualification-expiry` / `plan-expiry` | **会让商家掉权限** | 影响的商家数；6 家都是演示数据 |
| 10 | `inv-backfill` 库存搬运 | 量最大，且是进销存切换的判据 | 对差是否为零 |

**每开一个，等它至少跑过两轮**（看 `job_run.run_count` 涨到 2）再开下一个。
日级任务等不了两轮就用页面上的「立即执行」——它只是记下请求，
调度器最多 30 秒后跑，页面会显示「已排队」。

## 3. 回退

| 出事范围 | 怎么退 | 生效时间 |
|---|---|---|
| **某一个任务** | 页面上点「停用」 | ≤30 秒（下一轮轮询取消调度） |
| 整套调度 | env 去掉 `SHOP_JOB_ENABLED`，重启 | 一次重启 |
| 连这套代码都不想要 | profile 改回 `api,ops`，重启 | 一次重启 |

**第一行是这次做运营页面的全部意义**：出事时不必发版、不必重启、不必找人改配置。
在这一页存在之前，唯一的手段是改配置重启整个实例。

`ai_shop_job` 库**不用删**：里面只有调度自己的数据，留着还能回看那几天跑了什么。

## 4. 观察一周，看这三个数

```sql
-- 1) 有没有任务在连续失败（只统计 FAILED；跳过/超时/调不通都不算）
select job_name, consecutive_failures, last_status, last_run_at
  from job_definition d join job_run r using (job_name)
 where r.consecutive_failures > 0;

-- 2) 有没有任务「开着但从没跑过」—— cron 写错了会是这个样子
select job_name, cron, next_run_at from job_definition d
  left join job_run r using (job_name)
 where d.enabled = 1 and r.run_count is null;

-- 3) 日志表长得快不快（它是这个库里唯一会长的表）
select count(*), min(started_at), max(started_at) from job_log;
```

一周后没有第 1、2 条，且第 3 条的增长符合预期，就可以进 G4（拆独立进程）。
