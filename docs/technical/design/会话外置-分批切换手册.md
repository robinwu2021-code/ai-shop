## 1. 为什么要切

两件事，都不是「更先进」这种理由：

- **部署不再清空所有人的会话。** 2026-08-24 一次 `cp` 覆盖了正在跑的 jar，
  Ehcache 关闭时读到新字节 → `NoClassDefFoundError` → 下次启动判定 unclean shutdown，
  **删掉整个持久化目录**，日志里只有一行 `deleted root directory`，而所有人已经掉线。
- **多实例的必要条件之一。** 磁盘缓存只能被一个进程持有。
  （注意是**必要**不是充分 —— 见第 6 节。）

## 2. 代价，说在前面

**被切的那一端全员重新登录一次。** 旧的 ehcache 会话不迁移，也不该迁移：
迁移意味着把明文令牌从缓存搬进库，而库里存的是 SHA-256 —— 搬不过去。

所以顺序是 **运营端 → B 端 → C 端**：先在十几个人身上验证，最后才动全量用户。

## 3. 切运营端

### 3.1 前置检查

```bash
ssh soukmind-tx-root "
  mariadb -N -B -e \"SELECT COUNT(*) FROM ops_session\" ai_shop            # 表在
  grep -c SHOP_AUTH_TOKEN_STORE_BY_REALM /opt/ai-shop/shop-app.env         # 应为 0
  ls -l /opt/ai-shop/shop-app.jar                                          # 版本要含按端开关
"
```

jar 里必须有 `TokenStoreSelection` —— 2026-08-28 08:26 之后的包都有。
没有的话切下去会**整体**变成 db（那个版本只认全局开关），三端一起掉线。

### 3.2 改一行

```bash
ssh soukmind-tx-root "echo 'SHOP_AUTH_TOKEN_STORE_BY_REALM_OPERATOR=db' >> /opt/ai-shop/shop-app.env"
```

**名字必须逐字是这个。** 写错不会有任何报错，那一行等于注释，
而你会以为切过了 —— 今天早上 `JOB_WORKER_START_DISABLED` 就是这么白写的。
`TokenStoreSelectionEnvTest` 钉的就是这个名字。

`SHOP_TOKEN_STORE=ehcache` 那一行**不要动**：C 端与 B 端还得用它。

### 3.3 重启并验证

```bash
ssh soukmind-tx-root "systemctl restart ai-shop"
```

三条判据，缺一条都算没切成：

| 看什么 | 期望 | 不对时说明 |
|---|---|---|
| `grep '会话存储按端装配' /var/log/ai-shop/app.log \| tail -1` | `{CONSUMER=ehcache, MERCHANT=ehcache, OPERATOR=db}` | 没这行 = 按端开关没生效，检查变量名 |
| 运营登录一次后 `SELECT COUNT(*) FROM ops_session` | ≥ 1 | 0 = 会话还在写 ehcache |
| `SELECT event FROM ops_login_log ORDER BY id DESC LIMIT 1` | `LOGIN` | 空 = 审计没接上 |

还要确认 **C 端没被误伤**：`SELECT COUNT(*) FROM usr_session` 应当仍是 **0**
（C 端会话还在 ehcache 里）。这一条不是形式 —— 它是「只切了一端」的唯一硬证据。

### 3.4 回滚

```bash
ssh soukmind-tx-root "sed -i '/SHOP_AUTH_TOKEN_STORE_BY_REALM_OPERATOR/d' /opt/ai-shop/shop-app.env && systemctl restart ai-shop"
```

代价：运营端**再重登一次**。`ops_session` 里的行留着不用管，下次切回来还能用
（除非过了 TTL）。

## 4. 观察一天再往下

看这三个数，任何一个不对就先别推进：

- `ops_session` 行数：应当约等于「在线的运营人数」，不应当只增不减
  （`DbTokenStore` 到期会清；只增说明清理没跑）
- `ops_login_log` 里 `LOGIN_FAILED` 的比例：切换后短时间会升（旧令牌失效），
  **半小时内应当回落**。不回落说明有人一直在用旧令牌重试，前端没正确跳登录页
- `app.log` 里 `auth-revoke-poll` 相关的异常：撤销传播是每 5 秒一次的库查询，
  它出错不会影响登录，但会让「停用了账号却还能用」

## 5. B 端 / C 端（已完成）

三端已全部切到 `db`。B 端与 A7（改发 `btk_`）**并成了一次切换** ——
手册原本就建议这么做，省一次全员重登，实际执行也是这样。

真实代价比预估的小：切换那一刻线上只有 2 条有效会话，掉线的是一台测试真机。
**注意一个容易查错的地方**：A7 之前 B 端令牌是 `ctk_`、装在 `usr_session` 里，
不在 `mch_session`。当晚我先看 `mch_session`（0 行）就说「重登代价是 0」，
是错的 —— 要看的是 `usr_session`。

## 6. 切完之后仍然不能多实例

会话进库只是**必要条件**。这四个还在进程内：

`InMemoryRateLimiter`、`OtpStore`、`CaptchaService`、`PasswordResetTokens`

起第二个实例会出现：限流按实例各算一份、验证码在 A 实例发 B 实例验不过。
记在 ADR-015 §3.1。**别据此排期。**

## 7. 那几件「我做不了的事」后来怎么解决的

写这份手册时列了三件我做不了的事，切换当晚全部落地了 —— 记下解法，下次不用再卡：

- **改 `shop-app.env` 并重启生产**：由人决定时机，我执行并守到 `health=200`。
  ⚠️ 「重启完就走开」出过事故（一次 `health=000` 挂了六分钟没人知道），
  所以现在的规矩是**轮询到 200 才算这一步结束**。
- **登录一次以验证**：密码始终没有经我手 —— 由人在真机上输入，
  我从服务端读 nginx 与会话表给结论。判据见 §8.2。
- **选窗口**：切换在当晚进行，线上只有 2 条有效会话，代价最小的时刻确实是「越早越好」。

仍然做不了、且不该由我做的：**运营端的功能实测**（需要运营账号登录后逐页点）。
我只能验到静态产物、返回码与 computed 样式值。

## 8. A7 上线实录（2026-08-28 夜）

切换本身很顺，**问题全在 A7 那一侧**：把 B 端令牌从 `ctk_` 换成 `btk_`，
牵动的不只是前缀。当晚在生产上抓到三个缺陷，全量 1449 条测试一条都没红。

### 8.1 三个缺陷

| # | 缺陷 | 症状 | 为什么测试没抓到 |
|---|---|---|---|
| 1 | `BizContextFilter` 的判据还是 `isConsumer()` | 商家登进去后**每个操作都 403**（不是 401，看不出是登录问题） | 场景测试全部拿 `ctk_` 打 `/biz`，改完先炸的是它们自己 |
| 2 | 停用店员 / 注销账号的 `revokeUser` 还指着 C 端池 | **空吊销**：接口返回成功、状态确实改了、日志无异常，人还在线 | 有守卫，但它钉的是「调 CONSUMER 池」这一当前实现，A7 后照样绿 |
| 3 | 身份重建时丢了本池的 `realm` | 登录成功、六个端点全 200，**约 40 秒后掉线** | 单测用内存 store，直接存对象，根本没有重建这条路 |

第 3 个最值得记：`identityCache` 里存的是签发那一刻的对象（realm 正确），
只有 TTL（B 端池 30 秒）过期后才走 loader 重建，而 `ConsumerIdentityLoader`
无论谁来问都回 `CONSUMER`。**缓存给了它一段潜伏期**，任何
「登录→调接口→断言」的测试都在潜伏期内跑完。

修法是把 realm 的权威放回**池**：`DbTokenStore` 重建后 `withRealm(this.realm)`。
令牌前缀决定它是哪个端的会话，而能不能签进这个池，`issue()` 早就校验过。

### 8.2 验收判据（下次照抄）

不要用「有没有出现 401」当判据 —— **冷启动没令牌也是 401**。当晚我就是这么误报了一次。

成立的判据长这样：

```
登录时刻之后，/biz 请求全 200、401 = 0，
且带 30 秒轮询的端点连续 ≥5 次跨过 identityTtl 仍是 200
```

实测（23:20:11 登录）：40 个请求全 200，`unread-count` 连续 7 次轮询全 200，
覆盖 3 分 21 秒。对照修复前那次：22:44:58 还是 200，22:45:28 就 401。

### 8.3 顺带确认没问题的

- `/biz/auth/login` 里那个「顺手撤掉 `ctk_`」是生效的 —— 三条过渡会话都是 `revoked=LOGOUT`。
  （用 `count(*)` 会把软撤销的行也数进去，看着像没撤掉。）
- 运营端会话不受影响：`otk_` 走的是另一条链，重启后仍然有效。
- V270 给存量行的默认值是 `USR`。今天没造成损失是因为 `mch_session` 当时是空的 ——
  **如果表里已经有店员会话（主体是 `mch_account_no`、本该是 `MCH`），
  它们会被派给消费者 loader 而全部掉线**。这是运气，不是设计。
