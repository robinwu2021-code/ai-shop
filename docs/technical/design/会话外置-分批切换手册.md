# 会话外置 · 分批切换手册

> 一次只切一端。**这份手册里有几步我做不了**，写在最后一节。
> 前置能力（按端开关）已于 2026-08-28 上线，生产配置一个字没动。

## 0. 现在是什么状态

| 项 | 实测值（2026-08-28 08:xx） |
|---|---|
| `SHOP_TOKEN_STORE` | `ehcache` —— 三端会话混在 `/var/lib/ai-shop/sessions` 一个磁盘目录里 |
| `usr_session` / `mch_session` / `ops_session` | 表都在（V264–V266 已应用），**各 0 行** |
| `usr_login_log` / `mch_login_log` / `ops_login_log` | 表都在，只有失败记录会进（成功记录 2026-08-28 已接上） |
| `shop-app.env` 里的 `SHOP_AUTH_*` | 一条都没有 |

## 1. 为什么要切

两件事，都不是「更先进」这种理由：

- **部署不再清空所有人的会话。** 2026-08-24 一次 `cp` 覆盖了正在跑的 jar，
  Ehcache 关闭时读到新字节 → `NoClassDefFoundError` → 下次启动判定 unclean shutdown，
  **删掉整个持久化目录**，日志里只有一行 `deleted root directory`，而所有人已经掉线。
- **多实例的必要条件之一。** 磁盘缓存只能被一个进程持有。
  （注意是**必要**不是充分 —— 见第 6 节。）

## 2. 代价，说在前面

**被切的那一端全员重新登录一次。** 旧的 ehcache 会话不迁移，也不该迁移：
迁移意味着把明文令牌从缓存搬进库，而库里存的是 SHA-256 —— 搬不过去。

所以顺序是 **运营端 → B 端 → C 端**：先在十几个人身上验证，最后才动全量用户。

## 3. 切运营端

### 3.1 前置检查

```bash
ssh soukmind-tx-root "
  mariadb -N -B -e \"SELECT COUNT(*) FROM ops_session\" ai_shop            # 表在
  grep -c SHOP_AUTH_TOKEN_STORE_BY_REALM /opt/ai-shop/shop-app.env         # 应为 0
  ls -l /opt/ai-shop/shop-app.jar                                          # 版本要含按端开关
"
```

jar 里必须有 `TokenStoreSelection` —— 2026-08-28 08:26 之后的包都有。
没有的话切下去会**整体**变成 db（那个版本只认全局开关），三端一起掉线。

### 3.2 改一行

```bash
ssh soukmind-tx-root "echo 'SHOP_AUTH_TOKEN_STORE_BY_REALM_OPERATOR=db' >> /opt/ai-shop/shop-app.env"
```

**名字必须逐字是这个。** 写错不会有任何报错，那一行等于注释，
而你会以为切过了 —— 今天早上 `JOB_WORKER_START_DISABLED` 就是这么白写的。
`TokenStoreSelectionEnvTest` 钉的就是这个名字。

`SHOP_TOKEN_STORE=ehcache` 那一行**不要动**：C 端与 B 端还得用它。

### 3.3 重启并验证

```bash
ssh soukmind-tx-root "systemctl restart ai-shop"
```

三条判据，缺一条都算没切成：

| 看什么 | 期望 | 不对时说明 |
|---|---|---|
| `grep '会话存储按端装配' /var/log/ai-shop/app.log \| tail -1` | `{CONSUMER=ehcache, MERCHANT=ehcache, OPERATOR=db}` | 没这行 = 按端开关没生效，检查变量名 |
| 运营登录一次后 `SELECT COUNT(*) FROM ops_session` | ≥ 1 | 0 = 会话还在写 ehcache |
| `SELECT event FROM ops_login_log ORDER BY id DESC LIMIT 1` | `LOGIN` | 空 = 审计没接上 |

还要确认 **C 端没被误伤**：`SELECT COUNT(*) FROM usr_session` 应当仍是 **0**
（C 端会话还在 ehcache 里）。这一条不是形式 —— 它是「只切了一端」的唯一硬证据。

### 3.4 回滚

```bash
ssh soukmind-tx-root "sed -i '/SHOP_AUTH_TOKEN_STORE_BY_REALM_OPERATOR/d' /opt/ai-shop/shop-app.env && systemctl restart ai-shop"
```

代价：运营端**再重登一次**。`ops_session` 里的行留着不用管，下次切回来还能用
（除非过了 TTL）。

## 4. 观察一天再往下

看这三个数，任何一个不对就先别推进：

- `ops_session` 行数：应当约等于「在线的运营人数」，不应当只增不减
  （`DbTokenStore` 到期会清；只增说明清理没跑）
- `ops_login_log` 里 `LOGIN_FAILED` 的比例：切换后短时间会升（旧令牌失效），
  **半小时内应当回落**。不回落说明有人一直在用旧令牌重试，前端没正确跳登录页
- `app.log` 里 `auth-revoke-poll` 相关的异常：撤销传播是每 5 秒一次的库查询，
  它出错不会影响登录，但会让「停用了账号却还能用」

## 5. 再切 B 端 / C 端

同一套动作，把变量名换成 `..._MERCHANT` / `..._CONSUMER`。

**C 端那一批挑低谷**：它是全量用户，掉线代价与前两批不在一个量级。
B 端如果 A7（改发 `btk_`）也要做，两件事**可以并成一次切换**，省一次全员重登。

## 6. 切完之后仍然不能多实例

会话进库只是**必要条件**。这四个还在进程内：

`InMemoryRateLimiter`、`OtpStore`、`CaptchaService`、`PasswordResetTokens`

起第二个实例会出现：限流按实例各算一份、验证码在 A 实例发 B 实例验不过。
记在 ADR-015 §3.1。**别据此排期。**
