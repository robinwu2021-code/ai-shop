**批⑤ 的两处结论与原计划不同，都是动手之后才看清的：**

**P1-3 从「合并 cutoff」改成「定名分家」。** 原判据是「两个 `cutoff_at` 只有一个有人写」。
批③ 给 `prd_goods.cutoff_at` 补上写入路径之后，这个判据不成立了 —— 它们是两件真实存在的不同事：
商品级是**商家对买家的日常截单承诺**（「今天 18:00 前下单」），SKU 级是**平台配的预售采购闸门**
（`lockPresale` 的 WHERE 条件）。**责任人不同**：前者商家改，后者只有运营能改。
合并会把两者揉成一个，比同名更糟。改为在两个实体上互相指认，把「同名不同物」写死。

**P2-4 的真口子不在登记表，在两条查询上。** 补登 `prd_sku` 之后守卫立刻报出
`PlatformProductServiceImpl#listSkus` / `#listOversellSkus` **直接检索 prd_sku 且显式绕过数据域** ——
那才是「不带过滤条件的 `GET /ops/skus` 是全平台可见」的真正原因，光登记表拦不住。
两条已去掉绕过。前置的买家侧豁免（`loadSkus` / `snapshot` / `StockPort` 五处原子扣减）一并补齐 ——
少豁免一处的症状是**商品显示 ¥0 / 购物车空 / 下单说库存不足**，且日志干净。

**P1-2 只做了 TDD 更正，没有改端点路径。** `ops-web` 那一层早有注释写明
「后端解析到父商品再执行，路径保持 SKU 粒度是为了不改这一层与页面」—— 那是一个已记录的决定，
没有足够理由推翻。改的是 `TDD-ops-商品与类目` §2.2 里那台**不存在的 SKU 状态机**
（`DRAFT → PENDING → ON_SALE ⇄ OFF_SALE`，真库 `prd_sku` 没有状态列），
并写明「对一行点驳回 = 整件商品被打回」这个作用域。**UI 上的作用域提示仍未加**，是这条唯一的余项。

**P3-5 的处置改了**：原计划「补齐或从契约删掉」。实际动手时发现 `slots` / `card` /
`virtual` / `promotions` 被 c-app 的**五个页面**渲染着（分类 / 首页 / 搜索 / 商品 / 店铺），
删字段要同时改五处渲染，而「卡券与虚拟商品是不是商家自助能建的东西」还没有产品结论 ——
那是产品决策不是机械清理。改为在契约上逐条标注「**后端未下发**」，把差异摆到读代码的人眼前。

### P0-1 每次保存商品都会清空详情轮播图

| | |
|---|---|
| 位置 | [MerchantGoodsServiceImpl.java:361](../../../backend/shop-core/src/main/java/ai/neargo/shop/product/service/impl/MerchantGoodsServiceImpl.java) · [goods-edit/index.vue:589](../../../b-app/src/pages/goods-edit/index.vue) |
| 现象 | 编辑任何一件有轮播图的商品 → 保存 → `prd_goods.images` 变成 `[]`，C 端详情页只剩封面 |

根因是两处叠加：

```java
// 后端：无条件覆盖，null 被 writeJson 变成 "[]"

```
```ts
// b-app：提交体里压根没有 images 这一项（契约 GoodsDraft.images 是有的）
await api.mSaveGoods({ goodsNo, title, subtitle, type, categoryNo, cover, specGroups, skus });
```

与 `fulfillments` 的处理**恰好相反**：那边写了 `if (cmd.fulfillments() != null)`，所以不传 = 不改。
`images` 少了这一层判断，于是「不传」被当成了「清空」。

**处置**：
1. 后端加 `if (cmd.images() != null)`（与 `fulfillments` 同一形状）——先止血，一行。
2. b-app 商品编辑页补轮播图上传区（复用 `mUploadImage`），提交时带上 `images`。

**验收**：建一件带 3 张轮播图的商品 → 只改标题保存 → 详情仍是 3 张。

## P1 · 模型错位

### P1-1 品类改为类目派生（本轮结论的落地）

**目标**：录入上一个输入点（类目），存储上两个（`category_no` 权威 + `type` 只读快照）。

三个**前置条件**，不补齐就改会出事：

| # | 前置 | 不补的后果 |
|---|---|---|
| a | 类目树补 `VIRTUAL` 分支与 `template='VIRTUAL'` | `TEMPLATE_TO_TYPE` 只有 4 组映射，**虚拟商品再也建不出来** |
| b | `template` 从根继承到叶，子节点不可改 | 父 FRESH、子 STANDARD 现在无人拦，换个地方继续打架 |
| c | 存量 `category_no IS NULL` 的商品先回填 | 留着空值，「品类由类目推出」就有例外，例外迟早变通路 |

**改动顺序**：迁移（a+b+c）→ 后端 `SaveCommand` 去掉 `type`、按 `categoryNo` 查 `template` 派生 → b-app 删 `type` 下拉、类目改必填、形态改只读展示。

⚠️ 后端那步不能省：只改前端的话接口仍收 `type`，下一个接进来的人照样能传矛盾值。

**同时收敛命名**：`STANDARD↔NORMAL`、`VOUCHER↔CARD` 是历史遗留（`sys_channel_category_rule` 的 `GOODS` 已由 `V12` 刷成 `NORMAL`，这两组是仅剩的）。刷成同码后 `TEMPLATE_TO_TYPE` 这张映射表可以删掉。

**验收**：建品页只有一个分类控件；构造一次「叶菜类目 + NORMAL」的请求 → 后端忽略 `type` 并写入 FRESH。

### P2-2 库存在多市场行里冗余存储，靠约定同步

`prd_sku` 是「一市场一行」，而**价格分市场、库存不分市场** —— 于是 `stock` / `locked_stock` / `presale_quota` / `sold_count` 这四列在 N 行里各存一份相同的值。

原子扣减的 SQL **不带 market 条件**：

```sql
UPDATE prd_sku SET locked_stock = locked_stock + #{qty}
WHERE sku_no = #{skuNo} AND deleted = 0 AND stock - locked_stock >= #{qty}
```

今天是对的（一次更新 N 行，值一致），但正确性依赖「所有市场行的库存永远相同」这个**没有任何约束保证的约定**。一旦有一行漂了，条件逐行判定会出现**部分成功**，而 `affected > 0` 仍被判为锁定成功。

一期只有 CN，风险为零；开第二个市场的那天它会同时变成超卖和少卖两种故障。

**处置**（按代价排）：
1. 最小：在 `SkuMapper` 与 `PrdSku` 上写死这条约定，加一个「各市场行库存一致」的断言测试。
2. 正确：把库存四列从 `prd_sku` 拆到 `prd_sku_stock(sku_no)` 一行 —— 让「库存不分市场」从约定变成结构。

建议**开第二个市场之前必须做 2**。

## P3 · 口子与漂移

### P3-1 `/biz/spec-templates` 没有权限注解

[BizGoodsController.java:132](../../../backend/shop-core/src/main/java/ai/neargo/shop/product/api/biz/BizGoodsController.java) 的 GET 与 POST 都没有 `@PreAuthorize`，而同一个控制器里其余端点都有（`BizPerms.GOODS` / `STOCK`）。配送员、客服这类子账号能读写规格模板。

**处置**：两个都加 `@PreAuthorize("@perm.canBiz('" + BizPerms.GOODS + "')")`。

### P3-2 `/biz/goods` 不支持按类目筛

Service 支持 `categoryNo`，控制器写死传 `null`（与已修复的 `keyword` 是同一种遗漏）。类目变必填之后，按类目筛是商家找货的主路径。

### P3-3 B-4.1 的「缺货」筛选没有实现

需求写「在售 / 下架 / **缺货** 分筛」，后端 `applyStatus` 只有四态，b-app 页签也只有四个。口径已经现成（`outOfStockCountByStore` 用的是 `stock − locked ≤ 0`）。

### P3-4 死列

| 列 | 状态 | 处置 |
|---|---|---|
| `prd_goods.points_config` | 实体有字段，全仓无读写 | 接上（随积分域）或标 `RESERVED` |
| `prd_goods.sellable_override` | 同上；端可售实际走 `sys_channel_category_rule` | 同上 |
| `prd_category.attr_template` | 有列无消费 | **P0-4 正好需要它** —— 接上 |

死列本身不贵，贵在它们看起来像已经实现的能力。

### P3-5 shared 契约声明了后端不发的字段

`packages/shared` 的 `Goods` 上有 `slots` / `card` / `virtual` / `promotions` / `points`，`GoodsVO` 一个都没有。端上按契约写完了渲染，永远拿到 `undefined`，落进兜底分支，不报错。

与 P0-4 是同一个洞的两侧：一侧没有写入，一侧没有下发。**要么一起补，要么从契约里删掉**——留着最糟。
