## 零、已经定死的五条

这五条是后面所有改动的前提，不再讨论：

| # | 结论 | 为什么 |
|:--:|---|---|
| 1 | **类目是唯一分类输入，品类由它派生** | 两个输入点必然出现「叶菜类目 + 日用品品类」这种没人拦得住的矛盾 |
| 2 | **平台类目两级** | 三级让「商家选自己卖哪几类」这一步无法存在；叶菜/根茎菜的粒度对社区电商没有用 |
| 3 | **商品挂主体，ADR-011 不动** | 多门店是连锁不是独立摊位。下沉商品要付六条代价，而三个诉求都不需要它 |
| 4 | **建品看主体，上架看门店** | 门店类目约束落在 `prd_store_goods` 这一层，与资质校验同一个位置 |
| 5 | **标准品是「复制 + 溯源」** | 一期不做回流；`std_no` 那条线是聚合与统计要用的东西 |

### 批 B · 进件授码合一（迁移 `V169`）✅ 已落地

| # | 改动 | 为什么 |
|:--:|---|---|
| B1 | 加 `mch_entity_apply.category_codes` JSON 数组，与 `category` **并存** | 商家填「食品」是他的说法，码是平台的裁定。合成一列就分不开了，而追溯要的恰恰是两者的差 |
| B2 | `POST /ops/merchant/apply/{no}/audit` 收 `grantCodes`，与 `setCodes` **同一事务** | 见下 |
| B3 | `PUT /ops/merchants/{no}/auth-codes` 响应改为 `{codes, revoked, affected}` | 撤码时运营要看得见代价。**ops-web 的 mock 此前比后端严**（有在售商品就拒），已一并对齐 |

> **B2 是这批里最要紧的一条。** 现在「审核通过」与「授予经营类目」是两个动作，
> 于是存在一个中间状态：**通过了，但一个码都没授**。商家收到通过通知，
> 进去建品、点上架被拒，看到的是「你还没有资质授权」——去哪申请没人告诉他。
> 与 [类目树补齐方案](./类目树补齐方案.md) §五① 记的是同一类事：
> **一个只会拒绝的校验比没有校验更糟，它看起来在工作。**

### 批 C · 门店定价（迁移 `V170`）✅ 已落地

| # | 改动 |
|:--:|---|
| C1 | `prd_store_price(store_no, sku_no, entity_no, market, price, origin_price)` 建表 |
| C2 | **取价入口 `GoodsQueryPortImpl.snapshot()` 加门店价覆盖** |
| C3 | `GoodsVO.SkuVO` 增 `storePrice`（只在 B 端下发）；B 端详情按当前门店回填 |
| C4 | `POST /biz/goods/{goodsNo}/store-price`，与 `store-stock` 同形状。**挂 `biz:goods` 不是 `biz:stock`**（定价权 ≠ 补货），`price` 传空 = 取消本店定价 |

> **一处刻意留白**：C 端的商品列表与详情**仍显示主体价** —— 那条路径没有门店上下文
> （商品挂主体，门店由下单时的自提点定）。门店价在<b>结算那一步</b>生效，而预览与
> 下单共用 `split()`，两者必然一致。真要让买家在商品页就看到本店价，需要 C 端先有
> 「当前门店」这个概念（店铺页），那是另一件事，不在批 C 里假装做掉。

⚠️ **回退方向与库存相反，这是唯一不同构的地方**：

| | 无门店行时 | 理由 |
|---|---|---|
| 门店库存 | **视为 0**（fail-closed） | 回退主体总量 = 没配过的店无限供应。少卖可恢复，超卖不可 |
| 门店价格 | **回退主体价**（fail-back） | 视为 0 就是白送 |

照抄库存写法的症状：一家没配过价的店把所有货以 ¥0.00 卖出去，页面上看着像 bug，钱已经出去了。

C2 不能省：只改展示不改 `snapshot()`，症状是**页面显示门店价、下单按主体价扣钱** ——
与「购物车显示特价、下单按原价」同一形状。叠加顺序：门店价是基准价，限时特价仍覆盖它。

### 批 D · 商品生命周期（迁移 `V171`）✅ 已落地

| # | 改动 | 为什么 |
|:--:|---|---|
| D1 | `audit_status` 增 `DRAFT`；新建默认 `DRAFT`，显式「提交审核」才进 `AUDITING` | 现在**保存即提审**：商家填一半点保存就进了运营的待审队列 |
| D2 | `auditQueue` 排除 `DRAFT` | 队列里混着半成品，运营分不出哪些真要审 |
| D3 | 已上架商品的编辑：改完仍回 `AUDITING`（**一个字没动**）。草稿态只对新建与草稿本身生效 | 「改成别的东西再卖」这条路仍然堵着。给已过审商品做「改动暂存」需要一套版本/影子记录，不在批 D 里假装做掉 |
| D4 | `prd_goods.detail` 图文详情（长文本 + 图地址） | 现在只有轮播图，没有「详情描述」那一段 |
| D5 | `POST /biz/goods/{no}/presale`：只改截单与到货说明，**不触发重审、不下架** | 走 `save()` 的话改一次截单等于停一天生意（重审期间商品是下架的）。非生鲜调它直接拒 —— 那是一次没人会读的写入 |

> **一处已知的松口**：运营仍能直接对草稿调 `/ops/goods/{no}/audit` 把它审过 ——
> 队列里看不到它，只有手工构造请求才到得了。没堵是因为堵它要让所有「建品 → 过审 → 上架」
> 的链路都先提交一次，而它的实际风险为零：商品要不要卖仍由商家自己按上架。
>
> D1–D3 互相咬合：正因为没有草稿，D3 那条「改完回待审」的代价才被放到最大 ——
> 商家连「改完一起提交」都做不到。

## 六、守卫与验收

### 要同步更新的守卫

| 守卫 | 为什么会红 |
|---|---|
| `BizEndpointPermTest` | 新端点（门店类目 ×3、门店价、提审、改截单）都要登记权限 |
| `ops-data-scope.test.ts` | `mch_store_category` / `prd_store_price` 要登记 MERCHANT 锚点 `entity_no` |
| `MediaRefCoverageTest` | 主题封面 `prd_topic.cover`、图文详情里的图地址要进 `MediaRefSource`，否则会被当孤儿回收 |
| `enum-registry` | 新状态词 `DRAFT` 要登记（词典 §11 里它已经有定义：「作者还在编辑，没人在等它」） |
| `ops-role-endpoint-matrix.json` | 新的 ops 端点与角色映射 |
| `entity-alignment` | 每加一列都要同时补 Java 实体字段，否则那一列永远读出 null |

### 验收（每条都要能自己红）

**分类**
1. 平台类目建到第三级 → 拒绝
2. 建店选一个主体未授权的类目 → 拒绝，且报错里说得出缺哪张证
3. 建品选一个本店没加、主体已授权的类目 → **自动加入**
4. 建品选一个主体未授权的类目 → **建品这一步就拒**（不等到上架）
5. 商品类目不在本店类目里时上架 → 拒；同一商品在另一家有该类目的店上架 → 成功
6. 删一个底下还有商品的门店类目 → 拒绝

**进件**
7. 审核通过但不勾任何类目码 → 拒绝提交（不允许「通过了什么都上不了架」）
8. 撤销授权码 → 已上架商品**不变**，响应里报得出影响件数

**定价**
9. 未配门店价的店 → 读回**主体价**（不是 0）
10. 配了门店价的店 → 下单扣的是门店价（断言落在 `snapshot()` 上，不是页面）

**生命周期**
11. 新建商品落 `DRAFT`，**不进** `auditQueue`
12. 显式提交后进 `AUDITING`

**主题**
13. 一件商品同时在两个专题里 → 两边都查得到（多对多，与类目正交）

## 八、假设与待决

以下按**我的建议**写进方案，动手前确认一次即可（不确认也能开工，改起来是局部的）：

| # | 事项 | 方案里按什么写的 |
|:--:|---|---|
| Q1 | 门店类目可以一个都不选吗 | **可以**，建品时自动加入 |
| Q2 | 审核通过必须授码吗 | **必须**（验收第 7 条就是它） |
| Q3 | `apply.category` 改数组后，存量怎么回填 | **需要人工映射规则** —— 这条真的要人答，自由字符串没法自动翻译成码 |
| Q4 | 第二家店默认复制默认店类目吗 | **复制** |
