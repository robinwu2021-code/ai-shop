# 登录与 openid —— 现状梳理

状态：**现状记录（非设计提案）** · 2026-08-22（§6 缺口一已修）
关联：[TDD-小程序登录打通](./TDD-小程序登录打通.md) · [TDD-手机号授权与自动登录](./TDD-手机号授权与自动登录.md)

> 这篇不提新方案，只回答一个问题:**今天线上到底是怎么登录的**。
> 每一条都在生产环境或生产库上核过，核的办法写在旁边 ——
> 「设计上应该如此」和「线上确实如此」在这个项目里已经分开过太多次。

---

## 1. 一句话

小程序**打开即登录**：`wx.login` 拿一次性 code → 后端换 openid → 按 openid 认人 →
认不出就建户 → 发 token。**全程零点击，也不需要微信认证**。
手机号是登录之后的**可选补绑**，不是登录的前提。

---

## 2. 默认登录逻辑（端上视角）

```
小程序启动
   │
   ├─ App.vue onLaunch ──► user.silentLogin()          ①「顺手认一下」，失败不打扰
   │                          │
   │                          ├─ 已有 token 且非 force ──► 直接当作登录着
   │                          └─ 否则 wx.login() ──► POST /mp/auth/login
   │                                                   { grantType: "WX_MINI",
   │                                                     principal: <code> }
   │
   ├─ 首页 onShow ──► ensureIdentity()
   │                    ├─ 等静默登录落地
   │                    └─ **总是** loadProfile()      ② 不信本地快照
   │
   └─ 任一请求 401 ──► clearSession() → silentLogin(force: true)   ③ 换一个新的
```

三处**都是被具体故障换来的**，不是设计上的讲究：

| # | 不这么做会怎样 | 怎么发现的 |
|---|---|---|
| ① | 失败弹窗 → 网络抖一下就挡住「逛」这件事 | 设计时就定的：静默失败必须静默 |
| ② | 只信本地快照 → **账号已注销，端上仍显示登录着**，且一个请求都不发 | 注销流程真机实测 |
| ③ | 不先扔旧 token → `silentLogin()` 第一句 `if (this.token) return true` 把 401 吞掉，**卡在拿着死令牌的假登录态** | 注销后重开小程序，生产库账号数纹丝不动 |

还有一处赛跑:启动请求（购物车、资料）与静默登录同时发车,**先到的那个会拿 401**。
不等它就会把人 reLaunch 到登录页 —— 而一秒后静默登录成功了,
**token 有了、账号也建了,他看着的却是登录页**（2026-08-22 automator 抓到:
token 长度 36、生产账号数 1→2,当前页却是 `pages/login/index`）。
现在 401 处理器先 `await` 那个飞行中的 promise 再决定。

## 3. openid 是怎么拿到的

### 3.1 三条路，为什么走中间这条

| 方案 | 拿到什么 | 前置条件 | 现状 |
|---|---|---|---|
| `wx.login` + `code2Session` | openid（+ unionid） | **无** | ✅ **正在用** |
| `getPhoneNumber` 一键授权 | openid + 手机号 | 微信认证 300 元 + 按次计费 | ⛔ 未认证，端口留着（`WX_PHONE`） |
| 手机号 OTP | 手机号 | 短信通道 | ✅ 兜底，排第二 |

选第一条还有一条链路上的理由：**微信支付 JSAPI 下单必须带 openid**。
先拿到,商户号下来时支付能直接接,不用回头改登录。

### 3.2 服务端这一段

```
POST /mp/auth/login  { grantType: "WX_MINI", principal: <js_code> }
        │
        ▼
AuthServiceImpl.resolveCredentials()
   case GRANT_WECHAT_MP, GRANT_WX_MINI ──►  WxAuthPort.codeToSession(code)
        │                                        │
        │                                        ├─ WxAuthGateway（真）  GET /sns/jscode2session
        │                                        └─ StubWxAuthGateway    openId = code 原样返回
        ▼
   凭证列表（**按识别强度排序**）
     1. WX_UNIONID   ← 只有绑了开放平台才有
     2. WX_OPENID_MP
        │
        ▼
   findOrCreate() —— 依次找人，找不到才建户，
   并把本次新出现的凭证补登记上去
```

`WX_MINI` 与 `WECHAT_MP` **是同一个分支的两个名字**：端上分三种微信场景
（小程序 / 开放平台 / 一键手机号）,后端 code2Session 这一条对前两者是同一个端点。
这条对账挂在 [enum-alignment.test.ts](../../../packages/shared/tests/enum-alignment.test.ts)。

`session_key` **刻意不返回也不落库** —— 它是解密敏感数据的密钥,当前链路用不到,
存一个用不到的密钥只是多一处泄露面。

### 3.3 桩与真通道：一个必须盯住的开关

`shop.wx.login.stub=true` 时,`openId = jsCode` 原样返回。

**而 `wx.login` 的 code 每次启动都不一样** —— 于是桩模式下
「每开一次小程序就建一个新账号」,订单、卡券、积分每次清零,
**不报错、不空白,只是他的东西不见了**。

桩不是随便编的假数据,它精确保存了接 code2Session 之前的既有行为
（那时确实把 code 当 openid 存）。但它**只能用于本地**。

线上核对（2026-08-22）：

```
SHOP_WX_LOGIN_STUB=false          ← 真通道
WX_APPID=wxdb0513c549437ffe

usr_identity 里的 WX_OPENID_MP：长度 28、形如 o8p1M3…_Zq4
```

28 位、`o` 开头 —— 是真 openid,不是 code。**这条是本文唯一能证明
「openid 链路真的通了」的证据**，TDD-小程序登录打通 §6 最后一个未打勾项到此闭合。

## 4. 认人的规则

身份存在 `usr_identity`（一个账号多条凭证），登录时**按识别强度依次找**：

| 强度 | 凭证 | 说明 |
|---|---|---|
| 1 | `WX_UNIONID` | 跨应用稳定。**线上目前一条都没有** —— 小程序未绑开放平台 |
| 2 | `WX_OPENID_MP` | 按应用隔离；换成 App 或公众号就是另一个值 |
| — | `PHONE` / `PASSWORD` / `APPLE_SUB` | 各自入口 |

「返回列表而不是单个」是与旧实现最本质的区别：旧版每次只拿一个凭证、只按那一个查,
**同一个人换个入口就变成新账号**。

⚠️ **没有 unionid 的后果**：将来上 App 或 H5 走微信开放平台登录时,
同一个人会被当成**两个账号**。要避免就得先在微信开放平台绑定这个小程序 ——
绑定之后新登录才带 unionid,**已有账号不会自动合并**。

## 6. 查到的缺口

### 缺口一：万能验证码的守卫在生产上不生效 —— **已修（2026-08-22）**

`shop.auth.otp.fixed` 一旦设值,**任何人都能用它登进任意手机号**。
三道防线里第三道是「prod profile 下拒绝启动」（`FixedOtpGuard`），
而它认的是 `prod / production / prd`。

**问题比「漏写一个名字」更深**：

- 生产跑的是 `api,ops` —— 三个名字一个都不沾
- **本地开发也跑 `api,ops`** —— 判据两边取值相同

所以不是漏了一个别名，是**这个判据在本项目里区分不了任何东西**。
这道「最后一道闸」从上线第一天起就是空的，且**空得毫无症状**：
单测全绿（测试自己造了个叫 `prod` 的 profile），线上照常启动。
测试里那句 `run("123456", "api")` 断言的是「照常启动」——
**那恰恰就是生产的形状，这个断言当时是绿的，而线上是敞开的**。

**改法：换成能力判据 `shop.sms.stub`**（本地默认 `true`，生产 `false`）。

选它不只因为取值不同，而是两者**语义上本来就互斥**：预设码是用来
**替代短信通道**的。短信是真的、却还留着一把万能钥匙，只有一种解释 ——
这是一台正在给真实用户发码的机器。

它也扛得住原注释点名的那条主线（**配置继承**）：把测试环境的 env 拷到生产，
想让预设码生效就得连 `SHOP_SMS_STUB=true` 一起拷，而那会让**所有真实用户
都收不到验证码** —— 一个当天就会被发现的响亮故障，而不是
「系统一切正常，只是所有人的账号都是公开的」。

profile 那条留着当兜底，不再是主判据。

用例见 [FixedOtpGuardTest](../../../backend/shop-app/src/test/java/ai/neargo/shop/config/FixedOtpGuardTest.java)（7 条），
其中三条是新判据：生产实配拒绝启动 / **profile 完全不设也拒绝** / 真短信但没设预设码必须能起。
把主判据改成 `if (false)` 撤掉验过，前两条当场变红。

> ⏳ 线上当前**未设** `SHOP_OTP_FIXED`，所以本次改动不影响启动；
> 守卫随下次部署生效。

### 缺口二：真机连不上后端（与登录无关，但挡住一切验证）

`hxmall.top` 整域在 443 被按 SNI 拦截（不带 SNI 能握手,带 SNI 被掐）,
属备案未通过的典型症状。小程序真机强制 HTTPS + 已备案域名,
所以**目前只有开了调试的手机能测**。

### 缺口三：拿到 openid 之后要不要强制绑手机号，未定

现在是「弹一次,可以『以后再说』」。Apple 登录那条分支留着同样的 TODO,
两者应该一起定。
