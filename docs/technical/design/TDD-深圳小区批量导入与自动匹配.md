# TDD-深圳小区批量导入与自动匹配

状态：**方案待拍板（有一条前置未知）** · 创建 2026-09-17 · 档位 2（动库表 + 批量作业 + 改变 C 端所见）

关联：[[TDD-C端位置选择-地址取代自提点]]（M5/M6 —— 这一单会改变 M6 的触发频率）

---

## L1 这一单要解决什么

线上此刻**全平台只有 1 个已开通聚落**（福民社区，福田）。
深圳任何地方的买家都落不进围栏，全靠 M6 绑到那一个 19 公里外的点。

要的是：把深圳的小区**批量建出来**，让买家落进自己那个小区。

---

## L2 ⚠️ 一条前置未知 —— 它决定这活是帮忙还是帮倒忙

**虹选鲜果的经营范围是 `COMMUNITY` 还是 `CITY`/`PLATFORM`？**

今天查不出来：全平台只有 1 个 OPEN 聚落，三种取值投影出来的池子**一模一样**
（`reachableCommunities` 里 CITY/PLATFORM 走 `openCommunityNos()`，
COMMUNITY 走显式列表 —— 而两者此刻都等于 `{福民社区}`）。

导入 1 万个小区之后，两条路分叉：

| 经营范围 | 导入后 | 龙华买家的首页 |
|---|---|---|
| `CITY` / `PLATFORM` | 池子铺到全部新小区 | 照样有货 ✓ |
| `COMMUNITY`（只勾了福民社区） | 新小区池子**全是空的** | **从「有货」变成「空」** ✗ |

也就是说：**这一单有可能把我们今天刚做好的效果整个抹掉**，而症状是首页空了，
看起来像导入失败，实际是导入成功了、货没跟过去。

查它要运营账号或库权限。**这是第一步，不是并行项。**

## L3 怎么做

### M1 · 先量一次高德按圆搜的召回上限（真正的工程量在这儿）

现成链路：`GeoService.around(关键词, 圆心, 半径, 类型)` → 高德 Web 服务
（生产已配 `AMAP_WEB_KEY`），`EstateCacheService.resolve(scopeCode…)` 按**街道**
抓一片、落 `geo_poi_cache`、7 天 TTL、整片覆盖不合并。

⚠️ **但它是为「商家挑一个小区」设计的，不是为「把一个区抓全」设计的**：
半径写死 3000 米、关键词只有「住宅小区 / 小区」、类目收紧到 `120300|120302|190108`。
高德按圆搜单次返回有上限，而深圳市中心一个街道的小区数**一定超过那个上限**。

所以第一步是**量**，不是写：挑福田某个街道跑一次，把返回条数与人工数出来的条数比。
- 差得不多 → 按街道扫就够
- 差很多 → 要网格化（把街道切成 ~800 米网格逐格扫）或换成「按行政区 + 分页」的接口

**不量就写，写出来的是一份看起来很满、实际系统性缺失的小区表** ——
而缺失的那些小区里的买家，会落到别人家小区的围栏里。

### M2 · POI → 聚落

新增一步批量建档（`geo_poi_cache` → `cmt_community`）：

| 列 | 取值 | 为什么 |
|---|---|---|
| `origin_code` | 高德 POI id | 唯一键，重跑幂等；没有它重扫一次就是一万条重复 |
| `source` | `MAP` | 与提报建出来的区分开，将来要单独回收时认得出 |
| `kind` | `ESTATE` | |
| `region_code` | 所属街道 9 位 | 按区筛（M5）与运营端聚合都靠它 |
| `fence_radius` | **300**，不是默认的 1000 | 深圳小区密集，1000 米会让一个点同时落进十几个围栏 |
| `status` | `OPEN` | 不 OPEN 就既不参与匹配也不进商品池，等于没导 |

### M3 · 导入之后必须重建商品池 —— **最容易漏的一步**

`MerchantGoodsService.resyncAllCommunityPools()`（已有）。

不做的话：新小区一个都没有池行，买家落进自家小区看到的是空首页 ——
**症状与「导入失败」完全一样**，而实际上导入是成功的。

## L4 边界与代价

### 规模：这个模型会在「全市开通」这一步撞墙

`prd_community_pool` 的行数 = 在售商品数 × 覆盖社区数。

| 商品数 | 深圳约 1 万小区 |
|---:|---:|
| 1 件（今天） | 1 万行 |
| 100 件 | 100 万行 |
| 1000 件 | **1000 万行** |

今天无压力，但**不要假装它不存在**：投影式可见性在「一个城市全开」这个量级上
要换成「按范围实时算」而不是预铺。这一单不解决它，只把它记下来。

### 对 M6 的影响

导入之后围栏命中率大幅上升，M6 的第 2 级（绑最近的聚落）退居备用 —— 那正是它该待的位置。

⚠️ 但**匹配到自家小区 ≠ 那儿有货**。如果 L2 那条查出来是 `COMMUNITY`，
一个解药是把 M6 改成「最近的**有货的**聚落」。那是另一个决定，这一单先不做。

### 不做

- **不碰** `sys_region`（区划是国标数据，小区不是区划）
- **不动**自提点：新小区一个自提点都没有，所以它们只能做配送/快递货。
  自提货在这些小区会被 M4 的 `PICKUP_POINT_NONE_FOR_MERCHANT` 挡住 —— 这是对的

## 验收判据

1. 抽 3 个街道，扫出来的小区数与人工在地图上数的**同一量级**（对照量：人工那份要真数）；
2. 重跑一次**不产生重复行**（`origin_code` 唯一键）；
3. 站在某个已知小区的坐标上，`/mp/location/resolve` 返回的是**那个小区**，
   而不是 19 公里外的福民社区；
4. **同一个坐标，导入前后首页的商品件数不减少** —— 这条是 L2 那条风险的闸门，
   它变红就说明经营范围那件事没解决；
5. **消融**：`fence_radius` 改回 1000 → 判据 3 在密集区变红（一个点落进多个围栏，
   选出来的不是最近那个）。
