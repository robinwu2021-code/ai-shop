## 一、现状（2026-09-21，0.1.54）

下单只有**一页**：`pages/order-confirm`。它既是编辑页也是确认页，而能编辑的只有
地址、履约方式、券、积分、备注、发票 —— **数量改不了**（要退回购物车），
**支付方式在页面上但只有两种**（线上 / 当面付），券那一行在没有可用券时是灰的、点了没反应。

金额由后端 `POST /mp/order/preview` 算，任何一处改动都重算一次；提交走 `POST /mp/order`，
成功后直接进收银台（`pages/pay`）。

已经具备但端上没用起来的后端能力：

| 能力 | 端点 | 现状 |
|---|---|---|
| 最优券试算 + **不可用券及原因** | `POST /mp/coupon/best` | 后端做了，端上没调（挂在「后端做了没入口」清单上） |
| 我领到的券 | `GET /mp/coupon/mine` | 2026-09-20 刚接上 |
| 优惠依据（活动名 / 券名 + 各减多少） | 预览与订单详情的 `discountLines` | 2026-09-20 刚接上 |

## 二、流程：一页下单，直接支付

用户 2026-09-21 定了：**主流电商已经没有「确认订单」这一步，在下单页直接支付**。所以不做确认页、也不做确认层。

```
商品详情 / 购物车
      ↓
┌──────────────── 下单页（唯一一页）────────────────┐
│ 收货方式与地址 · 商品行（可改数量）· 优惠券       │
│ 积分 · 备注 · 发票 · 支付方式                     │
│ ─────────────────────────────────────────────── │
│ 底栏：应付 ¥35.00（已省 ¥15.00）  [ 立即支付 ]    │
└───────────────────────────────────────────────────┘
      ↓ 一次点击：建单 + 拉起微信支付
   支付结果页
```

**现状比这多一跳**：提交后先落到收银台页（`pages/pay`），在那儿再点一次「立即支付」才拉起微信。
那一页的存在理由是「待付款订单的二次支付入口」——但它不该出现在**首次**下单的路上。

改法：

- 下单页底栏按钮直接是「立即支付 ¥35.00」，点一次完成两件事：`POST /mp/order` 建单 → 拿返回的支付参数立刻 `requestPayment`。
- **收银台页保留，但只在两种情况下进**：① 支付被中断 / 失败（返回时落到它，带倒计时）；② 从订单列表点「去支付」。
- 建单成功但拉起支付失败（banned、网络断）→ 直接跳收银台页并说清原因，订单已经在那儿，不会丢。
- 当面付（线下付款）没有「拉起支付」这一步：点「提交订单」后直接进订单详情，按钮文案随支付方式变。

## 三、下单页：六个区块

### 1. 收货方式与地址（物流信息）

| 方式 | 要选什么 | 页面上给什么 |
|---|---|---|
| 快递配送 | 收货地址 | 地址卡；没有地址时整卡变成「添加收货地址」 |
| 商家自送 | 收货地址 | 地址卡 + 「超出配送范围」时当场拦住并说清 |
| 到店自提 | 自提点（后端按地址配） | 点名 + **离你多远**（已落地）+ 太远提示 |
| 邻里自提 | 团长家（团单专用） | 只显示，不可改 |
| 到店核销 | 无 | 显示门店地址与营业时间 |

**方式列表由后端给**（商品支持哪些履约方式是商品属性），端上不写死；只有一种时不显示切换器。

### 2. 商品行（可改数量）

- 步进器，上限 = `min(库存, 每人限购剩余)`；到上限时加号压暗，**旁边说清是哪一条挡住的**。
- 改数量 → 防抖 300ms → 重新 `preview` → 金额与优惠明细整体刷新。
- 刷新期间**旧金额保留并压暗**，不闪成 0；失败时回到上一次成功的金额并提示。
- 数量改到 0 = 移出本单（不动购物车）；最后一件移出时整单不可提交。
- 售罄 / 下架的行标灰保留，给「移出」。

### 3. 优惠券（含平台活动）

面板分三段，**这三段回答的是三个不同的问题**：

```
自动参与的活动（不用选）
  活动「开业直减」  −¥10.00      满 ¥30 可用 · 商家出资
  ↑ 平台活动同样列在这里，显示活动名称

可用券（2）
  满 30 减 5        −¥5.00       全场 · 满 ¥30 · 至 09-27   [选中]
  新人首单券 ¥3     −¥3.00       全场 · 无门槛 · 至 09-30

不可用（2）
  生鲜满减 ¥8                    还差 ¥20.00 到门槛
  张记粮油 ¥10                   本单没有这家店的商品
```

- **不可用的券必须列出来并给原因** —— 券在他券包里，不列等于「券丢了」。
  数据源是已有的 `POST /mp/coupon/best`（它本来就返回 `unusable` + `reason`）。
- **平台活动不是券，但要出现在同一个面板里**：买家问的是「这 10 块哪来的」，
  他不关心它在后端属于券还是活动。活动那一段标明「自动参与，无需选择」。
- 原因文案要给**可操作的差距**（「还差 ¥20.00」），不是「不满足使用条件」。
- 券与活动能不能叠加由后端算（现在的口径：先活动、后券，券作用在活动后的金额上），
  端上只展示结果。

### 4. 积分抵扣

- 一行开关 + 「可抵 ¥2.00（200 分）」；不足门槛时说清差多少。
- 抵扣上限是券后金额的固定比例（已有规则），抵不满时要说明白为什么。

### 5. 支付方式

- 微信支付（默认）/ 当面付。可选集由 `orderCapability` 给。
- **当面付与平台券互斥**（平台出资要走资金流补给商家，线下没有资金流）。
  选了平台券再切当面付时，**当场说清「切换会取消这张券」**，而不是提交时才报错。

### 6. 备注 / 发票

维持现状，收进一行。

## 四、金额与优惠的时序

```
任一编辑 → 防抖 300ms → preview（带 seq 号）
   ├─ 返回 seq 过期 → 丢弃（用户还在改）
   ├─ 成功 → 金额 + discountLines 一起换
   └─ 失败 → 保留上一次成功值 + 顶部提示「金额可能已变，提交时以实付为准」
```

提交时后端**再算一次**，以后端为准：券可能在这几分钟里被别处用掉、活动可能刚结束。
前后不一致时提交失败并说清哪一条变了（现在是一句笼统的报错）。

## 五、异常与边界

| 情况 | 现在 | 方案 |
|---|---|---|
| 库存变少 | 提交时报错 | 预览就带回可买数量，当场把数量压到上限并提示 |
| 券被用掉 / 过期 | 提交时 40002 | 提交失败时指名哪张券，并自动取消选择后重算 |
| 活动刚结束 | 金额变化无提示 | 预览返回的 `discountLines` 少了那条 → 顶部提示「XX 活动已结束」 |
| 地址超出自送范围 | 提交时拦 | 选地址那一刻就拦，并给「换地址 / 换配送方式」两条出路 |
| 一单多商家 | 已拆单 | 确认层里按商家分组显示，说清「会生成 N 笔订单」 |

## 六、落地顺序（每批都能单独上线）

1. **券面板**（接 `/mp/coupon/best`）：可用 / 不可用 / 活动三段 —— 这是用户这次最直接的诉求。
2. **数量可改**：步进器 + 重算 + 上限提示。
3. **一键支付**：底栏按钮直接建单并拉起微信支付，收银台页退回「二次支付入口」。
4. **支付方式与互斥提示**：当面付与平台券的冲突提前说。
5. 异常分支逐条补（表里那五条）。

## 七、已定与待定

**已定**（用户 2026-09-21）：
- 一页下单，底栏直接支付，不做确认页 / 确认层。
- 数量在下单页可改 —— 代价是每改一次都要重算优惠，券可能因此失效，所以要那条提示。
- 券面板要列出平台活动的名称与原因。

- 支付方式默认记住上一次的选择吗？建议记住，但当面付不记（它受商家与券的限制，默认回到微信支付更稳）。

## 八、整套下单逻辑（从点「立即支付」到退款）

状态模型不在这里重复定义，见 [订单状态·统一整理](../reference/订单状态-统一整理.md)：
**6 个抽象状态 × 履约方式**，履约方式加多少种，状态都是那 6 个。

```
WAIT_PAY ──付款成功──▶ WAIT_FULFILL ──交付方行动──▶ FULFILLING ──交接完成──▶ COMPLETED
    │                                                                        │
    │ 超时 / 主动取消                                             售后通过    │
    ▼                                                                        ▼
CANCELLED                                                               REFUNDED
```

### 8.1 建单（点「立即支付」的那一刻）

一次请求里按顺序做完，任一失败整笔回滚：

1. **拆单**：按商家拆成 N 张子单（一次支付覆盖这 N 张）。
2. **锁库存**：按行锁（`LOCKED`），不是直接扣 —— 没付款的单不该真的减掉库存。
3. **算钱**：活动（自动）→ 券（用户选的，作用在活动后的金额上）→ 积分抵扣。
   **以这一刻后端算的为准**，端上预览只是给人看的。
4. **占用**：券置为「使用中」、积分流水记 `PENDING`、活动配额 `quota_used +1`、
   预约时段占位、`pmt_apply` 落一行（这行就是后来「优惠依据」的来源）。
5. **落库**：主单 + 子单 + 行 + 状态日志（`WAIT_PAY`）。
6. **返回支付参数**：端上立刻 `requestPayment`。

幂等：请求带 `idempotencyKey`，重复提交返回同一组订单，不会建两笔。

### 8.2 支付成功

微信回调与端上「支付成功」两条路**都指向同一段代码**（`markPaid`），它自身幂等
（已经是 PAID 就直接返回）——用户连点两下、回调重发，都不会推乱。

一笔付款成功要做的事：

1. 主单转 `PAID`，子单按**履约方式**落状态（见状态整理 §2.2）：
   - 到店核销 / 上门服务 → 直接 `FULFILLING`（没有「发货」这一步），并**生成核销码**；
   - 其余（自提、自送、快递）→ `WAIT_FULFILL`。
2. **库存由锁定转扣减**。
3. **券置为已使用**、**积分流水由 `PENDING` 转 `CONFIRMED`**（抵扣的分真正扣掉）。
4. **发放购物积分**（按实付，不按原价）。
5. 通知：商家收到新单推送；买家收到「支付成功」。
6. 服务类商品在这一刻向微信**报发货**（虚拟商品的发货时点就是付款成功）。
7. 归因：记一笔「他买了一单」给会员域与裂变域。

端上：支付成功后**不回下单页**，直接进支付结果（自提单显示取货码、快递单显示「等待发货」）。

### 8.3 支付失败 / 中断

- 用户关掉微信支付面板 → 订单**已经建好**，落到收银台页（带倒计时），可以再付。
- 拉起失败（如当前的 `banned`）→ 同样落收银台页，并把原因说出来。
- 订单在 `WAIT_PAY` 状态最多存活 N 分钟（`TRADE_RULES.payTimeoutMinutes`），到点自动关。

### 8.4 超时关单 / 主动取消

两条路走**同一段代码**（`closeOne`）——分开写迟早漏掉一项：

1. 主单 `CLOSED`、子单 `CANCELLED`，写状态日志（谁关的、为什么）。
2. **释放库存**（只作用于 `LOCKED` 行，重复跑不会加两遍）。
3. **退回券**（回到券包，`我的券`里重新可用）。
4. **退回积分**（只认 `PENDING` 的 `USE` 流水，重复跑不会退两次）。
5. 释放预约时段。
6. 活动配额是否回滚：**当前不回滚**（`quota_used` 不减）——这是已知口径，
   若要改要连着对账一起改，不能只在这里减一行。

端上：订单详情要说清**为什么关的**，以及**券和积分回没回来** —— 不说的话用户以为券被吞了（原型 k10）。

### 8.5 退款（付款之后）

付款后的退款一律走**售后单**，不走「取消」：

```
买家申请 → 商家同意 / 拒绝 → （需要退货时）买家寄回 → 商家收货 → 退款
                   ↓ 拒绝
            买家可上升平台裁决
```

- 退款成功：售后单 `REFUNDED`，子单 `REFUNDED`，**按售后单回补库存**（`stockPort.restore`）。
- 钱原路退回微信；部分退款按行退。
- **券与积分目前不随退款退回** —— 这是现状，也是个要拍板的口径：
  行业通行做法是「整单退则退券、部分退不退」。要改的话是一处独立改动，
  牵涉结算口径（券的平台补贴已经结给商家了），不能顺手做。
- 商家侧的结算金额随之冲销（结算域按 `pmt_apply` 与实付算，见资金链路文档）。

### 8.6 每一步对应的界面

| 时刻 | 界面 | 必须说清的一句话 |
|---|---|---|
| 建单失败 | 下单页顶部提示 | 哪一条变了（库存 / 券 / 活动 / 配送范围） |
| 支付中断 | 收银台页 | 还剩多久自动关单 |
| 支付成功 | 支付结果页 | 下一步是什么（取货码 / 等发货 / 等上门） |
| 已关闭 | 订单详情 | 为什么关 + 券与积分的去向 |
| 退款中 | 订单详情的售后卡 | 到哪一步了、要不要我做什么 |
| 已退款 | 订单详情 | 退了多少、退到哪儿、几天到账 |

### 8.7 这套逻辑里现在还缺的

| 缺口 | 影响 | 建议 |
|---|---|---|
| 建单失败只给一句笼统报错 | 用户不知道改什么 | 按 §五 的表逐条给原因 |
| 首次下单多一跳收银台 | 多一次点击 | §二：底栏直接拉起支付 |
| 退款不退券 / 不退积分 | 整单退货的人损失一张券 | 要拍板；建议「整单退则退」 |
| 关单不回滚活动配额 | 限量活动的量会被没付款的单吃掉 | 要拍板；建议回滚并在对账里体现 |
