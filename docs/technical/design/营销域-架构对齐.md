## 一、业务抽象：营销域里存在哪些东西

**不看代码。** 只问：商家做营销这件事，涉及哪些真实存在的东西？

```
营销
├── 活动 ······ 一条规则：什么情况下、给谁、给什么、什么时候、最多给多少
│   └── 它作用在哪些货上（有的玩法要指定，有的不要）
├── 券 ········ 一张券的设计
│   ├── 发放 ·· 一次「发给哪些人」的动作
│   └── 用户券 · 发到某个人手上的那一张
├── 团 ········ 按团购活动开出来的一个团
│   └── 团员 ·· 谁进了这个团
└── 优惠发生 ·· 每一次真的减了钱
```

八个东西。**其中只有四个是聚合根**（有自己的生命周期、被单独引用）：
活动、券、团、优惠发生。其余四个都依附在某个根上。

## 二、逻辑抽象：聚合根与不变式

### 2.1 活动

| | |
|---|---|
| 身份 | 活动号 |
| 归属 | 主体（可选：某一家门店） |
| 生命 | 草稿 → 在跑 → 暂停 ⇄ 在跑 → 结束（**不可逆**） |
| 组成 | 触发 · 优惠 · 排期 · 受众 · 限量 |
| 附属 | 作用范围（哪些货/类目/全店）、受众条件 |

**不变式**

1. **总有停下来的那一天** —— 没有结束时间就必须有限量或预算；
2. **改单价 / 送商品必须有限量** —— 单次成本由商品决定，敞口随销量走；
3. **同一件货同时只能在一个团购活动里**（否则买家看到一个价、付另一个价）；
4. **成团人数 ≥ 2**，且团购的优惠只能是改单价；
5. **已结束的不可编辑** —— 改完只会立刻又结束一次。

### 2.2 券

| | |
|---|---|
| 身份 | 券号 |
| 生命 | 在发 → 暂停 ⇄ 在发 → 结束 |
| 组成 | 面额或折扣 · 门槛 · 有效期规则 · 发行量 · 每人限领 · 预算 |
| 附属 | 适用范围、发放记录 |

**不变式**

1. **发行量与预算是并发计数器**，不是缓存 —— 防超发靠一条带条件的 UPDATE；
2. **模板改了不影响已发出的那些**（有效期在领的那一刻算好落行）；
3. **算优惠只有一处实现** —— 分岔过一次：下单认折扣券而「最优券」只看面额。

### 2.3 团

| | |
|---|---|
| 身份 | 团号 |
| 依据 | **一条团购活动**（规则从活动读，不从商品读） |
| 生命 | 开团 → 凑人 → 成团 / 到期 |
| 组成 | 发起人（商家开的为空）· 自提点 · 成团价 · 起团人数 · 已参人数 |

**不变式**

1. **不成团不作废** —— 按原价照常发货（生鲜场景下退款 = 用户白等一天）；
2. **成团价低于原价**，否则「团购」是假的；
3. **活动不在跑就开不出团**；
4. **活动结束 ≠ 已开出的团结束** —— 两个生命周期互不牵连。

### 2.4 优惠发生

**只增不改。** 撤销是写一个时间戳，不是删行。线上线下同一张表。

### 2.5 一条跨聚合的规矩

**先算活动，再算券。** 券作用在活动优惠之后的金额上 ——
理由是用户视角：满减是他没得选的，券是他挑的。

## 三、对齐代码：领域对象

| 业务上的东西 | 代码里的类 | 表 | 列数 | 对得上吗 |
|---|---|---|---:|---|
| 活动 | `PmtActivity` | `pmt_activity` | 24 | ✅ |
| └ 作用范围 | `PmtActivityGoods` | `pmt_activity_goods` | 4 | ✅ |
| └ 受众 | `PmtActivityAudience` | `pmt_activity_audience` | 4 | ✅ |
| 券 | `PmtCoupon` | `pmt_coupon` | 25 | ✅ |
| └ 适用范围 | `PmtCouponScope` | `pmt_coupon_scope` | 3 | ✅ |
| └ 发放 | `PmtCouponIssue` | `pmt_coupon_issue` | 14 | ✅ |
| 用户券 | `PmtUserCoupon` | `pmt_user_coupon` | 12 | ✅ |
| 团 | `MktGroupBuy` | `mkt_group_buy` | 14 | ⚠️ **名字还在老命名空间** |

| 优惠发生 | `PmtApply` | `pmt_apply` | 14 | ✅ |

### 3.1 三处名不符实

**① `pmt_activity.goal`（第 5 列）—— 业务上不存在这个东西。**
它是「拉新客 / 唤回老客 / 清库存 / 提高客单」，而那只是<b>受众 + 优惠的预设组合</b>，
不是活动的属性。2026-09-18 已停写，**列还在**（回滚窗口）。

**② 团在 `mkt_*` 命名空间下，而它不属于老模型。**
团是实例，与模型新旧无关 —— 老模型退场时它**不跟着走**。
名字留在 `mkt_` 下会让人以为它也要迁。

**③ `mkt_campaign` 等十个老表是同一批概念的旧实现**，不引入任何新概念。

### 3.2 一处业务上有、代码里没有

**「活动作用在哪些货上」对团购是必填，对满减无意义** —— 而 `pmt_activity_goods`
没有任何东西表达「这个玩法要不要指定商品」。今天靠端上判（`isItemCost`）
与后端 `assertSane` 各写一份。**两份判据分头维护**，是下一个分岔点。

## 四、对齐代码：数据库结构

### 4.1 新模型八张表

```
pmt_activity ──┬── pmt_activity_goods    (activity_no)
               └── pmt_activity_audience (activity_no)
pmt_coupon ────┬── pmt_coupon_scope      (coupon_no)
               ├── pmt_coupon_issue      (coupon_no)
               └── pmt_user_coupon       (coupon_no, user_no)
pmt_apply ····· 记录，谁都不挂
mkt_group_buy ─┬── mkt_group_member      (group_no)
               └── 引用 pmt_activity     (**这条今天只在代码里，库上没有外键**)
```

### 4.2 三条要说清的

**① 数据域只登记入口表。** `pmt_activity` / `pmt_coupon` 按 `entity_no` 登记；
`pmt_activity_goods` / `_audience` / `pmt_coupon_scope` **不登记** ——
它们挂在父号上，从不作为检索入口。

> 代价是：查它们必须先经过父表，或者显式绕域。
> 2026-09-18 就为此付过一次 —— 七处读漏了绕域，商家永远看不到自己建的活动。

**② 团与活动之间没有外键。** `mkt_group_buy` 存的是成团价与人数的**快照**，
不存 `activity_no`。这是有意的（活动改价不该改已开出的团），
但**代价是查不出「这个团是按哪条活动开的」**。

**③ 唯一键要含逻辑删列，否则「整批换掉」撞键。**
`uk_pmt_activity_goods(tenant_no, activity_no, scope_type, ref_no)` 不含 `deleted`，
而 `saveGoods` 用的是逻辑删 —— 2026-09-18 查实：**任何活动只要编辑时保留原来那件商品，
第二次保存必撞键**，已改成物理删。

## 五、对齐代码：API

### 5.1 B 端

| 业务动作 | 端点 | 状态 |
|---|---|---|
| 看活动 | `GET /biz/activities` | ✅ |
| 活动详情 | `GET /biz/activities/{no}` | ✅ |
| 建 / 改活动 | `POST /biz/activities` | ✅ |
| 启停 / 结束 | `PUT /biz/activities/{no}/status` | ✅ |
| 撞车预检 | `POST /biz/activity-conflicts` | ⚠️ **只是建议**，硬拦在服务端 |
| 看券 / 详情 / 建改 / 启停 | `/biz/coupons*` | ✅ |
| 定向发券 | `POST /biz/coupons/{no}/issue` | ✅ |
| 发放记录 | `GET /biz/coupon-issues` | ✅ |
| 到店核销 | `GET/POST /biz/coupon-redeem*` | ✅ |
| 我的商家团 / 开团 | `GET/POST /biz/groups` | ✅ |
| ~~老活动三个~~ | `/biz/campaign*` | ❌ **该退场** |

### 5.2 C 端

| | 端点 |
|---|---|
| 券列表 / 领取 | `GET /mp/coupon`、`POST /mp/coupon/{no}/receive` |
| 团列表 / 详情 / 参团 | `/mp/group-buy*` |
| 发起团 / 我发起的 / 签收 / 核销 | `/mp/group-buy*` |
| **活动** | **没有端点** —— 活动是自动生效的，C 端不需要问它 |

> 最后一行是对的：活动不需要 C 端接口，它在算价时生效。
> 但**商品详情要显示「拼团价」时需要知道有没有在跑的团购活动** ——
> 今天走的是 `GroupRulePort`（服务端内部），不走 HTTP。

### 5.3 两处 API 层面的欠账

**① `/biz/activity-conflicts` 是建议不是闸门。** 服务端已硬拦（2026-09-18 加），
但这个端点还在，容易让人以为「端上查过就行」。**建议保留**（它给的是提前提示），
但文档里要写明它不是判据。

**② 老端点 `/biz/campaign*` 下线方式未定** —— 见 `TDD-活动与营销活动的合并` §六。

## 五之三、线上实况（2026-09-18 查得，只读）

| 表 | 行数 |
|---|---:|
| `pmt_activity` | 1（真机上建的团购） |
| `pmt_activity_goods` | 1 |
| `pmt_apply` | 0 |
| `pmt_coupon` / `pmt_user_coupon` | 0 / 0 |
| `mkt_campaign` / `mkt_coupon` | 0 / 0 |
| `mkt_group_buy` / `mkt_group_member` | **0 / 0** |

**除了那一条团购活动，整个营销域线上是空的。** 这决定了所有迁移的代价：
不需要搬数据、不需要两套并存，只需要改代码与删表。
<b>这是做这些结构调整最便宜的时刻</b> —— 有第一笔真实营销数据之后就不是了。

## 六、这一份得出的三条结论

1. **新模型的领域对象是完整的**，八个业务上的东西都有落点，没有缺失的表；
2. **三处名不符实**：`goal` 列（业务上不存在）、团在 `mkt_` 命名空间、老模型十张表；
3. **一处判据有两份**：「这个玩法要不要指定商品」端上一份、后端一份 ——
   这是下一个会分岔的地方，值得收成一处。
