## 0. 这份方案怎么用

前面五份文档回答的是「做什么、长什么样、表怎么建、接口怎么定」。
**这一份只回答两件事：按什么顺序做，每一步做完怎么算数。**

三条贯穿的排期原则：

1. **每一步都能独立上线，也能独立回退。** 不做「攒三周一起发」——
   这个项目今晚刚因为一次混着三条线的部署宕过 4 分钟。
2. **先做不碰算价的。** 算价（`OrderServiceImpl.Discounts`）是被最多用例覆盖、
   也最贵的一条路径；把它放在最后，前面所有阶段都不会威胁交易。
3. **每阶段自带守卫。** 没有测试的阶段不算完成 —— 尤其是那几条合规约束
   （线索不可触达、手机号只出后四位、频次闸），它们写在文档里三个月后没人记得。

## 2. 逐阶段执行

### P0 · 身份（`usr_person`）

| | |
|---|---|
| **迁移** | `usr_person`、`usr_person_merge_log`；`phone_hash` NOT NULL + 唯一键 |
| **后端** | `user` 域：`PersonService`（`resolveByPhone` / `bindPhone` A·B·C 三分支 / `merge`）、`PersonPort` |
| **接入点** | 注册登录成功后 → 解析或建人档并绑账号（现有 `AuthServiceImpl` 一处调用） |
| **端上** | 无 |
| **测试** | `PersonBindFlowTest`：A 建新档 · B 绑已有线索档 · **C 拒绝（手机号已绑别的账号）** · 换号 · 合并留痕 |
| **验收** | 老用户登录不受影响（回归现有登录用例）；新用户注册后库里有一份人档 |
| **风险** | 碰登录链路。缓解：只在登录**成功之后**追加一步，失败不阻塞登录 —— 人档补不上明天再补，登录挡住是事故 |

| | |

## 3. 每一步都要过的守卫

| 什么时候 | 跑什么 | 为什么 |
|---|---|---|
| 改了页面/标题/菜单/原型 | `python3 scripts/gen-ui-catalog.py` | pre-push 有闸门，对不上推不上去 |
| 加了 `/biz` 端点 | 在 `BizEndpointPermTest` 决策表登记 | 否则架构用例红；它挡的是「忘了判权」 |
| 加了域包 | 登记进 `ArchitectureTest.DOMAINS` | 不登记就不受域间依赖规则约束，等于没边界 |
| 加了迁移 | `ls db/migration \| grep -oE "^V[0-9]+" \| sort -n \| uniq -d` | 并行会话撞号，本地不报、上生产起不来 |
| 改了实体/加了列 | 跑 entity-alignment 守卫 | 只改一处，那一列永远读出 null |
| 提交前 | `git diff HEAD -- <file>` 自己读一遍 | 共享工作区，`git add` 会扫到别人的 hunk |
| 后端发版前 | HEAD 干净 worktree 编一遍 + 四步验证 | 见 §4 |

## 4. 发布流程（后端）

```
1  git status --porcelain | grep '^??'      # ?? 的新文件不在 M 列里，最容易漏交
2  开 HEAD 干净 worktree 编译               # 编不过就别发，把缺的文件报给对应会话
3  cp shop-app.jar shop-app.jar.bak-$(date +%m%d-%H%M)
4  候选 jar 传上去，用临时端口起一次：
   · 进程活着 · 日志无 Flyway validate 异常 · /biz/health 无 token 返回 401
   ⚠ 临时端口只隔应用不隔库 —— 迁移会真的跑进生产库，回滚方式要先想好
5  停候选、换 8081 那份、重启、复验
```

前端（H5 / ops-web）不走 maven，可单独发；**但依赖新端点的界面要用开关挡住**，
上线顺序永远是「后端先、端上后」——反过来就是今晚那种「按钮点了 404」。

## 6. 风险与止损

| 风险 | 触发信号 | 止损 |
|---|---|---|
| 算价回归 | 交易用例出现金额级差异 | Port 切回旧实现（旧表还在），当天可回退 |
| 回填把库拖慢 | 回填任务运行时接口 P99 上升 | 分批 + 手动触发，随时可停；不在启动时跑 |
| 触达烧掉通知权限 | 退订率上升 | 频次闸在 `sys_setting`，即时收紧；必要时全平台停发 |
| 并行会话撞车 | 迁移号重复、生成物冲突 | 撞号自己让路；生成物含别人未提交的迁移就本次不提交 |
| 合规 | 商家能看到完整手机号 / 线索被推送 | 这三条写成测试（P1、P2、P7 各一条），红了就不许发 |

## 7. 建议的推进顺序

**先做 P0 + P1。** 它们不碰算价、不碰交易、不打扰用户，做完就能回答商家最常问的那个问题
（「谁是我的老客」），也是后面所有东西的地基。

P0 大约是一支迁移 + 一个 service + 一组用例；P1 是四张表 + 一次回填 + 一页界面。
两步都做完之后再决定要不要接着往下走 —— 那时会员名单已经在手上，
后面每一步的价值都能用真实数字判断，而不是凭设计文档判断。
