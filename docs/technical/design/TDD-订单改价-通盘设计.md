# TDD 订单改价 · 通盘设计（四行业）

状态：**草稿 · 待确认** · 创建 2026-08-30
起因：电子元器件分析册把「订单成立后能否协商改价」列为**唯一翻盘条件**（能改 = 要另起一套订单）。
业务确认：**可以改价，且餐饮、零售同样需要**。故本册通盘重做 —— 结论也随之修正（§八）。

---

# 一 · 先自我更正两处

## 1.1 「订单之后不可改」从来就不是铁律 —— 我自己的设计里已有例外

[订单域规格书](./订单域V2-设计规格书.md) 里 `ord_item.weigh_adjust_minor` 的注释写着
「**本行计量差价：正补款负退款**」，`applyMeteredAdjust` 是公开 Service 方法。
也就是说：**称重生鲜早就在做"订单成立后金额变了"**，而且它在主干上跑通了。

我在元器件分析册里写"订单之前可谈、订单之后不可改"，是把一条**局部规律**（价格快照不被商品改动影响）
误当成了**全局铁律**。真正成立的是更弱也更准的一条：

> **订单行的原始快照不可被覆盖；金额的后续变化必须是有来源、可追溯的追加记录。**

`weigh_adjust_minor` 恰恰符合它 —— 它没有改 `price`，而是在旁边加了一个差额。

## 1.2 「改价」不是元器件特有，是四行业共同需求

把它当成元器件的翻盘条件，是"带着单一行业视角看通用问题"的又一次复发
（与此前"带着对照做需求梳理"同一类错误）。本册按老规矩：**先分行业梳理，再合并**。

# 三 · 合并：这不是一个需求，是四类

把 24 条摊开对齐后，**"改价"其实混着四种性质完全不同的东西** ——
它们对下游（退款 / 结算 / 发票 / 报表）的影响各不相同，混作一谈是这个设计最大的坑。

| 类 | 是什么 | 例子 | 金额落点 | 下游影响 |
|---|---|---|---|---|
| **① 让利（DISCOUNT）** | 商家主动少收 | 折扣 · 抹零 · 免单 · 赠送 · 员工价 | `discount_merchant` | 结算按实收算佣金；平台不承担 |
| **② 补差（ADJUST）** | 实际交付与下单时不同，**双向** | 称重 · 换项目 · 升级 · 数量变更 | `weigh_adjust_minor` 泛化 | 正=补款单、负=退款；发票按最终额 |
| **③ 重定价（REPRICE）** | **单价本身变了** | B2B 还价 · 行情 · 汇率 · 后续批次 | 新的行价快照（见 §4.3） | 最敏感：影响成本核算与历史可比 |
| **④ 更正（CORRECTION）** | 原来就录错了 | 价格填错 · 选错规格 | **冲正 + 重开**，不是改 | 审计要看得出这是纠错不是让利 |

**判据一句话**：
- 交付内容没变、只是少收钱 → **让利**；
- 交付内容变了 → **补差**；
- 交付内容没变但单价重新谈了 → **重定价**；
- 当初就是错的 → **更正**。

> 把免单做成"改价为 0"是最常见的错法：报表上会看不出这是服务补偿，
> 而它与"这道菜本来就免费"（赠品）在财务口径上是两件事。

# 四 · 设计：调整是**追加记录**，不是覆盖

## 4.1 核心规则

```
原始快照（ord_item.price / qty）    永不修改   ← 保住「行是历史凭证」
                ↓
调整记录（ord_adjustment）          只追加     ← 有类型、有原因、有操作人、可审批
                ↓
有效金额 = 原始金额 + Σ 调整         现算       ← 与「台账不存合计」同一条道理
```

**为什么不直接改 `price`**：改了之后，"这单当初为什么是这个价"就再也复现不出来 ——
而这正是 `price_hit`（O8：无解析命中记录的价格拒单）当初存在的理由。
改价把 `price_hit` 变成谎言，是它真正的代价，不是"技术上做不到"。

## 4.2 阶段决定形态，不是禁止

| 订单阶段 | 允许的类 | 形态 |
|---|---|---|
| **未支付**（`WAIT_PAY` / `WAIT_OFFLINE_PAY`） | ①②③④ 全部 | 调整记录 + 待付金额重算（**没有资金流**，最简单） |
| **已支付未履约** | ①②③ | 差额为负 → 退款；为正 → **补款单**（新订单，见 §4.4） |
| **已履约完成** | ①②（③需审批） | 同上，且进入售后视野 |
| **已结算** | 仅 ④ 更正 | **必须走冲正**，不允许静默调整 |

**这张表就是原来那条"不可改"的正确版本** —— 不是不能改，是**越往后，形态越受限、留痕要求越高**。

## 4.3 重定价（③）的特殊处理：不改旧行，写新行价

B2B 还价与分批改价（E-a/E-b/E-d）**不是调整一个差额，是单价换了**。
落法：**行版本化** —— 原行 `price` 不动，新增一条调整记录携带 `new_unit_price`，
有效单价 = 最新一条重定价记录（没有则用原 `price`）。

这样 E-d（前 3000 按老价、后 7000 按新价）自然成立：**重定价记录带生效数量区间**，
已发部分按发货时的有效价结算，未发部分按新价。

## 4.4 已支付后的正向差额：补款单而不是"改大金额"

已付订单要多收钱时，**不修改原订单金额**，而是生成一张关联的**补款订单**：

```
原单 O-1（已付 ¥800）
  └── 补款单 O-1-A（¥200，type=SUPPLEMENT，refs O-1）
```

理由：`markPaid` 是幂等的、且"已付"是终态语义；把已付订单的应付金额改大，
会让"这单付清了没有"变成一个需要重新计算的问题 —— 而它现在是一个状态。
**补款单让资金流始终与订单状态一一对应。**

（称重补差今天走的是 `weigh_adjust_minor` + 线下补收，本册把它统一到补款单形态，
既有链路作为兼容保留 —— 见 §八 回填清单。）

# 五 · 对四条链路的影响（当初判"要另起一套"的依据，逐条复核）

| 链路 | 影响 | 是否需要另起 |
|---|---|---|
| **快照** | 原始 `price`/`qty`/`price_hit` **一个字节不动**，调整在旁边 | ❌ 不需要 |
| **退款** | 负向调整 → 走既有售后（`refundLine` 已支持按行、含 modifier） | ❌ |
| **结算** | 结算读**有效金额**而非原始金额；调整明细进结算快照，佣金按实收算 | ❌ 加一个求和 |
| **发票** | 未开票：按有效金额开；已开票：红冲重开（财务既有流程） | ❌ |

**四条链路无一被推翻。** 当初的判断错在假设"改价 = 覆盖原值"——
一旦改成追加记录，四条链路读的都是"原值 + 调整"，而它们本来就要处理
`discount` / `points_deduct` / `asset_deduct` / `weigh_adjust` 这些减项，多一类不改变结构。

# 六 · 数据库

```sql
CREATE TABLE ord_adjustment (
  adjustment_no VARCHAR(32) NOT NULL,
  order_no      VARCHAR(32) NOT NULL,
  sub_order_no  VARCHAR(32) NULL COMMENT '整单级调整（抹零/整单折）时为空',
  order_item_id BIGINT      NULL COMMENT '行级调整；整单级为空',
  kind          VARCHAR(16) NOT NULL COMMENT 'DISCOUNT 让利 / ADJUST 补差 / REPRICE 重定价 / CORRECTION 更正',
  reason_code   VARCHAR(24) NOT NULL COMMENT '取值域按 kind 分组：SERVICE_COMPENSATION 免单 · WEIGH 称重 · NEGOTIATION 议价 · INPUT_ERROR 录错 …',
  reason_text   VARCHAR(255) NULL COMMENT '免单/议价**必填**（内控要害）',
  amount_minor  BIGINT      NOT NULL COMMENT '有符号：负=少收，正=多收。整单让利记负数',
  new_unit_price BIGINT     NULL COMMENT '仅 REPRICE：新单价（原行 price 不动）',
  qty_from      INT         NULL COMMENT '仅 REPRICE：生效数量区间起（分批改价 E-d）',
  qty_to        INT         NULL,
  supplement_order_no VARCHAR(32) NULL COMMENT '正向差额生成的补款单（§4.4）',
  approved_by   VARCHAR(64) NULL COMMENT '超阈值需审批；门店可配阈值',
  operator      VARCHAR(64) NOT NULL,
  idem_key      VARCHAR(64) NOT NULL,
  UNIQUE KEY uk_adjustment (adjustment_no), UNIQUE KEY uk_adjustment_idem (idem_key),
  KEY idx_adj_order (order_no), KEY idx_adj_item (order_item_id)
) COMMENT='订单调整：只追加不覆盖。有效金额 = 原始 + Σ调整，现算不落库';
```

**订单侧加列（1 处）**：
```sql
ALTER TABLE ord_order ADD COLUMN supplement_of VARCHAR(32) NULL
  COMMENT '本单是哪张订单的补款单（§4.4）；NULL=普通订单';
```

**`weigh_adjust_minor` 的归宿**：语义并入 `kind=ADJUST, reason_code=WEIGH`，
既有列**保留为冗余汇总**（读侧兼容，不再是唯一真源）—— 与 `modifier_total_minor` 同一手法。

# 七 · 约束与不变量（新增 A1–A7）

| # | 律 |
|---|---|
| A1 | 原始 `price` `qty` `price_hit` **永不被调整覆盖**（改价的代价是让 `price_hit` 变谎言，故禁止） |
| A2 | 有效金额 = 原始 + Σ调整，**现算不落库**；且**结果不得为负** |
| A3 | `kind` 与阶段的组合受 §4.2 表约束；已结算订单只允许 `CORRECTION` 且必须冲正 |
| A4 | `SERVICE_COMPENSATION`（免单）与 `NEGOTIATION`（议价）**`reason_text` 必填** —— 无原因的减免是内控漏洞 |
| A5 | 超过门店阈值需 `approved_by`；阈值为 0 表示该类必须逐笔审批 |
| A6 | 已付订单的正向差额**只能生成补款单**，不得改大原单应付 |
| A7 | `REPRICE` 的数量区间不得重叠；已发货数量部分按发货时有效价，**追溯改价不影响已发批次的结算** |

**权限**：`order:adjust:discount` / `order:adjust:reprice` / `order:adjust:correct` **三码分离** ——
让利、议价、纠错是三种不同的内控动作（与收款/冲正/结清三码分离同理）。

# 八 · 结论修正与回填清单

## 8.1 结论修正（本册的直接目的）

[电子元器件分析册](./电子元器件-需求梳理与方案分析.md) §3.1 把"订单成立后能否改价"列为**唯一翻盘条件**，
判"能改 = 要另起一套"。**该判断作废**：

> 改价能力**不推翻**复用结论。它推翻的只是"改价 = 覆盖原值"这个隐含假设 ——
> 改成**追加调整记录**后，快照/退款/结算/发票四条链路无一被动摇（§五）。
> 而且它是**四行业共同需求**，本就该做在基座，不该由某个行业触发。

**结论仍然是：复用现有商品/订单，不另起一套。** 且七条核心不变量的检验结论不变。

1. **免单/大额让利的审批阈值**由谁配（平台给默认 + 门店可调？）；
