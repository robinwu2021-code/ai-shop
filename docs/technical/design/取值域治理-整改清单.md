## §1 已验证的问题

### P1 · 词典把一个未实现的履约方式写成了现有的 —— 而它是「规定」

**症状**　[项目词典](../../requirements/项目词典.md) §5 写：

> **Fulfilment type** | 履约方式 | `FULFILLMENT` | 7 种：`PICKUP` 自提点自提 / `NEIGHBOR_PICKUP` / `DELIVERY` 商家自送 / `EXPRESS` / `STORE_VERIFY` / `APPOINTMENT` / `INSTANT` 即时发放

两处不对：

1. **`INSTANT` 后端没有**，端上代码已明确把它列进 `PLANNED_FULFILLMENTS`
   （注释写着「后端未实现…是待办不是缺陷」）。词典把它与另外 6 个并列，**无任何标记**。
2. **列的是端上键名不是 wire 取值**。`FULFILLMENT.PICKUP = "STORE_PICKUP"`、
   `FULFILLMENT.DELIVERY = "MERCHANT_DELIVERY"`。照词典去写筛选条件
   （`?fulfillment=PICKUP`）**必然筛不出东西**，而这正是词典 §3 第 2 条
   「端上常量：键名随意，值必须逐字等于库」要防的。

**为什么现在没人发现**　`glossary.test.ts` 只核对「反引号里的标识符在代码里存不存在」——
`PICKUP` 与 `INSTANT` 在端上代码里**确实存在**（一个是键、一个是 planned），断言通过。
「存在」与「是这个业务概念的合法取值」是两条不同的断言。

**复现**
```bash
grep -n "Fulfilment type" docs/requirements/项目词典.md
grep -c "public static final String" backend/shop-base/src/main/java/ai/neargo/shop/common/Fulfillments.java   # 6
grep -rn '"INSTANT"' backend --include="*.java" | grep -v /target/                                            # 空
sed -n '/PLANNED_FULFILLMENTS: readonly/,/^\];/p' packages/shared/src/utils/constants/index.ts
```

**建议动作**　改词典那一行：取值写 wire 值（`STORE_PICKUP` / `MERCHANT_DELIVERY`…），
键名若要保留就单独标明是端上键；`INSTANT` 单列并标「二期，后端未实现」。
**注意这是改规范**：词典自称「冲突时改代码，不改本页」，所以这一条要评审，不能顺手改。

**档位**　0（只改文档），但需评审。**影响面**　无代码。

**复核（2026-09-06 接手会话）**　四条复现命令全部重跑，结论成立：
`Fulfillments.java` 里 6 个常量、`grep '"INSTANT"' backend` 为空、
`FULFILLMENT.PICKUP = "STORE_PICKUP"`。补一条你没提到的旁证：
`check-enum-fields.mjs` 的履约那条已经把这件事写在注释里了 ——
「INSTANT 未接，由端上的 PLANNED_FULFILLMENTS 申报，不在这里列」，
也就是**代码侧早就把 INSTANT 单独归了类，只有词典把它与另外 6 个并列**。
**没有替你改**：它是规定不是记录，改它要评审。

### P2 · 触达场景码有三个声明处；一向早有守卫，另两向没有 ✅ 已做完

> ⚠️ **本条原标题与正文里「没有任何东西保证它继续一致」「没有任何守卫检查这条规则」
> 两句是错的**（提出者写的）。`SceneChannelSeedTest#everyHandledSceneIsSeeded`
> 自 2026-08-17（`572c86fbc`）就守着 ①→③ 那一向。错因是只比了三处集合相等、
> **没有去搜有没有现成的测试** —— 与本清单 §2 批评的那种下结论方式是同一个。
> 真正缺的是 ③→① 与 ①↔②，接手会话按这个重新分了工，见下方「复核」。
> 原文保留不删：走错过一次比假装没走过有用。

**症状（提出时的状态，现已修复）**　「通知场景」是一个真实的取值域（需求端在
[需求矩阵-三端](../../requirements/需求矩阵-三端.md) §5.4 有完整清单，16 条带实现状态），
但代码里**没有具名声明处**，散在三处字面量：

| # | 位置 | 形态 |
|---|---|---|
| ① | `shop-core/.../message/NotificationConsumer.java` L33-37 | 一个字面量集合（已知场景） |
| ② | 同文件 | `switch` 的 7 个 `case "…"` |
| ③ | `shop-app/.../db/migration/V156__msg_scene_channel.sql` | 种子行的 `scene_code` |

**今天三处完全一致（各 7 个码，两两差集为空）**——所以这不是现存缺陷，是**没有护栏**：
加一个场景要同时改三处，漏掉任一处都零报错。漏 ③ = 配置表没有这一行，通道全关，通知永不发出；
漏 ①② = 配置表有行而消费者不认识这个码，事件被静默丢弃。

**为什么现在没人发现**（这段也不准，见上方更正）　违反
[枚举统一方案](枚举统一方案.md) §3 第 3 条「一个概念一个声明处，禁止裸字面量」——
这一条确实没有守卫。但「三处会不会不一致」并非全无人管：①→③ 一直有
`SceneChannelSeedTest` 守着，没被搜到而已。

**复现**
```bash
A=$(sed -n '33,37p' backend/shop-core/src/main/java/ai/neargo/shop/message/NotificationConsumer.java \
    | grep -oE '"[A-Z_]+"' | tr -d '"' | sort -u)
B=$(grep -oE 'case "[A-Z_]+"' backend/shop-core/src/main/java/ai/neargo/shop/message/NotificationConsumer.java \
    | sed 's/case "//;s/"//' | sort -u)
C=$(grep -oE "SELECT '[A-Z_]+'" backend/shop-app/src/main/resources/db/migration/V156__msg_scene_channel.sql \
    | sed "s/SELECT '//;s/'//" | sort -u)
diff <(echo "$A") <(echo "$B"); diff <(echo "$A") <(echo "$C")   # 今天都为空
```

**建议动作**　提取具名常量类（如 `NotifyScene`），三处都引用它；
迁移已应用**不能改**（Flyway checksum），所以 ③ 那一侧只能加守卫：
断言「常量类的取值 == 种子行的 scene_code 集合」。
守卫要先绿再挂 —— 今天它就是绿的，正是挂闸门的时机。

**档位**　1。**影响面**　`NotificationConsumer` 一个文件 + 一个新常量类 + 一条测试。不动迁移、不动运行时行为。

**复核（2026-09-06 接手会话）**　⚠️ **「没有任何东西保证它继续一致」这句不准。**
`SceneChannelSeedTest#everyHandledSceneIsSeeded` 早就守着 ①→③ 这一向
（每个处理中的场景都必须有种子行，且 INAPP 开启 + 至少一条加速通道），
`NotificationConsumer` 里那句注释也指着它。真正没护栏的是另外两向：

- **①↔②**（集合与 switch）—— 已消掉，不是加守卫而是**让它们引用同一个符号**：
  `NotifyScene` 的常量是编译期常量，`case NotifyScene.ORDER_PAID ->` 直接可用。
  能消掉的不一致就不要留给守卫看着。
  原来 `default` 分支的注释写着「走到这里说明两处不一致」—— 作者知道这个风险，
  当时没有办法消掉它；现在那一支改成 `log.warn` 点名场景码。
- **③→①**（种子行里有、消费者不认识）—— 加了 `everySeededSceneIsHandled`。
  这一向的后果与 ①→③ 完全不同：那一行谁都不读，而运营在触达配置页上看得见它、
  还会去开关它，以为自己配的东西生效了。查过 `/ops/scene-channel` 只有 GET，
  配置行只来自迁移，所以这是一条真不变式。

消融两向都做了：往 `ALL` 加一个没有种子的场景 → 正向红并点名；
从 `ALL` 删掉 `ORDER_PAID` → 反向红并点名。

**追加（同日，你指出注释说满之后）**　`NotifySceneCoverageTest`：
`ALL` 里的每个成员在 `NotificationConsumer` 里都必须有一个 `case`。
共用常量消掉的是**拼写**不一致，消不掉**遗漏** —— 往 `ALL` 加一个成员、
忘了加分支，`supports()` 照样放行，事件落进 `default`，什么都不做且零报错。
而**上面那两条守卫都拦不住这一种**：只要种子行也补了，两向都是绿的，只有分支是缺的。
判据读源码（分支是 switch 的语法结构，反射看不见），放在 shop-core 自己的测试目录里。
消融：往 `ALL` 加一个没有 `case` 的成员 → 红并点名。
`default` 那一支的注释也改了：原来写「走不到」，把范围说宽了。

**再追加（同日，你复核这条守卫之后）**　守卫自己有两处潜伏，都实证过、都修了：

- **扫描面没有下界** —— 循环靠 `f.getType() == String.class` 认成员。
  这组常量一旦改写成 Java enum，`getDeclaredFields()` **一个 String 字段都不返回**
  （单独写了个 5 行的 demo 实测：0 个），于是 `missing` 为空、断言通过，
  而 `ALL` 还在，另外两条守卫照旧绿 —— **测试全绿而一个成员都没查过**。
  补 `checked == NotifyScene.ALL.size()`。这条同时钉住反向：
  `ALL` 里放了一个没有对应常量的裸串时 `checked` 会偏小，一样红。
  消融：把判据改成认不出成员 → 红，并说「只检查了 0 个成员，而 ALL 有 7 个，这个测试正在空转」。
- **`contains` 的前缀问题** —— 一个成员是另一个的前缀时（假如同时有 `ORDER` 与 `ORDER_PAID`），
  `case NotifyScene.ORDER_PAID ->` 这一行里含着 `case NotifyScene.ORDER` 这个子串，
  短的那个缺分支也判成有。今天七个成员两两互不为前缀（跑过），所以是潜伏项。
  判据收成带词边界的正则。消融：加一个是别人前缀、且没有 `case` 的成员 → 红并点名。

**这两条与它们守的东西是同一个形状**：「找出违规」型的判据，少扫等于全绿。
所以每一条这样的判据都要配一句「我确实看了这么多个」。

**越是没有具名声明的取值域，越危险，也越不可能被一个只扫具名声明的工具发现。**

(a) 扩扫描面：把「同一文件里 ≥3 个大写字面量出现在 `case`/`Set.of`/`List.of` 里」也当候选；
(b) 不扩，但在清单抬头**明说这个盲区**，并由 P2 那条守卫覆盖。

## §2 方向修正：不要用字面特征配对

2026-09-06 用四种字面判据找过同物异名，**四次全部不成立**。这四个反例请留着，
下一个人一定会想「自动配一下不就行了」：

| 判据 | 报出来的 | 为什么错 |
|---|---|---|
| 取值集合相同 | `CouponFunder` ↔ `SpecTemplateScope` | 都是 `MERCHANT\|PLATFORM`，毫无关系 |
| 字段名相同 | `ViolationAction` ↔ `OverdueAction` | 都叫 `action`，一个是违规处置一个是超期处理 |
| 属主名相同 | 两个 `InvoiceRequest.status` | 一个是 `ord_invoice_request`（买家开票）、一个是 `stl_settle_invoice`（商家结算开票）。**取值不同恰恰是对的** |
| 取值集合不同 → 判为漂移 | 同上 | 同一个假设的反面，一样错 |

**业务身份不在写法里。** 相似度只能用来给候选排序，判定必须有人做。
