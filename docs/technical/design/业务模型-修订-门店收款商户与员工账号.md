# 业务模型修订：门店与收款商户的关联、员工账号独立

> 状态：**已落地 V46**（2026-08-09）· 修订对象：[业务模型](./业务模型-账号商户门店与增长.md) · [ADR-011](../ADR/ADR-011-经营主体与门店边界.md)
> 已落地并受影响：V44（门店与子账号）· V45（订单双写）

---

## 零之一、四个实体，一次说清

**结构是：主体 · 商户 · 门店 · 员工。** 四样东西各有落点，两两之间的关系不同：

| 实体 | 是什么 | 表 | 状态 |
|---|---|---|---|
| **主体** | 经营主体 —— 谁在做这门生意 | `usr_merchant` | ✅ 已有 |
| **商户** | **收款商户号**（进件产生的 `sub_mchid`），每通道一条 | `usr_merchant_payment` | ✅ 已有 |
| **门店** | 物理经营场所 | `usr_store` | ✅ V44 |
| **员工** | 在这个主体下干活的人 | `usr_merchant_staff` | ✅ V44 |

```
                    usr_merchant（主体）
          ┌──────────────┼──────────────┬──────────────┐
     归属 │         归属 │         归属 │         归属 │
          ▼              ▼              ▼              ▼
  usr_merchant_    usr_store     usr_merchant_    prd_goods
     payment        （门店）        staff          （商品目录）
    （商户号）          │           （员工）            │
          ▲            │              │                │
          └──关联──────┘              └──逐店授权──────┘
        payment_no 可换          usr_staff_store（每店一个角色）
```

**四条关系里只有两条是可变关联，其余是归属**：

| 关系 | 类型 | 说明 |
|---|---|---|
| 主体 → 商户号 / 门店 / 员工 / 商品目录 | **归属** | 不改。它们都是这个经营者的东西 |
| **门店 → 商户号** | **关联，可换** | 这家店的钱走哪个口子 |
| **员工 → 门店** | **关联，逐店角色** | 同一个人可以 A 店店长、B 店店员 |

**员工归属主体而不是门店** —— 这一点容易搞反：
如果员工归属门店，那么「他同时管两家店」就要建两条员工记录，
而两条记录意味着两次登录，等于把多门店要解决的问题又还回去了。
所以：**身份挂主体，权限挂门店**。

## 零之二、口径确认，与我最初的误读

四条反馈。**第 1 条我一开始读错了**，先把它写清楚：

| 词 | 指的是 | 落点 |
|---|---|---|
| **主体** | 经营主体 —— **就是现在的 `usr_merchant`** | 已有 |
| **商户** | **收款商户号**（微信/支付宝进件产生的 `sub_mchid`） | 已有 `usr_merchant_payment` |
| **门店** | 物理经营场所 | 已有 `usr_store`（V44） |

我最初把「商户」读成了「一张营业执照的经营实体」，据此提了一套
**主体 / 商户 / 门店三层新模型**，还打算新建一张主体表。那是过度设计 ——
三样东西两样已经存在，缺的只是**门店与收款商户号之间的那条可变关联**。

> **这次误读的教训**：「商户」在支付语境里是商户号，在工商语境里是经营实体。
> 同一个词在两个语境下指两样东西，而我没问就选了一个。

**「App 上门店可换商户，小程序不支持」也随之解释通了**：
小程序只有微信一个进件，没得换；App 上一个主体可以有多个收款商户号
（微信 + 支付宝，或同一通道下多个进件），门店可以指定用哪个收款。

## 一、真正要改的：门店 → 收款商户号是关联，可换

```
              usr_merchant（主体）
             ╱        │         ╲
    归属    ╱         │归属      ╲   归属
           ▼          ▼           ▼
  usr_merchant_payment  usr_store   prd_goods
   （收款商户号，每通道）  （门店）    （商品目录）
           ▲              │
           └───关联───────┘
        usr_store.payment_no（可换）
        「这家店的钱走哪个商户号」
```

| 关系 | 类型 | 改了会怎样 |
|---|---|---|
| 主体 → 收款商户号 | 归属 | 不改。进件是主体的资质 |
| 主体 → 门店 | 归属 | 不改。门店是主体的资产 |
| 主体 → 商品目录 | 归属 | 不改 |
| **门店 → 收款商户号** | **关联** | **可换**：换个商户号收款，店照常开 |

**为什么必须是关联而不是归属**：一个主体可能有多个收款商户号
（不同通道、不同业务线各进一件）。如果门店归属商户号，
换收款方就等于换店 —— 评价清零、老客断链、历史订单查不到门店。
而它本质上只是换了个收钱的口子。

### 1.1 换商户号时，什么跟着走、什么不动

| 跟着新商户号走 | 留在门店 |
|---|---|
| **新订单**的分账接收方、开票主体 | 地址、营业时间、公告、门店码 |
| 该通道的费率与限额 | 评价与评分、库存、选品 |
| | 员工授权、顾客关系 |

**历史订单一律不动**。分账已经按当时的商户号执行完了，
回头改历史订单的收款方等于把已完成的分账凭空改掉 —— 那是财务事故不是数据修正。

> M2 的双写设计在这里额外得了一分：`store_no` 让「这家店历史卖了多少」
> 跨商户号变更仍然可查，`merchant_no` 则忠实记录当时的结算主体。

### 1.2 换商户号的硬约束

| 约束 | 为什么 |
|---|---|
| 新商户号必须**同属该主体** | 否则钱进了别人的账 |
| 新商户号必须 `apply_status = ACTIVE` 且分账主体就绪 | 换到一个收不了款的号上，下一单就失败 |
| 有**未完成订单**时不换旧号 | 那些单的分账要走旧号。**新单用新号、旧单走旧号**，不是"切换后全部改" |
| 变更**留痕** | 这是会改变钱去向的操作 |

### 1.3 不配时的兜底

`usr_store.payment_no` 为空 = **用主体的默认商户号**（该通道下 `ACTIVE` 的第一个）。

单店 + 单通道时永远为空，行为与今天完全一致 —— 这一列只有多商户号时才有意义。

## 二、商品挂哪一层（第 3 问）

**目录挂主体，销售关系挂门店。不分场景 —— 一套模型同时装下两种场景。**

主体口径确认之后，这一条**现状就是对的，不用改**：`prd_goods.merchant_no` 挂的正是主体。

```
prd_goods（五常大米）──────── 挂主体：老王卖这个
     │
     ├─ prd_store_goods(文三路店, 大米, 在架)  ← 挂门店：这家店卖不卖（M3）
     └─ prd_store_stock(文三路店, SK001, 30)   ← 挂门店：这家店有几件（M3）
```

| 为什么不挂门店 | 为什么不挂收款商户号 |
|---|---|
| 连锁店上一款新米要在三家店各录一遍，改价改三次 | 商品与"钱从哪个口子进"毫无关系；换商户号会把目录带走 |

**"分场景"的那部分在选品关系里**，不在目录归属上：

| 场景 | 表现 |
|---|---|
| 连锁型 | 一个商品，N 条选品行 |
| 多业态型（菜摊 + 五金） | 每个商品只有 1 条选品行，B 端按当前门店过滤 = 天然隔离 |

`prd_sku` 的 `(merchant_no, sku_no, market)` 唯一键**保持不变** ——
它挂的也是主体，与目录一致。（我在上一版修订里担心的"价格锚点要跟着改"，
在主体口径确认后不存在。）

## 三、员工账号：独立身份 + 可选关联（第 4 问）

**你说得对，我之前的设计只考虑了小程序。**

我当时的理由是「店员多半已是 C 端用户，新发一套等于让他记两个密码」——
这在小程序里成立，因为他本来就在微信里。在 App 上完全不成立：
**要求店员先注册成消费者才能上班，是把雇佣关系硬塞进消费关系里。**

### 3.1 修订后的模型

```
usr_merchant_staff
  ├── merchant_no        归属主体（不变）
  ├── login_phone        ← 新：员工自己的登录身份，独立账号池
  ├── linked_user_no     ← 改：原 user_no，现在**可空**（小程序免登用）
  └── is_owner / status
```

| 载体 | 登录方式 |
|---|---|
| **App** | 员工手机号 + 验证码，**独立账号**，不需要 C 端账号 |
| **小程序** | 微信授权 → `user_no` → 命中 `linked_user_no` 则免登 |
| 同一个人两边都用 | 绑定后两条路走到同一条员工记录 |

### 3.2 三条必须守住的规则

| 规则 | 为什么 |
|---|---|
| **员工身份不依赖 C 端账号存在** | `linked_user_no` 可空；解绑不影响他上班 |
| 一个 C 端账号在一个主体下最多绑**一条**员工记录 | 否则"我是谁"在小程序里有两个答案 |
| 老板身份仍可走 C 端账号 | 入驻从 C 端发起，他本来就是消费者；也可以再绑员工登录 |

### 3.3 与已落地的 V44 的差距

| 现状（V44） | 目标 |
|---|---|
| `user_no` NOT NULL | 改为 `linked_user_no` 可空 |
| 无独立登录身份 | 加 `login_phone`，与 `linked_user_no` **至少有一个非空** |
| 身份解析只查 `user_no` | 两条路径都能解析到同一条记录 |

## 四、修订总结：比最初的方案小得多

| 我最初提的 | 实际需要 |
|---|---|

| 门店/员工/商品的归属全部换外键 | ❌ 不需要 —— 现在挂的已经是主体 |
| `prd_sku` 价格锚点迁移 | ❌ 不需要 |
| —— | ✅ `usr_store.payment_no`：门店 → 收款商户号的可变关联 |
| —— | ✅ 员工独立登录身份 + `linked_user_no` 可空 |
