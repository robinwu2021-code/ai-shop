## 一、总览

一笔钱从用户口袋到商家账户，要穿过**四段**，每段有各自的流水表：

| 段 | 谁付给谁 | 流水表 | 凭据 |
|---|---|---|---|
| ① 收款 | 用户 → 平台（收付通/直付通） | `stl_payment` | 通道回调原文 |
| ② 计提 | —（只记账，钱不动） | `stl_bill` | 支付成功即算定 |
| ③ 分账 | 平台 → 商家 | `stl_split_log` | 通道分账回执 |
| ④ 积分补差 | 积分池 → 二级商户账户（**商家不感知**） | `stl_payment`（`SUBSIDY`）+ `stl_points_pool` | 通道补差回执 |

![资金全链路表关系](./diagrams/topic-money.svg)

**商家只看到一个数**（V34）：

```
商家实收 = 订单金额（含被积分抵掉的部分）
         − 通道费 − 佣金 − 履约服务费 − 积分服务费
```

用户抵了多少分、平台补了多少、资金池 —— 对商家**全部不可见**。
对他而言这就是一笔 100 元的订单，卖了 100 就收 96。

账户里就是这个数：用户实付 70 + 平台补差 30 = 100，分账扣掉佣金后可提现 98。

积分抵扣掉的部分由**平台在分账前补进二级商户账户**（通道原生的补差接口，§二⑤），
所以商家账上直接就是订单全额 —— 不存在「应收与到账差一截」这回事。

### 表一览

| 表 | 段 | 职责 | 增长量级 |
|---|---|---|---|
| `ord_order` | ① | 主订单，一次支付 | 每次下单一行 |
| `ord_sub_order` | ①②④ | 子订单，**一次分账一条履约链**；金额拆分的落点 | 每单每商家一行 |
| `ord_after_sale` | ①③ | 售后单，退款的发起处 | 少量 |
| `stl_payment` | ① | **收款与退款流水**，带通道回执与对账状态 | 每次支付尝试一行 |
| `stl_bill` | ② | 结算单（按子单），计提与分账状态 | 每子单一行 |
| `stl_split_log` | ③ | 分账指令与回执，**append-only** | 每次分账调用一行 |
| `pts_user_ledger` | ④ | 用户积分真源；USE 行即一次兑付 | 每笔积分变动一行 |
| `stl_points_pool` | ④ | 积分营销资金账户流水（按 `market` × `pay_channel` 记账） | 与订单同量级 |
| `sys_pay_channel` | ①③④ | 支付通道注册表与能力位（`supports_subsidy` 等） | 每通道一行 |

## 二、分段

### ① 收款：`stl_payment`

**收款与退款在同一张表**，靠 `direction` 区分。退款是反向的同一件事 ——
通道回执结构一样、幂等要求一样、对账要一起做。拆两张表会有大量共同字段，
而对账时还得 union 起来。

三件事只有这张表能做：

| 做什么 | 靠哪列 | 没有它会怎样 |
|---|---|---|
| **重试幂等** | `payment_no`（本方流水号） | 退款失败重试变成退两次 |
| **逐笔对账** | `out_trade_no` + `trade_no` | 与通道账单核不上，只能人肉查订单 |
| **掉单发现** | `reconciled_at` 为空 | 用户付了钱我方没收到回调，**只能等投诉** |

`raw_notify` 存通道回调**原文**：解析后的字段不能举证，出纠纷时要原文。

> 一笔订单可能有**多次支付尝试** —— 超时关单后重下、切换支付方式、用户重复点击。
> `ord_order.pay_trade_no` 只是「成功那次」的快照，真源在这张表。

### ② 计提：`stl_bill`

**支付成功时就把账算定，但钱不动。** 四项扣减在这一刻全部确定：

| 列 | 来源 |
|---|---|
| `channel_fee_minor` + `channel_fee_rate` + `channel_fee_source` | 通道回执实扣，不是按费率算的 |
| `commission_minor` + `commission_rate` | 费率按 `traffic_source` 分档，下单时快照 |
| `service_fee_minor` | 自提单给承接方，非自提为 0 |
| `points_fee_minor` | 本单发分的费用金，结算时从货款扣走进积分池 |

`accrued_at`（计提）与 `split_at`（实际分账）**分开两列**：账面和资金是两个时点。

> 费率一律**落库快照**（`commission_rate` / `channel_fee_rate`）。
> 费率会调，历史账不能跟着变 —— 只存费率不存快照的话，调一次费率所有历史账单全变。

### ③ 分账：`stl_split_log`

**append-only**，一次调用一行，成功失败都记。`request_no` 是幂等号。

分账时点是**售后期结束**（货款解冻），与积分转可用同一时刻。
提前分账不会让商家多拿什么（冻结期内他本来就用不了），却要多写一条
「退款时回退分账」的失败路径 —— 所以**平台永远不用写佣金回退逻辑**。

### ④ 积分补贴：商家不感知

**商家侧没有积分账。** 他只感知一件事：开了积分，每笔订单要付一笔发分服务费
（`stl_bill.points_fee_minor`，像佣金一样按单计提）。

用户在他店里用积分抵扣时，他收到的仍是订单全额减各项费用 —— 差额由平台补，
这件事**不进他的账单**。

```
发分侧：stl_bill.points_fee_minor  →  stl_points_pool(IN, MERCHANT_RECEIVE)
补差侧：stl_payment(SUBSIDY)        →  stl_points_pool(OUT, MERCHANT_PAY)
```

> `V34` 删掉了 `pts_merchant_ledger` 与 `stl_points_bill`。
> 商家不感知积分抵扣之后，前者只剩发分服务费，与 `stl_bill.points_fee_minor`
> **一比一对应** —— 一比一的两份记录不是冗余备份，是一对迟早会不一致的账，
> 而不一致时没人知道该信哪一份。后者的 income 恒为 0，退化成 `stl_bill` 的聚合视图。

### ⑤ 积分抵扣：走通道原生补差（`V38`）

用户用积分抵扣时，进商家二级商户账户的现金就少了那一部分。
**微信收付通与支付宝直付通都提供了补差接口**：平台在**分账前**把差额转入二级商户账户。

| 步骤 | 动作 | 二级商户账户 | 平台账户 |
|---|---|---:|---:|
| 1 | 用户支付 70（商品 100，积分抵 30） | +70（冻结） | — |
| 2 | **平台调补差补 30**（支付成功即调） | +30（冻结） | −30 |
| 3 | 售后期结束，解冻并分账（基数 **100**） | −2 | +2 |
| 4 | 商家可提现 | **98** | — |

商家账单：**订单 100 − 佣金 2 = 实收 98**，与订单金额匹配。他看不到第 2 步。

#### 平台不欠商家钱

补差在用户支付的那一刻就补足了 —— **从头到尾不存在「欠款」这个状态**。
`V32` 曾为此建过 `stl_merchant_payable`（应付余额）与「少分」冲抵机制，
那是在「平台无法反向分账」这个**错误前提**上设计的，已于 `V38` 整套删除。

补差失败也不需要余额表兜底：**失败会阻断分账**，钱还冻结着，商家一分没拿到，
售后期全是重试窗口 —— 失败是**响亮的**，不是静默少给。
监控靠查 `stl_payment` 里未成功的 `SUBSIDY` 行，不靠一张表。

> 什么时候才需要商家侧账户：**除非将来商家可以「收积分」**（直接持有积分抵平台费用），
> 那时平台欠商家的是积分不是钱，需要的是商家积分账户，与应付余额不是一回事。

#### 通道能力决定能不能用积分

`sys_pay_channel.supports_subsidy = 0` 时，`canPoints()` 直接判否，
用户看到「当前支付方式不支持积分抵扣」。

**不做兜底记账** —— 那意味着一套余额表、冲抵逻辑、打款流程和监控，
而它服务的是一个尚不存在的通道。等真有了再说，那时的约束条件也才知道。

#### 池子的钱分散在两个账户

`stl_points_pool` 带 `pay_channel`，`balance_after` 按 `(market, pay_channel)` 各自累计。

商家发分的服务费进哪个账户取决于他的收单通道，补差从哪个账户出取决于用户这次走哪个通道，
而**用户的积分不分通道**。不按通道记账的话，账面永远是平的，
而两个真实账户一个溢一个空，**没有任何指标能看出来**。

跨通道净流动按期轧差调拨（生成建议，实际调拨走人工）。

#### 这笔钱在法律上是什么

三笔独立的资金动作，没有一笔在归集商户交易资金：

| 动作 | 性质 | 归集商户交易资金？ |
|---|---|---|
| 用户付款 → 商家二级商户号 | 交易资金 | **否**，直接进商家 |
| 分账扣商家的积分服务费 → 平台 | 平台的**技术服务费收入** | 否 |
| 补差 → 二级商户账户 | 平台**自己的钱**的支出（营销费用） | 否 |

**这就是平台优惠券的资金流**，只是券换成了积分 —— 官方文档里补差接口的典型场景
就是「平台出资的满 200 减 20」。二清的认定核心是归集商户交易资金再转付，
本方案后两笔之间**没有「代 A 把钱付给 B」这层法律关系**。

⚠️ 以上是设计意图说明，**不是法律意见**，最终定性要走法务与税务确认。

#### 池子是自筹的，不需要垫资

有多少流通中的积分，就有多少对应的现金压在池子里（恒等式 6）。而且时序上是**先收后付**：
费用金进池的时点（售后期结束解冻分账）与积分变得可用的时点**是同一个**，
而用户拿到分后不会当天花完。

唯一要守的是**红线余额**：佣金收入与池子的钱在同一个通道账户里，
可提现额 = 总余额 − 池子账面余额。没有这条线，一次正常的佣金提现就可能让补差失败。

#### 订单与收入怎么匹配

补差之后二级商户账户里就是订单全额，所以商家的收入口径与账户余额**天然一致**：

```
商家收入   100 元   ← 会计上确认这个数，按它开票缴税
账户入账   100 元   ← 用户实付 70 + 平台补差 30
分账扣走     2 元   ← 佣金
可提现      98 元
```

不再有「应收与到账差一截」的解释成本 —— 这正是选补差而不是少分的直接收益。

详细方案见 [积分抵扣的资金补差-方案](./积分抵扣的资金补差-方案.md)。

## 三、逐表详情

每张表一句话职责 + 关键列 + 设计要点。**逐字段清单见** [数据库-ER图](./数据库-ER图.md)（由迁移生成）。

### 3.1 `ord_order` —— 主订单

**一次支付**。用户视角：一次结算可以跨多个商家，合单支付。

| 列 | 说明 |
|---|---|
| `pay_amount` / `goods_amount` / `freight_amount` / `discount_amount` | 金额四段 |
| `pay_scene` | 下单端 `MP_WECHAT` / `MP_ALIPAY` / `IOS` / `ANDROID` / `H5` |
| `pay_channel` | 支付通道 `WECHAT` / `ALIPAY`。**端不等于通道** —— App 两个通道都能走 |
| `pay_trade_no` | 成功那笔的通道交易号，**快照**；真源是 `stl_payment`（一单可能多次支付尝试） |
| `pay_deadline_at` | 超时关单时点 |

### 3.2 `ord_sub_order` —— 金额拆分的落点

**一次分账一条履约链**。商家视角，所有费用拆分都落在这里。

| 列 | 说明 |
|---|---|
| `goods_amount` / `freight_amount` / `discount_amount` | 下单时的三段 |
| `discount_platform` / `discount_merchant` | 优惠**由谁承担**，决定佣金基数 |
| `pay_amount` | 用户实付。**已扣掉积分抵扣** |
| `points_deduct` / `points_deduct_minor` | 本单抵扣的分数与金额。**平台内部字段，不下发商家端** |
| `weigh_adjust_minor` | 称重差价：正 = 补款，负 = 退款 |
| `channel_fee_minor` | 通道手续费，按**用户实付**算（补差那部分不走支付通道） |
| `commission_minor` / `service_fee_minor` / `points_fee_minor` | 佣金 / 履约服务费 / 积分服务费 |
| `merchant_recv_minor` | **商家实收** = 订单金额 − 上面四项。补差后账户里就是订单全额 |
| `points_granted` | 发放幂等标记，防重复核销重复发分 |
| `traffic_source` | `MERCHANT_OWNED` / `PLATFORM`，下单时固化 —— 决定佣金档 |

### 3.3 `ord_item` —— 订单明细（商品快照）

**一行一个 SKU。** 它是金额拆分、积分发放、称重差价、按行退款的共同基础。

| 列 | 说明 |
|---|---|
| `sub_order_no` / `order_no` | 归属。索引都在这两列上 |
| `goods_no` / `sku_no` | 指向商品与规格 |
| `title` / `cover` / `spec` | **下单时快照**，不随商品改名改图变动 |
| `price` / `qty` / `amount` | 单价 × 数量 = 行金额。`price` 也是快照 |
| `category_type` | 品类，决定履约策略与可售规则 |
| `nominal_gram` | **标称克重**：`FRESH` 按重计价时下单锁定的重量 |
| `weighed` | 是否已实际称重。未称重时差价为 0 |
| `is_gift` | 赠品行：价格 0，不参与计价，**不发积分**（否则「买赠 + 积分」可叠出套利），履约时随单发出 |

**为什么必须存快照而不是 join 商品表**：下单到履约之间商品会改价、改名、下架。
join 的话历史订单会显示今天的价格 —— 用户看到的和他当初付的不一致，
而这在售后纠纷里是致命的：他截图的订单和系统里的对不上。

#### ⚠️ 这张表有四处缺口

都是「现在不报错，将来算不出账」的类型：

| # | 缺什么 | 后果 |
|---|---|---|
| 1 | **没有业务主键**（只有 `id`，无 `item_no`） | 现在**不算问题** —— 订单行不需要被外部引用，下单幂等由 `sys_idempotent` 保证。但第 2、4 条一旦落地，行就要被引用，那时才需要 |
| 2 | **没有积分列** | 发分是**按行算**的（每行 `points_config` 优先，赠品行不发），但行上不记「这一行发了多少分 / 扣了多少服务费」。退其中一行时**算不出该扣回多少积分** |
| ~~3~~ | ~~称重差价金额只在子单上~~ | **✅ `V39` 已补** `ord_item.weigh_adjust_minor`，子单那列改为汇总 |
| 4 | **售后是子单粒度，没有行级引用** | `ord_after_sale` 只有 `sub_order_no`。用户买三样只想退一样，现在没有表达方式 —— 这与「部分退款要不要支持」那条待决是同一个问题 |

第 2、4 条互相咬合：**部分退款一旦支持，第 2 条就立刻变成阻塞项** ——
退一行要扣回该行发的分，而那个数没地方查。第 1 条则是这两条的前置。

建议的补法（**未执行**，等产品先定「部分退款支不支持」）：

```
ord_item  + item_no          VARCHAR(64)  业务主键，UNIQUE
          + points_earn      INT          本行发放的积分数（赠品行为 0）
          + points_fee_minor BIGINT       本行的积分服务费
ord_after_sale + item_no     VARCHAR(64)  NULL = 整子单退，有值 = 退这一行
```

> 我起初把第 1 条写成「全库其他表都有 `xxx_no`，这张缺了」—— **那是错的**：
> 12 张表没有业务键，多数有正当理由（append-only 日志、配置表、购物车行）。
> 订单行同样不需要被外部引用，所以它现在不缺什么。**先查证再断言。**

### 3.3b `ord_status_log` —— 状态时间线

**append-only**，子单粒度。`operator_type`（`USER`/`MERCHANT`/`PLATFORM`/`SYSTEM`）
与 `operator_no` 一起留痕 —— 客服代客操作必须查得出是谁做的。

售后纠纷时它是「什么时候发生了什么」的唯一依据，所以只增不改。

### 3.3c 退款的通道约束

**两家都支持部分退款** —— 功能本身不是障碍，但有四条约束会反过来影响表设计：

| 约束 | 微信 | 支付宝 | 对本方案 |
|---|---|---|---|
| 部分退款 | 支持，**最多 50 次/单**，需换退款单号，**调用间隔 1 分钟** | 支持，多次需不同 `out_request_no` | 社区零售一单几件，够用。但**不能设计成「每件独立退」的高频路径** |
| 已分账后退款 | 先分账回退，再退款 | 同 | 我们分账在**售后期后**，期内退款不触发回退 |
| **分账回退授权** | **接收方必须已开启**，否则不支持 | 同，且要在商家平台开启 | ⚠️ **进件时没采集这个**，见下 |
| 接收方为个人 | **不支持回退** | 同 | 与「小微不参与积分」是同一类约束 |
| 回退后重新分账 | **不支持** | — | 用**部分回退**规避，不要全额回退再重分 |
| 单笔分账比例上限 | — | **最高 30%** | 我们分走 3–5%，安全 |

#### 分账回退授权（`V39` 已补）

`usr_merchant_payment.split_reversible` + `split_reversible_at`。

**这不只影响部分退款，任何售后期后的退款都撞这一条**（质量问题、法定退货权），
所以它是退款路径的前置依赖。为 0 时的失败时点最糟：

```
用户申请退款 → 商家同意 → 调通道 → 失败（接收方未授权）
→ 钱退不了，而用户已经在等，商家也已经答应了
```

记下来才能提前拦：要么进件流程里就要求授权，要么售后受理时先告知。
`split_reversible_at` 是排查用的 —— 授权之前成交且已分账的单，同样退不了。

上表那三条数字（50 次 / 60 秒 / 30%）也落进了 `sys_pay_channel`
（`max_partial_refunds` / `refund_interval_seconds` / `max_split_rate`）——
它们是查通道文档得来的**事实**，会随对方发版而变，放文档会漂移、放常量要发版才能改。

> `capability.test.ts` 有一条守卫盯着分账比例：平台分走的（佣金 + 积分服务费）
> 一旦逼近支付宝 30% 的上限就报错。**调过头的表现是分账被通道拒绝**，
> 而那时订单已经付过款了。

### 3.4 `ord_after_sale` —— 售后单

子单粒度。一个子单可以有多条（部分退款）。

| 列 | 说明 |
|---|---|
| `type` | `REFUND_ONLY` / `RETURN_REFUND` / `EXCHANGE` |
| `refund_minor` | 退款金额 |
| `points_offset_minor` | 积分扣不回来的部分，折现从退款里扣。**退款单必须明示** |
| `refund_payment_no` | 对应的退款流水（`stl_payment`）。退款要重试，重试要幂等 |
| `liability` | `PLATFORM` / `MERCHANT` / `PICKUP` —— 定责决定谁承担 |
| `split_reversed` | 已分账后退款，是否已回退分账 |
| `express_no` | **退货**单号 —— 与 `ord_sub_order.express_no`（发货单号）方向相反，不可混 |

### 3.5 `stl_payment` —— 资金流水

收款 / 退款 / 补差 / 补差回退 / 打款，**五种方向同一张表**：回执结构一样、幂等要求一样、对账要一起做。

| 列 | 说明 |
|---|---|
| `payment_no` | 本方流水号，**幂等键** |
| `direction` | `PAY` / `REFUND` / `SUBSIDY` / `SUBSIDY_REVERSE` / `PAYOUT` |
| `out_trade_no` | 我方给通道的号 —— **用户报障时报的是这个** |
| `trade_no` | 通道交易号 —— **对账单上是这个** |
| `raw_notify` | 回调原文，**唯一的资金凭据**（解析后的字段不能举证） |
| `reconciled_at` / `reconcile_batch` | 为空 = 未对账。**掉单只能靠这个发现** |

金额 `amount_minor` **恒为正**，方向看 `direction` —— 负数金额在通道对账单上没有对应概念。

### 3.6 `stl_bill` —— 结算单

按子单一张。支付成功即计提（`accrued_at`），分账在售后期后（`split_at`）—— **账面与资金是两个时点**。

| 列 | 说明 |
|---|---|
| `gross_minor` | 结算基数 = 订单金额。补差后账户里真实就是这个数 |
| `commission_rate` / `channel_fee_rate` | **费率快照**。费率会调，历史账不能跟着变 |
| `split_amount_minor` | 实际发起分账的金额 = 佣金 + 履约服务费 + 积分服务费。**分账指令以它为准**，不在发起时重算 |
| `pay_channel` | 分账实现按它路由，对账按它切分 |
| `fee_bearer` | 通道费由商家还是平台承担 |

状态机 `DRAFT → CONFIRMED → SETTLED`。

### 3.7 `stl_split_log` —— 分账回执

**append-only**，一次调用一行，成功失败都记。`request_no` 是幂等号
（注意与 `mkt_request.request_no` 同名不同义，**不可 join**）。

### 3.8 `pts_user_account` —— 用户积分账户

**派生缓存**，真源是流水。按 `(user_no, market)` 唯一。

| 列 | 说明 |
|---|---|
| `balance` | 可用余额。**只放能花的分** |
| `pending_balance` | 待生效（已发放未过售后期）。**不计入 balance** —— 合成一个数的话用户看到 500 却只能用 400，无法解释 |
| `expire_at` / `last_active_at` | **滚动到期**：任何积分变动都把到期日推后 |
| `expire_notified_at` | 到期提醒幂等位。到期是**一次性全部清零**，不提醒对用户是敌意的 |

### 3.9 `pts_user_ledger` —— 积分流水（真源）

`EARN` / `USE` / `REFUND` / `EXPIRE` / `REVOKE` 五种行，**没有批次概念**（`V30` 起按账户滚动到期）。

一张表两种形状，按 `biz_type` 分流后才能读：

| 只有 EARN 行有 | 只有 USE 行有 |
|---|---|
| `available_at`（售后期后才可用）、`issuer_merchant_no`（**仅统计**，不参与资金） | `acceptor_merchant_no`、`amount_minor`、`rate_snapshot`、`status`、`period` |

### 3.10 `stl_points_pool` —— 积分营销资金账户

**平台自己的钱**，用于兑现平台发出的积分（同平台优惠券补差）。

| 列 | 说明 |
|---|---|
| `pool_type` | `MERCHANT_RECEIVE` 收商家发分服务费 / `MERCHANT_PAY` 补差给二级商户 / `EXPIRE_INCOME` 到期转平台收入 / `RECOVERY` / `PENALTY` / `BAD_DEBT` |
| `pay_channel` | **钱实际在哪个通道账户**。`balance_after` 按 `(market, pay_channel)` 各自累计 |
| `ref_no` | 关联单据 |

### 3.11 `sys_pay_channel` —— 通道注册表

**表管能力，类型管取值**：取值域在代码的 `PayChannel` 联合类型里，能力位在表里。

| 列 | 说明 |
|---|---|
| `supports_subsidy` | **能否补差 —— 为 0 则该通道不开积分抵扣**（`canPoints()` 判否），不做兜底记账 |
| `supports_split` / `supports_payout` | 能否分账 / 能否打款给商家 |
| `pay_methods` / `markets` | 支付方式、可用市场 |
| `pool_account_ref` | 平台在该通道的资金账户标识，**只存对账引用，不存密钥或完整账号** |

由 `capability.test.ts` 断言 seed 行与联合类型一致 —— 只有表会冒出谁都没定义过的通道，
只有类型则每次通道调整都要发版。

## 四、注意事项

### 恒等式

对账任务校验，违反即告警：

| # | 恒等式 | 违反说明 |
|---|---|---|
| 1 | `stl_payment(PAY, SUCCESS)` 金额 == `ord_order.pay_amount` | 收款与订单对不上 |
| 2 | `stl_payment` 中 `reconciled_at` 为空且 `succeeded_at` 超过 T+2 | **掉单或通道未出账** |
| 3 | `stl_bill.net_minor` == `ord_sub_order.merchant_recv_minor` | 计提与订单快照分叉 |
| 4 | `Σ stl_split_log(SUCCESS)` == `stl_bill.split_amount_minor` | 分账金额与结算单不符 |
| 4b | `stl_bill.split_amount_minor` == 佣金 + 履约服务费 + 积分服务费 | 分账金额算错，商家多拿或少拿 |
| 4c | `stl_payment(SUBSIDY, SUCCESS)` 金额 == `ord_sub_order.points_deduct_minor` | **补差没补足**，商家实收对不上订单 |
| 4d | 已分账的子单，其 `SUBSIDY` 行必须是 `SUCCESS` | 补差失败却放行了分账 —— 商家少收且无人知晓 |
| 5 | `Σ ord_sub_order.points_deduct_minor` == `Σ pts_user_ledger.amount_minor(USE, CONFIRMED)` | **货款账与积分账对不上** |
| 6 | 池子余额 == Σ 流通中积分 × 汇率 | 有分没钱，或有钱没分 |
| 7 | 每个 `(market, pay_channel)` 的池子余额 ≥ 0 | 跨通道错配已抽干一侧，该轧差调拨了 |

第 5 条是两本账唯一的勾稽点，由 `packages/shared/tests/schema-lineage.test.ts` 守住通路。

### 容易看错的地方

**商家实收只有一个口径**：`ord_sub_order.merchant_recv_minor` = 订单全额 − 各项费用。
补差之后账户里就是订单全额，所以它同时是**会计收入**、**账户入账**与**分账基数** ——
`V34` 之前这里曾是两个数（货款路 + 积分路按账期结），那套已随补差方案废除。

**同名不同义，不可 join：**

| 列 | 差别 |
|---|---|
| `request_no` | `mkt_request` 是求团需求单号；`stl_split_log` 是分账幂等号 |
| `express_no` | `ord_sub_order` 是发货单号；`ord_after_sale` 是退货单号，**方向相反** |

**通道费用两处都有**：`ord_sub_order.channel_fee_minor` 是支付时按费率算的预估，
`stl_payment.channel_fee_minor` 是回执实扣。**以回执为准** —— 两者不一致时是费率配置过期了。

**`channel` 与 `pay_channel` 不是一回事**：`mkt_attribution.channel` 是**归因渠道**
（流量来源，VARCHAR(64)），支付侧一律叫 `pay_channel`（VARCHAR(16)）。
血缘守卫只查 `*_no` 结尾的业务键，看不见这一对 —— `V38` 靠改名解决。
