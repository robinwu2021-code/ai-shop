关联：[多渠道推送与运营端触达配置](./多渠道推送与运营端触达配置-设计.md)（provider 路由 + 场景×通道，已实现）· [触达能力矩阵](./触达能力矩阵.md)（通道现状权威）· [TDD-通知与消息推送](./TDD-通知与消息推送.md) · [ADR-018](../ADR/ADR-018-App生产形态与推送通道.md)

## 0. 这份方案要解决的问题

触达能力现在是**对的但散的**：短信、邮件、微信订阅、聚合推送（个推）、平台直连推送
（FCM/APNs）、站内信各自能用，但代码分散在三个模块、配置一半在环境变量一半在库、
「渠道」这个概念没有一等公民 —— 想回答「平台现在有哪些渠道、各自什么状态、谁能开关它、
商家能不能自带一套」都得翻代码。

本方案把它抽象成一个**独立的触达中台模块**，让「渠道」成为可登记、可配置、可启停、
可观测的一等实体，并把三类接入（平台接入 / 外部接入 / 测试接入）统一到一个模型下。

**范围**：短信、邮件、聚合推送、各平台直连推送、平台站内信、渠道配置/状态/启停、
外部/平台/测试接入、推送记录、运营端管理。**不含**：具体业务事件何时触达（那是各领域
的编排，仍留在领域侧，只调中台的门面）。

## 1. 现状盘点（已核对代码，2026-08-17）

| 层 | 现在在哪 | 内容 |
| --- | --- | --- |
| 领域 SPI | `shop-base/spi/notify` | `SmsPort`/`MailPort`/`WxSubscribePort`/`PushPort`/`PushGateway`/`PushProvider`/`SendResult`/`NotifyBizType` |
| 网关实现 | `shop-channel/notify/port` | Ali短信、SMTP邮件、微信订阅、个推、FCM、APNs + 各自 Stub；`PushCrypto` |
| 编排/服务 | `shop-core/message` | `NotificationConsumer`(事件→触达)、`MessageService`(站内信)、`PushRouter`(按 provider 分发)、`PushSender`、`SceneChannelRouting`、`WxSubscribeSender`、`NotifyLogWriter`、`NotifyChannelService`(体检)、`NotifyLogService` |
| 端点 | `shop-core/message/api` | ops：通道体检/模板/频控/场景通道/记录；biz/mp：站内信、push-token |
| 表 | 迁移 | `msg_message`(站内信)、`msg_template`(模板)、`msg_scene_channel`(场景×通道)、`msg_push_token`(设备)、`msg_subscribe`(订阅额度)、`sys_notify_log`(记录) |
| 配置 | `application.yml` + env | `shop.sms.*`/`shop.mail.*`/`shop.wx.*`/`shop.push.{getui,fcm,apns}.*`，`@ConditionalOnProperty(stub)` 决定装哪个 bean |

**四个痛点**：
1. **「渠道」不是实体**：开关靠 `@ConditionalOnProperty` + 部署期环境变量，运营要开一条渠道得改配置重启；
2. **配置两处分裂**：启停在环境变量、模板号/频控/场景在库 —— 状态从哪看不统一；
3. **只有平台一套接入**：商家不能自带短信签名 / 推送账号（外部接入无位置）；
4. **记录不分供应商**：`sys_notify_log.channel=PUSH` 把个推/FCM/APNs 混在一起，拆不出各家计数（见上一方案 §运营体检的取舍）。

## 2. 核心抽象：两根正交的轴

一条「渠道」由**两根正交的轴**定位，别混成一个枚举（合并会让非法组合在类型上可表达，同 ADR-013 教训）：

- **轴 A · 通道类型 × 供应商**（谁来投递）：
  `SMS/{ali,…}`、`MAIL/{smtp,…}`、`PUSH/{getui,fcm,apns}`、`INAPP/{internal}`、（预留）`WXSUB/{wechat}`
- **轴 B · 接入范围**（用谁的凭据、发给谁）：
  - `PLATFORM` **平台接入** —— 平台统一账号，默认；
  - `MERCHANT` **外部接入** —— 商家自带凭据（自己的短信签名 / 推送应用），只服务该商家；
  - `TEST` **测试接入** —— 桩 / 沙箱，不真发，本地与测试默认走它。

> **一条渠道实例 = (通道类型, 供应商, 接入范围, 归属租户, 凭据引用, 启停, 状态, 优先级)**。
> 「平台的个推」「商家 M0001 自带的阿里短信」「测试桩短信」是三条不同实例，各有启停与状态。

「聚合推送」（个推）与「各平台独立推送」（FCM/APNs）在此模型里都是 `PUSH` 通道下的不同**供应商**，
已有的 [`PushRouter`](./多渠道推送与运营端触达配置-设计.md) 就是 PUSH 通道内的供应商路由，本方案把它上升为
**所有通道通用的渠道选择器**。

## 3. 模块边界与依赖方向

新增 Maven 模块 **`shop-notify`**（触达中台）。依赖方向保持领域不感知通道：

```
  领域(shop-core/order/merchant…) ──调用──▶ 触达 SPI (shop-base/spi/notify)  ◀──实现── shop-notify
                                                                                          │
                                     shop-notify 依赖 shop-base(SPI) + 通道 SDK(纯 JDK)   │
```

- **`shop-base/spi/notify`（不动）**：领域面向的契约。领域只说「发什么」，永不感知渠道/供应商/接入范围。
- **`shop-notify`（新，收敛）**：
  - `channel/` 渠道注册表 + 状态机 + 选择器（原 `PushRouter` 泛化）；
  - `gateway/` 各供应商网关（从 `shop-channel/notify/port` 迁入）+ Stub；
  - `dispatch/` 统一发送门面 + 留痕（原 `PushSender`/`NotifyLogWriter`/各 `NotifyLogging*Port` 装饰器）；
  - `template/`、`quota/`（模板、频控）；
  - `api/ops/` 运营端渠道治理端点。
- **`shop-core/message`（瘦身留下）**：
  - `NotificationConsumer`（业务事件→收件人解析→调 SPI）—— 它知道「谁该收到来单提醒」，是领域知识，留在领域侧；
  - `MessageService` 站内信**写**入口作为 `INAPP` 通道实现下沉到 shop-notify，但**收件箱读**（`msg_message` 列表/未读）是用户域，留在 shop-core。

> **为什么 SPI 留在 shop-base 而不进 shop-notify**：领域若依赖 shop-notify 就形成
> 领域→通道的反向依赖。SPI 在 shop-base，领域与中台各自依赖它，方向永远是「领域→契约←中台」。

## 4. 数据模型

### 4.1 新增 `notify_channel`（渠道实例注册表）

```
notify_channel
  channel_no    VARCHAR   -- 渠道编号（业务主键）
  channel_type  VARCHAR   -- SMS / MAIL / PUSH / INAPP / WXSUB
  provider      VARCHAR   -- ALI / SMTP / GETUI / FCM / APNS / INTERNAL / WECHAT
  scope         VARCHAR   -- PLATFORM / MERCHANT / TEST（接入范围，轴 B）
  owner_no      VARCHAR   -- scope=MERCHANT 时的商家号；PLATFORM/TEST 为空
  enabled       TINYINT   -- 运营启停（软开关，不重启）
  status        VARCHAR   -- 见 §5 状态机：UNCONFIGURED/STUB/READY/DISABLED/DEGRADED
  priority      INT       -- 同类型同供应商多实例时的选择优先级
  cred_ref      VARCHAR   -- 凭据引用键（指向 env 前缀，**不存密钥明文**，见 §6）
  config_json   JSON      -- 非密参数（签名/模板号/topic/projectId 等，可回显）
  last_health_at DATETIME -- 上次体检时刻
  last_health_ok TINYINT
  tenant_no, 审计列…
  -- 唯一键 (channel_type, provider, scope, owner_no)
```

### 4.2 复用 / 演进现有表

| 表 | 处置 |
| --- | --- |
| `sys_notify_log` | **加 `channel_no` + `provider` 列**：记录归到具体渠道实例，解决「个推/FCM/APNs 拆不开计数」；旧行 provider 回填 GETUI/按 channel 猜 |
| `msg_scene_channel` | 保留（场景×受众×通道开关）；语义不变，`channel` 维度对齐 `notify_channel.channel_type` |
| `msg_template` | 保留（模板正文/服务商模板号/启停） |
| `msg_push_token` | 保留（已含 provider） |
| `msg_subscribe` | 保留（订阅额度/频控计数） |
| `msg_message` | 保留（站内信 = INAPP 通道的落地表，也是收件箱） |

> **不为「统一」而重命名 msg_* → notify_***：重命名要改实体/迁移/前端契约一大片，风险远大于收益；
> 新表用 `notify_` 前缀，旧表保留 `msg_` 前缀，文档里说明「同一个中台的两代命名」即可。

## 5. 渠道状态机

`status` 由三个事实推导，不手填（手填必与现实分叉）：

```
UNCONFIGURED  凭据缺失（cred_ref 指向的 env 未配齐）           —— 运营看：要去配密钥
STUB          走桩（本地/测试，或平台故意挂桩）                —— 不真发，只留痕
READY         凭据齐 + enabled=1                              —— 真发
DISABLED      凭据齐但 enabled=0（运营主动关）                 —— 暂停
DEGRADED      READY 但最近一次体检/发送失败率超阈值            —— 报警，仍尝试发
```

- 派生规则：`!credsPresent → UNCONFIGURED`；`stubFlag → STUB`；`!enabled → DISABLED`；
  `enabled && credsPresent && healthOk → READY`；`… && !healthOk → DEGRADED`。
- **启停是软开关**：`enabled` 在库，运营点一下即时生效（选择器每次读），不重启、不改环境变量。
- **桩仍由部署期决定**：`STUB` 来自 `shop.*.stub`，是安全底线（本地不真发），不给运营在生产随手关桩的口子。

## 6. 配置模型：密钥归 env，治理归库（一条铁律）

沿用并固化现有边界（[NotifyChannelService](../../..) 注释里那条「密钥明文永不出后端」）：

| 项 | 存哪 | 谁改 | 为什么 |
| --- | --- | --- | --- |
| 密钥（AK/SK/masterSecret/私钥/password） | **环境变量**，库里只存 `cred_ref` 前缀 | 运维 | 能在 Web 读出生产密钥的接口泄漏一次就是全平台可群发 |
| 非密标识（签名/模板号/appId/projectId/topic） | `notify_channel.config_json`，可回显 | 运营 | 本就印在短信/推送里，运营要能核对端上是否同值 |
| 启停 / 优先级 / 场景路由 | 库 | 运营 | 策略要不发版就能改 |
| 桩开关 | env（`shop.*.stub`） | 运维 | 安全底线，不给生产关桩口子 |

> **外部接入（商家自带）的密钥怎么办**：商家不该把密钥交给运维塞 env。为 `scope=MERCHANT` 的渠道
> 引入**加密列**（`config_json` 里的敏感段用平台 KMS/对称密钥加密存库，读时解密进内存、永不回前端明文）。
> 这是平台接入（env）与外部接入（加密库）唯一的配置差异，单列说明，**一期可只做平台接入 + 测试接入，外部接入留 P 后期**。

## 7. 发送链路（统一门面 + 渠道选择）

领域侧不变（仍调 `SmsPort`/`PushPort`/…）。中台内部统一为：

```
领域调 SPI（发什么：目标 + 内容 + bizType + 级别）
  → NotifyDispatcher（门面，实现各 SPI）
      → ChannelSelector：按 (通道类型, 目标所属租户, 设备 provider) 选渠道实例
            · 先 scope=MERCHANT(该商家自配且 READY) → 否则 scope=PLATFORM → 测试环境 scope=TEST
            · PUSH 通道内再按设备 provider 选 GETUI/FCM/APNS（现有 PushRouter 逻辑）
      → 命中实例的 Gateway.send(...)
      → 留痕 notify_log（channel_no + provider + status + providerMsgId/error）
      → 失败：站内信必达兜底不变；外发通道失败留痕不阻塞
```

- **站内信必达原则不变**：INAPP 恒发、不受 `notify_channel` 启停影响（事实记录不能被开关抹掉），与
  [场景×通道方案](./多渠道推送与运营端触达配置-设计.md) 一致。
- **频控位置不变**：仍只作用于 `MARKETING`，交易/待办不受限。

## 8. 三类接入的落地

| 接入 | 是什么 | 一期 |
| --- | --- | --- |
| **平台接入** `PLATFORM` | 平台统一账号（现在就是它）。渠道实例凭据走 env，运营管启停/非密项/场景 | ✅ 做 |
| **测试接入** `TEST` | 桩 + 沙箱。本地/测试默认；运营端「模拟发送」按渠道预览与试发（现有能力归位到渠道维度） | ✅ 做 |
| **外部接入** `MERCHANT` | 商家自带凭据，只服务该商家（自有签名/推送应用）。需加密列 + 商家端配置页 | ⏸ 留后期（P 之后），一期把模型位置留好（scope/owner_no/加密列设计定下） |

## 10. 迁移策略（Strangler，不停机不改行为）

**默认行为逐格不变**是硬约束（种子 = 现状），分期用绞杀者模式把散落代码收进 `shop-notify`：

| 阶段 | 内容 | 风险 |
| --- | --- | --- |
| **N1 · 起模块 + 迁网关** | 建 `shop-notify`，把 `shop-channel/notify/port/*` 网关与 `PushCrypto` 迁入；SPI 不动、行为不变 | 低（纯搬家 + 改 import） |
| **N2 · 渠道注册表** | `notify_channel` 表 + 注册表 + 状态派生；种子把现有 5 类通道各登一条 `PLATFORM` + 一条 `TEST`；`NotifyChannelService.health()` 改从注册表读 | 中（体检数据源切换，有测试兜底） |
| **N3 · 统一门面 + 选择器** | `NotifyDispatcher` + `ChannelSelector`，把 `PushSender`/`PushRouter`/各 `NotifyLogging*Port` 收敛；`sys_notify_log` 加 channel_no/provider | 中（发送链路重构，端到端测试护住） |
| **N4 · 运营渠道管理页** | 渠道列表 + 软启停（enabled）+ 非密项编辑；发送记录加 provider 筛选 | 低（读写现有表） |
| **N5 · 外部接入（可选）** | `scope=MERCHANT` + 加密列 + 商家配置页 | 高（多租户 + 密钥，单独立项） |

每阶段自带守卫：渠道注册表种子必须覆盖代码里的（通道类型×供应商）枚举；`notify_log` 的 channel_no
必须能在注册表里找到；站内信恒发不可关的断言。

## 11. 决策与取舍

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 抽成独立模块 | `shop-notify`，SPI 仍留 shop-base | 领域不反向依赖通道；中台可独立演进/测试 |
| 通道模型 | 通道类型 × 供应商 × 接入范围 三者正交 | 合并成一个枚举会让非法组合可表达（ADR-013 教训） |
| 密钥 | 永远 env，库只存 cred_ref + 非密项 | 泄漏一次即全平台可群发；这条边界不让步 |
| 启停 | 软开关在库、桩开关在 env | 运营要能不发版改策略；桩是安全底线不给生产口子 |
| 表命名 | 新表 `notify_`，旧表保留 `msg_` | 重命名的改动面远大于收益 |
| 站内信 | 恒发、不入渠道启停 | 事实记录不能被开关抹掉 |
| 外部接入 | 一期只留模型位置，实现后延 | 多租户 + 密钥加密是独立重活，不阻塞平台接入落地 |
| 迁移 | 绞杀者分五期，种子 = 现状 | 默认行为逐格不变，可回滚 |

## 12. 风险

- **发送链路重构（N3）**碰核心触达，靠现有端到端测试（`NotifyEndToEndFlowTest`、`PushNotifyFlowTest`）与
  新增门面单测护住；种子保证默认行为不变。
- **`sys_notify_log` 加列**要同步 `schema-test.sql` 与实体（entity-alignment 守卫），且旧行 provider 回填有歧义 —— 用 channel 推断 + 标注。
- **外部接入的密钥加密**若一期硬上会拖慢平台接入落地，故明确后延。
