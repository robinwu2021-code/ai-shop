# 一 · 「系统支持的行业」是两张清单，先分清

| 清单 | 在哪 | 语义 | 内容 |
|---|---|---|---|
| **准入清单** | `sys_industry`（7 行种子） | 平台**收不收**这类商家（进件白名单、强制积分） | CATERING / RETAIL / LIFE_SERVICE / ENTERTAINMENT / TRANSPORT / ONLINE / OTHER |
| **工作流清单** | `mch_store.industry_pkg`（规划中） | 收进来之后**按什么流程做生意** | RETAIL（基线）/ FOOD / BEAUTY，共 3 个 |

**7 ≠ 3 不是缺陷，是现状**：休闲娱乐、交通出行、线上虚拟的商家今天可以入驻，
但只能按零售基线的流程卖东西。本册回答的问题是：**这 7 类商家的商品需求，V2 设计接得住多少** ——
接不住的部分，就是工作流清单未来扩张时商品域要补的账。

业态细分（需求按业态梳理，行业太粗）：

| sys_industry | 业态 | 已梳理？ |
|---|---|---|
| CATERING | 正餐 / 快餐档口 / 茶饮咖啡 / 烘焙 | ✅ 三行业梳理已覆盖 |
| RETAIL | 便利超市 / 生鲜果蔬 | ✅ 同上（基线） |
| LIFE_SERVICE | **美业**（已梳理）/ **家政保洁** / **维修安装** / **洗衣** / **宠物服务** | ⚠️ 美业之外四个业态**本册补** |
| ENTERTAINMENT | **棋牌·台球·KTV** / **健身·瑜伽** / **密室·剧本杀** / 亲子乐园 | ❌ 本册补 |
| TRANSPORT | **搬家货运** / 代驾 | ❌ 本册补 |
| ONLINE | 虚拟商品 / 卡券 | ❌ 本册补 |
| OTHER | 兜底，无业态 | —（不梳理，收进来按零售基线） |

图例：✅ 现模型直接覆盖 · 🔧 配置即可（ProductType/数据，零发版）· 🧩 需新 Trait（一次发版）· ↗ 不在商品域 · ❓ 待定

# 四 · 缺口收敛：7 条缺口其实是 4 个设计题

## 4.1 「按实计量结算」是一个题，不是三个 —— METERED Trait

加时按半小时（H-06）、KTV 按时（K-01/02/03）、搬家按里程（T-02/05）——
**与已有的 CATCH_WEIGHT（按实际称重结算）是同一个模式**：

```
下单：按标称量出预估价（或 0 元开台）
结算：按实测量 × 费率表出实价，差额进订单行调整（既有 weighAdjustMinor 的先例）
```

设计方向：把 CATCH_WEIGHT 泛化成 **`METERED(dimension)`**，dimension ∈ {WEIGHT, TIME, DISTANCE}，
带费率表（起步量 + 起步价 + 步长 + 步长价 + 分时段费率行）。
**订单域不用改结构** —— 称重差价那条链路已经证明过「按实结算」在主干上是通的。

## 4.2 「先收后抵」—— 上门费/检测费（X-01/02）

下单收 30 上门费 → 报价确认 → 尾款单里抵 30。
本质是**两张订单 + 一次抵扣**，与「定金—尾款」同构（那是二期预定要做的东西）。
**商品域只需一个标记**（此商品为可抵扣费用项）；抵扣链路属交易域，与预定共用一套。**不单独建。**

## 4.3 「按区间数量计价」—— 寄养按晚（P-02）

价 = 单晚价 × 晚数，节假日晚用不同价行。
`sell_price_entry` 的 valid 窗口已能表达节假日价；缺的是**订单行数量 = 日期区间长度**这个下单形态。
**商品域零改动，预约域加日期区间占用** —— 归预约域的账。

## 4.4 卡的第三种形态 —— PERIOD 期限卡（G-01）

会员资产今天规划了 TIMES（次卡）与 VALUE（储值）。健身会籍是 **PERIOD：期限内不限次**。
`mbr_card` 已有 `expire_at`，缺的只是「不扣次」的核销口径。**会员资产域加一个枚举值的事**，
商品域的 CARD 类型带 `card_kind` 即可。

## 4.5 Modifier 的两个小扩展（顺带）

- **负加价**（自带工具 −10）：`price_delta` 允许为负，但要加不变量「行合计不得为负」；
- **按比例加价**（加急 +50%）：`price_delta_pct` 与定额二选一。
两者都是 Modifier 表加列，**不动结构**。

## 4.6 纪律：缺口记账，不预建

按仓库一贯的口径（默认关的那一半没人测；YAGNI）：
**上面 4 个设计题，只有对应业态真的入驻时才施工。**
本册的产出是「账本」——缺什么、归哪个域、大概多大 —— 不是排期。
唯一建议提前的是 **4.1 的 METERED 泛化方向**要在实现 CATCH_WEIGHT 时就留好形状
（费率表独立成对象，不要把「克重单价」写死在称重逻辑里），因为改形状比加形态贵。

# 五 · 对 V2 设计的三条修订建议

1. **Trait 清单加注「已验证业态」列**：每个 Trait 标注它被哪些业态的哪条需求消费 ——
   防止 Trait 变成想象出来的抽象（本册 §三 就是首版数据源）。
2. **`CatchWeight` 更名/泛化为 `Metered` 预留 dimension** —— 见 §4.1，趁还没写代码。
3. **商品加「售后策略」字段**（V-03）：实物默认七天退、虚拟不可退、服务类按预约取消规则 ——
   一列 + 取值域，交易域售后按它分流。这条三行业其实也要（餐饮退菜、美业退卡各有口径），
   之前的梳理漏了它。
