## L1 · 这份补什么

已有的 API 设计册定了**分层与契约规则**（四类接口、金额一律分、
时间一律毫秒、状态一律码+文案、契约先行）。这份补的是这一轮要的东西：

1. **金额在多币种下怎么表达** —— 现有规则「金额一律 Minor」不够（§二）
2. **动钱的写操作要幂等** —— 今天只有下单有（§三）
3. 三端要新增的端点（§四–§六）
4. 与现有端点的差集（§七）

写法同前几份：从需求出发，最后与现有端点对齐。

## L2 · 二、金额：`Minor` 不够了

### 问题

现有契约里金额是一个裸数字：`amountMinor: 12345`。
单币种下这没问题 —— 端上除以 100 显示成 `123.45`。

**多币种下这条会算错**，而且不报错：

| 币种 | 小数位 | `amountMinor: 100` 的真实含义 |
|---|---:|---|
| 人民币 CNY | 2 | 1.00 元 |
| 日元 JPY | **0** | **100 日元** |
| 科威特第纳尔 KWD | **3** | **0.1 第纳尔** |

端上按 2 位除的话，日元会**少显示 100 倍**，第纳尔会**多显示 10 倍**。
这不是显示瑕疵 —— 用户看到的付款金额是错的。

### 决定

**响应里的金额一律带币种，小数位由市场元数据给。**

```jsonc
// 金额的标准形状
{ "amountMinor": 12345, "currency": "CNY" }
```

小数位**不逐个金额带** —— 一个页面上几十个金额，每个都带一遍
既冗余又给了「两处不一致」的机会。端在启动时拉一次市场元数据：

```
GET /mp/market           → [{ market, name, currency, currencyScale, displayRate }]
```

**关键的保护**：端拿不到市场元数据时**不显示金额**，
而不是回落到 2 位。<b>回落是这条链上唯一会静默算错的地方</b> ——
显示不出来是明显的故障，显示错 100 倍不是。

> 为什么不干脆返回格式化好的字符串（`"¥123.45"`）：
> 那样端上没法做加减、没法排序、没法按用户语言换货币符号位置
> （阿拉伯语是 `123.45 ر.س`）。**格式化是端的事，口径是服务端的事。**

### 迁移

现有响应里的裸金额字段**不改名、不删** ——
加一个同级的 `currency` 字段即可，端上按有没有它决定用新逻辑还是旧逻辑。
单币种期间两条路结果一样，<b>而这正是可以安全上线的原因</b>。

## L2 · 三、幂等：动钱的写操作一个都不能少

### 现状

仓库里有幂等执行器（`Idempotency-Key` 命中就返回首次结果），
但**只有下单一处在用**。

**真正动钱的写操作一处都没有**：发起支付、退款、放款、
提现审批、保证金扣划、欠款核销。

后果不是理论上的：用户在弱网下连点两次「去支付」、
运营页面重复提交一次放款、通道回调重推 —— 这三件事天天发生。
今天靠各自的业务幂等挡（比如「复用未终态的收款」），
<b>而业务幂等是逐个写的，写漏一个没有任何东西会提醒</b>。

### 决定

| 端点类 | 幂等键 | 谁生成 |
|---|---|---|
| C 端发起支付 | `Idempotency-Key` 头 | 端上生成，一次收银台会话一个 |
| C 端申请退款 | 同上 | 端上 |
| 运营端放款 / 挂起 / 解挂 | 同上 | 运营端，按钮点击时生成 |
| 运营端提现审批 / 保证金扣划 / 欠款核销 | 同上 | 同上 |
| 通道回调 | **不用头**，用通道单号 | 通道回执自带 |

**通道回调那一行是刻意的**：通道不会给我们幂等头，
它给的是商户单号 + 通道交易号。<b>用那两个做键，
比要求通道配合更可靠</b>。

**加一条闸门**：所有 `/ops/**` 与 `/mp/**` 下动钱的 `POST`
必须走幂等执行器 —— 这可以做成一条静态检查，
按路径前缀 + 方法名匹配，漏一个当场红。

## L2 · 四、C 端（`/mp`）

需求矩阵里 C 端八条应有里四条缺，对应四个端点动作。

| # | 端点 | 说明 |
|---|---|---|
| **C-1** | `GET /mp/order/{orderNo}/pay-method` | **这一单可用的支付方式。**已经算好交集（市场 × 类目支付方式 × 门店通道锁 × 各商家进件），端上直接渲染 |
| **C-2** | `POST /mp/order/{orderNo}/pay` | 已有。**body 增加 `payMethod`**；带 `Idempotency-Key` |
| **C-3** | `POST /mp/order/{orderNo}/pay`（同一个） | **换一种方式重付走同一个端点** —— 见下 |
| **C-4** | `GET /mp/market` | 市场元数据（币种、小数位、展示汇率）。端启动拉一次 |

### C-1 的返回形状

```jsonc
{
  "currency": "CNY",
  "methods": [
    { "methodCode": "MINIPROGRAM", "payChannel": "WECHAT",
      "name": "微信支付", "icon": "...", "available": true },
    { "methodCode": "ALIPAY_H5", "payChannel": "ALIPAY",
      "name": "支付宝", "available": false,
      "unavailableReason": "该店铺尚未开通支付宝收款" }
  ]
}
```

**不可用的方式也返回，并带原因。**
过滤掉的话用户会问「为什么别人有支付宝我没有」，而客服答不上来。
<b>原因文案由服务端出</b>（沿用既有契约规则）。

⚠️ **空列表与「未配置」要分开。**
一个商家都没配支付方式时（进件还没走完），
今天的代码把交集当作「未配置」跳过而不是「一种都不支持」——
这条语义**必须在 API 上也体现**：

```jsonc
{ "methods": [], "configured": false }   // 未配置：端上照常允许下单，钱先欠着
{ "methods": [], "configured": true }    // 真的一种都不支持：端上拦
```

两者在端上是相反的动作。合成一个空数组的话，
<b>一个完全正常的订单会被拦死</b>。

### C-3 换一种方式重付

**不新增端点**，复用 `POST /mp/order/{orderNo}/pay`：

- 该订单有**未终态**收款 → 返回那一笔的参数（同一个商户单号）
- 该订单的收款已**关闭/失败** → 开新的一笔，商户单号加尝试序号

后端 2026-09-01 已经支持换号。**端上要做的是把这条路暴露出来**：
支付失败页给一个「换一种方式」的入口，回到 C-1 重选。

> 今天这条能力<b>没有任何用户能触达</b> —— 后端有测试有守卫全绿，
> 而端上没有入口。这是「做了一半」最典型的形状。

## L2 · 五、B 端（`/biz`）

| # | 端点 | 说明 |
|---|---|---|
| **B-1** | `GET /biz/merchant/pay-channel` | 已有。**改为按本商家的市场筛** —— 今天传的是「不限市场」 |
| **B-2** | `POST /biz/merchant/payment` | 已有（提交进件）。**响应补驳回原因的中文说明** |
| **B-3** | `GET /biz/settle/bills` 等 | 已有。**响应金额补 `currency`** |

### B-2 的驳回原因

通道退回的是英文码（`NOT_MATCH_CERT`、`OUT_OF_BUSINESS_SCOPE`…）。
**要有一份码 → 中文说明 + 怎么改的映射**，由服务端出：

```jsonc
{
  "applyStatus": "REJECTED",
  "rejectCode": "OUT_OF_BUSINESS_SCOPE",
  "rejectReason": "营业执照的经营范围不含所选类目",
  "howToFix": "换一个在经营范围内的类目，或先去市场监管部门增项"
}
```

**三个字段都要**：码给程序判、原因给商家看、怎么改让他不用来问客服。
只给码的话商家看到的是一串大写字母。

## L2 · 六、平台端（`/ops`）

需求矩阵里平台端缺的五条，对应五组端点。

### 市场

| 端点 | 说明 |
|---|---|
| `GET /ops/markets` | 全部市场（含未启用） |
| `POST /ops/markets` | 新增。**币种与小数位一旦有交易就不可改** |
| `PUT /ops/markets/{market}` | 改名、改排序、启停 |

⚠️ **币种与小数位要有改动保护**：改它等于换账本。
接口层面禁止 —— 已有该市场的交易时返回明确错误，
而不是「改了但历史数据不动」那种半吊子行为。

### 支付方式

| 端点 | 说明 |
|---|---|
| `GET /ops/pay-methods` | 全部方式及其所属通道 |
| `POST /ops/pay-methods` | 新增一种 |
| `PUT /ops/pay-methods/{methodCode}` | 改名、图标、排序、启停 |
| `PUT /ops/pay-methods/{methodCode}/markets` | **在哪些市场可用** |

### 通道 × 市场

| 端点 | 说明 |
|---|---|
| `PUT /ops/settle/pay-channels/{channel}/markets` | 这个通道在哪些市场可用 |

### 渠道报文（V286 已在落数据，今天没有任何地方能看）

| 端点 | 说明 |
|---|---|
| `GET /ops/channel-messages` | 按单号 / 通道 / 时间 / 结论筛 |
| `GET /ops/channel-messages/{messageNo}` | 单条详情 |

**可见范围**：只给财务与技术支持角色。**不进商家端** ——
商家看自己的报文没有用，而报文里有通道侧的商户号。

**报文已脱敏**（签名、证书序列号、Authorization 都不入库），
所以这个接口<b>不需要再脱敏一次</b>，但要在响应里说明这一点：

```jsonc
{ "payload": "...", "payloadNote": "已脱敏，不可用于重放验签；举证请到通道后台调原件" }
```

### 进件的平台侧视图

| 端点 | 说明 |
|---|---|
| `GET /ops/payment-merchants` | 全平台进件档案：卡在哪一步、退回原因、额度用量 |
| `GET /ops/payment-merchants/{merchantNo}` | 单个商家的全部通道签约 |

**今天只有商家自己看得到自己的进件** —— 运营接到「我进件卡住了」
的工单时，<b>没有任何地方可以查</b>。

### 通道凭证：**刻意不做管理界面**

| 端点 | 说明 |
|---|---|
| `GET /ops/settle/pay-channels/{channel}/credential-status` | **只读**：已配置 / 未配置 + 证书指纹后 6 位 + 到期日 |

**没有写接口。**做成可编辑的话，商户私钥会经过 HTTP、
经过应用日志、经过数据库备份。凭证放服务器文件，
运营端只回答「配没配、快到期了没有」这两个问题。

> 这与 V286 报文脱敏是同一条原则：
> <b>凭据不进任何会被复制的地方。</b>

## L3 · 七、与现有端点的差集

| 类别 | 新增 | 改造 | 不动 |
|---|---:|---:|---|
| C 端 `/mp` | 2 | 1 | 其余 |
| B 端 `/biz` | 0 | 3 | 其余 |
| 平台端 `/ops` | 13 | 0 | 其余 |
| 回调 `/callback` | 0 | 0 | 全部 |
| 内部 `/internal` | 0 | 0 | 全部 |

**新增 15 个、改造 4 个。**

> 这个数字先写成「12 新增 5 改造」，用脚本数了一遍才发现 `/ops` 是 13 不是 10。
> **这一轮里第四次把自称数字写错**（前三次在领域对象那几份）。
> 数字可以用一行命令数出来：把文档里 `` `METHOD /path` `` 形式的端点抓出来去重。
> <b>凡是能数的就不要用手数</b> —— 这条已经在领域模型那份钉进闸门了。

回调与内部接口一个都不动 —— 这一轮的改动全在「配置」与「展示」两侧，
<b>钱怎么流的那条链一个端点都不改</b>。这是它可以与 A 组（通道接入）
并行推进而不互相阻塞的原因。

### 契约先行的规矩

新端点要**先进契约文件再写实现**（`endpoints.ts` / OpenAPI），守卫会比对两边。

**资源段单复数按域，有真闸门在拦**（`api-path-naming.test.ts`，读的是三份 OpenAPI）：

| 前缀 | 约定 | 依据 |
|---|---|---|
| `/mp` | **单数** | 实况 24:1，已经落地，闸门只防回潮 |
| `/biz` | **单数** | 27:29 没有多数派，跟同族 `/mp` 走 |
| `/ops` | **复数** | 实况 7:140。<b>它不是 140 条违规，它内部是一致的</b> |

所以上面 §四 的 `/mp/pay-method`、`/mp/market` 是单数，
§六 的 `/ops/markets`、`/ops/pay-methods`、`/ops/channel-messages`、
`/ops/payment-merchants` 是复数 —— <b>这不是笔误，是两套各自一致的约定</b>。

⚠️ 破例要登记，而**仓库里有两个同名的 `known-plural-paths.txt`、判据不同，
登记一份不够** —— 这条写在闸门自己的注释里，新增端点时会撞上。

## L4 · 八、四条要先定的

1. **`GET /mp/market` 的缓存策略。**
   市场元数据几乎不变，但端上缓存过期时拿到旧的小数位会算错。
   建议：响应带版本号，端上每次启动校验；<b>版本对不上就不显示金额</b>。
2. **幂等键的有效期。**
   首次结果要存多久才能安全丢弃？建议一个完整账期 ——
   与破坏性改动的废弃期限同一个口径。
3. **报文查询的权限码。**
   建议新增 `finance:message:read`，不复用结算的读权限 ——
   报文里有通道侧商户号，可见面比结算单窄。
4. **不可用支付方式的原因要不要对商家可见。**
   C-1 里「该店铺尚未开通支付宝收款」是给**买家**看的。
   对买家说「这家店没开通」合适吗？还是说得更中性
   （「暂不支持」）—— 这是产品口径，不是技术问题。
