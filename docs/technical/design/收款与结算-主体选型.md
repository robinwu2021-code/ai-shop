# 收款与结算 · 主体选型（方便 + 税负）

> 状态：**待决策** · 2026-08-06
> 起因：核心诉求确认为 ①商家入驻方便 ②税负低。按这两条重新评估收款路径。
> **结论与 [ADR-002](./ADR/ADR-002-结算走微信支付分账.md) 现行方案不同**，若采纳需修订该 ADR。
> 政策数据来自微信支付官方文档与财政部税务总局公告，链接见文末。

## 一句话结论

**把商家做成收款主体（平台收付通 + 小微商户），不要用「平台收款再分账到个人零钱」。**

后者在这两条诉求上**都更差**：入驻并不更简单，税负明显更重，而且有一个会直接吃掉利润的技术限制。

---

## 一、四条路径对比

| | 收款主体 | 商家门槛 | 钱最终到哪 | 平台是否碰钱 |
|---|---|---|---|---|
| **A** 平台收款 + 分账到个人零钱<br>（ADR-002 现行） | 平台 | 微信授权即可 | 个人**零钱** | 是（冻结待分） |
| **B** 收付通 + **小微商户** | 商家 | 身份证 + 银行卡 + 门店照<br>**5 分钟审核** | **T+1 个人银行卡** | 否 |
| **C** 收付通 + 个人卖家 | 商家 | 经营满 6 个月且累计收入 > 20 万 | 个人账户 | 否 |
| **D** 收付通 + 个体工商户 | 商家 | 营业执照 | 对公/个人 | 否 |

C 的门槛（满 6 个月 + 20 万）冷启动阶段没人满足，直接排除。真正的选择在 **A 与 B** 之间。

---

## 二、为什么 A 在「方便」上并不占优

直觉上「不用办任何手续，微信授权就能收钱」听起来最方便。但实际对比：

| | A 分账到个人 | B 小微商户 |
|---|---|---|
| 商家要提供 | 在**平台小程序内**微信授权（拿 openid） | 身份证 + 结算银行卡 + 门店照两张 |
| 审核 | 无 | **5 分钟** |
| 钱到哪 | 微信**零钱** | **个人银行卡**（T+1 自动结算） |
| 商家取用 | 零钱提现有手续费/限额 | 已在银行卡里 |

小微商户多的那几样东西，**开个小店本来就有**（身份证、银行卡、店面）。而 A 省下的这点手续，
换来的是钱只能进零钱、每月 20 万封顶、以及下面两条硬伤。

### A 的硬伤 1：分账到个人**不支持分账回退**

官方文档明确：分账到个人（`PERSONAL_OPENID`）的资金**不支持分账回退**。

对生鲜/团购这种退款高频的业务，这是致命的：
钱一旦分到商家个人零钱，用户再退款时**平台无法通过分账回退追回**，
只能自己垫付，然后线下找商家要。跑了一个商家就是一笔坏账。

B 路径下钱在商家自己的二级商户账户里，退款直接从商家账户出，平台不垫。

### A 的硬伤 2：每月 20 万封顶

分账到个人**单月收款限额 20 万元**。一个日流水 7000 元的小店就会触顶。
触顶之后当月无法再分账给他，只能等下月——**业务做得越好越早撞墙**。

## 三、为什么 A 在「税」上明显更差

这是本次评估最关键的一点：**谁是收款主体，决定了这笔钱按什么税目征、由谁交、能不能享优惠。**

| | A 分账到个人 | B 小微商户 / D 个体户 |
|---|---|---|
| 收入性质 | 平台向自然人付款 → **劳务报酬所得** | 商家自己经营收款 → **经营所得** |
| 谁申报 | **平台是法定扣缴义务人**，必须代扣代缴 | 商家自己申报，平台无扣缴义务 |
| 增值税 | 自然人零星收入，按次起征点 | **月销售额 10 万以下免征**（季度 30 万），超过按 1% |
| 个税 | 劳务报酬预扣率 20%–40% | 经营所得五级累进，且可核定征收 |

**月销售额 10 万以下免征增值税**这条优惠（现行政策延续至 2027-12-31），
**只有经营主体享受得到**。走 A 路径的个人拿不到——这是政策设计本身的区别，不是操作技巧。

### 平台侧的责任差别

A 路径下平台向大量个人付款却不代扣个税，是**平台的法律责任**，不是商家的。
规模小的时候没人管，做起来就是追缴 + 滞纳金。这一点 ADR-002 §4 已经点到了，
但当时的结论是「先跑起来再说」——按现在确认的「少交税」诉求，这条不能再往后拖。

> ⚠️ 小微商户虽然是微信支付认可的**收款主体**，但它**没有营业执照**，
> 工商与税务上仍是自然人。它解决的是「钱怎么合规地进商家口袋」，
> **不等于自动解决了商家的税务登记问题**。
> 《电子商务法》对「零星小额」「个人销售自产农副产品」等情形有免于登记的豁免，
> 具体适用**必须由财税/法务顾问确认**——我不做这个判断。

## 三点五、资金到底走哪条路（这是本方案的核心机制）

「钱直接进商家账户」这句话容易被误读成「平台完全失去控制」。实际不是。

### 收付通模式的资金流

```
用户在平台小程序支付
        │
        ├─ 合单支付：按商家拆分，**分别直接进入各二级商户账户**
        │              （钱从不进平台账户）
        ▼
   二级商户账户（冻结态）        ← 下单时传分账标识即冻结，默认 180 天
        │
        │  平台在业务条件满足时（确认收货 / 售后期过）：
        ├──→ 调分账接口，抽取平台佣金 → 平台账户
        └──→ 解冻剩余资金 → 商家可用余额
                    │
                    ▼
            预约提现 → 商家银行卡（次日发起，当日到账）
```

### 与现行 ADR-002 方案的真正区别

两种方案的钱**都会冻结**，区别在于**冻结在谁的账户里**：

| | 现行 A（平台收款 + 分账） | 推荐 B（收付通二级商户） |
|---|---|---|
| 支付后钱在哪 | **平台商户号**（冻结待分） | **商家二级商户账户**（冻结） |
| 平台账面 | 挂着一大笔不属于自己的钱 | 干净，只有自己的佣金 |
| 商家视角 | 看不见，只能等平台分 | 「我的钱在这，还没解冻」 |
| 平台控制力 | 分账指令 | 解冻时点 + 分账指令 |
| 退款追回 | 分账给个人后**无法回退** | 从商家账户退，链路短 |

**平台的控制力没有丢**——控制点从「要不要分给你」变成「什么时候给你解冻」，
而后者对平台其实更有利：钱在商家名下，平台不承担资金保管责任，但仍能卡住放款时点。

### 为什么必须用收付通，而不是裸的小微商户直连

小微商户直连模式下是 **T+1 自动提现到个人银行卡**——没有冻结、没有账期。

这对本项目是不可接受的：生鲜到货确认、自提核销、售后申请都发生在支付之后。
钱如果 T+1 就落到商家银行卡，用户第三天申请退款时**平台拿什么退**？
只能自己垫，然后线下追——又回到 A 方案那个坑。

**收付通的冻结机制正是为这个场景设计的**（官方原话是「对二级商户进行账期管理」）。
所以选型要写清楚是「**收付通 + 小微商户作为二级商户**」，不是「小微商户直连」。

## 三点六、费率：钱在路上被扣几道

结论先给：**全链路只有一道费——支付手续费。分账、解冻、提现都不额外收费。**

### 逐环节

| 环节 | 是否收费 | 官方口径 |
|---|---|---|
| 用户支付 | **收**，按费率扣 | 标准 0.60%，优惠活动可低至 0.2%–0.6% |
| 资金进二级商户账户 | 免费 | 「订单资金**扣除微信支付手续费后**先冻结」 |
| 分账（平台抽佣） | **免费** | 「零成本，免手续费」——服务商和商户都不承担 |
| 解冻剩余资金 | 免费 | — |
| 二级商户提现到银行卡 | 未见额外收费 | 协议措辞留了口子（见下方风险） |
| 退款 | 不再另收 | 全额退款时**原手续费全额冲回**；部分退款按比例冲回 |

**退款手续费会冲回**这条对本项目很重要：生鲜退款率高，如果手续费不退，
每笔退款都要吃掉 0.6%。官方计算规则明确会冲回（1214 元订单收 7.28 元，全退则冲回 7.28 元）。

### 扣费顺序决定了佣金基数

```
订单金额 100 元
  − 支付手续费 0.6 元（0.6%）        ← 微信先扣
  = 99.4 元进入二级商户账户（冻结）
       ├─ 平台分账抽佣 X%            ← 从 99.4 算，不是从 100 算
       └─ 剩余解冻给商家
```

**平台佣金的基数是「扣完支付手续费后的余额」**，不是订单原金额。
按 100 元算佣金会导致每笔都差几分钱，累积起来对不上账——
`stl_bill.gross_minor` 存的应当是**扣费后**的可分金额，这一点要在实现时写死并加注释。

### 与 A 方案（平台收款+分账到个人）的费率差别

**没有差别**——两种方案都是 0.6% 一道费，分账都免费。

所以费率不是选型的决定因素，**决定因素仍然是税、退款可追回性、以及 20 万月限额**。
这一点值得明确，免得有人以为「钱不进平台能省手续费」——省不了。

### 两处需要向服务商确认

1. **实际费率档位**：0.6% 是泛行业标准，零售/居民生活服务可能有优惠费率活动，
   服务商可代二级商户申请。**这个差价直接进平台或商家的口袋，值得谈**。
2. **提现是否收费**：官方协议写的是「从每笔交易款中扣除……**及/或**从每笔提现款项中扣除」——
   措辞上留了对提现收费的口子。目前未见收付通二级商户提现收费的明确规定，
   但**要让服务商书面确认**，尤其是小微商户 T+1 结算到个人银行卡这一档。

## 三点七、支付宝、以及 App / H5 渠道

项目是 uni-app，本来就要出 **小程序 / H5 / App** 三端；用户又可能用支付宝。
所以「收款主体」这个选型不能只按微信小程序一个场景定。

### 支付宝有对等产品

| | 微信 | 支付宝 |
|---|---|---|
| 平台电商方案 | **收付通** | **直付通** |
| 二级商户主体 | 小微 / 个体户 / 企业 | 小微（无照个人）/ 个体户 / 企业 |
| 资金流向 | 直接进二级商户账户 | **同样直接进二级商户账户**，不经服务商 |
| 账期控制 | 冻结 + 平台解冻 | 平台发起「确认结算」后才结算给商户 |
| 合单支付 | 支持 1–50 个二级商户 | 支持多商户合并支付 |
| 标准费率 | 0.60% | 约 0.55%–0.60% |

**结构上是对等的**——两家都提供「平台代进件 + 钱直接进商家 + 平台控制放款时点 + 分账抽佣」。
所以选型逻辑不用为支付宝另起一套：同一套二级商户模型，两个通道各进一次件。

> ⚠️ 支付宝这一列的细节来自二手资料（官方文档站是 JS 渲染，抓不到正文）。
> **接入前必须以支付宝官方文档与服务商书面口径为准**，本表只用于判断「方向是否可行」。

### ⚠️ 卡住三端的一条硬约束：小微主体只能走 JSAPI

微信官方明确各主体被授权的支付方式：

| 主体类型 | 授权的支付方式 |
|---|---|
| **小微** | 付款码、**JSAPI**、Native —— **无 APP 支付、无 H5 支付** |
| 个体工商户 | 按经营场景授权：小程序→JSAPI、**App→APP 支付**、网站→JSAPI/Native |
| 企业 | 同个体户 |

**后果很直接**：

| 渠道 | 商家是小微 | 商家是个体户/企业 |
|---|---|---|
| 微信小程序（JSAPI） | ✅ | ✅ |
| **H5**（海外/浏览器） | ❌ | ✅ |
| **App** | ❌ | ✅ |

也就是说：**只要商家还是小微主体，这个平台就只能有小程序一个收款渠道。**
H5 和 App 打包出来能用，但**收不了钱**。

### 这条约束改变了「一键代办个体户」的定位

ADR-002 §4 把代办个体户当作**税务与限额**的解法（成长期再做）。
加上这条约束之后，它同时是**渠道解锁**的前置条件：

> 商家不升个体户 → 平台永远只有小程序一个收款入口。

如果 App 是既定路线（项目已按 uni-app + Capacitor 规划），那代办个体户就不是「成长期再说」，
而是**产品成立的必要条件**，优先级要提前。

### 三条可选的组合路线

| | 组合 | 适合 | 代价 |
|---|---|---|---|
| **R1** 小程序单渠道起步 | 收付通 + 小微 | 冷启动最快，商家零门槛 | App/H5 收不了钱，出海路线卡住 |
| **R2** 双通道小程序 | 微信收付通 + 支付宝直付通，均小微 | 覆盖两家用户 | 两套进件、两套对账，仍无 App/H5 |
| **R3** 个体户为主 + 小微兜底 | 能办照的走个体户（全渠道），办不了的走小微（仅小程序） | 渠道完整 | 商家分两档，前端要按主体裁剪支付方式 |

**R3 是唯一能同时满足「三端」与「零门槛入驻」的**，代价是系统里要承认
「商家的可用支付渠道取决于其主体类型」这件事——
`usr_merchant` 上要落 `subject_type` 与**已授权支付方式**，下单时按它决定能不能拉起支付。

这不是可以事后补的字段：**它决定了某个商家的商品在 App 端能不能下单**，
属于可见性/可售性的一部分，要和 `service_scope` 一样早点定。

## 三点八、小微 / 个体户 / 企业 到底差在哪

先破一个常见误解：**这三者不是同一维度上的三个档位。**

- **个体工商户 / 企业** 是**工商登记主体**——有营业执照、有统一社会信用代码、能开票、能签合同、独立承担责任。
- **小微商户** 不是工商概念，是**微信支付/支付宝在支付层面给自然人开的一个特例**：
  没有营业执照，工商上仍是个人，只是被允许作为收款方进件。

所以准确的说法是：小微是「**没有主体资格的人也能收钱**」，个体户是「**真的成为了一个经营主体**」。

### 逐项对比

| 维度 | 小微 | 个体工商户 | 企业 |
|---|---|---|---|
| **营业执照** | 不需要 | 需要 | 需要 |
| **进件材料** | 身份证 + 结算银行卡 + 门店照（门口/店内各一张） | 执照 + 法人身份证 + 结算账户 | 执照 + 法人身份证 + 对公账户 |
| **审核时长** | **5 分钟** | 约 1–2 个工作日 | 约 1–2 个工作日 |
| **谁能申请** | **只能服务商代申请**，商户自己申请不了 | 自行或服务商代进件 | 自行或服务商代进件 |
| **支付方式授权** | 付款码、**JSAPI**、Native<br>**无 APP、无 H5** | 按经营场景：小程序→JSAPI、**App→APP 支付**、网站→JSAPI/Native | 同个体户 |
| **行业限制** | **仅线下行业**（餐饮、线下零售、居民生活服务、休闲娱乐、交通出行等），排除线上 | 无此限制 | 无此限制 |
| **结算账户** | **经营者个人银行卡** | 对公 or 经营者个人卡 | **必须对公账户** |
| **管理工具** | 商家助手小程序（无商户平台） | 小程序 + **商户平台** | 小程序 + 商户平台 |
| **费率** | 固定档位枚举 | 标准费率，可申请优惠费率 | 同个体户 |
| **税务身份** | 自然人（**无税务登记**） | 经营所得，小规模纳税人可享**月 10 万免增值税**，可核定征收 | 企业所得税 + 增值税 |
| **能否开票** | 否 | 可（税务代开或自开） | 可自开 |

### 对本项目而言，真正卡人的是这三条

**① 支付渠道**（见 §三点七）
小微只有 JSAPI —— 商家是小微，他的商品在 App 和 H5 上**收不了钱**。
这是唯一一条「无论怎么谈都绕不过去」的技术限制。

**② 开票能力**
小微开不了票。B 端商家一旦有企业客户（比如公司订水果做福利），
**对方要发票而商家开不出来，这单就做不成**。个体户可以税务代开。

**③ 结算账户与规模**
小微结算到个人卡，额度天花板会先于业务触顶（各方口径不一，**需服务商确认**）。
企业必须对公，反而是最重的一档——对小店没有意义。

### 所以三段式路径的真实理由

ADR-002 §4 那条「个人 → 个体户 → 企业」的路径是对的，但**理由要更新**：

| 阶段 | 原理由 | 加上本次调研后的真实理由 |
|---|---|---|
| 小微 | 入驻零门槛 | 零门槛**但只能小程序、不能开票** —— 是「先做起来」的临时态 |
| 个体户 | 解决限额与税务 | **同时解锁 App/H5 渠道 + 开票能力** —— 从「优化项」变成「必需项」 |
| 企业 | 规模化 | 不变；对邻里小店基本用不上 |

**中间那一步的价值被低估了。** 它不只是"额度更高、税更省"，
而是**商家能不能在 App 上卖货、能不能开票**的分水岭。

「平台内一键代办个体户」因此不是锦上添花，是**把大部分商家从残疾状态救出来的动作**。

---

## 四、推荐方案：B 起步，D 兜住上限

沿用 ADR-002 §4 的三段式思路，但**把起点从「分账到个人零钱」换成「小微商户」**：

| 阶段 | 商家形态 | 收款 | 平台侧动作 |
|---|---|---|---|
| 冷启动 | 无照小店 | **小微商户**（收付通二级商户） | 服务商代进件，5 分钟出结果 |
| 成长期 | 个体工商户 | 二级商户（个体户类型） | 平台内「一键代办个体户」，**代办费平台补贴** |
| 成熟期 | 企业 | 二级商户（企业类型） | 常规进件 |

平台佣金走**服务商分账**：从二级商户的资金里按费率抽，不是平台先收后返。

### 一个额外的契合点

平台收付通支持**合单支付**：1–50 个二级商户的商品一次支付，
资金**分别进入各二级商户账户**。

这和项目现有的「购物车跨商家拆成子订单、共享 `payGroupNo` 一次支付」**结构完全一致**——
`ord_order`（主订单/支付组）对应合单，`ord_sub_order`（子订单）对应各二级商户。
不需要为此改数据模型。

## 五、待确认（不要按经验值写代码）

1. **小微商户的行业限制**：官方限「餐饮、线下零售、居民生活服务、休闲娱乐、交通出行及其他线下行业」，
   明确排除线上行业。邻里小店属线下零售/居民生活服务，但交易发生在小程序——
   **这算线下还是线上，必须让服务商给书面口径**。这条不通，整个 B 方案要重来。
2. 小微商户的**收款额度**与升级路径（各方口径不一，以服务商确认为准）。
3. 二级商户资金**默认冻结 180 天**的解冻条件与操作时点。
4. 平台佣金的服务商分账**比例上限**（单笔订单分账总额受商户平台「订单分账最大比例」限制）。
5. **支付宝直付通**的主体类型、费率、结算与分账细节——本文该列为二手资料，需官方确认。
6. 若走 App 渠道：微信开放平台**移动应用**注册与审核所需材料（软著/应用信息），以及
   支付宝 App 支付的签约要求。
7. 商家的**税务登记**是否必需，以及《电子商务法》豁免的适用性——**找财税顾问，不要自行判断**。

## 六、若采纳，对现有代码的影响

| 项 | 现状 | 需要变成 |
|---|---|---|
| 收款 | 平台 mchid 收款 | 下单传 `sub_mchid`（商家二级商户号） |
| `usr_merchant` | **无任何分账/收款列** | 补 `sub_mchid` / 进件状态 / 结算账户类型 |
| `SplitGateway` | 分账给接收方 | 改为服务商分账（平台作为接收方抽佣） |
| `stl_bill` | 按子单记应分金额 | 语义不变，但「分给商家」变成「从商家抽佣」 |
| 退款 | 需先回退分账 | 从二级商户账户退，链路更短 |
| `usr_merchant` 主体 | 无 `subject_type` 落库 | 补主体类型 + **已授权支付方式**——决定该商家在哪些端可售 |
| 下单 | 不区分渠道 | 按商家主体裁剪可用支付方式（小微仅 JSAPI） |
| ADR-002 | 决策为「平台收款 + 分账」 | **需修订** |

`SplitGateway` 当初抽成接口就是为了「接真通道时只换这一个实现」——
这个抽象在方案改变后依然成立，改的是实现不是调用方。
