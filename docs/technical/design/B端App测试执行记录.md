## 缺陷

### F1（M1.5）· 验证码错误提示是 `Invalid request`

**现象**：输错验证码，用户看到英文的 "Invalid request"。

**两个问题叠在一起**：

1. **语义**：验证码不对走的是 `ErrorCode.BAD_REQUEST`（10400「请求参数有误」）。
   而 `ErrorCode` 自己的注释里写着「员工管理的三条闸分成三个码而不是共用 10400」，
   理由是「10400 让人去检查自己传了什么」—— 这里正好违反了自己定的规矩。
   用户看到「请求无效」不知道下一步该干什么；应当是「验证码不对或已过期，重新获取」。
2. **语言**：页面其余文案是端上 i18n 的中文，这句来自后端、按系统语言回了英文。
   **同一屏两种语言**。

**影响**：登录是所有人的第一步，而输错验证码是最常见的一次失败。

**修法**：新增 `err.otp_invalid`（含中/英/阿三份），`verifyOtp` 改抛它。

### F2（M5.3 引出）· 快递单没有收货地址也能下单

**现象**：`POST /mp/order` 传 `fulfillment=EXPRESS` 而**不传 `addressId`**，下单成功
（实测建出 `SO202608151013280003710`）。商家侧订单详情的 `receiver` 是 null ——
**货发不出去，而系统全程没有任何异常**。

**库里的佐证**：55 张 EXPRESS 子单，**有收货人的 0 张**（`usr_address` 一行都没有）。

**不是端上的问题**：C 端 `order-confirm` 页第 206 行有
`(!needAddress || !!address)`，页面是拦着的。**缺的是后端那道校验** ——
于是任何绕过页面的调用（旧版 App、脚本、将来的其它端）都能造出发不出去的订单，
库里那 55 张正是这么来的。

**代码里那句注释不能替它挡**：`OrderServiceImpl` 写着「取不到不让下单失败……
宁可让商家看到「地址：—」去问一句」——那句话说的是**下单时地址查询失败**，
不是**从头就没给过地址**。前者是容错，后者是漏校验。

**修法**：`createOrder` 里对 EXPRESS / MERCHANT_DELIVERY 校验收货地址可解析，
不可解析就拒绝**创建**（不是支付后再拦 —— 那时钱已经付了）。

### F3（M6.2b）· 核销漏传验证码 → 500

**现象**：`POST /biz/pickup/verify` 请求体是 `{}`（漏传 `verifyCode`）→
`10500 系统开小差了，请稍后再试`。

**根因**（后端日志里的栈）：`VerifyReq.verifyCode` 没有 `@NotBlank`，null 一路走到
`PickupServiceImpl.log()` 的插入，而 `ful_verify_log.verify_code` 是 `NOT NULL`
且无默认值 → `SQLException: Field 'verify_code' doesn't have a default value` → 500。

**为什么值得修**：一个本该 400 的输入变成了 500，而「系统开小差了」这句话
会把排查引向服务端故障 —— 真正的原因是请求里少了一个字段。

**修法**：`VerifyReq.verifyCode` 加 `@NotBlank`（与 `record ApplyAfterSaleReq` 同一手法）。

### F4（M11.6）· 员工授权日志的「谁干的」**从上线起一条都没记下来**

**现象**：17 条授权变更记录，`actor` 非空 **0 条**。而库里 `actor_account_no`
**17 条全有值**（`U202608121818140000713` = 老板）。

**两层原因叠在一起**：

1. **两个键混用**。写的时候存 `userNo`（`StaffAuditLogger` 里的 `LoginUser::userNo`），
   读的时候拿它去查一张以 `mchAccountNo` 为键的表 —— 永远对不上。
   `targetAccountNo` 存的是 account no，所以 `targetName` 有值，正好把这个错衬出来。
2. **老板没有任何可显示的名字**。他的 `mch_account` 行 `display_name` 与
   `login_phone` **两列都是 NULL**（他走消费者账号登录），而**绝大多数授权操作
   都是他做的**。同一个原因让员工列表第一行的名字也是空的。

**最阴的地方**：VO 上写着「取不到当前身份时为空 —— 空就是空，不写『系统』」。
于是这个 null 被读成「当时没取到身份」，**一条设计良好的注释把 bug 解释成了预期行为**。
B-11.10.3 要的四件事（谁、何时、把谁、改成什么）少了第一件，而追责恰恰只看第一件。

**修法**：读侧两种键都认（`mchAccountNo` 与 `userNo` 都放进映射）；
标签加第三层回落 —— 老板显示「店主」而不是 `SF2026…`（后者谁也认不出）。
写侧不动，但补注释说明「这里存的是 userNo」，免得下一个人只改一处。

## 记录方法上的两条教训

1. **截图不能当判据**。toast 1.5 秒就消失，`adb exec-out screencap` 本身有约 1 秒延迟 ——
   十有八九抓不到。用 `uiautomator dump` 取页面文本，判据才能被 grep。
2. **口径要从代码里读，不能猜**。本轮两次误判都出在这上面：
   「待分拣」我按门店算（实际是**按自提点、不限商家** —— 一个点承接多家的货），
   改库存的请求体我猜成 `items[]`（实际是 `{skuNo, stock}`）。
   两次都先看起来像缺陷。**猜出来的判据会制造假缺陷，而假缺陷比漏测更贵**。

## 对照测试（B 端跑完之后做）

同一批数据要在三端各看一遍 —— **同一件事在三端的表述必须一致**，
而不一致恰恰不会报错。计划：

| 对照点 | B 端看到 | C 端应看到 | 运营端应看到 |
| --- | --- | --- | --- |
| 新建商品 | 待审核 + 下架 | **搜不到、店铺页看不到** | 审核队列里有它 |
| 改价 | 回到待审核 | 旧价还是新价？**下单价必须与页面一致** | 审核记录里有价格变更 |
| 库存改 0 | 商品仍在列表 | **不可购买**（不是不可见） | 缺货统计里有它 |
| 订单发货 | 转已发货 | 「已发货」+ 物流号 | 订单列表状态同步 |
| 售后同意/驳回 | 卡片文案变 | 用户侧看到同一句话 | 仲裁台可见 |
| 评分变化 | 商品页评分 | 店铺页评分**同一个数** | 商家评分统计一致 |

具体用例与数据在 B 端跑完后补，届时**复用同一批订单号与商品号**，
不新造数据 —— 用不同的数据对照，对不上的时候分不清是缺陷还是数据不同。
