## L1 · 这份对齐怎么做的

需求层 29 个对象，逐条去代码里找对应物。**两个方向都要有结论**：

| 方向 | 处置原则 |
|---|---|
| 需求有 · 代码没有 | 欠账，进待办 |
| 代码有 · 需求没有 | **不能默认「代码是对的」** —— 逐个判定是需求漏写，还是实现多余 |
| 两边都有但语义不同 | 最危险的一类，当场定口径 |

**对齐当场推翻了需求层的一条断言**（退款，见 §三·2）——
这正是双向对齐要做的事：需求层不看代码是对的，
但它下的每一条「今天没有」都必须回来验一遍。

## L2 · 二、代码有 · 需求没有（反方向）

这个方向更容易被跳过，而它恰恰能暴露需求写漏了什么。

| 代码里的东西 | 需求层为什么没写 | 判定 |
|---|---|---|
| **风控判定** `pay_risk_shadow_log` | **需求漏写。**§四·流程 4 提到「风控判定」这个动作，却没有给它一个对象 —— 而判定结果要留底（影子期靠它复盘、正式期靠它解释为什么挂起某一批） | **补进需求层** |
| **增值包订阅** `mch_entity_plan` + 档位定义 | 它是「档位与配额」，今天**不涉及真实付费**：支付域里零处引用，也没有任何流水与它关联 | **不是资金对象**（将来收费时再进） |
| **支付域设置** `pay_setting` | 配置不是领域对象 | 不进 |
| 商家域另外 14 张表（员工、角色、会话、履约、服务范围……） | 与「钱怎么流」无关 | 不进 |

> ⚠️ 顺带一个观察：`mch_entity_plan` 给 FREE 档位也标 `BY_SELF_PAID`（自付）。
> 免费档不是「自己付的」—— 这是个语义错用。今天无害（没人读它做资金判断），
> 但将来真开始收费时，<b>「谁付过钱」这个问题会拿到一个错误答案</b>。

## L2 · 三、七处差异，逐条定口径

### 1. 收款单与支付流水合一 🟡

**需求层**：收款单是「意图」（一笔订单要收多少），流水是「实际的资金变动」。
一笔订单可以有多次收款尝试，意图只有一个。

**代码**：合一在 `stl_payment`。每次尝试落一行，靠商户单号
（`订单号[-尝试序号]`）区分。

**口径**：**保持合一，不拆。**
「意图」今天没有独立属性 —— 它需要的一切（订单号、金额、通道）
在每一行流水上都有。拆出来会多一张表、多一次 join，
而换来的只是概念上的整齐。

<b>但要补一条约束</b>：同一订单的未终态收款**最多一行**。
今天靠代码里的「复用未终态收款」保证，应当有巡检兜底。

### 2. 退款单在订单域，缺支付域那一半 🟡

**这条推翻了需求层的断言。**需求层写「今天没有退款对象」，实际上有 ——
售后单兼任退款单，且相当完整：

| 需求层要的 | 售后单上的 |
|---|---|
| 退多少 | `refund_minor` |
| 退到哪一步 | `APPLIED → REFUNDING → REFUNDED / REJECTED / ARBITRATING / CLOSED` |
| 分账回退了没有 | `split_reversed` |
| 积分冲抵 | `points_offset_minor` |
| 失败能重试 | 停在 `REFUNDING`，有续跑任务 |
| 有巡检 | I4（已退款而分账未回退）· I5（卡住的退款单） |
| 顺序约束 | 「回退分账永远在退款之前，失败绝不往下走」—— 已写死 |

**真正缺的是支付域那一半**：
- `stl_payment` 的 `REFUND` 方向**从没被写过**
- 售后单上的 `refund_payment_no` 字段**只声明、没有任何地方赋值**
  （因为支付域的退款方法只打了一行日志、返回一个被丢弃的假单号）

**口径**：**退款单留在订单域**，不搬。
理由：退款的触发、审批、状态机、与库存/评分的联动都在那边，
搬过来等于把售后流程劈成两半。

**支付域要补的是**：一行 `REFUND` 方向的流水，
并把它的号回填到 `refund_payment_no`。
<b>那一行是「这笔退款在资金上真的发生过」的唯一证据</b>，
也是让退款进入对账范围的前提。

### 3. 支付流水五个方向只写了一个 🟡

**需求层**：五种方向同一个对象，理由是「通道回执结构一样、
幂等要求一样、**对账要一起做**」。

**代码**：只有 `PAY` 在写。`REFUND` / `SUBSIDY` / `SUBSIDY_REVERSE` / `PAYOUT`
四个常量定义了、注释写了，一行都没落过。

**后果**：退款、补差、打款**不在对账范围内**（对账扫 `direction = PAY`）。
运营看到的「对账覆盖范围」说的是「渠道账单未接入」，
它没说的是<b>另外四个方向根本没有账可对</b>。

**口径**：**按方向逐个补，从 `REFUND` 开始**（它有真实业务在跑）。
`SUBSIDY` / `SUBSIDY_REVERSE` 跟着补差链路走，`PAYOUT` 等出款真正接通。
每补一个方向，**对账的覆盖范围声明要跟着改** ——
覆盖范围说的话必须是真的，否则「零差异」是句假话。

### 4. 对账轮次只有通用任务记录 🟡

**需求层**：轮次要能说出「什么时候跑的、覆盖哪个范围、扫了多少」。
因为「今天没差异」与「今天没跑」在结果上都是零条差异，含义却相反。

**代码**：有通用的任务运行记录（跑没跑、跑多久、结果摘要），
差异表上只有账期日期，没有轮次号。

**口径**：**不新建轮次表**，扩展现有的任务运行记录。
理由：「跑没跑过」通用记录已经答得了；缺的是对账特有的
「这一轮覆盖了什么」，而那是一段结构化摘要，
挂在任务运行记录的详情上即可 —— 为它单开一张表，
换来的是又一处要维护的双写。

<b>但覆盖范围必须结构化</b>，不能是一句人写的话：
它要能回答「这一轮扫了哪些方向、哪些渠道、渠道账单接没接」。

### 5. 市场：只有一个字符串列 ❌

**代码**：通道表上有一个市场列表字段，此外没有任何东西。
两处取可用通道的地方都传的是「不限市场」——
<b>台湾商家与大陆商家今天看到同一份通道列表</b>。

**口径**：**建市场表**。
「一个市场一种记账币种」这条规则需要有地方存；
散在各表的市场码字符串上，它无法被约束，只能靠每个调用点自觉。

### 6. 币种：有列，从没被显式写过 ❌

**代码**：支付流水上有币种列（默认人民币），
而生产代码里**没有任何一处给它赋值**。结算侧三张表根本没有这一列。

**口径**：**先补结算侧的列并回填**，再让下单链路显式写入。
这一条<b>与多区域无关，今天就该补</b> ——
单币种下它也是对的，只是没有第二个币种时看不出错。
而越晚补，回填的行数越多。

### 7. 支付方式不存在 ❌

**代码**：C 端只有一个写死的桩通道。

**口径**：**建支付方式表，挂在通道下**。
不做的话，接聚合网关那天 C 端按钮要跟着改，而那本该是后台配置。

## L3 · 四、十条跨对象规则的巡检覆盖

| # | 规则 | 有巡检？ | 备注 |
|---|---|:---:|---|
| R1 | 收款成功的订单必须已支付 | ✅ | I8，每小时 |
| R2 | 已支付子单必须有结算单 | ✅ | I1 |
| R3 | 结算单的子单必须真的付过 | ✅ | I2 |
| R4 | 标记已发积分必须有发分流水 | ✅ | I3 |
| R5 | 流通积分 ≡ 池子里的钱 | ✅ | 恒等式 2 |
| R6 | 批次合计 ≡ 其下结算单之和 | 🟡 | 有字段有测试，**没有独立巡检** |
| R7 | 批次只能相加同币种 | ❌ | 币种列都没有 |
| R8 | 退款完成 ⟺ 五件事各有结论 | 🟡 | I4/I5 覆盖了分账与卡单，**没覆盖发票红冲与佣金冲减** |
| R9 | 额度已用量 ≡ 成功收款之和 | 🟡 | 有累加有测试，**没有对账式核验** |
| R10 | 账户余额 ≡ 流水之和 | 🟡 | 同 R9 |

**五条 🟡 的共同形状**：<b>写入路径有、核验路径没有。</b>
写对了当然一致，写错了没有任何东西会发现 ——
而这类账目错误的特点是**不报错、只是数字不对**。

产出目标 schema，然后与现有库做第二次对齐（表级 + 字段级）。
