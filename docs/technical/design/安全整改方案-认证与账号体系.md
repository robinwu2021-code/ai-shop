# 安全整改方案 · 认证与账号体系

> 2026-08-09 · 对应[后端模块规划](../archive/后端模块规划-理想方案.md) §八 与落地顺序 **序 0**。
> 三项均为**已存在的缺陷**（逐条核对过代码），与架构重构无关，可独立发布。
> 排在所有重构之前的理由：重构会搬动这些代码，先修完再搬，不用改两次。

## 零、三项一览

| # | 缺陷 | 位置 | 危害 | 改动量 | 存量影响 |
|---|---|---|---|---|---|
| **A** | 运营密码用 `String.hashCode()` 派生 | `OpsServiceImpl:372` | **可爆破 → 改费率/批提现/封商家** | 小（3 处调用点） | 需重置密码 |
| **B** | OTP 零限流 | `OtpStore` | 短信轰炸 · 验证码可枚举 | 中（新增组件） | 无 |
| **C** | C/B 端共用一个令牌 Realm | `Realm.java` | 令牌类型层面不可区分 | 中（改枚举 + 拆链） | 存量会话失效 |

三项**互不依赖**，可并行也可分批发。建议顺序 **A → B → C**：A 危害最大且最快，
C 会让存量会话失效、最好挑低峰。

## 一、缺陷 A：运营密码哈希

### 1.1 现状

```java
// OpsServiceImpl:372
public static String hash(String raw) {
    return Integer.toHexString(("shop$" + raw).hashCode());
}
// OpsServiceImpl:76
if (staff == null || !hash(password).equals(staff.getPassword())) { ... }
```

四个问题叠在一起：

1. `String.hashCode()` 是 **32 位**且设计目标是散列均匀，不是抗碰撞——
   彩虹表可秒查，碰撞可构造
2. **无盐**：两个运营用同一个密码，库里两行完全相同
3. **不可调工作因子**：BCrypt 可以随硬件变快而调 cost，这个不能
4. `.equals` 比较**非恒定时间**，理论上可计时侧信道

而这是权限最高的那套账号：能改费率、批提现、封商家、改类目授权。

### 1.2 目标

| | 现状 | 目标 |
|---|---|---|
| 算法 | `hashCode()` | **BCrypt，cost=10**（Spring Security 自带，无新依赖） |
| 盐 | 无 | 每条独立随机盐（BCrypt 内建，存在同一字符串里） |
| 比较 | `String.equals` | `PasswordEncoder.matches()`（恒定时间） |
| 列宽 | `VARCHAR(128)` | **不用改**——BCrypt 输出 60 字符 |

### 1.3 改动清单（3 处调用点）

| 文件 | 改法 |
|---|---|
| `shop-base` 新增 `PasswordEncoder` Bean | `new BCryptPasswordEncoder(10)`；放 base 是因为三套账号池将来都可能用 |
| `OpsServiceImpl:76` 校验 | `encoder.matches(raw, staff.getPassword())` |
| `OpsServiceImpl:372` `hash()` | **删除**（public static 被 DevSeeder 依赖，见下） |
| `DevSeeder:122` | 改调 `encoder.encode(rawPassword)` |

### 1.4 存量数据迁移

现状运营账号只由 `DevSeeder` 造（未发现其他写入方），所以**生产大概率还没有真实账号**。
分两种情况：

**情况 1：生产无存量账号（预期）**
直接替换算法，重跑种子即可。**推荐**——最干净。

**情况 2：已有存量账号**
旧哈希不可逆推，无法平滑迁移。两条路：

- **强制重置**（推荐）：加一列 `password_reset_required BOOLEAN`，
  迁移时全置 `true`，下次登录强制改密。运营账号数量少（个位数到几十），可行
- **双读兼容**（不推荐）：`matches()` 失败时回退旧 `hash()` 比对，成功后
  透明升级为 BCrypt。代码里留一条旧算法路径，容易忘记删——
  **弱算法的兼容期就是弱算法的有效期**

### 1.5 顺带补齐（同一批做，成本几乎为零）

- **登录失败锁定**：同账号连续 5 次失败锁 15 分钟，须管理员解锁。
  没有这条，BCrypt 只是把爆破从"秒"变成"天"，不是"不可能"
- **密码强度**：≥10 位，含大小写与数字；创建与改密时校验
- **不回显账号是否存在**：账号不存在与密码错误返回同一个错误，
  否则接口变成账号枚举器

## 二、缺陷 B：OTP 限流

### 2.1 现状

`OtpStore` 只有三个方法：`save` / `verifyAndConsume` / `peek`。
没有任何频率或次数约束，于是：

| 攻击 | 现状可行性 |
|---|---|
| 短信轰炸（骚扰他人 + 烧平台短信费） | 循环调 `/mp/user/otp/send` 即可 |
| **验证码枚举** | 6 位数字 = 100 万组合，无失败次数限制 → **必中** |
| 撞库预备（枚举哪些手机号已注册） | 若发码接口对未注册号返回不同结果 |

第二条是真正致命的：验证码的安全性**完全**依赖"猜的次数有限"，
没有失败计数就等于没有验证码。

### 2.2 目标：四道闸，缺一不可

| 闸 | 限什么 | 建议阈值 | 存哪 | 超限后 |
|---|---|---|---|---|
| ① 发码间隔 | 同手机号 | **60 秒**一次 | Redis | 提示"请稍后" |
| ② 发码总量 | 同手机号 / 天 | **10 次** | Redis | 当日拒发 |
| ③ 发码来源 | 同 IP / 小时 | **20 次** | Redis | 拒绝 + 告警 |
| ④ **验码失败** | **同手机号连续失败** | **5 次 → 锁 15 分钟** | Redis | 锁定期直接拒绝，且**作废当前码** |

> ④ 是四条里最重要的。①②③ 防的是骚扰与费用，**④ 防的是账号被攻破**。

### 2.3 结构

限流是基础设施不是业务，落 `shop-base`，三套账号池共用：

```
shop-base/common/ratelimit/
 ├─ RateLimiter          接口：tryAcquire(key, rule) → 允许 / 拒绝(剩余等待)
 ├─ RedisRateLimiter     生产实现（滑动窗口或令牌桶）
 ├─ InMemoryRateLimiter  单机/测试实现
 └─ RateRule             record(窗口, 次数)
```

`OtpStore` 增加 `recordFailure(phone)` / `isLocked(phone)`；
`AuthService` 在发码与验码两处各调一次闸。

### 2.4 顺带修的两处

| 问题 | 现状 | 改法 |
|---|---|---|
| **OTP 明文入日志** | `log.info("[DEV-ONLY] otp for {} = {}", …)` | 改 `log.debug` + 仅 `dev` profile；生产日志级别不可能打出 |
| **OTP 明文存储** | `Entry(String code, …)` 明文 | 存 `hash(code+phone)`，验时比哈希。内存 dump / Redis 快照泄露时不直接暴露 |

> `peek()` 保留——它只在测试用，且注释写清了"生产没有任何调用方"。
> 这比给生产代码开"万能验证码"后门正确得多，不要改。

## 三、缺陷 C：令牌 Realm 拆三值

### 3.1 现状

```java
// Realm.java
CONSUMER,   // C 端与 B 端共用（token 前缀 ctk_）
OPERATOR    // ops-web（otk_）
```

三个账号池、两个 Realm。后果：**C 端令牌与 B 端令牌在类型层面无法区分**，
`/mp/**` 与 `/biz/**` 又同在一条 `SecurityFilterChain`，
隔离完全依赖业务层的 `BizContext` 判断。

这不是"现在有漏洞"，而是**防线只有一道**：任何一个 `/biz/**` 接口忘了取
`BizContext`，C 端令牌就能直接访问商家接口，而过滤器层不会拦。

### 3.2 目标

```java
CONSUMER,   // ctk_  → /mp/**
MERCHANT,   // mtk_  → /biz/**     ← 新增
OPERATOR    // otk_  → /ops/**
```

配套把 `SecurityConfig` 现在合并的那条链拆开：

| 链 | 匹配 | 接受的 Realm |
|---|---|---|
| consumerChain | `/mp/**` | 仅 `CONSUMER` |
| merchantChain | `/biz/**` | 仅 `MERCHANT` |
| operatorChain | `/ops/**` | 仅 `OPERATOR` |

**收益**：拿错域的令牌在**进业务代码之前**就 401，与现状 `/ops/**` 的隔离等价。
防线从一道（业务层）变成两道（过滤器 + 业务层）。

### 3.3 改动清单

| 文件 | 改法 |
|---|---|
| `Realm.java` | 加 `MERCHANT` 及前缀 `mtk_` |
| `SecurityConfig` | 拆出 `merchantChain`；`consumerChain` 的 matcher 收窄为 `/mp/**` |
| `ConsumerTokenAuthFilter` | 改为按链注入期望 Realm，校验令牌前缀与之匹配 |
| B 端签发处（`BizAuthController` → `AuthService`） | 签发时用 `Realm.MERCHANT` |

### 3.4 存量影响：会话失效

现有 B 端令牌是 `ctk_` 前缀，改造后打 `/biz/**` 会被拒。
**所有 B 端用户需要重新登录一次。**

三种处理，按发布窗口选：

| 方案 | 做法 | 适用 |
|---|---|---|
| **直接切**（推荐） | 挑低峰发布，B 端用户重登一次 | 商家数量少、有发布窗口 |
| 兼容期 | `merchantChain` 临时同时接受 `ctk_` 与 `mtk_`，两周后移除 | 商家多、不想打扰 |
| 预热 | 发版前一天推送"将需重新登录" | 与上面任一组合 |

> 若选"兼容期"，**必须同时建一个到期删除的提醒**（日历 / issue）。
> 兼容代码没有到期日就会变成永久代码，而它正是这次要消灭的那个问题。

## 四、验收

每项都要有**能失败**的测试，而不是只跑通正常路径：

| 缺陷 | 测试 |
|---|---|
| A | ① 同一密码两次 encode 结果不同（有盐）② 旧 `hash()` 已从代码中消失 ③ 连续 5 次错密码后第 6 次被锁 ④ 账号不存在与密码错误返回同一响应 |
| B | ① 60s 内第二次发码被拒 ② 连续 5 次错码后第 6 次即使**码正确**也被拒 ③ 锁定期结束后可正常登录 ④ 日志中不出现验证码明文 |
| C | ① `ctk_` 打 `/biz/**` → 401（且**未进入业务代码**，用 mock 验证 Service 零调用）② `mtk_` 打 `/mp/**` → 401 ③ 三条链各自的正常路径通过 |

B② 与 C① 是两条最容易写成"假通过"的：
B② 必须用**正确的码**验证锁定生效，否则测的是"码错了"而不是"被锁了"；
C① 必须断言业务层未被调用，否则测的是业务层拦截，而不是过滤器拦截。

# 第二部分 · 多端认证与身份统一

> 承接[模块规划](../archive/后端模块规划-理想方案.md) §四（渠道层）与 §八（用户体系）。
> 这一部分回答两件事：**不同来源用不同的认证方式**、**并且能认出是同一个人**。

## 六、缺陷 D：一个人会变成多个账号（结构性）

### 6.1 现状

`usr_account` 把三种凭证**平铺成三个列**，各带一个单列唯一键：

```sql
phone VARCHAR(32),      UNIQUE KEY uk_phone
openid VARCHAR(64),     UNIQUE KEY uk_openid
apple_sub VARCHAR(128), UNIQUE KEY uk_apple_sub
unionid VARCHAR(64)     -- 有列，无索引，且代码里从未读写
```

登录时 `findOrCreate` **只按本次用的那一列查**，查不到就建新账号：

```java
// AuthServiceImpl:113
UsrAccount existing = userMapper.selectOne(
    Wrappers.<UsrAccount>lambdaQuery().eq(true, identity.column(), identity.value()));
if (existing != null) return existing;
// ↓ 否则新建，且只写入本次这一个凭证列
```

于是：

| 场景 | 结果 |
|---|---|
| 张三小程序登录（openid=X）→ 建账号 ① | ① 只有 openid |
| 同一个张三在 App 用手机号登录 | 按 phone 查 → 无 → **建账号 ②** |
| 张三的订单、积分、卡包、优惠券 | **分裂在两个账号上，且没有任何报错** |

`unionid` 的实体注释写着*"小程序与 App 是同一个人的唯一依据"*——
**但这条依据从未被使用**。

### 6.2 还有一个更硬的限制

单表单列唯一键意味着**一个账号只能有一个 openid**。而微信的 openid 是
**按应用隔离**的：同一个人在小程序、公众号、App 里是三个不同的 openid。

也就是说：**现在的表结构根本存不下"同一个人从小程序和 App 都登录过"这个事实**，
这是 App 方案落地前必须先解决的结构问题，不是优化项。

### 6.3 目标：账号与凭证分离

```
usr_account（人）                    usr_identity（凭证，一对多）
  user_no          ◄──────────────    user_no
  nickname/avatar                     identity_type
  status                              identity_value
  community_no / pickup_no            channel        （MP|APP|H5，来源留痕）
  entity_no（常去店）                  verified_at
  ❌ 删除 phone/openid/unionid/apple_sub    UNIQUE(identity_type, identity_value)
                                           INDEX(user_no)
```

一个人多条凭证，新增来源只是多一行，**不再需要改表**。

### 6.4 凭证类型与识别强度

| identity_type | 来源 | 作用域 | 能否跨端认人 |
|---|---|---|---|
| **`WX_UNIONID`** | 微信开放平台 | **同主体下所有微信应用** | ✅ **最强** |
| `WX_OPENID_MP` | 小程序 `code2Session` | 仅该小程序 | ❌ |
| `WX_OPENID_APP` | App 微信 SDK | 仅该 App | ❌ |
| `WX_OPENID_OA` | 公众号网页授权（H5） | 仅该公众号 | ❌ |
| **`PHONE`** | 短信 OTP / 微信手机号快速验证 | 全局 | ✅ **次强** |
| `APPLE_SUB` | Apple identityToken 的 `sub` | 仅该 App | ❌ |

> 三个 openid 互不相通，**只有 unionid 能把它们串成一个人**——
> 这就是 §6.5 那个前提为什么是硬要求。

### 6.5 微信生态的前提（必须先做，否则统一无从谈起）

**小程序、公众号、App 三者必须绑定到同一个微信开放平台主体**，
否则拿不到共同的 unionid，跨端识别在技术上不可能。

这是**注册配置问题，不是代码问题**，且要在 App 立项前确认——
事后补绑，历史用户的 unionid 需要回填，代价高得多。

各来源的最优认证路径：

| 来源 | 推荐方式 | 一次拿到 | 说明 |
|---|---|---|---|
| **小程序** | `wx.login` + `getPhoneNumber` | openid · unionid · **phone** | **最优**：一次授权同时拿到弱标识与强标识，直接完成识别，几乎不产生"无手机号账号" |
| **App** | 微信 SDK 授权 / 手机号 OTP / Apple | openid_app · unionid ／ phone ／ apple_sub | Apple 登录是**上架 iOS 的强制项**（提供第三方登录就必须提供 Apple） |
| **H5** | 公众号网页授权 / 手机号 OTP | openid_oa · unionid ／ phone | 微信外的 H5 只能走 OTP |

### 6.6 识别同一个人：按强度依次查

登录时**不是只查一个凭证**，而是把本次能拿到的全部凭证按强度排队去找人：

```
① WX_UNIONID  ── 命中即认定（跨微信应用最可靠）
② PHONE       ── 命中即认定（跨生态，人真实控制）
③ 本次 openid / apple_sub ── 命中即认定（同应用回访）
④ 全部未命中  ── 建新账号，并把本次拿到的凭证一次性全部登记
```

命中之后**补登本次新出现的凭证**（例如小程序老用户首次在 App 登录，
命中 unionid，则补一行 `WX_OPENID_APP`）。这样识别能力**随使用越来越强**。

关键改进：现状是"只用一把钥匙开一把锁"，目标是"手上所有钥匙都试一遍，
开了之后把新钥匙也挂到同一串上"。

### 6.7 账号合并：定策略，不自动合

即使有上述机制，仍会残留冲突：账号①（仅 openid，无手机号）与
账号②（仅 phone）本是同一人，直到某天①补绑手机号才发现——而该手机号已属②。

**策略：不自动合并。**

自动合并要迁移订单、积分、卡包、优惠券、地址，横跨 5 个域；
一旦合错，用户资产错乱且**难以回滚**。正确做法：

| 步骤 | 做法 |
|---|---|
| 1 检测 | 绑定时发现凭证已属他人 → 不报"手机号已占用"这种含糊错误，明确提示"该手机号已关联另一账号" |
| 2 验证 | 要求用户**同时证明对两个账号的控制权**（两边各验一次） |
| 3 合并 | 走**显式的合并流程**（跨域编排 / saga），逐域迁移并记录 |
| 4 留痕 | 合并写入 `sys_audit_log`，保留双方原始 user_no，**可追溯** |
| 5 预防 | 小程序侧优先用 `getPhoneNumber` 一次拿全，从源头减少"无手机号账号" |

一期可以只做 1、2、4（检测 + 阻止 + 留痕），把 3 放到有真实需求时再建——
但**检测必须有**，否则冲突会以"手机号已被占用"的形式让用户莫名其妙。

### 6.8 改动清单

| 项 | 内容 |
|---|---|
| 建表 | `usr_identity`，含 `UNIQUE(identity_type, identity_value)` |
| 数据迁移 | `usr_account` 的 phone/openid/apple_sub 三列各拆成 `usr_identity` 一行；unionid 若有值一并迁 |
| 删列 | 迁移验证后删除 `usr_account` 的四个凭证列与三个唯一键 |
| 认证改造 | `resolveIdentity` 返回**凭证集合**而非单个；`findOrCreate` 改为 §6.6 的按强度查找 + 补登 |
| 渠道对接 | `shop-channel/auth/` 落地 `code2Session`、微信手机号解密、Apple token 验签（现状三处都是 `TODO(S4)`） |
| 绑定接口 | "补绑手机号 / 绑定微信"走同一套凭证登记，含 §6.7 的冲突检测 |

> 这项与缺陷 C（Realm 拆三值）**都动认证主干，建议合并成一个批次**，
> 只做一次回归测试。

## 七、缺陷 E：三端授权强度不一致

### 7.1 现状对比

| | C 端 | B 端 | 运营端 |
|---|---|---|---|
| Realm | CONSUMER | **CONSUMER（与 C 端共用）** | OPERATOR |
| authorities | `ROLE_CONSUMER` 固定 | **与 C 端完全相同** | `ROLE_OPERATOR` + 各角色 |
| 功能权限 | 无 | **无** | `@PreAuthorize("@perm.can(码)")` |
| 实际防线 | Service 层 `requireUser()` | **业务层 `BizContext.requireXxx()`** | 过滤器 + 方法注解 + 数据域 |

**B 端是三者里最弱的一环**：`mch_store_role` 表已建（MANAGER/CLERK），
但**从未接入 Spring Security 的 authorities**。于是"店员不能改价"这类规则，
现在只能靠每个接口自己记得判——漏一个就是越权。

### 7.2 目标：两条正交的防线

| 防线 | 回答什么 | 载体 |
|---|---|---|
| **功能权限** | 这个角色**能不能做**这件事 | `authorities` + `@PreAuthorize` |
| **数据域** | 他**能操作哪些行** | `BizContext` + `DataScopeHandler`（SQL 层） |

两者不可互相替代：`BizContext` 能判"这是不是他家的店"，
但判不了"店员能不能改价"；反过来也一样。

B 端接入后：

```java
// merchantChain 里，按 mch_store_role 挂 authorities
ROLE_OWNER / ROLE_MANAGER / ROLE_CLERK   （角色）
biz:goods:price / biz:order:refund / …    （权限码）

@PreAuthorize("@perm.can('biz:goods:price')")   // 店员没有这个码
public void changePrice(...) { ... }
```

`BizContext` **保留**，继续管数据域——职责收窄，不再兼职做授权。

### 7.3 缺陷 F：角色→权限码硬编码

`Perms.java` 的注释自己写着*"一期硬编码，M9b 接 DB"*：

```java
private static final Map<String, List<String>> ROLE_PERMS = Map.of(
        "SUPER_ADMIN", List.of("*"), "BD", …, "GOODS_OPS", …, "SUPPORT", …);
```

加一个角色、调一次权限都要**发版**。目标：建 `sys_role` / `sys_role_perm` 两张表，
`Perms.java` **只保留权限码常量**（编译期可引用，`@PreAuthorize` 里能写死不怕拼错），
角色→码的映射入库。

配套：改权限后已登录的会话要能立刻失效——`TokenStore.SessionData` 已预留
`permStamp`，改权限时递增，过滤器比对不一致即强制重新加载权限。

### 7.4 缺陷 G：权限码覆盖不足

现状只有 **5 个**权限码，而运营端功能矩阵是 **18 个模块**；
`OpsController` 一个类 15 个端点，多数落在同一个粗码上。

补齐时定命名规范：`<域>:<对象>:<动作>`（如 `merchant:apply:audit`、
`settle:withdraw:approve`），与 ops-web 前端的权限码**同名**——
前端已有 `useCan(...)` 按码控制按钮，两边同名才能一一对账。

> 补权限码与 §九的"垂直切片"是同一件事的两面：Controller 按域切开后，
> 每个域的权限码自然就在该域的 `api/ops` 包里定义，不再堆在一个 `Perms.java`。

### 7.5 改动清单

| # | 内容 | 依赖 |
|---|---|---|
| E1 | `merchantChain` 按 `mch_store_role` 挂 authorities | **需先做缺陷 C**（Realm 拆三值） |
| E2 | B 端敏感操作加 `@PreAuthorize`（改价、退款、提现、改店铺资料） | E1 |
| F1 | 建 `sys_role` / `sys_role_perm`，映射入库 | 无 |
| F2 | `permStamp` 生效：改权限即时失效会话 | F1 |
| G1 | 权限码补齐到 18 模块，与前端同名 | 无（可并行） |

## 八、整体批次建议

七项缺陷按"改哪块代码"归成四批，每批一次回归：

| 批 | 含 | 特点 |
|---|---|---|
| **批一** | A 密码哈希 · B OTP 限流 | 独立、可立即发；**危害最大，先做** |
| **批二** | C Realm 拆三 · D 身份统一 | 都动认证主干，一起改一起测；D 含数据迁移 |
| **批三** | E B 端授权接入（依赖批二） | 授权模型对齐 |
| **批四** | F 角色入库 · G 权限码补齐 | 与垂直切片重构一起做更省事 |

**批一与批二之间不必等**，批一改的是密码与限流，批二改的是身份与令牌，
代码几乎不重叠。
