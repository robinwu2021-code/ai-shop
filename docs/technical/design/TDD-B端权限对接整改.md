## 1. 需求摘要

B 端六角色判权（13 码 × 62 端点）已落地并由 4 条守卫锁住，**后端机制层无需改动**。
本次整改解决的是它落地之后暴露出来的三类问题：

1. **前端裁剪跟不上后端判权**（A 组 6 项）—— 页面门禁只写一个码，`load()` 里却打了要
   另一个码的端点。后端正确返回 70006，前端把它渲染成「这家店什么都没有」。
   **验收标准：六个角色各登录一次，每一页要么正常可用、要么显示 denied 空态，
   不出现整页空白或 toast 报错。**
2. **需求文档被实现越过**（D 组 6 项）—— 三份需求文档仍把已落地的能力标成
   ⬜/🔴/「待实施」。**验收标准：三份文档与产物一致，且不再各抄一份角色表。**
3. **功能面缺入口**（B 组 2 项）与**员工管理的三个缺口**（E 组 3 项）。

其中 **D2（配送员订单视图）是唯一一条真正没落地的需求**，需要先拍板 —— 见 §3.0。

## 3. 方案设计

### 3.0　D2 配送员订单视图 —— **唯一需要拍板的选型**

> 需求 §4.4 原文：配送员的 `biz:order:view` 标 **🟡 不是 ✅**，
> 「全方案唯一需要新增后端能力的地方……他要『待自送的单 + 地址』，不该看到金额与全店订单。
> 手法照抄 `PickupOrderVO` 那套裁剪，**不用条件序列化藏字段** —— 那种藏法迟早被某个 DTO 复用漏出去。」

现状：`BizOrderController:33` 的 `/biz/order` 对所有持 `biz:order:view` 的角色返回同一个
完整 `OrderVO`（`Amount` 四档金额、`verifyCode`、`pickupName`、全店订单）。

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **1 裁剪 VO** | 新增 `CourierOrderVO`（子单号/地址/状态/收件人），`/biz/order` 按当前角色选 VO | 需求原文指定；不动权限模型；`PickupOrderVO` 有现成范式 | 同一端点两种返回，契约要写清楚；前端要按角色分支渲染 | **推荐** |
| 2 加细码 | 新增 `biz:order:view:limited`，COURIER 换成它，端点按码分岔 | 判权仍只看码，守卫天然覆盖 | 13 码变 14；「同一端点两种返回」的问题一个没少；矩阵要重排 | 备选 |
| 3 明确降级 | 接受配送员看得到金额，把 §4.4 的 🟡 改成 ✅ 并写下理由 | 零成本；小店场景配送员多半就是店员兼的 | 「不该看到金额」是需求写下的判断，推翻它要有同等分量的理由 | **也是正当答案** |

**推荐方案 1**，理由：`verifyCode` 一并被裁掉 —— 现在 COURIER 与 CS 读得到全店取货码，
虽不构成绕过（核销端点仍要 `biz:verify`），但取货码是凭证，顺手收掉比单独立项划算。

**若选方案 3，任务 1 退化为纯文档改动**（改 §4.4 与 `需求矩阵-三端.md:72` 两处），
任务 2（A1 配送页）不受影响。

> ⚠️ **任务顺序依赖**：方案 1/2 会改配送页的数据源，A1 必须等它定了再动，否则返工。

### 3.1　A 组：前端裁剪（6 项，全部在 b-app）

**共同原则（不新增机制，只推广已有写法）**：

```
① 页面门禁 denied ⊇ 该页所有调用所需的码   —— 兜底，管「进不进得来」
② 页内并发调用一律各自 catch，不用裸 Promise.all —— 管「少一块而不是整页没」
③ 按钮/分区跟着自己的码走 v-if="can(...)"  —— 管「不画点不动的东西」
```

| 任务 | 文件 | 改法 | 验收 |
|---|---|---|---|
| **A1** | `pages/delivery/index.vue:35` | `mDeliveryRule()` 用 `can('biz:store')` 包住并 `.catch(() => null)`；规则卡片 `v-if="rule"` | COURIER 进配送页：看得到待送单、看不到规则卡片、无报错 |
| **A2** | `pages/picking/index.vue:40` | 两个调用各自 `.catch()`；到货区 `v-if="can('biz:verify')"` | PICKER 进分拣页：分拣单可见、可上报短少 |
| **A3** | `pages/goods-list/index.vue` | 加 `:denied="!merchant.can('biz:stock')"` | CS 点商品 tab：denied 空态，无 toast |
| **A4** | `pages/orders/index.vue` TABS | 售后 tab 加 `perm: 'biz:aftersale'`，`TABS.filter(t => !t.perm \|\| can(t.perm))` | CLERK 看不到售后 tab |
| **A5** | `pages/order/index.vue:22-28` | `canShip`/`canDeliver` 各加 `&& merchant.can('biz:ship')` | CS 进详情页看不到发货按钮 |
| **A6** | `goods-edit` / `stats` / `order` | 各补 `:denied` | 深链/刷新时是 denied 空态 |
| **A7** | `pages/home/index.vue:119` | 三个调用前先 `can()`，与同文件 `blockers` 一致 | 店员进首页只发 1 个请求 |

**A2 的附带后端决策**：若「标记到货」对理货员是必需的，`/biz/pickup/orders` 应从
`VERIFY` 改成 `canAnyBiz(VERIFY, RECEIVE)`。

- 倾向**不改**：分拣页的到货区按 `can('biz:verify')` 隐藏即可，理货员的活是分拣与报短少，
  「标记到货」触发的是给买家的到货通知，属于交付面 —— 与 `RECEIVE`/`VERIFY` 的分界
  （对货 vs 对顾客）一致。
- 若产品认为理货员必须能标到货，再改端点，**那时要同步更新矩阵与 §4.3**。

**A3 的附带问题**：custom tabBar 已开（`pages.json: "custom": true`），
是否对 CS/COURIER 隐藏「商品」tab？**建议本次不做** —— tabBar 少一格会让四格布局变形，
denied 空态已经把话说清楚了。记入清单待产品确认。

### 3.6　任务 16：前端权限守卫（本次唯一的新机制）

**命题**：页面的 `denied` 门禁必须 ⊇ 该页所有 `api.*` 调用在 `REQUIRED` 里要求的码。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A 豁免清单式**（仿 `BizEndpointPermTest.PUBLIC`） | 每条豁免要写理由；新页面默认被拦 | 需要维护豁免表 | ✅ 采用 |
| B 基线快照式（仿 `ops-perm-matrix`） | 零维护 | 「页面 × 码」的变化是 diff，不强迫人回答「为什么这页可以不判」 | ❌ |

**落点**：`packages/shared/tests/biz-page-perm.test.ts`，
从 `scripts/gen-biz-feature-perm-matrix.mjs` 导入纯函数（与 `ops-perm-matrix.test.ts` 同形）。

**必须有豁免表**，因为有两种合法的「门禁不足」：

1. **页内逐块裁**（`home` 的每个格子跟着 `c.perm`）—— 正确写法，豁免
2. **调用点自己 catch 且 UI 判空**（A1/A2 改完之后的 `delivery`/`picking`）—— 也是正确写法

→ 豁免表的 key 是 `页面 + 码`，value 是理由字符串，**理由为空则测试红**。

**核心接口**（生成器新增导出，不改现有产物逻辑）：

```js
export function scanPages(root)        // → [{ dir, gates: string[], calls: string[] }]
export function requiredOf(root)       // → Map<归一化端点, 权限码>
export function clashesOf(page, req, roles)  // → [{ role, missing: string[] }]
```

### 浏览器验证抓到一个我自己写出来的回归 —— 值得记下来

改完 A1 之后，**老板打开配送页也看不到规则卡了**。

原因：`load()` 里用 `can('biz:store')` 决定要不要发请求，而 `can()` 在 perms 没加载时
一律返回 false（fail-closed，这是对的）；深链或刷新时 `onShow` 会早于外壳的
`ensureScope()` 跑完 —— **于是判权状态没到位，就等于把自己锁在门外，而且不会重试**。

这与 `merchant.ts` 里 `ensureScope` 那段注释记的是同一个坑
（「老板刷新商品页，四个按钮全没了」），只是换了个形态：
那次是**渲染**依赖 perms，这次是**发不发请求**依赖 perms。

修法：凡是拿 `can()` 决定「要不要发这个请求」的 `load()`，
开头先 `await merchant.ensureScope()`（幂等 + 并发去重）。已加在 `delivery`、`picking`、`home` 三页。

> **结论**：`can()` 用来**画不画**是安全的（错了只是晚一拍出现），
> 用来**发不发请求**必须先等 scope —— 错了就是一个静默的功能缺失。
> 这一条应写进任务 #16 的守卫说明里。
