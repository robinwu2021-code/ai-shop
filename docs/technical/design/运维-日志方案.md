## L1 定位

生产服务器（腾讯云单机）上**所有日志**从产生、本机滚动、归档到删除的统一规则：
**每一类都有上限、有保留期、有归宿；失控能在小时级被发现。**

起因：2026-09-14 根分区被一个从未轮转过的 `app.log` 写满（41.6G），线上 DOWN 约 23 小时。
它从 9-4 就开始被刷，**十天没有任何人知道**。那次止血只补了看得见的那个洞，这份方案把整台机过一遍。

## L2 结构

![日志从产生到删除](./diagrams/运维-日志从产生到删除.svg)

图上看不出来的四件事：

- **最要紧的是底下那条告警线**，不是中间那几格上限。上限只保证日志写不满盘，
  挡不住别的东西写满盘；而这次真正的失败是「十天没人知道」。
- 第 ② 列每一格的「上限」不是一回事：应用日志用的是 logback 的**总量封顶**，
  是真上限；其余用的是 logrotate 的「单文件大小 × 保留份数」，只是间接上限。
  只有前一种能保证「刷得再凶也超不过某个数」。
- 应用日志进 COS 的那条是虚线：法规要的是网络日志；应用日志里可能有手机号等个人信息，
  归档一年等于把暴露面放大一年。**先核脱敏再定。**
- `deploy.log` 长得像日志，其实是**回滚的真源**（`deploy-backend.sh --rollback`
  读它的倒数第二行），任何轮转都不许碰它。

### 总表：每类日志去哪、多大、留多久

| 类 | 来源 | 本机位置 | 本机上限 | 本机保留 | 进 COS | 总保留 | 依据 |
|---|---|---|---|---|---|---|---|

| 应用错误 | ai-shop | `…/app/error.log*` | 总量 200M | 30 天 | 待定 | — | 排障常要回看一个月 |

## L3 详情

### 1. 现状（2026-09-14 实测）

| 问题 | 实测 | 后果 |
|---|---|---|
| 三个 Java 服务**都没有日志配置** | 仓库里没有 `logback-spring.xml`，`application.yml` 只设了级别；全用 Spring Boot 默认 —— 只打控制台 | 文件、大小、保留全靠外部；应用自己**没有任何上限** |
| 落点三种写法 | ai-shop、job：systemd `append:` 写文件；pay：进 journal | 排障要去三处找；`append:` 的文件被 systemd 握着句柄，只能 copytruncate |
| logrotate 给不出总量上限 | 只有「单文件 × 份数」；copytruncate 在拷贝与截断之间有丢行窗口 | 9-14 之前连这个都没配 |
| 访问日志只留 14 天 | 发行版默认 `rotate 14` | **不满足法定 ≥ 6 个月** |
| 堆栈无节制 | outbox 一次失败 140 多行堆栈，同一条事件重试 16 万次 | 41.6G 的直接来源 |
| **没有任何告警** | 没有磁盘告警，没有增速告警 | 从 9-4 刷到 9-13，十天无人知道 |
| 非日志的累积物没人清 | `/tmp` 里 5 个残留 jar 近 1G（部署脚本中途退出时不清）；`shop-app.env.bak*` 13 份，都含真实凭据 | 另一种写满盘的方式；凭据副本越散越难管 |

**已经有人管、本方案不重复的**：旧 jar（部署脚本按「最近 5 个 + 当前软链」保留，见部署约定 §5）；
数据库每日备份（本机 3 天 + COS，见 `backup-to-cos.sh`）。

### 2. 目录规划

```
/var/log/ai-shop/                     deploy:deploy 750
├── app/   app.log   app.log.2026-09-14.0.gz …   error.log   error.log.2026-09-14.0.gz …
├── job/   job.log   …                            error.log   …
├── pay/   pay.log   …                            error.log   …
└── ops/   backup.log   housekeeping.log   logwatch.log   archive.log
/var/log/nginx/                       发行版位置，不动
/var/log/mysql97/                     已按此建
/var/log/journal/                     系统
/opt/ai-shop/deploy.log               ← 留在原处：回滚真源，部署脚本写死了这个路径
/opt/ai-shop/incident-YYYYMMDD/       事故留档；归档到 COS 后本机留 90 天
```

| # | 规则 | 为什么 |
|---|---|---|
| 1 | 一个服务一个子目录 | 每个服务都会有 `error.log`，平铺必然撞名；预算和告警也按目录算 |
| 2 | 文件名固定为 `<服务>.log` + `error.log`，滚动后缀由 logback 生成 | 归档脚本与巡检按固定模式找文件 |
| 3 | 发行版管的（nginx、journal、syslog）不挪 | 挪了之后包升级会和它打架 |
| 4 | 属主 `deploy:deploy 750` | 三个服务都以 deploy 运行，自己写、自己滚 |
| 5 | 路径走环境变量，不写进 jar | 同一个 jar 在本地与生产落点不同；零硬编码 |

现有的 `/var/log/ai-shop/{app,job,backup}.log` 在 P3 切换时迁走，旧文件按原规则自然过期。

### 3. 大小控制：两层

#### 3.1 应用层 —— 真上限

用 Spring Boot 自带的滚动配置，**不写代码**，只在各服务的环境文件里加：

```bash
# /opt/ai-shop/shop-app.env（job、pay 同理，路径与额度按总表）
LOGGING_FILE_NAME=/var/log/ai-shop/app/app.log
LOGGING_LOGBACK_ROLLINGPOLICY_MAX_FILE_SIZE=100MB
LOGGING_LOGBACK_ROLLINGPOLICY_MAX_HISTORY=14
LOGGING_LOGBACK_ROLLINGPOLICY_TOTAL_SIZE_CAP=1GB
LOGGING_THRESHOLD_CONSOLE=ERROR           # 控制台只留 ERROR：它现在进 journal
LOGGING_EXCEPTION_CONVERSION_WORD=%wEx{30} # 每个异常最多 30 帧堆栈（需 P3 实测参数是否被接受）
```

滚动文件名默认就是 `app.log.%d{yyyy-MM-dd}.%i.gz`（自带压缩），不用另配。

**ERROR 另存一份**要一个 `logback-spring.xml`：引入 Spring Boot 默认的文件与控制台 appender，
再加一个带 `ThresholdFilter(ERROR)` 的滚动 appender 写 `error.log`（30 天、总量 200M）。
三个服务各放一份、内容相同，由一条测试守着三份一致 ——
pay 正在和主工程解耦（`backend/known-pay-reverse-deps.txt`），不能指望它依赖一个共享模块。

systemd 单元随之改为 `StandardOutput=journal`：应用自己写文件、自己滚，
journal 里只剩 ERROR 和 logback 初始化之前的 JVM 输出（启动即崩时看得见）。

**为什么这一层是关键**：`maxFileSize 100M + totalSizeCap 1G` 意味着刷得再凶，
这个目录也停在 1.1G 附近 —— 这是 logrotate 给不出的保证。

#### 3.2 系统层 —— 兜底

| 对象 | 规则 | 状态 |
|---|---|---|
| journald | `SystemMaxUse=500M`、`SystemMaxFileSize=64M` | ✅ 9-14 已加 |
| `/var/log/ai-shop/*.log` | daily + 超 200M 立即轮、留 14 份、copytruncate | ✅ 9-14 已加（P3 前的过渡） |
| logrotate.timer | 每小时一次（让 maxsize 及时生效） | ✅ 9-14 已加 |
| **P3 之后** | app/job/pay 从 logrotate **撤出**，logrotate 只管 `ops/*.log` | 同一个文件两个机制轮会打架：logback 正要滚，logrotate 把它截了 |
| nginx、rsyslog | **不改发行版配置** | 见 L4 取舍：改了 conffile 会让自动更新跳过它们的安全补丁；长留交给 COS |

#### 3.3 预算

| 目录 | 最坏占用 | 由谁保证 |
|---|---|---|
| `/var/log/ai-shop/app` | ≈ 1.3G | logback：运行 1G + 错误 200M + 两个当前文件 |
| `/var/log/ai-shop/job` | ≈ 0.3G | logback：运行 200M + 错误 50M + 当前文件 |
| `/var/log/ai-shop/pay` | ≈ 0.5G | logback：运行 300M + 错误 150M + 当前文件 |
| `/var/log/ai-shop/ops` | < 10M | logrotate |
| `/var/log/nginx` | < 5M | 发行版：14 天，每天压缩后 27–80K |
| `/var/log/journal` | 500M | journald |
| syslog、auth.log 等 | < 100M | 发行版 |
| `/var/log/mysql97` | < 100M | logrotate |
| **合计** | **≈ 2.8G** | 告警线定在 5G |

### 4. 定期删除

#### 4.1 日志：一条规则只有一个执行者

| 对象 | 谁删 | 规则 |
|---|---|---|
| 应用滚动文件 | logback | maxHistory + totalSizeCap |
| `ops/*.log` | logrotate | 90 天 |
| nginx、syslog | logrotate（发行版） | 14 天 / 4 周 |
| journal | journald | 500M |
| COS 归档 | 桶生命周期 | 365 天 |

**两个机制删同一类东西，出了问题查不清是谁删的。** 所以归档脚本只传不删，
本机文件照原规则到期；归档失败由告警兜住（本机留 14 天，够补传）。

#### 4.2 非日志累积物：每日 housekeeping

`deploy/tencent/housekeeping.sh` + `ai-shop-housekeeping.timer`（每天 04:10）：

| 对象 | 规则 | 说明 |
|---|---|---|
| `/tmp/shop-app-*.jar`、`/tmp/pay-svc-*.jar` | 超过 1 天就删 | 部署中途退出的残留；**同时给 `deploy-backend.sh` 加退出时清理**，治本 |
| `shop-app.env.bak*`、`pay.env.bak*` | 各留最新 5 份，全部 `600 root` | 含真实凭据 |
| `pre-v*.sql.gz`、`predeploy/*` | 30 天 | 迁移前的安全网；每日全量备份在 COS 另有一份 |
| `incident-*/` | 归档到 COS 后，本机留 90 天 | |
| 旧 jar | **只核对不删**：超过 6 个就在日志里报一行 | 部署脚本已经在管；一条规则只能有一个执行者 |

先 **dry-run 一周**（只列出要删什么，不删），对过清单再打开删除。每次删了什么记进 `ops/housekeeping.log`。

### 5. 归档到 COS —— 满足 ≥ 6 个月

| 项 | 定法 |
|---|---|
| 桶 | `hxmall-backup-1301656997`：已有、私有、写入者就是服务器定时任务 |
| 前缀 | `serverlogs/<来源>/<YYYY>/<MM>/<DD>/<原文件名>`（`logs/` 已被 COS 自身的访问日志投递占用） |
| 来源 | `nginx-access` · `nginx-error` · `auth`；`app` / `job` / `pay` 待定（见 L4） |
| 时机 | 每天 03:40（在 03:20 的备份之后），上传**最近一次轮转出来、不再变化**的那份。注意 nginx 配了 `delaycompress`：前一天的是**未压缩**的 `access.log.1`，第二天才变成 `.2.gz` —— 脚本自己压缩后上传，不等那一天；`auth.log` 是按周轮的，随之按周归档 |
| 核对 | 上传后比对大小与 MD5（`cos_put.py` 是否已支持待确认）；成功写一行进 `ops/archive.log` |
| 生命周期 | 按 COS 桶规划既定：30 天转低频、90 天转归档、365 天删除 |
| 量 | nginx 压缩后每天 27–80K（实测）；应用日志约 20MB/天、压缩后约 2MB → 每月不到 100MB |
| 密钥 | 沿用备份脚本那把。桶规划里早记着「应换成只能写 backup 桶的子账号密钥」—— 本方案不解决它，但它是归档一年日志的前置风险 |

**P2 开工前必须先核的**：
- nginx 访问日志的 URL 查询串里有没有令牌、手机号 —— 有的话先在 `log_format` 里去掉，再归档
- 应用日志里有没有手机号、证件号、密钥 —— 这决定应用日志进不进 COS

### 6. 监控与告警

| 告警 | 阈值 | 由谁发 | 为什么 |
|---|---|---|---|
| 根分区使用率 | > 80% 警告，> 90% 严重 | 腾讯云云监控（CVM 自带指标，控制台配策略） | **这次缺的就是它** |
| `/var/log` 总量 | > 5G | 本机巡检（每小时） | 预算线 |
| 日志增速 | 任一目录 1 小时增长 > 200MB | 本机巡检 | 这次是 0.65G/时；正常在 1MB/时量级 |
| 归档失败 | 昨天没有成功记录 | 本机巡检 | 本机只留 14 天，过了就补不回来 |
| outbox 出现 FAILED | > 0 | 应用侧（已开任务） | 毒消息停住之后，得有人看得见 |

本机巡检 `deploy/tencent/logwatch.sh` + timer。它的**通知出口要定**：
只写 journal 的 err 级等于只能被动查；要主动推，得有一个通道 → 见 L4 待决 3。

### 7. 应用日志内容规范

1. 同一个异常反复发生，只在第一次（或每 N 次）打完整堆栈 —— outbox 的修法，已开任务
2. 每个异常最多 30 帧堆栈（§3.1 的 `exception-conversion-word`）
3. 第三方库降噪：Tomcat、Hikari、MyBatis 设为 WARN
4. **不得出现**：手机号明文、证件号、密钥、令牌、支付敏感字段 —— 进 COS 的日志要存一年，
   漏一条就放大一年
5. 生产用 INFO。DEBUG 只能临时开、要写明到期时间 —— 环境文件改完要记得改回来

### 8. 分阶段实施与验收

| 阶段 | 内容 | 要发版吗 | 验收（都要能证伪） |
|---|---|---|---|
| **P0** ✅ 9-14 | truncate 41.6G · 20 条毒消息改 FAILED · logrotate `/var/log/ai-shop/*.log` · 每小时 timer · journald 500M | 否 | 已验：health UP；稀疏文件夹住 maxsize 门限；journald 自报 max 500.0M |
| **P1** 本机配置 | housekeeping（先 dry-run）· `deploy-backend.sh` 退出清 `/tmp` · `ops/` 目录与 backup.log 迁入 · 巡检 · **云监控磁盘告警（需你在控制台配）** | 否 | dry-run 清单与实测一致；往 `ops/` 放一个 1.1G 稀疏文件，下一轮巡检必须报警（验完删掉） |
| **P2** COS 归档 | 前置核查（URL 里的令牌与手机号）· 归档脚本与 timer · 桶生命周期 | 否 | 跑一次后 COS 上能列出昨天的 nginx `.gz`、MD5 一致；人为让一次上传失败，巡检必须报警 |
| **P3** 应用层 | 三个服务的环境变量 + `logback-spring.xml` · 单元改 journal · **同一次改动里**把 app/job/pay 从 logrotate 撤出 | **三个服务各发一次** | 测试环境里造洪水（每秒上千条带堆栈），目录总量停在 totalSizeCap 附近；消融：去掉 totalSizeCap，必须继续涨 |
| **P4** 结构性 | 独立日志盘 · MariaDB binlog | 需决策 | 见 L4 |

P1、P2 不发版、可随时回退（删掉对应的 timer 与配置即可）；P3 改的是配置项，回退只需恢复环境文件与单元。

## L4 边界

### 待决（需要你定）

1. **应用日志进不进 COS。** 建议：先不进，只归档法规要求的网络日志与安全事件；等 P2 的脱敏核查有结论再定。
2. **本机保留期**：应用 14 天、错误与支付 30 天，够不够排障。
3. **告警通知给谁、走什么通道**：云监控可发短信 / 邮件 / 微信；本机巡检要主动推的话，需要一个企业微信群机器人之类的 webhook。
4. **P3 的发版窗口**：三个服务各重启一次（按部署文档，ai-shop 的会话持久化在 ehcache，重启不掉线）。
5. **独立日志盘**：给 `/var/log` 挂一块 CBS 数据盘。结构上最稳 —— 日志再怎么刷也写不满根分区、拖不垮同盘的 MariaDB；代价是要花钱，迁移时要短停一次。
6. **MariaDB 的 binlog 关着** → 没有按时间点恢复，最坏丢一天数据。和日志相关但不属于本方案，建议单独立项。

### 取舍记录

| 选了 | 没选 | 为什么 |
|---|---|---|
| logback 自己滚动、总量封顶 | 继续 systemd `append:` + logrotate | logrotate 只能「单文件 × 份数」，给不出总量上限；copytruncate 有丢行窗口；`append:` 让 systemd 握着句柄 |
| 满了丢最老的（totalSizeCap） | 满了停写 | 停写会让应用报错或阻塞；丢老的只损历史 —— 而 ERROR 另存了一份，告警也会响 |
| 本机短留 + COS 长留 | 本机留 6 个月 | 本机只有一块 59G 系统盘，还和数据库同盘 |
| nginx / rsyslog 不改发行版配置 | 改 rotate、加 maxsize | 那是 dpkg 的 conffile，改了之后 unattended-upgrades 会因要提示覆盖而**跳过它们的安全更新** |
| 走备份桶的 `serverlogs/` 前缀 | 新开一个日志桶 | COS 桶规划的规矩：写入者相同、生命周期相同就走前缀 |
