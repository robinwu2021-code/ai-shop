## 二、全库三条通则

每张表都遵守，不在表上逐条重复。

| # | 通则 | 防住什么 |
|---|---|---|
| ① | **没有 `tenant_no`** | `owner_id` 就是隔离维度。再加一层租户会让每个唯一键多一列，而那一列在可预见的部署里只有一个取值 —— **独立领域的好处之一就是不背平台的横切列** |
| ② | **没有 `deleted` 软删列** | 主数据用 `status=ARCHIVED`、单据用 `VOIDED`、流水**根本不能删**。三种「消失」各有各的语义，压成一个 `deleted` 之后「这行为什么不见了」没人答得清；而流水一旦有删除入口，这张表的全部价值当场归零 |
| ③ | **没有外键** | 完整性由聚合根在应用层保证 + 唯一键兜底。建了外键，「哪些引用允许悬空」就分散在 DB 与代码两处，两处不一致时以谁为准没人答得清 |

前缀 `inv_`，**不用 `prd_`** —— 那是平台商品域的前缀，独立交付时客户库里出现 `prd_` 会让人以为还有个商品系统。

## 三、19 张表

| # | 表 | 用途 | 谁写 | 量级 |
|---|---|---|---|---|
| 1 | `inv_owner` | 业主 | ACL 同步 | 商家数 |
| 2 | `inv_location` | 库位（门店/仓/在途/虚拟） | ACL 同步 + 人 | 门店数 ×1.2 |
| 3 | `inv_uom` | 计量单位字典（**全局，不带 owner**） | 种子 | 8 行 |
| 4 | `inv_item` | 物料（零售形态即 SKU） | ACL 同步 + 人 | SKU 数 |
| 5 | `inv_item_ref` | 外部引用（平台/ERP/条码/收银） | ACL 同步 + 人 | SKU 数 ×1–3 |
| 6 | `inv_stock_balance` | **库存余额** ★ | 过账 + 预留 | SKU × 库位 |
| 7 | `inv_ledger` | **流水**（只追加） | 过账 | 最大的一张 |
| 8 | `inv_reservation` | 预留头 | 交易域 | 订单数 |
| 9 | `inv_reservation_line` | 预留行 | 交易域 | 订单行数 |
| 10 | `inv_inbound_order` | 入库单头 | 人 + 系统 | 中 |
| 11 | `inv_inbound_line` | 入库单行 | 同上 | 中 |
| 12 | `inv_outbound_order` | 出库单头 | **系统为主** | 订单数 |
| 13 | `inv_outbound_line` | 出库单行 | 同上 | 订单行数 |
| 14 | `inv_stock_count` | 盘点单头 | 人 | 小 |
| 15 | `inv_stock_count_line` | 盘点单行 | 人 | 小 |
| 16 | `inv_transfer_order` | 调拨单（编排一出一入） | 人 | 小 |
| 17 | `inv_outbox` | 领域事件出站 | 系统 | 中 |

**后续两张，不在 V1**：`inv_daily_snapshot`（D3 报表日快照）· `inv_open_credential`（D4 的 Open API 凭证）。
形状还会变，早建等于早改。

### 为什么没有幂等表

平台有 `sys_idempotent`，这里**不需要对应物** —— 幂等一律走自然键：

| 场景 | 幂等键 |
|---|---|
| 预留重试 | `uk_reservation_ext (owner_id, external_ref)` |
| 过账重放 | `uk_doc_line (doc_no, line_no)` |
| 单据重复提交 | `uk_inbound / uk_outbound (owner_id, doc_no)` |
| Open API `stock:sync` | 调用方的 `request_id` **参与生成单号** → 落到 `uk_outbound` 上 |

**多一张幂等表就多一个要过期清理的东西**，而自然键不用清理。

### 为什么要自带 outbox

独立库意味着**用不了平台的 `sys_outbox`**。这是「独立交付」这条约束顺带产生的成本，
如实记在这里 —— 投递侧将来换 MQ，写入侧不动。

## 四、唯一键与索引：每一条的理由

| 键 | 表 | 理由 |
|---|---|---|
| `uk_balance (owner, item, location)` | 余额 | **身份三元组无可空项**。并发下靠它 + 条件更新防超卖 |
| `uk_doc_line (doc_no, line_no)` | 流水 | 过账重放不写两行 |
| `uk_ref (owner, ref_system, ref)` | 外部引用 | 一个物料可有多个条码；**一个条码不能指向两个物料** —— 否则收银台扫一次出来两件货 |
| `uk_item_code (owner, item_code)` | 物料 | 货号在业主命名空间内唯一，**允许多行 NULL**（没填货号的货有的是；NOT NULL 会逼人编一个） |
| `uk_owner_ext (external_ref)` | 业主 | 业主与平台主体 **1:1**（已定）。多执照商家仍是一个业主 —— 货是同一批货 |
| `uk_reservation_ext (owner, external_ref)` | 预留 | 网络超时重试是常态，不幂等会预留两次而第二次没人释放 |
| `idx_ledger_seq (owner, item, location, id)` | 流水 | 自校验回放与「这个 SKU 的变动明细」 |
| `idx_ledger_cursor (owner, id)` | 流水 | 外部增量拉取。**排序用 `id` 不用时间** —— 时钟回拨会让游标漏行 |
| `idx_ledger_reason (owner, reason_code, occurred_at)` | 流水 | 「这个月报损了多少」免 join 单据 |
| `idx_balance_moved (owner, last_moved_at)` | 余额 | 滞销判定不必扫流水 |
| `idx_reservation_expire (status, expires_at)` | 预留 | 回收任务扫它 —— **跨进程之后兜底必须在本领域内** |

## 五、不变式 ↔ 数据库约束

| 不变式 | 由谁保证 |
|---|---|
| I1 `available = on_hand − reserved ≥ 0` | 条件更新 + `uk_balance`（DB 表达不了，靠应用 + 并发测试） |
| I2 余额变动与流水 1:1 | 同事务写入 + `uk_doc_line` + **回放守卫** |
| I3 流水不可变 | 表上**没有** `updated_at` / `updated_by` / 删除路径；作废写反向行 |
| I4 调拨全程 `Σ on_hand` 守恒 | `TRANSIT` 库位 + 调拨必生成两张单（应用层） |
| I5 预留只改 `reserved` | 预留不写流水（应用层 + 场景测试） |
| I6 `external_ref` 唯一 | `uk_ref` |

> **三条要靠应用层**（I1/I4/I5）。DB 表达不了的，就要有一条**撤掉修复必须变红且点名**的守卫 ——
> 只写在文档里的约束，半年后没人记得。

## 六、建库与迁移

### 6.1 独立 Flyway 历史

```
backend/shop-inventory/src/main/resources/db/inventory/V1__inventory_baseline.sql
```

平台的 Flyway 配置是 `locations: classpath:db/migration` —— **目录不同，扫不到这里**，
两条历史天然互不知情。这正是要的：带着平台 260 条迁移交付出去，
第一句话就得是「请先装一个 `ai_shop`」。

**顺带的好处**：迁移号从 `V1` 重新开始，与平台那边的撞号问题彻底无关。

### 6.2 一次性数据搬运（**不是** Flyway）

存量 `prd_sku.stock` / `prd_store_stock` → 进销存。
**跨库，所以不能是一条迁移**，是一个可重跑的搬运任务：

| 步 | 动作 |
|---|---|
| 1 | 每个业主建 `is_default` 库位与 `TRANSIT` 库位 |
| 2 | `prd_sku` → `inv_item` + `inv_item_ref(AISHOP)` |
| 3 | 主体级 `prd_sku.stock` → **默认库位**的余额；店级 `prd_store_stock` → 对应库位 |
| 4 | 每条余额写一行 `INIT` 入库单 + 流水（否则第一次盘点的自校验必然失败 —— 没有上一行） |
| 5 | **对差报告**：逐 SKU 比两边的数，不为零就列出来 |

三条要求：**幂等可重跑**、**只读平台库不写**、**结束时打印对差**。
这是唯一一次不可回退的数据动作，D1 的双写对差期不能省。

### 6.3 平台侧的配套改动（很少）

| 项 | 动作 |
|---|---|
| `prd_sku.stock` / `locked_stock` | D2 之后降为**只读缓存**，加列注释说明真源在 `inv` |
| `prd_sku.cost_price` | 写权移交进销存（唯一的反向同步），平台侧无写入口 |
| ~~`mch_store.store_type`~~ | **撤销** —— 仓已经是 `inv_location.kind` 的一种，平台不需要知道哪个门店是仓 |

> 第三条是这次独立库决策**省掉**的一处改动。上一版建议给 `mch_store` 加 `store_type`，
> 那是「仓寄生在门店表里」的方案；库独立之后仓有了自己的家，平台那一列不必加。

## 七、守卫缺口（要补）

现有两个 DDL 守卫**只扫平台目录**：

| 守卫 | 扫描范围 | 缺口 |
|---|---|---|
| `packages/shared/tests/ddl-parsable.test.ts` | `backend/shop-app/.../db/migration` | 扫不到 `db/inventory` |
| `packages/shared/tests/entity-alignment.test.ts` | 同上 | 同上 |

**S0/D1 要把这两个的扫描目录扩成两处**，否则新库的 DDL 与实体从第一天起就没有守卫 ——
而「迁移加了列、实体没补，那一列永远读出 null」这个坑，这个仓库已经踩过。

## 八、这次「按建议」定下了什么

> 完整决策清单（含本轮新定的十余条）见[决策记录](./进销存-决策记录.md)。

如实记一份，免得半年后有人问「这几条是谁定的」。

| 出处 | 决策 | 结果 |
|---|---|---|
| 建品到出入库 ① | 删档位时余额不为零 | **拦住**，不自动生成报损单 |
| 建品到出入库 ② | 投影时机 | **建品保存即投影**，让「有没有这件货」只有一个答案 |
| 建品到出入库 ③ | 删 SPU | 物料**归档**，**不删流水** |
| 领域对象详解 ① | `on_hand` 为负 | **绝不允许** |
| 领域对象详解 ② | 部分收货 | 一期**不做**，已留位 |
| 领域对象详解 ③ | 盘点冻结出库 | **不冻结**，靠 `book_qty` 快照 |
| 领域对象详解 ④ | `reason_code` 冗余到流水 | **采纳**（快照，不是真源） |
| 领域对象详解 ⑤ | 批次 / 效期 | 一期**只留位**（`track_batch` / `batch_no` / `expire_at`） |
| 领域模型 ② | 物理库 | **先同实例 + 守卫**，D4 再拆物理 |
| 领域模型 ③ | Owner : entity_no | **1:1** |
| 模块化 ① | 模块名 | **`shop-inventory`** |
| 模块化 ② | `cost_price` 写权 | 移到进销存 |
| 模块化 ④ | 写权守卫 | **拦提交**，不只报告 |
| 进销存与报表 ③ | 进货与毛利档位 | **PRO** |
| 进销存与报表 ⑤ | 报表前缀 | 登记 `rpt_`（平台侧，不在本库） |
