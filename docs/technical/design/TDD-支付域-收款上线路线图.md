## L1 · 这份文档回答什么

**「设计、进件、支付」这三件事离能收到第一笔钱还差什么，按什么顺序做。**

不重复各分册的设计，只做一件事：把**现状量出来**，
然后按「哪一步不做则后面全做不了」排序。

其余分册回答「怎么设计」，这份回答「先做哪个」。

## L2 · 一、现状盘点（2026-09-01 逐条验过，不是凭印象）

### 已经能跑的

| | 状态 |
|---|---|
| 结算、分账、账期批次、退款回退 | 有实现，有场景测试 |
| 对账自查（四条轴）+ 差异裁决 | 有实现；本日起按渠道分解 |
| 积分发放 / 抵扣 / 池子恒等式 | 有实现，端开关可控 |
| 通道回调的**验签** | 微信 APIv3、支付宝 RSA2 两家都有实现 |
| 渠道报文落库 | 本日起有（V286） |
| 进件的**业务侧**（提交 / 刷新 / 轮询 / 按门店开通） | `MerchantPaymentServiceImpl` 六个方法齐 |
| 运营端资金页面 | 结算单、批次、分账、费率、支付流水核对，均已实现 |
| `pay-svc` 独立进程 | **线上 8083 已在跑**；费率查询走远程调用 |

### 空的 —— 三处，且互相咬着

**① `ChannelClient` 没有任何生产实现。**

它是「通道 HTTP 调用与签名」那一层。今天 `implements ChannelClient`
只在两个**测试类**里出现。而靠它的有四个：
`WechatPayGateway`、`AlipayPayGateway`、两家 `ApplymentGateway`。

它们都挂着 `@ConditionalOnProperty(shop.pay.*.enabled=true)`，
所以默认不装配、应用照常启动 —— **但把那个开关打开，启动就 NoSuchBean**。
「配了就能用」在这里是假的。

<b>这是唯一一处「不做则支付与进件都无法真正发生」的缺口。</b>

**② 下单链路根本没走网关。**

`OrderServiceImpl` 里通道写死 `"STUB"`，返回一组假的支付参数。
`PayGatewayRouter` 今天只被**对账回查**用到 —— 也就是说
「下单 → 向通道下单 → 拿到支付参数」这一段接线不存在。

**③ C 端收银台的参数没接上。**

`c-app/src/pages/pay/index.vue` 调的是真的 `uni.requestPayment`，
但传进去的是 `{}` —— 后端返回的 `prepayId` 一个都没带上。
页面在、接线没通。

> 三处的关系：② 依赖 ①（没有 client 就没有网关可路由），
> ③ 依赖 ②（没有真参数可传）。**顺序不能换。**

### 缺的 —— 多区域的三张表

| 表 | `currency` | `market_code` |
|---|---|---|
| `sys_pay_channel` | ✅ | ✅（`markets`） |
| `stl_bill` | ❌ | ❌ |
| `stl_settle_batch` | ❌ | ❌ |
| `mch_entity` | ❌ | ❌ |

还有两处 `enabledChannels(null)`（`MerchantPaymentServiceImpl` 第 100、376 行）——
**台湾商家和大陆商家今天看到同一份通道列表**。

## L3 · 三、多区域的市场清单要重新定

[多区域通道](./TDD-支付域-多区域通道.md) 按五个市场写的：
**中国大陆、中国台湾、阿联酋、沙特、东南亚**。

2026-09-01 追加的清单多出三个：**中国香港、美国、欧洲**。

这三个不是「再加三行种子」那么轻：

- **美国**：卡组织直连（Stripe / Adyen），
  资金流是「授权 → 请款 → 结算」三段，与国内的「支付即到账」不是一个模型。
  退款链路、拒付（chargeback）都要单独的状态机。
- **欧洲**：SEPA + 强客户认证（SCA / 3DS2）是**法规强制**，
  不是可选项；还要面对 GDPR 对报文留存的约束 —— 这与 V286 报文表直接相关。
- **中国香港**：相对轻，通道（支付宝 HK / 微信 HK / FPS）成熟。

**建议**：香港按现有模型直接加；**美国与欧洲单独立项**，
不要混进这一轮 —— 混进来会让「支付通道」这个抽象被迫同时表达
两种资金流模型，而那个抽象一旦拧了，先做好的那几个市场也要跟着改。

## L4 · 四、要先定的几条

1. **首发市场**：先把哪一个市场的链路走通？
   多区域那份建议 TW 或 SG（币种简单、法规轻）。
   而如果第一笔真钱要在**大陆**收，那 A 组的通道就是微信 + 支付宝。
2. **美国 / 欧洲是不是这一轮**：见 §三。建议不是。
3. **阿联酋**：标准商品库那边此前砍掉了阿联酋范围。
   支付通道这边保留 —— 确认一下是不是这个意思
   （没有商品就不会有订单，通道做了暂时用不上）。
4. **真通道凭证谁来拿**：商户证书与私钥**不经过我**。
   需要人在服务器上放，我只接线、不碰值。
5. **生产要不要走一笔真实订单**：A4 的最后一步。
   建议小额自购 + 当场原路退，比沙箱更能证明链路是通的。

## L4 · 五、顺序建议

```
现在就能开始（互不阻塞）：
  C1 → C2        既有欠账，越晚补回填越多
  D2             pay-svc 冒烟，一次性投入很小

拿到通道凭证之后（关键路径）：
  A1 → A2 → A3 → A4
       └→ B1 → B2 → B3

A 组走通之后：
  C3 → C4 → C5   多区域
  D1 / M11       拆分收尾
```

**不建议先做的**：在 A1 之前完善 A2/A3 的测试覆盖。
对着桩写出来的绿，在真通道接上那天要重写一遍 ——
而重写之前，没人知道它们绿的是什么。
