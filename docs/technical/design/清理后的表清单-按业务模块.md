## 3 库的定义与说明

| 库 | 定义 | 表数 |
|---|---|---:|
| 平台基础库 | 谁在平台上、能登录、能做什么。 | 39 |
| 平台服务库 | 平台替各业务做的事：通知、打印、发票、风控、地理与文件。 | 49 |

| 行业库 | 餐饮、美业各自特有的营业过程；商品和订单不在这里。 | 14 |

| 库存库 | 实物库存的唯一事实来源：有什么货、在哪、进出过多少。 | 25 |
| 支付库 | 收单：这一笔钱收到了没有、退了没有。 | 24 |
| 账务结算库 | 钱记在谁名下、该分给谁、什么时候给。 | 15 |
| 支付商户库 | 谁有资格收钱、用哪个渠道、在哪台终端。 | 19 |
| 报表库 | 每日经营数据：从各业务库汇总出来给人看的数字，不是业务的事实来源。 | 12 |
| 任务库 | 定时任务：有哪些任务、现在什么状态、每次跑的结果、处理到哪了。 | 4 |

| 和其他库的关系 | 各库原来各自的任务状态、游标、任务锁都收到这里。 |
| 现状 | 已有（正式库 ai_shop_ume_job_pilot）。 |

## 4 贯穿各库的约定

- **库里只存业务数据。** 事件收发、发号是公共能力，在基础能力库各一套；防重是功能能力，由应用层做，加业务表唯一键兜底，不建表。
- **字典、事件、轻量审批各用一个统一的模型。** 都在基础能力库：字典一张、事件一套、轻量审批一张。
- **重的审核与工单不在这些库里。** 入驻审核、客服工单、门店待办、内容审核由独立的审核与工单服务承担，业务表只存单号。
- **App 不在这里管。** App 的版本与功能目录由单独的 App 项目管理。
- **合并要有业务理由。** 同一对象的多套、旧一代、同构的重复才合并；一对多的明细保留为表。
- **一个业务对象只有一个归属库。** 其他库只存它的编号和必要的快照。
- **库之间不联表、不共事务。** 跨库协作走接口或公共事件，要有重试、对账与补偿。
- **三端的认证各一套，B 端与运营端的角色权限各一套。**
- **订单保留两层。** 支付单是一次付款，商家订单是各商家各自的履约与售后。
