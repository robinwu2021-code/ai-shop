## 一、一句话

把「谁是谁」「钱先进谁的账户」「谁是销售主体」**三个被混作一谈的轴拆开**，
然后把散落在这三个轴上的判断逐一改判到正确的那根轴上 ——
**积分能否开启、要不要补差、售后派给谁、能不能开票、价格字段叫什么、评分算谁的**，
此前有五处判在错的轴上或根本没接。

---

## 二、为什么这些改动是必要的

不是重构，是**六处正在发生的错**。共同形状：**不报错**。

| # | 症状 | 真实原因 |
|---|---|---|
| 1 | 无照农户被拒绝开积分 | 判据用了主体类型，且读的是**通道进件档**（微信小微档）而不是法律形态 |
| 2 | 归集路径的单子在跑补差 | 「要不要补差」判在 `business_mode` 上，而它该判 `funds_mode` |
| 3 | 自营售后先派给「商家」，而那个商家就是平台 | 一条本该一步的路走了两段，中间那段是平台审自己 |
| 4 | 无照自然人显示「本商家无法开具发票」 | 判的是商家自己开不开得出票，而归集下**开票的是平台**。这句话还把销售方指给了商家 —— 归集资金模式因此不成立 |
| 5 | 用户看得见分在涨，一分也花不出去 | 发放时不写 `available_at`，转正任务不存在 → `balance` 恒 0 |
| 6 | 积分池只出不进 | 发分费用金**从来没被收过**：两张表的 `points_fee_minor` 全库零写入，`MERCHANT_RECEIVE` 只在测试里被调过 |

第 6 条最危险：它和本轮新加的出账（用户花分时付给收单方）是**同一个恒等式的两端**。
只补出账不补入账，`FEATURES.points` 一开池子立刻变负。

## 三、改了什么

### 3.1 数据结构（迁移 V78–V94，其中 V83/V85/V88/V89 让给并行会话）

| 迁移 | 内容 |
|---|---|
| V78 / V80 / V86 | ops 三个新页面的功能点（无照自营风险 / 资质档案 / 积分资金看板） |
| V79 | `mch_entity_apply.qualification_items` —— 接通资质链路 |
| V81 | **`mch_entity.funds_mode`**（轴②）+ `stl_bill.funds_mode` + `points_cost_minor` + `is_agri_producer` |
| V82 | `pts_user_ledger.activated_at` —— 转正的幂等键 |
| V84 | 申诉状态补 `REJECTED` |
| V87 | `MICRO` → `NATURAL_PERSON` + `biz_qualification` + `exempt_type` |
| V91 | `shedlock` 锁表 |
| V93 | 微信 `subject_type` 映射修正 + `PERSONAL_OPENID` → `PERSONAL_BANK_CARD` |
| V94 | `ord_invoice_request` —— 开票申请 |

### 3.2 三个轴（本轮的核心）

| 轴 | 字段 | 回答什么 |
|---|---|---|
| ① 商户类型 | `mch_entity.legal_form` | 他是谁 |
| ② **资金路径** | `mch_entity.funds_mode` | **钱先进谁的账户** ← 本轮新建 |
| ③ 经营模式 | `mch_store.business_mode` | 谁是销售主体 |

**本轮所有「改判到正确的轴」，判的都是轴②** —— 责任跟着钱走。

### 3.3 改判的六处

| 判断 | 此前 | 现在 |
|---|---|---|
| 积分能否开 | 主体类型 + 读错字段 | 无照 **且** 直连才拒 |
| 要不要补差 | `business_mode` | `funds_mode` |
| 售后派给谁 | 一律先派商家 | 归集直接进平台仲裁 |
| 能不能开票 | 商家自己的能力 | 归集下平台开，与商家执照无关 |
| 价格字段叫什么 | 一律「售价」 | 归集下「期望收购价」 |
| 评分算谁的 | 全算商家 | 归集下服务/时效标为平台承担（**标注，不隐藏**） |

### 3.4 补上从未执行过的链路

| 链路 | 补了什么 |
|---|---|
| 积分转正 | `available_at` 写入 + `PointsActivateJob`（每日 00:05） |
| 积分到期 | `expireIdleAccounts` + `EXPIRE_INCOME` 入账（00:20） |
| 积分兑付 | `confirmDeduction` → `CONFIRMED` + `MERCHANT_PAY` 出池。**两个入口**：直连在分账后、归集在 `markPaid`（自营不走分账） |
| **积分收费** | `GrantResult.feeMinor` → 子单 → 账单扣减 → `MERCHANT_RECEIVE` 入池 |
| 资质转存 | 入驻通过时把申请单的资质写进 `mch_qualification`（此前该表**实测 0 行**） |
| 开票 | `ord_invoice_request` + C 端 3 端点 / ops 3 端点 + 订单页入口 |
| 定时任务锁 | 四个 `@Scheduled` 全挂 ShedLock |

### 3.5 通道映射修正（对着微信官方文档核过）

| 位置 | 原值 | 实际 |
|---|---|---|
| `INDIVIDUAL.wechat_code` | `'SMALL'` | **取值域里没有这个值** → `'INDIVIDUAL'` |
| `settle_account_type` | `'PERSONAL_OPENID'` | **微信不结算到 openid**，是个人银行卡 → `'PERSONAL_BANK_CARD'` |
| 进件接口 | 当成一个接口 | **小微走独立接口**（特约商户进件不收小微），暂记 `remark`，C1 联调时提升为字段 |

B 端入驻页的「微信零钱（个人）」已改为「本人银行卡」——
商家据此以为不用提供银行卡，而进件时那三个字段是必填的。

## 六、评审时值得多看两眼的地方

1. **`funds_mode` 的默认值。** V81 用了默认值，而 V23 那次「存量默认最严」
   把 54 张第三方单永久卡死。这次能用默认值**只因为默认值恰好等于事实**
   （全库都是平台收款），迁移注释里写明了这个区别 —— 不是「加列都可以这么写」。

2. **`fundsModeOf()` 查不到时默认归集。** 那个默认在补差轴上安全（宁可不补，
   不能重复付款），**在开票轴上不安全**（查不到主体 ≠ 平台是销售主体）。
   开票那处因此直接读实体，没复用这个 helper。
   → 复用 helper 时要问的不是「它对不对」，是**「它的默认值朝哪个方向兜底」**。

3. **积分恒等式的两端要一起看。** `confirmDeduction`（出）与
   `GrantResult.feeMinor`（入）必须同时存在，只做一半池子会变负。

4. **开票是手工版。** 条件 2 要的是「承担义务并实际履行」，不要求自动化。
   单量扛不住那天就是该接票据系统的信号 —— 状态机在 `ISSUED` 之后延长，
   不改前面的。
