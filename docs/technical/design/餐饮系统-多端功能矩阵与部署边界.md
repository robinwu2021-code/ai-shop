## 一、定位与设计选择

餐饮系统独立拥有菜单选配、就餐台账、点餐批次、制作上菜、退餐编排等业务；复用现有商品、交易、支付、库存和售后权威能力。所有终端调用同一业务服务，独立部署与集成部署采用同一业务语义。

选择独立项目和适配器边界，便于独立发布、部署及门店能力扩展。复制完整商品与交易系统会形成两套价格、资金和库存来源；直接把餐饮业务全部加入 core 会增加零售流程对餐饮的依赖。独立部署默认仍在线调用共享底座，断网营业另需门店边缘运行模式。

## 二、终端与结构

![餐饮项目两种部署方式](../diagrams/food-deployment-boundary.svg)

本地与远程适配器是部署差异，业务层、鉴权规则和幂等语义保持一致。即使集成部署，也通过明确服务接口访问基础能力，不直接写核心表；跨模块流程按真实事务边界恢复，不把远程流程假定为单库事务。

| 终端 | 使用人及范围 | 定位 |
|---|---|---|
| 收银端 Cashier/POS | 门店收银员、值班经理 | 点餐、结账、现金登记、当班与设备处理 |
| 服务员端 Waiter | 门店服务人员 | 开台、代客点餐、桌台服务、上菜 |
| 厨房端 KDS | 厨师、传菜、工位负责人 | 接单、制作、出品、异常协作 |
| 商家运营端 Merchant Ops | 商家/连锁总部/门店运营，Web | 菜品餐牌、门店规则、设备、权限、经营管理 |
| 老板端 Owner | 现有 B 端 App 的授权经营者 | 移动看经营、异常审批和门店管理；复用现有身份体系 |
| 平台运营端 Platform Ops | 平台运营、客服、实施运维 | 商家开通、能力治理、排障与审计 |
| 顾客端 Customer | 扫码/H5/小程序顾客 | 自助点餐、支付、进度和服务申请 |
| 点餐机 Kiosk | 顾客使用的门店设备 | 设备身份下的自助点餐、支付与取餐 |

“运营系统”在此明确为商家运营；平台运营单独授权。角色范围不是页面是否显示，而是后端校验的商家、门店、工位、操作及金额权限。

## 五、独立 Java 项目与两种部署形态

项目沿用ADR-019的同仓 `backend-plugins/`、独立Maven reactor及版本目标，不加入主干reactor；独立迁移历史与可剔除零售回归保留，不做运行时热插拔。共享底座契约与 `food-api` 的餐饮契约明确区分，避免重复定义通用接口。部署级校验契约兼容，门店级按启用能力校验依赖。

模块以[代码结构与对象清单](./餐饮系统-代码结构与对象清单.md)为准，采用core零售相同的api/dto/service/service.impl/entity/mapper包，不再沿用早期七模块分层。

| 项目模块 | 职责 | 部署边界 |
|---|---|---|
| `food-api` | 最小餐饮契约，优先复用已有SPI | 不包含框架及核心实体 |
| `food-core` | Controller、Service/Impl、Entity、Mapper及必要策略和配置 | 嵌入宿主或由独立server引用，同一业务实现 |
| `food-channel` | 远程核心协议与外部通道适配 | 不包含营业规则及财务判断 |
| `food-server` | 独立启动和远程适配装配 | 独立部署时使用 |

集成形态：宿主应用引用food-core，宿主bridge实现本地Port；餐饮不反向依赖shop-core实现。这里“集成到core”指随承载core的应用部署，不把餐饮表和规则塞入零售模块。

独立形态：food-server引用food-core与food-channel，装配远程Port。认证与公共响应复用现有体系；远程代办、报价、履约、收退款等缺失合同先补齐，不能假定全部已有。餐饮可独立数据库。

同一商家/门店在任一时刻只使用一套餐饮业务写入实例集合和数据归属；不能让独立服务与宿主各自处理相同事件、生成两份派工。切换形态需迁移路由、数据归属、消费位置及在途任务。共享打印以通用打印契约接入，可随应用部署或独立运行。

| P2 堂食后付与桌台协作 | 后付、加菜、转台/拼桌、包间预约转开台、未结巡检、结账冻结、退餐编排 | 后付库存承诺、取消守卫、先交付后付款语义；可先逐单收款，明确不等于一次整桌收款 |
| P3 完整收银与复杂选配 | 跨单结账、混合支付、AA、按菜拆账、部分退餐退款、称重补差、渠道价格/服务费用、套餐配料计价 | 核心收银资金分配、行级金额分摊/应收调整/退款、报价与库存展开；交接班现金账纳入同一资金口径 |
| P4 外部与断网 | 第三方适配、门店边缘、断网现金营业与恢复 | 外部权威归属、边缘单写者/租约、编号认领、库存额度、未知支付恢复及事件去重 |

阶段表示依赖顺序，不取消已确认的第三方和断网目标。真实营业收款、核心库存、菜品销量沿统一权威链路；点餐份数、出品份数、损耗是独立经营指标，避免打印重试或同步重放重复记账。

## 七、取舍与后续设计入口

1. 商家运营负责配置、老板App负责移动经营与审批，两个终端共用服务；避免每端各写一套规则。
2. 先保留完整目标矩阵，逐项标能力开关与核心前置条件；不因有页面或表就宣称收银能力已支持。
3. 当前菜品方案中的口味字典需收敛为复用已有规格/属性值字典；收费配料关联SKU，餐饮仅新增选择规则与快照，后续修订ER时统一。
4. 前轮19张营业流程表是基础清单。本矩阵新增的正式交接班、盘点、审批等范围，需在详细数据设计中核对既有公共能力后决定是否增加业务表，不能以19张作为完整目标的硬上限。
5. 下一步依次形成：领域边界与核心端口契约 → 台账/制作/结账/退餐状态机 → 表设计和并发规则 → 各端API及权限清单 → 双部署装配与恢复方案。进入代码实施前完成这些设计的评审。

默认产品范围：单门店内拼桌与结账，连锁可统一配置但不跨门店合账；商家运营优先复用现有商家Web入口。包间预约纳入P2；排队、配送平台运营、原料采购与完整财务总账另列专题。匿名顾客主体、第三方首家协议及离线支付范围将在契约设计中具体确定。
