## #1 改划线价/限购「发布后不生效」—— 根因与修复

### 逻辑现状（已端到端追证）
划线价（`prd_sku.origin_price`）与每人限购（`prd_goods.limit_per_user`）**四层接线都对**：
前端发（`index.vue:1397/1456`）→ 后端收（`SaveCommand.limitPerUser`、`Sku.originPrice`）
→ 落实体（`applyOptional:1421`、`saveSkus:1607`，`origin_price` 挂 `@TableField(updateStrategy=ALWAYS)` 专门绕开 updateById 跳 null）
→ 发布重放（`swapFromDraft` 反序列化 payload 重跑 save，**全字段原子重放**）→ C 端读线上行（`GoodsServiceImpl.detail`）。
**不存在字段级丢失。** 所以「发布后不生效」有两个真实嫌疑：

- **嫌疑 A（最可能）：双版本流程被截断。** 在售商品 `/save` 只写 `prd_goods_draft.payload`，**线上一字节不动**；改动要到商家**显式发布**（差异页 → `publishDraft`）才生效。商家只点了「保存」没走发布 → 买家必然看到旧值。这与 #2 同根。
- **嫌疑 B（唯一能藏静默不对称处）：草稿 payload 的 Jackson 版本不一致。** 序列化用注入的 Jackson 3（`json` bean），反序列化却 `new` 了一只临时 Jackson 2（`:1166/1215/1324`）。探子用默认 mapper 实测两字段 round-trip 完好，但**生产那只被 Spring 配过的 Jackson 3** 若带了非默认命名/包含策略，这里是唯一可能静默读不回某些字段的地方。

### 修复方案（先验证，再动手）
1. **先坐实（impl 第一步，不在方案阶段跑）**：取一条「改了但没生效」的在售商品，直接查它 `prd_goods_draft.payload` 的 JSON——
   - payload 里**没有** `limitPerUser`/`skus[].originPrice` → 问题在序列化或前端实际请求体，往前移；
   - **有**、而线上行没更新 → 发布重放缺陷（多半是嫌疑 B）。
2. **统一草稿 mapper**：把 `:1166/1215/1324` 三处临时 `new ObjectMapper()` 换成注入的 `json`（Jackson 3）做反序列化——消灭唯一的版本不对称，无论 B 成不成立都该做。档 1（不改契约，改装配）。
3. **流程兜底**：嫌疑 A 由 #2 根治（让商家不会以为「保存=生效」）。

> 判据：修完要能**消融**——撤掉统一 mapper，用生产 Jackson 3 配置重放一条带这两字段的 payload，若此前确有不对称，字段应变回丢失。

## #2 发布流程提示 —— 让「草稿≠生效」看得见

### 现状
在售商品保存 = 落草稿；反馈是一条 **1.2 秒 toast「已保存为草稿」** 然后**自动返回**；发布入口藏在**列表徽标 + 差异页**。商家改完以为生效了。

### 交互方案
1. **保存后不自动返回、不用一闪而过的 toast**，改为一张**常驻结果层**（`sh-sheet`）：
   - 标题：「已保存为草稿 · 线上仍是旧版」
   - 主按钮（醒目主色）：**「立即发布」** → 直接调 `publishDraft`，就地完成，不用去列表找徽标
   - 次按钮：「稍后发布」→ 返回，列表徽标照旧
   - 发布成功后换成明确成功态：「已发布 · 买家现在看到的是新版」，要手动关，不一闪而过
2. **编辑页常驻状态条**：当存在未发布草稿时，页顶固定一条「有未发布改动」+ 「查看差异 / 发布」，离开页面也带着，消除「改了就走、忘了发」。
3. 文案守 `b-app-copy-no-jargon`：不用「双版本」「快照」这类黑话，只说「线上旧版 / 待发布的新版」。

档 0/1（B 端 UI + 复用既有 `publishDraft`，不改契约）。

## #3 限购地区：持久化 + 展示 + 反选

### 现状缺口
- 识别出的 `excludeRegionText` **只跳转、不落库、不展示**（TDD-商品快速录入 AC9/AC13 明确「只回文本」）。
- 「限购地区」唯一落库点是**运费模板 `out_of_range`**（省份全名、仅快递、**整店**；默认模板已有西藏 REJECT / 新疆 SURCHARGE）。
- **没有「某商品不卖到某省」的字段。**

### 设计决策（需你拍板，见末尾）
推荐 **商品级「限购地区」= 排除式（反选）**，省级粒度：

- **逻辑**：`prd_goods` 加一列 `restricted_regions`（JSON，省级 `regionCode` 数组，如 `["65","54"]`）。语义固定为**排除**：默认「全国可售」，列表里的省**不可售**。为什么用码不用省名：运费模板那套用省名 `startsWith` 是老债，新字段直接对 `sys_region.region_code`（省级两位码）对齐，下单时按收货地址解析出的 regionCode 前两位匹配，稳过字符串前缀。
- **与运费模板的关系**：两者并存、语义分层——运费模板管「整店快递的运费/拒单」，商品级 `restricted_regions` 管「这件货不卖到哪」。下单拦截**两道都过，任一命中即拒**（见 #4 合一的拦截点）。
- **展示（C 端商品页）**：详情页加一行「不发货地区：新疆、西藏」（regionCode → 省名，走 `sys_region`）。空则不显示那一行。
- **录入（B 端）交互 —— 反选器**：
  - 默认态：「销售范围：全国」
  - 一个「排除地区」入口 → 省级多选（复用 `sys_region` PROVINCE 列表，34 个省级），勾中的进 `restricted_regions`
  - 回显成 chip：`全国，排除：[新疆 ×][西藏 ×]`
  - **识别联动（接 #4/#5）**：文字识别出的 `excludeRegionText`（如「不发西藏新疆」）→ 规则映射到省级 regionCode → 进确认层（#5），确认后**落 `restricted_regions`**，而不再只跳转。这就补上了「文字里有、商品页没有」。

档 2（新列 + 迁移 + 对外 JSON + C 端展示 + 下单拦截，跨端 + 不可逆存储决策）。

## #4 销售地区 ↔ 定位可见 ↔ 收货地址拦截：收敛到一套

### 现状的两处分叉（探子实证）
1. **可见 vs 框选分叉**：`reachableCommunities` 里**快递（EXPRESS）分支把可见性拉成全部开放社区**，旁路掉 `mch_service_area` 的 INCLUDE 框选（只剩 EXCLUDE 生效）。于是「框了龙华，却全市可见」。
2. **可见 vs 下单拦截两套逻辑**：可见走「定位→社区→`prd_community_pool`」；下单拦截走「收货地址省名→运费模板 REJECT」，**只拦快递**，自提/自送不过；且判的是**买家绑定社区**不是**本单收货地址**。

### 逻辑方案：一个「有效销售范围」，两处共用
定义单一事实源 **effectiveScope(merchant/store, 商品)** = `mch_service_area` 的 INCLUDE 并集 − EXCLUDE − 商品级 `restricted_regions`（#3）。两处都查它：

- **（a）定位匹配可见**：买家定位 → regionCode + communityNo → 命中 effectiveScope 才可见。
  **修分叉 1**：EXPRESS 不再无条件开放全部社区——**商家框了范围就尊重框选**（INCLUDE 生效），没框才回落「全国可售」。即「履约可达（能不能快递到）」与「销售范围（卖不卖给你）」解耦：快递只决定**怎么送**，不决定**卖不卖**。
  > ⚠️ 这条动的是 `reachableCommunities`（记忆「销售区域与可见性分叉」+「我曾把方向说反」），**必须**先列出所有读 `reachableCommunities` 的调用点、逐个消融，灰度（先一家店）验证。最高风险项。
- **（b）收货地址拦截（限单）**：下单时解析**本单收货地址** → regionCode → 对同一 effectiveScope 校验；不在范围 → 统一错误码（复用或新增，区别于运费模板的 20003）。**对所有履约类型生效**（自提按门店所在、自送按半径+范围、快递按地址），不再只拦快递。
  - 商品级 `restricted_regions` 命中（收货省在排除表）→ 拒，文案「该商品不发往{省}」。

### 交互方案
- **C 端**：定位在范围外 → 商品/门店不出现在列表（现状已是池机制，修完分叉后框选才真生效）；进了详情但切了收货地址到范围外 → 下单按钮置灰 + 「该地址不在销售范围」。
- **B 端**：销售范围编辑页（已存在 `biz-region-picker`）继续管 INCLUDE/EXCLUDE；商品级限购地区在 #3 的反选器。

档 2（改可见性核心 + 下单拦截 + 跨端）。**分两步上**（记忆「拆域先延后再隔离」）：先上**收货地址拦截（b，纯新增闸，低风险）**，再灰度**修可见性分叉（a，高风险）**。

## #5(a) 识别结果确认层（接管 AC11）

### 现状
快速录入那条线刚落地「边输边识别·持续自动填」——识别到就直接改属性，没有逐项确认。

### 交互方案（与那条线协调，叠加而非推翻）
- 识别（图片 LLM / 文字规则）产出候选后，**不直接自动落**，改为进一张**确认层**（`sh-sheet`）：
  - 每项一行：维度名 + 识别值 + **勾选框**，默认按置信度勾/不勾（价格类低置信默认不勾，守现有 AC8）
  - 顶部「全选 / 全不选」；底部「确认所选」→ 只 `applyParamPicks` 勾中的（**批量**）
  - 单项也可点一下即填（**逐个**）
  - 地区类（限购地区）识别项在这里确认后落 #3 的 `restricted_regions`；经营范围仍只跳转（守 AC9）
- **与「边输边识别」的关系**：边输边识别保留为**产出候选**，但候选进确认层待勾，不再静默改写商家已填。这点要与快速录入那条线对齐口径（避免两种相反交互打架）。

档 1（B 端交互 + 复用 applyParamPicks；若地区落库则连 #3 的契约）。

## 需你拍板的决策点

1. **#3 限购地区放商品级还是沿用整店运费模板？** 我推荐**商品级新字段 `restricted_regions`（省级排除）**（因为你要的是「商品页展示 + 识别落到这件货」）。确认走商品级我就按档 2 设计迁移。
2. **#3 粒度**：省级够不够，还是要到市/区？（省级最简，覆盖「新疆/西藏」这类；到区县要接 `sys_region` 下钻。）
3. **#4 要不要动可见性分叉（a）？** 它是最高风险项（改 `reachableCommunities`）。可以**只先做收货地址拦截（b）**，把（a）单独排期灰度。你定是「b 先行」还是「a+b 一起」。
4. **优先级/顺序**：#1+#2 是止血（商家现在就困惑），建议最先；#3/#4 是新能力、档 2，随后。#5(a) 依赖快速录入那条线协调窗口。
