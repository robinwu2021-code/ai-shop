# 营销域 · 活动统一模型

> 状态：**草稿 · 待确认** · 2026-09-18
> 起因：店主「期望用一个逻辑抽象出各种活动，如何进行设计」
> 这一份**不看现有代码**，只从业务上回答「一个活动由什么组成、怎么覆盖所有玩法」。
> 落到代码怎么改，另起一份 TDD；概念与用词以 [营销域-概念对齐](./营销域-概念对齐.md) 为准。
> 相关：[TDD-活动的逻辑重排](./TDD-活动的逻辑重排.md)、[TDD-团购从商品挪进活动](./TDD-团购从商品挪进活动.md)

## 一、一句话

**活动 = 头 + 条件 + 利益 + 约束（+ 实例）。类型不是枚举，是组合的名字。**

满减、特价、拼团、秒杀、发券……都是这五块的不同填法。
**加一种新玩法 = 加一种条件或一种利益，不是加一个类型。**

```
活动
├── 头       名称、目的、发起方、出资方、状态、时间
├── 条件     什么情况下算命中（列表，全部满足才算）
├── 利益     命中后给什么（列表，按顺序生效）
├── 约束     最多给多少、和谁能叠加
└── 实例     有状态的玩法才有：一个团、一次砍价、一笔定金
```

---

## 二、五块各是什么

### 2.1 头 —— 所有活动都一样

| 字段 | 说明 |
|---|---|
| 名称、说明 | 展示用 |
| 目的 | 拉新 / 唤回 / 提客单 / 清库存。**只影响新建时的默认值和复盘看什么指标**，不参与算价 |
| 发起方 | 平台发起（商家报名）还是商家自建 |
| 出资方 | 让利由商家、平台、供应商谁出，按什么比例。直接决定结算 |
| 时间 | 见 2.1.1 |
| 状态 | 草稿 → 待审 → 预热 → 进行中 ⇄ 暂停 → 结束。结束要记原因：到期 / 份数用完 / 预算用完 / 手动停 |

#### 2.1.1 时间不是一个字段，至少四段

| 段 | 含义 | 谁用得到 |
|---|---|---|
| 展示期 | 看得到但还不能买（预热） | 秒杀、预售 |
| 参与期 | 可以下单 / 参团 | 所有 |
| 兑现期 | 成团截止、尾款截止 | 拼团、集单、预售 |
| 使用期 | 送出的券、积分什么时候能用 | 送券、送积分 |

每一段都可以是**一次性**（有起有止）或**周期性**（每周三、每天 18–20 点）。
满减只用参与期；预售四段全要。

### 2.2 条件 —— 列表，全部满足才命中

每条条件 = **类型 + 参数**。列表为空 = 无条件（「进店即送券」）。

| 条件类型 | 参数 | 用在 |
|---|---|---|
| 商品范围 | 全店 / 类目 / 指定商品 / 排除清单 | 几乎所有 |
| 金额门槛 | 满 X 元 | 满减、满折 |
| 件数门槛 | 满 N 件、第 N 件 | 满赠、第二件半价 |
| 人群 | 新客 / 会员等级 / 标签 / 社区 / 自提点 | 定向 |
| 首单 | 是否首次购买 | 拉新 |
| 成团 | 人数 ≥ N，或截单时间到 | 拼团、社区集单 |
| 名额 | 前 N 名 | 秒杀 |
| 动作 | 分享 / 邀请 / 签到 / 付定金 | 裂变、预售 |

### 2.3 利益 —— 列表，可多条

| 利益类型 | 参数 |
|---|---|
| 减金额 | 减 X 元 |
| 打折 | 打 X 折，可设封顶 |
| 改单价 | 改成 X 元 |
| 阶梯 | 满 100 减 10、满 200 减 30（同一条利益内的多档） |
| 送商品 | 商品 + 数量 |
| 送券 | 券模板 + 张数 |
| 送积分 | 积分数 |
| 免运费 | — |
| 给资格 | 优先购、专属价 |

「折扣 / 现金」就是「打折」与「减金额」两种利益并列，**不需要在活动上分「折扣型」「现金型」**。

### 2.4 约束 —— 最多给多少

| 字段 | 说明 |
|---|---|
| 总量 / 预算 | **至少一个**。长期活动强制：没有结束时间又没上限就是永久敞口 |
| 每人限次、每单限件 | |
| 叠加组 | 同组内互斥取最优，不同组可叠加 |
| 优先级 | 同组冲突时谁赢 |

### 2.5 实例 —— 只有跨单、跨人的玩法才有

拼团的「一个团」、砍价的「一次砍价」、预售的「一笔定金」、签到的「一张卡」。
实例记的是**某一次参与进行到哪一步**，有自己的生命周期（开始 → 进行中 → 达成或失败）。

> **活动结束了，已经开出去的团还在。** 这是把规则和实例分开的根本原因。
> 混在一起，商家停掉活动会以为团也散了（它们不会）。

单单即时型（满减、特价）没有实例，规则直接算价。

## 三、按机制分：决定一个玩法做起来简不简单

| 机制 | 特点 | 玩法 | 要不要实例 |
|---|---|---|---|
| **A. 单单即时** | 只看当前这一单 | 满减、满折、特价、第 N 件折扣、组合价、满赠 | 不要 |
| **B. 领取** | 先领后用，领和用隔开时间 | 优惠券、兑换码 | 用户券即实例 |
| **C. 集体达成** | 要多个人凑够条件 | 拼团（按人数）、社区集单（按截单时间或件数） | **要** |
| **D. 个人累积** | 跨多单、多天累计 | 签到、累计消费返、集点卡 | **要** |
| **E. 资格竞争** | 名额有限，先到先得或抽 | 秒杀、预售、抽奖 | 秒杀不要，预售要 |
| **F. 裂变** | 靠别人的行动达成 | 邀请有礼、助力、砍价 | **要** |

**机制 × 条件 × 利益 = 玩法。** 同样是集体达成，可以成团后打折，也可以成团后送赠品。

## 四、用这个模型表达各种玩法

| 玩法 | 条件 | 利益 | 实例 |
|---|---|---|---|
| 满 100 减 10 | 金额 ≥ 100 | 减 10 | 无 |
| 限时 8 折 | 商品范围 = 指定商品 | 打 8 折 | 无 |
| 第二件半价 | 件数：第 2 件 | 打 5 折 | 无 |
| 满 3 件送 1 件 | 件数 ≥ 3 | 送商品 ×1 | 无 |
| 新客立减 | 首单 | 减 5 | 无 |
| 拼团 | 商品范围 + 成团人数 ≥ 3 | 改单价 | **团** |
| 社区集单 | 商品范围 + 截单时间到 | 改单价 | **单次集单** |
| 秒杀 | 商品范围 + 名额前 100 | 改单价 | 无（名额是约束） |
| 预售 | 商品范围 + 付定金 | 定金抵扣 / 减金额 | **一笔定金** |
| 邀请有礼 | 动作 = 邀请成功 | 送券 | **一次邀请** |
| 进店送券 | （空） | 送券 | 无 |
| 会员日 | 人群 = 会员 + 参与期周期性 | 打折 | 无 |

同一套字段，全部填得进去。

## 五、算价：所有活动走同一条路

```
1. 取候选：按时间、状态、商家筛出进行中的活动
2. 过条件：每条条件算一遍，全过才命中
3. 分组取优：同一叠加组内取对用户最优的一个
4. 按序生效：跨组按优先级依次作用在金额上
5. 再算券：券作用在活动之后的金额上
6. 落记录：每一次真的减了钱，记一行（活动号、订单号、金额）
```

有实例的玩法在第 2 步多一件事：「成团」「付定金」这类条件要去查**实例的状态**，
而不是只看当前这一单。

## 六、界面：组合不暴露给商家

模型是组合式的，但商家看到的是「选一个玩法」。每个玩法是一个**模板**：
预填了条件与利益的类型，商家只填参数。

```
模板「满减」 = 条件 [金额门槛] + 利益 [减金额]
      → 商家只填：满多少、减多少、哪些货、什么时候
```

模板是**配置**不是代码：新玩法 = 新模板，不改算价。
平台或高级用户可以直接组合条件与利益，普通商家只看模板。

---

## 七、三条不能省的边界

1. **券不是活动的一种，是活动的一种利益。** 「发券」活动的利益是「送券」；券自己有模板与用户持有记录。
2. **规则 / 实例 / 记录三层分开。** 活动只存规则；团、定金在实例；每次减钱在记录。混在一起对不了账。
3. **平台活动多一段流程。** 商家报名、审核、提报商品。规则模型共用，流程单独。

## 八、待确认

1. **条件之间只有 AND，还是也要 OR？** 建议只有 AND；「满 100 或满 3 件」用两个活动表达，不进模型。
2. **叠加规则要多细？** 建议先做「所有活动互斥取最优，再叠券」，模型里预留叠加组字段。
3. **「团购」在本业务里指哪一种？** 拼团（凑够几个人）还是社区集单（到截单时间）。
   在「社区 + 自提点」形态下后者可能才是核心，它对时间与履约的要求远高于人数。
4. 与 [营销域-概念对齐](./营销域-概念对齐.md) 的关系：那份定义词，这份定义结构。
   这份的「条件 × 利益」对应那份的「触发 × 优惠」，**要不要统一成一个词**。
