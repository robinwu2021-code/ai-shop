## 一、异常单是**视图**，不是表

这一条是这批里最要紧的设计决定：

```ts
// contracts/order.ts
listExceptionOrders(q?): Promise<Page<OrderException>>
```

`OrderException` 由 `orders` 实时算出来，**不落库**。落库的异常记录会过期 ——
订单已经推进了，记录还挂在队列里，运营点进去处理一个不存在的问题。
所以这个队列里也没有"标记已处理"按钮：处置完它自己就消失了。
`order.test.ts` 第一条用例锁的就是这个行为。

阈值按状态分别给（`STUCK_MINUTES`），不给一个统一值：

| 状态 | 时限 | 理由 |
| --- | --- | --- |
| 待支付 | 15 分钟 | 与关单策略默认值对齐，超了说明关单任务没跑 |
| 已支付 | 30 分钟 | 商家该接单了 |
| 备货中 | 120 分钟 | |
| 配送中 | 240 分钟 | |
| 已送达待自提 | 1440 分钟 | 放一天很正常，一刀切会把它刷成异常 |
| 售后中 | 2880 分钟 | |

终态不设时限。一刀切的后果不是"误报几条"，而是队列变噪音之后没人再看它。

待支付超时单独归成 `PAY_TIMEOUT` 而不是 `STUCK`：它指向的是关单任务本身出了问题，
处置方式和"卡在配送中"完全不同。

### mock 数据的时间基准

`statusAt` 用「相对现在」生成（`Date.now() - N 分钟`）而不是写死时间戳 ——
写死的话过一天所有非终态订单都会超时，异常队列退化成订单列表。
`createdAt`/`paidAt` 仍是固定的业务数据。

## 二、人工干预也走状态机

`interveneOrder` 用的是同一张 `ORDER_TRANSITIONS`，抽屉里的下拉**只列合法的下一步** ——
把非法选项摆出来再报错，是在骗运营点一次。原因必填，`orderInterventions` 记 from/to/操作人/时间。

## 三、代客下单不代付款

| 规则 | 不这么做会怎样 |
| --- | --- |
| 落到 `PENDING_PAY`，不是已支付 | 代付款等于平台替用户付了钱，账对不上 |
| 一次只能下一个商家的货 | 全站按商家拆单（E3），混着下会拆出对不上的单 |
| 只能选 `ON_SALE` 的商品 | 下架/驳回的照样卖出去就是事故 |
| 库存不足直接拒绝 | 超卖 |
| **校验全部通过后才扣库存** | 中途抛错会留下扣了一半的库存 |
| 代下原因必填 | 它绕过了用户自主下单 |

代客取消同理：原因必填，走状态机（已完成的单只能走售后），
已支付的取消**必然原路退款** —— 契约里就没有"取消但不退款"这条路。

## 四、页面拆分与守卫

订单页加两块后会到 600 行（其余 17 个页面都在 400 行以内），所以拆成
`exception-tab.tsx` / `proxy-tab.tsx`，只通过 `OrdersCopy` 与 page.tsx 相连。

拆之前先补了守卫：`lib/page-copy.test.ts` 原来只扫 `page.tsx`，
拆文件等于给裸中文开了后门 —— 现在扫**页面目录下的每个 .tsx**。
`layout.tsx` 例外并写明了理由：`<head>` 的 metadata 在服务端渲染前就要定，拿不到客户端语言态。
