## 1. 为什么是这两个

- **P-6 售后治理**：矩阵 §七 的六条必闭合链路里，「售后赔付」是**唯一三端整条全缺**的。C 端申请、B 端处置、平台裁决三段缺任何一段，用户的坏果就没人赔。
- **P-8 团购与求团**：C 端已实现（矩阵 §四 8.1/8.2 标 ✅），**B/P 两端全缺** —— 用户能发起求团但没人能指派商家报价，功能是断的。

## 2. 方案

### 2.1 页面

| 页面 | tab | 覆盖 |
|---|---|---|
| `/after-sales` | 售后工单 · 平台介入 · 极速退规则 | P-6.1.1 / 6.1.3 / 6.1.4 / 6.1.2 |
| `/groups` | 商家团 · 求团需求 · 报价与信用 | P-8.1 / P-8.2 |

**责任判定（P-6.1.4）不单独成页**：它是裁决动作的一部分 —— 判了责任才谈得上赔付归属，
拆成两页会出现「裁决完了忘了判责」的空档。

### 2.2 数据模型要点

**aftersale.ts**
- `AfterSale`：类型（仅退款/退货退款/换货）、状态机 `APPLIED → MERCHANT_HANDLING → (AGREED|REJECTED|PLATFORM_INTERVENE) → REFUNDED|CLOSED`
- **责任与赔付归属**（P-6.1.4，矩阵 M4 待定）：`liability` 三选一（平台/供货商家/自提点商家）+ `share` 三方比例
  —— 口径未定，所以**存结构不存结论**：等 M4 定了只改默认值不改模型
- `FastRefundRule`（P-6.1.2）：金额上限 / 时限 / 适用品类 / 开关

**group.ts**
- `GroupCampaign` 商家团：起团人数、团购价、已参团、状态（待审/进行中/已成团/未成团）
- `DemandOrder` 求团需求：发起人、+1 人数、社区、状态（征集中/报价中/已选定/已关闭）
- `Quote` 报价：单价、起订量、有效期、**改价次数** `priceChanges`、**是否毁约** `breached`

### 2.3 关键规则（mock 层强制）

**售后**
1. 退款金额**不得超过订单实付**（查 `orders` 校验，跨域一致性）
2. 平台介入裁决**必须同时给出责任方与三方赔付比例，且比例之和为 100**
3. 已退款/已关闭的单不能再裁决
4. 极速退阈值：金额上限 > 0、时限 ≥ 1 小时（0 小时等于关掉极速退但看起来像开着）

**团购**（ADR-003：报价不做事前审核，用锁价 + 公示 + 信用）
5. 团模板：起团人数 ≥ 2；**团购价必须低于原价**（否则"团购"是假的）
6. 同一需求同一商家**只能有一条有效报价**（改价走改价而不是再发一条）
7. **涨价必须留痕并公示**：`priceChanges` 累加；超过阈值（3 次）**禁止再改价**
8. **毁约次数 ≥ 3 的商家禁止对新需求报价**（与商家信用档案 P-11.1.5 同源）

### 2.4 权限

复用：`aftersale:ticket:read/handle`、`aftersale:refund:approve`、`group:campaign:read/audit`、`group:demand:read/assign`。**不新增模块。**

### 实现期的一个模型修正

毁约计数最初写成「数报价表里 breached 的条数」，但毁约可能发生在报价之外（成团后不发货），
只数报价会漏。改为**取商家档案的 `breachCount`**（P-11.1.5 信用档案），并在标记毁约时同步累加 ——
两处不同步的话，「限制报价」会按一个永远长不大的数判。
