## 一、配错的后果是订单发不出去

这一页与别的配置页不同：填错一个数字不是"显示不对"，而是快递链路当场断掉。
三条规则各自对应一种断法：

| 规则 | 配错会怎样 |
| --- | --- |
| **没配密钥的不能启用** | 启用后每一单预约都当场失败。比不启用更糟 —— 至少不启用时运营知道它不可用 |
| **还有在途单的不能停用** | 停了之后那些单的轨迹拉不回来 |
| **不能把最后一家启用的也停掉** | 全停之后快递单无处可下 |
| 优先级不能重复 | 同优先级时选哪家取决于数组顺序，那是隐性行为 |
| 截单时间必须 `HH:mm`、时效为正 | 过点顺延的判断依据坏掉 |

界面与 mock 层**同向**：每一行的停用/启用按钮旁边直接写着为什么不能点
（`还有 1 个在途单` / `未配密钥，启用后下单会失败` / `最后一家启用的运力`），
而不是等点了才报错。判断在途单数量要读快递单表，所以这一页同时查了 `listShipments`。

## 二、密钥不进契约

`CarrierConfig` 里只有 `apiKeyConfigured: boolean`，**没有密钥字段** ——
哪怕是脱敏的也不给。密钥由运维在服务端配置，这一页只显示配没配。
有一条用例专门断言契约里不存在 `apiKey` / `apiSecret`，防止以后有人"顺手加上去"。
