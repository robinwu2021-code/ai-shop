## 一、phase 与 ready 是两件事

矩阵把 P-12.2 标为 P1 二期，所以这两个叶子保留 `phase: 2`（分期徽章不能因为做完了就改）。
能不能点由 `ready` 单独表达 —— 它的口径写在 `lib/nav.ts`：mock 层真落库、状态机强制、
**浏览器实机验证过关键路径**。三条都满足，才加 `ready: true`。

第一次跑起来时页面显示的是「Not available yet」，正是这套机制在起作用：
去掉 `soon` 不够，phase 门禁是另一层。这不是 bug，是设计。

## 二、提现是运营端唯一会把钱打出去的动作

所以校验最密，界面也做了别处没做的两件事。

### 通过后落「已通过」而不是「已打款」

```
PENDING → APPROVED → PAID   ← PAID 由渠道回执驱动
```

界面上**根本不提供「标记已打款」**。给了这个按钮，就等于允许在钱没到账时把单子做平 ——
之后对账差异出来，没人分得清是渠道慢了还是根本没打。

### 抽屉里先摆前置条件清单

四条条件在点之前就算好、不满足的标红，省得"点了才知道被拒"：

| 条件 | 不满足会怎样 |
| --- | --- |
| 已报备分账接收方（ADR-002） | 没有收款账户，批了钱也打不出去 |
| 商家未封禁（P-11.1.4） | 解封是另一条链路上的决定，不在这里绕过去 |
| 金额未超可提余额 | 超额放款 |
| 金额达到单笔下限（10 元） | 渠道手续费比本金还贵 |

余额用的是**申请那一刻的快照**而不是实时值：审批看的是"他申请时能提多少"，
实时值会因为期间的新订单而漂移，那样同一张单在不同时刻审会得到不同结论。

超过 5000 元必须写复核说明 —— 大额是最容易被冒用的口子。驳回原因原样回商家 B 端。

## 三、发票与个税同页

它们是同一个问题的两半：开票是对外的凭证，代扣是对内的扣除。分两页会让人以为可以只做一半。

| 规则 | 不这么做会怎样 |
| --- | --- |
| **开票金额 ≤ 该周期已结算金额** | 超出部分没有真实交易对应，就是虚开 |
| 企业抬头必须有纳税人识别号 | 开出来的票作废 |
| **已开票/已驳回的不能再处理** | 重复开票就是重复虚开 |
| 发票流水号必填 | 没有流水号的"已开票"查不到票 |
| 代扣税率 ≤ 45% | 超过一定是配置错误 |
| 个税只对个人主体生效，且有起征点 | 不设起征点会给每笔几块钱的提现都产生一条扣税记录 |

## 五、已知取舍

- `availableBalance` 在 mock 里是样本快照。接后端后它应在**创建提现单时**由结算表算出并落库，
  而不是查询时实时算 —— 那样这条"快照口径"就名存实亡了。
- 个税代扣目前只有规则配置，没有代扣流水列表。流水要等提现真正打款后才产生，
  而打款回执这条链路本身还没接。
