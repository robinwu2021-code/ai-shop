## 3. 不做什么（明确边界）

1. **不引入第三方组件库**（antd/arco）：会与已定的 token 三层体系打架，且分层规矩会失效。
2. **不为单页需求加通用组件**：某页专有的展示留在该页；出现第二个调用点再上移（`components/README.md` 的既有判据）。
3. **不动 token 体系本身**：五档圆角、两档边界、语义色三档是已验证结论，这次只让组件**真正消费**它们。

## 8. 实现记录（2026-08-06）

**N 收口**：after-sales 页有**两张表单**，第一轮只改了极速退规则那张，裁决抽屉那张（责任方 +
三方比例 + 裁决结论）漏了 —— 是新加的守卫把它报出来的，不是复查看出来的。
裁决表单不从 query 派生（开抽屉时初始化），所以没套 `useEditableConfig`，改成 `setForm((p) => ...)`。

守卫要**跳过注释行**：注释里写反面例子（「不要 `setForm({ ...editing })`」）恰恰是应该的，
第一次跑就把 growth 页的那句说明当成了违规。

**O 收口**：15 个页面的 8 行样板换成一行 `usePageTab(TABS, () => { ... })`。
原来 `useEffect` 与 `onChange` 两处各写一遍切 tab 的副作用，现在只剩 `onSwitch` 一处 ——
这两处本来就该一致，分开写迟早会漂。

**P/Q/R 收口**：6 张配置卡片改 `ConfigCard`（含 system 页并排的两张）、7 处 `FieldGrid`、6 处 `StatRow`。
`ConfigCard` 实现时补了两个 prop：

- `readOnly`：`ReadOnlyNotice` 要放在**卡片内部**。摆到外面会横跨整个页宽，
  看着像页面级公告，而它说的只是这一张卡片能不能改。
- `saveLabel`：皮肤那张的按钮是「下发」不是「保存」—— 立刻对外生效的动作不能让人以为只是存草稿。

**新增三条守卫**（`design-tokens.test.ts`，基线全 0）：

| 守卫 | 挡住什么 |
|---|---|
| 页面层不许出现 `sp.get("tab")` | 手写 tab 同步漏 `setPage(1)` → 切了 tab 停在第 3 页，列表空白像没数据 |
| 页面层不许出现 `上次修改：` | 各写各的措辞 → 运营排查「谁什么时候改的」找不到同一行字 |

**校验**：`npm run check` = tsc 0 error + vitest **321 passed**（+3 守卫）；`npm run build` 静态导出 22 路由。
实机：`/after-sales?tab=fastrefund` 深链直达且页脚正常、`/system` 两张卡并列、

### 过程中踩的坑（记下来，别再犯）

批量删「已不再使用的 import」的脚本干了两件蠢事，都当场被 tsc 抓住：

1. 用 `list(re.finditer(...))` 预先取好所有匹配位置，然后**边遍历边改字符串** ——
   第一次替换后偏移就全错了，把两个 import 语句拼成了 `import { Treeimport { Tree } ...`。
   改法：每次替换后重新搜索，或从后往前改。
2. 判断「这个名字还有没有被用到」时，拿 `type Column` 整串去搜正文 ——
   正文里写的是 `Column<Material>`，永远搜不到，于是把在用的类型导入删了。
   改法：先剥掉 `type ` 前缀再搜标识符。

# 第三轮（2026-08-06）：第一轮标 P1、一直没做的五项

第一轮把这五项判为 P1 缓做，理由是"能用"。铺完 22 个页面后它们都变成了**每天都会碰到**的摩擦。

| # | 问题 | 改法 |
|---|---|---|
| S | 筛选生效时下拉框混在一排「全部 XX」里毫不显眼；清空得一个个点回「全部」 | `Toolbar` 下方出「生效中的筛选」chip，点 × 清单项，两个以上出「清空筛选」 |
| T | 每页条数写死 10；对账、导出前核数要翻 5 页去数 100 条 | `Pagination` 加 `onSize`，10 / 20 / 50；配 `lib/use-paging.ts` |
| U | 长抽屉里字段等距堆着，**要填的**和**只是给你看的**混在一起 | `DrawerSection`（小标题 + 分隔线） |
| V | 空态只有一句话，没有出路 | `EmptyState` / `DataTable` 加 `action` / `emptyAction` |
| W | 骨架屏是 6 条等宽灰条，加载完列宽一变整张表跳一下 | 骨架渲染**真实表头** + 按列宽铺占位格 |

## 9. 问题与实现要点

**S 的关键是不要两份真相**。让页面自己再传一份 chips，等于「筛选器一处、回显一处」，
加个筛选项忘了加回显是必然的。所以改成**控件自报**：`components/ui/filter-chip.ts` 定义
`toChip(props)`，`FilterSelect` 与 `ShowArchivedToggle` 各自声明，`Toolbar` 只认这个字段、
不认具体是谁。chip 前缀直接从 `aria-label`（「按状态筛选」）里剥出来，不额外要求调用方再写一份名字。

用静态字段而不是在 Toolbar 里 import 那两个控件，是因为 `ShowArchivedToggle` 在 `components/`、
Toolbar 在 `components/ui/` —— 让 ui 反向 import 上层会把依赖方向拧成环。

**T**：`setSize` 内部一定 `setPage(1)`。换了每页条数还停在第 5 页，很可能落到不存在的页 ——
表格空白，看着像"筛没了"。绑在一个 hook 里，调用方想漏都漏不掉。

**V 的取舍**：只在**能新增**的三个页面（素材 / 帮助中心 / 黑名单）挂了「新增」按钮。
「筛过头了」那一类不再单独给按钮 —— chip 行就在空表格正上方，已经有「清空筛选」，
再放一个是同一件事说两遍。顺手把工具条里内联的新增回调提成具名函数：
工具条和空态指向同一个动作，内联两份迟早会漂。

**W**：骨架现在长成**这张表**的样子（表头照常渲染，占位格按列宽铺、宽度错落）。
除了不跳，还有个附带好处：表头先到，这页在等哪几列一目了然。

## 10. 新增守卫（基线全 0）

| 守卫 | 挡住什么 |
|---|---|
| 页面层不许 `const [page, setPage] = useState(` | 绕开 `usePaging`，换每页条数不复位页码 |
| `<Pagination>` 必须带 `onSize` | 少一个页面就退回固定 10 条 |
| `<Toolbar>` 里的控件必须声明 `toChip` | 新筛选控件的选中态不进回显 → 用户以为没筛，对着少掉的数据找半天 |

## 11. 校验

`npm run check` = tsc 0 error + vitest **324 passed**；`npm run build` 静态导出 22 路由。

实机：订单页选两个筛选 → 出两个 chip + 「清空筛选」，点后列表恢复 6 条；
每页条数选择器在分页行左侧；订单详情抽屉分「订单概况 / 商品明细 / 同次结算的其它子订单」三段；
售后裁决抽屉把「工单情况（不可修改）」与「平台裁决」分开；
商家页勾「显示已归档」→ 出 `显示已归档 ×` chip；
把 mock 延迟临时调到 5s 看骨架屏 —— 表头与列宽与加载完成后完全一致（已复原为 200ms）。

## 13. 改法

**边界（X1）**：画布改 `--gray-2`、卡片保持纯白，另加一条 `--card-border` hairline。
密集界面里"边界"应当由**线**来说，阴影只负责"浮起来"。

**焦点环（X2）**：`app/globals.css` 加 `@utility focus-ring`，14 个组件改成只写这一个类。
> 中途踩了个坑值得记：先写成一条手写 `box-shadow`，理由是"@utility 好像没生成"——
> 实际是我在浏览器里遍历 styleSheets 的探针有问题。**用 `@utility` 才是对的**：
> Tailwind 的 ring 通过 `--tw-ring-*` 与 `--tw-shadow` 叠加成一条 box-shadow，
> 手写会把元素原有阴影整个顶掉（主按钮一聚焦就没影子）。已按正确结论落地并实测：
> 键盘 Tab 到按钮，`boxShadow` = 白 2px + 主色 4px 两层。

## 22. 开暗色时查出来的两个真问题

**Z4 暗色下画布与卡片又是同色**（都是 `--gray-2`，对比度 1.00）——

更尴尬的是：`.dark` 块里**自己写着**「卡片要整体上移一档（用 gray-3 而不是 gray-2）」，
而代码里写的就是 gray-2 —— 注释和代码互相矛盾，两边都在，没人对过。
现在画布 gray-2、卡片 gray-3，侧栏与画布同色（外壳是一整块，不该看着像浮起来）。

**Z5 `Badge` 的 `default` tone 过不了 AA**：底用主色 14% 浅底，文字却直接是 `--primary`，
时尚蓝皮肤下实测 **3.18:1**。而 badge.tsx 的注释里**恰恰记着**语义色早就因为同样的原因修过一轮
（"直接拿语义色当文字色只有 ~2.8:1"）—— default 是那条规矩的漏网之鱼，因为主色缺 ink 这一档。
补 `--primary-ink`（浅色往黑压 62%、暗色往白提 72%）后实测：
黑白灰 **14.63:1**、时尚蓝 **9.02:1**、促销橙 **7.18:1**，全部通过。

# 第七轮（2026-08-06）：22 个页面的一致性 review

前六轮改的是组件本身，这一轮把**页面**逐个过一遍：同一件事是不是都用同一种写法。

## 25. 先说结论：token 层已经很干净

写死 hex、Tailwind 默认圆角/阴影、字面控件高度、手写 focus 链、任意色值 —— **全 0**。
22 个页面里只剩 3 个裸 `<button>`（都是表格行内的纯文本跳转，不是控件）。
这是前几轮守卫的直接结果：**能被守卫盯住的，就不会漂**。

漂的是**守卫盯不住的结构层**，这一轮查出 4 处。

## 26. C1 —— 导航里一个"点了没反应"的叶子（真缺陷）

`lib/nav.ts` 把「商家档案」标成 `ready` 并指向 `/merchants?tab=list`，
而 `app/merchants/page.tsx` **根本不读 `?tab`**：点进去面包屑变成「商家档案」、
L3 高亮也跟着变，**表格还是入驻审核那一张**。

修法不是补个 tab 了事 —— 两个视图本来就该不一样：

- 「入驻审核」= 只看还没走完审核的两档（`SUBMITTED` / `REVIEWING`），它是**待办**
- 「商家档案」= 全量商家，它是**台账**

已通过/已封禁的商家混在待办队列里，是这条链路上最容易让人漏审的形态。
顺带给 mock 的 `eqHit` 加了逗号分隔多值支持 —— 否则页面只能拉全量再前端过滤，分页数会全错。

**守卫**：`nav.test.ts` 新增一条 —— 已解锁的 `?tab=` 叶子，页面必须真的认这个 tab。

## 27. C2 —— 两种页头件

17 个业务页用 `TabHeader`，`merchants` 与 `orders` 用 `PageTitle`。
`PageTitle` 有 `desc` 而 `TabHeader` 没有，这就是当初分叉的原因。

给 `TabHeader` 补了 `desc`（单 tab 时显示），两页统一过来。
`PageTitle` 只留给工作台 —— 它没有 L3 导航，标题不对应任何子功能。
**守卫**：业务页出现 `<PageTitle>` 且没有 `<TabHeader>` 就红。

## 28. C3 —— 分页器两种写法 + 一处重复

多 tab 页面里有两派：一派用 `current`/`current$` 指向当前 tab 的查询、只放一个分页器；
另一派在每个 tab 里各放一个。`reviews` 更是把**一模一样的那行**写了两遍
（加第三个分页 tab 时必然漏掉一个）。

统一成「一页一个分页器，绑 `activeList`」。名字从 `current` 改成 `activeList` 是有原因的：
多数页面里 `current` 已经被"选中的那一行"占用了 —— 这正是当初有人被迫写 `current$` 的由来，
不是随手起的名。

## 29. C4 —— 9 处空态文案没说"为什么空"

`components/README.md` 早就写着空态要说清「为什么空、下一步做什么」，
但「没有角色定义。」「黑名单是空的。」这类一句话空态还有 9 处。
运营看到空表的第一反应是"系统是不是坏了"，一句话答不了这个问题。

全部改写，并加守卫：`empty` 文案 < 20 字就红。
判据用长度是粗糙的，但实际分布很干净 —— 写清了原因与出路的那些一律超过 20 字。

## 30. 查了但**没有问题**的几项（记下来，免得重复查）

- 金额一律走 `money()`：4 处 `/100` 是**表单回填**与**万分比**，不是金额显示
- 时间一律走 `fmtTime()`：0 例外
- 数字列都传了 `numeric`：0 例外
- 行内操作按钮都 ≤2 个：0 例外
- 页面没有自己拼语义色提示块（`Notice` 的 tone 补上之后就没人手拼了）

## 31. 校验

- `npm run check` = tsc 0 error + vitest **332 passed**（+2 守卫）；`npm run build` 静态导出 22 路由
- 实机：`/merchants` 入驻审核只剩 2 条待审、点「商家档案」切到全量 6 条（这个链接此前是死的）；

# 第八轮（2026-08-06）：把对比度验证做成可回归的，然后它立刻抓到一个真缺陷

第六轮欠着一句话：「5 套皮肤 × 明暗共 10 组的对比度没能自动化跑通」。这一轮补上。

## 32. 工具：`/dev/ui` 的「全量对比度」

`app/dev/ui/sweep.ts` —— 切一组 → 等样式生效 → 在 DOM 上量一遍 → 记录 → 下一组 → 还原。
与页面上的 `<Probe>` **共用同一套 `measure/aaThreshold`**，所以两边数字必然一致。

三个决定值得记：

1. **不复用 `<Probe>`**：探针是 React 组件，只在页面自身开关触发 `PreviewVersionCtx`
   变化时才重量；外部脚本改 `<html>` 属性不会触发它 —— 这正是上一轮"批量验证"做不成、
   还得到过假阴性的原因。
2. **扫描期间冻结过渡动画**。第一次跑出了 `1.23:1` 这种不可能的读数：控件普遍带
   `transition-colors 180ms`，切完皮肤两帧后量到的是**过渡中途的插值色**。
   比没有数字更糟 —— 它看起来像个真缺陷。注入一条 `transition:none!important` 之后才可信。
3. **跳过 disabled 与半透明**（WCAG 不对禁用态做要求；半透明本页另有一栏讨论），
   并报出「每组量了多少个节点」——**空集不能被读成"全部通过"**，这是上一轮踩过的坑。

## 33. 它抓到的：三套皮肤的主按钮文字过不了 AA

| 皮肤 | 主色 | 白字 | 墨字 |
|---|---|---|---|
| 生鲜绿 | `#00b578` | **2.66** ✗ | 6.80 ✓ |
| 促销橙 | `#ff6010`（ops 现值） | **3.03** ✗ | 5.98 ✓ |
| 时尚蓝 | `#2f6bff`（ops 现值） | **4.50** ✗ | 4.03 ✗ |
| 黑白灰 / 商务蓝 | — | 18.75 / 11.04 ✓ | — |

默认皮肤是黑白灰（18.75:1），所以**平时完全看不出来**，换个皮肤才暴露。
我用独立的 WCAG 公式复算了一遍，与工具读数完全吻合（2.66 / 3.03 / 4.50），不是工具算错。

**这不是本项目新发现的**：C 端 `packages/shared/src/design/tokens.ts` 的注释里早就写着
「绿底配墨字 6.80，配白字只有 2.66」，运营端只是没跟上那个结论 —— 它把
`--primary-foreground` 一律写成了 `#ffffff`。

顺带查出两个**与 C 端对不上的色值**（而注释一直写着"同名同色，改一处要改两处"）：

- promo 用的是 C 端的 **dark** 值 `#ff6010`，light 应为 `#d24600`
- blue `#2f6bff` 应为 `#2c69ff`

## 34. 改法

- 每套皮肤各自选白字或墨字，取能过 4.5 的那个：fresh 用墨字 `#14161a`（6.80），
  promo / blue 对齐 C 端色值后用白字（4.55 / 4.59）
- mono 保持 `#0f1218` 不与 C 端 `#18181b` 对齐 —— 这是**明确记录在案的例外**：
  两者对白字都是 17~19:1、肉眼无差，但 `#18181b` 与正文色几乎同亮度，
  会让主按钮和正文一样重（第四轮 X5 的原因）

## 35. 最关键的一步：把它变成单测

`lib/skin-contrast.test.ts` 直接读 `app/globals.css` 里的 hex 算 WCAG 对比度：

- 每套皮肤的 `--primary` + `--primary-foreground` 必须 ≥ 4.5
- business 整套块单独验
- fresh / promo / blue 的色值必须与 `packages/shared` 一致（把口头约定变成断言）
- 抓到的皮肤块少于 5 个就直接失败 —— **不让"零违规"变成假阴性**

**验证守卫真的会红**：临时把 fresh 改回白字 → 测试失败并打印
`[data-theme="fresh"] #00b578 + #ffffff = 2.66:1`；改回来 → 通过。
按钮要人点，单测不用。

## 36. 校验

- 「全量对比度」重跑：**10 组全部通过 AA**（每组 537 个文本节点，跑完皮肤已还原）
- 工具灵敏度双向验证过：修之前报 fresh 2.66、修之后消失；冻结过渡前报 1.23、冻结后消失
- `npm run check` = tsc 0 error + vitest **336 passed**（28 个测试文件）；`npm run build` 22 路由

# 第九轮（2026-08-06）：页面正文中英化（**已完成**）

用户确认要做前几轮一直挂着的「页面正文英文」。先量了工作量：
**944 条 / 6557 字，分布在 18 个页面**。

## 37. 机制：文案表按页就近放

`lib/use-copy.ts` + `app/<页面>/copy.ts`（`{ zh, en }` 两份 key 齐平的表）。

**为什么不塞进 `lib/i18n/messages/*.ts`**：那份是**框架层**文案（按钮、分页、状态枚举），
全站共用、条目稳定。页面正文是另一回事 —— 按页聚集、改页面时多半要一起改。
放同一个大文件有两个坏处：一千多行的 catalog 里改 A 页要翻 B 页的 key；
看页面时看不到文案、看文案时看不到页面，对不上就会译歪。

## 38. 守卫（`lib/page-copy.test.ts`）

对**每个已接入的页面**分别断言四条：

1. zh / en 的 key 完全齐平 —— 漏一条会静默显示中文，很难发现
2. 英文里不许残留汉字 —— 复制粘贴漏译
3. **page.tsx 里不许再有裸中文** —— 挡住"改了一半"的页面（中英混排）
4. 至少有一个页面接入 —— 否则上面三条全是空转（第六轮踩过这种假阴性）

第 3 条第一版写错过：只看行首判断注释，把多行 JSX 注释的**续行**误判成违规。
改成状态机跟踪块注释才对。**验证过守卫真的会红**：往已转换页面塞一句中文 → 失败并打印行号。

## 40. 过程中查出的四个真问题（都不是翻译问题）

**Z6 页面里写死 mock 数据**。`groups` 的「可指派商家」是页面内硬编码的 5 个中文店名。
我一度想把它们塞进文案表，守卫拒绝了（en 里不许有汉字）—— 守卫是对的：
**店名是数据不是文案**。正确修法是去查真实列表（`listMerchants({ status: "APPROVED" })`），
这同时修掉了"接了后端就是错的"这个更根本的问题。

**Z7 `merchants` 的「商家档案」是个死链**（第七轮 C1 已修，这轮复验通过）。

**Z8 筛选 chip 的前缀在英文下失效**。chip 前缀靠正则剥中文「按…筛选」，
页面英文化后 aria-label 变成 "Filter by status"，剥不掉 —— chip 会显示成
`Filter by status：Paid`（还带个全角冒号）。改成两种语言的模式都剥，
分隔符也交给 i18n（中文全角、英文半角）。

**Z9 筛选 chip 在多 tab 页整页消失**。`chipsFrom` 只遍历直接子节点，
而页面普遍把筛选器包在 `{tab === "x" && (<>…</>)}` 里 —— `React.Children.forEach`
拿到的是 Fragment，没有 `toChip`，于是静默跳过。
`orders`/`merchants` 这种直接挂的页面是好的，所以**"一半页面好使"的失效**一直没被发现。
改成递归，并补了 `lib/filter-chip.test.ts`（5 条，含 Fragment 那条）——
**验证过它会红**：退回旧实现，Fragment 那条立刻失败。
