## 一、轨迹是承运商的，平台不编

页面上**没有**「手工加一条轨迹」。理由不是懒：平台自己写的轨迹一旦与承运商记录不一致，
纠纷时反而站不住。运营在这一页能做的只有一件事 —— 换运单号，而这件事本身会写进轨迹。

| 规则 | 不这么做会怎样 |
| --- | --- |
| 同一承运商下运单号不能重复 | 重号会把两单的轨迹搅在一起，之后谁也说不清哪条是哪单的 |
| 不同承运商可以同号 | 单号只在承运商内唯一，跨承运商拦截是误伤 |
| **已签收的不许改单号** | 货都到了再改，等于把一条已完成的轨迹指向别处 |
| 换单号必须写原因 | 之后对不上时这是唯一线索 |

`EXCEPTION`（疑难件）**不是终态**，徽标用 warning 不用 danger：
承运商还可能派送成功，做成终态就得靠人工把单子拉回来，而那本该是回传的事。

## 二、运费模板与超区同页

它们是同一个决定的两面：「这单收多少运费」与「这个地址到底发不发」。
分成两页配，必然出现模板算得出运费、却根本不该配送的地址。

| 规则 | 不这么做会怎样 |
| --- | --- |
| 首重 ≥ 100 克 | 首重 0 克意味着"拿起来就收首重费"，是配置错误不是策略 |
| 续重单位 > 0 | 否则续重费无从计算 |
| **同一区域只能配一条超区规则** | 配两条时命中哪条取决于顺序，那是隐性行为 |
| 不配送的区域不能填加价额 | 传了就是调用方理解错了，**报错而不是静默清零** |
| 加价配送的加价额 > 0 | 否则这条规则等于没配 |
| 默认模板不能归档 | 归档之后新商家没有模板可用 |

单位口径：重量一律**克**、金额一律**分**，都是整数，避免 0.1kg + 0.2kg 这类浮点误差
在算钱的地方冒出来。表单让运营输入"元"，落库前换回分。

界面上两处呼应规则：切成「不配送」时前端就把加价额清零并禁用输入（否则保存时才报错，
是个只能靠报错发现的坑）；默认模板不给归档按钮（摆一个必然报错的按钮是在骗人点一次）。

## 三、被守卫拦下的一次设计错误

第一版写的是 `deleteFreightTemplate` + `client.del`。两条守卫同时报警：

```
禁止 delete* —— 软删除一律 archive*/unarchive*（架构 §10.6）
每个契约方法都有对应的 client 调用
```

第一条是对的，而且理由比"约定"更实在：硬删会把历史订单的运费依据一起抹掉，
之后谁也说不清那单当时为什么收了 8 元。改成 `archiveFreightTemplate` /
`unarchiveFreightTemplate` + `listFreightTemplates({ showArchived })`，
`client.del` 随之删掉 —— 本仓不需要它。
