## 1. 为什么这两个一起做

**归因链路是风控识别异常裂变的数据源**。分开做的话，风控页只能显示"这个用户可疑"，
点不进去看他到底是怎么被归因的 —— 而"同设备批量注册后互相邀请"正是从归因链路上看出来的。

另外 P-9.1 在矩阵里标着 **B1 未拍板**（店铺码归因规则）。把配置项做出来、把三种处置策略摆在页面上，
比继续在文档里讨论更容易推动那个决策。

## 2. 方案

### 2.1 页面

| 页面 | tab | 覆盖 |
|---|---|---|
| `/growth` | 归因规则 · 归因链路 · 裂变活动 | P-9.1.1/9.1.2/9.1.4/9.1.5 · P-9.1.3 · P-9.2 |
| `/risk` | 风险事件 · 黑名单与申诉 · 拦截规则 | P-16.2.1/16.2.2/16.2.3 · 16.2.4 · 16.2.5 |

**三类风险事件合成一张表**（刷单 / 异常裂变 / 恶意退款）用 `type` 区分：
它们的结构一致（主体 + 信号 + 分值 + 处置），拆三张表会让"这个用户同时命中几类"看不出来 ——
而那恰恰是最该优先处理的情况。

### 2.2 数据模型要点

**growth.ts**
- `AttributionRule`：`priority` 是**全序数组**（店铺码 > 邀请人 > 渠道），不是三个独立开关；
  `windowDays` 窗口期；`conflictPolicy` 冲突处置（B1 的三个候选）；`newUserFactors` 新客判定因子
- `AttributionTrace`：一条归因链路 = 用户 + 归因源 + 归因时间 + 关联订单，`conflictWith` 记冲突对象
- `FissionCampaign`：邀请有礼。**奖励类型只能是券**（ADR-004：不存在现金激励，否则职业薅羊毛立刻回来）

**risk.ts**
- `RiskEvent`：类型 + 主体 + 命中信号 + 分值 + 处置状态
- `BlacklistEntry`：主体（用户/商家/设备）+ 原因 + 到期时间 + 申诉状态
- `RiskRule`：各类型的触发阈值 + 是否自动拦截

### 2.3 关键规则（mock 层强制）

1. **归因优先级必须是全序**：三个来源不重不漏，缺一个或重复都拒绝 —— 半个优先级表在冲突时会随机裁决
2. **窗口期 1–90 天**：0 天等于关掉归因，超过 90 天的归因没有业务意义
3. **邀请有礼只能发券**（ADR-004）：奖励类型选现金直接拒绝
4. **新客判定至少一个因子**（设备 / 手机号），一个都不选等于所有人都是新客
5. **黑名单必须带原因与到期时间**：无期限拉黑没有申诉出口，是产品事故不是风控严格
6. **申诉必须有裁决结论**，且解除拉黑要留痕
7. **拦截阈值 > 0**：0 等于全量拦截

### 2.4 权限

复用 `growth:attribution:read`、`growth:fission:read/update`、`risk:rule:read/update`、`risk:blacklist:update`。
`risk:blacklist:update` 是矩阵 §2.3 的高危码，只有超管与风控持有。

### 实现期抓到的三个问题

1. **类型名跨域撞车**：`AppealStatus` 在评价域（差评申诉）已占用，风控的「解禁申诉」同名会让
   `lib/types` 总出口直接冲突。改名 `BlacklistAppealStatus`。
2. **契约方法名跨域撞车**：`decideAppeal` 同理会被扁平合并静默覆盖 → 改名 `decideBlacklistAppeal`，
   并在 `contract.test.ts` 加了一条**跨域重名守卫**，把这类问题前移到"加方法就红"。
3. **表单 stale closure（实机才发现）**：连续勾选两个复选框时，第二次点击读到的是上一次渲染的
   state，第一次的变更被覆盖 —— 表现为"取消了两个因子，只有一个真的取消"。
   改成函数式更新 `setForm(prev => ...)`，并在注释里写明输入框场景不易触发、复选框连点必然触发。
