# 一 · 痛在哪

三个行业卖的东西名字不同（商品 / 菜品 / 服务项目），**但它们是同一个对象**：
有标题、有图、有类目、有规格、有 SKU、有价格、有库存、有上下架、有审核、有门店覆盖。

如果按"每个行业一套"做，痛点是可以逐条点名的：

| 痛点 | 具体表现 |
|---|---|
| **建品页分叉** | b-app 要维护三套建品表单，共同字段改一次要改三处，漏一处不报错 |
| **搜索与列表分叉** | 「按社区逛全部商品」是 C 端首页主查询，三张表就要 union 三次 |
| **审核分叉** | 平台审核员要在三个页面审同一件事 |
| **标准品失效** | `stdNo` 跨店可比是平台的资产，行业各建一套品就没有可比性 |
| **规格库白做** | V195 的四层规格模型只服务其中一套 |
| **能力开关退化** | 「这家店能不能卖服务」本该是能力，变成「这家店装没装某个包」 |
| **数据割裂** | 报表要按行业 union；一个主体同时开餐厅和美容店时，商品数怎么算都不对 |

**而这些痛全都不必付** —— 因为商品域今天已经有一套按品类分段的机制在跑，只是它是写死的。

# 二 · 现状盘点：商品域已经有四套扩展机制

这一节是本册的地基。**先把已有的四套逐一判定，才谈得上要不要第五套。**

## 2.1 ① 五品类 + 分段（`FreshSpec` / `ServiceSpec`）—— 在用，就是它

```java
// MerchantGoodsService.SaveCommand（节选）
record SaveCommand(String goodsNo, String title, …,
                   String categoryNo,          // 唯一的分类输入
                   FreshSpec   fresh,          // 只在派生出的品类是 FRESH 时写入
                   ServiceSpec service, …)     // 只在 SERVICE 时写入
```

- 类目 → 五品类由服务端派生（`CategoryService.TEMPLATE_TO_TYPE`），**商家不填品类**；
- 线上 73 个类目全部有 `template` 值；
- `prd_goods` 上已经有 FRESH 段（`cutoffAt`/`arrivalDesc`/`weighed`/`origin`）与 SERVICE 段（`durationMin`/`storeName`）的列。

**这就是"一套接口 + 额外插件"的形状，已经在生产上跑。** 缺的只有一件事：段是写死的五个，不能注册第六个。

## 2.2 ② 规格库四层（V195，SALE 维度）—— 不能用

规格项 / 规格值 / 类目绑定 / 商家覆盖四层，只把 **SALE** 维度下发给商家做 SKU 矩阵。

**不能承载行业属性的理由**：SALE 维度进 SKU 笛卡尔积。
「出品部门 = 热菜」不是在卖两种不同的东西，把它做成规格维度，
一道菜会因为部门 × 做法炸成一堆 SKU —— 而 V195 那一版的全部目的就是**避免笛卡尔积爆炸**。

## 2.3 ③ 商品参数（PROP，V250）—— 不能用，但它是最像的一个

`prd_goods.params`（JSON 列）：产地 / 保质期 / 材质这一类，`usage_type=PROP`，不分 SKU。
`GoodsParam(dimNo, name, valueNo, code, label)`，`valueNo` 来自平台值池，**有它才参与筛选与跨店比较**。

它看起来完全能装下"出品部门"。**但不能用**，三条理由：

1. **它是给买家看的。** 商品参数会渲染在 C 端详情页的参数区。
   放进去，顾客点开一道宫保鸡丁会看到「出品部门：热菜」;
2. **它的值池是给跨店比较用的。** 每家店自己的厨房分区塞进平台值池，
   「按产地筛选」那套逻辑立刻被污染；
3. **它是 JSON 列，不能 JOIN。** 出品部门要参与分单打印的路由匹配，
   每次出票去 JSON 里挑一个 key，路由规则就没法用 SQL 表达。

> **这一条要写在最显眼处**：`params` 是四套里最容易被后人误用的一个。
> 判据是一句话 —— **参数是给买家看的，段是给系统用的。**

## 2.4 ④ `prd_category.attr_template` —— 已废弃，不许复活

`@Deprecated`，全仓零读者，生产 73 个类目**一个有值的都没有**，
且 `prd_goods` 上根本没有存放这些属性值的地方。它自己的注释写着：

> 不要再往它上面建东西 —— 第三套同类机制只会让「建品页字段从哪来」变成一个没人答得清的问题。

**本方案遵守这条**：不复活它，**也不新造通用属性袋**（`prd_goods_attr` 之类的自由 KV
正是它警告的那个"第三套"）。

## 2.5 判定小结

| 机制 | 状态 | 能否承载行业属性 |
|---|---|---|
| ① 五品类 + 分段 | 在用 | ✅ **采用**，把写死的段开放为可注册 |
| ② 规格库四层（SALE） | 在用 | ❌ 会炸 SKU 笛卡尔积 |
| ③ 商品参数（PROP） | 在用 | ❌ 那是给买家看的参数 |
| ④ `attr_template` | 废弃 | ❌ 注释明令不许再建 |
| ⑤ 通用属性袋 | 不存在 | ❌ 就是 ④ 警告的第三套 |

# 三 · 方案

**一句话：不造第五套机制，把第①套从"写死五段"开放成"可注册段"。**

```
                    categoryNo（唯一分类输入）
                            │
                    派生 → type（五品类，恒定五条）
                            │
        ┌───────────────────┼────────────────────┐
        ▼                   ▼                    ▼
   公共字段            固定段（基座）          注册段（可扩展）
 title/images/…    FreshSpec / ServiceSpec   food / …（行业注册）
        └───────────────────┴────────────────────┘
                            │
                  同一个 POST /biz/goods/save
                  同一个 GET  /biz/goods/{no}
                  同一个 GET  /biz/goods/form-schema
```

三条设计原则：

1. **接口不增。** 行业**不得**新增商品维护端点。段通过既有接口的一个字段进出。
2. **段可枚举。** 每个段必须声明字段清单（`schema()`），不允许自由 KV。
   「建品页字段从哪来」永远只有一个答案：**五品类固定段 + 该门店已启用的注册段**。
3. **段不认识基座，基座也不认识段的内容。** 基座只做路由、校验调度、事务边界。

# 四 · 段的完整契约

```java
public interface GoodsSegment {

    /** 段码，进 API 的 segments 字典，如 "food"。全局唯一。 */
    String code();

    /** 只在这些五品类上出现。空集 = 所有品类。 */
    Set<String> appliesToTypes();          // NORMAL / FRESH / SERVICE / VIRTUAL / CARD

    /** 门店没开这个能力，段不出现在 form-schema 里，也不接受写入。 */
    String capability();                    // 见核心能力清单 A4

    /** SPU 级还是门店级 —— 见 §六，这一条决定它落哪张表、按什么键存。 */
    Scope scope();                          // SPU | STORE

    /** 字段清单。驱动 form-schema，也是校验的白名单。 */
    List<FieldSpec> schema();

    /** 段自己的校验。基座已经做完公共校验才会调到这里。 */
    void validate(Ctx ctx, Map<String,Object> values);

    /** 写。**与基座商品写入同一个事务**。 */
    void save(Ctx ctx, Map<String,Object> values);

    /** 读。缺行返回空 Map，不是异常。 */
    Map<String,Object> load(Ctx ctx);

    /** 改这个段要不要触发重审。**默认 false**，理由见 §七.3。 */
    default boolean triggersReaudit() { return false; }
}

record FieldSpec(String key, String label, Type type, boolean required,
                 String optionsFrom,   // 选项来源：段自己提供的一个只读端点
                 String help) {}

enum Type { TEXT, INT, BOOL, ENUM, REF }   // REF = 引用，选项由 optionsFrom 供给
```

**`optionsFrom` 是这套设计的关键一环**：出品部门的选项来自 `fnb_dept`，
基座给不出、也校验不了。段自己提供一个只读端点，`form-schema` 把地址下发给前端，
校验时由段的 `validate` 负责查引用是否存在。**基座全程不认识 `fnb_dept`。**

# 五 · 一套接口的完整定义

**端点一个不加。** 下表列出段在每个既有端点里的位置：

| 端点 | 段在其中 | 说明 |
|---|---|---|
| `GET /biz/goods` 列表 | 可选带出 | `?withSegments=food` 时带；默认不带（列表页不需要，省一次 N+1） |
| `GET /biz/goods/{no}` 详情 | **一并返回** `segments: {food:{…}}` | 缺段 = 该门店没开那个能力，不是错误 |
| `POST /biz/goods/save` | **入参加一个字段** `segments: {food:{…}}` | 与 `fresh`/`service` 同一口径：**不传 = 不改** |
| `GET /biz/goods/form-schema` | **新增**（唯一的新端点） | 见 §5.1 |
| `POST /biz/goods/{no}/toggle` | 不涉及 | 上下架是公共动作 |
| `POST /biz/goods/{no}/submit` | 不涉及 | 送审是公共动作 |
| `POST /biz/goods/{no}/stock` `/store-stock` | 不涉及 | 沽清就走它，**餐饮不另做沽清接口** |
| `POST /biz/goods/{no}/store-price` | 不涉及 | 门店价是公共能力 |
| `POST /biz/goods/{no}/presale` | 不涉及 | 生鲜截单的免重审旁路（**段的先例，见 §七.3**） |

> **唯一新增的是 `form-schema`。** 它不是"多一个接口"，它是**把今天写死在 b-app 里的
> 三段 `if (type === …)` 挪到后端** —— 不挪，注册段就没有入口。

## 5.1 `GET /biz/goods/form-schema?categoryNo=&storeNo=`

```jsonc
{
  "type": "SERVICE",                    // 由 categoryNo 派生，前端不再自己判
  "common":  [ /* FieldSpec[] */ ],     // 标题、图、履约方式、限购…
  "fixed":   { "service": [ /* durationMin, bufferBeforeMin, … */ ] },
  "segments":[ { "code":"food", "label":"出品设置",
                 "fields":[ {"key":"deptNo","type":"REF",
                             "optionsFrom":"/biz/x/food/dept/options"} ] } ],
  "specs":   [ /* 规格库四层给出的 SALE 维度，形状不变 */ ]
}
```

三件事一次说清：**这个类目是什么品类、有哪些字段、字段的选项从哪来。**
b-app 据此渲染一套表单，**三个行业共用同一个页面**。

# 六 · 作用域：段有两级，不能只有一级

商品域今天已经是**主体级 + 门店级**双层，且是成熟模式：

| 主体级（`entity_no`） | 门店级（`store_no`） |
|---|---|
| `prd_goods` 商品本体 | `prd_store_goods` 门店上架 |
| `prd_sku` 价格与库存基线 | `prd_store_price` 门店价 · `prd_store_stock` 门店库存 |

段必须沿用这两级：

| 段 | scope | 为什么 |
|---|---|---|
| SERVICE 段（时长、缓冲、资源类型） | **SPU** | 「面部护理 60 分钟」是这个项目的属性，不是这家店的 |
| 餐饮段（出品部门、做法模板、上菜顺序） | **STORE** | 同一主体两家店的厨房分区不同；总店有水吧、分店没有 |

**只做一级会怎样**：只做 SPU 级，连锁餐饮的分店没法各自配部门；
只做门店级，美业每开一家分店都要重配一遍时长。**两级都要，由段自己声明。**

# 七 · 三条链路：校验、事务、重审

## 7.1 校验链（顺序固定，先拦公共的）

```
① 作用域    BizContext.requireMerchantNo() —— 路径与入参一律不接受 merchantNo
② 公共字段  标题非空、图数量、履约方式取值域（Fulfillments）、支付方式（PayModes）
③ 类目派生  categoryNo → type；stdNo 有值时类目与 optionCode 以标准品为准
④ 固定段    只在品类匹配时写入，不匹配则**静默忽略**（既有行为，不改）
⑤ 注册段    a) 门店开没开 capability → 没开就拒收（不是忽略，见下）
            b) 段码是否注册 → 未注册拒收
            c) 字段是否在 schema 白名单 → 不在拒收
            d) 段自己的 validate（引用完整性在这里）
```

**⑤a 为什么是"拒收"而不是"忽略"**：固定段不匹配品类时忽略是既有行为（给 b-app 容错），
但注册段是**能力驱动**的 —— 没开能力却收到了段数据，说明前端拿的是过期的 schema，
静默忽略会让商家"配了没生效"且不报错，那正是最难查的一类问题。

## 7.2 事务

**基座商品写入与所有段的 `save()` 在同一个事务里。**
段写失败 → 整单回滚。理由与行业附属表同一条：不同事务会出现
「商品建了但段没写上」，而它在两边都看不出异常。

## 7.3 重审：段默认不触发

商品保存会把 `on_sale` 置 false 送重审，过审时用 `pending_on_sale` 放回上架意向。
**段不该走这条路** —— 改一次出品部门等于让这道菜下架一次。

既有先例就在旁边：`POST /biz/goods/{no}/presale`
「只改截单与到货说明（生鲜）。**不触发重审、不下架** —— 生鲜商家每天晚上定明天的截单，
走 `/save` 的话改一次等于停一天生意」。

所以：**`triggersReaudit()` 默认 false**；确有需要（例如服务时长从 60 改成 30，
买家看到的东西变了）的段字段，由段显式声明 —— 且那是**平台审核策略**，不是技术选择（§十四）。

# 八 · 三行业逐字段归属

**判据两条**：① 零售也要用吗？② 它的选项/校验依赖行业自有对象吗？

| 字段 | 零售 | 餐饮 | 美业 | 归属 | 依据 |
|---|:--:|:--:|:--:|---|---|
| 标题 / 图 / 详情 / 类目 / 规格 / SKU / 价格 / 库存 | ✅ | ✅ | ✅ | **公共** | — |
| 履约方式 `fulfillments` | ✅ | ✅ | ✅ | **公共** | 可外卖 = 含 `EXPRESS`/`MERCHANT_DELIVERY`；可上门 = 含 `APPOINTMENT` |
| 支付方式 `payModes` | ✅ | ✅ | ✅ | **公共** | 四层判定的第 ④ 层 |
| 限购 / 拼团档 / 积分配置 | ✅ | ✅ | ✅ | **公共** | — |
| 商品参数（产地、材质） | ✅ | ○ | ○ | **公共 PROP** | 给买家看的 |
| 截单 / 到货 / 按重计价 / 产地 | ✅ | ✅ | — | **FRESH 段（已有）** | 餐饮的称重海鲜直接用 |
| 服务时长 `durationMin` | — | — | ✅ | **SERVICE 段（已有）** | 基座早就有这一列 |
| 前后缓冲 | — | — | ✅ | **SERVICE 段（扩）** | 上门服务都要，家政维修同理 |
| 需要哪类资源 | — | ○ | ✅ | **SERVICE 段（扩）** | 资源模型在基座 |
| 是否必须选技师 | — | — | ✅ | **SERVICE 段（扩）** | 资源预约能力的配置 |
| 组合商品（套餐 / 疗程包） | ✅ | ✅ | ✅ | **公共 B4** | 套餐 ≡ 疗程包 ≡ 礼盒装 |
| 沽清 | ✅ | ✅ | ○ | **门店库存置 0** | 不另建沽清表 |
| 谁能做这个项目 | — | — | ✅ | **`mch_staff_skill`** | 是员工能力，不是商品属性 |
| **出品部门** | — | ✅ | — | **餐饮段（REF）** | 选项来自 `fnb_dept`，且要 JOIN 参与分单路由 |
| **做法模板** | — | ✅ | — | **餐饮段（REF）** | 同上 |
| **上菜顺序**（先上/后上/等叫） | — | ✅ | — | **餐饮段（ENUM）** | 纯标量但只有出品队列有语义 |

**结果**：

| | 段 | 表 | 端点 |
|---|---|---|---|
| 零售 | 无 | 无 | 无 |
| **美业** | **无** | **无** | **无** —— 商品域零行业代码 |
| 餐饮 | 1 个（3 字段） | `fnb_goods_ext`（store 级） | 1 个只读 options 端点 |

# 九 · 存储

```sql
-- 基座：SERVICE 段扩四列（都是标量，且不是美业专属）
ALTER TABLE prd_goods ADD COLUMN buffer_before_min INT NULL;
ALTER TABLE prd_goods ADD COLUMN buffer_after_min  INT NULL;
ALTER TABLE prd_goods ADD COLUMN resource_type     VARCHAR(16) NULL;   -- STAFF/SEAT/ROOM
ALTER TABLE prd_goods ADD COLUMN need_staff_pick   TINYINT NULL;

-- 餐饮段：行业表，store 级，只放引用与队列语义
CREATE TABLE fnb_goods_ext (
  store_no       VARCHAR(32) NOT NULL,
  goods_no       VARCHAR(32) NOT NULL,
  dept_no        VARCHAR(32) NULL,      -- REF fnb_dept，要 JOIN，必须落列
  modifier_group VARCHAR(32) NULL,      -- REF 做法组
  serve_priority VARCHAR(16) NULL,
  PRIMARY KEY (store_no, goods_no)
);
```

**不新建任何通用属性表。** 段的值由段自己落表：
基座的固定段落 `prd_goods` 的列，行业段落行业表的列。
**JSON 只在"确定不会被查询"时使用**，而现有三个字段全都要查。

# 十 · 生命周期：段在哪几步出现

```
建品   POST /save（含 segments）──同事务──> prd_goods + 段表
  │                                          │
  ├─ 段不触发重审，公共字段触发 ──────────────┘
  ▼
送审   POST /submit  ── 平台审核（段的内容是否进审核视图：见 §十四）
  ▼
上架   POST /toggle  ── 过审才允许
  ▼
门店上架 prd_store_goods（公共）
  ▼
日常   改沽清 → /store-stock（公共）
       改出品部门 → /save 只带 segments.food（不下架、不重审）
       改截单 → /presale（既有旁路）
```

**存量兼容**：段缺行 = 默认值，不是错误。
73 个类目、全部存量商品在段落地当天**行为零变化** —— 这与基座阶段 0 的验收标准一致。

# 十一 · 读侧：不需要行业聚合读端点

ADR-020 允许行业提供聚合读端点。**商品域用不上**：
`GET /biz/goods/{no}` 本来就会把已注册段的值一并带出，
C 端 `GET /mp/goods/{no}` 同理（按能力过滤，且**只带 `visibleToBuyer=true` 的字段** ——
出品部门不给买家看）。

于是三行业的商品读也是一套接口。**这比 ADR-020 §1 第 2 条更省一层。**

# 十二 · 边界：这四件事不属于商品域

| 不属于 | 属于哪 |
|---|---|
| 加料展开成独立订单行、指定技师加价成附加行 | **交易域**（下单编排） |
| 用服务时长算占几个时段格 | **预约编排**（读商品属性的人是行业，被读的东西在基座） |
| 出品部门 → 打印机的路由规则 | **打印域** `prn_route`（商品只说自己属于哪个部门） |
| 沽清的每日重置 | **任务域** `JobHandler` |

**一句话判据**：商品域只回答「**这件商品是什么**」，不回答「**拿它怎么办**」。

# 十三 · 测试与闸门

**单元**
- `schema()` 与 `validate/save` 接受的字段集**必须一致** —— 遍历所有已注册段的一条测试；
- 能力关着时提交段数据 → **必须报错**（不是静默忽略）；
- 未注册段码 / 不在白名单的字段 → 拒收；
- 段写失败 → 商品写入整单回滚；
- 段缺行 → `load()` 返回空 Map，详情接口 `segments` 为 `{}`，不抛异常。

**场景**
1. 零售商品全流程（建 → 审 → 上架 → 门店上架 → 改价改库存），**段落地前后结果逐字节相同**；
2. 美业项目：只用公共字段 + SERVICE 段建成，**不装任何行业包**也能建、能约；
3. 餐饮菜品：带 `segments.food` 建成，改出品部门**不下架、不重审**；
4. 跨行业主体：同一主体下餐厅与美容店各建一件商品，列表页一次查询同时返回。

**闸门**
- **`-Pcore-only` 下建品全流程必须全绿** —— 段机制不能让基座依赖任何行业包；
- ArchUnit：基座不许 import 任何 `fnb_*` / `bty_*` 类；
- `form-schema` 契约测试：字段集与 `SaveCommand` 能接受的入参一致（前后端分岔的唯一防线）；
- 撤掉「能力关着拒收段」的判定 → 对应用例必须变红。

# 十五 · 待确认

1. **段的内容进不进平台审核视图？** 出品部门显然不用审；服务时长可能要。
   这是审核策略，不是技术 —— 定了才好决定 `triggersReaudit` 的默认值要不要按字段细化。
2. **C 端可见性**：`FieldSpec` 要不要带 `visibleToBuyer`？本册假设要（§十一），但由谁配、能不能改，要定。

4. **一个主体跨行业时的建品页**：同一个商家既有餐厅又有美容店，
   建品时按**门店**决定出哪个段 —— 那么"还没选门店"的那一步要不要先选店？这会改建品页的第一屏。
