## 0. 先纠正一个口径

这七个域**已经各有一份 TDD，且都标着「已实现」**。逐份读下来，
那个「已实现」指的是 **ops-web 页面 + mock 层已实现**：

| 已有方案 | 覆盖 | 提到建表/端点 |
|---|---|---|
| `TDD-ops-增长与风控` | 风控 · 增长 | ❌ 一次都没有 |
| `TDD-ops-提现与税` | 财务（提现/税） | 几乎没有 |
| `TDD-ops-内容审核与榜单问答` · `TDD-ops-消息素材与系统` | 内容 · 系统 | 几乎没有 |
| `TDD-ops-履约与获客` · `TDD-ops-快递与运费` · `TDD-ops-第三方运力配置` | 履约 | 少量 |
| `TDD-ops-主页模板配置` | 门店经营支持 | 几乎没有 |

**所以缺的不是需求，也不是产品设计 —— 缺的是后端那一半。**
这份文档只写后端：要什么表、什么端点、按什么顺序做。
产品语义一律引用已有的那几份，不重写。

> ⚠️ **T0（先做，5 分钟）**：把那七份 TDD 的状态从「已实现」
> 改成「**前端已实现 · 后端待建**」。
> 一个说自己已实现、而后端一个端点都没有的方案文档，
> 会让下一个人以为这块能用 —— 这与「mock 比后端好看」是同一种错，
> 只是发生在文档层。

## 1. 契约已经写死了，不用再设计

七个域的端点契约**不需要从需求推导** —— ops-web 的 `lib/api/https/*.ts`
里每一条 `client.get/post` 都是一条已确定的契约，
mock 层还给出了每个字段的形状与业务规则。

后端要做的是**照着实现**，而不是另起一套。这一点很重要：
今晚修的一半缺陷都源于两边各自演化（路径单复数、裸数组 vs 分页包、
字段命名 `title` vs `name`）。**契约以 ops-web 现有调用为准**，
后端有异议就改前端，不要两边各写一套再来对。

`docs/api/openapi-ops.yaml`（`npm run gen:api` 生成）是这份契约的机器可读版本，
可直接作为后端的验收清单。

## 2. 分域清单

每节格式：**端点数 · 依赖 · 新表 · 关键约束**。
端点明细见 `openapi-ops.yaml`，此处只列结构与要注意的地方。

### 2.1 系统与配置（`system`）—— 建议第一个做

**7 条**：`appearance` `feature-flags` `rule-texts` `markets`
（`auth-codes` `industries` `service-scopes` **后端已有**）

- **新表**：`sys_setting` 已存在，四类配置全部落它，**不新建表**
- **依赖**：无
- **为什么第一个**：零依赖、全是键值读写、能立刻让「系统」这个 section
  从整域灰掉变成可用；且 `feature-flags` 是后面几个域灰度上线的前提

关键约束：`rule-texts`（协议文本）**要留版本**。
用户同意的是某一版协议，改一次就覆盖掉的话，
「他当时同意的是什么」永远查不回来。

### 2.2 内容与素材（`content`）

**12 条**：帖子审核（含批量）· 问答（回答/隐藏）· 榜单（建/启停）· 素材（建/发布）

- **新表**：`cnt_post` `cnt_question` `cnt_ranking` `cnt_material`
- **依赖**：审核动作要写审计日志（`audit:view` 那条链路已有）
- **关键约束**：
  - **批量通过要逐条留痕**。批量是操作方式，不是审计粒度 ——
    出事时要能回答「这一条是谁放过去的」
  - 审核决定必须带原因（与既有 `reason` 必填口径一致）

### 2.3 风控（`risk`）

**7 条**：风险事件（列表/处置）· 黑名单（列表/加/申诉）· 拦截规则（读/改）

- **新表**：`rsk_event` `rsk_blacklist` `rsk_rule`
- **依赖**：**归因链路**（2.4）是风险事件的数据源 ——
  已有方案里明确写了「分开做的话风控页只能显示这个用户可疑，
  点不进去看他是怎么被归因的」
- **关键约束**：
  - 三类事件（刷单/异常裂变/恶意退款）**合成一张表**用 `type` 区分 ——
    已有方案的结论，拆三张会让「同时命中几类」看不出来，
    而那恰恰是最该优先处理的
  - 拉黑必须带原因与期限；解除要留痕
  - **风控目前只有 `order:view` 一个权限码**（见 `Perms.java`）。
    这个域落地时要同批加 `risk:govern`，并从 UI 的 `UNIMPLEMENTED` 里移出

### 2.4 增长与归因（`growth`）

**6 条**：归因规则（读/改）· 归因链路（查）· 裂变活动（列表/建/启停）

- **新表**：`grw_attribution_trace` `grw_fission_campaign`；归因规则落 `sys_setting`
- **依赖**：**埋点**。已有方案里写明「归因链路的真实数据来自埋点，
  mock 只造了三种典型样本」—— 没有埋点，这个域做出来是空表
- **关键约束**：与 [ADR-004](./ADR/ADR-004-增长模型从孵化团长转向商家自带客流.md) 一致，
  主路径是门店分享而非裂变玩法；`P-9.1` 的店铺码归因规则**仍标着未拍板**

> **这个域的前置是埋点，不是后端 CRUD。** 建议先确认埋点方案，
> 否则做完是一组永远查不出数据的接口。

### 2.5 门店经营支持（`store`）

**7 条**：门店页审核（列表/裁决）· 门店码 · 获客数据 · 装修模板（列表/建/启停）

- **新表**：`str_page_audit` `str_template`；门店码与获客数据**不建表**（见下）
- **依赖**：门店主数据（已有）· 归因链路（获客数据要它）
- **关键约束**：
  - **门店码不落表**，按 `store_no` 现算现发 —— 它是门店主数据的投影，
    存一份就会有「改了门店名，码上的名字没变」
  - **获客数据依赖 2.4**。归因没做之前这个 tab 应保持 `UNIMPLEMENTED`，
    而不是返回一组零

### 2.6 履约调度（`fulfillment`）

**14 条**：批次（列表/改状态）· 核销台 · 分拣 · 运单 · 承运商启停 ·
运费模板（列表/建/归档）· 逾期规则

- **新表**：`ffl_batch` `ffl_shipment` `ffl_freight_template`；
  承运商与逾期规则落 `sys_setting`
- **依赖**：订单与核销（已有）· 第三方运力对接（见 `TDD-ops-第三方运力配置`）
- **关键约束**：
  - **运费模板归档而非删除** —— 历史订单要能查到当时用的是哪一版
  - 批次状态机要与订单状态**正交**，不要互相驱动：
    批次是「这一车货到哪了」，订单是「这单到哪了」，
    一个批次里有部分订单被取消是常态

### 2.7 财务（`finance`）—— 建议最后做

**7 条**：进项票（列表/开票/驳回）· 提现（列表/审批）· 税率（读/改）
（`settlements` `split-records` `fee-rules` **后端已有**）

- **新表**：`fin_invoice` `fin_withdraw`；税率落 `sys_setting`（**要版本**）
- **依赖**：结算（已有）· `settle:manage` 权限（已有，今晚给了 FINANCE 岗）
- **关键约束**：
  - **提现是唯一真正划转资金的动作**。它需要的不是一个端点，
    是幂等键 + 状态机 + 对账 + 失败重试。按 `SETTLE_MANAGE` 的既有口径，
    「没有顺手给一下的空间」
  - 税率改动必须留版本与生效时间。按当前税率重算历史结算单，
    会让已经付出去的钱对不上账

## 3. 建议顺序

```
第一批（零依赖，立刻能用）
  系统与配置  ──▶ feature-flags 就位，后面几个域可灰度

第二批（并行）
  内容与素材        履约调度
     │                 │
第三批（有前置）        │
  埋点 ──▶ 增长与归因 ──┴──▶ 门店经营支持（获客）
              │
              ▼
           风控（事件源）

第四批（最重，要资金流程配套）
  财务：进项票 → 提现
```

**四条硬前置**，不满足就不要开工：

1. 增长要**埋点方案**先定
2. 风控要**增长**先有数据
3. 门店获客要**增长**先有数据
4. 财务提现要**资金操作流程**（谁审、双人复核、对账口径）先定

## 4. 每个域的完成定义

一个域算做完，必须同时满足：

- [ ] 端点全部实现，且与 `openapi-ops.yaml` 一致
- [ ] **从 `UNBUILT_DOMAINS` 移出**，剩余缺口逐条登记进 `KNOWN_GAPS`
      —— 这是棘轮守卫最关键的时刻：域一活，页面就看着能用，
      而漏掉的那几条会变成死按钮
- [ ] `perm-map.ts` 里相关 UI 码从 `UNIMPLEMENTED` 换成真实权限码
- [ ] 需要新权限码的（风控、财务审批）在 `Perms.java` 补，
      并给对应角色配上（今晚补的七个角色里有三个在等这个）
- [ ] ops-web 从 mock 切真后端跑通一次，**在浏览器里点一遍**
- [ ] 该域的 TDD 状态更新为「已实现（前后端）」

## 5. 风险

- **最大的风险不是工作量，是「做完一半」**。一个域的端点做了七成，
  页面看着全是活的 —— 而那三成是死按钮，且没有任何报错。
  棘轮守卫（`KNOWN_GAPS`）就是为这一刻准备的，**必须逐条登记，不能跳过**。
- **契约漂移**：后端实现时若觉得 ops-web 的形状不合理，
  要改前端而不是各写一套。今晚踩到的路径单复数、裸数组 vs 分页包
  都是这么来的，症状统一是「接口 200、页面空白」。
- 七个域全做完是**数月量级**，不是一个迭代。这份文档的价值在于
  给出顺序与前置，而不是承诺一次做完。
