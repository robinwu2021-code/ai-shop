# 部署 · 流程与约定（后端 + 前端）

> 2026-08-29 立。此前部署是每次凭记性 ssh 敲一遍，而
> `deploy/tencent/README.md` 里那套「服务器上自构建」**早已不通**
> （私有父 POM 从服务器 `~/.m2` 消失，退回本机打包 scp）。
>
> 这份文档记的不是理想流程，是**今天真出过事的那几处**，以及它们各自被什么挡住。

## 0. 一条命令

```bash
scripts/deploy-backend.sh                 # 从当前 HEAD 打包并上线
DRY=1 scripts/deploy-backend.sh           # 只打包与核对，不切软链、不重启
scripts/deploy-backend.sh --rollback      # 切回上一版并守到 health=200
```

**它不跑测试闸门** —— 那是 `scripts/check-head-compiles.sh`（约 4 分钟）。
脚本会把 HEAD 的提交号打出来，你自己对一下刚才那次闸门跑的是不是同一个。

## 1. 五道防护，各自防什么

| 步骤 | 防的事故 |
|---|---|
| ⓪ 自己找 JDK 21 | **脚本第一次跑就死在这儿** —— 写它的人整晚手动 `export JAVA_HOME`，于是「它当然是配好的」 |
| ① 出发时记一次线上版本 | 08-29 07:55 与 07:57，两个会话先后切了同一个软链，**先推的那版无声消失**，双方都验过「我的包装上了」 |
| ② 从干净 HEAD 副本构建 | 主工作区常有别人未提交的半成品，在那儿打包会把它们一起推上线，而 `git status` 里那些行看起来跟你毫无关系 |
| ③ 新文件名 + MD5 比对 | 覆盖在跑的 jar 会让接口挂起且**不打任何日志** |
| ④ 切换前再看一次，变了就拒绝 | 打包那几分钟正是别人也在推的窗口 |
| ⑤ 守到 `health=200` 才返回 | 08-28 那次 `health=000`，人被新话题岔开走了，**线上挂了六分钟没人知道** |
| ⑥ 验进程真的在跑那个提交 | 切软链与「进程在跑它」是两件事 |

## 2. 排队：服务器上的锁

`$REMOTE_DIR/.deploy.lock`，**用 `mkdir` 不用 `flock`**。

`flock` 只在持有它的那条 ssh 命令存活期间有效，而部署脚本的 ssh 立刻返回 ——
锁在获取的下一毫秒就释放了，整个部署期间等于无锁，**而日志照样打印
「已拿到部署锁」**。第一版就是这么写的。`mkdir` 是原子的，且一直存在到显式删除。

- 抢不到锁 → 打印**持锁者**（谁、哪台机、什么时候开始），退出码 1
- 锁超过 30 分钟 → 提示可能是崩掉没放锁，给出清理命令，**但不自动抢**：
  自动抢会把我们要防的并发又放回来
- 拿到锁的**下一行**就装 `trap`：中间隔任何一步，那一步失败就会把锁漏在
  服务器上，而下一个人看到的是「有人正在部署」——一个不存在的人

锁挡的是走脚本的人；第 ①④ 两次比对挡的是**手动 ssh** 的人 ——
08-29 那次覆盖恰恰是手动敲的，锁拦不住它。两道都要。

## 3. 版本标识：三处，且必须能互相对上

| 位置 | 形式 |
|---|---|
| jar 文件名 | `shop-app-<时间戳>-<短SHA>.jar` |
| `/actuator/info` | `build.gitSha` |
| `$REMOTE_DIR/deploy.log` | 时间 / 包名 / 提交 / 谁 |

SHA 由部署脚本 `-Dgit.sha=` 传进 Spring Boot 自带的 `build-info`，**不引额外插件**
（`git-commit-id` 不在本机 `~/.m2`，而构建是离线的）。附带好处：文件名里的 SHA
与 `build.gitSha` **来自同一个变量**，天然不可能对不上。

**判据**：

```bash
curl -s http://<host>/actuator/info | grep gitSha     # 进程在跑的
ssh <host> readlink /opt/ai-shop/shop-app.jar          # 软链指向的
```

两者不一致 = **换了包但没重启**，或**重启失败仍在跑旧包**。这两种过去只能靠猜，
而它们正是「我明明部署了怎么没生效」的两大来源。部署脚本第 ⑥ 步会自动比这一条。

手工 `mvn package` 出来的包，`gitSha` 是 `unknown` —— 那也如实反映了
「这个包不是走部署流程出来的」。

> ⚠️ **公开暴露的取舍**：`/actuator/info` 经 nginx 是公开可达的
> （2026-08-29 实测 200），提交号会对外可见。这是有意识的选择：换来的是
> 任何人（包括监控）都能一句话问出线上版本。不接受的话，把 `management.
> endpoints.web.exposure.include` 收回只留 `health`，改从 jar 文件名与
> `deploy.log` 查版本，代价是每次都要 ssh。

## 4. 回滚

```bash
scripts/deploy-backend.sh --rollback
```

目标取自服务器 `deploy.log` 的倒数第二行。做成一条命令而不是打印提示让人现场拼 ——
**人在出事那一刻最不该做的就是拼 ssh 命令**。

`deploy.log` 是 2026-08-29 才开始记的，在那之前的版本回滚要手动指定包名。

## 5. 保留策略

保留**最近 5 个 + 当前软链指向的那个**（即使它已排在 5 名之外）。

少了后半句会出事：某次回滚到旧版之后，下一次部署会把脚下那个删掉。

## 6. 前端（ops-web / c-app / b-app）

```bash
scripts/deploy-frontend.sh ops-web        # 或 c-app / b-app
DRY=1 scripts/deploy-frontend.sh c-app    # 只构建与自检，不上传
```

与后端同一套规矩，几处不同：

- **锁按 app 分**（`.deploy-<app>.lock`）—— 三端之间没有共享资源，不必互相阻塞
- **版本标识是产物根目录的 `VERSION`**（`sha` / `built` / `app`），
  `curl http://<host>/ops-web/VERSION` 即可读。此前产物里**没有任何东西**
  能说明它是哪个提交构建的：ops-web 有个 Next 的 buildId，但那是内容哈希，
  对不回 git 提交，所以 08-28 判断「落后几个提交」只能靠 `mtime` 加 `git log` 反推
- **校验比对内容，不看状态码**。nginx 那几条 `location` 都带
  `try_files ... /index.html` —— `VERSION` 不存在时会回落到首页并返回 **200**。
  只看状态码是假绿。（这条是拿真实的前后两态验过的：部署前读同一个 URL 得到
  HTML，部署后读到 `sha=`。）
- **备份留最近 3 份**。08-29 一查已经堆了 17 个、314M；清到 3 份后 248M。
  再往前的版本 git 里有，重新构建比留着更可靠 —— 那些旧备份目录不带任何版本
  标识，光看名字分不清里面是哪个提交
- **属主用数字 `uid:gid`**。第一版写 `stat -c '%U:%G'`，而这些目录的属主是
  uid 501（本机用户），服务器上没有这个账号，`%U` 返回 `UNKNOWN`，chown 失败。
  失败的位置最坏：rsync 已落地、校验和 deploy.log 都还没跑，于是
  **部署其实成功了、脚本却报失败** —— 照着去回滚会把好版本退掉。
  由此也定了一条：**分清哪些失败必须停（rsync）、哪些不该停（chown）**，
  别把每一步都用 `&&` 串成同等重要

## 7. 什么时候不该部署

- 闸门没绿。脚本不替你跑闸门，也不替你判断。
- 出发点变了。脚本会拒绝，**别去 `rm -rf` 锁然后强推** —— 先问是谁推的、要不要保留。
- 只有你一个人能验的东西没验。部署完成不等于功能正确：脚本能验到的是
  health、进程版本，验不到任何业务行为。
