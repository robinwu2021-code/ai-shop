# 积分订单事件契约（第三阶段 C1）

状态：契约与定向测试已实现；尚未接入真实订单生产者。沿用 pay 内独立积分模块与门店账务维度，不开启真实资金或生产任务。

## 源事件边界

PointsOrderEvent 是源订单事件的冻结归属信封，包装一个既有 SourceFactsPort.Fact，不新增平行积分状态机。信封保存 orderNo、subOrderNo、merchantNo、storeNo、userNo、typeCode、currency、sourceVersion、occurredAt；Fact 保存补扫序号与唯一载荷。eventNo 沿用原载荷，重试不生成新号。

门店始终是结算和退款边界，merchantNo 用于归属验证。生产者必须从持久化订单与支付快照取值，校验子单、门店、商家和用户关系及积分类型币种，不能相信客户端传入的关联编号。DTO 校验一致性，不能代替权限、支付成功证据或订单存在性校验。

| 原业务事实 | 既有载荷 | 完成条件与范围 |
|---|---|---|
| 支付明确成功 | lifecycle PAID | 可信支付核验后，冻结子单商品金额与逐行范围；随后按独立 earning 事件发放 |
| 购物返分 | earning GrantCommand | 必须包含同店同商家原 PaymentSnapshot；规则按受理时点冻结，明确零规则不可改成兜底 |
| 未付款取消/异常关闭 | lifecycle CANCELLED | 必须确认未付款；支付结果未知时继续查原支付号，不能仅凭订单超时声明取消 |
| 订单结算终局 | lifecycle FINALIZED | 只处理子单剩余积分；不能代替退款责任关闭 |
| 部分/全额退款现金环节明确完成 | refund RefundConfirmationFact | 绑定不可变 preparation/inputHash 与可信退款支付号；逐行累计范围由原准备快照引用，不按当前商品或规则重算 |
| 合法零现金退款完成 | zeroCash ZeroCashCompletionFact | 门店、币种、版本、发生时间一致；净现金必须零；仍需原准备版本与授权证明核验 |
| 售后窗口与资金责任关闭 | closure RefundClosureFact | 无未结售后且资金终局，窗口关闭时间明确；关闭范围为整张子单，不能用普通 lifecycle REFUND_CLOSED 绕过 |

lifecycle 仅允许 PAID/CANCELLED/FINALIZED。现有枚举中的 REFUND_SUCCEEDED/REFUND_CLOSED 不作为通用成功捷径，退款和责任关闭必须走专用证明载荷。每个信封恰好一种载荷；缺载荷或多个载荷同时存在均拒绝。

## 版本、幂等和乱序

- 同一业务转换的 eventNo、源版本、载荷、发生时间固定；网络重试和补扫复用原记录。
- 同号同载荷按现有 Inbox 幂等处理；同号不同正文是冲突，不覆盖旧记录。
- 同子单同类事实按 sourceVersion 比较：低版本保留为 STALE，同版本不同正文冲突；新版本交给既有积分状态机，不直接覆盖余额。
- 取消先到后拒绝新占用；退款先到和发放后到按累计退款快照处理。不能假设消息按支付、发放、退款、终局顺序到达。
- occurredAt 是原业务事实发生时间；消费时间、重试时间另行留痕，不能覆写。会计日期由资金/市场规则推导，不用消费者机器默认时区。
- 未知事件类型、门店、积分类型或缺少权威证据，失败关闭并留痕；资金 UNKNOWN 仅回查原票，不换号重付。

## 持久化与补扫约束（后续 C2/C3 实现）

源订单事务必须将冻结信封与业务状态一同写入持久化 Outbox；事务提交后才投递。pay 先写 Inbox 再异步处理，远程资金调用不放在源订单或 pay 长事务内。

SourceFactsPort.scan 必须读取同一份不可变源记录，不能用当前订单/商品状态拼装历史事件。单纯以自增主键最大值推进游标不安全：较小序号事务晚提交可能永久漏扫。实现应提供可证明的连续可见水位或持久化逐事件投递/确认机制，并测试“低序号晚提交、高序号先提交”；C1 本身不提供这个数据库适配。

## 当前调用点与后续实现顺序

### 接线与脱离约束（2026-10-18 补充）

订单基本链路必须能够在不接入积分时独立完成下单、支付、取消和纯现金退款。订单只调用统一的积分接入门面，门面负责接线状态、可选实现和订单绑定判断；订单业务代码不散落积分 Bean 查找、开关和异常吞噬。保持 pay 内业务模块，不拆独立 jar，不启动旧积分引擎兜底。

接入模式与积分类型本身的生命周期分开：

| 接入模式 | 新订单 | 已受理积分交易 | 可否移除处理实现 |
|---|---|---|---|
| DETACHED 未接线 | 不占用、不承诺返分，按正常纯现金价格交易 | 有存量绑定时不能使用空实现跳过 | 仅在没有存量义务时允许 |
| ACTIVE 已接线 | 按门店与场景受理积分，冻结接入版本和交易快照 | 按原绑定处理 | 否 |
| DRAINING 停止新增、存量收尾 | 不新增占用或返分承诺 | 继续支付确认、释放、已承诺发放、退款、结算、补扫和 UNKNOWN 原号恢复 | 否；收尾完毕才允许完全脱离 |

关闭接线立即影响之后的新受理；已受理交易不会被改为纯现金。进入完全脱离前，必须核查未决占用、已承诺返分、未投递/未消费事件、退款/结算、资金在途与UNKNOWN等义务。只看接口调用量为零或任务暂时空闲，不足以判定可以移除实现。

接线状态支持运行时配置，以门店为最小灰度维度，并可按场景分别控制新增发放和核销。当前 `shop.points.enabled` 是启动配置，新接线门面不能把它当成运行时动态开关；上述三模式尚待实现，不代表已有开关已满足此要求。

#### 受理、故障与价格边界

- 下单前未接线时，quote明确返回不可用/不参与，不写积分数据；前端隐藏抵扣入口或展示不可用。按纯现金计算并展示应付金额，不制造成功流水。
- 尚未受理任何积分承诺时，积分不可用可走纯现金路径；若价格较用户确认结果变化，须返回重新确认，不能静默增加支付金额。
- 一旦 hold 已提交或结果未知，不得捕获超时后切换纯现金、生成新 hold 或重复扣减。按原幂等号查明结果，明确释放后才允许重新报价。
- 支付后返分用可靠事件异步处理，积分消费失败不撤销已确认的现金支付；已冻结的发放承诺保留待处理，不因关开关而丢弃。
- 已绑定积分的退款、释放、结算仍要求正确收尾。服务不可用时可进入明确待处理状态，不能假装积分已退、已释放或已清偿；这类交易不能承诺完全不受积分故障影响。
- 非积分订单不写积分专属事件、不触碰积分表；已参与订单必须可靠保存绑定与源事实。需要写入的事实失败不能吞异常后提交一个缺失恢复证据的订单状态。
- 接入决策与 hold/承诺建立必须定义并发顺序：关闭前已受理者按绑定继续，关闭后未受理者拒绝新增；不能只在报价时检查一次开关。

#### 订单绑定与可选实现

订单按门店子单冻结是否参与、类型、接入配置版本、规则/协议、积分与货币金额、hold/事实标识及原支付路由。关闭或重新接线不能重算这些字段，也不能对停接线期间的纯现金订单追补积分。

空实现只服务于未接线且未绑定积分的订单。接口实现缺失时，纯现金路径可继续；已有绑定必须返回明确不可处理状态并留痕，不能通过默认零值、no-op或旧引擎掩盖义务。完整应用编译仍保留公共SPI依赖，“可脱离”首先是业务运行路径隔离，不承诺随意删除代码包后所有现有 Bean 都能启动。

接线、停止新增和重新接线均记录操作人、原因、配置版本与时间。上线前验证已有负债与处理能力，资金通道和生产任务另行受控，不能因接线动作自动开启。

#### 接线验收用例

1. 未接线或无可选实现：下单、现金支付、取消及纯现金退款不访问积分实现，结果与基础订单一致。
2. 接线后按门店灰度：同主体两店可分别参与/不参与，金额与订单绑定准确。
3. 关闭接线与下单并发：新增受理和关闭有确定顺序，不出现无绑定扣分或关后新增承诺。
4. hold超时但实际成功：禁止纯现金降级和换号重扣，恢复时使用原号。
5. 关闭后到达的支付/发放/退款事件：原订单正常收尾，新纯现金订单不补分。
6. 消费者暂停再恢复、重复投递及低序号晚提交：不丢事件、不重复记账。
7. 有任何未决义务时拒绝完全移除处理实现；重新接线后继续原号收尾。
8. 全程使用合成数据和隔离网关，记录订单主链延迟及各测试耗时。

1. OrderServiceImpl 的 deduct/grant/reverse 与 AfterSaleServiceImpl 的 pendingImpactOf 仍经旧 spi.settle.PointsPort；先按门店和订单行冻结来源，不能只按主体分组。
2. 绑定实际支付快照、原路由、原账户版本与积分类型；实现新的 SourceFactsPort 扫描和源 Outbox 生产者。
3. 分别接入 quote/hold/release 与 PAID/earning/finalization，再接售后准备/可信现金确认/closure。
4. 对照新路径清理旧适配器、旧策略门面及 C/B 端旧积分查询；不迁移业务余额，不保留双引擎。
