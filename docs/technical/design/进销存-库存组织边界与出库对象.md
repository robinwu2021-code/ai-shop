# 进销存 · 库存组织边界与出库对象

> 状态：C1 ~ C5、C7 已实现（2026-10-30，TDD-进销存独立服务与多业态 §2.19 / M9；接口见 [进销存独立服务-API文档.md](进销存独立服务-API文档.md)）；C6、C8 后置。
> 本文**取代** [组织关系-ai-shop与独立进销存-业务抽象.md](组织关系-ai-shop与独立进销存-业务抽象.md) §5 和 [组织抽象-技术方案与缺口.md](组织抽象-技术方案与缺口.md) §1.4 中「进销存保存管理范围（`inv_scope`）」的设想。

## 0. 结论

提议：
> 库存服务只保存**最底层、和库存直接相关的组织**；多级组织关系留在业务系统；出库对象按需同步。

**判断：合理，建议采纳。** 但要加三条约束，否则会在「连锁当账本」这里出错：

1. **账本边界 = 库存能互相共享的边界**，不是组织层级。连锁只有在它的门店真的共用一份货（统一仓、互相直接发货、一起预留）时才当账本；否则账本是门店，连锁不进库存服务。
2. **账本粒度在开户时定，之后改它就是并账或拆账**，属于一次库存迁移，不是改个字段。组织调整（门店换连锁）默认**不动账本**。
3. **兄弟门店若有自己的账本，就是「出库对象」，并且关联到对方账本**。货过去是一出一入两张单，不是调拨。

## 1. 库存服务只认四样东西

| 对象 | 是什么 | 由谁定义 | 库存服务知道的 |
|---|---|---|---|
| **系统** | 调用方，如 SHOP / SHAREHUB / FOOD | 平台开户 | 系统码、凭证、档案 |
| **库存组织（账本，Owner）** | 独立持有、独立核算、可整体预留的一份库存 | 业务系统选定 | 外部类型和外部编号（不透明）、写入方、档案 |
| **库位（Location）** | 货在哪：仓、门店、站点、在途、虚拟 | 业务系统同步，服务内维护 | 种类、发货源、外部编号、可选的持有方标记 |
| **出库对象（Target）** | 货出去给谁：商家、站点、人、供应商、兄弟门店 | 业务系统同步 | 类型、编号、上级、状态、版本，可选的关联账本 |

**库存服务不保存**：账户、经营主体、连锁 / 品牌层级、管理空间、授权、收款、结算。这些都由业务系统负责，库存服务只接收它们翻译出来的结果：「这次以哪个账本、在哪个库位、对哪个出库对象操作」。

## 2. 库存组织：怎么选粒度

### 2.1 判定规则

账本是库存一致性的边界。账本内能做到、跨账本做不到的事，决定了它该多大：

| 账本内 | 跨账本 |
|---|---|
| 一次预留可以同时锁多个库位（单据原子性） | 做不到，只能分别锁，失败要补偿 |
| 调拨：同一份货换位置，成本不变 | 一出一入两张单，各自记成本 |
| 一个写入方，同一套档案 | 可以各自不同 |
| 统一估值和盘点 | 各自估值 |

所以：
> **能互相直接发货、需要一起预留的那几处库存，必须在同一本账里。** 再往上的组织层级只是「看」和「管」，不进库存服务。

### 2.2 电商（ai-shop）

| 场景 | 账本 | 库位 | 连锁在库存服务里的身份 |
|---|---|---|---|
| 单店 | **门店** | 门店本身，可以再加后仓 | 不存在 |
| 多店、不共享库存（各进各的货） | **每店一本** | 各自门店 | 不存在；需要汇总看时由业务系统逐本查询 |
| 直营连锁、**统一仓配送**、门店可以互相调货 | **连锁一本**（以连锁库存组织的名义） | 总仓 + 各门店（门店的发货源指向总仓） | 就是账本 |
| 加盟连锁 | **总部一本**（总仓），**每个加盟店各一本** | 各自 | 总部账本；加盟店是总部的**出库对象**（关联到加盟店账本） |
| 现状（存量商家） | **经营主体一本**（`ownerIdOf(entityNo)`） | 主体默认仓 + 各门店 | 不存在 |

说明：
- 「门店，或上级连锁」是对的，但要以**是否共享库存**来选，而不是以组织层级来选。加盟连锁不能当一本账，否则不同主体的货混在一本账里，估值和成本归属都说不清。
- 现状「一个主体一本账」实际上就是「同一主体的门店共享默认仓」这个闭包，**存量不迁**。在库存服务看来，它和「直营连锁一本账」是同一种东西：一个外部类型不同的库存组织。
- 直营连锁如果跨了多个主体（一个集团多张执照）又共用一个仓：可以一本账，货在主体之间移动由业务系统做内部往来。库位上可以挂一个**持有方标记**（`holder_ref`，库存服务不解释它），供业务系统按主体出财务口径的库存报表。

### 2.3 充电宝（ShareHub）

| 场景 | 账本 | 库位 | 出库对象 |
|---|---|---|---|
| 平台运营（现状） | **运营方一本**（`powerbank-<env>`） | 平台仓；如需逐站点盘点，站点也作为库位 | 商家（同步）、站点（上级 = 商家）、领用人、供应商 |
| 多运营方（将来） | 每个运营方一本 | 同上 | 同上 |
| 商家自有设备（如果出现） | 每个商家一本 | 商家的仓 / 站点 | 领用人 |

ShareHub 的商家、站点只是**出库对象**，不是组织层级。平台把货「投放给商家 / 站点」就是一次带出库对象的出库（领用池交接），与现状一致。

## 3. 出库对象：同步，不建模

### 3.1 定义

出库对象 = 货离开本账本之后**去了谁那里**。它的存在只为三件事：
- 单据上写清楚交给了谁；
- 按对象统计发了多少、还有多少在外；
- 有上下级时（站点属于商家）能按上级汇总。

| 字段 | 现状（`inv_target_ref`） | 本方案 |
|---|---|---|
| 类型 / 编号 / 名称 | 有 | 不变；类型由档案的 `targetTypes` 声明 |
| 上级 | `parent_type/parent_ref` | 不变（站点 → 商家；门店 → 连锁也可以用，只用于汇总） |
| 状态 / 版本 | `status`, `source_version`（旧版本忽略） | 不变 |
| **关联账本** | 无 | **新增 `linked_owner_id`**：这个对象在本服务里也有自己的账本（兄弟门店、加盟店） |

### 3.2 各业态的出库对象

| 业态 | 类型 | 来源 | 关联账本 |
|---|---|---|---|
| ShareHub | MERCHANT / SITE（上级 MERCHANT）/ PERSON / SUPPLIER | ShareHub 同步 | 无 |
| 电商：加盟总部出货 | STORE（加盟店） | ai-shop 同步 | 加盟店账本 |
| 电商：门店之间调货（不同账本） | STORE（兄弟门店） | ai-shop 同步 | 兄弟门店账本 |
| 电商：退供应商 | SUPPLIER | 现有供应商主数据 | 无 |

**兄弟门店是不是出库对象，取决于它是否在同一本账里**：
- 同一本账：它是**库位**，货过去走调拨，不需要出库对象；
- 不同账本：它是**出库对象**，带关联账本。

这条规则由业务系统按 §2 的粒度自动决定，门店员工感觉不到差别。

### 3.3 同步规则

- 业务系统**按需同步**：只同步会出现在出库单上的对象，不是全量组织树。
- 幂等：`(owner, system, type, ref)` 唯一，`source_version` 只增不减。
- 停用：停用后不能再作为新出库单的对象，历史单据照常可查。
- 上级只用于汇总，**不做权限**：库存服务不因为「站点属于商家」就允许商家看站点的货，判权由业务系统负责。

## 4. 跨账本出货：关联账本的一出一入

关联了账本的出库对象（兄弟门店、加盟店），货过去走**成对单据**：

```
A 账本  出库单(TRANSFER_OUT / SUPPLY_OUT, 对象 = 门店B)  ──生成──▶  B 账本 待收入库单(TRANSFER_IN / SUPPLY_IN)
         扣 A 的在手                                          B 确认收货（可有差异）才入 B 的在手
```

| 规则 | 说明 |
|---|---|
| 关联 | 两张单共用一个 `transfer_ref`；A 的出库单号写在 B 的入库单 `basis` 上 |
| 在途 | 出库过账后、收货前，货已离开 A 的在手、尚未进入 B 的在手；「已发未收」由成对记录的 `SHIPPED` 状态表达（实现时没有再经 TRANSIT 库位，见 TDD §6 M9） |
| 收货差异 | B 收多收少按 B 的收货差异流程；差异回传 A，生成 A 侧的差异单 |
| 成本 | 目标：B 的入库成本 = A 出库成本（直营内部往来）或业务系统给的供货价（加盟）。**本版未做**：B 入库不带单价，按 B 的估值方式处理 |
| 写入方 | 成对单据由**服务内**生成，要求 B 的写入方是 SVC（过账时判定，否则 `NOT_WRITER`）。任一方仍由宿主内嵌写时，由业务系统分两次调用普通出库和入库 |
| 钱 | 库存服务不管。加盟供货的应收应付由 ai-shop 结算，库存服务只回传「已发 / 已收 / 差异」事件 |

这取代了之前设想的「跨账本供货单」和「范围凭证代写」，也不需要 `inv_scope`。

## 5. 业务系统负责什么

| 职责 | ai-shop | ShareHub |
|---|---|---|
| 组织 → 账本 / 库位映射 | 门店 / 连锁 / 主体 → 账本 + 库位（`StockOrgResolver`，见 §7） | 运营方 → 账本 |
| 出库对象同步 | 兄弟门店、加盟店、供应商 | 商家、站点、人 |
| 判权 | 账户授权 → 能动哪本账的哪些库位（现有 `locationsOfStores`） | 自有账户体系 |
| 多账本汇总 | 「连锁看所有门店库存」= 按连锁成员逐本查询或批量查询，在业务侧汇总 | 不需要（一本账） |
| 组织变更 | 门店换连锁：**账本不动**，只更新出库对象的上级。涉及并账或拆账时，按 §6 编排 | 商家、站点变更即同步 |
| 资金与财务口径 | 供货结算、按主体的库存报表（用 `holder_ref`） | 押金、分润 |

库存服务只需要提供一个**批量查询**：系统凭证 + 多个账本外部编号，一次返回余额和汇总。它不知道这些账本为什么被一起查。

## 6. 账本粒度变更：并账与拆账

只在业务形态真正改变时发生，例如单店加入直营连锁、开始共用总仓，或者直营转加盟。

| 操作 | 步骤 | 库存服务提供 |
|---|---|---|
| **并账**（门店账本 → 连锁账本的一个库位） | 冻结门店账本写入 → 盘点 → 门店账本按结存出库（`MERGE_OUT`）→ 连锁账本在新库位入库（`MERGE_IN`，带原成本）→ 门店账本停用（只读） | 冻结（复用写入方 FLIPPING 闸）、成对单据、只读停用 |
| **拆账**（连锁账本的库位 → 独立账本） | 反向同理 | 同上 |
| 历史 | 原账本只读保留，单据和流水不迁移 | 账本状态 `ARCHIVED` |

**不做**的事：在账本之间搬历史流水，或把两本账的历史合成一本。

## 7. 相对现状要改的东西

| # | 改动 | 层 | 说明 |
|---|---|---|---|
| C1 | `inv_owner` 增加 `external_type` | 表 | 外部编号的类型（STORE / CHAIN / ENTITY / PLATFORM …），库存服务**不解释**，只用于唯一性 `(system, external_type, external_ref)`，避免不同层级的编号撞号。存量全部回填为 `ENTITY`（SHOP）或 `PLATFORM`（SHAREHUB） |
| C2 | `inv_target_ref` 增加 `linked_owner_id` | 表 | 同系统内的另一本账；同步时由业务系统给出对方账本的外部类型和编号，服务端解析 |
| C3 | 成对单据 | 领域 + 端点 | 出库对象带关联账本时：出库过账后生成对方的待收入库；收货差异回传；`transfer_ref` 关联。现有 `TransferService` 只能在账本内调拨，保持不变 |
| C4 | `inv_location` 增加 `holder_ref`（可空） | 表 | 业务系统的持有方标记，库存服务只存储、只按它过滤 |
| C5 | 多账本批量查询 | 端点 | 系统凭证 + 外部编号列表 → 各账本余额和合计；每次上限 N 本 |
| C6 | 账本归档与并账 / 拆账 | 领域 + 管理端点 | 见 §6；可以放在最后做 |
| C7 | 电商档案 `shop.json` | 档案 | `targetTypes` 增加 `STORE`（上级可为 CHAIN）；`outboundPurposes` 增加 `SUPPLY_OUT`（加盟供货，需要对象 STORE） |
| C8 | ai-shop 侧 `StockOrgResolver` | 业务系统 | 把「门店 → 账本 + 库位」的决策从各处的 `ownerIdOf(entityNo)`（22 个文件）收拢到一处。存量商家返回主体账本，**行为不变**；新的连锁或单店形态按 §2.2 返回 |
| — | 取消 `inv_scope` / 范围凭证 / 保管方字段 | 方案 | 由「业务系统汇总 + 批量查询 + 出库对象」替代。ShareHub 站点作为库位时，「谁保管」用站点的上级商家（出库对象）表达，不再另加 `custodian_ref` |

顺序：
1. C1、C8：不改变行为，先把映射收拢；
2. C2、C3、C7：兄弟门店、加盟出货；
3. C5；
4. C4；
5. C6。

## 8. 风险与取舍

| 风险 | 应对 |
|---|---|
| 连锁当账本后，门店退出连锁 | 默认账本不动（门店仍是连锁账本的库位，由业务系统停止把它算作连锁成员）；确实要分离时走拆账。在连锁开账前，业务侧要把这一点讲清楚 |
| 跨账本预留做不到原子 | 规则 2.1 已经避免：需要一起预留的必须同账。跨账本只做「发货—收货」，本来就不要求原子性 |
| 业务系统汇总多账本，性能差 | C5 批量查询；连锁维度的报表由业务侧按日汇总入库，不实时扫描 |
| 外部类型不透明，各宿主随意取值 | 设想：档案里声明允许的 `ownerTypes`，开户时校验。**本版未做**：服务不解释类型，暂无校验需求 |
| 主体一本账（存量）与门店一本账（新）并存 | 两者在服务里是同一种对象；差别只在 ai-shop 的 `StockOrgResolver` 里，按商家形态返回。不追求统一迁移 |

## 9. 待确认

1. 新入驻的单店，账本按**门店**开，还是沿用**主体**？建议沿用主体：一个主体通常就是一家店，而且将来开分店可以共享默认仓，不用并账。
2. 直营连锁统一仓：账本挂在**连锁**上，还是挂在**总部主体**上？建议挂在连锁上，`external_type=CHAIN`，库位带 `holder_ref` 标出各店的主体。
3. 门店之间调货（不同账本）：是否需要对方确认收货才入账？建议需要，与加盟供货共用同一条流程。
4. ShareHub 站点是否升级为库位（逐站点盘点）？这一条沿用之前的待确认事项。
