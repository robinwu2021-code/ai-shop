## 一、结论先行：不用新建表

数据模型早就够用——`mch_account` 是账号↔证照的多对多关联表（`entity_no` + `user_no` + `is_owner`），
`mch_store.entity_no` 已经是外键。这次要改的是**请求层怎么解析"用户现在在哪张证照下"**，
以及补几个跨证照查询的接口。数据库改动只有两条数据值调整，没有 DDL。

---

## 二、核心机制改动：身份解析从「取第一个」改成「按门店反查」

### 2.1 现状（复核确认）

- `BizContextFilter`（`backend/shop-base/.../auth/BizContextFilter.java:47-58`）**每个请求都重新解析**，
  用 `ThreadLocal` 存一次性的 `BizContext`，没有跨请求缓存——切换这件事本来就是无状态的，改造成本低。
- `BizIdentityResolverImpl.resolve(userNo)`（`backend/shop-merchant/.../BizIdentityResolverImpl.java:109-224`）
  查出账号名下所有 `mch_account` 成员行后，**固定取 `memberships.get(0)`**（按 `is_primary desc, id asc` 排序），
  在此基础上一次性算出这张证照的 `storeNos`/`rolesByStore`/`permsByStore`/`owner`。
- `X-Store-No` 请求头在 `resolve()` **之后**才被读到（`BizContextFilter.withRequestedStore`），
  且 `BizContext.withStore()` 只窄化 `currentStoreNo` 一个字段，不会换掉整套证照绑定的权限包。

**结论**：今天的架构里，"选哪张证照"和"选哪家店"是两件独立的事，且前者压根不受请求控制——
这正是要改的地方。

### 2.2 改法

把 `X-Store-No` **提前**到身份解析这一步，让 `resolve()` 有能力"按店反查证照"：

```java
// BizIdentityResolver 接口签名改动
BizContext resolve(String userNo, String requestedStoreNo);   // 原来只有 userNo

// BizContextFilter：调整读取顺序——先读请求头，再解析身份
String requestedStoreNo = req.getHeader(STORE_HEADER);
BizContext ctx = resolver.resolve(userNo, requestedStoreNo);
```

`resolve()` 内部新增一条分支（其余逻辑不变）：

```
requestedStoreNo 非空？
  ├─ 是 → 按 storeNo 查 mch_store.entity_no，拿到目标证照
  │        校验：mch_account 里是否存在 (user_no=当前人, entity_no=目标证照) 的成员行
  │          ├─ 存在 → 用这张证照重新走一遍现有的「算 storeNos/rolesByStore/…」逻辑
  │          └─ 不存在 → 当成没传，走下面的默认分支（不报错——见 §2.3 安全边界）
  └─ 否 → 原逻辑：取 memberships.get(0)（primary 优先）
```

**这一步是唯一的安全边界，必须重点测试**：`X-Store-No` 是客户端可控的请求头，
如果只按 `storeNo → entity_no` 反查就换权限包，等于「猜一个别人的门店号就能拿到别人证照的权限」。
校验点是「这个 storeNo 反查出的 entity_no，当前登录人是否在 `mch_account` 里有这张证照的成员行」——
不是成员就静默回退到默认证照，**不抛错**（避免把"猜号失败"和"系统故障"混成一种反馈，也避免给攻击者
一个可用来枚举有效 storeNo 的判据）。

### 2.3 `BizContext.withStore()` 废弃，改由 `resolve()` 一次性给全套

现在 `withStore()` 只改 `currentStoreNo`，因为过去只有一张证照，其余字段不会变。
证照可能不同之后，`currentStoreNo` 变了，`storeNos`/`rolesByStore`/`permsByStore`/`merchantNo` 全部要跟着变——
所以不再是"resolve 一次 + 事后窄化"，而是"resolve 这一步就把 storeNo 考虑进去，一次性出正确的整套"。
`withStore()` 方法删除，调用方（`BizContextFilter`）改成只调 `resolve(userNo, requestedStoreNo)`。

## 三、接口改动清单

### 3.1 新增

| 接口 | 说明 |
|---|---|
| `GET /biz/stores/mine` | 01 屏用。**不经过 `BizContext.merchantNo`**——直接用 `SecurityUtils.currentUserNo()` 查 `mch_account` 全部成员行，逐张证照取门店列表（owner 给全部，员工只给被授权到的那几家），按证照分组返回。这是唯一一个"故意不吃 BizContext 单证照限制"的接口 |
| `GET /biz/entities` | 03 屏用。查 `mch_account`（`user_no`=当前人，`is_owner`=true）关联的所有 `mch_entity`，带状态（营业中/审核中/未通过）与门店数 |
| `GET /biz/entity/{entityNo}` | 04 屏用。返回证照基本信息 + 收款账户摘要 + 资质证件摘要 + 门店列表（只读）。内部拼接 §3.2 里三个既有服务的读方法，不是新业务逻辑 |

### 3.2 扩展（加一个可选 `entityNo` 参数）

| 接口 | 现状 | 改动 |
|---|---|---|
| `GET/POST /biz/merchant/profile` | 隐式用 `BizContext.requireMerchantNo()` | 加 `entityNo` 可选参数；传了就走 §3.3 的 owner 校验后使用它，不传保持原行为 |
| `GET/POST /biz/qualifications` | 同上 | 同上——「查看/更新营业执照」复用这个接口（`type=BUSINESS_LICENSE`），**不需要单独的营业执照接口**，`mch_qualification` 表本来就把执照当一种资质文档存 |
| `GET/POST /biz/merchant/payment` | 同上 | 同上 |
| `POST /biz/store/create` | 门店固定挂在 `BizContext.merchantNo` 下 | 加 `entityNo` 可选参数（02 屏"选/建证照"用）；传了就走 owner 校验后挂在指定证照下，不传保持原行为（挂当前证照，兼容存量单证照账号） |

**统一的 owner 校验**：新增一个共用方法，控制器层调用，不下沉进各个 service：

```java
// BizContext 新增
String requireOwnedEntity(String entityNoParam) {
    if (entityNoParam == null || entityNoParam.isBlank()) return requireMerchantNo();  // 原行为
    boolean owns = accountMapper 存在 (user_no=当前人, entity_no=entityNoParam, is_owner=true);
    if (!owns) throw BizException.of(ErrorCode.FORBIDDEN);
    return entityNoParam;
}
```

改动只发生在控制器方法体的第一行（把 `BizContext.requireMerchantNo()` 换成
`BizContext.requireOwnedEntity(req.entityNo())`），service 层签名不用动——它们本来就接收
`merchantNo` 作为显式参数，不关心这个 `merchantNo` 是"当前证照"还是"我拥有的另一张证照"。

### 3.3 权限：直接复用 `STORE_ADMIN`，不加新权限码

`BizPerms.STORE_ADMIN`（`biz:store:admin`）已经**不允许自定义角色勾选**
（`BizPerms.assignableCodes()` 显式排除，`backend/shop-base/.../BizPerms.java:157-161`），
界面与后端两道都拦。这个码的语义（"建店、停用、挂收款号、管员工"）跟"建证照/管证照"是同一档敏感度，
§3.1/3.2 所有新增与扩展接口统一挂 `@PreAuthorize("@perm.canBiz(STORE_ADMIN)")`，
天然满足"只有老板能建店/管证照"，不用引入新权限码。

## 四、数据库改动

**没有 DDL。** 两条数据值调整：

| # | 改动 | 方式 |
|---|---|---|
| 1 | FREE 套餐门店配额 1 → 3 | `sys_merchant_plan_def` 表 FREE 行 `store_quota` 字段，一条 `UPDATE`（migration） |
| 2 | 证照数量上限 5 | 不落库——`MerchantPortImpl.activate()`（新建证照分支）与入驻申请提交处各加一个计数校验：`count(mch_account where user_no=? and is_owner=true 的不同 entity_no)` ≥ 5 时拒绝。两处都要校验：申请提交时给早期反馈，激活时兜底（防止并发提交多份申请绕过前一道） |

`mch_store`、`mch_account`、`mch_entity` 三张表结构原样不动。

| 阶段 | 内容 | 依赖 |
|---|---|---|
| 1 | `BizIdentityResolver` 改造（§二）+ 越权测试（伪造别人的 `storeNo` 必须拿不到权限） | 无，最先做，这是地基 |

不是接口数量多寡。

## 七、测试要点

- 越权：账号 A 传账号 B 名下一个真实存在的 `storeNo`，`X-Store-No` 头伪造，确认拿到的还是 A 自己的默认证照，不是 B 的
- 员工（非 owner）的 `X-Store-No` 只能落在他被授权到的门店范围内，即使他知道同证照下其他店的 `storeNo`
- 员工传一个自己完全没有成员关系的证照下的 `storeNo`，静默回退，不报错也不越权
- 单证照账号（现在绝大多数商家）前后端全程无感——`entities.length <= 1` 的短路要覆盖到
- 建店/证照上限（3 家店、5 张证照）：达到上限时前端提前变灰 + 后端兜底拒绝，两处都要测，不能只测前端
- 新证照入驻申请：账号已有 ACTIVE 证照时再交一份新申请不受 `uk_apply_active_owner` 阻塞（已复核确认该约束只挡"同一人同时两份进行中申请"，不挡"已有证照再开一张"）
