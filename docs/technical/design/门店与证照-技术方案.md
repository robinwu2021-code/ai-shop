## 一、结论先行：不用新建表

数据模型早就够用——`mch_account` 是账号↔证照的多对多关联表（`entity_no` + `user_no` + `is_owner`），
`mch_store.entity_no` 已经是外键。这次要改的是**请求层怎么解析"用户现在在哪张证照下"**，
以及补几个跨证照查询的接口。数据库改动只有两条数据值调整，没有 DDL。

## 二、核心机制改动：身份解析从「取第一个」改成「按门店反查」

### 2.1 现状（复核确认）

- `BizContextFilter`（`backend/shop-base/.../auth/BizContextFilter.java:47-58`）**每个请求都重新解析**，
  用 `ThreadLocal` 存一次性的 `BizContext`，没有跨请求缓存——切换这件事本来就是无状态的，改造成本低。
- `BizIdentityResolverImpl.resolve(userNo)`（`backend/shop-merchant/.../BizIdentityResolverImpl.java:109-224`）
  查出账号名下所有 `mch_account` 成员行后，**固定取 `memberships.get(0)`**（按 `is_primary desc, id asc` 排序），
  在此基础上一次性算出这张证照的 `storeNos`/`rolesByStore`/`permsByStore`/`owner`。
- `X-Store-No` 请求头在 `resolve()` **之后**才被读到（`BizContextFilter.withRequestedStore`），
  且 `BizContext.withStore()` 只窄化 `currentStoreNo` 一个字段，不会换掉整套证照绑定的权限包。

**结论**：今天的架构里，"选哪张证照"和"选哪家店"是两件独立的事，且前者压根不受请求控制——
这正是要改的地方。

### 2.2 改法

把 `X-Store-No` **提前**到身份解析这一步，让 `resolve()` 有能力"按店反查证照"：

```java
// BizIdentityResolver 接口签名改动
BizContext resolve(String userNo, String requestedStoreNo);   // 原来只有 userNo

// BizContextFilter：调整读取顺序——先读请求头，再解析身份
String requestedStoreNo = req.getHeader(STORE_HEADER);
BizContext ctx = resolver.resolve(userNo, requestedStoreNo);
```

`resolve()` 内部新增一条分支（其余逻辑不变）：

```
requestedStoreNo 非空？
  ├─ 是 → 按 storeNo 查 mch_store.entity_no，拿到目标证照
  │        校验：mch_account 里是否存在 (user_no=当前人, entity_no=目标证照) 的成员行
  │          ├─ 存在 → 用这张证照重新走一遍现有的「算 storeNos/rolesByStore/…」逻辑
  │          └─ 不存在 → 当成没传，走下面的默认分支（不报错——见 §2.3 安全边界）
  └─ 否 → 原逻辑：取 memberships.get(0)（primary 优先）
```

**这一步是唯一的安全边界，必须重点测试**：`X-Store-No` 是客户端可控的请求头，
如果只按 `storeNo → entity_no` 反查就换权限包，等于「猜一个别人的门店号就能拿到别人证照的权限」。
校验点是「这个 storeNo 反查出的 entity_no，当前登录人是否在 `mch_account` 里有这张证照的成员行」——
不是成员就静默回退到默认证照，**不抛错**（避免把"猜号失败"和"系统故障"混成一种反馈，也避免给攻击者
一个可用来枚举有效 storeNo 的判据）。

### 2.3 `BizContext.withStore()` 废弃，改由 `resolve()` 一次性给全套

现在 `withStore()` 只改 `currentStoreNo`，因为过去只有一张证照，其余字段不会变。
证照可能不同之后，`currentStoreNo` 变了，`storeNos`/`rolesByStore`/`permsByStore`/`merchantNo` 全部要跟着变——
所以不再是"resolve 一次 + 事后窄化"，而是"resolve 这一步就把 storeNo 考虑进去，一次性出正确的整套"。
`withStore()` 方法删除，调用方（`BizContextFilter`）改成只调 `resolve(userNo, requestedStoreNo)`。

## 二·五、无证照开店：占位主体 + 可见性闸门

### 2.5.1 为什么是「占位主体」而不是「门店可以没有主体」

`mch_store.entity_no` 是 **NOT NULL**（`V1__baseline.sql`），而且整个权限模型都挂在
`BizContext.merchantNo` 上——真让 `entity_no` 可空的话，`BizContext` 里 `merchantNo` 为 null，
所有 `/biz/**` 直接 403，爆炸半径覆盖全部 B 端接口。

所以做法是：**建店时同时建一个「待补证照」的主体行**，门店照常挂在它下面。
对商家来说是「我还没交执照」，对系统来说结构完全没变。

```
mch_entity.status 新增取值 PENDING_LICENSE（待补证照）
  ├─ name        = 老板填的门店名
  ├─ legal_form  = null（还不知道是个体户还是公司）
  ├─ 营业执照相关字段全空
  └─ 不建 mch_payment_merchant —— 没证照没法进件
```

补证照 = 对这个**已存在的**主体提交一份入驻申请（`mch_entity_apply.entity_no` 预填占位主体号）
→ 审核通过 → `activate()` 走 `existing != null` 分支，把它就地升级为 `ACTIVE`。
**这条分支现在就有**（原本是给"重复点通过"的幂等重放用的，`MerchantPortImpl.activate():609-621`），
语义上刚好吻合：都是"这份申请对应的主体已经存在，更新它"。不用新写激活逻辑。

⚠️ 待实现时验证：`mch_entity_apply` 创建路径是否允许预填 `entity_no`。
现在只有 `OpsServiceImpl:310` 在审核通过后回填，商家提交时应该是空的——
需要让"补证照"这条提交路径能带上它。

### 2.5.2 第一家店的入口问题

**没有主体的账号调不了 `/biz/store/create`** ——`BizContext.merchantNo` 为空，
`@PreAuthorize` 直接 403。所以"第一家店"不能复用建店接口。

新增 `POST /biz/merchant/quick-start`：不要求 `BizContext`（跟入驻申请一样用
`SecurityUtils.currentUserNo()`），收店名 + 地址，一个事务里建
`mch_entity`（PENDING_LICENSE）+ `mch_account`（owner 行）+ `mch_store`（默认店）+ FREE 档 plan。
**不进审核队列**——没有证照可审，走的不是审核链路。

第 N 家店走的还是 `POST /biz/store/create`（那时 `BizContext` 已经有了），
`entityNo` 传空即"新建一个占位主体"，传值即挂到指定证照下。

### 2.5.3 可见性闸门（必做，且是本次唯一影响买家侧的改动）

`MerchantPortImpl.reachableCommunities()`（`:126-131`）是 **C 端可见性的唯一出口**——
上架写社区池、商家详情可达性、履约全都只认它。它现在只算履约能力 × 地理覆盖，
**完全不看 `mch_entity.status`**。

加一处判断即可：

```java
// reachableCommunities 开头，m == null 那个判断的隔壁
if (!ACTIVE.equals(m.getStatus())) {
    return List.of();   // 未激活的主体（含 PENDING_LICENSE）对谁都不可见
}
```

正因为当初收敛到了这一处，这个闸门只用加一行——调用方一个都不用动。

**副作用要事先讲清楚**：这一行同时会把**今天已经存在的、非 ACTIVE 状态的主体**一起挡掉。
上线前必须先查一遍生产库 `mch_entity` 各状态的分布与对应的在架商品数，
确认没有"本来在正常卖货、但 status 不是 ACTIVE"的存量商家——有的话先修数据再上这行代码，
否则就是一次静默的批量下架。

### 2.5.4 状态与能力对照

| 能力 | 判据 | PENDING_LICENSE | ACTIVE |
|---|---|---|---|
| 建店 / 改店铺资料 | `BizContext` 有 entityNo | ✅ | ✅ |
| 录商品 / 上架 | 现有类目资质闸门 | ✅ | ✅ |
| **对买家可见** | `reachableCommunities()`（§2.5.3 新增） | ❌ | ✅ |
| **下单 / 收款** | 上一条已挡住（看不见就下不了单）+ 进件 `canReceiveMoney` | ❌ | 看进件 |
| 员工管理 / 经营范围 | `BizContext` | ✅ | ✅ |

「能开店 ≠ 能收钱」这句话在 `MerchantPaymentFlowTest:62` 的注释里已经写着了——
这次只是把它往前推了一格：**能建店 ≠ 能开张**。

## 三、接口改动清单

### 3.1 新增

| 接口 | 说明 |
|---|---|
| `GET /biz/stores/mine` | 01 屏用。**不经过 `BizContext.merchantNo`**——直接用 `SecurityUtils.currentUserNo()` 查 `mch_account` 全部成员行，逐张证照取门店列表（owner 给全部，员工只给被授权到的那几家），按证照分组返回。这是唯一一个"故意不吃 BizContext 单证照限制"的接口 |
| `GET /biz/entities` | 03 屏用。查 `mch_account`（`user_no`=当前人，`is_owner`=true）关联的所有 `mch_entity`，带状态（营业中/审核中/未通过）与门店数 |
| `GET /biz/entity/{entityNo}` | 04 屏用。返回证照基本信息 + 门店列表。**不是我名下的 → 403 而不是 404**：它确实存在，只是不属于他；给 404 会让他以为记错了证照号而反复去找。收款账户与资质证件摘要由应用层用既有服务按 `entityNo` 拼上去（跨域拼接不下沉进 merchant 域） |

### 3.2 扩展（加一个可选 `entityNo` 参数）

| 接口 | 现状 | 改动 |
|---|---|---|
| `GET/POST /biz/merchant/profile` | 隐式用 `BizContext.requireMerchantNo()` | 加 `entityNo` 可选参数；传了就走 §3.3 的 owner 校验后使用它，不传保持原行为 |
| `GET/POST /biz/qualifications` | 同上 | 同上——「查看/更新营业执照」复用这个接口（`type=BUSINESS_LICENSE`），**不需要单独的营业执照接口**，`mch_qualification` 表本来就把执照当一种资质文档存 |
| `GET/POST /biz/merchant/payment` | 同上 | 同上 |
| `POST /biz/store/create` | 门店固定挂在 `BizContext.merchantNo` 下 | 加 `entityNo` 可选参数（02 屏"选/建证照"用）；传了就走 owner 校验后挂在指定证照下，不传保持原行为（挂当前证照，兼容存量单证照账号） |

**统一的 owner 校验**：新增一个共用方法，控制器层调用，不下沉进各个 service：

```java
// BizContext 新增
String requireOwnedEntity(String entityNoParam) {
    if (entityNoParam == null || entityNoParam.isBlank()) return requireMerchantNo();  // 原行为
    boolean owns = accountMapper 存在 (user_no=当前人, entity_no=entityNoParam, is_owner=true);
    if (!owns) throw BizException.of(ErrorCode.FORBIDDEN);
    return entityNoParam;
}
```

改动只发生在控制器方法体的第一行（把 `BizContext.requireMerchantNo()` 换成
`BizContext.requireOwnedEntity(req.entityNo())`），service 层签名不用动——它们本来就接收
`merchantNo` 作为显式参数，不关心这个 `merchantNo` 是"当前证照"还是"我拥有的另一张证照"。

### 3.3 权限：直接复用 `STORE_ADMIN`，不加新权限码

`BizPerms.STORE_ADMIN`（`biz:store:admin`）已经**不允许自定义角色勾选**
（`BizPerms.assignableCodes()` 显式排除，`backend/shop-base/.../BizPerms.java:157-161`），
界面与后端两道都拦。这个码的语义（"建店、停用、挂收款号、管员工"）跟"建证照/管证照"是同一档敏感度，
§3.1/3.2 所有新增与扩展接口统一挂 `@PreAuthorize("@perm.canBiz(STORE_ADMIN)")`，
天然满足"只有老板能建店/管证照"，不用引入新权限码。

> **⚠️ 勘误（B2 实施时发现）**：「统一挂」对 `GET /biz/stores/mine` **不成立**。
> 它是**门店切换器**，不是管理页 —— 挂上 STORE_ADMIN 之后，
> 「A 店店长 + B 店店员」这种人一家店都切不了，而那正是多门店授权的主要用途。
> 它与既有的 `/biz/store/list` 是同一性质（那个也刻意不要 `biz:store`），
> 已按 PUBLIC（登录即可）登记进 `BizEndpointPermTest`，
> 范围靠**结果裁剪**保证：店员只拿到 `mch_store_role` 授权到的门店。
>
> `/biz/entities` 与 `/biz/entity/{entityNo}` 按原方案挂 STORE_ADMIN，不变。

## 四、数据库改动

**仍然没有 DDL** —— `mch_entity.status` 是 `VARCHAR(16)`，加一个 `PENDING_LICENSE` 取值
不需要改表结构（枚举在代码里，不在库里）。三张表 `mch_store`/`mch_account`/`mch_entity`
结构原样不动。

两条数据值调整：

| # | 改动 | 方式 |
|---|---|---|
| 1 | 门店配额阶梯上移：FREE 1→3、**PRO 3→10、CHAIN 10→30** | `sys_merchant_plan_def` 的三行 + `mch_entity_plan` 存量快照，`V221__plan_store_quota_raise.sql`。<br>**为什么三档一起抬**：只抬 FREE 到 3，它就和 PRO 相等（PRO 原本正是 3）——门店数量这个最直观的升级理由当场消失。<br>**为什么存量快照也要抬**：`mch_entity_plan.store_quota` 是快照不是每次读定义（防运营下调档位时已开店的商家突然变只读）。只改定义的话，这次放开只对新入驻的人生效，而抱怨"只能开一家"的正是存量商家 |
| 2 | 证照数量上限 5 | 不落库——`MerchantPortImpl.activate()`（新建证照分支）与入驻申请提交处各加一个计数校验：`count(mch_account where user_no=? and is_owner=true 的不同 entity_no)` ≥ 5 时拒绝。两处都要校验：申请提交时给早期反馈，激活时兜底（防止并发提交多份申请绕过前一道） |

`mch_store`、`mch_account`、`mch_entity` 三张表结构原样不动。

## 六、实施顺序

### 6.1 先看清楚：这是两条独立的线

加入"无证照开店"之后，这件事不再是一条线，而是**两条互不依赖的线**，
只在"新建门店"这一个表单上汇合：

```
线 A · 无证照开店         线 B · 多证照
（降开店门槛）            （一个账号多张执照）
      │                        │
   占位主体                身份解析改造
   可见性闸门              跨证照查询
   补证照链路              证照管理页
      │                        │
      └────────┬───────────────┘
               ▼
        新建门店表单
   「挂在哪张证照下」：已有的 / 新建 / 暂不填
```

**A 不依赖 B**：第一家店走 `quick-start`，账号那时只有一张（占位）证照，
根本不需要跨证照能力。
**B 不依赖 A**：多证照切换对 ACTIVE 证照就能跑通。

### 6.2 建议顺序：A 先于 B

| # | 阶段 | 内容 | 依赖 |
|---|---|---|---|
| **A1** | 占位主体 | `PENDING_LICENSE` 状态 + `POST /biz/merchant/quick-start`（§2.5.1/2.5.2） | 无 |
| **A2** | **可见性闸门** | `reachableCommunities()` 加 status 判断（§2.5.3）+ **上线前查存量数据分布** | 与 A1 同批，不能拆开发布 |
| **A3** | 补证照链路 | 入驻申请支持预填 `entity_no`，激活走既有 existing 分支（§2.5.1） | A1 |
| **A4** | 前端 A | 快速开店表单 + 首页「还不能开张营业」blocker + 证照列表「待补证照」态 | A1–A3 |
| **B1** | 身份解析改造 | `resolve(userNo, storeNo)` 按门店反查证照 + **越权测试**（§二） | 无（可与 A 并行） |
| **B2** | 跨证照查询 | `/biz/stores/mine`、`/biz/entities`、`/biz/entity/{no}`（§3.1） | B1 |
| **B3** | 既有接口扩展 | 加 `entityNo` 可选参数 + `requireOwnedEntity`（§3.2） | B1 |
| **B4** | 前端 B | 01 门店选择 / 03 证照列表 / 04 证照详情 | B1–B3 |
| **AB** | 汇合 | 02 屏建店表单：选已有证照 / 新建 / **暂不填** | A1、B2 |
| **C** | 配额 | 门店额度阶梯上移 FREE 3 / PRO 10 / CHAIN 30 + 证照上限 5（§四） | 独立，随时 |

### 6.3 为什么 A 排在 B 前面

1. **风险不对称**。B1 动的是身份解析**按门店反查**——`X-Store-No` 是客户端可控的请求头，
   改错了就是越权。A 这边只放宽身份解析认哪些 status（见下方勘误），入参口径原样不动，
   最重的一步（A2）是加一行 `if`，那一行的风险是"可能挡掉存量商家"，
   靠上线前查一次数据就能确认，比越权好验证得多。

> **⚠️ 勘误（实施时发现，本文原来写错了）**：这里原文写的是「A 全程不碰身份解析」，**不成立**。
> `BizIdentityResolverImpl.resolve()` 查主体时带着 `status = ACTIVE` 条件，
> 于是 `PENDING_LICENSE` 的老板拿到 `BizContext.NONE`，**所有 `/biz/**` 全部 403** ——
> 店建出来了，人进不去。A1 必须把这个条件放宽成 `in (ACTIVE, PENDING_LICENSE)`。
>
> 它与 B1 的区别仍然成立、也正是风险不对称的由来：这里改的是**认哪些 status**，
> `resolve()` 的入参与「取哪个主体」的口径一个字没动，客户端仍然无法影响解析结果；
> B1 改的是**入参**——把客户端可控的 `X-Store-No` 喂进解析，那才是越权面。
2. **A2 是在补一个今天就漏着的洞**。可见性不看商家状态这件事现在就存在，
   不做无证照开店它也该修。早修早收敛。
3. **A 的价值链条更短**：降低开店门槛 → 更多商家建店 → 补证照转化。
   B 的价值（一个人管多张执照）只对已经有多份生意的老板有意义，用户面窄。
4. **A 做完不阻塞 B，B 做完却不能替代 A**。先做 A 的话，B 的 02 屏天然多一个选项即可；
   反过来先做 B，A 还是得从头做。

### 6.4 唯一的先后硬约束

**A1 与 A2 必须同一批发布，不能只上 A1。**
先上 A1、后上 A2 的话，中间那段时间里"没有证照的店，货直接对买家可见且能下单"——
比今天还糟：今天至少还要走完审核才有主体，那之后是谁都能建一家能卖货的店。

## 七、测试要点

- 越权：账号 A 传账号 B 名下一个真实存在的 `storeNo`，`X-Store-No` 头伪造，确认拿到的还是 A 自己的默认证照，不是 B 的
- 员工（非 owner）的 `X-Store-No` 只能落在他被授权到的门店范围内，即使他知道同证照下其他店的 `storeNo`
- 员工传一个自己完全没有成员关系的证照下的 `storeNo`，静默回退，不报错也不越权
- 单证照账号（现在绝大多数商家）前后端全程无感——`entities.length <= 1` 的短路要覆盖到
- 建店/证照上限（FREE 3 家店、5 张证照）：达到上限时前端提前变灰 + 后端兜底拒绝，两处都要测，不能只测前端
- 新证照入驻申请：账号已有 ACTIVE 证照时再交一份新申请不受 `uk_apply_active_owner` 阻塞（已复核确认该约束只挡"同一人同时两份进行中申请"，不挡"已有证照再开一张"）

### 无证照开店专项

- **存量数据核对（上线 A2 前必做）**：查生产库 `mch_entity` 按 `status` 分组的行数，
  以及每组名下的在架商品数。确认没有"status 不是 ACTIVE 但正在正常卖货"的商家——
  有的话先修数据，再上可见性闸门那一行
- `PENDING_LICENSE` 主体：建店成功、能录商品能上架，但 `reachableCommunities()` 返回空、
  C 端搜不到、商品详情页进不去
- 补证照审核通过后，**同一批商品立刻对买家可见**，不需要重新上架
- `quick-start` 的并发：同一账号连点两次不能建出两个占位主体（幂等或加锁）
- 占位主体也占「一个账号最多 5 张证照」的名额——否则可以靠反复建店绕过上限
