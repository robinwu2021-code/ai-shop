# 守卫与闸门 · 问题与优化方案

> 状态：**方案（待执行）** · 2026-08-29 立 · 数字均为当天实测

> 2026-08-29。这份不是又一批新规矩，是把**这次复核里所有问题的共同形状**收拢成七条，
> 再给出按「能挡住多少事故 ÷ 成本」排序的方案。
>
> 每一条都带当天实测的数字。

## 0. 一句话

**不是缺判据，是判据没人跑。**

`packages/shared/tests` 有 **61 份**守卫，`.githooks/pre-push` 的 vitest 清单里只有 **18 份**。
把剩下 43 份跑一遍：**16 份红、28 条断言失败**。其中至少四条是**已经被突破的棘轮**——
记录值写在代码里，实测早就越过去了，而没有任何东西会说：

| 守卫 | 记录值 | 实测 | 它在防什么 |
|---|--:|--:|---|
| `data-scope-coverage` | 56 | **70** | 带归属列却没登记数据域的表 = 那张表永远不过滤 |
| `biz-contract-fields` | 15 | **24** | 后端在发、B 端契约没接的字段 |
| `doc-standard` | 27 | **42** | 没有状态行的文档 |
| `ops-endpoint-exists` | — | — | 反向：已经接通了却还留在 KNOWN_GAPS 里的陈行 |

> ⚠️ 顺带更正复核报告里的一条：我说「`DataScopeRegistration` 注释点名的
> `DataScopeCoverageTest` **不存在**」。按 Java 类名找确实没有，但**等价守卫存在**——
> `packages/shared/tests/data-scope-coverage.test.ts`，而且它自己也在做同一件事的棘轮。
> 真正的问题不是它不存在，是**它不在闸门里，红了四个月也没人知道**。
> 这个错法本身就是下面第 ③ 条的例子：**判据比结论窄，就会得出反过来的结论。**

## 1. 七个形状

### ① 判据存在但没人跑

- 61 份守卫 / 闸门 18 份；ops-web 自己那 50 份测试**一份都不在**
- `ops-perm-matrix` 红着（`/ops/stream` 未登记）——本次修绿并挂上
- `ops-data-scope` 自 2026-08-25 起红着
- `data-scope-coverage` 棘轮被突破 14 张

**根因**：闸门的清单是**手工枚举的白名单**，新写的守卫默认在外面。
写守卫的人以为写完就生效了 —— 而「写了守卫」与「有闸门」是两件事。

**方案**：**白名单改黑名单**。默认全跑，例外要登记且要写理由。
但今天有 16 份红，直接切换等于把所有人挡在门外，所以先冻结基线再默认全跑。

> **挂闸门那一刻要预料到的事**：一条规则从「写了」到「有闸门」之间，
> 仓库里会积一批**存量违例**，而**第一个撞上的人往往不是引入者**。
> 挂闸当晚就发生了：有人给 `docs/v2/` 新增一篇数据字典、里面有两处 mermaid，
> 于是那条棘轮 12 → 13，**挡住了所有人的推送** —— 而 mermaid 这条规则写了很久，
> 只是今天才第一次真的拦人。
>
> 所以挂新闸时要连带做两件事：**① 先跑一遍、把存量冻成基线**（否则恒红）；
> **② 撞上的人第一句话要说清「不是你做错了新东西，是这条规则今天才生效」** ——
> 否则他会以为自己引入了一个缺陷，然后去找一个不存在的原因。

> ⚠️ **第一版这里做错了，另一条会话当天就指出来。记下来因为这个错很容易再犯。**
>
> 我把 29 条一律冻成「已知缺陷，容忍」。而这里面至少三条**本身就是棘轮**
> （`没有状态行的文档` 41 篇、`README 索引` 未登记、`不使用 mermaid` 12 处），
> 它们的语义是「只降不升」。冻成「允许失败」之后，「41 > 27」就不再报警 ——
> **下一个人再加 100 篇没状态行的文档，闸门一声不吭。**
> 那不是容忍一个已知缺陷，是**把一条正在收紧的规则关掉**；
> 而且它伪装得比恒红更好：清单上有一行，看起来是「有人管着」。
>
> 改法：每条基线带一个**观测值** `@<=N`，实测超过就红。N 按可信度依次取
> ①vitest 的结构化形状 ②守卫自述的棘轮话术（`70 张（记录值 56）`）
> ③兜底数消息里列了几项。**已知弱点**：靠 ③ 那几条会被 vitest 的列表截断限住，
> 挡得住「多冒出一类」，挡不住「同一类多几十条」—— 取到 ① 的没有这个问题。
>
> 这条本身就是本文第 ① 个形状的翻版：**判据比结论宽（或窄），结论就是错的。**

### ② 同一事实存了两份

| 事实 | 两份在哪 | 后果 |
|---|---|---|
| 「哪些 `/ops` 端点不判权」 | `gen-perm-endpoint-matrix.PUBLIC` × `OpsEndpointPermTest.ANY_OPERATOR` | 差一条（`/ops/stream`），生成器打了一路警告然后退出 0 |
| 角色 → 权限码 | `Perms.ROLE_PERMS`（回落表）× `sys_role_point`（库，真源） | 本次红过一次：库里有、代码里没有 |
| 同上，再抄一份 | `ops-web/lib/permissions.ts` 的 `BACKEND_ROLE_PERMS` | 漂了会报**假警报** |
| UI 码 → 后端码 | `ops-web/lib/perm-map.ts` × `Perms` | 漏登记 → `can()` 一律无权限，**入口消失且不报错** |
| 「后端有哪些端点」 | `docs/api/API清单.md`（生成物）× `docs/technical/reference/API清单.md`（手写草稿） | 追溯矩阵读的是手写那份，平台端只有 10% 路径对得上 |

**根因**：跨层的同一事实各存一份，靠人同步。

**方案**：**每一对都要么单向派生、要么有对账闸门**。本次已做一对
（生成器改成读 `ANY_OPERATOR`，对不上退出 1）。其余四对照做，成本各十几行。

### ③ 度量本身会假报，且假报方向朝「看起来更安全」

- 角色×端点矩阵按**字符距离**配注解 → `GET /ops/captcha` 与
  `POST /ops/staffs/me/password` 这两个**故意敞开**的端点被报成「要权限」
- `nav-function-point` 只认单行 `INSERT INTO` → 九条「缺功能点」里**八条是假报**，
  照着补会插出重复行
- 追溯矩阵读手写清单 → 平台端「9/233 已实现」是假的低估
- 我自己在这次排查里读了**上一轮遗留的 surefire 报告**，据此说了一次「还在红」

**根因**：解析器脆弱，而且**没有对照量**——扫不到东西时它与「真的没问题」长得一模一样。

**方案**：**每个守卫必须带一条「解析没失效」的控制断言**。
`ops-data-scope` 已经是范本（`expect(classes.size).toBeGreaterThan(300)`），
`nav-function-point` 的那条在本次修改中**当场抓到了我的第一版错误**。
可以立一条元规则：断言文件里必须出现至少一个上界/非空的控制断言，否则闸门红。

### ④ 注释里写着的纪律，没有对应的判据

- `DataScopeRegistration`：「注册是建表的一部分」+ 点名一个 Java 类（叫法与实际不符）
- `V267`：「翻亮那天必须连 `perm_code` 一起还原」——**没人做**，
  生产 `SHOP_INVENTORY_ENABLED=true` 而菜单灰着
- `perm-endpoint-map`：「进销存在运营端没有写口」——加了写口之后它成了假话
- 需求矩阵 §4 的状态列：一批 P0 缺口其实早已上线

**根因**：文档与注释里的**断言**没有机器判据，只能靠人记得。

**方案**：低成本的一条——**注释里点名的测试类/脚本必须真的存在**（一条 grep 级的 lint）。
高价值的一条——凡是写「将来某天要连带改 X」的注释，改成一条会红的断言。

### ⑤ 单跑绿、全量红

- `OpsPermConfigFlowTest.dbConfigMatchesHardcoded`（本次）
- `superAdminHasEveryPoint`（长期）

**根因**：整套测试共享一份 H2，某个用例改了库没还原。

**方案**：仓库里已有这条教训。可加一道**收尾指纹**：全量跑完后比对
`sys_function_point` / `sys_role_point` 的行数与校验和，与开跑前不同就点名。
成本一个探针类，本次已用它验过一次（跑完 157/157，说明是**运行中途**的瞬态）。

### ⑥ 生产配置与代码假设脱节

| 配置 | 代码假设 | 实际 |
|---|---|---|
| `SHOP_SEED_ENABLED` | 默认关，只在本地灌 | 生产 **true** → 11 个弱口令运营账号 |
| `SHOP_INVENTORY_ENABLED` | 关着，所以菜单标 `NOT_IMPLEMENTED` | 生产 **true** → 功能开着菜单灰着 |
| `NEXT_PUBLIC_USE_MOCK` | 本地 mock，部署走 `build:prod` | 对，但**本地永远是通的**，缺接口看不出来 |

**根因**：没有「生产配置 vs 代码假设」的对照表，只能靠人记得去 ssh 看一眼。

**方案**：一条 `scripts/check-prod-config.sh`——ssh 读**指定的几个键**（只取布尔值，
不碰任何密钥），与期望表比对，不一致就打印。**它不该进 pre-push**（依赖网络），
放进部署脚本的第 ⓪ 步或一条定时任务。

### ⑦ 唯一的信号，在最需要它的场景里不可达

**名字刻意绑在症状上，不绑在成因上** —— 已经撞到的两个成因完全不同（一个在包装层，
一个在控制流顺序），而症状一样，排查时的无力感也一样。绑成因会让下一个人以为
「我们没用那个包装层，所以与我无关」。

它与「守卫恒红没人看」是一枚硬币的两面：一个永远响、一个永远不响，
共同点是**输出与被测事实脱钩了**。

#### 成因一：全局信封把 4xx 裹成 200

**这一条是 2026-08-29 傍晚现场撞出来的，而它比撞出它的那件事大得多。**

一笔改动（`945a089e`，15 处 `@Valid` 首次真正生效）上线前，有人提出「部完盯一眼
`app.log` 里有没有突然冒出的 400」。那听起来完全合理 —— **而它是瞎的**，
当场验出来的：

| 想用的判据 | 实际 |
|---|---|
| `app.log` 里的 400 / 业务码 | **不记业务码、也不记请求路径**。我自己刚打出好几个 10400，`grep -c 10400` 是 **0** |
| nginx access.log 的状态码 | 看到的是 **200** —— 业务错误裹在 `ApiResult` 信封里 |

于是「重启后 34×200 / 4×401，无 400」这句话**什么都不证明**。

**根因不在那笔改动，在信封**：`ApiResponseWrapper` 把所有业务错误统一成
`200 + {code, msg}`（这本身是有理由的，见它的类注释），但副作用是
**按状态码统计的那一整条链路全部失明** —— 监控看到一片绿，nginx 分不出来，
日志里没有。今天被 `@Valid` 撞出来是巧合，下一个撞上它的会是别的东西。

**方案**：凡是「拒绝」都要在服务端留一条**可见但不刺耳**的痕迹。
`b8f686d3` 已按这条补了入参被拒的 WARN（全局处理器那一支，带方法 + 路径 +
字段名 + 约束名，**不打 body 不打字段值**），并且把它做成了断言而不是约定：
`InvalidRequestIsVisibleTest` 断言生产日志级别下必须留下 WARN、且一个真格式的
假号不许出现在日志行里 —— 改回 `log.debug` 立刻红。

#### 成因二：控制流顺序 —— 信号被 `return` 掉了

同一天傍晚关生产的 `SHOP_SEED_ENABLED` 时，原本打算拿
「重启后日志里不再出现 `[DEV-ONLY] seeding demo data`」当判据。查下来那句话
**最后一次出现是 08-20**，而开关当天 20:22 才关 —— 中间每次重启开关都开着，
它一次都没打。原因在 `DevSeeder` 的控制流：

```java
seedStaffs(...);                                   // 运营账号在总闸**之前**（有意的，注释写明了理由）
if (communityMapper.selectCount(...) > 0) return;  // 总闸：库里有社区就 return
log.warn("[DEV-ONLY] seeding demo data ...");      // 这句在总闸之后
```

于是**账号播种每次重启都在跑，而唯一能说明它在跑的那句日志被 return 掉了** ——
在「库里已有数据」的环境（也就是**生产**）里永远不打印。

**这一处比信封那处更狠**：信封至少把信号换了个形状（400 → 200 + code），
换个地方还找得到；这里是信号根本没产生。而且它有个恶性的性质 ——
**环境越像生产（库里已有数据），这个信号越不可能出现；而只有生产才需要它。**

所以这一条要盘的不只是「有没有打日志」，是「**这条信号在真实条件下走不走得到**」。

**盘完了（2026-08-29 夜）。** 拒绝一共五个出口，当时**四个在生产上完全无痕**：

| 出口 | 触发 | 原来 | 现在 |
|---|---|---|---|
| `ApiAuthEntryPoint` | 过滤器层 401 —— 过期 / 被吊销 / **跨端令牌** | **一行都没有** | WARN，带方法 + 路径 + **令牌前缀三字符**（不打令牌本身） |
| `onUnauthorized` | 控制器层 401（`/mp` 是 permitAll，由 `currentUser()` 抛） | 一行都没有 | 带了令牌却失效时 WARN；没带令牌不打（游客与探测器是常态，全打会淹掉上面那条） |
| `onDenied` | `@PreAuthorize` 拒绝（403） | 有 WARN，但打的是 `access denied: Access is denied` —— **不带路径，几乎零信息** | WARN，带方法 + 路径 |
| `onBiz` | 业务拒绝（含 10403 / 70006） | `log.debug`，生产是 INFO，一行不打 | **只有「拒绝类」四个码升 WARN**（10401/10402/10403/70006），其余保持 debug |
| `onInvalid` | 入参校验 | —— | 已由 `b8f686d3` 补上 |

**为什么只挑四个码升 WARN**：业务异常绝大多数是预期内的（库存不足、券领完了），
全升会把日志淹掉然后没人再看 —— 那和不打是一回事。这四个的共同点是
**有人被拒了而他多半不知道为什么**，也正是排查「这个账号怎么什么都看不到」时唯一的线索。

**还有一个出口在结构上不可能有痕迹**：数据域 fail-closed 拼出 `1=0` 之后返回空列表 ——
没有异常、没有拒绝，就是「查出来没有」。它只能靠 `ops-data-scope` 那几道静态守卫防，
运行时看不见。这一条写在这里是为了**不让人以为拒绝已经全可见了**。

判据：`RejectionIsVisibleTest`（把 logger 按生产设成 INFO，断言留下 WARN 且认得出端点、
**令牌一个字符不许出现**）。改回 `debug` 或去掉路径立刻红，验过。

剩下的同类：**「按状态码做的监控还有多少是真的在看东西」** —— 还没盘。

## 2. 一条常规动作：**修守卫之前，先证伪守卫**

这不是形状之一，是从七个形状里长出来的一个操作习惯 —— 单独立一节，因为
它是这一轮里**收益最高的一个动作**，而且很容易被跳过（守卫红了，第一反应是去改代码）。

### 2026-08-29 一天之内查到九处「守卫自己错了」

| 守卫 / 脚本 | 它错在哪 | 报出来的样子 |
|---|---|---|
| `gen-perm-endpoint-matrix` | 按**字符距离**给端点配 `@PreAuthorize` | 两个**故意敞开**的端点被报成「要权限」 |
| `ops-data-scope` | Mapper 按**简名**建映射，两个 `CouponMapper` 撞车 | 报出一张那个类从没碰过的表 |
| `ops-data-scope` | `extends BaseMapper<…>` 的正则不认换行与全限定名 | 整个 Mapper 没登记，落到同名的另一个上 |
| `biz-page-perm` | 只认内联 `:denied="!merchant.can()"`，不认 computed | 42 条冲突里 **19 条是假报** |
| `ddl-parsable` | 只认 `CREATE`，不认 `DROP` | 指着一张**已被删掉的表**喊「解析不了」，还给了错的排查方向 |
| `nav-function-point` | 只认单行 `INSERT INTO`（漏 `INSERT IGNORE`、多行列清单、多元组 `VALUES`） | 九条「缺功能点」里 **八条是假报** |
| ops-web 契约守卫 | 按**路径**建表，同路径的 GET/POST 互相覆盖 | 「B 端 24 个字段没接」这个**棘轮数字本身是假的** |
| ops-web 文案闸 | 注释判定逐行 | 把 JSX 注释当页面文案报 |
| `deploy-backend` 的漂移判据 | `cut -c1-7` 取 7 位，而 `--short` 给 8 位 | 「就是这一版」那条分支**从出生就不触发** |

### 三件事让它们比「漏报」更贵

1. **报错的方向朝着「看起来更安全」或「指向无关的地方」。** 把敞开的端点说成有码、
   指着一张不存在的表 —— 下一个人会照着它去改一张不存在的表，或者放心地不去看那个敞开的端点。
2. **假的欠账数会被冻进基线，变成一条永远降不完的账。** 「24 个字段没接」就是这么来的。
3. **它们退化的样子往往是「看起来完全正常」。** `cut -c1-7` 那处不是报错，是**永远落到另一条分支**，
   而那条分支在多数情况下打印的正是一句让人安心的话。

### 所以动手之前先问三句

- **这个守卫是怎么得出这个结论的？** 把它的判据读一遍，而不是只读它的报错文案。
- **它有没有「解析没失效」的对照量？** 没有就先补一条 —— `ops-data-scope` 那句
  `expect(classes.size).toBeGreaterThan(300)` 当天真的抓到了我的一次错改。
- **换一条独立的路径重算一遍，数字对不对得上？** 本轮两次靠这个发现真相：
  一次是「546 条对得上」证明匹配器没整体失效，一次是「330 + 12 = 342」两边闭合。
  第三次是当晚的 mermaid 那条，而它同时是**这一节最好的反面教材**（见下）。
- **手工复现时，有没有还原闸门的真实运行环境？** 同一晚撞了三种：

| 复现出错的方式 | 那次的样子 |
|---|---|
| **环境不对** | 同伴在 HEAD 副本里裸跑守卫、没软链 `node_modules` → 「vitest 没产出结果 → 直接红」，差点当成恒红报出去 |
| **读到中间态** | 我在**共享工作区**手工跑 `--check`，读到别人正在写的文件，报了一条几十秒后自己消失的「新增失败」 |
| **口径不对** | 见下 |

  **闸门跑的是干净 HEAD 副本 + 软链依赖**，手工复现少哪一样，得到的就是假阴性或假阳性。

### 一个反面教材：我用一个错的口径，去证伪一个真的缺陷

守卫报「mermaid **6**」，我裸 `grep -c` 数到「**17** 处 / 7 篇」，据此断定它有问题。
**结论碰巧是对的，两个数字却都不是我以为的意思：**

- 守卫的 `6` 是**文件数**（`FILES.filter(...)`）—— 这是**真缺陷**：
  往一个已经在名单里的文件里再加八张图，棘轮一动不动。已修成按张数计
  （`filter` → `flatMap`），基线 `@<=6` → `@<=16`。
- 我的 `17` 也是**错的** —— `grep` 没限行首，把 `docs/文档规范.md` 里那个
  用来说明「查的是什么」的自引用字面量也算了进去。真值是 **16 张 / 6 篇**。

**两条独立路径对不上时，先别假定是对方错。** 我当时的下一步是「查守卫的代码」，
运气好查对了方向；但同样合理的下一步是「查自己的 grep」，而那才是发现两个数
各错各的唯一办法。修复由同伴做，他动手前先自己重算了一遍 —— 那一步才把我的 17 纠成 16。

> 反向验证要打在**修复声称覆盖的那个洞**上，不是随便加一条。
> 同伴的做法：往那篇已在名单里、含 8 张图的文档再加一张 ——
> 新口径 `16 → 17` 变红，旧口径文件数仍是 6、一动不动。**那才叫证明修好了。**

#### 而真正让人不得不去查的，是「量具错了会静默」

同伴补的一句，它是上面那件事的另一半：

> **假如没重算、直接按 17 冻基线，那个错误不会以任何形式暴露。**

基线冻高了只是把闸门**调松** —— 不红、不报错、看不出来。代价要等到某天有人
真的把欠账加到那个数以内，闸门说「够不着上限，通过」，而那一刻没人会想到
是几个月前一次口径错误留下的松扣。**与本节其他所有失效同一个形状：错了不会说。**

所以这一节的两条是有先后的：**「两条路径对不上先别假定对方错」是发现问题的方法；
而让人不得不去用它的理由，是「量具错了会静默」。**
标题说「先证伪守卫」，证伪的对象**包括你自己的量具**。

已经据此改了工具：`check-shared-guards.mjs --update` 现在会把**变大的观测值**
和**新增的免检条目**单独打出来（缩小不必说，调松要人看一眼）。

> **这一类为什么特别难被发现**（同伴的话）：`--update` 是**人主动调用**的，
> 而人调用它的那一刻，心里已经认定「我知道我在干什么」。
> 闸门失效通常是**没人看**；这一类是**有人看、但那一刻正好不设防**。
> 所以警告放在这里是对的 —— 它不是给不知情的人看的，
> 是给「以为自己知情」的人一个停顿。
>
> 验它的时候我只做了阳性（调松要报），**阴性是同伴补的**：
> 正常 `--update`（没有任何调松）时，警告出现 **0** 次。
> 理由与本节其他地方一样 —— **一个永远报警的提示等于没有提示**，
> 它会被当成正常输出划过去，然后真的调松那次也一样划过去。

> **为什么那几天特别容易撞上**：闸门刚从 18 份扩到 61 份，平时不跑的守卫突然都在跑，
> 谁都还没建立起对这些数字的直觉 —— **量具最容易被质疑的，正是它刚开始被用的那几天。**

> **一个假的守卫比没有守卫更贵。** 没有守卫时人知道自己没有判据；
> 假守卫会让人理直气壮地按它去对齐。

### 2.1 三条当晚补的，都关于「判据自己出问题」

**① 为了让一个报错闭嘴而加的开关，把「没发生」变成了「成功」。**

同伴用 `-Dtest='A+B'`（surefire 要逗号，`+` 匹配到 **0 个**用例），又为绕开上游模块
报错加了 `-Dsurefire.failIfNoSpecifiedTests=false` —— 于是「一个都没跑」变成
`BUILD SUCCESS`，他据此向用户报过一次「两个都通过」。

**这个开关本文档的作者整晚都在用。** 对策不是别用，是：**凡是用了它，必须看
`Tests run: N` 的那个 N**，而不是看 `BUILD SUCCESS`。与「`[DEV-ONLY]` 那句在总闸之后」
同一个形状：信号被结构性地消掉，而剩下的那个信号看起来完全正常。

**② 「只有测试红，那多半是测试环境的问题」——这句话必须是查完的结论，不能当成跳过排查的理由。**

当晚它恰好是对的（见下），但同一晚另一位同伴有四次「只有某一半会红」的缺陷，**最后全是真的**
（登录才犯游客不犯、全量才崩单跑不崩、生产才 404 开发不 404）。
分辨方法：**打两边库里那一行的实际值来比，别比代码。**

**③ 数据库可移植性有两条轴，而只有一条有闸门。**

| 轴 | 问的是 | 闸门 |
|---|---|---|
| MariaDB → MySQL | 将来换库会不会炸 | `check-sql-portability.mjs`（9 条扫迁移文本的规则）✓ |
| **H2（测试）↔ MariaDB（生产）** | **今天的测试结论算不算数** | **没有** |

当晚那条 bug 属于第二条轴，而且连「SQL 层」都不是：迁移里的 `'[\"CN\"]'`
**在两个方言里都是合法 SQL**，只是 MariaDB 解转义存成 `["CN"]`、H2 不解存成 `[\"CN\"]`；
坏的是 **Java 里那句 `contains("\"CN\"")` 假设了库里存的是解过转义的形态**。
于是它在生产成立、在测试永远不成立 —— 症状是一个与支付通道毫无关系的用例报
「没有可用支付通道」。

所以那道 SQL 闸门**拦不住、也不该被改成能拦**（同伴的判断，我同意）：要拦得住，
判据得是「**跨方言的字面量比较**」，那已经不是扫 SQL 文本的量程。
现有的 `SchemaDriftTest` 只比**列**，不比**值**。

> **这条轴值得单独立一道闸**：对迁移里灌入的字面量，断言 H2 与 MariaDB 存进去的
> 是同一串字节。成本不低（要两个真库），但它覆盖的是**机制**而不是已知写法 ——
> 而「测试绿 ≠ 生产对」是这个仓库反复出现的一类。列为方案第 9 条。

**闸门立起来之前，那句警告放在哪** —— 同伴的意见，我采纳了：
**不放进 `backend/known-sql-dialect.txt`**。那份的语义是「每条对应一处不能碰的存量、
只准变短」，而这句话不对应任何一行存量、也永远消不掉；放进去会让那个数字三个月不变短，
下一个人就会开始怀疑它有没有意义 —— **一条消不掉的条目会毁掉「只准变短」这条规矩**。

放的是 `SchemaDriftTest` 的类注释（它已经在比 H2 与迁移了）。理由是**离犯错现场最近**：
下一个要写「JSON 列字符串包含判断」的人，多半是先打开这个测试类，而不是先打开一份基线名单。

### 2.1.1 两类基线长得一模一样，语义却相反

这个仓库里现在有两种「一列条目 + 一个数」的文件，**外观完全一致**：

| | 例子 | 语义 | 条目数不降说明 |
|---|---|---|---|
| **待办清单** | `packages/shared/known-guard-failures.txt`、`ops-web/…` | 修好一条删一行 | 有人在拖 |
| **止血线** | `backend/known-sql-dialect.txt`、`known-plural-paths` | **每条都改不得**（改一个字符 Flyway checksum 就对不上，线上起不来），只挡新增 | **正常** |

**只看条目数分不出来。** 同伴当晚为此栽了两次：把两份止血线都当成了待办清单，
跟用户报「下一个啃那 50 条」，而那 50 条一条都碰不得
（其中 38 条还是同一条规则，收尾办法是**一条新的 ALTER 迁移统一转换**，不是改 50 个文件）。
他自己归纳的根因很具体：**看的是条目数，没看清单头部那段说明。**

已据此给两份待办清单加了**第一行定性**（「这是待办清单，不是止血线」+ 指向对照的那一份）——
头部说明写在第六行和写在第一行，被读到的概率不一样。

### 2.2 「怎么才能证明我错了」应该是第一步，不是走投无路的手段

同伴给的，用来治「**修复生效 ≠ 诊断正确**」——这两件事在反馈上长得一模一样：

> 他的诊断是「共享种子被我污染了」，于是加了 `executeWithoutScope` 与还原断言。
> **断言全绿，而红还在** —— 假设是错的，但顺手修的那处恰好也是对的，
> 于是没有任何反馈告诉他方向不对。最后是「换一个不碰种子的类做对照」排除掉的。

关键在于：那个对照他**本来第一步就能做**，却把它当成了走投无路时的手段。

**所以诊断成立时，先说出「如果我错了，会看到什么」。**
这与本文反复说的阳性/阴性对照是同一件事，只是从**验证信号**挪到了**验证诊断**。

**「谁手上有上下文谁改」有个边界**（同伴提的）：它成立的前提是**改的人能自己验证**。
mermaid 计数那次他能改，是因为反向验证做得起来（往那篇加一张图就知道对不对）；
换成一条他验证不了的规则，即使上下文在他手上，也该交回给能验证的人。
