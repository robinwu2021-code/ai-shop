## L1 · 定位

六条主逻辑，每条给**时序 + 不变式 + 最容易写错的那一处**。

不变式是这份文档的重点：**时序会变，不变式不会**。
改实现时先看不变式还成不成立，比对着时序图逐行改安全得多。

## L2 · 一、进件

```
商家提交 ─▶ 校验资料齐 ─▶ 落 APPLYING + channel_apply_no ─▶ 通道审
                                                              │
      ACTIVE / REJECTED ◀── 回调 ⑨ ApplymentPollJob 兜底 ◀────┘
```

| # | 不变式 |
|---|---|
| 1 | 资料不齐**不发给通道** —— 发过去被拒，商家看到的是通道的话，而问题在我方 |
| 2 | 通道没回单号就**不落 APPLYING** —— 落了之后我们会一直等一个不存在的结果 |
| 3 | 一主体一通道一条进件记录（`entity_no + store_no + pay_channel` 唯一） |
| 4 | 日志**不记** `entityName` / `contactName` / `settleAccount` —— 记条数与类型即可 |
| 5 | 未知的通道状态码**不猜** —— 映射不出来就保持原状态并告警 |

**最容易写错**：第 5 条。把未知状态映射成 `ACTIVE` 是灾难（放款给一个没开通的账户），
映射成 `REJECTED` 是骚扰（商家白重交一次）。**保持原状态 + 告警**是唯一安全的选择。

## L2 · 二、收单

```
下单 ─▶ 选通道（按主体形态 × 端 × 市场裁剪）
     ─▶ 调通道下单【必带分账标识】
     ─▶ 返回支付参数
     ─▶ 用户付
     ─▶ 回调【验签 → 幂等 → markPaid → 生成结算单】
     ─▶ ⑩ PayQueryJob 兜底（回调丢了主动查）
```

| # | 不变式 |
|---|---|
| 1 | **分账标识只能在下单时传，漏传事后无法补** —— 缺失即拒绝下单，不是记日志 |
| 2 | 回调**只推进不回退**：乱序到达时旧状态不覆盖新状态 |
| 3 | 幂等键是**订单号**，不是通道单号 —— 通道可能换号重试 |
| 4 | 「改订单状态 + 生成结算单」同一事务（阶段 1/2）或 Outbox（阶段 3） |
| 5 | 收到即落**原始报文**，事后复盘只有它 |

**最容易写错**：第 1 条。它不报错、不影响下单成功、不影响用户付款 ——
唯一的表现是**几十天后那笔钱直接落进商家口袋，售后时追不回**。
这就是为什么它要写成「拒绝下单」而不是「记一条 WARN」。

## L2 · 三、账期与放款 ★ 本期主体

```
T2 到 ──① SettleableScan──▶ settleable_at 落值
                             │
                       ② BatchCollect ──▶ 入批（DRAFT）
                             │
                  T3 到 ──③ BatchClose──▶ COLLECTED
                             │
                       ④ BatchRecon ──▶ 门1 门2 门3
                             │
                    ┌────────┴────────┐
              RECONCILED           BLOCKED ──⑧ 超时──▶ 放行 + 告警
                    │
              ⑤ BatchRelease ──▶ 逐单 executeSplit ──▶ SPLITTING
                    └──▶ ⑪ DebtOffset（同事务扣欠款）
```

| # | 不变式 |
|---|---|
| 1 | 一主体 × 通道 × 区间**只能一批**（`uk_stl_batch_period`）—— 重复开批 = 放两次款 |
| 2 | 单据级差异只挂该单，**批次级差异挂整批** |
| 3 | 放行**只从 `RECONCILED` 出发**，靠状态不靠时序 |
| 4 | 放行与欠款抵扣**同事务** —— 分开的话，放了款没扣欠款就永远扣不到了 |
| 5 | 批次的 `recon_scope` 要如实落 `SELF_ONLY` / `BOTH`，界面据此标注 |
| 6 | `freeze_expire_at` 取本批**最早一单**的 T0 + 冻结窗口 |

**最容易写错**：第 6 条。取平均或取最晚都会让告警晚于实际到期 ——
整批一起放，而最早的那一笔先到期，**它到期就意味着这一批已经出问题了**。

### 门 1 的判据（唯一现在就能实现的一道）

```
基数 == 佣金 + 服务费 + 积分费 + 通道手续费 + 实得
```

不等就挂该单并记差异。**不要「自动修正」**——
差额来自哪一项是个需要判断的问题，自动补平只会把问题藏起来。

## L2 · 四、退款：按钱在哪走四条路

```
收到退款请求
   │
   ├─ 单据状态 PENDING / RETRYING      ──▶ Z1 原路退（从冻结资金）
   ├─ SPLITTING                        ──▶ Z2 先 reverseSplit 再退
   ├─ SPLIT / SPLIT_CONFIRMED          ──▶ Z3 分账回退 → 成功则退
   │                                        └─ 失败 ──▶ Z4
   └─ Z4 追偿：① 保证金 ─▶ ② 欠款 ─▶ ③ 停放款转人工
```

| # | 不变式 |
|---|---|
| 1 | **`reverseSplit` 返回 false 必须阻断退款** —— 钱已给商家还退给买家，平台要垫 |
| 2 | `split_reversible = 0` 的商家**不许进入 Z3** —— 放款前就该拦住 |
| 3 | 追偿三层**不跳级**：保证金不足才记欠款，欠款抵扣不掉才停放款 |
| 4 | 一个源单**只产生一次欠款**（`uk_mch_debt_txn_source`）—— 售后事件会重投 |
| 5 | 买家侧**不因追偿失败而拿不到钱** —— 走售后裁决，与追偿是两条链路 |
| 6 | 欠款余额恒 `>= 0`，负数是 bug 不是「预付」 |

**最容易写错**：第 5 条。追偿失败与买家退款是两件事，
把它们串成一条（追不回就不退买家）会直接变成投诉与监管风险。

## L2 · 五、对账

```
每 10 分钟 ──▶ 四条轴各自扫
   收款轴   我方有单无回调 / 通道账单比对
   分账轴   已发指令超时未确认 / 通道分账查询
   出款轴   已付款无流水号 · 流水号重复 / 银行流水
   积分池   恒等式（不逐笔）
                    │
              产生 stl_recon_diff
                    │
      ┌─────────────┼─────────────┐
 CHANNEL_ONLY   PLATFORM_ONLY   AMOUNT_DIFF
   查单补记        查单关单       **必须人工**
```

| # | 不变式 |
|---|---|
| 1 | 每条轴**各说各的覆盖范围**（`coverage()`），查不了的写在页面上 |
| 2 | 线下单（`OFFLINE_SETTLED`）**排除在通道对账外** —— 它从不出现在通道流水里 |
| 3 | 积分池轴**不产生逐笔差异** —— 失衡是整体现象，逐笔记会记出成千上万条指向同一件事的待处置 |
| 4 | `AMOUNT_DIFF` 不自动处置 —— 金额差不存在安全的自动动作 |
| 5 | 差异处置**必须留痕**（谁、什么时候、依据是什么） |

**最容易写错**：第 1 条被省掉。
省掉之后「今天没有差异」听起来像一切正常，**而它可能只是没查**。
这也是为什么批次要落 `recon_scope`。

## L2 · 六、积分预扣（阶段 3 准入条件）

```
下单前  hold(userNo, amount, orderNo)     ─▶ 占用，带超时
下单成  commit(orderNo)                   ─▶ 占用转已扣
下单败  release(orderNo)                  ─▶ 还回
超时    ⑭ PointsHoldExpiryJob             ─▶ 自动还回
```

| # | 不变式 |
|---|---|
| 1 | `hold` 之后余额立刻减少（用户看到的是可用余额）—— 否则他会以为还能再用一次 |
| 2 | `commit` / `release` 幂等，键是**订单号** |
| 3 | 超时释放之后 `commit` 仍然要能成功（幂等 + 补扣） |
| 4 | **宁可多释放一次，不可少还一次** |

**最容易写错**：第 3 条。超时释放与 `commit` 竞态时，
若 `commit` 直接失败，用户的单成了而分没扣 —— 平台白送。
正确做法是 `commit` 发现已释放则**重新扣一次**（余额不足则记欠分，走对账）。

## L3 · 七、六条逻辑共同依赖的三件事

| | 什么 | 为什么是共同的 |
|---|---|---|
| **幂等** | 业务唯一键，不用「已处理」标记 | 六条链路的输入全都会重投 |
| **快照** | 费率 / 模式 / 收款号在单据生成时固化 | 六条都要回答「当时按什么算的」 |
| **可解释** | 每一次拒绝 / 挂起都能说出人话 | 六条都会拒绝人，而申诉链路只有一条 |
