# 评审：商品关联能不能「设置只改状态、关联在查询时做」

状态：评审（**没有改任何代码**）
日期：2026-10-07 · 评审人：本会话
起因：用户定的原则 ——「所有的设置都只调整状态值，不要同步修改关联数据，数据关联应该是在查询的时候关联查询」

---

## 一、结论

**方向成立，而且现状比预想的更糟。** 今天线上这条链路上，派生数据已经有四处与真源不符，
每一处都不报错、只在买家那一侧表现为「看不见」或「不该看见却看得见」。

但**不是「把 join 写出来」那么轻**：可见性规则散在五个 Java 方法里，我在生产上用 SQL 复刻时
**两次没写对**（先漏「店级在架」、再漏别的），这件事本身就是对工作量的度量。

---

## 二、现状：商品关联这条线上，设置会顺手写哪些数据

| 真源（设置） | 顺手写的派生数据 | 入口 |
|---|---|---|
| 门店送货方式 | `prd_community_pool` | `StoreFulfillmentServiceImpl.save` → `resyncPools` |
| 门店状态（停用/恢复） | 同上 | `StoreAdminServiceImpl.setStatus` |
| 门店资料保存 | 同上 | `MerchantStoreServiceImpl` |
| 主体经营范围 | 同上 | `MerchantPortImpl`（审核/范围变更） |
| 商品上下架 | 同上 | `MerchantGoodsServiceImpl.syncPool`（3 处调用） |
| 商品**下架**一次 | `prd_store_goods` **播种**（给其它门店插行） | 同文件 2399 行 |

即：**六个设置动作，都会同步重写别的表**。

## 三、数据量：28 行配置 → 53 万行物化

| 表 | 行数 | 说明 |
|---|---|---|
| `mch_service_area` | **3** | 经营范围（真源） |
| `mch_fulfillment_channel` | **16** | 送货方式开关（真源） |
| `mch_store` | **5** | 门店（真源） |
| `mch_channel_area` | **4** | 门店范围子集（真源） |
| `prd_goods` | 21 | 商品 |
| `prd_store_goods` | 62 | 店级在架 |
| `cmt_community` | 23 656 | 开放小区 |
| **`prd_community_pool`** | **536 168**（活 283 872） | **以上几张表的笛卡尔展开** |

决定「谁能看见什么」的配置一共 **28 行**，物化出来 **53 万行**，相差约 19 000 倍。
每改一次那 28 行里的一行，就要重算 28 万行。

## 四、读写两套口径（已经分叉过）

| 路径 | 读什么 | |
|---|---|---|
| C 端列表 `GoodsServiceImpl#poolGoodsNos` | **池** | 物化 |
| C 端详情「送不送到你这儿」`deliverableTo` | **池** | 物化 |
| 下单落店 `OrderServiceImpl#nearestServingStore` | `reachableCommunities` | **实时** |
| 下单履约校验 `requireFulfillmentSupported` | `enabledFulfillmentsFor` | **实时** |

同一个问题两套实现，差异只会表现为「看得见、下不了单」或反过来。
代码注释里已经记过一次分叉（销售区域 vs 可见性）。

## 五、查到的具体问题（都有证据，都不报错）

1. **池里残留已下架商品。** 2026-10-07 19:10 池里 17 组 (商品×门店) 活行，而在售只有 10 件 ——
   6 件已下架的货还在池里，买家搜得到，其中两件是「【测试】0.1元体验装」。当天几次重建才清掉。
2. **框了范围等于没框。** 两家店 `scope_mode=SUBSET`，界面显示「送货范围：仅 1 项」，
   而它们引的 `area_no=SVA202610052039310171173` **在 `mch_service_area` 里根本不存在**（4 行悬挂引用）。
   与主体足迹取交后为空 → 落回「快递开着且没框 → 全国」。**商家以为收窄了，系统实际放开到全国。**
3. **池表没有以 `goods_no` 打头的索引。** 索引只有 `uk(community_no,goods_no,store_no)` 与 `idx(store_no)`，
   而重建时按 `goods_no` 查 —— 53 万行全表扫，每件货一次。
4. **保存一次设置 = 20 秒。** 已修到 4~5 秒（见「可见性按门店算-方案」§十一），但本质没变：
   改 1 行配置仍要重算 28 万行。
5. **演示店 5 件在售、0 件进池。** 主体 `PENDING_LICENSE`，按现有规则对买家不可见 —— 这一条是设计如此，
   但如果苹果审核从买家侧看这家店，看到的是空的。

## 六、可行性：在生产上验过

用一条 SQL 表达「某小区能看见哪些货」（主体/门店状态 + 渠道开关 + 范围 INCLUDE 前缀展开 − EXCLUDE + 店级在架），
在生产库直接跑：

| 小区 | 区划 | 关联查询 | 池 |
|---|---|---|---|
| C202609161512010009882（深圳福田） | 440304004 | **10** | 10 |
| C202609280646480045383（山西运城） | 140802001 | **10** | 10 |

单次耗时 60ms 量级（池查同样量级）。**买家侧每次只问一个小区**，而池是把 23 656 个小区的答案全预先算好 ——
反向只查一个，基数从两万多降到几十行配置。

**但要诚实说三件事**：

1. 我**第一次写错**（漏了店级在架 `prd_store_goods`），**第二次又对不上**（全量对账 70 968 vs 池 283 872）。
   规则分布在 `reachableCommunities` / `expand` / `minusExcluded` / `storesSelling` / `activeStoreNos` 五处，
   一次搬全不容易。这是工作量，也是风险。
2. **表之间字符集不一致**（`prd_goods` 是 `utf8mb4_unicode_520_ci`，`mch_store` 是 `utf8mb4_general_ci`），
   跨表 join 必须显式 `COLLATE`，否则直接报 1267。要么统一字符集，要么每处 join 都带上。
3. 排序（就近）现在存在池的 `sort_weight` 里。改成查询时算的话，要在「几十家店」上算距离 ——
   比现在给两万多个小区预算距离**更省**，但要重写排序那一段。

## 七、建议的做法（分步，每步能独立上线、独立回退）

1. **先止血，不动结构**：把第五节的 2（悬挂引用）与 3（缺索引）修掉。
   前者是正在生效的错误放开，后者是一行迁移。
2. **把规则收成一个可测的东西**：现在它散在五个方法里。先抽成一处（纯函数 + 一组判定用例），
   让「规则」有唯一出处 —— 不管最终用 SQL 还是 Java，这一步都要做，且现在就能做。
3. **双读对账**：读路径同时走池与实时规则，只记日志不改行为，跑一周。
   差异为零再谈切换 —— 这是唯一能证明「搬对了」的办法，比任何测试都强。
4. **切读，再停写**：读切到实时之后，池先留着不写也不读（可随时切回），观察一轮再删表。
5. **商品上下架那条也一起**：`syncPool` 与 `prd_store_goods` 播种同属一类问题，
   但播种那段有自己的业务含义（新店要不要默认在架），**不要顺手一起改**，单独立项。

## 八、不建议

- **不要只把重建挪到后台。** 今天试过，被两条场景测试拦下：放宽可见性晚一步无所谓，
  收窄（停用门店、关一路）晚一步就是「买家还搜得到、点进去、下单被拦」。
- **不要在没有双读对账的情况下直接切。** 可见性是所有买家看到什么的唯一出口，
  切错的症状是静默的（看不见，没人报错）。
