## 二、业务场景逐项比较

“覆盖”指当前设计覆盖，不表示代码完成。

| 历史场景 | 新矩阵原覆盖情况 | 本轮对齐结果 | 主要终端/阶段 |
|---|---|---|---|
| F1 快餐先付、柜台叫号 | 覆盖 | 保留无桌快餐、取餐号；不强制台账 | 收银/厨房/点餐机，P1 |
| F2 扫码先付、多轮点单 | 覆盖 | 保留桌台会话、多端购物车和已付派工 | 顾客/服务员/收银，P1 |
| F3 正餐后付、多轮加菜 | 覆盖 | 增加长时未结巡检；后付库存与取消守卫先验收 | 收银/服务员/厨房/老板，P2 |
| F4 服务员代客点单 | 覆盖 | 明确操作人不等于买家，赠菜与折扣分别审批计价 | 服务员/收银，P1起 |
| F5 外卖 | 已列配送边界，作业项不够明确 | 补备餐完成→基座配送交接及配送状态查看 | 收银/服务员/厨房，P1按基座能力 |
| F6 自取 | 点餐覆盖，叫号核销不够明确 | 补取餐号/叫号/正式核销，不把厨房出品等同取走 | 收银/服务员/厨房/顾客，P1 |
| F7 包间预约→转开台 | 被整体列为另题，存在遗漏 | 补回目标范围；排队仍另题，预约排P2 | 商家运营/服务员/收银/顾客，P2 |
| F8 AA、按单、按人 | 覆盖但粒度含混 | 按单选择、预先按人分单、事后按菜分摊分别标依赖；补AA | 收银/顾客，P2逐单、P3资金拆分 |
| F9 减菜/退菜 | 覆盖 | 保留申请与审批；已付部分退款需核心支持，取消重下不直接沿用 | 服务员/收银/厨房，分阶段 |
| F10 沽清与时段菜单 | 覆盖 | 区分停售、每日配额、物理库存和营业日重置 | 商家运营/厨房/收银，P1起 |
| F-14 长时未结账巡检 | 未单列 | 补告警、认领、升级；不因超时自动免债或取消已制作单 | 收银/运营/老板，P2 |
| F-15 营业日报 | 覆盖通用看板 | 补台数、翻台率、客单价、未结应收及营业日口径 | 运营/老板，P1基础、P2桌台 |
| 旧餐饮§2.4 称重菜 | 遗漏 | 补标称量/实称录入、差价确认及补退款；不认定当前可直接复用 | 收银/服务员/厨房，P3 |
| 旧§16 服务费/茶位费、堂食外卖双价 | 规则中出现但展示不够明确 | 补功能项；仍由统一报价与金额快照处理 | 运营/收银/老板，P3 |

## 三、设计冲突与取舍

| 主题 | 历史口径 | 当前设计与对齐决定 |
|---|---|---|
| 商品与订单 | 一套基础商品交易，行业只扩展 | 一致；餐饮台账/制作独立，支付资金与基础成交共享 |
| 项目与部署 | 独立Maven行业jar，Spring装配；不做热插拔 | 保留同仓backend-plugins、独立reactor/版本目标；新增独立server及远程适配。独立构建不自动等于独立服务 |
| 契约依赖 | shop-industry-spi，零依赖 | 保留共享底座契约；food-api只放餐饮对外契约，不能再定义一套同义CoreOrderApi。正式模块名在接口设计统一 |
| 全量依赖检查 | 所有餐饮门店强依赖预约、套餐、打印等 | 改为部署级契约兼容检查＋按门店启用能力检查。无桌快餐不强依赖包间预约；未就绪功能禁用并明确原因 |
| 菜单 | 旧fnb_menu；V2提供collection/availability | 餐饮菜单管理时段、终端、例外日和版本。若实现通用collection/availability，基础陈列和时段能力通过适配复用，不建立两套独立可编辑规则 |
| 套餐 | V2 trait_bundle/component，支持CHOICE | 优先统一可售SKU与报价/库存展开契约。fnb_bundle*为当前扩展候选；通用组合正式落地后应映射或迁移，不同时维护两份套餐定义 |
| 选配 | V2 prd_modifier*与ord_item_modifier，可负价差 | 免费口味优先复用现有字典；收费配料关联SKU，组合与选择约束由餐饮扩展。现有fnb_modifier* ER待收敛；通用选配落地后引用其标识，禁止重复价格真源 |
| 工位 | V2 mch_station；旧fnb_dept | 统一工位引用合同。fnb_station为候选实现；不能与mch_station分别编辑同一工位。多工位制作路由可为餐饮专属 |
| 桌台资源 | mch_resource负责占用 | 保留资源端口，餐饮occupancy保存台账/座位业务关系；有通用资源服务时由其仲裁占用。资源服务不存在时须明确实现/适配归属，不能两个系统各自发放占用 |
| 后付 | WAIT_OFFLINE_PAY后立即派工，描述为基座已具备 | 不沿用“已有”结论。离线收款模式不等于后付业务许可；需库存承诺、取消守卫与先交付后付款合同 |
| 混合收款 | ord_payment＋settle逐单MIXED；更旧版fnb_payment已作废 | 保留统一资金域方向；不能加MIXED枚举就复用一笔流水确认多单。跨根分配、冲正、退款追踪需正式核心能力 |
| 结账金额 | 台账不存金额，账单只读不落库 | 保留核心金额权威；fnb_settlement可保存冻结的结账范围和金额快照，用于并发及恢复；不自行定价或记资金流水 |
| 未付退菜 | 整单取消＋剩余重下，被描述为零风险 | 已制作单不能自动采用。先核验库存耗用、优惠、厨房去重及应收调整，保存原批次与逆向关系 |
| 已付退菜 | refundLine作为已有能力 | 当前仅整门店订单退款，部分退款继续列核心缺口，不在餐饮包直接退款 |
| 沽清 | 旧库存归零恢复；V2每日配额 | 采用销售限制或每日配额，独立于实存。营业日重置仅恢复临时限制/配额，不回填旧库存数 |
| 制作映射 | ord_item.id一对一餐饮附属 | 保留稳定核心行关联，但允许同SKU多口味、套餐组件、多工位、分次出品；使用源行与数量映射，不能一对一约束全部场景 |
| 事务 | 建单与行业附属1–4同事务 | 双部署统一采用幂等意图、结果关联、事件与恢复。集成部署也遵守核心真实事务，不承诺跨服务本地事务 |
| 打印 | 通用prn_printer/template/route/job，全部在通道包 | 保留共享打印；业务任务与渠道适配分层。prn_device与prn_printer统一命名后选其一，新增attempt记录为重试审计，不另建第二套打印 |
| 包间预约 | 原始范围内 | 补回当前目标；取消、爽约、到店开台需处理时段hold与开放占用接力，失败不丢原占用 |
| 外卖与自取台账 | 无台账 | 保留；批次和制作独立于台账，不强制生成空堂食台账 |

## 四、相对 V2 新增并保留的目标

六端明确分工、现有老板App整合、独立server部署、点餐机设备身份、拼桌分账与并桌区分、多人多终端协作、第三方餐饮接入、门店断网与边缘单写者均保留。旧文未列入或明确另题的范围，按本轮用户目标进入分期；不把第三方接入继续整体排除。

## 五、对当前设计的修订与待落地事项

已修订多端矩阵：预约包间、称重菜、AA、渠道价格/费用、自取叫号核销、配送交接、巡检与营业日指标；追加V2来源与独立构建/契约规则。历史文档保留正文，入口加本对齐说明，避免改写其他行业设计。

本轮未修改已有ER真源：22张菜品相关候选表与19张营业流程候选表不是最终迁移清单。详细表设计必须先核定通用Modifier/Bundle/Collection/Station/Resource的实现与所有权，再逐项决定直接复用、扩展或替代，禁止把V2目标表和fnb候选表直接累加。

当前核心退款边界见[退款结清M1契约](../订单退款结清-M1流程与契约.md)。本轮对backend Java类名和迁移文件进行了定向检索，没有据此确认整套V2目标能力已落地；未找到同名类不能证明能力不存在。后续端口设计需逐项核验实际入口、调用链、数据库迁移和测试。

验收需求：F1–F10均能映射到端、状态机、权威能力及分期；先付与后付不重复派工；预约转开台失败可恢复；跨单结账资金可追踪；厨房补打不重做；物理库存不因营业日重置增加；可剔除餐饮仍可运行零售；本地/远程适配通过同一合同用例。
