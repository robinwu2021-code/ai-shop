# B 端 / C 端权限方案 · 功能 → 功能点 → 角色 → 人员

> 状态：**已确认 · 待实现** · 创建 2026-08-12
> 范围：B 端（商家侧）与 C 端（消费者侧）的授权模型，**并落库**
> 依据：[三端功能点矩阵](../reference/三端功能点矩阵.md)（生成物，扫描三份 OpenAPI 得到）
> · [需求矩阵-三端 §2.3](../../requirements/需求矩阵-三端.md)
> 关联：平台端权限已在 `Perms.java` 落地（硬编码），本方案是**同一模型的两端延伸 + 落库**

**基于已实现的功能**整理，不是基于设想 —— 功能点清单直接来自扫描出的端点，
而不是从需求文档抄。矩阵里标 🔴 的域（后端零实现）**不进本方案**：
给一个不存在的功能配权限，配了也没有任何东西会检查它。

---

## 0. 一句话

**四层：功能（模块）→ 功能点（可授权的最小动作）→ 角色（一组功能点）→ 人员（持有角色）。**

B 端这套已经在跑，只是**硬编码在 `BizPerms.java`**；C 端还没有这一层。
本方案做两件事：把两端的模型写清楚，然后**把功能/功能点/角色配置搬进数据库** ——
硬编码的问题不是「对不上」，而是**加一个角色要发一次版**。

## 1. B 端：已在跑的模型

### 1.1 现状（`BizPerms.java`）

13 个权限码 × 6 个角色，**授权二维正交**：角色（能做什么）× 门店（能碰谁的数据）。

| 角色 | 权限码 | 一句话 |
|---|---|---|
| `OWNER` 老板 | `*` | 全部，含钱与员工 |
| `MANAGER` 店长 | 除 `finance` / `store:admin` 外的 11 个 | 能管店，**不碰钱、不改主体** |
| `CLERK` 店员 | `receive` `verify` `ship` `order:view` `stock` | 日常出货 |
| `PICKER` 拣货 | `receive` `stock` | 只碰货 |
| `COURIER` 配送 | `ship` `order:view` | 只送货 |
| `CS` 客服 | `review` `aftersale` `order:view` | **只对着顾客说话**，不碰货不碰钱 |

> 三条既有决定保留不动：**一个人可以有多个角色，取并集**（老板同时勾了店员与配送，
> 他要的就是两样都能干）；**空角色集 = 零权限**（认不出角色时给权限是最坏的失败方式）；
> **数据边界是门店**，与角色正交。

`@PreAuthorize` 里扫出来的**真实**判据，不是设计意图。

#### 从矩阵上一眼看到的两处

**① 「工作台与基础」被算进了 `CAMPAIGN/CUSTOMER`。** 那一格里混着
`/biz/auth`（登录）、`/biz/context`（取当前门店）、`/biz/upload`（传图）
这三类**进门就要用**的端点，和 `/biz/dashboard`（要 CAMPAIGN/CUSTOMER 才看得全）。

dashboard 归到各自的业务功能里 —— 现在这样，

**② 店员/拣货/配送在「订单与履约」上都是 ◐。** 这是对的（各自只碰自己那段），
但**◐ 的具体含义在数据库里必须能查**：现在只能从 `BizPerms.java` 反推。
落库之后 `sys_role_point` 会把「拣货能不能点核销」变成一行数据。

## 2. C 端：这一层还不存在

### 2.1 C 端有没有「角色」

有，但**不是员工那种角色**。C 端的授权来自**身份**，而身份来自数据关系：

| 身份 | 怎么获得 | 多出来的能力 |
|---|---|---|
| 游客 | 未登录 | 逛商品、看门店、看社区 |
| 用户 | 手机号/微信登录 | 下单、售后、券包、积分、评价 |
| **团发起人** | 发起了一个邻里团（`ful_group_pickup.user_no`） | 轻核销本团、看参团邻居的**脱敏**信息 |
| **求团发起人** | 发起了求团（`group-request`） | 选定报价、二次确认、锁价 |

> **C 端身份是「按数据关系算出来的」，不是「管理员配的」** —— 这是它与 B 端最大的区别。
> 没有人给某个用户「授予团发起人角色」，他发起了团就是。

### 2.2 所以 C 端要不要落 角色→人员 表

**要，但语义不同**：C 端的角色表是**能力开关**，不是身份授予。

三类真实存在的需求：

1. **灰度**：新功能只对一部分用户开（`feature-flags` 已落地，但它是全局的，
   不能「只对这批用户」）
2. **内测/白名单**：某些用户能用未公开的功能
3. **处置**：风控拉黑之后要**收回**部分能力（不能下单但能看订单）——
   这是 C 端唯一真正需要「按人收权」的场景

前两个是「多给」，第三个是「少给」。**第三个才是必须的** ——
风控域现在零实现，而拉黑要落地就需要这一层。

## 3. 落库：四张表

按并行协议取 **V62**。

```
sys_function        功能（模块）
  function_code · name · end(B|C) · sort · enabled

sys_function_point  功能点
  point_code · function_code · name
  method · path            ← 与矩阵一一对应，**可追溯到真实端点**
  perm_code               ← 映射到现有 BizPerms 的码；C 端多数为空（不受约束）

sys_role            角色
  role_code · name · end(B|C) · builtin · entity_no(可空)
  ↑ builtin=1 是平台预置（OWNER/MANAGER/…），不可删；
    entity_no 非空 = 某商家自定义的角色

sys_role_point      角色 × 功能点
  role_code · point_code
```

**人员 → 角色**：新增 `sys_role_member`（见
[数据库设计与数据清单](./权限配置落库-数据库设计与数据清单.md) §1.5）。

> ⚠️ **本节初稿写的「不新建表」是错的**，连表名都写错了
> （写成 `mch_account_role`，实际叫 `mch_store_role`）。查证后的结论分两半：
> B 端那张**已经是关联表且已支持多角色**（V18 专门把唯一键放宽成
> `(账号, 门店, 角色)`），不动它；而**运营端的角色存在 `sys_ops_staff.roles`
> 这个 JSON 列里** —— 查不了「哪些人有 FINANCE 角色」，那才是要建表的一半。

### 3.1 落库之后，代码怎么读

**不改判权逻辑**：`BizPerms.can(roles, code)` 的签名不变，
只是 `ROLE_PERMS` 从常量改成「启动时从库加载 + 缓存」。

> 这条很重要：**落库是把配置搬家，不是把判权重写**。
> 判权逻辑一改，所有既有测试的意义就都要重新论证一遍。

### 3.2 初始化数据从哪来

- **B 端角色与映射**：直接从 `BizPerms.ROLE_PERMS` 导出 —— 现在跑着的就是它
- **功能点**：从 `docs/technical/reference/三端功能点矩阵.md` 生成
  （它本身是扫描端点生成的，**不手写**）
- **运营端角色与映射**：从 `Perms.ROLE_PERMS` 导出（11 个角色，今晚刚补齐）
- **C 端**：只落功能与功能点，角色表先只放 `GUEST` / `USER` 两个内置角色

## 4. 做什么 / 不做什么

### 做
1. V62 四张表
2. **生成器**（不手写种子）：扫端点 + 读 `BizPerms`/`Perms` → 生成 `INSERT`
   —— 与功能点矩阵同一手法，手写的清单三个月后必然过期
3. 三端种子：B 端 6 角色 / 运营端 11 角色 / C 端 2 角色
4. **一致性守卫**：库里的角色→权限码映射必须与 `BizPerms`/`Perms` 逐条相等
   —— 这是「行为不变」唯一可验证的形式
5. `BizPerms` / `Perms` 改成从库加载（签名不变、行为不变）
6. 平台端只读页面：看到「这个角色有哪些功能点」

### 不做（登记）

| 不做 | 为什么 |
|---|---|
| ~~平台端 `Perms.java` 也落库~~ | **改为一起做**（2026-08-12）：既然运营端的功能点与矩阵已经整理进本方案，把它排除在外会让同一套表只装两端的数据 —— 而「三端同一套表」正是这个模型的价值。三端一起导，验收标准同样是「什么都不变」 |
| 商家自定义角色的**编辑界面** | 先把表和数据落地，界面下一批 —— 没有界面时预置角色照常工作 |
| C 端按人收权（风控拉黑） | 风控域零实现，等它开工时一起做 —— 现在建了没有消费方 |
| 数据域（门店/商家边界） | 与本方案正交，且它自己是一件独立的事（见今晚的结论） |

> ⚠️ **本方案落库之后，行为应当与现在完全一致**。
> 这是验收标准：种子数据导入后跑全量测试，一条都不能变红 ——
> 变红就说明导出的配置与硬编码的不一致，而那正是要防的。

## 5. 要你确认的

| # | 问题 | 我的建议 |
|---|---|---|
| **Q1** | C 端角色表这一批只放 `GUEST`/`USER` 两个内置角色，还是连风控拉黑的收权一起做？ | **只放两个** —— 收权要等风控域，现在建了没有消费方 |
| **Q2** | 功能点的 `perm_code`：C 端大多数为空（不受权限约束），可以吗？ | 可以，且要**显式记成空**而不是不建行 —— 空是一条信息（「这个功能点谁都能用」） |
| **Q3** | `BizPerms` 改从库加载，缓存怎么失效？ | 启动加载 + 改角色时清缓存。一期商家自定义角色的界面还没有，改动频率极低 |
| Q4 | 迁移号 V62？ | 是（V60 员工数据域、V61 内容域已占用） |

**Q1 决定这一批的边界**，其余按建议走即可。
