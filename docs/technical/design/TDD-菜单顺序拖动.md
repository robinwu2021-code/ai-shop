# TDD-菜单顺序拖动

状态：**已实现**
关联设计：[TDD-权限配置对齐与tab门禁](TDD-权限配置对齐与tab门禁.md) §3.1 缺口 C
创建日期：2026-08-12

---

## 1. 需求摘要

`/iam?tab=menu` 现在只能一次上移/下移一格。把一个分区从第 12 位挪到第 2 位要点十次。
支持**拖动**排序。

验收标准：

1. 拖动分区或菜单项到同级的新位置，松手即生效，菜单与页面 tab 跟着变
2. **不能跨父级拖**（把 A 分区的菜单项拖进 B 分区）—— 那是改结构，不是排序
3. ↑/↓ 保留：键盘可达，且拖动在触屏/辅助技术下不可靠
4. 一次拖动 = **一次请求**，不是 N 次相邻交换

---

## 2. 当前架构分析

- 后端只有 `move {UP|DOWN}`：同级与相邻项交换 `sort`
- 前端 `/iam?tab=menu` 用共享的 `Tree` 渲染，行内挂 ↑/↓
- **全仓没有任何拖拽依赖，也没有一处用过原生 HTML5 拖拽**

`sort` 值当前是 `(i+1)*10` 的等差序列（生成器产出），交换式 `move` 保持了这个形状。

---

## 3. 方案设计

### 3.1 用原生 HTML5 拖拽，不引依赖

| 方案 | 结论 |
|---|---|
| `@dnd-kit`（~30KB + 两个包） | ❌ 为一个页面引一套拖拽框架 |
| **原生 `draggable` + dragover/drop** | ✅ 采用 |

**理由不是"能省则省"，是这个仓库已经表过态**：`globals.css` 里为了三个动画类
手写了 keyframes，注释写着「补上真实实现，而不是加一个依赖」。
一个后台的同级列表排序，原生 API 够用。

代价写明：**不支持触屏拖动**。运营端是桌面工具（Rail + 面板 + ⌘K），
且 ↑/↓ 全程保留 —— 触屏与键盘用户走按钮那条路。

### 3.2 新接口：整段顺序，不是 N 次交换

```
POST /ops/perm/functions/reorder   { codes: ["OPS_DASHBOARD", "OPS_MERCHANT", ...] }
POST /ops/perm/points/reorder      { functionCode: "OPS_IAM", codes: [...] }
```

服务端按数组下标重写 `sort = (i+1)*10`。

**为什么不复用 `move` 连点 N 次**：N 个请求会产生 N-1 个中间状态，
任何一个失败都会把顺序卡在半路 —— 而那半路顺序**看起来是合法的**，没人能发现它错了。
整段提交是一个事务，要么全对要么不动。

**校验**：`codes` 必须与该父级下的现有集合**完全相同**（同一个多重集合），
只是顺序不同。多一个、少一个、混进别的父级的 —— 一律拒绝。
这是「不能跨父级拖」在服务端的兜底：前端拦是体验，服务端拦才是约束。

### 3.3 模块设计

**新增**

| 模块 | 路径 | 职责 |
|---|---|---|
| `reorderFunctions` / `reorderPoints` | `PermConfigService` + 控制器 | 整段重写 sort，挂 `iam:role:grant` |
| `MenuOrderTree` | `ops-web/app/iam/menu-order-tree.tsx` | 页面局部组件：两层列表 + 拖动 + ↑/↓ |

**不改共享 `Tree`**：它同时服务于角色抽屉的勾选树，那里拖动没有意义。
把拖动塞进去等于让一个被两处使用的组件长出一半用不到的状态。
（P1 的顺序是「复用 → 扩展 → 才新建」，这里扩展会伤到另一个调用方，所以新建。）

**保留** `move` 接口与 ↑/↓：它们已有测试，且是键盘可达的那条路。

### 3.4 交互细节

- 拖起来的行半透明；**落点用一条 2px 的横线**指示（插在哪两行之间），不用整行高亮
  —— 高亮说不清是「放在它上面」还是「替换它」
- 跨父级拖动时**不显示落点线**，松手无事发生（不弹错误：拖错了是常事，报错太重）
- 拖动进行中禁用 ↑/↓，避免两条路径同时改
- 松手到接口返回之间，列表用乐观顺序（本地先排），失败则回滚并 toast

## 5. 风险与注意事项

| 风险 | 处置 |
|---|---|
| 不支持触屏 | ↑/↓ 全程保留，是键盘与触屏的可用路径 |
| 乐观更新与服务端结果不一致 | 失败回滚 + toast；成功后 invalidate 重新拉 |
| `sort` 被重写成等差序列，覆盖手工调过的值 | 这正是期望：顺序的真源是这份列表 |
| 拖动中并发点 ↑/↓ | 拖动期间禁用按钮 |
| 新接口要不要也进 e2e 种子一致性守卫 | 不需要：它改的是 `sort`，不改授权 |

## 7. 实施记录

**结果**：后端 708/708、前端 602/602。实机拖动 → 库 → Rail 完整打通并还原。

### 实机验证挖出两个缺陷，都不是拖拽本身

**① 判定依赖「两次事件之间发生过渲染」。** 第一版把拖动中的项只存在 state 里，
于是 `onDragOver`/`onDrop` 的闭包依赖 dragstart 之后发生过一次重渲染。
真实拖动有帧间隔所以看着没问题 —— 但那是巧合不是保证。改成 ref 供判定、state 供渲染。

**② 没有菜单叶子的分区拿不到 sort，顺序怎么调都不动。**
`build()` 统计「这个分区本来有没有叶子」时**把 ACTION 点也算进去了**：
经营看板有 1 个 ACTION、0 个菜单点，于是被判成「有叶子但一条都没授权」而整个分区
不返回 —— 端上没有它的 sort，它被前端的「缺 sort 就跟着前一项」规则钉死在首位。
**表现是：拖了、库变了、界面纹丝不动，且不报错。**

注释里写的意图（「本来就没有叶子的分区要留」）是对的，是 ACTION 点破坏了它。
`build()` 加一个 `candidate` 谓词区分「算不算本视图的叶子」，并补了回归测试。

这两个都只有真的去拖一次才会暴露 —— 单测全绿。
