## 〇、一眼看全：这条链上有几屏、每屏交出什么

```
商品卡 ＋        goods 加入购物车        goods 立即购买      store 再来一单
     │                  │                      │                   │
     └──────────────────┴───────┬──────────────┘                   │
                                ▼                                  │
                          cart 购物车  ◀────────────────────────────┘
                                │  勾选（限一种取货方式）
                                ▼
                     order-confirm 确认订单
                                │  提交（幂等 key）
                                ▼
                          pay 收银台 ── 取消 ──▶ orders
                                │  回查订单状态为准
                                ▼
                     pay 成功态（码 / 引导语）
                                │
                     ┌──────────┴──────────┐
                     ▼                     ▼
              orders 订单列表  ◀──▶  order 订单详情 ──▶ after-sale / review-write
```

**三处「不另开一条链路」的决定**，看清单时要记着：

| 决定 | 后果 |
|---|---|
| 立即购买 = 先加购再进结算 | 详情页不需要另一套下单逻辑；代价是车里会多出一件 |
| 一次结算 = 一种取货方式 | 确认页只服务一种收货信息形态；勾选因此被约束在一组内 |
| 跨商家 = 拆成 N 笔子订单、共享 `payGroupNo` | 用户感知仍是「买了一次」，但三处都要提前说清会拆几单 |

## 一、加购入口（进购物车之前）

| # | 位置 | 元素 | 点了发生什么 | 边界 / 失败 |
|---|---|---|---|---|
| A1 | `home` `category` `search` `merchant` `store` 的商品卡 | 右下角「＋」 | 取**第一个有货的**规格加购 1 件，附**飞入动效**；全规格无货时这里画的是「已售罄」不是「＋」 | 五页写法逐字相同：加购被业务规则拒（生鲜过了截单、限购、超区）时 toast 原话。多规格不弹规格选择；落点是购物车图标的**真实坐标**。⚠️ 取的是**下标 0**，不是「第一个有货的」—— 见 §八 G9 |
| A2 | `store` 常买项 | 「加购」 | 加购 1 件 + toast | 这一处**没有飞入动效**（那一屏没有购物车落点）|
| A3 | `goods` | 规格选项 | 换选中的 SKU | 组合不存在时**点了没反应**（不禁用、不提示）|
| A4 | `goods` | 数量 −／＋ | `1 ≤ qty ≤ min(限购, 可售库存)` | 两个上限**缺省都是不限**，不是 0。换规格时数量跟着回落到新 SKU 的上限内。提交时后端仍会锁库存 —— 那才是真源，这一层只是让人早点知道 |
| A5 | `goods` | 加入购物车 | 加购当前 SKU × qty，飞入动效 | 禁用条件有**四条**（`buyable`）：没命中 SKU、售罄、过了当日截单、预约类没选时段。按钮文案说前两条、截单有一枚红 chip，**其余由操作条上方的一句话说明**（`buyBlockedReason`，判据与 `buyable` 共用一份；已经说过的返回空串，不重复说）|
| A6 | `goods` | 立即购买 | **先加购**，再跳确认页只带这一个 SKU | 禁用条件同 A5；预约类把已选时段一起带过去 |
| A7 | `goods` | 操作条上的购物车图标 | `switchTab` 到购物车 | 角标 = 车里总件数，>99 显示 `99+` |
| A8 | `goods` | 分享图标 | **空实现**（`@tap="() => {}"`） | 见 §八 缺口 |
| A9 | `store` | 常买项加购前置判断 | 打烊、失效各有专门一句 toast，不进加购 | 加购被业务规则拒（生鲜过了截单、限购、超区）时 toast 原话 —— 不接住的话点了没反应，用户只会以为按钮坏了 |
| A10 | `store` | 一键再来一单 | 取最近一笔非取消订单整单复制进车 | 未登录先跳登录；没有历史单说一句；**丢了什么、涨价了什么都要说出来** |

> A1 与 A5 的差别值得记住：列表页的「＋」不问规格，详情页才问。
> 这是刻意的 —— 邻里商品多数只有一个规格，为一个规格弹一次面板是纯摩擦。
>
> 两处挑 SKU 的口径**曾经不一样**（详情页选「第一个有货的」、列表页直接取 `skus[0]`），
> 清点时发现，当天修成同一条口径（G9）。

## 二、购物车 `pages/cart`

### 2.1 普通态

| # | 元素 | 出现条件 | 点了发生什么 | 边界 / 失败 |
|---|---|---|---|---|
| C1 | 顶栏「共 N 件」 | 车非空 | 只读 | N = **全部件数，含失效件**（与 tabBar 角标同一个数）|
| C2 | 顶栏「编辑」 | 车非空 | 进编辑态 | 进出都**清空上一次的标记** |
| C3 | 履约组头勾选框 | 普通态 | 整组勾／取消 | 勾的是另一种取货方式时，**前一组整组让位** + toast 说明 |
| C4 | 履约方式 chip | 恒在 | 只读标签 | — |
| C5 | 「一次只结一种取货方式」 | `groups.length > 1` | 只读 | 只有一组时不画 —— 那时它是句废话 |
| C6 | 商家段头勾选框 | 普通态 且 `merchants.length > 1` | 整段勾／取消 | 同 C3 的让位规则 |
| C7 | 商品行勾选框 | 恒在 | 勾／取消这一件 | 同 C3 的让位规则 |
| C8 | 商品行主体（图 / 标题 / 规格） | 恒在 | 进商品详情 | **编辑态下不跳** —— 那时手指是在勾东西 |
| C9 | 减号 | 恒在 | 数量 −1 | `qty ≤ 1` 时**禁用**（透明度 0.35）。此前它会传 0 下去 = 静默删除 |
| C10 | 数量 | 恒在 | 弹输入框改数量 | 数字键盘；上限已知时提示「最多 N 件」，未知时「想买几件？」；取消不动；输 0 或乱输**忽略**（删除是另一个动作）；超上限截断；与原值相同不发请求 |
| C11 | 加号 | 恒在 | 数量 +1 | 到 `available` 上限时禁用；后端没给 `available` 时兜底上限 999 |
| C12 | 「仅剩 N 件」 | `0 < available ≤ 5` | 只读 | 有货时报数字是噪音，只有快没了才改变决定 |
| C13 | 赠品行 | `giftQty > 0` | 只读 | 不计价 |
| C14 | 拆单提示 | `merchants.length > 1` | 只读 | 「来自 N 家店，结算时会生成 N 笔订单，一次付清」 |
| C15 | 底栏全选 | 车非空 | 勾／取消**当前那一组** | 没勾任何东西时作用于默认组，不是全车 |
| C16 | 底栏「合计（不含运费）」 | 车非空 | 只读 | 只算勾选的；**运费在下一页按地址算**，不说这句会被当成算错了 |
| C17 | 底栏「去结算 (n)」 | 车非空 | 跳确认页，只带勾选的 SKU | 一件没勾时**灰且点了出一句** |

### 2.2 编辑态

| # | 元素 | 变化 |
|---|---|---|
| C18 | 顶栏 | 「编辑」→「完成」 |
| C19 | 组头 / 商家段头勾选框 | **消失** —— 那一刻的动作是删，与结算的分组无关 |
| C20 | 商品行勾选框 | 语义从「我要买」变成「我要删」（store 里是**另一个字段**）|
| C21 | 失效件 | 也可勾 —— 它们正是最该被删的那些 |
| C22 | 底栏全选 | 跨组、含失效件 |
| C23 | 底栏按钮 | 「去结算」→「删除」；标记为空时灰 |
| C24 | 删除 | 二次确认弹层（「删除这 N 件商品？／删掉之后要重新加购」），确认后批量删；删空则自动退出编辑态。一件没勾时点它会 toast 一句（与「去结算」同一条规矩：灰按钮必须配一句话）|

### 2.3 失效区

| # | 元素 | 出现条件 | 说明 |
|---|---|---|---|
| C25 | 「失效商品 N」 | 有失效件 | 排在有效件之后，**单独一张卡** |
| C26 | 原因文案 | 恒在 | 端上按 `invalid` / `available` 组装：已下架 ／ 已售罄 |
| C27 | 「移除」 | 恒在 | **只删这一件**，不顺手清空所有失效的 |
| C28 | 整行压暗 | 恒在 | 压暗但**不隐藏** —— 用户要能看见自己加过什么 |

> **不许出现的东西**：一键「清空失效商品」。那是替用户做主 ——
> 他可能只想去掉其中一件、把别的留着等它恢复。守卫钉着这一条。

### 2.4 空态

| # | 元素 | 出现条件 |
|---|---|---|
| C29 | 「购物车还是空的 / 去看看邻居们都在买什么 / 去逛逛」 | **第一次拉完之后**且车空 |

> 不等第一次拉完的后果：冷启动那一瞬间空态先闪一下再被商品顶掉，
> 看起来像刚被谁清空了。

### 2.5 三条不显眼、但用户一定会感知的规则

| 规则 | 内容 | 不这么做会怎样 |
|---|---|---|
| **默认勾谁** | 没有历史勾选时，默认全勾**件数最多的那一组** | 取「第一组」的话，一件很久以前加的快递商品会让默认勾选只剩那一件 |
| **让位** | 勾另一种取货方式 → 前一组整组让位，出一句 toast | 静默让位的话，用户以为刚才勾的那几件还在 |
| **全不选是一种意图** | 用户手动取消全部之后，重新进页**不许替他勾回来** | 否则「挑完了，一件都不要」会被当成「还没挑过」 |
| **加购不抢勾选** | 商品页加购的那件默认勾上，但**取货方式对不上时什么都不做** | 否则在他看不见购物车的地方，把之前勾的三件静默取消 |

## 三、确认订单 `pages/order-confirm`

### 3.1 页首：付款前必须说的三件事

| # | 元素 | 出现条件 | 语气 |
|---|---|---|---|
| D1 | 没有共同支持的支付方式 | 后端给了能力且交集为空 | **拦下**（danger）|
| D2 | 商家收款额度不足 | 有商家 `quotaExhausted` 或 `quotaWouldExceed` | **拦下**（danger）|
| D3 | 有商家开不了票 | 有商家 `invoiceCapable = false` | 提醒（warning）|

> 三条的共同后果都是**付款那一刻才炸**，而那时平台既解释不清也补救不了。
> 放页首不放底部：注意力从上往下走，放底部他会先看完金额才看到「其实付不了」。

### 3.2 收货信息区：按履约方式变形

| 履约方式 | 区里是什么 | 可点吗 |
|---|---|---|
| 自提点自提 | 自提点名 · 归属社区 · 到货说明 · 地址 | 只读 |
| 送货上门 / 快递 | 收货人 · 电话 · 「更换」· 地址全文 | 整块可点 → 地址簿（选择模式）|
| 上门预约 | 同上（**师傅要知道去哪**）+ 独立的时段卡 | 同上 |
| 到店核销 / 即时发放 | 一句说明 | 只读 |

| # | 元素 | 出现条件 | 行为 |
|---|---|---|---|
| D4 | 「请选择收货地址 / 去添加」 | 需要地址且一条都没选中 | 进地址簿 |
| D5 | 送不到**点名是哪一家** | 自送单 且 有商家超出配送半径 | 只读；同时拦住提交 |
| D6 | 「这一单要送到『当前位置』？」 | 需要地址 且 当前位置是临时定位 | 带坐标跳新建地址页，**不替他偷偷存一条** |
| D7 | 预约时段卡 | 上门预约 | 弹面板选时段 |

> D7 的面板最多列 12 档，**过去的时段不列**（后端也会拒，早点拦住比让他撞一次好）。
> 已选的那一档打勾 —— 这是系统动作面板做不到的一件事。

### 3.3 商品与优惠

| # | 元素 | 出现条件 | 行为 / 边界 |
|---|---|---|---|
| D8 | 按商家分段 + 段头店名 | `merchantSegments.length > 1` | 只读。**这一页才是拆单真正发生的地方** |
| D9 | 拆单提示 | 同上 | 「这些商品来自 N 家店，将生成 N 笔订单，一次付清」 |
| D10 | 赠品行 | 有赠品 | 只读，不计价 |
| D11 | 支付方式（在线 / 当面付） | **只在真有得选时才画** | 切到当面付追加一句「平台券用不了」并说明为什么 |
| D12 | 优惠券 | 恒在 | 弹面板；第一项是「不使用」；无可用时点了不弹 |
| D13 | 积分抵扣 | 开关开 且 余额 > 0 | 不可用时**仍显示余额并说明原因**，只是没有开关 |
| D14 | 备注 | 恒在 | 最长 255 |

> D11 有一条自愈：后端不再给线下时**当场退回线上**。
> 不退的话，用户先选当面付、再把履约改成快递，选项已经消失而值还是 OFFLINE，
> 下单被拒而屏幕上看不出他选了什么。
> D12 同理：已选平台券又改成当面付 → 把券摘掉。

### 3.4 金额与提交

| # | 元素 | 出现条件 | 行为 / 边界 |
|---|---|---|---|
| D15 | 金额明细（商品 / 运费 / 优惠 / 积分抵扣 / 可得积分） | 有金额 | **以后端试算为准**，端上不自己算 |
| D16 | 「网络不稳，这里是估算金额」 | 服务端试算失败 | 兜底显示本地估算，但要说出来 —— 两个数长得一模一样 |
| D17 | 底栏标签 | 试算在途时变「计算中…」，金额压暗 | 上一次的数仍然是最好的猜测，所以不换成骨架 |
| D18 | **提交不了的原因** | `canSubmit` 为假 | 一次只说一条，见下表 |
| D19 | 提交订单 | 恒在 | 见 3.5 |

**D18 的顺序**（按「他能立刻动手改的」在前）：

| 顺序 | 条件 | 说的话 |
|---|---|---|
| 1 | 一件商品都没有 | 走空态，不走这条 |
| 2 | 需要地址而没选 | 先选一个收货地址才能提交 |
| 3 | 需要时段而没选 | 先选一个上门时段才能提交 |
| 4 | 有商家送不到 | 换个地址或把这家的货挪出这一单 |
| 5 | 没有共同支付方式 | 分开下单即可 |
| 6 | 商家额度不足 | 暂时下不了单 |

### 3.5 提交这一下会发生什么

```
点提交
  ├─ 自提单但没绑自提点 → toast +（800ms 后）跳选社区页
  ├─ 账号没有手机号     → 弹「留个手机号」，绑完**自动继续提交**
  └─ 都齐了 → createOrder（带幂等 key，重复点提交的是同一个 key）
              → 重新拉购物车 → redirectTo 收银台
```

| 边界 | 处理 |
|---|---|
| 提交中再点 | `submitting` 挡住 |
| 后端拒 | toast 原话，停在本页 |
| 车里那几件已经没了 | 整页换成「这些商品已经不在购物车里了」+ 回购物车 |
| 从地址簿返回 | **重新拉地址簿并接住刚选的那条**，两件事缺一不可 |

## 四、收银台 `pages/pay`

**一页两态**：待支付 / 已支付。判据是订单状态，不是端上的支付回调。

### 4.1 待支付

| # | 元素 | 出现条件 | 行为 / 边界 |
|---|---|---|---|
| P1 | 应付金额（大字） | 恒在 | — |
| P2 | 「本次付款覆盖 N 笔订单」+ 逐店金额 | `subOrders > 1` | 单商家时不画 —— 那等于把总额又抄一遍 |
| P3 | 倒计时 | 有关单时间 | 每秒走；到点变「支付超时，订单已关闭」并锁住支付键 |
| P4 | 支付方式列表 | 后端给了列表 | **不可用的也列出来并显示原因**；点不可用的没反应 |
| P5 | 「支付方式将在下一步确认」 | 列表为空 | 未进件 ≠ 一种都不可用，两者文案不同 |
| P6 | 拦下原因 | 确实配过 且 一种都不可用 | 别只给一个灰按钮 |
| P7 | 立即支付 | 恒在 | 支付中 / 超时 / 被拦时灰 |
| P8 | 取消订单 | 恒在 | 二次确认 → 取消 → `redirectTo` 订单列表 |

**P7 点下去的顺序**（这条顺序是所有支付接入最容易错的地方）：

```
① 先向后端下单拿真参数（payOrder）      ← 不能反过来
② 再唤起收银台（requestPayment）
③ 用户取消 → toast「已取消支付」，单还在，可换一种方式再来
④ 唤起失败 → 弹**通道的原话**（未开通、appid 不匹配、签名错…）
⑤ 唤起成功 → **回查订单状态**为准，端侧返回值不作数
⑥ 顺带收集订阅消息授权，并**上报**（不上报的话后端额度永远是 0）
```

### 4.2 已支付

| # | 元素 | 出现条件 |
|---|---|---|
| P9 | ✓ + 「支付成功」 | 恒在 |
| P10 | 引导语按品类分 | 虚拟 → 兑换码；卡券 → 卡包；有取货码 → 自提点；其余 → 备货 |
| P11 | 取货码 / 兑换码 | 各自有值时 |
| P12 | 「查看订单」 | 恒在 → `redirectTo` 订单详情 |
| P13 | 「继续逛逛」 | 恒在 → `switchTab` 首页 |

| O1 | 七个页签 | 全部 / 待付款 / 待发货 / **待取货** / **待收货** / 已完成 / 售后 |
| O2 | 换页签 | **重新向后端取数**（筛选在后端，不换数据就还是上一个页签的结果）|
| O3 | 订单卡 | 整卡可点 → 详情 |
| O4 | 「去支付」 | 仅待付款；`@tap.stop`，不触发整卡跳转 |
| O5 | 取货码行 | 有码 且 未完成 |
| O6 | 商品行最多 3 条 + 「还有 N 件」 | 超出折叠 |
| O7 | 「还有 N 笔没显示」 | 后端总数 > 本页 50 条 | 
| O8 | 空态 + 去逛逛 | 加载完且这一页签为空 |

> **页签是谓词，不是状态值**：「待取货」= `FULFILLING ∧ 自己去取`。
> 于是加一种履约方式不需要加状态。曾经把 `ARRIVED`/`SHIPPED` 当状态并成一个页签，
> 表现是**买快递的用户在「待取货」下看到自己的单**。
>
> 「售后」是唯一不按订单状态筛的页签 —— 售后是挂在订单上的**另一张单**，
> 一个「已完成」的订单照样可以有一张处理中的售后单。

## 七、反馈形态：什么时候用哪一种

| 形态 | 用在哪 | 规矩 |
|---|---|---|
| toast（无图标） | 让位说明、加购被规则拒、取消支付、一件没勾就结算 | 说完就走，不挡操作 |
| 二次确认弹层 | 删购物车、取消订单 | **危险档（红实心）只给弹层里的最终一击**，页面上的危险操作用描边 |
| 输入弹层 | 改数量、发票抬头、退货单号、申诉理由 | 说明与初值是**两个参数**，不能混（系统弹框那个 `content` 有二义）|
| 选择面板 | 选券、选预约时段 | 当前已选的那一档要打勾 |
| 页内条（warning 底） | 「还差一步」：提交不了的原因、开不了票 | 它不是故障 |
| 页内条（danger 底） | 「拦下了」：没有支付方式、额度不足 | 用户动作不同，所以颜色不同 |
| 灰按钮 | 任何点不动的主操作 | **必须配一句话** —— 同一个灰按钮五种原因，等于什么都没说 |

### 10.1 清单被改对的七处

| 条目 | 原来怎么写 | 实际是什么 |

| A1 | 没提失败反馈 | 五页写法逐字相同，被业务规则拒时 toast 原话 |

> 七处里有五处是**同一种失手**：照着端上的类型声明描述行为，而没去后端核一遍
> 那个字段到底发不发。这正是 [TDD-购物车与下单优化](./TDD-购物车与下单优化.md) §1 缺陷 D
> 的同族 —— 写清单的时候我自己又踩了一次。

### 10.2 七处代码问题与修法

按「改起来多大、影响多深」排，前三条建议优先。

#### G16 · 售后入口对履约中的订单是关着的

**根因**：`canAfterSale` 的判据是 `["PAID","ARRIVED","SHIPPED","COMPLETED"].includes(status)`，
而 `ARRIVED` / `SHIPPED` 在状态模型重整时已经并成 `FULFILLING`（见 `OrderStatus` 的注释）。

**为什么类型没抓到**：数组字面量被推断成 `string[]`，`Array<string>.includes()` 收任何字符串。
判据用了两个「合法的字符串、非法的状态」，编译器无话可说。

**修法**：

```ts
// 把集合标成 OrderStatus[]，废弃值当场编译不过
const AFTER_SALE_STATES: readonly OrderStatus[] = ["PAID", "FULFILLING", "COMPLETED"];
const canAfterSale = computed(
  () => !!order.value && AFTER_SALE_STATES.includes(order.value.status),
);
```

同一处理顺手用在 `canInvoice` 上 —— 它排除的 `"CLOSED"` 同样不是 `OrderStatus` 的成员。

**回归位**：给订单详情页加组件测试，`FULFILLING` 的单必须能看到售后入口。

#### G14 · 取消订单：该给的没给，给了的是死路

**根因**：端上 `canCancel = WAIT_PAY || PAID`，而后端状态机是
`WAIT_PAY → {PAID, CANCELLED, CLOSED}`、`WAIT_OFFLINE_PAY → {PAID, CANCELLED}`、
**`PAID → {}`**。两边对不上，两个方向都错。

**修法**：

```ts
const canCancel = computed(() =>
  order.value?.status === "WAIT_PAY" || order.value?.status === "WAIT_OFFLINE_PAY",
);
```

已付款要退钱走的是**售后**，不是取消 —— 这也正是 G16 修好之后该走的那条路。
顺带把收银台的 `cancel()` 补上 `try/catch + toast`：它现在
`await api.cancelOrder(...)` 之后直接跳转，**失败时既不跳也不说**，
而同一个动作在订单详情页是接住并 toast 的（两处同一个动作两套写法）。

**回归位**：状态机的可迁移集合是后端的真源，端上不该再抄一份。
更彻底的做法是让 `OrderVO` 带上 `cancellable`，端上只读它 —— 那是一次契约变更，
可以与 G15 一起做。

#### G15 · 四个字段端上声明了、后端不发

| 字段 | 端上用它做什么 | 真实链路上的表现 |
|---|---|---|
| `reviewed` | 「去评价」的第二个条件 | 恒 undefined → 已评价的订单照样显示按钮 |
| `redeemCode` | 兑换码卡 | 卡永不出现；后端把三种码合在 `verifyCode` 里，于是虚拟商品的码落进「取货码」卡，**标签是错的** |
| `afterSale` | 「售后进行中」卡 + 填退货单号 + 提出申诉 | 整张卡与两个动作永不出现 |
| `payGroupNo` | 详情页的拆单补充说明 | 那一句不出现 |

**为什么一直没人发现**：四个都是**可选字段**，「契约里的必填字段后端必须真的有」
那道守卫按设计跳过可选字段；而 **mock 四个都有**（`payGroupNo` / `redeemCode` / `afterSale`
在建单与售后时写上，`reviewed` 在评价成功后置真）—— 本机点一遍全都对，
只有真机是哑的。这与「默认关闭的那一半没人测」是同一个形状。

**修法（两条路，建议混用）**：

| 字段 | 建议 | 理由 |
|---|---|---|
| `afterSale` `payGroupNo` | **后端补进 `OrderVO`** | 都是订单自身的事实，端上没有别的来源；`payGroupNo` 库里本来就有 |
| `redeemCode` | **端上改口径** | 后端已明说三种码共用 `verifyCode`，端上不该再要一个字段；改成按 `items[0].type` 决定标签叫「取货码 / 核销码 / 兑换码」 |
| `reviewed` | 两条都行 | 后端补最省事；不补的话端上要另开一次查询，为一个按钮多一个来回 |

**守卫要一起改**，否则这一类还会再长出来：现在的棘轮只量
「后端发了、端上没接」一个方向，**反方向只覆盖必填字段**。
建议给可选字段也加一条棘轮（只许降不许升），先量出基线再说。

#### G17 · 订单列表与详情没有失败态

列表的 `orderList` 不 catch（同一个 `Promise.all` 里的 `afterSaleList` 反而 catch 了），
失败就是一页空白、无提示、无重试；详情整页挂在 `v-if="order"` 上，拉不到连外壳都不渲染
（连标题栏与皮肤根节点都没有）。传输层只集中处理 401，其余错误不弹。

**修法**：照 `pages/community` 已经做过的那一套 —— `loaded / failed` 两个标记，
失败时渲染一句说明 + 重试按钮。那一页有现成的组件测试可以照抄。

#### G12 · 数量能设到库存之上

商品详情的 `stepQty` 只封 `limitPerUser`；加购与预览都不校验库存
（预览**刻意**不锁库存，因为用户会在结算页反复改地址）。
于是「库存 3 件、买 50 件」一路走到提交才被后端的锁库存拒。

**修法**：`stepQty` 的上限取 `min(limitPerUser || ∞, sku.stock)`，
并沿用购物车那条「仅剩 N 件」的提示。**不改后端** —— 提交时锁库存那一道必须留着，
它才是真源，端上这一层只是让人早点知道。

#### G13 · 有一条禁用原因页面上不说

没选预约时段时，「加入购物车 / 立即购买」双双变灰而页面上一个字都没有。
（售罄写在按钮文案里，过了截单有一枚红 chip，只有这一条没有。）

**修法**：与结算页 `submitBlockedReason` 同一个做法 —— 一个 `buyBlockedReason`
