## L1 · 这份解决什么

**把发码从「三处各写一遍」收成一个模块**，并回答三个一直没答的问题：

1. B 端注册发码怎么防刷 —— 小程序有 openid，**App 怎么办**；
2. 怎么在不打扰真实用户的前提下加人机验证；
3. 三端（C / B / 运营）的差异要不要各写一套。

结论先给：

> **不要把工程投在「识别请求是不是来自真 App」上 —— 那件事在安卓上无解。**
> 投在「统一发起主体 + 系统水位分级」上，两者都不依赖任何外部能力。

## L2 · 一、先钉住无解的那一半

**服务端无法识别请求是不是来自真 App。** App 装在别人手里，任何内置的密钥、
签名算法、请求头约定都能被反编译取走。**客户端无法自证**，这是结论不是选型。

唯一的例外是 **iOS App Attest**：它可信是因为签名由**苹果的服务器**做，
不在你的包里，攻击者拿不到苹果私钥。**安卓国内没有等价物**
（Play Integrity 要 GMS）。这个不对称要写明白，不能含糊过去。

### openid 也不是那道闸

一个常见的误解：「小程序有 openid，所以能证明请求来自小程序」。

**挡不住的是这件事**：攻击者自己走一遍你的小程序登录，拿到一个**属于他自己的
合法 openid**，然后拿它刷接口。

openid 真正的价值不是「证明来自小程序」，是**它给了一个攻击者难以批量获取的
稳定标识** —— 要刷一万次就要一万个微信号，而微信号有获取成本。
**这是成本壁垒，不是身份证明。**

想清楚这一点，App 侧该做什么就明确了：**造一个成本相当的标识**。

## L2 · 二、统一的关键抽象：发起主体（Principal）

> **openid 与设备凭证不是两种东西，是同一个东西的两种实现。**

它们提供的都是「一个攻击者难以批量获取的稳定标识」，用来回答
**「这次发码算在谁头上」**。模块只认这一个概念：

| 来源 | 取自 | 可用于 | 批量获取成本 |
|---|---|---|---|
| `ACCOUNT` | 已登录会话的 `userNo` | 换绑手机号等登录后场景 | 最高（要有真账号） |
| `WX_OPENID` | 小程序 `code2session`<br>（MP / APP / OA 三种同一套处理） | C 端小程序、B 端小程序 | 高（要微信号） |
| `DEVICE` | App 首启注册的设备凭证 | C 端 App、B 端 App | 中（要过注册闸） |
| `ANON` | 以上都没有（H5、或直接打接口） | 兜底，走最严路径 | 零 |

**这个抽象让三端的差异消失**：闸门只看 Principal 的 id 与强度，
不关心它从哪来。以后加支付宝小程序只是多一个 `ALIPAY_USERID` 来源，
闸门一行不用改。

### 已有的件：`IdentityType` 已经把渠道身份列全了

仓库里 `IdentityType` 有 `WX_OPENID_MP` / `_APP` / `_OA` / `WX_UNIONID` /
`APPLE_SUB`，并按识别强度排了序。**发码这一侧没有用上它** —— 这份方案不重造
身份体系，只是把它接进发码链路。

## L2 · 三、量到的缺陷：第四道闸在 B 端是空的

```
C 端  MpUserController   → authService.sendOtp(phone, userNo)   ← 四道闸齐
B 端  BizAuthController  → authService.sendOtp(phone)           ← 只有三道
```

第四道闸（**按发起人每日**）挡的正是「一个会话对着不同号码轮着发」：
每个号都在自己额度内、IP 换个网络就绕开，**从任何单一维度看都不异常**，
而受害者是被发的那些号。**B 端登录页此刻没有这道防线。**

`MpUserController` 的注释写着「B 端登录页没有会话可言，那里仍然只能靠
号码与 IP 两道」—— 那句话在**加设备凭证之前**成立，加了之后就不成立了。

## L2 · 四、第一根轴：把攻击成本抬起来

按**攻击者要多花什么**排，不按技术新旧排：

| 手段 | 攻击者要多付出 | 性质 |
|---|---|---|
| **设备凭证**（密钥在 Secure Enclave / StrongBox **自己生成**） | 每个身份都要完整走一次注册。<br>**包里没有钥匙可偷 —— 它从没进过包** | 基础 |
| 注册时人机验证 | 打码平台，量级 ¥0.005/次 | 抬价 |
| 注册频次限流（按 IP /24） | 住宅代理池 | 抬价 |
| 设备指纹 | 改机工具 / 云真机。<br>它的主要作用是**留痕做关联**，不是拦截 | 抬价 + 留痕 |
| iOS App Attest | 批量真机 | **硬闸（仅 iOS）** |
| **延迟授信** | —— **绕不过，只能等** | **最有效** |
| 通道每日总量熔断 | —— 无法绕过 | 损失上限 |

### 最关键的一行不抬成本，它砍收益

**新注册的设备当天只能发 1 条，且必须完成一次真实登录才升级。**

于是攻击者注册一千个设备，当天也只能发一千条 —— 而且是**一千个不同号各一条**
（同号 60 秒那道闸还在）。

> **批量注册没有被阻止，是它的产出被摊薄到无意义。**
> 这比试图阻止它现实得多。

### 把账算完

```
攻击者要发 1000 条：
  1000 次打码 ≈ ¥5  ＋ 住宅代理 ≈ ¥20–50
  ＋ 1000 个不同手机号   ← 这一项才是真门槛
  ────────────────────────────
  换来：平台短信成本 ≈ ¥30–50，分散在 1000 个陌生号上
```

他花的比我们多，而两种收益都不成立：骚扰某个特定的人被同号限流挡死，
烧平台的钱他自己先亏。**剩下只有纯破坏** —— 对它靠总量熔断兜底。
（金额是数量级估算，按实际合同价核。）

### 注册协议：六步

1. **客户端生成密钥对** —— Android 用 Keystore、iOS 用 Keychain，
   硬件支持时落 StrongBox / Secure Enclave。私钥不出安全区。
2. **取一份完整性证明** —— iOS 调 App Attest；**安卓直接跳过**，
   不要为它假装有一层。
3. **过一次人机验证** —— 注册是低频动作，这里可以拦得比发码狠。
4. **提交注册** —— `公钥 + 设备指纹 + 完整性证明 + 验证码 token`，
   服务端存一条设备记录，**初始信任级 = 0**。
5. **此后每次发码都签名** —— 用私钥签 `nonce + 手机号 + 时间戳`。
   **签名不是用来防伪造设备的**，它防的是**凭证被抄走复用**：
   抓包拿到别人的 `device_id` 没有用，私钥在安全区里出不来。
6. **信任级随行为升** —— 完成一次真实登录 → 级 1；用满 7 天无异常 → 级 2。

### 批量注册的痕迹：识别与整批作废

这是**唯一一处不对称站在我们这边**的地方：他注册一千个是线性成本，
我们识别出一批并整批作废是常数成本。

| 信号 | 正常 | 批量 |
|---|---|---|
| 注册时间分布 | 随机散布 | 聚在几分钟内 |
| 设备指纹多样性 | 机型/分辨率/时区各异 | 高度雷同**或完全随机**（两者都异常） |
| 注册后行为 | 注册 → 登录 → 用起来 | **只发码，从不登录** |
| 手机号归属 | 散布 | 集中在少数号段 |

## L2 · 五、第二根轴：按系统水位分级放行

### 为什么以系统水位为主、单请求风险为辅

判断「这一个请求是不是坏的」很难：信号弱、易误伤，而且需要历史数据才准
—— 我们现在两样都没有。

判断「系统整体是不是在被刷」**很容易也很准**：数一下今天发了多少条就行。

代价是水位高时会误伤一部分真实用户（要拖一次滑块），
**但那只发生在系统确实被攻击时** —— 平时一个人都看不到。

### 水位怎么算

| 档 | 判据（任一命中即升档） | 含义 |
|---|---|---|
| 绿 | 都不命中 | 常态 |
| 黄 | 近 1 小时发送量 > 基线 × 2<br>或 今日发送量 > 基线 × 1.5<br>或 今日新设备注册量 > 基线 × 2 | 可能在被刷 |
| 红 | 近 5 分钟发送量 > 基线小时量 × 0.5（突刺）<br>或 今日发送量 > 基线 × 3 | 正在被刷 |

> **基线取过去 7 天同时段的中位数，不取均值。**
> 均值会被一次攻击拉高 —— 今天被刷了一万条，明天的基线就跟着涨，
> **同样的攻击第二次就不报了**。中位数对离群值不敏感，这正是我们要的。
>
> 同时段：凌晨三点的一百条与下午三点的一百条，异常程度差得远。

### 动作矩阵

水位定**严格程度**，Principal 强度定**这个人具体怎么走**：

| | `ACCOUNT` | `WX_OPENID` | `DEVICE` 老 | `DEVICE` 新 | `ANON` |
|---|---|---|---|---|---|
| **绿** | 无感 | 无感 | 无感 | 无感 | 滑块 |
| **黄** | 无感 | 无感 | 无感 | 滑块 | 滑块 + 降额 |
| **红** | 无感 | 滑块 | 滑块 | 滑块 + 降额 | 拒绝 |

两条刻意的选择：

- **红档下 `ACCOUNT` 仍然无感** —— 他已经登录了，发码是为了换绑手机号。
  被攻击时把老客户的正常操作也拦掉，代价比漏过几条大。
- **`ANON` 一路都要验** —— 它涵盖 H5 与直接打接口两种，前者是真实但少见的
  用户，后者是攻击的默认形态。让它们走同一条较严的路，比试图区分它们现实。

## L3 · 六、模块结构

```
OtpModule
├─ PrincipalResolver   把一次请求解析成 Principal（四种来源，按强度取最高）
├─ OtpSendGuard        四道闸              ← 已有，改为一律传 principal
├─ OtpWaterMark        系统水位统计
├─ ChallengePolicy     水位 × Principal 强度 → 放行 / 滑块 / 拒绝
├─ CaptchaService      出题与核验          ← 已有，扩滑块题型
├─ OtpStore            码的存取与一次性消费 ← 已有
└─ SmsPort             通道抽象            ← 已有，补每日总量熔断
```

**只有两个新件**（`PrincipalResolver` 与 `OtpWaterMark`），其余是把已有的接起来。
这也是这份方案值得做的理由：投入小，而它补的是一个**正在生效**的洞。

### 统一入口

```
POST /{mp|biz|ops}/auth/otp/send
  Header: X-Client        端标识（MP_WECHAT / IOS / ANDROID / H5）
          X-Device-Id     App 有；小程序无
          X-Device-Sign   设备私钥对 nonce+phone+ts 的签名
          Authorization   已登录时有
  Body:   { phone, scene, captchaToken? }
```

`scene` 说明**这条码用来做什么**（登录 / 注册 / 换绑 / 支付确认）——
不同用途的额度与文案本来就该不同，而今天它们共用一份。

> **三个端保留各自的路径，不合并成一个。**
> 前缀纪律之外有个更实际的理由：三端的鉴权链本来就不同
> （C 端 `ctk_`、B 端 `btk_`、运营 `otk_`），而**限流策略将来一定会分开** ——
> 运营端发码的正常量与 C 端差两个数量级，共用一套阈值意味着两边都不准。
>
> 共用的是**实现**（同一个 OtpModule），不是**端点**。

### 判定链

1. **解析 Principal** —— 按强度取最高。
   **签名验不过 = 降级成 ANON，不是报错** —— 报错会告诉攻击者「这里有一道签名闸」。
2. **四道闸** —— 同号 60 秒 → **同 Principal 每日** → 同号每日 → 同 IP 每小时。
   顺序有意义：**按发起人的那道要在按号码之前**，否则被拒的那次已经占掉了
   受害号码的额度。
3. **算水位**。
4. **定动作**（上面那张矩阵）。
5. **发码** —— **闸在生成码之前**：放在之后的话，被拒的那次会把上一条
   还没用的有效码冲掉，而用户看到的是「操作太频繁」，两件事对不上。
6. **记账** —— 每条都落 `sys_notify_log`：Principal 来源与 id、端、水位、
   动作、通道回执。**水位统计的输入就是它**，不额外建表。

## L3 · 七、滑块：服务端要验什么

只验落点是**没用的** —— 那是一个几百以内的整数，脚本试几十次就中。四条一起验：

| 验什么 | 为什么 |
|---|---|
| 落点在缺口 ±4px | 基本正确性 |
| **采样点数 ≥ 15** | 真人拖 200px 会产生几十个移动事件，脚本只发它需要的那几个 |
| **步长变异系数 > 0.25** | **这一条才是真正挡脚本的** —— 匀速时 std/mean ≈ 0，人手做不到匀速 |
| 耗时 300ms–20s | 太快是脚本，太慢是挂着的会话 |
| 题目一次性，答对即作废 | 否则一道题能重放无数次 |

缺口位置**只存服务端**，图片按题目 id 现生成。把答案随图下发是最常见的错 ——
那时滑块只是一段动画。

> ⚠️ **只判「落点分散度」是不够的。** 原型第一版写的是
> 「落点分了几个桶 > 3」，而 **5 个等距点就能凑出 5 个桶** ——
> 一个走 5 步、停 400ms 的脚本照样通过。**是拿脚本实际打了一遍才发现的。**

### 键盘操作要用另一套判据

**「步长要有抖动」是为指针设计的**，而键盘天然规整：一次按键固定走 7px，
变异系数 ≈0.16 —— **永远过不了那道门**。原型第一版就是这么写的，
实测把自己的无障碍通道挡死了。

给键盘掺随机抖动是拿假信号骗自己的判据。正确做法是承认**两种输入的正常形态
本来不同**：键盘改判「按键 ≥ 10 次且耗时 ≥ 300ms」。脚本走键盘路同样要发
10 次事件并等够时间，**成本没被放宽**，而真实键盘用户不再被误杀。

## L3 · 八、落地顺序

| 步 | 动作 | 依赖 |
|---|---|---|
| 1 | **限流挪 Redis** —— 今天是进程内，多实例下实际阈值是「每实例 N 次」 | 无 |
| 2 | **`PrincipalResolver` + B 端补上第四道闸** —— 先只用 `ACCOUNT` 与 `WX_OPENID` 两种来源 | 无 |
| 3 | **水位统计，只记录不判定** —— 用真实数据校准阈值倍数 | 1 |
| 4 | **设备注册 + `DEVICE` 来源** —— 新建设备表 | 2 |
| 5 | **延迟授信** —— 新设备当天 1 条，真登录后升级 | 4 |
| 6 | **滑块 + 动作矩阵** | 3、5 |
| 7 | **通道每日总量熔断** —— 成本几乎为零，但它是损失上限 | 无 |

> **第 2 步单独可上线，而且它是唯一一条「现在就在错」的。**
> 不需要设备凭证、不需要水位、不需要滑块 —— 只要把 B 端那次调用
> 从 `sendOtp(phone)` 改成带 Principal 的版本，第四道闸立刻对 B 端生效。
>
> 第 1 步与第 7 步也不依赖任何东西，可以并行。

> **第 3 步先只观察不判定，这一条别省。** 阈值倍数（×2 / ×1.5 / ×3）
> 现在是猜的。拿两周真实数据看一眼分布再定，比上线后天天调强得多 ——
> 而调错的方向是「误伤真实用户」，那个代价比漏过几次刷码高。

## L4 · 九、验收

| 要验的 | 怎么验 |
|---|---|
| 四道闸对三端都生效 | 三端各跑一遍「同一发起人换号连发」，第 N+1 次必须被拒 |
| 降级不报错 | 伪造一个设备签名 → 走 ANON 路径，不是 401 |
| 水位用中位数 | 造一天离群值，验次日基线不被拉高 |
| 闸在生成码之前 | 触发限流后，上一条码仍然有效 |
| 键盘能过滑块 | 指针与键盘用不同判据，套用会把无障碍通道挡死 |

> ⚠️ **第一条要写成会失败的形状。**
> 「B 端换号连发被拒」如果直接写断言，**今天它会绿** —— 因为那道闸不存在，
> 请求根本没走到那里。要先断言**那道闸被调用过**，再断言它的结果。
>
> 否则这条用例在第 2 步做完之前是绿的，做完之后也是绿的，**它什么都没证明**。

## L4 · 十、不做什么

- **不接第三方验证码服务（暂时）**。腾讯云 / 顶象都能用，但要引 SDK、
  过网络、按次计费，而今天真实用户量还撑不起这笔账。自研滑块挡住脚本足够了；
  等真出现众包打码再换 —— 接口形状留成可替换的。
- **不做「检测是否为真 App」**。见 §一。把工程投在一个无解的问题上，
  代价是那些能做的层反而没做。
