# TDD · 门店经营类目

> 状态：**已上线**（后端 a06f812a · B 端 0.4.78/205）· §6 已核对 · 2026-09-20
> 原型：[门店经营类目](https://claude.ai/artifact/2Ajyyb4EbSPyoyHn2PASfY)
> 起因：店主「虽然是自营店，虽然不需要提交资料，但是每个门店也需要经营的类目」；
> 具体表现是虹选鲜果只卖水果，App 里却到处列着蔬菜、日用百货、生活服务……
> 上游：[TDD-品类约束全链路](TDD-品类约束全链路.md)（08-21，待确认）—— 本文是它 §3.1「门店经营类目」
> 与 §④「建品可选范围 = 当前门店的经营类目」的**落地版**，只做这一块，不动它的进件与资质部分。

---

## 1 要解决的是什么

「门店经营类目」这个概念早就有了，数据也在：`mch_store_category` 按门店存，
B 端「我的类目」页底部那份「本店货架」就是它。虹选鲜果·福田店的经营类目现在正是 **水果** 一项
（真机与 C 端店铺页接口都核过：`categories = [{水果, 1}]`）。

缺的是**用上它**。上游 TDD 写了、代码没做的两处：

| 上游设计 | 现在的实现 | 店主看到的 |
|---|---|---|
| 建品时类目可选范围 = **当前门店**的经营类目 | 列平台全量类目树（`GET /biz/category/tree` → `categoryService.tree()`，不分门店） | 建一件梨，要从「电子产品 / 生活服务」里翻过去 |
| 商品类目 ∈ 门店经营类目 | 不在就**自动加进去**（`StoreCategoryPort.ensure`，保存 L881、上架 L1856） | 经营类目会被一次误选悄悄撑大 |
| —— | 「我的类目」页把平台整棵树铺在上面、本店的压在底部 | 以为这些都是自己的类目 |

## 2 概念

- **门店经营类目**：这家门店卖哪几类。按门店存，一家一份（`mch_store_category`，不新建表）。
- **平台类目**：平台维护的全量两级树。它是经营类目的**候选池**，不是任何一家店的类目。
- **自营 / 第三方**：**门店**的经营模式 `mch_store.business_mode`（`MchStore.SELF_OPERATED` / `THIRD_PARTY`）。
  ⚠️ 是门店级不是商家级 —— 自营开店走 `governService.setBusinessMode(storeNo, SELF_OPERATED)`
  （`SelfOperatedServiceImpl` L255）。同一主体下可以既有自营店又有第三方店，按商家判会判错。

规则三条：

1. **商品的类目必须在当前门店的经营类目里。** 不在就拒，不再自动加入
2. **加经营类目：自营门店不需要资质，勾选即生效；第三方照旧走资质闸**（`requireSelectable`，现为「只记不拦」，开关不变）
3. **撤经营类目：底下还有商品就拒**（现有 `STORE_CATEGORY_IN_USE`，`replace` L85，不变）

## 3 为什么把「自动加入」改成「拒」

`ensure` 两处的注释各自写了当时不拒的理由，这里逐条回应：

| 当时的理由 | 现在为什么不成立 |
|---|---|
| 保存 L881：「选一个本店还没摆的类目是他要开始卖这个了，让他先去勾一遍再回来是两趟」 | 前提是「选到的都是他想卖的」。平台树里 6 大类 30 来个二级类，误点一个就永久撑大经营类目，而撤掉要先把商品移走。**经营类目是门店的承诺，不该是一次点击的副作用** |
| 上架 L1856：「硬拒的话商家看到『本店不能卖这一类』，而他明明有资质」 | 改完后建品页只列经营类目，**正常路径上根本走不到这一步**。能走到的只有老商品、多门店互相上架、接口直调 —— 那时一句「请先在经营类目里添加『蔬菜』」正是他需要的出路 |

两趟的代价由 UI 抵掉：建品页类目选择的末尾放一条「添加经营类目」，**就地打开勾选面板**，加完回到原处继续填，不离开编辑页。

## 4 设计

### 4.1 后端

| 位置 | 改动 |
|---|---|
| `MerchantGoodsServiceImpl.save` L881 | `ensure` → **校验**：有门店上下文且 `categoryNo ∉ categoryNosOf(store)` → `GOODS_CATEGORY_NOT_IN_STORE` |
| `MerchantGoodsServiceImpl.toggle` L1856 | 同上（上架那家店） |
| `StoreCategoryPort.ensure` | 两个调用点都撤掉后删除；接口上保留 `categoryNosOf` |
| `StoreCategoryServiceImpl.replace` L56 → `requireSelectable` L155（shop-merchant） | **这家门店**是自营时跳过资质那一段（「启用」校验照做）；第三方不变 |
| 新错误码 | `GOODS_CATEGORY_NOT_IN_STORE`（70068）+ `err.goods.category_not_in_store` 三语：「本店经营类目里没有「{c}」，请先添加」 |

- **没有门店上下文时不校验**（单店老账号、运营代操作）—— 与 `ensure` 原来的 `ctxStore != null` 同一个边界
- **不追溯存量**：规则只在「保存 / 上架」那一刻判。已上架的老商品不受影响，下次编辑时才会被要求
- 草稿也要判：草稿是「打算在这家店卖」，与上架同一个承诺；否则草稿存得进、上架时才拒，是把问题推后
- 不新增接口：经营类目读写沿用 `GET/POST /biz/store/{storeNo}/categories`

### 4.2 B 端

**「我的类目」→ 改名「经营类目」**

- 默认只显示本店已开的经营类目（福田店：水果 · 在售 1），可改显示名；点整行进这一类的商品（现有）
- 贴底一颗「调整经营类目」（`sh-actionbar`），点开是**按一级分组的面板**（`sh-sheet` + `sh-option`）：
  **点灰的加入、点亮的移出**，一下一保存（现有「勾选即保存」，理由不变：拒绝要当场发生）；
  底下有商品的移出被拒，用现有文案「该类目下仍有商品，请先移至其他类目」
- 列表行上**不放左滑 / 长按**：藏起来的手势看不出能点
- 第三方且该类目需要资质时，候选项标「需资质」（现有 `ungranted` 判据），自营不标
- 工作台入口卡同步改名，说明句「本店摆哪几类、叫什么名」→「本店卖哪几类」
- 空态说明「建一件商品，它的类目会自动加进来」→「先添加经营类目，再建商品」—— 改成拒绝后原句是错的

**编辑商品 · 类目**

- 候选 = **当前门店的经营类目**（`mStoreCategories(storeNo)`），不再是平台全量树
- 经营类目只有一项时直接选中，不让他点
- 末尾一颗「＋ 添加经营类目」（`sh-chip--dashed`）：就地打开同一个面板，新加的那一类回填为选中
- 「最近用过」去掉：候选本来就是本店那几类，不再需要

### 4.3 C 端

不改。店铺页类目栏的规则（有在售商品的类目）不变；规则 1 生效后，新商品不会再落到经营类目外。

## 5 边界

| 情形 | 处理 |
|---|---|
| 新门店，一个经营类目都没有 | 建品页类目区只有「添加经营类目」，先加再选。建店时不传类目默认**复制默认店的**（现状，不变） |
| 多门店：A 店有水果、B 店没有 | 在 B 店上下文里上架这件梨 → 拒并提示去 B 店加「水果」。商品挂主体，经营范围在门店（ADR-011） |
| 老商品类目不在本店经营类目里 | 不动；下次保存 / 上架时被要求先加类目 |
| 撤掉最后一个经营类目 | 允许（前提是底下没商品）—— 空店是合法状态 |
| 资质闸开关（sys_config `category.gate.enforce`，商品上架与摆货架读同一个） | 不动。自营跳过资质只是「不判」，不改开关本身 |

## 7 验证

场景测试 `StoreCategoryFlowTest`（与原有经营类目用例同一个类）：

1. 保存商品，类目在本店经营类目里 → 通过；不在 → `GOODS_CATEGORY_NOT_IN_STORE`，且**经营类目没有被撑大**（读回 `categoryNosOf` 仍是原集合）
2. 上架同上
3. 无门店上下文 → 不校验（老路径不断）
4. 自营门店加一个需要资质的类目 → 成功；**同一主体下的第三方门店**同样的操作 → 走资质闸（开关关着时只记不拦，开着时拒）
5. 撤一个底下有商品的经营类目 → `STORE_CATEGORY_IN_USE`（回归）
6. 老商品（类目不在经营类目里、已上架）→ 读、列表、C 端下单都不受影响

**消融**：把 L881 的校验改回 `ensure`，第 1 条的「经营类目没有被撑大」必须变红。

**夹具跟着改**：26 个场景类的建品夹具原先靠「自动加入」，规则收紧后在建品那一行一起断了。
它们改为先调 `support/TestStoreCategory.open(...)` 开类目 —— 与店主的真实流程同序，
不是给规则开后门。

## 8 不做什么

- 不动平台类目树、不动进件与资质授予（上游 TDD 的其余部分）
- 不做主体级经营类目：主体卖哪些 = 各门店经营类目的**并集，派生不存**（上游 TDD 第 191 行，同一结论）
- 不迁移、不清洗存量商品

## 10 修订（2026-09-20，已实现）：「自营免资质」改按主体判

### 10.1 问题

规则 2 现在按**门店**的 `mch_store.business_mode = SELF_OPERATED` 跳过资质。这正是
V329（`mch_entity.self_operated`）迁移注释里点名不能做的事：

- `business_mode` 的建表默认值就是 `SELF_OPERATED`（V23），入驻流程不改它 ——
  **每一家新店一出生都是「自营」**，包括第三方商家的店
- 它回答的是「谁是销售主体」；代销的第三方商家在归集模式下销售主体也是平台，
  按它豁免会把 ADR-017 §3.4 要求先核验的那一档一起放过

现在资质闸（`category.gate.enforce`）关着，所以还没有实际后果；**闸一打开，
所有没被运营改过模式的第三方门店加经营类目都不查资质**，且不会有任何报错。

### 10.2 改法

| 位置 | 改动 |
|---|---|
| `StoreCategoryServiceImpl.isSelfOperated(storeNo)` | 门店 → `entityNo` → `mch_entity.self_operated = 1` 才跳过资质；不再看 `business_mode` |
| `StoreVO` | 加 `selfOperated`（主体级，同一判据）；`businessMode` 保留不删 —— 0.4.78 已装机，删了老包会读到 `undefined` |
| `biz-category-sheet.vue` | 「需资质」标签改读 `currentStore.selfOperated` |
| 场景测试 | ①门店 `SELF_OPERATED`（默认值）+ 主体非自营 + 闸开 → **要资质**（这条就是本次要堵的洞）；②主体自营 → 免资质（虹选鲜果的情形）|

- 不迁移、不回填：`self_operated` 的写入口只有 `POST /ops/merchants/self-operated`，由人逐个确认（V329 的约定）
- 线上核对：虹选鲜果主体 `M202609161449440002055` 已是 `selfOperated = true`（C 端商品详情接口回读），
  改完后它两家门店的行为不变

### 10.3 不在本次范围

`business_mode` 默认 `SELF_OPERATED` 同样影响**结算口径**（V28 费率规则按它分毛利率 / 佣金率）。
第三方门店若从没被改过模式，结算会走自营口径。这属于入驻与结算域，另立 TDD，不在经营类目里顺手改。

### 10.4 实现与验证

- 场景测试 `StoreCategoryFlowTest`：`gatedCategoryNeedsTheCode` 断言门店模式保持默认 SELF_OPERATED、
  主体非自营时开闸要资质；`selfOperatedStoreSkipsQualification` 把门店模式故意设成 THIRD_PARTY，
  主体自营仍免资质。**消融**：判据改回按门店 business_mode，两条都变红
- 夹具跟着改：`CategoryTreeFlowTest` / `Phase1MasterDataTest` 测的是商品上架那道闸，
  改为在闸门关着时开经营类目（模拟开闸前就有的存量类目），否则建品走不到上架
- 全量 2093 条通过

### 10.5 留给开闸那天的问题（未决）

闸门打开后，非自营主体**没有证就加不了**需要证的经营类目，因而连草稿都建不了。
这与 `CategoryTreeFlowTest` 里「保存草稿不拦，上架才拦」的原意相冲突（那条原意是：
商家可能正在申请证，别逼他归到错误类目）。现在闸门关着，不影响任何人；开闸之前要定：
经营类目这一步是「没证也能加、上架才拦」，还是维持现状「加的时候就拦」。

## 11 开闸前的规则（2026-09-20 定）

§10.5 的问题定了：**维持「加经营类目时就拦」**，不改成「加不拦、上架才拦」。
出路不在放宽判据，而在运营那一侧：

| 谁 | 规则 |
|---|---|
| 平台自营主体（`mch_entity.self_operated = 1`） | **不受限**，加任何经营类目都不判资质（§10 已实现） |
| 第三方主体，有那张证 | 自己加，照旧 |
| 第三方主体，没那张证 | 加不了，也就建不了这一类的商品（含草稿）。**由运营在运营端增加 / 放行** |

**运营侧两条路都已经有了，本次不新增端点：**

- **增加（授码）**：运营端「入驻与资质 → 类目授权」（`merchant:category:grant`，
  `PUT /ops/merchants/{merchantNo}/auth-codes`，带 reason 留痕）。授完商家自己就能加类目、建商品
- **放行**：同一处 —— 授予该类目要求的码就是放行；没有第二套「豁免但不授码」的开关，
  刻意不做：豁免若不落在授权表上，就没有谁在什么时候放的谁这条记录

**商家侧的出路已经写在拒绝语里**：70002 的文案指向 B 端「经营资质」页（`pages/qualifications`），
商家从那里提交申请，运营在上面那一页处理。

**验证**：`StoreCategoryFlowTest.opsGrantOpensTheCategory` —— 闸开着、第三方主体、没有证 →
加类目被拒（70002）；运营授予 `FRESH_VEG` 之后，同一次调用通过。

**开闸的前置条件**（`category.gate.enforce` 现仍为关）：先按上表把在卖的第三方商家的码补齐，
否则开闸当天他们会在「加经营类目」这一步集体卡住。
