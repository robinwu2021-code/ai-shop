# 积分运营端流转与类图

本图补充积分模块总图，描述阶段 B 已实现的运营边界。积分内核与账务位于 pay-domain；payclient 负责登录主体的数据域授权，Controller 负责功能权限。所有金额沿用类型汇率与最小货币单位，门店号是操作和账务维度，商家仅用来解析授权归属。

## 运营操作流转

```mermaid
flowchart TD
    UI[积分运营工作区] --> HTTP[Ops Controller：功能权限与登录操作人]
    HTTP --> Scope{应用门面：数据域校验}
    Scope -->|逐店操作| Store[门店目录解析归属并匹配授权商家]
    Scope -->|全量资金或用户数据| All[要求平台 ALL 范围]
    Store --> Audit[幂等操作日志：原始请求、操作人、服务端时间]
    All --> Audit
    Audit --> Config[类型 / 规则 / 协议 / 开关]
    Audit --> Maker[资金申请或周期计划版本]
    Maker --> Request[周期申请保留该配置版本真实制单人]
    Request --> Checker{不同操作人复核}
    Checker -->|通过| Kernel[积分内核与短 pay 事务]
    Audit --> Statement[按门店、原路由组与 revision 操作账单]
    Statement --> Permission{PREPARE_PAYOUT：付款执行权限}
    Permission -->|授权通过| Kernel
    Kernel --> Intent[提交原始资金意图]
    Intent --> Executor[事务外执行或查询原号]
    Executor --> Unknown{资金结果}
    Unknown -->|UNKNOWN| Executor
    Unknown -->|可信明确结果| Confirm[短 pay 事务确认、流水与审计]
    All --> Query[只读 DTO：四池、预留、锁定、独立 R]
    Store --> Query
```

R 不作为现金；只对同店账单抵销。准备付款生成的 READY 意图可被恢复任务执行，因此准备动作本身必须取得付款执行权限。运营端不能提交权威订单支付或退款成功事实。

类型、公开规则与协议条款元数据允许受限运营读取，仍需原功能权限；全量流水、平台账户、用户账户、重建和对账要求平台范围。逐店查询、账单、退款、应收和资金恢复逐次授权；无法从可信门店目录确认归属时拒绝操作。社区、自提点等范围暂不推导为某门店的完整财务授权。
