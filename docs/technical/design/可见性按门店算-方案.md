# 可见性按门店算（矩阵 §7.1 / §7.4）

> 2026-08-25。动手前的现状核对与方案，**未实施**。
> 涉及 C 端可见性这条主链路（所有买家看到什么都归它管），所以先出方案。

---

## 一、今天是什么

三张表 + 一个派生索引：

| 东西 | 挂在哪 | 说明 |
|---|---|---|
| `mch_service_area` | **主体** `entity_no` | 商家的地理足迹（社区/街道/区/市，国标码前缀展开） |
| `mch_fulfillment_channel` | **门店** `store_no` + `channel` | 这家店跑哪几路（自提/自送/快递），`scope_mode` = ALL / SUBSET |
| `mch_channel_area` | **门店** `store_no` + `channel` → `area_no` | SUBSET 时，这家店这一路覆盖主体足迹里的哪几块 |
| `prd_community_pool` | `(community_no, goods_no)` **唯一键** | 派生索引，C 端按社区列货只读它 |

可见性的唯一出口是 `MerchantPortImpl.reachableCommunities(entityNo)`
（那段注释写着「**这个方法是可见性的唯一出口**」，确实如此）。它做的是：

```
主体非 ACTIVE            → 空
开了快递                 → 平台全部开放社区
范围空 + 开了自送         → 平台全部开放社区
范围空 + 只有自提         → 空
否则                     → 主体全部 service_area 展开成社区集合
```

注意第一行取的是 `enabledFulfillments(merchantNo, **null**)` ——
**主体级并集，任何一家门店送得到就算整个主体可达**。这是当初写死的口径，
注释里也明说了：「可见性是主体级的」。

## 二、这个口径今天错在哪

三件事，都能具体复现，且都不报错。

### 2.1 A 店的货出现在只有 B 店服务的社区里

主体有两家店：文三路店只服务 CM001，古墩路店只服务 CM002（`mch_channel_area` 分得清清楚楚）。
可见性取并集 → 池里 `(CM001, 货X)` 和 `(CM002, 货X)` 都有，
**而货 X 其实只摆在文三路店的货架上**（`prd_store_goods`）。
CM002 的买家搜到它、下了单 —— 古墩路店没有这件货。

> `prd_store_goods`（门店选品）在可见性链路上**一个读者都没有**。
> 它今天只在 B 端商品列表与上下架总闸里被读。

### 2.2 多业态在 C 端根本没隔离（矩阵 §7.4）

同一个账号开餐饮 + 零售两家店，两边的货在同一个社区里混着出现。
§7.4 写的「由选品天然隔离」不成立 —— 因为选品不参与可见性。

### 2.3 单落到不服务这个社区的门店上

`OrderServiceImpl.storesOfEntities`：门店取的是**自提点所属店，否则默认店**。
完全不看「哪家店真的服务买家所在社区」。

所以即便 2.1 修好、可见性按 B 店算，单仍然落到默认店 A ——
**可见性与履约对不上**，比现在更难查（页面说得通、单发错店）。
所以这一条必须和 7.1 同一批做，不能留到下一步。

## 三、好消息：地基已经有了

**不需要新建「门店服务范围」这个概念** —— 它已经存在：

- 这家店跑哪几路：`mch_fulfillment_channel(store_no, channel)`
- 这家店这一路覆盖哪几块：`mch_channel_area(store_no, channel, area_no)`，
  `scope_mode=ALL` 时 = 主体全部足迹
- 而 `enabledFulfillments(merchantNo, storeNo)` **本来就支持传门店**，
  只是可见性那处传了 `null`

也就是说 §7.1 不是建模型，是**把一个已经写好的参数从 null 改成真实门店号**，
再让派生索引带上门店维度。

## 四、方案

### 4.1 口径

```
货 G 在社区 C 可见  ⟺  ∃ 门店 S，使得
      S 属于的主体是 ACTIVE
   ∧  S 在架卖 G                （prd_store_goods 的三态语义，见 §7.2）
   ∧  S 可达 C                  （reachableCommunities(entityNo, S)）
   ∧  G 本身在架且过审           （prd_goods.on_sale + audit_status）
```

对**单店商家**这个式子与现状逐字等价 —— 这是它能安全上线的原因。
生产库现在 6 个主体 / 8 家店，其中只有 1 个主体是多门店，且**没有任何门店配过 SUBSET**
（`mch_channel_area` 0 行），所以那一个多门店主体也走 ALL 分支、同样等价。
换句话说：**这次切口径在今天的生产数据上是零行为变化的**，
真正的收益在于往后开第二家店的人不会再撞上 §2.1／§2.3。

### 4.2 三处改动

| # | 改什么 | 说明 |
|---|---|---|
| **A** | `reachableCommunities(entityNo)` → 增加 `(entityNo, storeNo)` 重载 | 老签名保留为「主体并集」，仍给「这家商家覆盖哪儿」这类主体级问题用（商家详情页）。新签名把 `enabledFulfillments(merchantNo, storeNo)` 的 null 换掉，SUBSET 走 `mch_channel_area` |
| **B** | `prd_community_pool` 加 `store_no`，唯一键 `(community_no, goods_no)` → `(community_no, goods_no, store_no)` | 池仍是派生索引（读性能不退化），只是多一维。C 端列表按 `goods_no` 去重；**详情/下单要用 store_no** |
| **C** | 下单挑门店：`自提点店 → 默认店` 改成 `自提点店 → 服务该社区且在架的店 → 默认店` | 与 B 同批，否则可见性与履约对不上（§2.3） |

**为什么保留池而不是查询时 join**：C 端列表是最高频的读，
现在是「一次 in 查询」；改成 join `prd_store_goods` × `mch_channel_area` × 区划前缀展开，
每次列表都要展开一次前缀树。池的代价是写放大（一件货 × 门店数 × 社区数），
而门店数是个位数、社区数受经营范围约束 —— 写放大可控，读不退化。

### 4.3 池的重建触发点

现在有三个（前两个是 2026-08-25 刚补的，见 `e7cc4f24`）：

1. 商品上下架 —— 已有
2. 主体激活 / 经营范围保存 → `StoreShelfPort.resyncPools` —— 已有
3. **新增：门店选品变了**（`prd_store_goods` 写入）、**门店送货方式/覆盖范围变了**
   （`mch_fulfillment_channel` / `mch_channel_area` 写入）

第 3 条是这次必须补的：口径里加了门店维度，那么「门店那一侧变了」就得重建。
少了它就是 2026-08-25 那个回归的翻版 —— 派生索引不跟着因变。

## 五、分步（每步能独立上线、独立回退）

| 步 | 内容 | 能独立上线吗 |
|---|---|---|
| **1** | A：加 `reachableCommunities(entityNo, storeNo)` 重载，**不改任何调用方** | 能。纯新增，行为零变化。用例覆盖 SUBSET / ALL / 空范围三种 |
| **2** | B：池加 `store_no`（可空），回填 = 每个主体的默认店；写入口改成按门店逐条写 | 能。唯一键先不动（新列可空），C 端仍按 goods_no 去重，行为不变 |
| **3** | 切口径：`syncPool` 改成按门店算可达 + 读 `prd_store_goods` | **这一步才真正改行为**。上线前必须查存量：多门店主体有几个、他们的 `mch_channel_area` 配了没 |
| **4** | 唯一键换成三元组；C：下单挑门店按可达 | 与 3 同批发布 |
| **5** | 补第 3 类重建触发点（门店选品 / 门店覆盖范围变更） | 与 3 同批 |

**第 3 步之前线上没有任何行为变化**，1 和 2 可以先合。

## 六、风险

| 风险 | 说明 | 怎么防 |
|---|---|---|
| **多门店主体没配 `mch_channel_area`** | `scope_mode` 默认 ALL 时等价于主体全足迹，与今天一致；但如果有主体配了 SUBSET 且配得不全，切口径当天那些货会消失 | ✅ **已查（2026-08-25 生产库）**：多门店主体 **1** 个（共 8 家店 / 6 个主体），`scope_mode=SUBSET` 的门店-路 **0** 条，`mch_channel_area` **0** 行，社区池 **6** 行。<br>**全部走 ALL 分支 = 按门店算与按主体算逐字等价，切口径当天零行为变化。**上线前重查一次即可 |
| 池写放大 | 一件货 × 门店 × 社区。单店不变；两家店服务同一社区 = 两行 | 列表按 goods_no 去重；写入按门店差集增删，不全删重插（唯一键含逻辑删的老坑） |
| `repointSettlement` 撞键 | `ProductSettlementRefPortImpl` 合并聚落时按 `(community_no, goods_no)` 去重，加了 store_no 之后去重维度要跟着改 | 第 4 步换唯一键时一并改，它有现成用例 |
| 「没框范围」的两种含义 | 自提空 = 谁也看不到、自送空 = 不限（ADR-013 §6.2）。按门店算之后这条规则要逐店判 | 第 1 步的重载里保持逐字同一套分支，用例把三种情况都钉住 |

## 七、两个口径：已定（2026-08-25）

### 7.1 一件货摆在两家店、两家店都服务同一社区 → **按「离这个社区最近的那家店」展示**

C 端列表按 `goods_no` 去重，留下距离最近的那一条；并列或算不出距离时退到**默认店**。

**为什么按社区算距离而不是买家 GPS**：买家未必授权定位，而列表要能稳定排序、
更要能**在写入时算好**。社区有坐标（`cmt_community.lat_e6/lng_e6`），
门店也有（`mch_store.lat_e6/lng_e6`），两点距离在**建池的那一刻**就能定下来。

**落在哪一列**：`prd_community_pool.sort_weight` —— 这一列建表时就有，
而至今**每一处都写死 0**（`MerchantGoodsServiceImpl:1479`、`DevSeeder:495`）。
拿它装「这家店到这个社区的距离（米）」，列表按它升序取第一条即可，不加列、不加查询。

> 距离算不出来时（门店或社区缺坐标）写一个**很大的数**而不是 0 ——
> 写 0 会让缺坐标的店排到最前面，恰好与意图相反。

### 7.2 「主体在架，但这家店一条选品行都没有」→ **算这家店卖**（维持 `prd_store_goods` 三态语义）

```
某商品一条店级行都没有   → 走 prd_goods.on_sale，主体下所有 ACTIVE 门店都算在架
有了任意一条            → 转为店级管理，没有行的店视为未上架
```

**这是必须维持的**：改成「没有行就不卖」的话，存量商家（全部没有店级行）
在切口径当天**从 C 端集体消失**。而且这条语义与 `prd_store_stock` 逐字一致
（V13 注释里专门论证过），两处分岔的症状极难查：库存说这家店有货、
选品说这家店没这商品，页面显示与下单结果各说各话。

## 八、实施计划

迁移号从 **V240** 起（V231–V236 已被占用，留一档余量）。

### 第 1 步 · 门店级可达（纯新增，行为零变化）

| 文件 | 改动 |
|---|---|
| `MerchantQueryPort` | 加 `List<String> reachableCommunities(String entityNo, String storeNo)`；老签名保留，语义仍是「主体并集」，商家详情页等主体级问题继续用它 |

用例 `StoreReachFlowTest`（新）：

- `subsetStoreOnlyReachesItsAreas` —— SUBSET 门店只可达自己那几块
- `pickupOnlyWithNoAreaReachesNobody` / `deliveryWithNoAreaReachesAll` —— 空范围的两种含义
- 变异：把新重载改成转调老签名，前两条必须红

| 文件 | 改动 |
|---|---|

- `orderLandsOnTheStoreThatServesTheBuyer` —— §2.3
- `singleStoreMerchantBehavesExactlyAsBefore` —— 存量口径不变（最重要的一条）

**上线前必须重查生产**：多门店主体数、`scope_mode=SUBSET` 门店-路数、
`mch_channel_area` 行数。今天分别是 1 / 0 / 0，全走 ALL 分支所以等价；
这三个数只要有一个变了，就要重新评估再发。

### 第 4 步 · 唯一键与合并去重

- `V241__pool_uk_store.sql`：`uk_community_goods` → `uk_community_goods_store (community_no, goods_no, store_no)`
- `ProductSettlementRefPortImpl.repointSettlement` 的去重维度跟着改成三元组（它有现成用例）

### 第 5 步 · 补重建触发点

口径里加了门店维度，那么「门店那一侧变了」就得重建池，否则是
`e7cc4f24` 那个回归的翻版（派生索引不跟着因变）：

- `prd_store_goods` 写入（门店选品 / 门店上下架）
- `mch_fulfillment_channel`、`mch_channel_area` 写入（门店送货方式与覆盖范围）

用例：改完门店覆盖范围后，货在旧社区搜不到、在新社区搜得到（与
`scopeChangeMovesGoodsOutOfOldCommunity` 同形状，但作用在门店而非主体）。

### 发布切分

- **1 + 2 一起发**：纯新增，线上零行为变化，可以先落地攒着
- **3 + 4 + 5 必须同批发**：只发 3 会让唯一键挡住第二家店的池行（撞
  `uk_community_goods`）；只发 3 不发 5 就是派生索引不跟着因变；
  只发 3 不发 4 的下单挑店会与可见性对不上

### 回退

第 3 步的回退是把 `syncPool` 的可达算法换回主体级并集并重建一次池
（`StoreShelfPort.resyncPools` 已经在，全量重建就是遍历主体调它）。
**不需要回退迁移** —— 多出来的 `store_no` 列与三元组唯一键对主体级口径无害。

## 九、停用门店的收尾能力（2026-09-29）

状态：已实现（2026-09-29，提交 1e3da3d6c） · 关联需求：`docs/requirements/多门店与分享激励-需求.md` **B-11.12.4**
「停用的门店 C 端不可见，**历史订单可查**」

### 9.1 线上撞到的

「虹选鲜果·福田店」是 `READONLY`。它货架上那两件测试商品，**店主用尽所有办法都撤不下来**：

- 带 `X-Store-No` 指向它 → `/biz/context` 回来的仍是默认店，**头被静默忽略**
- 于是 `toggle {"onSale":false}` 落在默认店上（那家本来就已下架）→ 返回 `code 0`，
  **一次什么都没做的成功**
- `/ops/goods/{no}/force-off` 要 `PRODUCT_SKU_AUDIT`，库里只有 `SUPER_ADMIN` 有

根因在 `BizIdentityResolverImpl`：**老板**的门店集合只装 `status='ACTIVE'` 的店 ——

```java
Set<String> storeNos = isOwner
        ? storeMapper.selectList(… .eq(MchStore::getStatus, "ACTIVE")) …   // ← 这里
        : roleMapper.selectList(…)      // 店员分支不过滤状态
```

而 `BizContextFilter` 的规则是「请求的门店不在我的权限集合里就回落到默认店」。
两条各自都说得通，合起来就是：**老板一旦停用一家店，就再也进不去那家店**。
店员反而进得去 —— 他的集合来自授权表，从不看状态。

这把两件事混为一谈了：**营业状态是给买家看的，管理权限是给老板的**。
停业之后老板正需要进去收尾 —— 撤货、清库存、查历史订单（B-11.12.4 明写的那一条）、
重新开业。把它们绑在一起，等于停业按钮按下去就锁了门。

### 9.2 第二处：主体总闸被停业门店撑着

`toggle` 里主体级 `on_sale` 的计算看的是**全部**门店行：

```java
boolean anyOn = onSale || storeGoodsRows(goodsNo).stream()
        .anyMatch(r -> Boolean.TRUE.equals(r.getOnSale()));
```

于是把所有 `ACTIVE` 门店都下架之后，停业门店那一行仍把总闸顶着 `1`。

**社区池不受影响**（`storesSelling` 已经改用 `activeStoreNos`，见 §四），
买家在社区上下文里确实看不到、买不了 —— 线上实测带 `communityNo` 的列表 `total=0`、
详情 `deliverable=false`。漏的是**不带社区**的那条列表：它按主体级 `on_sale` 出数，
于是商品还在里面列着。点进去买不了，但「商家侧显示已全部下架、买家侧还列着」本身就是要修的。

### 9.3 改法

| AC | 改哪儿 |
|---|---|
| **AC1** 老板停用门店后，仍能带 `X-Store-No` 切进去（撤货、查历史订单） | `BizIdentityResolverImpl`：老板的 `storeNos` 取主体下**全部**门店 |
| **AC2** 主体总闸只由 `ACTIVE` 门店的行决定 | `MerchantGoodsServiceImpl#toggle` 的 `anyOn` 只数 `ACTIVE` 门店那几行 |
| **AC3** 默认门店仍优先落在 `ACTIVE` 门店上 | 同 `BizIdentityResolverImpl`：`defaultStore` 先在 ACTIVE 里挑 |
| **AC4** 自提点核销范围不跟着扩大 | `pickupNos` 仍按 ACTIVE 门店算，不用放开后的 `storeNos` |

**AC3、AC4 是为放开 AC1 配的两道边**：不设 AC3，默认店被停用的商家一登录就站在停业店里；
不设 AC4，停业店门口的自提点会重新进核销范围 —— 那不是「收尾」，是把店又开了一半。

**数据域不受影响**：`scopeStoreNos()` 对老板返回 `null`（不限），放开的是上下文切换，不是可见范围。

**停业店还能上架吗**：能，但没有任何买家侧效果 —— `storesSelling` 排除非 ACTIVE 门店，
池里不会多一行；AC2 之后主体总闸也不认它。记账上它是「这家店重开时货还在架上」，
与 `prd_store_goods` 的三态语义一致（见 §7.2）。

### 9.4 不做什么

- **不加「门店已停业」的报错**：`X-Store-No` 回落到默认店这个行为本身是对的
  （端上缓存了旧门店号时不该让整个 App 报错），它只是不该把老板自己的停业店也算成越权。
  放开之后这条回落只剩它本来的职责。
- **不动店员分支**：它从授权表取，本来就不看状态。
- **不动 `/mp/goods` 不带社区时的口径**：AC2 之后这件商品自然就不在里面了；
  「无社区上下文该不该出数」是另一个决定。

### 9.5 三处对账

**需求 → 设计**：B-11.12.4「停用的门店 C 端不可见，历史订单可查」的后半句，
此前一处实现都没有 —— 老板连门店上下文都切不进去。§9.3 的 AC1 就是它的落点。

**设计 → 实现**

| §9.3 的条目 | 实际改的文件 |
|---|---|
| AC1 老板的 `storeNos` 取全部门店 | `BizIdentityResolverImpl` |
| AC3 默认门店优先 ACTIVE | `BizIdentityResolverImpl`（同一处新增 `activeStoreNos`） |
| AC4 自提点仍按 ACTIVE 算 | `BizIdentityResolverImpl`（`pickupNos` 改用 `activeStoreNos`） |
| AC2 主体总闸只数 ACTIVE 门店的行 | `MerchantGoodsServiceImpl#toggle` |
| （**设计里没写、实现时补的**）`platformOfflineStore` 里的同一个口径 | `MerchantGoodsServiceImpl#platformOfflineStore` |

最后一行是偏差：写设计时只看到 `toggle` 那一处，实现时发现平台强制下线走的是另一段
一模一样的 `anyOn` 计算。两处口径必须一致，否则「谁最后操作」决定总闸对不对。

**实现 → 需求**

| AC | 测试方法 |
|---|---|
| AC1 停用后仍切得进去、撤得下货 | `SuspendedStoreWindDownFlowTest.ownerCanStillWindDownASuspendedStore` |
| AC2 总闸只由 ACTIVE 门店决定 | 同上（**顺序是判据的一部分**：先撤 A 店、把停业店那行留着在售）＋ `sellingInASuspendedStoreChangesNothingForBuyers` |
| AC3 / AC4 | 无独立用例 —— 见下 |

**消融**（各自单独撤回，都变红）：

- 撤 AC1（`storeNos` 改回只装 ACTIVE）→ 两条全红，第一条断在「切不进去」
- 撤 AC2（`anyOn` 改回数全部门店行）→ 两条全红，断在「总闸被停业店顶开」

### 9.6 偏差说明

- **AC3、AC4 没有独立用例**。它们是为放开 AC1 配的边，正确的判据分别是
  「默认店被停用的商家登录后站在哪家店」与「停业店门口的自提点在不在核销范围里」——
  两者都要先造出「默认店被停用」「门店下有自提点」的前提，而那两套夹具都不小。
  **先记在这里，不假装它们被测到了**：现在挡着这两条的只有代码里的注释。
- **`platformOfflineStore` 那一处是实现时补的**，见 §9.5 的表。
- **线上那两件测试商品没有借这次修复收尾**：它们属于「虹选科技」，
  要等这版部署后才撤得下来。买家侧本来就看不到（带 `communityNo` 的列表 `total=0`、
  详情 `deliverable=false`），不急。

### 9.7 线上验证（2026-09-29，`02259c97a`）

拿生产上现成的停业门店「虹选鲜果·福田店」（`READONLY`）实测：

| | 部署前 | 部署后 |
|---|---|---|
| 带 `X-Store-No` 指向它，`/biz/context` 回什么 | 默认店（头被静默吃掉） | **它自己** |
| 不带头时落在哪家店 | 默认店 | 默认店（仍是 ACTIVE 的那家，AC3 成立） |
| 撤它货架上的商品 | `code 0` 但 `on_sale` 不变 | 撤下来了，回读 `prd_goods.on_sale=0`、门店行无一在售 |

**AC4 在生产上也验不了**：`mch_channel_pickup` 是 0 行 —— 线上根本没有挂在门店下的
自提点。对照量为零时，"验过了"和"没验"给出的是同一个结果，那不是证据。
所以 AC4 至今只有代码里的注释挡着，与 §9.6 说的一样，**这里不因为跑了一趟线上就改口**。
