# 可见性按门店算（矩阵 §7.1 / §7.4）

> 2026-08-25。动手前的现状核对与方案，**未实施**。
> 涉及 C 端可见性这条主链路（所有买家看到什么都归它管），所以先出方案。

---

## 一、今天是什么

三张表 + 一个派生索引：

| 东西 | 挂在哪 | 说明 |
|---|---|---|
| `mch_service_area` | **主体** `entity_no` | 商家的地理足迹（社区/街道/区/市，国标码前缀展开） |
| `mch_fulfillment_channel` | **门店** `store_no` + `channel` | 这家店跑哪几路（自提/自送/快递），`scope_mode` = ALL / SUBSET |
| `mch_channel_area` | **门店** `store_no` + `channel` → `area_no` | SUBSET 时，这家店这一路覆盖主体足迹里的哪几块 |
| `prd_community_pool` | `(community_no, goods_no)` **唯一键** | 派生索引，C 端按社区列货只读它 |

可见性的唯一出口是 `MerchantPortImpl.reachableCommunities(entityNo)`
（那段注释写着「**这个方法是可见性的唯一出口**」，确实如此）。它做的是：

```
主体非 ACTIVE            → 空
开了快递                 → 平台全部开放社区
范围空 + 开了自送         → 平台全部开放社区
范围空 + 只有自提         → 空
否则                     → 主体全部 service_area 展开成社区集合
```

注意第一行取的是 `enabledFulfillments(merchantNo, **null**)` ——
**主体级并集，任何一家门店送得到就算整个主体可达**。这是当初写死的口径，
注释里也明说了：「可见性是主体级的」。

## 二、这个口径今天错在哪

三件事，都能具体复现，且都不报错。

### 2.1 A 店的货出现在只有 B 店服务的社区里

主体有两家店：文三路店只服务 CM001，古墩路店只服务 CM002（`mch_channel_area` 分得清清楚楚）。
可见性取并集 → 池里 `(CM001, 货X)` 和 `(CM002, 货X)` 都有，
**而货 X 其实只摆在文三路店的货架上**（`prd_store_goods`）。
CM002 的买家搜到它、下了单 —— 古墩路店没有这件货。

> `prd_store_goods`（门店选品）在可见性链路上**一个读者都没有**。
> 它今天只在 B 端商品列表与上下架总闸里被读。

### 2.2 多业态在 C 端根本没隔离（矩阵 §7.4）

同一个账号开餐饮 + 零售两家店，两边的货在同一个社区里混着出现。
§7.4 写的「由选品天然隔离」不成立 —— 因为选品不参与可见性。

### 2.3 单落到不服务这个社区的门店上

`OrderServiceImpl.storesOfEntities`：门店取的是**自提点所属店，否则默认店**。
完全不看「哪家店真的服务买家所在社区」。

所以即便 2.1 修好、可见性按 B 店算，单仍然落到默认店 A ——
**可见性与履约对不上**，比现在更难查（页面说得通、单发错店）。
所以这一条必须和 7.1 同一批做，不能留到下一步。

## 三、好消息：地基已经有了

**不需要新建「门店服务范围」这个概念** —— 它已经存在：

- 这家店跑哪几路：`mch_fulfillment_channel(store_no, channel)`
- 这家店这一路覆盖哪几块：`mch_channel_area(store_no, channel, area_no)`，
  `scope_mode=ALL` 时 = 主体全部足迹
- 而 `enabledFulfillments(merchantNo, storeNo)` **本来就支持传门店**，
  只是可见性那处传了 `null`

也就是说 §7.1 不是建模型，是**把一个已经写好的参数从 null 改成真实门店号**，
再让派生索引带上门店维度。

## 四、方案

### 4.1 口径

```
货 G 在社区 C 可见  ⟺  ∃ 门店 S，使得
      S 属于的主体是 ACTIVE
   ∧  S 在架卖 G                （prd_store_goods 的三态语义，见 §7.2）
   ∧  S 可达 C                  （reachableCommunities(entityNo, S)）
   ∧  G 本身在架且过审           （prd_goods.on_sale + audit_status）
```

对**单店商家**这个式子与现状逐字等价 —— 这是它能安全上线的原因。
生产库现在 6 个主体 / 8 家店，其中只有 1 个主体是多门店，且**没有任何门店配过 SUBSET**
（`mch_channel_area` 0 行），所以那一个多门店主体也走 ALL 分支、同样等价。
换句话说：**这次切口径在今天的生产数据上是零行为变化的**，
真正的收益在于往后开第二家店的人不会再撞上 §2.1／§2.3。

### 4.2 三处改动

| # | 改什么 | 说明 |
|---|---|---|
| **A** | `reachableCommunities(entityNo)` → 增加 `(entityNo, storeNo)` 重载 | 老签名保留为「主体并集」，仍给「这家商家覆盖哪儿」这类主体级问题用（商家详情页）。新签名把 `enabledFulfillments(merchantNo, storeNo)` 的 null 换掉，SUBSET 走 `mch_channel_area` |
| **B** | `prd_community_pool` 加 `store_no`，唯一键 `(community_no, goods_no)` → `(community_no, goods_no, store_no)` | 池仍是派生索引（读性能不退化），只是多一维。C 端列表按 `goods_no` 去重；**详情/下单要用 store_no** |
| **C** | 下单挑门店：`自提点店 → 默认店` 改成 `自提点店 → 服务该社区且在架的店 → 默认店` | 与 B 同批，否则可见性与履约对不上（§2.3） |

**为什么保留池而不是查询时 join**：C 端列表是最高频的读，
现在是「一次 in 查询」；改成 join `prd_store_goods` × `mch_channel_area` × 区划前缀展开，
每次列表都要展开一次前缀树。池的代价是写放大（一件货 × 门店数 × 社区数），
而门店数是个位数、社区数受经营范围约束 —— 写放大可控，读不退化。

### 4.3 池的重建触发点

现在有三个（前两个是 2026-08-25 刚补的，见 `e7cc4f24`）：

1. 商品上下架 —— 已有
2. 主体激活 / 经营范围保存 → `StoreShelfPort.resyncPools` —— 已有
3. **新增：门店选品变了**（`prd_store_goods` 写入）、**门店送货方式/覆盖范围变了**
   （`mch_fulfillment_channel` / `mch_channel_area` 写入）

第 3 条是这次必须补的：口径里加了门店维度，那么「门店那一侧变了」就得重建。
少了它就是 2026-08-25 那个回归的翻版 —— 派生索引不跟着因变。

## 五、分步（每步能独立上线、独立回退）

| 步 | 内容 | 能独立上线吗 |
|---|---|---|
| **1** | A：加 `reachableCommunities(entityNo, storeNo)` 重载，**不改任何调用方** | 能。纯新增，行为零变化。用例覆盖 SUBSET / ALL / 空范围三种 |
| **2** | B：池加 `store_no`（可空），回填 = 每个主体的默认店；写入口改成按门店逐条写 | 能。唯一键先不动（新列可空），C 端仍按 goods_no 去重，行为不变 |
| **3** | 切口径：`syncPool` 改成按门店算可达 + 读 `prd_store_goods` | **这一步才真正改行为**。上线前必须查存量：多门店主体有几个、他们的 `mch_channel_area` 配了没 |
| **4** | 唯一键换成三元组；C：下单挑门店按可达 | 与 3 同批发布 |
| **5** | 补第 3 类重建触发点（门店选品 / 门店覆盖范围变更） | 与 3 同批 |

**第 3 步之前线上没有任何行为变化**，1 和 2 可以先合。

## 六、风险

| 风险 | 说明 | 怎么防 |
|---|---|---|
| **多门店主体没配 `mch_channel_area`** | `scope_mode` 默认 ALL 时等价于主体全足迹，与今天一致；但如果有主体配了 SUBSET 且配得不全，切口径当天那些货会消失 | ✅ **已查（2026-08-25 生产库）**：多门店主体 **1** 个（共 8 家店 / 6 个主体），`scope_mode=SUBSET` 的门店-路 **0** 条，`mch_channel_area` **0** 行，社区池 **6** 行。<br>**全部走 ALL 分支 = 按门店算与按主体算逐字等价，切口径当天零行为变化。**上线前重查一次即可 |
| 池写放大 | 一件货 × 门店 × 社区。单店不变；两家店服务同一社区 = 两行 | 列表按 goods_no 去重；写入按门店差集增删，不全删重插（唯一键含逻辑删的老坑） |
| `repointSettlement` 撞键 | `ProductSettlementRefPortImpl` 合并聚落时按 `(community_no, goods_no)` 去重，加了 store_no 之后去重维度要跟着改 | 第 4 步换唯一键时一并改，它有现成用例 |
| 「没框范围」的两种含义 | 自提空 = 谁也看不到、自送空 = 不限（ADR-013 §6.2）。按门店算之后这条规则要逐店判 | 第 1 步的重载里保持逐字同一套分支，用例把三种情况都钉住 |

## 七、要拍板的两件事

1. **一件货摆在两家店、两家店都服务同一个社区** —— C 端列表去重后，
   详情页显示哪一家？建议：**离买家最近的那家**（有坐标）→ 否则默认店。
   这决定 `store_no` 在池里是否要带排序权重。
2. **门店选品今天是「三态」**（无行 = 走主体总闸）。按门店算可见性之后，
   「主体在架但这家店一条选品行都没有」= 这家店卖不卖？
   建议维持现状语义（**没有任何店级行 = 所有店都卖**），否则存量单店商家全部消失。
