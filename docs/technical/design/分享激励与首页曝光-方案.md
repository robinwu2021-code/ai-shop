# 分享激励与首页曝光 · 方案

> 状态：**设计待确认** · 上游 [增值服务与分享激励-需求](../../requirements/多门店与分享激励-需求.md) §三 · 决策 [ADR-004 增长模型](../ADR/ADR-004-增长模型从孵化团长转向商家自带客流.md) · 优先级 P0
> 相关：归因（`mkt_attribution`，V9）· 风控域（L2-16）

---

## 一、一句话

**曝光交换**：商家帮平台曝光（把自己的社交关系带进来），平台帮门店曝光（给它首页位置
和一条持续触达顾客的通道）——一次交换，不是一次补贴，所以这个机制不花钱也能成立。

## 一之二、交换的两层：拉新 + 留存

只做「首页展示 N 天」是把交换做成了**一次性**的：曝光期一过，
商家和那些点进来的顾客就断了联系，下次想要曝光只能再分享一次。

平台还给商家的应该是**两样东西**：

| 层 | 平台给什么 | 解决什么 |
|---|---|---|
| **① 拉新** | 首页曝光位 N 天 | 让还不认识这家店的人看到它 |
| **② 留存** | 那些进来过的人，**持续收到这家店的最新动态**（新品/优惠/活动） | 让来过的人**第一时间**回到店里 |

第 ② 层才是商家真正想要的：**一次分享换来的不该只是一次曝光，
而是一批"以后能再触达"的顾客**。这也是他愿意反复分享的理由——
每一次分享都在扩大自己的可触达面，而不是买一次广告。

对平台的收益同样是两层：新用户进来（①），以及他们有理由回来（②）。

## 二、为什么是这个方案

### 2.1 奖励挂在什么指标上，决定了机制会不会被玩坏

需求的目的是「促进**系统**曝光」——受益方是平台，不只是那家店。
顺着这句话往下推，指标只有一种选法：

| 计什么 | 平台实际得到了什么 | 结论 |
|---|---|---|
| 总点击数 | 老客点一下 = 0（他本来就在平台上） | ❌ 给没发生的事付钱 |
| **未归因到本店的用户点击** | 一次真实的外部曝光 | ✅ 基准 |
| 新注册 | 一个新用户 | ✅ 加权 |

只认新注册会把门槛抬到商家够不着（分享十次可能一个注册都没有），机制就没人玩；
只认点击则等于白送。所以：**未归因点击 = 1 分，新注册 = N 分**。

### 2.2 被否掉的做法

| 方案 | 为什么否掉 |
|---|---|
| **A. 分享给现金/佣金减免** | ADR-004 的核心是不用钱买增长。现金有真实成本且会招来专业刷子 |
| **B. 曝光位按有效曝光数排序** | 强者恒强。两周后只剩头部几家在玩，那时它已经不是激励，是马太效应放大器 |
| **C. 分享排行榜 / 公开竞赛** | 把「分享给邻居」变成「刷量竞赛」，与邻里场景相悖 |
| **D. 复用现有 `mkt_attribution` 记录分享点击** | 归因表回答的是「这个用户属于谁」（30 天窗口、一人一条有效）；曝光要回答的是「这个门店最近带来了多少人」。语义不同，混用会让归因窗口被分享点击反复刷新 |
| **E. 曝光池实时计算（下单时按分享数排序）** | 首页是最高频查询，实时聚合分享记录会把它拖垮 |

## 三、结构：三步 + 两层

```
 ① 分享                    ② 记录                     ③ 展示
┌──────────────┐      ┌──────────────────┐      ┌──────────────────┐
│ B 端生成分享码 │──→──│ 用户点击 → 落地页  │──→──│  首页「邻里在逛」  │
│ mkt_share_link│      │ mkt_share_click  │      │ mkt_exposure_pool │
│  谁·哪家店·哪件货│      │  防刷后计分       │      │  权重轮播 N 天    │
└──────────────┘      └──────────────────┘      └──────────────────┘
                              │                          ▲
                              └──── 计分累加 / 续期 ──────┘
                              │
                              └──→ usr_store_follow ──→ 首页「我常逛的店」
                                   （逛过即建立关系）      ← ② 留存
                                          ▲
                                   mkt_store_feed
                                   （新品/优惠/开团/公告，
                                     由业务事件自动产生）
```

| 表 | 回答什么 | 为什么不能合并 |
|---|---|---|
| `mkt_share_link` | 谁在什么时候分享了什么 | 一次分享会被点很多次 |
| `mkt_share_click` | 谁点了、算不算有效、为什么不算 | **不算的也要记**——否则商家问「我分享了怎么没效果」时无法回答 |
| `mkt_exposure_pool` | 现在哪些商品在曝光池里、权重多少、什么时候到期 | 首页是最高频查询，必须读一张已经算好的表 |
| `usr_store_follow` | 谁逛过哪家店（②留存的关系底座） | 与曝光池是两件事：一个是"给陌生人看"，一个是"给来过的人看" |
| `mkt_store_feed` | 门店动态：新品/优惠/开团/公告 | 由业务事件自动产生，商家不需要单独"发动态" |

## 四、详细设计

### 4.1 怎么分享

**入口**：B 端门店主页「分享」按钮、商品详情「分享」按钮（复用现有 B-11.2.7 分享素材）。

**产物**：一条 `mkt_share_link` + 三种形态的素材（小程序卡片 / 海报 / 群发文案）。

| `mkt_share_link` 列 | 说明 |
|---|---|
| `share_code` | 短码，进落地页 URL。**每次分享生成新的** |
| `merchant_no` `store_no` | 归属。多门店下分享的是**某一家店** |
| `goods_no` | 分享商品时有值；分享门店主页时为空 |
| `shared_by` | 哪个子账号分享的 —— 店员也能分享，业绩要能看到是谁带来的 |
| `channel` | WECHAT_SESSION / MOMENTS / POSTER / COPY_LINK |
| `created_at` | |

**为什么每次分享新建一条而不是复用一个固定码**：固定码无法回答
「上周那次朋友圈效果怎么样」。而这个问题正是商家会问的第一个问题。

**落地页**：`/pages/store/index?storeNo=..&from=SHARE&sc=<share_code>`
或商品页同理。`store` 页本来就是为扫码/分享直达设计的（游客可访问，不经选社区）。

### 4.2 怎么记录

用户点开落地页 → 前端带 `sc` 调 `POST /mp/share/click`（游客可调）。

**判定顺序**（先便宜后昂贵，任何一条不过就记原因并结束）：

| # | 规则 | 不通过时 `invalid_reason` |
|---|---|---|
| 1 | `share_code` 存在且未过期（30 天） | `LINK_EXPIRED` |
| 2 | 点击者不是本主体的 OWNER/子账号 | `SELF_CLICK` |
| 3 | 该用户**未归因到本店**（查 `mkt_attribution`） | `EXISTING_CUSTOMER` |
| 4 | 同一用户 × 同一门店，7 天内没算过 | `DUPLICATE` |
| 5 | 该用户注册满 10 分钟（游客按设备指纹） | `TOO_NEW` |
| 6 | 本店今日有效曝光未超上限 | `DAILY_CAP` |

通过 → `valid = 1`，`score = 1`；若该用户**在本次会话内完成注册**，追加 `score += N`。

> **不通过也要写一条 `mkt_share_click`。** 商家问「我分享了怎么没效果」时，
> 后台要能回答"其中 12 次是老客、3 次是你自己点的"。
> 只记有效的，这个问题就只能靠猜。

**归因怎么处理**：点击**照常写归因**（`source=SHARE`，商家自带客流，ADR-004 §6），
这与曝光计分是两件事——归因决定这单算谁的客流，计分决定曝光池权重。
第 3 条规则读归因表但**不修改**它，避免曝光机制反复刷新归因窗口（否决方案 D）。

**放在哪个域**：判定规则 1–6 属于**风控**（L2-16，与已有的归因防刷同处），
不在营销域另起一套。营销域只负责"拿到有效分之后怎么用"。

### 4.3 怎么上首页（①拉新）

**入池**：一次有效点击 → upsert `mkt_exposure_pool`：

| 列 | 说明 |
|---|---|
| `store_no` `goods_no` | 曝光对象。分享门店主页时，取该店**主推商品**入池（首页是逛货的地方，见 4.4） |
| `score` | 累计有效分 |
| `expire_at` | **每次新有效点击续期到 now+7 天**，不是叠加 |
| `status` | ACTIVE / EXPIRED / **BLOCKED**（风控或运营下架） |

**续期而非叠加**是刻意的：叠加会让一次爆发（比如一条朋友圈爆了）
占住位置一个月，而这个机制要奖励的是**持续经营**，不是一次好运。

**展示**：C 端首页新增「邻里在逛」区块，取当前社区可达的曝光池条目。

**排序 = 权重轮播**（否决按分排序的方案 B）：

```
权重 w = score × 时间衰减(now - last_click)
展示时按 w 加权随机抽 K 条，而不是取 Top-K
```

- 分高的**出现频率**高，但分低的**也会出现**
- 每次刷新看到的不完全一样 —— 这本身也让首页更值得逛
- 商家看不到"我排第几"，但**每个人都能看到自己出现过**

这条是整个机制能不能长期跑下去的关键：目的是**鼓励分享**，
不是把流量给最强的那家。按分排序两周后就只剩头部在玩了。

**可达性**：曝光位仍受 ADR-009 的社区可达性约束 ——
分享挣来的曝光**不能突破经营范围**，否则用户会看到一家送不到他这儿的店。

### 4.4 曝光的是商品，不是门店

首页展示**商品**；点进去可到门店。理由：首页是逛货的地方，
放一个门店卡片，用户点进去还要再找一遍买什么。

分享门店主页时取该店主推商品（`featured` 第一个）入池；没配主推则取近 7 天销量最高的。
**门店主页的曝光走「店铺」tab**，那里本来就是逛店的。

### 4.5 留存（②）：来过的人要能持续拿到这家店的动态

这是交换的第二层，也是商家愿意**反复**分享的理由：
一次分享换来的不该只是一次曝光，而是**一批以后能再触达的顾客**。

#### 4.5.1 关系怎么建立

分享进店 = 建立一条「逛过」关系（`usr_store_follow`），**不需要用户点关注**：

| 建立时机 | 说明 |
|---|---|
| 从分享链接进店（有效或无效点击都算） | 他确实来过这家店 |
| 下过单 | 已有 `visitedMerchants` |
| 主动收藏 | 已有 `favoriteStores` |

**不要求用户点关注**是关键：要求点关注会让转化在最开始就掉一大半，
而"他从邻居的分享点进来看了一圈"这件事本身已经表达了兴趣。

三种来源合并成一个「我常逛的店」概念，按最近互动时间排序。
**已有的 `favoriteStores`/`visitedMerchants` 不新建一套**，而是并入同一个视图 ——
顾客心里没有"收藏的店"和"逛过的店"两个抽屉。

#### 4.5.2 动态怎么产生

门店发生这几件事时产生一条动态（`mkt_store_feed`）：

| 类型 | 触发 | 例子 |
|---|---|---|
| `NEW_GOODS` | 新商品过审上架 | 「今天到了新米」 |
| `PROMOTION` | 新建优惠活动/发券 | 「满 50 减 10」 |
| `GROUP_BUY` | 开团 | 「苹果 5 人成团」 |
| `ANNOUNCEMENT` | 店主改公告 | 「今天有土鸡蛋」 |

**由业务事件自动产生，不让商家单独"发动态"**：多一个发布入口，
就多一件商家要记得做的事，而小店老板不会记得。
他上架商品、开活动本来就要做，动态跟着出来最省事。

#### 4.5.3 顾客怎么看到

**首页新增「我常逛的店」区块**（在「邻里在逛」之下）：

```
首页
├─ 自提点/搜索
├─ 邻里团购
├─ 邻里在逛      ← ① 拉新：曝光池（不认识的店）
├─ 我常逛的店     ← ② 留存：动态流（来过的店）   ★ 新增
└─ 社区在卖
```

两个区块**刻意分开**：一个是"你可能没见过的"，一个是"你去过的"。
混在一起用户分不清哪些是熟店，而这两种决策的心智完全不同
（与 ADR-004 §3.3「挑店与挑货是两种决策」同一条理由）。

**排序**：按动态时间倒序，同一门店**同时只出一条**（取最新）——
否则一家上了 5 个新品的店会刷屏，把其他店挤没。

#### 4.5.4 主动触达要克制

除了首页展示，是否推送（订阅消息）：

| 场景 | 建议 |
|---|---|
| 顾客**下过单**的店发布优惠/开团 | 可推，频次上限**每店每周 1 条** |
| 只是从分享点进来看过 | **不推**，只在首页「我常逛的店」出现 |
| 顾客关闭该店动态 | 立即生效，且不再计入 |

**只逛过就推送是最快把人推走的做法**：他只是点了邻居的一个链接，
收到推送会觉得"我什么时候关注了这家店"。
首页展示是**他来的时候才看到**，推送是**追到他那里去**——两者的打扰程度差一个量级。

> 频次上限与关闭入口是硬要求，不是优化项。ADR-004 的增长模型建立在
> 「邻里关系」上，而骚扰会先毁掉关系，再毁掉增长。

### 4.6 费率：曝光位进来的订单算谁的客流

见需求 §3.2 —— 这是本方案与 ADR-004 唯一的冲突点。

新增 `trafficSource = MERCHANT_EARNED`（自带客流换来的平台位），
**费率按 `MERCHANT_OWNED` 走**。

不这么做的话：商家分享 → 挣到首页位 → 用户从首页进来 → 算 `PLATFORM` → **费率更高**。
**越分享越贵，激励是反的**，机制上线即自相矛盾。

保留独立取值而不是直接写成 `MERCHANT_OWNED`，是为了让运营能回答
「曝光位到底带来了多少生意」——那是评估这个机制值不值得继续的唯一依据。

## 五、接口

| 路由 | 端 | 说明 |
|---|---|---|
| `POST /biz/share/links` | B | 生成分享码 + 素材 |
| `GET /biz/share/stats` | B | **我的曝光状态**：还剩几天、带来多少有效曝光、其中多少新客 |
| `POST /mp/share/click` | C（游客） | 记录点击并判定 |
| `GET /mp/home/exposure` | C（游客） | 首页「邻里在逛」（①拉新） |
| `GET /mp/home/following` | C（登录） | 首页「我常逛的店」动态流（②留存） |
| `POST /mp/store/{storeNo}/mute` | C | 关闭某店动态 —— **必须有，且立即生效** |
| `GET /ops/exposure-pool` | 平台 | 查看与人工干预（BLOCKED） |
| `POST /ops/exposure-rules` | 平台 | 曝光位数量、时长、防刷阈值 |

**`GET /biz/share/stats` 不是锦上添花**：看不到效果的激励等于没有激励。
商家分享完不知道有没有用，第二次就不分享了。

## 六、取舍记录

| 冲突 | 让了谁 | 为什么 |
|---|---|---|
| 计点击 vs 计新客 | **未归因点击为基准，新注册加权** | 只认点击是白送；只认注册门槛太高没人玩 |
| 复用归因表 vs 新建点击表 | **新建** | 语义不同；复用会让曝光点击反复刷新 30 天归因窗口 |
| 无效点击丢弃 vs 记录原因 | **记录** | 商家问「怎么没效果」时要能答"12 次老客、3 次你自己" |
| Top-K 排序 vs 权重轮播 | **权重轮播** | 目的是鼓励分享，不是把流量给最强的 |
| 曝光叠加 vs 续期 | **续期** | 叠加让一次爆发占住位置一个月，奖励的是运气不是经营 |
| 首页放门店 vs 放商品 | **商品** | 首页是逛货的地方，放门店卡片等于让用户多点一次 |
| 曝光突破可达性 vs 受限 | **受限** | 否则用户看到一家送不到他这儿的店 |
| 实时算 vs 预计算池 | **预计算** | 首页是最高频查询 |
| 要求点关注 vs 逛过即建立关系 | **逛过即建立** | 要求点关注会让转化在最开始掉一大半 |
| 商家手动发动态 vs 业务事件自动产生 | **自动** | 多一个发布入口就多一件商家要记得做的事，小店老板不会记得 |
| 「常逛的店」与「邻里在逛」合并 vs 分开 | **分开** | 一个是没见过的、一个是去过的，两种决策心智不同 |
| 逛过就推送 vs 只有下过单才推送 | **只有下过单** | 只逛过就推，他会觉得"我什么时候关注了这家店" |

## 七、待确认

| # | 事项 | 建议 |
|---|---|---|
| Q1 | 新注册的加权分 N | 5。让"带来一个新用户"明显重于"被老邻居点一下"，但不到"只有注册才算"的程度 |
| Q2 | 曝光期长度 | 7 天 |
| Q3 | 单店每日有效曝光上限 | 20。就算前五条防刷全被绕过，收益也有天花板 |
| Q4 | 首页「邻里在逛」展示几条 | 6 条，一屏能看完；再多会挤掉「社区在卖」 |
| Q5 | 店员分享算谁的 | 算门店的（曝光给门店），但 `shared_by` 记到人 —— 老板要能看到是谁在推 |
| Q6 | 曝光池要不要人工加白 | 要。新店冷启动时运营可以手动放进去，与「平台推荐位」同一个用途（ADR-009） |
