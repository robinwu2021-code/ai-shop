## 一、契约现状：三处对不上

积分的契约写在 `V17` 建模**之前**，至今没跟上。三处都不是笔误，是形状不对：

| # | 问题 | 后果 |
|---|---|---|
| 1 | `merchantPointAccount()` 返回 `PointAccount` —— **用户侧的形状** | 商家页面字段一个都对不上 |
| 2 | 该接口挂在 **C 端契约**（`c-app`，`/mp/merchant/point/account`） | 与 ADR-007「B 端契约独立」相悖 |
| 3 | `PointAccount` **没有 `pendingBalance`** | `V25` 的「待生效积分」没有下发通道 |

### 1.1 用户侧与商家侧根本不是同一种东西

| | 用户 | 商家 |
|---|---|---|
| 单位 | 积分个数 | **钱** |
| 关心什么 | 我有多少分、什么时候过期 | 本期付出多少费用金、收回多少 |
| 数据来自 | `pts_user_account` | `pts_merchant_ledger` 按期聚合 |

`PointAccount`（余额 + 累计收支 + 过期提醒）是用户侧的形状。
**商家不关心自己有几分，只关心这个月净收还是净付。**

### 1.2 修法

```ts
/** 商家积分账户 —— 预付费模型下只有**一本账**（资金） */
export interface MerchantPointAccount {
  // ── 资金（单位：分）
  /** 本期收到的积分对应金额（别人的分在本店被花掉，池子付我） */
  periodIncomeMinor: number;
  /** 本期付出的积分费用金（本店发分即扣，**不是**「我的分在别人那被花掉」） */
  periodExpenseMinor: number;
  /** 本期净额，正 = 平台付给商家，负 = 从下期货款扣 */
  periodNetMinor: number;
  /** 当前账期标识，如 2026-08 */
  period: string;

  // ── 开关（含主体前置）
  /** 本店积分是否生效 —— L1 AND L2 AND 主体 AND L3 */
  enabled: boolean;
  /** 不生效的原因，直接展示给商家 */
  disabledReason?: string;
  /** 平台按行业强制开，商家不可自行关闭 */
  forced: boolean;
}
```

`PointAccount` 补两个字段，让「可用 / 待生效」能分开展示：

```ts
  /** 待生效积分：已发放但未过售后期。**不计入 balance** */
  pendingBalance: number;
  /** 最近一批待生效积分的可用时间。pendingBalance=0 时为空 */
  pendingActivateAt?: number;
```

> 不补第二组的话，C 端只能显示一个 `balance`，
> 而设计要求的是「可用 400 分 / 待生效 100 分，3 天后到账」——
> 少了这两个字段，`V25` 拆出 `pending_balance` 的意义就没了。

**归属问题（#2）待定**：`merchantPointAccount` 是留在 C 端（商家用小程序看账）
还是迁到 `b-app`，取决于商家端形态（[ADR-001](../ADR/ADR-001-商家端形态与拆分时机.md)）。
本文按「接口形状先修对，位置后定」处理 —— 形状错了两端都做不对，位置错了只是搬家。

## 二、核心算法

上游文档给了规则（R1–R8），这里给**可实现的算法**。

### 2.1 发放：`grantOnPay(subOrder)`

触发时点：**支付成功**（R1.1）。用户立刻看得到分，但要等 `available_at` 才能用。

```
grantOnComplete(subOrder):
  1. 幂等闸：subOrder.points_granted == 1 → 直接返回（R1.7）
  2. 开关闸：canPoints(merchant) 为否 → 不发，标记 granted=1 并记原因
  3. 计算基数（R1.2）：
       base = Σ(订单行金额)                   ← 不含运费
              − 平台券补贴部分                 ← 商家没收到的钱不该由他出分
              − 赠品行                        ← is_gift = 1 的行不发
  4. 计算积分数：
       每行 points_config 有值 → 按行配置
       否则                    → base × 兜底比例
  5. 算费用金：feeMinor = points / 兑换比例
  6. 落账（同一事务）：
       pts_user_ledger   +EARN 行
                         available_at = 履约完成时间 + 售后期
       pts_user_account  **pending_balance** += points          ← 不进 balance
                         balance 只放能花的分，否则用户看到的数字没有意义
       pts_user_account  last_active_at = now                     ← **续期**
                         expire_at = now + inactiveDays
       pts_merchant_ledger  ISSUE_FEE, amount_delta_minor = −feeMinor
       ord_sub_order.points_fee_minor = feeMinor                ← 结算时从货款扣
       ord_sub_order.merchant_recv_minor -= feeMinor            ← 商家实收同步减少
       ord_sub_order.points_granted = 1
```

**第 6 步是预付费模型的全部**：发放的那一刻商家就付了钱（记账），
所以不存在或有负债，也不需要额度台账去追踪"还欠多少"。

**费用金只计提不移动**：钱在售后期前是冻结的，实际进池在解冻时（R4.6）。
`accrued_at` 与 `split_at` 分别记这两个时点。

### 2.2 抵扣：`deductOnPlace(order, usePoints)`

触发时点：**下单时**（R1.3——不是支付后，防同一笔分同时下多单）。

```
deductOnPlace(order, usePoints):
  1. 开关闸：canPoints(merchant) 为否 → usePoints 强制为 0
  2. 上限（R1.4）：
       maxDeductMinor = (券后金额 − 运费) × 30%
       maxPoints      = maxDeductMinor / 兑换比例
       actual         = min(usePoints, maxPoints, userBalance)
  3. 顺序：**券先抵、积分后抵**（R1.4）
       —— 顺序反了会让券的门槛达不到
  4. 落账（同一事务）：一条 USE 流水就够了 —— **没有批次可挑**
       pts_user_ledger   +USE 行 {
           points = −actual, amount_minor, rate_snapshot,
           acceptor_merchant_no,   ← 在谁家用的（池子要付给它）
           status = PENDING, sub_order_no }
       pts_user_account  balance -= actual
                         last_active_at = now            ← **续期**
                         expire_at = now + inactiveDays
       ord_sub_order.points_deduct / points_deduct_minor  ← 快照，结算与售后直接读
```

第 4 步曾经是「FIFO 取批次逐批递减 remaining」。批次概念在 `V30` 随滚动到期一起废除 ——
`remaining` 与批次级 `expire_at` 唯一的读者就是过期任务本身。

**这里不记「这些分是谁发的」**。积分发出去的那一刻商家就付过费用金了，
此后它是平台对用户的负债；收单方从池子拿钱，与发放方无关。
京东京豆、支付宝积分都是这个口径 —— 平台单一账户，兑付不追来源。

> 曾经有一张 `pts_redeem_alloc` 按发放商家把一次使用拆成多条。
> 那是**信用模型**的需求（A 发的分被花掉，A 要付钱给 B，所以必须知道拆分）。
> 改成预付费后这个需求就不存在了，表已于 `V28` 删除。

`status = PENDING` 表示**预占**：此时池子还没付给收单方，因为订单还可能取消或退款。

### 2.3 兑付成立：`confirmUseOnActivate(subOrder)`

触发时点：**售后期结束**（与积分转可用、货款解冻同一时点）。

```
confirmUseOnActivate(subOrder):
  use = 该子单的 USE 流水(status=PENDING)
  use.status = CONFIRMED; use.period = 当期
  stl_payment: SUBSIDY, sub_order_no = 本单, amount = use.amount_minor  # 通道补差
  stl_points_pool: OUT, MERCHANT_PAY, amount = use.amount_minor
```

**一次使用 → 一条进账 → 一笔出池**，三者一一对应。
之前要在这里 Σ 一遍拆分明细，现在没有明细可 Σ。

> **收单方的钱来自池子，不是来自发放方。**
> 这是预付费与信用模型最直接的差别：`REDEEM_OUT` 那一笔不存在了。

### 2.3b 转正：`activateDaily()`

```
每日任务（也可在售后期到点时触发）：
  for 行 in pts_user_ledger(biz_type=EARN, available_at <= now, 未转正):
     pts_user_account  pending_balance -= points
                       balance         += points
```

走 `idx_pts_activate (available_at, biz_type)` 全表扫 —— **按时间**扫不是按用户扫。

`available_at` 与到期无关：它管「这批分能不能花」（售后期内不能），
到期管「账户还留不留分」（长期不活跃就清零）。两件事，`V30` 之后只有前者留在流水行上。

### 2.4 取消与退款：`reverse(subOrder, kind)`

退款按三种情形分流（**用 A/B/C 编号，避免与开关的三级灰度 L1/L2/L3 混淆**）。上一版靠「等待期后不可退款」把最麻烦的那层绕过去了，
但那是**假设不是保证** —— 质量问题、法定退货权都可能让退款发生在售后期之后。

| 层 | 情况 | 已发的分 | 商家费用金 | 退款金额 |
|---|---|---|---|---|
| **情形 A** | 待生效期内（**绝大多数**） | 从 `pending_balance` 撤销 | 退还 | 全额 |
| **情形 B** | 已生效、账户余额够扣 | 从 `balance` 扣回 | 退还 | 全额 |
| **情形 C** | 已生效、**账户余额不够扣** | 能扣多少扣多少 | **差额部分不退** | **扣减差额** |

判据从「这批分被用掉了多少」改成「**账户现在够不够扣**」——
后者只要一次余额比较，不需要任何批次消耗明细。这也是京东的口径：
「所购商品发生退货，需要扣除该商品所获赠的京豆，如账户京豆不足，则从商品退款金额中扣除相应的现金」。

```
reverse(subOrder, kind):
  # ── 先还回本单**抵扣**掉的分（与发放侧无关，任何情形都要做）
  use = 该子单的 USE 流水
  if use and use.status != REVERSED:
     if use.status == CONFIRMED:
        pts_merchant_ledger(use.acceptor): −use.amount_minor
        stl_points_pool: IN, RECOVERY, +use.amount_minor
     use.status = REVERSED
     pts_user_ledger +REFUND 行 { points = +use 的绝对值 }   ← 就是加回余额
     balance += 返还数
     # 「退回的分有效期怎么算」这个问题在 V30 **整个消失** ——
     # 到期挂在账户上，退回就是加回余额，顺带把到期日往后推

  # ── 再扣回本单**发放**的分
  earn = 本单的 EARN 行
  if 未到 earn.available_at:                     # 情形 A
     pending_balance −= earn.points
     作废该 EARN 行；pts_merchant_ledger REVOKE_REFUND, +已扣费用金
  else:
     clawback = min(earn.points, balance)        # ← 唯一的判据
     balance −= clawback
     shortfall = earn.points − clawback
     if shortfall == 0:                          # 情形 B
        pts_merchant_ledger REVOKE_REFUND, +已扣费用金
     else:                                       # 情形 C
        offset = shortfall / earn.rate_snapshot   # 折成钱
        ord_after_sale.points_offset_minor = offset
        退款金额 = 应退 − offset                  ← **必须在退款单上明示**
        # 差额对应的费用金**不退**：那部分分已经被兑现，池子付出去了
     pts_user_ledger +REVOKE 行（记录扣回，balance_after 快照）
```

**为什么不让余额变负**：用户看到负余额会来投诉，而且他要是不再消费，
那就是一笔坏账永远挂在账上没人处理。从退款里扣是**当场结清**。

**为什么按账户余额而不是按「这批分被用掉了多少」**：
两者在多数情况下结果相同，但后者要求全程维护批次消耗明细。
用户的分是混同的一池 —— 他账上还有 500 分，就没有理由追问「这 500 里有没有你这单发的」。

⚠️ `points_offset_minor` **必须在退款单上明示**：
「已使用积分优惠 1.00 元，本次退款 99.00 元」。不写清楚必然客诉。

### 2.5 到期清零：`expireDaily()`

滚动到期（`V30`）：**扫账户不扫流水**，每个用户一行。

```
每日任务：
  # ── 先提醒。到期日因人而异，用户不可能自己算出来
  for acc in pts_user_account(expire_at - now <= 30 天, expire_notified_at 为空):
     推送「你的 {balance} 积分将于 {expire_at} 到期，消费或使用积分即可续期」
     acc.expire_notified_at = now

  # ── 再清零
  for acc in pts_user_account(expire_at <= now, balance + pending_balance > 0):
     total = acc.balance + acc.pending_balance
     pts_user_ledger  +EXPIRE 行（−total，整账户一次）
     acc.balance = 0; acc.pending_balance = 0
     stl_points_pool: OUT, EXPIRE_INCOME, amount = total / 兑换比例
     # 商家不退还（决策 2026-08-06）—— 故无 EXPIRE_BACK 记账
```

**提醒不是可选项**。滚动到期是**一次性全部清零**，冲击远大于零星过期；
而到期日因人而异，用户没有任何办法自己算出来。不提醒的话这个模型对用户是敌意的 ——
他不知道自己在倒计时，醒来发现全没了。`expire_notified_at` 是幂等位，任务重跑不能提醒两遍。

**续期发生在 EARN 与 USE，不发生在 REVOKE / EXPIRE**。
用分也算活动是因为兑换正是我们想鼓励的行为 —— 只认「获得」的话，
一个只花不赚的用户会被清零，而他恰恰在帮池子出清。
REVOKE 不算：那不是用户主动行为，且「退一单续一年」可以被反复触发。

> **过期资金归平台**（决策 2026-08-06）。要记一笔 `EXPIRE_INCOME` 出池，
> 而不是让钱静静躺着 —— 不记的话池子余额只增不减，恒等式对不上，
> 而对不上时没人分得清是「有分没钱」的事故还是「到期沉淀」的正常现象。

### 2.6 对账：`reconcileDaily()`

上游 R7 要求明细可查、可监控。校验两条恒等式：

```
① 用户侧：pts_user_account.balance == Σ pts_user_ledger.points
② 池子侧：stl_points_pool 余额 == Σ(流通中未兑付积分 × 汇率)
```

不一致时**以流水为准**，重算账户并告警——账户表是派生的（上游 2.1 已定此规矩）。

第三条跨账勾稽（与资金账）：

```
③ Σ ord_sub_order.points_deduct_minor == Σ pts_user_ledger.amount_minor(USE, CONFIRMED)
```

对不上说明有一侧漏记，是[总方案 §7.3](./多端多通道-平台能力总方案.md) 要求的勾稽点。

## 三、接口设计

### 3.1 C 端 `/mp/**`

| 方法 | 路径 | 说明 | 状态 |
|---|---|---|---|
| GET | `/mp/points/account` | 我的积分账户（含**待生效**） | ⚠️ 契约里是 `/mp/point/account`（单数），要统一 |
| GET | `/mp/points/records` | 积分流水（分页） | ⚠️ 同上，且**改为分页** |
| GET | `/mp/points/deductible` | **结算页试算**：本单最多可抵多少 | ★ 新增 |

`/mp/points/deductible` 入参 `{ items[], couponNo?, merchantNo }`，出参：

| 字段 | 说明 |
|---|---|
| `maxPoints` | 本单最多可用积分数 |
| `maxDeductMinor` | 对应金额 |
| `balance` | 用户当前余额 |
| `enabled` | 本店积分是否可用 |
| `disabledReason` | 不可用原因——**小微商家在这里返回"升级后可开启"** |

> 【为什么要单独一个试算接口】上限是 `(券后金额 − 运费) × 30%`，
> 依赖券的选择。端上自己算必然与服务端算法分叉，
> 而**分叉的表现是"页面说能抵 5 元、下单只抵了 3 元"**——用户会认为在骗他。

### 3.2 B 端 `/biz/**`

| 方法 | 路径 | 说明 | 状态 |
|---|---|---|---|
| GET | `/biz/points/account` | 本期发分服务费 + 开关状态 | ★ 新增（目前挂在 C 端契约，形状也不对） |
| GET | `/biz/points/records` | 发分服务费明细（按单） | ★ 新增，数据来自 `stl_bill.points_fee_minor` |
| POST | `/biz/points/toggle` | 开/关本店积分 | ★ 新增 |

> **原来这里还有两条「积分账期单」端点，已删。** `stl_points_bill` 在 `V34` 随
> 「商家不感知积分抵扣」一起废除 —— 商家侧没有积分账期这回事了，
> 他只有一项按单计提的发分服务费，混在普通结算单里。
>
> `/biz/points/records` 的数据源也从已删的 `pts_merchant_ledger` 换成了 `stl_bill`。

`POST /biz/points/toggle` 的规则（**服务端强制**，不靠前端禁用按钮）：

| 情况 | 行为 |
|---|---|
| 主体是 `MICRO` | **拒绝**，返回"升级为个体工商户后可开启" |
| `forced = 1` | **拒绝关闭**，返回强制开的说明与申诉入口（R3.3） |
| L1/L2 未开 | 拒绝，返回"平台/本社区暂未开放" |
| 关闭 | 允许，**仅影响将来**；存量已发积分仍有效、债务仍需承担（R2.2） |

## 四、幂等与并发

| 场景 | 手段 | 说明 |
|---|---|---|
| 重复发放 | `ord_sub_order.points_granted` | V17 已有 |
| 重复抵扣 | 下单幂等 `idempotencyKey` | 抵扣随下单发生 |
| 重复兑付 | USE 流水的 `status` 状态机 | `PENDING → CONFIRMED → REVERSED` |
| 余额并发扣减 | **条件写在 WHERE 里** | 见下 |
| 费用金重复计提 | `ord_sub_order.points_granted` | 订单维度，无共享计数器 |
| 重复转正 | EARN 行是否已转正（`pending → balance` 只做一次） | 转正任务可能重跑 |

```sql
-- 用户余额扣减：先查后扣在并发下必然扣穿
UPDATE pts_user_account
   SET balance = balance - #{points}, total_use = total_use + #{points}, version = version + 1
 WHERE user_no = #{userNo} AND deleted = 0 AND balance >= #{points}

-- 费用金没有并发争用：它是订单维度的一次计提，靠 points_granted 幂等即可，
-- 不像额度那样是商家维度的共享计数器 —— 这也是预付费模型顺带省掉的一处并发设计。
```

返回 0 行 = 余额不足，**按业务分支处理，不重试**。

## 五、状态机

### USE 流水的 `status`（原 `pts_redeem_alloc.status`）

```
PENDING ──▶ CONFIRMED ──▶ REVERSED（退款/取消，反向记账）
   │
   └──▶ REVERSED   订单在兑付成立前就取消

自发自用不是一个状态，而是 `self_used=1` 标记：
它照常 CONFIRMED，但账期单聚合时按该标记排除（R5.3）。
状态（走到哪一步）与是不是自用（谁对谁）是两件正交的事，压成一个枚举会丢信息。
```

### `stl_points_bill.status`

```
DRAFT ──▶ CONFIRMED ──▶ SETTLED
```

`DRAFT` 是账期内边跑边攒的草稿，期末封账转 `CONFIRMED`，打款后 `SETTLED`。

净额为正 → 平台付给商家；为负 → 并入下期货款扣除（R5.2）。

## 七、验收

| 断言 | 防住什么 |
|---|---|
| 同一子单重复调 `grantOnComplete` 只发一次 | 重复核销重复发分（R1.7） |
| 赠品行不发分、运费不计入基数 | 买赠 + 积分叠出套利（R1.2） |
| 抵扣上限恒 ≤ 券后金额 30%，运费不参与 | 整单抵扣商家一分收不到（R1.4） |
| **券先抵、积分后抵** | 顺序反了券的门槛达不到 |
| 退款后用户积分**不净赚**（两笔都走） | R1.6 |
| 发放即产生 `ISSUE_FEE`，金额等于 points / 兑换比例 | 或有负债藏在账外 |
| 未到 `available_at` 的分**不进 balance** | 等待期内就能花分 = 套利窗口打开 |
| 待生效的分**不计入** `balance` | 用户看到的可用数字是假的 |
| 情形 C 退款时 `points_offset_minor` 有值且退款单明示 | 用户白赚优惠，且不知道为什么少退了 |
| 任何积分变动都刷新 `expire_at` | 不刷新的话滚动到期退化成固定期限，而没有任何症状 |
| 过期时**释放发放方额度** | 额度只增不减最终停发 |
| `MICRO` 主体调 `/biz/points/toggle` 被拒 | 小微不参与积分（总方案 §8.1） |
| `forced=1` 时关闭被拒 | R3.3 |
| 三条对账恒等式成立 | §2.6 |
