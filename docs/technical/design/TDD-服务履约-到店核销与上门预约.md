## 1. 为什么现在做（L1）

**多场景履约是这个平台的定位，不是可选项**：服务、自提、自送、物流、到店核销并存。
而现在后端只认四种，服务类那两种（到店核销、上门预约）**整个不存在**——
连带的后果是「家政服务」这个已经注册的小程序类目，**没有任何功能对应它**。

好消息是：**缺的比看上去少**。端上早就建完了，后端的地基也留好了位置。

### 地基已经留好的三处

| 处 | 内容 | 意味着 |
|---|---|---|
| `prd_goods.duration_min` | 服务时长（分钟） | 库里早就为服务类留了字段 |
| `prd_goods.fulfillments` | 商品支持的履约方式（复数） | 一个商品可支持多种，下单时选一种 |
| `ord_sub_order.appointment_at` | 预约开始时间戳 | 预约时间不用新增列 |

### 状态机**不用改**

```
WAIT_FULFILL → FULFILLING | COMPLETED | REFUNDED
```

`WAIT_FULFILL → COMPLETED` 本来就允许直连。**到店核销就是这条路**：
付款后持码，核销即完成，中间不需要 `FULFILLING`（没有"在途"这回事）。

## 3. 核心设计：展示状态怎么定（L3）

> ⚠️ **本节（3.1–3.2）已被 [订单状态-统一整理](../reference/订单状态-统一整理.md) 取代。**
> 那里提出的原则是「状态抽象、展示分化」：新增 `TO_USE` / `TO_SERVE` 意味着
> **每来一种履约就加一批状态**，不可扩展。正确做法是状态保持 6 个抽象值，
> 由 `(状态 × 履约 × 信息)` 决定展示。下面保留原文只为记录当时的推理。

### 3.1 ~~划分依据：用户的下一步动作~~（已被取代）

已有的 `ARRIVED` / `SHIPPED` 之所以要分开，不是因为库里不同（库里同为 `FULFILLING`），
而是因为**用户要做的事不同**：一个是「你去取」，一个是「你等着」。

把这条原则贯彻下去，服务类的两种也就定了：

| 用户的下一步 | 拿实物 | 用服务 |
|---|---|---|
| **你去** | `ARRIVED` 待取货 | **`TO_USE` 待使用** |
| **你等着** | `SHIPPED` 待收货 | **`TO_SERVE` 待服务** |
| 你什么都不用做 | `PAID` 待发货 | 同左 |

- **`TO_USE`（到店核销）**：持码，随时去店里用掉。用户随时可动，**没有时间约束**
- **`TO_SERVE`（上门预约）**：约好了时间。用户要做的是「到点在场」，
  **界面必须显示预约时间**——没有时间的「待服务」等于没说

> **为什么不合成一个「待使用」**：这两者对用户的信息需求不同。
> 到店核销要的是「码是多少、店在哪」，预约要的是「几点、谁来」。
> 合成一个词，预约单的时间就没有自然的落点。

### 3.2 `INSTANT` 不进这套

虚拟商品与卡券**付款即完成**（`instant: true`，策略里已这么写），
直接落 `COMPLETED`，不经过任何等待态。不需要展示状态。

### 3.3 各层改动清单

| 层 | 文件 | 改什么 | 量 |
|---|---|---|---|
| 后端常量 | `common/Fulfillments.java` | 加 `STORE_VERIFY` / `APPOINTMENT` / `INSTANT` | 小 |
| 后端视图 | `trade/service/OrderStatusView.java` | 加 `TO_USE` / `TO_SERVE` 两个展示状态与双向映射 | 小 |
| 后端下单 | `OrderServiceImpl.requireFulfillmentSupported` | 放行新履约；`APPOINTMENT` 必须带 `appointmentAt`，缺了拒绝 | 小 |
| 后端核销 | 核销入口 | 现在只认自提点场景；要支持**按商家门店核销**（到店核销与预约共用） | **中** |
| 后端商品 | `prd_goods.type` | 认 `SERVICE`；`duration_min` 接上 | 中 |
| 契约 | `packages/shared` | `OrderStatus` 加两个值；`PLANNED_FULFILLMENTS` 清空 | 小 |
| c-app | 订单 tab、订单详情、结算页 | 见 §4.4；预约要有时段选择器 | **中** |
| b-app | 核销台、订单页签 | 核销台要能核服务单；页签加「待服务」 | **中** |
| 守卫 | `enum-alignment.test.ts` | 删掉 `FULFILLMENT` 豁免那半句 | 小 |

**最重的是核销入口**：现在的核销是「自提点运营者核销代收的货」，
而服务核销是「商家在自己店里核销自己卖的服务」——两者的权限与数据范围不同
（见[项目词典](../../requirements/项目词典.md) §Pickup vs Store verify 那条对照）。

### 3.4 待你拍板：tab 会变成 8 个

加完之后 c-app 订单页签是：

```
全部 · 待付款 · 待发货 · 待取货 · 待收货 · 待使用 · 待服务 · 已完成 · 售后
```

**9 个。** 现在 7 个在 375px 下已经要横滑了。两条路：

| 方案 | 页签 | 取舍 |
|---|---|---|
| **A. 按「下一步动作」归并**（推荐） | 全部 · 待付款 · **待处理**(PAID) · **该你了**(ARRIVED+TO_USE) · **等着收**(SHIPPED+TO_SERVE) · 已完成 · 售后 = 7 个 | 页签数不涨；但「该你了」这类词要斟酌，且同一页签内混着实物与服务 |
| **B. 一状态一页签** | 9 个 | 语义最清楚，横滑最长。老用户找单要滑三下 |

**展示状态本身两种方案都一样定义**（后端不受影响），差别只在 c-app 怎么归并页签。
b-app 那边不受这个决定影响——商家侧本来就该一状态一页签（他要分别处理）。

## 9. 一期实现记录（2026-08-17）

**比 §3.3 估的小得多** —— 因为订单状态先做了[统一整理](../reference/订单状态-统一整理.md)：
状态集合封闭之后，接一种履约不再需要碰状态、状态机、三端页签。

| 层 | 实际改动 |
|---|---|
| `Fulfillments` | 加 `STORE_VERIFY`；同时抽出 `SERVICE_LIKE` 与 `PHYSICAL` 两个语义分组 |
| `OrderStateMachine` | 放行 `WAIT_PAY → FULFILLING` 一条边 |
| `OrderServiceImpl` | 支付成功分支：服务类落 `FULFILLING`，实物类仍落 `WAIT_FULFILL` |
| `OrdSubOrder` | 加常量（枚举对账扫的是这里） |
| shared / 守卫 | `PLANNED_FULFILLMENTS` 摘掉它；`enum-alignment` 与 `check-enum-fields` 的白名单跟上 |
| 核销 | **一行没改** |

### 核销为什么不用改

`findByVerifyCode` 与 `complete()` 本来就**不看履约方式**；
而 b-app 的「待核销」页签在状态重整时已改成谓词
`FULFILLING ∧ {SELF_PICKUP, SELF_SERVE}` —— `STORE_VERIFY` 归在 `SELF_SERVE`，
自动就进去了。**这正是「状态集合封闭、履约集合开放」想要的效果。**

### 顺手堵的一个坑

新建商品的默认履约原本是硬编码的四个值。加第五个值时没受影响纯属侥幸 ——
下一个人很可能顺手把 `APPOINTMENT` 塞进去，于是**一件大米声称支持上门预约**。
抽成 `Fulfillments.PHYSICAL` 并在注释里写明「服务类要商家显式选」，
让这个意图挡得住下一次扩充。

> 同一个坑踩了两次：Java 常量写成引用（`= Fulfillments.X`）时枚举对账扫不到字面量，
> 而「扫不到」与「两端不一致」在报告里长得一样。`FULFILLING` 和 `STORE_VERIFY`
> 各中了一次。

### 未验

支付是桩，**到店核销的完整链路没有真跑过**：发服务商品 → 下单 → 支付 → 核销 → 完成。
测试覆盖的是状态机与取值域，不是那条链路本身。接了真支付要补一轮。

## 10. 二期实现记录（2026-08-17，上门预约）

与一期的差别**只有两道闸**，都不涉及状态：

| 闸 | 规则 | 不加会怎样 |
|---|---|---|
| **预约时段** | `APPOINTMENT` 必须带 `appointmentAt`，且不能是过去 | 单能下成、能付款，然后商家不知道该几点去、买家不知道约了没有 —— 两边只能打电话 |
| **上门地址** | 并入 `SHIPPED_FULFILLMENTS`（要地址的那一组） | 师傅不知道去哪 |

> 地址那道闸按「**要不要地址**」分组，而不是按实物/服务 ——
> 上门预约与快递、自送在这件事上是同一类，按需求分组比按品类分组更贴近它真正要判的东西。

**`appointmentAt` 从下单一路落到子单再下发**：`CreateOrderReq` → `CreateOrderCommand`
→ `ord_sub_order.appointment_at` → `OrderVO`。端上契约里这个字段**一直都在**，
只是后端从没发过 —— 又是一处「端上声明了、后端不发」。

### 仍然不需要新增状态

`APPOINTMENT` 归进 `SERVE_TO_BUYER` 交付形态，文案由 `orderView()` 给出
`FULFILLING_SERVE_AT`（带时间）。**状态枚举、状态机、三端页签一行没动。**

### 三端跟进

ops-web 的 `FulfillmentType` 与两处 i18n 要补 `APPOINTMENT` ——
枚举对账当场报了「后端有、端上没有」。第三端总是最容易掉队的那个。

### 二期收尾：c-app 时段选择器（同日完成）

结算页加了「上门时段」区块 —— 与地址**并列**而不是塞进地址块：
它们回答两个不同的问题（「去哪」和「几点」），缺任何一个这单都履约不了。

| 点 | 做法 |
|---|---|
| 时段来源 | 今天起 `TRADE_RULES.appointmentWindowDays`（7 天）× 每天 5 个整点 |
| 过去的时段 | 端上就滤掉 —— 后端那道闸也会拒，早点拦住比让他撞一次好 |
| 提交闸 | 没选时段按钮灰掉，理由同上 |
| **`needAddress`** | **顺手修了一处两端不一致**：端上此前只算快递与自送，而后端的 `SHIPPED_FULFILLMENTS` 已含 `APPOINTMENT` —— 端上放行、后端拒收，用户点提交拿到一个说不清的错误 |
| mock | 两道闸逐条同形。mock 宽松而后端严格是最坏的一种不一致：本地怎么点都对，一连真后端就炸 |

**不做真正的排期**（师傅有没有空）—— 一期就说明不做，仍不做。
这里只解决「买家说个时间、商家知道几点去」，商家线下确认。
