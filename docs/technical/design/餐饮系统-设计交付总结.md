# 餐饮系统设计交付总结

> 状态：待评审 · 2026-10-20。本文汇总方案与交互原型；不表示后端接口已实现或数据库迁移已执行。

## 一、已确定的设计方向

复用当前商品、SKU、定价、库存、订单、支付与退款能力，以额外餐饮表和独立 Java 模块承载行业规则。支持独立部署与集成到 core；账号、主体、商户、门店、营业时间和公共协议沿用项目底座。

菜单独立管理，菜品引用基础商品；收费配料引用 SKU，免费口味复用属性字典并增加餐饮选择规则。套餐、配料组合、时段餐牌、工位和成交快照通过餐饮扩展表达，避免复制商品价格与库存账。

就餐台账与核心交易订单分开：支持线上线下、多终端、现付后吃与先吃后付、加退餐、转并拼桌、厨房制作、打印、交班、营业日与日结报表。第三方餐饮对接和断网营业纳入目标范围，通过适配与恢复合同逐步落地。

## 三、可查看的交互原型

- [平板收银原型](../../../prototypes/food-cashier-tablet.html)：桌台、点餐、收款与交班四屏；白底黑按钮，保留菜品图片，点击直接加购，购物车调整数量，分类位于菜品区；保留其他主题选择。
- [服务员点餐原型](../../../prototypes/food-ordering.html)：桌台、点餐、制作进度及预结账四屏。

原型使用演示数据，不执行真实支付和日结。图片随仓库保存，平板交互脚本独立存放。通过仓库根目录静态 HTTP 服务访问，可避免本地文件打开限制。

## 四、实施前必须确认的边界

当前核心退款以整门店订单全额退款为边界；按菜品部分退款、后付库存与履约、跨支付根结账及混合收款必须补齐核心合同。不能直接写核心表或用前端状态代替资金结清。

离线写者仲裁、幂等恢复、第三方映射、打印重试、日结资金水位及签核证据均需在实施阶段验证。文档中的接口、表与类是目标清单；正式迁移前还需确认物理索引、并发 SQL、容量和通用能力复用。
