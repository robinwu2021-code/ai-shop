## 一、一句话

多门店的**骨架已经通了**（切店、店级库存、店级上架、店级订单、门店档案），
缺的是三样：**额度这道闸**、**这个包真正卖的东西（跨店总览与对比）**、**收钱的链路**。

**而第二样是最要命的**：跨店总览与对比**一行代码都没有**。
先做额度闸再卖包，等于卖一个「除了限制你什么都没多给」的东西。

### 2.2 三条结论

1. **多门店本身不用再造**。第 5–8 项都在跑，且有测试。计划的起点不是「做多门店」，是「给它装闸和装价值」。
2. **第 9/10 项是这个包的全部卖点**，而它们是空的。需求 §2.2 原话：只做「能开第二家店」不做总览与对比，**商家花了钱仍然要切来切去，他会觉得被骗了**。
3. **第 13 项不是一个接口，是一条新链路**。商家向平台付款与现有的交易收款方向相反，涉及通道、发票、退订退款——**一期不做**（TDD T1），走运营手工授予。

## 三、执行计划：四期，每期可独立发布

排序原则：**先让额度闸「存在但不改变行为」，再补价值，最后才谈收钱。**
这样任何一期停下来，线上都是自洽的。

### P1 · 额度模型落地（零行为变化）

**目标**：把「能开几家店」从全局配置换成按主体的档位，**上线当天所有商家零感知**。

| 步骤 | 完整工作 |
|---|---|
| 1.1 建表与种子 | `sys_merchant_plan_def` + `mch_entity_plan`（DDL 见 TDD §4.2.1）· 三档种子 FREE 1/0、PRO 3/3、CHAIN 10/15 · **存量主体全部回填 FREE 1/0** · 同步 `schema-test.sql` · ⚠️ 回填是 DML，测试库不跑，**上预发库单独验一次** |
| 1.2 `mch_store` 加 `plan_suspended` | 区分「降级压下的」与「商家自己停用的」（TDD §4.6.2）· 同步 `schema-test.sql` |
| 1.3 `MerchantPlanService` | 读有效额度（override → 快照 → 配置兜底三级）· 能力位查询 · **建店/加子账号事务开头锁 plan 行**（TDD §4.6.1 的并发闸） |
| 1.4 额度校验接入 | `StoreAdminServiceImpl.create()` 换掉 `@Value` · 子账号邀请接入 · 超额错误带三个数（现在几家/上限几家/怎么解决），复用 `STORE_QUOTA_EXCEEDED` 70020 |
| 1.5 测试 | 额度闸拒绝与放行 · **并发建店不越额**（两线程同时建，只成一个）· 无 plan 行时走配置兜底 · **存量回归：单店商家行为逐字不变** |

**验收**：全量测试绿；一个 FREE 商家建第二家店被拒且报错说清三个数；存量商家无任何可感知变化。

**为什么先做它且要求零行为变化**：额度是后面所有事的地基，而它一旦搞错就是「商家突然开不了店」。
先让它在不改变任何人行为的前提下跑起来，把风险留在可回滚的一步里。

**后端落地记录（2026-08-14）**：

| 项 | 结论 |
|---|---|
| 接口 | `GET /biz/cross-store/overview` · `GET /biz/cross-store/compare?days=30`，权限均挂既有 `biz:customer`（与 `/biz/dashboard/stats` 同一档，**不新造码**） |
| 门禁 | 两道**正交**的门：权限管「这个人能不能看」，能力位管「这家店买没买」。无能力位报新错误码 `PLAN_CAPABILITY_REQUIRED`(70023)，文案带**当前档位** |
| 聚合 | `statsByStore` / `todoByStore` / `compareByStore` 三个方法，**一次扫描按店分组**，不逐店循环调 `stats()`（那是 N 次全表扫，而门店数正是这个功能的自变量） |
| 待办 | 只给门店维度的 `toShip`/`toDeliver`/`toStock`。`toVerify`/`toPick` **刻意不给** —— 它们是自提点维度且不限商家，摆进门店列会被读成「这家店的活」 |
| **评分** | ⚠️ **仍是主体级，放在返回体顶层，不进每店那一行**。`rvw_review` 只有 `entity_no` 没有 `store_no`，门店维度的评分**没有数据源**。塞进每行会让各店显示同一个数，用户会以为是 bug。要按店得先做「评价归门店」（C 端写入 + 历史回填），是独立改造 |
| 缺货 | 该店 `prd_store_stock` 里可用量（stock − locked）≤ 0 的行数，**只数已启用店级库存的 SKU** |
| 历史单 | `store_no` 为空的老单**不计入任何一行**（随便挂给默认店会让那家店与它自己的订单列表对不上）—— 于是「各店之和」可能小于主体总数，这是刻意的 |

**为什么 2.5 要给 FREE 看到**：这一页是升档的唯一说服力来源。
藏起来的结果是商家不知道有这个东西，而运营还得靠电话去讲。

#### P3 落地记录（2026-08-14）

11 条场景测试全绿（`OpsMerchantPlanFlowTest`，手机号段 126011xxxxx / 130011xxxxx）。
与上面这张表相比有**两处刻意的偏离**，都写在代码注释里：

| 偏离 | 计划原文 | 实际做法与理由 |
|---|---|---|
| 档位定义的写权限 | 「权限挂既有商家治理码，**不新造码**」 | 仍不新造码，但用的是 `system:param:update` 而**不是** `merchant:merchant:ban`。这是一次职责分离：**BD 能给某家授予套餐，但不能改「套餐是什么」** —— 后者影响这一档之后的所有新订阅，与「功能开关、灰度、汇率」同级。读（档位列表）反过来挂 `merchant:merchant:read`，因为授予对话框要拿它填下拉 |
| 端点数 | 「六条端点（看板/**详情**/授予/额度覆盖/档位定义/升档信号）」 | 仍是六条，但**详情那一条没做**，换成了「档位定义」的读写各一条。列表行本身已带全部字段（额度/已用/状态/到期/来源/降级时间），再要一条详情等于多一个出口、多一条权限规则，而它答不出列表答不出的任何问题。另有一条实际收益：`/ops/merchant-plans/{merchantNo}` 会在路径匹配上吞掉 `/upgrade-signals`，而那种冲突不报错，只是让信号页返回「主体不存在」 |

**落地时发现并修掉的两个真缺口**：

1. **`MchStore.planSuspended` 字段根本不存在** —— V150 建了 `plan_suspended` 列，实体上却没有对应字段。
   于是「降级压店时标明是平台压的」这件事在 P1 只存在于 DDL 里，代码一行都写不出来。
   这是 P1 自查没抓到的：迁移与实体分两处改，只改一处**不报错**，直到有人去写那个赋值。
2. **无权限的断言写法** —— 本仓库把 `AccessDeniedException` 映射成统一信封（HTTP 200 + `code=10403`），

## 四、依赖与并行

```
P1 额度模型 ──┬──→ P3 运营端管理 ──┐
              │                     ├──→ P4 商家侧与购买
P2 跨店价值 ──┴─────────────────────┘
```

- **P1 是所有事的前置**（没有 plan 表，P3/P4 无从谈起）
- **P2 与 P3 可并行**（一个在 b-app + trade 聚合，一个在 ops-web + merchant 域）
- **P4 必须在 P2 之后**：没有跨店价值就开卖，卖的是一个空壳

## 五、每期的「完成」定义

沿用仓库既有口径（[交付计划-商家侧](../../requirements/交付计划-商家侧.md)）：
**一件事没有全链路打通（端 → API → Controller → Service → Mapper → DB → 测试），就不算交付。**

每期额外必须满足：

| 项 | 要求 |
|---|---|
| 迁移 | 同步 `schema-test.sql`；含 DML 的**在预发库单独验过** |
| 权限 | 端点挂 `@PreAuthorize`；规则登记进 `perm-endpoint-map.mjs`；矩阵基线重生成；**function_point 种子落库**（不落 = 页面在但 403） |
| 前端 | `npm run check` 绿；`gen:api` 绿；若后端补齐了某能力，**同步翻掉 `perm-map.ts` 的 UNIMPLEMENTED**（不翻 = 功能白做） |
| 测试 | 断言能在撤掉实现后变红；**不只断言接口 200** |
| 文档 | 状态行更新；与代码不符时**改文档**（代码是事实） |

## 六、待确认（Q1 决定 P4 的形状）

| # | 问题 | 建议 |
|---|---|---|
| **Q1** | **购买怎么收钱** | 一期建议**不接支付**：商家点「升级」→ 联系平台 → 运营在 ops 端授予（`granted_by=PLATFORM`）。理由：「商家 → 平台」的收款方向**一条链路都没有**，接它涉及通道签约、发票、退订退款，是一个独立项目；而在验证「有没有人愿意买」之前建这条链路，是拿最贵的一步去赌一个未验证的假设 |

## 七、这个计划刻意不做的

| 不做 | 为什么 |
|---|---|
| 自动续费与账单 | 支付侧的事，且一期没有支付（Q1） |
| 跨主体的门店转移 | 转移意味着历史订单结算方变了，是财务事故不是功能（需求 §四） |
| 门店级独立进件 / 独立费率 | 通道按主体发号（ADR-011），费率是主体谈的 |
| 把费率做成档位差异 | 等于回到抽佣，只是换了个名字（上游方案否决的方案 F） |
| 降级时关店 | 关店伤的是消费者（下了单提不了货），而欠费是商家与平台之间的事 |
