## P1 · 每人限购：后端一处都不拦

### 实测

- 商品表有 `limit_per_user`，B 端能设（`MerchantGoodsServiceImpl:1326`），C 端详情页能看到「每人限购 N 件」。
- **下单链路一处都没校验它** —— `trade` 包里搜不到任何限购判断。
- **只有 mock 在拦**（`c-app/src/api/mocks/catalog.ts:192`：加购超限抛「每人限购 N 件」）。
  于是在本机点一遍是对的，真后端上买 50 件也照样下单。**mock 把缺口盖住了。**

### 方案

- **后端下单时校验**（建单与预览两处，预览给信息、建单是闸门）：
  - 已买量 = 这个用户在这件商品上，**状态不是 CANCELLED / REFUNDED** 的子单行数量之和；
  - `本单数量 + 已买量 > 限购` → 建单拒绝，错误码新开 `PURCHASE_LIMIT_EXCEEDED`，文案带「还能买 N 件」。
- **预览的 `maxQty` 取 `min(库存, 限购 − 已买量)`**，并补 `limitReason`（`STOCK` / `PER_USER`）——
  端上步进器那句「仅剩 N 件」要能说成「每人限购 5 件，你已买 3 件」。
- 加购也拦（购物车那条路现在同样不拦）。
- **去掉 mock 里的限购拦截**，改成读后端同一套规则的替身 —— 否则它会继续替真后端背书。

### 口径要点

- 已取消、已退款的不算已买 —— 退了货还占着名额，用户会觉得被坑。
- 统计窗口：**不设窗口**（终身限购）。若商家要「每天限购」那是另一个字段，本次不做。

### 测试

后端：限购 2 → 买 2 成功，再买 1 被拒；取消其中一单后能再买；预览 `maxQty` 随已买量变。
消融：去掉建单校验 → 红。端上：`limitReason = PER_USER` 时文案不同。

## P2 · 退款退积分：拆成风险差很大的三块

### 实测（这一条改变了原计划）

原以为「付款成功时抵扣就转 CONFIRMED」—— **不对**。抵扣的确认点是**分账**：
`SettleServiceImpl` 在分账成功（或归集付款）那一刻才调 `confirmDeduction`，
理由写在代码里：「分账成立意味着钱真的到了商家账户，此刻才谈得上平台已付」。
而退款前必须先回退分账（E4，状态机强制）。

所以退款时，那笔抵扣处于哪个状态，取决于**分账有没有发生**：

| 退款时点 | 抵扣流水状态 | 资金池 | 难度 |
|---|---|---|---|
| 分账前（售后期内，大多数退款） | `PENDING` | **没动过** | 现成的 `reverse` 就能退 |
| 分账后 | `CONFIRMED` | 已记一笔 `MERCHANT_PAY` 出池 | 要连池子一起冲 |

### P2a · 分账前退款（建议马上做）

- 整单退款时（与 B6 退券同一个判据：主单下所有子单都不在履约中），逐子单调 `pointsPort.reverse`。
- 流水还是 `PENDING`，`reverse` 本来就是为这个状态写的；**池子一分没动过，退回也不碰池子**。
- 分账后的单 `reverse` 会静默返回（它只认 PENDING）—— 所以这一步上线后不会误动已确认的账，
  只是那部分暂时还退不回来（交给 P2b）。

测试：付款 → 整单退款（未分账）→ 抵扣的分回到账户、流水转 `REVERSED`。消融：不调 reverse → 红。

### P2b · 分账后退款（要与结算域一起定）

要新开 `refundConfirmed(subOrderNo)`，做三件事：流水 `CONFIRMED → REVERSED`、
分退回账户、**池子记一笔反向流水**（与 `MERCHANT_PAY` 对冲）。
难点不在代码，在账：分账回退时商家那部分钱已经从商家账户划回，
「平台替用户付给商家的那几块积分钱」要不要、以什么时点回到池子，要与结算的对账口径一致。
**开工前先与结算域对一次账**，确认 `reverseSplit` 里补差回退（`SUBSIDY_RETURN`）与积分这笔的关系。

### P2c · 收回已发放的购物积分（口径要你定）

发放时落的是 `pending_balance`，到期由 `activateDuePoints` 转正。整单退款时：

- **还在待生效期**：直接从 `pending_balance` 扣回、那条 EARN 流水作废 —— 无争议。
- **已经转正、而且被花掉了**：扣成负数？还是只扣到 0？还是不收回？

行业通行是「扣成负数，下次获得时先抵」。这一条**要你定**，定了才能写。

## P3 · 已取消 / 已退款：说清券与积分去向（原型 k10）

### 现状

B5 已经给了「接下来会发生什么」，但已取消 / 已退款的单只能说「这一单已经关闭」。
券回没回来、积分回没回来，端上无从知道 —— 编一句「已为你退回」是在说可能不成立的话。

### 方案

订单详情（只在详情视角）在 `CANCELLED` / `REFUNDED` 时附一个 `returned` 块，**从数据里查，不靠状态推**：

- `couponTitle`：这一单用过的券，现在状态是 `UNUSED` → 已退回；
- `pointsReturned`：这一单的 `REFUND` 流水分数之和（P2a 上线后才会有值）。

端上：有值才说「「满 30 减 5」已回到券包」「200 积分已退回」；没值就不说。

测试：取消用券的单 → 详情 `returned.couponTitle` 有值；没用券的单为空。

## P4 · 回补历史关单占掉的活动配额（一次性数据修复）

### 实测

线上「abc」活动：限量 100、`quota_used = 5`。今天那几单**全部是已取消**（没付款超时关掉的）。
B6-1 只管**以后**关掉的单，历史上已经占掉的不会自己退回来。

### 方案

写一个一次性脚本（不是迁移，不进 Flyway）：
对所有 `pmt_apply` 里属于**已关闭主单**的 ACTIVITY 行，按 B6-1 同一段逻辑退配额、作废那一行。
**先 dry-run 出清单给你看**（哪个活动退几份），你点头后再执行。

风险：动线上数据。所以只读 dry-run → 你确认 → 执行 → 回读 `quota_used`。

## P6 · 两条异常分支

1. **库存变少**：预览返回的 `maxQty` 小于当前数量时，**自动把数量压到上限**并提示「库存变少了，已调整为 N 件」——
   而不是等提交时报错。纯端上。
2. **选地址时就判超范围**：现在自送超范围是提交时才拦。
   改成选完地址立刻走一次预览，后端在预览里就返回「超出配送范围」的标记，端上当场给「换地址 / 换配送方式」。
   需要预览把现在只在建单时抛的 `OUT_OF_DELIVERY_RANGE` 改成**预览里给标记、建单时才拦**（与自提点「预览不拦、建单才拦」同一个口径）。

## P7 · 常驻 + 无门槛直减的风险提示（要你定做不做）

「abc」没有结束时间是因为它是**常驻活动**（`ALWAYS_ON`），设计如此，不是漏校验。
但「常驻 + 无门槛 + 每单直减 ¥10」合在一起，等于每一单都白送 10 块，直到限量用完。
建议 B 端保存这种组合时弹一次确认：「这个活动常驻、无门槛，每单减 ¥10，最多 100 单（共 ¥1000）」。
**不拦，只让商家看清楚他在做什么。**

## P8 · 顶栏「按 XX 小区供货」副文案

顶栏已经改成真实地名，而货仍按所在小区供。两者不一致是对的，但可能让人困惑。
**先观察**：有人问「为什么我在文体中心、看的是男生公寓那边的货」再补这行。
