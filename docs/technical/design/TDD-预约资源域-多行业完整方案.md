# 二 · 行业需求（压缩，各用各的行话）

| 行业 | 要什么 |
|---|---|
| 美业 | 指定技师占位；**90 分钟连占 N 格 × 双人 M 资源，要么全成要么全退**；改约先占后放；爽约释放+按规则罚；排班生成时段；请假影响面提示 |
| 餐饮 | 开台占桌（**不定时长的开放占用**）；转台先占后放；包间预定（时段占位→到店转开台） |
| 健身 | 团课场次：**一个时段 20 个名额**，会员各占 1；私教=指定教练占位 |
| 剧本杀 | 场次容量 8 人：**拼场各占 n 人、包场占满** |
| 家政/维修/搬家 | 上门时段占师傅/车辆档期，含路途缓冲 |
| 宠物 | 寄养**日期区间**占用（按晚）|
| 零售 | 预约自提时段（门店级，无资源）—— 现有旧径 |
| 餐饮+美业共同 | 排队叫号（无预约的等待队列）|

# 三 · 对齐与判定

## 3.1 头号判定：**占位聚合上收基座（BookingHold）**

美业 TDD 原方案：行业自己循环 `tryBook` 占 N 格 × M 资源、自己回退（`bty_appointment_slot` 做回退单位）。
再按三条合并判据审一次：

| 判据 | 原子占位 |
|---|---|
| 零售也要用？ | 要 —— 预约自提就是单格占位；APPOINTMENT 本来就是基座能力 |
| 换行业只换数据？ | 是 —— 美业 N×M、团课 1 格 n 名额、剧本杀拼场，全是同一个"占位单"的参数 |
| 被多域读？ | 是 —— 订单（确认/释放）、任务（TTL 过期）、报表 |

**⇒ 上收为基座聚合 `BookingHold`**：一次占位的全部明细（格 × 资源 × 份数）在基座内**原子成败**、
带 TTL、释放幂等。**"失败一半永久漏占名额"这种并发要害只在基座实现一次、测试一次。**
`bty_appointment_slot` 作废（§九）。

## 3.2 两种占用模式，同一张资源表

| 模式 | 语义 | 谁用 |
|---|---|---|
| **时段占位**（slot hold） | 按时间格计数占用，有始有终 | 预约、团课、场次、寄养 |
| **开放占用**（open occupancy） | 占住直到释放，**不知道何时结束** | 餐台开台、KTV 包厢、转台 |

强并成一种会两头难受：开台没有"格"可言，团课没有"独占"可言。
基座各给一套原语，资源表共用。

## 3.3 其余判定

| 事项 | 判定 |
|---|---|
| 资源 vs 工位 | **两个概念不合并**：`mch_resource` 管**时间占用**，`mch_station` 管**产出路由**（商品域 V2 已建）。一张按摩床是资源不是工位；热菜档口是工位不是资源 |
| 技师即资源 | `mch_resource.ref_no` 类型化引用（STAFF 行=staff_no，TABLE 行被 `fnb_table` 反向引用），**不用 attrs JSON 藏业务键** |
| 人员档案/技能 | 基座 E3（已定）：`mch_staff` 可无登录账号；`mch_staff_skill(staff_no, goods_no)` |
| 排班 | **规则→生成→调整→留痕全在基座**（E4 能力）；规则简化为 days_mask+时窗+粒度+容量，滚动生成（JobHandler）；**改规则只影响未来未占用时段**；`bty_schedule_log` 上收为 `mch_schedule_change_log` |
| 可约查询 | **基座读服务**：技能 ∩ 排班 ∩ 余量 ∩（时长+缓冲）一次算完 —— 四个输入全在基座，行业不必拼 |
| 预约单据/工单/爽约规则 | **留行业**（开单时机与业务规则是工作流的事）；基座只做 HELD 的 TTL 过期 |
| 订单集成 | `ord_sub_order` 加 `booking_hold_no NULL`；单时段旧径（slot_no）原样保留 |
| 日期区间（寄养） | 就是"连续天粒度的时段占位"—— 粒度=1440 分钟，**零新机制** |
| 排队叫号 | **记账不预建**；形状=开放占用的等待队列，业态入驻再施工 |

# 四 · 决策记录

| # | 决策 | 一行理由 |
|---|---|---|
| 1 | 占位上收基座 `BookingHold`（N 格 × M 资源 × n 份，原子、TTL、幂等释放） | 并发要害实现一次；三条合并判据全过 |
| 2 | 时段占位与开放占用是**两套原语**，资源表共用 | 开台无格、团课无独占，强并两头难受 |
| 3 | `mch_appointment_slot` 加 `resource_no NULL`（NULL=门店级旧行为）；`tryBook` 签名不动，内部改走 1 格 hold | 存量零变化；条件 UPDATE 手法一个字不改 |
| 4 | 时段格支持**份数**（`booked += n` 条件更新） | 团课 20 名额、剧本杀拼场包场同一机制 |
| 5 | 资源与工位两表两义，不合并 | 占用与路由是不同下游 |
| 6 | 排班全链（规则/生成/调整/留痕）归基座 | E4 是基座能力，log 跟着能力走 |
| 7 | 可约查询是基座读服务 | 四个输入（技能/排班/余量/时长缓冲）全在基座 |
| 8 | 预约单据留行业；基座无"预约"概念，只有"占位" | 开单时机（组合模型 W2）是工作流参数 |
| 9 | 释放幂等 = 明细行 `released_at` 先标记后减数 | 既有手法推广到 hold 明细 |
| 10 | 唯一例外仍只有"零时段=放行"一条 | 不许长第二条 |
| 11 | 端点从 3 扩到完整面（资源/人员/排班/时段/占位查询） | "复用内核不是接口"这个坑就此填掉 |
| 12 | 生成与过期用既有 `JobHandler`，不另造调度 | 一贯口径 |

# 六 · 不变量（B1–B10）

B1 `booked + n ≤ capacity` 只能条件 UPDATE；B2 hold 内全部明细原子成败，失败零残留；
B3 释放幂等（明细 `released_at` 先标记）；B4 HELD 有 TTL、CONFIRMED 永不过期；
B5 开放占用同一资源同时至多一个活动占用；B6 slot 与 resource 必须同店（越权闸两层都设）；
B7 零时段=放行（唯一例外）；B8 重生成绝不动已占用时段；
B9 `appointment_at` 只由时段推出，不信端上；B10 STAFF 资源恒容量 1，容量语义在时段格上。

# 七 · Service 概览（签名在规格书）

基座：`ResourceService`（资源 CRUD + 开放占用 occupy/release）· `StaffService`（档案+技能）·
`ScheduleService`（规则/生成/调整/留痕）· `BookingService`（hold/confirm/release/expire ——
**全系统唯一占位判定处**）· `AvailabilityQueryService`（可约查询，含按资源/按人）。
行业经 `CoreBookingApi / CoreResourceApi / CoreStaffApi` 进来；基座对行业只发事件（hold 过期、时段被调整影响预约）。

# 八 · 测试与闸门

单元：B1–B10 正反用例；**并发抢最后一格只成一个**；hold 第 k 单元失败前 k−1 全回退；
双人 90 分钟 = 4 格 × 2 资源 = 8 单元原子；团课 20 名额扣到 0 再拒；开放占用抢同一桌只成一个。
场景：美业约-改约-爽约链、餐饮包间预定转开台、团课报名满员、零售自提时段旧径回归。
闸门：`-Pcore-only` 全绿；撤掉条件 UPDATE 或回退逻辑，对应用例必须变红且点名正确；
`AppointmentSlotFlowTest` 原样通过；新端点登记 perm map + 重跑生成器。
