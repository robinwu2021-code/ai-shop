## 四、要解决的问题，按重要性

1. **发布打断任务**（真正的驱动）。合并进业务实例的话，每次发布重启都会打断正在跑的任务。
   9 个有幂等口径的能靠下一轮自愈，**4 个不能**。将来的日结、对账通常也不幂等——
   跑一半留下的是半张账，**而半张账不报错**。
2. **该跑的没跑，没人知道**。`sys_job_run` 记着，但没有任何人看得见。
3. **停不掉、也重启不了**。某个任务在生产上闹事时，唯一的手段是改配置重启整个实例。

## 五、方案

### 5.1 一个必须先想清楚的取舍：`@Scheduled` 撑不起「运行时可配」

`@Scheduled(cron = "${...}")` 的 cron 是**启动时读一次**的常量。
要做到「运营页面改了 cron / 关掉某个任务，**不重启**就生效」，
就不能再用注解，得换成**注册表驱动**：

```
JobRegistry ──持有──> ThreadPoolTaskScheduler
     │                      │
     └─ 从 sys_job_def 读配置，schedule(runnable, CronTrigger)
        返回 ScheduledFuture，存起来
        关任务 = future.cancel()；改 cron = cancel + 重新 schedule
```

**这是本方案里唯一有分量的改造**，15 个任务都要从「注解声明」改成「注册进表」。
好处是开关、改 cron、立即触发、重启单个任务这四件事**一次全解决**，
而且它们本来就是同一个机制的四个动作。

> 不做这一步的话，「可配置」只能退化成「改配置文件 + 重启」，
> 那与今天的差别只是把 yaml 换成了数据库，**而重启正是我们要避免的那件事**。

### 5.2 数据模型（两张新表 + 一张既有）

| 表 | 用途 | 说明 |
|---|---|---|
| `sys_job_def` **新** | 任务定义与配置 | `job_name`(唯一) / `display_name` / `cron` / `enabled` / `lock_at_most_sec` / `description` / `owner_module`。**代码启动时把全部任务 upsert 进来**（代码是源头，表是可调的覆盖层）——新加任务不用写迁移 |
| `sys_job_run` 既有 | **当前状态**（每任务一行） | 已有 `last_run_at`/`duration_ms`/`status`/`detail`/`error`/`consecutive_failures`/`run_count`，够用，不改 |
| `sys_job_log` **新** | **执行日志**（每次一行） | `job_name` / `started_at` / `duration_ms` / `status` / `detail` / `error` / `trigger_type`(CRON/MANUAL) / `instance`。**按天分区或定期清理**——5 秒一次的任务一天 17280 行，两个这样的任务一年 1200 万行 |

> ⚠️ `sys_job_log` 的保留策略必须和表一起定，否则它自己会长成这个库里最大的表。
> 建议：秒级任务只在**状态变化或失败**时落日志，其余只更新 `sys_job_run`；
> 分钟级及以上每次都落；统一保留 30 天，由一个新任务清理（它自己也在清单里）。

### 5.3 运营端

| 接口 | 动作 |
|---|---|
| `GET /ops/jobs` | 列表：名称、cron、开关、最后一次跑的时间/耗时/结果、连续失败数、累计轮次 |
| `GET /ops/jobs/{name}/logs` | 执行日志，按时间倒序分页 |
| `POST /ops/jobs/{name}/enable` · `/disable` | 开关，**立即生效不重启** |
| `POST /ops/jobs/{name}/cron` | 改 cron，立即生效 |
| `POST /ops/jobs/{name}/trigger` | 立即跑一次（`trigger_type=MANUAL`），**仍走 ShedLock**，正在跑时拒绝 |

权限：新增 `system:job:read` / `system:job:manage`。
**读写分开**——看运行情况的人（排查问题）比能关掉任务的人多得多。

> ⚠️ 运营端菜单在库里（`sys_function` / `sys_function_point`），**只改 `nav.ts` 菜单不会出现**，
> 要跑生成器落迁移。这个坑本仓库踩过。

### 5.4 独立部署

- 新模块 `shop-job`：只装**调度器 + 注册表**，触发器留在各域，业务仍在各域
- 打成独立 jar，同机第二个 systemd 单元，`SPRING_PROFILES_ACTIVE=worker`
- **ShedLock 已接好，业务实例与 worker 同时开着也不会重复执行** —— 迁移期可以两边都开
- 触发方式**先保持进程内调用**（12/14 已是薄触发器，改动最小）。
  改 HTTP/RPC 是后一步，它换来「业务发布完全不影响 worker」，
  但也把「被打断」换成了「业务重启期间调用失败」——见 5.5

### 5.5 「一定执行」需要补偿层，独立部署不提供

独立解决的是**不被打断**，不是**一定执行**。要真做到后者还缺：

- 漏跑检测：到点没跑成的，记下来
- 补跑：重试到成功；跨天的要能补昨天那一轮
- 日结/对账专用：**按业务日期而不是按时钟**驱动（「2026-08-25 这一天的账结了吗」，
  而不是「昨晚 3 点那次跑了吗」）——这一条是日结对账与其它任务的根本差别

`sys_job_run.consecutive_failures` 是种子，但没有补跑。**日结对账真正需要的是这一层**，
它与独立不独立正交，建议单独排期。

待处理媒体资产      0（238 个全 ACTIVE）

**在有数据的时候第一次跑一个从没跑过的任务**，是本仓库今天刚踩过的形态。

### 关于 native（第 7 步）

GraalVM 的两个收益是**启动毫秒级**与**低常驻**。
任务进程是常驻的，启动优势对它**无效**；常驻从 ~900MB 降到 ~200MB，
在只有一个 worker 实例、机器闲着 5.8GB 时不构成理由。

它值得做的那天是：任务被拆成按需拉起的短生命周期进程，或者要在一台机器上跑多个 worker。
届时 `mybatis-plus` 的反射问题若已随 Spring Data AOT 迁移解决，代价会低得多。
**顺序不能颠倒**：独立部署的理由是发布隔离，native 是独立之后顺手拿到的收益。

# 附：定稿的表结构、代码结构与 API（2026-08-26）

三个待拍板的按建议定了：
**① 秒级任务只在状态变化或失败时落日志；② 手动触发只给分钟级以上；③ 先做开关与页面，再开 worker。**

## A. 表结构（`V260__job_def_and_log.sql`，已落地）

三张表各答一个问题，**不要合并**：

| 表 | 回答 | 形态 |
|---|---|---|
| `sys_job_def` **新** | 这个任务**该怎么跑** | 配置，每任务一行，运营可改 |
| `sys_job_run` 既有 V95 | 它**现在是什么状态** | 当前状态，每任务一行，被覆盖 |
| `sys_job_log` **新** | 它**每一次跑了什么** | 执行历史，每次一行，追加 |

两个刻意的决定：

- **`sys_job_def` 不写种子。** 任务定义的源头在代码里，启动时 upsert。
  写死种子的代价是「以后每加一个任务都要写一支迁移」，而忘了写的那个会**静默不注册**——
  表里没有它，注册表就不调度它，且没有任何地方报错。
- **upsert 只补不覆盖。** 已存在的行只更新 `display_name`/`description`/`owner_module`
  这些纯展示字段，**不动 `cron` 与 `enabled`**——那两个是运营调过的，
  每次发布把它们冲回默认值等于运营的调整全部作废，而他不会收到任何提示。

日志量的两道闸（否则 `sys_job_log` 会长成这库里最大的表）：
`log_every_run=0` 的秒级任务只在**由成功转失败 / 由失败转成功 / 失败**时落一行；
统一保留 30 天，由新增的 `job-log-purge` 任务清理（它自己也进任务清单）。

## B. 代码结构

**原则：模块装引擎，触发器留在各自的域，独立的是部署单元不是编译单元。**

把 15 个触发器搬进一个模块，会让那个模块反向依赖 6 个域——比现在更糟。
而它们本来就已经是薄触发器（12/14 只持有 Service/Port），留在原地即可。

```
shop-base/ai/neargo/shop/job/          共享契约，谁都能引
  JobSupport.java        既有 —— 跑一轮 + 记 sys_job_run。**扩展**：按 log_every_run 决定要不要落 sys_job_log
  SysJobRun.java         既有
  SysJobDef.java         新 —— 配置实体
  SysJobLog.java         新 —— 日志实体
  JobDefinition.java     新 —— 一个任务的声明（见下）
  JobRegistrar.java      新 —— SPI：各域实现它，交出自己的 JobDefinition 列表

<各域模块>/**/job/*.java   14 个触发器：从 @Scheduled 改成实现 JobRegistrar。**位置不动**

shop-job/                 新模块 —— worker 的可部署单元（角色同 shop-app）
  JobApplication.java    Spring Boot 主类，profile=worker
  JobRegistry.java       注册表 + ThreadPoolTaskScheduler，持有 ScheduledFuture
  JobConfigWatcher.java  轮询 sys_job_def，把运营的改动应用到注册表

shop-app/**/portal/ops/
  OpsJobController.java  新 —— 运营端接口。**只读写数据库，不与 worker 通信**
```

### B1. `JobDefinition`——一个任务的全部声明

```java
record JobDefinition(
    String  name,            // 与 @SchedulerLock、sys_job_run.job_name 一致，三表连接键
    String  displayName,     // 「套餐到期扫描」
    String  ownerModule,     // shop-settle
    String  defaultCron,     // 首次 upsert 用；之后以 sys_job_def.cron 为准
    int     lockAtMostSec,
    boolean manualTrigger,   // 秒级任务给 false
    boolean logEveryRun,     // 秒级任务给 false
    String  description,     // 运营页面直接显示
    Runnable body)           // 就是今天 @Scheduled 方法体里那一句 jobs.run(...)
```

### B2. 为什么必须换掉 `@Scheduled`

`@Scheduled(cron = "${...}")` 的 cron 是**启动时读一次的常量**。
要做到「页面上改了、不重启就生效」，只能换成注册表驱动：

```
JobRegistry
  ├─ 启动：收集全部 JobRegistrar → upsert sys_job_def → 按 enabled/cron 逐个 schedule
  ├─ 持有 Map<String, ScheduledFuture>
  ├─ disable(name)  = future.cancel(false) —— **取消调度，不是让它空跑一趟**
  ├─ enable(name)   = 重新 schedule
  ├─ reschedule(name, cron) = cancel + schedule
  └─ triggerNow(name) = 直接跑一次，trigger_type=MANUAL，**仍走 ShedLock**
```

开关、改 cron、立即触发、重启单个任务——**这四件事是同一个机制的四个动作**，
一次全解决。不换的话「可配置」只能退化成「改配置 + 重启」，而重启正是要避免的那件事。

### B3. 运营端与 worker 之间**不建通信**

这是本方案里最省事也最稳的一条：

```
运营页面 ──改配置──> shop-app ──写──> sys_job_def
                                        │
                          shop-job 每 30 秒轮询 ──> 应用到 JobRegistry
```

不做 RPC/MQ 的三个理由：
- **不需要实时。** 关一个任务晚 30 秒生效，与「立刻」在运维上没有区别
- **少一个故障面。** 有 RPC 就有「worker 连不上」这种新失败，而它恰恰会在发布时发生——
  那正是我们要隔离的时刻
- **worker 挂了也不影响运营页面。** 页面读的是库，`sys_job_run` 会显示
  「最后一次跑的时间是 2 小时前」，**这本身就是最有用的告警**

代价：手动触发也要经轮询，最长 30 秒后才动。可接受——手动触发只给分钟级以上的任务。

## C. API

权限**读写分开**：看运行情况的人（排查）比能关任务的人多得多。
新增 `system:job:read` / `system:job:manage`。

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/ops/jobs` | read | 列表。合并 `sys_job_def` + `sys_job_run`：名称、模块、cron、开关、最后一次时间/耗时/结果/detail、连续失败数、累计轮次 |
| GET | `/ops/jobs/{name}` | read | 单个详情 |
| GET | `/ops/jobs/{name}/logs` | read | 执行日志，`started_at` 倒序分页；可按 `status` 筛 |
| POST | `/ops/jobs/{name}/enable` | manage | 开。写 `enabled=1`，worker 轮询后生效 |
| POST | `/ops/jobs/{name}/disable` | manage | 关。**取消调度**，不是空跑 |
| PUT | `/ops/jobs/{name}/cron` | manage | 改 cron。**先校验表达式再落库**——落一个非法 cron 进去，worker 会在下一轮轮询时注册失败，而运营看到的是「改成功了」 |
| POST | `/ops/jobs/{name}/trigger` | manage | 立即跑一次。`manual_trigger=0` 的任务返回 403 而不是静默忽略 |

四条约束：

1. **每个写操作都记 `updated_by`**——「谁把这个任务关了」必须查得到
2. **`cron` 写入前用 `CronExpression.parse` 校验**，非法直接 400
3. **`trigger` 走 ShedLock**，正在跑时返回「已在运行」，不排队、不并发
4. **端点要登记进 `OpsEndpointPermTest`**（若有）与运营端菜单——
   ⚠️ 菜单在库里（`sys_function` / `sys_function_point`），**只改 `nav.ts` 不会出现**，要跑生成器落迁移
