## 一、结论：符合需求吗

**大体符合，且对齐得比预想的好** —— 29 个需求条目里 **28 个在菜单上有落点**，
菜单项自带的 `matrix` 编号与需求清单**几乎一一对应**。这说明前端不是照着感觉做的。

但**「有落点」不等于「能用」**：

| 口径 | 数 |
|---|---:|
| 需求条目 | 29 |
| 菜单上有落点 | 28 |
| **后端全通** | **18** |
| 🟡 部分通 | 2 |
| ❌ **后端一条都没有** | **7** |
| 需求有、菜单没有 | 1（`P-3.4`） |
| 菜单有、需求清单没有 | 1（`P-8.1`） |

> 也就是说：**需求 → 界面这一段是齐的，界面 → 后端这一段缺了四分之一**。
> 这与今晚反复撞到的形状一致 —— 断裂点从来不在需求和 UI 之间。

## 二、两处编号对不上（都不是错，但都要处理）

### 2.1 `P-3.4 规格模板维护` —— 需求写了「❌ 缺」，菜单里真的没有

需求清单原文：

> **规格模板维护** `P-3.4`（待建）｜❌ **缺**：B-4.4 商家能选平台模板，
> 但平台端没有维护入口——**模板是死的**

**这是三方一致的诚实缺口**：需求承认缺、菜单没造假入口、后端也没有。
但「模板是死的」意味着商家在 B 端选到的永远是那几个初始模板 ——
`/biz/spec-templates` 有 2 个端点在跑，**它读的数据没有人能维护**。

> ⚠️ 这是**唯一一处「B 端在用、平台端无法维护」**的主数据。

### 2.2 `P-8.1` 菜单有、需求清单没有编号

菜单项「商家团（审核与监控）」标着 `matrix: "P-8.1"`，
而需求清单里 8.x 只有两行、都编成了 `P-8.2`（「需求单池与指派」与「改价留痕与毁约」）。

看内容：需求清单的 8.x 讲的全是**求团**，而菜单那一项是**商家团**——
两件不同的事（ADR-005 里商家团与邻里求团是两条链路）。
**结论：需求清单漏了「商家团审核」这一条**，而不是菜单编错。

## 三、七个「后端一条都没有」

这七个不是新发现（`UNBUILT_DOMAINS` 早已登记），但**放进需求对齐表之后能看出优先级**：

| 需求 | 菜单项 | 需求状态 | 判断 |
|---|--:|---|---|
| **P-5.1 履约调度** | 4 | ✅ 应做 | **最该先补**：需求标 ✅、四个菜单项、且它是履约闭环的平台侧 |
| **P-16.2 风控** | 3 | ✅ 应做 | 高危：拦截/黑名单一直没有落点 |
| **P-10.1 门店主页与获客** | 4 | ✅ 应做 | 一期主获客路径（矩阵 L2-10 标 P0），而平台侧零实现 |
| **P-9.1 归因链路** | 2 | ✅ 应做 | 前置是**埋点**，不是后端 CRUD |
| **P-9.2 邀请有礼** | 1 | ✅ 应做 | 同上 |
| P-5.2 第三方运力 | 3 | 🔜 二期 | 与排期一致，不算缺口 |
| P-12.2 提现/发票 | 2 | 🔜 二期 | 同上，但**提现涉及真实资金**，做的时候要配资金流程 |

**前五个的需求状态都是「✅ 应做」，而后端零实现** —— 这五条是真正的待办；
后两个标着二期，是排期而非缺口。

## 五、建议顺序

```
S6 规格模板（小，且 B 端在等）
   ↓
S1 履约调度（需求 ✅、四个菜单项、无前置）
   ↓
W2 + W3 + R1/R2/R3（收口，半天）
   ↓
G1 + G2 守卫
   ↓
S4 埋点（要先定方案）→ S2 风控 / S3 获客 / S5 邀请有礼
   ↓
S7 财务提现（要先定资金流程）
```

**S6 排第一不是因为它大**，而是因为它是唯一一处
「**B 端正在用、而平台端无法维护**」的数据 —— 那种缺口不会报错，
只会让商家永远看到同样几个模板。
