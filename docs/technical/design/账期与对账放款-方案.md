> 上游：[资金链路-三方对齐](./资金链路-三方对齐.md) · [收款与分账-总体逻辑](./收款与分账-总体逻辑.md) ·
> [对账差异-方案](./对账差异-方案.md) · [ADR-002 结算走微信支付分账](../ADR/ADR-002-结算走微信支付分账.md)
> 回答的问题：**账期怎么定 · 对账通过之前钱在哪 · 商家把钱提走之后买家退款怎么办**

---

## L1 · 一句话

**账期不是「平台先把钱拿着」，是「通道那边先冻着」。**
平台发的只是「什么时候解冻多少」的指令，从头到尾没有支配权——
这是它与二清的分界线，也是整套设计不能越的那条。

在这个前提下，「对账通过才到商家账户」是可实现的：
对账不通过就**不发解冻指令**，钱留在冻结态，而不是留在平台账上。

---

## L2 · 一、账期模型：三个时点 + 一个硬窗口

```
T0 成交        T1 履约完成      T2 可结算        T3 应结日          Tmax 冻结到期
 │                │              │                │                   │
 ├── 冻结 ────────┼──────────────┼────────────────┼───────────────────┤
 │                │  售后期 N 天  │   账期规则      │  ← 安全余量 →      │
 生成结算单                      无进行中售后      对账通过才发指令      资金自动解冻
```

| 时点 | 定义 | 来源 |
|---|---|---|
| **T0** 成交 | 支付成功 | 已有：`accrued_at` |
| **T1** 履约完成 | 自提已核销 / 快递已确认收货 / 服务已完成 | 已有：子单履约状态 |
| **T2** 可结算 | `T1 + 售后期 N 天`，且**无进行中售后** | 🆕 `stl_bill.settleable_at` |
| **T3** 应结日 | 按账期规则从 T2 推出 | 🆕 `stl_settle_batch.due_at` |
| **Tmax** 冻结到期 | `T0 + 通道冻结窗口` | 通道规则，**外部约束** |

### Tmax 是硬约束，不是参考值

微信分账的冻结窗口有上限（收付通与普通分账口径不同，**待通道书面确认**）。
超期资金**自动解冻回商家**，而佣金还没收——这就是《收款与分账-总体逻辑》里的
`FROZEN_BACK`，文档说它「不是异常分支，是必然会发生的分支」，而**今天代码里这个状态不存在**。

所以账期规则必须满足：

```
T3 + 重试余量 + 人工处置余量  <  Tmax − 安全余量
```

**账期能定多长，上限由通道给，不由我们定。**
拿不到那个数就不能上账期——猜一个值，第一次撞上限的是真实商家的真实货款。

### 账期规则（`sys_pay_channel.settle_cycle` 已有列，今天没有消费者）

| 规则 | T3 = | 适合 |
|---|---|---|
| `T+1` | T2 次日 | 默认；现金流最友好 |
| `T+N` | T2 + N 日 | 风险较高的类目 |
| `WEEKLY` | T2 所在自然周的次周首日 | 批量处理，差异集中看 |
| `SEMI_MONTHLY` | 1–15 日 → 16 日；16–月末 → 次月 1 日 | 与开票周期对齐 |
| `MONTHLY` | 次月首日 | ⚠️ **最容易撞 Tmax**，用前先算 |

> 账期是**主体 × 通道**属性（`mch_payment_merchant.settle_cycle`），通道级的 `sys_pay_channel.settle_cycle` 是它的**上限**：
> 通道只支持 T+1 的话，主体配成月结也只能按 T+1 走。两处不一致时取更短的那个——
> 反过来会让指令在通道侧被拒，而拒绝理由不会说「因为你配了月结」。

## L2 · 二、三道对账门：钱要过三道才走

「对账通过后才能到商家账户」落成三道门，**逐道收窄**：

| 门 | 判什么 | 数据源 | 不过怎么办 |
|---|---|---|---|
| **门 1** 单据自查 | 恒等式成立：`gross = 佣金 + 服务费 + 积分费 + 通道手续费 + 实得` | 本方单据 | 该单挂起，记差异 |
| **门 2** 收款对账 | 这笔钱通道那边**确实收到了** | `stl_payment` × 通道账单 | 该单挂起 |
| **门 3** 批次对账 | 本批次的差异**全部已处置** | `stl_recon_diff` | **整批**不放行 |

**门 3 是批次级的，前两道是单据级的。** 这个分级是有意的：

- 单据级差异（某一单对不上）不该卡住同批的其他单——否则一笔小差异冻结全体商家的货款；
- 批次级不通过（比如通道账单还没下载下来）**必须卡住整批**——
  这时我们对这一批的任何一笔都没有把握，逐单放行等于在没对账的情况下放款。

> 今天的实现里**三道门一道都没有**：`executeSplit` 生产零调用点，
> 而它本身也不检查任何对账状态。这份方案的主体工作量就在这三道门。

### 批次：`stl_settle_batch`（🆕）

没有批次对象的话，「这个账期对完了没有」无处安放。

```
批次状态机
DRAFT ──▶ COLLECTED ──▶ RECONCILING ──▶ RECONCILED ──▶ RELEASED
  │           │              │              │
  │           │              └──▶ BLOCKED（有未处置差异，人工介入后回 RECONCILING）
  │           └──▶ 收单完成，本批不再接新单
  └──▶ 按 (主体, 账期, 通道) 开批
```

| 状态 | 含义 | 谁推进 |
|---|---|---|
| `DRAFT` | 开批，正在收单 | 系统（T2 到达的单入批） |
| `COLLECTED` | 截止，本批锁定 | 系统（T3 到达） |
| `RECONCILING` | 三道门在跑 | 系统 |
| `BLOCKED` | 有未处置差异 | 系统判定，**运营处置** |
| `RECONCILED` | 全过，可放行 | 系统 |
| `RELEASED` | 已发解冻/分账指令 | 系统 |

`RELEASED` 之后每张单各走各的 `SPLITTING → SPLIT → SPLIT_CONFIRMED`——
**批次管「能不能放」，单据管「放得成不成」**，两件事不要塞进一个状态机。

## L2 · 三、退款：按钱在哪分四个时区

这是整份方案里唯一真正棘手的部分。**判据是「钱在哪」，不是「过了多久」。**

| 时区 | 钱在哪 | 退款怎么走 | 平台垫资 | 今天有没有 |
|---|---|---|---|---|
| **Z1** 冻结中（账期内） | 商家二级户 · 冻结 | 原路退，直接从冻结资金扣 | ❌ 不垫 | 部分（`refund`） |
| **Z2** 指令已发未确认 | 通道处理中 | 先 `reverseSplit` 再退 | ❌ 不垫 | 有代码，无触发 |
| **Z3** 已解冻 · 商家未提走 | 商家可用余额 | 分账回退（通道有时限） | ❌ 不垫 | 有代码，无触发 |
| **Z4** 已解冻 · **商家已提走** | 商家银行卡 | **回退必然失败** | ⚠️ **这里** | ❌ 无 |

### Z4 是真缺口，而且它一定会发生

商家在通道侧提现是**他自己的动作**，我们既看不见也拦不住（ADR-002 的模型下，
平台对那笔钱本来就没有支配权——这正是不二清的代价）。
所以 Z4 不是「设计得好就不会发生」，是**发生频率可以压低，但不能压到零**。

**事前压低（四条，按性价比排序）：**

1. **账期本身就是最有效的防线。** 售后期设得比退款高发期长，
   绝大多数退款落在 Z1，一分钱风险都没有。这是《收款与分账-总体逻辑》§4.2
   已经拍过板的取舍：**宁可让商家晚拿到钱，也不要写一整套补偿链路**。
2. **`split_reversible = 0` 的商家不许进入 Z3。**
   这一列已经在 `mch_payment_merchant` 上（进件回执写入），
   意思是「接收方还没开启分账回退授权」。没开就放款，Z3 也会失败，
   等于把一个本可以避免的 Z4 提前造出来。
3. **高风险主体缩短账期、提高保证金。** 准入矩阵（S 轴）已有，接上即可。
4. **单批放款额度上限。** 一次放行的总额不超过「保证金 + 在途货款」的某个倍数。

**事后追偿（三层，按顺序，不跳级）：**

```
Z4 发生 ──▶ ① 记欠款（自动）──▶ ② 后续货款抵扣（自动）──▶ ③ 仍不清则停止放款
            mch_debt 🆕          从下一批实得里扣            批次 BLOCKED
                │
                └──▶ 保证金抵扣（**人工**，运营在后台按）
                     mch_deposit，已有表与 DEDUCT 流水
```

> ⚠️ **2026-08-30 修正**：本节初稿写的是「① 保证金扣划 → ② 货款抵扣」，
> 而 [ADR-022 §3.3](../ADR/ADR-022-资金风控的拦截点与误伤代价.md) 定的是
> **扣划保证金必须人工**（动商家的钱，且未经同意扣款的合规边界未定）。
> 两处打架，以 ADR 为准 —— 顺序因此改成「先自动记欠款，保证金是人工偿还的一种方式」。
> 这样**自动的那条链路上一分钱都不动商家的本金**。

| 层 | 动作 | 已有 | 缺 |
|---|---|---|---|
| 保证金 | 从 `mch_deposit` 扣划抵欠款，落 `mch_deposit_txn(DEDUCT)` | ✅ 表与流水类型都在 | **人工入口**（不自动，见上方修正） |
| ① | 记入商家**欠款账户**，从后续批次的实得里逐笔抵扣 | ✅ 2026-08-30 落地 | 触发方（Z4 与批次放行）还没建 |
| ② | 该主体的新批次一律不放行，转人工追偿 | ❌ | 批次放行时判欠款 |

> **欠款不能塞进保证金表。** 保证金是商家的钱（平台代管，将来要退还），
> 欠款是商家欠平台的钱——两者方向相反。合在一张表上用正负号表达的话，
> 「应退还多少保证金」这个问题就永远算不清了，而那是要退店时结账的数。

### 一条不做的：**平台垫付**

Z4 追不回来时，不由平台先垫给买家再去追商家。
垫付会让「这笔钱到底是谁的」在账上彻底失去边界，而且它会变成常态——
第一次垫付之后，追偿的紧迫性就消失了。

买家侧的处理是**售后规则问题不是资金问题**：
Z4 的退款要走平台的售后裁决（可能动用保证金先行赔付），
而那条链路已经存在（`refundSplitPending` / 售后判责）。

## L3 · 四、对账逻辑：四条轴 × 两侧 × 三种差异

现有的 `ReconAxis` 抽象已经把四条轴分开了，这一节只补**判据与处置**。

### 每条轴今天能查到什么

| 轴 | A 侧（我方自查） | B 侧（与对方账单比对） | 今天 |
|---|---|---|---|
| **收款** | 我方有单而无回调 | 通道账单 × `stl_payment` | A 有；B **缺通道账单下载** |
| **分账** | 已发指令超时未确认 | 通道分账查询 × `stl_split_log` | A 有；B 缺 |
| **出款** | 已付款无流水号 / 流水号重复 | 银行流水 × `paymentRef` | A 有；B 缺（无银行接入） |
| **积分池** | 恒等式失衡（不逐笔） | — | A 有 |

> **B 侧全缺，而这不是可以「以后再说」的。**
> A 侧只能回答「我方内部一致吗」，回答不了「对方到底做了什么」。
> 门 2 与门 3 需要的正是 B 侧——**没有 B 侧，「对账通过」是一句自证的话。**
>
> 过渡期的诚实做法：`coverage()` 已经在做的那件事——
> **把查不了的那一类写在页面上**。批次放行时也要如实标注
> 「本批仅通过 A 侧自查」，而不是显示一个纯粹的「已对账」。

### 三种差异 × 处置

| 差异 | 含义 | 默认处置 | 谁定 |
|---|---|---|---|
| `CHANNEL_ONLY` | 通道有、我方无 | **查单补记**：用户付了钱我方没收到回调 | 系统查单 → 补记 |
| `PLATFORM_ONLY` | 我方有、通道无 | **关单**：我方发起失败 | 系统查单 → 关单 |
| `AMOUNT_DIFF` | 两边金额不等 | **必须人工**——金额差不存在安全的自动处置 | 运营 |

三种类型已在 `StlReconDiff` 上；缺的是**自动处置的那两条**——
今天全部落到人工，而 `CHANNEL_ONLY` / `PLATFORM_ONLY` 靠一次查单就能定性。

### 线下单必须排除

`OFFLINE_SETTLED` 的单**从不出现在任何通道流水里**，
混进对账就是永久的无解差异，而且它的量会随线下生意增长。
（这条 PRD 的 AC-5 已经写明，现有实现已做对，新增的批次对账要照做。）

## L3 · 五、数据模型改动

| 对象 | 改动 | 理由 |
|---|---|---|
| `stl_bill` | 🆕 `settleable_at` | T2。今天没有任何地方记录「这单什么时候可以结」 |
| `stl_bill` | 🆕 `batch_no` | 归属批次；没有它，「这单卡在哪一批」查不出来 |
| `stl_settle_batch` | 🆕 表 | 账期批次与它的对账状态 |
| `mch_payment_merchant` | 🆕 `settle_cycle` | 主体×通道账期。**不落 `mch_entity`** —— 后者留在主库，放那儿等于每次截批都跨库读配置 |
| `mch_debt` / `mch_debt_txn` | 🆕 表 | 商家欠款与流水。**不并进保证金表** |
| `stl_bill.status` | ✅ 不加状态 | 「对账没过」是批次的状态，不是钱的状态。混进来会让 `status` 同时表达两件事 |

**一处需要迁移但没有新表的**：`FROZEN_BACK`。
它是 `stl_bill.status` 的一个新取值——冻结窗口到期、资金已自动解冻、佣金收不到。
它必须与分账下发**同批上线**，不能留到「以后补」：
分账一接通，这个分支就开始有流量，而那时没有任何地方会报警。

## L4 · 七、待确认（不确认不能上线）

1. **通道冻结窗口到底多长？**（Tmax）拿不到这个数，账期上限就是猜的。
2. **分账回退的时限与条件**——Z3 能不能走通全看它。
3. **默认账期定多少？** 与售后期 N 一起定；两者相加必须远小于 Tmax。
4. **保证金扣划要不要商家确认？** 法务问题：未经同意从保证金扣款的合规边界。
5. **欠款追不回时的止损线**——欠多少停止合作、走什么流程。
6. **过渡期是否接受「仅 A 侧对账」放款？** 若接受，页面必须如实标注，
   不能显示成「已对账」。这是产品与风控的联合决定。
