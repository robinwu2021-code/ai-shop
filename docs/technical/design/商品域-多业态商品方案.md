## 2 由场景归纳出的需求轴

把上面的场景按「它要求商品模型表达什么」归类，得到 6 条相互独立的轴。方案就是给每条轴定一个唯一的表达位置。

| 轴 | 问的是什么 | 涉及场景 |
|---|---|---|
| A 交易形态 | 买完以后怎么交付：发货或自提、到店服务、核销、发卡 | R11、R17、B1、B4、B8、X4 |
| B 计量与价格 | 按件还是按重；默认价、门店价、目录价、市场价 | R5、R8、R9、R12、F3、F10 |
| C 可售与供给 | 上没上架、什么时段卖、还能卖几份 | R8、R10、R13、R18、F2、F9、B3 |
| D 组成与选配 | SKU 怎么生成；套餐、加料、口味、附加项 | R4、F5、F6、F7、B9 |
| E 交付要求与执行定义 | 交付要用什么角色、资源或工位；服务的时长、缓冲、步骤 | F11、B2、B4 |
| F 治理与版本 | 审核、修订、回滚、平台下架、渠道 | R6、R7、R21、F4、F8 |

## 3 方案

### 3.1 原则

1. **一个主档**：服务、称重、虚拟、卡、菜品都是 `prd_goods` + `prd_sku`，不为某类商品另建主档。
2. **形态决定交易流程，能力决定附加行为**：
   - 形态（轴 A）只有少数几种，决定下单、履约、售后走哪条路；
   - 称重、预售、限量、套餐、选配、交付要求是能力，任何形态都可以组合（称重菜、称重生鲜共用称重能力）。
3. **多个模块要读、要参与计算的，用列；只有一个行业懂的，用行业扩展**。行业扩展的结构由行业模块定义并校验，商品领域只负责存、留修订、结转；写入经商品端口，美业执行定义就是这种做法。
4. **「怎么做」不进商品**：工位路由运行态、出品、工单、服务任务、配方耗用留在行业库或进销存，只引用 `goods_no`、`sku_no`、修订号。
5. **一个概念只建一套**：同一业务概念有多套建模的，收敛到定稿表（§3.6）。

### 3.2 模型分层

| 层 | 表（定稿 05） | 管什么 |
|---|---|---|
| 主档 | `prd_goods`、`prd_sku`、`prd_sku_barcode`、`prd_standard_goods`、`prd_category` | 标题图文、类目、形态、能力列、行业扩展；SKU 规格取值、默认价、税类 |
| 规格 | `prd_spec_dim`、`prd_spec_value`、`prd_spec_usage` | 维度用途：`SALE` 生成 SKU、`PROP` 只描述、`OPTION` 下单选配；选配值可挂一个收费 SKU（加料） |
| 组成 | `prd_bundle_group`、`prd_bundle_choice` | 套餐分组与可选项、差价、组合加料用量 |
| 服务定义（**新增**） | `prd_service_definition` | 服务的时长、前后缓冲、步骤、注意事项；按商品写默认行，按 SKU 写覆盖行；**有自己的版本号**，与商品修订脱钩 |
| 交付要求 | `prd_fulfillment_requirement` | 执行角色、资源、工位，数量、顺序、偏移、时长、分配方式；可再按 `sku_no`、`store_no` 细分。服务的交付要求按服务定义版本记，其余按商品修订号记 |
| 门店与目录 | `prd_store_sku`、`prd_store_catalog`、`prd_catalog_item`、`prd_catalog_item_sku`、`prd_catalog_schedule`、`prd_store_category` | 门店价与在售；多份目录（草稿、已发布、上一版）、条目、目录价、按下单来源区分、周时段与例外 |
| 供给 | `prd_sellable_rule`、`prd_sales_quota`、`prd_stock_lock` | 可售量规则；估清、限量、预订限量；下单锁量 |
| 治理与版本 | `prd_goods_revision`（+ 审核服务） | 草稿、送审、上线、被替换、驳回；免审直通 |
| 交易侧引用 | `ord_item.industry_ext`、`ord_appointment_item.definition_version_no` | 下单时冻结的行业快照；预约项目行记服务定义版本号 |

### 3.3 分类码统一（轴 A、D）

| 现有 | 取值 | 处理 |
|---|---|---|
| `prd_goods.type`（形态） | NORMAL、FRESH、SERVICE、VIRTUAL、CARD | **作为唯一的形态码** |
| `prd_category.template`（类目模板） | STANDARD、FRESH、SERVICE、VIRTUAL、VOUCHER | 只决定录入表单，不另立形态；STANDARD↔NORMAL、VOUCHER↔CARD 的对应写进常量 |
| `prd_sku.sku_kind` | STANDARD、BUNDLE、MODIFIER、CARD | **作为唯一的 SKU 种类** |
| 餐饮 `dishKind` | SINGLE、BUNDLE、ADDON | 退役，并入 `sku_kind`（SINGLE→STANDARD、BUNDLE→BUNDLE、ADDON→MODIFIER），不再写进 `industry_ext` |
| 行业码 | 一处 FNB，一处 FOOD；美业有 BEAUTY 和 BEAUTY_SERVICE | 全库统一成一组常量 `RETAIL / FNB / BEAUTY`（与 05 的 `prd_goods`、`ind_store_policy` 一致）；`FOOD`、`BEAUTY_SERVICE` 只在迁移时换值。**需与 V2 确认**（§4 Q1） |
| SERVICE 形态 | 同时承载「零售到店核销服务」与「美业预约项目」 | 形态都是 SERVICE，用**履约方式**区分：`STORE_VERIFY` 到店核销、`APPOINTMENT` 预约 |

### 3.4 能力（轴 B、C、D、E）

| 能力 | 表达位置 | 适用 | 说明 |
|---|---|---|---|
| 称重 | `prd_goods.weighed` + `prd_sku.nominal_gram`；计量精度与允差统一进 SKU 或商品的列 | 生鲜、称重菜 | 收敛三种表达（§3.6 第 5 条） |
| 预售与截单 | `prd_sku.presale_*`、`prd_goods.cutoff_at`、`arrival_desc` | 生鲜、零售预售 | 活动里的截单只引用这里，不再自存 |
| 估清、限量 | `prd_sales_quota` + `prd_stock_lock(QUOTA)` | 餐饮为主，零售每日限量（R22）也用它 | |
| 可售量 | `prd_sellable_rule` + `prd_store_sku.sellable_qty` | 记进销存的商品 | 由 `inv_mode` 决定是否参与 |
| 套餐 | `sku_kind=BUNDLE` + `prd_bundle_*` | 餐饮套餐、零售组合装、美业组合项目 | |
| 选配与加料 | 规格维度（用途为下单选配），收费的挂 `prd_spec_value.sku_no`；目录条目可替换 | 餐饮口味加料、美业附加项（B9）、零售选购加项（R22） | B9、R22 用这一套，不另立模型 |
| 交付要求 | `prd_fulfillment_requirement` | 美业角色与资源、餐饮工位 | 工位**路由规则**在这里，工位**运行态**留行业库 `fnb_station` |
| 服务定义 | `prd_service_definition` | 服务形态中需要预约、占资源的项目（美业为主） | §3.5；零售到店核销服务不需要 |
| 行业扩展 | `prd_goods.industry_ext` | 只有一个行业懂的简单属性：餐饮制作秒数、过敏标签等 | 结构归行业，§3.5 |
| 卡与权益 | `type=CARD`、`sku_kind=CARD` + `prd_sku.entitlement_version_no`；权益定义在会员营销库 `ent_template` | 储值卡、次卡、疗程卡、礼品卡 | 商品只管「卖」，权益与核销在会员营销 |
| 目录与时段 | `prd_store_catalog` 等 | 三个行业 | 零售目录的 `frozen_content` JSON 改用定稿的分类表、时段表 |
| 渠道 | `chn_*` | 三个行业 | 收敛三处（§3.6 第 9 条） |
| 进销存 | `inv_mode` + 进销存接口 | 实物 | 配方、耗材定额归进销存 |
| 拼团、团购 | 活动域（`pmt_*`）；社区团购 `cmt_*` 归零售能力 | 零售 | `prd_goods.group_*` 按 TDD-团购从商品挪进活动迁出 |

### 3.5 服务定义与行业扩展（轴 E）

**服务定义**（`prd_service_definition`，用户 2026-11-28 定「服务 = 商品 + SKU + 服务定义」）：
- **为什么单独成表**：服务的执行定义有版本、会因 SKU 不同（B1 按时长或等级分 SKU）、被预约和工单冻结引用，是结构化的业务事实，不适合放 JSON。
- **结构**：按商品写一行默认值（`sku_no` 为空）；某个 SKU 不同的，按 SKU 写覆盖行，只写不同的项。时长、缓冲是列，步骤、注意事项是 JSON。
- **版本**：服务定义自己的版本号，按商品递增，一个版本是一组行（默认行加覆盖行，连同这一版的交付要求）。商家改标题、价格不产生新的服务定义版本；发布服务定义也不产生商品修订。不需要结转，不扩展商品保存指令。
- **写入**：商品域提供端口（发布 / 当前 / 按版本 / 按时刻列出），在商品事务里写服务定义与交付要求；按调用方的操作号防重，重放返回同一版本；只改服务定义免审，直接生效。美业保留发布入口与操作日志。
  - 发布可点名写默认行或某 SKU 的覆盖行；按 SKU 发布的行业（美业）不点名，由商品域定：商品只有一个 SKU 或还没有定义时写默认行，否则写该 SKU 的覆盖行（实现见 TDD-美业域迁移新库 §2.8 P3–P5）。
- **时长只有一处**：有服务定义的商品，时长只由服务定义发布写，并镜像到 `prd_goods.duration_min`，供展示和现有读方使用；商家保存商品时不写时长（整行更新从不写这一列，商家保存与定义发布各用定向更新）。没有服务定义的服务（零售到店核销）沿用商品自己的时长。
- **引用**：预约项目行、服务任务记「SKU 号 + 服务定义版本号」。

**行业扩展**（`prd_goods.industry_ext`）：
- 只放一个行业懂的简单属性（餐饮制作秒数、过敏标签等），带 `schemaVersion`，结构由行业模块定义并校验，商品领域按行业码存取。
- 写入经商品端口；商家编辑商品时忽略这些字段，防止旧编辑页把它回滚。
- 不做通用的「交付规格表」：等第二个行业也有带版本、按 SKU 区分的结构化规格时，再考虑与服务定义合并。
