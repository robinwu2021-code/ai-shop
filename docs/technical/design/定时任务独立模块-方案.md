## 二、现状：地基比预想的厚，但从来没通电

| | 现状 |
|---|---|
| 分布式锁 | ✅ ShedLock 已接（`JdbcTemplateLockProvider` + `@EnableSchedulerLock`），**多实例安全的前提已具备** |
| cron 可配 | ✅ 13/14 走 `${shop.job.*.cron:默认}`（`MediaPurgeJob` 是 `fixedDelayString`） |
| 运行记录 | ✅ `sys_job_run`：`last_run_at` / `duration_ms` / `status` / `detail` / `error` / `consecutive_failures` / `run_count` |
| 失败升级 | ✅ `JobSupport` 连续失败 3 次升级成 error 日志 |
| 按任务开关 | ❌ 只有 1 个 |
| 运营端可见 | ❌ `sys_job_run` **没有任何接口读它**——数据在库里，没人看得见 |
| **是否运行过** | ❌ **一次都没有** |

**「一次都没有」是这份方案最重要的一条前提**（2026-08-26 查生产）：

```
sys_job_run   0 行
shedlock      0 行      ← ShedLock 一次锁都没拿过
sys_outbox    空表
```

原因是生产跑 `SPRING_PROFILES_ACTIVE=api,ops`，而任务全在 `worker` 上。
**隔离做完了，「谁来跑」这半件没做。**

## 三、资源：不是理由（实测）

当初没做的顾虑是"服务器扛不住"。数据说不用担心：

```
内存   total 7685MB   used 1899MB   available 5785MB
swap   1987MB，used 0MB              ← 从来没换出去过
CPU    负载 0.10 / 0.04 / 0.01（4 核）
磁盘   13G / 59G（23%）
JVM    -Xmx2g 配着，堆实际 used 117MB / total 512MB，RSS 913MB
30 天 OOM 记录 0 · ai-shop NRestarts 0
```

worker 进程没有 Tomcat、没有请求涌入，`-Xmx512m` 足够，预计常驻 300–400MB。
加上去之后约 **2.3GB / 7.7GB**，仍有 5.4GB 空闲。

> 顺带两条与本方案无关但更早会成为瓶颈的：`innodb_buffer_pool_size` 只有 **128MB**
> （机器闲着 5.8GB）；业务实例 `-Xmx2g` 相对 117MB 的实际堆偏大。
> 真到内存紧张那天，先动这两个数字比做 native 有效得多。

## 四、要解决的问题，按重要性

1. **发布打断任务**（真正的驱动）。合并进业务实例的话，每次发布重启都会打断正在跑的任务。
   9 个有幂等口径的能靠下一轮自愈，**4 个不能**。将来的日结、对账通常也不幂等——
   跑一半留下的是半张账，**而半张账不报错**。
2. **该跑的没跑，没人知道**。`sys_job_run` 记着，但没有任何人看得见。
3. **停不掉、也重启不了**。某个任务在生产上闹事时，唯一的手段是改配置重启整个实例。

## 五、方案

### 5.1 一个必须先想清楚的取舍：`@Scheduled` 撑不起「运行时可配」

`@Scheduled(cron = "${...}")` 的 cron 是**启动时读一次**的常量。
要做到「运营页面改了 cron / 关掉某个任务，**不重启**就生效」，
就不能再用注解，得换成**注册表驱动**：

```
JobRegistry ──持有──> ThreadPoolTaskScheduler
     │                      │
     └─ 从 sys_job_def 读配置，schedule(runnable, CronTrigger)
        返回 ScheduledFuture，存起来
        关任务 = future.cancel()；改 cron = cancel + 重新 schedule
```

**这是本方案里唯一有分量的改造**，14 个任务都要从「注解声明」改成「注册进表」。
好处是开关、改 cron、立即触发、重启单个任务这四件事**一次全解决**，
而且它们本来就是同一个机制的四个动作。

> 不做这一步的话，「可配置」只能退化成「改配置文件 + 重启」，
> 那与今天的差别只是把 yaml 换成了数据库，**而重启正是我们要避免的那件事**。

### 5.2 数据模型（两张新表 + 一张既有）

| 表 | 用途 | 说明 |
|---|---|---|
| `sys_job_def` **新** | 任务定义与配置 | `job_name`(唯一) / `display_name` / `cron` / `enabled` / `lock_at_most_sec` / `description` / `owner_module`。**代码启动时把 14 个任务 upsert 进来**（代码是源头，表是可调的覆盖层）——新加任务不用写迁移 |
| `sys_job_run` 既有 | **当前状态**（每任务一行） | 已有 `last_run_at`/`duration_ms`/`status`/`detail`/`error`/`consecutive_failures`/`run_count`，够用，不改 |
| `sys_job_log` **新** | **执行日志**（每次一行） | `job_name` / `started_at` / `duration_ms` / `status` / `detail` / `error` / `trigger_type`(CRON/MANUAL) / `instance`。**按天分区或定期清理**——5 秒一次的任务一天 17280 行，两个这样的任务一年 1200 万行 |

> ⚠️ `sys_job_log` 的保留策略必须和表一起定，否则它自己会长成这个库里最大的表。
> 建议：秒级任务只在**状态变化或失败**时落日志，其余只更新 `sys_job_run`；
> 分钟级及以上每次都落；统一保留 30 天，由一个新任务清理（它自己也在清单里）。

### 5.3 运营端

| 接口 | 动作 |
|---|---|
| `GET /ops/jobs` | 列表：名称、cron、开关、最后一次跑的时间/耗时/结果、连续失败数、累计轮次 |
| `GET /ops/jobs/{name}/logs` | 执行日志，按时间倒序分页 |
| `POST /ops/jobs/{name}/enable` · `/disable` | 开关，**立即生效不重启** |
| `POST /ops/jobs/{name}/cron` | 改 cron，立即生效 |
| `POST /ops/jobs/{name}/trigger` | 立即跑一次（`trigger_type=MANUAL`），**仍走 ShedLock**，正在跑时拒绝 |

权限：新增 `system:job:read` / `system:job:manage`。
**读写分开**——看运行情况的人（排查问题）比能关掉任务的人多得多。

> ⚠️ 运营端菜单在库里（`sys_function` / `sys_function_point`），**只改 `nav.ts` 菜单不会出现**，
> 要跑生成器落迁移。这个坑本仓库踩过。

### 5.4 独立部署

- 新模块 `shop-job`：只装**调度器 + 注册表 + 14 个触发器**，业务仍在各域
- 打成独立 jar，同机第二个 systemd 单元，`SPRING_PROFILES_ACTIVE=worker`
- **ShedLock 已接好，业务实例与 worker 同时开着也不会重复执行** —— 迁移期可以两边都开
- 触发方式**先保持进程内调用**（12/14 已是薄触发器，改动最小）。
  改 HTTP/RPC 是后一步，它换来「业务发布完全不影响 worker」，
  但也把「被打断」换成了「业务重启期间调用失败」——见 5.5

### 5.5 「一定执行」需要补偿层，独立部署不提供

独立解决的是**不被打断**，不是**一定执行**。要真做到后者还缺：

- 漏跑检测：到点没跑成的，记下来
- 补跑：重试到成功；跨天的要能补昨天那一轮
- 日结/对账专用：**按业务日期而不是按时钟**驱动（「2026-08-25 这一天的账结了吗」，
  而不是「昨晚 3 点那次跑了吗」）——这一条是日结对账与其它任务的根本差别

`sys_job_run.consecutive_failures` 是种子，但没有补跑。**日结对账真正需要的是这一层**，
它与独立不独立正交，建议单独排期。

## 六、分步（每步能独立停下、独立回退）

| 步 | 内容 | 停在这里也是有用的 |
|---|---|---|
| **1** | `sys_job_def` + 注册表驱动改造 + 按任务开关（**先不动部署**，仍在业务实例内） | 有了开关与可见性，后面每步都可回退 |
| **2** | `GET /ops/jobs` + 日志表 + 运营页面（含菜单落库） | 任务终于「看得见」 |
| **3** | 生产开 `worker`（仍合并在业务实例），**观察一周** | 14 个任务至今零执行；现在是零数据窗口，风险最低 |
| **4** | 拆 `shop-job` 独立 systemd 单元 | 拿到发布隔离 |
| **5** | 2 个直接摸 mapper 的改走 port；评估 HTTP/RPC 触发 | 为多机部署铺路 |
| **6** | 补偿层（漏跑检测 + 补跑 + 按业务日期驱动） | 日结、对账的前置 |
| **7** | Spring Data AOT 迁移完成后再评估 native | 见下 |

### 关于第 3 步的时间窗

**现在是启用的最佳窗口，而且有期限。** 2026-08-26 查生产：

```
已过期待降级的套餐  0      → PlanExpiryJob 今天什么都不做
待处理媒体资产      0（238 个全 ACTIVE）
资质记录            0
订单                0
outbox              空
```

**今天开等于空转一圈。** 但线上那个 PRO 套餐 **2026-09-03 到期**——
到那天 `PlanExpiryJob` 会第一次真的降级压店。
**在有数据的时候第一次跑一个从没跑过的任务**，是本仓库今天刚踩过的形态。

### 关于 native（第 7 步）

GraalVM 的两个收益是**启动毫秒级**与**低常驻**。
任务进程是常驻的，启动优势对它**无效**；常驻从 ~900MB 降到 ~200MB，
在只有一个 worker 实例、机器闲着 5.8GB 时不构成理由。

它值得做的那天是：任务被拆成按需拉起的短生命周期进程，或者要在一台机器上跑多个 worker。
届时 `mybatis-plus` 的反射问题若已随 Spring Data AOT 迁移解决，代价会低得多。
**顺序不能颠倒**：独立部署的理由是发布隔离，native 是独立之后顺手拿到的收益。

## 七、要拍板的三件事

1. **`sys_job_log` 的保留策略**：秒级任务是否只在「状态变化或失败」时落日志？（不然一年千万行）
2. **手动触发要不要限流**：`POST /ops/jobs/{name}/trigger` 连点会被 ShedLock 挡住，
   但对 5 秒级任务意义不大——是否只给分钟级以上的任务开这个按钮？
3. **第 3 步（开 worker）与第 1、2 步的先后**：先开着裸跑一周攒真实数据，
   还是先把开关与页面做好再开？我倾向后者——**没有开关的启用是不可回退的**。
