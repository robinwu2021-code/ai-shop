## 一、一句话

商户能做什么，由**三件正交的事**决定：**他是谁**（商户类型）、**钱先进谁的账户**（资金路径）、
**谁是销售主体**（经营模式）。此前把后两件当成一件，是本轮发现的最大一处混淆。

---

## 二、三个轴的定义（规范）

本节是**词汇表**。下文与各分册出现这三个词时，一律以此处为准。

### 2.0 为什么必须分开

②③ 高度相关但**不是同一件事**，压成一个字段会立刻出错：

```
归集(AGGREGATED) + 自营(SELF_OPERATED)   平台收钱、平台卖    ← 今天唯一在跑的
直连(DIRECT)     + 第三方(THIRD_PARTY)   商家收钱、商家卖    ← 尚未落地
直连(DIRECT)     + 自营(SELF_OPERATED)   钱进商家户、平台是销售主体  ← 非法，要拦
```

**第三行是关键**：正因为它可表达，才需要两个字段各自判。
（同型教训见 ADR-013：合成一个枚举后，非法组合在类型上就是可表达的。）

### 2.1 轴① 商户类型 —— **他是谁**

| | |
|---|---|
| 字段 | `mch_entity.legal_form` |
| 谁决定 | **工商登记**（平台只是记录） |
| 变化节奏 | 办照 / 公司化时变，年为单位 |
| 判据 | **有没有营业执照、执照是什么** —— 只看执照，不看其他任何证 |

| 取值 | 含义 | 执照 | 责任形式 |
|---|---|---|---|
| `NATURAL_PERSON` | 自然人经营者 | **无** | 个人无限责任 |
| `INDIVIDUAL` | 个体工商户 | 个体户执照 | 经营者个人**无限责任** |
| `ENTERPRISE` | 企业 | 企业执照 | 公司资产，**有限责任** |

> 现库里是 `MICRO`/`INDIVIDUAL`/`ENTERPRISE`。`MICRO`（小微）**是通道概念不是法律形态**，
> 且与法规「小微企业（有照）」重名且含义相反 —— 第五步改名为 `NATURAL_PERSON`，
> `MICRO` 降级为通道档 `WECHAT_SMALL`。

#### 类型内部的四个属性（不拆成子类型）

同类型内差异很大，但那些差异**各自已是独立维度**：

| 属性 | 字段 | 取值 |
|---|---|---|
| 经营资格 | `biz_qualification` | `REGISTERED` / `EXEMPT` / `UNREGISTERED` / `GRANDFATHERED` |
| 豁免类型 | `exempt_type` | `AGRI` 自产农副产品 / `HANDCRAFT` / `SERVICE` / `PETTY` |
| 农业生产者 | `is_agri_producer` | 0 / 1 |
| 进件级别 | 由 `mch_qualification` + `mch_payment_merchant` 派生 | K0 未实名 → K3 执照进件 |

**只有 `PETTY` 受 10 万元/年 约束**；`AGRI`/`HANDCRAFT`/`SERVICE` 三类无金额上限。

#### 不变式

```
legal_form != NATURAL_PERSON  ⇒  biz_qualification = REGISTERED   （有照必已登记）
biz_qualification = EXEMPT    ⇒  exempt_type IS NOT NULL
is_agri_producer = 1          ⇒  biz_qualification ∈ {EXEMPT, REGISTERED}
```

### 2.2 轴② 资金路径 —— **钱先进谁的账户**

| | |
|---|---|
| 字段 | `mch_entity.funds_mode` ⟵ **待建（第三步）** |
| 谁决定 | **商户类型**（ADR-017 §3.2），平台不能自选 |
| 变化节奏 | 类型升级或通道开通时变 |
| 判据 | **这家商户开不开得出票** |

| 取值 | 用户付给谁 | 钱的性质 | 给商家的钱 | 发票 | 依赖 |
|---|---|---|---|---|---|
| `AGGREGATED` 归集（代销） | **平台商户号** | **平台的营业收入** | 货款（B2B 应付） | 平台开给消费者；商家开给平台 | 无，今天就能跑 |
| `DIRECT` 直连（分账） | 商家二级商户号 | 商家的钱 | 分账，钱从未进平台 | 商家开给消费者 | EDI + 收付通 |

> `AGGREGATED` **不等于**「打进对公账户再转账」—— 那是真二清，已被否掉。
> 这里平台是交易主体，付出去的是采购/代销货款，走对公转账 + 合同 + 发票。

#### 类型 → 允许的路径

```
ENTERPRISE       → {AGGREGATED, DIRECT}
INDIVIDUAL       → {AGGREGATED, DIRECT}
NATURAL_PERSON   → {DIRECT}                        ← 归集禁止：开不出票
  ↳ is_agri_producer=1 且售自产农产品 → {AGGREGATED, DIRECT}   ← 平台自开收购发票
```

#### 不变式

```
legal_form = NATURAL_PERSON ∧ is_agri_producer = 0  ⇒  funds_mode ≠ AGGREGATED
funds_mode = AGGREGATED  ⇒  补差动作不存在（subsidy_minor 恒为 0）
funds_mode = DIRECT      ⇒  该主体必须有 ACTIVE 的 mch_payment_merchant
```

**第二条是钱的安全边界**：归集下应付已按全额算，再补一次就是**重复付款**。

### 2.3 轴③ 经营模式 —— **谁是销售主体**

| | |
|---|---|
| 字段 | `mch_store.business_mode`（挂**门店**不挂主体） |
| 谁决定 | 商务关系，**只开在运营端**，不给商家自己勾 |
| 变化节奏 | 换合作方式时变；**只对新单生效** |
| 现状 | `DEFAULT 'SELF_OPERATED'`，全库 145 家门店无一例外 |

| 取值 | 销售主体 | 结算状态机 | 进项票 |
|---|---|---|---|
| `SELF_OPERATED` 自营 | **平台** | `PENDING_RECON → CONFIRMED → PAID` | **必须有** |
| `THIRD_PARTY` 第三方 | 商家 | `PENDING → SPLITTABLE → SPLIT` | 不需要 |

> 挂门店的理由：同一主体下旗舰店自营、加盟店第三方是常见形态（V23）。
> `stl_bill.business_mode` 是**下单时快照** —— 门店改模式，历史单不跟着改口径。

#### 自营成立的四个必要条件（ADR-017 §3.4）—— **做不到就退回第三方**

| # | 条件 | 违反的后果 |
|---|---|---|
| 1 | 合同相对方是平台 | 合同写商家 → 钱是商家的 → **二清** |
| 2 | 平台开票给消费者，商家开票给平台 | 票流资金流不一致 |
| 3 | **平台对消费者承担商品与售后责任** | 责任在商家 → 实质是平台模式 |
| 4 | 四流一致（合同/发票/资金/货物） | 按实质定性，名义无效 |

第 3 条是产品上最疼的：**退款、赔付、质量投诉都由平台先扛**。

### 2.4 三轴合法组合表

| 类型 | `funds_mode` | `business_mode` | 合法 | 说明 |
|---|---|---|:---:|---|
| 企业 / 个体户 | `AGGREGATED` | `SELF_OPERATED` | ✅ | 今天唯一在跑的 |
| 企业 / 个体户 | `DIRECT` | `THIRD_PARTY` | ✅ | 待 EDI |
| 自然人 · 农产品 | `AGGREGATED` | `SELF_OPERATED` | ✅ | 收购发票 |
| 自然人 · 非农 | `DIRECT` | `THIRD_PARTY` | ⚠️ | 待通道核实（个人卖家 2500） |
| 自然人 · 非农 | `AGGREGATED` | 任意 | ❌ | **无票，成本不可扣** |
| 任意 | `DIRECT` | `SELF_OPERATED` | ❌ | 钱进商家户却说平台是卖方 |
| 任意 | `AGGREGATED` | `THIRD_PARTY` | ❌ | 钱进平台户却说商家是卖方 → **二清** |
| `UNREGISTERED` | 任意 | 任意 | ❌ | **法律禁止交易** |

**最后三行必须在写库那一刻拦**，不能只靠入驻校验 —— 运营在后台改一个字段就能造出来。

---

### 2.5 「要不要补差」看的是轴②，不是轴③

本文更正的第一处（详见 §三）：

```
钱在商家账户  → 积分抵扣让他少收 → 平台必须补差进去
钱在平台账户  → 平台自己少收     → 无人需要补
```

判据是**钱在谁手里**＝ `funds_mode`。用 `business_mode` 判，
在两者不一致时会判错 —— 而库里恰好有一批这样的单（§4.3）。

## 三、两处更正（我方的错，以上游为准）

### 3.1 `canPoints` 的判据：按 `funds_mode`，不是 `business_mode`

[分步实施方案 §5.4](./平台优化-分步实施方案.md) 我提议给 `canPoints` 加 `businessMode` 入参。
**作废**，改按 [积分与资金结算 §五#6](./积分与资金结算-按资金路径重整.md) 的口径：

```ts
export function canPoints(ctx: {
  globalOn: boolean;
  communityOn: boolean;
  merchantOn: boolean;
  legalFormCanPoints: boolean;
  legalFormDenyReason: string;
  /**
   * 资金路径。**补差只在 DIRECT 下发生** —— 钱在商家账户才需要补进去。
   * 不要用 business_mode 判：那说的是「谁是销售主体」，与「钱在谁手里」正交。
   */
  fundsMode: "AGGREGATED" | "DIRECT";
  channelSupportsSubsidy: boolean;
}): Verdict
```

### 3.2 「自营下积分对所有类型可开」—— 过宽

[全链条清单 §七](./商户类型-全链条清单.md) 那句要收窄。
我把「自营」当成了免检条件，**漏掉「补差本身就是一次平台 → 自然人付款」**：

| 组合 | 平台有没有直接付钱给自然人 | 积分 |
|---|---|---|
| 自然人 + **直连** | **有** —— 补差就是平台付给他 | ❌ **维持禁止** |
| 自然人 + **归集**（仅自产农产品） | 没有 —— 付的是货款，且有收购发票 | ✅ 可开 |
| 个体户 / 企业 + 任一路径 | — | ✅ |

### 4.3 V23 的实证：`DEFAULT` 回填存量已经发生过一次

54 张 `business_mode = SELF_OPERATED` 的单，状态是第三方轨道的 `PENDING`。
代码分支没错（`SettleServiceImpl:201`），时间对得上：

| | 时间 |
|---|---|
| 这 54 张单创建于 | 08-10 ~ **08-11 13:14** |
| **V23 加 `business_mode` 列**（`DEFAULT 'SELF_OPERATED'`） | **08-11 15:18** |

## 五、目标态：三类 × 两路径 × 能力

### 5.1 类型 → 可走哪条路径（ADR-017 §3.2）

| 商户类型 | A 归集（代销） | B 直连（分账） | 决定性理由 |
|---|---|---|---|
| **企业商户** | ✅ 首选 | ✅ 需 EDI | 能开专票 |
| **个体工商户** | ✅ | ✅ 需 EDI | 普票/代开专票，**有凭证** |
| **自然人商户** | ❌ **禁止** | ✅ 唯一可行 | 开不出票 → 成本不可税前扣除 |
| ↳ 自产农产品 | ✅ **例外** | ✅ | 平台可自开**农产品收购发票** |

### 5.2 能力矩阵（今天 = 归集 + 自营）

| | 自然人`UNREGISTERED` | 自然人`EXEMPT`·非农 | 自然人`EXEMPT`·**农产品** | 个体工商户 | 企业商户 |
|---|:---:|:---:|:---:|:---:|:---:|
| 今天可交易 | ❌ 法律禁止 | ❌ 无进项凭证 | **✅** | ✅ | ✅ |
| 可走路径 | — | 仅 B（待通道） | **A + B** | A + B | A + B |
| 进项凭证 | — | — | **平台自开收购票** | 普票/代开专票 | 专票 |
| 用户拿票 | ❌ | ❌ | ✅ 平台开 | ✅ | ✅ |
| 积分（A 路径） | — | — | **✅** | ✅ | ✅ |
| 积分（B 路径） | ❌ 仍禁 | ❌ 补差=付款给自然人 | ❌ 同左 | ✅ | ✅ |
| C 端位置 | 集市 | 集市 | **正常货架** | 正常货架 | 正常货架 |

### 5.3 代销的四个必要条件（ADR-017 §3.4）——**做不到就退回 B**

| # | 条件 | 违反的后果 |
|---|---|---|
| 1 | 合同相对方是平台 | 合同写商家 → 钱是商家的 → **二清** |
| 2 | 平台开票给消费者，商家开票给平台 | 票流资金流不一致 |
| 3 | **平台对消费者承担商品与售后责任** | 责任在商家 → 实质是平台模式 |
| 4 | 四流一致 | 按实质定性，名义无效 |

### 5.4 表述即法律关系（ADR-017 §3.5）——**产品措辞受法律约束**

| 可以说 | **不能说** |
|---|---|
| 供货商：XX 果蔬 | 本商品由 XX 果蔬**销售** |
| 产地 / 门店：XX 店 | 售后请**联系 XX 商家** |
| 由 XX 店配送 | 「入驻商户」「第三方卖家」 |
| 商家评分、门店主页 | **「平台仅提供信息展示，交易由商家与您达成」** |

> 最后一行最要命：**那句免责声明恰恰是承认自己是平台模式**，写了就不能再走 A 路径。
> 所以销售主体的表述必须**单一来源**（一处配置 + 三端引用）+ 守卫。
>
> ⚠️ 这条约束**推翻了我在全链条清单 §六里给展示商户写的措辞**
> （「交易与付款线下完成，平台不担保」）—— 展示商户本身不交易所以无害，
> 但**那句话绝不能出现在任何走 A 路径的商品上**。

#### 到期清零：为什么它是恒等式的前提

池子恒等式是「流通中的积分 == 池子里的钱」。分过期了却不清零：
流通侧不减，池子侧也不记 `EXPIRE_INCOME` —— **池子只增不减，
失衡量随时间单调增长**。滚动到期的写侧一直是对的，只是没人在到期那天来收。

顺序上**先记流水再清余额**：反过来的话中间崩一次就只剩「余额没了」
而没有任何记录解释得了它去哪 —— 而积分是用户看得见的东西。

#### `supports_subsidy` 判在结算侧，不在扣分那一刻

**下单时通道还没定**（`markPaid` 才有），那时判等于拿一个还不存在的事实做判断。
所以放在 `executeSplit`：通道不支持补差 → 转 `MANUAL` 并写明原因，
而不是发起一次注定失败的补差、然后整单转重试 ——
后者的根因（通道压根没这个能力）要翻网关日志才看得出来。

> 实做时发现既有补差测试的 fixture **没设 `payChannel`**，
> 加校验后本该全红却没红 —— 因为它们本来就没走到那一步。
> 补齐 fixture 的通道后，再加一条专门覆盖「通道不支持」的分支。

#### 这个缺口为什么特别难发现

不是「数字不对」，是**根本没有数字**：
B 端「本期积分支出」永远是 0，而 overview 的恒等式（流通积分 vs 池子余额）
**两边都是 0，看着还挺平**。只有真的发过一笔分才会暴露。

#### 方向不靠符号表达

`recordPoolFlow` 的金额**必须为正**，进出由 `poolType` 决定。
符号与类型两处表达同一件事，迟早对不上 —— 而对不上时恒等式只会告诉你「不平」，
不会告诉你是哪一笔。0 与负数直接忽略。

#### 后端那份判错了两处，不止一处

方案 §3.1 只写了「选错轴」。实做时发现**还读错了字段**：

```java
// 旧：mch_payment_merchant.legalForm == MICRO
```

那一列是**通道进件档**（微信小微 / 个体户），不是主体的法律形态 ——
**通道给他开了小微户，不代表他就是无照**。两处叠加的后果是同一个：
农产品农户（无照 + 归集，平台自开收购发票）被误拒。

现在：法律形态走注册表 `needLicense()`，路径走 `funds_mode`。

#### 前端那份顺带补上了后端缺的闸

TS 版原本有全局开关与通道补差两闸，Java 版都没有；
而 Java 版读的字段是错的。改完之后两份的判据序列一致：

```
全局 → (仅 DIRECT) 通道能否补差 → 社区 → 无照×直连 → 商家开关
```

**「通道能否补差」只在直连下问** —— 归集根本不发起补差，
拿通道能力去拦它就是错误拒绝。这一条前端有断言守着。

#### 幂等为什么要一个显式标记，而不是靠 `available_at <= now`

只按时间判的话，任务每天扫到的都是**同一批已经转过的行**。
第二次转正会被 `pending_balance >= points` 的守卫拦下、返回 0 行、
任务当成「没事发生」—— **账面不报错，但也永远不知道自己在空转**。

`activated_at` 一次性写死，任务只扫「到点且未转正」的行。
幂等靠它，余额守卫只是兜底。

#### `pendingDays` 为什么 0 也要走转正流程

配置成 0（发放即可用）时不能特判成「直接加 balance」——
那会让立即/延迟两条路径各写一套加余额的逻辑，
而其中一条平时跑不到，**坏了没人知道**。

#### 多实例并发：已知未处理

本仓库现有两个 `@Scheduled` 任务同样没有分布式锁。
这条链路靠 `activated_at` 幂等 + 乐观守卫兜底，重复执行不会重复加钱，
但**上多实例前要补 ShedLock** —— 幂等只保证不加错，不保证不空转。已写进任务的类注释。

#### 禁用词守卫：先建守卫，再改代码

这条**守的是资金模式的合法性，不是文案风格**。
一句「平台仅提供信息展示，交易由商家与您达成」写了，就是白纸黑字承认自己是居间方，
此时再让钱进平台账户就是二清 —— **很多平台是在用户协议里栽的，不是在业务上**。

所以顺序是先写守卫、塞一句禁用词确认它会红（两条规则都命中），再动产品代码。
每条禁用词都要能回答「它为什么推翻资金模式」——
只是「读着别扭」的不进这张表，那属于文案评审，混进来会让守卫变成谁都想绕过的东西。

#### `selfOperated` 由 `funds_mode` 派生，不查门店

| 为什么 | |
|---|---|
| 法律上对 | 「谁是销售主体」看的是**钱进谁的账户** —— 归集即平台收款、平台开票、平台担责 |
| 工程上对 | 门店级 `business_mode` 要按店查，而 Brief 出现在**每一张商品卡**上，会变成 N+1 |

空值按自营：今天唯一在跑的就是归集，而**漏标是法定义务的缺失**，多标只是显示问题。

#### 标识放在店名之前

它回答的是「谁在卖」，而店名只回答「货是谁供的」。放后面会被读成店名的一个后缀。

**商家信息照常展示**（供货商、产地、评分）—— 要禁的是把销售方指给商家的**表述**，
不是商家信息本身。这是 ADR-017 §3.5 那张表的分界线。
