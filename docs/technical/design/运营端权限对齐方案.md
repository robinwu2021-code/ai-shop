# 运营端权限：对齐方案（实施细则）

> ⚠️ **角色与权限码清单已并入
> [三端角色权限功能对齐清单](../requirements/三端角色权限功能对齐清单.md)**
> —— 那份是唯一权威。本文只保留运营端的**实施步骤 S1–S5**。
>
> 2026-08-11 · 起因：枚举 P5 复核时发现 ops-web 与后端的角色码、权限码、
> 登录响应结构三层都对不上。角色码已在 http 层加映射修好，**权限码体系没有**。
>
> 结论先说：**这不是「两套码要对齐」，是「前端自己在给自己授权」。**
> 而且两边的能力集合根本不一样 —— 对齐的第一步是承认这件事。

---

## 1. 现状：三句话

> 1. 后端 10 个粗粒度权限码，守住了 55/57 个 ops 端点，**模型是干净的**。
> 2. ops-web 58 个细粒度权限码，**其中 9 个模块后端根本没有对应端点**。
> 3. 前端判权读的是**它自己写死的 `ROLE_PERMS` 表**，不是后端下发的 `perms` ——
>    而 `LoginResp` 的注释写着「权限判定以后端为准」。

第 3 条是真正的问题。前两条只是让它更难修。

---

## 2. 摸到的数

### 2.1 后端（`Perms.java`）

| 项 | 数 |
|---|---|
| 权限码 | 10 |
| 角色 | 4（SUPER_ADMIN / BD / GOODS_OPS / SUPPORT） |
| ops 端点 | 57 |
| 带 `@PreAuthorize` 的 | **55**（另 2 个是 `/ops/auth/login` 与 `/ops/auth/me`，本就不该要） |

后端这套是**能用的**：粒度粗但覆盖完整，读写已经分开
（`community:view` 与 `industry:manage` 分家那次就是被真实事故逼出来的）。

### 2.2 ops-web（`permissions.ts`）

| 项 | 数 |
|---|---|
| `ROLE_PERMS` 里的权限码 | 58 |
| 页面实际调用的码 | 46 |
| 角色 | 11 |
| 与后端对得上的角色 | **1**（SUPER_ADMIN） |

### 2.3 模块对不上的部分

ops-web 的 17 个权限模块里，**9 个后端没有任何端点**：

| 有后端端点 | 后端没有 |
|---|---|
| merchant · order · product · community · review · aftersale · store · iam | content · finance · fulfillment · group · growth · marketing · message · risk · system |

**IAM 模块尤其**：ops-web 打 7 个端点（`/ops/staffs`、`/ops/roles/{r}/perms`…），
后端只有一个 `/ops/staff`（单数，路径都不同）。也就是「角色权限配置页」
连一个能通的写接口都没有。

### 2.4 现在实际会发生什么

`ops-web/.env` 里 `NEXT_PUBLIC_USE_MOCK=0` —— **默认就是连真后端**。
配合刚修掉的 `role: undefined`（那条已修），链路是：

```
后端 staff.perms = ["merchant:audit","order:view"]   ← 下发了
        ↓ 前端不读
ROLE_PERMS["MERCHANT_BD"] = ["merchant:*","order:order:read",…]  ← 用这个判
```

结果：**前端显示的权限与后端实际允许的没有任何关系**。两种错都会发生 ——

- 前端放行、后端 403：用户点得到按钮，点完报「没有操作权限」
- 前端拦住、后端本来允许：功能存在但用户根本看不见入口

## 3. 建议：以后端为准，但**不是**把 58 个码搬到后端

### 3.1 为什么以后端为准

不是因为后端「更权威」这种空话，而是三条具体的：

1. **只有后端的判定是有效的。** 前端那份改一行就绕过了，它从来不是安全边界，
   只是菜单裁剪。让不生效的一方定义词表，等于让词表脱离现实。
2. **后端已经把 perms 下发了**（`staff.perms`），前端不读是纯粹的浪费 ——
   而且是那种「看起来接了、其实没接」的浪费。
3. **后端的 10 个码是被端点验证过的**，58 个里有 20 多个对应的能力压根不存在。
   把不存在的能力的权限码搬到后端，是在为一个还没有的东西建规矩。

### 3.2 为什么**不**把 58 个码搬过去

这是本方案最重要的一句：

> **粒度差异不是缺陷，是两件不同的事。**
> 后端的码回答「这次请求能不能执行」，前端的码回答「这个按钮要不要画」。
> 后者天然更细（同一个端点在三个页面上有三个入口），前者天然更粗。

强行统一到 58 个细粒度码的代价是：后端要为一个「按钮级」的词表负责，
而它根本看不到按钮。将来加一个入口，后端得跟着加一个权限码 ——
**这是把前端的展示结构烧进后端的授权模型**。

### 3.3 建议的模型：**后端定词表，前端做映射**

```
后端 perms（10 个，权威，随登录下发）
        ↓  一张映射表（在前端，显式、可测）
前端 UI 能力（46 个，只管画不画按钮）
```

关键点：**前端不再有自己的 ROLE_PERMS**。
`allow("merchant:apply:audit")` 的答案来自「后端给了我 `merchant:audit` 吗」，
而不是「我的角色在我自己那张表里有没有这条」。

对于后端没有对应能力的 9 个模块，映射表里显式写 **`UNIMPLEMENTED`** ——
这些入口一律不显示，而不是靠角色碰巧没权限而隐藏。
两者的区别在于：前者是「这功能还没有」，后者是「你没权限」，
而运营看到后者会去找管理员要权限，然后发现谁都给不了。

## 4. 方案

### S1 · 前端改读后端下发的 perms（**必做，其余都建立在它上面**）

- `AuthState` 存 `perms: string[]`（登录时从 `staff.perms` 拿，已在下发）
- `allow(code)` 改成：查映射表得到所需的后端 perm → 看 `perms` 里有没有
- `*` 仍然通配（超管）

**验收**：用 `bd` 账号登录，能看到的入口 ⊆ 后端真的会放行的端点。

### S2 · 建映射表 `UI_PERM_MAP`

```ts
// 前端 UI 能力码 → 后端权限码；UNIMPLEMENTED = 后端还没有这块能力
const UI_PERM_MAP: Record<string, string | typeof UNIMPLEMENTED> = {
  "merchant:apply:audit": "merchant:audit",
  "order:order:read":     "order:view",
  "order:order:intervene":"order:intervene",
  "product:category:*":   "category:manage",
  "finance:settle:read":  UNIMPLEMENTED,   // 后端无 finance 模块
  …
};
```

**这张表是这次工作的核心产物**，它把「前端以为有的能力」与「后端真有的能力」
的差集变成一份可读、可测的清单 —— 而那份差集现在散在 58 个码里没人看得见。

### S3 · 两条守卫

1. **映射表必须覆盖页面实际调用的每一个码**
   （扫 `allow(...)` / `canModule(...)` 的字面量，与表比对）——
   漏一个就是运行时 `undefined`，而 `undefined` 会被当成「没权限」，
   表现为按钮神秘消失。
2. **映射到的后端码必须真的存在于 `Perms.java`**
   （从 Java 源码里抽常量比对）—— 否则表里写一个手滑的 `order:veiw`，
   永远判 false，同样表现为按钮消失。

### S4 · 清理与登记

> ⚠️ **2026-08-11 更正**：这一条原本写的是「ops-web 的 Role 收敛为后端实际有的
> 4 个，多出的 7 个删掉」。**撤销** —— 做完整对齐后发现，ops-web 的 11 个角色与
> [需求矩阵 §2.3](../requirements/需求矩阵-三端.md) **逐条一一对应**，
> 一个不多一个不少。前端没多造，是后端少做了 7 个。砍前端等于砍需求。
>
> 详见 [三端角色权限功能对齐清单](../requirements/三端角色权限功能对齐清单.md)。
>
> **先看到代码不一致就断定「前端乱做」是一种偏见** —— 判断谁对谁错之前，
> 得先找到那个双方都在照着做的规格。

- ops-web 的 `Role` **保留 11 个**（它们是矩阵的规格）；
  后端未实现的 7 个在 UI_PERM_MAP 里标 `UNIMPLEMENTED`，入口不显示
- IAM 页的「角色权限配置」标为未实现（后端无 `/ops/roles/*` 端点），
  而不是让它调一个 404 的接口
- 枚举登记表里 `ops-web:Role` 的 note 更新为「已对齐」

### S5 · 后端补两处（小）

- `/ops/staff` 与前端的 `/ops/staffs` 路径不一致 —— 定一个（建议复数，与其余
  `/ops/merchants`、`/ops/pickups` 一致），另一边改
- `/ops/auth/me` 返回 perms（前端刷新页面后要能重新拿到，不能只在登录时给一次）

---

## 5. 不做什么

| 不做 | 为什么 |
|---|---|
| 把 58 个细粒度码搬进后端 | 把前端的展示结构烧进后端授权模型，见 §3.2 |
| 后端权限接 DB（`Perms.java` 注释里的 M9b） | 与本次对齐正交。硬编码的问题是「改要发版」，不是「对不上」 |
| 给那 9 个模块补后端能力 | 那是产品排期，不是权限对齐。本方案只负责**如实标出它们没有** |

---

## 6. 工作量与风险

| 步骤 | 量 | 风险 |
|---|---|---|
| S1 前端改读 perms | 小（auth store + allow 两处） | 中：所有页面的按钮可见性都会变 |
| S2 映射表 | 中（46 条，逐条对） | 低：纯新增 |
| S3 守卫 | 小 | 无 |
| S4 清理 | 小 | 低 |
| S5 后端两处 | 小 | 低 |

**唯一的实质风险在 S1**：改完之后，很多现在看得见的入口会消失 ——
因为它们本来就不该看得见（后端会 403）。这不是回归，是**把一直存在的错误显示出来**。

建议 S1 落地时同时做一次运营端全页面走查：用四个真实角色各登录一次，
记录每个页面看得到什么 —— 这份记录本身就是「权限模型到底长什么样」的第一份真实文档。

---

## 7. 一句话总结

> 现在的问题不是「两套权限码」，而是**前端那套根本不判权，只是画画**。
> 对齐的目标不是让 58 = 10，而是让那 46 个按钮的显示与否，
> 真的由后端那 10 个码决定。

## 8. 执行记录 · 七个角色补配置（2026-08-11）

方案里悬而未决的那条 —— 「ops-web 有 11 个角色，后端只配了 4 个」——
**由后端补齐**（另一个选项是从 ops-web 删掉 7 个，已在 S4 撤销：
砍前端等于砍需求）。

### 配了什么

| 角色 | 权限码 | 说明 |
|---|---|---|
| CAMPAIGN_OPS | `marketing:govern` `order:view` `community:view` | 判断活动对不对要看它产生的订单 |
| COMMUNITY_OPS | `industry:manage` `community:view` `order:view` | 社区/自提点端点用的就是 `industry:manage` |
| AUDITOR | `goods:audit` `review:govern` `community:view` | **不给 `merchant:audit`**：商家资质归 BD |
| FINANCE | `settle:manage` `order:view` | `settle:manage` 的「只给超管」是四角色时代的写法 |
| RISK | `order:view` | 后端**零风控端点** |
| ANALYST | `community:view` | 矩阵写明「只读脱敏」，**故意不给 `order:view`** |
| TECH_OPS | `audit:view` | 灰度与环境切换没有端点 |

### 短得反常的那三个不是漏配

风控、数据分析、技术运维拿到的清单很短，因为**后端那几块根本没有端点**。

这里刻意没做的一件事：把它们映射到一个语义相近的现有码。
那样权限表看着是满的，而实际上什么都点不动 ——
更坏的是可能顺手给出远超职责的权限（风控要「封禁」，
就把 `merchant:audit` 给它，于是风控还能批入驻）。

「配了」不等于「够用」。功能缺口由 `perm-map.ts` 的 `UNIMPLEMENTED`
与 `ops-endpoint-exists.test.ts` 守着，与这次的角色配置正交。

### 两个连带发现

**① 配了权限却没有账号，等于没配。** 七个角色一个种子账号都没有 ——
而这件事之所以能一直存在，正是因为没人能登进去看一眼。
补了七个 dev 账号（campaign/community/auditor/finance/risk/analyst/techops，
密码 `<用户名>123`）。

**② DevSeeder 的总闸让新账号在已有开发库上永远不生效。**
总闸只看社区表，非空即整段 `return`，后面所有 `seedXxx` 都不执行。
实测表现：权限配好了、代码也对，七个账号登录全是「登录已失效」。
把员工种子提到闸前（`seedStaff` 自己按 username 判存在性，重复调用安全）。

### 棘轮翻面

`nav.test.ts` 里那条把「7 个角色没配」钉成清单的断言**已翻转**：
现在守的是「ops-web 的角色后端必须都配」。
棘轮走完就要拆掉 —— 留着一份写死了 7 个名字的期望值，
下次谁删掉一个角色配置反而会红得莫名其妙。

同时新增一条：后端配了的角色，ops-web 的 `BACKEND_ROLE_PERMS` 与
`BACKEND_ROLE`（角色码翻译）必须都认得。漏一个的表现是**静默降级** ——
登录成功、拿到空 perms、看到一个空后台，没有任何报错。

### 实测（真后端 8081/8082，非 mock）

- 七个账号全部登录成功，`perms` 与配置逐条一致
- `finance` 的 token 打 `/ops/staffs`、`/ops/merchant/apply`、`/ops/audit-log`、
  `/ops/communities` → 全部 `10403`；打 `settle` 侧正常
- `techops` 打 `/ops/audit-log` → `0`，打 `/ops/staffs` → `10403`
- 浏览器：campaign 看到 5 个入口（看板/订单/营销/团购/社区）、
  community 3 个、techops 2 个（看板 + 审计日志）

> 顺带验到了 `me()` 启动刷新：手改 localStorage 里的 perms 后刷新页面，
> 被后端下发的真实身份纠正回来 —— 这正是它要防的那件事。
