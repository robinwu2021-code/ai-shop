## 1. 需求摘要

三端都要能被通知触达；App 推送必须走厂商系统级通道（小米 / 华为 / OPPO / vivo / 荣耀等 + 苹果 APNs，做到**息屏可达**），微信侧走订阅消息（服务通知）：

- **C 端**：交易关键节点（支付、到货、退款）必达。到货通知是履约闭环核心（C-FF-02，M1-3）。触达 = 站内消息中心 + 微信订阅消息 + App 厂商推送。
- **B 端**：商家**不盯屏幕也要知道来新订单了**（响铃/横幅）；售后、差评、结算、报价采纳进消息中心。触达 = 站内 + App 厂商推送 + 微信订阅消息。
- **平台端**（ops-web，桌面浏览器）：客服与运营的待办要主动到人——新工单、入驻审核、团模板审核、评价申诉、风控告警。触达 = 站内铃铛 + 浏览器桌面通知。

## 4. 方案设计

### 4.1 总体：事件驱动的统一触达编排

```
业务域(trade/settle/review/…)──发事件──▶ Outbox ──▶ NotificationConsumer(shop-core/message)
                                                    │ 1. 事件→通知规则表（§4.5）
                                                    │ 2. 受众解析
                                                    │    C: userNo ｜ B: 门店×权限→staffNo ｜ P: 平台角色→opsNo
                                                    │ 3. 频控 + 订阅授权检查（MARKETING 类才限）
                                                    ▼
                          站内信（必发，落 msg_message，dedupKey = eventNo + receiver）
                                                    │
                          附加通道（尽力而为，失败只留痕不阻塞）
                            ├─ PushPort          App 厂商推送（小米/华为/OPPO/vivo/荣耀 + APNs）
                            ├─ WxSubscribePort   微信订阅消息（服务通知，mp-weixin C+B）
                            └─ SmsPort           短信兜底（仅强通知，一期不加新场景）
```

关键取舍：**站内信是事实记录、必达；其余通道都是加速器**。发送在 Outbox 消费侧异步执行，通道失败写 `sys_notify_log` 后放行——厂商通道抖动不该把事件卡在重试队列里，站内信保证最终可见。

### 4.2 方案选型

**决策 1 · 后端推送出口：聚合通道 vs 厂商直连**

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A：聚合推送服务商，一个 API 出口（推荐） | 后端只对接一家；厂商通道（小米/华为/OPPO/vivo/荣耀/魅族）与 APNs 在服务商控制台配置；离线走厂商系统通道、在线走长连接，自动路由 | 依赖第三方 | ✅ 采用。`PushPort` 隔离服务商，换商=换 gateway |
| B：逐厂商直连（小米 SDK + 华为 HMS + OPPO + … + APNs） | 无第三方 | 6+ 套对接、6 套证书轮换、6 套回执格式，与「单城市几百商家」规模完全不匹配 | ❌ |

聚合服务商候选：**个推**（uni-push 2.0 的底座）或 **极光 JPush**，能力等价。若决策 2 选 uni-app 打包则天然绑个推（uni-push），否则二选一，本文默认按个推写，`PushPort` 保证可换。

**决策 2 · App 生产形态（前置 ADR，三期开工前拍板）**

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A：uni-app 原生打包（HBuilderX 云打包/离线 SDK）+ uni-push 2.0（推荐） | b/c 两端本就是 uni-app，产物即真 App；uni-push 封装好厂商通道注册 + clientId 获取 + 点击深链，原生代码量≈0；iOS 打包即得 APNs | 需 DCloud appid 与云打包账号；受 DCloud 生态绑定 | ✅ 推荐 |
| B：现有 android-shell 演进为生产壳 + 聚合商原生 SDK + 自建 JS 桥 | 不依赖 DCloud | 要自建：clientId 桥、推送点击→H5 路由深链、前后台状态桥；支付/扫码等其它原生能力同样都得手写；iOS 壳从零起 | ❌ 除非 DCloud 路线被否 |

**决策 3 · 平台端（桌面浏览器）触达方式**

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A：轮询 unread-count（15s）+ 浏览器 Notification API（推荐） | 零新基建；页面开着就能弹桌面横幅（含最小化时）；实现半天 | 浏览器关掉收不到——运营工作时段 ops-web 常开，可接受 | ✅ 一期采用 |
| B：Web Push（Service Worker + VAPID） | 浏览器关了也能达 | 需推送订阅管理 + SW 生命周期 + 各浏览器差异；国内 Chrome 内核浏览器 FCM 依赖不可靠 | ❌ 观察一期效果再议 |
| C：WebSocket/SSE | 秒级 | 同 B 端结论：规模不匹配（TDD-backend §1 约束 8） | ❌ |

**B 端实时性**：30s 轮询 unread-count + App 推送响铃弥补到达延迟（WebSocket 二期有真实需求再上，理由同上）。

### 4.3 模块与接口设计

**新增 SPI**（`shop-base/spi/notify`，沿用 `SmsPort` 哲学——接口只说「发什么」，厂商模板号/通道概念不进领域）：

```java
/** App 推送。clientId 是聚合商设备标识，厂商路由由聚合商完成。 */
public interface PushPort {
    /** @param channel 提醒级别（NORMAL / RING——B 端新订单用系统通道高优先级+铃声） */
    SendResult push(String clientId, String title, String body, String link, String channel);
}

/** 微信小程序订阅消息（服务通知）。scene → 微信模板号的映射在通道配置里。 */
public interface WxSubscribePort {
    SendResult send(String openId, String scene, Map<String, String> params);
}
```

**通道实现**（`shop-channel/notify/port`）：`GetuiPushGateway`（个推 REST，透传厂商通道 intent 深链）、`WxSubscribeGateway`（`subscribeMessage.send`，一次性额度消耗后写回 `msg_subscribe`）、各配 Stub；`NotifyLoggingPushPort` / `NotifyLoggingWxSubscribePort` 装饰器留痕，模式与短信完全一致。`NotifyBizType` 新增 `TRADE_NOTIFY` / `BIZ_NOTIFY` / `OPS_NOTIFY`。

**shop-core/message 新增**：

- `NotificationConsumer implements OutboxConsumer`：吸收现有 `OrderEventConsumer`（3 个 case 平移进规则表，行为不变，原测试必须继续通过）。
- `MessageService`：收件人从 `userNo` 泛化为 `(receiverType: USER|STAFF|OPS, receiverNo)`；`list()/markRead()/unreadCount()` 按当前登录身份（双令牌池已区分）自动路由。
- `PushTokenService`：登录后上报 `(platform, clientId)`；退出登录**必须解绑**——共用设备的门店换班，前一个账号的订单不能推到下一个人的手机上。
- 受众解析：B 按 `merchant_no + store + 权限点` 查 staffNo（走 user 域 Port，不直依赖其 svc，ArchUnit 约束）；P 按平台角色查 opsNo。

**新增/改动表**（进 `V1__baseline.sql` 基线）：

```
msg_message      user_no → receiver_type + receiver_no；dedup 唯一索引改 (dedup_key, receiver_no)
msg_push_token   (receiver_type, receiver_no, platform ENUM(APP_ANDROID/APP_IOS),
                  client_id, updated_at, UNIQUE(receiver_type, receiver_no, platform))
```

**Portal 端点**：

| 端点 | 说明 |
|------|------|
| `GET /biz/message` · `/biz/message/{no}/read` · `/biz/message/read-all` · `/biz/message/unread-count` | 与 `/mp/message` 同形 |
| `GET /ops/message` 同形四件套 | ops-web 铃铛 |
| `GET /mp/message/unread-count` | c-app 红点 |
| `POST /mp/push-token` · `POST /biz/push-token`（含 `DELETE` 解绑） | App 登录/登出上报 |

**前端**：

- b-app：`pages/messages`（复制 c-app 同页改前缀）；tabBar 红点 30s 轮询（onShow 起、onHide 停）；App 端收到推送进前台时刷新列表。
- c-app：补未读红点；**订阅授权引导时机 = 支付成功页**，勾选「到货通知」等模板（一次性订阅每单收集一次，`msg_subscribe` 已支持记拒绝防反复弹窗）。
- ops-web：顶栏铃铛 + 下拉近 10 条 + 15s 轮询；首次进入请求 `Notification.requestPermission()`，高紧急事件（P-N-1/5/6）弹桌面横幅，点击跳对应工作台页。

### 4.4 频控与授权执行点

编排器发送前串两道检查（只作用于 `MARKETING`；`TRADE`/待办类不限——到货通知或新工单被频控拦掉是事故）：
1. `NotifyQuota`：日上限 + 同模板最小间隔（`msg_message.templateNo` 为此存在）。
2. `msg_subscribe`：订阅消息通道要求存在未消耗的同意记录，消耗后标记；无授权→该通道静默降级，站内信兜底。

### 4.6 平台限制与运维前置项（写进验收口径）

- **厂商通道逐家报备**：小米/华为/OPPO/vivo/荣耀各需厂商开发者账号 + 应用创建 + 通道申请（部分厂商审「消息分类」资质，交易类才给高优先级）；苹果需开发者账号 + APNs 证书/Token。全部在聚合商控制台完成配置，**不产生后端代码**，但周期以周计，三期开工前启动。
- **息屏可达仅 App**：小程序端做不到后台响铃（微信限制）。商家小程序在后台时，新订单提醒走订阅消息进「微信服务通知」；「息屏也响铃」只有 App（厂商系统通道）能承诺。对商家话术如实。
- 订阅消息是**一次性**授权，发一条耗一条；额度不足静默降级站内信。
- 现有 `android-shell` 定位是开发预览，**不承载生产推送**；生产 App 形态按决策 2 的 ADR 执行。

## 5. 测试策略

- 单元：规则路由、三类受众解析、频控拦截/放行、授权消耗、token 绑定/解绑。
- 场景（扩展 `M8MessageFlowTest` + 新 `BizNotifyFlowTest` / `OpsNotifyFlowTest`）：
  1. 真实链路：C 下单支付（走事件，**不直接调 push**）→ B 端有单权限员工 `/biz/message` 收到，无权限员工收不到；Stub PushPort 被以 RING 级调用；
  2. `mMarkArrived` 批量到货 → 用户收到**一条**（不是 N 条）+ Stub 订阅消息网关被调 + `sys_notify_log` 留痕；
  3. 工单创建 → 客服角色 `/ops/message` 可见；
  4. 事件重投 → dedup 挡住第二条；
  5. MARKETING 触发频控 → 拦 + 留痕；TRADE 不受限；
  6. 通道 Stub 抛异常 → 站内信仍在、事件不卡重试；
  7. 登出后解绑 token → 换账号登录不再收到前一账号的推送。
- 回归：现有 3 条 C 端消息平移后原测试全绿；按「真实链路验证」惯例，每条新逻辑撤掉修复必须变红。

## 8. 微信订阅消息全量接入（2026-09-29）

状态：**方案待确认** · 档位 1（每批各动模板号配置 + 场景码 + 种子迁移）

### 8.1 为什么现在做：一期上线一年，一条都没发出去过

线上实测（2026-09-29）：

```
notify_subscribe（订阅额度表）    0 行
sys_notify_log  channel=WXSUB     0 条
usr_store_favorite（店铺收藏）    0 行
```

一期的代码、模板号、通道全是通的（`SHOP_WX_SUBSCRIBE_STUB=false`，启动即校验凭据，
日志里「订阅消息通道已启用」），**缺的是没有一个真人点过那个授权弹窗**。

所以这一轮的目标不是「再多接几个通知」，而是**让这条链第一次真的跑起来**，
并且把「该通知什么」一次盘完，免得每次想起一个补一个。

### 8.2 三条硬约束（它们决定了方案的形状）

**① 只有一次性订阅。** 后台「长期订阅」那一栏写着「暂时没有可选用的模板」——
官方只向政务民生、医疗、交通、金融、教育等线下公共服务开放，生鲜电商拿不到。
「会员订阅（Beta）」要虚拟支付订阅制，也不适用。

**一次授权 = 一条消息，发完即止。** 这不是打折，是换了一种东西：
它是「一次预约」而不是「订阅关系」。

**② 授权必须由用户的点击行为触发**，且一次最多问 5 个模板、标题不能重复。
挪到 `onShow` 或定时器里会静默失败——弹不出来，也不报错。

**③ B 端不需要订阅消息。** 店主用的是 App（uni-push / 个推，见 §6 三期），
b-app 的 H5 只是调试用。微信订阅消息在这个系统里**只服务 C 端买家**。
这一条砍掉了一半的盘点范围。

> **推论**：瓶颈不在「哪些节点该通知」，在**「在哪几个点能拿到授权、每次换哪几条」**。
> 所以下面 §8.4 按「授权采集点」组织，而不是按通知节点组织。

### 8.3 先更正上一版清单的一个实质错误

第一版 §8.3 把「履约」等同于「自提」——只盘了「到自提点可取」这一条，
把「已取货」判成低价值（「人在自提点现场」）就过去了。

**线上数据说明这个前提是反的**（2026-09-29 查 `ord_sub_order`）：

```
MERCHANT_DELIVERY  COMPLETED       3    ← 真实成交全在这条链
EXPRESS            WAIT_FULFILL    1    ← 一单等着发货，挂着
EXPRESS            CANCELLED      20    （测试单）
STORE_PICKUP       （无）          0    ← 自提一单都没有
```

系统支持**三种**履约方式，自提只是其中之一，而且是生产上唯一**零使用**的那一种。
真实买家走的是商家配送与快递——**而那两条链上，从下单到完成，买家一条通知都收不到**。

### 8.3b 履约链路的通知缺口（本节是 8.3 的主体）

查证方式：`grep` 出所有 `eventBus.publish` 的调用点，与三条履约链的状态迁移逐个对。

| 履约方式 | 节点 | 谁改的状态 | 发事件？ | 站内信 | 订阅消息 |
|---|---|---|---|---|---|
| 自提 | 到自提点可取 | `FulfillmentQueryPortImpl` | ✅ `SubOrdersArrived` | ✅ | ✅（一次未发） |
| 自提 | 核销取货 | 同上 | ✅ `SubOrderCompleted` | ✅ | — |
| **商家配送** | **开始配送**（`/biz/order/*/ship`） | `MerchantOrderServiceImpl#ship` → `FULFILLING` | ❌ | ❌ | ❌ |
| **商家配送** | **已送达**（`/biz/order/*/delivered`） | 同上 → `COMPLETED` | ❌ | ❌ | ❌ |
| **快递** | **已发货**（含快递单号） | `#ship`（收 `expressNo`/`expressCompany`） | ❌ | ❌ | ❌ |
| **快递** | 已签收 | — | ❌ **无物流回调** | ❌ | ❌ |
| 全部 | 买家确认收货 | `OrderServiceImpl#confirmReceipt` → `COMPLETED` | ❌ | ❌ | — |
| 全部 | **待确认收货提醒** | — | ❌ **没有自动确认收货的 job** | ❌ | ❌ |

**三条要紧的事实**：

**① 这不只是「差几个订阅消息模板」。** `ship` 与 `delivered` **连事件都不发** ——
站内信没有、App 推送没有、消息中心里也查不到。补模板解决不了，
要先补事件（与 §10「新品开售提醒」那次一样，一半工作量在补事件）。

**② 「已送达」是全系统最该通知而没有的一条。** 商家配送把生鲜放在门口或前台，
买家不知道——东西会坏。自提那条链反而有通知，而自提零使用。

**③ 快递单发出去就挂住了。** 没有物流回调、也没有自动确认收货的 job，
`EXPRESS` 单 `ship` 之后停在 `FULFILLING`，除非买家自己想起来点确认。
线上那 1 单 `WAIT_FULFILL` 正挂着。这条会连带拖住结算。

### 8.3c 其余节点清单



**判据**：这个节点，用户**会不会离开小程序去等结果**。
会等的才值得用订阅消息（它的用途就是把人拉回来）；人还在页面上的，站内信足够。

| # | 节点 | 会离开等吗 | 价值 | 现状 |
|---|---|---|---|---|
| 1 | **到货，可去自提点取** | ✅ 会等一整天 | **最高** | 场景+模板+端上采集齐 · 从未发出 |
| 2 | **拼团成团** | ✅ 开团后就走了 | **高** | ❌ 成团**不发任何事件**，站内信也没有 |
| 3 | **拼团未成团（到期失败）** | ✅ 钱要退 | **高** | ❌ 同上（`GroupExpireJob` 只改状态） |
| 4 | **售后被拒** | ✅ 在等结果 | **高** | ❌ 无场景 |
| 5 | **退货单要寄回** | ✅ 有时限，不寄会自动关 | 中高 | ❌ 无场景 |
| 6 | ~~订单被取消 / 缺货~~ | — | — | **这个场景不存在，见 §12.1** |
| 7 | 售后超时自动处理 | ✅ | 中 | ❌ `AfterSaleTimeoutJob` 三条时限，不通知 |
| 8 | 未付款订单被自动关闭 | ⚠️ 未必在等 | 中 | ❌ `OrderAutoCloseJob`，不通知 |
| 9 | **收藏的店上新** | ⚠️ 营销类 | 中 | ✅ 2026-09-28 接入（本轮前一批） |
| 10 | 券即将过期 | ⚠️ 营销类 | 中 | ❌ 无 job、无场景 |
| 11 | 退款到账 | ❌ | — | **刻意不做**：微信支付自带到账通知，再发一条是重复 |
| 12 | 订单已支付 | ❌ 人就在支付结果页 | 低 | 站内信有；WXSUB 无模板也不需要 |
| 13 | 已取货（子单完成） | ❌ 人在自提点现场 | 低 | 站内信有，够了 |
| 14 | 会员等级变化 | ❌ | 低 | 不做 |

**结论**：把 §8.3b 的履约链算进来之后，值得上订阅消息的是——

1. **已发货 / 开始配送**（商家配送 + 快递，含快递单号）← 新，**最高**
2. **已送达**（商家配送）← 新，**最高**：东西在门口，生鲜会坏
3. 到自提点可取 ← 已接，**一次未发**
4. 拼团成团 / 未成团 ← 新
5. 售后被拒 / 要寄回 ← 新
6. 订单取消 / 缺货 ← 新
7. 收藏的店上新 ← 已接（§10）

「待确认收货提醒」暂不进订阅消息：它要先有自动确认收货的 job，
否则提醒了也没有兜底，单子照样挂着（见 §8.3b ③）。

### 8.4 采集点 × 模板配对（方案核心）

一次最多 5 个、标题不能重复，所以要把「用户此刻的动作」与「他将来会等的那件事」配起来：

| 采集点（用户的点击） | 问哪几条 | 理由 |
|---|---|---|
| **支付成功页**（已有） | **发货/送达** · 到货 · **成团/未成团** | 付完钱就走人，后面所有的等待都从这里开始。<br>**一次最多 5 个**，所以这里只放买家必然会等的那几条 |
| **开团 / 参团**（新） | **成团/未成团** | 团页是开团人唯一会反复回来看的页面；这里再问一次，补上从别处进来的人 |
| **提交售后**（新） | **售后结果（通过/被拒）** · **要寄回** | 提交那一刻是唯一能确定「他在等结果」的时刻 |
| **订单详情页**（新） | **发货/送达** · **订单取消/缺货** | 补上从别处进来、或在支付页拒绝过的人 —— <br>会点进订单详情的人，正是在等这件事的人 |
| **收藏店铺**（已有） | 新品开售 | §10 已落地 |

**不新增采集点**给「券过期」和「订单自动关闭」——
它们够不上「用户会离开去等」，为它们多弹一次窗会稀释前面几条的通过率。

### 8.4b 再更正一次：发货/送达**不该**由我们发订阅消息

拉下公共模板库（1818 条）之后才看清，已选的那两个模板是**特殊的**：

```
xh2lV45U50Ikkg6bGf1uYQWCiP…  购物（自提）服务动态      content 为空
xh2lV45U50Ikkg6bGf1uYaKHxpf…  购物（实体物流）服务动态  content 为空
```

`content` 为空、`getpubtemplatekeywords` 也取不到格 —— 因为它们**不是普通模板**，
而是微信**交易组件 / 发货信息管理**体系的「服务动态」：
商家调 `upload_shipping_info` 上报物流，**微信自己给买家推服务通知**，
既不需要我们调 `subscribeMessage.send`，也**不需要用户点订阅授权**。

所以 §8.4 把「发货/送达」排进支付成功页那 5 个名额是错的 —— 它们根本不占名额。

**而这条链我们早就建好了**：

| 件 | 状态 |
|---|---|
| 两个服务动态模板 | ✅ 已选进账号 |
| `WxShippingGateway` + `StubWxShippingGateway` | ✅ 已实现 |
| `ship()` / `delivered()` → `notifyShipping()` → `enqueue` | ✅ 已接线（`delivered` 那条是 2026-09-28 补的） |
| 生产开关 `SHOP_WX_SHIPPING_STUB` | ✅ `false`（真上报） |
| `trd_shipping_upload` 线上记录 | ❌ **0 行 —— 还没有任何订单走过这条新代码** |

与 §8.1 的 `notify_subscribe 0 行` 是同一个形状：**建好了，没跑过**。

**结论**：发货/送达这一段从「2 天开发」变成「半天验证」。
B 批的内容随之改为**验证 + 补缺口**，而不是从零接一套订阅消息。

### 8.5 注册计划（**自动**，不去后台点）

**已经不用手工点了** —— `scripts/wx-subscribe-templates.py` 把这件事做成了命令：

```bash
python3 scripts/wx-subscribe-templates.py categories        # 本账号的类目
python3 scripts/wx-subscribe-templates.py search 送达        # 按标题搜公共模板库
python3 scripts/wx-subscribe-templates.py keywords 17993     # 这个模板有哪几格
python3 scripts/wx-subscribe-templates.py add 17993 1,2,3 "订单送达后通知买家"
python3 scripts/wx-subscribe-templates.py mine               # 已选进账号的
```

两个设计要点，都不是可选的：

**① `access_token` 必须走 `stable_token`。** 老的 `cgi-bin/token` 每次调用都签发新 token
并挤掉旧的 —— 这个脚本一跑就会把**正在跑的后端**的 token 挤掉，
表现是线上随机 40001，而没有任何东西会指向「刚才有人跑了个脚本」。

**② 只能在生产服务器上跑**（微信对这些接口做 IP 白名单，开发机直连拿到
`40164 invalid ip ... not in whitelist`）。脚本检测到不在服务器上会**把自己传过去执行**，
在本机敲同一条命令即可。凭据只在服务器上读，不打印、不接受命令行传入。

**为什么不手工去后台点**：后台点完只留下一个模板号，没人知道当初为什么选它、
那几格分别映射到哪个业务字段。走脚本的话，`add` 的入参（tid + kidList + 场景说明）
本身就是决策记录，`search` / `keywords` 的输出可以贴进本文当依据。

搜索时挑**字段能填满**的那一个
（公共模板字段固定，挑一个有「商品/店铺名称」的，比只有「备注」的强得多；
字段填不满会被审核打回，或者发出去是一条看不懂的消息）：

| 要找的模板 | 搜索词 | 需要的字段 |
|---|---|---|
| **发货通知** | `发货` `订单发货` `物流` | 商品、快递公司+单号（**单号那一格是关键**，没有它这条通知等于只说了「发了」） |
| **送达通知** | `送达` `配送` `已送达` `同城配送` | 商品、送达时间、放在哪儿 |
| 拼团结果 | `拼团` `成团` `团购结果` | 团名/商品、状态、人数或时间 |
| 售后结果 | `售后` `退款结果` `申请结果` | 单号或商品、结果、原因 |
| 退货寄回 | `退货` `寄回` `物流` | 商品、地址或时限 |
| 订单异常 | `订单取消` `缺货` `订单状态` | 商品、原因、金额 |

⚠️ **已选模板的类目要对得上**：本小程序挂了 5 个类目
（家政服务 · 生鲜/初级食用农产品 · 3C数码 · 个护家清 · 玩具），
「新品开售提醒」当初是在 **3C数码** 下选的——能用，但换模板时要确认新模板的类目也在这 5 个里。

**产出**：每个模板拿到 `模板ID`，两边各配一次，**必须同值**：
后端 `WX_TPL_*`（`shop.wx.templates.*`）· 前端 `VITE_WX_TPL_*`。
不同值的症状是「用户点了允许、额度记下了、一条都发不出去」，两边各自看都像配好了。

### 8.6 对接计划

每批的形状与已落地的「新品开售提醒」完全一致，照着做即可：
SPI 加场景 + 三个实现（真网关/桩/留痕装饰器）+ `WxSubscribeSender` 一个方法 +
`NotifyScene` 一个常量 + `NotificationConsumer` 一个 case + 迁移种子 + 端上采集 + 场景测试。

| 批 | 内容 | 前置 | 估算 |

是因为它补的是三条链上的事件，且要同时接站内信与 App 推送（`ship`/`delivered`

## 9. B 批：履约链的通知（2026-09-29 已实现）

状态：**已实现** · 档位 1（新场景码 + 事件字段 + 种子迁移 V364）

### 9.1 补的是事件，不是订阅消息

§8.4b 已经查清：发货/送达的**微信通知**由交易组件的「服务动态」承担
（商家 `upload_shipping_info`，微信自己推，不占订阅授权额度），
而且 2026-09-29 已实测 `trd_shipping_upload` 走到 `SUCCESS`。

所以 B 批补的是**我们自己的**那一路：`ship` / `delivered` 此前**连事件都不发**，
于是站内信、App 推送、消息中心一并没有。两者不重复 ——
前者只在微信里，后者是消息中心与手机通知栏。

### 9.2 三条履约链说的话必须不一样

| 履约方式 | 发货/配送 | 走到终态 |
|---|---|---|
| 自提 `STORE_PICKUP` | —（到自提点那条已有） | 已取货 |
| 商家配送 `MERCHANT_DELIVERY` | **开始配送**（"商家已出发，请保持电话畅通"） | **已送达** |
| 快递 `EXPRESS` | **已发货**（"顺丰 SF123…，可在订单里查看物流"） | **已签收** |
| 不认识的 | — | 订单已完成（中性回落） |

**`SubOrderCompleted` 加了 `fulfillment` 字段**，消费端按它分文案。
不加的话三条链共用一句「已取货」—— 收到快递的人会以为自己去过某个自提点。
这正是「新枚举值漏进老分支」那类缺陷：不报错，只是对用户说错话。

**快递单号是发货通知的全部价值**：没有它，「已发货」只说了一件买家本来就在等的事。
自送没有单号，说的是时间（他要在家），所以另起一句话而不是发一条缺了单号的「已发货」。

### 9.3 种子只开 INAPP + PUSH，不开 WXSUB

`V364__notify_shipped_scene.sql`。不开 WXSUB 是因为微信那一路已有服务动态，
再发一条订阅消息既重复、又白耗用户的一次性授权额度。
PUSH 用 `NORMAL` 不用 `RING` —— 买家不该被震醒去接一个还在路上的包裹。

### 9.4 判据

`ShipNotifyFlowTest` 5/5。消融「按履约方式分文案」→ 2 条变红
（`completionWordingDependsOnFulfillment`、`unknownFulfillmentFallsBackToNeutral`）。

## 10. C 批：拼团结果的通知（2026-09-29 已实现）

状态：**已实现** · 档位 1（新场景码 ×2 + 事件 + 库表列 + 种子迁移 V365）

### 10.1 拼团是唯一「必须离开去等结果」的玩法

开团的人把链接转出去之后就退出小程序了。团成没成、钱退没退，
此前他只能自己想起来回去看 —— 成团那条原子 UPDATE 与 `GroupExpireJob`
**都不发事件**，连站内信都没有。

而 `group-expire` 这个任务在运营端**还是关着的**（今天一并开了，见 §8.6b 的清单），
所以到期的团连状态都不会变。两件事叠起来：**开了一个没人凑够的团，
钱扣着、状态不动、一条通知都没有。**

### 10.2 幂等挂在 `notified_at`，不挂在「状态是不是 FORMED」

成团发生在 `GroupJoinPortImpl` 的一条原子 UPDATE 里：

```sql
status = CASE WHEN status = 'OPEN' AND joined_count + 1 >= min_count
              THEN 'FORMED' ELSE status END
```

**每个后付的人都会再走一遍**，团照旧是 `FORMED`。挂在状态上的话，
第 5、第 6 个人付款时会再通知一遍全团。

挂在 `mkt_group_buy.notified_at`（V365）上则天然幂等：
带条件 UPDATE 只有一个线程能把它从 NULL 改成非 NULL，抢到的那个负责发事件。
与 `prd_goods.new_notified_at`（V356）同一个套路。

### 10.3 一条事件、两个场景码

`MarketingEvents.GroupSettled` 用 `status` 分，`eventType()` 据此返回
`GROUP_FORMED` / `GROUP_FAILED`。发布点是同一处（团的状态机），
分成两个 record 会让发布方多一个分支，**而那个分支迟早会漏掉一边**；
消费端要分文案，那是消费端的事。两个场景码分开登记，运营可以分别开关。

**名单直接放进事件**：团规模有界（`min_count` 通常个位数），
不必为此新开一条跨域查询。

### 10.4 未成团那条要把退款说出来

```
成团    「阳光玫瑰青提 3 人团」已成团，等商家发货
未成团  「阳光玫瑰青提 3 人团」人数没凑够，货款将原路退回
```

人关心的不是「没成」，是**「我的钱呢」**。不说的话他会来问客服，
而答案本来就该写在通知里。

### 10.5 不开 WXSUB

这两条要发给**全团的人**，而订阅消息是一次授权一条 ——
团里多数人没在这个场景下授权过，发出去大半会被 43101 拒。
真要上，得先在开团/参团页收集授权（§8.4 的采集点表里列了这一条）。

### 10.6 判据

`GroupNotifyFlowTest` 5/5。消融「幂等」→ `secondCallDoesNotNotifyAgain` 变红。

写测试时踩到同一个坑的两面，都是「逻辑删除仍占唯一键」：

**其一**：mapper 的 `delete` 是**逻辑删除**，
而 `uk_group_no` 是**不带 deleted 的**唯一键 —— 清理过的行照样占着号，
下一个用例插同一个号就撞。那种失败报的是「唯一键冲突」，
与被测的东西毫无关系，很容易被当成「测试不稳」。改成每个用例一个团号。

**其二**（更隐蔽，而且它不是测试问题）：清理时**不要删站内信**。

`uk_msg_dedup` 是**单列**唯一键（不含 `deleted`），而 `MessageServiceImpl#pushTo`
的查重走 MyBatis-Plus 的逻辑删除过滤 —— **查重看不见软删的行，唯一键看得见**。
于是「查重说不存在 → insert → 撞唯一键 → DuplicateKeyException」，
事件被 OutboxDispatcher 无限重投。

**它不在本类里报错**：重投把 `sys_outbox.retrying` 顶起来，
最后变红的是别人家的 `OpsLinkHealthFlowTest`（它判「投递任务是不是停了」，
retrying 非 0 会先落到 `CONSUMER_FAILING`）。**跨类的假失败就是这么来的**，
而错误信息指向一个与真因毫无关系的地方。

这是**生产缺陷**而不是测试问题，只是线上还没有删站内信的路径所以触发不到，
已单独记案。测试侧改成**用例级唯一的收件人号**，不再制造软删行。

## 11. D 批：售后结果的通知（2026-09-29 已实现）

状态：**已实现** · 档位 1（新场景码 ×2 + 事件 + 种子迁移 V366）

### 11.1 两件都是「买家正在等的结果」

| 节点 | 此前 | 现在 |
|---|---|---|
| 商家驳回 | ❌ 不发事件，买家不知道自己被驳回了 | 「售后未通过」+ **商家说明** |
| 同意退货、等寄回 | ❌ 不发事件 | 「请寄回商品」+ **说明有时限** |

### 11.2 驳回必须把理由带上

只说「被拒了」，买家不知道下一步能做什么 —— 他要么放弃（我们少了一次挽回），
要么来问客服（多一通电话）。商家没写理由时也要指一条路：
「可在售后详情里申请平台介入」，而不是让他盯着一句「未通过」。

不寄回会被 `AfterSaleTimeoutJob` 自动关单（那条时效 2026-09-27 才加上），
而买家会以为「同意了就等着收钱」——**他是在毫不知情的情况下错过那个时限的**。
文案里同时点出「填写快递单号」：少了这一步，寄回去了系统也不知道。

### 11.4 不开 WXSUB

本小程序没有对应的报备模板（公共模板库里退款/售后那一类不是每个类目都有，见 §8.5），
端上也没有在提交售后时收集过这两条的授权。等模板与采集点都就位再开 ——
那是 §8.4 采集点表里「提交售后」那一行的事。

### 11.5 判据

## 13. 推送时机现状对账（2026-10-09 生产实查）

> 起因：用户实测一单（虹选盐，真微信支付）后反馈「下单后消费者和商家都没收到通知，只收到一个发货通知」。

### 13.1 C 端（买家，都在微信小程序里）

| 时机 | 事件 | 站内信 | 个推 | 微信订阅 | **买家实际收到** |
|---|---|---|---|---|---|
| 支付成功 | `ORDER_PAID` | ✅ | ❌关 | **无此渠道行** | 只有站内信（静默，进消息中心） |
| 已发货 | `SUB_ORDER_SHIPPED` | ✅ | ✅开但无效 | ❌关（无模板、无发送方法） | **微信「发货信息录入」自带通知** —— 用户收到的那条就是它，不是本系统发的 |
| 到货自提 | `ORDER_ARRIVED` | ✅ | ✅开但无效 | ✅开 + 模板✓ + 支付页收授权 | **本该通，实际发不出** —— 见 13.3 缺陷 ③ |
| 订单完成 | `SUB_ORDER_COMPLETED` | ✅ | ❌关 | 无 | 站内信 |
| 退款成功 | `AFTER_SALE_REFUNDED` | ✅ | ❌关 | ❌关 + **模板号为空** | **全链路死** —— 见缺陷 ① |

发货由微信「发货信息录入」覆盖，支付成功买家刚在微信里付完、再推一条是冗余。

### 13.2 B 端（商家，原生 APK，走个推）

| 时机 | 事件 | 站内信 | 个推 | 实际 |
|---|---|---|---|---|
| 新订单（已付） | `SUB_ORDER_PAID` | ✅ | ✅ RING | 我方 `SENT` 成功；**到达取决于厂商通道**，见缺陷 ② |
| 售后申请 | `AFTER_SALE_APPLIED` | ✅ | ✅ | 同上 |
| 新评价 | `REVIEW_CREATED` | ✅ | ✅ | 同上 |

### 13.3 review 代码发现的四个缺陷

**① 退款通知全链路死（三处都缺）**
`WX_TPL_REFUNDED` 生产为空、`c-app/.env` 没有 `VITE_WX_TPL_REFUNDED`、`notify_scene_channel`
里 `AFTER_SALE_REFUNDED/C_USER/WXSUB` = 0。三处任一缺失都发不出，现在三处全缺。
退款是买家最在意的一条。**要先在小程序后台申请退款类服务模板**（§三 的合规约束同样适用），
拿到模板号后两端同值配置 + 打开渠道开关。

**② 商家个推的厂商通道从未报备（§4.6 的行政前置项至今未完成）**
代码侧没问题：`GetuiPushGateway` 已按 `settings.strategy.default=1` 请求「在线走长连接、离线转厂商通道」，
`channel_level=4` 走紧急通知栏。但厂商通道要在个推控制台逐家报备（华为/小米/OPPO/vivo/荣耀），
**不报备则 APP 退到后台或息屏就收不到** —— 这正是商家说「没收到新订单」的直接原因。
§6 三期已标注「真机验收待行政项」，该项至今未闭合。

**③ 订阅授权从未收集成功 —— 到货模板一次都没授权过**
`notify_subscribe` 全表只有 1 行（新品模板，2026-09-29，`quota=0`）；**到货模板 0 行**。
日志里 `/mp/message/subscribe` 近三天（含 01:58 那笔真实支付）**一次都没被调用**。
即「到货」这条配齐了模板、开关、代码，却因为**没有授权额度**而永远发不出。

根因在调起时机：`pay/index.vue` 在 `await requestPayment(...)` 与 `await api.orderDetail(...)`
**两个 await 之后**才调 `requestSubscribe`，而微信要求 `requestSubscribeMessage`
**由用户点击手势直接触发**（该文件 `fail` 分支的注释自己写着「2.8.2 起必须由点击行为触发」）。
手势上下文在 await 之后已失效 → `fail` → 返回空数组 → 两个 `if (r.xxx.length)` 都不成立
→ **不上报、不记日志、界面无任何异常**。三种完全不同的原因（模板没配 / 用户拒绝 / 弹框没调起）
收敛成同一个症状「什么都没发生」。

> 待真机复验：`fail` 分支会把 errCode 打进 console（20004 = 用户关了订阅消息总开关）。
> 要在真机开控制台看一次，才能区分「手势失效」与「用户把总开关关了」。

**④ 买家侧的个推开关开着但永远到不了（白跑，不报错）**
`notify_push_token` 里 `receiver_type=USER` **0 台**（只有 3 台 STAFF，其中 1 台在用）。
买家都在小程序里，拿不到个推 CID。而 `SUB_ORDER_SHIPPED` / `ORDER_ARRIVED` /
`AFTER_SALE_REJECTED` / `_RETURN_WAIT` / `GROUP_FORMED` / `_FAILED` 六个场景的
`C_USER/PUSH` 都是开的 —— 每次都走一遍推送分支、查不到设备、静默结束。
不造成错误，但让「这条通知发过了」在日志上看起来成立。

### 13.4 结论

- 用户收到的那条「发货通知」来自微信发货信息录入，**我方通知系统这一单实际一条都没送达买家**。
- 买家侧唯一可用的真实触达是微信订阅消息，而它卡在缺陷 ③（没有授权额度）。
- 商家侧卡在缺陷 ②（厂商通道未报备），属行政项，不产生后端代码。
