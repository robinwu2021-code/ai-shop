## 二、方案

### 2.1 一句话

> **买家问的永远是「这一个小区（或这一个区）」。** 所以从小区出发反查：
> 先问商家域「哪些门店服务这里」，再问商品域「这些门店在卖什么」。
> 两个问题各自只读几十行配置，谁都不用把两万多个小区预先展开。

### 2.2 拆成两个问题，各归各的域

```
                   ┌──────────── 商家域（MerchantQueryPort）────────────┐
小区号 / 区划码 ──▶ │ servingStores(community)                            │──▶ { 主体号 → [门店号…] }
                   │  主体 ACTIVE ∧ 门店 ACTIVE ∧ ReachRule.covers(店, 小区) │
                   └────────────────────────────────────────────────────┘
                                          │  只传「号」，不跨域 join
                   ┌──────────── 商品域（GoodsServiceImpl）──────────────┐
                   │ on_sale=1 ∧ audit_status=APPROVED ∧ entity_no IN (…)  │──▶ 商品号 + 由哪家店提供
                   │ ∧ ( 这件货一条店级行都没有                              │
                   │     ∨ 存在 store_no IN (服务门店) 且 on_sale=1 的店级行 )│
                   └────────────────────────────────────────────────────┘
```

**不写跨域 SQL join。** 评审时在生产上验证用的那条 SQL 把 `prd_goods` 和 `mch_*` join 在一起，
所以撞上了字符集不一致（1267），也违反域边界（`ArchitectureTest` 管的就是这个）。
这里商家域先用 Java 算出门店号，再作为参数传进商品域的查询，**字符集问题就不存在了**，
不需要统一字符集的迁移。

### 2.3 规则只有一个出处：`ReachRule.covers`

现在「某家店送不送得到某个小区」只能**正着展开**：`reachableCommunities` 把范围展开成小区清单。
反查要的是一个**判定**：给一家店、一个小区，回答是或否。

新增纯函数（商家域，`shop-merchant/.../merchant/reach/ReachRule.java`）：

```java
record CommunityRef(String communityNo, String regionCode, String parentNo, boolean open) {}
record StoreReach(Set<String> channels, String legacyReach,          // 渠道集合；空 = 回落旧列
                  List<Area> activeIncludes, List<Area> excludes,     // 主体范围
                  Set<String> subsetAreaNos /* null = 不裁剪 */) {}

static boolean covers(StoreReach s, CommunityRef c)
```

`reachableCommunities(merchant, store)` 也改成「开放小区里 `covers` 为真的那些」，
**下单（B4）和可见性用同一个函数**。现在「两套口径」这个问题就是这样从根上消失的，
不靠事后对账。

#### 搬规则时容易漏的地方（逐条从现有代码读出来）

我在评审时用 SQL 复刻漏过两次，下面每一条都要有一行判定用例：

| # | 规则 | 出处 |
|---|---|---|
| R1 | 主体非 ACTIVE（含 `PENDING_LICENSE`）→ 谁也看不到 | `reachableCommunities` :210 |
| R2 | **门店非 ACTIVE → 这家店不算**（`reachableCommunities` 自己不查门店状态，是 `storesSelling` 用 `activeStoreNos` 筛的） | `MerchantGoodsServiceImpl` :2873 |
| R3 | 渠道集合为空 → 回落 `fulfillment_reach` 旧列（SHIPPING / PICKUP / 其它） | :229 |
| R4 | 快递开着且**没有 ACTIVE 的 INCLUDE** → 全部开放小区减去 EXCLUDE | :266 |
| R5 | INCLUDE 只认 `status=ACTIVE`；**EXCLUDE 不看 status**（待审的排除也立即生效） | :259 与 :270 |
| R6 | 门店 SUBSET：取该店所有 SUBSET 路的 `area_no` **并集**，再与主体 INCLUDE 取交；`null`（没有 SUBSET 路）和空集含义不同 | `storeSubsetAreaNos` :452 |
| R7 | 裁剪后 INCLUDE 为空：开了自送 → 全部开放小区减 EXCLUDE；只有自提 → 空 | `reachOf` :368 |
| R8 | COMMUNITY 级 INCLUDE：**引用的那个小区本身不检查是否开放**，它的子级只取开放的，而且只往下一层 | `expand` :400 |
| R9 | STREET / DISTRICT / CITY 级：区划码前缀匹配，只取开放小区 | `expand` → `openCommunityNosUnderRegion` |
| R10 | EXCLUDE 的展开与 INCLUDE 用同一套规则（排除园区 = 排除它的楼栋） | `minusExcluded` :430 |
| R11 | 商品没有任何店级行 → 主体下所有 ACTIVE 门店都算在卖；有店级行 → 只有 `on_sale=1` 的那几家 | `storesSelling` :2872 |

R8 是最容易写错的一条：「判定」写法会自然地写成 `c.open && …`，结果就和现在不一样了。
**这些细节在第四节阶段 1 里先原样搬过来，有没有道理以后再说。** 搬的时候顺手修正，就没法对账了。

### 2.4 每条读路径改后怎么算

| 功能 | 改后 | 量级（今天） |
|---|---|---|
| B1 按小区 | 读 1 个小区的 `(region_code, parent_no, open)`，读平台全部 ACTIVE 主体的配置（4 张小表，共约 28 行），在内存里判定，再查一次商品 | 5 次小查询 |
| B1 按区县 | 读该区开放小区的 `CommunityRef`；对每家店**找到第一个命中就停** | 区里几千个小区 × 5 家店，在内存里 |
| B2 哪家店提供 | 本页商品（20 件）的店级行 ∩ 服务门店 → 默认店优先，否则门店号最小 | 1 次查询 |
| B3 送不送得到 | `servingStores(小区)` 中属于这件货主体的门店 ∩ `storesSelling(这件货)` 是否为空 | 2 次小查询 |
| B5 供给分布 | 每家 ACTIVE 门店算一次 `reachableCommunities`（现在重建时就要算），按门店聚合商品数 | 与今天重建池的「可达」那一步同量级（约 0.3 秒），只在运营打开这一屏时发生 |
| B6 合并小区 | **商品域什么都不用做**；`mch_service_area` 的引用由商家域那一份 `MerchantSettlementRefPortImpl` 改掉 | — |

**按区县查反而会更快。** 现在的做法是用 `IN (该区几千个小区号)` 去查池，把每个小区的每一行都读回来
（几千 × 十件货 = 上万行），再在 Java 里去重。

### 2.5 排序：`sort_weight` 没有任何读方

池行写入时会算距离、写进 `sort_weight`，但全仓库**没有一处读它**：

- `poolStoreOfGoods` 的选店规则是「默认店优先，否则按门店号」，不看距离。
- 列表按销量排（`orderByDesc(sales)`）。

保存设置那 20 秒里最大的一块就是 `distancesFor`，而它算出来的数是写给没人读的列用的。
**改后不算距离**，行为不变。以后真要「就近」，就在服务门店的那几家上实时算，那是另一单。

### 2.6 不改的

| 不改 | 原因 |
|---|---|
| `prd_store_goods` 的播种（A9） | 那是**真源**（门店卖不卖这件货），不是派生数据。它播种是因为「没有行 = 全部门店在卖」这个三态语义，改语义会影响新开门店的默认值 —— 这是产品决策，见第六节 |
| `NewGoodsOnSale` / `GoodsOnSaleChanged` 两条事件 | 它们描述的是商品自己的状态变化，原则上该留；只是挪出 `syncPool`，见 F5 |
| `mch_entity_community` | 旧的手工勾选小区表，可见性已不读它 |
| 主体总闸回算（`prd_goods.on_sale` 由各店在架行推出） | 同属「从别的行推出来再写下」，和播种一起处理，见第六节第 2 条 |
| 下单那道闸 | 本来就是实时算的，只是换成调用同一个 `covers` |

### 2.7 规模边界

每次 C 端请求都读**全平台** ACTIVE 主体的范围配置。今天是 6 个主体、28 行。
上千个主体时要换成按区划前缀建索引（`idx_service_area_ref(level, ref_code)` 已有），
或者加一层短 TTL 缓存。**现在不加缓存**：缓存正是「设置改了、读到旧值」的又一个来源，
需要它的时候再加，而且到那时会有量测数据。

### F0 可达判定（公共能力）

**现在**：「某家店送不送得到某个小区」只能正着展开，`reachableCommunities` 把范围展开成小区清单。
规则分散在商家域 5 个方法（`reachableCommunities` / `reachOf` / `expand` / `minusExcluded` / `storeSubsetAreaNos`）
和商品域 2 个方法（`storesSelling` / `activeStoreNos`）里。我在评审时用 SQL 复刻漏过两次。

**改后**：一个纯函数 `ReachRule.covers(门店配置, 小区)` 回答「是 / 否」。
正向展开和反查都基于它：正向 = 在开放小区里筛出 `covers` 为真的；反查 = 给定一个小区，筛出 `covers` 为真的门店。

| 阶段 | | 位置 | 改动 |
|---|---|---|---|
| 1 | ➕ | `shop-merchant/.../merchant/reach/ReachRule` | `covers`、`CommunityRef`、`StoreReach`；R1–R11 原样搬过来（见 2.3），**搬的时候不改规则** |
| 1 | ➕ | `shop-merchant/.../merchant/reach/StoreReachLoader` | 一次读 4 张配置表，组装每家门店的 `StoreReach` |
| 1 | ➕ | `CommunityQueryPort#communityRef` / `#openCommunityRefsUnderRegion` 及实现 `CommunityQueryPortImpl` | 返回小区号、区划码（`region_code`）、上级号（`parent_no`）、是否开放。三列在 `cmt_community` 里都有，不加列 |
| 1 | ✏️ | `MerchantPortImpl#reachableCommunities(m, s)` | 内部改为调用 `covers`，签名和返回值不变 |
| 2 | ➕ | `MerchantQueryPort#servingStores(小区)` / `#servingStoresInRegion(区划)` | 反查「哪些主体的哪些门店服务这里」，同时过滤主体 ACTIVE（R1）和门店 ACTIVE（R2） |
| 4 | ➖ | `reachOf` / `expand` / `minusExcluded` | 旧实现，等价对照用完后删除 |

### F2 经营范围（A2 商家改范围，A3 运营审核范围）

**现在**
- A2：`MerchantStoreServiceImpl#replaceAreas` 写完 `mch_service_area` 后重建池。
