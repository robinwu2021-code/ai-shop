# TDD-B 端员工与授权改版（自定义角色 + 审计）

[三端角色权限功能对齐清单](../../requirements/三端角色权限功能对齐清单.md) §四 §十一（**本方案推翻其中一条**）
上游方案：[TDD-B端权限对接整改](./TDD-B端权限对接整改.md)（六角色判权与审计落库已完成）
创建日期：2026-08-12

---

## 1. 需求摘要

「员工与授权」现在能用但不好用，且缺两块能力。三条要求：

1. **员工管理** —— 认得出人、找得到人、看得懂他现在能做什么
2. **角色管理** —— **商家可自定义角色**（2026-08-12 拍板，见 §3.0）
3. **审计** —— 「今天谁动过权限」要能直接看到，而不是逐个人点开

验收标准：老板在这一页能回答三个问题 ——
**「这些人都是谁」「某个角色到底能干什么」「上周三谁把张三提成了店长」**。

---

## 2. 当前形态与它的六个问题

现状：一页平铺，每个员工一张卡，点「改授权」展开 `门店 × 角色` 的 chip 矩阵。

| # | 问题 | 后果 |
|---|---|---|
| 1 | 列表只有脱敏号 `139****1111` | **三个人以后谁也分不清** |
| 2 | 角色只有名字，没有说明 | 老板不知道「理货员」能干什么，只能猜着给 |
| 3 | 「更多角色」二次折叠 | 一半角色（理货/配送/客服）默认看不见 |
| 4 | 没有搜索、没有状态筛选 | 人一多只能翻 |
| 5 | 变更记录埋在每个人卡片里 | 「今天谁动过权限」看不到 —— 这恰恰是审计最常被问的一句 |
| 6 | 入口在工作台第二屏，「我的」里没有 | 找不到（用户实际反馈） |

> ⚠️ 1 与 5 是这次改版的**主要价值**；2 在允许自定义角色之后变成必答题。

## 3. 方案设计

### 3.0　自定义角色 —— 推翻了什么，以及不能一起推翻的是什么

**推翻的**：需求 §十一「不做什么」中的
「让商家自定义**权限码**（13 列勾选矩阵）—— 角色是答案，权限码矩阵是把问题还给他」。
本次改为：**商家可以建自己的角色并勾权限码**。§十一 那一条随本方案一起改掉。

**不能一起推翻的（硬边界，写死在后端 + 测试）**：

| 边界 | 为什么 |
|---|---|
| **自定义角色不得包含 `biz:store:admin`** | 那是「管人」的码。给出去 = 被授权者能改所有人的授权、能给自己加任何角色 —— **一次授权就绕开了整个模型**。需求 §4.5 ② 的原话：「授权别人 = 扩散权限」 |
| 自定义角色不得是 `*` | 通配只属于 OWNER，且 OWNER 不走这张表 |
| 预置 6 角色**只读** | 新增权限码时预置角色的语义要保持稳定；商家要改就「复制为自定义角色」 |
| 角色码全主体唯一，且不得与预置码同名 | 同名不同义是本项目反复在治的病 |

`biz:finance` **允许**授出：「让会计看账」是真实诉求，且它只看不改结构。
店长仍然默认没有它 —— 老板要给，得显式建一个带 finance 的角色，那是他的明示意图。

### 3.1　数据模型

```
mch_role（新，V71）
  entity_no      商家主体；预置角色用 '*'（全局共享，只读）
  role_code      角色码。预置：OWNER/MANAGER/…；自定义：R + 业务键
  name           显示名（「夜班店长」）
  perms          JSON 数组，权限码
  builtin        1 = 预置只读
  唯一键 uk_role(entity_no, role_code)

mch_account 加一列（V71）
  display_name   备注名。列表与审计都显示它 —— 一列尾号谁也分不清
```

`mch_store_role.role` **不变**（仍存角色码字符串），所以已有授权与判权链路的形状不动。

### 3.2　判权链路：在哪一步把「角色」换成「权限码」

现在：`BizContextFilter` 解析出 `rolesByStore` → `BizContext.can()` → `BizPerms.can()`（**静态表**）。

| 方案 | 做法 | 缺点 | 结论 |
|---|---|---|---|
| **A 在 Filter 里算好 permsByStore** | 解析角色时顺带 join `mch_role`，Context 里直接存**权限码并集** | 每请求多一次查询（与现有角色查询同批，可一次 join 完） | ✅ 采用 |
| B 判权时再查库 | `BizPerms.can` 改成读库 | 每个 `@PreAuthorize` 一次查询；且判权点在事务外，缓存失效难写对 | ❌ |
| C token 里带 perms | 登录时算好写进会话 | **改了角色的权限，已登录的人不生效** —— 而「收回权限」必须立刻生效 | ❌ |

方案 A 顺带解决了「改完立刻生效」：Filter 每请求跑一次，读的是库。

`BizPerms.ROLE_PERMS` 的定位随之变化：**从「判权的真源」变成「预置角色的种子」**。
新增一条守卫钉住二者一致（否则库里的预置角色与代码里的说明会分叉）。

### 3.3　接口

| 端点 | 权限 | 说明 |
|---|---|---|
| `GET /biz/roles` | `biz:store:admin` | 本主体可用角色（预置 + 自定义），**每个角色带权限码与中文说明** |
| `POST /biz/roles` | `biz:store:admin` | 建自定义角色。拒绝含 `biz:store:admin` 的 perms |
| `POST /biz/roles/{roleCode}` | `biz:store:admin` | 改名 / 改权限码。预置角色拒 |
| `POST /biz/roles/{roleCode}/delete` | `biz:store:admin` | 删除。**仍被授权的角色不许删**（否则那些人的权限凭空消失） |
| `GET /biz/staff/logs` | `biz:store:admin` | 已有。加 `action` 筛选 |
| `POST /biz/staff` | `biz:store:admin` | 已有。加 `displayName` |

**角色说明谁来写**：预置角色的中文说明从 `BizPerms` 的字段注释生成（与两份矩阵同源），
自定义角色显示「勾了哪几个码」。**前端一个字都不抄** —— 抄一份就会漂。

### 3.4　界面：三段式列表 + 两个详情页

> **「一切都塞在列表里」正是现在不好用的根因**：一张卡片里同时要放
> 身份、状态、角色摘要、门店 × 角色矩阵、变更记录 —— 于是矩阵被压成两行 chip、
> 「更多角色」被折起来、记录只能按人看。**该分页的分页。**

#### 列表层：顶部三个 tab

**员工 tab**
- 搜索（备注名 / 尾号）+ 状态筛选（在职 / 已停用）
- 每行只放认人与决策要的四样：**备注名 · 脱敏号 · 状态标 · 一句话摘要**
  （他在各店的角色并集，如「文三路店 店长 · 古墩路店 店员」）
- 点整行 → **员工详情页**。列表里不再内联展开

**角色 tab**
- 预置 6 个（只读）+ 自定义，每行：角色名 · 权限条数 · **现在几个人在用**
- 点整行 → **角色详情页**
- 底部「+ 新建角色」；预置角色行上有「复制为自定义角色」——
  从预置起步比从空白勾 13 个码容易得多

**审计 tab**
- 全量倒序流水，可按人 / 按动作筛
- 每条：时间 · 谁 · 对谁 · 做了什么（结构化渲染，不显示原始码）

#### 员工详情页（`pages/staff-detail`）

一个人的全部，从上到下按「先认人、再看权、最后是危险动作」排：

| 区块 | 内容 |
|---|---|
| 身份 | 备注名（可改）· 脱敏号 · 状态 · 加入时间 · 是不是老板 |
| **门店 × 角色授权** | 矩阵搬到这里，一屏放得下：每家店一行，行内是角色 chip，可点开看这个角色能做什么 |
| 他现在能做什么 | 各店角色的**权限并集**，用中文列出来 —— 这是老板真正想确认的那句话 |
| 变更记录 | 只看这个人的（复用 `/biz/staff/logs?mchAccountNo=`） |
| 危险动作 | **停用**（保留授权，回来即用）· **移除某店授权**。两件事文案分开写清楚 |

#### 角色详情页（`pages/role-detail`）

| 区块 | 内容 |
|---|---|
| 角色名 | 自定义角色可改；预置角色只读并标明「平台预置」 |
| 能做什么 | 13 个权限码分组勾选（自定义）或只读展示（预置）。**`biz:store:admin` 直接不出现在可勾列表里**（§3.0 硬边界），并在页面上写明为什么 |
| 谁在用 | 持有这个角色的员工列表，可点进员工详情 |
| 删除 | 仅自定义且无人使用时可删；有人在用时按钮禁用并说明「还有 3 人在用」 |

#### 导航与入口

- `pages.json` 新增两页；两页都要有 `:denied="!merchant.can('biz:store:admin')"` ——
  **这不是可选项**：`biz-page-perm.test.ts` 会扫到新页面并要求它有门禁或写豁免理由。
- 「我的」补一个 cell（判 `biz:store:admin`），与结算、经营数据并列。
  现状唯一入口在工作台第二屏，用户实际反馈就是「没看到添加员工的功能」。

### 3.5　运营端展示商家与门店人员（追加需求）

运营要能看到「这家商家有哪些人、各在哪家店担任什么」。

**只读**：运营不改商家的授权 —— 那是商家自己的事，运营插手会让「谁给的权限」这条链断掉
（而审计正是为了这条链）。真要处置，走已有的封店/停用商家，不是替他改人。

| 项 | 方案 |
|---|---|
| 端点 | `GET /ops/merchant/{entityNo}/staffs` —— 复用 `MerchantStaffService.list`，多一层运营权限 |
| 权限 | 运营端权限码，取 `merchant:view` 一档（能看商家详情就能看他的人）。**不新增码** |
| 落点 | ops-web 商家详情页新增一个「人员」tab：备注名 · 脱敏号 · 状态 · 各店角色 |
| 脱敏 | 与 B 端同一口径（`StaffVO` 已脱敏）—— 运营也不需要商家员工的完整手机号 |

> ⚠️ **与并行会话冲突**：另一个会话正在改 `ops-web/` 与运营端 IAM（`platform/perm`、
> `sys_audit_log` 的 V70）。这一条落在同一片区域，**要么等他们那批合并后再做，
> 要么只做后端端点、前端页面留给他们那边一起排**。不并行改同一批文件。

## 5. 风险

1. **判权链路改造是本次唯一动到安全边界的地方**。缓解：Filter 一处改动、
   `BizPerms.can` 的签名不变（仍是「一组码 + 一个码」），先让新守卫红再变绿。
2. **自定义角色让矩阵产物不再完备** —— 两份矩阵只覆盖预置角色。
   产物里要显式写明这一点，否则它会变成一份「看起来全、实际不全」的表。
3. **迁移要把现有 6 角色写进 `mch_role`**，否则升级瞬间所有人的权限为空。
   迁移里做，且与 `BizPerms` 同源生成。

## 7. 实现记录

### ①② （2026-08-12）：迁移 + 判权链路

`mch_role`（6 个预置 `entity_no='*'` 只读 + 商家自定义）、`mch_account.display_name`；
`BizIdentityResolverImpl` 解析身份时把「角色」翻译成「权限码并集」放进
`BizContext.permsByStore`，判权那一刻仍是纯内存比较。

`BizContext.can` 先看 `permsByStore`，取不到回落 `BizPerms` ——
回落这条路留给六/七段式构造与单元测试，两者由 `BizRoleSeedTest` 钉住语义一致。

**新守卫 `BizRoleSeedTest`（3 条）**：迁移里的预置角色必须与 `BizPerms.ROLE_PERMS`
逐条相同、只能有 6 个 builtin、只有 OWNER 能带通配。
验证过它会咬人：把店长的 `biz:stock` 从迁移里删掉，立刻红。

#### 这一步被真实测试抓到两个错

1. **迁移注释里的引号把 DDL 劈成两半**。我在 `COMMENT` 里写了 `''*''`
   想强调那个星号 —— 而 SQL 里 `''` 是转义引号，字符串提前结束，
   生成出来的 `schema-test.sql` 变成
   `entity_no VARCHAR(64) NOT NULL'*''**（全局共享、只读）'`，
   整个 Spring 上下文起不来。**注释也是 SQL 的一部分。**
2. **`Map.of().get(null)` 抛 NPE，不是返回 null**。
   一个建了账号但一家店都没授权的员工，`currentStoreNo` 就是 null；
   而判权链路上抛异常的表现是 10500「系统开小差」，
   本该是最干脆的一个 70006。**红的那条恰好是「空角色 = 零权限」** ——
   安全性最关键的那条。

> 两个都不是「想不到」，是「不跑就看不见」。第二个尤其：
> 它只在「有账号、零授权」这个组合下出现，而那正是**新员工刚被加进来的那一刻**。

### ③④⑤⑥（2026-08-12）：端点 + 界面 + 运营端

b-app 拆成**三段式列表**（员工 / 角色 / 审计）+ **两个详情页**。列表层只回答
「这些人是谁 / 这个角色能干什么 / 上周三谁把张三提成了店长」，其余全在详情页 ——
上一版把身份、状态、角色摘要、门店×角色矩阵、变更记录全塞进一张卡片，
于是矩阵被压成两行 chip，而被折起来的恰好是理货/配送/客服这三个最需要区分的。

运营端：`GET /ops/merchants/{merchantNo}/staff`（`merchant:merchant:read`），
**只读，刻意不做写** —— 谁能进这家店是商家的雇佣关系，平台替商家改授权
等于替他决定谁能动他的钱；要处置走封禁，那是另一个层级、另一个权限码。
`OpsMerchantStaffViewTest` 里有一条专门盯着这件事：这条路径上出现写端点就红。

#### 中途改掉的三个决定

1. **手机号不再脱敏**（用户拍板）。原先的理由是「一份可导出的通讯录」，
   但它在这里站不住：手机号**就是员工的登录用户名**，
   老板要核对「他用哪个号登进去的」、人换号时要改 —— 脱敏之后这两件事都做不了，
   而号码本来就是老板自己填进去的。审计文案里仍然脱敏：
   那是长期留存、可能被导出的文本，它要回答的是「谁改了谁」，不需要完整号码。
2. **去掉员工详情页的「他现在能做什么」**（用户）。它是各店角色权限的并集，
   而同一份东西在角色详情页也有一份 —— 两处会各自漂移，且漂移的那份没人会发现。
3. **界面上不出现权限码**（用户）。`biz:stock` 对店主没有意义。
   端上有中/英/阿三份文案，后端下发的中文作兜底。

#### 又被生成器/守卫抓到三个

1. **可勾权限点少一条**。端上原先把 6 个预置角色的权限并起来当选项 ——
   `biz:finance` 只有 OWNER 有，而 OWNER 那行是 `*`，于是它被并没了。
   后端收这个码、界面却勾不到，**看起来像功能没做**。
   改成由 `/biz/role-perms` 下发（`BizPerms.assignableCodes()`，与建角色时的拒绝同一份定义）。
2. **`/biz/roles/{roleCode}` 违反资源单数规矩**（ADR-007），`gen:api` 直接拒绝生成。
   带 id 的那两条改成 `/biz/role/{roleCode}`。
   这条在写代码时完全没有症状 —— 契约生成器才是那道闸。
3. **审计里写的是角色码**。自定义角色的码是 `R2026…` 一串生成的业务键，
   写进日志等于这条记录三个月后没人读得懂。改成写显示名，
   `auditSpellsRoleName` 钉住；撤掉修复后它确实变红（日志里出现了那串码）。
