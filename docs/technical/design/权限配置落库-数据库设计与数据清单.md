## 0. 先说一个要你确认的冲突

你要求「**菜单中给出后端未实现的标识**」。而现在的做法是**隐藏** ——
`perm-map.ts` 里标 `UNIMPLEMENTED` 的一律判 `false`，菜单上不渲染，
理由写在那份文件里：「显示出来然后点出 404，比藏起来坏得多」。

**两者可以同时成立**，做法是：

| 做法 | 是否可点 | 结论 |
|---|:--:|---|
| 现在：隐藏 | — | 诚实，但**运营不知道平台规划了这个功能** |
| 你要的：显示 + 标识 | ❌ **禁用** | ✅ **采用** |
| 危险的做法：显示且可点 | ✅ | ❌ 点下去 404 —— 正是要防的 |

**渲染但禁用、并写明「后端未实现」**，与「不要死按钮」不冲突 ——
死按钮的定义是「看着能点、点了出错」，而禁用项从一开始就说明了自己不能用。

> 落到实现：菜单项照常出现在导航里，**灰显 + 角标「待建」**，
> 点击不跳转、鼠标悬停给一句「该功能后端尚未实现」。
> 这也让 §3 那 21 行数据在界面上真的有用武之地，而不是只躺在库里。

## 1. 表设计（4 张）

### 1.1 `sys_function` 功能（菜单分区）

```sql
function_code   VARCHAR(64)  NOT NULL   -- OPS_MERCHANT / BIZ_ORDER / MP_TRADE
name            VARCHAR(64)  NOT NULL
end_code        VARCHAR(8)   NOT NULL   -- OPS | BIZ | MP。三端同一套表
icon            VARCHAR(32)             -- 菜单图标（运营端 lucide 名）
href            VARCHAR(128)            -- 分区默认落地页
sort            INT          NOT NULL
enabled         TINYINT      NOT NULL DEFAULT 1
UNIQUE KEY (end_code, function_code)
```

⚠️ **`end_code` 进唯一键**：三端各有自己的 `ORDER`/`FINANCE`，
不带端做唯一键的话，B 端的「订单」和运营端的「交易订单」会撞码。

### 1.2 `sys_function_point` 功能点（菜单叶子 / 可授权的最小动作）

```sql
point_code      VARCHAR(64)  NOT NULL
function_code   VARCHAR(64)  NOT NULL
name            VARCHAR(64)  NOT NULL
group_name      VARCHAR(32)             -- 二级分组：「入驻与资质」「信用与处置」
href            VARCHAR(128)            -- 菜单跳转地址
ui_perm_code    VARCHAR(64)             -- 前端 UI 码（运营端 45 个细粒度码）
perm_code       VARCHAR(64)             -- **后端权限码**；NULL = 不受权限约束
backend_status  VARCHAR(16)  NOT NULL   -- IMPLEMENTED | NOT_IMPLEMENTED | NOT_APPLICABLE
ui_ready        TINYINT      NOT NULL DEFAULT 1
matrix_code     VARCHAR(16)             -- 需求编号 P-x.y，**可追溯到需求**
sort            INT          NOT NULL
UNIQUE KEY (point_code)
KEY (function_code, sort)
```

**三个字段专为「未实现标识」而设，缺一不可**：

| 字段 | 取值 | 界面表现 |
|---|---|---|
| `backend_status` | `NOT_IMPLEMENTED` | 灰显 + 「待建」角标，不可点 |
| `perm_code` | `NULL` | 不受权限约束（如经营看板），**谁都能看** |
| `ui_ready` | `0` | 后端通了但前端页面还没做完 |

> ⚠️ **`perm_code = NULL` 与 `backend_status = NOT_IMPLEMENTED` 是两回事**，
> 必须分开存：前者是「谁都能用」，后者是「谁都不能用」。
> 合成一个字段的话，经营看板会和风控页长得一样。

### 1.3 `sys_role` 角色

```sql
role_code   VARCHAR(32)  NOT NULL
name        VARCHAR(32)  NOT NULL
end_code    VARCHAR(8)   NOT NULL
builtin     TINYINT      NOT NULL DEFAULT 1   -- 平台预置，不可删
entity_no   VARCHAR(64)                       -- 非空 = 某商家自定义的角色
sort        INT
UNIQUE KEY (end_code, role_code, entity_no)
```

### 1.4 `sys_role_point` 角色 × 功能点

```sql
role_code   VARCHAR(32)  NOT NULL
point_code  VARCHAR(64)  NOT NULL
entity_no   VARCHAR(64)          -- 与 sys_role 一致，自定义角色才有值
UNIQUE KEY (role_code, point_code, entity_no)
```

### 1.5 `sys_role_member` 人员 × 角色（**本次新增**）

```sql
end_code     VARCHAR(8)   NOT NULL   -- OPS | BIZ | MP
subject_no   VARCHAR(64)  NOT NULL   -- 运营 staff_no / 商家 mch_account_no / 用户 user_no
role_code    VARCHAR(32)  NOT NULL
scope_no     VARCHAR(64)             -- 角色的作用域：B 端是 store_no，运营端为空
granted_by   VARCHAR(64)
granted_at   BIGINT
UNIQUE KEY (end_code, subject_no, role_code, scope_no)
```

**唯一键把 `role_code` 包含进来，这就是「一人多角色」的落点** ——
少了它就是「一人一角色」，而小店最常见的那种人是
「站收银台的顺手把货送了」（店员 + 配送员）。

> ⚠️ **上一版方案写的「人员→角色不建表」是错的**，理由也写错了
> （说 B 端已有 `mch_account_role`，实际那张表叫 `mch_store_role`）。
> 但结论要分两半看，查证之后是这样的：

| 端 | 现状 | 本次 |
|---|---|---|
| **B 端** | ✅ `mch_store_role` **已是关联表且已支持多角色** —— V18 专门把唯一键从 `(账号,门店)` 放宽成 `(账号,门店,角色)`，理由与上面一字不差 | **不动它**，`sys_role_member` 对 B 端只做视图口径 |
| **运营端** | ❌ `sys_ops_staff.roles` 是一个 **JSON 数组列** | **迁进 `sys_role_member`** —— 这是真正需要建表的那一半 |
| **C 端** | 身份按数据关系算出来 | 只在需要「按人开关能力」时才写行（本批不写） |

**为什么 B 端不合并进来**：`mch_store_role` 带着 `store_no` 这个作用域，
且已经在跑、有数据、有 `revive` 那套逻辑（逻辑删 + 业务唯一键的坑踩过三次）。
把它搬到新表 = 一次没有收益的数据迁移，还要重写那段逻辑。
**同一件事有两张表是问题，但「已经对的那张」不该为了整齐去动。**

> 落地时 `sys_role_member` 对 B 端提供一个**只读视图**
> （`SELECT 'BIZ', mch_account_no, role, store_no FROM mch_store_role`），
> 这样上层「查某人有哪些角色」只有一个入口，而真源仍是原表。

### 1.6 运营端的迁移：JSON 列 → 关联表

`sys_ops_staff.roles` 现在是 `["SUPER_ADMIN"]` 这样的 JSON。迁移三步：

1. V62 里把每个 staff 的 roles 数组**展开成行**写进 `sys_role_member`
2. 读侧改成查表（`OpsServiceImpl.login` / `me` / `staffList`）
3. `roles` 列**保留但停写**，标注「已迁移，勿再使用」——
   直接删列会让回滚变成不可能，而这批要改的是判权链路

> **为什么运营端值得迁**：JSON 列查不了「哪些人有 FINANCE 角色」——
> 而那恰恰是权限审计最常问的一句。今晚补七个角色时就想查，只能全表捞出来再解析。

## 2. 数据从哪来（生成，不手写）

| 数据 | 来源 | 为什么不手写 |
|---|---|---|
| 运营端功能/功能点 | `ops-web/lib/nav.ts` | 菜单树本身就是功能分解，且它每天在变 |
| `perm_code` 映射 | `ops-web/lib/perm-map.ts` | 权限码细化后**多数是恒等映射**，但 `UNIMPLEMENTED` 标记与少数真翻译仍在那里 |
| `backend_status` | 同上（`UNIMPLEMENTED` 标记） | **它已经是维护好的事实**，抄一遍必然过期 |
| `matrix_code` | `nav.ts` 的 `matrix` 字段 | 需求追溯 |
| 运营端角色映射 | `Perms.ROLE_PERMS` | 现在跑着的就是它 |
| B 端角色映射 | `BizPerms.ROLE_PERMS` | 同上 |

生成器：`ops-web/scripts/gen-perm-seed.mjs`。
`--doc` 把同一份数据渲染进本文档 §3（解析它自己刚生成的 SQL，
所以文档描述的**就是**种子本身）。

> ⚠️ 还有一条**生成器自己**的覆盖率约束：`Perms.ROLE_PERMS` 用到而
> `UI_PERM_MAP` 映射不出来的后端码，必须由末段「按后端码兜底」那一块补上功能点。
> 漏了的话，角色→功能点靠 `perm_code` 对不上，那条授权就**无处安放、静默消失** ——
> 2026-08-12 因此丢过 22 个码（FINANCE 一个角色 9/16）。
> `ops-web/lib/nav.test.ts` 与 `PermSeedParityE2eTest` 分别在生成器层与真库层守这条。

## 5. 落库后的读取路径

```
登录 → 查 sys_role_point（按角色）→ 得到功能点集合
     → 关联 sys_function_point 得到菜单树（含 backend_status / ui_ready）
     → 前端按 backend_status 渲染：IMPLEMENTED 正常 / NOT_IMPLEMENTED 灰显+待建
```

**判权仍走 `perm_code`**（`can()` 签名与行为不变）——
菜单是**展示**，判权是**拦截**，两者读同一份数据但用途不同。
