## 0. 这份清单要解决什么

终局只有三个候选，选错了要拆一年：

| | 方案 | 一句话 |
|---|---|---|
| **A** | 基座为主，行业补充 | 基座暴露接口，行业包只加自己的对象与附属入口（**当前 TDD 的形态**） |
| **B** | 行业统一入口 | 每个行业包是该行业商户的唯一 API 层，全部代理并调基座 |
| **C** | 按模块拆 | 差异大的模块（如商品视图、履约、结账）走行业接口，其余走基座 |

**这三个不能靠讨论选，要靠数据选。** 数据就是：**同一件事，三个行业的接口和流程到底差多少、差在哪。**

所以顺序必须是：**先定度量 → 逐行业盘 → 对比 → 选型**。
先拍架构再补论证，是这三个选项里最贵的一种错法。

本清单只定义工作，不预判结论。

## 2. P0 · 定度量与盘点模板

### 2.1 端点全表怎么来 —— 不手工列

仓库里已经有 `scripts/gen-api-index.mjs`：扫描后端 `@*Mapping` + 三份 OpenAPI + 各端 `endpoints.ts`，
产出 `docs/api/API清单.md`。**扩它，不另起一个。**

新增四列（人工填，但有默认推断规则）：

```
npm run gen:api-index     # 现有
node scripts/gen-industry-endpoint-inventory.mjs   # 新增：在 API 清单基础上加四列，输出 CSV/MD
```

> 按仓库规矩，这是**生成物**：改了源不重跑等于没改，且 pre-push 有闸门。

### 2.2 每个端点一行的字段（取值域必须先定死）

| 字段 | 取值域 | 说明 |
|---|---|---|
| `endpoint` | — | 方法 + 路径（路径参数归一 `{x}`） |
| `portal` | `mp` / `biz` / `ops` | 端 |
| **`subject`** | `order` `order_item` `goods` `sku` `stock` `member` `member_asset` `coupon` `settle` `store` `staff` `resource` `slot` `print` `after_sale` `pay` `platform` | **主语** —— 这个动作在改谁。**选型的核心维度** |
| `rw` | `R` / `W` | 读 / 写 |
| `external` | `Y` / `N` | 是否外部系统调（支付回调、物流回调、三方平台） |
| `cross` | `Y` / `N` | 一次调用是否可能跨多个商家/行业（如混合购物车下单） |
| **`food`** | `S/P/V/X/N` | 餐饮相对基线的关系（见 2.3） |
| **`beauty`** | `S/P/V/X/N` | 美业同上 |
| `retail` | 基线 | 零售即基线，恒为 `S` |
| `verdict` | `CORE` / `IND_VIEW` / `IND_OWN` | 归属建议：走基座 / 行业聚合读 / 行业独有 |
| `note` | — | 判定理由，**只在不显然时写** |

### 2.3 关系码（五档，互斥）

| 码 | 含义 | 例子 | 对选型的含义 |
|---|---|---|---|
| **S** | 完全相同 | `POST /biz/goods` 建商品 | 支持方案 A |
| **P** | 参数化差异（同一接口多几个字段/过滤） | 商品列表多一个「出品部门」过滤 | 支持 A（加字段即可） |
| **V** | **视图差异**：读模型不同，写完全相同 | 菜品列表 vs 服务项目列表 | 支持 **C**（读走行业、写走基座） |
| **X** | 结构差异：流程不同，必须分开 | 结账（餐饮多单合结 vs 美业耗卡） | 支持 C 或 B |
| **N** | 该行业不适用 | 桌台之于零售 | 行业独有，与选型无关 |

**判定必须落到具体接口，不许对「模块」整体打码。**
一个模块里 18 个接口 17 个 `S`、1 个 `X`，与 18 个全 `X`，指向的方案完全不同 —— 而按模块打码这两种情况长得一模一样。

### 2.4 盘点范围与取舍（说清楚，不假装全盘）

| 范围 | 端点数 | 本轮盘不盘 |
|---|---|---|
| `/biz` 商家端 | **206** | ✅ 全盘 —— 行业差异主要在这里 |
| `/mp` 买家端 | **93** | ✅ 全盘 —— 下单链路的差异决定 C 端要不要分门 |
| `/ops` 运营端 | **338** | ❌ 本轮不盘 —— 运营面是平台自己的界面，行业诉求低；**P4 结论里要显式声明它没被盘过** |

盘 299 条。按域分批，一批一次 review。

## 3. P1 · 美业包方案（对标餐饮那份）

**章节骨架必须与 `TDD-餐饮包-场景与工作流.md` 逐节对齐**，否则 P3 没法逐条比对：

| 节 | 餐饮那份是什么 | 美业这份要回答什么 |
|---|---|---|
| 一 · 业务场景 | 六个场景 × 四问 | 到店/上门/办卡/疗程/团体课？同样四问 |
| 二 · 项目建模（基础 + 服务） | 做法/加料/沽清/时段菜单/称重 | 项目时长、指定技师加价、疗程拆次、耗材、可售时段 |
| 三 · 工作流主干 | 菜单→选择→下达→制作→交付→结账 | 项目→预约→到店→服务→核销耗卡→结账 |
| 四 · 各阶段详细 | 下达两条链、KDS、交付、结账 | 预约占位、开工单、换人、完成核销、结账 |
| 五 · 动作精确逻辑 | 七个动作 × 钱收没收 | 改约/取消/爽约/换人/退卡/转卡 × **钱与次数收没收** |
| 六 · 入口与调用方向 | 主语判据 + 编排示例 | 同一套判据，看结论是否一致（**这是 P3 的关键输入**） |
| 七/八 · 三类表 | A/B/C 分类 + DDL | 同一套分类规矩 |
| 九–十六 | 对象/服务/交互点/权限/打印/不做/测试/待确认 | 同 |

**P1 已完成，三个盯点的结论**：
1. **购物车**：美业**不需要**共享购物车（一次预约一到三个项目、一个人选），预约单自带项目行。
   → 与餐饮的第一处实质结构差异，P3 记 `X`；
2. **一单多次履约**：疗程包**不是**一张订单履约十次 —— 卖卡一张单，每次服务另开一张实收 0 的单。
   「订单 ≡ 一次消费」这条假设**保住了**；
3. **耗卡算支付**：作为一种 `sys_pay_channel` 走 `markPaid`，实收 0、原价留在 `ord_item.price`。
   **代价是基座要加一列 `assetDeductMinor`**（既不是平台补贴也不是商家让利，是预收款核销）——
   已写进美业包的 `requiredCapabilities()`，缺它拒绝启动。

## 4. P2 · 零售基线

零售不是「没有行业」，它是**基线**。要盘的是：

- 现有 `/biz` `/mp` 里哪些接口零售**真的在用**（有前端调用方），哪些是有能力没消费方；
- 零售自身的流程五段（下单/支付/履约/售后/结算）落在哪些接口上；
- **零售缺哪些**（例如收银台、小票、储值）—— 这些正是基座该补的，不是行业包的。

> 没有这一步，P3 的「差异」就没有参照物 —— 说「餐饮和美业不一样」是没有信息量的，
> 要说的是「相对零售，餐饮在这 12 个接口上是 X 档」。

## 5. P3 · 三行业对比矩阵

产物两份：

**① 接口矩阵**（生成物 + 人工判定列）
```
按 subject 分组 → 每组统计 S/P/V/X/N 的条数与占比
```
必须能回答的三个问题：
1. 结构差异（`X`）占全部接口的百分之几？
2. `X` 集中在哪些 `subject`？是集中在 2–3 个，还是摊在所有 subject 上？
3. `V`（读视图差异）有多少？—— 它决定「行业聚合读」这条中间路值不值得。

**② 流程对比表**（五段 × 三行业）

| 段 | 零售 | 餐饮 | 美业 | 差异性质 |
|---|---|---|---|---|
| 下单 | | | | |
| 支付 | | | | |
| 履约 | | | | |
| 售后 | | | | |
| 结算 | | | | |

每格写「同 / 多一步 X / 顺序反了 / 完全不同」，**并注明差异是在基座能表达的范围内还是超出**。

## 6. P4 · 终局选型：判定条件先写死

**在拿到数据之前就把判定条件定下来**，否则数据出来后总能解释成自己想要的结论。

| 若数据是 | 则结论 | 理由 |
|---|---|---|
| `X` < 15%，且集中在 ≤3 个 subject | **A（基座为主）** | 现状形态就够，差异用附属表和少量行业入口吸收 |
| `X` 15–40%，且集中在少数 subject；`V` 显著 | **C（按模块拆）** | 只把差异模块行业化，其余共用 —— 代价与收益都可控 |
| `X` > 40%，或摊在多数 subject 上 | **B（行业统一入口）** | 共用部分太少，代理成本反而低于强行统一的扭曲 |
| 任何情况下 `external=Y` 的接口 | **恒走基座** | 支付/物流回调地址只能有一个，外部系统不认识行业 |
| 任何情况下 `cross=Y` 的接口 | **恒走基座** | 一次调用跨多个商家/行业时，行业门没有唯一答案 |

**分母已由 P2 定死**（§7）：299 − 27（无消费方）− 20（社区团购）− external ≈ **250**。
上表的 15% / 40% 按这个分母算。**P3 之后不许改。**

后两条是**否决项**，不参与统计 —— 它们与占比无关，是事实约束。

### 6.1 成本模型（真实数字，选型时直接代入）

| 方案 | 一次性成本 | 持续成本 | 已知硬约束 |
|---|---|---|---|
| A | 低（现状） | 行业差异靠附属表，前端要拼两次读 | 无 |
| B | **代理 299 个端点 × 行业数**；SPI 从 8 个窄口子扩到全量 | 基座每加一个端点，每个行业包跟一次；权限码 99 × 行业数 | 需内网 Maven 仓库；回调与跨行业下单仍要开后门 |
| C | 只代理差异模块 | 边界要维护（哪个模块归谁） | 边界漂移风险，需 ADR 钉住 |

## 7. 需要先回答的问题（会改变盘点口径）

1. **`/ops` 要不要盘？** 本清单默认不盘。若运营端也要行业化（例如按行业的营业报表），P0 范围翻一倍。
2. **零售是否有第三方在开发行业包的计划？** 有的话方案 B 的权重立刻上升（第三方不该拿到基座全量接口）。
3. **私有化单行业交付是否在路线图内？** 是的话 P4 要一并给出 L2 运行时加载的排期。
4. **耗卡算不算支付？**（P1 的第 3 个盯点）—— 这条会反过来改基座会员资产的设计，越早定越好。
5. **P1 与 P2 谁先？** 建议并行；只能串行的话先 P2（基线不定，P1 的「差异」无处可比）。

## 8. 这份清单不做的事

## 9. 风险

1. **盘点变成填表运动**：299 行如果没人真读代码，关系码会全填 `S`。
   对策：每个 subject 抽 3 条做交叉复核，复核不一致就整组重盘。
2. **判定条件被事后调整**：§6 的阈值一旦在看到数据后被改，整个方法就白做了。
   **阈值要在 P0 完成时定稿并签字，P3 之后不许改。**
3. **P1 拖成实现**：美业包方案容易写着写着变成实现设计。它的产出是**可比对的方案**，不是可施工的代码。
4. **零售基线被跳过**：最容易被省的一步，也是让「差异」有意义的唯一参照。
