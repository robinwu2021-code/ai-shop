# TDD · 活动：先理逻辑，再理界面

> 状态：**草稿 · 待确认** · 2026-09-18
> 起因：店主「新建活动页面 UI 也不对，整理逻辑应该是活动名、活动类型、开始以及
> 结束日期以及其他选项」「先整理活动逻辑再整理 UI」
> 相关：[TDD-团购从商品挪进活动](./TDD-团购从商品挪进活动.md)、`promotion` 包的 `package-info`

---

## 一、一句话

**现在这一页问的是「你想达成什么」，而店主脑子里装的是「我要建一个什么活动」。**

四步的顺序是按<b>模型</b>排的（触发 → 优惠 → 排期 → 受众），
不是按<b>他说话的顺序</b>排的。

---

## 二、现状（读代码得到，不是印象）

### 2.1 四步问的是什么

| 步 | 标题 | 实际在问 |
|---|---|---|
| 1 | 活动类型 | **活动目标**（拉新客 / 唤回老客 / 清库存 / 提高客单 / 开团购）+ 活动名 |
| 2 | 优惠 | 优惠方式（满减 / 特价 / 买赠）+ 各自的参数 + 选商品 |
| 3 | 时间 | 排期（限时 N 天 / 长期 / 每周几）+ 限量 / 预算 |
| 4 | 适用人群 | 所有人 / 非会员 / 沉睡 / 熟客 |

### 2.2 「目标」这一层是个**默认值生成器**，不是一个字段

```
ACQUIRE → benefit=CUT   audience=NON_MEMBER
WAKEUP  → benefit=CUT   audience=LEVEL:SLEEPING
CLEAR   → benefit=PRICE audience=（空）
BASKET  → benefit=CUT   audience=（空）
GROUP   → benefit=PRICE audience=（空）· triggerType=GROUP
```

**它只在第 1 步写一次默认值，之后第 2/4 步可以随便改回去。** 于是：

- 选了「拉新客」再把人群改成「所有人」—— 活动名还叫「新客立减」，而它对谁都减；
- 「清库存」与「开团购」**都是 PRICE**，靠目标才分得开（我 2026-09-18 已经把
  凡判团购的地方改成看 `goal`，但那是补丁，不是模型）。

### 2.3 一个真实的后果

`pmt_activity` 表里 `goal` 是**存下来的**，而它与 `benefitType` / `audience`
**可以互相矛盾**，没有任何一处校验。列表上按 `goal` 给文案、按 `triggerType`
分团购，两套判据并存。

## 三、店主的语序

他说的是：「我要做一个**团购**，叫**中秋团**，**这周六到下周日**，香梨，三人成团 8 块。」

拆开是：**类型 → 名字 → 起止 → 对象 → 参数**。

与现在四步的差别：

| | 现在 | 他的语序 |
|---|---|---|
| 第一个问的 | 目标（拉新客…） | **类型**（满减 / 特价 / 团购 / 买赠） |
| 名字 | 混在第 1 步末尾 | 紧跟类型 |
| 时间 | 第 3 步 | **第 2 位** —— 「这周六到下周日」是他先说出口的 |
| 受众 | 单独一步 | 多数时候<b>不说</b>（= 所有人） |

---

## 四、方案

### 4.1 「目标」降级成「类型」，不再存

**类型就是 `triggerType × benefitType` 的那五个组合**，直接把它做成界面上的五选一：

| 类型 | triggerType | benefitType | 要问的参数 |
|---|---|---|---|
| 满减 | AMOUNT | CUT | 满多少、减多少 |
| 特价 | GOODS | PRICE | 哪些货、特价多少 |
| 团购 | **GROUP** | PRICE | 哪些货、几人成团、成团价 |
| 买赠 | QTY | GIFT | 买几件、送几件、送什么 |
| 发券 | NONE | COUPON | 发哪张券 |

`goal` 列**保留但不再写**（与 `prd_goods` 那两列同一处置：回滚窗口留长）。
「拉新客 / 唤回老客」这类**变成受众那一步的预设**，它们本来就是受众的别名。

### 4.2 四步改成三步

```
① 是什么      类型（五选一）+ 活动名
② 什么时候    起止日期（默认今天 → 七天后）+ 限量 / 预算
③ 优惠什么    该类型的参数 + 哪些货 + 给谁（默认所有人，折叠）
```

**时间提到第 2 位**，因为他先说出口的是它；**受众折进第 3 步**，
因为多数活动不挑人 —— 单独一步会让每建一个活动都多点一次「所有人」。

### 4.3 起止日期要能直接选

现在是「限时 N 天」（填天数）/ 长期 / 每周几。店主说的是
**「这周六到下周日」** —— 给两个日期选择器，而不是让他去算天数。
「长期」与「每周几」留着，收成第二排的两枚切换。

## 五、这一轮不动的

- **`mkt_campaign` 老模型**：退场中，不在这条线上
- **受众的四个预设**：它们是对的，只是位置不对
- **限量 / 预算的校验**：长期必须有上限、改价必须限量 —— 这两条继续硬拦

## 六、待确认

1. **「发券」要不要现在放进类型里。** 模型支持（`BENEFIT_COUPON`），
   但券有自己的一页（`/pages/coupons`），两处都能发券会让人不知道该去哪儿。
   我倾向**先不放**，在类型里也不列。
2. **`goal` 停写之后，已存的四个 demo 活动怎么显示。** 线上真实数据只有 1 条
   （我昨天在真机上建的团购），demo 是 mock 里的 —— 所以**不需要迁移**，
   但要确认一下你没在别处依赖 `goal`。
3. **「每周几」这种周期活动今天有人用吗。** 它让排期那一步复杂了一倍
   （三种排期各有各的参数）。线上 0 条，可以考虑收进「高级」。

---

## 七、闸门

- 类型五选一 → 存出来的 `triggerType × benefitType` 必须与表里那一行一致
  （消融：把团购那一行改成 `GOODS`，用例必须变红）
- 起止日期：选「这周六到下周日」存出来的 `startAt/endAt` 必须是那两天的
  **本地日历日**边界，不是「今天 + N 天」
- 受众不选时 `audiences` 为空数组 = 对所有人（与现在逐字一致）
