# TDD-定位与未开通区域

状态：**已实现（2026-08-21）**
关联需求：[C 端功能清单](../../requirements/C端功能清单.md) C-1 选社区自提点
创建日期：2026-08-21

## 1. 起因

体验版真机上「选择社区自提点」页一片空白。查下来是三个叠在一起的问题，
其中两个在此之前**从来不会报错**：

| # | 问题 | 为什么一直没暴露 |
|---|---|---|
| 1 | 页面没有失败态与空态 | 请求挂了 `v-for` 渲染 0 条，只剩标题栏；错误是未捕获的 Promise rejection |
| 2 | **定位结果拿到了却没传给后端** | `getLocation()` 的返回被丢弃，`loadNearby()` 不带参数 —— 后端永远走「无坐标」分支 |
| 3 | **后端没有距离过滤** | 返回全部已开通社区；广州坐标实测返回杭州「阳光花园」，距离 1056 公里，排在第一位 |

第 3 条最贵：它不是「查不到」，是**查到了一个错的**。用户能绑定一个 1000 公里外的
自提点，然后下单一件他永远取不到的货 —— 而系统全程不认为有任何异常。

## 2. 「没有匹配的门店」应该怎么办

**先定死一件事：空不能是死路。** 这一页是新用户的第一屏，
让他停在「你所在的区域暂未开通」而没有任何下一步，等于在第一屏劝退。

| 方案 | 结论 |
|---|---|
| A. 空态 + 可浏览全部已开通社区（**采用**） | 异地下单在社区团购里是真实高频场景：给父母下单、出差前囤货。手动选一个远点是**用户的知情选择**，与系统把远点伪装成「附近」是两回事 |
| B. 空态 + 留资「开通后通知你」 | ❌ 一期没有承接渠道（短信/订阅消息都要额度与模板），留了也发不出去 —— 那是收集了期待却不兑现 |
| C. 硬拦：不绑定不能逛 | ❌ 商品、门店、团购在后端本来就是游客可访问的，为了一个归属把逛也拦掉，代价远大于收益 |

采用 A，并加一道**知情确认**：手动选择的自提点若超出服务半径，
二次确认里把真实距离说出来（「离你约 1056 公里，确定要绑这里吗？」）。
不拦、但要他自己看见那个数。

## 3. 设计

### 3.1 后端

```
GET /mp/community/nearby?lat=&lng=   附近（带半径过滤）
GET /mp/community                    全部已开通（手动选 / 异地下单）  ← 新增
```

- 半径 `shop.community.nearby-radius-m`，默认 **5000 米**。
  自提是走过去取，几公里之外的点在物理上就不成立。
- **坐标缺失的社区不算「附近」**。它们的 `distance` 兜底为 0，
  若按 0 米参与过滤，一个没配坐标的社区会出现在**每个人**的附近列表里，
  而且排第一。未知就是未知，不是零。
  （这类社区会长期存在：商家提报审过后建出来的只有名字与区划，坐标靠运营后补。）
- 没传坐标时（定位失败/拒绝）**不过滤**，保持库序返回全部 —— 那时没有「近」可言，
  由端上明示「未定位」。

### 3.2 端上

| 状态 | 显示 | 用户的下一步 |
|---|---|---|
| 定位中 | 「正在定位附近社区…」 | 等 |
| 加载失败 | 「没能加载附近的自提点」+ 重试 | 重试（多半是网络/域名白名单） |
| 附近为空 | **不推他去选社区页**，留在首页 + 一次性提示 | 先逛；顶栏「选自提点」入口一直在 |
| 附近为空且他自己点进来 | 「这一带还没有自提点」+ **查看全部已开通社区** | 手动选（异地下单） |
| 未定位 | 顶部提示「未获取定位，以下是全部已开通社区」 | 手动选 |

定位结果**必须传下去**：`loadNearby(coords?.lat, coords?.lng)`。

## 4. 测试策略

- `CommunityNearbyFlowTest`
  - 近处坐标 → 返回；远处坐标 → **不返回**（同一个社区，只换坐标）
  - 坐标缺失的社区：任何坐标下都不进 nearby，但进 `/mp/community`
  - 不传坐标 → 全部返回（不过滤）
  - 半径可配：`@SpringBootTest(properties = ...)` 单独验一次
- 端上：`community.loadNearby` 传参的回归由类型签名保证；空态/失败态人工验收

## 4.1 「附近没有」时不再强推选社区页（2026-08-21 追加）

首页 `onShow` 原先是 `if (!community.bound) gotoCommunity()` —— **无条件推**。
所在区域还没开通的用户，每次回首页都被推去一个只会说「这一带还没有自提点」的页面：
那一页对他没有任何用处，却是他绕不过去的第一屏。

改成 `probeNearby()` 先探再决定：

- 有 → 照旧推他去选（那正是他要做的事）
- 没有 / 探不出来 → **留在首页先逛**，一次会话提示一次

配套两条，缺一条就把问题推到下一站：

1. **探测结果按会话缓存**，否则每次切回首页都定位 + 请求一次。
   但**网络失败不缓存、也不当成「没有」** —— 那会把一次网络抖动固化成
   「这个区域没开通」，而用户下次回来还是这个结论。
2. **下单页兜底**：自提单而未绑归属时，先提示再送他去选社区页。
   不拦的话后端回 `70025 请先选择自提点` —— 一句正确但没有出口的话：
   他站在结算页，不知道去哪儿选。

> **这一段没有自动化测试覆盖。** c-app 没有 vitest 环境（三端的测试都是
> packages/shared 里的源码扫描式守卫），而这是首屏路由行为，
> 用正则去钉「首页必须先探再推」既脆又容易骗过自己。
> 距离规则那部分由 `CommunityNearbyFlowTest` 钉住，这一段靠人验。

## 5. 风险

- **改的是第一屏**。半径设小了，已开通社区的用户也会看到空态。
  5000 米是社区自提的物理上限，且可配 —— 真出问题改一个配置项，不用发版。
- 老用户已绑定的远点不受影响：这次只改「怎么选」，不动已有归属。
