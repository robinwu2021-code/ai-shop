## 0. 先说现状：这个 tab 现在是坏的

`/iam?tab=roles` 有完整的权限树、危险权限二次确认、保存按钮。
它调的是：

```
GET  /ops/roles                → 404
POST /ops/roles/{role}/perms   → 404
```

实测确认。这条缺口**已诚实登记**在 `ops-endpoint-exists.test.ts` 的
`UNBUILT_DOMAINS` 里（`"roles"`），所以守卫是绿的、没有骗人 ——
但对着屏幕的人不知道，他会勾一堆权限、点保存、拿到一个报错。

后端刚补的写接口在**另一个路径**上：`/ops/perm/roles`。
两头都在，中间没接上 —— 今晚第 N 次这个形状。

## 1. 最要紧的一处不对齐：**授权的粒度不同**

这不是改个路径的事。

| | 前端现在 | 后端现在 |
|---|---|---|
| 勾什么 | **权限码** `merchant:audit` | **功能点** `OPS_MERCHANT_01` |
| 树从哪来 | `nav.ts` 里 `leaf.perm` 去重 | `sys_function` × `sys_function_point` |
| 有多少 | **16** 个去重权限码 | **78** 个功能点 |

78 → 16 不是「更细 vs 更粗」这么简单，实测三个数：

- **56** 个功能点有 `perm_code`，去重后只剩 **16** 个码 —— 多个菜单项共用一个码
- **22** 个功能点 `perm_code` 为空
- **22** 个功能点 `backend_status = NOT_IMPLEMENTED`

> ⚠️ **按权限码勾选，表达不了那 22 个 `perm_code` 为空的功能点。**
> 那些菜单项的可见性根本不在权限码这个维度上 ——
> 无论树里怎么勾，它们的可见性都不变。
> 也就是说：**现在这棵树即使接通了，也有 22 项是勾不动的**，
> 而界面上不会有任何提示说明为什么。

`sys_role_point` 存的是功能点，**菜单与判权都从它推导**
（功能点 → `perm_code` → 权限快照）。所以：

> **建议：树改成「功能 → 功能点」两层，勾功能点。**
> 权限码作为功能点的一个展示属性（`code` 标签），不再是勾选单位。

代价：这棵树从 16 个叶子变成 78 个，且要按 `groupName` 分组才看得清。
收益：**勾什么 = 库里存什么 = 他登录后看到什么**，中间没有翻译层。
今晚的缺陷有一半来自翻译层两边各写一套。

## 2. 对齐清单

### 2.1 数据库 —— **不动**

五张表（`sys_function` / `sys_function_point` / `sys_role` /
`sys_role_point` / `sys_role_member`）本轮已建好，字段够用。
`sys_role.wildcard` 已能表达超管。

### 2.2 API

| 前端契约（现） | 后端现有 | 处置 |
|---|---|---|
| `GET /ops/roles` | `GET /ops/perm/roles?end=OPS` | **改前端**，跟后端路径 |
| `POST /ops/roles/{role}/perms` | `POST /ops/perm/roles/{code}/points` | **改前端**，且入参从 `perms` 换成 `pointCodes` |
| — | `GET /ops/perm/functions?end=OPS` | **新加**：树的数据源 |
| — | `GET /ops/perm/roles/{code}/points` | **新加**：选中角色时拉已勾项 |
| — | `POST /ops/perm/roles` | **新加**：建自定义角色 |
| — | `POST /ops/perm/roles/{code}/delete` | **新加**：删角色 |

**后端零改动**，六条端点都已实现并有测试。

### 2.3 对象

`RoleDef`（前端）与后端 `RoleVO` 的差：

| `RoleDef` 字段 | 后端有吗 | 处置 |
|---|---|---|
| `role` | `roleCode` | 改名 |
| `label` | `name` | 改名 |
| `builtin` | `builtin` | ✅ |
| `perms: string[]` | — | **删掉**：改成单独拉 `points` |
| `staffCount` | ❌ **没有** | 见下 |

> **`staffCount` 要后端补**。它现在撑着列表里「持有该角色的账号数」那一列，
> 而且是删除角色前唯一能看出「删了会影响谁」的信息 ——
> 后端 `deleteRole` 已经拦住了在用的角色（10441），
> 但**拦在点下去之后**。列表上就显示出来，才不会让人白点一次。
> `sys_role_member` 按 `role_code` 聚合，一条 SQL。

### 2.4 Controller / Service / Mapper

| 层 | 改动 |
|---|---|
| Controller | 无（六条端点都在） |
| Service | `PermConfigServiceImpl.roles()` 补 `staffCount` |
| Mapper | `SysRoleMemberMapper` 加一个 count-by-role 的聚合查询 |

## 3. 三件要小心的

### 3.1 内置角色在界面上要**渲染但禁用**，不是藏起来

后端对预置角色返回 10440（只读）。前端**不能因此把它们藏掉** ——
超管、BD、客服是运营最常看的三个，藏起来等于「角色列表里没有客服」。
按今晚定下的第三条路：**渲染、可查看已勾功能点、保存按钮禁用并说明为什么**
（「预置角色是代码里那份的镜像，改了会与回落表分叉」）。

### 3.2 未实现的功能点要在树上灰显

22 个 `NOT_IMPLEMENTED`。勾了它们不会报错，但**勾了也没用** ——
后端还没有那个端点。树上直接标出来，与菜单那侧的灰显同一口径。

> 不标的后果很具体：运营给风控角色勾满了功能点，
> 那个人登录进去还是一个空看板，而没有任何东西告诉他们原因。

### 3.3 改完角色的功能点，**持有者的会话要踢**

判权读的是登录那一刻的快照。`setRolePoints` 现在只调了
`resolver.invalidate()`（清缓存），**没有踢会话** ——
所以改完之后，已经登录的人要等下次登录才生效。

`setStaffRole/Enabled/Scope` 三个都调了 `revokeUser`，
这里漏了。**要补**：按 `sys_role_member` 找出持有者，逐个 `revokeUser`。

## 4. 做什么 / 不做什么

### 做

1. `lib/api/https/iam.ts` 六条端点改到 `/ops/perm/**`
2. 契约 `IamApi` 换形状：`listRoles` / `listRoleFunctions` / `getRolePoints` /
   `setRolePoints` / `createRole` / `deleteRole`
3. mock 跟着换（守卫会比对契约与 mock）
4. 权限树改成「功能 → 功能点」两层，按 `groupName` 分组
5. 未实现功能点灰显；内置角色渲染但禁用
6. 后端补 `staffCount` + 改功能点后踢会话
7. 从 `UNBUILT_DOMAINS` 删掉 `"roles"`
8. 测试 + 浏览器实测（**换源之后的断言**：新建角色 → 勾功能点 →
   授予某人 → 他重新登录后菜单真的变了）

### 不做（登记）

| 不做 | 为什么 |
|---|---|
| B 端角色配置界面 | `mch_store_role` 是另一套，本批只做运营端 |

| 数据域跟着一起配 | 它是员工行上的动作，且数据域本身还没真正生效（§5.1） |
