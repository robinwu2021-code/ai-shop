# 商品域 —— 三行业能不能一套接口

状态：**分析 · 待确认** · 创建 2026-08-28
关联：[核心能力清单](../reference/核心能力清单.md) B 节 · [TDD-餐饮包](./TDD-餐饮包-场景与工作流.md) §2 · [TDD-美业包](./TDD-美业包-场景与工作流.md) §2 · [ADR-020](../ADR/ADR-020-行业接口终局形态.md)

---

## 0. 结论先行

**能，而且这套机制已经在跑 —— 不需要新造，只需要把它开放给行业注册。**

`BizGoodsController` 今天的形状就是「一套接口 + 按品类分段」：

```java
GoodsSaveReq(… 公共字段 …,
             FreshReq   fresh,    // 留空 = 不改；只在品类是 FRESH 时写入
             ServiceReq service)  // 留空 = 不改；只在品类是 SERVICE 时写入
```

把 `FreshReq` / `ServiceReq` 这两个**写死的段**换成**可注册的段**，商品域的行业化就完成了。

三条实测结论：

| | 结论 |
|---|---|
| **接口** | 一套。`POST /biz/goods/save` 不动，**不新增行业商品接口** |
| **美业** | 商品域**零行业包代码** —— `bty_goods_ext` 整张表可以取消 |
| **餐饮** | 从 6 列瘦到 3 列，且剩下的三列都是**引用行业自有对象**的，删不掉 |

## 1. 先纠正三处「以为要新建、其实基座早就有」

盘 `PrdGoods` / `PrdSku` / `BizGoodsController` 时发现的，都是我此前两份行业 TDD 里多设计的东西：

| 我原本设计的 | 基座已有的 | 结论 |
|---|---|---|
| `bty_goods_ext.duration_min` 服务时长 | **`prd_goods.durationMin`**（SERVICE 段，已存在） | ❌ 删掉，直接用 |
| `bty_goods_ext.home_service` 可上门 | **`prd_goods.fulfillments`** 含 `APPOINTMENT` | ❌ 删掉，可上门 = 履约方式里有它 |
| `fnb_goods_ext.takeout_allowed` 可外卖 | 同上，含 `EXPRESS` / `MERCHANT_DELIVERY` | ❌ 删掉 |
| 餐饮「称重菜」（海鲜按斤） | **FRESH 段** `weighed` / `nominalGram` / `cutoffAt` | ❌ 删掉，本来就有 |
| 餐饮「沽清」 | **`prd_store_stock`** 置 0 | ❌ 删掉（原设计已是这样） |
| 美业「谁能做这个项目」 | **`mch_staff_skill`**（基座 E3） | ❌ 不是商品属性 |

**这一列是本册最值钱的部分**：不是"能不能一套接口"，而是**行业属性里有一半根本不是行业属性** ——
它们要么已经在基座，要么本来就该在基座。

> ⚠️ 顺带记一条**不能碰的**：`prd_category.attr_template` 是 `@Deprecated`，
> 全仓零读者、73 个类目一个有值的都没有，且 `prd_goods` 上没有存放属性值的地方。
> 它的注释写明「**不要再往它上面建东西 —— 第三套同类机制只会让「建品页字段从哪来」
> 变成一个没人答得清的问题**」。本方案**不复活它，也不新造通用属性袋**（那正是第三套）。

## 2. 逐个分析：三个行业的「商品」到底差什么

### 2.1 零售 · 商品（基线）

五品类里的 `NORMAL` 与 `FRESH`，现成。`FRESH` 段已经承载了截单、到货、按重计价、产地。
**零售不需要任何新东西。**

### 2.2 餐饮 · 菜品

| 属性 | 性质 | 归属 | 理由 |
|---|---|---|---|
| 出品部门 | **引用** `fnb_dept` | **餐饮段** | 选项来自行业表，基座给不出选项、也校验不了；且要参与分单打印的 SQL 匹配 |
| 做法模板（免辣/少冰） | **引用** 行业的做法组 | **餐饮段** | 同上 |
| 先上 / 后上 / 等叫 | 标量枚举 | **餐饮段** | 纯标量，但只有出品队列有语义，上收基座等于给零售一个永远为空的字段 |
| 可否外卖 | — | ~~删~~ | `fulfillments` 已表达 |
| 称重（海鲜按斤） | — | ~~删~~ | FRESH 段已有 |
| 沽清 | — | ~~删~~ | 门店库存置 0 |
| 套餐 | — | **基座** | 组合商品 `prd_sku_bundle`（B4），≡ 美业疗程包 |
| 加料 / 做法在**下单时**的行为 | — | **交易域** | 加料展开为独立订单行 —— 那是交易逻辑，不是商品属性（见 §4） |

**餐饮段最终三列**：`dept_no` · `modifier_group` · `serve_priority`。

### 2.3 美业 · 服务项目

| 属性 | 性质 | 归属 | 理由 |
|---|---|---|---|
| 服务时长 | 标量 | **基座 SERVICE 段（已有）** | `durationMin` 就在 `prd_goods` 上 |
| 前后缓冲（路途） | 标量 | **基座 SERVICE 段（扩）** | 上门服务都要，不是美业专属 —— 家政、维修同样需要 |
| 需要哪类资源 | 标量枚举 | **基座 SERVICE 段（扩）** | 资源模型（`mch_resource`）本来就在基座 |
| 是否必须选技师 | 标量布尔 | **基座 SERVICE 段（扩）** | 资源预约能力的配置项 |
| 可上门 | — | ~~删~~ | `fulfillments` 含 `APPOINTMENT` |
| 谁能做（技能） | 关系 | **基座 `mch_staff_skill`** | 不是商品属性，是员工能力 |
| 疗程包 | — | **基座 `prd_sku_bundle`** | ≡ 餐饮套餐 |

**美业段：不存在。** `ServiceReq` 从 2 个字段扩到 5 个，全部在基座。
**美业在商品域一行行业代码都不用写。**

## 3. 机制：把写死的段换成可注册的段

### 3.1 接口形状（不变）

```
POST /biz/goods/save        一套，带若干可选段
GET  /biz/goods/{no}        一套，返回公共字段 + 已注册段的值
GET  /biz/goods/form-schema?categoryNo=…&storeNo=…
                            建品页字段从哪来的**唯一**答案：
                            五品类固定段 + 该门店已启用的行业段
```

`form-schema` 是关键一环：b-app 一套建品页，字段由后端下发。
今天 b-app 是按 `type` 硬渲染的，加段之后必须改成读 schema —— 否则行业段有值也没有入口。

### 3.2 段的契约（基座定义，行业实现）

```java
public interface GoodsSegment {
    String code();                       // "food" / "service-ext"
    Set<String> appliesToTypes();        // 只在这些五品类上出现
    String capability();                 // 门店没开这个能力就不出现
    List<FieldSpec> schema();            // 字段清单，驱动 form-schema
    void validate(String goodsNo, Map<String,Object> values);
    void save(String goodsNo, Map<String,Object> values);   // 与基座写入同事务
    Map<String,Object> load(String goodsNo);
}
```

**基座只负责路由分段、校验调度、事务边界，不认识段的内容。**
于是 `dept_no` 引用 `fnb_dept` 这件事，基座完全不需要知道。

### 3.3 段的值存哪 —— 一条判据

| 情况 | 存法 |
|---|---|
| 要被 SQL 查询 / JOIN（出品部门要参与分单路由） | **落列**，落在段自己的表 |
| 只读出来展示 | 也落段自己的表，一列 JSON 即可 |
| **通用属性袋（`prd_goods_attr` KV / 复活 `attr_template`）** | **❌ 不做** |

不做通用属性袋的理由不是洁癖：`attr_template` 的注释已经把代价写清楚了 ——
**「建品页字段从哪来」会变成一个没人答得清的问题**。
段是**可枚举的注册表**，属性袋是**开放的自由 KV**，两者在可维护性上不是一个量级。

### 3.4 「不一定要用额外的包」—— 对，商品域确实不用

段的注册**不要求独立 jar**：一个 `@Component implements GoodsSegment` 就够。

- **美业**：连段都不需要（全部上收基座），商品域零代码；
- **餐饮**：需要一个段，因为它引用 `fnb_dept`。
  这个段放哪都行 —— 放餐饮包里是顺手（那个包**本来就因为台账、桌台、制作而存在**），
  放基座里则要求基座认识 `fnb_dept`，那才是真正的耦合。
  **所以是"因为已经有包所以放进去"，不是"因为要扩商品所以建包"。**

## 4. 什么**不能**一套 —— 三条边界

一套接口能覆盖的是「**这件商品是什么**」。下面三件事不在其中：

1. **下单时的行为差异。** 加料展开为独立订单行、指定技师加价作为附加行 ——
   这是**交易域**的编排，不是商品属性。商品只提供"有哪些加料可选"。
2. **参与计算的时机。** 服务时长要参与预约占位的格数计算 ——
   但计算方在预约编排里**读**这个属性即可，属性本身留在基座。**读的人是行业，被读的东西不是。**
3. **读视图的组装。** 商品列表要显示"出品部门 + 沽清"或"时长 + 可选技师数"。
   一套接口把已注册段的值一并返回（`segments: {...}`）就够 ——
   **连行业聚合读端点都不用另建**，这比 ADR-020 §1 的第 2 条更省。

## 6. 风险

1. **段被滥用成第二个属性袋。** 对策：段必须声明 `schema()`，字段可枚举；
   新增段要走评审，与「加扩展点要走 ADR」同一条规矩。
2. **`form-schema` 与实际写入分岔**（schema 说有这个字段、save 不认）。
   对策：一条测试遍历所有已注册段，`schema()` 的字段集必须与 `validate/save` 接受的一致。
3. **b-app 改造被跳过。** 后端加了段而前端还在硬渲染，现象是"配了没生效"且不报错。
   对策：段落地与建品页改造**同一个 PR**。
4. **餐饮段的引用完整性。** `dept_no` 指向 `fnb_dept`，删部门时商品上会留下悬空引用。
   对策：删部门前检查引用数，与删类目同一套做法。
