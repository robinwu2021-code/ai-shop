## 一、仓库的分层约定（抽出来的，不是我发明的）

守卫在 `backend/shop-app/src/test/java/ai/neargo/shop/arch/ArchitectureTest.java`，
新模块必须一次就长成这个样子 —— 长歪了是测试红，不是评审意见。

| 约定 | 守卫方法 |
|---|---|
| **Service 必须是接口** | `serviceMustBeInterface` |
| **impl 在专属包**（`service/impl`） | `implsMustLiveInDedicatedPackage` |
| **Controller 不许碰 Mapper** | `controllersMustNotTouchMappers` |
| Controller 只能在域的 `api/**` 或 portal | `controllersInDomainApiOrPortal` |
| **Port 接口只在 spi**（`shop-base`） | `portInterfacesOnlyInSpi` |
| **域模块之间不许互相依赖** | `svcModulesMustNotDependOnEachOther` |
| 域不许依赖 app 层 / web 运行时 / channel | 三条 |
| 不许写全限定名引用 | `noFullyQualifiedReferences` |

**Mapper 的形状**：一个域**一个 `final class`**，里面是嵌套的 `interface XxxMapper extends BaseMapper<T>`
（见 `SettleMappers` / `ProductMappers`），不是一个类一个文件。

**Controller 前缀**只能是 `/biz` `/mp` `/ops` —— 前缀是部署隔离的判据（`@Profile` 按它分实例）。

### 2.1 `StockPostingService` 是整个模块的收口

**所有余额变动都从这一个方法过**：

```java
/** 过账：唯一改变 on_hand 的动作。入库单与出库单都走它。 */
public interface StockPostingService {
    /**
     * @throws BizException INV_INSUFFICIENT 出库超过实存时，带上差多少
     * @return 本次产生的流水 id 列表
     */
    List<Long> post(String ownerId, PostingDoc doc);

    /** 作废：写反向流水，不删原行、不改原单。 */
    void reverse(String ownerId, String docNo, String reason);
}
```

**为什么收口在一处**：`available >= 0`（不变式 I1）与「变动必有且仅有一行流水」（I2）
各只需要在这一个方法里证明一次。分散到六个 Service 各写各的，就要证明六次，
而第七个人加第七条路径时没有任何东西会拦他。

### 2.2 条件更新放在 Mapper，不放在 Service

```java
public interface BalanceMapper extends BaseMapper<InvStockBalance> {
    /** 实存增减。返回 0 = 会扣成负数，调用方据此抛 INV_INSUFFICIENT。 */
    @Update("""
        UPDATE inv_stock_balance SET on_hand = on_hand + #{delta},
               last_moved_at = NOW(), version = version + 1
         WHERE owner_id = #{ownerId} AND item_id = #{itemId} AND location_id = #{locationId}
           AND on_hand + #{delta} >= 0
        """)
    int applyDelta(...);

    /** 预留：只动 reserved，且不许让 available 变负。 */
    @Update("""
        UPDATE inv_stock_balance SET reserved = reserved + #{qty}, version = version + 1
         WHERE owner_id = #{ownerId} AND item_id = #{itemId} AND location_id = #{locationId}
           AND on_hand - reserved - #{qty} >= 0
        """)
    int hold(...);
}
```

与今天 `ProductMappers.SkuMapper.lockStock` **完全同一手法** —— 靠 SQL 的条件更新做原子，
不是「先查后改」。先查后改在并发下必然超卖：两个请求都查到「还有 1 件」。

## 三、从 API 到数据库的一条竖切

以**盘点过账**为例，看一次请求穿过几层：

| 层 | 干什么 |
|---|---|
| `POST /biz/inventory/counts/{no}/post` | —— |
| `BizStockCountController` | `@Profile("biz")` ＋ `@PreAuthorize("@perm.canBiz('biz:stock')")`；从 `BizContext` 取主体，**经 ItemSyncService 解析成 `ownerId`**；不碰 Mapper |
| `StockCountService.post(ownerId, countNo)` | 读盘点单与行；`diff > 0` 的行交给 `InboundService`，`diff < 0` 的交给 `OutboundService`；`diff = 0` 不生成任何东西 |
| `InboundService` / `OutboundService` | 建单（`COUNT_GAIN` / `COUNT_LOSS`），落 `inv_*bound_order(_line)` |
| ★ `StockPostingService.post` | 逐行 `BalanceMapper.applyDelta` → 返回 0 就抛 `INV_INSUFFICIENT`；读回 `balanceAfter` → `LedgerMapper.insert`；写一行 `inv_outbox`（`DocumentPosted`） |
| 表 | `inv_stock_count(_line)` · `inv_inbound_order(_line)` · `inv_outbound_order(_line)` · `inv_stock_balance` · `inv_ledger` · `inv_outbox` |

**一个事务**。跨的是同一个库的六张表 —— 这正是「进销存自己的一致性不需要分布式事务」那句话在代码上的样子。

## 四、与今天代码的对齐

### 4.1 现状：库存写入路径一共 **12 处**

我此前说「`MerchantGoodsServiceImpl` 的三处写入点」，**数少了**。逐处数清楚：

| # | 位置 | 形式 | 写什么 |
|---|---|---|---|
| 1 | `MerchantGoodsServiceImpl` 建品/改品保存 | `row.setStock(sku.stock())` | `prd_sku.stock` |
| 2 | 同上，新建店级行 | `row.setStock(0)` | `prd_store_stock.stock` |
| 3 | `saveStock(...)` 改主体库存 | `row.setStock(stock)` | `prd_sku.stock` |
| 4 | `saveStoreStock(...)` insert / update | `row.setStock(stock)` | `prd_store_stock.stock` |
| 5–7 | `SkuMapper.lockStock / releaseStock / confirmStock` | 条件更新 SQL | `prd_sku.stock` / `locked_stock` |
| 8–9 | `SkuMapper.lockPresale / releasePresale` | 条件更新 SQL | `prd_sku.sold_count` |
| 10–12 | `StoreStockMapper.lockStock / releaseStock / confirmStock` | 条件更新 SQL | `prd_store_stock` |

**12 处里只有 5–12 这 8 条走 `StockPortImpl`**，1–4 是 Service 直接写实体。
这就是「谁改的查不出来」的代码层原因 —— 没有一处收口，也就没有一处可以顺手写流水。

### 4.2 每一处去哪

| 现状 | 新结构 | 说明 |
|---|---|---|
| 1 · 2 建品时写 stock | **不再写余额**，只投影 `inv_item`（余额起始 0） | 建品是主数据，不是入库。见九屏 s01→s05 那条链 |
| 3 · 4 改库存 | **变成一次单件盘点**：`StockCountService` 开单 → 录数 → 过账 | 界面按钮仍叫「改数」，底下是一张单 |
| 5–7 锁定三段 | `ReservationService.reserve/release/commit`，条件更新搬到 `BalanceMapper` | 语义升级，调用方不改 |
| 8–9 预售 | **暂留平台侧**（`presale_quota` 是销售策略不是库存），D2 再定 | 见待确认 ① |
| 10–12 店级 | 并入 5–7 —— 独立库里「店」就是一个 `location`，不再有两套路径 | **少一半分支** |

> **10–12 并入 5–7 是这次结构调整最实的一处收益**：今天每一个库存动作都要先判
> `hasStoreStock(skuNo)` 再走两条路径之一，两条路径各写各的 SQL；
> 独立库里主体级 = 一个默认库位，**判断消失、路径合一**。

### 4.3 `StockPort` 的语义升级对照

| 今天 | 升级为 | 调用方要改吗 |
|---|---|---|
| `lock(lockNo, List<SkuQty>)` → `List<String>` 失败的 SKU | `reserve(externalRef, lines, ttl)` | **不改**（保留旧签名做默认方法转发） |
| `release(lockNo)` | `release(externalRef)` | 不改 |
| `confirm(lockNo)` | `commit(externalRef)` ＋ **产生 `SALE` 出库单** | 不改 |
| —— | `restore(afterSaleNo, lines)` | **新增**：退货入库，今天的缺口 |
| `SkuQty(skuNo, qty, storeNo)` | 保持 | `skuNo` → `itemId` 在防腐层解析 |

`StockPort` 接口**留在 `shop-base`**（守卫：Port 只在 spi），实现从
`shop-core/product/port/StockPortImpl` 搬到 `shop-inventory/port/`。

### 4.4 要搬 / 要留 / 要新建

| 动作 | 类 |
|---|---|
| **搬**（纯搬家，单独一次提交，0 行差异） | `StockPortImpl` · `PrdStoreStock` · `PrdStockLock` ＋ 它们的 Mapper 嵌套接口 |
| **留在 `shop-core`** | `PrdSku`（它是商品定义，只有几列是库存）· `MerchantGoodsServiceImpl`（改库存那两个方法改成调 Port） |
| **新建** | 17 个实体 · `InventoryMappers` · 12 个 Service ＋ impl · 8 个 Controller · 3 个 Job · `InventoryDataSourceConfig` |

### 4.5 独立数据源要注意的两件

| # | 事 | 不做会怎样 |
|---|---|---|
| 1 | MyBatis 要**两个 `SqlSessionFactory`**，按 `basePackages` 分：`inventory.mapper` 走 `invSqlSessionFactory` | 混在一起时，`inv_*` 的查询会打到平台库 |
| 2 | **DataScope 拦截器不要装到 inv 的 factory 上** | 领域只认 `ownerId`，不认平台的数据域。装上去之后，`shop-inventory` 就依赖了 `BizContext` 的线程上下文 —— 独立交付时那个上下文不存在 |

### 4.6 会红的三个守卫（S0 要一起处理）

| 守卫 | 为什么红 | 处置 |
|---|---|---|
| `ddl-parsable` | 只扫 `shop-app/.../db/migration`，扫不到 `db/inventory` | 扩扫描目录 |
| `entity-alignment` | 同上 | 扩扫描目录 |
| **写权守卫（新）** | 首次上线就会红在 §4.1 的 1–4 处 | 那正是要收口的地方 —— **守卫与 D1 是同一件事的两面** |

## 五、命名落点检查

| 项 | 取值 | 依据 |

| 表前缀 | `inv_` | 不用 `prd_`（那是平台商品域的） |

## 六、开工顺序

| 步 | 内容 | 判据 |
|---|---|---|
| **S0-a** | 建模块 ＋ pom ＋ `InventoryDataSourceConfig`（独立 DataSource / factory / Flyway） | 空模块能起来，17 张表能建 |
