## 零、一处更正：商家类目挂**门店**，不挂主体

上一篇（[TDD-分类模型重构](./TDD-分类模型重构.md) §四）写的是「商家类目挂主体」，理由是
「商品挂主体，分组粒度要一致」。**加上「门店按资质约束品类」这条之后，那个判断不成立了** ——
门店才是被约束的那一级，货架当然也在门店上。

但这立刻撞上一个真问题：

> **商品挂主体（ADR-011），而类目约束在门店。同一件商品在 A 店的类目内、在 B 店的类目外，它算不算合规？**

三种解法，只有一种不推翻既有模型：

| | 做法 | 代价 |
|---|---|---|
| 甲 | 约束退回主体级，门店只做展示 | 不满足「门店按资质约束」这条需求 |
| 乙 | 商品改为挂门店 | **推翻 ADR-011 双键模型** —— 订单、库存、结算全要跟着改 |
| **丙** | **商品仍挂主体；约束落在「上架到门店」这一步** | **无** |

**选丙。** 而且它不是妥协，是这条链本来就该有的形状：

- 商品是**主体的资产**（一次录入，各店共用），这与今天一致；
- 「这家店卖不卖它」本来就已经是一张独立的表（`prd_store_goods`）；
- 资质校验**今天就在上架那一步**（`toggle()` 里的 `requireCategoryAuthorized`）——
  再加一道「该商品的类目在不在这家店的经营类目里」，是同一个位置的同一类判断。

一句话：**建品看主体，上架看门店。**

## 一、完整链路

```
① 平台类目维护                     运营
   两级树，每个类目挂 required_code（空 = 无门槛）
        │
        ▼
② 进件：提交资质 → 审核 → 授予经营类目码      商家 → 运营
   mch_entity_apply.qualifications  （证件）
   mch_entity.category_codes        （审核后授予的码，如 ["FOOD","FRESH_VEG"]）
        │
        ▼
③ 建店：选这家店经营的类目                    商家
   可选范围 = 无门槛类目 ∪ 主体已授权码覆盖的类目
   mch_store_category                        ← 新表
        │
        ▼
④ 建品：商品选类目                            商家
   可选范围 = **当前门店**的经营类目
   选到未加入的 → 自动加入这家店的类目（不拦）
        │
        ▼
⑤ 上架：两道闸                                商家点，服务端判
   闸一（已有）资质：required_code ∈ category_codes，且证未过期
   闸二（新增）门店：商品的 category_no ∈ 该门店的经营类目
```

**四个节点各回答一个问题，且回答的人不同**：

| 节点 | 问题 | 谁答 | 答错的后果 |
|---|---|---|---|
| ① 类目 | 这类货要什么资质 | 运营 | 门槛挂错，一整类商家上不了架 |
| ② 授权码 | 这家店**够不够格**卖这类 | 运营（凭证件） | 发多了是合规风险，发少了商家寸步难行 |
| ③ 门店类目 | 这家店**打算**卖哪几类 | 商家 | 只影响自己 |
| ④⑤ 商品类目 | 这件货归哪一类、能不能在这家店上架 | 商家 + 服务端 | 见下 |

## 二、现状对照：这条链今天断在哪

| 节点 | 现状 | 缺口 |
|:--:|---|---|
| ① | `prd_category` + `required_code` + `sys_auth_code` | ⚠️ 三级树（要降二级） |
| ② 提交资质 | `mch_entity_apply.qualifications` | ✅ |
| ② 申请时填的「经营类目」 | `mch_entity_apply.category` 是**一个 VARCHAR(64) 字符串** | 🔴 无结构。商家填「食品」，运营还得自己翻译成码 |
| ② 授予码 | `PUT /ops/merchants/{no}/auth-codes` | 🔴 **与入驻审核是两个动作**，见 2.1 |
| ③ 建店 | `POST /biz/store/create` **只收一个 name** | 🔴 没有类目这个概念 |
| ④ 建品 | 从**整棵平台树**选 | 🔴 不受门店约束 |
| ⑤ 上架闸一 | `requireCategoryAuthorized`（资质） | ✅ 已有 |
| ⑤ 上架闸二 | — | 🔴 **不存在** |

### 2.1 「入驻通过」与「授予经营类目」是两个动作，中间是断的

审核通过走 `POST /ops/merchant/apply/{no}/audit`，授码走
`PUT /ops/merchants/{no}/auth-codes` —— **后者不是前者的一部分**。

于是存在一个谁都没想过的中间状态：**审核通过了，但一个码都没授**。
商家收到「入驻通过」的通知，兴冲冲进去建品，选类目、点上架 —— 被拒。
而他看到的是「你还没有资质授权」，去哪申请没人告诉他。

> 这与 [类目树补齐方案](./类目树补齐方案.md) §五① 记的是同一类事：
> 「**一个只会拒绝的校验比没有校验更糟：它看起来在工作。**」
> 那次补的是发证机关（`sys_auth_code`），这次要补的是**发证的时机**。

**处置**：审核通过的动作里带上码。运营在审核抽屉里勾选要授予的类目码，
`audit(approved=true)` 与 `setCodes` 落在同一个事务里 —— 一次决定，一次留痕。
单独的 `PUT auth-codes` 保留，那是**事后调整**（加类目、撤类目），不是初次授予。

## 三、新表与改动

### 3.1 门店经营类目（新）

```sql
mch_store_category
  store_no       VARCHAR(64) NOT NULL     -- 挂门店：被资质约束的是门店
  entity_no      VARCHAR(64) NOT NULL     -- 冗余，数据域锚点用
  category_no    VARCHAR(64) NOT NULL     -- 引用平台类目
  display_name   VARCHAR(64)              -- 自定义显示名；空 = 用平台类目名
  sort           INT NOT NULL DEFAULT 0   -- 店铺页里的顺序，商家拖动改的就是它
  enabled        TINYINT NOT NULL DEFAULT 1
  UNIQUE (store_no, category_no)
```

**显示名只是皮**：底下的 `category_no` 不变，商家把「蔬菜」叫成「今日现摘」，跨店聚合照常成立。
自由命名的分组做不到这一点 —— 一家「蔬菜区」、一家「新鲜蔬菜」、一家「绿叶子」，聚合当场失效。

### 3.2 建店表单加类目

`POST /biz/store/create` 现在只收 `name`。加一个 `categoryNos`：

- **可选范围** = 无门槛类目 ∪ 主体已授权码覆盖的类目；
- **可以一个都不选**：那时这家店还没决定卖什么，建品时自动加入（见 §四）；
- 已有门店走 `POST /biz/store/{storeNo}/categories` 改。

### 3.3 上架闸二

```java
// MerchantGoodsServiceImpl.toggle(onSale=true) 里，紧挨着 requireCategoryAuthorized
requireStoreCategory(storeNo, g.getCategoryNo());
```

**为什么放在上架而不是建品**：与资质那道闸同一条理由 ——
商家把一件货归到一个这家店还没开的类目下不该被拦（他可能正准备开），
真正不能发生的是**它对这家店的买家可见**。

## 四、四条规则

1. **建品时选到本店未加入的类目 → 自动加入，不报错**（前提：该类目在主体授权范围内）。
   硬拦的话商家被踢去另一个页面勾选、再回来重填，而他表达的意思很清楚：「我要开始卖这类了」。
   **自动加入是把他的意思执行掉，不是放松校验。**
2. **不在主体授权范围内的类目 → 建品时就拦**，不等到上架。
   这一条与上一条相反，因为它不是「商家还没做的事」，而是「他做不了的事」——
   让他填完整个表单再告诉他不行，是最差的一种拒绝。报错里要说清缺哪张证、去哪申请。
3. **删一个底下还有商品的门店类目 → 拒绝**。不拦的话那些商品会挂在一个这家店已经不存在的
   货架上，店铺页里就此消失，而商家在商品列表里还看得到它们。
4. **撤销主体授权码时，不自动下架已上架的商品**，但要在运营侧提示影响范围。
   自动下架会让一次「调整授权」变成一次无声的批量下架 —— 而商家不知道发生了什么。
   与资质过期那条一致：过期不删已在架的，只拦新上架（另有定时任务单独处置）。

## 五、多门店时的三个具体问题

一期绝大多数是单店（主体与门店一一对应），感知不到差别。多门店时：

| 问题 | 答案 |
|---|---|
| 主体级的「我卖哪几类」是什么 | **各门店类目的并集，派生不存**。存一份就要和门店那份同步，而两份迟早分岔 |
| 一件商品能在 A 店上架、B 店不能吗 | **能**，且这正是这个模型要表达的。B 店没有那个类目，闸二拦住 |
| 新建的第二家店默认有哪些类目 | **复制默认店的**。多门店商家开分店卖的多半是同一批货，从零勾选是纯负担 |

## 七之前 · 已定：商品仍挂主体，ADR-011 不动（2026-08-21）

曾经考虑把商品整体下沉到门店。**算过账之后放弃**，记在这里免得下次重问。

多门店在这个产品里是**连锁**（一个老板、同一批货），不是各自独立的摊位。
「各店独立」如果真的成立，最省的实现从来不是把商品挂到门店，而是
**让每家店成为独立主体**（各自进件、各自收款）—— 一期主体与门店本来就一一对应，
那样一行代码都不用改。在共享主体内部再造一套隔离，是最贵的实现方式。

下沉商品的六条代价：

| # | 代价 |
|:--:|---|
| 1 | 同一件货在三家店 = 三条记录，标题/图/规格要维护三遍 —— 而「一次录入各店共用」正是多门店增值包的卖点 |
| 2 | C 端会重复：同一袋米在社区列表出现三次。现在按 `goods_no` 天然去重 |
| 3 | 商品是门店的、钱是主体的（分账收款方是主体，`stl_bill` 按主体出账），订单要同时引两层 |
| 4 | `prd_store_goods` / `prd_store_stock` 白做 —— 它们的存在理由就是「商品在上层、按店覆盖」 |
| 5 | 跨店可比只剩 `std_no` 一条线，标准品库从锦上添花变成不做就没有可比性 |
| 6 | 要写新 ADR 推翻 ADR-011，而双键模型是订单/库存/结算/履约共同的地基 |

### 三个诉求的落点（都不需要下沉商品）

| 诉求 | 落点 | 状态 |
|---|---|---|
| **各店卖不同的货** | `prd_store_goods` 覆盖语义 | ✅ **已支持**，一件货可以只在 A 店上架 |
| **各店品类不同** | `mch_store_category` + 上架闸二 | 本文 §一～§五 |
| **各店价格不同** | `prd_store_price` 覆盖表（新） | 见下 |

### 门店定价：与库存同构，但**回退方向相反**

```sql
prd_store_price
  store_no    VARCHAR(64) NOT NULL
  sku_no      VARCHAR(64) NOT NULL
  entity_no   VARCHAR(64) NOT NULL      -- 数据域锚点
  market      VARCHAR(8)  NOT NULL      -- 与 prd_sku 同构，免得开第二个市场时再改一次
  price       BIGINT      NOT NULL
  origin_price BIGINT                   -- 划线价也分店：不分的话折扣标会与实际售价对不上
  UNIQUE (store_no, sku_no, market)
```

⚠️ **这里有一处绝不能照抄库存的语义。**

| | 无门店行时 | 为什么 |
|---|---|---|
| 门店**库存** | **视为 0**（fail-closed） | 回退主体总量会让没配过的店变成无限供应。**少卖可恢复，超卖不可** |
| 门店**价格** | **回退主体价**（fail-back） | 视为 0 就是白送。这是这两张表唯一不同构的地方 |

照抄库存那套「没有行的店视为 0」，结果是**一家没配过价的店把所有货白送出去**，
而页面上显示的是 ¥0.00 —— 看起来像个 bug，实际上钱已经出去了。

**取价的唯一入口必须一起改**：`GoodsQueryPortImpl.snapshot()` 是下单、购物车、
预览三条路共用的价格入口。只改展示不改它，症状是**页面显示门店价、下单按主体价扣钱** ——
与「购物车显示特价、下单按原价」是同一形状，那次的教训就是把覆盖放在 `snapshot()` 里。

叠加顺序：**门店价是基准价，限时特价仍覆盖它**（活动是主体级的，商家给整个主体配的）。
