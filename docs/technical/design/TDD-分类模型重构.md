## 一、定下来的模型

```
① 平台类目（运营维护，两级）        prd_category
   食品生鲜
     ├ 蔬菜
     ├ 水果
     └ 预包装食品
   日用百货
     ├ 纸品清洁
     └ 家居用品
        ↓ 商家从中挑自己卖的（子集，可排序、可改显示名）
② 商家类目                          mch_entity_category  ← 新表
   李婶菜摊：蔬菜 / 水果
        ↓ 建品时只在自己的类目里选
③ 商品                              prd_goods.category_no
```

**三个节点各自回答一个问题**，谁也替代不了谁：

| 节点 | 回答 | 谁维护 | 变更代价 |
|---|---|---|---|
| ① 平台类目 | 这货**是什么**、要什么资质、是什么形态 | 运营 | 后台点几下（一级仍锁在迁移里） |
| ② 商家类目 | 这家店**卖哪几类**、店铺页怎么摆 | 商家 | 商家自己点 |
| ③ 商品的类目 | 这件货归到哪一类 | 商家（建品时） | 改一件商品 |

### 1.1 这个模型比「自由店内分类」好在哪

上一版梳理里，④「店内分类」写的是**商家自定义分组**（蔬菜区 / 熟食区，名字自己起）。
现在定成「**平台类目的子集**」，这是个更好的决定，理由是它同时解决两件事：

1. **商家要的陈列**：店铺页按他选的类目分组，与自定义分组的效果一样；
2. **平台要的可比**：三家店的「蔬菜」指向同一个 `categoryNo`。自定义分组做不到这一点 ——
   一家叫「蔬菜区」、一家叫「新鲜蔬菜」、一家叫「绿叶子」，跨店聚合当场失效。

**显示名仍然可以自定义**（`display_name` 可空），但它只是**皮**：底下的 `category_no` 不变。
商家把「蔬菜」叫成「今日现摘」，聚合照常成立。

### 1.2 为什么从三级降到两级

现有是三级（食品生鲜 › 蔬菜 › 叶菜）。降到两级的实际收益：

- **商家选类目这一步才可能存在**。三级树让「选自己卖哪几类」变成一个要展开两层的操作，
  而商家心里的答案就是「蔬菜、水果」这一层；
- **叶菜 / 根茎菜的粒度对社区电商没有用**。它服务的是搜索导购与比价，
  而这个平台一个社区就几十家店，那个粒度带来的只有录入负担。

代价是**资质粒度变粗**：现在 `required_code` 挂在三级（叶菜 → `FRESH_VEG`），
降级后挂到二级（蔬菜 → `FRESH_VEG`）。判据没变，只是范围从「叶菜」扩到「蔬菜」——
而这两者要的本来就是同一张证（食品经营许可证）。

## 二、与现有的差异（要改什么）

| # | 现状 | 目标 | 量级 |
|:--:|---|---|---|
| 1 | `MAX_LEVEL = 3`，种子里有 3 个三级节点 | 两级封顶 | 迁移 + 一行常量 |
| 2 | 商家建品时从**整棵平台树**选 | 只从**自己的类目**里选 | 新表 + 新端点 + 建品页改选择器 |
| 3 | 没有「商家类目」这个东西 | `mch_entity_category` | 新表 + B 端管理页 |
| 4 | 店铺页按上架时间平铺 | 按商家类目分组 | C 端店铺页 + B 端排序 |
| 5 | `mch_store.featured` 扁平主推列表 | 保留（「主推」与「分类」是两件事） | 不动 |

⚠️ **`mch_entity.category_codes` 不是这个东西**，别混：那是**平台批给商家的资质授权码**
（`FRESH_VEG`），决定他**能不能上架**；新表是**商家自己选的经营类目**，决定他**店里怎么摆**。
一个是平台发的证，一个是商家的货架。两者在建品链路上先后出现，但责任人不同。

## 三、三级降二级：迁移怎么走（**这条要你拍板**）

三个三级节点，各自挂着资质码，且**已经被引用**：

| 三级节点 | 父 | `required_code` | 谁在引用 |
|---|---|---|---|
| `CAT111` 叶菜 | `CAT110` 蔬菜 | `FRESH_VEG` | 标准品 `STD1001/1002/1003` |
| `CAT112` 根茎菜 | `CAT110` 蔬菜 | `FRESH_VEG` | 标准品 `STD1011/1012/1013` |
| `CAT121` 浆果 | `CAT120` 水果 | `FRESH_FRUIT` | 标准品 `STD1021/1022` |

**推荐做法（方案 A · 并入父级）**：

```sql
-- ① 资质码上移到二级：判据不变，范围从「叶菜」扩到「蔬菜」，要的是同一张证
UPDATE prd_category SET required_code='FRESH_VEG'   WHERE category_no='CAT110';
UPDATE prd_category SET required_code='FRESH_FRUIT' WHERE category_no='CAT120';
-- ② 引用三级的商品与标准品上移到父级
UPDATE prd_goods    SET category_no='CAT110' WHERE category_no IN ('CAT111','CAT112');
UPDATE prd_goods    SET category_no='CAT120' WHERE category_no='CAT121';
UPDATE prd_spu_std  SET category_no='CAT110' WHERE category_no IN ('CAT111','CAT112');
UPDATE prd_spu_std  SET category_no='CAT120' WHERE category_no='CAT121';
-- ③ 三级节点归档而不是删除 —— 历史审计要查得回「当时归的是叶菜」
UPDATE prd_category SET status='ARCHIVED' WHERE level=3;
```

**为什么归档不删**：`prd_goods` 上没有历史类目的留痕，删掉之后
「这件商品当初归在哪」就永远查不回来了。归档只是让它不再出现在选择器里。

> 备选（方案 B · 三级提为二级）会把「蔬菜」和「叶菜」变成同级，
> 语义上是错的（叶菜是蔬菜的一种），**不建议**。

## 四、新表

```sql
mch_entity_category                       -- 商家类目（商家的货架）
  entity_no      VARCHAR(64) NOT NULL     -- 挂主体，与商品一致（ADR-011 双键模型）
  category_no    VARCHAR(64) NOT NULL     -- 引用平台类目
  display_name   VARCHAR(64)              -- 自定义显示名；空 = 用平台类目名
  sort           INT NOT NULL DEFAULT 0   -- 店铺页里的展示顺序，商家拖动改的就是它
  enabled        TINYINT NOT NULL DEFAULT 1
  UNIQUE (entity_no, category_no)
```

**挂主体不挂门店**：商品挂主体，商家类目是商品的分组，两者粒度必须一致 ——
挂门店会立刻冒出「A 店有蔬菜区、B 店没有，那这件蔬菜在 B 店摆哪」这个没有答案的问题。

**不存商品与类目的关系**：那已经在 `prd_goods.category_no` 上。
这张表只回答「这家店有哪几个货架」，不回答「哪件货在哪个架上」。

## 五、链路与规则

```
运营建平台类目（两级，一级锁在迁移里）
      ↓
商家在「我的类目」里勾选 → mch_entity_category
      ↓
商家建品，类目选择器**只列自己勾过的**
      ↓ 保存
prd_goods.category_no ∈ 该商家的类目集合   ← 服务端校验
      ↓ 上架时另一道闸（不变）
required_code × mch_entity.category_codes  ← 资质准入
```

三条规则：

1. **建品时选到未加入的类目 → 自动加入**，不报错。
   硬拦的话，商家在建品页被拦住、要跳去另一个页面勾选、再回来重填 ——
   而他表达的意思很清楚：「我要开始卖这类了」。**自动加入是把他的意思执行掉，不是放松校验。**
2. **删掉一个商家类目时，如果底下还有商品 → 拒绝**，与平台类目归档同一条规矩。
   不拦的话那些商品会挂在一个这家店已经不存在的货架上，店铺页里就此消失。
3. **资质准入不变**：仍然在**上架**时校验，不在选类目或建品时。
   商家可以先把货架摆好、再去申请证。

## 七、落地顺序

| 步 | 内容 |
|:--:|---|
| 1 | 迁移：三级并二级（方案 A）+ `mch_entity_category` 建表 + `MAX_LEVEL` 改 2 |
| 2 | 后端：`/biz/categories` 增删改查（我的类目）· 建品时校验 `category_no ∈ 我的类目` + 自动加入 |
| 3 | b-app：「我的类目」管理页（勾选平台类目 / 改显示名 / 拖动排序）· 建品页类目选择器改成两级且只列我的 |
| 4 | C 端：店铺页按商家类目分组 |
| 5 | 守卫：`/biz/categories` 进 `BizEndpointPermTest`；`mch_entity_category` 登记数据域（MERCHANT 锚点 `entity_no`） |

**验收（每条要能自己红）**

1. 平台类目建到第三级 → 拒绝
2. 商家类目里没有「水果」时建一件水果商品 → **自动加入**，之后「我的类目」里能看到它
3. 删一个底下还有商品的商家类目 → 拒绝
4. 商家 A 的类目选择器里看不到商家 B 加的类目（那本来就是同一批平台类目，但排序与显示名是各自的）
5. 店铺页按商家类目分组，顺序 = 商家拖出来的顺序
