## 1. 类型梳理（本文的地基）

触达有**两个正交维度**，此前混在一起谈，导致菜单与筛选都不好画。

### 1.1 维度 A：通道（怎么送出去）

| 通道码 | 名称 | 送达对象 | 送达地址 | 后端落点 | 记 `sys_notify_log` |
|--------|------|---------|---------|---------|:---:|
| `SMS` | 短信 | 手机号 | 明文手机号 | `SmsPort` → 阿里云 / 桩 | ✅ |
| `MAIL` | 邮件 | 邮箱 | 邮箱 | `MailPort` → SMTP / 桩 | ✅ |
| `WXSUB` | 微信订阅消息 | 微信用户 | `openid` | `WxSubscribePort` → 微信 / 桩 | ✅ |
| `PUSH` | App 推送 | 已装 App 的设备 | `clientId`（个推 cid） | `PushPort` → 个推 / 桩 | ✅ |
| `INAPP` | 站内信 | 三端收件箱 | `receiver_type + receiver_no` | `MessageService.push*` | ❌ **见下** |

> ⚠️ **`INAPP` 的不对称是刻意的，不是遗漏**：站内信本身就是一张可查的表
> （`msg_message`，三端都有页面在读），再往 `sys_notify_log` 抄一份等于同一件事存两处，
> 而两处必然对不上。**发送记录页要如实说明这一点** —— 否则运营会以为
> 「站内信没发出去」，而实际是它压根不从这里过。
> 站内信要查就在各自的收件箱里查（本文 §5.4 给一个入口）。

**前四条与 `INAPP` 的根本差别**：前四条是**尽力而为**的加速通道（会失败、要留痕、要对账），
`INAPP` 是**必达的事实记录**（落库即成功）。这也是为什么只有前四条需要发送记录。

### 1.2 维度 B：业务类型（为什么送）

`sys_notify_log.biz_type`（常量在 `NotifyBizType`）：

| bizType | 含义 | 触发方 | 有操作人 |
|---------|------|--------|:---:|
| `OTP` | 登录验证码 | 系统自动 | ❌ |
| `OPS_INIT_PASSWORD` | 运营账号初始密码 | 运营建号 | ✅ |
| `OPS_RESET_PASSWORD` | 运营账号密码重置 | 运营/本人 | ✅ |
| `TEST` | **运营端手动模拟发送** | 运营 | ✅ |
| `TRADE_NOTIFY` | 交易触达（到货/退款/新订单…） | 事件驱动 | ❌ |

**两个维度是正交的**：同一个 `TRADE_NOTIFY` 会同时走 WXSUB 与 PUSH；
同一条 `SMS` 通道上既有 OTP 也有 TEST。发送记录必须能**按两个维度分别筛**。

### 1.3 维度 C：配置的三个层级（决定什么能在页面上改）

这是本文最重要的一条边界。三类配置的**存放位置与可改性完全不同**：

| 层 | 例子 | 存放 | 运营端可否改 |
|----|------|------|------------|
| **凭据** | 阿里云 AK/SK、SMTP 密码、微信 appsecret、个推 masterSecret | **环境变量**（`application.yml` 里全是 `${VAR:}`） | ❌ **只读展示「配没配」** |
| **通道业务参数** | 微信模板号映射、短信签名、发件人、推送响铃通道名 | 环境变量（现状）→ 建议迁 `sys_setting` | ⚠️ 部分可改（见 §4.2） |
| **触达策略** | 频控日上限/模板间隔、模板启停 | `sys_setting` / `msg_template` | ✅ 已可改 |

> **凭据绝不进数据库、绝不在页面上编辑**。`application.yml` 顶上那句
> 「密钥一律走环境变量，不写进这个文件、不进代码库」是既有约定，本文不推翻它。
> 页面上给运营的是**「配了没有 / 连不连得通」**，不是密钥本身 ——
> 一个能在 Web 上读写生产短信密钥的表单，泄漏一次就是全平台可群发。

## 3. 菜单拆分方案

### 3.1 拆分原则

**按通道拆，不按功能拆**。理由：运营排查触达问题时的第一个问句永远是
「**哪条通道**没到」，而不是「配置还是记录」。一条通道的配置、记录、自检放在一起，
一次排查在一个页面里完成；按功能拆则要在三个页面之间来回跳。

### 3.2 新菜单结构（L1「消息与客服」下）

```
消息与客服 /messages
├─ 触达（分组）
│   ├─ 通道总览      /messages                    ← 新：四通道状态一屏
│   ├─ 短信          /messages/sms                ← 新
│   ├─ 邮件          /messages/mail               ← 新
│   ├─ 微信订阅消息   /messages/wxsub              ← 新
│   ├─ App 推送      /messages/push               ← 新
│   ├─ 站内信        /messages/inapp              ← 新（模板 + 频控，原「消息模板与推送」）
│   └─ 发送记录（全通道）/messages/logs            ← 由原 ?tab=notifyLog 升级
└─ 客服（分组，不动）
    ├─ 客服工单与代客留痕  /messages/tickets
    └─ 帮助中心维护        /messages/faq
```

**每个通道页的统一三段式**（四页同构，学一次会用四次）：

```
┌ 通道状态 ────────────────────────┐
│ 启用/桩 · 凭据齐备 · 今日发送量/成功率 │
├ 配置 ───────────────────────────┤
│ 只读凭据清单（配了✓/缺✗）+ 可改的业务参数 │
├ 模拟发送 ────────────────────────┤
│ 收件人 + 图形验证码 → 发一条             │
├ 最近发送记录（本通道，10 条）───────────┤
│ 时间 · 业务类型 · 收件人 · 状态 · 失败原因 │
└ 「查看全部」→ /messages/logs?channel=XXX ┘
```

> **原 `/messages` 不删，改为通道总览**：老书签与 nav 里的 `href` 都还指着它；
> 删掉的话点进来是 404。总览页本身有价值 —— 四条通道的健康度一屏看完。

### 3.3 权限

**不新增权限码**，沿用 `message:template:read` / `message:template:update`
（既有注释写明：维护模板的与看记录的是同一批人，多一个码只增加配置负担）。

- 看（通道页、记录、配置只读）：`message:template:read`
- 改（业务参数、模板启停）+ **模拟发送**：`message:template:update`

## 4. 通道配置（「系统配置功能」）

### 4.1 只读部分：凭据体检

后端新增 `GET /ops/notify-channels`，返回四条通道的**体检结果**，不含任何密钥：

```jsonc
[{
  "channel": "SMS",
  "enabled": false,          // stub=false 时为 true
  "stub": true,              // 当前走桩
  "credentials": [           // 逐项「配了没有」，值一律不回传
    { "key": "ALI_SMS_AK",  "envVar": "ALI_SMS_AK",  "present": false, "required": true },
    { "key": "ALI_SMS_SIGN","envVar": "ALI_SMS_SIGN","present": false, "required": true }
  ],
  "params": [                // 非密的业务参数，可回显
    { "key": "endpoint", "value": "dysmsapi.aliyuncs.com" },
    { "key": "templates.otp", "value": "SMS_474945291" }
  ],
  "today": { "sent": 12, "failed": 1 }
}]
```

**实现要点**：`present` 由后端判断字符串非空得出，**明文永不出后端**；
模板号/endpoint/签名这类非密参数可以回显（它们本就印在短信里）。

### 4.2 可写部分：只开放三类

| 可改项 | 存放 | 为什么可改 |
|--------|------|-----------|
| 触达频控（日上限 / 同模板间隔） | `sys_setting` | 已实现（P-14.1.4），本次只是搬到通道页 |
| 模板启停（`msg_template.enabled`） | 表 | 已实现，停用即刻生效 |
| **微信订阅消息场景 → 模板号映射** | `sys_setting`（新） | mp 后台报备后会变；改它要发版是不合理的 |

> 微信模板号映射是**唯一建议从环境变量迁到 DB 的一项**：它不是密钥（模板号本身
> 不构成凭据），且报备/换模板是运营行为不是运维行为。迁移后
> `WxSubscribeGateway.templateId()` 改为读 `sys_setting`，回落到环境变量默认值。
> **两端必须同值**的约束不变（前端 `VITE_WX_TPL_*`），页面上要把这句话写在输入框旁边。

其余一律不可改：凭据（安全）、stub 开关（改它等于在生产上切真假通道，必须走发布）。

### 4.3 ★缺口 3 的修复：补 `application.yml`

```yaml
  # 微信小程序（登录 code2Session + 订阅消息）。密钥同样走环境变量。
  wx:
    stub: ${SHOP_WX_STUB:true}
    appid: ${WX_APPID:}
    secret: ${WX_SECRET:}
    mp-state: ${WX_MP_STATE:formal}
    templates:
      order-arrived: ${WX_TPL_ORDER_ARRIVED:}
      refunded: ${WX_TPL_REFUNDED:}
  # App 推送（个推 / uni-push，ADR-018；免费档）
  push:
    stub: ${SHOP_PUSH_STUB:true}
    getui:
      app-id: ${GETUI_APP_ID:}
      app-key: ${GETUI_APP_KEY:}
      master-secret: ${GETUI_MASTER_SECRET:}
```

同步补 `backend/.env.local.example`。

## 5. 模拟发送（逐通道设计）

**四条通道的模拟发送形态与风险各不相同，不能套同一个表单。**
共同点：都走 `bizType=TEST` 留痕、都要图形验证码 + 操作人限流、都写审计。

### 5.1 短信（已有，不动）

收件人=手机号，发一条固定内容的验证码。风险：**花钱 + 骚扰真人**。
现有三道闸已足够。

### 5.2 邮件（已有，不动）

收件人=邮箱。风险最低。

### 5.3 微信订阅消息（新，**风险最高，要特殊设计**）

⚠️ **不能简单照抄短信的表单**：订阅消息要消耗用户的**一次性授权额度**
（`msg_subscribe.quota`）。拿真实用户测一次，就烧掉他一次「到货通知」的机会 ——
而他攒这次额度是为了知道自己的货到了。

**设计**：
- 输入 **userNo**（不是 openid：运营手上没有 openid，且 openid 不该出现在运营界面）；
- 后端校验该用户**当前额度 > 0**，额度不足直接给出可读错误（「该用户没有可用的订阅额度，
  测试会白发」）而不是发出去被微信拒；
- **额度照常扣减**——不扣的话测的就不是真实链路（[[verify-on-real-path]]）；
- 页面上必须写明这句话：**「会消耗该用户一次真实的订阅额度，请用测试账号」**。

### 5.4 App 推送（新）

**输入 userNo，不是 clientId** —— 运营拿不到 cid。后端按 `msg_push_token` 查该用户
绑定的设备，没有设备时给可读错误（「该用户没有绑定 App 设备，可能没装或没登录过 App」）。

- 可选 **提醒级别**（NORMAL / RING）：RING 是 B 端新订单的形态，
  上线前必须能在真机上验一次它到底响不响（免费档下还受厂商配额约束）。
- 一个人多台设备时全推，返回推了几台。

### 5.5 站内信（新，形态不同）

站内信不进 `sys_notify_log`，它的「模拟发送」= 往某个收件箱塞一条消息。
- 输入：收件人类型（USER/STAFF/OPS）+ 编号 + 标题/正文/落点链接；
- 用途：验证三端收件箱与角标链路；
- **不需要图形验证码**（它发不出平台，骚扰不到外部），但仍要权限码 + 审计。

### 5.6 统一的失败可读化

四个通道的失败原因今天是通道原文（如 `个推拒绝：10003 token 过期`）。
方案：**原文照留**（排查要它），但页面在原文之上加一层**可读归因**：

| 形状 | 归因文案 |
|------|---------|
| 凭据类错误码 | 「凭据无效或未配置 —— 去通道配置检查」 |
| 配额/限流类 | 「通道配额已用尽（免费档有日配额）」 |
| 收件人类（cid 失效/未订阅） | 「收件人不可达：未装 App / 未授权 / 已卸载」 |
| 网络类 | 「通道网络异常，可重试」 |

### 实施中偏离方案的三处（都是方案没想到的）

1. **微信模板号覆盖放在装饰器，不放在网关**。方案原写「网关读 `sys_setting`」，
   实测后发现两个问题：走桩时覆盖完全不生效（桩不读配置，运营在本地改了看不出效果），
   且 `shop-channel` 会因此依赖数据库。现改为 `NotifyLoggingWxSubscribePort` 叠加覆盖 ——
   模板号映射是**领域配置**，通道只认自己那份。副产品：常量落在 SPI 契约上
   （`WxSubscribePort.TEMPLATES_SETTING_KEY`），core 与 channel 都能引用而不互相依赖。
2. **新增预检端点**。图形验证码是一次性的，而「这个用户没额度 / 没绑设备」输完 userNo
   就能知道。不预检的话，运营填完表、输完验证码、点了发送才被告知「换个账号」，
   那张验证码已经废了。预检与真正发送**共用同一份判断**，不写两遍。
3. **菜单要落 Flyway 迁移**（V140）。ops-web 的菜单标签与权限来自 DB 的
   `sys_function_point`，`nav.ts` 只是生成器的真源与本地回落。只改 `nav.ts` 的话，
   本地开发看得到、接上真实后端就没有 —— 按 V99/V103 的惯例跑生成器取新增行。
   ⚠️ 角色授权必须**逐行**写 `INSERT ... SELECT ... FROM DUAL`：
   `gen-test-schema.py` 不认 `CROSS JOIN` 形式，写成一条会让 H2 那份 schema 里
   一条授权都没有（症状是 `superAdminHasEveryPoint` 少 5 条）。

## 8. 风险与注意事项

1. **★1 是当前就在骗人的缺陷**：推送/订阅消息的记录显示成「短信」。
   本方案落地前，运营看这张表得出的结论都是错的 —— 建议 B3 优先做。
2. **微信订阅消息的模拟发送会烧真实用户额度**（§5.3）。文案必须写明，
   否则第一次用它的人会拿正式用户测。
3. **凭据不进 DB** 是硬边界（§1.3）。若后续有「多租户各配各的短信账号」需求，
   那是另一个话题（需要加密存储 + 密钥轮换），不在本方案内。
4. 菜单从 4 条变 9 条，`/messages` 老路径保留为总览页避免 404。
5. 免费档配额（ADR-018）会让推送的模拟发送在配额耗尽时失败 —— 归因文案要能说清
   「不是你配错了，是今天的免费额度用完了」。
