## 三、核心对象关系与状态

- 商品域Product/SKU → 餐饮Dish/Menu/Bundle/Option；基础价格及库存不复制，配置发布冻结版本。
- DiningCheck 1:N OrderBatch；一台账多桌、多台账一桌经Occupancy关联；Reservation可转Check。
- OrderBatch 1:N CoreOrderBinding及FoodLine；FoodLine经Allocation关联ord_item，支持多源行分配到同一核心行且数量守恒；batch.check_no保存原就餐归属，当前服务归属用membership追加记录。
- FoodLine 1:N Component/Modifier及KitchenTask；Task经ServiceEvent登记分批制作上菜，Course与Seat支持西餐。
- Settlement 1:N ScopeItem及ChargeIntent；资金分配由核心持有，Return关联菜品及正式售后，不能直接修改核心状态。
- BusinessDay 1:N CloseRun版本；CashShift可跨营业日，现金按真实发生归班归日；CloseRun引用权威资金和Report水位快照。

| 对象 | 目标状态与关键守卫 |
|---|---|
| Check | 无交易接待可OPEN→VOIDED/RELEASED；正式交易OPEN→SETTLING→CLOSED；冻结后加菜阻止或显式新范围；有未结资金不能伪结清；MERGED保留来源 |
| Batch | PREPARED→PLACING→BOUND→ACCEPTED；UNKNOWN以原幂等请求查询恢复，不另建单 |
| Task | HELD/QUEUED→MAKING→READY→SERVED；以数量事实决定分批状态；VOID须退餐授权 |
| Settlement | DRAFT→FROZEN→COLLECTING→SETTLED；取消要求无未知或不可撤销资金，核心结清才终结 |
| Return | REQUESTED→APPROVED→PROCESSING→COMPLETED；财务与厨房分轨完成 |
| CloseRun | DRAFT→CHECKING→REVIEW→SIGNED；水位/指纹一致且差异已处理或获准结转；签核不可覆盖 |

制作与财务分属不同聚合；跨域动作使用本地意图/outbox及幂等恢复，不使用跨服务数据库事务。集成模式也遵循相同契约；餐饮应用不写prd/ord/pay表。

## 五、现状依据与取舍

当前真实OrderService.create/createFor/preview/pay/payResult可适配；其Item(goodsNo,skuNo,int qty)没有源行、选配及小数计量透传。ord_order是支付根，ord_sub_order是门店订单，ord_item.id是稳定成交行。基础商品字典prd_spec_dim/prd_spec_value继续复用。源行映射、堂食交付、后付库存、跨根收款、部分退款分别补合同，不能因目标表存在就认定已实现。当前退款仍为整门店订单全额边界。

餐饮菜单不用基础后台类目替代；餐饮口味不再复制字典；套餐/配料组合是配置候选，通用Bundle/Modifier能力确认后复用或迁移，不能双维护。共享打印prn_device与历史prn_printer需选其一；报表新增营业日维度不改变原自然日统计。旧菜品ER被本源中的口味与行分配修订取代，不把两份DDL同时执行。

## 六、实施前验证闸门

领域及表数量是本轮候选设计，不是最终迁移预算。必须逐项确认通用资源/选配/计量/审批/资金接口实现、匿名主体、日结资金对账及专项业态合同；数据库逻辑引用不自动转跨库FK。12域及109项仅表示设计追踪覆盖，完整性能和所有边缘场景仍按需求验收。
