# 商品 · 规格 · 参数：模型、分层与查询性能

状态：现状梳理 + 分阶段建议（2026-08-28）
关联：[数据库表清单](../reference/数据库表清单.md)、[B端商品管理-节点梳理](./B端商品管理-节点梳理.md)

---

## 0. 结论先行

**现有模型的主干是对的，不要推倒。** 它已经在关键的一处做了反范式，而且做对了：
写侧（商家建品）用规范化的规格库，读侧（买家浏览）用 `prd_goods` 上的 JSON 快照，
**C 端详情页一行读出全部规格，不连一张表**。

真正的问题不在范式，在三件更具体的事：

| # | 问题 | 证据 | 现在疼吗 |
| --- | --- | --- | --- |
| 1 | **C 端最热的列表查询一个索引都用不上** | 生产 `EXPLAIN`：`type=ALL`、`possible_keys=NULL`、`Using filesort` | 不疼（380 行），到万级开始疼 |
| 2 | **`prd_goods` 冷热混在一张表**：43 列、8 个 TEXT，列表页只要其中 ~10 列 | `information_schema` | 不疼（大字段平均 59 字节，都是空的），上了富文本详情就疼 |
| 3 | **列表页有一处 N+1**：批量接口被逐行调用 | `GoodsServiceImpl.java:147` | 20 行/页 = 20 次调用，现在也在发生 |

**「不能仅按三范式」这个判断是对的**，但要说清反范式**反哪几处、代价记在哪、谁来保一致**——
否则下一个人看到冗余列会顺手「规范化回去」，那才是最贵的一次改动。§4 就是为此写的。

⚠️ **今天生产只有 380 个商品 / 396 个 SKU。** 下面每一条都标了「到什么量级再做」——
现在全做完是浪费，而有几条**现在做便宜、以后做贵**（改表结构要停机，加索引不用）。

## 1. 三个概念到底是什么

这三个词在电商语境里最容易混，先钉死：

| | 是什么 | 分不分 SKU | 举例 | 落在哪 |
| --- | --- | --- | --- | --- |
| **商品**（SPU） | 一件在卖的东西 | — | 「烟台红富士」 | `prd_goods` |
| **规格**（SALE 维度） | **决定价格与库存**的选项轴 | **分** | 重量：5 斤 / 10 斤 | `prd_spec_dim` + `prd_spec_value` |
| **参数**（PROP 维度） | **只写给买家看**的属性 | **不分** | 产地：烟台；保质期：7 天 | 同上两张表 |

**规格与参数共用同一套表，只差 `usage_type` 一个字段**（`SALE` / `PROP`）。
这不是偷懒 —— 它们的结构完全一样（有轴、有可选值、要归一），
差别只在「要不要生成 SKU」。分两套表会让「产地」将来想变成规格时无路可走。

> 代码里这条判据在 `SpecLibraryServiceImpl.forCategory` 的 `wantUsage`。
> 把 PROP 误当 SALE 下发，商家就会把「不锈钢」建成一个要单独定价备库存的 SKU 轴。

### 值有身份，才谈得上比价

`prd_spec_value` 每个值有 `value_no` + `code` + `numeric_value`。
`numeric_value` 是**归一量**：500g / 半斤 / 0.5kg 都存 500。
没有它，「按规格排序」会把 1kg 排在 500g 前面，「同规格跨店比价」根本无从谈起。

### 四层裁剪：平台 → 类目 → 商家 → 门店

```
prd_spec_dim / prd_spec_value          平台值池：这根轴上一共有哪些档
        ↓ prd_category_spec(_value)    类目裁剪：蔬菜这一类用哪几根轴、每根用哪几档
        ↓ prd_merchant_spec_override   商家覆盖：本店用哪几个、什么顺序、叫什么
        ↓ prd_store_goods/price/stock  门店差异：这家店卖不卖、什么价、还有几件
```

**每一层都是「稀疏」的：没有行 = 完全跟上一层走。**
这条性质很值钱——运营给类目加一个新档位，没动过手的商家**自动获得它**，
不需要回填任何行。代价是读侧要做一次合并（§3）。

## 2. 写侧与读侧是两条路 —— 这是全篇最重要的一件事

```
┌── 写侧（B 端建品 / 我的规格）───────────────────────────────┐
│  规范化的规格库，四层合并，N+1 查询                          │
│  SpecLibraryServiceImpl.forCategory：~10-15 条 SQL / 次      │
│  QPS 极低（商家一天建几次品），可读性 > 性能                  │
└──────────────────────────┬───────────────────────────────┘
                           │  建品时**拍一张快照**
                           ▼
              prd_goods.spec_groups  (TEXT / JSON)
              prd_goods.params       (TEXT / JSON)
              prd_sku.option_values  (文案) + option_value_nos (编号)
                           │
┌──────────────────────────▼───────────────────────────────┐
│  读侧（C 端列表 / 详情）                                    │
│  **不碰规格库任何一张表**，反序列化 JSON 即可                 │
│  GoodsServiceImpl.toVO：0 条额外 SQL                        │
└──────────────────────────────────────────────────────────┘
```

**快照不是缓存，是业务语义。** 商家事后把「5 斤」改叫「约 2.5 公斤」，
**已经建好的商品不跟着变** —— 买家下单时看到的规格，必须和他当时看到的一致。
所以这里的「不一致」是要的，不是要修的。

> 这一点必须写下来，否则迟早有人认为 `spec_groups` 是冗余、
> 改成实时 join 规格库「保证一致性」—— 那会让所有历史订单的规格文案跟着漂移。

**同理 `prd_sku` 同时存 `option_values`（文案）与 `option_value_nos`（编号）**：
前者给人看（快照，不变），后者给机器聚合（身份，跨店可比）。少任何一个都不行。

## 3. 实测：现在的瓶颈在哪

### 3.1 列表查询：全表扫 + 文件排序（最要紧的一条）

`GoodsServiceImpl.list()` 生成的 SQL 大致是：

```sql
SELECT * FROM prd_goods
 WHERE deleted=0 AND on_sale=1 AND audit_status='APPROVED' AND category_no=?
 ORDER BY sales DESC LIMIT 20;
```

生产库上 `EXPLAIN` 的结果：

```
type: ALL | possible_keys: NULL | key: NULL | rows: 380 | Extra: Using where; Using filesort
```

`prd_goods` 上只有三条二级索引（`V1__baseline.sql`）：

```
KEY idx_entity (entity_no)      KEY idx_type (type)      KEY idx_title (title(32))
```

**过滤用的四个列一个都没索引，排序列 `sales` 也没有。**
380 行时这是免费的；38 万行时它是一次全表扫 + 一次外部排序，
而它是 C 端首页、分类页、搜索页**每一次翻页**都要跑的那条。

### 3.2 关键词搜索：`LIKE '%kw%'` 永远用不上索引

代码注释写着「S1 用 like 前缀索引」，但 MyBatis-Plus 的 `like()` 生成的是
**两边通配** `%kw%`，前缀索引 `idx_title(title(32))` 对它无效
（要前缀索引得用 `likeRight()`）。`EXPLAIN` 同样是 `type=ALL`。

> 这不是「注释写错了」这么简单：它让人以为搜索这条路已经有索引兜底，
> 于是「上 ES」这件事的紧迫性被低估了。

### 3.3 一处正在发生的 N+1

`GoodsServiceImpl.java:147`：

```java
.map(g -> toVO(g, skus.get(...),
        campaignPort.flashPrices(List.of(g.getGoodsNo())).get(g.getGoodsNo())))
//                              ↑ 批量接口，被逐行调用。20 行/页 = 20 次
```

同一个文件里 `promoted()`（:99）与 `detailAll()`（:180）用的是**批量形式**，
:175 还留着一句注释说「都有批量版」—— 说明有人知道，只是漏了 `list()` 这一处。

### 3.4 社区池：先查 ID 再 `IN (...)`

社区筛选是「先查 `prd_community_pool` 拿全部 `goodsNo`，再 `WHERE goods_no IN (...)`」。
生产上最大的社区池是 **137 条**，还行。到几千条时这条 SQL 的文本本身就是几十 KB，
且 `IN` 大列表会让优化器放弃索引。

### 3.5 冷热混表

`prd_goods` **43 列，其中 8 个 TEXT/LONGTEXT**
（`images` `detail` `spec_groups` `sellable_override` `title_i18n` `subtitle_i18n`
`detail_images` `params`）。列表页真正要的是 ~10 列。

今天这几个大字段平均只有 **59 字节**（多是空的），所以全表扫很快。
一旦商品详情用上富文本（`detail` 动辄几 KB 到几十 KB），
**每翻一页都在把用不到的详情正文读进内存**。

### 3.6 全后端零缓存

`grep -c "@Cacheable"` = **0**。每一次请求都落到 MySQL。
类目树、规格库、平台值池这些**几乎不变、所有人都读**的数据也不例外。

## 3.7 JSON 快照方案的代价 —— 这是全篇最该看清的一节

§2 说快照方案「做对了」，指的是**读路径**。它同时有一笔明确的账，
而这笔账在这个仓库里**已经付过两次了**，不是推演。

### (1) 改 JSON 里的一个字段 = 整块重写，而且没有部分更新

`spec_groups` 是 TEXT 里的一段 JSON。要给所有商品的规格组补一个 `templateNo` 字段，
数据库层面**没有「改这一个 key」这种操作**——只能把整个值读出来、改完、整个写回去。

实际发生的两次：

| 迁移 | 行数 | 做了什么 | 结果 |
| --- | --- | --- | --- |
| `V229__backfill_goods_spec_dims.sql` | **255 行** | 逐条 `UPDATE prd_goods SET spec_groups='<整块新 JSON>' WHERE goods_no=? AND spec_groups='<整块旧 JSON 原文>'` | 198 件里回填 **105** 件，放弃 92 件 |
| `V236__backfill_goods_spec_dims_2.sql` | 73 行 | 同样的手法再来一轮 | 又拿下 **22** 件，仍剩 1 件回填不了 |

三个细节值得单独记：

- **一行商品一条 UPDATE。** 不能写成一条带 `WHERE` 的批量语句，因为新值逐行不同，
  而 JSON 里没有可供 `SET` 的列。这两条迁移是**脚本生成**出来的。
- **`WHERE` 里要带整块旧 JSON 的原文精确匹配**，当乐观锁用（迁移注释原话：
  「商家若在这中间改过这件商品，那一条就不该再套用旧快照」）。
  如果是普通列，一个 `version` 字段就够了；JSON 整块重写只能拿全文当版本号。
- **回填不了的那些是永久欠账。** 71 件放弃，理由写在 V229 末尾（类目没绑维度、
  语义是「计价单位」而非规格）。规范化存储里这些是 `NULL` 外键、一眼可查；
  JSON 里它们是一段**长得和别人一样、只是少了个 key** 的文本。

### (2) 查 JSON 里的字段：现在不需要，而这正是风险所在

全仓扫下来，**没有任何一条 SQL 查 JSON 内部**（没有 `JSON_EXTRACT`、没有 `->`、
没有对 `spec_groups` 的 `LIKE`）。读路径只是整块反序列化，所以今天不疼。

但 `prd_sku.option_value_nos` 与 `spec_groups.optionCodes` 存进去的**恰恰是身份**——
它们存在的唯一理由是「将来能按规格聚合、跨店比价」（§1「值有身份，才谈得上比价」）。
而这类查询长这样：

```sql
-- 「所有 5 斤装的苹果，哪家便宜」
WHERE 某个 SKU 的规格值集合 包含 'SV_WEIGHT_W2500G'
```

**这个形状答不了那个问题**，而且「误命中」不是假设 —— 生产库里现成就有：

```
SELECT value_no FROM prd_spec_value WHERE value_no LIKE 'SV_COUNT_C1%';
   SV_COUNT_C1 / SV_COUNT_C10 / SV_COUNT_C100 / SV_COUNT_C12     ← 四个都在
```

`LIKE '%SV_COUNT_C1%'` 会把这四个**全部**命中。要精确匹配就得连边界一起写
（`'%"SV_COUNT_C1"%'`），而那依然**用不上任何索引**——
MariaDB 没有 PostgreSQL 那种能直接索引数组元素的 GIN。

顺带一提：`option_value_nos` 的列类型是 **`varchar(512)`，不是 JSON 类型**
（`option_values` 同）。也就是说连「这是不是一段合法 JSON」数据库都不校验。
512 这个上限今天很宽裕（生产最长 20 字符），但它是个硬上限，
规格轴多起来时要复核 —— 三根轴 ×20 字符加括号引号已经八十多。

> 也就是说：**数据被认真地赋予了身份，然后被存进了一个按身份查不了的形状里。**
> 这不是现在的 bug，是一颗定时的：比价功能一开工就会撞上，
> 而那时要动的是存量所有 SKU 的存储结构。

**该怎么留后路**（不必现在做，但要现在知道）：
建一张 `prd_sku_spec_value (sku_no, dim_no, value_no, numeric_value)` 倒排表，
**由写侧在保存 SKU 时同步落行**。JSON 继续留着给读路径用，倒排表只服务聚合与筛选。
这是「同一份数据两种形状」——**又一次反范式**，代价记在写侧。

> ⚠️ 另记一笔：`prd_goods.params`（商品参数）在生产库里**每一行都是 NULL**。
> 参数这条路线**还没有任何真实数据**，所以上面关于它的判断都只是结构推演，
> 没有实测支撑 —— 真要动它之前得先有货。

### (3) 没有类型与结构约束，schema 会静默漂移

V229 注释里的原话最能说明问题：

> 线上 198 件带规格的商品里，**只有 1 件的规格组带 `templateNo`**。

`spec_groups` 的形状随代码演进（后来加了 `templateNo`、`optionCodes`），
而**已经写进去的行不会跟着变**，数据库也不会报任何错。
于是「新老两种形状并存」这件事，是靠人翻数据翻出来的，不是被任何守卫拦下的。

规范化的列做同一件事：加列 → 老行是 `NULL` → `WHERE x IS NULL` 一句话数得清。

### (4) 并发写覆盖

两个人同时编辑同一件商品的不同规格组，各自读出整块 JSON、各改各的、各写回去 ——
**后写的把先写的整块盖掉**。`prd_goods` 有 `version` 乐观锁列，
所以这一条在应用层是挡住的；但要意识到挡住它的是乐观锁，不是存储结构。
规范化存储里两个人改不同的行，本来就不冲突。

### 小结：这四条各自该怎么办

| 代价 | 现在的处置 |
| --- | --- |
| 改 JSON 内字段 = 整块重写 | **接受**。这类回填是低频的（两次），且脚本生成 + 原文匹配的做法是对的 |
| 按规格值查询/聚合 | **留后路**：比价功能开工前先建倒排表，别等撞上 |
| schema 静默漂移 | **补一道守卫**：扫 `spec_groups` 里缺 `templateNo` / `optionCodes` 的行并报数，接进现有闸门 |
| 并发覆盖 | 已由 `version` 乐观锁挡住，无需额外动作 |

## 4. 该反范式的地方 —— 以及代价记在哪

> 三范式解决的是**写入时的更新异常**。互联网读多写少的场景里，
> 读一次要拼四层裁剪、跨五张表，这个成本乘以 QPS 之后远大于冗余带来的写入成本。
> 所以反范式不是「破坏规范」，是**把 join 的成本从每次读挪到每次写**。
> 关键是：**每一处冗余都要写明谁来维护、不一致了会怎样。**

### 4.1 已经做对的（**别规范化回去**）

| 冗余 | 在哪 | 为什么 | 不一致时 |
| --- | --- | --- | --- |
| `spec_groups` / `params` JSON 快照 | `prd_goods` | C 端一行读出全部规格，不连表 | **故意的**：快照就该不跟随规格库改名 |
| `option_values`（文案）+ `option_value_nos`（编号） | `prd_sku` | 前者给人看、后者给机器聚合 | 同上，文案是快照 |
| `numeric_unit` | `prd_spec_value` | 「不连表就能比」（DDL 注释原话） | 与维度 `unit` 同源，改维度单位要一起改 |
| `store_name` | `prd_goods` | 列表页显示店名，免去 join 商家表 | 商家改名后旧行会陈旧 → **需要一个回填任务，目前没有** |
| `sales` / `rating` / `rating_count` | `prd_goods` | 排序列必须在本表，否则无法用索引排序 | 允许延迟，最终一致即可 |

⚠️ `store_name` 那一行是**已知欠账**：商家改名后列表页会显示旧名，
而没有任何机制会修正它。要么补一个订阅商家改名事件的回填，要么承认它是快照并写进文档。

### 4.2 建议新增的反范式

#### (a) 列表读模型：把过滤条件与排序键收进一张窄表

```
prd_goods_list  (读模型，写侧维护)
  community_no, category_no, goods_no,
  title, cover, store_name, min_price, sales, on_sale_at
  PRIMARY KEY (community_no, category_no, sales DESC, goods_no)
```

**一次查询解决社区筛选 + 类目筛选 + 排序 + 分页**，
既去掉 §3.4 的 `IN` 大列表，也去掉 §3.5 的宽行读取。
一个商品铺 N 个社区就有 N 行 —— 这正是反范式：**用空间换掉每次读的那个 join**。

维护：商品上下架 / 改价 / 铺货变更时由 outbox 事件驱动重建该商品的行。
不一致的表现是「列表里还能看到已下架的商品，点进去提示已下架」——
可接受，且详情页是权威。

> **到 5 万商品 / 或社区池上千条时再做。** 现在做等于凭空多一张要维护一致性的表。

#### (b) 冷热拆表：`prd_goods` 瘦身

把 `detail` / `detail_images` / `sellable_override` 这三个只有详情页要的大字段
挪到 `prd_goods_detail (goods_no PK, ...)`。
`spec_groups` / `params` **留在主表** —— 列表页的规格摘要要用。

> **到详情正文平均超过 2KB 时再做**（现在 59 字节）。改表要停机，
> 而加索引不用 —— 所以这条排在索引后面。

#### (c) 类目树与规格库进本地缓存

它们是「几乎不变 + 所有人都读」，是缓存收益最高的一类。
`@Cacheable` + 运营改动时 `@CacheEvict` 即可，不需要引 Redis。

> **现在就可以做**，成本低、风险低。

### 4.3 明确**不**建议做的

- **不要把 `prd_spec_value` 的 `label` 冗余进 `prd_category_spec_value`。**
  那一层已经有 `label_override`（类目内换名），再冗余一份就有两个「本类目叫什么」，
  而它们会分岔。
- **不要为了「查得快」把规格拍平成 `spec1/spec2/spec3` 列。**
  轴的数量是业务变量（有的类目 2 根，有的 5 根），拍平之后加第 6 根要改表。
  现在的 JSON 快照已经解决了读的问题。
- **不要现在引 ES。** 380 个商品，`LIKE` 全表扫也是毫秒级。
  到 5 万商品或搜索 QPS 上来时再上，接口 `GoodsService` 不变（这一点原设计已经留好了）。

## 5. 分阶段建议

### 第一阶段 · 现在就做（成本低、不改表结构、不会白做）

| # | 做什么 | 为什么现在做 |
| --- | --- | --- |
| 1 | **补 `prd_goods` 的复合索引**（见下） | 加索引不停机，且量上来之后再加要锁表 |
| 2 | 修 `GoodsServiceImpl:147` 的 N+1 | 三行改动，现在就在发生 |
| 3 | 改掉「用 like 前缀索引」那句错注释 | 它让人低估了搜索这条路的欠账 |
| 4 | 类目树 / 规格库加本地缓存 | 收益最高、风险最低的一类缓存 |

索引要**两条**，不是一条：

```sql
-- 带类目的（分类页）
CREATE INDEX idx_goods_cat_sales ON prd_goods (deleted, on_sale, audit_status, category_no, sales);
-- 不带类目的（首页 / 全站列表）
CREATE INDEX idx_goods_sales     ON prd_goods (deleted, on_sale, audit_status, sales);
```

**为什么不能只建第一条**：不带 `category_no` 时，索引前缀停在 `audit_status`，
中间跳过了 `category_no`，`sales` 就**不能用于索引排序**了。

这一条我在生产库上拿现成的 `idx_stl_pool_channel (market, pay_channel, id)` 实测过：

```
WHERE market=? AND pay_channel=? ORDER BY id   → key=idx_stl_pool_channel, ref=const,const, 无 filesort
WHERE market=?                  ORDER BY id   → key=PRIMARY  ← 优化器整个放弃了那条复合索引
```

**实测比我原本的说法更准确**：跳过中间列时优化器不是「用索引再 filesort」，
而是**整条索引都不用了**。上面那个例子里它退到扫主键（因为排序列恰好就是主键，
扫主键白得一个有序序列）；而 `prd_goods` 的排序列是 `sales`，**没有这个便宜可占**，
退化的结果就是 §3.1 那个 `ALL + filesort`。

> ⚠️ 那张表当时只有 1 行、`Cardinality=0`，所以这个执行计划只能用来说明
> **优化器的选择方向**，不能当作性能数据。真要定论得在有数据的表上复测。

### 第二阶段 · 到 5 万商品 / 社区池上千条

- 列表读模型表（§4.2a）
- 搜索切 ES 或 MySQL ngram 全文索引

### 第三阶段 · 详情正文变大之后

- 冷热拆表（§4.2b）
- 门店价/库存读模型（`prd_store_price` / `prd_store_stock` 现在**是空表**，
  多门店读路径还没被点亮；点亮那天读侧会多两次查询，要一起进读模型）

## 6. 怎么验证（不能只看「感觉快了」）

每一条改动都要有**能证伪的判据**：

| 改动 | 判据 |
| --- | --- |
| 加索引 | 同一条 SQL 的 `EXPLAIN` 从 `type=ALL` + `filesort` 变成 `type=range/ref` 且 **Extra 里没有 filesort** |
| 修 N+1 | 一次列表请求的 SQL 条数从 `1 + 1 + N` 降到 `1 + 1 + 1`（用 p6spy 或 MyBatis 日志数，别估） |
| 加缓存 | 第二次请求的 SQL 条数为 0；**并且撤掉缓存要变回非 0**（否则测的可能是别的东西） |
| 读模型 | 造 5 万商品的压测数据再比 —— **在 380 行上测不出任何东西**，这一点必须先说清 |

⚠️ **在 380 行的库上做性能对比是没有意义的**：全表扫 380 行和走索引查 20 行
都是亚毫秒，差异全在噪声里。要么造数据，要么就只用 `EXPLAIN` 的**执行计划形状**
当判据（上面第一行就是这么写的）——**别拿计时数字说事**。
