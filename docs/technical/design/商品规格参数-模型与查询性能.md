# 商品 · 规格 · 参数：模型、分层与查询性能

状态：现状梳理 + 分阶段建议（2026-08-28）
关联：[数据库表清单](../reference/数据库表清单.md)、[B端商品管理-节点梳理](./B端商品管理-节点梳理.md)

---

## 0. 结论先行

**现有模型的主干是对的，不要推倒。** 它已经在关键的一处做了反范式，而且做对了：
写侧（商家建品）用规范化的规格库，读侧（买家浏览）用 `prd_goods` 上的 JSON 快照，
**C 端详情页一行读出全部规格，不连一张表**。

真正的问题不在范式，在三件更具体的事：

| # | 问题 | 证据 | 现在疼吗 |
| --- | --- | --- | --- |
| 1 | **C 端最热的列表查询一个索引都用不上** | 生产 `EXPLAIN`：`type=ALL`、`possible_keys=NULL`、`Using filesort` | 不疼（380 行），到万级开始疼 |
| 2 | **`prd_goods` 冷热混在一张表**：43 列、8 个 TEXT，列表页只要其中 ~10 列 | `information_schema` | 不疼（大字段平均 59 字节，都是空的），上了富文本详情就疼 |
| 3 | **列表页有一处 N+1**：批量接口被逐行调用 | `GoodsServiceImpl.java:147` | 20 行/页 = 20 次调用，现在也在发生 |

**「不能仅按三范式」这个判断是对的**，但要说清反范式**反哪几处、代价记在哪、谁来保一致**——
否则下一个人看到冗余列会顺手「规范化回去」，那才是最贵的一次改动。§4 就是为此写的。

⚠️ **今天生产只有 380 个商品 / 396 个 SKU。** 下面每一条都标了「到什么量级再做」——
现在全做完是浪费，而有几条**现在做便宜、以后做贵**（改表结构要停机，加索引不用）。

## 1. 三个概念到底是什么

这三个词在电商语境里最容易混，先钉死：

| | 是什么 | 分不分 SKU | 举例 | 落在哪 |
| --- | --- | --- | --- | --- |
| **商品**（SPU） | 一件在卖的东西 | — | 「烟台红富士」 | `prd_goods` |
| **规格**（SALE 维度） | **决定价格与库存**的选项轴 | **分** | 重量：5 斤 / 10 斤 | `prd_spec_dim` + `prd_spec_value` |
| **参数**（PROP 维度） | **只写给买家看**的属性 | **不分** | 产地：烟台；保质期：7 天 | 同上两张表 |

**规格与参数共用同一套表，只差 `usage_type` 一个字段**（`SALE` / `PROP`）。
这不是偷懒 —— 它们的结构完全一样（有轴、有可选值、要归一），
差别只在「要不要生成 SKU」。分两套表会让「产地」将来想变成规格时无路可走。

> 代码里这条判据在 `SpecLibraryServiceImpl.forCategory` 的 `wantUsage`。
> 把 PROP 误当 SALE 下发，商家就会把「不锈钢」建成一个要单独定价备库存的 SKU 轴。

### 值有身份，才谈得上比价

`prd_spec_value` 每个值有 `value_no` + `code` + `numeric_value`。
`numeric_value` 是**归一量**：500g / 半斤 / 0.5kg 都存 500。
没有它，「按规格排序」会把 1kg 排在 500g 前面，「同规格跨店比价」根本无从谈起。

### 四层裁剪：平台 → 类目 → 商家 → 门店

```
prd_spec_dim / prd_spec_value          平台值池：这根轴上一共有哪些档
        ↓ prd_category_spec(_value)    类目裁剪：蔬菜这一类用哪几根轴、每根用哪几档
        ↓ prd_merchant_spec_override   商家覆盖：本店用哪几个、什么顺序、叫什么
        ↓ prd_store_goods/price/stock  门店差异：这家店卖不卖、什么价、还有几件
```

**每一层都是「稀疏」的：没有行 = 完全跟上一层走。**
这条性质很值钱——运营给类目加一个新档位，没动过手的商家**自动获得它**，
不需要回填任何行。代价是读侧要做一次合并（§3）。

## 2. 写侧与读侧是两条路 —— 这是全篇最重要的一件事

```
┌── 写侧（B 端建品 / 我的规格）───────────────────────────────┐
│  规范化的规格库，四层合并，N+1 查询                          │
│  SpecLibraryServiceImpl.forCategory：~10-15 条 SQL / 次      │
│  QPS 极低（商家一天建几次品），可读性 > 性能                  │
└──────────────────────────┬───────────────────────────────┘
                           │  建品时**拍一张快照**
                           ▼
              prd_goods.spec_groups  (TEXT / JSON)
              prd_goods.params       (TEXT / JSON)
              prd_sku.option_values  (文案) + option_value_nos (编号)
                           │
┌──────────────────────────▼───────────────────────────────┐
│  读侧（C 端列表 / 详情）                                    │
│  **不碰规格库任何一张表**，反序列化 JSON 即可                 │
│  GoodsServiceImpl.toVO：0 条额外 SQL                        │
└──────────────────────────────────────────────────────────┘
```

**快照不是缓存，是业务语义。** 商家事后把「5 斤」改叫「约 2.5 公斤」，
**已经建好的商品不跟着变** —— 买家下单时看到的规格，必须和他当时看到的一致。
所以这里的「不一致」是要的，不是要修的。

> 这一点必须写下来，否则迟早有人认为 `spec_groups` 是冗余、
> 改成实时 join 规格库「保证一致性」—— 那会让所有历史订单的规格文案跟着漂移。

**同理 `prd_sku` 同时存 `option_values`（文案）与 `option_value_nos`（编号）**：
前者给人看（快照，不变），后者给机器聚合（身份，跨店可比）。少任何一个都不行。

## 3. 实测：现在的瓶颈在哪

### 3.1 列表查询：全表扫 + 文件排序（最要紧的一条）

`GoodsServiceImpl.list()` 生成的 SQL 大致是：

```sql
SELECT * FROM prd_goods
 WHERE deleted=0 AND on_sale=1 AND audit_status='APPROVED' AND category_no=?
 ORDER BY sales DESC LIMIT 20;
```

生产库上 `EXPLAIN` 的结果：

```
type: ALL | possible_keys: NULL | key: NULL | rows: 380 | Extra: Using where; Using filesort
```

`prd_goods` 上只有三条二级索引（`V1__baseline.sql`）：

```
KEY idx_entity (entity_no)      KEY idx_type (type)      KEY idx_title (title(32))
```

**过滤用的四个列一个都没索引，排序列 `sales` 也没有。**
380 行时这是免费的；38 万行时它是一次全表扫 + 一次外部排序，
而它是 C 端首页、分类页、搜索页**每一次翻页**都要跑的那条。

### 3.2 关键词搜索：`LIKE '%kw%'` 永远用不上索引

代码注释写着「S1 用 like 前缀索引」，但 MyBatis-Plus 的 `like()` 生成的是
**两边通配** `%kw%`，前缀索引 `idx_title(title(32))` 对它无效
（要前缀索引得用 `likeRight()`）。`EXPLAIN` 同样是 `type=ALL`。

> 这不是「注释写错了」这么简单：它让人以为搜索这条路已经有索引兜底，
> 于是「上 ES」这件事的紧迫性被低估了。

### 3.3 一处正在发生的 N+1

`GoodsServiceImpl.java:147`：

```java
.map(g -> toVO(g, skus.get(...),
        campaignPort.flashPrices(List.of(g.getGoodsNo())).get(g.getGoodsNo())))
//                              ↑ 批量接口，被逐行调用。20 行/页 = 20 次
```

同一个文件里 `promoted()`（:99）与 `detailAll()`（:180）用的是**批量形式**，
:175 还留着一句注释说「都有批量版」—— 说明有人知道，只是漏了 `list()` 这一处。

### 3.4 社区池：先查 ID 再 `IN (...)`

社区筛选是「先查 `prd_community_pool` 拿全部 `goodsNo`，再 `WHERE goods_no IN (...)`」。
生产上最大的社区池是 **137 条**，还行。到几千条时这条 SQL 的文本本身就是几十 KB，
且 `IN` 大列表会让优化器放弃索引。

### 3.5 冷热混表

`prd_goods` **43 列，其中 8 个 TEXT/LONGTEXT**
（`images` `detail` `spec_groups` `sellable_override` `title_i18n` `subtitle_i18n`
`detail_images` `params`）。列表页真正要的是 ~10 列。

今天这几个大字段平均只有 **59 字节**（多是空的），所以全表扫很快。
一旦商品详情用上富文本（`detail` 动辄几 KB 到几十 KB），
**每翻一页都在把用不到的详情正文读进内存**。

### 3.6 全后端零缓存

`grep -c "@Cacheable"` = **0**。每一次请求都落到 MySQL。
类目树、规格库、平台值池这些**几乎不变、所有人都读**的数据也不例外。

## 3.7 JSON 快照方案的代价 —— 这是全篇最该看清的一节

§2 说快照方案「做对了」，指的是**读路径**。它同时有一笔明确的账，
而这笔账在这个仓库里**已经付过两次了**，不是推演。

### (1) 改 JSON 里的一个字段 = 整块重写，而且没有部分更新

`spec_groups` 是 TEXT 里的一段 JSON。要给所有商品的规格组补一个 `templateNo` 字段，
数据库层面**没有「改这一个 key」这种操作**——只能把整个值读出来、改完、整个写回去。

实际发生的两次：

| 迁移 | 行数 | 做了什么 | 结果 |
| --- | --- | --- | --- |
| `V229__backfill_goods_spec_dims.sql` | **255 行** | 逐条 `UPDATE prd_goods SET spec_groups='<整块新 JSON>' WHERE goods_no=? AND spec_groups='<整块旧 JSON 原文>'` | 198 件里回填 **105** 件，放弃 92 件 |
| `V236__backfill_goods_spec_dims_2.sql` | 73 行 | 同样的手法再来一轮 | 又拿下 **22** 件，仍剩 1 件回填不了 |

三个细节值得单独记：

- **一行商品一条 UPDATE。** 不能写成一条带 `WHERE` 的批量语句，因为新值逐行不同，
  而 JSON 里没有可供 `SET` 的列。这两条迁移是**脚本生成**出来的。
- **`WHERE` 里要带整块旧 JSON 的原文精确匹配**，当乐观锁用（迁移注释原话：
  「商家若在这中间改过这件商品，那一条就不该再套用旧快照」）。
  如果是普通列，一个 `version` 字段就够了；JSON 整块重写只能拿全文当版本号。
- **回填不了的那些是永久欠账。** 71 件放弃，理由写在 V229 末尾（类目没绑维度、
  语义是「计价单位」而非规格）。规范化存储里这些是 `NULL` 外键、一眼可查；
  JSON 里它们是一段**长得和别人一样、只是少了个 key** 的文本。

### (2) 查 JSON 里的字段：现在不需要，而这正是风险所在

全仓扫下来，**没有任何一条 SQL 查 JSON 内部**（没有 `JSON_EXTRACT`、没有 `->`、
没有对 `spec_groups` 的 `LIKE`）。读路径只是整块反序列化，所以今天不疼。

但 `prd_sku.option_value_nos` 与 `spec_groups.optionCodes` 存进去的**恰恰是身份**——
它们存在的唯一理由是「将来能按规格聚合、跨店比价」（§1「值有身份，才谈得上比价」）。
而这类查询长这样：

```sql
-- 「所有 5 斤装的苹果，哪家便宜」
WHERE 某个 SKU 的规格值集合 包含 'SV_WEIGHT_W2500G'
```

**这个形状答不了那个问题**，而且「误命中」不是假设 —— 生产库里现成就有：

```
SELECT value_no FROM prd_spec_value WHERE value_no LIKE 'SV_COUNT_C1%';
   SV_COUNT_C1 / SV_COUNT_C10 / SV_COUNT_C100 / SV_COUNT_C12     ← 四个都在
```

`LIKE '%SV_COUNT_C1%'` 会把这四个**全部**命中。要精确匹配就得连边界一起写
（`'%"SV_COUNT_C1"%'`），而那依然**用不上任何索引**——
MariaDB 没有 PostgreSQL 那种能直接索引数组元素的 GIN。

顺带一提：`option_value_nos` 的列类型是 **`varchar(512)`，不是 JSON 类型**
（`option_values` 同）。也就是说连「这是不是一段合法 JSON」数据库都不校验。
512 这个上限今天很宽裕（生产最长 20 字符），但它是个硬上限，
规格轴多起来时要复核 —— 三根轴 ×20 字符加括号引号已经八十多。

> 也就是说：**数据被认真地赋予了身份，然后被存进了一个按身份查不了的形状里。**
> 这不是现在的 bug，是一颗定时的：比价功能一开工就会撞上，
> 而那时要动的是存量所有 SKU 的存储结构。

**该怎么留后路**：见 §4.4 —— 那一节把「能不能给 JSON 建索引 / 有没有必要 /
能不能用冗余字段」三个问题在 20 万行上逐条实测过了，结论是**倒排子表**，
而且要把排序键一起冗余进去。

> ⚠️ 另记一笔：`prd_goods.params`（商品参数）在生产库里**每一行都是 NULL**。
> 参数这条路线**还没有任何真实数据**，所以上面关于它的判断都只是结构推演，
> 没有实测支撑 —— 真要动它之前得先有货。

### (3) 没有类型与结构约束，schema 会静默漂移

V229 注释里的原话最能说明问题：

> 线上 198 件带规格的商品里，**只有 1 件的规格组带 `templateNo`**。

`spec_groups` 的形状随代码演进（后来加了 `templateNo`、`optionCodes`），
而**已经写进去的行不会跟着变**，数据库也不会报任何错。
于是「新老两种形状并存」这件事，是靠人翻数据翻出来的，不是被任何守卫拦下的。

规范化的列做同一件事：加列 → 老行是 `NULL` → `WHERE x IS NULL` 一句话数得清。

### (4) 并发写覆盖

两个人同时编辑同一件商品的不同规格组，各自读出整块 JSON、各改各的、各写回去 ——
**后写的把先写的整块盖掉**。`prd_goods` 有 `version` 乐观锁列，
所以这一条在应用层是挡住的；但要意识到挡住它的是乐观锁，不是存储结构。
规范化存储里两个人改不同的行，本来就不冲突。

### 小结：这四条各自该怎么办

| 代价 | 现在的处置 |
| --- | --- |
| 改 JSON 内字段 = 整块重写 | **接受**。这类回填是低频的（两次），且脚本生成 + 原文匹配的做法是对的 |
| 按规格值查询/聚合 | **留后路**：比价功能开工前先建倒排表，别等撞上 |
| schema 静默漂移 | **补一道守卫**：扫 `spec_groups` 里缺 `templateNo` / `optionCodes` 的行并报数，接进现有闸门 |
| 并发覆盖 | 已由 `version` 乐观锁挡住，无需额外动作 |

## 4. 该反范式的地方 —— 以及代价记在哪

> 三范式解决的是**写入时的更新异常**。互联网读多写少的场景里，
> 读一次要拼四层裁剪、跨五张表，这个成本乘以 QPS 之后远大于冗余带来的写入成本。
> 所以反范式不是「破坏规范」，是**把 join 的成本从每次读挪到每次写**。
> 关键是：**每一处冗余都要写明谁来维护、不一致了会怎样。**

### 4.1 已经做对的（**别规范化回去**）

| 冗余 | 在哪 | 为什么 | 不一致时 |
| --- | --- | --- | --- |
| `spec_groups` / `params` JSON 快照 | `prd_goods` | C 端一行读出全部规格，不连表 | **故意的**：快照就该不跟随规格库改名 |
| `option_values`（文案）+ `option_value_nos`（编号） | `prd_sku` | 前者给人看、后者给机器聚合 | 同上，文案是快照 |
| `numeric_unit` | `prd_spec_value` | 「不连表就能比」（DDL 注释原话） | 与维度 `unit` 同源，改维度单位要一起改 |
| `store_name` | `prd_goods` | 列表页显示店名，免去 join 商家表 | 商家改名后旧行会陈旧 → **需要一个回填任务，目前没有** |
| `sales` / `rating` / `rating_count` | `prd_goods` | 排序列必须在本表，否则无法用索引排序 | 允许延迟，最终一致即可 |

⚠️ `store_name` 那一行是**已知欠账**：商家改名后列表页会显示旧名，
而没有任何机制会修正它。要么补一个订阅商家改名事件的回填，要么承认它是快照并写进文档。

### 4.2 建议新增的反范式

#### (a) 列表读模型：把过滤条件与排序键收进一张窄表

```
prd_goods_list  (读模型，写侧维护)
  community_no, category_no, goods_no,
  title, cover, store_name, min_price, sales, on_sale_at
  PRIMARY KEY (community_no, category_no, sales DESC, goods_no)
```

**一次查询解决社区筛选 + 类目筛选 + 排序 + 分页**，
既去掉 §3.4 的 `IN` 大列表，也去掉 §3.5 的宽行读取。
一个商品铺 N 个社区就有 N 行 —— 这正是反范式：**用空间换掉每次读的那个 join**。

维护：商品上下架 / 改价 / 铺货变更时由 outbox 事件驱动重建该商品的行。
不一致的表现是「列表里还能看到已下架的商品，点进去提示已下架」——
可接受，且详情页是权威。

> **到 5 万商品 / 或社区池上千条时再做。** 现在做等于凭空多一张要维护一致性的表。

#### (b) 冷热拆表：`prd_goods` 瘦身

把 `detail` / `detail_images` / `sellable_override` 这三个只有详情页要的大字段
挪到 `prd_goods_detail (goods_no PK, ...)`。
`spec_groups` / `params` **留在主表** —— 列表页的规格摘要要用。

> **到详情正文平均超过 2KB 时再做**（现在 59 字节）。改表要停机，
> 而加索引不用 —— 所以这条排在索引后面。

#### (c) 类目树与规格库进本地缓存

它们是「几乎不变 + 所有人都读」，是缓存收益最高的一类。
`@Cacheable` + 运营改动时 `@CacheEvict` 即可，不需要引 Redis。

> **现在就可以做**，成本低、风险低。

### 4.3 明确**不**建议做的

- **不要把 `prd_spec_value` 的 `label` 冗余进 `prd_category_spec_value`。**
  那一层已经有 `label_override`（类目内换名），再冗余一份就有两个「本类目叫什么」，
  而它们会分岔。
- **不要为了「查得快」把规格拍平成 `spec1/spec2/spec3` 列。**
  轴的数量是业务变量（有的类目 2 根，有的 5 根），拍平之后加第 6 根要改表。
  现在的 JSON 快照已经解决了读的问题。
- **不要现在引 ES。** 380 个商品，`LIKE` 全表扫也是毫秒级。
  到 5 万商品或搜索 QPS 上来时再上，接口 `GoodsService` 不变（这一点原设计已经留好了）。

## 4.4 四个问题的直接回答：JSON 能不能建索引 / 有没有必要 / 能不能用冗余字段 / 要不要换 MySQL

下面每一条都在**本机 MariaDB 12.2（生产是 12.3，同代）上跑过 20 万行的实测**，
不是查文档抄来的。造的表与 `prd_sku` 同构：`option_value_nos VARCHAR(512)`
装一段 JSON 数组，每行 1~3 个规格值。

### 问题一：能不能对 JSON 里的字段建索引？

> ⚠️ **这一节的结论来自官方文档与 MariaDB 的 Jira，不是我本机跑出来的。**
> 我最初只跑了一个 `SELECT CAST('["a"]' AS ARRAY)`，拿到 `ERROR 4161` 就下了结论 ——
> 那只证明**一种语法**不可用，证明不了「不存在别的机制」。查过之后果然差了两条
> 重要事实（下面标 ★ 的两处），而那两条都不是测试能测出来的。

**分两种情况，答案完全不同。**

| 要查的东西 | MariaDB 现在（12.x） | 依据 |
| --- | --- | --- |
| **标量**：`$.details.foodType` 这种一行一个值 | **能** —— 虚拟/持久生成列 + 索引 | MariaDB 官方文档 |
| **数组成员**：「这个 SKU 的规格值里**含不含** SV_WEIGHT_W2500G」 | **不能** | MySQL 的多值索引 MariaDB 尚未实现 |

★ **第一条比我原先写的强**：MariaDB 官方就是这么推荐的 ——
`ALTER TABLE ... ADD COLUMN food_type VARCHAR(25) AS (JSON_VALUE(attr,'$.details.foodType')) VIRTUAL;`
然后对这个虚拟列建索引。而且**从 MariaDB 11.8 起优化器能直接识别 WHERE 里的
那个表达式**并走 range/ref，不必在 SQL 里写出虚拟列名（生产是 12.3，有这个能力）。

★ **第二条有个时间表，我原先不知道**：多值索引在 MariaDB 是
[MDEV-25848](https://jira.mariadb.org/browse/MDEV-25848) ——
**状态 In Progress、优先级 Critical、目标版本 13.2**，负责人 Sergei Golubchik，
2026-08-19 还在更新。所以「MariaDB 永远没有」是错的说法，
准确的说法是「12.x 没有，13.2 在做」。

另外两条官方事实，与这个决策相关：

- **MariaDB 的 `JSON` 是 `LONGTEXT COLLATE utf8mb4_bin` 的别名**，不是原生类型
  （官方说明：JSON 类型与 SQL:2016 标准冲突，且实测性能不低于原生实现）。
  用 `JSON` 声明列时会自动挂一条 `JSON_VALID()` 的 CHECK 约束 ——
  而我们的 `option_value_nos` 是裸 `varchar(512)`，**连这条约束都没有**。
- 我们的表是 `utf8mb4_uca1400_ai_ci`（见 `V1__baseline.sql`），这一点在问题四里会变成一个坎。

### ⚠️ 生成列这条路在**我们这个场景**下会给出错误答案

标量能索引，但规格值**不是标量，是数组**。有人会想「那就用生成列抽第一个元素」。
本机 MariaDB 12.2 上 20 万行实测：

```sql
ALTER TABLE sku ADD COLUMN first_val VARCHAR(64)
      AS (JSON_VALUE(option_value_nos,'$[0]')) PERSISTENT;
ALTER TABLE sku ADD INDEX idx_first_val (first_val);
```

| 查法 | 命中行数 | 执行计划 |
| --- | --- | --- |
| `JSON_CONTAINS(option_value_nos,'"SV_WEIGHT_W2500G"')` | **5000**（正确） | `type=ALL`，扫 198750 行 |
| `first_val = 'SV_WEIGHT_W2500G'` | **3333**（**错**） | `type=ref`，`Using index` |

**它快了 20 多倍，代价是静默漏掉 1667 行** —— 生成列只能锁定**固定下标**，
规格值排在第 1、2 位的它看不见。

> **快而错比慢而对危险得多。** 症状是「比价页少了几家店」，
> 没人会把它联想到索引上。所以在这个场景里，生成列不是「凑合能用」，是**不能用**。
> 它对「一行一个值」的字段（品牌、产地）仍然是好办法 —— 别把这两件事混为一谈。

### 问题二：有没有必要给 JSON 建索引？能带来好处吗？

**今天：没有必要。** 全仓没有一条 SQL 查 JSON 内部，C 端读路径是整块反序列化。
现在去建任何 JSON 索引，是在解决一个不存在的问题。

**将来做比价 / 按规格筛选时：必要的是「按规格值查得快」，
不必要的是「JSON 索引」这个特定手段。** 这两件事要分开 ——
下一节的实测说明，就算把多值索引摆在面前，它也解决不了我们那条查询的后半截。

### 问题四：要不要为此换成 MySQL？

**结论：不换。** 理由不是「迁移麻烦」，是**换过去也解决不了这条查询**。

我们真正要跑的查询是「**含某个规格值 → 按价格排序 → 取前 10**」。
MySQL 8.0.17+ 的多值索引（MVI）能解决前半截，但官方文档明确写着它解决不了后半截：

> "An index with a multi-valued key part **does not support ordering** and therefore
> cannot be used as a primary key."
> "A multi-valued index **cannot be a covering index**."
> "…a multi-valued index **does not support range scans or index-only scans**."
> —— MySQL 8.0 Reference Manual, *Limitations and Restrictions on Multi-Valued Indexes*

翻译成这条查询会发生什么：MVI 定位到约 5000 个匹配的 SKU → 因为不能覆盖，
逐个回聚簇索引取 `price` → 因为不能排序，对这 5000 行做一次 filesort → 取前 10。

**这正是我实测的路线 3（6.31 ms），不是路线 4。** 也就是说：

| 方案 | 数据库 | 这条查询的形态 | 实测 |
| --- | --- | --- | --- |
| 多值索引 | 需换 MySQL 8.0.17+ | 索引定位 → 回表 → **filesort 5000 行** | ≈ 6 ms 量级 |
| **倒排子表 + price 冗余** | **MariaDB 现在就行** | 主键定位 → **顺着读 10 行就停** | **测不出（<0.05 ms）** |

**一张普通子表，在现有数据库上，比换库之后的专用特性还快。**
因为 `(value_no, price, sku_no)` 这个主键把「筛选」和「排序」编进了同一棵 B 树，
而 MVI 按定义做不到这一点。

另外三条会一起算进账里的成本：

1. **字符集要动。** MVI 只支持 `binary` 或 `utf8mb4_0900_as_cs`；
   我们全库是 `utf8mb4_uca1400_ai_ci`（`V1__baseline.sql`）。
   而 `_as_cs` 是**区分大小写与重音**的 —— 换过去会改变所有字符串比较的语义，
   影响面远超商品域。
2. **建索引要锁表。** 官方："Online creation of a multi-value index is not supported,
   which means the operation uses `ALGORITHM=COPY`."
3. **MariaDB 自己也在做这个特性**（MDEV-25848，目标 13.2）。
   为一个「对方也快有了、而且有了也不够用」的能力换数据库，账算不过来。

> **什么时候换库才值得讨论**：不是为了 MVI，而是当「多个规格维度任意组合筛选」
> （faceted search）成为核心功能时 —— 而那个场景的标准答案是搜索引擎（ES/OpenSearch），
> 不是关系库的任何索引类型。这一点 §4.3 已经写过：接口 `GoodsService` 不变，
> 到 5 万商品再上。

### 问题三：能不能直接用冗余字段？

**能，而且这就是正确答案 —— 但「冗余成一个列」和「冗余成一张子表」是两件事。**

| 数据形状 | 冗余成什么 | 为什么 |
| --- | --- | --- |
| 一行一个值（品牌、产地、主规格） | **冗余列** | 一个列装得下。**优于生成列**：写侧可控、可加校验、可回填、不绑数据库特性 |
| 一行 N 个值（一个 SKU 的全部规格值） | **子表**（倒排表） | 可变长集合塞不进一个列。塞成 JSON 就回到了原点 |

倒排表长这样，写侧保存 SKU 时同步落行：

```sql
CREATE TABLE prd_sku_spec_value (
  value_no VARCHAR(64) NOT NULL,
  price    BIGINT      NOT NULL,   -- ← 冗余，见下
  sku_no   VARCHAR(64) NOT NULL,
  PRIMARY KEY (value_no, price, sku_no)
);
```

**20 万 SKU（40 万倒排行）上的实测**，查「含某个规格值、按价格排序取前 10」：

| 路线 | 单次净耗时 | 答案对不对 | 执行计划 |
| --- | --- | --- | --- |
| 1 `JSON_CONTAINS` | **57.3 ms** | ✅ 对 | `type=ALL`，全表扫 |
| 2 生成列索引 | 2.56 ms | ❌ **错**（3333/5000） | `type=ref` |
| 3 倒排表 + join 回 sku 取价 | 6.31 ms | ✅ 对 | `Using temporary; Using filesort` |
| 4 倒排表 + **price 一起冗余** | **测不出**（<0.05 ms） | ✅ 对 | `Using where`，无排序无 join |

> 单次净耗时 = 单连接内跑 1000 次的均值减去空查询基线。
> 路线 4 落在测量下限以下：主键 `(value_no, price, sku_no)` 本身就按价格有序，
> 定位之后读 10 行就停 —— 它压根没有「扫描」这个动作。

**路线 3 → 4 就是「冗余字段」的全部价值**：把 `price` 冗余进倒排表，
`ORDER BY price LIMIT 10` 从「临时表 + 文件排序」变成「顺着索引读十行」。
6.31 ms → 测不出，而多出来的成本只是**每次改价要多更新一张表的几行**。

### 结论：优化方案

```
标量字段要查 → 冗余列（不是生成列）
集合字段要查 → 倒排子表，并把排序键（price）一起冗余进去
JSON 继续留着 → 它服务的是「整块读出来渲染」，那条路它是最优解，不要动
```

**三份数据、三种形状、各服务一类查询** —— 这就是「不能仅按三范式」的具体含义。
**而且不用换数据库**（问题四）。
代价全部记在写侧：保存 SKU 时多写一张表，改价时多更新几行。
**这笔代价必须有守卫盯着**（见 §6），否则倒排表会悄悄和主表分叉，
而症状是「比价页少了几家店」—— 与上面生成列那个错误一模一样，
只是这次是数据不同步造成的。

## 5. 完整设计方案：目标模型

> **前置约束（2026-08-28 拍板）**：将来一定切 MySQL，所以下面每一张表、每一条 SQL
> 都必须 MariaDB 与 MySQL 8 都能跑。规矩与闸门见
> [数据库可移植性-MariaDB到MySQL](./数据库可移植性-MariaDB到MySQL.md)。
> 本节所有 DDL 都按那份规矩写：排序规则一律 `utf8mb4_unicode_520_ci`，
> 不用 `IF NOT EXISTS`，不用任何一边独有的语法。

### 5.1 一句话概括：**同一份事实，三种形状，各服务一类问题**

严谨性与性能不是二选一 —— 它们由**不同的形状**分别承担：

| 形状 | 服务什么 | 权威性 | 一致性要求 |
| --- | --- | --- | --- |
| **规范化的规格库**（现有四层） | 写侧：商家配规格、运营配类目 | **唯一真源** | 强一致（事务内） |
| **JSON 快照**（`spec_groups`/`params`） | 读侧：详情页整块渲染 | 快照，**故意不跟随** | 无需一致 —— 见 §2 |
| **倒排 / 读模型**（新增） | 读侧：按规格筛选、排序、聚合 | 派生 | 最终一致 + **对账守卫** |

**这三种形状不是冗余三份数据，是同一份事实的三种索引方式。**
判断一个新需求该落在哪，只问一句：**它是「谁说了算」、「给人看」、还是「按它查」。**

### 5.2 新增的表（两张，都为「按规格查」而生）

#### (a) `prd_sku_spec_value` —— SKU 的规格值倒排表

```sql
CREATE TABLE prd_sku_spec_value (
  value_no      VARCHAR(64)  NOT NULL COMMENT '规格值编号，prd_spec_value.value_no',
  price         BIGINT       NOT NULL COMMENT '冗余自 prd_sku.price。它在这里是为了让排序免费，见下',
  sku_no        VARCHAR(64)  NOT NULL,
  goods_no      VARCHAR(64)  NOT NULL,
  entity_no     VARCHAR(64)  NOT NULL,
  dim_no        VARCHAR(64)  NOT NULL COMMENT '冗余自值表。按维度聚合时免去一次回查',
  numeric_value DECIMAL(14,4) DEFAULT NULL COMMENT '归一量，冗余自值表。同规格比价靠它',
  tenant_no     VARCHAR(32)  NOT NULL DEFAULT 'MAIN',
  PRIMARY KEY (value_no, price, sku_no),
  KEY idx_ssv_sku (sku_no),
  KEY idx_ssv_dim_num (dim_no, numeric_value)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_520_ci
  COMMENT='SKU→规格值倒排。为「按规格筛选/比价」而生，权威在 prd_sku';
```

**主键顺序 `(value_no, price, sku_no)` 是这张表的全部要点。**
它把「筛选」和「排序」编进同一棵 B 树 —— [§4.4 实测](#44-四个问题的直接回答json-能不能建索引--有没有必要--能不能用冗余字段)：
比 join 回主表快一个数量级，也比换到 MySQL 用多值索引快（多值索引官方明确不支持排序）。

⚠️ **代价要写清**：`price` 冗余在这里，意味着**商家改价要同步更新这张表**。
这是这个设计里唯一一处「写放大」，而它换来的是读侧的排序免费。
改价频率远低于浏览频率，这笔账划算 —— 但**必须有守卫**（§7）。

#### (b) `prd_goods_list` —— 列表读模型（**第二阶段再建**）

```sql
CREATE TABLE prd_goods_list (
  community_no VARCHAR(64) NOT NULL,
  category_no  VARCHAR(64) NOT NULL,
  sales        INT         NOT NULL DEFAULT 0,
  goods_no     VARCHAR(64) NOT NULL,
  title        VARCHAR(255) NOT NULL,
  cover        VARCHAR(512) DEFAULT NULL,
  store_name   VARCHAR(128) DEFAULT NULL,
  min_price    BIGINT      NOT NULL,
  entity_no    VARCHAR(64) NOT NULL,
  tenant_no    VARCHAR(32) NOT NULL DEFAULT 'MAIN',
  PRIMARY KEY (community_no, category_no, sales, goods_no),
  KEY idx_gl_goods (goods_no)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_520_ci
  COMMENT='C 端列表读模型。一个商品铺 N 个社区就有 N 行 —— 空间换掉每次读的那个 IN 子查询';
```

一次查询同时解决**社区筛选 + 类目筛选 + 排序 + 分页**，
既去掉 §3.4 的 `IN` 大列表，也去掉 §3.5 的宽行读取（列表页不再碰 8 个 TEXT 列）。

> **不要现在建。** 现在生产 380 个商品、最大社区池 137 条 —— 建了只是凭空多一张
> 要维护一致性的表。触发条件写在 §6 第二阶段。

### 5.3 现有表要改的（不新增表的部分）

| 表 | 改什么 | 阶段 |
| --- | --- | --- |
| `prd_goods` | 补两条复合索引（§6.1） | **一** |
| `prd_goods` | `spec_groups` 加 `JSON_SCHEMA_VALID` 的 CHECK 约束 | 二（要先收敛存量） |
| `prd_goods` | 拆出 `prd_goods_detail`：`detail` / `detail_images` / `sellable_override` | 三 |
| `prd_sku` | `option_value_nos` 从 `varchar(512)` 收紧为 `JSON` 类型 | 二 |
| 全部 160 张表 | 排序规则转 `utf8mb4_unicode_520_ci` | 单独排期，见可移植性文档 §3 |

`option_value_nos` 那一条值得单说：现在是裸 `varchar(512)`，
**连「是不是一段合法 JSON」数据库都不校验**（§3.7）。改成 `JSON` 类型之后
两边都会自动挂 `JSON_VALID()` 约束；而且切到 MySQL 后它是真正的二进制格式，
按 key 直接定位，不必整段解析。**这一条是纯收益，只是要等存量清洗完。**

### 5.4 严谨性靠什么保证 —— 三条，缺一不可

反范式的风险不在「冗余」，在**冗余之后没人知道谁该负责同步**。所以：

1. **每一处冗余都在 DDL 注释里写明「冗余自哪里」**（上面两张表都写了）。
   下一个人看到 `price` 出现在倒排表里时，不必去猜它是不是笔误。
2. **权威只有一个**：倒排表与读模型都是派生物，**任何冲突一律以 `prd_sku` /
   `prd_goods` 为准**。重建脚本要能从权威表全量重算 —— 这是它们可被信任的前提。
3. **每一处冗余配一道对账守卫**（§7），且守卫必须做过消融。
   没有守卫的冗余就是一颗定时的数据不一致。

## 6. 完整优化方案：分三阶段

### 6.1 第一阶段 · 现在就做

**判据：成本低、不改表结构、不会白做、且「现在做便宜以后做贵」。**

| # | 做什么 | 收益 | 风险 |
| --- | --- | --- | --- |
| 1 | 补 `prd_goods` 两条复合索引 | C 端最热查询从 `ALL + filesort` 变成索引扫 | 低（加索引不停机） |
| 2 | 修 `GoodsServiceImpl:147` 的 N+1 | 每页 20 次调用 → 1 次 | 低（三行） |
| 3 | 改掉「用 like 前缀索引」那句错注释 | 不再低估搜索的欠账 | 无 |
| 4 | 类目树 / 规格库加本地缓存 | 零缓存的现状里收益最高的一类 | 低 |
| 5 | **SQL 可移植性闸门**（已完成） | 债不再长 | 无 |

索引要**两条**，不是一条：

```sql
CREATE INDEX idx_goods_cat_sales ON prd_goods (deleted, on_sale, audit_status, category_no, sales);
CREATE INDEX idx_goods_sales     ON prd_goods (deleted, on_sale, audit_status, sales);
```

**为什么不能只建第一条**：不带 `category_no` 时索引前缀停在 `audit_status`，
中间跳过了 `category_no`，`sales` 就不能用于索引排序。

这一条在生产库上拿现成的 `idx_stl_pool_channel (market, pay_channel, id)` 实测过：

```
WHERE market=? AND pay_channel=? ORDER BY id  → key=idx_stl_pool_channel, ref=const,const, 无 filesort
WHERE market=?                  ORDER BY id  → key=PRIMARY  ← 优化器整条索引都不用了
```

**实测比我原本的说法更准确**：跳过中间列时不是「用索引再 filesort」，
而是**整条索引被放弃**。那个例子里它退到扫主键（排序列恰好是主键，白得一个有序序列）；
`prd_goods` 的排序列是 `sales`，**没有这个便宜可占**，退化结果就是 §3.1 的 `ALL + filesort`。

> ⚠️ 那张表当时只有 1 行、`Cardinality=0`，所以这个执行计划只能说明
> **优化器的选择方向**，不能当性能数据。

### 6.2 第二阶段 · 触发条件明确，不到不做

| 触发条件 | 做什么 |
| --- | --- |
| 开工做「按规格筛选 / 跨店比价」 | 建 `prd_sku_spec_value`（§5.2a）+ 对账守卫 |
| 商品 > 5 万 **或** 最大社区池 > 1000 条 | 建 `prd_goods_list`（§5.2b） |
| 商品 > 5 万 **或** 搜索 QPS 起来 | 搜索切 ES / MySQL ngram 全文索引（`GoodsService` 接口不变） |
| 存量 `spec_groups` 清洗完 | 加 `JSON_SCHEMA_VALID` CHECK；`option_value_nos` 改 `JSON` 类型 |

**「不到不做」是这一阶段的重点。** 每张派生表都是一份要维护一致性的负担，
提前建等于提前付代价、还没有收益。

### 6.3 第三阶段 · 数据形态变了才做

| 触发条件 | 做什么 |
| --- | --- |
| 详情正文平均 > 2KB（现在 59 字节） | 冷热拆表 `prd_goods_detail` |
| 多门店读路径点亮（`prd_store_price`/`stock` 现在**是空表**） | 门店价/库存进读模型 —— 点亮那天读侧会多两次查询 |
| 决定切 MySQL | 按可移植性文档执行；排序规则转换**要单独排期** |

## 7. 冗余靠什么守住 —— 每一处配一道对账

**这一节不是可选项。** §5.4 第 3 条说的就是它：没有守卫的冗余是一颗定时的数据不一致，
而症状（「比价页少了几家店」）与索引缺陷长得一模一样，排查方向完全不同。

| 冗余 | 对账判据 | 消融方式 |
| --- | --- | --- |
| `prd_sku_spec_value` 的行 | 展开 `prd_sku.option_value_nos` 与倒排表做**双向差集**，两边都必须为空 | 手删倒排表一行 → 守卫变红并点名那个 sku |
| 倒排表里的 `price` | `JOIN prd_sku` 比对，不等的行数必须为 0 | 改一行的 price → 变红并点名 |
| `prd_goods_list` | 按权威表全量重算一遍，与现表比对 | 同上 |
| `prd_goods.store_name` | 与 `mch_entity.name` 比对 —— **今天就是坏的**（§4.1 已知欠账，商家改名后无人修正） | — |

> 最后一行是现成的教训：`store_name` 冗余了、但**没有任何机制会修正它**，
> 商家改名后列表页一直显示旧名。这不是推演，是现在就存在的状态。
> 新增的每一处冗余都可能变成它 —— 除非配上守卫。

## 8. 怎么验证（不能只看「感觉快了」）

每一条改动都要有**能证伪的判据**：

| 改动 | 判据 |
| --- | --- |
| 加索引 | 同一条 SQL 的 `EXPLAIN` 从 `type=ALL` + `filesort` 变成 `type=range/ref` 且 **Extra 里没有 filesort** |
| 修 N+1 | 一次列表请求的 SQL 条数从 `1 + 1 + N` 降到 `1 + 1 + 1`（用 p6spy 或 MyBatis 日志数，别估） |
| 加缓存 | 第二次请求的 SQL 条数为 0；**并且撤掉缓存要变回非 0**（否则测的可能是别的东西） |
| 读模型 | 造 5 万商品的压测数据再比 —— **在 380 行上测不出任何东西**，这一点必须先说清 |
| 倒排表（§4.4） | 一道**对账守卫**：把 `prd_sku.option_value_nos` 展开后与 `prd_sku_spec_value` 做差集，两边都必须为空。<br>**必须做消融**：手工删掉倒排表里的一行，守卫要变红并点名那个 sku —— 不然它只是一段永远绿的代码 |

⚠️ **在 380 行的库上做性能对比是没有意义的**：全表扫 380 行和走索引查 20 行
都是亚毫秒，差异全在噪声里。要么造数据，要么就只用 `EXPLAIN` 的**执行计划形状**
当判据（上面第一行就是这么写的）——**别拿计时数字说事**。

## 附：本节结论的出处

结构与能力的判断来自官方资料，性能数字来自本机实测，两类分开列，便于复核：

**官方资料**

- [MDEV-25848 Support for Multi-Valued Indexes](https://jira.mariadb.org/browse/MDEV-25848)
  —— MariaDB 多值索引的状态（In Progress / 目标 13.2 / Critical，2026-08-19 更新）
- [MySQL 8.0 Reference Manual · CREATE INDEX](https://dev.mysql.com/doc/refman/8.0/en/create-index.html)
  —— *Limitations and Restrictions on Multi-Valued Indexes*：不支持排序、不能覆盖、
  不支持 range/index-only scan、建索引走 `ALGORITHM=COPY`、字符集限于
  `binary` 或 `utf8mb4_0900_as_cs`
- [MariaDB Documentation · JSON Data Type](https://mariadb.com/docs/server/reference/data-types/string-data-types/json)
  —— `JSON` 是 `LONGTEXT COLLATE utf8mb4_bin` 的别名，自动挂 `JSON_VALID()` CHECK
- [MariaDB Documentation · Virtual Column Support in the Optimizer](https://mariadb.com/docs/server/ha-and-performance/optimization-and-tuning/query-optimizations/virtual-column-support-in-the-optimizer)
  —— 11.8 起优化器能识别 WHERE 里的虚拟列表达式并走 range/ref

**本机实测**（MariaDB 12.2，生产 12.3 同代；20 万 SKU / 40 万倒排行；
单连接跑 1000 次减去空查询基线。压测库用完已 DROP）

- 正确性：`JSON_CONTAINS` 5000 ✅ / 生成列 3333 ❌ / 倒排表 5000 ✅
- 耗时：57.3 ms / 2.56 ms / 6.31 ms / 测不出（<0.05 ms）

> ⚠️ **这两类证据的效力不一样。** 实测能告诉你「这条 SQL 在这个版本上多快、对不对」，
> 但**不能**告诉你「这个数据库有没有别的机制」——
> 我第一版就是只跑了一个失败的 `CAST(... AS ARRAY)` 就下了结论，
> 因此漏掉了「官方推荐虚拟列」和「MDEV-25848 在做」这两条。能力判断要查文档。
