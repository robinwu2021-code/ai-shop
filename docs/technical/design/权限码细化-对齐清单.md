# 权限码细化 · 对齐清单

> 状态：**待确认 · 2026-08-12**
> 起因：接角色配置界面时发现，**权限码没有对应到界面功能**
> 关联：[角色配置接前端-对齐清单](./角色配置接前端-对齐清单.md)（本文是它的前置）·
> [权限体系-Java方案与调用链](./权限体系-Java方案与调用链.md)

**开发前先对齐，确认了再写代码。**

---

## 1. 现状：16 个码盖 147 个端点、64 个界面功能

全量扫了 `/ops/**`：**150 个端点，147 个挂了 `@PreAuthorize`**，
用的是 `Perms` 里的 **16** 个码。三个数摆在一起：

| | 数量 |
|---|--:|
| 界面功能（功能点） | **78** |
| ops-web 维护的 UI 权限码（去重） | **64** |
| **后端权限码** | **16** |
| /ops 端点（挂了判权的） | 147 |

> 没挂 `@PreAuthorize` 的只有 3 条，都是有意的：
> `/ops/menu`（本来就按人切片）、`/ops/auth/login`、`/ops/auth/me`。
> **这一层是干净的**，问题不在覆盖率，在粒度。

**细粒度码表不需要新设计——它已经存在。** `ops-web` 的 `uiPermCode`
维护着 64 个码，与界面功能一一对应。后端从来没采纳它。

---

## 2. 三处不是「粗」，是**错**

粗到一定程度就变成配置错误。逐条摆事实：

### 2.1 `merchant:audit` = 19 个端点：**只读商家档案和封禁商家同一个权限**

```
GET  /ops/merchants                      商家档案（只读）
POST /ops/merchants/{merchantNo}/status  违规处置与封禁
POST /ops/merchants/{merchantNo}/verified 认证标
POST /ops/qualifications/{qualNo}/revoke  吊销资质
POST /ops/stores/audits/{auditNo}/decide  店招审核
```

前端那份码早就分开了（`merchant:merchant:read` vs `merchant:merchant:ban`），
**后端分不开**。想给一个人「能查商家、不能封店」，现在做不到。

### 2.2 `settle:manage` = 22 个端点：**看结算单和标记已付款同一个权限**

```
GET  /ops/settlements                    结算单（只读）
POST /ops/payables/{settleNo}/paid       标记已打款
POST /ops/settle/fee-rules               改费率规则
POST /ops/admission/deposits/{no}/txns   保证金流水写入
POST /ops/purchase-invoices/{no}/verify  进项发票核验
```

财务里最该分离的两件事——**制单与付款**——是同一个码。
这不是粒度问题，是内控问题。

顺带：`PUT /ops/stores/{storeNo}/business-mode`（改门店经营模式）
也挂在 `settle:manage` 下，**它根本不是结算**。

### 2.0 ⚠️ `order:view` 挂着两个写动作 —— **11 个角色里 7 个能裁决售后退款**

写在最前面，因为它不是「粒度粗」，是**现在就在生效的越权**：

```java
@PostMapping("/ops/after-sales/{afterSaleNo}/decide")   // 裁决售后，可触发退款
@PreAuthorize("@perm.can('" + Perms.ORDER_VIEW + "')")

@PostMapping("/ops/after-sales/fast-refund-rule")        // 改极速退阈值
@PreAuthorize("@perm.can('" + Perms.ORDER_VIEW + "')")
```

`order:view` 是**看单**的码。持有它的有 BD、商品运营、客服、活动运营、
社区运营、财务、风控 —— 也就是说**风控和社区运营今天就能批退款、改极速退阈值**。

讽刺的是 `Perms.ORDER_VIEW` 自己的 javadoc 写着这条原则：

> 「看单和改单是两件事 —— 前者客服天天做，后者是把系统的判断覆盖掉。
> 给客服看单的权限时顺手给了改单，等于每个客服都能把任意订单改成已完成。」

为此专门建了 `ORDER_INTERVENE`。而售后那两条还是落到了读码上 ——
**原则写下来了，没有守卫钉住它**。这也是这次为什么先做守卫再动注解。

> 这条建议**不等阶段 B**：它是唯一一处被广泛授予的写权限。
> 修它会让矩阵守卫报「7 个角色各少 2 条」—— 那正是预期中的红。

### 2.3 `industry:manage` = 19 个端点：名字只覆盖其中 4 条

```
POST /ops/industries/{industry}/enabled        行业开关   ← 只有这 4 条名副其实
POST /ops/communities/{communityNo}/fence      社区围栏
POST /ops/communities/applies/{applyNo}/decide 社区开通审批
POST /ops/pickups/{pickupNo}/status            自提点管理
GET  /ops/regions                              行政区划
```

行业配置、社区网格、自提点是三件不相干的事，共用一个码。
**看名字判断不出谁能碰什么** —— 这类码是审计时最难交代的。

---

## 3. 方案：分两步，第一步零行为变化

直接把 16 拆成 64 并同时收紧，是一次**同时改判权和改授权**的操作。
判错一处的两种后果不对称：**判紧了会有人报错（看得见）；判松了没人报错（看不见）**。
所以拆成两步。

### 阶段 A · 等价拆分（**零行为变化**）

1. `Perms` 采纳 ops-web 那 64 个码
2. 147 个端点逐个改挂细码
3. `ROLE_PERMS` 里，**原来持有粗码的角色，拿到该粗码展开出的全部细码**

做完之后**每个角色能访问的端点集合与拆分前完全相同**——纯重构。

> **守卫**：对 11 个角色 × 147 个端点算一张可访问矩阵，
> 断言拆分前后逐格相同。这张矩阵能从 `@PreAuthorize` + `ROLE_PERMS` 生成，
> 不靠人比对。**没有这张守卫不要动这一步。**

### 阶段 B · 真正收紧（**这一步才改变行为**）

按 [运营端-动态菜单×角色矩阵](./运营端-动态菜单×角色矩阵.md) 逐条 review：
哪个角色不该有哪个细码。每一条都要有理由，且都会让某个人**少一样东西**。

先做前面那三条最刺眼的：
- 只读商家档案 ≠ 封禁
- 看结算单 ≠ 标记已付款
- 门店经营模式从 `settle:*` 挪到 `merchant:*`

### 阶段 C · 接角色配置界面

到这一步，界面上勾一个功能点 = 授一个码 = 一组端点，**一一对应**，
[那份清单](./角色配置接前端-对齐清单.md)里「藏起来的按钮不等于关掉的权限」这条注意事项自动消失。

## 4. 对齐清单

### 4.0 做登记表时发现的两处，改变了阶段 A 的范围

**① 24 个细码在库里没有对应功能点。**
判权现在读库（`RolePermResolver`），**没有功能点 = 那个码没法授给任何角色**。
FINANCE 拿不到 `finance:payout:execute`，就是「本该有权限的岗位静默失权」。
所以 V64 除了改 `perm_code`，还要给这 24 个补 `point_type=ACTION` 的功能点
（无 href，与已有的 10 个页面内动作点同一种）。

**② 两个细码横跨了两个粗码**（资质码字典 vs 给某商家授资质）。
机械展开时会让只有其中一个粗码的角色白拿另一半 —— **这就是静默放宽**。
已拆开：`/ops/auth-codes`（世界上有哪些资质码）归类目维护面，
`/ops/merchants/{no}/auth-codes`（给这家店授哪几个）归商家治理。

> 自检脚本已经并进登记表的守卫，以后再出现横跨会直接红。

### 4.1 数据库

| 表 | 改动 |
|---|---|
| `sys_function_point.perm_code` | 从 16 个值 → 68 个值。**一次性 UPDATE**，值取自登记表 |
| `sys_function_point`（新增行） | 24 个 ACTION 点，对应没有菜单入口的后端能力 |
| `sys_role_point` | 阶段 A 不动（授的是功能点，不是码）；阶段 B 才动 |
| 其余三张 | 不动 |

> `perm_code` 与 `ui_perm_code` 细化后基本重合。**不合并这两列** ——
> 合并之后就没有东西能校验「前端认为的码」与「后端判的码」一致了，
> 而这正是这次问题被发现的方式。

### 4.2 API

**不变。** 147 个端点的路径、入参、返回都不动，只换 `@PreAuthorize` 里的字符串。

### 4.3 对象 / Controller / Service / Mapper

| 层 | 改动 |
|---|---|
| `Perms.java` | 16 常量 → 64 常量；`ROLE_PERMS` 重写（阶段 A 机械展开，阶段 B 人工收紧） |
| Controller | 147 处 `@PreAuthorize` 换码 —— **改动量全在这里** |
| Service / Mapper | 无 |
| `RolePermResolver` | 无（它读库，码变细自动跟着变） |
| `gen-perm-seed.mjs` | 重跑（生成物） |

### 4.4 端点 → 功能点的归属怎么定

**这是本批真正的工作量：147 个判断。**

我不打算假装它能全自动生成。可以做到的是**生成候选**：
按 controller 文件名 + 路径前缀匹配到功能点，机器给建议、人逐条确认，
把最终结果落成一份**登记表**（`perm-endpoint-map`），
再由守卫校验「每个端点都在表里、每个码都有端点」。

> 手写一份 147 行的映射三个月后必然过期，所以它必须是**被守卫钉住的登记表**，
> 而不是文档里的一张表格。

## 5. 风险与代价

| 风险 | 处置 |
|---|---|
| 拆错一个端点的码 → **静默放宽** | 阶段 A 的等价矩阵守卫；阶段 B 每条单独 review |
| 147 处改动与另一会话冲突 | 全在 controller 注解行，冲突面小但**要先约提交边界**（#52 还没定） |
| `ROLE_PERMS` 从 16 列变 64 列，可读性下降 | 按功能分组书写 + 生成一份角色×码矩阵作为 reference |
| 阶段 B 会让人「突然少了权限」 | 分批上，每批通知到岗位；**这是这次改造的目的，不是副作用** |

**代价诚实说**：阶段 A 是一天量级的机械改动加一个守卫；
阶段 B 是逐条评审，取决于你愿意收紧多少。

## 6. 要你确认的

| # | 问题 | 我的建议 |
|---|---|---|
| **Q1** | 后端直接采纳 ops-web 那 64 个 UI 码，还是另设一套？ | **采纳**。另设一套等于再造一个翻译层，而这次的问题就是翻译层两边不一致 |
| **Q2** | 分两步（A 等价拆分 → B 收紧），还是一次到位？ | **分两步**。判松了不报错，必须有一步是可机器验证的 |
| **Q3** | 阶段 B 收紧到什么程度？ | 先做三条最刺眼的（封禁 / 标记已付款 / 经营模式挪位），其余按矩阵逐条评审 |
| Q4 | 端点→功能点落成受守卫钉住的登记表？ | 是 |

确认后我从阶段 A 的**守卫**开始写 —— 先让矩阵能算出来，再动第一个注解。
