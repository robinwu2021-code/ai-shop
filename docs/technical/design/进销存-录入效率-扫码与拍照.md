# 进销存 · 录入效率：扫码与拍照

> 状态：**草稿 · 待确认** · 创建 2026-08-30
> 上游：[供应商与发货要素](./进销存-供应商与发货要素.md)（同一个诉求的另一半）·
> [B 端功能与流程](./进销存-B端功能与流程.md)
> 起因：**「同时考虑入库出库的便捷性，比如扫码、图像识别。」**

## 一、家底：三块都已经有，只有一块是断的

**都当场查过，不取自文档。**

| 能力 | 现状 |
|---|---|
| 端上扫码 | ✅ `packages/shared/src/ports/scan.ts` 的 `scanCode()`，`verify` 页在用 |
| 图像识别 | ✅ `GoodsVisionGateway`（拍照建品 B-11.3.7）+ `POST /biz/goods/recognize` |
| 资质识别 | ✅ `CertVisionGateway` + `POST /biz/qualifications/recognize` |
| 货品 ↔ SKU 桥 | ✅ `inv_item_ref` **209 / 209 全映上**（`AISHOP` → `SK0001` 这类） |
| **条码 → 货品** | ❌ **断的**，见下 |

## 二、断在哪：扫一个条码，今天解析不到任何东西

```
prd_sku.barcode      0 / 396      商家 SKU 一个条码都没有
prd_goods.std_no     0 / 380      也没有一件连到标准库
prd_spu_std.barcode  297 / 311    ← 条码全在标准库里，而没人连过去
```

**两处都断，所以链路整条不通。** 条码只存在于标准库，
而商家的货一件都没连到标准库上。

这与[供应商方案](./进销存-供应商与发货要素.md) §二 记的
「13 组重名货、207 件货号全空」是**同一个病灶的三种症状**：
商家的货没有任何稳定标识 —— 没有货号、没有条码、没有标准库归属，
于是只能靠名字，而名字会漂。

还有一条要写进方案的边界，来自 `SpuStdVO` 的原话：

> 商品条码。**空是常态** —— 生鲜、现做熟食、服务本来就没有条码。

**所以扫码永远只能覆盖一部分货**（预包装）。
把它当主路会让生鲜商家用不了，当加速器才成立。

## 三、方案：让使用行为顺便把数据补上

**不做数据清洗项目。** 「先补 396 条条码再上扫码」是走不通的 ——
没人会为了一个还没上线的功能去录 396 个条码。

反过来做：**第一次扫到不认识的条码时，问一句「这是哪件货？」**
商家选一次（从他自己的货里选，这一步他本来就要做），
系统把条码写回 `prd_sku.barcode`。**下一次扫同一件，直接命中。**

于是：

- 第一天的收益 = 0（每件都要选一次，与现在一样）
- 第二次进同样的货 = 一扫即中
- **数据是被用出来的，不是被录出来的**

### 3.1 解析链路

```
扫到的码
  ├─ 命中 prd_sku.barcode          → sku_no → inv_item_ref → item_id   ✅ 直接落
  ├─ 命中 prd_spu_std.barcode      → 提示「标准库里是《XX》，你的哪件货是它？」
  └─ 都不命中                       → 提示「这个码还没绑过，选一件货绑上」
```

第二条是白捡的：标准库 297 条有码，**扫到时至少能说出这是什么东西**，
比让商家从 204 件里翻要快得多。

### 3.2 落点：三个页面同一个入口

进货、出库、盘点的「添加货品」弹层顶上，搜索框右边加一个扫码图标。
**不是新页面**，是现有弹层的第二种找货方式。

**盘点要连续扫码**：盘点是一件一件过，每扫一件退出扫码界面再进去，
比手选还慢。要一个「连续模式」—— 扫中即加、不退出，直到手动结束。

### 3.3 拍照识别：复用现成的，但用在对的地方

`POST /biz/goods/recognize` 现成可用（拍照建品）。两种用法，价值差很多：

| 用法 | 值不值 |
|---|---|
| 拍**商品**认出是哪件货 | 一般。生鲜拍出来是「一堆青菜」，落不到具体 SKU；且商家自己认得自己的货 |
| **拍送货单 → 出货品与数量** | **这才是进货场景真正省时间的** —— 一次替掉十几行手工录入 |

后者是另一个模型任务（多行表格 OCR + 与商家货品对齐），
**本轮不做**，但要写进这里，免得下次又从「加个拍照按钮」开始想。

## 四、要改的东西

| # | 内容 | 说明 |
|---|---|---|
| 1 | `GET /biz/inventory/items/by-barcode?code=` | 按 §3.1 三段返回：命中货品 / 命中标准库 / 未知 |
| 2 | `POST /biz/goods/{skuNo}/barcode` | 绑码。**幂等**；同一商家内条码唯一 |
| 3 | 挑货弹层加扫码入口 | 三个页面共用同一个组件 |
| 4 | 盘点连续扫码模式 | 扫中即加、不退出 |

**不新增 `inv_item.barcode`**：条码是商品的属性不是库存的属性，
放两处一定会分岔。进销存通过 `inv_item_ref` 回读 `prd_sku.barcode`。

## 五、明确不做

- **不做条码批量导入**。见 §三：数据要被用出来。
- **不做拍送货单**。§3.3，单独提。
- **不给生鲜找扫码替代方案**。它本来就没有条码，手选是对的。
- **不做「扫码直接过账」**。扫描只负责找到货，数量仍要人确认 ——
  扫错一件和数错一件的代价不一样，前者商家不会发现。

## 六、验证方式

- **在真机上验，不在 mock 上验**。扫码要用摄像头，mock 给不了；
  这也是 2026-08-29 那一轮的教训（见[真机验证清单](./进销存-真机验证清单.md)）。
- **绑码要验第二次**：扫一个未知码 → 绑 → **再扫一次必须直接命中**。
  只验第一次等于没验绑上。
- **未命中的三条分支各走一次**：命中货品 / 命中标准库 / 完全未知。
  只测命中那条，另外两条上线才发现。
- **连续模式要验「扫错能撤」**：连扫十件，撤掉第三件，其余九件还在。
