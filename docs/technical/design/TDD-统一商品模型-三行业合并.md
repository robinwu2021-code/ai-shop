# TDD 统一商品模型 —— 三行业合并为一套

状态：**草稿 · 待确认** · 创建 2026-08-28

关联：[核心能力清单 B 节](../reference/核心能力清单.md) · [TDD-餐饮包](./TDD-餐饮包-场景与工作流.md) · [TDD-美业包](./TDD-美业包-场景与工作流.md)

> **总入口**：本册已并入 [TDD-商品域-完整方案](./TDD-商品域-完整方案.md)，细节冲突时以那份为准。

> **目标口径**：一套 API、**一套数据库**、一套业务逻辑，**同时**服务零售 / 餐饮 / 美业。
> 不是「一个接口分别服务三种商家」，是「三个行业的商品需求合并成同一个模型」。

# 一 · 分别梳理：三个行业的商品功能需求

先用**各行业自己的话**把需求列全，不做任何抽象 —— 抽象要发生在第二步，
提前抽象会把需求裁剪成"能塞进现有模型的那部分"。

# 二 · 需求对照：同一件事的三种叫法

把 §一 的三张表按"同一件事"归行，行业的名字只是**术语**：

| 通用概念 | 零售叫 | 餐饮叫 | 美业叫 |
|---|---|---|---|
| **门店内分组** | 本店推荐 | 菜单分类 | 项目分组 |
| **可售时段** | 早市特价 | 时段菜单 | 可约时段 |
| **选配项** | 包装 / 刻字 / 延保 | 做法 / 加料 | 指定技师 / 加项耗材 |
| **履约分组** | 拣货区 | 出品部门 | 服务区 / 资源类型 |
| **履约时长与缓冲** | 制作周期 | 出餐时长 | 服务时长 + 清洁缓冲 |
| **每日限量与重置** | 每日限量 | 沽清 / 估清 | 每日可约量 |
| **渠道价与附加费** | 线上线下差价 | 堂食价 / 外卖价 / 餐盒费 | 上门加价 / 服务费 |
| **最小起订** | 起订量 | 起售份数 | 最少人数 |
| **组合商品** | 礼盒装 | 套餐 | 疗程包 |
| **按重计价** | 生鲜称重 | 海鲜按斤 | — |

**十个概念，覆盖了三张需求表里除四条以外的全部。** 那四条在 §八。

# 三 · 合并判据

不是所有"看起来像"的都该合并。三条判据**同时成立**才合并：

| # | 判据 | 反例（不合并） |
|---|---|---|
| ① | **语义同构**：三者在系统里要做的事是同一件（同样的存储、同样的校验、同样的下游消费） | 「上菜顺序」与「发货优先级」看着像，但一个驱动出品队列、一个驱动拣货波次，下游完全不同 |
| ② | **零售也可能用**（哪怕现在没做） | 「技师技能」零售不会有，它属于员工域 |
| ③ | **统一后不会产生"永远为空的字段"** | 若某字段只有一个行业填、另两个恒 null，说明抽象是硬凑的 |

**判据②是关键的一条**：`§1.1` 的 R18–R24 全都是**零售自己就缺的能力**。
所以合并不是"为了迁就行业而给基座加东西"，而是**基座本来就该有，行业只是先把它逼出来了**。

# 四 · 合并结果：八个通用概念

## 4.1 门店内分组 `store_group`
门店自己维护的陈列分组，**与平台类目正交**（类目回答「这是什么货、要什么资质」）。
与已有 `prd_topic`（平台运营的陈列专题）也正交：那是**平台**摆首页，这是**商家**摆自己的店。

- 一件商品可属多个分组，分组内有序；
- 餐饮的"菜单分类"就是它；美业的"项目分组"就是它；零售的"本店推荐"就是它。

## 4.2 可售时段 `sell_window`
「这个时刻这件商品能不能点」。**只控可售，不控价格、不控上下架**。

- 餐饮时段菜单 = 一组 sell_window；美业"周一到周五才做" = 同上；零售早市特价 = 时段 + 渠道价；
- 与上下架分开：下架是商家的决定，时段是规则。合并会让"晚上自动下架"变成一次真的下架，第二天没人给它上回来。

## 4.3 选配项 `option_group` / `option`
**这是合并里最值钱的一个** —— 它一次吃掉了做法、加料、指定技师加价、加项耗材、礼品包装、刻字。

```
option_group: 名称 / 单选或多选 / 必选与否 / 最少最多 / 排序
option:       名称 / 加价（可为 0）/ 是否默认 / 关联 SKU（有加价时）/ 引用来源
```

三条设计要点：

1. **加价的选配项必须落成独立订单行**（与既有 `ord_item` 结构相容，基座金额链一行不改）；
   不加价的选配项写进 `ord_item.spec` 快照 + 结构化明细。这与餐饮 TDD §2.1/2.2 的结论一致；
2. **`option` 支持"引用来源"**：指定技师的选项不是手工维护的，来自资源池
   （`mch_resource` 的 STAFF 行）。引用来源是**基座已有的表**，不是行业表 —— 见 4.4；
3. 选配项挂在**商品**上，也可挂在**分组**上复用（一个"辣度"组给 30 道菜用）。

## 4.4 履约分组 `fulfillment_group`
「这件商品由谁/哪个工位产出」。**取代了原方案里的 `fnb_dept`。**

- 餐饮：热菜 / 凉菜 / 水吧 → 分单打印按它路由；
- 零售：拣货区 A / 冷藏区 → 自提点分拣打单按它分组；
- 美业：美甲区 / 护理房 → 与资源类型联动。

**这是本册与上一版最大的差别**：上一版让餐饮包自己建 `fnb_dept`，
于是"选项从哪来"必须由行业段供给、基座不能校验。
合并后它是**基座的门店级主数据**，选项、校验、路由全在基座，**行业零表零代码**。

> 顺带解决一个隐患：`prn_route.match_expr` 要按出品部门匹配。
> 部门在行业表时，打印路由要跨域读行业表；在基座时，它就是一次普通 JOIN。

## 4.5 履约时长与缓冲 `lead_time`
`prepare_min`（出餐 / 服务 / 制作）+ `buffer_before_min` / `buffer_after_min`。

- 美业：占位格数 = `ceil((prepare + buffer) / 时段粒度)`；
- 餐饮：出餐预估，给顾客看"约 15 分钟"；
- 零售：定制商品 3 天 → 影响可选的最早收货日。

**基座只存这三个数，怎么用是各域的事**（预约编排读它算格数，交易读它算预计送达）。

## 4.6 每日限量与重置 `daily_quota`
「今天还能卖几份」。**不是库存**，是每日重置的配额。

- 餐饮沽清 = 把今日配额置 0（次日自动回来）；
- 零售每日限量 = 每天 20 份；美业每日可约量 = 同理。

**与 `prd_store_stock` 分开的理由**：库存是存量（卖完要补货），配额是流量（每天回满）。
用库存表达沽清，第二天要有人去把它改回来 —— 而没人会记得。

## 4.7 渠道价与附加费 `channel_price` / `surcharge`
`prd_store_price` 今天是 `(store_no, sku_no, market)`，**加一个 `channel` 维度**即可：
`DINE_IN` / `TAKEOUT` / `ONLINE` / `HOME`。

- 餐饮堂食价 ≠ 外卖价；零售线上线下差价；美业上门加价；
- 附加费（餐盒费、服务费）**落成独立订单行**，与选配项加价同一手法。

## 4.8 最小起订 `min_order_qty`
一个整数。餐饮起售份数、零售起订量、美业最少人数。

# 五 · 一套数据库（**零行业表**）

```sql
-- ── 4.1 门店内分组 ────────────────────────────────────
CREATE TABLE prd_store_group (
  group_no  VARCHAR(32) NOT NULL PRIMARY KEY,
  store_no  VARCHAR(32) NOT NULL,
  entity_no VARCHAR(32) NOT NULL,
  name      VARCHAR(32) NOT NULL,        -- 「凉菜」「面部护理」「本店推荐」
  sort      INT NOT NULL DEFAULT 0,
  status    VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',
  KEY idx_psg_store (store_no, status, sort)
);
CREATE TABLE prd_store_group_goods (
  group_no VARCHAR(32) NOT NULL,
  goods_no VARCHAR(32) NOT NULL,
  sort     INT NOT NULL DEFAULT 0,
  PRIMARY KEY (group_no, goods_no)
);

-- ── 4.2 可售时段 ──────────────────────────────────────
CREATE TABLE prd_sell_window (
  window_no VARCHAR(32) NOT NULL PRIMARY KEY,
  store_no  VARCHAR(32) NOT NULL,
  name      VARCHAR(32) NOT NULL,        -- 「午市」「早市特价」
  days      VARCHAR(16) NOT NULL,        -- 1-7 位掩码
  start_min INT NOT NULL,                -- 自 00:00 起的分钟数，跨夜用两条
  end_min   INT NOT NULL,
  channels  VARCHAR(64) NULL,            -- 空 = 所有渠道
  enabled   TINYINT NOT NULL DEFAULT 1
);
CREATE TABLE prd_goods_sell_window (
  goods_no  VARCHAR(32) NOT NULL,
  window_no VARCHAR(32) NOT NULL,
  PRIMARY KEY (goods_no, window_no)
);
-- 一条都没有 = 全时段可售（存量商品行为零变化）

-- ── 4.3 选配项 ────────────────────────────────────────
CREATE TABLE prd_option_group (
  og_no      VARCHAR(32) NOT NULL PRIMARY KEY,
  store_no   VARCHAR(32) NOT NULL,
  name       VARCHAR(32) NOT NULL,       -- 「辣度」「加料」「指定技师」「包装」
  multi      TINYINT NOT NULL DEFAULT 0, -- 0=单选 1=多选
  required   TINYINT NOT NULL DEFAULT 0,
  min_pick   INT NOT NULL DEFAULT 0,
  max_pick   INT NULL,
  source     VARCHAR(24) NOT NULL DEFAULT 'MANUAL',
      -- MANUAL = 手工维护选项
      -- RESOURCE:STAFF = 选项来自 mch_resource 的 STAFF 行（指定技师）
  sort       INT NOT NULL DEFAULT 0
);
CREATE TABLE prd_option (
  option_no  VARCHAR(32) NOT NULL PRIMARY KEY,
  og_no      VARCHAR(32) NOT NULL,
  name       VARCHAR(32) NOT NULL,
  extra_sku_no VARCHAR(32) NULL,         -- 有加价时指向真实 SKU（金额链走既有 ord_item）
  is_default TINYINT NOT NULL DEFAULT 0,
  ref_no     VARCHAR(32) NULL,           -- source 非 MANUAL 时的外部键，如 resource_no
  sort       INT NOT NULL DEFAULT 0
);
CREATE TABLE prd_goods_option_group (
  goods_no VARCHAR(32) NOT NULL,
  og_no    VARCHAR(32) NOT NULL,
  sort     INT NOT NULL DEFAULT 0,
  PRIMARY KEY (goods_no, og_no)
);

-- ── 4.4 履约分组 ──────────────────────────────────────
CREATE TABLE prd_fulfillment_group (
  fg_no    VARCHAR(32) NOT NULL PRIMARY KEY,
  store_no VARCHAR(32) NOT NULL,
  name     VARCHAR(32) NOT NULL,         -- 「热菜」「冷藏区」「美甲区」
  kind     VARCHAR(16) NOT NULL,         -- KITCHEN / PICKING / SERVICE
  sort     INT NOT NULL DEFAULT 0
);
-- 商品 → 履约分组：门店级（连锁分店厨房分区不同）
CREATE TABLE prd_store_goods_ext (
  store_no       VARCHAR(32) NOT NULL,
  goods_no       VARCHAR(32) NOT NULL,
  fg_no          VARCHAR(32) NULL,       -- 4.4
  daily_quota    INT NULL,               -- 4.6，NULL = 不限
  quota_reset    VARCHAR(16) NULL,       -- DAILY / NONE
  min_order_qty  INT NULL,               -- 4.8
  serve_priority VARCHAR(16) NULL,       -- §八：未合并项，先放这里
  PRIMARY KEY (store_no, goods_no)
);

-- ── 4.5 履约时长与缓冲：加在 prd_goods（SPU 级）──────
ALTER TABLE prd_goods ADD COLUMN prepare_min       INT NULL;
ALTER TABLE prd_goods ADD COLUMN buffer_before_min INT NULL;
ALTER TABLE prd_goods ADD COLUMN buffer_after_min  INT NULL;
ALTER TABLE prd_goods ADD COLUMN resource_type     VARCHAR(16) NULL;  -- STAFF/SEAT/ROOM
-- ⚠️ duration_min 已存在（SERVICE 段），本期与 prepare_min 二选一收敛，见 §十.3

-- ── 4.7 渠道价：既有表加一维 ──────────────────────────
ALTER TABLE prd_store_price ADD COLUMN channel VARCHAR(16) NOT NULL DEFAULT 'ALL';
-- 唯一键 (store_no, sku_no, market) → (store_no, sku_no, market, channel)
```

**行业表：零张。** `fnb_goods_ext` 与 `bty_goods_ext` **都不存在了**。

# 六 · 一套 API

端点**一个不加**，`SaveCommand` 加一组可选字段（**不传 = 不改**，与既有口径一致）：

```java
record SaveCommand(…既有字段…,
    List<String>  storeGroupNos,     // 4.1 门店分组
    List<String>  sellWindowNos,     // 4.2 可售时段
    List<String>  optionGroupNos,    // 4.3 选配项组
    LeadTime      leadTime,          // 4.5 prepare/buffer/resourceType
    StoreExt      storeExt) {}       // 4.4/4.6/4.8：fgNo, dailyQuota, minOrderQty

record StoreExt(String storeNo, String fgNo, Integer dailyQuota,
                String quotaReset, Integer minOrderQty) {}
```

主数据各有一组 CRUD（**三行业共用**，不按行业分）：

```
GET/POST /biz/store-groups          门店分组
GET/POST /biz/sell-windows          可售时段
GET/POST /biz/option-groups         选配项组与选项
GET/POST /biz/fulfillment-groups    履约分组
GET      /biz/goods/form-schema     字段与选项来源（唯一新增的读端点）
```

**读侧一套**：`GET /biz/goods/{no}` 与 `GET /mp/goods/{no}` 一并返回这些结构，
按门店能力过滤、按 `visibleToBuyer` 裁剪（履约分组不给买家看）。

# 七 · 术语层：模型统一，叫法按行业翻译

模型统一之后，**界面上不能让餐饮商家看到"履约分组"**。
术语是**展示层的一张翻译表**，不是数据结构：

| 字段 | 零售显示 | 餐饮显示 | 美业显示 |
|---|---|---|---|
| `store_group` | 商品分组 | 菜单分类 | 项目分组 |
| `sell_window` | 售卖时段 | 时段菜单 | 可约时段 |
| `option_group` | 选购选项 | 做法 / 加料 | 加项 / 指定技师 |
| `fulfillment_group` | 拣货分区 | 出品部门 | 服务区 |
| `prepare_min` | 备货天数 | 出餐时长 | 服务时长 |
| `daily_quota` | 每日限量 | 沽清份数 | 每日可约 |

**落法**：`form-schema` 下发 `label` 与 `help`，由**门店的行业包码**选一套词条，
b-app 原样渲染。翻译表是数据（i18n 词条 + 行业维度），不是代码分支。

> 这是整套方案能被商家接受的前提。**模型统一是给系统的，术语分行业是给人的** ——
> 两者混为一谈，要么模型分叉，要么商家看不懂自己的后台。

# 八 · 没能合并的四条（诚实记录）

| 需求 | 为什么不合并 | 去哪 |
|---|---|---|
| **上菜顺序**（先上/后上/等叫） | 判据①不成立：它驱动**出品队列的调度**，零售的"发货优先级"驱动的是拣货波次，下游完全不同。硬合并会得到一个零售永远为空、语义还对不上的字段 | 先放 `prd_store_goods_ext.serve_priority`，**标注为待观察**；若第二个行业出现同构需求再提炼 |
| **技师技能**（谁能做这个项目） | 判据②不成立：这是**员工能力**，不是商品属性 | 基座 `mch_staff_skill`（员工域） |
| **提前预约期 / 最晚可约** | 不是商品属性，是**预约规则** | 预约域 `bty_store_config` → 建议上收基座门店配置 |
| **连锁通兑范围** | 是**门店覆盖 + 结算跨主体**的问题，不是商品字段 | 单独议题，成本主要在结算 |

**保留"上菜顺序"这一条不合并，是这份方案诚实性的检验点**：
八个概念合并得很顺，第九个硬凑就会破坏判据。宁可留一个待观察字段。

# 九 · 与上一版方案的差异

| | 上一版（可注册段） | **本版（统一模型）** |
|---|---|---|
| API | 一套 ✅ | 一套 ✅ |
| **数据库** | **不是一套** —— `fnb_goods_ext` 是行业表 | **一套** —— 零行业表 |
| 出品部门 | 行业段的 REF，选项由行业供给、基座不能校验 | **基座门店级主数据** `prd_fulfillment_group` |
| 做法 / 加料 | 行业段字段 | **通用选配项** `prd_option_group` |
| 段机制 | 核心机制 | **降级为兜底**（§十.1） |
| 餐饮包在商品域 | 1 个段 + 1 张表 + 1 个端点 | **零代码** |
| 美业包在商品域 | 零代码 | 零代码 |

**为什么上一版没走到这一步**：上一版是从"现有代码有什么机制"往外推，
所以停在了"给行业开一个口子"；本版是从"三个行业的需求"往回归，
于是发现**那些看着像行业特有的东西，零售自己也缺**（§1.1 的 R18–R24）。

**上一版仍然保留**（历史不改写），且它的段机制**不作废** —— 见 §十.1。

# 十 · 风险与遗留

## 10.1 段机制降级为兜底，但不删
八个概念覆盖了绝大部分，但**下一个行业一定会带来第九个**。
`GoodsSegment` 保留为兜底通道，**并加一条使用纪律**：
> 新需求先按 §三 的三条判据试合并；**只有判据不成立时**才用段。
> 每次用段都要在评审里说明"哪一条判据不成立"。

没有这条纪律，段会变成绕过合并的后门，一年后回到每行业一张表。

## 10.2 过度抽象的风险
把"出品部门"叫成"履约分组"，代价是**新人读代码时少了一层直觉**。
对冲：术语层（§七）+ 表注释里写清三个行业各自的叫法（本仓库的注释惯例本来就这么做）。

## 10.3 `duration_min` 与 `prepare_min` 重复
`prd_goods.durationMin` 已存在（SERVICE 段）。本册引入 `prepare_min` 是更通用的名字。
**必须二选一收敛**，不能两列并存 —— 两列并存就会出现"服务时长填了 60、出餐时长填了 30"而没人知道该读哪个。
建议：保留 `duration_min` 语义、**改用途注释**，不新增 `prepare_min`（改名的代价高于收益）。**待确认。**

## 10.4 选配项与规格 SKU 的边界
"大杯 / 中杯"是规格（进 SKU 矩阵），"加珍珠"是选配项（独立订单行）。
边界判据：**会不会影响这件商品本身的成本与库存** —— 会 → 规格；不会 → 选配项。
判错的后果是 SKU 笛卡尔积爆炸（V195 那一版正是为此而做）。**这条判据要写进建品页帮助文案。**

## 10.5 迁移
新增 6 张表 + 5 个 ALTER。全部"**一行都没有 = 旧行为**"：
无分组、无时段（全时段可售）、无选配、无履约分组、无配额（不限）、渠道价缺省 `ALL`。
**存量 73 类目与全部存量商品行为零变化** —— 与基座阶段 0 的验收标准一致。
并行会话同时加迁移必然撞号，改号后 `clean package`；**加列必须同步实体字段**。

# 十一 · 测试与闸门

**单元**
- 每个新表"零行 = 旧行为"各一条；
- 可售时段：跨夜（22:00–02:00）拆两条、边界分钟、无时段=全时段；
- 选配项：必选未选拒收、多选超上限拒收、加价项必须有 `extra_sku_no`；
- 选配项 `source=RESOURCE:STAFF` 时，选项与 `mch_resource` 的一致性；
- 每日配额：置 0 = 沽清、次日重置回满、配额与库存**互不影响**；
- 渠道价：`channel=ALL` 与具体渠道并存时**具体优先**。

**场景（三行业各一条，跑在同一套接口上）**
1. 零售：建品 → 审 → 上架 → 门店价 → 下单，**与现状逐字节相同**；
2. 餐饮：建菜 → 配菜单分类 + 午市时段 + 做法组 + 加料组 + 出品部门 → 扫码点单 → 分单打印命中；
3. 美业：建项目 → 配时长缓冲 + 指定技师选配组 → 预约占位格数正确；
4. **跨行业主体**：同一主体下餐厅与美容店各建一件，`GET /biz/goods` **一次查询同时返回**。

**闸门**
- `-Pcore-only`（不装任何行业包）下，**三条场景全部可跑** —— 这是"一套库"是否为真的唯一硬判据；
- ArchUnit：基座商品域不许 import 任何 `fnb_*` / `bty_*`；
- 撤掉"零行 = 旧行为"的兼容分支，存量回归必须变红；
- `form-schema` 契约测试：字段集与 `SaveCommand` 一致。
