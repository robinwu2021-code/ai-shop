# 优惠券与活动 · 全链路梳理（B 端建 → C 端领 / 参与 → 下单选择 → 抵扣详情）

状态：梳理完成、设计待拍板（2026-09-21）
依据：用户 2026-09-21「梳理优惠券的流程，b 端建活动，c 端领券或者参与活动，订单页面可以展示优惠券或者活动，
客户可以选择参与或者不参与，结账信息需要展示抵扣详情」
不改的既有决定：[PRD-营销-活动统一模型](../../requirements/PRD-营销-活动统一模型.md) §4.1 ——
**同一单里多个活动互斥取最优，券在活动之后的金额上再算**。本篇只在它之上补「客户可以选」。

## 二、现状（2026-09-21 实测代码）

### 2.1 B 端建

| 能力 | 现状 | 缺口 |
|---|---|---|
| 建券 | `coupon-edit` → `POST /biz/coupons` → 新模型 `pmt_coupon`。四种：满减、无门槛、折扣、商品券 | 表单**写死**「定向发放」「全店可用」—— 商家建的券只能按人群发，**顾客没有地方领** |
| 发放方式 | 模型有领券中心 / 定向 / 活动送 / 券码四种 | 界面只给定向 |
| 适用范围 | 模型有全店 / 门店 / 类目 / 商品 | 界面只给全店；「门店」与「最少件数」下单时不校验 |
| 包邮券 | 模型有 | 下单算不出（恒 0），界面也没开放 |
| 建活动 | `activity-edit` 九个玩法模板，满减 / 满件减 / 无门槛减 / 新客减 / 特价 / 买赠 / 组合都能在下单时算 | 常驻无门槛直减已加保存确认（P7） |
| 平台活动 | 运营建、商家报名 | 只支持减钱类 |

### 2.2 C 端领 / 参与

| 能力 | 现状 | 缺口 |
|---|---|---|
| 领券入口 | **只有商品详情页**一处 | 店铺页、首页没有入口；没有领券中心 |
| 领券读哪套券 | 读**老模型** `mkt_coupon` | **B 端新建的券（新模型）顾客看不到、领不到** |
| 券包 | 新老两套都读 | — |
| 活动露出 | 特价有划线价；满减类**只在下单页出现** | 商品页的「满 N 减 M」标签后端从不下发 `promotions`，真后端上永远不显示 |
| 参与活动 | 命中即自动参与 | 没有「不参与」的路 |

### 2.3 下单页

| 能力 | 现状 | 缺口 |
|---|---|---|
| 叠加顺序 | 活动（每家店取最优一个）→ 券（门槛按活动后金额判）→ 积分 | 符合 PRD |
| 选券 | 面板三段：自动活动 / 可用券 / 不可用券（说原因） | **不自动选最优券**（后端算了 `bestUserCouponNo`，端上没用） |
| ~~选券传错号~~ | ~~传券模板号，后端按持有的那张查 → 真后端上选任何券都失败~~ | **已修（本次，commit 见落地记录）** |
| 活动可否不参与 | 不可以 | 要补 |
| 抵扣明细 | 活动逐条、券一行、说不出名字的「优惠」、积分、底栏「共减」 | 基本齐；老模型的券与活动不写 `pmt_apply`，**详情里说不出名字** |

### 2.4 订单详情

| 端 | 现状 | 缺口 |
|---|---|---|
| C 端 | 优惠合计 + 逐条明细 + 关闭后的去向 | 老模型券 / 活动没有明细行 |
| B 端 | 只有应付、积分、去向 | **没有优惠明细** —— 商家看不到这单减了什么、谁出的钱 |

### 2.5 根因：两套券模型没有接上

```
B 端建券 ──→ 新模型 pmt_*   ──→ 只能定向发（界面写死）
运营建平台券 → 老模型 mkt_*
C 端领券 / 最优券试算 ──→ 读老模型 mkt_*
下单 ──→ CouponPortRouter 按「这张券属于哪套」分流（两套都能用）
```

下单能用两套，**领券只接了老的那套**。于是商家在 B 端建了券，顾客那边一张都看不到 ——
这不是某一处写错，是迁移只做了一半。

## 三、目标流程

### 3.1 B 端建

**券**（`coupon-edit` 补两项，其余不变）：

| 字段 | 选项 | 默认 |
|---|---|---|
| 发放方式 | 顾客领取（领券中心）· 定向发给人群 · 下单即送 | **顾客领取** |
| 适用商品 | 全店 · 指定商品 | 全店 |

- 选「顾客领取」时必须填总量与每人限领（敞口在建券时算清，与 TDD-营销预算前置一致）。
- 包邮券继续不开放（下单算不出之前不给入口）。

**活动**：不改。玩法模板、常驻确认（P7）照旧。

### 3.2 C 端领 / 看到

| 位置 | 显示 | 动作 |
|---|---|---|
| 商品详情 | 「领券」条（本店可领的券 + 平台券）；活动标签「满 50 减 8」「新客立减 5」 | 领券 → 进券包 |
| 店铺页（新增） | 同一个领券条 + 本店进行中的活动 | 同上 |
| 券包 | 可用 / 已用 / 已过期 | 去使用 → 跳店铺 |

活动**不需要报名**：看到标签、下单时满足条件就自动命中。「参与 / 不参与」放在下单页选（3.3）。

### 3.3 下单页：客户可以选

**默认替他选好最省钱的组合，他可以改**。主流电商都是这个做法：进来先看到最低价，而不是先做一道选择题。

优惠面板（点金额明细里的「活动」或「优惠券」行打开）：

```
┌ 优惠 ─────────────────────────────── × ┐
│ 活动  ·  同一家店只能参加一个          │
│   ◉ 满 50 减 8          -¥8.00         │
│   ○ 新客立减 5          -¥5.00         │
│   ○ 不参加活动                          │
│                                        │
│ 优惠券  ·  用在活动之后的金额上          │
│   ◉ 满 30 减 5（本店）  -¥5.00  09-30 到期 │
│   ○ 不使用优惠券                        │
│   不可用 2 张：差 ¥12 可用 / 已过期      │
│                                        │
│ 当前组合共减 ¥13.00        [ 确定 ]    │
└────────────────────────────────────────┘
```

规则：

1. **默认组合 = 活动与券一起算、总优惠最大的那一组**，不是「先挑最优活动、再在剩下的金额上挑券」。
   两者会不一样：参加满减后金额掉到券门槛以下，可能「不参加活动、只用券」反而更省 ——
   这正是「客户可以选择不参与」最常见的理由，系统应该先替他想到。
2. 客户改了活动，券的可用性当场重算（门槛按活动后金额判），不可用的说原因。
3. 选「不参加活动」时，这家店的活动一个都不命中；其他店不受影响。
4. 选择只在这一单有效，不记忆。

### 3.4 结账抵扣详情

确认页金额明细（已有，保持）：

```
商品金额                    ¥59.60
运费                          免运费
活动 · 满 50 减 8            -¥8.00   ← 可点，打开优惠面板
优惠券 · 满 30 减 5          -¥5.00   ← 可点
积分抵扣 200 分              -¥2.00
────────────────────────────────
应付 ¥44.60          共减 ¥15.00
```

- 每一笔优惠**只出现一次**（已做）；按商家拆单时，每家店的活动各占一行，行首带店名。
- 订单详情（C 端与 **B 端**）显示同一份明细，B 端多一列「谁出的钱」（本店 / 平台）——
  商家对账时要知道这 ¥5 是他让的还是平台补的。

## 四、后端要改的

| # | 改动 | 契约 |
|---|---|---|
| B1 | C 端领券、券包、最优券试算**改读新模型**（老模型只保留存量券的使用与退回） | `/mp/coupon*` 返回形状不变，数据源换 |
| B2 | 最优组合：预览里按「活动 × 券」枚举（每家店的候选活动 + 不参加 × 可用券 + 不用券）取总优惠最大 | 预览新增 `activityOptions`（每家店命中的活动与金额、当前选中的）与 `bestCouponNo` |
| B3 | 下单与预览接受客户的选择 | `CreateOrderCommand` 加 `activityChoices: {merchantNo, activityNo \| "NONE"}[]`；不传 = 系统默认组合 |
| B4 | 建单时**再算一次**校验客户的选择仍然成立（活动没结束、券还能用），不成立就回错误码让端上重选，不静默换 | 复用 40001 / 40002，活动新开一个码 |
| B5 | 老模型的券与活动在下单时也写 `pmt_apply`（只为了明细有名字） | 无 |
| B6 | 商品详情下发 `promotions`（本店进行中、此商品能命中的活动标签） | `GoodsVO.promotions` |
| B7 | 店铺页领券列表：按店铺取可领的券 | `GET /mp/coupon?merchantNo=` |
| B8 | B 端订单详情带 `discountLines`，每行加出资方 | `OrderVO.DiscountLine.funder` |

B2 的枚举规模：每家店命中的活动通常 1–3 个、手里可用券通常不超过 10 张，
一单几家店相乘也在几百以内，预览里算得动；超过上限（比如 200 组）就退回「先活动后券」的贪心算法并记日志。

## 五、要你拍板的四件事

| # | 问题 | 建议 | 理由 |
|---|---|---|---|
| Q1 | 两套券模型怎么收口 | **C 端全部改读新模型**，老模型只让存量券用完、退回 | 商家从 B 端建的券现在顾客根本看不到；老模型没有范围、发放方式这些字段 |
| Q2 | 进下单页要不要替客户选好券 | **要，默认最优组合** | 不选的话多数人不会点开面板，券白领了；主流电商都默认选好 |
| Q3 | 「不参与活动」的粒度 | **每家店选一个活动或不参加** | 活动本来就按店算、同店互斥；整单一个开关会误伤别的店 |
| Q4 | 默认组合怎么算 | **活动与券一起枚举、总优惠最大** | 「先活动后券」会漏掉「不参加活动只用券更省」的情况，那正是客户要自己去点「不参与」的原因 |
