## 2 和已定口径对不上的地方

| 表 | 问题 |
|---|---|
| `prd_goods` | 原表注释是“商品只属于一家门店（ADR-030）”，和“连锁共用商品与 SKU”冲突。字段里先把门店号改成可空，空表示主体下各店共用。要和 ADR-030 对一下 |
| `mch_store_fulfillment` | 清单说履约方式包括堂食、到店服务，但原表的取值不接受这两类，取值范围要放开 |
| `mch_entity` | 说明里写主体上有“评分”，备注又说评分、销量是派生数据不放主体上。字段按备注去掉了，评分从哪里读要定 |
| `stl_payment` | 交易流水的方向里有补差、出款，和“支付库只管收单”不符，应迁到账务结算库。对账差异 `stl_recon_diff` 已移到账务结算库 |
| `pay_channel_operation_intent` | 分账和现金退款回退并进了渠道操作，分账应归账务结算库 |
| `pts_record` | 发分规则应该每行一版，现在只有修订号；积分应收是资金，宜由统一账户记；可用性投影、日统计是派生数据 |
| `pay_points_funds_authority` | 去掉技术列后几乎没有业务含义，建议确认是否并入出款后不建 |
| `job_cursor` | 并入的两张积分表不是游标：一张是幂等记录，一张是退款重试的待办单。后者如果是业务待办，应归订单或积分 |
| `sys_outbox` | 并入的 `cim_operation` 是对外操作的工单，不是事件 |
| `pay_operation_audit` | 已经是全平台的统一审计，表名还带 `pay_` 前缀，建议改名 |
| `pay_refund_review_rule` | 原规则要求“生效确认人不得等于起草人”，和“同一人可填可审”的约定可能冲突 |
| `ind_config_revision` | 带着美业专属的列，可以收进定义内容，让这张表和行业无关 |

## 3 各份之间没有统一的做法

字段是分 11 份设计的，下面几处各份处理不一致，落地前要统一。

- **正式与测试环境的标记列 `execution_environment`**：支付库保留了，支付商户库、账务结算库、基础能力库、会员营销库当作技术列去掉了。要定一个口径。
- **去重键算不算业务数据**：通知、风控事件上的去重键当作业务去重保留了，打印任务上的当作技术件去掉了。
- **打印机的投递权与租约到期**：清单的说明要求有，但它本质是分布式锁，和“技术件不入库”冲突。
- **数量用整数还是小数**：库存余额、限量额度是小数，但日结存、预占行、购物车行、下单锁量、资源容量沿用了原表的整数。餐饮要称重或半份的话要统一改成小数。
- **原列改名**：有几处为了统一口径改了原有的列名，如餐牌号改成目录号、内容的帖子号改成内容号、几张规则表的版本号统一叫 `version_no`。迁移时要对应。
- **凭据改存密钥库编号**：出款账户的账号密文、终端的设备密钥、通知渠道的商家凭据、店长授权码、报文的数据密钥，都从“存密文”改成了“存密钥库编号”。这是存储方式的变化，迁移时要搬存量；其中店长授权码要求密钥库能按值校验，报文的数据密钥如果要求和密文存在一起，需要和密钥库的方案再对。
- **同义的重复列**：`pay_terminal`、`prn_job`、`usr_account`、`ord_after_sale_item` 等保留的表里有新旧并存的同义列，按“保留的表不改原列”都列出了，迁移时各留一个。

## 4 取值是推测的

原表没有写枚举取值、字段说明里的取值是按含义推测的，落地前要拿代码核对：`rpt_daily_expectation` 的状态、`inv_demand_plan` 的状态、`cmt_pickup_point` 的状态。其他表的枚举取自原列注释。
