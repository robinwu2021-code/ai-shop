# 会员营销库：表说明

状态：设计稿。创建：2026-11-26。上一层：[清单](../01-清单.md)。下一层：[表字段](../字段/07-会员营销库.md)。

## 这个库是什么

**商家和顾客的关系，以及给顾客的优惠与预付资产。**

| 项 | 说明 |
|---|---|
| 管什么 | 会员、来源、门店档案、标签与分群；触达；活动及其范围、版本、报名；额度与预留；券与次卡的发放、持有、流水、核销；券、次卡与储值方案的模板；储值发行方、账户与入账；归因；品牌活动成本的分摊规则与依据；专题与运营位；单位客户；收藏与到店足迹；拼团的团与团成员；卡券与支付之间的对接与对账；评价、点赞、申诉与内容（帖子、问答、素材）；顾客档案；会员等级规则 |
| 不管什么 | 钱的结算（支付库）；一张订单里优惠怎么分摊到每一行（门店交易库的报价分摊）；用户账号（平台基础库）；卡券与支付的对账运行（任务库）与对账差异（账务结算库） |
| 谁在用 | 商户端做活动、发券、管会员；C 端领券、充值、用卡；门店交易库下单时来算优惠、核销卡券。 |
| 和其他库的关系 | 商户储值的规则、账户和入账归本库；门店间清分由账务结算库承接。平台积分亦归账务结算库。 |
| 现状 | 新建，从 shop 库拆出。 |

## 会员、活动和卡券对齐

原始评审基线为 v2 的 `bc21cec44`，本轮基于 `f939a629e` 工作区复核。下表用手持收银机清单的页面编号对应目标表。「并入」是目标设计，现行写入和历史单据仍按 v2 的归属处理。

| 业务入口 | v2 行为 | 目标设计与合并条件 |
|---|---|---|
| C03、V01–V06 会员识别、档案与消费 | 多店主体用 `mbr_member_store` 记录会员在各店的订单数、消费和分层；单店读取主体记录。等级重算从 `mbr_member_source` 的 ORDER 来源按会员、门店分别统计近 90 天订单。 | 保留来源明细和子订单幂等键。门店往来并入 `mbr_store_profile`，按原会员号定位各门店统计，主体人数只计一次。STORE 身份用于独立门店会员。退订与黑名单仍按原身份生效；门店私有备注与顾问归 `mbr_store_profile`。V04 的积分明细由账务结算库提供。 |
| V08、V10–V12 等级与人群 | `MemberLevelServiceImpl` 从 `SettingPort` 读取经营分层策略，结合近 90 天订单和末次下单时间计算 `level`。 | 经营分层与等级权益分别记录。V707 增设的 `mbr_level_rule` 保存版本化等级权益规则，对应 `grade_code`。标签定义、会员标签关系、分群条件及一次圈选结果各有不同粒度，分别保留。 |
| T01–T03、T05–T07、T10 活动配置与成效 | `ActivityVersionServiceImpl.publish` 校验草稿修订号，发布时保存规则、人群快照及哈希。`ActivityRuleValidator` 将参与门店限定为 ALL 或 STORES。 | 保留活动主表和发布版本。范围明细共用 `pmt_activity_scope`，按租户、对象类型、对象号和版本隔离；参与门店、目标商品和受众仍按各自规则校验。触达任务引用活动和人群，按投递记录统计触达；核销成效按去重后的使用记录统计。 |
| T02、T04、T08 制券、发券与核销 | 旧券由 `PmtCouponServiceImpl` 管理；统一权益由 pay 域处理。结账由 `LegacyCouponRouteResolver` 查持有人、来源与迁移状态，切换后核对目标实例和切换凭据；迁移冻结期间暂停使用。 | 模板与版本合为 `ent_template`，模板范围并入共用范围表，已发实例引用发行版本。区分批次、单次发放、持有实例；消费依次产生使用意向、实例分摊、确认流水与核销记录。取消释放原占用，退款按原核销记录冲回。旧编号仍需路由到唯一写入方。 |
| T09 团购取货 | 手持清单将取货列为独立业务入口。 | `pmt_group`、`pmt_group_member` 保存成团及参与关系。取货履约结果由交易侧提供，卡券核销只登记实际使用的权益。 |

**待确认项**

- 会员合并前验证同一会员跨两店的来源回放、门店分层、退订与单店回落，确定原会员号到范围行的映射。
- 新报名及重报按提交修订冻结选品，记录当时可核实的平台发布版；旧报名保留明细。V12、T07 已接入固定人群发券和即时发送。T10 可按活动筛选事件，按原成交日回算的五项指标还需订单行分摊与支付时会员事实。进度见[重构任务清单](../会员营销重构任务清单.md)。
- 卡券合并前验证旧券、已切换券及历史退款均能定位原使用记录，重复确认或冲回只计一次，再决定效果投影的物理实现。储值的分配粒度见下文。

### v2 会员与活动的库表切换

| 迁移 | 当前写入路径 | 回填与恢复 |
|---|---|---|
| V725 门店档案 | 多店会员的下单统计、分层重算和报表使用 `mbr_store_profile`。主体和运营范围身份继续按原号识别。 | 依据租户、主体会员、人档与门店归属核对存量有效往来。匹配已有档案时仅更新经营指标，保留顾问和私有备注；有歧义的行须先处置。 |
| V722 活动范围 | 版本化发布保存参与门店和分群快照。报名及重报按提交修订保存选品；详情和算价按报名提交修订读取选品，缺修订的历史报名读取旧选品。 | 已发布版本保留原快照与哈希。无提交修订的历史报名仍读取原商品明细。 |
| V723 活动额度与预留 | 总额度与个人计数写 `pmt_quota`，以预留号、原来源摘要和参数摘要驱动 `pmt_reservation` 确认、释放和超时核查。 | 迁入旧额度、已用与占用量和存量预留的原始状态。待处理预留继续按原来源查最终决定。 |
| V707 等级权益 | 已有会员的 `level` 保持原经营口径，等级规则表和权益等级引用列单独建模。 | 历史会员的权益等级引用初始为空。录入正式规则并核定等级前不授予权益。 |

部署时暂停受影响的会员、活动写入及后台恢复任务，待旧事务排空后执行迁移，再统一启用新版写入。旧表保留迁移前数据；一旦新版已有交易，回滚前须核对并回补该时段增量。以上改动沿用现有核心事务数据源，表的物理分库另行切换。

### 首批商家自发券的实施范围

| 环节 | v2 写入及兼容方式 |
|---|---|
| 商家制券、改券 | Core 为符合条件的订单单次抵现券、封顶折扣券发布 `pmt_coupon_version`，范围写入 `pmt_activity_scope` 的 `ENT_TEMPLATE` 版本。领券中心和定向发放使用当时的版本，之后编辑模板不会重定价已发券。 |
| 领券、定向发放 | 自领的 `pmt_user_coupon` 记录领用版本；定向发放同时记录 `pmt_coupon_issue` 批次号和版本。调用方重试同一操作时复用原 `Idempotency-Key`。库存、每人限领和预算按实际发出数扣占。 |
| 历史券筛选 | V724 只为 MAIN 下可证明原始规则的整族旧券补版本。要求商家承担、全范围、模板未编辑、计数及批次归属一致，每张券均未过期、未用且无用券流水。存在已核销后退回的券、旧 MKT 重号或归属不明时，整族留在原路径。 |
| 切换与继续发放 | 按原券号排空并冻结源端，暂存完整快照，在迁移计划指定 `UNUSED_MERCHANT_COUPONS`，核验后提交并导入。切换前由 Core 发券，切换后旧入口按归属路由到 Pay 统一权益，同一请求可重放原回执。无核销历史的商家券按实例的领用版本导入；同族多版本须能逐版还原规则、适用门店，并对平全族累计敞口。Pay 报价和占用继续校验原面额及范围。已验证同族旧版仅门店 A 可用、面额 100，新版全店可用、面额 200。 |
| 下单与取消 | 报价只读；已切换的商家券在 Pay 占用，Core 建单成功后确认核销。建单失败释放占用；成功核销后整单取消按原核销额恢复一次，来源为 `ORDER_CANCEL`，保存原订单号。 |
| 整单退款 | 返券开关开启、所有子单满足退结条件后，由 Core 确认整单返券。Pay 将 `AFTER_SALE` 来源、真实售后号、返还优惠额和次数记入 `ent_use_reversal`，通过同租户 `usage_no` 关联原 `ent_usage`。重复处理返回同一结果。 |
| 有核销历史的券 | Core 所有的券按原 `pmt_apply` 撤销；已迁入的历史核销通过 `ent_migration_usage` 按原 apply_no 定位，按原基线回补并写冲回明细。仅有历史撤销状态且无权威决定的记录保留原证据。 |
| 表数口径 | `pmt_coupon_version` 是兼容期来源表，目标并入 `ent_template`。历史核销和售后继续按原归属查询，目标用 `ent_usage` 关联多笔 `ent_use_reversal`，两表分别计数。 |

新建交易按子单内商品行的金额分摊券优惠，按最大余数分配尾分，保存 `ord_item.coupon_share_minor`。同一行分次退件时，按累计退件比例的前后差额确定当次 `ord_after_sale_item.coupon_return_minor`。首批已迁商家券按真实售后号在原 `ent_usage` 下记金额；部分退不恢复次数，整单符合退结条件时只恢复一次。到期券保留到期状态。缺行证据的历史券维持既有整退规则。

上线 V708、V709 和 V724 时先排空旧版制券和发券写入，待所有写入节点均支持版本绑定后恢复。历史券的权属切换另按券号执行。

## 储值链路与支付调用

储值链路已按 v2 `f939a629e` 复核。现行储值写入使用 `payTxManager`；目标由会员营销库作为账户、批次、使用意向和凭证的唯一写入方。交易侧继续提供订单、授权和最终决定，账务结算库按消费凭证及使用记录承接跨店清分。跨库交付按稳定业务号去重，失败可重放。

| 环节 | 会员营销的处理与凭据 | 外部调用与恢复 |
|---|---|---|
| 充值收款 | 冻结来源、发行方、方案版本、本金和赠金，建立 `sv_recharge`。v2 的 CASH、TRANSFER、MERCHANT_OFFLINE 由经办方提交实收金额和回执，核对金额等于本金、回执摘要匹配后从 WAIT_COLLECTION 经 SUBMITTED 到 RECEIVED。 | 此线下流程直接登记凭据。若后续接线上渠道，由收款方调用支付发起收单，接收结果并按原支付号查单；确认实收后才产生到账依据。 |
| 充值到账 | 根据已确认收款决定锁定充值单和账户，建 `sv_lot`，更新本金、赠金、账序，同事务写 `sv_voucher`、`sv_entry`、`sv_posting_line`，置 CREDITED。以原充值号恢复 RECEIVED 未到账单，已到账重放返回原结果。 | 余额、赠金和充值流水由会员营销查询；重试到账沿用同一收款事实。 |
| 消费预占 | v2 核对 CORE/SERVICE_USE 来源、订单快照、钱包、币种、金额和有效授权。锁意向、账户和批次，以 `operation_no + lot_no` 固化本金、赠金和行分摊，同事务更新两级冻结额及 HELD 状态。 | 交易侧提供来源与授权。纯储值核销由会员营销执行；未来组合收款如获支持，仅外部实付部分调用支付。 |
| 消费确认或取消 | 按原意向查询来源决定。确认逐批解除冻结并扣本金、赠金，更新账户账序，生成凭证、批次分录、备查账、使用记录和清分依据。取消只解除原冻结，置 RELEASED。相同决定重放返回原结果。 | 来源决定为 PENDING 或 UNKNOWN 时保留占用并查原决定。支付结果只证明渠道款项，交易侧负责形成整单决定。 |
| 纯储值消费后整笔退款 | Core 在已确认的服务单保存退款决定及命令快照。储值账核实原 `ent_usage`、消费凭证和金额，按原 `sv_entry.lot_no` 分别回补本金与赠金，追加 REFUND 凭证、批次分录、按池配平的备查账、正向退款账单；有跨店清分时冲回原清分。成功后核销置 REVERSED。 | 使用固定退款号恢复丢失的回执，以原消费凭证唯一约束防止换号重复退款。纯储值全退无需渠道调用。混合付款的外部资金腿另行处理。 |
| 充值撤销或退资 | v2 允许 WAIT_COLLECTION、SUBMITTED 取消。已到账退资是单独的待定能力，需先确认批次已用、已冻时可退本金及赠金收回规则，再锁定原批次、记录冲正并关联原收款。 | 对已发生外部实收的退资分别处理渠道原路退款或线下退款凭证；业务冲正与资金退回均有确认结果后才能标记完成。 |

**按行部分退款的证据。** 新占用的 `sv_hold_allocation.items_allocation` 按原批次和服务行保存行号、占用总额、本金与赠金。逐行按累计比例取整，尾行取该批次余数。历史占用仅有行号与总额，整退按原批次回补；缺证历史单无法据此计算单行应返本金和赠金。按行退款资金执行仍待业务放行。

**支付边界。** 现有普通交易可用 `OrdinaryPaymentPort.open/query/refresh` 和 `OrdinaryPaymentInitiationPort.initiate` 建立、发起和核实渠道收款；`OrdinaryRefundPort.request/query` 以冻结的原请求执行、恢复渠道退款。这些是外部资金腿的接口依据，v2 的线下储值充值没有接入这条线上链路。支付保有渠道交易号、收退款回执及对账事实。储值报价、冻结、确认、释放、余额和批次查询均归会员营销，门店间结算由账务结算接收可追溯的清分依据。

**待确认项。** 消费后部分退的行级累计额度与并发冲回约束、充值退资政策及线上支付接入尚需专项确认。`sv_statement` 的历史展示和分页、`pmt_recharge_intent` 的来源幂等与结果回写继续保留，物理承接单列待定。
