# 设计思考：这份库表方案是怎么想出来的

状态：参考材料。创建：2026-11-26。
用途：记下整理过程中的判断、走过的弯路和没有采纳的做法，供以后做设计决定时参考。结论本身见[清单](01-清单.md)和各库文档；逐轮的调整记录见[清单复核](../清单复核-重复、错放与遗漏.md)。

这份方案是纸面的目标：库里的表和代码都没有动，合并与归属没有对着代码验证。

## 1 要解决什么问题

正式库里有 1078 张表（shop 库 850、支付库 251、库存库 57、报表库 23、任务库 4，重名只算一次）。问题不是“表多”，而是三件事：

- 同一个业务对象建了多套。订单、商品、预约在零售、餐饮、美业各有一套；密钥、权限、事件在支付和 shop 各有一套。
- 表放错了地方。约 170 张支付域的表建在了 shop 库；餐饮的交班、日结其实是收银的事。
- 业务库里混着大量技术件。每个模块各自的事件收发、幂等、发号、变更日志。

目标是按业务域分成干净的新库。现在是 14 个库、376 张。

## 2 走过的弯路

下面几条是做错后被纠正的，记下来是因为它们都很容易再犯。

| 做法 | 为什么不对 | 改成 |
|---|---|---|
| 按“空表、代码零引用”找冗余 | 空表可能是还没上线的功能；零引用可能是按前缀动态拼的表名（库存的事件表就是）。它回答的是“现在用没用”，不是“该不该有” | 按业务对象判断：同一个对象有没有建多套 |
| 用联表关系、代码依赖矩阵来分库 | 现有代码的耦合是历史形成的，照着它分只会把现状固化 | 先定业务域，再看表属于哪个域 |
| 为了压表数，把一对多的明细并进主表 | 运单轨迹、核销明细、菜单时段并进主表后只能存成一段内容，查不了、约束也没了。这类问题前后出现过三轮 | 明细保留为表；合并要有业务理由 |
| 给每个业务库各配一套技术件 | 等于把冗余换个地方再建一遍 | 事件、发号是公共能力，只有一套；防重由应用层做 |
| 用行数、现有列来论证该不该合并 | “这张头表现在几乎没内容”说的是现况。逻辑上需要而现况没有的，应该补上 | 结论从业务逻辑推出，现况只用来估迁移代价 |
| 每定一条就改一遍清单和所有文档 | 结论还在变，反复改写既慢又容易前后不一致 | 讨论时只记结论，按指令一次性更新 |

## 3 判断一张表的四个问题

对每张表依次问：

1. **它是哪个业务对象？** 说不出对象的，多半是技术件或过渡表。
2. **这个对象是不是已经有了？** 有就合并，前提是两者真的是同一个对象，不只是长得像。
3. **它归谁？** 一个对象只有一个归属库，其他库只存编号和必要的快照。
4. **它是不是通用能力？** 是就用平台的那一套，业务库不建。

冗余因此分四类：重（同一对象多套）、旧（旧一代或迁移过渡）、错域（放错了库）、技（技术件）。

## 4 定下来的原则和理由

### 4.1 按业务抽象收敛，合并要有业务理由

同一对象的多套、旧一代、同构的重复才合并。判断“是不是同一个对象”看三点：生命周期是否一样、是否被同样的东西引用、状态是不是一回事。

反例值得记住：

- **账号和人员不是一个对象。** 账号是登录凭据，人员是对顾客提供服务的人；有人员没有账号，有账号不是服务人员。合成“员工”后两种状态搅在一起，后来恢复成两张。
- **标准品和商品不是一个对象。** 标准品是平台的商品模板，没有主体、没有价格、不上下架。
- **平台的单和商家订单不是一个对象。** 平台单先于商家订单存在，没接的、导入失败的都没有商家订单。
- **渠道账号和门店连接不是一个对象。** 一个品牌一个账号，下面挂多家店。

### 4.2 一对多的明细保留为表

只要“有多条，且各自有状态或需要被查询”，就是表，不是主表上的一段内容。结构不固定的扩展属性（行业扩展内容）才用一个内容字段。

### 4.3 库里只存业务数据

事件收发、发号是公共能力，在基础能力库各一套。防重是功能能力，由应用层做，加业务表唯一键兜底，不建表。一次性随机数、验证码状态这类短期数据放缓存。各环境的接入地址是配置。

### 4.4 通用的能力用平台的一套

| 能力 | 在哪 | 业务库怎么用 |
|---|---|---|
| 字典 | 基础能力库 `sys_dict_item` | 引用字典项编码。行业、市场、行政区划、计量单位、类目授权码、渠道产品、支付渠道、支付产品都是字典类型。字典只放定义；定义下面一对多、各自要开关的东西（如支付产品的能力）仍是业务表 |
| 事件 | 基础能力库 `sys_outbox` 等 | 发事件；对外部接入方的通知也是事件的一种投递 |
| 轻量审批 | 基础能力库 `sys_approval` | 店内和运营的快速审批（退菜、改价、调费率档），业务表存审批单号 |
| 重的审核与工单 | 独立的审核与工单服务 | 入驻、变更申请、客服工单、门店待办、内容审核。它还负责审核通过后的执行编排。业务表只存单号 |
| 审计 | 基础能力库统一审计 | 谁在何时改了什么。各模块不再建自己的变更日志表 |
| 密钥 | 密钥库 | 业务表只存密钥编号 |
| 通知、打印、发票、物流、风控与告警 | 平台服务库 | 业务库不各建一套 |
| 定时任务 | 任务库 | 同步运行、批次都用它 |

App 的版本与功能目录由单独的 App 项目管理，不在这些库里。

### 4.5 带版本的表分三类

“带版本”在业务上是三种不同的东西：

| 类型 | 业务含义 | 表怎么建 | 例子 |
|---|---|---|---|
| 规则与定义 | 业务按当时生效的那一版执行，事后要能查回是哪一版；本身没有运行状态 | 一张表，每行一版，带版本号、状态、生效起止 | 套餐、卡券模板、计价定义、费率档、提成规则、配方 |
| 活的业务对象 | 自己有运行状态，被别人长期引用；版本只是某个时刻的内容 | 对象 + 修订两张 | 商品、商城 SKU、活动、密钥、预约单 |
| 申请与提交 | 一次申请有自己的流程状态，过程中多次提交 | 申请 + 每次提交两张 | 进件、开票申请 |

判断是不是第一类，看头表是不是只剩一个编号。

凡是直接决定钱或权益怎么算的规则，都要有版本，即使现在没有：改了规则不能影响已经算过的结果。只看当前值的（告警阈值之外的各类设置、通知模板、班表）不需要版本，改动留在审计里。

门店目录是个特例：它不留历史版本。订单行自带下单时的品名、规格和价格，没有业务要回查当时那一版目录。它只需要草稿与已发布之分、一个版本号供各端同步对齐，最多留上一版供回退。

## 5 库是怎么分出来的

### 5.1 为什么是这 14 个

| 库 | 回答的问题 | 单独成库的理由 |
|---|---|---|
| 平台基础库 | 谁在这个平台上 | 主体、门店、人、账号是所有业务的前提，判权限不跨库 |
| 基础能力库 | 各库共用的公共能力 | 不属于任何一个业务 |
| 密钥库 | 钥匙单独锁起来 | 渠道凭据能直接动钱，不能让所有能连基础能力库的服务都够得着 |
| 平台商城库 | 商户向平台买什么 | 面向 B 端，和 C 端交易是两门生意 |
| 门店交易库 | 门店卖东西 | 三个行业公用的商品域与订单域 |
| 行业库 | 餐饮、美业特有的营业过程 | 行业各自演进，不影响交易主库 |
| 会员营销库 | 顾客关系、优惠与预付资产 | 和交易隔离，可以独立扩展 |
| 库存库 | 货从哪来、还剩多少 | 已经是独立的库 |
| 支付商户库 | 谁有资格收钱、按什么条件 | 是配置类数据，和交易没有同事务要求 |
| 支付库 | 把钱收进来 | 收单要稳，范围越小越好 |
| 账务结算库 | 把钱记清、分好、付出去 | 账要独立于收单 |
| 平台服务库 | 平台替大家做的事 | 通知、打印、发票、物流、风控 |
| 报表库 | 每天看结果 | 是算出来的数 |
| 任务库 | 后台定时做的事 | 各库共用 |

### 5.2 几个反复掂量过的划分

**零售、餐饮、美业合不合。** 餐饮和美业的订单依赖零售的订单，所以商品域和订单域只能有一套，放在门店交易库。行业特有的过程（桌台、厨房、堂食服务、人员安排、服务步骤）单独成库，只通过编号引用订单、到店单、预约单。代价是两库不能同事务：下单后出品、到店后占桌走事件，会有短暂延迟。并台拆台要改订单行，所以留在门店交易库。

**资源预约放哪。** 留在门店交易库。它不是某个行业特有的；如果搬到行业库，公用的预约单反过来要依赖行业库。

**积分和储值在不在一起。** 不在。积分作为资金结算，在账务结算库；储值都在商户，是卡券的一种，在会员营销库。

**支付要不要拆。** 拆成三个：支付商户（配置）、支付（收单）、账务结算。支付商户是配置类，建议最先拆。

**平台基础和账号认证合不合。** 合。账号、B 端授权、门店同库，判权限不跨库，入驻是一个事务。

**密钥放两处还是一处。** 先考虑过“同一套结构、支付的密钥单独存放”，要多 7 张表；最后选了单独一个密钥库，只要一套。代价是支付取渠道凭据要依赖密钥服务，所以密钥服务要高可用，支付侧要有短时缓存。

**订单要不要合成一层。** 保留两层。支付单是顾客的一次付款，商家订单是各商家各自的履约与售后。先吃后付时商家订单先于支付单存在。

### 5.3 认证与权限

- 三端的认证各一套；会话、登录日志各一张。
- B 端与运营端的角色权限各一套：B 端在平台基础库，运营端在基础能力库。
- 网关只做认证和透传，谁提供接口谁判权限。所以支付运营的权限映射与数据范围授权留在支付商户库，支付判权限不依赖别的库。
- 店主默认全权，App 的权限由 ai-shop 决定。

## 6 几个具体的设计

### 6.1 门店目录

连锁里真正共用的是商品库，不是菜单。总部建商品和 SKU，各店自己选品上架、自己定价，这是多数连锁的常态；总部把菜单复制给门店是一次操作，不是持续的关系。所以目录是“一家店的一份在售清单”，一家店可以有多份。只有大型直营品牌才需要“一份目录发给多家店”，到时再加一张表即可。

目录下面有四样明细，各是一张表：生效时段（每周时段与日期例外）、条目的 SKU 价（外卖菜单另一个价靠它）、限量与估清（按营业日）、可售量规则（库存里拿多少出来卖）。

### 6.2 渠道（外卖、团购平台）

渠道来的订单就是普通的商家订单，不另建订单表。但有两样必须独立：渠道账号（一个品牌一个账号）和渠道订单（平台的单，先于商家订单存在，要让店里看到没接的和导入失败的）。“同步什么”就是一份门店目录，零售的渠道选品不另建一套。

### 6.3 支付接口的三层

一次支付接口调用涉及三件事，分在三处：

- 谁在调：开放应用，在基础能力库，是平台级的，支付和库存的对外接口共用。
- 凭什么证明：密钥，在密钥库。
- 能做什么：权限。运营端的角色在基础能力库，支付侧的权限映射与数据范围在支付商户库。

### 6.4 商户支付产品与产品定义

这是两件事。“有哪些支付产品”由代码里有没有接决定，是字典。“这个商户开通了哪些”是业务事实，有开通状态、来源、证明、额度，必须是表，而且只能由渠道回执或运营确认写入，不能按主体类型推断。

### 6.5 渠道费率

费率是业务规则，在支付，不在字典。三张表：

- 费率档：档位的定义，每行一版，带自动定档的适用条件与优先级。
- 费率档明细：档里每个渠道、每种支付产品、每个市场的费率。
- 门店费率档：门店现在在哪一档，自动还是人工，按生效起止留历史。

人工指定优先于自动，走轻量审批。要给某家店单独的优惠费率时，建一个专用的档指给它。渠道向平台收的成本费率是一种特殊的档，不另建表；它不随商户的档位变，所以不能做成明细上的一列。

平台佣金率（按经营模式与流量来源定的抽成）是另一回事，在账务结算库。

### 6.6 终端上的“会话”

支付终端的操作员会话按列看是登录令牌（令牌摘要、过期、吊销），所以并入 B 端会话。“谁在这台终端上当班”由收银班次承担。连带的要求：每笔收款、退款要自己记操作员号和班次号，不能只引用会话；同一班次中途换人时以收款上的操作员号为准。

### 6.7 设计字段时才暴露的明细

表的取舍定完之后设计字段，才发现有些信息是一对多、各有状态的，清单里却没有表。逐条看下来分成三种：

- **真的缺表，补上。** 支付产品的能力、每次投递的尝试、进件资料逐项、券的适用范围、裂变邀请、发货明细、打印路由的规则、门店码，共 8 张。
- **其实已经有表承担了。** 运营账号的角色用授权表，设备的历史密钥在密钥库的版本里，售卡的逐份交付就是履约单元，权益使用历史就是卡券使用记录。这类不补，是设计字段的人没看到全局。
- **作属性够用。** 组合很少、不单独查询的（目录的下单来源与履约方式、厨显订阅的工位）。

教训：只看表名和说明定取舍，容易漏掉明细。合并一张表之前，先看它的列里有没有“多条、各有状态”的东西。

同一轮还去掉了卡券对接的三张：防重入的栅栏是技术件，对账运行归任务库，异常处置走工单。对账差异从支付库移到账务结算库，作为全平台的对账差异。

### 6.8 对照功能清单再看一遍

表的清单是从“库里有什么”出发整理的，容易漏掉“功能需要什么”。拿手持收银机的功能清单（19 个模块、201 页）逐模块对了一遍，结果分三种：

- **功能佐证了之前把握不高的表。** SKU 条码、打印路由的规则、门店码、限量与估清、分摊份额、渠道账号、离线草稿单，都有对应的页面。
- **功能有、表没有。** 受信任装置、员工打卡、总部下发及各店的套用状态、门店级的设置。前三个是有状态的对象；门店设置是一批散落的开关（PIN 策略、自动锁屏、开票时机）没有落点。
- **同一个东西两处各存一份。** 手持机是一台设备，激活、装置管理、换机操作的都是它，却同时登记在门店设备和支付终端两张表里；推送活动的发送记录和通知的发送记录是同一批。

教训：功能清单只代表一个端，“没出现”不等于“没用”，只能用来补和合，不能用来删。

### 6.9 命名

- 库名统一以 `n_` 开头。
- 表名是“业务前缀 + 对象名”，一个库里只用登记过的前缀。清理过程中很多表换了库，前缀却还是原来的（订阅在商城库却叫 `mch_`，资源预约在交易库却叫 `mch_`，统一审计叫 `pay_`），所以按现在的归属统一改了 47 张。
- 每张表都有同一组公共字段：自增主键、创建时间、创建人、更新时间、更新人。只有更新时间用 `timestamp`，创建时间和业务时间用 `datetime`。
- 逻辑删除和乐观锁版本号按业务需要加：主数据和配置才要逻辑删除，流水、明细、资金记录不允许删；会被并发修改的行才要版本号，只追加的流水不要。
- 表改了名，引用它的字段名也跟着改。

规则见[命名与字段规范](02-命名与字段规范.md)。过程文档里用的还是改名之前的名字，对照见[表名对照](03-表名对照.md)。

## 7 没有采纳的做法

| 做法 | 没有采纳的原因 |
|---|---|
| 餐饮 14 张空表直接删 | 是规划中的功能，保留 |
| 把积分和储值的账都放账务结算库 | 储值目前都在商户，留在商户一侧 |
| 行业并成一棵树 | 进件行业和门店行业不是父子，是两套分类 |
| 行业库并回门店交易库 | 保持单独成库 |
| 餐牌时段与资源班表共用一张时段表 | 一个管卖不卖，一个管能不能约，硬放一起会互相牵制 |
| 求购关注并入通用收藏 | 把握不够 |
| 离线草稿不建表 | 离线单可能要长期当凭证查 |
| 同步范围并入资源映射 | 同步策略可能要按目录分别设 |
| 支付的密钥与其他密钥分两处存放 | 要多一套表，改成单独的密钥库 |
| 一份目录多店共用 | 先按单店，各店自己处理是常态 |

## 8 还没有定的

- 内部的下单结账服务要不要登记为开放应用。它发起了线上全部支付订单，但属于内部服务之间的调用。
- 支付库里 4 处把握不够的合并：终端验收交工单、渠道交易上下文并入交易流水、回跳凭据并入收银台会话、渠道往来日志与渠道操作和渠道观测是否重复。要读代码才能定。
- 风控是否进一步做成全平台统一。支付的告警已并入，支付的风控规则还没有看。
- 连锁的区域层级。
- 员工的邀请与加入、账号注销与个资删除请求，可能是遗漏。
- 支付库有 8 张暂存表有线上数据（一张一万八千行）却标了不迁入，迁库前要确认。

## 9 用这份方案之前要知道的

- **没有对着代码验证。** 合并与归属按列结构和业务含义定。最重的几处：订单行、报价分摊、统一账务、统一结算、卡券承载券与次卡与储值卡三类资产、指派与执行。落地前要先验证。
- **字段是草案。** 保留的表沿用现有的列；合并和新建的表的字段是按并入的旧表推出来的，没有对着代码核过。
- **没有迁移步骤。** 这份方案只说了目标是什么，还没有写怎么从现在的库迁过去。
- **跨库协作的代价要认。** 库之间不联表、不共事务，协作走接口或事件，要有重试、对账与补偿。统一事件要支持签名的 webhook 和按接收方重试，才接得住原来支付对接入方的通知。
- **敏感资料的访问控制。** 主体资料归平台基础库之后，进件用的证件、银行资料也在那里，访问控制要跟上。
