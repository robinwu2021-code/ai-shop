## D2　储值账迁移演练

1. 按批次确定来源租户和共同截止位置，记录在途占用、未到账充值、未回执退款及未消费的清分事件。复制期间若允许旧端写入，应单独记录水位后的增量。
2. 先回填历史，再停止该批旧端写入和后台恢复，待原事务排空后补齐增量。在两个库同一业务水位执行[只读对照 SQL](../../../../scripts/sql/stored-value-cutover-evidence.sql)。脚本默认 MAIN，需按相同租户逐行比较两个输出，并与已知来源账户数核对。查询结果包含业务编号，留在受控环境。
3. 核对资格后切换唯一写入方和恢复任务。回放原业务号，观察旧占用释放、消费入账、原退款的回执补全以及结算侧按原号接收。核对时同步检查业务域已有的按账户、批次、分录和凭证的资金对账。
4. 回退需先停止新写、排空事务，把切换后的增量按业务键和账序补回旧端，再次比对并恢复旧路由。分库后单表自增 ID 不能充当跨库增量水位。

### 在途储值退款的扫描交接

V720 在交易库 05 建立 `ord_service_refund_recovery_owner`。现有受支持租户 MAIN 初始归 PAY。绑定 `shop.modules.member-marketing.datasource` 的恢复节点属于 TARGET。使用远程 Pay 时，恢复节点与其调用的 Pay 服务须采用同一部署归属。两个节点的定时退款扫描使用不同的 ShedLock 名称，各自从同一交易库取待回执订单。

1. 在两侧先部署支持交接的版本。按上面的 D2 流程停止该租户对外写入，然后在交易库执行下面第一条更新。它会等待已进入退款恢复的任务退出。同步排空旧 Pay 端已接收的请求，尤其是调用方断连或超时的请求，再补齐增量、核对账本。
2. 核对通过后执行第二条更新。每次更新须影响一行；影响零行时查明当前归属。新节点从交易侧持久的退款决定恢复，旧节点已领到的指针会在执行前被拦下。复用原服务单、核销号、退款号和决定；已入账时核验原命令摘要并返回原凭证回执。
3. 回切时按同样顺序从 TARGET 改为 PAUSED，待目标端写入排空、增量补回和双方对照完成，再从 PAUSED 改回 PAY。查询沿用原单号。

```sql
UPDATE ord_service_refund_recovery_owner SET scan_owner='PAUSED' WHERE tenant_no='MAIN' AND scan_owner='PAY';
UPDATE ord_service_refund_recovery_owner SET scan_owner='TARGET' WHERE tenant_no='MAIN' AND scan_owner='PAUSED';
```

2026-11-27，`StoredValueConsumptionFlowTest` 共 14 项通过。参数化用例 `restartedTargetResumesOriginalRefundWhileOldWorkerHoldsPointer` 分别在入账前和入账后未确认时重建恢复节点，并发执行旧指针和目标端扫描。两例均得到一张原核销对应的反向凭证、恢复后的完整余额及交易侧 REFUNDED；回切后的原单仍可查询。此用例在共享 H2 业务库上隔离 worker 上下文。

**本地演练结果。** 2026-11-27 在隔离 MySQL 9.7.4 建立两个空库，使用 V489、V495、V498、V502、V535、V570、V712、V713 的实际表结构和合成数据。账户含本金 70、赠金 14，其中冻结 5、1；另有已消费的本金 30、赠金 6，原服务单为 REFUND_PENDING，并有跨店清分。首次复制后 11 张储值相关表的对照结果相同。目标端追加整退及反向清分后，对照能识别差异；将新增事实及账户、批次、核销状态补回后，两端输出再次一致。交易侧待回执记录仍可按原号查询。

本次验证了同结构下的复制、差异发现和退款增量回补。在同一 MySQL 实例的两个隔离库，又以可更新 MERGE 视图将原写入表名路由到目标 11 张物理表。使用原表名写退款后回滚，目标退款凭证数为 0；再次提交后目标库出现唯一反向凭证。将增量补到保留的原表后一次性切回，并复核余额、冻结、账序、分录和清分。此方式验证了同实例过渡路由。

### 跨实例账本对照与回切

2026-11-27 在本机启动两个独立的 MySQL 9.7.4 进程，校验其 server UUID 不同。使用同一套 11 张表结构和合成储值数据，将源端复制到目标端。退款事务回滚后，两端仍相同；目标端单独提交原消费 30 本金、6 赠金的退款及反向清分后，对照能够识别差异。回切前按租户和原业务键将增量补回源端，特意让两端新增凭证的自增 ID 不同。相同增量执行两次后，两端一致；原交易服务单的待退款回执记录仍在。

实际执行对照时，先排空该批两个端点的写入并确认租户业务水位，再使用各自的只读连接配置。下例中的配置文件和库名由目标环境提供。

```sh
python3 scripts/verify-stored-value-cutover.py \
  --source-config /path/to/pay-reader.cnf --source-db pay \
  --target-config /path/to/member-reader.cnf --target-db member_marketing \
  --tenant MAIN
```

[只读对照工具](../../../../scripts/verify-stored-value-cutover.py)在每个实例的同一一致性快照内执行[账内检查](../../../../scripts/sql/stored-value-cutover-balance.sql)和[跨库对照](../../../../scripts/sql/stored-value-cutover-evidence.sql)。工具返回 0 表示该租户有账户、两个端点不同、账内检查通过且导出的业务证据一致。已用仅有 SELECT 权限的账号验证以下结果。

| 隔离试验 | 结果 |
|---|---|
| 两个空快照，或源、目标误指同一库 | 返回 1 |
| 金额一致，只有目标端账户的顾客号错误 | 返回 1 |
| 两端均把同一批次的冻结本金从 5 改为 4，账户仍为 5 | 返回 1，定位到账户与批次冻结额 |
| 两端账户账序均多 1，找不到对应凭证 | 返回 1；同时校验逐笔账序及两种账后余额 |
| 两端均将同一凭证的赠金借贷分录各加 1 | 返回 1；借贷仍平，但两本备查账均与原凭证不符 |
| 按业务键补回退款增量并重复执行 | 返回 0 |

本次验证的是数据库读写、业务键回补和只读对照。目标部署仍需以实际应用数据源完成写入切换、恢复任务接管及合表转换，并使用获授权的业务快照复核。

## M2 正式会员等级

首版按 `mbr_member.entity_no` 对应的商家主体定级。同一主体的门店共用一套规则，跨主体品牌各自定级。按门店经营的开关继续控制近 90 天经营分层。正式定级使用会员累计订单数，不汇总跨主体品牌数据，不生成门店私有等级。

发布和回填由 [member-grade.py](../../../../scripts/member-grade.py) 执行，参数需要明确指定数据库、租户、主体和经手人。运行依赖 Python 3 和 PyMySQL。发布时为每档给出唯一编码及最低订单数，第一档从零开始。首发不传 `--previous`，续版填写当前已发布的末版号。以下为隔离样本用法，实际档位和时间由发布人填入。

```sh
python3 scripts/member-grade.py --defaults-file "$GRADE_MYSQL_CNF" --database "$GRADE_SCHEMA" \
    --tenant MAIN --entity "$GRADE_ENTITY" --actor "$GRADE_ACTOR" publish \
    --rule R --version V2 --previous V1 --effective-from 2027-01-01T00:00:00+08:00 \
    --levels '[{"code":"BASE","minOrders":0},{"code":"GOLD","minOrders":4}]'
python3 scripts/member-grade.py --defaults-file "$GRADE_MYSQL_CNF" --database "$GRADE_SCHEMA" \
    --tenant MAIN --entity "$GRADE_ENTITY" --actor "$GRADE_ACTOR" backfill
```

生效区间使用 UTC 左闭右开。新旧版本在同一事务中相接，规则内容发布后保留，纠正档位时发布下一版本。回填以取得主体锁后的数据库时间选版，只核定当前范围的 ACTIVE 会员。未定级者首次写入，已有同一规则的会员按本次复核时的订单数升降级。已有等级缺少可信版本归属时保留原引用。生效后、正式复核前，设置页显示现行版本，会员详情继续显示上次核定的版本。回填只写两个等级引用及审计字段，不调用积分、券或储值发放。发布、核定均须显式运行。

## C3 部分返券与 S1–S3 储值扩展算例

以下金额均为最小货币单位。C3 已接首批商家券；储值扩展的资金执行范围见下方 S1–S3。

| 任务 | 输入 | 可确定的结果 | 待决定 |
|---|---|---|---|
| C3 券部分退 | 两行成交使用同一张一次券，共抵 100；假设交易侧已确认行优惠分别为 40、60。 | 先退第一行、重复该售后、再退第二行，优惠累计最多 100，一张一次券累计最多返还一次。 | 先按冻结的行实付确定行优惠容量，再在该容量内分摊券额。同一行分次退件取累计比例之差；部分退只记券额，整单退结才恢复次数，到期状态沿原有效期判断。 |
| S1 储值部分退 | 批次甲扣本金 80、赠金 20，行一/二分别占 60/40；批次乙扣本金 30、赠金 10，全部归行二。 | 整退固定返 110、30。甲的行一可为 60、0，也可为 40、20；两种都与现有证据一致。历史单单靠行总额不能决定应退本金、赠金。 | 新单行内拆分、尾差和历史缺证策略。若选择甲行一退 48、12，则行二应退 62、18；两次合计 110、30。 |
| S2 充值退资 | 实收 100、赠 20。未用时余额 100、20；用去 30、6 后余 70、14；若另冻 10、2，则可用余 60、12。 | 充值实收、仍持有额和可用额是三组不同的数。外部原收款只能按本金实际退款结果对账。 | 未用、已用及已冻分别可退多少；冻结等待还是先解冻、已用赠金如何处理。需分别保存余额冲正与资金退回结果，未知时按原请求号查证。 |
| S3 混合付款 | 原交易 100，储值实扣 60、外部实付 40。 | 整退两条腿的上限分别为 60、40；渠道超时不能导致储值腿重复返 60。 | 确认支持的渠道、部分退分配、处理顺序及一腿成功另一腿未决时向门店展示的状态。 |

### S1　消费按行退回

**已实现的新占用证据。** `StoredValueRedemptionPostingServiceImpl.prepare` 在原支付事务中锁账户和批次，逐批插入 `sv_hold_allocation`。每个 `items_allocation` 元素保存 `orderLineNo`、`amountMinor`、`principalMinor`、`bonusMinor`。批次及可用额度仍由原分摊策略决定。对同一批次，按原报价行序将每行累计金额乘以批次实际占用赠金、除以批次实际占用总额后向下取整；相邻累计值之差是本行赠金，行总额减赠金即本金。末行恰好取尽剩余。本批只有新 hold 写入该证据，旧记录维持原样，提交、释放、整退仍读原批次占用。

| 业务样本（本金 / 赠金） | 批次甲 | 批次乙 | 本次退回 | 两批次合计尚可退 |
|---|---:|---:|---:|---:|
| 原核销，行一 60、行二 80 | 80 / 20 | 30 / 10 | — | 110 / 30 |
| 先退行一，原占用全在甲 | 48 / 12 | 0 / 0 | 48 / 12 | 62 / 18 |
| 同一售后重放 | 0 / 0 | 0 / 0 | 回原结果 | 62 / 18 |
| 行二再退，或按整单决定结清余量 | 32 / 8 | 30 / 10 | 62 / 18 | 0 / 0 |

**拟采用的执行契约，待确认。** 交易按原订单行和售后决定冻结本次退额。若同一行只退一部分，先按原批次占用顺序用完各块，在块内按累计退款额摊赠金，使用与新占用同样的累计取整算法；末次取尽该块残额。支付以租户、原核销号、售后号确定一次退款，回执保留原凭证、原行、原批次和本次本金/赠金。相同业务键、相同载荷返回同一回执，载荷冲突拒绝。对同一原核销加锁，依各行各批次未退款余额判定并一次提交凭证、分录、累计额与备查账；两个售后同时申请行一全额最多成功一个。整单结清与逐笔退款共用该累计上限。V712 当前一个原凭证只允许一个 `REFUND`，开放前需区分逐笔售后回执与唯一整退回执，并在一个原核销锁下处理两条路径。直接移除整退唯一键不能保证累计上限。

跨主体清分按原 `sv_clearing_entry` 的付款、收款主体、原币种及原清分号逐块反向。两主体不同则应付冲回本次本金，赠金冲回发行方承担额；同一主体应付仍为零。两次合计正好抵消原清分。历史数据只支持证据可唯一还原的范围；现行历史单继续使用原整退，不按今天的比例推算旧行。

增量验证覆盖两批相交、两行和取整。行一改为 61、行二改为 79 时，甲分别为 49/12、31/8，乙只供行二 30/10。[StoredValueAllocationPolicyTest](../../../../backend/pay/pay-domain/src/test/java/ai/neargo/shop/pay/storedvalue/policy/StoredValueAllocationPolicyTest.java) 的 4 个测试方法均通过，另含最大整数金额及范围限制。

### S2　充值退资

当前 `sv_recharge` 记录充值号、实收本金、促销赠金、线下收款方式与收款凭据。充值退资应以原充值、原到账凭证和原批次为单位，消费售后号和消费整退凭证不能作为退资依据。以下是拟采用的**整批剩余退资**规则，待资金与运营确认。

| 原充 100 / 赠 20 | 原批次现存本金 / 赠金 | 本次处理建议 | 可付还顾客 |
|---|---:|---|---:|
| 全未使用 | 100 / 20 | 冻结可退款 100 和待收回赠金 20，确认外部已退后冲正原批次 | 100 |
| 已消费本金 30、赠金 6 | 70 / 14 | 只退现存本金，收回现存赠金；已消费 6 赠金不向顾客追收 | 70 |
| 同上，另冻结本金 10、赠金 2 | 70 / 14，其中可用 60 / 12 | 整批退资等待原占用完成。若释放可退 70、收回 14；若提交且正好耗用 10/2，则退 60、收回 12 | 冻结期间无外部付款 |

拟定状态为“待冻结 → 已冻结待原路退款 → 退款结果待核对 → 已退待冲账 → 完成”。冻结时锁定原账户和批次，并核实原实收凭据、原收款方与币种；资金退款和余额负债分别留凭证。每次处理绑定同一退资号与原充值号。现金须有实际付款确认和收款人凭据，转账须有银行出款凭据；`MERCHANT_OFFLINE` 需核实实际收款方式。线上支付按原渠道流水查证后退款。外部结果未知时保留冻结并查询原退款号，不另付一笔。确认未出款且停止处理才释放冻结。外部已付而本地冲账失败，只补原批次余额冲正、赠金收回及分录。若原消费在退资完成后才售后退回，按原批次退回并重新核对本次增量的退资资格，不复用已完成的退款回执再次付款。

### S3　线上充值与混合支付

现有储值充值 `StoredValuePort.CollectionMethod` 只有 `CASH`、`TRANSFER`、`MERCHANT_OFFLINE`，账务以商户实际收款确认核定充值。储值服务单要求确认的储值金额等于所有服务行合计，余额不足只可试算，不会生成余款外部支付。其他业务已有外部支付渠道，当前储值单未将这些渠道收款、退款和入账绑定成同一订单。

**支付顺序建议。** 交易先冻结订单行及分支付来源的金额、币种、主体和顾客身份。例如订单 100，储值 60、外部 40，每行须有两种来源的原始分摊。储值先按原订单号占用 60，再按原渠道支付单号收 40。外部明确失败或未收且已撤销时释放 60。渠道结果未知时订单显示「付款核对中」，保留占用并查同一渠道流水。明确已收 40 后按原订单决定提交储值 60；若储值已释放且不可提交，按同一原支付单退 40，确认后关闭。两边均有成功凭证才显示已付款。

**退款与恢复建议。** 交易按售后号冻结对应行的两种原资金来源。在整退例中，外部原路最多退 40，储值最多返原批次 60。若先退一行，其原分摊为储值 18、外部 12，则第二次结清只返 42、28。用同一售后决定分别生成储值回执和原渠道退款单，按「外部确认 → 储值冲回 → 完成」恢复。单腿未知或失败显示「退款处理中」，已成功的一腿只查询，另一腿复用原业务号重试。外部明确失败且已造成金额分歧时进入人工核对，不把整单标记退款完成。商家实收对原外部收退款流水，顾客余额对原批次及储值凭证，交易按两份成功回执核对订单应付。线上充值同样先查原收款成功事实，再用原充值号入账；外部收款成功后入账失败只恢复入账。本节均为设计建议，未开通新的收退款渠道。
