# TDD-按坐标算可见性（多位置第二步）

状态：**草稿（待确认）** · 2026-09-03 · 前置：[TDD-多位置单生效](./TDD-多位置单生效.md) 第一步已上线
关联：[TDD-定位能力受限下的位置模型](./TDD-定位能力受限下的位置模型.md) · ADR-009（经营范围三档）

---

## 1. 一句话

去掉「地址 → 归属社区」那一跳，改由后端**按坐标**算「这家店能不能服务这个位置」。
这样办公楼、任意门牌这类**不属于任何已开通小区**的位置也能用。

---

## 2. 第一步留下的形状

```
生效位置（有坐标）
     │  ← 端上 location store 的 syncCommunityFromActive：查最近的已开通社区
     ▼
communityNo  ──► 商家可见性 / 商品池 / 佣金归属 / 配送范围
```

第一步刻意保留了这一跳，所以后端一行没改。**第二步就是把这一跳删掉**：

```
生效位置（有坐标） ──► 商家可见性 / 商品池 / …
```

端上除了删掉 `syncCommunityFromActive`，**其它一行不用改** —— 这是分两步的全部回报。

---

## 3. 先看一个必须先解决的事实

```sql
select service_scope, count(*) from mch_entity where deleted=0 group by service_scope;
  COMMUNITY  5
  PLATFORM   1

select count(*) from mch_entity_community where deleted=0;
  0
```

**5 家 COMMUNITY 范围的商家，一条社区绑定都没有** —— 也就是说它们对任何
绑定了社区的买家**都不可见**，线上真正能被看到的只有那 1 家 PLATFORM。

这件事对第二步的意义：**现有的 communityNo 轴根本没被填起来**。
所以「换轴」的风险比想象中小 —— 不是把一套跑得好好的东西拆掉，
而是把一套没跑起来的换成能跑的。但也意味着：

> ⚠️ **换轴之后如果还是没人配范围，结果一样是「什么都看不见」。**
> 坐标算得再准，`mch_entity` 上没有可服务的区域描述，算出来就是空集。
> **第二步必须连带解决「商家怎么声明自己服务哪儿」，否则只是换了个空转的方式。**

---

## 4. 设计

### 4.1 商家怎么声明服务范围

三档（ADR-009）保留，但表达从「社区清单」换成**几何**：

| 档 | 现在 | 改后 |
|---|---|---|
| `PLATFORM` | 全平台可见 | 不变 |
| `CITY` | 按市 | 按市（行政区划码，不需要几何） |
| `COMMUNITY` | `mch_entity_community` 清单 | **中心点 + 半径**（自送半径），可选叠加社区清单 |

**为什么用半径而不是画多边形**：商家自己画不出来。
「我送三公里」是他能回答的问题，「请在地图上圈出配送区」不是 ——
b-app 那边已经在用「3 公里内当天送到」这种说法（见店铺页文案）。
多边形留给将来运营代画，不作为第一版的要求。

### 4.2 判定

```
可见(商家, 位置) =
    PLATFORM                                    → true
  | CITY      且 位置.cityCode == 商家.cityCode   → true
  | COMMUNITY 且 distance(位置, 商家) <= 半径      → true
  | COMMUNITY 且 位置落在商家勾选的社区里           → true   ← 存量兼容
```

最后一条是**存量兼容**：已经勾了社区清单的商家不用重配。

### 4.3 性能

商家数量在可预见的将来是**几千**这个量级，不是几十万。
所以第一版**不做空间索引**：按 `cityCode` 粗筛之后在内存里算距离即可。

> 写下这条是为了防止过度设计。真到了需要 R-tree 的量级，
> 那时的瓶颈也不会是这里 —— 而现在引入它，代价是每次改判定逻辑
> 都要同时改索引的维护，且很难验证两边一致。

## 5. 佣金归属：**这是第二步最难的一块**

现在佣金按 `communityNo` 归到自提点的承接方。去掉社区这一跳之后，
「这一单算谁的」失去了依据。

三种可能，**本方案不替它做决定**（需要业务拍板）：

| 方案 | 归给谁 | 问题 |
|---|---|---|
| A. 按履约点 | 货实际落到哪个自提点，就算谁的 | 配送到家的单没有自提点 |
| B. 按下单时快照 | 下单那一刻的归属，写进订单 | 需要在订单上加字段（**现在就该加**） |
| C. 不再有社区佣金 | — | 改变分润模型，影响已签约的承接方 |

> **B 的那一列现在就该加**，理由与 `payer_openid` 相同：
> 现在加成本为零，等有了订单再补，那批订单永远补不回来。

---

## 6. 迁移路径

1. `mch_entity` 加中心点 + 半径两列（可空）
2. 判定加上「半径」那一支，**与社区清单并存**（先或起来，不删旧路）
3. 让商家在 b-app 上填半径（有默认值：3 公里）
4. 观察一段时间：两条路各自命中多少
5. 确认之后再删「地址 → 社区」那一跳

**第 2 步是可逆的**：并存期间任何一条路出问题，去掉另一支即可回到原状。
不要一次性替换 —— 可见性算错的表现是「商家说我的店不见了」，
而那时候已经影响真实生意。
