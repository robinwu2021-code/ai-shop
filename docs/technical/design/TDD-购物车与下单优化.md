## 1. 这是什么（L1）

小程序的购物车与下单页做完整一轮优化。动手前先把两页读了一遍，
**发现的不是「界面不够好看」，是三处会算错账的缺陷**——它们都不报错、不崩，
所以谁也没报过：

| # | 缺陷 | 用户看到的 | 真实后果 |
|---|---|---|---|
| **A** | 失效商品**一件都不显示** | 车里少了一件商品，凭空消失 | `groups` 只遍历 `validItems`，那段「不可售要说出来」的模板**一次都没渲染过**（[cart.ts](../../../c-app/src/stores/cart.ts) `groups`） |
| **B** | 结算按钮的件数**把失效的也算进去** | 「去结算 (3)」，屏幕上只有 2 件、合计也只有 2 件的钱 | `count` 走 `items`、`totalFen` 走 `validItems`，同一条底栏上的两个数不是一回事 |
| **C** | 数量减到 1 再点减号 → **静默删除** | 商品没了，没有任何确认 | `dec()` 传 `qty-1 = 0`，后端与 mock 都把 `qty<=0` 当删除 |
| **D** | **失效标记根本传不到端上** | 已下架的商品在车里**完全正常**，能勾能结算 | 后端 `CartItemVO` 发的是 `invalid: boolean` + `available: int`，端上 `CartItem` 声明的是 `invalidReason?: string` —— **同物异名，字段到端上就没了**。于是 A 那段模板就算修好也永远拿不到数据 |

D 是 A 的根因，也解释了为什么 A 能藏这么久：**两条都坏着，症状互相掩护**。
它与 [TDD-购物车商家可见](./TDD-购物车商家可见.md) §2 是同一形状——「后端发了、契约不接」，
`biz-contract-fields` 那道棘轮的注释里甚至点过它的名（「同物异名而非真丢」），
只是当时判为「改契约名要连页面一起动，不在这次范围里」。这次范围里。

在这四条之上，才是真正的功能缺口：

| # | 缺口 | 为什么算缺口 |
|---|---|---|
| **D** | **没有勾选** | 契约里 `invalidReason` 的注释写着「有值即**不可勾选**结算」——勾选是设计里一直有的，只是没做。没有它就只能「整组一起结」，想少买一件只能先删掉 |
| **E** | **不能删除有效商品** | 唯一的删除入口是 C 那条静默路径。想清空要一件一件点减号点到 0 |
| **F** | 结算要**先弹面板选取货方式** | 多组时先弹一个动作面板，是把内部的「一组一单」直接暴露成一次额外点击 |
| **G** | 下单页禁用了**不说为什么** | `canSubmit` 有五个否决条件，任何一条不满足都只是把按钮变灰。同一个灰按钮五种原因 |
| **H** | 试算**没有竞态保护** | 改地址/换券连点，先发的响应后到就会覆盖后发的——屏幕上是上一次的价 |

## 2. 当前架构分析（L2）

### 2.1 相关模块

| 层 | 路径 | 职责 |
|---|---|---|
| 视图模型 | `c-app/src/stores/cart.ts` | 服务端为准的购物车；`groups` 做「履约 → 商家」二级分组 |
| 页面 | `c-app/src/pages/cart/index.vue` | 购物车 |
| 页面 | `c-app/src/pages/order-confirm/index.vue` | 结算/下单 |
| 契约 | `packages/shared/src/types/trade.ts` | `CartItem` |
| 组件 | `packages/ui/src/components/sh-check.vue` | 勾选框（**已存在，购物车此前没用**） |

### 2.2 后端购物车的现状

`MpTradeController` 有四个端点：`list / add / update / remove`。
`CartItemVO` 发七个业务字段 + `selected` / `invalid` / `available` 三个状态字段，
**端上一个状态字段都没接**（见 §1 缺陷 D 与 §3.6）。

`update(skuNo, qty)` 在 `qty <= 0` 时走逻辑删除 —— 缺陷 C 的另一半就在这里：
后端把「数量减到 0」定义成删除是合理的，问题在端上把减号一路减到 0。

### 2.3 为什么「一次只结一种取货方式」必须留着

`order-confirm` 一页只服务一种履约方式：自提选自提点、快递填地址、上门选时段，
**三种收货信息塞不进同一页**（这是 TDD-购物车商家可见 §3 已经确认过的结构）。

所以勾选**不能跨履约方式**。但缺口 F 说的那个动作面板也不对——
它把这条约束变成了「每次结算多点一次」。

## 3. 方案设计（L3）

### 3.1 勾选的作用域：三选一

| 方案 | 做法 | 结论 |
|---|---|---|
| **A（采用）** | 勾选自由，但**只在一个履约组内成立**：勾了另一组的商品，前一组自动让位 + 一句 toast 说明发生了什么 | ✅ 底栏的合计**永远等于下一单要付的钱**；结算不再多一次点击 |
| B | 允许跨组勾选，结算时再弹面板挑一组 | ❌ 底栏合计 ¥50（自提+快递），进确认页变 ¥30——**同一笔单两个金额**，正是这个仓库反复吃过亏的形状 |
| C | 每组各有一个「去结算」按钮，取消全局底栏 | ❌ 单组（绝大多数情况）也要在卡片里找按钮，合计没有固定位置 |

采用 A。自动让位是有代价的，代价用**一句 toast 说清**（「一次只结一种取货方式，已切换到快递」），
而不是让它静默发生。

### 3.2 默认勾选哪些

进页面时若没有历史勾选，**默认全选「件数最多的那一组」**（并列取先出现的）。

不是「第一组」：加购顺序决定组序，一件很久以前加的快递商品会让默认勾选只剩一件；
也不是「不选」：绝大多数会话里全车就一组，一进来什么都没勾等于每次都要先点全选。

### 3.3 编辑态

删除不做侧滑——小程序上侧滑要引一个手势组件，且与页面滚动争手势。
**用编辑态**：右上角「编辑 / 完成」，编辑态下底栏的主动作从「去结算」换成「删除」，
复用同一批勾选框。这也顺手把缺口 E 补上：批量删。

编辑态下**失效商品也可勾选**——它们正是最该被删掉的那些。

### 3.4 失效商品

单独一张卡，排在有效商品之后，卡头有「清空失效商品」。
行内保留原因文案与单件「移除」（那段模板此前渲染不到，现在真的渲染了）。

**不自动删**这条决定原样保留（原注释：「那是他的东西，删不删由他决定」）。

### 3.5 步进器

| 变更 | 理由 |
|---|---|
| `−` 在 `qty === 1` 时**禁用** | 修缺陷 C：减号的语义是减数量，不是删除 |
| `+` 在 `qty >= available` 时禁用 | 上限走后端已经在发的 `available`。**缺省视为不限**，不能默认 0 —— 默认 0 会让所有没带这个字段的行（mock、老版本后端）一件都加不了 |
| 点数字**直接输入** | 一次买 20 件不用点 19 下。走 `prompt()`（库里已有），不用 `showModal` |
| `−` `＋` 两个字符换成 `sh-icon minus/plus` | 字符当图标跟着系统字形走，`icon-chars` 守卫点名过 C 端这十处 |

### 3.6 契约变更：接住后端一直在发的两个字段

这是缺陷 D 的修法。**改的是端上，不是后端** —— 后端发的形状是对的：

| 后端 `CartItemVO` | 端上此前 | 端上现在 |
|---|---|---|
| `invalid: boolean` | `invalidReason?: string`（**没人发**） | `invalid?: boolean` |
| `available: int` | 无 | `available?: number` |
| `selected: boolean` | 无 | 不接，见 §3.6.1 |

**为什么不反过来让后端发 `invalidReason` 字符串**：那是一句要显示给用户的话，
而这个 app 有三门语言。让后端发中文字符串，等于把文案钉死在服务端。
端上拿 `invalid` / `available` 两个事实自己组装本地化文案（下架 / 售罄），
i18n 守卫也才管得着它。

两个字段都是**可选**的：接旧版本后端、跑 mock 时都可能没有。
`invalid` 缺省 = 有效，`available` 缺省 = 不设上限。

#### 3.6.1 后端的 `selected` 列这次不接

`trd_cart_item` 有 `selected` 列，`CartItemVO` 也在发它，注释写着「结算只取勾选行」——
**但没有任何端点能写它**：`add` 建行时置 true，此后再没有第二处改过。
它是一根只读的死线。

这次的勾选**留在端上**（跟 pinia 持久化走），理由两条：

1. 接它要新增 `/mp/cart/select` 端点 —— 后端 + 契约 + mock + 端点表四处登记，
   那是一件独立的事，不该塞进「优化小程序界面」里顺手做；
2. 勾选是**一次结算之内的意图**，不是购物车的属性。换台设备接着买时，
   用户预期是重新挑，不是「上次在手机上勾的三件还勾着」。

代价说清楚：多设备之间勾选不同步。**已单独开任务跟进**把 `selected` 接通，
届时端上这套换成写后端即可，页面一行不用动（store 的 action 签名不变）。

### 3.7 下单页

| 变更 | 修的是 |
|---|---|
| `submitBlockedReason` 计算属性，按 `canSubmit` 的五个否决条件各给一句话，显示在提交条上方 | 缺口 G |
| `refreshAmount` / `refreshCapability` / `refreshPoints` 各加一个**请求序号**，过期响应直接丢弃 | 缺口 H |
| 试算在途时应付金额压暗 + 「计算中」 | 金额跳变时用户不知道该信哪个数 |
| 服务端试算失败 → 明说「金额以提交时为准」 | 此前静默回落到本地估算，两个数长得一样 |
| `items` 为空（商品已不在车里）→ 空态 + 回购物车 | 此前是一页空白 + 一个灰按钮 |

### 3.8 顺手清掉的两处存量债

两条守卫此前就点名了购物车页，改这一页时一并清掉（都在本次要动的那几行上）：

- `.invalid` 的 `12rpx` 圆角不在五档上（`typography` 守卫）
- `.invalid__act` 用 `var(--sh-primary)` 当文字色（`design-tokens` 守卫，对比度不足）

## 4.1 顺带查出来的一件事：这条契约守卫已经空转了一段时间

缺陷 D（后端发 `invalid`、端上声明 `invalidReason`）本该被
`packages/shared/tests/biz-contract-fields.test.ts` 的棘轮拦住 —— 它就是干这个的。
动手改完去拧那个基线，发现**拧不动：把基线设成 0 它照样绿**。

根因是一处判据失效：

```
endpoints() 的键是 "GET /mp/cart"（带方法，为了区分同路径的 GET/POST）
而循环里写的是   if (!url.startsWith(prefix)) continue;   // prefix = "/mp"
```

`"GET /mp/cart".startsWith("/mp")` 永远是 false —— **一条端点都没进循环**。
两条断言（★★★ 必填字段、★★ 棘轮）因此双双空转，而空转的表现是**全绿**。
注释里还写着「b-app 15 / c-app 29」，那是它还能扫的时候量的数。

修法三件事：

| # | 做什么 | 为什么 |
|---|---|---|
| 1 | 加 `pathOf()`，判据只拿路径段比 | 修根因 |
| 2 | 两条循环各加一个 `scanned` 计数断言（`> 10`） | **判据自己也要有人守**：少扫=全绿这件事不能靠人再撞一次 |
| 3 | 基线按实测重设：b-app 31 / c-app 25 | 旧值是空转前量的。**不是放宽** —— 空转期间新欠的账现在全都在数里了，从今天起只许降 |

修完当场验了一次消融：把 `CartItem.available` 撤掉，c-app 从 25 变 26，闸门变红。

`CartItem` 的 `invalid` / `available` 两条已经从名单里消失；
剩下的 `CartItem.selected` 是 §3.6.1 那个明写的决定。

## 5. 风险与注意事项

- **勾选持久化会存到旧数据**：`selected` 里可能留着已经不在车里的 `skuNo`。
  每次 `load()` 后剪枝，且剪枝要在「默认全选」之前跑，否则脏 id 会顶掉默认。
- **`count` 的语义不动**：tabBar 角标与商品页角标都在用它（「车里有几件」），
  改成勾选数会让角标在勾选时跳动。结算按钮另用 `selectedCount`。
- **`available` 是可选字段**：mock 与旧后端都可能不发，
  每一处都要按「空 = 不限」处理。默认成 0 的后果是**整车一件都加不了**，
  而且只在没带这个字段的环境里才出现。
- **`invalidReason` → `invalid` 要连守卫一起改**：`c-app/tests/active-address.test.ts`
  有三条断言钉着旧字段名。守卫钉的是一个**从来没有数据的字段**，
  改它是把断言接回真实字段，不是放宽（三条断言的强度一条不减，见该文件注释）。
