## 一、先读这一条：哪些现在测不了（L1）

**不区分「没测」和「测不了」是这类清单最常见的失效方式**——跑完一轮全是黄色，
没人知道该去修什么。所以先把测不了的挑出来，它们在下面用 🚫 标注，**不计入通过率**。

| 链路 | 状态 | 为什么 | 解除条件 |
|---|---|---|---|
| 支付 | 🚫 | `OrderServiceImpl` 返回 `stub_<orderNo>`，唤不起收银台 | 微信认证 + 商户号 + 接 JSAPI 下单 |
| 手机号 OTP | ⚠️ | 短信走桩，验证码不真发 | 配阿里云短信，或本地开 `shop.auth.otp.fixed` |
| 订阅消息实收 | ⚠️ | 通道走桩，`msg_subscribe` 额度记账仍可验 | mp 后台报备两个模板号 |
| 图片上传 | ⚠️ | 落本地磁盘，多实例读不到 | 接对象存储 |

**其余全部可测**——包括登录拿真 openid、下单到「待支付」为止的整条链路、
履约、售后、评价、发票、消息。

### 2.1 环境

| 项 | 值 |
|---|---|
| 后端 | `10.221.117.8:8091`（`api` profile，`.env.local` 带真 appid/secret） |

| 前置 | 手机与后端同一 WiFi；体验版右上角 `…` → **打开调试**（否则域名校验拦掉 http） |

### 2.2 三种账号状态

大量缺陷只在状态切换处出现，所以每轮至少覆盖这三种：

| 代号 | 状态 | 为什么单列 |
|---|---|---|
| **A0** | 未登录 | 未登录不该拉未读数、不该显示「已全部阅读」（真出过） |
| **A1** | 已登录·未绑社区 | 没绑社区就没有「能买什么」的答案 |
| **A2** | 已登录·已绑社区·有历史订单 | 复购路径、常买、再来一单都依赖它 |

### 2.3 优先级

| 级 | 含义 |
|---|---|
| **P0** | 断了就没法用（登录、绑社区、下单、取货码） |
| **P1** | 主路径受损但可绕（搜索、券、评价） |
| **P2** | 体验/边界 |

## 四、一条端到端冒烟（每次发版必跑）

上面是逐点验，这条是**串起来验**——分开都对、串起来断掉的情况比想象中多。

```
微信登录（拿真 openid）
  → 绑社区 + 选自提点
  → 首页看到本社区的货
  → 加购两家店的商品
  → 结算 → 拆成 2 笔子订单、共享 payGroupNo
  → 🚫 支付（此处中断，用后端把状态推到 PAID）
  → 订单列表「待提」看到它
  → B 端标到货 → C 端订单详情首屏看到取货码
  → 核销 → COMPLETED
  → 写评价（三维度）
  → 申请仅退款 → 积分回收 + 退还同时发生
```

**中断点只有一个**（支付），其余每一步都能真跑。支付那步用后端直接推状态，
**但要在报告里写明这一步是人工推的**——把它记成「通过」，下次接了真支付时没人知道这里从未验过。

## 五、边界（L4）

- **本文只覆盖 C 端**。B 端核销、平台端审核在各自的用例文档里；上面几条跨端用例
  （核销、报价、标到货）需要 B 端配合，跑之前先确认 B 端环境也在
- **不含性能与并发**：库存超卖、同一取货码并发核销这类要单独设计，人工点不出来
- **未定口径的不写预期**：跨商家优惠摊分、售后责任归属（M4）还没定，
  写了预期就是把一个未决问题伪装成已决
- **数字一律不写在这里**：极速退阈值、截单时间、未支付关单时长都引用
  [规则表](../../requirements/需求矩阵-三端.md#七之二交易规则常量唯一事实源)——
  复述一次就会有一处忘了改

#### ❌ TC-C-CT-02-1：购物车按**履约方式**分组，不是按商家

功能清单 C-CT-02 写的是「购物车按店分组展示，**因为结算时会拆单**」。
实测两家店的商品挤在同一张卡里，卡上的标签是「自提点自提」，**店名一个字都没有**。

代码证实不是渲染问题：`cart/index.vue:51` 是 `v-for="g in cart.groups" :key="g.fulfillment"`，
`cart.groups` 本身就按 `fulfillment` 聚的，全页没有任何按商家的分组。

**为什么这条不是「小差异」**：确认订单页同样只列一份清单，
于是用户从头到尾看到的是「一单」，提交后拿到的是**两笔子订单**。
C-CT-02 的理由那句话（「因为结算时会拆单」）正是在防这个，而防线没建起来。

> 修法有两种，取舍不同：把购物车改成按商家分组（对齐清单），
> 或者保留履约分组但在确认页披露拆单（对齐 C-OD-06 的思路）。**没定，等拍板。**

#### ⚠️ 命名漂移：`payGroupNo` 三处三个名字

清单 C-CT-04 说「N 笔子订单共享 `payGroupNo`」。**同一件事三处三个名字**：

| 层 | 叫什么 |
|---|---|
| 端上契约 | `Order.payGroupNo` |
| 后端 VO | `OrderVO.payOrderNo` |
| 库 | `ord_order.order_no` |

行为是对的，按契约名去后端或库里找会找不到。已在类型定义处加了对照注释，

#### ⚠️ TC-C-OD-03-1：只有 5 个 tab，且「待取货」名不副实

清单 C-OD-03 写的是六个：**全部 / 待付 / 待提 / 待收 / 待评 / 售后**。
实际是五个（`orders/index.vue:20`）：

```
all → toPay(WAIT_PAY) → toPick(PAID/ARRIVED/SHIPPED) → done(COMPLETED) → afterSale
```

两处对不上，性质不同：

**① 「待收」被并进了「待取货」。** `toPick` 的状态集里含 `SHIPPED`，而它的文案是
「待取货」——**买快递的用户会在「待取货」下看到自己的单**。他并不需要去取，
是在等送到。合并本身可以讨论，但标签得说实话。

**② 「待评」整个没有。** `done` 只按 `COMPLETED` 筛，评没评过混在一起。
影响的是评价率：C-RV-01 说评价要「总分 + 三维度」，而用户找不到「哪些还没评」，
积分激励也就无从触发。

> **① 已修（2026-08-17）**，且修法不是「补两个 tab」这么简单：
> 查下来后端早有 `OrderStatusView` 把 `FULFILLING × 履约方式` 算成
> `ARRIVED`（待取货）/ `SHIPPED`（待收货），**b-app 一直用着，只有 c-app 没接**。
> 现在 c-app 改为按页签把展示状态传给后端筛，7 个 tab。
> 顺带修掉一个更严重的：端上要 100 条、后端只给 50，**老用户的订单会静默缺失** ——
> 现在 `PAGE_SIZE` 与后端上限对齐，超出部分明说「还有 N 笔更早的订单未显示」。
> 详见[订单状态与履约-定义整理](../reference/订单状态与履约-定义整理.md)。
>
> **② 待评价 tab 仍未决**：能力已具备（`Order.reviewed`），是纯产品决定。

### 第三轮 · 2026-08-17 · 契约漏接翻出来的两条真缺陷

反方向棘轮（`biz-contract-fields` 的「后端发了、契约没接」）翻出 32 个字段，
逐条看的时候撞到两个**用户能看见**的：

| 缺陷 | 后果 | 状态 |
|---|---|---|
| `StoreHome.closed` 没接 | 扫码进一家**已停业的店**，看起来与正常营业毫无区别 —— 加购、下单一路走到底，最后撞一个说不清的错误 | ✅ 已修 |
| 门店页没接 `@add` | 「全部商品」区的 ＋ **点了完全没反应**：不是报错，是什么都不发生 | ✅ 已修 |

第二条与契约无关，是顺着第一条查加购链路时撞见的：
`biz-goods-card` 把 `add` **emit** 出来，而门店页没有接。
首页、分类、商家页、搜索页**四处都接了，只有门店页漏了** ——
而门店页恰恰是[主获客路径](../../requirements/C端功能清单.md)（C-ST-01，扫码直达）。

#### 实测（对照法）

```
店停业（mch_store.status=READONLY）→ 横幅「这家店已停业，暂时不能下单」；点 ＋ 零请求
店营业（status=ACTIVE）           → 横幅消失；点同一个 ＋ → POST /mp/cart/add → 200
```

**用对照而不是只看一次**：只测停业那次的话，「零请求」既可能是守卫拦住了，
也可能是那个按钮本来就是死的 —— 而它当时确实是死的。
