# 第一部分：卡券域

## 1. 现状盘点

### 1.1 「卡券」其实是三个不同的东西

这是本域最容易搞错的一点。现在混在一个词里的有三种：

| | 是什么 | 谁出钱 | 库里现状 |
|---|---|---|---|
| **优惠券** Coupon | 满减/折扣，**下单时抵扣** | 平台或商家（`funder`） | ✅ `mkt_coupon` + `mkt_user_coupon` |
| **卡** Card（储值卡/次卡） | **商品本身**，用户花钱买，之后凭卡消费 | 用户自己 | ❌ 无表 |
| **会员卡** MemberCard | 订阅制权益包（月费） | 用户自己 | ❌ 无表（P-7.4 标注二期） |

优惠券是**促销工具**，卡是**商品**——用户买它、它有余额、能核销、能退。
两者在会计上完全不同：券是费用，卡是**预收款（负债）**。

> 待办 [T-9](../api/待办-契约对齐.md) 记的「`UserCard` ↔ `mkt_user_coupon` 映射不成立」，
> 根因就在这里：把商品映射到了促销工具的表上。

### 1.2 已经实现到哪一步

| 环节 | C 端 | B 端 | 平台端 | 库 |
|---|---|---|---|---|
| 券：领取/列表/下单抵扣 | ✅ | — | ✅ 发券 | ✅ |
| 卡：作为商品售卖 | ✅ 商品详情有 `CardSpec` | ✅ 可录入 | — | ⚠️ 属性挤在 `prd_goods` |
| 卡：购买后进卡包 | ✅ `myCards` | — | — | ❌ **无表** |
| **卡：核销/消费** | ❌ | ❌ | ❌ | ❌ |
| 会员卡 | — | — | 🔜 二期 | ❌ |

**最大的洞是核销**：mock 里买了卡就进卡包（`issueCard`），然后**没有任何地方能用掉它**。
`balanceMinor` 与 `timesLeft` 永远不变——储值卡余额只增不减，次卡次数永远用不完。

一期把卡卖出去却没法用，用户第一次想核销时才发现，那时钱已经收了。

## 2. 需求

每条标注**防住什么**——防不住任何东西的需求不该进一期。

### 2.1 卡的售卖与发放（K1）

| # | 需求 | 防住什么 |
|---|------|---------|
| K1.1 | 卡是 `CategoryType=CARD` 的商品，属性含面值/次数/有效期，**支付成功即发放**，不经备货 | 卡没有物流，走备货流程会卡在「待发货」 |
| K1.2 | 一次买 N 张就发 N 张**独立的卡**，各自有卡号与余额 | 合成一张会让「送朋友一张」做不到，且余额混在一起没法分别过期 |
| K1.3 | 发放幂等：同一订单行只发一次 | 支付回调重试 → 重复发卡 → 平台白送钱 |
| K1.4 | 卡的面值是**预收款**，不是收入；核销时才转收入 | 会计口径错误；且未核销余额是对用户的负债，要能随时算出总额 |

### 2.2 卡的核销与消费（K2）**← 当前完全缺失**

| # | 需求 | 防住什么 |
|---|------|---------|
| K2.1 | 储值卡按**金额**扣减，次卡按**次数**扣减，两者不可互换 | 混用会让「10 次卡」被当成「10 元卡」 |
| K2.2 | 核销由**商家**发起（出示卡号/二维码），不是用户自己点 | 用户自助扣减 = 没消费也能把卡刷空 |
| K2.3 | 核销必须**原子扣减**，条件写在 WHERE 里（余额≥本次金额 / 次数≥1） | 并发下先查后扣必然超额核销 |
| K2.4 | 每次核销落一条流水，含核销前后余额 | 只存余额的话，用户质疑「我的钱哪去了」时答不上来 |
| K2.5 | 卡**只能在发卡商家**核销（跨店除非显式配置） | 甲店的储值卡在乙店刷，甲收了钱乙出了货，分账无解 |
| K2.6 | 过期卡不可核销；过期余额的处理方式**需产品拍板**（作废/退款/延期） | 直接作废可能违反预付卡相关规定 |

### 2.3 卡的退款（K3）

| # | 需求 | 防住什么 |
|---|------|---------|
| K3.1 | 未核销过的卡可整卡退；已部分核销的退**剩余价值**，需产品确认是否允许 | 用了 9 次的 10 次卡全额退 = 白嫖 |
| K3.2 | 退卡要先冻结卡，再走退款；退款成功才作废 | 先作废后退款失败 → 用户卡没了钱也没退 |

### 2.4 优惠券的补齐（K4）

券的主链路已有，缺的是：

| # | 需求 | 现状 |
|---|------|------|
| K4.1 | 商家券要落在 `mkt_campaign`（V16 已建）而不是 `mkt_coupon` | 两张表的关系**未定义**，需明确：平台券走 `mkt_coupon`、商家券走 `mkt_campaign` |
| K4.2 | 券的适用范围要可校验（限商品/限类目/限店），不只是 `scope_desc` 文案 | 现在只有展示文案，**服务端无法校验** |

### 2.5 会员卡（K5）—— 建议维持二期

平台端功能清单已标 🔜 二期。本文不设计，但**要在卡的表结构上留位**：
会员卡与储值卡的差别是「按周期续费 + 权益包」，若一期把卡表做成只支持余额/次数，
二期会被迫另建一套。留位方式见 §3.1 的 `card_kind`。

## 3. 技术方案（卡券）

### 3.1 表结构

**四张新表**。核心判断：**卡的模板与卡的实例必须分开**——
模板是商品配置（改了影响后续售卖），实例是用户手里的资产（**改了就是动用户的钱**）。

```
mkt_card_template   卡模板（挂在 CARD 类商品上）
mkt_user_card       用户持有的卡（实例）        ← 卡包的真源
mkt_card_ledger     核销/退卡流水（append-only）← 余额的真源
mkt_card_redeem     核销单（商家发起的一次核销动作）
```

#### `mkt_card_template`

| 列 | 类型 | 说明 |
|---|---|---|
| `template_no` | VARCHAR(64) | 模板号 |
| `goods_no` | VARCHAR(64) | 所属商品，唯一 |
| `merchant_no` | VARCHAR(64) | 发卡商家——**核销作用域的判据**（K2.5） |
| `card_kind` | VARCHAR(16) | `STORED_VALUE` 储值 / `TIMES` 次卡 / `MEMBER` 会员卡（二期留位，K5） |
| `face_value_minor` | BIGINT | 储值卡面值；次卡为 0 |
| `times_total` | INT | 次卡总次数；储值卡为 0 |
| `valid_days` | INT | 有效期天数，从发放日起算 |
| `cross_store` | TINYINT | 是否允许跨店核销，默认 0（K2.5） |

> 为什么不直接用 `prd_goods` 上的 JSON 属性：核销要按 `merchant_no` 和 `card_kind` 做条件查询与校验，
> JSON 列走不了索引，且校验逻辑会散在应用层。

#### `mkt_user_card`

| 列 | 说明 |
|---|---|
| `card_no` | 卡号，**用户出示的就是它**，唯一 |
| `template_no` / `goods_no` / `merchant_no` | 冗余下来避免核销时多一次 join（核销在收银台，要快） |
| `user_no` | 持卡人 |
| `order_no` / `sub_order_no` / `order_item_id` | 来源订单；**`(sub_order_no, order_item_id, seq)` 唯一 → 发放幂等（K1.3）** |
| `balance_minor` | 储值卡剩余金额（派生，真源是流水） |
| `times_left` | 次卡剩余次数（派生） |
| `status` | `ACTIVE` / `USED_UP` / `EXPIRED` / `FROZEN`（退款中）/ `REFUNDED` |
| `expire_at` | 过期时间 |
| `currency` | 购卡时锁定 |

#### `mkt_card_ledger`（append-only）

余额的**真源**。与积分域同一条原则：账户是派生的，流水才是真相。

| 列 | 说明 |
|---|---|
| `card_no` | |
| `change_type` | `ISSUE` 发放 / `REDEEM` 核销 / `REFUND` 退卡 / `EXPIRE` 过期作废 |
| `amount_minor` | 金额变动（储值卡），正增负减 |
| `times` | 次数变动（次卡），正增负减 |
| `balance_after_minor` / `times_after` | **变动后余额** —— 只存变动量的话，一条错后面全错 |
| `redeem_no` | 关联核销单 |

#### `mkt_card_redeem`

一次核销动作。与流水分开：核销是**商家发起的业务动作**（可能失败、可能被撤销），
流水是**已经发生的事实**。合成一张表就无法表达「发起了但没成功」。

| 列 | 说明 |
|---|---|
| `redeem_no` | 核销单号 |
| `card_no` / `merchant_no` / `operator_no` | 谁的卡、在哪核销、谁操作的 |
| `amount_minor` / `times` | 本次核销多少 |
| `request_no` | **幂等号**，唯一键 —— 收银台网络抖动重复提交只算一次（K2.3） |
| `result` | `SUCCESS` / `FAILED`，失败原因存 `message` |

### 3.2 核销的并发正确性（K2.3）

条件写在 `WHERE` 里，靠影响行数判断成败——与券领取、库存锁定同一个写法：

```sql
-- 储值卡
UPDATE mkt_user_card
   SET balance_minor = balance_minor - #{amountMinor}, version = version + 1
 WHERE card_no = #{cardNo} AND deleted = 0 AND status = 'ACTIVE'
   AND expire_at > #{now} AND balance_minor >= #{amountMinor}
```

返回 0 行就是「余额不足 / 已过期 / 已冻结」，**不要先查后扣**：
两个收银台同时刷同一张卡，先查后扣必然扣穿。

### 3.3 接口设计

**C 端**（新增 1 条，其余已有）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/mp/card/mine` | 我的卡包 ✅ 已有 |
| GET | `/mp/card/{cardNo}` | 卡详情 + 核销流水 **新增** |

**B 端**（全部新增）—— 核销台

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/biz/card/{cardNo}` | 查卡（出示卡号后先看余额与归属） |
| POST | `/biz/card/{cardNo}/redeem` | 核销，body `{amountMinor?, times?, requestNo}` |
| GET | `/biz/card/redeems` | 本店核销记录 |

**平台端**：卡模板管理 + 预收款报表（未核销余额总额 = 平台负债）。

### 3.4 与结算的关系（**需拍板**）

储值卡的钱在**购卡时**就收了，但商家在**核销时**才提供服务。分账时点有两个选择：

- (a) 购卡时即分账给商家 —— 商家先拿钱，用户没核销就退卡时要从商家账上追回
- (b) 核销时才分账 —— 平台代持预收款，**但这可能构成资金池，需合规确认**

⚠️ 这条我不建议默认实现任何一种。它同时牵涉分账时限（微信分账有时间窗，见 ADR-002）
与预付卡合规，**必须与支付服务商和法务确认后再定**。

# 第二部分：工单域

## 4. 现状盘点

### 4.1 断链：工单池收不到单

| 端 | 现状 |
|---|---|
| 平台端 | ✅ 工单池、分派、代客留痕、状态机（`TICKET_TRANSITIONS`）全都有 |
| 库 | ✅ `msg_ticket` 表存在 |
| **C 端** | ❌ **没有任何提工单的接口**（`contract.ts` 里搜不到 ticket/help/feedback） |
| B 端 | ❌ 无 |

**工单只能由客服在平台端手工创建**——用户遇到问题没有任何自助入口。
这与「评价申诉裁决台建好了但没有申诉入口」是同一类问题，上一轮已经修过一次。

### 4.2 现有表能力不足

`msg_ticket` 只有 `subject/content/reply/replied_at/replied_by` ——
**单轮问答模型**：用户问一次、客服答一次，结束。

但契约里的 `Ticket` 有 `assignee`（分派）、`proxyActions[]`（代客操作留痕）、
四态状态机（OPEN→ASSIGNED→RESOLVED→CLOSED）——**表撑不起契约**。
真实客服场景也需要多轮往返。

## 5. 需求

### 5.1 提单入口（G1）

| # | 需求 | 防住什么 |
|---|------|---------|
| G1.1 | C 端可提工单，**可关联订单**（从订单详情进入时自动带上 `orderNo`） | 不关联订单的话客服要先问「你哪个单」，多一轮 |
| G1.2 | 提单要选**问题分类**（订单/支付/售后/账号/其他） | 无分类则无法分派也无法统计「大家在问什么」 |
| G1.3 | 可上传截图 | 支付类问题说不清，截图最快 |
| G1.4 | 同一订单未关闭的工单**不允许重复提** | 用户连点产生一堆重复单，客服重复处理 |
| G1.5 | B 端商家同样可提单（对平台的问题：结算、规则、申诉） | 商家现在只能靠线下找运营 |

### 5.2 处理流程（G2）

| # | 需求 | 防住什么 |
|---|------|---------|
| G2.1 | 状态机 OPEN→ASSIGNED→RESOLVED→CLOSED，**非法迁移拒绝** | 未分派直接标已解决，无人负责 |
| G2.2 | 分派到具体员工；**只能分派给数据域覆盖该工单的员工** | 社区运营看到别片区的单（P-1.1.3 数据域） |
| G2.3 | **多轮消息**，用户与客服都能追加 | 单轮问答解决不了真实问题 |
| G2.4 | `RESOLVED` 后用户可**重开**（回到 ASSIGNED） | 客服草草结单，用户无处申诉 |
| G2.5 | 关闭必须写结论 | 与驳回必须写理由同一条规矩 |

### 5.3 代客操作留痕（G3）

| # | 需求 | 防住什么 |
|---|------|---------|
| G3.1 | 客服代客操作（改地址、取消单、补发券）**必须落痕**：谁、对哪个对象、做了什么、因为哪个工单 | 客服权限最大且直接碰用户资产，无痕等于无法追责 |
| G3.2 | 留痕**不可删不可改**（append-only） | 可删的审计等于没有审计 |
| G3.3 | 补偿类操作（发券/退款）要有**额度上限**，超限需上级审批 | 单个客服可以无限发券 |

> G3.3 的额度上限值**需产品拍板**，本文不设默认值。

### 5.4 帮助中心（G4）

`FaqEntry` 契约已有，库里无表。它是**工单的减压阀**：
高频问题沉淀成 FAQ，提单前先展示相关条目，能挡掉相当一部分工单。

## 6. 技术方案（工单）

### 6.1 表结构

`msg_ticket` **保留但扩列**（已有数据结构基本可用），新增两张：

```
msg_ticket          工单主表（扩列）
msg_ticket_message  工单往返消息（新建）  ← 支撑多轮
msg_proxy_action    代客操作留痕（新建）  ← append-only
msg_faq             帮助中心条目（新建）
```

#### `msg_ticket` 扩列

| 新增列 | 说明 |
|---|---|
| `category` | `ORDER`/`PAY`/`AFTER_SALE`/`ACCOUNT`/`OTHER`（G1.2） |
| `source` | `C_USER` / `B_MERCHANT`——提单方是用户还是商家（G1.5） |
| `submitter_no` | 提单人业务键，按 source 落在 `user_no` 或 `merchant_no` |
| `assignee_no` | 分派到的员工（G2.2） |
| `assigned_at` | |
| `community_no` / `merchant_no` | **数据域裁剪键**（G2.2）——不冗余下来，分派校验就要跨域查订单 |
| `images` | JSON（G1.3） |
| `conclusion` | 关闭结论，`CLOSED` 时必填（G2.5） |
| `reopen_count` | 重开次数（G2.4）；异常高说明客服在敷衍 |

保留 `reply`/`replied_at`/`replied_by`：老数据要能读。新工单的往返走 `msg_ticket_message`。

> **重复提单**（G1.4）：唯一索引 `uk_open_order (order_no, status)` 做不到

> 所以放在应用层校验 + 一个普通索引 `idx_order_status (order_no, status)` 支撑查询。

#### `msg_proxy_action`（append-only，无 `deleted` 列）

### 6.2 接口设计

**C 端**（全部新增）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/mp/ticket` | 我的工单列表 |
| POST | `/mp/ticket` | 提单，body `{category, title, content, images?, orderNo?}` |
| GET | `/mp/ticket/{ticketNo}` | 详情 + 往返消息 |
| POST | `/mp/ticket/{ticketNo}/reply` | 追加消息（G2.3） |
| POST | `/mp/ticket/{ticketNo}/reopen` | 重开（G2.4） |
| GET | `/mp/faq` | 帮助中心（G4） |

**B 端**：同构的 `/biz/ticket/**`（G1.5）。

**平台端**：`listTickets` / `assignTicket` / `closeTicket` / `addProxyAction` 与 FAQ 的三条**都已有**。
缺两条：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/ops/tickets/{no}/reply` | 客服回复（G2.3）—— 现在只能分派和关闭，**没法回话** |
| POST | `/ops/tickets/{no}/resolve` | 标记已解决 —— 状态机里有 `RESOLVED`，但没有动作能到达它 |

`RESOLVED` 是个**到不了的状态**：`TICKET_TRANSITIONS` 声明 `ASSIGNED → RESOLVED`，
而契约里只有 `close`。这类「状态机里有、接口里没有」的洞，和评价申诉裁决台收不到单是同一类。

### 6.3 与售后的边界（**重要**）

售后（`ord_after_sale`）与工单（`msg_ticket`）**不是一回事**，不要合并：

| | 售后单 | 工单 |
|---|---|---|
| 处理方 | **商家**先处理，争议才上升平台 | **平台客服** |
| 有无资金 | 有（退款金额、责任划分） | 无 |
| 状态机 | 7 态，含 `PLATFORM_INTERVENE` | 4 态 |

关系是：售后单上升平台后**可以派生一个工单**给客服跟进，但两者各自独立流转。
`msg_ticket.category=AFTER_SALE` 时可关联 `after_sale_no`（建议加这一列）。

## 8. 需要拍板的问题

写在这里而不是替你决定，因为这几条选错的代价是**返工 + 合规风险**：

1. **储值卡的分账时点**（§3.4）——购卡时 or 核销时？后者可能构成资金池，需合规确认。
2. **过期卡余额如何处理**（K2.6）——作废 / 可退 / 可延期？预付卡有相关规定。
3. **部分核销后是否允许退卡**（K3.1）——允许的话按什么价退。
4. **客服补偿额度上限**（G3.3）——单笔多少、日累计多少、超限走谁审批。
5. **卡是否跨店通用**（K2.5）——默认不跨店；若要跨店，分账规则要一并定。
6. **商家券落在哪张表**（K4.1）——`mkt_coupon.funder=MERCHANT` 还是 `mkt_campaign`？
   两处都能表达，**现在是重复的**，必须选一个。
