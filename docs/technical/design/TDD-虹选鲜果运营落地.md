## 1 展示 · 位置四级缓存 + 写回基础信息

> **「防止频发调用高德」那一层早就做好了**（`geo_place`）。这里要补的是它<b>前面</b>的内存层、
> <b>后面</b>的用户档案写回，和端上的跨冷启动持久化。先盘清四层，再说补哪三件。

### 现状盘点（逐层查过，不是推测）

| 层 | 载体 | 现状 |
|---|---|---|
| **L0 端上内存** | `c-app/src/stores/location.ts` 的 `here` + `HERE_TTL=5min` | ✅ `ensureHere()` 全端唯一入口，时刻 TTL（不是「拉过没有」，App 进程长这点做对了）。❌ **不跨冷启动**——杀进程重进顶栏先空着、重新定位、弹授权框 |
| **L1 服务端 DB** | `geo_place`（geohash 精度 8 ≈ 建筑级，线上 39 行） | ✅ **已完整实现**。`PlaceResolver` 做 cache-aside：命中不超期→**不打高德**；超期→先用旧的 + 后台单线程回刷；从没见过的格子→同步打一次高德→落库；高德不可用→用陈旧并标 `stale`；都没有→退区县、不编地名。`hit_count` 攒够升聚落。有 `PlaceResolveChainTest` |
| **L1.5 服务端内存** | — | ❌ **无**。每次 resolve 都读一跳 `geo_place`（DB）。同一栋楼多人、同一格子反复解析，本可连 DB 都不读 |
| **L2 用户基础信息表** | `usr_account`（有 `community_no` 绑定聚落、`active_address_id`、`pickup_no`） | ⚠️ 存的是用户**主动绑定**的聚落（强信号）。`resolveLocation` 只返回 `LocationVO`，**实时反解的位置不写回**任何用户档案 |

> 另：`usr_address` 存收货地址的精确坐标（lat_e6/lng_e6/region/house_no），那是用户**主动录**的，与这里的被动定位是两条线，不混。

### 要补的三件（按风险从低到高）

**① L1.5 服务端内存热缓存 —— 挡住 DB 读洪峰（已实现 2026-10-04）**
- `PlaceResolver` 读 `geo_place` 前加一个**进程级 LRU**：`geohash → Place`。
- 容量有界（如 1 万格子）、**TTL 短（分钟级）**。因为 `geo_place` 自己有 30 天过期回刷，
  这层只省重复 DB 读、**不省高德**（那是 L1 的职责）；TTL 短是为了不盖住 L1 的后台回刷结果。
- **只缓存命中且新鲜的**（`SOURCE_MAP`/`PLACE_DB` 且非 stale）；`stale`/不可用的不进内存，
  让它们继续走 L1 的回刷。
- 不上 Redis：本工程没有，热点集中在少数格子，单机 LRU 够；多实例各存一份也无妨（内容一致）。

  **已实现**：`PlaceResolver` 加 `geohash→Place` 的 LRU（`shop.geo.hot-max:10000` / `hot-ttl-ms:300000`，走 @Value 默认不进 yml，同 place-precision）。
  内存命中跳过 `selectOne`；`hit_count` 仍记（后台原子自增 `hit_count+1`，单行写放后台线程不占首页那一跳）。
  map 结果入缓存时 source 归一成 `PLACE_DB`（走内存=没打地图=用我们自己的数据），本次返回仍是 `MAP`。
  只缓存**新鲜**命中，stale 不进。
  测试：`PlaceResolverHotCacheTest`（①第二次不读库 ②stale 不缓存，各带消融）；
  `PlaceResolveChainTest` 补 `clearHotCache()` 做跨用例隔离（同 `breaker.reset()`）。

**② L0 端上内存持久化 —— 冷启动秒显（已实现 2026-10-04）**
- `here`（place/region/粗坐标/at）落本地（走 `@shared/ports/persist`）。
- 冷启动：先读持久层 → 顶栏**立即**显示上次地名（标「可能不是最新」）→ 后台 `ensureHere` 按 TTL 刷 → 变了再更新。
  首屏不白、授权框只在首次或过期时弹。
- 「重新定位」(`force`) 清三处：内存 + 持久层 + 下游（既有 force 扩到持久层）。
- 隐私：只存地名/区县/粗坐标，与现有内存层同口径；私密模式/清缓存丢了就重新定位，不崩（try/catch 包读写）。

  **已实现**：location store 加 `persist: { key: STORAGE.location, pick: ["here","coarseRegion"] }`，
  走既有 `uniPersistStorage`（uni.getStorageSync，三端一致）。冷启动恢复 `here` → 顶栏立即读到上次地名；
  首页仍调 `ensureHere()`，持久的 `at` 过 TTL 就重定位、届时更新。
  **偏差**：持久恢复的地名暂不额外标「可能不是最新」（刷新秒级到来），stale 标记留到需要时再加。

**③ L2 写回用户基础信息表 —— 已知用户免重解析 + 运营看分布（动库表，最重）**
- resolve 命中后，**异步 + 节流**把「最后已知位置」写回 `usr_account`：
  新增 `last_lat_e6` / `last_lng_e6` / `last_region_code` / `last_place` / `last_located_at`。
  （加列三处：迁移 + 实体 + `schema-test.sql`，见 [[migration-needs-entity-field]]）
- **节流**：移动超阈值（如 500m）**或**距上次写入超 N 分钟才写 —— 否则每次定位一次写，频繁且无意义。
- **与 `community_no` 不互相覆盖**：`community_no` 是用户**主动选**的聚落（强），`last_*` 是**被动探**得的（弱）。
  下单、取货仍以 `community_no` 为准（既有口径不动）；`last_*` 只用于：
  - 端上持久层没了 / 换设备时的**兜底**（服务端还记得上次在哪）；
  - 运营看**用户地理分布**；
  - 新用户还没绑聚落时**预选**最近的开放聚落（只是建议，不自动绑）。
- **精度：精确到小区级**（2026-10-04 定）。`last_lat_e6`/`last_lng_e6` 存**精确坐标**（不降精度），
  并解析出所在小区/聚落一并落：新增 `last_community_no`（落进开放聚落时）与 `last_place`（小区/楼盘名，`geo_place` 的 AOI 级）。
  —— 这是用户明确要的精度，用于首页直接定位到小区（见下）、运营看小区级分布。
- 隐私：精确位置是敏感数据，不降精度就要靠访问控制兜底 ——
  运营端查看 `last_*` 要**权限位 + 留痕**（谁查了谁的位置），对外接口/导出一律不带它；
  写回要有**配置开关**可整体关（出问题能一键停）。
- 异步：复用 `PlaceResolver` 已有的后台线程池模式（单线程 + 有界队列 + 满了丢），不开全局 `@EnableAsync`。

**④ 首页进入即定位到小区并作为当前位置（展示口径，L0/L1/L2 的消费端）**
- 现状：`ensureHere()` 每次进首页都调（5min TTL），但它解析出的小区**只驱动顶栏**；
  商品列表用的是 `community.community?.communityNo`（**主动绑定**的聚落）或粗区县。
  于是**新用户进首页，顶栏有小区名、商品却按区县拉** —— 没「定位到小区」。
- 改法：进首页 resolve 到小区级后，**若落进一个开放聚落且用户没有显式绑定别的**，
  就用这个聚落作为**当前位置**（顶栏显示小区名 + 商品按该聚落拉），并持久化（L0）+ 写回（L2）。
  - 显式绑定仍是**覆盖**：用户手选过别的聚落，以它为准，不被自动定位顶掉。
  - 落不进任何开放聚落（偏远/未开通）→ 维持现有「退区县 + 未开通引导」。
  - 这是**用「被动探得的 last_*」补「主动绑定 community_no」的空窗**，两者优先级：显式绑定 > 自动定位 > 区县。

### 顺序与理由
① 纯服务端、零契约、立竿见影、风险最低 → ② 纯端上体验提升 → ③ 动库表 + 隐私口径，要 TDD + 消融，最重。

### 另一条本就该有的：区域覆盖对账（新疆/西藏排除）
- 覆盖全国靠运营**批量开聚落**，偏远区的排除就是**不开**。但没有对账视图 → 误开/漏开看不出。
- 运营端加「区域覆盖对账」：按省/区列**已开放聚落数**，标出①应覆盖却 0 聚落的区、②**应排除却有聚落**的区（新疆/西藏聚落数应为 0，非 0 要红）。
- 这是**新建守卫**，口径（哪些区算「应覆盖」「应排除」）需运营给一份名单做基线，否则守卫没有基准（见 §9）。

### AC
- AC1（L1.5）同一格子第二次 resolve **不读 DB**；`stale` 结果**不进**内存缓存。
- AC2（L0）冷启动命中持久层 → 顶栏立即是上次地名 + 后台刷新；`force` 清内存/持久层/下游三处。
- AC3（L2）resolve 后 `usr_account.last_*`（含 `last_community_no` + 精确坐标 + 小区名）异步写入；
  500m 内重复 resolve **不重复写**；主动绑定的 `community_no` **不被覆盖**。
- AC4（首页）新用户进首页，坐标落进开放聚落 → 顶栏显示**小区名**且商品按该**聚落**拉（不是区县）；
  显式绑定过别的聚落 → 以绑定的为准；落不进任何聚落 → 退区县 + 未开通引导。
- AC5（对账）每区可见开放聚落数；新疆/西藏非 0 则守卫红；应覆盖区 0 聚落被列出。
- AC6（隐私）运营端查看他人 `last_*` 需权限位且留痕；对外响应/导出不含 `last_*`。

  「快递+运单号」留给真用快递的单。微信侧用自送的发货类型上报，不要单号。
- **遗留点**：是否需要「同城配送（无物流单号）」作为独立履约/发货类型，
  使微信支付单也能无单号发货？—— 岔口 B，默认用自送覆盖，不新增类型。

### AC

2. **B 端展示**：B-app 加「到访/浏览」页：本店近 N 天到访 UV/PV、
   明细（时间、来源渠道、是否下单）—— 读 `mkt_store_visit`，作用域限本店（`executeWithoutScope` 带店过滤）。
3. **运营端展示**：在既有获客聚合上加**下钻**（点某商家 → 逐条到访明细），
   复用 `OpsStoreAcquisitionController` 加一个 detail 端点。

### AC
- AC1 C 端打开虹选鲜果门店/商品后，`mkt_store_visit` 新增一行（含渠道、时间；商品级含 goodsNo）。
- AC2 B 端「到访」页展示本店近 7 天 UV/PV 与明细，**只看得到本店**（换店上下文数据跟着变）。
- AC3 运营端能从商家聚合行下钻到逐条到访，口径与聚合一致（下钻合计 = 聚合值）。

## 7 测试用例规划

> 每条按 dev-standards：**happy + 边界 + 一次能证伪的消融**。★ 标注必须有消融的。

### 7.1 位置（§1）
- ★ 冷启动命中持久缓存：预置本地 `here`（未过期）→ 首屏顶栏立即是该地名，且触发后台刷新。
  消融：去掉持久化读取 → 首屏为空/「定位中」。
- 过期：`here.at` 超 TTL → 不用缓存，重新定位。
- 重新定位 force：清缓存+持久层+下游。
- ★ 区域对账：新疆/西藏造一个聚落 → 守卫红；应覆盖区 0 聚落 → 守卫列出。
  消融：移除排除名单断言 → 偏远区聚落不报。

### 7.2 购买（§2，回归）
- 虹选鲜果真实商品：可达聚落下单成功，拿到 orderNo、金额与预览一致。
- 幂等：同 `idempotencyKey` 重复提交返回同一单。
- 边界：不可达聚落下单被拒、未开线下收款时线下支付入口不出现。

### 7.3 发货（§3）
- ★ 自送单点「已送达」无单号完成发货 → 状态流转 + `SubOrderShipped` 触达。
  消融：撤掉自送发货分支 → 自送单无法完成发货。
- 快递单缺运单号被拒；填齐后发货成功并满足微信发货录入。
- 权限：无 `biz:ship` 的员工看不到发货按钮（既有，回归）。

### 7.4 收款（§4，回归）
- 门店+商品都开 → 线下收款一笔成功、流水回读。
- ★ 门店开/商品关 → 该商品线下收款入口不出现（两层开关，消融任一层都该变）。

### 7.5 订单导出/复制（§5）
- ★ 复制内容逐字段等于订单详情（多商品行、含备注）。消融：模板漏收件人 → 断言红。
- 自提单无收件人 → 跳过收货/地址行，不出现 "null"。
- ★ 复制写一条审计。消融：去掉审计调用 → 断言红。

### 7.6 浏览记录（§6）
- ★ C 端开店/开商品 → `mkt_store_visit` +1（去重：同日同人同货只 +1）。
  消融：去掉 record 调用 → 行数不增。
- B 端「到访」页只显示本店数据；换店上下文数据随之变（作用域正确）。
- ★ 运营端下钻合计 = 聚合行的值（跨粒度对账）。消融：下钻漏一种渠道 → 两数不等。

## 8 批次与优先级

| 批 | 内容 | 依赖 | 价值 |
|---|---|---|---|
| **B1** | 运营前置：虹选鲜果商品在售、两层线下收款、目标区批量开聚落 | 无（运营动作） | 没有它后面都跑空 |
| **B2** | 订单复制给供应商（§5，净新、最小、最急） | B1 | 供货流程当天能用 |
| **B3** | 位置持久缓存 + 区域对账（§1） | 无 | 首屏体验 + 防漏开偏远区 |
| **B4** | 浏览记录 B 端展示 + 运营下钻（§6） | 记录已在跑 | 经营可见性 |
| **B5** | 同城/自送发货口径收敛（§3，多为确认+回归） | B1 | 发货不卡单号 |

## 9 偏差与遗留（先写下来，不假装没有）

- 商品级浏览记录是否要做，取决于岔口 A；不做则 §6 只覆盖门店到访。
- 同城无单号发货是否需独立履约类型，取决于岔口 B；默认用自送覆盖。
- 批量导出不在本期（岔口 C）。
- 区域覆盖对账是**新建守卫**，口径（哪些区算"应覆盖"）需运营给一份名单，否则守卫没有基线。
