# 零售基线 —— 接口与流程（P2）

状态：**草稿 · 待确认** · 创建 2026-08-27
关联：[方案梳理清单](./方案梳理清单-行业化接口盘点与终局选型.md) P2 · [TDD-餐饮包](./TDD-餐饮包-场景与工作流.md) · [TDD-美业包](./TDD-美业包-场景与工作流.md) · [核心能力清单](../reference/核心能力清单.md)

> **零售不是"没有行业"，它是基线。**
> 说「餐饮和美业不一样」没有信息量；要说的是「**相对零售**，餐饮在这 12 个接口上是 X 档」。
> 本册就是那个参照物。

---

## 1. 基线的定义

**零售 = 不装任何行业包时，系统能跑的全部。**
`mch_store.industry_pkg = 'RETAIL'`，能力开关按核心能力清单附表的「零售默认」列展开。

一条自检：**`-Pcore-only` 构建出的 jar 能跑通的，就是基线**。跑不通的不属于基线。

## 2. 盘点结果（实测，不是估计）

扫描后端全部 `@*Mapping`，取 `/biz` 与 `/mp` 两端：

| 维度 | 数 |
|---|---|
| 端点总数 | **299**（`/biz` 206 + `/mp` 93） |
| 读（GET） | **149** |
| 写（POST/PUT） | **150**（POST 140 + PUT 10，**无 DELETE**） |
| 有前端调用方 | **272** |
| **无消费方**（后端有能力，`endpoints.ts` 里没人调） | **27** |
| `/ops` 运营端 | 338 —— **本轮不盘**（P0 §2.4 已声明） |

> 方法：端点路径取到第一个 `{` 之前的静态前缀，在 `b-app/src/api/endpoints.ts` 与
> `c-app/src/api/endpoints.ts` 里做子串匹配。**会有假阳性**（前缀相同但实际未调），
> 所以 272 是**上界**，真实消费面只会更小。P3 用它做相对比较，不做绝对断言。

### 2.1 读写各占一半 —— 这个数字直接影响选型

149 读 / 150 写。上一轮定的方向是「**写按主语走基座门，读允许行业聚合**」——
这意味着**行业化的空间最多覆盖一半接口，而且是风险最低的那一半**。
P3 统计 `V`（读视图差异）时，分母就是这 149。

### 3.1 三个立刻能看出来的事

**① `slot` 只有 1 个端点。**
基座的预约能力（`mch_appointment_slot` + `AppointmentSlotPort` + 并发占位 + 场景测试）**后端是完整的**，
但**对外只暴露了 3 个端点**：B 端一读一写、C 端一读。
→ 美业包依赖的 E2 能力，实际可用面几乎为零。**P1 里"复用基座预约"这句话，复用的是内核不是接口。**
这条要写进美业包的施工前提，否则第一天就会撞上。

**② `stock` 27 个是 B 端最大的一组**，且属于独立数据源的 `shop-inventory`。
餐饮的沽清、美业的耗材都要碰它 —— 但两者用的都只是"设库存"这一个动作。
**行业包不该碰进销存的其余 26 个接口。**

**③ `group`（社区团购）20 个是本平台特有的。**
它既不是零售通用能力，也不属于任何行业包 —— 它是**这个平台的业务形态**。
P3 打关系码时，这一组对餐饮/美业多数是 `N`（不适用），
**不能算进"差异率"的分母**，否则会人为抬高 `X` 占比、把结论推向方案 B。

## 4. 零售的五段流程

| 段 | 零售怎么走 | 主要端点 | 对照 |
|---|---|---|---|
| **下单** | 加购 → 结算试算 → 下单（选履约方式）→ `WAIT_PAY` | `/mp/cart/*`、`/mp/order/*` | 餐饮：台账购物车 + 多轮下单；美业：预约单先行 |
| **支付** | 线上支付 → 回调 → `markPaid` | `/mp/order/pay`、`/callback/**` | 餐饮：可后付；美业：可资产付 |
| **履约** | 自提 / 邻里自提 / 商家自送 / 快递，四选一 | `/biz/pickup/*`、`/biz/delivery/*` | 餐饮：堂食（无交付动作）；美业：到店核销 |
| **售后** | 申请 → 退款 / 驳回 → 申诉裁决 | `/mp/after-sale/*`、`/biz/after-sale/*` | 两个行业**完全复用**，一行不加 |
| **结算** | 账单 → 对账 → 自营付款 / 第三方分账 | `/biz/settle/*` | 两个行业**完全复用** |

**这张表本身就是一个结论**：五段里**售后与结算两段，三个行业完全相同**。
它们合计 18 个端点，在 P3 里应当整组落 `S`。

## 5. 零售缺什么 —— 这些是基座该补的，不是行业包的

盘完之后，零售自己就缺这些（与两个行业包无关，它们只是也需要）：

| 缺口 | 为什么是基座的 | 现状 |
|---|---|---|
| **收银台 / 线下开单** | 便利店、生鲜店都要，不是餐饮专属 | ❌ 无 |
| **小票打印** | 零售出小票、快递打面单 | ❌ 无（核心能力清单 I1–I4） |
| **储值 / 次卡** | 三行业都要，且是预收款、牵动财务口径 | ❌ 无（F2） |
| **组合商品** | 零售的"礼盒装"≡餐饮套餐≡美业疗程包 | ❌ 无（B4） |
| **能力开关** | 行业化的地基 | ❌ 无（A4） |
| **资源与时段的对外接口** | 后端有内核，**接口只有 1 个** | ⚠️ §3.1① |
| **`assetDeductMinor` 列** | 预收款核销，既非平台补贴也非商家让利 | ❌ 无（美业包硬依赖） |

**注意这一列的意义**：它们全部落在基座阶段 0，
而阶段 0 的验收标准是「**什么都没变**」—— 补完这些，零售商家的行为不该有任何变化。

## 6. 27 个无消费方端点

后端有能力、前端没人调。分布：

```
biz/settle 4 · mp/ticket 3 · mp/topics 2 · mp/coupon 2 · biz/deposit 2 · mp/search 2
mp/help 1 · biz/quote 1 · mp/risk 1 · biz/inventory 1 · biz/merchant 1 · mp/store 1
mp/attribution 1 · mp/stores 1 · biz/qualifications 1 · …
```

**P3 里这 27 条要单独标记，不参与关系码统计。**
理由：一个没人调的接口，说它"三个行业是否有差异"是没有意义的 ——
它的差异永远是零，会**系统性地把 `S` 的占比推高**，让结论偏向方案 A。

同时这也是一份**独立的清理清单**：要么补前端，要么删接口。留着的每一条都在稀释统计。

## 7. 怎么用这份基线（P3 的操作说明）

对 299 条里的每一条，问两个问题：

1. **餐饮做同一件事，用的是这个接口吗？**
   - 是，且参数相同 → `S`
   - 是，但要多几个字段/过滤 → `P`
   - 是（写相同），但返回的东西不一样 → `V`
   - 不是，流程根本不同 → `X`
   - 这件事餐饮没有 → `N`
2. **美业同上。**

**三条统计口径先定死**（P3 之后不许改）：

| 排除项 | 条数 | 理由 |
|---|---:|---|
| 无消费方端点 | 27 | 差异恒为零，会抬高 `S` |
| `group`（社区团购） | 20 | 平台形态，对两个行业多为 `N`，会抬高 `X` |
| `external=Y`（支付/物流回调） | 待 P0 标注 | 否决项，恒走基座，不参与占比 |

**有效分母 ≈ 299 − 27 − 20 − external ≈ 250 上下。**
判定阈值（清单 §6 的 15% / 40%）按这个分母算。

## 8. 局限（P4 结论里要再声明一次）

1. **`/ops` 的 338 个端点没盘。** 运营端若要行业化（如按行业的营业报表），本册结论不覆盖。
2. **"有前端调用方"是静态前缀匹配**，272 是上界。
3. **本册只盘接口，没盘 Service 层。** 同一个接口内部为行业分叉的可能性不在本册视野内 ——
   但那正是方案 A/C 要防的东西，P4 讨论时要记得它没被度量过。
4. **社区团购（`group`）没有被当作"第四个行业"审视。** 它今天是平台形态；
   若将来它也要行业包化，本册的分母要重算。
