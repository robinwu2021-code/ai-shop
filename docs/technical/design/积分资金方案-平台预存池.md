# 积分资金方案 · 平台出资预存池

> 状态：**待确认**（2026-10-14 起草）· 取代：[积分域-完整方案](./积分域-完整方案.md) 的资金模型（商家发分费 1:1）
> 决策：[ADR-036 积分改为平台出资预存池](../ADR/ADR-036-积分改为平台出资预存池.md) ·
> 落地设计：[TDD-积分域重整](../TDD-积分域重整.md)（业务抽象 / 类设计 / 库表 / 接口）
> 范围：本期只做「购物返积分」，只开 `CN / CNY` 一个区域；模型按多区域、多币种、多场景设计。

---

## 一、一句话

**平台先把钱存进积分池，再发分；池子里没有钱就停发。**
每一分积分（包括还不能花的待生效积分）在发出那一刻就有等额资金被锁定，
所有变动只能通过一张借贷平衡的「记账凭证」写入，写不平就写不进去。

---

## 二、为什么是这个方案

### 被否掉的四个资金模型

| 方案 | 机制 | 否掉的理由 |
|---|---|---|
| 商家发分费（**现状**） | 商家每发 1 分，结算时从货款扣 1 分钱进池 | ① 发分时钱还没到，费用金只是**账面应收**：建结算单那一刻就记了入池，而售后期内退款（绝大多数）时这笔从没真正收到；② 线下单、积分退款等路径收不到费用金，池子凭空少钱；③ 商家要理解「我为别人家的兑付付钱」，推广阻力大 |
| 信用模型 | 发分只记负债，兑付时再找发放方要钱 | 或有负债藏在账外，商家跑路时平台才发现要垫付；需要授信额度、超授信停发、跨商家清算三套东西（V17 → V22 已否过一次） |
| 佣金到账时才进池 | 发分只记承诺，结算终局时从佣金划钱进池 | 待生效的分没有资金对应 —— 售后期内如果平台账户被挪用，承诺就是空的；也做不出「超过预算就停发」这一运营诉求 |
| 不设池子，花分时平台直接掏钱 | 兑付时从平台经营账户付 | 没有任何上限，营销成本随成交量线性失控；无法回答「平台现在为积分备了多少钱」 |

### 选中的方案：预存池

| 运营诉求（2026-10-14） | 方案里对应的机制 |
|---|---|
| 运营创建积分，含对标币种、兑换比例 | 「积分种类」主数据；兑换比例**生效后锁定** |
| 创建资金池，超过就停发 | 一个种类一个池子；发分前条件扣减「未分配」，扣不动即停发 |
| 定期补充 | 补充单（双人复核）+ 定期补充计划（只生成待审批单，不自动动钱） |
| 详细的发放与核销记录，按平台 / 门店 / 用户统计 | 每张凭证的每一行带齐维度；三视角汇总从明细重算 |
| 能暂停 | 发放、核销分开暂停，粒度到全局 / 区域 / 种类 / 场景 / 端 / 门店 / 用户 |
| 不超发、资金安全 | 恒等式 `C + R == m(P + A + H)` 在**写入时**由凭证保证，事后三层对账兜底 |

## 三、结构

### 3.1 钱怎么流

![积分资金流](../diagrams/pts2-fund-flow.svg)

图上要读出三件事：

1. **池子只有一个入口带新钱进来**：补充（TOPUP）。退款回池、现金抵扣只是把出去的钱收回来。
2. **发分不动真钱**，只是池子内部从「未分配 U」挪到「已承诺 C」。真钱只在三处离开池子：
   兑付给收单方、到期转平台收入、提取回平台账户。
3. **池子是平台账户里的专项**（本期），不是独立银行账户。所以外部对账要校验
   「平台账户实际余额 ≥ 池子 U + C + 其他待付」—— 这是「专项」这个选择的代价，必须用对账补上。

### 3.2 五格余额

每个积分种类有一个池子、每个用户在每个种类下有一个账户：

| 对象 | 格子 | 含义 | 不变式 |
|---|---|---|---|
| 资金池 | **U** 未分配 | 已补进来、还没承诺给任何积分的钱 | `U ≥ 0`（条件扣减） |
| | **C** 已承诺 | 已发出的积分对应的钱（含待生效） | `C ≥ 0` |
| | **R** 待追回 | 该回池、钱还在外面（补差回退失败） | `R ≥ 0`；超 N 天告警 |
| 用户账户 | **P** 待生效 | 已发放、未到结算终局，**可见不可用** | `P ≥ 0` |
| | **A** 可用 | 能花的 | `A ≥ 0`（**不许负余额**） |
| | **H** 占用 | 下单已扣、尚未兑付给收单方 | `H ≥ 0` |

**总恒等式（每个种类各自成立）**：

```text
C + R == m(P + A + H)        有分就有钱；R 是「钱该在、暂时追回中」
U ≥ 0                         没有钱就发不出分
U + C == 池子账面余额 == 平台账户里这笔专项   （外部对账）
```

`m(x)` 是积分折成金额。兑换比例存为既约分数 `points_unit : minor_unit`
（例：100 积分 = 1 元 → 100 : 100 → 1 : 1），**凭证里的分数必须是 `points_unit` 的整数倍**，
所以 `m(x) = x / points_unit × minor_unit` 永远整除 —— 余数是对账差异最常见的来源，这里从结构上消灭它。

### 3.3 三个时点

![积分生命周期](../diagrams/pts2-lifecycle.svg)

| 时点 | 发生什么 | 防住什么 |
|---|---|---|
| **支付成功**（提交后） | 发放：P +x，池子 U → C | 用户立刻看得到「待生效 x 分」，不会以为没给 |
| **结算终局**（直连 `SPLIT_CONFIRMED` / 归集 `CONFIRMED`） | 转正：P → A | 「下单拿分 → 立刻花掉 → 退单」：终局在售后期之后，期内退款时分还在 P，原样收回 |
| **收单子单结算终局** | 兑付：H 清掉，C 付给收单方 | 抵扣的钱在订单可能取消/退款期间不离开池子 |

> 现状是「支付 + 7 天」固定转正，与发货、签收、售后期都无关 ——
> 上门预约、慢发货的单，分会在售后期结束前就能花。改挂结算终局后这条缺口消失。
> 注意：桩网关永远停在 `SPLIT`、不会到 `SPLIT_CONFIRMED`，测试环境要用回执驱动，否则分永远不转正。

## 四、详细设计

### 4.1 凭证：唯一的写入口

每个业务动作开一张凭证，`biz_ref` 唯一（同一动作重放只生效一次），
过账时在**同一个事务**里对账户、池子、头寸做条件更新，任何一行影响 0 行就整张回滚。

| 凭证 | 触发 | 用户账户 | 资金池 | 头寸 | 写不进去 = 什么情况 |
|---|---|---|---|---|---|
| `TOPUP` 补充 | 补充单审批通过 | — | U +M | — | 回单号缺失、提交人 = 审批人 |
| `WITHDRAW` 提取 | 提取单审批通过 | — | U −M | — | U 不够（**只能提未分配，C 一分不能动**） |
| `GRANT` 发放 | 支付提交后 | P +x | U −m, C +m | 发放头寸 granted = x | U 不够 → **停发**，头寸记 `SKIPPED/POOL_EXHAUSTED` |
| `ACTIVATE` 转正 | 发放子单结算终局 | P −x, A +x | — | activated = x | 已收回的部分不转 |
| `HOLD` 占用 | 下单 | A −y, H +y | — | 占用头寸 held = y（按子单） | A 不够 → 降级为不抵扣（不挡下单） |
| `RELEASE` 释放 | 取消 / 未成交 / 兑付前退款 | H −r, A +r | — | released += r | 已进入 REDEEMING 或已兑付 |
| `REDEEM` 兑付 | 收单子单结算终局（两阶段，见 4.3） | H −y | C −m（付给收单方） | redeemed = y | 头寸不在 REDEEMING |
| `RETURN` 退回 | 兑付后退款 | A +r | C +m（补差回退成功）或 R +m（失败） | returned += r | 超过已兑付 |
| `REVOKE` 收回 | 发放子单退款 | P −z 或 A −z | C −m, U +m | revoked += z | 超过已发放 |
| `EXPIRE` 到期 | 账户闲置满期 | A −a | C −m（转平台收入） | — | A 已变化（下一轮再判） |
| `ADJUST` 调账 | 调账单审批通过 | A ±x | 加分：U → C；减分：C → U | — | 双人复核未过 |
| `RECOVER` 追回 | 待追回的钱到账 | — | R −m, C +m | — | — |
| *`PROMO_GRANT`* | *将来：签到等营销场景* | *A +x* | *U → C* | — | *本期只预留类型* |

两条硬规则（ArchUnit 守）：

- **新钱进池只有 `TOPUP`**；收回的钱经 `RETURN`、`RECOVER`、`REVOKE`（现金抵扣部分）回池；离池只有 `REDEEM`、`EXPIRE`、`WITHDRAW`。
- **A 只有 `ACTIVATE`、`RELEASE`、`RETURN`、`ADJUST`（将来加 `PROMO_GRANT`）能加**。
  P 变 A 必须走 `ACTIVATE`，而 P 本身是 `GRANT` 带着钱进来的 —— 这就是「不超发」在写入时成立的原因。

### 4.2 发放：返多少

```text
x = Σ 每行规则(类目规则 / 商品例外)        ← 返多少由规则定（运营在种类下配）
x = floor_to_unit(x)                         ← 取 points_unit 的整数倍
可选：x ≤ m⁻¹(本单佣金 × 封顶比例)          ← 本期默认关闭，只留接口
池子：U ≥ m(x) 才发；否则整单不发            ← 不部分发：「为什么只给了 37 分」解释不清
```

- 规则：`FIXED` = 每件 n 分 × 件数（**现状按行发、不乘件数，改正**）；`RATIO` = 行实付（不含运费、已扣券与积分）× 万分比。赠品不发。
- 不发的情形也落一行发放头寸（`SKIPPED` + 原因），统计里能看到「因池子不足少发了多少」—— 这是运营决定补多少钱的依据。

| 不发的原因 | 为什么 |
|---|---|
| `POOL_EXHAUSTED` 池子不足 | 不超发 |
| `PAUSED` 任一粒度暂停发放 | 运营控制 |
| `OFFLINE` 线下单 | **平台出资后，线下单是刷分入口**：成交由商家自报、平台无法核验，商家与买家串通造单就能套平台的钱 |
| `FROZEN` 用户被风控冻结 | 风控 |
| `RULE_ZERO` 规则算出 0 | 如储值卡明确配 0 分 |

### 4.3 核销：两阶段兑付

占用头寸的状态机：

```text
HELD ──beginRedeem──▶ REDEEMING ──confirmRedeem──▶ REDEEMED
  ▲                        │
  └──────abortRedeem───────┘
退款 / 取消只作用于 HELD；遇 REDEEMING 返回「处理中」由调用方重试
```

1. 结算域在发起补差**之前**调 `beginRedeem(子单)`：条件更新 `HELD → REDEEMING`，
   返回**此刻真实的补差额**（= held − released）。返回 0 → 这单不补差。
2. 调通道补差（直连）；归集路径没有通道动作，1 与 3 在结算单确认时一并完成。
3. 成功 → `confirmRedeem` 过账 `REDEEM`；失败 → `abortRedeem` 回到 `HELD`。
4. 3 走 outbox，按 `biz_ref` 幂等 —— 防「通道成功了而凭证没记上」；巡检扫超时的 `REDEEMING`。

> **防住什么**：现状的补差额是结算单生成时的快照（`stl_bill.subsidy_minor`），
> 与积分是否已退回无关 —— 积分退款形式下，买家拿回了抵扣的分，分账照样补差，同一笔付两次。

核销规则：

| 规则 | 防住什么 |
|---|---|
| 一单只用一种积分（本期每区域只有一种，自然满足） | 多种叠加让单笔让利失控 |
| 上限 = 可用子单的（券后、不含运费金额）× 抵扣比例，按种类配 | 整单抵光，收单方一分收不到；运费要付给运力 |
| 只在**可用**的子单间按金额分摊，余数给最后一家 | 分摊到不可用的子单会让它凭空少收钱 |
| 线下单不能抵扣 | 线下结算单是终态 `OFFLINE_SETTLED`，没有任何通道能把池子的钱付给收单方 |
| 收单门店能用的支付通道必须都支持补差 | 现状到分账时才发现、转人工；改在下单时拦 |

### 4.4 退款：两侧分开、按累计比例

一张子单可能既「用了分」（收单侧）又「返了分」（发放侧）。按**累计**退款比例算，部分退款多次也不会多退：

```text
k        = 本子单累计已退金额 ÷ 子单实付（头寸上的快照）
应退回    = floor_to_unit(held × k)   − 已退回
应收回    = floor_to_unit(granted × k) − 已收回
全额退款时 k = 1，取到精确值，没有余数遗留
```

| 侧 | 情形 | 用户 | 池子 / 现金 |
|---|---|---|---|
| 收单侧 | 未兑付（绝大多数） | `RELEASE` H → A | 不动 |
| | 已兑付、补差回退成功 | `RETURN` A + | C + |
| | 已兑付、补差回退失败 | `RETURN` A +（不让买家替平台吃亏） | R +，挂待追回告警 |
| 发放侧 | 待生效（绝大多数） | `REVOKE` P − | C → U |
| | 已转正、A 够 | `REVOKE` A − | C → U |
| | 已转正、A 不够（分已经花了） | A 扣到 0，**不许负** | 差额 m(z − 已扣) **从退款现金里扣**，扣下的钱进 U；退款单明示 |

**顺序：先积分、后现金。** 退款流程先调积分的 `applyRefund`（幂等，返回现金要扣多少），
再按「退款额 − 扣减」退现金。现金退款失败重试时，积分侧已经落定、不会重复扣。

### 4.5 到期

- **账户级滚动到期**（沿用 V30）：任何 `GRANT`、`HOLD` 都把到期日推后 `闲置天数`；`REVOKE`、`EXPIRE` 不推（退一单续一年会被反复触发）。
- 到期时刻取**区域时区**的当天 23:59:59。
- 到期只清 A；P、H 不动（还在流程中）。`EXPIRE` 的钱 **转平台收入**（2026-10-14 定），按日汇总成一张划拨单。
- **到期前 30 天推送提醒**，`expire_notified_at` 幂等。滚动到期是一次性全清，不提醒对用户是敌意的。
- **核销暂停期间到期时钟停走**：恢复时把该种类账户的到期日顺延暂停时长 —— 否则用户「用不了还被清零」。
- 清零是**条件清零**（`WHERE available = 读到的值 AND expire_at <= now`），批量循环到清完为止，不再是一天 500 条。

### 4.6 运营

| 能力 | 规则 | 防住什么 |
|---|---|---|
| 创建积分种类 | 区域 + 币种（取自 `MarketService`）+ 兑换比例 + 抵扣比例 + 返分规则 + 闲置天数；`草稿 → 生效 → 停用` | 每区域同时只有一种生效中的平台积分 |
| 兑换比例 | **生效后锁定**；要改就新建种类，用迁移凭证把余额换过去 | 直接改会把所有存量负债按新比例重估，池子当场对不上 |
| 开池 | 建种类时同时建，U = 0；生效前必须有过至少一笔补充 | 没钱就上线 |
| 补充 / 提取 | 补充单：录金额 + 回单号 → 另一人审批 → 过账 | 一个人既能录钱又能批钱 |
| 定期补充计划 | 按月（固定额 / 上月佣金 × 比例）**生成待审批补充单** | 计划自动动钱 = 没有复核 |
| 低水位预警 | 可发天数 = U ÷ 近 7 天日均发放额，低于阈值告警；U = 0 时停发并告警 | 池子悄悄见底，用户发现「这几天怎么没返分」 |
| 暂停 | 发放 / 核销分开；粒度：全局、区域、种类、场景、端、商家、门店、用户；必填原因、留审计 | 暂停只影响将来，在途订单照常走完 |
| 调账 | 调账单双人复核；加分从 U 出资 | 后门直接改余额 |

### 4.7 统计

**明细只有一份**：凭证行，带区域、种类、场景、凭证类型、用户、订单 / 子单、**发放门店 / 收单门店**、商家主体、时间、分数、金额。

| 视角 | 内容 |
|---|---|
| 平台 | 按区域 × 种类 × 日 / 月：发放、停发（次数与少发量）、转正、核销、退回、收回、到期；流通负债 P / A / H；池子 U / C / R、补充、提取；可发天数 |
| 门店 | 本店返出（平台出资）、本店收进的分与补差金额，下钻到单；门店在 B 端只看本店 |
| 用户 | 三格余额、到期日、逐笔明细（链接订单）；运营可按用户查累计获得 / 使用 / 收回 / 到期 |

汇总表按凭证号水位增量计算（每 5 分钟），**随时可从明细重算** —— 汇总错了不丢账。

### 4.8 对账与告警

| 层 | 内容 | 频率 |
|---|---|---|
| **L1 写入时** | 凭证在同一币种内平衡；`biz_ref` 唯一；全部条件更新 | 每次 |
| **L2 内部** | 在**同一个一致性快照**（`START TRANSACTION WITH CONSISTENT SNAPSHOT`）里核 I1–I6 | 每小时 |
| **L3 外部** | 平台账户余额 ≥ U + C + 其他待付；通道补差 / 补差回退流水与 `REDEEM` / `RETURN` 逐笔 | 每日 |

| # | 核对 | 粒度 |
|---|---|---|
| I1 | `C + R == m(P + A + H)` | 每个种类 |
| I2 | 账户三格 == Σ 该账户流水 | 逐账户（按水位只查有变动的） |
| I3 | 池子三格 == Σ 池子流水 | 每个池子 |
| I4 | 发放头寸 `granted == pending + activated + revoked`；占用头寸 `held == 在占 + released + redeemed` | 逐子单 |
| I5 | 结算单补差额 == 该子单 `REDEEM` 金额；结算终局的子单都有对应凭证；`REDEEMING` 不超过 30 分钟 | 逐子单 |
| I6 | 每张划拨单金额 == 它覆盖的池子流水之和 | 逐划拨单 |

能定位到单据的（I2、I4、I5、I6）落差异单，进现有对账总览的 `POINTS` 轴；I1 是整体指标，只告警。
告警走 `OpsAlertPort` 发到企微群，不再只写日志：池子低水位 / 停发、I1 失衡（**为负 = 资金缺口**，最高级）、
外部余额不足、R 超 7 天、`REDEEMING` 超时、补充单待审批超 24 小时、暂停超 7 天未恢复。

## 五、与现状的对比

依据：2026-10-14 对 `PointsServiceImpl` 等的逐行 review（见会话记录与 TDD §1）。

| 维度 | 现状 | 新方案 | 消掉的缺陷 |
|---|---|---|---|
| 出资方 | 商家，每单 `points_fee_minor` 1:1 | 平台，预存入池 | 商家「替别人兑付」的推广阻力 |
| 发分时有没有钱 | 没有：费用金在建结算单时**记账**入池，并未收到 | 有：`U ≥ m` 才发 | 超发；退款单的费用金永久挂在池里（review P1-7） |
| 停发 | 无 | U 不足自动停发 + 预警 | 发放量无上限 |
| 种类 / 币种 / 比例 | 隐式 CN；比例在 `points.config` JSON，运营随时可改 | 种类主数据，绑定区域与币种，比例生效后锁定 | 改比例让存量负债重估（review P2） |
| 写入口 | 6 个方法各自改账户 / 流水 / 池子 | 唯一的 `post(voucher)` | 「改了一边忘了另一边」这一整类 |
| 幂等 | 先查后写，表上无唯一键 | `biz_ref` 唯一 + 头寸条件增量 | 并发退两次分、记两笔兑付（review P1-4） |
| 状态迁移 | `updateById`，乐观锁冲突静默 0 行且返回值无人看 | 条件更新，0 行即整张回滚 | 清零写了流水没清余额（review P1-5） |
| 转正时点 | 支付 + 7 天 | 结算终局 | 售后期未过分就能花 |
| 兑付 | `confirmDeduction` 与补差快照脱钩 | 两阶段，补差额以积分域为准 | 积分退回后仍补差，付两次（review P0-1） |
| 部分退款 | 只在整单退完时退；一退全退 | 按累计比例 | 退 50 元退回全部抵扣积分 + 收回全部返分 |
| 扣不回 | 默认允许负余额；`points_offset_minor` 零写入 | 不许负；差额从退款现金扣并明示 | 与方案自相矛盾（review P1-8） |
| 线下单 | 可抵扣，收单方被抵的钱永远拿不到 | 不返、不抵 | review P0-2 |
| 积分退款形式 | 平台直接加可用余额，无资金来源、不受任何开关 | 下线；将来作为营销场景须先预存 | review P0-1 |
| 全局开关 | `features.points` 只下发前端 | 后端闸门矩阵，所有写凭证入口先过闸 | review P0-3 |
| 到期 | 一天一次 `LIMIT 500`；`updateById` 清零；无提醒 | 条件清零、循环到清完；提前 30 天提醒；暂停顺延 | review P2 |
| 池子快照 | `balance_after` 全错（`pay_channel` 传 null → `= NULL` 匹配 0 行） | 池子一行余额条件更新，流水带变动后值 | review P1-6 |
| 对账 | 一个恒等式，只写日志；靠 cron 错开避免读到中间态 | L1–L3、逐单差异单、一致性快照、企微告警 | 失衡没人知道；假告警 |
| 统计 | 只有商家本期发分费 | 平台 / 门店 / 用户三视角 | — |
| 商家开关 | 商家自开 + 行业强制 + 小微判定 | 运营黑名单（商家 / 门店） | 平台出资后商家开关失去意义 |

**沿用的**：账户级滚动到期、待生效概念、类目规则 + 商品例外、区域隔离、子单分摊余数给最后一家、抵扣失败降级不挡下单。

## 六、取舍记录

| 冲突 | 让了谁 | 代价 | 为什么接受 |
|---|---|---|---|
| 平台成本 ↔ 商家成本 | **平台出** | 营销成本随成交线性增长 | 池子上限 + 停发把它变成一个可控的预算，而不是敞口 |
| 物理隔离 ↔ 落地快 | **专项（不隔离）** | 平台账户被挪用时池子是空的 | 外部对账每日校验「账户余额 ≥ U + C」，不足即最高级告警；专户留作将来 |
| 池子不足时部分发 ↔ 整单不发 | **整单不发** | 用户少拿一点分 | 「为什么只给 37 分」无法解释；少发量进统计，运营据此补钱 |
| 到期的钱回池 ↔ 转收入 | **转收入**（2026-10-14 定） | 池子多一个出口、每日一张划拨单 | 财务口径清楚：过期即实现收入 |
| 线下单返分 ↔ 防刷 | **防刷** | 线下用户拿不到分 | 平台出资后线下单无法核验成交，是零成本刷分入口 |
| 写入时强制恒等式 ↔ 热点行 | **不把 P/A/H 合计放进池子行** | I1 要靠快照求和、每小时一次 | 每张凭证都更新池子行会让下单抢同一行锁；L1 已保证每张凭证平衡，I1 只防带外写 |
| 两阶段兑付 ↔ 简单 | **两阶段** | 多一个中间态与巡检 | 「补差在途时被退款」是真实并发，不拦就是付两次 |
