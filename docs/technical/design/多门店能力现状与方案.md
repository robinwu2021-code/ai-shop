# 多门店：现状盘点与方案

> 2026-08-10 · 起因：全链路回归跑完后要判断「一个商家开第二家店」现在能不能走通。
> 结论先说：**骨架已经搭好了，但只有履约那一段真的通到底；商品、库存、结算、营销全在主体级。**

---

## 1. 现状：一句话

> **门店已经是「顾客感知的边界」，但还不是「经营的边界」。**

一家主体开第二家店，今天会发生的事是：
两家店卖**同一批商品**、共用**同一份库存**、共用**同一套营销活动**、
结算**混在一张账单里**——只有「这单是哪家店发的货」分得开。

---

## 2. 已经有的（骨架完整）

| 项 | 状态 |
|---|---|
| `mch_store` 表 | ✅ 有 `store_no` / `name` / `is_default` / `status` / `pay_merchant_no` / 装修字段 |
| 一主体多店 | ✅ 建表就支持；`is_default` 保证「找不到具体门店时去哪」有答案 |
| **每店独立收款号** | ✅ `pay_merchant_no` + `payment_changed_at`（切换有审计） |
| 员工按店授权 | ✅ `mch_store_role`（哪个员工能管哪几家店） |
| 订单落店 | ✅ `ord_sub_order.store_no` 双写（`entity_no` 结算 / `store_no` 履约） |
| B 端门店管理 | ✅ `/biz/store/list`、`/biz/store/create`、店铺码、分享物料 |
| 门店装修审核 | ✅ `mch_store_audit` + `/ops/stores/audits` |
| C 端门店主页 | ✅ 有独立页面与收藏（`usr_store_favorite`） |

`OrdSubOrder.storeNo` 的注释把这个设计讲得很清楚：

> 「双写门店：`entity_no` 是**结算键**（分账/积分/对账都按它），
> `store_no` 是**履约键**（发货/自提/评价/门店报表按它）。
> 单店时两者恒等 —— 这正是多门店能分阶段发布的原因。」

**这个分层是对的**，也是后面所有工作能增量做的前提。

---

## 3. 缺的（按「开第二家店那天会先撞上哪个」排序）

全库带 `store_no` 的表只有 **3 张**：`mch_store` / `mch_store_role` / `ord_sub_order`。
其余全部只有 `entity_no`。这句话本身就是缺口清单。

### 3.1 库存不分店 🔴 最先撞上

`prd_sku` 的唯一键是 `(entity_no, sku_no, market)`——**没有 store_no**。

后果：文三路店卖光了，古墩路店也显示无货；反过来，顾客在 A 店下单，
库存从「全公司总量」里扣，而货其实在 B 店。**自提场景下这是直接的履约事故**：
顾客到店取不到货。

> 这一条不解决，多门店就不能开给真实商家用。

### 3.2 商品不分店

`prd_goods` 只有 `entity_no`。两家店必然卖同一批商品、同一个价。

真实小店不是这样：文三路店卖早点、古墩路店卖生鲜；同一款米在两个小区可以差两块钱。

### 3.3 营销活动不分店

`mkt_campaign.entity_no NOT NULL`，没有 store 维度。
今天刚接通的四种活动（满减/特价/买赠/店铺券）**一律全主体生效**。
「新店开业第一周满减」这种最常见的诉求做不了。

### 3.4 结算不分店

`stl_bill` 只有 `entity_no`。两家店的钱混在一张流水里。

> **更正（2026-08-10 复查）**：这里原先写的是「收款分了，结算没分」。
> **说多了——收款也没分。** `pay_merchant_no` 全库只有两个消费方：
> 写进去（`setPayment`）和显示出来（`StoreVO`），支付与结算侧零消费方。
> 分账接口 `split(subOrderNo, amountMinor, requestNo)` **连收款账户参数都没有**。
> 所以现状不是「两套账户一本账」，是**配了两套账户但谁都没读过** ——
> 与本轮反复撞到的「有能力没有消费方」同形状。

详见 [多门店结算方案](./多门店结算方案.md)。

### 3.5 自提点与门店没有关联

`cmt_pickup_point.owner_ref` 在 `type=STORE` 时存的是 **`entity_no`**，不是 `store_no`。
所以「这个自提点属于哪家店」表达不了，多店时无法判断货该送到哪个点。

### 3.6 B 端没有「当前门店」这个上下文

`b-app` 存了 `shbr_store_no`，但工作台、商品、订单、营销都不按它过滤。
店长登录后看到的是全公司的数据 —— 而 `mch_store_role` 明明已经限定了他能管哪几家。
**授权模型做了，消费方没接**（与本轮反复出现的「有录入没有消费方」同形状）。

---

## 4. 方案

### 4.0 一条贯穿的原则

> **`entity_no` 管钱与合规，`store_no` 管货与人。**

每加一张表的 `store_no` 之前先问：这件事是「公司层面的」还是「这家店的」。
答错会让迁移反复做——比如把结算改成按店，就等于承认每家店是独立纳税主体，
那不是产品决定能改的。

### 4.1 P0 · 库存分店（不做这个，其余都不能上线）

| 动作 | 说明 |
|---|---|
| 新表 `prd_store_stock(store_no, sku_no, stock, locked_stock)` | **不动 `prd_sku.stock`** —— 它作为「总量」保留，避免一次性迁移 |
| `StockPort` 增加 store 维度 | 下单时按 `cmd.pickupNo → store_no` 扣对应店的库存 |
| 单店兼容 | 只有一家店时，`store_no = 默认店`，行为与今天完全一致 |

**验收**：两家店各 10 件，A 店卖光后 B 店仍可下单；A 店下单不扣 B 店的数。

### 4.2 P1 · 商品上架分店

不改 `prd_goods`（商品定义仍在主体级——同一款米就是同一款米），
新增 `prd_store_goods(store_no, goods_no, on_sale, price_override)`。

**为什么是「上架关系」而不是「商品复制」**：复制会让改一次标题要改 N 遍，
而且历史订单的快照本来就固化了，不需要靠复制来保历史。

### 4.3 P2 · 营销分店

`mkt_campaign` 加 `store_no`（可空 = 全主体）。
可空是刻意的：「全店满减」与「新店开业满减」都要能表达。
`CampaignPort` 的三个方法各加一个 store 参数。

### 4.4 P3 · 自提点归属改到门店

`cmt_pickup_point.owner_ref` 在 `type=STORE` 时改存 `store_no`。
**要迁移历史数据**（现存的是 entity_no），且要在同一个版本里改完读写两侧。

### 4.5 P4 · 结算分店（业务已答）

> **资金按店统计；打款按结算账户；两种模式都要支持。**

不需要在「分开 or 合并」里二选一——把三个维度拆开之后，两种模式是配置的结果：
`store_no` 管统计、`pay_merchant_no` 管打款、`entity_no` 管合规。
两家店配同一个收款号就是合并，配不同的就是分开。

完整方案见 [多门店结算方案](./多门店结算方案.md)。

### 4.6 P5 · B 端接上「当前门店」上下文

工作台/商品/订单/营销按 `shbr_store_no` 过滤；店长只看得到自己管的店。
`mch_store_role` 已经有数据，缺的是消费方。

---

## 5. 建议的顺序与判据

```
P0 库存分店  ←── 不做这个，多门店不能开给真实商家（会出履约事故）
   ↓
P5 B 端门店上下文  ←── 与 P0 同批：库存分了，界面得能选店
   ↓
P1 商品上架分店
   ↓
P3 自提点归属（要数据迁移，单独一批）
   ↓
P2 营销分店
   ↓
P4 结算分店  ←── 卡在业务问题上，先回答再动
```

**每一批都要保证单店行为逐字不变** —— 现在所有真实商家都是单店，
任何一次多门店改造让单店行为变了，都是拿全量用户给一个还没人用的功能试错。

---

## 6. 已做：验证地基（2026-08-10）

按上面那条建议做了，结论是**地基比预想的更实**：

| 检查 | 结果 |
|---|---|
| 真实库 `ord_sub_order.store_no` 填充率 | **44 单 / 0 空 / 100%** |
| 后端 `/biz/order` 支不支持按门店过滤 | **早就支持**（`allStores` 参数） |
| 它区不区分「老板的全部」与「店员的全部」 | **区分**（`allowedStoresOrAll`） |
| 端上传过这个参数吗 | **从没传过** |

也就是说：**后端把多门店的订单作用域做完了，端上从没接**。
于是 b-app 订单页恒等于「当前门店」，而界面上既不显示是哪家店、也没有切换入口 ——
单店时看不出区别，多店老板会以为自己看到的是全部流水。

与本轮反复撞到的是同一形状：**有能力没有消费方**（营销活动建了没人读、
`mch_store_role` 授权了没人用、`shbr_store_no` 存了没人读）。

### 做了什么

· b-app 契约补 `allStores`，订单页接上门店范围切换
· 切换**只在真的有多家店时显示** —— 单店商家看到「全部门店/当前门店」只会疑惑
· 补 `MultiStoreOrderScopeTest` 两条：
  开第二家店后默认只看当前门店、`allStores=true` 才看到全部；
  以及**直接查库确认 store_no 真的被写了** ——
  只测接口的话，「过滤生效」与「一条都没写但恰好都被过滤掉」分不开

### 这对 P0 意味着什么

双写是可信的，门店过滤的语义也已经被想清楚（包括「空集合 ≠ 不过滤」这个
越权陷阱，后端注释里点明了）。**库存分店可以直接在这个地基上做**，
不需要先补一轮门店基础设施。

# 执行结果（2026-08-11）

P0–P5 六批全部落地。**全库带 `store_no` 的表从 3 张变成 8 张**
（新增 `prd_store_stock` / `prd_store_goods`，以及 `stl_bill` / `mkt_campaign` /
`mch_payment_merchant` 三张表的新列），`cmt_pickup_point.owner_ref` 的含义
从主体改成门店。

| 批次 | 做了什么 | 关键约束 |
|---|---|---|
| P0 库存分店 | `prd_store_stock` 可选覆盖层 | 无行 = 0，**不是**回退主体总量 |
| P5 B 端门店上下文 | 商品页显示当前门店的库存、能切店 | 两处口径必须一致，否则「显示有货、下单说没货」 |
| P4 结算分店 | 三个维度拆开：统计 / 结算 / 合规 | 快照，不实时解析；改号不影响历史流水 |
| P1 商品上架分店 | `prd_store_goods` 上架关系 | **不做分店价**（动的是算价链路，单独一批） |
| P3 自提点归属 | `owner_ref` → `store_no` + 数据迁移 | 顺带解锁「下单按自提点选店」 |
| P2 营销分店 | `mkt_campaign.store_no` | **只有满减**能限定门店 |

## 一条贯穿始终的语义

三处「主体级 → 门店级」的转换用的是**同一套规则**：

> 一条店级行都没有 → 走主体级，行为逐字不变；
> 有了任意一条 → 整体转为店级，**没有行的那家店视为「没有」**（0 件 / 未上架）。

反过来（「没有行就回退主体级」）会让商家给 A 店设完之后 B 店变成无限供应、
或者「只在 A 店卖」变成两家店都卖 —— 都与他刚做的事相反。

## 实测抓到、而单元测试没抓到的三个

| 现象 | 根因 |
|---|---|
| A 店下架把 B 店一起带下架 | 转成店级的**那一刻**只给被操作的店写了行。测试先把两店都显式上架过，正好绕开了转换时刻 |
| 结算页突然变空 | 按门店筛把没有门店归属的存量流水全滤掉了；而「一条没有」与「没有结算单」长得一样 |
| 下架再上架 500 | 与多门店无关的**既有缺陷**：下架是逻辑删，唯一键不含 deleted，插同一对必然撞键 |

**「迁移瞬间」是最容易被跳过的用例**：写用例时习惯先把状态摆好，
而缺陷恰恰发生在从旧状态切到新状态的那一步。

## 仍未做的（各有明确原因）

| 项 | 为什么还没做 |
|---|---|
| **分店价** | 动的是算价链路（详情价 → 购物车 → 下单 → 营销叠加 → 订单快照），与「卖不卖」不是一个风险等级。**没有先建 price_override 列放着** —— 那正是本轮反复在修的「有字段没消费方」 |
| **C 端按门店浏览** | C 端没有这个入口：顾客按社区看货，「门店主页」其实是主体主页。要做得先定「顾客怎么选店」 |
| **限时特价 / 买赠分店** | 它们改的是商品页展示，而浏览时自提点还没选 —— 会让页面价与下单价打架。已在创建时拒绝（70005） |
| **店铺券分店** | 券有自己的核销链路，门店限定该在券侧做 |
| **多商户号的真实进件** | `mch_payment_merchant` 已支持每店一条，但落地前要核实微信侧「同一主体可进件多少个特约商户号」 |

## 一个环境约束

多门店要显式打开：`SHOP_STORE_MAX_PER_ENTITY=3`（默认 1）。
这是刻意的 —— **放开多门店是一次显式的配置变更，而不是升个版就悄悄变了**。
