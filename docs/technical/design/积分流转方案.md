## 〇、三条支柱

| # | 规则 | 解决什么 |
|:--:|------|---------|
| **①** | **积分在订单完成时产生，在下单时扣减，在订单完成时才兑付** | 三个时点各自防一类问题（§1） |
| **②** | **能发才能收：`canIssue == canAccept`，同一个开关** | **搭便车** —— 只收不发等于白蹭别人的客流（§2） |
| **③** | **积分收支走独立账期结算单，不并入订单结算单** | 兑付时点晚于结算单生成时点（§4，**v1 的错误在此修正**） |
| **④** | **商家积分账户 = 额度台账（发放即占用，授信兜底）+ 资金台账（兑付才付钱）** | 在债务发生那一刻就能拦住超发与跑路（§4bis） |

其上是灰度与强制开（§5）与平台监控（§6）。

## 一、积分何时产生、何时扣、何时兑付

**三个动作、三个时点，刻意不合并**：

```
下单 ──────→ 支付 ──────→ 备货 ──────→ 核销/收货 ─→ COMPLETED
  │                                                      │
  │ ② 扣减（用户 −N）                         ① 产生（用户 +M）
  │   立即扣，防「同时下多单花同一笔分」        订单完成才发，防「拿分即退款」
  │                                                      │
  └──────────────────────────────────────────→ ③ 兑付（商家之间结账）
                                             完成才兑付，取消/退款则不发生
```

| 动作 | 时点 | 为什么是这个时点 |
|------|------|-----------------|
| **产生** | 订单 `COMPLETED` | 支付即发的话，「下单 → 拿分 → 立刻花掉 → 退款」是白拿。完成才发从根上堵掉 |
| **扣减** | 下单即扣 | 支付后才扣的话，同一笔分可以同时下多个单 |
| **兑付** | 订单 `COMPLETED` | 订单还可能取消/退款，那时用户的分要退回，**商家之间的账就不该发生过** |

### 1.1 产生多少

| 项 | 规则 |
|----|------|
| 发放维度 | **按商品配置**（生鲜 30 / 家电清洗 500 / 储值卡 0） |
| 未配置 | 按成交额兜底比例（现千分之一） |
| **赠品不发** | 否则「买赠 + 积分」可叠出套利 |
| **计算基数** | **商家实收部分**，不含运费、不含平台券补贴 —— 商家没收到的钱不该由他出积分 |
| 上限 | 平台设发放比例上限，商家不能自定义超出（防超发套现） |

### 1.2 扣减多少

| 项 | 值 | 理由 |
|----|---|------|
| 汇率 | 100 分 = 1 元（P2 待定） | — |
| 抵扣上限 | **券后金额的 30%** | 整单抵扣 = 商家一分钱收不到 |
| 运费不参与 | — | 运费要付给运力，用积分抵等于平台自掏腰包 |
| 顺序 | **券先、积分后** | 反过来会让用户先用积分压低金额，导致券的门槛达不到 |

## 二、能发才能收（**本方案的机制核心**）

### 2.1 规则

> **`merchant.points_enabled` 一个开关同时决定「能发」与「能收」。**
> 开 = 我给顾客发分，也接受别人的分；关 = 两样都没有。**不存在只收不发或只发不收。**

### 2.2 为什么必须对称

| 若允许只收不发 | 若允许只发不收 |
|---------------|---------------|
| 商家白拿别人送来的客流，自己不贡献。理性商家全会这么选，于是**没人发分，积分归零** | 商家单方面付出，客人被推去别家却推不回来。他很快会关掉 |

**对称性让「参与」变成一个整体决定**：想享受社区的积分网络，就得自己也往里放水。
这不是道德约束，是**机制上不给搭便车留位置** —— 与 ADR-003「不做事前审核，靠机制约束」是同一种思路。

### 2.3 关掉开关时，存量怎么办（**关键边界**）

**关闭只影响将来，不消灭已发生的债务。**

| 对象 | 关闭后 |
|------|--------|
| 已发出、用户手里未花的分 | **仍然有效**，用户可在**其他开启的商家**使用 |
| 该商家的存量或有负债 | **仍需承担** —— 别人在别处花掉他发的分，他照样要付 |
| 新订单发放 | 停止 |
| 顾客拿分来他店里抵扣 | **不可用**，端上明确提示「本店暂不支持积分抵扣」 |

> **不能一关了之**：允许关闭即免债的话，商家会「先猛发分把客人引来，再关开关赖账」。
> 存量债务跟着商家走，直到过期或用完 —— 这一条要写进商家协议。

### 2.4 端上如何表达

| 端 | 表达 |
|----|------|
| C 端商详/结算 | 不支持的店：**不显示积分抵扣入口**，而不是显示了再报错 |
| C 端积分账户 | 「可在 XX 个社区商家使用」+ 可用商家列表 |
| B 端 | 开关旁边直接写清楚：「开启后可向顾客发放积分，同时接受其他商家的积分」 |

## 三、账户模型

| 账本 | 主体 | 记什么 | 流水类型 |
|------|------|--------|---------|
| **用户积分账户** | `userNo` | 积分**个数** | `EARN` · `USE` · `REFUND` · `EXPIRE` |
| **商家积分账本** | `merchantNo` | **钱** | `ISSUE`(或有负债) · `REDEEM_OUT`(我发的分被花，支出) · `REDEEM_IN`(别人的分在我这花，收入) · `SETTLE` |

两点不变量：

1. **余额由流水推导，不单独存字段**。积分能折成钱，两处存迟早对不上，对不上就是资损。
   每条流水带 `balance_after` 快照，用于定位「从哪条开始错的」。
2. **汇率在兑付那一刻固化进商家账本**。之后调汇率不影响已发生的账。

> **`ISSUE` 与 `REDEEM_OUT` 必须分开**：发出去但没被花掉的分是**或有负债**，
> 不该进商家当期成本 —— 那笔钱可能永远不会被花（过期）。
> 只有被核销的那一刻，它才变成真实的钱。这一条决定商家看到的数字可不可信。

## 四、如何结算（**修正 v1 的时点错误**）

### 4.1 v1 错在哪

v1 写的是「积分收支进订单结算单的 `gross`」。**这是错的**：

```
支付成功 ──→ 生成订单结算单（M7 已实现，同事务）
                    ↓  T+n 天
              订单完成 ──→ 积分才兑付
                           此时结算单**早就生成了**，甚至可能已经分账
```

**兑付时点晚于结算单生成时点**，塞不进去。硬塞的话要么改已分账的单（要走回退，正是 M5/M7
极力避免的），要么把结算单延迟到订单完成（商家要多等好几天才拿到货款，不可接受）。

### 4.2 修正：独立的积分账期结算单

**货款按订单结算（即时），积分按账期结算（周期性），两条线并行。**

```
stl_bill         每个子订单一张，支付成功即生成 —— 货款
stl_points_bill  每个商家每期一张，账期结束时生成 —— 积分净额
```

积分账期单的构成：

```
本期积分收入  = Σ REDEEM_IN    别人发的分在我这儿被花掉
本期积分支出  = Σ REDEEM_OUT   我发的分在别人那儿被花掉
本期净额     = 收入 − 支出
              ├─ 净额 > 0 → 平台**付给**商家（并入下期分账）
              └─ 净额 < 0 → 平台**从商家货款里扣**
```

**自发自用不进账期单**：本店发、本店花，直接冲抵，不产生任何跨商家账目 ——
既省一次清算，也顺手堵掉「自己刷自己」（§6.3）。

### 4.3 为什么独立而不是并入

| 并入订单结算单（v1） | 独立账期单（v2） |
|---------------------|-----------------|
| 时点对不上，要么改已分账的单、要么拖延货款 | 两条线各按各的节奏 |
| 商家看到的 gross 里混了别的订单的积分，无法验算 | 货款一单一验，积分一期一验，**都能自己算清楚** |
| 积分口径变化会污染货款对账 | 互不影响 |

> 代价是商家要看两张单。但**「一张看不懂的单」比「两张看得懂的单」糟得多** ——
> 商家对账时每一次心算都是一次客诉的机会。

### 4.4 商家看到的（B 端）

```
【货款结算】本期 12 笔    实收 ¥1,842.00
【积分结算】本期账期 8 月
   积分收入  +204.00   （别人的分在我这儿花掉 20400 分）
   积分支出  −128.00   （我发的分在别人那儿花掉 12800 分）
   ─────────────────
   本期净额  + 76.00   → 并入 9 月 1 日货款一起到账
```

**商家看的是钱，不是分**。给商家看「发出了 12800 积分」没有意义——积分个数是平台的内部单位。

## 四之二、资金流：钱到底怎么走（**先纠正一个前提**）

### 4bis.1 「平台收到的是积分」——这个说法不成立

用户用 3000 分（=30 元）抵扣，在 B 店买 100 元的货，实付 70 元现金。这 3000 分是 **A 店**发的。

> ❗ **平台并没有「收到积分」。平台收到的是「少了 30 元的现金」。**
>
> 积分不是资产，是**债务凭证** —— 它代表「A 店欠这个生态 30 元」。
> 用户花掉它的那一刻，这笔债务从「A 欠用户」转成了「A 欠 B」，平台只是记账人与中转方。

把积分当成平台的资产，会推导出一个错误结论：平台账上多了一笔积分资产、少了一笔现金。
实际上平台账上**什么都没多**，只是替 B 记了一笔应收、替 A 记了一笔应付。

### 4bis.2 三方的钱

| 主体 | 这一单发生了什么 |
|------|-----------------|
| **用户** | 付 70 元现金 + 3000 分。账户 −3000 分 |
| **B 店（收款方）** | 卖了 100 元的货，**应收 100 元**（减佣金）。但当期只从支付通道分到 70 元 → **差 30 元** |
| **A 店（发放方）** | 没参与这笔交易，但他发的分被兑付了 → **欠 30 元** |
| **平台** | 现金进 70、分账出 70（**分账只能分实收，这是支付通道的物理约束**）。30 元的缺口靠积分账期轧平 |

```
T0 支付   用户 ─70元→ 平台 ─70元(减佣金)→ B          ← 走微信分账，只能分实收
T+n 完成  积分兑付：A 记支出 30，B 记收入 30           ← 只记账，不动钱
月末      积分账期结算：A 的货款扣 30，B 的货款加 30    ← 钱在这一刻才动
```

> **为什么分账时不能直接给 B 补 30 元**：微信支付分账只能分「这笔订单实际收到的钱」，
> 平台手里就只有 70。要补 30 就得平台先垫付，再向 A 追收 —— 那平台就承担了 A 跑路的风险。
> 让缺口留在账期里轧平，平台**全程零垫付**。

### 4bis.3 采纳「商家积分账户」模型 —— 但它是**两本账**

你说的「专有积分账户，发放时从里面抵扣」**采纳**。但必须先拆开一件事，否则会重复扣钱：

> **「能发多少」和「要付多少钱」是两本账，不能合成一个余额。**

| | 额度台账（单位：**分**） | 资金台账（单位：**元**） |
|---|---|---|
| 管什么 | 我**还能发**多少分 | 我这期**要收/要付**多少钱 |
| 发放 ISSUE | **−N**（占用额度） | 不动 —— 发出去的分可能永远没人花 |
| 我发的分被花掉 REDEEM_OUT | **不动**（发放时已占用） | **−金额**（真实成本，此刻才发生） |
| 别人的分在我这花 REDEEM_IN | **不动** | **+金额** |
| 我发的分过期 EXPIRE | **+N**（额度释放） | 不动 —— 从没花过，本来就不用付 |
| 账期结算 SETTLE | 不动 | 清零，并入货款 |

两条不能违反的规则：

- **REDEEM_OUT 不再扣额度** —— 发放时已经占用过了。再扣一次 = 同一笔分占两次额度。
- **REDEEM_IN 不增加额度** —— 它已经给了你**现金**。再给额度 = 同一笔收入拿两遍好处。

```
额度台账：已发放未兑付未过期 ≤ 授信额度      ← 纯风控，防超发/跑路
资金台账：REDEEM_IN − REDEEM_OUT → 账期单   ← 纯钱，§4.2
```

> **为什么额度在发放时就占用**：这是唯一能在**债务发生的那一刻**拦住它的时点。
> 等兑付才发现超了，分已经在用户手里了，拦不住了。

### 4bis.4 额度不足怎么办：授信兜底，不是拒绝发放

新商家额度台账占用为 0、可用为 0。若「没额度就不能发」，积分对新商家永远启动不了。
所以额度不靠预存获得，**靠授信**：

```
授信额度 = min(固定上限, 近 3 期平均货款 × 系数)
可发放   = 授信额度 − 已发放未兑付未过期

在授信内   → 正常发放
超出授信   → **自动停止发放**；按发收对称（§2），同时停止接收
```

| 商家类型 | 授信额度 | 理由 |
|---------|---------|------|
| 新入驻 | 低（如 200 元额度对应的分） | 没有货款流水做担保，防「猛发分 → 跑路」 |
| 经营满 3 期 | 按货款流水核定 | 有真实收入兜底 |

> **授信额度就是平台的最大风险敞口** —— 商家跑路能带走的上限，正好等于他的授信占用。
> 额度与货款挂钩 = 每一分债务背后都有一条现金流兜着。

### 4bis.5 所以「从专有积分账户抵扣」= 额度台账的那一次扣减

**商家不需要先花钱买积分**，额度台账不是预付费钱包 —— 里面是授信，不是现金。
真正的钱只在**兑付发生时**才动，而且是从货款里扣，不是提前预存。

这是刻意的：让商家先掏钱买积分，等于给一个还没被验证的功能设付费门槛，
小商家不会买单，积分永远启动不了（同 ADR-004「降低商家参与门槛」的取向）。

## 四之四、平台积分清算账户

### 4quater.1 为什么需要它

§4bis 里跨商家的钱是「A 的货款扣 30 → B 的货款加 30」，看起来两两轧平不需要中间账户。
但有三件事没有它就没地方落：

| 场景 | 没有池子会怎样 |
|------|--------------|
| **A 当期货款不够扣** | B 该拿的 30 元没有来源。要么拖欠 B（B 立刻退出积分），要么平台临时垫（无科目可记） |
| **A 跑路 / 注销** | 存量债务永远收不回，但 B 已经把货卖了。**坏账必须有人承接** |
| **平台自己发的积分**（拉新、客诉补偿、活动） | 没有发放商家可扣，成本无处可出 |

所以池子不是可选项 —— 它是**跨商家清算必然要有的中间科目**。

### 4quater.2 账户构成

`stl_points_pool` —— 单位是**钱**，不是分：

| 方向 | 项 | 说明 |
|:--:|------|------|
| **收** | 净流出商家的账期扣款 | 发分多、被别处花掉的商家付进来 |
| **收** | 坏账追偿回款 | 跑路商家后续追回的部分 |
| **收** | 保证金/授信违约金 | 超授信未补足的处置（P13） |
| **付** | 净流入商家的账期付款 | 接客流多的商家拿走 |
| **付** | **平台自发积分被兑付的成本** | 平台自己掏钱，唯一一处平台真实承担成本的地方 |
| **付** | **坏账核销** | 商家跑路后 B 侧的缺口，由池子补上 |

### 4quater.3 恒等式（把 §6.4 的第三条对账显性化）

```
Σ 全平台商家积分账期净额  +  平台池子本期净额  =  0
```

这条在 v2 里是一条对账规则，现在它变成**一个账户的余额**：

> **池子余额 ≠ 0，差额就是坏账敞口。**
> 池子长期为负 = 有商家欠的钱没收回来，平台在实质垫付。
> 这比任何监控指标都直接 —— **一个数字就能回答「积分这摊事亏没亏钱」**。

风险准备金规模建议按**全平台授信占用总额**的一定比例计提（§4bis.4 的授信额度就是最大敞口）。

### 4quater.4 商家跑路时的处置链

```
超授信未补足 ──→ 停发停收（§4bis.4）
      │
      └─ 逾期 N 期 ──→ 转催收，债务不消灭（§2.3）
                │
                └─ 确认无法追回 ──→ **池子核销**
                        B 侧照付，用户手里的分照样能花
```

关键取向：**坏账由池子吃掉，不传导给用户和收单商家**。
让 B 承担「A 跑路」的损失，等于告诉所有商家「接别人的积分有风险」，
发收对称（§2）建立起来的参与意愿会瞬间瓦解。

### 4quater.5 ⚠️ 合规红线：这个账户**不能**做成兑付资金池

这是本节最要紧的一条。同一个账户，定性不同，监管等级差一个量级：

| | 清算备付账户（**采纳**） | 兑付资金池（**不做**） |
|---|---|---|
| 资金来源 | 只来自商家货款轧差 | 用户/商家充值买积分 |
| 平台角色 | 商家之间的**记账与清算中介** | 积分的**发行人与兑付人** |
| 谁对用户负责 | 发放商家 | 平台 |
| 会计 | 往来科目 | **递延收益 / 平台负债** |
| 监管 | 一般商事清算 | 跨商户通用 + 可兑付 ≈ **多用途预付卡，需支付业务许可** |

保住「清算备付」定性的三条硬约束，**代码层面必须拦死**：

1. **积分不可充值** —— 用户和商家都不能拿钱买积分。积分只能由交易产生（§1.1）。
2. **积分不可提现、不可转让** —— 只能在交易中抵扣。
3. **平台不承诺兑付** —— 兑付责任始终在发放商家（ADR-006 §1）。池子只是清算通道，
   坏账核销是平台的**商业损失**，不是对用户的兑付义务。

> 破了任意一条，积分就从「商家折扣的记账工具」变成「平台发行的支付凭证」。
> 这不是文档措辞问题 —— **三条约束要写成代码里没有对应接口**（没有充值 API、
> 没有提现 API、没有转赠 API），而不是靠后台配置关掉。

## 四之三、积分明细（商家看什么、平台看什么）

### 4ter.1 商家侧：积分账户流水（B 端）

**每一笔都要能追到订单**，否则商家对不了账：

| 时间 | 类型 | 额度变动 | 金额 | 关联 |
|------|------|---------|------|------|
| 08-03 | 发放给顾客 | −300 分 | — | 订单 SUB-8823（张先生） |
| 08-05 | **收到积分**（别人的分在我这花） | — | **+20.00** | 订单 SUB-9012（李女士，**老张粮油发放**） |
| 08-09 | 我发的分在别处被花 | — | **−12.80** | 老李水果核销，我 07-20 发放 |
| 08-12 | 我发的分过期 | **+150 分** | — | 07-12 发放给王先生，未使用，额度释放 |
| 08-31 | 账期结算 | — | **+76.00** | 积分账期单 PB-202608，并入 9/1 货款 |

顶部还要有一行状态条，这是商家每天真正会看的：

```
可发放额度  1,240 / 2,000 分   （授信 2,000，已占用 760）
本期积分净额  +76.00 元        （9/1 随货款到账）
```

三个要点：
- **同时给「分」和「钱」两列** —— 商家用钱思考，但对账时需要看分。
- **「收到积分」要写明是谁发的**（老张粮油）—— 这是本方案的价值所在：
  商家能直观看到「隔壁店把客人送到我这儿来了」。
- **额度列与金额列分开** —— 混在一列商家一定会问「为什么发了 300 分只扣 3 块又没扣」（§4bis.3）。
- **过期释放额度单独成行** —— 商家会问「我发出去的分怎么又回来了」，写清楚比解释十次强。

### 4ter.2 平台侧：全量 + 授信

| 视图 | 内容 |
|------|------|
| 商家积分账户总表 | 授信额度、已占用、可发放、本期资金净额、是否已触顶停发 |
| **授信风险榜** | 按「授信占用率」排序 —— 占用高的是跑路风险最高的 |
| 单商家账户流水 | 与商家看到的同一份（客服争议时要能对着同一张表说话） |
| 跨商家流向图 | 谁在喂谁 —— 净流出榜的可视化（§6.2） |
| 全平台积分负债表 | Σ 用户余额 = Σ 商家已发未兑付；不等就是记错了 |

## 五、灰度与强制开

### 5.1 三级开关，从上往下收敛

| 层级 | 开关 | 谁控制 | 语义 |
|:---:|------|--------|------|
| L1 | `FEATURES.points` | 平台 | 全局总闸。关 = 全平台无积分（现状） |
| L2 | `community.points_enabled` | 平台（社区运营） | **按社区灰度** |
| L3 | `merchant.points_enabled` | **商家自己** | 发收对称的那个开关（§2） |

**任一层关闭即不可用**。L2 存在的理由：积分的价值来自商家密度，
只有 2 家店的社区开积分，跨店通用几乎等于商家专属，反而增加解释成本。

### 5.2 建议的灰度节奏

| 阶段 | 范围 | 通过标准 |
|:---:|------|---------|
| G1 | 1 个商家密度最高的社区 | 连续跑满**一个完整账期**且日终对账连续平账 |
| G2 | 3–5 个社区 | 无清算争议工单；净流出商家未出现批量关闭 |
| G3 | 全平台开放（商家仍可自选） | — |

> 积分是能折成钱的东西。第一个账期出错的代价是商家信任，那个东西掉了很难再建起来。

### 5.3 强制开（按行业属性）

**将来平台可对特定类目/行业强制开启**（L3 由平台接管，商家不可关）：

| 判据 | 举例 | 为什么这类该强制 |
|------|------|-----------------|
| **高频复购** | 生鲜、粮油、日用 | 最受益于社区流量循环；也最容易只收不发 |
| **高毛利** | 家政、维修、服务 | 积分成本占比低，承受得起 |
| **平台重点扶持类目** | 运营策略决定 | — |

**强制开必须满足三个前提**（否则会引发商家反弹）：

1. **提前公示**：新入驻商家在协议里写明；存量商家给不少于 30 天的通知期。
2. **费率补偿**：强制开的类目应在佣金档上给出对冲（与 R16 的 `trafficSource` 分档并列）。
3. **可申诉**：极端毛利结构的商家（如代卖、寄售）可申请豁免，走平台审核。

> ⚠️ **强制开是一把双刃剑**：它能保证网络效应启动，但商家会算账。
> 如果一个商家长期是净流出方（发的比收的多）却被强制参与，他会离开平台。
> 因此**强制开必须与 §6 的监控联动** —— 发现某类目系统性净流出，就该调整规则而不是硬压。

### 5.4 数据表达

```sql
-- 三个开关落在三张已有的表上，不新建配置表
sys_feature_flag.points_enabled       -- L1
cmt_community.points_enabled          -- L2
usr_merchant.points_enabled           -- L3（发收对称）
usr_merchant.points_forced            -- L3 被平台强制开启，商家不可关
```

## 六、平台监控

积分是**能折成钱的凭证**，监控不是运营看板，是风控与财务的一部分。

### 6.1 总量指标（每日）

| 指标 | 含义 | 异常信号 |
|------|------|---------|
| **沉淀量** | 已发放未使用 = 全商家或有负债总额 | 持续走高 = 激励无效；骤降 = 集中兑付，查套利 |
| 发放量 / 使用量 | 当日新增与消耗 | 使用量骤增且集中在少数商家 → 查 |
| 过期量 | 当期过期作废 | 过高说明有效期或提醒有问题 |
| **兑付率** | 使用量 ÷ 发放量（滚动 90 天） | 长期 <10% 说明积分没人当回事，激励白花钱 |

### 6.2 商家维度（每期）

| 指标 | 用途 |
|------|------|
| **净流入 / 净流出** | 谁在被喂、谁在喂别人。**长期净流出方是流失风险最高的商家** |
| 发收比 | 发放金额 ÷ 收到金额，长期偏离 1 的要人工看 |
| 自发自用占比 | 高 = 积分没有跨店流动，网络效应没发生（或在刷） |

> **净流出榜是平台最该主动看的一张表**：这些商家在为社区贡献流量却没拿到回报。
> 该做的是给他们导流或调费率，而不是等他们自己关开关走人。
> 这也是「强制开」不能脱离监控单独执行的原因。

### 6.3 风控

「商家自发自收套现」机制上防不住，但可以让它**不划算**且**可发现**：

| 手段 | 效果 |
|------|------|
| **积分不可提现、只可抵扣** | 唯一出口是真实交易，套现必须先真实付钱，成本 > 收益 |
| **自发自用不产生跨商家账目** | 自己刷自己不产生任何现金流 |
| **发放比例上限由平台设** | 断掉「超发」这条路 |
| 同一用户在同一商家的兑付集中度告警 | 「一个账号总在一家店花分」是典型套利特征 |
| 新商家开启后前 N 天发放限额 | 防「开店猛发分 → 关店赖账」 |

> 这几条的共同点：**不试图证明某笔交易是不是刷的**（做不到），
> 而是让刷的收益低于成本，并让异常模式浮出来给人看。

### 6.4 对账（每日三方核对）

```
① Σ 用户积分流水（EARN − USE + REFUND − EXPIRE）  = 全平台用户积分余额
② Σ 商家账本已兑付部分                              = Σ 用户 USE 中已完成订单的部分
③ Σ 全平台积分账期净额                              = 0   ← 跨商家轧差必然归零
```

**③ 是这套设计最强的自检**：跨商家清算是零和的，一方的收入必然是另一方的支出。
全平台净额不为零，只可能是记账错了 —— 这条约束比任何人工核对都可靠。

对账不平时**锁定当期积分结算**（货款结算不受影响，两条线独立正是好处）：
宁可积分晚结一期，不能错结一分。
