## L1 · 定位

TDD 回答「做成什么样」，本篇回答「**按什么顺序、在哪个环境、谁来做、做到什么程度算完、出问题怎么退**」。

一条主线：**同一个构件，靠配置决定部署成一套还是两套**。测试环境一套、装下全部业态，逼出通用性问题；生产两套，电商的下单锁库存与设备的批量作业互不拖累。两种部署之间的差异**只允许出现在环境文件里**，代码里不出现「我是哪套」的判断。

## L2 · 结构

### 一、环境与部署拓扑

| 项 | 本机开发 | 测试环境（共用一套） | 生产 · 电商套 | 生产 · 设备套 |
|---|---|---|---|---|
| 实例代号 `inventory.instance.code` | `DEV` | `TEST` | `SHOP` | `DEVICE` |
| 放行的系统 `inventory.instance.allowed-systems` | 全部 | `SHOP,SHAREHUB,CHARGING` | `SHOP` | `SHAREHUB,CHARGING` |
| 进程 | IDE / `mvn spring-boot:run` | `neargo-inventory@test` | `neargo-inventory@shop` | `neargo-inventory@device` |
| 端口（待核） | 8086 | 8086 | 8086 | 8087 |
| 库 | 本机 MySQL 9.7 `inventory_dev` | `inventory_test`（一个库装全部业态） | **`ai_shop_inv` 原地升级** | **新建 `neargo_inv_device`**（空库跑迁移） |
| 调用方 | 测试 | ai-shop 测试实例 · ShareHub 测试实例 · 充电桩模拟器 | ai-shop `shop-app` | ShareHub 后端 · 充电桩后端 |
| 任务服务目标 | 本机 | `INVENTORY_TEST` | `INVENTORY_SHOP`（系统组 `SHOP`） | `INVENTORY_DEVICE`（系统组 `SHAREHUB`） |
| 上线时间 | M1 起 | M1 起 | **M8**（此前商城内嵌直连 `ai_shop_inv`） | **M6** |
| 堆 | — | 512m | 384m | 384m |

**为什么两套生产用不同的库，而不是同库两实例**：拆实例是为了隔离负荷与故障，同库仍共享连接、锁与 IO —— 设备的一次全仓盘点照样能拖慢商城锁库存。分库后两套之间**没有任何共享资源**，只共享构件版本。

**两套之间怎么防串**：

| 防线 | 做法 | 防住什么 |
|---|---|---|
| 实例放行系统 | `inventory-guard` 解析凭证后，系统不在 `allowed-systems` 内 → 403 `inventory.instance.system_not_served` | ShareHub 配错地址打到电商套，写进商城的库 |
| 凭证分库签发 | 凭证只在所属实例的库里存在；另一套查不到 → 401 | 同上，第二道 |
| 健康检查带实例代号 | `/actuator/info` 返回 `instance.code` 与 `allowed-systems`；调用方启动自检比对 | 部署时 env 文件拷错 |
| 监控分开 | 告警名带实例代号 | 一套出事误判成另一套 |

### 通用性验证（贯穿 M2 ~ M5，测试环境专属）

测试环境共用一套的全部意义在这里。每个里程碑出口都要求下面五项为绿：

| # | 验证 | 做法 | 发现什么问题 |
|---|---|---|---|
| G1 | **跨业态回归套件** | 同一组核心场景（入库、出库、盘点、汇总、幂等、事件）按四份档案参数化，**在同一实例、同一库上依次跑** | 内核里藏着某个业态的假设（例：默认按数量、默认无收货方） |
| G2 | **隔离** | 用 A 系统凭证读写 B 系统业主；用 A 业主的 SN / 单号 / 外部目标引用去碰 B 业主 | 唯一键或查询漏带 `owner_id` / `system_code` |
| G3 | **混合负载** | 商城预留压测（持续）+ 同时跑设备批量入库 2 000 SN、全仓盘点开盘 | 记录预留 P95 的劣化幅度 —— 这是生产分两套的量化依据，也是将来「能不能合回去」的判据 |
| G4 | **档案切换** | 改档案版本后跑历史单据查询与新单据过账 | `profile_version` 解释不了历史 |
| G5 | **内核无业态分支** | 静态检查：`inventory-domain` 不出现 `SHAREHUB` / `CHARGING` / `MERCHANT` / `SITE` 等档案值字面量 | 业态差异漏进代码 |

G5 写成 ArchUnit / 文本扫描规则进 pre-push；G1 ~ G4 进测试环境的每日流水线。

### M6 · 设备套上线（第 15 ~ 17.5 周）

| 步骤 | 做法 |
|---|---|
| T6.1 | ShareHub 迁移工具：测试环境 dry-run → 差异报告评审 → apply → 重复 apply 无变化 |
| T6.2 | 监控告警（两套分开命名） |
| T6.3 | 故障演练（库停、重启、事件重放、回包丢失） |
| T6.4 | systemd 单元、env 模板、备份、回滚手册 |
| **生产形态演练** | 上线前在测试机按生产形态**临时起两套**（`SHOP` + `DEVICE`，两个库），跑 G1、G2 与 AC-28；证明「一套能跑」推得出「两套能跑」 |

**上线步骤（设备套）**：

1. 建库 `neargo_inv_device`、独立账号；`backup-to-cos.sh` 的 `DBS` 加上它（脚本注释写明：漏备一个库的事故 2026-09-16 发生过）。
2. 放 jar 与 `inventory.env`（`DEVICE`、`SHAREHUB,CHARGING`）；`systemctl enable --now neargo-inventory@device`；首启跑迁移（空库）。
3. 任务服务登记 `INVENTORY_DEVICE`；平台运维接口开通 ShareHub 业主、签凭证、装档案。
4. ShareHub 生产配置指向 `127.0.0.1:8087`；启动自检比对 `/actuator/info` 的实例代号。
5. 迁移工具生产 dry-run → 评审差异 → apply。
6. ShareHub 切单一写权：旧仓储模块停写，仓储页改读写库存服务。
7. 观察 3 天：命令失败率、冲突率、事件积压、游标延迟。

**回滚**：ShareHub 侧切回旧仓储模块（第 6 步前的状态保留到观察期结束）；库存服务停机不影响电商。迁移数据可整库丢弃重来（空库起步、迁移可重复）。

**出口**：ShareHub 生产在设备套上运行满观察期；电商零影响。

### M7 · 第二业态：充电桩（第 17.5 ~ 19.5 周，可与 M8 并行）

T7.1 ~ T7.3。测试环境装充电桩档案、跑 AC-17。生产：充电桩后端就绪后**接入设备套**（档案 + 凭证，不新部署）。

**出口**：AC-17 绿；`inventory-domain` 相对 M6 只多 T7.1、T7.2 的改动（`git diff --stat` 为证）。

### M8 · 电商套上线与商城切流（第 17.5 ~ 22.5 周）

| 步骤 | 做法 |
|---|---|
| T8.1 | 预留能力包对外、`expires_at` 回收 |
| T8.2 | ai-shop 订单侧 `confirm` 移出事务、写 Outbox |
| T8.3 | `invbridge` 与控制器改调客户端；超时与熔断（熔断即拒单） |
| T8.4 | 餐饮生产扣料经 Outbox |
| T8.5 | `write_authority` 翻转工具与对账 |
| 测试环境 | ai-shop 测试实例切为调服务；**测试环境内所有商城业主翻到 `SVC`**，跑商城全量回归 + G1 ~ G3 |

**上线步骤（电商套）**：

1. **先备份** `ai_shop_inv`（迁移前导出到 `/data/backup/ai-shop/predeploy/`，并上传 COS）。
2. 放 jar 与 `inventory.env`（`SHOP`、`SHOP`、库 `ai_shop_inv`、端口 8086）；启动跑 V16 起的迁移（原地升级：补 `system_code = SHOP`、`write_authority = EMBEDDED`、默认档案）。此时商城仍内嵌、写入方仍是 `EMBEDDED`，服务只读。
3. 任务服务登记 `INVENTORY_SHOP`；签 `SHOP` 凭证给 shop-app。
4. 发版 shop-app（含 T8.2、T8.3，开关默认走内嵌）。
5. **按业主灰度**：先选一个内部测试商家 → 翻 `SVC` → 跑下单、支付、关单、退款、进货、盘点 → 对账（余额、流水逐条）→ 观察 1 天 → 分批翻其余业主。生产订单今天为 0，批次可以大。
6. 全部翻完 + 观察期 2 周 → T8.6 删除内嵌装配（单独一次发版）。

**回滚**：任一业主异常 → 翻回 `EMBEDDED`（AC-27 保证两边数据一致）；整体异常 → shop-app 开关切回内嵌、停电商套。T8.6 之前回滚路径始终存在。

**出口**：所有商城业主 `SVC`；AC-20、25 ~ 27 绿；T8.6 完成后 `shop-app` 不再依赖 `inventory-domain`。

## L4 · 风险与待确认

### 七、执行风险

| 风险 | 对策 |
|---|---|
| M1 大移动与其他会话撞车 | 冻结窗口 + 每次提交只移一类 + 显式路径提交 |
| 测试环境「一套能跑」掩盖「两套才暴露」的问题（端口、账号、任务目标、凭证分库） | M6、M8 上线前必做生产形态演练 |
| 测试环境共库让隔离缺陷被数据量掩盖 | G2 专测隔离；G5 静态扫描 |
| 电商套原地升级 `ai_shop_inv` 失败 | 迁移前导出；迁移在测试环境用生产脱敏副本先跑；失败即回滚到导出 |
| ShareHub 配错实例地址 | 实例放行系统 + 凭证分库 + 启动自检 |
| 单机内存不足 | 实测后定堆；两套负荷低，先压它们 |
| 契约冻结后 ShareHub 发现缺口 | 只做向后兼容的增加；破坏性变更走新路径并行 |
