## 一、B 端与 C 端不是同一种测法（L1）

C 端一个人一条路走到底；**B 端的核心风险是「谁能看到什么」**——
六个角色 × 13 个权限码 × 逐店授权，错一格就是店员看到了营业额、配送员翻到了全店订单。

所以本文的重心不在功能能不能用，在**能不能被不该用的人用**。
每个域下的功能用例只列主路径，权限用例单独成 §四，且是 P0 主体。

### 已知的两类历史缺陷，用例里都留了对应条目

| 类型 | 出处 | 本文对应 |
|---|---|---|
| **mock 跑通、真链路断** | 两轮联调 20 条：核销失败显示成成功、编辑丢主图/丢译文、审核中显示成已下架…… | 所有用例**必须在 `VITE_USE_MOCK=0` 下跑**，§二 写死了 |
| **契约有、后端不发** | 6 条同根因：售后时间显示 NaN、C 端「商家回复」不显示、分拣单 `buyers` 抛错 | 涉及跨端可见的用例都要求**去 C 端回看一眼**（TB-B-7-3、TB-B-9-2） |

### 现在测不了的（🚫，不计入通过率）

| 链路 | 为什么 | 解除条件 |
|---|---|---|
| 支付/收款到账 | `OrderServiceImpl` 返回 `stub_<orderNo>` | 微信认证 + 商户号 + 接 JSAPI 下单 |
| 进件真实通过 | 收付通进件要平台服务商资质 | 见[小程序上线指南](./小程序上线指南.md) §一 |
| 营业执照 OCR | 识别模型未接 | — |
| 平台人工审核 | 要运营端配合，b-app 单跑验不了 | 与运营端联跑 |

### 4.1 矩阵：9 个入口 × 6 角色，54 格

**52 格与预期一致。** 两格不符，查下来**都是用例写错了，不是缺陷**：

| 格 | 用例预期 | 实测 | 结论 |
|---|---|---|---|
| 全店订单 / COURIER | ❌ | ✅ | **用例写窄了**。端点可访问，但返回的是裁剪视图 `CourierOrderVO`：只有单号 / 状态 / 履约 / 件数 / 时间 / 收件人（手机号掩码），**没有金额、没有商品明细**。设计就是「可访问但看得少」，不是「拦住」 |

**顺带推翻用例里的一句话**：§4.1 写着「配送单（**仅自己的**）」——
而 `ord_sub_order` **根本没有配送员归属字段**，这件事在数据模型里表达不出来。
与 [ADR-005](../ADR/)「商家自送不做骑手系统，老板要的是点一下已送达」一致：
**不是缺口，是那句话不该写**。

#### TB-PERM-2 的对照做法（值得记下来）

第一次只看 HTTP code：`CLERK` 带 `X-Store-No: <未授权店>` 返回 `code=0`，
**看起来像放行了**。差一点报一个假缺陷。

实际是 `currentStoreNo` 仍停在他被授权的那家店 —— **未授权的门店头被忽略，不是被接受**。
但当时二店一条订单都没有，「没漏」也可能只是没东西可漏。于是造了一条二店的单再验：

```
一店 25 条 · 二店 1 条（SUB…48008）

CLERK  带二店头 → 25 条，不含 SUB…48008   ✅ 隔离住了
MULTI  带二店头 →  1 条，正是 SUB…48008   ✅ 他被授权了，切得过去
```

> 中间还踩了一脚：我先按 `record.storeNo` 判断归属，而 **`OrderVO` 里根本没有这个字段** ——
> 判断恒为 false，两边都"通过"。改用条数对照才是能证明的做法。

#### TB-PERM-4：401 此前分不出「没登录」与「过期」

初测：过期令牌与无令牌**都是 HTTP 401 空响应体** —— 端上无从分辨，
而联调原缺陷正是把过期说成了「没权限」：
**一个让人重新登录，一个让人去找老板要权限，下一步动作完全相反。**

根因不在业务代码：`GlobalExceptionHandler` 那条 401 分支本来就带包体，
但这两种情况**根本走不到它** —— Spring Security 的 `HttpStatusEntryPoint`
在进控制器之前就返回了，而它只发状态码。

修法（`ApiAuthEntryPoint`）：区分所需的信息本来就在过滤器里 ——
「令牌为 null」是没登录，「令牌有但会话查不到」是过期。过滤器打一个 request 属性，
entry point 据此选码。**两条链（`/mp`+`/biz` 与 `/ops`）一起改** ——
同一个问题只修一半，下次在另一条链上还会再出一次。

```
无令牌       → 401 {"code":10401,"msg":"请先登录"}
过期/无效令牌 → 401 {"code":10402,"msg":"登录已过期，请重新登录"}
有效令牌     → 200 {"code":0,...}
```

**状态码仍是 401**：端上 http-client 只对 401 做「清 token 跳登录」，
改成 200 + 业务码会让那条既有逻辑整个失效。这次加的是包体，不是换状态码。

> 复测时有个巧合值得记：重启后端清空了内存 TokenStore，于是之前拿的真令牌
> 也报「登录已过期」—— 那正是这个功能该说的话，误打误撞演示了一遍。

### 本轮没跑的

§三 全部功能用例（商品、订单、履约、售后、评价、结算、多门店、消息）。
它们要真实操作数据，比权限矩阵重得多，且大多依赖支付 —— 单独排一轮。

### 抓到的两个缺口

> **修复状态（2026-08-17 当天）**：三个缺口全部已修，都在真后端复验过。

#### 1. 自提单**不带自提点**也能下单，之后整条链路卡死（P0）· ✅ 已修

`POST /mp/order` 传 `fulfillment=STORE_PICKUP` 而**不传 `pickupNo`**，后端照收。
后果不是当场报错，而是**后面每一步都失败且原因都指错**：

```
到货登记 /biz/pickup/arrived → data: []        （像是「没有这单」）
核销     /biz/pickup/verify  → NOT_THIS_PICKUP （像是「顾客走错店了」）
```

店员会让顾客去别的自提点 —— 而那单根本不属于任何自提点。

与另一位加的收货地址闸（`RECEIVER_REQUIRED`，快递/自送没地址不让下单）**是同一形状**：
履约必需的信息缺了，要拦在创建，不是拦在履约。

**修法**：`OrderServiceImpl.requirePickupPointWhenPickup`，与收货地址那条闸并排，
新错误码 **70025 `PICKUP_POINT_REQUIRED`**「请先选择自提点」。连「点存不存在」一起校 ——
只判空的话，传一个不存在的点号照样落进同一个坑，而那正是端上传错参数最常见的样子。

复验（真后端 8091）：

```
不带 pickupNo    → 70025 请先选择自提点
pickupNo=PP-NOPE → 70025（不存在的点等同没给）
pickupNo=PP0001  → code 0（正路径没被误伤）
```

#### 2. 未到货的码可以核销（P1，邻居自提点才要紧）· ✅ 已修

`PickupServiceImpl.verify` 的状态分支只有 `COMPLETED / REFUNDED|CANCELLED / WAIT_PAY`，
`WAIT_FULFILL`（货还没送到点上）落进 `default → 继续核销`。

自家店无所谓（货本来就在店里）；**邻居自提点**是真问题：货还在路上就被核销成「已取货」，
之后没有任何人知道它没到。契约里的 reason 枚举也没有「未到货」这一项。

**修法（拍板：未到货一律拒绝）**：`PickupServiceImpl.doVerify` 补 `WAIT_FULFILL` 分支，
新 reason **`NOT_ARRIVED`** + 三语文案。**不复用 `NOT_THIS_PICKUP`** ——
那句话是「这单不归你，让顾客换个点」，而这里顾客站对了地方，该说的是「等到货通知」；
说错的代价是把人支去一个根本没有他货的点。

取舍写在案上：拦住的代价是「货到了但没人点到货登记」时店员被卡一下（先点一次到货），
放行的代价是一件货不知去向 —— 后者不可逆。

连带把三个**付款后直接核销**的既有用例改成走真实两步（M4×5、M8×1、BizNotify×1）：
它们此前能过，只是因为那条闸不存在。守卫 `M4FulfillmentFlowTest.cannotVerifyBeforeArrival`
正反两面都钉：未到货拒 `NOT_ARRIVED`，登记到货后**同一个码**核销成功（拒的是时机，不是这张单）。

复验（真后端，邻居自提点 PP0002）：

```
未到货核销    → success:false  reason:NOT_ARRIVED
登记到货后    → success:true
```

#### 3. 主体级改库存对「按店管理」的 SKU 静默无效（P1）· ✅ 已修

```
store-stock 设 33 → 读回 33
stock       设 99 → code 0，读回仍是 33
```

`/biz/goods/{no}/stock` 写的是主体总量，而 SKU 一旦有过分店库存行，读的就是分店那份 ——
**返回成功、数字不动、没有任何提示**。

b-app 已经绕开了（多店走 `store-stock`、单店走 `stock`，代码注释里写明了这个坑），
但**两边判据不同**：端上按「商家是否多店」，后端按「这个 SKU 是否已按店管理」。
单店商家若有按店库存的 SKU（例如关掉一家店之后），就会撞上这个静默无效。

**修法**：让**写落到读的地方** —— SKU 已按店管理时，主体级那条端点转写当前门店那一行。
不改成报错，是因为报错之后那位商家在界面上**没有任何可用路径**去改这件商品的库存
（单店模式根本不显示分店库存入口）。守卫 `StoreStockFlowTest.mainStockWriteLandsWhereTheReadLooks`
—— 撤掉修复它当场变红（验过）。复验（真后端）：读 33 → 主体级设 99 → 读 99。

#### 顺带修掉的两处撞号

`ErrorCodeUniqueTest` 在 HEAD 上是红的：`70014` 被 `RECEIVER_REQUIRED` 与
`FULFILLMENT_TIER_DENIED` 同时占着，`70015` 被 `ROLE_PERM_NOT_ASSIGNABLE` 与
`INVOICE_REQUIRED` 同时占着。撞号意味着两种错在端上分不开 ——
「没选地址」要把人送去地址簿，「这家店不能用这种送法」要让他换一家买，下一步动作相反。
把后加的那两个挪到 `70024` / `70026`（端上已经在用的语义留在原号）。

## 五、端到端冒烟（每次发版必跑）

```
老板手机号登录（新号）
  → 入驻申请（个人主体，免资质）
  → 平台端审核通过
  → 建店 + 绑收款 + 申请覆盖社区
  → 上架一个多 SKU 商品（带主图与译文）
  → C 端下单 → 🚫 支付（后端推 PAID）
  → B 端接单 → 分拣 → 标到货
  → C 端出示取货码 → B 端核销 → COMPLETED
  → C 端写评价 → B 端回复 → 回 C 端确认回复可见
  → C 端申请售后 → B 端处理
  → 看结算单，逐项对上公式
  → 加一个店员，授 CLERK，用店员登录确认「财务入口看不到」
```

**中断点只有支付一处**，其余每一步都能真跑。
支付那步用后端推状态，**报告里必须写明是人工推的**——
记成「通过」的话，接了真支付时没人知道这里从未验过。
