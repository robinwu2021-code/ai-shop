# 商户主数据与门店 · 方案

> 状态：**主数据已落地 V40/V41 · 门店字段去重已落地 V42 · 多门店已决策不做** · 上游 [商户主数据与门店-需求](../requirements/商户主数据与门店-需求.md) · 优先级 P0
> 决策记录：[ADR-010 主数据模型](./ADR/ADR-010-主数据模型.md) · [ADR-011 主体与门店边界](./ADR/ADR-011-经营主体与门店边界.md)

---

## 一、一句话

把「商家是什么行业、什么主体、走哪个通道」这三件**规则来自支付通道**的事，
从散在四处的硬编码收敛成三张平台可维护的注册表，并让入驻在**提交那一刻**就知道能不能做成。

---

## 二、为什么是这个方案

### 2.1 被否掉的做法

| 方案 | 为什么否掉 |
|---|---|
| **A. 加两个字段就完了**（`industry` + `description`） | 字段加了但没人用：`activate` 不传，商家主体上永远是空的。而「行业决定可选主体」这条规则没有落点，商家照样在进件时撞墙 |
| **B. 主体类型用 Java 枚举 + 常量** | 枚举改一次要发版。而它的取值规则来自通道——微信调整白名单、支付宝放开小微，都是对方的日常调整 |
| **C. 三条接口分别下发行业/主体/渠道** | 它们在**同一屏**上被同时用到（选行业→过滤主体→决定要不要执照）。分三次请求会出现"行业回来了、主体还没回来"的中间态，那个中间态里表单不知道该不该禁用某个选项 |
| **D. 进件时再校验主体** | 那时入驻早已通过、商品已经上架。告诉他「你这行不能用这个主体」，要么改主体重走资质，要么这家店根本收不了款——两条都不是他的错 |
| **E. 直接把存量取值改名成通道口径** | 改名穿透实体、契约、三端与测试。而在改名之前，代码里那三处"PERSONAL 是不是小微"的判断会各错各的 |

### 2.2 选定的做法

**表管能力，类型管取值**——与已有的 `sys_pay_channel`、`sys_industry` 同构。

规则进表（会变，来自通道），取值域进 shared 类型（稳定，是产品决策），
守卫保证两边一致。

## 三、结构

```
                        ┌─────────────────────┐
   平台端 /ops/industries │   sys_industry       │  能否小微 · 是否强制积分
                        ├─────────────────────┤
                        │ sys_merchant_subject │  通道码 · 要不要执照 · 结算账户形态
                        ├─────────────────────┤
                        │   sys_pay_channel    │  能否分账/补差/打款 · 限额
                        └──────────┬──────────┘
                                   │ MasterDataService
                                   ▼
                     GET /common/master-data   （游客可读，三端共用）
                                   │
              ┌────────────────────┼────────────────────┐
              ▼                    ▼                    ▼
        C 端入驻表单          B 端入驻/资料          平台端筛选
```

| 组件 | 职责 | 位置 |
|---|---|---|
| `sys_industry` | 行业注册表 | V40 |
| `sys_merchant_subject` | 主体类型注册表 | V41 |
| `sys_pay_channel` | 渠道注册表 | V38 |
| `MasterDataService` | 三端只读快照 + 主体口径翻译 | `shop-svc-platform` |
| `IndustryService` | 平台维护行业 | 同上 |
| `CommonMetaController` | `/common/master-data` | `shop-app` |

## 四、详细设计

### 4.1 数据

`sys_merchant_subject` 的关键三列，每一列都对应一个此前散在代码里的判断：

| 列 | 取代了什么 |
|---|---|
| `legacy_subject` | 「PERSONAL 是不是就是小微」——此前代码里出现三次，各写各的 |
| `need_license` | 「这个主体要不要传营业执照」——三端各写一遍 |
| `industry_gated` | 「行业白名单对谁生效」——写死成 `if (subject == PERSONAL)` |

`wechat_code` / `alipay_code` 为空表示该通道不收这种主体。
**支付宝的小微留空**——限制尚未确认，守卫拦住"想当然照抄微信"。

### 4.2 入驻链路

```
提交申请
  ├─ 校验：行业 + 主体
  │    canonicalSubject(subject)          翻译成通道口径（唯一入口）
  │    industryGated(canonical) == false  → 放行（个体户/企业不受白名单限制）
  │    microAllowed(industry, WECHAT|ALIPAY) 任一为真 → 放行
  │    否则 → 70001 INDUSTRY_SUBJECT_NOT_ALLOWED
  ├─ 落库 usr_merchant_apply（含 industry / description）
  ▼
平台审核通过
  └─ MerchantAdminPort.activate(… industry, description)
       └─ 写入 usr_merchant.industry / description   ← 此前这一步不存在
```

**行业为空时放行**：存量商家的行业还要人工映射（V40 刻意可空），
这里拦住等于把老商家的重新提交也一并堵死。行业必填由端上表单保证。

### 4.3 接口

| 路由 | 权限 | 说明 |
|---|---|---|
| `GET /common/master-data` | 游客 | 行业 + 主体 + 渠道，只含启用的 |
| `GET /ops/industries` | `industry:manage` | 管理视图，**含停用的**，带 `merchantCount` |
| `POST /ops/industries/{industry}/micro-allowed` | 同上 | 改准入，**必须写 remark** |
| `POST /ops/industries/{industry}/enabled` | 同上 | 启停，只影响新入驻 |
| `POST /ops/industries/{industry}/points-forced` | 同上 | 只改默认值，不回写存量 |

`industry:manage` **不给 BD**——它改的是「哪些行业能开小微」，
那是通道规则的落点，不是招商能自行判断的事；改错的后果是一批商家进件被拒。

## 五、取舍记录

| 冲突 | 让了谁 | 为什么 |
|---|---|---|
| 主体口径：入驻侧 vs 通道侧 | **通道侧** | 主体类型的唯一硬约束来自通道（能不能进件、要什么资质、钱打到哪儿）；展示名可以随便改。让权威贴着约束走，映射只需一个方向 |
| 校验时机：提交 vs 进件 | **提交** | 进件时才拦 = 入驻已通过、商品已上架，此时改主体要重走资质 |
| 端上体验：禁用选项 vs 提交后报错 | **禁用** | 让人填完再拒是最差的一种告知方式。所以 `master-data` 的每个行业带 `microAllowed` |
| 兜底 `needLicense` | **true** | 少要一次执照 = 放进一个不该通过的商家；多要一次只是麻烦 |
| 兜底 `industryGated` | **false** | 未知不该凭空加一条限制 |
| 存量取值 | **已统一到通道口径** | 按 ADR-010 §4 的五步走完前四步（V43）。第 5 步（删 `legacy_subject`）刻意暂缓——它是旧取值的唯一翻译源，删早了会把"被翻译"变成"存进一个认不出来的值"，且不报错 |
| `points_forced` 改行业默认值时 | **不回写存量** | 强制开积分要提前 30 天通知 + 费率补偿 + 申诉通道（ADR-006）。一个开关改掉所有存量商家的成本结构是不行的 |
