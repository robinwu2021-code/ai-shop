## C5-A · 快递闭环（C→B→C 一整圈 · 全通）

**这是整份方案的核心：同一单在两端各看一眼，状态一致。**

| 步 | 端 | 实测 |
| --- | --- | --- |
| 1. C 下快递单 + 付款 | C/8083 | 子单 `WAIT_FULFILL`，收货人「测试买家」 |
| 2. **B 端接单** | B/8083 | B 端查到这单，**看到收货人「测试买家」**（F2 的价值链：C 端有地址 → B 端看得到 → 才能发货） |
| 2. **B 端发货**（填运单号） | B/8083 | → `SHIPPED` / `FULFILLING`，运单号 `YT9999888877776` |
| 3. C 端看订单（子单号） | C/8083 | **`SHIPPED` + 运单号 + 收货人全可见** |
| 4. 确认收货 | — | **C 端无手动确认收货按钮** —— 社区电商快递单靠物流签收/超时自动完成，是产品设计不是缺陷 |

> **一次虚惊（记下来免得重犯）**：步 3 我第一次用**主单号** `SO…` 打 detail，
> 拿到 `status=PAID`、运单号 null —— 看着像「C 端看不到发货」的大缺陷。
> 实为 `detail(orderNo)` **先按子单号查**（Q6：C 端订单视角就是子单），
> 传主单号会走「支付视角」`payView`。C 端列表返回的 `orderNo` 本就是**子单号**
> `SUB…9253`，真实路径完全正确。**用错号造出的假缺陷，比漏测更浪费时间** ——
> 与 B 端那两次口径误判同一个教训。
>
> 顺带印证一条已修的历史缺陷：`OrderServiceImpl:1029` 注释「买家要靠它查物流；
> 此前库里有这一列而 VO 里没有，发货对买家不可见」——**运单号对买家可见**这条修过了。

## 小结（本轮 C 端）

跑到 C1 + C3 + C4 + **C5-A 快递闭环**，核心的「注册 → 下单 → B 端接单 → C 端看到发货」
一整圈通了，**无新缺陷**（F7 是用错号的虚惊）。F1（验证码文案）在 C 端顺带回归通过，
F2（下单必须有地址）在真实闭环里显出价值链 —— C 端下单有地址是 B 端能发货的前提。

**三条履约闭环全部走通**（快递 / 自提 / 自送），加评价、属主边界、幂等、取消 ——
**C 端无新缺陷**。三端「同一个库一份真相」再次成立：C 端下单的每一步，
B 端都在同一份数据上接着处理，两端看到的状态逐一对上。

**C 端全模块跑完，0 代码缺陷。** 五条 C↔B 闭环全通：快递、自提、自送、售后、求团 ——
C 端每发起一件事，B 端都在同一份数据上接着处理，两端状态逐一对上。

**值得记的模式**：C 端这一轮「看着像缺陷」的出现了 **4 次，全是测试端问题**，无一是代码 ——
主单号 vs 子单号（C5-A）、`priceMinor` vs `unitPriceMinor`（C8.5）、
门店主页读错嵌套层级（C2.6）、正则匹配到 reviewNo 里的数字当手机号（C10.4）。
四次的共同根因是**不查契约就猜字段/路径**。它们比真缺陷更耗时，因为要先证伪。
下一轮的纪律：**判据里的每个字段名都从契约或 VO 定义里抄，不凭印象**。

**F1 / F2 在 C 端的回归全部通过**：F1 验证码文案覆盖 C 端；F2 的地址校验在三条
履约闭环里显出完整价值链（C 端有地址 → B 端看得到 → 才能履约）。
