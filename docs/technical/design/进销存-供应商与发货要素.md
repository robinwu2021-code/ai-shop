## 一、现状：只有两处还在手输，而它们正好是最贵的两处

**盘点方式**：逐页数 `<input>` / `prompt()`（手输）与 `pick()`（选择），
再与 `ai_shop_inv` 的真实列对照。不取自任何既有文档。

| 要素 | 现状 | 落点 |
|---|---|---|
| 货品 | ✅ 弹层选 | `inv_item` |
| 库位 | ✅ 选 | `inv_location` |
| 调拨的出／入库位 | ✅ 选 | `inv_location` |
| 盘点差异原因 | ✅ 四选一 | 枚举 |
| 报损原因 | ✅ 四选一 `BROKEN/EXPIRED/GIFT/OTHER` | 枚举 |
| **供应商** | ❌ **自由输入框** | `inv_inbound_order.supplier_name varchar(64)` |
| **发货信息** | ❌ **不存在** | `ship(no)` 只收单号 |
| 出库去向 | ❌ 写死 `purpose="SCRAP"` | 没有「发给谁」这个概念 |
| 数量 / 进价 | 输入框 —— **保留** | 它们不是实体，见 §五 |

进货页自己写着「**仅作记录，不建立供应商档案**」——
那句话是当时的决定，这份文档要改的就是它。

## 二、为什么这两处值得单独做

**① 用名字存供应商，一定会漂。**
同一家「老周粮油」会被打成「老周粮油店」「老周」「周老板」，
而进货报表按名字聚合 —— 商家看到的是三个供应商，进货额被拆成三份。

这不是假想：2026-08-29 真机验证当天量到，同一商家
**13 组重名货、207 件货号全空**，挑货弹层里几行长得一模一样，
挑错了没有任何办法发现。**同一类病，只是换了个对象。**

**② 没有供应商实体 ⇒ 应付账款、进价历史、供应商对账都无从谈起。**
这不是界面问题，是缺一个域对象。补界面（下拉框里塞历史输入过的名字）
只会把漂移固化下来。

**③ 调拨发出去之后没有任何可追的东西。**
`ship(no)` 只收单号：发给谁、谁在运、运单号多少，一个都不存。
库存页「在途 N」点进去看得到单，而收货方只能凭记忆核对。

## 三、三个判断的结论

### ① 商家自建，**同时从第一天就留平台层的位置**

拍板：**两者都要**。商家能自己建档，将来也要能用平台维护的供应商。

关键是**别把「将来」推给将来** —— 那样做的结果通常是：平台层落地时发现
商家已经自建了一批同名档案，两边合不拢，只能做一次痛苦的人工归并。
所以第一天就把两件事分开：

| | 谁维护 | 谁能改 |
|---|---|---|
| `platform_supplier_no` 为空 | 商家自建 | 商家 |
| `platform_supplier_no` 非空 | 平台档案 | **商家只读**（名称、联系方式跟平台走） |

商家侧永远只有一张 `inv_supplier`：选平台供应商时**在本地建一条引用行**，
而不是让进货单直接指平台表。三条理由：

- 进销存是独立库，跨库不能外键；
- 商家可能要给同一家平台供应商记自己的备注、自己的联系人；
- **停用是商家自己的事** —— 平台还在合作，不代表这家商家还在从它进货。

平台侧那张表这一轮**不建**，但列先留出来。留一个可空外键的成本接近零，
而事后补的代价是一次数据归并。

### ② 承运方复用 `ful_carrier`

拍板：**复用**。存 `carrier_no` + 冗余 `carrier_name`。

进销存是独立库、独立数据源，跨库不能外键。冗余名字是为了**单据能自证**：
承运方三个月后改了名，历史调拨单上该显示当时那个名字，而不是跟着变。

`ful_carrier` 现有 **3 行**，在主库、履约域。进销存侧**不做写入** ——
它只读一份可选列表；承运方的增删改仍归履约域。

### ③ 出库去向：方案如下，**这一轮不实现**

先说一件动手前必须知道的事 —— **`purpose = SALE` 手工建是被明令禁止的**，
`OutboundService.createDraft` 的原话：

> **销售出库只能由预留 commit 产生**：允许手工建的话，
> 商家能凭空造一笔销售出库，而它会进销量榜。

所以「发货给客户」**不能**做成出库单上的一个新选项 —— 那正是这条闸门挡的事。
真正缺的去向是另外两个：

| `purpose` | 去向对象 | 谁能开 |
|---|---|---|
| `SCRAP` | 无 | 商家（现有） |
| `INTERNAL_USE`（内部领用） | 无，或门店 `store_no` | 商家 |
| **`RETURN_SUPPLIER`（退供应商）** | **`inv_supplier`** | 商家 |
| `SALE` | 订单 `order_no` | **只有系统**（预留 commit），闸门不动 |

**`RETURN_SUPPLIER` 是本方案真正的收尾**：供应商建了档，退货才有对象可指，
而「这个月退给老周多少货」是应付账款对账的一半。它与 §四 的供应商是同一件事，
不是新维度。

去向落两列：`target_type` + `target_no`，加冗余 `target_name`（理由同 §三②）。
`SCRAP` 两列为空 —— **不要拿 `reason_code` 兼作去向**，
那会让「报损原因」和「退给谁」挤在同一列，报表再也分不开。

## 四、方案

### 4.1 新表 `inv_supplier`

| 列 | 说明 |
|---|---|
| `supplier_no` | 主键编号 |
| `owner_id` | 商家隔离。**进销存不走平台的 DataScope** —— 那套机制只覆盖平台迁移里的 163 张表，`inv_*` 一张都不在（当场查过）。这里靠每个查询显式 `.eq(ownerId)`，与既有 15 处同一口径。**漏一处就是跨商家泄露，而它不会报错** |
| `platform_supplier_no` | **可空**。空 = 商家自建；非空 = 引用平台档案，名称与联系方式商家只读。平台表这一轮不建，列先留（见 §三①） |
| `name` / `short_name` | 名称；短名给单据列表用 |
| `contact_name` / `contact_phone` | 联系人 |
| `status` | `ACTIVE` / `ARCHIVED` —— **停用不删除**：历史单据要指得回去 |
| `remark` | 备注。**平台档案也让商家写** —— 那是他自己的话 |

**唯一性**：`(owner_id, name)` 唯一。同一个商家不许有两个同名供应商 ——
这条约束正是本方案存在的理由，不加等于把漂移换了个地方继续长。
（跨商家同名是正常的，不约束。）

**不做的**：结算账期、授信额度、资质附件。那是应付账款的活，
这一轮只解决「进货单能指向一个稳定的对象」。

### 4.2 `inv_inbound_order` 加 `supplier_no`

**`supplier_name` 保留不删。** 两条理由：
存量 206 张单里的名字是唯一的历史事实，删了就没了；
而新单据的 `supplier_name` 作为**下单当时的名字快照**继续写，
与 §三②「单据要能自证」同一条规矩。

### 4.3 调拨发货：`ship` 收三个新字段

`carrier_no`（选）、`tracking_no`（输 —— 它是运单号不是实体）、`shipped_by`。
`inv_transfer_order` 相应加三列。

### 4.4 界面

- 进货页：供应商输入框 → **选择器**，底部「+ 新建供应商」（同一层弹层内完成，不跳页）
- 新增「供应商」管理页：挂在库存页的 `单据 / 报表 / 库位` 那一排后面
- 调拨发货：弹一层填承运方（选）+ 运单号（输）

### 4.5 迁移与灰度

**存量 206 张单的 `supplier_no` 留空** —— 不猜。
按名字反查建档会把「老周粮油」和「老周」合成一个，那是造假不是迁移。
界面上老单显示 `supplier_name`，新单显示档案名。

## 五、明确不改的：数量与进价仍然手输

「不要手输」针对的是**关联要素**（指向另一个对象的那些字段）。
数量、进价、运单号是**值**不是实体，给它们做列表既不可能也没意义。
盘点那一屏的数字输入是对的，不在本方案范围内。

不接受「代码写完了」当判据。每一步的判据都写在上表里，且：
