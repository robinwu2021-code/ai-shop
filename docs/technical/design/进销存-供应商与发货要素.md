## 一、现状：只有两处还在手输，而它们正好是最贵的两处

**盘点方式**：逐页数 `<input>` / `prompt()`（手输）与 `pick()`（选择），
再与 `ai_shop_inv` 的真实列对照。不取自任何既有文档。

| 要素 | 现状 | 落点 |
|---|---|---|
| 货品 | ✅ 弹层选 | `inv_item` |
| 库位 | ✅ 选 | `inv_location` |
| 调拨的出／入库位 | ✅ 选 | `inv_location` |
| 盘点差异原因 | ✅ 四选一 | 枚举 |
| 报损原因 | ✅ 四选一 `BROKEN/EXPIRED/GIFT/OTHER` | 枚举 |
| **供应商** | ❌ **自由输入框** | `inv_inbound_order.supplier_name varchar(64)` |
| **发货信息** | ❌ **不存在** | `ship(no)` 只收单号 |
| 出库去向 | ❌ 写死 `purpose="SCRAP"` | 没有「发给谁」这个概念 |
| 数量 / 进价 | 输入框 —— **保留** | 它们不是实体，见 §五 |

进货页自己写着「**仅作记录，不建立供应商档案**」——
那句话是当时的决定，这份文档要改的就是它。

## 二、为什么这两处值得单独做

**① 用名字存供应商，一定会漂。**
同一家「老周粮油」会被打成「老周粮油店」「老周」「周老板」，
而进货报表按名字聚合 —— 商家看到的是三个供应商，进货额被拆成三份。

这不是假想：2026-08-29 真机验证当天量到，同一商家
**13 组重名货、207 件货号全空**，挑货弹层里几行长得一模一样，
挑错了没有任何办法发现。**同一类病，只是换了个对象。**

**② 没有供应商实体 ⇒ 应付账款、进价历史、供应商对账都无从谈起。**
这不是界面问题，是缺一个域对象。补界面（下拉框里塞历史输入过的名字）
只会把漂移固化下来。

**③ 调拨发出去之后没有任何可追的东西。**
`ship(no)` 只收单号：发给谁、谁在运、运单号多少，一个都不存。
库存页「在途 N」点进去看得到单，而收货方只能凭记忆核对。

## 三、三个产品判断（**需要拍板，我不替你定**）

### ① 供应商建在哪一层

| | 商家自有档案 | 平台统一维护 |
|---|---|---|
| 表 | `inv_supplier`（带 `owner_id`，商家隔离） | 平台库 + 商家从中选 |
| 好处 | 简单；商家想怎么记就怎么记 | 能做集采、统一对账、供应商资质 |
| 代价 | 同一家供应商在 100 个商家那里是 100 条 | 要有人维护；商家自己的小供货商进不来 |

> **倾向：先做商家自有。** 平台统一是一门生意上的决定（要不要做集采），
> 而商家自有是记账的最低要求。两者不冲突：将来加 `platform_supplier_no`
> 指向平台档案即可，先做的这一层不会白做。

### ② 承运方复用 `ful_carrier` 还是自己一份

主库已有 `ful_carrier`（**3 行**，履约域）。而进销存是**独立库、独立数据源**，
跨库不能外键 —— 只能存 `carrier_no` + 冗余 `carrier_name`。

> **倾向：复用编号、冗余名字。** 承运方是全平台共用的事实，
> 再造一张只会让两处名字对不上。冗余名字是为了**单据要能自证**：
> 三个月后承运方改了名，历史调拨单上该显示当时那个名字。

### ③ 出库要不要「发给谁」

现在写死 `SCRAP`（报损）。若要支持发货给客户／门店，
那是出库单的新维度，牵扯订单域 —— **建议这一轮不做**，
先把「报损」之外的 `purpose` 留空，等第一笔真实订单跑通投递再谈。

## 四、方案（按上面倾向展开；拍板不同则相应调整）

### 4.1 新表 `inv_supplier`

| 列 | 说明 |
|---|---|
| `supplier_no` | 主键编号 |
| `owner_id` | 商家隔离。**带归属列就要登记数据域**，否则那张表永远不过滤 |
| `name` / `short_name` | 名称；短名给单据列表用 |
| `contact_name` / `contact_phone` | 联系人 |
| `status` | `ACTIVE` / `ARCHIVED` —— **停用不删除**：历史单据要指得回去 |
| `remark` | 备注 |

**不做的**：结算账期、授信额度、资质附件。那是应付账款的活，
这一轮只解决「进货单能指向一个稳定的对象」。

### 4.2 `inv_inbound_order` 加 `supplier_no`

**`supplier_name` 保留不删。** 两条理由：
存量 206 张单里的名字是唯一的历史事实，删了就没了；
而新单据的 `supplier_name` 作为**下单当时的名字快照**继续写，
与 §三②「单据要能自证」同一条规矩。

### 4.3 调拨发货：`ship` 收三个新字段

`carrier_no`（选）、`tracking_no`（输 —— 它是运单号不是实体）、`shipped_by`。
`inv_transfer_order` 相应加三列。

### 4.4 界面

- 进货页：供应商输入框 → **选择器**，底部「+ 新建供应商」（同一层弹层内完成，不跳页）
- 新增「供应商」管理页：挂在库存页的 `单据 / 报表 / 库位` 那一排后面
- 调拨发货：弹一层填承运方（选）+ 运单号（输）

### 4.5 迁移与灰度

**存量 206 张单的 `supplier_no` 留空** —— 不猜。
按名字反查建档会把「老周粮油」和「老周」合成一个，那是造假不是迁移。
界面上老单显示 `supplier_name`，新单显示档案名。

## 五、明确不改的：数量与进价仍然手输

「不要手输」针对的是**关联要素**（指向另一个对象的那些字段）。
数量、进价、运单号是**值**不是实体，给它们做列表既不可能也没意义。
盘点那一屏的数字输入是对的，不在本方案范围内。

## 六、工作量与顺序

| 步 | 内容 | 判据 |
|---|---|---|
| S1 | `inv_supplier` 建表 + 实体 + 数据域登记 | 迁移跑通；`entity-alignment` 绿 |
| S2 | 供应商 CRUD 三个 `/biz` 端点 | 契约闸门绿 |
| S3 | 进货页选择器 + 新建入口 | 真机上能选、能新建、能落到 `supplier_no` |
| S4 | `inv_transfer_order` 三列 + `ship` 改签名 | 真机发一次货，单据上看得到承运方与运单号 |
| S5 | 供应商管理页 | 界面清单同步 |

**S1–S3 是一件事**（供应商），**S4 是另一件**（发货），可以分两笔上线。
