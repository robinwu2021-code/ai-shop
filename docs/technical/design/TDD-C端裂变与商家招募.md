## 0. 先说结论

两件事的现状完全不同，方案的重心也因此不同：

| 目标 | 现状一句话 | 重心 |
|---|---|---|
| **C 端裂变** | 后端**全链路已经通了**（配置 → 归因 → 注册落台账 → 首单回填 → 运营看数），<br>唯独**买家侧一个入口都没有** | 补最后一公里 |
| **商家招募** | 官网已经是招商站、C 端也有入驻接口与表单，<br>官网的联系方式**只有一个邮箱**；主渠道（小程序）原先按类目红线不出招商，<br>**2026-09-28 改判为开放**（见 §7.6） | 换路径，不是补功能 |

## 1. 现状（查证过的事实，不是判断）

### 1.1 邀请有礼：差的只是 C 端那一半

| 环节 | 在哪 | 状态 |
|---|---|---|
| 活动配置（奖励几张券、邀请人/被邀请人各几张） | `mkt_fission_campaign`（V121）+ 运营端「邀请有礼配置」(`/growth?tab=fission`) | ✅ 有 |
| 分享路径带邀请人 | `ports/share.ts` 的 `withAttribution()`，写 `inviterNo` + `merchantNo` | ✅ 有 |
| 新用户注册落台账 | `AuthServiceImpl` 注册分支 → `fissionPort.onRegister(...)` | ✅ 有（2026-08-30 接上） |
| 首单转化回填 | `FissionOutboxConsumer` 吃 `ORDER_CREATED` | ✅ 有 |
| **买家侧入口**：哪儿看得到「邀请有礼」、邀请了几个、得了几张券 | —— | ❌ **一处都没有** |
| **落地页的钩子**：被邀请人点进来，凭什么知道自己有奖励 | —— | ❌ 没有 |

所以线上 `mkt_fission_invite` 为 0 有两个各自独立的原因：**运营没建过活动**，
以及**买家不知道分享能得券**。两个都不修，补哪一个都不会有数据。

### 1.2 分享入口：三个页面、两种端，只有一处能点

| 页面 | `onShareAppMessage` | 页面上的可见入口 |
|---|---|---|
| 商品 `pages/goods` | ✅ | ✅ 一个（`open-type="share"`） |
| 门店 `pages/store` | ✅ | ❌ **零** |
| 商家 `pages/merchant` | ✅ | ❌ **零** |
| 首页 / 订单 / 拼团 / 需求 | ✅ | 拼团那一处有 |

两条更要紧的：

- 商品页那个按钮挂在 `v-if="nativeShare"` 上，而 `canNativeShare()` **只在微信小程序返回 true**
  → **H5（`/c/`）上三个页面一个分享入口都没有**，而 H5 没有胶囊菜单可以兜底。
- 全仓 **没有 `onShareTimeline`、没有海报（`poster`/`canvas` 零命中）** ——
  朋友圈这条路今天完全走不了，而社区场景里朋友圈与群聊是同一量级的入口。

### 1.3 商家招募：能力都在，路被类目红线挡住

- C 端有 `/mp/merchant/apply`（提交）与 `GET`（查状态），`pages/me` 有完整表单。
- 但入口挂在 `merchantApplyVisible()` 上，**小程序里恒为 false**——这是已拍板的合规约束：
  以自营类目提交的包里出现「招商 / 入驻 / 商家申请」会被判**平台型经营**而驳回。
  代码与审核流程都留着，等拿到平台类目改一处就露出来。
- 官网 `hxmall.top` 首页**已经是招商站**（受众写着「还没入驻的社区门店店主」，
  CTA 是「免费开店 / 联系招商」）。
- **联系方式只有一个邮箱** `hello@hxmall.top`，「联系招商」是个 `mailto:`。
  社区门店店主用微信和电话 —— 这个入口等于没有。

## 3. 方案一：C 端裂变

### 3.1 批 A（最小闭环）：让已经通了的链路有人走

**A1 · 「邀请有礼」入口**。放在「我的」页，与已有的优惠券/积分同一区。
一屏三件事：当前活动给多少（邀请人 N 张 / 被邀请人 M 张）、我邀了几个/成了几单、
一个「邀请好友」按钮。没有在跑的活动时**整条不出现**——
不摆一个点进去说「暂无活动」的入口。

**A2 · 分享带上活动**。`ShareParams` 加可选 `fissionNo`；
分享文案在有活动时换成带奖励的那一句（「新朋友下单各得 N 元券」），
没活动时保持原样。文案走 i18n，三语。

**A3 · 落地页的钩子**。被邀请人点进来（`inviterNo` 在 query 上），
首屏给一条**可关闭**的提示条：「{邀请人昵称} 邀请你，首单后各得 X 元券」。
**不做强弹窗**——弹窗在社区场景里的第一反应是关掉，且它挡住的正是商品本身。

**A4 · 运营侧先建一个活动**。没有活动，A1~A3 全部是空转。
这一步我做不了（运营账号），要有人在 `/growth?tab=fission` 建。

### 3.2 批 B：把分享入口补齐

**B1 · 门店页与商家页各加一个可见分享按钮**，与商品页同形。

**B2 · H5 上的分享**。`canNativeShare()` 在 H5 恒 false，导致 H5 没有任何入口。
H5 不能调起微信转发，但能做两件事：**复制带归因的链接**（`uni.setClipboardData`），
以及**长按保存海报**（见 B3）。按钮始终在，只是行为按端分叉。

**B2b · 朋友圈（`onShareTimeline`）**。全仓此前**一处都没有** ——
小程序右上角那一栏里「分享到朋友圈」是灰的，点不了。

⚠️ **它与转发给好友不是同一个形状**：朋友圈落的是「单页模式」，微信只接受 `query`，
给 `path` 会被忽略。把 `buildShareMessage` 的结果直接返回给 `onShareTimeline`，
归因参数会跟着那个被忽略的 path **一起没掉** —— 人从朋友圈进来了却算不到任何人头上，
而页面上一切正常。所以另起 `buildShareTimeline` 只拼 query。

**B3 · 海报**。朋友圈只吃图片，没有海报就没有朋友圈这条路。
一张海报 = 商品主图 + 店名 + 价格 + 小程序码（带 `inviterNo` 的 scene）。
小程序码走后端已有的码生成能力（`/biz/store/qrcode` 那套的 C 端版本）。
**这一条成本最高**，所以排在 B 的最后，且先只做商品页一种版式。

### 3.3 不做的

| 做法 | 为什么不做 |
|---|---|
| 现金/红包奖励 | ADR-004 的核心是不用钱买增长；现金会招来职业薅羊毛，且给归因作弊一条变现路径（V121 的表注释同此） |
| 分享排行榜 | 把「分享给邻居」变成刷量竞赛，与邻里场景相悖（已有方案 §2.2 已否掉一次） |
| 强制分享解锁（砍一刀） | 微信明令禁止诱导分享，小程序会被处罚 |
| 在小程序里做「邀请商家入驻得奖励」 | 直接踩类目红线，见 §4.1 |

## 4. 方案二：商家招募

### 4.1 红线与它的改判（2026-09-28）

**原结论**：小程序（主渠道）里不能出现招商、入驻、商家申请、"我要开店"、代理加盟 ——
微信按类目审，自营类目的包里出现这些可能被判**平台型经营**而整包驳回。

**改判**：拍板要**在小程序上开放商家注册**，并在注册后引导下载商家版 App。

那条风险**并没有消失**，变的是谁来承担它。所以落地方式是一条**后端开关**
（`merchant.apply.mp-visible`，默认开），而不是把端上那个 `#ifdef` 删掉：

| | 写死在端上 | 后端开关 |
|---|---|---|
| 被驳回时怎么止血 | 改代码 → 发版 → **重新提审** | 运营后台关一下，下次冷启动生效 |
| 恢复 | 同上 | 同上，开回来即可 |
| 时间量级 | 几天 | 分钟 |

为此补上了一条一直断着的链：`/mp/config/bootstrap` 此前**只发 yml 里那几个开关**，
而运营端「功能开关」那一屏改的是平台开关 —— 两边互不相干，
于是「运营后台改一下」对买家侧的任何行为都不成立。现在两者在后端合流
（同名以运营端为准），端上冷启动拉一次 —— **端上此前一次都没调过这条端点**。

**客服入口**仍然保留（小程序原生 `open-type="contact"`）：它与招商无关，
任何小程序都该有，且不需要后端。⚠️ 要在微信后台配过客服人员才有反应。

**这条路已经实测过**（§9.1b：生产上真关了一次，30 秒后开回来，审计有记录）。

**提审前要决定的一件事**：这条开关现在默认**开**。若想先让首个版本过审再放开，
把 `PlatformConfigServiceImpl.DEFAULT_FLAGS` 里它的 `enabled` 改成 `false`，
由运营在后台开 —— 那样提交的包里就没有入驻入口。

### 4.2 官网招商页：把联系方式做实

今天的「联系招商」是 `mailto:hello@hxmall.top`。三件事：

1. **加微信与电话**。社区门店店主不用邮箱。微信二维码（可长按识别）+ 一个电话，
   与邮箱并列；移动端把微信那一项排在最前。
2. ~~留资表单~~ **不做**（§7.1）：`/mp/merchant/apply` 是 `auth: true`，
   官网访客没有登录态，而开一条匿名端点已拍板不做。线索靠人接。
3. **可核验的承诺**上移。首页已经写了「无入驻费、无押金、无年费」，
   这三个词是社区店主最先问的，值得放在第一屏而不是最后一屏。

### 4.3 B 端 App 与官网的衔接

官网下载页已经给安卓包与版本号。补一条：**下载页面上留同样的微信/电话** ——
装完包第一件事是找人问，而那一刻他手里只有 App。

### 4.4 从买家变商家：谁会注册

真实路径有两条，都不经过小程序里的「招商」二字：

- **自提点商家**：他已经在平台里（承接自提），最可能升级成卖家。这条路由运营直接触达，
  不需要 C 端入口。
- **顾客里的店主**：他在小程序里买东西，看到的是「这家店怎么做到的」。
  给他的不是招商话术，而是**商家页上的一行可核验信息**（例如「本店已服务 N 位邻居」）。
  好奇的人会去问客服 —— 合规，且把判断权留给他。

## 5. 影响面与登记

- 新端点：**0**。邀请有礼、入驻申请、码生成都用现成的。
- 契约新增字段：`ShareParams.fissionNo`；C 端「我的邀请」需要一条查询 —— 
  **先确认后端有没有现成的**（`FissionService` 已有按活动统计），没有再议。

  **这一条要先拍板**：是开一条匿名的线索端点，还是官网只留联系方式不做表单。

## 7. 拍板结论（2026-09-28）

### 7.1 官网不开匿名端点

**不做留资表单**，官网只留联系方式。随之而来的是：§2 的 M4「招商线索数」
**系统里记不到** —— 线索落在微信与电话里，只能人工记。这不是遗漏，是这条拍板的代价，
写在这里免得以后有人拿「线索数是 0」下结论。

### 7.2 券额度：双方各一张「满 60 减 8」，7 天有效

建议值，依据是线上真实数据（2026-09-28 查）：

| 量 | 实际 |
|---|---|
| 真实客单价（剔除 0.1 元测试单，16 单） | **¥73.7** |
| 在售主力 | 大豆油 ¥60 · 菜籽油 ¥70 · 面粉 ¥31.9~66.9 · 花生油 ¥130 |
| 最便宜的在售品 | 生抽/老抽 ¥15 |

- **门槛 ¥60**：正好卡在主力粮油上 —— 拿券能买走一桶油，而买不走一瓶 ¥15 的生抽。
  门槛设低（如满 20）会把券变成「买瓶生抽」，那种单不产生复购判断。
- **面值 ¥8**：约客单价的 11%，一次成功邀请双边成本 ¥16。
- **保守备选**：满 60 减 5（双边 ¥10，7%）。两个都给运营，由他们定。
- **必须设上限**：`mkt_coupon` 有 `total_count` 与 `budget_minor` 两道闸，
  首批建议 `total_count = 200`（≈100 次成功邀请），`budget_minor` 按 200×面值 设。
  **不设上限的活动不要上线** —— 裂变的成本是乘出来的。

### 7.3 海报：做，但码只能是店铺码

**一条硬约束**：小程序码走 `wxacode.getUnlimited`，是**永久码且每个 appid 总量有限
（十万级）**，所以 `StoreCodeService` 的做法是**一店一码、生成一次落库复用**
（那段注释写着：每次现调，几百个商家刷新页面就能把额度耗光，之后新入驻的商家再也拿不到码）。

因此海报上的码 = **该店已有的店铺码**，邀请人信息**不进码**：

- 海报承担的是「朋友圈曝光 → 进店」，归因到**店**；
- **邀请归因（`inviterNo`）走小程序内转发**那条路，不走海报。

这是个取舍，不是疏漏：把 `inviterNo` 编进 scene 意味着「每个用户一张永久码」，
用户一多就把额度烧穿，而烧穿之后**新商家拿不到店铺码** —— 代价落在完全无关的地方。

### 7.4 商家页用真实数据，不用「邻居」这个词

**先说一件要紧的**：`mch_entity.sales_count` / `goods_count` 与 `prd_goods.sales`
**线上全是 0**，而实际已有 24 单 —— 这几列声明了却没人维护。
商品页那枚销量 chip 挂在 `sales > 0` 上，所以它**从来没出现过**。

所以「真实数据」不能取这几列。能取且真实的只有两类：

| 量 | 今天的真值 | 用不用 |
|---|---|---|
| 该商家的成交单数 / 买过的人数 | **1~2 单、1 位** | ❌ 真实，但显示出来是在自曝冷启动 |
| 在售商品数 | 5~7 件 | ✅ |
| 开店时长 | 有 `created_at` | ✅ |

**取后两者**：「在售 N 件 · 开店 N 天」。它同样是真实的、可核验的，
而且不会因为数小就变成反效果。等成交量起来了再把成交数加进去 ——
那时它才是个有说服力的数。

**文案不用「邻居」**（用户指定）：统一说「顾客」。

### 7.5 顺带记一笔账

`sales_count` / `goods_count` / `prd_goods.sales` 三列没人写 —— 不在本篇范围内，
但它让「商品页销量」「商家页成交」这类展示全都失效。单独记进商品域的欠账，别在这儿顺手改。

### 7.6 小程序开放商家注册（2026-09-28 改判）

**推翻的是 §4.1 的原结论**：小程序上要能注册商家，注册完引导下载商家版 App 做管理。

类目红线那条风险**没有消失**，变的是承担方式 —— 落地成后端开关
`merchant.apply.mp-visible`（默认开），而不是端上的编译期判断：

- 真被驳回：运营后台关掉，下次冷启动生效（分钟级），不用改代码、不用重新提审；
- 恢复：开回来即可。

为此接通了一条一直断着的链：`/mp/config/bootstrap` 此前只发 yml 里那几个开关，
与运营端那一屏改的平台开关互不相干；且**端上一次都没调过这条端点**。
现在两者在后端合流（同名以运营端为准），端上冷启动拉一次。

**提审前要决定**：这条开关默认开。若想让首个版本先过审，把
`PlatformConfigServiceImpl.DEFAULT_FLAGS` 里它的 `enabled` 改成 `false`，
提交的包里就没有入驻入口，由运营在后台放开。

## 8. 第二轮拍板（2026-09-28 晚）

§7 之后用户又给了四个口径。三条与 §7 有差异或是新增，记在这里 ——
**§7 不改**，那是当时的依据，改它会让「为什么当初那样定」失去出处。

### 8.1 券预算改判：试水额度 200 元，面值降到 3 元

§7.2 定的是「满 60 减 8」× 200 张（双边一次 16 元，总面值 1600 元）。
用户口径是 **「奖励先给一个 200 元的额度」** —— 总预算 200 元。

按原面值算：`200 ÷ 16 = 12 次`成功邀请。**12 次跑不出漏斗** ——
分享量、点开率、注册率、首单率四层，每层再打个折，末端个位数，
看不出哪一层是瓶颈，而这轮的目的正是找瓶颈（§2 的 M1~M3）。

所以面值跟着降：

| 项 | §7.2 | 本轮 |
|---|---|---|
| 门槛 | 满 60 | 满 60（**不动**） |
| 面值 | 8 元 | **3 元** |
| 双边一次成本 | 16 元 | **6 元** |
| `budget_minor` | 160000 | **20000** |
| 能撑多少次成功邀请 | 100 | **约 33** |

**为什么门槛不动**：60 元卡在主力粮油上（大豆油 60 / 菜籽油 70 / 面粉 31.9~66.9），
拿券能买走一桶油，买不走一瓶 15 元的生抽。降门槛会把券变成「买瓶生抽」——
那种单不产生复购判断，跑出来的数据没有意义。降面值只是降力度，不改变券的用途。

**3 元是不是太少**：约客单价 4%。它确实弱，但这一轮要的是**漏斗形状**不是转化率绝对值：
33 次成功邀请足够看出「分享出去有没有人点」「点了有没有人注册」这两层。
力度不够导致的低转化会均匀压低末端，不会改变哪一层最窄。
真要放量再调 `budget_minor` 与面值，两个都是活动参数，不发版。

**两道闸都要设**（`mkt_coupon`）：`total_count = 66`（双边各一张 × 33 次）、
`budget_minor = 20000`。**不设上限的活动不要上线** —— 裂变成本是乘出来的。

### 8.2 门店关注：功能早就在，缺的是「关注之后会发生什么」

用户说「门店关注做」。查证后的事实：**全链路已经做完了**，只是叫「收藏」——

| 层 | 现状 |
|---|---|
| 表 | `usr_store_favorite`（user_no + entity_no） |
| 服务 | `StoreFavoriteServiceImpl` |
| 端点 | `POST /mp/favorite/store/:merchantNo`、`GET /mp/favorite/store` |
| C 端入口 | 店铺页收藏按钮、「我的」页「我的收藏」商品/店铺两栏 |
| **线上数据** | **0 行** |

**0 行不是入口问题**。入口在、点得动、接口通 —— 没人点是因为**收藏了什么都不发生**。
所以增量不在「再加一个关注按钮」，在三件事：

| 批 | 内容 | 档位 | 为什么 |
|---|---|---|---|
| **A** | 商家上新 / 开活动 → 给收藏者推小程序订阅消息 | 1 | 这才是收藏的价值。没有它，收藏是个只写不读的表 |
| **B** | b-app 工作台显示「N 人收藏本店」 | 1（新 /biz 端点 → 七处登记） | 商家看不到就不会有动力经营收藏者 |
| **C** | 店铺页显示「N 人收藏」，**0 人时不显示** | 1（C 端要一个计数） | 社会证明；0 人时显示等于自曝冷启动（与 §7.4 同一取向） |

**命名保持「收藏」不改成「关注」**：改名要动三语 i18n + 现有测试 + 用户已有认知，
而功能收益为零。文档里以后统一说「收藏」，别再出现两个词。

### 8.3 邀请拉商家：字段在端内，奖励规则在站外

用户要「邀请拉商家」的方案。**§3.3 那条不做的仍然成立** ——
小程序里出现「邀请商家入驻得 X 元」是拉人头 + 奖励，
比单纯的「我要开店」入口（§4.1 已放开）风险高一个量级：前者是分销特征，
被判平台型经营会整包驳，而 §4.1 那条开关只能止住入口、止不住已经提交过的包。

所以切成三段，**归因链完整而端上零宣传**：

```
① 小程序侧 —— 只留字段，零奖励文案
   入驻表单加一行「推荐人手机号（选填）」
   → mch_entity_apply 加列 referrer_phone
   → 端上不写任何奖励规则、不写「得多少钱」

② 站外宣传 —— 官网 + 企微（微信类目管不到这两处）
   官网招商页与企微话术里写清「推荐一家店，双方各得 X」
   配合 §4.2 已填的 salesPhone=18503088359 与待填的企微二维码

③ 运营端发奖 —— 人工把关
   审核页显示 referrer_phone
   → 审核通过后运营给推荐人发券
   → 不做自动发奖：奖励规则一旦要在端上展示就踩线
```

**为什么这样切是对的**：`referrer_phone` 是中性字段（记录来源，任何平台都有，
审核时也本来就要知道这家店哪来的）；奖励规则只在站外出现；归因靠手机号对人。
**代价是发奖要人工** —— 首批一个月可能十几笔，这个代价远小于整包被驳。

**不做的**：不在 C 端展示「我推荐了几家店」。那等于把奖励规则搬回端内。

### 8.4 实施顺序

按「独立性 × 价值 ÷ 风险」排，每批可单独上线：

| 批 | 内容 | 依赖 | 档位 |
|---|---|---|---|
| **批 1** | §8.3 的 `referrer_phone`：加列 + 实体字段 + C 端表单一行 + 运营端审核页显示 | 无 | 1 |
| **批 2** | §8.2 的 C + B：收藏数展示（店铺页 + b 端工作台） | 无 | 1 |
| **批 3** | §8.2 的 A：收藏者触达（订阅消息） | 要先在微信后台配模板 ID | 1 |
| **运营动作** | §8.1 建裂变活动并填两道闸 | 要运营账号 | — |

**批 3 有外部前置**（微信订阅消息模板要人去后台申请），所以排最后 ——
排前面会让整条链卡在一个我们控制不了的审批上。

## 10. 批 3：新品开售提醒（2026-09-28 设计）

状态：**已实现（2026-09-28）** · 档位 1 · 对账见 §10.6 · 待真机验 AC1 与配生产 env

### 10.1 设计前提换过一次

§8.4 把这一批排最后，理由是「微信订阅消息模板要人去后台申请」。
**这个前提不成立**：登进 mp 后台一看，`ro****1501` 在 **2026-09-03** 就选好了
「新品开售提醒」（模板 `RpcP4uNQriF7fDw1Jz8oU805jjtPyBzTgL9NrDOlMJ8`，模版编号 383）。

真正的约束是另一条，而且更硬：**长期订阅拿不到**。
后台「公共模板库 → 长期订阅」这一栏写着「暂时没有可选用的模板」——
官方只向政务民生、医疗、交通、金融、教育等线下公共服务开放。
「会员订阅（Beta）」也不行，它要虚拟支付订阅制。

所以 §8.2 A 原本设想的「收藏了这家店 → 以后上新一直收到通知」**在微信上不可能**。
能做的只有一次性订阅：**一次授权 = 一条消息**，发完即止。

这不是打折，是换了一种东西：它从「订阅关系」变成了「一次预约」。
设计要顺着这一点走，而不是假装还能长期推送。

### 10.2 验收标准

| AC | 内容 |
|---|---|
| **AC1** | 在店铺页点「收藏」时弹订阅授权；点「允许」后后端额度 +1（`notify_subscribe`） |
| **AC2** | 该店有商品**第一次**上架时，给有额度的收藏者各发一条「新品开售提醒」 |
| **AC3** | 同一件商品**只通知一次** —— 下架再上架不再发 |
| **AC4** | 没 openid / 没额度 / 没配模板号 → 静默跳过，不报错、不让事件重试 |
| **AC5** | 一次授权只够一条：发完额度归零，下次上新收不到（**这是设计，不是缺陷**） |
| **AC6** | 店铺一个收藏者都没有时，不产生任何发送开销 |

### 10.4 三个不显然的决定

**① 幂等靠 `prd_goods.new_notified_at`，不靠「上架」这个动作。**
`setOnSale(true)` 在 `MerchantGoodsServiceImpl` 里有 **5 处**调用点，
多数是「下架后重新上架」。挂在动作上的话，商家反复上下架就能给收藏者刷屏，
而且加第 6 处调用点的人不会知道要带上这件事
（同一类坑：新枚举值漏进老分支）。

挂在列上则天然幂等：为空才发，发完写上。**第 6 处调用点什么都不用改。**

**② 站内信默认关（`INAPP enabled=0`），只开 `WXSUB`。**
`NotificationConsumer` 的类注释写着「只发收件人**必须知道**的事」——
上新是营销，不是事实记录，塞进消息中心会稀释「到货了去取」那几条。
而订阅消息这一路有用户当场点过的授权把关，且额度天然限流。
要开站内信，运营在后台那一屏打开即可，不用发版。

**③ 模板的「温馨提示」那一格用来引导续订。**
一次授权只够一条，用户收到之后这条链就断了。
`thing7` 写「想继续收到，回店铺再点一次收藏」——
否则用户会以为自己还在订阅中，而实际上再也收不到。

### 10.5 为什么不做「一次授权攒多条」

微信允许用户勾「总是保持以上选择」从而静默复用授权，但那是用户的选择，
不是我们能替他做的。代码层面**不得**用反复弹窗去攒额度：
一次交互弹多次授权会被判骚扰，而且弹窗必须由点击行为触发，攒不起来。

### 10.7 偏差说明

**① 删掉了一个多余的数据域旁路。** `StoreFavoritePortImpl` 第一版写了
`executeWithoutScope`，理由是「带域表在 SELF 维度下会 fail-closed」。消融两次都没红，
查 `DataScopeRegistration` 才知道：登记的 114 张表里**没有任何 `usr_` 表**，
数据域是商家/门店维度的，用户域的表本来就不受它管。
`StoreFavoriteServiceImpl#countByMerchant` 的注释里已经记过同一件事 —— 我又踩了一遍。
已删除，注释改成真正要守的那条（这是跨用户查询，别加 userNo 条件）。

**② 场景×通道守卫改了判据，不是放宽。** `SceneChannelSeedTest` 原本要求
**每个**场景的 `INAPP` 必须开着（「站内信是必达事实记录」），而这是仓库里
**第一个非事实类场景**。没有直接放宽断言，而是在 `NotifyScene.MARKETING` 里
显式声明它的类别，守卫按类别分流 —— 其余七条事实类场景仍然被拦着，
且营销类仍要求「有 INAPP 行」（可以关着），否则运营在后台连开都开不了。

**③ 默认话术从网关上移到 sender。** 「想继续收到，回店铺再点一次收藏」原本写在
真网关的默认值里，于是桩世界看不到它 —— 而「用户到底有没有被告知」
恰恰是这条设计成不成立的关键，测不到等于没做。另外两条场景的默认话术
（「包裹已到自提点」）确实是通道话术，留在网关里没动。

**④ 迁移号从 V354 改到 V356**：写的时候 V354/V355 已被同伴占用，本地不报、上生产才炸。
