## 零、本次范围

## 一、数据库设计

### 1.1 `usr_merchant_payment` —— 商家 × 通道的进件与能力

对应总方案 §3.2。**一个商家在每个通道有独立的一行**。

```sql
CREATE TABLE IF NOT EXISTS usr_merchant_payment
(
    id                    BIGINT       AUTO_INCREMENT PRIMARY KEY,
    merchant_no           VARCHAR(64)  NOT NULL,
    -- WECHAT / ALIPAY。留字符串不留枚举表：加通道是配置不是建模
    channel               VARCHAR(16)  NOT NULL,

    -- 该通道下的主体类型。**可能与其它通道不同**（微信进小微、支付宝进个体户），
    -- 所以它在这张表上而不是 usr_merchant 上
    subject_type          VARCHAR(16)  NOT NULL DEFAULT 'MICRO' COMMENT 'MICRO/INDIVIDUAL/ENTERPRISE',

    sub_mchid             VARCHAR(64)   NULL COMMENT '二级商户号，进件成功后回填',
    channel_apply_no      VARCHAR(64)   NULL COMMENT '通道侧的进件申请单号（区别于平台入驻的 apply_no）',
    apply_status          VARCHAR(16)  NOT NULL DEFAULT 'NONE' COMMENT 'NONE/APPLYING/ACTIVE/REJECTED/FROZEN',
    reject_reason         VARCHAR(512)  NULL COMMENT '驳回原因，原样给商家',

    -- **通道回执的实际授权**，不按主体类型推断（总方案 §2.1）。
    -- 推断会在规则变化时静默失效：以为个体户有 App 支付，实际进件时没勾那个经营场景。
    pay_methods           JSON          NULL COMMENT '["JSAPI","APP","H5","NATIVE"]',

    invoice_capable       TINYINT      NOT NULL DEFAULT 0 COMMENT '能否开票 —— 下单前要披露',

    -- 结算账户只存脱敏与类型，真实账号由后端/通道持有（ADR-002 §5）
    settle_account_type   VARCHAR(24)   NULL COMMENT 'PERSONAL_BANK/CORPORATE_BANK',
    settle_account_masked VARCHAR(64)   NULL,

    -- 手续费承担方（总方案 §6.2）。按主体分档时用它落每商家的实际约定
    fee_bearer            VARCHAR(16)  NOT NULL DEFAULT 'MERCHANT' COMMENT 'MERCHANT/PLATFORM',

    applied_at            BIGINT        NULL,
    activated_at          BIGINT        NULL,
    tenant_no             VARCHAR(32)  NOT NULL DEFAULT 'MAIN',
    created_at            DATETIME     NOT NULL,
    created_by            VARCHAR(64)   NULL,
    updated_at            DATETIME     NOT NULL,
    updated_by            VARCHAR(64)   NULL,
    version               BIGINT       NOT NULL DEFAULT 0,
    deleted               TINYINT      NOT NULL DEFAULT 0,

    -- 一个商家一个通道只能有一条
    UNIQUE KEY uk_mp_merchant_channel (merchant_no, channel),
    -- 分账回调按 sub_mchid 反查
    KEY idx_mp_sub_mchid (sub_mchid),
    -- 运营看「哪些进件卡住了」
    KEY idx_mp_status (apply_status, channel)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT '商家支付进件（每通道一条）';
```

> ⚠️ 约束名带 `mp_` 前缀：MySQL 的索引名是**表级**唯一、H2 是 **schema 级**唯一。
> 不带前缀迟早与别的表撞车（`stl_split_log` 已经踩过一次，注释里有记录）。

### 1.2 `sys_channel_category_rule` —— 端 × 品类 可售规则

对应总方案 §4.1。**规则是数据不是常量**，因为 Apple 的规则会变，改表不用发版。

```sql
CREATE TABLE IF NOT EXISTS sys_channel_category_rule
(
    id            BIGINT       AUTO_INCREMENT PRIMARY KEY,
    -- 端，不是支付通道：IOS/ANDROID/MP_WECHAT/MP_ALIPAY/H5
    scene         VARCHAR(16)  NOT NULL,
    category_type VARCHAR(16)  NOT NULL COMMENT 'GOODS/FRESH/SERVICE/VIRTUAL/CARD',
    sellable      TINYINT      NOT NULL DEFAULT 1,
    -- 不可售原因：给运营看，也直接作为端上的提示文案来源
    reason        VARCHAR(255)  NULL,
    updated_by    VARCHAR(64)   NULL,
    tenant_no     VARCHAR(32)  NOT NULL DEFAULT 'MAIN',
    created_at    DATETIME     NOT NULL,
    created_by    VARCHAR(64)   NULL,
    updated_at    DATETIME     NOT NULL,
    version       BIGINT       NOT NULL DEFAULT 0,
    deleted       TINYINT      NOT NULL DEFAULT 0,
    UNIQUE KEY uk_ccr_scene_category (scene, category_type)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT '端 × 品类 可售规则（iOS IAP 约束等）';
```

**初始数据**：25 行（5 端 × 5 品类）全部 `sellable=1`，
仅 `(IOS, VIRTUAL)` 置 0，`reason='iOS 平台规则限制，请在小程序端购买'`。

> 全量铺 25 行而不是「只存例外」：**缺行时的默认值是个陷阱**——
> 新增品类或新增端时，「查不到=可售」会静默放行，而这正是审核被拒的场景。
> 全量存在，运营也能一眼看全。

### 1.4 数据归属说明

| 数据 | 落在哪 | 为什么不落在别处 |
|---|---|---|
| 商家主体类型 | `usr_merchant_payment.subject_type` | 各通道可能不同，放 `usr_merchant` 表达不了 |
| 可用支付方式 | `usr_merchant_payment.pay_methods` | 通道回执，不可推断 |

| 商品例外 | `prd_goods.sellable_override` | 个别例外，不是常态 |
| 积分开关 | `usr_merchant.points_enabled`（V17 已有） | 与通道无关，是商家级属性 |

## 二、核心逻辑

### 2.1 三个判断函数

**同一份规则，三处使用**（列表 / 结算 / 下单）。做法：
**规则表由后端下发给端上，两侧用同一套判断逻辑。**

```ts
// packages/shared/src/capability/index.ts  —— 端上与 mock 共用
// 后端 Java 侧实现同名逻辑，两边由守卫测试比对用例

type Scene = "IOS" | "ANDROID" | "MP_WECHAT" | "MP_ALIPAY" | "H5";
type Channel = "WECHAT" | "ALIPAY";
type PayMethod = "JSAPI" | "APP" | "H5" | "NATIVE";

/** 端 → 该端使用的支付产品 */
const SCENE_PAY_METHOD: Record<Scene, PayMethod> = {
  MP_WECHAT: "JSAPI",
  MP_ALIPAY: "JSAPI",
  IOS: "APP",
  ANDROID: "APP",
  H5: "H5",
};

/** ① 这件商品在这个端能不能卖 —— 总方案 §4 */
export function canSell(
  goods: { categoryType: string; sellableOverride?: Record<string, boolean> },
  scene: Scene,
  rules: ChannelCategoryRule[],
): Verdict {
  // 商品级例外优先
  const ov = goods.sellableOverride?.[scene];
  if (ov === false) return deny("该商品在当前端不可售");
  if (ov === true) return allow();

  const rule = rules.find((r) => r.scene === scene && r.categoryType === goods.categoryType);
  // 查不到不是「放行」而是「拒绝」：新增品类/端时静默放行正是审核被拒的场景
  if (!rule) return deny("该品类在当前端的售卖规则未配置");
  return rule.sellable ? allow() : deny(rule.reason);
}

/** ② 这个商家在这个端能不能收钱 —— 总方案 §5.1 */
export function canPay(
  payments: MerchantPayment[],   // 该商家的全部进件记录
  scene: Scene,
  channel: Channel,
): Verdict {
  const p = payments.find((x) => x.channel === channel);
  if (!p) return deny("商家未开通该支付方式");
  if (p.applyStatus !== "ACTIVE") return deny("商家支付进件未完成");
  const need = SCENE_PAY_METHOD[scene];
  if (!p.payMethods.includes(need)) return deny("商家在当前端不支持支付");
  return allow();
}

/** ③ 积分是否生效 —— 总方案 §8.1（含小微前置） */
export function canPoints(ctx: {
  globalOn: boolean;
  communityOn: boolean;
  merchantOn: boolean;
  subjectType: string;
}): Verdict {
  if (!ctx.globalOn) return deny("积分功能未开放");
  if (!ctx.communityOn) return deny("本社区暂未开放积分");
  // 小微不参与积分：主体前置在商家开关**之前**判，
  // 因为它是「不可开」而不是「关着」，提示语也不同
  if (ctx.subjectType === "MICRO") return deny("本店暂不支持积分（升级为个体工商户后可开启）");
  if (!ctx.merchantOn) return deny("本店未开启积分");
  return allow();
}
```

`Verdict` 统一形状 `{ ok: boolean; reason?: string }`——
**每一处拒绝都要能说出原因**，不能只返回 false（总方案 §5.1）。

### 2.2 规则怎么到端上

```
端启动 / 进入首页
   └─ GET /mp/capability?scene=IOS
         ├─ rules[]        端 × 品类 规则（该端的 5 条）
         ├─ channels[]     该端可用的支付通道
         └─ version        规则版本号，端上缓存用
```

- 端上缓存 `version`，变了才重新拉
- **服务端不信任端上的裁剪**：下单接口重新跑一遍三个函数
- 这是「一份规则三处用」的落法：端上用于展示裁剪，服务端用于兜底

### 2.3 下单时的判断链

```
POST /mp/order  { items, scene, channel, ... }
   │
   ├─ 1. 逐个商品 canSell(goods, scene)          ✗ → 400 + 原因
   ├─ 2. 逐个商家 canPay(payments, scene, channel) ✗ → 400 + 原因
   ├─ 3. 按商家拆子订单
   ├─ 4. canPoints(...) 决定积分抵扣是否生效
   ├─ 5. 计价（券 → 积分 → 运费，顺序见积分域 R1.4）
   └─ 6. 调通道合单支付，**必带分账标识**
```

> 第 6 步的分账标识**只能在下单时传，事后无法补**——
> 漏传的订单资金不冻结，售后时追不回（总方案 §2.2）。
> 实现上应当**在 Gateway 层强制**：不接受「不带分账标识」的下单参数，而不是靠调用方记得传。

### 2.4 结算流程

沿用[总体逻辑 §3](./收款与分账-总体逻辑.md) 的核心决定：**抽佣与解冻同一时点，且在售后期之后**。

```
定时任务：扫描可结算子订单
   条件：履约完成 AND 售后期已过 AND 无进行中售后
   │
   ├─ 生成 stl_bill（一子单一张，唯一键保证幂等）
   │     channel / pay_scene / channel_fee_* 从订单带入
   │     gross_minor = 实付 − channel_fee_minor    ← 扣费后才是可分金额
   │
   ├─ 调 SplitGateway(channel).split(...)  带 requestNo 幂等号
   │     platform_fee = gross_minor × commission_rate
   │     service_fee  = 自提单的履约服务费
   │
   └─ 解冻剩余 → 商家可用余额
```

**恒等式**（每张单必须成立，对账任务校验）：

```
gross_minor = commission_minor + service_fee_minor + net_minor
```

### 2.5 兜底调度

冻结窗口按通道不同（微信分账 30 天 / 收付通 180 天，支付宝待确认）：

```
定时任务：扫描逼近冻结窗口的子订单
   截止时间 = 支付时间 + 该通道的冻结窗口 − 安全余量
   到点仍未结算 → 强制发起结算，并告警
```

> `FROZEN_BACK` 不是异常分支是**必然分支**：超期资金自动解冻，佣金就收不到了。
> 截止时间**按通道分别计算**，不能用统一常量（总方案 §4.2）。

## 三、API 设计

### 3.1 C 端 `/mp/**`

| 方法 | 路径 | 说明 | 出参 |
|---|---|---|---|
| GET | `/mp/capability` | 当前端的可售规则与可用通道 | `CapabilityResp` |

`CapabilityResp`：

| 字段 | 类型 | 说明 |
|---|---|---|

## 四、状态机

### 4.1 进件 `apply_status`

```
NONE ──▶ APPLYING ──▶ ACTIVE ──▶ FROZEN ──▶ ACTIVE
            │                        
            └──▶ REJECTED ──▶ APPLYING（补材料重提）
```

| 迁移 | 触发 |
|---|---|
| `NONE → APPLYING` | 商家或运营发起进件 |
| `APPLYING → ACTIVE` | 通道回调进件成功 |
| `APPLYING → REJECTED` | 通道驳回，`reject_reason` 原样存 |
| `REJECTED → APPLYING` | 补材料重提 |
| `ACTIVE ⇄ FROZEN` | 平台风控冻结/解冻 |

**非法迁移必须拒绝**——与订单、售后、评价同一套做法（`*_TRANSITIONS` 常量 + 断言）。

### 4.2 结算 `stl_bill.status`

不变，沿用已有的 `PENDING/SPLITTING/SPLIT/FAILED/FROZEN_BACK`。

## 五、幂等与并发

| 场景 | 手段 |
|---|---|
| 重复下单 | `idempotencyKey`（已有） |
| 重复生成结算单 | `uk_sub_order` 唯一键（已有） |
| 重复分账指令 | `stl_split_log.uk_split_request_no`（已有） |
| 重复进件 | `uk_mp_merchant_channel` 唯一键 |
| 进件回调乱序 | 状态机 + 乐观锁 `version` |

**条件写在 WHERE 里，靠影响行数判定**——与券领取、库存锁定同一写法：

```sql
UPDATE usr_merchant_payment
   SET apply_status = 'ACTIVE', sub_mchid = #{subMchid}, version = version + 1
 WHERE merchant_no = #{merchantNo} AND channel = #{channel}
   AND apply_status = 'APPLYING' AND deleted = 0
```

返回 0 行 = 状态已变（回调重复或乱序），**不报错、不重试，记日志即可**。

## 七、验收

### 7.1 守卫测试（新增）

| 断言 | 防住什么 |
|---|---|
| `canSell` 规则缺失时**返回拒绝**而非放行 | 新增品类/端时静默放行 → 审核被拒 |
| `canPoints` 对 `MICRO` 恒拒绝，**且早于商家开关判断** | 小微被强制开或被误开 |
| `sys_channel_category_rule` 初始数据**恰好 25 行** | 漏配某个组合 |
| `stl_bill` 恒等式 `gross = commission + service + net` | 分账算错 |
| 三个函数的用例表**前后端一致** | 一份规则三处用，实现却分叉 |

### 7.2 人工验收红线

沿用[总方案 §八](./多端多通道-平台能力总方案.md)的 12 条，本次新增：

13. `pay_methods` 只能由**通道回调**写入，任何按主体推断的代码路径视为缺陷
14. 下单接口**必须重跑** `canSell` / `canPay`，端上裁剪仅用于展示
15. 分账标识在 **Gateway 层强制**，不接受不带该标识的下单参数

## 八、与待确认项的关系

本设计**不阻塞于任何外部确认**——待确认项影响的是数据，不是结构：

| 待确认 | 影响 | 本设计的处理 |
