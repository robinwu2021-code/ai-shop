先修这四处，再谈商户类型改造。

## 二、最要紧的发现：同一种断法出现了四次

| # | 闸门读什么 | 数据源 | 结果 |
|---|---|---|---|
| 1 | ops 资质授权读 `m.qualifications` | 后端 VO **没有这个字段** | ~~真接口下 TypeError 崩页~~ **已修，见 §四P0-1** |
| 2 | 上架闸门读 `mch_qualification` | 入驻通过时**不写入** | 表恒空 → 闸门恒不触发 |
| 3 | 积分抵扣读 `balance` | 发放只写 `pending_balance`，`available_at` **全库零写入** | 余额恒 0 → 抵扣恒失败 |
| 4 | 积分开关读 `supports_subsidy` | **零读取** | 不支持补差的通道照样开积分 |

**四条的共同点：都不抛错，都表现为「配置了但没生效」。**
这类问题的排查成本极高 —— 人会先怀疑数据、再怀疑配置，最后才怀疑链路没接。

### 2.1 ops 资质崩页（已核实，最急）

```
ops-web/lib/types/merchant.ts:69        qualifications: string[]      ← 声明为必填
ops-web/app/merchants/authorize-tab.tsx:72   m.qualifications.length       ← 直接取
                                       :116   current.qualifications.includes(...)
backend/.../MerchantGovernService.java:101-105  MerchantProfileVO           ← 无此字段
```

真接口返回的对象没有 `qualifications`，前端按必填数组用 —— **`undefined.length` 抛错**。
现在没暴露是因为 ops-web 走 mock（`ops-web/lib/mock/db/merchant.ts:12` 有这个字段）。

> 这正是 git log 里那条已归档结论的又一例：
> **「契约有、后端不发」是字段问题，不是类型问题** —— 类型检查过得去，运行时才炸。

### 2.2 资质链路整体断裂（已核实）

```
b-app 入驻表单收 licenses（图片 URL 数组）
   ↓  apply/index.vue:127
mch_entity_apply.qualifications（JSON）
   ↓  ✗ 审核通过时不转存
mch_qualification（结构化表）          ← 恒空
   ↓
上架闸门 hasExpiredQualification / 类目授权码   ← 恒不触发
```

- 唯一写 `mch_qualification` 的是 ops 手工登记接口
  （`OpsQualificationController.java:51-63`）—— 而**它在 ops-web 里没有任何调用方**
- 商家传的执照图，除了审核抽屉里几个文件名链接外**没有下游消费者**
- 进件时的 licenses 是商家**重新上传的另一份**（`b-app/src/pages/payment/index.vue`）

**结果：资质过期闸门、类目授权闸门，两个都写好了，都从不触发。**

### 2.3 积分发了永远花不掉（已核实）

```java
// PointsServiceImpl.java:455-476  grantOnPay
accountMapper.grantPending(...)        // 只加 pending_balance
// ✗ 全程没有 setAvailableAt
```

全库 `available_at` **零写入点**（已 grep 确认）。注释说「转正由独立任务负责」——
**那个任务不存在**（`@Scheduled` 只有 `ReconScanJob`、`QualificationExpiryJob`）。

后果链：`balance` 恒 0 → `deductOnPlace` 余额闸算出 0 → 抵扣永远抵不了；
`account()` 的 `nextActivate` 因 `available_at` 为 NULL 恒返回 null → 页面连「何时生效」都显示不了。

> 当前未暴露，因为 `FEATURES.points = false`。**但这是上线即炸的那种没接。**

### 2.4 唯一真正拦执照的地方，不在入驻

| 位置 | 拦不拦 |
|---|---|
| b-app 入驻提交校验 | ❌ `canSubmit` 不含 licenses |
| 后端 `createApply` / `auditApply` | ❌ 都不检查 |
| **进件 `MerchantPaymentServiceImpl:301-316`** | ✅ **唯一硬拦** |

也就是说：**没有执照的商家可以完成入驻、建店、上架**，
直到他去做支付进件那一刻才被拦。而入驻通过时系统已经自动为他建好了
`mch_payment_merchant` 行（`MerchantPortImpl:481-499`，`apply_status=APPLYING`）。

### 2.5 更正：`NO_INVOICE` 不是「一次点击」—— 它根本点不到

本文初稿把 `NO_INVOICE` 列为 P0，理由是「运营点一下即可标记无票并放行付款」。
**实测之后这条不成立**：

| 层 | 现状 |
|---|---|
| 后端端点 | ✅ 存在，且 `reason` 已必填校验、权限限 `FINANCE_INVOICE_VERIFY` |
| **ops-web 页面** | **不存在** —— `app/finance/` 下只有 `invoice-tab`（销项票申请）、`withdraw-tab`、`fee-rule-tab`，**没有应付账款页** |
| 前端调用 | 全库 `noInvoice` 零命中 |

所以真实状况与初稿相反：**不是太容易点，是够不着**。
后端能力存在但运营用不了 —— 这是「功能不可达」，不是「防护不足」。

> **我犯的是这轮反复在提醒别人的那个错**：
> 从「端点存在」推出「有人在点它」，没有去看 UI 层。
> 与「从字段存在推出业务链路」同一类。记在这里，因为下一个读这份文档的人
> 会照着 P0 列表去改代码。
>
> 修正后的动作：**本轮不做**。将来建应付账款页时，把
> 「无票支出不得税前扣除」的说明与显式知悉勾选作为**首日要求**，
> 而不是先建页面再补警示。

### 2.6 全量查库：三条推断转实测，一条定性更正

#### 实测数据（本地库，2026-08-13）

| # | 查什么 | 结果 |
|---|---|---|
| ① | 主体档位 × 门店经营模式 | **145 家门店无一例外全是 `SELF_OPERATED`**（99 家无照 + 46 家个体户） |
| ② | 结算单 × 进项票状态 | 60 张单**全部 `PENDING_INVOICE`**；`MICRO` 50 张 ¥1,415.50 / `INDIVIDUAL` 10 张 ¥460.18 |
| ③ | `stl_purchase_invoice` | **0 行** |
| ④ | `mch_qualification` | **0 行** |

#### 三条推断 → 实测确认

| 原推断 | 实测 |
|---|---|
| 上架资质闸门读的表是空的（§2.2 由代码推理） | ✅ `mch_qualification` **实测 0 行**，闸门确实永不触发 |
| `NO_INVOICE` 从来没人走过（§2.5） | ✅ 60 张单**零张** `NO_INVOICE`、零张 `VERIFIED` |
| 第三方模式没落地 | ✅ **一家门店都没有** `THIRD_PARTY` —— 该轨道从未被走过 |

#### 定性更正：是结构性风险，不是已发生的敞口

初稿把「99 家无照 × 自营 × 50 单」写成需要交财务确认的**已发生税务敞口**。
**项目尚未上生产，这些全是本地测试数据** —— 没有一笔真钱，没有一张真票。

准确的说法：

| 不是 | 是 |
|---|---|
| 已经产生了不可扣除的成本 | **代码路径允许它，且默认就会走到** |
| 要财务追认历史账 | 要在上生产**之前**补上校验 |

**这个区别改变了优先级**：不必倒查历史，但**上线前必须堵住**。
`business_mode` 默认自营 + 无「无照禁自营」校验，意味着生产第一天就会复现同一批数据。

#### 新发现：V23 的 DEFAULT 已经回填过一次存量

库里 54 张 `business_mode = SELF_OPERATED` 的单，状态却是 `PENDING` ——
**那是第三方轨道的状态**。代码分支本身是对的
（`SettleServiceImpl:201` `selfOperated ? PENDING_RECON : PENDING`），所以只能是数据来源问题。

时间对得上：

| | 时间 |
|---|---|
| 54 张 `PENDING` 单创建于 | 08-10 00:02 ~ **08-11 13:14** |
| **V23 加 `business_mode` 列** | **08-11 15:18** |
| 3 张 `PENDING_RECON`（正确的自营状态）创建于 | 08-12 之后 |

`V23__self_operated_settle.sql` 里那句

```sql
ALTER TABLE stl_bill ADD COLUMN business_mode VARCHAR(16) NOT NULL DEFAULT 'SELF_OPERATED'
```

**把 54 张历史第三方单回填成了自营**。

> 这正是[分步实施方案](./平台优化-分步实施方案.md) §0.2 与第六步反复警告的那条 ——
> **「新增默认最严」是安全设计，「存量默认最严」是生产事故**。
> 我当时是从设计推理出来的，现在有了实证：**它已经在 V23 上发生过一次。**
>
> 后果：这 54 张单的 `business_mode` 快照是假的 —— 走不进自营对账
> （`confirmRecon` 要求 `status = PENDING_RECON`），也回不去第三方分账。**卡死了。**
> 测试数据无所谓，但同样的写法上生产就是真事故。
>
> **第六步的 `GRANDFATHERED` 方案因此不是过度设计，是必需的。**

## 三、商户类型的结论落到现状

### 3.1 好消息：`legal_form` 已经贯通全链

```
b-app 入驻表单选主体  →  apply  →  mch_entity.legal_form  →  进件档位推导
                                        ↓
                              ops 商家档案 legalForm  +  C 端 merchant.type chip
```

**三分改造（自然人/个体户/企业）不需要新建链路，是在既有链路上换取值。**

### 3.2 坏消息：C 端直接把「小微」这个错名显示给了消费者

`c-app/src/pages/merchant/index.vue:61-77` 渲染 `merchant.type` chip，
i18n 取值就是 `MICRO`/`INDIVIDUAL`/`ENTERPRISE`（`i18n/locale/zh-CN.ts:239`）。

消费者看到「小微」，理解的是法规意义上的**小微企业（有照）**，
而实际含义是**无照自然人**。[§商户类型定义 6.4④](./商户类型定义.md) 讲的重名风险，
**在 C 端已经发生了**。

### 3.3 电商法 §37 自营标记：C 端零处

C 端**全链路零处**区分自营与第三方（已核：`SELF_OPERATED|businessMode|自营`
在 c-app 生产代码命中 0，唯一「自营」文案是未被引用的死 i18n key）。

而 `mch_store.business_mode` 默认 `SELF_OPERATED` —— **意味着现在所有店都是自营，
且没有一处告诉消费者**。§37 要求自营业务显著标记，这是法定义务。

连带的两处：

| | 现状 | 应该 |
|---|---|---|
| 售后 | 自营店的售后也派给「商家」（即平台自己），走商家审 + 平台仲裁两段 | 自营应直接进平台客服 |
| 发票 | 无开票入口；只有下单前一句「以下商家无法开具发票」（`order-confirm/index.vue:108`，判据 `invoiceCapable: !m.micro`） | 自营下平台是销售方，**平台开票** |
