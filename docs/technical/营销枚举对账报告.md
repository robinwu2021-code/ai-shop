# 营销活动 · 枚举对账报告（只读，不动代码）

## 0. 先更正我自己

《枚举统一方案》§1 ⑤ 写的是「**三端三套词，一个都对不上**」，并把
`FULL_REDUCE`/`GIFT`/`BUY_N_GET_M` 全列为同物异名。

**这个结论是错的。** 我把三个不同的东西当成了一个字段来比对。
查清之后，实际是三个各自独立的概念：

| # | 概念 | 载体 | 状态 |
|---|---|---|---|
| ① | 店铺级营销活动 | `mkt_campaign.type` | **三端已对齐** ✅ |
| ② | 商品级买赠促销 | `Goods.promotions[].type` | 端上独有，后端无此字段 |
| ③ | 平台投放场次 | ops-web `Campaign` | 后端未实现，**有意不同名** |

错因是方法上的：我按「名字像营销活动的枚举」去搜，搜到了 ops-web 的
`CampaignType` 和 shared 的 `PROMOTION_TYPE`，就没有再往下看 shared
自己的 `CampaignType`（它在 `types/index.ts`，与常量文件不在一处）。
**只比对名字相近的声明，会把不同层的东西并到一起。**

## 1. 逐个核对

### ① 店铺级营销活动 —— 已对齐，无事可做

| 位置 | 取值 |
|---|---|
| 库 `mkt_campaign.type` | `COUPON` `FULL_CUT` `FLASH` `BUY_GIFT` |
| 后端 `MktCampaign` 常量类 | 逐字一致 ✅ |
| shared `CampaignType` | 逐字一致 ✅ |
| b-app i18n 词条键 | `typeCOUPON` / `typeFULL_CUT` / `typeFLASH` / `typeBUY_GIFT` ✅ |

商家建活动这条链，命名上没有任何问题。

### ② 商品级买赠 —— 端上独有

`Goods.promotions[].type = "BUY_N_GET_M"`，配 `buyN` / `giftM`。
C 端商品详情页展示「买 2 送 1」、下单时按它算赠品件数
（`packages/shared/src/utils/promotion.ts`）。

**后端 `GoodsVO` 没有 `promotions` 字段。** 真实环境下它恒为 `undefined`，
于是 `giftQtyFor()` 恒返回 0 —— 商品页不显示买赠，下单也不送赠品。

与 `mkt_campaign` 里的 `BUY_GIFT` 是同一件业务事，两处建模：
一个挂在活动上（`buyN`/`giftM` 两列就在 `mkt_campaign` 表里），
一个挂在商品上。**这不是命名问题，是同一件事建了两次模。**

另有一个 `PROMOTION_TYPE = { BUY_N_GET_M: "BUY_N_GET_M" }` 常量对象，
**全仓零引用** —— 所有地方都直接写字面量。它唯一的作用是让对账工具
以为 shared 用 `BUY_N_GET_M` 表达买赠活动，从而报出一条并不存在的差异。

### ③ 平台投放场次 —— 有意不同名，后端未实现

ops-web `CampaignType = FLASH | SECKILL | FULL_REDUCE | GIFT | NEWCOMER`。

代码里已有明确注释（`ops-web/lib/types/marketing.ts`）说明这是**另一个领域对象**：
带 `position`（秒杀场按投放位置分组做重叠校验），由运营建，
而 `mkt_campaign` 是店铺级的（`entity_no NOT NULL`，不跨店）由商家建。

那条注释还预判了对账工具会报这几个值，并写明「结论不是改名对齐，
而是这块后端还没实现 —— 真按后端那套改，等于把两个概念合并成一个」。
**这个判断是对的**，本次核对确认后端确无对应表。

## 2. 真正的问题不是命名

查这一圈最值得报的不是枚举，是这个：

> **`CampaignService` 的引用方只有它自己的 Controller。
> 后端交易链路完全不读营销活动。**

```
grep -rln "MktCampaign|CampaignService" backend/.../trade  backend/.../product
→ 空
```

也就是说，商家在 b-app 建的活动，后端存下来了，**但没有任何消费方**：

| 活动类型 | 商家以为 | 实际 |
|---|---|---|
| `FULL_CUT` 满减 | 满额自动减 | ~~不减~~ **已接通**（CampaignPort，2026-08-10） |
| `FLASH` 限时特价 | 时段内改价 | ~~不改~~ **已接通** |
| `BUY_GIFT` 买赠 | 随单发赠品 | ~~不发~~ **已接通** |
| `COUPON` 店铺券 | 用户领取后抵扣 | ~~建了不会变成任何可领的券~~ **已接通** |

> **⚠️ 订正（2026-08-10）**：本节初稿写的是「券无处核销」，**那是错的**。
> 后端有**两套互不相干的营销模型**，我当时只 grep 了 `MktCampaign` 就下了结论：
>
> | 模型 | 状态 |
> |---|---|
> | `mkt_coupon` + `mkt_user_coupon` + `CouponPort` | ✅ **完整**：领券 → 下单选券 → 算价扣减 → 核销 → 取消时回滚 |
> | `mkt_campaign` | ❌ 四种类型全部只有 CRUD，读它的只有它自己的 mapper/service/controller |
>
> 所以准确的说法是：**平台券能用，而商家在 B 端建的「店铺券活动」不会生成任何一张券**
> —— `MktCoupon` 本身已经支持商家券（有 `entityNo` 与 `funder=MERCHANT` 两列），
> 缺的只是 `CampaignService` 保存 COUPON 型活动时到 `mkt_coupon` 的那一次写入。
>
> 教训与本文 §0 那条同源：**只查名字相近的东西，会漏掉名字不同的那一半。**

这与之前那个「**只有门槛没有发证机关**」是同一形状的反面：
那次是有校验没有发证方，这次是**有录入没有消费方**。
两者的共同点是——单看任何一端都是完整的，只有把链路走通才会发现断在中间。

四层测试全绿，是因为后端测的是「活动能不能建、字段校验对不对」，
没有任何一条测「建了活动之后，下单金额有没有变」。

## 3. 待业务确认的问题

只有一个问题需要业务回答，且它与命名无关：

> **①（店铺活动）与 ③（平台场次）要不要合并成一张表？**

- 合并：一套增删改查、一套叠加规则。但店铺级与平台级的权限、审核、
  投放位置模型差别很大，硬合会长出一堆 `if (isPlatform)`。
- 不合并：需要给平台场次单独建表。那时**建议复用同一套词**
  （`FULL_CUT` 而不是 `FULL_REDUCE`、`BUY_GIFT` 而不是 `GIFT`）——
  两个领域对象可以不同名，但同一个业务概念在同一个代码库里
  不该有两种拼法，否则第三个人来读时无从判断它们是不是一回事。

`SECKILL` 与 `FLASH`、`NEWCOMER` 的归属，等这个问题定了再谈：
如果不合并，它们就是平台场次自己的取值，无需与 `mkt_campaign` 对齐。

## 5. 进度（2026-08-10 收尾）

**四种类型已全部接通**：满减（CampaignPort.autoDiscount）· 店铺券（CampaignService
保存时桥接到 mkt_coupon）· 限时特价（GoodsQueryPort.snapshot 与商品展示两条路）·
买赠（下单时加赠品行）。共 16 条用例，全部测的是「建了活动之后有没有变」。

### 遗留的三个待确认（都是**模型**层面的，不是实现取舍）

1. **限时特价没有 SKU 维度** —— `mkt_campaign` 是「几个商品 + 一个活动价」，
   多规格商品会被拉成同一个价。实测 G0001 的 10 斤装（¥49.80）与
   20 斤装（¥95.80）现在都是 ¥30.00。**有真实亏损风险**，要改得先改表。
2. **赠品只能是同款** —— 只有 buyN/giftM，没有「赠哪件」。
   端上 `Promotion` 有 giftGoodsNo（买米送油），后端表达不了。
3. **售后退赠没有处理** —— 赠品价格为 0，退款金额不受影响，
   但商家的货实际送出去了。退款时要不要追回赠品需要业务定。
