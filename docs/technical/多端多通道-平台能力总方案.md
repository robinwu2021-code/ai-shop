## 零、一句话架构

**五个维度全部建成数据，用同一套「多级开关求交集」的模式表达；
任何一处判断都是纯函数，前后端共用一份规则。**

不这么做的话，`3 主体 × 2 通道 × 5 端 × 5 品类 × 3 级积分开关` 会变成
散落在几十个文件里的 if——**必然写错，且改不动**。

## 一、五个维度

| # | 维度 | 取值 | 决定什么 |
|---|---|---|---|
| 1 | **主体** | 小微 / 个体户 / 企业 | 能进哪些通道、能用哪些支付方式、能否开票、税务归属 |
| 2 | **通道** | 微信 / 支付宝（预留更多） | 走谁家的钱、费率、进件规则、冻结窗口 |
| 3 | **端** | 微信小程序 / 支付宝小程序 / Android / iOS / H5 | 可用支付产品；**iOS 额外受 IAP 约束** |
| 4 | **品类** | 日用 GOODS / 生鲜 FRESH / 服务 / 虚拟 / 卡券 | 计价与履约策略；**iOS 上的可售性** |
| 5 | **积分** | L1 全局 / L2 社区 / L3 商家 | 能否发放与抵扣（已落地） |

前四个决定**「这件商品此刻能不能被买到」**，第五个决定**「买的时候积分参不参与」**。

## 二、统一模式：多级开关求交集

积分域已经用了这个模式（L1 全局 → L2 社区 → L3 商家，**层层与**），
其余维度照抄，不发明第二套。

```
生效 = L1 平台级 AND L2 中间级 AND L3 最细级
```

| 能力 | L1 | L2 | L3 |
|---|---|---|---|
| **积分**（已落地） | `sys_config.FEATURES.points` | `cmt_community.points_enabled` | `usr_merchant.points_enabled` |
| **端×品类可售** | 平台规则表 | — | 商品级覆盖 |
| **支付可用** | 通道启用 | 商家进件状态 | 该通道授权的支付方式 |

三条统一的原则：

1. **上层关，下层一定关**——不允许下层覆盖上层的关闭
2. **关闭只影响将来**——存量订单、存量积分、存量债务照旧（积分域 R2.2 已定此规矩）
3. **强制开是例外，要有补偿**——`points_forced` 的做法（提前 30 天通知 + 费率补偿 + 申诉通道）
   是所有"平台强制"类开关的模板

## 三、商户入驻：一个商家，多条进件线

### 3.1 现状问题

入驻现在被当成**一次性动作**（`usr_merchant_apply` 一张表、一个 `status`）。
但真实形态是：

- 一个商家要在**多个通道**分别进件，各自有独立状态
- 主体会**升级**（小微 → 个体户 → 企业），升级后要重新进件
- 不同通道的主体类型**可以不同**（微信进小微、支付宝进个体户）

### 3.2 模型

```
usr_merchant                商家主数据（平台侧身份，一个）
   │
   ├── usr_merchant_apply   平台入驻申请（已有，管"能不能上架卖货"）
   │
   └── usr_merchant_payment 支付进件（每通道一条，管"能不能收钱"）  ★ 新建
```

**这两件事必须分开**：平台审核通过（能上架）不等于支付进件通过（能收钱）。
合成一个状态会出现"审核通过了但收不了钱"无法表达。

`usr_merchant_payment` 关键列：

| 列 | 说明 |
|---|---|
| `merchant_no` + `channel` | 联合唯一 |
| `subject_type` | **该通道下的**主体类型 |
| `sub_mchid` | 二级商户号 |
| `apply_status` | `NONE`/`APPLYING`/`ACTIVE`/`REJECTED`/`FROZEN` |
| `pay_methods` | JSON，**通道回执的实际授权**，不按主体推断 |
| `invoice_capable` | 能否开票 |
| `settle_account_masked` | 结算账户（脱敏，真实账号后端持有） |

### 3.3 入驻引导：按目标端倒推主体

商家入驻时**不要问"你想当小微还是个体户"**——他不知道这是什么。
要问**"你想在哪儿卖"**，然后倒推：

| 商家想要 | 最低主体 | 引导话术 |
|---|---|---|
| 只在小程序卖 | 小微（5 分钟） | "身份证 + 银行卡 + 门店照，5 分钟开张" |
| 也要在 App 卖 | **个体户** | "App 售卖需要营业执照，我们可以代办（T+3）" |
| 要给企业客户开票 | **个体户** | "需要开票的话要办执照" |

> 【简单】把合规术语翻译成**商家关心的结果**。
> "小微不能做 App 支付"对商家没有意义，"办了执照才能在 App 上卖"才有。

## 四、可售性：iOS 屏蔽品类怎么做

### 4.1 规则是品类级的，不是商品级的

iOS 的 IAP 约束针对的是**商品性质**（数字内容 vs 实物/线下服务），
所以规则主体应当是**（端 × 品类）**，而不是给每个商品挂一个开关。

```
sys_channel_category_rule    端 × 品类 的可售规则   ★ 新建
    scene           IOS / ANDROID / MP_WECHAT / MP_ALIPAY / H5
    category_type   GOODS / FRESH / SERVICE / VIRTUAL / CARD
    sellable        是否可售
    reason          不可售原因（给运营看，也给端上提示用）
```

一期的初始数据（**待产品确认 `VIRTUAL` 定义后定稿**）：

| 端 | 生鲜 | 日用 | 服务 | 卡券 | 虚拟 |
|---|---|---|---|---|---|
| 微信小程序 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 支付宝小程序 | ✅ | ✅ | ✅ | ✅ | ✅ |
| Android | ✅ | ✅ | ✅ | ✅ | ✅ |
| **iOS** | ✅ | ✅ | ✅ | ⚠️ 待定 | **❌ 屏蔽** |
| H5（海外） | ✅ | ✅ | ✅ | ⚠️ | ⚠️ |

> **为什么用表不用常量**：Apple 的规则会变（2025 年美区外链裁定就是一例），
> 而改常量要发版、改表不用。审核被拒时能当天调整，这是【安全】的一部分。

商品级只保留**覆盖**能力（`prd_goods.sellable_override`），用于个别例外，默认为空。

### 4.2 屏蔽必须发生在列表层

| 层 | 做什么 |
|---|---|
| 商品列表 / 搜索 / 首页楼层 | **直接过滤掉**，不展示 |
| 商品详情（直链进入） | 展示但禁止下单，说明原因 |
| 下单接口 | 服务端拒绝，**不信任端上裁剪** |

> 【安全】只在结算页拦是不够的：用户在 iOS 上看到商品、加了购物车、
> 到结算才被告知买不了——这是差评的直接来源。

## 五、收款与支付路由

### 5.1 判断链

```
用户在 [端] 选了 [通道] 要买 [商品]（属于 [商家]）
   │
   ├─ 1. 品类在该端可售？        sys_channel_category_rule
   ├─ 2. 商家在该通道进件了？     usr_merchant_payment.apply_status == ACTIVE
   ├─ 3. 该端的支付产品被授权？   pay_methods 包含 (端 → 支付产品)
   └─ 4. 都通过 → 可下单
```

四步任何一步不过，**都要给出可读的原因**，不能只返回"不可购买"。

### 5.2 购物车跨通道 / 跨端

合单支付是**单通道内**的。结算页要做两级分组：

```
购物车
  ├─ 按「该端可售」过滤       ← iOS 上先去掉虚拟品类
  └─ 按「可支付通道」分组     ← 微信组 / 支付宝组
        └─ 同组内合单支付
```

推荐策略：**默认选中当前通道可付的那组，其余灰置并说明**。
不要让用户勾选了却在支付时失败。

## 六、分账、抽佣与通道成本

### 6.1 三笔钱要分清

一笔 100 元订单，涉及三个不同性质的数：

| | 是什么 | 谁定 | 落在哪 |
|---|---|---|---|
| **通道手续费** | 微信/支付宝收的 | 通道费率（0.55%–0.6%） | 支付时**先扣**，进商家账户前就没了 |
| **平台佣金** | 平台的收入 | 业务定，按 `trafficSource` 分档 | 分账时从商家账户抽 |
| **履约服务费** | 自提点承接方的收入 | R15 口径（待定） | 分账时抽给承接方 |

```
订单 100 元
  − 通道手续费 0.6 元          ← 通道扣，平台管不着
  = 99.4 元进商家二级商户账户（冻结）
       ├─ 平台佣金   × 费率     ← 基数是 99.4，不是 100
       ├─ 履约服务费（自提单）
       └─ 剩余解冻给商家
```

**佣金基数是扣费后金额**——按 100 算每笔差几分，累积对不上账。

### 6.2 手续费承担方是个产品杠杆

协议允许约定手续费由二级商户或平台承担，**比例可协商**。这不是技术约束：

- 平台承担 → 降低入驻阻力，成本进平台
- 商家承担 → 平台净收入更高，但商家感知费率更高

**建议按主体分档**：小微阶段平台承担（降门槛），升个体户后转商家承担（作为升级激励）。
这需要 `usr_merchant_payment` 上有 `fee_bearer` 列。

### 6.3 通道费率差异**透传给商家，并标注来源**

> **决策（2026-08-06）：按实际通道费率据实结算，账单上标明每笔走的是哪个通道、扣了多少。**

两个通道费率略有差异（微信 0.6%，支付宝 0.55%–0.6%）。
曾考虑由平台吸收差价、对商家用统一名义费率，理由是「商家控制不了用户选哪个通道，
波动无法解释」。**决策改为透传**——因为「无法解释」的前提是账单不告诉他，
而账单一旦标明来源，波动就是可解释的，且据实结算比平台补贴更干净：

| | 透传（采纳） | 平台吸收 |
|---|---|---|
| 商家账面 | 与实际一致，可自行核对 | 与实际有差，只能信平台 |
| 平台 | 无隐性补贴，成本结构清晰 | 要单独记一本通道差价账 |
| 争议时 | **可下钻到单笔，指着通道说明** | 说不清「你的钱去哪了」 |

#### 落地要求

1. **每笔都要落费率快照**——费率会变，历史账不能跟着变。
   沿用 `stl_bill.commission_rate` 已有的做法（注释里就写着这条）。
2. **账单行必须带通道标识**，商家能按通道筛选与汇总。
3. **费率来源要可追溯**：是标准费率还是优惠费率活动，一并记下。
   优惠费率是申请来的、有有效期，到期回落时商家会发现费率变了，
   那时要能答出「哪天起、因为什么」。

`stl_bill` 相应增列：

| 列 | 说明 |
|---|---|
| `channel` | 通道 |
| `channel_fee_minor` | 该笔实际扣的通道手续费 |
| `channel_fee_rate` | **费率快照**（万分比） |
| `channel_fee_source` | `STANDARD` / `PROMO`——费率来源，供追溯 |

#### ⚠️ 一个必须一起解决的副作用

费率透传之后，**商家有动机只进件费率低的那个通道**。

后果不在费率，在**可售性**：商家只进支付宝 → 微信小程序的用户买不到他的货 →
购物车跨通道问题（§5.2）从边缘场景变成常态。

三选一，**需决策**：

| | 做法 | 代价 |
|---|---|---|
| (a) **强制双通道进件** | 平台审核要求两边都进件才能上架 | 入驻门槛提高，与「方便」冲突 |
| (b) 允许单通道，但**在商家端明示后果** | 「只进一个通道，另一端的用户看不到你的货」 | 商家可能仍选单通道，用户体验受损 |
| (c) 平台按通道**调节佣金**抹平商家的通道偏好 | 低费率通道佣金略高，商家无所谓走哪个 | 佣金规则变复杂，且要随通道费率变动维护 |

**倾向 (b)**：把选择权和后果一起给商家，这与「服务范围选错会卖到送不到的地方」
是同一个处理方式（ADR-009 §3 的做法：给出后果说明，不替商家做决定）。
(a) 与「入驻方便」正面冲突；(c) 把简单的事做复杂了。

## 七、对账单：两本账，要能勾稽

### 7.1 资金账（已有 `stl_bill` / `stl_split_log`）

多通道多端之后，`stl_bill` 需要能按多维切分：

| 新增列 | 用途 |
|---|---|
| `channel` | 通道（分账实现路由 + 对账切分） |
| `pay_scene` | 下单端（分析各端产出，也用于排查端相关问题） |
| `channel_fee_minor` | 通道手续费（从对账单回来的真实值） |
| `fee_bearer` | 手续费承担方 |

**恒等式**（每张结算单必须成立）：

```
gross_minor = platform_fee + service_fee + net_minor
```

其中 `gross_minor` 是**扣完通道手续费后**的可分金额。

### 7.2 积分账（已有 `pts_*` / `stl_points_bill` / `stl_points_pool`）

积分是**平台负债**，独立成账。V17 已建好账户、流水、跨商家兑付分摊、备付池。

### 7.3 两本账的勾稽点

**订单里既有钱又有分**，两本账必须能对上：

| 勾稽点 | 资金账 | 积分账 |
|---|---|---|
| 用户积分抵扣 | 商家实收减少 | 用户积分扣减 + 商家收到积分 |
| 商家积分兑付 | 平台付钱给商家 | 商家积分核销 |

> **`ord_sub_order.points_deduct_minor` 是这两本账的连接点**（V17 已落）。
> 对账任务要校验：**资金账里商家少收的部分 = 积分账里商家收到的积分对应金额**。
> 对不上就是有一侧漏记，必须告警。

### 7.4 商家看到的对账单

商家不关心内部分几本账，B 端要给一张**合并视图**：

```
本期账单
  商品收入          ¥ X
  − 通道手续费       ¥ a   （若由商家承担）
  − 平台佣金         ¥ b
  − 履约服务费       ¥ c   （自提单）
  + 积分兑付         ¥ d   （收到的积分换的钱）
  = 实收            ¥ Y
```

每一行**可下钻到明细**。不能下钻的对账单等于没有对账单——
商家质疑时答不上来，就只能靠信任，而信任经不起一次差错。

## 八、积分与其它维度的交互

积分开关已落地，但要补几条与新维度的关系：

| 交互 | 规则 | 理由 |
|---|---|---|
| 积分 × 端 | **与端无关**，各端一致 | 同一个用户在不同端看到不同积分规则，是 bug 不是特性 |
| 积分 × 通道 | **与通道无关** | 积分是平台负债，与走谁家的钱无关 |
| 积分 × 主体 | **小微不参与积分**（已决策） | 见 §8.1 |
| 积分 × iOS 屏蔽品类 | 被屏蔽的品类**在该端不产生积分** | 买不到自然不发分；但**不影响其它端** |

### 8.1 小微不参与积分（决策 2026-08-06）

> **小微主体的商家不发放、也不接收积分。升级为个体户/企业后方可开启。**

理由：积分兑付**涉及平台向商家付钱**，而小微的税务定性本就模糊
（见[税务矩阵 §3.5](./税务方案-主体与渠道矩阵.md)），叠加后平台的扣缴风险更高。
同时它天然成为一个升级激励。

#### 这不只是「关一个开关」——四处连带影响

**① `points_enabled` 对小微是「不可开」，不是「默认关」**

两者差别很大：默认关意味着商家能自己打开。要在 L3 开关上加主体前置：

```
canPoints(merchant) =
      L1 全局 AND L2 社区 AND L3 商家开关
  AND merchant.subject_type != MICRO        ← 新增前置
```

B 端的积分开关对小微商家应当**置灰并说明原因**，而不是隐藏——
隐藏了商家不知道有这回事，也就不知道升级能换来什么。

**② `points_forced` 与主体冲突时，主体优先**

`points_forced`（按行业强制开）遇上小微主体时**不生效**。
这条要显式写进规则，否则「强制开」会绕过主体限制——
而强制开的初衷是行业普及，不是突破合规边界。

**③ 用户侧会出现「有积分但这店不能用」**

积分域 R2.1 定的是 `canIssue == canAccept`（同一个开关，不拆分），
所以小微商家**既不发分也不收分** —— 用户在这家店**不能用积分抵扣**。

这是真实的体验断层，必须在**下单前**说清楚：

| 位置 | 展示 |
|---|---|
| 商品详情 | 不显示「可得 X 积分」 |
| 结算页 | 积分抵扣区**置灰 + 一句说明**，不是直接不显示 |

直接不显示会让用户以为是 bug（"我明明有积分"）。置灰加说明才是诚实的。

**④ 升级后不自动开启**

商家从小微升为个体户后，积分开关变为**可开但默认关**，需商家自己确认。

理由：开启即产生兑付义务（发出去的分是要认的），
**这类会产生债务的动作不能由系统替商家做决定**——
这与积分域 R2.2「关闭只影响将来，存量债务仍需承担」是同一条原则的两面。

## 九、数据模型总表

| 表 | 状态 | 改动 |

## 十、落地顺序

| 阶段 | 内容 | 前置 |

| **P0** | `usr_merchant_payment` + `sys_channel_category_rule` + 三个纯函数 | 无——**现在就能做** |
