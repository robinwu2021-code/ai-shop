## §0 结论先行

按京东自营旗舰店的定位（ADR-011 §4.5），**入驻这件事可以大幅简化，而且骨架都已经在**：

| 能力 | 现状 |
|---|---|
| 平台主动开店（建主体+门店+账号，一次调用） | ✅ `SelfOperatedService.create`，且已设 `FUNDS_AGGREGATED` |
| 代商家进件 | ✅ `merchant:apply:onbehalf` |
| 商家自助申请 | ✅ `mch_entity_apply` 全套 |
| 收款银行账号 | ✅ V358 `mch_payout_account` |
| 资质链路 | ✅ `qualifications` / `qualificationItems` |
| **分阶段要资料** | ❌ **唯一的缺口** —— 现在是一次性提交全套 |

**真正要做的只有一件事：把「一次性交齐」改成「按需要的时机要」。**

---

## §1 为什么现在的入驻偏重

`mch_entity_apply` today 要的是：主体名、法律形态、联系人、类目、类目码、
经营描述、服务范围、社区清单、资质图、行业、行业备注 —— 十一项。

这套是按**第三方商家自行收款**设计的：那个形态下平台要先判断
「这家能不能收钱、能收哪类钱」，所以准入要一次性问清。

而自营旗舰店形态下，平台是销售主体、平台收款。商家在法律上是供应商，
**准入判断的重心从「他能不能收钱」变成「他是不是一个真实的经营主体、货款打给谁」**。
前者要十一项，后者要两项。

## §2 方案

### 2.1 把准入材料按时机拆成三段

**这是本方案的全部内容。** 不新建模型，只改「什么时候要什么」。

| 时机 | 必需 | 为什么是这一刻 |
|---|---|---|
| **开店** | 手机号 · 店名 | 能登录、能建店。其余都不是开店的前提 —— 一个空店铺不产生任何风险 |
| **上架前** | 营业执照 · 类目资质 | **卖什么决定要什么资质**，没上架就没有这个问题。类目资质本来就挂在类目上（`required_code`） |
| **首次结算前** | 收款银行账号 · 户名 | 钱要打出去才需要账号。而户名必须等于执照主体名，所以执照要先有 —— 这条顺序不能反 |

**三道闸各自独立**，商家可以停在任一段：开了店不上架、上了架还没到账期。
今天的模型把这三件事压成一道闸，结果是第一次登录就面对一张长表单。

### 2.2 主路径变成「平台开店 → 商家认领」

新定位下 BD 谈下来的商家是主要来源，所以：

```
运营在 ops-web 建店（主体 + 门店 + 账号，手机号即登录名）
   → 商家用那个手机号登录 B 端（验证码，无需注册）
   → 引导补执照（上架前）
   → 引导补收款账号（首次结算前）
```

`SelfOperatedService.create` 已经能做第一步且是幂等的（`created` 标志）。
缺的是第二步之后的**引导**：商家登录后要知道「还差什么、什么时候要」。

### 2.3 落到代码上

| 动作 | 位置 | 说明 |
|---|---|---|
| 新增 | `mch_entity.onboarding_stage` | `OPENED` / `LISTABLE` / `SETTLEABLE` 三段。**派生不了要存**：它要能被运营筛选与催办 |
| 修改 | 上架校验 | 加一条：无有效执照不得上架。今天只校验类目资质 |
| 修改 | 首次结算 | 加一条：无 ACTIVE 收款账户的主体，结算单可以生成但**不进付款清单**（P2 的导出已经只取 ACTIVE，这里是把原因显式化） |
| 新增 | B 端「开店进度」卡 | 三段式进度 + 当前缺什么 + 为什么现在要 |
| 修改 | `mch_entity_apply` 的必填 | 自助申请路径上，类目/服务范围/行业改成**选填**（它们是经营配置） |
| 不动 | 进件链路 | 默认不走，但保留 —— 见 ADR-011 §4.5 的警告 |

### 2.4 ⚠️ 不能简化掉的两样

- **营业执照**：它不只是合规留档，还是 V358 户名校验的**唯一比对基准**。
  没有它，「户名必须等于主体名」这条硬校验就没有右边那个值。
- **收款银行账号**：线下转账的依据。它本身已经是 V358 的独立流程（要运营核），
  不要为了"简化入驻"把它挪进入驻表单 —— 那会让它绕过审核。

## §3 将来支持多商户：不改模型，切两个字段

| | 今天（自营旗舰店） | 将来（多商户） |
|---|---|---|
| `business_mode` | `SELF_OPERATED` | `THIRD_PARTY`（**按门店**切，不是按主体） |
| `funds_mode` | `AGGREGATED` | `DIRECT` |
| 进件 | 不走 | 走，拿二级商户号 |
| 谁收款 | 平台 | 商家自己的商户号 |
| 准入材料 | 执照 + 银行账号 | 回到全套（通道要什么就要什么） |

**V23 把 `business_mode` 挂在门店而不是主体上，正是为这一天留的**：
同一个主体下可以旗舰店自营、加盟店第三方，不必整体二选一。

## §4 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **「自营」没有真的承担销售主体责任** | 形式合规撑不住（ADR-011 §2 已警告） | 商务与法务把关，技术保证不了 |
| 先开店后补照，中间这段 | 店开着、商品上不了架，商家以为系统坏了 | 进度卡要说清「现在缺什么、补了能做什么」 |
| 代运营时的权责 | 平台代运营又是销售主体，商品出问题时商家是否免责 | **待确认**，见 §5 |
| 简化被读成"不要执照了" | 无照主体混进来，户名校验失去基准 | 执照是上架的硬闸，不是可选项 |

## §5 待确认（附建议，2026-09-29）

### 1. 平台代运营时的权责边界 —— 建议：**对外统一、对内分类**

问题问成「商家是否免责」会答不出来，因为它把两件独立的事压成了一件：
**谁供货**与**谁运营**。拆开之后每一类都有明确归属：

| 责任类型 | 内部归属 | 依据 |
|---|---|---|
| 商品本身的质量 / 安全 / 资质 | **商家（供货方）** | 采购合同的质保条款 |
| 商品信息（描述、图片、价格、规格） | **谁录入谁担** —— 代运营时是平台 | 录入留痕 |
| 履约（发货、时效） | 谁发货谁担 | 商家自发 / 平台仓 |
| 对消费者的先行赔付 | **一律平台** | 平台是销售主体，这是必然结果不是选择 |

**对消费者永远是平台负责**，这一条没有商量余地 —— 自营旗舰店形态下
消费者的合同相对方就是平台。内部追偿再按上表划分。

**技术上要支持的只有一件事：关键写入要记「是谁做的、是不是代做的」。**
商品的创建与改价、上下架、发货，都要留 `operated_by` 与
「代运营」标记 —— 没有这个，代运营期间写错价格的追偿方向无从判断。
仓库里已有同形状的先例：入驻申请的 `submitted_by`（代填人），
以及「代填的人不能审自己填的那一张」那条闸。

⚠️ **代运营必须有书面授权**（商家签字同意平台代其运营并承担运营方责任）。
这一条不是技术能替代的 —— 没有授权，平台改了价格就是无权处分。

### 2. 无照个人能不能开店 —— 建议：**自营模式下不开放**

ADR-002 §4 的三段式路径里确实有「个人（无照）」一档，但那是
**分账到个人零钱**的形态：钱不经过平台，平台不是付款人。
自营模式是**平台付款给他**，三条都不成立：

1. **税务**：平台向个人支付经营所得，**平台是法定扣缴义务人**（ADR-002 §4 原话）。
   小规模时容易忽略，一旦规模化就是追缴加滞纳金。与无票供应商是同一类问题。
2. **户名校验失去基准**：V358 的硬校验是「户名 == 执照主体名」，没有执照就没有右边那个值。
3. **追偿不可行**：平台先行赔付之后，向无照个人追偿基本落不了地。

**替代路径 ADR-002 §4 已经设计好**：平台内「一键代办个体工商户」，
市面有成熟服务商、最快 T+3 出照。那一节的结论正是
「不是没有资质，而是资质由平台代办掉」—— 把无照个人引到这条路上，
比放进来再处理税务与追偿便宜得多。

### 3. 执照过期 —— 建议：**阶段不回退，另加一个独立的有效性标记**

`onboarding_stage` 是**单调前进**的（开店 → 可上架 → 可结算），
退回会丢掉「他到过哪一步」这个事实；而且退回 `OPENED` 等于连收款账号也一起作废，
但收款账号与执照过期没有关系。

所以另立一个 `license_valid_until`，过期与否由它判。**关键是影响面要分清**：

| | 执照过期时 |
|---|---|
| 已上架商品 | **下架** —— 卖的那一刻必须有有效执照 |
| 新上架 | 拦 |
| **已产生的结算单** | **照常结算付款** —— 那批货是有效期内卖的，钱该给。扣着不付是另一个错误 |
| 新订单 | 自然不产生（商品已下架） |
| 登录 / 查看 / 补传 | 照常 —— 他要能看到催办和补传入口 |

⚠️ **到期前 30 天开始提醒，不是过期当天才拦。** 过期当天拦的后果是
一批商品突然下架而商家不知道为什么。

⚠️ 还有一条来自教训：**标记要有人读**。`store_status` 的 `READONLY`
就是写了没人读、对买家完全无效。所以这里要写明读它的是谁 ——
上架校验与每日的过期扫描任务，两处都要落地，缺一个这个标记就等于没有。

---

**前两条的最终定性需要法务**：上面给的是技术上可落地的划分方式与依据，
不是合规结论。第三条是产品决定，可以直接定。

## §6 落地记录（2026-09-29）—— §2.3 那张表大半推翻了

动手前逐条查了现状，**六行里只有一行是真缺口**。以下是每一行的实际结论，
写在这里是因为「按设计做下去」会造出重复且互相冲突的东西。

| §2.3 原计划 | 结论 | 依据 |
|---|---|---|
| 加 `mch_entity.onboarding_stage` | **不做** | `status` 已有 `PENDING_LICENSE`（"无证照快速开店建出来的占位主体"）与 `ACTIVE`，正是前两段；第三段由 `mch_payout_account` 派生，P2 的付款清单已在用。再加一列就是**第二把尺**：status 变了而 stage 没跟上，两处说法不一致，而界面读哪一个取决于谁写的代码 |
| 上架校验加「无有效执照不得上架」 | **不做，且与现有设计冲突** | `PENDING_LICENSE` 的设计正是「让他先把货录进去，只是买家看不到」。加这道闸等于把那条路堵死。而「资质**过期**不能上架」已经实现（`requireCategoryAuthorized` 末段），只是与类目闸共用 `shop.category.gate.enforce`，默认关着只记 WARN |
| 首次结算加账户闸 | **已实现** | P2 付款清单的 `blocked`，原因文案是「没有生效中的收款账户，钱不知道打给谁」 |
| **B 端开店进度卡** | **本次交付**（下详） | 唯一的真缺口 |
| 入驻申请必填放宽 | **已成立** | 自助 `ApplyReq` 与代填 `OnBehalfReq` 都只硬校验手机号/店名/主体名，类目、行业、范围、资质全是选填；且 `/biz/merchant/quick-start` 只要店名与地址 |
| 不动进件链路 | 不动 | 无变化 |

### 6.1 真缺口：归集商户看不到「货款打不出去」

工作台早有 `blockers` 机制（**只在有问题时出现**，全通过不挂绿卡），四档：
没证照 / 通道进件没完成 / 买家看不见 / 协议没勾。

**缺的那一档是收款账户。** 而且 `payment` 那一档在 `fundsAggregated` 时**刻意不提**
（归集商户不需要二级商户号）—— 于是自营供应商模式下的商家，
在工作台上**完全看不到**「你还没填收款账户」，而那正是他拿不到钱的唯一原因：
结算单照样生成、状态照样推进，钱停在「已确认应付」上，页面每一步都是绿的。

交付：第五档 `payoutAccount`，判据抽进 `@shared/utils/onboarding` 的 `payoutReady`
（与 `visibleToBuyers` 同一条规矩：判据只有一份）。

**判据是「还要不要他再做点什么」，不是「有没有一张生效的卡」** ——
所以待审（`PENDING`）算办完了，被驳回（`REJECTED`）与停用（`DISABLED`）不算。
这与 `includedAreas` 把 PENDING 算进范围是同一条道理：
提交完等着审的人，与从没提交过的人，看到的不该是同一条提示。

### 6.2 §5 三条待确认的落地影响

- 第 1 条（代运营留痕）：`operated_by` 这一层本次**没做**，它要等代运营真的开跑。
  仓库里已有同形状的先例（`submitted_by` + 「代填的人不能审自己填的那一张」）。
- 第 2 条（无照个人不开放）：建议就是维持现状，**无需改动**。
- 第 3 条（执照过期不回退阶段）：既然没有 `onboarding_stage`，这条自然成立。
  过期由 `mch_qualification.status` 管，`QualificationExpiryJob` 已在扫。
