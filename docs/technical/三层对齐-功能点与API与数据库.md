# 三层对齐：功能点 → API 契约 → 数据库

> 2026-08-10 · 承接[三端功能点矩阵](./三端功能点矩阵.md)（哪一列是空的）与
> [三端闭环对齐清单](./三端闭环对齐清单.md)（为什么断）。
>
> **这份只回答一个问题：补一个缺口，要挖多深？**
>
> 「平台端 0/20」这种数字看起来一样严重，实际差别极大——
> 客服工单的字段全都现成，写两个端点就通；风控是**一张表都没有**，
> 是整块新建。把这两件事排进同一个迭代，一定会翻车。

---

## 一、三级分类

| 级 | 含义 | 域 | 平台端缺口 |
|:---:|---|---|---|
| **A** | 表和字段现成，**只差端点**（可能要补契约） | 客服工单 · 拼团 · 报价 · 营销与优惠券 | 0/7 · 0/3 · 0/3 · 0/16 |
| **B** | 域已存在，但**关键表没建** | 资金与结算 · 履约与配送 · 消息通知 · 增长 | 0/20 · 0/15 · 0/7 · 0/10 |
| **C** | **一张表都没有**，整块新建 | 风控 · 内容运营 | 0/7 · 0/21 |

**A 级加起来 29 个功能点，代价接近零**——数据模型早就为它们准备好了。
**C 级 28 个功能点，是两个全新的域**。两者数量相近，工作量差一个数量级。

## 二、逐域：缺什么

### A 级 · 只差端点

| 域 | 现有表 | 差什么 |
|---|---|---|
| **客服工单** | `msg_ticket`（含 `reply` / `replied_at` / `replied_by`） | **只差端点**。且**契约里没有「回复工单」这个功能点**——平台端 7 条里有分派、关闭、代客留痕，唯独没有写 `reply` 的那个动作。**先补契约再写端点** |
| **拼团** | `mkt_group_buy` · `mkt_group_member` · `ful_group_pickup` | 只差平台侧的 3 条干预端点（中止违规团等） |
| **报价** | `mkt_quote` · `mkt_quote_revision` · `mch_violation` | 差一个**状态枚举值**：`mkt_quote.status` 现在只有 `ACTIVE` / `WITHDRAWN`，没有 `BREACH`。毁约的信用落点已现成——`mch_violation.type` 里 `BREACH` 就在，注释还写着「只有 BREACH 计入 breach_count」 |
| **营销与优惠券** | `mkt_campaign` · `mkt_coupon` · `mkt_user_coupon` | 表齐。平台侧 16 条是**查询 + 干预**（停券、停活动），不需要新表 |

> 报价这条值得单独说：**上下游都建好了，中间少一个枚举值**。
> 这种缺口最容易被漏——它不像缺表那样一眼可见。

### B 级 · 域在，关键表没建

| 域 | 现有表 | **缺的表** |
|---|---|---|
| **资金与结算** | `stl_bill` · `stl_payment` · `stl_split_log` · `stl_points_pool` | **提现单**、**发票申请**。核实过：全库没有任何 `withdraw` / `invoice` 表；`invoice_capable` 只是 `mch_payment_merchant` 上的一个「能不能开票」标志位，不是发票记录 |
| **履约与配送** | `ful_batch` · `ful_verify_log` · `ful_group_pickup` | **运费模板**、**发货单**。`freight_amount` 只是订单上的一个金额字段，不是模板；`shipment` 表不存在 |
| **消息通知** | `msg_message` · `msg_subscribe` | **消息模板**、**发送配额**、**推送任务**。`msg_subscribe.template_id` 引用了模板 ID，但**没有任何表管理这些模板** |
| **增长** | `mkt_attribution` · `mkt_attribution_log` · `mkt_request` · `mkt_request_interest` | **裂变活动**表。归因与需求墙的表是齐的，裂变没有 |

> **资金那两张表是这一级里最要紧的**，因为它同时卡在产品决策上——
> 见[闭环清单](./三端闭环对齐清单.md) §3.2。契约里已经声明了
> `/ops/finance/withdrawals/{withdrawNo}/decide`（平台审批提现），
> 说明产品意图是「平台代收后再结给商家」，而不是收付通直接到账。
> **这个前提定了，提现单表才谈得上怎么设计。**

### C 级 · 整块新建

| 域 | 平台端声明 | 现状 |
|---|---|---|
| **风控** | 7（`risk-events` · `risk-rules` · `blacklists`） | **零表零列**。唯一沾边的是 `mch_violation`（商家违规处置），但那是**事后处置记录**，不是风控规则与事件 |
| **内容运营** | 21（`contents` · `content-slots` · `appearance` · `materials` · `rule-texts`） | **零表**。`content` 那一列是工单正文，与内容运营无关 |

这两块**不该叫「补齐」**，它们是新功能。放进「对齐」清单里会让人低估工作量。

## 三、API 层：42 条后端有、契约没有

这是 API 对齐里最大的一处问题，与上面的缺口是**反方向**的：
不是契约声明了没实现，而是**实现了却没写进契约**。

| 端 | 条数 | 例子 |
|---|---:|---|
| C 端 | 29 | `/mp/ticket`、`/mp/order/preview`、`/mp/user/phone/bind`、`/mp/store/by-code` |
| B 端 | 6 | `/biz/quote/{id}/revise`、`/biz/context`、`/biz/settle/bills/{id}` |
| 平台端 | 5 | `/ops/auth/me`、`/ops/order`、`/ops/staff`、`/ops/audit-log` |

**为什么这件事有代价**（不只是「文档不全」）：

1. **所有对齐统计都会低估后端**。`gen-api-index` 按契约算覆盖率，
   这 42 条不在分母也不在分子——[功能点矩阵](./三端功能点矩阵.md)里它们显示为
   「（契约未声明）」，正是为了不让单元格假空
2. **前端拿不到类型**。三端的 API 类型由 OpenAPI 生成，契约里没有就得手写
3. **改了没人知道**。契约是唯一有 diff 的地方；不在契约里的接口，
   改参数不会触发任何评审

> 注意 `/mp/ticket` **同时出现在两个问题里**：后端实现了但契约没声明（C 端），
> 而平台端契约声明了却没实现，且连「回复」都没定义。
> 一个功能在三层上各错了一处，这正是要做三层对齐的原因。

## 四、建议顺序

按「挖多深」排，不按「有多重要」排——同一批里放深浅差一个数量级的活，是排期翻车的主因。

| 批 | 内容 | 为什么这个顺序 |
|---|---|---|
| **1** | 补 42 条契约（纯文档/YAML，不动代码） | 无依赖，做完之后所有统计才是真的。**先做这个，否则后面每一批的进度都算不准** |
| **2** | A 级四个域的端点（29 个功能点） | 表全现成。含报价的 `BREACH` 枚举值与工单的「回复」契约补齐 |
| **3** | 定资金模式 → 建提现单/发票表 → 端点 | 卡产品决策，不卡技术。决策没定之前写的表可能白建 |
| **4** | B 级其余（履约、消息、增长的缺表） | 常规建表 + 端点 |
| **5** | C 级（风控、内容运营） | 新域，按新功能立项，不要混进「对齐」的排期里 |

## 五、边界

- **本文的表清单是 2026-08-10 手工核对的**（65 张表，`V1`–`V17`）。
  功能点数字来自[功能点矩阵](./三端功能点矩阵.md)，那份是生成的；
  **本文的分级是判断，不是生成物**——新增表之后要手工复核这里
- **「缺表」不等于「必须建表」**。比如消息模板，如果全部走微信订阅消息、
  模板 ID 在微信后台管理，那平台侧可能只需要一张很薄的映射表，而不是完整的模板系统
- **C 级两个域没有做需求评估**。这里只说「零表」，不评价它们该不该做、
  优先级如何——那是产品决策，不是对齐能回答的
