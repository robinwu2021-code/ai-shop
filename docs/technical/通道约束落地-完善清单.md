## 三、模型层（3 项，阻塞其余全部）

### M1 ⚠️ 同一个「主体」概念有**四套枚举**

| 出处 | 取值 |
|---|---|
| `usr_merchant.type` | `PERSONAL` / `INDIVIDUAL` / `COMPANY` |
| `usr_merchant_payment.subject_type` | `MICRO` / `INDIVIDUAL` / `ENTERPRISE` |
| shared `MerchantType` | `PLATFORM` / `COMPANY` / `INDIVIDUAL` |
| shared `SubjectType` | `MICRO` / `INDIVIDUAL` / `ENTERPRISE` |

第 1、2 套讲的是**同一件事**（个人/个体户/企业），却用了不同的词；
第 3 套还多出一个 `PLATFORM`、少了「个人」这一档。

**这不是命名洁癖**：通道能力（能不能补差、能不能分账回退、能不能开积分）
是按**主体**判的。四套枚举意味着**判断散在四处**，而它们迟早会不一致 ——
不一致的表现是「同一个商家在 A 页面能开积分、B 页面不能」。

#### 方案

**统一到 `SubjectType`（`MICRO` / `INDIVIDUAL` / `ENTERPRISE`）**，理由：
它与通道的口径一致（微信叫小微/个体/企业），而通道口径是**外部约束，改不了**。

| 动作 | 说明 |
|---|---|
| `usr_merchant.type` → `subject_type` | 取值映射 `PERSONAL→MICRO`、`COMPANY→ENTERPRISE`，`INDIVIDUAL` 不变 |
| shared `MerchantType` 废弃 | 它的 `PLATFORM` 不是主体，是**归属**（平台自营店）—— 拆成独立的 `ownerType` |
| 保留 `SubjectType` 为唯一真源 | 加守卫：库里的取值必须是这个联合类型的成员 |

> `PLATFORM` 混进主体枚举是个典型的「两个概念挤在一个字段」：
> 平台自营店的**主体**是企业（平台自己），**归属**才是平台。
> 混着的后果是「平台自营店」这一档在能力判断里没有对应的通道主体。

### M2 ❌ 没有「**行业**」字段

微信小微的白名单是按**行业**给的（餐饮 / 线下零售 / 居民生活服务 / 休闲娱乐 / 交通），
而我们只有：

- `prd_category` —— **商品类目树**（一件商品属于哪一类）
- `usr_merchant_apply.category` —— 主营类目，注释写的是「决定类目授权范围」

**商品类目 ≠ 行业。** 一家便利店（线下零售）可以卖生鲜、日用、饮料，
横跨多个商品类目；而它的**行业**只有一个。

连带后果：`usr_merchant.points_forced` 的注释写着「**按行业**强制开」——
**这个字段目前没有判断依据**，那句注释是空的。

#### 方案

新增 `usr_merchant.industry` + 一张行业注册表，与 `sys_pay_channel` 同一个模式
（**表管能力，类型管取值**）：

```
sys_industry
  industry            主键：CATERING / RETAIL / LIFE_SERVICE / ENTERTAINMENT / TRANSPORT / ONLINE / ...
  name                展示名
  wechat_micro_allowed  微信能否以小微主体进件   ← 白名单落在这里
  alipay_micro_allowed  支付宝同上（待确认）
  points_forced         是否按行业强制开积分     ← 补上 points_forced 的依据
  enabled
```

**为什么是表不是枚举**：白名单是**通道的规则**，会随对方调整而变；
放代码里每次变都要发版。取值域仍在 shared 的 `Industry` 联合类型里，守卫保证两边一致 ——
与 `PayChannel` 完全同构。

> **行业与商品类目的关系**：行业挂在**商家**上（一个商家一个行业），
> 商品类目挂在**商品**上（一个商家可以卖多个类目）。
> 二者不是父子，是两个维度 —— 现在把它们混在 `apply.category` 一个字段里，
> 才导致「按行业」这件事做不了。

### M3 ⚠️ `split_reversible` 有列无源

`V39` 加了 `usr_merchant_payment.split_reversible`，但**怎么知道商家开没开还没确认**。

#### 方案（三条，按可行性排序）

| 方案 | 可行性 |
|---|---|
| 进件回执里带这一位 | 待查文档。**最理想** —— 进件完就知道 |
| 单独的查询接口 | 待查。次优，可定时刷 |
| **试探性调用**：分账时若报「未授权」就回填 0 | 兜底。缺点是**第一次总会失败** |

在确认之前，产品上按「**未知 = 未授权**」处理：售后受理时提示
「该商家的退款可能需要人工处理」，而不是等调用失败。
**宁可提示得保守，也不要让用户在等待中失败。**

## 四、流程层（4 项）

| # | 补什么 | 为什么现在没有 |
|---|---|---|
| P1 | 进件流程加一步：**开启分账回退授权** | 通道对齐前不知道有这一步 |
| P2 | 服务商侧开通「**下载二级商户资金账单**」产品权限 | 它不在进件流程里，是平台自己的一次性动作 |
| P3 | 售后申请**按申请聚合**（不按商品行发起退款） | 60 秒间隔约束刚查到 |
| P4 | 支付宝分账前**确认结算 + 等 30 秒** | 同上 |

P2 是**一次性**的（平台自己做一次），P1/P3/P4 是**每单/每商家**的流程改动。

## 五、经营类目的完善方案（M2 展开）

以此为例说明模型层怎么补 —— 其余两项同法。

### 现在的样子

```
usr_merchant_apply.category   一个字符串，注释说是「主营类目」
                              实际被当成 prd_category 的引用
usr_merchant.type             PERSONAL/INDIVIDUAL/COMPANY，商家自己选
usr_merchant.points_forced    「按行业强制开」—— 而行业不存在
```

商家在入驻表单上**自己选主体**，没有任何校验。

### 补完之后

```
① 商家选【行业】（单选，来自 sys_industry）
        ↓
② 系统按 sys_industry.wechat_micro_allowed 算出【可选主体】
        ↓
③ 商家在可选范围内选主体；小微不可选时，页面说明「你的行业不支持小微，
   通道规则如此」—— 而不是让他选了再被拒
        ↓
④ 进件时把 industry 一并提交给通道
```

`usr_merchant_apply.category`（商品主营类目）**保留不动** ——
它管的是类目授权范围，与行业是两件事。

### 迁移路径

| 步 | 动作 | 风险 |
|---|---|---|
| 1 | 建 `sys_industry` + seed（含微信白名单） | 无 |
| 2 | `usr_merchant` / `usr_merchant_apply` 加 `industry`，**可空** | 无 |
| 3 | 存量商家按现有 `category` **人工映射**一次 | 需运营参与，量小 |
| 4 | 新入驻**必填** industry | 表单改动 |
| 5 | `industry` 转非空 | 存量映射完才能做 |

> 第 3 步不能自动推 —— 商品类目到行业**不是函数关系**（卖生鲜的可能是超市、
> 也可能是餐饮）。自动推的结果是一批商家被划错行业，
> 而错的行业会直接影响他能不能开小微。**宁可人工，不要猜。**

### 守卫

| 守什么 | 怎么守 |
|---|---|
| `sys_industry` 的 seed 与 `Industry` 联合类型一致 | 照搬 `sys_pay_channel` 那条 |
| 主体枚举只有一套 | 断言库里不再出现 `PERSONAL` / `COMPANY` |
| 每个行业都声明了 `wechat_micro_allowed` | 缺省值不能是「允许」—— **默认允许 = 默认让商家撞墙** |

## 六、执行顺序

```
M1 主体枚举统一  ┐
M2 行业模型      ├→ P1–P4 流程  →  B/C/运营三端
M3 授权位数据源  ┘
```

**M1 与 M2 可以并行**，M3 卡在通道文档确认上（不阻塞其余）。
