## 1. 结论与现状

建议先换用资质有效的联调商家，再决定是否增加后端测试主体白名单；未明确接受实例级影响前，不直接开放全部功能。

## 2. 配置及作用范围矩阵

以下是 Spring 配置的规范属性名，不假设服务器已配置；应通过新增受控配置文件或正确合并现有配置实施，不直接覆盖现有环境文件或密钥。

| 所属服务 | 配置 | 放开的能力 | 实际作用范围与连带影响 |
|---|---|---|---|
| Core | shop.promotion.activity.enabled | 统一活动草稿、发布等写入 | 实例级；旧活动路由不调用此新开关，不能据此宣称旧营销完全受控 |
| Core | shop.promotion.presets.enabled | 预置活动推荐可用性 | 仍需每条预置 enabled、执行器与真实能力证据；不会自动使40条全部可用 |
| Core | shop.member-code.enabled | 新统一会员凭证签发/识别入口 | 实例级会员能力；仍检查登录、有效期、商家及门店权限，不等于扣款授权 |
| Pay | shop.pay.entitlement.catalog.enabled | 权益模板定义与发布 | 实例级，涉及其他具备模板权限的商家 |
| Pay | shop.pay.entitlement.issue.enabled | 新权益发放 | 同时依赖 catalog；可能产生真实权益和待处理批次 |
| Pay | shop.pay.stored-value.enabled | 新储值充值办理和入账入口 | 实例级；一旦确认实收，将形成真实余额、账本及后续事件，不是演示数据 |
| Pay | shop.pay.entitlement.use.enabled | 权益使用；与 stored-value 共同决定储值核销能力 | 共享开关，会影响卡券使用和储值使用，不能只视为打开查余额 |
| Core | shop.core.entitlement.authorization.enabled | 消费者权益/储值确认授权写入 | 实例级；消费成功链路的独立前置，不以商家扫码代替消费者同意 |

当前能力适配器对 MAIN 租户做支持判断，但上述开关本身没有 entityNo/storeNo 白名单。MAIN 下其他满足条件的主体是本轮评估的实际扩散范围；身份隔离和金额校验仍保留。

本轮不建议开启：shop.pay.paid-card.enabled、shop.trade.paid-card-sale.enabled、shop.pay.entitlement.code.enabled、legacy-coupon 及迁移/修复开关。付费月卡次卡销售、独立兑换码、历史券迁移均不属于当前已完成页面的联调范围。

## 3. 预置及身份范围

- 储值推荐只考虑 AP008（普通储值）或一条经核对匹配目标业态的储值预置，其他预置保持原状。
- 预置数据位于 pmt_preset_template，以租户、templateCode、templateVersion 精确定位并保存变更前值；enabled 是目录级控制，不是单商家授权。
- 当前未找到现成的运营端预置启停接口；实施前应核实正式管理路径，必要时使用带行数断言及备份的受控数据变更，不能批量启用全部种子。
- 测试身份须为资质有效、行业被主数据识别的商家；从其合法门店中指定一家，再指定自愿参与的消费者测试账号。
- 不恢复、删除或覆盖当前 REVOKED 资质来凑联调条件；美业验收应选真实获准的美业商家。零售商家最多验证通用能力。
- 不把当前自动化白名单扩大到其他用户；测试会话沿用现有正常权限。

## 4. 分阶段最小开通顺序

| 步骤 | 开通或准备内容 | 本步验证 | 暂不执行 |
|---|---|---|---|
| A | 有效商家/门店/消费者准备，确认现有资产和后台待办；只保留查询 | 权限、历史数据、能力缺失项和健康基线 | 所有新增资产操作 |
| B | Core 统一活动写入 | 使用明确测试名称保存草稿、原号查询、修订和幂等恢复 | 发布、充值、发券。预置仍不可用时只做API草稿验证，不宣称页面新建闭环通过 |
| C | 按域完成会员、Pay储值和使用能力；精确启用一条储值预置及推荐开关 | 预置返回 available=true，再从页面创建、编辑、发布测试活动 | 未指定消费者和额度前不确认实收；仅用于补齐推荐证据时也要承认Pay入口已对其他合格调用者开放 |
| D | Pay catalog；必要时单独开启 issue | 定义、发布一个测试模板；由已开发页面或受控API验证发放批次及重试 | issue只在实际验证发放时开启；当前发放UI未完成，不称为B端页面全链路通过 |
| E | 消费者授权、有效统一会员码；事先明确测试实收方式、金额、赠送额和清理路径 | 指定测试账号办理一次最小实收、到账、查余额，再确认一次消费并核对账本和通知 | 真实资金动作须有明确测试范围；不提供线上退款、不用SQL抹账 |

B至E不是仅配置渐进：C涉及实例级入账与核销能力，E形成真实业务事实。建议先在同一实例增加服务端测试主体白名单，再进行C至E；白名单必须覆盖新命令的Core与Pay入口，不能只隐藏UI或过滤预置列表。原操作重试、历史查询及已有承诺收尾不应被新白名单截断。白名单目前未实现，不宣称已经隔离。

## 5. 执行前检查及部署影响

1. 确认是接受实例级开放，还是先实现后端主体白名单；指定商家、门店和消费者，不用“仅测试时点一下”代替边界。
2. 备份两服务环境配置、当前jar软链、预置原值；只记录密钥是否存在及满足长度，不输出密钥。核对Core→Pay内部鉴权、端口和配置来源。
3. 按需要检查稳定的权益游标密钥；只有开启相关兑换码能力才检查兑换码密钥。本轮不无差别生成或轮换所有密钥。
4. 核查现存权益、充值待办、收款确认和事件积压。新开关不代表系统里一定没有待完成操作，不以“当前测试商家列表0条”推断全平台无资产。
5. 采用独立增量配置文件的方案时，使用规范属性名并明确合并顺序；若设置 SPRING_CONFIG_ADDITIONAL_LOCATION，须保留已有位置。配置片段由计划确认后的执行步骤生成，不直接替换整个 SPRING_APPLICATION_JSON。
6. Pay先启用对应能力并重启、确认健康及内部能力响应，再重启Core；这只是准备顺序，不能消除Pay先开放期间的实例级影响。若部署白名单，应先完成两侧代码与边界测试。
7. 单实例重启存在短暂不可用窗口；当前不是滚动双副本部署，不承诺零停机。核心支付服务变更需选择窗口并观察健康与错误率。
8. 不修改已应用Flyway迁移；本次开通不以重新建库、重跑迁移或替换生产数据为手段。

## 6. 验收与止损

先验查询/权限，再验草稿/发布，然后才进行经指定的资产操作；每步失败停在该步，不自动继续发券或确认实收。只回归本步变更及修复问题，不跑全量测试。

必须留下活动号与版本号、模板版本、批次号、充值号、服务单号、请求幂等键的安全摘要，以及对应余额、核销记录和事件状态；不记录明文会员凭证和会话令牌。联调金额上限及消费者账号在执行前单独明确，本方案没有授权任何金额。

停止条件包括：非测试主体获得超出确认范围的新增能力、任意重复到账/重复扣减、主体或门店越权、Core/Pay能力不一致、服务健康异常、事件持续失败、消费者账单不一致。

## 7. 回退边界

- 未产生资产：恢复原配置与单条预置原值，按服务检查健康；保留测试草稿/发布记录的可追踪状态，不删除审计记录。
- 已产生资产：先停止新发放/新充值入口，查清已确认实收、已提交核销、幂等重放和事件待办，再按原操作完成或走受支持的取消流程。不能关闭全部开关后就认定恢复完成。
- catalog/issue可单独停止新发行；use与已有持有人可用性有关，应根据现有承诺决定是否保留，不能将关停发放等同于关停使用。
- 已入账的实收与已消费余额不能靠改余额SQL、删流水或恢复jar撤销；系统不支持消费者线上退款，需按商家既有线下退款及系统受支持的业务流程处理，若无可用清理流程则不得先做真实入账测试。
- 没有预先确认可逆的业务清理路径时，验收到草稿/发布阶段为止。配置回退不等于资产回滚。
