# 五域全栈对齐核查：注册 · 进件 · 门店 · 分类 · 商品

> 2026-08-09 · 逐层核对 **三端 → API → Controller → Service → Mapper → DB**。
> 每一行都对着代码查过；「实现」列写的是现状，不是计划。
> 上游：[入驻进件建店-需求与四层对齐](../requirements/入驻进件建店-需求与四层对齐.md) · [Ops契约对账](./Ops契约对账.md)

## 零、一句话结论

**注册、进件、门店三段已全栈打通；商品是老链路本来就通的；分类这一段从上到下几乎是空的。**

最值得先看的三条：

| # | 问题 | 影响 |
|---|---|---|
| 1 | 🔴 **分类整条链断在端上**：后端有 `prd_category` 三级树和 `/mp/category/tree`，但**没有任何端调用它**，商品编辑页也不选类目 → `prd_goods.category_no` 恒为空 | 类目资质校验、属性模板、按类目检索全部落空 |
| 2 | 🔴 **员工能被创建但登不进 App**：后端 `/biz/auth/staff-login` 有实现有测试，**b-app 端点表里没有它**，登录页也只有一种登录方式 | 上一轮做的员工管理，员工侧无法使用 |
| 3 | 🟡 **C 端「分类」页筛的是商品形态**（`prd_goods.type`：生鲜/服务/虚拟…），与 `prd_category` 那棵树没有任何关系 | 看起来分类能用，其实类目树从未被触达 |

| 端 × 品类可售规则 | —— | （下单时内部判） | —— | —— | —— | `sys_channel_category_rule`（25 条种子） | ✅ |

> ### 🔴 §4 的真相：**两套「分类」并存，且真正在用的那套不是数据库里的树**
>
> | | `prd_category`（三级类目树） | `prd_goods.type`（商品形态） |
> |---|---|---|
> | 定义在哪 | 数据库表 + CategoryService + `/mp/category/tree` | 枚举值，写在 `GoodsDraft.type` 上 |
> | 取值 | `CAT001…` 三级 | `NORMAL` / `FRESH` / `SERVICE` / `VIRTUAL` / `CARD` |
> | 商品上的列 | `prd_goods.category_no` | `prd_goods.type` |
> | 谁在读 | **没有任何端** | C 端分类页 tab、商品筛选、规格模板推荐 |
> | 谁在写 | **没有任何端**（只有 DevSeeder 写死 `CAT001`） | 商品保存时必传 |
>
> 也就是说：**平台类目树建好了、有表有接口有 Service 有 Mapper，但整条链上没有一个真实的写入方和读取方。**
> C 端「分类」页看起来在用分类，其实筛的是**商品形态**（生鲜/服务/虚拟…）——
> 它是「这件商品怎么履约」，不是「它属于哪个类目」。两者恰好都能撑起一个 tab 栏，所以一直没人发现缺口。
>
> 形态够用于导航，但它**不承载资质要求与属性模板**，也无法回答「这个类目能不能卖」——
> 而 `prd_category.qualification_required` / `attr_template` 两列正是为此存在的。
>
> **要拍板的是一件事**：类目树到底做不做。
> - 做 → 补三处：运营维护面、b-app 商品编辑选类目、上架时按 `qualification_required` 校验
> - 不做 → 把 `prd_category` 与 `/mp/category/tree` 一起删掉，让 `CATEGORY_TYPE` 成为唯一的分类口径
>
> 现在这样**留着一棵没人用的树**是最差的选项：它看起来像已实现，任何按类目做的需求都会先撞上它。

## 六、按层汇总：哪一层最先断

| 层 | 注册 | 进件 | 门店 | 分类 | 商品 |
|---|---|---|---|---|---|
| **DB** | ✅ | ✅ | ✅ | ✅ | 🟡 缺选品/门店库存 |
| **Mapper** | ✅ | ✅ | ✅ | ✅ | 🟡 同上 |
| **Service** | ✅ | 🟡 只有 stub 网关 | ✅ | 🟡 只有读树 | ✅ |
| **Controller** | ✅ | ✅ | ✅ | 🟡 只有 `/mp/category/tree` | ✅ |
| **API 契约** | 🟡 缺 staff-login | ✅ | ✅ | 🔴 **端上无声明** | ✅ |
| **三端** | 🔴 员工登不进 | ✅ B 端已接 | 🟡 缺「当前门店」 | 🔴 **零接入** | 🟡 商品不选类目 |

**规律**：越靠近端，缺口越多。DB 与 Mapper 层基本没有欠账（V1 基准把表建全了），
**断点集中在「API 契约 → 三端」这两层** —— 后端做完了但端上没接，或端上有页面而后端是 mock。

## 七、建议的下一批（按「断链严重度」排）

| 序 | 事项 | 为什么排这里 |
|---|---|---|
| **1** | **b-app 接 `/biz/auth/staff-login`** + 登录页加员工入口 | 后端与测试都齐，端上一条声明的事；不接的话上一轮的员工管理等于白做 |
| **2** | **分类拍板**（做 or 删，见 §4） | 留着一棵没人用的树是最差选项 —— 它看起来像已实现 |
| **3** | `BizContext` 扩「当前门店」+ B 端门店切换 | 能建三家店但所有业务页仍按主体取数，是当前最大的半成品 |
| **4** | 商品编辑选类目 + 上架资质校验（若 §2 选「做」） | 依赖 2 |
| **5** | ops-web 接行业开关与商品审核 | 后端已有，纯对接，成本最低的两条 |
| **6** | 进件真实通道 + 回调入口 | 真钱之前必须做，但依赖通道资质进度 |
| **7** | M3 选品 + 门店库存 | 依赖 3；它才让多门店真正有意义 |
