## 0. 本文的位置

前两份分册各自解决一件事，本文把**五个域串成一条链**并解决它们的交叉：

```
商品        这件货支持什么支付方式、属于哪个类目（→ 决定积分规则）
  ↓
支付方式    线上 / 线下 —— 决定钱经不经过平台
  ↓
订单        状态机、抵扣与冻结的时机
  ↓
积分        能不能用（五道闸）、发多少（按类目）
  ↓
结算        走不走分账、佣金与让利怎么记
```

**已拍板的四条**（本文按此设计，不再讨论）：

1. 线下支付**不抽佣**。
2. **积分由平台统一按类目管理**。
3. 线下支付**能否用积分，由平台开关控制**。
4. 积分可用性将来要能按**商家资质**与**端**判断（小程序可能不支持）。

---

## 1. 五个域的边界（一张表说清谁管什么）

| 域 | 管什么 | **不管什么** |
|---|---|---|
| 商品 | 支持哪些支付方式、属于哪个类目 | 积分发多少（那是平台按类目定的） |
| 支付方式 | 钱经不经过平台 | 商品能不能卖、订单能不能退 |
| 订单 | 状态流转、抵扣与冻结的时机 | 积分规则本身 |
| 积分 | 能不能用、发多少、账户与流水 | 钱怎么流（那是结算的事） |
| 结算 | 走不走分账、佣金、让利记账 | 积分规则、支付方式的合法性 |

> 这张表是本方案唯一的防腐层。今天已经踩过一次同类问题：
> 商品侧的 `fulfillments` 曾经是「无取值域的自由 JSON、建品时写死」，
> 因为**没人规定它归谁管**。

## 2. 商品：加一列 `pay_modes`，不加积分列

```sql
ALTER TABLE prd_goods ADD COLUMN pay_modes VARCHAR(128) NOT NULL DEFAULT '["ONLINE"]';
```

取值域由 `PayModes` 常量类约束（与 `Fulfillments` 同构、同理由）。

**商品上不再新增积分配置。** 已有的 `prd_goods.points_config` 处置见 §5.2 ——
按第 2 条拍板（平台统一按类目管理），它**不再对商家开放**。

---

## 3. 支付方式：`OFFLINE` 是一条主数据，不是一个 if

```sql
INSERT INTO sys_pay_channel (pay_channel, name, enabled,
    supports_subsidy, supports_split, supports_payout)
VALUES ('OFFLINE', '线下收款', 1, 0, 0, 0);
```

三个开关全关，于是**下游天然不给它补贴、不给它分账、不给它打款** ——
代码里不需要到处 `if (线下)`。这是选主数据而不是枚举换来的。

**组合合法性**（详见分册 §3.4）：只有「当面能收到钱」的履约方式允许线下支付 ——
到店自提、商家自送（货到付款，单独开关）、到店核销、上门预约。
**排除快递**（货已寄出）与**自提点自提**（自提点不是卖家，让它代收货款就是资金归集）。

## 4. 订单：一个新状态，其余全部复用

```
WAIT_PAY ──线上支付成功──────────→ PAID
    │
    └──选了线下支付──→ WAIT_OFFLINE_PAY ──商家确认收款──→ PAID
                              │
                              └──超时未确认──→ CANCELLED（释放库存、解冻积分）
```

**`WAIT_OFFLINE_PAY → PAID` 走的是同一个 `markPaid`**（幂等、不关心钱从哪来）。
于是库存转实扣、入会、发分、结算触发、积分实扣**全部零改动**。

### 4.1 积分与订单状态的对齐

| 时刻 | 积分动作 | 线下支付有无差别 |
|---|---|---|
| 下单 | **冻结**抵扣的积分（不是扣减 —— 单可能不付） | 无 |
| 支付成功 / 确认收款 | 抵扣转实扣 | **无** —— 同一个 `markPaid` |
| 取消 / 超时关单 | 解冻 | 无 |
| **订单完成** | **发放**积分（不是支付时，防「下单→拿分→花掉→退款」） | 无 |
| 售后退款 | 回收已发 + 退回已抵（`ord_after_sale.points_offset_minor` 已有） | 无 |

**线下支付不需要为积分写任何分支。**

## 5. 积分

### 5.1 能不能用：五道闸，全通过才可用

按第 3、4 条拍板，可用性不是一个布尔值，而是一串判定。**顺序从粗到细，短路返回**：

| 闸 | 判据 | 数据来源 | 现状 |
|---|---|---|---|
| ① **平台总开关** | 积分功能是否启用 | 配置 | 已有（当前**未启用**，账户 0 条） |
| ② **端** | 这个端允不允许**发放** / 允不允许**核销**（两个独立开关） | `pay_scene`（已有列，**从没写过**），见 5.4 | ⚠️ 列在、写入缺 |
| ③ **商家资质** | 这家店够不够格 | `mch_qualification` | 表已有，判定需新建 |
| ④ **商家自身开关** | 商家愿不愿意参加 | `mch_entity.points_enabled` | ✅ 已有 `toggleMerchant` |
| ⑤ **支付方式** | 线下支付允不允许用积分 | **平台开关**（第 3 条拍板） | ❌ 需新建 |

> **④ 为什么必须留着**：第 2 条定的是「平台统一定规则」，而 ADR-006 定的是
> 「**成本由商家承担**」。平台定规则 + 商家出钱 = 商家没有话语权却要付账 ——
> 这中间必须有一个「我不参加」的出口，否则这条规则推不下去。
> 幸运的是它已经存在（`toggleMerchant`，且注释写明「关闭只影响将来，不动已发出的分」）。

### 5.2 发多少：平台按类目统一管理

```sql
CREATE TABLE prd_category_points (...)   -- 类目 → 发放规则，与 prd_category_spec 同构
```

**取值优先级（取一个值，不是相加）**：

```
类目配了  → 用类目的
否则      → 平台兜底比例（PointsConfig.earnPerMinor，现为千分之一）
```

**商家不再参与配置。** 已有的 `prd_goods.points_config`：

- **不删列**（删要迁移、要改实体，而它没妨碍谁 —— 与预售字段同一条处置）。
- **不对商家开放**，b-app 不给入口。
- 保留给**运营**做单品例外（极少数情况），读取优先级排在类目之前。
- 线上现状是 **199 件里 0 件配了**，所以「不再开放」不影响任何存量数据。

> **一个必须防的坑**：三层取值时，「配了 0」与「没配」是两件事。
> 储值卡配 0 分是一个明确决定，不能因为值是 0 就掉到下一层拿一个非 0 的值。
> `points_config` 是 JSON 列 —— **用「键存不存在」判，不能用「值是否为 0」判。**

### 5.3 为什么是类目而不是商品（拍板依据，留档）

线上实测：**199 件商品，配了积分的 0 件**。而这是同一个项目里的第四次同一形态 ——
商品规格（198 件里 197 件靠兜底）、标准品（导入 297 条启用 0 条）、预售（0 使用）、积分（0 件）。

**要求每个商家对每件商品做一次决定的配置项，不会被填。**
反面已验证：运营配 30 个类目是做得到的事（现在 30/30 全配齐了规格）。
同样叫「配置」，两者的可完成性差一个量级。

### 5.4 端：**发放**与**核销**分开控制

#### 5.4.1 先纠正我上一版的说法：抓手其实已经有了

上一版我写「按端判断要先造一个不存在的抓手」。**这是错的** ——
`ord_order.pay_scene` 与 `stl_bill.pay_scene` 从 **V1 baseline 就存在**，
注释写得清清楚楚：

> `pay_scene VARCHAR(16) COMMENT '下单端 MP_WECHAT/MP_ALIPAY/IOS/ANDROID/H5'`
> `stl_bill` 那份还多一句：'**退款也要记** —— 退回原路，端不同接口不同'

**缺的不是列，是写入**：全代码库搜不到一次 `setPayScene`。
（顺带核了一下：生产 `ord_order` **0 条**，所以这一列全 NULL 也有一半是「还没有订单」，
不能全算到「没人填」头上 —— 与规格/标准品那几处不是同一种病。）

所以要做的是：

```
① C 端三个客户端在请求头带 X-Client：MP_WECHAT / MP_ALIPAY / IOS / ANDROID / H5
   —— 取值直接用 pay_scene 注释里那一套，不另起一套词
② 网关解析进 RequestMetaContext（复用现成机制，不新建上下文）
③ 下单时**快照进 ord_order.pay_scene**，结算时带进 stl_bill.pay_scene
④ 平台配两张表：哪些端允许发放、哪些端允许核销
```

#### 5.4.2 两个独立开关，不是一个

| 开关 | 控制什么 | 判定时读哪个端 |
|---|---|---|
| **发放** earn | 这个端下的单，完成时发不发积分 | **订单快照上的 `pay_scene`** —— 不是当前请求的端 |
| **核销** redeem | 这个端能不能用积分抵扣 | **当前请求的端** |

**为什么发放必须读快照 —— 这是本节最要紧的一条。**
ADR-006 定的发放时机是**订单完成时**，而那一刻：

- 用户可能已经换了端（小程序下单、App 里确认收货）；
- 更常见的是**根本没有用户在场** —— 超时自动确认收货是系统动作，没有「当前端」。

读当前端的话，同一笔订单发不发积分取决于用户碰巧在哪个端点的确认，
甚至取决于是不是定时任务跑的 —— **不可复现、无法解释、也无法对账**。
所以发放的端判定**只能读下单时固化在订单上的那个值**。

#### 5.4.3 回收与解冻**不受端控制**

退款回收已发积分、取消订单解冻已冻结积分 —— 这两件事**任何端、任何情况下都必须能做成**。

按端拦住的话：用户在小程序下单用了积分，退款时因为「小程序不允许核销」而收不回来，
账上就凭空多出一笔积分。**那是资金事故，不是策略。**

同理，**已经发出去的分不因为开关关闭而收回**（`toggleMerchant` 的注释早就写明这条规矩：
「关闭只影响将来，不动已发出的分 —— 否则关一次开关就是一次资金事故」）。端开关沿用同一条。

#### 5.4.4 跨端不一致是这个设计的固有代价，必须在界面上说明

**积分账户是用户级的，不是端级的。** 于是「小程序能发不能核销」会造出这样一幕：
用户在小程序里看到余额 500 分，结算页却没有抵扣入口。

- **不能静默隐藏入口** —— 用户会认为是 bug，然后去投诉。
- 要显示余额、显示「本端暂不支持积分抵扣」，并说明**在哪个端可以用**。
- 反过来「能核销不能发放」体感更差（花得掉攒不到），**建议不要配出这种组合**，
  并在运营端配置页做一次校验提示 —— 不硬性禁止，因为可能真有合规场景要这么配。

#### 5.4.5 为什么小程序可能要关

微信小程序对虚拟货币/虚拟支付有平台规则限制，尤其 iOS 端。
**这是合规判断不是技术判断** —— 方案只负责让开关存在、判得准、说得清，
关不关、关哪个（发放还是核销）由运营按当时的平台规则定。

⚠️ **端标识来自客户端，天然可伪造。** 所以它只能用于**这一类「平台侧策略」判定**，
绝不能用于权限或资金判定。这条要写进代码注释，否则下一个人会拿它当身份用。

### 5.5 判定的唯一入口

```java
/** 能不能核销（抵扣）。五道闸全通过才可用，任何一道不过都返回不可用**与原因** ——
 *  原因要能直接变成给用户看的话（「本端暂不支持积分抵扣」），否则界面只能说「不可用」。 */
PointsAvailability canRedeem(String userNo, String merchantNo, String payMode, String clientType);

/**
 * 能不能发放。**端来自订单快照 `ord_order.pay_scene`，不是当前请求** ——
 * 订单完成常由定时任务触发，那一刻没有「当前端」（见 §5.4.2）。
 */
PointsAvailability canEarn(String orderNo);
```

**禁止别处重复实现这串判定** —— 加守卫测试钉死（与 `PointsRuleResolver` 同一条规矩）。
不这样做的话，下单页说能用、结算时说不能用，是必然会发生的形态。

## 6. 结算

| 场景 | 账单状态机 | 佣金 | 积分 |
|---|---|---|---|
| 线上 · 第三方 | `PENDING → SPLITTABLE → SPLIT`（走分账） | 照收 | `points_cost_minor` 记账；DIRECT 模式记 `subsidy_minor` |
| 线上 · 自营 | `PENDING_RECON → CONFIRMED → PAID` | 照收 | 同上 |
| **线下** | **`OFFLINE_SETTLED`（新终态，不进分账）** | **0**，另记 `waived_commission_minor` | **不需要任何资金动作** —— 商家当面少收即是抵扣 |

**结算域早就有一条不走分账的路**（自营那条），所以线下支付**不必新造结算链路**，只加一个终态。

### 6.1 `waived_commission_minor`：只记不扣

既然定了不抽佣，这一列**不是为了将来去收**，而是**为了知道让了多少** ——
缺了它，连「线下这部分生意值多少钱」都算不出来，将来无论继续免还是重新定价都没有依据。
与 `commission_minor` 并列，一眼看出「本该收多少、实际收了 0」。**代价是一列，不是一个子系统。**

## 7. 交叉矩阵（本方案的核心结论）

| | 线上支付 | 线下支付 |
|---|---|---|
| **积分抵扣** | ✅ 平台在结算时从商家收入扣 | ✅ **商家当面少收即可，平台零动作**（受 §5.1 第⑤闸控制） |
| **积分发放** | ✅ 订单完成时 | ✅ **完全相同** |
| **商家券** | ✅ | ✅ 商家自己少收 |
| **平台券** | ✅ 平台补给商家 | ❌ **没有资金流可补**，硬发就是白送且无处对账 |
| **佣金** | ✅ 分账时扣 | ❌ 不收，记 `waived_commission_minor` |
| **分账** | ✅ | ❌ 落 `OFFLINE_SETTLED` |

> **「线下支付能用积分」这一条曾被我写反过。** PRD 初稿的 AC-5 写的是
> 「线下不参与优惠券与积分抵扣」，错在只看到「平台没有资金流可扣」，
> 没分清**这笔钱本来就不该平台出**（ADR-006：成本在商家）。已订正，留档于此以免重犯。

### 7.1 一处会离开系统的地方

线下支付 + 抵扣之后，商家该收的是**抵扣后的金额**。
b-app 的确认收款页必须**大字显示应收金额**并标出「已抵扣 X 元」——
这是整条链路上唯一一处「抵扣」离开系统、落到人当面执行的地方，界面说不清就是纠纷。

## 8. 实现顺序（三批，批内可并行）

| 批 | 内容 | 依赖 |
|---|---|---|
| **一批** | `PayModes` + `pay_modes` 列 + `OFFLINE` 通道 + `WAIT_OFFLINE_PAY` + 确认收款 + `OFFLINE_SETTLED` | 无 |
| **一批（并行）** | `prd_category_points` + `PointsRuleResolver` + 运营端类目积分页 | 无 |
| **二批** | 五道闸的 `PointsAvailability` + `X-Client` 端标识 + **补写 `pay_scene`**（下单快照 + 带进结算）+ 发放/核销两张端开关表 | 依赖一批的 `pay_modes` |
| **二批（并行）** | 预约排期（时段 + 容量） | 无 |
| **三批** | 预定（定金＋尾款） | **依赖线下支付** |

> **积分是否启用不在任何一批里。** 发放维度定对是一回事，开闸是另一个决定 ——
> 账户 0 条、流水 0 条，而积分一旦发出去就收不回来。

## 8.1 端这一轴的必测场景

前两份分册各自有测试策略，这里只列**端**引入的、别处覆盖不到的：

1. **发放读快照不读当前端**：小程序下单 → 关掉「小程序可发放」→ 订单完成时不发分；
   **并且用定时任务触发完成**（此刻没有任何「当前端」）→ 结论不变。
   这条钉死 §5.4.2，是整个端设计里最容易写错的一处。
2. **发放的端开关不追溯**：下单时允许发放，完成前把该端关掉 →
   仍按**下单时**的规则发。与 `toggleMerchant`「关闭只影响将来」同一条规矩。
3. **核销读当前端**：关掉「小程序可核销」后，同一用户同一批商品，
   小程序结算页拿不到抵扣额度，App 上可以。
4. **回收不受端控制**：在被禁用的端上发起退款 → 已发积分照常收回。
5. **解冻不受端控制**：在被禁用的端上取消订单 → 已冻结积分照常解冻。
6. **不可用要带原因**：`canRedeem` 返回的不可用理由能直接渲染成给用户看的话，
   而不是一个布尔值 —— 否则界面只能说「不可用」，用户不知道去哪用。

> 4 与 5 是**资金正确性**，不是策略：拦住的话账上会凭空多出积分。
> 它们必须有独立测试，不能只靠「反正没人会那么配」。

## 9. 风险

| 风险 | 应对 |
|---|---|
| **动了下单主流程** | `create` 是全站最要害的方法。新增校验一律前置且只读，回归以线上支付全链路一条不红为准 |
| 五道闸在多处各判一遍 | `PointsAvailability` 与 `PointsRuleResolver` 各自唯一入口 + 守卫测试 |
| 端标识被当成身份用 | 它来自客户端、可伪造。代码注释写死「只用于平台策略，不得用于权限或资金判定」 |
| **发放时读了当前端而不是订单快照** | 订单完成常由系统触发，那时没有「当前端」。判定只读 `ord_order.pay_scene`，加测试钉死（用定时任务触发完成，仍按下单端发放） |
| **回收/解冻被端开关拦住** | 那是资金事故不是策略。回收与解冻**不经过任何端判定**，单独一条测试 |
| 用户在某端看得到余额却用不了 | 显式提示「本端暂不支持积分抵扣」并说明哪个端可用，**不静默隐藏入口** |
| 平台定规则、商家出钱 | 保留 `toggleMerchant` 作为商家的退出口（§5.1 ④） |
| 「配了 0」掉到下一层 | 按键存在与否判，不按值判。单独一条测试（§5.2） |
| 线下单混进分账报表 | 报表按 `pay_channel` 分组时排除 `OFFLINE`，用测试钉死 |

## 10. 明确不做

- 不做平台代收代付、不做资金池（ADR-002）。
- 不做线下单抽佣（已拍板）。
- **不启用积分**（独立决定）。
- 不做跨商家积分清算（ADR-006 §2 未定，建议仍是先 B 后 A）。
- 不改积分汇率、抵扣上限、发放时机（ADR-006 已定）。
- 不给商家开放积分配置（第 2 条拍板）。
- 不做「指定服务人员」排期、不做预售入口。
