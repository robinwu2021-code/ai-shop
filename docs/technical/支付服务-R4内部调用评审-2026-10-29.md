# 支付服务 R4 内部调用评审

状态：评审完成，内部链路仍有待收尾项 · 2026-10-29
基线：7908c0a86及本分支法币P1修复增量。范围：商城/餐饮内部普通支付、内嵌/远程装配、调用留痕及支付结果回传；不包含储值积分全流程或真实渠道联调。本轮专项只读，不在本报告中实施事件化或生产切流。

## 一、结论与进度

内部调用已具备内嵌/远程SPI、调用方来源记录、按业务类型隔离的支付单端点，以及普通支付的原请求/付款人身份校验。但内部普通发起仍走旧兼容通道路径，未统一进入本批完整账户证明与新路由准入；内部成功结果仍依赖直接调用业务或补单，不能判定独立部署闭环已完成。

| 检查项 | 代码现状 | 结论 |
|---|---|---|
| 业务支付单身份 | PaymentPortImpl按内部app建单，app+outOrderNo幂等，查询按bizType分app | 已有实现及测试；未知类型映射需收口 |
| 内嵌/远程装配 | OrdinaryPaymentRouting只装embedded；RemoteOrdinaryPaymentInitiationPort/RemoteOrdinaryPaymentPort用于standalone | 分支装配存在；不等于生产已切流 |
| 请求和付款人 | 原PaymentOpen快照、requestHash、付款人冻结及重放冲突校验 | 已有；本批保留旧JSON/摘要兼容 |
| 路由和资金账户 | 内部普通PaymentOpen默认无acquiringRoute，发起器保留legacy prepay入口 | 尚未进入新路径安全保证，R4-01 |
| 内部留痕 | PaymentPort包装RecordingPaymentPort；普通发起内嵌lambda未包同一recorder | 留痕覆盖不完整，R4-03 |
| 成功回传与恢复 | PARTNER持久webhook；内部仍直接markPaid，I8扫描补单 | 内部持久事件闭环未完成，R4-02 |
| 内部鉴权 | 新支付端点受InternalGuard来源/IP/配置开关约束；普通支付旧端点使用InternalServiceResponses共享服务令牌 | 两套入口按已批准过渡设计并存；上线需核对实际配置，不把识别来源当凭据已验证 |
| 部署验收 | 本轮没有部署两进程和真实渠道 | 不标生产或独立形态验收完成 |

## 二、问题与证据

### R4-01 · P1 · 内部普通支付仍未使用统一的账户证明与路由准入

位置：`backend/shop-core/src/main/java/ai/neargo/shop/trade/service/impl/OrderServiceImpl.java:2256`、`:2328`；`backend/shop-app/src/main/java/ai/neargo/shop/payclient/OrdinaryPaymentRouting.java:32`；`backend/pay/pay-domain/src/main/java/ai/neargo/shop/pay/service/impl/OrdinaryPaymentInitiationServiceImpl.java`的无acquiringRoute分支。

业务侧构造旧PaymentOpen（含原门店路由的交易有stores快照，但没有新的收款商户id/接入模式/签名密钥版本契约），经OrdinaryPaymentInitiationPort进入旧兼容prepay；不会像PaymentService.start一样执行新RouteSelectionPolicy及冻结账户执行能力检查。内部支付单创建还从首个子单的当前PayStore带fundsPath，不能凭此证明与实际原收款账户相同。

本批P1已经阻断明确acquiringRoute路径的默认账户回退，但保留了旧普通协议兼容，**不能据此宣称内部所有法币支付已获得同样保证**。该问题在本轮按代码路径确认，未执行真实商户转账。

建议：先定义业务订单与支付单之间的唯一发起契约和冻结事实来源，再统一内部调用。商城多门店订单、餐饮/积分来源已冻结现金意图，需要分别保留其权威来源，不能统一时强行选首家店或填当前配置。旧在途交易只复用有证明的原快照，不猜补。

验收：商城、餐饮分别验证内嵌与HTTP调用，实际渠道上下文/原交易号/金额币种/主体门店完全相同；多门店DIRECT账户不一致明确拒绝；真实渠道账户未证明时零网络请求。

### R4-02 · P1 · 内部支付成功缺少已完成的持久投递与消费闭环

位置：`pay-domain/.../notify/service/impl/BizNotifyServiceImpl.java:94`；`pay-portal/.../api/callback/ChannelPayCallbackController.java:107`；`shop-app/.../paybridge/PaymentFollowUpResolver.java:31`；`shop-app/.../paybridge/OrderPaidReconciler.java:99`。

通知落库仅覆盖PARTNER；内部成功在支付记账后直接调用OrderRepairPort，补查也直接调用markPaid。虽然I8可拉取补单，但尚未发现支付专属INTERNAL_EVENT的完整生产者、投递、去重消费者及失败恢复实现。通用Outbox或枚举注释存在，不等于这条链已经接通。

本批已修I8正常业务补单资格：已关联支付单的Money异常、晚到或重复到账不得因原始流水SUCCESS被补成业务已付；原始现金事实仍保留。该修复只解决错误投影，不能替代可靠投递能力。

建议：支付事务内持久记录内部支付结果，事务外投递；业务侧按事件id/单据状态版本幂等消费；记录重试、死信和人工恢复；各回调/查单/补单统一为同一结果来源。

验收：支付成功后立即使业务服务不可用、超时或重启，恢复后业务最终且仅一次变为已付；重复/乱序事件、取消后到账不推进正常业务状态；第三方订单仍走自己的webhook。

### R4-03 · P2 · 内嵌普通发起与远程普通发起的内部留痕覆盖不同

位置：`shop-app/.../payclient/OrdinaryPaymentRouting.java:32`、`:49`；`shop-app/.../payclient/port/RemoteOrdinaryPaymentInitiationPort.java:33`。

PaymentPort建单/查询/关闭等经过RecordingPaymentPort，普通发起却是直接调用service.initiate的lambda；远程普通发起则经过HTTP与内部入口。未发现内嵌普通发起具有同样的InternalCallRecorder包装。渠道调用日志不等于业务调用来源记录，因此不能把M2的“内部调用都有记录”推广到这条入口。

建议：按逻辑调用统一记录来源、追踪id、结果和异常，避免内嵌少记或远程两层重复计数；保留HTTP访问日志和渠道调用日志各自职责。

验收：同一普通支付请求在embedded/standalone两种形态各形成一条可对应的逻辑内部调用记录，成功、业务拒绝、未预期异常均覆盖，来源字段一致。

### R4-04 · P2 · 未知内部业务类型自动归入商城

位置：`pay-domain/.../acquiring/port/PaymentPortImpl.java`的appOf；`pay-domain/.../client/port/RemotePaymentPort.java`的appOf。

两处都只识别FOOD_CHECK，其他字符串均返回MALL。未知或拼错的bizType因此被解释为商城，而不是明确拒绝；远程端点own校验也依赖同一映射。该行为按源码确认，不认定已发生越权事故。

建议：明确业务类型注册值域或显式映射，未知类型拒绝；若某些业务有意复用MALL接入方，应逐项登记并保留原业务类型，不能用默认分支代替协议。

验收：有效商城/餐饮映射保持一致；空值、未知值、错拼值在本地和HTTP端点均明确拒绝且无支付单/尝试写入。

## 三、验证范围

本批支付模块全测包含PaymentPortLocalRemoteParityTest：启动真实随机HTTP端口，但PaymentService、RefundService等域服务为替身，验证字段、错误和调用方边界，**不是两独立进程+真实支付库的业务端到端证明**。

定向跨域回归覆盖RemoteOrdinaryPaymentInitiationPortTest、RemoteOrdinaryPaymentPortTest，以及付款结果、关闭/取消、退款、历史回填和架构约束；最终数量和命令见[TDD法币收款P1收尾](./TDD-支付服务-法币收款P1收尾.md)§5。本报告不把这些通过等同于以上四项缺口已修复。

真实微信/支付宝的路由账户与签名凭据版本尚未建立可证明绑定；新路径默认拒绝此类执行是安全边界，不是渠道联调完成。生产主应用和支付服务仍为上一轮只读确认的旧版本，本轮未改变。
