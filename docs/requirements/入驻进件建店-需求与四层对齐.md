## 第一部分 · 需求

### 一、这三段到底在解决什么

| 段 | 业务问题 | 完成的标志 |
|---|---|---|
| **入驻** | 平台怎么确认「这家店是谁、能不能开」 | `mch_entity` 有一行 ACTIVE |
| **进件** | 钱怎么进到这张执照名下 | `mch_payment_merchant.pay_merchant_no` 有值且 ACTIVE |
| **建店** | 顾客在哪儿买、货从哪儿发 | `mch_store` 至少一行、有地址与服务范围 |

三段**不是一件事的三个步骤**，是三条各自可失败、可重试的独立链路：

- 入驻通过但进件没过 → 店能开、商品能上架、**收不了钱**
- 入驻通过但服务范围没定 → 店开着、商品在架、**对谁都不可见**（且不报错）
- 进件过了但门店没地址 → 能收钱、**顾客不知道去哪取**

> 所以 B 端必须给出**分段的状态**，而不是一个「入驻中」进度条。
> 商家最常问的三个问题就是「我能开张了吗 / 我能收钱了吗 / 我的店能被看到吗」，
> 它们分别对应这三段，混成一个进度条就一个都答不了。

### 二、入驻需求（S1）

#### 2.1 谁发起

| 场景 | 现状 | 定稿 |
|---|---|---|
| C 端小程序里看到「我要开店」 | 消费者账号发起 | 消费者账号发起，**通过后派生商家账号** |
| B 端 App 直接注册开店 | ⬜ 不支持 | **商家账号自行注册后发起** |
| 被驳回后补交 | B 端补交（人已装 App） | 不变 |

> 两套账号池彻底独立，但**入驻是唯一合法的跨池入口**：
> C 端用户提交申请 → 通过时以申请里的 `contact_phone` 建 `mch_account`。
> 这不违反「不关联」—— 派生之后两个账号各活各的，不存在互指列。

#### 2.2 商家要填什么

| 字段 | 必填 | 为什么 |
|---|---|---|
| 店铺名 | ✅ | —— |
| **行业** | ✅ | 决定能不能小微、要不要资质、是否强制积分 |
| **法律形态**（小微/个体户/企业） | ✅ | 决定进件通道主体、结算账户形态、能否开票 |
| 联系人 + 手机号 | ✅ | 审核要打电话；且**手机号就是将来的商家账号** |
| 主营类目 | ✅ | —— |
| 店铺简介 | ✅ | —— |
| 服务范围 + 覆盖社区 | 🟡 申请时可空 | **审核通过时必须确定**，否则商家上着架对谁都不可见 |
| 资质图片（执照/身份证） | ⬜ 选填 | 属**进件**不属入驻。逼一个还没过审的人先传执照，只会把人挡在门外 |
| 是否兼做自提点 | ⬜ 选填 | 小店既是供给方也是取货点 |

**约束**：一人同时只能有一份进行中申请（库级唯一键）。
文案必须说「**同时**只能有一份」而不是「只能有一个」—— 否则商家以为平台不支持多执照。

#### 2.3 平台审核

| 需求 | 说明 |
|---|---|
| 接单认领 | 防两个运营同时审同一单 |
| 通过 / 驳回，驳回必填原因 | 驳回只说"不合格"等于让人再猜一次 |
| 通过时**必须确定服务范围** | 申请时可空，通过时不能空 |
| 全程留痕 | 谁、何时、依据什么 |
| **幂等按申请单，不按人** | ✅ 已修，见 §2.4 |

#### 2.4 ✅ 通过时的幂等（已修）

**曾经的缺陷**：判据是「这个人是不是已有主体」。老板申请**第二张执照**、通过时被当成
重复点击，**去改第一个主体** —— 名称/行业/法律形态被覆盖，两家店变一家，**全程无报错**。

**修法**：`ActivateCommand` 末位传 `activatedEntityNo`（= `mch_entity_apply.entity_no`）。
非空即这份申请已激活过，按它幂等重放；为空一律新建。
回归用例锁住两条：`secondLicenseCreatesSecondEntity` 与 `repeatedApproveIsIdempotent`。

#### 2.5 通过时自动派生（同一事务）

| 派生物 | 规则 |
|---|---|
| 主体 `mch_entity` | 一份申请一个主体 |
| owner 商家账号 `mch_account` | 用申请里的 `contact_phone` 作 `login_phone` |
| 默认门店 `mch_store` | `ST-{entityNo}`、`is_default=1`；**名称默认取店铺名** |
| 进件占位 `mch_payment_merchant` | `APPLYING`，通道 WECHAT |
| 服务社区 `mch_entity_community` | 单一写入口，与店铺设置共用 |
| 自提点 `cmt_pickup_point` | 勾了才建 |

> 派生失败必须整体回滚。「主体建了但没有默认门店」这种半成品，
> 表现是商家登进来看到空工作台，而后台数据看起来是正常的。

### 三、进件需求（S3）

#### 3.1 为什么它必须独立成段

进件是**支付通道的开户流程**，不是平台的审核流程：

| | 入驻审核 | 收款进件 |
|---|---|---|
| 谁批 | 平台运营 | 微信/支付宝 |
| 依据 | 平台规则（行业、社区） | 通道规则（执照、法人、结算账户） |
| 失败后果 | 开不了店 | 店能开，**收不了钱** |
| 可重试 | 补交重提 | 补资料重新提交进件 |

把它们合成一步，就会出现「平台批了但通道拒了」时**没有地方承载这个状态**。

#### 3.2 需求清单

| # | 需求 | 说明 |
|---|---|---|
| 3.2.1 | 激活时建占位记录 | ✅ 已有。否则第一笔订单来了发现没有收款方，钱收了分不出去 |
| 3.2.2 | 法律形态 → 通道主体的翻译走主数据 | ✅ 已有。曾有三处各写各的 if，判错一次就是进件被拒 |
| 3.2.3 | B 端补交进件资料 | ✅ `POST /biz/merchant/payment`；明文只在请求里存在，库里只留掩码 |
| 3.2.4 | 提交进件 → 通道回执 → 落 `sub_mchid` / `pay_merchant_no` | ✅ `PayApplymentGateway` + `MerchantPaymentService`；回查幂等，重复回执不换号 |
| 3.2.5 | 进件状态对商家可见 | ✅ B 端「收款设置」页；`canReceiveMoney` + `missing` 逐条列出缺什么 |
| 3.2.6 | 进件被拒 → 原因回显 + 补交重提 | ✅ 重提会清掉上次拒因，免得商家以为没提交成功 |
| 3.2.7 | 多通道各一条（微信/支付宝） | 🟡 表支持，只自动建了微信 |
| 3.2.8 | 未进件成功时的**下单拦截口径** | ⬜ **仍待拍板**：建议允许上架、下单时拦并给明确文案 |

#### 3.3 结算账户的处理原则

真实账号**只有后端持有**，B 端与 C 端一律只看掩码（`settle_account_masked`）。
账户形态由法律形态决定默认值（小微→个人收款，其余→对公），不让商家猜该填哪个。

## 第三部分 · 四层对齐

### 八、🔴 最严重的错位：Ops 端与后端**契约都不是同一套**

| ops-web 调用 | 后端实际提供 | 结果 |
|---|---|---|
| `GET /ops/merchants` | `GET /ops/merchant/apply` | ❌ 路径不同 |
| `POST` 状态/认证/归档系列 | 仅 `accept` + `audit` | ❌ 无对应 |
| `GET /ops/stores/audits` `/qrcodes` `/acquisition` `/templates` | **零实现** | ❌ 全部 mock |
| `GET /ops/merchants/violations` `/auth-codes` | **零实现** | ❌ |
| `GET /ops/payments/recon-diffs` `/close-rule` | **零实现** | ❌ |

ops-web 的开关是 `NEXT_PUBLIC_USE_MOCK !== "0"` —— **默认走 mock**，
所以页面一直是绿的，没人会发现后端根本没这些接口。

> **建议**：先做一次**契约对账**（把 ops-web 的 http 层路径与后端 Controller 逐条比对，
> 产出「后端要补的接口」清单），再决定哪些进 M-Ops。
> 在那之前，ops-web 上线**只能**当 demo 用 —— 这一点要写进发布清单，别让它悄悄上生产。

| category | ✅ | ✅ | ✅ | ✅ | `category` | `category` |
| desc | ✅ | ✅ | ✅ | ✅ | `description` | `description` |
| asPickupPoint | ✅ | ✅ | ✅ | ✅ | `asPickupPoint` | `as_pickup_point` |
| serviceScope / communityNos | ✅ | ✅ 已补（含"选大了/选小了"后果说明） | ✅ | ✅ | 同名 | `service_scope` / `community_nos` |
| licenses | ✅ | ⬜ 表单缺 | ✅ | ✅ | `qualifications` | `qualifications` |
| settleAccountType | ✅ | ⬜ 表单缺 | ✅ | ✅（转进件） | —— | 落 `mch_payment_merchant` |
| **industry** | ✅ 已补登 | ✅ 行业选择器 | ✅ 行业选择器 | ✅ | `industry` | `industry` |

**三处已修（本轮）**：

1. **`industry` 此前不在契约里，而且没有任何端在传** —— 比最初判断的更糟：
   后端一直在收、库里一直有这一列，于是 `mch_entity.industry` **恒空**，
   进件时才发现主体类型选错了。现已补进契约，并在 B/C 两端都做成**行业选择器**，
   由 `/common/master-data` 驱动「这个行业能不能选小微」的联动。
2. **b-app 的申请表单缺 `serviceScope` / `communityNos`** —— B 端提交的申请服务范围恒空，
   本该由运营在审核时补，而运营侧那条链是 mock，于是**没有任何地方能填上它**，
   商家上架后对谁都不可见。现已补上，并带「选大了送不到、选小了搜不着」的后果说明，
   「仅本社区却一个都没选」拦在提交前。
3. `licenses` / `settleAccountType` 从入驻表单**移到了进件页**（B-8）——
   它们本来就属于开户流程而不是入驻申请（ADR-002），放在入驻表单里只会把人挡在门外。
3. **命名三层不一致**：契约 `subject` → 实体 `legalForm` → 表 `legal_form`。
   实体与表已按基准对齐，契约还是旧词。转换点在 Controller，属已知欠账（契约改名期）。
