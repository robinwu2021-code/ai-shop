# PRD · 定时任务管理

> 2026-08-26。技术方案见[定时任务独立模块](../technical/design/定时任务独立模块-技术方案.md)。

---

## 一、为什么要做

### 1.1 一句话

平台有 **15 个定时任务**（14 个已提交 + 1 个在写），它们负责关单、投递事件、对账、
积分转正、套餐到期、资质到期这些**没有人会手动去做的事**。

**而它们在生产上一次都没跑过。**

### 1.2 事实（2026-08-26 查生产库）

```
sys_job_run   0 行        ← 任务运行记录表，空的
shedlock      0 行        ← 分布式锁一次都没被拿过
sys_outbox    空表        ← 领域事件一条都没投递出去
```

原因：生产实例跑的是 `SPRING_PROFILES_ACTIVE=api,ops`，
而 15 个任务全部挂在 `@Profile("worker")` 上。**没有任何进程在跑 worker。**

隔离做完了，「谁来跑」这半件没做——而这件事**没有任何地方会报错**。

### 1.3 今天没出事，是因为还没有真实业务

平台至今 **0 笔成交**、outbox 空表、无待处理媒体、无资质记录。
所以「关单任务没跑」这件事现在看不出后果。

**但窗口有期限**：线上唯一那个 PRO 套餐 **2026-09-03 到期**。
到那天 `PlanExpiryJob` 会第一次真的降级压店——
**在有数据的时候，第一次跑一个从没跑过的任务**。

### 1.4 三个必须解决的问题

| # | 问题 | 今天的表现 |
|---|---|---|
| P1 | **该跑的没跑，没人知道** | 15 个任务零执行，而没有任何告警、页面、日志指出这件事 |
| P2 | **停不掉，也重启不了** | 15 个里只有 1 个有开关。某个任务在生产上闹事时，唯一手段是改配置重启整个业务实例 |
| P3 | **发布会打断任务** | 一旦启用，每次发布重启都会打断正在跑的任务。15 个里 **4 个没有幂等口径**，其中「营销推送」打断重跑就是**发两遍消息** |

## 二、谁在用

| 角色 | 要做什么 | 频率 |
|---|---|---|
| **运营** | 看任务跑没跑、跑成没成、失败了多少次；出事时**关掉某个任务**；补救时**手动触发一次** | 日常巡检 + 出事时 |
| **开发/运维** | 排查「上周四凌晨那次为什么失败」；改某个任务的执行时间 | 排查时 |
| **平台自己** | 到点执行，失败重试，连续失败时升级告警 | 持续 |

**运营是第一用户。** 所有界面文案按「不看代码也能明白」写——
任务名不能是 `plan-expiry`，得是「增值包到期扫描」；
结果不能是 `OK/null`，得是「本轮无到期主体」。

## 三、任务清单（业务视角）

按频率排。**「做什么」这一列就是运营页面上要显示的原话**。

| 任务 | 做什么 | 频率 | 不跑的后果 |
|---|---|---|---|
| 事件投递 | 把已落库的领域事件发给消费者 | 5 秒 | 事件永远积在库里，下游什么都收不到 |
| 进销存事件投递 | 同上，独立库自带一份 | 5 秒 | 同上 |
| 媒体回收执行 | 执行运营已确认的回收批次。**唯一真的删文件的任务** | 30 秒 | 运营点了「确认删除」之后没有反应 |
| 超时订单关闭 | 关掉超时未支付的订单，释放它占住的库存、券、积分 | 1 分钟 | **库存被永久占住**，别人买不到 |
| 营销推送下发 | 到点把排队的推送任务发出去 | 1 分钟 | 定时推送永远不发 |
| 预留过期回收 | 回收到期未确认的库存预留 | 1 分钟 | 同上，库存被占住 |
| 媒体上传对账 | 收拾上传崩在半路留下的半截记录 | 1 小时 | 「磁盘有文件、库里没有」的孤儿越积越多，只能靠人去 `du` 才发现 |
| 收款对账自查 | 每轮扫超时未终态的收款并尝试修复 | 10 分钟 | 用户看到「我的订单不见了」，只能等人工 |
| 库存存量搬运 | 一次性把存量库存搬进新模型 | 10 分钟 | （一次性任务，已有开关，默认关） |
| 待生效积分转正 | 把过了售后期的积分从「待生效」挪进「可用」 | 每天 00:05 | 用户的积分永远不到账 |
| 积分恒等式自检 | 对账：池子里的钱 == 还欠用户的钱 | 每天 00:40 | 两边分家了也没人知道 |
| 资质到期扫描 | 把过期资质对应的在架商品下架 | 每天 03:10 | 没有资质的商品继续在卖 |
| 媒体标记扫描 | 标记疑似可回收的文件。**只改状态，一个都不删** | 每天 03:20 | 无人清理，空间持续增长 |
| 增值包到期扫描 | ACTIVE → 宽限 7 天 → 降级压店 | 每天 03:25 | **商家过期后门店照常接单**，事后再压等于把「已经卖掉的货」变成争议 |
| 进销存日快照 | T+1 结算昨天的库存账 | 每天 03:30 | 日账缺一天，之后每天都对不平 |

> 最后一个（进销存日快照）由另一条会话实现（`7f686dba`）。
> 本 PRD 把它算进范围，但实现归属那边。

## 四、功能需求

### F1 · 看得见

| # | 需求 | 验收 |
|---|---|---|
| F1.1 | 运营端有一页列出全部任务：中文名、所属模块、执行频率、开关状态 | 15 个任务一个不少 |
| F1.2 | 每个任务显示**最后一次**：什么时候跑的、耗时、成功还是失败、**这一轮做了什么**（「关单 3 单」） | 从没跑过的显示「从未执行」，不是空白 |
| F1.3 | 显示**连续失败次数**与**累计执行轮次** | 连续失败 ≥3 时在列表里高亮 |
| F1.4 | 能看每个任务的**执行日志**，按时间倒序分页，可按成功/失败筛选 | 失败的能看到原因 |
| F1.5 | 日志区分**定时触发**与**人工触发** | 出事时分得清是不是人点出来的 |

### F2 · 控得住

| # | 需求 | 验收 |
|---|---|---|
| F2.1 | 关掉某个任务，**不重启进程**即生效 | 关掉后不再产生新的执行记录 |
| F2.2 | 重新开启，同样不重启 | 开启后按 cron 恢复执行 |
| F2.3 | 改某个任务的执行时间（cron），不重启即生效 | 非法表达式**当场拒绝**，不能落库 |
| F2.4 | **立即执行一次** | 正在跑时拒绝并说明，不排队、不并发 |
| F2.5 | 秒级任务**不提供**「立即执行」按钮 | 等一下它自己就跑了，给按钮只会让人误以为坏了 |
| F2.6 | 每一次开关/改 cron 都记下**是谁改的** | 「谁把这个任务关了」查得到 |

### F3 · 跑得住

| # | 需求 | 验收 |
|---|---|---|
| F3.1 | 多实例同时运行时，同一任务**不会被跑两遍** | 已有 ShedLock，需保持 |
| F3.2 | 单个任务失败**不影响其它任务** | 一个抛异常，其余照常 |
| F3.3 | 连续失败达阈值时升级告警 | 已有（3 次升级 error 日志），需在页面上也能看到 |
| F3.4 | **发布业务不打断正在执行的任务** | 独立部署单元；见技术方案 |

### F4 · 将来（本期不做，但结构上要留出位置）

| # | 需求 |
|---|---|
| F4.1 | **漏跑检测**：到点没跑成的，记下来 |
| F4.2 | **补跑**：重试到成功；跨天的能补昨天那一轮 |
| F4.3 | **按业务日期驱动**：日结/对账问的是「2026-08-25 这一天的账结了吗」，不是「昨晚 3 点那次跑了吗」 |

> F4 三条合起来才是「一定执行」。**独立部署只解决「不被打断」，不解决「一定执行」**——
> 这两件事经常被当成一回事，而日结与对账真正需要的是 F4。

## 五、非功能需求

| # | 要求 | 依据 |
|---|---|---|
| N1 | 独立部署单元，与业务实例分开重启 | F3.4 |
| N2 | 常驻内存 ≤ 512MB | 实测：业务实例 `-Xmx2g` 而堆只用 117MB；worker 无 Tomcat、无请求涌入，512MB 宽裕 |
| N3 | 执行日志**自动清理**，保留 30 天 | 5 秒一轮的任务一天 17280 行；不设闸它会长成库里最大的表 |
| N4 | 配置改动 30 秒内生效 | 关一个任务晚 30 秒，与「立刻」在运维上没有区别 |
| N5 | 新增任务**不需要写迁移**，上线即出现在列表里 | 否则忘了写迁移的那个任务会静默不注册，且不报错 |

**资源不是约束**（2026-08-26 实测）：内存 used 1899/7685MB、swap 从未使用、
负载 0.10/4 核、30 天 0 次 OOM。当初「怕机器扛不住」的顾虑可以放下。

## 六、明确不做

| 不做 | 为什么 |
|---|---|
| 把 15 个任务搬进一个模块 | 会让那个模块**反向依赖 6 个域**，比现在更糟。它们本来就是薄触发器（12/14 只持有 Service/Port），留在原地 |
| 运营端与 worker 之间建 RPC | 多一个「worker 连不上」的失败面，而它恰恰在发布时发生——那正是要隔离的时刻。改走数据库 + 轮询 |
| GraalVM native | 任务进程常驻，启动优势无效；常驻内存收益在只有一个 worker、机器闲 5.8GB 时不成立。等 Spring Data AOT 迁移完、且要跑多个 worker 时再评估 |
| 任务编排 / DAG 依赖 | 现有 15 个互不依赖。真需要时再说，先做出来一个没人用的编排引擎更糟 |

---

## 七、验收标准（一句话版）

1. 运营在页面上**看得到** 15 个任务各自跑没跑、跑成没成、上一轮做了什么
2. 运营能**关掉**其中任意一个，且不重启进程
3. 发布业务时，正在跑的任务**不被打断**
4. `sys_job_log` **不会无限增长**
5. 新增一个任务，**不写迁移**就出现在列表里
