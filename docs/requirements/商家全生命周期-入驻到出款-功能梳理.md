## 0. 为什么要串起来看

这七个环节各自都有页面，也各自都有人在做。**问题从来不出在某一环里，出在环与环之间**：

- 审核通过了，但收款进件没走完 —— 商家能上架、能卖，**钱收不到**
- 积分开关是「商家自己开」的，而他看不到自己发分花了多少钱
- 结算单状态是「已分账」，而底下是桩 —— **账面与资金脱节**

所以这份梳理按**链**排，不按模块排。每一节回答同一组问题：
谁做、在哪做、做完之后系统里变了什么、**下一环凭什么知道上一环好了**。

## 2. 环与环之间的判据

这一节是这份文档的重点：**下一环凭什么认为上一环好了**。

| 从 → 到 | 判据 | 现状 |
|---|---|---|
| 审核 → 上架 | `mch_entity.status = ACTIVE` | ✅ 判得对 |
| 审核 → **收款** | **没有判据** | ❌ **审核通过不代表能收钱** |
| 进件 → 结算 | `payMerchantNoOf()` 解析得到收款号 | ⚠️ 解析不到时**账单照常生成**（钱欠着），发起打款那步才拦 |
| 资质 → 线下收款 | `expire_at` 现算，不看 `status` | ✅ 本批落地（那个置 EXPIRED 的定时任务在生产不跑） |
| 积分开关 → 发分 | 社区 → 商家逐级 | ✅ |
| 结算 → 出款 | 状态 `SPLIT` | ❌ **它同时表示「指令已发出」与「钱已到」** |

### 2.1 最要紧的一条：审核 ↛ 收款

**入驻审核通过与「能不能收到钱」是两件事，而系统里没有任何地方表达这个区别。**

商家审核通过 → 能建店、能上架、能被下单 → 订单成立 → 结算单生成 →
`payMerchantNoOf()` 解析不到收款号 → 账单留空、钱欠着。

而商家这一路上**没有收到任何提示**。他看到的是订单在来、结算单在生成。

> 现有代码其实已经预料到了（结算那段注释写着「进件还没走完时留空：账单照常生成，
> 钱是欠着的，不是不存在」）—— 但那是**结算侧的兜底**，不是**入驻侧的闸**。
> 兜底保证了不出错，没保证有人知道。

**建议**：在商家工作台上给一条「你还不能收款」的提示，判据是进件状态而不是审核状态。
这是这条链上代价最小、覆盖最广的一个补丁。

## 3. 各环节的缺口

### 3.1 收款进件（第 4 环）

- 通道未接：`mch_payment_merchant` 有状态机，但没有真的进件调用
- **三档主体（小微 / 个体 / 企业）的差异没有落到界面上** ——
  商家不知道自己该走哪一档，也不知道选错的后果（小微没有 H5/App 支付方式）
- 资金路径（归集 / 直连）在运营端可配，**B 端完全不可见** ——
  而它决定了商家的钱走哪条路

### 3.2 积分（第 5 环）

- B 端**零页面**：`/biz/points/account`、`/records`、`/toggle` 三个接口都在，没有出口
- 开关是「商家自己开」，而他看不到成本 —— **让人在看不到代价的情况下做决定**
- 类目规则由平台配，商家侧应当**只读展示**（他要知道自己这类发多少）
- 积分池恒等式有 `checkIdentity`，**没有告警** —— 要人主动去看

### 3.3 出款（第 7 环）

见 [PRD-商家资金到账与对账](PRD-商家资金到账与对账.md)。一句话：
分账网关是桩，第三方商家的钱没有真能到手的路；而「提现」在分账模型下是二清，
不是补全它就行的事。

## 4. 建议的推进顺序

按「**让看不见的变得看得见**」优先，而不是按功能大小：

1. **工作台「你还不能收款」提示**（第 2.1 节）—— 一条判据，覆盖整条链最大的盲区
2. **B 端积分两屏**（S04 / S05）—— 接口现成，只差出口；让开关的决定有依据
3. **`SPLIT` 语义拆分 + B 端到账进度**（S06 / S08）—— 让「账面已结算而钱没到」这件事显形
4. **四轴对账**（收款 / 分账 / 出款 / 积分池）—— 见 TDD
5. **分账接通** —— 卡在 B7 商务前置，不是技术问题

> 1–4 都不依赖 B7。**第 5 项拿不到书面口径就不要开工** ——
> 猜一个限额去试，第一次撞上限的是真实商家的真实货款。
