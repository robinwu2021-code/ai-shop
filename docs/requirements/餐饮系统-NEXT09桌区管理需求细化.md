## 2 目标与业务边界

### 2.1 业务目标

门店管理人员能够把实际就餐空间组织为“大厅”“一楼”“二楼”“包间区”“露台”等桌区，按门店查询和排序展示；名称变化不影响原有桌区引用。暂不使用的桌区可安全停用，满足条件后可恢复启用。

中餐、西餐、火锅、茶餐厅等沿同一桌区模型配置，不增加业态专用表。无桌快餐、纯外卖等不强制创建桌区，也不自动造一个“默认桌区”。先吃后付与先付后吃不改变桌区配置规则。

### 2.2 建模选择

采用既有的**门店内平铺桌区**：一个桌区属于一个门店，一个桌区后续可关联多张桌台。名称可表达楼层和区域。

不引入楼栋→楼层→桌区的树形结构，避免增加父子节点和继承规则；不使用商品分类承载桌区，避免混合商品与就餐空间的生命周期。这两种方案均不纳入本轮。

### 2.3 本轮与后续范围

| 本轮交付 | 后续切片 |
|---|---|
| 桌区分页列表、创建、改名和排序、启停 | TBL-02桌台配置、容量、桌号、资源状态 |
| 主体门店校验、同店编码唯一、版本及重复提交处理 | TBL-03桌码、扫码会话 |
| 停用前核验启用桌台和活动占用 | TBL-04开台、人数座位、占用仲裁 |
| 真实操作人、审计和必要领域事件 | TBL-05清台；后续转台、拼桌、并桌 |
| 两部署方式一致的业务行为 | AA、拆合账、订单、支付、打印、厨房、日结和报表 |

本轮不提供删除、归档、跨店迁移、修改编码、批量排序、桌区平面图、包间费、最低消费、服务员分区排班或桌区级营业时间。已有全局餐饮需求继续保留，仅不进入NEXT-09交付范围。

## 5 业务规则

### 5.1 对象与字段

| 字段 | 已有约束 | 本轮确认规则 |
|---|---|---|
| areaNo | 系统生成，最长32，稳定业务编号，不暴露物理id | 创建后不变，不允许客户端指定 |
| entityNo / storeNo | 沿现有主体、门店业务编号 | 当前授权上下文与实际对象归属一致；客户端body不接受归属重写 |
| code | 必填，最长32，同门店唯一，编码保留不复用 | 去除两端空白，空串拒绝；不增加正则或自动大小写转换；按现有二进制排序规则精确判重 |
| name | 必填，最长64 | 去除两端空白，空串拒绝；名称不做唯一约束 |
| sortNo | 必填int32 | 数值升序，允许重复及int32合法值；同值按areaNo稳定排序，不做全店自动重排 |
| status | ACTIVE / DISABLED | 创建默认ACTIVE；修改接口不可顺带改状态 |
| version | 沿BaseEntity乐观锁 | 创建初始版本沿平台填充规范并真实返回；编辑和启停携带当前版本，不能猜测或省略 |
| reason | 启停接口必填 | 去空白后不能为空，最长255；直接写已有fnb_action_log.reason，不新增桌区列 |

同门店编码唯一沿现有 `(store_no, code)` 唯一键；应用检查用于友好报错，最终以数据库约束兜底。同一主体下不同门店可以使用相同编码，禁止跨主体引用门店。

### 5.2 列表

page默认1，size默认20、最大100；超出合法范围应返回参数错误，不能静默返回其他门店数据。status可省略；省略时返回当前门店所有未逻辑删除的启用及停用桌区，传入时仅接受ACTIVE或DISABLED。

主体和当前门店过滤必须同时应用于records和total。排序采用sortNo升序、areaNo升序。不保证并发写入期间跨多个分页请求得到历史快照。

### 5.3 创建和修改

创建不要求先存在菜品、订单、支付账户或库存配置；不把营业时间和当前餐饮接单日历作为创建桌区的前置条件。门店存在、归属有效、账号获授权以及平台已有餐饮接入条件仍须满足。

创建后返回完整桌区对象。编辑仅允许name、sortNo、version；不接受code、status、storeNo、entityNo或actorNo等未定义输入。停用桌区也允许改名、改排序，以便重新启用前整理配置。

写请求带原有Idempotency-Key；同主体、门店、动作和操作人下同键同参重放返回首次结果，同键异参或换操作人拒绝。编辑和启停的请求摘要包含areaNo及version，防止同键误用于其他对象。业务冲突及参数失败不产生业务变更记录。

同一个请求重试时优先重放首次成功结果；不同键的新请求必须重新校验version。具体键作用域及过期策略沿现有IdempotencyService，不创建第二套幂等表。

### 5.4 启停

状态转换为ACTIVE→DISABLED与DISABLED→ACTIVE，不增加“空闲”“占用”“已付款”等桌区状态。

停用必须同时满足：本主体本门店本桌区下没有ACTIVE桌台，且没有活动占用。活动占用依据关联桌台的 `fnb_table_occupancy.ended_at IS NULL` 判断，不能只看桌台的资源状态投影或是否已付款。有异常活动占用时，即使桌台已停用，也必须拒绝停用桌区。

不级联停用桌台，不自动清台、退款或关闭台账。失败时引导先处理桌台及占用；启用只改变桌区自身状态。

本轮规则：新请求若目标状态已经满足，仍先校验version；版本正确时作为无变更成功返回，不递增版本、不重复写“状态变化”审计或事件。幂等受理结果仍沿现有机制保存；旧版本仍返回冲突。

未来桌台创建、移区和重新启用必须验证目标桌区ACTIVE，并与停用桌区共用同一仲裁行，在事务内避免“刚检查为空就被新增桌台”的竞态。本轮停用检查需覆盖真实关联表，不能因桌台写接口尚未开发而直接放行；后续桌台切片不得绕过此契约。

### 5.5 权限与原子性

B端沿原认证、门店权限与目录核验。编辑和启停路径仅有areaNo，也必须校验当前门店与实际对象归属；知道编号不构成访问许可。不得通过body伪造操作人或主体。越权及不存在对象沿平台既有错误映射，不向其他主体泄露对象内容。

成功变更与原幂等结果、动作审计和必要Outbox记录同一主事务提交，失败全部回滚。创建记录编码、名称及顺序；编辑记录前后值；启停记录前后状态和reason。原审计列保留前后指纹，已有Outbox事件保存before/after业务快照，以operationNo关联；reason同时保存于原审计列。列表读取不产生业务变更事件。本轮不承诺事件下游已经完成消费。

## 6 API与数据设计对齐

保持原路径、请求字段和响应包装，不增加一组新命名接口：

| API | 方法与路径 | 输入 | 成功data |
|---|---|---|---|
| 092 | GET /biz/x/food/stores/{storeNo}/table-areas | 路径storeNo；query page、size、status | records、total、page、size |
| 093 | POST /biz/x/food/stores/{storeNo}/table-areas | 路径storeNo；body code、name、sortNo；幂等头 | area |
| 094 | PUT /biz/x/food/table-areas/{areaNo} | 路径areaNo；body name、sortNo、version；幂等头 | area |
| 095 | POST /biz/x/food/table-areas/{areaNo}:set-status | 路径areaNo；body status、version、reason；幂等头 | area |

建议TableArea输出仅包含业务所需的areaNo、storeNo、code、name、sortNo、status、version；正式VO在字段设计阶段与既有代码清单对齐，不直接序列化Entity。092描述中的“写操作CAS/幂等”仅约束写请求，读取不要求version或幂等头。

主写表仅使用既有 `fnb_table_area`。停用安全检查读取本餐饮域 `fnb_table`、`fnb_table_occupancy`；审计、幂等、Outbox沿已接入的既有能力，不增加业务表，不修改冻结V1。账号、主体、商户、门店继续由其现有权威域维护。

沿BizTableAreaController→TableService→TableServiceImpl→FoodMappers.TableAreaMapper现有规划，复用已有FnbTableArea。独立部署时food-web通过typed内部合同调用food-server；内部接口不复制用户认证，必须携带可信主体、门店和操作人，并由核心服务校验对象范围。不在此阶段新增C端或平台端桌区管理Controller。

本轮不调用支付或进销存。后续订单和交易仍按既定独立支付、库存合同接入，不能因桌区验收通过而宣称交易就绪。

## 8 验收场景

| 编号 | 操作与条件 | 必须结果 |
|---|---|---|
| AC01 | 授权门店查询，无桌区 | 空records、total=0，保留正确page/size |
| AC02 | 两主体、同主体两门店分别建数据后分页查询 | records及total仅来自当前授权主体门店，排序稳定 |
| AC03 | 创建大厅，重复同键同参提交 | 同areaNo、同回执，只有一条桌区及一次实际创建审计 |
| AC04 | 同店同编码以不同键并发创建 | 仅一条成功，不重复；冲突转换为平台业务错误 |
| AC05 | 不同门店使用相同编码；同店使用相同名称 | 按既有唯一键及本次建议允许，互不覆盖 |
| AC06 | 修改名称和排序 | areaNo、code、storeNo不变；返回新version |
| AC07 | 两人持同version分别修改，或一人编辑一人启停 | 仅首个实际变更成功；旧version不能覆盖，失败零业务写入 |
| AC08 | 改其他门店areaNo、伪造主体/操作人、绕过门店头 | 原安全链拒绝，目标对象不变，响应不泄露其他门店内容 |
| AC09 | 有ACTIVE桌台、或只有异常活动占用时停用 | 两种情况分别拒绝；原桌区状态不变 |
| AC10 | 所有桌台停用且所有占用已结束后停用，再启用 | 仅桌区状态变化；桌台与历史关系不变，reason可追溯 |
| AC11 | 同键异参/异对象/异actor；缺key、空名称、非法状态等 | 对应冲突或参数拒绝，不新增业务数据 |
| AC12 | 同目标状态的新请求 | 按评审后约定验证version；无变更不制造重复状态变化 |
| AC13 | 写审计/幂等/事件阶段注入异常 | 桌区、审计、幂等、Outbox全回滚，不留半成功 |
| AC14 | 相同场景分别经集成入口及独立HTTP传输执行 | 参数、范围、状态、版本、回执和业务错误一致，不静默重试写入 |
| AC15 | 菜品订单为空、支付库存未接通，但非交易配置前置满足 | 可维护桌区；不创建订单，不访问支付库存 |

验证要使用真实数据库和实际Controller/内部HTTP合同覆盖关键行为，不能只靠路由存在性或Mock返回空数据证明交付。场景对应测试方法、实际执行数和数据库验证结果见M0方案NEXT-09实施收据。
