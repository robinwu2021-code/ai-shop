# 代客下单（P-4.1.4）需求梳理

> 2026-09-03。写这份是因为「代客下单」是 ops-web 最后 6 个 mock 端点里唯一一条
> **不在二期、也没有外部阻塞**的 —— 它卡的是几个没人拍过的产品决定。
> 每条决定都标了**现状证据**（文件:行）与**不定就动手会造成什么**。

## 〇、原始需求只有一句话

- 《平台端功能清单》P-4.1：**「老人打电话来下单的场景。必须留痕（P-1 审计）」**
- 《需求矩阵-三端》M6：**「客服代客操作的权限边界与金额阈值」** —— 待定，业务 + 风控

其余全部是实现方在 mock 里顺手写下的假设，**没有经过产品确认**。

## 一、现状：已经有的别重复建

| 有 | 在哪 |
|---|---|
| 代客**取消** | `OpsOrderController.java:128` `POST /ops/orders/{no}/proxy-cancel`，判 `order:order:proxy`，走 `intervene` + 审计 |
| 运营端整页 + mock | `ops-web/app/orders/proxy-tab.tsx`、`lib/api/mocks/order.ts:95` |
| 下单主干 | `OrderService.create(cmd, idempotencyKey)`；实现里已经是 **`doCreate(cmd, userNo)`**（`OrderServiceImpl.java:498`）—— userNo 是参数不是全局，代客要接的就是这个缝 |
| 线下支付整条链路 | `payMode=OFFLINE` → 落 `WAIT_OFFLINE_PAY`（`OrderServiceImpl.java:643`）→ 商家 `/biz/orders/{subNo}/confirm-offline-pay` → PAID |
| 找人 | `/ops/members`、`/ops/persons/{no}`；`OpsPersonVO` 带 **`userNo`**（`MemberVOs.java:131`，空 = 只是被商家录进来的号） |
| 权限码 | `order:order:proxy` 已存在，挂在 **SUPPORT（客服）** 角色上（`Perms.java:549`） |

**缺的只有一条**：`POST /ops/orders/proxy`。

## 二、六个要拍的决定

### 决定 1 · 这单挂在谁名下（最关键，其余都从它派生）

mock 现在收的是 **`buyerNickname`** —— 一个自由文本。照它建后端，会造出**一张没有主人的订单**：

- 用户在 C 端看不到它（`/mp/order` 按 `sub.user_no = 当前登录人` 查，`OrderServiceImpl.java:1174`）
- 他也**付不了款**
- 售后、退款、积分、优惠、归因全都没有落点

| 选项 | 含义 | 代价 |
|---|---|---|
| **A（建议）** | 客服按手机号在人档里找到人 → 取 `userNo` → 落单；人档里没绑账号的**下不了单**，明确提示 | 覆盖不到「从没装过 App 的老人」 |
| B | 为电话用户建**占位账号**（人档已有手机号，缺的是 user） | 要定：占位账号怎么被本人认领、认领前订单谁能看 |
| C | 挂在客服自己名下 | ❌ 会污染客服的订单/积分/归因，且用户永远看不到这单 |

**要产品拍的是**：要不要支持**从没装过 App 的人**电话下单。要 → A 之后补 B；不要 → A 就够。

### 决定 2 · 谁付款、走哪条支付

| 方式 | 落什么状态 | 适不适合「电话下单」 |
|---|---|---|
| ONLINE | `WAIT_PAY`，用户自己在 App 里付（mock 的假设） | ⚠️ 关单时限在下单那一刻就盖在 `pay_deadline_at` 上（`OrderServiceImpl.java:66` 起）。老人挂了电话再打开 App，**多半已经关单了** |
| **OFFLINE（建议默认）** | `WAIT_OFFLINE_PAY`，到店/送货**当面付**，商家确认收款 | ✅ 这才是这个场景的原生形态 —— 平台不碰这笔钱，也就不存在「代客付款」 |

线下支付的现成约束（不用重新定，照用）：

- 只有 `STORE_PICKUP / MERCHANT_DELIVERY / STORE_VERIFY / APPOINTMENT` 能线下付（`OrderServiceImpl.java:1679`）
- 货到付款还要门店开 `cod_enabled`
- 商品/门店要显式开线下收款（新建商品默认只给线上）
- **平台券不能用于线下单**（平台没有资金流可补，`ErrorCode.PLATFORM_COUPON_OFFLINE_FORBIDDEN`）

**要拍的数**：如果也允许 ONLINE，代客单的支付时限给多长（现在的通用值对电话场景太短）。

### 决定 3 · 归因算谁的（**有钱的后果**）

下单这一刻固化：`sub.setTrafficSource(attributionPort.resolveTrafficSource(userNo, merchantNo))`
（`OrderServiceImpl.java:756`），而 **trafficSource 决定佣金档**（`OrdSubOrder.java:230`）。

mock 硬写 `PLATFORM`。如果这个人本来是商家自己带来的（`MERCHANT_OWNED`），
一通电话就让商家**为自己的客人付了平台档佣金** —— 而没有任何人会发现。

**建议**：照常按 `userNo` 解析，**不因为「客服代下」而改档**。代客只是录入通道，不是流量来源。
（若产品要把它算平台流量，那是一个明确的商业决定，要写下来并让商家知道。）

### 决定 4 · 库存怎么扣

现成规则照用：`create` 锁库存 → 支付成功实扣 → 超时关单释放。

⚠️ 但**关单任务只扫 `WAIT_PAY`**（`OrderServiceImpl.java:1251`），
`WAIT_OFFLINE_PAY` 不在里面 —— 线下单的库存会**一直锁着**。
这是现存行为（C 端线下单也一样），代客下单只是会放大它。

**要拍的数**：线下单多久不付款算作废（建议接在同一张关单策略表上，给一个明显更长的时限）。

### 决定 5 · 用户的钱包资产能不能替他用

券 / 积分 / 会员权益都是**用户的资产**。

**建议第一版一律不代用**（不传 `couponNo`、`usePoints=0`）：客服替人花掉券和积分，
事后说不清，而它也不影响「把货订上」这个目的。

⚠️ **一个会静默出错的地方**：算优惠那段取的是**安全上下文里的人**
（`couponPort.allocate(SecurityUtils.currentUserNo(), ...)`，`OrderServiceImpl.java:446`，
被 `doCreate` 调用）。代客路径若原样复用，会去**扣客服自己的券**。
积分那条已经是参数化的（`pointsPort.deduct(userNo, ...)`，:601），只有券这一处没有。

### 决定 6 · 履约方式与地址

- **自提 / 到店**：只要 `pickupNo` / 门店，客服填得出来 —— 第一版够用
- **快递 / 商家配送**：要 `addressId`，且 `userPort.receiverOf(userNo, addressId)` 会校验归属
  （`OrderServiceImpl.java:1687`）—— **客服不能替用户新建地址**（个人信息，也没法当面核对）

**建议**：只允许选用户**已有的**收货地址；一个都没有就只能自提。

## 三、权限、阈值与留痕（M6）

- 权限码有了（`order:order:proxy`，在 SUPPORT 角色上）
- **待定**：单笔金额上限？每日笔数上限？超阈值要不要二次审批？
- 留痕：审计日志之外，**订单本身要看得出「这单是代下的、谁下的、为什么」** ——
  否则事后只有审计能查，而客服和商家打开订单时看不出任何异常。
  建议在订单上留 `proxy_by` / `proxy_reason`，或复用已有的干预留痕表（代客取消就写在那里）。

## 四、第一版（已落地 · 2026-09-03）

> 下面这份原本是「建议」，现在是**已实现**的范围：后端 `POST /ops/orders/proxy`
> （`PlatformOrderService#createProxyOrder`）+ 运营端表单 + 6 条场景测试（逐条做过消融）。
> 与建议的唯一出入：**支付方式两种都做了**（默认线下付）——
> 线下付要商家先开（四层判定），没开的商家只能走线上，硬只做一种会让功能对多数商家不可用。

1. 客服按手机号在人档里找到人 → 取 `userNo`；**没绑账号的明确挡住**并提示怎么办
2. 选商家 → 选商品与数量 → 选自提点/门店 → 履约方式（默认自提）
3. `payMode` **默认 OFFLINE** → 落 `WAIT_OFFLINE_PAY`；商家当面收款后自己确认
4. **不代用券、不代扣积分**
5. `reason` 必填 → 落审计 + 订单上可见
6. 后端复用 `doCreate(cmd, userNo)`；**价格一律服务端算**，端上传的只有 skuNo/qty

## 五、明确不做，以及为什么

| 不做 | 为什么 |
|---|---|
| 代付款（任何形态） | 平台不碰用户的钱；这也是选 OFFLINE 作默认的原因 |
| 跨商家一单 | 全站按商家拆单（E3），跨商家应当下多单（mock 已经这样） |
| 代建收货地址 | 个人信息，且没法当面核对 |
| 代用平台券 | 线下单本来就禁；线上单也不该由客服替人花 |

## 六、待拍的四个数（其余都能照现成规则走）

1. **从没装过 App 的人能不能电话下单**（决定 1 的 B 分支）
2. 线上代客单的**支付时限**
3. 线下代客单**多久不付作废**（库存锁多久）
4. 代客单的**金额 / 笔数阈值**，以及超阈值要不要二次审批（M6）

前三个不定，第一版就按「A + OFFLINE + 不代用资产」做，**都是可回退的保守选择**；
第四个不定不影响开工 —— 权限码已经在客服角色上，阈值是后加的一层。

### 落地后仍然待拍的（2026-09-03 复核）

1. **没装过 App 的人**：现在明确挡住，运营端提示「先让他用这个手机号登录一次」。
   要支持的话就是决定 1 的 B 分支（占位账号 + 认领）。
2. **线上代客单的支付时限**：用的是平台通用关单时限，没有为电话场景特殊化。
   表单里写明了「顾客要在关单时限内自己付掉」，但那个数对老人可能仍然太短。
3. **线下单多久不付作废**：仍然没有 —— 关单任务只扫 `WAIT_PAY`，
   `WAIT_OFFLINE_PAY` 的库存会一直锁着。这是现存行为，代客下单会放大它。
4. **金额 / 笔数阈值**（M6）：没做。今天客服能代下任意金额的单，只有留痕没有闸门。
