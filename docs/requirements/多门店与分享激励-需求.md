## 一、三条需求

| # | 需求 | 一句话 |
|---|---|---|
| **R1** | 多门店：**一个商家端统一管理多家店**，一个手机看全部；含跨店统计与对比 | 卖的是**统一管理与数据**，不是"多开几家店的权限" |
| **R2** | 子账号：多人共同管理，权限分工 | 与 R1 同属**增值服务包** |
| **R2b** | 一个账号支持**多商家**（App）；小程序仍单商家多门店 | 账号是管理入口，不是经营主体 |
| **R2c** | 跨店的积分与权益（券） | 权益边界是**主体**，同主体多门店通用 |
| **R3** | 分享激励：商家分享门店/商品 → 用户点击 → 该门店/商品一段时间内进消费者首页 | 商家的分享给**平台**带来曝光，平台用**曝光位**回馈 |

R1+R2 是一个付费包（经营效率），R3 是免费的增长机制（双向获益）。

### 这套东西在商业模式里的位置

[ADR-004](../technical/ADR/ADR-004-增长模型从孵化团长转向商家自带客流.md) 定了
「对自带客流的小商家零佣金」，但**没有回答不抽佣平台靠什么活**。
增值服务就是那个答案，而且与零佣金是同一套逻辑的两段：

| 阶段 | 商家状态 | 平台做什么 | 收什么 |
|---|---|---|---|
| **孵化期** | 一店一人几十客 | 免费给全套开店能力 | **不收**——收了他就走 |
| **成长期** | 要请人、想开第二家 | 给他自己搭不出来的经营工具 | 订阅费 |
| **成熟期** | 多店多人、要数据做决策 | 数据与效率 | 订阅费（更高档） |

**收费时点是关键**：最脆弱的时候不收钱，等他**因为做大而产生新问题**时才卖解决方案。
这时他付费的理由不是"平台要收钱"，是"我确实需要"。

**一条硬约束**：现在免费的一切（单店经营、商品、订单、履约、结算、单店数据）
**永远留在免费档**；零佣金对所有档位一视同仁。
把免费功能挪进付费档，是最快毁掉"免费孵化"这层关系的做法。

### 关键：R1 卖的到底是什么

**不是「允许你开第二家店」** —— 那个他开两个主体就能有，只是麻烦。
**是「一个手机管完，并且能横着比」**：

- 三家店的订单在同一个列表里，不用退出登录再进去
- 今天哪家卖得好、哪家库存要补、哪家评分掉了 —— 一屏看完
- 跨店对比本身就是数据服务：两个主体**永远做不到这件事**，因为数据在两个账号里

这条定住之后，「用两个主体替代」就不再是等价方案了 ——
它替代的是"能开店"，替代不了"能一起管、能比"。

## 二、R1 多门店

### 2.1 为什么这次要做

[ADR-011 §6.2](../technical/ADR/ADR-011-经营主体与门店边界.md) 记录了决策反转。
8-07 否掉它的理由是「让店主开两个主体，代价只是切换账号」。

**那个理由现在站不住，不是因为收费，是因为需求本身不同了**：
要的是**一个手机管完 + 横着比**，而两个主体的数据在两个账号里，
跨店对比**做不到**——不是麻烦，是不可能。

所以这次要做的不是"多开几家店的权限"，是**统一管理与跨店数据**。

### 2.2 功能点

| ID | 功能 | 说明 |
|---|---|---|
| B-11.12.1 | 门店切换 | B 端顶部切当前门店；商品/订单/履约/数据全部跟着切 |
| B-11.12.2 | 新建门店 | 第一个免费；超出免费额度要有增值包 |
| B-11.12.3 | 门店资料 | 地址、营业时间、公告、主推、经营范围与覆盖社区 —— 现有 `usr_merchant_store` 的内容按门店拆 |
| B-11.12.4 | 门店启停 | 停用的门店 C 端不可见，历史订单可查 |
| **B-11.12.5** | **全部门店总览** | 不选具体门店时的默认视图：今日订单/销售额/待办**按店并列** |
| **B-11.12.6** | **跨店对比** | 选定指标（销售额/订单数/复购率/评分/缺货）横向比，**这是付费的核心理由** |
| P-11.2.1 | 门店列表与统计 | 平台端按主体看下属门店 |
| P-11.2.2 | 门店额度调整 | 谈下来的连锁客户不走自助付费 |

**B-11.12.5/6 不是附加功能，是这个包卖的东西本身。** 只做"能开第二家店"
而不做总览与对比，商家花了钱得到的仍然是"要切来切去"，那他会觉得被骗了。

### 2.2.1 R2 子账号（同属增值包）

| ID | 功能 | 说明 |
|---|---|---|
| B-11.10.1 | 子账号管理 | 邀请/停用，绑定手机号 |
| B-11.10.2 | 角色与门店授权 | **两个维度**：能做什么（角色）× 管哪几家店（门店范围） |
| B-11.10.3 | 操作日志 | 谁在哪家店做了什么 |

**门店范围是子账号的关键**，不是角色的附属：连锁店的店长只该看自己那家。
只做角色不做门店范围，等于把三家店的数据都给了每个店员 ——
而 B-11.11 的客户数据是脱敏但仍敏感的。

> ⚠️ 后端已有 `BizContext.merchantNo` 作为 B 端作用域。子账号 + 多门店会让它
> 变成 `(merchantNo, storeNos)` 两级 —— **这是越权防线的第一道**（TDD-backend §5.1），
> 改它要格外小心，且必须有测试锁住「店员看不到别家店」。

### 2.3 Plan 档位与收费（详见[方案 §4.4](../technical/design/增值服务-多门店与子账号-方案.md)）

| | FREE（孵化） | PRO（成长） | CHAIN（连锁） |
|---|---|---|---|
| 门店 / 子账号 | 1 / 0 | 3 / 3 | 10 / 15 |
| 跨店总览与对比 | — | ✅ | ✅ |
| 单店经营全套 · 零佣金 | ✅ | ✅ | ✅ |

试用 14 天（一主体一次）· 到期进 GRACE 7 天（能力全保留）· 之后降级不关店。

#### 原收费模型讨论（保留记录）

> **我上一轮建议「一次性开通费」，现在改为订阅制。** 改的理由是需求变了：
> 当时以为卖的是"开店权限"（一次性的东西），现在明确卖的是
> **统一管理 + 跨店数据 + 子账号**（持续提供的服务）。
> 一次性收费买断一个持续成本的服务，是平台亏。

| 方案 | 怎么收 | 欠费时 |
|---|---|---|
| **A 增值包订阅** ← 建议 | 按月/年，一个包含多门店额度 + 子账号 | **降级到免费档**，不是关店 |
| B 一次性开通费 | 开一个门店付一次 | 不存在 |
| C 按门店数阶梯订阅 | 每多一店多收 | 同 A |

**上一轮否掉订阅制的理由是「欠费时三家店关哪一家没有好答案」——
这个反对意见在增值包的框架下不成立**：欠费不是关店，是**降级**。

| 降级后 | 商家还能做什么 |
|---|---|
| 超出免费额度的门店 | **只读**：历史订单可查、可核销未完成的单，但不能上架、不接新单 |
| 子账号 | 停用，主账号仍可登录 |
| 跨店总览与对比 | 隐藏 |

只读而不是关闭，是因为**关店伤的是消费者**（下了单提不了货），
而欠费是商家和平台之间的事，不该让买家承担。
降级可逆：补缴后原样恢复，不需要重新配置。

**一期先做 A 的最小形态**：只做「有没有增值包」这个开关 + 降级规则，
不做自动续费与账单——那是支付侧的事，可以在验证有人买之后再接。

### 2.4 四个跨域问题的结论

[ADR-011 §2](../technical/ADR/ADR-011-经营主体与门店边界.md) 列的四个问题，
按 §3 的模型给出结论：

| 问题 | 结论 | 理由 |
|---|---|---|
| 进件按主体还是门店 | **主体** | 收付通的二级商户号按营业执照发，这是硬约束 |
| 订单归属 | **双写**：`merchant_no`（结算键）+ `store_no`（履约键） | 结算/分账/积分链路一行不改，多门店可分阶段上线 |
| 积分开关 | **主体** | 积分是主体的成本结构（ADR-006 费率补偿按主体谈） |
| 自提点与门店 | 自提点**挂门店**（`owner_ref` 从 merchant_no 改 store_no） | 承接取货的是具体那家店，不是集团 |

补充两条 8-07 已定的：**库存按门店独立**（邻里店之间不互相调货）、
**评价归门店**（顾客评的是「楼下那家」，三家混一个评分会让好店被差店拖下去）。

## 三、R3 分享激励：商家给平台带曝光，平台还他曝光位

### 3.1 机制

```
商家在 B 端分享门店主页 / 某个商品
        ↓  带 storeNo + goodsNo? + 分享码
用户点击链接进入
        ↓  记录一次「有效点击」（防刷规则见 3.3）
该门店 / 商品进入**首页曝光池**，持续 N 天
        ↓
在消费者首页的「邻里在逛」位展示
```

### 3.1.1 目的决定了奖励挂在什么指标上

需求原话是「鼓励商家分享、经营门店，**促进系统曝光**」——
受益方是**平台**（新用户进来了），不只是那家店。这句话直接决定了两件事：

**① 奖励应该挂「带来的新用户」，不是「点击数」。**
点击数可以由老客贡献，而老客本来就在平台上，分享他不产生系统曝光。
按点击给奖励 = 给一件没发生的事付钱。

| 计什么 | 平台得到了什么 |
|---|---|
| 老客点击 | 什么也没有 —— 他本来就在 |
| **未归因用户点击** | 一次真实的外部曝光 ✅ |
| 新注册 | 一个新用户 ✅✅ |

建议：**有效曝光 = 未归因到本店的用户点击**，新注册**加权**计。
不要只认注册——那会把门槛抬到商家够不着，机制就没人玩了。

**② 这解释了平台为什么愿意给出首页位。** 这不是补贴，是交换：
商家把自己的社交关系换成平台的新用户，平台把边际成本近乎为零的曝光位还给他。
双方都拿到了自己没有的东西——所以这个机制**不需要花钱也能成立**（ADR-004 的核心主张）。

### 3.2 与 ADR-004 的冲突（**必须先解决**）

ADR-004 §6 用**费率**区分客流来源：

| `trafficSource` | 含义 | 费率 |
|---|---|---|
| `MERCHANT_OWNED` | 商家自带（店铺码/分享进入） | 低费率或零佣金 |
| `PLATFORM` | 平台分配（首页/搜索/推荐） | 正常费率 |

新机制会产生一种**两边都沾**的客流：商家分享挣来的首页曝光位，
用户从**首页**点进去下单。按现有规则它是 `PLATFORM`，走正常费率——

**于是商家越分享，费率越高。激励是反的。**

**我的建议**：曝光奖励期内、从该曝光位进店的订单，仍计 `MERCHANT_OWNED`。
理由：这个位置是他自己分享挣来的，不是平台分配的。
需要新增一个来源值 `MERCHANT_EARNED`（自带客流换来的平台位）以便区分统计，
但**费率按 `MERCHANT_OWNED` 走**。

### 3.2.1 功能点

| ID | 功能 | 端 |
|---|---|---|
| B-11.13.1 | 分享门店/商品（链接带 `storeNo`） | B |
| B-11.13.2 | **我的曝光状态**：还剩几天、带来多少点击 | B |
| C-9.4.1 | 首页「邻里在逛」位展示曝光池里的商品 | C |
| P-9.3.1 | 曝光池查看与人工干预 | 平台 |
| P-9.3.2 | 曝光位数量与时长配置 | 平台 |
| P-9.3.3 | 刷量拦截规则 | 平台（风控域） |

**B-11.13.2 不是锦上添花**：看不到效果的激励等于没有激励 ——
商家分享完不知道有没有用，第二次就不分享了。

### 3.3 防刷（**这条不做，机制就是白送**）

商家自己点自己的分享链接是零成本的。规则：

| 规则 | 为什么 |
|---|---|
| 只计**未归因到本店**的用户 | 老客点一下不产生系统曝光 —— 他本来就在平台上（见 3.1.1） |
| 同一用户 × 同一门店，**窗口内只计一次** | 否则一个人反复点就能刷满 |
| 排除商家自己及其店员账号 | 最直接的刷法 |
| 新注册用户在 **X 分钟内**的点击不计 | 挡批量注册小号 |
| 单店**每日有效点击上限** | 就算前面都绕过了，收益也有天花板 |

> 平台端已有风控域（L2-16）与归因防刷，这些规则应落在那里，不要在营销域另起一套。

### 3.4 曝光位是有限资源（**待拍板，见 §五 Q3**）

首页位置有限，而分享的商家可能很多。分配规则必须明确，否则
「我分享了却没看到自己」比没有这个机制更伤商家关系。

| 方案 | 说明 | 问题 |
|---|---|---|
| **A 按有效点击数排序** | 分享带来的人越多越靠前 | 强者恒强，新店永远进不去 |
| **B 轮播 + 权重** | 池子里轮流展示，点击数决定出现频率 | 商家看不到"我在第几位"，但**每个人都能看到自己出现过** |
| **C 时间衰减队列** | 最近有点击的排前面 | 简单，但一次爆发能占很久 |

**我的建议：B**。这个机制的目的是**鼓励分享**，不是把流量给最强的那家。
A 会让机制在两周后只剩头部几家在玩，那时它就不再是激励了。

## 四、不在本需求内

| 不做 | 为什么 |
|---|---|
| 跨主体的门店转移 | 转移意味着历史订单结算方变了，是财务事故不是功能 |
| 门店级独立进件 / 独立费率 | 通道按主体发号；费率是主体谈的 |
| 分享给现金奖励 | ADR-004 的核心是不用钱买增长。曝光是平台的边际成本近乎为零的资源，现金不是 |
| 分享排行榜 / 公开竞赛 | 会把「分享给邻居」变成「刷量竞赛」，与邻里场景相悖 |
