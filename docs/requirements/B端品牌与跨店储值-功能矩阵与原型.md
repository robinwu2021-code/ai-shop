# B端品牌与跨店储值：双线入口、功能矩阵与UI原型

状态：待评审的V2产品原型，非已实现能力。2026-10-21。
原型：[品牌与门店双线储值](../../prototypes/brand-stored-value-b.html)。本轮仅原型及文档，无生产业务代码改动，不部署、不连接真实充值、核销或结算接口。

## 1. 本轮确认的模型（替代V1自动按品牌决定全部储值范围）

- 经营管理空间由账户所有人／授权管理员管理，品牌、经营主体、支付商户、门店入口平级；品牌是运营维度，经营主体是结算维度，不建立两者的直接归属关系。
- 门店分别关联品牌与经营主体。有品牌共享品牌会员关系，无品牌按单店；平台顾客身份稳定唯一，私有备注与服务档案不自动共享。
- **顶层品牌储值与店内门店储值独立。**品牌门店仍能发行仅本店可用活动；不是“有品牌就只能品牌储值”。
- 一个品牌一个品牌发行方；一家门店最多一个单店发行方，并可接受所属品牌发行方余额。取代旧的“门店只有一个总发行方”说法。两账户不合并、不暗中组合扣减。
- 单店入口自动当前店、不再选品牌；顶层先选择品牌再发行。当前门店切换不会修改顶层品牌配置、财务报表选择或品牌账户。
- 顾客账户仍按tenant/issuer/customer/currency唯一；不同活动和档位进入对应发行方账户，来源批次独立记录，报表按实际批次分配归属。
- 品牌发行方指定结算主体；本店发行方默认本店经营主体，不任意选择无授权主体。品牌样例指定主体统一收款；单店样例本店主体收款。同主体单店消费为内部对账，不编造跨主体付款。
- “储值活动”为业务入口和生命周期；发行方、方案版本、账户与账务归Pay，Core统一活动入口引用发行配置，金额不双写。不要求再创建一个通用营销活动。接口及迁移另行设计。

## 2. 入口与角色矩阵

| 功能 | 账户所有人／授权经营管理员 | 品牌管理员 | 门店负责人／店员 | 原型 |
|---|---|---|---|---|
| 基础管理 | 品牌、经营主体、支付商户、门店平级 | 授权品牌资料和成员 | 当前门店设置，按授权 | s01–s08 |
| 品牌储值创建 | 选品牌后创建 | 明确发行权限后可创建 | 只执行已发布品牌活动 | s11–s15 |
| 门店储值创建 | 按授权管理／审批，不混为品牌活动 | 可配置其门店管控（需授权） | 本店独立创建，受上限与审批约束 | s09、s10、s23、s30、s33 |
| 上层限制 | 全局底线及单店覆盖 | 品牌下门店覆盖 | 只读生效限制，不能放宽 | s25、s26 |
| 审批 | 仅授权门店审批 | 需独立审批授权 | 提交、查看待审批／退回 | s27–s29 |
| 会员及办理 | 按明确数据范围 | 品牌会员关系共享 | 一个搜索入口、详情储值、双余额 | s16、s17 |
| 核销选账 | 不因管理角色获得扣款权 | 同左 | 有核销权限且订单授权，一次选一个账户 | s32 |
| 资金汇总 | 品牌与各单店发行方分开 | 品牌范围 | 本店独立储值及获授权的本店执行数据 | s19、s20、s31、s34 |
| 清分结算 | 需要相应主体财务授权 | 不因品牌权限自动获得 | 本店对账；他店账单不可见 | s21、s22 |
| 空态／异常 | 无品牌、无授权等按入口退化 | 角色与范围明确 | 无方案、待审批、禁止发行、余额不足等就地提示 | s08、s24、弹层 |

| s23 | 新建门店活动 | 自动当前店、本店主体，展示生效规则及输入校验 |
| s24 | 权限边界 | 明确账户、品牌、门店与财务角色分别授权 |

| s33 | 确认门店活动 | 金额、范围、管控检查和提交审批／直接发布 |

## 4. 两条创建流程

品牌：经营管理→品牌储值→选择品牌→新建活动→充赠档位及有效期→核对品牌发行方与结算主体→发布。品牌范围独立于门店切换。

门店：切换当前门店→门店储值→新建本店活动→检查上层限制→符合规则直接发布或提交审批→上层复核→进行中。关联品牌不会把本店活动转换为品牌活动。

会员办理：统一搜索→顾客详情→储值→底部“门店储值／品牌储值”明确选择→选择档位→原账户到账。只修改选定账户，另一账户不变；待审批活动不能办理。刷新重置演示数据。

核销：服务订单／收银→识别会员→选择本店或品牌账户→订单绑定消费者授权→既有预占和扣减内核。s32只演示选账，不请求消费者授权接口或扣款。

## 5. 顶层限制与执行时机

示例全局硬边界：赠送≤30%、单笔实收≤1000元、赠送金额≤300元、最长365天、未消费余额≤200000元；悦颜门店覆盖赠送≤20%、赠送金额≤200元、发布需审批。品牌门店覆盖只作用于门店独立发行，不误限制总部品牌活动。

生效顺序：平台硬约束→账户经营管控→品牌下门店覆盖→指定门店覆盖→活动自身配置。上限取更严格值，禁止优先；单店不能放宽。现原型交互编辑一个品牌门店覆盖，其他作用范围在列表给出入口，完整多范围编辑留实现设计。

- 输入阶段显示生效上限及来源。
- 发布阶段校验金额、赠送比例、期限、权限及最新规则版本。
- 审批阶段重新校验最新规则；硬超限必须改活动或由有权上层改规则，不能仅点通过。
- 办理阶段复核是否允许新发行、单笔及赠送限制、剩余额度；实际后端需在事务内原子校验并发额度。原型用内存累加演示，非并发账务实现。
- 管控收紧不重写历史本金／赠金、不撤销既有核销权利；禁止新发行不等于禁止消费。
- 部分付款、历史余额承接、自动打款、跨租户协作不在本轮交互实现。

## 6. 报表与结算口径

品牌固定样例：期初0，实收10000、赠送3000、到账13000、核销2600、批次剩余10400。办理归因A6000/B4000，核销A1040/B1560。统一收款，按来源批次实收比例清分，示例应付A800/B1200，赠送部分600由发行方承担，不当作现金应付款重复计入。规则仅为评审样例，非强制默认。

单店固定样例：A实收600、赠送120、到账720、核销240、剩余480；B实收100、赠送20、到账120、核销100、剩余20。顶层各单店经营合计实收700、赠送140、核销340、剩余500；两个钱包依然不能互用。这些固定经营快照不随单笔办理演示重算，实时顾客余额与新增收支则会变化。

结算按发行方+期间+对手主体+币种生成，活动仅为来源分析维度，避免重复计数。品牌账单：待核对→待付款→待收款确认→已结算，付款与收款岗位分开。单店同主体只做内部收支对账，不把自己的核销虚构成应付自己的跨主体账单。切换财务查看门店不切换门店工作台上下文。

活动统计依据实际批次分配，不能把顾客共享余额复制到每个活动。历史单据保留品牌、门店、实际经营／收款主体、发行方及清分规则快照。

## 7. 统一UI及核验范围

沿用现行规范-版面、规范-组件、规范-字体及proto.css，375pt×0.8预览：白底卡片分隔、胶囊按钮、sh-sheet底部选择、sh-actionbar底部主操作。品牌、主体、档位及核销账户不使用select；收支筛选仅三类Tab与时间弹层。

## 8. V2浏览器定向核验结果

- 双账户隔离：A店本店余额60，选择本店100送20后变为180；品牌余额保持130。外层切换B店后，本店余额20，品牌仍130；本店活动与收支同步切换。
- 管控：门店100送30超过20%时进入s27，无直接发布／绕过审批动作；调整为20后进入s33并提交，状态为待审批；此时本店储值弹框不提供可办理方案。
- 审批：上层通过后状态为进行中，适用范围仍为本店，没有转为品牌活动。审批提交与通过均按最新内存规则再检查。
- 分类结算：切到门店储值，仅显示单店发行方与同主体内部对账，不包含品牌跨店应付款；财务查看门店为独立选择，不改变门店工作台。
- 页面与基础验证：JS语法通过，34屏锚点唯一、内部链接均可达、无移动端select及内联style、无真实业务API调用；原型登记和284项UI目录一致性通过。品牌及单店样例金额分别勾稽，无全量回归。
