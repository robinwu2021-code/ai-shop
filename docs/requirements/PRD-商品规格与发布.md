# PRD · 商品、规格与参数：维护要自由，发布要严谨

## 0. 一句话

商家和运营要能**随时随地改规格、改参数、改商品**而不用提心吊胆；
买家看到的每一件在售商品必须**完整、一致、可比**。
这两个诉求天然相反 —— 本需求的全部内容，是把它们拆到**两个时刻**去各自满足：
**编辑时刻自由，发布时刻严谨。**

---

## 1. 三个概念（业务口径，全文只用这一套词）

| 词 | 是什么 | 分不分 SKU | 例子 |
|---|---|---|---|
| **商品** | 一件在卖的东西 | — | 烟台红富士 |
| **规格** | **决定价格与库存**的选项轴 | 分 | 重量：5 斤 / 10 斤（各有各的价和库存） |
| **参数** | **只写给买家看**的属性 | 不分 | 产地：烟台；保质期：7 天 |

判断一个属性是规格还是参数，只问一句：**不同取值要不要单独定价备库存。**
要 → 规格；不要 → 参数。把参数误做成规格，商家就得给「不锈钢」单独备库存。

规格与参数的**取值都有平台身份**（值编号 + 归一量：500g/半斤/0.5kg 都归一成 500）——
这是「跨店比价」「按规格筛选」将来能成立的唯一前提。

## 2. 谁维护什么（四层，每层只管自己的事）

| 层 | 谁 | 管什么 | 例子 |
|---|---|---|---|
| 平台值池 | 运营 | 这根轴上一共有哪些档 | 重量轴：250g~50kg 全谱 |
| 类目裁剪 | 运营 | 这一类用哪几根轴、每根用哪几档 | 蔬菜只留 500g~10 斤 |
| 商家覆盖 | 商家 | 本店用哪几个、什么顺序、叫什么 | 「重量」本店叫「份量」，不卖 10 斤档 |
| 门店差异 | 商家 | 这家店卖不卖、什么价、几件库存 | A 店 5 斤卖 29.8，B 店不卖 |

**没动过的自动跟上游走**：运营给类目加一个新档，没调过的商家自动获得，零操作。

## 3. 商品生命周期（核心需求）

### 3.1 状态与规则

```
草稿/已下架 ──保存(随便改)──► 提交 ──[审核开关]──► 发布 = 原子换版 ──► 在售(快照冻结)
     ▲                                                                    │
     └────────────────── 下架（线上快照保留，回到可编辑）◄─────────────────┘
```

- **在售商品 = 冻结快照**。买家从看到、加购到下单，规格文案与结构不变。
  热改白名单只有两样：库存、上下架本身。
- **改在售商品不打断销售**：编辑落**草稿**，线上继续卖旧版；
  发布时一次性换版 —— 买家看到的要么整份旧版、要么整份新版，
  **不存在改一半的中间态**（「先下架再上架」以零窗口方式实现，
  没有列表消失、购物车失效的真空期）。
- **有草稿的商品要一眼看得出**：列表带「有未发布修改」标识；
  发布前能看到**逐字段的差异清单**（本次发布将改变：标题…价格…第 2 档…）。
- **发布是校验点**：草稿引用的档位这期间被平台停用/合并了 → 发布被拦，
  **逐条点名哪一档**，而不是带着失效引用悄悄上架。

### 3.2 审核开关

审核做成**平台级开关**（很多门店不需要事前审）：

- 开：提交 → 运营审 → 过审自动发布（审核期间**线上继续卖旧版**）
- 关：提交即发布，落一条「免审自动通过」的记录备查
- **关掉的只是人审**：发布校验（3.1 最后一条）、强制下架、平台冻结照常有效

### 3.3 改规格库时的提示（按影响分三级）

| 商家/运营做什么 | 系统反馈 |
|---|---|
| 改文案、改本店叫法、调顺序 | 信息条：「不影响已上架的 N 件在售商品；各商品重新发布时生效」 |
| 停用一档/一轴 | **硬拦**：「N 件在售商品正在使用」，附商品清单 + 「批量下架这 N 件」快捷入口 —— 两条路都摆出来 |
| 合并两个重复档 | 确认框：「影响 N 件商品的聚合归属（买家看到的文案不变）」 |

## 4. 性能要求（互联网产品的底线）

- C 端**详情页**：读一件商品不超过 2 张表、零 JOIN（现状已达成，不许倒退）
- C 端**列表页**：翻页走索引，不允许全表扫 + 文件排序（现状未达成，要修）
- 将来「按规格筛选 + 按价排序」：索引直达，不随商品量线性变慢
- 高频共享数据（类目树、平台值池）有缓存，运营改动 30 秒内可见

## 5. 明确不做 / 暂不做

- **不做**「规格库一改、线上商品跟着变」的自动级联 —— 会破坏买家一致性
- **不做**按商家/类目分级的审核开关（先平台一把总闸）
- **暂不做** ES 搜索、列表读模型、倒排表（各有触发条件，见 TDD）

## 6. 验收标准（每条可测）

1. 在售商品被商家编辑并保存后，C 端立即访问：**看到的仍是旧版完整内容**，商品在架
2. 发布后 C 端看到新版；发布事务中途失败 → 线上仍是完整旧版
3. 草稿引用了已停用档位 → 发布被拒，错误信息含该档文案
4. 审核开关两态各走一遍完整「编辑→发布」流，行为符合 3.2 表格
5. 运营停用一个被 N 件在售商品使用的档 → 被拦且给出 N 与清单入口
6. 合并两档后：SKU 身份、商品规格组、参数**三处**都不再出现退役编号；文案逐字不变
7. 类目页翻页 SQL 的执行计划无全表扫、无 filesort
8. 列表接口一次请求的 SQL 条数与页大小无关（无 N+1）
