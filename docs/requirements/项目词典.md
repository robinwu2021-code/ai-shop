> 更新：2026-08-06 ｜ **英文为主**：代码、API、数据库、OpenAPI 用的都是英文，词典的第一职责是**把每个概念的英文名定死**。
> 词汇取自代码（`packages/shared/src/types` 与 `utils/constants`），不是从产品文档抄的。
> 标 **`建议`** 的是尚未在代码里出现、但后端/接口需要时应采用的命名。
>
> 冲突时：代码是事实 → 改文档；代码本身错了 → 先改代码再回来改这里。
> 枚举值有断言守着（`packages/shared/tests/glossary.test.ts`），词典写错或漏收都会让 `npm test` 失败。

## 2. Actors · 人

| Term | 中文 | 代码 | 是什么 / 不是什么 |
|---|---|---|---|
| **Consumer** | 消费者 / 邻居 | `User` | C 端用户 |
| **Merchant** | 商家 / 店主 | `Merchant` | 一个手机号一家店。手机号是店铺主标识，转让交接都靠它 |
| **Staff** `建议` | 店员 | ⬜ 未做 | 店主的受限子账号。**不是**平台运营员工 |
| **Pickup host** | 自提点承接方 | `PickupPoint.ownerType` | 帮别家收货、供邻居来取。**看不到金额与完整手机号** |
| **Group host** | 团发起人 | `Order.hostNo` | 发起自发团的普通用户，负责签收与本团轻核销。**零报酬** |
| ~~Group leader~~ | ~~团长~~ | **已废除** | 抽佣与「服务小商家」冲突（ADR-004）。要抽佣就该以商家身份入驻 |
| **Ops staff** | 运营员工 | `ops-web` IAM | 带数据域。不代管商品、不代定价、不替商家发活动 |

## 3. Places · 地（履约网络）

| Term | 中文 | 代码 | 说明 |
|---|---|---|---|
| **Community** | 社区 | `Community` | **商品可见性的基本单位**。开一个社区≈开一个市场 |
| **Pickup point** | 自提点 | `PickupPoint` | 收货与取货的物理点位 |
| ├ **Store pickup point** | 商家自提点 | `ownerType: "MERCHANT"` | 便利店、菜摊代收 |
| └ **Neighbour pickup point** | 邻里自提点 | `ownerType: "USER"` + `groupNo` | 承接方是**用户自己家**，且只限自己发起的团 |
| **Service scope** | 经营范围 | `SERVICE_SCOPE` | 这家店的货能卖到哪：`COMMUNITY` 只做谈下来的小区 / `CITY` 上门服务 / `PLATFORM` 无履约半径 |

> **Scope ≠ Fulfilment**：范围管「能不能卖给你」，履约管「怎么送到你手上」。
> 一家全市范围的家政能上门到你家，但它进不了你社区的自提点。

## 4. Catalogue · 货

| Term | 中文 | 代码 | 说明 |
|---|---|---|---|
| **Category type** | 品类类型 | `CATEGORY_TYPE` | 驱动计价与履约策略分发，不是展示标签：`GOODS` 日用 / `FRESH` 生鲜 / `SERVICE` 服务 / `VIRTUAL` 虚拟 / `CARD` 卡券 |

| **List price** | 划线价 | `originPrice` | 派生展示值（标折扣用），不是定价 |

## 5. Trade · 交易

| Term | 中文 | 代码 | 说明 |
|---|---|---|---|
| **Order split** | 拆单 | `createOrder` | 一次结算按商家拆成 N 笔子订单，一单只属一家 |
| **Pay group** | 支付组 | `payGroupNo` | 同次结算共享，**一次支付付掉整组**。用户感知仍是「买了一次」 |
| **Fulfilment type** | 履约方式 | `FULFILLMENT` | 7 种：`PICKUP` 自提点自提 / `NEIGHBOR_PICKUP` 邻居家自提 / `DELIVERY` 商家自送 / `EXPRESS` 快递 / `STORE_VERIFY` 到店核销 / `APPOINTMENT` 上门预约 / `INSTANT` 即时发放 |
| **Verify code** | 取货码 / 核销码 | `verifyCode` | 到自提点出示的码 |
| **Redeem / Verify** | 核销 | `mVerify` | 承接方确认「这个人把货取走了」。三校验：码有效 / 未核销过 / **属于本自提点** |
| **Picking** | 分拣 | `mPickingList` | 一批货到点后分开。按商品聚合=分货用，按用户聚合=装袋用 |
| **Mark arrived** | 到货确认 | `mMarkArrived` | 标记「货到了」并通知邻居，`PAID → ARRIVED` |
| **Idempotency key** | 幂等键 | `idempotencyKey` | 防重复提单 |

### Order status · 订单状态（`OrderStatus`，非法迁移直接抛错）

| Value | 中文 | 下一步可去 |
|---|---|---|
| `WAIT_PAY` | 待付款 | `PAID` `CANCELLED` |
| `PAID` | 已付款、待发货 | `ARRIVED` `SHIPPED` `COMPLETED` `REFUNDED` `CANCELLED` |
| `ARRIVED` | 已到点（待核销） | `COMPLETED` `REFUNDED` |
| `SHIPPED` | 已发货 | `COMPLETED` `REFUNDED` |
| `COMPLETED` | 已完成 | `REFUNDED` |
| `REFUNDED` | 已退款 | 终态 |
| `CANCELLED` | 已取消 | 终态 |

> **订单状态里没有「售后中」。** 曾经有一个 `REFUNDING`，那是**售后单**的状态
> （见 §6），后端 `ord_sub_order.status` 从不下发它。两者并存而非互斥 ——
> 一个「已完成」的订单照样能挂一张处理中的售后单，做成订单状态就必须二选一。
> 代价实测过：两端的「售后」页签按它筛，因此恒为空。

## 6. After-sales · 售后

| Term | 中文 | 代码 | 说明 |
|---|---|---|---|
| **After-sale ticket** | 售后单 | `AfterSale` / `afterSaleNo` | **独立资源**，一笔订单可能有多次售后。所有售后动作按 `afterSaleNo` 寻址，不是 `orderNo` |
| **Refund only** | 仅退款 | `REFUND_ONLY` | 货不退回 |
| **Return & refund** | 退货退款 | `RETURN_REFUND` | 寄回后才退款 |
| **Instant refund** | 极速退 | `instantRefundMaxMinor` | 小额自动通过，**仅对仅退款成立**——货没回来就秒退等于白送 |
| **Dispute / Escalation** | 争议 / 平台介入 | `ARBITRATING` | 商家驳回后用户上升，平台裁决（P-6.1） |
| **Liability ruling** | 判责 | 平台端 | 裁决时同时定责任方与出资比例，**与裁决在同一个抽屉**——拆开会出现「裁决完了忘了判责」 |

### After-sale status · 售后状态（`AfterSaleStatus`）

`APPLIED` 待商家处理 → `REFUNDING` 已同意、退款处理中 → `REFUNDED` 退款完成
旁路：`REJECTED` 商家驳回 → `ARBITRATING` 用户已上升平台；`CLOSED` 用户撤销或超时关闭

> **同意后只有一个 `REFUNDING`，没有「等寄回 / 已收货」两态。**
> 退货退款的物流走 `returnExpressNo` 字段，不是状态 —— 有没有寄回看这个字段有没有值。
> C/B 两端此前各自补了一套更细的流程词（AGREED / RETURNING / RECEIVED / DONE / DISPUTED
> —— 不加反引号是因为它们已不存在于代码，本页的守卫会核对每个反引号标识符是否真实），
> 与后端**只有 `REJECTED` 一个词重合**，于是售后详情页的状态永远落进兜底分支、
> 「填退货单号」按钮永远不出现（它 gate 在一个后端不会下发的 AGREED 上）。
> 粒度差异是后端真实的设计选择，端上不能自己补细然后假装后端会给。

> **驳回不改订单状态**——置回已完成会把「申请平台介入」的路堵死。

## 11. Confusable pairs · 易混淆词（这一节最该先读）

| A | B | 区别 |
|---|---|---|
| **Pickup**（自提点自提） | **Store verify**（到店核销） | 去**代收点**取别人送来的货 vs 去**卖家门店**消费自己买的服务 |
| **Pickup**（自提点自提） | **Neighbour pickup**（邻居家自提） | 承接方是**商家** vs **用户自己家**；后者零报酬且只限自己发起的团 |
| **Picking**（分拣） | **Redeem**（核销） | 到货当天**把货分开** vs 取货那一刻**确认给了谁** |
| **Group host**（发起人） | ~~Group leader~~（团长） | 发起人零报酬、只管自己那个团；团长是已废除的职业抽佣角色 |
| **Store home**（门店主页） | **Merchant detail**（商家详情页） | 主页是**交易页**（老客复购入口，第一屏「我买过的」）vs 介绍页 |
| **Merchant points**（商家积分） | **Platform points**（平台积分） | 各店独立 vs 全平台通用 |
| `MerchantTier`（规模） | `MerchantSubject`（主体） | `SMALL/MEDIUM/LARGE` vs `MICRO/INDIVIDUAL/ENTERPRISE`。**平台端把两者写混了**（矩阵 §七之四） |
| `AfterSaleStatus`（单据状态） | 三端同名同义 | **2026-08 已统一**：ops-web 曾经有另一套「处理阶段」式的名字，与库和 C/B 端的 `REFUNDING`/`ARBITRATING` 对不上，而它只跑 mock 所以从没被真实响应打脸过。现已对齐到库的口径（旧名字不在此列出 —— 词典里的大写标识符必须在代码里真实存在，那是本页的守卫规则） |
| **List price**（划线价） | **Discount chip**（折扣标） | 同一件事的两种说法——**同一行里不并存**（商品卡规则） |
| **Service scope**（经营范围） | **Fulfilment type**（履约方式） | 能不能卖给你 vs 怎么送到你手上 |
| **Cutoff**（截单） | **Arrival**（到点） | 截单是**当天几点前下单**，到点是**次日几点货到自提点** |

## 维护约定

1. **新概念先定英文名再写代码**——代码、API、数据库、OpenAPI 都用英文，中文只是这份词典里的注解。
2. 标 `建议` 的英文名尚未落到代码里（如 `Staff`），实现时按此命名，别另起一个。
3. 词典里的**枚举值必须与代码一致**，有断言守着；漏收新值或写了不存在的值都会让 `npm test` 失败。
4. 废弃的名词不删，划掉并写明原因（如 Group leader）——不然过一阵又会有人提。

## 行业 / 主体类型 / 经营范围

三个最容易混的词。详见 [商户主数据与门店-需求](./商户主数据与门店-需求.md) §四。

| 词 | 含义 | 不要混淆 |
|---|---|---|
| **行业** | 商家的经营业态（餐饮/线下零售/居民生活服务/休闲娱乐/交通出行/线上虚拟/其他）。挂**商家**，决定通道准入（能否小微） | ≠ **商品类目**：类目挂**商品**，决定授权范围。一家便利店横跨生鲜/日用/饮料多个类目，行业只有一个 |
| **主体类型** | 小微 / 个体工商户 / 企业。决定要不要营业执照、钱打到个人还是对公 | ≠ **商家分层**（`tier`，为引入大商家预留，一期恒 SMALL） |
| **经营范围** | 本仓库指 `service_scope`：`COMMUNITY`/`CITY`/`PLATFORM`，**这家店的货能被谁看到**（ADR-009） | ≠ 营业执照上的经营范围。后者不在库里，进件资质在 `qualifications` |
| **主体 / 门店** | 主体是**通道与税务认的**那个；门店是**顾客感知的**那个 | 一期两者一一对应（ADR-011） |
