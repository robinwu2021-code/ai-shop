## 一、三端与载体

| L1 | 端 | 载体（一期） | 载体（二期） | 一句话 |
|----|----|-------------|-------------|--------|
| C | 消费者端 | 微信小程序（P0）+ App（P1，uni-app/Capacitor 同码） | 同 | 邻居在自己社区买东西 |
| B | 经营端 | **独立 b-app**（uni-app，与 C 端同技术栈、同共享层）；重管理走 ops-web | 同 | 小商家供货 + 履约 |
| P | 平台端 | ops-web（PC Web） | 同 + 数据/风控子系统 | 运营把商品、活动、商家、钱管起来 |

> ⚠️ **2026-08-06 变更**：B 端已实现为**独立应用 `b-app/`**（20 个页面，M0–M7，42 个契约方法），
> 即 ADR-001 的「二期形态」提前落地 —— 其一期「内嵌 C 端」的结论作废，见 [TDD-b-app](../technical/design/TDD-b-app.md) §2。

## 二、角色矩阵

> 📌 **本节是规格。它与代码的逐条对账见
> [三端角色权限功能对齐清单](./三端角色权限功能对齐清单.md)** ——
> 那份回答「这 25 个角色里，哪些前端做了、哪些后端做了、哪些只写在这里」。
>
> 已知差异（2026-08-11）：B 端实际只有 3 个角色且**权限完全一样**（`StaffRole` 不判权）；
> 平台端 11 个角色后端只实现了 4 个。

### 2.1 C 端角色

| 角色 | 定义 | 关键门控 | 可见功能域 |
|------|------|---------|-----------|
| 游客 | 未登录 | 可逛不可买；加购/下单强制登录 | 2 3 8(只读) 13(只读) |
| 已登录用户 | 微信 openid / 手机号 OTP / Apple | 可下单，须绑归属社区+自提点 | 1–9 13 14 17 |
| 有归属用户 | 已绑定 `community_no`（+ `merchant_no` 常去的店） | 决定商品池、价格、履约时效 | 全部 C 域 |
| 常去店用户 | 从店铺码/店铺分享进入 | 首页前置「我的常去店」；订单记 `trafficSource=MERCHANT_OWNED` | +13.3 |
| 会员（P1） | 付费会员 | 会员价、免运费、专享券 | +7 |
| 团发起人 | 发起商家团实例或邻里求团的用户 | **不是身份，是团实例上的 `ownerId` 字段**；只有发起人能选定报价 | +8 |
| 风控/黑名单 | 刷单、恶意退款、异常裂变 | 拦截下单，给申诉入口 | 受限 |

> ⚠️ **删除「推广员」角色**（ADR-004）：不存在逐单抽佣，也就不存在分销身份。
> ⚠️ **发起人与参团者完全同价、无任何额外收益** —— 一旦发起有收益就会长出职业发起人，刷团与归因问题原样回来。

### 2.2 B 端角色

| 角色 | 定义 | 载体 | 核心职责 | 关键权限边界 |
|------|------|------|---------|-------------|
| 商家（申请中） | 提交入驻申请、审核中 | b-app | 补交资料、看审核状态 | **不可上架、不可收款** |
| 商家管理员 | 入驻主体的负责人（个人/个体户/企业） | b-app + ops-web 商家视图 | 商品、库存、报价、订单、履约、结算 | 只见**本 `merchantNo`** 数据 |
| **自提点商家（常驻）** | `PickupPoint.type=STORE` 的门店 | b-app 履约台 | **核销、分拣、到货确认**，收履约服务费 | 见**本 `pickup_no`** 的全部订单（含他家商品）；客户手机号脱敏 |
| **团发起人（临时点）** | `PickupPoint.type=NEIGHBOR`，送到自己家 | **C 端**「我发起的团」轻核销 | 批次签收 + 逐单核销 | **零报酬**；作用域限该 `group_no`；不计入商家评分（ADR-005） |
| **商家店员**（✅ 2026-08-12） | 商家授权的操作人。**实际拆成四个角色**：店长 `MANAGER` / 店员 `CLERK` / 理货员 `PICKER` / 客服 `CS` —— 履约不是一件事，是三件（对货 / 对顾客 / 对收件人） | b-app | 见 [B端功能点-权限码-页面](../technical/reference/B端功能点-权限码-页面.md) | 无财务、无结算账户可见性（`BizPermsTest.managerTouchesNeitherMoneyNorStaff` 锁住）；**店长也不行** |
| 服务人员/技师（P1） | 服务品类履约人 | C 端专区 | 排期、上门打卡、服务单 | 只见分配给自己的服务单 |
| **配送员**（✅ 2026-08-12，`COURIER`） | 即时配送履约人。**不是第三方运力** —— 小店老板骑电动车送两条街（ADR-005 §5，不做骑手系统） | b-app 配送页 | 取货、送达 | **只见配送单**：`CourierOrderVO` 无金额、无核销码、无买家明细。⚠️「+ 地址」这一半还没做 —— 那个字段 B 端从来没下发过，**所有角色都看不到** |

### 2.3 平台端角色

| 角色 | 核心职责 | 数据边界 | 高危权限 |
|------|---------|---------|---------|
| 超级管理员 | 账号、角色、权限、系统配置 | 全量 | ✅ 授权、开关 |
| 商品/类目运营 | 类目树、商品池、上下架、多语言文案 | 全量商品 | 上下架 |
| 活动运营 | 券、满减、限时、拼团、新人礼、皮肤下发 | 全量营销 | 发券预算 |
| 社区运营 | 社区网格、自提点建档与启停、履约调度 | 全量社区 | 自提点启停、迁移 |
| 商家运营（BD） | **商家拉新与入驻审核**、资质、类目授权、求团人肉撮合 | 全量商家 | 认证标、封禁 |
| 审核员 | 商品、评价、内容、凭证、图片审核 | 待审队列 | 驳回/下架 |
| 客服 | 工单、争议介入、代客操作、退款审批（阈值内） | 按工单授权 | 代客退款 |
| 财务/结算 | 分账、结算单、提现、发票、个税代扣 | 全量资金 | ✅ 打款、分账 |
| 风控 | 刷单、异常裂变、恶意退款、黑名单 | 全量行为 | ✅ 拦截、封禁 |
| 数据分析 | 看板、报表、归因分析 | 只读脱敏 | — |
| 技术运维 | 配置、灰度、日志、Mock 开关、发版 | 系统级 | ✅ 环境切换 |

> **权限模型**：RBAC + 数据域（`tenant_no=MAIN` / `merchant_no` / `community_no` / `pickup_no`）。所有 B 端角色的数据可见性由归属键裁剪，**不靠前端隐藏**。
> ⚠️ **三个裁剪维度正交**：`merchant_no` 裁「我卖的货」，`pickup_no` 裁「我要核销的货」，`group_no` 裁「我发起的团」。
> 自提点承接方会看到**别家商家**的商品到自己点上核销 —— 这是必然的，但**只能看到履约必需字段**（取货码、商品名、数量、收货人昵称），不得看到金额与完整手机号。
> **邻里自提（临时点）的脱敏要求更严**，且作用域只有单个 `group_no`（ADR-005 §4）。

### 7.1 三条主链路的完整时序

**下单 → 履约**（三端各自的动作与状态迁移）

```
C 加购 → 结算（按商家拆单，共享 payGroupNo）→ 支付整组
                      ↓
B 接单（PAID）→ 备货（PREPARING）→ 到货确认（ARRIVED，通知邻居）
                      ↓
C 到自提点出示取货码 → B 核销（三校验：码有效 / 未核销 / 属于本点）→ COMPLETED
                      ↓
P 按自然周跑批：毛收入 − 退款 − 佣金(按客流档) − 履约服务费(按件) = 应结
```

**售后 → 争议裁决**

```
C 申请（仅退款 / 退货退款）
   ├─ 仅退款 且 ≤ 极速退阈值 → 自动通过 → 退款
   └─ 其余 → B 处理
        ├─ 同意 · 仅退款   → 直接退款
        ├─ 同意 · 退货退款 → AGREED → C 填运单号(RETURNING) → B 确认收货 → 退款
        └─ 驳回（必须填理由，不改订单状态）→ C 可上升 → DISPUTED
                                                    ↓
                                        P 裁决 + 判责 + 出资比例 → 退款/驳回
```
> 退款永远是三件事一起：改状态 + 回收已得积分 + 退还已用积分（`settleRefund()`）。

**进店归因 → 费率**

```
C 扫店铺码/点分享卡片（带 merchantNo）→ 下单时写入 Order.trafficSource
                      ↓
P 归因规则判定：MERCHANT_OWNED（自带客流）还是 PLATFORM
                      ↓
B 结算单按档计佣金：自带 0% / 平台 2%（占位值，见规则表）
                      ↓
商家质疑时 → P 归因链路审计给凭据
```

## 七之四、两套类型系统的词汇对照

C/B 两端用 `packages/shared/src/types`，平台端有自己的 `ops-web/lib/types`。
22 个同名类型里 **8 个枚举值域不一致**——字段不同是正常的（平台看得到 `communityName`，
消费者看不到），**枚举值不同不是**：后端只会实现一套，一端写进去的值另一端读不出来。

现状已钉成断言（`packages/shared/tests/type-alignment.test.ts`）：
基线内的分歧不报错，**基线外的新分歧立刻失败**。今天是 8 个，不会悄悄变成 12 个。

| 概念 | shared（C/B 端） | ops（平台端） | 结论 |
|---|---|---|---|
| `OrderStatus` | `WAIT_PAY` `SHIPPED` `REFUNDING` `REFUNDED` | `PENDING_PAY` `DELIVERING` `AFTER_SALE` | **同物异名**。权威取 shared——状态机与 `assertTransition` 在这边；ops 侧改名 |
| `AfterSaleStatus` | 售后单自身的状态机：`PENDING→AGREED→RETURNING→RECEIVED→DONE` | 平台处理阶段：`APPLIED` `MERCHANT_HANDLING` `PLATFORM_INTERVENE` `REFUNDED` `CLOSED` | **语义不同名字也该不同**：ops 那套应叫 `AfterSaleStage`，两者是「单据状态」与「处理阶段」的关系 |
| `AfterSaleType` | `REFUND_ONLY` `RETURN_REFUND` | 多一个 `EXCHANGE` | 一期不做换货，用「退货重下」代替（C-AS-01）。ops 侧应去掉或标灰 |
| `MerchantStatus` | `NONE` `APPLYING` `REJECTED` `ACTIVE` `SUSPENDED` | `DRAFT` `SUBMITTED` `REVIEWING` `APPROVED` `REJECTED` | `APPROVED` 与 `ACTIVE` 是同一件事的两个名字，接后端前必须并成一个 |
| `MerchantTier` | 规模：`SMALL` `MEDIUM` `LARGE` | 主体：`PERSONAL` `INDIVIDUAL` `COMPANY` | **名字撞了、意思不同**——ops 的 tier 装的是 shared 里的 `MerchantSubject`。ops 侧改名，把 tier 让出来给规模 |
| `CampaignType` | 商家活动：`FULL_CUT` `BUY_GIFT` `COUPON` | 平台活动：`SECKILL` `FULL_REDUCE` `GIFT` `NEWCOMER` | 要么合并成一张表，要么显式拆成 `MerchantCampaignType` / `PlatformCampaignType` |
| `CampaignStatus` | 多 `PAUSED`（商家可暂停） | 多 `SCHEDULED`（平台可预约生效） | 都合理，合并即可 |
| `AppealStatus` | `ReviewAppealStatus`：`PENDING` `UPHELD` `REJECTED` | `AppealStatus` | 名字与值域一并对齐 |

**为什么现在不直接统一**：ops-web 侧这些字面量散在 20+ 个文件里（页面、mock、契约），
改名属于那条线的工作；而 shared 侧一改，两个 app 的状态机与 mock 全要跟着动。
接后端（E1）时必须一次做完——那时会有唯一一份 OpenAPI，词汇由它裁定。
在那之前，断言保证不会变得更糟。
