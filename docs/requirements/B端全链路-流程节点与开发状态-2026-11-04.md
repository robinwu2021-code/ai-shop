# B 端全链路流程节点与开发状态

更新日期：2026-11-04（Asia/Shanghai）。适用后端 `codex/commerce-foundation` 与 Flutter `ai-shop-bapp` 的标准注册进件流程。

目前已交付基础商业模块、注册建店与进件接口合同、Flutter 标准页面及本地测试。模拟器已安装启动，真实 API 只读访问通过；真实短信注册、建店、申请提交和支付进件尚未完成端到端验收。付费 Plan 购买仍是后续开发范围，不能把三档展示当作付费购买已完成。

## 一 完整流程与完成判据

### 主流程

环境与市场核对 → 登录协议确认 → 短信注册/登录 → 恢复账号和门店 → 选择经营类型、查看三档 → 创建门店并初始化 FREE → 精确选择门店并检查权益 → 完善主体/上传资质 → 提交入驻资料 → 匹配申请的商家协议确认及平台审核 → 按资金模式办理收款 → 渠道状态回查 → 开业就绪核验。

付费套餐是建店后的可选分支：选择付费商品 → 报价 → 下单 → 向平台付款 → 服务端确认支付事实 → 数字交付 → 门店权益更新。选择 FREE 可继续资料和收款流程，不强制先付费。

| 节点 | 用户或平台动作 | 主要接口或系统落点 | 完成判据 |
|---|---|---|---|
| N00 环境与市场 | 确定测试端、地区、手机号格式、币种、支付模式与渠道 | 开发配置、主数据和可用渠道 | App 可访问目标 API；市场/币种来自权威配置；明确 provider 是 stub、沙箱还是真实渠道 |
| N01 注册登录 | 阅读并确认登录协议，发送短信，输入当次验证码登录 | `POST /biz/auth/otp/send`、`POST /biz/auth/login` | 真实手机收码并成功验证；首次登录创建账号；无独立 register 接口 |
| N02 账号恢复 | 冷启动/重登，恢复可访问门店 | `GET /biz/merchant/profile`、`GET /biz/stores/mine` | 登录状态有效；列表加载失败不能当作无店；不沿用其他账号的店号 |
| N03 经营类型与三档 | 选择实际发布的经营类型，对比 FREE/PRO/CHAIN | `GET /biz/business-types`、`GET /biz/business-types/{typeCode}/plans` | 类型与卡片来自实际目录；商业经营类型与证照行业分别填写；禁止补造价格或可购买状态 |
| N04 建店与 FREE | 填店名并快速开店 | `POST /biz/merchant/quick-start` | 待补证主体、默认门店、商业账户及 FREE 权益同事务生成；精确使用响应 `currentStoreNo`；同类型重试不重复建店 |
| N05 进入门店 | 选择门店、恢复岗位和业务端上下文，查询权益 | `GET /biz/context`、`GET /biz/stores/{storeNo}/context`、`/subscription`、`/entitlements`；端准入/端会话 | 身份、成员、岗位、治理和端权益均通过；所有门店请求带匹配的 `X-Store-No`；FREE 不代表资质或收款已获批 |
| N06 套餐处理 | 保持 FREE，或进入付费套餐购买分支 | 只读 Plan 卡片；未来商城报价/订单/支付/交付 | 当前 FREE 查询正确；付费必须有真实订单与服务端支付事实、交付记录和权益变化才算购买成功 |
| N07 资料采集 | 按主体与行业填写资料、上传图片，按需 OCR | `GET /common/master-data`、`GET /biz/communities`、`POST /biz/upload/image`、`POST /biz/qualifications/recognize` | 必填项满足当前字典；上传 URL 可用；结构化类型/证号/有效期保存正确；OCR 失败可手填 |
| N08 提交入驻 | 提交资料并查询进度/驳回原因 | `POST /biz/merchant/apply`、`GET /biz/merchant/apply` | POST 返回档案，随后 GET 读到实际申请；区分 PENDING/REVIEWING/REJECTED/APPROVED；超时先回读，不盲目重发 |
| N09 协议与审核 | 本人确认匹配申请的商家协议；运营受理、通过或驳回 | `POST /biz/merchant/agreement/accept`；运营申请队列、`accept`、`audit` | 商家协议正文真实且明确确认；申请主体匹配，确认时间有效；审核结果落库。批准后刷新档案、资质和收款状态 |
| N10 收款模式与材料 | 查看资金模式、渠道及缺失项；财务岗补结算资料 | `GET /biz/merchant/pay-channel`、`GET /biz/merchant/payment` | 按实际 AGGREGATED/DIRECT 模式处理；归集模式不强制每店独立开户；主体默认收款行与分店独立行明确区分 |
| N11 提交支付进件 | 提交通道材料；确有独立结算需要时先建独立行 | `POST /biz/merchant/payment`；可选 `POST /biz/merchant/payment/store/{storeNo}` | 取得真实提交状态；默认行省略 body.storeNo，独立行才传选店号；未知结果先读回，不能重复开户 |
| N12 回查支付状态 | 等待通道处理，主动刷新、处理拒绝/冻结 | `GET /biz/merchant/payment`、`POST /biz/merchant/payment/{payChannel}/refresh` | 通道状态、商户号与 `canReceiveMoney` 一致；字典 enabled、submitted 或 ACTIVE 单一字段均不能独自代表可收款 |
| N13 开业验收 | 重新登录/切店，确认可经营、可见、可收款；渠道沙箱测试订单 | 档案、权益、服务范围、收款资格及订单支付记录 | 主体和治理允许经营、端准入有效、服务范围满足要求、实际收款资格有效；沙箱交易与回查/回调一致。真实扣款另按明确测试安排执行 |

商家入驻审核、商业套餐和支付渠道审核分别维护状态。登录协议勾选不等于商家服务协议落库；商家审核通过不等于支付进件通过；购买 Plan 也不能代替岗位或资质。

## 三 台湾场景的差异与阻塞

Flutter 会话另收到“台湾门店及蓝新、LINE Pay、街口”的测试要求，纳入后续验收范围，不能直接套用现有大陆手机号和微信/支付宝字典宣布完成。

| 范围 | 当前事实 | 下一完成条件 |
|---|---|---|
| 手机号 | 当前标准页面为11位手机号；用户已提供号码用于开发短信测试 | 明确是否用该号码验证通用账号，或要求台湾号码注册；核实区号、规范化、供应商收码及服务端校验，不自行改写号码 |
| 地区与币种 | 系统其他模块已有TW/TWD基础记录和相关测试；当前标准注册建店合同没有明确可核验的市场选择/回读路径 | 权威确定并回读市场、币种、主体和结算约束；不能只填台湾地址即认定为台湾商户 |
| 三个渠道 | 当前主数据只返回微信/支付宝；当前检查未发现蓝新、LINE Pay、街口的实际进件适配 | 补齐真实渠道契约/适配、配置及沙箱商户资料；主数据可用状态与运行网关一致 |
| 材料与开户 | 现有明确标注的测试图片/资料只能用于开发流程；provider仍stub | 各渠道沙箱所需主体/税号/结算材料满足合同；分别验证受理、拒绝、补件、通过及可收款 |
