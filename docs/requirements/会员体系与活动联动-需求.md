## 一、一句话

**把「在这家店买过一次的人」变成一份商家看得见、分得清来源、能打标签、能圈出来做活动的名单。**

## 二、为什么现在做

商家手上已经有三样东西：公告（说给进店的人听）、活动（改价格）、客户列表（看谁来过）。
它们之间没有连接：

- 公告只有进店的人看得到 —— 而店主真正想触达的是**今天没进店的老客**。
- 活动对所有人一视同仁 —— 「熟客专享」这种最常见的小店玩法做不出来。
- 客户列表只有「谁来过」，没有来源、没有标签、不能筛、不能当作活动的受众。

推送（给老客发一条消息）之所以卡住，不是通道问题（个推已接），是**没有受众**：
发给谁、他愿不愿收、发过几次，一个都答不上来。会员体系就是补这一层。

## 三、名词

| 词 | 定义 | 不是什么 |
|---|---|---|
| **会员** | 某个人与**某一家商家**的关系 | 不是平台会员，不是付费订阅（需求矩阵 7.4 的付费会员另说） |
| **线索会员** | 商家手工录入手机号、但本人还没在平台出现过 | **不可被推送、不享权益**，见 §五合规 |
| **来源** | 这个关系是怎么建立的 | 不是「客流来源费率」（`traffic_source`），两者相关但口径不同 |
| **系统标签** | 平台按规则算出来的（沉睡、熟客…） | 商家不可编辑 |
| **商家标签** | 商家自己打的（「爱吃辣」「只要土鸡蛋」） | 平台不解释其含义 |

## 四、会员从哪来（本次的核心）

| # | 来源 | 怎么产生 | 一期 | 备注 |
|---|---|---|---|---|
| 1 | `ORDER` 下过单 | 支付成功即入会，无需任何动作 | ✅ | 存量订单回填 |
| 2 | `SHARE` 分享点击后注册/授权 | 商家/老客分享 → 落地页 → 注册或授权 → 入会并记下分享人 | ✅ | 复用现有归因（`mkt_attribution`）|
| 3 | `SCAN` 扫店铺码进店 | 扫码 → 授权 → 入会 | ✅ | 已有店铺码 |
| 4 | `MANUAL` 商家手工录入 | 商家输入手机号（+备注/标签），进入**线索态** | ✅ | 见 §五 |
| 5 | `FAVORITE` 收藏本店 | 收藏即建立关系（弱） | ✅ | 已有 `usr_store_favorite` |
| 6 | `SEARCH` 小程序/App 搜索后主动加入 | 用户在店铺页点「加入会员」 | ✅ 一期 | C 端店铺页要有「加入会员」这个动作（2026-08-24 拍板并入一期）|

**每一次来源都要留一行明细**（`mbr_member_source`）：**从哪家门店进来**、哪条链接、
**谁发的链接**（商家自己 / 员工 / 老客转发）、**哪个员工录的**、因哪场活动、是不是首次。
只记「来自分享」而不记「谁分享的」，等于分享激励（R3）没法结算，商家也不知道该谢谁；
不记门店，则「按门店经营会员」这条路根本走不通。

### 验收标准

- AC-1 在某店支付成功后，该店会员列表里出现这个人，来源为 `ORDER`，首单时间正确。
- AC-2 通过分享链接注册的新用户，来源为 `SHARE`，且 `sourceDetail` 里能查到分享人。
- AC-3 商家录入一个未注册手机号，列表里出现**线索**标记；该号日后注册/登录后，自动变为正式会员，来源仍记 `MANUAL`，并记录认领时间。
- AC-4 同一个人在同一家店只有一条会员记录（多来源时记**首次**来源，另存补充来源）。

## 四点五、会员归属：挂主体，但要能按门店经营

会员关系**挂在主体**上（一份名单、一套标签），同时**必须记下来源门店**（他是从哪家店进来的），
并且允许商家选择用哪种口径经营：

| 口径 | 适用 | 会员列表 | 「新客」的含义 |
|---|---|---|---|
| **按主体**（默认，多数情况） | 一条街上的两家店、总店 + 分店 | 全部门店合并 | 对这个商家第一次买 |
| **按门店** | 城东城西各一家、相隔十公里 | 必须选一家店，默认当前门店 | **对这家店第一次买**（在别的店买过也算） |

**为什么是开关而不是二选一**：十公里外那家店的会员对这家确实没用 —— 他不会跑过来买菜；
而一条街上的两家店，让店主维护两份名单又是纯粹的重复劳动。两种都是真的。

开关只改**展示与分层口径**，不改底层存储（两级数据一直都在算），所以随时可切、不需要迁移。

两条不跟着开关变：**标签仍属主体**（「爱囤货」不因他在哪家店买而不同，门店维度体现在筛选上）；
**触达频次仍按人算**（按门店算的话三家店就是三倍轰炸，而挨骂的是平台的通知权限）。

## 五、合规边界（不可协商）

1. **手工录入 ≠ 获得触达许可**。线索会员不可被推送、不可被短信、不进任何活动受众，
   直到本人在平台注册/登录并完成认领。
2. **手机号只出示后四位**，全平台不提供会员导出。按手机号查找必须输入**完整号码**才返回结果 ——
   前缀模糊查询会把会员库变成通讯录。
3. **触达频次由平台管**，不由商家定：每店每人 7 天 ≤1 条；沉睡唤回 30 天 ≤1 条。
4. **买家可关**：店铺页一个开关，关掉后该店永不再触达，且商家看得到「已关闭」但不知道原因。

## 六、标签

| 类型 | 例子 | 谁维护 | 规则 |
|---|---|---|---|
| 系统 | `新客` `常客` `熟客` `沉睡` `高客单` `只买特价` `常自提` | 平台每日重算 | 商家只读；口径公开可查 |
| 商家 | 任意短文本 | 商家 | 每店 ≤50 个标签，每个会员 ≤10 个 |

- 系统标签**不可编辑**：可编辑的自动标签三周后一定是脏的（有人改了、有人没改，谁也不敢用它筛人）。
- 商家标签支持批量打/去（先筛出人，再一次性打标）。
- **商家标签跨门店共享**（2026-08-24 拍板）：标签属于**主体**不属于门店。
  同一个人在总店买米、在南门店买油，是同一个「爱囤货」的人；标签按门店各存一份的话，
  多店商家要在每家店重打一遍，而两份很快就会不一致。
  门店维度仍然保留在**筛选条件**里（「只看南门店的会员」）。

## 七、筛选

必须支持（可组合）：来源、系统标签、商家标签、最近下单区间、累计消费区间、**手机号精确匹配**。
筛选结果是一份**可执行的名单**：能一键发券、能设为活动受众、能发一条消息（受 §五 3 约束）。

## 八、与活动联动

### 8.1 活动现状（review 结论）

| 现状 | 位置 | 问题 |
|---|---|---|
| 四类活动：店铺券 / 满减 / 限时特价 / 买赠 | `mkt_campaign`，B-10.2 | **没有人群维度**，对所有人生效 |
| 叠加规则：活动 → 券 → 积分，同类取最优 | 下单算价 `OrderServiceImpl.Discounts` | 已稳定，**本次不改** |
| 定向发券的雏形：`target` / `target_desc` / `user_no` | `mkt_coupon_issue` | 只有运营端在用，商家侧没有入口 |
| 归因：user → 商家/邀请人/渠道 + 过期窗口 | `mkt_attribution(_log/_rule)` | 已有，会员来源直接复用 |
| 裂变：邀请有礼 | `mkt_fission_*` | 与会员来源 `SHARE` 是同一件事的两半 |

### 8.2 联动要做的四件事

1. **活动可以只给一部分人**：新建活动时可选受众（全部 / 某些标签 / 某些层 / 某些来源）。
   不选 = 全部，与今天行为完全一致（向后兼容，老活动不受影响）。
2. **从会员名单直接发券**：筛完人 → 发券，发放记录带上当时的筛选条件快照。
3. **活动带来的新会员自动打标**：`来自「中秋预售」`，让「这场活动到底拉来多少人」有答案。
4. **效果回看**：一场活动 / 一次发券 / 一条消息，各自给出「触达多少人、多少人来、带来多少单」。

### 8.3 明确不做

- 不做百分比折扣、不做 N 件优惠（B-10.2 已记：模型里没有，一期不扩）。
- 不做付费会员、储值卡、次卡（涉及预收资金与预付卡监管）。
- 不做店铺积分（ADR-006 已否，会与平台积分形成两套口径）。

## 九、分批交付

| 批次 | 内容 | 独立可上线 |
|---|---|---|
| **一** | 会员底座：入会（下单/扫码/收藏/**主动加入**）+ 来源标识 + 系统标签 + B 端会员页（替换现「客户」页）+ 手机号精确查找 + C 端「加入会员」 | ✅ 无新对外能力 |
| **二** | 手工录入 + 线索态 + 注册后自动认领 | ✅ |
| **三** | 商家标签 + 组合筛选 + 从名单定向发券 | ✅ |
| **四** | 活动受众 + 活动来源打标 + 效果回看 | ✅ |
| **五** | 触达（推送）+ 频次闸 + 退订 | ✅ 这才是最初的「通知老客」|
