# PRD 统一销售渠道接入

> 状态：需求草稿，依据用户2026-10-26连续确认的跨行业方向整理；已交付C0草稿和通用授权引擎切片；完整需求未全部实现，未在生产建表或上线。上游：[餐饮完整需求E02及外部接入](./餐饮系统-完整需求文档.md)、[品牌商品库与门店商品](./PRD-品牌商品库与门店商品.md)。设计：[统一销售渠道TDD](../technical/TDD-统一销售渠道接入.md)。

## L1 目标

零售与餐饮共用一套平台账号、店铺连接、目录同步、订单接入、状态回传和对账能力。现阶段不开发前端页面；当前嵌入既有宿主，接口与数据归属支持未来独立部署。

## L2 业务范围

| 业务产品 | 核心流程 | 业务责任方 |
|---|---|---|
| INSTANT_DELIVERY | 平台接单、制作/拣货、骑手交接 | 餐饮或零售 |
| ECOMMERCE / MARKETPLACE | 原付款事实核验、拣货、快递多包裹、退换货 | 原零售/仓库/订单 |
| LOCAL_LIFE | 验券、原消费授权、核销/撤销 | 原行业交易与权益 |

平台品牌、产品、市场、协议、业务来源和履约方式分别建模。台湾Uber Eats、foodpanda；阿联酋Keeta、Talabat、Deliveroo、noon Food、Careem Food、Smiles Food；中国大陆淘宝/天猫获准业务、抖店、抖音生活服务列为候选。Keeta按用户既定范围仅规划，真实接入须另行启动；其他真实平台也须获准协议及测试账号，不把候选列表当已支持。

商家管理账号、店铺连接、选品/餐牌及订单，平台运营仅提供基础配置和授权范围内支持，不审核商家目录。沿原账号、主体、商户、门店、营业时间、商品、核心订单、支付、库存及打印能力。首版同一连接的目录和订单均一个行业责任方，可同域聚合多个餐牌或选品；混合行业目录和订单关闭，取得统一跨行业导入合同后另行开放。

## L4 交付边界

自动同步由发布事件触发、手动同步由API触发，两者共用原动作日志；平台异步受理不等于远端全量生效。平台已收款不等于商家到账，订单通知不等于已付款或可发货。未知金额、映射和资金证据不能填0或默认成功。

支付资金执行、券核销和真实外部渠道逐项独立门禁，不因非支付底座完成就启用；经营报表最后，技术同步统计先按业务事实有界读取。可售量、库存余额、发货包裹、权益余额、成本不在渠道再建一套。

按用户交付节奏：整批源码和测试源码→统一编译→集中受影响专项→仅相关复测→统一提交推送与固定SHA集成发布。前轮仅整理设计；本轮已确认启动开发，按TDD实际子集登记进度，当前未发布。
