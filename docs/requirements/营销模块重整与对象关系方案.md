# 营销模块重整与对象关系方案

状态：产品设计评审稿，2026-10-20。先评审原型，不表示下列新增对象或页面已经实现。

## 0. 当前实施优先级：独立储值方案（2026-10-20 最新调整）

账户归属最新修订：本期仅门店独立，同一顾客在同一门店共用账户，不同门店余额隔离。独立储值方案按当前门店管理。连锁共用、模式设置、账户组绑定和跨店成本结算全部搁置；每笔充值与批次仍保留来源门店。当前待开发范围以《任务表-门店储值管理》为准。

按最新要求，先跳过活动：**营销 → 储值管理 → 新建储值方案 → 确认创建 → 选择方案办理**。本节替代下文关于“充赠必须通过活动”的首期约束；活动相关内容保留为后续规划。

| 功能 | 当前设计 |
|---|---|
| 多个独立方案 | 分别创建充50送10、充100送30、充200送50，可同时启用，每个方案一组实收与赠送金额 |
| 创建 | 名称、实收金额、赠送金额、自动计算到账合计；实收大于0、赠送不小于0，最多两位小数；赠送0即普通储值 |
| 适用范围 | 商家全部门店；不要求先创建、选择或发布活动 |
| 办理 | 识别顾客 → 选择可办理方案 → 核对实收与到账 → 商家确认线下收款 → 提交入账；不允许店员临时改赠送 |
| 生命周期 | 创建后可办理，可停用与重新启用；停用只阻止新办理，不改变已有余额与历史流水 |
| 账户 | 同一顾客在同一门店共用账户，不同门店隔离；多个方案不是多个钱包，入账流水分别保存方案编号、版本、名称和金额快照 |
| 消费 | 复用统一会员码识别；按消费单确认核销，保留服务、门店、金额、时间与余额变化记录 |
| C端 | 统一入口查看有储值记录的门店，按最近充值或核销时间倒序；重点查看消费记录；页面不拆本金赠金，不新增独立核销码，不提供线上退款 |

模块归属：Pay负责独立储值方案及版本、充值单、账户、入账批次与流水；Core提供商家/门店/会员上下文，后续营销活动可引用方案，不作为当前办理的必需条件。历史充值仍保留已有活动来源。

接口差异：现有充值契约依赖活动编号、版本与档位，尚不支持上述独立方案。本轮交互原型仅使用内存演示数据，刷新即还原；后续需新增独立方案的列表、创建、详情、启停及版本契约，并让充值单支持独立方案来源。后端必须校验商家、方案有效版本及金额快照，使用幂等键防重复入账，不以虚构活动适配独立办理。

原型路径：s11方案列表、s22创建、s23确认、s24详情与启停、s14办理、s25顾客账户列表、s13账户详情、s26收支记录、s27收支详情。储值管理分为“储值方案 / 顾客账户 / 收支记录”；顾客先从可搜索列表进入详情，有储值记录的账户按最近储值或核销时间倒序展示，包含余额为0的账户。储值与核销合并为收支记录，按发生时间倒序，支持“全部 / 储值 / 核销”Tab及时间弹框筛选，门店沿用统一切换，不在本页重复设置；从账户详情进入时限定当前顾客，时间弹框确认后生效，取消不改变已选范围；类型切换保留时间范围。页面仅保留业务字段和必要提示，设计说明放在图注。已保留活动原型以供后续讨论，不属于本轮储值前置流程。

## 1. 目标与现状

沿用现有营销首页、活动、优惠券、拼团、集单、会员及平台活动，解决新“活动与权益”入口与旧入口重复、创建储值直达专属表单、活动/资产/办理混排的问题。商家应能从营销新建所有已支持活动，也能不创建活动直接管理卡券、查储值及处理既有团和集单期。

原型真源：`prototypes/marketing-module-v2.html`。本轮仅设计；不删除旧实现、不改服务器数据。

## 2. 对象与模块边界

| 对象 | 管什么 | 独立性与关系 | 模块 |
|---|---|---|---|
| 活动 | 参与对象、排期、条件、利益、预算、发布版本 | 引用权益/充值方案或开出团、期；不拥有账户余额 | Core营销 |
| 卡券与权益 | 模板及版本、发行策略、持有权益、余次、核销 | 可以直接发放，也可由活动按规则发放 | Pay权益 |
| 储值账户 | 顾客在商家下的余额、冻结、流水、使用记录 | 不依赖任何一场活动存续，不按活动另开钱包 | Pay储值 |
| 基础充值方案（建议新增产品概念） | 常规充值金额或允许金额、适用范围、办理说明 | 可复用；不是有赠送就算基础方案。普通充值不用商家手动建活动 | Pay拥有充值/使用规则与账户；Core提供商家门店主数据、活动引用，具体契约待设计 |
| 储值活动 | 活动期内的固定充值档位与额外赠送 | 引用或快照基础规则，发起入账时冻结活动版本和档位；赠送不重复定义在两处 | Core活动，Pay执行 |
| 拼团活动 / 团 | 规则 / 一次团的成员、人数、时限、成散 | 一场活动产生多个团；活动暂停后已有团按原规则完成 | Core活动与团业务 |
| 集单活动 / 集单期 | 排期、起订及价格规则 / 某日订单、截单、采购和履约 | 一场活动产生多期；结束后不删历史期或终止已承诺履约 | Core活动与集单业务 |

“活动管理优惠券”准确表达为“活动引用券模板并控制发放条件”，不把券定义和用户已得权益归活动所有。储值同理：活动控制充赠条件，不管理余额本身。

## 3. 营销信息架构

营销首页保留唯一经营入口，移除“活动与权益”与旧活动/券双套入口并存的目标设计。一级分区如下：

| 页面入口 | 首页摘要 | 页面主任务 | 新建/动作去向 |
|---|---|---|---|
| 活动管理 | 进行中、草稿、待开始 | 查看/创建/发布/暂停活动 | 统一活动创建器 |
| 卡券与权益 | 可发模板、批次待处理 | 定义、发行策略、定向发放、持有及使用记录 | 独立建券；需要自动发放时建立活动关联 |
| 储值管理 | 有余额顾客、储值记录 | 顾客账户、充值方案、充值及消费流水 | 普通充值独立办理；充赠规则去活动创建器 |
| 拼团管理 | 待成团/临近截止 | 看团进展、成员、成散处理 | 新建规则回统一创建器的拼团类型 |
| 集单管理 | 今日一期、截单及待履约 | 按期收单、汇总、采购、配送 | 新建规则回统一创建器的集单类型 |
| 客户与触达 | 会员、标签、人群、已发送任务 | 找人、圈选、发消息 | 沿用现有会员与触达模块 |
| 平台活动 / 效果记录 | 可报名、分项指标 | 报名与回看 | 沿用相应入口 |

工作台保留高频“办理充值、服务核销、今日集单、待成团”快捷入口，营销管理页也提供上下文跳转；两处指向同一资源，不能复制一套业务。

## 4. 统一创建活动

营销 → 新建活动 → 选择大类 → 选择预置或自定义 → 填名称、排期、参与对象及合法规则 → 确认 → 保存草稿/发布。

| 大类 | 类型 | 引用对象 |
|---|---|---|
| 订单优惠 | 满减、满件优惠、折扣、特价、第二件优惠 | 商品/类目及计价规则 |
| 卡券活动 | 领券、定向发券、生日/唤醒/体验券 | 已发布权益模板版本；活动不再重复填写券面规则 |
| 储值活动 | 普通规则快捷配置、固定档位充赠、业态充赠 | 基础充值规则快照与活动档位；普通办理入口不强迫建促销 |
| 赠礼与积分 | 满赠、买赠、赠积分 | 商品、履约、积分发行规则与预算 |
| 拼团与集单 | 凑人成团、按期集单 | 团或期的价格、排期和成单条件 |

业态、新客、节日为推荐/受众/排期维度。自定义是同类型内自行配置合法字段，不是无限制组合引擎。月卡、次卡为权益商品，定义30次/30天、售价和使用限制后可关联促销，不直接归为“发券活动”。

## 5. 储值与活动的具体约束

1. 充值账户和消费记录独立于活动，多个来源入账汇入门店/连锁配置对应账户，Pay内部保留来源批次及扣减策略。
2. 普通充值只按基础规则办理，无营销赠送；促销充值必须命中已发布且适用的活动版本/档位。不能任意选择一个赠送，也不能由店员临时输入赠金。
3. 账户页面不按活动建子钱包；活动详情能追到入账来源，账户流水能追到相应活动与办理单。
4. 暂停活动停止新参与，不影响既有余额、用户券、已有团及集单期承诺。停止发行和停止使用分开。
5. 商家收款、平台记账；会员码识别人，不代表扣款授权。先报价、消费者确认，再核销，结果未知查询原单。
6. C端仅展示商家/门店、余额、储值和消费记录；不展示本金赠金拆分，不设专属储值码或线上退款。

## 6. 现有契约如何过渡

### 多档充赠的展示与办理

同一储值活动可以配置多档固定金额，不分别建立三场活动或三个账户：

| 实收 | 活动赠送 | 到账合计 |
|---|---|---|
| 50元 | 10元 | 60元 |
| 100元 | 30元 | 130元 |
| 200元 | 50元 | 250元 |

配置页可增加/删除档位，实时计算到账合计；确认页列出全部档位。活动发布冻结版本和各tierNo；办理时选择一档，赠送自动带出，提交实际收款金额须与所选档位一致。一次办理仅选择一档，不叠加，不把“充100送30”理解为“满100就送30”；150元不自动命中100元档。无促销的任意金额充值走获准的普通充值规则。

校验：至少1档、最多50档；实收大于0、赠送不小于0、最多两位小数、实收金额不重复。普通储值档位赠送固定为0。原型已演示三档配置、确认与办理选择，100元档对应实收100、赠送30、到账130；重复实收档位被阻止。该规则仍归活动，不把赠送策略复制到独立账户中。

当前 `/biz/stored-value/recharges` 强制 activityNo/versionNo/tierNo；不存在独立“基础充值方案”API。因此原型中的独立方案与普通办理是建议产品设计，不能直接宣称已接通。

近期可由系统维护零赠金的常规规则版本，办理时冻结来源，不要求商家在活动列表手动建一场“普通储值促销”。后续再评审独立基础方案、普通充值来源类型以及发布活动引用方式；沿用现有Pay账户、借贷分录、幂等与冻结来源，不能仅在UI隐藏必填参数或伪造版本。

模板/基础方案更新只影响未来使用；活动引用固定版本，已获得权益按原快照执行。原型没有决定活动可以直接覆盖已发布版本。

## 7. 原型功能矩阵与验收

| 屏 | 覆盖内容 |
|---|---|
| s01–s07 | 营销入口、统一活动列表、大类、预置/自定义、引用配置、确认、活动详情 |
| s08–s10 | 独立卡券模板、模板定义与直接/活动发放的关系 |
| s11–s14 | 独立储值管理、基础方案、账户流水、普通与活动充值 |
| s15–s18 | 拼团与集单的活动规则和实例管理分开，规则统一新建 |
| s19–s20 | 分项效果、工作台高频办理入口 |
| s21 | 活动暂停后既有账户/权益/履约仍可继续 |

可点击主链：新建储值活动→选预置→填写名称/规则→确认→演示发布；卡券管理→独立定义/发放→关联活动；储值管理→普通办理/活动办理→账户流水；拼团与集单→实例详情→来源活动；暂停活动→独立账户。所有数据为原型演示，不发送后台请求、不产生真实入账或发放。

本轮验证限定原型锚点、链接、表单校验、上述浏览器路径、原型登记及生成清单。不改业务代码，不重复运行既有Java回归。

验证记录：21屏锚点及所有静态页内链接通过；JS语法、原型登记与界面清单校验通过。浏览器实点营销→新建→储值类型→配置，空活动名被阻止；填写名称后确认及演示发布保留自定义名称和档位。普通/活动充值切换金额分别为1000/1000与1000/1200；团详情来源跳转显示拼团规则而非储值规则。原型只修改浏览器内演示状态。
