## 一、先看清全貌：两条并行的主路径，不是一条直线

「注册 → 进件」不是一根流水线。落到代码里是**两条各自独立、可先可后的路径**，
在「主体转 ACTIVE」这一点合流：

```
                          ┌───────────────────────────── 路径 A：快速开店（无证照）─────────────────────────────┐
  N0 注册/登录 ──┬──────► N1 quickStart ──► 建 PENDING_LICENSE 占位主体 + 默认门店（无社区、无进件占位）
  (B端账号)      │          店先开起来：录商品/配范围/加员工/印店铺码，但【买家看不到、下不了单】
                │                                             │
                │                                             └────────► 补证照 ──┐
                │                                                                  │（同一份申请，activatedEntityNo 指向占位主体）
                │       ┌──────────────────────────── 路径 B：入驻审核 ───────────┼──────────────────────┐
                └──────►│ N2 提交入驻申请 ──► N3 平台受理 ──► N4 审核(通过时定服务范围) ──► N5 激活派生 ─┼──► 主体 ACTIVE
                        │  /biz/merchant/apply      /accept          /audit(approved)      activate()      │   （合流点）
                        └───────────────────────────────────────────────────────────────────────────────┘
                                                                                                            │
                                                             ┌──────────────────────────────────────────────┘
                                                             ▼
  N6 进件（收款开户）：submit ──► 通道回执/回查 refresh ──► 写 sub_mchid + pay_merchant_no ──► 【能收钱】
                                                             │
  N7 门店管理：默认店已有 → 改资料/服务范围/店铺码/新建门店/换收款号  ◄──────────────────────────────────┘
  N8 三段状态总览：能开张吗(主体 ACTIVE) · 能收钱吗(进件 ACTIVE) · 能被看到吗(服务范围非空)
```

**三段各自可失败、可重试，B 端必须分段展示，不能合成一个「入驻中」进度条**：

| 段 | 完成的标志（可判据） | 卡住时的真实表现 |
|---|---|---|
| 入驻/开张 | `mch_entity.status = ACTIVE` | —— |
| 进件/收款 | `mch_payment_merchant` 有 `pay_merchant_no` 且 ACTIVE | 店能开、货能上架，**收不了钱**，且无报错 |
| 建店/可见 | `mch_entity_community` 非空（服务范围有社区） | 店开着、货在架，**对谁都不可见**，且无报错 |

### N5 · 激活派生（同一事务，合流点）

`OpsServiceImpl.auditApply(approved=true)` → `MerchantPortImpl.activate(ActivateCommand)`，
`@Transactional`，派生失败整体回滚：

| 派生物 | 规则 | 代码 |
|---|---|---|
| 主体 `mch_entity` | 一份申请一个主体；`status=ACTIVE`、`verified=true`、评分取中位初值 | `activate()` |
| owner 员工/账号 | 用申请里的 `contact_phone` | `ensureOwnerStaff()` |
| 默认门店 `mch_store` | `is_default=1`，名称默认取店铺名 | `ensureDefaultStore()` |
| FREE 订阅 `mch_entity_plan` | 门店额度起点 | `ensureFreePlan()` |
| 服务社区 `mch_entity_community` | 单一写入口，与店铺设置共用 | `syncCommunities()` |
| 进件占位 `mch_payment_merchant` | `apply_status=APPLYING`，通道 WECHAT | `ensurePayment()` |

> ⚠️ **`cmt_pickup_point` 不在这里派生（与早期文档不符）**：`asPickupPoint` 只写在申请单上、
> 在 VO 里回显，`activate()` **不建**自提点。自提点仅由平台社区管理侧创建
> （`CommunityAdminServiceImpl.createPickup`，`/ops/...`）或种子。旧文档「勾了才建自提点」在激活事务里**未实现**。

**两个关键判据（均已修 + 有回归用例）**：

- **`COMMUNITY` 却零社区 → 直接拒绝激活**，不「先建了再说」（否则产出隐形商家，ADR-009）。`activate()` line 828。
- **幂等按 `activatedEntityNo`**：非空即重放/升级这份申请，为空一律新建。老板申请第二张执照通过时不会再去改第一个主体。`activate()` line 840。
- **补证照升级支**：`PENDING_LICENSE` 占位主体转 ACTIVE 时，回填正式名称/法律形态/认证标，并 `storeShelfPort.resyncPools()` 重建社区池 —— 否则补齐证照后那批货仍对买家不可见。`activate()` line 858/888。
