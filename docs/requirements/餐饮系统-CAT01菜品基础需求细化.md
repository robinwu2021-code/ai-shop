## 一、目标与首次范围

在已有商品上维护餐饮展示与制作信息。基础商品拥有商品号、SKU、归属门店、基础图文、上下架、价格和库存；餐饮只拥有餐饮扩展及后续选配、餐牌、制作规则。同一菜品可以被多个餐牌引用，不复制一套商品。

本阶段覆盖API016维护餐饮属性、112列表、113详情。按“基础商品事实合同 → 维护及详情 → 列表查询”的顺序交付，每个切片单独验收。时段餐牌、口味组、收费配料、套餐、工位及真实交易沿CAT-02～08和订单阶段实现。

| 使用者 | 本阶段行为 | 范围 |
|---|---|---|
| 门店运营、获准商品管理员 | 选择已有商品，维护餐饮属性，查询配置 | 原主体及当前门店；写入沿原GOODS权限 |
| 收银、服务员及老板App | 复用B端菜品读取能力 | 原权限和门店范围；读配置不代表可点单 |
| 顾客H5、扫码、自助机 | 本阶段不开放草稿配置查询 | 后续沿已发布目录及会话范围读取 |
| 厨房端 | 后续读取订单冻结的制作快照 | 不因菜品配置修改而改写已受理批次 |
| 平台运营 | 沿既有平台权限诊断 | 不在本阶段增加跨主体编辑入口 |

## 三、数据和接口边界

### 3.1 菜品不是门店商品副本

`fnb_dish`现有唯一键为`goods_no`，没有`store_no`；`prd_goods.store_no`才是当前归属。API路径中的storeNo是授权上下文，不能直接当作fnb_dish查询条件，也不能给fnb_dish伪造一个不存在的门店列。不得仅校验主体相同便允许同主体跨店修改。

同一商品扩展与商品归属一同受权查询。商品跨店转移以后，旧门店立即失去编辑和读取权限；新的门店获准后可看到同一商品的餐饮扩展。已成交快照仍保留成交时归属。连锁共用配方/餐牌模板不等于让同一个商品同时属于多个门店。

### 3.2 维护输入与输出

沿API016既有目标字段，不在本次启动新增运行时接口：

| 输入 | 要求 |
|---|---|
| goodsNo / storeNo | 来自路径；基础商品权威核验当前主体和门店 |
| dishKind | SINGLE、BUNDLE或ADDON；配置类别不代表套餐/配料已可成交 |
| prepSeconds | 非负整数；不触发制作任务 |
| presentation | displayName、localizedNames、imageRefs、tags、allergenNotes；基础名称图片不在餐饮复制为权威 |
| measurement | unit、mode、scale、allowedDeviation；不能把SKU规格文字自动解释为计量合同 |
| version | 创建不传，修改必传；区分公共CAS版本与餐饮configVersion |
| Idempotency-Key | 写入必需；actor来自可信原登录上下文 |

输出沿Dish：goodsNo、dishKind、prepSeconds、presentation、measurement、configVersion、version。真实价格库存不放入餐饮扩展。媒体引用和语言/单位受控范围须沿平台已有目录核验；无可验证目录时先登记缺口，不自造“引用合法”成功结果。

### 3.3 配置、展示和交易分开验收

保存扩展不自动发布餐牌，不代表商品在所有终端可见。B端管理详情允许展示商品不可售原因；顾客目录仅展示获准发布配置与当前商品/时段的交集。基础商品可售也不代表套餐选配、称重、先吃后付等餐饮交易已经具备能力。

名称搜索须覆盖对端上实际显示名称的规则，不能将“名称”悄悄收窄为JSON别名，亦不能用内存过滤已分页结果伪造total。该查询合同在API112编码前定稿，先交付不依赖列表搜索的基础事实、维护和详情切片。

## 五、时段餐牌与配料套餐补充对齐

用户补充已纳入[增强方案E01～E06](../technical/TDD-餐饮系统-餐牌选配套餐与耗用增强方案.md)：早餐/午餐/晚餐及自定义/外送餐牌、渠道差异价格与选配、奶茶小料、套餐和菜品/原料消耗。CAT-01A已实现的基础事实查询保持不变；CAT-01B/C仍负责菜品基础，不独自承载所有组合交易。

后续编码前先核定餐牌条目覆盖、价格策略、配方单位/估值及制作扣料合同。配料配置必须区分免费口味、收费SKU和实际物料；不得把收费与库存塞进基础属性值或presentation JSON。餐饮配方和耗用编排可扩展独立表及包，但不复制商品、核心订单、库存账或价格权威。
