# PRD · 会员消息送达小程序买家

> 状态：草稿（2026-09-19，待拍板 §八）

## 一、一句话

**商家给会员发的消息，今天一个买家也收不到** —— 买家都在微信小程序里，而会员消息只走个推（原生 App）。
这份需求决定：哪些消息该通过什么渠道送到小程序买家手里，买家在什么时刻同意，以及做不到的那部分怎么如实告诉商家。

## 二、现状（2026-09-19 生产实查）

| 事实 | 数据 |
|---|---|
| 买家推送设备（`notify_push_token.receiver_type=USER`） | **0** 台；唯一一台是商家员工的安卓机 |
| 有小程序 openid 的用户（`usr_identity.WX_OPENID_MP`） | 1 个（真实 openid 格式）—— 小程序还在体验版，买家尚未进来 |
| 订阅消息模板（`WX_TPL_ORDER_ARRIVED` / `WX_TPL_REFUNDED`） | 均为空；同意记录 `notify_subscribe` 0 行 |
| 订阅消息底座 | 已建好：一次同意 = 一次额度、先扣额度后发送、失败静默回落站内信、运营端可改模板 id（见上游 TDD） |
| 会员消息的发出数 | 批 C 补丁后如实：所有买家落在「只用小程序，暂时收不到消息」，能发 0 人 |

**结论：通道与底座都在，缺的是三样东西 —— 小程序正式版（有买家）、订阅消息模板（审核通过）、会员消息接到这条通道上。**

## 三、硬约束：订阅消息不能用来做营销

微信的订阅消息规则（运营规范）要求模板内容与用户的**具体服务**相关，**不得用于营销推广**；
违规会被限制模板乃至接口能力。本项目的小程序已经有过一次「类目问题导致微信支付被限制、至今要人工申诉」的前车，
**这条线上不能再冒平台处罚的险**。

据此把三个触达场景分开看：

| 场景 | 内容性质 | 能否走订阅消息 |
|---|---|---|
| `COUPON` 发券通知 | 「你的券包里多了一张券」—— 账户变动，有具体服务对象 | **可以**（选「优惠券到账提醒」类服务模板，只写券名、面额、有效期，不写促销话术） |
| `NOTICE` 店铺公告 | 上新、调营业时间 | **营业时间 / 暂停营业可以**（与已下单或常去的服务相关）；**上新、促销不可以** |
| `WAKEUP` 唤回 | 「好久没来了」 | **不可以** —— 这就是营销 |

> ⚠️ 以上是按规则文字的理解，模板申请时以微信审核结果为准。拍板前建议在小程序后台的模板库里实际搜一遍，确认有可用的服务类模板。

## 四、要做的事

### B1 前置：小程序正式版与模板（不在本 PRD 范围内做，但本 PRD 依赖它）
小程序从体验版转正式版、有真实买家；订阅消息模板在小程序后台申请并审核通过，
模板 id 同时配进后端 `WX_TPL_*` / `sys_setting` 与端上 `VITE_WX_TPL_*`。
没有这一步，B2 以后都发不出去。**正式版由负责小程序上线的那条线推进。**

### B2 发券通知走订阅消息
- 新模板场景 `COUPON_RECEIVED`（「优惠券到账提醒」）：后端 `WxSubscribePort` 加一个场景与发送方法，
  模板 id 同样进 `sys_setting notify.wx.templates`，与端上构建变量一致（沿用上游 TDD 的规矩）。
- 商家「发券」之后，对**有该模板额度**的买家发一条；没额度的只进券包（今天的行为）。
- 发券结果页与「发出去的」如实分开写：**发出 N 张 · 其中 M 人收到提醒**。

### B3 买家在什么时刻同意（一次同意 = 一次额度）
订阅消息要买家**主动点「允许」**，而且一次同意只够发一条。同意时机决定了额度有多少：

| 时机 | 为什么 | 一次最多申请 |
|---|---|---|
| 支付成功页（已有，今天申请「到达自提点」） | 买家刚完成一单，最愿意点允许 | 同一次弹窗最多 3 个模板，**把「优惠券到账」加进去** |
| 领券 / 进店页「有券时提醒我」开关 | 主动表达意愿，转化最高 | 1 |
| 会员页「本店消息」开关（已有退订开关） | 与退订在同一处，买家看得懂 | 1 |

**不在打开小程序时就弹**：没有上下文的授权弹窗拒绝率最高，而拒绝之后同一模板在「总是保持以上选择」下再也弹不出来。

### B4 公告与唤回：不推送，如实告诉商家
- `NOTICE` 中「营业时间变动 / 暂停营业」：可走订阅消息（需另一个服务类模板），**只给近 30 天下过单的会员**。
- `NOTICE` 上新 / 促销、`WAKEUP` 唤回：**只进小程序站内信**（买家下次打开能看到；店铺页顶部红点）。
  发消息页把「推送送达」与「站内信」分开：`能推送 0 人 · 进站内信 25 人`，**不再把站内信算进「发出」**。
- 商家侧文案要说人话：「小程序的规则不允许推送营销消息，这条会放进顾客的消息列表，他下次打开时能看到。」

### B5 效果回看沿用批 C
点订阅消息跳到店铺页并带 `reach=`（订阅消息的 `page` 字段即可带参数），「进店 / 成单」回写不用改。
站内信点开同样带 `reach=`。

## 五、验收

| # | 验收 |
|---|---|
| AC-1 | 买家在支付成功页允许「优惠券到账」后，商家给他发券 → 他的微信服务通知里收到一条，点开落在该店的券包 / 店铺页 |
| AC-2 | 没有额度的买家：券照常进券包，发券结果页把他算在「未收到提醒」里 |
| AC-3 | 商家发「唤回」：发消息页显示「能推送 0 · 进站内信 N」，确认后买家小程序消息列表里有这条，**微信服务通知里没有** |
| AC-4 | 同一买家额度用完后，第二次发券不再尝试发订阅消息（不产生失败日志刷屏） |
| AC-5 | 从订阅消息 / 站内信点进店后下单，效果页「进店 / 成单」各 +1（沿用批 C 的回写） |
| AC-6 | 运营端改了模板 id 而端上构建变量没改 → 有闸门或体检能报出来（上游 TDD 反复警告过的缝） |

## 六、明确不做

- 不用订阅消息发任何促销、上新、唤回内容（§三）。
- 不接公众号模板消息 / 服务号（要另开公众号并绑定，另议）。
- 不做短信触达（成本与合规另议）。

## 七、分批建议

| 批 | 内容 | 依赖 |
|---|---|---|
| 0 | 小程序正式版 + 模板申请（B1） | 小程序上线那条线；模板需管理员在后台申请 |
| 1 | 站内信承接公告 / 唤回 + 发消息页「推送 / 站内信」分开计数（B4 后半） | 无（今天就能做，不依赖微信） |
| 2 | 发券通知走订阅消息 + 三个同意时机（B2、B3） | 批 0、模板审核通过 |
| 3 | 营业时间类公告走订阅消息（B4 前半） | 批 2 |

**批 1 不依赖微信，建议先做**：它让「发消息」这个功能今天就有一个真实的落点，而不是能发 0 人。

## 八、待拍板

1. 规则理解是否认可：公告里的上新 / 促销与唤回**只进站内信、不推送**。
2. 小程序正式版（批 0）什么时候发。
3. 模板申请：「优惠券到账提醒」「营业时间变更」两类，是否由你在小程序后台申请（需要管理员扫码）。
4. 先做批 1（站内信）是否同意。
