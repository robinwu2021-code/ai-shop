## L1 · 一句话

**支付域回答一件事：买家付的钱，怎么在合规的前提下，准时、准确、可追溯地到商家手里。**

它不负责「卖什么」「怎么送」，只负责钱。
边界的判据是：**这件事错了会不会直接损失金钱** —— 会，就在域内；不会，就不在。

## 1. 范围

### 1.1 在里面

| 能力 | 一句话 |
|---|---|
| **进件** | 商家在通道开通二级商户，拿到收款资格 |
| **收单** | 买家付款：调通道下单、收回调、落流水 |
| **结算** | 按子单生成结算单，算清佣金 / 服务费 / 手续费 / 实得 |
| **账期与放款** | 按账期成批，过三道对账门才放行 |
| **分账 / 应付** | 第三方走分账，自营走应付账款 |
| **退款与追偿** | 按钱在哪分四个时区处理；追不回走保证金与欠款 |
| **对账** | 四条轴，A 侧自查 + B 侧与对方账单比对 |
| **发票** | 进项票核验、销项票开具 |
| **积分** | 积分账户、流水、积分池与它的恒等式 |
| **资金风控** | 三个拦截点（见 [PRD-资金风控](./PRD-资金风控.md)） |

### 1.2 不在里面（明确不做）

| 不做 | 理由 |
|---|---|
| **平台提现**（商家从平台余额提钱） | 二清。ADR-002 §2 已排除，`stl_withdraw` 只是过渡账本，不补商家申请入口 |
| **C 端钱包与提现** | ADR-004 已删除；C 端不存在逐单抽佣，没有可提现收入 |
| **平台垫付** | 见 [账期方案 §三](../technical/design/账期与对账放款-方案.md)。垫了账上就没有边界，且追偿的紧迫性会消失 |
| **非资金风控**（内容 / 账号 / 刷单） | 留在既有风控域，见 ADR-022 §3.5 |
| **分账参数的技术兜底** | 拿不到书面口径就不接。猜一个限额去试，第一次撞上限的是真实商家的真实货款 |

## 2. 角色

| 角色 | 在这个域里做什么 | 最怕什么 |
|---|---|---|
| **买家** | 付款、申请退款 | 付了钱订单没生效；退款不知道退到哪了 |
| **商家** | 进件、看账、开票 | **不知道钱在哪、什么时候到**；被无解释地冻住 |
| **运营 · 财务** | 对账处置、应付付款、发票核验、放款复核 | 账对不上而说不清差在哪 |
| **运营 · 风控** | 处置挂起、名单、追偿 | 队列积压成常态而没人知道 |
| **通道** | 审进件、收付款、执行分账、出账单 | —— 我方只能查，不能判 |

> **商家那一栏是这个域的产品重心。**「钱在哪、什么时候到」今天在界面上答不出来：
> 结算页显示 `netMinor` 读起来像已到手，而实际上第三方的单永远停在 `PENDING`。

## 3. 主场景与验收

### S1 · 进件：商家开通收款

```
选通道 → 填资料（结算账户 / 联系人 / 证照）→ 提交 → 通道审 → ACTIVE / REJECTED
```

| # | 验收 |
|---|---|
| AC-1.1 | 商家能看到**能开的全部通道**，含还没开的（不是只列已开的） |
| AC-1.2 | 缺什么资料**逐条列出**，不是笼统的「资料不全」 |
| AC-1.3 | 「待补资料」与「审核中」在界面上是**不同的状态**——前者要他动手，后者只需要等 |
| AC-1.4 | 驳回原因原样展示，不做二次加工 |
| AC-1.5 | 状态变更**不依赖商家手动刷新**（回调或轮询任一） |
| AC-1.6 | 同一主体可同时开多个通道，各自独立进件、独立状态 |

> AC-1.1 / 1.2 / 1.3 / 1.4 / 1.6 **已实现**（2026-08-30）。AC-1.5 未做。

### S2 · 收单：买家付款

```
下单 → 选通道与支付方式 → 调通道下单 → 用户付 → 回调 → 订单置已付 + 生成结算单
```

| # | 验收 |
|---|---|
| AC-2.1 | 可选通道**按环境裁剪**（主体形态 × 端 × 市场），不可用的不展示 |
| AC-2.2 | 下单**必带分账标识**，缺失即拒绝下单（不是记日志）——漏传事后无法补 |
| AC-2.3 | 回调**验签通过才处理**，验签失败不泄露原因 |
| AC-2.4 | 回调**幂等**：重投不重复扣库存、不重复生成结算单 |
| AC-2.5 | 回调丢失时，**主动查单**能把状态补齐（不能只等回调） |
| AC-2.6 | 支付流水与订单**双向可查**：给订单号能找到流水，给通道单号也能找到订单 |

> AC-2.3 / 2.4 **已实现**。AC-2.1 部分。**AC-2.2 / 2.5 未做，且 2.2 是红线**。

### S3 · 结算：算清这一单的账

| # | 验收 |
|---|---|
| AC-3.1 | 一子单一张结算单，**靠唯一索引**保证，不靠应用层判断 |
| AC-3.2 | 恒等式成立：`基数 = 佣金 + 服务费 + 积分费 + 通道手续费 + 实得` |
| AC-3.3 | 费率、通道费率、经营模式、收款号**全部落快照**——配置会变，历史账不能跟着变 |
| AC-3.4 | 佣金基数 = 扣完通道手续费后的金额 |
| AC-3.5 | 手续费**没配过就留空**，不兜 0 —— 「没配过」与「配了 0%」必须分得开 |
| AC-3.6 | 线下（当面）收款单落终态，不抽佣、不分账，但**让掉多少要记下来** |

> **AC-3.1 / 3.3 / 3.4 / 3.5 / 3.6 已实现**（3.4 / 3.5 于 2026-08-30）。AC-3.2 未做（门 1）。

### S4 · 账期与放款

```
T2 可结算 → 入批 → T3 应结日截批 → 三道对账门 → RELEASED → 逐单发指令
```

| # | 验收 |
|---|---|
| AC-4.1 | 商家能看到每一笔的**预计到账日**，不是只看到一个金额 |
| AC-4.2 | 账期规则可按主体配置，**上限受通道 `settle_cycle` 约束**，取更短的那个 |
| AC-4.3 | `T3 + 余量 < Tmax`（通道冻结窗口）在配置时**就校验**，不是到期才发现 |
| AC-4.4 | 单据级差异只挂该单，**批次级差异挂整批** |
| AC-4.5 | 仅通过 A 侧自查的批次，界面上**如实标注**，不显示成「已对账」 |
| AC-4.6 | 冻结窗口到期前必须已发起；到期未发起落 `FROZEN_BACK` 并**告警** |

> **全部未做。** 这是本期的主体工作量。

### S5 · 退款

| # | 验收 |
|---|---|
| AC-5.1 | 按**钱在哪**（四个时区）选路径，不按时间长短 |
| AC-5.2 | 分账回退**失败必须阻断退款**，不能钱已给商家还退给买家 |
| AC-5.3 | `split_reversible = 0` 的商家**不许进入 Z3**（已解冻未提走） |
| AC-5.4 | Z4（已提走）走追偿三层：保证金 → 欠款抵扣 → 停止放款转人工 |
| AC-5.5 | 买家侧不因追偿失败而拿不到钱——走售后裁决，与追偿是两条链路 |

> AC-5.2 已实现（`reverseSplit` 返回 false 时调用方停止退款）。其余未做。

### S6 · 对账

| # | 验收 |
|---|---|
| AC-6.1 | 四条轴各自独立，**各说各的覆盖范围** |
| AC-6.2 | 每一类对账都写明**查不了什么**——否则「今天没有差异」是句假话 |
| AC-6.3 | 线下单**排除在通道对账之外**，混进去就是永久无解差异 |
| AC-6.4 | `CHANNEL_ONLY` / `PLATFORM_ONLY` 可自动处置（查单补记 / 关单）；`AMOUNT_DIFF` **必须人工** |
| AC-6.5 | 每一分钱可追溯到**指令与回执** |

> AC-6.1 / 6.2 / 6.3 已实现。AC-6.4 / 6.5 未做（B 侧全缺）。

### S7 · 发票

| # | 验收 |
|---|---|
| AC-7.1 | 进项票抬头与主体名不一致**不给核验**，且界面要说清是这个原因 |
| AC-7.2 | 企业抬头必须有税号；开票额不得超过已结算额；已开票的不能再开 |
| AC-7.3 | 无票供应商要在应付列表上**标出来**，让财务付款前就看见 |

> 全部已实现。

### S8 · 积分

| # | 验收 |
|---|---|
| AC-8.1 | 积分池恒等式：`池子余额 == 流通中积分 × 汇率 + 已扣未兑付` |
| AC-8.2 | 恒等式失衡要**主动开口**，不能等人去看 |
| AC-8.3 | 待生效积分（售后期内）不计入可用余额 |
| AC-8.4 | 抵扣的成本落哪一列**取决于资金路径**：直连补差、归集只记账 |

> 全部已实现。AC-8.2 于对账第四轴接入后成立。

## 4. 非功能要求

| 类 | 要求 | 为什么 |
|---|---|---|
| **幂等** | 所有对外指令带平台侧幂等号，重复下发不产生第二笔 | 回调与事件都会重投 |
| **可审计** | 账**只增不改**：改费率是加版本，改状态是加流水 | 「当时按什么算的」必须答得出 |
| **可解释** | 每一个拒绝 / 挂起都要能对当事人说出人话 | 说不出的话，申诉链路就是死的 |
| **时效** | 回调处理 < 3s；对账扫描 ≤ 10 分钟一轮；挂起处置有时限 | 时效不是性能指标，是**信任指标** |
| **降级** | 支付域不可用时，依赖它的链路要**明确报错而不是挂起** | 挂起最难排查，且用户会重复提交 |

## 5. 与今天的差距

按 [资金链路-三方对齐](../technical/design/资金链路-三方对齐.md) 的实测：

| 场景 | 已实现 | 缺 |
|---|---|---|
| S1 进件 | 5 / 6 | 状态自动推进 |
| S2 收单 | 2 / 6 | **下单发起是桩**、分账标识、主动查单 |
| S3 结算 | 5 / 6 | 恒等式自查 |
| S4 账期放款 | 0 / 6 | **全部** |
| S5 退款 | 1 / 5 | 四时区、追偿 |
| S6 对账 | 3 / 5 | B 侧、自动处置 |
| S7 发票 | 3 / 3 | — |
| S8 积分 | 4 / 4 | — |

**S4 是本期主体，S2 的两条卡在真实商户号，S6 的 B 侧卡在通道账单下载能力。**
