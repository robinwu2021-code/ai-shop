# 餐饮后端业务模块功能清单

> 状态：待评审 · 2026-10-20 · 功能分解，不代表已实现。
> 依据：[完整需求](./餐饮系统-完整需求文档.md)、[需求矩阵](./餐饮系统-需求矩阵.md)、[后端开发计划](../technical/TDD-餐饮系统-后端开发计划.md)。
> 本册调整开发组织方式：按业务模块推进，主线先“桌台 → 菜品餐牌 → 点餐订单”，不按技术层或终端分别开发。需求原FNB编号不变，每项指定唯一主责模块；跨模块依赖协作实现。

> 对齐结果：[数据库/API评审记录](../technical/TDD-餐饮系统-数据库与API评审对齐.md)；综合设计现为79张候选表、141个目标端点。原001–091编号保留，新补092–141；本册各模块原API范围是基线索引，完整追踪以API册第八节逐需求表为准。

> 代码落点：[按业务模块代码清单](../technical/design/餐饮系统-按业务模块代码清单.md)。API/表的主责、复用及新增修订分别登记，不能把关联数量当新增数量。

## 一、如何逐模块交付

每个模块先确认本册功能清单，再收敛状态/规则、表与接口、类清单、测试，最后交付可独立验收的后端业务切片。涉及其他模块时先确认边界并交付所需最小合同；完整营业链路在相关模块汇合后验收，不用Mock替代真实资金或核心联通验收。

模块编号是业务目录顺序，不是要求串行等待全部功能完成。桌台完成基础验收后即可进入菜品模块，桌台的订金等跨模块扩展待收银能力具备后补齐。权限、幂等、双部署及营业日规则先做最小前置支撑，随后贯穿各模块。

| 主线顺序 | 模块 | 主责范围 |
|---|---|---|
| MOD-01 | 桌台与就餐管理 | 桌区、桌台、座位、桌码、占用、就餐台账、预约排队；不负责资金拆合账。 |
| MOD-02 | 菜品与餐牌管理 | 引用基础商品/SKU，管理餐饮属性、餐牌、口味、套餐、配料组合、可售及制作路由。 |
| MOD-03 | 点餐与订单管理 | 管理草稿、点餐批次、餐饮源行、核心订单绑定、受理与恢复；支付资金属于模块05，制作属于模块04。 |
| MOD-04 | 厨房与履约管理 | 从已受理点餐批次生成制作任务，负责工位、数量、道次、出品、上菜与交接。 |
| MOD-05 | 收银与结账管理 | 管理应收范围、预结冻结及核心收款编排；持有资金分配的权威仍为核心。 |
| MOD-06 | 退餐与售后管理 | 统一退餐申请、审批、制作撤回、应收调整、退款与恢复，不覆盖历史成交。 |
| MOD-07 | 打印、通知与设备管理 | 冻结餐饮票面，复用共享打印投递、通知订阅与设备治理。 |
| MOD-08 | 班次与现金管理 | 管理钱箱责任、开交班、备用金、非销售收支和现金盘点。 |
| MOD-09 | 营业日、日结与对账管理 | 以营业日和资金水位编排预结、对账、签核、例外结转与更正。 |
| MOD-10 | 经营报表管理 | 消费交易、资金、桌台、制作、班次与日结投影查询、分析、导出。 |
| MOD-11 | 专项业态管理 | 基于通用桌台、菜品、订单扩展宴会、自助放题、寄存、房账等。 |
| MOD-12 | 第三方接入与离线营业 | 对外映射、同步恢复、边缘单写者及运行保障。 |
| MOD-13 | 营业配置与权限治理 | 复用项目身份门店，提供餐饮策略、日历、能力模板和高风险授权。 |

普通零售商品分类不替代餐饮餐牌；就餐台账不替代核心订单；拼桌、并桌不等于合账付款；打印成功不代表制作或资金成功。所有模块共用当前账号、主体、商户、门店、商品、交易和支付底座。

## 二、前三个模块的具体工作项

### MOD-01 桌台与就餐：先交付桌台业务

| 工作项 | 功能与规则 | 首次验收 |
|---|---|---|
| 桌区和桌台配置 | 大厅/包间分区；桌号、名称、排序、容量、启停用；有效占用期间限制停用/归档 | 同门店桌号不重复，跨主体引用拒绝 |
| 桌台查询 | 按门店、桌区、可用/占用/待清理等资源状态筛选；展示人数和关联台账 | 桌台状态与支付状态分别展示，不用“已付款”代替占用状态 |
| 桌码生命周期 | 生成、轮换、吊销；短会话绑定获准桌台/台账和有效期 | 旧码失效，扫码不暴露同桌其他独立台账隐私 |
| 开台与人数座位 | 人数、座位、服务员/操作人、开始时间；支持无桌快餐 | 并发开台不超容量，不为无桌订单伪造桌号 |
| 占用和就餐台账 | 桌台1:N台账用于拼桌，台账1:N桌台用于并桌；明确占用仲裁者 | 占用唯一性/容量以数据库并发测试证明 |
| 转台 | 校验目标桌容量、先占后放，记录原桌和目标桌 | 失败保留可恢复的原占用，不丢正在服务的台账 |
| 拼桌与并桌 | 拼桌各自点单结账；并桌保持同一就餐台账 | 不迁移已发生交易/资金，不自动合账 |
| 清台与异常 | 记录清台、释放占用、跨日占用巡检；有未结款或任务时按权限保留异常 | 清台不删除应收、订单和制作任务 |
| 预约及排队扩展 | 预约时段/人数/包间、到店转开台、取消爽约、排队叫号；订金与预点菜只持相应引用 | 预约草稿不提前造交易；排队号不等于取餐号 |
| 操作历史 | 开转并拼清台、座位和人数变更记录真实操作人 | 跨门店访问与越权变更拒绝 |

**首次完成边界：** 桌区桌台配置、查询、桌码、开台/人数、占用、清台及审计。转并拼桌和预约排队按后续切片逐项验收；桌台查询若超出现有API草案，先补设计源，不能认为原建桌接口已覆盖全部管理功能。

### MOD-02 菜品与餐牌：再交付可配置、可校验的菜品体系

| 工作项 | 功能与规则 | 首次验收 |
|---|---|---|
| 菜品基础信息 | 引用商品/SKU；餐饮展示名、图片、别名、多语言、标签、过敏提示 | 不复制商品价格库存真源，改名不影响旧单快照 |
| 餐牌及内部分类 | 早餐/午市/晚市/节日/堂食/外带等多餐牌，餐牌内分类和排序 | 同菜可进多个餐牌，不强迫基础商品分类随餐牌变化 |
| 适用与发布 | 门店、终端/渠道、时段/日期例外、草稿/发布版本、连锁下发和门店差异 | 生效范围可解释，发布不覆盖历史订单 |
| 口味做法 | 复用属性字典，菜品绑定口味组；必选/默认/互斥/数量限制 | 服务端提交再校验，非法选配拒绝 |
| 收费配料 | 基础SKU引用、可用菜品范围、数量和单位、价格引用 | 价格通过核心报价，不接受终端覆盖 |
| 配料组合 | 选择组、组合层级、半份/双拼、默认数量、总量限制 | 循环引用拒绝，数量单位可计算 |
| 套餐 | 固定/可选套餐、子组、替换、补差、组件和分摊规则 | 配置完整；核心报价/库存未支持前禁售该能力 |
| 工位和制作路由 | 工位、SKU/菜品路由、跨工位套餐规则 | 无路由可诊断，派工由厨房模块消费 |
| 可售与沽清 | 上下架/库存/餐牌时段/接单策略交集；每日配额、停售和恢复 | 恢复沽清不修改实物库存，下单前重新校验 |
| 价格费用与称重 | 场景/餐段价格引用、茶位锅底包材服务费、低消、称重/允差 | 规则可配置，成交金额及计量必须由权威核心支持 |
| 导入导出及目录 | 批量预检/错误明细、按端输出可售目录 | 非法SKU和跨主体引用拒绝，终端共用同一规则 |

**首次完成边界：** 基础菜品、餐牌分类/时段发布、口味、工位、沽清和目录查询。套餐配料组合需要完整功能清单和配置模型，收费、称重及交易展开在核心合同通过后单独验收。

### MOD-03 点餐与订单：随后交付同一套点餐业务

| 工作项 | 功能与规则 | 首次验收 |
|---|---|---|
| 点餐入口与身份 | 收银/服务员代点、扫码/H5/小程序、点餐机；区分操作人、买家、付款人 | 终端来源不决定支付/履约模式，设备不冒充员工 |
| 购物车 | 建草稿、直接加购、增减数量、改口味配料、移除、座位/人归属 | 同桌并发可识别版本冲突，草稿删除不取消正式订单 |
| 报价及确认 | 菜品、套餐、配料、费用、优惠、计量、可售版本；价格变化重新确认 | 后端校验选择和核心报价，不信任客户端金额 |
| 提交与稳定行 | 一次提交一个批次，源行号、配置及报价快照、核心订单/行绑定 | 同SKU不同做法可分辨，数量金额分配守恒 |
| 幂等与恢复 | 同键查原单，超时/处理中明确状态，绑定失败恢复 | 重试不重复建单、锁库存、扣款或派工 |
| 加菜 | 同台账追加新批次，保留原批次和成交快照 | 提交只清理此次草稿，不丢其他人未提交菜 |
| 先付后吃 | 核心权威确认已付后受理，支付/取消竞争按核心结果收敛 | 未付不派工；收银能力未交付时只验收待支付订单 |
| 先吃后付 | 获准受理、库存承诺、派工、后续收款；禁止沿普通待支付超时取消 | 后付合同未齐时门控关闭，不靠延长支付时限替代 |
| 查询与状态 | 按门店/台账/批次/来源/制作/支付状态查询，展示异常和操作历史 | 餐饮受理、厨房制作和核心资金状态分列 |
| 取消、赠换与改菜 | 草稿编辑、正式取消、退餐/换菜/赠送分别处理，差价和授权可追踪 | 不直接覆盖成交价；制作后通过售后与厨房协作 |
| 定时和跨日 | 预订外带、截止规则、预约生产、营业归期 | 预点草稿与已受理制作分开，归期不随查单日期漂移 |

**首次完成边界：** 多来源草稿、基础SKU报价、正式批次、稳定行绑定、查询、加菜及幂等恢复；联通核心后验证真实建单。先付/后付、复杂收费和取消退餐由所属模块合同共同验收，不能只通过Mock就宣称可营业。

## 三、全部模块功能条目与验收结果

以下109项均指定一个主责模块；关联模块共同实现但不重复记完成。API编号均指现有目标设计，端点之外的缺口须先修订设计源及输入输出，不机械认为原基线91个端点覆盖全部管理操作。

### MOD-01 桌台与就餐管理

**边界：** 桌区、桌台、座位、桌码、占用、就餐台账、预约排队；不负责资金拆合账。

**服务落点：** TableService、DiningSessionService、CheckService、ReservationService。**目标API索引：** 024–036（C07结账动作由模块05完成；排队/订金按共享合同补充）。

**交付切片：** 开台、人数座位、占用与清台先交付；预约、排队、转并拼桌逐项补齐；订金依赖模块05。

| 需求编号 | 功能清单 | 最低验收结果 |
|---|---|---|
| FNB-A04 | 桌区、桌台、座位与桌码生命周期 | 桌码可吊销且不能泄露其他台账 |
| FNB-C01 | 预约人数、时段、包间与预点菜 | 预点菜草稿不提前生成消费交易订单 |
| FNB-C02 | 订金、预付款与取消爽约规则 | 订金与消费款可核销并能处理退款与没收审批 |
| FNB-C03 | 排队取号、过号、叫号与通知 | 排队编号与自取取餐号分开 |
| FNB-C04 | 预约到店转开台与资源接力 | 新占用失败可恢复原预约不丢资源 |
| FNB-C05 | 开台、人数、座位编号与多人会话 | 并发开台不重复占用且支持无桌快餐 |
| FNB-C06 | 拼桌分账、并桌用餐与转台 | 桌台关系变化保留原交易资金归属 |
| FNB-C08 | 清台与跨日占用巡检 | 清台不删除未收应收和未完成任务 |

### MOD-02 菜品与餐牌管理

**边界：** 引用基础商品/SKU，管理餐饮属性、餐牌、口味、套餐、配料组合、可售及制作路由。

**服务落点：** DishService、MenuService、OptionGroupService、ModifierService、BundleService、StationService、KitchenRouteService、SalesRestrictionService。**目标API索引：** 004–023。

**交付切片：** 先基础菜品、餐牌、时段、口味、工位、沽清，再套餐/配料组合/称重等复杂规则；收费规则通过核心报价合同后才允许销售。

| 需求编号 | 功能清单 | 最低验收结果 |
|---|---|---|
| FNB-B01 | 商品SKU、规格与门店上下架 | 复用基础商品与价格不复制成交真源 |
| FNB-B02 | 餐牌分类、时段、节日与渠道可见 | 餐牌与上架库存求交且提交重新校验 |
| FNB-B03 | 口味、禁忌、做法及过敏信息 | 选择结构化并冻结且过敏信息不承诺医疗安全 |
| FNB-B04 | 必选任选组、互斥默认与数量上限 | 校验组及选项数量不允许客户端绕过 |
| FNB-B05 | 固定套餐、可选套餐、替换与补差 | 父子价格分摊和库存展开只计算一次 |
| FNB-B06 | 配料SKU、配料组合与双拼半份 | 组合数量单位明确且限制循环引用 |
| FNB-B07 | 堂食外带外卖价与餐段价格 | 报价保留命中规则版本且不覆盖原成交价 |
| FNB-B08 | 沽清、每日配额与限量预售 | 沽清恢复不回填物理库存 |
| FNB-B09 | 称重菜标称、实称、允差与计量单位 | 超允差需确认且补退款可追踪 |
| FNB-B10 | 茶位费、锅底、包材、服务费与低消 | 计费基数适用范围减免规则清晰且无隐藏收费 |
| FNB-B11 | 多语言菜名、标签、图片与导入校验 | 导入有预检结果且历史票面不随改名改变 |
| FNB-K01 | 连锁餐牌发布、门店差异与回滚 | 不覆盖历史订单和店内受保护配置 |

### MOD-03 点餐与订单管理

**边界：** 管理草稿、点餐批次、餐饮源行、核心订单绑定、受理与恢复；支付资金属于模块05，制作属于模块04。

**服务落点：** CheckCartService、DiningOrderService。**目标API索引：** 037–043；支付/退餐/履约经其他模块合同。

**交付切片：** 先在线基础下单及加菜；先付受理联通模块05，后付先补库存及取消合同；复杂换菜/定时出餐随后补齐。

| 需求编号 | 功能清单 | 最低验收结果 |
|---|---|---|
| FNB-D01 | 顾客扫码H5小程序与点餐机 | 顾客设备会话隔离且结束清除个人信息 |
| FNB-D02 | 收银服务员代客点餐与来源追踪 | 操作人买家付款人分别记录 |
| FNB-D03 | 同桌购物车并发与分人分座位 | 提交只清理本次草稿并可识别冲突 |
| FNB-D04 | 预览确认与价格变化提示 | 金额变化必须重新确认不得静默替换 |
| FNB-D05 | 点餐批次、加菜与同SKU不同做法 | 同一请求只一批且口味对应准确数量 |
| FNB-D06 | 赠菜、换菜、缺货替换与顾客确认 | 赠送与退款免单区别且替换差价可追踪 |
| FNB-D07 | 先付后吃与未付取消 | 权威已付前不派工并发取消付款有确定结果 |
| FNB-D08 | 先吃后付与受理门槛 | 受理后不按普通未付超时释放制作库存 |
| FNB-D09 | 预订外带与定时出餐 | 预点菜和已受理制作分开且有容量截止规则 |

### MOD-04 厨房与履约管理

**边界：** 从已受理点餐批次生成制作任务，负责工位、数量、道次、出品、上菜与交接。

**服务落点：** KitchenTaskService、CourseService、DiningOrderService。**目标API索引：** 044–055。

**交付切片：** 先派工、制作、出品上菜与自取交付，再等叫、齐套、道次、损耗、负载及配送交接。

| 需求编号 | 功能清单 | 最低验收结果 |
|---|---|---|
| FNB-E01 | 受理后派工与按工位拆分 | 事件重放不新增制作任务 |

## 四、开发与依赖规则

1. 做最小工程前置：构建、统一认证上下文、门店隔离、幂等、公共实体/错误协议、迁移与测试环境。仅为首个业务模块提供必要支撑，不一次性生成全部Controller和表。
2. 业务主线按 MOD-01桌台 → MOD-02菜品餐牌 → MOD-03点餐订单推进。每模块交付“功能清单 → 规则/状态 → 表/API差异 → 类清单 → 实现/测试”，完成基础验收即可进入下一模块。
3. 之后推进厨房、收银、退餐、打印；先付模式的厨房派工必须依赖真实支付确认，厨房可先独立验收任务规则，完整链路待收银汇合。打印、后付、复杂结账按所需合同逐项接入。
4. 现金班次基础须在现金收款之前；营业日规则须在第一张订单之前；日结、报表、权限、审计、事实事件不能等最后才补数据。完整日结报表完成前不作为生产试点已就绪。
5. 专项业态、第三方与断网营业分开验收。双部署、隔离、备份恢复从工程前置贯穿全过程；第三方供应商和离线获准支付范围待专项确定，不阻塞在线业务模块。

本册是当前业务开发组织入口；[后端计划](../technical/TDD-餐饮系统-后端开发计划.md)原B0–B11保留为工程合同、故障测试及验收工作包引用，不再用作跨业务穿插开发的主顺序。功能有新增时追加稳定编号并补主责模块，不改原需求编号。
