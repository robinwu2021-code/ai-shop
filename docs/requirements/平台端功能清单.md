## 〇、平台端存在的理由

C 端和 B 端各自只看得见自己那一侧：消费者看不到商家的账，商家看不到别家的单。**只有平台能看见全局**，所以平台端只做三类事：

1. **裁**——两端有争议时给结论（售后裁决、评价申诉、毁约判定）
2. **定**——两端共用的规则由谁定（费率、阈值、类目、模板、逾期规则）
3. **兜**——两端出故障时的人工兜底（掉单补偿、异常单、代客操作）

**不做**的是「替商家运营」：不代管商品、不代定价、不替商家发活动。

## 二、三端对照：谁定规则、谁执行、谁兜底

**这张表是本文档的重点**——它回答「B/C 端某个功能，平台端有没有对应支撑」。

| 能力 | C 端（消费者） | B 端（商家） | 平台端 | 结论 |
|---|---|---|---|---|
| 社区与自提点 | 绑定、选点 | 承接核销 | 网格与网点档案 | ✅ 三端闭合 |
| 类目 | 按类目逛 | 建品选类目 | 三级类目树 | ✅ |
| **规格模板** | — | 建品选模板 | **无维护入口** | ❌ **断裂**：模板是死的，商家只能用初始那几套 |
| 商品 | 浏览 | 上架定价 | 商品池与审核 | ✅ |
| 下单支付 | 下单 | 接单 | 检索 + 掉单补偿 | 🕐 补偿未建 |
| 履约 | 取货 | 分拣核销 | 批次调度 + 逾期规则 | ✅ |
| **售后裁决** | 申请介入 | 只读等结果 | **裁决 + 判责** | ✅ 三端闭合（本轮补齐） |
| 极速退阈值 | 享受秒退 | — | 阈值配置 | ✅ |
| **评价申诉** | 写评价 | B-9.4 申诉（≤3 星） | 申诉裁决台 | ✅ 已闭合 |
| 评分维度 | C-RV-01 三维度打分 | B-9.3 三维度展示 | 权重参数 | ✅ 已闭合 |
| 券与活动 | 领券用券 | 配店铺活动 | 平台券 + 楼层位 | ✅ |

## 五、真实性边界

ops-web 是 **Next.js**（与两端的 uni-app 不同栈），同样全跑 mock。
`ready` 表示**页面与 mock 数据已建**，不代表接了后端；`soon` 是导航里可见但点进去是占位。
131 个契约方法分布在 18 个模块契约文件里，与两端一样走「契约先行 + OpenAPI 对齐」。

## 维护约定

1. **数字不写在这里**——交易规则值一律引用[规则表](需求矩阵-三端.md#七之二交易规则常量唯一事实源)，它由 `npm run gen:rules` 从代码生成。文档里复述一次，就会有一处忘了改。
2. **跨端引用用 ID**（`C-AS-06` / `B-7.3` / `P-6.1`），不写「另一端那个功能」。ID 在三份清单之间可解析，改名时能查出所有引用点。
3. **状态取自代码**，不是计划：功能点的 ✅/⬜ 以页面与契约是否存在为准；平台端的 `ready/soon/phase2` 直接来自 `ops-web/lib/nav.ts`。
4. **发现文档与代码不符，改文档**——代码是事实。若代码本身错了，先改代码再回来改这里。
