## 一、排序依据

缺口清单末尾那句话是这份计划的排序依据：

> **每一层流失都对应一个具体的帮助动作，而不是一个报表。统计的价值在于它指向谁。**

于是三条规则：

1. **能指向具体商家的统计，排在通用报表前面。** 「上架率 2%」是一个数字；
   「这 4 家建了品没上架」是一个可以打电话的名单。
2. **统计与它的动作成对交付。** 只看不能动的看板，运营看两次就不看了 ——
   进销存②「0/4」正是这么来的。
3. **平台规则（①）押后，除非今天就能被滥用。** 预留 TTL 上限是唯一的例外：
   今天传一个很长的值就能把货占住，这是能被利用的洞，不是待完善的配置。

## 三、逐里程碑

### M1 · 商家链条画像

**一家一行**：建品 → 提审 → 上架 → 建账 → 首次进货 → 持续记账。

| | |
|---|---|
| 落点 | 经营看板 → 新 tab「商家链条」 |
| 数据源 | `prd_goods`（建品/待审/上架）· `inv_item`（建账）· `inv_document`（进货/最近记账） |
| 跨域 | **必须走 SPI Port** —— `GoodsQueryPort` 加聚合方法，进销存侧走 `StockPort`；直接引对方 mapper 会被 ArchitectureTest 拦 |
| 角色 | `SUPER_ADMIN` · `BD` · `GOODS_OPS` · `ANALYST` |
| 验收 | 一行一商家，六列各是一个数；**每一列可点**，落到那一层的明细。撤掉任一数据源，对应列必须显示「取不到」而不是 0 |

一次补上四项：商家③活跃与流失、商品③上架率、进销存③采用漏斗、贯穿③链条画像。

**已完成**（V305）。落在商家治理下自成一组「经营诊断」，而不是挂在经营看板下：
它的结论是「今天该找谁」，而找到人之后要做的事全在商家治理这个菜单里。

> **为什么它排第一**：缺口清单里商品③ 是 0/5、进销存③ 是 2/5，
> 而这两个空格子的绝大部分内容，本质是同一张表的不同列。
> 分开做要建三个页面，合起来是一张。

### M2 · 触达与轻干预

M1 的每一行后面跟一个动作。**没有 M2，M1 就是一张只能看的表。**

| 功能 | 落点 | 说明 |
|---|---|---|
| ✅ 主动触达商家 | 画像行内按钮 | V307。事由枚举与卡点一一对应，**一天一次** |
| ✅ 提醒商家记账 / 修账 | 同上，`STALE_LEDGER` / `NO_INBOUND` 两档 | 与上一条同一个端点，模板不同 |
| ✅ 库存存疑打标 | 库存对差页 | 走 `mch_violation`，**只记录不惩罚** —— 见下 |
| ✅ 手动补投影 | 库存对差页 | 默认试算，要显式 `apply` 才真搬 |

### 两个决定（原本挂着等业务定，这里由实现方决定并写明）

**① 「库存存疑」不影响曝光权重 —— 因为那套机制不存在。**

原始条目写的是「影响曝光权重，比下架轻」。查下来：**代码库里没有任何曝光权重 /
排序打分的机制**，要做就得先发明一套排序。而在那之前，一个「悄悄降权」的标记是
比下架**更糟**的东西：商家看不到、收不到通知、没有申诉入口，只知道单变少了。

改成走已有的 `mch_violation`：类型 `STOCK_DOUBT`、动作 `WARN`。
`recordViolation` 只对 `BREACH` / `SUSPEND` / `STORE_OFFLINE` 有副作用，
其余是**纯记录** —— 这正好是「比下架轻」的准确含义。它出现在信用档案里，
商家的对接人看得到，且可申诉。将来真有了曝光排序，读这张表即可。

**② 手动补投影默认试算，`apply=true` 才真搬。**

`InventoryBackfillService.run()` 早就有且有测试，缺的只是一个 ops 入口。
但它被 `shop.inventory.backfill.dry-run`（默认 **true**）挡着 ——
那个默认值是一个决定，不该被一个按钮悄悄绕过。
所以端点自己带 `apply`：不传就是试算（告诉运营「会搬 N 条」），
传了才写。**两步之间隔着一次人的确认**，而不是隔着一个配置项的默认值。

**已完成前两项**（V307，新码 `merchant:merchant:nudge`）。做的时候剔掉了一档：

> **`IN_AUDIT` 不是可提醒的事由。** 那一档的意思是「他的品全卡在平台的审核队列里」——
> 欠账的是平台。就这件事去提醒商家，等于把自己的积压说成对方的问题，
> 而商家收到之后能做的只有再等。画像上那一行给的出路改成「去审核队列」。

另外两条边界：一天一次（能被连点的推送入口就是骚扰工具），
而且第二次要**说出来**「今天已经提醒过了」—— 底层撞键是静默跳过，
静默的后果是运营看不出发没发出去，于是再点一次。

### M3 · 投影链路健康度

把它从「库存对差」里拆出来 —— **这是链路问题，被折叠进了一个数据指标**。

**已完成**（V306）。查明的两件事写在实现里：`SysOutbox.FAILED` 没有任何代码会设它
（按 status 统计失败数得到的是一个恒为 0 的列）；空队列时 `selectMaps` 返回的是
「一个 null 元素」而不是空列表 —— 只判 `isEmpty` 的话，**一切正常**这个最常见的状态直接 500。

| | |
|---|---|
| 落点 | 进销存 → 新 tab「链路健康」 |
| 数据源 | `sys_outbox` / `inv_outbox`：PENDING 积压、最老一条的年龄、最近成功时间、retry_count 分布 |
| 验收 | 2026-09-02 那次（投递任务停着、一条 `SKU_UPSERTED` 躺了六小时）在这一页上**必须一眼看得出**；停掉投递任务是它的消融测试 |

### M4 · 商品域统计补全

M1 之后剩下的四项，共用同一个统计端点：

- 类目使用率（73 个类目，14 个被用过）
- 审核吞吐与通过率（平均等多久、驳回原因分布）
- 条码 / 货号覆盖率（209 个 SKU 里 1 个有条码 —— **扫码功能的天花板就是这个数**）
- 规格库使用率（34 个维度，哪些从没被选中）

**已完成**（V308）。四个数都给分子与分母，不只给百分比 ——
73 个类目用了 14 个，与 7300 个用了 1400 个，同样是 19%，但该做的事完全不同。

> **「平均等多久」做不出来，没有硬凑。** `prd_goods` 上没有「什么时候审的」这一列，
> 只有 `updated_at`，而商家改一版也会动它 —— 拿它算出的平均值是一个
> 看起来很合理、实际在量别的东西的数。吞吐改从审计日志取（每次审核都有一行），
> 而「平均等多久」在界面上明说给不出，要它就得先加一列。

### M5 · 单体视图四张

| 功能 | 状态 | 落点 |
|---|---|---|
| 单店经营明细 | **本来就有** | `/ops/stores/{no}/stats` 早就实现、前端也早就在调 —— 缺口清单判错了，见那边的 §六.4 |
| 一家商家的全景 | ✅ 补齐另一半 | 抽屉原先覆盖主体/履约/人员/门店，缺商品与进销存那一段。M1 已经算好了，取那一行即可 |
| 单商品全链路状态 | ✅ | 商品池点商品号 → 抽屉。建账给 `已建/规格数` 而不是一个对勾 |
| 单商家进销存概况 | ✅ | 库存流水页顶部。**「没搬进来」与「搬了一笔没记」分开说** |

> **这一轮最值钱的产出是一条更正，不是一个功能。**
> 「单店经营明细整个是空的」是错的 —— 它早就实现了。
> 错因是对齐「今天有什么」时顺着菜单树看，而单店明细是点开一行弹出的抽屉，
> 在菜单维度上不存在。**④「查看某一个 X」这一栏最容易犯这个错**：
> 按定义它就是从列表点进去的，几乎不会有自己的菜单。
> 矩阵因此从 32.5/70 改为 33.5/70。

### M6 · 强动作 —— **不用做，三条全是误判**

去页面里逐条翻的结果：

| 原条目 | 实际 |
|---|---|
| 强制下架单个商品 | `POST /ops/skus/{no}/force-off` + `/ops/goods/{no}/force-off`，商品池抽屉里都有按钮 |
| 门店启停 | 压下＝「违规处置」里选 `STORE_OFFLINE`（带门店选择器）；解除＝门店档案抽屉里的按钮 |
| 代操作（帮商家下架某个 SKU） | 就是上面那个 SKU 级 force-off |

**与「单店经营明细」是同一个错**：这些动作是点开某一行之后才出现的按钮，
在菜单树上不存在，而我对齐「今天有什么」时看的是菜单。

**修正后的口径**：② 与 ④ 这两栏都不能只看菜单 —— ④ 是「点进去看」，
② 是「点进去做」，两者按定义都藏在列表行的后面。

### M7 · 平台规则

**预留 TTL 上限先做**，其余按业务量。

| 功能 | 优先 | 理由 |
|---|---|---|
| ~~预留 TTL 上限~~ ✅ | — | 已加（默认 24h 可配，超了**拒**不截断）。⚠️ 原来「今天传个长值就能把货占住」**说过头了**：三个调用方传的都是 30 分钟常量，开放 API 没有 reserve。它堵的是下一个把 TTL 接到外部输入的调用方 |
| ~~对差容忍度~~ → **对差所需连续轮数** ✅ | — | **原条目方向反了**：对库存来说任何差异都是账错了，该配的不是「差多少能忍」而是「连续几轮为零才够格切」。默认 7（一周，足够覆盖「周末没单所以看起来干净」）。此前这个 N 根本不存在，于是「够了没有」谁都答不了 |
| 入库必填项 | 低 | **采购入库已强制要成本价**，缺的是「运营能配」不是「没规则」 |
| ~~安全库存平台默认值~~ ⊘ | — | **不做**：读它的地方在 `shop-inventory`，而那是刻意隔离的模块（独立库、独立 Flyway、**零 SPI 引用**，为的是将来能单独交付）。为一个默认值拆掉那道边界，代价与收益差得太远 |
| ~~单位字典~~ ⊘ | — | **不做**：`inv_uom` 至今**零读者**。给一张没人读的表做维护页，是把「没接上」这件事盖住 —— 要做该先接上它，那是另一件事 |
| 建品前置约束 | 中 | 禁售词、必填图、标题规范。今天只有事后驳回 |
| SKU 数量上限 | 低 | **已在拦**（`MAX_SKUS = 100` 硬编码），缺的是「运营能改」不是「没有上限」 |
| 条码与货号规范 | 中 | 与 M4 的覆盖率成对：先能量，再能管 |
| 店招公告合规规则 | 中 | 禁用词前置，而不是发出来再审 |
| 单商家门店数上限 | 低 | 增值包里有 `storeQuota`，那是按家配不是平台底线 |

### M8 · 三处错位修正

**已完成**（V309）。

1. ✅ 「类目 × 支付方式」→ **「当面付禁用类目」**。业务成立（当面付意味着平台收不到钱、
   无法对账与风控，高风险类目该被禁 —— 类目在这里是风控维度），不成立的是名字。
   **只改 name 不改 href**：路由是内部键，改它要动 TAB_KEYS、清单产物、已有链接，
   而这些换不来任何东西。
2. ✅ 「增值包与额度」拆成「增值包授予」+「档位定义」两个 tab。
   两条权限本来就不同（授予走 `merchant:merchant:ban`，改定义走 `system:param:update`）——
   一个 tab 装两个码，页面只能取松的那个。
3. ✅ `/jobs` 按归属模块分组，组头直接给「几个关着」。
   判据来自那次事故本身：09-02 之前进销存三条命脉全关着、六条跨域链路堵了一整天，
   而在一张平铺的 17 行表里，「这三条都归进销存、而且都关着」是读不出来的。
   整组关掉时直接出红标。

## 四、明确不排期的 4.5 项

不是漏了，是**等的不是工期**：

| 项 | 等什么 |
|---|---|
| 商家①信用规则 | 几次违规降级、几次封禁 —— 要业务定阈值，不是技术问题 |
| 商家①认证标授予标准 | 同上 |
| 商家③分层分布 | 分层（FREE/PRO/CHAIN）本身还没定 |
| 进销存①功能分层 | 同上，`INV-P6` 卡在同一个决策上 |
| 门店③网点覆盖与密度 | 要与社区网格结合，而小区库今天只有 2 条真实数据 |

**`ANALYST` 的看板权限**也在这一栏：给一个角色开平台 GMV 的可见性该由人来定。

## 五、每个里程碑的收尾动作

新增页面 / 菜单不是改完 `nav.ts` 就完了，这条链上有五处：

1. `ops-web/lib/nav.ts` —— 菜单

4. 新端点五处登记：`endpoints.ts` / `contract.ts` / `http.ts` / `mock.ts` / `gen-openapi.mjs` 的 `RESPONSE_TYPES`
5. 跑生成器：`gen-ui-catalog.py` · `gen-ops-feature-list.py` · `gen-openapi.mjs` · `gen-perm-endpoint-matrix.mjs`
