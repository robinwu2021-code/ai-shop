## 一、排序依据

缺口清单末尾那句话是这份计划的排序依据：

> **每一层流失都对应一个具体的帮助动作，而不是一个报表。统计的价值在于它指向谁。**

于是三条规则：

1. **能指向具体商家的统计，排在通用报表前面。** 「上架率 2%」是一个数字；
   「这 4 家建了品没上架」是一个可以打电话的名单。
2. **统计与它的动作成对交付。** 只看不能动的看板，运营看两次就不看了 ——
   进销存②「0/4」正是这么来的。
3. **平台规则（①）押后，除非今天就能被滥用。** 预留 TTL 上限是唯一的例外：
   今天传一个很长的值就能把货占住，这是能被利用的洞，不是待完善的配置。

## 三、逐里程碑

### M1 · 商家链条画像

**一家一行**：建品 → 提审 → 上架 → 建账 → 首次进货 → 持续记账。

| | |
|---|---|
| 落点 | 经营看板 → 新 tab「商家链条」 |
| 数据源 | `prd_goods`（建品/待审/上架）· `inv_item`（建账）· `inv_document`（进货/最近记账） |
| 跨域 | **必须走 SPI Port** —— `GoodsQueryPort` 加聚合方法，进销存侧走 `StockPort`；直接引对方 mapper 会被 ArchitectureTest 拦 |
| 角色 | `SUPER_ADMIN` · `BD` · `GOODS_OPS` · `ANALYST` |
| 验收 | 一行一商家，六列各是一个数；**每一列可点**，落到那一层的明细。撤掉任一数据源，对应列必须显示「取不到」而不是 0 |

一次补上四项：商家③活跃与流失、商品③上架率、进销存③采用漏斗、贯穿③链条画像。

**已完成**（V305）。落在商家治理下自成一组「经营诊断」，而不是挂在经营看板下：
它的结论是「今天该找谁」，而找到人之后要做的事全在商家治理这个菜单里。

> **为什么它排第一**：缺口清单里商品③ 是 0/5、进销存③ 是 2/5，
> 而这两个空格子的绝大部分内容，本质是同一张表的不同列。
> 分开做要建三个页面，合起来是一张。

### M2 · 触达与轻干预

M1 的每一行后面跟一个动作。**没有 M2，M1 就是一张只能看的表。**

| 功能 | 落点 | 说明 |
|---|---|---|
| ✅ 主动触达商家 | 画像行内按钮 | V307。事由枚举与卡点一一对应，**一天一次** |
| ✅ 提醒商家记账 / 修账 | 同上，`STALE_LEDGER` / `NO_INBOUND` 两档 | 与上一条同一个端点，模板不同 |
| 库存存疑打标 | 库存对差页 | 影响曝光权重，比下架轻 |
| 手动补投影 | 库存对差页「账外」列 | 今天发现账外 SKU 之后做不了任何事 |

**已完成前两项**（V307，新码 `merchant:merchant:nudge`）。做的时候剔掉了一档：

> **`IN_AUDIT` 不是可提醒的事由。** 那一档的意思是「他的品全卡在平台的审核队列里」——
> 欠账的是平台。就这件事去提醒商家，等于把自己的积压说成对方的问题，
> 而商家收到之后能做的只有再等。画像上那一行给的出路改成「去审核队列」。

另外两条边界：一天一次（能被连点的推送入口就是骚扰工具），
而且第二次要**说出来**「今天已经提醒过了」—— 底层撞键是静默跳过，
静默的后果是运营看不出发没发出去，于是再点一次。

### M3 · 投影链路健康度

把它从「库存对差」里拆出来 —— **这是链路问题，被折叠进了一个数据指标**。

**已完成**（V306）。查明的两件事写在实现里：`SysOutbox.FAILED` 没有任何代码会设它
（按 status 统计失败数得到的是一个恒为 0 的列）；空队列时 `selectMaps` 返回的是
「一个 null 元素」而不是空列表 —— 只判 `isEmpty` 的话，**一切正常**这个最常见的状态直接 500。

| | |
|---|---|
| 落点 | 进销存 → 新 tab「链路健康」 |
| 数据源 | `sys_outbox` / `inv_outbox`：PENDING 积压、最老一条的年龄、最近成功时间、retry_count 分布 |
| 验收 | 2026-09-02 那次（投递任务停着、一条 `SKU_UPSERTED` 躺了六小时）在这一页上**必须一眼看得出**；停掉投递任务是它的消融测试 |

### M4 · 商品域统计补全

M1 之后剩下的四项，共用同一个统计端点：

- 类目使用率（73 个类目，14 个被用过）
- 审核吞吐与通过率（平均等多久、驳回原因分布）
- 条码 / 货号覆盖率（209 个 SKU 里 1 个有条码 —— **扫码功能的天花板就是这个数**）
- 规格库使用率（34 个维度，哪些从没被选中）

**已完成**（V308）。四个数都给分子与分母，不只给百分比 ——
73 个类目用了 14 个，与 7300 个用了 1400 个，同样是 19%，但该做的事完全不同。

> **「平均等多久」做不出来，没有硬凑。** `prd_goods` 上没有「什么时候审的」这一列，
> 只有 `updated_at`，而商家改一版也会动它 —— 拿它算出的平均值是一个
> 看起来很合理、实际在量别的东西的数。吞吐改从审计日志取（每次审核都有一行），
> 而「平均等多久」在界面上明说给不出，要它就得先加一列。

### M5 · 单体视图四张

| 功能 | 落点 |
|---|---|
| 单店经营明细 | 门店 → 点一行进详情。**这一格今天整个是空的** |
| 一家商家的全景 | 商家档案页聚合，今天要在四个档案 + 商品池 + 库存流水之间跳 |
| 单商品全链路状态 | 商品池 → 点一行：审核到哪、建账了吗、有库存吗、卖了多少 |
| 单商家进销存概况 | 库存流水页顶部 |

### M6 · 强动作

- 强制下架单个商品（今天只能连商家一起处置）
- 门店启停（今天一家店出问题只能封整个商家）
- 代操作：帮商家下架某个 SKU

**都要留审计痕迹**（`auditLogPort.record`），且都要能说明「为什么」—— 理由必填。

### M7 · 平台规则

**预留 TTL 上限先做**，其余按业务量。

| 功能 | 优先 | 理由 |
|---|---|---|
| 预留 TTL 上限 | **高** | 今天 TTL 由调用方传、平台没兜底，传个长值就能把货占住 |
| 对差容忍度与处置阈值 | 中 | 差多少算「不可信」、触发什么 |
| 入库必填项 | 中 | 成本价 / 供应商填不填，决定将来毛利口径能不能算 |
| 安全库存平台默认值 | 低 | |
| 单位字典 | 低 | `inv_uom` 建了表却一处读它的代码都没有 |
| 建品前置约束 | 中 | 禁售词、必填图、标题规范。今天只有事后驳回 |
| SKU 数量上限 | 低 | 3×4×3 = 36 个 SKU 就是 36 条要盘的账 |
| 条码与货号规范 | 中 | 与 M4 的覆盖率成对：先能量，再能管 |
| 店招公告合规规则 | 中 | 禁用词前置，而不是发出来再审 |
| 单商家门店数上限 | 低 | 增值包里有 `storeQuota`，那是按家配不是平台底线 |

### M8 · 三处错位修正

1. 「类目 × 支付方式」→ **「当面付禁用类目」**（业务成立，名字不成立）
2. 「增值包与额度」拆成 ①定义档位 / ②授予商家两个 tab
3. 进销存三条命脉（事件投递 / 预留回收 / 日快照）在 `/jobs` 页做**成组展示**

## 四、明确不排期的 4.5 项

不是漏了，是**等的不是工期**：

| 项 | 等什么 |
|---|---|
| 商家①信用规则 | 几次违规降级、几次封禁 —— 要业务定阈值，不是技术问题 |
| 商家①认证标授予标准 | 同上 |
| 商家③分层分布 | 分层（FREE/PRO/CHAIN）本身还没定 |
| 进销存①功能分层 | 同上，`INV-P6` 卡在同一个决策上 |
| 门店③网点覆盖与密度 | 要与社区网格结合，而小区库今天只有 2 条真实数据 |

**`ANALYST` 的看板权限**也在这一栏：给一个角色开平台 GMV 的可见性该由人来定。

## 五、每个里程碑的收尾动作

新增页面 / 菜单不是改完 `nav.ts` 就完了，这条链上有五处：

1. `ops-web/lib/nav.ts` —— 菜单
2. **迁移落 `sys_function_point` / `sys_role_point`** —— 菜单真源在库里，只改 nav.ts 接真后端就看不到
3. `Perms.java` + `ops-web/lib/permissions.ts` 两侧的角色授权（少一头守卫就红）
4. 新端点五处登记：`endpoints.ts` / `contract.ts` / `http.ts` / `mock.ts` / `gen-openapi.mjs` 的 `RESPONSE_TYPES`
5. 跑生成器：`gen-ui-catalog.py` · `gen-ops-feature-list.py` · `gen-openapi.mjs` · `gen-perm-endpoint-matrix.mjs`
