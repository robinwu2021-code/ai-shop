## 一、一句话

**运营端看不见门店，也管不动商品**：商家治理（P-11.1）已经三层贯通，
但「这个商家有几家店、每家店卖得怎么样、卖的什么」在运营端没有任何入口；
商品侧只有审核队列，审核通过之后平台对商品**失去一切干预手段**。
本需求补的就是这两块，并给出与 C/B 端的对齐顺序。

**核心判断（决定做法）**：这两块的缺口大多**不是领域层没做，而是领域层做了、ops 出口没开**。
门店 CRUD（`StoreAdminService`）、单商家/单店经营数据（`MerchantOrderService.stats/todo/customers`，
已带 `merchantNo, storeNos` 入参）、商品详情与上下架（`MerchantGoodsService.detail/toggle`）都已存在，
缺的是一层带鉴权与留痕的 ops Controller。**先开出口，再谈新建。**

## 二、现状盘点（三端对照）

### 2.1 用户提出的四块能力

| 能力 | C 端 | B 端 | 运营端现状 | 缺口性质 |
|---|---|---|---|---|
| **商家管理** | 入驻入口（C-AC-07） | 入驻/资料（B-1） | ✅ P-11.1 九个 tab，26/26 端点贯通，运营端最完整的一页 | 无 |
| **门店管理** | 门店主页（C-ST）、按店下单 | `/biz/store/*` 全套：建店/改名/启停/默认店/挂收款号/装修/配送规则/店铺码 | ❌ 只有三个零散口：店招审核队列、`business-mode` 写入、`store-modes` 只读。**没有门店列表、没有门店详情** | **缺 ops 出口**（`StoreAdminService` / `MerchantStoreService` 现成） |

### 2.2 商品与门店的模型关系（决定「门店的商品」怎么看）

- **商品挂主体（merchant），不挂门店**；门店维度是可选的库存覆盖层 `prd_store_stock`
  （某 SKU 一旦有任意一条店级行，整体转店级管理，没有行的店视为 0）。
- **订单双写** `merchant_no`（结算键）+ `store_no`（履约键）（ADR-011 §5）。

所以运营端「查看门店对应的商品」的正确形态是：**主体商品池 × 该店库存/在售状态的投影**，
而不是给商品加一个 `store_no`。做成后者会把 ADR-011 定下的双键模型推翻。

## 三、功能点

### 3.1 运营端门店档案（P-11.2.1 展开，P0）

落在商家治理域（P-11），入口两个：商家详情抽屉加「门店」tab + 独立的跨主体门店检索页。

| ID | 功能 | 说明 | 复用 |
|---|---|---|---|
| P-11.2.1a | 门店列表（按主体） | 商家详情内看该主体全部门店：名称/地址/状态/默认标/经营模式/收款商户号状态。**含停用的** —— 治理视角更不能看不见 | `StoreAdminService.list(merchantNo)` 直接用 |
| P-11.2.1b | 跨主体门店检索 | 按状态/社区/经营模式/关键词分页查全平台门店。BD 的问题是「这个片区有哪些店」，不是「这个商家有哪些店」 | 新增 repo 查询（表已有，查询简单） |
| P-11.2.1c | 门店详情 | 门面资料（公告/营业时间/地址）、配送规则、覆盖社区、挂靠自提点、店铺码获客数（P-10.1.4 已有页面，挂过来） | `MerchantStoreService.profile/deliveryRule` |
| P-11.2.1d | 门店经营状况 | 今日/本月订单数与 GMV、待办堆积（待发货/待核销/待售后）、评分。列表行内给缩略，详情给全量 | `MerchantOrderService.stats/todo(merchantNo, [storeNo])` 直接用 |
| P-11.2.1e | 门店商品投影 | 该主体商品池 + 本店库存（店级覆盖行存在时显示店级值并标注「店级管理」）。从这里可跳 3.2 的商品治理动作 | `/ops/goods?merchantNo=` 已有 + `prd_store_stock` 读接口（新增，只读） |
| P-11.2.1f | 门店订单 | `/ops/orders` 增加 `storeNo` 筛选 | `opsList` 加一个入参（订单表已有 `store_no`） |

**只读为主，治理动作最小化**：平台端的边界是「裁、定、兜」，不替商家运营（平台端功能清单 §〇）。
门店资料、价格、库存**一律不给运营改**——要改就变成了「平台代管门店」，出错时责任说不清。
运营侧仅有的两个写动作：

| 动作 | 归属 | 为什么 |
|---|---|---|
| 门店强制下线（C 端不可见，B 端可见并给原因） | 违规处置（P-11.1.4 扩展到门店级） | 现在封禁只有主体级：一家店出事要封整个商家，连坐其余门店。不做门店级，多门店商家的违规处置就是钝器 |
| 经营模式改写 `business-mode` | 已有 | 保持不动 |

**Plan/额度部分（P-11.2.2~11.2.6）不在本需求**：授予/延长 Plan、额度覆盖、降级看板依赖
增值包订阅模型（B-11.12 的 Q1/Q2 未拍板），先做档案与数据这一半，Plan 那一半等拍板后补。
`StoreAdminService.create` 的额度现在读配置 `shop.store.max-per-entity`，注释已写明 M4 后改由档位决定——衔接点已留好。

### 3.2 平台商品治理补齐（P-3.2/P-3.3/P-3.4，P0）

| ID | 功能 | 现状 → 目标 | 复用/新建 |
|---|---|---|---|
| P-3.2.2b | 商品详情 | 审核抽屉只有列表字段 → `/ops/goods/{goodsNo}` 全量（三语文案、多市场价、SKU 矩阵、审核历史） | `MerchantGoodsService.detail` 开出口（去掉 merchantNo 归属校验的旁路要显式） |
| P-3.2.3 | **强制下架** | ❌ 无 → 违规商品平台直接下架，**必填原因、进审计日志、通知商家**；商家改后重新提审走既有 P-3.2.2 | `toggle` 有，但它带 merchantNo 校验且无留痕——需要 ops 专用方法，不复用 biz 语义 |
| P-3.3.1~3 | SKU 池 / 预售额度 / 超卖告警 | ❌ 前端 5 条调用全 404 → 落地 `/ops/skus`、`/ops/skus/{no}/{force-off,presale}`、`/ops/skus/oversell` | **服务层要新建**（现有服务都是 goods 粒度） |
| P-3.4 | 规格模板维护 | ❌ 已知断裂（E27）：B-4.4 商家能选模板，平台没有维护入口，模板是死的 | 服务层要新建（类目 → 模板 → 选项 + `optionCode` 三层） |

**强制下架为什么不复用 `toggle`**：biz 的 toggle 语义是「商家管自己的货」，
ops 的语义是「平台裁决」——原因必填、审计留痕、触达商家三件事 biz 路径都没有。
共用一个方法，迟早有一条路径漏掉留痕，而那正是平台权力最需要制衡的地方（P-1 审计）。

### 3.3 经营看板下钻（P-16.1.3，P1）

平台大盘（3 条）之下加一层「商家/门店」维度：排行（GMV/订单/售后率）与单店趋势。
`DashboardService.kpi/trend/funnel` 目前无入参，下钻要扩签名——**放在 P1**：
门店档案页的 3.1d 已经覆盖「看单店经营状况」的日常问法，看板下钻是分析场景，不挡运营干活。

### 3.4 对齐机制（随功能一起交付，不单列）

- 每落一个端点：`@PreAuthorize("@perm.can('...')")` 照抄 B 端①的手法（守卫先红后绿，对齐清单 §10.1）；
  `perm-map.ts` 翻掉对应 `UNIMPLEMENTED`；`npm run gen:api` 重出 `openapi-ops.yaml`。
- 新权限码建议（2026-08-13 更正为 68 码细化后的现行词表）：门店档案读挂 `merchant:merchant:read`（BD 已持有），
  强制下架挂 `product:sku:audit`，门店强制下线挂 `merchant:merchant:ban`——**不为本需求新造码**，
  造码等价于造角色，而 11 个角色里 7 个后端还没实现，先别扩词表。
- 命名漂移随手修（前端 `/ops/audit-logs` vs 后端 `/ops/audit-log` 一类），修在前端 http 层，后端不动。

| 序 | 事项 | 为什么是这个位置 |

| ① | 本需求 3.1 + 3.2 的「开出口」部分（门店档案、商品详情、强制下架、门店订单筛选） | 领域层现成，纯 Controller + 前端翻标记，投入产出比最高；而且是运营日常最高频的问法 |

## 五、不做什么

| 不做 | 为什么 |
|---|---|
| 运营端代改门店资料/商品价格/库存 | 平台边界是「裁、定、兜」，不替商家运营。代管一旦开口，客服会拿它当万能通道，出错责任说不清 |
| 商品加 `store_no` | 商品挂主体是 ADR-011 定的双键模型；门店维度走 `prd_store_stock` 投影（§2.2） |
| 为门店/商品治理新造权限码或角色 | 后端 11 角色只实现 4 个，先把活挂在已有的码上；扩词表是 §四 ④ 之后的事 |
| 门店级独立进件/费率 | 通道按主体发号（ADR-011），费率是主体谈的 |
| 把 `/ops/order` 旧口径一起收敛 | 值得做（`PlatformOrderService.search` 已被 `opsList` 覆盖），但属清理不属本需求，避免混批 |
