# B 端与运营端：从注册开始，一步一步走一遍

> 2026-08-09 · 不按模块分，**按人真实走的顺序**排。每一步写清：他看到什么 · 点了会怎样 · 现在通不通。
> 事实来源：[五域全栈对齐核查](../technical/archive/五域全栈对齐核查.md)。图例：✅ 通 · 🟡 有但不完整 · 🔴 断 · ⬜ 没有

---

## 零、两条路，两个人

先分清楚这两端服务的**不是同一个人**：

| | B 端（商家 App / 小程序） | 运营端（ops-web） |
|---|---|---|
| 谁在用 | 老板、店长、店员 | 平台 BD、客服、超管 |
| 第一次打开时他是谁 | **还不是商家** —— 什么都没有 | 已经有账号（平台建的），不存在"注册" |
| 第一个动作 | 登录 → 申请开店 | 登录 → 看待办 |
| 成功的标志 | 能收钱、能被顾客看见 | 待办清零 |

> **一个关键区别**：B 端的人是**从零开始**的，运营端的人是**被派进来干活**的。
> 所以 B 端的每一步都要回答「我下一步该干嘛」，运营端的每一步都要回答「哪些是我的活」。

## 第一部分 · B 端：一个新商家的完整路径

### 步骤 1 · 打开 App，登录

**他看到**：登录页，手机号 + 验证码（App 上还有微信/Apple 登录）。

| 项 | 现状 |
|---|---|
| 手机号验证码登录 | ✅ `POST /biz/auth/login` |
| 微信 / Apple 登录 | ✅ 按端下发（`loginMethods()`，安卓包里不放 Apple 按钮） |
| **员工用工号手机登录** | ✅ 登录页顶部「我是老板 / 我是店员」切换（本轮补） |

> ✅ **断点 1 已闭合**：身份切换放在页面**最上面** —— 它决定后面所有输入的含义，
> 放下面的话人会先填完再发现选错，而选错的表现是「登进去什么都看不到」。
> 快捷登录（微信/Apple）只给老板：它们拿到的是**消费者身份**，混在一起会让店员点了微信却登成消费者。

### 步骤 2 · 登录后：工作台告诉他"还没开张"

**他看到**：整屏只讲一件事 —— 「还没有店铺」+ 一个「去开张」按钮（`home` 页的 `!merchant.isActive` 分支）。✅

> 这个设计是对的：新商家第一次进来看到一堆空数据面板，只会以为系统坏了。

### 步骤 3 · 填入驻申请

**他看到**：行业 → 主体类型 → 店名 → 联系人 → 类目 → 简介 → **服务范围** → 自提点意愿。

| 字段 | 现状 |
|---|---|
| 行业（驱动能否选小微） | ✅ 本轮接通，来自 `/common/master-data` |
| 主体类型（行业不允许小微时禁用并说明理由） | ✅ |
| 店名 / 联系人 / 手机号 / 主营类目 / 简介 | ✅ |
| **服务范围 + 覆盖小区** | ✅ 本轮补上，带「选大了送不到、选小了搜不着」的后果说明 |
| 是否兼做自提点 | ✅ |
| 资质图（执照） | 🟡 **已从这里移到进件页** —— 它属于开户流程不属入驻（逼一个还没过审的人先传执照只会把人挡在门外） |

> **约束**：一人同时只能有一份进行中的申请（库级唯一键）。
> 文案要说「**同时**只能有一份」，不是「只能有一个」—— 否则他以为平台不支持多执照。

### 步骤 4 · 等审核（这一步他最焦虑）

**他看到**：申请页顶部显示「审核中」；被驳回时显示**驳回原因** + 表单已回填上次内容。✅

> 补交不是重来 —— 驳回往往只缺一张执照，让人从头重填一遍，有相当一部分人就不回来了。

### 步骤 5 · 审核通过：系统替他建好四样东西

他什么都不用做，后台同一个事务里生成：主体 · owner 商家账号 · 默认门店 · 进件占位 · 覆盖社区（+ 自提点）。✅

> 本轮修了一个静默缺陷：幂等判据曾按「人」判重，于是**申请第二张执照通过时会改掉第一个主体** —— 两家店变一家，全程无报错。现已改为按申请单判。

### 步骤 6 · ✅ 工作台的三段状态卡（本轮补）

通过之后他面对的是三个**互相独立**的状态，而工作台现在只有一个「已开张」：

| 他会问 | 谁回答 | 现状 |
|---|---|---|
| 我能开张了吗？ | 主体 ACTIVE | ✅ |
| 我能收钱了吗？ | 进件 ACTIVE | ✅ 卡住时工作台直接说「还不能收款」并可点进去 |
| 我的店能被看到吗？ | 服务范围非空 | ✅ 卡住时说「顾客还搜不到你」 |

> ✅ **断点 2 已闭合**。两条设计取舍：
> ① **只在有问题时出现** —— 全通过还挂一张绿卡，是每天都要划过去的噪音；
> ② 三段与待办**一起取**（`Promise.all`）—— 分开取的话「能不能收钱」会晚一拍出现，而那一拍里工作台看着是全绿的。

### 步骤 7 · 收款设置（进件）

**他看到**：每个通道一张卡 —— 状态、**能不能收钱**、还缺什么，以及补资料表单。

| 项 | 现状 |
|---|---|
| 进件状态 + `canReceiveMoney` | ✅ |
| 缺什么逐条列出（结算账户 / 执照） | ✅ 「还差结算账户」比「审核中」有用得多 |
| 补资料并提交 | ✅ 明文账号只在请求里存在，库里只留掩码 |
| 驳回原因回显 + 补交重提 | ✅ 重提会清掉上次拒因 |
| 主动回查（回调会丢） | ✅ |
| 真实通道 | 🟡 **只有 stub** —— 真钱之前必须接 |
| 通道回调入口 | ⬜ 现在只能靠他自己点"刷新状态" |

### 步骤 8 · 店铺设置（门面）

公告 / 营业时间 / 地址 / 主推 / 服务范围 / 店铺码 / 分享素材。✅
🟡 **只作用于默认店** —— 多门店之后这一页要跟着门店走。

### 步骤 9 · 门店管理

列表 / 新建（受额度）/ 改名 / 停用 / 转默认 / 换收款号。✅ 本轮全通。

> 🟡 **断点 3**：能建三家店，**但 B 端所有业务页仍按主体取数** ——
> 订单、商品、核销都没有门店维度，`BizContext` 里也只有一个 `merchantNo`。
> 换句话说：多门店现在只是"能建出来"，还不能"分开经营"。

### 步骤 10 · 员工与授权

加员工（只要手机号）/ 停用 / 逐店角色（A 店店长 + B 店店员）。✅ 本轮全通。
🔴 **但员工登不进来**（见步骤 1）—— 这一步做完等于没做。

### 步骤 11 · 上商品

商品列表 / 新建 / 编辑 / 上下架 / 改库存 / 规格模板 / 图片识别。✅

| 缺口 | 说明 |
|---|---|
| 🔴 **不选类目** | `GoodsDraft` 里没有 `categoryNo` → `prd_goods.category_no` 恒为空 |
| 🟡 库存挂主体不挂门店 | A 店卖光 B 店也没货（M3 下沉） |
| 🟡 可见性靠社区池 | 不是门店选品（M3） |

### 步骤 12 · 等订单

到这里他的链路才算走完。**能不能来订单取决于三件事同时成立**：进件 ACTIVE + 服务范围非空 + 商品在架。
其中前两件在步骤 6 里没有任何汇总提示 —— 这是商家最容易卡住又最难自查的地方。

## 第二部分 · 运营端：BD 的一天

### 步骤 1 · 登录

`/ops/auth/login` + `/ops/auth/me`（带角色与权限码）。✅
不存在"注册" —— 运营账号由平台建（`sys_ops_staff`）。

### 步骤 2 · 进「商家治理 → 入驻审核」

**他看到**：待办列表（待审 + 审核中），可按状态/关键词检索历史。

| 项 | 现状 |
|---|---|
| 待办列表 + 历史检索 | ✅ 本轮接真后端 |
| 受理（告诉商家有人在看了） | ✅ |
| 通过 / 驳回（驳回必填理由） | ✅ |
| **通过时补服务范围** | ✅ 本轮新增 —— 商家没填时运营在这里补，此前**没有任何地方能填** |
| 审核留痕 | 🟡 后端有 `/ops/audit-log`，页面仍未接 |

> 这条链本轮从 mock 换成了真后端，**且换了数据模型**：
> 从「商家的一个状态」改成「独立的申请单」—— 通过之前商家不存在，驳回不会留下僵尸商家。

### 步骤 3 · 其余入口：点进去全是 mock

导航里「商家治理」下面还有 5 个叶子（商家档案 / 类目授权 / 认证标 / 信用档案 / 违规封禁），
「门店主页」下面还有 4 个（店招审核 / 模板配置 / 店铺码 / 获客看板）。

**🔴 这些页面都能打开、都有数据、都是 mock。** 后端一条都没有。

| 域 | ops-web 声明 | 后端实现 |
|---|---|---|
| 商家治理 | 13 | 4（全是入驻审核） |
| 门店治理 | 7 | **0** |
| 商品治理 | 9 | 2（`/ops/goods/**`，页面未接） |
| 系统设置 | 8 | 3（行业开关，页面未接） |
| 其余 14 个模块 | 144 | **0** |

> **发布口径**：`NEXT_PUBLIC_USE_MOCK` 默认是 mock。一旦设成 `0`，页面会**成片 404**，
> 不是个别功能缺失。在契约补齐之前 ops-web **只能当 demo**，这条要写进发布清单。

### 步骤 4 · 两条最便宜的补齐

| 事项 | 结果 |
|---|---|
| 行业开关接真 | ✅ 「系统配置 → 行业与小微白名单」，改完 B/C 端入驻表单立刻联动 |
| 商品审核接真 | ✅ 「商品与类目 → 商品审核（真后端）」，goods 粒度不是 sku 粒度 |

> 顺手修了一个后端缺陷：**待审队列返回的是全部商品**（走的是不带条件的公共目录查询）——
> 运营审完一件，队列长度纹丝不动，只会以为没保存成功，反复再审一遍。
> 原有的那条测试断言是 `onSale ∈ {true,false}`，恒真，所以一直没发现。
