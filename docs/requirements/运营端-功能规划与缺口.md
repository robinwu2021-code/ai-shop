## 一、方法：先推导应然，再对齐实然

按四类运营职责推导每个域该有什么，**然后才去对齐今天有什么**：

| | |
|---|---|
| ① **全局设置** | 平台定规则，与具体商家无关 |
| ② **商家 / 门店管理** | 对某一家动手：准入、授权、处置、干预 |
| ③ **平台数据统计** | 跨商家聚合，回答「整体怎么样」 |
| ④ **商家数据查看** | 单家明细，只读 |

**顺序不能反。** 从现有功能倒推分类，只能得到「现有功能的一种分法」——
从没做过的那些不会出现在任何格子里，而那恰恰是要找的东西。

## 二、矩阵总览

| | ① 全局设置 | ② 管理动作 | ③ 平台统计 | ④ 商家查看 | 合计 |
|---|---|---|---|---|---|
| 商家 | 3/5 | 7/9 | 2/4 | 4/5 | **16/23** |
| 门店 | 1/3 | 2/3 | 1/3 | **0/1** | **4/10** |
| 商品 | 5.5/9 | 2/4 | **0/5** | 1/2 | **8.5/20** |
| 进销存 | **0/6** | **0/4** | 2/5 | 1/2 | **3/17** |
| 合计 | 9.5/23 | 11/20 | 5/17 | 6/10 | **31.5/70** |

分母是按业务推导的应有条目，分子是今天已实现的（「有一半」计 0.5）。

**四个空格子，每一个都是一句能说出口的缺失：**

- **进销存没有任何平台级规则**（①0/6）—— 它整个是商家自己的账本，平台只在旁边看。
- **进销存发现问题后动不了**（②0/4）—— 唯一的写口「开放对接」改的是「谁能读这些货」，
  是授权不是治理。只能看不能动的看板，运营看两次就不看了。
- **商品域一个统计数字都没有**（③0/5）—— 而商品是这个平台的主体。
- **门店看不到单店明细**（④0/1）—— 门店是真正的履约与库存单位，却没有自己的经营视图。

## 三、这条链今天的真实流量

沿「配类目 → 建品 → 建账 → 进货 → 售出」实测（2026-09-03，线上库）：

```
73   平台类目
14   ← 被商品用到的（59 个类目没人用）
200  商家建的商品（SPU）
194  ← 卡在审核中，最早的提交于 08-20，等了 14 天
4    ← 买家能看到的（已上架）
209  SKU
1    ← 填了条码的（货号 0 个）
209  进销存里的物料（建账成功，一个不缺）
2    ← 真在记账的商家（共 6 家）
6    ← 出库流水（进货 216 条）
```

**每一层都在流失，而运营端一层都看不见。**
这条链上没有任何一处能回答「上一步到这一步掉了多少、掉在谁身上」。

已有的三块统计（库存健康度、库存对差、获客看板）都是**某一环的快照**，
没有一处是**贯穿链条的漏斗**。而上面这组数说明：真正的问题不在某一环内部，
在环与环之间的落差。

## 四、逐域清单

图例：**✅** 已有 · **◐** 有一半或藏在别处 · **○** 缺

### 4.1 商家域

平台管商家的本质是三件事：**让不该进来的进不来、让进来的守规矩、让守规矩的活下去**。
前两件今天做得最全，第三件几乎没有。

| 类 | 功能 | 状态 | 说明 |
|---|---|---|---|
| ① | 类目准入规则 | ✅ | 哪些类目要哪张证 |
| ① | 保证金与限额规则 | ✅ | 准入门槛按类目配 |
| ① | 增值包档位定义 | ✅ | 与「授予」混在同一个 tab，见 §六 |
| ① | 信用规则 | ○ | 几次违规降级、几次封禁。今天是人工判断 |
| ① | 认证标授予标准 | ○ | 什么条件够格，今天靠运营记忆 |
| ② | 入驻审核 · 类目授权 · 资质到期 · 准入保证金 · 认证标 · 违规处置 · 增值包授予 | ✅ | 7 项 |
| ② | 主动触达商家 | ○ | 发现问题后唯一的轻量动作，消息通道已有、没接 |
| ② | 代操作 | ○ | 极端情况帮商家下架某个 SKU，比封整店轻 |
| ③ | 进件看板 · 无照自营风险 | ✅ | |
| ③ | 商家活跃与流失 | ○ | 多久没上过新品、没记过账、没出过单 |
| ③ | 分层分布 | ○ | 各档位多少家、升降级趋势。分层落地后必需 |
| ④ | 商家 / 门店 / 资质 / 信用 四个档案 | ✅ | |
| ④ | 一家商家的全景 | ○ | 今天要在四个档案 + 商品池 + 库存流水之间跳，各自主键不同 |

### 4.2 门店域

门店是**真正的履约与库存单位** —— 多门店商家的货、单、码都挂在门店上。
但运营端今天只把它当作「一个要审核店招的页面」。

| 类 | 功能 | 状态 | 说明 |
|---|---|---|---|
| ① | 主页模板配置 | ✅ | |
| ① | 店招公告的合规规则 | ○ | 禁用词前置，而不是发出来再审 |
| ① | 单商家门店数上限 | ○ | 增值包里有 `storeQuota`，那是按家配，不是平台底线 |
| ② | 店招公告审核 · 店铺码生成导出 | ✅ | |
| ② | 门店启停 | ○ | 一家店出问题时，今天只能封整个商家 |
| ③ | 获客效果看板 | ✅ | 一行一门店 |
| ③ | 门店经营排行 | ○ | 经营看板有商家排行，没有门店维度 |
| ③ | 网点覆盖与密度 | ○ | 与社区网格结合才答得出「这片区够不够」 |
| ④ | 单店经营明细 | ○ | **这一格整个是空的**。「这家店最近怎么样」没有一处答得上 |

### 4.3 商品域

平台在这个域的角色是**画骨架（类目与规格）+ 守门（审核）**。
骨架画得最全，守门有入口但不会找上门，而**整个域没有一个统计数字**。

| 类 | 功能 | 状态 | 说明 |
|---|---|---|---|
| ① | 类目树 · 规格库 · 类目×规格 · 标准品库 · 主题分类 | ✅ | 6 项，全域最全 |
| ① | 类目 × 当面付 | ◐ | 菜单叫「类目 × 支付方式」，**名不副实**，见 §六 |
| ① | 类目 × 积分 | ✅ | 生鲜与家电不该同一比例；商品级配置实测 0% 填充率，所以收到类目层 |
| ① | 建品前置约束 | ○ | 禁售词、必填图、标题规范。今天只有事后驳回 |
| ① | SKU 数量上限 | ○ | 3×4×3 = 36 个 SKU 就是 36 条要盘的账 |
| ① | 条码与货号规范 | ○ | EAN-13 校验、商家货号格式 |
| ② | 商品审核队列 · 预售额度与超卖 | ✅ | |
| ② | 审核积压主动告知 | ○ | **194 件等了 14 天**，而没有任何地方主动说 |
| ② | 强制下架单个商品 | ○ | 违规商品今天只能连商家一起处置 |
| ③ | 商品与类目规模分布 | ○ | 73 个类目只有 14 个被用过，这个数没有一处显示 |
| ③ | 审核吞吐与通过率 | ○ | 平均等多久、驳回原因分布 |
| ③ | 上架率 | ○ | 200 个 SPU 只有 4 个上架 |
| ③ | 条码 / 货号覆盖率 | ○ | 209 个 SKU 里 1 个有条码。**扫码功能的天花板就是这个数** |
| ③ | 规格库使用率 | ○ | 34 个规格维度，哪些从没被选中。规格库只增不减，清理依据不存在 |
| ④ | 商品池 | ✅ | |
| ④ | 单商品全链路状态 | ○ | 审核到哪了、建账了吗、有库存吗、卖了多少 |

### 4.4 进销存域

平台管的不是「商家有多少货」，是**这本账可不可信** ——
库存不准的代价（下单失败、超卖赔付、纠纷无据）全都落在平台身上。

| 类 | 功能 | 状态 | 说明 |
|---|---|---|---|
| ① | 谁能用哪些功能 | ○ | 进货 / 调拨 / 建仓 / 报表今天对所有商家免费全开 |
| ① | 预留 TTL 上限 | ○ | TTL 由调用方传，平台没有兜底；传个很长的值就能把货占住 |
| ① | 对差容忍度与处置阈值 | ○ | 差多少算「不可信」，触发什么 |
| ① | 入库必填项 | ○ | 成本价、供应商填不填，决定将来毛利口径能不能算 |
| ① | 安全库存平台默认值 | ○ | |
| ① | 单位字典 | ○ | `inv_uom` 建了表却一处读它的代码都没有（维护页已撤销，见 INV-P7） |
| ② | 开放对接凭据 | ◐ | 唯一的写口，但它改的是「谁能读这些货」，是授权不是治理 |
| ② | 提醒商家记账 / 修账 | ○ | |
| ② | 库存存疑打标 | ○ | 影响曝光权重，比直接下架轻 |
| ② | 手动补投影 | ○ | 发现账外 SKU 之后做不了任何事 |
| ③ | 库存健康度 · 库存对差 | ✅ | |
| ③ | 采用漏斗 | ○ | **6 家商家里 2 家在用**，运营端答不出这个数 |
| ③ | 投影链路健康度 | ◐ | 账外数被折叠进「对差」的 `pending` 里，每天只跑一次。见 §五 |
| ③ | 对差趋势 | ○ | 只有当天的数，而判据是「连续 N 天为零」 |
| ④ | 库存流水 | ✅ | 商家 → SKU → 变动明细，无任何修改入口 |
| ④ | 单商家进销存概况 | ○ | 记了多少笔、最近一笔什么时候、账实差多少 |

## 五、链条视角：越靠后，运营越只剩「看」

把同一批功能按链条七段重排，会看出另一个形状：

| 段 | 谁做 | ① 设置 | ② 管理 | ③ 统计 | ④ 查看 |
|---|---|---|---|---|---|
| 01 配类目、绑规格 | 运营 | 9 项 | 类目授权 | ○ | ○ |
| 02 建 SPU | 商家 | ○ | 审核队列 | ○ | 商品池 |
| 03 生成 SKU 矩阵 | 系统 | ○ | — | ○ | 商品池 |
| 04 填价 / 条码 / 单位 | 商家 | ○ | 预售额度 | ○ | 商品池 |
| **05 投影建账** | 系统 | ○ | ○ | ◐ | ○ |
| 06 入库过账 → 上架 | 商家 | ○ | **○ 一件都没有** | ○ | 库存流水 |
| 07 下单预留 → 出库 | 系统 | ○ | **○ 一件都没有** | 健康度 · 对差 | 库存流水 |

**01 有 9 项设置、1 项管理动作；到 06 与 07，管理这一栏整个是空的。**
而越靠后的环节，出问题的代价越直接落在买家身上。

### 05 是最脆的一跳，而运营端对它几乎没有可见性

它是**整条链上唯一的跨域跳**（商品域 → 进销存），也是唯一异步的一跳。

2026-09-02 实际发生过：投递任务停着，一条 `SKU_UPSERTED` 在队列里躺了六个小时 ——
那件货在库存里不存在，商家看不到、盘不着、进不了货，**而任何地方都不会报错**。
它在运营端的唯一痕迹，是「库存对差」里的「待搬 1 个」。

问题在于：**这是链路问题，却被折叠进了一个数据指标**。运营看到那个数，
推断不出「投影链路断了」；而它每天只跑一次。

## 六、三处错位（不是缺口，是放错了地方或叫错了名字）

### 「类目 × 支付方式」名不副实

看到这个名字会以为是配微信 / 支付宝，而它实际只管一件事：
**这个类目能不能当面付**（四层判定「类目 → 主体资质 → 门店 → 商品」的第一层，黑名单制）。

业务上成立：当面付意味着平台收不到钱、没有流水、无法对账与风控，
所以高风险类目该被禁 —— **类目在这里是风控维度**。
但名字该改成「当面付禁用类目」之类，否则每个第一次看到它的人都要重新问一遍。

### 「增值包与额度」一个 tab 混了 ① 和 ②

它同时管「定义档位」（`planDefs` / `savePlanDef`，一年动几次的产品决策）
与「授予某商家」（`grantPlan` / `overridePlanQuota`，天天做的运营动作）。
混在一屏，前者会被后者的噪声淹没。而它正是分层落地前必须理清的地基。

### 进销存的三条命脉挂在「系统配置」下

事件投递、预留回收、日快照在 `/jobs` 页。2026-09-02 之前这三个任务全是关着的，
六条跨域链路堵了整整一天，而进销存那四个 tab 上**看不出任何异常** ——
因为它们读的是数据，不是链路。

## 七、补的顺序

1. **审核积压主动告知**（商品②）—— 194 件等 14 天是今天最贵的一处堵。
   一个角标的成本，和它挡住的 194 个商品不成比例。
2. **商家维度的链条画像**（贯穿③）—— 一家一行：建品 → 提审 → 上架 → 建账 →
   首次进货 → 持续记账。一次补上商品与进销存两个域的统计空白，
   而且它**指向具体的人**，不只是一个报表。
3. **投影链路健康度**（05③）—— 把它从「对差」里拆出来。队列积压、最近成功时间，
   这是链路问题不是数据问题。
4. **最轻的干预：提醒**（②）—— 消息通道已有，接上即可。比「限制接单」这类强动作先做。
5. **拆开增值包的两类职责**（①/②）—— 成本低，是分层落地的地基。
6. **进销存的平台规则**（①）—— 预留 TTL 上限最要紧（今天可以被一个长 TTL 把货占住），
   其余等业务量起来。

### 一条判断的依据

**每一层流失都对应一个具体的帮助动作，而不是一个报表。**
194 件卡审核 → 该催的是审核的人；条码 1/209 → 该给商家一个批量导入；
6 家里 2 家在记账 → 该知道另外 4 家卡在建账还是卡在第一笔进货。
统计的价值在于**它指向谁**。
