## 一、方法：先推导应然，再对齐实然

按四类运营职责推导每个域该有什么，**然后才去对齐今天有什么**：

| | |
|---|---|
| ① **全局设置** | 平台定规则，与具体商家无关 |
| ② **商家 / 门店管理** | 对某一家动手：准入、授权、处置、干预 |
| ③ **平台数据统计** | 跨商家聚合，回答「整体怎么样」 |
| ④ **商家数据查看** | 单家明细，只读 |

**顺序不能反。** 从现有功能倒推分类，只能得到「现有功能的一种分法」——
从没做过的那些不会出现在任何格子里，而那恰恰是要找的东西。

## 三、这条链今天的真实流量

沿「配类目 → 建品 → 建账 → 进货 → 售出」实测（2026-09-03，线上库）：

```
73   平台类目
14   ← 被商品用到的（59 个类目没人用）
200  商家建的商品（SPU）
194  ← 卡在审核中，最早的提交于 08-20，等了 14 天
4    ← 买家能看到的（已上架）
209  SKU
1    ← 填了条码的（货号 0 个）
209  进销存里的物料（建账成功，一个不缺）
2    ← 真在记账的商家（共 6 家）
6    ← 出库流水（进货 216 条）
```

**每一层都在流失，而运营端一层都看不见。**
这条链上没有任何一处能回答「上一步到这一步掉了多少、掉在谁身上」。

已有的三块统计（库存健康度、库存对差、获客看板）都是**某一环的快照**，
没有一处是**贯穿链条的漏斗**。而上面这组数说明：真正的问题不在某一环内部，
在环与环之间的落差。

## 四、逐域清单

图例：**✅** 已有 · **◐** 有一半或藏在别处 · **○** 缺

### 4.1 商家域

平台管商家的本质是三件事：**让不该进来的进不来、让进来的守规矩、让守规矩的活下去**。
前两件今天做得最全，第三件几乎没有。

| 类 | 功能 | 状态 | 说明 |
|---|---|---|---|
| ① | 类目准入规则 | ✅ | 哪些类目要哪张证 |
| ① | 保证金与限额规则 | ✅ | 准入门槛按类目配 |
| ① | 增值包档位定义 | ✅ | 与「授予」混在同一个 tab，见 §六 |
| ① | 信用规则 | ○ | 几次违规降级、几次封禁。今天是人工判断 |
| ① | 认证标授予标准 | ○ | 什么条件够格，今天靠运营记忆 |
| ② | 入驻审核 · 类目授权 · 资质到期 · 准入保证金 · 认证标 · 违规处置 · 增值包授予 | ✅ | 7 项 |
| ② | 主动触达商家 | ○ | 发现问题后唯一的轻量动作，消息通道已有、没接 |
| ② | 代操作 | ✅ | **判错了** —— `POST /ops/skus/{no}/force-off` 早就有，商品池抽屉里有按钮 |
| ③ | 进件看板 · 无照自营风险 | ✅ | |
| ③ | 商家活跃与流失 | ○ | 多久没上过新品、没记过账、没出过单 |
| ③ | 分层分布 | ○ | 各档位多少家、升降级趋势。分层落地后必需 |
| ④ | 商家 / 门店 / 资质 / 信用 四个档案 | ✅ | |
| ④ | 一家商家的全景 | ○ | 今天要在四个档案 + 商品池 + 库存流水之间跳，各自主键不同 |

门店是**真正的履约与库存单位** —— 多门店商家的货、单、码都挂在门店上。
但运营端今天只把它当作「一个要审核店招的页面」。

| ① | 主页模板配置 | ✅ | |
| ① | 店招公告的合规规则 | ✅ | **判错了（第四次）** —— `MerchantStoreServiceImpl.screen()` 早就在发布前机审，命中转人审并保留旧公告。真问题是它的词表在 `sys_setting` 里、**没有任何运营入口**（V10 种了 8 个词，维护页从来没建），现已接上「禁售词」那一份 |
| ① | 单商家门店数上限 | ○ | 增值包里有 `storeQuota`，那是按家配，不是平台底线 |
| ② | 店招公告审核 · 店铺码生成导出 | ✅ | |
| ② | 门店启停 | ✅ | **判错了** —— 压下在「违规处置」选 `STORE_OFFLINE`（带门店选择器），解除在门店档案抽屉里 |
| ③ | 获客效果看板 | ✅ | 一行一门店 |
| ③ | 门店经营排行 | ✅ | 看板加一张，与商家排行并排。**带所属商家名** —— 两家都在垫底时，「同一个老板的」与「两家不相干的」该做的事完全不同 |
| ③ | 网点覆盖与密度 | ○ | 与社区网格结合才答得出「这片区够不够」 |
| ④ | 单店经营明细 | ✅ | **此前判错了，见下** —— 门店档案点开一行，抽屉里有今日/本月订单与 GMV、自带客流占比、四项待办堆积 |

### 4.3 商品域

平台在这个域的角色是**画骨架（类目与规格）+ 守门（审核）**。
骨架画得最全，守门有入口但不会找上门，而**整个域没有一个统计数字**。

| 类 | 功能 | 状态 | 说明 |
|---|---|---|---|
| ① | 类目树 · 规格库 · 类目×规格 · 标准品库 · 主题分类 | ✅ | 6 项，全域最全 |
| ① | 类目 × 当面付 | ◐ | 菜单叫「类目 × 支付方式」，**名不副实**，见 §六 |
| ① | 类目 × 积分 | ✅ | 生鲜与家电不该同一比例；商品级配置实测 0% 填充率，所以收到类目层 |
| ① | 建品前置约束 | ◐ | 禁售词已做（V312，提审当场拒并点名那个词）。必填图与标题规范仍缺 |
| ① | SKU 数量上限 | ◐ | 代码里 `MAX_SKUS = 100` **已在拦**，缺的是「运营能改」而不是「没有上限」 |
| ① | 条码与货号规范 | ○ | EAN-13 校验、商家货号格式 |
| ② | 商品审核队列 · 预售额度与超卖 | ✅ | |
| ② | 审核积压主动告知 | ✅ | 看板加「待审商品」待办卡（件数 + 最早等了几天），整卡点进审核队列。顺带补了 `AUDITOR` 的看板权限 —— 见 §七.1 |
| ② | 强制下架单个商品 | ✅ | **判错了** —— SKU 级与整件级都有（整件 = 撤销过审，商家必须改完重新提审） |
| ③ | 商品与类目规模分布 | ○ | 73 个类目只有 14 个被用过，这个数没有一处显示 |
| ③ | 审核吞吐与通过率 | ○ | 平均等多久、驳回原因分布 |
| ③ | 上架率 | ○ | 200 个 SPU 只有 4 个上架 |
| ③ | 条码 / 货号覆盖率 | ○ | 209 个 SKU 里 1 个有条码。**扫码功能的天花板就是这个数** |
| ③ | 规格库使用率 | ○ | 34 个规格维度，哪些从没被选中。规格库只增不减，清理依据不存在 |
| ④ | 商品池 | ✅ | |
| ④ | 单商品全链路状态 | ○ | 审核到哪了、建账了吗、有库存吗、卖了多少 |

### 4.4 进销存域

平台管的不是「商家有多少货」，是**这本账可不可信** ——
库存不准的代价（下单失败、超卖赔付、纠纷无据）全都落在平台身上。

| 类 | 功能 | 状态 | 说明 |
|---|---|---|---|
| ① | 谁能用哪些功能 | ○ | 进货 / 调拨 / 建仓 / 报表今天对所有商家免费全开 |
| ① | 预留 TTL 上限 | ✅ | 上限已加（默认 24h，可配）。**原来那句话说过头了**：今天三个调用方传的都是 30 分钟常量，开放 API 也没有 reserve —— 它堵的是下一个调用方 |
| ① | 对差所需连续轮数 | ✅ | **原条目叫「容忍度」，方向反了** —— 对库存来说任何差异都是账错了，该配的不是「差多少能忍」，是「连续几轮为零才够格切」。此前那个 N 根本不存在 |
| ① | 入库必填项 | ◐ | **采购入库已强制要成本价**（`InboundServiceImpl` 里在拦），缺的是「运营能配哪些必填」而不是「完全没规则」 |
| ① | 安全库存平台默认值 | ⊘ | **不做**：读它的地方在 `shop-inventory`，而那是刻意隔离的模块（独立库、零 SPI 引用，为的是能单独交付）。为一个默认值拆掉那道边界不值 |
| ① | 单位字典 | ⊘ | **不做**：`inv_uom` 至今零读者。给一张没人读的表做维护页，是把「没接上」这件事盖住 |
| ② | 开放对接凭据 | ◐ | 唯一的写口，但它改的是「谁能读这些货」，是授权不是治理 |
| ② | 提醒商家记账 / 修账 | ○ | |
| ② | 库存存疑打标 | ○ | 影响曝光权重，比直接下架轻 |
| ② | 手动补投影 | ○ | 发现账外 SKU 之后做不了任何事 |
| ③ | 库存健康度 · 库存对差 | ✅ | |
| ③ | 采用漏斗 | ○ | **6 家商家里 2 家在用**，运营端答不出这个数 |
| ③ | 投影链路健康度 | ◐ | 账外数被折叠进「对差」的 `pending` 里，每天只跑一次。见 §五 |
| ③ | 对差趋势 | ✅ | 对差页顶上给「已连续 N 轮为零」。**数据本来就在**：`inv-recon` 每天一轮，结论落在它自己的运行记录里 —— 另存一份迟早两处两种说法 |
| ④ | 库存流水 | ✅ | 商家 → SKU → 变动明细，无任何修改入口 |
| ④ | 单商家进销存概况 | ○ | 记了多少笔、最近一笔什么时候、账实差多少 |

## 五、链条视角：越靠后，运营越只剩「看」

把同一批功能按链条七段重排，会看出另一个形状：

| 段 | 谁做 | ① 设置 | ② 管理 | ③ 统计 | ④ 查看 |
|---|---|---|---|---|---|
| 01 配类目、绑规格 | 运营 | 9 项 | 类目授权 | ○ | ○ |
| 02 建 SPU | 商家 | ○ | 审核队列 | ○ | 商品池 |
| 03 生成 SKU 矩阵 | 系统 | ○ | — | ○ | 商品池 |
| 04 填价 / 条码 / 单位 | 商家 | ○ | 预售额度 | ○ | 商品池 |
| **05 投影建账** | 系统 | ○ | ○ | ◐ | ○ |
| 06 入库过账 → 上架 | 商家 | ○ | **○ 一件都没有** | ○ | 库存流水 |
| 07 下单预留 → 出库 | 系统 | ○ | **○ 一件都没有** | 健康度 · 对差 | 库存流水 |

**01 有 9 项设置、1 项管理动作；到 06 与 07，管理这一栏整个是空的。**
而越靠后的环节，出问题的代价越直接落在买家身上。

### 05 是最脆的一跳，而运营端对它几乎没有可见性

它是**整条链上唯一的跨域跳**（商品域 → 进销存），也是唯一异步的一跳。

2026-09-02 实际发生过：投递任务停着，一条 `SKU_UPSERTED` 在队列里躺了六个小时 ——
那件货在库存里不存在，商家看不到、盘不着、进不了货，**而任何地方都不会报错**。
它在运营端的唯一痕迹，是「库存对差」里的「待搬 1 个」。

问题在于：**这是链路问题，却被折叠进了一个数据指标**。运营看到那个数，
推断不出「投影链路断了」；而它每天只跑一次。

## 六、三处错位（不是缺口，是放错了地方或叫错了名字）

### 「类目 × 支付方式」名不副实

看到这个名字会以为是配微信 / 支付宝，而它实际只管一件事：
**这个类目能不能当面付**（四层判定「类目 → 主体资质 → 门店 → 商品」的第一层，黑名单制）。

业务上成立：当面付意味着平台收不到钱、没有流水、无法对账与风控，
所以高风险类目该被禁 —— **类目在这里是风控维度**。
但名字该改成「当面付禁用类目」之类，否则每个第一次看到它的人都要重新问一遍。

### 「增值包与额度」一个 tab 混了 ① 和 ②

它同时管「定义档位」（`planDefs` / `savePlanDef`，一年动几次的产品决策）
与「授予某商家」（`grantPlan` / `overridePlanQuota`，天天做的运营动作）。
混在一屏，前者会被后者的噪声淹没。而它正是分层落地前必须理清的地基。

### 进销存的三条命脉挂在「系统配置」下

事件投递、预留回收、日快照在 `/jobs` 页。2026-09-02 之前这三个任务全是关着的，
六条跨域链路堵了整整一天，而进销存那四个 tab 上**看不出任何异常** ——
因为它们读的是数据，不是链路。

### 第四次：店招合规规则

`screen()` 早就在公告发布前机审，命中转人审并保留旧公告 —— 正是缺口清单写的
「禁用词前置，而不是发出来再审」。这次连菜单都不用看，是<b>我没去读那个 service</b>。

真问题不是没有规则，是**词表没有维护入口**：它在 `sys_setting` 的一个 JSON 数组里，
V10 种了 8 个词、注释写着「运营要能随时加词」，而那个页面四年没建。
现已接上 V312 的禁售词表 —— **一份词表，两处生效，两种处置**：
公告命中转人审（时效内容，全部先审后发等于这个功能没用），
商品标题命中当场拒（本来就要过审，早拒一步省的是审核员的时间）。

### 同一个错又犯了三次 —— ②「管理动作」那一栏

M6 的三条（强制下架单个商品 / 门店启停 / 代操作）**全部早就实现**，
而且都有按钮：SKU 级与整件级 force-off 在商品池抽屉里，
门店压下在「违规处置」里选 `STORE_OFFLINE`（带门店选择器），解除在门店档案抽屉里。

**与下面那条是同一个错**：这些动作是<b>点开某一行之后</b>才出现的按钮，
在菜单树上不存在。而这份矩阵对齐「今天有什么」时看的是菜单。

**修正后的口径**：④ 与 ② 这两栏都不能只看菜单 ——
④ 是「点进去看」，② 是「点进去做」，两者按定义都藏在列表行的后面。
逐条复核之后，矩阵从 32.5/70 改到 **37/70**：多出来的 4.5 项<b>一行代码都没写</b>，
是原来数错了。

> 顺带一条量的更正：「预留 TTL 上限」原文写「今天传个很长的值就能把货占住」——
> **不成立**。三个 `reserve` 调用点传的都是 30 分钟常量，开放 API 只有
> items / ledger / sync，没有 reserve。上限还是加了（默认 24h），
> 但它堵的是<b>下一个</b>把 TTL 接到外部输入的调用方，不是一个正在被利用的洞。

### 「单店经营明细整个是空的」—— 判错了

`/ops/stores/{storeNo}/stats` **早就实现，前端也早就在调**：门店档案点开一行，
抽屉里有今日/本月订单与 GMV、自带客流占比、待发货/待自送/缺货/待售后四项堆积，
九个字段一个不少，注释还写着为什么这么排。

**错在哪**：这份矩阵对齐「今天有什么」时，是顺着菜单树看的 ——
而配套的[功能清单](../technical/reference/运营端-功能清单.md)按定义就是
`nav.ts` 的投影：**它只看得见菜单叶子**。而单店经营明细不是一个菜单项，
它是门店档案里点一行弹出来的抽屉。

这类东西（抽屉、行内展开、点开某行才出现的详情）在菜单维度上不存在，
于是「没有这个菜单」被读成了「没有这个功能」。
**同一类错在④这一栏最容易犯** —— 「查看某一个 X 的明细」按定义就是从列表点进去的，
几乎不会有自己的菜单。所以这一栏的每一条都该<b>去页面里翻一遍</b>再下结论。

（M5 逐条复核的结果：门店④ 已实现；商家④「全景」实现了大半，
缺的是商品与进销存那一段；进销存④「概况」确实缺。）
