# 交付计划：商家侧（从注册登录开始）

> 2026-08-09 · **交付单位是「商家能完成的一件事」，不是端点或页面。**
> 一件事没有全链路打通（端 → API → Controller → Service → Mapper → DB → 测试），就不算交付。
>
> 进度数字见 [三端全栈对齐清单](../technical/三端全栈对齐清单.md)（`npm run gen:delivery` 自动重算）。
> 流程口径见 [B端与运营端-从注册开始的流程梳理](./B端与运营端-从注册开始的流程梳理.md)。

---

## 零、交付的定义

一项交付要同时满足这五条，缺一条都算「在做」而不是「做完」：

| # | 条件 | 怎么验 |
|---|---|---|
| 1 | 端上有入口，人能点到 | 手动走一遍 |
| 2 | 后端有实现，不是 mock | `npm run gen:delivery` 里它不在缺口表 |
| 3 | 有**场景测试**，覆盖成功与至少一种失败 | `mvn test` |
| 4 | 真库跑通过一次 | 真实 MariaDB + 真实 HTTP |
| 5 | 契约与守卫全绿 | `npm test` · `npm run check:api` |

> **为什么第 3 条要求「至少一种失败」**：只测成功路径的测试，等于把「资料不齐会被拒」
> 「越权门店号不认」这类分支永久留在开发期之外 —— 而它们才是真实世界里最常发生的。

**状态标记**：✅ 已交付 · 🔨 进行中 · ⬜ 未开工 · ⚠️ 待决策

### 每项交付的验收清单模板

下面每个阶段的「验收点」都按这四类列，**四类缺一不可**：

| 类 | 问什么 |
|---|---|
| **正路** | 他要做的那件事，做成了吗 |
| **越权** | 别家的数据，他能不能碰到 —— *测不到就等于没有* |
| **业务规则** | 系统该拦的拦住了吗（必填、状态、额度、幂等） |
| **可观测** | 出问题时，能不能查到是谁在什么时候做的 |

用例与代码的对应见[测试用例清单](../technical/测试用例清单.md)。

## 四、阶段 D：做生意（🔨 进行中 —— D1/D2 已交付，余 10 项）

现在他能开店、能上架、能收到单，但**收到单之后要做的每一件事都没有后端**。

> ✅ **D1–D2 已交付**（`BizOrderFulfillFlowTest` 5 用例 + 真库七步）。
>
> 做的过程中查出并补掉一个更基础的缺口：**`OrderVO` 里根本没有 `expressNo`** ——
> 库里有这一列、shared 契约里有这个字段，而后端 VO 没带出来。
> 也就是说即使发了货，**买家也看不到快递单号** —— 那发货这件事对买家就没有意义。
> 现已在买家/商家/平台三个视角的 VO 里都带上。
>
> 另一处收获：重复发货的语义。状态机对 `from==to` 是幂等友好的（为回调重放设计），
> 所以「重复发货」不会被拒 —— 于是要在服务层区分：同单号重发是空操作，
> **换单号是「改单号」：允许但必须留痕**（填错单号要能改，拒了商家只能打客服；
> 而静默改掉买家看到的物流号，是纠纷的开始）。

## 六、Review 与测试的做法

每交付一项，按这个顺序走一遍 —— **顺序是有讲究的**：

| 步 | 做什么 | 为什么在这一步 |
|---|---|---|
| 1 | 先写**失败用例**，再写实现 | 先写成功路径的话，失败分支多半就不写了 |
| 2 | `mvn -o -f shop-app/pom.xml test` | H2 跑得快，先把逻辑锁住 |
| 3 | `npm test` + `npx vue-tsc` | 契约与类型 |
| 4 | `npm run check:api` | 端点在三端与后端之间不许漂 |
| 5 | **真库跑一次**（重置库 → 启动 → curl 走链路） | H2 与 MariaDB 的差异只有真库能暴露（本轮踩过三次） |
| 6 | `npm run gen:delivery` | 把这一项从缺口表里划掉 |

> **第 5 步不能省**。本轮真库暴露过：`GoodsVO` 字段名与我写的类型对不上、
> 待审队列没过滤、`/biz/order` 被数据域按 `user_no` 过滤成空 ——
> 这三条在 H2 单测里全是绿的。
