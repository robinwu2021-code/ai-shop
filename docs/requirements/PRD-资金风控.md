## L1 · 一句话

**资金风控的目标不是「拦住坏人」，是「让钱出去之前有人看过」。**

它只拦三处 —— 放款前、退款前、进件时 —— 而且**处置一律是挂起加人工，不自动拒绝**。

---

## 1. 为什么取向是「宁可漏放」

两个方向的错，代价不对称：

| | 后果 | 可逆吗 | 有没有第二道防线 |
|---|---|---|---|
| **漏放** | 钱出去追不回（Z4） | 基本不可逆 | ✅ 保证金 → 欠款抵扣 → 停止放款 |
| **误伤** | 真实商家的货款被冻住 | 钱可逆，**信任不可逆** | ❌ 没有 |

直觉说「漏放更严重，宁可多拦」。**在这里这个直觉是错的**：
漏放有三层兜底，误伤一层都没有；而且被误伤的商家不会等我们排查完。

> 这一条决定了后面所有阈值的方向：**先松后紧，用影子模式找位置**，
> 而不是先设一个「安全」的严阈值再慢慢放松 —— 后者的每一天都在制造误伤。

## 2. 三个拦截点

### P1 · 进件时

| 拦什么 | 判据 | 处置 |
|---|---|---|
| 主体黑名单 | `risk_blacklist` 命中 | 拒绝，给出原因 |
| 同一证照多主体 | 同一执照号已被其他主体使用 | 转人工 |
| 结算账户异常 | 同一账户绑定多个不相关主体 | 转人工 |

**验收**

- AC-P1.1 拒绝要给**可申诉的原因**，不是「不符合条件」
- AC-P1.2 转人工的进件在商家侧显示「审核中」并给**预计时长**
- AC-P1.3 拒绝后可重新提交（进件是低代价可重试的动作）

### P2 · 放款前 ★ 主战场

批次从 `RECONCILED` 走向 `RELEASED` 的那一刻。

| 信号 | 判据 | 数据在 |
|---|---|---|
| **退款率突增** | 近 N 天退款额 / 成交额 > 阈值 | 支付库 |
| **集中大额** | 本批放款额 > 保证金 × 倍数 | 支付库 |
| **欠款未清** | `mch_debt` 余额 > 0 | 支付库 |
| **交易形态异常** | 同人同店高频 / 整数额集中 / 深夜集中 | 支付库 + 订单 |
| **主体名单命中** | 黑名单或关联主体 | 主库 `risk_*` |

**验收**

- AC-P2.1 命中则**整批挂起**，不逐单放行
- AC-P2.2 商家能看到「本批因 XX 转人工复核」，**判据说人话**（含具体数字与阈值）
- AC-P2.3 挂起有**时限**，超时**自动放行并告警**
- AC-P2.4 人工放行 / 继续挂起都**必须写原因**，留痕
- AC-P2.5 影子模式下只记录不拦截，且记录与真拦截**用同一套判据代码**

> AC-P2.5 是防「影子模式测的不是将来要跑的那件事」——
> 两套代码的话，切真拦那天的行为与影子期观察到的不是同一个东西。

### P3 · 退款前

| 拦什么 | 判据 | 处置 |
|---|---|---|
| 退款滥用 | 同一买家对同一店高频退 | 转人工裁决 |
| 金额异常 | 退款额 > 原单额 | **硬拦**（这是错误不是风险） |

**验收**

- AC-P3.1 **不自动拒绝退款** —— 拒的是买家，直接变成投诉与监管风险
- AC-P3.2 金额超原单是**数据错误**，硬拦并告警，不进人工队列
- AC-P3.3 转人工期间买家侧显示「处理中」，不显示「已拒绝」

## 3. 处置权限表

| 动作 | 自动 | 人工 | 谁 |
|---|---|---|---|
| 挂起放款 | ✅ | ✅ | 系统 / 风控 |
| 超时自动放行 | ✅ | — | 系统（**必告警**） |
| 人工放行 | — | ✅ | 风控（写原因） |
| 拒绝进件 | ✅ | ✅ | 系统 / 风控 |
| 扣划保证金 | ❌ | ✅ | 财务（法务边界未定，见 §6） |
| 拒绝退款 | ❌ | ✅ | 售后裁决 |
| 封禁主体 | ❌ | ✅ | 既有风控域，本文不改 |

## 4. 影子模式：上线前必须先跑

**不先跑影子模式就定阈值，等于拿真实商家的货款做实验。**

```
第 1–2 周   只记录：命中了谁、命中了什么规则、如果真拦会拦住多少钱
第 3 周     复盘：命中的都是什么人？其中有几个是真问题？
第 4 周     定阈值 → 小范围真拦（先只对新商家 / 小额批次）
```

**开跑之前就要定好「凭什么说可以真拦了」**，否则两周后只会得到一堆数字和一次拍脑袋。
建议的判据：

| 判据 | 目标 |
|---|---|
| 命中批次占比 | < 5%（高于此说明阈值太松，噪声淹没信号） |
| 命中中确认为真问题的比例 | > 30%（低于此说明规则选错了信号） |
| 单条规则的独立贡献 | 每条规则至少要有一次**只有它命中**的案例，否则它是冗余的 |

第三条是防「一堆规则其实在说同一件事」——那种规则集看着覆盖很全，
实际上只有一个维度，而且调其中任何一条都不会改变结果。

---

## 5. 商家侧要看到什么

被拦住的商家会做三件事：找客服、发火、准备走。**能减少这三件事的只有信息。**

| 场景 | 商家看到 | 不要写 |
|---|---|---|
| 批次挂起 | 「本批 3,240 元因近 7 天退款率 32%（阈值 20%）转人工复核，预计 2 个工作日」 | 「风控审核中」 |
| 有欠款 | 「待抵扣 128 元，将从下一批货款中扣除」 | 悄悄扣掉不说 |
| 进件被拒 | 原样给通道的驳回原因 + 我方的补充 | 「不符合准入条件」 |
| 保证金被扣 | 扣了多少、因为哪一单、什么时候 | 只改余额不给流水 |

> **每一条都要能对上一笔具体的钱。**说不出是哪一笔的提示，
> 商家读完之后还是要找客服 —— 那这条提示等于没有。

## 6. 待确认（不确认不能上线）

1. **阈值全部未定** —— 见 §4，先跑影子模式
2. **保证金扣划的合规边界**：未经商家同意扣款，协议怎么写、要不要事前通知（法务）
3. **欠款止损线**：欠多少停止合作、走什么流程、谁批
4. **挂起时限定多久**：2 个工作日是建议值，要与运营的实际处置能力对齐 ——
   定得比处置能力短，超时放行就会变成常态，那道门就形同虚设
5. **影子模式的准入判据**：§4 的三条是建议，要在开跑前定死
