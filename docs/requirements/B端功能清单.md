## 〇、一句话产品

**让小店把自己的老客搬到线上并留住**：填一张表就开张（个人主体免资质），一部手机管完接单、分拣、核销、结算。
不是给大商家用的后台——**自带客流佣金 0%**，平台不靠抽小店的佣金赚钱。

## 一、角色

| 角色 | 能做什么 | 状态 |
|---|---|---|
| 店主 | 全部 | ✅ |
| 自提点承接方 | 核销、分拣、到货确认（**只看得到履约必需字段**，看不到金额与完整手机号） | ✅ |
| 店员 | 受限子账号 | ⬜ 开放入驻后必做 |

### B-6 履约（自提点）

| 编号 | 功能 | 逻辑 | 契约 |
|---|---|---|---|
| B-6.0 | **履约总览** | 承接方进来最关心的三个数：待核销 / 今日到货 / 累计服务费。**都从同一份订单数据算**，不另存计数器——否则迟早「总览说 3 单、点进去只有 2 单」 | `mPickupOverview` |
| B-6.1 | 待到货订单 | | `mPickupOrders` |
| B-6.2 | 分拣单 | 按商品聚合（分货用）/ 按用户聚合（装袋用）两种视图 | `mPickingList` |
| B-6.3 | 到货确认 | 批量标记到货并通知邻居，`PREPARING → ARRIVED` | `mMarkArrived` |
| B-6.4 | 核销 | 输码或扫码。**校验三件事**：码有效、未核销过、**这单属于本自提点** | `mVerify` |
| B-6.4b | **批量核销** | 连续扫多张、最后一次提交。**逐条尝试、失败逐条回报**，不整批回滚——一张废码不该让另外四单白扫，而「3 成功 2 失败」这种汇总店主还得自己找是哪两单 | `mVerifyBatch` |
| B-6.5 | 核销即完成 | `PREPARING` 的单核销时先补 `ARRIVED` 再转 `COMPLETED`，不跳状态 | `mVerify` |
| B-6.6 | 破损/短少上报 | **只留痕并通知用户，不自动退款**——责任归属未定，自动退等于默认平台兜底 | `mReportShortage` |
| B-6.7 | 分拣单打印/导出 | ⬜ 到货当日高频，手机上看着分货容易串 | — |
| B-6.8 | 配送规则 | 起送价、配送费、免配送门槛、覆盖范围 | `mDeliveryRule` `mSaveDeliveryRule` |

> ⚠️ **自提点可见字段**：承接方会看到**别家商家**的货来核销，字段必须裁剪到履约必需（取货码/品名/数量/昵称），不得暴露金额与完整手机号。边界清单待定（B12）。

## 七、真实性边界

前端全部跑 mock（`VITE_USE_MOCK=1`）。mock 里**有真规则**：状态机强制、资质校验、核销三校验、活动时间校验、结算公式都真算；**没有的**是支付、图片、识别模型、平台人工审核。
首次打开会自动播一个演示商家（M002 阿明果蔬合作社）与一批待办单——否则各页面全空，看着像功能坏了。

## 维护约定

1. **数字不写在这里**——交易规则值一律引用[规则表](需求矩阵-三端.md#七之二交易规则常量唯一事实源)，它由 `npm run gen:rules` 从代码生成。文档里复述一次，就会有一处忘了改。
2. **跨端引用用 ID**（`C-AS-06` / `B-7.3` / `P-6.1`），不写「另一端那个功能」。ID 在三份清单之间可解析，改名时能查出所有引用点。
3. **状态取自代码**，不是计划：功能点的 ✅/⬜ 以页面与契约是否存在为准；平台端的 `ready/soon/phase2` 直接来自 `ops-web/lib/nav.ts`。
4. **发现文档与代码不符，改文档**——代码是事实。若代码本身错了，先改代码再回来改这里。
