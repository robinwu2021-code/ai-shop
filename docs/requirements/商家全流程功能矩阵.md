## 零、一页看懂这条链

```
① 注册            商家账号（mch_account）
      │             ⚠️ 现状：入驻仍由消费者账号发起
      ▼
② 入驻申请        mch_entity_apply         商家填：名称/法律形态/行业/联系人/服务范围/资质
      │
      ▼  平台审核（ops）
③ 主体激活        mch_entity               ← 一张营业执照 = 一个主体
      │  自动派生三件事（同事务）
      ├─→ owner 账号   mch_account
      ├─→ 默认门店     mch_store（ST-{entityNo}）
      └─→ 进件占位     mch_payment_merchant（APPLYING）
      │
      ▼
④ 收款进件        pay_merchant_no ← 通道返回 sub_mchid    ⬜ 只有占位，没有推进链路
      │
      ▼
⑤ 门店            mch_store（多店/切主体/换收款号）+ mch_store_role（员工逐店角色）
      │
      ▼
⑥ 分类            prd_category（平台树，运营维护）
      │
      ▼
⑦ 商品目录        prd_goods + prd_sku      ← 挂**主体**，录一次
      │
      ▼
⑧ 门店选品/库存   prd_store_listing + prd_store_stock   ⬜ M3，当前靠 prd_community_pool 近似
      │
      ▼
   顾客可见 = 门店服务区域 ∩ 平台已开城 ∩ 门店在架
```

**一句话口径**：**注册的是账号，审核的是执照，卖货的是门店，商品挂主体、上架挂门店。**

## 五、分类（S5）

分类在这套模型里是**三层不同的东西**，最容易混：

| 层 | 是什么 | 谁维护 | 数据 | 状态 |
|---|---|---|---|---|
| **平台类目** | 全平台统一的三级树，决定资质要求与属性模板 | 平台运营 | `prd_category` | 🟡 有表有树，**没有运营维护接口**（靠 DevSeeder 灌） |
| **商品归类** | 这件商品属于哪个平台类目 | 商家 | `prd_goods.category_no` | ✅ 商品编辑时选 |
| **门店分组** | 顾客在店内看到的货架分组 | —— | 由选品派生 | ⬜ 依赖 M3 选品 |

| # | 功能 | 接口 | 状态 |
|---|---|---|---|
| 5.1 | C 端读类目树 | `GET /mp/category/tree` | ✅ |
| 5.2 | 商品选类目 | 商品保存时带 `categoryNo` | ✅ |
| 5.3 | 端 × 品类可售规则（iOS IAP 约束等） | `sys_channel_category_rule`（25 条种子） | ✅ |
| 5.4 | **运营维护类目树**（增删改、排序、启停） | `GET/POST /ops/categories` · `/{no}/archive` · `/unarchive` | ✅ 含 `showArchived` 全量视图 |
| 5.5 | 类目绑资质要求 → 上架时校验 | `required_code` × `mch_entity.category_codes` | ✅ 校验在**上架**而非保存（`MerchantGoodsServiceImpl.requireCategoryAuthorized`）。`qualification_required` 是给人看的文案，不是判据 |
| 5.6 | 类目属性模板 → 商品属性表单 | `attr_template` | 🟡 同上 |

> **为什么类目挂平台而不是挂主体**：连锁与多业态都要在同一个树里被检索、被资质管控。
> 挂主体会让「同一件五常大米在 A 店叫粮油、B 店叫米面」，C 端搜索直接碎掉。
> 商家的个性化在**门店分组**那一层解决，不在平台树上改。

## 九、这份矩阵没有覆盖的

订单履约、售后、结算分账、积分、券与营销、评价、消息 —— 它们在商家开出第一单**之后**，
不属于「注册到商品」这条开店链路。见[产品架构与实体关系](../technical/reference/产品架构与实体关系.md)。
