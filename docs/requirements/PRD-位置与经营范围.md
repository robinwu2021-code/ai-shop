## 0. 一句话

**买家选一个位置，商家框一片范围，两者在平台这里对上号 —— 对上了才有生意。**

这一模块回答的是同一个问题的三种问法：

| 端 | 用户心里那句话 | 系统要回答的 |
|---|---|---|
| C 端 | 「我在家 / 在公司 / 我现在这儿」 | 这个位置能看到哪些商家与商品 |
| B 端 | 「我做哪儿的生意」 | 这家店的货应该出现在谁的首页 |
| 运营端 | 「供需在哪儿对不上」 | 哪些位置没人服务、哪些商家框了范围却没人看得见 |

**为什么必须独立成模块**：这三件事此前分散在三份 TDD、两个交互方案和若干迁移里，
各自都对，但**没有一处把它们连起来看**。而这条链上任何一环断掉，
症状都长得一模一样 —— 买家打开首页，空的。谁都查不出是哪一环。

## 1. 模块边界

**在本模块内**：

- 买家的位置：地址簿、生效位置、当前定位、选点
- 商家的范围：经营范围（多粒度）、自送半径、门店坐标
- 平台的底图：聚落（小区 / 村 / 写字楼）、行政区划、商家提报
- 三者的**匹配规则**：一个位置能看到哪些商家、一张单送不送得到
- 运营端对以上全部的**查看、干预与分析**

**不在本模块内**（各有归属，本模块只引用）：

- 订单履约方式的选择（自提 / 自送 / 快递）—— 见交易域
- 佣金归属与分账 —— 见结算域
- 商品上架审核 —— 见商品域
- 自提点承接与团长 —— 见社区网点

### 2.1 真正的缺口是坐标，不是绑定

链路 `经营范围 → 社区池 → 商品` 是**按 communityNo 对齐**的，它今天能跑。
断的是另一半 —— **凡是要算距离的地方，两端都缺坐标**：

- 门店 9 家只有 2 家标过点，而 `requireWithinDeliveryRadius` 明写着「没坐标就放行」
  → **7 家商家设的自送半径形同虚设**，多远的单都进得来，等他要送货才发现送不到
- 买家 3 条地址里 2 条有坐标（新加的选点页起作用了），但存量与手填的路仍然产出无坐标地址
- 已开通聚落 23 个，而**「按坐标算可见性」需要每个聚落都有围栏或中心点**

## 3. 概念与口径（这一节是本模块的词典）

**四组最容易混的概念，每一组混掉都会造成一类查不出的故障：**

| 概念 | 回答什么 | 存在哪 | 混掉的后果 |
|---|---|---|---|
| **生效位置** | 我**现在**按哪儿看货 | `usr_account.active_address_id` | 与默认合并 → 给父母下单时改了收货人 |
| **默认收货地址** | 下单时**预填**哪个收货人 | `usr_address.is_default` | 同上，反向 |
| **这一单的地址** | **这一单**送到哪儿 | 只在结算页内存里，下单时快照进订单 | 与默认合并 → 寄一次父母家，从此每单都预填那儿 |
| **订单地址快照** | 这张单当时**寄到了哪儿** | `ord_sub_order.receiver_*` | 与地址簿共用 → 用户改地址会改写历史订单 |

| 概念 | 含义 | 注意 |
|---|---|---|
| **聚落**（community） | 小区 / 村 / 写字楼，挂在街道（L4）下 | **村不是区划粒度**，它和小区同级（2026-08-22 定） |
| **经营范围**（service area） | 商家做哪儿：省 / 市 / 区 / 街道 / 聚落，**可跨粒度组合** | 「三个小区 + 一个区」= 四条 |
| **社区池**（community pool） | 「这件商品出现在哪些社区」的**派生索引** | 是产物不是真源，改口径后要重建 |
| **自送半径** | 门店自送的圆，圆心是门店坐标 | 与经营范围是**两把尺**，见 §7.3 |

## 6. 交互流程

### 6.1 C 端：选一个位置

```
打开 App
   │
   ├── 有生效位置 ──► 顶栏显示它（家 / 公司 / 地址简称）
   │                      │ 点它
   │                      ▼
   │                 位置列表：每条可「切到这里」
   │                 底部「管理收货地址 ›」
   │
   └── 一个位置都没有 ──► 顶栏「选择位置」
                          **不弹窗、不跳转** —— 首屏在零位置信息下也要有东西看
                              │ 点它
                              ▼
                        选点页（搜索 / 当前定位 / 附近 / 地图 / 手动）
```

**切换位置之后系统做什么**（用户看不见但必须一致）：

1. 生效位置写到服务端（换设备后仍是同一个上下文）
2. 用它的坐标解析归属聚落 → 换商品池
3. 购物车里在新位置买不到的行**标出来并禁选**，不静默清空（那是用户的东西）
4. **已下的订单不受影响** —— 订单在创建那一刻就快照了自己的收货地址

#### C10 缺口：「当前位置」还不是一个可选项

用户心里的三个选项是「家 / 公司 / **我现在这儿**」，而第三个在系统里
**必须先变成一条地址才能生效** —— 因为生效位置指向 `addressId`。

要补的是**一次性浏览上下文**：选「当前位置」时不入地址簿，
只在本次会话里按这个坐标看货；下单时再问他要不要存成地址。

> 这一条卡在能力上：微信 2026-09-03 驳回了 `getLocation`（开放范围不含
> 「匹配附近服务」与「辅助填写收货地址」），所以小程序里拿不到静默精确定位。
> 可行的形态是 `chooseLocation`（用户在地图上点一下）或 `getFuzzyLocation`（区级）。

### 6.1.1 智能匹配：从一个坐标到「我要看哪几个片区的货」

**先把两根轴分开，否则后面每一条都说不清：**

| 轴 | 取值 | 决定什么 | 存在哪 |
|---|---|---|---|
| **位置** | **单值**（一个坐标） | 智能匹配的输入；送不送得到 | `usr_account.active_address_id` |
| **服务单位** | **可多选**（上限 3） | 首页/搜索/分类看到哪些商家与商品 | 待建，见 §6.1.4 |

用户嘴里的「我在家」是位置；「我要看阳光里和隔壁写字楼的货」是服务单位。
**一个位置可以匹配出多个单位，但一个单位不代表一个位置** —— 合并这两根轴的后果，
是「我想同时看两个小区」被迫表达成「我有两个家」。

```
定位 / 选中的地址（一个坐标）
        │
        ▼
  nearbyCommunities(lat,lng)      ← 已有：中心点 5km 内按距离排
        │                            （`shop.community.nearby-radius-m`，可配）
        ▼
  候选服务单位列表（小区 / 村 / 楼栋）
        │
        ├── 默认选中**最近的那一个**        ← 保持今天的行为，不打扰存量用户
        └── 用户可加选、可换、可全取消      ← 新增
```

**默认只选一个，多选是用户主动加的。** 反过来（默认把 5 公里内全勾上）会让新用户
第一眼看到一锅混合的货，而他不知道为什么 —— 社区电商的价值恰恰是「**我邻居**在买什么」，
默认混合等于把这个价值稀释掉。多选是给「住在两个小区交界」「家和公司离得近」这类人的出口，
不是默认形态。

### 6.1.2 楼栋这一级：与小区**平级**，不做父子

商家可以只服务一栋写字楼，用户也确实住在某栋楼里。但**不要做成「小区 › 楼栋」的父子结构**：

- 现有模型是刻意扁平的（「村不是区划粒度，它和小区一样是挂在街道下的聚落」）
- 一旦有父子，就要回答「商家选了小区，算不算覆盖里面每一栋楼」——
  而这个问题**没有普遍正确的答案**：物业类服务按楼算，生鲜配送按小区算
- 父子还会让经营范围选择器多一层下钻，而它现在的设计是「任何一个地点都是一行」

**做法**：`cmt_community.kind` 增加 `BUILDING`，与 `ESTATE` / `VILLAGE` 平级，同样挂街道（L4）。
重叠由**多选**来解 —— 用户站在阳光里 3 幢，智能匹配同时给出「阳光里 3 幢」与「阳光里小区」两条，
他可以两个都选。**这正是多选存在的第一个理由**：不用建包含关系，也能表达重叠覆盖。

### 6.1.3 多选之后，每一条链路怎么走

**总则一句话：多选只影响「看」，不影响「结算」。**

这条总则是整个设计的承重墙。佣金归属、团长、自提点都挂在**单个** `communityNo` 上，
如果浏览时的多选能渗进下单，这三样立刻变得说不清 ——
而它们说不清的表现是**结算完之后**才出现的分账错误，那时改不回来了。

| 场景 | 多选时的规则 | 为什么 |
|---|---|---|
| **首页 / 分类 / 搜索的商品** | 各单位商品池取**并集**，按 `goodsNo` 去重 | 商家可能同时选了小区和其中一栋楼，不去重他会出现两次 |
| **商家列表** | 同样并集去重（按 `merchantNo`） | 同上 |
| **排序** | 按「商家门店到**当前位置**的距离」排，**不按单位分组** | 分组会把「隔壁楼的菜摊」排到「三公里外同小区的店」后面 |
| **某商家只在其中一个单位可见** | **显示**（并集语义：任一命中即可见） | 交集语义会让多选越选越少，与用户预期正好相反 |
| **加入购物车后取消勾选该单位** | 车里那行标 `invalidReason`，**禁选但不删** | 那是用户的东西；静默清空比留着更糟 |
| **自提下单** | 自提点列表 = 已选单位的并集；**用户选定的那个自提点决定这一单的 `communityNo`** | 归属由履约对象定，不由浏览态定 |
| **商家自送** | **与多选完全无关**，按坐标算半径（§7.2） | 半径是米，不是片区 |
| **快递** | 与多选无关 | 同上 |
| **佣金归属 / 团长** | 由订单的 `communityNo` 决定，而它来自上面那一行 | 订单一创建就快照，之后改多选也不动它 |
| **切换位置（家 → 公司）** | **重新智能匹配，清掉旧的多选**，并提示「已按公司重新匹配」 | 旧多选是另一个地方的单位，留着就是错的 |
| **全部取消勾选** | 回落到「无位置」的首屏（平台推荐 + 全域在售），**不空屏** | 与新用户同一条路径 |
| **一个单位都没匹配到**（新城区） | 同上，并给「按区域手动找」的入口 | 附近没开通是常态，不是故障 |

**上限 3**。理由不是性能（`where community_no in (…)` 毫无压力），是**首页会变成大杂烩**：
超过三个片区之后，「邻居在买什么」这句话就不成立了，而那是这个产品的立身之本。
达到上限时**不弹错误**，而是让新勾的那个替换掉最早勾的，并说一句。

### 6.1.4 多选存在哪

**与生效位置同源：存服务端。** 换设备、重装之后仍是同一套上下文 ——
生效位置已经这么做了（`usr_account.active_address_id`），多选跟着它走，
否则会出现「手机上看得到、平板上看不到」这种没人能复现的差异。

结构上是一张 `usr_active_area`（user_no, community_no, sort_no），
而不是往 `usr_account` 上加一列 JSON —— 后者查不了「这个聚落有多少人在看」，
而那正是运营端 O6 要的数（§8）。

## 7. 业务逻辑

### 7.1 一个位置能看到哪些商品

**今天的实现（按 communityNo 对齐）：**

```
生效位置(有坐标) ──► nearbyCommunities 取覆盖它的聚落 ──► communityNo
                                                            │
商家经营范围(mch_service_area) ──► 投影 ──► prd_community_pool
                                                            │
                                                            ▼
                                            GoodsServiceImpl 按 communityNo 过滤
```

- 经营范围为**空**的商家：对**所有人不可见**（不是「全域可见」）
- 经营范围为 **PROVINCE/CITY** 级：按国标码前缀展开到该范围内所有已开通聚落
- 位置**没有坐标**：推不出聚落 → 保持原有归属不变，**不清空**
  （微信地址簿导入的地址就没有坐标，清空会让用户「换了个地址商品全没了」）

**多选之后这条链怎么变**（§6.1.3 的规则在这里落成一句 SQL）：

```
已选服务单位 [A, B, C] ──► prd_community_pool where community_no in (A,B,C)
                                    │
                                    ▼
                        按 goodsNo 去重 ──► 按门店到当前位置的距离排
```

**去重必须按 `goodsNo` / `merchantNo`，不能按 (单位, 商品)** ——
商家同时选了「阳光里小区」和「阳光里 3 幢」时，用户两个都勾就会看到他两次。
这个重复不会报错，只会让首页看起来像数据出了问题。

**将来（按坐标算可见性，第二步，未做）**：去掉中间那一跳，后端按坐标 + 范围实时算。
好处是办公楼、任意门牌这类**不属于任何已开通聚落**的位置也能用。

### 7.2 一张单送不送得到

只对**商家自送**判，且**逐商家判**（购物车跨商家会拆成多张子单，各家圆心半径不同）。

**三条放行**，端上后端必须一字不差：

| 放行条件 | 为什么 |
|---|---|
| 收货地址没坐标 | 存量地址都是纯手填的，拿缺失数据去拦会误伤 |
| 门店没标过点 | 同上，圆心都没有 |
| 半径 ≤ 0 | 那是「不限距离」的表达 |

拦在**创建订单**这一步，不是支付后：付过钱再说「超出范围」，他要先退款才能重下。
端上在结算页提前置灰并**点名是哪一家**（车里三家店时，只说「超出范围」他不知道该改什么）。

### 7.3 经营范围与自送半径是两把尺，别合并

| | 经营范围 | 自送半径 |
|---|---|---|
| 回答 | 我的货**出现在**谁的首页 | 我**送不送得到**这个门牌 |
| 粒度 | 聚落 / 街道 / 区 / 市 / 省 | 米 |
| 判定 | communityNo 对齐 | 门店坐标 ↔ 收货坐标算距离 |
| 缺数据时 | 范围为空 = 谁也看不见 | 缺坐标 = **放行** |

**注意两者缺省行为相反**：范围为空是「关」，半径算不出是「开」。
这不是不一致 —— 范围是商家主动声明的（没声明就是没开张），
而半径是一条**保护性校验**（数据不全时不该把正常订单挡在门外）。

### 7.4 位置数据的三条不变量

1. **一个用户至多一条默认地址**，由应用层保证（设新默认时先清旧）；
   **不建 `(user_no, is_default)` 唯一索引** —— 那会让非默认地址也只能有一条
2. **生效位置指向的地址被删掉 = 当作没有**，不抛异常。
   删自己的地址是正常操作，不该让首页因此打不开
3. **订单一旦创建，地址就与地址簿脱钩**（整体快照）。用户改地址不影响历史订单
4. **浏览态永远不进订单。** 已选服务单位是「我在看哪几片」，
   而订单的 `communityNo` 来自这一单实际选的履约对象（自提点 / 收货坐标）。
   把多选写进订单的后果是佣金归属与团长分账**说不清**，
   而那件事的症状出现在结算之后 —— 那时改不回来了
5. **可见性是并集不是交集。** 任一已选单位能看到，就显示。
   交集会让「多选越选越少」，与用户按下那个勾时的预期正好相反

### 7.5 运营端干预的副作用（必须在界面上说清）

| 动作 | 连带影响 |
|---|---|
| 合并两个重复聚落 | 被并掉的那条关闭（历史订单仍指着它），**一批商家的经营范围与社区货架改到保留的那条上** |
| 停用一条区划 | 只影响新选择，**存量商家的范围不动** |
| 聚落不挂区划 | 商家按「整个 XX 区」勾时**命中不到它**，只能被逐个点名 |
| 重建社区池 | 只重算索引，不改商品本身；改过可见性口径后必须做一次 |

## 8. 运营端新增功能的数据口径（O6–O9）

**这三张视图共用一张事实表**：聚落 × 买家数 × 商家数。

| 指标 | 口径 | 取自 |
|---|---|---|
| 聚落的买家数 | 生效位置解析到该聚落的用户数 | `usr_account.active_address_id` → `usr_address` → 聚落 |
| 聚落的地址数 | 收货地址落在该聚落的条数（含非生效） | `usr_address` |
| 聚落的商家数 | 经营范围覆盖该聚落的主体数 | `mch_service_area` 展开 |
| 聚落的商品数 | 社区池里的行数 | `prd_community_pool` |
| 供需状态 | 买家>0 且 商家=0 → **缺供给**<br>买家=0 且 商家>0 → **缺需求**<br>两者皆 0 → 空聚落 | 组合判定 |

**必须同时给出「算不了的那部分」**，否则这三张视图会把缺数据说成缺需求：

- 没有坐标的地址：**解析不到任何聚落**，它们既不算在任何一格里，也不该被静默丢掉
- 没有标点的门店：自送半径失效，但**不影响**经营范围口径的商家数
- 未开通的聚落：买家可能住在那儿（地址是自由填的），但它不在底图上

> 这一条是本节的要害：**分母写错的分析，比没有分析更危险** ——
> 它会让运营去某个「没需求」的片区撤商家，而那里只是没人标过坐标。

## 11. 待确认

1. **C10「当前位置」的形态**：一次性上下文（不入地址簿）还是自动存成一条「临时」地址？
   前者干净但下单时要多问一步；后者会让地址簿被一堆临时地址塞满（上限只有 20 条）。
2. **O6 的买家口径用「生效位置」还是「所有地址」**？前者反映真实浏览，
   后者反映潜在需求。建议两个都给，但**默认展示生效位置**，因为它才是「现在有多少人在这儿看货」。
3. **未开通聚落里的买家怎么算**？他们的地址是自由填的、解析不到聚落。
   建议按街道（L4）兜底归集 —— 那一级一定有区划码。
4. **B5 门店坐标要不要设成建店必填**？现在 9 家有 7 家没标。
   设必填能一次性解决，但会挡住存量商家的其它编辑操作（与门牌号那次是同一类取舍）。
5. **多选上限 3 是拍的，不是算的。** 我按「首页还能不能叫『邻居在买什么』」定的，
   但真正的依据要等 O13（多选分布）跑一段时间：如果大多数人只选 1 个，
   这个功能的优先级就该往后放；如果普遍选满 3 个，说明片区划分本身太碎。
6. **楼栋（`BUILDING`）要不要现在就加 kind？** 加了 B 端选择器与运营端聚落维护都要跟着改。
   若暂不加，写字楼可以先当作一个 `ESTATE` 建进去（语义上勉强成立），
   代价是运营端分不清「小区」与「写字楼」两类的分布。
7. **切位置时清空多选，还是保留同名单位？** 我倾向清空并提示 —— 保留会出现
   「切到公司了、却还在看家附近小区的货」，而那正是「顶栏说了三件矛盾的事」那类缺陷。
8. **§2 那条作废的旧结论**要不要直接改进 TDD-按坐标算可见性？
   它现在被当作第二期的动机写着，而动机是错的 —— 第二步仍然值得做，但理由要换成
   「办公楼与任意门牌不属于任何聚落」，不是「商家没有绑定」。
