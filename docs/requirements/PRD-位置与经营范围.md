## 0. 一句话

**买家选一个位置，商家框一片范围，两者在平台这里对上号 —— 对上了才有生意。**

这一模块回答的是同一个问题的三种问法：

| 端 | 用户心里那句话 | 系统要回答的 |
|---|---|---|
| C 端 | 「我在家 / 在公司 / 我现在这儿」 | 这个位置能看到哪些商家与商品 |
| B 端 | 「我做哪儿的生意」 | 这家店的货应该出现在谁的首页 |
| 运营端 | 「供需在哪儿对不上」 | 哪些位置没人服务、哪些商家框了范围却没人看得见 |

**为什么必须独立成模块**：这三件事此前分散在三份 TDD、两个交互方案和若干迁移里，
各自都对，但**没有一处把它们连起来看**。而这条链上任何一环断掉，
症状都长得一模一样 —— 买家打开首页，空的。谁都查不出是哪一环。

## 1. 模块边界

**在本模块内**：

- 买家的位置：地址簿、生效位置、当前定位、选点
- 商家的范围：经营范围（多粒度）、自送半径、门店坐标
- 平台的底图：聚落（小区 / 村 / 写字楼）、行政区划、商家提报
- 三者的**匹配规则**：一个位置能看到哪些商家、一张单送不送得到
- 运营端对以上全部的**查看、干预与分析**

**不在本模块内**（各有归属，本模块只引用）：

- 订单履约方式的选择（自提 / 自送 / 快递）—— 见交易域
- 佣金归属与分账 —— 见结算域
- 商品上架审核 —— 见商品域
- 自提点承接与团长 —— 见社区网点

### 2.1 真正的缺口是坐标，不是绑定

链路 `经营范围 → 社区池 → 商品` 是**按 communityNo 对齐**的，它今天能跑。
断的是另一半 —— **凡是要算距离的地方，两端都缺坐标**：

- 门店 9 家只有 2 家标过点，而 `requireWithinDeliveryRadius` 明写着「没坐标就放行」
  → **7 家商家设的自送半径形同虚设**，多远的单都进得来，等他要送货才发现送不到
- 买家 3 条地址里 2 条有坐标（新加的选点页起作用了），但存量与手填的路仍然产出无坐标地址
- 已开通聚落 23 个，中心点与围栏半径**都齐**（这一侧反而是最完整的）——
  但**围栏没有被匹配读取**，实际判定用的是全局 5000 米，见 §6.1.2

## 3. 概念与口径（这一节是本模块的词典）

**四组最容易混的概念，每一组混掉都会造成一类查不出的故障：**

| 概念 | 回答什么 | 存在哪 | 混掉的后果 |
|---|---|---|---|
| **生效位置** | 我**现在**按哪儿看货 | `usr_account.active_address_id` | 与默认合并 → 给父母下单时改了收货人 |
| **默认收货地址** | 下单时**预填**哪个收货人 | `usr_address.is_default` | 同上，反向 |
| **这一单的地址** | **这一单**送到哪儿 | 只在结算页内存里，下单时快照进订单 | 与默认合并 → 寄一次父母家，从此每单都预填那儿 |
| **订单地址快照** | 这张单当时**寄到了哪儿** | `ord_sub_order.receiver_*` | 与地址簿共用 → 用户改地址会改写历史订单 |

| 概念 | 含义 | 注意 |
|---|---|---|
| **聚落**（community） | 小区 / 村 / 写字楼，挂在街道（L4）下 | **村不是区划粒度**，它和小区同级（2026-08-22 定） |
| **经营范围**（service area） | 商家做哪儿：省 / 市 / 区 / 街道 / 聚落，**可跨粒度组合** | 「三个小区 + 一个区」= 四条 |
| **社区池**（community pool） | 「这件商品出现在哪些社区」的**派生索引** | 是产物不是真源，改口径后要重建 |
| **自送半径** | 门店自送的圆，圆心是门店坐标 | 与经营范围是**两把尺**，见 §7.3 |

## 6. 交互流程

### 6.1 C 端：选一个位置

```
打开 App
   │
   ├── 有生效位置 ──► 顶栏显示它（家 / 公司 / 地址简称）
   │                      │ 点它
   │                      ▼
   │                 位置列表：每条可「切到这里」
   │                 底部「管理收货地址 ›」
   │
   └── 一个位置都没有 ──► 顶栏「选择位置」
                          **不弹窗、不跳转** —— 首屏在零位置信息下也要有东西看
                              │ 点它
                              ▼
                        选点页（搜索 / 当前定位 / 附近 / 地图 / 手动）
```

**切换位置之后系统做什么**（用户看不见但必须一致）：

1. 生效位置写到服务端（换设备后仍是同一个上下文）
2. 用它的坐标解析归属聚落 → 换商品池
3. 购物车里在新位置买不到的行**标出来并禁选**，不静默清空（那是用户的东西）
4. **已下的订单不受影响** —— 订单在创建那一刻就快照了自己的收货地址

#### C10 缺口：「当前位置」还不是一个可选项

用户心里的三个选项是「家 / 公司 / **我现在这儿**」，而第三个在系统里
**必须先变成一条地址才能生效** —— 因为生效位置指向 `addressId`。

要补的是**一次性浏览上下文**：选「当前位置」时不入地址簿，
只在本次会话里按这个坐标看货；下单时再问他要不要存成地址。

> 这一条卡在能力上：微信 2026-09-03 驳回了 `getLocation`（开放范围不含
> 「匹配附近服务」与「辅助填写收货地址」），所以小程序里拿不到静默精确定位。
> 可行的形态是 `chooseLocation`（用户在地图上点一下）或 `getFuzzyLocation`（区级）。

### 6.1.1 智能匹配：从一个坐标到「我该看哪片货」

```
定位 / 选中的地址（一个坐标）
        │
        ▼
  落在哪些聚落的围栏里            ← 判据是**每个聚落自己的围栏**，见 §6.1.2
        │
        ├── 落进了 ──► 取**最内层**那个（楼栋 › 小区/村）作为「我在哪」
        │                └─► 沿**归属链向上**展开，商品取链上并集（§6.1.4）
        │
        └── 一个都没落进 ──► 按距离给候选列表让他挑；挑不到回落到无位置首屏
```

**用户看到的始终是一个地方**（顶栏「阳光里 3 幢」），
链上还有小区、街道、区 —— 那是系统内部的事，不该变成用户要管理的清单。

### 6.1.2 先修匹配精度：围栏这一列**已经有了，但没人读**

线上实测（2026-09-04）：

| 事实 | 值 |
|---|---|
| `cmt_community.fence_radius` | **23 个聚落全设了，全是 1000 米** |
| 运营端设置入口 | ✅ `OpsCommunityController.setFence`，有审计日志 |
| ops 列表展示 | ✅ `CommunityAdminServiceImpl:720` |
| **匹配时读它** | ❌ **一行都没读** —— `withinRadius()` 用的是全局 `shop.community.nearby-radius-m`（默认 **5000**） |

于是今天的「智能匹配」实际是**「中心点 5 公里内按距离排」**。
小区尺度上这还凑合（1 公里的围栏被放大成 5 公里，只是候选多了些）；
**楼栋尺度上它直接不成立** —— 5 公里内的写字楼可以有几十栋，排第一的那个大概率不是你所在的这栋。

**所以楼栋要落地，第一步不是加 `kind`，是让匹配读 `fence_radius`。**
这一步不加表、不加字段、不改端上，只是把一个已经在库里的数用起来。

### 6.1.3 楼栋**有归属**：挂在小区 / 园区下，不是平级

> 这一节推翻了本文早先「楼栋与小区平级、不做父子」的写法。
> 当时的理由是「商家框了小区，算不算覆盖里面每栋楼」没有普遍正确答案 ——
> 而 §6.2.1 的 **include / exclude** 正好补上了这个缺口：
> **默认覆盖，商家可点名、可排除**。有了这个出口，父子结构就是对的。

```
街道（sys_region L4）
 ├── 阳光里小区   (ESTATE,  parent_no = null)
 │    ├── 3 幢     (BUILDING, parent_no = 阳光里小区)
 │    └── 5 幢     (BUILDING, parent_no = 阳光里小区)
 ├── 星光科技园   (ESTATE,  parent_no = null)   ← 园区与小区同一档
 │    └── A 座     (BUILDING, parent_no = 星光科技园)
 └── 牛杜村       (VILLAGE, parent_no = null)
```

- `cmt_community` 加一列 **`parent_no`**（可空）。小区 / 村 / 园区的 parent 为空，
  它们直接挂 `region_code`（街道）；楼栋的 parent 指向所属小区或园区
- **只做两层，不做无限递归**。园区 › 楼 › 单元 › 户会没完没了，
  而单元和户**不是服务单位** —— 没有商家会按单元框范围，它们属于收货地址的门牌号
- 楼栋**同时**要有 `region_code`（冗余存所属街道）：
  这样「整个西湖区」这类粗粒度范围可以只按区划码前缀展开，不必先下钻到小区再找楼

**为什么归属必须是「声明的」而不是「靠圆圈算的」**：
本文上一版打算用围栏重叠来表达「楼栋在小区里」。那在几何上不可靠 ——
大小区边上的一栋楼可能落在小区中心圆之外，而隔壁小区的圆反而把它罩进去。
**归属是事实，不该由半径推断。** 围栏只负责回答「我此刻站在哪一个聚落里」，
归属关系由数据声明。

### 6.1.4 C 端的匹配：先定位到**最内层**，再沿归属链**向上**

```
坐标
  │
  ├─ 落在「阳光里 3 幢」的围栏里（150 m）
  └─ 也落在「阳光里小区」的围栏里（1000 m）
                    │
                    ▼
          取**最内层**那个 = 阳光里 3 幢     ← 这是「我在哪」，单值，顶栏显示它
                    │
                    ▼
          沿归属链向上展开（声明的，不是算的）
          阳光里 3 幢 → 阳光里小区 → 文新街道 → 西湖区 → 杭州市 → 浙江省
                    │
                    ▼
          商品池 = 覆盖**链上任一节点**的商家 − 被 exclude 的
```

**「最内层」的判据**：优先 `BUILDING`，其次 `ESTATE`/`VILLAGE`；同档时取距离近的。
楼栋的围栏本来就更小，所以多数情况下距离判据也会给出同一个答案 ——
但**层级优先于距离**，否则站在楼门口时，隔壁小区的中心可能比本楼中心更近。

**这样就不再需要「重叠自动纳入」那套几何合并**：归属链是声明的、确定的，
而围栏只用来回答一个问题 —— 我站在哪一个最内层聚落里。

### 6.1.5 手动多选：**评估过，不做**

> 本节保留完整推演，因为「同时选家和公司」是个非常自然的诉求，
> 三个月后一定会有人再提一次。

诉求的原话是「同时选择办公场地和家」。而这个例子恰恰说明它不该做：

**这两件事发生在不同时刻，不是同时。**

- 中午在办公室想买楼下便利店 → 家附近的生鲜团购是**噪音**
- 下班想让菜送到家 → 办公楼的便利店是**噪音**

首页混着两个地方的货，用户每次都要自己心里过滤一遍。
而这个产品的立身之本是「**我邻居**在买什么」—— 混合直接把它稀释掉。

**成本这一侧很具体：**

| 要新增的 | |
|---|---|
| `usr_active_area` 一张表 | 多选要能查「这个聚落有多少人在看」，塞 JSON 列查不了 |
| 并集查询 + 去重 | |
| 购物车不可售标记接多选 | 取消勾选后那些行要变灰 |
| 顶栏形态「主单位 · 等 N 个」 | |
| 上限与替换交互 | |
| 切位置时清空 + 提示 | |
| 运营端 O13 多选分布 | 否则上限定几个没有依据 |
| **一整套「只影响看、不影响结算」的规则（8 条）** | ← **这套规则本身就是复杂性的证据** |

最后一行是关键：**需要写八条规则才能让一个功能不出错，说明它在跟系统其它部分较劲。**
佣金归属、团长、自提点都挂在单个 `communityNo` 上，多选每天都在试图渗进去，
而挡住它靠的是纪律，不是结构 —— 纪律会松。

**替代方案拿到它 90% 的收益，成本接近零：**

| | 手动多选 | §6.1.4 归属链上溯 + §6.1.6 免费切换 |
|---|---|---|
| 边界处 / 楼栋在小区里 | 解决 | 解决，**而且更准**（归属是声明的，不靠用户判断，也不靠圆圈猜） |
| 家 + 公司 | 混合，认知负担 | 切换，**每次都干净** |
| 用户要学的新概念 | 服务单位 / 主单位 / 上限 3 | **无** |
| 新表 / 新规则 | 1 张表 + 8 条规则 | 0 |
| 归属歧义 | 靠规则挡 | **不存在** |

### 6.1.6 把切换做到几乎免费

多选的真实驱动力是「切换太麻烦」。那就把切换变便宜，而不是绕过它：

1. **定位变了主动问一句**：「你好像在公司附近，切过去吗？」—— 一次点击，不弹强制弹窗
2. **顶栏常驻两个 chip**（家 / 公司），点一下就换，不用进列表
3. **切换后首页是干净的一个地方**，不是混合
4. 时段性可以作为**提示的时机**（工作日上午优先提示公司），但**不自动切** ——
   自动切会让人在完全没察觉的情况下看到另一个地方的货，那比麻烦糟得多

### 6.1.7 切换地址：完整规则

用户在位置列表 / 地址簿里把生效位置从 A 换成 B。

| # | 情况 | 系统行为 |
|---|---|---|
| 1 | B **有坐标** | 重新匹配（§6.1.1）→ 换最内层聚落 → 换归属链 → 换商品池 |
| 2 | B **没有坐标**（存量地址、微信导入、粘贴识别） | **保持原有归属不变**，并明说「这个地址没有定位点，商品仍按 XX 显示」。**绝不清空** —— 清空的表现是「换了个地址，商品全没了」 |
| 3 | B 有坐标但**一个围栏都没落进** | 归属降级为空 → 首页回落到平台推荐 + 全域在售，并提示「这一带还没开通，给你看全部」 |
| 4 | 切换成功 | **顶栏、副标题、商品池三处同时变**，不允许只变其一（顶栏写「公司」而货还是家那边的，是已经踩过的坑） |
| 5 | 购物车 | 重算不可售：新归属下买不到的行**标出来并禁选**，**不删** |
| 6 | 已下的订单 | **完全不受影响**。订单创建那一刻就快照了自己的收货地址与自提点 |
| 7 | 切换失败（网络） | 维持原状并提示，**不留半切状态**（服务端换了、端上没换＝下次打开又变回去） |

**写在哪**：生效位置存服务端（`usr_account.active_address_id`），
端上本地留一份做即时响应 —— 切换要立刻生效，不能等一次网络往返。**以服务端为准。**

### 6.1.8 当前位置：完整规则

「我现在这儿」与「家 / 公司」不同 —— 它**不是一条地址**，是一次性的浏览上下文。

| # | 来源 | 精度 | 能不能用来匹配聚落 |
|---|---|---|---|
| 1 | `chooseLocation`（用户在地图上点一下） | **米级** | ✅ 可以，走正常匹配 |
| 2 | `getLocation`（静默精确） | 米级 | ⚠️ **微信 2026-09-03 驳回**，小程序上拿不到 |
| 3 | `getFuzzyLocation`（静默模糊） | **区级，误差约 5 km** | ❌ **不能** —— 见下 |
| 4 | 浏览器定位（H5） | 视设备 | ⚠️ 没配地图 JS key，`chooseLocation` 直接 fail |

**模糊定位为什么不能用来匹配聚落**：围栏是 1000 米（小区）到 150 米（楼栋）的量级，
而模糊定位的误差是 5 公里 —— **用它匹配出来的聚落是噪音，不是结果**。
它够用的地方只有一个：**把你落到你所在的区**，然后给该区的候选列表让你挑。
那一步恰恰是手选省市区里最烦的一步，所以它仍然有价值 —— 只是不能假装成精确匹配。

**其余规则：**

- **不入地址簿**。地址簿上限 20 条，每次「用一下当前位置」都存一条会很快塞满
- **只作用于本次会话**。App 重开回到生效位置 —— 「现在这儿」按定义就是临时的
- **下单时才问**：需要收货地址时提示「要把这个位置存成收货地址吗」，
  存了才进地址簿。**不存也能下单**（他可以选地址簿里已有的另一条收货）
- **顶栏要标出来**：显示「当前位置 · XX」而不是只显示地名 ——
  否则他分不清现在看的是临时位置还是家
- 拿不到定位**不弹窗、不拦路**：首屏在零位置信息下也要有东西看

### 6.2.1 include / exclude：默认覆盖，可点名、可排除

**这是「商家框了小区算不算覆盖里面每栋楼」的答案：默认算，但给两个出口。**

`mch_service_area` 加一列 **`mode`**（`INCLUDE` 默认 / `EXCLUDE`）。

| 商家想表达 | 怎么勾 |
|---|---|
| 整个小区都做 | INCLUDE 阳光里小区（**自动含全部子楼栋**） |
| 只做其中两栋 | INCLUDE 3 幢、INCLUDE 5 幢（不勾小区） |
| 小区都做，但 3 幢不做 | INCLUDE 阳光里小区 + **EXCLUDE 3 幢** |
| 整个街道都做，但某个园区不做 | INCLUDE 文新街道 + **EXCLUDE 星光科技园**（含其全部楼栋） |

**三条判定规则：**

1. **展开顺序是「先并后减」**：`覆盖 = ⋃(INCLUDE 展开) − ⋃(EXCLUDE 展开)`
2. **EXCLUDE 总赢**。同一个对象既被 include 又被 exclude 时，结果是不覆盖 ——
   排除是更强的意图声明。但**更好的做法是在输入端就不让它发生**：
   B 端界面上勾了排除就把对应的 include 项去掉，反之亦然。
   **从输入端消除矛盾，比从判定端消除矛盾诚实** —— 后者要求用户记住一条规则
3. **EXCLUDE 只能排除已被覆盖的东西**。排除一个本来就不在范围里的楼栋是无意义输入，
   界面上不给这个选项 —— 否则商家会以为自己「防住」了什么

**待审的不参与展开**（沿用 ADR-013 §4.2）：省市区级 INCLUDE 在审核通过前不生效。
**EXCLUDE 不需要审核** —— 缩小自己的范围不影响别人。

## 7. 业务逻辑

### 7.1 匹配规则：同一个覆盖关系的两个方向

**B 端问的是「我覆盖谁」，C 端问的是「谁覆盖我」。**
两边算的必须是同一件事，否则会出现「商家看着自己覆盖了、买家就是看不到」——
而那种问题商家永远查不出来。

投影表 `prd_community_pool` 就是 **B 方向算好的结果**，C 端只查它。

#### 7.1.1 B 端匹配规则：我的货出现在哪些聚落

```
对每一条 mch_service_area：
  level=COMMUNITY, ref=小区/村   → 它自己 + 它的**全部子楼栋**
  level=COMMUNITY, ref=楼栋      → 它自己
  level=STREET                   → 该街道下全部聚落（含楼栋）
  level=DISTRICT/CITY/PROVINCE   → 按国标码前缀展开到范围内全部聚落
  ↓
INCLUDE 项取并集，减去 EXCLUDE 项的并集        ← §6.2.1
  ↓
过滤掉 status=PENDING 的 INCLUDE 项（待审不生效）
  ↓
写进 prd_community_pool（商品 × 聚落）
```

**四条边界：**

| 情况 | 结果 | 为什么 |
|---|---|---|
| 范围**一条都没有** | **谁也看不到**（不是全域可见） | 没声明就是没开张。B 端必须明说这件事，否则商家以为自己在营业 |
| 只有 EXCLUDE、没有 INCLUDE | 谁也看不到 | 从空集里减东西还是空集。界面上应该拦住这种输入 |
| 聚落**没挂区划** | 命中不到任何粗粒度范围，只能被逐个点名 | 平台不按名字猜归属：猜错不报错，只会让它悄悄出现在别人的范围里 |
| 楼栋的 `region_code` 缺失 | 同上 —— 所以楼栋建档时**必须**同时写 parent 与 region_code | |

#### 7.1.2 C 端匹配规则：我能看到哪些货

```
一个坐标（生效位置 / 当前位置）
  │
  ① 落在哪些聚落围栏里 → 取**最内层**（BUILDING › ESTATE/VILLAGE；同档取近）
  │     └── 一个都没落进 → 候选列表让他挑 → 仍挑不到 → 无位置首屏
  │
  ② 沿**归属链**向上：楼栋 → 小区/园区 → 街道 → 区 → 市 → 省
  │
  ③ 商品池 = prd_community_pool 中 community_no ∈ 链上任一聚落
  │     （链上的街道/区/市/省不是聚落，它们已在 B 方向展开时化成了聚落集合）
  │
  ④ 按 goodsNo / merchantNo 去重 → 按门店到**当前坐标**的距离排
```

**为什么第 ④ 步必须去重**：商家同时框了「阳光里小区」和「阳光里 3 幢」时，
站在 3 幢的人两条都会命中。这个重复不报错，只让首页看起来像数据坏了。

**为什么排序按坐标不按聚落**：按聚落分组会把「隔壁楼的菜摊」排到
「三公里外同小区的店」后面 —— 而用户要的是近。

#### 7.1.3 两端必须一致的三条

| # | 规则 | 一边写错的后果 |
|---|---|---|
| 1 | **EXCLUDE 优先于 INCLUDE** | B 端显示「已排除」，C 端照样看得到 —— 商家会以为排除功能坏了 |
| 2 | **待审的 INCLUDE 不生效** | 商家看着范围在清单里，却一个订单都不来，而这是他自己永远查不出来的 |
| 3 | **可见性是并集不是交集**（链上任一命中即可见） | 交集会让「站得越准看到越少」 |

### 7.2 一张单送不送得到

只对**商家自送**判，且**逐商家判**（购物车跨商家会拆成多张子单，各家圆心半径不同）。

**三条放行**，端上后端必须一字不差：

| 放行条件 | 为什么 |
|---|---|
| 收货地址没坐标 | 存量地址都是纯手填的，拿缺失数据去拦会误伤 |
| 门店没标过点 | 同上，圆心都没有 |
| 半径 ≤ 0 | 那是「不限距离」的表达 |

拦在**创建订单**这一步，不是支付后：付过钱再说「超出范围」，他要先退款才能重下。
端上在结算页提前置灰并**点名是哪一家**（车里三家店时，只说「超出范围」他不知道该改什么）。

### 7.3 经营范围与自送半径是两把尺，别合并

| | 经营范围 | 自送半径 |
|---|---|---|
| 回答 | 我的货**出现在**谁的首页 | 我**送不送得到**这个门牌 |
| 粒度 | 聚落 / 街道 / 区 / 市 / 省 | 米 |
| 判定 | communityNo 对齐 | 门店坐标 ↔ 收货坐标算距离 |
| 缺数据时 | 范围为空 = 谁也看不见 | 缺坐标 = **放行** |

**注意两者缺省行为相反**：范围为空是「关」，半径算不出是「开」。
这不是不一致 —— 范围是商家主动声明的（没声明就是没开张），
而半径是一条**保护性校验**（数据不全时不该把正常订单挡在门外）。

### 7.4 位置数据的三条不变量

1. **一个用户至多一条默认地址**，由应用层保证（设新默认时先清旧）；
   **不建 `(user_no, is_default)` 唯一索引** —— 那会让非默认地址也只能有一条
2. **生效位置指向的地址被删掉 = 当作没有**，不抛异常。
   删自己的地址是正常操作，不该让首页因此打不开
3. **订单一旦创建，地址就与地址簿脱钩**（整体快照）。用户改地址不影响历史订单
4. **浏览态永远不进订单。** 匹配到的聚落（可能不止一个）只决定「看到什么」，
   而订单的 `communityNo` 来自这一单实际选的履约对象（自提点 / 收货坐标）。
   把浏览态写进订单的后果是佣金归属与团长分账**说不清**，
   而那件事的症状出现在结算之后 —— 那时改不回来了
5. **重叠时可见性是并集不是交集。** 任一命中即显示。
   交集会让「站得越准看到越少」，与直觉正好相反
6. **围栏是每个聚落自己的事，不是全局常量。** 小区 1 公里、写字楼可能 150 米、
   村可能 3 公里 —— 用一个全局值代替它，等于宣称所有聚落一样大

### 7.5 运营端干预的副作用（必须在界面上说清）

| 动作 | 连带影响 |
|---|---|
| 合并两个重复聚落 | 被并掉的那条关闭（历史订单仍指着它），**一批商家的经营范围与社区货架改到保留的那条上** |
| 停用一条区划 | 只影响新选择，**存量商家的范围不动** |
| 聚落不挂区划 | 商家按「整个 XX 区」勾时**命中不到它**，只能被逐个点名 |
| 重建社区池 | 只重算索引，不改商品本身；改过可见性口径后必须做一次 |

## 8. 运营端新增功能的数据口径（O6–O9）

**这三张视图共用一张事实表**：聚落 × 买家数 × 商家数。

| 指标 | 口径 | 取自 |
|---|---|---|
| 聚落的买家数 | 生效位置解析到该聚落的用户数 | `usr_account.active_address_id` → `usr_address` → 聚落 |
| 聚落的地址数 | 收货地址落在该聚落的条数（含非生效） | `usr_address` |
| 聚落的商家数 | 经营范围覆盖该聚落的主体数 | `mch_service_area` 展开 |
| 聚落的商品数 | 社区池里的行数 | `prd_community_pool` |
| 供需状态 | 买家>0 且 商家=0 → **缺供给**<br>买家=0 且 商家>0 → **缺需求**<br>两者皆 0 → 空聚落 | 组合判定 |

**必须同时给出「算不了的那部分」**，否则这三张视图会把缺数据说成缺需求：

- 没有坐标的地址：**解析不到任何聚落**，它们既不算在任何一格里，也不该被静默丢掉
- 没有标点的门店：自送半径失效，但**不影响**经营范围口径的商家数
- 未开通的聚落：买家可能住在那儿（地址是自由填的），但它不在底图上

> 这一条是本节的要害：**分母写错的分析，比没有分析更危险** ——
> 它会让运营去某个「没需求」的片区撤商家，而那里只是没人标过坐标。

## 8.5 数据模型变更清单

本文提出的三处结构变更。**每一处都要按「加列必须同时改的七处」走一遍**
（见 [C端地址管理-交互方案 §6](../technical/design/C端地址管理-交互方案.md)）——
那份清单是加 `house_no` 时踩出来的，漏掉的两处都是「不报错」的那种。

| # | 变更 | 影响面 |
|---|---|---|
| 1 | `cmt_community.kind` 增加 `BUILDING` | 枚举登记表、三端词条、B 端选择器、运营端建档 |
| 2 | `cmt_community.parent_no`（可空，楼栋 → 小区/园区） | 建档必填校验、归属链查询、运营端展示层级 |
| 3 | `mch_service_area.mode`（`INCLUDE` 默认 / `EXCLUDE`） | 投影算法、B 端选择器、运营端覆盖明细、`prd_community_pool` **要全量重建一次** |

**另外两处不加列、只改代码：**

| # | 变更 | 说明 |
|---|---|---|
| 4 | 匹配读 `fence_radius` 而不是全局 `nearby-radius-m` | 数已在库里（23 个聚落全设了 1000 米），只是没人读 —— 见 §6.1.2 |
| 5 | 精确定位与模糊定位**分用途** | 模糊只用于「落到区」，不用于聚落匹配 —— 见 §6.1.8 |

> ⚠️ 第 3 项加完之后 `prd_community_pool` **必须全量重建**：
> 存量池行是按「没有 EXCLUDE」的口径写下来的，不重建的话排除项一条也不会生效，
> 而 B 端界面会显示「已排除」—— 说的和做的对不上，且没有任何报错。

## 10. 验收标准

| # | 场景 | 判据 |
|---|---|---|
| A1 | 买家切到「公司」 | 顶栏、副标题、商品池三处**同时**变过去，不出现互相矛盾的三句话 |
| A2 | 买家在结算页换地址 | 这一单变了，**默认地址纹丝不动** |
| A3 | 买家选了超出自送半径的地址 | 结算页提前置灰并点名商家；提交按钮不可点 |
| A4 | 买家地址没有坐标 | 一切照常可用，只是提示「还没有定位点」；**不拦保存、不拦下单** |
| A5 | 商家框「整个西湖区」 | 待运营审核；审过后该区所有已开通聚落都能看到他的货 |
| A6 | 商家用地图加一个新小区 | 直接开通、立即生效，不需要提报审核 |
| A7 | 商家没设经营范围 | 他的货**谁也看不到**（不是全域可见），且 B 端要明说这件事 |
| A8 | 运营合并两个重复聚落 | 提示会影响多少商家的范围；确认后商家范围与货架都指向保留的那条 |
| A9 | 运营看位置分布 | 「算不了的」单列一格，不混进「没需求」 |
| A10 | 用户注销/删地址 | 生效位置降级为无，首页照常有东西看 |
| A11 | 把某个聚落的围栏从 1000 改成 200 | 站在 500 米外的人**不再**匹配到它 —— 证明匹配真的读了这一列 |
| A12 | 站在楼栋里 | 顶栏显示**楼栋**（层级优先于距离）；商品是归属链并集 |
| A13 | 某商家同时框了小区与其中一栋楼 | 首页里他**只出现一次** |
| A14 | 某商家只框了小区、没框楼栋 | 站在楼栋里**也看得到他**（自动覆盖下级） |
| A20 | 商家框小区 + 排除 3 幢 | 站在 3 幢**看不到他**；站在 5 幢看得到 |
| A21 | 商家框街道 + 排除某园区 | 该园区**全部楼栋**都看不到他 |
| A22 | 商家只有 EXCLUDE、没有 INCLUDE | 谁也看不到；**B 端在保存时就拦住并说明** |
| A23 | 切到一条没有坐标的地址 | 归属**不变**，且明说「这个地址没有定位点，商品仍按 XX 显示」 |
| A24 | 只拿到模糊定位（区级） | **不匹配聚落**，改为按区给候选列表；不显示任何距离 |
| A25 | 用「当前位置」逛，然后下单 | 提示要不要存成地址；**不存也能下单**（选地址簿里已有的收货） |
| A15 | 自提下单 | 自提点列表是重叠聚落的并集；**选定的那个**决定订单 communityNo 与佣金归属 |
| A16 | 已下单后位置变了 | 历史订单的归属、分账、自提点**纹丝不动** |
| A17 | 一个围栏都没落进 | 给候选列表让他挑；挑不到回落到无位置首屏，**不空屏** |
| A18 | 定位变了（到了公司附近） | 主动问一句，**不自动切**；他不点就维持原样 |

## 11. 待确认

1. **C10「当前位置」的形态**：一次性上下文（不入地址簿）还是自动存成一条「临时」地址？
   前者干净但下单时要多问一步；后者会让地址簿被一堆临时地址塞满（上限只有 20 条）。
2. **O6 的买家口径用「生效位置」还是「所有地址」**？前者反映真实浏览，
   后者反映潜在需求。建议两个都给，但**默认展示生效位置**，因为它才是「现在有多少人在这儿看货」。
3. **未开通聚落里的买家怎么算**？他们的地址是自由填的、解析不到聚落。
   建议按街道（L4）兜底归集 —— 那一级一定有区划码。
4. **B5 门店坐标要不要设成建店必填**？现在 9 家有 7 家没标。
   设必填能一次性解决，但会挡住存量商家的其它编辑操作（与门牌号那次是同一类取舍）。
5. **手动多选：本文的结论是不做**（§6.1.5 有完整推演与成本清单）。
   如果你仍要保留这个方向，请把它当作**独立一期**排，
   并接受它需要一张新表与八条「只影响看不影响结算」的纪律 —— 而纪律会松。
6. **`parent_no` 只做两层够不够？** 园区 › 楼 › 单元 › 户会没完没了，
   我按「单元和户不是服务单位（没有商家按单元框范围）」砍在两层。
   如果将来真有「按单元做物业服务」的商家，这条要重议。
7. **EXCLUDE 要不要计入「待审」？** 我的判断是不用 —— 缩小自己的范围不影响别人。
   但如果运营担心商家用排除做变相的歧视性拒单（比如排除某个老旧小区），
   那它就该进审核队列。这是个业务判断，不是技术判断。
8. **围栏的默认值 1000 米对写字楼太大。** 建 `BUILDING` 时默认给多少？
   建议 150 米（一栋楼的占地量级），并在运营端把默认值按 `kind` 分开。
9. **楼栋（`BUILDING`）加不加 kind？** 加了 B 端选择器与运营端聚落维护都要跟着改。
   暂不加的话写字楼可以先当 `ESTATE` 建进去（语义上勉强成立），
   代价是运营端分不清「小区」与「写字楼」两类分布，且默认围栏会用错档。
10. **定位变了要不要主动问？** 我倾向问一句而**绝不自动切** ——
   自动切会让人在完全没察觉的情况下看到另一个地方的货，比麻烦糟得多。
11. **§2 那条作废的旧结论**要不要直接改进 TDD-按坐标算可见性？
   它现在被当作第二期的动机写着，而动机是错的 —— 第二步仍然值得做，但理由要换成
   「办公楼与任意门牌不属于任何聚落」，不是「商家没有绑定」。
