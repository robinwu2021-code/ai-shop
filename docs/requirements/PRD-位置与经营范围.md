## 0. 一句话

**买家选一个位置，商家框一片范围，两者在平台这里对上号 —— 对上了才有生意。**

这一模块回答的是同一个问题的三种问法：

| 端 | 用户心里那句话 | 系统要回答的 |
|---|---|---|
| C 端 | 「我在家 / 在公司 / 我现在这儿」 | 这个位置能看到哪些商家与商品 |
| B 端 | 「我做哪儿的生意」 | 这家店的货应该出现在谁的首页 |
| 运营端 | 「供需在哪儿对不上」 | 哪些位置没人服务、哪些商家框了范围却没人看得见 |

**为什么必须独立成模块**：这三件事此前分散在三份 TDD、两个交互方案和若干迁移里，
各自都对，但**没有一处把它们连起来看**。而这条链上任何一环断掉，
症状都长得一模一样 —— 买家打开首页，空的。谁都查不出是哪一环。

## 1. 模块边界

**在本模块内**：

- 买家的位置：地址簿、生效位置、当前定位、选点
- 商家的范围：经营范围（多粒度）、自送半径、门店坐标
- 平台的底图：聚落（小区 / 村 / 写字楼）、行政区划、商家提报
- 三者的**匹配规则**：一个位置能看到哪些商家、一张单送不送得到
- 运营端对以上全部的**查看、干预与分析**

**不在本模块内**（各有归属，本模块只引用）：

- 订单履约方式的选择（自提 / 自送 / 快递）—— 见交易域
- 佣金归属与分账 —— 见结算域
- 商品上架审核 —— 见商品域
- 自提点承接与团长 —— 见社区网点

### 2.1 真正的缺口是坐标，不是绑定

链路 `经营范围 → 社区池 → 商品` 是**按 communityNo 对齐**的，它今天能跑。
断的是另一半 —— **凡是要算距离的地方，两端都缺坐标**：

- 门店 9 家只有 2 家标过点，而 `requireWithinDeliveryRadius` 明写着「没坐标就放行」
  → **7 家商家设的自送半径形同虚设**，多远的单都进得来，等他要送货才发现送不到
- 买家 3 条地址里 2 条有坐标（新加的选点页起作用了），但存量与手填的路仍然产出无坐标地址
- 已开通聚落 23 个，中心点与围栏半径**都齐**（这一侧反而是最完整的）——
  但**围栏没有被匹配读取**，实际判定用的是全局 5000 米，见 §6.1.2

## 3. 概念与口径（这一节是本模块的词典）

**四组最容易混的概念，每一组混掉都会造成一类查不出的故障：**

| 概念 | 回答什么 | 存在哪 | 混掉的后果 |
|---|---|---|---|
| **生效位置** | 我**现在**按哪儿看货 | `usr_account.active_address_id` | 与默认合并 → 给父母下单时改了收货人 |
| **默认收货地址** | 下单时**预填**哪个收货人 | `usr_address.is_default` | 同上，反向 |
| **这一单的地址** | **这一单**送到哪儿 | 只在结算页内存里，下单时快照进订单 | 与默认合并 → 寄一次父母家，从此每单都预填那儿 |
| **订单地址快照** | 这张单当时**寄到了哪儿** | `ord_sub_order.receiver_*` | 与地址簿共用 → 用户改地址会改写历史订单 |

| 概念 | 含义 | 注意 |
|---|---|---|
| **聚落**（community） | 小区 / 村 / 写字楼，挂在街道（L4）下 | **村不是区划粒度**，它和小区同级（2026-08-22 定） |
| **经营范围**（service area） | 商家做哪儿：省 / 市 / 区 / 街道 / 聚落，**可跨粒度组合** | 「三个小区 + 一个区」= 四条 |
| **社区池**（community pool） | 「这件商品出现在哪些社区」的**派生索引** | 是产物不是真源，改口径后要重建 |
| **自送半径** | 门店自送的圆，圆心是门店坐标 | 与经营范围是**两把尺**，见 §7.3 |

「谁能对这件事做什么」。**空白格不是遗漏，是刻意不给**。

| 能力 | C 端买家 | B 端商家 | 运营端 |

## 6. 交互流程

### 6.1 C 端：选一个位置

```
打开 App
   │
   ├── 有生效位置 ──► 顶栏显示它（家 / 公司 / 地址简称）
   │                      │ 点它
   │                      ▼
   │                 位置列表：每条可「切到这里」
   │                 底部「管理收货地址 ›」
   │
   └── 一个位置都没有 ──► 顶栏「选择位置」
                          **不弹窗、不跳转** —— 首屏在零位置信息下也要有东西看
                              │ 点它
                              ▼
                        选点页（搜索 / 当前定位 / 附近 / 地图 / 手动）
```

**切换位置之后系统做什么**（用户看不见但必须一致）：

1. 生效位置写到服务端（换设备后仍是同一个上下文）
2. 用它的坐标解析归属聚落 → 换商品池
3. 购物车里在新位置买不到的行**标出来并禁选**，不静默清空（那是用户的东西）
4. **已下的订单不受影响** —— 订单在创建那一刻就快照了自己的收货地址

#### C10 缺口：「当前位置」还不是一个可选项

用户心里的三个选项是「家 / 公司 / **我现在这儿**」，而第三个在系统里
**必须先变成一条地址才能生效** —— 因为生效位置指向 `addressId`。

要补的是**一次性浏览上下文**：选「当前位置」时不入地址簿，
只在本次会话里按这个坐标看货；下单时再问他要不要存成地址。

> 这一条卡在能力上：微信 2026-09-03 驳回了 `getLocation`（开放范围不含
> 「匹配附近服务」与「辅助填写收货地址」），所以小程序里拿不到静默精确定位。
> 可行的形态是 `chooseLocation`（用户在地图上点一下）或 `getFuzzyLocation`（区级）。

### 6.1.1 智能匹配：从一个坐标到「我该看哪片货」

```
定位 / 选中的地址（一个坐标）
        │
        ▼
  匹配覆盖它的聚落                ← 判据应是**每个聚落自己的围栏**，见 §6.1.2
        │
        ├── 落在一个里 ──► 就是它
        ├── 落在多个里 ──► **系统自动全部纳入**，商品取并集（§6.1.4）
        └── 一个都没落进 ──► 按距离给候选列表，让他自己挑；挑不到就回落到无位置首屏
```

**用户看到的始终是「一个地方」**（顶栏写着「阳光里 3 幢」），
而不是一个需要他管理的清单。重叠是系统内部的事，不该变成用户的概念。

### 6.1.2 先修匹配精度：围栏这一列**已经有了，但没人读**

线上实测（2026-09-04）：

| 事实 | 值 |
|---|---|
| `cmt_community.fence_radius` | **23 个聚落全设了，全是 1000 米** |
| 运营端设置入口 | ✅ `OpsCommunityController.setFence`，有审计日志 |
| ops 列表展示 | ✅ `CommunityAdminServiceImpl:720` |
| **匹配时读它** | ❌ **一行都没读** —— `withinRadius()` 用的是全局 `shop.community.nearby-radius-m`（默认 **5000**） |

于是今天的「智能匹配」实际是**「中心点 5 公里内按距离排」**。
小区尺度上这还凑合（1 公里的围栏被放大成 5 公里，只是候选多了些）；
**楼栋尺度上它直接不成立** —— 5 公里内的写字楼可以有几十栋，排第一的那个大概率不是你所在的这栋。

**所以楼栋要落地，第一步不是加 `kind`，是让匹配读 `fence_radius`。**
这一步不加表、不加字段、不改端上，只是把一个已经在库里的数用起来。

### 6.1.3 楼栋挂区划：合理，但理由不是「楼栋有行政意义」

**结论：合理，按 `kind=BUILDING` 与小区、村平级挂在街道（L4）下。**

真实理由只有一条：**粗粒度经营范围需要一棵完整的树来展开**。
商家说「我做整个西湖区」时，系统靠区划码前缀把它展开到该区所有聚落；
楼栋不挂上去就命中不到任何粗粒度范围 —— 运营端自己的文案早写着这条：
「没挂区划的社区，商家按『整个西湖区』这样勾范围时命中不到它，它只能被逐个点名」。
而区划树是我们唯一一棵**完整且官方**的树。

办公场景与小区场景有两处不同，都**不影响这个结构**，但要知道：

| | 小区 | 写字楼 |
|---|---|---|
| 成员关系 | 稳定（住在那儿、团长是邻居、自提点在门口） | **时段性**（一天九小时） |
| 密度 | 一个街道下几个到几十个 | CBD 一个街道下可能几十栋 |
| 物流单元强度 | 中（可能多门多栋） | **强**（一个大堂、一个前台、骑手进不去） |

- **密度**由「街道」这一档解掉：商家不必逐栋勾，勾街道即可；自送的精度归半径管，不归聚落管
- **物流单元强度高**反而是好消息：写字楼比小区更适合做自提点与集中配送
- **时段性**是唯一真正的新问题 —— 它指向 §6.1.5，也正是「多选」被提出来的根源

### 6.1.4 重叠：系统自动纳入，**不做成用户的多选**

坐标同时落在「阳光里 3 幢」与「阳光里小区」两个围栏里时，
**系统把两个都算上**，商品池取并集、按 `goodsNo` 去重。

- 去重必须按 `goodsNo` / `merchantNo`，不能按 (单位, 商品) ——
  商家同时框了小区和其中一栋楼时，不去重他会出现两次；这个重复不报错，只让首页看着像数据坏了
- 可见性是**并集**：任一命中即可见
- 用户界面上**不出现「服务单位」这个词**，顶栏只显示最内层那个（「阳光里 3 幢」）

**这样就不需要包含关系（父子结构）。** 有了父子就得回答
「商家框了小区，算不算覆盖里面每一栋楼」—— 而这个问题**没有普遍正确的答案**：
物业类服务按楼算，生鲜配送按小区算。让围栏去重叠，比让模型去表达包含关系诚实。

### 6.1.5 手动多选：**评估过，不做**

> 本节保留完整推演，因为「同时选家和公司」是个非常自然的诉求，
> 三个月后一定会有人再提一次。

诉求的原话是「同时选择办公场地和家」。而这个例子恰恰说明它不该做：

**这两件事发生在不同时刻，不是同时。**

- 中午在办公室想买楼下便利店 → 家附近的生鲜团购是**噪音**
- 下班想让菜送到家 → 办公楼的便利店是**噪音**

首页混着两个地方的货，用户每次都要自己心里过滤一遍。
而这个产品的立身之本是「**我邻居**在买什么」—— 混合直接把它稀释掉。

**成本这一侧很具体：**

| 要新增的 | |
|---|---|
| `usr_active_area` 一张表 | 多选要能查「这个聚落有多少人在看」，塞 JSON 列查不了 |
| 并集查询 + 去重 | |
| 购物车不可售标记接多选 | 取消勾选后那些行要变灰 |
| 顶栏形态「主单位 · 等 N 个」 | |
| 上限与替换交互 | |
| 切位置时清空 + 提示 | |
| 运营端 O13 多选分布 | 否则上限定几个没有依据 |
| **一整套「只影响看、不影响结算」的规则（8 条）** | ← **这套规则本身就是复杂性的证据** |

最后一行是关键：**需要写八条规则才能让一个功能不出错，说明它在跟系统其它部分较劲。**
佣金归属、团长、自提点都挂在单个 `communityNo` 上，多选每天都在试图渗进去，
而挡住它靠的是纪律，不是结构 —— 纪律会松。

**替代方案拿到它 90% 的收益，成本接近零：**

| | 手动多选 | §6.1.4 自动纳入 + §6.1.6 免费切换 |
|---|---|---|
| 边界处 / 楼栋在小区里 | 解决 | 解决，**而且更准**（靠围栏，不靠用户判断） |
| 家 + 公司 | 混合，认知负担 | 切换，**每次都干净** |
| 用户要学的新概念 | 服务单位 / 主单位 / 上限 3 | **无** |
| 新表 / 新规则 | 1 张表 + 8 条规则 | 0 |
| 归属歧义 | 靠规则挡 | **不存在** |

### 6.1.6 把切换做到几乎免费

多选的真实驱动力是「切换太麻烦」。那就把切换变便宜，而不是绕过它：

1. **定位变了主动问一句**：「你好像在公司附近，切过去吗？」—— 一次点击，不弹强制弹窗
2. **顶栏常驻两个 chip**（家 / 公司），点一下就换，不用进列表
3. **切换后首页是干净的一个地方**，不是混合
4. 时段性可以作为**提示的时机**（工作日上午优先提示公司），但**不自动切** ——
   自动切会让人在完全没察觉的情况下看到另一个地方的货，那比麻烦糟得多

## 7. 业务逻辑

### 7.1 一个位置能看到哪些商品

**今天的实现（按 communityNo 对齐）：**

```
生效位置(有坐标) ──► nearbyCommunities 取覆盖它的聚落 ──► communityNo
                                                            │
商家经营范围(mch_service_area) ──► 投影 ──► prd_community_pool
                                                            │
                                                            ▼
                                            GoodsServiceImpl 按 communityNo 过滤
```

- 经营范围为**空**的商家：对**所有人不可见**（不是「全域可见」）
- 经营范围为 **PROVINCE/CITY** 级：按国标码前缀展开到该范围内所有已开通聚落
- 位置**没有坐标**：推不出聚落 → 保持原有归属不变，**不清空**
  （微信地址簿导入的地址就没有坐标，清空会让用户「换了个地址商品全没了」）

**坐标落在多个围栏里时**（§6.1.4 的规则落成一句 SQL）：

```
匹配到的聚落 [A, B] ──► prd_community_pool where community_no in (A,B)
                                │
                                ▼
                  按 goodsNo 去重 ──► 按门店到当前位置的距离排
```

**去重必须按 `goodsNo` / `merchantNo`，不能按 (聚落, 商品)** ——
商家同时框了「阳光里小区」和「阳光里 3 幢」时，站在 3 幢的人会看到他两次。
这个重复不会报错，只会让首页看起来像数据出了问题。

**这是系统行为，用户无感**：他看到的仍是一个地方（顶栏「阳光里 3 幢」）。

**将来（按坐标算可见性，第二步，未做）**：去掉中间那一跳，后端按坐标 + 范围实时算。
好处是办公楼、任意门牌这类**不属于任何已开通聚落**的位置也能用。

### 7.2 一张单送不送得到

只对**商家自送**判，且**逐商家判**（购物车跨商家会拆成多张子单，各家圆心半径不同）。

**三条放行**，端上后端必须一字不差：

| 放行条件 | 为什么 |
|---|---|
| 收货地址没坐标 | 存量地址都是纯手填的，拿缺失数据去拦会误伤 |
| 门店没标过点 | 同上，圆心都没有 |
| 半径 ≤ 0 | 那是「不限距离」的表达 |

拦在**创建订单**这一步，不是支付后：付过钱再说「超出范围」，他要先退款才能重下。
端上在结算页提前置灰并**点名是哪一家**（车里三家店时，只说「超出范围」他不知道该改什么）。

### 7.3 经营范围与自送半径是两把尺，别合并

| | 经营范围 | 自送半径 |
|---|---|---|
| 回答 | 我的货**出现在**谁的首页 | 我**送不送得到**这个门牌 |
| 粒度 | 聚落 / 街道 / 区 / 市 / 省 | 米 |
| 判定 | communityNo 对齐 | 门店坐标 ↔ 收货坐标算距离 |
| 缺数据时 | 范围为空 = 谁也看不见 | 缺坐标 = **放行** |

**注意两者缺省行为相反**：范围为空是「关」，半径算不出是「开」。
这不是不一致 —— 范围是商家主动声明的（没声明就是没开张），
而半径是一条**保护性校验**（数据不全时不该把正常订单挡在门外）。

### 7.4 位置数据的三条不变量

1. **一个用户至多一条默认地址**，由应用层保证（设新默认时先清旧）；
   **不建 `(user_no, is_default)` 唯一索引** —— 那会让非默认地址也只能有一条
2. **生效位置指向的地址被删掉 = 当作没有**，不抛异常。
   删自己的地址是正常操作，不该让首页因此打不开
3. **订单一旦创建，地址就与地址簿脱钩**（整体快照）。用户改地址不影响历史订单
4. **浏览态永远不进订单。** 匹配到的聚落（可能不止一个）只决定「看到什么」，
   而订单的 `communityNo` 来自这一单实际选的履约对象（自提点 / 收货坐标）。
   把浏览态写进订单的后果是佣金归属与团长分账**说不清**，
   而那件事的症状出现在结算之后 —— 那时改不回来了
5. **重叠时可见性是并集不是交集。** 任一命中即显示。
   交集会让「站得越准看到越少」，与直觉正好相反
6. **围栏是每个聚落自己的事，不是全局常量。** 小区 1 公里、写字楼可能 150 米、
   村可能 3 公里 —— 用一个全局值代替它，等于宣称所有聚落一样大

### 7.5 运营端干预的副作用（必须在界面上说清）

| 动作 | 连带影响 |
|---|---|
| 合并两个重复聚落 | 被并掉的那条关闭（历史订单仍指着它），**一批商家的经营范围与社区货架改到保留的那条上** |
| 停用一条区划 | 只影响新选择，**存量商家的范围不动** |
| 聚落不挂区划 | 商家按「整个 XX 区」勾时**命中不到它**，只能被逐个点名 |
| 重建社区池 | 只重算索引，不改商品本身；改过可见性口径后必须做一次 |

## 8. 运营端新增功能的数据口径（O6–O9）

**这三张视图共用一张事实表**：聚落 × 买家数 × 商家数。

| 指标 | 口径 | 取自 |
|---|---|---|
| 聚落的买家数 | 生效位置解析到该聚落的用户数 | `usr_account.active_address_id` → `usr_address` → 聚落 |
| 聚落的地址数 | 收货地址落在该聚落的条数（含非生效） | `usr_address` |
| 聚落的商家数 | 经营范围覆盖该聚落的主体数 | `mch_service_area` 展开 |
| 聚落的商品数 | 社区池里的行数 | `prd_community_pool` |
| 供需状态 | 买家>0 且 商家=0 → **缺供给**<br>买家=0 且 商家>0 → **缺需求**<br>两者皆 0 → 空聚落 | 组合判定 |

**必须同时给出「算不了的那部分」**，否则这三张视图会把缺数据说成缺需求：

- 没有坐标的地址：**解析不到任何聚落**，它们既不算在任何一格里，也不该被静默丢掉
- 没有标点的门店：自送半径失效，但**不影响**经营范围口径的商家数
- 未开通的聚落：买家可能住在那儿（地址是自由填的），但它不在底图上

> 这一条是本节的要害：**分母写错的分析，比没有分析更危险** ——
> 它会让运营去某个「没需求」的片区撤商家，而那里只是没人标过坐标。

## 10. 验收标准

| # | 场景 | 判据 |
|---|---|---|
| A1 | 买家切到「公司」 | 顶栏、副标题、商品池三处**同时**变过去，不出现互相矛盾的三句话 |
| A2 | 买家在结算页换地址 | 这一单变了，**默认地址纹丝不动** |
| A3 | 买家选了超出自送半径的地址 | 结算页提前置灰并点名商家；提交按钮不可点 |
| A4 | 买家地址没有坐标 | 一切照常可用，只是提示「还没有定位点」；**不拦保存、不拦下单** |
| A5 | 商家框「整个西湖区」 | 待运营审核；审过后该区所有已开通聚落都能看到他的货 |

| A7 | 商家没设经营范围 | 他的货**谁也看不到**（不是全域可见），且 B 端要明说这件事 |

| A9 | 运营看位置分布 | 「算不了的」单列一格，不混进「没需求」 |
| A10 | 用户注销/删地址 | 生效位置降级为无，首页照常有东西看 |
| A11 | 把某个聚落的围栏从 1000 改成 200 | 站在 500 米外的人**不再**匹配到它 —— 证明匹配真的读了这一列 |
| A12 | 站在楼栋里（楼栋与小区围栏重叠） | 顶栏显示**楼栋**；商品是两者并集 |
| A13 | 某商家同时框了小区与其中一栋楼 | 首页里他**只出现一次** |
| A14 | 某商家只框了小区、没框楼栋 | 站在楼栋里**也看得到他**（并集，不是交集） |

| A17 | 一个围栏都没落进 | 给候选列表让他挑；挑不到回落到无位置首屏，**不空屏** |
| A18 | 定位变了（到了公司附近） | 主动问一句，**不自动切**；他不点就维持原样 |

## 11. 待确认

1. **C10「当前位置」的形态**：一次性上下文（不入地址簿）还是自动存成一条「临时」地址？
   前者干净但下单时要多问一步；后者会让地址簿被一堆临时地址塞满（上限只有 20 条）。
2. **O6 的买家口径用「生效位置」还是「所有地址」**？前者反映真实浏览，
   后者反映潜在需求。建议两个都给，但**默认展示生效位置**，因为它才是「现在有多少人在这儿看货」。
3. **未开通聚落里的买家怎么算**？他们的地址是自由填的、解析不到聚落。
   建议按街道（L4）兜底归集 —— 那一级一定有区划码。
4. **B5 门店坐标要不要设成建店必填**？现在 9 家有 7 家没标。
   设必填能一次性解决，但会挡住存量商家的其它编辑操作（与门牌号那次是同一类取舍）。
5. **手动多选：本文的结论是不做**（§6.1.5 有完整推演与成本清单）。
   如果你仍要保留这个方向，请把它当作**独立一期**排，
   并接受它需要一张新表与八条「只影响看不影响结算」的纪律 —— 而纪律会松。
6. **围栏的默认值 1000 米对写字楼太大。** 建 `BUILDING` 时默认给多少？
   建议 150 米（一栋楼的占地量级），并在运营端把默认值按 `kind` 分开。
7. **楼栋（`BUILDING`）加不加 kind？** 加了 B 端选择器与运营端聚落维护都要跟着改。
   暂不加的话写字楼可以先当 `ESTATE` 建进去（语义上勉强成立），
   代价是运营端分不清「小区」与「写字楼」两类分布，且默认围栏会用错档。
8. **定位变了要不要主动问？** 我倾向问一句而**绝不自动切** ——
   自动切会让人在完全没察觉的情况下看到另一个地方的货，比麻烦糟得多。
8. **§2 那条作废的旧结论**要不要直接改进 TDD-按坐标算可见性？
   它现在被当作第二期的动机写着，而动机是错的 —— 第二步仍然值得做，但理由要换成
   「办公楼与任意门牌不属于任何聚落」，不是「商家没有绑定」。
