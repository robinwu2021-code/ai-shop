## 0. 一句话

**买家选一个位置，商家框一片范围，两者在平台这里对上号 —— 对上了才有生意。**

同一个问题的三种问法：

| 端 | 用户心里那句话 | 系统要回答的 |
|---|---|---|
| C 端 | 「我在家 / 在公司 / 我现在这儿」 | 这个位置能看到哪些商家与商品 |
| B 端 | 「我做哪儿的生意」 | 这家店的货应该出现在谁的首页 |
| 运营端 | 「供需在哪儿对不上」 | 哪些位置没人服务、哪些商家框了范围却没人看得见 |

**为什么独立成模块**：这三件事此前分散在三份 TDD、两个交互方案和若干迁移里，
各自都对，但没有一处把它们连起来看。而这条链上**任何一环断掉，症状都一样** ——
买家打开首页，空的。谁都查不出是哪一环。

---

## 1. 模块边界

**在本模块内**：买家的位置（地址簿 / 生效位置 / 当前位置 / 选点）· 商家的范围（经营范围 / 自送半径 / 门店坐标）·
平台的底图（聚落 / 区划 / 商家提报）· 三者的**匹配规则** · 运营端对以上的查看、干预与分析。

**不在本模块内**（各有归属，本模块只引用）：履约方式的选择（交易域）· 佣金与分账（结算域）·
商品上架审核（商品域）· 自提点承接与团长（社区网点）。

## 3. 概念与口径（本模块的词典）

**四组最容易混的，每混一组就是一类查不出的故障：**

| 概念 | 回答什么 | 存在哪 | 混掉的后果 |
|---|---|---|---|
| **生效位置** | 我**现在**按哪儿看货 | `usr_account.active_address_id` | 与默认合并 → 给父母下单时改了收货人 |
| **默认收货地址** | 下单时**预填**哪个收货人 | `usr_address.is_default` | 同上，反向 |
| **这一单的地址** | **这一单**送到哪儿 | 结算页内存，下单时快照 | 与默认合并 → 寄一次父母家，从此每单都预填那儿 |
| **订单地址快照** | 这张单当时**寄到了哪儿** | `ord_sub_order.receiver_*` | 与地址簿共用 → 用户改地址会改写历史订单 |

| 概念 | 含义 | 要点 |
|---|---|---|
| **聚落** | 服务单位：小区 / 村 / 园区 / **楼栋** | 小区村园区挂街道（L4）；楼栋挂小区或园区（§8.2） |
| **归属链** | 楼栋 → 小区/园区 → 街道 → 区 → 市 → 省 | **声明的，不是靠围栏算的**（§7.1.2） |
| **围栏** | 每个聚落自己的覆盖半径 | 只回答「我此刻站在哪个聚落里」，不表达归属 |
| **经营范围** | 商家做哪儿，可跨粒度组合，**可 include 可 exclude** | §7.1.1 |
| **社区池** | 「这件商品出现在哪些聚落」的**派生索引** | 是产物不是真源，改口径后要重建 |
| **自送半径** | 门店自送的圆，圆心是门店坐标 | 与经营范围是**两把尺**（§7.3） |

## 6. 交互流程

### 6.1 C 端

#### 6.1.0 一条铁律：**位置永远是一条地址**

> 2026-09-04 修正。此前本文把「定位」和「选中的地址」写成了两条并列的入口 ——
> 那是多余的一层。

**定位只做一件事：匹配用户自己的收货地址。**

```
定位坐标
  ├── 匹配到某条收货地址 ──► 在列表里标出来；**点一下直接切**，不弹窗不追问
  └── 一条都没匹配到    ──► 以**当前位置**那条地址为准（逆地理出来的地址，临时的）
                              │
        （无论哪条）生效位置都是一条地址 ──► 它的坐标 ──► 聚落匹配 ──► 商品池
```

**为什么这样更对：**

- 用户脑子里只有「我在哪」这一个概念，而「哪」永远是一个地址（家 / 公司 / 我现在这儿）。
  把定位做成能直接选聚落的第二条路，等于让他理解两套东西
- 归属、下单预填、送不送得到，全都挂在地址上 —— 位置不是地址时，
  这几件事各自要一套兜底
- **「没匹配到」不是死路**：以当前位置为准，他照样能逛、能下单
  （下单时再问要不要把它存成地址）

**匹配的判据**：坐标到收货地址的直线距离，取最近的一条且要足够近
（沿用 §6.1.6 的 1 公里）。**不匹配聚落** —— 那是下游的事。

#### 6.1.1 打开 App → 我在哪 → 看什么

```
打开 App
   │
   ├── 有生效位置 ──► 顶栏显示它（家 / 公司 / 阳光里 3 幢）
   │                      │ 点它 ──► 位置列表，每条可切；底部「管理收货地址 ›」
   │
   └── 一个都没有 ──► 顶栏「选择位置」。**不弹窗、不跳转**
                          │ 点它 ──► 选点页（搜索 / 当前定位 / 附近 / 地图 / 手动）
                          ▼
                     首屏在零位置信息下**照常有东西看**
```

匹配（细则见 §7.1.2）：

```
坐标 → 落在哪些聚落围栏里 → 取**最内层**（楼栋 › 小区/村；同档取近）  ← 这是「我在哪」
                                    │
                                    ▼
                    沿**归属链**向上 → 商品取链上并集去重
```

**用户看到的始终是一个地方**（顶栏「阳光里 3 幢」）。链上还有小区、街道、区 ——
那是系统内部的事，不该变成用户要管理的清单。

#### 6.1.2 切换地址：七条规则

| # | 情况 | 系统行为 |
|---|---|---|
| 1 | 新地址**有坐标** | 重新匹配 → 换最内层聚落 → 换归属链 → 换商品池 |
| 2 | 新地址**没有坐标** | **保持原有归属不变**，并明说「这个地址没有定位点，商品仍按 XX 显示」。**绝不清空** —— 清空的表现是「换了个地址，商品全没了」 |
| 3 | 有坐标但**一个围栏都没落进** | 归属降级为空 → 回落到平台推荐 + 全域在售，提示「这一带还没开通」 |
| 4 | 切换成功 | **顶栏、副标题、商品池三处同时变** —— 顶栏写「公司」而货还是家那边的，是已经踩过的坑 |
| 5 | 购物车 | 重算不可售：买不到的行**标出来并禁选**，**不删** |
| 6 | 已下的订单 | **完全不受影响**（创建那一刻已快照收货地址与自提点） |
| 7 | 切换失败（网络） | 维持原状并提示，**不留半切状态** |

**存哪**：服务端为准（`usr_account.active_address_id`），端上留一份做即时响应。

#### 6.1.3 当前位置：一次性上下文

| 来源 | 精度 | 能否匹配聚落 |
|---|---|---|
| `chooseLocation`（用户在地图上点） | **米级** | ✅ 走正常匹配 |
| `getLocation`（静默精确） | 米级 | ⚠️ **微信 2026-09-03 驳回**，小程序拿不到 |
| `getFuzzyLocation`（静默模糊） | **区级，误差约 5 km** | ❌ 见下 |
| 浏览器定位（H5） | 视设备 | ⚠️ 没配地图 JS key，`chooseLocation` 直接 fail |

**模糊定位为什么不能匹配聚落**：围栏是 1000 米（小区）到 150 米（楼栋）量级，
而模糊定位误差 5 公里 —— **用它匹配出来的是噪音，不是结果**。
它只够把你**落到你所在的区**，然后给该区候选让你挑 —— 而那一步恰恰是手选省市区里最烦的一步。

其余规则：**不入地址簿**（20 条上限会被塞满）· **只作用于本次会话** ·
顶栏显示「当前位置 · XX」把它标出来 · **下单时才问**要不要存成地址，**不存也能下单** ·
拿不到定位**不弹窗不拦路**。

**它不是备胎，是默认值**（§6.1.0）：定位匹配不到任何一条收货地址时，
系统直接以当前位置为准，而不是回落到「无位置首屏」。
后者只留给**连定位都拿不到**的情况。

### 6.2 B 端：建店框范围

```
建店 / 编辑门店
   ▼
经营范围选择器
   ├── Tab A 按区划：省 › 市 › 区 › 街道 › 聚落（村/小区/园区/楼栋混排）
   │      每一级都有「整个 XX」一行
   ├── Tab B 搜索：跨层级匹配，按层级从大到小排
   └── 末尾固定「在地图上选点添加」   ← 小区/楼栋从地图来的唯一入口
   ▼
勾选 → 省市区待审 / 街道及以下自助生效
   │      **可点名到楼栋，也可从已勾范围里排除某几栋**
   ▼
门店坐标：从地图上标一个点        ← B6，9 家有 7 家没做
   ▼
反馈：这个范围覆盖多少活跃买家     ← B11
```

**include / exclude**（判定见 §7.1.1）：

| 商家想表达 | 怎么勾 |
|---|---|
| 整个小区都做 | INCLUDE 小区（**自动含全部子楼栋**） |
| 只做其中两栋 | INCLUDE 3 幢、5 幢 |
| 小区都做但 3 幢不做 | INCLUDE 小区 + **EXCLUDE 3 幢** |
| 整条街做但某园区不做 | INCLUDE 街道 + **EXCLUDE 园区**（含其全部楼栋） |

**矛盾在输入端消除**：勾了排除就把对应的 include 去掉，反之亦然 ——
比在判定端消除诚实，后者要求用户记住一条规则。

## 7. 业务逻辑

### 7.1 匹配规则：同一个覆盖关系的两个方向

**B 端问「我覆盖谁」，C 端问「谁覆盖我」。两边算的必须是同一件事** ——
否则会出现「商家看着自己覆盖了、买家就是看不到」，而那种问题商家永远查不出来。

投影表 `prd_community_pool` 就是 **B 方向算好的结果**，C 端只查它。

#### 7.1.1 B 方向：我的货出现在哪些聚落

```
对每一条 mch_service_area：
  COMMUNITY, ref=小区/村/园区  → 它自己 + 它的**全部子楼栋**
  COMMUNITY, ref=楼栋          → 它自己
  STREET                       → 该街道下全部聚落（含楼栋）
  DISTRICT / CITY / PROVINCE   → 按国标码前缀展开到范围内全部聚落
  ↓
覆盖 = ⋃(INCLUDE 展开) − ⋃(EXCLUDE 展开)        ← 先并后减
  ↓
滤掉 status=PENDING 的 INCLUDE（待审不生效；**EXCLUDE 不需审核**）
  ↓
写进 prd_community_pool（商品 × 聚落）
```

**四条边界：**

| 情况 | 结果 | 为什么 |
|---|---|---|
| 范围**一条都没有** | **谁也看不到**（不是全域可见） | 没声明就是没开张 —— B13 必须明说 |
| 只有 EXCLUDE、没有 INCLUDE | 谁也看不到 | 空集减东西还是空集，B 端保存时就该拦 |
| 聚落**没挂区划** | 命中不到粗粒度范围，只能被逐个点名 | 平台不按名字猜归属：猜错不报错，只会让它悄悄出现在别人范围里 |
| 楼栋缺 `region_code` | 同上 —— 所以楼栋建档**两个字段都必填** | |

#### 7.1.2 C 方向：我能看到哪些货

```
一个坐标（生效位置 / 当前位置）
  ① 落在哪些聚落围栏里 → 取**最内层**（BUILDING › ESTATE/VILLAGE；同档取近）
  │     └── 一个都没落进 → 候选列表让他挑 → 仍挑不到 → 无位置首屏
  ② 沿**归属链**向上：楼栋 → 小区/园区 → 街道 → 区 → 市 → 省
  ③ 商品池 = prd_community_pool 中 community_no ∈ 链上任一聚落
  ④ 按 goodsNo / merchantNo 去重 → 按门店到**当前坐标**的距离排
```

- **① 层级优先于距离**：站在楼门口时，隔壁小区的中心可能比本楼中心更近
- **④ 必须去重**：商家同时框了小区和其中一栋楼时，站在楼里两条都命中；
  这个重复不报错，只让首页看起来像数据坏了
- **④ 排序按坐标不按聚落**：分组会把「隔壁楼的菜摊」排到「三公里外同小区的店」后面

#### 7.1.3 两端必须一致的三条

| # | 规则 | 一边写错的后果 |
|---|---|---|
| 1 | **EXCLUDE 优先于 INCLUDE** | B 端显示「已排除」，C 端照样看得到 —— 商家以为排除坏了 |
| 2 | **待审的 INCLUDE 不生效** | 商家看着范围在清单里，却一个订单都不来，且他永远查不出来 |
| 3 | **可见性是并集不是交集**（链上任一命中即可见） | 交集会让「站得越准看到越少」 |

#### 7.1.4 归属是声明的，围栏只回答「我站在哪」

**不要用围栏重叠去表达「楼栋在小区里」。** 几何上不可靠：大小区边上的一栋楼
可能落在小区中心圆之外，而隔壁小区的圆反而把它罩进去。

- **归属**：`parent_no` + `region_code`，**数据声明**
- **围栏**：`fence_radius`，只回答「此刻我站在哪一个最内层聚落里」

而**围栏这一列今天没人读** —— 匹配用的是全局 `shop.community.nearby-radius-m`（5000）。
小区尺度上还凑合；**楼栋尺度上直接不成立**（五公里内几十栋写字楼）。
所以楼栋要落地，**第一步不是加 `kind`，是让匹配读 `fence_radius`** —— 不加表不加字段。

### 7.2 一张单送不送得到

只对**商家自送**判，且**逐商家判**（跨商家会拆成多张子单，圆心半径各不同）。

**三条放行**，端上后端必须一字不差：

| 放行条件 | 为什么 |
|---|---|
| 收货地址没坐标 | 存量地址都是手填的，拿缺失数据去拦会误伤 |
| 门店没标过点 | 同上，圆心都没有 |
| 半径 ≤ 0 | 那是「不限距离」的表达 |

拦在**创建订单**这一步，不是支付后。端上在结算页提前置灰并**点名是哪一家**。

### 7.3 经营范围与自送半径是两把尺

| | 经营范围 | 自送半径 |
|---|---|---|
| 回答 | 我的货**出现在**谁的首页 | 我**送不送得到**这个门牌 |
| 粒度 | 聚落 / 街道 / 区 / 市 / 省 | 米 |
| 判定 | 聚落对齐（归属链） | 门店坐标 ↔ 收货坐标算距离 |
| 缺数据时 | 范围为空 = **谁也看不见** | 缺坐标 = **放行** |

**缺省行为相反不是不一致**：范围是商家主动声明的（没声明就是没开张），
半径是一条**保护性校验**（数据不全时不该把正常订单挡在门外）。

### 7.4 六条不变量

1. **一个用户至多一条默认地址**，应用层保证；**不建 `(user_no, is_default)` 唯一索引** ——
   那会让非默认地址也只能有一条
2. **生效位置指向的地址被删 = 当作没有**，不抛异常
3. **订单一旦创建，地址就与地址簿脱钩**（整体快照）
4. **浏览态永远不进订单**：匹配到的聚落只决定「看到什么」，
   订单的 `communityNo` 来自这一单实际选的履约对象（自提点 / 收货坐标）
5. **可见性是并集不是交集**
6. **围栏是每个聚落自己的事，不是全局常量** —— 小区 1 公里、楼栋 150 米、村可能 3 公里。
   用一个全局值代替它，等于宣称所有聚落一样大

### 7.5 运营端干预的副作用（必须在界面上说清）

| 动作 | 连带影响 |
|---|---|
| 合并两个重复聚落 | 被并掉的关闭（历史订单仍指着它），**一批商家的范围与货架改到保留的那条** |
| 停用一条区划 | 只影响新选择，**存量商家的范围不动** |
| 聚落不挂区划 | 商家按「整个 XX 区」勾时**命中不到它** |
| 调整围栏半径 | 改变「谁站在这里算进来」，**买家侧立刻可感** |
| 重建社区池 | 只重算索引，不改商品本身；改过口径后**必须做一次** |

## 8. 数据模型

### 8.1 现有结构

```
sys_region (L1 省 › L2 市 › L3 区 › L4 街道 › L5 村居委会)
     ▲ region_code
cmt_community  聚落：kind = ESTATE | VILLAGE          ← 待加 BUILDING + parent_no
     ▲ ref_code (level=COMMUNITY)
mch_service_area  商家范围：level + ref_code           ← 待加 mode
     │ 投影
     ▼
prd_community_pool  商品 × 聚落                        ← GoodsServiceImpl 查它
```

### 8.2 变更清单

**每一处都要按「加列必须同时改的七处」走一遍**（见
[C端地址管理-交互方案 §6](../technical/design/C端地址管理-交互方案.md)）——
那份清单是加 `house_no` 时踩出来的，漏掉的两处都是「不报错」的那种。

| # | 变更 | 影响面 |
|---|---|---|
| 1 | `cmt_community.kind` 增加 `BUILDING` | 枚举登记表、三端词条、B 端选择器、运营端建档 |
| 2 | `cmt_community.parent_no`（可空；楼栋 → 小区/园区，**只做两层**） | 建档必填校验、归属链查询、运营端层级展示 |
| 3 | `mch_service_area.mode`（`INCLUDE` 默认 / `EXCLUDE`） | 投影算法、B 端选择器、运营端覆盖明细 |

**两处不加列、只改代码：**

| # | 变更 | 说明 |
|---|---|---|
| 4 | 匹配读 `fence_radius` 而非全局 `nearby-radius-m` | 数已在库（23 个全设了 1000 米），只是没人读 |
| 5 | 精确定位与模糊定位**分用途** | 模糊只用于「落到区」，不用于聚落匹配 |

> ⚠️ **第 3 项加完 `prd_community_pool` 必须全量重建**：存量池行是按「没有 EXCLUDE」
> 的口径写下来的，不重建的话排除一条也不生效，而 B 端会显示「已排除」——
> 说的和做的对不上，且没有任何报错。**这一步要写进上线步骤，不能指望有人记得。**

**为什么 `parent_no` 只做两层**：园区 › 楼 › 单元 › 户会没完没了，
而**单元和户不是服务单位** —— 没有商家按单元框范围，它们属于收货地址的门牌号。

### 8.3 运营端分析的数据口径（O10–O13）

三张视图共用一张事实表：**聚落 × 买家数 × 商家数**。

| 指标 | 口径 | 取自 |
|---|---|---|
| 聚落的买家数 | 生效位置解析到该聚落的用户数 | `active_address_id` → `usr_address` → 聚落 |
| 聚落的地址数 | 收货地址落在该聚落的条数（含非生效） | `usr_address` |
| 聚落的商家数 | 经营范围覆盖该聚落的主体数（**减 EXCLUDE**） | `mch_service_area` 展开 |
| 聚落的商品数 | 社区池行数 | `prd_community_pool` |
| 供需状态 | 买家>0 商家=0 → **缺供给**<br>买家=0 商家>0 → **缺需求**<br>皆 0 → 空聚落 | 组合判定 |

**必须同时给出「算不了的那部分」**，否则这三张视图会把缺数据说成缺需求：

- 没坐标的地址：解析不到任何聚落，既不算进任何一格，也**不该被静默丢掉**
- 没标点的门店：自送半径失效，但**不影响**经营范围口径的商家数
- 未开通的聚落：买家可能住在那儿（地址是自由填的），但它不在底图上

> **分母写错的分析，比没有分析更危险** —— 它会让运营去某个「没需求」的片区撤商家，
> 而那里只是没人标过坐标。

## 11. 决策记录

**D1 · 楼栋有归属（父子），不与小区平级**
早先的草稿写的是「扁平、不做父子」，理由是「商家框了小区算不算覆盖里面每栋楼」
没有普遍正确答案（物业按楼算、生鲜按小区算）。
**D2 的 include / exclude 补上了这个缺口**：默认覆盖，商家可点名、可排除。
有了这个出口，父子就是对的。归属声明在数据里，不靠围栏几何推断（§7.1.4）。

**D2 · 经营范围支持 EXCLUDE**
默认「框上级即覆盖下级」，配一个显式的排除口。矛盾**在输入端消除**而不是判定端 ——
后者要求用户记住「排除总赢」这条规则，而规则会被忘记。
EXCLUDE **不进审核队列**：缩小自己的范围不影响别人（§11 待确认 Q3 保留了反对意见）。

**D3 · 手动多选服务单位：评估后不做**
诉求是「同时选办公场地和家」。而这个例子恰恰说明它不该做 ——
**这两件事发生在不同时刻，不是同时**：中午在办公室时家附近的生鲜团购是噪音，
下班想让菜送到家时办公楼的便利店是噪音。首页混着两个地方的货，
用户每次都要自己心里过滤，而这个产品的立身之本是「**我邻居**在买什么」。

成本一侧：一张 `usr_active_area` 表、并集去重、购物车标记接多选、顶栏「主单位·等 N 个」、
上限替换交互、切位置清空提示、运营端要先有多选分布才能校准上限，
以及一整套「只影响看、不影响结算」的**八条规则**。
**最后一条才是要害：需要八条规则才能让一个功能不出错，说明它在跟系统其它部分较劲。**
佣金归属、团长、自提点都挂在单个 `communityNo` 上，挡住多选靠的是纪律不是结构 —— 纪律会松。

**替代方案拿到 90% 收益、成本接近零**：归属链上溯（D1，比多选更准，且用户无感）
+ 把切换做到几乎免费（定位变了主动问、顶栏常驻 chip）。

**D4 · 模糊定位不用于聚落匹配**
围栏 1000 米（小区）到 150 米（楼栋），模糊定位误差 5 公里。
用它匹配出来的是噪音不是结果。它只用于「落到区」再给候选。

**D5 · 先修分母，再谈分析**
O10 坐标健康度排在所有分布/缺口分析之前。分母写错的分析比没有分析更危险。

## 12. 待确认

1. **门店坐标要不要设成建店必填？** 现在 9 家有 7 家没标。设必填能一次性解决，
   但会挡住存量商家的其它编辑操作（与门牌号那次是同一类取舍）。
2. **`parent_no` 只做两层够不够？** 我按「单元和户不是服务单位」砍在两层。
   若将来真有「按单元做物业服务」的商家，这条要重议。
3. **EXCLUDE 要不要计入待审？** 我的判断是不用（缩小范围不影响别人）。
   但若运营担心商家用排除做变相拒单（比如排除某个老旧小区），它就该进审核队列 ——
   **这是业务判断，不是技术判断。**
4. **`BUILDING` 的默认围栏给多少？** 1000 米对写字楼太大，建议 **150 米**，
   并在运营端把默认值**按 `kind` 分档**。
5. **O11 的买家口径用「生效位置」还是「所有地址」？** 前者反映真实浏览，后者反映潜在需求。
   建议两个都给，**默认展示生效位置** —— 它才是「现在有多少人在这儿看货」。
6. **未开通聚落里的买家怎么算？** 他们的地址解析不到聚落。
   建议按街道（L4）兜底归集 —— 那一级一定有区划码。
7. **`TDD-按坐标算可见性` 要不要按 §2 的复查结论重写动机？**
   已在该文标注作废，但正文仍以「商家没有绑定」作为第二步的理由。
