## 7. 踩过的坑（别再踩一遍）

### 排序：迁移文件必须按版本号数字排，不是字典序

字典序把 `V15` 排在 `V2` 前面。`gen-test-schema.py` 因此在建表之前重放 V15 的 ALTER，
`tables.get()` 拿到 None 直接 return —— **不报错、不提示**，产出一份缺列的 schema。
已修，且把静默 return 改成报错退出。**任何遍历迁移文件的新脚本都要注意这条。**

### 解析 DDL 必须处理 `ALTER TABLE`

只看 `CREATE TABLE` 会得到**已被后续迁移修正过的旧结构**。
真实后果：`ord_sub_order.pickup_code` 在 V6 就改名成 `verify_code` 了，
而对齐报告一直说「契约的 verifyCode 与库列 pickup_code 命名不一致」—— 早就一致了。
反向更危险：漏看 `ADD COLUMN` 会把已有的列报成缺失，照着补一遍就是重复加列。

### JS 对象字面量的重复键会静默覆盖

`gen-model-align.mjs` 的映射表里踩过两次（`DERIVED.Merchant`、`DERIVED.GroupBuy`），
后写的静默胜出，前面那条登记凭空消失，报告随之多出几条假的「缺列」。
已加守卫，重复键当场抛错。

### 生成器漏跑一端不会报错，只会让文件保持旧样子

根 `gen:api` 曾经只跑 c-app 和 b-app，漏了 ops-web。
磁盘上那份平台端 spec 停在 151 个端点，实际契约已经 178 个，谁也没察觉。
已修，且有守卫检查 `gen:api` 必须覆盖三个 workspace。**新增一端时记得同步。**

### 别把「派生」当「缺失」

对齐清单把字段分五档：✅ 直接对上 / ≈ 命名不一致 / ↗ 来自关联表 / ƒ 派生不存 / ❌ 真缺。
`distance`（依赖当前用户位置）、`reached`（由 joined_count 与 min_count 算）这类**故意不存**，
落成列必然有过期的那一刻。判断依据写在 `gen-model-align.mjs` 的 `DERIVED` / `RELATION` 里，
**新增契约类型时要在那里登记**，否则会落进「未定性」并让测试失败（这是刻意的）。

## 8. 两处刻意保留的「不一致」

不要顺手"修"掉它们，两处都有原因，也都记在待办里：

1. **`cmt_pickup_point` 同时有 `service_fee_rate`（费率）与 `service_fee_per_item_minor`（按件）**
   —— R15 口径未定（按单/按件/保底），先都留着由结算侧按配置取其一。口径定了要删掉没用的那列（T-17）。

2. **契约里 `Order.verifyCode` 与 `Order.redeemCode` 指向同一个库列**
   —— `verify_code` 一列承载自提码/核销码/兑换码三态（V6 注释写明）。
   契约侧两个名字需要收敛成一个（T-16），但**不要**为此在库里再加一列。
