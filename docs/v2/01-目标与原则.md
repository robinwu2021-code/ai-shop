# 01 · 目标与原则

> 本层回答：**为什么这么做**。只有结论与依据，无实现细节。

## 1. 目标一句话

**一套数据库、一套接口、一套业务逻辑，同时服务零售 / 餐饮 / 服务业（及后续行业）。**
不是"一个系统分别适配三种商家"，而是"三个行业的需求合并成同一个模型，差异表达为数据与工作流"。

## 2. 公式

```
零售订单   = 基础订单流 + ∅
餐饮订单   = 基础订单流 + 餐饮工作流（台账轨）
服务业订单 = 基础订单流 + 服务业工作流（预约轨 + 工单轨）
未来行业   = 基础订单流 + 新写一条工作流（六件事声明模板）
```

## 3. 为什么敢：判定数据（可复算）

对现有 299 个端点逐条打行业关系码（有效分母 252）：

| 结论 | 数 |
|---|---|
| 三行业**完全相同** | **91.7%** |
| 结构差异 | **2.0%（5 条，100% 集中在下单/购物车）** |
| 行业自有面（含新增端点） | 16.6%–17.3% —— 行业包不是薄壳，排期按这个估 |

五段流程互相印证：售后与结算完全相同、履约只是取值域加一档、支付共用同一个 `markPaid`，
**只有"下单"是真差异** —— 恰好就是那 5 条。

## 4. 商品域五条根决策

| # | 决策 | 一行理由 |
|---|---|---|
| D1 | **Catalog / Offer 分离**：Product（是什么）与 Listing（怎么卖） | 改价沽清每天几十次、改商品几周一次 |
| D2 | **ProductType 是数据，行为是 Trait** | 新行业=配数据零发版；新行为=一个 Trait 三行业同时可用 |
| D3 | **Option 与 Modifier 严格分离** | 影响成本或库存身份才进 SKU；判错=笛卡尔积爆炸或库存失真 |
| D4 | **描述属性走 Schema，行为字段走强类型列** | 系统逻辑永远不读属性袋 |
| D5 | **前台陈列与后台类目分离** | 类目管资质一年不动；菜单分类一天三改 |

## 5. 订单域骨架零改动 + 七件落位

三层结构（主单=支付边界/子单=商家×履约/行=快照）、三张状态机、幂等且不关心钱从哪来的
`markPaid` —— **91.7% 相同的根源，一个不动**。行业化压来的七件事全部以加法落位：
收款流水上收 `ord_payment`、行内选配 `ord_item_modifier`、行类别 `line_kind`、
资产抵扣列、计量结算语义扩、收银台入基座、下单五步固定编排。

## 6. 工作流六条组合定律

L1 单向依赖（工→基只经 A1–A4，基→工只经 A5 事件）· L2 金额与状态真源在基础流 ·
L3 同步点全部幂等 · L4 多单各自独立走完基础流 · L5 工作流可整体缺席（`-Pcore-only` 闸）·
**L6 新工作流不得要求基础流加状态或加边**（检验问题：零售也需要这个状态吗？）

## 7. 三条合并判据（所有"上收基座"的裁决标准）

① 零售也要用 ② 换行业只换数据不换代码 ③ 被两个以上的域读 —— **同时成立才上收**。
已按此裁决：收款流水、原子占位、出品工位、选配项、可售时段、陈列分组、排班全链。

## 8. 反模式清单（明确不做的）

行业分支 `if(行业)` · 通用属性袋 / 复活 `attr_template` · `/v2` 平行命名空间 ·
跨行业工作流登记表（状态双真源）· Modifier 建成 Variant · 用库存表达沽清 ·
预约即下单（幽灵订单）· 台账存金额 · 事后劈账。
