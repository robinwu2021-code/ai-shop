> 2026-08-06 立。**本仓库所有技术方案文档的标准输出格式。**
> 参考实现：[数据库-ER图](./technical/reference/数据库-ER图.md)（结构类）· [积分域-完整方案](./technical/design/积分域-完整方案.md)（方案类）

## 一、渐进式：一份文档四层

读者进来时不知道自己要看多深。**把深度做成台阶，让他自己停在需要的那一层**——
而不是一上来就摊开全部细节，也不是只给概要让他去翻源码。

| 层 | 回答什么 | 篇幅 | 谁会停在这里 |
|---|---|---|---|
| **L1 定位** | 这是什么、为什么存在 | 一两句 | 路过的人 |
| **L2 结构** | 有哪些部分、怎么连 | 一张图 + 一张表 | 要建立心智模型的人 |
| **L3 详情** | 每个部分的字段/接口/规则 | 逐项展开 | 要动手实现的人 |
| **L4 边界** | 什么没定、为什么这么选 | 待决 + 取舍记录 | 要改设计的人 |

**每一层都要能独立读完**。L2 不能写成"详见 L3"，L3 不能假设读者读过 L1。

### 反面例子

- 一上来就是 20 张表的字段清单 —— 没有 L1/L2，读者不知道自己在看什么
- 只有"本模块负责积分" —— 只有 L1，等于没写
- 把待决事项散在正文里 —— 没有 L4，改设计的人要通读全文才知道哪些能动

## 二、图：一律生成 SVG，不用 mermaid

### 规则

| # | 规则 |
|---|---|
| 1 | 图存成 `.svg` 文件，放 `docs/**/diagrams/` |
| 2 | Markdown 用 `![说明](./diagrams/xxx.svg)` 引用 |
| 3 | 生成 HTML 时**内联** SVG（相对路径在别处会失效） |
| 4 | **结构图必须从真源生成**（schema / 契约），不手画 |
| 5 | 流程图、架构图可以手写 SVG —— 它们表达意图，没有可生成的真源 |

### 为什么不用 mermaid

| | mermaid | SVG |
|---|---|---|
| 渲染 | 要 VS Code 扩展 / GitHub / CDN | **到处都能看**：浏览器、编辑器、PPT、聊天窗口 |
| 离线 | 需要 CDN 或本地包 | 不需要 |
| 布局 | 自动，但**内容一多就糊** | 可控 |
| 语法错误 | **静默不渲染**，页面空白 | 不存在 |

mermaid 的致命点是第四条：写错一个字符整张图不显示，**而且不报错**。
本仓库为此丢过图——直到有人问"这里怎么是空的"。

### 每张图必须配文字说明

图旁边要有一段文字回答**图上看不出来的东西**：为什么这么连、哪条线最重要、
哪两个看起来像但不是一回事。**图给结构，文字给理由。**

## 三、结构类文档的标准骨架

数据库、API、状态机这类"有真源可生成"的文档，一律按这个骨架：

```
# XXX

> 生成方式 · 真源位置 · 勿手改

## 一、总览          ← L1 + L2
   一段定位
   ![总览图](./diagrams/xxx-overview.svg)
   一张汇总表（各部分及其规模）

## 二、分组          ← L2 展开
   每组一节：
     ![组内关系图](./diagrams/xxx-{组}.svg)
     跨组引用（一行文字）

## 三、逐项详情      ← L3
   每项一张卡片：字段 / 类型 / 约束 / 说明 / 关联

## 四、注意事项      ← L4
   容易看错的地方、刻意保留的不一致、待决
```

**图的层级要和文档层级对齐**：总览图一张（不超过 15 个节点），
分组图每组一张（不超过 12 个节点）。超了就再分一层，不要把图撑满。

## 四、方案类文档的标准骨架

设计方案这类"没有真源、要论证"的文档：

```
# XXX 方案

> 状态（待决策 / 已落地 V##）· 上游 · 优先级

## 一、一句话        ← L1
## 二、为什么是这个方案   ← 对比被否掉的选项，写清否掉的理由
## 三、结构          ← L2：图 + 表
## 四、详细设计      ← L3：数据/接口/算法
## 五、取舍记录      ← L4：冲突时让了谁、为什么
## 六、待确认        ← L4：什么没定、卡住谁
```

**第二节和第五节是这类文档的价值所在**。只写「我们选了 A」没有用，
要写「B 和 C 是什么、为什么否掉」——否则半年后有人会重新提 B，
而没人记得当初为什么不行。

---

## 五、每条设计要写「防住什么」

规则、约束、字段说明，都要能回答**不这么做会怎样**：

| 写法 | 评价 |
|---|---|
| 「积分在支付成功时发放」 | ❌ 只有结论 |
| 「积分在支付成功时发放，可用时点推到售后期后 —— 否则会被「下单拿分→立刻花掉→退款」白拿」 | ✅ 结论 + 防住什么 |

防不住任何东西的规则，多半是可以删掉的。

## 六、生成与校验

```bash
npm run gen:docs   # 全部重新生成（契约 / ER 图 / SVG / HTML）
npm test           # 其中 doc-standard 一组校验本规范
```

`packages/shared/tests/doc-standard.test.ts` 把本规范里**机器能判**的部分变成断言：

| 断言 | 对应本文哪一节 |
|---|---|
| 没有 ` ```mermaid ` 围栏 | §二 |
| md 引用的 `.svg` 必须存在 | §二 |
| 每张 SVG 都有 `<title>` 与 `<desc>` | §二「每张图必须配文字说明」 |
| 标了「勿手改」的文档确实有生成脚本 | §六 |

四层递进、每条设计写「防住什么」判不了，靠评审。

### 生成物不手改

带「由 xxx 生成，勿手改」抬头的文件改了也会被覆盖。要改内容去改真源（schema / 契约 / markdown）。

### HTML 是 Markdown 的投影

`docs/**/*.html` 由 `gen-doc-html.mjs` 从同名 `.md` 生成，**Markdown 是唯一真源**，
且 HTML **不入库**（见 .gitignore）—— 两份都提交的话，diff 里迟早出现
「改了 md 忘了重跑」的半成品状态，而 review 的人无从判断哪份是对的。
要看网页版，本地跑一次 `npm run gen:docs`。

SVG 相反，**要入库**：它是 md 的一部分，GitHub 上直接渲染，不重跑也能看。

## 七、这份规范自己的边界

- **不管命名、不管代码风格** —— 那些在 CLAUDE.md 与各 ADR 里
- **不强制篇幅** —— 四层结构是骨架，某层内容少就少写，但不能没有
- **图的美观不是目标** —— 能看清、不漂移、到处都能打开，就够了
