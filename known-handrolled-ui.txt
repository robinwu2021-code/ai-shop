# ── 2026-08-28 语义色收编：B 端 29 处已清零，C 端 14 处**先挂着** ──────────────
#
# 收编的是「只设一个 color，取 --sh-danger / success / warning」这类规则。
# B 端收编前 29 处各写一份，而且**同一个红用了六个名字**：
#   is-out / is-bad / is-loss / is-warn / row__bad / minus / led__out / tag--warn …
# 绿有 is-in / is-gain / is-ok / led__in，橙有 is-transit / opt__gate / group__note。
# 判据不认名字（认了永远追不上下一个新名字），只认「只改颜色 + 取语义 token」。
#
# C 端这 14 处**没有照搬**，因为有两个判断要先定，而 C 端界面这一轮没审：
#
#  ① 3 处会被父类权重压掉：`order`/`order-confirm` 的 `.amt__v--off` 撞 `.amt__v`、
#     `address` 的 `.op--danger` 撞 `.op` —— 那些父类自己设了 color，是 scoped 的
#     (0,2,0)，而库件 `.is-danger` 是全局 (0,1,0)，直接换会**静默变回原色**。
#     （`.inline` 撞 UnoCSS 那次就是这么断的，见 check-page-spec.py 的「撞工具类」。）
#
#  ② `review-write` 的 `.star.is-on` 与 `store` 的 `.fav.is-on` 用的是 `--sh-warning`，
#     但那是**星星/收藏的装饰色，不是告警状态**。收进语义件之后，
#     哪天把告警色调成另一种橙，星星会跟着变 —— 同一个 token，两种意图。
#     这一条得先定「装饰色要不要单独一档」，不该顺手一起收。
#
# ── 后续（同日）：①② 都定了，14 处收掉 8 处，剩 5 页 ──────────────────────
#
# **② 装饰色定了：加 token，不加类。** `--sh-star`（星标点亮色）与 `--sh-warning`
# 今天同值，但不是同一件事 —— 哪天把告警色调成另一种橙，星星不该跟着变。
# review-write 的星、store 的收藏都改指 `--sh-star`，判据自然就不再命中它们。
# 没有为这 2 处建库件：2 个调用点不值得，但值得给这个**意图**一个名字 ——
# 否则以后有人会「顺手」改成 `.is-warning`，把星星和告警色绑死。
#
# **① 权重那 5 处：库件客观上替代不了，不是「有件不用」。**
# 它们是 BEM 基类 + 修饰符（`.amt__v` 设 ink，`.amt__v--off` 覆盖成红），
# 或复合状态（`.status` 设 primary-text，`.status.is-WAIT_PAY` 覆盖成橙）——
# 基类本身设了 color，两者都是 scoped 的 (0,2,0)，而库件 `.is-danger` 是全局 (0,1,0)。
# 换过去会**静默变回基类的颜色**（`.inline` 撞 UnoCSS 那次就是这么断的）。
# 要收得先把基类的 color 也拿掉，而那是另一件事，得逐页看基类那个色是不是必需。
#
# points 的 `.rec__v.is-out` 是第六处，理由不同：它配对的 `.rec__v.is-in` 用的是
# `--sh-primary-text`，不在语义三色里 —— **只换红的等于把一对拆一半，比不换更糟**。
#
