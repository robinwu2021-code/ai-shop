## 一、一句话

**进销存成为一个不认识 ai-shop 的独立服务 `inventory`**：自己的父 POM、自己的包名 `ai.neargo.inventory`、自己的库、自己的进程与版本线，可以单独部署。它**可以依赖不含业务的基础包**（neargo 框架、任务契约、服务调用件，都以 Maven 包引入），但**不依赖 ai-shop 的业务代码与运行时**（商城主库、Redis、商城登录），不 import 任何 `ai.neargo.shop.*`。ai-shop 与 ShareHub、充电桩一样，只是它的**调用方之一**（系统码 `SHOP`），**也经 `inventory-client` 远程调用** —— 全部业态最终只有一种部署形态、一个实例、一个库（§四）。

在此之上采纳主方案的边界与能力（仓内管到交接为止、SN、出库池、服务凭证、幂等、拉取事件），并保留第一版的两处骨架：

1. **业态差异走配置（业态档案），不走代码分支**（§五）。
2. **契约分「通用内核 + 能力包」**（§六）。

代码**暂留 ai-shop 仓库 `backend/inventory/`**，但按「明天就能整目录搬走」的标准写：目录内自洽、只靠 Maven 包就能单独构建、仓库里的闸门证明它没有回头依赖 ai-shop 的业务代码。

## 二、支付服务做到了什么、进销存要多做什么

「参考支付服务」参考的是它的**切法**，不是它的**独立程度** —— 支付今天只做到了进程独立：

| 维度 | 支付服务今天（2026-10-29 实测） | 进销存目标 |
|---|---|---|
| 父 POM | `ai.neargo.shop:shop-parent` | **`ai.neargo:neargo-build-parent:2.0.0-SNAPSHOT`**，与 ai-shop 平级 |
| 依赖的构件 | `shop-base`、`shop-store-mybatis`、`shop-base-auth`（guard / portal）、`secret-*` | 只依赖**白名单里的基础包**（§3.3）+ Spring Boot、MyBatis-Plus、Flyway、MySQL 驱动；不依赖任何 `shop-*` |
| 包名 | `ai.neargo.shop.pay…` | `ai.neargo.inventory…` |
| 反向依赖 | 41 处业务 Port（`known-pay-reverse-deps.txt` 棘轮） | **零**；商城需要的事实由商城推给它（物料同步），不是它回头查商城 |
| 库 | 曾连主库 `ai_shop`（ADR-025 要求先分库） | 已有独立数据源与 `inv_flyway_history`，**照用** |
| 进程 | `ai-shop-pay.service` | `neargo-inventory.service`（不带 shop） |
| 多系统 | ADR-025 改造中：`system` 维度、每系统一把令牌 | **从第一天就有**：系统码 + 业主 + 凭证 |
| 形态 | A 内嵌 shop-app / B 独立，两种长期并存 | **终态只有独立一种**；内嵌只在商城切流期间作为过渡与回滚手段，全部业主切完后删除 |

照搬的切法：

| 支付服务 | 进销存 | 内容 |
|---|---|---|
| `pay-domain` | `inventory-domain` | 领域 + 持久化 + 迁移（「持久层只有一套」） |
| `pay-guard` | `inventory-guard` | 入口守卫：凭证 → `InventoryPrincipal(system, owner, actor)` |
| `pay-svc` | `inventory-svc` | 独立形态的启动类、控制器、健康检查 |
| `pay-portal` | 不要 | 进销存不对人开放；人的入口全在各宿主 |
| `pay-channel` | 不要 | — |
| （无） | `inventory-api` | DTO、错误码、事件信封、业态档案 schema、OpenAPI |
| （无） | `inventory-client` | 生成的客户端 + 幂等 / 重试封装 |

支付的另一条规矩照搬：**内嵌形态也必须按「没有共享事务」写**。商城下单与库存预留不在一个事务里，内嵌只省一跳网络，不改语义 —— 否则内嵌能跑、独立跑不通。

## 三、「独立」的定义与闸门

### 3.1 命名

| 项 | 取值 | 现名 |
|---|---|---|
| 目录 | `backend/inventory/` | `backend/shop-inventory/` |
| 坐标 | `ai.neargo.inventory:inventory-{api,domain,guard,svc,client}`，版本线 `1.0.0-SNAPSHOT` | `ai.neargo.shop:shop-inventory:0.1.0-SNAPSHOT` |
| 包 | `ai.neargo.inventory.{api,domain,guard,svc,client}` | `ai.neargo.shop.inventory` |
| 配置前缀 | `inventory.*` | `shop.inventory.*` |
| 进程 / systemd | `inventory-svc` / `neargo-inventory.service` | — |
| 库 | **沿用现进销存库**（已是独立数据源 + `inv_flyway_history`），只改连接配置与库名；ShareHub 等数据按系统码进同一个库 | 现进销存库 |
| 表 / 迁移历史 | `inv_*` / `inv_flyway_history` **不改** | 同 |
| 错误码 | `inventory.*` | 部分在 shop-base `ErrorCode` |
| 系统码 | `SHOP` · `SHAREHUB`（按 powerbank ADR-023 / 025 的平台代号，主方案写的 `POWERBANK` 改掉）· 充电桩待定 | — |

表名与迁移历史表不改：改了已上线的商城进销存库会被 Flyway 当成空库重跑。

`shop-inventory` 这个名字**留给 ai-shop 侧的适配模块**（见 §4.4）—— 它确实属于 shop，前缀名副其实。

### 3.2 闸门（每条都能失败）

| # | 闸门 | 怎么跑 | 防住什么 |
|---|---|---|---|
| I1 | **单独构建** | `mvn -f backend/inventory/pom.xml verify`，`~/.m2` 里删掉 `ai/neargo/shop` 后仍绿（白名单基础包从 Nexus 解析） | 传递依赖偷偷带进 shop 构件 |
| I2 | **import 白名单** | ArchUnit：`ai.neargo.inventory..` 只能依赖自身、`ai.neargo.common..`、`ai.neargo.job.api..`、`ai.neargo.svc.client..` 与第三方；**不得**依赖 `ai.neargo.shop..` | 「先 import 一个商城工具类」 |
| I3 | **Maven 依赖白名单** | `maven-enforcer` `bannedDependencies`：禁 `ai.neargo.shop:*`（`job-api`、`svc-client` 两个例外），`ai.neargo*` 下只放行 §3.3 白名单里「允许」的构件 | 同上，构建期拦；也拦住经传递依赖带进 Redis / Spring Security |
| I4 | **目录自洽** | 脚本检查 `backend/inventory/` 内任何文件不出现 `../` 指向目录外（POM `relativePath`、文档链接、脚本路径） | 整目录搬走时断链 |
| I5 | **空库启动** | `StandaloneContextTest`：只连库存库、无 Redis、无商城配置，迁移幂等 | 运行期依赖商城 |
| I6 | **过渡期两种装配同一组用例** | 核心用例基类以内嵌装配与独立装配各跑一遍（T8.6 后退役） | 「内嵌能跑、独立不通」 |

I1 ~ I4 挂进 `.githooks/pre-push`（纯读文件或增量构建，秒级）；I5、I6 进后端测试。

### 3.3 构建关系

- `backend/inventory/pom.xml` **以 `neargo-build-parent` 为父**；`backend/pom.xml` 在 `<modules>` 里**聚合**它（聚合 ≠ 继承，方便一条命令全量构建），但 ai-shop 的父 POM 不向它传任何属性与依赖管理。
- ai-shop 依赖它用**显式版本**（`inventory.version` 属性），不靠 reactor 隐式版本 —— 搬出仓库那天只是把版本从 SNAPSHOT 换成 Nexus 上的发布版。
- ai-shop enforcer 现在只放行 `ai.neargo:*:2.0.0-SNAPSHOT`；新坐标的 groupId 是 `ai.neargo.inventory`，不受此规则约束，**不用改**它。
- 基础包都按**显式版本**引入；搬出仓库后，它们要么已在 Nexus（neargo 框架），要么随 ai-shop 的共用服务一起发布到 Nexus（任务契约、服务调用件）。

**可以依赖的基础包**（判据：不含任何业务语义，且不把 ai-shop 的运行时带进来）：

| 构件 | 包名 | 用来替换 | 结论 |
|---|---|---|---|
| `ai.neargo:neargo-common-core` | `ai.neargo.common.core` | `BizException`（23）、`ErrorCode`（22）的承载；`Result` / `PageResult`；`IdGenerator` 替换 `BizKey` | **允许**。ai-shop 的 `shop-base` 今天已经依赖它；进销存自己的错误码键（`inventory.*`，三语）放 `inventory-api`，框架 `ErrorCode` 只表达 HTTP 级别 |
| `ai.neargo:neargo-common-data` | `ai.neargo.common.data` | MyBatis-Plus 装配、实体基类、审计填充 | **允许**，但**不启用**它的数据范围引擎与租户行拦截器 —— 业主隔离由进销存在 SQL 里显式传参（同支付「显式传参比拦截器安全」） |
| `ai.neargo.shop:job-api`（包 `ai.neargo.job`，零依赖） | `ai.neargo.job.api` | `JobSupport`（3）—— 进销存的定时任务（Outbox 投递、快照、冻结超时）注册到共用任务服务，作为它的一个 worker 目标 | **允许**。groupId 带 shop 是历史原因，契约本身零依赖；搬出仓库前随任务服务改坐标 |
| `ai.neargo.shop:svc-client`（只依赖 spring-web） | `ai.neargo.svc.client` | `InternalHttp`（4）—— `inventory-client` 的传输层 | **允许**，理由同上 |
| `ai.neargo:neargo-common-web` | `ai.neargo.common.web` | 全局异常处理 | 可选，`inventory-svc` 用；不在 `inventory-domain` 里用 |
| `ai.neargo:neargo-common-security` / `neargo-auth-core` | — | — | **不用**：它们是「人」的会话与 RBAC，进销存只认系统凭证 |
| `ai.neargo.shop:shop-base` | `ai.neargo.shop.*` | — | **不允许**：含 22 个业务域的 `spi` 契约与商城错误码，依赖它等于依赖商城的词汇表 |
| `shop-store-mybatis` / `shop-base-auth` | — | — | **不允许**：传递带入 Redis、Spring Security、`shop-auth-store`，正是「独立启动要商城运行时」的根源 |

注意 neargo 框架按 powerbank ADR-025 处于冻结（不做 2.x 重排），但 `2.0.0-SNAPSHOT` 已在 Nexus、ai-shop 在用；进销存只用其中已稳定的类，不等框架解冻。

## 四、部署形态：一个实例、一个库，商城切流期间有过渡

### 4.1 终态

| 项 | 取值 |
|---|---|
| 进程 | 一个 `inventory-svc`（`neargo-inventory.service`），可多实例无状态横向扩 |
| 库 | 一个：**现商城进销存库**原地升级为服务库（迁移接 V15 之后），商城存量数据不用搬；ShareHub、充电桩的数据按 `system_code + owner_id` 进同一个库 |
| 调用方 | ai-shop（`SHOP`，含商城与餐饮）· ShareHub（`SHAREHUB`）· 充电桩 · 将来 —— **全部经 `/api/inventory/v1` + 每系统一把凭证** |
| 网络 | 同机内网（各系统与 ai-shop 在同一台腾讯云机器，ADR-025）；`/api/inventory/v1` 与 `/actuator` 都不经 nginx 对外。服务**自己验凭证**、强制以凭证里的系统与业主覆盖请求参数 —— 同机多系统时，内网不等于可信 |
| 定时任务 | 注册到共用任务服务（`ai-shop-job`，已按 ADR-025 多系统化）作为一个 worker 目标；任务服务不可用时 Outbox 只延迟投递、不丢 |

第一版 G8 写的「经 nginx 暴露」作废。

### 4.2 过渡：商城切流期间的内嵌形态

商城今天在生产上进程内调用进销存，不能一刀切。过渡期借用支付的双形态做法：

| 项 | 内嵌（过渡） | 独立（终态） |
|---|---|---|
| 谁用 | 尚未切流的商城业主 | 已切流的商城业主 + 所有外部系统 |
| 进程 | `shop-app` 依赖 `inventory-domain` 构件 | `inventory-svc` |
| 身份 | 适配层把 `BizContext` 翻译为 `InventoryPrincipal(system=SHOP)` | 凭证 |
| 库 | **同一个库** | 同左 |

**每个业主只有一个写入方**（`inv_owner.write_authority = EMBEDDED / SVC`），按业主灰度翻转；翻回去就是回滚。全部业主切完、观察期过后，删除内嵌装配与 `write_authority = EMBEDDED` 分支（T8.6）。

过渡期内**同一组核心用例以两种装配各跑一遍**（AC-20）；删除内嵌后这条用例随之退役。

### 4.3 商城切流：下单预留跨进程

[TDD-进销存模块化与独立部署](../../docs/technical/design/TDD-进销存模块化与独立部署.md) §2.2「扣减永远不跨进程」的依据是 `OrderServiceImpl` 里 `stockPort.confirm(orderNo)` 与订单转态、结算计提同在一个事务。[TDD-进销存领域模型](../../docs/technical/design/TDD-进销存领域模型.md) §二 已更正：**在预留协议下跨进程仍是同步强一致**，`available ≥ 0` 只需在进销存自己的库里成立。本计划按后者落地，并**修订**前者 §2.2（写进 ADR-046）。

| 步骤 | 做法 | 失败时 |
|---|---|---|
| 下单前 | `POST /reservations`（幂等键 = 订单号，全成全败，`expires_at` ≥ 支付窗口 + 余量） | 拒单（熔断后**拒单而不是放行**） |
| 订单事务 | 订单落库 + 同事务写 Outbox「待确认 / 待释放」，**不在事务里调远程** | 事务回滚 → 预留靠 `expires_at` 自动回收 |
| 支付成功 | Outbox 投递 `POST /reservations/{ref}/commit`，幂等，可重试 | 预留已过期 → 尝试重新预留；仍失败告警进人工（发货前拦截） |
| 关单 / 退款 | Outbox 投递 `release` / 退款回补 | 重试直到成功 |
| 餐饮生产扣料 | 同样经 Outbox 投递，`PRODUCTION` 能力包 | 重试 |

要付的代价如实写：进销存不可用 = 商城不能下单（今天进程内挂了也一样）；下单多一次同机 RTT（1 ~ 3 ms）；`expires_at` 回收任务成为必需品。

### 4.4 ai-shop 侧留下什么

进销存搬走后，ai-shop 里与库存有关的代码全部是**调用方代码**，收在 `shop-inventory`（适配模块，保留 shop 前缀）与 `shop-app/invbridge`：

| 原位置 | 去向 |
|---|---|
| `api/biz`（6）、`api/ops`（2）、`api/open`（1）、`api/internal`（3）控制器 | 留在 `shop-inventory`，作为商城自己的 BFF：判权、数据域在这里做完；过渡期调 `inventory-domain`，切流后调 `inventory-client` |
| `port/` 4 个 Port 实现、`InventoryReportFactsPortAdapter` | 留在 `shop-inventory`；实现 shop-base 的 `spi.inventory.*` / `spi.report.*`，内部调进销存 |
| `portal/internal/InternalMaterialCatalogController` | 移到 `shop-app` |
| shop-base 的 `spi.inventory.*`（18 文件）、shop-core 的引用（9 文件） | 接口**不动**，它们是商城自己的端口；但 `confirm` 从「订单事务内调用」改为「订单事务写 Outbox、事务外投递」（§4.3），这是 ai-shop 侧唯一的语义改动 |
| `shop-app/invbridge`（32 文件） | 切流后改调 `inventory-client` |
| `MaterialCatalogQueryPort`（进销存回头向商城要物料资料） | **反转**：商城在商品变更时调用 `PUT /items` 把物料推给进销存；进销存不再回查 |

于是方向只有一条：`ai-shop → inventory`。

## 五、业态档案（Business Profile）

（与第一版相同，只把系统码改为 `SHAREHUB`。）

业态之间真正不同的只有下面几类规则。做成**业主级、带版本的配置**，内核按档案求值；内核里不出现任何业态名。

| 档案项 | 作用 | 修改约束 |
|---|---|---|
| `capabilities` | 开通的能力包：`SERIAL` / `DISPATCH_POOL` / `RESERVATION` / `PRODUCTION` | 关闭时须无进行中的对象 |
| `targetTypes[]` | 外部目标类型、名称键、`parentType`（如 `SITE → MERCHANT`） | 删除须无引用 |
| `inboundPurposes[]` | 启用的入库用途；每个用途是否要依据 / 附件 | 有草稿时不可停 |
| `outboundPurposes[]` | 启用的出库用途；每个用途的**目标规则**（必填类型、可选类型、层级约束）与 `handover = POOL / NONE` | 同上 |
| `gateRefTypes[]` | 放行凭证类型（`QC`、`ACCEPTANCE`…）；物料 `gatePolicy = REF_REQUIRED` 时指定其一 | — |
| `countReview` | 盘点是否强制复核、复核人 ≠ 录入人 | — |

档案以 `inv_business_profile(owner_id, version, body JSON)` 存，单据过账时记下所用 `profile_version`。档案由**平台管理员**经运维接口修改，宿主只读。

### 5.1 四个业态

| 档案项 | 商城（电商） | 餐饮 | ShareHub（充电宝） | 充电桩（预案） |
|---|---|---|---|---|
| 系统码 | `SHOP` | `SHOP` | `SHAREHUB` | 待定 |
| 业主 | 商家主体 | 商家主体 | 运营方（ADR-026 唯一运营方 → 一个业主） | 运营方 |
| 能力包 | `RESERVATION` | `RESERVATION`、`PRODUCTION` | `SERIAL`、`DISPATCH_POOL` | `SERIAL`、`DISPATCH_POOL` |
| 物料 | SKU 按数量 | 原料按数量 | 柜、宝**都按 `SERIAL`** | 桩主机 / 模块 `SERIAL`；枪线、耗材 `QUANTITY` |
| 放行凭证 | 无 | 无 | `QC` | `ACCEPTANCE` |
| 目标类型 | 无（销售走预留） | 无 | `MERCHANT`、`SITE → MERCHANT`、`PERSON` | `PROJECT`、`STATION → PROJECT`、`PERSON` |
| `ISSUE` 规则 | 不启用 | 不启用 | 必填 `MERCHANT` + `PERSON`，可选 `SITE`；`POOL` | 必填 `STATION` + `PERSON`；`POOL` |
| 其它出库 | `SALE`（仅预留确认）、`TRANSFER_OUT`… | `PRODUCTION` | `SCRAP`、`RETURN_SUPPLIER` | **`CONSUME` 维修领用**：必填 `PERSON`、可选工单引用；`NONE` |
| 不良品 | — | — | 复检不过不入库（归业务） | 同仓单独的不良品库位 |
| 成套 | — | — | **柜 SN ⊃ 宝 SN**（组装关系，§5.2） | 桩 + 枪线 / 模块（成套行） |

### 5.2 充电宝按 SN 的配套（裁决 D3）

一柜 8 ~ 48 块宝，全按 SN 后出入库与盘点的扫码量翻几十倍；不配套就是把成本转嫁给仓管。四件事一起做，**从 M7 提前到 M3 / M4 / M5，作为 ShareHub 交付的 P0**：

| 配套 | 做法 | 防住什么 |
|---|---|---|
| **组装关系** | `inv_serial.parent_serial_id`：宝挂在柜下；入库时随柜登记（宿主质检单里本来就有柜内宝清单），在仓期间可拆装（`POST /serials/{sn}/assemble`、`/disassemble`，写流水不改余额） | 出库只扫柜码却要逐块录宝 |
| **扫柜码带出宝** | 单据行与盘点扫码接受柜 SN，服务展开为「柜 + 当前挂着的宝」；展开结果写进 `inv_document_serial`，单据上逐块可查 | 同上；且展开在服务里做，宿主不用各自实现 |
| **成套随动** | 出库池记录以柜为单位，宝作为从属记录随柜调整 / 撤回 / 签收 / 退货；单独动从属记录 409 | 只撤柜留下孤儿宝 |
| **批量上限** | 单命令上限按**展开后**计 ≤ 2 000 SN；草稿可分批追加行（`PATCH`），过账一次完成 | 5 柜 × 48 宝就超出主方案的 200 上限 |

签收后不再跟踪：宝在商家处换柜、丢失，库存服务不知道也不该知道；退货回仓时按实收重新登记组装关系（新周期）。

充电桩的「桩 + 枪线 / 模块」若也按 SN 管，直接复用这套；按数量管则用成套行（`parent_line_no`）。

### 5.3 新业态接入判据

| 新业态需要的 | 怎么做 | 要不要 ADR |
|---|---|---|
| 新的单据用途、目标类型、放行类型、层级约束 | 改档案 | 否 |
| 只展示、不参与规则的物料属性 | 物料 `attributes` JSON | 否 |
| 新的状态机（寄售、租赁到期回收…） | 新能力包 | **是** |
| 库存跟踪出库后的位置 | 不做，归宿主 | 推翻需 ADR |
