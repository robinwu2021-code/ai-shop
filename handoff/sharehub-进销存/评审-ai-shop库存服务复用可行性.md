# 评审：ai-shop 库存服务能否作为本项目设备库存的微服务

> 2026-10-28 · 审查对象 `ai-shop/backend/shop-inventory`（103 个 Java 文件、15 个迁移）· 对照本项目 `sharehub-svc-core` 的 `inv` 模块与设备生命周期设计。

## 结论

**不建议用它承载设备库存。** 它是一套成熟的**数量型进销存**（SKU × 库位 → 数量），而本项目的设备库存是**逐台资产管理**（每台柜 / 宝有 SN、状态机、质检、出库池归属）。核心模型对不上，硬套等于在它上面重写一遍逐台追踪，并把现在单事务成立的不变量拆成跨服务的最终一致。

它适合将来管**配件与耗材**（线材、贴纸、包装、备件），那正是数量型库存的本行。前提是 ai-shop 先完成独立部署（它自己的任务 CORE-01D 尚未完成，见下文）。

## 一、它是什么

| 方面 | 现状 | 证据 |
|---|---|---|
| 模型 | 物料（SKU）× 库位 → 在手 / 预留数量；只追加的流水；批次 / 保质期 | `InvItem`、`InvStockBalance`、`InvLedger` |
| 单据 | 入库、出库、调拨（一出一入，中途 TRANSIT，带承运商 / 运单号）、盘点（快照 + 操作）、退货收货 | `InvInboundOrder`、`InvTransferOrder`、`InvStockCount*` |
| 明细粒度 | 只有 `itemId + 数量 + 批次`，**没有序列号** | `InvOutboundLine`、`InvStockCountLine` |
| 库位 | `STORE / WAREHOUSE / TRANSIT / VIRTUAL` | `V1__inventory_baseline.sql:71` |
| 归属 | `InvOwner`（库存归谁），按 `ownerId` 隔离，不用平台数据权限 | `InvOwner`、`InventoryDataSourceConfig` |
| 其它 | 预留 / 履约、估值与成本、每日快照、safety stock、Outbox、开放 API（`/open/v1/items`、`stock-ledger`、`stock:sync`） | `ReservationService`、`InventoryValuationService`、`OpenInventoryController` |
| 部署 | **嵌入在 shop-app 单体里**，`shop.inventory.enabled` 开关；独立数据源 + 独立 Flyway 历史表，为独立交付做了准备，但**没有独立启动模块、内部 HTTP 合同与客户端** | 唯一依赖方 `shop-app/pom.xml`；ai-shop 文档 `TDD-餐饮系统-独立支付库存合同核验.md` §1.2、§3 CORE-01D |
| 耦合 | 依赖 ai-shop 的 `shop-base`（BizException / ErrorCode）、`shop-base-auth`（BizContext、BizPerms）、outbox、job、`svc` InternalHttp | import 统计 |

## 二、逐项对照本项目的设备库存需求

| 本项目需求 | ai-shop 库存 | 匹配度 |
|---|---|---|
| **逐台追踪**：每台柜 / 宝有 SN，库存里能看到「哪一台」在哪 | 只有数量 + 批次 | ❌ 核心不符。用「批次号 = SN、数量 = 1」硬套会失去 SN 唯一约束，流水和余额都按台膨胀 |
| **设备状态机联动**：在仓 / 在途 / 出库池 / 已绑定 / 已上线由 `dev_cabinet` 的状态与 `warehouse_no`、`issued_agent_no`、`location_no` 派生 | 库存只知道数量在哪个库位 | ❌ 库存状态必须与设备状态在同一事务里改 |
| **不变量 I1 / I4**：在仓与在出库池互斥；每批一个事务 | 跨服务后只能靠 Outbox / Saga 最终一致 | ❌ 一致性降级，且出库、绑定、撤机每条链路都要补偿逻辑 |
| **调拨逐件签收**：收货逐台勾，缺件当场生成资产差异 | 调拨按数量收 | ❌ 需新增逐件明细 |
| **入库质检**：按台记质检，PENDING / FAILED 不能发货、不能上线 | 无 | ❌ |
| **出库池（商家归属、未部署）** | `InvOwner` 可表达「归谁」，但设备绑定上线后就离开库存域 | ⚠️ 概念相近，语义不同 |
| **仓库、区域** | `WAREHOUSE` 库位 | ✅ |
| **盘点** | 有，快照 + 操作，很完整 | ⚠️ 按数量盘；设备要按 SN 盘 |
| **调拨物流信息**（承运商、运单号） | 有 | ✅ 本项目没有，值得借鉴 |
| **估值、成本、预留、安全库存、开放同步** | 有 | — 设备是固定资产、不销售，基本用不上 |
| **租户与权限**：`tenant_id` + 平台数据权限（DataScope） | `ownerId` | ⚠️ 要做映射 |
| **技术栈** | Spring Boot + MyBatis-Plus，与本项目同源 | ✅ 迁移成本低，但父 POM、基础库不同 |

## 三、真要用它，需要做什么

1. **先让它能独立运行**（ai-shop 侧，CORE-01D）：独立启动模块、内部 HTTP 合同、客户端、鉴权。目前 ai-shop 自己的独立库存验收都还是阻塞状态。
2. **补逐台追踪**：新增序列号表、逐件出入库与调拨签收、按 SN 盘点、逐台质检。这是库存核心模型的扩展，要改到余额与流水的过账逻辑。
3. **本项目侧**：把出库、退回、绑定、撤机、调拨改成远程调用 + Outbox 补偿；重做 I1 / I4 的保证。
4. **两仓同步维护**：一份库存代码同时服务零售与设备两种模型，双方的需求会互相牵制。

工作量相当于重写设备库存，还多了跨服务一致性和跨仓库维护两份长期成本。

## 四、建议

1. **设备库存继续用本项目自己的 `inv` 模块。** 它已经是逐台的（`inv_transfer_item` 按柜号 / 宝号逐件、`inv_asset_diff`、`dev_cabinet.warehouse_no`），与设备状态机同库同事务。仓库后端按既定口径暂缓，恢复时在这个模块上做。
2. **借鉴 ai-shop 的四个设计**（不引入代码）：
   - 只追加的库存流水（本项目现在只有结存 `inv_stock`，没有流水，事后还原不了某台何时进出哪个仓）；
   - 调拨单的承运商、运单号、发货 / 收货时间；
   - 盘点「快照 + 逐次操作」，盘点期间冻结过账的互斥点（`InventoryMutationGuard`）；
   - Outbox 统一投递（库存事件对外通知）。
3. **配件与耗材**（若将来要管）：等 ai-shop 完成独立部署后，作为外部服务接入它，只管数量型物料，不碰设备。
