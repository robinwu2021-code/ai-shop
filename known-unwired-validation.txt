# 已知「DTO 上有校验注解、方法参数却没有 @Valid」的欠账 —— 那些注解一次都没跑过。
# 判据与说明在 packages/shared/tests/bean-validation-wired.test.ts。
#
# 键是「文件路径 类型名」，**不带行号** —— 行号会随无关改动漂移，
# 而漂移会让清单在每次别人动这个文件时莫名其妙地红一次。
#
# ★ 为什么先挂清单而不是一次改完：接上 @Valid 会改变 **22 个线上端点的报错行为** ——
# 现在传空串是走到下游才失败（或根本没失败），接上之后当场 400。
# 这不是纯内部重构，得逐个看清调用方现在到底传什么。**先立闸门止血，再逐条清。**
#
# ★ 好消息是风险比预想小：这 22 处的约束**清一色是 @NotBlank，没有一个 @Pattern**。
# 也就是说接上之后只会拒空值，不会因为格式变严把存量数据挡在外面。
# 特别是 MpUserController 的 LoginReq / OtpReq（登录与发码链路）——
# 它们只有 @NotBlank，所以「收紧手机号格式会不会把老用户锁在门外」那个问题
# 在这里**还没被触发**：格式判据（Phones.CN_MOBILE）目前只加在写入口，没加在登录链路。
#
# 清一条就删一条。**只许变短。**
#
# ── 2026-08-29：ops 那 7 条已接（22 → 15）────────────────────────────────
# 先清运营端是因为**调用方就是我们自己**（ops-web），而且它至今没上线
# （见 ops-web-never-deployed）—— 接上 @Valid 之后传空串会当场 400，
# 而唯一会传空串的调用方是我们的前端，改起来在同一个仓库里。
# 七条的约束**清一色是 @NotBlank**，逐个核过：登录/找回/重置密码的用户名口令、
# 通道试发的 channel/target、站内信试发的收件人与标题、推送任务的名称与文案。
# 没有一个是 @Pattern，所以不存在「格式变严把存量挡在外面」的风险。
#
# 剩下的 15 条（biz 2 / mp 13）调用方是已发出去的 App，**改报错行为要先确认
# 那些端上此刻传的是什么** —— 尤其 MpUserController 的 LoginReq / OtpReq，
# 那是登录链路。
