## 2. Identity, unit and binding invariants

1. The supported lane is owner-resolved `STORE_ORDER + MANUAL_OFFLINE + SERVICE_EXECUTION + STORE_VERIFY + COUNT`, MAIN/CNY, one actual scoped USER or GUEST. Core verifies operation, parent, child, declaration, original line/item and original stock evidence. Requested source kind/admission mode is never authority. Funded orders are unsupported here; assets retain the distinct C11 owner path.
2. A source line's `Q` is the persisted `OrdCheckoutLine.quantity`, equal to the actual `OrdItem.qty` and accepted manual line quantity, with `1 <= Q <= 999`. Task and binding use `BigDecimal.compareTo(ONE)==0`; `intValueExact` only follows validation. `1.000000` is one; `0.5`, `1.5`, `2`, unsupported uom or mismatched old snapshots fail `UNSUPPORTED_TASK_QUANTITY`. Do not round, split existing tasks, migrate balances or infer done from duration.
3. One permanent unit identity is `(MAIN, sourceLineNo, unitOrdinal)` with ordinal 1..Q. It permanently binds `(caller=BEAUTY, entity, store, workOrderNo, taskNo, bindingNo, bindingRevision)`. It survives RELEASED, VOIDED, cancellation, soft deletion, cache eviction and new request keys. Another task, recreated work order, new binding or different source line cannot claim it. A task has at most one permanent unit across its lifetime in this lane; Core uniqueness does not include request key or binding revision.
4. Beauty assigns the lowest unused ordinal under the canonical source allocation guard, consulting **all existing execution fence rows including terminal rows**, and commits it with START intent before Core IO. This is a proposed identity, not quantity authority. Core verifies the committed beauty proof and independently serializes/validates that ordinal under its real source-line root. No client chooses ordinal. Rows are append-only in identity; no deletion/recycling path exists.
5. Under Core parent/child roots, `activeReserved + performed + voided <= Q`. Count unit rows once: RESERVED includes PREPARED, SUSPEND_REQUESTED, STARTED, STARTED_SUSPENDED and RELEASING; PERFORMED includes acknowledged fulfillment; VOIDED is a disjoint M6 terminal category. A released row returns to BOUND **for its original task only**. Binding count and capacity count are separate. No extra reservation is created for handover, step change or another participant.
6. The original binding is immutable; task revision at initial freeze, work-order/scope revision, source epoch/revision/hash, declaration revision, definition/execution snapshot hash and exact frozen plan hash are retained. Later legitimate step revisions and participant segments have separate versions; they do not replace initial binding or allocate another quantity.
7. Same original action key + same complete action hash returns its original operation/result. Same key + changed field conflicts. Different key + same live task returns conflict with the scoped original execution reference, not another unit. M3 has attempt 1 only. A later explicitly authorized same-task/unit attempt requires sealed original no-effect proof, terminal old attempt, current actor checks and CAS of `attemptNo+1`; M4/M5 must implement that exact transition before exposing retries. Terminal replay never rearms an old attempt. A new task or binding is not this exception.

No backfill guesses: V544/V10 add empty authority tables, without changing old task/binding data. Existing legitimate qty=1 manual bindings may be lazily adopted on their first current-authorized freeze only after all scoped parent/source/plan facts validate. Historical done/void/start quantities, missing context/definition/arrangement, deleted parent or ambiguous bindings are ineligible and stay visible for coordination.

## 4. Source freeze, owner preparation and durable observation

**Beauty freeze / `ServiceTaskExecutionServiceImpl.prepareTask`:**

1. Outside local TX require authenticated current merchant/store scope, SERVICE_TASK_SELF and Task62 LINKED person/assignment/link fact. Match current person against the task's frozen assignment; an OWNER without an effective person has no SELF start. A current linked account is not the customer and cannot change USER/GUEST buyer history. Read immutable task/definition/arrangement and current source projection. UNASSIGNED/direct/ADD tasks without a concrete plan return RESOURCE_PLAN_REQUIRED; there is no empty-plan grant.
2. Repeat live auth/person after slow preflight and immediately before the short transaction. Lock canonical manual observation → sorted source guards → work order → sorted tasks → execution fence → START submission. Verify current root scope not frozen, task PENDING/done=void=0/no startedAt, exact single binding qty1/manual party and source hash/revision, complete original appointment/group lineage and hashes. Determine unit ordinal; create permanent fence and original execution/action/resource command numbers server-side. Persist `START_MANUAL_V1` frozen JSON in existing `bty_service_submission`, action START, status EXECUTION_PENDING, and fence intent state FROZEN. Commit before any Core call.
3. Invoke Core prepare outside TX with complete original binding/action digest. On reply, repeat current auth before a human-facing final local mutation. Apply only to the same fence/submission/hash and claimed execution observation epoch. Save owner grantNo/revision/state as evidence. Do not change task status/startedAt/participation/steps/doneQty. A lost response or revoked actor leaves pending original state; a query-only recovery may copy already-committed owner evidence without a new human start.

**Core prepare / `ServiceExecutionServiceImpl.prepare`:**

1. `DelegatedIdentityContext.outside()`/no current transaction; validate binding shape and exact SELF purpose. Read original beauty intent with matching scope/task/source/unit/plan/person namespace, and current `PersonnelOperatorFactsPort.current` for the initiating actor. Inspect original stock using the admission's **frozen original** StockDispositionPort manifest/authority/confirmation operation, not today's provider or a new reservation. The server resolves source kind from the persisted checkout operation/parent/child/declaration. No CheckoutPort.source/ManualServiceAdmissionPort.source call on a technician's behalf.
2. The stock snapshot must prove APPLIED and supported full ALLOCATED/CONSUMED with zero released quantity, exact manifest/confirmation and owner revisions. Missing/delayed/inconsistent stock is UNKNOWN and cannot create PREPARED. Recheck current auth after IO. Start a fresh primary RC transaction; lock in §5 order; reread all Core facts, expected declaration/source/item revisions and conflict counts. Validate against the original manual source observation without changing its serialized bytes. No remote/session/resource/stock call while locks are held.
3. Replay lookup comes before new acceptance but **after current caller authorization**. Validate original key/hash/complete binding; a replay reads original PREPARED or pending state instead of re-running an old command as new. For first prepare, compare the source operation's persisted manual revision/hash to the beauty freeze and recompute the exact existing hash inputs through the shared owner-internal snapshot reader. Preserve `MANUAL_SOURCE_V1`, counter wrapping, ordering, null representation and old observation update semantics. Reject altered order/item/mapping/declaration or an already suspended/unknown source.
4. Under the locked line, insert/check permanent task/unit ownership; count disjoint unit buckets; insert attempt PREPARED and immutable PREPARE action result, CAS unit BOUND→RESERVED with currentExecutionNo and generation. All affected counts are exactly one; duplicate key is resolved by rereading the original row and exact comparison, never INSERT IGNORE or success-on-zero. Grant persistence itself does not update checkout parent/child/item/mapping/observation versions. This avoids self-invalidating the accepted source hash.
5. Return the minimal grant. `PREPARED` authorizes quantity reservation only. It is not resource success and cannot make public canStart true.

**Observation epochs:** every cross-owner observation first CAS-increments a grant/fence `observation_epoch` in a short local transaction, marks pending outcome without dropping the prior definitive receipt, then performs IO. Application requires original execution/action/payload hash + expected row version + exact claimed epoch. A lower epoch reply is ignored even when successful; re-query original for current truth. A higher grant revision with same binding may advance monotonically; changed binding/digest or regressions are conflicts. Source observation retains its existing independent manual epoch; do not conflate these two counters. Local polling lease controls who may copy a result, not whether a unit/resource can be released. The actual producer and Core consumer of source suspension are fixed below. A transient UNKNOWN observation retains pending state and is not a durable suspension or no-effect decision.
