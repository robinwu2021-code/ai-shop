## 1. Decisions and scope

Finish the ordinary beauty core in this order: common order/manual admission → real source binding and guest order → serialized start → actual capacity → task work/participation → managed fulfillment/closure → BM06 task/resource calendar. First collect, then serve. Cash or an actually observed offline transfer is recorded by an authorized cashier as a merchant declaration, never a bank-verified fact. No credit/post-pay/free-price exception, Pay calls, refund automation, card balance/count consumption, or duplicate beauty order/money ledger.
Root provisionally accepted during this design: (R1) dedicated Core manual transition may reuse `PAID`, with immutable manual provenance and explicit downstream exclusions; (R2) typed shared USER/GUEST identity with conditional nullable account fields, delivered in the second bounded slice; (R3) first identified-user slice may retain actual C purchase confirmation but cannot require Pay configuration or routing. These are technical root rulings for independent review, not a new user question or coding authorization.
Alternatives: existing `OfflineReceiptPort` creates a Pay receipt and violates the phase; opening old `confirmOfflinePay`/receiptless `markPaid` weakens global safety; beauty-owned unpaid exceptions duplicate order authority. Adopt a dedicated shared Core manual lane using the same SKU/catalog/price calculation, order/item/source identities and a tightly checked manual transition. A generic order-party table would avoid direct guest columns but adds joins and a broad owner abstraction; adopt discriminated USER/GUEST columns on the existing owner aggregates instead. Requiring every walk-in to claim a C account would avoid DDL but does not deliver actual guest service.
P1: MAIN/CNY, one store/customer, ordinary SERVICE/STORE_VERIFY/COUNT, frozen single SERVICE step; public repetitions expand into qty=1 tasks. First slice accepts positive-price plain services without coupons, activities, points, gifts, group/period/card/therapy products. Existing common pricing is reused; merchant-only discounts may be added in a later explicitly tested sub-slice, never free-amount input. P4 stages/parallelism/assets/therapy remain deferred. A core completion claim requires the guest slice and entire service/calendar sequence, not just the first slice.
