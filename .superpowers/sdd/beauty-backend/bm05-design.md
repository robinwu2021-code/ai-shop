## 1. Scope and architecture decisions

Preserve the sequence: real start authority (including current operator/personnel prerequisite) → reserved-unit handoff → open/end/cleanup → overdue/active changes → task workflow/participation/quantity → Core fulfillment and work-order closure. Each slice includes its own recovery, audit and outbox.
P1 remains one store/customer, prepaid ordinary SERVICE/STORE_VERIFY/COUNT, MAIN/CNY, frozen single SERVICE step. No therapy sales/assets, advanced P4 definitions/parallel stages, BM06 calendar/frontends, or beauty financial/resource ledgers.
Approaches considered: (a) paid snapshot + beauty lock is insufficient against Core/Pay writers; (b) shared distributed transaction conflicts with independent beauty/Pay deployment; (c) durable owner-local fences and original-operation saga is recommended. No RPC under owner locks; UNKNOWN retains protection. Pay protection is a Core-approved line/unit budget with a permanent managed-source marker, not a temporary whole-payment freeze that disappears at service completion.
Current `canStart=false` remains until the complete supported start chain is real. Identity facts, acceptance, source binding and paid receipts alone never enable it. Legacy managed-completion guards remain.
Public request quantities are expanded into separate qty=1 tasks by current opening AND ADD flows. Raw table/Mapper support for decimal COUNT or qty>1 is not a delivered workflow: reject unsupported historical task shapes at start, preserve facts, do not reinterpret quantity as resource capacity.
