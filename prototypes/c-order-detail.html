买家小程序 · 界面原型 · v2 2026-10-10（物流详情不自建：用微信插件）

订单详情：一眼看懂「货到哪、我该做什么」

v2 修两件在真机上才看出来的事：① 「查看物流」入口的条件写窄了 —— 只有微信插件可用时才给。插件现在确实通了（生产两条运单都拿到了 token），但非微信支付的单、H5 与 App 恒不可用，那几种情况一个入口都没有。改成只要有运单就给入口：插件可用就打开插件，不可用就地展开我们自己的轨迹。② 吸底条与页内按钮重复 —— 「再来一单 / 申请售后」同时出现在页尾那一排和吸底条里，某些状态下吸底条自己两颗还都是「再来一单」；现在操作只有一处：吸底条是唯一的操作区，页内不再排按钮。

01 — 04

四个状态，同一套骨架

从上到下恒定：① 状态头（大字状态 + 一句「接下来」+ 有运单就给「查看物流」）② 收货 / 自提 ③ 店铺 + 商品 ④ 金额 ⑤ 订单信息（单号 / 时间，可复制）⑥ 吸底操作条（随状态变，且只在这里）。状态头只铺最新一条轨迹；明细要么在微信插件那一屏（微信支付单），要么点「查看物流」就地展开（见 05）—— 不自建物流详情页。
05

「查看物流」两种落地，都不是新页

入口的显示条件是「这一单有运单」，不是「插件可用」。点下去分两种：微信支付的单交给微信物流插件（openWaybillTracking，全屏、微信自己维护）；其余的单（线下收款 / 余额支付，以及 H5 与 App）就地展开我们自己的轨迹。不自建物流详情页 —— 那等于把插件那一屏再抄一遍，同一份数据两套渲染，还多一个路由与一次发布依赖。
06

操作去重：吸底条是唯一的操作区

规则三条：① 页内不排按钮（页尾那排 .ops 整块删掉）；② 吸底条用库件 <sh-actionbar>（C 端统一贴底形态），主操作只有去支付 / 评价 / 再来一单三种，次要位最多再给一颗（取消 / 再来一单），主次必须不同；③ 有后续状态的事（退款、售后、发票）一律做成会回读状态的卡片行，不上吸底条 —— 它们都带「申请中 / 已处理 / 被驳回」的后续，钉在常驻条上既重复又每单都在问「是不是有问题」。下表是每个状态下吸底条给什么、哪些入口在卡片。
状态次要（左）主要（右）卡片行
待付款取消订单去支付—
待发货（无）再来一单退款 / 售后
运输中（无）再来一单查看物流 · 退款 / 售后
已完成 · 可评价再来一单发表评价查看物流 · 发票
已完成 · 评过（无）再来一单查看物流 · 发票
已取消 / 已退款（无）再来一单退款进度

重复出自三处：secondaryOp 与 primaryKey 都回落「再来一单」（已完成不可评价时吸底条两颗同名）；页尾 .ops 又无条件给一颗；售后（含退款）既在吸底条又在售后卡（运输中态两颗「申请售后」）。收敛后：吸底主操作只剩三种，售后/退款/发票全进卡片行，「再来一单」全页只出现一次，每行主次不同名。
